Lesson 1: Client-Server Communication and HTTP Fundamentals

Understand how frontend applications communicate with backend servers using HTTP, requests, responses and REST APIs.

1. Learning Objectives

After completing this lesson, you will be able to:

  • Explain client-server architecture.
  • Understand how browsers communicate with web servers.
  • Describe the HTTP request-response cycle.
  • Identify URLs, endpoints and query parameters.
  • Understand HTTP methods and their purposes.
  • Explain request headers, response headers and bodies.
  • Understand common HTTP status codes.
  • Differentiate HTTP and HTTPS.
  • Understand REST API fundamentals.
  • Inspect HTTP communication using browser Developer Tools.

2. What Is Client-Server Architecture?

Client-server architecture is a software architecture in which one system requests services or resources and another system provides them.

Client

A client is an application or device that sends requests to a server.

Examples:

  • Google Chrome
  • Mozilla Firefox
  • Mobile applications
  • Desktop applications
  • JavaScript frontend applications

Server

A server receives client requests, performs the required processing and returns responses.

Common server responsibilities include:

  • Authenticating users.
  • Processing application logic.
  • Reading and updating databases.
  • Validating incoming data.
  • Returning requested information.

Example: Online Shopping Application

  1. A user opens an online shopping website.
  2. The browser displays the frontend interface.
  3. The user clicks the Products button.
  4. JavaScript sends a request to the backend server.
  5. The server retrieves product information.
  6. The server sends a response.
  7. JavaScript processes the response and updates the page.
The frontend is generally responsible for the user interface and user interactions. The backend handles server-side processing, application rules and data access.

3. How Does Client-Server Communication Work?

In a typical web application, the browser and server communicate using HTTP or HTTPS.

Request-response cycle

       CLIENT (Browser)
              |
              |
        HTTP Request
              |
              v
       SERVER (Backend)
              |
              |
       Process Request
              |
              v
         Database
              |
              |
       Retrieve Data
              |
              v
       SERVER (Backend)
              |
              |
       HTTP Response
              |
              v
       CLIENT (Browser)
              |
              |
       Update Web Page

Step-by-step explanation

Step Operation
1 The client creates an HTTP request.
2 The request is transmitted over the network.
3 The server receives and processes the request.
4 The server may communicate with a database or another service.
5 The server creates an HTTP response.
6 The client receives and processes the response.
7 The frontend displays or updates the information.
HTTP is an application-layer protocol. Actual communication also depends on lower network layers, DNS resolution, transport connections and other networking mechanisms.

4. What Is HTTP?

HTTP stands for Hypertext Transfer Protocol. It is an application-layer protocol used to transfer information between clients and servers.

HTTP is commonly used to transfer:

  • HTML documents
  • CSS and JavaScript files
  • Images and other media
  • JSON data
  • API request and response data

Important characteristics of HTTP

  • Client-server model: Clients send requests and servers return responses.
  • Stateless protocol: Each request is treated independently at the protocol level.
  • Extensible: Headers allow additional information to be exchanged.
  • Media-independent: It can transfer different types of content.

What does stateless mean?

Stateless means HTTP does not automatically remember the previous request as part of the protocol's basic request model.

Applications can maintain user sessions through mechanisms such as cookies, session identifiers, tokens and server-side session storage.

HTTP being stateless does not mean websites cannot remember users. Session-management mechanisms provide continuity across requests.

5. What Is HTTPS?

HTTPS stands for Hypertext Transfer Protocol Secure. It uses HTTP over a secure connection provided by TLS.

HTTPS provides:

  • Encryption: Protects transmitted data from being read by unauthorized parties.
  • Integrity: Helps detect unauthorized modification of transmitted data.
  • Authentication: Uses digital certificates to authenticate the server's identity.
HTTP HTTPS
Does not provide TLS protection by itself. Uses TLS to protect communication.
Common default port: 80. Common default port: 443.
Data is not protected by TLS encryption. Communication is encrypted through TLS.
Used where secure transport is not configured. Recommended for modern websites and APIs.
HTTPS protects data in transit. It does not automatically make an application secure against vulnerabilities such as SQL injection, broken access control or cross-site scripting.

6. Understanding URLs and API Endpoints

A URL identifies a resource that a client can access. An API endpoint is a specific URL or route through which an API exposes a resource or operation.

Example URL

https://api.example.com:443/products/25?category=electronics
Component Value Meaning
Scheme https Communication protocol.
Host api.example.com Server hostname.
Port 443 Network port.
Path /products/25 Resource route.
Query parameter category=electronics Additional filtering information.

Common URL components

https://example.com/products?page=2&limit=10#results
  • https — scheme.
  • example.com — hostname.
  • /products — path.
  • page=2 — query parameter.
  • limit=10 — another query parameter.
  • #results — fragment identifier.

Example API endpoints

Endpoint Purpose
/api/users Access user resources.
/api/products Access product resources.
/api/orders Access order resources.
/api/products/25 Access a specific product.

7. HTTP Request Structure

An HTTP request contains information that tells the server what the client wants to do.

A typical HTTP request can contain:

  • Request method
  • Request target or path
  • HTTP version
  • Request headers
  • Optional request body

Example HTTP request

POST /api/users HTTP/1.1
Host: example.com
Content-Type: application/json
Accept: application/json

{
    "name": "Rahul",
    "email": "rahul@example.com"
}

Request components

Component Explanation
POST HTTP method indicating the requested operation.
/api/users Request target.
HTTP/1.1 HTTP version.
Host Identifies the target host in HTTP/1.1.
Content-Type Describes the format of the request body.
Accept Indicates acceptable response media types.
Request body Contains the user data being submitted.
The example shows the familiar HTTP/1.1 message format. HTTP/2 and HTTP/3 use different wire representations, although the same general request concepts remain useful.

8. HTTP Request Methods

HTTP methods describe the intended operation for a resource. They are also called HTTP verbs.

Method Purpose Example
GET Retrieve a resource. Get product details.
POST Submit data, often creating a resource or triggering an operation. Create a new user.
PUT Replace a resource's representation. Replace user information.
PATCH Apply a partial modification. Update a user's email.
DELETE Request removal of a resource. Delete a product.
HEAD Retrieve response headers without the response body. Check resource metadata.
OPTIONS Discover communication options supported by a resource. Inspect allowed methods.

GET example

GET /api/products/25 HTTP/1.1
Host: example.com
Accept: application/json

POST example

POST /api/products HTTP/1.1
Host: example.com
Content-Type: application/json

{
    "name": "Keyboard",
    "price": 1200
}

PUT versus PATCH

PUT generally replaces the target resource representation, while PATCH applies a partial modification according to the patch format or application-defined behavior.

Interview point: GET, PUT and DELETE are defined as idempotent methods. Repeating an idempotent request has the same intended effect on server state as making it once. POST is not generally idempotent.

GET is defined as a safe method, meaning it is intended for retrieval rather than changing server state.

9. HTTP Request Headers

Request headers provide additional information about the request, its content, the client and the expected response.

Common request headers

Header Purpose
Accept Specifies acceptable response media types.
Content-Type Specifies the media type of the request body.
Authorization Provides authentication credentials or tokens.
Cache-Control Provides caching directives.
Accept-Language Indicates preferred response languages.
User-Agent Identifies information about the requesting client.

Example

GET /api/profile HTTP/1.1
Host: example.com
Accept: application/json
Authorization: Bearer YOUR_ACCESS_TOKEN
Never place real passwords, private API keys or sensitive credentials directly in frontend source code. Browser JavaScript is visible to users. Authentication tokens also require appropriate storage and security practices.

10. HTTP Response Structure

The server returns an HTTP response after processing a request.

A typical response contains:

  • HTTP version
  • Status code
  • Status message or reason phrase, where applicable
  • Response headers
  • Optional response body

Example HTTP response

HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: no-cache

{
    "id": 25,
    "name": "Keyboard",
    "price": 1200
}

Response components

Component Explanation
HTTP/1.1 HTTP version.
200 HTTP status code.
OK Reason phrase in this HTTP/1.1 example.
Content-Type Identifies the response body's media type.
Response body Contains the returned product information.

11. HTTP Status Code Categories

HTTP status codes indicate the result of processing a request.

Category Range Meaning
1xx 100–199 Informational responses.
2xx 200–299 Successful responses.
3xx 300–399 Redirection responses.
4xx 400–499 Client error responses.
5xx 500–599 Server error responses.

Important status codes

Status Name Meaning
200 OK Request succeeded.
201 Created Request successfully created a resource.
202 Accepted Request accepted for processing, which may not be complete.
204 No Content Request succeeded without response content.
301 Moved Permanently Resource has a permanent redirect.
302 Found Temporary redirect.
304 Not Modified Cached representation may be reused.
400 Bad Request Request cannot be processed because of a client-side request problem.
401 Unauthorized Valid authentication credentials are missing or invalid.
403 Forbidden Server refuses to authorize the request.
404 Not Found Requested resource was not found.
405 Method Not Allowed HTTP method is not supported for that resource.
409 Conflict Request conflicts with the current resource state.
422 Unprocessable Content Request content cannot be processed semantically.
429 Too Many Requests Client has sent too many requests.
500 Internal Server Error Unexpected server-side failure.
502 Bad Gateway Gateway received an invalid response from an upstream server.
503 Service Unavailable Server is temporarily unable to handle the request.
504 Gateway Timeout Gateway did not receive a timely upstream response.
Placement point: Be able to distinguish 401 (authentication required or invalid) from 403 (the server refuses authorization), and 404 (resource not found) from 500 (server failure).

12. What Is REST API?

REST stands for Representational State Transfer. It is an architectural style for designing networked applications and APIs.

A RESTful API commonly exposes resources through URLs and uses HTTP methods to operate on those resources.

Example: Product API

HTTP Method Endpoint Operation
GET /api/products Retrieve all products.
GET /api/products/10 Retrieve product with ID 10.
POST /api/products Create a product.
PUT /api/products/10 Replace product 10.
PATCH /api/products/10 Partially update product 10.
DELETE /api/products/10 Delete product 10.

Important REST concepts

  • Resources: Data entities such as users, products and orders.
  • Resource identifiers: URLs that identify resources.
  • Stateless communication: Each request contains the information needed to process it.
  • Representations: Resources are transferred in representations such as JSON.
  • Uniform interface: Consistent interaction conventions for resources.
REST is an architectural style, not a programming language or a specific data format. JSON is commonly used by REST APIs, but REST does not require JSON.

13. What Happens When You Enter a Website URL?

When a user enters a website address into a browser, several operations occur before the page is displayed.

  1. URL processing: The browser interprets the URL.
  2. DNS lookup: The browser or operating system resolves the hostname to an IP address, if needed.
  3. Connection establishment: The browser establishes the required network connection.
  4. TLS handshake: For HTTPS, a secure connection is established.
  5. HTTP request: The browser sends a request to the server.
  6. Server processing: The server processes the request.
  7. HTTP response: The server returns a response.
  8. Resource processing: The browser processes HTML, CSS, JavaScript and other resources.
  9. Rendering: The browser constructs and displays the page.
This is a simplified model. DNS and connection information may already be cached, and modern browsers can reuse connections. HTTP/2 and HTTP/3 also change some transport and multiplexing details.

14. JavaScript's Role in Client-Server Communication

JavaScript allows frontend applications to communicate with backend APIs without requiring a complete page reload for every operation.

Common browser technologies include:

  • Fetch API: Sends HTTP requests and processes responses.
  • XMLHttpRequest: An older browser API for network requests.
  • JSON: A common format for exchanging structured data.
  • DOM: Updates the visible page using received data.
  • WebSocket: Supports bidirectional communication over a persistent connection.

Basic Fetch example

fetch("https://jsonplaceholder.typicode.com/users")
    .then(response => {
        console.log("Status:", response.status);

        return response.json();
    })
    .then(users => {
        console.log(users);
    })
    .catch(error => {
        console.error("Request failed:", error);
    });

This example sends a GET request to a demonstration API, converts the response body to JSON and displays the result.

Fetch normally rejects for network-level failures, but an HTTP error status such as 404 does not automatically reject the Fetch Promise. The response status must be checked separately.

Detailed Fetch API implementation, request configuration, response processing and error handling are covered in the following lessons.

15. What Is CORS?

CORS stands for Cross-Origin Resource Sharing. It is a browser security mechanism that controls whether frontend JavaScript can access resources from another origin.

What is an origin?

An origin consists of three components:

  • Scheme (protocol)
  • Hostname
  • Port

Two URLs have the same origin only when all three components match.

Example

URL Relationship to https://example.com
https://example.com/products Same origin.
https://api.example.com Different origin: hostname differs.
http://example.com Different origin: scheme differs.
https://example.com:8443 Different origin: port differs.

How does CORS work?

  1. A browser page sends a cross-origin request.
  2. The browser applies the same-origin policy and CORS rules.
  3. The server may return CORS response headers.
  4. The browser checks whether the response can be shared with the requesting origin.

Example response header:

Access-Control-Allow-Origin: https://myfrontend.com

This header tells the browser that the specified origin is permitted to access the response.

CORS is enforced by browsers. It is not a replacement for server-side authentication or authorization. A CORS error usually requires an appropriate server-side configuration, not simply changing frontend JavaScript.

16. Inspect HTTP Requests Using Developer Tools

Browser Developer Tools help frontend developers inspect requests, responses, headers, status codes and timing.

Steps in Google Chrome

  1. Open a website in Chrome.
  2. Press F12 or Ctrl + Shift + I.
  3. Select the Network tab.
  4. Reload the page.
  5. Click a request in the request list.
  6. Inspect the Headers, Payload, Preview and Response tabs.

Important Network panel information

Field What to inspect
Name Requested resource or endpoint.
Status HTTP response status code.
Type Resource type.
Initiator What triggered the request.
Size Transferred or resource size information.
Time Request timing information.

Practical debugging checklist

  • Is the request URL correct?
  • Is the correct HTTP method being used?
  • Are required request headers present?
  • Is the request payload correct?
  • What status code did the server return?
  • Does the response contain the expected data?
  • Is a CORS error being reported?
  • Is the request taking too long?

17. Common HTTP and API Mistakes

Mistake 1: Using GET to modify server data

GET should be used for retrieval. Use an appropriate method such as POST, PUT or PATCH for modifications.

Mistake 2: Confusing 401 and 403

401 indicates missing or invalid authentication credentials. 403 indicates the server refuses authorization.

Mistake 3: Treating every response as successful

A response object can be received with an HTTP error status. Always inspect the status or response.ok.

Mistake 4: Confusing Content-Type and Accept

Content-Type describes the representation being sent. Accept describes the response media types the client can accept.

Mistake 5: Assuming HTTP is stateful

HTTP is stateless at the protocol level. Applications implement sessions and authentication separately.

Mistake 6: Trying to fix CORS only in frontend code

CORS permission is communicated by the server through response headers. Frontend code cannot grant itself permission.

Mistake 7: Exposing secret credentials

Never hardcode private credentials or secret API keys in public frontend JavaScript.

18. Placement Interview Questions and Answers

Q1. What is client-server architecture?

It is an architecture in which a client sends requests and a server processes those requests and returns responses.

Q2. What is HTTP?

HTTP is an application-layer protocol used for communication between clients and servers.

Q3. What is HTTPS?

HTTPS is HTTP communication protected using TLS.

Q4. What does stateless mean in HTTP?

Each request is treated independently at the protocol level. Additional mechanisms such as cookies or tokens can maintain application sessions.

Q5. What is an API endpoint?

An endpoint is a URL or route through which an API exposes a resource or operation.

Q6. What is the difference between GET and POST?

GET is used to retrieve resources. POST submits data, often to create a resource or trigger processing.

Q7. What is the difference between PUT and PATCH?

PUT generally replaces a resource representation. PATCH applies a partial modification.

Q8. What is an HTTP header?

An HTTP header carries additional metadata about a request or response.

Q9. What is a request body?

It is optional content sent with a request, commonly containing JSON data for POST or PUT operations.

Q10. What is the difference between 401 and 403?

401 indicates an authentication problem. 403 indicates that the server refuses access.

Q11. What is a 404 status code?

It indicates that the requested resource was not found.

Q12. What is a 500 status code?

It indicates an unexpected internal server error.

Q13. What is REST?

REST is an architectural style for designing networked applications around resources and a uniform interface.

Q14. What is JSON?

JSON is a text-based data interchange format commonly used for exchanging structured data between frontend and backend applications.

Q15. What is CORS?

CORS is a browser security mechanism that uses server response headers to determine whether cross-origin responses may be shared with frontend JavaScript.

Q16. What is the purpose of the Authorization header?

It carries authentication credentials or tokens used by the server to identify or authenticate a request.

Q17. What is the difference between Content-Type and Accept?

Content-Type describes the media type of the message body. Accept indicates which response media types the client prefers.

Q18. What is the purpose of the Network tab?

It helps developers inspect HTTP requests, responses, headers, payloads, status codes and timing.

  • URLs identify resources and endpoints.
  • HTTP methods describe the intended operation.
  • Headers carry request and response metadata.
  • Status codes describe the result of request processing.
