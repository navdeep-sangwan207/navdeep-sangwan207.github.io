Handling API Responses, Status Codes and Errors

JavaScript Course | Chapter 11: Fetch API, JSON, Storage and Debugging

Lesson 4

1. Learning Objectives

After completing this lesson, you will be able to:

  • Understand the Fetch Response object.
  • Interpret common HTTP status codes.
  • Check HTTP request success using response.ok.
  • Handle HTTP errors separately from network errors.
  • Parse JSON responses safely.
  • Handle empty and invalid response bodies.
  • Implement reusable API error-handling functions.
  • Handle timeouts and request cancellation.
  • Debug API failures using browser Developer Tools.

2. Understanding the Fetch Response Object

When a Fetch request receives an HTTP response, its Promise fulfills with a Response object. This object contains information about the server response. 

fetch("https://jsonplaceholder.typicode.com/users/1")
    .then(response => {
        console.log(response);
    })
    .catch(error => {
        console.error(error);
    });

Important Response Properties

Property Description
response.status Returns the HTTP status code, such as 200 or 404.
response.statusText Returns the status message, when provided.
response.ok Returns true for HTTP status codes from 200 through 299.
response.headers Provides access to response headers.
response.url Returns the final response URL.
response.redirected Indicates whether the response followed a redirect.
response.type Describes the response type, such as basic, cors or opaque.

Example: Inspect Response Properties

fetch("https://jsonplaceholder.typicode.com/users/1")
    .then(response => {
        console.log("Status:", response.status);
        console.log("Status Text:", response.statusText);
        console.log("Success:", response.ok);
        console.log("URL:", response.url);
        console.log("Redirected:", response.redirected);
    })
    .catch(error => {
        console.error("Request failed:", error);
    });
Typical output: 
Status: 200
Status Text: OK
Success: true
URL: https://jsonplaceholder.typicode.com/users/1
Redirected: false

3. Understanding HTTP Status Codes

HTTP status codes indicate the result of an HTTP request. They are grouped into five major categories.

Range Category Meaning
100–199 Informational The request is continuing or has received preliminary information.
200–299 Success The request was successfully received and processed.
300–399 Redirection Further action is required, often involving another URL.
400–499 Client Error The request has a problem or cannot be fulfilled due to the client request.
500–599 Server Error The server failed to fulfill an apparently valid request.

Common HTTP Status Codes

Status Name Meaning
200 OK Request succeeded.
201 Created A resource was successfully created.
202 Accepted Request was accepted for processing but may not be completed.
204 No Content Request succeeded and the response has no content.
301 Moved Permanently The resource has a permanent new URL.
302 Found Temporary redirection.
304 Not Modified Cached representation can be reused.
400 Bad Request The request is invalid or malformed.
401 Unauthorized Valid authentication credentials are missing or invalid.
403 Forbidden The server refuses access to the requested resource.
404 Not Found The requested resource was not found.
405 Method Not Allowed The HTTP method is not supported for the resource.
409 Conflict The request conflicts with the current resource state.
422 Unprocessable Content The request content is understood but cannot be processed.
429 Too Many Requests The client has exceeded a rate limit.
500 Internal Server Error An unexpected server-side error occurred.
502 Bad Gateway A gateway received an invalid response from an upstream server.
503 Service Unavailable The server is temporarily unable to handle the request.
504 Gateway Timeout A gateway did not receive a timely upstream response.
Placement tip: Be particularly familiar with 200, 201, 204, 400, 401, 403, 404, 405, 409, 422, 429, 500, 502, 503 and 504.

4. Why Fetch Does Not Automatically Reject HTTP Errors

One of the most important concepts in Fetch API error handling is that HTTP errors and network errors are different.

If the server returns HTTP 404 or HTTP 500, Fetch generally fulfills its Promise with a Response object. It does not automatically enter the catch() block.

Example: HTTP 404 Response

fetch("https://jsonplaceholder.typicode.com/users/99999")
    .then(response => {
        console.log("Status:", response.status);
        console.log("Success:", response.ok);
    })
    .catch(error => {
        console.error("Network error:", error);
    });

Possible output:

Status: 404
Success: false

The catch block does not run merely because the server returned HTTP 404.

Difference Between HTTP and Network Errors

HTTP Error Network Error
Server returns an HTTP error status. The browser cannot successfully complete the request.
Fetch normally fulfills with a Response object. Fetch Promise rejects.
Check response.ok or status. Handle the rejected Promise.
Examples: 404, 500, 403. Examples: network failure, CORS blocking, aborted request.

5. Checking response.ok

The response.ok property is true when the HTTP status code is between 200 and 299. 

fetch("https://jsonplaceholder.typicode.com/users/1")
    .then(response => {

        if (!response.ok) {
            throw new Error(
                `HTTP Error: ${response.status}`
            );
        }

        return response.json();
    })
    .then(user => {
        console.log("User:", user.name);
    })
    .catch(error => {
        console.error("Error:", error.message);
    });

How It Works

  1. Fetch sends the request.
  2. The response is received.
  3. response.ok checks whether the status is successful.
  4. If false, an Error is thrown.
  5. The rejected Promise reaches the catch handler.
  6. If true, the response body is parsed as JSON.
Checking response.ok before parsing is a useful default pattern, but production applications may need to parse an error response body to display server validation messages.

6. Handling HTTP Errors Using Promise Chaining

The following example demonstrates how to distinguish an unsuccessful HTTP response from a network-level failure. 

function getUser(userId) {

    const url =
        `https://jsonplaceholder.typicode.com/users/${userId}`;

    return fetch(url)
        .then(response => {

            if (!response.ok) {
                throw new Error(
                    `Request failed with status ${response.status}`
                );
            }

            return response.json();
        })
        .then(user => {
            console.log("User Name:", user.name);
            console.log("Email:", user.email);
            return user;
        })
        .catch(error => {
            console.error("Unable to get user:", error.message);
            throw error;
        });
}

getUser(1);

Why Throw the Error Again?

The function logs the error and rethrows it. This allows the calling code to handle the failure as well. 

getUser(1)
    .then(user => {
        console.log("User loaded successfully.");
    })
    .catch(error => {
        console.log("Caller handled:", error.message);
    });
If you handle an error and do not rethrow it, the Promise chain may fulfill with the value returned by the catch callback. Rethrow when the caller must also know that the operation failed.

7. Handling Different HTTP Status Codes

Some applications display different messages depending on the status returned by the backend.

Example: Status-Based Error Messages

function getErrorMessage(status) {

    switch (status) {

        case 400:
            return "Invalid request data.";

        case 401:
            return "Please log in.";

        case 403:
            return "You do not have permission.";

        case 404:
            return "Requested resource was not found.";

        case 409:
            return "A resource conflict occurred.";

        case 422:
            return "Validation failed.";

        case 429:
            return "Too many requests. Try again later.";

        case 500:
            return "Internal server error.";

        case 503:
            return "Service temporarily unavailable.";

        default:
            return "An unexpected HTTP error occurred.";
    }
}

const status = 404;

console.log(getErrorMessage(status));
Expected output: 
Requested resource was not found.

Important Distinction: 401 vs 403

  • 401: Authentication is required or the supplied credentials are invalid.
  • 403: The server refuses access, even though the request may be authenticated.

8. Safely Parsing JSON Responses

An API may return valid JSON, invalid JSON, plain text or an empty response body. A frontend should not assume every response contains JSON.

Example: Handling JSON Parsing Errors

fetch("https://jsonplaceholder.typicode.com/users/1")
    .then(response => {

        if (!response.ok) {
            throw new Error(
                `HTTP Error: ${response.status}`
            );
        }

        return response.json();
    })
    .then(data => {
        console.log("Parsed Data:", data);
    })
    .catch(error => {
        console.error("Request or parsing error:", error.message);
    });

If the response body is not valid JSON, the Promise returned by response.json() rejects.

Handling an Empty Response

A successful HTTP 204 response has no content. Calling response.json() on an empty body will normally produce a parsing error. 

fetch("/api/users/1", {
    method: "DELETE"
})
.then(response => {

    if (!response.ok) {
        throw new Error(
            `HTTP Error: ${response.status}`
        );
    }

    if (response.status === 204) {
        console.log("Deleted successfully. No response body.");
        return null;
    }

    return response.json();
})
.then(data => {
    if (data !== null) {
        console.log(data);
    }
})
.catch(error => {
    console.error(error.message);
});
Do not assume every DELETE request returns 204. Follow the API documentation and inspect the actual response status and body.

9. Reading Error Details from an API

Many backend APIs return structured error information when validation or business rules fail.

Example error response:

{
    "message": "Validation failed",
    "errors": {
        "email": "Email address is required",
        "password": "Password is too short"
    }
}

Example: Read the Error Response Body

fetch("/api/register", {
    method: "POST",

    headers: {
        "Content-Type": "application/json"
    },

    body: JSON.stringify({
        email: "",
        password: "123"
    })
})
.then(async response => {

    const data = await response.json();

    if (!response.ok) {
        throw new Error(
            data.message || `HTTP Error: ${response.status}`
        );
    }

    return data;
})
.then(result => {
    console.log("Registration:", result);
})
.catch(error => {
    console.error("Registration failed:", error.message);
});

This example assumes the API returns JSON for both successful and unsuccessful responses.

In production, check the response Content-Type before parsing JSON when an API may return different response formats.

10. Checking Response Content-Type

The response Content-Type header describes the format of the response body. 

fetch("https://jsonplaceholder.typicode.com/users/1")
    .then(async response => {

        const contentType =
            response.headers.get("content-type");

        if (!response.ok) {
            throw new Error(
                `HTTP Error: ${response.status}`
            );
        }

        if (contentType &&
            contentType.includes("application/json")) {

            return response.json();
        }

        return response.text();
    })
    .then(data => {
        console.log("Response Data:", data);
    })
    .catch(error => {
        console.error(error.message);
    });

Why Is This Useful?

  • An API may return JSON for successful requests.
  • A proxy or server may return an HTML error page.
  • Some endpoints return plain text.
  • Checking Content-Type helps select the correct parsing method.

11. Creating a Reusable API Request Function

In professional frontend applications, the same error handling logic should not be repeated for every API call. A reusable API function improves consistency and maintainability.

Reusable Fetch Function

async function apiRequest(url, options = {}) {

    const response = await fetch(url, options);

    const contentType =
        response.headers.get("content-type") || "";

    let data = null;

    if (response.status !== 204) {

        if (contentType.includes("application/json")) {
            data = await response.json();
        } else {
            data = await response.text();
        }
    }

    if (!response.ok) {

        const message =
            data && typeof data === "object"
                ? data.message || `HTTP Error: ${response.status}`
                : data || `HTTP Error: ${response.status}`;

        throw new Error(message);
    }

    return data;
}

// GET request
apiRequest(
    "https://jsonplaceholder.typicode.com/users/1"
)
.then(data => {
    console.log(data);
})
.catch(error => {
    console.error(error.message);
});

Advantages

  • Centralizes HTTP error handling.
  • Reduces repeated Fetch code.
  • Supports JSON and text responses.
  • Handles 204 No Content responses.
  • Makes API calls easier to maintain.
This is a practical starting point, not a complete production HTTP client. A real application may also need authentication, request timeouts, schema validation, retry policies and more detailed error types.

12. Handling Network Errors

Network errors occur when Fetch cannot successfully complete the request.

Possible causes include:

  • No internet connection.
  • DNS resolution failure.
  • Server is unreachable.
  • Browser blocks access because of CORS.
  • The request is aborted.

Example

fetch("https://invalid-domain-example.test/api")
    .then(response => response.json())
    .then(data => {
        console.log(data);
    })
    .catch(error => {
        console.error("Network failure:", error.message);
    });

The invalid domain is used intentionally to demonstrate a network-level failure.

Important: A CORS failure can appear as a rejected Fetch Promise, but JavaScript often cannot inspect the underlying reason in detail. Use the browser Console and Network panel for further diagnosis.

13. Handling Request Timeouts

An application may need to stop waiting for an API request after a specified time.

Fetch does not provide a dedicated timeout option. A common approach is to use AbortController with setTimeout().

Example: Request Timeout

async function fetchWithTimeout(url, timeout = 5000) {

    const controller = new AbortController();

    const timer = setTimeout(() => {
        controller.abort();
    }, timeout);

    try {

        const response = await fetch(url, {
            signal: controller.signal
        });

        if (!response.ok) {
            throw new Error(
                `HTTP Error: ${response.status}`
            );
        }

        return await response.json();

    } catch (error) {

        if (error.name === "AbortError") {
            throw new Error("Request timed out or was cancelled.");
        }

        throw error;

    } finally {
        clearTimeout(timer);
    }
}

fetchWithTimeout(
    "https://jsonplaceholder.typicode.com/users",
    5000
)
.then(data => {
    console.log(data);
})
.catch(error => {
    console.error(error.message);
});

How It Works

  1. Create an AbortController.
  2. Start a timeout using setTimeout().
  3. Pass the controller signal to Fetch.
  4. If the timeout expires, abort the request.
  5. Handle the resulting AbortError.
  6. Clear the timeout in finally.
The example uses a fixed timeout. A request can also be cancelled manually, so a more advanced application may distinguish user cancellation from an actual timeout.

14. Retry Logic for Temporary Failures

Some API failures are temporary. For example, a service may temporarily return HTTP 503 or a network request may fail.

A retry mechanism can attempt the request again. However, retrying every request is not always safe.

Example: Retry a GET Request

function delay(ms) {
    return new Promise(resolve => {
        setTimeout(resolve, ms);
    });
}

async function fetchWithRetry(url, attempts = 3) {

    for (let attempt = 1; attempt <= attempts; attempt++) {

        try {

            const response = await fetch(url);

            if (!response.ok) {
                throw new Error(
                    `HTTP Error: ${response.status}`
                );
            }

            return await response.json();

        } catch (error) {

            if (attempt === attempts) {
                throw error;
            }

            console.log(`Attempt ${attempt} failed. Retrying...`);

            await delay(1000 * attempt);
        }
    }
}

fetchWithRetry(
    "https://jsonplaceholder.typicode.com/users",
    3
)
.then(data => {
    console.log("Data received:", data);
})
.catch(error => {
    console.error("All attempts failed:", error.message);
});

Production Considerations

  • Retry only appropriate temporary failures.
  • Do not retry invalid requests such as most HTTP 400 errors.
  • Respect server-provided Retry-After information when applicable.
  • Use exponential backoff and possibly random jitter.
  • Be careful when retrying POST or other operations that may create side effects.
  • Use idempotency mechanisms when supported by the API.
HTTP GET is generally idempotent, so repeating it has the same intended effect. POST is not generally idempotent. A retry may create duplicate resources unless the backend supports an idempotency key or equivalent protection.

15. Handling Errors in Frontend Applications

A frontend application should communicate errors clearly instead of leaving users with a blank screen.

Example: Display an API Error Message

<h2>User Information</h2>
<button id="loadBtn">Load User</button>
<p id="message"></p>
<div id="userInfo"></div>

<script>
const loadBtn = document.getElementById("loadBtn");
const message = document.getElementById("message");
const userInfo = document.getElementById("userInfo");

loadBtn.addEventListener("click", async () => {

    message.textContent = "Loading...";
    userInfo.textContent = "";

    try {

        const response = await fetch(
            "https://jsonplaceholder.typicode.com/users/1"
        );

        if (!response.ok) {
            throw new Error(
                `Unable to load user. Status: ${response.status}`
            );
        }

        const user = await response.json();

        message.textContent = "User loaded successfully.";

        userInfo.textContent =
            `${user.name} - ${user.email}`;

    } catch (error) {

        message.textContent = error.message;

    }
});
</script>

This example uses textContent to display API-provided values safely as text.

16. Debugging API Requests in Chrome

Chrome Developer Tools provides useful information for diagnosing API problems.

Network Tab

  1. Open the webpage in Chrome.
  2. Press F12 or Ctrl + Shift + I.
  3. Select the Network tab.
  4. Filter requests using Fetch/XHR.
  5. Trigger the API request again.
  6. Select the relevant request.
  7. Inspect Headers, Payload, Preview and Response.

What to Inspect

Section What to Check
General Request URL, method and status code.
Request Headers Content-Type, Accept and Authorization.
Payload Request body sent to the server.
Response Headers Content-Type and CORS-related headers.
Preview Formatted response data.
Response Raw response content.
Timing Request duration and network timing details.

Common Debugging Situations

  • 404: Verify the endpoint and resource ID.
  • 401: Check authentication credentials.
  • 403: Check permissions and access rules.
  • 400: Inspect request parameters and body.
  • 500: Investigate the backend error.
  • CORS error: Check server CORS configuration.
  • Network failure: Check connectivity and server availability.

17. Common Mistakes

Mistake 1: Not Checking response.ok

// Incorrect
fetch("/api/users")
    .then(response => response.json());

// Better
fetch("/api/users")
    .then(response => {
        if (!response.ok) {
            throw new Error(`HTTP ${response.status}`);
        }

        return response.json();
    });

Mistake 2: Assuming Every Response Contains JSON

A 204 response or a plain-text error response may not contain valid JSON. Check the response contract and Content-Type before parsing.

Mistake 3: Swallowing Errors

// Avoid silently hiding failures
fetch("/api/users")
    .catch(error => {
        console.log(error);
    });

Log useful diagnostic information and communicate an appropriate failure to the calling code or user. Rethrow errors when callers must handle them.

Mistake 4: Retrying Every Failed Request

Repeating a request for an invalid URL or invalid input usually does not fix the problem. Retry only when the failure is likely to be temporary and the operation is safe.

Mistake 5: Displaying Raw Internal Error Details

Backend stack traces, database errors and sensitive diagnostic information should not be exposed to ordinary users. Show a suitable message and keep technical diagnostics in secure logs.

18. Placement Interview Questions and Answers

Q1. What is a Response object in Fetch?

Answer: It represents the HTTP response received from the server and provides status information, headers and methods to read the response body.

Q2. What does response.ok return?

Answer: A Boolean value. It is true for HTTP status codes from 200 to 299 and false otherwise.

Q3. Why does Fetch not reject on HTTP 404?

Answer: HTTP error statuses are valid HTTP responses. Fetch fulfills with the Response object. Developers must check the status explicitly.

Q4. What is the difference between HTTP and network errors?

Answer: HTTP errors are server responses with unsuccessful status codes. Network errors prevent Fetch from successfully completing the request and normally reject its Promise.

Q5. What does HTTP 204 mean?

Answer: The request succeeded, but the response contains no content.

Q6. What is the difference between HTTP 401 and 403?

Answer: 401 indicates missing or invalid authentication credentials. 403 indicates the server refuses access to the requested resource.

Q7. How do you handle a 404 response?

Answer: Check the response status or response.ok, then throw or return a suitable application error for the calling code to handle.

Q8. What happens if response.json() receives invalid JSON?

Answer: The Promise returned by response.json() rejects with a parsing error.

Q9. What is the purpose of finally?

Answer: The finally block executes after a Promise chain settles, whether fulfilled or rejected. It is useful for cleanup operations.

Q10. How can you implement a Fetch timeout?

Answer: Use AbortController with a timer. When the timeout expires, call controller.abort().

Q11. Why should an API response Content-Type be checked?

Answer: It helps determine whether the response should be parsed as JSON, text or another format.

Q12. What is a reusable API function?

Answer: It is a shared function that centralizes common request behavior such as response parsing and error handling.

Q13. What is retry logic?

Answer: It attempts a request again after certain temporary failures, subject to retry limits and operation safety.

Q14. What is an idempotent HTTP method?

Answer: An idempotent method has the same intended server effect when the same request is repeated multiple times as when it is performed once. GET, PUT and DELETE are defined as idempotent methods in HTTP semantics.

Q15. How do you debug a failed API request?

Answer: Use the browser Network tab to inspect the request URL, method, headers, payload, response, status and timing. Use the Console to inspect JavaScript errors.

21. Lesson Summary

  • Fetch returns a Response object when an HTTP response is received.
  • response.status provides the HTTP status code.
  • response.ok indicates whether the status is in the 200–299 range.
  • HTTP errors do not automatically reject the Fetch Promise.
  • Network failures and aborted requests normally reject the Promise.
  • Use throw to propagate unsuccessful HTTP responses as application errors.
  • Use response.json() to parse JSON and handle invalid or empty bodies.
  • Use Content-Type to determine the response format.
  • Use AbortController for request cancellation and timeout handling.
  • Retry temporary failures carefully and consider idempotency.
  • Use Chrome Developer Tools to debug API requests.

You should now be able to inspect API responses, interpret HTTP status codes and implement structured error handling in JavaScript applications.
