Chapter 10: Asynchronous JavaScript, Promises and Event Loop

Lesson 7: Event Loop, Call Stack and Task Queues

Understand how JavaScript executes synchronous code, handles asynchronous callbacks, and coordinates the call stack, browser APIs, task queues and event loop.

1. Learning Objectives

After completing this lesson, you will be able to:

  • Explain JavaScript's single-threaded execution model.
  • Understand the call stack and execution contexts.
  • Explain the role of browser Web APIs.
  • Understand callback scheduling and task queues.
  • Explain how the event loop coordinates execution.
  • Trace setTimeout() and Promise-based execution.
  • Predict output in event-loop interview questions.
  • Understand how blocking JavaScript affects browser responsiveness.

2. JavaScript Execution Model

JavaScript code is executed by a JavaScript engine. In a typical browser environment, JavaScript code in a given execution context runs on a single main thread.

This means ordinary JavaScript statements execute one at a time on that thread. The browser environment provides APIs and scheduling mechanisms that allow asynchronous operations to complete without requiring the JavaScript thread to wait continuously.

Example: Synchronous execution

console.log("First");

console.log("Second");

console.log("Third");
First
Second
Third

Each statement executes in order. The next statement begins after the previous statement completes.

Single-threaded does not mean no asynchronous operations

JavaScript can coordinate timers, network requests, user events and other asynchronous operations through its host environment. Their callbacks are scheduled to run when the JavaScript execution context can process them.

The ECMAScript language defines JavaScript execution semantics and Promise behavior. Browser APIs such as DOM events, timers and Fetch are provided by the browser environment, not by ECMAScript itself.

3. What Is the Call Stack?

The call stack is a Last In, First Out (LIFO) structure used by the JavaScript engine to keep track of currently executing function calls.

When a function is called, its execution context is pushed onto the stack. When the function finishes, its context is popped from the stack.

Example: Function calls

function first() {
    console.log("First function");
    second();
}

function second() {
    console.log("Second function");
    third();
}

function third() {
    console.log("Third function");
}

first();

console.log("Program completed");

Expected output:

First function
Second function
Third function
Program completed

4. Execution Context and Call Stack

An execution context is the environment in which JavaScript code is evaluated. It contains information required to execute that code, such as its bindings and execution state.

Common execution context categories include:

Execution context Purpose
Global execution context Created for the top-level script execution.
Function execution context Created when a function is invoked.
Module execution context Used when JavaScript code is evaluated as a module.

Example

const globalMessage = "Global";

function showMessage() {
    const localMessage = "Function";

    console.log(globalMessage);
    console.log(localMessage);
}

showMessage();
Global
Function

The global script has its execution context. Calling showMessage() creates a function execution context that is placed on the call stack.

5. What Are Web APIs?

Web APIs are capabilities provided by the browser environment. They allow JavaScript applications to interact with the browser and external resources.

Examples include:

  • setTimeout() and setInterval().
  • DOM event handling such as click and keyboard events.
  • fetch() for network requests.
  • Browser storage APIs.
  • Geolocation and other browser capabilities.

Example: Timer callback

console.log("Start");

setTimeout(() => {
    console.log("Timer callback");
}, 1000);

console.log("End");

Expected output:

Start
End
Timer callback
The callback runs after its timer becomes eligible and the event loop can process it.

The browser manages the timer. When its delay has elapsed, the callback becomes eligible to run through the task scheduling mechanism. It does not interrupt synchronous JavaScript that is already executing.

6. What Are Task Queues?

Asynchronous callbacks are scheduled for later execution. In the browser event loop model, tasks are selected from task queues when the JavaScript execution context is ready.

A task can represent work such as a timer callback, a user interaction event or another browser-scheduled operation.

Examples of task-producing operations

Operation Example callback
Timer setTimeout(callback, 1000)
Interval setInterval(callback, 1000)
DOM event Button click handler
Message event Message event callback
Browser task scheduling is more detailed than one universal FIFO queue. Different task sources may have separate queues and scheduling rules. For interview-level tracing, focus on synchronous execution, Promise microtasks and timer tasks.

7. What Is the Event Loop?

The event loop is the scheduling mechanism that coordinates JavaScript execution with queued tasks and microtasks in the host environment.

At a simplified browser level, its responsibilities include:

  • Allowing the current JavaScript task to finish.
  • Processing the microtask queue at the appropriate checkpoint.
  • Selecting another eligible task when the environment can proceed.
  • Coordinating with browser rendering opportunities.

Simplified event loop diagram

This diagram is a simplified teaching model. The browser's actual event-loop processing includes task sources, microtask checkpoints and rendering steps.

8. How the Event Loop Handles setTimeout()

A timer callback does not execute immediately when setTimeout() is called. The timer establishes a minimum delay before the callback becomes eligible for scheduling.

Example: Timer and synchronous statements

console.log("A");

setTimeout(() => {
    console.log("B");
}, 0);

console.log("C");

Expected output:

A
C
B

Execution explanation:

  1. The first statement prints A.
  2. The timer callback is registered.
  3. The final synchronous statement prints C.
  4. After the current task finishes, the timer callback can run when eligible.
Interview point: A zero-millisecond timer does not mean immediate execution. It means the callback becomes eligible after the minimum delay, subject to scheduling and current execution.

9. Event Loop with Nested Function Calls

function first() {

}

Expected output:

First
Second
Third
First completed
Global completed
Timer callback

The timer callback cannot interrupt the active call stack. The nested function calls and remaining synchronous statements finish first.

10. Event Loop with Promises

Promise handlers such as .then(), .catch() and .finally() are scheduled as microtasks.

In the browser model, after the current task completes, microtasks are processed at a microtask checkpoint before the event loop proceeds to another task.

Example: Promise and timer

console.log("Start");

setTimeout(() => {
    console.log("Timer");
}, 0);

Promise.resolve().then(() => {
    console.log("Promise");
});

console.log("End");

Expected output:

Start
End
Promise
Timer

Execution sequence:

  1. Start is printed.
  2. The timer callback is scheduled as a task.
  3. The Promise handler is scheduled as a microtask.
  4. End is printed.
  5. The current task finishes and the microtask runs.
  6. The timer callback runs when its task is selected and eligible.

11. Blocking the Call Stack

A long-running synchronous operation blocks the JavaScript thread from processing other JavaScript work on that thread. This can make a browser interface unresponsive.

Example: Blocking synchronous loop

console.log("Start");

const start = Date.now();

while (Date.now() - start < 2000) {
    // Busy waiting for approximately two seconds
}

console.log("Loop completed");

setTimeout(() => {
    console.log("Timer callback");
}, 0);

console.log("End");

Expected output order:

Start
Loop completed
End
Timer callback

The loop occupies the JavaScript thread. No timer callback or other ordinary JavaScript callback can execute on that thread until the loop finishes.

Do not use busy waiting in real applications. It wastes CPU time and can make the browser unresponsive.

12. Browser Rendering and JavaScript

In a browser, JavaScript execution is coordinated with rendering opportunities. Long-running JavaScript can delay visual updates and user interaction.

Examples of work that can affect responsiveness include:

  • Large synchronous loops.
  • Expensive calculations on the main thread.
  • Repeated DOM updates.
  • Excessively long event handlers.
  • Large amounts of work performed in one task.

Practical performance techniques

  • Break large jobs into smaller chunks when appropriate.
  • Use Web Workers for suitable CPU-intensive computations.
  • Avoid unnecessary DOM operations.
  • Use efficient algorithms and data structures.
  • Keep event handlers short.
Web Workers run JavaScript in separate worker contexts and communicate with the main thread through messaging. They do not directly manipulate the document DOM.

13. Practical Example: Button Click and Event Loop

A browser click handler is scheduled in response to a user interaction. The following code demonstrates synchronous execution and a timer inside an event handler. 

const button = document.querySelector("#loadButton");

button.addEventListener("click", () => {
    console.log("Button clicked");

    setTimeout(() => {
        console.log("Loading completed");
    }, 1000);

    console.log("Click handler finished");
});

Output after clicking the button:

Button clicked
Click handler finished
Loading completed
The final message appears after approximately one second or later.

The event handler runs as a task. The timer callback is scheduled separately and does not interrupt the handler.

14. Call Stack Overflow

A call stack has limited capacity. Excessive nested function calls, especially uncontrolled recursion, can exceed that capacity and cause a stack overflow error.

Example: Infinite recursion

function repeat() {
    repeat();
}

repeat();

Typical browser error:

RangeError: Maximum call stack size exceeded

Correct approach: Use a base condition

function countDown(number) {
    if (number <= 0) {
        console.log("Finished");
        return;
    }

    console.log(number);

    countDown(number - 1);
}

countDown(3);
3
2
1
Finished

A base condition prevents uncontrolled recursion and allows function calls to return normally.

15. Common Mistakes and Debugging

Mistake 1: Assuming setTimeout(..., 0) executes immediately

A timer callback runs only after the current synchronous task finishes and the callback becomes eligible for scheduling.

Mistake 2: Assuming asynchronous callbacks interrupt the call stack

Ordinary callbacks do not interrupt currently executing synchronous JavaScript on the same thread.

Mistake 3: Assuming every asynchronous operation uses the same queue

Browser scheduling includes different task sources and microtask processing. Promise handlers are microtasks, while timer callbacks are tasks.

Mistake 4: Assuming Web APIs are part of the JavaScript language

Browser APIs are supplied by the browser environment. JavaScript engines implement the language, while the host provides capabilities such as timers and DOM events.

Mistake 5: Writing long synchronous operations

Long-running synchronous work can block the main thread and make the user interface unresponsive.

Mistake 6: Confusing the call stack with the task queue

The call stack tracks currently executing function calls. Task queues hold scheduled work that can be processed later.

16. Placement Interview Questions and Answers

Q1. Is JavaScript single-threaded?

JavaScript execution in a typical browser main-thread context is single-threaded. Browsers can perform other work using separate internal threads and worker contexts.

Q2. What is the call stack?

It is a LIFO structure that tracks active function calls and their execution contexts.

Q3. What is an execution context?

It is the environment in which JavaScript code is evaluated, containing the bindings and execution state needed by that code.

Q4. What are Web APIs?

They are browser-provided capabilities such as timers, DOM events, Fetch and browser storage.

Q5. What is the event loop?

It coordinates execution by allowing scheduled tasks and microtasks to be processed when the JavaScript execution context can run them.

Q6. What happens when setTimeout() is called?

The timer is registered with the host environment. After its minimum delay, the callback becomes eligible to be scheduled as a task. It does not interrupt the current call stack.

Q7. Why does setTimeout(callback, 0) not execute immediately?

The callback must wait until the current task finishes and the timer callback is eligible for processing.

Q8. What is the difference between the call stack and task queue?

The call stack contains currently executing function calls. The task queue contains scheduled callbacks waiting for an opportunity to execute.

Q9. Where are Promise handlers scheduled?

Promise reaction handlers are scheduled as microtasks and run at a microtask checkpoint.

Q10. What causes a stack overflow?

Excessive nested function calls, commonly caused by recursion without a proper base condition, can exceed the call stack limit.

Q11. Why can long synchronous code make a browser unresponsive?

It occupies the main JavaScript thread and delays event handlers, rendering-related work and other JavaScript tasks.

Q12. Are Web APIs part of ECMAScript?

No. They are supplied by the host environment, such as a browser. ECMAScript defines the JavaScript language itself.

Q13. Does the event loop execute callbacks while the call stack is busy?

No. Ordinary JavaScript callbacks on the same thread wait until the currently executing JavaScript work yields.

Q14. What is the role of the browser rendering process?

The browser coordinates rendering opportunities with event-loop processing. Long-running JavaScript can delay visual updates.

18. Practical Coding Exercises

Exercise 1: Call Stack Tracing

  • Create three functions that call one another.
  • Display messages before and after each nested call.
  • Trace the order of function execution.

Exercise 2: Timer Scheduling

  • Print a synchronous message.
  • Schedule two callbacks using setTimeout().
  • Print another synchronous message.
  • Predict and verify the output order.

Exercise 3: Promise and Timer Execution

  • Schedule a timer callback.
  • Create a resolved Promise with a then handler.
  • Print synchronous messages before and after both operations.
  • Explain why the Promise handler runs before the timer callback.

Exercise 4: Avoid Blocking the Main Thread

  • Create a large synchronous loop.
  • Schedule a timer before the loop.
  • Observe when the timer callback executes.
  • Explain how blocking affects browser responsiveness.

Exercise 5: Prevent Stack Overflow

  • Write a recursive countdown function.
  • Use a correct base condition.
  • Display each countdown value.
  • Compare it with uncontrolled recursion.

Exercise 6: Browser Event Handling

  • Create a button in an HTML page.
  • Attach a click event listener.
  • Inside the handler, schedule a timer and print synchronous messages.
  • Observe the execution order in the browser console.

19. Lesson Summary

  • JavaScript executes ordinary code on a call stack.
  • The call stack follows LIFO behavior.
  • Function calls create execution contexts.
  • Browser APIs provide timers, DOM events and network capabilities.
  • Asynchronous callbacks are scheduled for later execution.
  • The event loop coordinates tasks and microtasks.
  • Timer callbacks do not interrupt synchronous execution.
  • Promise handlers run as microtasks.
  • Long-running synchronous code blocks the main JavaScript thread.
  • Excessive recursion can cause a stack overflow.
  • Web Workers can run suitable JavaScript work in separate worker contexts.
Placement preparation focus: Master call-stack tracing, timer scheduling, Promise execution, event-loop diagrams and output-based questions. These concepts are essential for JavaScript frontend interviews and asynchronous coding rounds.
