1. Introduction to the AUTOSAR Development Workflow

The AUTOSAR development workflow describes how automotive embedded software is specified, designed, configured, implemented, integrated, tested and released.

It provides a structured approach for developing software components and integrating them with the AUTOSAR Classic Platform.

1.1 Main Development Activities

  • Requirement analysis
  • System architecture design
  • Software component development
  • ARXML description and configuration
  • RTE generation
  • BSW and MCAL configuration
  • Software implementation
  • ECU integration
  • Verification and validation
  • Release and maintenance

The workflow is iterative. Changes in requirements, architecture or configuration may require updates to earlier development activities and regenerated artifacts.

3. Requirement Analysis

Requirement analysis identifies what the automotive ECU must do and the constraints under which it must operate.

3.1 Types of Requirements

Requirement Type Description
Functional Defines the functions the ECU must perform.
Performance Defines timing, response and resource constraints.
Interface Defines communication with other components or ECUs.
Safety Defines applicable safety objectives and constraints.
Diagnostic Defines fault detection and diagnostic behavior.

3.2 Example: Cooling Fan ECU

Example functional requirements:

  • Read engine temperature from the configured input.
  • Activate the cooling fan when temperature exceeds a threshold.
  • Deactivate the fan when the temperature falls below a defined threshold.
  • Report configured sensor faults.
  • Transmit fan status through the configured communication network.
Requirements should be measurable and testable. For example, a requirement should define the expected temperature threshold, timing and fan response rather than simply stating that the fan must operate correctly.

4. System Architecture Design

System architecture describes how functions are distributed across ECUs and how those ECUs communicate.

4.1 Architecture Activities

  • Identify vehicle-level functions.
  • Identify required ECUs.
  • Allocate software components to ECUs.
  • Define communication interfaces.
  • Define network signals and messages.
  • Identify hardware and software dependencies.

5. Software Component Development

AUTOSAR application software is organized into Software Components (SWCs).

5.1 SWC Design Activities

  • Identify application software functions.
  • Define atomic software components.
  • Create component ports.
  • Define sender-receiver or client-server interfaces.
  • Define data elements and operations.
  • Define runnable entities.
  • Configure events and execution behavior.

5.2 Example SWCs

SWC Responsibility
TemperatureSensor_SWC Processes temperature input.
FanControl_SWC Determines fan operating state.
Diagnostic_SWC Provides application-level diagnostic behavior where required.

6. ARXML Description and Configuration

The AUTOSAR architecture and configuration are represented using ARXML descriptions.

6.1 Main Activities

  1. Create or import SWC descriptions.
  2. Define ports and interfaces.
  3. Describe system-level architecture.
  4. Allocate components to ECUs.
  5. Prepare ECU-specific information.
  6. Configure communication and BSW modules.
  7. Validate references and configuration consistency.

Configuration tools can use these descriptions to generate ECU-specific software infrastructure and configuration artifacts.

7. RTE and BSW Configuration

7.1 RTE Configuration

The RTE provides communication between application software components and the underlying software infrastructure.

  • Configure component connections.
  • Map runnable entities to OS tasks.
  • Configure communication behavior.
  • Generate RTE source and header files.
  • Review generator diagnostics.

7.2 BSW Configuration

BSW configuration establishes the required ECU software services and hardware abstraction.

  • Configure operating system modules.
  • Configure communication stack modules.
  • Configure diagnostic services.
  • Configure ECU management.
  • Configure MCAL and hardware drivers.
  • Validate module dependencies.

8. Software Implementation and Build

After architecture and configuration activities, developers implement application logic and integrate generated software with the required platform packages.

8.1 Implementation Activities

  • Write application C code.
  • Use generated RTE interfaces as specified by the toolchain.
  • Integrate BSW and MCAL packages.
  • Configure compiler and linker settings.
  • Build the ECU software.
  • Resolve compilation and linking errors.

8.2 Build Output

Depending on the project toolchain, build outputs may include:

  • Object files (.o or .obj)
  • Executable or ELF files
  • HEX files
  • Map files
  • Debug information

9. Introduction to the V-Model / V-Cycle

The V-Model is a development and verification approach in which development activities on the left side of the V are associated with corresponding verification and validation activities on the right side.

The bottom of the V represents implementation and integration activities. Testing progresses upward on the right side.

9.1 V-Cycle Diagram

The diagram is a simplified representation. Actual automotive projects may use additional levels, such as hardware testing, software qualification, safety validation and vehicle testing.

10. Left Side of the V-Cycle: Development

10.1 Requirement Definition

The customer and system requirements define expected ECU functions, performance and constraints.

10.2 System Design

System design defines the ECU architecture, hardware allocation, software functions and communication interfaces.

10.3 Software Architecture

Software architecture defines the software components, their relationships, interfaces and execution concepts.

10.4 Detailed Design and Implementation

Detailed design specifies internal component behavior. Developers implement the required software using the selected programming language and development environment.

11. Right Side of the V-Cycle: Testing

11.1 Unit Testing

Unit testing verifies individual software units or components against their detailed design and requirements.

Examples:

  • Temperature conversion function.
  • Fan threshold calculation.
  • Diagnostic status handling function.

11.2 Integration Testing

Integration testing verifies whether combined software units and modules interact correctly.

Examples:

  • SWC-to-SWC communication through RTE.
  • RTE and OS integration.
  • COM, PduR and CanIf communication path.

11.3 System Testing

System testing checks the integrated ECU against system-level requirements.

Examples:

  • Temperature-based fan operation.
  • CAN communication behavior.
  • Diagnostic response verification.
  • Fault handling and recovery.

11.4 Acceptance Testing

Acceptance testing evaluates whether the delivered system meets customer or stakeholder acceptance criteria.

12. Verification and Validation

Verification Validation
Checks whether work products meet specified requirements. Checks whether the resulting system satisfies intended use.
Reviews, inspections and tests may be used. System-level and acceptance activities may be used.
Focuses on correctness against specifications. Focuses on suitability for stakeholder needs.
Interview point: Verification asks whether the product was built according to its specifications. Validation asks whether the right product was built for its intended use.

15. Practical Example: Cooling Fan ECU V-Cycle

15.1 Requirement

The cooling fan must activate when engine temperature exceeds a configured threshold and deactivate when temperature falls below the configured lower threshold.

15.2 Development Activities

  1. Define temperature and fan-control requirements.
  2. Design the ECU software architecture.
  3. Create TemperatureSensor and FanControl SWCs.
  4. Define sender-receiver interfaces.
  5. Configure ARXML and ECU allocation.
  6. Generate RTE and configure BSW.
  7. Implement application logic.
  8. Build the ECU software.

15.3 Corresponding Testing Activities

Development Work Corresponding Test
Detailed software design Unit testing
SWC and RTE architecture Integration testing
System requirements System testing
Customer requirements Acceptance testing

15.4 Example Test Conditions

  • Temperature below the lower threshold: fan should be off.
  • Temperature above the upper threshold: fan should be on.
  • Temperature sensor fault: configured fault response should occur.
  • CAN communication failure: configured timeout or fault handling should occur.
  • Recovery after fault: behavior should match the specified recovery requirements.

The exact thresholds, hysteresis, diagnostic behavior and timing must come from the project requirements.

17. Placement Interview Questions and Answers

Q1. What is the AUTOSAR development workflow?

It is the structured process of requirements analysis, architecture design, SWC development, configuration, code generation, implementation, integration and testing.

Q2. What is the V-Model?

The V-Model is a development and testing approach that connects development stages with corresponding verification and validation activities.

Q3. What is performed on the left side of the V?

Requirement analysis, system design, software architecture, detailed design and implementation.

Q4. What is performed on the right side of the V?

Unit testing, integration testing, system testing and acceptance testing.

Q5. What is unit testing?

Testing an individual software unit or component to verify its behavior against its detailed design or requirements.

Q6. What is integration testing?

Testing combined software units or modules to verify their interfaces and interactions.

Q7. What is system testing?

Testing the complete integrated system against its system-level requirements.

Q8. What is acceptance testing?

Testing whether the delivered system meets the acceptance criteria of the customer or stakeholders.

Q9. What is the difference between verification and validation?

Verification checks conformance to specified requirements. Validation checks whether the system meets its intended purpose and stakeholder needs.

Q10. What is requirement traceability?

It is the ability to link requirements to design, implementation, test cases and test results.

Q11. What is SIL testing?

Software-in-the-Loop testing executes software in a simulated environment to evaluate behavior without requiring the final physical target ECU.

Q12. What is HIL testing?

Hardware-in-the-Loop testing uses a real controller or ECU connected to a real-time simulation environment.

Q13. Why is integration testing important in AUTOSAR?

It verifies that SWCs, RTE, BSW, MCAL and communication modules work together correctly.

Q14. What is the purpose of test coverage?

It measures which parts of the software or specified behavior have been exercised by testing. Coverage does not alone prove that software is correct.

Q15. Why is the V-Model useful in automotive software?

It encourages planned verification, traceability and systematic testing throughout development.
