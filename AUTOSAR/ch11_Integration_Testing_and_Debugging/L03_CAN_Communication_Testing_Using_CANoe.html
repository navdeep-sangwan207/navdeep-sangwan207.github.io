1. Introduction to CAN Communication Testing

Controller Area Network (CAN) is a serial communication protocol widely used in automotive electronic control units (ECUs). It allows multiple ECUs to exchange information over a shared bus.

CAN communication testing verifies whether ECUs transmit, receive and process messages correctly according to the configured network specification.

Typical CAN testing activities include:

  • Monitoring CAN frames.
  • Verifying message identifiers.
  • Checking message transmission intervals.
  • Verifying payload data.
  • Testing signal values and scaling.
  • Checking timeout and error handling.
  • Simulating other ECUs.
  • Analyzing communication faults.

2. CAN Network Architecture

All nodes connected to the same CAN bus can observe transmitted frames. Each node processes frames according to their identifiers and configured acceptance rules.

3. CAN Frame Structure

A Classical CAN data frame contains fields used for arbitration, control, data transfer and error detection.

3.1 Important CAN Frame Fields

Field Purpose
SOF Start of Frame.
Identifier Message identification and arbitration priority.
Control Field Contains control information, including payload length.
Data Field Contains the transmitted payload.
CRC Error detection.
ACK Receiver acknowledgment field.
EOF End of Frame.

3.2 Standard and Extended CAN Identifiers

  • Standard CAN identifier: 11 bits.
  • Extended CAN identifier: 29 bits.
  • Classical CAN payload: 0 to 8 bytes.
  • CAN FD payload: up to 64 bytes.
CAN identifiers are used for message identification and arbitration; they are not inherently ECU addresses.

5. CANoe Configuration

A CANoe project is configured according to the network architecture, database descriptions and test objectives.

5.1 Basic Configuration Steps

  1. Create or open a CANoe configuration.
  2. Select the required network channel.
  3. Configure the CAN interface hardware.
  4. Set the correct CAN bit rate.
  5. Import the required network database, such as a DBC file.
  6. Configure network nodes and simulation behavior.
  7. Configure measurement and logging windows.
  8. Start the measurement.
A DBC file describes CAN messages, signals, identifiers, layouts and related database information. It does not automatically guarantee that the ECU implementation matches the database.

6. CAN Message Monitoring

CANoe's Trace Window displays communication frames captured during measurement.

6.1 Example CAN Messages

CAN ID DLC Data Description
0x100 8 32 00 00 00 00 00 00 00 Engine status example
0x200 8 50 01 00 00 00 00 00 00 Temperature example
0x300 8 01 00 00 00 00 00 00 00 Vehicle status example

These are illustrative frames. Actual identifiers, payloads and message layouts must be obtained from the project network database or communication specification.

6.2 What to Check in Trace Window

  • Correct CAN identifier.
  • Correct frame format.
  • Correct data length code (DLC).
  • Expected payload values.
  • Message transmission interval.
  • Unexpected or missing messages.
  • Error frames and bus disturbances.

7. Signal Decoding Using DBC

A CAN frame contains raw bytes. A DBC database defines how those bytes and bits represent application signals.

7.1 Signal Properties

  • Start bit.
  • Signal length.
  • Byte order.
  • Signed or unsigned representation.
  • Scaling factor.
  • Offset.
  • Minimum and maximum values.
  • Unit.

7.2 Signal Conversion Formula

Physical Value = Raw Value × Factor + Offset

Example:

Raw Value = 50
Factor    = 0.5
Offset    = -40

Physical Value = 50 × 0.5 - 40

Physical Value = -15°C

The example demonstrates signal scaling. Real scaling parameters must come from the network specification.

9. CANoe CAPL Programming

CAPL (Communication Access Programming Language) is a C-like event-driven programming language used in Vector tools for network simulation and testing.

9.1 CAPL Example: Transmit a CAN Message

variables
{
    message 0x100 EngineStatus;
}

on key 't'
{
    EngineStatus.dlc = 8;

    EngineStatus.byte(0) = 0x32;
    EngineStatus.byte(1) = 0x00;
    EngineStatus.byte(2) = 0x00;
    EngineStatus.byte(3) = 0x00;
    EngineStatus.byte(4) = 0x00;
    EngineStatus.byte(5) = 0x00;
    EngineStatus.byte(6) = 0x00;
    EngineStatus.byte(7) = 0x00;

    output(EngineStatus);
}

When the configured key event occurs, this example prepares and transmits a Classical CAN message using the specified identifier. The exact CAPL syntax and message declaration should be checked against the installed CANoe version and configuration.

9.2 CAPL Example: Periodic Message Transmission

variables
{
    message 0x200 TemperatureStatus;
    msTimer txTimer;
}

on start
{
    setTimer(txTimer, 100);
}

on timer txTimer
{
    TemperatureStatus.dlc = 8;
    TemperatureStatus.byte(0) = 0x50;

    output(TemperatureStatus);

    setTimer(txTimer, 100);
}

This example sends a message periodically using a timer. The remaining payload bytes are left at their configured or default values.

12. CAN Error Analysis

CAN provides error detection and fault confinement mechanisms. CANoe can help engineers investigate communication problems.

12.1 Common CAN Error Conditions

  • Bit error.
  • Stuff error.
  • CRC error.
  • Form error.
  • ACK error.
  • Bus-off condition.

12.2 Possible Causes

  • Incorrect bit rate.
  • Missing or incorrect termination.
  • Wiring faults.
  • Noise and signal integrity problems.
  • Transceiver or controller faults.
  • Incorrect sample point or timing configuration.
For a conventional high-speed CAN bus with two end terminators of 120 Ω each, the powered-down resistance measured across CANH and CANL is approximately 60 Ω when both terminators are present and no other significant parallel paths affect the measurement.

13. AUTOSAR CAN Communication Path

In AUTOSAR Classic, CAN communication commonly uses the following software path for a configured transmit or receive flow. 

Application SWC
      |
      v
     RTE
      |
      v
     COM
      |
      v
    PduR
      |
      v
    CanIf
      |
      v
   Can Driver
      |
      v
   CAN Controller
      |
      v
     CAN Bus

The receive path generally follows the reverse direction through the configured communication stack.

CanTp is used when transport protocol communication is required, such as segmented diagnostic messages. Exact routing and module usage depend on the ECU configuration.

14. Practical Example: Temperature Message Testing

Assume a temperature ECU transmits a CAN message with identifier 0x200. The first data byte contains a raw temperature value.

14.1 Test Setup

  • CANoe installed on the test computer.
  • Compatible Vector CAN interface.
  • ECU connected to the CAN network.
  • Correct network bit rate.
  • Project DBC file.
  • Power supply and properly terminated CAN bus.

14.2 Test Procedure

  1. Open the CANoe configuration.
  2. Select the required CAN channel.
  3. Configure the correct bit rate.
  4. Load the project DBC file.
  5. Start the measurement.
  6. Observe message 0x200 in the Trace Window.
  7. Verify the data bytes.
  8. Check the decoded temperature signal.
  9. Measure the message cycle time.
  10. Record the test result and any defects.

14.3 Expected Results

  • The expected CAN identifier is visible.
  • The received DLC matches the specification.
  • The payload contains expected values.
  • The decoded signal matches the expected physical value.
  • The message interval meets the timing requirement.
  • Timeout behavior works when the message is absent.

15. Placement Interview Questions and Answers

Q1. What is CAN?

CAN is a serial communication protocol that allows multiple automotive ECUs to exchange messages over a shared bus.

Q2. What is CANoe?

CANoe is a Vector tool used for automotive network simulation, analysis, testing and validation.

Q3. What is a DBC file?

A DBC file describes CAN messages and signals, including identifiers, bit positions, lengths and scaling information.

Q4. What is CAPL?

CAPL is an event-driven programming language used in Vector tools for communication simulation and testing.

Q5. What is a CAN identifier?

It identifies a message and participates in bus arbitration. Lower numerical identifiers generally have higher arbitration priority when comparing identifiers in the same arbitration format.

Q6. What is the difference between standard and extended CAN?

Standard CAN uses an 11-bit identifier, whereas extended CAN uses a 29-bit identifier.

Q7. What is the maximum Classical CAN payload?

Classical CAN supports up to 8 data bytes per frame.

Q8. What is CAN FD?

CAN FD is an extension of CAN that supports larger payloads, up to 64 bytes, and can use a faster data phase.

Q9. What is CAN bus termination?

Termination reduces signal reflections. A conventional high-speed CAN bus typically uses 120 Ω termination at each physical end.

Q10. What is a CAN timeout?

It occurs when an expected message is not received within its configured monitoring period.

Q11. What is bus-off?

Bus-off is a CAN controller error-confinement state reached after its transmit error counter exceeds the specified threshold.

Q12. What is the purpose of the Trace Window?

It displays captured communication frames and helps engineers inspect identifiers, data, timestamps and errors.

Q13. What is signal scaling?

Signal scaling converts raw CAN data into a physical value using a factor and offset.

Q14. What is the role of PduR?

PduR routes Protocol Data Units between configured communication modules in the AUTOSAR communication stack.

Q15. What is the role of CanIf?

CanIf provides an abstraction interface between upper communication modules and CAN controller drivers.
