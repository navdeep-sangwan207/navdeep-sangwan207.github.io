1. Introduction to Debugging

Debugging is the systematic process of identifying, analyzing and correcting defects in software. Troubleshooting extends this process to investigate problems across software, hardware, communication interfaces and ECU integration.

AUTOSAR ECUs contain multiple software layers. A fault may originate in an application component, generated RTE code, BSW configuration, MCAL driver, operating system, microcontroller or external hardware.

1.1 Objectives of Debugging

  • Identify the root cause of software defects.
  • Find incorrect data flow between SWCs.
  • Investigate RTE and BSW integration problems.
  • Analyze task scheduling and timing faults.
  • Detect CAN communication failures.
  • Investigate ECU startup and initialization problems.
  • Verify that corrective changes resolve the defect.
Important: A symptom is not necessarily the root cause. For example, a fan that does not operate may be caused by sensor input, application logic, RTE communication, task scheduling, PWM configuration or an electrical fault.

Debugging should follow the data and execution path across the layers rather than assuming that the first visible failure is the actual source of the defect.

3. Types of Debugging

3.1 Source-Level Debugging

Source-level debugging allows engineers to inspect program execution using source code, breakpoints, variables and call stacks.

3.2 Hardware-Level Debugging

Hardware-level debugging investigates microcontroller registers, peripheral configuration, memory, clocks, pins and external circuits.

3.3 Communication Debugging

Communication debugging investigates CAN messages, signal values, message timing, timeouts and network errors.

3.4 Runtime Debugging

Runtime debugging investigates failures that occur while the ECU software is executing, including incorrect states, timing problems, memory corruption and unexpected resets.

5. Breakpoints and Step-by-Step Debugging

A breakpoint pauses program execution at a selected location. The engineer can then inspect program state and determine how execution reached that point.

5.1 Types of Breakpoints

  • Software breakpoint – inserted through the debugger.
  • Hardware breakpoint – implemented using processor debug resources.
  • Conditional breakpoint – pauses when a specified condition is met.
  • Data or watchpoint – detects access to a selected memory location, where supported.

5.2 Step Commands

Command Purpose
Step Into Enters a called function.
Step Over Executes a function call without entering its body.
Step Out Continues execution until the current function returns.
Continue / Run Resumes normal execution until the next halt condition.

6. Watch Window and Variable Inspection

A watch window displays selected variables and expressions during debugging. It helps engineers verify whether data is updated correctly and whether calculations produce expected values.

6.1 Example

volatile unsigned int temperature;
volatile unsigned int fanDuty;

void Fan_Control(void)
{
    if (temperature >= 90)
    {
        fanDuty = 100;
    }
    else if (temperature >= 75)
    {
        fanDuty = 60;
    }
    else
    {
        fanDuty = 0;
    }
}

During debugging, an engineer can inspect:

  • temperature – current input value.
  • fanDuty – calculated output command.
  • Function call sequence.
  • Whether the function executes when expected.
The volatile qualifier is useful for objects that can change outside the normal program flow, such as memory-mapped registers or variables updated by an interrupt. It does not make access atomic or automatically solve concurrency problems.

8. Debugging RTE Problems

RTE problems can occur when software component interfaces, connections, generated code or runnable activation are incorrect.

8.1 Common RTE Problems

  • Incorrect port connection.
  • Incompatible data element types.
  • Incorrect interface configuration.
  • Missing generated RTE source or header files.
  • Incorrect runnable-to-task mapping.
  • Data not available when expected.
  • Incorrect communication semantics.

8.2 Troubleshooting Procedure

  1. Check the SWC port definitions.
  2. Verify the sender-receiver or client-server interface.
  3. Check component connections and ECU mapping.
  4. Inspect generated RTE APIs and files.
  5. Verify runnable activation events.
  6. Check the task mapping and execution timing.
  7. Inspect the received and transmitted data.

9. Debugging BSW Problems

BSW defects can arise from incorrect module configuration, initialization dependencies, communication routing or service integration.

10. Debugging MCAL and Hardware Problems

MCAL provides access to microcontroller peripherals. Incorrect configuration or hardware conditions can prevent the peripheral from working as expected.

10.1 Common Peripheral Problems

  • ADC returns an unexpected value.
  • PWM output is missing.
  • GPIO pin does not change state.
  • SPI communication fails.
  • CAN controller does not transmit.
  • Timer interrupt does not occur.

10.2 Troubleshooting Checks

  1. Verify microcontroller derivative and driver compatibility.
  2. Check clock and peripheral initialization.
  3. Verify pin multiplexing and direction.
  4. Inspect peripheral register values where appropriate.
  5. Check electrical supply and ground.
  6. Measure signals using an oscilloscope or logic analyzer.
  7. Compare measured behavior with the hardware specification.

11. CAN Communication Troubleshooting

CAN communication failures can occur because of incorrect configuration, wiring, timing or physical-layer problems.

11.1 Common CAN Problems

  • Message not transmitted.
  • Message not received.
  • Incorrect CAN identifier.
  • Incorrect payload or signal scaling.
  • Unexpected message cycle time.
  • CAN error frames.
  • Bus-off condition.

12. OS and Timing Troubleshooting

AUTOSAR OS manages task execution, interrupts, alarms and resources. An incorrect OS configuration or software interaction can cause unexpected execution behavior.

12.1 Common Problems

  • Task activation failure.
  • Unexpected task execution delay.
  • Missed deadline.
  • Incorrect event handling.
  • Resource-related blocking.
  • Excessive interrupt load.
  • Stack overflow.

12.2 Debugging Checks

  • Verify task priority and scheduling configuration.
  • Check task activation and event-setting paths.
  • Inspect execution time and deadline measurements.
  • Check resource acquisition and release.
  • Review stack usage and OS error information.
  • Check interrupt configuration and nesting rules.
A task that appears not to execute may be waiting for an event, blocked by a resource, incorrectly activated or scheduled later than expected. Inspect OS state before changing priorities.

13. Memory and Runtime Faults

Memory-related defects can cause unpredictable ECU behavior, unexpected resets or corrupted application data.

13.1 Common Memory Problems

  • Stack overflow.
  • Buffer overflow.
  • Invalid pointer access.
  • Uninitialized variable.
  • Memory corruption.
  • Incorrect array indexing.
  • Memory allocation failure, where dynamic allocation is used.

13.2 Example: Array Boundary Error

int data[5];
int i;

for (i = 0; i <= 5; i++)
{
    data[i] = i;
}

The valid indexes are 0 to 4. The condition i <= 5 accesses an invalid array element when i becomes 5.

Corrected loop:

for (i = 0; i < 5; i++)
{
    data[i] = i;
}

14. Watchdog and Unexpected ECU Reset

A watchdog monitors software execution and can trigger a reset or other configured reaction if the expected service is not provided within the required time.

14.1 Possible Causes of Watchdog Reset

  • Software stuck in an infinite loop.
  • Task deadline violation.
  • Interrupt-related execution problems.
  • Incorrect watchdog configuration.
  • Failure to execute the configured watchdog servicing sequence.

14.2 Troubleshooting

  1. Check reset-cause information if available.
  2. Inspect watchdog configuration and timing.
  3. Review task and interrupt execution.
  4. Inspect program flow before the reset.
  5. Check whether the configured watchdog servicing conditions are met.

15. Root Cause Analysis

Root Cause Analysis (RCA) identifies the underlying reason for a defect instead of only correcting its visible symptom.

15.1 Five Whys Technique

The Five Whys technique repeatedly asks why a problem occurred until the underlying cause is identified.

15.2 Example

Problem:
Cooling fan does not start.

Why 1:
No PWM output is observed.

Why 2:
PWM driver is not initialized.

Why 3:
Required initialization was not completed.

Why 4:
The configured initialization sequence is incorrect.

Why 5:
A module dependency was not included in the integration plan.

Root Cause:
Incorrect integration dependency configuration.

The investigation must confirm the actual cause using logs, measurements, code inspection and repeatable tests.

16. Practical Debugging Example: Fan Control ECU

Assume the fan does not start even though the temperature is above the configured activation threshold.

16.1 Troubleshooting Sequence

  1. Measure or simulate the temperature sensor input.
  2. Check whether the ADC driver reports the correct value.
  3. Inspect the temperature SWC output.
  4. Verify RTE communication to the fan-control SWC.
  5. Check whether the fan-control runnable executes.
  6. Inspect the calculated fan command.
  7. Verify the PWM driver configuration.
  8. Measure the physical PWM output.
  9. Check the actuator driver and fan supply.
  10. Record the root cause and verify the correction.

17. Debugging Best Practices

  • Reproduce the defect before changing the software.
  • Record the exact software and configuration versions.
  • Check logs and build messages.
  • Use breakpoints and watch windows systematically.
  • Verify one layer at a time.
  • Check both software and physical signals.
  • Preserve test evidence.
  • Use version control for corrective changes.
  • Perform regression testing after a fix.
  • Document the confirmed root cause.

18. Placement Interview Questions and Answers

Q1. What is debugging?

Debugging is the process of identifying, analyzing and correcting software defects.

Q2. What is a breakpoint?

A breakpoint pauses program execution at a selected location to allow inspection of program state.

Q3. What is a watch window?

It displays selected variables and expressions during debugging.

Q4. What is a call stack?

It shows the active function-call sequence and helps trace the execution path.

Q5. What is the purpose of TRACE32?

TRACE32 is an embedded development tool used for debugging, processor inspection and trace analysis.

Q6. What causes an RTE error?

Possible causes include incorrect interfaces, missing generated files, incompatible data types or incorrect component connections.

Q7. What is a watchdog timer?

It monitors software execution and triggers a configured reaction when expected servicing conditions are not met.

Q8. What is stack overflow?

Stack overflow occurs when software uses more stack memory than the configured or available stack space.

Q9. What is root cause analysis?

RCA identifies the underlying reason for a defect rather than only addressing its visible symptom.

Q10. What causes CAN bus-off?

A CAN controller enters bus-off when its transmit error counter reaches the specified error-confinement threshold.

Q11. How do you debug a task that does not execute?

Check task activation, scheduling configuration, event conditions, resource blocking and OS error information.

Q12. How do you debug an ADC problem?

Check input voltage, pin configuration, clock, ADC initialization, conversion status and result registers.

Q13. What is regression testing?

It verifies that a software change has not broken previously working functionality.

Q14. Why is an oscilloscope useful?

It measures electrical signals and helps inspect voltage levels, waveforms, timing and signal integrity.

Q15. What is the difference between a symptom and a root cause?

A symptom is the visible effect of a problem. The root cause is the underlying reason that produces the symptom.

20. Lesson Summary

  • Debugging identifies and corrects software defects.
  • Breakpoints and watch windows help inspect program execution.
  • Call stacks reveal function execution paths.
  • RTE, BSW and MCAL problems require layer-specific investigation.
  • CAN troubleshooting combines software and physical-layer analysis.
  • OS timing and memory faults can affect ECU reliability.
  • Watchdog resets require investigation of execution and reset causes.
  • Root Cause Analysis helps prevent recurring defects.
  • Regression testing verifies corrective changes.
