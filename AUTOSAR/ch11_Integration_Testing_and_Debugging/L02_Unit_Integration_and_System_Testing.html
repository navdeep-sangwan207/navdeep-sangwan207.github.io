1. Introduction to Software Testing

Software testing is the process of evaluating software to determine whether it behaves according to specified requirements and to identify defects before deployment.

In AUTOSAR ECU development, testing is performed at different levels. Each level checks a different scope of software functionality.

  • Unit Testing
  • Integration Testing
  • System Testing
  • Acceptance Testing
Interview concept: Unit testing checks an individual software unit, integration testing checks interactions between units, and system testing checks the complete integrated system.

Testing generally progresses from smaller software elements to larger integrated systems. In real projects, testing levels can overlap and be performed iteratively.

3. Unit Testing

Unit testing verifies an individual software unit independently. A unit may be a function, module, runnable entity or another testable software element, depending on the project.

3.1 Objectives of Unit Testing

  • Verify individual functions and algorithms.
  • Check input and output behavior.
  • Verify boundary conditions.
  • Identify logical errors.
  • Check error handling.
  • Verify expected behavior under invalid inputs.

3.2 Example: Temperature Threshold Function

Consider a function that decides the fan speed based on the measured temperature. 

int Fan_Control(int temperature)
{
    if (temperature >= 90)
    {
        return 100;
    }
    else if (temperature >= 75)
    {
        return 60;
    }
    else
    {
        return 0;
    }
}

3.3 Unit Test Cases

Input Temperature Expected Fan Duty Purpose
50°C 0% Below first threshold
75°C 60% First boundary
85°C 60% Middle operating range
90°C 100% Second boundary
100°C 100% Above second threshold

  • Unity – Embedded C unit testing framework.
  • Vendor-specific testing and analysis tools.

4. Test Stubs, Drivers and Mocks

When a unit depends on other modules or hardware, test doubles can be used to isolate the unit being tested.

4.1 Test Stub

A stub provides a simplified implementation of a dependency. It supplies predefined responses to the unit under test.

4.2 Test Driver

A test driver invokes the unit under test, supplies test inputs and collects the results.

4.3 Mock

A mock simulates a dependency and can also verify whether expected interactions or function calls occurred. 

          Test Driver
               |
               v
        Unit Under Test
               |
               v
          Mock / Stub
               |
               v
        Simulated Dependency
A stub mainly supplies controlled responses. A mock can additionally verify expected interactions. The exact terminology may vary between testing frameworks.

5. Integration Testing

Integration testing verifies the interaction between two or more software modules after they have been combined.

In AUTOSAR, integration testing can involve:

  • SWC-to-SWC communication.
  • SWC and RTE interaction.
  • RTE and BSW interaction.
  • BSW module interaction.
  • BSW and MCAL interaction.
  • Communication stack integration.

5.1 Example: SWC Integration

Integration testing checks whether the temperature value is transmitted correctly, received by the fan-control component and converted into the expected actuator command.

5.2 Integration Testing Checks

  • Interface compatibility.
  • Data type and data element consistency.
  • Correct port connections.
  • RTE communication behavior.
  • Runnable activation and task mapping.
  • Error handling between components.
  • Timing and data consistency.

6. Integration Testing Approaches

6.1 Big Bang Integration

All or most modules are combined before testing their interactions. This approach can make it difficult to isolate the source of a defect.

6.2 Top-Down Integration

Higher-level modules are integrated and tested first. Lower-level dependencies that are not yet available can be represented using stubs.

6.3 Bottom-Up Integration

Lower-level modules are integrated and tested first. Higher-level dependencies can be represented using test drivers.

6.4 Incremental Integration

Modules are integrated step by step, with testing performed after each integration stage. This makes defects easier to isolate. 

Incremental Integration:

Module A
   |
   v
Test A
   |
   v
Add Module B
   |
   v
Test A + B
   |
   v
Add Module C
   |
   v
Test A + B + C
Incremental integration is useful in complex ECU projects because it helps identify interface and dependency problems earlier.

7. System Testing

System testing verifies the complete integrated ECU or system against its specified functional and non-functional requirements.

7.1 Objectives

  • Verify complete ECU functionality.
  • Check end-to-end signal flow.
  • Verify communication with other ECUs.
  • Test diagnostic services.
  • Check timing and performance requirements.
  • Verify fault handling and recovery.
  • Check behavior under normal and abnormal conditions.

8. Acceptance Testing

Acceptance testing determines whether the completed system satisfies the agreed acceptance criteria and intended operational requirements.

In automotive development, acceptance activities may include customer or OEM reviews, requirement-based testing, vehicle-level testing and formal release evaluations.

9. Verification and Validation

9.1 Verification

Verification checks whether the software or system has been developed according to specified requirements and design.

Question: Are we building the product correctly?

9.2 Validation

Validation checks whether the resulting product meets its intended use and stakeholder needs.

Question: Are we building the correct product?

Verification Validation
Checks conformance to specifications. Checks suitability for intended use.
Can include reviews and static analysis. Can include system and vehicle-level tests.
Often checks design and implementation artifacts. Evaluates the resulting product in its intended context.

10. SIL Testing – Software-in-the-Loop

SIL testing executes software in a simulated environment, usually on a host computer. It allows software behavior to be evaluated without requiring the final physical ECU hardware.

10.1 SIL Testing Objectives

  • Test software algorithms.
  • Verify control logic.
  • Run automated test cases.
  • Check input and output behavior.
  • Identify software defects early.

10.2 SIL Test Setup

10.3 Advantages

  • No physical ECU is required for the SIL environment.
  • Test cases can be automated.
  • Many input combinations can be evaluated.
  • Useful for early software verification.

11. HIL Testing – Hardware-in-the-Loop

HIL testing uses a real ECU connected to a real-time simulation system. The simulation system provides electrical or communication signals that represent the external vehicle environment.

11.1 HIL Test Setup

              v

              |
              | ECU Outputs
              v
      Measurement System
              |
              v

11.2 HIL Testing Objectives

  • Test real ECU hardware and software together.
  • Verify hardware interfaces.
  • Test sensor and actuator signals.
  • Check communication behavior.
  • Inject faults and verify responses.
  • Evaluate timing under realistic conditions.

11.3 SIL vs HIL

13. Test Coverage

Test coverage measures how much of the software or its logic has been exercised by the test cases.

13.1 Statement Coverage

Measures the proportion of executable statements exercised by tests.

13.2 Branch Coverage

Measures whether each decision outcome, such as true and false, has been exercised.

13.3 Condition Coverage

Checks whether individual Boolean conditions have evaluated to both true and false.

13.4 Modified Condition/Decision Coverage (MC/DC)

MC/DC checks that each condition can independently affect the outcome of a decision. It is particularly important in safety-related software development where required by the applicable process.

High code coverage does not by itself prove that software is correct. Test quality, requirements coverage, boundary conditions and expected-result checks are also important.

14. Defect Reporting and Test Documentation

Every detected defect should be recorded with enough information for another engineer to reproduce and investigate it.

14.1 Typical Defect Report Fields

  • Defect ID.
  • ECU and software version.
  • Test case ID.
  • Preconditions and test environment.
  • Steps to reproduce.
  • Expected result.
  • Actual result.
  • Logs, traces and screenshots.
  • Severity and priority.
  • Defect status and assigned owner.

14.2 Example Defect

Defect ID: ECU-TEST-024

Module: Fan Control SWC

Test: Temperature threshold test

Input: 90°C

Expected Result: Fan duty = 100%

Actual Result: Fan duty = 60%

Possible Area:
Threshold comparison or control logic.

Status: Open

15. Placement Interview Questions and Answers

Q1. What is unit testing?

Unit testing verifies an individual software unit independently, such as a function or module.

Q2. What is integration testing?

It verifies the interactions and interfaces between two or more integrated software modules.

Q3. What is system testing?

It verifies the complete integrated system against specified functional and non-functional requirements.

Q4. What is a test stub?

A stub is a simplified replacement for a dependency that supplies controlled responses to the unit being tested.

Q5. What is a test driver?

A test driver invokes the unit under test, provides inputs and collects outputs.

Q6. What is a mock object?

A mock simulates a dependency and can verify expected interactions with the unit under test.

Q7. What is incremental integration?

It combines modules step by step and tests after each integration stage.

Q8. What is SIL testing?

SIL testing executes software in a simulated environment, typically without the final physical ECU.

Q9. What is HIL testing?

HIL testing connects a real ECU to a real-time simulation system to test hardware and software together.

Q10. What is the main difference between SIL and HIL?

SIL tests software in a simulated execution environment, whereas HIL tests real ECU hardware connected to simulated external systems.

Q11. What is statement coverage?

It measures how many executable statements are exercised by the test suite.

Q12. What is branch coverage?

It checks whether each decision outcome has been exercised.

Q13. What is MC/DC?

Modified Condition/Decision Coverage verifies that each Boolean condition can independently affect the decision outcome.

Q14. What is regression testing?

Regression testing checks that software changes have not introduced new defects or broken previously working functionality.

Q15. What is a defect report?

It is a record of a detected software problem, including reproduction steps, expected and actual results, environment and supporting evidence.

17. Lesson Summary

  • Unit testing checks individual software units.
  • Integration testing checks interfaces and module interactions.
  • System testing checks the complete integrated ECU.
  • Stubs, drivers and mocks support isolated testing.
  • SIL supports software testing in a simulated environment.
  • HIL tests a real ECU with simulated external systems.
  • Coverage metrics help evaluate test execution.
  • Defect reports support systematic troubleshooting.
