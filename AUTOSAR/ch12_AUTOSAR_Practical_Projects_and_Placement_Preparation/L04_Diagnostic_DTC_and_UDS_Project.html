1. Project Introduction

Automotive ECUs continuously monitor sensors, actuators and internal software conditions. When a fault is detected, the ECU may record diagnostic information so that technicians can identify and troubleshoot the problem.

This project demonstrates how an AUTOSAR Classic ECU detects a fault, processes a diagnostic event, stores a Diagnostic Trouble Code (DTC), and responds to diagnostic requests using Unified Diagnostic Services (UDS).

1.1 Project Objective

  • Understand automotive diagnostic architecture.
  • Study Diagnostic Event Manager (DEM).
  • Understand Diagnostic Communication Manager (DCM).
  • Learn Diagnostic Trouble Codes (DTCs).
  • Understand UDS request and response messages.
  • Study diagnostic communication over CAN.
  • Develop a simplified fault-monitoring example.

2. Project Scenario

Consider an engine cooling system ECU that monitors coolant temperature. If the temperature exceeds a configured diagnostic threshold for the required time, the ECU reports a fault event to DEM.

DEM processes the event and manages its diagnostic status and associated DTC. A diagnostic tester can then request the DTC information through UDS.

3. Important Diagnostic Terms

3.1 Diagnostic Event

A diagnostic event represents a monitored condition that may indicate a fault in an ECU or vehicle function.

Examples:

  • Coolant temperature sensor circuit fault.
  • Engine temperature too high.
  • Fan actuator malfunction.
  • Communication timeout.
  • Supply voltage outside the permitted range.

3.2 Diagnostic Trouble Code (DTC)

A DTC is an identifier used by diagnostic systems to represent a detected fault. DTCs allow diagnostic testers and technicians to identify the type of fault recorded by an ECU.

Example illustrative DTC:

DTC: 0x123456
Description: Engine Coolant Temperature Too High
Status: Test Failed

The example DTC is project-specific and is not a universal standard DTC assignment.

3.3 DEM

DEM stands for Diagnostic Event Manager. It manages diagnostic events and their associated information.

  • Processes reported diagnostic events.
  • Manages event status information.
  • Manages DTC status according to configuration.
  • Supports debouncing.
  • Manages configured freeze-frame and extended data.
  • Supports diagnostic data access by other modules.

3.4 DCM

DCM stands for Diagnostic Communication Manager. It handles diagnostic communication between an external tester and the ECU.

DCM processes diagnostic requests, manages diagnostic sessions and security-related access, and provides configured UDS services.

6. Simplified C Fault Monitoring Example

The following standalone C example demonstrates threshold monitoring and a simplified debounce counter. It is not a complete AUTOSAR DEM implementation. 

#include <stdio.h>
#include <stdint.h>

#define TEMP_LIMIT       110U
#define DEBOUNCE_LIMIT   3U

static uint8_t faultCounter = 0U;

void MonitorTemperature(uint16_t temperature)
{
    if (temperature > TEMP_LIMIT)
    {
        if (faultCounter < DEBOUNCE_LIMIT)
        {
            faultCounter++;
        }
    }
    else
    {
        if (faultCounter > 0U)
        {
            faultCounter--;
        }
    }

    if (faultCounter >= DEBOUNCE_LIMIT)
    {
        printf("Fault Detected\n");

        /*
         * Illustrative location for a configured
         * AUTOSAR diagnostic event report.
         */
    }
    else
    {
        printf("Fault Not Confirmed\n");
    }
}

int main(void)
{
    MonitorTemperature(115U);
    MonitorTemperature(116U);
    MonitorTemperature(118U);

    return 0;
}

6.1 Expected Output

Fault Not Confirmed
Fault Not Confirmed
Fault Detected
Important: This counter is a teaching example. AUTOSAR DEM supports configured debounce strategies and event-processing behavior. A real application normally reports event status through generated or configured interfaces, rather than implementing the DEM internally.

7. Reporting a Diagnostic Event to DEM

In AUTOSAR Classic, an application fault monitor reports the event through the configured diagnostic event interface. A commonly used API pattern is: 

Dem_SetEventStatus(
    DEM_EVENT_ID_TEMPERATURE_HIGH,
    DEM_EVENT_STATUS_PREFAILED
);

When the monitor determines that the fault condition has passed, it may report: 

Dem_SetEventStatus(
    DEM_EVENT_ID_TEMPERATURE_HIGH,
    DEM_EVENT_STATUS_PREPASSED
);

The event identifier and generated symbols are illustrative. The exact API availability and integration depend on the AUTOSAR release, DEM configuration and supplier implementation.

8. DTC Status Management

A DTC status byte contains flags that describe the diagnostic state of a DTC. The commonly defined UDS status bits include:

Bit Status Meaning
0 testFailed Test currently indicates failure.
1 testFailedThisOperationCycle Test failed during the current operation cycle.
2 pendingDTC DTC is pending according to its status rules.
3 confirmedDTC DTC has reached the configured confirmation criteria.
4 testNotCompletedSinceLastClear Test has not completed since the last clear operation.
5 testFailedSinceLastClear Test has failed since the last clear operation.
6 testNotCompletedThisOperationCycle Test has not completed in the current operation cycle.
7 warningIndicatorRequested A warning indicator is requested according to diagnostic logic.

The reported status depends on diagnostic configuration, event qualification, operation cycles and status availability.

9. UDS Protocol Introduction

UDS stands for Unified Diagnostic Services. It is specified by ISO 14229 and provides diagnostic services for communication between a tester and an ECU.

9.1 Common UDS Services

Service SID Purpose
Diagnostic Session Control 0x10 Changes diagnostic session.
ECU Reset 0x11 Requests an ECU reset.
Clear Diagnostic Information 0x14 Requests clearing of configured diagnostic information.
Read DTC Information 0x19 Reads diagnostic trouble code information.
Read Data By Identifier 0x22 Reads configured data identifiers.
Security Access 0x27 Performs configured security access procedures.
Write Data By Identifier 0x2E Writes permitted configured data identifiers.
Tester Present 0x3E Maintains diagnostic session activity.

10. UDS Request and Response Example

A diagnostic tester can request DTC information using Read DTC Information (SID 0x19). The exact subfunction and response layout depend on the requested DTC information type.

10.1 Example Request

Request:
19 02 FF

19 = Read DTC Information
02 = Report DTC By Status Mask
FF = Status Mask

10.2 Example Positive Response

59 02 00 12 34 56 0F

59 = Positive response for service 0x19
02 = Response subfunction
00 = Availability/status information example
12 34 56 = Illustrative DTC
0F = Illustrative DTC status byte

This byte sequence is an illustrative response layout. Actual response content and length depend on the requested subfunction, status mask, number of DTCs and applicable UDS specification.

10.3 Negative Response

7F 19 31

7F = Negative response
19 = Original request service
31 = Request Out Of Range

A negative response has the general format: 

7F [Request SID] [Negative Response Code]

A positive response SID is generally the request SID plus 0x40. Some UDS services have additional service-specific response rules.

11. Diagnostic Communication over CAN

UDS messages can be transported over CAN using ISO 15765-2 (DoCAN). This transport protocol supports segmentation and reassembly when a diagnostic message does not fit into a single CAN frame.

11.1 ISO-TP Frame Types

  • Single Frame (SF): Carries a message that fits in one frame.
  • First Frame (FF): Starts a segmented message.
  • Consecutive Frame (CF): Carries subsequent message data.
  • Flow Control (FC): Controls segmented message transmission.

12. Practical Project Configuration Workflow

  1. Define the temperature monitoring requirement.
  2. Create or identify the application fault monitor.
  3. Define the diagnostic event in DEM configuration.
  4. Assign the event to a configured DTC.
  5. Configure debounce behavior and event status processing.
  6. Configure required freeze-frame or extended data records.
  7. Configure DCM diagnostic sessions and UDS services.
  8. Configure diagnostic communication routing through PduR and CanTp where required.
  9. Generate configured BSW and integration code.
  10. Build and flash the ECU using the approved development workflow.
  11. Connect a diagnostic tester and verify the fault response.

13. Diagnostic Testing Using CANoe

CANoe can be used to send diagnostic requests, observe responses and verify diagnostic behavior. Diagnostic configuration and the appropriate diagnostic description must be loaded into the test setup.

13.1 Test Scenarios

Test Action Expected Result
TC01 Keep temperature below threshold. No over-temperature DTC confirmation.
TC02 Increase temperature above threshold for the configured debounce period. Fault event qualifies and DTC status updates.
TC03 Send UDS Read DTC Information request. ECU returns the configured DTC information.
TC04 Send an authorized Clear Diagnostic Information request. ECU performs the configured clearing operation.
TC05 Return temperature to normal. Event status follows configured recovery behavior.
TC06 Send an unsupported diagnostic request. ECU returns an applicable negative response if required.
Clearing a DTC does not repair the underlying fault. If the fault remains present, the diagnostic monitor may report it again and the DTC may be stored again according to the configured qualification rules.

14. Common Diagnostic Problems

Problem Possible Cause Investigation
DTC not stored Event not reported or qualification incomplete Check event reporting, debounce and DEM configuration.
DTC not readable Incorrect DCM service or DTC configuration Check DCM and DEM configuration.
No diagnostic response Transport or routing issue Inspect CanTp, PduR, CanIf and CAN communication.
Negative response Invalid session, unsupported service or invalid parameter Check the NRC and service preconditions.
DTC returns after clearing Fault condition still exists Inspect the physical signal and fault monitor.

15. Important Placement Concepts

  • DEM manages diagnostic events and DTC information.
  • DCM handles diagnostic communication and UDS services.
  • UDS is specified by ISO 14229.
  • DoCAN transport over CAN is specified by ISO 15765-2.
  • Read DTC Information uses SID 0x19.
  • Clear Diagnostic Information uses SID 0x14.
  • Negative responses use the general format 7F, request SID, NRC.
  • Debouncing prevents transient conditions from immediately becoming qualified faults.
  • Freeze-frame data can capture configured operating conditions associated with a fault.
  • DTC status depends on configured event processing and diagnostic rules.

16. Placement Interview Questions and Answers

Q1. What is a DTC?

A Diagnostic Trouble Code is an identifier representing a detected fault condition in an ECU or vehicle system.

Q2. What is DEM?

DEM manages diagnostic events, DTC status and configured diagnostic event data.

Q3. What is DCM?

DCM handles diagnostic communication between an external tester and an ECU and processes configured UDS services.

Q4. What is UDS?

UDS stands for Unified Diagnostic Services. It is an automotive diagnostic protocol specified by ISO 14229.

Q5. What is the SID for Read DTC Information?

0x19.

Q6. What is the SID for Clear Diagnostic Information?

0x14.

Q7. What is diagnostic debouncing?

Debouncing qualifies a fault condition using configured counter-based or time-based criteria to avoid reacting immediately to transient failures.

Q8. What is freeze-frame data?

It is a configured snapshot of operating data associated with a diagnostic event or DTC.

Q9. What is ISO-TP?

ISO-TP is a transport protocol used to transmit diagnostic messages over CAN, including messages requiring segmentation.

Q10. Does clearing a DTC fix the fault?

No. Clearing diagnostic information does not repair the physical or software fault. The fault may be detected again.

Q11. What is a negative response?

It indicates that the ECU cannot process a diagnostic request as requested. The general format is 7F, request service ID and negative response code.

Q12. What is NRC 0x78?

ResponsePending. It indicates that the ECU needs more time to complete the requested service.
