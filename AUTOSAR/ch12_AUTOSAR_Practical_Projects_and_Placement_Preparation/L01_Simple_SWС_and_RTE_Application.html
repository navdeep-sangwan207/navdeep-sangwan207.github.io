1. Project Introduction

In this project, we will develop a simple AUTOSAR application using two Software Components (SWCs) that communicate through the Runtime Environment (RTE).

The first component generates a temperature value. The second component receives that value and determines whether a cooling fan should be activated.

1.1 Project Objective

  • Create two application Software Components.
  • Understand sender-receiver communication.
  • Define ports and interfaces.
  • Understand runnable entities.
  • Understand RTE communication APIs.
  • Study the application-to-RTE execution flow.

4. Software Component Design

A Software Component represents an application software unit with defined interfaces and behavior.

4.1 TemperatureSensor_SWС

Responsibilities:

  • Obtain or calculate the temperature value.
  • Store the temperature data.
  • Provide the temperature through a sender port.

4.2 FanControl_SWC

Responsibilities:

  • Receive temperature data.
  • Compare temperature with the activation threshold.
  • Determine the fan operating state.
  • Provide the fan state to the configured output interface.

5. Ports and Interfaces

Ports define how a Software Component communicates with other components or the ECU environment.

5.1 Provided Port (P-Port)

A provided port makes a component's interface available to other components.

In this project, TemperatureSensor_SWС provides the temperature data through a sender-receiver interface.

5.2 Required Port (R-Port)

A required port allows a component to receive data or request services from another component.

FanControl_SWC requires the temperature data through its sender-receiver interface.

5.3 Sender-Receiver Interface

Sender-receiver communication transfers data elements from a sender component to one or more receiver components.

Parameter Example

6. Runnable Entities

A runnable entity is an executable unit of application software inside a Software Component. It is activated by an event configured in the AUTOSAR model.

6.1 Temperature Runnable

The temperature runnable obtains a temperature value and writes it to the sender-receiver data element.

6.2 Fan Control Runnable

The fan control runnable reads the received temperature and calculates the required fan state.

7. RTE Communication APIs

The RTE generator provides component-specific APIs based on the configured ports, interfaces and data elements.

7.1 Rte_Write()

Used by a sender component to write data through a configured sender-receiver interface. 

Std_ReturnType status;

status = Rte_Write_TemperaturePort_TemperatureValue(temperature);

7.2 Rte_Read()

Used by a receiver component to read data through a configured sender-receiver interface. 

uint16 temperature;

Std_ReturnType status;

status = Rte_Read_TemperaturePort_TemperatureValue(&temperature);
The API names above are illustrative. Actual generated names depend on the SWC port, interface, data element, configuration and AUTOSAR toolchain.

8. Application Logic

8.1 Temperature Sensor Logic

For this learning project, use a simulated temperature value. In a real ECU, the value would normally originate from a sensor driver or another configured software interface. 

temperature = 85;

Write temperature through RTE;

8.2 Fan Control Logic

Fan activation condition:

IF temperature >= 80
    fan_state = ON;
ELSE
    fan_state = OFF;

The threshold is an example. A production system may use calibrated thresholds, hysteresis, diagnostics and safety-related fault handling.

9. Simplified Application Code

The following C example demonstrates the application logic without a real AUTOSAR-generated RTE. It is useful for understanding the data flow before working with a configuration toolchain.

9.1 Temperature Sensor Component

#include <stdint.h>

uint16_t ReadTemperature(void)
{
    /* Simulated temperature input */
    uint16_t temperature = 85;

    return temperature;
}

9.2 Fan Control Component

#include <stdint.h>

uint8_t CalculateFanState(uint16_t temperature)
{
    if (temperature >= 80U)
    {
        return 1U;  /* Fan ON */
    }
    else
    {
        return 0U;  /* Fan OFF */
    }
}

9.3 Standalone Integration Demonstration

#include <stdio.h>
#include <stdint.h>

uint16_t ReadTemperature(void)
{
    return 85U;
}

uint8_t CalculateFanState(uint16_t temperature)
{
    if (temperature >= 80U)
    {
        return 1U;
    }

    return 0U;
}

int main(void)
{
    uint16_t temperature;
    uint8_t fan_state;

    temperature = ReadTemperature();

    fan_state = CalculateFanState(temperature);

    printf("Temperature: %u C\n", temperature);

    if (fan_state == 1U)
    {
        printf("Cooling Fan: ON\n");
    }
    else
    {
        printf("Cooling Fan: OFF\n");
    }

    return 0;
}

11. How the Actual AUTOSAR Tool Workflow Works

A real AUTOSAR implementation requires configuration and code generation using an AUTOSAR-compatible toolchain.

  1. Create the TemperatureSensor and FanControl SWCs.
  2. Define the sender-receiver interface.
  3. Create a provided port and a required port.
  4. Define the data element and its implementation data type.
  5. Connect the two components in the composition.
  6. Define runnable entities and their activation events.
  7. Map runnable entities to suitable OS tasks.
  8. Configure the ECU and generate the RTE.
  9. Implement the application runnable code.
  10. Build, integrate and test the ECU software.

14. Practical Concepts for Interviews

  • SWC separates application functionality into reusable components.
  • Ports define component communication interfaces.
  • Sender-receiver interfaces transfer data elements.
  • RTE provides the generated communication infrastructure.
  • Runnable entities contain executable application behavior.
  • OS tasks schedule runnable execution through configured mappings.
  • Rte_Read and Rte_Write are common sender-receiver access APIs.

15. Placement Interview Questions and Answers

Q1. What is an AUTOSAR Software Component?

An SWC is an application software unit with defined interfaces and behavior. It communicates through configured ports and the RTE.

Q2. What is RTE?

RTE stands for Runtime Environment. It provides ECU-specific communication between application software components and the underlying software infrastructure.

Q3. What is a sender-receiver interface?

It is an AUTOSAR communication interface used to transfer data elements from a sender component to receiver components.

Q4. What is a P-Port?

A provided port exposes an interface provided by a component.

Q5. What is an R-Port?

A required port represents an interface that a component requires from another component or the ECU environment.

Q6. What is a runnable entity?

It is an executable unit inside an SWC that is activated by a configured event.

Q7. What is Rte_Write()?

It is a generated RTE API used by a sender component to write data through a configured sender-receiver interface.

Q8. What is Rte_Read()?

It is a generated RTE API used by a receiver component to read data through a configured sender-receiver interface.

Q9. Does RTE replace the operating system?

No. The RTE and operating system have different responsibilities. The OS schedules tasks, while RTE provides configured communication and interaction mechanisms.

Q10. What happens if the sender and receiver data types differ?

The configuration tool may report an incompatibility, or communication may require a valid configured mapping or conversion. Compatible data definitions should be used.

Q11. What is runnable-to-task mapping?

It is the configuration that associates runnable execution with an operating system task.

Q12. Is the standalone C example a complete AUTOSAR application?

No. It demonstrates application logic only. A real AUTOSAR application also requires SWC descriptions, ports, interfaces, RTE generation, ECU configuration and integration.
