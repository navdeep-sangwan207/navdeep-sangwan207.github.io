1. Project Introduction

AUTOSAR ECU development involves configuring software components, the Runtime Environment, Basic Software modules, microcontroller drivers and communication interfaces.

Configuration tools are used to define these elements and generate configuration code and integration artifacts. This project demonstrates a simplified end-to-end configuration and integration workflow for an automotive temperature monitoring ECU.

1.1 Project Objectives

  • Understand AUTOSAR ECU configuration.
  • Study ARXML-based configuration and integration.
  • Configure Software Components and interfaces.
  • Understand RTE generation.
  • Configure selected BSW modules.
  • Understand MCAL configuration.
  • Study code generation and build integration.
  • Perform basic integration testing.

2. Project Scenario

Develop a simplified temperature monitoring ECU with the following functions:

  • Read temperature from a sensor interface.
  • Process the temperature in an application SWC.
  • Control a cooling fan based on temperature.
  • Transmit temperature information over CAN.
  • Report an over-temperature diagnostic event.

3. AUTOSAR Configuration Overview

AUTOSAR configuration defines how software components, interfaces, BSW modules and hardware resources work together. The configuration is represented using standardized models and configuration parameters.

3.1 Main Configuration Activities

  1. Define system architecture.
  2. Create software component descriptions.
  3. Define ports and interfaces.
  4. Map software components to the ECU.
  5. Configure RTE behavior.
  6. Configure required BSW modules.
  7. Configure MCAL and hardware resources.
  8. Validate configuration consistency.
  9. Generate configuration code.
  10. Build and integrate the ECU software.

4. ARXML Configuration

ARXML stands for AUTOSAR XML. It is an XML-based format used to describe AUTOSAR system models, software components, interfaces, ECU configuration and related artifacts.

4.1 Common ARXML Artifacts

Artifact Purpose
System Description Describes the overall system architecture.
SWC Description Describes software components, ports and behavior.
ECU Extract Contains the system information relevant to a particular ECU.
ECU Configuration Describes configuration values for BSW modules.
Data Type Description Defines application and implementation data types.
Communication Description Describes communication signals, mappings and related elements.

4.2 Example ARXML Structure

The following is a simplified illustrative XML fragment. Actual AUTOSAR ARXML requires the appropriate schema, namespace, package hierarchy and valid AUTOSAR elements. 

<?xml version="1.0" encoding="UTF-8"?>

<AUTOSAR xmlns="http://autosar.org/schema/r4.0">

    <AR-PACKAGES>

        <AR-PACKAGE>

            <SHORT-NAME>TemperatureSystem</SHORT-NAME>

        </AR-PACKAGE>

    </AR-PACKAGES>

</AUTOSAR>
This fragment illustrates the XML hierarchy only. It is not a complete, validated SWC or ECU configuration file and should not be imported as a production configuration.

5.3 Runnable Configuration

A runnable entity contains application behavior and is activated through configured RTE events. The runnable is mapped to an OS task as part of ECU configuration. 

Runnable:
    TemperatureRunnable

Event:
    TimingEvent

Period:
    100 ms

Mapped OS Task:
    Task_10ms or another configured task
The example's 100 ms runnable period should be mapped to a task configuration capable of providing the required timing. A task named Task_10ms would not automatically satisfy a 100 ms period without an appropriate activation strategy.

6. RTE Configuration and Generation

The Runtime Environment provides communication and access mechanisms between application software components and configured BSW services.

6.1 RTE Generation Workflow

  1. Define SWCs and their behavior.
  2. Configure ports and interfaces.
  3. Define runnable entities.
  4. Configure runnable activation events.
  5. Map runnables to OS tasks.
  6. Configure ECU-specific component instances.
  7. Validate component connections.
  8. Generate RTE source and header files.

6.2 Illustrative RTE Application Code

#include "Rte_FanControl_SWC.h"

void FanControlRunnable(void)
{
    uint16 temperature;

    if (Rte_Read_Temperature_RPort_TemperatureValue(
            &temperature) == RTE_E_OK)
    {
        if (temperature >= 80U)
        {
            /* Request fan ON */
        }
        else
        {
            /* Request fan OFF */
        }
    }
}

The generated header and API names depend on the SWC model, tool configuration and vendor implementation.

8. MCAL Configuration

The Microcontroller Abstraction Layer provides standardized drivers for supported microcontroller peripherals.

8.1 MCAL Modules

  • ADC – Analog-to-Digital Converter.
  • DIO – Digital Input/Output.
  • PORT – Pin configuration.
  • CAN – CAN controller driver.
  • SPI – Serial Peripheral Interface.
  • GPT – General Purpose Timer.
  • PWM – Pulse Width Modulation.
  • Wdg – Watchdog driver.

8.2 Example Configuration

Peripheral Configuration
ADC Temperature sensor input channel
DIO Digital fan enable output, if applicable
PORT Pin direction and electrical configuration
CAN Controller, baud rate and hardware objects
PWM Fan speed control output, if applicable
MCAL configuration is microcontroller-specific. A module must be supported by the selected MCU, AUTOSAR release and supplier package. The presence of a module in this list does not mean every ECU requires it.

11. Integration Process

Integration combines application software, generated RTE, BSW, MCAL, operating system and hardware-specific components into a working ECU software image.

11.1 Integration Steps

  1. Collect application and configuration artifacts.
  2. Verify AUTOSAR release and tool compatibility.
  3. Validate ARXML consistency.
  4. Generate RTE and configured BSW code.
  5. Integrate application source files.
  6. Resolve module dependencies and include paths.
  7. Configure compiler and linker settings.
  8. Compile all required modules.
  9. Resolve compilation and linking errors.
  10. Generate the ECU executable.
  11. Perform software and ECU-level tests.

12. Example Integration Problems

Problem Possible Cause Solution
RTE generation failure Invalid ports or unresolved references Validate SWC descriptions and component connections.
Compilation error Missing header or incompatible source Check include paths and module versions.
Undefined reference Missing implementation or library Check build inputs and link configuration.
CAN message not received Incorrect signal mapping or routing Check COM, PduR, CanIf and CAN configuration.
Task not activated Incorrect OS event or task mapping Inspect OS and RTE event configuration.
ADC value incorrect Incorrect channel or conversion configuration Check MCAL ADC setup and sensor scaling.

15. Placement Interview Questions and Answers

Q1. What is AUTOSAR configuration?

It is the process of defining and validating the software component, RTE, BSW and hardware-related parameters required to build an AUTOSAR ECU.

Q2. What is ARXML?

ARXML is an XML-based file format used to describe AUTOSAR models and configuration artifacts.

Q3. What is an ECU Extract?

An ECU Extract contains the relevant subset of system description information needed for development and configuration of a particular ECU.

Q4. Why is RTE generation required?

RTE generation creates ECU-specific communication and integration code connecting application SWCs with other software components and configured BSW services.

Q5. What is BSW configuration?

It defines parameters and relationships for required Basic Software modules, such as COM, OS, DEM, DCM and CanIf.

Q6. What is MCAL configuration?

It defines microcontroller-specific driver parameters such as ADC channels, DIO channels, CAN controllers and pin configurations.

Q7. What is code generation?

It is the process of generating source code and configuration artifacts from validated AUTOSAR models and configuration data.

Q8. What is ECU integration?

It is the process of combining application software, generated RTE, BSW, MCAL and other required components into a buildable and testable ECU software image.

Q9. Why should generated files not normally be edited manually?

Manual changes can be overwritten during regeneration and can make the build difficult to reproduce. The underlying model or configuration should normally be corrected instead.

Q10. Name some AUTOSAR configuration tools.

Vector DaVinci, EB tresos Studio and ETAS ISOLAR are examples of tools used in AUTOSAR development workflows.

Q11. What is the difference between a compiler and linker?

A compiler translates source code into object code. A linker combines object files and libraries, resolves symbols and produces the executable.

Q12. What should be checked before ECU integration?

Check AUTOSAR release compatibility, ARXML validity, configuration dependencies, generated artifacts, compiler settings, linker settings and hardware-specific configuration.
