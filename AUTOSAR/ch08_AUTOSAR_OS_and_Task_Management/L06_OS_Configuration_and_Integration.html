Lesson 6: OS Configuration and Integration

AUTOSAR OS and Task Management

Understand how AUTOSAR OS is configured, generated, integrated and verified in an automotive ECU.

1. Learning Objectives

  • Understand AUTOSAR OS configuration.
  • Identify important OS configuration parameters.
  • Understand tasks, alarms, counters and ISR configuration.
  • Learn the OS configuration and code generation workflow.
  • Understand OS integration with RTE and BSW modules.
  • Learn startup and shutdown sequences.
  • Understand OS testing, debugging and integration problems.

2. What Is AUTOSAR OS Configuration?

AUTOSAR OS configuration is the process of defining the operating system objects, scheduling behavior, interrupt handling and execution permissions required by an ECU software application.

Typical configuration objects include:

  • Tasks and task priorities.
  • Task activation limits and scheduling policies.
  • Events and resources.
  • Counters, alarms and schedule tables.
  • Interrupt Service Routines (ISRs).
  • OS applications and access permissions.
  • Timing protection and memory protection, where supported and configured.
AUTOSAR OS is generally configured statically. The configuration tool generates OS-related configuration data and code for the selected OS implementation.

3. Why Is OS Configuration Required?

Configuration is required to define:

  • Which tasks exist in the ECU.
  • Which task has higher or lower priority.
  • Which tasks are periodic or event-driven.
  • Which alarms activate tasks or set events.
  • Which resources protect shared hardware or data.
  • Which interrupts are handled by the OS.
  • Which software entities can access specific OS objects.

4. Important OS Configuration Parameters

Configuration Item Purpose
Task Name Identifies a configured task.
Task Priority Defines scheduling priority.
Task Type Defines Basic or Extended Task behavior.
Activation Limit Sets the maximum outstanding activations.
Preemption Configuration Defines whether and when a task can be preempted.
Event Configuration Defines events available to Extended Tasks.
Resource Configuration Defines shared resource protection.
Alarm Configuration Defines counter-based alarm actions.
ISR Configuration Associates interrupt sources with configured ISRs.

5. Task Configuration Example

Consider a temperature-monitoring ECU with three tasks.

Task Type Priority Purpose
SensorTask Basic 3 Reads sensor information.
ControlTask Basic 5 Calculates control output.
DiagnosticTask Extended 2 Waits for diagnostic events.

The priority values above are illustrative. The actual priority numbering and scheduling behavior depend on the OS configuration.

6. Counter and Alarm Configuration

Counters provide the time base used by alarms and schedule tables. An alarm can activate a task or set an event when its configured expiry condition is reached.

Example

  • Counter tick: 1 ms.
  • Alarm offset: 10 ticks.
  • Alarm cycle: 10 ticks.
  • Action: Activate SensorTask.

The alarm is configured to request periodic task activation according to its counter and timing parameters. 

/* Illustrative OS service usage */

SetRelAlarm(
    SensorAlarm,
    10,
    10
);
The counter tick duration is configuration-dependent. A 1 ms tick is only an example, not a universal AUTOSAR OS requirement. Alarm identifiers and startup configuration are generated by the selected OS toolchain.

7. ISR Configuration

Interrupt configuration associates hardware interrupt sources with the appropriate ISR and OS integration settings.

Typical configuration includes:

  • ISR name.
  • ISR category.
  • Interrupt source or vector.
  • Interrupt priority.
  • OS service permissions.
  • Related task activation or event notification.

8. AUTOSAR OS Configuration Workflow

  1. Requirement analysis: Identify ECU functions and their timing requirements.
  2. Task design: Identify task types, priorities and activation patterns.
  3. OS object configuration: Configure tasks, events, resources, counters and alarms.
  4. ISR configuration: Associate hardware interrupts with the required ISR categories.
  5. RTE mapping: Map runnable entities to configured OS tasks through the AUTOSAR configuration workflow.
  6. Code generation: Generate OS and related configuration artifacts.
  7. Integration: Integrate generated code with BSW, RTE, MCAL and application software.
  8. Build: Compile and link the ECU software.
  9. Verification: Test scheduling, timing, interrupts and application behavior.

9. AUTOSAR Configuration Tools

AUTOSAR development commonly uses configuration tools to configure ECU software components and generate integration artifacts.

Examples of commercial tool environments include:

  • Vector DaVinci Configurator.
  • EB tresos Studio.
  • ETAS ISOLAR-A and ISOLAR-B.
  • Vendor-specific AUTOSAR configuration environments.
Tool capabilities and supported AUTOSAR modules vary by product, release and license. The exact workflow is project-dependent.

10. Generated OS Configuration

After configuration, the toolchain generates or prepares OS-specific configuration artifacts.

These can include:

  • Task and ISR configuration data.
  • Alarm and counter configuration.
  • Event and resource definitions.
  • Generated identifiers and configuration headers.
  • OS initialization and integration code.

The exact filenames and structure depend on the selected OS vendor and project build environment.

11. OS Integration with RTE

AUTOSAR RTE connects software components and coordinates runnable activation according to the configured system design. OS tasks provide the execution context in which mapped runnables execute.

Integration Flow

  1. An SWC contains one or more runnable entities.
  2. Runnable activation is configured through the AUTOSAR model.
  3. The RTE maps runnable execution to an OS task context.
  4. The OS task is activated by the configured mechanism.
  5. The OS scheduler selects the task.
  6. The runnable executes in the selected task context.

12. OS Integration with BSW

Basic Software modules also depend on OS execution mechanisms for their scheduled activities.

BSW Module or Function OS Relationship
Communication Stack Scheduled main functions and interrupt-driven processing.
Diagnostic Communication Manager (DCM) Scheduled diagnostic processing.
Diagnostic Event Manager (DEM) Scheduled event and diagnostic processing.
Watchdog Manager (WdgM) Supervision of configured software execution.
ECU State Manager (EcuM) Coordinates ECU initialization and state transitions.

Actual task assignments and scheduling arrangements are defined by the ECU integration configuration.

13. OS Startup Sequence

The OS startup process initializes the configured operating system and makes the ECU software ready for normal operation.

Typical Simplified Sequence

  1. Processor reset and startup code execute.
  2. Low-level hardware and MCU initialization takes place.
  3. Required BSW initialization is performed.
  4. AUTOSAR OS initialization is invoked at the configured point.
  5. Startup hooks and configured startup behavior execute.
  6. Configured startup tasks become eligible for execution.
  7. RTE and application activities begin according to the integration design.
This is a simplified conceptual sequence. The exact order of OS initialization, BSW initialization, startup hooks and application startup depends on the ECU project and AUTOSAR integration design.

14. OS Shutdown

OS shutdown is performed when the ECU software needs to stop OS-controlled execution or transition into a shutdown process.

Typical considerations include:

  • Stopping or coordinating application activities.
  • Performing required shutdown operations.
  • Handling configured shutdown hooks.
  • Managing hardware and power-state transitions.
  • Recording relevant error or diagnostic information.

15. OS Hooks and Error Handling

AUTOSAR OS provides hooks that allow configured application or integration code to respond to specific OS lifecycle and error conditions.

Hook Purpose
StartupHook Executes during OS startup.
ShutdownHook Executes during OS shutdown.
ErrorHook Handles configured OS service errors.
PreTaskHook Executes before a task begins or resumes execution, according to OS rules.
PostTaskHook Executes after a task stops running, according to OS rules.

Hook availability, restrictions and invocation conditions must be checked against the selected AUTOSAR OS implementation.

16. OS Integration Testing

After configuration and code generation, the OS must be verified as part of the ECU software.

Important test activities include:

  • Verify task activation and termination.
  • Check task priority and scheduling behavior.
  • Verify periodic alarm activation.
  • Test event setting and waiting.
  • Verify resource acquisition and release.
  • Test ISR execution and task notification.
  • Measure task execution time and response time.
  • Check timing protection and memory protection where configured.
  • Verify startup and shutdown behavior.

17. Common OS Integration Problems

  1. Define the ECU software requirements.
  2. Configure the required OS tasks and priorities.
  3. Configure counters, alarms, events and resources.
  4. Configure interrupt handling.
  5. Map SWC runnables to OS tasks.

19. Interview Questions and Answers

Q1. What is AUTOSAR OS configuration?

It is the process of defining tasks, priorities, alarms, counters, events, resources, ISRs and other OS parameters for an ECU.

Q2. Why is OS configuration usually static?

Static configuration allows OS objects and scheduling behavior to be defined and generated before ECU execution, supporting predictable embedded system behavior.

Q3. What are the main OS configuration objects?

Tasks, events, resources, counters, alarms, schedule tables, ISRs and OS applications.

Q4. Name some AUTOSAR configuration tools.

Vector DaVinci Configurator, EB tresos Studio and ETAS ISOLAR are examples of AUTOSAR development tool environments.

Q5. What is the relationship between RTE and OS?

RTE coordinates runnable activation and communication, while OS manages task execution and scheduling.

Q6. What is an OS hook?

An OS hook is a configured callback invoked at a defined OS lifecycle or error condition.

Q7. What is ErrorHook()?

It is an OS hook used to handle configured OS service errors.

Q8. Why is OS integration testing required?

It verifies task scheduling, timing, interrupt handling, resource management and correct interaction with other ECU software.

Q9. What is the purpose of an alarm?

An alarm uses a counter to trigger an action, such as task activation or setting an event.

Q10. What happens after OS code generation?

Generated artifacts are integrated with the ECU software, compiled, linked and verified through appropriate tests.

20. Lesson Summary

  • AUTOSAR OS configuration defines the ECU's OS objects and behavior.
  • Tasks, priorities and activation limits determine task execution behavior.
  • Counters, alarms and schedule tables support time-based activation.
  • ISRs connect hardware interrupt sources to software handling.
  • RTE maps runnable execution to configured OS task contexts.
  • OS works with BSW and application software during ECU integration.
  • Configuration tools generate OS-related artifacts.
  • Integration testing verifies functional and timing behavior.
