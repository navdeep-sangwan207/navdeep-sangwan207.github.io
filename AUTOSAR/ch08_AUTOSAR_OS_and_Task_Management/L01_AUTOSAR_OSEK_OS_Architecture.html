Lesson 1: AUTOSAR OSEK OS Architecture

Chapter 8 – AUTOSAR OS and Task Management

Learn the OSEK/VDX foundation, AUTOSAR Classic OS architecture, operating system services and real-time execution concepts used in automotive ECUs.

1. Introduction to OSEK/VDX

OSEK/VDX is a standardized operating system and communication framework originally developed for automotive embedded systems.

OSEK stands for the German phrase "Offene Systeme und deren Schnittstellen für die Elektronik im Kraftfahrzeug", referring to open systems and their interfaces for automotive electronics. VDX refers to the French automotive initiative "Vehicle Distributed eXecutive".

The objective was to establish common software interfaces and operating system services for automotive electronic control units (ECUs).

Why was OSEK developed?

  • Automotive ECUs require predictable real-time execution.
  • Different manufacturers needed standardized OS interfaces.
  • Embedded controllers have limited memory and processing resources.
  • Multiple software activities must execute in a coordinated manner.
  • Software portability and reuse across automotive projects are important.

Important OSEK characteristics

  • Priority-based task management.
  • Real-time scheduling.
  • Interrupt handling.
  • Event and resource management.
  • Alarm and counter services.
  • Configuration-based operating system objects.

4. AUTOSAR OS Architecture

The AUTOSAR OS provides services to manage software execution on the ECU microcontroller.

Main architectural components

Component Function
Task Management Manages task activation, execution and termination.
Scheduler Selects the next eligible task for execution.
Interrupt Management Controls the handling of hardware and software interrupts.
Event Management Supports event-based synchronization of Extended Tasks.
Resource Management Controls access to shared resources.
Counter Management Provides time bases for OS timing services.
Alarm Management Triggers configured actions based on counter values.
Schedule Table Management Provides time-driven execution through configured expiry points.
OS Application Management Supports grouping and access control of OS objects where configured.

5. OS Conformance Classes and Scalability

The original OSEK OS specification introduced conformance classes to support different application requirements and system complexity.

Conformance Class General Characteristics
BCC1 Basic tasks, one activation per task, and limited task configuration complexity.
BCC2 Basic tasks with multiple activations permitted within configured limits.
ECC1 Extended tasks with event support, with one activation per task.
ECC2 Extended task functionality with additional activation capabilities.

These classes describe the traditional OSEK OS conformance model. AUTOSAR OS implementations and conformance requirements must be checked against the applicable AUTOSAR release and supplier documentation.

Why are conformance classes useful?

  • Allow systems to select suitable OS functionality.
  • Support different ECU complexity levels.
  • Help manage memory and processing requirements.
  • Provide a standardized way to describe OS capabilities.

7. Real-Time Scheduling Concept

A real-time operating system must provide predictable execution behavior so software can meet its timing requirements.

Important concepts

  • Task priority: Determines the relative scheduling importance of a task.
  • Preemption: Allows an eligible higher-priority task to interrupt a lower-priority running task, subject to OS scheduling rules.
  • Deadline: The time by which a particular operation must complete.
  • Execution time: The processor time needed by a task or operation.
  • Period: The interval between recurring activations of a periodic activity.

Example: Engine control ECU

9. Advantages of AUTOSAR OS

  • Standardization: Provides defined OS interfaces and services.
  • Predictability: Supports controlled real-time scheduling.
  • Modularity: Separates execution management from application functionality.
  • Reusability: Helps reuse software across compatible ECU platforms.
  • Scalability: Supports different ECU complexity and configuration requirements.
  • Integration: Works with AUTOSAR RTE and Basic Software modules.
  • Resource control: Provides mechanisms for shared resource management.

10. AUTOSAR OS vs FreeRTOS

Feature AUTOSAR Classic OS FreeRTOS
Primary domain Automotive ECU software General embedded systems
Standardization AUTOSAR OS specification, based on OSEK concepts RTOS implementation with its own API
Configuration Typically generated from ECU configuration Configured through project settings and application code
Task management Basic and Extended Tasks RTOS tasks
Event mechanism OS events for Extended Tasks Event groups and other synchronization primitives
Timing services Counters, alarms and schedule tables Software timers and tick-based timing services
Automotive integration Designed for AUTOSAR Classic architecture Requires integration with the application and automotive software architecture

Both can support embedded real-time applications, but they have different architectures, APIs and integration models.

11. Placement-Oriented Interview Questions

Q1. What is OSEK/VDX?

Answer: OSEK/VDX is an automotive standardization initiative that defined operating system and communication concepts for embedded automotive ECUs.

Q2. What is AUTOSAR OS?

Answer: AUTOSAR OS is the operating system module of the AUTOSAR Classic Platform. It manages tasks, interrupts, scheduling and timing services.

Q3. Is AUTOSAR OS based on OSEK?

Answer: Yes. AUTOSAR Classic OS builds on OSEK/VDX concepts and extends them with AUTOSAR-specific requirements.

Q4. In which layer is AUTOSAR OS located?

Answer: It is part of the Basic Software Services Layer.

Q5. What are the four traditional OSEK OS conformance classes?

Answer: BCC1, BCC2, ECC1 and ECC2.

Q6. What is the purpose of an OS scheduler?

Answer: It selects the next eligible task for execution according to configured scheduling rules and priorities.

Q7. What is static OS configuration?

Answer: It is the process of defining OS objects and their properties before code generation, compilation and deployment.

Q8. What is the relationship between RTE and AUTOSAR OS?

Answer: RTE coordinates software component runnable activation and communication. Runnable entities are mapped to OS tasks, and the OS schedules those tasks.

Q9. What is the difference between AUTOSAR OS and FreeRTOS?

Answer: AUTOSAR OS is designed for AUTOSAR Classic automotive ECU integration and follows the AUTOSAR OS specification. FreeRTOS is a general embedded RTOS with its own task and synchronization APIs.

Q10. Why is deterministic behavior important in automotive systems?

Answer: Automotive control functions must respond within specified timing constraints to maintain correct and safe system behavior.

12. Lesson Summary

  • OSEK/VDX established standardized OS concepts for automotive ECUs.
  • AUTOSAR Classic OS builds on OSEK/VDX concepts and adds AUTOSAR requirements.
  • AUTOSAR OS is located in the BSW Services Layer.
  • Its architecture includes task, interrupt, event, resource and timing services.
  • Traditional OSEK conformance classes are BCC1, BCC2, ECC1 and ECC2.
  • OS objects are typically configured before code generation and deployment.
  • RTE coordinates runnable activation, while OS schedules tasks.
