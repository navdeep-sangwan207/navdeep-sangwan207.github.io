Lesson 4: Interrupt Handling and ISRs

AUTOSAR OS and Task Management

Understand interrupt sources, ISR categories, interrupt control and their relationship with task scheduling.

1. Learning Objectives

  • Understand interrupts in automotive ECUs.
  • Differentiate hardware interrupts and software execution.
  • Explain Interrupt Service Routines (ISRs).
  • Understand AUTOSAR OS Category 1 and Category 2 ISRs.
  • Learn interrupt handling and OS interaction.
  • Understand interrupt latency and priority.
  • Relate interrupts to CAN, ADC, timers and communication peripherals.

2. What Is an Interrupt?

An interrupt is a signal that requests the processor to respond to an event that requires attention.

When an interrupt occurs, the processor temporarily suspends its current execution, saves the required execution context and transfers control to an interrupt handler.

Automotive Examples

  • CAN controller receives a message.
  • Timer reaches a configured match value.
  • ADC conversion completes.
  • UART receives a character.
  • External input pin changes state.
  • Hardware detects an error condition.
Example: When an ECU receives a CAN frame, the CAN controller can generate an interrupt. The processor then executes the configured interrupt handling routine to process or acknowledge the event.

3. What Is an ISR?

An Interrupt Service Routine (ISR) is a function or handler executed in response to a particular interrupt.

An ISR generally performs tasks such as:

  • Identifying the interrupt source.
  • Acknowledging or clearing the interrupt condition as required.
  • Reading hardware status or captured data.
  • Recording information in a buffer.
  • Notifying an OS task when appropriate.

Basic Interrupt Flow

  1. A peripheral generates an interrupt request.
  2. The interrupt controller detects the request.
  3. The processor accepts the interrupt according to its priority and masking rules.
  4. The processor transfers execution to the configured ISR.
  5. The ISR performs the required interrupt-level processing.
  6. The ISR completes and normal execution resumes or scheduling occurs as applicable.

4. Interrupts in AUTOSAR Classic

AUTOSAR Classic OS provides mechanisms to configure and manage interrupt service routines and their interaction with OS tasks.

Interrupt configuration includes details such as interrupt source, category, priority, handler association and hardware-specific configuration.

5. Category 1 ISR

A Category 1 ISR is an interrupt service routine with restricted interaction with AUTOSAR OS services.

  • It has limited OS service access.
  • It is generally intended for short and time-critical processing.
  • It does not use the normal Category 2 ISR OS-service interaction model.
  • Its execution and interrupt control are subject to the processor and OS integration rules.

Typical Use Cases

  • Very short hardware event handling.
  • Time-critical interrupt processing with minimal OS involvement.
  • Specific low-level hardware functions.

6. Category 2 ISR

A Category 2 ISR is an ISR integrated with AUTOSAR OS interrupt management. It can use the OS services permitted for its context.

  • It is configured and managed by AUTOSAR OS.
  • It can interact with supported OS services.
  • It can activate tasks or set events where permitted.
  • It participates in OS-managed interrupt and scheduling behavior.

Example

A CAN receive interrupt can be configured as a Category 2 ISR. After handling the required hardware-level work, it may activate a communication task to perform further processing.

Category 1 and Category 2 are AUTOSAR/OSEK OS interrupt categories. They should not be confused with the hardware interrupt priority levels of a particular microcontroller.

7. Category 1 vs Category 2 ISR

Task activation Not through the normal Category 2 ISR service model Supported where permitted
Typical application Short, low-level interrupt handling Interrupt handling requiring OS coordination

9. Interrupt Priority

Interrupt priority determines the relative urgency of interrupt requests according to the microcontroller's interrupt controller and OS integration.

Important concepts include:

  • Higher priority: An interrupt may be serviced before a lower-priority interrupt, subject to masking and controller rules.
  • Interrupt masking: Temporarily prevents selected interrupts from being accepted.
  • Nested interrupts: A higher-priority interrupt may interrupt a lower-priority ISR if the hardware and configuration permit it.
  • Interrupt latency: Time between an interrupt request and the beginning of its service.

10. Interrupt Latency

Interrupt latency is the delay between an interrupt request and the start of its ISR execution.

Factors affecting interrupt latency include:

  • Time spent with interrupts disabled or masked.
  • Currently executing ISR and interrupt nesting rules.
  • Processor interrupt response time.
  • Hardware interrupt controller behavior.
  • Memory and processor execution conditions.
Long ISRs and unnecessarily long interrupt-disabled sections can increase system latency and cause missed timing requirements.

11. Interrupt Control Services

AUTOSAR OS provides interrupt control services for supported interrupt contexts.

Service Purpose
SuspendAllInterrupts() Suspends all maskable interrupts according to OS and hardware rules.
ResumeAllInterrupts() Resumes interrupts suspended using the corresponding service.
SuspendOSInterrupts() Suspends the configured category of OS-managed interrupts.
ResumeOSInterrupts() Resumes the corresponding suspended OS-managed interrupts.
These services have strict nesting and usage rules. They are not interchangeable, and the exact interrupt masking behavior depends on the OS implementation and microcontroller architecture.

12. Example: CAN Receive Interrupt

Consider a CAN receive interrupt in an automotive ECU.

  1. The CAN controller receives a frame.
  2. The controller raises an interrupt request.
  3. The processor executes the configured CAN ISR.
  4. The ISR acknowledges the interrupt and performs the required minimal processing.
  5. The ISR makes the communication task READY using a permitted OS service.
  6. The OS scheduler selects the task according to scheduling rules.
  7. The task performs further CAN message processing.

Illustrative Category 2 ISR

ISR(CAN_Rx_ISR)
{
    /* Acknowledge or clear the hardware interrupt
       using the MCU/vendor-specific driver. */

    /* Notify the communication task */
    ActivateTask(CommunicationTask_ID);
}

This example is conceptual. Actual ISR declarations, interrupt acknowledgement, driver integration and permitted OS services depend on the AUTOSAR OS vendor and microcontroller.

13. Example: Timer Interrupt

A timer peripheral can generate an interrupt when a configured counter or compare value is reached.

Typical Flow

  1. Timer counter reaches its match value.
  2. Timer hardware generates an interrupt.
  3. The timer ISR executes.
  4. The ISR handles the timer status.
  5. A configured task can be activated or notified when required.

This technique is useful for periodic monitoring, control-loop timing and time-triggered activities.

14. ISR Design Best Practices

  • Keep interrupt routines short and predictable.
  • Perform only essential work inside the ISR.
  • Move lengthy processing to OS tasks.
  • Acknowledge hardware interrupt conditions correctly.
  • Use only OS services permitted in the ISR category.
  • Protect shared data using appropriate synchronization.
  • Avoid unnecessary interrupt disabling.
  • Measure interrupt latency and execution time during testing.

16. AUTOSAR ISR Configuration

During AUTOSAR configuration, interrupt-related parameters are defined according to the selected microcontroller and OS vendor.

Typical configuration items include:

  • ISR name and category.
  • Interrupt source or vector association.
  • Interrupt priority.
  • Interrupt enable configuration.
  • OS application or access permissions where applicable.
  • Associated task activation or event notification.

The configuration tool generates or integrates the necessary OS and microcontroller-specific code.

17. Interview Questions and Answers

Q1. What is an interrupt?

An interrupt is a request that causes the processor to temporarily suspend normal execution and handle an event.

Q2. What is an ISR?

An ISR is an interrupt handler executed when a configured interrupt occurs.

Q3. What are Category 1 and Category 2 ISRs?

Category 1 ISRs have restricted OS service interaction, while Category 2 ISRs are managed by AUTOSAR OS and can use supported OS services.

Q4. Can a Category 2 ISR activate a task?

Yes, where the service is permitted and the task and ISR configuration are valid.

Q5. Why should an ISR be short?

Long ISRs increase interrupt latency, delay other processing and can cause timing problems.

Q6. What is interrupt latency?

It is the time between an interrupt request and the start of the corresponding ISR.

Q7. What is interrupt nesting?

It is the execution of a higher-priority interrupt while a lower-priority ISR is already executing, when permitted by hardware and configuration.

Q8. What is the difference between an ISR and a task?

An ISR executes in interrupt context in response to an interrupt. A task executes under OS scheduling in task context.

Q9. Why move lengthy processing out of an ISR?

To keep interrupt response predictable and allow the OS scheduler to manage longer processing in task context.

Q10. What is the purpose of SuspendAllInterrupts()?

It suspends maskable interrupts according to the OS and hardware implementation, for a controlled critical section.

18. Lesson Summary

  • Interrupts allow hardware events to receive timely processor attention.
  • An ISR handles the corresponding interrupt.
  • Category 1 and Category 2 ISRs have different OS integration rules.
  • Category 2 ISRs can use permitted OS services.
  • Interrupt priority and masking affect response behavior.
  • Interrupt latency is an important real-time performance measure.
  • Long processing should generally be moved from ISR context to task context.
  • Interrupt configuration depends on the OS vendor and microcontroller.
Placement Preparation: Be prepared to explain Category 1 vs Category 2 ISR, ISR vs task, interrupt latency, interrupt nesting and how a CAN receive interrupt can notify an AUTOSAR communication task.
