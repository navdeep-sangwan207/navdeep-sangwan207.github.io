Lesson 3: Events, Resources and Scheduling

AUTOSAR OS and Task Management

Understand event-based task synchronization, shared resource protection and real-time scheduling.

1. Learning Objectives

After completing this lesson, you will be able to:

  • Explain events in AUTOSAR OS.
  • Differentiate Basic Tasks and Extended Tasks.
  • Use event-related OS services conceptually.
  • Explain resources and shared resource protection.
  • Understand priority inversion and priority ceiling.
  • Differentiate preemptive and non-preemptive scheduling.
  • Relate OS scheduling to AUTOSAR RTE runnable execution.

2. What Are Events in AUTOSAR OS?

An event is a synchronization mechanism used by an Extended Task to wait for a particular condition or occurrence.

Instead of continuously checking whether data is available, a task can wait for an event. Another task or an approved interrupt-level service can set that event.

Automotive Example

Consider a vehicle ECU receiving CAN messages. A communication task may wait until a particular CAN message has been received. When the message is ready, the event is set and the waiting task can become ready for execution.

Important: Only Extended Tasks can wait for events using the standard AUTOSAR OS event mechanism. Basic Tasks do not have the WAITING state associated with event waiting.

3. Event-Related OS Services

Service Purpose
WaitEvent() Allows an Extended Task to wait for one or more events.
SetEvent() Sets an event for a specified task.
ClearEvent() Clears specified event bits of the calling task.
GetEvent() Reads the current event mask of a task.

Event Masks

AUTOSAR OS represents events using event masks. Each event is assigned a bit position in the configured event mask. 

#define CAN_RX_EVENT       0x01
#define SENSOR_EVENT       0x02
#define DIAGNOSTIC_EVENT   0x04

For example, if CAN_RX_EVENT is set, the corresponding bit becomes active in the task's event mask.

4. Event-Based Task Execution

Consider a communication task that waits for a CAN reception event.

void CommunicationTask(void)
{
    EventMaskType receivedEvents;

    for(;;)
    {
        /* Wait until CAN reception event occurs */
        WaitEvent(CAN_RX_EVENT);

        /* Read the task's event mask */
        GetEvent(CommunicationTask_ID, &receivedEvents);

        if(receivedEvents & CAN_RX_EVENT)
        {
            /* Process received CAN data */
            ProcessCANMessage();

            /* Clear the processed event */
            ClearEvent(CAN_RX_EVENT);
        }
    }
}
Implementation note: This is illustrative AUTOSAR OS code. Actual task identifiers, event definitions, service signatures and generated configuration depend on the AUTOSAR release and OS vendor. The task must be configured as an Extended Task.

5. Extended Task State Transitions

An Extended Task can move between the following states:

  • SUSPENDED: The task is inactive.
  • READY: The task is eligible for execution.
  • RUNNING: The task is currently executing.
  • WAITING: The task is waiting for an event.

Typical Event Flow

  1. The Extended Task starts executing.
  2. It calls WaitEvent() for a configured event.
  3. If the required event has not occurred, the task enters WAITING.
  4. Another task or permitted service calls SetEvent().
  5. The waiting task becomes READY.
  6. The scheduler selects it according to scheduling rules.
  7. The task resumes and processes the event.
If the event is already set when WaitEvent() is called, the task does not need to enter the WAITING state; it can continue execution.

6. What Are Resources?

A resource is an AUTOSAR OS mechanism used to protect shared resources from conflicting access by tasks.

Examples of shared resources include:

  • Shared data structures.
  • SPI peripheral access.
  • Shared communication buffers.
  • Common memory areas.
  • Hardware registers requiring controlled access.

Example: Shared SPI Peripheral

Suppose two tasks need to communicate with different devices using the same SPI peripheral. If both tasks access the peripheral simultaneously, their operations may interfere.

A configured OS resource can serialize access so that only one eligible task holds the resource at a time.

7. Resource-Related OS Services

Service Purpose
GetResource() Requests ownership of a configured OS resource.
ReleaseResource() Releases a resource previously acquired by the task.

Illustrative Example

void SPITask(void)
{
    for(;;)
    {
        GetResource(SPI_RESOURCE);

        /* Protected SPI access */
        SPI_TransmitData();

        ReleaseResource(SPI_RESOURCE);

        /* Continue other processing */
    }
}

The resource must be released after the protected operation. The exact legal API usage and resource nesting rules depend on the OS configuration and applicable AUTOSAR OS specification.

8. Priority Inversion

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task holding a shared resource.

Example

  1. Low-priority Task L acquires a shared resource.
  2. High-priority Task H becomes ready and needs the same resource.
  3. Task H cannot obtain the resource while Task L holds it.
  4. Task L must finish its protected operation and release the resource.
  5. Task H can then proceed.

If medium-priority tasks repeatedly preempt Task L, Task H may experience an unexpectedly long delay.

9. Priority Ceiling Protocol

AUTOSAR OS resource management follows the OSEK-style priority ceiling resource protocol. The configured ceiling of a resource is based on the priorities of tasks that use it.

When a task obtains a resource, its effective scheduling priority is raised as required by the resource ceiling rules. This limits interference from other tasks and helps prevent unbounded priority inversion.

Placement concept: The resource protocol is not simply a normal mutex lock. It has OS-defined priority and nesting rules. Correct resource ceilings and configuration are essential.

Important Resource Rules

  • Use a resource only for its configured purpose.
  • Release a resource after completing the protected operation.
  • Follow the configured resource nesting order.
  • Avoid long operations while holding a resource.
  • Do not perform operations that violate OS resource restrictions.

10. What Is Task Scheduling?

Scheduling is the process by which AUTOSAR OS selects a READY task for execution on the processor.

Task selection depends on factors such as:

  • Task priority.
  • Task state.
  • Preemption configuration.
  • Resource ownership and scheduling restrictions.
  • OS scheduling rules.

11. Preemptive Scheduling

In preemptive scheduling, a higher-priority READY task can interrupt the execution of a lower-priority task when the OS reaches a permitted scheduling point.

Example

  • Task L is running at low priority.
  • Task H becomes READY at a higher priority.
  • The OS preempts Task L when permitted.
  • Task H executes.
  • After Task H finishes or blocks, Task L may resume.

12. Non-Preemptive Scheduling

In non-preemptive scheduling, a running task is not preempted merely because a higher-priority task becomes READY. The running task continues until it reaches a permitted scheduling point, such as termination, chaining or an applicable scheduling service.

Non-preemptive execution can increase the response time of higher-priority tasks. Long-running non-preemptive sections must therefore be avoided in time-critical ECU software.

13. Preemptive vs Non-Preemptive Scheduling

Feature Preemptive Non-Preemptive
Higher-priority task becomes READY Can preempt at a permitted scheduling point Does not automatically preempt the running task
Response time Generally better for urgent tasks Can be longer
Implementation complexity Higher Generally lower
Typical concern Context switching and shared data protection Long blocking execution periods

14. Same-Priority Task Scheduling

Tasks with equal priority are scheduled according to the applicable AUTOSAR OS scheduling rules and configuration. Do not assume that every OS implementation uses unrestricted round-robin scheduling.

Task activation limits, scheduling points and configuration influence when an equal-priority task gets processor time.

15. Relationship Between RTE and OS Scheduling

In AUTOSAR Classic, application software is organized into Software Components (SWCs). Their runnable entities are mapped to OS tasks through the configured RTE and OS scheduling setup.

  1. A sensor value or communication event occurs.
  2. The RTE coordinates the configured runnable activation.
  3. The mapped OS task becomes READY when appropriate.
  4. The AUTOSAR OS scheduler selects the task.
  5. The runnable executes within the task context.
The RTE handles communication and runnable activation according to the configured mapping. The OS handles task scheduling and execution control. They perform different but connected roles.

16. Automotive Example: Cooling Fan ECU

Consider an ECU controlling a vehicle cooling fan.

Function OS Concept
Receive temperature-related CAN data Event-based activation or task activation
Process temperature information Runnable mapped to an OS task
Access shared sensor data Resource protection where required
Calculate fan speed Task scheduling by priority
Update fan output Scheduled task execution and peripheral access

19. Interview Questions and Answers

Q1. What is an event in AUTOSAR OS?

An event is a synchronization mechanism that allows an Extended Task to wait for a particular condition or occurrence.

Q2. Can a Basic Task wait for an event?

No. Standard AUTOSAR OS event waiting is supported by Extended Tasks.

Q3. What is the purpose of WaitEvent()?

It allows an Extended Task to wait until one or more specified events are set.

Q4. What is the purpose of SetEvent()?

It sets the specified event for a task, potentially making a waiting Extended Task READY.

Q5. What is a resource in AUTOSAR OS?

A resource protects shared resources from conflicting access by tasks.

Q6. Which APIs are used for resource management?

GetResource() and ReleaseResource().

Q7. What is priority inversion?

It occurs when a high-priority task is delayed because a lower-priority task holds a resource it needs.

Q8. What is the priority ceiling protocol?

It is a resource management protocol that adjusts task execution priority according to configured resource ceilings to control priority inversion and resource access.

Q9. What is preemptive scheduling?

It allows a higher-priority READY task to preempt a lower-priority running task at a permitted scheduling point.

Q10. What is the relationship between RTE and OS?

RTE coordinates runnable activation and communication, while AUTOSAR OS schedules and manages the execution of the mapped tasks.

20. Lesson Summary

  • Events provide synchronization for Extended Tasks.
  • WaitEvent() waits for configured events.
  • SetEvent() sets an event for a task.
  • Resources protect shared data and hardware access.
  • GetResource() and ReleaseResource() manage resource ownership.
  • Priority ceiling rules help control priority inversion.
  • Preemptive and non-preemptive scheduling determine task execution behavior.
  • RTE runnable mapping and OS task scheduling work together.
Placement Preparation: Be prepared to explain the difference between events and resources, Basic and Extended Tasks, priority inversion, resource ceiling, and preemptive versus non-preemptive scheduling using an automotive ECU example.
