Lesson 5: UDS Diagnostic Services and CAN Diagnostics

Chapter 9 – Diagnostics and Error Management

1. Learning Objectives

  • Understand Unified Diagnostic Services (UDS).
  • Understand UDS service identifiers and request formats.
  • Learn important UDS services used in automotive ECUs.
  • Understand positive and negative diagnostic responses.
  • Understand CAN-based diagnostic communication.
  • Learn the role of ISO-TP, CanTp, PduR and DCM.
  • Understand practical diagnostic request and response examples.

2. What Is UDS?

UDS stands for Unified Diagnostic Services. It is an automotive diagnostic protocol specified by ISO 14229.

UDS defines diagnostic services that allow an external tester to communicate with an ECU. A tester can request diagnostic information, read data, change diagnostic sessions, perform supported routines and access other configured functions.

Applications of UDS

  • Reading diagnostic trouble codes.
  • Clearing supported diagnostic information.
  • Reading ECU identification data.
  • Changing diagnostic sessions.
  • Performing security access.
  • Executing supported diagnostic routines.
  • Supporting ECU programming and software download workflows.

3. UDS Request Structure

A UDS request generally contains a Service Identifier (SID) followed by service-specific parameters. 

    +----------------------+---------------------------+
    | Service Identifier   | Service Parameters        |
    +----------------------+---------------------------+
    | SID                  | Subfunction / DID / Data   |
    +----------------------+---------------------------+

Example: ReadDataByIdentifier

    Request:
        22 F1 90

    22 = ReadDataByIdentifier
    F1 90 = Example DID for VIN

    Positive Response:
        62 F1 90 [VIN Data]

    62 = Positive response SID

For many UDS services, the positive response SID is calculated by adding 0x40 to the request SID.

4. Important UDS Diagnostic Services

SID Service Name Purpose
0x10 DiagnosticSessionControl Changes the diagnostic session.
0x11 ECUReset Requests a supported ECU reset.
0x14 ClearDiagnosticInformation Requests clearing of supported diagnostic information.
0x19 ReadDTCInformation Reads supported DTC information.
0x22 ReadDataByIdentifier Reads configured diagnostic data.
0x27 SecurityAccess Performs configured security access.
0x2E WriteDataByIdentifier Writes configured diagnostic data.
0x31 RoutineControl Controls configured diagnostic routines.
0x3E TesterPresent Indicates that the tester remains active.

5. DiagnosticSessionControl – SID 0x10

DiagnosticSessionControl is used to request a change in the ECU's diagnostic session.

Common Session Subfunctions

Subfunction Session
0x01 Default Session
0x02 Programming Session
0x03 Extended Diagnostic Session 
    Request:
        10 03

    10 = DiagnosticSessionControl
    03 = Extended Diagnostic Session

    Positive Response:
        50 03 [Session Timing Parameters]

The ECU accepts or rejects the session request according to its configuration and current operating conditions.

6. ECUReset – SID 0x11

ECUReset allows a diagnostic tester to request a supported reset operation.

Common Reset Subfunctions

  • 0x01 – Hard Reset
  • 0x02 – Key Off On Reset
  • 0x03 – Soft Reset
    Example Request:
        11 01

    11 = ECUReset
    01 = Hard Reset

    Positive Response:
        51 01
Reset types and their availability depend on ECU implementation. A reset request may be restricted by diagnostic session, security level or vehicle operating conditions.

7. ReadDTCInformation – SID 0x19

ReadDTCInformation allows a diagnostic tester to request supported diagnostic trouble code information from an ECU.

Example

    Example request:
        19 02 FF

    19 = ReadDTCInformation
    02 = Example subfunction for reporting DTCs by status mask
    FF = Example DTC status mask

    Positive response:
        59 02 [Status Availability Mask] [DTC Records]

The returned information can include DTC identifiers and their supported status information.

8. ReadDataByIdentifier – SID 0x22

This service is used to read configured data from an ECU using a Data Identifier (DID).

Example: VIN Request

    Request:
        22 F1 90

    Positive Response:
        62 F1 90 [VIN Data]

DID 0xF190 is commonly used for the Vehicle Identification Number. Other DIDs may contain software versions, hardware information or manufacturer-specific data.

9. SecurityAccess – SID 0x27

SecurityAccess provides a mechanism for controlling access to protected diagnostic functions.

Seed-Key Concept

    Tester                         ECU
      |                             |
      |---- Request Seed ---------->|
      |                             |
      |<--- Seed -------------------|
      |                             |
      | Calculate Key               |
      |                             |
      |---- Send Key -------------->|
      |                             |
      |<--- Access Result ----------|

The ECU validates the key using its configured security mechanism. If access is granted, protected services may become available.

10. Negative Response Codes (NRC)

A negative response indicates that the ECU cannot process a diagnostic request as requested.

General Format

    7F [Request SID] [NRC]

Important NRC Values

NRC Name Meaning
0x10 GeneralReject General rejection.
0x11 ServiceNotSupported Requested service is not supported.
0x12 SubFunctionNotSupported Requested subfunction is not supported.
0x13 IncorrectMessageLengthOrInvalidFormat Request length or format is incorrect.
0x22 ConditionsNotCorrect Required operating conditions are not satisfied.
0x31 RequestOutOfRange Requested parameter or value is outside the permitted range.
0x33 SecurityAccessDenied Required security access is not available.
0x78 ResponsePending Request processing is still in progress. 
    Example:

    Request:
        22 F1 90

    Negative Response:
        7F 22 31

    7F = Negative response
    22 = Original request SID
    31 = Request out of range
NRC 0x78 means the ECU needs additional time to complete the requested processing. It is not the same as a final rejection.

11. What Is CAN-Based Diagnostics?

CAN-based diagnostics is the exchange of diagnostic messages between a diagnostic tester and an ECU over a Controller Area Network (CAN) bus.

CAN provides the data-link communication mechanism. UDS defines diagnostic services, while ISO 15765-2 defines the transport protocol commonly used to carry diagnostic messages over CAN.

Important Standards

Standard Purpose
ISO 14229 Unified Diagnostic Services (UDS).
ISO 15765-2 Diagnostic communication transport protocol over CAN.
ISO 11898 Controller Area Network communication standards.

12. Why Is ISO-TP Required?

Classical CAN carries a maximum of 8 data bytes in a single CAN frame. CAN FD supports a larger data field, up to 64 bytes. A diagnostic message may exceed the available payload of one CAN frame.

ISO-TP provides transport mechanisms to transfer larger diagnostic messages by dividing them into multiple frames and reassembling them at the receiver.

ISO-TP Frame Types

Frame Type Purpose
Single Frame (SF) Transfers a message that fits within one transport frame.
First Frame (FF) Starts a multi-frame message transfer.
Consecutive Frame (CF) Carries subsequent portions of a multi-frame message.
Flow Control (FC) Controls the sender's multi-frame transmission behavior.

13. ISO-TP Multi-Frame Communication

       Sender                         Receiver
         |                               |
         |------ First Frame ---------->|
         |                               |
         |<----- Flow Control ----------|
         |                               |
         |------ Consecutive Frame ---->|
         |------ Consecutive Frame ---->|
         |------ Consecutive Frame ---->|
         |                               |
         |       Message Complete        |

Flow Control Parameters

  • Block Size (BS): Number of consecutive frames allowed before another flow-control response is required. A value of zero means no further block-size limit for that transfer.
  • Separation Time (STmin): Minimum requested separation time between consecutive frames.
  • Flow Status (FS): Indicates whether the receiver allows, waits or rejects the transfer.
ISO-TP frame payload and addressing details depend on Classical CAN or CAN FD, addressing format and transport configuration.

15. Physical and Functional Addressing

Physical Addressing

Physical addressing targets a particular ECU. It is commonly used when a tester communicates with an individual ECU.

Functional Addressing

Functional addressing targets a group of ECUs or a functional diagnostic audience. Depending on the service and configuration, multiple ECUs may receive the request.

Not every UDS service supports functional addressing. ECU response behavior and addressing rules depend on the applicable diagnostic and transport configuration.

16. Practical Example – Reading DTCs over CAN

System Setup

  • One diagnostic tester.
  • One AUTOSAR-based ECU.
  • CAN communication interface.
  • CAN transport protocol.
  • DCM and DEM configured in the ECU.

Processing Steps

  1. The tester sends a UDS ReadDTCInformation request.
  2. The request is transmitted over CAN.
  3. CanIf receives the CAN communication data.
  4. CanTp processes the transport message.
  5. PduR routes the diagnostic request to DCM.
  6. DCM processes the UDS service.
  7. DCM obtains the requested diagnostic information through DEM.
  8. The response is routed back through the communication stack.
  9. The tester displays the DTC information.
    Example UDS request:
        19 02 FF

    Example positive response structure:
        59 02 [Status Availability Mask] [DTC Records]

    Note:
    Actual DTC records depend on the ECU's diagnostic configuration.

17. Placement Interview Questions and Answers

Q1. What is UDS?

UDS stands for Unified Diagnostic Services. It is an automotive diagnostic protocol specified by ISO 14229.

Q2. What is the UDS service identifier for ReadDTCInformation?

0x19.

Q3. What is the UDS service identifier for ReadDataByIdentifier?

0x22.

Q4. What is a negative response?

It indicates that a diagnostic request could not be processed as requested. Its general format starts with 0x7F.

Q5. What is NRC 0x78?

ResponsePending. It indicates that request processing is still in progress.

Q6. What is ISO-TP?

ISO-TP is the transport protocol specified by ISO 15765-2 for carrying diagnostic messages over CAN.

Q7. Why is ISO-TP required?

It allows diagnostic messages larger than a single CAN frame's available payload to be transferred through segmentation and reassembly.

Q8. Name the four ISO-TP frame types.

Single Frame, First Frame, Consecutive Frame and Flow Control.

Q9. What is the role of CanTp?

CanTp handles transport protocol functions such as segmentation, reassembly and flow control for CAN diagnostic communication.

Q10. What is the role of PduR?

PduR routes configured protocol data units between communication modules.

Q11. What is the difference between UDS and CAN?

UDS defines diagnostic services, whereas CAN provides a communication network over which diagnostic messages can be transported.

Q12. What is the difference between physical and functional addressing?

Physical addressing targets an individual ECU, whereas functional addressing targets a configured group or functional diagnostic audience.

19. Lesson Summary

  • UDS is specified by ISO 14229.
  • UDS defines diagnostic services used by testers and ECUs.
  • Positive responses commonly use request SID + 0x40.
  • Negative responses generally start with 0x7F.
  • ISO 15765-2 defines transport protocol functions for diagnostics over CAN.
  • ISO-TP supports Single, First, Consecutive and Flow Control frames.
  • CanTp handles transport protocol processing in AUTOSAR.
  • PduR routes configured PDUs.
  • DCM processes UDS services and DEM manages diagnostic event information.
