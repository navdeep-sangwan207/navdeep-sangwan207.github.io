Lesson 4: Diagnostic Communication Manager (DCM)

Chapter 9 – Diagnostics and Error Management

1. Learning Objectives

  • Understand the role of DCM in AUTOSAR Classic.

  • Prepare for AUTOSAR diagnostic placement interviews.

2. What Is DCM?

DCM stands for Diagnostic Communication Manager. It is an AUTOSAR Classic Basic Software module responsible for diagnostic communication between an external diagnostic tester and an ECU.

DCM processes supported diagnostic requests, checks whether requested services are permitted, invokes the appropriate diagnostic functionality and generates responses.

Examples of Diagnostic Operations

  • Read diagnostic trouble codes.
  • Read ECU identification data.
  • Clear supported diagnostic information.
  • Change diagnostic sessions.
  • Perform configured security access.
  • Execute supported diagnostic routines.
  • Write configured diagnostic data identifiers.

4. Main Responsibilities of DCM

Function Description
Request Reception Receives diagnostic requests routed through the configured communication stack.
Service Processing Identifies and processes supported UDS services.
Session Management Controls diagnostic session transitions and service availability.
Security Access Handles configured diagnostic security mechanisms.
Data Access Coordinates configured reading and writing of diagnostic data.
Response Handling Generates positive or negative diagnostic responses.
Timing Management Manages applicable diagnostic communication timing requirements.

5. DCM Functional Submodules

5.1 Diagnostic Session Layer (DSL)

DSL manages diagnostic communication behavior such as diagnostic sessions, timing and communication-related state.

  • Manages diagnostic session state.
  • Handles applicable diagnostic timing.
  • Coordinates diagnostic request and response communication.
  • Supports configured protocol and connection handling.

5.2 Diagnostic Service Processing Layer (DSP)

DSP processes supported diagnostic services. It performs the service-specific handling and coordinates access to the appropriate diagnostic information or functions.

  • Processes configured UDS services.
  • Validates service parameters.
  • Coordinates data and routine access.
  • Creates service-specific response information.

5.3 Diagnostic Session Layer and Service Interface (DSD)

DSD is the Diagnostic Service Dispatcher. It identifies the requested service and dispatches it to the appropriate service processing functionality, subject to configured checks.

The traditional DCM functional decomposition is DSL, DSD and DSP. Remember their roles: DSL manages communication state, DSD dispatches services, and DSP processes diagnostic services.

6. Diagnostic Sessions

UDS diagnostic sessions determine which diagnostic services and functions are available at a particular point in the diagnostic communication.

Common UDS Session Types

Session SID / Subfunction Purpose
Default Session 0x10 0x01 Normal diagnostic communication state.
Programming Session 0x10 0x02 Supports configured ECU programming operations.
Extended Diagnostic Session 0x10 0x03 Enables additional configured diagnostic services.

A tester uses DiagnosticSessionControl (SID 0x10) to request a session transition. The ECU checks whether the requested session is supported and permitted.

Session availability and service permissions are ECU-specific. A programming session does not automatically permit every programming operation.

7. Security Access

SecurityAccess (UDS SID 0x27) provides a mechanism for restricting access to protected diagnostic services.

Conceptual Seed-Key Process

    Diagnostic Tester             ECU / DCM
           |                          |
           |---- Request Seed ------->|
           |                          |
           |<--- Seed Response -------|
           |                          |
           | Calculate Key            |
           |                          |
           |---- Send Key ----------->|
           |                          |
           |<--- Access Result -------|
           |                          |
           | Protected service may    |
           | now be permitted         |

The seed-key algorithm is manufacturer-specific or otherwise defined by the applicable security design. The DCM coordinates the configured security access mechanism.

SecurityAccess is not encryption by itself. A robust ECU security design must use an appropriate security mechanism and protect against replay, brute-force and other attacks.

8. UDS Request and Response Processing

UDS is specified by ISO 14229. A diagnostic request contains a service identifier (SID) followed by service-specific parameters.

Positive Response

For many UDS services, the positive response service identifier is the request SID plus 0x40. 

    Example:

    Request SID:
        0x22 - ReadDataByIdentifier

    Positive Response SID:
        0x62

    Request:
        22 F1 90

    Positive response:
        62 F1 90 [Data bytes]

Negative Response

A negative response generally begins with 0x7F, followed by the original request SID and a Negative Response Code (NRC). 

    General negative response format:

    7F [Original Request SID] [NRC]

    Example:
    7F 22 31

    7F = Negative response
    22 = Original service
    31 = Request out of range
The examples are illustrative. Actual request acceptance and response contents depend on service parameters, session, security, configuration and ECU implementation.

9. Important UDS Services Handled by DCM

SID UDS Service Purpose
0x10 DiagnosticSessionControl Changes diagnostic session.
0x11 ECUReset Requests a supported ECU reset.
0x14 ClearDiagnosticInformation Requests clearing of supported diagnostic information.
0x19 ReadDTCInformation Reads supported DTC information.
0x22 ReadDataByIdentifier Reads configured diagnostic data.
0x27 SecurityAccess Performs configured security access.
0x2E WriteDataByIdentifier Writes configured diagnostic data.
0x31 RoutineControl Starts, stops or requests results of configured routines.
0x3E TesterPresent Indicates that the tester remains active.

10. Diagnostic Data Identifiers (DIDs)

A Data Identifier (DID) is a configured identifier used to access specific ECU data through UDS services.

ReadDataByIdentifier (SID 0x22) is used to request configured data. WriteDataByIdentifier (SID 0x2E) is used to write data when the ECU supports and permits the operation.

Example DID Requests

Example DID Possible Data
0xF190 Vehicle Identification Number (VIN) in common UDS usage.
Manufacturer-specific DID ECU software version, hardware number or configured sensor data.
DID assignments and data formats must follow the applicable diagnostic specification and ECU configuration. Do not assume that every ECU supports the same DIDs.

12. Diagnostic Communication over CAN

In a CAN-based ECU, diagnostic messages are transported through the configured communication stack. 

    Diagnostic Tester
          |
          v
       CAN Bus
          |
          v
        CanIf
          |

        CanTp

        PduR
          |
          v
        DCM
          |

CanTp supports segmentation and reassembly when diagnostic messages require transport beyond the payload capacity of a single CAN frame. PduR routes configured protocol data units.

DCM handles diagnostic services; CanTp handles transport protocol functions. These are separate responsibilities.

13. Practical Example – Reading ECU Software Version

System Description

A service technician wants to read the ECU software version using a diagnostic tester.

Request and Response Flow

  1. The tester sends a ReadDataByIdentifier request using SID 0x22.
  2. The request contains the configured software-version DID.
  3. The communication stack routes the request to DCM.
  4. DCM checks the service and applicable diagnostic conditions.
  5. DCM obtains the configured data through the relevant interface.
  6. DCM creates a positive or negative response.
  7. The response is routed back to the tester.
    Tester Request:
        22 [DID High Byte] [DID Low Byte]

    ECU Positive Response:
        62 [DID High Byte] [DID Low Byte] [Data]

The actual DID and returned software-version format are determined by ECU diagnostic configuration.

14. Placement Interview Questions and Answers

Q1. What is DCM in AUTOSAR?

DCM stands for Diagnostic Communication Manager. It processes diagnostic communication between an external tester and an ECU.

Q2. What are the three traditional DCM submodules?

DSL (Diagnostic Session Layer), DSD (Diagnostic Service Dispatcher) and DSP (Diagnostic Service Processing).

Q3. What is the purpose of DSL?

DSL manages diagnostic session state, timing and communication-related behavior.

Q4. What is the purpose of DSD?

DSD dispatches diagnostic services to the appropriate processing functionality.

Q5. What is the purpose of DSP?

DSP processes supported diagnostic services and coordinates access to diagnostic data and functions.

Q6. Which UDS service changes the diagnostic session?

DiagnosticSessionControl, SID 0x10.

Q7. Which UDS service is used for security access?

SecurityAccess, SID 0x27.

Q8. What is a DID?

A Data Identifier is a configured identifier used to access diagnostic data through supported UDS services.

Q9. What is the difference between DCM and DEM?

DCM manages diagnostic communication, while DEM manages diagnostic events and associated DTC information.

Q10. What is a negative response?

It is a UDS response indicating that a diagnostic request could not be processed as requested. It generally begins with 0x7F.
