2. What Is Diagnostic Testing?

Diagnostic testing verifies whether an ECU and its connected systems operate within specified conditions. It checks whether faults are detected, reported, stored and communicated correctly.

Objectives

  • Detect sensor and actuator failures.
  • Verify diagnostic event reporting.
  • Verify DTC storage and retrieval.
  • Test diagnostic communication with an external tester.
  • Verify fault recovery and event status transitions.
  • Check diagnostic behavior after ECU restart.

4. Types of Automotive Diagnostic Faults

Fault Type Example
Sensor Fault Temperature sensor open circuit or short circuit.
Actuator Fault Motor or relay fails to respond.
Communication Fault CAN message timeout or missing communication.
Power Supply Fault ECU supply voltage outside the permitted range.
Memory Fault Configured memory integrity or access failure.
Software Fault Unexpected software state or failed internal monitoring.

5. Diagnostic Event Reporting to DEM

A software component or diagnostic monitor detects a fault and reports its status to the Diagnostic Event Manager (DEM).

Depending on the configured interface and AUTOSAR release, diagnostic event status can be reported using mechanisms such as Dem_SetEventStatus() or a configured monitor-function interface.

Conceptual Example

    if (sensor_value > MAX_LIMIT)
    {
        /* Report failed diagnostic event */
        Dem_SetEventStatus(
            DEM_EVENT_ID_TEMPERATURE,
            DEM_EVENT_STATUS_FAILED
        );
    }
    else
    {
        /* Report passed diagnostic event */
        Dem_SetEventStatus(
            DEM_EVENT_ID_TEMPERATURE,
            DEM_EVENT_STATUS_PASSED
        );
    }
This is illustrative AUTOSAR-style pseudocode. Exact API signatures, generated event identifiers and reporting methods depend on the AUTOSAR release and supplier implementation.

6. Diagnostic Debouncing

Debouncing prevents short-duration or temporary signal variations from being immediately treated as confirmed faults.

Common Debouncing Methods

6.1 Counter-Based Debouncing

A fault counter increases when a failure is detected and decreases or resets when the monitor reports normal operation, according to the configured algorithm. 

    Fault detected:
        Counter increases

    Normal condition:
        Counter decreases or resets

    Counter reaches configured threshold:
        Fault may be confirmed

6.2 Time-Based Debouncing

The monitor evaluates how long a fault condition remains present. A fault may be qualified after the configured time threshold.

Debouncing thresholds and algorithms are configured for each diagnostic event. A confirmed fault is not necessarily stored immediately in non-volatile memory; storage behavior is also configuration-dependent.

7. DTC Status and Fault Confirmation

A Diagnostic Trouble Code (DTC) represents a diagnostic fault identified by a configured code. DEM manages associated event and DTC information.

Common UDS DTC Status Bits

Bit Name Meaning
0 TestFailed Monitor has detected a failure.
1 TestFailedThisOperationCycle Failure detected during the current operation cycle.
2 PendingDTC DTC has met the applicable pending criteria.
3 ConfirmedDTC DTC has met the applicable confirmation criteria.
4 TestNotCompletedSinceLastClear Test has not completed since the last clear operation.
5 TestFailedSinceLastClear Failure has been detected since the last clear operation.
6 TestNotCompletedThisOperationCycle Test has not completed during the current operation cycle.
7 WarningIndicatorRequested Associated warning indicator request is active.
These are the standard UDS DTC status-bit meanings. Whether a particular bit is supported or set depends on the ECU diagnostic configuration and monitor behavior.

8. Event Memory and Freeze Frame Data

DEM can maintain diagnostic event information and associated records according to configuration.

Freeze Frame Data

Freeze frame data captures selected operating parameters associated with a diagnostic event. It can help engineers understand the conditions under which a fault occurred.

Example Freeze Frame Parameters

  • Engine speed.
  • Vehicle speed.
  • Coolant temperature.
  • Battery voltage.
  • Sensor measurement value.
  • Operating condition or load information.

Extended Data

Extended data contains additional diagnostic information configured for a DTC, such as fault occurrence counters or other event-related records.

9. Diagnostic Testing Using UDS

A diagnostic tester can verify ECU diagnostic behavior by sending UDS requests and analyzing the responses.

Test Operation UDS SID Purpose
Change diagnostic session 0x10 Verify supported session transitions.
Read DTC information 0x19 Verify DTC reporting.
Clear diagnostic information 0x14 Verify supported DTC clearing behavior.
Read ECU data 0x22 Verify configured DID access.
Tester presence 0x3E Verify tester-present handling.
Execute routine 0x31 Verify configured diagnostic routines.

10. CAN Diagnostic Testing Tools

  • CANoe: CAN network simulation, analysis and testing.
  • CANalyzer: CAN traffic monitoring and analysis.
  • PCAN-View: CAN message monitoring with supported PEAK hardware.
  • CAN USB Interface: Connects a computer to a physical CAN network.
  • UDS Diagnostic Tester: Sends diagnostic requests and interprets responses.
  • Oscilloscope: Helps inspect CANH and CANL electrical signals.
  • Multimeter: Checks supply voltage, ground and resistance where appropriate.
Software tools alone cannot verify physical CAN wiring or electrical signal quality. Hardware measurements require suitable test equipment and safe access to the vehicle or ECU network.

11. CAN Communication Troubleshooting

Problem Possible Cause Checks
No CAN communication Power, wiring, termination or configuration issue. Check ECU supply, ground, CANH/CANL and bitrate.
Bus-off condition Excessive CAN transmission errors. Inspect wiring, bit timing, transceiver and bus errors.
Incorrect message reception Identifier or filter configuration mismatch. Check CAN IDs, masks and communication configuration.
UDS timeout Missing response or transport/application delay. Inspect tester timing, DCM processing and transport flow.
ISO-TP transfer failure Flow-control or sequence problem. Inspect FF, FC and CF frames, block size and STmin.
Negative UDS response Unsupported service or unmet conditions. Decode NRC and check session, security and parameters.

12. Physical CAN Bus Checks

12.1 CAN Termination

A conventional high-speed CAN network typically uses two 120-ohm termination resistors, one at each physical end of the bus.

With the network powered down and isolated appropriately, resistance measured between CANH and CANL is commonly approximately 60 ohms when both 120-ohm terminators are connected in parallel.

12.2 CAN Wiring

  • Inspect CANH and CANL connections.
  • Check for open circuits and short circuits.
  • Check connector pin assignments.
  • Inspect grounding and shielding where applicable.
  • Check the physical bus topology and termination locations.

12.3 CAN Signal Inspection

An oscilloscope can help inspect differential CAN signaling. On a conventional high-speed CAN bus, the recessive state has CANH and CANL near the same common-mode voltage, while the dominant state produces a differential voltage between them.

Resistance checks must be performed with power removed and the network in a safe, appropriate measurement condition. Do not disconnect or probe live vehicle wiring without following the applicable service procedures.

15. Practical Example – Engine Temperature Sensor Fault

System Description

An ECU monitors an engine temperature sensor. The sensor signal is expected to remain within a configured operating range.

Fault Scenario

  1. The sensor signal becomes invalid or exceeds the configured range.
  2. The diagnostic monitor detects the fault.
  3. The monitor reports the event to DEM.
  4. DEM applies the configured debouncing algorithm.
  5. The event and associated DTC status are updated.
  6. Configured event memory records may be stored.
  7. A diagnostic tester sends a ReadDTCInformation request.
  8. DCM obtains the diagnostic information and returns a UDS response.
  9. The technician checks the fault and investigates the sensor circuit.

Possible Troubleshooting Checks

  • Inspect sensor connector and wiring.
  • Check sensor supply and ground.
  • Measure the sensor output according to its specification.
  • Check ADC input and scaling in the ECU software.
  • Check diagnostic monitor thresholds.
  • Verify DEM event reporting and DTC status.
  • Read the DTC and relevant records using a diagnostic tester.

16. Diagnostic Test Case Format

A diagnostic test case should define the preconditions, test procedure and expected result.

Test Case Verify DTC detection and reporting
Precondition ECU is powered and diagnostic communication is available.
Test Input Apply a controlled sensor fault condition.
Expected Monitor Result Diagnostic monitor detects the configured fault.
Expected DEM Result Event status changes according to configured debouncing.
Diagnostic Request Send a supported ReadDTCInformation request (SID 0x19).
Expected Response Configured DTC information is returned.
Pass Criteria Observed behavior matches the ECU diagnostic specification.

17. Diagnostic Troubleshooting Methodology

  1. Identify the problem: Record the reported fault, symptoms and operating conditions.
  2. Read diagnostic information: Retrieve supported DTCs and status information.
  3. Check communication: Verify CAN communication and UDS request/response behavior.
  4. Inspect hardware: Check power, ground, connectors, wiring and sensor signals.
  5. Inspect software: Verify monitor logic, event reporting and diagnostic configuration.
  6. Reproduce the fault: Apply a controlled test condition where safe and permitted.
  7. Verify the repair: Confirm that the monitor completes successfully and the fault is no longer active.
  8. Document results: Record test conditions, diagnostic responses and corrective actions.
Clearing a DTC does not repair the underlying fault. Always verify the actual fault condition and confirm correct monitor behavior after repair.

18. Placement Interview Questions and Answers

Q1. What is diagnostic testing?

Diagnostic testing verifies that faults are detected, reported, stored and communicated correctly by an ECU.

Q2. What is diagnostic debouncing?

It filters temporary fault conditions using configured counter- based or time-based qualification mechanisms.

Q3. What is a DTC?

A Diagnostic Trouble Code identifies a configured diagnostic fault condition.

Q4. What is freeze frame data?

It is a configured record of operating parameters associated with a diagnostic event.

Q5. What is the difference between pending and confirmed DTC?

A pending DTC indicates that applicable pending criteria have been met. A confirmed DTC indicates that the configured confirmation criteria have been satisfied.

Q6. What is the purpose of DEM?

DEM manages diagnostic events, event status, DTC-related information and configured diagnostic records.

Q7. What is the purpose of DCM?

DCM manages diagnostic communication and processes supported diagnostic services.

Q8. How do you troubleshoot a CAN communication failure?

Check ECU power and ground, CANH/CANL wiring, termination, bitrate, transceiver operation, communication configuration and CAN error information.

Q9. Why might a DTC not be stored?

The event may not be reported, debouncing criteria may not be satisfied, or event-memory and storage configuration may prevent the expected record.

Q10. Does clearing a DTC fix a fault?

No. Clearing removes supported stored diagnostic information; it does not correct the physical or software cause of the fault.
