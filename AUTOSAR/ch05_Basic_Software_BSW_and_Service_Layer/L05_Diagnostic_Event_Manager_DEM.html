Lesson 5: Diagnostic Event Manager (DEM)

AUTOSAR Basic Software – Diagnostic Events, DTCs and Fault Memory

1. Introduction to DEM

DEM stands for Diagnostic Event Manager. It is an AUTOSAR Basic Software module responsible for processing and managing diagnostic events reported by software components and other configured modules.

In an automotive ECU, sensors, actuators and electronic circuits are continuously monitored. When a fault is detected, the responsible software reports a diagnostic event. DEM processes the event, maintains its status and manages associated diagnostic information.

Important responsibilities include:

  • Processing diagnostic event reports.
  • Managing event status information.
  • Managing Diagnostic Trouble Codes (DTCs).
  • Handling event debouncing.
  • Managing diagnostic event memory.
  • Providing diagnostic information to other modules.

3. What is a Diagnostic Event?

A diagnostic event represents a monitored fault condition or abnormal behavior in an ECU.

Automotive examples

  • Engine temperature exceeds a configured limit.
  • Battery voltage is outside the permitted range.
  • A sensor signal is missing or invalid.
  • An actuator circuit has an open-load condition.
  • Communication with another ECU is interrupted.
  • A monitored hardware component reports a failure.

The software responsible for monitoring a condition reports the corresponding diagnostic event to DEM.

4. Diagnostic Event and DTC

A diagnostic event and a Diagnostic Trouble Code (DTC) are related, but they are not identical.

Diagnostic Event Diagnostic Trouble Code (DTC)
Represents a monitored fault condition. Identifies a diagnostic fault for external diagnostic reporting.
Used internally for event processing. Used by diagnostic services and testers.
Has an event status and configured properties. Has a configured code and associated diagnostic information.

An event can be associated with a configured DTC. Multiple events may also be associated with a DTC depending on the diagnostic configuration.

A DTC is not simply the event's memory address or event ID. Its relationship to diagnostic events is defined through the ECU diagnostic configuration.

A simplified diagnostic event processing flow is:

Processing stages

  1. Fault monitoring: A software component monitors a sensor, actuator or system condition.
  2. Event reporting: The responsible software reports the event to DEM.
  3. Debouncing: DEM applies the configured qualification mechanism where applicable.
  4. Status update: DEM updates the diagnostic event status.
  5. DTC processing: Associated DTC information is updated according to the configuration.
  6. Memory management: Qualified diagnostic information may be stored in event memory.

6. Diagnostic Event Status

DEM maintains status information to describe the condition and history of a diagnostic event.

Important UDS-related DTC status bits include:

Status Bit Meaning
TestFailed The diagnostic test has currently failed.
TestFailedThisOperationCycle The test failed during the current operation cycle.
PendingDTC The DTC has met the configured pending criteria.
ConfirmedDTC The DTC has met the configured confirmation criteria.
TestNotCompletedSinceLastClear The test has not completed since the last clear operation.
TestFailedSinceLastClear The test has failed at least once since the last clear operation.
TestNotCompletedThisOperationCycle The test has not completed in the current operation cycle.
WarningIndicatorRequested A warning indicator is requested according to configured conditions.
These are the standardized UDS DTC status-bit meanings. Their current values depend on event processing, operation cycles, aging, clearing and ECU configuration.

7. Event Debouncing

Debouncing is used to prevent temporary or unstable signals from being immediately treated as confirmed faults.

Example: Battery Voltage Monitoring

Assume an ECU monitors battery voltage. A fault is suspected when voltage falls below a configured threshold. 

        Battery Voltage
               |
               v
        Compare with Threshold
               |
               v
        Fault Condition Detected
               |
               v
        Debouncing Mechanism
               |
        -------------------------
        |                       |
        Fault Qualifies      Fault Does Not
        as Failed             Qualify
        |                       |
        v                       v
        DEM Records          No Confirmed
        Failure Status       Failure Status

Common debouncing approaches

  • Counter-based: A counter increases or decreases according to reported test results and configured thresholds.
  • Time-based: The fault condition must remain present for a configured period before it qualifies as a failure.

Debouncing helps avoid false diagnostic reports caused by short-duration electrical disturbances or noisy sensor signals.

8. Diagnostic Event Memory

DEM manages configured diagnostic event memory. This allows diagnostic information to be retained for later analysis and retrieval.

Important concepts

  • Primary memory: A commonly used event memory area for diagnostic information.
  • Secondary memory: An additional configured memory area where supported and required.
  • Permanent memory: A specialized memory concept used for particular diagnostic requirements where configured.
  • Freeze-frame data: Contextual data captured in association with a diagnostic event.
  • Extended data: Additional diagnostic information associated with an event or DTC.

Event memory storage and retention depend on configured memory size, event priority, storage conditions and diagnostic requirements.

9. Freeze-Frame and Extended Data

9.1 Freeze-Frame Data

Freeze-frame data provides selected operating information captured when a diagnostic event meets configured storage conditions.

Example information may include:

  • Engine speed.
  • Battery voltage.
  • Coolant temperature.
  • Vehicle speed.
  • Sensor readings.

9.2 Extended Data

Extended data provides additional diagnostic information associated with an event or DTC, such as configured occurrence-related or aging-related information.

Freeze-Frame Data Extended Data
Captures selected operating conditions. Stores additional diagnostic information.
Helps understand the conditions when a fault occurred. Helps understand diagnostic history and event behavior.

10. DEM APIs and Event Reporting

AUTOSAR provides standardized interfaces for diagnostic event reporting and querying. The exact available APIs depend on the configured software interface and AUTOSAR release.

Important API examples

API Purpose
Dem_SetEventStatus() Reports a diagnostic event status using the configured event ID.
Dem_GetEventStatus() Retrieves diagnostic event status information.
Dem_GetDTCStatusAvailabilityMask() Retrieves the availability mask for DTC status bits.
Dem_GetStatusOfDTC() Retrieves the status of a configured DTC through the supported interface.
Dem_ClearDTC() Requests clearing of diagnostic information for the specified DTC group.
These are illustrative API names from AUTOSAR DEM interfaces. Some APIs are intended for internal software interfaces and others for diagnostic services. Do not assume every API is directly callable by every SWC.

Conceptual C example

#include "Dem.h"

void BatteryVoltageMonitor(void)
{
    if (BatteryVoltage < MIN_VOLTAGE)
    {
        Dem_SetEventStatus(
            DEM_EVENT_ID_BATTERY_LOW,
            DEM_EVENT_STATUS_FAILED
        );
    }
    else
    {
        Dem_SetEventStatus(
            DEM_EVENT_ID_BATTERY_LOW,
            DEM_EVENT_STATUS_PASSED
        );
    }
}

This example demonstrates the reporting concept only. The event identifier, generated symbols, header access and permitted calling context must match the ECU's DEM configuration and generated interfaces.

12. DEM Configuration

DEM behavior is defined through ECU-specific diagnostic configuration.

Important configuration elements

  • Diagnostic event identifiers.
  • DTC identifiers and event-to-DTC associations.
  • Event reporting and qualification conditions.
  • Debouncing configuration.
  • Operation cycle configuration.
  • Event memory and storage conditions.
  • Freeze-frame and extended data records.
  • DTC status and aging-related settings.

Typical configuration workflow

  1. Identify ECU fault-monitoring requirements.
  2. Define diagnostic events.
  3. Assign configured DTCs to events.
  4. Configure debouncing and operation cycles.
  5. Configure event memory and diagnostic records.
  6. Generate and integrate DEM configuration.
  7. Test event reporting and diagnostic behavior.

13. Common DEM Problems and Troubleshooting

Problem Possible Cause / Check
DTC is not reported Check event reporting, event ID and DEM configuration.
False diagnostic fault Check monitoring logic, thresholds and debouncing.
DTC remains active Check test results, operation cycles and event healing conditions.
Freeze-frame data is missing Check storage conditions and freeze-frame configuration.
DTC cannot be cleared Check clear conditions, DTC group and diagnostic request handling.
Event memory is full Check memory capacity, event priority and configured displacement strategy.

14. Placement-Oriented Interview Questions

Q1. What is DEM in AUTOSAR?

DEM is the Diagnostic Event Manager. It processes diagnostic events, maintains event status and manages associated DTC information and event memory.

Q2. What is a diagnostic event?

A diagnostic event represents a monitored fault condition reported by the responsible software.

Q3. What is a DTC?

A Diagnostic Trouble Code identifies a diagnostic fault for reporting and troubleshooting through diagnostic services.

Q4. What is the difference between an event and a DTC?

An event represents an internally monitored fault condition. A DTC is the configured diagnostic code associated with one or more events.

Q5. What is debouncing in DEM?

Debouncing qualifies a fault condition before it is treated as a diagnostic failure. It helps avoid false fault detection caused by temporary signal disturbances.

Q6. What is freeze-frame data?

It is selected operating information captured when configured diagnostic storage conditions are met.

Q7. What is the difference between DEM and DCM?

DEM manages diagnostic events and DTC information. DCM processes external diagnostic communication requests and provides configured diagnostic services.

Q8. What is a pending DTC?

It is a DTC whose pending status bit has been set according to the configured diagnostic test and confirmation rules.

Q9. What is the purpose of event memory?

Event memory retains configured diagnostic information so that faults can be analyzed later.

Q10. How do you troubleshoot a DTC that is not stored?

Check fault-monitoring logic, event reporting, event configuration, debouncing, storage conditions and event-memory configuration.

15. Lesson Summary

  • DEM stands for Diagnostic Event Manager.
  • It is part of the AUTOSAR BSW Services Layer.
  • It processes diagnostic events reported by software.
  • It manages event status and associated DTC information.
  • It supports event debouncing and diagnostic event memory.
  • It manages configured freeze-frame and extended data.
  • It works with DCM for diagnostic information access.

DEM is an important AUTOSAR module for ECU diagnostics, fault monitoring, BSW integration and automotive embedded software placement interviews.
