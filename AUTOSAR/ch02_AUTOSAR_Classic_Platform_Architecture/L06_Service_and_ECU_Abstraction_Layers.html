1. Introduction

The AUTOSAR Basic Software (BSW) is divided into different software layers. Two important areas are the Services Layer and ECU Abstraction Layer.

The Services Layer provides common software services to application software and other BSW modules. The ECU Abstraction Layer hides hardware-specific details of ECU devices from upper software layers.

  • Services Layer: Provides operating system, communication, memory and diagnostic services.
  • ECU Abstraction Layer: Provides standardized access to ECU-specific hardware devices.

3. Services Layer

The Services Layer provides common software functions required by application software and other BSW modules. It helps applications use standardized services without directly managing all low-level hardware operations.

Main Responsibilities

  • Operating system and task management.
  • Communication services.
  • Diagnostic services.
  • Memory management services.
  • ECU state and mode management.
  • Watchdog and system supervision services.

4. Important Services Layer Modules

A. AUTOSAR Operating System (OS)

The AUTOSAR OS manages ECU software execution through tasks, interrupts, alarms, counters and scheduling mechanisms.

Important functions include:

  • Task activation and termination.
  • Task scheduling.
  • Interrupt management.
  • Alarm and counter handling.
  • Resource management.
Example: An engine ECU may execute sensor acquisition, communication and control tasks at configured priorities and timing intervals.

B. ECU State Manager (EcuM)

EcuM manages important ECU lifecycle activities, including startup, shutdown and sleep-related state transitions.

  • Coordinates ECU startup.
  • Supports shutdown sequences.
  • Coordinates sleep and wakeup activities.
  • Works with other BSW modules during state transitions.

C. BSW Mode Manager (BswM)

BswM coordinates configured mode requests and mode-dependent actions among BSW modules and application components.

Example: A vehicle mode change may trigger configured actions for communication, diagnostics or other software modules.

D. Communication Services

Communication-related BSW modules support exchange of data between software components and communication networks.

  • COM: Handles signal-level communication.
  • PduR: Routes protocol data units between configured modules.
  • CanIf: Provides an interface to CAN hardware drivers.
  • CanTp: Supports segmented CAN transport communication.
  • CanNm: Supports CAN network management.

E. Diagnostic Services

  • DEM: Diagnostic Event Manager records and manages diagnostic events.
  • DCM: Diagnostic Communication Manager handles diagnostic communication services.

These modules support fault monitoring, diagnostic trouble codes and diagnostic communication with external test equipment.

F. Memory Services

AUTOSAR memory services manage access to non-volatile memory through standardized abstraction and management modules.

  • MemIf: Provides a common memory abstraction interface.
  • Fee: Provides flash EEPROM emulation.
  • Ea: Provides EEPROM abstraction.
  • NvM: Manages configured non-volatile memory blocks.

Fee and Ea are above the underlying memory drivers; they are not MCAL drivers.

5. ECU Abstraction Layer

The ECU Abstraction Layer provides access to ECU-specific hardware devices without requiring upper software layers to know their detailed hardware implementation.

Its responsibilities include:

  • Abstract external hardware devices.
  • Provide standardized interfaces to upper layers.
  • Hide device-specific implementation details.
  • Support hardware reuse across ECU variants where configured.
  • Connect upper BSW modules with lower-level drivers.
Example: An ECU may use an external watchdog device. The appropriate hardware abstraction driver provides a common interface for the software that uses the watchdog.

6. ECU Abstraction Layer Components

A. External Device Abstraction

This area provides access to external devices connected to the ECU, such as certain external watchdogs, sensors or other peripheral ICs.

B. Memory Hardware Abstraction

Memory hardware abstraction provides interfaces for memory devices and connects upper memory services to the relevant lower-level drivers.

C. Communication Hardware Abstraction

Communication hardware abstraction helps upper communication modules access communication hardware through standardized interfaces.

Important distinction: CanIf is a communication hardware abstraction module. It connects the communication stack with the CAN driver. The CAN controller driver itself belongs to MCAL.

9. Services Layer vs ECU Abstraction Layer

Provides common software services. Abstracts ECU-specific hardware devices.
Supports OS, diagnostics, communication and memory management. Provides interfaces to external devices and hardware resources.

10. Interview Questions and Answers

Q1. What is the Services Layer?

It provides common software services such as operating system, communication, diagnostics and memory management.

Q2. What is the ECU Abstraction Layer?

It abstracts ECU-specific hardware devices and provides standardized interfaces to upper software layers.

Q3. What is the function of EcuM?

EcuM coordinates ECU startup, shutdown, sleep and wakeup-related activities.

Q4. What is the function of BswM?

BswM coordinates configured mode requests and mode-dependent BSW actions.

Q5. What is the function of DEM?

DEM manages diagnostic events and related fault information, including configured DTCs.

Q6. What is the function of DCM?

DCM handles diagnostic communication services, including configured UDS services.

Q7. What is NvM?

NvM is the AUTOSAR Non-volatile Memory Manager. It manages configured non-volatile memory blocks.

Q8. What is CanIf?

CanIf is the CAN Interface module. It provides an abstraction between upper communication modules and CAN hardware drivers.

Q9. What is the difference between Fee and Fls?

Fee provides flash EEPROM emulation at the memory abstraction level. Fls is the lower-level flash driver that accesses supported flash hardware.

Q10. Why are these layers important?

They separate common software services and hardware-specific operations, improving modularity, integration and reuse.

11. Lesson Summary

  • The Services Layer provides common software services.
  • The ECU Abstraction Layer hides ECU-specific hardware details.
  • OS, EcuM and BswM support system and mode management.
  • COM, PduR and diagnostic modules support communication and diagnostics.
  • NvM, MemIf, Fee and Ea support non-volatile memory management.
  • CanIf connects upper communication modules with the CAN driver.
  • MCAL provides lower-level microcontroller peripheral drivers.
