Lesson 3: AUTOSAR Runtime Environment (RTE)

Chapter 2 – AUTOSAR Classic Platform Architecture

RTE Architecture | APIs | Communication | Integration

1. Introduction to RTE

RTE stands for Runtime Environment. It is a fundamental part of the AUTOSAR Classic Platform. It provides communication infrastructure between application Software Components (SWCs) and configured Basic Software services.

RTE is generated and configured according to the software component interfaces and ECU configuration.

Its main purposes are:

  • Enable communication between SWCs.
  • Provide standardized interfaces to application software.
  • Connect SWCs with required BSW services.
  • Support software component integration.
  • Hide many communication and implementation details from application code.

RTE is a software communication layer. It is not a physical bus or a separate hardware device.

3. Main Functions of RTE

A. SWC-to-SWC Communication

RTE supports communication between application components through configured interfaces.

B. SWC-to-BSW Communication

RTE provides configured interfaces through which application components can access required Basic Software services.

C. Interface Abstraction

Application software uses generated RTE APIs instead of depending directly on many lower-level implementation details.

D. Runnable Activation Support

RTE works with configured events and operating system tasks to support activation of runnable entities.

E. Communication Mapping

RTE generation implements configured connections between software component ports and interfaces.

4. Types of RTE Communication

A. Sender-Receiver Communication

Sender-Receiver communication is used to exchange data between software components.

Temperature Monitoring SWC
Sender
↓
RTE Sender-Receiver Communication
↓
Fan Control SWC
Receiver

Example: A temperature-monitoring component sends the engine temperature to a fan-control component.

B. Client-Server Communication

Client-Server communication is used when one software component requests an operation provided by another component.

Client SWC
Requests an Operation
↓
RTE Client-Server Communication
↓
Server SWC
Executes the Operation

Example: A client component requests a calculation or service from a server component.

5. Generated RTE APIs

RTE generator tools create APIs based on the configured software component interfaces. Application software uses these APIs to communicate through RTE.

Common RTE API Families

  • Rte_Read: Reads data from a receiver port.
  • Rte_Write: Writes data to a sender port.
  • Rte_Send: Sends data through a sender port where that API is configured.
  • Rte_Receive: Receives data through a receiver port where that API is configured.
  • Rte_Call: Calls a configured client-server operation.
  • Rte_IRead: Reads an implicit data access value in a runnable.
  • Rte_IWrite: Writes an implicit data access value in a runnable.

The exact API names and available operations depend on the configured ports, interfaces and communication semantics.

Important: Rte_Read and Rte_Write are common APIs for sender-receiver communication. They should not be treated as universal functions available in every SWC.

6. RTE and Runnable Entities

A runnable entity contains executable application behavior inside a software component. RTE supports its activation according to configured events and execution mapping.

Common Events

  • Timing Event
  • Data Received Event
  • Operation Invoked Event
  • Init Event
Example: A temperature-monitoring runnable may be activated periodically every 100 milliseconds by a configured timing event.

7. RTE Generation and Configuration

RTE is not normally written entirely by hand. It is generated using AUTOSAR configuration information and development tools.

Typical RTE Development Workflow

  1. Define application Software Components.
  2. Define ports and interfaces.
  3. Configure component connections.
  4. Map software components to ECU instances.
  5. Configure runnable events and task mapping.
  6. Configure required BSW services.
  7. Generate RTE source code and header files.
  8. Compile and integrate generated code with application and BSW software.
  9. Perform testing and debugging.
Typical generated files: RTE-related source and header files, including component-specific RTE headers such as Rte_TemperatureMonitor.h. Actual filenames depend on the configuration tool.

8. Conceptual Example Using RTE APIs

The following example illustrates the use of sender-receiver APIs. The RTE API names are representative; actual generated function signatures depend on the AUTOSAR configuration.

Temperature Sender Component

#include "Rte_TemperatureSender.h"

void TemperatureSenderRunnable(void)
{
    float temperature = 95.0f;

    Rte_Write_TemperaturePort_Temperature(temperature);
}

Fan Receiver Component

#include "Rte_FanReceiver.h"

void FanReceiverRunnable(void)
{
    float temperature;

    if (Rte_Read_TemperaturePort_Temperature(&temperature)
        == RTE_E_OK)
    {
        if (temperature >= 90.0f)
        {
            /* Request cooling fan ON */
        }
        else
        {
            /* Request cooling fan OFF */
        }
    }
}

These snippets are illustrative, not directly compilable without matching generated RTE headers, data types, port names and API signatures.

9. RTE vs BSW

RTE BSW
Provides communication infrastructure and generated interfaces. Provides system services and hardware abstraction.
Connects SWCs and configured services. Implements operating system, diagnostics, communication and driver functions.
Generated according to application and ECU configuration. Configured and integrated according to ECU requirements.
Located between Application Layer and BSW. Located below RTE in the Classic Platform architecture.

10. Advantages of RTE

  • Provides standardized communication interfaces.
  • Reduces direct dependencies between SWCs.
  • Supports software component reuse.
  • Hides many communication implementation details.
  • Supports integration of application software and BSW.
  • Helps map application behavior to ECU execution resources.

11. Interview Questions and Answers

Q1. What is RTE in AUTOSAR?

RTE stands for Runtime Environment. It provides communication infrastructure between SWCs and configured interfaces to BSW services.

Q2. Where is RTE located?

It is located between the Application Layer and Basic Software in AUTOSAR Classic.

Q3. Is RTE hardware or software?

RTE is software. It is not a physical bus or hardware device.

Q4. What is RTE generation?

It is the process of generating RTE source code and interfaces from configured AUTOSAR software components and ECU descriptions.

Q5. What is Rte_Read?

It is a commonly generated API used by a receiver component to read sender-receiver data.

Q6. What is Rte_Write?

It is a commonly generated API used by a sender component to write sender-receiver data.

Q7. What is Rte_Call?

It is a generated API used by a client component to invoke a configured client-server operation.

Q8. What are the two common communication patterns supported by RTE?

Sender-Receiver and Client-Server communication.

Q9. Does RTE generate the application logic?

No. RTE generation creates communication infrastructure and interfaces. Application behavior is implemented in SWCs.

Q10. What is the relationship between RTE and OS tasks?

Configured runnable entities are mapped to operating system tasks. RTE supports their execution and activation according to the configured events and scheduling design.

12. Lesson Summary

  • RTE stands for Runtime Environment.
  • It is positioned between Application Layer and BSW.
  • It supports SWC-to-SWC communication.
  • It provides configured interfaces to BSW services.
  • Sender-Receiver communication exchanges data.
  • Client-Server communication invokes operations.
  • RTE APIs are generated according to configuration.
  • Runnable entities are mapped to OS execution resources.
  • RTE is software, not a physical communication bus.
