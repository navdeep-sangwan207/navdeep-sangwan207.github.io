Lesson 4: SWC Configuration and RTE Generation

AUTOSAR Methodology and Configuration Tools

Placement-Oriented Embedded Automotive Software Training

1. Introduction

An AUTOSAR Software Component (SWC) is a modular software unit that implements a particular application function inside an ECU. Examples include temperature monitoring, motor control, window control and vehicle speed processing.

SWC configuration describes how software components communicate, which data they exchange, which operations they provide and when their software functions execute.

The Runtime Environment (RTE) provides the communication and execution infrastructure between software components and between application software and Basic Software.

Important: The RTE is generated for a particular ECU configuration. It is not an operating system and is not normally written manually by application developers.

2.1 Atomic Software Component

An atomic SWC is a component whose internal behavior is defined independently. It is a basic unit of software composition and configuration.

Examples:

  • Temperature Sensor SWC
  • Fan Control SWC
  • Vehicle Speed SWC
  • Battery Monitoring SWC

2.2 Composition Software Component

A composition SWC groups other SWCs and defines how they are connected. It helps organize a larger application into manageable functional subsystems.

2.3 Application SWC

Application SWCs implement application-level functionality. They usually interact with hardware through configured interfaces and services rather than directly accessing microcontroller registers.

3. Ports in AUTOSAR

Ports are communication points through which a software component exchanges information or requests services.

3.1 Provided Port (P-Port)

A provided port offers an interface or service to another component. It is commonly used when a component publishes data or provides operations.

3.2 Required Port (R-Port)

A required port consumes data or requests a service from another component. 

 Temperature SWC                 Fan Control SWC
+------------------+            +------------------+
|                  |            |                  |
|  P-Port          |----------->|  R-Port          |
|  TemperatureData |            |  TemperatureData |
|                  |            |                  |
+------------------+            +------------------+
A P-Port provides an interface; an R-Port requires an interface. The actual communication path is established through the system composition and connector configuration.

4. AUTOSAR Interfaces

An interface defines the information or operations exchanged through ports. The interface type determines the communication model.

4.1 Sender-Receiver Interface

The Sender-Receiver interface is used to exchange data elements between software components.

Example:

  • Temperature SWC sends measured temperature.
  • Fan Control SWC receives temperature data.
  • Fan Control SWC calculates the required fan speed.

4.2 Client-Server Interface

The Client-Server interface is used when one component requests an operation from another component.

Example:

  • Client SWC requests a diagnostic operation.
  • Server SWC executes the requested operation.
  • Server returns a result or status.

5. Data Elements and Operations

5.1 Data Elements

A Sender-Receiver interface contains data elements that describe the information exchanged between components.

Example data elements:

  • TemperatureValue
  • VehicleSpeed
  • BatteryVoltage
  • MotorCurrent

5.2 Operations

A Client-Server interface defines operations. An operation can contain input arguments, output arguments and return values.

Example:

Operation: ReadTemperature

Input:
    SensorChannel

Output:
    TemperatureValue

Return:
    OperationStatus

6. Runnable Entities

A Runnable Entity is an executable unit of behavior inside an AUTOSAR software component. The RTE and configured execution environment coordinate its activation.

Example runnable entities:

  • ReadTemperature_Runnable
  • CalculateFanSpeed_Runnable
  • UpdateDiagnosticStatus_Runnable

6.1 Runnable Activation Events

Event Purpose
TimingEvent Activates a runnable periodically or at a configured time interval.
DataReceivedEvent Activates a runnable when configured data is received.
OperationInvokedEvent Activates a server runnable when an operation is invoked.
InitEvent Activates initialization behavior.

6.2 Runnable-to-Task Mapping

Runnable entities are mapped to execution contexts, commonly OS tasks. The mapping determines the task context in which the runnable executes. Scheduling and timing are then handled through the configured OS and RTE integration.

The runnable is not itself an OS task. Multiple runnable entities may be mapped to an execution context according to the ECU configuration.

7. Internal Behavior Configuration

Internal behavior describes how a software component executes. It includes runnable entities, events, data access, operation access, and other execution-related definitions.

Typical configuration activities include:

  • Define runnable entities.
  • Configure activation events.
  • Define data access points.
  • Configure operation access points.
  • Specify execution-related properties.
  • Map runnable entities to OS execution contexts.

8. SWC Communication Connections

Components are connected through configured ports and compatible interfaces. These connections describe how data or operations move between software components.

9. Runtime Environment (RTE)

The RTE is the ECU-specific communication infrastructure between AUTOSAR software components and between application software and Basic Software.

9.1 Main Functions of RTE

  • Provides communication mechanisms between SWCs.
  • Provides generated APIs for accessing configured interfaces.
  • Coordinates runnable activation.
  • Supports communication across configured execution contexts.
  • Provides access to configured BSW services.
  • Helps isolate application software from implementation details.

10. RTE Generation

RTE generation is the process of producing ECU-specific RTE source code and related configuration artifacts from AUTOSAR descriptions and ECU configuration information.

10.1 Typical RTE Generation Inputs

  • Software Component descriptions.
  • Port and interface definitions.
  • Runnable entities and activation events.
  • System and ECU configuration descriptions.
  • SWC-to-ECU allocation information.
  • Communication connections.
  • OS and BSW integration configuration.

10.3 Generated Artifacts

Depending on the AUTOSAR release and toolchain, generated artifacts can include:

  • RTE header files.
  • RTE source files.
  • Generated communication APIs.
  • Runnable declarations and integration code.
  • RTE configuration and mapping artifacts.
  • Supporting configuration files.
Generated file names, APIs and directory structures depend on the AUTOSAR version, configuration model and tool vendor.

11. Common RTE APIs

The RTE generator creates APIs according to configured ports, interfaces and data elements. Common API patterns include:

11.1 Rte_Read()

Used by a receiver component to read data through a configured Sender-Receiver interface. 

Std_ReturnType status;
TemperatureType temperature;

status = Rte_Read_TemperaturePort_TemperatureValue(
             &temperature
         );

11.2 Rte_Write()

Used by a sender component to write data through a configured Sender-Receiver interface. 

TemperatureType temperature = 75;

status = Rte_Write_TemperaturePort_TemperatureValue(
             temperature
         );

11.3 Rte_Call()

Used by a client component to invoke a configured Client-Server operation. 

status = Rte_Call_DiagnosticPort_ReadStatus(
             &diagnosticStatus
         );
These examples illustrate API patterns only. Actual generated function names, parameter types and signatures must be taken from the generated RTE headers for the target ECU.

12. Explicit and Implicit Communication

12.1 Explicit Communication

In explicit communication, the runnable accesses data through generated RTE APIs at the point where it needs to read or write the data.

12.2 Implicit Communication

In implicit communication, data access is coordinated with runnable execution. The RTE can provide a consistent data view for the runnable according to the configured communication semantics.

The appropriate communication mode depends on the interface, runnable configuration and system requirements.

13. Practical Example: Temperature Monitoring and Fan Control ECU

Consider an ECU that monitors engine temperature and controls a cooling fan.

13.1 Software Components

  • Temperature Sensor SWC: obtains temperature information.
  • Fan Control SWC: calculates the required fan command.
  • Fan Actuator SWC: requests fan operation through configured services.

13.2 Example Logic

Temperature = ReadTemperature();

if (Temperature >= 90)
{
    FanSpeed = 100;
}
else if (Temperature >= 75)
{
    FanSpeed = 60;
}
else
{
    FanSpeed = 0;
}

WriteFanCommand(FanSpeed);

This is illustrative application logic. In a real AUTOSAR ECU, sensor acquisition and actuator control are integrated through configured SWCs, interfaces, RTE APIs and the relevant BSW drivers.

15. Placement Interview Questions and Answers

Q1. What is an AUTOSAR Software Component?

An SWC is a modular software unit that implements application functionality and communicates through defined interfaces.

Q2. What is an atomic SWC?

An atomic SWC is a component whose internal behavior is defined independently and which serves as a basic unit of software composition.

Q3. What is a P-Port?

A P-Port is a provided port through which a software component offers data or services.

Q4. What is an R-Port?

An R-Port is a required port through which a software component consumes data or requests services.

Q5. What is the difference between Sender-Receiver and Client-Server?

Sender-Receiver is used for data exchange, whereas Client-Server is used for operation requests and responses.

Q6. What is a Runnable Entity?

A runnable is an executable unit of behavior within an AUTOSAR software component.

Q7. What is a TimingEvent?

A TimingEvent activates a runnable according to a configured timing schedule.

Q8. What is the RTE?

The Runtime Environment is ECU-specific infrastructure that supports communication and execution coordination between application software components and their configured environment.

Q9. Is RTE manually written?

The RTE is generally generated by AUTOSAR configuration tools from software and ECU configuration descriptions.

Q10. What is Rte_Read()?

It is a generated API pattern used by a receiver component to read data through a configured Sender-Receiver interface.

Q11. What is Rte_Write()?

It is a generated API pattern used by a sender component to write data through a configured Sender-Receiver interface.

Q12. What is Rte_Call()?

It is a generated API pattern used to invoke a configured Client-Server operation.

Q13. Is RTE an operating system?

No. RTE is communication and execution infrastructure. The AUTOSAR OS manages configured operating-system tasks and scheduling.

Q14. How are runnables executed?

Runnables are activated through configured events and execute in their assigned execution contexts, commonly OS tasks.

Q15. What happens if RTE generation fails?

The configuration must be checked for inconsistent ports, interfaces, mappings, events, missing dependencies or other tool-reported validation errors.

17. Lesson Summary

  • SWCs implement modular automotive application functionality.
  • Ports define how components provide or require communication.
  • Interfaces define exchanged data or callable operations.
  • Runnable entities contain executable component behavior.
  • Events control runnable activation.
  • RTE provides ECU-specific communication and execution infrastructure.
  • RTE code is generated from AUTOSAR configuration descriptions.
  • Generated APIs support configured communication between components.
