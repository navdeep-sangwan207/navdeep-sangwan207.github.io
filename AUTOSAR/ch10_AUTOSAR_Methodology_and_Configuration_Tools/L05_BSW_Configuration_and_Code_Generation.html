Lesson 5: BSW Configuration and Code Generation

AUTOSAR Methodology and Configuration Tools

Placement-Oriented Embedded Automotive Software Training

1. Introduction to BSW Configuration

Basic Software (BSW) is the standardized software layer that provides common services and hardware-independent functionality to AUTOSAR application software.

BSW configuration defines how individual software modules operate inside a particular ECU. Configuration includes module parameters, hardware resources, communication settings, dependencies and integration requirements.

After configuration and validation, tools can generate configuration source code, header files and other integration artifacts.

Important: BSW configuration is not the same as writing every BSW module from scratch. Many module implementations are supplied by the AUTOSAR tool vendor or software supplier. The project configures and integrates the modules required by the ECU.

2. BSW Architecture

AUTOSAR Classic BSW is commonly organized into three major layers:

  • Services Layer
  • ECU Abstraction Layer
  • Microcontroller Abstraction Layer (MCAL)

Complex Drivers provide additional access paths for special or time-critical hardware requirements. They are not mandatory in every ECU.

2.1 Services Layer

The Services Layer provides common services to application software and other BSW modules.

Examples:

  • Operating System (OS)
  • ECU State Manager (EcuM)
  • Diagnostic Event Manager (DEM)
  • Diagnostic Communication Manager (DCM)
  • Communication Services such as COM
  • Memory services such as NvM

2.2 ECU Abstraction Layer

The ECU Abstraction Layer provides standardized interfaces to hardware-related components and external devices. It hides microcontroller-specific implementation details from upper layers.

Examples:

  • CAN Interface (CanIf)
  • Memory Interface (MemIf)
  • I/O Hardware Abstraction (IoHwAb), where implemented
  • EEPROM and Flash abstraction modules, depending on configuration

2.3 Microcontroller Abstraction Layer (MCAL)

MCAL contains microcontroller-specific drivers that provide access to on-chip peripherals.

Examples:

  • DIO Driver
  • PORT Driver
  • ADC Driver
  • PWM Driver
  • SPI Driver
  • CAN Driver
  • GPT Driver

4. ECU Configuration (ECUC)

ECUC refers to the AUTOSAR ECU configuration model used to describe configuration parameters for BSW modules and related ECU software.

Configuration descriptions define the parameters and references required by modules. Tools use these descriptions to validate configuration and generate corresponding artifacts.

4.1 Configuration Parameters

Typical parameter categories include:

  • Numerical parameters, such as timing values.
  • Boolean parameters, such as enabling or disabling a feature.
  • Enumeration parameters, such as selecting a configured mode.
  • Reference parameters, which connect one configuration object to another.
  • Container parameters, which group related configuration settings.

4.2 Example: DIO Configuration

Consider an ECU using a digital output to control an indicator LED. The DIO configuration describes the required channel and its initial behavior.

The actual channel identifiers and configuration structure depend on the selected microcontroller and MCAL implementation.

Module dependencies are not always a simple one-directional stack. Use the module dependency information and configuration rules provided by the selected AUTOSAR release and vendor.

6. MCAL Configuration

MCAL configuration adapts microcontroller drivers to the target hardware and project requirements.

6.1 Common MCAL Configuration Areas

  • Clock and peripheral initialization.
  • Port pin direction and alternate functions.
  • Digital input and output channels.
  • ADC channels and conversion groups.
  • PWM channels and period settings.
  • SPI channels and sequences.
  • CAN controllers and baud-rate settings.
  • Interrupt and hardware notification configuration.

6.2 Example: PWM Configuration

Assume an ECU controls a cooling fan through a PWM output. The PWM driver configuration defines the hardware channel, period, polarity and initial duty cycle. 

PWM Configuration
       |
       +-- PWM Channel
       |
       +-- Period
       |
       +-- Polarity
       |
       +-- Duty Cycle
       |
       +-- Notification (if required)

The application may request a duty-cycle change through an appropriate configured interface. The RTE and BSW integration connect application behavior to the relevant driver functionality.

7. Communication Stack Configuration

Automotive ECUs use communication modules to exchange data with other ECUs and diagnostic tools.

7.1 Important Modules

  • COM: Signal packing and unpacking.
  • PduR: Protocol Data Unit routing.
  • CanIf: CAN interface abstraction.
  • Can: CAN controller driver.
  • CanTp: CAN transport protocol.
  • CanSM: CAN State Manager.
  • CanNm: CAN Network Management, when required.
  • CanTrcv: CAN transceiver driver, where applicable.

7.2 Configuration Activities

  1. Define communication controllers and channels.
  2. Configure CAN baud rate and hardware resources.
  3. Define transmit and receive PDUs.
  4. Configure PDU routing paths.
  5. Map signals to I-PDUs.
  6. Configure transmission modes and timing.
  7. Validate communication references and dependencies.

8. Diagnostic Module Configuration

Diagnostic modules support fault monitoring, DTC storage and diagnostic communication.

8.1 DEM Configuration

  • Diagnostic events.
  • Event-to-DTC relationships.
  • Debouncing methods.
  • Operation cycles.
  • Freeze-frame records.
  • Extended data records.

8.2 DCM Configuration

  • Diagnostic sessions.
  • Security access configuration.
  • Diagnostic service support.
  • Data Identifiers (DIDs).
  • Routine control configuration.
  • Diagnostic communication connections.
Diagnostic configuration must follow the ECU's diagnostic requirements and applicable OEM specifications. Not every ECU supports every UDS service.

9. OS and EcuM Configuration

9.1 OS Configuration

The AUTOSAR OS configuration defines the execution environment for software components and BSW modules.

Typical OS objects include:

  • Tasks and task priorities.
  • Alarms and counters.
  • Events and resources.
  • Interrupt service routines.
  • Application modes.
  • Schedule tables, where used.

9.2 EcuM Configuration

The ECU State Manager supports ECU startup, shutdown and state management. Its configuration describes the required initialization and shutdown behavior and interactions with other BSW modules.

Typical activities:

  • Configure startup and shutdown behavior.
  • Configure initialization lists or sequences.
  • Configure wake-up sources.
  • Coordinate required BSW module initialization.
  • Configure ECU state transitions.

10. Configuration Variants

AUTOSAR projects may use configuration variants to support different ECU product configurations or operating conditions.

Common concepts include:

  • Pre-compile configuration: selected settings are fixed during compilation and may influence compiled code.
  • Link-time configuration: selected configuration information is resolved during linking.
  • Post-build configuration: supported configuration data can be selected or supplied after compilation.
Not every BSW module supports every configuration variant. The available options depend on the AUTOSAR release, module implementation and vendor toolchain.

12. Build Integration

Generated files must be integrated into the ECU software build. The build system compiles source files, resolves dependencies and links the final executable.

12.1 Build Activities

  • Add generated source files to the project.
  • Configure include directories.
  • Set compiler and preprocessor options.
  • Configure linker scripts and memory layout.
  • Resolve module dependencies.
  • Compile and link the ECU software.
  • Review warnings and errors.

12.2 Common Build Problems

  • Missing header files.
  • Undefined references during linking.
  • Duplicate symbol definitions.
  • Incorrect compiler settings.
  • Incompatible generated and supplied module versions.
  • Missing source files in the build configuration.

13. Practical Example: Configure an ECU for Temperature-Based Fan Control

Consider a microcontroller-based ECU that reads temperature, controls a cooling fan using PWM and reports a diagnostic fault when a sensor failure occurs.

13.1 Required Modules

Module Purpose
ADC Reads the temperature sensor voltage.
PWM Controls fan speed.
DIO Controls a status indicator.
OS Schedules application execution.
DEM Manages sensor fault events.
DCM Provides configured diagnostic communication.
EcuM Coordinates ECU initialization and shutdown.

13.2 Configuration Sequence

  1. Select the target microcontroller and its supported MCAL package.
  2. Configure ADC channel and conversion group.
  3. Configure PWM output channel and duty-cycle limits.
  4. Configure DIO status output.
  5. Configure OS task and runnable execution timing.
  6. Configure DEM event for sensor failure.
  7. Configure DCM diagnostic access if required.
  8. Configure EcuM startup behavior and module dependencies.
  9. Validate and generate configuration artifacts.
  10. Compile, link and test the ECU software.

13.3 Application Logic Illustration

Read temperature from configured ADC path

If sensor is faulty:
    Report diagnostic event
    Set safe fan command
Else:
    If temperature >= 90:
        Fan duty = 100%
    Else if temperature >= 75:
        Fan duty = 60%
    Else:
        Fan duty = 0%

Update PWM output

The ADC and PWM hardware operations are provided through configured software interfaces and driver services. The actual implementation depends on the selected MCAL and application architecture.

Problem Possible Cause Action

Invalid reference Incorrect module or container reference Check referenced configuration objects.

Linker error Missing source or unresolved symbol Check build files and module dependencies.

15. Placement Interview Questions and Answers

Q1. What is BSW in AUTOSAR?

BSW is the Basic Software layer that provides standardized services, hardware abstraction and microcontroller driver functionality.

Q2. What are the three main BSW layers?

Services Layer, ECU Abstraction Layer and Microcontroller Abstraction Layer (MCAL).

Q3. What is MCAL?

MCAL provides microcontroller-specific drivers for peripherals such as ADC, PWM, DIO, SPI and CAN.

Q4. What is ECUC?

ECUC is the ECU configuration model used to describe configuration parameters and references for BSW modules and related ECU software.

Q5. What is a BSW module dependency?

It is a relationship in which one module requires another module or service to provide its functionality.

Q6. What is the purpose of CanIf?

CanIf provides a standardized CAN interface abstraction between upper communication modules and the CAN driver.

Q7. What is the purpose of PduR?

PduR routes Protocol Data Units between configured communication modules.

Q8. What is the difference between Fee and Fls?

Fee provides flash EEPROM emulation at a higher abstraction level, whereas Fls is the lower-level flash memory driver.

Q9. What is DEM?

Diagnostic Event Manager manages diagnostic events and associated fault information according to ECU configuration.

Q10. What is DCM?

Diagnostic Communication Manager handles configured diagnostic communication services, including supported UDS services.

Q11. What is EcuM?

EcuM coordinates ECU initialization, startup, shutdown and related ECU state management.

Q12. What is BSW code generation?

It is the process of generating configuration-related source code, headers and other artifacts from configured BSW module descriptions.

Q13. Is all BSW source code generated?

No. Module implementations are often supplied by vendors, while configuration tools generate module-specific configuration artifacts.

Q14. What is post-build configuration?

It is a supported configuration approach in which selected configuration data can be supplied or selected after compilation, according to the module's implementation.

Q15. Why is configuration validation important?

It identifies missing parameters, invalid references, dependency problems and configuration inconsistencies before code integration.

17. Lesson Summary

  • BSW provides standardized ECU software services and hardware abstraction.
  • Its three main layers are Services, ECU Abstraction and MCAL.
  • ECUC describes module configuration parameters and references.
  • BSW modules have dependencies that must be configured consistently.
  • MCAL configuration adapts drivers to the selected microcontroller.
  • Communication, diagnostics, memory and OS modules require ECU-specific configuration.
  • Configuration tools generate module-specific configuration artifacts.
  • Validation, build integration and testing are essential before ECU deployment.
