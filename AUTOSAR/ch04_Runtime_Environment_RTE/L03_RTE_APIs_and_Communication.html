Lesson 3: RTE APIs and Communication

Chapter 4 – Runtime Environment (RTE)

Rte_Read | Rte_Write | Rte_Call | Communication

1. Introduction to RTE APIs

RTE APIs are generated software interfaces that allow AUTOSAR Software Components (SWCs) to exchange data, request operations and access configured services.

Application software components generally use RTE APIs instead of directly accessing the implementation details of other components.

Example: A vehicle speed component obtains speed data from a sensor-related component and sends the value to a dashboard component through configured RTE communication.

2. Why are RTE APIs Required?

  • Enable communication between software components.
  • Provide abstraction from communication implementation details.
  • Support Sender-Receiver communication.
  • Support Client-Server communication.
  • Provide access to configured BSW services.
  • Support data access and runnable execution.
  • Improve software component portability and reusability.

3. Main Categories of RTE APIs

API Category Purpose Examples
Sender-Receiver Exchange data between SWCs Rte_Read, Rte_Write
Client-Server Request an operation from another SWC Rte_Call
Implicit Communication Access data through runnable-specific buffers Rte_IRead, Rte_IWrite
Queued Communication Send or receive queued data samples Rte_Send, Rte_Receive
Mode Management Access or request configured mode information Mode-related RTE APIs

The actual generated API names and signatures depend on the AUTOSAR configuration and RTE generator.

4. Sender-Receiver Communication APIs

Sender-Receiver communication transfers data from a providing software component to one or more receiving components.

Sender SWC
Rte_Write()
↓
Runtime Environment (RTE)
Configured Data Communication
↓
Receiver SWC
Rte_Read()

A. Rte_Write()

Used by a sender component to write a value to a configured Sender-Receiver data element. 

uint16 speed = 80;

Rte_Write_SpeedPort_VehicleSpeed(speed);

B. Rte_Read()

Used by a receiver component to read a value from a configured Sender-Receiver data element. 

uint16 speed;

if (Rte_Read_SpeedPort_VehicleSpeed(&speed) == RTE_E_OK)
{
    /* Process received speed */
}

C. Rte_Send() and Rte_Receive()

These APIs are used for configured queued Sender-Receiver communication. 

/* Sender-side illustrative call */
Rte_Send_MessagePort_Message(message);

/* Receiver-side illustrative call */
Rte_Receive_MessagePort_Message(&message);

Queued communication can preserve multiple data samples, subject to the configured queue length and communication behavior.

5. Explicit and Implicit Communication

Explicit Communication

Explicit communication uses APIs such as Rte_Read() and Rte_Write() to access Sender-Receiver data.

Implicit Communication

Implicit communication uses runnable-specific data access APIs and configured buffering behavior. 

/* Illustrative implicit data access */

uint16 speed;

speed = Rte_IRead_DashboardRunnable_SpeedPort_VehicleSpeed();

A runnable may use Rte_IWrite() to provide output data through configured implicit communication.

Important: Implicit communication is associated with runnable execution and data access semantics. It is not simply another name for ordinary Rte_Read() or Rte_Write().

6. Client-Server Communication API

Client-Server communication is used when one software component requests an operation provided by another component.

Client SWC
Requests an operation
↓ Rte_Call()
Runtime Environment
Configured operation invocation
↓
Server SWC
Executes the requested operation

Example: Battery Voltage Service

/* Illustrative Client-side call */

float voltage;
Std_ReturnType result;

result = Rte_Call_BatteryService_GetVoltage(&voltage);

if (result == RTE_E_OK)
{
    /* Process battery voltage */
}

Rte_Call() invokes a configured server operation. The generated interface determines the actual arguments and return behavior.

7. RTE APIs for BSW Service Access

An application software component can access configured Basic Software services through appropriate RTE interfaces.

Examples include:

  • Diagnostic services.
  • Non-volatile memory services.
  • Mode management services.
  • Communication-related services.
  • Configured ECU state information.
Important: The exact access mechanism depends on the service, its AUTOSAR interface and ECU configuration. Not every BSW module is accessed using the same API pattern.

8. Sender-Receiver vs Client-Server

Feature Sender-Receiver Client-Server
Purpose Exchange data Request an operation
Communication Data-oriented Operation-oriented
Typical API Rte_Read / Rte_Write Rte_Call
Example Vehicle speed value Read battery voltage service
Direction Data from sender to receiver Client invokes server operation

9. Practical Example: Vehicle Speed Communication

Consider an ECU that reads vehicle speed and displays it on the dashboard.

  1. Vehicle Speed SWC obtains the configured speed data.
  2. The sender writes the value using its generated RTE interface.
  3. The RTE handles the configured communication.
  4. Dashboard SWC reads the value using its generated interface.
  5. The dashboard application processes the speed value.
/* Sender runnable - illustrative */

void VehicleSpeedRunnable(void)
{
    uint16 speed = 80;

    Rte_Write_SpeedPort_VehicleSpeed(speed);
}

/* Receiver runnable - illustrative */

void DashboardRunnable(void)
{
    uint16 speed;

    if (Rte_Read_SpeedPort_VehicleSpeed(&speed) == RTE_E_OK)
    {
        /* Update dashboard using speed */
    }
}

These examples demonstrate the API usage pattern. They are not standalone programs; generated headers, declarations and configuration are required for a real AUTOSAR build.

10. Common RTE API Errors

  • Using an API name that does not match the generated interface.
  • Using an incorrect data type or pointer argument.
  • Calling an API for an unconfigured port.
  • Using a Sender-Receiver API for a Client-Server interface.
  • Ignoring API return status where applicable.
  • Using stale generated headers after configuration changes.
  • Incorrect runnable or event configuration.

Always check the generated RTE header files and the tool's configuration reports when troubleshooting an API issue.

11. Interview Questions and Answers

Q1. What are RTE APIs?

Generated interfaces used by AUTOSAR software components for communication and configured service access.

Q2. What is Rte_Read()?

It is an API used to read data through a configured Sender-Receiver interface.

Q3. What is Rte_Write()?

It is an API used to write data through a configured Sender-Receiver interface.

Q4. What is Rte_Call()?

It is used by a client component to invoke a configured server operation.

Q5. What is queued communication?

It is communication in which multiple data samples can be stored in a configured queue for reception.

Q6. What is the difference between Rte_Read() and Rte_Receive()?

Rte_Read() is generally used for non-queued Sender-Receiver data access, while Rte_Receive() is used for configured queued reception.

Q7. What is implicit communication?

It is a configured data access mechanism associated with runnable execution and runnable-specific data buffers.

Q8. Can SWCs communicate without RTE?

In the AUTOSAR Classic application architecture, configured SWC communication is normally mediated by the RTE.

Q9. Are RTE API names always identical?

No. Generated names and signatures depend on the configured ports, interfaces, data elements and RTE generator.

Q10. What is the main difference between Sender-Receiver and Client-Server?

Sender-Receiver exchanges data, whereas Client-Server is used to invoke operations.

12. Lesson Summary

  • RTE APIs provide communication interfaces for SWCs.
  • Rte_Read() and Rte_Write() support Sender-Receiver data access.
  • Rte_Send() and Rte_Receive() support configured queued communication.
  • Rte_Call() invokes Client-Server operations.
  • Rte_IRead() and Rte_IWrite() support implicit data access.
  • Generated API names depend on ECU configuration.
  • SWCs use RTE interfaces to communicate within the AUTOSAR architecture.
