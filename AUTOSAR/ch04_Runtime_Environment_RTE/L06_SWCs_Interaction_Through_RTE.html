1. Introduction

In AUTOSAR Classic Platform, Software Components (SWCs) communicate through the Runtime Environment (RTE).

The RTE provides the communication interfaces and configured implementation needed for software components to exchange data and invoke operations.

Example: A temperature sensor-related SWC provides temperature data. A cooling fan controller SWC receives the data through the RTE and determines whether the fan should operate.

2. Why Do SWCs Need to Communicate?

  • Exchange sensor information.
  • Share vehicle operating parameters.
  • Coordinate application functions.
  • Request services from other components.
  • Separate software functionality into reusable modules.
  • Support integration of independently developed components.

The communication is configured using software component ports, interfaces and connectors. The RTE provides the generated interfaces used by the application code.

4. Communication Through Sender-Receiver Interface

Sender-Receiver communication is used when one SWC provides data and another SWC consumes it.

Communication Steps

  1. Sender SWC calculates or receives a data value.
  2. Sender writes the value through its RTE interface.
  3. RTE handles the configured communication.
  4. Receiver reads the value through its RTE interface.
  5. Receiver processes the received data.

Illustrative C Example

/* Sender SWC */

void TemperatureSenderRunnable(void)
{
    uint16 temperature = 85;

    Rte_Write_TemperaturePort_Temperature(temperature);
}

/* Receiver SWC */

void FanControllerRunnable(void)
{
    uint16 temperature;

    if (Rte_Read_TemperaturePort_Temperature(&temperature)
        == RTE_E_OK)
    {
        if (temperature > 80)
        {
            /* Request fan activation */
        }
    }
}

The API names and signatures are illustrative. Actual code must use the generated RTE interfaces for the configured ECU.

5. Communication Through Client-Server Interface

Client-Server communication is used when one SWC requests an operation from another SWC.

Client SWC
Requests an operation
↓ Rte_Call()
RTE
Configured operation invocation
↓
Server SWC
Executes the requested operation

Illustrative Example

/* Client-side illustrative code */

float voltage;
Std_ReturnType result;

result = Rte_Call_BatteryService_GetVoltage(&voltage);

if (result == RTE_E_OK)
{
    /* Process battery voltage */
}

The client invokes the configured server operation using the generated RTE interface.

6. Role of Ports and Interfaces

Provided Port (P-Port)

A P-Port provides an interface or service to another component.

Required Port (R-Port)

An R-Port requires an interface or service from another component.

Interface

An interface defines the communication contract, such as data elements or operations.

Element Purpose
P-Port Provides functionality or data.
R-Port Requires functionality or data.
Sender-Receiver Interface Defines data exchange.
Client-Server Interface Defines operations and arguments.
Connector Connects compatible component ports.

8. Complete Automotive Example: Cooling Fan Control

Consider a cooling fan control application containing three software components.

SWC 1: Temperature Sensor Component

  • Obtains temperature information.
  • Provides temperature data to the RTE.

SWC 2: Fan Controller Component

  • Reads temperature data.
  • Compares temperature with a configured threshold.
  • Determines the required fan state.

SWC 3: Fan Actuator Component

  • Receives the fan command.
  • Requests the configured actuator or BSW service.
  • Controls the fan through the appropriate lower-level software.
Application flow:

Temperature Sensor SWC → RTE → Fan Controller SWC → RTE → Fan Actuator SWC

In a real ECU, the actuator component uses the configured interfaces and lower-level software to control hardware. It does not automatically imply direct access to MCU registers from the application SWC.

9. Internal and Inter-ECU Communication

Internal ECU Communication

SWCs located within the same ECU can communicate through configured RTE interfaces.

Inter-ECU Communication

When information must travel between different ECUs, communication generally involves the communication stack and vehicle network.

ECU 1
Application SWC
↓
RTE and Communication BSW
COM | PduR | CanIf
↓
CAN Network
↓
ECU 2
Communication BSW → RTE → Application SWC

The exact communication path depends on the configured network, protocol and ECU architecture. The RTE does not itself replace the CAN communication stack.

10. Advantages of RTE-Based SWC Communication

  • Hardware abstraction.
  • Modular application design.
  • Software component reusability.
  • Standardized communication interfaces.
  • Improved integration between development teams.
  • Separation of application logic and communication implementation.
  • Support for configured intra-ECU communication.

12. Interview Questions and Answers

Q1. How do AUTOSAR SWCs communicate?

They communicate through configured RTE interfaces using mechanisms such as Sender-Receiver and Client-Server.

Q2. What is the role of RTE in SWC communication?

RTE provides generated communication interfaces and supporting implementation between software components.

Q3. What is Sender-Receiver communication?

It is a data-oriented communication mechanism in which one component provides data and another component receives it.

Q4. What is Client-Server communication?

It is an operation-oriented mechanism in which a client invokes an operation provided by a server.

Q5. What is the purpose of a P-Port?

It provides an interface or service to other software components.

Q6. What is the purpose of an R-Port?

It represents an interface or service required by a software component.

Q7. Can multiple SWCs communicate within one ECU?

Yes. They can exchange data and invoke operations through configured RTE interfaces.

Q8. How does communication take place between two ECUs?

It generally uses the configured communication stack and vehicle network, such as CAN, along with application-level RTE interfaces in each ECU.

Q9. Does RTE directly control hardware?

RTE provides software interfaces. Hardware access is normally handled through appropriate BSW and MCAL layers.

Q10. What is the main advantage of RTE-based communication?

It separates application components from communication implementation details, supporting modularity and reusability.
