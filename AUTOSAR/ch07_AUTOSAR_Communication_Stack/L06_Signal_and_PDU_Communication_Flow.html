Lesson 6: Signal and PDU Communication Flow

AUTOSAR – Chapter 7: AUTOSAR Communication Stack

Focus: Signal Flow, I-PDU, PduR, CAN Frame and End-to-End Communication

1. Introduction

In AUTOSAR, automotive ECUs exchange information using configured communication signals and Protocol Data Units (PDUs). The communication stack processes this information and transfers it between software components and network interfaces.

Understanding the complete signal-to-PDU flow is important for embedded software development, AUTOSAR integration, configuration and debugging.

2. Important Communication Terminology

Term Meaning
Signal A logical data value, such as vehicle speed or engine temperature.
Signal Group A configured collection of related signals.
I-PDU Interaction Layer PDU carrying configured communication data.
PDU Protocol Data Unit exchanged between communication layers.
CAN Frame A CAN protocol frame containing an identifier, control information and data.
CAN Identifier Identifies a CAN message and participates in bus arbitration.

3. Relationship Between Signal, I-PDU and CAN Frame

Signals are logical application data. COM packs configured signals into I-PDUs. The lower communication layers map those I-PDUs to the appropriate network representation.

Application Signals
↓
COM Signal Packing
↓
I-PDU
↓
PduR Routing
↓
CanIf and CAN Driver
↓
CAN Frame
↓
CAN Bus

An I-PDU and a CAN frame are not interchangeable terms. The configured CAN interface maps the communication PDU to the CAN hardware transmission representation.

4. Transmit Communication Flow

Transmit flow describes how an ECU sends application information to another ECU.

Sensor / Application Data
↓
Software Component (SWC)
↓
RTE
↓
COM
↓
PduR
↓
CanIf
↓
CAN Driver
↓
CAN Controller
↓
CAN Transceiver
↓
CAN Network

Step-by-Step Explanation

  1. The application obtains information from a sensor or another software function.
  2. The SWC updates the configured signal through the RTE.
  3. COM receives the signal value and updates the corresponding I-PDU.
  4. PduR routes the I-PDU to the configured lower communication module.
  5. CanIf forwards the transmission request to the CAN Driver.
  6. The CAN Driver configures the controller transmission request.
  7. The CAN controller transmits the CAN frame through the transceiver.
  8. The transceiver places the corresponding electrical signal on the CAN bus.

5. Receive Communication Flow

Receive flow describes how an ECU receives information from another ECU.

CAN Network
↓
CAN Transceiver
↓
CAN Controller
↓
CAN Driver
↓
CanIf
↓
PduR
↓
COM
↓
RTE
↓
Receiving SWC

Step-by-Step Explanation

  1. The CAN transceiver receives the electrical bus signal.
  2. The CAN controller detects and processes the CAN frame.
  3. The CAN Driver provides the received information to CanIf.
  4. CanIf identifies the configured receive PDU.
  5. PduR routes the received I-PDU to COM.
  6. COM extracts the configured signal values.
  7. The RTE makes the received data available to the SWC.
  8. The receiving application uses the signal for its function.

6. Role of Each Communication Module

Module Transmit Responsibility Receive Responsibility
RTE Provides configured communication access to SWCs. Makes received data available to SWCs.
COM Packs signals into I-PDUs. Extracts signals from I-PDUs.
PduR Routes I-PDUs to lower modules. Routes received I-PDUs to upper modules.
CanIf Forwards transmission requests to CAN Driver. Provides received CAN data to upper modules.
CAN Driver Requests CAN controller transmission. Handles received controller data and indications.
CAN Controller Handles CAN protocol transmission. Receives and validates CAN frames at the controller level.
CAN Transceiver Converts controller signals to bus electrical signaling. Converts bus electrical signaling to controller-side signals.

7. Example: Vehicle Speed Communication

Consider ECU-A measuring vehicle speed and transmitting the value to ECU-B.

ECU-A: Transmitter

  1. A speed sensor provides measurement information.
  2. The application calculates the vehicle speed.
  3. The speed SWC updates the VehicleSpeed signal.
  4. COM packs the signal into a configured I-PDU.
  5. PduR and CanIf route the I-PDU toward the CAN Driver.
  6. The CAN controller transmits the corresponding CAN frame.

ECU-B: Receiver

  1. The CAN controller receives the frame.
  2. The CAN Driver and CanIf process the receive indication.
  3. PduR routes the I-PDU to COM.
  4. COM extracts the VehicleSpeed signal.
  5. The RTE provides the value to the receiving SWC.
  6. The receiving application uses vehicle speed for its function.

8. Example of Signal Packing

Assume a configured I-PDU contains the following signals:

Signal Bit Length Example Value
Vehicle Speed 16 bits 100
Engine Temperature 8 bits 90
Door Status 4 bits 1
Reserved 4 bits 0

Total signal length = 16 + 8 + 4 + 4 = 32 bits = 4 bytes.

COM places the signal values at their configured bit positions. The exact encoded bytes depend on signal byte order, start bit, scaling and offset.

9. PDU Routing

PduR stands for PDU Router. It routes PDUs between configured communication modules according to the routing configuration.

Example Routing

COM
↓
PduR
↓
CanIf
↓
CAN Driver

PduR can also route communication data between other configured modules and communication paths. It does not interpret application signal meaning or control the CAN electrical bus.

10. Communication Through CAN Transport Protocol

A single CAN frame has a limited payload. When larger diagnostic or other configured messages must be transferred, CAN Transport Protocol (CanTp) can segment the data.

Upper Layer Data
↓
CanTp
↓
First Frame / Consecutive Frames
↓
CanIf
↓
CAN Driver
↓
CAN Network

On reception, CanTp reassembles the segmented data and provides the complete PDU to the configured upper module.

CanTp is commonly used for diagnostic communication. It is distinct from the normal signal-oriented COM path. Exact routing depends on the configured ECU communication design.

12. Communication Configuration Workflow

  1. Define the required communication signals.
  2. Define signal data types, lengths and properties.
  3. Configure sender and receiver ports and interfaces.
  4. Configure I-PDUs and signal-to-I-PDU mapping.
  5. Configure transmission and reception behavior in COM.
  6. Configure PDU routing in PduR.
  7. Configure CAN identifiers, controller and interface settings.
  8. Generate configuration and integration artifacts.
  9. Build, flash or simulate the ECU software as supported.
  10. Verify communication using appropriate debugging tools.

13. Communication Debugging

Observed Problem What to Check
Signal value not updated SWC logic, RTE connection and COM signal configuration.
I-PDU not transmitted COM transmission mode, I-PDU group state and PduR routing.
No CAN frame on bus CanIf configuration, CAN Driver, controller state and physical layer.
Incorrect CAN identifier CAN PDU and identifier configuration.
Receiver obtains incorrect value Signal start bit, length, byte order, scaling and offset.
Diagnostic transfer fails DCM, CanTp, PduR and diagnostic routing configuration.
Intermittent communication Bus errors, timing, termination, wiring and network configuration.

15. Common Placement Interview Questions

Q1. What is the difference between a signal and a PDU?

Answer: A signal is a logical data value, while a PDU is a data container exchanged between communication layers.

Q2. What is an I-PDU?

Answer: It is an Interaction Layer PDU that carries configured communication data such as signals.

Q3. What is the role of COM?

Answer: COM packs signals into I-PDUs for transmission and extracts signals from received I-PDUs.

Q4. What is the role of PduR?

Answer: PduR routes PDUs between configured communication modules.

Q5. What is CanIf?

Answer: CanIf provides the standardized interface between upper communication modules and CAN hardware drivers.

Q6. Explain the CAN transmit path in AUTOSAR.

Answer: A typical signal-based path is SWC → RTE → COM → PduR → CanIf → CAN Driver → CAN Controller → Transceiver → CAN Bus.

Q7. Explain the CAN receive path.

Answer: A typical receive path is CAN Bus → Transceiver → CAN Controller → CAN Driver → CanIf → PduR → COM → RTE → SWC.

Q8. What is CanTp?

Answer: CanTp handles segmentation and reassembly of larger communication messages over CAN.

Q9. What is the difference between COM and DCM?

Answer: COM handles signal-based communication, while DCM handles diagnostic communication such as UDS requests and responses.

Q10. How would you debug a missing CAN message?

Answer: Check the SWC signal update, RTE connection, COM transmission configuration, PduR routing, CanIf configuration, CAN Driver, controller state and physical bus.

16. Lesson Summary

  • Signals represent logical application data.
  • COM packs and unpacks signals into configured I-PDUs.
  • PduR routes communication PDUs.
  • CanIf connects upper communication modules with CAN hardware drivers.
  • The CAN Driver handles CAN controller operations.
  • The transceiver provides the electrical interface to the CAN bus.
  • CanTp supports segmentation and reassembly for larger messages.
  • Transmit and receive paths are essential AUTOSAR placement topics.
  • Configuration consistency is critical for reliable ECU communication.
