Lesson 08: Embedded System Design Process

Chapter 01 – Introduction to Embedded Systems

1. Learning Objectives

After completing this lesson, you will be able to:

  • Understand the complete embedded system design process.
  • Identify the major stages of product development.
  • Perform basic requirements analysis.
  • Understand hardware and software design activities.
  • Explain component selection and system architecture.
  • Understand firmware development and implementation.
  • Differentiate between verification and validation.
  • Understand integration, testing and deployment.

2. Introduction to Embedded System Design

Embedded system design is the systematic process of developing an electronic system that performs a specific function using hardware and software.

It involves understanding the problem, defining requirements, selecting components, designing hardware, developing firmware, integrating the system and testing the final product.

A well-designed embedded system should satisfy its functional requirements while meeting constraints such as cost, size, power consumption, performance, reliability and safety.

Example: Designing an automatic temperature-controlled fan requires a temperature sensor, a controller, firmware, a motor driver and a suitable power supply.

4. Problem Identification

The first stage is to identify the problem that the embedded system must solve.

Questions to consider include:

  • What problem needs to be solved?
  • What function should the system perform?
  • Who will use the product?
  • Where will the system operate?
  • What environmental conditions will it experience?
  • What are the expected operating conditions?

Example: Automatic Fan Controller

Problem: A room requires automatic fan-speed adjustment according to the measured temperature.

The system must measure temperature and control the fan without continuous manual intervention.

5. Requirements Analysis

Requirements analysis identifies and documents what the embedded system must do and the constraints under which it must operate.

5.1 Functional Requirements

Functional requirements describe the operations and features that the system must provide.

Examples:

  • Measure temperature periodically.
  • Display the measured temperature.
  • Adjust fan speed according to temperature.
  • Generate an alarm when a defined limit is exceeded.

5.2 Non-Functional Requirements

Non-functional requirements describe quality attributes and operating constraints.

  • Power consumption.
  • Response time.
  • Reliability.
  • Operating temperature range.
  • Product cost.
  • Physical size.
  • Safety and security.
Requirement Type Example
Functional Read temperature from a sensor.
Functional Control fan speed using PWM.
Non-functional Operate with low power consumption.
Non-functional Respond to temperature changes within a specified time.
Requirements should be measurable wherever possible. For example, instead of writing "the system should respond quickly", specify an acceptable response time.

6. System Specification

System specification converts the requirements into a detailed technical description of the system's expected behavior.

A system specification may include:

  • Input and output definitions.
  • Operating voltage and current requirements.
  • Processing and timing requirements.
  • Communication protocols.
  • Memory requirements.
  • Environmental and safety limits.
  • Performance targets.
  • Testing and acceptance criteria.

Example: Temperature-Controlled Fan

Parameter Illustrative Specification
Input Temperature sensor signal.
Controller Microcontroller.
Output PWM control signal.
Actuator Fan with a suitable driver.
Control behavior Increase fan speed as temperature rises.

7. System Architecture and Component Selection

System architecture defines how the major hardware and software components interact.

7.1 Hardware Architecture

Hardware architecture identifies the processor, memory, sensors, actuators, communication interfaces, power supply and supporting circuits.

7.2 Software Architecture

Software architecture divides the firmware into functional modules and defines how those modules communicate.

Typical modules include:

  • System initialization.
  • GPIO driver.
  • ADC driver.
  • Communication driver.
  • Sensor processing.
  • Application logic.
  • Error handling.

7.3 Component Selection Criteria

  • Processing capability.
  • Memory capacity.
  • Peripheral availability.
  • Operating voltage.
  • Power consumption.
  • Cost and availability.
  • Development tool support.
  • Long-term product support.

8. Hardware Design

Hardware design involves developing the electronic circuits required to implement the system.

Major Activities

  • Preparing the hardware block diagram.
  • Selecting the microcontroller and components.
  • Designing the power supply.
  • Connecting sensors and actuators.
  • Designing signal-conditioning circuits.
  • Defining communication interfaces.
  • Preparing the schematic diagram.
  • Designing the PCB layout.

Hardware Design Tools

  • KiCad.
  • Altium Designer.
  • OrCAD.
  • Proteus Design Suite.
Hardware design must consider electrical ratings, component tolerances, heat dissipation, grounding, signal integrity and protection against faults.

9. Software and Firmware Development

Firmware development involves writing the software that controls the embedded hardware.

Major Activities

  1. Set up the development environment.
  2. Configure the microcontroller and clock.
  3. Initialize required peripherals.
  4. Develop hardware drivers.
  5. Implement application logic.
  6. Handle interrupts and communication.
  7. Compile and link the source code.
  8. Debug and optimize the firmware.

Firmware Development Tools

  • Keil uVision.
  • Arm Development Studio.
  • GCC-based embedded toolchains.
  • Visual Studio Code with suitable embedded extensions.

Typical Firmware Build Process

The exact output files depend on the toolchain. Debugging information may be retained in an ELF file, while HEX or BIN files are commonly used for programming target memory.

10. Hardware-Software Integration

Integration combines the hardware and firmware components into a complete working system.

Integration Activities

  • Connect the controller to the required peripherals.
  • Load or execute the firmware on the target platform.
  • Verify peripheral initialization.
  • Check communication between modules.
  • Verify sensor input processing.
  • Check output control behavior.
  • Resolve hardware-software compatibility issues.

Integration problems may result from incorrect pin configuration, timing mismatches, voltage incompatibility, incorrect register settings or firmware defects.

11. Testing and Debugging

Testing checks whether the system behaves according to its requirements. Debugging identifies and corrects the causes of defects.

11.1 Unit Testing

Individual software modules or hardware functions are tested separately.

11.2 Integration Testing

Combined modules are tested to verify that they interact correctly.

11.3 System Testing

The complete embedded system is tested against its functional and non-functional requirements.

11.4 Performance Testing

Response time, execution time, memory usage, power consumption and other performance characteristics are measured.

11.5 Debugging Tools

  • Debugger and breakpoints.
  • JTAG or SWD debug interfaces, where supported.
  • Oscilloscope.
  • Logic analyzer.
  • Digital multimeter.
  • Serial terminal.
Simulation is useful for checking program flow, register configuration and selected peripheral behavior. It does not replace physical testing of electrical characteristics and real hardware.

12. Verification and Validation

Verification and validation are two important activities used to establish the correctness and suitability of an embedded system.

12.1 Verification

Verification checks whether the system or development output conforms to its specified requirements.

Common techniques include reviews, inspections, static analysis and testing against specifications.

12.2 Validation

Validation checks whether the completed system meets the actual needs and intended use of the customer or end user.

Verification Validation
Are we building the product correctly? Are we building the correct product?
Checks conformance to specifications. Checks suitability for intended use.
May include reviews and technical tests. May include user acceptance and operational tests.

13. Deployment and Maintenance

13.1 Deployment

Deployment is the process of preparing and releasing the completed embedded product for actual operation.

It may include:

  • Final firmware programming.
  • Hardware assembly.
  • Configuration and calibration.
  • Production testing.
  • Installation and commissioning.
  • Product documentation.

13.2 Maintenance

Maintenance keeps the system operational throughout its service life.

Typical maintenance activities include:

  • Correcting firmware defects.
  • Replacing faulty components.
  • Updating firmware.
  • Improving performance.
  • Addressing security vulnerabilities.
  • Maintaining technical documentation.

14. Design Constraints and Trade-Offs

Embedded systems are developed under constraints. Improving one characteristic may affect another. Engineers therefore evaluate trade-offs.

Design Factor Design Consideration
Cost Component and manufacturing expenses.
Performance Processing speed and response time.
Power Energy consumption and battery life.
Memory Program and data storage capacity.
Size PCB dimensions and enclosure requirements.
Reliability Ability to operate correctly over time.
Safety Prevention of hazardous operation.

Example: Battery-Powered Sensor

A battery-powered sensor may require low power consumption and long operating life. The designer may select a low-power microcontroller and use sleep modes, while balancing response time and communication frequency.

15. Practical Example: Design of an Automatic Fan Controller

Step 1: Identify the Problem

Automatically adjust fan speed according to room temperature.

Step 2: Define Requirements

  • Measure temperature.
  • Process sensor readings.
  • Adjust fan speed.
  • Provide safe motor operation.

Step 3: Select Components

  • Microcontroller.
  • Temperature sensor.
  • Motor driver.
  • Fan.
  • Power supply.

Step 4: Design Hardware

Connect the sensor to a suitable input interface and connect the motor through an appropriately rated driver circuit.

Step 5: Develop Firmware

initialize_system(); initialize_sensor(); initialize_pwm(); while (1) { temperature = read_temperature(); if (temperature < 25) { set_fan_speed(0); } else if (temperature < 30) { set_fan_speed(30); } else if (temperature < 35) { set_fan_speed(60); } else { set_fan_speed(100); } delay_ms(1000); }

This is illustrative pseudocode. Functions such as read_temperature(), set_fan_speed() and delay_ms() must be implemented for the selected microcontroller, sensor and motor driver.

Step 6: Test the System

  • Check sensor reading accuracy.
  • Verify threshold decisions.
  • Check PWM duty-cycle generation.
  • Test motor driver operation.
  • Verify safe behavior during sensor faults.

Step 7: Validate the Product

Confirm that the fan controller provides the expected temperature-based speed control under its intended operating conditions.

16. Common Mistakes in Embedded System Design

  • Starting implementation without defining requirements.
  • Selecting a microcontroller without checking peripheral requirements.
  • Ignoring voltage and current ratings.
  • Underestimating memory requirements.
  • Ignoring timing constraints.
  • Failing to consider electrical noise and grounding.
  • Testing software without testing hardware interactions.
  • Skipping verification and validation.
  • Ignoring fault handling and recovery.
  • Failing to document design decisions.

17. Interview Questions and Answers

Q1. What is the embedded system design process?

It is the systematic development process involving problem identification, requirements analysis, specification, architecture, hardware and firmware design, integration, testing, validation and maintenance.

Q2. What is requirements analysis?

It identifies and documents the functions, performance characteristics and constraints that the system must satisfy.

Q3. What is the difference between functional and non-functional requirements?

Functional requirements describe what the system must do. Non-functional requirements describe qualities and constraints such as performance, reliability, cost and power consumption.

Q4. What is system architecture?

System architecture defines the major hardware and software components and their interactions.

Q5. What is hardware-software integration?

It is the process of combining hardware and firmware components and checking their correct interaction.

Q6. What is unit testing?

Unit testing checks individual software modules or hardware functions independently.

Q7. What is the difference between verification and validation?

Verification checks conformance to specifications, whereas validation checks whether the system meets its intended purpose and user needs.

Q8. Why is debugging important?

Debugging identifies and corrects defects that prevent the system from operating correctly.

Q9. What are design trade-offs?

Design trade-offs are decisions that balance competing requirements such as cost, performance, power consumption and reliability.

Q10. Why is maintenance necessary?

Maintenance corrects defects, updates firmware, improves performance and keeps the product reliable during its service life.

18. Multiple-Choice Questions

Q1. Which stage identifies what the system must do?

  1. Requirements analysis
  2. Deployment
  3. Maintenance
  4. Manufacturing

Answer: A – Requirements analysis.

Q2. Which requirement describes power consumption?

  1. Non-functional requirement
  2. Functional requirement
  3. Source code requirement
  4. Input requirement only

Answer: A – Non-functional requirement.

Q3. Which stage combines hardware and firmware?

  1. Integration
  2. Problem identification
  3. Requirement gathering
  4. Maintenance

Answer: A – Integration.

Q4. What does verification check?

  1. Conformance to specifications
  2. Product marketing
  3. Manufacturing cost only
  4. Customer preferences only

Answer: A – Conformance to specifications.

Q5. What is the purpose of system testing?

  1. Test the complete system
  2. Only compile source code
  3. Only select components
  4. Only design the PCB

Answer: A – Test the complete system.

Q6. Which tool is commonly used to inspect electrical waveforms?

  1. Oscilloscope
  2. Text editor
  3. Compiler
  4. Linker

Answer: A – Oscilloscope.

Q7. Which stage follows product deployment during its service life?

  1. Maintenance
  2. Problem identification
  3. Initial specification
  4. Component selection

Answer: A – Maintenance.

Q8. Which is an example of a design trade-off?

  1. Balancing power consumption and performance
  2. Deleting all requirements
  3. Ignoring component ratings
  4. Skipping testing

Answer: A – Balancing power consumption and performance.

20. Lesson Summary

Embedded system design is a structured engineering process that converts an application requirement into a complete hardware and software product.

The process includes problem identification, requirements analysis, system specification, architecture design, component selection, hardware design, firmware development, integration, testing, verification, validation and maintenance.

Careful planning and testing help ensure that the final system meets its functional, performance, reliability, cost and safety requirements.
