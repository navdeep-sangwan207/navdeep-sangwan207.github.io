1. Introduction

Debugging is the process of identifying, analyzing, and correcting errors in software.

Embedded software debugging is especially important because firmware interacts directly with processors, memory, registers, interrupts, and hardware peripherals.

A program may compile successfully but still behave incorrectly during execution. Debugging tools help developers observe program behavior and locate the source of problems.

Learning objectives:
  • Understand debugging in embedded systems.
  • Learn different types of software errors.
  • Understand breakpoints and single-step execution.
  • Learn register and memory inspection.
  • Understand watch windows and call stack.
  • Explore debugging methods in Keil uVision.
  • Understand hardware debugging interfaces.
  • Learn systematic debugging techniques.

2. What Is Debugging?

Debugging is a systematic process of finding the cause of incorrect software behavior and correcting it.

Why debugging is necessary

  • Identify logical errors.
  • Detect incorrect register configurations.
  • Find memory-related problems.
  • Analyze unexpected program execution.
  • Verify interrupt handling.
  • Identify timing and synchronization problems.
  • Improve software reliability.
Write Source Code | v Build Program | v Execute Program | v Observe Behavior | v Is Output Correct? / \ Yes No | | v v Verify Debug Program | | v v Complete Find and Fix Error | v Test Again

3. Types of Software Errors

Embedded software can contain several types of errors. Each type requires a suitable debugging approach.

Error type Description Example
Syntax error Violation of programming language rules. Missing semicolon.
Compilation error Compiler cannot translate the source successfully. Undeclared identifier.
Linker error Required symbols or sections cannot be resolved correctly. Undefined function reference.
Runtime error Problem occurs during execution. Invalid memory access.
Logical error Program executes but produces incorrect results. Incorrect calculation.
Hardware configuration error Peripheral or pin configuration is incorrect. Wrong PINSEL configuration.
Timing error Program does not meet timing requirements. Incorrect timer delay.

5. What Is a Breakpoint?

A breakpoint is a debugging mechanism that temporarily stops program execution at a specified instruction or source-code location.

It allows developers to inspect the program state before execution continues.

Types of breakpoints

Type Description
Software breakpoint Uses debugger-supported mechanisms to stop execution at a selected code location.
Hardware breakpoint Uses processor debug resources to stop execution.
Conditional breakpoint Stops execution only when a specified condition is satisfied, if supported.
Data watchpoint Stops execution when a selected memory location is accessed in a configured way, if supported.

Example

int main(void)
{
    int a = 10;
    int b = 20;

    int sum = a + b;  // Set breakpoint here

    while (1)
    {
    }
}

When execution reaches the breakpoint, the debugger can display the values of a, b, and other available program state.

Breakpoint availability and limits depend on the processor, debug interface, and debugger configuration.

6. Single-Step Execution

Single-step execution allows developers to execute a program one instruction or source-level statement at a time.

Common execution controls

Operation Purpose
Step Into Executes the next statement and enters a called function when applicable.
Step Over Executes the current function call without stepping through its internal statements.
Step Out Continues execution until the current function returns.
Run / Go Continues program execution until a breakpoint or another debug event occurs.
Stop Halts the current debugging execution.

Example

int main(void)
{
    int x = 5;
    int y = 10;

    x = x + y;

    y = x * 2;

    while (1)
    {
    }
}

By stepping through the statements, the developer can observe how the values of x and y change.

7. Register Inspection

Register inspection is the process of viewing the current contents of processor registers and peripheral registers during debugging.

Important ARM7 registers

Register Purpose
R0–R12 General-purpose registers.
R13 / SP Stack pointer.
R14 / LR Link register.
R15 / PC Program counter.
CPSR Current Program Status Register.
SPSR Saved Program Status Register in exception modes.

Why register inspection is useful

  • Check program counter movement.
  • Verify function return addresses.
  • Inspect arithmetic results.
  • Check processor status flags.
  • Investigate exception behavior.
  • Verify stack pointer initialization.

8. Memory Inspection

Memory inspection allows developers to examine the contents of RAM, Flash, and memory-mapped registers through a debugger.

Applications

  • Inspect global and local variables.
  • Check array contents.
  • Examine stack memory.
  • Inspect data structures.
  • Verify memory initialization.
  • Inspect memory-mapped peripheral registers.

Example

int data[4] = {10, 20, 30, 40};

int main(void)
{
    int result = data[2];

    while (1)
    {
    }
}

A debugger memory window can be used to inspect the array's memory locations and stored values.

Always use the correct memory address and access width. Reading an unsupported or side-effecting peripheral register may alter hardware behavior on a real target.

9. Watch Window

A watch window displays selected variables and expressions during program debugging.

Example

int temperature = 25;
int threshold = 30;
int alarm = 0;

int main(void)
{
    if (temperature > threshold)
    {
        alarm = 1;
    }

    while (1)
    {
    }
}

The debugger can monitor:

  • temperature
  • threshold
  • alarm
  • temperature > threshold

Watch windows are useful for tracking variable changes without repeatedly searching the source code.

10. Call Stack and Function Debugging

The call stack shows the sequence of active function calls that led to the current execution point.

Example

void function_C(void)
{
    int value = 100;
}

void function_B(void)
{
    function_C();
}

void function_A(void)
{
    function_B();
}

int main(void)
{
    function_A();

    while (1)
    {
    }
}

If execution stops inside function_C(), the call stack may show:

main() | v function_A() | v function_B() | v function_C() | v Current Execution

This helps identify which function called the current routine and understand the program's execution flow.

11. Debugging in Keil uVision

Keil uVision provides debugging facilities for supported target devices and configured debug methods.

Common debugging facilities

  • Source-level debugging.
  • Breakpoints.
  • Single-step execution.
  • Register windows.
  • Memory windows.
  • Watch windows.
  • Call stack inspection.
  • Peripheral register views where supported.

General debugging procedure

  1. Open the embedded project.
  2. Select the correct target device.
  3. Build the project successfully.
  4. Open the debug configuration.
  5. Select the available simulator or hardware debug method.
  6. Start the debugging session.
  7. Set a breakpoint at the required source-code line.
  8. Run the program.
  9. Inspect registers, variables, and memory.
  10. Use single-step controls to investigate program flow.
  11. Correct the error and rebuild the project.
For your LPC2129 learning environment, use the Keil simulator to inspect supported CPU registers, memory, variables, and program execution. Simulator support for individual peripherals and external electrical behavior is limited and must not be assumed.

12. Serial Debugging

Serial debugging uses a communication interface such as UART to transmit diagnostic information from an embedded application to a terminal.

Example diagnostic message

System Initialized
UART Communication Started
Sensor Value: 512
Application Running

Applications

  • Display system status.
  • Print sensor measurements.
  • Report error codes.
  • Monitor communication events.
  • Track application state transitions.

Advantages

  • Simple diagnostic method.
  • Useful when source-level debugging is unavailable.
  • Can provide runtime information.

Limitations

  • UART output consumes execution time.
  • Messages can change timing-sensitive behavior.
  • Output may be unavailable if UART is not configured correctly.
  • Excessive logging can consume memory.
UART debug messages require a working UART implementation and an appropriate terminal connection. A Keil simulator does not automatically create a physical serial connection.

13. Hardware Debugging Interfaces

Hardware debugging interfaces provide access to the processor's debug facilities through a supported hardware connection.

JTAG

JTAG is a standardized test and debug interface commonly used to access processor debug functionality.

SWD

Serial Wire Debug (SWD) is an ARM debug interface used by many Cortex-M microcontrollers. It is not the standard debug interface for the ARM7TDMI-S LPC2129.

Interface Typical application
JTAG Debugging and boundary-scan operations on supported devices.
SWD Debugging supported ARM Cortex-M devices.
UART Serial diagnostics and communication.
Interface availability depends on the target device, board connections, debug probe, and toolchain support.

14. Logic Analyzer and Oscilloscope in Debugging

Logic analyzer

A logic analyzer captures digital signals over time. It is useful for analyzing communication protocols and digital timing.

Common applications:

  • UART transmission analysis.
  • I2C START and STOP condition analysis.
  • SPI clock and data inspection.
  • Digital GPIO timing analysis.

Oscilloscope

An oscilloscope displays electrical waveforms and helps engineers analyze voltage, timing, noise, and signal integrity.

Common applications:

  • Clock signal measurement.
  • PWM waveform inspection.
  • Voltage level measurement.
  • Signal rise and fall time analysis.
  • Noise and transient investigation.
A logic analyzer focuses on digital logic states, whereas an oscilloscope displays analog voltage waveforms.

15. Systematic Debugging Techniques

1. Reproduce the problem

Identify the conditions under which the error occurs and make it repeatable.

2. Check build messages

Review compiler and linker warnings and errors.

3. Isolate the faulty module

Test individual functions and peripherals separately.

4. Use breakpoints

Stop execution at important program locations.

5. Inspect variables and registers

Verify the actual program state against expected values.

6. Check timing and interrupts

Investigate delays, interrupt priorities, and shared resource access.

7. Fix and retest

Correct the root cause and repeat relevant tests to confirm the solution.

16. Common Embedded Debugging Problems

Problem Possible cause Debugging approach
Program stuck in an infinite loop Incorrect condition or missing state transition. Use breakpoints and inspect variables.
Incorrect GPIO behavior Wrong direction or PINSEL configuration. Inspect GPIO and pin-multiplexing registers.
Incorrect timer delay Wrong peripheral clock or prescaler. Verify clock settings and timer registers.
UART communication failure Incorrect baud rate or pin configuration. Inspect UART configuration and transmission status.
Unexpected variable values Memory corruption or initialization error. Inspect memory and variable updates.
Unexpected interrupt behavior Incorrect VIC configuration or handler setup. Inspect interrupt configuration and execution flow.
Stack overflow Insufficient stack allocation or excessive nesting. Review stack size and function call depth.

17. Practical Exercise: Debug an Embedded C Program

Objective

Practice breakpoints, single-step execution, and variable inspection in the Keil debugging environment.

Program

int main(void)
{
    int a = 10;
    int b = 20;
    int sum = 0;
    int result = 0;

    sum = a + b;

    result = sum * 2;

    while (1)
    {
    }
}

Procedure

  1. Create a new LPC2129 project in Keil uVision.
  2. Add the program to the project.
  3. Build the project.
  4. Start the supported simulator debugging session.
  5. Set a breakpoint at sum = a + b;.
  6. Run the program until the breakpoint is reached.
  7. Inspect a, b, sum, and result.
  8. Use Step Over to execute the statement.
  9. Inspect sum again.
  10. Continue execution to the next assignment.
  11. Verify the final value of result.

Expected variable values

Variable Expected value
a 10
b 20
sum 30
result 60
These are expected program values, not measurements from physical hardware.

18. Practical Exercise: Debugging a GPIO Configuration

Objective

Understand how register inspection can help identify an incorrect GPIO configuration.

Example LPC2129 code

#include <LPC21xx.h>

int main(void)
{
    // Configure P0.5 as GPIO.
    PINSEL0 &= ~(3U << 10);

    // Configure P0.5 as output.
    IODIR0 |= (1U << 5);

    // Set P0.5 high.
    IOSET0 = (1U << 5);

    while (1)
    {
    }
}

Registers to inspect

Register Expected configuration
PINSEL0 Bits 11:10 = 00 for GPIO function on P0.5.
IODIR0 Bit 5 = 1 for output.
IOSET0 Writing bit 5 sets the output latch high.

Use the debugger to inspect these register values where the simulator supports the relevant register behavior.

The simulator's register state does not prove that a physical LED is illuminated. Real electrical behavior requires a correctly connected board and appropriate hardware testing.

19. Interview Questions and Answers

Q1. What is debugging?

Debugging is the process of identifying and correcting software errors.

Q2. What is a breakpoint?

A breakpoint temporarily stops execution at a selected location so the program state can be inspected.

Q3. What is single-step debugging?

It executes the program one instruction or source-level statement at a time.

Q4. What is Step Into?

Step Into executes the next statement and enters a called function when applicable.

Q5. What is Step Over?

Step Over executes a function call without stepping through its internal statements.

Q6. What is a watch window?

It displays selected variables and expressions during debugging.

Q7. What is a call stack?

It shows the sequence of active function calls leading to the current execution point.

Q8. What is register inspection?

It examines the contents of processor or peripheral registers during debugging.

Q9. What is memory inspection?

It examines values stored at selected memory addresses.

Q10. What is JTAG?

JTAG is a standardized interface used for testing and debugging supported electronic devices.

Q11. What is the difference between a logic analyzer and an oscilloscope?

A logic analyzer captures digital logic states, while an oscilloscope displays electrical waveforms.

Q12. What is serial debugging?

It uses a serial communication interface such as UART to send diagnostic messages to a terminal.

Q13. Why can debugging affect program timing?

Breakpoints, logging, and instrumentation can alter execution timing and interrupt behavior.

Q14. What is a watchpoint?

A watchpoint is a debug resource that can halt execution when a configured memory access occurs.
