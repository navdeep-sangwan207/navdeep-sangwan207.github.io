1. Introduction

When an embedded microcontroller is powered on or reset, the processor does not immediately execute the application's main() function.

It first follows a reset mechanism and executes startup instructions that prepare the processor and its runtime environment.

Startup code performs essential initialization tasks, such as setting the stack pointer, initializing memory, configuring runtime support, and transferring control to the application.

A linker script or equivalent linker configuration specifies how program sections are arranged in the target memory.

Learning objectives:
  • Understand embedded system startup.
  • Understand the reset sequence.
  • Learn the purpose of startup code.
  • Understand vector tables and reset handlers.
  • Learn stack pointer initialization.
  • Understand .data and .bss sections.
  • Understand linker scripts and memory maps.
  • Explore startup concepts for ARM7 and LPC2129.

2. What Is Startup Code?

Startup code is a low-level program executed immediately after processor reset and before the main application begins normal execution.

It prepares the processor and memory environment required by the application.

Major responsibilities

  • Initialize the processor's execution environment.
  • Set up stack pointers for required processor modes.
  • Initialize memory sections.
  • Initialize runtime support.
  • Configure essential processor settings when required.
  • Call the C runtime initialization routine.
  • Transfer control to main().
Startup code is usually written in assembly language or supplied as part of the compiler's device support and runtime environment. Its exact implementation depends on the processor, compiler, and project.

3. Embedded System Reset Sequence

A reset returns the processor to a defined initial execution state. The processor then obtains its initial execution address according to its architecture.

General startup sequence

Power ON / RESET | v Processor Reset State | v Reset Vector Execution | v Reset Handler | v Processor Initialization | v Stack Initialization | v Memory Initialization / \ / \ v v .data Copy .bss Clear \ / \ / | v Runtime Initialization | v main() | v Application Execution

This is a conceptual sequence. Actual startup routines may perform additional steps or use a different ordering depending on the processor and toolchain.

4. Reset Vector and Vector Table

A reset vector identifies the initial execution entry associated with processor reset. An interrupt or exception vector table provides entry points for other processor exceptions and interrupts.

ARM7 vector table

ARM7TDMI uses a vector table containing fixed exception entry locations. The table normally begins at the processor's configured exception-vector base.

Address offset Exception
0x00 Reset
0x04 Undefined Instruction
0x08 Software Interrupt (SWI)
0x0C Prefetch Abort
0x10 Data Abort
0x14 Reserved
0x18 IRQ
0x1C FIQ

Each vector entry typically contains an instruction that branches to the corresponding handler.

The ARM7 exception vector table is not identical to the vectored interrupt controller (VIC) vector slots of the LPC2129. The processor exception vectors and peripheral interrupt dispatch mechanisms are related but separate concepts.

5. Reset Handler

The reset handler is the first software routine executed after the processor follows its reset entry.

It performs the initial system setup and transfers execution to the application's runtime initialization.

Typical reset handler responsibilities

  1. Establish the required processor execution state.
  2. Initialize stack pointers.
  3. Configure essential clock or memory settings if required.
  4. Initialize global and static memory sections.
  5. Call runtime initialization.
  6. Enter main().

Conceptual pseudocode

Reset_Handler:

    Initialize_Processor_State();

    Initialize_Stack_Pointers();

    Initialize_Memory();

    Initialize_Runtime();

    Call main();

Stop:
    Branch Stop;

This is illustrative pseudocode, not a complete processor-specific startup implementation.

6. Stack Initialization

The stack is a memory region used for temporary data during program execution.

It stores function call information, local variables, saved registers, and other temporary execution data.

Stack pointer

The stack pointer (SP) is a processor register that identifies the current stack position.

Before normal application execution, startup code must establish valid stack memory and initialize the appropriate stack pointer.

ARM7 processor modes and stacks

ARM7TDMI provides banked stack pointer registers for different processor modes.

Processor mode Stack pointer
User R13_usr
System R13_usr (shared with User mode)
Supervisor R13_svc
IRQ R13_irq
FIQ R13_fiq
Abort R13_abt
Undefined R13_und
ARM7TDMI has banked stack pointers for exception modes. Startup code must establish valid stacks for the modes that the application and its exception handlers use.

Stack growth

A common ARM application convention uses a descending stack, in which the stack grows toward lower memory addresses. The exact stack convention depends on the selected ABI and startup implementation.

7. Memory Initialization

Embedded applications use different memory sections for program instructions, initialized variables, uninitialized variables, and temporary data.

Startup code prepares these sections before the application begins normal execution.

Important memory sections

Section Purpose
.text Contains executable program instructions.
.rodata Contains read-only constants and data.
.data Contains initialized global and static variables.
.bss Contains zero-initialized or uninitialized global and static variables.
Stack Stores temporary function execution data.
Heap Supports dynamic memory allocation when used.

8. .data Section Initialization

The .data section stores global and static variables that have explicit initial values.

Example

int system_mode = 1;
int counter = 100;

int main(void)
{
    while (1)
    {
    }
}

The initial values of these variables must be available when the application begins execution.

How initialization works

  1. Initial values are stored in the program image, usually in non-volatile memory.
  2. Startup code identifies the load and execution addresses of the .data section.
  3. The initial values are copied into the RAM execution region.
  4. The application can access the initialized variables.
FLASH / ROM .data initial values | | Copy during startup v RAM .data execution region
The load address is where the initial data is stored in the firmware image. The execution address is where the variables are accessed during program execution.

9. .bss Section Initialization

The .bss section contains global and static variables that are zero-initialized before the C application begins normal execution.

Example

int counter;
static int status;

int main(void)
{
    while (1)
    {
    }
}

In this example, counter and status have static storage duration and are initialized to zero before main() begins.

How initialization works

  1. Startup code identifies the beginning of the .bss section.
  2. It identifies the end of the section.
  3. It writes zero to the memory locations in that range.
  4. The program begins with these variables initialized to zero.
for (unsigned int *p = bss_start;
     p < bss_end;
     p++)
{
    *p = 0;
}

This is conceptual C-style pseudocode. Actual startup code often uses assembly instructions or compiler runtime routines.

10. .data vs .bss

Feature .data .bss
Variables Initialized global and static variables. Zero-initialized global and static variables.
Initial values Explicit values. Zero.
Firmware image Stores initial data values. Usually does not need to store zero-filled data bytes.
Startup operation Copy initial values to RAM. Clear the RAM region to zero.

Example

int a = 10;       // .data

int b;             // .bss

static int c = 5;  // .data

static int d;      // .bss

11. What Is a Linker Script?

A linker script is a configuration file used by certain toolchains to control how input sections from object files are arranged in the output image.

It specifies memory regions, section placement, addresses, and other linking rules.

Main responsibilities

  • Define available memory regions.
  • Place executable code in program memory.
  • Place writable data in RAM.
  • Define load and execution addresses.
  • Reserve stack and heap space where configured.
  • Control section alignment and placement.
  • Detect memory overflow during linking.
Different toolchains use different linker configuration formats. GNU ld uses linker scripts, while Keil projects use the memory and scatter-loading configuration supported by their selected toolchain.

12. Memory Regions

An embedded microcontroller typically contains several memory regions with different purposes.

Common memory types

Memory Purpose
Flash Non-volatile storage for program code and constant data.
SRAM Volatile storage for variables, stack, and heap.
ROM Non-volatile memory containing fixed code or data.
Peripheral registers Memory-mapped control and status registers.

Conceptual memory map

HIGH MEMORY ADDRESS +----------------------+ | Peripheral Registers | +----------------------+ | | | SRAM | | | | Stack / Heap | | .bss / .data | | | +----------------------+ | | | FLASH | | | | .text / .rodata | | Initial .data | | | +----------------------+ LOW MEMORY ADDRESS

This is a conceptual illustration, not an LPC2129 address map. Actual memory addresses and sizes must be taken from the selected device's memory map and project configuration.

13. Example GNU Linker Script

The following is a simplified educational example showing how memory regions and sections can be described using GNU ld syntax. 

ENTRY(Reset_Handler)

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x00000000, LENGTH = 256K
    RAM   (rwx) : ORIGIN = 0x40000000, LENGTH = 32K
}

SECTIONS
{
    .text :
    {
        KEEP(*(.vectors))
        *(.text*)
        *(.rodata*)
    } > FLASH

    .data :
    {
        _data_start = .;
        *(.data*)
        _data_end = .;
    } > RAM AT > FLASH

    _data_load = LOADADDR(.data);

    .bss :
    {
        _bss_start = .;
        *(.bss*)
        *(COMMON)
        _bss_end = .;
    } > RAM
}

Explanation

  • ENTRY(Reset_Handler) identifies the entry symbol for the linker.
  • MEMORY defines the available memory regions.
  • FLASH is used for executable code.
  • RAM is used for writable data.
  • .text contains code and read-only data in this simplified example.
  • .data executes from RAM but is loaded from FLASH.
  • .bss reserves RAM for zero-initialized data.
The memory sizes and addresses above are illustrative, not verified LPC2129 linker settings. Never copy this example into an LPC2129 production project without checking the device memory map, startup implementation, and toolchain requirements.

14. Scatter Files in Keil

Keil toolchains can use scatter-loading descriptions to specify how code and data regions are arranged in memory.

A scatter file describes load regions and execution regions. It can also control placement of code, read-only data, writable data, and other sections.

Important terms

Term Meaning
Load Region Region where the initial image is stored.
Execution Region Region where code or data is accessed during execution.
RO Read-only content.
RW Read-write initialized content.
ZI Zero-initialized content.
In Keil uVision, the exact linker configuration interface depends on the selected compiler and project setup. Older ARM Compiler workflows and newer Arm Compiler workflows may use different settings and syntax.

15. Startup Code and Linker Configuration Relationship

Startup code and linker configuration work together. The linker determines where sections are located, while startup code uses the relevant addresses and initialization information to prepare memory.

SOURCE FILES | v COMPILER | v OBJECT FILES | v LINKER | +----+-----+ | | v v MEMORY MAP STARTUP / SECTIONS SYMBOLS | | +----+-----+ | v FIRMWARE IMAGE | v RESET / STARTUP CODE | v INITIALIZED RAM | v main()

Why coordination matters

  • Startup code must use the correct memory boundaries.
  • The linker must place sections in valid memory regions.
  • Stack memory must not overlap application data.
  • Initialized data must have valid load and execution addresses.
  • Vector table placement must match processor requirements.

16. LPC2129 Startup Concepts

The LPC2129 uses an ARM7TDMI-S core. Its startup implementation must account for ARM7 exception modes, stack organization, memory layout, and the microcontroller's clock and peripheral configuration.

Typical LPC2129 startup considerations

  1. Provide a valid exception vector table.
  2. Establish stack pointers for the required ARM modes.
  3. Configure the PLL and peripheral clock if required by the application.
  4. Initialize the memory sections.
  5. Initialize runtime support.
  6. Enter the main application.

Example application-level clock configuration

#include <LPC21xx.h>

int main(void)
{
    // Example application entry point.
    // Clock initialization should be performed
    // using the project's startup and clock routines.

    while (1)
    {
        // Application code
    }
}

The example demonstrates an application entry point only. It does not implement the reset handler, stack initialization, or .data/.bss initialization.

In your LPC2129 Keil simulator workflow, inspect the startup file and linker configuration included in the project. Do not replace compiler-provided startup code unless you understand its vector table, stack, memory initialization, and runtime requirements.

17. Common Startup and Linker Problems

Problem Possible cause Solution
Program does not reach main() Incorrect reset handler or startup configuration. Inspect the reset vector and startup execution.
Global variables contain unexpected values Incorrect .data or .bss initialization. Verify memory initialization routines.
Stack corruption Incorrect stack address or insufficient stack size. Review stack configuration and memory boundaries.
Linker memory overflow Sections exceed available target memory. Inspect the memory map and reduce memory usage.
Incorrect section placement Invalid linker or scatter configuration. Verify memory regions and section placement.
Interrupt malfunction Incorrect vector table or handler configuration. Inspect exception vectors and interrupt setup.

18. Practical Exercise: Inspect Startup and Memory Configuration

Objective

Understand the startup process and identify how the LPC2129 project organizes program and data memory.

Tools required

  • Keil uVision.
  • LPC2129 project.
  • Device startup source file.
  • Linker or scatter configuration, if applicable.
  • Build output and map file.

Procedure

  1. Open the LPC2129 project in Keil uVision.
  2. Locate the startup assembly or startup source file.
  3. Find the reset handler and exception vector definitions.
  4. Identify stack initialization instructions.
  5. Locate the .data and .bss initialization routines.
  6. Open the target memory configuration.
  7. Build the project successfully.
  8. Inspect the linker map file if generated.
  9. Identify the code and data memory addresses.
  10. Use the debugger to inspect memory and registers where supported.

Expected observations

  • Startup code provides a reset entry point.
  • Stack pointers are established before normal application execution.
  • Initialized data and zero-initialized data have defined memory regions.
  • The linker map shows section placement and memory usage.
The Keil simulator can help inspect CPU registers, execution flow, and memory. It does not establish that a physical LPC2129 board has been programmed or that external hardware operates correctly.

19. Interview Questions and Answers

Q1. What is startup code?

Startup code is low-level code executed after reset to initialize the processor and runtime environment before the application starts.

Q2. What is a reset handler?

It is the routine entered after reset that performs initial system setup and transfers execution to application runtime initialization.

Q3. What is a vector table?

A vector table contains exception or interrupt entry points used by the processor to locate the appropriate handler.

Q4. What is a stack pointer?

It is a processor register that identifies the current position of the stack in memory.

Q5. What is the .data section?

It contains initialized global and static variables. Their initial values are normally copied into RAM during startup.

Q6. What is the .bss section?

It contains zero-initialized or uninitialized global and static variables that are set to zero before main() begins.

Q7. What is a linker script?

It is a configuration file that controls memory regions and section placement during linking.

Q8. What is a scatter file?

It is a linker configuration file used by supported Keil toolchains to define load and execution regions.

Q9. What is the difference between .data and .bss?

.data stores explicit initial values, while .bss represents zero-initialized data.

Q10. Why is startup code necessary?

It prepares the processor, stack, memory, and runtime environment required for reliable application execution.

Q11. What is a load address?

It is the address where a section's initial contents are stored in the firmware image.

Q12. What is an execution address?

It is the address where a section is accessed during program execution.

Q13. What is the purpose of a linker map file?

It provides information about memory regions, section placement, symbols, and memory usage.

Q14. Does main() execute immediately after reset?

No. The reset handler and startup routines execute first and prepare the application runtime environment.
