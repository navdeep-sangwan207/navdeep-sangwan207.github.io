1. Introduction

Embedded system simulation and emulation are techniques used to develop, test, and verify embedded software before or during deployment on physical hardware.

These techniques help developers understand processor behavior, test program logic, examine memory operations, and investigate interactions between software and hardware components.

Simulation generally uses a software model to represent a system or selected parts of it. Emulation uses a different implementation, often dedicated hardware, to reproduce the behavior of a target system.

Learning objectives:
  • Understand embedded system simulation.
  • Understand embedded system emulation.
  • Differentiate simulation and emulation.
  • Learn instruction-set and processor simulation.
  • Understand peripheral modeling.
  • Explore hardware-in-the-loop testing.
  • Understand the role of Keil uVision simulation.
  • Identify the advantages and limitations of simulation.

2. What Is Simulation?

Simulation is the process of representing the behavior of a real system using a software model or mathematical model.

In embedded systems, a simulator can model processor instructions, memory, selected peripherals, and interactions between system components.

Example

A microcontroller simulator may execute compiled instructions and allow a developer to inspect:

  • CPU registers.
  • Program counter.
  • Memory locations.
  • Variables.
  • Instruction execution.
  • Selected peripheral registers.
Embedded Application | v Compiled Program | v Software Model | v Simulated Execution | v Observe Program Behavior
A simulator only reproduces the behavior represented by its models. It does not automatically reproduce every electrical, mechanical, or timing characteristic of a physical embedded system.

3. What Is Emulation?

Emulation is the process of reproducing the behavior of a target system using another implementation that provides compatible behavior.

In embedded development, emulation may use dedicated hardware or a specialized platform to reproduce the target processor or system environment.

Example

A hardware emulator can provide a development environment that behaves similarly to the intended embedded target and allows software to be evaluated before the final product is available.

Applications

  • Testing firmware before final hardware production.
  • Evaluating processor behavior.
  • Testing software compatibility.
  • Investigating difficult-to-reproduce faults.
  • Developing and validating embedded applications.
Emulation is not necessarily faster or more accurate than simulation. Its usefulness depends on the implementation, target behavior, and testing objective.

4. Difference Between Simulation and Emulation

Parameter Simulation Emulation
Basic concept Models system behavior. Reproduces target behavior using another implementation.
Implementation Usually software or mathematical models. May use dedicated hardware or specialized platforms.
Execution Runs within the simulator's modeled environment. Runs within an emulated target environment.
Hardware dependency Can operate without the actual target board. May use dedicated emulation hardware.
Typical use Algorithm, instruction, and modeled peripheral testing. Target-system behavior and compatibility testing.
Limitations Limited by model accuracy and coverage. Limited by emulation fidelity and supported features.
The terms simulation and emulation can overlap in commercial tools. Always identify what the particular tool actually models or reproduces.

5. Types of Embedded System Simulation

5.1 Software Simulation

Software simulation uses a program to model the behavior of a system or component.

It can be used to test algorithms, application logic, state machines, and selected system interactions.

5.2 Processor Simulation

Processor simulation models CPU behavior, including instruction execution and register operations.

Typical features include:

  • Instruction execution.
  • Register updates.
  • Program counter movement.
  • Memory access modeling.
  • Processor status updates.

5.3 Instruction Set Simulation

Instruction Set Simulation (ISS) models the instruction set of a processor.

It allows compiled machine instructions to be executed in a software environment that models the target processor's instruction behavior.

5.4 Peripheral Simulation

Peripheral simulation models selected hardware peripherals such as timers, UART, GPIO, ADC, and communication controllers.

5.5 System-Level Simulation

System-level simulation represents interactions between multiple components of an embedded system.

  • Processor.
  • Memory.
  • Communication interfaces.
  • Sensors and actuators.
  • Control algorithms.

6. Instruction Set Simulator (ISS)

An Instruction Set Simulator is a software tool that models the instruction set architecture of a processor.

It executes instructions according to the modeled processor architecture and updates the simulated processor state.

Example

    MOV R0, #10
    MOV R1, #20
    ADD R2, R0, R1

An ARM instruction-set simulator can model the execution of these instructions.

Expected register values

Register Expected value
R0 10
R1 20
R2 30

Advantages

  • Allows instruction-level testing.
  • Helps understand processor behavior.
  • Supports debugging without the physical processor.
  • Can help investigate instruction execution problems.

7. Peripheral Modeling

A peripheral model represents the behavior of a hardware peripheral in a simulator.

It may model registers, control operations, status flags, and selected input/output behavior.

Common peripheral models

Peripheral Possible simulated behavior
GPIO Input/output register behavior and pin states.
Timer Counter progression and selected match events.
UART Selected transmit and receive register behavior.
ADC Modeled conversion values and result registers.
PWM Selected period and duty-cycle behavior.
I2C Selected controller status and transfer behavior.
A peripheral appearing in a device header file or memory map does not prove that the simulator fully models it. Check the debugger and simulator documentation for supported functionality.

8. Simulation of Embedded C Programs

Embedded C applications can be compiled and executed in a supported simulator environment.

General workflow

    int total = 0;

    {
        total = total + count;

    }

Expected result

A debugger can be used to set breakpoints, execute the program step by step, and inspect the variables.

9. Keil uVision Simulator

Keil uVision provides a simulator option for supported processor targets. It can be used to execute and debug software without connecting a physical target board.

Common debugging capabilities

  • Source-level debugging.
  • Breakpoint-based execution.
  • Single-step execution.
  • CPU register inspection.
  • Memory inspection.
  • Variable monitoring.
  • Program execution analysis.

General procedure

  1. Open the LPC2129 project in Keil uVision.
  2. Verify the selected target device.
  3. Build the project.
  4. Open the project debug settings.
  5. Select the available simulator option.
  6. Start the debugging session.
  7. Set breakpoints in the source code.
  8. Run or step through the program.
  9. Inspect CPU registers and variables.
  10. Inspect supported peripheral registers where available.
Application to your LPC2129 learning environment: The Keil simulator can be used to practice program execution, breakpoints, variable inspection, and supported register-level debugging. It does not replace a physical LPC2129 board for validating electrical signals, actual sensor readings, or external peripheral connections.

10. Hardware Emulation

Hardware emulation uses a hardware-based platform or specialized implementation to reproduce selected behavior of a target embedded system.

Examples of hardware emulation platforms

  • FPGA-based processor emulation.
  • Hardware development platforms.
  • Specialized processor emulators.
  • Target hardware with debug and trace support.

FPGA-based emulation

A Field Programmable Gate Array (FPGA) can be configured to implement digital hardware logic. It may be used to reproduce a processor or selected hardware components for testing.

Target System Design | v Hardware Model | v FPGA Platform | v Emulated Hardware | v Firmware Evaluation

Applications

  • Early hardware and firmware development.
  • Digital system verification.
  • Processor architecture evaluation.
  • Interface and integration testing.

11. Hardware-in-the-Loop (HIL) Testing

Hardware-in-the-Loop testing is a verification technique in which a real controller or embedded device interacts with a simulated environment.

The simulated environment provides input signals and models the system being controlled. The actual controller processes these inputs and generates outputs that are returned to the simulation.

Simulated Plant / Environment | Input Signals | v Real Embedded Controller | Output Signals | v Simulation Updates the Model | +------ Feedback

Example: Motor control system

A motor controller can be connected to a simulated motor model. The controller generates PWM commands, and the simulated motor model calculates the corresponding response.

Applications

  • Automotive electronic control units.
  • Motor control systems.
  • Industrial automation.
  • Power electronics control.
  • Flight control system testing.

Advantages

  • Tests real controller hardware in a controlled environment.
  • Can reproduce selected operating conditions.
  • Helps test fault conditions safely.
  • Supports repeatable testing.

12. Model-in-the-Loop and Software-in-the-Loop

Model-in-the-Loop (MIL)

Model-in-the-Loop testing verifies a control algorithm or system design using models before deploying it to actual embedded hardware.

Software-in-the-Loop (SIL)

Software-in-the-Loop testing executes software within a simulated environment to evaluate its behavior without requiring the final physical target.

Hardware-in-the-Loop (HIL)

Hardware-in-the-Loop testing uses the actual controller hardware connected to a simulated environment.

Method What is tested?
MIL System or control models.
SIL Software implementation in a simulated environment.
HIL Real controller hardware interacting with a simulated system.
MIL, SIL, and HIL are different stages or methods of verification. They are commonly used together in model-based development and control-system testing.

13. Advantages of Simulation and Emulation

Simulation advantages

  • Reduces dependence on physical hardware during early development.
  • Allows repeatable software testing.
  • Supports debugging of modeled processor behavior.
  • Helps identify software errors early.
  • Can reduce development cost and time.
  • Supports testing of selected operating conditions.

Emulation advantages

  • Can reproduce selected target-system behavior.
  • Supports early firmware evaluation.
  • Can provide access to hardware-oriented behavior.
  • Helps evaluate system integration.
  • Can support testing before final hardware production.

14. Limitations of Simulation and Emulation

Simulation limitations

  • Model behavior may differ from physical hardware.
  • Some peripherals may not be implemented.
  • Electrical characteristics may not be represented.
  • Real-world timing and signal effects may be missing.
  • External devices may require separate models.

Emulation limitations

  • Emulation hardware can be expensive.
  • Not every hardware behavior may be reproduced.
  • Platform setup can be complex.
  • Performance may differ from the final target.
  • Hardware interfaces may require specialized tools.
Successful simulation does not guarantee that firmware will work correctly on physical hardware. Final validation must include target hardware testing.

15. Simulation vs Real Hardware Testing

Parameter Simulation Real hardware testing
Processor Modeled processor behavior. Actual physical processor.
GPIO Modeled pin or register behavior. Actual electrical pin behavior.
Sensor input May use modeled or manually supplied values. Actual sensor signals.
UART May model selected communication behavior. Actual electrical serial communication.
Power consumption Requires suitable power models. Can be measured using physical equipment.
Electrical noise Only represented if modeled. Can be observed in the real circuit.
Hardware faults Only represented if modeled. Actual hardware faults can be investigated.

16. Practical Exercise: Simulating an Embedded C Program

Objective

Execute a simple embedded C program in the Keil simulator and inspect the variable values.

Program

#include <LPC21xx.h>

int main(void)
{
    unsigned int count = 0;
    unsigned int sum = 0;

    for (count = 1; count <= 10; count++)
    {
        sum = sum + count;
    }

    while (1)
    {
    }
}

Procedure

  1. Open the LPC2129 project in Keil uVision.
  2. Add the source file to the project.
  3. Build the program.
  4. Select the configured simulator.
  5. Start the debugging session.
  6. Set a breakpoint after the for loop.
  7. Run the program until the breakpoint.
  8. Inspect count and sum in the watch window.

Expected result

Variable Expected value
count 11
sum 55
This exercise verifies software execution and variable values. It does not test external hardware or electrical signals.

17. Practical Exercise: Understanding GPIO Simulation

Objective

Understand how GPIO register operations can be examined during a simulator debugging session.

Example LPC2129 code

#include <LPC21xx.h>

int main(void)
{
    // Select GPIO function for P0.5.
    PINSEL0 &= ~(3U << 10);

    // Configure P0.5 as output.
    IODIR0 |= (1U << 5);

    while (1)
    {
        IOSET0 = (1U << 5);
    }
}

Registers to examine

Register Purpose
PINSEL0 Selects the pin function.
IODIR0 Configures the direction of Port 0 pins.
IOSET0 Sets the selected output latch bits.

Use the debugger to inspect the register values where the simulator supports the relevant LPC2129 register behavior.

The code does not demonstrate physical LED illumination. A simulator may show register-level changes without reproducing the electrical output at the actual pin.

18. Interview Questions and Answers

Q1. What is simulation?

Simulation represents system behavior using a software or mathematical model.

Q2. What is emulation?

Emulation reproduces target-system behavior using another implementation, often a specialized hardware platform.

Q3. What is the difference between simulation and emulation?

Simulation models selected system behavior, while emulation attempts to reproduce the target's behavior through a compatible implementation.

Q4. What is an instruction-set simulator?

It is a software tool that models a processor's instruction set and executes instructions in a simulated environment.

Q5. What is peripheral simulation?

It models the behavior of hardware peripherals such as timers, UART, GPIO, and ADC.

Q6. What is an ISS?

ISS stands for Instruction Set Simulator.

Q7. What is hardware emulation?

It uses a hardware-based platform or specialized implementation to reproduce selected target-system behavior.

Q8. What is FPGA-based emulation?

It uses programmable digital logic to implement hardware behavior for development and verification.

Q9. What is HIL testing?

Hardware-in-the-Loop testing connects a real controller to a simulated environment.

Q10. What is SIL testing?

Software-in-the-Loop testing executes software in a simulated environment.

Q11. What is MIL testing?

Model-in-the-Loop testing verifies system or control models before implementation on target hardware.

Q12. Can simulation replace real hardware testing?

No. Simulation cannot automatically verify real electrical behavior, physical connections, and environmental effects.

Q13. What is the purpose of the Keil simulator?

It provides a supported environment for executing and debugging software without connecting a physical target board.

Q14. What are the limitations of peripheral simulation?

A simulator may support only selected registers and peripheral behavior. External electrical signals and devices may not be represented.

21. Lesson Summary

  • Simulation models system behavior using software or mathematical models.
  • Emulation reproduces selected target behavior using another implementation.
  • An ISS models processor instruction execution.
  • Peripheral models represent selected hardware functions.
  • Keil uVision provides simulation and debugging facilities for supported targets.
