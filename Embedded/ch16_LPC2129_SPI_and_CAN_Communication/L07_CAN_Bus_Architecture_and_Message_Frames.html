Lesson 07: CAN Bus Architecture and Message Frames

Study CAN bus topology, message frame structure, standard and extended identifiers, and the different types of CAN frames used in embedded communication.

1. Learning Objectives

After completing this lesson, you will be able to:

  • Understand CAN bus architecture and topology.
  • Explain the two-wire CAN physical bus.
  • Understand CAN frame structure.
  • Identify the fields of a Classical CAN data frame.
  • Differentiate standard and extended CAN frames.
  • Understand the purpose of the identifier and DLC.
  • Explain CRC, ACK and end-of-frame fields.
  • Differentiate data, remote, error and overload frames.
  • Understand bit stuffing in CAN communication.
  • Identify CAN frame timing and bus termination requirements.

2. CAN Bus Architecture

Controller Area Network uses a shared communication bus that connects multiple electronic control units and embedded devices.

Unlike point-to-point communication, CAN allows multiple nodes to communicate over the same pair of bus wires.

Basic CAN Bus Structure

     120 ohm termination                 120 ohm termination
             |                                   |
             +===================================+
             |           CAN_H / CAN_L           |
             +===================================+
                   |          |          |
                +--+--+    +--+--+    +--+--+
                |Node1|    |Node2|    |Node3|
                +-----+    +-----+    +-----+

                 Shared CAN communication bus

Bus Components

ComponentFunction
CAN_HHigh-side differential signal.
CAN_LLow-side differential signal.
CAN NodeElectronic device participating in the network.
CAN ControllerProcesses CAN protocol operations.
CAN TransceiverProvides the physical bus interface.
TerminationReduces signal reflections at bus ends.

3. CAN Network Topology

A high-speed CAN network normally uses a linear bus topology. Each node connects to the main bus through a short branch called a stub.

Linear Bus Topology

       120 ohm                         120 ohm
          |                               |
          +=========== Main Bus ==========+
                     |       |
                     |       |
                   Node A  Node B
                     |
                   Node C

Important Design Rules

  • Use a properly terminated main bus.
  • Install termination resistors at the two physical ends.
  • Keep node stubs short.
  • Use a suitable twisted-pair cable.
  • Maintain correct CAN_H and CAN_L polarity.
  • Ensure all nodes use compatible bit timing.
  • Follow the transceiver's common-mode voltage limits.
CAN network length, stub length and maximum bit rate are related. A higher bit rate generally requires a shorter network and more careful signal-integrity design.

4. CAN Physical Layer

The physical layer defines the electrical signals, cabling, connectors, termination and signaling characteristics used to transmit CAN bits.

Differential Signaling

Vdiff = V(CAN_H) - V(CAN_L)
Bus State Typical CAN_H Typical CAN_L Typical Differential Voltage
Recessive 2.5 V 2.5 V Approximately 0 V
Dominant 3.5 V 1.5 V Approximately 2 V

These are typical illustrative high-speed CAN values. Actual electrical levels depend on the transceiver and network conditions.

Dominant and Recessive States

  • Dominant state represents logic 0.
  • Recessive state represents logic 1.
  • Dominant overrides recessive on the shared bus.

5. Introduction to CAN Frames

CAN communication is organized into structured units called frames.

A frame contains control information, an identifier, optional data and error-checking fields.

Types of Classical CAN Frames

Frame TypePurpose
Data FrameTransfers application data.
Remote FrameRequests transmission of a data frame with a specified identifier.
Error FrameSignals detection of a CAN protocol error.
Overload FrameProvides additional delay between frames under defined conditions.
Classical CAN and CAN FD have different frame capabilities. This lesson focuses on Classical CAN frame structure used by the LPC2129 CAN controller.

An extended Classical CAN frame uses a 29-bit identifier instead of the 11-bit identifier.

9. Start of Frame (SOF)

The Start of Frame field indicates the beginning of a CAN message.

  • SOF consists of one dominant bit.
  • It marks the start of a data or remote frame.
  • Nodes use it to synchronize with the incoming frame.
  • It follows the bus idle condition.

10. Identifier Field

The identifier field identifies the message and determines its priority during arbitration.

Important Characteristics

  • Standard identifier contains 11 bits.
  • Extended identifier contains 29 bits.
  • Lower numerical identifier generally means higher priority.
  • All nodes can observe the identifier.
  • Acceptance filters can select relevant messages.
The identifier is a message identifier, not necessarily the address of the transmitting or receiving device.

11. Remote Transmission Request (RTR)

The RTR bit distinguishes a data frame from a remote frame in Classical CAN.

Frame TypeRTR Value
Data FrameDominant (0)
Remote FrameRecessive (1)

A remote frame requests a data frame with the same identifier. It contains no data field.

Remote frames are part of Classical CAN. CAN FD does not support remote frames.

12. Identifier Extension (IDE)

The IDE bit identifies whether a frame uses the standard or extended identifier format.

IDE ValueFrame Format
Dominant (0)Standard 11-bit identifier.
Recessive (1)Extended 29-bit identifier.

13. Data Length Code (DLC)

The DLC field is four bits long and indicates the number of data bytes in a Classical CAN data frame.

Classical CAN supports a maximum of 8 data bytes. CAN FD uses different DLC interpretation rules for payload lengths greater than 8 bytes.

14. Data Field

The data field carries the application information transmitted by the CAN node.

Example: Vehicle Speed Message

Identifier = 0x123
DLC        = 2

Data Byte 0 = 0x64
Data Byte 1 = 0x00

In this illustrative example, the two bytes could represent a vehicle-speed value according to a system-specific encoding.

CAN itself does not define the engineering meaning of application data. The scaling, byte order, units and signal layout must be specified by the system's communication design.

15. Cyclic Redundancy Check (CRC)

CRC is an error-detection mechanism used to check the integrity of transmitted CAN frames.

Classical CAN CRC

  • CRC sequence contains 15 bits.
  • CRC delimiter follows the CRC sequence.
  • The receiver checks the frame's CRC.
  • A CRC error is one type of CAN frame error.

The CRC is generated from the relevant preceding frame bits using the defined CAN CRC algorithm.

16. Acknowledgement (ACK) Field

The ACK field allows a receiving node that has correctly received a frame to acknowledge it.

  • The transmitter sends a recessive bit in the ACK slot.
  • A receiver that correctly receives the frame can drive the ACK slot dominant.
  • The transmitter monitors the bus during the ACK slot.
  • The ACK delimiter is recessive.
An ACK confirms that at least one node acknowledged the frame at the CAN protocol level. It does not prove that the intended application processed the message correctly.

17. End of Frame (EOF)

The End of Frame field marks the completion of a Classical CAN data or remote frame.

  • EOF consists of seven recessive bits.
  • It follows the ACK delimiter.
  • It indicates that the frame transmission is complete.
  • The bus can return to the idle state after the frame.

18. Bit Stuffing

CAN uses bit stuffing to maintain synchronization between transmitting and receiving nodes.

After five consecutive bits of the same polarity in the applicable stuffed region, the transmitter inserts one bit of the opposite polarity.

Example

Original sequence:
11111

Stuffed sequence:
111110

The receiver removes the inserted stuff bit. A violation of the bit-stuffing rule can cause a stuff error.

Bit stuffing applies to the defined CAN frame region from SOF through the CRC sequence. It does not apply to the CRC delimiter, ACK field or EOF.

19. CAN Data Frame Example

Consider a standard Classical CAN data frame containing two application data bytes. 

Identifier : 0x123
Frame Type : Standard Data Frame
RTR        : 0
IDE        : 0
DLC        : 2
Data       : 0x64, 0x00

CRC        : Generated by CAN controller
ACK        : Provided by a valid receiving node
EOF        : 7 recessive bits

Frame Transmission Sequence

  1. The bus becomes idle.
  2. The transmitter sends SOF.
  3. The identifier and control fields are transmitted.
  4. The data bytes are transmitted.
  5. The CRC sequence is transmitted.
  6. Receivers acknowledge a valid frame.
  7. The transmitter sends the EOF sequence.

20. Remote Frame

A Classical CAN remote frame requests that another node transmit a data frame using a particular identifier.

Characteristics

  • Contains an identifier.
  • RTR is recessive.
  • Contains no application data field.
  • Contains a DLC indicating the requested data length.
Remote frames are rarely used in many modern CAN application designs. CAN FD does not support remote frames.

21. Error Frame

An error frame is transmitted when a CAN node detects a protocol error and signals that the current frame is invalid.

Error Frame Components

  • Error flag.
  • Error delimiter.

Error Flag Types

TypeCharacteristics
Active Error FlagSix consecutive dominant bits.
Passive Error FlagSix consecutive recessive bits.

Error signaling and recovery are handled by the CAN protocol controller.

22. Overload Frame

An overload frame provides additional delay between frames when a node requires more time to prepare for the next communication.

Characteristics

  • It is used in Classical CAN.
  • It contains an overload flag and delimiter.
  • It is separate from normal data transmission.
  • It affects the timing between successive frames.

25. Interview Questions and Answers

Q1. What is a CAN frame?

A CAN frame is a structured message containing an identifier, control fields, optional data and error-checking information.

Q2. What is SOF?

Start of Frame is the one-bit dominant field that marks the beginning of a CAN frame.

Q3. What is the length of a standard CAN identifier?

11 bits.

Q4. What is the length of an extended CAN identifier?

29 bits.

Q5. What is the maximum Classical CAN data length?

8 bytes.

Q6. What is the purpose of DLC?

DLC indicates the number of data bytes in a Classical CAN data frame.

Q7. What is the purpose of CRC?

CRC helps detect errors in the transmitted frame.

Q8. What is the purpose of the ACK field?

It allows a receiver to acknowledge successful reception at the CAN protocol level.

Q9. What is bit stuffing?

It is the insertion of an opposite-polarity bit after five consecutive bits of the same polarity in the applicable frame region.

Q10. What is the difference between standard and extended CAN?

Standard CAN uses an 11-bit identifier, while extended CAN uses a 29-bit identifier.

Q11. What is an error frame?

It is a frame used by a CAN node to signal detection of a protocol error.

Q12. Does CAN FD support remote frames?

No. Remote frames are not supported in CAN FD.

28. Lesson Summary

  • CAN uses a shared two-wire differential bus.
  • High-speed CAN normally uses linear bus topology.
  • Classical CAN has four frame types.
  • Standard identifiers contain 11 bits.
  • Extended identifiers contain 29 bits.
  • Classical CAN carries up to 8 data bytes.
  • DLC indicates the data length.
  • CRC provides error detection.
  • ACK provides protocol-level acknowledgement.
  • Bit stuffing helps maintain synchronization.
  • CAN FD supports larger data fields but is not supported by the LPC2129 CAN controller.
