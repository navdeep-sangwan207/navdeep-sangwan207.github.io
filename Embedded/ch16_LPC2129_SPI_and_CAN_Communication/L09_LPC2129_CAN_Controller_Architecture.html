Lesson 09: LPC2129 CAN Controller Architecture

Study the internal architecture of the LPC2129 CAN controllers, transmit and receive message buffers, controller registers, acceptance filtering and CAN message processing.

1. Learning Objectives

After completing this lesson, you will be able to:

  • Explain the CAN controller architecture of the LPC2129.
  • Identify the purpose of CAN1 and CAN2.
  • Understand the CAN controller block diagram.
  • Describe transmit and receive message buffers.
  • Identify important CAN controller registers.
  • Understand the Acceptance Filter (AF).
  • Explain CAN message transmission and reception.
  • Understand controller status and interrupt registers.
  • Differentiate a CAN controller from a CAN transceiver.
  • Prepare for LPC2129 CAN programming.

2. Introduction to the LPC2129 CAN Controller

The LPC2129 microcontroller includes two on-chip CAN controller interfaces. They allow the microcontroller to communicate with other CAN-enabled devices using the Controller Area Network protocol.

Two CAN Interfaces

InterfacePurpose
CAN1First independent CAN controller interface
CAN2Second independent CAN controller interface

Each controller has its own control, status, timing and message-buffer registers. The controllers can be configured and operated independently.

Important: Two CAN controllers allow the LPC2129 to participate in two CAN networks or connect to separate CAN segments, subject to correct pin configuration and external transceiver hardware.

4. Main Functional Blocks

4.1 Control and Status Logic

Controls the operating mode of the CAN controller and reports its current condition.

  • Normal operating mode.
  • Reset mode.
  • Transmit and receive status.
  • Error status and interrupt conditions.

4.2 Bit Timing Logic

Controls the timing of CAN communication.

  • Configures the nominal bit rate.
  • Controls synchronization and sample timing.
  • Defines timing segments and synchronization jump width.
  • Supports reliable communication between compatible CAN nodes.

4.3 Transmit Message Buffers

Store messages waiting to be transmitted onto the CAN bus.

4.4 Receive Message Buffers

Store messages received from the CAN bus so that the processor can retrieve them.

4.5 Protocol and Error Handling

Handles CAN frame processing, bit monitoring, error detection, acknowledgements and retransmission behavior according to the CAN protocol.

4.6 Acceptance Filter

Checks incoming message identifiers against configured acceptance rules and determines which messages should be accepted for controller processing.

5. CAN1 and CAN2 Controller Interfaces

The LPC2129 provides two CAN controller register sets.

ControllerIndependent CAN controllerIndependent CAN controller

The shared acceptance filter resources are configured to recognize messages for the available CAN controller interfaces.

Do not assume that CAN1 and CAN2 use identical pin numbers or pin-multiplexing settings. Consult the LPC2129 pin-function table for the selected package and device revision.

6. CAN Message Buffers

Message buffers temporarily store CAN frame information during transmission and reception.

6.1 Transmit Buffers

The CAN controller provides three transmit buffers. They allow software to prepare messages for transmission.

A transmit message normally contains:

  • CAN identifier.
  • Frame format information.
  • Data length code (DLC).
  • Data bytes.
  • Transmission control information.

6.2 Receive Buffers

The controller provides receive buffering for incoming messages. Software reads the received identifier, frame information, data length and payload from the receive registers.

The transmit and receive message-buffer resources are controller-specific. The acceptance filter is a shared resource, so its configuration must account for messages needed by both CAN interfaces.

The LPC2129 CAN controllers are programmed through memory-mapped registers.

Corresponding CAN2 Registers

CAN2 has corresponding registers with the C2 prefix, such as C2MOD, C2CMR, C2GSR, C2BTR and C2RFS.

Register names and available transmit-buffer register groups should be checked against the exact LPC2129 device header and NXP user manual. Do not assume that every CAN register is interchangeable between CAN1 and CAN2.

8. CAN Mode Register (MOD)

The Mode Register controls the operating mode of the CAN controller.

For CAN1, the register is C1MOD. For CAN2, the corresponding register is C2MOD.

Common Mode Controls

BitSymbolPurpose
0RMReset Mode
1LOMListen Only Mode
2STMSelf Test Mode
3TPMTransmit Priority Mode
4SMSleep Mode
5RPMReceive Priority Mode
6TMTest Mode

Reset Mode

Reset mode is used while configuring the CAN controller. Software normally places the controller in reset mode before changing configuration registers that require it.

Listen Only Mode

Listen-only mode allows a controller to monitor CAN traffic without actively transmitting frames or sending normal acknowledgements.

Self Test Mode

Self-test mode supports controller testing without requiring the usual external acknowledgement from another node. The exact behavior depends on the selected test configuration.

9. Command Register (CMR)

The Command Register requests operations from the CAN controller.

For CAN1, it is C1CMR. For CAN2, it is C2CMR.

Common Command Bits

BitSymbolFunction
0TRTransmission request
1ATAbort transmission
2RRBRelease receive buffer
3CDOClear data overrun
4SRRSelf reception request

These command bits allow firmware to control transmission, reception and buffer management.

A command register is not an ordinary storage register. Writing a command bit requests an action from the controller. Follow the device manual for the correct command sequence.

10. Global Status Register (GSR)

The Global Status Register provides information about the CAN controller's current state.

For CAN1, it is C1GSR. For CAN2, it is C2GSR.

Information Reported

  • Receive status.
  • Data overrun status.
  • Transmit buffer status.
  • Transmit error counter.
  • Receive error counter.

Software can inspect status information to determine whether a message has been received, whether a transmit operation has completed and whether error counters have changed.

11. Bit Timing Register (BTR)

The Bit Timing Register configures the CAN controller's nominal bit timing.

For CAN1, it is C1BTR. For CAN2, it is C2BTR.

Important Fields

FieldPurpose
BRPBaud Rate Prescaler
SJWSynchronization Jump Width
TESG1Time Segment 1
TESG2Time Segment 2
SAMSampling mode selection

The bit timing configuration determines the nominal CAN bit rate and sample point. All nodes communicating on the same network must use compatible bit timing.

The detailed bit timing calculations and register programming are covered in Lesson 10.

12. Acceptance Filter Architecture

The Acceptance Filter (AF) is a hardware filtering mechanism that determines which incoming CAN messages should be accepted for processing.

Why Is an Acceptance Filter Needed?

  • A CAN bus can carry messages for many devices.
  • A controller may need only a subset of those messages.
  • Filtering reduces unnecessary processor work.
  • It helps manage receive-buffer resources.

The acceptance filter has its own control and lookup resources.

Acceptance Filter Modes

  • Normal mode: use configured acceptance filter entries.
  • Acceptance filter bypass: accept messages without normal identifier filtering.
  • FullCAN mode: supports hardware-assisted handling of selected standard CAN messages.
Acceptance filter configuration is shared by CAN1 and CAN2. Changing the filter table can affect message acceptance on both interfaces. Configure it as part of the overall network design.

14. CAN Message Transmission Process

The following sequence describes a typical software-controlled CAN transmission.

  1. Configure the CAN controller and operating mode.
  2. Configure the nominal bit timing.
  3. Prepare the transmit message identifier.
  4. Set the frame format and data length.
  5. Load the payload bytes into the transmit registers.
  6. Request transmission using the command register.
  7. The CAN controller performs arbitration and transmits the frame when it wins access to the bus.
  8. Software checks the transmission status or interrupt.

15. CAN Message Reception Process

The reception process begins when a CAN frame arrives from the bus.

  1. The CAN controller detects the incoming frame.
  2. It receives and checks the frame according to CAN protocol rules.
  3. The acceptance filter evaluates the message.
  4. An accepted message is stored in receive buffering.
  5. The controller updates receive status.
  6. Software detects the message through polling or an interrupt.
  7. Software reads the identifier, DLC and data bytes.
  8. Software releases the receive buffer when required.

16. CAN Interrupt Architecture

The CAN controller can generate interrupts for important events.

Typical Interrupt Events

  • Receive buffer available.
  • Transmit buffer completion.
  • Data overrun.
  • Error warning conditions.
  • Error passive or bus-off related status changes.

The controller's interrupt enable and interrupt capture registers help software identify and respond to these events.

The CAN interrupt is routed through the LPC2129 Vectored Interrupt Controller (VIC). The relevant interrupt source assignments should be taken from the LPC2129 VIC source table for the selected controller.

Interrupt-based CAN programming is useful when the processor must handle other tasks instead of continuously polling the CAN status registers.

The LPC2129 CAN controller cannot directly drive the differential CANH/CANL network. An appropriate external CAN transceiver and correct bus termination are required for physical CAN communication.

18. CAN Network Termination

A typical high-speed CAN bus uses termination resistors at the two physical ends of the main bus.

120 ohm                                      120 ohm
   |                                            |
CANH+------------------------------------------+CANH
   |                CAN Bus                    |
CANL+------------------------------------------+CANL

In a conventional high-speed CAN network, the two end terminations are commonly 120 Ω each. The exact physical layout and termination arrangement must follow the selected CAN physical-layer specification.

Termination helps control signal reflections. It is not a substitute for correct cable topology, transceiver selection or bit timing.

19. LPC2129 CAN Programming Preparation

Before writing a CAN application, prepare the following configuration items.

  • Select CAN1 or CAN2.
  • Check the required pin multiplexing.
  • Connect the appropriate external CAN transceiver.
  • Configure the controller operating mode.
  • Calculate and configure bit timing.
  • Configure acceptance filtering.
  • Prepare transmit and receive buffer handling.
  • Choose polling or interrupt-based operation.
  • Check error and bus-off status.
  • Verify communication with another CAN node.

Software Architecture Example

main()
{
    SystemClock_Init();

    CAN_Pin_Init();

    CAN_Controller_Init();

    CAN_BitTiming_Init();

    CAN_AcceptanceFilter_Init();

    while (1)
    {
        CAN_Process_ReceivedMessages();

        CAN_Process_TransmitRequests();

        CAN_Check_ControllerStatus();
    }
}

This is a structural example, not a complete compilable driver. The function names represent application-level modules.

21. Common Mistakes

  • Confusing a CAN controller with a CAN transceiver.
  • Assuming the LPC2129 directly drives CANH and CANL.
  • Using incorrect CAN pin multiplexing.
  • Changing bit timing while the controller is operating normally.
  • Ignoring acceptance filter configuration.
  • Reading receive data without checking receive status.
  • Failing to release a receive buffer.
  • Ignoring transmit completion and error status.
  • Assuming CAN1 and CAN2 have the same physical pin mapping.
  • Assuming successful compilation proves communication with another CAN node.

22. Interview Questions and Answers

Q1. How many CAN controllers are available in LPC2129?

Two: CAN1 and CAN2.

Q2. What is the purpose of a CAN controller?

It handles CAN frame transmission, reception, arbitration, bit timing and protocol-related error processing.

Q3. What is a transmit buffer?

A buffer that stores a CAN message waiting to be transmitted.

Q4. What is a receive buffer?

A buffer that stores an incoming CAN message for software retrieval.

Q5. What is the purpose of the C1MOD register?

It controls the operating mode of CAN1.

Q6. What is the purpose of the C1CMR register?

It requests CAN1 operations such as transmission, abort and receive-buffer release.

Q7. What is the purpose of C1BTR?

It configures CAN1 nominal bit timing.

Q8. What is an Acceptance Filter?

Hardware that selects incoming CAN messages according to configured acceptance rules.

Q9. Is the acceptance filter shared?

Yes. The LPC2129 acceptance-filter resources are shared by the CAN controller interfaces.

Q10. Why is an external CAN transceiver required?

It converts the controller's logic-level signals into differential CAN bus signals and senses the bus.

Q11. What is the purpose of the GSR register?

It reports global controller status, including transmission, reception and error information.

Q12. Can CAN1 and CAN2 communicate on separate CAN networks?

Yes, when their pin configurations, transceivers, bit timing and network connections are correctly implemented.

25. Lesson Summary

  • LPC2129 provides two CAN controller interfaces: CAN1 and CAN2.
  • Each controller has its own control, status and timing registers.
  • Transmit buffers hold messages waiting for transmission.
  • Receive buffers hold incoming messages for software processing.
  • C1MOD controls CAN1 operating mode.
  • C1CMR requests CAN1 operations.
  • C1GSR reports global status.
  • C1BTR configures bit timing.
  • The Acceptance Filter selects incoming messages.
  • Acceptance filter resources are shared.
  • An external transceiver is required for physical CAN bus communication.
  • CAN programming requires correct pin configuration, timing and buffer management.
