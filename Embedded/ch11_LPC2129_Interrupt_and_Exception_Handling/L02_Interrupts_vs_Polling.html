1. Introduction

Embedded systems continuously interact with peripherals such as timers, UARTs, switches, sensors, and communication interfaces.

The processor must detect when these peripherals generate events and perform the required operations.

Two common techniques are used to detect and respond to peripheral events: polling and interrupt-driven programming.

Learning objectives:
  • Understand polling-based programming.
  • Understand interrupt-driven programming.
  • Compare their execution mechanisms.
  • Analyze CPU utilization and response time.
  • Write basic Embedded C examples.
  • Identify suitable applications for each technique.

2. What Is Polling?

Polling is a programming technique in which the processor repeatedly checks the status of a peripheral or hardware input to determine whether an event has occurred.

The processor continues checking the peripheral until the required condition becomes true.

Example: Checking a Switch

Suppose a push button is connected to LPC2129 GPIO pin P0.6. The processor continuously reads the GPIO input register to detect whether the button is pressed.

Start Program
↓
Read GPIO Input
↓
Check Button State
↓
Button Pressed?
↓
Yes: Perform Required Operation
No: Read GPIO Input Again

Characteristics of Polling

  • The processor checks peripheral status repeatedly.
  • No interrupt request is required for event detection.
  • The program controls when status checking occurs.
  • CPU time is consumed during repeated checking.
  • Response time depends partly on the polling interval and execution flow.

3. Polling Example Using LPC2129 GPIO

Objective: Read a push button connected to P0.6 and control an LED connected to P0.5.

Pin configuration

Pin Function
P0.6 Push-button input, active-LOW example
P0.5 LED output, active-HIGH example

Program

#include <LPC21xx.h>

#define BUTTON_PIN (1U << 6)
#define LED_PIN    (1U << 5)

int main(void)
{
    // Select GPIO function for P0.5 and P0.6
    PINSEL0 &= ~((3U << 10) | (3U << 12));

    // Configure LED as output
    IODIR0 |= LED_PIN;

    // Configure button as input
    IODIR0 &= ~BUTTON_PIN;

    while (1)
    {
        // Active-LOW button pressed
        if ((IOPIN0 & BUTTON_PIN) == 0)
        {
            // LED ON
            IOSET0 = LED_PIN;
        }
        else
        {
            // LED OFF
            IOCLR0 = LED_PIN;
        }
    }
}

Program explanation

  1. PINSEL0 selects GPIO functionality for P0.5 and P0.6.
  2. IODIR0 configures P0.5 as output.
  3. P0.6 is configured as input.
  4. IOPIN0 is continuously read inside the infinite loop.
  5. If the button is pressed, the LED output is set HIGH.
  6. Otherwise, the LED output is cleared.

Expected result

The program repeatedly reads the button input. The LED output follows the button state, assuming the specified active-LOW button and active-HIGH LED circuit.

This is a polling example. It does not use an external interrupt or VIC configuration. In Keil simulation, inspect GPIO registers and program execution; external switch behavior may not be modeled.

4. Advantages and Disadvantages of Polling

Advantages

  • Simple programming structure.
  • Easy to understand and debug.
  • No interrupt controller configuration is required.
  • Suitable for simple applications with frequent status checks.
  • Useful when the processor has little other work to perform.

Disadvantages

  • CPU time is spent repeatedly checking status registers.
  • Important events may be detected only at the next polling check.
  • Frequent polling can reduce processing efficiency.
  • Long polling intervals can increase event detection delay.
  • Multiple peripherals can make polling loops complicated.

5. What Is Interrupt-Driven Programming?

Interrupt-driven programming is a technique in which a peripheral or external source generates an interrupt request when a particular event occurs.

The processor does not need to continuously check the peripheral status. Instead, it can execute other instructions until an eligible interrupt request is accepted.

Example: Timer Interrupt

  1. Configure Timer 0 and its match register.
  2. Configure the timer interrupt source.
  3. Enable the interrupt through the VIC and processor as required.
  4. The processor continues normal program execution.
  5. When the timer match event occurs, an interrupt request is generated.
  6. The processor executes the timer ISR.
  7. The ISR services and acknowledges the interrupt source.
  8. The processor returns to normal execution.

6. Interrupt-Driven Programming Example

Objective: Understand how a timer interrupt can update a software event counter.

Conceptual program

#include <LPC21xx.h>

volatile unsigned int timer_event = 0;

void Timer0_ISR(void)
{
    // Record the timer event
    timer_event++;

    // Clear Timer 0 Match 0 interrupt flag
    T0IR = (1U << 0);
}

int main(void)
{
    // Timer, VIC and processor interrupt
    // configuration must be completed here.

    while (1)
    {
        if (timer_event != 0)
        {
            timer_event = 0;

            // Process the timer event
        }
    }
}

Explanation

  1. The timer interrupt event is generated by the peripheral.
  2. The interrupt handler is executed when the request is accepted.
  3. The ISR increments timer_event.
  4. The ISR clears the timer's Match 0 flag.
  5. The main program checks the event variable.
  6. The main program processes the event outside the ISR.
This is a conceptual ISR example, not a complete LPC2129 interrupt program. A working implementation also needs the compiler-specific ISR declaration, Timer 0 configuration, VIC source configuration, vector setup, and interrupt acknowledgment. These are covered in the later lessons.

7. Advantages and Disadvantages of Interrupts

Advantages

  • Reduces unnecessary repeated status checking.
  • Allows the processor to perform other tasks.
  • Supports event-driven application design.
  • Can provide faster event detection than slow polling loops.
  • Useful for asynchronous peripheral communication.
  • Supports periodic and time-critical operations.

Disadvantages

  • Requires additional hardware and software configuration.
  • Interrupt handling adds processor overhead.
  • Long ISRs can delay other interrupt requests.
  • Shared data between ISR and main code requires careful handling.
  • Priority and interrupt nesting must be considered.
  • Debugging can be more complicated than polling.

8. Polling vs Interrupts – Comparison

Parameter Polling Interrupts
Event detection Processor repeatedly checks status. Peripheral generates an interrupt request.
CPU activity CPU performs repeated checking. CPU can execute other code between events.
Configuration Usually simpler. Requires interrupt source and controller configuration.
Response time Depends on polling frequency and program flow. Depends on interrupt latency, masking, and priority.
Software complexity Generally lower. Generally higher.
CPU overhead Repeated checking consumes processing time. Interrupt entry, servicing, and return consume processing time.
Suitable applications Simple systems and frequent status checks. Asynchronous events and responsive systems.
Example Continuously checking a GPIO input. Using an external interrupt for a switch event.

9. CPU Utilization Comparison

Polling approach

In polling, the processor repeatedly checks a peripheral even when no event has occurred. 

while (1)
{
    check_timer_status();

    check_uart_status();

    check_button_status();

    perform_other_operations();
}

Interrupt-driven approach

In interrupt-driven programming, the processor can perform useful work while waiting for a peripheral event. 

int main(void)
{
    configure_timer_interrupt();
    configure_uart_interrupt();

    while (1)
    {
        perform_main_application_tasks();
    }
}

void Timer_ISR(void)
{
    // Handle timer event
}

void UART_ISR(void)
{
    // Handle UART event
}
Interrupts can reduce unnecessary polling, but they do not eliminate CPU overhead. The processor still spends time entering, executing, and returning from ISRs.

10. Response Time and Event Detection

The response time of a polling system depends on how frequently the program checks the peripheral.

If a status check occurs every 10 ms, an event may wait nearly 10 ms for the next check, depending on when it occurs relative to the polling cycle.

In an interrupt-driven system, the peripheral can request processor service as soon as its interrupt condition occurs. Actual response still depends on interrupt latency, interrupt masking, and priority.

Parameter Polling Interrupts
Detection delay May be related to polling interval. Depends on interrupt response and masking.
CPU checking Repeated checks required. No continuous checking required for the interrupt source.
Event handling Performed in normal program flow. Begins in the interrupt handler.
Interrupt-driven programming is not automatically faster in every situation. A very frequent event or a heavily loaded interrupt system can create substantial overhead.

11. When Should Polling Be Used?

Polling is suitable when:

  • The application is simple.
  • Events are checked frequently as part of normal operation.
  • The processor has enough time to perform repeated checks.
  • Low software complexity is important.
  • Events do not require very fast response.

Examples

  • Checking a button in a simple demonstration program.
  • Reading a peripheral status register in a short operation.
  • Waiting for a conversion to complete in a simple blocking application.
  • Checking a flag during initial peripheral testing.

12. When Should Interrupts Be Used?

Interrupts are suitable when:

  • Events occur asynchronously.
  • The processor must perform other tasks between events.
  • Event detection delay must be controlled.
  • Communication peripherals generate events.
  • Periodic timer events are required.
  • The system has several independent event sources.

Examples

  • UART receive interrupt.
  • Timer periodic interrupt.
  • External sensor event detection.
  • ADC conversion-complete interrupt.
  • Communication and industrial control applications.

13. Can Polling and Interrupts Be Used Together?

Yes. Many embedded systems use both techniques depending on the requirements of individual peripherals.

For example, an LPC2129 application might use:

  • Timer interrupts for periodic scheduling.
  • UART interrupts for receiving serial data.
  • Polling to check a simple GPIO input.
  • Polling to inspect a status flag during initialization.
The correct approach depends on event frequency, response requirements, CPU workload, software complexity, and peripheral capabilities.

15. Common Mistakes

Mistake Correct understanding
Assuming polling always uses less CPU time. Repeated polling can consume significant CPU time.
Assuming interrupts have no overhead. Interrupt entry, ISR execution, and return require processor time.
Assuming interrupts always execute immediately. Masking, priority, and current processor state affect response.
Writing lengthy operations inside an ISR. Keep the ISR short and perform lengthy processing in the main program.
Using interrupts without clearing the source. Follow the peripheral's documented interrupt acknowledgment method.
Assuming polling cannot miss events. Short events can occur between polling checks and may be missed unless hardware latches them.

16. Interview Questions and Answers

Q1. What is polling?

Polling is a technique in which the processor repeatedly checks a peripheral status register to detect an event.

Q2. What is interrupt-driven programming?

It is a technique in which a peripheral or external source requests processor service when an event occurs.

Q3. What is the main difference between polling and interrupts?

Polling requires repeated processor checks, whereas interrupts allow the peripheral to request service when an eligible event occurs.

Q4. Which technique consumes more CPU time?

Frequent polling can consume substantial CPU time through repeated status checks. Interrupts also have overhead, but can avoid unnecessary repeated checking.

Q5. What is interrupt latency?

It is the time between an interrupt request becoming active and the beginning of its handler execution.

Q6. Can polling be used in real-time systems?

Yes. Polling can be appropriate when its timing and execution requirements are predictable and meet the system's deadlines.

Q7. Why are interrupts useful in UART communication?

UART interrupts can notify the processor when data is received or transmission service is required, avoiding continuous status checking.

Q8. Can polling and interrupts be used together?

Yes. A system can use interrupts for important asynchronous events and polling for simpler peripheral checks.

Q9. What happens if a polling interval is too long?

Event detection may be delayed, and short events may be missed if the hardware does not latch them.

Q10. Does an interrupt always have higher priority than the main program?

An accepted interrupt causes exception handling, but interrupt masking and priority rules determine which requests can be serviced and when.

20. Lesson Summary

  • Polling repeatedly checks a peripheral status.
  • Interrupts allow peripherals to request processor service.
  • Polling is generally simpler to implement.
  • Frequent polling can waste CPU time.
  • Interrupts support event-driven program execution.
  • Interrupts introduce context-switching and servicing overhead.
  • Polling response depends on checking frequency and program flow.
  • Interrupt response depends on latency, masking, and priority.
  • Both techniques can be used in the same embedded system.
  • The correct method depends on application requirements.
