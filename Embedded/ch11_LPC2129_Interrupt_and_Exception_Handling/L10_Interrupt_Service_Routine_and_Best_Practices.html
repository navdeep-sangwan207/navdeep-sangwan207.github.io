1. Introduction

An Interrupt Service Routine (ISR) is a special function that executes when the processor accepts an interrupt request. It temporarily interrupts normal program execution to respond to an event.

In embedded systems, ISRs are commonly used to respond to timer events, UART communication, external signals, and other peripheral events.

An ISR must be designed carefully. Poor interrupt handling can cause missed events, incorrect data, excessive latency, unpredictable execution, and system instability.

Learning objectives

  • Understand interrupt entry and return.
  • Learn peripheral interrupt acknowledgement.
  • Understand VIC interrupt completion.
  • Learn how to share data between an ISR and main program.
  • Understand volatile and atomic access.
  • Learn interrupt latency and response time.
  • Understand nested interrupts and interrupt priority.
  • Apply reliable ISR programming practices.
  • Debug interrupt-related problems in Keil uVision.

2. What Is an Interrupt Service Routine?

An ISR is a function associated with an interrupt source. When an enabled and unmasked interrupt is accepted, the processor transfers execution to the appropriate interrupt handler.

Example

Suppose Timer 0 generates an interrupt after a configured match event. The processor executes the Timer 0 ISR, acknowledges the timer event, updates application data, and returns to the interrupted program.

Main Program Running
↓
Peripheral Generates Interrupt Request
↓
VIC Selects and Routes Interrupt
↓
ARM7 Enters IRQ or FIQ Exception Mode
↓
Interrupt Service Routine Executes
↓
Peripheral and VIC Handling Completed
↓
Processor Returns to Interrupted Program

3. Main Responsibilities of an ISR

An ISR should perform only the operations required to service the interrupt safely.

  1. Identify the interrupt source.
  2. Read the relevant peripheral status.
  3. Acknowledge or clear the peripheral interrupt condition.
  4. Capture essential data if required.
  5. Update a small shared variable or set an event flag.
  6. Complete VIC handling when using a vectored IRQ.
  7. Return using the correct compiler-generated interrupt convention.
A peripheral interrupt flag and the VIC interrupt controller are separate parts of the interrupt path. Completing VIC handling does not automatically clear every peripheral's interrupt flag.

4. ISR Structure in Embedded C

The syntax used to declare an ISR depends on the compiler and target architecture. In Keil ARM Compiler projects for LPC2129, the __irq keyword is commonly used for an IRQ handler.

Basic Keil-style example

#include <LPC21xx.h>

volatile unsigned int event_count = 0;

__irq void Timer0_ISR(void)
{
    /* Interrupt service operations */

    event_count++;

    /* Peripheral acknowledgement and
       VIC completion are required here. */
}

The example shows the function declaration and a simple shared variable update. A complete handler must also acknowledge the actual peripheral interrupt condition and complete the VIC protocol when handling a vectored IRQ.

The compiler's interrupt declaration and return sequence are important. Do not assume an ordinary C function can safely be used as an IRQ handler.

5. Peripheral Acknowledgement

Many peripherals maintain their own interrupt status flags. The ISR must acknowledge the event according to the peripheral's register semantics.

Timer 0 example

Timer 0 uses T0IR to report match and capture interrupt flags. 

/* Clear Timer 0 Match 0 interrupt flag */
T0IR = (1U << 0);

The LPC2129 timer interrupt flags use write-one-to-clear behavior. Writing 1 to the relevant flag clears it.

UART example

UART interrupt handling is different. The handler must examine the UART interrupt identification and status information and service the relevant receive, transmit, or line-status condition according to the UART register requirements.

Never assume all peripherals clear interrupt flags in the same way. Consult the LPC2129 user manual for the acknowledgement procedure of each peripheral.

6. VIC Interrupt Completion

The LPC2129 Vectored Interrupt Controller supports vectored IRQ handling. When a vectored IRQ is serviced, the VIC uses its vector address mechanism to identify the selected handler.

After the handler has serviced the interrupt, the software completes vectored IRQ handling by writing to VICVectAddr. 

VICVectAddr = 0;

Two separate operations

Operation Purpose
Peripheral acknowledgement Clears or services the interrupt condition inside the peripheral.
VIC completion Signals completion of the vectored IRQ service to the VIC.
For a Timer 0 vectored IRQ, a typical handler acknowledges the T0IR flag and then writes zero to VICVectAddr. Both operations are important.

7. Complete Timer 0 ISR Example

The following example uses the project clock configuration:

  • CCLK = 60 MHz
  • PCLK = 15 MHz
  • PR = 14999
  • TC increment interval = 1 ms
  • MR0 = 1000
  • Timer 0 VIC source = 4
#include <LPC21xx.h>

#define TIMER0_SOURCE 4U

volatile unsigned int timer0_events = 0;

__irq void Timer0_ISR(void)
{
    /* Acknowledge Timer 0 Match 0 */
    T0IR = (1U << 0);

    /* Record the interrupt event */
    timer0_events++;

    /* Complete vectored IRQ handling */
    VICVectAddr = 0;
}

void Timer0_Init(void)
{
    /* Stop and reset Timer 0 */
    T0TCR = 0x02;

    /* Configure 1 ms timer counter increments */
    T0PR = 14999;
    T0PC = 0;
    T0TC = 0;

    /* Configure match value */
    T0MR0 = 1000;

    /* Interrupt and reset on MR0 match */
    T0MCR = 0x03;

    /* Clear any previous MR0 flag */
    T0IR = (1U << 0);

    /* Configure Timer 0 as IRQ */
    VICIntSelect &= ~(1U << TIMER0_SOURCE);

    /* Assign Timer 0 to vectored slot 0 */
    VICVectCntl0 =
        (1U << 5) | TIMER0_SOURCE;

    /* Install ISR address */
    VICVectAddr0 = (unsigned int)Timer0_ISR;

    /* Enable Timer 0 interrupt */
    VICIntEnable = (1U << TIMER0_SOURCE);

    /* Start Timer 0 */
    T0TCR = 0x01;
}

int main(void)
{
    Timer0_Init();

    while (1)
    {
        /* Main application */
    }
}

Expected logical behavior

  1. Timer 0 starts counting.
  2. The timer counter increments every nominal 1 ms.
  3. When TC reaches 1000, MR0 matches.
  4. The match interrupt flag is set.
  5. The timer counter resets because reset-on-match is enabled.
  6. The processor executes Timer0_ISR if the interrupt is accepted.
  7. The ISR clears T0IR bit 0.
  8. The ISR increments timer0_events.
  9. The ISR completes VIC handling.

8. What Is Interrupt Latency?

Interrupt latency is the time between the occurrence of an interrupt request and the start of execution of its interrupt service routine.

Interrupt latency can be affected by:

  • Current processor instruction execution.
  • IRQ or FIQ masking.
  • Higher-priority interrupt activity.
  • Interrupt controller selection and routing.
  • Exception entry and vector handling.
  • Memory access and instruction execution conditions.

Interrupt response sequence

Interrupt Event Occurs
↓
Interrupt Request Becomes Pending
↓
Processor Accepts Interrupt
↓
Exception Entry and Handler Dispatch
↓
ISR Begins Execution

The interval between the first and last steps represents the interrupt response delay.

In real-time embedded systems, interrupt latency must be considered when determining whether the system can respond to an event before its deadline.

9. What Is ISR Execution Time?

ISR execution time is the time required for the processor to execute the interrupt service routine.

Interrupt latency and ISR execution time are different measurements.

Term Meaning
Interrupt latency Time from interrupt request to ISR start.
ISR execution time Time spent executing the ISR.
Interrupt response time Time until the required interrupt response or action is completed.

A long ISR can delay the main program and other interrupt service routines. Therefore, interrupt handlers should be short and predictable.

10. Shared Data Between ISR and Main Program

An ISR and the main program may access the same variable. Such a variable is called shared data.

Example

volatile unsigned int event_count = 0;

__irq void Timer0_ISR(void)
{
    event_count++;

    T0IR = (1U << 0);

    VICVectAddr = 0;
}

int main(void)
{
    unsigned int previous_count = 0;

    while (1)
    {
        if (event_count != previous_count)
        {
            previous_count = event_count;

            /* Process the new event */
        }
    }
}

The ISR updates event_count. The main program checks whether the value has changed and processes the event.

The shared variable is declared volatile because it can change asynchronously from the main program's point of view.

11. Volatile Keyword in Interrupt Programming

The volatile keyword tells the compiler that a variable may change outside the normal execution flow being analyzed. This is important for data shared with an ISR and for memory-mapped peripheral registers.

Without volatile

unsigned int event_flag = 0;

With volatile

volatile unsigned int event_flag = 0;

If the ISR changes event_flag, the main program must be able to observe that change. Declaring the shared variable volatile helps prevent the compiler from incorrectly assuming that its value cannot change unexpectedly.

volatile does not make an operation atomic. It does not automatically protect shared data from race conditions or guarantee safe access to multi-step operations.

12. Atomic Access and Race Conditions

An atomic operation is an operation that cannot be observed in a partially completed state by another execution context.

A race condition occurs when the correctness of a program depends on the timing or ordering of concurrent operations.

Example of a possible race condition

volatile unsigned int event_count = 0;

/* ISR */
event_count++;

/* Main program */
event_count = event_count + 1;

Both the ISR and main program modify the same variable. An increment normally involves reading, modifying and writing the value. If the two operations overlap, an update can be lost.

Safer design approaches

  • Use simple shared flags where possible.
  • Use naturally atomic accesses supported by the processor and compiler.
  • Protect multi-step operations with a short critical section.
  • Use compiler-supported atomic operations when available.
  • Avoid unnecessary shared writable variables.
The exact atomicity of a C access depends on the processor, data width, alignment and compiler. Do not assume every 32-bit C operation is automatically safe in every context.

13. Critical Sections

A critical section is a part of a program that must execute without interruption by selected interrupt sources.

On ARM7, interrupt masking can be used to protect a short operation from IRQ interference. Compiler-specific intrinsics or carefully written assembly are preferred for changing processor status masks.

Conceptual sequence

1. Save the current interrupt mask state.

2. Disable the relevant interrupt class.

3. Access or update shared data.

4. Restore the previous interrupt mask state.
Do not blindly enable interrupts at the end of a critical section. Restore the previous mask state so that an interrupt that was already disabled remains disabled.

Critical sections should be as short as possible because masking interrupts increases response latency.

14. Nested Interrupts

Nested interrupts occur when one interrupt handler is interrupted by another interrupt handler.

Nested interrupt handling can improve response to urgent events, but it introduces additional complexity.

Conceptual example

Main Program
↓
IRQ Handler Starts
↓
Higher-Priority Interrupt Accepted
↓
Higher-Priority Handler Executes
↓
Return to Previous IRQ Handler
↓
Return to Main Program

Important considerations

  • Preserve processor state correctly.
  • Manage stack usage carefully.
  • Protect shared data.
  • Understand interrupt masking and priority.
  • Avoid uncontrolled recursive interrupt behavior.
  • Keep the total worst-case execution time within system limits.
ARM7 IRQ handling does not automatically provide unrestricted nesting. A handler must deliberately manage interrupt masks and context if nested IRQ behavior is required. This should be implemented only with a verified compiler and processor-specific design.

15. IRQ and FIQ Handling Considerations

ARM7 supports two interrupt exception classes: IRQ and FIQ.

Feature IRQ FIQ
Meaning Normal interrupt request Fast interrupt request
Processor mode IRQ mode FIQ mode
Banked registers Banked SP and LR Banked R8–R14
Typical use General peripheral events Time-critical interrupt handling
Mask bit CPSR I bit CPSR F bit

The VIC can route selected interrupt sources to IRQ or FIQ using VICIntSelect. FIQ is a separate processor exception path and is not simply another vectored IRQ slot.

16. Best Practices for ISR Programming

Keep the ISR short

Perform only the essential interrupt service operations inside the handler.

Acknowledge the interrupt correctly

Clear or service the peripheral interrupt condition using the documented register procedure.

Use event flags

Set a flag or increment a counter in the ISR and let the main program perform longer processing.

Avoid blocking operations

Avoid delay loops, blocking communication calls, and waiting for external events inside an ISR.

Protect shared data

Use appropriate synchronization for variables accessed by both the ISR and the main program.

Understand the interrupt controller

Configure the VIC source, vector slot, handler address and interrupt enable correctly.

Measure timing

Analyze worst-case interrupt latency and execution time for real-time applications.

17. Operations to Avoid Inside an ISR

Avoid Reason Better approach
Long delay loops Increase interrupt execution time. Use a timer or schedule work in the main program.
Blocking UART transmission Can keep the processor inside the ISR for too long. Store data in a buffer and transmit later.
Complex calculations Increase execution time and response delay. Defer processing to the main loop.
Dynamic memory allocation May have unpredictable execution time and failure modes. Use preallocated buffers.
Unbounded loops May prevent the ISR from returning. Use bounded, predictable operations.
Unsafe shared-data updates Can cause race conditions. Use suitable synchronization.

18. Interrupt Debugging in Keil uVision

Interrupt debugging involves checking the peripheral, VIC configuration, processor interrupt state and ISR execution.

Debugging procedure

  1. Build the LPC2129 project successfully.
  2. Enter Debug mode in Keil uVision.
  3. Set a breakpoint at the beginning of the ISR.
  4. Inspect the timer or peripheral control registers.
  5. Check the peripheral interrupt flag.
  6. Inspect VICIntSelect and VICIntEnable.
  7. Check the configured vector control register.
  8. Check the handler address and compiler interrupt declaration.
  9. Inspect CPSR interrupt mask bits where supported.
  10. Run the program and determine whether the ISR is reached.
  11. Inspect shared variables after interrupt service.

Important registers for Timer 0

Register What to inspect
T0TCRTimer enable and reset state
T0TCCurrent timer counter value
T0PRPrescaler configuration
T0MR0Match value
T0MCRMatch interrupt and reset actions
T0IRTimer interrupt flags
VICIntEnableEnabled interrupt sources
VICVectCntl0Vectored slot configuration
VICVectAddr0Installed handler address
VICVectAddrVIC vectored IRQ completion
The Keil simulator may not reproduce every LPC2129 peripheral event or interrupt behavior. If a breakpoint is not reached, check simulator support, project startup code and interrupt configuration. Register inspection is not proof of physical hardware operation.

19. Common Interrupt Programming Problems

Problem Possible cause What to check
ISR never executes Interrupt source is not enabled. Peripheral enable, VICIntEnable and CPSR masks.
ISR executes only once Peripheral flag is not cleared. Peripheral acknowledgement procedure.
Repeated interrupt entry Interrupt condition remains pending. Peripheral status and flag handling.
Incorrect vector execution Wrong slot or handler address. VICVectCntl and VICVectAddr registers.
Shared counter is incorrect Race condition or non-atomic access. Data width and synchronization.

20. Practical Exercise: Timer Interrupt Event Counter

Objective

Configure Timer 0 to generate periodic match interrupts and increment a software event counter inside the ISR.

Program

#include <LPC21xx.h>

#define TIMER0_SOURCE 4U

volatile unsigned int interrupt_count = 0;

__irq void Timer0_ISR(void)
{
    /* Clear MR0 interrupt flag */
    T0IR = (1U << 0);

    /* Update event counter */
    interrupt_count++;

    /* Complete VIC handling */
    VICVectAddr = 0;
}

void Timer0_Setup(void)
{
    T0TCR = 0x02;

    T0PR = 14999;
    T0PC = 0;
    T0TC = 0;

    T0MR0 = 1000;
    T0MCR = 0x03;

    T0IR = (1U << 0);

    VICIntSelect &= ~(1U << TIMER0_SOURCE);

    VICVectCntl0 =
        (1U << 5) | TIMER0_SOURCE;

    VICVectAddr0 = (unsigned int)Timer0_ISR;

    VICIntEnable = (1U << TIMER0_SOURCE);

    T0TCR = 0x01;
}

int main(void)
{
    Timer0_Setup();

    while (1)
    {
        /* Inspect interrupt_count in debugger */
    }
}

Expected logical result

If the timer and VIC interrupt path operate correctly, interrupt_count increases by one for each serviced Timer 0 match interrupt.

Keil simulator procedure

  1. Build the program.
  2. Enter Debug mode.
  3. Set a breakpoint inside Timer0_ISR.
  4. Run the simulation.
  5. Inspect interrupt_count.
  6. Inspect T0IR and VIC registers.
  7. Verify whether the ISR is repeatedly entered.
Expected result: The event counter should increase when Timer 0 match interrupts are successfully generated and serviced. Actual simulator behavior depends on the peripheral model.

21. Interview Questions and Answers

Q1. What is an ISR?

An ISR is a function executed in response to an accepted interrupt.

Q2. Why should an ISR be short?

To reduce interrupt execution time, avoid blocking other work and improve system response.

Q3. What is interrupt latency?

It is the time between an interrupt request and the start of its ISR.

Q4. What is the difference between latency and execution time?

Latency is the delay before the ISR starts. Execution time is the time required to execute the ISR.

Q5. Why is volatile used in an ISR?

It tells the compiler that a variable can change unexpectedly, such as through an ISR or hardware.

Q6. Does volatile guarantee atomic access?

No. volatile does not guarantee atomicity or protect against race conditions.

Q7. What is a critical section?

It is a section of code protected against selected interruptions while a sensitive operation is performed.

Q8. What is a nested interrupt?

It occurs when an interrupt handler is interrupted by another accepted interrupt.

Q9. What is the purpose of VICVectAddr?

It is used by the VIC's vectored IRQ mechanism, including signaling completion of a vectored IRQ.

Q10. Why must the peripheral interrupt flag be cleared?

Otherwise, the interrupt condition may remain pending and cause repeated interrupt requests.

Q11. What is the difference between IRQ and FIQ?

IRQ is the normal interrupt exception. FIQ is a separate fast interrupt exception with additional banked registers.

Q12. Why should blocking functions be avoided inside an ISR?

They can keep the processor inside the handler for too long and delay other operations.

Q13. What is a race condition?

It is a condition where the result depends on the timing or ordering of concurrent accesses.

Q14. What is interrupt masking?

It is the process of preventing selected interrupt classes from being accepted by the processor.
