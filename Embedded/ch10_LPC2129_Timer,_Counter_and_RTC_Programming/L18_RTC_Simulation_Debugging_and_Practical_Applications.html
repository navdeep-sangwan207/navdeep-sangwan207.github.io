2. RTC System Review

The Real-Time Clock is a hardware peripheral that maintains time and calendar information. It is commonly used when an embedded system needs to associate events with a date and time.

The LPC2129 RTC section covered the following operations:

Operation Purpose
RTC architecture Understand the RTC clock source and internal counters.
RTC register configuration Configure the peripheral and its counter registers.
Prescaler and clock tick Understand the clock tick generation mechanism.
Time and calendar initialization Load the initial date and time.
Reading and updating counters Read or modify date and time information.
Alarm and interrupts Generate an interrupt when the programmed alarm matches.
UART display Transmit RTC information to a serial terminal.
Simulation and debugging Validate configuration, operation and application behavior.

The debugger can be used to inspect RTC registers while the application is running or halted.

Debugging principle: Inspect the actual peripheral register values instead of assuming that a successful compilation means the RTC is operating correctly.

5. RTC Initialization Verification

Before debugging RTC applications, verify that the initialization sequence has been executed correctly.

5.1 Initialization Checklist

  • Confirm that the RTC peripheral is accessible.
  • Check the RTC clock source configuration.
  • Check that the RTC clock is enabled.
  • Verify that the counter reset bit is not unintentionally left asserted.
  • Confirm that the prescaler configuration is appropriate.
  • Initialize the time and calendar counters with valid values.
  • Check that the date and time values are within their valid ranges.
  • Confirm that the RTC is not being repeatedly reset by application code.

5.2 Valid Time and Calendar Values

The day-of-month value must also be valid for the selected month and year. February has a different maximum day count depending on whether the year is a leap year.

6. RTC Counter Debugging

6.1 Verify Seconds Counter

Set a breakpoint after the RTC initialization routine. Inspect the SEC register and record its initial value. Continue execution and inspect it again.

If the RTC is operating, the seconds counter should progress from 0 to 59 and then roll over.

6.2 Verify Minute Rollover

Observe the seconds and minutes counters near the end of a minute. 

Before rollover:
SEC = 59
MIN = 25

After rollover:
SEC = 0
MIN = 26

6.3 Verify Hour Rollover

Before rollover:
HOUR = 10
MIN  = 59
SEC  = 59

After rollover:
HOUR = 11
MIN  = 0
SEC  = 0

6.4 Verify Calendar Rollover

Check the transition between the final day of a month and the first day of the next month. Also verify the transition from December to January.

Calendar rollover testing should include February, leap-year handling and months with 30 or 31 days. Do not assume that checking only the seconds counter proves the calendar logic is correct.

7. RTC Alarm Debugging

The RTC alarm mechanism compares selected current counter values against the programmed alarm registers.

7.1 Registers to Inspect

Register Purpose
ALSECAlarm seconds
ALMINAlarm minutes
ALHOURAlarm hours
ALDOMAlarm day of month
ALDOWAlarm day of week
ALDOYAlarm day of year
ALMONAlarm month
ALYEARAlarm year
AMRAlarm comparison mask
ILRRTC interrupt flags

7.2 Alarm Debugging Checklist

  1. Confirm that the RTC clock is enabled.
  2. Inspect the programmed alarm values.
  3. Verify the AMR mask configuration.
  4. Check that the intended fields are enabled for comparison.
  5. Inspect the RTC alarm flag in ILR.
  6. Verify the RTC interrupt configuration.
  7. Check the VIC interrupt enable and vector configuration.
  8. Verify that the interrupt service routine clears the alarm flag correctly.
  9. Check that the VIC interrupt is acknowledged.

7.3 Interrupt Flag Handling

The RTC Interrupt Location Register contains separate status flags for counter increment and alarm events. Its interrupt flags use write-one-to-clear behavior. 

ILR bit 0: RTCCIF
ILR bit 1: RTCALF

Clear counter increment flag:
ILR = 0x01;

Clear alarm flag:
ILR = 0x02;

Clear both flags:
ILR = 0x03;
Do not clear an RTC interrupt flag by writing zero to it. Write the corresponding one to clear the intended flag. Also verify that the interrupt source has been acknowledged correctly at the VIC.

8. UART-Based RTC Debugging

UART output is useful for debugging RTC applications because it allows the program to transmit internal values in a readable format.

8.2 Debugging Sequence

  1. Inspect PINSEL0 and confirm UART0 pin selection.
  2. Inspect U0LCR and verify the line configuration.
  3. Check U0DLL and U0DLM for the baud-rate divisor.
  4. Inspect U0FDR for fractional divider configuration.
  5. Check U0LSR bit 5 before transmitting a character.
  6. Inspect the UART output window if supported by the simulator.
  7. Compare transmitted values with the RTC counter values.

9. Common RTC Errors and Solutions

Error Possible reason Debugging solution
RTC does not start Clock enable or clock source configuration is incorrect. Inspect CCR and the clock configuration.
Time resets repeatedly Counter reset is repeatedly asserted. Check the RTC initialization sequence.
Seconds do not increment RTC clock is not progressing or simulator support is limited. Inspect CCR and verify simulator peripheral support.
Incorrect date Invalid calendar initialization. Validate DOM, MONTH and YEAR values.
Alarm does not occur Incorrect alarm values or AMR mask. Inspect alarm registers and AMR.
ISR is not executed VIC or CPU interrupt configuration is incorrect. Inspect VIC enable, vector and global interrupt settings.
Repeated alarm behavior Alarm flag or comparison transition is misunderstood. Check the matching condition and flag-clearing sequence.
Wrong weekday DOW convention differs from software mapping. Verify weekday initialization and display mapping.
UART garbage output Incorrect baud-rate configuration. Recalculate divisor using PCLK.
UART output stops Transmit routine is waiting for THRE or the peripheral is not operating. Inspect U0LSR and UART configuration.

14. Simulator-Only Testing Strategy

This course uses Keil µVision simulation rather than a physical LPC2129 development board. Therefore, testing must distinguish software correctness from peripheral-model limitations.

14.1 What Can Be Tested Through Software Debugging?

  • RTC initialization sequence and register writes.
  • Program logic for reading and formatting counter values.
  • Range validation and calendar calculations.
  • Alarm configuration values.
  • Interrupt service routine logic when the interrupt model supports it.
  • UART configuration and transmit routine logic.
  • Application state transitions and event-handling logic.

14.2 What Requires Peripheral Simulation Support?

  • Actual RTC clock progression.
  • Automatic seconds and calendar rollover.
  • RTC alarm match generation.
  • RTC interrupt delivery to the VIC.
  • UART transmission through a simulated serial interface.

14.3 When the RTC Does Not Advance

If the simulator does not advance RTC counters, use controlled software test values to validate the application logic.

For example, test the date-formatting function with known values such as 23 November 2026. This verifies the software conversion logic, but it does not prove that the RTC hardware clock is operating.

Do not manually change read-only RTC consolidated registers or treat debugger-edited values as proof of hardware counter progression. Use the documented register behavior and distinguish simulated test data from actual peripheral operation.

17. Placement Interview Questions and Answers

Q1. What is the purpose of an RTC in an embedded system?

An RTC maintains date and time information independently of normal CPU instruction execution. It is useful for scheduling, timestamping and event logging.

Q2. What is the difference between a timer and an RTC?

A timer generally measures intervals or generates periodic events using a configured clock. An RTC maintains calendar time such as seconds, minutes, hours, day, month and year.

Q3. Why is a 32.768 kHz clock commonly used for RTCs?

It is a power-of-two frequency. Dividing 32768 by 32768 produces one tick per second, making it useful for low-power timekeeping circuits.

Q4. What is the function of the RTC CCR register?

CCR controls RTC clock operation, including clock enable and counter reset behavior.

Q5. What is the purpose of the RTC AMR register?

AMR selects which alarm fields participate in the comparison. Masked fields are ignored during matching.

Q6. What is the function of ILR?

ILR contains RTC interrupt status flags, including counter increment and alarm interrupt flags.

Q7. Why should an ISR be kept short?

A short ISR reduces interrupt latency and prevents lengthy processing from delaying other time-critical activities. It is generally preferable to set a flag and process the event outside the ISR.

Q8. What is a VIC?

The Vectored Interrupt Controller manages interrupt sources and provides interrupt handling and vector selection for the ARM7-based LPC2129.

Q9. How can RTC operation be verified in a debugger?

Inspect the RTC control and counter registers, execute the application and check whether the counter values progress as expected.

Q10. Why might an RTC program work on hardware but not in a simulator?

The simulator may not implement the complete RTC clock source, counter progression, alarm or interrupt behavior. The hardware peripheral may operate correctly even when the simulator model is incomplete.

Q11. Why is RTC useful in a data logger?

It provides timestamps that associate each sensor measurement with the date and time at which it was acquired.

Q12. How would you debug an RTC alarm that does not trigger?

Verify the RTC clock, alarm register values, AMR mask, alarm flag, interrupt configuration, VIC enable state, vector setup and ISR flag-clearing sequence.

Q13. What is the purpose of UART in RTC debugging?

UART allows the application to transmit internal RTC values and diagnostic messages to a serial terminal.

Q14. What is timestamping?

Timestamping is the process of associating an event or measurement with a date and time.

Q15. Give examples of RTC-based embedded applications.

Digital clocks, data loggers, access control systems, scheduled controllers, industrial monitoring systems and fault-recording systems.
