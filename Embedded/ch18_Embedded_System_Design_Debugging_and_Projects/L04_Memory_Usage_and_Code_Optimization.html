Lesson 04: Memory Usage and Code Optimization

Chapter 18: Embedded System Design, Debugging and Projects

Level: Advanced

Understand embedded memory organization, Flash and SRAM usage, stack and heap allocation, memory maps, code-size optimization and execution-time optimization.

1. Introduction to Memory Management

Memory management is the process of organizing and controlling how program instructions, variables, temporary data and application information use available memory.

Embedded systems often have limited memory resources. A microcontroller may have a fixed amount of on-chip Flash and SRAM, so firmware must use these resources efficiently.

Memory optimization helps to:

  • Reduce firmware size.
  • Reduce RAM consumption.
  • Prevent stack overflow.
  • Avoid memory corruption.
  • Improve execution efficiency.
  • Meet real-time performance requirements.
  • Reduce unnecessary memory copying.
Example: An embedded temperature monitoring system may store program instructions in Flash, sensor variables in SRAM, temporary function data on the stack and communication buffers in reserved RAM.

2. Types of Memory in Embedded Systems

2.1 ROM (Read-Only Memory)

ROM is non-volatile memory used to store information that must remain available when power is removed.

Traditional ROM contents are programmed during manufacturing or through a specialized programming process.

2.2 Flash Memory

Flash is non-volatile memory that can be electrically erased and reprogrammed. It commonly stores embedded firmware.

  • Retains data without power.
  • Stores program instructions.
  • Can store constant lookup tables.
  • Supports firmware updates, subject to device capabilities.

2.3 SRAM

Static Random Access Memory is volatile memory used for variables, buffers, stack and other runtime data.

  • Fast read and write access.
  • Does not require refresh cycles like DRAM.
  • Loses its contents when power is removed.
  • Usually more limited than external storage.

2.4 EEPROM

Electrically Erasable Programmable Read-Only Memory is non-volatile memory commonly used for small amounts of persistent data.

Examples include configuration settings, calibration values and device parameters.

2.5 DRAM

Dynamic RAM stores information using capacitive memory cells and requires periodic refreshing. It is used in systems that need larger amounts of working memory.

Memory Volatile? Typical Embedded Use
ROM No Permanent program storage
Flash No Firmware and constants
SRAM Yes Variables, stack and buffers
EEPROM No Configuration and calibration data
DRAM Yes Large runtime memory requirements

3. LPC2129 Memory Organization

The LPC2129 is an ARM7TDMI-S-based microcontroller with on-chip Flash and SRAM.

Its memory organization provides addressable regions for program storage, data storage and peripheral registers.

Memory Resource LPC2129 Capacity Typical Purpose
On-chip Flash 256 KB Firmware and program constants
On-chip SRAM 16 KB Runtime variables, stack and buffers
These are the LPC2129 device specifications. Always check the exact microcontroller part number and its datasheet before using memory-size assumptions in a project.

Memory-Mapped Peripherals

The LPC2129 uses memory-mapped I/O. Peripheral registers are assigned addresses within the processor's address space. Firmware accesses them through register definitions. 

#include <LPC21xx.h>

int main(void)
{
    /* Configure P0.5 as GPIO output */
    PINSEL0 &= ~(3U << 10);
    IODIR0 |= (1U << 5);

    /* Set the output latch */
    IOSET0 = (1U << 5);

    while (1)
    {
    }
}

The GPIO registers are not ordinary application variables. They represent hardware control and status registers.

4. Embedded Program Memory Layout

A compiled embedded application is commonly divided into sections according to the type of information stored.

Section Contents Typical Location
.text Executable instructions Flash
.rodata Read-only constants Flash, when configured by the toolchain
.data Initialized writable global/static variables SRAM at runtime
.bss Zero-initialized or uninitialized global/static variables SRAM
Heap Dynamically allocated memory Reserved RAM region, if used
Stack Function calls and automatic local data Reserved RAM region

Conceptual Memory Layout

             EMBEDDED MEMORY
          +----------------------+
          |       FLASH          |
          |----------------------|
          | Vector Table         |
          | Program Instructions |
          | Read-only Constants  |
          | Initialized Data     |
          +----------------------+

          +----------------------+
          |        SRAM          |
          |----------------------|
          | .data                |
          | .bss                 |
          | Heap (if used)       |
          | Free / Reserved RAM  |
          | Stack                |
          +----------------------+
This is a conceptual layout, not an exact LPC2129 linker memory map. Actual section placement, vector placement, stack locations and reserved regions depend on the startup code, linker configuration and selected toolchain.

5. Global, Local and Static Variables

5.1 Global Variables

A global variable is declared outside functions and can be accessed by functions within its scope. 

#include <stdint.h>

uint32_t system_status = 0U;

void Update_Status(void)
{
    system_status = 1U;
}

int main(void)
{
    Update_Status();

    while (1)
    {
    }
}

Global variables with initial values generally occupy the initialized data section at runtime. Their initial values are represented in the program image.

5.2 Local Variables

Local variables are declared inside functions or blocks. Automatic local variables commonly use stack storage, although compilers may keep some values in registers or optimize them away. 

void Calculate(void)
{
    unsigned int result = 100U;

    result = result + 25U;
}

5.3 Static Variables

A static variable retains its value throughout program execution. A local static variable has block scope but static storage duration. 

void Count_Events(void)
{
    static unsigned int count = 0U;

    count++;
}

Static and global variables are normally stored in .data or .bss depending on initialization.

6. Stack Memory

The stack is a memory region used to support function calls, local automatic variables, saved registers and return information.

Typical Stack Operations

  1. A function is called.
  2. Required return information and registers are saved.
  3. Local storage may be allocated.
  4. The function executes.
  5. Local storage is released when the function returns.

Example

unsigned int Add(unsigned int a, unsigned int b)
{
    unsigned int result;

    result = a + b;

    return result;
}

int main(void)
{
    unsigned int answer;

    answer = Add(10U, 20U);

    while (1)
    {
    }
}

Stack Overflow

Stack overflow occurs when stack usage exceeds the memory reserved for it.

Common causes include:

  • Deep or uncontrolled recursion.
  • Large local arrays.
  • Excessive function-call nesting.
  • Large local structures.
  • Interrupt handlers requiring additional stack space.
Embedded C recommendation: Avoid large automatic arrays and uncontrolled recursion in systems with limited SRAM. Estimate stack requirements and verify them using the compiler's map file and suitable stack monitoring techniques.

7. Heap Memory

The heap is a memory region used for dynamic memory allocation during program execution.

Standard C provides functions such as malloc(), calloc(), realloc() and free() for dynamic allocation.

Example

#include <stdlib.h>

int main(void)
{
    unsigned int *data;

    data = (unsigned int *)malloc(5U * sizeof(unsigned int));

    if (data != NULL)
    {
        data[0] = 100U;

        free(data);
        data = NULL;
    }

    while (1)
    {
    }
}

Common Heap Problems

  • Memory leak: Allocated memory is not released when no longer needed.
  • Fragmentation: Free memory becomes divided into smaller separated blocks.
  • Double free: The same allocation is released more than once.
  • Use after free: A pointer is used after its memory has been released.
  • Allocation failure: The requested memory is unavailable.
Dynamic allocation is not automatically unsuitable for embedded systems, but it must be evaluated carefully. In deterministic real-time firmware, fixed-size buffers or controlled memory pools may provide more predictable behaviour than unrestricted heap allocation.

8. Stack vs Heap

Feature Stack Heap
Allocation Usually automatic Explicit dynamic allocation
Lifetime Usually associated with function/block execution Until explicitly released or runtime cleanup
Management Compiler and runtime conventions Allocator and application code
Common problem Stack overflow Leaks and fragmentation
Typical use Function calls and local data Variable-size runtime data

9. Code Size Optimization

Code-size optimization reduces the amount of memory required to store executable firmware.

9.1 Remove Unused Code

Remove unused functions, unnecessary modules and redundant code. Linker dead-code elimination may also remove unreferenced sections when enabled and supported.

9.2 Use Appropriate Data Types

Choose data types according to the required range and processor characteristics. A smaller integer type is not always faster or smaller after alignment and compiler decisions.

9.3 Avoid Unnecessary Duplication

Reusable functions can reduce repeated code, but excessive function calls may add overhead. Compare the generated machine code rather than assuming that one style is always smaller.

9.4 Use Compiler Optimization Options

Embedded compilers commonly provide optimization options for code size and execution speed.

Optimization Goal Typical Purpose
Optimize for size Reduce firmware code footprint
Optimize for speed Improve execution performance
Balanced optimization Balance code size and execution time
No optimization Can simplify some debugging activities
Compiler optimization can change instruction order, remove unused variables and inline functions. Debugging optimized code may therefore differ from debugging unoptimized source code.

10. Execution-Time Optimization

Execution-time optimization improves how efficiently firmware performs its required operations.

10.1 Reduce Unnecessary Calculations

Avoid repeating expensive calculations when the required value has not changed.

10.2 Use Efficient Algorithms

Algorithm selection can have a greater impact on execution time than small source-code changes.

10.3 Avoid Unnecessary Polling

Polling a status register continuously may consume CPU time. Interrupt-driven or event-driven techniques can be more efficient when the application and timing requirements support them.

10.4 Use Hardware Peripherals

Timers, PWM units, UARTs, SPI, I2C and ADC peripherals can perform specialized operations without requiring the CPU to implement every signal transition in software.

10.5 Minimize Unnecessary Data Copying

Passing large structures by value or copying large buffers repeatedly can increase execution time and stack usage. Use appropriate pointers or references where safe and supported by the design.

11. Constant Data and Lookup Tables

Lookup tables store precomputed values that can be accessed when required. They may reduce repeated calculations, particularly in applications involving mathematical transformations.

Example: Constant Lookup Table

#include <stdint.h>

static const uint16_t voltage_table[5] =
{
    0U,
    825U,
    1650U,
    2475U,
    3300U
};

int main(void)
{
    uint16_t value;

    value = voltage_table[2];

    while (1)
    {
    }
}

The const qualifier indicates that the application must not modify the table through this declaration. A suitable embedded toolchain can commonly place such data in Flash or another read-only region.

The exact storage location of const data depends on the compiler, linker configuration and target architecture. Check the map file instead of assuming that every const object is stored in Flash.

12. Bit Manipulation for Efficient Register Access

Embedded firmware frequently uses bitwise operations to configure hardware registers.

Set a Bit

register_value |= (1U << bit_position);

Clear a Bit

register_value &= ~(1U << bit_position);

Toggle a Bit

register_value ^= (1U << bit_position);

Test a Bit

if ((register_value & (1U << bit_position)) != 0U)
{
    /* Bit is set */
}
These are general read-modify-write patterns for ordinary software variables or registers whose hardware specification permits such operations. Do not use them blindly with write-one-to-clear or write-one-to-set hardware registers. Use the access method specified in the device manual.

13. Memory Alignment and Data Structures

Memory alignment refers to placing data at addresses appropriate for the processor's access requirements.

Some processors access naturally aligned data more efficiently. Other processors may impose restrictions on unaligned accesses.

Structure Padding

A compiler may insert padding bytes between structure members to satisfy alignment requirements. 

struct SensorData
{
    uint8_t status;
    uint32_t reading;
    uint16_t temperature;
};

The total structure size may be greater than the sum of the individual member sizes because of padding and alignment. Check the actual compiler's layout.

Optimization Considerations

  • Choose suitable member types.
  • Review structure padding.
  • Avoid unnecessary large structures.
  • Consider alignment when defining communication buffers.
  • Do not change structure packing without checking access safety.

14. Memory Optimization in LPC2129 Applications

The LPC2129 has limited on-chip SRAM, so memory use should be planned before integrating multiple firmware modules.

Example Application: Sensor Monitoring

Consider an application that uses ADC, UART, timer and LCD. Its memory requirements may include:

Memory Item Purpose
ADC result variable Stores the latest sensor conversion
Temperature variable Stores calculated temperature
UART transmit buffer Stores outgoing serial data
LCD message buffer Stores display text
Timer event counter Tracks periodic events
Stack Supports function calls and local variables

Example: Fixed-Size Buffer

#include <stdint.h>

#define UART_BUFFER_SIZE 32U

static uint8_t uart_buffer[UART_BUFFER_SIZE];

void Clear_Buffer(void)
{
    uint32_t i;

    for (i = 0U; i < UART_BUFFER_SIZE; i++)
    {
        uart_buffer[i] = 0U;
    }
}

A fixed-size buffer has a predictable storage requirement. Its size should be selected according to the maximum expected message length and the available RAM budget.

15. Linker Map File and Memory Analysis

A linker map file provides information about how the compiler and linker have arranged program sections and symbols in memory.

Information Available in a Map File

  • Memory region definitions.
  • Section start addresses.
  • Section sizes.
  • Symbol addresses.
  • Flash and RAM usage.
  • Stack and heap reservations, when defined.

Why It Is Important

A map file helps determine whether the application fits within available memory and whether unexpected sections are consuming significant space.

Keil uVision Workflow

  1. Open the LPC2129 project.
  2. Open the target build options.
  3. Check the linker and output settings.
  4. Enable map-file generation if it is not already enabled.
  5. Build the project.
  6. Open the generated map file.
  7. Review code, data and memory-region usage.
Exact menu names and output locations depend on the Keil toolchain version and project configuration. Use the generated build output and map file as the authoritative evidence for the current project.

16. Memory Optimization Best Practices

  • Know the available Flash and SRAM capacity.
  • Estimate memory requirements before implementation.
  • Use fixed-size buffers when predictable allocation is required.
  • Avoid unnecessary global variables.
  • Limit large local arrays and structures.
  • Use stack and heap reservations deliberately.
  • Check all dynamic allocation results.
  • Release dynamically allocated memory correctly.
  • Use suitable constant-data placement.
  • Review compiler optimization settings.
  • Inspect map files after significant changes.
  • Measure performance instead of guessing.
  • Retest after optimization to verify functional correctness.

18. Interview Questions and Answers

Q1. What is memory management in embedded systems?

It is the organization and control of memory used for program instructions, variables, buffers and runtime data.

Q2. What is the difference between Flash and SRAM?

Flash is non-volatile and commonly stores firmware. SRAM is volatile and stores runtime data.

Q3. What is the stack?

The stack is a memory region used for function calls, return information, saved registers and local automatic data.

Q4. What is the heap?

The heap is a memory region used for dynamic memory allocation during program execution.

Q5. What is stack overflow?

Stack overflow occurs when stack usage exceeds the available stack region.

Q6. What is memory fragmentation?

Fragmentation occurs when free memory becomes divided into separated blocks, potentially preventing a large allocation even when total free memory is sufficient.

Q7. What is a memory leak?

A memory leak occurs when allocated memory is no longer needed but is not released.

Q8. What is a linker map file?

It describes memory-region and section placement produced during linking, helping developers analyze memory usage.

Q9. What is code-size optimization?

It reduces the memory required to store executable firmware.

Q10. What is execution-time optimization?

It improves the efficiency with which firmware performs its operations.

Q11. Why are fixed-size buffers useful?

They provide predictable memory requirements and avoid runtime allocation for that buffer.

Q12. Does const always mean Flash storage?

No. The actual storage location depends on the compiler, linker configuration and target architecture.

Q13. Why should embedded developers monitor stack usage?

Limited SRAM and nested function or interrupt calls can cause stack exhaustion if the reserved stack is too small.

Q14. What is the purpose of compiler optimization?

Compiler optimization can improve code size, execution efficiency or both, depending on the selected settings.

21. Lesson Summary

  • Memory management is essential in resource-constrained embedded systems.
  • Flash commonly stores firmware and read-only information.
  • SRAM stores runtime variables, stack and buffers.
  • The stack supports function calls and automatic storage.
  • The heap supports dynamic memory allocation.
  • Memory leaks and fragmentation can affect system reliability.
  • Code-size optimization reduces firmware storage requirements.
  • Execution-time optimization improves runtime efficiency.
  • Lookup tables can reduce repeated calculations.
  • Linker map files help analyze memory placement and usage.
  • Memory optimization must preserve correctness and timing requirements.
