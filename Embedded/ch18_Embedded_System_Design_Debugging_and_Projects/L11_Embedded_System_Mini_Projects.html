Chapter 18: Embedded System Design, Debugging and Projects

Level: Practical Application – Beginner to Advanced

Learn how to combine microcontroller peripherals, sensors, actuators and firmware modules to develop complete embedded applications.

1. Introduction to Embedded System Mini Projects

An embedded system mini project is a small application that combines hardware and firmware to perform a specific task.

Mini projects help develop practical knowledge of:

  • Microcontroller architecture.
  • Embedded C programming.
  • GPIO input and output.
  • Timers and interrupts.
  • ADC sensor interfacing.
  • UART, I2C, SPI and CAN communication.
  • LCD and keypad interfacing.
  • PWM-based control.
  • Firmware testing and debugging.
Development environment: The example projects in this lesson use LPC2129 concepts and Embedded C. Since Keil uVision simulation is the available development environment, distinguish register-level simulation from actual hardware testing.

2. Project Development Workflow

  1. Identify the problem statement.
  2. Define the project objectives.
  3. Select the microcontroller and peripherals.
  4. Prepare the hardware block diagram.
  5. Allocate GPIO and peripheral pins.
  6. Design the firmware architecture.
  7. Write and compile the Embedded C program.
  8. Debug using the IDE and simulator.
  9. Test individual modules.
  10. Integrate and validate the complete system.
  11. Document results and limitations.

3. Project 1 – Digital Temperature Monitoring System

Objective

Measure temperature using a temperature sensor and display the calculated temperature on an LCD.

Hardware Requirements

  • LPC2129 microcontroller.
  • LM35 temperature sensor or a suitable analog temperature sensor.
  • 16×2 LCD.
  • Power supply and supporting components.

Block Diagram

LM35 Sensor
    |
    v
LPC2129 ADC
    |
    v
Temperature Calculation
    |
    v
16x2 LCD Display

Working Principle

  1. The sensor produces an analog voltage corresponding to temperature.
  2. The LPC2129 ADC converts the voltage into a digital value.
  3. Firmware converts the ADC result into an estimated sensor voltage.
  4. The temperature is calculated using the sensor's specified transfer characteristic.
  5. The LCD displays the temperature.

Example Calculation

For an LM35 with a nominal scale factor of 10 mV/°C:

Temperature (°C) = Sensor Voltage (V) / 0.010

If the measured sensor voltage is 0.25 V:

Temperature = 0.25 / 0.010
            = 25 °C

Firmware Algorithm

Initialize ADC
Initialize LCD

while (1)
{
    adc_value = ADC_Read(AIN0);

    voltage = (adc_value * VREF) / 1023.0;

    temperature = voltage / 0.010;

    LCD_DisplayTemperature(temperature);
}
The example assumes an LM35-compatible sensor and a correctly configured reference voltage. ADC channel mapping, input voltage limits, sensor wiring and calibration must be verified for the actual circuit.

Applications

  • Room temperature monitoring.
  • Industrial temperature monitoring.
  • Equipment temperature indication.

4. Project 2 – Automatic Street Light Controller

Objective

Automatically switch a light output based on ambient light intensity.

Hardware Requirements

  • LPC2129.
  • LDR sensor.
  • Resistor for voltage-divider circuit.
  • LED or suitable external lamp driver.

Block Diagram

Ambient Light
     |
     v
LDR Voltage Divider
     |
     v
LPC2129 ADC
     |
     v
Threshold Comparison
     |
     v
GPIO Output
     |
     v
Light Driver

Working Principle

  1. The LDR resistance changes with incident light.
  2. A voltage divider converts the resistance variation into a voltage.
  3. The ADC measures the voltage.
  4. Firmware compares the ADC reading with a threshold.
  5. The light output is activated when the configured dark condition is detected.

Firmware Algorithm

Initialize ADC
Initialize GPIO output

while (1)
{
    light_value = ADC_Read(AIN0);

    if (light_value < DARK_THRESHOLD)
    {
        Light_ON();
    }
    else
    {
        Light_OFF();
    }
}
The threshold direction depends on the voltage-divider arrangement. An LDR connected above or below the fixed resistor can produce opposite voltage responses to increasing light.

Possible Improvements

  • Introduce hysteresis to avoid rapid switching.
  • Add a manual override switch.
  • Use a timer for delayed switching.
  • Monitor sensor faults.

5. Project 3 – Password-Based Door Lock System

Objective

Develop a password-controlled access system using a keypad and an LCD.

Hardware Requirements

  • LPC2129.
  • 4×4 matrix keypad.
  • 16×2 LCD.
  • Relay driver or suitable actuator interface.
  • Power supply.

Block Diagram

4x4 Keypad
     |
     v
LPC2129
     |
     +------> LCD
     |
     +------> Driver Circuit
                    |
                    v
                Lock Unit

Working Principle

  1. The user enters a password using the keypad.
  2. The firmware scans keypad rows and columns.
  3. Entered digits are stored in a buffer.
  4. The entered password is compared with the configured credential.
  5. If the password is correct, the controller activates the lock driver for a defined period.
  6. If the password is incorrect, access is denied.

Firmware Logic

Initialize Keypad
Initialize LCD
Initialize Lock Output

while (1)
{
    password = Keypad_ReadPassword();

    if (Password_IsValid(password))
    {
        LCD_Display("Access Granted");
        Lock_Activate();
        Delay_LockPeriod();
        Lock_Deactivate();
    }
    else
    {
        LCD_Display("Access Denied");
    }
}

Possible Improvements

  • Limit repeated incorrect attempts.
  • Add a password-change feature.
  • Use non-volatile storage for credentials.
  • Add an alarm output after repeated failures.
For a real access-control product, use secure credential storage, appropriate authentication design and safe actuator control. A hard-coded demonstration password is not suitable for production security.

6. Project 4 – Digital Voltmeter Using LPC2129 ADC

Objective

Measure a suitably scaled analog voltage using the LPC2129 ADC and display the calculated voltage.

Hardware Requirements

  • LPC2129.
  • Voltage-divider or suitable signal-conditioning circuit.
  • 16×2 LCD or UART terminal.
  • Protected, regulated input source.

Block Diagram

Input Voltage
      |
      v
Voltage Divider
      |
      v
LPC2129 ADC
      |
      v
Digital Conversion
      |
      v
Voltage Calculation
      |
      v
LCD / UART Output

Working Principle

The input voltage is scaled to remain within the ADC's permitted analog input range. The ADC converts the scaled voltage into a 10-bit result.

Calculation

ADC Voltage = (ADC Result / 1023) × VREF

Input Voltage = ADC Voltage × Divider Ratio

For example, if a divider reduces an input voltage by a factor of 2, the original input estimate is twice the ADC pin voltage.

Firmware Example

adc_value = ADC_Read(AIN0);

adc_voltage =
    ((float)adc_value * VREF) / 1023.0f;

input_voltage =
    adc_voltage * DIVIDER_RATIO;
Never connect an unrestricted high-voltage source directly to an ADC input. Design the divider, protection, resistor ratings, isolation and calibration for the actual input range. The ADC input must remain within the device's specified analog limits.

7. Project 5 – UART-Based PC Communication System

Objective

Establish serial communication between LPC2129 and a computer for command transmission and status reporting.

Hardware Requirements

  • LPC2129.
  • USB-to-UART adapter with compatible logic levels.
  • Computer with serial terminal software.
  • Suitable power supply.

Block Diagram

Computer Terminal
       |
       v
USB-to-UART Adapter
       |
       v
LPC2129 UART0
       |
       v
Command Processing
       |
       v
GPIO / Status Response

Working Principle

  1. Configure UART0 pins and baud rate.
  2. Open a serial terminal on the computer.
  3. Receive a command character or string.
  4. Decode the command.
  5. Perform the requested operation.
  6. Transmit a response.

Example Command Set

CommandAction
1Turn LED ON
0Turn LED OFF
SSend system status
HDisplay help message

Firmware Example

UART0_Init();

while (1)
{
    command = UART0_ReceiveChar();

    switch (command)
    {
        case '1':
            LED_ON();
            UART0_SendString("LED ON\r\n");
            break;

        case '0':
            LED_OFF();
            UART0_SendString("LED OFF\r\n");
            break;

        case 'S':
            UART0_SendString("System Ready\r\n");
            break;

        default:
            UART0_SendString("Invalid Command\r\n");
            break;
    }
}

Possible Improvements

  • Use interrupt-based reception.
  • Add command framing and validation.
  • Implement a checksum for longer messages.
  • Add configurable parameters.

8. Project 6 – DC Motor Speed Control Using PWM

Objective

Control the average power delivered to a DC motor by changing PWM duty cycle.

Hardware Requirements

  • LPC2129.
  • DC motor.
  • Suitable motor driver or MOSFET stage.
  • External motor power supply.
  • Optional speed feedback sensor.

Block Diagram

Speed Command
      |
      v
LPC2129 Firmware
      |
      v
PWM Peripheral
      |
      v
Motor Driver
      |
      v
DC Motor
      |

Working Principle

  1. Configure the PWM period.
  2. Set a duty cycle corresponding to the requested motor command.
  3. Send the PWM output to a suitable driver.
  4. The driver controls motor current using the external supply.
  5. Optional feedback can be used to estimate actual speed.

Duty Cycle Example

Duty CycleConceptual Output
25%Lower average applied voltage
50%Intermediate average applied voltage
75%Higher average applied voltage
100%Continuously active output

Firmware Concept

Initialize_PWM();

while (1)
{
    duty = Read_Speed_Command();

    if (duty > 100U)
    {
        duty = 100U;
    }

    PWM_SetDuty(duty);
}
A microcontroller GPIO or PWM pin must not directly drive a motor. Use a driver rated for the motor's voltage, current and switching requirements. Include appropriate transient protection and thermal design.

9. Project 7 – Digital Clock Using Timer Interrupt

Objective

Develop a digital clock that maintains elapsed time using a periodic timer interrupt and displays the time on an LCD.

Hardware Requirements

  • LPC2129.
  • 16×2 LCD.
  • Optional push buttons for time adjustment.

Block Diagram

Timer0
   |
   v
Periodic Match Event
   |
   v
Timer ISR
   |
   v
Time Counters
   |
   v
Main Loop
   |
   v
LCD Display

Working Principle

  1. Configure Timer0 and its prescaler.
  2. Configure a periodic match event.
  3. Enable the Timer0 interrupt through the VIC.
  4. Update a time-base counter in the ISR.
  5. Convert the time-base count into seconds, minutes and hours in the main loop.
  6. Update the LCD when the displayed time changes.

Conceptual Firmware

volatile unsigned int tick_count = 0;

void Timer0_ISR(void)
{
    // Clear the Timer0 match interrupt flag.
    T0IR = (1U << 0);

    tick_count++;

    // Complete the VIC interrupt.
    VICVectAddr = 0;
}

int main(void)
{
    Timer0_Init();
    VIC_Timer0_Init();
    LCD_Init();

    while (1)
    {
        UpdateClockFromTicks(tick_count);
        LCD_UpdateTime();
    }
}
The ISR declaration and vector configuration depend on the compiler and startup code. For Keil ARM compiler projects, use the supported IRQ-handler convention. Shared multi-byte data may require a critical section when copied between the ISR and main loop.

10. Project 8 – Sensor-Based Alarm System

Objective

Monitor one or more sensor inputs and activate an alarm when a configured threshold or event is detected.

Hardware Requirements

  • LPC2129.
  • Suitable sensor or sensor module.
  • Buzzer driver circuit.
  • Optional LCD.

Block Diagram

Sensor Input
     |
     v
Signal Conditioning
     |
     v
LPC2129 ADC / GPIO
     |
     v
Threshold or Event Logic
     |
     +------> Buzzer Driver
     |
     +------> LCD / UART Alert

Working Principle

  1. Read the sensor through ADC or GPIO.
  2. Validate the input range.
  3. Compare the measured value with the configured limit.
  4. Activate the alarm if the condition is detected.
  5. Clear the alarm when the recovery condition is satisfied.

Firmware Concept

InitializeSensor();
InitializeAlarmOutput();

while (1)
{
    sensor_value = Sensor_Read();

    if (sensor_value > ALARM_THRESHOLD)
    {
        Alarm_ON();
    }
    else
    {
        Alarm_OFF();
    }
}

Possible Improvements

  • Use separate alarm and recovery thresholds.
  • Filter noisy sensor readings.
  • Log alarm events using UART.
  • Detect disconnected or invalid sensors.

11. Project 9 – CAN-Based Communication Between Controllers

Objective

Exchange sensor data and control messages between two CAN-enabled embedded nodes.

Hardware Requirements

  • Two CAN-capable controllers.
  • Suitable CAN transceivers.
  • CANH and CANL bus wiring.
  • Correct bus termination.
  • Power supplies and development tools.

Block Diagram

CAN Node 1
    |
    v
CAN Transceiver
    |
    +========== CAN Bus ==========+
                                 |
                                 v
                           CAN Transceiver
                                 |
                                 v

Working Principle

  1. Configure CAN bit timing on both nodes.
  2. Configure the acceptance filter.
  3. Prepare a CAN message with an identifier and payload.
  4. Request transmission through the CAN controller.
  5. The second node receives and validates the message.
  6. The receiver processes the payload and may send a response.

Example Message Design

FieldExample
Identifier0x120
Frame typeStandard data frame
DLC2 bytes
Byte 0Sensor status
Byte 1Sensor value

Firmware Tasks

  • Initialize CAN controller.
  • Configure bit timing.
  • Transmit messages.
  • Check transmission completion and errors.
  • Receive and release receive buffers.
  • Validate identifier and payload.
The CAN controller does not directly drive the differential CAN bus. An external CAN transceiver is required. High-speed CAN normally uses termination at the two physical ends of the bus. A single controller in a simulator cannot demonstrate a complete physical two-node network.

12. Project 10 – Multi-Peripheral Monitoring and Control System

Objective

Build an integrated embedded application that reads sensors, displays system status and controls outputs using multiple LPC2129 peripherals.

Hardware Requirements

  • LPC2129.
  • Analog sensor.
  • Push buttons.
  • 16×2 LCD.
  • LED indicators.
  • Optional motor driver and buzzer.

Block Diagram

     Analog Sensor ----> ADC
                              |
Push Buttons ----------> GPIO|

                              |
             +----------------+----------------+
             |                |                |
             v                v                v

             |                |                |
             v                v                v

Working Principle

  1. Initialize all required peripherals.
  2. Read analog sensor values periodically.
  3. Read user inputs from GPIO.
  4. Update the system state.
  5. Display readings and status on the LCD.
  6. Transmit diagnostic information through UART.
  7. Control an output using GPIO or PWM.
  8. Monitor faults and move to a defined safe state when required.

Suggested Firmware Architecture

    |
    +---- gpio.c / gpio.h
    |
    +---- adc.c / adc.h
    |

    |

    |

Main Loop Concept

int main(void)
{
    System_Init();

    GPIO_Init();
    ADC_Init();
    UART0_Init();
    LCD_Init();
    PWM_Init();

    while (1)
    {
        ReadInputs();
        UpdateApplicationState();
        UpdateDisplay();
        SendDiagnostics();
        UpdateOutputs();
    }
}

Possible Improvements

  • Use timer-based periodic scheduling.
  • Introduce a finite state machine.
  • Use interrupt-driven communication.
  • Add watchdog supervision.
  • Introduce sensor fault detection.
  • Separate drivers from application logic.

14. Firmware Design Best Practices

  • Use modular drivers for each peripheral.
  • Keep hardware configuration separate from application logic.
  • Use meaningful names for registers, masks and functions.
  • Use fixed-width integer types where appropriate.
  • Validate sensor readings before using them.
  • Use bounded waits and timeout handling.
  • Keep interrupt service routines short.
  • Protect shared data accessed from main code and ISRs.
  • Use state machines for applications with multiple operating modes.
  • Document clock settings, pin assignments and register configurations.
  • Use version control to track changes.
  • Test each module before integration.

15. Testing and Debugging in Keil uVision

For simulator-based project development, use the following workflow:

  1. Create an LPC2129 project in Keil uVision.
  2. Select the correct device and startup configuration.
  3. Add source files and required header files.
  4. Compile and resolve errors and warnings.
  5. Start the simulator and execute the program.
  6. Set breakpoints at important functions.
  7. Inspect CPU registers and peripheral registers where supported.
  8. Watch application variables and state transitions.
  9. Test boundary conditions and error paths.
  10. Record what was observed and what remains unverified.

The Keil simulator may not model every LPC2129 peripheral or external device. Register inspection and successful compilation do not prove that an LED lights, an LCD displays, an analog sensor is measured accurately, a motor rotates or a physical communication bus works. Those behaviours require appropriate hardware testing.

17. Interview Questions

Q1. Why are mini projects important in embedded systems?

They demonstrate practical knowledge of microcontrollers, peripheral configuration, firmware design, debugging and system integration.

Q2. What is the difference between a sensor and an actuator?

A sensor measures a physical quantity and provides an input to the system. An actuator converts a control signal into a physical action.

Q3. Why is modular programming important?

It improves code organization, reuse, testing, maintenance and separation of responsibilities.

Q4. Why should an ISR be short?

A short ISR reduces interrupt latency for other events and avoids unnecessarily delaying the main application or other tasks.

Q5. Why is a motor driver required?

Microcontroller pins cannot safely supply the current required by most motors. A suitable driver provides the required current and switching capability.

Q6. How do you test an embedded project without physical hardware?

Use compilation, simulator execution, breakpoints, variable inspection and peripheral-register inspection where supported. Document all external hardware behaviour that remains unverified.

Q7. What is a finite state machine?

A finite state machine represents an application using a defined set of states and transitions triggered by events or conditions.

Q8. What is system integration?

System integration combines separately developed hardware and software modules and verifies that they operate together as intended.
