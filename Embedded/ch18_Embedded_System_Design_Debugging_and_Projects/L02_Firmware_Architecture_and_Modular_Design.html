Lesson 02: Firmware Architecture and Modular Design

Chapter 18: Embedded System Design, Debugging and Projects

Level: Advanced

Understand how embedded firmware is organized into layers and independent modules to improve maintainability, reusability, debugging and system scalability.

1. Introduction to Firmware Architecture

Firmware is the software stored in an embedded system that controls the microcontroller and its connected hardware. It directly or indirectly manages peripherals, processes input data and performs application-specific operations.

As an embedded application becomes more complex, placing all program instructions inside one large function becomes difficult to maintain and debug.

Firmware architecture defines how the software is divided into layers, modules and interfaces.

Example: A temperature monitoring system may contain separate modules for:
  • ADC sensor acquisition.
  • Temperature calculation.
  • LCD display.
  • UART communication.
  • Alarm control.
  • Application scheduling.
Each module has a defined responsibility and communicates with other modules through functions or data interfaces.

2. Objectives of Modular Firmware Design

  • Divide complex firmware into smaller modules.
  • Separate hardware-dependent code from application logic.
  • Improve code readability and maintainability.
  • Reuse drivers across different projects.
  • Make unit testing and debugging easier.
  • Reduce unintended dependencies between modules.
  • Support future feature additions.

3. Layered Firmware Architecture

Layered architecture separates firmware according to responsibilities. Higher layers use services provided by lower layers. 

+---------------------------------------------+
|             Application Layer              |
|       Monitoring, Control, User Logic       |
+---------------------------------------------+
|             Middleware Layer                |
|   Communication Protocols, Data Services    |
+---------------------------------------------+
|          Peripheral Driver Layer             |
|     ADC | UART | GPIO | Timer | I2C | SPI   |
+---------------------------------------------+
|       Hardware Abstraction Layer (HAL)       |
|       Common Hardware Access Functions      |
+---------------------------------------------+
|               Hardware Layer                |
|             LPC2129 Microcontroller          |
+---------------------------------------------+

3.1 Hardware Layer

This is the physical layer containing the microcontroller, sensors, memory, communication devices and actuators.

3.2 Hardware Abstraction Layer

A Hardware Abstraction Layer (HAL) provides a consistent software interface for accessing hardware resources.

It hides some hardware-specific register operations from higher-level application code.

3.3 Peripheral Driver Layer

Device drivers initialize and control individual microcontroller peripherals.

  • GPIO driver.
  • ADC driver.
  • UART driver.
  • Timer driver.
  • I2C driver.
  • SPI and CAN drivers.

3.4 Middleware Layer

Middleware provides reusable services between drivers and application software.

Examples include:

  • Communication protocol handling.
  • Data formatting and parsing.
  • Command processing.
  • Protocol stacks.
  • File systems and reusable software services.

3.5 Application Layer

The application layer implements the main product functionality using services from lower layers.

It should generally avoid directly manipulating peripheral registers when suitable driver interfaces are available.

4. What Is Modular Programming?

Modular programming is a software development technique in which a large program is divided into smaller independent units called modules.

Each module performs a specific task and communicates through a defined interface.

Example Module Organization

Embedded Application
       |
       +---- ADC Module
       |
       +---- UART Module
       |
       +---- LCD Module
       |
       +---- GPIO Module
       |
       +---- Timer Module
       |
       +---- Application Logic

Characteristics of a Good Module

  • Has a clearly defined responsibility.
  • Provides a small and understandable interface.
  • Hides unnecessary internal implementation details.
  • Minimizes dependencies on unrelated modules.
  • Can be tested independently where practical.
  • Can be reused in other applications.

5. Advantages of Modular Firmware

Advantage Description
Maintainability Changes can be made within the responsible module.
Reusability Drivers can be reused in other projects.
Debugging Faults can be isolated to individual modules.
Readability Smaller functions are easier to understand.
Testing Modules can be tested independently.
Scalability New features can be added with less disruption.
Portability Hardware-dependent code can be isolated.

6. Coupling and Cohesion

6.1 Coupling

Coupling describes the degree of dependency between software modules.

Low coupling means that one module depends on relatively little internal information from another module.

Example of high coupling: An application function directly modifies several UART registers, changes UART configuration and accesses UART receive data in multiple unrelated places. Changes to the UART implementation can then affect several application functions.

6.2 Cohesion

Cohesion describes how closely related the responsibilities inside one module are.

High cohesion means that a module performs one closely related set of tasks.

Example of high cohesion: A UART driver contains functions for initialization, transmission, reception and status checking. These functions all relate to UART communication.

Good Design Principle

Aim for low coupling and high cohesion.

  • Keep unrelated operations in separate modules.
  • Expose only necessary functions and data.
  • Avoid unnecessary global variables.
  • Use clear interfaces between modules.

7. Header Files and Source Files

In C-based embedded firmware, modules are commonly organized into header files and source files.

Header File (.h)

A header file commonly contains:

  • Function declarations.
  • Public data types.
  • Macros and constants.
  • Required public structure definitions.

Source File (.c)

A source file commonly contains:

  • Function definitions.
  • Private helper functions.
  • Internal variables.
  • Hardware-specific implementation details.
Example project structure:

8. Creating a Modular GPIO Driver

Consider a GPIO driver for controlling an LED connected to LPC2129 pin P0.5.

8.1 gpio.h

#ifndef GPIO_H
#define GPIO_H

void GPIO_Init(void);
void GPIO_LED_On(void);
void GPIO_LED_Off(void);
void GPIO_LED_Toggle(void);

#endif

8.2 gpio.c

#include <LPC21xx.h>
#include "gpio.h"

#define LED_PIN (1U << 5)

void GPIO_Init(void)
{
    /* Select GPIO function for P0.5 */
    PINSEL0 &= ~(3U << 10);

    /* Configure P0.5 as output */
    IODIR0 |= LED_PIN;

    /* Initial output state: LOW */
    IOCLR0 = LED_PIN;
}

void GPIO_LED_On(void)
{
    IOSET0 = LED_PIN;
}

void GPIO_LED_Off(void)
{
    IOCLR0 = LED_PIN;
}

void GPIO_LED_Toggle(void)
{
    if (IOPIN0 & LED_PIN)
    {
        IOCLR0 = LED_PIN;
    }
    else
    {
        IOSET0 = LED_PIN;
    }
}

8.3 main.c

#include "gpio.h"

int main(void)
{
    GPIO_Init();

    while (1)
    {
        GPIO_LED_On();

        /* Application delay or event handling */

        GPIO_LED_Off();

        /* Application delay or event handling */
    }
}

Program Explanation

  • gpio.h declares the public GPIO functions.
  • gpio.c contains the hardware implementation.
  • main.c uses the GPIO interface without repeating register operations.
  • The application is separated from the GPIO implementation.
The toggle function reads the actual GPIO pin state. Its behaviour therefore depends on the selected pin mode and hardware model. For output-latch-based toggling, maintain a software state variable or use an appropriate hardware register strategy.

9. Creating a Modular UART Driver

UART communication can also be separated into a driver module and an application module.

9.1 uart.h

#ifndef UART_H
#define UART_H

void UART0_Init(void);
void UART0_SendChar(char data);
void UART0_SendString(const char *str);
char UART0_ReceiveChar(void);

#endif

9.2 uart.c

#include <LPC21xx.h>
#include "uart.h"

void UART0_Init(void)
{
    /* Configure P0.0 as TXD0 and P0.1 as RXD0 */
    PINSEL0 &= ~0x0FU;
    PINSEL0 |= 0x05U;

    /* Enable access to divisor registers */
    U0LCR = 0x83U;

    /* Example divisor and fractional setting */
    U0DLM = 0U;
    U0DLL = 0x47U;
    U0FDR = 0x83U;

    /* 8 data bits, no parity, one stop bit */
    U0LCR = 0x03U;
}

void UART0_SendChar(char data)
{
    while ((U0LSR & (1U << 5)) == 0U)
    {
        /* Wait for transmitter holding register */
    }

    U0THR = (unsigned char)data;
}

void UART0_SendString(const char *str)
{
    while (*str != '\0')
    {
        UART0_SendChar(*str);
        str++;
    }
}

char UART0_ReceiveChar(void)
{
    while ((U0LSR & (1U << 0)) == 0U)
    {
        /* Wait for received data */
    }

    return (char)U0RBR;
}

9.3 Application Example

#include "uart.h"

int main(void)
{
    UART0_Init();

    UART0_SendString("Embedded System Ready\r\n");

    while (1)
    {
        /* Application processing */
    }
}
Important: The UART example uses the established PCLK = 15 MHz configuration and fractional divisor values DLL = 0x47 and FDR = 0x83, giving approximately 9603 baud. The polling functions have no timeout and are intended for a basic demonstration. Production drivers should handle timeouts, errors and receive-buffer management. External UART communication also requires a supported simulator model or suitable physical interface.

10. Hardware Abstraction Layer (HAL)

A Hardware Abstraction Layer provides a common interface for accessing hardware while hiding some device-specific implementation details.

Without HAL

/* Application directly manipulates registers */

IODIR0 |= (1U << 5);
IOSET0 = (1U << 5);

With a Driver Interface

GPIO_LED_Init();
GPIO_LED_On();

The second approach makes application code easier to understand and reduces direct dependence on register-level implementation.

Benefits of HAL

  • Improves portability between hardware platforms.
  • Centralizes hardware-specific operations.
  • Provides consistent interfaces.
  • Makes application code easier to test.
  • Reduces repeated register-level code.
HAL does not automatically make firmware portable. Different microcontrollers may have different peripheral capabilities, timing requirements and pin configurations. Hardware-specific code still requires adaptation.

11. State Machines and Event-Driven Architecture

Larger embedded applications often use finite state machines to organize application behaviour.

Example: Monitoring Application States

        +-------------+
        |    INIT     |
        +------+------+
               |
               v
        +-------------+
        |   IDLE      |
        +------+------+
               |
          Sensor Event
               |
               v
        +-------------+
        |  MEASURE    |
        +------+------+
               |
               v
        +-------------+
        |  PROCESS    |
        +------+------+
               |
          Threshold Check
           /         \
          /           \
         v             v
   +----------+   +----------+
   |  ALARM   |   | NORMAL   |
   +----------+   +----------+

Example State Definitions

typedef enum
{
    STATE_INIT,
    STATE_IDLE,
    STATE_MEASURE,
    STATE_PROCESS,
    STATE_ALARM
} SystemState;

Example State Processing

SystemState current_state = STATE_INIT;

void Application_Task(void)
{
    switch (current_state)
    {
        case STATE_INIT:
            current_state = STATE_IDLE;
            break;

        case STATE_IDLE:
            /* Wait for a measurement event */
            break;

        case STATE_MEASURE:
            /* Acquire sensor data */
            current_state = STATE_PROCESS;
            break;

        case STATE_PROCESS:
            /* Evaluate measurement */
            current_state = STATE_IDLE;
            break;

        case STATE_ALARM:
            /* Handle alarm condition */
            break;

        default:
            current_state = STATE_INIT;
            break;
    }
}

This example demonstrates state organization. A complete application must define how events, sensor readings and threshold decisions cause state transitions.

12. Interrupts and Modular Firmware

Interrupt service routines are another part of firmware architecture. They should be separated from application processing wherever practical.

Recommended Approach

  • Keep interrupt service routines short.
  • Acknowledge the peripheral interrupt source correctly.
  • Set an event flag or update a suitable data structure.
  • Perform longer processing in the main application or task.
  • Protect shared data when concurrent access is possible.
volatile unsigned int timer_event = 0U;

/* Conceptual interrupt handler:
   Use the correct compiler-specific ISR declaration. */

void Timer_Event_Handler(void)
{
    timer_event = 1U;
}

int main(void)
{
    while (1)
    {
        if (timer_event != 0U)
        {
            timer_event = 0U;

            /* Perform application processing */
        }
    }
}
This is a conceptual event-handling example, not a complete LPC2129 ISR. A real handler must use the appropriate compiler-specific interrupt declaration, clear the timer peripheral interrupt flag and complete VIC interrupt handling. volatile does not guarantee atomic access to multi-byte shared data or make compound operations safe.

14. Common Modular Design Mistakes

Mistake Why It Is a Problem Better Approach
One large main function Hard to debug and maintain Divide code into modules and functions
Too many global variables Creates hidden dependencies Use controlled interfaces
Direct register access everywhere Hardware dependencies spread through application code Use peripheral drivers
Unclear module responsibilities Causes duplicated or conflicting logic Define module ownership
Long interrupt handlers Increases interrupt latency Defer lengthy processing
Blocking waits without timeout May cause the system to hang Use bounded waits and error handling
Duplicated initialization Can produce inconsistent configuration Centralize initialization

15. Testing Modular Firmware

Each module should be tested before it is integrated into the complete application.

Module Suggested Test
GPIO Verify direction and output latch operations.
UART Verify configuration and transmit/receive logic.
ADC Verify channel configuration and result processing.
Timer Verify prescaler, match and interrupt configuration.
LCD Verify command and data sequencing.
Application Verify decisions using controlled input values.

If external hardware is unavailable, application logic can be tested using simulated inputs, stubs or test functions. Such tests verify software behaviour, not physical peripheral operation.

16. Interview Questions and Answers

Q1. What is firmware architecture?

Firmware architecture defines how embedded software is organized into layers, modules and interfaces.

Q2. What is modular programming?

It is the technique of dividing a program into smaller independent modules, each with a specific responsibility.

Q3. What is a hardware abstraction layer?

HAL provides software interfaces that hide some hardware-specific implementation details from higher-level application code.

Q4. What is coupling?

Coupling is the degree of dependency between software modules.

Q5. What is cohesion?

Cohesion describes how closely related the responsibilities within a module are.

Q6. What is the ideal coupling and cohesion approach?

Good modular design generally aims for low coupling and high cohesion.

Q7. What is the difference between a header and source file?

A header file generally declares interfaces, types and macros. A source file contains their implementation.

Q8. Why should drivers be separated from application logic?

It improves code reuse, testability and maintainability while reducing hardware-specific dependencies in the application layer.

Q9. What is middleware?

Middleware provides reusable services between lower-level drivers and higher-level application software.

Q10. Why should an ISR be short?

A short ISR reduces interrupt latency and minimizes the time spent preventing other interrupt or application processing.

Q11. What is a finite state machine?

A finite state machine organizes program behaviour into defined states and transitions triggered by events or conditions.

Q12. Does HAL guarantee portability?

No. HAL improves portability, but hardware-specific implementations and device differences still need to be handled.
