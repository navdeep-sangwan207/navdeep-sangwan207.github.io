Lesson 05: Watchdog Timer and System Reliability

Chapter 18: Embedded System Design, Debugging and Projects

Level: Advanced

Learn watchdog timer principles, timeout management, firmware recovery, fault detection and techniques for building reliable embedded systems.

1. Introduction to System Reliability

System reliability is the ability of an embedded system to perform its intended functions correctly over a specified period under defined operating conditions.

Embedded systems may operate continuously in industrial equipment, vehicles, medical instruments, communication devices and consumer products. Unexpected firmware failures can interrupt their operation.

Common causes of system failure include:

  • Software deadlocks and infinite loops.
  • Unexpected program execution paths.
  • Stack overflow and memory corruption.
  • Power supply instability.
  • Electrical noise and electromagnetic interference.
  • Peripheral communication failures.
  • Incorrect timing and synchronization.
  • Hardware faults and component failures.
Example: Consider an embedded temperature monitoring system. If the firmware becomes stuck while communicating with a sensor, it may stop updating the display and responding to new measurements. A correctly designed recovery mechanism can help restore operation.

2. What Is a Watchdog Timer?

A watchdog timer (WDT) is a hardware timer used to detect firmware that has stopped making expected progress. The application periodically services or refreshes the watchdog before its timeout expires.

If the watchdog is not serviced within the configured time, the watchdog generates its specified response. Depending on the microcontroller, this may be a reset, interrupt or another hardware-defined action.

Basic Operating Principle

  1. The firmware configures the watchdog timer.
  2. The watchdog begins counting.
  3. The application performs its normal operations.
  4. The application services the watchdog at an appropriate point.
  5. The watchdog counter is restarted or cleared according to the hardware design.
  6. If servicing does not occur before timeout, the watchdog response is triggered.

Watchdog Block Diagram

        +-------------------------+
        |     Main Firmware       |
        |                         |
        | Sensor Read             |
        | Data Processing         |
        | Communication           |
        | Output Control          |
        +------------+------------+
                     |
                     | Valid service
                     v
        +-------------------------+
        |     Watchdog Timer      |
        |                         |
        | Counter / Timeout       |
        +------------+------------+
                     |
             Timeout expires
                     |
                     v
        +-------------------------+
        | Hardware Response       |
        |                         |
        | System Reset / IRQ      |
        | (device dependent)      |
        +-------------------------+
A watchdog is a recovery mechanism, not a guarantee that firmware is correct. It can recover from certain hangs, but it cannot automatically identify or repair every software or hardware fault.

3. Why Is a Watchdog Timer Required?

A microcontroller may continue receiving power while its firmware is no longer executing correctly. Without an appropriate recovery mechanism, the system may remain stuck indefinitely.

Typical Situations

Problem Possible Watchdog Benefit
Firmware stuck in an infinite loop Can trigger recovery if the loop prevents valid servicing
Software deadlock Can reset a system that stops making progress
Unexpected program flow May detect loss of normal execution
Peripheral communication wait Can recover if a blocked task prevents servicing
Temporary software malfunction May restore operation through a controlled reset
If a watchdog is serviced unconditionally inside a loop, the system may continue servicing it even when an important task has failed. Watchdog servicing must represent genuine application progress.

4. Types of Watchdog Timers

4.1 Hardware Watchdog

A hardware watchdog is implemented independently of the main application software execution path. It can continue operating even when the CPU is stuck, provided its clock and power source remain operational.

  • Can detect firmware execution failures.
  • May operate from a dedicated clock source.
  • Can generate a hardware reset.
  • Is generally more dependable than a software-only timer for detecting CPU hangs.

4.2 Software Watchdog

A software watchdog is implemented using a timer or periodic software task. The application monitors whether important tasks have completed within their expected time.

  • Can monitor multiple application tasks.
  • Can identify individual task timeouts.
  • Depends on the software scheduler or monitoring mechanism continuing to execute.

4.3 Windowed Watchdog

A windowed watchdog requires servicing within a defined time window. Servicing too early or too late can cause a fault response.

It helps detect both missed servicing and unexpected execution timing.

Type Operation Typical Purpose
Hardware watchdog Hardware counter and timeout Recovery from processor or firmware hangs
Software watchdog Software task monitoring Monitoring application task progress
Windowed watchdog Service allowed only in a defined interval Detecting incorrect servicing timing

5. Watchdog Timer Timeout

The watchdog timeout is the maximum permitted interval between valid service operations, subject to the microcontroller's watchdog implementation.

Timeout Selection

The timeout must be long enough to accommodate the application's worst-case execution time, including scheduling delays and expected temporary operations.

A suitable design considers:

  • Maximum task execution time.
  • Interrupt latency.
  • Communication timeouts.
  • Scheduling intervals.
  • Temporary CPU load increases.
  • Required system recovery time.

Example Calculation

Assume a monitoring application has the following approximate execution requirements:

Operation Maximum Time
Sensor reading 20 ms
Data processing 10 ms
Display update 15 ms
Communication operation 30 ms
Additional scheduling allowance 25 ms
Total estimated interval 100 ms

A watchdog timeout must exceed the worst-case interval between valid service operations, with an appropriate safety margin.

The 100 ms example is illustrative. Real timeout selection requires measured or justified worst-case execution times, device clock tolerances and the actual watchdog timing specification.

6. LPC2129 Watchdog Timer Overview

The LPC2129 includes an on-chip watchdog timer. It can be configured to monitor firmware execution and request a processor reset when the watchdog timeout condition occurs.

Important Watchdog Registers

Register Purpose
WDMOD Watchdog mode and status control
WDTC Watchdog timer constant
WDFEED Watchdog feed sequence register
WDTV Watchdog timer value

WDMOD Register

WDMOD controls watchdog operating mode and provides watchdog status information.

Bit Name Function
0 WDEN Watchdog enable
1 WDRESET Watchdog reset enable
2 WDTOF Watchdog time-out flag
3 WDINT Watchdog interrupt flag

WDTC Register

WDTC stores the watchdog timer constant. It determines the watchdog timeout according to the watchdog clock and the LPC2129 watchdog timing specification.

WDFEED Register

The watchdog must be fed using a specific two-write sequence:

  1. Write 0xAA to WDFEED.
  2. Write 0x55 to WDFEED immediately afterward.
WDFEED = 0xAAU;
WDFEED = 0x55U;
The two feed writes must follow the required sequence without an intervening operation that violates the watchdog feed timing requirement. Do not replace this sequence with a single write or a read-modify-write operation.

7. LPC2129 Watchdog Clock and Timeout Calculation

The watchdog timeout depends on the watchdog clock source and the programmed timer constant.

For the LPC2129, the watchdog timer uses the microcontroller watchdog clock derived from the system clock according to the device's clocking specification.

The general timer relationship is:

Timeout = Watchdog Timer Constant
          / Watchdog Timer Clock Frequency

For an accurate LPC2129 calculation, use the watchdog clock definition and timing formula in the device user manual. Do not substitute PCLK automatically: the watchdog clock is not simply the peripheral clock.

User project clock configuration: FOSC = 12 MHz, CCLK = 60 MHz and PCLK = 15 MHz. These values do not by themselves establish the exact watchdog timeout. The watchdog clock source and implementation-specific divider must also be considered.

8. LPC2129 Watchdog Initialization

A typical watchdog setup involves:

  1. Configure the watchdog timer constant.
  2. Configure watchdog mode.
  3. Enable reset mode if reset recovery is required.
  4. Enable the watchdog.
  5. Feed the watchdog using the required sequence.
  6. Service it at suitable points in the application.

Example Register Configuration

#include <LPC21xx.h>

#define WD_ENABLE       (1U << 0)
#define WD_RESET_ENABLE (1U << 1)

static void Watchdog_Feed(void)
{
    WDFEED = 0xAAU;
    WDFEED = 0x55U;
}

static void Watchdog_Init(void)
{
    /*
       Example timer constant only.
       Select the actual value using the
       LPC2129 watchdog timing specification.
    */
    WDTC = 0x0000FFFFU;

    /*
       Enable watchdog and watchdog reset.
       Configure before normal application operation.
    */
    WDMOD = WD_ENABLE | WD_RESET_ENABLE;

    Watchdog_Feed();
}

int main(void)
{
    Watchdog_Init();

    while (1)
    {
        /*
           Application tasks go here.
        */

        Watchdog_Feed();
    }
}
This is an instructional register-level example, not a validated production timeout configuration. The WDTC value must be calculated for the required timeout and checked against the LPC2129 watchdog clock and timer limits. Also verify the device-specific watchdog enable, mode and feed requirements before running on hardware.

9. Correct Watchdog Servicing Strategy

The watchdog should be serviced only when the application has completed the operations that demonstrate healthy execution.

Incorrect Servicing Strategy

while (1)
{
    Watchdog_Feed();

    /* Important application tasks may never execute */
}

This code feeds the watchdog continuously. If the application has stopped performing useful work, the watchdog may never detect the problem.

Improved Application Structure

while (1)
{
    Read_Sensor();

    Process_Data();

    Update_Display();

    Send_Status();

    /*
       Feed only after the required application
       operations have completed successfully.
    */
    Watchdog_Feed();
}

This is a simplified example. In a larger system, each critical task should report successful completion to a central watchdog supervisor.

10. Task Monitoring with a Software Watchdog

A software watchdog supervisor monitors the progress of multiple tasks. Each critical task reports completion through a flag, counter or heartbeat.

Example Task Monitoring Concept

#include <stdint.h>

#define SENSOR_TASK_DONE  (1U << 0)
#define DISPLAY_TASK_DONE (1U << 1)
#define UART_TASK_DONE    (1U << 2)

volatile uint32_t task_status = 0U;

void Sensor_Task(void)
{
    /* Read and validate sensor */
    task_status |= SENSOR_TASK_DONE;
}

void Display_Task(void)
{
    /* Update display */
    task_status |= DISPLAY_TASK_DONE;
}

void UART_Task(void)
{
    /* Process communication */
    task_status |= UART_TASK_DONE;
}

int main(void)
{
    const uint32_t ALL_TASKS_DONE =
        SENSOR_TASK_DONE |
        DISPLAY_TASK_DONE |
        UART_TASK_DONE;

    while (1)
    {
        task_status = 0U;

        Sensor_Task();
        Display_Task();
        UART_Task();

        if (task_status == ALL_TASKS_DONE)
        {
            Watchdog_Feed();
        }

        /*
           If a required task fails to complete,
           the watchdog is not serviced.
        */
    }
}
This example demonstrates the monitoring concept only. In a real interrupt-driven or RTOS application, task flags require suitable synchronization and time-bounded monitoring. The software supervisor must itself be protected against becoming stuck or falsely reporting success.

11. Reset Handling and Recovery

When a watchdog reset occurs, the processor restarts according to the microcontroller reset sequence. The startup code executes and the application initializes its required resources.

Typical Recovery Sequence

  1. Watchdog timeout occurs.
  2. Hardware requests a reset.
  3. Processor restarts.
  4. Startup code initializes the runtime environment.
  5. Firmware checks reset-cause information if available.
  6. Required peripherals are initialized.
  7. Application enters its normal operating state.

Why Reset-Cause Information Matters

Recording the reset cause helps developers distinguish watchdog resets from power-on resets, external resets and other supported reset sources.

The LPC2129 watchdog mode and status bits provide watchdog-related information. Check the reset-status and startup behaviour in the LPC2129 user manual before implementing a persistent reset-cause diagnostic.

12. Reliability Techniques Beyond Watchdogs

A reliable embedded system requires several complementary design techniques. A watchdog alone is insufficient.

12.1 Input Validation

Validate sensor readings, communication packets and configuration values before using them.

12.2 Error Detection

Use checksums, parity, CRC and protocol status checks where appropriate.

12.3 Timeout Handling

Use bounded waits for peripheral operations. Avoid indefinite waiting for hardware flags or communication responses.

12.4 Safe-State Design

Define what the system should do when a fault is detected. For example, a motor-control application may need to disable drive outputs when a critical fault occurs.

12.5 Power Supply Monitoring

Use suitable power supervision and brown-out protection where supported by the microcontroller and system design.

12.6 Defensive Programming

  • Check function return values.
  • Validate array indexes.
  • Check pointer validity.
  • Use bounded buffers.
  • Handle communication errors.
  • Avoid undefined behaviour.

13. Watchdog Timer vs. Normal Timer

Feature Normal Timer Watchdog Timer
Main purpose Generate timing events and measure intervals Detect missing firmware servicing
Typical use Periodic interrupts, delays and event timing System supervision and recovery
Servicing Configured according to application timing Must be serviced before watchdog timeout
Failure response Depends on configured timer action Device-specific timeout response
Reliability role Supports application timing Supports fault recovery

14. Common Watchdog Design Mistakes

  • Choosing a timeout that is too short.
  • Choosing a timeout that is unnecessarily long.
  • Feeding the watchdog unconditionally.
  • Feeding the watchdog from an interrupt that runs even when application tasks have failed.
  • Ignoring communication timeouts.
  • Failing to check reset-cause information.
  • Using an incorrect watchdog clock calculation.
  • Ignoring the required feed sequence.
  • Assuming watchdog reset fixes the original fault permanently.
  • Failing to test recovery behaviour.
Never use watchdog servicing as a substitute for diagnosing faults. Repeated watchdog resets may hide an underlying software, hardware or power problem.

15. Watchdog Testing and Validation

Watchdog behaviour should be tested deliberately during development. A test plan should verify both normal servicing and timeout recovery.

Test Procedure Expected Behaviour
Normal operation Service watchdog at the intended interval No watchdog timeout
Missing service Stop servicing the watchdog Configured timeout response occurs
Task failure Prevent one critical task from reporting completion Supervisor withholds watchdog service
Reset recovery Allow watchdog reset to occur Startup and recovery sequence execute
Repeated failure Simulate repeated application failure Fault is detected and recorded where possible

Testing Checklist

  • Confirm the watchdog clock configuration.
  • Confirm the timeout calculation.
  • Verify the feed sequence.
  • Check normal servicing behaviour.
  • Test intentional watchdog timeout.
  • Verify reset and startup behaviour.
  • Check whether reset cause is recorded correctly.
  • Verify that outputs enter a safe state after recovery.

17. Interview Questions and Answers

Q1. What is a watchdog timer?

A watchdog timer is a hardware timer used to detect missing firmware servicing and initiate a configured recovery response.

Q2. Why is a watchdog timer used?

It helps recover from certain firmware hangs, deadlocks and unexpected execution failures.

Q3. What is watchdog timeout?

It is the configured time interval within which the watchdog must receive a valid service operation.

Q4. What is watchdog feeding?

Feeding is the required operation that refreshes or restarts the watchdog counter.

Q5. What is a hardware watchdog?

It is a watchdog implemented in hardware, often capable of detecting a CPU hang independently of normal application execution.

Q6. What is a software watchdog?

It is a software monitoring mechanism that checks whether application tasks are completing within expected intervals.

Q7. What is a windowed watchdog?

It is a watchdog that accepts service only within a defined time window.

Q8. What is WDFEED in LPC2129?

WDFEED is the watchdog feed register. It requires the specified sequence of 0xAA followed by 0x55.

Q9. What is WDMOD?

WDMOD is the watchdog mode register used to configure watchdog operation and examine watchdog status.

Q10. Why should the watchdog not be fed continuously?

Unconditional servicing can prevent the watchdog from detecting a system in which critical application tasks have stopped making progress.

Q11. What is a safe state?

A safe state is a predefined system condition that reduces risk when a fault is detected.

Q12. Does a watchdog prevent every system failure?

No. It detects certain missing-servicing conditions. It does not replace fault diagnosis, input validation, hardware protection or system-level testing.

20. Mini-Project: Watchdog-Protected Sensor Monitoring System

Objective

Design a sensor monitoring application that uses a watchdog supervisor to detect failure of critical application operations.

Required Modules

  • LPC2129 microcontroller.
  • ADC sensor input.
  • Timer for periodic scheduling.
  • LCD for measurement display.
  • UART for diagnostic messages.
  • Watchdog timer for system supervision.

Functional Sequence

  1. Initialize the system clock and peripherals.
  2. Initialize ADC, LCD, UART and timer modules.
  3. Configure the watchdog using a verified timeout.
  4. Read the sensor value.
  5. Validate and process the measurement.
  6. Update the LCD and communication status.
  7. Report completion to the watchdog supervisor.
  8. Service the watchdog only after all required operations succeed.
  9. Investigate the recovery sequence when a task fails.

Expected Design Outcome

The application should continue normal operation while critical tasks complete correctly. If a monitored task fails to make progress, the watchdog supervisor should withhold servicing so that the configured recovery mechanism can operate.

This project is a firmware design exercise. With the user's Keil simulator-only setup, do not claim that an actual external sensor, LCD or watchdog reset has been physically tested.

21. Lesson Summary

  • System reliability is essential for continuous embedded operation.
  • A watchdog detects missing servicing within a configured interval.
  • Hardware, software and windowed watchdogs have different roles.
  • Timeout selection must account for worst-case execution time.
  • LPC2129 provides WDMOD, WDTC, WDFEED and WDTV registers.
  • The LPC2129 watchdog feed sequence is 0xAA followed by 0x55.
  • Watchdog servicing should represent genuine application progress.
  • Task monitoring can supervise multiple critical operations.
  • Reset-cause analysis helps diagnose system failures.
  • Watchdog protection should be combined with other reliability techniques.
  • Recovery behaviour must be tested and validated.
