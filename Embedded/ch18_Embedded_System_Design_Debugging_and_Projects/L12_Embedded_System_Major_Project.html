1. Project Overview

Project Title: LPC2129-Based Industrial Monitoring and Control System

This project demonstrates a modular embedded system that monitors an analog sensor, displays operating information, communicates with a computer and controls an external output according to configurable limits.

Project Objectives

  • Acquire analog sensor measurements using the LPC2129 ADC.
  • Display sensor values and system status on a 16×2 LCD.
  • Transmit measurements and diagnostic messages through UART.
  • Monitor user inputs through GPIO.
  • Generate PWM for an externally driven control output.
  • Use a timer for periodic sampling and application scheduling.
  • Implement alarm conditions and safe-state behaviour.
  • Develop modular and maintainable firmware.
This is an educational monitoring and control architecture. It is not a certified industrial safety controller. Safety-critical applications require independent protection mechanisms, hazard analysis and appropriate hardware validation.

2. Problem Statement

Industrial equipment often requires continuous monitoring of operating parameters such as temperature, voltage, pressure or other sensor measurements.

A monitoring controller should:

  1. Read sensor values at regular intervals.
  2. Convert raw ADC readings into engineering units.
  3. Compare measurements with configured operating limits.
  4. Display current values and alarm status.
  5. Transmit diagnostic information to a computer.
  6. Control an output when required.
  7. Detect invalid readings and communication faults.
  8. Enter a defined safe state when a critical fault occurs.

9. Sensor Acquisition and ADC Calculation

For an LPC2129 10-bit ADC, the digital conversion result ranges from 0 to 1023.

ADC Voltage =
    (ADC Result / 1023) × VREF

Example

Assume:

  • ADC result = 512.
  • Reference voltage = 3.3 V.
  • ADC resolution = 10 bits.
ADC Voltage = (512 / 1023) × 3.3
            ≈ 1.652 V

ADC Reading Function

#include <LPC21xx.h>

unsigned int ADC_Read_AIN0(void)
{
    unsigned int result;
    unsigned int data;

    // Select AIN0 on P0.27.
    PINSEL1 &= ~(3U << 22);
    PINSEL1 |=  (1U << 22);

    // Enable ADC, select AIN0,
    // PCLK = 15 MHz, CLKDIV = 3.
    ADCR = (1U << 0) |
           (3U << 8) |
           (1U << 21);

    // Start immediate conversion.
    ADCR |= (1U << 24);

    do
    {
        data = ADDR;
    }
    while ((data & (1U << 31)) == 0U);

    // Extract 10-bit result.
    result = (data >> 6) & 0x3FFU;

    // Stop the start request.
    ADCR &= ~(7U << 24);

    return result;
}
This example uses the legacy LPC2129 ADCR/ADDR register interface. The ADC input must remain within the specified analog input range. The code uses a polling loop without a timeout; production firmware should use bounded waiting and explicit error handling. Keil simulation of analog input depends on the selected device model.

10. Timer-Based Periodic Scheduling

Use Timer0 to establish a nominal periodic time base.

For PCLK = 15 MHz and PR = 14999:

TC Increment Frequency =
    15,000,000 / (14999 + 1)

  = 1000 Hz

TC Increment Interval = 1 ms

Timer0 Initialization Example

#include <LPC21xx.h>

void Timer0_Init(void)
{
    T0TCR = (1U << 1);

    T0PR = 14999U;
    T0PC = 0U;
    T0TC = 0U;

    // Match after 1000 TC increments.
    T0MR0 = 1000U;

    // Interrupt on MR0 and reset TC on match.
    T0MCR = (1U << 0) |
            (1U << 1);

    // Clear pending match flag.
    T0IR = (1U << 0);

    // Start Timer0.
    T0TCR = (1U << 0);
}

This setup establishes a nominal one-second match interval when the counter starts at zero and the match/reset configuration operates as expected.

This example demonstrates timer setup only. To use a Timer0 interrupt, configure the VIC source, vector slot and ISR according to the interrupt chapter. For a complete application, keep the ISR short and use it to set a scheduling flag or increment a time-base counter.

11. UART Communication

UART0 can transmit measurements and diagnostic information to a computer.

Example Diagnostic Message

System Status: RUNNING
Sensor ADC: 512
Sensor Voltage: 1.652 V
Alarm Status: NORMAL
Output Command: 50%

Communication Design

  • Configure UART pins through PINSEL.
  • Configure baud rate using DLL, DLM and FDR as applicable.
  • Set the required line format, such as 8N1.
  • Use transmit and receive functions with bounded waits.
  • Validate received commands before acting on them.
  • Use a structured message format for larger data exchanges.
For PCLK = 15 MHz, an example UART0 9600-baud configuration uses DLL = 71, DLM = 0 and FDR = 0x83, giving approximately 9603 baud.

13. PWM-Based Output Control

PWM can control an external driver based on a user command or measured operating condition.

Example Duty Cycle

CommandPWM Duty
Low25%
Medium50%
High75%
Maximum100%

Duty-Cycle Calculation

Duty Cycle (%) =
    (Pulse Width / Period) × 100

For a nominal period of 1000 timer ticks and a pulse width of 500 ticks:

Duty Cycle = (500 / 1000) × 100
           = 50%

Firmware Concept

void ApplyOutputCommand(unsigned int duty)
{
    if (duty > 100U)
    {
        duty = 100U;
    }

    PWM_SetDuty(duty);
}
Configure the correct PWM pin function and use a suitable external driver. Do not connect a motor, relay coil or other high-current load directly to the microcontroller output.

14. Alarm and Fault Management

The firmware should distinguish normal operating conditions, warnings and critical faults.

ConditionSystem Response
Normal measurementContinue monitoring
Warning threshold crossedDisplay warning and record event
Critical threshold crossedEnter defined safe state
ADC conversion timeoutMark measurement invalid
UART communication timeoutRecord communication fault
Watchdog resetRestart and record reset cause if available

Example Threshold Logic

if (sensor_value > CRITICAL_LIMIT)
{
    system_state = SYSTEM_SAFE_STATE;
}
else if (sensor_value > WARNING_LIMIT)
{
    system_state = SYSTEM_WARNING;
}
else
{
    system_state = SYSTEM_RUNNING;
}

Use hysteresis where appropriate to prevent repeated switching near a threshold.

15. Main Application Structure

The following is an application-level framework showing how the modules fit together. Driver functions must be implemented separately and checked against the exact device and compiler configuration.

#include <LPC21xx.h>
#include "system.h"
#include "gpio.h"
#include "adc.h"
#include "timer.h"
#include "uart.h"
#include "lcd.h"
#include "pwm.h"
#include "application.h"

int main(void)
{
    unsigned int adc_value;
    float sensor_voltage;

    System_Init();

    GPIO_Init();
    ADC_Init();
    Timer0_Init();
    UART0_Init();
    LCD_Init();
    PWM_Init();

    UART0_SendString("System Started\r\n");
    LCD_DisplayStartup();

    while (1)
    {
        adc_value = ADC_Read_AIN0();

        sensor_voltage =
            ((float)adc_value * 3.3f) / 1023.0f;

        Application_Update(adc_value,
                           sensor_voltage);

        LCD_Update();
        UART_SendDiagnostics();

        Control_Update();
    }
}
This is a structural integration example, not a complete compilable project. Functions such as System_Init(), ADC_Init(), LCD_Update() and Control_Update() require their own implementations. A production application should also schedule acquisition, display and communication at defined rates rather than executing every operation continuously in an uncontrolled loop.

17. Keil uVision Simulation and Debugging

Use Keil uVision to compile and inspect the firmware.

Practical Procedure

  1. Create an LPC2129 project.
  2. Select the appropriate target device.
  3. Configure startup and system clock files.
  4. Add all driver and application source files.
  5. Compile the project.
  6. Resolve errors and warnings.
  7. Start the simulator.
  8. Set breakpoints in ADC, timer and application functions.
  9. Inspect CPU and peripheral registers where supported.
  10. Monitor application variables and state transitions.
  11. Test threshold and fault-handling paths.
  12. Document simulator observations.
Keil uVision simulation does not establish actual sensor accuracy, LCD operation, physical UART communication, motor behaviour, power consumption or external bus reliability. These require hardware-based testing with suitable instruments and test equipment.

20. Project Viva and Interview Questions

Q1. Why did you select LPC2129?

It provides an ARM7TDMI-S processor core, on-chip memory and multiple integrated peripherals suitable for learning embedded firmware development.

Q2. Why is ADC required?

ADC converts analog sensor voltage into a digital value that the microcontroller can process.

Q3. Why did you use a timer?

A timer provides periodic timing events for sensor sampling, scheduling and time-based application functions.

Q4. Why is UART used?

UART provides a simple serial interface for communicating with a computer or another compatible serial device.

Q5. Why use modular programming?

It separates peripheral drivers and application logic, improving readability, reuse and testing.

Q6. What is the role of a watchdog?

It can help recover the system if the firmware stops operating correctly and fails to service the watchdog.

Q7. How did you debug the project?

Explain the build process, breakpoints, variable inspection, register inspection and the tests performed. Distinguish simulator evidence from physical measurements.

Q8. What are the limitations of your project?

Identify what was simulated, which peripherals were not physically validated, what environmental conditions were not tested and what further work is required.
