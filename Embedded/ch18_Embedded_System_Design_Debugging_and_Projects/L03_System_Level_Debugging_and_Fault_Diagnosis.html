Lesson 03: System-Level Debugging and Fault Diagnosis

Chapter 18: Embedded System Design, Debugging and Projects

Level: Advanced

Learn how to identify, isolate, analyze and correct faults that affect an entire embedded system, including hardware, firmware, peripherals, timing and communication interfaces.

1. Introduction to System-Level Debugging

Debugging is the systematic process of identifying, analyzing and correcting errors or unexpected behaviour in a software or embedded system.

In a simple software program, a fault may be limited to one function. In an embedded system, a problem can involve several interacting components:

  • Microcontroller hardware.
  • Power supply and reset circuitry.
  • Peripheral configuration.
  • Firmware modules.
  • Communication interfaces.
  • Interrupts and timing.
  • External sensors and actuators.

System-level debugging examines the complete system rather than looking only at the source code of one function.

Example: Suppose an LPC2129 application reads a sensor through ADC and displays the result on an LCD. If the LCD shows an incorrect value, possible causes include incorrect ADC channel selection, wrong reference voltage, conversion-result extraction, incorrect calculation, memory corruption or LCD data-transfer errors.

2. Objectives of System-Level Debugging

  • Identify the source of system failures.
  • Separate hardware faults from firmware faults.
  • Trace data flow between software modules.
  • Analyze peripheral registers and status flags.
  • Detect timing and synchronization problems.
  • Identify memory corruption and stack problems.
  • Determine the root cause of intermittent faults.
  • Verify that corrective actions resolve the problem.

3. Types of Embedded System Faults

3.1 Hardware Faults

Hardware faults originate in physical components or connections.

  • Incorrect power supply voltage.
  • Open or short circuit.
  • Incorrect pin connections.
  • Damaged components.
  • Incorrect clock or reset circuitry.
  • Electrical noise or poor grounding.

3.2 Firmware Faults

Firmware faults originate in the software implementation.

  • Incorrect algorithm.
  • Wrong register configuration.
  • Invalid pointer access.
  • Array index out of bounds.
  • Incorrect data type or arithmetic.
  • Missing initialization.

3.3 Peripheral Configuration Faults

  • Incorrect PINSEL configuration.
  • Wrong peripheral clock.
  • Incorrect baud-rate divisor.
  • Incorrect ADC channel selection.
  • Incorrect timer match configuration.
  • Missing peripheral enable bit.

3.4 Timing Faults

  • Incorrect delay calculation.
  • Race conditions.
  • Missed events.
  • Interrupt latency.
  • Communication timing violations.
  • Incorrect synchronization.

3.5 Communication Faults

  • Incorrect UART baud rate.
  • I2C address mismatch.
  • SPI mode mismatch.
  • CAN bit-rate mismatch.
  • Missing acknowledgement.
  • Incorrect data framing.

4. Debugging Methodology

A structured debugging process prevents random code changes and helps identify the actual cause of a failure.

  1. Observe: Identify the unexpected system behaviour.
  2. Reproduce: Create conditions under which the fault occurs.
  3. Collect information: Record inputs, outputs, register values and error conditions.
  4. Isolate: Identify the affected hardware or firmware module.
  5. Form a hypothesis: Determine a possible technical cause.
  6. Test the hypothesis: Use measurements, breakpoints or controlled inputs.
  7. Correct: Make a targeted change to address the root cause.
  8. Verify: Repeat the original test and check the result.
  9. Regression test: Confirm that related functionality still works.
  10. Document: Record the cause, correction and test evidence.
Avoid changing multiple unrelated settings simultaneously. If several variables are changed at once, it becomes difficult to determine which change actually corrected or caused the fault.

5. Debugging Tools and Techniques

5.1 Breakpoints

A breakpoint temporarily stops program execution at a selected instruction.

Breakpoints are useful for:

  • Checking whether a function is executed.
  • Inspecting variable values.
  • Examining program flow.
  • Identifying where incorrect data first appears.

5.2 Single Stepping

Single stepping executes instructions or source statements one at a time, depending on the debugger mode.

It helps verify:

  • Function execution order.
  • Conditional branches.
  • Loop behaviour.
  • Register assignments.
  • Data processing operations.

5.3 Watch Window

A Watch window displays selected program variables while debugging.

Typical observations include:

  • ADC result.
  • Temperature calculation.
  • Timer event counter.
  • Communication status.
  • Application state variable.

5.4 Register Inspection

Register inspection verifies whether the microcontroller peripherals have been configured correctly.

Register Purpose
PINSEL0 / PINSEL1 Pin function selection
IODIR0 / IODIR1 GPIO direction
IOPIN0 / IOPIN1 GPIO pin state
U0LCR UART line configuration
U0LSR UART line status
T0TC Timer 0 counter value
T0IR Timer 0 interrupt flags
ADCR ADC control configuration
ADDR Legacy LPC2129 ADC result register

5.5 Debug Output and Logging

Logging records selected events, values and error conditions to help reconstruct what happened during execution.

In a physical embedded system, logging may use UART, a trace interface, a memory buffer or a dedicated debug communication channel.

6. Systematic Hardware Fault Diagnosis

Hardware debugging should begin with basic electrical checks before investigating complex firmware behaviour.

Recommended Inspection Sequence

  1. Verify the power supply output.
  2. Check common ground connections.
  3. Verify reset pin behaviour.
  4. Check oscillator and clock configuration.
  5. Inspect the microcontroller pin connections.
  6. Verify sensor and actuator supply requirements.
  7. Check pull-up and pull-down resistors.
  8. Inspect signal levels using appropriate instruments.

Common Instruments

Instrument Typical Use
Digital multimeter Voltage, resistance and continuity checks
Oscilloscope Voltage waveforms and timing analysis
Logic analyzer Digital signal and protocol analysis
Serial terminal UART data observation
Power supply Controlled power delivery and current observation
Never assume that a digital pin is electrically safe merely because a register accepts the intended value. Verify device voltage limits, current limits, external circuitry and component datasheets before connecting hardware.

7. Peripheral-Level Debugging

7.1 GPIO Debugging

Check the following:

  • Correct pin function in PINSEL registers.
  • Correct direction in IODIR registers.
  • Correct output operation through IOSET and IOCLR.
  • Correct input reading through IOPIN.
  • Correct active-HIGH or active-LOW logic.

7.2 Timer Debugging

Inspect:

  • Peripheral clock frequency.
  • Prescaler register PR.
  • Timer counter TC.
  • Match register MR.
  • Match control register MCR.
  • Interrupt flag register IR.
  • Timer control register TCR.

7.3 UART Debugging

Inspect:

  • TXD and RXD pin selection.
  • Peripheral clock frequency.
  • DLL, DLM and FDR configuration.
  • Line Control Register LCR.
  • Line Status Register LSR.
  • External interface voltage and wiring.

7.4 ADC Debugging

Inspect:

  • Correct analog channel selection.
  • Correct pin function.
  • ADC clock frequency.
  • Power and conversion-start configuration.
  • DONE flag and result extraction.
  • Reference voltage and analog input range.

7.5 I2C Debugging

Check:

  • SDA and SCL pin configuration.
  • Pull-up resistors.
  • I2C clock configuration.
  • 7-bit slave address.
  • START and STOP sequence.
  • ACK and NACK status codes.
  • Correct service of I2C state-machine status.

7.6 SPI and CAN Debugging

For SPI, inspect CPOL, CPHA, clock frequency, chip select, data length and status flags.

For CAN, inspect bit timing, acceptance filtering, controller mode, transmit status, receive status and physical transceiver connections.

8. Firmware Fault Diagnosis

8.1 Incorrect Variable Values

An incorrect variable may result from wrong input data, arithmetic errors, memory corruption or an incorrect function call.

8.2 Invalid Pointer Access

An invalid pointer can cause unintended memory access, unexpected program behaviour or processor exceptions.

8.3 Buffer Overflow

A buffer overflow occurs when data is written beyond the allocated buffer boundaries. 

#include <stdio.h>

int main(void)
{
    unsigned char buffer[5];
    unsigned int i;

    /* Correct: indices 0 through 4 */
    for (i = 0U; i < 5U; i++)
    {
        buffer[i] = (unsigned char)i;
    }

    return 0;
}
The example demonstrates valid array indexing. Always verify buffer capacity before copying, receiving or formatting data in embedded applications.

8.4 Missing Initialization

Uninitialized variables, pointers and peripheral registers can produce unpredictable behaviour. Initialize software state and configure required hardware before using it.

8.5 Incorrect Data Types

Incorrect signedness, width or arithmetic conversions can cause unexpected results. Select data types based on the range and representation required by the application.

9. Timing and Synchronization Faults

9.1 Race Condition

A race condition occurs when the result depends on the unpredictable timing or order of multiple operations accessing shared data or resources.

9.2 Shared Data Between ISR and Main Code

An interrupt routine and the main program may access the same variable. This requires careful consideration of data width, atomicity and synchronization. 

volatile unsigned int event_count = 0U;

/* Conceptual ISR-side update */
void Timer_Event(void)
{
    event_count++;
}

/* Main application */
void Application_Task(void)
{
    unsigned int local_count;

    local_count = event_count;

    /* Process local_count */
}
volatile ensures that the compiler treats accesses as observable operations, but it does not make read-modify-write operations atomic. The example is conceptual; shared-data protection must be selected according to the processor, compiler and data width.

9.3 Timing Fault Examples

  • Waiting indefinitely for a peripheral status flag.
  • Using a software delay that is not calibrated.
  • Failing to clear an interrupt source flag.
  • Blocking an application while waiting for communication.
  • Using an incorrect timer prescaler.

10. Root-Cause Analysis

Root-cause analysis identifies the underlying reason a fault occurs rather than only correcting its visible symptom.

Example: UART Communication Failure

Observed symptom: The receiver displays incorrect characters.

Possible causes:

  • Incorrect baud rate.
  • Incorrect data-bit configuration.
  • Incorrect parity configuration.
  • Incorrect stop-bit configuration.
  • Incorrect pin multiplexing.
  • Incorrect electrical interface.

Root-Cause Investigation

  1. Confirm the configured PCLK.
  2. Calculate the actual UART baud rate.
  3. Inspect DLL, DLM and FDR.
  4. Inspect LCR settings at both ends.
  5. Verify TXD and RXD connections.
  6. Verify the signal using an appropriate measurement tool.
  7. Correct the identified configuration or electrical fault.
  8. Repeat the communication test.

11. Fault Tree Analysis

Fault Tree Analysis (FTA) is a systematic method for identifying possible causes of a top-level system failure.

12. Failure Mode and Effects Analysis (FMEA)

FMEA is a structured technique used to identify possible failure modes, their effects and ways to reduce risk.

Failure Mode Effect Possible Action
ADC channel misconfigured Incorrect sensor reading Verify pin and channel setup
UART baud mismatch Communication errors Verify both baud-rate configurations
Timer interrupt not cleared Repeated interrupt handling Correctly acknowledge interrupt source
Stack overflow Memory corruption or crash Review stack usage and call depth
Power supply failure System reset or shutdown Verify power design and monitoring

Formal FMEA may assign Severity, Occurrence and Detection ratings. These ratings can be combined into a Risk Priority Number (RPN), depending on the organization's methodology.

13. Example: Debugging an LPC2129 GPIO Problem

Consider an application where P0.5 is intended to operate as a GPIO output, but the output latch does not behave as expected.

Step 1: Check Pin Function

PINSEL0 &= ~(3U << 10);

P0.5 uses PINSEL0 bits 11:10. Clearing both bits selects the GPIO function.

Step 2: Check Direction

IODIR0 |= (1U << 5);

This configures P0.5 as an output.

Step 3: Set Output Latch

IOSET0 = (1U << 5);

Step 4: Inspect Relevant Registers

Register Expected Condition
PINSEL0[11:10] 00 for GPIO
IODIR0[5] 1 for output
IOSET0 write Bit 5 written as 1 to set the output latch
IOSET0 and IOCLR0 use write-one-to-set and write-one-to-clear semantics. Assign the mask directly; do not use read-modify-write operations such as IOSET0 |= mask.

14. Keil uVision Debugging Practice

The following activities can be performed using the Keil uVision simulator for the LPC2129 project.

Exercise 1: Inspect GPIO Configuration

  1. Open the LPC2129 project.
  2. Set a breakpoint after GPIO initialization.
  3. Start the debugger.
  4. Inspect PINSEL0 and IODIR0.
  5. Check the P0.5 configuration.

Exercise 2: Inspect Timer Configuration

  1. Set a breakpoint after timer initialization.
  2. Inspect T0PR and T0TCR.
  3. Inspect T0TC where supported by the simulator.
  4. Verify the intended register configuration.

Exercise 3: Inspect UART Configuration

  1. Set a breakpoint after UART initialization.
  2. Inspect U0LCR.
  3. Inspect divisor and fractional divider registers.
  4. Inspect U0LSR during transmission where supported.

Exercise 4: Debug Application Logic

  1. Set a breakpoint inside a processing function.
  2. Inspect the input value.
  3. Execute the conditional statements step by step.
  4. Verify the selected output action.
Keil simulator support depends on the selected device model. Register inspection and CPU execution do not prove actual electrical output, external communication or physical peripheral operation. Use suitable hardware and instruments for physical validation.

15. Debugging Checklist

  • Confirm the fault can be reproduced.
  • Record the exact conditions and inputs.
  • Check power, clock and reset assumptions.
  • Inspect pin multiplexing and peripheral enable settings.
  • Check peripheral status flags.
  • Inspect important variables and memory locations.
  • Check interrupt configuration and shared data.
  • Verify timing calculations.
  • Isolate modules to narrow down the problem.
  • Test one hypothesis at a time.
  • Repeat tests after applying a correction.
  • Record the final root cause and solution.

16. Interview Questions and Answers

Q1. What is system-level debugging?

It is the process of investigating failures across the complete embedded system, including hardware, firmware, peripherals and their interactions.

Q2. What is fault diagnosis?

Fault diagnosis identifies the nature, location and likely cause of a system failure.

Q3. What is root-cause analysis?

It identifies the underlying reason for a failure rather than only correcting its visible symptom.

Q4. What is a breakpoint?

A breakpoint temporarily stops program execution at a selected instruction or source location.

Q5. What is a race condition?

A race condition occurs when the result depends on the timing or order of concurrent operations.

Q6. What is buffer overflow?

Buffer overflow occurs when a program writes beyond the allocated memory boundary of a buffer.

Q7. What is FMEA?

Failure Mode and Effects Analysis is a systematic technique for identifying possible failures and evaluating their effects.

Q8. What is Fault Tree Analysis?

Fault Tree Analysis represents how combinations of lower-level faults can lead to a defined system failure.

Q9. Why is register inspection useful?

It helps verify whether peripheral configuration and status match the intended firmware operation.

Q10. What is the difference between a symptom and a root cause?

A symptom is the observed problem. A root cause is the underlying reason that produces the problem.

Q11. Why should debugging changes be controlled?

Controlled changes make it easier to identify which change affects the observed behaviour and reduce the chance of introducing unrelated faults.

Q12. Can a simulator diagnose every hardware fault?

No. A simulator can help debug supported firmware and peripheral behaviour, but it cannot fully reproduce physical electrical faults or all hardware interactions.

20. Lesson Summary

  • System-level debugging investigates the complete embedded system.
  • Faults may originate in hardware, firmware, timing or communication.
  • Breakpoints, watch windows and register inspection are useful tools.
  • Peripheral-specific debugging requires checking configuration and status registers.
  • Root-cause analysis identifies the underlying reason for failure.
  • Fault Tree Analysis organizes possible causes logically.
  • FMEA evaluates possible failure modes and their effects.
  • Race conditions and memory corruption require careful investigation.
  • Testing after correction confirms that the problem has been resolved.
  • Physical validation is necessary for real hardware behaviour.
