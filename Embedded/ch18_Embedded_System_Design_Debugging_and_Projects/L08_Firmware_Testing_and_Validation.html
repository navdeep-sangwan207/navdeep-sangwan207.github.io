Lesson 08: Firmware Testing and Validation

Chapter 18: Embedded System Design, Debugging and Projects

Level: Advanced

Learn firmware test strategies, unit testing, integration testing, system testing, verification, validation, test coverage and regression testing.

1. Introduction to Firmware Testing

Firmware is software that controls the operation of embedded hardware. It interacts with processors, memory, peripherals, sensors, actuators and communication interfaces.

Firmware testing is the systematic process of checking whether firmware behaves correctly under specified operating conditions.

Why Firmware Testing Is Important

  • Detects programming and logic errors.
  • Verifies correct peripheral configuration.
  • Checks communication reliability.
  • Identifies timing and synchronization problems.
  • Verifies system response to normal and abnormal inputs.
  • Reduces the risk of field failures.
  • Provides evidence that requirements have been satisfied.
Example: A temperature monitoring controller must read an ADC value, convert it into temperature, display the result and activate an alarm above a threshold. Each operation and the complete sequence must be tested.

2. Verification and Validation

2.1 Verification

Verification determines whether the firmware and its development outputs conform to specified requirements and design specifications.

It addresses the question: Are we building the product correctly?

2.2 Validation

Validation determines whether the completed system meets its intended use and user needs in the target operating environment.

It addresses the question: Are we building the right product?

VerificationValidation
Checks conformance to specifications.Checks suitability for intended use.
May include reviews, inspections and tests.Includes evaluation of the complete product in its intended environment.
Can occur throughout development.Often includes system-level acceptance activities.
Focuses on specified requirements.Focuses on actual operational needs.
Verification and validation are complementary activities. Passing a software test does not automatically establish that the complete hardware product is safe, reliable or suitable for its intended environment.

3. Firmware Testing Levels

Firmware testing is performed at different levels, beginning with individual software units and progressing to the complete embedded system.

3.1 Unit Testing

Unit testing checks an individual function, module or software component independently.

Examples:

  • Testing an ADC voltage conversion function.
  • Testing a temperature calculation function.
  • Testing a UART string-processing function.
  • Testing a checksum calculation function.

3.2 Integration Testing

Integration testing checks whether multiple modules work correctly when combined.

Examples:

  • ADC driver integrated with temperature processing.
  • UART driver integrated with a command parser.
  • Timer module integrated with an interrupt handler.
  • Sensor driver integrated with an LCD display module.

3.3 System Testing

System testing evaluates the complete embedded system against its functional and non-functional requirements.

Examples:

  • Complete temperature monitoring operation.
  • Motor speed control under different commands.
  • Communication between multiple system components.
  • Power-up, normal operation and fault recovery.

3.4 Acceptance Testing

Acceptance testing determines whether the delivered system meets the acceptance criteria agreed for its intended use.

Testing LevelMain Focus
UnitIndividual functions and modules
IntegrationInteraction between modules
SystemComplete system behaviour
AcceptanceCustomer or operational acceptance criteria

4. Functional and Non-Functional Testing

4.1 Functional Testing

Functional testing verifies what the system does.

  • Correct GPIO operation.
  • Correct sensor measurement.
  • Correct UART transmission and reception.
  • Correct interrupt response.
  • Correct motor-control command processing.

4.2 Non-Functional Testing

Non-functional testing evaluates how well the system operates.

  • Performance and response time.
  • Memory consumption.
  • Power consumption.
  • Reliability and stability.
  • Robustness under abnormal conditions.
  • Environmental and EMC performance.
A UART function may pass functional testing because it transmits the correct characters. Performance testing may additionally measure its throughput, timing and CPU usage.

5. Test Planning and Test Cases

A test plan defines the scope, approach, resources, environment and acceptance criteria for testing.

Typical Test Plan Contents

  • Features to be tested.

  • Hardware and software test environment.
  • Test methods and tools.
  • Pass/fail criteria.
  • Test schedule and responsibilities.
  • Defect reporting procedure.

7. Boundary Value Testing

Boundary value testing checks behaviour at, below and above important limits.

Example: ADC Result Range

The LPC2129 ADC is 10-bit, so the result range is 0 to 1023.

Test InputExpected Result Range
Minimum inputNear 0
Low inputLow ADC code
Mid-scale inputNear 512
High inputHigh ADC code
Maximum valid inputNear 1023

Example: Temperature Threshold

Assume an alarm activates when temperature exceeds 50°C.

  • 49°C: alarm should remain inactive.
  • 50°C: verify the exact comparison rule.
  • 51°C: alarm should activate.
Boundary testing should include the exact threshold because the implementation may use either greater-than (>) or greater-than-or-equal-to (>=) comparison.

8. Positive and Negative Testing

Positive Testing

Positive testing checks whether the system behaves correctly with valid inputs and normal operating conditions.

Negative Testing

Negative testing checks how the system handles invalid, unexpected or abnormal inputs and conditions.

ModulePositive TestNegative Test
UARTReceive a valid command.Receive an invalid command or malformed frame.
ADCMeasure a valid analog input.Handle an out-of-range input safely.
I2CCommunicate with a responding target.Handle a missing target or NACK.
TimerGenerate the expected match event.Handle unexpected or repeated events.
CANTransmit a valid frame.Handle bus errors and missing acknowledgements.

9. Regression Testing

Regression testing checks whether previously working functionality continues to work after a firmware change.

Why Regression Testing Is Required

  • A bug fix may affect another module.
  • A driver modification may change timing.
  • A compiler setting may change generated behaviour.
  • A new feature may consume additional memory.
  • A configuration change may affect peripheral operation.

Regression Testing Process

  1. Maintain a baseline of previously passing tests.
  2. Make the firmware modification.
  3. Build the new firmware.
  4. Run the relevant new tests.
  5. Run previously passing regression tests.
  6. Compare results with the baseline.
  7. Record and resolve failures.
Example: If the UART baud-rate calculation is modified, retest UART transmission, reception, command parsing and any application functions that depend on serial communication.

10. Firmware Test Coverage

Test coverage measures how much of a defined testing target has been exercised by the test suite.

10.1 Statement Coverage

Measures the proportion of executable statements executed by the tests.

Statement Coverage (%) =
    (Executed Statements / Total Statements) × 100

10.2 Branch Coverage

Measures whether each decision outcome, such as true and false, has been exercised.

10.3 Function Coverage

Measures whether the functions included in the coverage scope have been called.

10.4 Requirement Coverage

Measures whether each defined requirement is linked to one or more tests.

High code coverage does not prove that firmware is correct. Test quality, boundary conditions, requirement coverage, timing behaviour and fault handling are also important.

11. Static and Dynamic Analysis

11.1 Static Analysis

Static analysis examines source code without executing the program.

It can identify:

  • Potential null-pointer access.
  • Uninitialized variables.
  • Unreachable code.
  • Suspicious type conversions.
  • Possible buffer overflows.
  • Some concurrency and coding-standard violations.

11.2 Dynamic Analysis

Dynamic analysis examines firmware while it is executing or being tested.

Examples:

  • Runtime debugging.
  • Memory monitoring.
  • Execution-time measurement.
  • Stack usage analysis.
  • Runtime error detection.
  • Communication monitoring.
Static AnalysisDynamic Analysis
Examines source or compiled representations without running the target behaviour.Examines behaviour during execution.
Can detect certain defects early.Can expose runtime and integration faults.
Does not prove runtime correctness.Only covers exercised execution paths and conditions.

12. Hardware-in-the-Loop Testing

Hardware-in-the-Loop (HIL) testing connects the real embedded controller to a test system that simulates selected external components or physical processes in real time.

HIL Testing Architecture

     Test Computer
           |
     HIL Simulation
           |
    Signal Interface
           |
   Embedded Controller
           |
    Controller Outputs
           |
     HIL Simulation

Advantages

  • Tests firmware with real controller hardware.
  • Can simulate operating conditions that are difficult to reproduce physically.
  • Supports repeatable test scenarios.
  • Can test selected fault conditions.
  • Helps validate timing and interface behaviour.

Applications

  • Automotive electronic control units.
  • Industrial automation controllers.
  • Motor-control systems.
  • Power electronics controllers.
  • Safety-related embedded equipment.

13. Simulation and Emulation Testing

Simulation

Simulation uses a software model to represent selected processor, peripheral or system behaviour.

Emulation

Emulation uses hardware or a specialized platform to reproduce selected target-system behaviour for development and testing.

Keil uVision Debugging

  • Set breakpoints in firmware.
  • Execute code step by step.
  • Inspect CPU registers.
  • Monitor variables using Watch windows.
  • Inspect memory locations.
  • Observe supported peripheral registers.
  • Review compiler and linker output.
The Keil simulator is useful for code-level debugging and supported peripheral behaviour. It does not automatically reproduce every external device, electrical condition, analog signal, communication bus or real-time hardware effect.

14. Test Automation

Test automation uses scripts, test frameworks and tools to execute test cases and compare actual results with expected results.

Benefits

  • Repeatable test execution.
  • Reduced manual effort for repeated tests.
  • Faster regression testing.
  • Consistent result reporting.
  • Support for continuous integration workflows.

Typical Automated Test Flow

1. Build firmware
2. Check build result
3. Prepare test environment
4. Execute test cases
5. Capture output
6. Compare actual and expected results
7. Generate test report
8. Record failures

Example: Function-Level Test

#include 

int Add(int a, int b)
{
    return a + b;
}

int main(void)
{
    int result = Add(10, 20);

    if (result == 30)
    {
        printf("PASS\n");
    }
    else
    {
        printf("FAIL\n");
    }

    return 0;
}

Expected Result:

PASS

This is a simple host-side C test example. It demonstrates function-level testing and does not access LPC2129 hardware.

15. Defect Reporting and Tracking

A defect is an observed difference between actual behaviour and expected behaviour.

Defect Report Contents

  • Unique defect ID.
  • Firmware version and build information.
  • Test case ID.
  • Hardware configuration.
  • Steps to reproduce.
  • Expected result.
  • Actual result.
  • Severity and priority.
  • Logs, screenshots or measurements.
  • Assigned owner and resolution status.

Defect Severity

SeverityMeaning
CriticalMajor system failure or serious safety impact.
HighImportant function unavailable or seriously incorrect.
MediumFunction works with limitations or a workaround.
LowMinor issue with limited functional impact.

Severity describes the impact of a defect. Priority describes how urgently it should be addressed.

16. Reliability and Stress Testing

Reliability testing evaluates whether the embedded system continues to operate correctly over time and under specified operating conditions.

Common Reliability Tests

  • Long-duration operation testing.
  • Repeated power cycling.
  • Temperature testing.
  • Voltage variation testing within specified limits.
  • Communication load testing.
  • Memory and resource stress testing.
  • Fault injection and recovery testing.

Stress Testing

Stress testing applies demanding but defined operating conditions to identify weaknesses and failure limits.

Stress tests must use controlled limits and suitable equipment. Never apply arbitrary overvoltage, overcurrent or temperature conditions to a controller without an approved test procedure.

17. Firmware Testing Workflow

  1. Study system requirements.
  2. Prepare a test plan.
  3. Review the firmware architecture.
  4. Create unit test cases.
  5. Test individual software modules.
  6. Integrate and test the modules.
  7. Perform system-level testing.
  8. Execute boundary and negative tests.
  9. Measure timing, memory and power behaviour.
  10. Record and resolve defects.
  11. Perform regression testing.
  12. Complete validation and acceptance activities.
  13. Prepare the final test report.

19. Keil uVision Practical Exercises

Exercise 1: Unit-Level Debugging

  1. Open the LPC2129 project.
  2. Select a small function such as a bit-manipulation helper.
  3. Set a breakpoint.
  4. Run the program and inspect input and output variables.
  5. Compare the result with the expected value.

Exercise 2: Peripheral Register Verification

  1. Open the peripheral initialization code.
  2. Set a breakpoint after configuration.
  3. Inspect relevant register values.
  4. Compare them with the intended configuration.
  5. Record any mismatch.

Exercise 3: Regression Test Checklist

  1. Build the firmware.
  2. Run the previously prepared test cases.
  3. Check for compiler and linker errors.
  4. Compare expected and observed behaviour.
  5. Record failures and investigate their causes.
The user's Keil uVision workflow is simulator-only. Register inspection and successful compilation do not establish physical electrical performance, real communication with external devices or analog measurement accuracy.

20. Interview Questions and Answers

Q1. What is firmware testing?

It is the systematic process of checking embedded firmware against specified requirements and expected behaviour.

Q2. What is verification?

Verification checks whether development outputs conform to specified requirements.

Q3. What is validation?

Validation checks whether the completed system meets its intended use and user needs.

Q4. What is unit testing?

Unit testing checks an individual function or module independently.

Q5. What is integration testing?

Integration testing checks interactions between combined software modules or components.

Q6. What is system testing?

System testing evaluates the complete system against its requirements.

Q7. What is regression testing?

Regression testing checks that previously working functionality remains correct after changes.

Q8. What is boundary value testing?

It checks behaviour at and around important input limits and thresholds.

Q9. What is code coverage?

Code coverage measures how much of a defined code structure or execution behaviour has been exercised by tests.

Q10. What is static analysis?

Static analysis examines source code or compiled representations without executing the program.

Q11. What is HIL testing?

Hardware-in-the-Loop testing connects the real controller to a system that simulates selected external processes or components.

Q12. Why is regression testing important?

It helps detect unintended effects introduced by firmware modifications.

23. Lesson Summary

  • Firmware testing checks embedded software against expected behaviour.
  • Verification checks conformance to specifications.
  • Validation checks suitability for intended use.
  • Testing levels include unit, integration, system and acceptance testing.
  • Functional and non-functional testing cover different quality aspects.
  • Test cases define inputs, procedures and expected results.
  • Boundary and negative testing examine abnormal conditions.
  • Regression testing detects unintended effects of changes.
  • Coverage helps evaluate test completeness but does not prove correctness.
  • Static and dynamic analysis help identify different classes of defects.
  • HIL testing combines real controller hardware with simulated external conditions.
  • Test results and defects must be documented.
