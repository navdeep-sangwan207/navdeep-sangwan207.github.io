Learn how to document embedded hardware and firmware, maintain technical records, manage source code, control changes and support products throughout their operational life.

1. Introduction to Embedded System Documentation

Embedded system documentation is the collection of technical information that describes the design, implementation, operation, testing and maintenance of an embedded product.

Documentation allows developers, testers, technicians and maintenance engineers to understand how the system works and how to modify or troubleshoot it safely.

Why Documentation Is Important

  • Explains system architecture and functionality.
  • Helps developers understand existing firmware.
  • Supports hardware troubleshooting.
  • Improves collaboration between engineering teams.
  • Records design decisions and configuration details.
  • Supports testing, verification and validation.
  • Helps maintain products after their initial development.
  • Reduces dependency on individual developers.
Example: An engineer working on an LPC2129-based controller should be able to identify its clock configuration, GPIO assignments, UART settings, ADC channels, interrupt configuration and firmware version from the project documentation.

2. Types of Embedded System Documentation

2.1 Requirements Documentation

Describes what the embedded system must do and the constraints under which it must operate.

Typical contents:

  • Functional requirements.
  • Performance requirements.
  • Electrical requirements.
  • Communication requirements.
  • Environmental requirements.
  • Safety and reliability requirements.

2.2 System Architecture Documentation

Describes the major hardware and software components and their relationships.

  • System block diagram.
  • Processor and peripheral architecture.
  • Memory organization.
  • Communication interfaces.
  • Power architecture.
  • Firmware module relationships.

2.3 Hardware Documentation

  • Schematic diagrams.
  • PCB layout and fabrication files.
  • Bill of Materials (BOM).
  • Connector and pin assignments.
  • Power supply specifications.
  • Component datasheets.

2.4 Firmware Documentation

  • Source-code structure.
  • Function descriptions.
  • Header-file information.
  • Register configuration details.
  • Interrupt and task descriptions.
  • Build and compiler settings.

2.5 Testing Documentation

  • Test plans.
  • Test cases.
  • Expected and actual results.
  • Defect reports.
  • Verification and validation reports.

3. System Requirements Specification

A System Requirements Specification (SRS) defines the expected behaviour and constraints of the product.

Typical Requirements

Requirement TypeExample
FunctionalThe controller shall read a temperature sensor.
PerformanceThe measurement shall update at a specified interval.
ElectricalThe input voltage shall remain within the specified range.
CommunicationThe controller shall transmit data using UART.
ReliabilityThe controller shall recover from specified faults.
EnvironmentalThe product shall operate within its rated temperature range.

Good Requirement Characteristics

  • Clear and unambiguous.
  • Measurable or verifiable.
  • Consistent with other requirements.
  • Feasible to implement.
  • Traceable to design and test activities.

4. Hardware Design Documentation

Hardware documentation explains the electrical and physical design of the embedded system.

4.1 Circuit Schematic

A schematic shows the electrical connections between components.

It normally includes:

  • Microcontroller connections.
  • Power supply circuits.
  • Reset and clock circuits.
  • Sensor interfaces.
  • Communication transceivers.
  • Driver circuits.
  • Protection components.

5. Firmware Documentation

Firmware documentation describes the software architecture, source code, data flow and peripheral operations.

5.1 Source-Code Comments

Comments should explain the purpose of code, important design decisions and non-obvious behaviour.

/*
 * Function: ADC_Read
 * Purpose : Start an ADC conversion and return
 *           the 10-bit conversion result.
 * Input   : ADC channel number
 * Output  : ADC result
 *
 * Note:
 * This function assumes that the selected channel
 * and its pin configuration are already initialized.
 */

unsigned int ADC_Read(unsigned int channel)
{
    /* ADC conversion implementation */
}

5.2 Function Documentation

Function documentation should identify:

  • Function name.
  • Purpose.
  • Input parameters.
  • Return value.
  • Global variables used.
  • Hardware dependencies.
  • Possible errors or limitations.

5.3 Register Configuration Documentation

For each important peripheral, record the configured registers and explain the intended settings.

Example – Timer0 configuration:
  • PCLK: 15 MHz.
  • Prescaler register PR: 14999.
  • TC increment interval: 1 ms.
  • Match register MR0: application-dependent.
  • Match control: selected interrupt/reset/stop actions.

Benefits of Modular Organization

  • Improves readability.
  • Separates hardware access from application logic.
  • Simplifies testing.
  • Supports code reuse.
  • Reduces maintenance effort.
  • Helps teams work on different modules.

7. Version Control and Source-Code Management

Version control records changes to source code and allows developers to manage different revisions of a project.

Why Version Control Is Needed

  • Track source-code modifications.
  • Identify who changed a file and when.
  • Restore previous versions.
  • Support multiple developers.
  • Maintain release history.
  • Compare changes between revisions.

9. Firmware Maintenance

Firmware maintenance is the process of modifying, correcting or improving software after its initial delivery.

9.1 Corrective Maintenance

Fixes defects discovered after deployment.

Example: Correcting a UART communication fault.

9.2 Adaptive Maintenance

Modifies firmware to work with a changed environment or external dependency.

Example: Updating a driver to support a replacement sensor.

9.3 Perfective Maintenance

Improves performance, usability, maintainability or functionality.

Example: Optimizing a sensor-processing routine.

9.4 Preventive Maintenance

Reduces the likelihood of future problems by improving the system before a failure occurs.

Example: Refactoring complex code and improving fault handling.

Maintenance TypeMain Objective
CorrectiveFix existing faults.
AdaptiveAdjust to environmental or dependency changes.
PerfectiveImprove existing functionality.
PreventiveReduce future maintenance and failure risk.

10. Change Management

Change management is the controlled process of proposing, evaluating, approving, implementing and verifying modifications to a product.

Change Management Workflow

  1. Submit a change request.
  2. Describe the reason for the change.
  3. Evaluate technical and operational impact.
  4. Assess risks and affected requirements.
  5. Approve or reject the change.
  6. Implement the modification.
  7. Review and test the updated firmware.
  8. Perform regression testing.
  9. Update documentation.
  10. Release the approved revision.

Example Change Request

11. Configuration Management

Configuration management controls the versions and settings of hardware, software, tools and documentation that form a product.

Configuration Items

  • Firmware source code.
  • Hardware schematics.
  • PCB design files.
  • Compiler and IDE configuration.
  • Linker scripts and startup files.
  • Test procedures and results.
  • Release binaries.
  • Product documentation.

Configuration Baseline

A baseline is an approved and controlled reference configuration. Changes to it are managed through the defined change process.

A reproducible embedded firmware build requires more than saving the source files. Toolchain versions, compiler options, libraries, linker settings and target configuration should also be recorded.

12. Field Maintenance and Firmware Updates

Field maintenance involves supporting embedded products after installation or deployment.

Common Field Activities

  • Fault diagnosis.
  • Replacement of defective hardware.
  • Firmware updates.
  • Configuration changes.
  • Performance monitoring.
  • Preventive inspection.
  • Failure analysis.

Firmware Update Considerations

  • Verify the target device and firmware compatibility.
  • Protect the update process against power interruption.
  • Validate the firmware image before installation.
  • Maintain a recovery mechanism where required.
  • Preserve critical configuration and calibration data.
  • Record the installed firmware version.
Firmware updates can make a device unusable if interrupted or if an incompatible image is installed. Robust update systems should include integrity checks, recovery strategy and suitable access control.

13. Firmware Maintenance Challenges

  • Legacy source code with limited comments.
  • Unavailable original development tools.
  • Obsolete electronic components.
  • Undocumented hardware revisions.
  • Changes in sensor or peripheral behaviour.
  • Limited memory and processing resources.
  • Difficulty reproducing field failures.
  • Compatibility with earlier firmware versions.
  • Maintaining safety and regulatory requirements.

Ways to Reduce Maintenance Difficulty

  • Maintain source-code documentation.
  • Use modular firmware architecture.
  • Preserve build environments and release artifacts.
  • Maintain hardware revision records.
  • Keep test procedures current.
  • Use version control and change review.
  • Record known issues and workarounds.

Prepare a technical documentation package for an LPC2129-based sensor monitoring system.

  • Are peripheral settings recorded?

17. Interview Questions and Answers

Q1. What is embedded system documentation?

It is the technical record of system requirements, hardware, firmware, testing, configuration and maintenance information.

Q2. Why is documentation important?

It improves communication, troubleshooting, reproducibility and long-term maintenance.

Q3. What is an SRS?

A System Requirements Specification defines the expected system functionality and constraints.

Q4. What is a BOM?

A Bill of Materials is a list of components required to manufacture or assemble a product.

Q5. What is version control?

Version control records and manages changes to project files over time.

Q6. What is a firmware baseline?

It is an approved reference version of firmware and its associated configuration.

Q7. What is corrective maintenance?

It fixes faults identified in an existing product.

Q8. What is adaptive maintenance?

It modifies firmware to accommodate changes in the operating environment or dependencies.

Q9. What is preventive maintenance?

It reduces the likelihood of future failures by improving the system before a fault occurs.

Q10. What is change management?

It is the controlled process of evaluating, approving, implementing and verifying product changes.

Q11. Why should compiler settings be documented?

They help reproduce the firmware build and investigate differences between releases.

Q12. What is configuration management?

It controls the versions and settings of product components and their associated documentation.
