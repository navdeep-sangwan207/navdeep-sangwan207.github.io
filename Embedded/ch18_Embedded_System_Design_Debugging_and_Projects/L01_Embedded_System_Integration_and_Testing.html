Lesson 01: Embedded System Integration and Testing

Chapter 18: Embedded System Design, Debugging and Projects

Level: Advanced

Learn how individual hardware components, peripheral drivers and application software are combined into a complete embedded system and verified through systematic testing.

1. Introduction

An embedded system generally consists of a microcontroller, memory, sensors, actuators, communication interfaces, power circuits and firmware.

During development, these components are often designed and tested separately. However, a complete product requires all components to work together correctly.

The process of combining hardware modules, firmware modules and peripheral interfaces into one functional system is called embedded system integration.

After integration, the complete system is evaluated through testing to verify that it satisfies its functional and non-functional requirements.

Example: Consider an LPC2129-based temperature monitoring system. It may use:
  • ADC to measure an analog temperature sensor.
  • LCD to display the measured temperature.
  • UART to transmit readings to a computer.
  • GPIO to control an alarm output.
  • Timer to schedule periodic measurements.
All these modules must be integrated so that they operate correctly without interfering with one another.

2. Objectives of System Integration

  • Combine hardware and software components.
  • Verify communication between peripheral modules.
  • Identify pin multiplexing and resource conflicts.
  • Configure clocks and peripheral operating parameters.
  • Verify timing and execution requirements.
  • Detect integration faults.
  • Confirm that the complete system meets its requirements.

3. Embedded System Architecture

A typical embedded system can be divided into hardware, low-level firmware, peripheral drivers and application software. 

        +----------------------------------+
        |        Application Software      |
        |  Monitoring, Control, Processing |
        +----------------------------------+
        |        Peripheral Drivers        |
        | GPIO | ADC | UART | I2C | SPI    |
        +----------------------------------+
        |       Microcontroller Core       |
        |       ARM7 LPC2129 CPU           |
        +----------------------------------+
        |          Hardware               |
        | Sensors | LCD | Memory | Outputs |
        +----------------------------------+

3.1 Hardware Layer

Includes physical components such as:

  • Microcontroller and clock circuitry.
  • Power supply and reset circuitry.
  • Sensors and actuators.
  • LCD, keypad and external memory.
  • Communication transceivers and interface circuits.

3.2 Firmware Layer

Firmware controls the microcontroller and communicates with hardware through registers and peripheral drivers.

  • GPIO driver.
  • ADC driver.
  • Timer driver.
  • UART driver.
  • I2C, SPI and CAN drivers.
  • LCD and keypad drivers.

3.3 Application Layer

The application layer implements the actual product functionality using the peripheral drivers.

For example, a temperature controller reads ADC data, calculates temperature, updates an LCD and activates an alarm when a configured threshold is exceeded.

4. Hardware and Firmware Integration

4.1 Hardware Integration

Hardware integration involves connecting the microcontroller with external components and verifying their electrical and interface requirements.

  • Verify supply voltage and current requirements.
  • Check ground connections.
  • Verify clock and reset circuits.
  • Check sensor output ranges.
  • Verify GPIO voltage and current limits.
  • Check communication interface connections.
  • Verify pull-up and termination requirements.

4.2 Firmware Integration

Firmware integration combines individual software modules into a complete application.

  • Include the required header files.
  • Configure the system clock.
  • Initialize peripherals in a suitable sequence.
  • Connect driver functions to application logic.
  • Resolve shared-resource conflicts.
  • Compile, link and debug the complete firmware.
Hardware integration and firmware integration are related but different activities. Correct firmware cannot compensate for an incorrectly wired circuit, and correct hardware cannot compensate for faulty firmware.

6. System Clock Integration

Peripheral timing depends on the microcontroller clock configuration. Incorrect clock configuration can cause communication errors and incorrect timing.

Project clock configuration used in this course:

Clock Frequency
FOSC 12 MHz
CCLK 60 MHz
PCLK 15 MHz

Why Clock Configuration Matters

  • UART baud-rate generation depends on PCLK.
  • Timer counting depends on PCLK.
  • ADC conversion clock depends on PCLK and CLKDIV.
  • PWM timing depends on the peripheral clock.
  • SPI and I2C communication rates depend on clock configuration.
Timer example:

Given PCLK = 15 MHz and PR = 14999: 

TC frequency = PCLK / (PR + 1)

             = 15,000,000 / 15,000

             = 1000 Hz

TC increment interval = 1 / 1000

                      = 1 ms

Therefore, the timer counter increments once every nominal 1 ms in timer mode.

7. Integration Sequence

Integrating all modules at once makes fault identification difficult. A better approach is to integrate and verify modules progressively.

  1. Requirement analysis: Identify system functions and interfaces.
  2. Hardware verification: Check power, reset, clock and connections.
  3. Clock configuration: Establish the required CPU and peripheral clocks.
  4. GPIO verification: Test digital input and output configuration.
  5. Peripheral driver testing: Test ADC, timers and communication modules individually.
  6. Module integration: Connect peripheral drivers to application logic.
  7. Functional testing: Verify the required application behaviour.
  8. System testing: Test the integrated application under defined conditions.
  9. Documentation: Record test results and unresolved issues.

8. Types of Embedded System Testing

8.1 Unit Testing

Unit testing verifies one software module independently.

Examples:

  • Testing an ADC conversion function.
  • Testing a UART transmit function.
  • Testing a timer initialization function.

8.2 Integration Testing

Integration testing verifies whether multiple modules communicate and operate correctly together.

Examples:

  • ADC measurement displayed on LCD.
  • Timer event triggering an ADC measurement.
  • Sensor data transmitted through UART.

8.3 System Testing

System testing verifies the behaviour of the complete embedded application against its requirements.

Examples:

  • Verify complete sensor monitoring operation.
  • Verify alarm activation at a configured threshold.
  • Verify communication and display operation together.

8.4 Regression Testing

Regression testing repeats previously successful tests after firmware changes to check that existing functionality has not been broken.

8.5 Acceptance Testing

Acceptance testing determines whether the completed product satisfies the agreed customer or system requirements.

Testing Type Primary Focus
Unit Individual module
Integration Interaction between modules
System Complete application
Regression Previously working functionality
Acceptance Customer and system requirements

9. Functional and Non-Functional Testing

Functional Testing

Functional testing checks whether the system performs its specified operations.

  • ADC reads the selected input channel.
  • UART transmits the configured data.
  • LCD displays the required information.
  • GPIO changes state according to application logic.

Non-Functional Testing

Non-functional testing evaluates system characteristics such as performance, reliability, power consumption and timing behaviour.

  • Response time.
  • Execution time.
  • Memory utilization.
  • Power consumption.
  • Reliability and fault recovery.
  • Communication performance.

10. Test Plan and Test Cases

11. Example: Integrated LPC2129 Application

Consider a simplified monitoring application that:

  1. Reads a simulated sensor value.
  2. Processes the value in an application function.
  3. Determines whether an alarm condition exists.
  4. Updates a status output.

The following example demonstrates the application logic using a supplied test value. It does not access the physical ADC or prove that an external sensor is connected. 

#include <LPC21xx.h>

#define LED_PIN (1U << 5)
#define ALARM_THRESHOLD 600U

void GPIO_Init(void)
{
    /* Select GPIO function for P0.5 */
    PINSEL0 &= ~(3U << 10);

    /* Configure P0.5 as output */
    IODIR0 |= LED_PIN;

    /* Start with output LOW */
    IOCLR0 = LED_PIN;
}

void Process_Sensor_Value(unsigned int adc_value)
{
    if (adc_value > ALARM_THRESHOLD)
    {
        IOSET0 = LED_PIN;
    }
    else
    {
        IOCLR0 = LED_PIN;
    }
}

int main(void)
{
    unsigned int test_adc_value = 700U;

    GPIO_Init();

    /* Test application logic using a supplied value */
    Process_Sensor_Value(test_adc_value);

    while (1)
    {
        /* Application can process new readings here */
    }
}

Program Explanation

  • GPIO_Init() configures P0.5 as a GPIO output.
  • LED_PIN defines the output bit mask.
  • ALARM_THRESHOLD defines the comparison threshold.
  • Process_Sensor_Value() implements the application decision.
  • The supplied test value is 700, which is greater than 600.
  • The program therefore writes a HIGH state to the P0.5 output latch.
Expected logical result: 
Test ADC value       = 700
Alarm threshold     = 600
Comparison          = 700 > 600
Output latch action = IOSET0 bit 5
The result describes the GPIO register operation. It does not establish that a physical LED lights in the simulator.
This is an application-logic integration example, not a complete ADC driver. A real implementation must initialize the ADC, select the correct analog input, perform conversion, check the conversion result and pass the measured value to the processing function.

12. Integration Challenges and Common Faults

Problem Possible Cause Debugging Approach
Peripheral not working Incorrect PINSEL configuration Inspect pin function registers.
Incorrect UART baud rate Wrong PCLK or divisor Verify clock and baud-rate calculations.
Incorrect timer interval Incorrect PR or match value Check PCLK, PR, TC and MR settings.
ADC value incorrect Wrong channel or reference voltage Check channel selection and analog input range.
LCD not responding Incorrect wiring or initialization Check pin mapping and command sequence.
Intermittent communication Timing, electrical or protocol problem Inspect signal timing and peripheral status.
Unexpected output behaviour Shared pin or register conflict Review pin allocation and module ownership.

13. System-Level Debugging Techniques

  • Register inspection: Inspect peripheral configuration and status registers.
  • Breakpoints: Stop program execution at selected instructions.
  • Single stepping: Execute instructions one at a time.
  • Watch variables: Observe application variables and counters.
  • Logging: Record events and errors through an appropriate debug interface.
  • Module isolation: Temporarily disable unrelated modules to identify faults.
  • Boundary testing: Test minimum, maximum and threshold input values.

A useful debugging strategy is to reproduce the problem, isolate the affected module, inspect its inputs and outputs, identify the root cause, apply a correction and repeat the relevant tests.

14. Keil uVision Simulator Practice

The LPC2129 course uses Keil uVision simulator-based development. You can use it to practice firmware execution and inspect supported processor and peripheral registers.

Suggested Procedure

  1. Create or open an LPC2129 project.
  2. Add the required source and header files.
  3. Compile and resolve errors.
  4. Start the debugger.
  5. Set breakpoints in initialization functions.
  6. Inspect PINSEL0, IODIR0 and IOSET0/IOCLR0.
  7. Inspect application variables in the Watch window.
  8. Step through the application logic.
  9. Record the observed register and variable values.
Simulator limitation: Peripheral simulation support depends on the selected Keil device model. Register inspection and successful code execution do not prove external LCD, keypad, sensor, UART, I2C, SPI, CAN or analog hardware operation. Physical timing, voltage levels, electrical connections and signal quality require suitable hardware and instruments.

15. Best Practices for Embedded System Integration

  • Prepare a hardware block diagram before implementation.
  • Maintain a peripheral and pin allocation table.
  • Verify the clock tree before configuring peripherals.
  • Test each driver independently before integration.
  • Use modular and reusable firmware functions.
  • Define clear interfaces between software modules.
  • Use meaningful error codes and diagnostic information.
  • Test boundary conditions and failure scenarios.
  • Keep test results and firmware versions documented.
  • Repeat regression tests after changes.

16. Interview Questions and Answers

Q1. What is embedded system integration?

It is the process of combining hardware components, peripheral drivers and application software into one functional embedded system.

Q2. What is the difference between unit testing and integration testing?

Unit testing verifies an individual module independently. Integration testing verifies communication and interaction between multiple modules.

Q3. Why is clock configuration important?

Peripheral timing and communication rates depend on the clock configuration. An incorrect clock can produce incorrect baud rates, timer intervals and ADC clock rates.

Q4. What is regression testing?

Regression testing checks that previously working functionality remains correct after firmware changes.

Q5. What is system testing?

System testing evaluates the complete integrated application against its specified requirements.

Q6. Why is pin allocation important?

Microcontroller pins can support multiple functions. Incorrect allocation can cause peripheral conflicts and prevent interfaces from operating correctly.

Q7. What is the purpose of a test plan?

A test plan defines the scope, test procedures, resources, expected results and acceptance criteria for testing.

Q8. What is root-cause analysis?

Root-cause analysis identifies the underlying reason for a failure instead of merely correcting its visible symptoms.

Q9. What is the difference between functional and non-functional testing?

Functional testing checks required operations. Non-functional testing evaluates characteristics such as timing, memory, reliability and power consumption.

Q10. Can a simulator completely replace hardware testing?

No. A simulator is useful for firmware execution and debugging, but physical hardware testing is necessary to verify electrical behaviour, real peripheral interfaces and actual environmental performance.

20. Lesson Summary

  • System integration combines hardware and firmware modules.
  • Peripheral drivers connect application software to hardware.
  • Pin allocation and clock configuration are essential.
  • Integration should proceed in controlled stages.
