1. Introduction

Embedded firmware interacts directly with microcontroller hardware. Errors in firmware can cause incorrect peripheral operation, unexpected outputs, communication failures or system instability.

Debugging is the process of identifying, analyzing and correcting errors in a program. Optimization improves program performance, memory usage, execution efficiency and resource utilization.

Debugging: Finding and correcting errors in firmware.

Optimization: Improving firmware efficiency while preserving the required functionality and correctness.

2. Types of Errors in Embedded C

2.1 Syntax Errors

Syntax errors occur when the program violates the grammar rules of the C language. 

int main(void)
{
    int a = 10

    return 0;
}

The semicolon is missing after the declaration of variable a.

2.2 Compilation Errors

Compilation errors occur when the compiler cannot translate the source code because of problems such as invalid declarations, incompatible types or missing definitions.

2.3 Linker Errors

Linker errors occur when the linker cannot resolve required symbols or construct the final program image.

Example:

void LED_On(void);

int main(void)
{
    LED_On();

    return 0;
}

If no linked source file defines LED_On(), the linker may report an unresolved symbol.

2.4 Runtime Errors

Runtime errors occur while the program executes.

  • Invalid memory access.
  • Incorrect pointer usage.
  • Unexpected program state.
  • Stack overflow.
  • Incorrect peripheral configuration.

2.5 Logical Errors

Logical errors occur when the program executes but produces an incorrect result. 

if (temperature > 50)
{
    /* High temperature action */
}
else
{
    /* Normal operation */
}

If the intended threshold was 60 degrees, the comparison contains a logical error.

3. Common Embedded Firmware Problems

Problem Possible Cause
GPIO not responding Incorrect PINSEL or IODIR configuration.
UART communication failure Incorrect baud rate, pin selection or frame configuration.
Incorrect timer interval Wrong peripheral clock or prescaler calculation.
ADC result incorrect Incorrect channel, pin selection or conversion configuration.
Interrupt not executing Incorrect interrupt source, VIC setup or acknowledgement.
Program stops unexpectedly Invalid memory access, exception or stack problem.

4. Compiler Warnings and Their Importance

A compiler warning indicates a potentially unsafe or unintended coding condition. The program may still compile, but the warning should be investigated.

Example: Unused Variable

int main(void)
{
    int count = 10;

    return 0;
}

A compiler may warn that count is declared but never used.

Example: Missing Return Statement

int Calculate(void)
{
    int result = 10;
}

The function has an integer return type but does not return a value.

Recommended Practices

  • Read all compiler warnings.
  • Correct warnings instead of ignoring them.
  • Use meaningful variable names.
  • Check data types and signedness.
  • Initialize variables before use.
  • Enable appropriate compiler warning levels.
A warning-free build is a useful quality goal, although it does not prove that firmware is logically correct or free from runtime faults.

7. Breakpoints

A breakpoint is a debugging instruction that pauses program execution at a specified location.

Breakpoints help developers:

  • Inspect program execution at a particular statement.
  • Verify variable values.
  • Trace function calls.
  • Identify incorrect program flow.
  • Examine peripheral configuration sequences.

Example

int main(void)
{
    int count = 0;

    count = count + 1;

    count = count + 1;

    count = count + 1;

    while (1)
    {
    }
}

Place a breakpoint on the second assignment to inspect the value of count before and after execution.

Breakpoints are particularly useful for investigating unexpected state changes and incorrect register initialization.

8. Single-Step Execution

Single-step execution allows a developer to execute a program one source statement or machine instruction at a time.

Common Debugging Operations

Operation Purpose
Step Into Enter a function when it is called.
Step Over Execute a function call without entering its body.
Step Out Continue execution until the current function returns.
Run Execute until a breakpoint or stop condition.

These operations help developers understand the order in which firmware statements execute.

9. Watch Window

A watch window allows the developer to monitor the values of selected variables and expressions during debugging.

Example

unsigned int temperature = 25U;
unsigned int threshold = 40U;
unsigned int alarm = 0U;

void Check_Temperature(void)
{
    if (temperature > threshold)
    {
        alarm = 1U;
    }
    else
    {
        alarm = 0U;
    }
}

The watch window can be used to inspect:

  • temperature
  • threshold
  • alarm

The developer can observe how the variables change as the program executes.

10. Register Inspection

Embedded firmware interacts with hardware through memory-mapped peripheral registers. Inspecting these registers is an important debugging technique.

LPC2129 GPIO Registers

Register Purpose
PINSEL0 Selects pin functions for supported pins.
IODIR0 Configures GPIO direction.
IOPIN0 Reads the port pin levels.
IOSET0 Sets selected output latch bits.
IOCLR0 Clears selected output latch bits.

Example

#include <LPC21xx.h>

#define LED_MASK (1U << 5)

void GPIO_Init(void)
{
    PINSEL0 &= ~(3U << 10);

    IODIR0 |= LED_MASK;

    IOCLR0 = LED_MASK;
}

During debugging, inspect PINSEL0, IODIR0 and IOCLR0 to verify the intended register configuration and output-latch operation.

Register visibility and peripheral simulation depend on the selected Keil device model and simulator support. A register value alone does not prove that a physical external signal changed.

11. UART-Based Debugging

UART communication can be used to send diagnostic messages from firmware to a serial terminal.

Typical diagnostic information includes:

  • System startup messages.
  • Sensor readings.
  • Peripheral initialization status.
  • Application state changes.
  • Error codes.

Conceptual Example

void Application_Task(void)
{
    /* Read input */

    /* Process input */

    /* Send diagnostic information using UART */

    /* Update output */
}
UART debugging is useful when a debugger is unavailable or when diagnostic information needs to be observed during normal execution.

12. Firmware Optimization

Firmware optimization improves the use of processor time, memory and other hardware resources.

Main Optimization Areas

  • Execution time optimization.
  • Code size optimization.
  • RAM usage optimization.
  • Flash memory optimization.
  • Power consumption optimization.
Optimization should preserve functional correctness, timing requirements and system reliability. Faster code is not automatically better if it violates real-time requirements.

13. Code Size Optimization

Code size optimization reduces the amount of program memory required by firmware.

Common Techniques

  • Remove unused functions and variables.
  • Avoid unnecessary duplicated code.
  • Use appropriate compiler optimization settings.
  • Choose suitable data types.
  • Review large lookup tables.
  • Avoid unnecessary library dependencies.

Example: Repeated Code

void Task_A(void)
{
    /* Same initialization code */
}

void Task_B(void)
{
    /* Same initialization code */
}

If the same operation is genuinely required in both places, a shared function may improve maintainability and can reduce duplicated code. 

void Common_Init(void)
{
    /* Shared initialization code */
}

void Task_A(void)
{
    Common_Init();
}

void Task_B(void)
{
    Common_Init();
}
Compiler optimization and function inlining can affect the final code size. Always inspect the generated build output rather than assuming a source-level change reduces memory usage.

14. RAM Optimization

RAM is used for global variables, static variables, stack, heap and other runtime data.

Optimization Techniques

  • Remove unused variables.
  • Use suitable data types.
  • Avoid unnecessary large local arrays.
  • Limit dynamic memory allocation in constrained systems.
  • Review stack requirements.
  • Reuse buffers when their lifetimes do not overlap.
  • Place constant data in appropriate memory sections.

Example

unsigned int sensor_value;

/* Use a suitable range for the variable */
unsigned char status_flag;

A smaller data type may reduce memory usage when its range is sufficient. However, the actual benefit depends on alignment, ABI rules and compiler behavior.

15. Execution Time Optimization

Execution time optimization reduces the time required to perform important firmware operations.

Common Techniques

  • Avoid unnecessary calculations inside frequently executed loops.
  • Use efficient algorithms.
  • Reduce unnecessary function calls where appropriate.
  • Use hardware peripherals for timing and repetitive operations.
  • Optimize interrupt service routines.
  • Avoid excessive busy waiting.

Example: Repeated Calculation

while (1)
{
    unsigned int mask = (1U << 5);

    /* Use mask */
}

If the mask is constant, it can be defined outside the loop. 

#define LED_MASK (1U << 5)

while (1)
{
    /* Use LED_MASK */
}
Compilers may already optimize constant expressions. The main benefit of the named constant is improved readability and consistent configuration.

16. Compiler Optimization Levels

Embedded C compilers provide optimization options that control how aggressively the compiler transforms the program.

Optimization Level General Purpose
O0 Little or no optimization; useful for initial debugging.
O1 Basic optimization.
O2 More extensive performance optimization.
Os Optimization focused on reducing code size.
Exact options and behavior depend on the selected compiler version. Debugging optimized code can be more difficult because statements may be reordered, combined or removed.

17. Importance of volatile During Debugging and Optimization

The volatile qualifier is important when a variable can change outside the normal flow of execution visible to the compiler.

Typical examples include:

  • Memory-mapped hardware registers.
  • Variables modified by interrupt service routines.
  • Variables shared with certain hardware or external agents.

Example

volatile unsigned int event_flag = 0U;

void Timer_ISR(void)
{
    event_flag = 1U;
}

int main(void)
{
    while (1)
    {
        if (event_flag)
        {
            event_flag = 0U;

            /* Process event */
        }
    }
}

Volatile tells the compiler that accesses to event_flag must account for changes that may occur outside the visible control flow.

Volatile does not guarantee atomicity, mutual exclusion, event counting or safe synchronization. Shared data may need additional protection, depending on the processor and application.

18. Debugging Versus Optimization

Debugging Optimization
Finds and corrects defects. Improves resource efficiency.
Uses breakpoints and watch windows. Uses compiler settings and code analysis.
Focuses on correctness. Focuses on performance and resource usage.
Examines program behavior. Examines execution time and memory consumption.

Debugging and optimization are complementary activities. Firmware should be verified for correctness before and after optimization.

19. Practical LPC2129 Debugging Exercise

Objective

Configure P0.5 as an output and inspect GPIO register operations in Keil uVision.

Program

#include <LPC21xx.h>

#define LED_MASK (1U << 5)

void GPIO_Init(void)
{
    /* Configure P0.5 as GPIO */
    PINSEL0 &= ~(3U << 10);

    /* Configure output direction */
    IODIR0 |= LED_MASK;
}

int main(void)
{
    GPIO_Init();

    while (1)
    {
        IOSET0 = LED_MASK;

        IOCLR0 = LED_MASK;
    }
}

Debugging Procedure

  1. Create an LPC2129 project in Keil uVision.
  2. Add the program to the project.
  3. Build the program.
  4. Start the simulator debug session.
  5. Set a breakpoint inside GPIO_Init().
  6. Step through the PINSEL0 configuration.
  7. Inspect the IODIR0 register.
  8. Set a breakpoint inside the infinite loop.
  9. Inspect the IOSET0 and IOCLR0 register writes.
  10. Continue execution and observe the repeated operations.
Expected register-level result: P0.5 is configured for GPIO operation and output direction. The program repeatedly writes to the set and clear registers for bit 5.
Because the loop has no delay, the output-latch writes occur rapidly. The simulator may not display every intermediate operation at normal execution speed. Use breakpoints and single-step execution to inspect them. This exercise does not verify physical LED operation.

20. Embedded Firmware Debugging Best Practices

  • Build firmware frequently during development.
  • Read and resolve compiler warnings.
  • Use meaningful function and variable names.
  • Test peripheral initialization separately.
  • Use breakpoints to trace program flow.
  • Inspect hardware registers when debugging peripheral issues.
  • Use UART diagnostic messages when appropriate.
  • Verify clock and peripheral configuration calculations.
  • Check stack and memory usage.
  • Retest firmware after compiler optimization changes.
  • Document known limitations and test results.

21. Interview Questions and Answers

Q1. What is debugging?

Debugging is the process of identifying, analyzing and correcting software defects.

Q2. What is firmware optimization?

It is the process of improving code execution, memory usage and resource efficiency while preserving required behavior.

Q3. What is a breakpoint?

A breakpoint pauses program execution at a specified location for inspection.

Q4. What is the purpose of a watch window?

It allows developers to monitor variable values and expressions during debugging.

Q5. What is register inspection?

It is the process of examining processor or peripheral register values to verify hardware configuration and program behavior.

Q6. What is the difference between a compiler error and a warning?

An error generally prevents successful compilation, whereas a warning identifies a potentially problematic condition that may still allow compilation to continue.

Q7. What is code size optimization?

It reduces the amount of program memory required by firmware.

Q8. What is RAM optimization?

It reduces unnecessary RAM usage by managing variables, buffers, stack requirements and memory allocation efficiently.

Q9. Why is volatile important in embedded systems?

It prevents the compiler from assuming that a volatile object remains unchanged between accesses when external changes are possible.

Q10. Why can optimization make debugging difficult?

Optimization can change instruction ordering, remove redundant operations and make source statements difficult to correlate with machine instructions.
