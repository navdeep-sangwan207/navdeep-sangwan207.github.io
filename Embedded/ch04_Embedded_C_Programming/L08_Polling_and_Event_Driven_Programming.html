Lesson 08: Polling and Event-Driven Programming

Chapter 04 – Embedded C Programming

Embedded Systems – Complete Study Course

1. Introduction

Embedded systems continuously interact with hardware peripherals such as sensors, switches, timers, UART modules and communication controllers.

The microcontroller must detect when a peripheral requires attention and execute the appropriate operation.

Two commonly used approaches are polling and event-driven programming.

Polling: The CPU repeatedly checks a hardware status or condition to determine whether an event has occurred.

Event-driven programming: Program execution responds to events when they occur, commonly through interrupts or event notifications.

2. What Is Polling?

Polling is a programming technique in which the processor repeatedly checks the status of a peripheral or input condition.

The CPU continues checking until the required condition becomes true.

Basic Polling Flow

       Start
         |
         v
   Read Peripheral
       Status
         |
         v
   Is Event Ready?
      /       \
    No         Yes
    |           |
    |           v
    |       Process Event
    |           |
    +-----------+
         |
         v
     Repeat

Example Applications

  • Checking whether a switch is pressed.
  • Checking UART transmission readiness.
  • Waiting for ADC conversion completion.
  • Checking a timer match flag.
  • Reading sensor status registers.

3. Polling Using Embedded C

A polling loop can continuously check a status register until a particular bit becomes set.

General Example

#include <LPC21xx.h>

int main(void)
{
    while (1)
    {
        if (IOPIN0 & (1U << 10))
        {
            /* Input condition detected */
        }
        else
        {
            /* Input condition not detected */
        }
    }
}

This example repeatedly reads the state of P0.10. It assumes the pin has been configured appropriately as a GPIO input.

Polling frequency depends on the execution time of the loop and other work performed by the CPU. A fast polling loop can detect changes quickly, but it consumes processor time.

4. What Is Busy Waiting?

Busy waiting is a form of polling in which the CPU continuously executes a loop while waiting for a condition to become true.

Example

while ((status_register & 0x01U) == 0U)
{
    /* Wait continuously */
}

The CPU repeatedly reads the status register. It does not perform another useful task inside this loop.

Characteristics

  • Simple to implement.
  • Consumes CPU processing time.
  • Can provide a straightforward waiting mechanism.
  • May increase power consumption.
  • Can delay other software activities.
Busy waiting is useful for short waits or simple peripheral operations, but it is generally unsuitable for long waits in systems with multiple responsibilities.

5. Types of Polling

5.1 Continuous Polling

The CPU continuously checks a condition without introducing a deliberate waiting interval. 

while (1)
{
    if (event_detected())
    {
        process_event();
    }
}

5.2 Periodic Polling

The CPU checks a condition at fixed or approximately fixed intervals. 

while (1)
{
    check_sensor();

    delay_ms(10);
}

Periodic polling can reduce unnecessary repeated checks, but the detection time is limited by the polling interval.

5.3 Sequential Polling

The CPU checks several peripherals one after another. 

while (1)
{
    check_uart();
    check_switch();
    check_timer();
    check_sensor();
}

A condition checked later in the sequence may experience a longer response delay.

6. Advantages and Disadvantages of Polling

Advantages Disadvantages
Simple program structure. CPU time is consumed checking conditions.
Easy to debug. May waste processing resources.
Suitable for simple applications. Response time depends on polling frequency.
Does not require interrupt configuration. Long waits can block other operations.
Useful for predictable periodic checks. May miss short events if they are not latched or sampled appropriately.

7. What Is Event-Driven Programming?

Event-driven programming is a programming approach in which the execution of a task is triggered by an event.

An event may be generated by hardware, a timer, a communication peripheral, or another software component.

Examples of Events

  • External switch press.
  • Timer match event.
  • UART data reception.
  • ADC conversion completion.
  • Communication packet reception.
  • Sensor threshold detection.

Basic Event-Driven Flow

      System Running
            |
            v
      Wait for Event
            |
            v
       Event Occurs
            |
            v
     Event Notification
            |
            v
      Handle the Event
            |
            v
       Continue Work

In a microcontroller, an interrupt can notify the processor that a hardware event requires attention.

8. Interrupt-Based Event Handling

An interrupt is a signal that requests the CPU to temporarily suspend its normal execution and execute an interrupt service routine (ISR).

The ISR handles the event, performs the necessary short operation and returns control to the interrupted program.

Interrupt-Based Flow

       Main Program
            |
            v
      Normal Execution
            |
            v
      Hardware Event
            |
            v
     Interrupt Request
            |
            v
       Execute ISR
            |
            v
      Return from ISR
            |
            v
      Resume Main Program

Example: Interrupt Event Flag

#include <LPC21xx.h>

volatile unsigned int event_flag = 0U;

void Timer_ISR(void)
{
    event_flag = 1U;

    /* Acknowledge the actual timer interrupt
       using the appropriate timer and VIC setup. */
}

int main(void)
{
    while (1)
    {
        if (event_flag != 0U)
        {
            event_flag = 0U;

            /* Process the timer event */
        }

        /* Other main-program work */
    }
}
This is an event-flag programming pattern, not a complete LPC2129 interrupt configuration. The timer, VIC, vector, interrupt acknowledgement and ISR registration must also be configured.

9. Event Flags

An event flag is a variable used to indicate that a particular event has occurred.

An ISR or event producer sets the flag. The main program checks the flag and processes the event.

Example

volatile unsigned int uart_event = 0U;

/* Called when UART reception is handled */
void UART_Event_Handler(void)
{
    uart_event = 1U;
}

int main(void)
{
    while (1)
    {
        if (uart_event != 0U)
        {
            uart_event = 0U;

            /* Process received data */
        }
    }
}

Why Use Event Flags?

  • Separate event detection from event processing.
  • Keep interrupt service routines short.
  • Allow the main program to perform other work.
  • Improve software organization.
A single Boolean-style flag can lose repeated events if another event occurs before the previous one is processed. Use a counter, queue, hardware buffer or suitable synchronization mechanism when every event must be preserved.

10. Polling vs Event-Driven Programming

Polling Event-Driven Programming
CPU repeatedly checks a condition. Execution responds to event notifications.
May consume CPU time continuously. Can avoid repeated checking for supported events.
Response depends on polling interval and execution order. Response depends on interrupt or notification latency and scheduling.
Generally simpler to implement. Requires event and concurrency management.
Useful for simple peripheral checks. Useful for asynchronous hardware events.
Can be blocking. Can allow the main program to perform other work.

11. Hybrid Approach

Many embedded applications combine polling and event-driven techniques.

For example, an interrupt may indicate that a UART message has arrived. The main program can then process the received message using a buffer. Other non-critical sensors may be checked periodically.

Hybrid System Example

while (1)
{
    /* Process events reported by interrupts */
    if (uart_event_flag != 0U)
    {
        uart_event_flag = 0U;
        process_uart_data();
    }

    /* Periodically check a sensor */
    check_sensor();

    /* Perform other application tasks */
    update_application();
}
A hybrid design can balance responsiveness, simplicity and processor utilization.

12. Practical Example: Switch Monitoring

Objective

Demonstrate polling of a GPIO input using the LPC2129.

Program

#include <LPC21xx.h>

int main(void)
{
    /* Select GPIO for P0.10 */
    PINSEL0 &= ~(3U << 20);

    /* Configure P0.10 as input */
    IODIR0 &= ~(1U << 10);

    /* Select GPIO for P0.5 */
    PINSEL0 &= ~(3U << 10);

    /* Configure P0.5 as output */
    IODIR0 |= (1U << 5);

    while (1)
    {
        if ((IOPIN0 & (1U << 10)) != 0U)
        {
            IOSET0 = (1U << 5);
        }
        else
        {
            IOCLR0 = (1U << 5);
        }
    }
}

Program Explanation

  1. P0.10 is configured as GPIO input.
  2. P0.5 is configured as GPIO output.
  3. The program continuously reads P0.10.
  4. If the input reads HIGH, the P0.5 output latch is set.
  5. If the input reads LOW, the P0.5 output latch is cleared.
This example assumes the input signal is externally defined and electrically valid. No switch wiring, pull-up or pull-down circuit is simulated by this code. In Keil uVision, inspect the GPIO register-level operations rather than assuming physical switch or LED behavior.

13. Practical Example: Event Flag Processing

Objective

Demonstrate how an event flag separates event notification from application processing.

Program

#include <stdio.h>

volatile unsigned int event_flag = 0U;

void simulate_event(void)
{
    event_flag = 1U;
}

int main(void)
{
    simulate_event();

    if (event_flag != 0U)
    {
        event_flag = 0U;

        printf("Event received and processed\n");
    }

    return 0;
}

Expected Result

Event received and processed
Result: The program demonstrates event-flag handling. The function simulates an event through an ordinary software call; it does not generate a hardware interrupt.

15. Common Mistakes

  • Using continuous polling for every peripheral without considering CPU utilization.
  • Assuming event-driven programming always has zero response latency.
  • Performing lengthy operations inside an ISR.
  • Forgetting to acknowledge a peripheral interrupt.
  • Sharing variables between an ISR and main code without appropriate synchronization.
  • Using one event flag when multiple events must be retained.
  • Assuming volatile makes shared operations atomic.
  • Ignoring switch bounce when implementing mechanical switch inputs.

16. Interview Questions and Answers

Q1. What is polling?

Polling is a technique in which the CPU repeatedly checks a peripheral or condition to detect an event.

Q2. What is busy waiting?

Busy waiting is continuously executing a loop while waiting for a particular condition.

Q3. What is event-driven programming?

It is a programming approach in which tasks are performed in response to events.

Q4. What is an ISR?

An Interrupt Service Routine is a function executed to handle a configured interrupt.

Q5. What is an event flag?

An event flag is a variable used to indicate that an event has occurred and requires processing.

Q6. What is the main disadvantage of polling?

It can waste CPU processing time by repeatedly checking conditions.

Q7. Why should an ISR be short?

A short ISR reduces interrupt latency for other work and allows the main program to resume sooner.

Q8. What is a hybrid approach?

It combines polling and event-driven mechanisms within the same embedded application.

Q9. Can polling miss an event?

Yes. A short event can occur between polling samples unless hardware latches or stores it.

Q10. When should interrupts be preferred?

Interrupts are useful for asynchronous events that require timely handling without continuous CPU polling.

17. Multiple Choice Questions (MCQs)

1. What is polling?
  1. Repeatedly checking a condition
  2. Generating a clock
  3. Writing to Flash memory
  4. Compiling a program

Answer: A – Repeatedly checking a condition.

2. What is busy waiting?
  1. CPU sleeps until an event
  2. CPU repeatedly executes a waiting loop
  3. DMA transfers data
  4. CPU enters reset mode

Answer: B – CPU repeatedly executes a waiting loop.

3. Which technique responds to event notifications?
  1. Event-driven programming
  2. Busy waiting only
  3. Static linking
  4. Memory allocation

Answer: A – Event-driven programming.

4. Which function handles a hardware interrupt?
  1. main()
  2. ISR
  3. printf()
  4. malloc()

Answer: B – ISR.

5. What is the purpose of an event flag?
  1. Store program instructions
  2. Indicate that an event occurred
  3. Configure the clock
  4. Generate PWM

Answer: B – Indicate that an event occurred.

6. Which approach can consume CPU time continuously?
  1. Busy waiting
  2. Event notification
  3. Interrupt-driven waiting
  4. CPU sleep

Answer: A – Busy waiting.

7. What should an ISR generally avoid?
  1. Setting a flag
  2. Acknowledging an interrupt
  3. Long blocking operations
  4. Capturing essential event data

Answer: C – Long blocking operations.

8. What is a hybrid approach?
  1. Only polling
  2. Only interrupts
  3. Combining polling and event-driven methods
  4. Only software delays

Answer: C – Combining polling and event-driven methods.

19. Lesson Summary

  • Polling repeatedly checks a peripheral or condition.
  • Busy waiting consumes CPU time while waiting.
  • Event-driven programming responds to events.
  • Interrupts are commonly used for hardware event notification.
  • Event flags separate event detection from event processing.
  • ISRs should generally perform short, bounded operations.
  • Volatile does not provide atomicity or synchronization.
  • Hybrid designs combine polling and event-driven techniques.
