1. Introduction

As embedded firmware becomes larger, writing the entire program inside one source file becomes difficult to maintain, debug and extend.

Modular programming solves this problem by dividing firmware into smaller, independent modules. Each module performs a specific function and communicates with other modules through defined interfaces.

In Embedded C, modules are commonly organized using source files (.c) and header files (.h).

Definition: Modular programming is a software design approach in which a large program is divided into smaller functional modules with clearly defined interfaces.

2. What Is a Source File?

A source file is a file containing C program implementation, including function definitions, variable definitions and executable statements.

Source files generally use the .c extension.

Example: gpio.c

#include <LPC21xx.h>
#include "gpio.h"

void GPIO_Init(void)
{
    PINSEL0 &= ~(3U << 10);
    IODIR0 |= (1U << 5);
}

void GPIO_SetPin(unsigned int pin)
{
    IOSET0 = (1U << pin);
}

void GPIO_ClearPin(unsigned int pin)
{
    IOCLR0 = (1U << pin);
}

The file contains the actual implementation of GPIO-related functions.

3. What Is a Header File?

A header file contains declarations and definitions that need to be shared between source files.

Header files generally use the .h extension.

Example: gpio.h

#ifndef GPIO_H
#define GPIO_H

void GPIO_Init(void);

void GPIO_SetPin(unsigned int pin);

void GPIO_ClearPin(unsigned int pin);

#endif

This header file declares the GPIO functions. Other source files can include it to use these functions.

A function declaration tells the compiler about a function's name, return type and parameters. Its implementation normally appears in a source file.

4. Difference Between .c and .h Files

Source File (.c) Header File (.h)
Contains function implementations. Contains function declarations.
Contains executable statements. Contains shared declarations and definitions.
Compiled as a translation unit. Usually included by source files.
Examples: gpio.c, uart.c. Examples: gpio.h, uart.h.
The header file describes the module interface. The source file implements that interface.

5. Function Declaration and Function Definition

A function declaration specifies how a function can be called. A function definition provides its implementation.

Function Declaration

void LED_On(void);

Function Definition

void LED_On(void)
{
    IOSET0 = (1U << 5);
}

Function Call

LED_On();

These three operations have different purposes:

  • Declaration: informs the compiler about the function.
  • Definition: provides the function implementation.
  • Call: requests execution of the function.

6. The #include Directive

The preprocessor directive #include inserts the contents of a specified header file into the source file during preprocessing.

System Header

#include <LPC21xx.h>

Project Header

#include "gpio.h"
Syntax Typical Usage
<header.h> Compiler or toolchain-provided headers.
"header.h" Project or local headers.

The compiler's configured include search paths determine where header files are located.

7. Include Guards

A header file may be included by multiple source files or indirectly through other headers. Repeated inclusion can cause redefinition errors if the header contains definitions that should appear only once in a translation unit.

Include guards prevent the same header contents from being processed more than once in a single translation unit.

Example

#ifndef UART_H
#define UART_H

void UART0_Init(void);

void UART0_SendChar(char data);

void UART0_SendString(const char *str);

#endif

How It Works

  1. #ifndef UART_H checks whether UART_H is not defined.
  2. #define UART_H defines the guard macro.
  3. The header contents are processed.
  4. #endif closes the conditional block.
  5. Later inclusions skip the guarded contents.
Include guards are a standard and widely used technique for preventing repeated header inclusion.

8. Modular Programming in Embedded Systems

Embedded firmware can be divided according to hardware peripherals and application functions.

Common Modules

Module Responsibility
GPIO Digital input and output operations.
UART Serial communication.
Timer Timer configuration and timing operations.
ADC Analog-to-digital conversion.
LCD Display control and data output.
Application Product-specific application logic.

Modular Design Concept

The application layer uses driver interfaces without needing to repeat low-level register operations throughout the firmware.

9. Advantages of Modular Programming

  • Code reusability: Modules can be reused in other projects.
  • Maintainability: Changes can be isolated to specific modules.
  • Readability: Code is easier to understand.
  • Debugging: Individual modules can be tested separately.
  • Team development: Different developers can work on different modules.
  • Scalability: New features can be added more systematically.
  • Separation of concerns: Hardware access and application logic remain distinct.

10. Complete LPC2129 Modular Project

Consider a simple project that controls an LED connected to P0.5.

Project Structure

LPC2129_LED_Project/
|
|-- main.c
|
|-- gpio.c
|
|-- gpio.h
|
|-- system.c
|
|-- system.h

File 1: gpio.h

#ifndef GPIO_H
#define GPIO_H

void GPIO_Init(void);

void LED_On(void);

void LED_Off(void);

#endif

File 2: gpio.c

#include <LPC21xx.h>
#include "gpio.h"

#define LED_PIN  5U
#define LED_MASK (1U << LED_PIN)

void GPIO_Init(void)
{
    /* Select GPIO function for P0.5 */
    PINSEL0 &= ~(3U << 10);

    /* Configure P0.5 as output */
    IODIR0 |= LED_MASK;

    /* Initialize output to LOW */
    IOCLR0 = LED_MASK;
}

void LED_On(void)
{
    IOSET0 = LED_MASK;
}

void LED_Off(void)
{
    IOCLR0 = LED_MASK;
}

File 3: system.h

#ifndef SYSTEM_H
#define SYSTEM_H

void System_Init(void);

#endif

File 4: system.c

#include "system.h"
#include "gpio.h"

void System_Init(void)
{
    GPIO_Init();
}

File 5: main.c

#include "system.h"
#include "gpio.h"

void Delay(void)
{
    volatile unsigned int i;

    for (i = 0U; i < 100000U; i++)
    {
        /* Software delay */
    }
}

int main(void)
{
    System_Init();

    while (1)
    {
        LED_On();

        Delay();

        LED_Off();

        Delay();
    }
}

Program Execution Flow

          Startup Code
                |
                v
             main.c
                |
                v
          System_Init()
                |
                v
           system.c
                |
                v
           GPIO_Init()
                |
                v
             gpio.c
                |
                v
          Configure P0.5
                |
                v
           while (1)
                |
          +-----+-----+
          |           |
          v           v
        LED_On()   LED_Off()
          |           |
          +-----+-----+
                |
              Repeat
Expected result: The source files provide separate interfaces and implementations. The program configures P0.5 as GPIO output and repeatedly writes to its output latch.
In Keil uVision, add all three source files (main.c, system.c and gpio.c) to the project. Header files must be available through the project include paths. Inspect register values in the simulator; physical LED behavior is not established by simulator-only testing.

11. Important Rules for Header Files

  • Use include guards in project header files.
  • Declare public functions in the corresponding header.
  • Keep function implementations in source files.
  • Include only the headers required by a source file.
  • Avoid unnecessary dependencies between modules.
  • Use consistent and meaningful file names.
  • Keep private implementation details inside source files where possible.
Avoid defining ordinary global variables in header files. Prefer an extern declaration in the header and one actual definition in a source file when a shared global is genuinely needed.

Example: Shared Variable

In system.h:

#ifndef SYSTEM_H
#define SYSTEM_H

extern unsigned int system_status;

#endif

In system.c:

#include "system.h"

unsigned int system_status = 0U;

The header declares the variable, while the source file provides its single definition.

12. Compilation and Linking of Multiple Files

A modular embedded project is built by compiling its source files and linking the resulting object files into an executable image. 

main.c  ------> main.o
system.c ------> system.o
gpio.c  ------> gpio.o
                    |
                    v
                  Linker
                    |
                    v
             Firmware Image

Build Stages

  1. Preprocessing: Handles header inclusion and macros.
  2. Compilation: Translates C code into assembly or an intermediate representation.
  3. Assembly: Produces object code.
  4. Linking: Combines object files and resolves external symbols.
  5. Output generation: Produces the target firmware image, such as an ELF or HEX file depending on project settings.
A function declared in a header but not defined in any linked source file can result in an undefined reference or unresolved symbol error.

13. Adding Source Files in Keil uVision

  1. Open the LPC2129 project in Keil uVision.
  2. In the Project window, select the target group.
  3. Right-click the group.
  4. Select Add Existing Files to Group.
  5. Choose the required source files, such as main.c, system.c and gpio.c.
  6. Add the files to the project.
  7. Ensure the project can locate the required header files.
  8. Build the project.
  9. Resolve any compilation or linking errors.
  10. Start the simulator and inspect the program execution.
Adding a header file to the project group can make it visible in the Project window, but compilation does not require every included header to be added as a separate project source file. The compiler must be able to find it through the include path.

14. Common Errors in Modular Programming

Error Possible Cause
Header file not found Incorrect include path or filename.
Undefined symbol Function implementation missing from linked files.
Multiple definition Same global object or function defined more than once.
Redefinition error Missing or incorrect include guards.
Conflicting declaration Header declaration does not match the definition.
Duplicate source symbols Multiple source files define the same external symbol.

15. Interview Questions and Answers

Q1. What is modular programming?

It is the practice of dividing a large program into smaller modules with specific responsibilities.

Q2. What is the difference between .c and .h files?

A .c file generally contains implementations, while a .h file generally contains shared declarations.

Q3. What is a function prototype?

It is a declaration specifying a function's return type, name and parameter types.

Q4. What is an include guard?

It is a preprocessor technique that prevents repeated processing of a header's contents within one translation unit.

Q5. Why are header files used?

They provide a shared interface for functions, types, macros and other declarations.

Q6. What is the purpose of extern?

It declares an object or function whose definition is provided elsewhere.

Q7. What is a translation unit?

It is the source file after preprocessing, including the contents of its included headers.

Q8. What does the linker do?

It combines object files and resolves references between separately compiled modules.

Q9. Why should hardware drivers be separated?

Separation improves reuse, maintainability, testing and isolation of hardware-specific code.

Q10. Should a header file contain all function implementations?

Generally no. Function implementations normally belong in source files, with selected exceptions such as carefully designed inline functions.

18. Lesson Summary

  • Modular programming divides firmware into functional modules.
  • Source files generally contain function implementations.
  • Header files provide declarations and shared interfaces.
  • Function prototypes describe how functions are called.
  • Include guards prevent repeated header processing.
  • extern declares objects or functions defined elsewhere.
  • The linker combines object files and resolves symbols.
  • Keil uVision projects can contain multiple source and header files.
  • Modular design improves firmware reuse and maintainability.
