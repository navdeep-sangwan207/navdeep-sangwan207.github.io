Lesson 06: Volatile Keyword in Embedded C

Chapter 04 – Embedded C Programming

Embedded Systems – Complete Study Course

1. Introduction

The volatile keyword is an important feature of Embedded C. It tells the compiler that a variable's value may change unexpectedly from the perspective of the normal program flow.

Such changes may occur because of hardware activity, an interrupt service routine, or another execution context that the compiler cannot treat as an ordinary sequence of statements.

Without appropriate volatile qualification, the compiler may optimize accesses in ways that are unsuitable for hardware communication.

Definition: volatile is a type qualifier that tells the compiler that accesses to a particular object are observable and must not be eliminated or transformed as though the object were an ordinary unchanging variable.

2. Why Is Volatile Required?

Compilers optimize programs to improve execution speed and reduce code size. They may remove unnecessary memory accesses or reuse previously loaded values.

In embedded systems, however, a variable may be changed by something outside the ordinary program flow.

Common situations include:

  • Hardware peripheral registers.
  • Interrupt service routines.
  • Hardware status flags.
  • Polling loops that wait for an external event.
  • Memory locations shared with another execution context.
Important: Volatile does not disable every compiler optimization. It specifically constrains optimizations involving accesses to volatile-qualified objects.

3. Declaring a Volatile Variable

The volatile keyword is written before or after the data type.

Syntax

volatile int value;

int volatile status;

Both declarations qualify the variable as volatile.

Example

#include <stdio.h>

int main(void)
{
    volatile int counter = 0;

    counter = 10;
    counter = 20;

    printf("Counter = %d\n", counter);

    return 0;
}

Expected Result

Counter = 20

The program demonstrates a volatile variable. The important difference is how the compiler must handle accesses to that object.

4. Compiler Optimization and Volatile

Consider a program that continuously checks a variable.

Example Without Volatile

int flag = 0;

while (flag == 0)
{
    /* Wait for flag to change */
}

If the compiler can establish that no operation in the program changes flag, it may optimize the loop based on that assumption.

This is unsuitable if an external hardware event or an interrupt is expected to update the flag.

Example With Volatile

volatile int flag = 0;

while (flag == 0)
{
    /* Repeatedly read flag */
}

The compiler must preserve the required volatile accesses so that the loop observes changes to the object according to the C abstract machine.

A volatile read must not simply be replaced with a previously cached value when doing so would remove an observable volatile access.

5. Volatile with Memory-Mapped Registers

Microcontrollers use memory-mapped I/O to access hardware peripherals through specific memory addresses.

A peripheral register may change because of hardware activity even when the CPU does not execute a normal assignment to that register.

Therefore, register definitions in device header files commonly use volatile-qualified types.

Example

volatile unsigned int *reg;

reg = (volatile unsigned int *)0xE0028000U;

*reg = 0x01U;

This illustrates the use of a volatile-qualified pointer target for a memory-mapped register. The address is only illustrative here; real peripheral addresses must come from the microcontroller reference manual.

Accessing an LPC2129 Register

#include <LPC21xx.h>

int main(void)
{
    /* Configure P0.5 as GPIO */
    PINSEL0 &= ~(3U << 10);

    /* Configure P0.5 as output */
    IODIR0 |= (1U << 5);

    /* Set P0.5 output latch */
    IOSET0 = (1U << 5);

    while (1)
    {
    }
}

The LPC2129 device header defines peripheral registers with appropriate hardware access qualifications. This is why register definitions supplied by a device header should normally be used instead of inventing ordinary variables for hardware registers.

6. Volatile with Polling Loops

Polling is a technique in which the CPU repeatedly checks a status flag until a particular condition occurs.

For example, a UART program may wait until the transmitter is ready.

Example

volatile unsigned int status = 0U;

while ((status & 0x01U) == 0U)
{
    /* Wait until bit 0 becomes 1 */
}

In an actual embedded application, the status variable may represent a hardware register or a properly shared status flag.

A volatile variable does not itself create a hardware event or guarantee that a flag will eventually change. The hardware or another execution context must update it.

7. Volatile with Interrupt Service Routines

An interrupt service routine (ISR) executes when an interrupt event occurs. An ISR may update a variable that is also accessed by the main program.

A common example is a flag that tells the main program an interrupt has occurred.

Example

#include <LPC21xx.h>

volatile unsigned int interrupt_flag = 0U;

void timer_isr(void)
{
    interrupt_flag = 1U;

    /* Acknowledge the timer interrupt here,
       according to the configured timer and VIC. */
}

int main(void)
{
    while (1)
    {
        if (interrupt_flag != 0U)
        {
            interrupt_flag = 0U;

            /* Perform the required task */
        }
    }
}

The volatile qualification ensures that accesses to the flag are treated as volatile accesses.

Important: Volatile does not make an operation atomic and does not prevent race conditions. If a flag can be modified while the main program reads or clears it, use an appropriate synchronization strategy. On a microcontroller, this may involve carefully designed critical sections or interrupt masking.

8. Volatile and Pointers

Volatile can be applied to the object pointed to by a pointer or to the pointer itself.

Pointer to a Volatile Object

volatile unsigned int *ptr;

The object accessed through ptr is volatile. The pointer itself can be changed.

Constant Pointer to a Volatile Object

volatile unsigned int * const ptr =
    (volatile unsigned int *)0x40000000U;

The pointer cannot be reassigned after initialization, but the object it points to is volatile.

Volatile Pointer

unsigned int * volatile ptr;

The pointer itself is volatile, but the pointed-to object is not qualified as volatile by this declaration.

Constant Volatile Pointer

volatile unsigned int * const volatile ptr =
    (volatile unsigned int *)0x40000000U;

Both the pointer and the pointed-to object are volatile-qualified, and the pointer cannot be reassigned.

9. Difference Between Volatile and Const

Volatile Const
Indicates that accesses to an object are observable. Prevents modification through the qualified access path.
Useful for hardware registers and externally updated objects. Useful for read-only data through a particular reference.
Does not prevent assignments to the object. Prevents assignments through a const-qualified lvalue.
Does not guarantee atomicity. Does not guarantee atomicity.

Using Const and Volatile Together

volatile const unsigned int *status_reg;

This declaration represents an object that may change independently, but is not to be modified through this pointer.

This pattern is useful for read-only hardware status registers.

10. Volatile Does Not Guarantee Atomicity

Atomicity means that an operation is performed as an indivisible operation with respect to relevant concurrent execution contexts.

Consider the following statement: 

counter++;

This is generally a read-modify-write operation. It is not guaranteed to be atomic merely because the counter is declared volatile. 

volatile unsigned int counter = 0U;

counter++;

If an interrupt also modifies the counter, an update can be lost depending on the generated instructions and timing.

Remember: Volatile controls compiler treatment of accesses. It does not provide mutual exclusion, synchronization, memory ordering between execution contexts, or hardware-level atomic operations.

11. Volatile vs Atomic

Feature Volatile Atomic
Main purpose Preserves observable accesses. Provides indivisible operations and synchronization semantics as specified.
Prevents compiler from removing required volatile accesses Yes Atomic operations have their own specified semantics.
Guarantees atomic read-modify-write No For supported atomic operations, yes.
Typical use Memory-mapped hardware registers. Shared data synchronization.

C11 provides atomic facilities through <stdatomic.h>. Whether those facilities are available and appropriate depends on the compiler, target architecture and runtime.

12. Practical Program: Volatile Flag

Objective

To understand how a volatile variable is accessed repeatedly in a polling loop.

Program

#include <stdio.h>

int main(void)
{
    volatile unsigned int flag = 0U;

    printf("Initial flag = %u\n", flag);

    flag = 1U;

    if (flag != 0U)
    {
        printf("Flag is SET\n");
    }

    flag = 0U;

    if (flag == 0U)
    {
        printf("Flag is CLEAR\n");
    }

    return 0;
}

Expected Result

Initial flag = 0
Flag is SET
Flag is CLEAR
Result: The program demonstrates reads and writes to a volatile-qualified variable. It does not simulate an actual external hardware event or interrupt.

13. Practical LPC2129 Example

Objective

Configure P0.5 as an output and use the LPC2129 GPIO register definitions to set and clear its output latch.

Program

#include <LPC21xx.h>

int main(void)
{
    /* Select GPIO function for P0.5 */
    PINSEL0 &= ~(3U << 10);

    /* Configure P0.5 as output */
    IODIR0 |= (1U << 5);

    while (1)
    {
        /* Set output latch */
        IOSET0 = (1U << 5);

        /* Clear output latch */
        IOCLR0 = (1U << 5);
    }
}

Program Explanation

  1. The device header provides the LPC2129 register definitions.
  2. PINSEL0 selects GPIO functionality for P0.5.
  3. IODIR0 configures P0.5 as an output.
  4. IOSET0 sets the output latch.
  5. IOCLR0 clears the output latch.
  6. The loop repeats the two register writes.
Keil uVision Simulation: Step through the program and inspect the GPIO registers. The simulator can be used to observe register-level operations, but this does not demonstrate a physically connected LED blinking.

14. Common Mistakes

Mistake Correct Understanding
Assuming volatile makes a variable constant. Volatile does not prevent modification.
Assuming volatile makes operations atomic. Atomicity requires separate guarantees.
Using volatile for every variable. Use it when the object's access semantics require it.
Assuming volatile provides thread synchronization. Use appropriate synchronization mechanisms.
Declaring a normal local variable volatile to simulate an interrupt. A normal assignment in the same program does not simulate an independent interrupt event.
Assuming volatile prevents all compiler optimizations. It constrains optimizations involving volatile accesses, not all optimizations.

15. Interview Questions and Answers

Q1. What is the volatile keyword?

Volatile is a type qualifier that informs the compiler that accesses to an object are observable and that its value may change independently of the ordinary program flow.

Q2. Why is volatile used in Embedded C?

It is used for memory-mapped registers, hardware status flags and variables shared with interrupt service routines.

Q3. What happens if volatile is not used for a hardware register?

The compiler may optimize accesses in a way that does not preserve the required hardware interactions.

Q4. Does volatile make a variable thread-safe?

No. Volatile does not provide mutual exclusion or synchronization.

Q5. Does volatile guarantee atomicity?

No. An operation such as incrementing a volatile variable may still involve multiple machine operations.

Q6. Can const and volatile be used together?

Yes. A read-only hardware status register is a common example.

Q7. Why is volatile used in polling?

It ensures the compiler preserves the required accesses to a flag that may change outside the normal program flow.

Q8. Can an ISR modify a volatile variable?

Yes. Volatile is commonly used for ISR-shared flags, but additional synchronization may be needed for multi-step operations.

Q9. What is a volatile pointer?

A pointer declared volatile has volatile-qualified pointer accesses. This is different from a pointer to a volatile object.

Q10. Does volatile disable compiler optimization completely?

No. It only affects optimizations involving accesses to volatile-qualified objects.

16. Multiple Choice Questions (MCQs)

1. What does volatile tell the compiler?
  1. The variable cannot change.
  2. Accesses to the object are observable.
  3. The variable is always stored in ROM.
  4. The variable is constant.

Answer: B – Accesses to the object are observable.

2. Which is a common use of volatile?
  1. Memory-mapped peripheral registers.
  2. Ordinary mathematical constants.
  3. Function names.
  4. Comments.

Answer: A – Memory-mapped peripheral registers.

3. Does volatile guarantee atomicity?
  1. Yes, always.
  2. No.
  3. Only for floating-point values.
  4. Only for arrays.

Answer: B – No.

4. Which declaration makes the pointed-to object volatile?
  1. unsigned int *ptr;
  2. unsigned int * volatile ptr;
  3. volatile unsigned int *ptr;
  4. const unsigned int ptr;

Answer: C – volatile unsigned int *ptr.

5. Which qualifier prevents modification through a particular access path?
  1. volatile
  2. const
  3. extern
  4. register

Answer: B – const.

6. Can volatile be used with const?
  1. Yes
  2. No
  3. Only in C++
  4. Only with arrays

Answer: A – Yes.

7. Which is a common example of an ISR-shared variable?
  1. Interrupt status flag
  2. Source-code comment
  3. Function prototype
  4. Header guard name

Answer: A – Interrupt status flag.

8. What does volatile NOT guarantee?
  1. Observable volatile accesses
  2. Atomicity
  3. Hardware register access qualification
  4. Repeated volatile reads where required

Answer: B – Atomicity.

18. Lesson Summary

  • Volatile is a type qualifier in C.
  • It is important for hardware register access.
  • It is commonly used with interrupt-shared flags.
  • It helps preserve required accesses in polling loops.
  • It does not make operations atomic.
  • It does not provide thread synchronization.
  • It can be combined with const.
  • It can qualify a pointer, its target, or both.
