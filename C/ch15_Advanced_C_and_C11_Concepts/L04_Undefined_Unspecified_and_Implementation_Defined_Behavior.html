Lecture 04: Undefined, Unspecified and Implementation-Defined Behavior

Chapter 15 – Advanced C and C11 Concepts

Understand C language behavior, portability and common programming pitfalls.

1. Learning Objectives

  • Understand the meaning of defined and undefined behavior.
  • Differentiate undefined, unspecified and implementation-defined behavior.
  • Identify common undefined behavior in C programs.
  • Understand expression evaluation and sequencing.
  • Recognize signed integer overflow and invalid memory access.
  • Understand why compiler optimizations depend on language rules.
  • Solve output-prediction and interview questions.

2. Why Are These Concepts Important?

C gives programmers considerable control over data types, memory and hardware. However, certain operations have restrictions defined by the C standard.

If a program violates those restrictions, its behavior may not be predictable or portable.

Consider:

#include <stdio.h>
#include <limits.h>

int main(void)
{
    int value = INT_MAX;

    value = value + 1;

    printf("%d\n", value);

    return 0;
}

A beginner may expect the value to wrap around to a negative number. However, signed integer overflow is undefined behavior.

Interview principle: Never assume that an expression has a predictable result merely because it compiles successfully.

3. Three Important Behavior Categories

Category Meaning Implementation Requirement
Undefined behavior The C standard imposes no requirements on what happens. No particular result is guaranteed.
Unspecified behavior The standard permits multiple possibilities without requiring which one is chosen. The implementation need not document its choice.
Implementation-defined behavior The standard permits multiple possibilities and requires the implementation to document its choice. The implementation must document the selected behavior.
These are three different concepts. In particular, unspecified behavior and implementation-defined behavior are not the same as undefined behavior.

4. Undefined Behavior (UB)

Undefined behavior occurs when the C standard does not impose requirements on the behavior of a program because it has performed an operation for which the standard defines no behavior.

A compiler is not required to detect or report every instance of undefined behavior.

Example 1 – Division by Zero

#include <stdio.h>

int main(void)
{
    int a = 10;
    int b = 0;

    printf("%d\n", a / b);

    return 0;
}
Undefined behavior: Integer division by zero is undefined. Do not expect a particular output or error message.

Example 2 – Signed Integer Overflow

#include <limits.h>

int main(void)
{
    int value = INT_MAX;

    value++;

    return 0;
}

An int cannot represent the mathematical result of INT_MAX + 1. Signed integer overflow is undefined behavior.

Example 3 – Accessing an Array Outside Its Bounds

#include <stdio.h>

int main(void)
{
    int arr[3] = {10, 20, 30};

    printf("%d\n", arr[5]);

    return 0;
}
Accessing arr[5] is outside the array bounds and results in undefined behavior.

Example 4 – Dereferencing a Null Pointer

int *ptr = NULL;

*ptr = 100;

Dereferencing a null pointer is undefined behavior.

Example 5 – Use After Free

#include <stdlib.h>

int main(void)
{
    int *ptr = malloc(sizeof *ptr);

    if (ptr == NULL)
    {
        return 1;
    }

    *ptr = 50;

    free(ptr);

    *ptr = 100;  /* Undefined behavior */

    return 0;
}

After free() releases the allocated object, accessing it through the old pointer is invalid.

5. More Common Examples of Undefined Behavior

Example Problem
Signed integer overflow Result cannot be represented by the signed type.
Integer division by zero Invalid arithmetic operation.
Out-of-bounds array access Access outside the permitted array elements.
Null pointer dereference Invalid pointer access.
Use after free Access to an object whose allocated lifetime has ended.
Modifying a string literal String literals must not be modified.
Unsequenced conflicting accesses Unsequenced modification and access of the same scalar object.
Invalid pointer arithmetic Pointer arithmetic outside the permitted array range.
Returning from a non-void function without a value Using the resulting function-call value is undefined when the caller uses it.

6. Unspecified Behavior

Unspecified behavior occurs when the C standard permits two or more possibilities but does not require the implementation to document which possibility it chooses.

The program must not depend on one particular permitted choice.

Example – Order of Function Argument Evaluation

#include <stdio.h>

int first(void)
{
    printf("First ");
    return 1;
}

int second(void)
{
    printf("Second ");
    return 2;
}

int main(void)
{
    int result = first() + second();

    printf("\nResult = %d\n", result);

    return 0;
}

The order in which first() and second() are evaluated is unspecified.

Both function calls are evaluated, but C does not specify which one must execute first. A permitted implementation may evaluate first() first or second() first.

Possible Output 1

First Second
Result = 3

Possible Output 2

Second First
Result = 3

These outputs illustrate the permitted ordering. The result is 3 in either case because both functions return fixed values.

Important Distinction

Unspecified order does not automatically mean undefined behavior. The expression above is valid because the function calls do not perform conflicting unsequenced accesses to the same object.

7. Implementation-Defined Behavior

Implementation-defined behavior occurs when the C standard allows an implementation to choose from multiple possibilities and requires the implementation to document its choice.

Example 1 – Plain char Signedness

#include <stdio.h>

int main(void)
{
    printf("char size = %zu\n", sizeof(char));
    printf("char signed = %d\n", ((char)-1 < 0));

    return 0;
}

Whether plain char behaves as a signed or unsigned integer type is implementation-defined.

The size of char is always one C byte. A C byte is not necessarily eight bits; CHAR_BIT from limits.h specifies the number of bits in a byte.

Example 2 – Right Shift of a Negative Signed Value

#include <stdio.h>

int main(void)
{
    int value = -8;

    printf("%d\n", value >> 1);

    return 0;
}

In C11, the result of right-shifting a negative signed integer is implementation-defined.

Do not assume that every compiler uses arithmetic right shift for negative signed values. Use unsigned types when predictable bit shifting is required.

Example 3 – Integer Type Widths

The exact widths of types such as int and long depend on the implementation, subject to the minimum requirements of the C standard. 

#include <stdio.h>

int main(void)
{
    printf("int = %zu bytes\n", sizeof(int));
    printf("long = %zu bytes\n", sizeof(long));

    return 0;
}

Different conforming implementations can produce different sizes.

8. Comparison of the Three Categories

Feature Undefined Unspecified Implementation-Defined
Multiple outcomes permitted? No guaranteed requirements. Yes. Yes.
Must document the choice? No. No. Yes.
Portable to rely on one result? No. No. Only if the documented implementation behavior is suitable.
Example Signed integer overflow. Function argument evaluation order. Plain char signedness.

9. Sequence Points and Sequencing

C expressions have rules that determine when evaluations are sequenced relative to one another.

In C11, the important concepts are:

  • Sequenced before: One evaluation is guaranteed to complete before another.
  • Unsequenced: Neither evaluation is sequenced before the other.
  • Indeterminately sequenced: One evaluation completes before the other, but the order is unspecified.

Example 1 – Undefined Behavior

#include <stdio.h>

int main(void)
{
    int i = 5;

    int result = i++ + i++;

    printf("%d\n", result);

    return 0;
}
Undefined behavior: The two modifications of i are unsequenced relative to each other.

Do not try to calculate a guaranteed output for this program.

Example 2 – Well-Defined Sequencing

#include <stdio.h>

int main(void)
{
    int i = 5;

    int first = i++;

    int second = i++;

    printf("First = %d\n", first);
    printf("Second = %d\n", second);
    printf("i = %d\n", i);

    return 0;
}
Expected Output 
First = 5
Second = 6
i = 7

Each full expression is completed before the next statement executes, so the modifications are properly sequenced.

Example 3 – Logical AND Sequencing

#include <stdio.h>

int main(void)
{
    int i = 0;

    if (i++ == 0 && i == 1)
    {
        printf("Condition true\n");
    }

    printf("i = %d\n", i);

    return 0;
}
Expected Output 
Condition true
i = 1

The left operand of logical AND is evaluated first. If it is nonzero, the right operand is evaluated afterward. The sequencing rule makes this expression well-defined.

10. Compiler Optimization and Undefined Behavior

Compilers optimize programs based on the assumption that the program follows the C language rules.

When a program contains undefined behavior, the compiler is not required to preserve the programmer's expected result.

Example

int check(int x)
{
    if (x < 0 && x >= 0)
    {
        return 1;
    }

    return 0;
}

For every valid int value, the condition is false. A compiler can therefore optimize the function to return zero.

Important Example – Signed Overflow Assumption

int test(int x)
{
    return x + 1 > x;
}

For ordinary values that do not overflow, the expression evaluates to true. Because signed overflow is undefined, a compiler may optimize under the assumption that the addition does not overflow.

This is one reason why programs that appear to work without optimization may behave differently when compiled with optimization options such as -O2.

11. Common C Programming Mistakes

Mistake Correct Approach
Assuming signed overflow wraps around Check ranges before arithmetic or use suitable unsigned types.
Using an array index without checking bounds Validate the index before accessing the array.
Dereferencing an unchecked pointer Validate pointer values and object lifetimes.
Modifying string literals Use a writable character array.
Depending on argument evaluation order Use separate statements when order matters.
Assuming plain char is signed Use signed char or unsigned char explicitly.
Using signed values for hardware bit manipulation without care Prefer appropriately sized unsigned integer types.

12. Writing Portable C Code

Portable code should avoid depending on implementation-specific assumptions unless those assumptions are explicitly documented and acceptable for the target.

Recommended Practices

  • Use standard integer types or fixed-width types where appropriate.
  • Check array indexes before accessing elements.
  • Avoid signed integer overflow.
  • Initialize variables before use.
  • Check memory allocation results.
  • Release dynamically allocated memory correctly.
  • Avoid expressions that modify the same object without proper sequencing.
  • Do not depend on unspecified evaluation order.
  • Document required compiler and platform assumptions.

Compiler Warning Example

gcc -std=c11 -Wall -Wextra -Wpedantic -Wconversion -Wshadow program.c -o program

These options can help identify suspicious conversions and other programming problems. Warnings are diagnostic aids; they do not prove that a program is free of undefined behavior.

13. Embedded C Applications

Embedded software frequently interacts with hardware registers, interrupts, timers and communication peripherals. Incorrect assumptions about C behavior can lead to difficult-to-diagnose failures.

Example – Safer Unsigned Register Operation

#include <stdint.h>
#include <stdio.h>

int main(void)
{
    uint32_t control_register = 0x00000001U;

    control_register |= (uint32_t)(1U << 5);

    printf("Register = 0x%08X\n",
           (unsigned int)control_register);

    return 0;
}
Expected Output 
Register = 0x00000021

The example uses an unsigned integer mask to set bit 5. For portable bit manipulation, ensure the shift count is nonnegative and less than the width of the promoted left operand.

Hardware register access also requires the correct register definitions, access width and device-specific semantics. A normal C variable in a desktop program is not a substitute for an actual memory-mapped peripheral register.

14. Placement-Oriented Interview Questions

Q1. What is undefined behavior?

Answer: It is behavior for which the C standard imposes no requirements.

Q2. What is unspecified behavior?

Answer: It is behavior where the standard permits multiple possibilities but does not require the implementation to document its choice.

Q3. What is implementation-defined behavior?

Answer: It is behavior where the implementation selects from multiple possibilities and must document its choice.

Q4. Is signed integer overflow undefined behavior?

Answer: Yes. Signed integer arithmetic that produces an unrepresentable result has undefined behavior.

Q5. Is unsigned integer overflow undefined behavior?

Answer: No. Unsigned arithmetic is defined modulo one more than the maximum value of the unsigned type.

Q6. Is the order of function argument evaluation specified?

Answer: The order is generally unspecified in C11. Function argument evaluations are not required to occur from left to right.

Q7. Is plain char signed or unsigned?

Answer: Its signedness is implementation-defined.

Q8. What happens when a program accesses an array out of bounds?

Answer: Accessing an element outside the permitted array range results in undefined behavior.

Q9. Why can optimization change the apparent result of an invalid program?

Answer: The compiler may assume that undefined behavior does not occur and optimize based on that assumption.

Q10. What is the safest way to handle evaluation order?

Answer: Separate operations into statements and use explicit sequencing when the order matters.

15. Output Prediction Practice

Problem 1 – Unspecified Evaluation Order

#include <stdio.h>

int a(void)
{
    printf("A ");
    return 10;
}

int b(void)
{
    printf("B ");
    return 20;
}

int main(void)
{
    int result = a() + b();

    printf("\n%d\n", result);

    return 0;
}

Question: Is the order of A and B guaranteed?

Answer: No. Either function may be evaluated first. The final arithmetic result is 30.

Problem 2 – Undefined Behavior

#include <stdio.h>

int main(void)
{
    int i = 10;

    printf("%d %d\n", i++, i++);

    return 0;
}
Answer: Undefined behavior. The two modifications of i are unsequenced. There is no guaranteed output.

Problem 3 – Defined Sequencing

#include <stdio.h>

int main(void)
{
    int i = 10;

    printf("%d\n", i++);

    printf("%d\n", i);

    return 0;
}
Expected Output 
10
11

Problem 4 – Implementation-Defined Behavior

#include <stdio.h>

int main(void)
{
    signed char value = -8;

    printf("%d\n", value >> 1);

    return 0;
}
Answer: The result of right-shifting a negative signed integer is implementation-defined in C11. Do not assume a universal output.

16. Practical Lab Exercise

Objective

Identify safe and unsafe expressions and understand the importance of sequencing and range validation.

Complete C11 Program

#include <stdio.h>
#include <limits.h>
#include <stdint.h>

int main(void)
{
    int a = 10;
    int b = 20;

    int result = a + b;

    printf("Safe addition = %d\n", result);

    unsigned int x = UINT_MAX;
    x = x + 1U;

    printf("Unsigned wraparound = %u\n", x);

    int i = 5;

    int first = i++;
    int second = i++;

    printf("First = %d\n", first);
    printf("Second = %d\n", second);
    printf("Final i = %d\n", i);

    return 0;
}

Compile

gcc -std=c11 -Wall -Wextra -Wpedantic behavior.c -o behavior

Run

./behavior
Expected Output 
Safe addition = 30
Unsigned wraparound = 0
First = 5
Second = 6
Final i = 7

Lab Observations

  1. Ordinary representable signed addition is well-defined.
  2. Unsigned arithmetic wraps according to its defined range.
  3. Separate statements provide clear sequencing.
  4. Expressions with unsequenced conflicting modifications must be avoided.

18. Key Takeaways

  • Undefined behavior has no requirements imposed by the C standard.
  • Unspecified behavior permits multiple outcomes without requiring documentation.
  • Implementation-defined behavior must be documented by the implementation.
  • Signed overflow, invalid memory access and unsequenced conflicting modifications can cause undefined behavior.
  • Function argument evaluation order is not generally left-to-right in C11.
  • Plain char signedness is implementation-defined.
  • Compiler optimizations rely on the assumption that undefined behavior does not occur.
  • Portable C code should avoid relying on unspecified or undocumented implementation choices.
