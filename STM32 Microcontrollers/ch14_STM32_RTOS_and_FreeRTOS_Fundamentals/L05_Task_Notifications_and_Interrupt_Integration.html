Lesson 5: Task Notifications and Interrupt Integration

STM32 RTOS and FreeRTOS Fundamentals

1. Learning Objectives

  • Understand direct-to-task notifications in FreeRTOS.
  • Learn task notification APIs and notification actions.
  • Understand interrupt integration with FreeRTOS.
  • Learn how an ISR signals a task.
  • Understand Cortex-M interrupt-priority restrictions.
  • Implement interrupt-driven embedded applications.

2. What is a Task Notification?

A direct-to-task notification is a lightweight mechanism used to send a notification or a 32-bit value directly to a task. It can be used for synchronization, event signaling and simple data transfer.

Unlike a queue or semaphore, a task notification is associated directly with a particular task. This often makes it more efficient when only one receiving task is required.

Applications

  • Signal that an ADC conversion has completed.
  • Notify a task that UART data has arrived.
  • Wake a task after a GPIO interrupt.
  • Signal completion of a DMA transfer.
  • Send simple event information to a task.

3. Task Notification Architecture

+-------------------------+
|     Hardware Event      |
| GPIO / UART / ADC / DMA |
+-------------------------+
             |
             v
+-------------------------+
| Interrupt Service       |
| Routine (ISR)           |
+-------------------------+
             |
             | Notify task
             v
+-------------------------+
|    FreeRTOS Kernel      |
| Task Notification       |
+-------------------------+
             |
             v
+-------------------------+
|     Receiving Task      |
| Process Event or Data   |
+-------------------------+

The ISR performs only the necessary interrupt servicing and notification. The receiving task performs the longer application processing.

4. Task Notification APIs

API Purpose
xTaskNotifyGive() Increment a task's notification value.
vTaskNotifyGiveFromISR() Increment a task's notification value from an ISR.
ulTaskNotifyTake() Wait for and decrement or clear a notification count.
xTaskNotify() Send a notification value using a selected action.
xTaskNotifyFromISR() Send a notification value from an ISR.
xTaskNotifyWait() Wait for a notification and optionally update its value.
xTaskNotifyStateClear() Clear the notification state of a task.

A task can have an array of notification entries in supported FreeRTOS versions and configurations. The default commonly provides one notification entry per task.

5. Task Notification as a Binary Event

A notification can be used to wake a task when an event occurs. The following example uses a task notification as an event signal. 


#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t processingTaskHandle = NULL;

void Processing_Task(void *argument)
{
    for (;;)
    {
        if (ulTaskNotifyTake(
                pdTRUE,
                portMAX_DELAY
            ) > 0)
        {
            /* Process the received event. */
        }
    }
}

void Event_Generator_Task(void *argument)
{
    for (;;)
    {
        vTaskDelay(pdMS_TO_TICKS(1000));

        xTaskNotifyGive(processingTaskHandle);
    }
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();

    xTaskCreate(
        Processing_Task,
        "Process",
        256,
        NULL,
        2,
        &processingTaskHandle
    );

    xTaskCreate(
        Event_Generator_Task,
        "Generator",
        256,
        NULL,
        1,
        NULL
    );

    vTaskStartScheduler();

    Error_Handler();

    while (1)
    {
    }
}

With pdTRUE, the notification count is cleared when the task takes it. If multiple notifications arrive before the task processes them, they may be handled as one wake-up. Use pdFALSE when decrementing one notification count at a time is required.

6. Task Notification with a 32-Bit Value

Task notifications can also transfer a 32-bit value. The notification action determines how the receiving task's notification value is updated.

Common Notification Actions

  • eNoAction – Update notification state without changing the value.
  • eSetBits – Set specified bits in the notification value.
  • eIncrement – Increment the notification value.
  • eSetValueWithOverwrite – Replace the existing value.
  • eSetValueWithoutOverwrite – Write only when the previous notification is not pending.

Example


TaskHandle_t dataTaskHandle;

void Data_Task(void *argument)
{
    uint32_t receivedValue;

    for (;;)
    {
        if (xTaskNotifyWait(
                0,
                0xFFFFFFFFU,
                &receivedValue,
                portMAX_DELAY
            ) == pdTRUE)
        {
            /* Process receivedValue. */
        }
    }
}

void Send_Data(void)
{
    xTaskNotify(
        dataTaskHandle,
        100U,
        eSetValueWithOverwrite
    );
}

The overwrite action replaces an earlier pending value. Use it only when the newest value is more important than retaining every previous value. Use a queue when every data item must be preserved.

7. Interrupt Integration with FreeRTOS

Embedded applications often use hardware interrupts to detect events such as GPIO transitions, UART reception, timer updates, ADC completion and DMA completion.

In an RTOS application, an ISR should generally acknowledge the hardware event, capture minimal information and notify an appropriate task. The task then performs the remaining processing.

Interrupt-to-Task Flow

  1. A hardware peripheral generates an interrupt.
  2. The Cortex-M processor enters the corresponding ISR.
  3. The ISR services or acknowledges the interrupt source.
  4. The ISR sends an ISR-safe notification or queue message.
  5. The scheduler can switch to an unblocked higher-priority task.
  6. The task processes the event outside interrupt context.

8. Task Notification from an ISR

The vTaskNotifyGiveFromISR() API can be used to notify a task from an interrupt service routine. 


TaskHandle_t adcTaskHandle;

void ADC_Task(void *argument)
{
    for (;;)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* Read or process the completed ADC result. */
    }
}

void ADC_IRQHandler(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;

    /* Service and acknowledge the ADC interrupt here. */

    vTaskNotifyGiveFromISR(
        adcTaskHandle,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(higherPriorityTaskWoken);
}

This is a conceptual example. A real STM32 ADC interrupt handler must use the correct device-specific interrupt flags and peripheral handling, or the generated HAL IRQ handler. Do not create a second handler if CubeMX already generated one.

9. STM32 HAL Callback and FreeRTOS Task

When using STM32 HAL, a peripheral interrupt handler commonly forwards control to a HAL IRQ handler. HAL then invokes the appropriate callback. The callback can notify a task using an ISR-safe FreeRTOS API when the interrupt priority permits it.

Example: UART Reception Completion


#include "main.h"
#include "FreeRTOS.h"
#include "task.h"

extern UART_HandleTypeDef huart2;

TaskHandle_t uartTaskHandle;

uint8_t rxByte;

void UART_Task(void *argument)
{
    for (;;)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* Process rxByte after notification. */

        HAL_UART_Receive_IT(&huart2, &rxByte, 1);
    }
}

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;

    if (huart->Instance == USART2)
    {
        vTaskNotifyGiveFromISR(
            uartTaskHandle,
            &higherPriorityTaskWoken
        );

        portYIELD_FROM_ISR(higherPriorityTaskWoken);
    }
}

Start the first UART receive operation before the scheduler begins or from a suitable initialized task. The receiving buffer must remain valid until reception completes. For continuous or high-rate data, use a suitable circular DMA or receive-to-idle design rather than assuming one-byte interrupt reception is sufficient.

10. Cortex-M Interrupt Priority Restrictions

FreeRTOS Cortex-M ports impose interrupt-priority rules because some interrupts are allowed to call kernel APIs while others are not.

Important Concepts

  • Lower numerical NVIC priority values represent higher urgency.
  • Only interrupts at permitted priority levels may call FreeRTOS ISR APIs.
  • configMAX_SYSCALL_INTERRUPT_PRIORITY defines an important API-calling priority boundary in common Cortex-M ports.
  • configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY may be used by STM32 FreeRTOS projects as a library-level configuration value.
  • Priority values must account for the number of implemented NVIC priority bits and any priority grouping configuration.

An interrupt configured at a priority that is too urgent must not call FreeRTOS kernel APIs. It can instead set a hardware flag or use another permitted communication mechanism, with processing deferred appropriately.

Always check the selected FreeRTOS port documentation and the project's FreeRTOSConfig.h. Do not copy priority numbers from another STM32 project without checking its configuration.

11. Interrupt Latency and Real-Time Performance

Interrupt latency is the time between an interrupt event occurring and the processor beginning the corresponding interrupt handler.

Factors Affecting Latency

  • Interrupt priority.
  • Time spent with interrupts masked.
  • Execution time of higher-priority ISRs.
  • Processor clock frequency.
  • Memory and bus access delays.
  • Critical sections and kernel port behavior.

Task response time also includes scheduling delay and the time needed for the receiving task to execute. A fast ISR does not automatically guarantee a fast task response.

12. Task Notification vs Queue vs Semaphore

Feature Task Notification Queue Semaphore
Primary use Notify one task Transfer data Synchronization
Receiver Specific task One or more waiting tasks Waiting task(s)
Data storage 32-bit notification value per entry Configured item storage Synchronization state/count
Overhead Often lower for simple one-task signaling Higher for general data transfer Depends on semaphore type
ISR support ISR-safe notification APIs ISR-safe queue APIs ISR-safe give APIs

Select the mechanism according to the number of receivers, data requirements and whether events must be counted or retained.

13. Common Programming Errors

  • Calling task-context APIs from an ISR.
  • Using an interrupt priority that is not permitted to call FreeRTOS APIs.
  • Forgetting to acknowledge the hardware interrupt source.
  • Failing to initialize the receiving task handle.
  • Using a notification value without defining its update behavior.
  • Assuming notifications preserve every data item when overwrite or clear behavior is used.
  • Performing long processing inside an ISR.
  • Using a temporary buffer that becomes invalid before an asynchronous operation completes.

14. Placement-Oriented Interview Questions and Answers

Q1. What is a task notification?

A task notification is a lightweight mechanism for sending an event or value directly to a specific task.

Q2. What is the size of a task notification value?

The notification value is 32 bits wide.

Q3. Which API increments a task notification from an ISR?

vTaskNotifyGiveFromISR().

Q4. What does ulTaskNotifyTake() do?

It waits for a task notification and either clears or decrements the notification value according to its clear-on-exit argument.

Q5. Why are task notifications efficient?

They operate directly on a receiving task and avoid the general data-storage overhead of a queue for simple signaling.

Q6. Can a task notification transfer data?

Yes. It can transfer a 32-bit value using notification actions.

Q7. Why should long processing be avoided inside an ISR?

Long ISRs increase interrupt latency and delay other interrupts and task execution.

Q8. What is portYIELD_FROM_ISR() used for?

It requests an appropriate context switch when an ISR unblocks a higher-priority task, according to the port implementation.

Q9. What is interrupt latency?

It is the delay between an interrupt event and the start of its service routine.

Q10. Can every NVIC interrupt call a FreeRTOS API?

No. Only interrupts at permitted priority levels may call FreeRTOS ISR-safe APIs.

Q11. What is configMAX_SYSCALL_INTERRUPT_PRIORITY?

It defines the interrupt-priority boundary used by common Cortex-M FreeRTOS ports for API-calling interrupts.

Q12. When should a queue be preferred over a task notification?

Use a queue when multiple data items, structured messages or communication with multiple receiving tasks is required.

16. Lesson Summary

  • Task notifications provide efficient direct signaling to a task.
  • Notification values can carry 32-bit information.
  • ISRs can use ISR-safe notification APIs.
  • Long processing should be deferred from ISR context to tasks.
  • Cortex-M FreeRTOS ports impose interrupt-priority restrictions.
  • Interrupt latency and task response time are important real-time metrics.
  • Queues are preferable when structured or multiple data items must be retained.
