2. What is a Real-Time Embedded System?

A real-time embedded system is a computer system that must produce a correct response within a specified timing constraint. Correctness depends on both the result and the time at which the result is produced.

Examples

  • Automotive braking and engine control systems.
  • Industrial motor control.
  • Medical monitoring equipment.
  • Robotics and automation.
  • Power electronics controllers.
  • Communication and networking equipment.

3. Types of Real-Time Systems

3.1 Hard Real-Time System

A hard real-time system must meet its specified deadlines. Missing a critical deadline is considered a system failure.

Examples: Safety-critical control and certain protection systems.

3.2 Soft Real-Time System

A soft real-time system can tolerate occasional deadline misses, although performance or quality may decrease.

Examples: Multimedia playback and user-interface updates.

3.3 Firm Real-Time System

A firm real-time system can tolerate occasional missed deadlines, but a result delivered after its deadline has no useful value.

Examples: Some time-sensitive inspection and data-processing systems.

Type Deadline Requirement Effect of Missed Deadline
Hard Must be met System failure or unacceptable hazard
Firm Expected to be met Late result becomes useless
Soft Important but flexible Reduced quality or performance

4. Important Real-Time Performance Terms

Deadline

The latest acceptable time by which a task or operation must complete.

Latency

The delay between an event occurring and the system beginning or completing its response. The exact measurement must be defined for the application.

Jitter

Variation in the timing of an event or task execution between repeated occurrences.

Response Time

The time between a triggering event and the completion of the corresponding system response.

Determinism

The ability to produce predictable behavior within known timing bounds under specified operating conditions.

5. Real-Time Task Design

A real-time application is commonly divided into tasks according to functionality and timing requirements.

Example: Industrial Monitoring System

Task Function Example Priority
Control Task Process control inputs and outputs High
Sensor Task Acquire sensor readings Medium-High
Communication Task Transmit monitoring data Medium
Display Task Update LCD or display Low
Logging Task Store diagnostic information Low

These priorities are illustrative. Actual priorities should be selected using task deadlines, execution times, blocking behavior and system schedulability analysis.

6. Task Scheduling and Priority Assignment

Task priorities should reflect the urgency of the work and the consequences of delayed execution.

Priority Assignment Considerations

  • Task execution time.
  • Task period or arrival rate.
  • Deadline requirements.
  • Resource blocking time.
  • Interrupt interference.
  • Worst-case execution time.

Common Scheduling Approaches

Fixed-Priority Scheduling: Each task has a configured priority.

Rate-Monotonic Scheduling: Periodic tasks with shorter periods receive higher fixed priorities under the classical assumptions.

Deadline-Monotonic Scheduling: Tasks with shorter relative deadlines receive higher fixed priorities under the applicable assumptions.

Earliest Deadline First: The task with the nearest absolute deadline is selected. This is a dynamic-priority scheduling approach.

FreeRTOS commonly uses fixed task priorities. It does not automatically implement every scheduling algorithm listed above.

7. Worst-Case Execution Time (WCET)

Worst-case execution time is the maximum execution time estimated or measured for a task under defined operating conditions.

Why WCET Matters

  • Helps determine whether deadlines can be met.
  • Supports task priority assignment.
  • Helps identify CPU overload.
  • Supports system timing analysis.

Example

Task Execution Time Period
Control 1 ms 10 ms
Sensor 2 ms 20 ms
Communication 3 ms 50 ms

For this simplified periodic-task example, CPU utilization is: 


U = C1/T1 + C2/T2 + C3/T3

U = 1/10 + 2/20 + 3/50

U = 0.26

CPU utilization = 26%

This utilization estimate does not by itself prove that all deadlines will be met. Interrupt overhead, blocking, context switching, release jitter and scheduling assumptions must also be considered.

8. Periodic and Aperiodic Tasks

Periodic Tasks

Periodic tasks execute at regular intervals.

Examples: Sensor sampling every 10 ms or control-loop execution every 1 ms.

Aperiodic Tasks

Aperiodic tasks execute in response to events that do not occur at fixed intervals.

Examples: Button press handling or an unexpected communication request.

Sporadic Tasks

Sporadic tasks are event-triggered tasks with a known minimum interval between successive arrivals.

9. Deterministic Programming Techniques

  • Use bounded execution loops.
  • Avoid unnecessary dynamic memory allocation during time-critical operation.
  • Use fixed-size buffers where appropriate.
  • Keep interrupt service routines short.
  • Use queues and notifications for task communication.
  • Limit critical-section duration.
  • Use timeouts instead of indefinite waits when required by the application.
  • Measure execution time and task response time.
  • Prevent uncontrolled priority inversion.
  • Monitor stack and heap usage.

10. Resource Sharing and Deadlock Prevention

Multiple tasks may need access to the same peripheral or data structure. Resource access must be coordinated.

Common Protection Methods

  • Mutexes for mutual exclusion between tasks.
  • Queues for transferring ownership of data.
  • Short critical sections for suitable small shared operations.
  • Dedicated peripheral-owner tasks for shared hardware.

Deadlock Prevention

  • Acquire multiple resources in a consistent order.
  • Avoid holding one mutex while waiting indefinitely for another.
  • Keep resource ownership periods short.
  • Use finite timeouts where appropriate.
  • Document resource ownership and task dependencies.

11. Practical STM32 FreeRTOS Application

Project: Real-Time Temperature Monitoring System

Design an STM32 application with multiple tasks to acquire temperature data, process it and transmit the results through UART.

System Architecture

+------------------------+
|   Temperature Sensor   |
+------------------------+
            |
            v
+------------------------+
|       Sensor Task      |
| Read ADC / Sensor      |
+------------------------+
            |
            | Queue data
            v
+------------------------+
|      Data Queue        |
+------------------------+
            |
            v
+------------------------+
|   Processing Task      |
| Convert / Check Limit  |
+------------------------+
            |
            v
+------------------------+
| Communication Task     |
| UART Transmission      |
+------------------------+
            |
            v
+------------------------+
|       UART Output      |
+------------------------+

Example Code


#include "main.h"
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

extern ADC_HandleTypeDef hadc1;
extern UART_HandleTypeDef huart2;

QueueHandle_t temperatureQueue;

typedef struct
{
    uint16_t adcValue;
    float voltage;
} TemperatureData;

void Sensor_Task(void *argument)
{
    TemperatureData data;

    for (;;)
    {
        HAL_ADC_Start(&hadc1);

        if (HAL_ADC_PollForConversion(
                &hadc1,
                10
            ) == HAL_OK)
        {
            data.adcValue = HAL_ADC_GetValue(&hadc1);

            data.voltage =
                (data.adcValue * 3.3f) / 4095.0f;

            xQueueSend(
                temperatureQueue,
                &data,
                pdMS_TO_TICKS(10)
            );
        }

        HAL_ADC_Stop(&hadc1);

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void Communication_Task(void *argument)
{
    TemperatureData receivedData;
    char message[80];

    for (;;)
    {
        if (xQueueReceive(
                temperatureQueue,
                &receivedData,
                portMAX_DELAY
            ) == pdPASS)
        {
            int length = snprintf(
                message,
                sizeof(message),
                "ADC: %u, Voltage: %.2f V\r\n",
                (unsigned int)receivedData.adcValue,
                (double)receivedData.voltage
            );

            if (length > 0 && length < sizeof(message))
            {
                HAL_UART_Transmit(
                    &huart2,
                    (uint8_t *)message,
                    (uint16_t)length,
                    100
                );
            }
        }
    }
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();

    MX_GPIO_Init();
    MX_ADC1_Init();
    MX_USART2_UART_Init();

    temperatureQueue = xQueueCreate(
        5,
        sizeof(TemperatureData)
    );

    if (temperatureQueue == NULL)
    {
        Error_Handler();
    }

    if (xTaskCreate(
            Sensor_Task,
            "Sensor",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        Error_Handler();
    }

    if (xTaskCreate(
            Communication_Task,
            "UART",
            512,
            NULL,
            1,
            NULL
        ) != pdPASS)
    {
        Error_Handler();
    }

    vTaskStartScheduler();

    Error_Handler();

    while (1)
    {
    }
}

Project Explanation

  1. The sensor task starts an ADC conversion.
  2. The ADC result is converted into an approximate voltage.
  3. The sensor task sends the result to a FreeRTOS queue.
  4. The communication task waits for queue data.
  5. The communication task formats the reading and transmits it through UART.

Important: This is a framework example, not a complete temperature measurement implementation. The voltage conversion assumes a 12-bit ADC and a 3.3 V reference. A temperature sensor transfer function must be added for an actual temperature reading. Verify ADC configuration, sensor wiring, queue errors, UART timeouts, task stack sizes and peripheral initialization for the selected STM32.

12. Real-Time Debugging and Performance Measurement

Important Debugging Techniques

  • Use STM32CubeIDE breakpoints and variable inspection.
  • Measure task execution time.
  • Check task stack high-water marks.
  • Monitor heap availability.
  • Inspect task states and priorities.
  • Use GPIO timing markers with an oscilloscope or logic analyzer.
  • Enable suitable FreeRTOS trace and runtime-statistics features.

Common Performance Problems

  • High-priority task running continuously.
  • Long interrupt service routines.
  • Excessive critical sections.
  • Blocking communication calls.
  • Incorrect task priorities.
  • Stack overflow and heap exhaustion.
  • Excessive queue or mutex waiting.

13. Real-Time Application Design Checklist

  • Define the system's timing requirements.
  • Identify periodic, aperiodic and sporadic tasks.
  • Estimate or analyze worst-case execution times.
  • Assign task priorities based on timing requirements.
  • Choose suitable communication mechanisms.
  • Identify shared resources and protect them correctly.
  • Check interrupt priorities and ISR execution time.
  • Estimate stack, heap and total memory requirements.
  • Test under maximum expected workload.
  • Measure deadline compliance and response-time variation.

14. Placement-Oriented Interview Questions and Answers

Q1. What is a real-time embedded system?

A system in which correctness depends on both the result and its timing.

Q2. What is a hard real-time system?

A system in which specified critical deadlines must be met.

Q3. What is a soft real-time system?

A system in which occasional deadline misses reduce performance or quality but are tolerated.

Q4. What is a firm real-time system?

A system in which a late result has no useful value, although occasional deadline misses may be tolerated.

Q5. What is jitter?

Jitter is variation in the timing of repeated events or task executions.

Q6. What is WCET?

Worst-case execution time is the maximum execution time determined for a task under defined conditions.

Q7. What is determinism?

Determinism means system behavior and timing are predictable within defined bounds.

Q8. What is Rate-Monotonic Scheduling?

It is a fixed-priority scheduling approach that assigns higher priority to periodic tasks with shorter periods under classical assumptions.

Q9. What is Earliest Deadline First scheduling?

EDF is a dynamic-priority scheduling approach that selects the task with the nearest absolute deadline.

Q10. What is CPU utilization?

It is the fraction of processor capacity consumed by executing tasks over a defined interval.

Q11. Why should blocking calls be controlled in real-time tasks?

Unbounded blocking can cause unpredictable response times and missed deadlines.

Q12. How can real-time performance be measured?

Measure execution time, response time, interrupt latency, jitter, CPU utilization and deadline compliance.
