Lesson 4: Queues, Semaphores and Mutexes

STM32 RTOS and FreeRTOS Fundamentals

1. Learning Objectives

  • Understand inter-task communication in FreeRTOS.
  • Learn queue creation, sending and receiving.
  • Understand binary and counting semaphores.
  • Learn mutexes and shared-resource protection.
  • Understand priority inversion and priority inheritance.
  • Implement communication and synchronization on STM32.

2. Inter-Task Communication

In an RTOS-based embedded system, multiple tasks execute independently. They often need to exchange information and coordinate access to shared resources.

FreeRTOS provides several mechanisms:

  • Queues
  • Binary semaphores
  • Counting semaphores
  • Mutexes
  • Recursive mutexes
  • Direct-to-task notifications
  • Event groups

|   Sensor Task    |        |   Display Task   |
+------------------+        +------------------+
         |                           ^
         | Send data                 | Receive data
         v                           |
       +--------------------------------+
       |           FreeRTOS Queue        |
       +--------------------------------+

3. Queue in FreeRTOS

A queue is a kernel-managed communication object that transfers data between tasks and, through ISR-safe APIs, between interrupt service routines and tasks.

Queue Characteristics

  • Stores a fixed number of items.
  • Each item has a configured fixed size.
  • Normally uses FIFO ordering.
  • Supports blocking send and receive operations.
  • Copies item data into and out of queue storage.

Queue Working

+-------------+       Send data
| Sensor Task | -------------------+
+-------------+                   |
                                  v
                         +----------------+
                         |  FreeRTOS      |
                         |    Queue       |
                         +----------------+
                                  |
                                  | Receive data
                                  v
                         +----------------+
                         | Display Task   |
                         +----------------+

4. Queue APIs

API Purpose
xQueueCreate() Create a queue dynamically.
xQueueSend() Send data to the back of a queue.
xQueueSendToFront() Send data to the front of a queue.
xQueueReceive() Receive data from a queue.
uxQueueMessagesWaiting() Get the number of queued items.
vQueueDelete() Delete a queue.

Queue Creation Syntax


QueueHandle_t xQueueCreate(
    UBaseType_t uxQueueLength,
    UBaseType_t uxItemSize
);

uxQueueLength specifies the number of items and uxItemSize specifies the size of each item in bytes.

5. Queue Programming Example

A sensor task sends a temperature value to a display task. 


#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t temperatureQueue;

void Sensor_Task(void *argument)
{
    float temperature = 25.5f;

    for (;;)
    {
        temperature += 0.1f;

        if (xQueueSend(
                temperatureQueue,
                &temperature,
                pdMS_TO_TICKS(100)
            ) != pdPASS)
        {
            /* Handle queue-full condition. */
        }

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void Display_Task(void *argument)
{
    float receivedTemperature;

    for (;;)
    {
        if (xQueueReceive(
                temperatureQueue,
                &receivedTemperature,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Display or process received temperature. */
        }
    }
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();

    temperatureQueue = xQueueCreate(5, sizeof(float));

    if (temperatureQueue == NULL)
    {
        Error_Handler();
    }

    if (xTaskCreate(
            Sensor_Task, "Sensor", 256, NULL, 2, NULL
        ) != pdPASS)
    {
        Error_Handler();
    }

    if (xTaskCreate(
            Display_Task, "Display", 256, NULL, 1, NULL
        ) != pdPASS)
    {
        Error_Handler();
    }

    vTaskStartScheduler();

    Error_Handler();

    while (1)
    {
    }
}

Program Explanation

  1. A queue is created with five floating-point entries.
  2. The sensor task generates a temperature value.
  3. The sensor task sends the value into the queue.
  4. The display task waits for queue data.
  5. When data arrives, the display task receives and processes it.

Queue operations copy the item bytes. The example is illustrative; production sensor code should send a measured value and handle queue-full conditions according to the application's data policy.

6. Binary Semaphore

A binary semaphore has two logical states: available and unavailable. It is commonly used for synchronization between tasks or between an ISR and a task.

Common Applications

  • Signaling that an interrupt event occurred.
  • Waking a task when a peripheral operation completes.
  • Synchronizing producer and consumer operations.

Binary Semaphore APIs


SemaphoreHandle_t xSemaphoreCreateBinary();

BaseType_t xSemaphoreGive(
    SemaphoreHandle_t xSemaphore
);

BaseType_t xSemaphoreTake(
    SemaphoreHandle_t xSemaphore,
    TickType_t xTicksToWait
);

A newly created binary semaphore is initially empty. A task or ISR must give it before a successful take can occur.

7. Binary Semaphore Example

A task waits until another task signals that an event has occurred. 


#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t eventSemaphore;

void Event_Task(void *argument)
{
    for (;;)
    {
        if (xSemaphoreTake(
                eventSemaphore,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process the signaled event. */
        }
    }
}

void Signal_Task(void *argument)
{
    for (;;)
    {
        vTaskDelay(pdMS_TO_TICKS(2000));

        xSemaphoreGive(eventSemaphore);
    }
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();

    eventSemaphore = xSemaphoreCreateBinary();

    if (eventSemaphore == NULL)
    {
        Error_Handler();
    }

    xTaskCreate(Event_Task, "Event", 256, NULL, 2, NULL);
    xTaskCreate(Signal_Task, "Signal", 256, NULL, 1, NULL);

    vTaskStartScheduler();

    Error_Handler();

    while (1)
    {
    }
}

A binary semaphore can represent that an event occurred, but repeated gives may coalesce while the semaphore is already available. Use a queue or counting mechanism if every event must be preserved.

8. Counting Semaphore

A counting semaphore maintains a count rather than only two states. It is useful for tracking multiple available resources or counting events.

Example

Suppose an embedded system has three identical communication buffers. A counting semaphore initialized to three can track how many buffers are available.

Counting Semaphore API


SemaphoreHandle_t xSemaphoreCreateCounting(
    UBaseType_t uxMaxCount,
    UBaseType_t uxInitialCount
);

Example Usage


SemaphoreHandle_t bufferSemaphore;

void Buffer_Task(void *argument)
{
    for (;;)
    {
        if (xSemaphoreTake(
                bufferSemaphore,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Use one available buffer. */

            /* Return the buffer when finished. */
            xSemaphoreGive(bufferSemaphore);
        }
    }
}

int main(void)
{
    bufferSemaphore = xSemaphoreCreateCounting(3, 3);

    if (bufferSemaphore == NULL)
    {
        Error_Handler();
    }

    /* Create tasks and start the scheduler. */
}

This example demonstrates counting only. Real buffer management must also identify which buffer is allocated and ensure that the same buffer is not returned more than once.

9. Mutex in FreeRTOS

A mutex, or mutual exclusion semaphore, protects a shared resource from simultaneous access by multiple tasks.

Example Shared Resources

  • UART communication peripheral.
  • Shared I2C bus.
  • Shared data structure.
  • Common logging interface.
  • Shared memory buffer.

Mutex APIs


SemaphoreHandle_t xSemaphoreCreateMutex();

BaseType_t xSemaphoreTake(
    SemaphoreHandle_t xMutex,
    TickType_t xTicksToWait
);

BaseType_t xSemaphoreGive(
    SemaphoreHandle_t xMutex
);

A mutex has ownership: the task that successfully takes it must release it. Mutexes should not be used from an ISR.

10. Mutex Programming Example

Two tasks share a UART resource. A mutex prevents them from using the protected UART operation simultaneously. 


#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t uartMutex;

void UART_Task1(void *argument)
{
    for (;;)
    {
        if (xSemaphoreTake(
                uartMutex,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Perform UART operation. */

            xSemaphoreGive(uartMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void UART_Task2(void *argument)
{
    for (;;)
    {
        if (xSemaphoreTake(
                uartMutex,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Perform another UART operation. */

            xSemaphoreGive(uartMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();
    MX_USART2_UART_Init();

    uartMutex = xSemaphoreCreateMutex();

    if (uartMutex == NULL)
    {
        Error_Handler();
    }

    xTaskCreate(UART_Task1, "UART1", 256, NULL, 2, NULL);
    xTaskCreate(UART_Task2, "UART2", 256, NULL, 1, NULL);

    vTaskStartScheduler();

    Error_Handler();

    while (1)
    {
    }
}

In production code, keep the mutex held only while the shared resource is actually in use. Check the return value of every task-creation operation.

11. Priority Inversion

Priority inversion occurs when a high-priority task is blocked because a lower-priority task holds a resource that the high-priority task needs.

Example

  1. Low-priority Task L acquires a mutex.
  2. High-priority Task H becomes ready and needs the same mutex.
  3. Task H blocks because Task L owns the mutex.
  4. Medium-priority Task M becomes ready and executes.
  5. Task L cannot run to release the mutex, delaying Task H.

Priority Inheritance

FreeRTOS mutexes support priority inheritance. When a higher priority task blocks on a mutex held by a lower-priority task, the holder can temporarily inherit the higher priority so it can finish its critical section and release the mutex.

Priority inheritance reduces some priority inversion problems, but it does not eliminate every possible scheduling or resource-contention problem.

12. Difference Between Queue, Semaphore and Mutex

Feature Queue Semaphore Mutex
Main purpose Data communication Synchronization Resource protection
Stores data items Yes No application data payload No application data payload
Ownership No No Yes
ISR use ISR-safe queue APIs ISR-safe give APIs No
Typical application Send sensor readings Signal an event Protect shared UART

13. ISR Communication with Queues and Semaphores

Interrupt service routines must use the ISR-specific FreeRTOS APIs. Normal task APIs should not be called from an ISR.

Queue Send from ISR


void USART2_IRQHandler(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;
    uint8_t receivedByte = 0;

    /* Obtain receivedByte from the peripheral using
       the device-specific interrupt handling method. */

    xQueueSendFromISR(
        uartQueue,
        &receivedByte,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(higherPriorityTaskWoken);
}

Semaphore Give from ISR


void EXTI0_IRQHandler(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;

    /* Clear or acknowledge the EXTI source as required. */

    xSemaphoreGiveFromISR(
        eventSemaphore,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(higherPriorityTaskWoken);
}

These are conceptual patterns, not complete STM32 IRQ handlers. The peripheral interrupt must be serviced and cleared correctly. The exact yield macro and interrupt-priority restrictions depend on the selected FreeRTOS port. Cortex-M ports commonly restrict which NVIC priorities may call FreeRTOS ISR APIs.

14. Common Programming Mistakes

  • Using a normal queue or semaphore API inside an ISR.
  • Using a mutex inside an ISR.
  • Forgetting to check whether an object was created successfully.
  • Ignoring queue-full or queue-empty conditions.
  • Holding a mutex for too long.
  • Giving a mutex from a task that does not own it.
  • Using a binary semaphore when every event must be counted.
  • Configuring an interrupt priority that violates FreeRTOS port rules.

15. Placement-Oriented Interview Questions and Answers

Q1. What is a queue in FreeRTOS?

A queue is a kernel-managed object used to transfer data between tasks and compatible ISRs.

Q2. What is a binary semaphore?

A binary semaphore is a synchronization object with two logical states: available and unavailable.

Q3. What is a counting semaphore?

A counting semaphore maintains a count and can represent multiple available resources or pending events.

Q4. What is a mutex?

A mutex provides mutual exclusion to protect a shared resource from concurrent task access.

Q5. What is the main difference between a mutex and a binary semaphore?

A mutex has ownership and supports priority inheritance in FreeRTOS. A binary semaphore is primarily a synchronization mechanism and has no ownership.

Q6. Can a mutex be used inside an ISR?

No. Mutexes are task-level synchronization objects and must not be taken or given from an ISR.

Q7. What is priority inversion?

It occurs when a high-priority task is delayed by a lower-priority task holding a required resource.

Q8. What is priority inheritance?

It temporarily raises the priority of a mutex holder when a higher-priority task is blocked waiting for that mutex.

Q9. What is xQueueSendFromISR()?

It is an ISR-safe API used to send an item to a queue from an interrupt service routine.

Q10. What is the purpose of xSemaphoreGiveFromISR()?

It gives a semaphore from an ISR and can request a context switch when a higher-priority task is unblocked.

Q11. Why are queues useful in sensor applications?

They allow a sensor task to transfer readings to another task without requiring both tasks to execute simultaneously.

Q12. When should a queue be preferred over a binary semaphore?

Use a queue when actual data must be transferred or when multiple events must be retained as separate entries.

17. Lesson Summary

  • Queues transfer data between tasks and compatible ISRs.
  • Binary semaphores synchronize events.
  • Counting semaphores track counts of events or available resources.
  • Mutexes protect shared resources between tasks.
  • FreeRTOS mutexes support priority inheritance.
  • ISRs must use ISR-safe APIs.
  • Correct synchronization is essential for reliable embedded applications.
