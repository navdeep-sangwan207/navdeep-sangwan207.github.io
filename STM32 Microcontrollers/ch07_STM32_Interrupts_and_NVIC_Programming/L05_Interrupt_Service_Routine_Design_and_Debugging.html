2. What Is an Interrupt Service Routine?

An Interrupt Service Routine (ISR) is a special function executed when the processor accepts an interrupt or exception.

The ISR handles the event, acknowledges or clears the relevant interrupt condition when required, and returns control to the interrupted execution.

Basic ISR Execution Sequence


       Main Program
            |
            v
      Interrupt Occurs
            |
            v
    Processor Accepts Request
            |
            v
       Exception Entry
            |
            v
        Execute ISR
            |
            v
   Acknowledge Event / Handle
            |
            v
       Exception Return
            |
            v
     Resume Interrupted Code

3. Responsibilities of an ISR

An ISR should perform only the operations necessary to respond to the interrupt event.

Typical ISR Responsibilities

  • Identify the interrupt source.
  • Read essential peripheral status or data.
  • Acknowledge or clear the interrupt condition as required.
  • Store data in a buffer or update an event flag.
  • Notify the main loop or an RTOS task.
  • Return quickly to normal execution.
Example:

A UART receive ISR can read the received byte and place it into a ring buffer. The main loop can parse the command later instead of performing lengthy string processing inside the ISR.

4. ISR Design Best Practices

Recommended Practices

  1. Keep the ISR short and predictable.
  2. Acknowledge the interrupt source correctly.
  3. Avoid blocking delays.
  4. Avoid lengthy calculations.
  5. Avoid blocking communication operations.
  6. Use flags, queues or buffers to defer processing.
  7. Protect shared data where necessary.
  8. Consider interrupt priority and execution time.
  9. Ensure nested interrupts cannot exhaust the stack.
  10. Measure timing under realistic operating conditions.

Operations to Avoid in an ISR

Operation Why It Is Risky
HAL_Delay() Can block execution and may depend on a tick interrupt that cannot run.
Long loops Increase interrupt blocking time.
Blocking UART transmission Can keep the processor in the ISR for too long.
Large data processing Increases ISR execution time.
Unbounded waiting Can prevent timely handling of other events.

5. Shared Data Between ISR and Main Program

A shared variable is a variable accessed by both an ISR and the main program.

Since an ISR can execute asynchronously relative to normal code, shared data must be handled carefully.

Example: Shared Event Flag

#include "main.h"

volatile uint8_t timer_event = 0;

void HAL_TIM_PeriodElapsedCallback(
    TIM_HandleTypeDef *htim)
{
    if (htim->Instance == TIM2)
    {
        timer_event = 1;
    }
}

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();
    MX_TIM2_Init();

    HAL_TIM_Base_Start_IT(&htim2);

    while (1)
    {
        if (timer_event != 0)
        {
            timer_event = 0;

            /* Process the event outside the ISR */
        }
    }
}

The ISR sets the event flag. The main loop checks the flag and performs the required processing.

This simple flag is suitable when losing repeated events is acceptable or the event rate is controlled. If multiple events must be counted or preserved, use an appropriate counter, queue or buffer.

6. Understanding the volatile Keyword

The volatile keyword tells the compiler that a variable's value can change in ways not visible through the current execution flow, so accesses must follow the language's volatile rules.

Example

volatile uint8_t interrupt_flag = 0;

void EXTI0_IRQHandler(void)
{
    interrupt_flag = 1;
}

The main program can read the flag: 

while (1)
{
    if (interrupt_flag)
    {
        interrupt_flag = 0;

        /* Handle event */
    }
}

Important Properties of volatile

  • Prevents certain compiler optimizations of volatile accesses.
  • Useful for memory-mapped hardware registers.
  • Useful for variables shared with interrupt handlers.
  • Does not make operations atomic.
  • Does not provide a general synchronization mechanism.
  • Does not automatically protect compound operations.
A volatile variable is not automatically thread-safe. Use atomic operations, critical sections or suitable synchronization mechanisms when data consistency requires them.

7. Atomicity and Race Conditions

What Is Atomicity?

An operation is atomic when it appears indivisible to other execution contexts.

What Is a Race Condition?

A race condition occurs when the result of an operation depends on the timing or interleaving of accesses by multiple execution contexts.

Example: Shared Counter

volatile uint32_t event_count = 0;

void EXTI0_IRQHandler(void)
{
    event_count++;
}

The increment is a read-modify-write operation. It should not be assumed atomic merely because event_count is volatile.

Critical Section Concept

uint32_t primask = __get_PRIMASK();

__disable_irq();

/* Protect a short shared-data operation */

__set_PRIMASK(primask);
This example masks configurable interrupts globally and restores the previous PRIMASK state. Keep the protected section very short. NMI and HardFault are not masked by PRIMASK. Use an appropriate synchronization design for the actual application.

8. Interrupt Stack Usage

Cortex-M processors use a stack during exception handling. On exception entry, the processor automatically stacks a basic register frame.

The basic frame normally contains:

  • R0
  • R1
  • R2
  • R3
  • R12
  • LR
  • PC
  • xPSR

Additional stack space may be needed for compiler register saving, local variables, nested interrupts, alignment padding and floating-point context where supported and used.

Stack Usage Considerations

  • Keep ISR local variables small.
  • Avoid large local arrays.
  • Limit nested interrupt depth.
  • Estimate worst-case stack usage.
  • Check linker and startup stack configuration.
  • Use stack monitoring where available.

9. Interrupt Debugging Using STM32CubeIDE

STM32CubeIDE provides debugging features that help identify interrupt configuration and execution problems.

Debugging Procedure

  1. Build the project and resolve compilation errors.
  2. Start a debug session using ST-LINK or a supported target.
  3. Set a breakpoint in the interrupt handler.
  4. Set another breakpoint in the HAL callback if applicable.
  5. Run the processor.
  6. Trigger the peripheral event.
  7. Check whether the handler breakpoint is reached.
  8. Inspect peripheral and NVIC registers.
  9. Check interrupt enable, pending and priority settings.
  10. Step through the handler and inspect the return path.

Useful Debugging Views

  • Disassembly view.
  • Registers view.
  • Expressions and Variables view.
  • Memory view.
  • Peripheral register view, where supported.
  • Call Stack view.
Live register inspection and peripheral behavior depend on the selected target and debugger support. A hardware debugger is required to validate real external pin events on a physical board.

10. Measuring ISR Execution Time

Measuring ISR execution time helps verify that the interrupt handler meets timing requirements.

Method 1: GPIO Timing Measurement

Toggle a GPIO pin at the beginning and end of an ISR, then measure the pulse width using an oscilloscope or logic analyzer. 

void EXTI0_IRQHandler(void)
{
    HAL_GPIO_WritePin(
        GPIOB,
        GPIO_PIN_0,
        GPIO_PIN_SET
    );

    /* Handle interrupt event */

    HAL_GPIO_WritePin(
        GPIOB,
        GPIO_PIN_0,
        GPIO_PIN_RESET
    );
}

Method 2: Cortex-M Cycle Counter

On supported Cortex-M implementations, the DWT cycle counter can be used to measure elapsed processor cycles. 

uint32_t start_cycle;
uint32_t end_cycle;
uint32_t elapsed_cycles;

start_cycle = DWT->CYCCNT;

/* Code being measured */

end_cycle = DWT->CYCCNT;

elapsed_cycles = end_cycle - start_cycle;
DWT cycle-counter availability and enable procedure vary by Cortex-M implementation and debug configuration. Counter wraparound must also be considered. The example measures the code placed between the two reads; it does not automatically include exception-entry overhead.

11. Common ISR Debugging Problems

Problem Possible Cause Suggested Check
ISR never executes Interrupt source or NVIC not enabled. Check peripheral configuration and NVIC registers.
ISR executes repeatedly Interrupt condition not acknowledged. Inspect peripheral and EXTI pending flags.
Unexpected ISR order Priority grouping or priority configuration. Inspect priority registers and grouping.
Main loop appears stuck ISR too long or interrupt storm. Measure ISR execution and inspect pending sources.
Shared data is inconsistent Race condition or non-atomic access. Review synchronization and critical sections.
HardFault during interrupt Invalid memory access or stack problem. Inspect fault registers, stack and call stack.
Callback is not reached HAL handler not called or wrong callback condition. Inspect IRQ handler and HAL dispatch path.

12. HardFault and Interrupt Fault Analysis

A HardFault is a processor exception that can occur when a serious fault is detected or when another fault cannot be handled by the configured fault handlers.

Common Causes

  • Invalid pointer dereference.
  • Stack overflow or stack corruption.
  • Invalid memory access.
  • Incorrect function pointer or return address.
  • Faults occurring during interrupt execution.
  • Incorrect peripheral register access.

Debugging Steps

  1. Stop execution in HardFault_Handler.
  2. Inspect the processor's stacked exception frame.
  3. Examine the stacked PC and LR values.
  4. Inspect CFSR, HFSR and other supported fault registers.
  5. Locate the instruction that caused the fault.
  6. Check pointer validity, stack limits and memory layout.
Fault status registers and available fault types depend on the Cortex-M core. Use the selected STM32 reference manual and core documentation when interpreting fault status.

13. Placement-Oriented Interview Questions

Q1. What is an ISR?

An ISR is a function executed by the processor to handle an interrupt or exception.

Q2. Why should an ISR be short?

A short ISR reduces interrupt blocking time and helps other events meet their response deadlines.

Q3. Why should HAL_Delay() generally be avoided inside an ISR?

It is a blocking delay and may depend on a system tick interrupt that cannot execute while the current ISR is active or has a higher priority.

Q4. Why is volatile used for ISR-shared variables?

It prevents certain compiler optimizations that could otherwise hide changes made outside the current execution flow.

Q5. Does volatile guarantee atomicity?

No. Volatile does not guarantee atomic read-modify-write operations or provide full synchronization.

Q6. What is a race condition?

A race condition occurs when the result depends on the timing or interleaving of concurrent accesses.

Q7. What is a critical section?

A critical section is a protected region in which access to shared resources is controlled to prevent unsafe concurrent operations.

Q8. What is interrupt nesting?

Interrupt nesting occurs when a higher-priority interrupt preempts an ISR that is already executing.

Q9. How can ISR execution time be measured?

It can be measured using GPIO timing with an oscilloscope or by using a supported processor cycle counter such as DWT CYCCNT.

Q10. What is interrupt latency?

It is the time between an interrupt request becoming eligible and the beginning of its handler.

Q11. What happens if an interrupt flag is not cleared?

The interrupt may remain pending or be requested again, depending on the peripheral's interrupt and flag-clearing behavior.

Q12. How do you debug an ISR that does not execute?

Check the peripheral interrupt source, NVIC enable, priority, vector table, IRQ handler name and interrupt masking state.

Q13. What is stack overflow in interrupt handling?

Stack overflow occurs when interrupt and program stack usage exceeds the allocated stack space, potentially corrupting memory and causing faults.

Q14. What is the purpose of an event flag?

An event flag allows an ISR to signal the main program that an event occurred, so processing can be deferred outside the ISR.

15. Lesson Summary

  • ISR handles an accepted interrupt or exception.
  • Keep interrupt handlers short and predictable.
  • Acknowledge peripheral interrupt conditions correctly.
  • Use flags, queues and buffers to defer processing.
  • Volatile does not guarantee atomicity or synchronization.
  • Critical sections can protect short shared-data operations.
  • Nested interrupts increase stack and timing requirements.
  • GPIO and DWT cycle counter methods can measure execution time.
  • STM32CubeIDE helps inspect handlers, registers and fault states.
  • Correct interrupt design improves firmware reliability.
