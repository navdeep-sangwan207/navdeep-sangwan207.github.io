2. Runtime Memory Organization

During program execution, an STM32 application uses different memory areas for instructions, variables, function calls and dynamic allocation. 

             STM32 MEMORY
                  |
       +----------+----------+
       |                     |
       v                     v
    FLASH MEMORY          SRAM MEMORY
       |                     |
       |              +------+------+
       |              |      |      |
       v              v      v      v
     .text          .data  .bss   Runtime
     .rodata                       Memory
                                     |
                            +--------+--------+
                            |                 |
                            v                 v

                       Function calls    Dynamic memory
                       Local variables   malloc/free

The exact layout and stack/heap arrangement are determined by the linker script, startup code and runtime library.

3. What Is Stack Memory?

The stack is a memory area used to manage function calls and temporary execution data. It commonly stores return information, saved registers and automatic local variables.

Stack Characteristics

  • Supports function calls and returns.
  • Stores automatic local variables when allocated in memory.
  • Stores saved registers and return context.
  • Supports interrupt and exception context stacking.
  • Typically follows a last-in, first-out model.
  • On Cortex-M, the stack normally grows toward lower addresses.

Example

#include <stdint.h>

void Calculate(void)
{
    uint32_t a = 10;
    uint32_t b = 20;
    uint32_t result;

    result = a + b;
}

int main(void)
{
    Calculate();

    while (1)
    {
    }
}

The local variables have automatic storage duration. The compiler may keep some values in registers rather than placing them in stack memory.

4. How Stack Works During Function Calls

A function call may create a stack frame containing local storage, saved registers and other information required by the calling convention. 

main()
  |
  | calls Function_A()
  v
Function_A()
  |
  | calls Function_B()
  v
Function_B()
  |
  v
Function_B() returns
  |
  v
Function_A() resumes
  |
  v
Function_A() returns
  |
  v
main() resumes

When a function returns, its active stack frame is released according to the compiler's calling convention.

Stack Frame May Contain

  • Return address or return-state information.
  • Saved registers.
  • Local variables that require stack storage.
  • Spilled register values.
  • Temporary data and alignment padding.
The exact stack frame layout is compiler- and optimization-dependent. Do not assume every local variable is stored on the stack.

5. What Is Heap Memory?

The heap is a memory region used for dynamic memory allocation during program execution. In C, common dynamic memory functions are malloc(), calloc(), realloc() and free().

Heap Characteristics

  • Supports runtime memory allocation.
  • Memory remains allocated until released or reclaimed by the runtime.
  • Can be used for variable-size data structures.
  • May suffer from fragmentation.
  • Requires careful allocation failure handling.

Example

#include <stdlib.h>
#include <stdint.h>

void Heap_Example(void)
{
    uint32_t *ptr;

    ptr = malloc(5U * sizeof(uint32_t));

    if (ptr != NULL)
    {
        ptr[0] = 10;
        ptr[1] = 20;

        free(ptr);
        ptr = NULL;
    }
}
Embedded systems often avoid frequent dynamic allocation because of limited RAM, fragmentation, unpredictable allocation time and failure-handling complexity. Some projects use fixed-size memory pools or static allocation instead.

6. Stack vs Heap

Feature Stack Heap
Purpose Function execution and automatic storage Dynamic allocation
Management Compiler/runtime calling convention Allocator and application
Lifetime Usually limited to function or execution context Until explicitly released or reclaimed
Typical access Local variables and saved context Allocated objects through pointers
Common problem Stack overflow Fragmentation and leaks
Embedded usage Required for normal execution Optional and application-dependent

7. Static vs Dynamic Memory Allocation

Static Allocation

Static allocation reserves storage with a fixed size and lifetime determined by the program's declarations and memory layout. 

#include <stdint.h>

static uint8_t sensor_buffer[100];

void Process_Data(void)
{
    sensor_buffer[0] = 25;
}

Dynamic Allocation

Dynamic allocation requests memory while the application is running. 

#include <stdlib.h>
#include <stdint.h>

void Allocate_Buffer(void)
{
    uint8_t *buffer = malloc(100U);

    if (buffer != NULL)
    {
        buffer[0] = 25U;

        free(buffer);
        buffer = NULL;
    }
}
Static Allocation Dynamic Allocation
Size is fixed at build time. Size can be selected at runtime.
Predictable memory usage. Allocation may fail at runtime.
No general-purpose heap fragmentation. Can cause heap fragmentation.
Often preferred for predictable embedded systems. Useful when variable-size allocation is required.

8. Stack Overflow

Stack overflow occurs when execution requires more stack space than the configured stack region can provide.

Common Causes

  • Large local arrays.
  • Deep function call chains.
  • Uncontrolled recursion.
  • Nested interrupts with significant context usage.
  • Large local structures.
  • Insufficient RTOS task stack allocation.

Example of Risky Code

void Process_Data(void)
{
    uint8_t large_buffer[10000];

    large_buffer[0] = 10;
}

A large automatic array can consume substantial stack space. Whether this overflows depends on the configured stack size and other runtime usage.

Recursive Function Example

void Recursive_Function(void)
{
    Recursive_Function();
}

This function has no terminating condition and can exhaust the available stack.

Prevention

  • Estimate worst-case stack usage.
  • Avoid uncontrolled recursion.
  • Move large buffers to suitable static storage or memory pools.
  • Check nested interrupt and task stack requirements.
  • Use stack watermark or guard techniques where available.
  • Inspect linker and debugger memory information.

9. Heap Fragmentation and Memory Leak

Heap Fragmentation

Heap fragmentation occurs when free memory becomes divided into smaller non-contiguous blocks. A large allocation may fail even when the total free memory appears sufficient. 

Initial Heap:
+--------------------------------+
|             FREE               |
+--------------------------------+

After Allocations:
+----------+--------+-------------+
| Used A   | Free   | Used B      |
+----------+--------+-------------+

After Freeing A:
+----------+--------+-------------+
| Free     | Free   | Used B      |
+----------+--------+-------------+

Memory Leak

A memory leak occurs when allocated memory is no longer reachable by the application but has not been released. 

#include <stdlib.h>

void Memory_Leak_Example(void)
{
    int *ptr = malloc(10U * sizeof(int));

    if (ptr != NULL)
    {
        ptr[0] = 100;

        /* Missing free(ptr). */
    }
}

Prevention

  • Release allocated memory when no longer required.
  • Check every allocation result.
  • Avoid repeated allocation and deallocation in critical real-time paths.
  • Use fixed-size pools for predictable workloads.
  • Track allocation ownership carefully.

10. Firmware Memory Usage

Firmware memory usage is generally evaluated in terms of Flash and RAM consumption.

Memory Type Common Contents
Flash Code, read-only data, initialized-data load image and constants.
RAM Writable data, BSS, stack, heap and runtime buffers.

Example Memory Report

Program Size:
Code      = 32000 bytes
RO-data   =  4000 bytes
RW-data   =  1200 bytes
ZI-data   =  2800 bytes

Flash Load Usage:
32000 + 4000 + 1200
= 37200 bytes

Static RAM Usage:
1200 + 2800
= 4000 bytes

This is an illustrative report. Actual toolchains may classify sections differently. Stack and heap reservations must also be considered when estimating total RAM needs.

11. Estimating Stack Usage

Stack requirements should be estimated from the worst-case execution path, including function calls, interrupts and task contexts.

Example Estimate

Component Illustrative Usage
Main function and call chain 200 bytes
Local variables and temporary data 150 bytes
Interrupt context allowance 100 bytes
Safety margin 150 bytes
Estimated Total 600 bytes

The estimate is illustrative, not a universal stack-size recommendation. Actual usage should be measured or analyzed for the compiler, optimization level and application.

12. Firmware Memory Optimization

Flash Optimization

  • Enable suitable compiler optimization.
  • Remove unused code and data through linker garbage collection where appropriate.
  • Avoid unnecessary large lookup tables.
  • Use appropriate integer types.
  • Review library and debugging code included in Release builds.

RAM Optimization

  • Use appropriately sized buffers.
  • Reuse temporary buffers when safe.
  • Avoid unnecessary global arrays.
  • Limit stack-heavy local variables.
  • Use static allocation for predictable data requirements.
  • Review task stack sizes in RTOS applications.
Optimization must not compromise correctness. Do not shrink stack sizes or buffers without checking worst-case usage and transfer rates.

13. Memory Usage Inspection in STM32CubeIDE

  1. Build the STM32 project.
  2. Review the build console memory summary.
  3. Open the generated linker map file.
  4. Inspect Flash and RAM section sizes.
  5. Check linker errors for region overflow.
  6. Inspect variable addresses in the debugger.
  7. Review stack and heap configuration in the linker script or startup files.
  8. Use runtime stack watermarking or guards if implemented.

Common Files and Settings

Item Purpose
Linker script (.ld) Defines memory regions and section placement.
Map file (.map) Shows section and symbol memory usage.
Startup assembly file Defines reset handling and initial stack setup.
Build memory summary Reports program and data size.

14. RTOS Stack Considerations

In an RTOS application, each task normally has its own stack. Stack size must be selected according to task execution requirements. 

Task 1
  |
  +-- Task 1 Stack

Task 2
  |
  +-- Task 2 Stack

Task 3
  |
  +-- Task 3 Stack

Interrupt Handling
  |
  +-- Core/Handler Stack Context
  • Each task requires sufficient stack memory.
  • Task stack overflow can corrupt application data.
  • FreeRTOS provides stack high-water-mark APIs.
  • Stack overflow checking can be enabled in FreeRTOS configuration.
  • Interrupt stack behavior depends on the Cortex-M core and RTOS port.
FreeRTOS task stack-size units depend on the API and port configuration. In common FreeRTOS APIs, stack depth is specified in words rather than bytes. Check the selected port and version.

15. Placement Interview Questions and Answers

Q1. What is stack memory?

Stack memory supports function calls, saved context and automatic local storage.

Q2. What is heap memory?

Heap memory is used for dynamic memory allocation during program execution.

Q3. What is the main difference between stack and heap?

Stack usage is managed through function execution and calling conventions, whereas heap memory is managed by a dynamic allocator.

Q4. What is stack overflow?

It occurs when stack usage exceeds the available stack region.

Q5. What is heap fragmentation?

It is the division of free heap memory into smaller non-contiguous blocks.

Q6. What is a memory leak?

It occurs when allocated memory is not released and becomes unavailable for reuse.

Q7. What is static memory allocation?

It reserves fixed-size storage according to program declarations and memory layout.

Q8. Why is dynamic allocation often limited in embedded systems?

It can introduce fragmentation, allocation failures and less predictable execution time.

Q9. How can stack overflow be detected?

Techniques include stack watermarking, guard regions, MPU protection where available and runtime diagnostics.

Q10. What is a linker map file?

It reports how the linker placed program sections and symbols into memory.

Q11. How can RAM usage be reduced?

Optimize buffer sizes, avoid unnecessary arrays, reuse memory safely and use suitable static allocation.

Q12. Why does each RTOS task need a stack?

Each task needs execution context and storage for its function calls and local data when it runs.

  • Stack memory manages function execution and automatic storage.
