2. Introduction to STM32 Memory

An STM32 microcontroller contains different memory regions for storing firmware, variables, temporary data and peripheral registers.

The main memory types are:

  • Flash: Non-volatile memory used to store firmware and persistent constants.
  • SRAM: Volatile memory used for runtime variables, stack, heap and buffers.
  • System memory: Device-specific memory that may contain the factory bootloader.
  • Option bytes: Configuration storage for device-specific boot and protection settings.

3. Flash Memory

Flash is non-volatile memory. It retains its contents when power is removed. STM32 firmware is commonly programmed into internal Flash memory.

Features of Flash Memory

  • Non-volatile storage.
  • Stores program instructions.
  • Can store read-only constants.
  • Requires erase operations before programming in many STM32 Flash implementations.
  • Has limited erase/program endurance.
  • Read and programming capabilities depend on the device.

Typical STM32 Flash Uses

  • Application firmware.
  • Bootloader code.
  • Constant lookup tables.
  • Calibration data, when designed for persistent storage.
  • Firmware update images or metadata.
Flash capacity, sector/page organization, programming width, endurance and read-while-write capabilities vary across STM32 families. Always check the exact device datasheet and reference manual.

4. SRAM (Static Random Access Memory)

SRAM is volatile memory used while the microcontroller is running. Its contents are generally lost when power is removed.

Features of SRAM

  • Fast runtime memory access.
  • Stores global and local variables.
  • Stores stack and heap data.
  • Stores communication and DMA buffers.
  • Does not require Flash erase cycles for normal writes.

Example

#include <stdint.h>

uint32_t sensor_value = 0;

void Read_Sensor(void)
{
    uint16_t adc_result = 2048;

    sensor_value = adc_result;
}

The global variable and local variable normally occupy SRAM at runtime, although exact placement depends on initialization, compiler and linker settings.

6. STM32 Memory Map

The Cortex-M architecture defines a memory address space. STM32 devices implement selected regions within that address space. The exact physical mapping is device-specific.

Architectural Region Address Range Typical Purpose
Code 0x00000000 – 0x1FFFFFFF Code and memory-mapped executable regions.
SRAM 0x20000000 – 0x3FFFFFFF On-chip RAM and related mappings.
Peripheral 0x40000000 – 0x5FFFFFFF Memory-mapped peripheral registers.
External RAM 0x60000000 – 0x9FFFFFFF External memory interface region.
External Device 0xA0000000 – 0xDFFFFFFF External device region.
Private Peripheral and System 0xE0000000 – 0xFFFFFFFF Core system and private peripheral space.
These are architectural address regions, not a promise that every address contains physical memory on every STM32. For example, many STM32 devices map internal Flash at 0x08000000 and SRAM at 0x20000000. Check the exact device memory map.

8. Memory-Mapped I/O

STM32 peripherals are accessed through memory-mapped registers. The CPU reads and writes specific addresses to control peripheral hardware.

Example: GPIO Register Access

#include "stm32f4xx.h"

void GPIOA_Init(void)
{
    /* Enable GPIOA clock. */
    RCC->AHB1ENR |= RCC_AHB1ENR_GPIOAEN;

    /* Configure PA5 as output. */
    GPIOA->MODER &= ~(3U << (5U * 2U));
    GPIOA->MODER |=  (1U << (5U * 2U));
}

void LED_ON(void)
{
    GPIOA->BSRR = (1U << 5U);
}

void LED_OFF(void)
{
    GPIOA->BSRR = (1U << (5U + 16U));
}

This example targets an STM32F4-style GPIO register layout. The GPIO clock, pin availability and register definitions must be verified for the selected device.

Peripheral registers are not ordinary RAM. Their read and write behavior is defined by the hardware reference manual. Use CMSIS device headers rather than guessing peripheral addresses.

9. Program Memory and Data Memory

A compiled embedded application contains several logical sections that the linker places into Flash and RAM.

Section Purpose Typical Placement
.text Executable instructions Flash
.rodata Read-only constants Flash
.data Initialized writable variables RAM at runtime
.bss Zero-initialized or uninitialized static-storage variables RAM
Stack Function calls and automatic variables RAM
Heap Dynamic memory allocation RAM

Example

#include <stdint.h>

const uint32_t lookup_table[4] =
{
    10, 20, 30, 40
};

uint32_t initialized_value = 100;

uint32_t zero_initialized_value = 0;

void main_function(void)
{
    uint32_t local_value = 50;
}

The linker and compiler determine the actual section placement. A const-qualified object is not automatically guaranteed to be placed in Flash on every toolchain and memory configuration.

Important Operations

  1. The processor obtains the initial stack pointer from the vector table.
  2. The reset handler begins execution.
  3. Initialized data is copied from its load location in Flash to its runtime location in RAM.
  4. The BSS region is cleared to zero.
  5. System initialization and C runtime setup are performed.
  6. The application enters main().
The exact startup sequence and the position of SystemInit and runtime initialization depend on the startup file, CMSIS package, compiler and project configuration.

11. Flash Programming and Erase Operations

Flash programming stores data in internal non-volatile memory. Many STM32 Flash implementations require the relevant page or sector to be erased before programming.

General Flash Programming Sequence

Unlock Flash Controller
          |
          v
Select Page or Sector
          |
          v
Erase Required Region
          |
          v
Program Data
          |
          v
Verify Programmed Data
          |
          v
Lock Flash Controller

Important Flash Considerations

  • Erase granularity may be a page, sector or another device-defined unit.
  • Programming width and alignment are device-specific.
  • Flash endurance is limited.
  • Power loss during an update can corrupt stored data.
  • Firmware update design should include validation and recovery planning.
Never erase or program an arbitrary Flash address. Protect the application, bootloader, option bytes and data regions according to the linker script and device documentation.

12. Memory Protection and Access Restrictions

Some Cortex-M cores provide a Memory Protection Unit (MPU). The MPU can define access permissions and memory attributes for selected regions.

  • Read and write access permissions.
  • Execute-never protection.
  • Memory region attributes.
  • Isolation of selected memory areas.
  • Detection of certain invalid memory accesses.

MPU availability and features depend on the Cortex-M core and STM32 model. The MPU is not present on every STM32.

13. Memory Debugging in STM32CubeIDE

  1. Build the firmware and inspect build errors.
  2. Open the debugger and halt the processor.
  3. Open the Memory view.
  4. Enter a valid SRAM or Flash address.
  5. Inspect variable addresses in the Expressions view.
  6. Open the map file to inspect memory section usage.
  7. Check stack and heap allocation settings.
  8. Inspect linker errors for memory overflow.

14. Placement Interview Questions and Answers

Q1. What is Flash memory?

Flash is non-volatile memory used to store firmware and persistent data.

Q2. What is SRAM?

SRAM is volatile memory used for runtime variables, stack, heap and buffers.

Q3. What is the difference between Flash and SRAM?

Flash retains data without power and is used mainly for program storage. SRAM provides runtime read/write storage and normally loses its contents when power is removed.

Q4. Where is STM32 firmware stored?

It is commonly stored in internal Flash, although boot and execution arrangements depend on the device configuration.

Q5. What is a memory map?

A memory map defines the address regions assigned to code, RAM, peripherals and other memory resources.

Q6. What is memory-mapped I/O?

It is a method in which peripheral registers are accessed through specific memory addresses.

Q7. What is the .data section?

It contains initialized writable global and static-storage variables, typically loaded from Flash and copied to RAM at startup.

Q8. What is the .bss section?

It contains zero-initialized or otherwise uninitialized static-storage variables and is normally cleared at startup.

Q9. What is the purpose of startup code?

It initializes the runtime environment, including stack setup and memory initialization, before application execution.

Q10. What is a linker script?

It defines how program sections and symbols are placed into available memory regions.

Q11. Why is Flash endurance important?

Flash supports a limited number of erase and program cycles, so frequent updates require careful data-storage design.

Q12. What is an MPU?

A Memory Protection Unit controls access permissions and memory attributes for configured memory regions on supported cores.

15. Practical Exercises

  1. Identify Flash and SRAM regions in the selected STM32 memory map.
  2. Inspect the .text, .data and .bss sections in a map file.
  3. Find the address of a global variable using the debugger.
  4. Inspect an array stored in SRAM.
  5. Read a constant lookup table through the debugger.
  6. Inspect the vector table and reset handler in the startup code.
  7. Compare the Flash and RAM usage reported by the linker.
  8. Identify the memory region used by a DMA buffer.

16. Lesson Summary

  • Flash stores firmware and persistent data.
  • SRAM stores runtime data and buffers.
  • The memory map defines address regions.
  • Peripheral registers use memory-mapped I/O.
  • Linker sections organize program and data memory.
  • Startup code initializes runtime memory before main().
  • Flash erase and programming rules are device-specific.
  • Memory debugging helps identify allocation and access problems.
