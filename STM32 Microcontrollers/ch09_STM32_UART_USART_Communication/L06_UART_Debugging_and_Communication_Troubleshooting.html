2. UART Debugging Overview

UART debugging is the process of identifying and correcting problems in serial communication between an STM32 microcontroller and another device.

Common Debugging Tools

  • STM32CubeIDE debugger
  • USB-to-UART converter
  • Serial terminal software
  • Digital multimeter
  • Oscilloscope
  • Logic analyzer
A serial terminal helps inspect received characters. An oscilloscope or logic analyzer helps verify the actual electrical waveform and timing.

3. Verify UART Hardware Connections

UART communication requires correct signal wiring between the STM32 and the external device.

Basic Connection

STM32 Board                 USB-to-UART Adapter

UART_TX  -----------------> RX
UART_RX  <----------------- TX
GND      ------------------ GND

Connection Checklist

  • Connect STM32 TX to the external RX.
  • Connect STM32 RX to the external TX.
  • Connect a common ground when required.
  • Verify the selected UART pins.
  • Verify the GPIO alternate-function configuration.
  • Check the voltage compatibility of both devices.
STM32 UART pins normally use logic-level signals, not RS-232 voltage levels. Do not connect an RS-232 interface directly to MCU pins. Use a suitable level-translator or transceiver. Also verify whether the selected STM32 pin is 5 V tolerant before connecting a 5 V signal.

4. Verify Baud Rate and Frame Format

Both communicating devices must use compatible UART settings.

Example Configuration

ParameterSTM32Serial Terminal
Baud rate115200115200
Data bits88
ParityNoneNone
Stop bits11
Flow controlNoneNone

This is commonly called 115200, 8-N-1.

Bit Duration

Bit duration is the reciprocal of the baud rate for conventional binary UART signaling. 

Bit Duration = 1 / Baud Rate

For 115200 baud:

Bit Duration = 1 / 115200
             ≈ 8.68 microseconds

Incorrect baud rate, clock configuration, parity, word length or stop-bit settings can produce corrupted characters or framing errors.

5. Testing UART Using a USB-to-UART Converter

A USB-to-UART converter provides a serial connection between a computer and the STM32 UART interface.

Testing Procedure

  1. Connect the converter TX to STM32 RX.
  2. Connect the converter RX to STM32 TX.
  3. Connect the required ground reference.
  4. Connect the converter to the computer.
  5. Identify its COM port in Device Manager.
  6. Open a serial terminal.
  7. Select the correct COM port and UART settings.
  8. Run the STM32 firmware and test transmission.

Example Test Message

STM32 UART Communication Test
UART is working correctly.
Baud Rate: 115200
Common serial terminal applications include PuTTY, Tera Term and RealTerm. Use a terminal configuration that matches the firmware.

6. UART Loopback Testing

Loopback testing checks whether transmitted UART data can be received back by the same UART interface.

Basic Wiring

STM32 UART

TX  --------+
            |
            +-------- RX

Connect the selected UART TX pin to its RX pin where the board and peripheral configuration allow this test.

Polling-Based Loopback Example

#include "main.h"

extern UART_HandleTypeDef huart2;

uint8_t tx_data[] = "UART LOOPBACK";
uint8_t rx_data[sizeof(tx_data)];

void UART_Loopback_Test(void)
{
    if (HAL_UART_Transmit(
            &huart2,
            tx_data,
            sizeof(tx_data) - 1,
            1000) != HAL_OK)
    {
        Error_Handler();
    }

    if (HAL_UART_Receive(
            &huart2,
            rx_data,
            sizeof(tx_data) - 1,
            1000) != HAL_OK)
    {
        Error_Handler();
    }

    if (memcmp(
            tx_data,
            rx_data,
            sizeof(tx_data) - 1) == 0)
    {
        // Loopback test passed.
    }
    else
    {
        // Data mismatch.
    }
}

Include <string.h> for memcmp().

This blocking example requires the loopback connection to be established before transmission. It assumes the selected UART supports simultaneous TX and RX operation and that the pins are configured correctly.

7. Debugging UART Using STM32CubeIDE

Useful Debugging Features

  • Breakpoints
  • Step Into, Step Over and Step Return
  • Live Expressions
  • Variables and Expressions views
  • Peripheral Registers view
  • Call Stack view
  • Memory Browser

Variables to Inspect

huart2.gState
huart2.RxState
huart2.ErrorCode
rx_buffer
tx_buffer

The exact HAL handle members can vary by HAL version. Inspect the structure definition in the installed STM32 HAL driver.

Debugging Steps

  1. Set a breakpoint before the UART operation.
  2. Verify that the correct UART handle is used.
  3. Step over the HAL transmit or receive call.
  4. Check the returned HAL status.
  5. Inspect the transfer state and error code.
  6. Set breakpoints inside UART callbacks.
  7. Inspect the receive and transmit buffers.
Breakpoints can change real-time behavior. For high-speed or continuous UART communication, use non-intrusive methods such as GPIO timing markers, logic analyzers or trace facilities where available.

8. UART Error Conditions

ErrorDescriptionPossible Cause
Parity Error (PE) Received parity check failed. Incorrect parity configuration or signal corruption.
Framing Error (FE) Expected stop-bit condition was not detected. Baud mismatch, noise or incorrect frame format.
Noise Error (NE) Noise was detected during reception. Electrical interference or poor signal quality.
Overrun Error (ORE) Received data was not read before another arrived. CPU or DMA did not service the receive data in time.

Error flags and clearing procedures depend on the STM32 USART implementation. Follow the reference manual and HAL driver documentation for the selected device.

9. Checking HAL UART Error Codes

STM32 HAL provides HAL_UART_GetError() to retrieve the error status associated with a UART handle.

Example

void HAL_UART_ErrorCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART2)
    {
        uint32_t error_code = HAL_UART_GetError(huart);

        if (error_code & HAL_UART_ERROR_PE)
        {
            // Handle parity error.
        }

        if (error_code & HAL_UART_ERROR_FE)
        {
            // Handle framing error.
        }

        if (error_code & HAL_UART_ERROR_NE)
        {
            // Handle noise error.
        }

        if (error_code & HAL_UART_ERROR_ORE)
        {
            // Handle overrun error.
        }
    }
}

The callback should record the error and schedule recovery rather than perform lengthy processing. Error recovery may require restarting a receive operation or clearing peripheral error conditions, depending on the HAL and device.

10. Common UART Problems and Solutions

ProblemLikely CauseSolution
No output in terminal Wrong COM port or TX wiring Check port selection and TX-to-RX connection.
Unreadable characters Baud or frame mismatch Match baud, data bits, parity and stop bits.
Receive not working Wrong RX pin or alternate function Verify GPIO and peripheral configuration.
Interrupt callback missing NVIC or handler configuration issue Check IRQ handler and interrupt enable settings.
DMA callback missing DMA IRQ not configured Check DMA mapping, NVIC and generated handlers.
Characters lost Insufficient buffering or delayed processing Use appropriate buffering and DMA where needed.
Random communication errors Noise, grounding or electrical incompatibility Inspect wiring, signal quality and voltage levels.

11. UART Signal Analysis Using an Oscilloscope

An oscilloscope can help verify the electrical waveform of UART communication.

What to Check

  • Idle state is normally logic HIGH.
  • Start bit is logic LOW.
  • Data bits are transmitted least-significant bit first in conventional UART framing.
  • Parity bit is present only when configured.
  • Stop bit returns the line to logic HIGH.
  • Bit duration matches the configured baud rate.

Example: 115200 Baud

Bit Duration ≈ 8.68 microseconds

For 8-N-1:

1 Start Bit
8 Data Bits
0 Parity Bits
1 Stop Bit

Total = 10 bits per frame

Ideal frame duration ≈ 86.8 microseconds
Actual frame duration and observed timing depend on the configured frame format and clock accuracy. Use a suitable probe and voltage reference when measuring MCU logic signals.

12. Systematic UART Troubleshooting Procedure

  1. Confirm the correct STM32 UART peripheral is selected.
  2. Check the UART peripheral clock.
  3. Verify TX and RX pin alternate functions.
  4. Verify TX/RX cross-connections and ground reference.
  5. Check voltage-level compatibility.
  6. Match baud rate and frame settings.
  7. Test simple polling transmission first.
  8. Test reception with a known external message.
  9. Move to interrupt mode and verify callbacks.
  10. Move to DMA mode and verify transfer completion.
  11. Inspect error codes and signal waveforms.
  12. Test the complete application under expected operating conditions.

13. Practical Project: UART Command Interface

Build a simple command interface in which a computer sends commands to an STM32 through a serial terminal.

Example Commands

LED_ON
LED_OFF
STATUS
HELP

Expected Responses

LED_ON  -> LED turned ON
LED_OFF -> LED turned OFF
STATUS  -> STM32 is running
HELP    -> Available commands displayed

Implementation Tasks

  1. Configure USART2 at 115200 baud, 8-N-1.
  2. Receive command characters through UART.
  3. Build a bounded command buffer.
  4. Detect a command terminator such as carriage return or newline.
  5. Validate the command before execution.
  6. Control an LED using GPIO.
  7. Send a response to the serial terminal.
  8. Handle unknown commands and buffer overflow.
Never execute an incomplete or unvalidated command. Define maximum command length and explicitly handle buffer overflow, malformed input and line endings.

14. Placement Interview Questions and Answers

Q1. What is UART debugging?

It is the process of identifying communication problems by checking configuration, wiring, electrical signals, transfer state and received data.

Q2. What is the purpose of a USB-to-UART converter?

It provides a serial interface between a computer's USB port and a UART-based embedded device.

Q3. What is a UART loopback test?

It connects the UART transmitter to the receiver so transmitted data can be checked by receiving it back.

Q4. What causes framing errors?

Possible causes include baud-rate mismatch, incorrect stop-bit configuration and signal noise.

Q5. What causes UART overrun errors?

An overrun can occur when received data is not serviced before additional data arrives.

Q6. Why is common ground important?

It provides a shared voltage reference for non-isolated logic-level UART communication.

Q7. What is the purpose of a logic analyzer?

It captures and analyzes digital signals and can decode serial protocols such as UART.

Q8. Why can UART output contain garbage characters?

Common causes include incorrect baud rate, clock error, incorrect frame settings, noise or incompatible electrical levels.

Q9. What is the difference between TTL UART and RS-232?

They use different electrical signaling levels and conventions. A suitable transceiver is required when connecting between the two interfaces.

Q10. How do you debug a missing UART interrupt?

Verify the peripheral interrupt source, NVIC enable, correct vector handler, HAL IRQ forwarding and callback conditions.

Q11. Why use DMA for UART communication?

DMA reduces CPU involvement in data movement and is useful for larger or continuous transfers.

Q12. What is the first step when UART communication fails?

Check basic configuration and physical connections, including the selected UART pins, TX/RX wiring, ground and voltage compatibility.
