2. What Is a Microcontroller Reset?

A reset initializes the microcontroller and places its execution environment into a defined startup state. After reset, the processor begins its startup sequence and eventually executes the application.

Why Are Resets Required?

  • Power-up initialization.
  • Recovery from software lockups.
  • Recovery from watchdog timeout.
  • Restart after an external reset signal.
  • Recovery from selected system faults.
  • Applying a software-requested restart.

3. Types of STM32 Reset Sources

1. Power-On Reset (POR)

Power-On Reset occurs when the device is powered up. It places the MCU into a defined reset state while the supply voltage becomes valid.

2. Power-Down Reset (PDR)

Power-Down Reset circuitry monitors the supply voltage and helps keep the MCU in reset when the supply is insufficient.

3. Brown-Out Reset (BOR)

Brown-Out Reset occurs when the supply voltage falls below a configured or device-defined threshold.

4. External Reset

An external reset can be generated through the NRST pin or an external reset circuit.

5. Software Reset

Firmware can request a system reset using the Cortex-M system control mechanism.

6. Independent Watchdog Reset

IWDG generates a reset when its counter reaches the timeout condition without being refreshed.

7. Window Watchdog Reset

WWDG can generate a reset when the application refreshes outside the permitted window or fails to refresh before timeout.

8. Low-Power Reset or Wakeup-Related Reset

Certain low-power transitions and wakeup events can produce reset-like startup behavior. The exact behavior depends on the selected STM32 mode and device.

Reset sources and their names are not identical across STM32 families. Some devices combine or rename power reset mechanisms. Refer to the reset-control section of the exact reference manual.

5. Reset Status Flags

STM32 devices commonly provide reset-status flags in a reset and clock control register or a dedicated reset-status register. These flags help identify why the microcontroller restarted.

Common Reset Flag Names

Flag Meaning
PORRSTF Power-on reset flag.
PINRSTF External reset pin flag.
BORRSTF Brown-out reset flag.
IWDGRSTF Independent watchdog reset flag.
WWDGRSTF Window watchdog reset flag.
SFTRSTF Software reset flag.
These are common STM32 flag names, especially in older RCC implementations. Newer families may use different register names and flag definitions. Multiple flags can sometimes be set, so inspect all relevant flags before clearing them.

6. Reading Reset Flags Using STM32 HAL

Many STM32 HAL packages provide macros for reading reset flags.

Example: Identify Watchdog Reset

void Check_Reset_Cause(void)
{
    if (__HAL_RCC_GET_FLAG(
            RCC_FLAG_IWDGRST) != RESET)
    {
        /* IWDG reset detected. */
    }

    if (__HAL_RCC_GET_FLAG(
            RCC_FLAG_WWDGRST) != RESET)
    {
        /* WWDG reset detected. */
    }

    if (__HAL_RCC_GET_FLAG(
            RCC_FLAG_SFTRST) != RESET)
    {
        /* Software reset detected. */
    }

    if (__HAL_RCC_GET_FLAG(
            RCC_FLAG_PINRST) != RESET)
    {
        /* External pin reset detected. */
    }
}

Clear Reset Flags

__HAL_RCC_CLEAR_RESET_FLAGS();

A typical application reads and records the flags early during startup, then clears them after capturing the information.

HAL flag macros differ by family and HAL version. Use only macros available for the selected device. Do not clear reset flags before recording the original cause.

7. Software Reset Using CMSIS

Firmware can request a system reset through the Cortex-M system control interface.

CMSIS Function

#include "stm32xxxx.h"

void Software_Reset(void)
{
    NVIC_SystemReset();
}

Replace the illustrative device header with the correct CMSIS device header supplied by the STM32 software package.

Typical Applications

  • Restart after a critical configuration failure.
  • Recover from an unrecoverable software state.
  • Apply a new firmware configuration.
  • Restart after a controlled firmware update.
A software reset restarts the processor and may reset peripheral state. Save required information before requesting a reset.

8. Cortex-M Fault Exceptions

Cortex-M processors provide exception mechanisms for detecting and handling certain processor and memory-access errors.

Fault Purpose
HardFault Handles serious faults and faults that cannot be handled by enabled configurable fault handlers.
MemManage Handles supported memory protection violations.
BusFault Handles supported instruction or data bus errors.
UsageFault Handles supported instruction and execution errors.

Common Fault Causes

  • Invalid memory access.
  • Incorrect pointer usage.
  • Stack overflow or stack corruption.
  • Invalid instruction execution.
  • Unaligned access where unsupported.
  • Access to unavailable or protected memory.
Fault support differs between Cortex-M architectures. For example, configurable MemManage, BusFault and UsageFault handlers are available on many Cortex-M3/M4/M7 implementations, but not all Cortex-M cores.

9. What Is a HardFault?

HardFault is a serious processor exception. It can occur when a fault cannot be handled by a configurable fault handler, when a fault handler itself fails, or under other core-defined fault conditions.

Common HardFault Causes

  • Invalid pointer dereferencing.
  • Corrupted stack or return address.
  • Invalid memory access.
  • Fault escalation from another exception.
  • Incorrect peripheral or memory access.
  • Execution of an invalid instruction.

10. Fault Status Registers

Some Cortex-M processors provide system control block fault-status registers. These registers help determine why a fault occurred.

Register Purpose
CFSR Configurable Fault Status Register.
HFSR HardFault Status Register.
MMFAR MemManage Fault Address Register.
BFAR BusFault Address Register.
AFSR Auxiliary Fault Status Register.

These registers are accessed through the System Control Block (SCB) where implemented by the selected Cortex-M core.

Example: Read Fault Status

uint32_t fault_cfsr;
uint32_t fault_hfsr;
uint32_t fault_bfar;
uint32_t fault_mmfar;

void Capture_Fault_Status(void)
{
    fault_cfsr = SCB->CFSR;
    fault_hfsr = SCB->HFSR;
    fault_bfar = SCB->BFAR;
    fault_mmfar = SCB->MMFAR;
}
Not every Cortex-M core implements all these registers. MMFAR and BFAR contents are meaningful only when their corresponding validity bits indicate valid addresses. Check the core documentation before using these registers.

11. HardFault Handler Example

A basic HardFault handler can be used to stop execution at the fault location during debugging. 

void HardFault_Handler(void)
{
    /*
     * Capture diagnostic information
     * here when the target core supports it.
     */

    __disable_irq();

    while (1)
    {
        /*
         * Halt for debugger inspection.
         */
    }
}

In a production system, the handler should capture a minimal diagnostic record in a safe retained location when supported, then follow a defined recovery policy.

Do not assume that calling HAL functions, printing through UART or allocating memory is safe inside HardFault_Handler. The fault may have been caused by corrupted memory, an unavailable clock or a broken stack.

12. Debugging HardFault Using STM32CubeIDE

  1. Build the project with debug information.
  2. Start a debug session using ST-LINK or the supported debugger.
  3. Reproduce the fault condition.
  4. Check whether execution stops in HardFault_Handler.
  5. Inspect the call stack and available register values.
  6. Read SCB fault-status registers where implemented.
  7. Inspect the stacked PC and LR when the exception stack frame is valid.
  8. Locate the failing source instruction.
  9. Check pointer values, array boundaries and stack usage.
  10. Correct the root cause and retest.

Useful Debugging Views

  • Variables and Expressions.
  • Registers.
  • Call Stack.
  • Disassembly.
  • Memory Browser.
  • Peripheral Registers.

13. Practical Project: Reset Cause Logger

Project Objective

Create an application that identifies common reset sources and stores a basic diagnostic code for later inspection.

Project Steps

  1. Initialize the STM32.
  2. Read reset flags early during startup.
  3. Identify available reset causes.
  4. Store the result in a diagnostic variable or retained memory.
  5. Clear reset flags after recording them.
  6. Print or display the diagnostic result during normal execution.
  7. Test software and watchdog resets.

Example Diagnostic Concept

typedef enum
{
    RESET_UNKNOWN = 0,
    RESET_IWDG,
    RESET_WWDG,
    RESET_SOFTWARE,
    RESET_EXTERNAL_PIN
} ResetCause_t;

ResetCause_t reset_cause;

void Identify_Reset_Cause(void)
{
    if (__HAL_RCC_GET_FLAG(RCC_FLAG_IWDGRST))
    {
        reset_cause = RESET_IWDG;
    }
    else if (__HAL_RCC_GET_FLAG(RCC_FLAG_WWDGRST))
    {
        reset_cause = RESET_WWDG;
    }
    else if (__HAL_RCC_GET_FLAG(RCC_FLAG_SFTRST))
    {
        reset_cause = RESET_SOFTWARE;
    }
    else if (__HAL_RCC_GET_FLAG(RCC_FLAG_PINRST))
    {
        reset_cause = RESET_EXTERNAL_PIN;
    }
    else
    {
        reset_cause = RESET_UNKNOWN;
    }

    __HAL_RCC_CLEAR_RESET_FLAGS();
}
This simplified example selects the first matching flag. Real diagnostic firmware should capture all relevant flags because multiple reset flags may be set together. Flag names and clearing behavior vary across STM32 families.

14. Common Fault Diagnostic Mistakes

Mistake Effect Correct Approach
Clearing reset flags immediately Original reset cause is lost Capture flags before clearing.
Ignoring multiple reset flags Incomplete diagnosis Record all relevant flags.
Assuming every fault is HardFault Incorrect root-cause analysis Inspect available fault status.
Ignoring stack corruption Repeated or unpredictable faults Inspect stack usage and boundaries.
Using complex code inside a fault handler Secondary fault or loss of diagnostics Capture minimal information.
Assuming fault registers exist on every core Invalid diagnostic access Verify the Cortex-M architecture.

15. Placement Interview Questions and Answers

Q1. What is a microcontroller reset?

A reset places the microcontroller into a defined startup state and restarts its execution sequence.

Q2. What is POR?

POR stands for Power-On Reset. It occurs when the microcontroller is powered up.

Q3. What is BOR?

BOR stands for Brown-Out Reset. It protects the MCU when supply voltage falls below a specified threshold.

Q4. What is the NRST pin?

NRST is an external reset input used to reset the microcontroller.

Q5. How can firmware request a reset?

Firmware can use the CMSIS function NVIC_SystemReset() to request a system reset.

Q6. How can the reset source be identified?

By reading the device-specific reset status flags before clearing them.

Q7. What is HardFault?

HardFault is a serious Cortex-M exception used when certain processor faults cannot be handled by configurable fault handlers.

Q8. What causes a HardFault?

Common causes include invalid memory access, corrupted stack, invalid instruction execution and escalated configurable faults.

Q9. What is CFSR?

CFSR stands for Configurable Fault Status Register. It provides status information about supported configurable faults.

Q10. What is BFAR?

BFAR stands for BusFault Address Register. It can contain the address associated with a valid BusFault.

Q11. How do you debug a HardFault?

Inspect the fault handler, call stack, processor registers, stacked PC and available fault-status registers. Then trace the failing instruction.

Q12. Why should reset flags be read early?

Because software may clear the flags during initialization. Reading them early preserves evidence about the previous reset.

  • STM32 devices support multiple reset sources.
  • Reset flags help identify the cause of a restart.
  • Reset flags should be captured before they are cleared.

  • Reliable diagnostics require device-specific verification.
