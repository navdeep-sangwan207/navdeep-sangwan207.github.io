2. What Is a Watchdog Timer?

A watchdog timer is a hardware timer used to detect software failures. If the application does not refresh the watchdog within the configured time, the watchdog generates a reset or another device-defined recovery action.

Why Is a Watchdog Required?

  • To recover from software lockups.
  • To detect a program stuck in an unexpected loop.
  • To recover from certain firmware execution failures.
  • To improve unattended system reliability.
  • To support automatic recovery in industrial and automotive applications.

A watchdog is a recovery mechanism, not a substitute for correct software design. Refreshing it without checking application health can hide a stalled task.

3. Independent Watchdog (IWDG)

The Independent Watchdog is a hardware watchdog peripheral found on many STM32 microcontrollers. It typically uses a low-speed internal clock source, commonly LSI, independent of the main system clock.

Important Features

  • Uses an independent low-speed clock source.
  • Contains a down-counter.
  • Uses a prescaler to adjust the counter clock.
  • Uses a reload register to set the timeout.
  • Can reset the microcontroller if not refreshed in time.
  • On many STM32 devices, can continue operating when the main system clock stops.

4. IWDG Registers and Keys

Many STM32 IWDG implementations use dedicated registers to control the watchdog.

Register Purpose
IWDG_KR Key register for enabling, refreshing and unlocking configuration.
IWDG_PR Prescaler register.
IWDG_RLR Reload register.
IWDG_SR Status register for configuration update status.
IWDG_WINR Window register on devices implementing a window feature in the IWDG peripheral.

Common IWDG Key Values

Key Value Purpose
Enable 0xCCCC Starts the watchdog.
Refresh 0xAAAA Reloads the counter.
Unlock 0x5555 Enables access to configuration registers on applicable devices.
These are common STM32 IWDG key values. Register details and optional features must be checked against the exact device reference manual.

5. IWDG Prescaler and Reload Counter

The prescaler divides the watchdog clock. The reload value determines how many counter ticks occur before timeout.

Timeout Formula

For a typical STM32 IWDG down-counter: 

       IWDG Timeout =
       (Reload Value + 1) x Prescaler
       --------------------------------
                LSI Frequency

Here, the prescaler is the division factor, not the raw register encoding.

Example

Assume:

  • LSI frequency = 32,000 Hz
  • Prescaler division factor = 32
  • Reload value = 999
Timeout =
(999 + 1) x 32
----------------
     32000

Timeout = 1 second

Another Example

Assume:

  • LSI frequency = 40,000 Hz
  • Prescaler division factor = 64
  • Reload value = 1249
Timeout =
(1249 + 1) x 64
----------------
     40000

Timeout = 2 seconds
LSI is an internal oscillator and its frequency has tolerance. These calculations are nominal estimates. For a reliable design, calculate the minimum and maximum timeout using the specified LSI frequency limits and actual device constraints.

6. Watchdog Refresh Mechanism

The application must refresh the IWDG before the counter reaches zero. Refreshing reloads the counter with its configured reload value.

            |          |
            v          v

Important Design Rule

Refresh the watchdog only after the required application tasks have completed successfully or reported healthy status.

A watchdog refresh placed unconditionally inside a fast main loop may allow a faulty application to continue running without performing its essential work.

8. IWDG Programming Using STM32 HAL

The following example uses the STM32 HAL IWDG interface. It assumes the selected device and HAL package support these APIs.

Step 1: Declare the IWDG Handle

IWDG_HandleTypeDef hiwdg;

Step 2: Configure IWDG

void MX_IWDG_Init(void)
{
    hiwdg.Instance = IWDG;

    hiwdg.Init.Prescaler = IWDG_PRESCALER_32;
    hiwdg.Init.Reload = 999;

    if (HAL_IWDG_Init(&hiwdg) != HAL_OK)
    {
        Error_Handler();
    }
}

Step 3: Refresh the Watchdog

void IWDG_Refresh(void)
{
    if (HAL_IWDG_Refresh(&hiwdg) != HAL_OK)
    {
        Error_Handler();
    }
}

Step 4: Main Application

int main(void)
{
    HAL_Init();
    SystemClock_Config();

    MX_GPIO_Init();
    MX_IWDG_Init();

    while (1)
    {
        /* Perform application work. */
        Application_Task();

        /* Refresh after successful work. */
        if (Application_Health_Check())
        {
            HAL_IWDG_Refresh(&hiwdg);
        }
    }
}
This is a teaching example. The actual timeout must be calculated from the selected device's LSI frequency and supported prescaler/reload values. Also ensure the application health check cannot incorrectly report success when critical tasks are stalled.

9. IWDG Without HAL – Register-Level Concept

The following example illustrates the common IWDG key-register sequence. It is not a complete portable driver. 

/* Enable IWDG */
IWDG->KR = 0xCCCC;

/* Unlock configuration registers */
IWDG->KR = 0x5555;

/* Set prescaler encoding */
IWDG->PR = 3U;

/* Set reload value */
IWDG->RLR = 999U;

/* Refresh counter */
IWDG->KR = 0xAAAA;

On devices that require status-register synchronization, software must wait until the relevant update flags indicate that configuration changes have taken effect.

Prescaler register encoding is not the same as the prescaler division factor. The example's encoding and reload value must be validated for the selected STM32. Once enabled, IWDG may be difficult or impossible to stop without a reset.

10. What Happens When IWDG Times Out?

  1. The watchdog counter reaches its timeout condition.
  2. The IWDG generates a reset request.
  3. The microcontroller resets according to device reset behavior.
  4. Startup code executes again.
  5. The application can inspect reset flags if supported and retained.
  6. The system initializes and resumes normal operation.

Typical Applications

  • Industrial controllers.
  • Sensor monitoring devices.
  • Remote monitoring systems.
  • Motor control systems.
  • Unattended embedded equipment.

12. Practical Project: Watchdog-Based System Recovery

Project Objective

Implement a basic watchdog-based recovery mechanism for an STM32 application.

Project Operation

  1. Initialize system peripherals.
  2. Initialize the IWDG.
  3. Execute the application task.
  4. Check whether the required task completed.
  5. Refresh IWDG only after successful health checks.
  6. Test a controlled software hang.
  7. Verify that the watchdog resets the device.
  8. Inspect the reset cause after restart.

Example Health Check Concept

uint8_t sensor_task_ok = 0;
uint8_t communication_task_ok = 0;

uint8_t Application_Health_Check(void)
{
    if ((sensor_task_ok == 1U) &&
        (communication_task_ok == 1U))
    {
        return 1U;
    }

    return 0U;
}

In a real application, task health indicators must be updated with suitable timing and synchronization. A stale flag must not be treated as proof that a task is still healthy.

13. Placement Interview Questions and Answers

Q1. What is a watchdog timer?

A watchdog is a hardware timer that detects failure to refresh within a specified time and triggers a recovery action, commonly reset.

Q2. What is IWDG?

IWDG stands for Independent Watchdog. It is a watchdog peripheral that commonly uses an independent low-speed clock.

Q3. Why is it called independent?

It generally uses a clock source separate from the main system clock, allowing watchdog operation even if the main clock fails.

Q4. What happens if IWDG is not refreshed?

The counter reaches its timeout condition and normally generates a system reset.

Q5. What is the purpose of the prescaler?

It divides the watchdog clock to obtain a suitable counter frequency.

Q6. What is the reload register?

It stores the value used to reload the watchdog counter and determine its timeout.

Q7. What is the IWDG timeout formula?

For a typical implementation: (Reload + 1) × Prescaler division factor ÷ watchdog clock frequency.

Q8. Can IWDG operate when the main system clock fails?

It is designed to use an independent clock, so it can often continue operating. Exact behavior depends on the device.

Q9. Why should the watchdog not be refreshed unconditionally?

An application may continue refreshing the watchdog even when important tasks are no longer functioning correctly.

Q10. What is the difference between IWDG and WWDG?

IWDG commonly uses an independent low-speed clock and a timeout mechanism. WWDG uses a refresh window and can detect refreshes that occur too early as well as too late.

Q11. Can IWDG be used in low-power modes?

It can operate in certain low-power modes on supported STM32 devices. The exact behavior must be checked in the reference manual.

Q12. Where is IWDG used?

It is used in industrial controllers, monitoring systems, motor controllers and other applications requiring automatic recovery from software failures.

15. Lesson Summary

  • IWDG detects software execution failures through a timeout mechanism.
  • It commonly uses an independent low-speed clock.
  • The prescaler controls the watchdog counter frequency.
  • The reload value determines the timeout interval.
  • The application must refresh the watchdog in time.
  • Health checks should determine when refreshing is appropriate.
  • Watchdog timeout commonly generates a system reset.
  • Clock tolerance and device-specific limits must be considered.
