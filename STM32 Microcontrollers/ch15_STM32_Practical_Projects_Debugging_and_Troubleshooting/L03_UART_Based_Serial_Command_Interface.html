Lesson 3: UART-Based Serial Command Interface

STM32 Practical Projects, Debugging and Troubleshooting

1. Learning Objectives

  • Understand a UART-based command interface.
  • Configure UART communication using STM32CubeMX.
  • Transmit and receive serial data using HAL.
  • Receive commands from a computer terminal.
  • Implement a command parser.
  • Control GPIO peripherals using UART commands.
  • Understand UART communication errors and troubleshooting.

2. Project Overview

A UART-based serial command interface allows a computer or another controller to communicate with an STM32 microcontroller through serial commands.

In this project, a user enters commands through a serial terminal. The STM32 receives and processes each command and performs the requested operation.

Example Commands

Command Function
LED ON Switch ON the LED
LED OFF Switch OFF the LED
LED TOGGLE Toggle LED state
STATUS Display system status
HELP Display available commands

4. Hardware Requirements

  • STM32 development board.
  • Computer or laptop.
  • STM32CubeIDE.
  • Serial terminal application.
  • USB cable or compatible USB-UART adapter.
  • LED connected to a configured GPIO pin, if not built in.

UART Connections

STM32 Signal USB-UART Signal
TX RX
RX TX

Connect TX to RX and RX to TX. Ensure a common ground and compatible logic voltage levels. Do not connect an RS-232 voltage-level interface directly to STM32 GPIO pins.

5. UART Configuration Using STM32CubeMX

  1. Open the STM32CubeIDE project.
  2. Open the MCU configuration.
  3. Select a supported USART or UART peripheral.
  4. Enable asynchronous mode.
  5. Configure the TX and RX pins.
  6. Set baud rate to 115200 bits per second.
  7. Select 8 data bits, no parity and 1 stop bit (8-N-1).
  8. Disable hardware flow control for this basic project.
  9. Generate the code.

7. Transmitting a Welcome Message

First, verify that the STM32 can transmit a message to the computer.

Program


#include "main.h"
#include 

extern UART_HandleTypeDef huart2;

int main(void)
{
    HAL_Init();

    SystemClock_Config();

    MX_GPIO_Init();
    MX_USART2_UART_Init();

    uint8_t message[] =
        "STM32 Serial Interface Ready\r\n";

    while (1)
    {
        HAL_UART_Transmit(
            &huart2,
            message,
            sizeof(message) - 1,
            100
        );

        HAL_Delay(1000);
    }
}

Expected Result

The serial terminal displays the welcome message once every second.

This example assumes that USART2 is configured and connected to the computer. Replace the UART handle and instance if the board uses a different peripheral.

8. Receiving a Command from the Computer

The STM32 can receive a fixed number of bytes using HAL_UART_Receive(). For this project, commands will be received one character at a time until a newline character is detected.

Basic Character Reception


uint8_t receivedChar;

HAL_UART_Receive(
    &huart2,
    &receivedChar,
    1,
    HAL_MAX_DELAY
);

This blocking function waits until one byte is received or the configured timeout occurs. HAL_MAX_DELAY can wait indefinitely.

9. Complete Project: UART Command-Based LED Control

This program receives a line of text, compares it with known commands and controls an LED.

Program


#include "main.h"
#include 
#include 

extern UART_HandleTypeDef huart2;

#define COMMAND_SIZE 32

uint8_t commandBuffer[COMMAND_SIZE];

void UART_SendMessage(const char *message)
{
    HAL_UART_Transmit(
        &huart2,
        (uint8_t *)message,
        strlen(message),
        100
    );
}

void Process_Command(char *command)
{
    if (strcmp(command, "LED ON") == 0)
    {
        HAL_GPIO_WritePin(
            GPIOA,
            GPIO_PIN_5,
            GPIO_PIN_SET
        );

        UART_SendMessage("LED TURNED ON\r\n");
    }
    else if (strcmp(command, "LED OFF") == 0)
    {
        HAL_GPIO_WritePin(
            GPIOA,
            GPIO_PIN_5,
            GPIO_PIN_RESET
        );

        UART_SendMessage("LED TURNED OFF\r\n");
    }
    else if (strcmp(command, "LED TOGGLE") == 0)
    {
        HAL_GPIO_TogglePin(
            GPIOA,
            GPIO_PIN_5
        );

        UART_SendMessage("LED STATE TOGGLED\r\n");
    }
    else if (strcmp(command, "STATUS") == 0)
    {
        UART_SendMessage("STM32 SYSTEM RUNNING\r\n");
    }
    else if (strcmp(command, "HELP") == 0)
    {
        UART_SendMessage(
            "COMMANDS:\r\n"
            "LED ON\r\n"
            "LED OFF\r\n"
            "LED TOGGLE\r\n"
            "STATUS\r\n"
            "HELP\r\n"
        );
    }
    else
    {
        UART_SendMessage("INVALID COMMAND\r\n");
    }
}

int main(void)
{
    uint8_t receivedChar;
    uint8_t index = 0;

    HAL_Init();

    SystemClock_Config();

    MX_GPIO_Init();
    MX_USART2_UART_Init();

    UART_SendMessage(
        "\r\nSTM32 COMMAND INTERFACE\r\n"
        "Type HELP for commands\r\n"
    );

    while (1)
    {
        if (HAL_UART_Receive(
                &huart2,
                &receivedChar,
                1,
                HAL_MAX_DELAY) == HAL_OK)
        {
            if (receivedChar == '\r' ||
                receivedChar == '\n')
            {
                if (index > 0)
                {
                    commandBuffer[index] = '\0';

                    Process_Command(
                        (char *)commandBuffer
                    );

                    index = 0;
                }
            }
            else
            {
                if (index < COMMAND_SIZE - 1)
                {
                    commandBuffer[index++] =
                        receivedChar;
                }
                else
                {
                    index = 0;

                    UART_SendMessage(
                        "ERROR: COMMAND TOO LONG\r\n"
                    );
                }
            }
        }
    }
}

Program Explanation

  • UART_SendMessage() transmits a response.
  • HAL_UART_Receive() receives one character.
  • The command buffer stores incoming characters.
  • Carriage return or newline marks the end of a command.
  • strcmp() compares the received command.
  • The matching command performs the requested operation.
  • Unknown commands produce an error response.

The code is a basic blocking command-interface example. It assumes the generated GPIO and UART initialization functions are available and the LED is active-high on PA5. Change the pin and polarity to match the actual board.

For production firmware, also handle UART errors and timeouts, discard the remainder of an overlength command until the next line ending, and add input validation and command time limits. A nonblocking receive design is preferable when the application must continue performing other tasks.

11. Improving the Interface Using Interrupt Reception

Blocking reception prevents the main loop from progressing while waiting for the next character. Interrupt-based reception allows the processor to perform other work between received bytes.

Interrupt Reception Example


uint8_t rxByte;

void UART_StartReception(void)
{
    HAL_UART_Receive_IT(
        &huart2,
        &rxByte,
        1
    );
}

void HAL_UART_RxCpltCallback(
    UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART2)
    {
        /*
         * Process or store rxByte here.
         * Keep the callback short.
         */

        HAL_UART_Receive_IT(
            &huart2,
            &rxByte,
            1
        );
    }
}

Call UART_StartReception() after UART initialization. The interrupt handler must call HAL_UART_IRQHandler() for the configured UART instance.

In a complete application, the callback should place the received byte into a ring buffer or queue. Avoid parsing complete commands or performing lengthy transmissions inside the interrupt callback.

12. Command Parser Design

A command parser interprets received characters and determines which operation should be executed.

Basic Processing Flow

     |
     v

     |
     v

     |
     v

     |
     v
Compare Command
     |
     +----------------------+
     |          |           |
     v          v           v
  LED ON     LED OFF      STATUS
     |          |           |
     v          v           v
GPIO SET    GPIO RESET   Send Response

Good Parser Design Practices

  • Use a fixed-size receive buffer.
  • Prevent buffer overflow.
  • Validate command length.
  • Use clear command names.
  • Handle invalid commands.
  • Define command termination rules.
  • Use timeouts for incomplete commands.
  • Separate command parsing from hardware control.

13. UART Troubleshooting

Problem 1: No Serial Output

  • Check the selected COM port.
  • Verify UART TX pin configuration.
  • Check the USB-UART connection.
  • Verify the correct UART instance and handle.
  • Check peripheral clock configuration.

Problem 2: Garbled Characters

  • Check baud-rate settings at both ends.
  • Verify word length, parity and stop bits.
  • Check the UART peripheral clock.
  • Verify electrical signal levels and grounding.

Problem 3: Commands Are Not Recognized

  • Check line-ending configuration.
  • Check command spelling and capitalization.
  • Verify string termination with a null character.
  • Inspect buffer length and received bytes.

Problem 4: UART Reception Stops

  • Check the HAL return status.
  • Inspect UART error flags and error callbacks.
  • Verify that interrupt reception is rearmed.
  • Check for buffer overflow and overrun conditions.

14. Placement-Oriented Interview Questions and Answers

Q1. What is UART?

UART is an asynchronous serial communication peripheral used to transmit and receive data.

Q2. What is a baud rate?

It is the symbol rate of a serial communication signal. For conventional binary UART, the baud rate equals the bit rate.

Q3. What is 8-N-1?

It represents eight data bits, no parity and one stop bit.

Q4. Why are TX and RX connected in cross direction?

The transmitter of one device must connect to the receiver of the other device.

Q5. What is a virtual COM port?

It is a software interface that exposes a serial communication channel through USB.

Q6. What is a command parser?

A command parser processes received input and identifies the requested operation.

Q7. What is the difference between blocking and interrupt-based UART reception?

Blocking reception waits for data in the calling code, while interrupt-based reception reports data through an interrupt callback.

Q8. Why is a receive buffer required?

It stores incoming characters until a complete message or command is available for processing.

Q9. Why must a UART buffer be checked for overflow?

To prevent writes beyond its allocated memory and avoid memory corruption.

Q10. What is a UART overrun error?

It occurs when incoming data cannot be transferred or read in time and a new character arrives before the previous data is handled.

Q11. Why should lengthy processing be avoided inside a UART ISR?

Long interrupt processing increases latency and can interfere with other real-time activities.

Q12. How can UART communication be debugged?

Check the baud rate, pin mapping, clock, terminal settings, wiring and received data using a debugger or logic analyzer.

16. Lesson Summary

  • UART enables serial communication with a computer or another controller.
  • TX and RX signals must be connected correctly.
  • Matching baud rate and frame settings are essential.
  • HAL provides blocking, interrupt and DMA communication APIs.
  • A command parser converts received text into application actions.
  • Buffer validation prevents memory errors.
  • Interrupt callbacks should remain short and nonblocking.
