Lesson 7: Firmware Debugging and Fault Analysis

STM32 Practical Projects, Debugging and Troubleshooting

1. Learning Objectives

  • Understand embedded firmware debugging.
  • Use STM32CubeIDE debugging tools.
  • Configure breakpoints and watch expressions.
  • Inspect CPU registers and memory.
  • Understand Cortex-M exception and fault handling.
  • Analyze HardFault conditions.
  • Use UART, SWD and GPIO for debugging.
  • Develop a systematic firmware troubleshooting process.

2. What Is Firmware Debugging?

Firmware debugging is the process of identifying, analyzing and correcting errors in embedded software.

Embedded debugging may involve both software and hardware because firmware interacts directly with microcontroller peripherals, memory and external circuits.

Common Firmware Problems

  • Program does not start after reset.
  • Unexpected program execution.
  • Incorrect GPIO output.
  • UART communication failure.
  • Incorrect timer or PWM operation.
  • ADC readings are incorrect.
  • Stack overflow or memory corruption.
  • HardFault or other processor exceptions.

5. STM32CubeIDE Debugging Setup

  1. Open the STM32CubeIDE project.
  2. Build the project and resolve compilation errors.
  3. Connect the STM32 board to the computer.
  4. Connect the ST-LINK debug interface.
  5. Open the Debug Configurations menu.
  6. Select the appropriate STM32 debug configuration.
  7. Check the selected probe and interface settings.
  8. Click Debug to start a debugging session.
  9. Inspect the program in the Debug perspective.

The exact menu labels and available settings may differ between STM32CubeIDE versions.

6. Breakpoints

A breakpoint pauses program execution at a selected instruction so that the developer can inspect the program state.

Types of Breakpoints

  • Software breakpoint: Uses a debugger-supported instruction substitution mechanism where available.
  • Hardware breakpoint: Uses processor debug resources.
  • Conditional breakpoint: Stops execution when a specified condition is satisfied, if supported by the debugger.
  • Watchpoint: Monitors a memory access or address condition using available debug resources.

Example


int main(void)
{
    int count = 0;

    while (1)
    {
        count++;

        if (count == 10)
        {
            count = 0;  // Set a breakpoint here
        }
    }
}

When execution reaches the breakpoint, inspect the value of count and the current program location.

7. Step-by-Step Debugging

Debug Command Function
Step Into Enters a called function.
Step Over Executes a function call without entering its implementation.
Step Return Continues until the current function returns.
Resume Continues program execution.
Pause Requests a halt of program execution.
Reset Resets the target according to the selected debug configuration.

8. Variables and Expressions

The Variables and Expressions views allow the developer to inspect values while the target is halted.

Example


uint32_t adc_value = 2048;
float voltage;

voltage = (adc_value * 3.3f) / 4095.0f;

Useful expressions to inspect:

  • adc_value
  • voltage
  • Peripheral register values.
  • Pointer addresses.
  • Function return values.
  • Task and buffer state in RTOS applications.

Compiler optimization can change variable visibility and instruction order. For meaningful source-level debugging, select a suitable debug build configuration.

10. Understanding Cortex-M Fault Exceptions

Cortex-M processors provide exception mechanisms to handle system events and certain error conditions.

Common Fault Exceptions

Exception Typical Purpose
HardFault Handles faults that escalate or cannot be handled by a more specific fault handler.
MemManage Handles memory protection faults where supported.
BusFault Handles certain instruction or data bus access faults where supported.
UsageFault Handles certain invalid instruction and processor usage conditions where supported.

MemManage, BusFault and UsageFault availability and configuration depend on the Cortex-M core. A fault may escalate to HardFault if its handler is disabled or cannot be activated.

11. Common Causes of HardFault

  • Invalid memory access.
  • Incorrect pointer usage.
  • Stack corruption or stack overflow.
  • Invalid execution address.
  • Fault during exception handling.
  • Access to a peripheral or memory region in an invalid way.
  • Unaligned access where the instruction or memory region does not permit it.

Example: Invalid Pointer


int main(void)
{
    int *ptr = (int *)0x00000000;

    *ptr = 100;  // Invalid access in a typical application

    while (1)
    {
    }
}

This is an intentionally faulty example. Do not execute it in a production project. Its result depends on the MCU memory map and protection configuration, but it can cause a fault.

12. HardFault Handler

A HardFault handler is entered when the processor takes a HardFault exception. The following example provides a simple location to halt and inspect the debugger state. 


#include "main.h"

void HardFault_Handler(void)
{
    __disable_irq();

    while (1)
    {
        // Inspect the fault using the debugger.
    }
}

This simple handler does not identify the fault cause by itself. A production fault handler should preserve useful diagnostic information safely and avoid depending on unreliable application services.

13. Fault Status Registers

On Cortex-M cores that implement the System Control Block fault status registers, these registers can help identify the reason for a fault.

Register Purpose
CFSR Configurable Fault Status Register.
HFSR HardFault Status Register.
MMFAR MemManage Fault Address Register, when valid.
BFAR BusFault Address Register, when valid.
SHCSR System Handler Control and State Register.

These registers are not available in the same form on every Cortex-M core. Address validity flags must be checked before treating MMFAR or BFAR as the fault address. Consult the exact core documentation.

14. Capturing the Exception Stack Frame

On common Cortex-M exception entry, the processor stacks a basic exception frame containing:

  • R0
  • R1
  • R2
  • R3
  • R12
  • LR
  • PC
  • xPSR

This information can help identify the code location and register state at the time of the exception. Additional floating-point state or alignment padding may be present depending on the core and configuration.

Example: Fault Frame Inspection Concept


typedef struct
{
    uint32_t r0;
    uint32_t r1;
    uint32_t r2;
    uint32_t r3;
    uint32_t r12;
    uint32_t lr;
    uint32_t pc;
    uint32_t xpsr;
} FaultStackFrame;

This structure describes the common basic frame layout. A real fault-analysis routine must determine the correct stack pointer and account for the processor's exception frame format before reading it.

15. UART-Based Debugging

UART logging is a useful debugging technique when a hardware debugger is unavailable or when observing program behavior over time. 


#include "main.h"
#include 

extern UART_HandleTypeDef huart2;

void Debug_Message(char *message)
{
    HAL_UART_Transmit(
        &huart2,
        (uint8_t *)message,
        strlen(message),
        100
    );
}

int main(void)
{
    HAL_Init();

    SystemClock_Config();

    MX_GPIO_Init();
    MX_USART2_UART_Init();

    Debug_Message("System Started\r\n");

    while (1)
    {
        Debug_Message("Application Running\r\n");

        HAL_Delay(1000);
    }
}

Include string.h for strlen(). Configure the UART instance, pins and terminal baud rate according to the actual board. Blocking logging can affect real-time timing, so use suitable buffering or non-blocking methods in time-sensitive applications.

16. GPIO-Based Timing Debugging

A GPIO pin can be toggled around a function or code section. An oscilloscope or logic analyzer can then measure execution timing. 


void Process_Data(void)
{
    HAL_GPIO_WritePin(
        GPIOA,
        GPIO_PIN_5,
        GPIO_PIN_SET
    );

    // Code being measured

    HAL_GPIO_WritePin(
        GPIOA,
        GPIO_PIN_5,
        GPIO_PIN_RESET
    );
}

The pulse width gives an approximate duration of the measured code section. Ensure that the selected GPIO is configured as an output and that the measurement method does not materially change the timing being investigated.

17. Common Firmware Debugging Problems

Problem 1: ST-LINK Cannot Connect

  • Check USB cable and ST-LINK connection.
  • Verify target power and ground.
  • Check SWDIO and SWCLK wiring.
  • Verify the selected target device.
  • Try a supported connect-under-reset procedure if appropriate.

Problem 2: Program Stops Unexpectedly

  • Check breakpoints and watchpoints.
  • Inspect the call stack.
  • Check exception handlers.
  • Inspect fault status registers where available.

Problem 3: Variable Values Are Incorrect

  • Check data types and initialization.
  • Inspect pointer addresses.
  • Check array boundaries.
  • Review compiler optimization settings.
  • Check concurrent access and synchronization.

Problem 4: Firmware Enters HardFault

  • Inspect the stacked PC and LR when the frame is valid.
  • Inspect CFSR and HFSR if implemented.
  • Check the stack pointer and memory boundaries.
  • Inspect pointers and peripheral accesses.
  • Review the instruction at the faulting address.

18. Systematic Debugging Methodology

  1. Reproduce: Identify the exact conditions that cause the issue.
  2. Observe: Record symptoms, logs and hardware behavior.
  3. Isolate: Determine whether the problem is in software, hardware or their interaction.
  4. Inspect: Use breakpoints, registers, memory and peripheral state.
  5. Analyze: Identify the underlying cause rather than only the symptom.
  6. Correct: Apply a targeted fix.
  7. Verify: Repeat the test under normal and boundary conditions.
  8. Regress: Confirm that the correction has not broken other features.

19. Practical Debugging Checklist

  • Verify MCU power and reset.
  • Confirm the correct target device and clock configuration.
  • Build the project without errors.
  • Check startup and linker configuration.
  • Verify GPIO and alternate-function settings.
  • Inspect peripheral clock enables.
  • Check interrupt priorities and enable settings.
  • Inspect stack and heap usage.
  • Check fault status registers when available.
  • Test communication interfaces independently.
  • Document the root cause and corrective action.

20. Placement-Oriented Interview Questions and Answers

Q1. What is firmware debugging?

It is the process of identifying and correcting errors in embedded software.

Q2. What is a breakpoint?

A breakpoint pauses execution at a selected instruction for inspection.

Q3. What is SWD?

Serial Wire Debug is a two-wire debug interface commonly used with STM32 microcontrollers.

Q4. What is the purpose of ST-LINK?

It provides programming and debugging connectivity to supported STM32 devices.

Q5. What is a HardFault?

It is a processor exception used for faults that cannot be handled by a more specific configurable fault handler or that escalate to HardFault.

Q6. What causes a HardFault?

Possible causes include invalid memory access, stack corruption and escalated processor faults.

Q7. What is the purpose of CFSR?

It records configurable fault status information on cores that implement it.

Q8. What is the purpose of HFSR?

It records HardFault status information on cores that implement it.

Q9. What is the difference between Step Into and Step Over?

Step Into enters a called function, while Step Over executes the call without entering its implementation.

Q10. Why is UART debugging useful?

It provides diagnostic messages without requiring the developer to halt program execution.

Q11. What is a watchpoint?

A watchpoint monitors a selected memory access or address condition using available debug hardware.

Q12. Why can optimization affect debugging?

Optimization may remove, combine or reorder operations, making source-level stepping and variable inspection less direct.

Q13. What is a stack overflow?

It occurs when stack usage exceeds the allocated stack region and may corrupt adjacent memory or cause a fault.

Q14. Why should a fault handler be simple?

A fault may occur when the system is already in an invalid state, so the handler should avoid complex operations and preserve diagnostic information safely.
