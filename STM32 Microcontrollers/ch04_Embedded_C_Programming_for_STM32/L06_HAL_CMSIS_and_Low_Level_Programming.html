2. STM32 Firmware Software Architecture

STM32 firmware is commonly developed using several software layers. These layers help separate application logic from processor-specific and peripheral-specific implementation.

Typical Software Layers

+--------------------------------------+
|          Application Layer           |
|       Application and Project Logic   |
+--------------------------------------+
|          Middleware Layer            |
|     FreeRTOS, USB, TCP/IP, File System|
+--------------------------------------+
|      STM32 HAL / LL Drivers           |
|       Peripheral Driver APIs         |
+--------------------------------------+
|          CMSIS Device Layer           |
|     Device Registers and Definitions |
+--------------------------------------+
|          Cortex-M Core                |
|      NVIC, SysTick, Core Registers   |
+--------------------------------------+
|              Hardware                 |
|       CPU, Memory and Peripherals    |
+--------------------------------------+

Not every project uses all these layers. A small application may use CMSIS device definitions and direct register access, while a larger project may use HAL and middleware.

3. What is CMSIS?

CMSIS stands for Arm Cortex Microcontroller Software Interface Standard. It provides standardized software interfaces for Cortex-M processor-based microcontrollers.

Important CMSIS Components

Component Purpose
CMSIS-Core Processor core access, NVIC, SysTick and core registers.
CMSIS-Device Device-specific peripheral definitions supplied by the vendor.
CMSIS-DSP Optimized digital signal processing functions.
CMSIS-RTOS Standardized RTOS interfaces, with version-specific APIs.
CMSIS-Pack Software component and device support packaging.
CMSIS is an Arm standard. STM32 device-specific headers and peripheral definitions are supplied through the STM32 device support package.

4. CMSIS Core Programming

CMSIS-Core provides functions and definitions for accessing Cortex-M core features.

Example: Configure an NVIC Interrupt

#include "stm32f4xx.h"

void configure_irq(void)
{
    NVIC_SetPriority(EXTI0_IRQn, 5U);
    NVIC_EnableIRQ(EXTI0_IRQn);
}

Common CMSIS-Core Functions

Function Purpose
NVIC_EnableIRQ() Enable an external interrupt.
NVIC_DisableIRQ() Disable an external interrupt.
NVIC_SetPriority() Set an interrupt priority.
SysTick_Config() Configure the SysTick timer.
__disable_irq() Disable configurable interrupts globally.
__enable_irq() Enable configurable interrupts globally.
These APIs operate on Cortex-M core facilities. Peripheral interrupt flags and peripheral-specific interrupt enables must still be configured separately.

5. What is STM32 HAL?

HAL stands for Hardware Abstraction Layer. STM32 HAL is a vendor-provided driver library that offers high-level APIs for configuring and using STM32 peripherals.

Examples of HAL Functions

Function Purpose
HAL_Init() Initialize the HAL library and basic system services.
HAL_GPIO_WritePin() Set or reset a GPIO output pin.
HAL_GPIO_ReadPin() Read a GPIO input pin.
HAL_UART_Transmit() Transmit UART data.
HAL_UART_Receive() Receive UART data.
HAL_ADC_Start() Start an ADC conversion.
HAL_TIM_Base_Start() Start a timer base counter.

6. GPIO Programming Using HAL

Example: Toggle an LED

#include "main.h"

int main(void)
{
    HAL_Init();
    SystemClock_Config();
    MX_GPIO_Init();

    while (1)
    {
        HAL_GPIO_TogglePin(GPIOA, GPIO_PIN_5);

        HAL_Delay(500);
    }
}

Explanation

  • HAL_Init() initializes the HAL framework.
  • SystemClock_Config() configures the system clock.
  • MX_GPIO_Init() initializes GPIO using generated configuration.
  • HAL_GPIO_TogglePin() changes the output state.
  • HAL_Delay() provides a blocking delay based on the HAL time base.
GPIOA pin 5 is only an example. The LED port and pin must match the selected STM32 board and its circuit. The HAL time base must also be configured correctly.

7. What are STM32 LL Drivers?

LL stands for Low-Layer. STM32 LL drivers provide lower-level peripheral access than HAL and are designed to offer more direct control over peripheral registers.

Example: GPIO Output Using LL

#include "main.h"

int main(void)
{
    HAL_Init();
    SystemClock_Config();

    /* Enable GPIOA peripheral clock */
    LL_AHB1_GRP1_EnableClock(LL_AHB1_GRP1_PERIPH_GPIOA);

    /* Configure PA5 as output */
    LL_GPIO_SetPinMode(GPIOA, LL_GPIO_PIN_5, LL_GPIO_MODE_OUTPUT);

    while (1)
    {
        LL_GPIO_TogglePin(GPIOA, LL_GPIO_PIN_5);

        for (volatile uint32_t i = 0U; i < 100000U; i++)
        {
            /* Illustrative software delay only */
        }
    }
}
LL API names and available functions depend on the STM32 family and installed driver package. The loop is not a calibrated timing mechanism; use a hardware timer for accurate timing.

8. Register-Level Programming

Register-level programming accesses peripheral registers directly using CMSIS device definitions or carefully defined register addresses.

Example: Configure PA5 as Output (STM32F4)

#include "stm32f4xx.h"

int main(void)
{
    /* Enable GPIOA clock */
    RCC->AHB1ENR |= (1U << 0);

    /* Set PA5 mode to output */
    GPIOA->MODER &= ~(3U << 10);
    GPIOA->MODER |=  (1U << 10);

    while (1)
    {
        /* Set PA5 */
        GPIOA->BSRR = (1U << 5);

        /* Reset PA5 */
        GPIOA->BSRR = (1U << 21);
    }
}

In this example, each GPIO pin uses two MODER bits. PA5 uses bits 11:10. The BSRR lower half sets output bits, while the upper half resets output bits.

This example uses the STM32F4 GPIO register layout. It does not provide a visible blink delay. For another STM32 family, verify the RCC and GPIO register layout in its reference manual and device header.

9. HAL vs LL vs Register-Level Programming

Feature HAL LL Register-Level
Abstraction High Low Very low
Ease of use Generally easier Requires more peripheral knowledge Requires detailed register knowledge
Control Driver-managed More direct Direct register control
Portability Often easier within supported STM32 families Family-dependent Highly device-dependent
Development speed Usually faster Moderate Can require more development time
Typical use Application development Performance-sensitive peripheral control Specialized control and hardware learning

10. STM32CubeMX and Code Generation

STM32CubeMX is a configuration tool used to select the MCU, configure pins, clocks and peripherals, and generate initialization code for a project.

Typical Workflow

  1. Select the STM32 microcontroller or development board.
  2. Configure GPIO pins and alternate functions.
  3. Configure the clock tree.
  4. Configure peripherals such as UART, SPI, I2C and ADC.
  5. Configure NVIC settings where required.
  6. Select HAL or LL driver options where supported.
  7. Generate the project code.
  8. Build, flash and debug using STM32CubeIDE.
CubeMX-generated initialization functions commonly use names such as MX_GPIO_Init(), MX_USART2_UART_Init() and MX_ADC1_Init().

11. STM32 HAL Driver Structure

HAL drivers commonly use handle structures to maintain peripheral configuration and runtime state.

UART Handle Example

UART_HandleTypeDef huart2;

The handle is configured with information such as the UART instance, baud rate, word length, stop bits and other settings.

Example Initialization

huart2.Instance = USART2;

huart2.Init.BaudRate = 115200;
huart2.Init.WordLength = UART_WORDLENGTH_8B;
huart2.Init.StopBits = UART_STOPBITS_1;
huart2.Init.Parity = UART_PARITY_NONE;
huart2.Init.Mode = UART_MODE_TX_RX;
huart2.Init.HwFlowCtl = UART_HWCONTROL_NONE;
huart2.Init.OverSampling = UART_OVERSAMPLING_16;

if (HAL_UART_Init(&huart2) != HAL_OK)
{
    Error_Handler();
}

This is a typical STM32 HAL UART initialization pattern. The exact fields and supported settings depend on the device and HAL driver version.

12. Error Handling in HAL

HAL functions often return a status value that allows the application to detect configuration or operation errors.

Common HAL Status Values

Status Meaning
HAL_OK Operation completed successfully.
HAL_ERROR Operation failed.
HAL_BUSY Peripheral or driver is busy.
HAL_TIMEOUT Operation exceeded its allowed timeout.

Example

if (HAL_UART_Transmit(&huart2,
                      (uint8_t *)"STM32\r\n",
                      7U,
                      100U) != HAL_OK)
{
    Error_Handler();
}

13. Choosing the Right Programming Approach

Project Requirement Suitable Approach
Quick prototype using standard peripherals HAL
Application using multiple STM32 peripherals HAL with CMSIS
More direct peripheral control LL
Learning hardware register operation Register-level with CMSIS definitions
Custom timing or specialized hardware behavior LL or register-level, as appropriate

Real-world firmware often combines these approaches. The important requirement is to avoid conflicting ownership of the same peripheral between different software layers.

14. Common Development Errors

Error Recommended Check
HAL function returns an error Check handle initialization, peripheral clock and state.
Peripheral does not respond Check pin configuration, clock and wiring.
Incorrect register access Check the exact MCU reference manual and header.
Generated code does not match hardware Verify selected MCU and CubeMX configuration.
Unexpected HAL timeout Check peripheral state, clock configuration and timeout.
Interrupt callback not executed Check peripheral IRQ handler and NVIC configuration.

15. Placement-Oriented Interview Questions and Answers

Q1. What is CMSIS?

CMSIS is the Arm Cortex Microcontroller Software Interface Standard. It provides standardized interfaces for Cortex-M processor-based microcontrollers.

Q2. What is STM32 HAL?

HAL is STMicroelectronics' Hardware Abstraction Layer library for accessing STM32 peripherals through higher-level APIs.

Q3. What is an LL driver?

LL is a low-layer peripheral driver library that provides more direct control than HAL.

Q4. What is the difference between HAL and LL?

HAL provides higher-level APIs and manages more driver details. LL provides lower-level operations with more direct peripheral control.

Q5. What is register-level programming?

It is the direct reading and writing of hardware peripheral registers to configure and control the microcontroller.

Q6. What is the purpose of STM32CubeMX?

It configures MCU pins, clocks and peripherals and generates initialization code for STM32 projects.

Q7. What is a HAL handle?

It is a driver data structure that stores peripheral instance, configuration and runtime state information.

Q8. Can HAL and register-level programming be used together?

Yes, when carefully designed. Avoid modifying peripheral registers in ways that conflict with HAL's internal state or ongoing operations.

Q9. What is HAL_OK?

It is a HAL status value indicating that an operation completed successfully.

Q10. Which approach is best for embedded development?

It depends on project requirements, performance, maintainability, hardware control and development time.

17. Lesson Summary

  • CMSIS provides standardized Cortex-M software interfaces.
  • CMSIS device headers provide device-specific peripheral definitions.
  • HAL provides higher-level STM32 peripheral APIs.
  • LL provides lower-level peripheral operations.
  • Register-level programming gives direct hardware control.
  • STM32CubeMX generates peripheral initialization code.
  • HAL handles maintain peripheral configuration and runtime state.
  • Firmware can combine software layers when peripheral ownership is managed carefully.
