Lesson 5: Debugging Using STM32CubeIDE

Learn to find firmware defects using breakpoints, stepping, variables, registers, and memory inspection.

1. Learning Objectives

  • Understand debugging in embedded systems.
  • Learn the debugging workflow in STM32CubeIDE.
  • Set and manage software breakpoints.
  • Use step into, step over, and step return.
  • Inspect variables, registers, and memory.
  • Understand the Call Stack and Expressions views.
  • Recognize common firmware faults.
  • Develop a systematic debugging approach.

2. What is Debugging?

Debugging is the process of identifying, analyzing, and correcting defects in software.

In embedded systems, debugging helps engineers understand how firmware interacts with processor registers, memory, interrupts, and hardware peripherals.

Common Embedded Software Defects

  • Incorrect GPIO configuration.
  • Wrong peripheral clock settings.
  • Incorrect timer calculations.
  • UART communication failures.
  • Invalid pointer access.
  • Interrupt configuration errors.
  • Stack overflow and memory corruption.
  • HardFault exceptions.

Important Components

  • GDB: Controls program execution and inspects program state.
  • ST-LINK: Provides the physical debug connection.

4. Starting a Debug Session

Step-by-Step Procedure

  1. Open the STM32 project in STM32CubeIDE.
  2. Select the Debug build configuration.
  3. Build the project and check for errors.
  4. Connect the STM32 development board to the computer.
  5. Check that the ST-LINK connection is available.
  6. Select the project and choose Debug As or the debug launch configuration.
  7. Review the target device and debug connection settings.
  8. Start the debug session.
  9. Switch to the Debug perspective when prompted.
  10. Inspect the program state and begin debugging.
Depending on the launch configuration, the debugger may program the target and halt at the reset handler, main(), or another configured location.

5. What is a Breakpoint?

A breakpoint is a debugging mechanism that pauses program execution at a selected instruction or source-code location.

Why Use Breakpoints?

  • Inspect variable values.
  • Check whether a function is reached.
  • Analyze program flow.
  • Find the location of a defect.
  • Observe peripheral configuration before execution continues.

Example

int main(void)
{
    int counter = 0;

    while (1)
    {
        counter++;

        if (counter == 10)
        {
            counter = 0;  // Set breakpoint here
        }
    }
}

When execution reaches the breakpoint, the debugger pauses the processor so that the current program state can be examined.

Hardware breakpoints are limited by the target processor's debug resources. Software breakpoints and hardware breakpoints have different implementation constraints.

6. Types of Breakpoints

Breakpoint Purpose
Software Breakpoint Uses debugger-supported instruction replacement or another software mechanism to halt execution.
Hardware Breakpoint Uses processor debug hardware to stop at a specified instruction address.
Conditional Breakpoint Stops execution only when a specified condition is satisfied, where supported.
Watchpoint Stops execution when a monitored memory location is accessed in a configured way, where supported.
Hardware watchpoint resources are limited. A watchpoint is especially useful for locating unexpected changes to a variable.

7. Program Execution Controls

STM32CubeIDE provides execution controls for examining firmware one instruction or source statement at a time.

Command Function
Resume Continues execution until another breakpoint or debug event.
Suspend Requests that the running target halt.
Step Into Executes the next source statement and enters a called function when applicable.
Step Over Executes the next source statement without stepping into a called function.
Step Return Continues until the current function returns.
Terminate Ends the debug session.

8. Inspecting Variables

Variable inspection allows an engineer to observe the values of program variables while execution is paused.

Example

#include <stdint.h>

volatile uint32_t count = 0;

int main(void)
{
    while (1)
    {
        count++;
    }
}

Add count to the Expressions view or inspect it in the Variables view when the debugger can resolve it.

Variable Inspection Can Help Find

  • Unexpected counter values.
  • Incorrect calculation results.
  • Uninitialized or corrupted data.
  • Unexpected state-machine transitions.
  • Incorrect function parameters.
Local variables may be optimized away or shown as unavailable when compiler optimization is enabled. Use a suitable Debug configuration and inspect the generated code if necessary.

9. Registers View

The Registers view displays processor registers and, depending on the debugger configuration, peripheral registers.

Important Cortex-M Registers

Register Purpose
R0–R12 General-purpose registers.
R13 / SP Stack Pointer.
R14 / LR Link Register.
R15 / PC Program Counter.
xPSR Program status register view.

Register inspection helps diagnose incorrect execution flow, stack problems, exception behavior, and processor state.

10. Memory Browser

A memory browser allows an engineer to inspect memory contents at specified addresses.

Common Memory Regions

  • Flash memory.
  • SRAM.
  • Peripheral register address space.
  • System control and debug registers.

Example: Memory-Mapped Peripheral Access

#include <stdint.h>

#define GPIOA_BASE  0x40020000UL

volatile uint32_t *gpioa_moder =
    (volatile uint32_t *)(GPIOA_BASE);

int main(void)
{
    uint32_t mode = *gpioa_moder;

    while (1)
    {
        (void)mode;
    }
}
The address above is only an illustrative GPIOA base address for certain STM32 families, such as STM32F4 devices. Register addresses and layouts vary by STM32 family. Always use the selected device reference manual and CMSIS device header.

11. Call Stack

The Call Stack view displays the sequence of active function calls leading to the current execution point.

Example

main()
  |
  v
process_sensor()
  |
  v
read_adc()
  |
  v
calculate_voltage()

If execution stops inside calculate_voltage(), the Call Stack can help identify the functions that led to that location.

Uses

  • Identify the calling function.
  • Trace nested function calls.
  • Investigate unexpected function execution.
  • Analyze faults that occur during function calls.

12. Debugging Peripheral Registers

Peripheral register inspection is particularly important in embedded firmware because many failures are caused by incorrect hardware configuration.

Examples of Peripheral Checks

Peripheral What to Inspect
GPIO Mode, output type, pull-up/pull-down, and output data.
UART Baud-rate configuration, control, and status registers.
Timer Prescaler, auto-reload, counter, and status registers.
ADC Channel configuration, conversion control, and data register.
I2C Control, status, address, and data registers.
Some peripheral registers have read-to-clear or write-one-to-clear behavior. Reading or writing them during debugging can change hardware state. Consult the reference manual before manually modifying peripheral registers.

13. Debugging a HardFault

A HardFault is a processor exception that indicates a serious fault condition. The exact cause and available fault-status information depend on the Cortex-M core and device configuration.

Possible Causes

  • Invalid memory access.
  • Incorrect pointer usage.
  • Stack overflow or corruption.
  • Invalid instruction execution.
  • Unaligned access where not supported.
  • Escalation of another configurable fault.

Basic Debugging Procedure

  1. Halt the processor when the fault occurs.
  2. Check whether execution reached HardFault_Handler.
  3. Inspect the Call Stack.
  4. Inspect the Program Counter and Link Register.
  5. Examine the stacked exception frame where available.
  6. Check relevant fault-status registers supported by the core.
  7. Identify the failing instruction and source-code path.
  8. Correct the cause and test again.

Common Fault-Status Registers

Register Purpose
CFSR Configurable Fault Status Register, on cores that implement it.
HFSR HardFault Status Register.
MMFAR MemManage Fault Address Register, when implemented and valid.
BFAR BusFault Address Register, when implemented and valid.
SHCSR System Handler Control and State Register.
Not every Cortex-M core implements every configurable fault or fault-status register. An address register is meaningful only when its corresponding validity bit indicates valid information.

14. Common Debugging Problems and Solutions

Problem Possible Solution
Breakpoint is not reached Check execution flow, breakpoint address, and optimization settings.
Variable is unavailable Check scope, compiler optimization, and debug information.
Debugger cannot connect Check target power, ST-LINK, SWD wiring, and debug configuration.
Program repeatedly enters HardFault Inspect fault registers, stacked context, and the failing instruction.
Peripheral values appear incorrect Check peripheral clock, register configuration, and device-specific register behavior.
Program runs differently in Debug and Release Investigate optimization effects, timing, uninitialized data, and race conditions.
Breakpoint stops at unexpected source line Inspect generated instructions and compiler optimization.

15. Placement-Oriented Interview Questions and Answers

Q1. What is debugging?

Debugging is the process of identifying and correcting software defects by inspecting program execution and state.

Q2. What is a breakpoint?

A breakpoint pauses program execution at a selected instruction or source-code location.

Q3. What is the difference between Step Into and Step Over?

Step Into enters a called function when applicable, while Step Over executes the function call without stepping through its internal instructions.

Q4. What is a watchpoint?

A watchpoint monitors a memory location and can halt execution when a configured access or change occurs.

Q5. What is the purpose of the Call Stack?

It shows the sequence of active function calls and helps identify how execution reached the current location.

Q6. What is the purpose of the Registers view?

It allows the developer to inspect processor registers and diagnose execution-state problems.

Q7. What is a HardFault?

A HardFault is a processor exception used to report serious fault conditions or escalated configurable faults.

Q8. Why is volatile important in embedded debugging?

Volatile tells the compiler that an object's value can change outside ordinary program flow, such as through hardware or an interrupt. It prevents certain optimizations of accesses to that object, but does not provide atomicity or general synchronization.

Q9. Why might a variable disappear during debugging?

Compiler optimization may remove or transform variables, making them unavailable or difficult to inspect.

Q10. What is SWD used for?

SWD provides a debug connection that allows supported tools to program and inspect an ARM Cortex-M microcontroller.

Q11. What is the Program Counter?

The Program Counter identifies the instruction address associated with current processor execution.

Q12. How do you debug an STM32 peripheral?

Check its clock enable, configuration registers, status flags, interrupt settings, pin configuration, and external connections.

16. Practical Exercises

  1. Create a basic STM32 project in STM32CubeIDE.
  2. Set a breakpoint inside the main loop.
  3. Start a debug session.
  4. Use Resume, Step Into, and Step Over.
  5. Inspect local and global variables.
  6. Open the Registers view and inspect core registers.
  7. Use the Expressions view to monitor a variable.
  8. Open the Memory view and inspect a valid memory address.
  9. Inspect the Call Stack during a function call.
  10. Observe the behavior of the program when a breakpoint is reached.
No-hardware practice: If a physical STM32 board is unavailable, you can still study debugging concepts, inspect source code, build the project, and practice with a suitable simulator. Actual SWD debugging and peripheral behavior require a compatible target or a simulator that models the relevant hardware.

17. Lesson Summary

  • Debugging identifies and corrects firmware defects.
  • STM32CubeIDE supports source-level debugging.
  • Breakpoints pause execution at selected locations.
  • Step controls help trace program execution.
  • Variables and Expressions views help inspect program data.
  • Registers and Memory views help analyze processor and peripheral state.
  • The Call Stack reveals function execution history.
  • HardFault analysis helps diagnose serious processor faults.
  • Systematic debugging reduces firmware development time.
