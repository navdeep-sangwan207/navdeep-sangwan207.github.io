Mailboxes and Message Queues

1. Introduction

Mailboxes and message queues are inter-task communication mechanisms used by operating systems and RTOS kernels to exchange information between tasks.

They allow one task to send data or a command to another task without requiring both tasks to access the same application variable directly.

Basic concept: A sender places information into a communication object. A receiver obtains that information when it becomes available.

The terms mailbox and message queue are related, but their exact meanings depend on the RTOS implementation.

2. What Is a Mailbox?

A mailbox is a communication mechanism that commonly holds one message or one message pointer at a time.

Depending on the RTOS, a mailbox may:

  • Store one message.
  • Store a pointer to a message buffer.
  • Allow a sender to post a message.
  • Allow a receiver to wait for a message.
  • Support blocking and non-blocking operations.

Mailbox architecture

       +----------------+
       |  Sender Task   |
       +----------------+
               |
               | Post Message
               v
       +----------------+
       |    Mailbox     |
       |  One Message   |
       +----------------+
               |
               | Read Message
               v
       +----------------+
       | Receiver Task  |
       +----------------+

3. What Is a Message Queue?

A message queue is a communication mechanism that stores multiple messages in an ordered collection until receiving tasks retrieve them.

A typical message queue uses FIFO ordering: First In, First Out.

Message queue architecture

       +----------------+
       |  Sender Task   |
       +----------------+
               |
               | Send Messages
               v
       +----------------------+
       |     Message Queue    |
       |                      |
       |  [Message 1]         |
       |  [Message 2]         |
       |  [Message 3]         |
       |  [Empty Slot]        |
       +----------------------+
               |
               | Receive Message
               v
       +----------------+
       | Receiver Task  |
       +----------------+

4. Mailbox vs Message Queue

FeatureMailboxMessage Queue
StorageCommonly one message or pointer.Multiple messages.
CapacityOften one slot, depending on RTOS.Configured number of slots.
CommunicationPost and retrieve a message.Send and receive messages.
OrderingDepends on implementation.Typically FIFO; other operations may alter ordering.
BufferingLimited buffering.Supports a sequence of pending messages.
Typical useLatest status or single pending message.Commands, sensor samples, event records.
A mailbox is not universally a one-message queue. Some RTOS products define mailboxes as pointer-based message-passing services with different storage and ordering rules. Always check the specific RTOS documentation.

5. Why Are Mailboxes and Queues Required?

  • To exchange information between independent tasks.
  • To buffer messages when the receiver is temporarily busy.
  • To separate data acquisition from data processing.
  • To transfer commands and control information.
  • To support producer-consumer applications.
  • To coordinate asynchronous events.
  • To reduce uncontrolled shared-variable access.

6. FIFO Operation

FIFO means First In, First Out. The earliest queued message is normally received first.

Example

Suppose a sender submits three messages:

Message A
Message B
Message C

The receiver obtains them in this order:

First  : Message A
Second : Message B
Third  : Message C

This ordering is useful when every message represents a distinct event or command that must be processed in sequence.

7. Queue States

A message queue can be described using three basic conditions.

ConditionDescription
EmptyNo messages are waiting.
Partially FullSome message slots are occupied.
FullAll available message slots are occupied.

8. Queue Operations

Typical queue operations include:

OperationPurpose
CreateAllocate and initialize queue storage.
SendInsert a message into the queue.
ReceiveRemove and retrieve a message.
PeekInspect the next message without removing it, where supported.
ResetClear queued messages, where supported.
DeleteRelease the queue object and its resources.

9. FreeRTOS Queue Implementation

FreeRTOS provides queue services through its queue API. A queue has a fixed capacity and a fixed item size when it is created.

Important API functions

FunctionPurpose
xQueueCreate()Create a queue dynamically.
xQueueCreateStatic()Create a queue using application-provided storage when static allocation is enabled.
xQueueSend()Send an item to the back of a queue.
xQueueSendToFront()Send an item to the front of a queue.
xQueueReceive()Receive and remove an item.
xQueuePeek()Read an item without removing it.
uxQueueMessagesWaiting()Get the number of queued messages.
uxQueueSpacesAvailable()Get the number of free queue slots.
vQueueDelete()Delete a queue.

Exact availability may depend on FreeRTOS version and configuration.

10. Creating a Message Queue

The xQueueCreate() function creates a queue.

Syntax

QueueHandle_t xQueueCreate(
    UBaseType_t uxQueueLength,
    UBaseType_t uxItemSize
);
ParameterDescription
uxQueueLengthMaximum number of messages stored.
uxItemSizeSize of each message in bytes.

Example

QueueHandle_t xQueue;

xQueue = xQueueCreate(5, sizeof(int));

if (xQueue == NULL)
{
    /* Queue creation failed. */
}

This creates a queue that can hold five integer items.

11. Sending Messages to a Queue

The xQueueSend() function sends an item to the back of a queue.

Syntax

BaseType_t xQueueSend(
    QueueHandle_t xQueue,
    const void *pvItemToQueue,
    TickType_t xTicksToWait
);

Example

int temperature = 30;

if (xQueueSend(xQueue,
               &temperature,
               pdMS_TO_TICKS(100)) == pdPASS)
{
    /* Message successfully queued. */
}
else
{
    /* Queue remained full until timeout. */
}

The queue copies the configured item size from the supplied address into its storage.

12. Receiving Messages from a Queue

The xQueueReceive() function retrieves and removes the next available message.

Syntax

BaseType_t xQueueReceive(
    QueueHandle_t xQueue,
    void *pvBuffer,
    TickType_t xTicksToWait
);

Example

int receivedTemperature;

if (xQueueReceive(xQueue,
                  &receivedTemperature,
                  portMAX_DELAY) == pdPASS)
{
    /* Process received temperature. */
}

The receiver's buffer must be large enough for the configured queue item size.

13. Complete FreeRTOS Queue Example

The following application transfers temperature readings from a sender task to a receiver task.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t xTemperatureQueue;

void SensorTask(void *pvParameters)
{
    int temperature = 25;

    for (;;)
    {
        temperature++;

        if (xQueueSend(xTemperatureQueue,
                       &temperature,
                       pdMS_TO_TICKS(100)) != pdPASS)
        {
            /* Handle queue-full condition. */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void DisplayTask(void *pvParameters)
{
    int receivedTemperature;

    for (;;)
    {
        if (xQueueReceive(xTemperatureQueue,
                          &receivedTemperature,
                          portMAX_DELAY) == pdPASS)
        {
            /* Display or process the value. */
            Process_Temperature(receivedTemperature);
        }
    }
}

int main(void)
{
    xTemperatureQueue = xQueueCreate(5, sizeof(int));

    if (xTemperatureQueue == NULL)
    {
        for (;;)
        {
            /* Handle queue creation failure. */
        }
    }

    xTaskCreate(SensorTask,
                "Sensor",
                256,
                NULL,
                2,
                NULL);

    xTaskCreate(DisplayTask,
                "Display",
                256,
                NULL,
                2,
                NULL);

    vTaskStartScheduler();

    for (;;);
}

Program explanation

  1. A queue is created with five integer slots.
  2. The sensor task generates a temperature value.
  3. The sensor task sends the value to the queue.
  4. The display task waits for a message.
  5. When a message arrives, the display task receives it.
  6. The display task processes the received value.
This is a generic FreeRTOS example, not a verified LPC2129/Keil build. Actual stack sizes, scheduler configuration, port support, and hardware-specific output must be established for the selected target.

14. Mailbox-Like Communication Using a FreeRTOS Queue

FreeRTOS does not provide a separate kernel object named a traditional mailbox in its standard queue API. A queue with a length of one can provide a simple one-slot mailbox-like communication pattern.

Example

{
    xMailbox = xQueueCreate(1, sizeof(int));

    }

    return 0;

For a queue of length one, the application can use queue send and receive operations to exchange one pending integer message.

If the application needs to replace an existing pending value rather than wait for an empty slot, FreeRTOS provides xQueueOverwrite() for queues of length one.

A one-slot queue is useful for communicating the latest value when intermediate updates do not need to be preserved. It is not equivalent to a queue that stores every event.

15. Queue Full and Queue Empty Conditions

Queue full

A queue is full when all its message slots are occupied. A sender may fail immediately or block for the specified timeout.

Queue empty

A queue is empty when no message is available. A receiver may return immediately or wait for a message.

16. Queue Peek Operation

The xQueuePeek() function reads the next queue item without removing it.

Example

int nextValue;

if (xQueuePeek(xQueue,
               &nextValue,
               0) == pdPASS)
{
    /* Inspect nextValue. */
    /* The item remains in the queue. */
}

Use peek when the application needs to inspect the next message without consuming it. If multiple tasks can receive from the same queue, remember that the queue may change after the peek operation completes.

17. Queue Sets

FreeRTOS queue sets allow a task to wait for activity on multiple queue or semaphore objects that have been added to a queue set.

They can be useful when a task must receive from several communication sources without polling each source individually.

Queue sets require the appropriate configuration and queue-set storage. They should be used only when their additional complexity is justified.

18. Queue from ISR

An interrupt service routine may need to transfer received data to a task. FreeRTOS provides special queue functions for interrupt context.

Example pattern

void UART_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    unsigned char receivedByte;

    receivedByte = UART_Read_Byte();

    xQueueSendFromISR(xUARTQueue,
                      &receivedByte,
                      &xHigherPriorityTaskWoken);

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

This is a conceptual pattern. The exact ISR yield macro and interrupt integration depend on the FreeRTOS port.

Do not call ordinary blocking queue APIs from an ISR. Use the documented FromISR functions, handle a full queue, and follow the target port's interrupt-priority and yield requirements.

19. Advantages and Limitations

Advantages

  • Provides structured task-to-task communication.
  • Supports multiple pending messages.
  • Can provide blocking and timeout behavior.
  • Helps separate software modules.
  • Queue operations provide synchronization for queue storage.
  • Supports producer-consumer designs.

Limitations

  • Queue storage consumes RAM.
  • Copying large messages may increase execution time.
  • Queue capacity must be selected carefully.
  • Messages may be delayed when the receiver is busy.
  • Queue overflow requires a defined policy.
  • Pointer-based messages require ownership management.

20. Worked Numerical Problem 1 – Queue Memory

A queue stores 8 messages. Each message occupies 12 bytes.

Payload Storage = 8 × 12
= 96 bytes

Answer: The message payload requires 96 bytes, excluding queue control data and alignment overhead.

21. Worked Numerical Problem 2 – Queue Capacity

A producer generates 20 messages per second. The receiver may be delayed for 300 ms.

Required Slots = 20 × 0.3
= 6 messages

Answer: Six slots are required for the assumed arrival rate during the delay. A practical design should include margin for bursts and other delays.

22. Worked Numerical Problem 3 – Queue Data Rate

A system sends 25 messages per second. Each message contains 32 bytes.

Data Rate = 25 × 32
= 800 bytes/second

Answer: The queue carries 800 bytes per second of message payload at this rate.

23. Practical Activity – Sensor Mailbox and Queue

Develop a conceptual FreeRTOS application to compare a one-slot communication mechanism with a multi-slot queue.

Part A – One-slot mailbox-like queue

  1. Create a queue of length one.
  2. Send a sensor reading periodically.
  3. Receive and process the latest pending reading.
  4. Investigate the behavior when a new value arrives before the old one is received.

Part B – Multi-message queue

  1. Create a queue with five or more slots.
  2. Generate multiple sensor messages.
  3. Allow the receiver to process messages at a slower rate.
  4. Observe queue occupancy.
  5. Test the queue-full condition.
  6. Implement a suitable overflow policy.

Testing checklist

  • Check queue creation return values.
  • Check send and receive return values.
  • Verify FIFO behavior.
  • Test zero and finite timeout behavior.
  • Check queue-full and queue-empty conditions.
  • Verify message size and data types.

25. Lesson Summary

  • Mailboxes and message queues are communication mechanisms for RTOS tasks.
  • A mailbox commonly stores one pending message or pointer, depending on the RTOS.
  • A message queue stores multiple messages.
  • FIFO is the normal ordering for standard FreeRTOS queues.
  • FreeRTOS queues have a configured capacity and item size.
  • Queue send and receive operations can block for a specified timeout.
  • A one-slot FreeRTOS queue can provide mailbox-like behavior.
  • Queue capacity must account for message arrival rate and receiver delays.
  • ISR communication must use documented FromISR APIs.
