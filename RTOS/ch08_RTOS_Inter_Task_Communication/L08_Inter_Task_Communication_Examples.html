1. Introduction

Inter-Task Communication (ITC) allows independent RTOS tasks to exchange information and coordinate their operations.

In practical embedded applications, tasks are divided according to their responsibilities. For example, one task may acquire sensor data, another may process it, and a third may transmit the result through UART.

Objective: Understand how queues, shared memory, task notifications, event groups, and buffers are applied in practical RTOS communication designs.

2. Example 1 – Sensor Data Transfer Using a Queue

Application: Temperature monitoring system.

Task organization

  • Sensor Task: Reads temperature.
  • Processing Task: Checks the temperature limit.
  • Display Task: Receives the processed status.
     +------------------+
     |   Sensor Task    |
     +------------------+
              |
              | Sensor Structure
              v
     +------------------+
     |   Sensor Queue   |
     +------------------+
              |
              v
     +------------------+
     | Processing Task  |
     +------------------+
              |
              | Status Message
              v
     +------------------+
     |   Status Queue   |
     +------------------+
              |
              v
     +------------------+
     |   Display Task   |
     +------------------+

Code example

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

typedef struct
{
    int temperature;
    int voltage;
} SensorData;

typedef struct
{
    int alarm;
    int temperature;
} SystemStatus;

QueueHandle_t xSensorQueue;
QueueHandle_t xStatusQueue;

void SensorTask(void *pvParameters)
{
    SensorData data;

    for (;;)
    {
        data.temperature = Read_Temperature();
        data.voltage = Read_Voltage();

        if (xQueueSend(xSensorQueue, &data,
                       pdMS_TO_TICKS(100)) != pdPASS)
        {
            /* Handle queue full condition. */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ProcessingTask(void *pvParameters)
{
    SensorData input;
    SystemStatus output;

    for (;;)
    {
        if (xQueueReceive(xSensorQueue, &input,
                          portMAX_DELAY) == pdPASS)
        {
            output.temperature = input.temperature;
            output.alarm =
                (input.temperature > 60) ? 1 : 0;

            if (xQueueSend(xStatusQueue, &output,
                           pdMS_TO_TICKS(100)) != pdPASS)
            {
                /* Handle status queue failure. */
            }
        }
    }
}

void DisplayTask(void *pvParameters)
{
    SystemStatus status;

    for (;;)
    {
        if (xQueueReceive(xStatusQueue, &status,
                          portMAX_DELAY) == pdPASS)
        {
            Display_Status(status.temperature,
                           status.alarm);
        }
    }
}

Explanation: Each queue transfers a complete structure. The processing task receives a copy of the sensor data, evaluates it, and sends a separate status structure to the display task.

The example shows communication logic, not a complete buildable project. Implement the hardware-specific functions, create both queues, create all three tasks, check allocation failures, and start the scheduler. An RTOS alarm task must not be the only protection against a potentially dangerous electrical or mechanical condition.

3. Example 2 – Task Notification for Event Signaling

Application: A processing task waits until a communication task has received a complete command.

Working principle

  1. Communication task receives a complete command.
  2. It stores the command in a valid shared data location or queue.
  3. It notifies the processing task.
  4. The processing task wakes and handles the command.

Code example

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t xProcessingHandle;

void CommunicationTask(void *pvParameters)
{
    uint32_t commandCode;

    for (;;)
    {
        commandCode = Receive_Command();

        xTaskNotify(
            xProcessingHandle,
            commandCode,
            eSetValueWithOverwrite
        );

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void ProcessingTask(void *pvParameters)
{
    uint32_t receivedCommand;

    for (;;)
    {
        if (xTaskNotifyWait(
                0,
                0,
                &receivedCommand,
                portMAX_DELAY) == pdTRUE)
        {
            Process_Command(receivedCommand);
        }
    }
}

Explanation: The notification carries a 32-bit command value to a specific receiving task. With eSetValueWithOverwrite, a newer notification value can overwrite an earlier pending value.

Use a queue instead when every command must be preserved. A notification with overwrite semantics is appropriate when the latest value is sufficient.

4. Example 3 – Binary Semaphore for Task Synchronization

Application: A task waits for an event indicating that a measurement is ready.

Working principle

  • A measurement operation completes.
  • An event is signaled using a binary semaphore.
  • The waiting task becomes Ready.
  • The task reads and processes the available measurement.

Code example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xDataReadySemaphore;

void AcquisitionTask(void *pvParameters)
{
    for (;;)
    {
        Perform_Measurement();

        xSemaphoreGive(xDataReadySemaphore);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xDataReadySemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            Process_Measurement();
        }
    }
}

Explanation: The semaphore signals that a measurement event has occurred. The actual measurement data must be stored and transferred safely using a suitable buffer, queue, or shared-data protocol.

This example gives the semaphore from task context. If an ISR signals a task, use the appropriate ISR-safe semaphore API, such as xSemaphoreGiveFromISR(), and follow the port-specific yield requirements.

5. Example 4 – Shared Memory with a Mutex

Application: Two tasks access common system measurements.

Code example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

typedef struct
{
    int temperature;
    int voltage;
} SystemData;

SystemData sharedData;
SemaphoreHandle_t xDataMutex;

void UpdateTask(void *pvParameters)
{
    SystemData newData;

    for (;;)
    {
        newData.temperature = Read_Temperature();
        newData.voltage = Read_Voltage();

        if (xSemaphoreTake(
                xDataMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedData = newData;

            xSemaphoreGive(xDataMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void MonitorTask(void *pvParameters)
{
    SystemData localData;

    for (;;)
    {
        if (xSemaphoreTake(
                xDataMutex,
                portMAX_DELAY) == pdTRUE)
        {
            localData = sharedData;

            xSemaphoreGive(xDataMutex);
        }

        Check_System_Status(&localData);

        vTaskDelay(pdMS_TO_TICKS(200));
    }
}

Explanation: The mutex protects the shared structure while one task updates it or another task reads it. The monitor task copies the structure into local storage and performs its processing after releasing the mutex.

6. Example 5 – Event Groups for Multiple Conditions

Application: A controller waits until sensor initialization and communication initialization are both complete.

Event bit definitions

#define SENSOR_READY_BIT  (1U << 0)
#define UART_READY_BIT    (1U << 1)

Code example

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"

EventGroupHandle_t xSystemEvents;

void SensorInitTask(void *pvParameters)
{
    Initialize_Sensor();

    xEventGroupSetBits(
        xSystemEvents,
        SENSOR_READY_BIT
    );

    vTaskDelete(NULL);
}

void UARTInitTask(void *pvParameters)
{
    Initialize_UART();

    xEventGroupSetBits(
        xSystemEvents,
        UART_READY_BIT
    );

    vTaskDelete(NULL);
}

void MainControlTask(void *pvParameters)
{
    const EventBits_t requiredBits =
        SENSOR_READY_BIT | UART_READY_BIT;

    for (;;)
    {
        EventBits_t result = xEventGroupWaitBits(
            xSystemEvents,
            requiredBits,
            pdFALSE,
            pdTRUE,
            portMAX_DELAY
        );

        if ((result & requiredBits) == requiredBits)
        {
            Start_Main_Application();
        }

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

Explanation: The controller waits until both event bits are set. The pdTRUE argument requests wait-for-all behavior, while pdFALSE leaves the bits set when the wait completes.

Event groups communicate conditions, not complete data records. Use a queue or buffer to transfer actual sensor measurements or communication payloads.

7. Example 6 – UART Data Exchange Using a Queue

Application: A UART receive interrupt transfers received bytes to a communication task.

Architecture

       UART0 Hardware
              |
              v
          UART0 ISR
              |
              | FromISR Queue API
              v
        Character Queue
              |
              v
      UART Receive Task
              |
              v
       Message Processing

Code example – Conceptual ISR-to-task transfer

#include "FreeRTOS.h"
#include "queue.h"
#include "task.h"

QueueHandle_t xUARTQueue;

void UART0_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    unsigned char receivedByte;

    /*
       Read received byte from the UART hardware.
       The actual register access and interrupt
       acknowledgement depend on the MCU.
    */
    receivedByte = UART0_Read_Byte();

    xQueueSendFromISR(
        xUARTQueue,
        &receivedByte,
        &xHigherPriorityTaskWoken
    );

    /*
       Use the yield mechanism required by
       the selected FreeRTOS port.
    */
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void UARTReceiveTask(void *pvParameters)
{
    unsigned char byte;

    for (;;)
    {
        if (xQueueReceive(
                xUARTQueue,
                &byte,
                portMAX_DELAY) == pdPASS)
        {
            Process_Received_Byte(byte);
        }
    }
}
This is a generic FreeRTOS illustration. The UART register access, interrupt vector, interrupt acknowledgement, ISR API availability, and yield macro must match the actual MCU and FreeRTOS port. The code is not a verified LPC2129 FreeRTOS implementation.

8. Example 7 – Stream Buffer for Byte-Stream Communication

Application: Transferring UART data as a continuous byte stream.

A stream buffer is suitable when the application exchanges a sequence of bytes rather than fixed-size queue items.

Code example

#include "FreeRTOS.h"
#include "task.h"
#include "stream_buffer.h"
#include 

StreamBufferHandle_t xUARTStream;

void UARTProducerTask(void *pvParameters)
{
    uint8_t data[16];
    size_t bytesReceived;

    for (;;)
    {
        bytesReceived = Read_UART_Bytes(data, sizeof(data));

        if (bytesReceived > 0U)
        {
            size_t sent = xStreamBufferSend(
                xUARTStream,
                data,
                bytesReceived,
                pdMS_TO_TICKS(100)
            );

            if (sent != bytesReceived)
            {
                /* Handle partial transfer. */
            }
        }
    }
}

void UARTConsumerTask(void *pvParameters)
{
    uint8_t buffer[32];
    size_t received;

    for (;;)
    {
        received = xStreamBufferReceive(
            xUARTStream,
            buffer,
            sizeof(buffer),
            portMAX_DELAY
        );

        if (received > 0U)
        {
            Process_UART_Stream(buffer, received);
        }
    }
}

Explanation: The consumer receives a variable number of bytes. The application must implement protocol framing, such as delimiters, length fields, or another message-boundary method.

9. Example 8 – Message Buffer for Variable-Length Messages

Application: Transferring complete command messages with different lengths.

Code example

#include "FreeRTOS.h"
#include "task.h"
#include "message_buffer.h"
#include 
#include 

MessageBufferHandle_t xMessageBuffer;

void CommandProducerTask(void *pvParameters)
{
    const char message[] = "START";

    for (;;)
    {
        size_t sent = xMessageBufferSend(
            xMessageBuffer,
            message,
            sizeof(message),
            pdMS_TO_TICKS(100)
        );

        if (sent == 0U)
        {
            /* Message could not be sent. */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void CommandConsumerTask(void *pvParameters)
{
    char received[32];
    size_t length;

    for (;;)
    {
        length = xMessageBufferReceive(
            xMessageBuffer,
            received,
            sizeof(received),
            portMAX_DELAY
        );

        if (length > 0U)
        {
            Process_Command_Message(received, length);
        }
    }
}

Explanation: A message buffer preserves message boundaries. The receiving task obtains one complete message per successful receive operation, provided the receive buffer is large enough for that message.

10. Queue vs Stream Buffer vs Message Buffer

FeatureQueueStream BufferMessage Buffer
Data formatFixed-size itemsByte streamVariable-length messages
Message boundariesPreservedNot inherentPreserved
Typical useSensor structures and commandsUART byte streamsVariable-length frames
Typical access modelMultiple writers/readers supportedOne writer and one reader assumedOne writer and one reader assumed
Transfer APIxQueueSend / xQueueReceivexStreamBufferSend / ReceivexMessageBufferSend / Receive
FreeRTOS stream and message buffers assume one writer and one reader. Multiple writers or readers require external serialization. These facilities also depend on the relevant FreeRTOS configuration and version.

11. Choosing the Correct Communication Mechanism

RequirementRecommended Mechanism
Transfer fixed-size sensor structuresQueue
Transfer continuous UART bytesStream buffer
Transfer variable-length framesMessage buffer
Notify one specific taskTask notification
Wait for multiple system conditionsEvent group
Protect shared task-accessed dataMutex
Signal a simple eventBinary semaphore
Transfer large data blocks efficientlyPointer or buffer ownership transfer

12. Important FreeRTOS API Reference

APIPurpose
xQueueCreate()Create a queue.
xQueueSend()Send an item to a queue.
xQueueReceive()Receive an item from a queue.
xSemaphoreTake()Take a semaphore or mutex.
xSemaphoreGive()Give a semaphore or mutex.
xTaskNotify()Send a notification to a task.
xTaskNotifyWait()Wait for a task notification.
xEventGroupSetBits()Set event bits.
xEventGroupWaitBits()Wait for event bits.
xStreamBufferSend()Send bytes to a stream buffer.
xStreamBufferReceive()Receive bytes from a stream buffer.
xMessageBufferSend()Send a discrete message.
xMessageBufferReceive()Receive a discrete message.

Queue, semaphore, task notification, event group, stream buffer, and message buffer APIs have different semantics. Select APIs according to the communication requirement, not merely because they are available.

13. Common Programming Errors

  • Sending a pointer to memory that becomes invalid before the receiver uses it.
  • Ignoring queue-send failure and silently losing data.
  • Using a mutex inside an ISR.
  • Calling a blocking API from interrupt context.
  • Using a task notification when every message must be retained.
  • Using an event group as if it were a data queue.
  • Assuming a stream buffer preserves application message boundaries.
  • Using stream or message buffers with multiple writers/readers without serialization.
  • Holding a mutex for too long while performing unrelated processing.
  • Assuming volatile alone solves race conditions.

15. Keil Simulator and LPC2129 Learning Notes

The LPC2129 uses an ARM7TDMI-S processor. The examples in this lesson explain generic FreeRTOS communication patterns and should not be interpreted as proof that a compatible FreeRTOS port is available for the user's LPC2129/Keil setup.

With the Keil simulator, you can practise the underlying C concepts, inspect variables, follow function calls, and observe memory changes in standalone programs. Actual RTOS scheduling and communication API behavior require a compatible RTOS port and execution environment.

  • Practise structures and pointers using standalone C programs.
  • Implement a simple producer-consumer ring buffer.
  • Use UART0 register-level examples separately for LPC2129.
  • Study queue and semaphore behavior using a verified FreeRTOS-supported target or host environment.
  • Do not assume simulator variable inspection proves real-time timing behavior.

17. Lesson Summary

  • Queues transfer fixed-size data items between tasks.
  • Task notifications provide lightweight signaling to a particular task.
  • Semaphores coordinate task activity and event handling.
  • Mutexes protect shared resources accessed by tasks.
  • Event groups synchronize tasks using event bits.
  • Stream buffers transfer byte streams, while message buffers preserve variable-length message boundaries.
  • ISR communication requires interrupt-safe APIs.
  • Communication design must account for data ownership, buffer capacity, synchronization, and failure handling.
