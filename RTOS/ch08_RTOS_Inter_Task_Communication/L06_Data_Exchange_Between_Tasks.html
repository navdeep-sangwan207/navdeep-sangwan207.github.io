1. Introduction

Data exchange between tasks is the process of transferring information from one independently executing task to another in an RTOS-based application.

In a multitasking embedded system, different tasks often perform separate operations. One task may collect sensor measurements, another may process the measurements, and another may display or transmit the results.

Example: A temperature acquisition task measures temperature and transfers the result to a monitoring task. The monitoring task checks the operating limits and forwards the processed information to a communication task.

2. Why Is Data Exchange Required?

  • To transfer sensor readings between tasks.
  • To separate data acquisition from data processing.
  • To send commands to control tasks.
  • To share application status between software modules.
  • To coordinate communication and control operations.
  • To reduce direct dependencies between tasks.
  • To build modular and maintainable embedded applications.

5. Methods of Data Exchange

5.1 Shared Memory

Multiple tasks access a common memory location or data structure.

int sharedTemperature = 0;

Synchronization is required when concurrent access could cause inconsistent data or race conditions.

5.2 Message Queues

A sender transfers data by placing a message into a queue. A receiver retrieves the message.

xQueueSend(xQueue, &sensorData, timeout);

5.3 Mailbox-Like Communication

A one-slot communication object can hold one pending value or message, depending on the RTOS implementation.

5.4 Task Notifications

A task notification can signal another task and can optionally carry a 32-bit value using an appropriate notification action.

5.5 Event Groups

Event groups allow tasks to synchronize using one or more event bits. They are useful for indicating that data or an operation is ready.

5.6 Buffer-Based Communication

A producer writes data into a buffer and a consumer reads it according to a defined ownership and synchronization protocol.

6. Data Exchange Using a Queue

Queues are useful when individual data items must be transferred and preserved in order.

Example

#include "FreeRTOS.h"
#include "queue.h"

typedef struct
{
    int temperature;
    int voltage;
} SensorData;

QueueHandle_t xSensorQueue;

void SensorTask(void *pvParameters)
{
    SensorData data;

    for (;;)
    {
        data.temperature = Read_Temperature();
        data.voltage = Read_Voltage();

        if (xQueueSend(xSensorQueue,
                       &data,
                       pdMS_TO_TICKS(100)) != pdPASS)
        {
            /* Handle queue-full condition. */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ProcessingTask(void *pvParameters)
{
    SensorData receivedData;

    for (;;)
    {
        if (xQueueReceive(xSensorQueue,
                          &receivedData,
                          portMAX_DELAY) == pdPASS)
        {
            Process_Sensor_Data(&receivedData);
        }
    }
}

The queue copies the configured structure size into its storage and copies the received item into the receiver's local structure.

7. Data Exchange Using Shared Memory

Shared memory can be used when multiple tasks need access to common application state.

Example structure

typedef struct
{
    int temperature;
    int voltage;
    unsigned int status;
} SystemData;

SystemData sharedSystemData;

A producer can update the structure and a consumer can read it. If the data fields must represent one consistent snapshot, protect the update and read with an appropriate synchronization mechanism.

Task-level protection using a mutex

SemaphoreHandle_t xSystemDataMutex;

void UpdateSystemData(const SystemData *newData)
{
    if (xSemaphoreTake(xSystemDataMutex,
                       portMAX_DELAY) == pdTRUE)
    {
        sharedSystemData = *newData;

        xSemaphoreGive(xSystemDataMutex);
    }
}

SystemData ReadSystemData(void)
{
    SystemData localCopy = {0};

    if (xSemaphoreTake(xSystemDataMutex,
                       portMAX_DELAY) == pdTRUE)
    {
        localCopy = sharedSystemData;

        xSemaphoreGive(xSystemDataMutex);
    }

    return localCopy;
}

These functions are intended for task context. Do not call blocking mutex operations from an ISR.

8. Data Exchange Using Task Notifications

Task notifications are useful when one task needs to signal another task with a small value or event.

Example: Transfer a 32-bit value

TaskHandle_t xReceiverHandle;

/* Sender task */
void SenderTask(void *pvParameters)
{
    uint32_t sensorValue = 250;

    for (;;)
    {
        xTaskNotify(
            xReceiverHandle,
            sensorValue,
            eSetValueWithOverwrite
        );

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

/* Receiver task */
void ReceiverTask(void *pvParameters)
{
    uint32_t receivedValue;

    for (;;)
    {
        if (xTaskNotifyWait(
                0,
                0,
                &receivedValue,
                portMAX_DELAY) == pdTRUE)
        {
            Process_Value(receivedValue);
        }
    }
}

The example uses an overwrite notification action, so a new value can replace an earlier pending value. This is suitable when the latest value matters more than preserving every sample.

9. Copying Data vs Passing Pointers

Copying data

The communication mechanism copies the configured data bytes into its own storage or the receiver's destination.

  • Simple ownership model.
  • Receiver obtains an independent copy.
  • Suitable for small and medium-sized data items.
  • Large structures can increase copying overhead.

Passing pointers

The communication mechanism transfers an address rather than the complete data block.

  • Can reduce copying of large data blocks.
  • Requires valid memory for the entire period of use.
  • Requires clear ownership transfer rules.
  • Can cause corruption if the producer overwrites the buffer too early.
Never send a pointer to a task-local stack variable and assume the receiver can safely use it after the sender returns from that function. The pointed-to memory must remain valid throughout the receiver's use.

10. Producer-Consumer Data Exchange

The producer-consumer model separates data generation from data processing.

  • Producer: Generates or collects data.
  • Consumer: Receives and processes data.
  • Buffer: Temporarily stores data between the two tasks.

11. Data Synchronization

Data synchronization ensures that tasks access shared information in a controlled and consistent manner.

Common synchronization methods

12. Race Conditions During Data Exchange

A race condition occurs when the outcome depends on the order or timing of concurrent operations on shared data.

Example

sharedCounter = sharedCounter + 1;

If two tasks execute this read-modify-write operation concurrently, one update may overwrite the other.

Prevention

  • Use a suitable mutex for shared resources.
  • Use atomic operations where their guarantees fit the operation.
  • Use queues to transfer independent data items.
  • Keep critical sections short.
  • Define ownership of shared buffers.

13. Data Consistency and Memory Visibility

Data consistency means that the receiver obtains information that is logically valid and internally consistent.

For example, a temperature and voltage measurement stored in one structure may need to be read as a single snapshot. Reading one field before an update and another field after the update can produce an inconsistent combination.

Important concepts

  • Atomicity: An operation is indivisible with respect to the relevant observers.
  • Memory visibility: A task must observe data published by another task according to the synchronization and memory-ordering rules.
  • Consistency: Related values represent a valid state of the application.
  • Ordering: Operations occur in an order guaranteed by the synchronization model.
The C volatile keyword alone does not provide atomicity, mutual exclusion, or general inter-task memory synchronization.

14. Data Ownership and Lifetime

Every shared buffer should have a defined ownership model.

Example ownership sequence

  1. Producer owns an available buffer.
  2. Producer fills the buffer.
  3. Producer transfers the buffer reference to the consumer.
  4. Consumer owns and processes the buffer.
  5. Consumer returns the buffer to a free pool or transfers it to another owner.

Ownership rules prevent the producer from modifying data while the consumer is reading it.

15. Data Exchange in a UART-Based Embedded System

Consider an LPC2129-based application that receives data through UART0.

Task organization

  1. UART0 receives bytes through its interrupt mechanism.
  2. The interrupt handler captures the minimum required information.
  3. Received data is transferred using an appropriate interrupt-safe communication mechanism.
  4. A communication task assembles a complete message.
  5. A processing task validates the message.
  6. A display or control task uses the processed result.

16. Worked Numerical Problem 1 – Data Transfer Rate

A sensor task sends 40 samples per second. Each sample occupies 8 bytes.

Data Rate = Samples per Second × Bytes per Sample
= 40 × 8 = 320 bytes/second

Answer: The data transfer rate is 320 bytes per second, excluding communication metadata and protocol overhead.

17. Worked Numerical Problem 2 – Buffer Capacity

A producer generates 30 messages per second. The consumer may be delayed for 200 ms.

Required Slots = 30 × 0.2
= 6 messages

Answer: At least six slots are needed for the assumed arrival rate during the delay. Add capacity for bursts and existing queued messages.

18. Worked Numerical Problem 3 – Data Memory

An application stores 100 samples. Each sample occupies 4 bytes.

Memory Required = 100 × 4
= 400 bytes

Answer: The sample array requires 400 bytes, excluding additional metadata and alignment overhead.

19. Practical Activity – Sensor Data Exchange

Design a conceptual RTOS application with three tasks:

  • Sensor Task
  • Processing Task
  • Display Task

Requirements

  1. Define a sensor data structure.
  2. Generate temperature and voltage measurements.
  3. Transfer measurements from the sensor task to the processing task using a queue.
  4. Validate the received measurements.
  5. Calculate a processed status value.
  6. Transfer the status to the display task.
  7. Check queue operation return values.
  8. Handle queue-full and timeout conditions.
  9. Verify that all tasks use valid data.

Testing checklist

  • Check the data structure size.
  • Verify correct message order.
  • Check queue capacity.
  • Test producer and consumer timing differences.
  • Check for race conditions in any shared variables.
  • Verify buffer ownership if pointers are used.

21. Lesson Summary

  • Data exchange allows independent tasks to transfer application information.
  • Queues, shared memory, buffers, and task notifications are common mechanisms.
  • Queues are useful for preserving individual messages.
  • Shared memory requires suitable synchronization.
  • Pointer-based transfer requires explicit ownership and lifetime management.
  • Race conditions can cause lost updates and inconsistent data.
  • Data consistency and memory visibility are important in concurrent applications.
  • Buffer capacity must account for data rates and task delays.
  • ISR-to-task communication must use supported interrupt-safe mechanisms.
