1. Introduction

In a Real-Time Operating System (RTOS), multiple tasks execute under the control of a scheduler. Each task may perform a different function within an embedded application.

However, tasks rarely operate completely independently. One task may collect sensor data, another may process that data, and another may transmit the results through UART, CAN, or another communication interface.

These tasks need a mechanism to exchange information and coordinate their execution.

Inter-task communication (ITC) is the process through which tasks exchange data, send messages, signal events, or coordinate activities within an operating system.

Example: A temperature-monitoring task reads a sensor and sends the measured value to a display task. The display task receives the value and updates the user interface.

2. Why Is Inter-Task Communication Required?

Inter-task communication is required when different tasks need to cooperate to complete an application function.

Main purposes

  • Exchange data between tasks.
  • Transfer messages and commands.
  • Notify tasks about important events.
  • Synchronize task execution.
  • Share application information.
  • Coordinate access to common resources.
  • Separate application functions into independent modules.

Example: Industrial temperature monitoring

Consider an embedded temperature-monitoring system with three tasks:

  1. Sensor Task: Reads temperature values.
  2. Processing Task: Converts and checks the measured values.
  3. Display Task: Displays the processed temperature.

The tasks must exchange data to complete the monitoring operation.

4. Tasks and Data Exchange

A task can communicate with another task by exchanging data through a shared object or an RTOS-provided communication mechanism.

Example

Suppose Task A reads an ADC value and Task B calculates the corresponding voltage.

Voltage = (ADC Count / 1023) × Vref

For a 10-bit ADC with a 3.3 V reference, if the ADC count is 512:

Voltage = (512 / 1023) × 3.3 ≈ 1.652 V

Task A can transfer the ADC count to Task B using a queue or a properly synchronized shared-data structure.

5. Types of Inter-Task Communication

5.1 Shared Memory

Two or more tasks access a common memory location or data structure.

5.2 Message Passing

One task sends a message to another task through an RTOS communication mechanism.

5.3 Queues

Queues transfer data items in a defined order, commonly FIFO.

5.4 Semaphores

Semaphores provide synchronization and event signaling between tasks.

5.5 Mutexes

Mutexes protect shared resources from simultaneous access and can provide priority inheritance in supported RTOS implementations.

5.6 Event Groups

Event groups allow tasks to wait for one or more event conditions represented by bits.

5.7 Task Notifications

FreeRTOS task notifications provide lightweight signaling and, depending on the notification operation, can also transfer a 32-bit value.

6. Shared Memory Communication

Shared memory communication occurs when multiple tasks access the same memory location.

For example, a sensor task can update a shared temperature variable while a display task reads it.

Conceptual example

volatile int temperature = 0;

/* Sensor Task */
void SensorTask(void *pvParameters)
{
    for (;;)
    {
        temperature = Read_Temperature();

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

/* Display Task */
void DisplayTask(void *pvParameters)
{
    int localTemperature;

    for (;;)
    {
        localTemperature = temperature;

        Update_Display(localTemperature);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

Advantages

  • Simple for small data exchanges.
  • Can be efficient for frequently accessed data.
  • Does not require copying every data item through a queue.

Limitations

  • Race conditions may occur.
  • Data may be read while another task is updating it.
  • Synchronization may be required.
  • Complex structures may be observed in partially updated states.
The volatile keyword does not provide mutual exclusion or guarantee atomic access. Shared data must be protected using suitable synchronization or atomic operations.

7. Message Passing Communication

Message passing allows one task to send information to another task through an RTOS communication object.

The sender and receiver do not need to access the same application variable directly.

Working principle

  1. Sender task prepares a message.
  2. Sender sends the message to a communication object.
  3. The RTOS stores or transfers the message.
  4. Receiver task waits for the message.
  5. The receiver obtains and processes the message.

Message passing helps reduce direct dependencies between application tasks.

8. Queue-Based Communication

A queue is a common RTOS mechanism for transferring data between tasks.

In a typical FIFO queue, the first item sent is the first item received.

Queue architecture

       | FIFO Buffer |

             |

Example applications

  • Sensor readings transferred to a processing task.
  • UART messages transferred to a communication task.
  • Commands transferred to a motor-control task.
  • Event records transferred to a logging task.

Queues can also be used to communicate between an ISR and a task through the appropriate ISR-safe queue APIs.

10. Mutex-Based Resource Protection

A mutex is used to protect a shared resource from simultaneous access by multiple tasks.

For example, two tasks may need to access the same communication interface or shared data structure.

Typical operation

  1. Task A requests the mutex.
  2. If available, Task A acquires it.
  3. Task A accesses the shared resource.
  4. Task A releases the mutex.
  5. Another task can then acquire the mutex.
A mutex provides ownership-based mutual exclusion. It is not interchangeable with every semaphore use case. In FreeRTOS, mutexes provide priority inheritance, while binary semaphores do not.

11. Event Group Communication

An event group represents a collection of event bits.

Different tasks can set or wait for event bits to coordinate application activities.

Example

Consider a system that requires three conditions before starting a motor:

  • Sensor initialized.
  • Communication initialized.
  • Safety check completed.

An event group can represent these conditions using individual bits.

Bit 0: SENSOR_READY
Bit 1: COMMUNICATION_READY
Bit 2: SAFETY_CHECK_COMPLETE

          v

12. Task Notifications

FreeRTOS task notifications allow one task or an ISR to notify a particular task directly.

They can be used for event signaling, counting notifications, or passing a 32-bit notification value, depending on the selected notification action.

Typical example

TaskHandle_t xTaskBHandle;

/* Task A */
void TaskA(void *pvParameters)
{
    for (;;)
    {
        /* Perform some operation. */

        xTaskNotifyGive(xTaskBHandle);

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

/* Task B */
void TaskB(void *pvParameters)
{
    for (;;)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* Process notification. */
    }
}

Task notifications can be more memory-efficient than creating a separate queue or semaphore when only one receiving task needs to be notified.

13. Blocking and Non-Blocking Communication

RTOS communication APIs may support blocking and non-blocking behavior.

Blocking communication

A task waits for a specified event or resource. During this time, the scheduler can run other Ready tasks.

Non-blocking communication

A task attempts the operation and returns without waiting if the required condition is not satisfied.

FeatureBlockingNon-Blocking
WaitingMay wait for an event or resource.Returns immediately.
CPU usageTask does not continuously poll while blocked.Task can continue other work.
Typical applicationWaiting for queue data.Checking whether a queue item is immediately available.
TimeoutMay use a finite or indefinite timeout.Typically uses zero waiting time.
Blocking an RTOS task does not mean that the entire processor stops. The scheduler can execute another Ready task.

14. Inter-Task Communication vs Inter-Task Synchronization

These concepts are related but have different purposes.

CommunicationSynchronization
Transfers information between tasks.Coordinates when tasks execute or access resources.
Often uses queues and messages.Often uses semaphores, mutexes, and event groups.
Example: transfer an ADC reading.Example: wait until ADC conversion is complete.

A single RTOS mechanism may support both communication and synchronization, depending on how it is used.

15. Real-World Embedded System Example

Consider an industrial motor-monitoring application.

Task organization

This design divides a large application into independent tasks while allowing them to cooperate through communication mechanisms.

For safety-critical motor protection, do not rely solely on a low-priority application task if a hardware comparator, protection circuit, or dedicated fast shutdown path is required.

16. Advantages of Inter-Task Communication

  • Modular application architecture.
  • Better separation of responsibilities.
  • Efficient data exchange.
  • Improved synchronization.
  • Reduced direct dependencies between tasks.
  • Support for producer-consumer designs.
  • Easier testing and maintenance.
  • Better coordination of complex embedded applications.

17. Common Inter-Task Communication Problems

Race condition

Two or more tasks access shared data in an unsafe sequence.

Deadlock

Tasks wait indefinitely for resources held by one another.

Starvation

A task is repeatedly prevented from receiving the CPU or required resources.

Queue overflow

New data cannot be inserted because the queue is full.

Data inconsistency

A task reads a structure while another task is modifying it.

Priority inversion

A higher-priority task is blocked by a lower-priority task holding a required resource, while intermediate-priority tasks may delay the resource owner.

19. Worked Numerical Problem 1 – Data Transfer Rate

A sensor task produces 20 data samples per second. Each sample contains 4 bytes.

Solution

Data Rate = Samples per Second × Bytes per Sample
= 20 × 4 = 80 bytes/second

Answer: The communication mechanism must handle an average data rate of 80 bytes per second, excluding queue metadata and additional application overhead.

20. Worked Numerical Problem 2 – Queue Capacity

A producer task generates 25 messages per second. A consumer task may be delayed for 400 ms. Assume a constant arrival rate.

Solution

Required Queue Capacity = Message Rate × Delay
= 25 × 0.4 = 10 messages

Answer: At least 10 message slots are required under the stated assumptions. A practical queue should include additional capacity for bursts and variable scheduling delays.

21. Worked Numerical Problem 3 – Producer and Consumer Rates

A producer generates 30 messages per second, while a consumer processes 40 messages per second.

Solution

Net Processing Capacity = 40 − 30 = 10 messages/second

Answer: The consumer has an average surplus processing capacity of 10 messages per second. Under steady-state assumptions, the queue will not grow indefinitely.

If the producer rate becomes greater than the consumer rate for a sustained period, the queue will eventually fill unless the system applies flow control, increases processing capacity, or drops messages according to a defined policy.

24. Lesson Summary

  • Inter-task communication allows RTOS tasks to exchange information and coordinate activities.
  • Shared memory provides direct access to common data but requires synchronization.
  • Message passing separates sender and receiver through communication objects.
  • Queues transfer data and messages, commonly in FIFO order.
  • Semaphores signal events and support synchronization.
  • Mutexes protect shared resources.
  • Event groups coordinate multiple event conditions.
  • Task notifications provide efficient direct signaling.
  • Blocking communication allows other Ready tasks to execute.
  • Communication design must consider race conditions, deadlocks, starvation, and buffer capacity.
