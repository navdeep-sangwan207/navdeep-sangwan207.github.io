1. Introduction

Message passing is an inter-task communication technique in which one task sends information to another task through a defined communication mechanism.

Instead of directly accessing the same application variable, the sender prepares a message and transfers it to a communication object. The receiving task obtains the message and processes it.

Example: A sensor task sends a temperature measurement to a processing task. The processing task receives the message, checks the temperature limit, and sends an appropriate command to another task.

2. Why Is Message Passing Required?

  • To transfer information between independent tasks.
  • To reduce direct dependencies between software modules.
  • To separate data collection from data processing.
  • To transfer commands and status information.
  • To organize producer-consumer applications.
  • To avoid uncontrolled access to shared application data.
  • To improve modularity and maintainability.

The communication object may be implemented using a queue, mailbox, message buffer, or another RTOS-specific mechanism.

4. Components of Message Passing

4.1 Sender Task

The sender task creates or prepares the message and submits it to the communication mechanism.

4.2 Message

A message contains the information to be transferred. It may be a number, command, structure, status value, or buffer descriptor.

4.3 Communication Object

The communication object stores or transfers messages between tasks.

4.4 Receiver Task

The receiver waits for a message, obtains it, and performs the required operation.

5. Message Structure

A message can contain multiple related fields.

Example: Temperature monitoring message

typedef struct
{
    unsigned int messageID;
    float temperature;
    unsigned int timestamp;
    unsigned int status;
} TemperatureMessage;
FieldPurpose
messageIDIdentifies the message type.
temperatureStores the measured temperature.
timestampRecords the measurement time or application tick value.
statusIndicates the measurement or sensor status.

A well-defined message format helps the receiver interpret the transmitted information correctly.

6. Message Passing Using a Queue

In FreeRTOS, queues are commonly used to implement message passing between tasks.

A queue stores a configured number of items. In a standard queue, items are received in FIFO order.

Working sequence

  1. Create the queue.
  2. Prepare a message in the sender task.
  3. Send the message using xQueueSend().
  4. The receiver waits using xQueueReceive().
  5. The receiver processes the received message.
       Sender Task
            |
            | xQueueSend()
            v
       +------------+
       | RTOS Queue |
       +------------+
            |
            | xQueueReceive()
            v
      Receiver Task

7. FreeRTOS Message Passing Example

The following generic FreeRTOS example demonstrates message transfer using a queue.

Complete example

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

typedef struct
{
    unsigned int id;
    int temperature;
} Message;

QueueHandle_t xMessageQueue;

void SenderTask(void *pvParameters)
{
    Message msg;

    unsigned int counter = 0;

    for (;;)
    {
        msg.id = counter;
        msg.temperature = 25 + (counter % 10);

        if (xQueueSend(xMessageQueue,
                       &msg,
                       pdMS_TO_TICKS(100)) == pdPASS)
        {
            counter++;
        }
        else
        {
            /* Queue full or timeout. */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ReceiverTask(void *pvParameters)
{
    Message receivedMessage;

    for (;;)
    {
        if (xQueueReceive(xMessageQueue,
                         &receivedMessage,
                         portMAX_DELAY) == pdPASS)
        {
            /* Process received message. */
            Process_Message(&receivedMessage);
        }
    }
}

int main(void)
{
    xMessageQueue = xQueueCreate(5, sizeof(Message));

    if (xMessageQueue == NULL)
    {
        for (;;)
        {
            /* Handle queue creation failure. */
        }
    }

    xTaskCreate(SenderTask,
                "Sender",
                256,
                NULL,
                2,
                NULL);

    xTaskCreate(ReceiverTask,
                "Receiver",
                256,
                NULL,
                2,
                NULL);

    vTaskStartScheduler();

    for (;;);
}

Explanation:

  • xQueueCreate() creates a queue with five message slots.
  • sizeof(Message) defines the size of each queue item.
  • xQueueSend() copies the message item into the queue.
  • xQueueReceive() copies a message from the queue into the receiver's local variable.
  • portMAX_DELAY requests an indefinite wait when the relevant FreeRTOS configuration supports it.
  • The receiver processes a local copy, so it does not depend on the sender's local message variable remaining valid.
This is a generic FreeRTOS example. It requires a compatible FreeRTOS port, valid task stack sizes for the target, and the required kernel configuration. It is not a verified LPC2129/Keil project.

8. Message Copying and Pointer-Based Messages

8.1 Copying Message Data

By default, FreeRTOS queues copy the configured number of bytes from the sender's item into queue storage. Receiving also copies the item into the receiver's destination.

This is convenient for small and medium-sized messages.

8.2 Pointer-Based Messages

For large data blocks, an application may send a pointer to a buffer instead of copying the entire buffer into the queue.

typedef struct
{
    unsigned char *buffer;
    unsigned int length;
} BufferMessage;

The queue copies the pointer and length fields. It does not copy the memory block addressed by the pointer.

Pointer-based messaging requires an explicit ownership and lifetime protocol. The sender must not overwrite or release the buffer while the receiver is using it. Define who allocates, owns, transfers, and releases each buffer.

10. Synchronous and Asynchronous Message Passing

Synchronous message passing

The sender and receiver participate in a coordinated exchange in which the sender may wait for the receiver or for a response before continuing. The exact behavior depends on the communication mechanism.

Asynchronous message passing

The sender submits a message and continues execution without waiting for the receiver to process it. A queue is commonly used for this pattern.

FeatureSynchronousAsynchronous
CoordinationMore tightly coordinated.Sender and receiver operate independently.
WaitingMay wait for acknowledgement or receiver.Sender may continue after successful submission.
BufferingMay use direct rendezvous or a buffer.Usually uses a buffer or message queue.
Typical useRequest-response exchange.Sensor data and event reporting.

11. Message Passing and Blocking

Message operations may block depending on the API and timeout supplied.

Sender behavior

  • Zero timeout: return immediately if the queue cannot accept the message.
  • Finite timeout: wait up to the specified number of ticks.
  • Indefinite timeout: wait until space becomes available, subject to configuration and API rules.

Receiver behavior

  • Zero timeout: return immediately if no message is available.
  • Finite timeout: wait for a message up to the specified time.
  • Indefinite timeout: wait until a message arrives, subject to configuration.
A blocked sender or receiver does not continuously consume CPU time. The scheduler can run another Ready task.

12. Message Priority and Ordering

Standard FreeRTOS queues normally use FIFO ordering. A message sent first is normally received first.

FreeRTOS also provides queue operations that can place an item at the front of a queue. This changes message ordering and should be used only when the application explicitly requires it.

Message ordering and task scheduling priority are different concepts:

  • Message ordering: Determines which queued item is received next.
  • Task priority: Determines which Ready task is selected by the scheduler.

13. Error Handling in Message Passing

Communication failures must be handled explicitly.

ProblemPossible Handling
Queue fullRetry, block with a timeout, apply flow control, or drop according to policy.
Queue emptyWait for data or perform another task operation.
Invalid messageValidate message type, length, and values.
Corrupted dataUse suitable integrity checks where required.
Receiver delayedReview task priority, execution time, and queue capacity.
Lost buffer ownershipDefine explicit buffer ownership and release rules.

15. Real-World Example – UART Command Processing

Consider an embedded device that receives commands through UART.

Task organization

  1. UART interrupt handler receives a character or byte.
  2. The ISR performs minimal processing and transfers data using an appropriate ISR-safe mechanism.
  3. A communication task assembles and validates the complete command.
  4. The communication task sends a command message to the control task.
  5. The control task executes the requested operation.
       UART Peripheral
              |
              v
         UART ISR
              |
              | Received Data
              v
        Receive Queue
              |
              v
     Communication Task
              |
              | Command Message
              v
        Command Queue
              |
              v
        Control Task
              |
              v
       Execute Command

For example, the command MOTOR_START can be converted into a structured command message and sent to the motor-control task.

Do not perform lengthy command parsing, formatted printing, or blocking operations inside the UART ISR. Use only documented ISR-safe APIs and the appropriate port-specific yield mechanism.

16. Worked Numerical Problem 1 – Message Storage

A queue stores 10 messages. Each message occupies 16 bytes.

Solution

Queue Payload Storage = Queue Length × Message Size
= 10 × 16 = 160 bytes

Answer: The queue requires 160 bytes for message payload storage, excluding queue metadata, alignment, and other RTOS overhead.

17. Worked Numerical Problem 2 – Message Transfer Rate

A task sends 50 messages per second. Each message contains 20 bytes.

Solution

Data Rate = 50 × 20 = 1000 bytes/second

Answer: The application generates 1000 bytes per second of message payload.

18. Worked Numerical Problem 3 – Queue Capacity During Delay

A sender produces 40 messages per second. The receiver may be unable to run for 250 ms.

Solution

Required Capacity = 40 × 0.25 = 10 messages

Answer: At least 10 message slots are required to accommodate the assumed arrivals during the 250 ms delay. Additional capacity may be needed for bursts, timing variation, and existing queued messages.

19. Practical Activity – Command Message System

Develop a conceptual FreeRTOS application with two tasks:

  • Command Sender Task: Generates motor commands.
  • Command Receiver Task: Receives and processes commands.

Suggested message structure

typedef enum
{
    CMD_MOTOR_START,
    CMD_MOTOR_STOP,
    CMD_SET_SPEED
} CommandType;

typedef struct
{
    CommandType command;
    unsigned int value;
} CommandMessage;

Implementation requirements

  1. Create a queue with an appropriate number of command slots.
  2. Define the command structure.
  3. Create the sender and receiver tasks.
  4. Send a motor-start command.
  5. Send a motor-stop command.
  6. Send a speed-setting command with a numerical value.
  7. Validate received command types.
  8. Check all queue operation return values.
  9. Handle queue-full conditions.

Expected behavior

The receiver task should process valid commands in the order defined by the queue operations. Invalid commands should be rejected safely.

21. Lesson Summary

  • Message passing transfers information between independent tasks.
  • A message contains data, commands, events, or status information.
  • FreeRTOS queues are commonly used for message passing.
  • Queue operations normally copy queue items into and out of queue storage.
  • Pointer-based messages require explicit buffer ownership and lifetime management.
  • Blocking and non-blocking behavior depends on the specified timeout.
  • Message ordering is separate from task scheduling priority.
  • Queue capacity must account for message rate, receiver delays, and bursts.
  • Communication failures require explicit handling.
