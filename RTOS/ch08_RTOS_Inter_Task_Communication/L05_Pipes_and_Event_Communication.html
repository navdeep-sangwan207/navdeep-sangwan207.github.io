1. Introduction

Operating systems and real-time operating systems provide different mechanisms for transferring data and notifying tasks about important occurrences.

Two useful concepts are:

  • Pipes: Communication channels through which one software component writes a stream of data and another reads it.
  • Event communication: A mechanism through which tasks are notified that a particular event or condition has occurred.
Example: A communication task writes received bytes into a pipe-like buffer. A processing task reads the data. Separately, an event notification informs a monitoring task that a communication error has occurred.

2. What Is a Pipe?

A pipe is a unidirectional communication channel that transfers a stream of bytes between a writer and a reader.

The writer places data into the pipe, and the reader retrieves data from it. The operating system manages the pipe's internal buffering and synchronization.

Basic pipe architecture

       +----------------+
       |  Writer Task   |
       +----------------+
               |
               | Write Data
               v
       +----------------+
       |      PIPE      |
       |  Byte Buffer   |
       +----------------+
               |
               | Read Data
               v
       +----------------+
       |  Reader Task   |
       +----------------+

Unlike a message queue, a traditional byte-stream pipe does not necessarily preserve application message boundaries. The reader may receive fewer or more bytes than the writer submitted in one operation.

3. Characteristics of Pipes

  • Usually transfer data in one direction.
  • Use an internal buffer.
  • Allow a writer and reader to operate independently.
  • May support blocking and non-blocking operations.
  • Can connect related processes or tasks, depending on the OS.
  • Are suitable for byte-stream communication.

Important characteristics

CharacteristicDescription
DirectionTraditional pipe is unidirectional.
Data formatByte stream.
BufferingUses finite storage.
SynchronizationOperating system coordinates read/write access.
BlockingMay wait when empty or full, depending on configuration.

4. Types of Pipes

4.1 Anonymous Pipes

An anonymous pipe is commonly used for communication between related processes, such as a parent process and a child process in Unix-like systems.

4.2 Named Pipes (FIFOs)

A named pipe, also called a FIFO, has a name in the filesystem namespace and can be used by processes that do not necessarily have a parent-child relationship.

Anonymous pipes and named FIFOs are common Unix/Linux IPC mechanisms. They are not automatically equivalent to a dedicated RTOS kernel pipe service.

6. What Is Event Communication?

Event communication is a mechanism used to notify a task that a particular condition or occurrence has taken place.

An event may indicate:

  • Sensor data is ready.
  • A UART byte or message has arrived.
  • A timer has expired.
  • A motor has reached a limit.
  • A communication error has occurred.
  • A system operation has completed.

Basic event communication architecture

       +----------------+
       | Event Source   |
       +----------------+
               |
               | Event Occurs
               v
       +----------------+
       | Event Object   |
       +----------------+
               |
               | Notify
               v
       +----------------+
       | Waiting Task   |
       +----------------+
               |
               v
       Perform Action

8. Event Flags and Event Bits

An event flag is a Boolean indication that a particular event has occurred. Several event flags can be grouped into an event bit field.

Each bit can represent an independent condition.

Example

#define EVENT_UART_RX       (1U << 0)
#define EVENT_ADC_READY     (1U << 1)
#define EVENT_TIMER_EXPIRED (1U << 2)
#define EVENT_SENSOR_FAULT  (1U << 3)
BitEvent
Bit 0UART data received.
Bit 1ADC conversion completed.
Bit 2Timer expired.
Bit 3Sensor fault detected.

A task can examine the relevant bits and determine which conditions have occurred.

9. Event Groups in FreeRTOS

FreeRTOS provides event groups for synchronizing tasks using a collection of event bits.

Each bit represents an event or condition. Tasks can set, clear, and wait for combinations of bits.

Important FreeRTOS event-group APIs

APIPurpose
xEventGroupCreate()Create an event group.
xEventGroupSetBits()Set event bits from task context.
xEventGroupClearBits()Clear selected event bits.
xEventGroupWaitBits()Wait for one or more event conditions.
xEventGroupGetBits()Read the current event bit value.
xEventGroupSetBitsFromISR()Request event-bit setting from ISR context through the timer service mechanism.

Availability and behavior depend on FreeRTOS configuration. Event-group operations requested from an ISR may require the timer service task and a successful daemon queue submission.

10. Event Group Example

Consider an embedded system that waits for both ADC conversion completion and UART initialization before starting a monitoring operation.

Event definitions

#define EVENT_ADC_READY  (1U << 0)
#define EVENT_UART_READY (1U << 1)

EventGroupHandle_t xSystemEvents;

Creating the event group

xSystemEvents = xEventGroupCreate();

if (xSystemEvents == NULL)
{
    /* Handle allocation failure. */
}

Setting event bits

/* Called from task context after ADC setup. */
xEventGroupSetBits(xSystemEvents, EVENT_ADC_READY);

/* Called from task context after UART setup. */
xEventGroupSetBits(xSystemEvents, EVENT_UART_READY);

Waiting for both events

EventBits_t receivedEvents;

receivedEvents = xEventGroupWaitBits(
    xSystemEvents,
    EVENT_ADC_READY | EVENT_UART_READY,
    pdFALSE,
    pdTRUE,
    portMAX_DELAY
);

if ((receivedEvents &
     (EVENT_ADC_READY | EVENT_UART_READY)) ==
     (EVENT_ADC_READY | EVENT_UART_READY))
{
    /* Both initialization events have occurred. */
}

Explanation:

  • xEventGroupCreate() creates the event group.
  • xEventGroupSetBits() sets the specified bits.
  • xEventGroupWaitBits() waits for the selected conditions.
  • pdTRUE for the wait-for-all parameter means all requested bits must be set.
  • pdFALSE for the clear-on-exit parameter leaves the bits set after the wait completes.

11. Wait for Any Event vs Wait for All Events

Wait for Any

A task continues when at least one selected event bit becomes set.

xEventGroupWaitBits(
    xSystemEvents,
    EVENT_ADC_READY | EVENT_UART_READY,
    pdFALSE,
    pdFALSE,
    portMAX_DELAY
);

Wait for All

A task continues only after all selected event bits become set.

xEventGroupWaitBits(
    xSystemEvents,
    EVENT_ADC_READY | EVENT_UART_READY,
    pdFALSE,
    pdTRUE,
    portMAX_DELAY
);
ParameterMeaning
xClearOnExitWhether the selected bits are cleared when the wait condition is satisfied.
xWaitForAllBitspdTRUE waits for all selected bits; pdFALSE waits for any selected bit.
xTicksToWaitMaximum wait time in ticks.

12. Event Communication Using Task Notifications

FreeRTOS task notifications provide a lightweight mechanism for signaling a particular task.

They can be used to:

  • Notify a task that data is available.
  • Set or clear notification bits.
  • Increment a notification value.
  • Transfer a 32-bit value using suitable notification actions.

Example

TaskHandle_t xProcessingTaskHandle;

void ProcessingTask(void *pvParameters)
{
    uint32_t notificationValue;

    for (;;)
    {
        if (xTaskNotifyWait(
                0,
                0xFFFFFFFFUL,
                ¬ificationValue,
                portMAX_DELAY) == pdTRUE)
        {
            /* Process notificationValue. */
        }
    }
}

A sender task can notify the processing task:

xTaskNotify(
    xProcessingTaskHandle,
    1U,
    eSetBits
);

Task notifications are associated with a particular task and can be more lightweight than a separate queue or event group for simple one-task notification patterns.

15. Important Design Considerations

15.1 Buffer Capacity

Pipe capacity must be sufficient for the expected data arrival rate and reader delays.

15.2 Event Coalescing

Event flags represent conditions, not necessarily individual occurrences. If the same bit is set repeatedly before being cleared, the application may not know how many times the event occurred.

15.3 Data vs Notification

If every data item must be preserved, use a queue or buffer. An event can notify a task that data is available, but the event bit alone may not contain the data.

15.4 ISR Restrictions

Interrupt handlers must remain short and use only appropriate interrupt-safe communication APIs.

15.5 Timeouts

Choose timeouts based on system timing requirements. An indefinite wait is not appropriate for every real-time task.

16. Real-World Example – ADC Data Ready Event

Consider an embedded system that uses an ADC to measure an analog sensor.

Operation sequence

  1. The ADC conversion starts.
  2. The ADC peripheral completes the conversion.
  3. An interrupt indicates conversion completion.
  4. The ISR reads or records the conversion result as appropriate.
  5. The ISR notifies the processing task using a supported ISR-safe mechanism.
  6. The processing task calculates the sensor value.
  7. The display or communication task receives the processed result.
        ADC Peripheral
              |
              | Conversion Complete
              v
           ADC ISR
              |
              | Notify
              v
       Processing Task
              |
              | Process Result
              v
        Display Task
An event notification does not automatically transfer an ADC sample. The design must also provide a safe way to transfer the actual result, such as a queue, notification value, or protected buffer.

17. Worked Numerical Problem 1 – Pipe Buffer

A pipe has a capacity of 1024 bytes. A writer sends data at 256 bytes per second. Assume the reader does not consume any data.

Time to Fill = Buffer Capacity / Data Rate
= 1024 / 256 = 4 seconds

Answer: The pipe buffer fills in approximately 4 seconds if no data is read.

18. Worked Numerical Problem 2 – Event Bits

A system uses four event bits to represent four independent conditions.

Number of Bit Combinations = 2⁴ = 16

Answer: Four bits can represent 16 possible bit patterns, including the pattern in which no events are set. This is not the same as having 16 independent event types that are all individually represented by one bit.

19. Worked Numerical Problem 3 – Event Response

A task waits for a timer event. The event occurs at 100 ms, and the task begins processing at 103 ms.

Event-to-Task Start Delay = 103 − 100
= 3 ms

Answer: The observed event-to-task start delay is 3 ms. This measurement is not automatically a guaranteed worst-case response time.

20. Practical Activity – Event-Based Monitoring

Design a conceptual FreeRTOS application with three event sources:

  • ADC conversion completed.
  • UART data received.
  • Timer interval expired.

Requirements

  1. Create an event group.
  2. Define one bit for each event source.
  3. Set the corresponding bit when each event occurs.
  4. Create a monitoring task that waits for any selected event.
  5. Read the returned event bits.
  6. Process the required condition.
  7. Clear event bits according to the application's design.
  8. Handle event notification failures where applicable.

Testing checklist

  • Verify each event bit independently.
  • Test waiting for any event.
  • Test waiting for all events.
  • Test event timeout behavior.
  • Check whether repeated events can coalesce.
  • Verify that actual data is transferred separately when required.

22. Lesson Summary

  • Pipes transfer byte streams between software components or processes.
  • Anonymous pipes and named FIFOs are common Linux IPC mechanisms.
  • Event communication notifies tasks about important conditions.
  • Event flags and event groups can represent multiple conditions.
  • FreeRTOS event groups support wait-for-any and wait-for-all behavior.
  • Task notifications provide lightweight task-specific signaling.
  • Events do not necessarily preserve every occurrence or transfer the associated data.
  • Queues and buffers should be used when individual data items must be preserved.
  • ISR communication must follow the selected RTOS port's rules.
