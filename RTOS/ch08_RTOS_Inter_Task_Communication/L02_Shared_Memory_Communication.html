1. Introduction

Shared memory communication is a method in which two or more tasks access a common memory location or data structure to exchange information.

One task can write data into a shared variable, while another task reads the updated value. This approach is commonly used in embedded applications where multiple tasks need access to sensor readings, system status, counters, or application data.

Example: A sensor task updates a shared temperature variable. A display task reads that variable and displays the latest temperature.

2. Basic Shared Memory Architecture

       +----------------+
       |  Sensor Task   |
       +----------------+
               |
               | Write Data
               v
       +----------------+
       | Shared Memory  |
       | Temperature    |
       +----------------+
               |
               | Read Data
               v
       +----------------+
       |  Display Task  |
       +----------------+
               |
               v
       Update Display

The shared memory region acts as a common communication area between the tasks.

3. How Shared Memory Communication Works

  1. A shared variable or data structure is declared in memory.
  2. The producer task writes information into the shared location.
  3. The consumer task accesses the same location.
  4. The consumer processes the received information.
  5. Synchronization is applied when concurrent access could cause inconsistent results.

Example

int sensorValue = 0;

/* Producer Task */
void SensorTask(void *pvParameters)
{
    for (;;)
    {
        sensorValue = Read_Sensor();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

/* Consumer Task */
void ProcessingTask(void *pvParameters)
{
    int localValue;

    for (;;)
    {
        localValue = sensorValue;

        Process_Sensor_Value(localValue);

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

This is a conceptual example. The shared variable must be protected if its access can overlap or if the data requires a consistent multi-field snapshot.

4. Types of Shared Memory

4.1 Shared Global Variables

A global variable can be accessed by multiple tasks within the same application.

int systemStatus = 0;

4.2 Shared Structures

A structure can store related information such as temperature, voltage, current, and system status.

typedef struct
{
    float temperature;
    float voltage;
    float current;
    unsigned int status;
} SystemData;

SystemData sharedData;

4.3 Shared Arrays and Buffers

An array or buffer can store multiple sensor samples or communication data.

unsigned char receiveBuffer[128];

When multiple tasks access the same buffer, ownership and synchronization must be clearly defined.

6. Advantages of Shared Memory

  • Simple data exchange between tasks.
  • Efficient access to common data.
  • Suitable for frequently updated values.
  • Can avoid repeated copying of large data structures.
  • Useful for sharing system status and measurements.
  • Can support modular application architecture.

7. Limitations of Shared Memory

  • Race conditions may occur.
  • Tasks may read partially updated data.
  • Synchronization adds implementation complexity.
  • Incorrect locking can cause deadlocks.
  • Shared buffers require clear ownership rules.
  • Debugging timing-related errors can be difficult.
Shared memory is not automatically safe merely because all tasks belong to the same application. Concurrent access must be analyzed and synchronized where necessary.

8. Race Conditions in Shared Memory

A race condition occurs when the result of an operation depends on the timing or interleaving of multiple accesses to shared data.

Example: Shared counter

Suppose two tasks increment the same counter.

sharedCounter = sharedCounter + 1;

This operation generally involves multiple steps:

  1. Read the current counter value.
  2. Add one to the value.
  3. Write the updated value.

If two tasks interleave these steps, one increment may be lost.

Example interleaving

StepTask ATask BCounter
1Read 5—5
2—Read 55
3Calculate 6Calculate 65
4Write 6—6
5—Write 66

Expected counter value after two increments is 7, but the actual value is 6.

9. Critical Sections for Shared Memory Protection

A critical section is a section of code that accesses shared data and must be protected against unsafe concurrent access.

In FreeRTOS, task-context critical sections can be implemented using the appropriate port-specific critical-section macros.

Conceptual FreeRTOS example

volatile unsigned int sharedCounter = 0;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        taskENTER_CRITICAL();

        sharedCounter++;

        taskEXIT_CRITICAL();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    unsigned int localCounter;

    for (;;)
    {
        taskENTER_CRITICAL();

        localCounter = sharedCounter;

        taskEXIT_CRITICAL();

        Process_Counter(localCounter);

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

The critical section protects the counter update and read from conflicting task-level access, subject to the guarantees of the selected FreeRTOS port.

Keep critical sections short. Their interrupt-masking behavior is port-dependent. Do not assume that these macros disable every interrupt source on every processor.

10. Mutex-Based Shared Memory Protection

A mutex can protect a shared data structure when multiple tasks need mutually exclusive access.

Example

SemaphoreHandle_t xDataMutex;

typedef struct
{
    int temperature;
    int voltage;
} SensorData;

SensorData sharedData;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        SensorData newData;

        newData.temperature = Read_Temperature();
        newData.voltage = Read_Voltage();

        if (xSemaphoreTake(xDataMutex,
                           portMAX_DELAY) == pdTRUE)
        {
            sharedData = newData;

            xSemaphoreGive(xDataMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void DisplayTask(void *pvParameters)
{
    SensorData localData;

    for (;;)
    {
        if (xSemaphoreTake(xDataMutex,
                           portMAX_DELAY) == pdTRUE)
        {
            localData = sharedData;

            xSemaphoreGive(xDataMutex);
        }

        Display_Data(&localData);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

Create the mutex before starting the scheduler:

xDataMutex = xSemaphoreCreateMutex();

if (xDataMutex == NULL)
{
    /* Handle allocation failure. */
}

The local copy allows display processing to occur after the mutex has been released, reducing the time the shared resource remains locked.

11. Atomic Operations

An atomic operation is performed as an indivisible operation with respect to the relevant observers and execution model.

For example, an architecture-supported atomic increment can prevent lost updates to a shared counter.

Important considerations

  • Atomic support depends on the compiler and target architecture.
  • Not every data type has a lock-free atomic operation.
  • Atomicity does not automatically protect a complete multi-field structure.
  • Memory ordering may matter when publishing data between tasks.
  • Use compiler and processor documentation to verify guarantees.
For small shared counters, suitable atomic operations can be useful. For larger structures, a mutex, critical section, or carefully designed buffer-ownership mechanism may be more appropriate.

12. The Role of volatile

The volatile keyword tells the compiler that accesses to an object have observable side effects and should not be optimized as though the object cannot change unexpectedly.

Example

volatile unsigned int interruptFlag = 0;

void Timer_IRQHandler(void)
{
    interruptFlag = 1;
}

A task may inspect the flag, but additional synchronization may still be required.

13. Double Buffering

Double buffering uses two memory buffers so that one buffer can be filled while another is being processed.

Working principle

  1. Producer writes new data into Buffer A.
  2. Consumer processes Buffer B.
  3. After a controlled handover, their roles are exchanged.
  4. The producer and consumer continue using separate buffers.
       Producer Task
             |
             v
        +----------+
        | Buffer A |
        +----------+
             |
             | Buffer Handover
             v
        +----------+
        | Buffer B |
        +----------+
             |
             v
       Consumer Task

In a real implementation, the buffer handover itself must be synchronized. Simply swapping two pointers without a defined ownership protocol can introduce race conditions.

15. Practical Example – Shared Sensor Data

Consider an embedded monitoring system that uses two tasks:

  • Sensor Task updates temperature and voltage readings.
  • Monitoring Task reads the values and checks operating limits.

Data structure

typedef struct
{
    float temperature;
    float voltage;
    unsigned int sampleNumber;
} MonitoringData;

MonitoringData sharedMonitoringData;

Design requirements

  1. Read the sensors outside the critical section.
  2. Prepare a complete local data snapshot.
  3. Acquire the synchronization object.
  4. Copy the new snapshot into shared memory.
  5. Release the synchronization object.
  6. Allow the monitoring task to obtain a consistent copy.
  7. Perform calculations after releasing the mutex.

This approach minimizes the time spent holding the shared resource while ensuring that related measurements are read as a consistent group.

16. Worked Numerical Problem 1 – Shared Counter

Two tasks each increment a shared counter 100 times.

Solution

Expected Final Count = 100 + 100 = 200

If increments are protected by suitable synchronization and no increments are lost, the final count is 200.

Without synchronization, race conditions can cause the actual result to be less than 200.

17. Worked Numerical Problem 2 – Buffer Memory

A shared buffer contains 256 samples. Each sample occupies 2 bytes.

Solution

Buffer Size = 256 × 2 = 512 bytes

Answer: The buffer requires 512 bytes of data storage, excluding any additional metadata or alignment overhead.

18. Worked Numerical Problem 3 – Data Update Rate

A sensor task updates a shared data structure every 20 ms.

Solution

Update Frequency = 1 / Period
= 1 / 0.020 = 50 Hz

Answer: The shared data is updated 50 times per second.

19. Practical Activity – Shared Memory with Two Tasks

Develop a conceptual FreeRTOS application in which one task updates a shared counter and another task reads it.

Requirements

  1. Declare a shared counter.
  2. Create a mutex before starting the scheduler.
  3. Create a producer task.
  4. Create a consumer task.
  5. Protect counter updates and reads with the mutex.
  6. Copy the shared value into a local variable.
  7. Perform longer processing outside the critical section.
  8. Observe the counter values during debugging.

Testing checklist

  • Check whether both tasks execute.
  • Verify that the counter increments correctly.
  • Check mutex creation failure handling.
  • Ensure every successful mutex acquisition is followed by release.
  • Check for deadlocks and excessive blocking.
  • Verify that the shared data remains consistent.
This is a FreeRTOS programming exercise. It requires a compatible target port or suitable host-side test environment. The LPC2129 Keil simulator setup alone does not establish FreeRTOS port compatibility.

21. Lesson Summary

  • Shared memory allows multiple tasks to access common data.
  • Global variables, structures, arrays, and buffers can be shared.
  • Unsynchronized access can produce race conditions and inconsistent data.
  • Critical sections and mutexes can protect shared resources.
  • Atomic operations are useful for suitable individual data operations.
  • Volatile does not provide mutual exclusion or atomicity.
  • Double buffering can separate producer and consumer activities.
  • Shared memory designs require clear data ownership and synchronization rules.
