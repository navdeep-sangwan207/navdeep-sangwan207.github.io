Producer-Consumer Problem

1. Introduction

The Producer-Consumer Problem is a fundamental synchronization problem in operating systems and real-time systems. It describes how one or more producer tasks generate data and one or more consumer tasks process that data through a shared communication resource.

The producer places data into a buffer, while the consumer retrieves data from that buffer.

Embedded example: A sensor acquisition task produces temperature samples, and a processing task consumes those samples to calculate temperature limits and system status.

2. Basic Architecture

       +-------------------+
       |   Producer Task   |
       |                   |
       | Generates Data    |
       +-------------------+
                 |
                 | Insert Item
                 v
       +-------------------+
       |    Shared Buffer  |
       |                   |
       |  [D1] [D2] [D3]   |
       +-------------------+
                 |
                 | Remove Item
                 v
       +-------------------+
       |   Consumer Task   |
       |                   |
       | Processes Data    |
       +-------------------+

The buffer temporarily stores generated items until the consumer is ready to process them.

3. Producer Task

A producer task generates or collects data and places it into a communication buffer.

Examples

  • ADC task collecting analog measurements.
  • UART task receiving communication data.
  • Timer task generating periodic events.
  • Sensor task collecting temperature and pressure readings.
  • Data acquisition task recording measurement samples.

Typical producer operations

  1. Acquire or generate data.
  2. Prepare the data item.
  3. Check buffer availability.
  4. Insert the item into the buffer.
  5. Handle a full-buffer condition.

4. Consumer Task

A consumer task retrieves data from the buffer and performs the required operation.

Examples

  • Processing sensor readings.
  • Displaying measured values.
  • Transmitting collected data through UART.
  • Logging data to storage.
  • Checking alarm conditions.

Typical consumer operations

  1. Wait for data availability.
  2. Retrieve an item from the buffer.
  3. Validate the received data.
  4. Perform processing.
  5. Forward or store the result if required.

5. Buffer in the Producer-Consumer Problem

A buffer is temporary memory used to store data between the producer and consumer.

Common buffer types include:

Buffer TypeDescription
Single-item bufferStores one pending data item.
Linear bufferStores items sequentially in memory.
Circular bufferReuses storage positions after reaching the end.
Message queueStores separate message items.
Double bufferUses two memory regions to separate production and consumption phases.

6. Main Problems in Producer-Consumer Synchronization

6.1 Buffer Overflow

Buffer overflow occurs when the producer attempts to insert data into a full buffer.

6.2 Buffer Underflow

Buffer underflow occurs when the consumer attempts to retrieve data from an empty buffer.

6.3 Race Condition

A race condition occurs when producer and consumer operations interfere with each other because shared data is accessed without adequate synchronization.

6.4 Data Loss

Data loss occurs when new data overwrites unread data or when the application cannot keep up with the production rate.

6.5 Priority Inversion

Priority inversion may occur when a high-priority task waits for a resource held by a lower-priority task, while intermediate-priority tasks delay the lower-priority task's progress.

7. Bounded Buffer Problem

A bounded buffer has a fixed capacity. The producer must wait or handle an error when the buffer is full, and the consumer must wait when the buffer is empty.

       +-----------------------+
       |    Bounded Buffer     |
       |                       |
       | Capacity = 5 Items    |
       |                       |
       | [A] [B] [C] [ ] [ ]   |
       |                       |
       | Used = 3 Items        |
       +-----------------------+

The application must define what happens when either condition occurs.

8. Classical Semaphore-Based Solution

The traditional bounded-buffer solution uses three synchronization variables:

VariablePurpose
MutexProtects access to shared buffer metadata and storage.
EmptyCounts available buffer slots.
FullCounts occupied buffer slots.

For a buffer capacity of N:

Empty = N
Full = 0
Empty + Full = N

Producer pseudocode

wait(Empty);
wait(Mutex);

Insert_Item();

signal(Mutex);
signal(Full);

Consumer pseudocode

wait(Full);
wait(Mutex);

Remove_Item();

signal(Mutex);
signal(Empty);
This is the classical conceptual solution. The exact implementation must use semaphore APIs with appropriate counting, ownership, and priority behavior. A mutex and counting semaphores serve different purposes.

9. Producer-Consumer Problem Using FreeRTOS Queue

FreeRTOS queues provide a convenient mechanism for transferring data between producer and consumer tasks. Queue operations manage the internal synchronization and data copying.

Example: Temperature monitoring

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

typedef struct
{
    int temperature;
    unsigned int sampleNumber;
} SensorData;

QueueHandle_t xSensorQueue;

void ProducerTask(void *pvParameters)
{
    SensorData data;
    unsigned int count = 0;

    for (;;)
    {
        data.temperature = Read_Temperature();
        data.sampleNumber = count++;

        if (xQueueSend(
                xSensorQueue,
                &data,
                pdMS_TO_TICKS(100)) != pdPASS)
        {
            /* Queue full: handle the lost or delayed sample. */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ConsumerTask(void *pvParameters)
{
    SensorData receivedData;

    for (;;)
    {
        if (xQueueReceive(
                xSensorQueue,
                &receivedData,
                portMAX_DELAY) == pdPASS)
        {
            Process_Temperature(
                receivedData.temperature,
                receivedData.sampleNumber
            );
        }
    }
}

int main(void)
{
    xSensorQueue = xQueueCreate(10, sizeof(SensorData));

    if (xSensorQueue == NULL)
    {
        for (;;)
        {
            /* Queue creation failed. */
        }
    }

    xTaskCreate(
        ProducerTask,
        "Producer",
        256,
        NULL,
        2,
        NULL
    );

    xTaskCreate(
        ConsumerTask,
        "Consumer",
        256,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program explanation

  1. A queue with ten items is created.
  2. Each item stores a temperature and sample number.
  3. The producer generates a sample every 500 ms.
  4. The producer copies the sample into the queue.
  5. The consumer blocks while waiting for a queue item.
  6. When data becomes available, the consumer retrieves and processes it.
  7. The application checks whether queue creation and sending succeeded.
Read_Temperature() and Process_Temperature() are application-specific functions and must be implemented. Stack depth values and task priorities must be selected for the actual target and FreeRTOS port. This example is illustrative; it does not establish a verified FreeRTOS port for the LPC2129/Keil simulator.

10. Producer and Consumer with Different Priorities

Task priorities influence which task executes when both tasks are Ready.

Example

TaskPriorityOperation
Producer2Collects sensor data.
Consumer3Processes sensor data.

In a typical FreeRTOS fixed-priority preemptive configuration, the higher-priority consumer runs when it becomes Ready. If the consumer blocks waiting for data, the producer can run.

Equal-priority tasks may share CPU time when time slicing is enabled and both remain Ready.

A higher consumer priority does not guarantee that every sample will be processed on time. Execution time, queue capacity, interrupt load, blocking, and arrival rate must also be considered.

11. Circular Buffer Implementation

A circular buffer reuses a fixed-size array by wrapping its read and write positions back to the beginning when they reach the end.

Concept

Index:    0    1    2    3    4
        +----+----+----+----+----+
Buffer: | A  | B  | C  |    |    |
        +----+----+----+----+----+
          ^              ^
         Read           Write

Example: Single-producer, single-consumer ring buffer

#include 
#include 

#define BUFFER_SIZE 8U

typedef struct
{
    uint16_t data[BUFFER_SIZE];
    volatile unsigned int head;
    volatile unsigned int tail;
} RingBuffer;

void RingBuffer_Init(RingBuffer *rb)
{
    rb->head = 0U;
    rb->tail = 0U;
}

bool RingBuffer_Push(RingBuffer *rb, uint16_t value)
{
    unsigned int next =
        (rb->head + 1U) % BUFFER_SIZE;

    if (next == rb->tail)
    {
        return false;  /* Buffer full */
    }

    rb->data[rb->head] = value;
    rb->head = next;

    return true;
}

bool RingBuffer_Pop(RingBuffer *rb, uint16_t *value)
{
    if (rb->head == rb->tail)
    {
        return false;  /* Buffer empty */
    }

    *value = rb->data[rb->tail];

    rb->tail =
        (rb->tail + 1U) % BUFFER_SIZE;

    return true;
}

Important implementation details

  • This design reserves one array position to distinguish full from empty.
  • An array of eight elements therefore holds at most seven items.
  • It assumes exactly one producer modifies head and exactly one consumer modifies tail.
  • It assumes index accesses and the required memory ordering are safe for the target architecture and compiler.
  • volatile does not make the algorithm universally thread-safe or provide a general memory barrier.
  • For multiple producers or consumers, additional synchronization is required.
For an ISR/task implementation, verify atomic access, compiler ordering, interrupt nesting, and memory barriers for the actual MCU/compiler. Do not assume this portable-looking C example is automatically safe for every interrupt and task combination.

12. Data Production and Consumption Rates

The producer and consumer rates determine whether the buffer can keep up with the application.

Producer Rate = Items Generated / Second
Consumer Rate = Items Processed / Second
ConditionResult
Producer rate = Consumer rateAverage rates are balanced.
Producer rate greater than Consumer rateBuffer occupancy tends to increase.
Producer rate less than Consumer rateConsumer may frequently wait for data.

Equal average rates do not eliminate the need for buffer capacity because temporary bursts and scheduling delays can still occur.

13. Worked Numerical Problem 1 – Buffer Filling Time

A producer generates 20 samples per second. The consumer is temporarily unable to process data. The buffer capacity is 50 samples and starts empty.

Time to Fill = Buffer Capacity / Production Rate
= 50 / 20 = 2.5 seconds

Answer: The buffer fills in 2.5 seconds if the producer continues at a constant rate and no samples are consumed.

14. Worked Numerical Problem 2 – Consumer Throughput

A consumer processes one sample in 25 ms.

Processing Rate = 1000 / Processing Time (ms)
= 1000 / 25 = 40 samples/second

Answer: The theoretical processing capacity is 40 samples per second, assuming no additional blocking or overhead.

15. Worked Numerical Problem 3 – Queue Capacity

A producer generates 60 messages per second. The consumer may be delayed for 150 ms.

Minimum Capacity = 60 × 0.15
= 9 messages

Answer: At least nine message slots are required for this assumed delay. Additional capacity should be considered for bursts, existing queue occupancy, and timing uncertainty.

16. Multiple Producers and Multiple Consumers

Some applications use more than one producer or consumer.

Multiple producers

Several tasks generate data and send it to a common queue. A queue implementation can coordinate access to its internal storage.

Multiple consumers

Several tasks receive items from a common queue. Each successfully received item is removed and delivered to one receiving task.

Producer A -----+
                |
Producer B -----+----> Shared Queue ----+----> Consumer A
                |                      |
Producer C -----+                      +----> Consumer B

The application must still define message ordering, task priorities, processing ownership, and what happens if consumers have different processing capabilities.

17. Design Best Practices

  • Choose a buffer size based on arrival rates, burst size, and maximum consumer delay.
  • Check the return value of every queue send operation.
  • Define whether old data or new data should be discarded when capacity is exhausted.
  • Keep producer operations short and predictable.
  • Avoid unnecessary copying of large data structures.
  • Define clear ownership when transferring pointers.
  • Use suitable synchronization for shared buffers.
  • Measure consumer processing time and queue occupancy.
  • Consider backpressure when the consumer cannot keep up.
  • Do not use blocking operations inside an ISR.

18. Practical Activity – Sensor Producer and Consumer

Develop a conceptual RTOS application that transfers ADC samples from a producer task to a consumer task.

Requirements

  1. Create a queue with a capacity of ten samples.
  2. Create a producer task that generates one sample every 100 ms.
  3. Create a consumer task that receives samples.
  4. Calculate the average of five consecutive samples.
  5. Detect queue-send failures.
  6. Record the number of processed samples.
  7. Test the application with different consumer delays.
  8. Observe queue occupancy and identify overflow conditions.

Expected observations

  • The consumer waits when the queue is empty.
  • The producer waits or handles failure when the queue is full, depending on the selected API and timeout.
  • A slower consumer causes queue occupancy to increase.
  • A sufficiently fast consumer keeps the queue occupancy low under the tested workload.

20. Lesson Summary

  • The producer generates data and the consumer processes it.
  • A buffer stores data temporarily between the two tasks.
  • Bounded buffers require handling full and empty conditions.
  • FreeRTOS queues provide a convenient synchronized data-transfer mechanism.
  • Circular buffers efficiently reuse fixed memory storage.
  • Producer and consumer rates determine buffer occupancy.
  • Multiple producers and consumers require a clearly defined communication design.
  • Buffer capacity, data ownership, synchronization, and overflow handling are essential to reliable RTOS applications.
