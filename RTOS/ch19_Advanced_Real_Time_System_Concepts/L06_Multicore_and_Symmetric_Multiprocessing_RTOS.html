2. Introduction to Multicore Systems

A multicore processor contains two or more processing cores within a single processor device or package. Each core can execute instructions independently.

Multicore systems are used to improve processing capacity, support parallel workloads and separate application functions.

Single-Core Architecture

+----------------------+ | PROCESSOR | | | | +---------+ | | | CORE 0 | | | +---------+ | +----------------------+ | MAIN MEMORY

Multicore Architecture

+-----------------------------+ | MULTICORE CPU | | | | +---------+ +---------+ | | | CORE 0 | | CORE 1 | | | +---------+ +---------+ | | | | +---------+ +---------+ | | | CORE 2 | | CORE 3 | | | +---------+ +---------+ | +-----------------------------+ | SHARED MEMORY

Actual processor designs may include private caches, shared caches, memory controllers and interconnects.

3. Single-Core vs Multicore Processing

FeatureSingle-CoreMulticore
Processing coresOneTwo or more
Parallel executionNo simultaneous execution on separate CPU coresPossible across multiple cores
Task executionTasks share one CPU through schedulingTasks may execute on different cores
SynchronizationRequired for shared data and concurrencyRequired, including cross-core synchronization
SchedulingOne processor scheduling contextMay involve per-core or global scheduling
Design complexityGenerally lowerGenerally higher
Multicore does not automatically mean faster execution. The application must contain parallelizable work, and synchronization and communication overhead must be considered.

4. Multiprocessing and Parallel Execution

Multiprocessing uses multiple processing units to execute work. In a multicore processor, separate cores can execute different tasks at the same time.

Concurrency

Concurrency means multiple tasks make progress during overlapping time intervals. On a single-core processor, this is commonly achieved through task switching.

Parallelism

Parallelism means two or more operations execute simultaneously on separate processing resources.

SINGLE CORE – CONCURRENT EXECUTION Time ----------------------------> Core 0: | Task A | Task B | Task A | Task C | MULTICORE – PARALLEL EXECUTION Time ----------------------------> Core 0: | Task A | Task A | Core 1: | Task B | Task C |

Concurrency can exist without parallelism. Parallelism requires multiple execution resources.

5. Types of Multiprocessing Architectures

5.1 Asymmetric Multiprocessing (AMP)

In Asymmetric Multiprocessing, processor cores or processing units have different responsibilities. One processor may act as the master and coordinate other processors.

MASTER CORE | +--------+--------+ | | CORE 1 CORE 2 Application Application Task A Task B

Possible characteristics:

  • One core may control system initialization.
  • Different cores may run separate software images or operating environments.
  • Inter-processor communication is used to exchange information.
  • Responsibilities can be statically assigned.

5.2 Symmetric Multiprocessing (SMP)

In Symmetric Multiprocessing, multiple processor cores operate as peers under a coordinated operating-system or RTOS kernel. Tasks can be scheduled across the available cores according to the implementation.

SHARED RTOS KERNEL | GLOBAL TASK SYSTEM | +---------+---------+ | | CORE 0 CORE 1 | | TASK A TASK B | | +---------+---------+ | SHARED MEMORY

Possible characteristics:

  • Multiple cores can execute tasks concurrently.
  • Scheduling may distribute Ready tasks across cores.
  • Shared kernel data requires synchronization.
  • Task migration may be supported.

6. AMP vs SMP

FeatureAMPSMP
Core organizationDifferent or assigned responsibilitiesPeer processing cores
Operating environmentMay run separate software imagesCommon coordinated OS/kernel environment
Task allocationOften statically assignedScheduled across cores by kernel policy
Task migrationUsually limited or application-managedMay be supported
CommunicationOften explicit inter-processor communicationShared kernel and memory structures may be used
Typical usePartitioned control and processing functionsGeneral parallel task execution

These are broad architectural models. Real systems may combine features of AMP and SMP.

7. Multicore RTOS Architecture

A multicore RTOS provides scheduling and synchronization mechanisms for applications executing across multiple cores.

Typical Components

  • Task management.
  • Per-core scheduling or coordinated scheduling.
  • Interrupt management.
  • Inter-core communication.
  • Shared memory management.
  • Synchronization primitives.
  • Timer and clock services.
  • Memory protection, where supported.
MULTICORE RTOS | +------------+------------+ | | CORE 0 CORE 1 | | +----+----+ +----+----+ | Task A | | Task C | | Task B | | Task D | +---------+ +---------+ | | +-----------+-------------+ | SHARED RESOURCES | QUEUES / LOCKS / MEMORY

The exact architecture depends on the RTOS, processor and SMP port.

8. Multicore Task Scheduling

In a multicore system, the RTOS must decide which task should execute on which core.

Global Scheduling

A global scheduler considers tasks from a shared Ready-task set and assigns eligible tasks to available cores.

Partitioned Scheduling

Partitioned scheduling assigns tasks to specific cores. Each core schedules its assigned tasks independently or according to a coordinated policy.

Clustered Scheduling

Clustered scheduling groups cores into clusters and schedules tasks within each cluster.

ApproachBasic IdeaConsideration
GlobalTasks can be scheduled across a common set of cores.Migration and shared scheduling overhead.
PartitionedTasks are assigned to particular cores.Load balancing and partition assignment.
ClusteredScheduling occurs within groups of cores.Cluster boundaries and migration restrictions.

9. Task Affinity

Task affinity specifies which processor cores are permitted or preferred for a task.

Core Affinity Example

Task A -> Core 0 only
Task B -> Core 1 only
Task C -> Core 0 or Core 1

Advantages

  • Can reduce unnecessary task migration.
  • May improve cache locality.
  • Supports hardware-specific task assignment.
  • Can simplify analysis for partitioned workloads.

Disadvantages

  • May create uneven core utilization.
  • Can leave one core overloaded while another is idle.
  • Restricts scheduling flexibility.
Task affinity is an implementation-specific capability. A generic FreeRTOS application should not assume that affinity APIs exist in every FreeRTOS version or port.

10. Shared Memory in Multicore Systems

Multiple cores may access the same memory region. Shared memory provides an efficient way to exchange data, but concurrent access must be coordinated.

SHARED MEMORY | +--------+--------+ | | CORE 0 CORE 1 | | WRITE DATA READ DATA | | +--------+--------+ | SYNCHRONIZATION NEEDED

Common Problems

  • Race conditions.
  • Lost updates.
  • Inconsistent data structures.
  • Incorrect visibility of memory updates.
  • Cache coherency problems.

Example: Lost Update

Shared counter = 10

Core 0 reads counter = 10
Core 1 reads counter = 10

Core 0 calculates 10 + 1 = 11
Core 1 calculates 10 + 1 = 11

Core 0 writes 11
Core 1 writes 11

Final counter = 11

Expected counter = 12

Both cores performed an increment, but one update was lost because the operation was not atomic.

11. Race Conditions and Atomic Operations

A race condition occurs when the result of concurrent operations depends on their timing or interleaving.

An atomic operation completes as one indivisible operation from the perspective of other concurrent accesses.

Common Synchronization Methods

  • Mutexes.
  • Spinlocks.
  • Semaphores.
  • Atomic read-modify-write operations.
  • Critical sections.
  • Message passing.

Atomic Increment – Conceptual Example

atomic_increment(&sharedCounter);

This represents an atomic increment operation. Actual syntax depends on the language standard, compiler and target architecture.

Declaring a shared variable as volatile does not make read-modify-write operations atomic and does not provide general cross-core synchronization.

12. Cache Coherency

Modern multicore processors may contain private caches for each core. If multiple cores access the same memory location, their cached copies must remain consistent according to the processor's memory system rules.

MAIN MEMORY | +------+------+ | | CACHE 0 CACHE 1 | | CORE 0 CORE 1

Cache Coherency Problem

Suppose Core 0 updates a shared variable in its cache. Core 1 may hold an older cached copy if the hardware does not maintain coherency for that memory region.

Common Solutions

  • Hardware cache-coherency protocols.
  • Cache maintenance operations where required.
  • Correct memory attributes and shareability settings.
  • Memory barriers and synchronization primitives.
  • Non-cacheable shared-memory regions where appropriate.
A cache-coherent system still requires synchronization. Cache coherency does not make multi-step application operations atomic or eliminate data races.

13. Memory Barriers and Ordering

Processors and compilers may reorder memory operations when permitted by their execution and language models.

A memory barrier or fence constrains ordering and visibility according to the relevant architecture and programming model.

Conceptual Example

sharedData = 100;

/* Appropriate release ordering
   may be required here. */

readyFlag = 1;

A receiving core must use an appropriate acquire operation or synchronization mechanism before assuming that the data written before the flag is visible.

In C and C++, use the language's atomic and synchronization facilities where applicable. Platform-specific device memory and DMA operations may require additional architecture-specific barriers.

A memory barrier is not a substitute for a mutex or atomic protocol. It does not automatically make a data race safe.

14. Inter-Core Communication

Multicore processors require communication mechanisms for exchanging data and coordinating operations between cores.

Common Methods

  • Shared memory.
  • Inter-processor interrupts (IPI).
  • Message queues.
  • Mailbox hardware.
  • Hardware semaphores.
  • Dedicated interconnects.

Shared-Memory Communication

One core writes data to a shared buffer, and another core reads it after suitable synchronization.

Inter-Processor Interrupt

An IPI allows one processor core to notify another core that an event or request needs attention.

Mailbox Communication

A hardware or software mailbox provides a structured mechanism for exchanging messages between processing units.

CORE 0 | WRITE MESSAGE | SHARED BUFFER | SEND IPI / SIGNAL | CORE 1 | READ MESSAGE | PROCESS REQUEST

15. Load Balancing

Load balancing distributes work across available processor cores to avoid unnecessary overload on one core.

Example

CoreInitial Workload
Core 080%
Core 120%

A scheduling policy may move eligible work from Core 0 to Core 1 to improve overall balance.

Load Balancing Considerations

  • Task migration cost.
  • Cache locality.
  • Task affinity restrictions.
  • Interrupt distribution.
  • Shared-resource contention.
  • Real-time deadlines.
Equal CPU utilization across cores is not always optimal. Critical tasks may require dedicated cores, and task migration can introduce additional latency.

16. Multicore Real-Time Scheduling Challenges

Meeting deadlines on multicore systems is more complex than simply checking whether total CPU utilization is below the number of cores.

Important Challenges

  • Shared cache and memory-bus contention.
  • Inter-core synchronization delays.
  • Task migration overhead.
  • Interrupt distribution and interference.
  • Shared peripheral access.
  • Priority inversion across cores.
  • Non-deterministic memory access delays.
  • Thermal and power-management effects.

Example: Shared Peripheral Contention

Core 0 and Core 1 may execute separate tasks but both need access to the same SPI controller. A synchronization mechanism must coordinate access to that peripheral.

Even when CPU execution is parallel, a shared hardware resource can become a serialization bottleneck.

17. Priority Inversion in Multicore Systems

Priority inversion can occur when a high-priority task waits for a resource held by a lower-priority task.

In multicore systems, the situation may involve tasks executing on different cores and can be more complicated because of cross-core locking and scheduling.

Possible Solutions

  • Shorten critical sections.
  • Use suitable mutex protocols supported by the RTOS.
  • Establish a consistent lock-acquisition order.
  • Reduce shared-resource dependencies.
  • Use dedicated owner tasks for complex peripherals.
  • Include blocking in response-time analysis.

Priority inheritance is useful in supported mutex implementations, but it does not eliminate every form of multicore blocking or guarantee a deadline.

18. FreeRTOS SMP

FreeRTOS is available in different kernel and port configurations. SMP support is not a property of every FreeRTOS build.

An SMP-capable FreeRTOS configuration coordinates task execution across multiple cores supported by the selected SMP port.

General SMP Design Considerations

  • Use an SMP-capable kernel version and processor port.
  • Check the target hardware's core architecture.
  • Review the port's scheduling and task-affinity behavior.
  • Use supported synchronization APIs for shared data.
  • Verify interrupt routing and per-core interrupt behavior.
  • Check memory protection and cache-coherency requirements.
  • Analyze worst-case execution and blocking across cores.
Do not assume that standard single-core FreeRTOS APIs or a particular MCU port provide SMP functionality. SMP support, APIs and scheduling details depend on the exact FreeRTOS release and hardware port.

19. AMP and SMP Application Examples

AMP Example – Automotive Control

  • Processor A manages safety-critical control.
  • Processor B handles infotainment.
  • Processor C performs communication or diagnostics.

SMP Example – Industrial Processing

  • Core 0 processes sensor input.
  • Core 1 performs signal processing.
  • Core 2 handles communication.
  • Core 3 performs logging and diagnostics.

These are illustrative allocations. Actual designs must account for shared resources, safety partitions and timing constraints.

20. Practical Exercise 1 – Parallel Execution

Problem: Task A requires 8 ms of CPU time and Task B requires 6 ms. Assume both tasks are independent and can run simultaneously on separate cores.

Solution

Single-Core Sequential Time =
    8 + 6

    = 14 ms

Ideal Two-Core Parallel Time =
    max(8, 6)

    = 8 ms

Answer: Ideal completion time is 8 ms on two cores. Real systems may take longer due to scheduling, synchronization and shared-resource overhead.

21. Practical Exercise 2 – Core Utilization

Problem: Core 0 executes tasks for 70% of the observation interval, while Core 1 executes tasks for 40%. Calculate average utilization across both cores.

Total Core Utilization =
    70% + 40%
    = 110%

Average Per-Core Utilization =
    110% / 2

    = 55%

Answer: Average utilization is 55% per core. This does not reveal whether individual task deadlines are met.

22. Practical Exercise 3 – Shared Counter

Problem: Two cores increment the same counter 1000 times each. What should the final counter value be if every increment is completed correctly?

Core 0 increments = 1000
Core 1 increments = 1000

Expected Counter =
    1000 + 1000

    = 2000

If the increment is implemented as an unsynchronized read-modify-write operation, updates may be lost. Use an appropriate atomic operation or synchronization mechanism.

23. Practical Exercise 4 – AMP vs SMP Selection

Scenario: An embedded product has one processor dedicated to motor control and another processor running a separate Linux environment for user-interface and networking tasks.

Likely architecture: AMP-style partitioning.

Reason: The processing units have separate responsibilities and may run separate software environments, communicating through an explicit inter-processor mechanism.

24. Practical Exercise 5 – Multicore Design

Objective: Design a conceptual multicore embedded application with two cores.

Core 0Sensor acquisition and real-time control.
Core 1Communication, logging and diagnostics.

Design Tasks

  1. Identify data exchanged between the cores.
  2. Choose a shared-memory or message-based communication method.

25. Limitations for the LPC2129 Learning Setup

The LPC2129 uses a single ARM7TDMI-S processor core. It is not a multicore processor and therefore cannot demonstrate true simultaneous multicore execution.

Using Keil uVision in simulator-only mode, you can study:

  • Task scheduling concepts on a single core, if a compatible RTOS port is available.
  • Concurrency through task switching.
  • Shared-variable race conditions conceptually.
  • Mutex and semaphore behavior in a supported software environment.
  • Timing and synchronization algorithms through host-side examples.

To demonstrate actual SMP behavior, use a multicore development platform and an RTOS release with a supported SMP port.

For an embedded RTOS portfolio project, a multicore-capable development board with verified SMP support is a more appropriate practical platform than the LPC2129 simulator.

27. Lesson Summary

  • A multicore processor contains multiple independent processing cores.
  • Concurrency means overlapping progress; parallelism means simultaneous execution.
  • AMP assigns different responsibilities to processing units.
  • SMP coordinates multiple peer cores through a shared operating-system environment.
  • Task affinity controls which cores may execute a task.
  • Shared memory requires appropriate synchronization.
  • Atomic operations, mutexes and memory-ordering mechanisms help coordinate concurrent access.
  • Cache coherency does not eliminate application-level race conditions.
  • Multicore scheduling must consider migration, blocking and shared-resource contention.
  • FreeRTOS SMP support depends on the selected kernel release and hardware port.
  • The LPC2129 is single-core and cannot demonstrate true multicore parallel execution.
