2. Introduction to RTOS Security

RTOS security protects embedded software, hardware resources, data and communication channels against unauthorized access, modification, disruption and misuse.

Embedded systems are used in industrial controllers, automotive electronics, medical devices, IoT equipment and communication products. A security compromise can affect both information confidentiality and physical system behavior.

3. Embedded System Attack Surface

An attack surface is the collection of interfaces and components through which an attacker may attempt to interact with a system.

Common Attack Surfaces

  • UART debug interfaces.
  • USB and serial ports.
  • Ethernet, Wi-Fi and Bluetooth.
  • CAN and other fieldbus interfaces.
  • Bootloader and firmware-update interfaces.
  • External memory and removable storage.
  • Debug access such as JTAG and SWD.
  • Unprotected configuration interfaces.
EMBEDDED DEVICE | +------------+------------+ | | | NETWORK DEBUG PORT UPDATE PORT | | | Malformed Unauthorized Malicious Messages Debugging Firmware | | | +------------+------------+ | SECURITY RISK

Every enabled interface should have a defined purpose, access policy and protection mechanism.

5. Authentication, Authorization and Encryption

5.1 Authentication

Authentication verifies the identity of a user, device or software component.

Examples include passwords, cryptographic certificates and challenge-response protocols.

5.2 Authorization

Authorization determines what an authenticated entity is allowed to do.

For example, a maintenance interface may allow reading diagnostic data but restrict changes to safety-related configuration.

5.3 Encryption

Encryption transforms readable information into ciphertext using a cryptographic key. It protects confidentiality when correctly implemented and configured.

MechanismPrimary Purpose
AuthenticationVerify identity.
AuthorizationControl permissions.
EncryptionProtect confidentiality.
Digital signatureVerify authenticity and integrity of signed data.
Message Authentication Code (MAC)Verify message integrity and authenticity using a shared secret.
Hash functionCalculate a fixed-length digest for integrity checking.
A plain cryptographic hash does not authenticate a firmware image by itself. An attacker who can replace the image may also replace its hash. Use a trusted digital signature or authenticated mechanism when authenticity is required.

6. Privilege Levels and Access Control

Privilege levels separate software according to the operations it is allowed to perform.

Depending on the processor architecture, privileged software may access system control registers and protected resources, while unprivileged software is restricted.

PRIVILEGED KERNEL | TASK / APPLICATION CODE | RESTRICTED ACCESS | PROTECTED RESOURCES

Typical Privilege Separation

Execution LevelTypical Responsibility
Privileged kernelScheduling, interrupt control and resource management.
Unprivileged applicationApplication logic with restricted access.
Hardware protection layerEnforces memory and peripheral access restrictions.

Not all microcontrollers provide the same privilege architecture. Some small MCUs have limited or no hardware-enforced separation between application and kernel code.

7. Memory Protection

Memory protection prevents one software component from accessing memory regions that it is not authorized to use.

Common Memory Regions

  • Kernel code and data.
  • Application code.
  • Task stacks.
  • Shared buffers.
  • Peripheral registers.
  • Read-only configuration data.

Memory Protection Unit (MPU)

An MPU defines memory regions and access permissions, such as read-only, read-write, executable or non-executable, depending on processor support.

MPU | +--------+--------+ | | | REGION 1 REGION 2 REGION 3 | | | KERNEL TASK A PERIPHERAL MEMORY MEMORY REGION | | | ACCESS LIMITED CONTROLLED RULES ACCESS ACCESS

Benefits

  • Restricts accidental memory corruption.
  • Can isolate tasks from one another.
  • Protects kernel memory from unprivileged tasks.
  • Can prevent execution from selected memory regions.
An MPU does not automatically provide complete security. Incorrect region configuration, privileged-code vulnerabilities and DMA access may bypass intended software isolation.

Actual capabilities depend on the processor architecture. Some advanced processors include both address-translation and protection mechanisms.

9. Secure Boot

Secure boot establishes a chain of trust during startup. Each boot stage verifies the authenticity and integrity of the next stage before transferring execution to it.

POWER ON | ROOT OF TRUST | VERIFY BOOTLOADER | BOOTLOADER | VERIFY APPLICATION | APPLICATION START | NORMAL OPERATION

Secure Boot Process

  1. Processor starts from a trusted boot location.
  2. Immutable or hardware-protected code establishes the root of trust.
  3. The bootloader verifies the next software image.
  4. The image is accepted only if verification succeeds.
  5. Execution continues through the verified boot chain.

Verification Methods

  • Digital signature verification.
  • Cryptographic hash comparison against trusted data.
  • Hardware-protected public keys or key hashes.
  • Version and rollback-policy checks.
A checksum alone is not a secure authenticity mechanism. Secure boot requires a trust anchor that an attacker cannot freely replace.

10. Firmware Integrity and Digital Signatures

Firmware integrity ensures that program contents have not been modified without authorization.

Digital Signature Workflow

FIRMWARE IMAGE | HASH CALCULATION | PRIVATE KEY SIGNING | SIGNED FIRMWARE | DEVICE RECEIVES | PUBLIC KEY VERIFY | +-----+-----+ | | VALID INVALID | | ACCEPT REJECT

The firmware developer signs the image using a private signing key. The device verifies the signature using the corresponding trusted public key.

Security Requirements

  • Protect private signing keys.
  • Store verification keys securely.
  • Define signature algorithms and key sizes appropriately.
  • Authenticate image metadata and relevant configuration.
  • Define a policy for obsolete or revoked firmware.

11. Secure Firmware Update

A secure firmware update process ensures that only authorized firmware is installed and that interruption does not leave the device in an unrecoverable state.

Typical Update Sequence

RECEIVE UPDATE PACKAGE | VERIFY SIGNATURE | CHECK VERSION POLICY | CHECK IMAGE COMPATIBILITY | WRITE TO STORAGE | VERIFY WRITTEN IMAGE | ACTIVATE NEW FIRMWARE | STARTUP VALIDATION

Important Update Protections

  • Authenticate the update package.
  • Validate firmware compatibility.
  • Prevent unauthorized downgrade attacks.
  • Protect update transport where applicable.
  • Verify data after writing to flash.
  • Provide recovery from interrupted updates.
  • Maintain a known-good recovery image where required.

A/B Firmware Update Concept

Two firmware slots can be used. The device writes a new image to the inactive slot, verifies it and then changes the boot selection. If startup validation fails, the bootloader can revert according to the defined recovery policy.

A/B updates require careful handling of boot metadata, rollback state, flash endurance and power-loss conditions. Two slots alone do not guarantee secure recovery.

13. Replay Attack Protection

A replay attack occurs when an attacker captures a previously valid message and sends it again.

Example

Original command:
UNLOCK_DOOR, sequence = 105

Attacker records the message.

Later, the same message is transmitted again.

Without replay protection, the receiver
may accept the old command.

Possible Protections

  • Monotonically increasing sequence numbers.
  • Nonces.
  • Timestamps with trusted time assumptions.
  • Authenticated session state.
  • Message authentication codes or digital signatures.

The receiver must validate freshness as well as message authenticity. Sequence-number storage and reset behavior must be designed to prevent reuse or rollback.

14. Secure Debugging Interfaces

Debugging interfaces are useful during development but can expose sensitive memory, firmware and control functions.

Common Interfaces

  • JTAG.
  • SWD.
  • UART debug console.
  • USB service interface.

Protection Practices

  • Disable or restrict debug access in production.
  • Use authenticated debug features where available.
  • Protect bootloader and memory access.
  • Remove default credentials.
  • Restrict diagnostic commands.
  • Document authorized service procedures.
Disabling a debug port can make field diagnosis and recovery difficult. A production security policy should balance access control with authorized maintenance requirements.

15. Denial of Service and Resource Protection

A denial-of-service attack attempts to make a service unavailable by exhausting resources or preventing normal processing.

Possible RTOS Resource Targets

  • CPU time.
  • Task stacks.
  • Heap memory.
  • Message queues.
  • Network buffers.
  • Interrupt processing capacity.
  • Communication bandwidth.

Example: Queue Exhaustion

while (incomingMessageAvailable())
{
    xQueueSend(commandQueue,
               &message,
               0);
}

If the queue fills and the application does not handle failed sends, valid messages may be lost or the system may behave incorrectly.

Mitigation Methods

  • Validate input length and format.
  • Set queue and buffer limits.
  • Apply rate limiting.
  • Use bounded processing time.
  • Prioritize safety-related tasks appropriately.
  • Monitor resource exhaustion.
  • Define overload and recovery behavior.
A rate limiter or queue limit can reduce resource exhaustion but must be designed so that legitimate safety-related events are not silently discarded.

16. Cryptographic Security in Embedded Systems

Cryptography provides mechanisms for confidentiality, integrity, authentication and key establishment.

TechniqueExamplesUse
Symmetric encryptionAESEfficient data encryption using a shared secret key.
Asymmetric cryptographyECC, RSADigital signatures and key establishment.
Hash functionsSHA-256Message and firmware digest calculation.
Message authenticationHMACMessage integrity and authenticity using a shared secret.
Authenticated encryptionAES-GCM, ChaCha20-Poly1305Confidentiality and integrity together.

Key Management

  • Generate keys using suitable cryptographic randomness.
  • Store secret keys in protected hardware or secure storage.
  • Restrict key access.
  • Define rotation and revocation procedures.
  • Avoid hard-coded shared secrets across an entire product fleet.
  • Protect manufacturing and provisioning processes.
Do not invent custom cryptographic algorithms or reuse encryption nonces where the selected algorithm requires uniqueness. Use established libraries and reviewed protocols.

Hardware security features can protect sensitive operations and secrets from software-level attacks.

Hardware Random Number GeneratorProvides entropy for cryptographic operations.
MPUEnforces memory access permissions.

Feature availability differs across MCU families. A product must be designed around the actual hardware capabilities.

18. ARM Security Architecture Considerations

ARM security features differ significantly between processor families.

ARM7TDMI-S

  • Provides processor operating modes such as User, System, Supervisor, IRQ, FIQ, Abort and Undefined.
  • Does not provide the ARM TrustZone security architecture.
  • Does not include an integrated MPU in the LPC2129 configuration.
  • Software privilege separation alone does not provide comprehensive hardware memory isolation.

ARM Cortex-M with MPU

  • Some Cortex-M processors provide an MPU.
  • Memory regions can be configured with access permissions.
  • Some RTOS ports support task-level memory protection.
  • MPU support depends on the specific processor and port.

ARM Cortex-M with TrustZone

  • Supported Cortex-M processors can separate Secure and Non-secure execution environments.
  • Secure services can protect selected keys and operations.
  • Non-secure applications access Secure services through controlled interfaces.
Do not apply Cortex-M MPU, TrustZone or interrupt-priority assumptions to the LPC2129 ARM7TDMI-S processor.

19. FreeRTOS Security Considerations

FreeRTOS provides task scheduling and synchronization facilities. Security depends on the selected processor, port, application architecture and additional protection mechanisms.

Important Design Practices

  • Validate all external input before processing.
  • Use bounded buffers and check queue operation results.
  • Restrict access to privileged kernel operations where hardware permits.
  • Protect shared resources using suitable synchronization.
  • Use static allocation where appropriate to reduce runtime allocation risks.
  • Monitor task stacks and system resource usage.
  • Keep debug interfaces controlled in production.
  • Use authenticated firmware updates.
  • Protect cryptographic keys.
  • Keep kernel and application dependencies updated.

FreeRTOS MPU Support

Some FreeRTOS ports provide MPU-based task isolation. These features are port-specific and require compatible hardware, compiler support, configuration and application design.

Standard FreeRTOS task separation is not automatically a security boundary. On a microcontroller without hardware-enforced memory protection, tasks may share the same privileged address space.

20. Secure Coding Practices

  • Validate array indexes and buffer lengths.
  • Check pointers before dereferencing them.
  • Avoid unsafe string and memory operations.
  • Initialize variables and structures.
  • Check all API return values.
  • Handle integer overflow and invalid numeric ranges.
  • Use explicit ownership rules for dynamically allocated memory.
  • Do not expose passwords or secret keys in logs.
  • Use defensive parsing for communication packets.
  • Use compiler warnings and static analysis.
  • Review third-party libraries and update vulnerable dependencies.
  • Keep security-sensitive operations small and auditable.

21. Practical Exercise 1 – Firmware Integrity Check

Objective: Understand the difference between a basic checksum and cryptographic firmware authentication.

Scenario

A device receives a firmware image and calculates its SHA-256 digest.

Questions

  1. What does the digest help detect?
  2. Can a plain digest prove who created the firmware?
  3. What happens if an attacker replaces both the firmware and its stored digest?
  4. How can a digital signature improve the verification process?

Expected conclusion: A trusted digital signature allows the device to verify that the firmware was signed by a holder of the trusted private key and that the signed content has not been modified.

23. Practical Exercise 3 – Replay Protection

Objective: Design a simple message freshness check.

Message fields:
    Device_ID
    Sequence_Number
    Command
    Authentication_Tag

Receiver:
    1. Verify authentication tag.
    2. Check device identity.
    3. Check sequence number freshness.
    4. Validate command permissions.
    5. Execute accepted command.

The authentication tag must cover the relevant message fields, including the sequence number. The sequence state must survive resets or be re-established securely when required by the protocol.

24. Practical Exercise 4 – Denial-of-Service Protection

Scenario: An external communication interface receives messages faster than the application can process them.

Design a Protection Strategy

  1. Validate message length and structure.
  2. Set a maximum input buffer size.
  3. Apply an appropriate rate limit.
  4. Use a bounded queue.
  5. Check queue-send failures.
  6. Keep safety-related processing independent where required.
  7. Record abnormal traffic without blocking critical tasks.

25. Practical Exercise 5 – LPC2129 Security Review

Objective: Review security limitations of the LPC2129 learning platform.

  • Identify available processor operating modes.
  • Identify exposed UART and debug interfaces.
  • Review boot and firmware-update design assumptions.
  • Identify memory regions that require protection.
  • Determine which protections require external hardware or a different MCU.
  • Document limitations of the Keil simulator.
The LPC2129 and Keil simulator can be used to study basic access-control concepts and secure coding. They cannot demonstrate hardware features that the device does not contain, such as ARM TrustZone or a built-in MPU.

27. Lesson Summary

  • RTOS security protects embedded software, data, interfaces and hardware resources.
  • The main security objectives are confidentiality, integrity and availability.
  • Authentication verifies identity; authorization controls permissions.
  • Memory protection restricts unauthorized access to memory regions.
  • Secure boot verifies software during startup.
  • Digital signatures authenticate firmware and protect its integrity.
  • Secure updates require authenticity, version control and recovery planning.
  • Replay protection requires message freshness checks.
  • Hardware security features strengthen protection when correctly configured.
  • FreeRTOS does not automatically provide complete application security.
  • Security must be designed across hardware, firmware, communication and lifecycle processes.
