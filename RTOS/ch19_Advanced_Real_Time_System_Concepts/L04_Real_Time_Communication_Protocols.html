2. Introduction to Real-Time Communication

Real-time communication is the exchange of information between system components within timing constraints required by the application.

Communication may occur between:

  • Microcontroller and sensors.
  • Processor and memory devices.
  • Multiple microcontrollers.
  • RTOS tasks and communication drivers.
  • Embedded controller and industrial equipment.
  • Control systems and remote monitoring devices.
REAL-TIME EMBEDDED SYSTEM | COMMUNICATION LAYER | +----------+----------+ | | | SENSOR CONTROLLER ACTUATOR | | | +----------+----------+ | TIMELY DATA EXCHANGE

Correct data is not sufficient if it arrives too late. A real-time communication system must consider both data integrity and timing requirements.

3. Real-Time Communication Requirements

3.1 Latency

Latency is the time taken for data or an event to travel from its source to its destination.

Communication Latency =
    Reception Time - Transmission Time

3.2 Throughput

Throughput is the amount of useful data transferred per unit time.

It is commonly expressed in bits per second (bps), bytes per second or messages per second.

3.3 Jitter

Jitter is the variation in communication timing between repeated transmissions or deliveries.

For example, if a message normally arrives every 10 ms but actual intervals vary between 9 ms and 13 ms, the timing is not perfectly uniform.

3.4 Determinism

Determinism means that communication behavior has predictable timing under defined operating conditions.

3.5 Reliability

Reliability concerns successful data delivery and detection of communication errors.

3.6 Deadline

A communication deadline specifies the latest acceptable time by which a message must be delivered or processed.

ParameterDesign Question
LatencyHow quickly does the message arrive?
ThroughputHow much data can be transferred?
JitterHow much does delivery timing vary?
DeterminismCan timing be bounded and predicted?
ReliabilityHow are errors detected and handled?
DeadlineMust the message arrive before a specified time?

4. Communication Protocol Classification

4.1 Serial Communication

Serial communication transfers data sequentially over one or more communication lines.

4.2 Parallel Communication

Parallel communication transfers multiple bits simultaneously over multiple data lines. It can provide high transfer rates over short distances but requires more signal connections.

4.3 Synchronous Communication

Synchronous communication uses a shared or associated clock to coordinate data transfer.

Examples: SPI and I²C.

4.4 Asynchronous Communication

Asynchronous communication does not use a separate shared clock signal between the communicating devices. Both sides agree on parameters such as baud rate and framing.

Example: UART.

5. UART – Universal Asynchronous Receiver/Transmitter

UART is an asynchronous serial communication interface commonly used for point-to-point communication between embedded devices.

UART Signal Lines

  • TX – Transmit data.
  • RX – Receive data.
  • GND – Common reference ground.
DEVICE A DEVICE B +--------+ +--------+ | | ---- TX ----> | RX | | UART | | UART | | | <--- RX ----- | TX | | | ----- GND --- | GND | +--------+ +--------+

UART Frame Structure

A typical UART frame contains:

  • Start bit.
  • Data bits.
  • Optional parity bit.
  • One or more stop bits.
UART FRAME (8N1 EXAMPLE) | Start | D0 D1 D2 D3 D4 D5 D6 D7 | Stop | | 0 | 8 DATA BITS | 1 |

UART Characteristics

ParameterDescription
ClockNo separate clock line.
DuplexFull-duplex capability with separate TX and RX.
AddressingBasic UART does not provide built-in multi-device addressing.
Common UsesDebugging, GPS modules, serial terminals and device communication.

Baud Rate Example

At 9600 baud, a UART line transmits approximately 9600 symbols per second. For standard binary UART signaling, one symbol represents one bit.

For an 8N1 frame, each data byte uses 10 transmitted bits:

1 Start + 8 Data + 1 Stop = 10 bits

Approximate Byte Rate =
    9600 / 10

    = 960 bytes/second

This is a theoretical rate before accounting for software overhead, gaps and other protocol processing.

6. SPI – Serial Peripheral Interface

SPI is a synchronous serial communication protocol commonly used between a controller and peripheral devices.

SPI Signal Lines

  • SCLK – Serial clock.
  • MOSI – Master Out, Slave In.
  • MISO – Master In, Slave Out.
  • CS/SS – Chip Select / Slave Select.
SPI CONTROLLER SPI DEVICE +-------------+ +-------------+ | |--- SCLK -->| | | |--- MOSI -->| | | |<-- MISO ---| | | |--- CS ---->| | +-------------+ +-------------+

SPI Characteristics

  • Synchronous communication.
  • Separate transmit and receive data lines.
  • Full-duplex data transfer is possible.
  • Clock polarity and phase are configurable through SPI modes.
  • Multiple devices can share bus signals using separate chip-select lines.

SPI Modes

ModeCPOLCPHA
Mode 000
Mode 101
Mode 210
Mode 311

CPOL determines the clock's idle level. CPHA determines which clock edge is used for data sampling.

Common Applications

  • Flash memory.
  • Display controllers.
  • ADC and DAC devices.
  • Sensor interfaces.
  • Wireless communication modules.

7. I²C – Inter-Integrated Circuit

I²C is a synchronous two-wire serial communication protocol used to connect multiple devices on a shared bus.

I²C Signal Lines

  • SDA – Serial Data.
  • SCL – Serial Clock.
+-----------+ +-----------+ | Controller| | Device 1 | +-----+-----+ +-----+-----+ | | ======+===================+====== SDA ======+===================+====== SCL | | +-----+-----+ +-----+-----+ | Device 2 | | Device 3 | +-----------+ +-----------+

I²C Characteristics

  • Two shared bus lines.
  • Address-based device selection.
  • Supports multiple controllers and targets according to the bus implementation.
  • Uses acknowledgements during transfer.
  • Requires pull-up resistors on SDA and SCL for conventional I²C signaling.
  • Devices use open-drain or open-collector signaling.

Typical I²C Transfer

  1. Controller generates START condition.
  2. Controller transmits the target address and direction bit.
  3. Target acknowledges if it recognizes and can respond to the address.
  4. Data bytes are transferred with acknowledgement handling.
  5. Controller generates STOP condition when the transaction ends.

Common Applications

  • Temperature sensors.
  • EEPROM.
  • RTC modules.
  • Configuration registers.
  • Low-speed peripheral devices.

8. CAN – Controller Area Network

CAN is a robust serial communication protocol designed for communication among multiple electronic control units.

It is widely used in automotive, industrial and embedded control systems.

CAN Bus Structure

CAN NODE 1 | CAN TRANSCEIVER | CAN_H ========+================ CAN_H | CAN_L ========+================ CAN_L | CAN TRANSCEIVER | CAN NODE 2 Shared differential bus Termination at both physical ends

CAN Characteristics

  • Multi-node communication.
  • Message-oriented communication.
  • Message identifiers determine arbitration priority.
  • Non-destructive bitwise arbitration in classical CAN.
  • Error detection and fault confinement mechanisms.
  • Differential signaling through a CAN transceiver.

CAN Arbitration

When multiple nodes begin transmission simultaneously, arbitration determines which message continues.

In classical CAN, a lower numerical identifier generally has higher arbitration priority when comparing identifiers of the same format.

CAN arbitration priority is based on the transmitted identifier and frame arbitration rules, not on an RTOS task priority value.

CAN Applications

  • Automotive electronic control units.
  • Industrial automation.
  • Motor controllers.
  • Distributed embedded systems.
  • Vehicle diagnostics.

10. Communication Timing Analysis

Real-time communication design requires an estimate of the time needed to transmit, receive and process messages.

10.1 UART Transmission Time

Assume a UART frame contains 10 bits and the baud rate is 115200.

Frame Transmission Time =
    10 / 115200

    = 0.0000868 seconds

    ≈ 86.8 microseconds

For 100 bytes transmitted continuously:

Total Bits = 100 × 10
           = 1000 bits

Transmission Time =
    1000 / 115200

    ≈ 8.68 ms

This excludes software gaps, driver overhead and additional protocol framing.

10.2 SPI Transfer Time

For 100 bytes transferred at an SPI clock of 1 MHz:

Total Bits = 100 × 8
           = 800 bits

Transfer Time =
    800 / 1,000,000

    = 0.8 ms

This is the clocked data-transfer time. Chip-select setup, command bytes, device delays and software overhead may increase total transaction time.

11. Communication Latency Components

End-to-end communication latency may include several stages.

DATA GENERATED | TASK RELEASE DELAY | DRIVER QUEUE WAIT | BUS ARBITRATION | SERIAL TRANSMISSION | RECEIVER INTERRUPT | DRIVER PROCESSING | APPLICATION TASK WAKE-UP | DATA PROCESSING COMPLETE

A useful conceptual model is:

End-to-End Latency =
    Release Delay
  + Queueing Delay
  + Arbitration Delay
  + Transmission Time
  + Reception Delay
  + Processing Delay

For a rigorous analysis, define the measurement endpoints and account for overlapping operations, retransmissions where applicable and interference from other traffic.

12. Communication and RTOS Task Design

Communication drivers often interact with the RTOS through interrupts, queues, semaphores, notifications and DMA.

Typical Architecture

APPLICATION TASK | SEND / RECEIVE API | DRIVER AND BUFFERS | HARDWARE PERIPHERAL | INTERRUPT | ISR NOTIFIES TASK | COMMUNICATION TASK | PROCESS RECEIVED DATA

Design Guidelines

  • Keep interrupt service routines short.
  • Use ISR-safe RTOS APIs where supported by the port.
  • Use queues or notifications to transfer events to tasks.
  • Define buffer ownership and lifetime.
  • Handle receive-buffer overflow.
  • Check transmission and reception error status.
  • Define timeout and recovery behavior.
  • Prioritize messages according to application deadlines.

13. Interrupt-Driven Communication

In interrupt-driven communication, hardware generates an interrupt when a relevant event occurs, such as receiving a byte or completing a transmission.

Illustrative ISR Pattern

void UART_Receive_ISR(void)
{
    uint8_t receivedData;

    receivedData = UART_ReadDataRegister();

    /*
      Store data in a suitable buffer.
      Notify the application task using
      a supported ISR-safe mechanism.
    */

    NotifyCommunicationTaskFromISR();
}

The register and notification functions above are placeholders. Their implementation depends on the MCU, driver and FreeRTOS port.

Do not perform lengthy parsing, blocking operations, dynamic allocation or mutex acquisition inside an ISR.

14. DMA-Based Communication

Direct Memory Access (DMA) allows a hardware controller to transfer data between a peripheral and memory with limited CPU involvement.

DMA Communication Flow

APPLICATION TASK | CONFIGURE DMA | START TRANSFER | CPU DOES OTHER WORK | DMA TRANSFERS DATA | TRANSFER COMPLETE IRQ | NOTIFY APPLICATION TASK

Advantages

  • Reduces CPU involvement in large data transfers.
  • Can improve throughput.
  • Allows CPU and peripheral operations to overlap.
  • Can reduce interrupt frequency when using suitable transfer sizes.

Important Considerations

  • Buffer must remain valid until DMA finishes.
  • CPU and DMA access must be coordinated.
  • Cache coherency may require explicit maintenance on cache-equipped processors.
  • Alignment and memory-region restrictions may apply.
  • DMA completion does not necessarily mean application processing is complete.

15. CAN Real-Time Message Priority

CAN uses message identifiers during arbitration. Messages with higher arbitration priority can gain access to the bus before lower-priority messages.

Example

MessageIdentifierArbitration Priority
Emergency Stop0x080Higher
Motor Status0x180Medium
Temperature Data0x300Lower

For these standard identifiers, the lower numerical identifier wins arbitration when the messages compete under the same relevant frame-format rules.

Important Design Considerations

  • Assign identifiers based on message criticality.
  • Consider message periods and deadlines.
  • Calculate bus utilization.
  • Consider worst-case blocking by a frame already in transmission.
  • Account for bit stuffing, frame format and error retransmissions.
  • Avoid excessive high-priority traffic starving lower-priority messages.
CAN message priority is independent of RTOS task scheduling priority. A high-priority task can still wait for access to the CAN bus.

16. Communication Bus Utilization

Bus utilization is the fraction of available bus capacity consumed by transmitted messages.

A simplified utilization estimate for periodic messages is:

U = Σ (Ci / Ti)

Where:

  • Ci = bus transmission time for message i.
  • Ti = message period.

Example

Assume three periodic messages:

MessageTransmission TimePeriod
M11 ms10 ms
M22 ms20 ms
M31 ms50 ms
U = (1/10) + (2/20) + (1/50)

  = 0.10 + 0.10 + 0.02

  = 0.22

Bus Utilization = 22%

This is a simplified periodic-load estimate. Actual CAN schedulability requires protocol-specific response-time analysis, including arbitration, blocking, frame overhead and error conditions.

17. Communication Failure Handling

Real-time embedded systems should define how communication faults are detected and handled.

FaultPossible Handling
UART framing errorDiscard invalid frame and record error.
UART overrunDetect lost data and recover receiver state.
I²C NACKCheck address/device state and apply bounded retry policy.
I²C bus stuckUse a hardware-appropriate bus recovery procedure.
SPI transfer timeoutAbort or reset the transaction according to driver design.
CAN bus-offFollow controller recovery and application fault policy.
Queue fullApply a defined drop, backpressure or fault strategy.

Retries must be bounded and included in worst-case timing analysis. An unlimited retry loop can prevent a critical task from meeting its deadline.

Application RequirementPossible Choice

Protocol selection must also consider physical-layer requirements, cable length, electrical noise, device count, power consumption, error handling and implementation cost.

19. Practical Exercise 1 – UART Timing

Problem: A UART operates at 19200 baud using 8N1 framing. Calculate the ideal transmission time for 50 bytes sent continuously.

Solution

Bits per Frame = 1 + 8 + 1
               = 10 bits

Total Bits = 50 × 10
           = 500 bits

Transmission Time = 500 / 19200
                  = 0.02604 seconds

                  ≈ 26.04 ms

Answer: Approximately 26.04 ms, excluding additional protocol and software overhead.

20. Practical Exercise 2 – SPI Timing

Problem: Transfer 256 bytes over SPI at 4 MHz. Calculate the ideal clocked transfer time.

Solution

Total Bits = 256 × 8
           = 2048 bits

Transfer Time = 2048 / 4000000

              = 0.000512 seconds

              = 512 microseconds

Answer: 512 microseconds, excluding command, chip-select and device-specific delays.

21. Practical Exercise 3 – Communication Deadline

Problem: A sensor message has the following timing components:

ComponentDelay
Task release delay1 ms
Queue waiting2 ms
Transmission3 ms
Reception processing1 ms
Application processing2 ms

Solution

Total Latency =
    1 + 2 + 3 + 1 + 2

    = 9 ms

If the deadline is 10 ms, the estimated latency is within the deadline with 1 ms remaining margin.

This conclusion is valid only if the listed delays are reliable worst-case bounds and all relevant interference has been included.

22. Practical Exercise 4 – CAN Identifier Priority

Problem: Three CAN messages are ready simultaneously:

  • Message A: 0x120
  • Message B: 0x080
  • Message C: 0x300

Solution

The lower numerical standard identifier has higher arbitration priority.

  1. Message B – 0x080
  2. Message A – 0x120
  3. Message C – 0x300

Message B wins arbitration under the stated same-format, simultaneous-start assumptions.

23. Practical Exercise 5 – RTOS Communication Architecture

Objective: Design an application that receives UART data using an interrupt and processes it in a separate RTOS task.

Required Design

  1. UART peripheral receives incoming bytes.
  2. UART ISR reads the received data.
  3. ISR stores data in a suitable buffer or queue.
  4. ISR notifies the communication task using an ISR-safe mechanism.
  5. Communication task retrieves and processes received data.
  6. Application handles overflow and communication errors.
This is an architecture exercise. Actual ISR APIs, UART registers, DMA behavior and interrupt-priority restrictions depend on the MCU and RTOS port. Do not assume a Cortex-M interrupt-priority configuration applies to an ARM7 LPC2129.

25. Lesson Summary

  • Real-time communication requires correct data delivery within timing constraints.
  • Latency, throughput, jitter and determinism are important communication metrics.
  • UART is an asynchronous serial interface.
  • SPI is a synchronous interface with separate transmit and receive lines.
  • I²C provides address-based communication over a shared two-wire bus.
  • CAN provides multi-node communication with message-based arbitration.
  • RTOS communication drivers commonly use interrupts, queues, notifications and DMA.
  • Communication response time includes queuing, arbitration, transmission and processing.
  • Protocol selection depends on application requirements and physical constraints.
