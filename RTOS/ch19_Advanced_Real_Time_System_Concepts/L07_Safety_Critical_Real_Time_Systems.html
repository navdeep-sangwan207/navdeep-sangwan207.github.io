2. Introduction to Safety-Critical Systems

A safety-critical system is a system in which a malfunction or failure can contribute to unacceptable harm to people, property or the environment.

Such systems require systematic engineering, hazard analysis, fault handling, verification and validation.

Examples

  • Automotive braking and steering control.
  • Aircraft flight-control systems.
  • Medical infusion pumps and patient-monitoring equipment.
  • Industrial emergency shutdown systems.
  • Railway signaling and train protection systems.
  • Nuclear plant protection systems.
SAFETY-CRITICAL SYSTEM | +-----------+-----------+ | | | SENSORS CONTROLLER ACTUATORS | | | +-----------+-----------+ | SAFETY MONITORING | SAFE RESPONSE / STATE

The system must not only perform its intended function but also control the risks associated with failures.

3. Safety-Critical vs Mission-Critical Systems

FeatureSafety-CriticalMission-Critical
Primary concernPrevent unacceptable harm.Maintain essential operational capability.
Failure consequenceMay cause injury, death or environmental damage.May cause major service or operational disruption.
Design emphasisHazard control and safe behavior.Availability, continuity and recovery.
ExamplesAirbag deployment, emergency shutdown.Banking infrastructure, communication networks.

A system can be both safety-critical and mission-critical. The categories describe different engineering concerns, not mutually exclusive product types.

4. Real-Time Requirements in Safety-Critical Systems

Safety-related functions often have strict timing constraints.

Example: Overcurrent Protection

A motor controller monitors current. If current exceeds a specified safety threshold, the system must initiate an appropriate protective response within the required time.

CURRENT SENSOR | CURRENT MEASUREMENT | SAFETY THRESHOLD CHECK | OVERCURRENT DETECTED? | +----+----+ | | NO YES | | CONTINUE PROTECTIVE MONITORING RESPONSE | DISABLE / LIMIT OUTPUT AS DESIGNED

The required response time depends on the electrical, mechanical and thermal characteristics of the equipment and the safety analysis.

Important Timing Requirements

  • Maximum fault-detection time.
  • Maximum control response time.
  • Sensor sampling interval.
  • Actuator response time.
  • Communication timeout.
  • Safe-state transition time.

5. Hazard, Risk and Failure

5.1 Hazard

A hazard is a condition or situation that can lead to harm.

Example: An industrial motor continues rotating when a protective guard is open.

5.2 Risk

Risk considers the likelihood of harm and the severity of its consequences. Specific standards define their own risk evaluation methods.

5.3 Failure

A failure is the inability of a system, component or function to perform as required.

5.4 Fault

A fault is an abnormal condition that can cause an error or failure.

5.5 Error

An error is an incorrect internal state or value that may lead to system-level failure.

COMPONENT FAULT | INTERNAL ERROR | INCORRECT SYSTEM STATE | POSSIBLE SYSTEM FAILURE | POTENTIAL HAZARD

This is a conceptual fault-propagation chain. Detection and containment mechanisms may interrupt it at different stages.

6. Failure Modes

A failure mode describes the way a component or function fails.

Failure ModeExamplePossible Consequence
Open circuitDisconnected sensor wire.Measurement unavailable.
Short circuitDamaged signal line.Incorrect input or hardware damage.
Stuck valueSensor output remains constant.Fault may go undetected.
Incorrect outputController produces wrong command.Unsafe actuator behavior.
Timing failureControl task misses deadline.Protective response may be late.
Communication failureSafety message is lost.Remote controller lacks required information.

Safety engineering examines how each failure mode can be detected, contained or prevented from causing harm.

7. Fault Detection and Fault Tolerance

Fault detection identifies abnormal system behavior. Fault tolerance allows a system to continue providing an acceptable service despite specified faults.

Fault Detection Methods

  • Range checking.
  • Rate-of-change checking.
  • Sensor plausibility checking.
  • Communication timeout detection.
  • Memory integrity checks.
  • Watchdog monitoring.
  • Control-flow monitoring.
  • Redundant sensor comparison.

Fault Tolerance Methods

  • Redundant hardware.
  • Backup communication paths.
  • Fault containment.
  • Controlled degradation.
  • Automatic recovery where justified.
  • Transition to a defined safe state.

8. Fail-Safe Design

A fail-safe system is designed so that specified failures cause the system to enter or maintain a state that is acceptably safe.

Example: Industrial Motor

If the control system detects a critical fault, it may disable motor drive output and activate a protective mechanism according to the equipment's safety design.

NORMAL OPERATION | FAULT DETECTED | FAULT CLASSIFICATION | +-------+-------+ | | RECOVERABLE CRITICAL | | CONTROLLED SAFE RESPONSE RECOVERY | | OUTPUT DISABLED | OR SAFE CONTROL +-------+-------+ | FAULT LOGGING

Fail-Safe Design Principles

  • Define safe states for each relevant failure.
  • Use hardware protection where necessary.
  • Ensure fault detection occurs within the required time.
  • Prevent uncontrolled restart after critical faults.
  • Verify the physical behavior of actuators during power loss.
  • Define recovery and reset procedures.
A software command to turn an output off does not guarantee that the physical equipment is safe. Hardware failure, welded contacts, stored energy and actuator behavior must be considered.

9. Redundancy in Safety-Critical Systems

Redundancy uses additional components or processing paths to improve fault detection, availability or tolerance.

9.1 Hardware Redundancy

Additional hardware is used so that a single component failure does not necessarily cause loss of the required function.

9.2 Software Redundancy

Independent or diverse software implementations may be used to detect certain faults. However, software diversity does not eliminate common design errors.

9.3 Sensor Redundancy

Multiple sensors measure the same or related physical quantity. Their readings can be compared for plausibility.

9.4 Processor Redundancy

Multiple processing units may perform related computations or provide backup control.

Redundancy Architectures

ArchitectureDescription
Dual-channelTwo channels perform related functions.
Triple Modular Redundancy (TMR)Three channels use voting to tolerate certain single-channel faults.
Hot standbyBackup unit remains active and ready to take over.
Cold standbyBackup unit is activated after a failure.
Redundancy is not automatically equivalent to safety. Common-cause failures, design defects, power supply failures and shared environmental conditions can affect multiple redundant channels.

10. Triple Modular Redundancy (TMR)

Triple Modular Redundancy uses three channels that perform the same function. A voter compares their outputs and selects the majority result.

+-----------+ | CHANNEL 1 | +-----+-----+ | +-----------+ | CHANNEL 2 | +-----+-----+ | +-----------+ | CHANNEL 3 | +-----+-----+ | MAJORITY VOTER | SELECTED OUTPUT

Example

Channel 1Channel 2Channel 3Majority Output
1111
1011
0010
0111

TMR can tolerate one incorrect channel output under the assumptions of independent channel behavior and a correctly functioning voter.

A faulty voter or common-cause failure can defeat TMR. Redundant channels must be sufficiently independent for the intended safety argument.

11. Watchdog Monitoring

A watchdog timer monitors whether software continues to make expected progress. If the watchdog is not serviced within the allowed timing window, it can initiate a reset or another configured recovery action.

Watchdog Operation

SYSTEM START | START WATCHDOG | APPLICATION RUNS | HEALTH CHECKS | VALID PROGRESS? | +----+----+ | | YES NO | | SERVICE TIMEOUT WATCHDOG | | RESET / | FAULT ACTION +----<----+

Good Watchdog Design

  • Service only after relevant health checks pass.
  • Monitor meaningful task progress.
  • Set timeout using worst-case execution and scheduling delays.
  • Record reset causes where possible.
  • Prevent repeated uncontrolled restart loops.
  • Define safe behavior during startup and recovery.

Unconditionally refreshing a watchdog from a periodic timer can hide application failures.

12. Safety Monitoring and Diagnostic Mechanisms

Safety-related systems often include diagnostic functions to detect internal faults and abnormal operating conditions.

13. Safety Integrity Levels (SIL)

Safety Integrity Level (SIL) is a defined level of safety integrity used in functional safety standards such as IEC 61508 and related sector standards.

IEC 61508 defines four SIL levels, with SIL 4 representing the highest integrity level in that standard's framework.

LevelGeneral Interpretation
SIL 1Lowest of the four SIL levels.
SIL 2Higher integrity requirement than SIL 1.
SIL 3Higher integrity requirement than SIL 2.
SIL 4Highest integrity requirement in IEC 61508.

SIL requirements are determined through hazard and risk analysis. They are not selected simply because a product is technologically complex.

Low-Demand Mode – Average Probability of Failure on Demand

SILAverage Probability of Dangerous Failure on Demand
SIL 110⁻² to less than 10⁻¹
SIL 210⁻³ to less than 10⁻²
SIL 310⁻⁴ to less than 10⁻³
SIL 410⁻⁵ to less than 10⁻⁴
These probability ranges apply to the low-demand mode metric. High-demand and continuous modes use different measures, including dangerous failure frequency. SIL is not a simple software quality score.

14. Automotive Safety Integrity Level (ASIL)

Automotive safety engineering uses Automotive Safety Integrity Levels under ISO 26262.

LevelGeneral Classification
QMQuality Management; the function does not require an ASIL classification under the assessed safety requirements.
ASIL ALowest ASIL level.
ASIL BHigher than ASIL A.
ASIL CHigher than ASIL B.
ASIL DHighest ASIL level.

ASIL classification is based on the automotive hazard analysis and risk assessment, including severity, exposure and controllability.

SIL and ASIL are different classification systems. SIL levels must not be directly converted into ASIL levels.

15. Safety Lifecycle

Functional safety engineering follows a lifecycle covering concept, development, implementation, verification, validation and operation.

CONCEPT AND PLANNING | HAZARD ANALYSIS | SAFETY REQUIREMENTS | SYSTEM ARCHITECTURE | HARDWARE / SOFTWARE DESIGN | IMPLEMENTATION AND TEST | VERIFICATION / VALIDATION | DEPLOYMENT AND OPERATION | MAINTENANCE / MODIFICATION

Typical Lifecycle Activities

  • Define system scope and operating conditions.
  • Identify hazards and hazardous events.
  • Estimate and evaluate risk.
  • Specify safety functions and requirements.
  • Design hardware and software architecture.
  • Implement and verify safety mechanisms.
  • Validate the complete safety function.
  • Maintain safety evidence during operation and modification.

FMEA identifies potential failure modes, their effects and possible controls.

Fault Tree Analysis starts with a defined top-level failure and works backward to identify combinations of contributing events.

TOP EVENT Unsafe Motor Operation | OR +------+------+ | | Driver Fault Controller Fault | | Output Stuck Invalid Command | | Hardware Software Error Failure

16.3 HAZOP – Hazard and Operability Study

HAZOP uses guide words and structured review to identify deviations from intended process behavior.

16.4 FMEDA – Failure Modes, Effects and Diagnostic Analysis

FMEDA extends failure-mode analysis with diagnostic and safety-related quantitative information.

17. RTOS Design in Safety-Related Systems

An RTOS can support safety-related system architecture through predictable task scheduling, synchronization, timing services and fault monitoring.

Important RTOS Design Practices

  • Define task periods, priorities and deadlines.
  • Perform response-time and schedulability analysis.
  • Use bounded blocking and synchronization.
  • Monitor stack and memory usage.
  • Detect missed deadlines and task failures.
  • Keep interrupt processing bounded.
  • Control dynamic memory allocation where required.
  • Separate safety-related and non-safety-related functions where justified.
  • Define safe startup, shutdown and recovery behavior.
Using an RTOS does not automatically make an application functionally safe or compliant with a safety standard. The complete system, development process, hardware, software and safety evidence must satisfy applicable requirements.

18. Safety Partitioning and Freedom from Interference

Safety-related and non-safety-related software may share a processor or memory system. Their interactions must be controlled so that non-safety functions cannot adversely affect safety functions.

Potential Interference Sources

  • Memory corruption.
  • CPU starvation.
  • Interrupt overload.
  • Shared-resource blocking.
  • Communication flooding.
  • Power or clock disturbances.
  • Common drivers or libraries.

Possible Controls

  • Memory protection where supported.
  • Time and execution-budget monitoring.
  • Controlled interrupt priorities.
  • Resource ownership rules.
  • Independent safety monitoring.
  • Defined communication limits.

20. Practical Exercise 1 – Hazard Identification

Scenario: An industrial motor continues running after an emergency stop button is pressed.

Identify the Safety Issues

  1. Possible hazard: unintended motor operation.
  2. Potential causes: switch failure, wiring fault, software failure or output-driver fault.
  3. Possible detection: input plausibility, independent monitoring and output feedback.
  4. Possible protective action: independent drive disable or suitable safety-rated shutdown mechanism.
  5. Validation: test normal operation and relevant fault conditions.

21. Practical Exercise 2 – Redundancy

Problem: A three-channel system produces the following outputs:

Channel 1 = 1
Channel 2 = 0
Channel 3 = 1

Solution: Two channels agree on logic value 1. A majority voter therefore selects output 1.

This result assumes the voter and channel independence requirements are satisfied.

22. Practical Exercise 3 – Watchdog Timeout

Scenario: A controller must receive a valid health confirmation every 100 ms. The watchdog timeout is configured to 150 ms.

If a required task stops making progress and the supervisor stops refreshing the watchdog, the watchdog can detect the missing refresh after its timeout condition is reached.

Design questions:

  • Can all required tasks report progress within 100 ms under worst-case load?
  • Is 150 ms long enough for legitimate scheduling delays?
  • Does the watchdog reset create a safe physical state?
  • Can startup or recovery cause an unintended reset loop?

A timeout value alone does not establish that the watchdog design is safe.

23. Practical Exercise 4 – SIL Classification

Question: Which SIL level is the highest level in the IEC 61508 framework?

Answer: SIL 4.

The required SIL for a particular safety function must be determined through the applicable hazard and risk assessment process.

24. Practical Exercise 5 – Safety Design Review

Objective: Prepare a basic safety design review for an embedded overcurrent protection controller.

Review Checklist

  • Define normal and fault operating conditions.
  • Identify sensor failure modes.
  • Define overcurrent detection thresholds and timing.
  • Identify controller and output-driver failure modes.
  • Define the required safe state.
  • Specify independent protection where necessary.
  • Define watchdog and diagnostic requirements.
  • Analyze power-loss and restart behavior.
  • Verify timing under worst-case conditions.
  • Document verification and validation evidence.

26. Lesson Summary

  • Safety-critical systems must control risks that can lead to unacceptable harm.
  • Hazard analysis identifies unsafe conditions and their causes.
  • Fault detection and fault tolerance help manage abnormal conditions.
  • Fail-safe design defines acceptable behavior during specified failures.
  • Redundancy can improve fault tolerance but must address common-cause failures.
  • Watchdogs and diagnostics help detect certain software and hardware failures.
  • SIL belongs to the IEC 61508 framework; ASIL belongs to ISO 26262.
  • FMEA, FTA, HAZOP and FMEDA support safety analysis.
  • An RTOS provides useful mechanisms but does not automatically establish functional safety.
  • Verification, validation and lifecycle evidence are essential to safety engineering.
