2. Introduction to Reliability

Reliability is the probability that a system performs its required function without failure for a specified period under stated operating conditions.

Reliability is important in systems where unexpected failures can interrupt operation, damage equipment or create unsafe conditions.

Examples

  • Automotive engine control systems.
  • Industrial automation controllers.
  • Medical monitoring equipment.
  • Aircraft control systems.
  • Power-system protection equipment.
  • Robotics and autonomous systems.
REAL-TIME SYSTEM | RELIABILITY DESIGN | +--------+--------+ | | | DETECT CONTAIN RECOVER FAULTS FAULTS SAFELY | | | +--------+--------+ | CONTINUED SERVICE OR SAFE SHUTDOWN

3. Fault, Error and Failure

These terms describe different stages in a system malfunction.

TermMeaningExample
FaultA defect or abnormal condition that can cause an incorrect system state.A damaged sensor or software defect.
ErrorAn incorrect internal state caused by a fault.An invalid temperature value stored in memory.
FailureThe system does not deliver its required service.The controller fails to activate an alarm when required.

3.1 Relationship

FAULT | v ERROR | v FAILURE

A fault does not always produce an error, and an error does not always result in a visible failure. Detection and recovery mechanisms can prevent propagation.

4. Reliability, Availability and Maintainability

4.1 Reliability

Reliability measures the probability of failure-free operation over a specified time interval.

For a constant failure rate and an exponential lifetime model:

R(t) = e^(-λt)

Where:

  • R(t) = reliability at time t.
  • λ = constant failure rate.
  • t = operating time.

4.2 Availability

Availability is the proportion of time a system is operational and capable of providing service under the defined measurement conditions.

For a simple repairable system with steady-state assumptions:

Availability = MTBF / (MTBF + MTTR)
  • MTBF: Mean time between failures.
  • MTTR: Mean time to repair or restore service.

4.3 Maintainability

Maintainability describes how effectively a failed system can be diagnosed, repaired or restored.

PropertyMain Question
ReliabilityHow long can the system operate without failure?
AvailabilityHow much of the required time is the system operational?
MaintainabilityHow easily can the system be restored?
MTBF and MTTR are statistical measures. Their interpretation depends on the system boundary, operating conditions and repair assumptions.

5. Types of Faults in Real-Time Systems

5.1 Hardware Faults

  • Processor malfunction.
  • Memory corruption.
  • Power-supply failure.
  • Sensor failure.
  • Communication-interface failure.
  • Clock or oscillator failure.

5.2 Software Faults

  • Incorrect algorithm.
  • Buffer overflow.
  • Memory leak.
  • Race condition.
  • Deadlock.
  • Incorrect task scheduling.
  • Invalid pointer access.

5.3 Timing Faults

  • Missed deadline.
  • Excessive interrupt latency.
  • Task starvation.
  • Unexpected execution-time variation.
  • Communication timeout.

5.4 Environmental Faults

  • Excessive temperature.
  • Electromagnetic interference.
  • Vibration.
  • Moisture or contamination.
  • Supply-voltage variation.

6. Fault Detection

Fault detection identifies abnormal behavior before it causes a system failure or unacceptable consequence.

6.1 Common Detection Techniques

TechniquePurpose
Range checkingChecks whether sensor values are within valid limits.
Timeout monitoringDetects missing responses or overdue operations.
Watchdog timerDetects failure to provide expected periodic service.
Memory checksDetects selected memory corruption conditions.
Heartbeat monitoringChecks whether a task or subsystem is making expected progress.
Redundant comparisonCompares results from independent or redundant channels.
AssertionsDetects violated software assumptions.
CRC checksDetects many forms of data corruption.

6.2 Example – Sensor Range Checking

#include <stdint.h>
#include <stdbool.h>

#define MIN_TEMP  0
#define MAX_TEMP  100

bool IsTemperatureValid(int32_t temperature)
{
    if (temperature < MIN_TEMP ||
        temperature > MAX_TEMP)
    {
        return false;
    }

    return true;
}

The application can reject or flag sensor values outside the defined operating range.

Range checking detects implausible values but cannot detect every sensor fault. A failed sensor may produce a plausible but incorrect reading.

7. Fault Isolation

Fault isolation identifies the subsystem or component responsible for an abnormal condition.

It helps prevent a local fault from affecting unrelated parts of the application.

Example

Consider an industrial controller with three independent functional tasks:

INDUSTRIAL CONTROLLER | +--------+--------+ | | | SENSOR DISPLAY COMMUNICATION TASK TASK TASK | | | SENSOR DISPLAY NETWORK INPUT OUTPUT INTERFACE

If the communication task stops responding, the system can identify the communication subsystem as the affected component and apply a defined recovery policy.

Fault isolation techniques include:

  • Task-level status monitoring.
  • Separate communication buffers.
  • Input validation.
  • Module-level error reporting.
  • Independent watchdog supervision.
  • Hardware and software diagnostic checks.

8. Fault Recovery

Fault recovery attempts to restore the system to a valid operating condition after detecting an error or failure.

8.1 Recovery Techniques

  • Retry an operation.
  • Reset a peripheral.
  • Restart a failed task using a controlled procedure.
  • Reinitialize a communication interface.
  • Switch to a redundant component.
  • Enter a safe operating mode.
  • Perform a controlled system restart.

8.2 Example – Communication Retry

#include <stdint.h>
#include <stdbool.h>

#define MAX_RETRIES 3

bool SendWithRetry(void)
{
    uint32_t attempt;

    for (attempt = 0;
         attempt < MAX_RETRIES;
         attempt++)
    {
        if (SendMessage())
        {
            return true;
        }
    }

    return false;
}

If all attempts fail, the calling application should record the error and execute its defined recovery policy.

Retries should be bounded and designed with timing constraints in mind. Retrying indefinitely can block progress and cause deadline misses.

9. Fault Tolerance

Fault tolerance is the ability of a system to continue providing its required service, possibly at a reduced level, despite certain faults.

A fault-tolerant design does not necessarily prevent faults. Instead, it detects, contains and manages their effects.

9.1 Fault-Tolerant System Architecture

INPUT | +-----+-----+ | | CHANNEL A CHANNEL B | | PROCESSOR A PROCESSOR B | | +-----+-----+ | COMPARATOR | OUTPUT CONTROL

This is a simplified redundant-channel architecture. Real implementations require analysis of common-cause failures, independence, synchronization and output selection.

10. Redundancy Techniques

Redundancy provides additional resources or components so that the system can continue operating when one component fails.

10.1 Hardware Redundancy

Uses additional physical components.

  • Duplicate processors.
  • Redundant sensors.
  • Dual power supplies.
  • Backup communication links.

10.2 Software Redundancy

Uses multiple software mechanisms to detect or tolerate errors.

  • Independent algorithm implementations.
  • Input validation.
  • Cross-checking results.
  • Recovery routines.
  • Software assertions and diagnostics.

10.3 Information Redundancy

Adds extra information to detect or correct data corruption.

  • Parity bits.
  • Checksums.
  • Cyclic Redundancy Check (CRC).
  • Error-correcting codes (ECC).

10.4 Time Redundancy

Repeats an operation to detect transient faults or obtain a valid result, provided the timing budget permits it.

Redundancy does not automatically guarantee fault tolerance. Shared power, common software defects, environmental conditions or common input failures can affect multiple redundant channels.

11. N-Modular Redundancy

N-Modular Redundancy (NMR) uses multiple processing units that perform the same function. Their outputs are compared or voted on to determine the system result.

11.1 Triple Modular Redundancy (TMR)

Triple Modular Redundancy uses three processing channels and a majority voter.

INPUT | +-----+-----+ | | | CPU1 CPU2 CPU3 | | | +-----+-----+ | MAJORITY VOTER | SELECTED OUTPUT

If one channel produces a different result while the other two agree, the majority voter can select the agreeing result.

11.2 Example

ChannelOutput
CPU 1100
CPU 2100
CPU 3120
Majority Result100

TMR can tolerate one faulty channel under its assumptions, but voter failure and common-cause faults must also be considered.

12. Graceful Degradation

Graceful degradation means that a system continues providing essential functions when some components or features become unavailable.

Example – Industrial Monitoring System

ConditionSystem Behavior
Normal operationMonitoring, display, logging and communication operate.
Network failureLocal monitoring continues; communication is reported unavailable.
Display failureControl and safety functions continue if the architecture permits.
Sensor failureInvalid measurement is flagged and the defined safe response is initiated.

The objective is to preserve critical functionality rather than allowing one non-critical fault to disable the entire system.

13. Fail-Safe and Fail-Operational Systems

13.1 Fail-Safe

A fail-safe system moves to or maintains a defined safe state when a fault occurs.

Example: A machine stops motion when a critical safety sensor detects an unsafe condition.

13.2 Fail-Operational

A fail-operational system continues providing specified functionality despite certain failures, often through redundancy or reconfiguration.

Example: A vehicle control function continues operating using a redundant channel after a single channel failure, within the defined fault model.

Fail-SafeFail-Operational
Prioritizes reaching a safe condition.Prioritizes continued service.
May stop the system.May continue using backup resources.
Common in safety shutdown mechanisms.Common where service continuity is essential.
A system can combine both approaches: continue operating after some faults, but transition to a safe state when continued operation is no longer justified.

14. Watchdog Timer for Fault Detection

A watchdog timer is a hardware or software mechanism that detects when expected program activity does not occur within a configured interval.

14.1 Basic Operation

WATCHDOG TIMER | START COUNTDOWN | APPLICATION RUNS | VALID SERVICE? / \ YES NO | | REFRESH TIMEOUT | | RELOAD RESET OR TIMER FAULT ACTION

14.2 Example Pseudocode

void MainControlLoop(void)
{
    InitializeSystem();
    InitializeWatchdog();

    for (;;)
    {
        if (PerformControlCycle())
        {
            RefreshWatchdog();
        }
        else
        {
            /*
              Do not report healthy operation.
              Allow the defined watchdog response.
            */
        }
    }
}

The exact watchdog interface is hardware-specific.

Refreshing a watchdog unconditionally from a periodic timer or unrelated task can hide a failed control task. A robust design should verify meaningful system progress before servicing the watchdog.

15. Reliability Techniques in FreeRTOS

FreeRTOS provides kernel mechanisms that can support reliable application design. The application developer must combine them with suitable system-level fault handling.

FreeRTOS MechanismReliability Application
Task prioritiesGive critical work appropriate scheduling priority.
Task notificationsSignal task events efficiently.
QueuesTransfer data with defined capacity and blocking behavior.
SemaphoresSynchronize events and resource access.
MutexesProtect shared resources between tasks.
Software timersSchedule periodic or one-shot software actions.
Stack checkingDetect selected stack-overflow conditions.
Memory monitoringObserve heap and stack usage.
AssertionsDetect violated software assumptions.

These mechanisms do not automatically make an application fault-tolerant or safety-certified. The application still requires fault analysis, testing and a defined safe-state strategy.

16. Example – Fault Monitoring Task

Objective: Demonstrate a simple FreeRTOS task that monitors a simulated sensor value and records an abnormal condition.

Program

#include "FreeRTOS.h"
#include "task.h"
#include <stdint.h>
#include <stdbool.h>

#define MIN_VALUE  0
#define MAX_VALUE  100

volatile int32_t simulatedSensorValue = 50;
volatile uint32_t faultCount = 0;
volatile bool sensorFault = false;

void FaultMonitorTask(void *pvParameters)
{
    int32_t value;

    for (;;)
    {
        value = simulatedSensorValue;

        if (value < MIN_VALUE ||
            value > MAX_VALUE)
        {
            sensorFault = true;
            faultCount++;
        }
        else
        {
            sensorFault = false;
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

Expected Behavior

  • When the sensor value is between 0 and 100, the task marks the reading as valid.
  • When the value is outside the range, the task sets sensorFault to true.
  • faultCount records detected abnormal samples.
  • The task repeats its check every 100 milliseconds.
This is an educational range-checking example, not a complete safety mechanism. A production design needs defined fault latching, recovery, sensor diagnostics, concurrency protection and a safe-state response. The shared variables shown are illustrative and are not a general synchronization design.

17. Fault Handling State Machine

A state machine can organize fault detection and recovery behavior.

+----------+ | NORMAL | +----------+ | FAULT DETECTED | v +----------+ | FAULT | | DETECTED | +----------+ | ISOLATE FAULT | v +----------+ | RECOVERY | +----------+ / \ SUCCESS FAILURE | | v v +--------+ +-----------+ | NORMAL | | SAFE MODE | +--------+ +-----------+

The state machine should define:

  • Fault-detection conditions.
  • Fault severity and priority.
  • Maximum recovery attempts.
  • Recovery timeout.
  • Conditions for returning to normal operation.
  • Safe-state behavior when recovery fails.
  • Diagnostic information to retain.

18. Design Considerations

  1. Define the system's required functions and failure consequences.
  2. Identify hardware, software, timing and environmental faults.
  3. Define detection mechanisms for relevant faults.
  4. Separate fault detection from recovery decisions.
  5. Prevent one task from corrupting unrelated task data.
  6. Define bounded timeout and retry policies.
  7. Use watchdog supervision based on verified progress.
  8. Plan for memory exhaustion and stack overflow.
  9. Define safe states and recovery conditions.
  10. Test fault scenarios, not only normal operation.
  11. Record diagnostic information without creating new timing problems.
  12. Validate the design under realistic operating conditions.

21. Lesson Summary

  • Reliability describes failure-free operation over a specified period.
  • Availability describes the proportion of time a system can provide service.
  • A fault can produce an error, which may lead to system failure.
  • Fault detection, isolation and recovery are important reliability techniques.
  • Redundancy can improve fault tolerance when independence assumptions hold.
  • Graceful degradation preserves essential functions when some features fail.
  • Fail-safe systems prioritize a safe state; fail-operational systems prioritize continued service.
  • Watchdogs detect missing expected progress within a configured interval.
  • FreeRTOS mechanisms support reliable design but do not guarantee fault tolerance or safety certification.
