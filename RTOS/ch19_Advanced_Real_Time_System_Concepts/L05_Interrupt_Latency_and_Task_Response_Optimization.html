1. Learning Objectives

After completing this lesson, you will be able to:

  • Define interrupt latency and interrupt response time.
  • Understand the factors that affect interrupt latency.
  • Differentiate interrupt latency from task response time.
  • Understand context-switch overhead.
  • Analyze task response time and blocking.
  • Identify common sources of scheduling delay.
  • Apply practical techniques to optimize RTOS performance.
  • Understand timing measurement and its limitations.

2. Introduction

In a real-time embedded system, an event must be detected and processed within a specified time limit.

Examples include:

  • Detecting an emergency stop input.
  • Responding to a motor encoder pulse.
  • Receiving a communication packet.
  • Processing a timer expiration.
  • Handling an overcurrent fault.
  • Updating a control output at a fixed interval.

Two important timing properties are:

  • Interrupt latency: Time from an interrupt request becoming active to the beginning of its interrupt service routine.
  • Task response time: Time from a task's release or triggering event to completion of the required task operation.

3. Interrupt Latency

Interrupt latency is the delay between an interrupt request and the processor beginning execution of the corresponding interrupt service routine (ISR).

Interrupt Latency =
    ISR Entry Time - Interrupt Request Time
INTERRUPT REQUEST | | Interrupt latency | ISR EXECUTION BEGINS | | ISR execution time | ISR COMPLETES

Example

A timer interrupt request becomes active at 100 microseconds. The ISR begins at 104 microseconds.

Interrupt Latency = 104 - 100

                  = 4 microseconds

The measured interrupt latency is 4 microseconds for this observation.

A single measurement is not a worst-case latency guarantee. Worst-case analysis must consider all relevant interrupt masking, higher-priority interrupt activity, processor state and hardware behavior.

4. Factors Affecting Interrupt Latency

4.1 Interrupt Masking

If the processor masks an interrupt, the corresponding ISR cannot begin until the interrupt becomes eligible for service.

4.2 Higher-Priority Interrupts

An interrupt may be delayed by another interrupt that has higher priority or is already being serviced.

4.3 Current Processor State

The processor may need to complete or suspend the current instruction sequence and perform exception-entry operations.

4.4 Interrupt Controller Delay

Interrupt-controller arbitration, source routing and pending-state handling may contribute to the response delay.

4.5 Memory and Bus Wait States

Memory access delays and peripheral-bus behavior can affect interrupt entry and ISR execution.

4.6 Critical Sections

Long critical sections can delay eligible interrupts if the selected critical-section mechanism masks those interrupt sources.

FactorPossible Effect
Interrupt maskingDelays interrupt service.
Higher-priority ISRMay delay lower-priority ISR execution.
Long critical sectionMay increase interrupt response delay.
Memory wait statesMay increase entry and execution time.
Interrupt-controller processingAdds hardware-dependent delay.
Long ISR executionCan delay other interrupt and task processing.

5. Interrupt Response Time vs ISR Execution Time

These two measurements describe different parts of interrupt handling.

ParameterMeaning
Interrupt latencyRequest to ISR entry.
ISR execution timeISR entry to ISR completion.
Interrupt response timeRequest to completion of the required interrupt-level processing, as defined by the measurement boundary.
Interrupt Response Time =
    Interrupt Latency
  + ISR Execution Time

This simplified equation assumes the interrupt-level processing is completed entirely in that ISR and that the measurement ends at ISR completion.

Example

Interrupt Latency = 3 us
ISR Execution Time = 12 us

Interrupt Response Time =
    3 + 12

    = 15 us

6. Task Response Time

Task response time is the interval between a task's release and completion of the operation being analyzed.

Task Response Time =
    Task Completion Time - Task Release Time

It may include:

  • Release and interrupt-to-task notification delay.
  • Time spent waiting in the Ready state.
  • Preemption by higher-priority tasks.
  • Blocking on shared resources.
  • Execution time of the task itself.
EVENT OCCURS | INTERRUPT HANDLING | TASK BECOMES READY | SCHEDULING / READY QUEUE WAIT | TASK EXECUTION | POSSIBLE PREEMPTION OR BLOCKING | TASK OPERATION COMPLETES

Task response time is not the same as CPU execution time. A task can execute for 2 ms but take 8 ms from release to completion because it waits or is preempted.

7. Execution Time, Waiting Time and Response Time

TermDescription
Execution timeCPU time required by the analyzed task operation.
Waiting timeTime spent ready but not executing, or waiting for a resource/event, depending on the stated definition.
Blocking timeTime during which the task cannot proceed because it waits for a resource or condition.
Response timeElapsed time from release to completion.
DeadlineLatest permitted completion time relative to release.

Example

A task has the following timing:

ComponentTime
CPU execution2 ms
Ready-state waiting due to higher-priority work3 ms
Resource blocking1 ms
Response Time = 2 + 3 + 1

              = 6 ms

If its deadline is 8 ms, this example meets the deadline with 2 ms remaining margin, assuming the values are valid bounds and all relevant delays are included.

8. Context Switching Overhead

A context switch occurs when the processor stops executing one task and begins executing another task.

The RTOS may need to save the outgoing task's execution context and restore the incoming task's context.

TASK A RUNNING | SAVE TASK A CONTEXT | SCHEDULER DECISION | RESTORE TASK B CONTEXT | TASK B RUNNING

Context Information

  • Processor registers.
  • Stack pointer.
  • Program counter or return state.
  • Processor status information.
  • Additional port-specific task state.

Context-Switch Overhead

Context-switch overhead is the processor time consumed by saving and restoring task state and performing associated scheduling operations.

Frequent context switching can reduce useful CPU time and increase task response times.

The exact context saved and restored depends on the processor architecture, compiler, ABI and RTOS port. Do not assume every architecture saves identical register sets.

9. Causes of Excessive Context Switching

  • Very short task delays.
  • Unnecessary task yielding.
  • Excessive task creation and deletion.
  • Frequent task notifications and event signaling.
  • Too many tasks with similar priorities.
  • Poor task decomposition.
  • Excessive polling.

Optimization Approach

  • Use blocking APIs instead of continuous polling.
  • Combine closely related operations where appropriate.
  • Use queues and notifications efficiently.
  • Avoid unnecessary task wake-ups.
  • Choose suitable task priorities.
  • Measure context-switch frequency and execution overhead.

10. Task Scheduling Delay

A task can become Ready but may not execute immediately.

On a single-core fixed-priority preemptive RTOS, a Ready task generally waits while eligible higher-priority work executes, subject to scheduler and interrupt behavior.

Example

TaskPriorityExecution Time
Task A32 ms
Task B23 ms
Task C12 ms

Assume all three tasks become Ready simultaneously and the scheduler starts with no higher-priority work pending.

TIME (ms) 0 2 5 7 |-------|-----------|-------| A B C A: 0 - 2 ms B: 2 - 5 ms C: 5 - 7 ms

Task C has 2 ms of execution time but a response time of 7 ms from the common release instant.

11. Response-Time Analysis

Response-time analysis estimates whether a task can complete before its deadline under a defined scheduling model.

For a simplified single-processor, fixed-priority, preemptive task model, a common response-time recurrence is:

R_i = C_i + B_i
      + Σ ceil(R_i / T_j) × C_j

Where:

R_i = Worst-case response time of task i
C_i = Worst-case execution time of task i
B_i = Blocking time of task i
T_j = Period or minimum inter-arrival time
C_j = Execution time of higher-priority task j

The summation includes relevant higher-priority tasks under the analysis assumptions.

Important Assumptions

  • Single processor.
  • Fixed-priority preemptive scheduling.
  • Known task execution-time bounds.
  • Known periods or minimum inter-arrival times.
  • Blocking is bounded and modeled correctly.
  • Relevant interrupt interference and overhead are either included or analyzed separately.
This recurrence is a simplified fixed-priority response-time model. More complete analyses may include release jitter, self-suspension, interrupt interference, multiple blocking terms and other platform-specific effects.

Consider three periodic tasks on a single processor.

R1 = 1 ms

Task T2

R2 = C2 + ceil(R2 / T1) × C1

Initial value:
R2(0) = 1

Iteration 1:

      = 2 ms

Iteration 2:
R2(2) = 1 + ceil(2/4) × 1
      = 2 ms

Therefore:
R2 = 2 ms

Task T3

R3 = C3
   + ceil(R3/T1) × C1
   + ceil(R3/T2) × C2

Initial value:
R3(0) = 2

Iteration 1:
R3(1) = 2 + ceil(2/4) × 1
         + ceil(2/5) × 1
      = 4 ms

Iteration 2:
R3(2) = 2 + ceil(4/4) × 1
         + ceil(4/5) × 1
      = 4 ms

Therefore:
R3 = 4 ms

13. Priority Assignment and Response Optimization

Task priority affects how quickly a task receives CPU time when multiple tasks are Ready.

Priority Assignment Guidelines

  • Assign higher priority to tasks with stricter timing requirements where the scheduling policy supports that approach.
  • Consider task periods, deadlines and execution times.
  • Use rate-monotonic priority assignment for suitable periodic task sets with shorter periods receiving higher priorities.
  • Consider blocking and shared-resource access.
  • Prevent low-priority tasks from holding resources needed by critical tasks for excessive durations.
  • Analyze interrupt interference separately from task priority.
Assigning the highest priority to every important task is not a valid optimization strategy. It can create excessive interference and make lower-priority deadlines impossible to meet.

14. Critical Section Optimization

A critical section protects shared data or resources from conflicting concurrent access.

Excessively long critical sections can increase blocking and latency.

Recommended Practices

  • Keep protected operations short.
  • Avoid delays and blocking calls inside critical sections.
  • Do not perform lengthy calculations while interrupts are masked.
  • Use an appropriate synchronization primitive.
  • Copy shared data into a local buffer and process it outside the protected region when safe.
  • Document the maximum expected critical-section duration.

Illustrative Pseudocode

EnterCriticalSection();

localCopy = sharedData;

ExitCriticalSection();

/* Perform lengthy processing outside
   the protected section. */

ProcessData(localCopy);

The exact critical-section API and interrupt-masking behavior depend on the RTOS port and processor architecture.

15. ISR Optimization

An ISR should perform only the time-critical hardware operations required to acknowledge and capture the event.

Recommended ISR Structure

void Peripheral_ISR(void)
{
    uint32_t status;

    status = ReadInterruptStatus();

    AcknowledgeInterrupt(status);

    CaptureEssentialData(status);

    NotifyApplicationTaskFromISR();
}

The functions shown are placeholders, not portable FreeRTOS or LPC2129 API calls.

ISR Optimization Guidelines

  • Acknowledge the interrupt source correctly.
  • Capture essential data before it is lost.
  • Avoid lengthy loops.
  • Avoid blocking operations.
  • Avoid mutex operations.
  • Use supported ISR-safe queue or notification APIs.
  • Request a context switch on ISR exit when required by the port and a higher-priority task was unblocked.

16. FreeRTOS Techniques for Better Task Response

16.1 Task Notifications

Task notifications can efficiently signal a specific task without requiring a separate queue object for simple event signaling or notification values.

void SensorTask(void *pvParameters)
{
    uint32_t notificationValue;

    for (;;)
    {
        if (xTaskNotifyWait(
                0,
                0xFFFFFFFFUL,
                &notificationValue,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessSensorEvent(notificationValue);
        }
    }
}

This task blocks while waiting for a notification. The notification sender must use the appropriate task or ISR API for its execution context.

16.2 Blocking Instead of Polling

Blocking on a queue, semaphore or notification allows a task to wait without repeatedly consuming CPU time.

16.3 Appropriate Task Priorities

Priorities should reflect timing requirements and be validated through scheduling analysis.

16.4 Efficient Queue Design

Choose suitable item sizes and queue lengths. Avoid copying unnecessarily large structures when a carefully designed pointer-ownership scheme is more appropriate.

16.5 Static Allocation

Static task and queue allocation can reduce runtime allocation uncertainty and fragmentation risk, although memory sizing and stack requirements still need analysis.

17. Reducing Communication and Processing Delays

  • Use interrupt-driven reception instead of continuous polling where appropriate.
  • Use DMA for suitable large transfers.
  • Reduce unnecessary data copying.
  • Use suitable buffer sizes.
  • Keep parsing and processing outside ISRs.
  • Use bounded queue waits and timeout policies.
  • Give urgent messages an appropriate processing path.
  • Analyze bus contention and communication deadlines.

18. Timing Measurement and Profiling

Performance optimization should be based on measurement and analysis rather than assumptions.

Useful Measurement Methods

MethodPurpose
Hardware timerMeasure elapsed time with known resolution.
GPIO instrumentationObserve event-to-response timing with an external logic analyzer or oscilloscope.
RTOS run-time statisticsEstimate task CPU-time distribution.
Trace toolsInspect task switches, blocking and interrupt activity.
Cycle counterMeasure processor cycles where supported.

Measurement Example

start = ReadHardwareTimer();

/* Operation under test */

end = ReadHardwareTimer();

elapsed = end - start;

The timer's resolution, counter width, overflow behavior and read overhead must be accounted for.

Instrumentation changes execution behavior. Breakpoints, logging, tracing and GPIO operations can add overhead or alter timing. Use measurement methods appropriate to the required accuracy.

19. Worst-Case Execution Time (WCET)

Worst-Case Execution Time is a safe upper bound on the time required by a task or code segment under specified assumptions and operating conditions.

The largest execution time observed during testing is not automatically WCET.

WCET Analysis Considerations

  • Control-flow paths.
  • Loop bounds.
  • Memory and cache behavior, where applicable.
  • Processor and bus wait states.
  • Compiler optimization.
  • Interrupt interference.
  • Input-dependent execution paths.

WCET analysis is important for response-time and schedulability calculations.

20. LPC2129 and ARM7TDMI-S Considerations

The LPC2129 uses an ARM7TDMI-S core and a Vectored Interrupt Controller (VIC). Its interrupt and exception architecture differs from Cortex-M microcontrollers.

Important Points

  • ARM7TDMI-S supports IRQ and FIQ interrupt exceptions.
  • IRQ and FIQ have different processor-mode and register-banking behavior.
  • The LPC2129 VIC manages interrupt sources and vectored IRQ handling.
  • Interrupt response depends on processor state, masking, source configuration and current execution.
  • Do not apply Cortex-M NVIC, BASEPRI or Cortex-M-specific FreeRTOS interrupt-priority rules to LPC2129.

Keil Simulator Limitation

In a simulator-only workflow, you can inspect CPU execution, registers, memory and software timing behavior to the extent supported by the simulator.

However, simulated instruction timing and peripheral behavior must not be treated as proof of real hardware interrupt latency. Physical measurements require the actual target board and suitable instrumentation.

Problem: An interrupt request occurs at 250 microseconds. The ISR starts at 257 microseconds. Calculate interrupt latency.

Latency = 257 - 250

        = 7 microseconds

Answer: 7 microseconds.

22. Practical Exercise 2 – Task Response Time

Problem: A task requires 3 ms CPU execution, 2 ms ready-state waiting and 1 ms resource blocking. Calculate response time.

Response Time = 3 + 2 + 1

              = 6 ms

Answer: 6 ms.

23. Practical Exercise 3 – Deadline Analysis

Problem: A task has a worst-case response time of 7 ms and a relative deadline of 9 ms. Determine whether it meets its deadline.

Response Time = 7 ms
Deadline      = 9 ms

Margin = 9 - 7

       = 2 ms

Answer: It meets the deadline with a 2 ms margin, assuming the response-time bound is valid.

24. Practical Exercise 4 – Context-Switch Overhead

Problem: A system performs 500 context switches per second. Each context switch consumes 8 microseconds of processor time. Estimate the CPU time spent on context switching per second.

Total Time =
    500 × 8 microseconds

  = 4000 microseconds

  = 4 milliseconds

CPU Percentage =
    (4 / 1000) × 100

  = 0.4%

Answer: Approximately 0.4% of one CPU's time is consumed by the stated context-switch overhead, assuming the given cost is per switch.

25. Practical Exercise 5 – Response Optimization

Scenario: A high-priority sensor task frequently misses its deadline because it waits for a lower-priority communication task to release a shared resource.

Identify possible improvements:

  1. Reduce the duration of shared-resource ownership.
  2. Use an appropriate mutex with priority inheritance where supported.
  3. Consider a dedicated communication-owner task and message passing.
  4. Avoid blocking I/O while holding a mutex.
  5. Recalculate worst-case blocking and response time.
  6. Validate the solution under realistic load and fault conditions.

27. Lesson Summary

  • Interrupt latency is the delay from an interrupt request to ISR entry.
  • ISR execution time and interrupt latency are separate quantities.
  • Task response time includes execution and relevant waiting, blocking and interference.
  • Context switching introduces CPU overhead.
  • Long critical sections and ISRs can degrade real-time responsiveness.
  • Priority assignment must be supported by scheduling analysis.
  • FreeRTOS notifications, queues and blocking APIs can improve task coordination.
  • WCET requires a safe upper bound under defined assumptions.
  • Timing measurements must account for instrumentation overhead and hardware limitations.
