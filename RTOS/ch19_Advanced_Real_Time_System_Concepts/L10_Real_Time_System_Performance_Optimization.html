2. Introduction to Real-Time Performance Optimization

Real-time performance optimization is the process of improving execution efficiency, response time, resource utilization and predictability while preserving required functional and timing behavior.

A real-time system should not be optimized only for average speed. Its worst-case behavior, timing margins and deadline compliance are important.

Performance Parameters

ParameterMeaningOptimization Goal
CPU utilizationFraction of processor capacity used.Maintain adequate processing margin.
Response timeTime from event or release to task completion.Meet required response limits.
Execution timeProcessor time required by a task.Reduce unnecessary computation.
Interrupt latencyDelay from interrupt assertion to ISR entry.Keep latency bounded and predictable.
JitterVariation in timing.Reduce unwanted timing variation.
Memory usageRAM and program-memory consumption.Use resources efficiently and safely.
Power consumptionEnergy used during operation.Reduce energy while preserving deadlines.

3. CPU Utilization Optimization

CPU utilization represents the fraction of processor time used by tasks and other execution activities.

For independent periodic tasks on one processor:

U = Σ (Ci / Ti)

Where:

  • Ci = execution time of task i.
  • Ti = period of task i.
  • U = total utilization.

Example

TaskExecution TimePeriodUtilization
T11 ms5 ms20%
T22 ms10 ms20%
T32 ms20 ms10%
Total50%

Optimization Techniques

  • Remove unnecessary computations.
  • Reduce repeated calculations.
  • Use efficient algorithms and data structures.
  • Avoid excessive polling.
  • Use event-driven task activation.
  • Move non-critical work to lower-priority tasks.
  • Reduce unnecessary logging and diagnostic processing.
Low CPU utilization does not automatically prove schedulability. Deadlines, blocking, interrupt interference and workload assumptions must still be analyzed.

4. Task Execution-Time Optimization

Task execution time affects processor utilization and can influence response time for the task and other tasks.

Common Causes of Excessive Execution Time

  • Repeated calculations that could be reused.
  • Inefficient loops.
  • Unnecessary memory copying.
  • Expensive library operations.
  • Excessive floating-point calculations on processors without efficient floating-point hardware.
  • Long critical sections.
  • Blocking operations inside time-critical task paths.

Example: Repeated Calculation

Less efficient approach:

for (int i = 0; i < 100; i++)
{
    result[i] = input[i] * scale * calibration;
}

Improved approach:

float factor = scale * calibration;

for (int i = 0; i < 100; i++)
{
    result[i] = input[i] * factor;
}

The second approach calculates the constant factor once instead of repeatedly calculating it in the loop.

Compiler optimization and floating-point transformations can change numerical behavior. Verify accuracy, overflow limits and timing after every optimization.

5. Context-Switching Optimization

A context switch occurs when the processor saves the execution context of one task and restores another task's context.

Context-Switching Activities

  • Save registers and processor state.
  • Save the outgoing task's stack pointer.
  • Select the next eligible task.
  • Restore the incoming task's context.
  • Resume execution.

Reducing Unnecessary Context Switching

  • Avoid excessive task creation for short operations.
  • Use appropriate task priorities.
  • Avoid unnecessary yielding.
  • Use suitable blocking and notification mechanisms.
  • Combine closely related operations where appropriate.
  • Avoid excessive periodic task activation.
Context switching is necessary for multitasking. The objective is not to eliminate it, but to avoid unnecessary switching and excessive scheduling overhead.

6. Task Priority Optimization

Task priorities determine which ready task executes when multiple tasks compete for the processor.

Priority Design Guidelines

  • Analyze deadlines and response-time requirements.
  • Give time-critical tasks appropriate priority.
  • Consider interrupt interference and blocking.
  • Avoid giving every task the highest priority.
  • Keep lower-priority background work bounded.
  • Analyze starvation risks.
  • Use priority inheritance where supported and appropriate.

Example Task Set

TaskFunctionPriority
Control taskPeriodic control calculation.High
Communication taskProcess incoming commands.Medium
Logging taskStore diagnostic information.Low

Priority assignment must be justified by scheduling analysis, not merely by the apparent importance of a task.

7. Interrupt Latency Optimization

Interrupt latency is the time between an interrupt request becoming active and the processor beginning the corresponding ISR.

Factors Affecting Interrupt Latency

  • Interrupt masking duration.
  • Higher-priority interrupt activity.
  • Processor exception-entry behavior.
  • Memory and bus wait states.
  • Critical sections.
  • Nested interrupt configuration.

Optimization Techniques

  • Keep interrupt-disabled intervals short.
  • Use suitable interrupt priorities.
  • Avoid unnecessary interrupt masking.
  • Keep ISRs short and bounded.
  • Defer lengthy processing to tasks.
  • Avoid complex calculations in interrupt context.
  • Measure interrupt latency on target hardware.
INTERRUPT REQUEST | INTERRUPT LATENCY | ISR ENTRY | MINIMAL ISR WORK | SIGNAL / QUEUE | ISR EXIT | DEFERRED TASK WORK
Interrupt priority and RTOS task priority are different mechanisms. Exact interrupt-masking and ISR-to-task rules depend on the processor and FreeRTOS port.

8. Efficient Interrupt Service Routine Design

An ISR should perform only the work necessary to acknowledge the interrupt, capture essential information and arrange deferred processing.

Generic ISR Example

void Peripheral_IRQHandler(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the peripheral interrupt. */

    /* Capture the minimum required data. */

    xSemaphoreGiveFromISR(
        dataReadySemaphore,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(higherPriorityTaskWoken);
}

The corresponding task performs the longer processing after being unblocked.

This is generic FreeRTOS pseudocode. The peripheral acknowledgement, semaphore type, ISR API availability and yield macro must match the selected hardware and RTOS port. Do not copy Cortex-M interrupt-priority assumptions into an ARM7 application.

9. Memory Optimization

Memory optimization reduces RAM and program-memory consumption while maintaining safe operation.

Memory Areas

Memory AreaTypical Contents
FlashProgram code and constants.
SRAMGlobal variables, buffers, heap and stacks.
Task stackLocal variables, saved context and function-call data.
HeapDynamically allocated objects.
Peripheral memoryMemory-mapped hardware registers.

Memory Optimization Techniques

  • Remove unused variables and code.
  • Use suitable data types and alignment.
  • Reduce unnecessary buffer duplication.
  • Reuse buffers when ownership is clear.
  • Use static allocation where appropriate.
  • Size task stacks using measurement and analysis.
  • Avoid uncontrolled dynamic allocation in critical paths.
Do not reduce task stack sizes solely to save RAM. Stack overflow can corrupt adjacent memory and cause unpredictable system failures.

10. FreeRTOS Stack Optimization

Each FreeRTOS task has its own stack. Stack requirements depend on function-call depth, local variables, interrupt behavior and the processor port.

Stack Memory Calculation

Stack Memory (bytes)
    = Stack Depth × sizeof(StackType_t)

For example, if a task uses a stack depth of 256 elements and sizeof(StackType_t) is 4 bytes:

Stack Memory = 256 × 4
             = 1024 bytes

Stack High-Water-Mark API

UBaseType_t remaining;

remaining = uxTaskGetStackHighWaterMark(NULL);

The API reports the minimum unused stack observed since the task started, in stack elements. It is useful for stack analysis but does not prove that every execution path is safe.

Stack Optimization Process

  1. Start with a conservative stack allocation.
  2. Exercise representative and worst-case execution paths.
  3. Inspect stack high-water-mark measurements.
  4. Review compiler-generated stack usage where possible.
  5. Consider nested function calls and interrupt requirements.
  6. Retain an engineering safety margin.
  7. Repeat testing after software changes.

11. Heap Optimization

The FreeRTOS heap implementation affects dynamic memory allocation behavior.

HeapBehaviorImportant Consideration
heap_1Allocates memory but does not free it.Suitable for systems that allocate during initialization.
heap_2Supports allocation and freeing without adjacent-block coalescing.Can suffer fragmentation.
heap_3Wraps the C library malloc and free.Depends on the C library implementation.
heap_4Supports allocation, freeing and adjacent-block coalescing.Fragmentation is reduced but not eliminated.
heap_5Supports multiple non-contiguous memory regions and coalescing within regions.Requires correct region definition and memory layout.

Optimization Guidelines

  • Choose the heap implementation according to application needs.
  • Avoid repeated allocation and freeing in critical execution paths.
  • Use fixed-size memory pools for predictable allocation.
  • Check allocation failure.
  • Monitor free heap and minimum-ever-free heap where supported.
  • Use static allocation for objects with known lifetimes.
size_t freeHeap;
size_t minimumFreeHeap;

freeHeap = xPortGetFreeHeapSize();

minimumFreeHeap =
    xPortGetMinimumEverFreeHeapSize();
These heap-statistics APIs are not supported by every heap implementation. Confirm the selected FreeRTOS version and allocator before using them.

12. Communication Optimization

Communication between tasks and external devices can introduce CPU overhead, latency and memory consumption.

Common Optimization Techniques

  • Use queues for structured data transfer.
  • Use task notifications for suitable lightweight signaling.
  • Use DMA where supported and beneficial.
  • Reduce unnecessary data copying.
  • Choose suitable communication rates.
  • Use bounded buffers.
  • Batch non-urgent data where latency requirements permit.
  • Separate communication handling from critical control calculations.

Queue vs Task Notification

FeatureQueueTask Notification
Data transferCopies fixed-size items.Can carry a 32-bit value or signal, depending on notification mode.
Multiple receiversMultiple tasks can receive, subject to queue behavior.Notification is associated with a particular task.
Typical useStructured message communication.Lightweight signaling and simple data passing.
Resource useQueue control structure and item storage.Notification state is maintained in the receiving task's TCB.
A task notification is not a universal replacement for a queue. Choose the mechanism according to data ownership, receiver count and communication requirements.

13. Scheduling Overhead Optimization

Scheduling overhead includes the processor time used for task selection, context switching, tick processing and kernel bookkeeping.

Possible Improvements

  • Avoid unnecessarily high tick rates.
  • Use suitable task periods.
  • Reduce excessive task count where appropriate.
  • Avoid repeated task suspension and resumption without need.
  • Use blocking APIs instead of busy waiting.
  • Keep timer callbacks short.
  • Use tickless idle when supported and beneficial.

A higher tick frequency can improve nominal timing resolution but increases periodic interrupt and kernel overhead.

Reducing tick frequency changes timing resolution and conversion behavior. Recalculate task delays, timeouts and response-time assumptions before changing configTICK_RATE_HZ.

14. Blocking and Busy-Wait Optimization

Busy waiting repeatedly checks a condition while consuming processor time. Blocking allows a task to enter the Blocked state until an event or timeout occurs.

Busy-Wait Example

while (dataReady == 0)
{
    /* CPU repeatedly checks the variable. */
}

Event-Driven Alternative

if (xSemaphoreTake(
        dataReadySemaphore,
        portMAX_DELAY
    ) == pdTRUE)
{
    /* Process the available data. */
}

The blocking approach lets other Ready tasks execute while this task waits.

The event-driven design requires correct synchronization and event signaling. An indefinite wait is appropriate only if the application has a valid recovery policy for a missing event.

15. Power Optimization

Power optimization reduces energy consumption while preserving required system responsiveness.

Power Relationship

Power = Voltage × Current

Energy = Power × Time

Dynamic CMOS power is commonly approximated as:

Pdynamic ∝ C × V² × f

Where:

  • C = effective switched capacitance.
  • V = supply voltage.
  • f = switching frequency.

Power Optimization Techniques

  • Use sleep and low-power modes where supported.
  • Block tasks when they have no work.
  • Use tickless idle if the port supports it.
  • Disable unused peripherals safely.
  • Reduce unnecessary communication.
  • Use appropriate clock frequencies.
  • Consider wake-up latency in deadline analysis.
A low-power mode is not suitable if its wake-up latency, clock restoration or peripheral recovery time violates a real-time deadline.

16. Code Optimization and Compiler Settings

Compiler optimization can reduce execution time and code size, but it can also change timing and program behavior.

Common Compiler Optimization Levels

OptimizationTypical Effect
O0Minimal optimization; useful for debugging.
O1Basic optimization with moderate code transformation.
O2More aggressive optimization for performance.
OsOptimization focused on code size.
O3More aggressive performance optimization, where supported.

Exact options and behavior depend on the compiler.

Verification After Optimization

  • Check functional correctness.
  • Check numerical accuracy.
  • Measure execution time again.
  • Inspect stack usage.
  • Check interrupt and peripheral timing.
  • Verify worst-case execution paths.
Do not use volatile as a substitute for synchronization. It does not guarantee atomic access, mutual exclusion or inter-task ordering.

17. Profiling and Performance Measurement

Profiling collects information about program execution to identify performance bottlenecks.

Common Profiling Methods

  • Execution-time measurement.
  • CPU utilization monitoring.
  • Task runtime statistics.
  • Stack high-water-mark inspection.
  • Trace recording.
  • Hardware timer measurements.
  • Logic-analyzer or oscilloscope measurements on physical hardware.

Measurement Workflow

RUN APPLICATION | COLLECT METRICS | IDENTIFY BOTTLENECK | APPLY OPTIMIZATION | MEASURE AGAIN | VERIFY DEADLINES | ACCEPT / REVISE

Profiling should be performed under representative and stress workloads, not only during idle operation.

18. FreeRTOS Runtime Statistics

FreeRTOS provides optional runtime-statistics facilities that can help estimate the processor time spent by individual tasks.

Relevant Configuration

#define configGENERATE_RUN_TIME_STATS 1

#define portCONFIGURE_TIMER_FOR_RUN_TIME_STATS() \
        ConfigureRuntimeTimer()

#define portGET_RUN_TIME_COUNTER_VALUE() \
        ReadRuntimeCounter()

The timer setup and counter-reading functions are application- and port-specific.

Related APIs

  • uxTaskGetSystemState()
  • vTaskGetRunTimeStats()
  • TaskStatus_t

These facilities can report task execution statistics when correctly configured.

Runtime statistics need a suitable independent time base, adequate resolution and wraparound handling. Measurement overhead must be considered. Runtime percentages do not prove WCET or schedulability.

19. Trace and Debugging Optimization

Tracing records execution events such as task switches, task states, interrupts and synchronization activity.

Benefits

  • Identify unexpected task blocking.
  • Inspect scheduling behavior.
  • Find priority-related problems.
  • Analyze task interactions.
  • Identify excessive context switching.
  • Investigate timing anomalies.

FreeRTOS trace support may use configuration such as:

#define configUSE_TRACE_FACILITY 1

Additional trace hooks and tools depend on the FreeRTOS version and integration.

Tracing can perturb execution by consuming CPU time and memory. Record its overhead and repeat final timing verification with the production measurement configuration.

20. Benchmarking

Benchmarking compares performance under defined and repeatable conditions.

Typical Metrics

MetricWhat It Measures
Execution timeTime required for a defined operation.
Response timeRelease-to-completion delay.
Interrupt latencyInterrupt request-to-ISR-entry delay.
Context-switch timeTime spent switching task contexts.
Memory footprintRAM and Flash usage.
Energy per operationEnergy consumed to perform a defined operation.

Good Benchmarking Practice

  • Define the measurement start and end points.
  • Document hardware and compiler settings.
  • Use representative input data.
  • Include worst-case and stress conditions.
  • Repeat measurements.
  • Record measurement uncertainty and overhead.
  • Compare results against explicit requirements.

21. Optimization of a Motor Control System

Consider an RTOS-based motor controller with sensor acquisition, control calculations, communication and logging tasks.

MOTOR FEEDBACK | SENSOR ACQUISITION | CONTROL CALCULATION | PWM COMMAND | MOTOR DRIVE | +---------+---------+ | | COMMUNICATION LOGGING | | STATUS DATA DIAGNOSTICS

Performance Problems

  • Sensor acquisition blocks for too long.
  • Control calculations use excessive processor time.
  • Communication traffic delays control processing.
  • Logging consumes excessive memory.
  • Long interrupt handlers delay task activation.

Optimization Strategy

  1. Keep sensor ISR processing minimal.
  2. Notify the control task when fresh data is available.
  3. Bound the control calculation execution time.
  4. Assign priorities based on timing analysis.
  5. Use queues for status communication.
  6. Run logging as bounded background work.
  7. Measure control response and deadline margin.
  8. Validate the system under maximum communication load.

24. Practical Exercise 3 – Busy Waiting vs Blocking

Objective: Compare CPU usage in polling and event-driven designs.

Task A – Polling

for (;;)
{
    if (sensorReady())
    {
        processSensor();
    }
}

Task B – Blocking

for (;;)
{
    if (xSemaphoreTake(
            sensorReadySemaphore,
            portMAX_DELAY
        ) == pdTRUE)
    {
        processSensor();
    }
}

Expected result: Task B can block while waiting for the event, allowing other Ready tasks to execute. Its event source and recovery policy must be correctly implemented.

27. Keil uVision and LPC2129 Study

Objective: Understand which performance measurements can be studied in a simulation environment.

Possible Simulator Activities

  • Inspect program execution and CPU registers.
  • Study instruction-level behavior where supported.
  • Inspect variables and memory usage.
  • Compare different algorithm implementations.
  • Review generated assembly and compiler output.
  • Study task code if a compatible RTOS port is available.

Measurements Requiring Hardware Validation

  • Actual interrupt response under electrical conditions.
  • Physical UART, SPI, I2C and CAN timing.
  • Real power consumption.
  • Peripheral wake-up timing.
  • Electrical noise and signal-integrity effects.
  • Actual target-system worst-case timing.
The LPC2129 uses ARM7TDMI-S. Confirm FreeRTOS port and Keil integration before attempting RTOS simulation. Simulator measurements must not be presented as proof of physical target performance.

28. Performance Optimization Best Practices

  1. Optimize only after measuring the actual bottleneck.
  2. Preserve timing requirements while improving average performance.
  3. Use defensible WCET estimates.
  4. Keep interrupt handlers short and bounded.
  5. Minimize unnecessary context switching.
  6. Use blocking synchronization instead of uncontrolled polling.
  7. Allocate memory predictably.
  8. Keep critical sections short.
  9. Use suitable task priorities.
  10. Recheck stack and heap usage after changes.
  11. Measure power and wake-up latency.
  12. Retest under worst-case workload.
  13. Document optimization results and assumptions.

30. Lesson Summary

  • Real-time performance includes timing, resource efficiency and predictability.
  • CPU utilization helps estimate processor demand.
  • Execution-time optimization should focus on measured bottlenecks.
  • Unnecessary context switches and scheduling overhead should be minimized.
  • Interrupt handlers should be short and bounded.
  • Memory optimization must preserve stack and heap safety.
  • Blocking and event-driven designs can reduce busy-waiting.
  • Runtime statistics and trace tools help analyze task behavior.
  • Power optimization must account for wake-up and response latency.
  • Every optimization must be followed by functional and timing verification.
  • Final performance claims require evidence from the actual target platform.
