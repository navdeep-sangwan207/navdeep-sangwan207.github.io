2. Introduction to Watchdog Timers

A watchdog timer is a monitoring mechanism that detects when software fails to perform an expected operation within a specified time.

It is commonly used in embedded systems to recover from conditions such as:

  • Software deadlock.
  • Infinite loops.
  • Unexpected task blocking.
  • Control-task failure.
  • Processor execution getting stuck.
  • Failure to complete a required processing cycle.

A watchdog typically requires the application to periodically refresh, service or kick the timer. If the expected refresh does not occur before timeout, the watchdog triggers a configured response.

APPLICATION | NORMAL EXECUTION | REFRESH WATCHDOG | RESTART COUNTDOWN | APPLICATION FAILURE? / \ NO YES | | KEEP RUNNING TIMEOUT OCCURS | RESET OR FAULT ACTION

3. Why Is a Watchdog Needed?

Embedded systems may operate continuously for long periods. A software fault can prevent normal execution even if the processor and power supply remain active.

Example: Industrial Temperature Controller

Consider a controller that reads a temperature sensor and controls a cooling fan.

ConditionPossible System Behavior
Normal executionTemperature is read and fan control is updated.
Control task deadlockFan command may no longer be updated.
Communication task stuckRemote monitoring may stop receiving data.
Unexpected infinite loopApplication may stop making progress.
Watchdog timeoutHardware may reset the processor or trigger another configured response.
A watchdog reset does not automatically guarantee a safe physical state. Outputs, actuators and external hardware must be designed to enter a safe condition independently where required.

4. Types of Watchdog Timers

4.1 Hardware Watchdog

A hardware watchdog is implemented inside a microcontroller or as a separate external circuit.

  • Runs independently of normal application execution.
  • Uses a hardware timer or oscillator.
  • Can detect certain processor software failures.
  • May reset the processor when the timeout expires.

4.2 Software Watchdog

A software watchdog is implemented using an RTOS timer, task or software counter.

  • Monitors task activity.
  • Detects missed software deadlines.
  • Can identify stalled application modules.
  • Can initiate recovery procedures.
Hardware WatchdogSoftware Watchdog
Uses independent hardware timing.Depends on software execution and scheduling.
Can reset the processor.Usually reports or handles application-level faults.
Can remain active when application code is stuck.May stop working if its monitoring task cannot execute.
Hardware-specific configuration.Implemented using RTOS or application mechanisms.

5. Basic Hardware Watchdog Operation

A basic watchdog counts toward a timeout. The application periodically refreshes it before the timeout expires.

WATCHDOG INITIALIZATION | LOAD TIMEOUT | START TIMER | APPLICATION EXECUTES | VALID REFRESH? / \ YES NO | | RELOAD TIMEOUT COUNTER | | v | RESET | CONTINUE

5.1 Important Operations

OperationDescription
InitializeConfigure watchdog clock, timeout and response.
StartEnable watchdog counting.
Refresh / KickReload or service the watchdog before timeout.
TimeoutIndicates that the expected refresh was not received in time.
ResetHardware may reset the processor if configured to do so.

6. Watchdog Timeout Calculation

The watchdog timeout must be longer than the maximum legitimate interval between valid refresh operations, including scheduling delays and timing tolerances.

Example

Assume:

  • Control cycle execution: 40 ms.
  • Maximum expected scheduling delay: 15 ms.
  • Additional engineering margin: 25 ms.
Minimum Design Timeout =
    40 + 15 + 25

Minimum Design Timeout = 80 ms

A nominal watchdog timeout greater than 80 ms may be selected after accounting for hardware tolerance, worst-case timing and the system's fault-detection requirements.

Do not choose a watchdog timeout only from average execution time. Use a justified worst-case timing budget and verify it under the required operating conditions.

7. Watchdog Refresh

Refreshing the watchdog tells the watchdog hardware that the application has reached an expected point in its execution.

Illustrative Hardware-Specific Interface

void WatchdogRefresh(void)
{
    /*
      Write the hardware-specific refresh
      sequence to the watchdog register.
    */
}

The actual register sequence, key values and timing rules depend on the microcontroller.

Correct Refresh Strategy

  • Refresh only after required system operations have completed.
  • Check critical task health before refreshing.
  • Use a defined supervision period.
  • Record watchdog reset causes where hardware supports it.
  • Do not refresh unconditionally from an unrelated timer interrupt.
If a periodic interrupt refreshes the watchdog regardless of application health, a deadlocked control task may remain undetected because the interrupt can continue running.

8. Windowed Watchdog Timer

A windowed watchdog accepts refresh operations only during a specified time window.

Refreshing too early or too late can trigger a watchdog fault.

REFRESH TIME AXIS |---------|-------------|---------| START OPEN CLOSE TIMEOUT WINDOW WINDOW Too early Valid refresh Too late X OK X

Example

Assume a watchdog accepts refresh between 20 ms and 80 ms after the previous valid refresh.

Refresh TimeResult
10 msToo early – invalid.
35 msValid refresh.
65 msValid refresh.
90 msToo late – timeout condition.

Why Use a Windowed Watchdog?

  • Detects excessively early refresh operations.
  • Can reveal unexpected execution paths.
  • Helps detect some timing-control faults.
  • Provides stronger supervision than a simple timeout watchdog in suitable designs.
The exact window boundaries and fault behavior are defined by the watchdog hardware. Some devices use different timing conventions.

9. Software Watchdog in an RTOS

An RTOS application may contain several tasks. A software watchdog supervisor checks whether important tasks are making progress.

Example Task Architecture

RTOS APPLICATION | +------------+------------+ | | | SENSOR TASK CONTROL TASK COMM TASK | | | HEARTBEAT HEARTBEAT HEARTBEAT | | | +------------+------------+ | SUPERVISOR TASK | CHECK EXPECTED ACTIVITY | +--------+--------+ | | HEALTHY FAILURE | | SERVICE HW WD FAULT RESPONSE

Each monitored task reports progress. The supervisor checks whether all required tasks have reported within their expected monitoring intervals.

10. Task Heartbeat Monitoring

A heartbeat is a signal indicating that a task has reached a defined point in its execution.

Illustrative FreeRTOS Example

#include "FreeRTOS.h"
#include "task.h"
#include <stdint.h>

volatile uint32_t sensorHeartbeat = 0;
volatile uint32_t controlHeartbeat = 0;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read and validate sensor data. */

        sensorHeartbeat++;

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void ControlTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform control processing. */

        controlHeartbeat++;

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

The supervisor can observe heartbeat changes over a monitoring interval.

A heartbeat counter incremented unconditionally at the beginning of a task loop does not prove that the task completed its critical work. Place progress reporting after the operations that must be verified.

11. Software Watchdog Supervisor Example

Objective: Demonstrate basic task-progress monitoring using a supervisor task.

Program

#include "FreeRTOS.h"
#include "task.h"
#include <stdint.h>
#include <stdbool.h>

volatile uint32_t sensorHeartbeat = 0;
volatile uint32_t controlHeartbeat = 0;

static uint32_t previousSensorHeartbeat = 0;
static uint32_t previousControlHeartbeat = 0;

void SupervisorTask(void *pvParameters)
{
    bool sensorHealthy;
    bool controlHealthy;

    for (;;)
    {
        vTaskDelay(pdMS_TO_TICKS(500));

        sensorHealthy =
            (sensorHeartbeat != previousSensorHeartbeat);

        controlHealthy =
            (controlHeartbeat != previousControlHeartbeat);

        previousSensorHeartbeat = sensorHeartbeat;
        previousControlHeartbeat = controlHeartbeat;

        if (sensorHealthy && controlHealthy)
        {
            /*
              In a real system, service the
              hardware watchdog only after
              all required health checks pass.
            */
        }
        else
        {
            /*
              Record the fault and initiate
              the defined fault response.
            */
        }
    }
}

Expected Behavior

  • The supervisor waits for its monitoring interval.
  • It checks whether both heartbeat counters have changed.
  • If both have progressed, the monitored tasks pass this basic check.
  • If either has not progressed, a fault is recorded.
This is a teaching example, not a production-ready watchdog. A single counter change does not prove timely completion, correct output or correct execution. Use atomic or RTOS-protected data access as required by the target architecture. A robust design also needs per-task deadlines, stale-heartbeat handling, startup grace periods and a safe recovery policy.

12. Watchdog Integration with FreeRTOS

FreeRTOS does not automatically configure or service a microcontroller's hardware watchdog. The application must integrate the watchdog driver with the task architecture.

Recommended Architecture

  1. Initialize the hardware watchdog according to the device manual.
  2. Create the critical application tasks.
  3. Define what constitutes successful progress for each task.
  4. Have each task report progress after completing its required work.
  5. Run a supervisor task at an appropriate priority.
  6. Check task health and timing constraints.
  7. Refresh the hardware watchdog only when the required conditions are satisfied.
  8. Use a defined response when a monitored task fails.
  9. Capture reset cause and diagnostic information after recovery.

Illustrative Pseudocode

void WatchdogSupervisorTask(void *pvParameters)
{
    for (;;)
    {
        if (AllCriticalTasksHealthy() &&
            TimingConstraintsSatisfied())
        {
            HardwareWatchdogRefresh();
        }
        else
        {
            RecordSystemFault();

            /*
              Do not report a healthy system.
              Apply the defined fault policy.
            */
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

Functions such as AllCriticalTasksHealthy() and HardwareWatchdogRefresh() are application- and hardware-specific placeholders.

13. Watchdog and Task Priority

The supervisor task must receive enough CPU time to perform its checks without unnecessarily interfering with critical application tasks.

TaskExample PriorityPurpose
ControlTask4Performs time-critical control processing.
SensorTask3Acquires and validates sensor data.
SupervisorTask2Checks task health and watchdog conditions.
CommunicationTask1Handles non-critical communication.

These priority values are illustrative. The correct priority assignment depends on task deadlines, execution times, blocking and system scheduling analysis.

A high-priority supervisor can itself interfere with application deadlines. Watchdog supervision must be included in the system's timing and schedulability analysis.

14. Watchdog Reset and Fault Diagnosis

When a watchdog reset occurs, the application should identify the reset source and collect useful diagnostic information where possible.

Useful Diagnostic Information

  • Reset-cause register.
  • Last known application state.
  • Fault code.
  • Task health status.
  • Last successful control-cycle timestamp or counter.
  • Relevant error counters.
  • Persistent fault log, if available and safe to use.

Recovery Sequence

PROCESSOR RESET | READ RESET CAUSE | INITIALIZE HARDWARE | VALIDATE CONFIGURATION | RESTORE SAFE OUTPUTS | START APPLICATION | SELF-TEST AND MONITOR | NORMAL OPERATION

Startup logic should avoid repeatedly restarting into the same unsafe failure condition. A system may need a latched fault state, restricted operating mode or maintenance intervention.

16. Practical Exercise – Watchdog Timeout Calculation

Problem: A real-time control application has the following timing requirements:

ParameterValue
Maximum control processing time30 ms
Maximum scheduling delay10 ms
Maximum communication blocking allowance5 ms
Additional timing margin25 ms

Solution

Required Timing Budget =
    30 + 10 + 5 + 25

Required Timing Budget = 70 ms

A watchdog timeout must be selected to accommodate the justified worst-case interval between valid refresh operations. The final value must also satisfy the system's maximum fault-detection time.

17. Practical Exercise – Detect a Stalled Task

Problem: A control task should complete one control cycle every 100 ms. The supervisor observes no new completion report for 300 ms.

Questions

  1. What condition should the supervisor identify?
  2. Should it continue refreshing the watchdog?
  3. What diagnostic information should be recorded?

Suggested Answer

  1. The control task has failed its expected progress deadline.
  2. The supervisor should not report the system as healthy. It should follow the defined fault policy, which may allow the hardware watchdog to expire.
  3. Record the task identifier, last completion time, fault code, system state and relevant sensor or communication status.

19. Lesson Summary

  • A watchdog detects failure to perform expected activity within a defined time.
  • Hardware watchdogs can operate independently of application task execution.
  • Software watchdogs monitor application-level progress.
  • Watchdog timeout selection must consider worst-case timing and fault-detection requirements.
  • Windowed watchdogs detect both early and late refresh operations.
  • RTOS supervisors can monitor the health of multiple tasks.
  • Heartbeat reports should represent meaningful task progress.
  • Watchdog servicing should be conditional on required system health checks.
  • Reset-cause logging and safe startup behavior improve fault diagnosis.
