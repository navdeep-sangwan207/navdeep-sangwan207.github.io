2. Introduction to Low-Power RTOS Design

Low-power design aims to reduce the electrical energy consumed by an embedded system while maintaining its required functionality and real-time performance.

Power management is particularly important in:

  • Battery-powered embedded devices.
  • Wireless sensor networks.
  • Portable medical equipment.
  • Industrial monitoring systems.
  • Wearable electronics.
  • Remote monitoring and IoT devices.

Why Reduce Power Consumption?

  • Extend battery operating time.
  • Reduce heat generation.
  • Improve energy efficiency.
  • Reduce cooling requirements.
  • Increase system operating lifetime where battery replacement is difficult.

3. Power and Energy Fundamentals

3.1 Electrical Power

Electrical power is the rate at which electrical energy is consumed.

P = V × I

Where:

  • P = power in watts.
  • V = voltage in volts.
  • I = current in amperes.

3.2 Energy Consumption

E = P × t

Where E is energy, P is average power and t is operating time.

3.3 Average Power

For a system operating in multiple power states:

Pavg = (P1 × t1 + P2 × t2 + ... + Pn × tn) / T

Here, T is the total observation period and each state has its own power and duration.

4. Processor Power Modes

Microcontrollers commonly provide multiple power states. Exact names and behavior depend on the device.

Power ModeTypical Behavior
Run ModeCPU and selected peripherals operate normally.
Idle ModeCPU execution stops or pauses while selected clocks and peripherals remain active.
Sleep ModeCPU or selected clock domains are stopped; wake-up sources remain available.
Deep SleepMore clock domains or peripherals are disabled to reduce current.
Standby / Power-DownMost circuitry is disabled while selected wake-up and retention features remain active.
Power-mode names are not standardized across all microcontrollers. Always consult the target device datasheet and reference manual for exact retention, wake-up and clock behavior.

5. RTOS Power Consumption

An RTOS application can consume power even when application tasks have no useful work to perform.

Sources of Unnecessary Activity

  • Frequent periodic task wake-ups.
  • Continuous polling loops.
  • High-frequency system ticks.
  • Unnecessary peripheral operation.
  • Excessive communication activity.
  • Unnecessary memory and bus accesses.

Example: Polling vs Blocking

Polling approach:

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        if (SensorDataReady())
        {
            ProcessSensorData();
        }
    }
}

This task continuously checks the sensor and may prevent the processor from entering a low-power state.

Blocking approach:

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        WaitForSensorEvent();

        ProcessSensorData();
    }
}

In a real implementation, WaitForSensorEvent() should block using a suitable RTOS synchronization mechanism or hardware event mechanism. The task can remain Blocked until the event occurs.

Event-driven designs generally provide better opportunities for low-power operation than continuous polling.

6. FreeRTOS Idle Task

FreeRTOS automatically creates an Idle task when the scheduler starts.

The Idle task executes when no other task is Ready to run.

Functions of the Idle Task

  • Provides processor time when application tasks are blocked or suspended.
  • Performs kernel housekeeping, including deferred cleanup of dynamically allocated task resources.
  • Can execute an application-defined Idle Hook when configured.

Idle Hook

An Idle Hook is an application callback that executes while the Idle task runs.

void vApplicationIdleHook(void)
{
    /*
      Optional low-power operation may be
      performed here when the selected
      processor port supports it.
    */
}

Configuration commonly includes:

#define configUSE_IDLE_HOOK 1
The Idle Hook must not block or call APIs that block. It should be short and must not interfere with kernel housekeeping. Do not assume that entering a CPU sleep instruction from the hook is safe without checking the port's synchronization requirements.

7. Tick Interrupt and Power Consumption

FreeRTOS normally uses a periodic tick interrupt to maintain time and schedule task delays.

For example, with a tick rate of 1000 Hz:

Tick Frequency = 1000 Hz

Tick Period = 1 / 1000

Tick Period = 0.001 seconds
            = 1 millisecond

The periodic interrupt can wake the processor even when no application task needs to execute.

Potential Effects

  • Increased processor wake-ups.
  • Additional interrupt processing.
  • Reduced time available for deep sleep.
  • Increased energy consumption in applications with long idle periods.

8. Tickless Idle in FreeRTOS

Tickless idle reduces unnecessary periodic tick interrupts during extended idle periods.

Instead of waking for every normal tick, the RTOS can suppress periodic ticks temporarily and arrange a wake-up near the next required timeout.

ALL APPLICATION TASKS BLOCKED | IDLE PERIOD | DETERMINE NEXT TIMEOUT | SUPPRESS TICK EVENTS | ENTER LOW-POWER STATE | HARDWARE WAKE-UP EVENT | RECONSTRUCT ELAPSED TICKS | RESUME SCHEDULING

Benefits

  • Reduces unnecessary tick interrupts.
  • Increases the duration of idle periods.
  • Creates opportunities for deeper sleep modes.
  • Can reduce average power consumption.

Configuration

#define configUSE_TICKLESS_IDLE 1

The actual implementation requires support from the selected FreeRTOS port and hardware timer.

Setting configUSE_TICKLESS_IDLE alone does not guarantee correct low-power operation. The port must implement the required tick suppression, elapsed-time compensation and low-power entry/exit behavior.

9. FreeRTOS Tickless Idle Example – Concept

Consider a system where the next task timeout is expected after 500 milliseconds.

Normal Tick OperationTickless Idle Operation
Periodic tick interrupt continues at the configured frequency.Periodic tick interrupts are suppressed during the permitted idle interval.
CPU may wake repeatedly.CPU can remain asleep for a longer interval.
Each tick is processed normally.Elapsed time is accounted for when execution resumes.

For a nominal 1 kHz tick, a 500 ms interval corresponds to 500 nominal tick periods. The actual suppressed interval is limited by the next required timeout, hardware timer range, interrupt events and port implementation.

10. FreeRTOS Tickless Idle Port Configuration

Tickless idle is a port-level feature. A typical configuration may contain:

#define configUSE_TICKLESS_IDLE 1

/* Optional application threshold */
#define configEXPECTED_IDLE_TIME_BEFORE_SLEEP 2

The expected-idle-time threshold is available in applicable FreeRTOS versions and configurations. Its exact use should be checked against the selected kernel release.

A port may provide or require functions and hooks for:

  • Suppressing the periodic tick source.
  • Configuring a wake-up timer.
  • Entering a processor-specific sleep state.
  • Measuring elapsed sleep time.
  • Correcting the kernel tick count after wake-up.
The low-power implementation is processor- and port-specific. A generic application cannot safely substitute arbitrary sleep instructions for the port's tickless-idle implementation.

11. Task-Level Power Management

Tasks should be designed to spend as much time as practical in the Blocked state when no work is available.

Recommended Techniques

  • Use queues instead of continuous polling.
  • Use task notifications for event signaling.
  • Use semaphores for synchronization.
  • Use appropriate blocking timeouts.
  • Avoid unnecessary periodic wake-ups.
  • Batch operations when latency requirements permit.
  • Keep background processing efficient.

Example – Event-Driven Task

void DataProcessingTask(void *pvParameters)
{
    uint32_t notificationValue;

    for (;;)
    {
        if (xTaskNotifyWait(
                0,
                0xFFFFFFFFUL,
                &notificationValue,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessReceivedData(notificationValue);
        }
    }
}

The task blocks until it receives a notification. The notification value can carry a 32-bit value or event bits according to the selected notification action.

12. Peripheral Power Management

Peripheral modules can consume power even when the CPU is idle.

Common Peripheral Management Techniques

PeripheralPower-Saving Technique
ADCDisable conversion when measurements are not required.
UARTDisable unused communication interfaces and clocks where supported.
SPI / I2CDisable or reduce activity when no transaction is required.
TimersStop unused timer modules.
DisplayReduce refresh activity or enter display sleep mode.
RadioUse sleep, receive and transmit states appropriately.
SensorsUse standby or duty-cycled measurement modes.

Peripheral Management Sequence

void EnterPeripheralLowPowerMode(void)
{
    StopUnnecessaryADC();
    DisableUnusedUART();
    StopUnusedTimers();

    /*
      Hardware-specific peripheral
      power controls belong here.
    */
}

These functions are illustrative placeholders. Peripheral shutdown must not interrupt an active DMA transfer, communication transaction or required safety function.

13. Clock Management and Dynamic Frequency Scaling

Dynamic frequency scaling changes the processor clock frequency according to system workload.

Reducing clock frequency can reduce dynamic power consumption, although the actual savings depend on voltage, clock architecture and other circuit behavior.

A simplified dynamic power relationship is:

Pdynamic ∝ C × V² × f

Where:

  • C = effective switched capacitance.
  • V = supply voltage.
  • f = switching frequency.

Example

If voltage and effective capacitance remain unchanged and frequency is reduced to half:

New Dynamic Power ≈ 0.5 × Original Power

This is an idealized relationship for dynamic power, not a prediction of total board power. Static power, peripheral consumption and regulator losses also contribute.

Changing clock frequency can affect peripheral baud rates, timer periods, RTOS tick configuration and control-loop timing. Clock changes must be coordinated with the entire system.

14. Power Management and Real-Time Constraints

Power-saving operations introduce wake-up latency and may affect deadline satisfaction.

ParameterMeaning
Sleep Entry TimeTime required to enter a low-power state.
Wake-Up LatencyTime required to resume the required operation.
Clock StabilizationTime needed for clocks or oscillators to become valid.
Peripheral RestorationTime required to restore peripheral configuration.
Response TimeTime from the relevant event or release to completion of the required response.

The total wake-up and restoration delay must be included in response-time and deadline analysis.

Design Rule

Do not enter a power state whose wake-up and restoration latency makes the next required deadline impossible to meet.

15. Exercise 1 – Average Power Calculation

Problem: An embedded device operates in two states:

StatePowerDuration
Run100 mW2 seconds
Sleep10 mW8 seconds

Solution

Total Energy =
    (100 × 2) + (10 × 8)

    = 200 + 80
    = 280 mJ

Total Time = 2 + 8
           = 10 seconds

Average Power = 280 / 10
              = 28 mW

Answer: Average power consumption is 28 mW.

16. Exercise 2 – Energy Saving

Problem: A controller consumes 80 mW continuously. After implementing a suitable sleep strategy, it consumes 80 mW for 20% of the time and 8 mW for the remaining 80%.

Solution

Average Power =
    (80 × 0.20) + (8 × 0.80)

    = 16 + 6.4

    = 22.4 mW

Power Reduction =
    ((80 - 22.4) / 80) × 100

    = 72%

Answer: The theoretical average power reduction is 72%, assuming the stated power levels and time fractions.

17. Exercise 3 – Tickless Idle Decision

Problem: All application tasks are blocked. The next task is scheduled to wake after 300 ms. The port supports tickless idle.

Questions

  1. Why can tickless idle be useful?
  2. What happens to periodic tick interrupts during the permitted idle interval?
  3. What must happen when the processor wakes?

Suggested Answer

  1. It can reduce unnecessary periodic wake-ups and allow a longer low-power interval.
  2. The port suppresses the normal periodic tick for the selected interval.
  3. The port accounts for elapsed time and resumes normal scheduling.

18. Exercise 4 – Power vs Deadline

Problem: A processor enters deep sleep. Wake-up and clock restoration require 12 ms. A critical response must complete within 10 ms after an external event.

Solution

Wake-Up Latency = 12 ms
Deadline        = 10 ms

12 ms > 10 ms

Answer: The selected deep-sleep state cannot meet this deadline if the response depends on completing that 12 ms wake-up sequence first.

The designer must select a faster wake-up state, keep the required hardware active or redesign the event-response architecture.

19. Practical Design Exercise – Low-Power Sensor Node

Objective: Design an RTOS architecture for a battery-powered sensor node.

Requirements

  • Read a sensor once every 5 seconds.
  • Process the measurement.
  • Transmit data when required.
  • Remain in a low-power state between operations.
  • Detect sensor and communication failures.

Suggested Architecture

PERIODIC WAKE-UP | SENSOR TASK | VALIDATE DATA | PROCESS MEASUREMENT | TRANSMIT IF REQUIRED | BLOCK ALL TASKS | TICKLESS IDLE / SLEEP | NEXT WAKE-UP

Design Considerations

  1. Use an appropriate timer or hardware wake-up source.
  2. Use event-driven task communication.
  3. Disable unused peripherals.
  4. Minimize sensor and radio active time.
  5. Include wake-up latency in deadline analysis.
  6. Monitor battery voltage where required.
  7. Provide watchdog and fault-recovery behavior.

20. Important Low-Power Design Practices

  • Prefer event-driven processing over continuous polling.
  • Allow tasks to enter the Blocked state when idle.
  • Use tickless idle when supported and appropriate.
  • Disable unused peripheral clocks and modules.
  • Choose sleep modes according to wake-up requirements.
  • Minimize unnecessary memory and bus activity.
  • Use efficient communication and data batching where possible.
  • Consider clock and voltage scaling where supported.
  • Measure actual current consumption on target hardware.
  • Verify that power transitions do not violate real-time deadlines.
