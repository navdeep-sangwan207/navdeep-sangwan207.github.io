2. Introduction to Hard Real-Time Systems

A hard real-time system is a system in which specified timing constraints are mandatory. Missing a critical deadline constitutes a system failure according to the system requirements.

The system must produce the required result within its specified time limit, not merely produce the correct result eventually.

Examples

  • Aircraft flight-control functions.
  • Emergency shutdown systems.
  • Automotive airbag deployment functions.
  • Industrial machine protection.
  • Time-critical medical device functions.
  • High-speed motion-control systems.
INPUT / EVENT | RELEASE TASK | EXECUTE CONTROL | PRODUCE OUTPUT | CHECK DEADLINE | +-----+-----+ | | ON TIME TOO LATE | | VALID RESULT DEADLINE MISS | FAILURE HANDLING

Correctness includes both logical correctness and timing correctness.

4. Timing Parameters of Real-Time Tasks

Real-time task design requires a precise definition of release time, execution time, period and deadline.

ParameterMeaning
Release time (r)Time at which a task becomes eligible to execute.
Execution time (C)Processor time required by the task under specified assumptions.
Period (T)Time between releases of a periodic task.
Deadline (D)Required completion time relative to release or another defined reference.
Response time (R)Time from release to completion.
Blocking time (B)Time a task may be delayed by lower-priority resource ownership or other modeled blocking.
JitterVariation in release, start or completion timing.
WCETWorst-case execution-time upper bound under stated assumptions.

Task Timing Diagram

Release Start Completion | | | v v v +----------------+====================+ | Waiting Time | Execution Time | +----------------+====================+ |<------------- Response Time ------->| |<---------------- Deadline ---------->|

For a simple task with no suspension or preemption, response time may equal waiting time plus execution time. In a preemptive RTOS, interference and blocking must also be considered.

5. Execution Time and Worst-Case Execution Time

Execution time is the processor time required for a task to complete. It can vary with input data, branches, cache behavior, memory wait states and hardware conditions.

Best-Case Execution Time (BCET)

The minimum execution time under defined conditions.

Average Execution Time (AET)

The average observed or estimated execution time for a workload distribution.

Worst-Case Execution Time (WCET)

A safe upper bound on execution time under explicitly stated hardware, software and operating assumptions.

TASK EXECUTION TIME | +-------------+-------------+ | | | BCET AET WCET | | | Minimum Average Safe Upper Observed Behavior Bound
The largest execution time measured during testing is not automatically WCET. Testing may not exercise every worst-case path or hardware condition.

Methods for WCET Estimation

  • Static program analysis.
  • Measurement-based analysis.
  • Processor timing analysis.
  • Control-flow analysis.
  • Memory and peripheral wait-state analysis.
  • Conservative safety margins supported by engineering evidence.

6. Deadline Types

Deadline TypeMeaning
Implicit deadlineDeadline equals task period: D = T.
Constrained deadlineDeadline is no greater than period: D ≤ T.
Arbitrary deadlineDeadline may be greater than period: D can exceed T.

Example

A periodic sensor task has period T = 10 ms.

  • D = 10 ms: implicit deadline.
  • D = 8 ms: constrained deadline.
  • D = 15 ms: arbitrary deadline.

Scheduling analysis must use the actual deadline model rather than assuming every task has D = T.

7. CPU Utilization

CPU utilization estimates the fraction of processor capacity required by periodic tasks.

For a set of independent periodic tasks on a single processor:

U = Σ (Ci / Ti)

Where:

  • Ci = execution time of task i.
  • Ti = period of task i.
  • U = total utilization.

Example

TaskExecution Time (C)Period (T)Utilization
T11 ms5 ms0.20
T22 ms10 ms0.20
T33 ms20 ms0.15
Total0.55

Total CPU utilization = 0.55 × 100 = 55%.

A utilization below 100% does not by itself prove schedulability. Deadlines, task release patterns, blocking, interrupts and scheduling policy also matter.

8. Rate Monotonic Scheduling (RMS)

Rate Monotonic Scheduling is a fixed-priority scheduling algorithm for periodic tasks. Under the standard RMS assignment, shorter-period tasks receive higher priority.

Priority Assignment

TaskPeriodAssigned Priority
T15 msHighest
T210 msMedium
T320 msLowest

Liu-Layland Utilization Bound

U ≤ n(2^(1/n) - 1)

Where n is the number of independent periodic tasks.

For n = 3:

U ≤ 3(2^(1/3) - 1)
U ≤ approximately 0.7798

U ≤ 77.98%

This is a sufficient utilization bound for the classical RMS assumptions. A task set exceeding the bound may still be schedulable.

9. Earliest Deadline First (EDF)

EDF is a dynamic-priority scheduling algorithm. The task with the earliest absolute deadline among ready tasks receives the highest scheduling priority.

Example

TaskAbsolute DeadlineScheduling Priority
T112 msHighest
T28 msHighest at this instant
T315 msLowest at this instant

T2 executes first because it has the earliest absolute deadline.

For an ideal single processor with independent, preemptible periodic tasks and implicit deadlines, EDF is schedulable if total utilization does not exceed 100%:

U = Σ (Ci / Ti) ≤ 1
This EDF condition is not a universal guarantee for arbitrary deadlines, blocking, non-preemptive sections, release jitter or resource dependencies.

10. Fixed-Priority vs Dynamic-Priority Scheduling

FeatureFixed PriorityDynamic Priority
PriorityAssigned according to a fixed rule or configuration.Can change during execution.
ExampleRate Monotonic Scheduling.Earliest Deadline First.

ImplementationOften simpler in conventional RTOS kernels.Requires deadline-based priority management.

Standard FreeRTOS scheduling is fixed-priority. Changing a task priority with vTaskPrioritySet() does not implement EDF automatically.

11. Response-Time Analysis

Response-time analysis estimates the maximum time between task release and completion, considering execution, blocking and higher-priority interference.

For a fixed-priority preemptive task i, a common recurrence under suitable assumptions is:

Ri = Ci + Bi
     + Σ ceil(Ri / Tj) × Cj

The summation covers higher-priority tasks j.

Where:

  • Ri = worst-case response time of task i.
  • Ci = WCET of task i.
  • Bi = modeled blocking time.
  • Cj = WCET of higher-priority task j.
  • Tj = period or minimum inter-arrival time of higher-priority task j.

The recurrence is evaluated iteratively until it converges or exceeds the deadline.

This is a simplified fixed-priority response-time equation. Real systems may need to account for release jitter, interrupt interference, non-preemptive sections, self-suspension and other platform-specific effects.

13. Priority Inversion and Blocking

Priority inversion occurs when a high-priority task is indirectly delayed because a lower-priority task holds a resource that it needs.

Example

  1. Low-priority Task L acquires a shared mutex.
  2. High-priority Task H becomes ready and requests the same mutex.
  3. Task H blocks because Task L owns the mutex.
  4. Medium-priority Task M preempts Task L.
  5. Task H remains blocked until Task L runs and releases the mutex.

Mitigation

  • Use mutexes with priority inheritance where supported.
  • Keep critical sections short.
  • Avoid unnecessary nested locks.
  • Define a consistent lock-acquisition order.
  • Include worst-case blocking in schedulability analysis.
Priority inheritance reduces some forms of priority inversion but does not eliminate all blocking or guarantee that a task meets its deadline.

14. Interrupt Latency and Task Response

Interrupt latency and task response time are different timing measurements.

MetricMeaning
Interrupt latencyTime from interrupt assertion to the start of the ISR.
ISR execution timeTime spent executing the interrupt service routine.
Task release latencyDelay before a released task begins execution.
Task response timeTime from task release to task completion.

Design Recommendations

  • Keep ISRs short and bounded.
  • Defer non-urgent processing to tasks.
  • Use appropriate interrupt priorities.
  • Analyze interrupt masking and critical sections.
  • Include interrupt interference in timing analysis.
  • Measure and verify worst-case behavior on target hardware.

15. Task Architecture for Hard Real-Time Systems

A well-designed task architecture separates functions according to timing requirements, execution cost and dependencies.

Example: Industrial Motor Controller

SENSOR INPUT | ADC / CAPTURE ISR | NOTIFY CONTROL TASK | HIGH-PRIORITY TASK MOTOR CONTROL | CONTROL OUTPUT | +-------+-------+ | | MEDIUM-PRIORITY LOW-PRIORITY COMMUNICATION LOGGING TASK | | STATUS UPDATE DIAGNOSTIC LOG

Task Design Principles

  • Separate periodic control tasks from background tasks.
  • Assign priorities based on timing requirements and analysis.
  • Use bounded communication and synchronization.
  • Avoid long blocking operations in critical tasks.
  • Define task periods and deadlines explicitly.
  • Monitor missed releases and deadline violations.

16. FreeRTOS Implementation Considerations

FreeRTOS can implement many task-management and synchronization mechanisms used in real-time systems. Application timing still requires separate analysis.

Useful APIs

APIPurpose
xTaskCreate()Create a task dynamically.
vTaskPrioritySet()Change a task priority.
vTaskDelayUntil()Maintain a periodic task schedule.
xTaskGetTickCount()Read the RTOS tick count.
xQueueSend()Send data to a queue.
xSemaphoreTake()Acquire a semaphore or mutex.
uxTaskGetStackHighWaterMark()Inspect the minimum remaining task stack observed.

Periodic Task Example

#include "FreeRTOS.h"
#include "task.h"

static void ControlTask(void *pvParameters)
{
    TickType_t lastWakeTime;
    const TickType_t period = pdMS_TO_TICKS(10);

    (void) pvParameters;

    lastWakeTime = xTaskGetTickCount();

    for (;;)
    {
        /* Read inputs and execute control logic. */

        /* Maintain a nominal 10 ms period. */
        vTaskDelayUntil(&lastWakeTime, period);
    }
}

int main(void)
{
    BaseType_t result;

    result = xTaskCreate(
        ControlTask,
        "Control",
        256,
        NULL,
        3,
        NULL
    );

    if (result == pdPASS)
    {
        vTaskStartScheduler();
    }

    for (;;)
    {
        /* Scheduler startup failed or returned. */
    }
}
This is a generic FreeRTOS example. Stack depth is specified in StackType_t elements, not bytes. The 10 ms delay establishes a periodic release pattern but does not prove that the control task meets a 10 ms deadline.

17. Overload Management

Overload occurs when the processor or another resource cannot complete all released work within the required timing constraints.

Possible Causes

  • Unexpected interrupt frequency.
  • Excessive communication traffic.
  • Long execution paths.
  • Unexpected sensor-event bursts.
  • Blocking or deadlock conditions.
  • Insufficient processor capacity.

Overload Management Strategies

  • Bound incoming workload.
  • Prioritize safety-related functions.
  • Reject or defer non-critical work according to policy.
  • Use admission control where applicable.
  • Monitor deadline misses and queue saturation.
  • Define a controlled degraded operating mode.
  • Provide an appropriate protective response if required.
Never silently discard a safety-critical event as an overload-management shortcut. The response to overload must be specified and validated.

18. Fault Handling and Recovery

Hard real-time systems must define how the system responds to detected faults and timing violations.

Fault Handling Sequence

FAULT DETECTED | IDENTIFY FAULT | DETERMINE SEVERITY | +-------+-------+ | | RECOVERABLE CRITICAL | | CONTROLLED PROTECTIVE RECOVERY RESPONSE | | VERIFY STATE SAFE STATE | | +-------+-------+ | RECORD DIAGNOSTICS

Possible Recovery Mechanisms

  • Task restart when safe and permitted.
  • Peripheral reset.
  • Communication reconnection.
  • Watchdog-triggered system reset.
  • Switch to redundant hardware.
  • Controlled shutdown.
  • Transition to a defined safe state.

19. Hard Real-Time Design Workflow

  1. Define requirements: Identify functional and timing requirements.
  2. Identify hazards: Determine possible unsafe operating conditions.
  3. Decompose functions: Separate the application into tasks and interrupt handlers.
  4. Define timing parameters: Specify periods, deadlines and WCET bounds.
  5. Select scheduling policy: Choose a suitable fixed-priority or deadline-based approach.
  6. Analyze schedulability: Evaluate CPU utilization, response time and blocking.
  7. Design synchronization: Bound resource access and blocking.
  8. Design fault handling: Specify overload, fault and recovery behavior.
  9. Implement: Develop the RTOS application and hardware interfaces.
  10. Verify and validate: Test functional behavior and timing on the target platform.
  11. Maintain evidence: Record assumptions, test results and design changes.

22. Practical Exercise 3 – Deadline Analysis

Problem: A task has a release time of 100 ms, completes at 106 ms and has a relative deadline of 10 ms.

Absolute Deadline = Release Time + Relative Deadline

Absolute Deadline = 100 + 10
                  = 110 ms

Completion Time = 106 ms

Deadline Margin = 110 - 106
                = 4 ms

Expected result: The task completes 4 ms before its absolute deadline.

23. Practical Exercise 4 – WCET Budget

Problem: A control task has a 5 ms deadline. Its estimated WCET is 3 ms, and the analyzed maximum interference and blocking total 1 ms.

Response-Time Budget = WCET + Interference + Blocking

                    = 3 + 1

                    = 4 ms

Deadline = 5 ms

Remaining Margin = 5 - 4
                 = 1 ms

Expected result: The estimated response-time budget is 4 ms, leaving 1 ms of margin. This is only valid if the interference and blocking estimates are safe upper bounds and all other timing effects are included.

27. Lesson Summary

  • Hard real-time correctness requires both functional and timing correctness.
  • Task timing parameters include release time, execution time, period and deadline.
  • WCET must be a defensible upper bound under stated assumptions.
  • CPU utilization is useful but insufficient as a standalone schedulability test.
  • RMS assigns higher fixed priority to shorter-period tasks.
  • EDF selects the ready task with the earliest absolute deadline.
  • Response-time analysis considers execution, blocking and higher-priority interference.
  • Priority inversion can delay high-priority tasks.
  • Interrupt processing and synchronization must have bounded timing.
  • Overload and fault recovery require explicit system-level policies.
  • FreeRTOS provides scheduling mechanisms, but the application must be analyzed and validated on its target platform.
