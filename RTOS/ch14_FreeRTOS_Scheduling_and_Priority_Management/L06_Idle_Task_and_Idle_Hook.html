2. Introduction to the Idle Task

The Idle Task is a system task maintained by the FreeRTOS kernel. It provides an execution context when no other task is Ready.

In a typical FreeRTOS application, the Idle Task is automatically created as part of scheduler startup. The application does not normally create it manually.

Example

TaskPriorityState
Sensor Task3Blocked
Communication Task2Blocked
Display Task1Blocked
Idle Task0Ready

When all application tasks are Blocked or Suspended, the Idle Task can execute.

3. Idle Task Priority

The Idle Task has the lowest task priority in the standard FreeRTOS priority scheme. Its priority is represented by tskIDLE_PRIORITY, normally zero. 

#define tskIDLE_PRIORITY 0

Application tasks can be assigned priorities above the Idle Task. A Ready application task with a higher priority takes precedence.

TaskExample Priority
High Priority Task3
Medium Priority Task2
Low Priority Task1
Idle Task0
The numerical values are illustrative. The available priority levels depend on configMAX_PRIORITIES.

4. When Does the Idle Task Execute?

The scheduler selects the highest-priority Ready task. The Idle Task executes when no other task is Ready at a higher priority.

An application task may become Ready because a delay expires, queue data arrives, a semaphore is given or an interrupt wakes it. The Idle Task can then be preempted.

5. Main Responsibilities of the Idle Task

5.1 Background Execution

The Idle Task provides a task context for background processing when application tasks are not Ready.

5.2 Memory Cleanup

When a dynamically allocated task deletes itself, its kernel-allocated task memory is typically reclaimed later by the Idle Task.

5.3 Idle Hook Execution

If the application enables the Idle Hook, the kernel calls the application's hook function during Idle Task execution.

5.4 Power Management Opportunities

The Idle Task can provide an opportunity for low-power processing, but actual power saving requires processor-specific support and suitable application design.

6. Task Deletion and Idle Task Memory Cleanup

A task created dynamically using xTaskCreate() normally uses kernel-managed memory for its task control block and stack.

When such a task deletes itself using vTaskDelete(NULL), it is removed from the scheduler's task lists. Its dynamically allocated memory is typically reclaimed by the Idle Task. 

void TemporaryTask(void *pvParameters)
{
    /* Perform a temporary operation */

    vTaskDelete(NULL);

    /* Execution does not continue here */
}

Memory Reclamation Sequence

  1. A dynamically created task starts executing.
  2. The task completes its operation.
  3. The task calls vTaskDelete(NULL).
  4. The kernel removes the task from scheduling.
  5. The task's dynamically allocated memory is marked for cleanup.
  6. The Idle Task performs the deferred cleanup.
The Idle Task must receive processor time for this deferred cleanup. A continuously Ready higher-priority application task can starve the Idle Task and delay memory reclamation.

7. What Is an Idle Hook?

An Idle Hook is an application-defined function that FreeRTOS calls from the Idle Task when the Idle Hook feature is enabled.

The standard function name is: 

void vApplicationIdleHook(void);

The application provides the function. The kernel invokes it during Idle Task execution.

Configuration

#define configUSE_IDLE_HOOK 1

When enabled, the application must provide the required hook function implementation.

8. Idle Hook Function Example

The following example illustrates a simple Idle Hook that updates a counter. 

#include "FreeRTOS.h"
#include "task.h"

volatile unsigned long idleCounter = 0;

void vApplicationIdleHook(void)
{
    idleCounter++;
}

Explanation

  • The Idle Hook is called while the Idle Task executes.
  • Each invocation increments idleCounter.
  • The counter can be inspected using a debugger.
  • It can provide a rough indication of available idle execution time.
The counter is not a calibrated CPU-load measurement. Its value depends on processor speed, compiler optimization, tick interrupts and other system activity.

9. Restrictions of an Idle Hook

An Idle Hook must not interfere with normal kernel operation.

  • Do not call blocking APIs.
  • Do not call vTaskDelay() from the Idle Hook.
  • Do not wait indefinitely for a semaphore or queue.
  • Do not perform long-running operations.
  • Do not use APIs that could block the Idle Task.
  • Keep processing short and predictable.
  • Do not assume the hook executes at a fixed interval.
The Idle Hook runs in the Idle Task's context. If it blocks, it can prevent the Idle Task from performing essential background work, including deferred task-memory cleanup.

11. Idle Task and Low-Power Management

In battery-powered embedded systems, idle periods can be used to reduce power consumption. For example, the processor may enter a suitable sleep state when no application task needs to run.

However, entering a low-power state requires careful handling of:

  • Pending interrupts.
  • System tick timing.
  • Wake-up sources.
  • Peripheral activity.
  • Clock configuration.
  • Timekeeping after sleep.

A simple Idle Hook does not automatically implement safe tickless low-power operation. FreeRTOS ports may provide tickless idle support through separate configuration and port-specific sleep functions.

#define configUSE_TICKLESS_IDLE 1

The exact supported configuration and sleep implementation depend on the selected FreeRTOS version and processor port.

13. Idle Task Starvation

Idle Task starvation occurs when higher-priority tasks remain Ready for long periods and prevent the Idle Task from executing.

Example

void HighPriorityTask(void *pvParameters)
{
    for (;;)
    {
        /* Continuous CPU-intensive processing */
    }
}

If this task is continuously Ready and has higher priority than the Idle Task, the Idle Task may never receive processor time.

Consequences

  • Delayed cleanup of dynamically deleted tasks.
  • Reduced opportunity for idle-time processing.
  • Possible failure of application designs that depend on Idle Hook execution.
  • Increased CPU utilization.

Prevention

  • Block tasks when they have no work.
  • Use suitable task priorities.
  • Avoid unnecessary busy loops.
  • Keep processing bounded.
  • Use periodic delay mechanisms where appropriate.

14. Idle Task and Static Memory Allocation

FreeRTOS can support static memory allocation for kernel objects, including the Idle Task, when the relevant configuration is enabled. 

#define configSUPPORT_STATIC_ALLOCATION 1

In applicable FreeRTOS versions, the application may provide the Idle Task's memory through a callback such as: 

void vApplicationGetIdleTaskMemory(
    StaticTask_t **ppxIdleTaskTCBBuffer,
    StackType_t **ppxIdleTaskStackBuffer,
    configSTACK_DEPTH_TYPE *pulIdleTaskStackSize
);
The callback signature and stack-depth type depend on the FreeRTOS version. Check the selected kernel's port and API documentation before implementing it.

15. Practical Example – Idle Hook Counter

Objective: Observe Idle Hook execution when application tasks are not Ready.

Example Program

#include "FreeRTOS.h"
#include "task.h"

volatile unsigned long idleCounter = 0;
volatile unsigned long taskCounter = 0;

void ApplicationTask(void *pvParameters)
{
    for (;;)
    {
        taskCounter++;

        /* Block for a short interval */
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void vApplicationIdleHook(void)
{
    idleCounter++;
}

int main(void)
{
    BaseType_t result;

    result = xTaskCreate(
        ApplicationTask,
        "Application",
        256,
        NULL,
        1,
        NULL
    );

    if (result == pdPASS)
    {
        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Procedure

  1. Enable configUSE_IDLE_HOOK in FreeRTOSConfig.h.
  2. Compile the application with a compatible FreeRTOS port.
  3. Start the scheduler.
  4. Inspect idleCounter and taskCounter using a debugger.
  5. Observe that the application task blocks periodically.
  6. During eligible idle intervals, the Idle Hook increments idleCounter.
  7. Compare the counters under different application workloads.

Expected Result

The application task increments taskCounter during its execution. When it blocks and no other higher-priority task is Ready, the Idle Task executes and idleCounter increases.

16. Debugging Checklist

  • Verify that the scheduler starts successfully.
  • Verify configUSE_IDLE_HOOK is enabled if using the hook.
  • Confirm the hook function has the correct name and signature.
  • Check whether application tasks are continuously Ready.
  • Verify that tasks block when they have no work.
  • Inspect dynamically deleted task cleanup behavior.
  • Check stack usage and Idle Task stack configuration.
  • Keep the Idle Hook short and non-blocking.
  • Verify tickless idle configuration separately.
  • Check the processor port's low-power implementation.

17. Important Notes for LPC2129 and Keil

The LPC2129 uses an ARM7TDMI-S core. A working Idle Task and Idle Hook experiment requires a compatible FreeRTOS ARM7 port and a correctly configured project.

  • Verify the ARM7 port before compiling FreeRTOS examples.
  • Check the selected kernel version's hook configuration.
  • Confirm the Idle Task stack setup.
  • Do not assume Cortex-M tickless-idle implementation applies to ARM7.
  • Keil simulator support for the selected port must be verified.
This lesson provides generic FreeRTOS examples. It does not establish that the LPC2129 Keil simulator project has a working FreeRTOS port.
