Scheduler Suspension and Resumption

1. Learning Objectives

Scheduler suspension is a FreeRTOS kernel feature that temporarily prevents normal task context switching. It is useful in specific situations where an application needs a short sequence of operations to execute without another task being scheduled.

2. What Is Scheduler Suspension?

In normal FreeRTOS operation, the scheduler selects the highest-priority Ready task whenever a scheduling decision is required.

Scheduler suspension temporarily prevents the kernel from performing normal task context switches. The currently running task continues executing until the scheduler is resumed or another independent processor-level event changes execution.

FreeRTOS provides two functions:

  • vTaskSuspendAll() – suspends the scheduler.
  • xTaskResumeAll() – resumes the scheduler.
Scheduler suspension is not the same as suspending an individual task using vTaskSuspend().

3. vTaskSuspendAll() Function

The function vTaskSuspendAll() suspends normal task scheduling.

Syntax

void vTaskSuspendAll(void);

Purpose

  • Prevents normal task context switches while suspended.
  • Allows the current task to execute a short sequence without another task being scheduled.
  • Allows certain kernel operations to record tasks that become Ready for later scheduling.
  • Does not disable interrupts.
  • Does not stop hardware timer interrupts.

Example

vTaskSuspendAll();

/* Perform a short operation */

xTaskResumeAll();

The current task enters a scheduler-suspended region and then resumes normal scheduling.

4. xTaskResumeAll() Function

The function xTaskResumeAll() resumes task scheduling after a previous scheduler suspension.

Syntax

BaseType_t xTaskResumeAll(void);

Return Value

Return ValueMeaning
pdTRUEA context switch occurred as part of resuming the scheduler.
pdFALSENo context switch was required at that point.

The function processes scheduling work that was deferred while the scheduler was suspended. A higher-priority task that became Ready during suspension may be selected when scheduling resumes.

The return value indicates whether a context switch occurred; it is not a general success or failure status.

5. How Scheduler Suspension Works

  1. A task calls vTaskSuspendAll().
  2. The scheduler enters its suspended state.
  3. The current task continues executing.
  4. Interrupts can still occur.
  5. Some tasks may become Ready because of kernel or interrupt-related events.
  6. Normal task switching is deferred.
  7. The task calls xTaskResumeAll().
  8. The kernel processes pending scheduling work and performs a context switch if required.

6. Scheduler Suspension Does Not Disable Interrupts

One of the most important concepts is that scheduler suspension does not globally disable hardware interrupts.

An interrupt can still occur while the scheduler is suspended. Its ISR can execute according to the processor and interrupt-controller rules. The ISR may signal a task using an appropriate FreeRTOS FromISR API, subject to the selected port's rules.

OperationScheduler Suspended?
Normal task context switchDeferred.
Hardware interrupt occurrenceStill possible.
ISR executionStill possible.
Hardware timer operationStill possible.
Current task executionContinues.
Scheduler suspension does not make shared data safe against every interrupt or DMA access. Use an appropriate synchronization mechanism for each concurrent access.

7. Scheduler Suspension vs Task Suspension

FreeRTOS provides different mechanisms for suspending an individual task and suspending the scheduler.

FeaturevTaskSuspend()vTaskSuspendAll()

EffectMoves the specified task to Suspended state.Prevents normal task context switches.
Current taskCan suspend itself.Continues running.
Other Ready tasksCan execute normally.Wait for scheduler resumption before normal task switching.

8. Scheduler Suspension vs Critical Sections

Scheduler suspension and critical sections are not interchangeable.

Scheduler Suspension

vTaskSuspendAll();

/* Short task-level operation */

xTaskResumeAll();

Critical Section

taskENTER_CRITICAL();

/* Very short protected operation */

taskEXIT_CRITICAL();
FeatureScheduler SuspensionCritical Section
Main purposeDefer task context switches.Protect a short operation from relevant interrupt/preemption interference.
InterruptsNot globally disabled by scheduler suspension.Interrupt masking is port-specific.
Task switchingDeferred.Normally prevented while the critical section is active.
Typical useShort task-level operations.Very short access to shared state requiring protection from relevant interrupts.
Critical-section macros have port-specific semantics. They do not necessarily mask every interrupt source. Never assume that scheduler suspension or a critical section automatically protects data accessed by DMA or every ISR.

9. Example – Basic Scheduler Suspension

#include "FreeRTOS.h"
#include "task.h"

volatile unsigned long sharedCounter = 0;

void CounterTask(void *pvParameters)
{
    for (;;)
    {
        vTaskSuspendAll();

        sharedCounter++;
        sharedCounter++;
        sharedCounter++;

        xTaskResumeAll();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    BaseType_t result;

    result = xTaskCreate(
        CounterTask,
        "Counter",
        256,
        NULL,
        2,
        NULL
    );

    if (result == pdPASS)
    {
        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

The example demonstrates the API sequence. It does not require scheduler suspension for this simple counter in a real application. A suitable synchronization method should be chosen based on all tasks and interrupts that access the shared variable.

10. Nested Scheduler Suspension

FreeRTOS maintains scheduler-suspension state so that nested calls can be handled. A task may enter more than one scheduler suspension level before fully resuming scheduling. 

vTaskSuspendAll();

/* First protected task-level region */

vTaskSuspendAll();

/* Nested task-level region */

xTaskResumeAll();

/* Still within the outer suspension */

xTaskResumeAll();

/* Scheduler fully resumed */
Every successful scheduler-suspension call must be matched by a corresponding resume call. Unbalanced calls can leave the scheduler suspended and prevent normal task switching.

11. Deferred Context Switching

Suppose a low-priority task is executing while the scheduler is suspended. An interrupt occurs and makes a high-priority task Ready.

The ISR can execute, but the normal task context switch is deferred while scheduler suspension remains active. When the running task calls xTaskResumeAll(), the kernel processes the pending scheduling work. The high-priority task may then run.

Conceptual Example

StepEventResult
1Low-priority task runs.Low task is Running.
2Scheduler is suspended.Normal task switches are deferred.
3Interrupt makes high-priority task Ready.High task becomes Ready.
4ISR completes.Pending task switch remains deferred.
5Scheduler resumes.Kernel evaluates Ready tasks.
6High-priority task is selected.High task executes if it is the highest-priority Ready task.

12. Important Restrictions and Best Practices

  • Keep scheduler-suspended regions very short.
  • Always pair vTaskSuspendAll() with xTaskResumeAll().
  • Do not use scheduler suspension as a replacement for mutexes.
  • Do not assume interrupts are disabled.
  • Do not perform long blocking operations while the scheduler is suspended.
  • Avoid lengthy calculations and polling loops inside the suspended region.
  • Do not call APIs that can block the current task while the scheduler is suspended.
  • Check the selected FreeRTOS version and API restrictions.
  • Consider the effect of deferred task scheduling on response time.
  • Use queues, semaphores, mutexes or critical sections when they better match the synchronization requirement.

13. Effect on Real-Time Performance

Scheduler suspension delays normal task switching. If a high-priority task becomes Ready during this period, it cannot receive normal task-level execution until scheduling resumes.

Therefore, long scheduler-suspended intervals can increase task response time and cause deadline misses.

Example

If a task suspends the scheduler for 20 ms, a higher-priority task that becomes Ready during that interval may have to wait for scheduler resumption before it can execute. The actual delay depends on the timing of events and the port implementation.

14. Practical Experiment – Observe Deferred Scheduling

Objective: Understand how scheduler suspension affects task switching.

Experiment Setup

  • Create a low-priority task.
  • Create a higher-priority task that becomes Ready after a controlled event.
  • Temporarily suspend the scheduler in the low-priority task.
  • Generate the event that makes the higher-priority task Ready.
  • Resume the scheduler.
  • Observe which task executes next.

Procedure

  1. Build the test using a verified FreeRTOS port.
  2. Observe task states before scheduler suspension.
  3. Call vTaskSuspendAll().
  4. Make the higher-priority task Ready using a suitable event or test mechanism.
  5. Observe that normal task switching is deferred.
  6. Call xTaskResumeAll().
  7. Observe the scheduler's next selection.
  8. Record the execution order.

Expected Result

The higher-priority task can become Ready while the scheduler is suspended. Normal task execution switching is deferred until the scheduler resumes.

15. LPC2129 and Keil Simulator Considerations

The LPC2129 uses the ARM7TDMI-S processor. To run these examples, the project needs a compatible FreeRTOS ARM7 port and correct interrupt and context-switch integration.

  • Verify the ARM7 port for the exact kernel release.
  • Verify compiler compatibility.
  • Verify the tick interrupt implementation.
  • Verify context-switch and interrupt-exit behavior.
  • Check whether the Keil simulator supports the required port behavior.
  • Do not assume Cortex-M NVIC or BASEPRI behavior on LPC2129.
This lesson provides generic FreeRTOS concepts and code. It does not confirm that FreeRTOS runs on the user's current LPC2129 Keil simulator configuration.
