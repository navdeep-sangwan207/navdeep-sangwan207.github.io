Higher-Priority Task Preemption

Task Wakeups, Scheduling Decisions and Context Switching

1. Learning Objectives

Higher-priority task preemption is an important feature of preemptive FreeRTOS scheduling. It allows a newly Ready task with a higher priority to receive processor time before a lower-priority task completes its current operation.

  • Understand task preemption.
  • Learn when a higher-priority task becomes Ready.
  • Understand scheduling decisions after task wakeups.
  • Study preemption caused by queue and semaphore events.
  • Understand interrupt-triggered task wakeups.
  • Learn the role of context switching.
  • Analyze task execution timelines.
  • Identify factors that can delay preemption.

2. Introduction to Higher-Priority Preemption

In a preemptive FreeRTOS configuration, the scheduler normally selects the highest-priority task that is Ready.

Suppose a low-priority task is currently executing. If an event makes a higher-priority task Ready, the scheduler can switch execution to the higher-priority task at an appropriate scheduling point.

TaskPriorityInitial State
Task A1Running
Task B3Blocked

When Task B becomes Ready, it has higher priority than Task A and can preempt it.

3. Conditions Required for Preemption

Higher-priority task preemption depends on several conditions:

  1. Preemptive scheduling must be enabled.
  2. A higher-priority task must become Ready.
  3. The scheduler must be permitted to make a scheduling decision.
  4. Interrupt masking or critical-section restrictions must not prevent the required scheduling operation.
  5. The processor port must support the required context-switch mechanism.

Configuration

#define configUSE_PREEMPTION 1
A higher-priority task becoming Ready does not mean it executes at the exact instant of the event. The switch occurs when the kernel and processor port reach an appropriate scheduling point.

4. Step-by-Step Preemption Sequence

Consider a system with two tasks:

TaskPriorityResponsibility
LowTask1Background processing
HighTask3Urgent event processing

Execution Sequence

  1. LowTask is Running.
  2. HighTask is Blocked, waiting for an event.
  3. The required event occurs.
  4. HighTask becomes Ready.
  5. The kernel requests a scheduling decision.
  6. HighTask is selected because its priority is higher.
  7. LowTask is preempted and remains Ready.
  8. HighTask executes its work.
  9. HighTask blocks or otherwise stops being the highest-priority Ready task.
  10. LowTask can resume execution.

5. Preemption Timing Diagram

Time       T0      T1      T2      T3      T4      T5
           |-------|-------|-------|-------|-------|

LowTask    RUN     RUN     READY   READY   RUN     RUN
HighTask   BLOCK   BLOCK   RUN     RUN     BLOCK   BLOCK

Event              EVENT
                   OCCURS

RUN   = Running
READY = Ready
BLOCK = Blocked

At T2, HighTask becomes Ready and preempts LowTask. After HighTask blocks at T4, LowTask becomes eligible to run again.

6. Preemption When a Queue Receives Data

A common situation occurs when a high-priority task waits for data from a queue and a lower- priority task sends an item.

If the queue receive operation has blocked the high-priority task, sending an item can unblock it. The sender's API may cause the scheduler to select the newly Ready higher-priority task.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t dataQueue;

void ReceiverTask(void *pvParameters)
{
    int receivedData;

    for (;;)
    {
        if (xQueueReceive(
                dataQueue,
                &receivedData,
                portMAX_DELAY) == pdPASS)
        {
            /* Process received data */
        }
    }
}

void SenderTask(void *pvParameters)
{
    int data = 100;

    for (;;)
    {
        if (xQueueSend(
                dataQueue,
                &data,
                0) == pdPASS)
        {
            /* Data successfully sent */
        }

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    dataQueue = xQueueCreate(5, sizeof(int));

    if (dataQueue != NULL)
    {
        if (xTaskCreate(
                ReceiverTask,
                "Receiver",
                256,
                NULL,
                3,
                NULL) == pdPASS)
        {
            if (xTaskCreate(
                    SenderTask,
                    "Sender",
                    256,
                    NULL,
                    1,
                    NULL) == pdPASS)
            {
                vTaskStartScheduler();
            }
        }
    }

    for (;;)
    {
    }
}

Explanation

  • ReceiverTask has priority 3.
  • SenderTask has priority 1.
  • ReceiverTask waits for queue data.
  • SenderTask sends an integer value.
  • The receive operation can unblock ReceiverTask.
  • In a preemptive configuration, ReceiverTask can preempt SenderTask.

7. Preemption Through Semaphore Signaling

A semaphore can be used to signal that an event has occurred. A high-priority task can wait on the semaphore while a lower-priority task gives it.

Conceptual Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t eventSemaphore;

void HighPriorityTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                eventSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Handle the event */
        }
    }
}

void LowPriorityTask(void *pvParameters)
{
    for (;;)
    {
        /* Detect or generate an event */

        xSemaphoreGive(eventSemaphore);

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    eventSemaphore = xSemaphoreCreateBinary();

    if (eventSemaphore != NULL)
    {
        if (xTaskCreate(
                HighPriorityTask,
                "High",
                256,
                NULL,
                3,
                NULL) == pdPASS)
        {
            if (xTaskCreate(
                    LowPriorityTask,
                    "Low",
                    256,
                    NULL,
                    1,
                    NULL) == pdPASS)
            {
                vTaskStartScheduler();
            }
        }
    }

    for (;;)
    {
    }
}

When LowPriorityTask gives the semaphore, HighPriorityTask can become Ready. Since it has a higher priority, the scheduler can preempt the lower-priority task.

8. Interrupt-Triggered Task Preemption

An external hardware event may generate an interrupt. The ISR can notify a task using a suitable FreeRTOS FromISR API.

Typical Sequence

External Hardware Event
          |
          v
    Interrupt Occurs
          |
          v
       ISR Executes
          |
          v
   FromISR API Called
          |
          v
   High-Priority Task
       Becomes Ready
          |
          v
 ISR Requests a Yield
          |
          v
 ISR Exits
          |
          v
 Scheduler Selects Task

For example, an ISR may use a queue-send or semaphore-give FromISR API to wake a task. If the API reports that a higher-priority task was woken, the ISR can request a context switch using the mechanism defined by the selected port.

Never call ordinary blocking task APIs from an ISR. Use the documented FromISR versions where available. Do not use a mutex from an ISR.

9. portYIELD_FROM_ISR()

Many FreeRTOS ports provide a macro or equivalent mechanism named portYIELD_FROM_ISR() to request a context switch when an ISR wakes a higher-priority task.

Illustrative Pattern

void ExampleISR(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Use an appropriate FromISR API here. */

    portYIELD_FROM_ISR(
        xHigherPriorityTaskWoken
    );
}

The actual ISR must acknowledge the hardware interrupt and use the correct FromISR API. The code above shows the general pattern rather than a complete hardware-specific ISR.

The exact yield macro, parameters and interrupt requirements are port-specific. Always use the implementation supplied with the selected FreeRTOS port.

10. Factors That Can Delay Preemption

A newly Ready high-priority task may not execute immediately in every situation.

FactorEffect
Interrupt maskingCan delay kernel scheduling or context switching.
Critical sectionCan temporarily restrict preemption according to the port's implementation.
Scheduler suspensionDefers task scheduling decisions until the scheduler resumes.
Long-running ISRDelays task execution until interrupt processing completes.
Non-preemptive configurationRequires a suitable scheduling point before switching.
Higher-priority Ready taskThe newly Ready task may still wait behind another higher-priority Ready task.

11. Preemption and Critical Sections

A critical section protects a short sequence of operations from specified forms of interruption or concurrent kernel activity. FreeRTOS critical section behavior depends on the processor port.

While a critical section is active, a newly Ready task may not execute immediately. Once the protected region ends, the scheduler can make the required scheduling decision. 

taskENTER_CRITICAL();

/* Short protected operation */

taskEXIT_CRITICAL();
Critical sections must be short. Their interrupt masking behavior is port-specific, and they must not be used as a general replacement for mutexes or blocking synchronization.

12. Preemption and Scheduler Suspension

FreeRTOS provides scheduler suspension APIs that defer task switching while the scheduler is suspended. 

vTaskSuspendAll();

/* Short operation that does not block */

xTaskResumeAll();

Tasks can become Ready while scheduling is suspended, but the scheduler does not perform the normal task switch until scheduling resumes.

Scheduler suspension is not equivalent to disabling interrupts. Interrupts may still occur, subject to the port's interrupt configuration.

13. Practical Example – Queue-Based Preemption

Objective: Demonstrate how a queue can unblock a high-priority task while a lower-priority task sends data.

Procedure

  1. Create a queue with a suitable length and item size.
  2. Create a receiver task with priority 3.
  3. Create a sender task with priority 1.
  4. Make the receiver wait indefinitely for queue data.
  5. Allow the sender to send an item periodically.
  6. Observe the receiver becoming Ready when data arrives.
  7. Inspect task states and execution order using debugger or trace facilities.

Expected Result

When the sender places data into the queue, the blocked receiver can become Ready. Since the receiver has a higher priority, it can be selected before the sender continues its remaining work in a preemptive configuration.

14. Debugging and Verification

  • Verify configUSE_PREEMPTION is enabled.
  • Check that the awakened task has a higher priority.
  • Verify the task is actually Blocked before the event.
  • Inspect queue and semaphore return values.
  • Verify ISR APIs are used only from interrupt context.
  • Check the port-specific ISR yield mechanism.
  • Inspect critical-section duration.
  • Check scheduler suspension and resumption.
  • Measure event-to-task response time under realistic load.
  • Check for interrupt overload and higher-priority task interference.

15. Important Notes for LPC2129 and Keil

The LPC2129 uses an ARM7TDMI-S core. Actual FreeRTOS preemption requires a compatible ARM7 port with correct context-switch and interrupt integration.

  • Do not use Cortex-M NVIC assumptions for LPC2129.
  • Verify the ARM7 port's interrupt and yield implementation.
  • Check the processor's IRQ/FIQ behavior and VIC configuration.
  • Verify the tick source and context-switch mechanism.
  • Confirm Keil compiler and simulator compatibility.
This lesson explains generic FreeRTOS behavior. The example code should be executed only in a verified FreeRTOS port environment. It does not establish that the current LPC2129 simulator project supports FreeRTOS.

17. Lesson Summary

  • Preemption allows a higher-priority Ready task to replace a lower-priority Running task.
  • Queue and semaphore operations can unblock waiting tasks.
  • ISRs can wake tasks through suitable FromISR APIs.
  • Port-specific yield mechanisms support interrupt-triggered context switches.
  • Critical sections and scheduler suspension can defer task switching.
  • Long ISRs and interrupt masking increase response latency.
  • Actual preemption behavior depends on the FreeRTOS port and configuration.
