2. Scheduling Rules Used in These Examples

The examples assume a single-core FreeRTOS system using the standard fixed-priority scheduler.

  • The scheduler selects the highest-priority Ready task.
  • A Running task can be preempted by a higher-priority Ready task when preemption is enabled.
  • Equal-priority Ready tasks can share processor time when time slicing is enabled.
  • A task enters Blocked state when waiting for a delay, queue, semaphore or another event.
  • A task becomes Ready when its wait condition is satisfied.
  • The Idle Task runs when no higher-priority task is Ready.
A task becoming Ready does not mean it executes immediately in every configuration. Scheduling depends on task priority, scheduler state, interrupt handling and the selected port.

3. Example 1 – Two Tasks with Different Priorities

Consider two tasks:

TaskPriorityBehavior
Task A2Runs for a short period and blocks.
Task B1Runs when Task A is Blocked.

Execution Logic

void TaskA(void *pvParameters)
{
    for (;;)
    {
        /* Perform high-priority operation */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        /* Perform low-priority operation */

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

Scheduling Behavior

  1. Task A is Ready and has the higher priority.
  2. Task A executes first.
  3. Task A calls vTaskDelay() and becomes Blocked.
  4. Task B becomes the highest-priority Ready task and executes.
  5. When Task A's delay expires, it becomes Ready.
  6. Task A preempts Task B when preemptive scheduling permits.

5. Example 3 – Equal-Priority Tasks

Two tasks are created with the same priority.

TaskPriority
Task A2
Task B2

When both tasks remain continuously Ready and time slicing is enabled, the scheduler can rotate between them at tick boundaries. 

void TaskA(void *pvParameters)
{
    for (;;)
    {
        /* Task A operation */
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        /* Task B operation */
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

Because these tasks block periodically, their execution also depends on when they become Ready. Equal priority alone does not guarantee an exact alternating sequence.

6. Example 4 – Higher-Priority Task Preemption

Suppose Task A is Running at priority 1. An event occurs that makes Task B Ready at priority 3.

This is the fundamental behavior of preemptive fixed-priority scheduling. The exact switching point depends on the kernel API, interrupt handling and port.

7. Example 5 – Task Delay and Scheduling

The function vTaskDelay() blocks the calling task for a specified number of ticks. 

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read sensor */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

If the tick rate is 1000 Hz, one tick is nominally 1 ms. A 100 ms delay therefore corresponds to 100 ticks, subject to tick resolution and the conversion macro.

Important Difference

FunctionPurpose
vTaskDelay()Blocks the calling task for a relative number of ticks.
vTaskDelayUntil()Schedules periodic wake-ups using a previous wake-time reference and fixed increment.

8. Example 6 – Periodic Task Scheduling

For periodic activities, use vTaskDelayUntil() to maintain a nominal periodic schedule. 

void PeriodicTask(void *pvParameters)
{
    TickType_t lastWakeTime;
    const TickType_t period =
        pdMS_TO_TICKS(100);

    lastWakeTime = xTaskGetTickCount();

    for (;;)
    {
        /* Perform periodic operation */

        vTaskDelayUntil(
            &lastWakeTime,
            period
        );
    }
}

The task uses the previous scheduled wake time rather than simply delaying for a relative period after finishing its work. This helps reduce cumulative timing drift.

vTaskDelayUntil() does not guarantee that the task will meet its deadline. Execution time, higher-priority interference, blocking and interrupt latency must still be analyzed.

9. Example 7 – Task Starvation

Starvation occurs when a Ready task does not receive processor time because higher-priority tasks continuously occupy the processor.

TaskPriorityBehavior
Task A4Continuously Ready.
Task B2Ready and waiting.
Task C1Ready and waiting.

If Task A never blocks or yields and remains Ready, lower-priority tasks may starve. Equal-priority time slicing does not solve starvation caused by a continuously Ready higher-priority task.

Possible Solutions

  • Use appropriate task priorities.
  • Block tasks while waiting for events.
  • Use queues, semaphores and notifications.
  • Keep CPU-intensive work bounded.
  • Analyze processor utilization and response time.

10. Example 8 – Queue-Based Task Scheduling

A sensor task sends measurements to a display task through a FreeRTOS queue. The queue separates data production from data processing. 

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

typedef struct
{
    int temperature;
    int humidity;
} SensorData;

QueueHandle_t sensorQueue;

void SensorTask(void *pvParameters)
{
    SensorData data;

    for (;;)
    {
        data.temperature = 28;
        data.humidity = 65;

        xQueueSend(
            sensorQueue,
            &data,
            portMAX_DELAY
        );

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void DisplayTask(void *pvParameters)
{
    SensorData receivedData;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &receivedData,
                portMAX_DELAY) == pdPASS)
        {
            /* Process received sensor data */
        }
    }
}

int main(void)
{
    BaseType_t sensorResult;
    BaseType_t displayResult;

    sensorQueue = xQueueCreate(
        5,
        sizeof(SensorData)
    );

    if (sensorQueue != NULL)
    {
        sensorResult = xTaskCreate(
            SensorTask,
            "Sensor",
            256,
            NULL,
            2,
            NULL
        );

        displayResult = xTaskCreate(
            DisplayTask,
            "Display",
            256,
            NULL,
            2,
            NULL
        );

        if ((sensorResult == pdPASS) &&
            (displayResult == pdPASS))
        {
            vTaskStartScheduler();
        }
    }

    for (;;)
    {
    }
}

Explanation

  • The queue stores up to five SensorData items.
  • xQueueSend() copies the structure into the queue.
  • xQueueReceive() copies an item into the receiving task's variable.
  • The display task blocks while the queue is empty.
  • The sensor task blocks periodically for 1000 ms.
  • Both tasks have equal priority, so their execution depends on readiness and scheduling events.
The example checks task creation and queue creation. A production application should also define a clear policy for queue-full conditions and handle scheduler-start failure where applicable.

12. Scheduling Analysis – Worked Example

Consider three independent periodic tasks on a single processor. Assume preemptive fixed-priority scheduling, zero blocking, negligible context-switch overhead and Rate Monotonic priority assignment.

TaskExecution Time (C)Period (T)Priority
T11 ms4 msHighest
T21 ms5 msMiddle
T32 ms10 msLowest

CPU Utilization

\[ U = \frac{1}{4}+\frac{1}{5}+\frac{2}{10} \]

\[ U = 0.25+0.20+0.20=0.65 \]

Total processor utilization is 65%.

Response-Time Analysis

For this task set, use the fixed-priority response-time recurrence:

\[ R_i=C_i+\sum_{j\in hp(i)} \left\lceil\frac{R_i}{T_j}\right\rceil C_j \]

For T1, there are no higher-priority tasks:

\[ R_1=C_1=1\text{ ms} \]

For T2, T1 is the only higher-priority task:

\[ R_2=1+\left\lceil\frac{R_2}{4}\right\rceil(1) \]

The converged response time is:

\[ R_2=2\text{ ms} \]

For T3, T1 and T2 are higher priority:

\[ R_3=2+ \left\lceil\frac{R_3}{4}\right\rceil(1)+ \left\lceil\frac{R_3}{5}\right\rceil(1) \]

Iteration gives:

  • First estimate: R3 = 2 + 1 + 1 = 4 ms.
  • Next estimate: R3 = 2 + 1 + 1 = 4 ms.

Therefore, R3 = 4 ms.

TaskWorst-Case Response TimeDeadlineResult
T11 ms4 msPass
T22 ms5 msPass
T34 ms10 msPass
Under the stated assumptions, all three tasks meet their implicit deadlines. A complete engineering analysis must include blocking, release jitter, execution-time variation and other relevant overheads where applicable.

13. Practical Scheduling Exercises

Exercise 1

Task A has priority 3, Task B has priority 2 and Task C has priority 1. All tasks are Ready. Which task executes first?

Answer: Task A.

Exercise 2

Task B is Running. A higher-priority Task A becomes Ready. What happens in preemptive scheduling?

Answer: Task A can preempt Task B at an appropriate scheduling point.

Exercise 3

Two equal-priority tasks remain Ready. What does configUSE_TIME_SLICING control?

Answer: Normal tick-based rotation between equal-priority Ready tasks in the preemptive scheduler.

Exercise 4

A task calls vTaskDelay(100). Does it necessarily execute immediately after 100 ticks?

Answer: No. It becomes Ready when the delay expires, but another higher-priority Ready task may execute first.

Exercise 5

Why can a low-priority task starve?

Answer: Higher-priority tasks may continuously occupy the processor without blocking or yielding.

14. Common Scheduling Mistakes

MistakeCorrect Understanding
Assuming every task runs immediately after becoming Ready.The highest-priority Ready task is selected.
Using very high priorities for every task.Priorities should reflect timing requirements.
Using busy loops for periodic tasks.Use blocking delays or event-driven waits.
Assuming vTaskDelay() guarantees a deadline.Delay controls blocking, not deadline compliance.
Assuming equal priority means guaranteed alternating execution.Actual behavior depends on readiness and scheduling events.
Ignoring queue capacity.Define queue-full handling and data-loss policy.
Ignoring stack and execution-time requirements.Measure and analyze resource usage.

15. LPC2129 and Keil Simulator Considerations

The LPC2129 uses the ARM7TDMI-S processor. The examples in this lesson use generic FreeRTOS APIs and require a compatible port before they can be executed on that target.

  • Verify an ARM7-compatible FreeRTOS port.
  • Verify the compiler and startup configuration.
  • Verify the tick interrupt and context-switch implementation.
  • Check the simulator's support for the required port.
  • Use debugger or trace tools to inspect task states when supported.
  • Do not assume Cortex-M NVIC behavior on LPC2129.
The code examples are educational FreeRTOS examples, not verified LPC2129 Keil simulator projects. Their execution requires a supported kernel port and correct project integration.

17. Lesson Summary

  • FreeRTOS uses a fixed-priority scheduler in its standard configuration.
  • The highest-priority Ready task is selected.
  • Preemption allows higher-priority Ready tasks to interrupt lower-priority task execution at appropriate scheduling points.
  • Time slicing allows eligible equal-priority Ready tasks to share processor time.
  • Blocking APIs allow tasks to wait efficiently.
  • Periodic tasks can use vTaskDelayUntil().
  • Starvation can occur when higher-priority tasks continuously occupy the processor.
  • Queues provide structured communication between tasks.
  • Scheduling analysis helps evaluate timing feasibility.
