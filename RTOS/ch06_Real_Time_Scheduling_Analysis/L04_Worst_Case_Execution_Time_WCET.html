1. Introduction

In a real-time system, a task must complete its required computation within a specified time limit. To verify this requirement, engineers need to estimate how long the task may take under its most demanding execution conditions.

Worst-Case Execution Time (WCET) is a safe upper bound on the processor execution time required by a task or code segment under a clearly defined set of assumptions.

WCET is an important input to:

  • Real-time scheduling analysis.
  • Deadline verification.
  • Processor utilization calculation.
  • Task priority assignment.
  • Embedded software optimization.
  • Safety and reliability assessment.
Central concept: A real-time system should be designed using a defensible upper bound on execution time, not merely an average or a convenient measurement.

2. Definition of WCET

WCET represents the maximum execution time that a task can require under the assumptions of the timing analysis.

WCET = Safe Upper Bound on CPU Execution Time

Consider a task that performs sensor acquisition, data processing, and output control.

OperationExecution Time
Read sensor data1.0 ms
Process sensor data2.5 ms
Update control output0.5 ms
Total4.0 ms

If all relevant execution paths and hardware effects are properly bounded, 4 ms could be the WCET for this simplified task. However, merely adding typical operation times does not establish a valid WCET bound.

3. Best-Case, Average-Case and Worst-Case Execution Time

ParameterMeaningPurpose
BCETBest-case execution time under specified conditions.Understanding minimum processing time.
ACETAverage-case execution time based on a defined workload or probability model.Performance and typical CPU-load estimation.
WCETSafe upper bound on execution time under stated assumptions.Deadline and schedulability analysis.

Example

Suppose a task produces these execution-time measurements during testing:

Sample 1:  2.1 ms
Sample 2:  2.4 ms
Sample 3:  2.2 ms
Sample 4:  2.8 ms
Sample 5:  2.5 ms
  • Observed minimum = 2.1 ms.
  • Observed maximum = 2.8 ms.
  • Observed average = 2.4 ms.
The observed maximum of 2.8 ms is only the largest measurement in this test set. An untested execution path, cache or memory effect, interrupt condition, or input combination may produce a longer execution time.

4. Factors Affecting WCET

Execution time depends on both software structure and the target processor architecture.

4.1 Software-related factors

  • Number of executed instructions.
  • Conditional branches and alternative execution paths.
  • Loop iteration counts.
  • Function calls and recursion.
  • Data-dependent processing.
  • Compiler optimization and generated machine code.

4.2 Hardware-related factors

  • Processor clock frequency.
  • Instruction execution characteristics.
  • Memory wait states and bus contention.
  • Flash and RAM access timing.
  • Cache behavior on processors that have caches.
  • Peripheral and memory access characteristics.

4.3 System-related factors

  • Interrupt service routine execution.
  • Higher-priority task interference.
  • Critical sections and resource blocking.
  • Scheduler and context-switch overhead.
  • DMA or other bus-master activity where applicable.
WCET analysis must define what is being bounded. A task's own WCET is CPU execution time; interrupt interference and blocking are usually accounted for separately in response-time analysis, unless the chosen measurement or analysis model explicitly includes them.

5. Execution Paths and WCET

A program may contain multiple execution paths. Different input conditions can cause different branches and different execution times.

Example: Conditional execution

void ProcessSensor(int value)
{
    if (value > 100)
    {
        CalibrateSensor();
        GenerateAlarm();
    }
    else
    {
        UpdateDisplay();
    }
}

The two paths may require different amounts of CPU time.

Entry: ProcessSensor(value)
Decision: value > 100?
True path: CalibrateSensor() + GenerateAlarm()
False path: UpdateDisplay()
Exit: Function completes

If the true path is longer, it may determine the WCET, provided all possible inputs and relevant hardware conditions have been considered.

5.1 Loops and WCET

Loops can significantly affect execution time. A loop with a known maximum iteration count can be analyzed more easily than a loop with an unbounded or input-dependent iteration count.

void CalculateAverage(int data[], int count)
{
    int sum = 0;
    int i;

    for (i = 0; i < count; i++)
    {
        sum += data[i];
    }
}

If count is limited to a maximum of 100, the loop has a known maximum number of iterations. If there is no reliable upper limit, a finite WCET bound may be difficult or impossible to establish.

6. WCET Estimation Methods

There are several approaches to estimating or establishing WCET. Each has different strengths and limitations.

MethodDescriptionLimitation
Static analysisAnalyzes program structure and processor behavior without executing the program.Requires accurate models and careful treatment of program paths.
Measurement-based analysisMeasures execution time during actual program runs.May miss the true worst-case condition.
Hybrid analysisCombines static analysis with measurement and testing.Requires careful validation of assumptions.
Analytical estimationUses instruction timing and bounded execution paths to estimate an upper bound.Can become difficult for complex software and hardware.

7. Static WCET Analysis

Static WCET analysis estimates an upper execution-time bound by examining the program and the processor model without relying only on measured executions.

Typical analysis steps

  1. Inspect the source code and compiled machine instructions.
  2. Identify all possible execution paths.
  3. Determine loop bounds and recursion limits.
  4. Estimate instruction execution costs.
  5. Account for memory and processor timing effects.
  6. Calculate a conservative upper bound.

Advantages

  • Can reason about paths that testing may not execute.
  • Can establish conservative bounds when the model is sufficiently accurate.
  • Useful for safety-critical and timing-critical software.

Challenges

  • Complex branching increases analysis difficulty.
  • Unbounded loops prevent straightforward finite bounds.
  • Processor pipelines, caches, and memory systems can complicate analysis.
  • Incorrect assumptions can invalidate the resulting bound.

8. Measurement-Based WCET Analysis

Measurement-based analysis records execution times while running a program under selected test conditions.

Typical measurement procedure

  1. Identify the function or task to measure.
  2. Choose a suitable hardware timer or trace facility.
  3. Record a start timestamp.
  4. Execute the selected code.
  5. Record an end timestamp.
  6. Calculate elapsed execution time.
  7. Repeat using representative and demanding input conditions.

Example pseudocode

start_time = ReadHighResolutionTimer();

/* Code under measurement */
ProcessSensorData();

end_time = ReadHighResolutionTimer();

elapsed_time = end_time - start_time;

The timer must be correctly configured, and the measurement must account for timestamp-read overhead and counter wraparound where applicable.

Measurement-based analysis provides evidence about tested executions. It does not, by itself, prove that every possible execution path or hardware condition has been covered.

10. WCET and Processor Clock Frequency

Processor clock frequency influences instruction execution time, but clock frequency alone is not sufficient to calculate WCET.

Execution Time = Total Processor Cycles / Clock Frequency

For the same instruction sequence, a higher clock frequency may reduce execution time if other processor and memory conditions remain comparable.

Clock FrequencyClock Period
12 MHz83.33 ns
30 MHz33.33 ns
60 MHz16.67 ns
100 MHz10 ns

Actual execution time also depends on the instruction sequence, memory system, peripheral access, and processor implementation.

11. WCET and Real-Time Scheduling

WCET is used as the execution-time parameter in many real-time scheduling calculations.

11.1 CPU utilization

For a set of periodic tasks on a single processor, a common utilization expression is:

U = Σ (Cᵢ / Tᵢ)

Where:

  • Cᵢ: WCET of task i.
  • Tᵢ: Period of task i.
  • U: Total processor utilization under the model.

11.2 Numerical example

TaskWCET (C)Period (T)Utilization
Task 12 ms10 ms0.20
Task 23 ms20 ms0.15
Task 34 ms40 ms0.10
Total——0.45
U = 0.20 + 0.15 + 0.10 = 0.45 = 45%

The tasks consume 45% of the processor capacity under the stated utilization model.

Utilization alone does not prove schedulability for every scheduling policy and deadline model. Blocking, release patterns, deadlines, interrupt load, and scheduling overhead may also need to be analyzed.

12. WCET and Response Time

WCET and response time are related but different measurements.

WCETWorst-Case Response Time
Bounds the CPU execution time required by a task.Bounds elapsed time from release to completion.
Does not normally include time waiting for the CPU.Includes relevant waiting and interference.
Used as an input to timing analysis.Used to verify deadline compliance.

A task may have a WCET of 5 ms but a worst-case response time of 12 ms because it can be delayed by resource blocking, higher-priority tasks, and interrupts.

Deadline Requirement: WCRT ≤ Relative Deadline

13. WCET in FreeRTOS Applications

In a FreeRTOS application, WCET estimation should consider the task's own code and the execution environment in which it runs.

Important considerations

  • Measure or analyze the task's CPU execution separately from its blocked intervals.
  • Consider different input values and execution paths.
  • Bound loop iterations and recursive calls.
  • Account for compiler optimization and the actual compiled binary.
  • Analyze interrupt execution separately when using a response-time model that includes interrupt interference.
  • Use runtime statistics and trace tools to understand actual CPU behavior.
  • Check stack and memory behavior as part of system validation.

FreeRTOS runtime statistics can help identify how much CPU time each task has accumulated. They do not automatically calculate a proven WCET bound.

14. WCET Measurement Using LPC2129 and Keil uVision

The LPC2129 can be used to study timer-based execution-time measurement and processor behavior in a Keil uVision project.

ParameterConfiguration
Oscillator frequency12 MHz
CPU clock (CCLK)60 MHz
Peripheral clock (PCLK)15 MHz
Timer prescaler (PR)14999
Timer counter tick1 ms, with the stated timer clock configuration

A timer can measure elapsed time around a code segment. However, a 1 ms timer resolution is too coarse for many short functions. A higher-resolution measurement method is required when the execution time is significantly shorter than 1 ms.

Important simulator limitations

  • Keil uVision simulator timing is not necessarily equal to physical hardware timing.
  • Simulator execution speed is not a direct measurement of target CPU execution time.
  • External device delays and real electrical behavior are not fully represented.
  • ARM7TDMI-S does not provide the Cortex-M DWT cycle counter.
  • Do not assume a particular FreeRTOS port is supported for LPC2129 without verifying its availability.
Use the simulator to understand program flow, registers, and timer configuration. For a defensible hardware WCET measurement, use the actual target hardware, a suitable measurement source, and a validated analysis method.

15. Techniques to Reduce WCET

WCET optimization aims to reduce or tighten the upper bound on task execution time without compromising correctness.

  • Use efficient algorithms and appropriate data structures.
  • Reduce unnecessary loops and repeated calculations.
  • Bound loop iterations explicitly.
  • Avoid unnecessary function calls in time-critical paths.
  • Use suitable compiler optimization settings and validate the generated code.
  • Reduce unnecessary memory and peripheral accesses.
  • Keep interrupt service routines short.
  • Avoid unbounded waiting inside time-critical tasks.
  • Separate non-critical processing from deadline-critical processing.
  • Measure and analyze after every significant optimization.
Optimization should not make execution time unpredictable. A slightly longer but bounded algorithm may be preferable to a faster algorithm with an uncontrolled worst-case path.

16. Common Mistakes

MistakeCorrect Understanding
Maximum observed time is WCET.Observed maximum is not automatically a safe upper bound.
Average execution time is sufficient for deadline analysis.Worst-case timing is needed for conservative deadline guarantees.
WCET includes every task waiting interval.WCET normally bounds CPU execution; waiting and interference are treated in response-time analysis.
Clock frequency alone determines WCET.Instruction behavior, memory, branches, and system conditions also matter.
All branches take equal time.Different execution paths can have different timing costs.
Testing every common input proves WCET.Testing cannot automatically establish coverage of every possible path and hardware condition.
Reducing average execution time always reduces WCET.An optimization must be evaluated against the actual worst-case path and timing model.

17. Lesson Summary

  • WCET is a safe upper bound on CPU execution time under stated assumptions.
  • BCET, average execution time, and WCET are different measurements.
  • Execution paths, loops, branches, memory, and processor behavior affect WCET.
  • Static, measurement-based, analytical, and hybrid methods are used for WCET estimation.
  • Observed maximum execution time does not automatically prove WCET.
  • WCET is an important input to utilization and response-time analysis.
  • WCET and worst-case response time are different concepts.
  • Simulator measurements must not be treated as physical hardware guarantees.
