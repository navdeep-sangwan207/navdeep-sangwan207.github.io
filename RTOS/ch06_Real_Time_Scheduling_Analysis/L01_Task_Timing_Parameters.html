1. Introduction

Real-time scheduling analysis is the process of evaluating whether tasks in a real-time system can complete their required operations within specified timing constraints.

Every real-time task has timing requirements. These requirements determine when the task is released, how much processor execution it needs, how frequently it executes and when its result must be completed.

These values are called task timing parameters. They form the foundation of scheduling algorithms and schedulability analysis.

Important concept: A task is not considered successful merely because it produces the correct result. Its result must also be available within the required timing constraint.

2. What Is a Real-Time Task?

A real-time task is a unit of work that must satisfy specified timing requirements in addition to its functional requirements.

Examples in embedded systems include:

  • Reading temperature sensor data periodically.
  • Updating a motor-control output.
  • Processing UART communication data.
  • Monitoring battery voltage.
  • Executing a watchdog supervision function.
  • Processing an external interrupt event.

Example: Temperature Monitoring

Suppose an embedded controller reads a temperature sensor every 100 ms.

  • Task release interval: 100 ms.
  • CPU execution requirement: 2 ms.
  • Relative deadline: 80 ms.

The controller must complete each temperature-processing job within its specified deadline.

3. Important Task Timing Parameters

Parameter Symbol Description

Execution Time C Processor time required by a task job under the stated execution assumptions.
Worst-Case Execution Time WCET A safe upper bound on execution time under defined hardware and software assumptions.
Period T Time interval between successive releases of a periodic task.
Relative Deadline D Maximum permitted time from job release to its required completion.
Absolute Deadline d Actual completion deadline on the system time axis.
Response Time R Elapsed time between job release and job completion.
Jitter J Variation in the timing of releases, execution starts or completions, according to the selected definition.

4. Release Time

Release time is the instant at which a task job becomes available for execution.

A task may be released by:

  • A periodic timer event.
  • A hardware interrupt.
  • A received communication message.
  • A sensor threshold event.
  • A software notification from another task.

Example

A periodic task is released at 0 ms, 10 ms, 20 ms and 30 ms. 

First Release  = 0 ms

Second Release = 10 ms

Third Release  = 20 ms

Fourth Release = 30 ms

Each release makes a new job available for scheduling.

Release time is not necessarily the same as execution start time. A released job may wait before receiving the CPU.

5. Execution Time

Execution time is the amount of CPU time required to execute a task job.

It represents processor execution, not necessarily the total elapsed time between task release and completion.

Example

Task CPU Execution Time = 4 ms

The task requires 4 ms of processor execution
to complete its job under the stated assumptions.

Execution Time vs Elapsed Time

Suppose a task requires 4 ms of CPU execution but is interrupted by another higher-priority task for 2 ms. 

Task CPU Execution = 4 ms

Interference       = 2 ms

Elapsed Time       = 6 ms

The task still requires 4 ms of its own CPU execution, but its elapsed completion interval is 6 ms in this simplified example.

6. Worst-Case Execution Time (WCET)

Worst-Case Execution Time is a safe upper bound on the processor execution required by a task under a defined set of hardware, software and operating conditions.

WCET is important because scheduling analysis must consider demanding execution scenarios rather than relying only on average execution time.

Example

Execution Scenario Measured Time
Normal input2 ms
Second input3 ms
Complex input4 ms
Another tested input3.5 ms

The largest observed execution time is 4 ms. However, this observation alone does not prove that WCET is 4 ms.

WCET must account for all relevant execution paths and hardware effects under stated assumptions. The maximum value seen during testing is only a measured maximum, not automatically a proven WCET bound.

8. Deadline

A deadline is the time by which a task job must complete its required operation.

There are two important deadline representations.

8.1 Relative Deadline

Relative deadline is the allowed time interval between release and required completion. 

Relative Deadline = D

8.2 Absolute Deadline

Absolute deadline is the actual deadline timestamp. 

Absolute Deadline = Release Time + Relative Deadline

d = r + D

Example

Release Time       = 10 ms

Relative Deadline  = 8 ms

Absolute Deadline  = 10 + 8

                   = 18 ms

The task job must complete no later than 18 ms.

A deadline is not necessarily equal to the task period. A task can have a relative deadline shorter than, equal to or longer than its period, depending on the system model.

9. Relationship Between Period and Deadline

Period and deadline describe different timing requirements.

Parameter Meaning Example
Period Interval between task releases. 20 ms
Relative Deadline Allowed time after release to finish the job. 15 ms

Suppose a task is released every 20 ms and must complete within 15 ms of each release. 

Period T = 20 ms

Deadline D = 15 ms

D < T

The task has a deadline shorter than its period.

Common Deadline Models

  • Implicit deadline: D = T.
  • Constrained deadline: D ≤ T.
  • Arbitrary deadline: D may be greater than T.

These models are important when selecting the appropriate schedulability test.

10. Response Time

Response time is the elapsed time from a task job's release until that job completes. 

Response Time = Completion Time - Release Time

R = f - r

Here:

  • R = Response time.
  • f = Job completion time.
  • r = Job release time.

Example

Release Time   = 5 ms

Completion Time = 12 ms

Response Time = 12 - 5

              = 7 ms

The job takes 7 ms of elapsed time from release to completion.

Response time can include waiting, blocking, higher-priority task interference, interrupt interference and the task's own execution. It is not necessarily equal to CPU execution time.

12. Jitter

Jitter is the variation in timing from one execution or event to another.

It can occur because of interrupt interference, task scheduling, variable execution paths, communication delays or resource contention.

Example: Periodic Task Release Jitter

Task Instance Intended Release Actual Release Release Error
10 ms0.1 ms0.1 ms
210 ms10.3 ms0.3 ms
320 ms20.2 ms0.2 ms

The actual release times differ from the intended release times. This variation is release jitter.

Always identify the type of jitter being discussed: release jitter, start-time jitter, completion jitter or response-time variation.

13. Periodic, Aperiodic and Sporadic Tasks

13.1 Periodic Tasks

Periodic tasks are released at regular time intervals.

Examples:

  • Reading a temperature sensor every 100 ms.
  • Updating a display every 50 ms.
  • Monitoring a motor every 10 ms.

13.2 Aperiodic Tasks

Aperiodic tasks are triggered by events that do not occur at regular intervals.

Examples:

  • Processing a user button press.
  • Handling a communication request.
  • Responding to an external command.

13.3 Sporadic Tasks

Sporadic tasks are event-driven tasks with a specified minimum time between consecutive releases.

Examples:

  • Processing an emergency event with a minimum inter-arrival constraint.
  • Handling a fault notification that cannot occur more frequently than a defined interval.
Task Type Release Behavior
Periodic Regular, predictable intervals.
Aperiodic Irregular event-driven arrivals without a guaranteed minimum separation.
Sporadic Irregular event-driven arrivals with a specified minimum inter-arrival time.

14. Complete Numerical Example

Consider an embedded temperature-monitoring task with the following parameters.

Parameter Value
Release Time10 ms
Execution Time3 ms
Period20 ms
Relative Deadline12 ms
Completion Time17 ms

Step 1: Calculate Absolute Deadline

Absolute Deadline = Release Time + Relative Deadline

                  = 10 + 12

                  = 22 ms

Step 2: Calculate Response Time

Response Time = Completion Time - Release Time

              = 17 - 10

              = 7 ms

Step 3: Calculate Deadline Margin

Deadline Margin = Absolute Deadline - Completion Time

                = 22 - 17

                = 5 ms

Step 4: Check Deadline

Completion Time = 17 ms

Absolute Deadline = 22 ms

17 ms ≤ 22 ms
The task meets its deadline. Its response time is 7 ms, and its deadline margin is 5 ms.

15. Timing Parameters in FreeRTOS

FreeRTOS uses its tick counter and task-management mechanisms to support time-dependent scheduling operations.

Example: Periodic Task Using vTaskDelayUntil()

#include "FreeRTOS.h"
#include "task.h"

void TemperatureTask(void *pvParameters)
{
    TickType_t lastWakeTime;
    const TickType_t period = pdMS_TO_TICKS(100);

    lastWakeTime = xTaskGetTickCount();

    for (;;)
    {
        /* Read and process temperature data. */

        vTaskDelayUntil(&lastWakeTime, period);
    }
}

Explanation

  • xTaskGetTickCount() obtains the current RTOS tick count.
  • pdMS_TO_TICKS(100) converts 100 ms into RTOS ticks.
  • vTaskDelayUntil() maintains a periodic wake-up schedule relative to the previous target wake time.
  • The task performs its work after each release.
vTaskDelayUntil() supports periodic release timing, but it does not guarantee that the task completes before its deadline. Execution time, preemption, blocking and interrupt interference must also be analyzed.

Important Configuration Considerations

  • The RTOS tick frequency determines nominal tick resolution.
  • Very short delays may convert to zero ticks.
  • Tick count is not a calendar clock.
  • Actual timing accuracy depends on the hardware timer and selected FreeRTOS port.
  • Periodic task timing should be verified under expected system load.

16. Relationship Between Timing Parameters and Scheduling Analysis

Timing parameters are used to determine whether a real-time task set can meet its deadlines.

Analysis Required Parameters Purpose
CPU Utilization Execution Time and Period Estimates processor demand.
RMS Analysis Execution Time, Period and Task Count Checks fixed-priority periodic task feasibility.
EDF Analysis Execution Time, Period and Deadline Checks dynamic-deadline scheduling feasibility.
Response-Time Analysis Execution Time, Higher-Priority Interference, Blocking and Periods Calculates worst-case response time.
Jitter Analysis Intended and Actual Timing Values Measures variation in timing.

17. Common Mistakes

  • Confusing task period with task deadline.
  • Assuming release time and execution start time are identical.
  • Using average execution time as WCET.
  • Confusing CPU execution time with elapsed response time.
  • Ignoring higher-priority interference.
  • Ignoring blocking and synchronization delays.
  • Assuming all real-time tasks are periodic.
  • Assuming a task meets its deadline merely because its execution time is shorter than its period.
  • Ignoring tick resolution when converting milliseconds into RTOS ticks.

18. Lesson Summary

  • Release time indicates when a task job becomes Ready.
  • Execution time represents the CPU time required by a job.
  • WCET is a safe upper bound under defined assumptions.
  • Period specifies the interval between periodic releases.
  • Relative deadline specifies the permitted completion interval.
  • Absolute deadline is calculated from release time and relative deadline.
  • Response time is the elapsed time from release to completion.
  • Jitter describes variation in timing.
  • Periodic, aperiodic and sporadic tasks have different release patterns.
  • Timing parameters form the basis of schedulability analysis.
