1. Introduction

Response Time Analysis (RTA) is a mathematical technique used to determine how long a real-time task may take from its release until its completion.

It is especially important in fixed-priority preemptive real-time systems, where higher-priority tasks can interrupt lower-priority tasks.

Response Time = Completion Time − Release Time

RTA helps engineers determine whether a task can complete before its deadline, considering execution time, higher-priority interference, and resource blocking.

Example: A task is released at 10 ms and completes at 18 ms. Its response time is 8 ms, even if it used only 4 ms of CPU execution.

2. Execution Time vs Response Time

ParameterMeaning
Execution time (C)Processor time consumed by the task.
Waiting time (W)Time spent ready but waiting for processor access.
Blocking time (B)Time delayed by a resource or non-preemptive section.
Interference (I)Time during which higher-priority activities execute instead.
Response time (R)Elapsed time from task release to completion.

For a simplified non-overlapping decomposition:

R = C + W + B + I

Additional terms such as release jitter and scheduling overhead may need to be included in more detailed models. Avoid counting the same delay in multiple terms.

3. Timeline of Response Time

Consider a task released at 0 ms. It waits for 2 ms, executes for 3 ms, is preempted for 2 ms, and then executes for another 1 ms.

IntervalActivity
0–2 msTask waits for processor.
2–5 msTask executes for 3 ms.
5–7 msHigher-priority task executes.
7–8 msOriginal task completes its remaining execution.
C = 3 + 1 = 4 ms
R = 8 − 0 = 8 ms

The task consumes 4 ms of processor time but takes 8 ms to complete.

4. Worst-Case Response Time (WCRT)

Worst-Case Response Time (WCRT) is a safe upper bound on the response time of a task under a specified system model and its assumptions.

It considers the most demanding permitted interference and blocking conditions.

Factors affecting WCRT

  • Task execution time and WCET.
  • Higher-priority task execution.
  • Resource blocking.
  • Interrupt service routines.
  • Release jitter.
  • Context-switch and scheduler overhead.
  • Non-preemptive critical sections.
The largest response time observed during testing is not automatically a proven WCRT. Testing may not exercise every worst-case execution path or interference pattern.

5. Fixed-Priority Response-Time Analysis

For a suitable single-processor, fixed-priority preemptive task model, a commonly used response-time recurrence is:

Rᵢ = Cᵢ + Bᵢ + Σ ⌈Rᵢ / Tⱼ⌉ × Cⱼ

Where:

  • Rᵢ: Worst-case response time of task i.
  • Cᵢ: WCET of task i.
  • Bᵢ: Maximum blocking time experienced by task i.
  • Tⱼ: Period of higher-priority task j.
  • Cⱼ: WCET of higher-priority task j.
  • hp(i): Set of tasks having higher priority than task i.

The ceiling operation counts the maximum number of higher-priority job releases that can interfere during the response-time interval under the assumed periodic model.

This recurrence is a standard form for fixed-priority response-time analysis. More detailed models may need additional terms for release jitter, interrupt interference, scheduling overhead, and other effects. Its assumptions must be checked before using it.

6. Iterative Response-Time Calculation

The response-time equation contains R on both sides. Therefore, calculate it iteratively.

Calculation procedure

  1. Start with an initial response-time estimate, commonly Cᵢ + Bᵢ.
  2. Substitute the estimate into the interference equation.
  3. Calculate a new response-time estimate.
  4. Repeat until the result stops changing or exceeds the deadline.
  5. Check whether the converged response time is within the task deadline.

Mathematically:

w₀ = Cᵢ + Bᵢ
wₖ₊₁ = Cᵢ + Bᵢ + Σ ⌈wₖ / Tⱼ⌉ Cⱼ

Here, w represents the successive response-time estimates.

7. Numerical Example 1 – Response Time Without Blocking

Consider three independent periodic tasks scheduled using fixed-priority preemptive scheduling.

TaskExecution TimePeriodPriority
T11 ms4 msHighest
T21 ms5 msMedium
T32 ms10 msLowest

Assume implicit deadlines, no blocking, no release jitter, and negligible overhead.

Step 1: Analyze T1

T1 has no higher-priority task.

R1 = C1 = 1 ms

Deadline check:

1 ≤ 4 → Pass

Step 2: Analyze T2

T1 is the only higher-priority task.

R2 = 1 + ⌈R2 / 4⌉ × 1

Initial estimate:

w0 = 1

First iteration:

w1 = 1 + ⌈1 / 4⌉ × 1 = 2

Second iteration:

w2 = 1 + ⌈2 / 4⌉ × 1 = 2

Converged response time:

R2 = 2 ms

Deadline check:

2 ≤ 5 → Pass

Step 3: Analyze T3

T1 and T2 are higher-priority tasks.

R3 = 2 + ⌈R3 / 4⌉ × 1 + ⌈R3 / 5⌉ × 1

Initial estimate:

w0 = 2

First iteration:

w1 = 2 + ⌈2 / 4⌉ + ⌈2 / 5⌉ = 4

Second iteration:

w2 = 2 + ⌈4 / 4⌉ + ⌈4 / 5⌉ = 4

Converged response time:

R3 = 4 ms

Deadline check:

4 ≤ 10 → Pass

Final results

TaskWCRTDeadlineResult
T11 ms4 msPass
T22 ms5 msPass
T34 ms10 msPass

Conclusion: All three tasks pass the response-time checks under the stated assumptions.

8. Numerical Example 2 – Effect of Blocking Time

Consider a task T2 with the following parameters:

ParameterValue
Execution time C22 ms
Blocking time B21 ms
Higher-priority task execution C11 ms
Higher-priority task period T15 ms
Deadline D26 ms

Response-time recurrence:

wₖ₊₁ = 2 + 1 + ⌈wₖ / 5⌉ × 1

Initial estimate:

w0 = 2 + 1 = 3 ms

First iteration:

w1 = 3 + ⌈3 / 5⌉ = 4 ms

Second iteration:

w2 = 3 + ⌈4 / 5⌉ = 4 ms

Therefore:

R2 = 4 ms

Deadline check:

4 ≤ 6 → Pass

The blocking time increases the response time, even though it does not consume CPU execution by the blocked task.

9. Response Time and Deadline Analysis

A task meets its deadline when its response time does not exceed the allowed relative deadline.

Rᵢ ≤ Dᵢ → Deadline Met
Rᵢ > Dᵢ → Deadline Missed
Response TimeDeadlineInterpretation
4 ms10 msDeadline met with 6 ms margin.
8 ms8 msDeadline met exactly.
9 ms8 msDeadline missed.

Deadline margin or laxity for a completed response-time bound can be expressed as:

Deadline Margin = Dᵢ − Rᵢ

A positive margin indicates spare time before the deadline. Zero means the task meets the deadline exactly.

10. Release Jitter and Interference

Release jitter is the variation or delay between an expected release and the actual release of a job.

In systems with release jitter, higher-priority tasks may interfere differently from the ideal periodic model. A commonly used extended fixed-priority response-time expression includes a jitter term:

Rᵢ = Cᵢ + Bᵢ + Σ ⌈(Rᵢ + Jⱼ) / Tⱼ⌉ Cⱼ

Where Jⱼ is the release jitter of higher-priority task j.

This is an illustrative extended model, not a universal formula for every jitter definition or task model. Use a consistent release-jitter convention and a matching schedulability method.

11. Interrupt Interference

Hardware interrupts and their interrupt service routines can consume processor time and delay task execution.

For example, a high-frequency UART interrupt can interfere with a lower-priority control task.

Sources of interrupt interference

  • Timer interrupts.
  • UART receive and transmit interrupts.
  • ADC conversion-complete interrupts.
  • External interrupt requests.
  • Communication-controller interrupts.

For a complete timing analysis, include the processor demand from relevant interrupt sources. Depending on the model, interrupt interference may be represented as additional execution demand or higher-priority sporadic activities.

12. Response-Time Analysis in FreeRTOS

FreeRTOS applications can be analyzed using task WCET estimates, task periods, priorities, blocking behavior, and interrupt execution demand.

Example periodic task structure

void SensorTask(void *pvParameters)
{
    TickType_t lastWakeTime;

    lastWakeTime = xTaskGetTickCount();

    for (;;)
    {
        /* Acquire sensor data */

        /* Process acquired data */

        vTaskDelayUntil(&lastWakeTime,
                        pdMS_TO_TICKS(10));
    }
}

This example requests a periodic execution interval of 10 ms when the tick configuration and port support the required resolution.

Important considerations

  • Measure or safely estimate WCET.
  • Account for higher-priority task interference.
  • Account for mutex blocking and priority inheritance behavior.
  • Include interrupt execution demand.
  • Check the configured tick rate and delay resolution.
  • Include kernel and context-switch overhead where significant.
  • Verify stack and memory constraints separately.
vTaskDelayUntil() helps maintain periodic release timing. It does not prove that the task will finish before its deadline.

13. Response-Time Measurement in LPC2129 and Keil

For the LPC2129 ARM7TDMI-S target, response-time behavior can be studied conceptually and through simulator-visible execution, register state, and timer events.

ParameterProject Configuration
Oscillator frequency12 MHz
CPU clock (CCLK)60 MHz
Peripheral clock (PCLK)15 MHz
Timer prescaler PR14999
Timer counter tick1 ms

With PCLK = 15 MHz and PR = 14999, the timer counter increments once every 1 ms, assuming the timer is configured with the stated prescaler.

A hardware timer and simulator breakpoints can help demonstrate elapsed-time concepts. However, a 1 ms timer resolution is too coarse for measuring many short function execution times.

Measurement limitations

  • Simulator execution speed is not physical target execution speed.
  • Breakpoint pauses distort wall-clock observations.
  • Timer resolution limits measurement precision.
  • Interrupt and scheduler behavior must be represented correctly.
  • ARM7TDMI-S does not provide the Cortex-M DWT cycle counter.
A simulator exercise can demonstrate task release, blocking, preemption, and completion concepts. It cannot by itself establish a certified WCET or physical real-time guarantee.

14. Common Mistakes

MistakeCorrect Understanding
Execution time equals response time.Response time also includes waiting, blocking, and interference.
Only the task's own WCET matters.Higher-priority task and interrupt interference must be considered.
Measured maximum proves WCRT.Measurements alone may not cover every worst-case condition.
Blocking time consumes CPU time of the blocked task.Blocking delays the task; another task or activity may execute.
A periodic delay API guarantees deadlines.It controls release timing, not completion-time guarantees.
All response-time equations apply universally.Each equation has assumptions about priorities, deadlines, releases, and interference.

15. Lesson Summary

  • Response time is measured from job release to job completion.
  • Execution time is only the processor time consumed by a task.
  • WCRT is a safe upper bound under stated assumptions.
  • Fixed-priority response-time analysis accounts for higher-priority interference and blocking.
  • Iterative calculation is used to find the response-time bound.
  • A task meets its deadline when its response-time bound is no greater than its relative deadline.
  • Interrupt demand, release jitter, scheduling overhead, and resource blocking may require additional analysis.
  • Simulation and measurement support analysis but do not automatically prove WCET.
