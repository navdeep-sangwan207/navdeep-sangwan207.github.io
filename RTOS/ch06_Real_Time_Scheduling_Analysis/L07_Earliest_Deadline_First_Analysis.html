1. Introduction to EDF Scheduling

Earliest Deadline First (EDF) is a dynamic-priority scheduling algorithm used in real-time operating systems. The scheduler selects the ready job whose absolute deadline is earliest.

Earliest Absolute Deadline → Highest Scheduling Priority

Unlike Rate Monotonic Scheduling (RMS), EDF does not assign permanent priorities based on task periods. The scheduling order can change whenever a new job is released or a job completes.

Example: If three ready jobs have absolute deadlines of 20 ms, 15 ms, and 30 ms, EDF selects the job with the 15 ms deadline first.

2. What Is a Job?

A task is a recurring or logical unit of work. Each individual release of a task is commonly called a job.

TermMeaning
TaskA recurring or logical activity in a real-time system.
JobOne particular released instance of a task.
Release timeTime when a job becomes ready for execution.
Execution timeProcessor time required by the job.
Absolute deadlineLatest required completion time for that job.
Remaining execution timeProcessor time still required by an unfinished job.

For a job with release time r and relative deadline D:

Absolute Deadline d = r + D

3. Working Principle of EDF

EDF scheduling follows these basic steps:

  1. Monitor jobs released by periodic, sporadic, or supported aperiodic activities.
  2. Determine the absolute deadline of each ready job.
  3. Compare the deadlines of all ready jobs.
  4. Select the job with the earliest absolute deadline.
  5. Preempt the running job if a newly ready job has an earlier deadline and preemption is permitted.
  6. Re-evaluate scheduling decisions as jobs are released or completed.

5. EDF Processor Utilization

For a set of independent periodic tasks with implicit deadlines on an ideal single preemptive processor, total utilization is:

U = Σ (Cᵢ / Tᵢ)

Where:

  • Cᵢ: Worst-case execution time of task i.
  • Tᵢ: Period of task i.

Under the classical implicit-deadline task model, EDF is schedulable if and only if:

U ≤ 1

This means that the total processor utilization must not exceed 100% under the ideal assumptions.

The U ≤ 1 condition is not a universal EDF test for every task model. Constrained or arbitrary deadlines, release jitter, blocking, self-suspension, multiprocessor scheduling, and overhead may require additional analysis.

6. Numerical Example 1 – EDF Utilization Test

Consider three independent periodic tasks with implicit deadlines:

TaskExecution Time CPeriod T
T12 ms5 ms
T23 ms10 ms
T34 ms20 ms

Step 1: Calculate utilization

U1 = 2 / 5 = 0.40
U2 = 3 / 10 = 0.30
U3 = 4 / 20 = 0.20

Step 2: Calculate total utilization

U = 0.40 + 0.30 + 0.20 = 0.90

Total processor utilization = 90%.

Step 3: Apply the EDF condition

0.90 ≤ 1.00

Result: The task set passes the classical EDF utilization test. Under the stated assumptions, all deadlines can be met.

7. Numerical Example 2 – EDF Utilization Exceeds 100%

Consider three tasks with the following utilization:

TaskExecution TimePeriodUtilization
T13 ms5 ms0.60
T23 ms10 ms0.30
T33 ms20 ms0.15
U = 0.60 + 0.30 + 0.15 = 1.05

Total utilization = 105%.

Since the processor would need to provide more than 100% of its available execution capacity, this task set cannot be scheduled on one ideal processor under the classical implicit-deadline model.

Adding priorities or changing the EDF scheduling order cannot solve a fundamental processor-capacity overload. Execution demand must be reduced, deadlines or periods changed, or processing capacity increased.

9. Hyperperiod in EDF Analysis

The hyperperiod is the least common multiple (LCM) of the periods of periodic tasks. It is a useful interval for examining repeating release patterns when task periods are integral and the task model is periodic.

For T1 with period 5 ms and T2 with period 7 ms:

Hyperperiod = LCM(5, 7) = 35 ms

Within 35 ms, T1 has seven releases and T2 has five releases, including the releases at time zero and excluding the next release at the hyperperiod boundary.

EDF analysis does not always require drawing the entire hyperperiod. For large or complex task sets, demand-based schedulability analysis is more practical.

10. EDF with Constrained and Arbitrary Deadlines

The simple utilization condition U ≤ 1 applies to the classical periodic implicit-deadline model where Dᵢ = Tᵢ.

Deadline ModelRelationshipAnalysis Consideration
Implicit deadlineDᵢ = TᵢClassical utilization test applies under ideal assumptions.
Constrained deadlineDᵢ ≤ TᵢDemand-bound analysis may be required.
Arbitrary deadlineDᵢ may exceed TᵢMore general analysis is needed; jobs may overlap.

For constrained and arbitrary deadline systems, a common single-processor EDF analysis uses the demand-bound function.

dbf(t) = Σ max(0, floor((t − Dᵢ)/Tᵢ) + 1) × Cᵢ

This expression applies to periodic tasks with execution time Cᵢ, period Tᵢ, and relative deadline Dᵢ under the corresponding standard task model.

A processor-demand check compares the execution demand of jobs with deadlines in an interval against the available processor time in that interval. The exact test must respect the task model and assumptions.

11. EDF Advantages

  • Can achieve up to 100% utilization under the classical implicit-deadline model.
  • Priorities respond to actual absolute deadlines.
  • Can schedule a wider range of ideal periodic task sets than basic RMS.
  • Provides a clear scheduling rule: select the earliest deadline.
  • Useful in systems with varying job deadlines.

12. EDF Limitations

  • Dynamic priority management can add implementation complexity.
  • Overload can cause many deadline misses.
  • Blocking and resource sharing require additional analysis.
  • Deadline and release-time tracking must be correct.
  • Multiprocessor EDF has more complex scheduling behavior.
  • High utilization leaves little room for interrupt and kernel overhead.

13. EDF and FreeRTOS

Standard FreeRTOS uses fixed-priority scheduling rather than automatically selecting the ready task with the earliest absolute deadline.

FreeRTOS applications can still use deadline information for application-level logic, but changing task priorities dynamically does not automatically create a correct EDF scheduler.

Conceptual EDF selection logic

/* Conceptual pseudocode only */

while (ready_job_count > 0)
{
    selected_job = ready_jobs[0];

    for (i = 1; i < ready_job_count; i++)
    {
        if (ready_jobs[i].absolute_deadline <
            selected_job.absolute_deadline)
        {
            selected_job = ready_jobs[i];
        }
    }

    execute_or_dispatch(selected_job);
}

This illustrates the selection rule, not a complete scheduler implementation. A real EDF scheduler must also handle job release, preemption, execution accounting, deadline updates, blocking, context switching, and simultaneous deadlines.

Do not assume that a standard FreeRTOS project becomes EDF simply by calling vTaskPrioritySet(). A correct EDF implementation requires scheduler-level design and validation.

16. Lesson Summary

  • EDF is a dynamic-priority scheduling algorithm.
  • The ready job with the earliest absolute deadline is selected.
  • For ideal independent periodic implicit-deadline tasks on one preemptive processor, U ≤ 1 is necessary and sufficient.
  • Constrained and arbitrary deadlines require more general analysis.
  • Demand-bound analysis is useful for more general periodic task models.
  • EDF can provide high processor utilization but requires correct deadline management.
  • Standard FreeRTOS does not automatically implement EDF scheduling.
