1. Introduction

In a real-time system, completing a task is not enough. The task must produce its required result within the specified time limit.

Two important timing measurements are:

  • Execution time: The time a task actually spends executing on the CPU.
  • Response time: The elapsed time from the task's release until it completes.

A task can have a short execution time but a long response time because it may wait for CPU access, become blocked by a shared resource, or be interrupted by higher-priority activities.

Central concept: Execution time measures CPU work. Response time measures how long the task takes to deliver its completed result after release.

2. Execution Time

Execution time is the amount of processor time consumed by a task while its instructions are executing.

2.1 CPU execution time

Suppose a task requires 4 milliseconds of CPU processing. If it executes continuously without interruption, its execution time is 4 ms.

If another task preempts it, the elapsed time between its start and completion becomes longer, but the task's own CPU execution requirement remains 4 ms.

2.2 Types of execution-time measurements

MeasurementMeaning
Actual execution timeCPU time consumed during a particular execution.
Average execution timeAverage CPU time observed across multiple executions.
Best-case execution time (BCET)Shortest execution time under specified conditions.
Worst-case execution time (WCET)A safe upper bound on execution time under stated assumptions.
Important: The longest execution time observed during testing is not automatically the WCET. A valid WCET bound must account for relevant execution paths, processor behavior, memory effects, compiler behavior, and operating conditions.

3. Waiting Time

Waiting time is the time a released task spends ready to execute but not currently receiving CPU time.

For example, a low-priority task may become ready but remain in the Ready state while a higher-priority task executes.

  • The task has been released.
  • It is eligible to execute.
  • The scheduler has not selected it yet.
  • It receives no CPU execution during this waiting interval.

Waiting time is different from execution time because the processor is not executing that task during the waiting interval.

4. Blocking Time

Blocking time occurs when a task cannot continue because it is waiting for an event or resource.

Common reasons include:

  • Waiting to acquire a mutex.
  • Waiting for data in a message queue.
  • Waiting for a semaphore or event.
  • Waiting for an I/O operation to complete.
  • Waiting for a specified delay or timeout.

In fixed-priority response-time analysis, blocking due to lower-priority tasks holding shared resources is especially important. This is often represented by a blocking term, B.

A task blocked while waiting for a mutex is not executing on the CPU. Its waiting interval contributes to response time, even though it does not contribute to its own CPU execution time.

5. Preemption and Interference

Preemption occurs when the scheduler suspends a currently executing task so that another eligible task can use the CPU.

In a priority-based preemptive RTOS:

  • A higher-priority ready task can preempt a lower-priority running task.
  • The preempted task normally remains ready to execute again.
  • It resumes when the scheduler selects it.

Interference is the time during which other activities delay the completion of the task being analyzed.

Possible sources include:

  • Higher-priority tasks.
  • Interrupt service routines.
  • Scheduler and context-switch overhead.
  • Other processor activities included in the timing model.

6. Response Time

Response time is the elapsed time between the release of a task and its completion.

Response Time (R) = Completion Time − Release Time

Let:

  • r: Release time of the task.
  • s: First execution start time.
  • f: Completion time.
  • C: Total CPU execution time consumed by the task.

Then:

R = f − r
Waiting Before First Execution = s − r

Response time includes all elapsed intervals between release and completion, including CPU execution and relevant delays.

7. Response-Time Decomposition

For a simplified timing model, response time can be represented as:

R = C + W + B + I + O
SymbolComponentDescription
CExecution timeCPU time consumed by the task itself.
WReady waiting timeTime waiting for CPU access while ready.
BBlocking timeTime waiting for a resource or event.
IInterferenceTime consumed by other tasks or interrupts that delay completion.
OOverheadRelevant scheduling, dispatch, or context-switch overhead.
This is a conceptual decomposition, not a universal equation for every RTOS analysis method. The terms must represent distinct, non-overlapping intervals. If a response-time formula already includes interrupt or scheduling interference, do not add those terms again.

8. Numerical Example 1 – Waiting and Execution Time

A task has the following timing information:

ParameterValue
Release time0 ms
First execution start3 ms
Execution time4 ms
Completion time7 ms

Step 1: Calculate waiting time

Waiting Time = 3 − 0 = 3 ms

Step 2: Calculate response time

R = 7 − 0 = 7 ms

Step 3: Verify

R = Waiting Time + Execution Time = 3 + 4 = 7 ms

Result: The task consumes 4 ms of CPU time but takes 7 ms from release to completion.

9. Numerical Example 2 – Blocking and Interference

A task requires 5 ms of CPU execution. During its response interval, it experiences 2 ms of resource blocking and 3 ms of interference.

ComponentDuration
Task execution (C)5 ms
Resource blocking (B)2 ms
Interference (I)3 ms

Calculation

R = C + B + I
R = 5 + 2 + 3 = 10 ms

Result: The task needs 5 ms of CPU time but its total response time is 10 ms.

This calculation assumes the three intervals are separate, do not overlap, and that no additional overhead needs to be included.

10. Numerical Example 3 – Multiple Delay Sources

Consider a task with the following timing characteristics:

  • Release time = 0 ms.
  • Ready waiting time = 2 ms.
  • Resource blocking time = 1 ms.
  • CPU execution time = 4 ms.
  • Preemption/interference time = 2 ms.

Calculation

R = W + B + C + I
R = 2 + 1 + 4 + 2 = 9 ms

Result: The task completes 9 ms after release, although it requires only 4 ms of CPU execution.

11. Worst-Case Response Time

Worst-case response time (WCRT) is a safe upper bound on the response time of a task under specified scheduling, workload, resource-sharing, and hardware assumptions.

WCRT analysis is important because a real-time system must be designed to satisfy timing constraints even under demanding conditions.

Worst-Case Response Time ≤ Relative Deadline

If the calculated safe response-time bound is less than or equal to the task's relative deadline, the task meets its deadline under the assumptions of the analysis.

ConditionInterpretation
R ≤ DDeadline is met under the modeled assumptions.
R > DDeadline cannot be guaranteed by that response-time bound.
R = DTask completes exactly at its deadline.
An observed response time from a test run is not automatically a proven WCRT. Testing provides measurements for the tested conditions; formal or conservative analysis is needed to establish a safe bound.

12. Response-Time Analysis in Fixed-Priority Scheduling

In fixed-priority preemptive scheduling, a task's response time can be affected by:

  • Its own execution requirement.
  • Blocking from lower-priority tasks holding shared resources.
  • Interference from higher-priority tasks.
  • Relevant interrupt and scheduling overhead.

Conceptually, response-time analysis repeatedly estimates how long a task takes to complete while accounting for the higher-priority work that can execute before it finishes.

The detailed fixed-priority response-time recurrence and numerical analysis will be covered in Lesson 08: Response Time Analysis.

13. Execution Time vs Response Time vs Turnaround Time

ParameterDefinitionMeasurement
Execution timeCPU time consumed by a task.CPU execution intervals.
Response timeRelease-to-completion elapsed time.Completion − release.
Turnaround timeElapsed time from submission or arrival to completion.Completion − submission/arrival.
Waiting timeTime spent ready but not executing.Ready-state waiting intervals.
Blocking timeTime spent unable to proceed while waiting for an event/resource.Blocked intervals.

Turnaround time is commonly used in general operating-system scheduling. For a real-time task, response time is normally measured from the defined release event to task completion.

14. Measuring Task Timing in FreeRTOS

In FreeRTOS-based systems, timing measurements can help developers understand task execution and scheduling behavior.

14.1 Useful measurement techniques

  • Record a timestamp when a task is released or notified.
  • Record the timestamp when the task begins executing.
  • Record another timestamp when the task completes its required work.
  • Use trace hooks or a trace tool to observe task state transitions.
  • Repeat measurements under representative system load.

14.2 Runtime statistics

FreeRTOS provides optional runtime-statistics facilities, including vTaskGetRunTimeStats(), when the required configuration and application-provided runtime counter are available.

These statistics report accumulated CPU runtime for tasks. They are useful for analyzing CPU usage, but they do not automatically establish WCET or worst-case response time.

14.3 Important timing considerations

  • The runtime counter must have suitable resolution and a correctly implemented hardware source.
  • Timestamp reads introduce measurement overhead.
  • Tick-based timing has resolution limited by the configured tick frequency.
  • Use a higher-resolution timer when finer timing measurements are required and supported.
  • Test under realistic interrupt load, task load, and resource contention.
The availability of a FreeRTOS runtime-statistics API does not prove that a particular MCU/compiler/debugger combination has a working FreeRTOS port. Verify the selected port and timer implementation before using these techniques on hardware.

15. Timing Analysis Using Keil uVision and LPC2129

For LPC2129 experiments in Keil uVision, the simulator can help inspect program execution, CPU registers, memory, and peripheral-register behavior supported by the simulation model.

For the user's LPC2129 clock configuration:

ParameterValue
FOSC12 MHz
CCLK60 MHz
PCLK15 MHz
Timer prescaler PR14999
Timer counter increment1 ms, assuming the stated peripheral clock and prescaler configuration

A timer can be used to record timestamps around a software operation. For example, if the timer count is read at the start and end of a function, the difference gives an elapsed-time measurement in timer ticks, subject to timer configuration and wraparound handling.

/* Conceptual timer-based elapsed-time measurement */

unsigned int start_time;
unsigned int end_time;
unsigned int elapsed_time;

start_time = TIMER0_TC;

/* Execute the operation being measured */
perform_task_operation();

end_time = TIMER0_TC;

/* Handle counter wraparound in production code */
elapsed_time = end_time - start_time;

Important: This is conceptual C code. The timer register name and initialization must match the actual LPC2129 header and project configuration. It is not a complete FreeRTOS application.

  • Simulator timing is not necessarily identical to physical hardware timing.
  • Instruction execution measurements may depend on simulator settings.
  • External device delays and electrical behavior are not fully represented by a CPU simulator.
  • LPC2129 uses ARM7TDMI-S; do not use Cortex-M-specific DWT cycle-counter examples.
  • Do not assume that a FreeRTOS LPC2129/Keil port is available without verifying the actual port.

16. Common Mistakes

MistakeCorrect understanding
Execution time equals response time.Response time includes execution and all relevant elapsed delays.
Waiting time is CPU execution.Ready waiting means the task is not using the CPU.
Every delay is resource blocking.Blocking, ready waiting, and intentional delays are distinct states or intervals.
Preemption increases the task's CPU requirement.Preemption generally increases elapsed response time, not the task's own execution requirement.
One measured maximum proves WCET.WCET requires a safe bound under stated assumptions.
Runtime statistics prove deadline compliance.Runtime statistics alone do not prove worst-case response-time bounds.
All timing components can always be added directly.Only distinct, non-overlapping intervals should be added in a simple decomposition.

17. Lesson Summary

  • Execution time is the CPU time required by a task.
  • Response time is the elapsed time from release to completion.
  • Waiting time occurs when a task is ready but not executing.
  • Blocking time occurs when a task waits for a resource or event.
  • Preemption and interrupt interference can increase response time.
  • Worst-case response time must be bounded against the task deadline.
  • Runtime measurements are useful but do not automatically prove WCET or WCRT.
  • Keil simulator measurements must not be treated as physical hardware guarantees.
