Queues are one of the most important communication mechanisms in FreeRTOS. They allow independent tasks to exchange data without directly sharing and modifying the same application variables.

2. What Is Task-to-Task Communication?

In a multitasking system, different tasks perform different operations. One task may collect sensor data while another task processes or displays that data. These tasks need a communication mechanism to exchange information.

Task-to-task communication is the exchange of information or synchronization events between independently scheduled tasks.

Example

  • Sensor Task: Reads temperature values.
  • Processing Task: Performs calculations.
  • Display Task: Displays processed values.
+-------------+       +-------------+
| Sensor Task | ----> | Processing  |
|             | Queue | Task        |
+-------------+       +-------------+
                            |
                            | Queue
                            v
                      +-------------+
                      | Display Task|
                      +-------------+

3. Why Are Queues Used for Task Communication?

A shared global variable can be used for simple data exchange, but it may create race conditions when multiple tasks access the same data. A FreeRTOS queue provides a structured communication mechanism with built-in synchronization and optional blocking.

FeatureShared VariableFreeRTOS Queue
Data storageApplication-managed variable.Kernel-managed queue storage.
Data transferTasks read/write shared memory.Items copied using queue APIs.
SynchronizationMust be designed separately.Queue operations coordinate access.
Multiple pending itemsRequires additional design.Supported up to queue capacity.
Blocking behaviorNot provided by a variable.Senders and receivers can block.

4. Producer-Consumer Architecture

The producer-consumer model is a common task communication architecture. A producer generates data and places it into a queue. A consumer retrieves the data and processes it. 

       PRODUCER TASK
             |
             | xQueueSend()
             v
      +--------------+
      | FreeRTOS     |
      | Queue        |
      +--------------+
             |
             | xQueueReceive()
             v
       CONSUMER TASK

Producer Task

  • Generates application data.
  • Sends data into the queue.
  • Can block if the queue is full.

Consumer Task

  • Waits for data from the queue.
  • Receives and processes items.
  • Can block if the queue is empty.

5. Queue Creation for Task Communication

Before two tasks can communicate through a queue, the application must create the queue and share its handle with both tasks. 

#include "FreeRTOS.h"
#include "queue.h"

QueueHandle_t dataQueue;

void CreateCommunicationQueue(void)
{
    dataQueue = xQueueCreate(
        10,
        sizeof(int)
    );

    if (dataQueue == NULL)
    {
        /* Handle allocation failure */
    }
}
ParameterDescription
10Maximum number of items stored in the queue.
sizeof(int)Size of each queue item in bytes.

6. Sending Data from a Producer Task

A producer task uses xQueueSend() to place an item into a queue. The queue copies the specified item into its own storage.

Syntax

BaseType_t xQueueSend(
    QueueHandle_t xQueue,
    const void *pvItemToQueue,
    TickType_t xTicksToWait
);

Example

void ProducerTask(void *pvParameters)
{
    int sensorValue = 100;

    for (;;)
    {
        if (xQueueSend(
                dataQueue,
                &sensorValue,
                pdMS_TO_TICKS(100)
            ) == pdPASS)
        {
            /* Data sent successfully */
        }
        else
        {
            /* Queue remained full */
        }

        sensorValue++;

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

7. Receiving Data in a Consumer Task

A consumer task uses xQueueReceive() to retrieve an item from the queue. The received item is copied into the application buffer and removed from the queue.

Syntax

BaseType_t xQueueReceive(
    QueueHandle_t xQueue,
    void *pvBuffer,
    TickType_t xTicksToWait
);

Example

void ConsumerTask(void *pvParameters)
{
    int receivedValue;

    for (;;)
    {
        if (xQueueReceive(
                dataQueue,
                &receivedValue,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process receivedValue */
        }
    }
}

The consumer blocks while the queue is empty, subject to the configured wait behavior. When data becomes available, the task can become Ready.

8. Complete Producer-Consumer Program

This example demonstrates two tasks communicating through a queue. The producer sends integer values, and the consumer receives and processes them. 

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t dataQueue;

void ProducerTask(void *pvParameters)
{
    int value = 1;

    for (;;)
    {
        if (xQueueSend(
                dataQueue,
                &value,
                pdMS_TO_TICKS(100)
            ) == pdPASS)
        {
            /* Value sent */
        }

        value++;

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ConsumerTask(void *pvParameters)
{
    int receivedValue;

    for (;;)
    {
        if (xQueueReceive(
                dataQueue,
                &receivedValue,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process receivedValue */
        }
    }
}

int main(void)
{
    dataQueue = xQueueCreate(
        5,
        sizeof(int)
    );

    if (dataQueue == NULL)
    {
        for (;;)
        {
        }
    }

    if (xTaskCreate(
            ProducerTask,
            "Producer",
            configMINIMAL_STACK_SIZE,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
        }
    }

    if (xTaskCreate(
            ConsumerTask,
            "Consumer",
            configMINIMAL_STACK_SIZE,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
        }
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program Explanation

  1. A queue is created with five integer positions.
  2. The producer task generates integer values.
  3. The producer sends each value into the queue.
  4. The consumer waits for an available item.
  5. The consumer receives and processes the item.
  6. The queue provides the data-transfer mechanism between tasks.

Expected Result

The producer generates values such as 1, 2, 3, 4 and so on. The consumer receives the queued values in FIFO order and processes them. The exact execution timing depends on task priorities, scheduling and system load.

9. FIFO Communication Between Tasks

FreeRTOS queues normally operate in First-In, First-Out order when items are sent to the back and received from the front. 

Producer sends:

10 -> 20 -> 30

Queue:
+----+----+----+
| 10 | 20 | 30 |
+----+----+----+
  ^
  |
Next item received

Consumer receives:

10 -> 20 -> 30

The receiving task obtains the oldest queued item first when using normal FIFO send and receive operations.

10. Communication Between Multiple Producers and One Consumer

A single queue can be shared by multiple producer tasks. Each producer sends items to the same queue, and one consumer receives them. 

+----------------+
| Producer Task 1|
+----------------+
        |
        |
        v
   +----------+
   |          |
   |  Queue   | -----> Consumer Task
   |          |
   +----------+
        ^
        |
+----------------+
| Producer Task 2|
+----------------+

The queue serializes its own operations. However, the application must still define how to identify the source of each message if that information matters.

Message Structure Example

typedef struct
{
    int sourceID;
    int data;
} Message_t;

A producer can send a complete structure. The consumer receives the structure and uses sourceID to identify the producer.

11. Communication Between One Producer and Multiple Consumers

A queue can also be shared by multiple consumer tasks. When an item is received, it is removed from the queue and delivered to one receiving task. 

              Producer
                 |
                 v
             +-------+
             | Queue |
             +-------+
              /     \
             v       v
        Consumer  Consumer
          Task 1    Task 2
A normal FreeRTOS queue distributes items among competing consumers. It does not broadcast every item to all consumers. For broadcast behavior, use separate queues, an event group, or another suitable design.

12. Blocking and Non-Blocking Communication

Queue operations can be configured to wait for a specified number of ticks when the queue is full or empty.

Wait ValueBehavior
0Return immediately if the operation cannot complete.
Finite tick valueWait up to the specified number of ticks.
portMAX_DELAYWait indefinitely where supported by the configuration.

Non-Blocking Send

xQueueSend(
    dataQueue,
    &value,
    0
);

Blocking Receive

xQueueReceive(
    dataQueue,
    &receivedValue,
    portMAX_DELAY
);

13. Sending Structures Through Queues

Queues can transfer structures, not only individual integer values. The queue item size must match the structure size.

Structure Definition

typedef struct
{
    int temperature;
    int humidity;
    int sensorID;
} SensorData_t;

Queue Creation

QueueHandle_t sensorQueue;

sensorQueue = xQueueCreate(
    5,
    sizeof(SensorData_t)
);

Sending Structure

SensorData_t sensorData;

sensorData.temperature = 28;
sensorData.humidity = 65;
sensorData.sensorID = 1;

xQueueSend(
    sensorQueue,
    &sensorData,
    0
);

Receiving Structure

SensorData_t receivedData;

if (xQueueReceive(
        sensorQueue,
        &receivedData,
        portMAX_DELAY
    ) == pdPASS)
{
    /* Use receivedData fields */
}
The queue copies the complete structure. For structures containing pointers, only the pointer values are copied. The pointed-to objects require a separate lifetime and ownership strategy.

14. Queue Communication Using Pointer Items

A queue can also store pointers to data objects. This can reduce copying of large data structures, but it introduces additional memory-management requirements. 

typedef struct
{
    int sensorValue;
    int sensorID;
} SensorData_t;

QueueHandle_t pointerQueue;

/* Queue stores pointers */
pointerQueue = xQueueCreate(
    5,
    sizeof(SensorData_t *)
);

Sending a Pointer

SensorData_t *dataPtr;

xQueueSend(
    pointerQueue,
    &dataPtr,
    0
);

Receiving a Pointer

SensorData_t *receivedPtr;

if (xQueueReceive(
        pointerQueue,
        &receivedPtr,
        portMAX_DELAY
    ) == pdPASS)
{
    /* Access the pointed-to object */
}
The queue copies the pointer, not the pointed-to structure. Ensure that the object remains valid until the receiver finishes using it. Define who owns and releases the memory, and avoid sending pointers to short-lived local variables.

15. Queue Communication vs Direct Shared Memory

FeatureQueue CommunicationShared Memory
Data transferCopies items through queue APIs.Tasks access common memory.
SynchronizationBuilt into queue operations.Must be designed explicitly.
Data bufferingMultiple items can be pending.Requires application-managed buffering.
Memory overheadQueue storage and control structures.Shared data storage and synchronization objects.
Best suited forMessage and data exchange.Large shared data with carefully managed access.

16. Best Practices for Queue-Based Communication

  • Choose queue length according to producer rate and consumer response time.
  • Choose an item size that matches the actual data structure.
  • Always check xQueueSend() and xQueueReceive() return values.
  • Use blocking operations when appropriate instead of continuous polling.
  • Keep queue items reasonably small where practical.
  • Use a defined ownership protocol when sending pointers.
  • Use separate queues when independent consumers need every message.
  • Do not assume a queue broadcasts messages.
  • Use FromISR APIs when communicating from interrupt context.
  • Define queue-full and queue-empty recovery behavior.

17. Practical Experiment

Objective: Implement communication between two FreeRTOS tasks using a queue.

Procedure

  1. Create a queue for integer values.
  2. Create a producer task.
  3. Create a consumer task.
  4. Send values from the producer task.
  5. Receive values in the consumer task.
  6. Use a finite timeout for the send operation.
  7. Use a blocking receive operation.
  8. Observe task states and queue contents using available debugging tools.
  9. Repeat the experiment with a structure as the queue item.

Expected Result

The producer sends data to the queue and the consumer retrieves it in FIFO order. When the queue is empty, the consumer can block until data arrives. When the queue is full, the producer can wait or handle the failed send according to its timeout.

18. Common Programming Mistakes

MistakeCorrection
Incorrect queue item sizeUse the correct sizeof expression.
Ignoring queue creation failureCheck for NULL before using the handle.
Ignoring send or receive failureCheck the returned status.
Assuming queue sends broadcast dataUse separate queues or another broadcast design.
Sending pointers to local variablesEnsure the pointed-to memory remains valid.
Using task APIs from an ISRUse the corresponding FromISR API.
Making the queue too smallAccount for bursts and consumer delays.

20. Lesson Summary

  • Task-to-task communication allows independent tasks to exchange information.
  • FreeRTOS queues provide buffered communication.
  • Producer tasks send data using xQueueSend().
  • Consumer tasks receive data using xQueueReceive().
  • Queue operations copy fixed-size items.
  • Queues support integer values, structures and pointer values.
  • Normal queues distribute items among competing consumers; they do not broadcast.
  • Blocking time controls how long a task waits for queue space or data.
  • Pointer-based communication requires careful memory ownership.
