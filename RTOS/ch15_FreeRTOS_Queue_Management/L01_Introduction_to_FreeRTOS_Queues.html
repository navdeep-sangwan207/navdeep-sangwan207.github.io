2. What Is a Queue?

A queue is a data structure used to store multiple items in an organized sequence. FreeRTOS queues provide a mechanism for communication and synchronization between tasks and interrupt service routines.

In the standard queue operation, items are received in the order in which they were sent. This is commonly called FIFO (First In, First Out).

Basic Queue Representation

        SEND DATA
            |
            v
    +-------------------+
    |     QUEUE         |
    |-------------------|
    | Item 1            |
    | Item 2            |
    | Item 3            |
    | Item 4            |
    +-------------------+
            |
            v
       RECEIVE DATA

The sender places an item into the queue. The receiver retrieves an item from the queue.

3. Why Are Queues Required in RTOS?

In multitasking applications, different tasks often perform different operations. One task may collect sensor data, while another task processes or displays that data.

Queues allow these tasks to exchange data without requiring them to execute at the same time.

Example: Sensor and Display Tasks

Sensor Task
     |
     | Sensor data
     v
  FreeRTOS Queue
     |
     | Received data
     v
Display Task

Advantages

  • Provides structured inter-task communication.
  • Separates data production from data processing.
  • Can block a receiver until data becomes available.
  • Can block a sender while the queue is full.
  • Provides controlled data transfer.
  • Reduces the need for shared global data.
  • Supports task-to-task and ISR-to-task communication through suitable APIs.

4. FIFO – First In, First Out

A normal FreeRTOS queue uses FIFO behavior. The first item sent to the queue is normally the first item received.

Example

Suppose a task sends three values:

Queue Send: 10
Queue Send: 20
Queue Send: 30

The queue contains:

FRONT                     BACK
  |                         |
  v                         v
+------+    +------+    +------+
|  10  | -> |  20  | -> |  30  |
+------+    +------+    +------+

The receiver normally receives 10, then 20, then 30.

FreeRTOS also provides queue operations that can place an item at the front or back of a queue. FIFO behavior describes the normal send-to-back and receive-from-front pattern.

6. Queue Length and Item Size

When creating a queue, two important parameters are specified:

  • Queue length: Maximum number of items.
  • Item size: Number of bytes in each item.

Example

QueueHandle_t dataQueue;

dataQueue = xQueueCreate(
    5,
    sizeof(int)
);

This creates a queue with a capacity of five integer items, assuming dynamic allocation is enabled and sufficient heap memory is available.

ParameterValue
Queue length5
Item typeint
Item sizesizeof(int) bytes
Maximum stored items5

The queue's item storage requirement is approximately:

Queue item storage = Queue length × Item size

The total memory allocation also includes queue control and implementation overhead.

7. Queue Handle

A queue handle is a variable of type QueueHandle_t. It is used to refer to a queue created by FreeRTOS. 

QueueHandle_t sensorQueue;

After successful queue creation, the returned handle is used in queue operations. 

sensorQueue = xQueueCreate(
    10,
    sizeof(int)
);

if (sensorQueue == NULL)
{
    /* Queue creation failed */
}
QueueHandle_t is an opaque handle. Application code should use the public queue APIs rather than accessing internal queue-control structures.

8. Queue Data Transfer – Copying Mechanism

FreeRTOS queues normally copy each item into the queue's internal storage when it is sent. When an item is received, it is copied from the queue into the receiver's destination memory.

Data Transfer

Sender Variable
      |
      | xQueueSend()
      v
Queue Internal Storage
      |
      | xQueueReceive()
      v
Receiver Variable

For example, if an integer value is sent, the queue stores a copy of that integer. Changing the sender's original variable after the send does not change the queued copy.

If the queue item is a pointer, FreeRTOS copies the pointer value, not the data pointed to. The application must manage buffer ownership and lifetime correctly.

The xQueueCreate() function creates a queue dynamically.

10. Queue Sender and Receiver

Sender

The sender task uses a queue send API to place an item into the queue. 

int value = 100;

xQueueSend(
    sensorQueue,
    &value,
    0
);

Receiver

The receiver task uses a queue receive API to retrieve an item. 

int receivedValue;

xQueueReceive(
    sensorQueue,
    &receivedValue,
    portMAX_DELAY
);

The receiver waits indefinitely for an item when portMAX_DELAY is used, subject to the relevant FreeRTOS configuration.

11. Blocking and Non-Blocking Queue Operations

Queue APIs allow the application to specify how long a task should wait when a queue cannot immediately complete the requested operation.

Wait TimeBehavior
0 ticksDo not wait; return immediately if the operation cannot complete.
Finite ticksWait up to the specified number of ticks.
portMAX_DELAYWait indefinitely when supported by the configuration.

Example – Non-Blocking Send

if (xQueueSend(
        sensorQueue,
        &value,
        0
    ) == pdPASS)
{
    /* Item successfully queued */
}
else
{
    /* Queue is full */
}

Example – Blocking Receive

if (xQueueReceive(
        sensorQueue,
        &receivedValue,
        portMAX_DELAY
    ) == pdPASS)
{
    /* Process received item */
}

13. Queue vs Shared Global Variable

FeatureQueueShared Global Variable
Data storageCan store multiple items.Usually stores one current value.
Data transferCopies items through queue APIs.Tasks access the same memory.
SynchronizationQueue operations provide synchronization behavior.Requires appropriate synchronization.
BlockingSender and receiver can block.No built-in blocking behavior.
Multiple pending valuesSupported up to queue capacity.New writes may overwrite old values.

A queue is often a better choice when every message or data item must be transferred. A shared variable may be appropriate for a carefully synchronized latest-value design.

14. Important Queue Programming Rules

  • Always check whether queue creation succeeds.
  • Use the correct item size.
  • Check the return value of send and receive operations.
  • Choose queue capacity based on expected data rate and consumer delays.
  • Define a policy for queue-full conditions.
  • Use the appropriate FromISR API inside interrupt service routines.
  • Never use a blocking queue operation inside an ISR.
  • Do not assume sending a pointer copies the pointed-to data.
  • Manage pointer ownership and buffer lifetime carefully.
  • Use queues for data transfer and event communication where appropriate.

15. Practical Experiment – Basic Queue Communication

Objective: Understand how one task sends data to another task using a FreeRTOS queue.

Procedure

  1. Create a queue with capacity five and item size sizeof(int).
  2. Create a sender task.
  3. Create a receiver task.
  4. Send integer values through the queue.
  5. Receive values in the receiver task.
  6. Observe the received values using a debugger or suitable output mechanism.
  7. Test what happens when the queue is full.
  8. Test what happens when the queue is empty.

Expected Result

The receiver obtains the values in queue order when using normal send-to-back and receive-from-front operations. If the queue is empty, a blocking receiver waits for data. If the queue is full, a sender may wait or return failure depending on its wait time.

16. LPC2129 and Keil Simulator Considerations

The LPC2129 uses an ARM7TDMI-S processor. Running FreeRTOS queue examples requires a compatible kernel port and correct project integration.

  • Verify the ARM7-compatible FreeRTOS port.
  • Verify the compiler and startup configuration.
  • Verify heap configuration and available memory.
  • Use debugger inspection to examine task execution where supported.
  • Do not assume that queue examples will run in the current Keil simulator without a working port.
The examples are generic FreeRTOS educational code. They are not verified LPC2129 Keil simulator projects.

18. Lesson Summary

  • A FreeRTOS queue is used for inter-task and ISR-to-task communication.
  • Normal queue operation follows FIFO order.
  • Queue length determines the maximum number of stored items.
  • Item size determines the size of each queue item in bytes.
  • xQueueCreate() creates a queue dynamically.
  • Queue operations normally copy data into and out of queue storage.
  • Blocking time controls how long a task waits.
  • Pointer queues copy pointer values, not pointed-to data.
  • Queues help separate data production from data processing.
