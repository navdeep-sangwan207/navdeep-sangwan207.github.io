Queue Communication From ISR

Interrupt-Safe Data Transfer and ISR-to-Task Communication in FreeRTOS

1. Learning Objectives

Interrupt Service Routines (ISRs) handle time-sensitive hardware events. In a FreeRTOS application, an ISR may need to transfer data to a task for further processing. Queue FromISR APIs provide a mechanism for this communication.

  • Understand ISR-to-task communication.
  • Differentiate task-context and ISR-context queue APIs.
  • Study xQueueSendFromISR().
  • Study xQueueReceiveFromISR().
  • Understand higher-priority task wake-up behavior.
  • Learn interrupt-safe programming practices.
  • Develop an ISR-to-task communication example.

2. What Is ISR-to-Task Communication?

An interrupt occurs when a hardware or configured software event requires processor attention. The processor executes the corresponding Interrupt Service Routine.

An ISR should generally perform only essential, short-duration operations. If more processing is required, the ISR can place data into a queue and allow a task to process it later.

3. Why Should an ISR Communicate With a Task?

Some operations are not suitable for execution inside an ISR because they may take too much time or require blocking. A task provides a suitable context for extended processing.

ISR ResponsibilityTask Responsibility
Acknowledge or clear the interrupt source as required.Perform application-level processing.
Capture essential event information.Analyze received data.
Place data into a queue using an ISR-safe API.Update application state.
Request a context switch when appropriate.Perform longer operations and communication.

4. Task APIs vs ISR APIs

FreeRTOS provides separate API functions for task context and interrupt context. An ISR must use the appropriate FromISR function where one is provided.

Task Context APIISR Context APIPurpose
xQueueSend()xQueueSendFromISR()Send an item to a queue.
xQueueReceive()xQueueReceiveFromISR()Receive an item from a queue.
xQueuePeek()xQueuePeekFromISR()Inspect the front item without removing it.
xSemaphoreGive()xSemaphoreGiveFromISR()Give a semaphore.
Do not call task-context queue APIs from an ISR. Task APIs may block or perform operations that are not valid in interrupt context.

5. xQueueSendFromISR() Function

The xQueueSendFromISR() function sends an item to a queue from an Interrupt Service Routine. It does not block.

Syntax

BaseType_t xQueueSendFromISR(
    QueueHandle_t xQueue,
    const void *pvItemToQueue,
    BaseType_t *pxHigherPriorityTaskWoken
);

Parameters

ParameterDescription
xQueueHandle of the destination queue.
pvItemToQueuePointer to the item to copy into the queue.
pxHigherPriorityTaskWokenPointer to a flag indicating whether a higher-priority task was unblocked.

Return Value

  • pdPASS: Item was successfully placed in the queue.
  • errQUEUE_FULL: Queue had no available space.

6. Understanding pxHigherPriorityTaskWoken

When an ISR sends data to a queue, a task waiting for that data may become Ready. If the unblocked task has a higher priority than the task interrupted by the ISR, the kernel may need to switch tasks when the interrupt finishes. 

BaseType_t xHigherPriorityTaskWoken = pdFALSE;

xQueueSendFromISR(
    dataQueue,
    &eventData,
    &xHigherPriorityTaskWoken
);

/* Request port-specific ISR yield
   when required. */

The variable is initialized to pdFALSE before the ISR operation. The API may set it to pdTRUE when a higher-priority task has been unblocked.

The exact ISR-yield macro or mechanism depends on the FreeRTOS port. A common macro name is portYIELD_FROM_ISR(), but the selected port's documentation must be followed.

7. xQueueReceiveFromISR() Function

The xQueueReceiveFromISR() function receives an item from a queue inside an ISR without blocking. The item is copied into the application buffer and removed from the queue.

Syntax

BaseType_t xQueueReceiveFromISR(
    QueueHandle_t xQueue,
    void *pvBuffer,
    BaseType_t *pxHigherPriorityTaskWoken
);

Parameters

ParameterDescription
xQueueQueue handle.
pvBufferPointer to the destination buffer.
pxHigherPriorityTaskWokenPointer to the task-woken flag.

Return Value

  • pdPASS: An item was successfully received.
  • errQUEUE_EMPTY: The queue contained no item.
Receiving from a queue in an ISR is less common than sending data from an ISR to a task. Use it only when the application design genuinely requires interrupt-context queue reception.

8. Complete ISR-to-Task Communication Example

The following is a generic FreeRTOS illustration. A hardware interrupt captures an event value and sends it to a queue. A task receives the value and processes it. 

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t eventQueue;

void EventProcessingTask(void *pvParameters)
{
    unsigned int eventValue;

    for (;;)
    {
        if (xQueueReceive(
                eventQueue,
                &eventValue,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process eventValue */
        }
    }
}

/*
 * Illustrative ISR body.
 * Connect this to the actual hardware
 * interrupt using the selected port's
 * interrupt registration mechanism.
 */
void HardwareEventISR(void)
{
    BaseType_t xHigherPriorityTaskWoken =
        pdFALSE;

    unsigned int eventValue = 1;

    xQueueSendFromISR(
        eventQueue,
        &eventValue,
        &xHigherPriorityTaskWoken
    );

    /*
     * Use the ISR-yield mechanism required
     * by the selected FreeRTOS port.
     */
    portYIELD_FROM_ISR(
        xHigherPriorityTaskWoken
    );
}

int main(void)
{
    eventQueue = xQueueCreate(
        5,
        sizeof(unsigned int)
    );

    if (eventQueue == NULL)
    {
        for (;;)
        {
        }
    }

    if (xTaskCreate(
            EventProcessingTask,
            "EventTask",
            configMINIMAL_STACK_SIZE,
            NULL,
            3,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
        }
    }

    /*
     * Configure the actual interrupt source
     * and enable it at the appropriate point
     * for the selected hardware and port.
     */

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program Explanation

  1. A queue is created to store event values.
  2. A processing task waits for queue data.
  3. The hardware ISR captures an event.
  4. The ISR sends the event using xQueueSendFromISR().
  5. The task-woken flag records whether a higher-priority task was unblocked.
  6. The port-specific yield mechanism is used when required.
  7. The processing task handles the event outside interrupt context.
The example assumes that the selected FreeRTOS port defines the shown ISR-yield macro. Some ports use a different form. Do not copy the ISR declaration or yield macro into a hardware project without checking the port documentation.

9. ISR Queue Overflow Handling

An ISR cannot wait for queue space. If the queue is full, the send operation fails immediately. The application must define what happens when an event cannot be queued.

Example

BaseType_t sendStatus;
BaseType_t xHigherPriorityTaskWoken =
    pdFALSE;

sendStatus = xQueueSendFromISR(
    eventQueue,
    &eventValue,
    &xHigherPriorityTaskWoken
);

if (sendStatus != pdPASS)
{
    /* Record or handle queue overflow */
}

Possible Strategies

  • Increase queue capacity based on event bursts.
  • Reduce processing time in the consumer task.
  • Use a counter to record lost events.
  • Use a hardware FIFO or DMA where appropriate.
  • Define whether the newest or oldest data has priority.

          |
          v

The task does not execute in the middle of the ISR. If a context switch is requested, the scheduler can select the task at the appropriate interrupt-exit point.

11. Interrupt Priority and FreeRTOS API Rules

Not every hardware interrupt is necessarily allowed to call FreeRTOS APIs. The processor and port define interrupt-priority rules that determine which interrupt levels may safely interact with the kernel.

  • Use only interrupts permitted to call the FreeRTOS API.
  • Follow the selected port's interrupt-priority rules.
  • Do not assume Cortex-M NVIC or BASEPRI rules apply to ARM7.
  • Keep ISRs short and avoid blocking operations.
  • Use the correct FromISR API.
  • Follow the port-specific ISR-yield convention.
LPC2129 uses an ARM7TDMI-S core and a Vectored Interrupt Controller (VIC). Cortex-M interrupt-priority configuration and BASEPRI instructions are not applicable to this processor.

14. Best Practices for ISR Queue Communication

  • Keep interrupt handlers short.
  • Use FromISR APIs rather than task-context APIs.
  • Never use a blocking queue operation inside an ISR.
  • Check the return value of every queue send.
  • Initialize the higher-priority-task-woken variable as required.
  • Use the correct port-specific ISR-yield mechanism.
  • Size the queue to handle expected event bursts.
  • Define an overflow strategy.
  • Copy small event records rather than performing lengthy processing in the ISR.
  • Ensure data buffers remain valid when transferring pointers.
  • Respect interrupt-priority restrictions for kernel API calls.

17. LPC2129 and Keil Simulator Considerations

  • LPC2129 uses ARM7TDMI-S and a VIC for interrupt management.
  • Verify a compatible FreeRTOS ARM7 port before using kernel APIs in an ISR.
  • Check the port-specific ISR declaration and context-saving requirements.
  • Verify how the port requests a context switch on interrupt exit.
  • Use simulator-supported interrupt behavior only where confirmed.
  • Do not assume physical UART, ADC or external interrupt signals are automatically simulated.
This lesson uses generic FreeRTOS API examples. It does not establish that a working LPC2129 FreeRTOS port is available in the user's Keil simulator setup.

19. Lesson Summary

  • ISRs handle interrupt events and should remain short.
  • Queue FromISR APIs support communication from interrupt context.
  • xQueueSendFromISR() sends an item without blocking.
  • xQueueReceiveFromISR() receives an item without blocking.
  • pxHigherPriorityTaskWoken indicates whether a higher-priority task was unblocked.
  • Port-specific mechanisms handle any required scheduling at interrupt exit.
  • Queue-full conditions must be handled explicitly.
  • Interrupt-priority restrictions depend on the selected processor port.
  • Extended processing should normally be performed in task context.
