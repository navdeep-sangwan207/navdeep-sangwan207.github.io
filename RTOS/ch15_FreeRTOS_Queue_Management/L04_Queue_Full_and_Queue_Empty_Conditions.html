Queue Full and Queue Empty Conditions

Queue Capacity, Blocking, Timeouts and Error Handling

Home RTOS Course Chapter 15

1. Learning Objectives

A FreeRTOS queue has a finite capacity. When all available positions contain items, the queue becomes full. When no items remain, the queue becomes empty. Correctly handling these conditions is essential for reliable inter-task communication.

  • Understand queue capacity.
  • Study full and empty queue conditions.
  • Learn queue status-checking functions.
  • Understand blocking and timeout behavior.
  • Study queue overflow and data-loss risks.
  • Learn queue sizing and error-handling techniques.
  • Understand producer and consumer rate differences.

2. Queue Capacity

Queue capacity is the maximum number of items that a queue can store at one time. It is defined when the queue is created. 

QueueHandle_t dataQueue;

dataQueue = xQueueCreate(
    5,
    sizeof(int)
);

In this example, the queue can hold five integer items. The queue does not grow automatically when additional data arrives.

PropertyDescription
Queue lengthMaximum number of stored items.
Item sizeSize of each item in bytes.
Current item countNumber of items currently stored.
Available spacesUnused queue positions.

3. Queue Full Condition

A queue becomes full when its current number of items reaches its maximum capacity. A normal send operation cannot insert another item until space becomes available.

Example: Queue Capacity = 4

After sending 10:
+----+----+----+----+
| 10 |    |    |    |
+----+----+----+----+

After sending 20 and 30:
+----+----+----+----+
| 10 | 20 | 30 |    |
+----+----+----+----+

After sending 40:
+----+----+----+----+
| 10 | 20 | 30 | 40 |
+----+----+----+----+

Queue is FULL.

A fifth send cannot complete immediately because all four positions are occupied.

4. Queue Empty Condition

A queue is empty when it contains no items. A receive operation cannot retrieve data until an item is inserted. 

Initially:
+----+----+----+----+
|    |    |    |    |
+----+----+----+----+

Queue is EMPTY.

After sending 10:
+----+----+----+----+
| 10 |    |    |    |
+----+----+----+----+

After receiving 10:
+----+----+----+----+
|    |    |    |    |
+----+----+----+----+

Queue is EMPTY again.

5. Queue Status Functions

FreeRTOS provides functions to inspect the current number of queued items and available spaces.

FunctionPurpose
uxQueueMessagesWaiting()Returns the number of items currently in the queue.
uxQueueSpacesAvailable()Returns the number of free item positions.
xQueueIsQueueEmpty()Checks whether the queue is empty.
xQueueIsQueueFull()Checks whether the queue is full.

Syntax

UBaseType_t uxQueueMessagesWaiting(
    QueueHandle_t xQueue
);

UBaseType_t uxQueueSpacesAvailable(
    QueueHandle_t xQueue
);

BaseType_t xQueueIsQueueEmpty(
    QueueHandle_t xQueue
);

BaseType_t xQueueIsQueueFull(
    QueueHandle_t xQueue
);
These status functions provide a snapshot. In a system with multiple tasks, another task may change the queue immediately after the status check. Prefer performing the actual send or receive operation and checking its return value.

6. Checking Queue Status

#include "FreeRTOS.h"
#include "queue.h"

QueueHandle_t dataQueue;

void CheckQueueStatus(void)
{
    UBaseType_t messages;
    UBaseType_t spaces;

    messages = uxQueueMessagesWaiting(dataQueue);
    spaces = uxQueueSpacesAvailable(dataQueue);

    if (xQueueIsQueueEmpty(dataQueue) == pdTRUE)
    {
        /* Queue is empty */
    }

    if (xQueueIsQueueFull(dataQueue) == pdTRUE)
    {
        /* Queue is full */
    }
}

This example reads the current queue status. It assumes that dataQueue is a valid, successfully created queue handle.

7. Handling a Full Queue

When a queue is full, the sender has several possible strategies.

Strategy 1: Non-Blocking Send

if (xQueueSend(
        dataQueue,
        &value,
        0
    ) == pdPASS)
{
    /* Send successful */
}
else
{
    /* Queue full: handle failure */
}

The sender returns immediately if the item cannot be inserted.

Strategy 2: Blocking Send

if (xQueueSend(
        dataQueue,
        &value,
        pdMS_TO_TICKS(100)
    ) == pdPASS)
{
    /* Send successful */
}
else
{
    /* Timeout or send failure */
}

The calling task can wait for up to the specified number of ticks for queue space.

Strategy 3: Use a Suitable Overflow Policy

  • Retry later when losing data is unacceptable.
  • Record an error counter for diagnostics.
  • Use a larger queue if memory permits and analysis supports it.
  • Reduce producer rate or improve consumer throughput.
  • Use an overwrite strategy when only the latest value matters.

8. Handling an Empty Queue

When a queue is empty, a receiver cannot retrieve an item immediately.

Strategy 1: Non-Blocking Receive

if (xQueueReceive(
        dataQueue,
        &receivedValue,
        0
    ) == pdPASS)
{
    /* Data received */
}
else
{
    /* No data available */
}

Strategy 2: Blocking Receive

if (xQueueReceive(
        dataQueue,
        &receivedValue,
        pdMS_TO_TICKS(500)
    ) == pdPASS)
{
    /* Process received data */
}
else
{
    /* Receive timed out */
}

Strategy 3: Wait Indefinitely

xQueueReceive(
    dataQueue,
    &receivedValue,
    portMAX_DELAY
);

The receiver remains blocked until data becomes available, subject to the applicable configuration and queue lifecycle.

9. Blocking Behavior and Task States

When a task requests an operation that cannot currently complete and specifies a non-zero wait time, FreeRTOS can place it in the Blocked state.

Becoming Ready does not mean that the task executes immediately. The scheduler selects it according to the scheduling policy and task priorities.

10. Queue Overflow and Data Loss

Queue overflow occurs when the application produces data faster than the consumer can process it for long enough that the queue reaches its capacity.

Example

  • Sensor task produces one item every 10 ms.
  • Display task consumes one item every 100 ms.
  • Items accumulate faster than they are consumed.
  • The queue eventually becomes full.

If the sender uses a zero wait time, subsequent send attempts can fail. If it waits, it may block and affect other work.

Possible Solutions

  • Increase queue capacity after memory and timing analysis.
  • Improve consumer execution time.
  • Reduce unnecessary data production.
  • Use a latest-value design if intermediate values are not needed.
  • Use an explicit data-loss policy and diagnostic counter.

11. Queue Underflow

In queue-based application discussions, underflow describes an attempt to consume data when no item is available. For FreeRTOS, a receive from an empty queue does not return an invalid item: it either fails immediately or waits according to the specified timeout.

ConditionResult
Empty queue, zero waitReceive fails immediately.
Empty queue, finite waitReceiver waits up to the timeout.
Data arrives during waitReceive can complete successfully.
No data arrives before timeoutReceive returns failure.

12. Producer and Consumer Rate Analysis

Queue capacity should be selected using producer rate, consumer rate, burst size and the longest expected period during which the consumer cannot process data.

Example

A producer generates 20 items per second. The consumer can process 20 items per second on average, but may be unavailable for 200 ms.

Items generated during that interval:

20 items/second × 0.2 seconds = 4 items

At least four free positions are needed to absorb this particular interruption, plus additional capacity if bursts or other delays are possible.

Equal average production and consumption rates do not guarantee that a queue will never fill. Burst arrivals, scheduling delays and execution-time variation must also be considered.

13. Practical Program – Full and Empty Handling

#include "FreeRTOS.h"
#include "queue.h"

QueueHandle_t dataQueue;

void QueueTest(void)
{
    int value;
    int received;

    dataQueue = xQueueCreate(
        3,
        sizeof(int)
    );

    if (dataQueue == NULL)
    {
        return;
    }

    value = 10;
    xQueueSend(dataQueue, &value, 0);

    value = 20;
    xQueueSend(dataQueue, &value, 0);

    value = 30;
    xQueueSend(dataQueue, &value, 0);

    /* Queue now contains three items */

    value = 40;

    if (xQueueSend(dataQueue, &value, 0) != pdPASS)
    {
        /* Queue is full */
    }

    if (xQueueReceive(
            dataQueue,
            &received,
            0
        ) == pdPASS)
    {
        /* One item removed */
    }

    /* A queue position is now available */

    if (xQueueSend(
            dataQueue,
            &value,
            0
        ) == pdPASS)
    {
        /* New item inserted */
    }

    vQueueDelete(dataQueue);
    dataQueue = NULL;
}

Program Explanation

  1. A queue is created with capacity three.
  2. Three values are inserted successfully.
  3. A fourth immediate send is expected to fail while the queue is full.
  4. One item is received and removed.
  5. The freed position allows another item to be sent.
  6. The queue is deleted after the demonstration operations.

14. Best Practices

  • Choose queue length based on measured or analysed workload.
  • Always check send and receive return values.
  • Use finite timeouts when indefinite blocking is not appropriate.
  • Avoid polling loops that continuously check queue status without yielding or blocking.
  • Track failed sends when data loss matters.
  • Do not rely on a status check as a guarantee that the next operation will succeed.
  • Use queue overwrite only when replacing old data is intentional.
  • Ensure queue users stop before queue deletion.
  • Use FromISR APIs in interrupt context.

15. LPC2129 and Keil Simulator Considerations

  • LPC2129 uses ARM7TDMI-S architecture.
  • Verify the selected FreeRTOS ARM7 port and compiler integration.
  • Check the configured heap and available RAM.
  • Use debugger variables or a supported trace facility to inspect queue-related application state.
  • Do not assume that simulated peripheral activity represents real hardware timing.
The examples in this lesson use generic FreeRTOS APIs. They are not verified LPC2129 Keil simulator projects.

17. Lesson Summary

  • A queue has a fixed capacity defined at creation.
  • A full queue cannot accept another normal item immediately.
  • An empty queue cannot provide an item immediately.
  • Queue status functions report the current state.
  • Send and receive operations can block for a configured time.
  • Non-blocking operations return immediately.
  • Overflow can cause failed sends and data loss.
  • Queue capacity must account for bursts and consumer delays.
  • Always check operation return values.
  • Coordinate queue deletion with all queue users.
