1. Learning Objectives

Blocking time determines how long a task waits when a queue operation cannot immediately complete. It is an important parameter in real-time application design because waiting affects task execution, response time and system behavior.

2. What Is Blocking Time?

Blocking time is the maximum period for which a task is willing to wait for a queue operation to become possible.

For example, a receiver task may request data from an empty queue. Instead of repeatedly checking the queue, it can block and allow another task to execute.

3. xTicksToWait Parameter

The queue send and receive functions use the xTicksToWait parameter to specify the maximum time a task waits when the operation cannot complete immediately.

xQueueSend()

BaseType_t xQueueSend(
    QueueHandle_t xQueue,
    const void *pvItemToQueue,
    TickType_t xTicksToWait
);

xQueueReceive()

BaseType_t xQueueReceive(
    QueueHandle_t xQueue,
    void *pvBuffer,
    TickType_t xTicksToWait
);
ParameterDescription
xTicksToWaitMaximum number of RTOS ticks the calling task will wait for the requested queue operation.

4. Types of Blocking Time

FreeRTOS queue operations commonly use three waiting strategies.

TypeValueBehavior
Non-blocking0Return immediately if the operation cannot complete.
Finite blockingPositive tick countWait up to the specified number of ticks.
Indefinite blockingportMAX_DELAYWait indefinitely when supported by the configuration.

5. Zero Blocking Time

When xTicksToWait is zero, the task does not wait for queue space or data. The operation either succeeds immediately or returns a failure status.

Example

int value = 100;

if (xQueueSend(
        dataQueue,
        &value,
        0
    ) == pdPASS)
{
    /* Data inserted */
}
else
{
    /* Queue is full */
}

Characteristics

  • Does not block the calling task.
  • Useful when the task must continue immediately.
  • Requires explicit failure handling.
  • May result in dropped data if the queue remains full.

6. Finite Blocking Time

A finite blocking time allows a task to wait for a specified number of RTOS ticks. If the required queue condition occurs before the timeout, the operation can complete successfully. Otherwise, it returns failure.

Example

int receivedValue;

if (xQueueReceive(
        dataQueue,
        &receivedValue,
        pdMS_TO_TICKS(200)
    ) == pdPASS)
{
    /* Data received */
}
else
{
    /* Receive timeout */
}

In this example, the task waits for up to approximately 200 milliseconds, subject to tick resolution and scheduling behavior.

7. Indefinite Blocking Time

An indefinite wait allows a task to remain blocked until the requested queue operation becomes possible.

Example

int receivedValue;

if (xQueueReceive(
        dataQueue,
        &receivedValue,
        portMAX_DELAY
    ) == pdPASS)
{
    /* Process received data */
}

The receiver remains blocked while the queue is empty. When data arrives, the task can become Ready and execute when selected by the scheduler.

For the traditional indefinite-blocking behavior, check the relevant configuration, including INCLUDE_vTaskSuspend. Indefinite blocking also requires a sound queue lifecycle: the application must not assume that deleting a queue safely wakes and cancels every blocked user.

8. RTOS Tick and Time Measurement

FreeRTOS measures blocking intervals using the RTOS tick count. A periodic tick interrupt advances the system tick.

The tick frequency is configured using configTICK_RATE_HZ.

Tick FrequencyNominal Tick Period
100 Hz10 ms
250 Hz4 ms
500 Hz2 ms
1000 Hz1 ms

The nominal tick period is calculated as:

Tick period = 1 / Tick frequency

#define configTICK_RATE_HZ 1000

At 1000 Hz, the nominal tick interval is 1 millisecond.

The RTOS tick is a scheduling time base. It is not automatically a high-resolution measurement clock or a calendar clock.

9. Millisecond-to-Tick Conversion

The pdMS_TO_TICKS() macro converts a time expressed in milliseconds into the corresponding RTOS tick count.

Syntax

pdMS_TO_TICKS(milliseconds)

Example

TickType_t waitTime;

waitTime = pdMS_TO_TICKS(100);

xQueueReceive(
    dataQueue,
    &receivedValue,
    waitTime
);

For a tick rate of 1000 Hz, 100 milliseconds corresponds to approximately 100 ticks. For a tick rate of 100 Hz, it corresponds to approximately 10 ticks.

Tick conversion has finite resolution. A short millisecond interval may convert to zero ticks. Do not assume every positive millisecond value produces a positive wait. Check the selected port and macro behavior.

10. Queue Timeout Behavior

A timeout occurs when a queue operation cannot complete within the allowed waiting period.

Receive Timeout Example

int sensorValue;

if (xQueueReceive(
        sensorQueue,
        &sensorValue,
        pdMS_TO_TICKS(500)
    ) == pdPASS)
{
    /* Process received sensor value */
}
else
{
    /* No data received before timeout */
}

If the queue remains empty for the entire waiting interval, the receive operation returns a failure status.

Send Timeout Example

int command = 1;

if (xQueueSend(
        commandQueue,
        &command,
        pdMS_TO_TICKS(100)
    ) == pdPASS)
{
    /* Command queued successfully */
}
else
{
    /* No queue space became available in time */
}

11. Blocking Time vs Execution Time

Blocking time is not the same as task execution time.

ParameterMeaning
Execution timeTime during which the CPU executes the task's instructions.
Blocking timeTime the task waits for an event or resource.
Ready waiting timeTime a Ready task waits for CPU scheduling.
Response timeTime from task release or triggering event to completion.

A task may spend time executing, waiting for a queue, waiting in the Ready state and being preempted by higher-priority tasks. These delays all matter when analysing real-time response.

12. Blocking and Task Scheduling

When a task blocks on a queue, the scheduler can run another Ready task. This improves CPU utilization compared with continuous polling.

Example

  • Task A waits for sensor data using xQueueReceive().
  • Task A enters the Blocked state while the queue is empty.
  • Task B becomes the Running task if it is Ready and selected.
  • Task B sends data to the queue.
  • Task A becomes Ready.
  • The scheduler selects Task A according to priority and scheduling rules.
A task becoming Ready does not guarantee immediate execution. A higher-priority task may continue running.

13. Choosing a Suitable Timeout

Timeout selection depends on application requirements, task priority, data arrival patterns and acceptable response time.

ApplicationPossible Strategy
Periodic sensor acquisitionUse a bounded wait consistent with the sampling schedule.
Command processingUse a finite timeout if the command has a response deadline.
Background event receiverIndefinite wait may be appropriate if shutdown is coordinated.
Time-critical control taskUse a carefully analysed bounded wait and defined failure behavior.
Best-effort data loggingUse a finite wait or non-blocking send with an explicit loss policy.

14. Practical Program – Queue Receive with Timeout

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t sensorQueue;

void SensorReceiverTask(void *pvParameters)
{
    int sensorValue;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &sensorValue,
                pdMS_TO_TICKS(500)
            ) == pdPASS)
        {
            /* Process received data */
        }
        else
        {
            /* Handle timeout */
        }
    }
}

int main(void)
{
    sensorQueue = xQueueCreate(
        5,
        sizeof(int)
    );

    if (sensorQueue == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(
        SensorReceiverTask,
        "Receiver",
        configMINIMAL_STACK_SIZE,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program Explanation

  1. A queue is created for integer sensor values.
  2. A receiver task is created.
  3. The receiver waits for up to 500 milliseconds.
  4. If data arrives, the task processes it.
  5. If no data arrives before timeout, the task handles the failure case.

This example demonstrates the receive-side timeout. A complete application also needs a producer task or another valid source of queue data.

15. Common Programming Mistakes

MistakeCorrection
Using zero wait when data loss is unacceptableChoose a suitable blocking or retry policy.
Using indefinite waits without shutdown planningDefine a safe task and queue lifecycle.
Assuming milliseconds equal ticksUse pdMS_TO_TICKS().
Ignoring timeout return valuesCheck pdPASS and handle failure.
Choosing an excessive timeoutAnalyse the application's response-time requirements.
Assuming Ready means RunningConsider scheduler priority and preemption.
Using queue APIs from an ISR with a blocking timeoutUse appropriate FromISR APIs, which do not block.

16. Practical Experiment

Objective: Demonstrate zero, finite and indefinite queue waits.

Procedure

  1. Create a queue for integer values.
  2. Attempt to receive from an empty queue with zero wait.
  3. Repeat with a finite timeout.
  4. Use a separate sender task to insert an item.
  5. Test a receiver using portMAX_DELAY in a controlled experiment.
  6. Inspect the task state and operation return values.

Expected Result

The zero-wait operation returns immediately when no data is available. The finite-wait operation waits for the configured interval or until data arrives. The indefinite-wait operation remains blocked until data becomes available, subject to configuration and correct queue lifecycle management.

17. LPC2129 and Keil Simulator Considerations

  • LPC2129 uses the ARM7TDMI-S processor.
  • Verify the selected FreeRTOS ARM7 port and Keil compiler compatibility.
  • Check configTICK_RATE_HZ and the tick interrupt implementation.
  • Verify pdMS_TO_TICKS() in the selected kernel version.
  • Use debugger or trace facilities to inspect task state and tick-related variables where supported.
  • Do not assume simulated timing exactly represents physical hardware timing.
The code examples are generic FreeRTOS examples. They are not verified LPC2129 Keil simulator projects.

19. Lesson Summary

  • Blocking time specifies how long a task waits for a queue operation.
  • Zero wait provides non-blocking behavior.
  • Finite wait provides a bounded waiting period.
  • portMAX_DELAY requests indefinite waiting when supported.
  • FreeRTOS uses RTOS ticks to measure blocking intervals.
  • pdMS_TO_TICKS() converts milliseconds into ticks.
  • Timeout occurs when the operation cannot complete within the allowed wait.
  • A blocked task can allow other Ready tasks to execute.
  • Becoming Ready does not guarantee immediate execution.
  • Timeout selection must match system timing requirements.
