Event Groups and Timer Programming

RTOS & FreeRTOS – Chapter 11: Event Groups and Software Timers

Home RTOS Course Chapter 11

1. Learning Objectives

Event groups and software timers are useful FreeRTOS kernel services for coordinating application tasks and handling time-based events. This lesson combines these mechanisms into practical embedded software designs.

  • Understand how event groups and software timers work together.
  • Create and manage event groups.
  • Configure one-shot and auto-reload timers.
  • Use timer callbacks to signal application tasks.
  • Coordinate multiple tasks using event bits.
  • Handle timer and event-group API failures.
  • Design a complete timer-driven monitoring application.

2. Event Groups and Software Timers

Event Groups

An event group is a collection of event bits. Tasks can set, clear and wait for selected combinations of these bits. It is useful when an application must coordinate several conditions.

Software Timers

A software timer provides a time-based mechanism. When its configured period expires, FreeRTOS processes the expiration and invokes its registered callback in the timer service task.

Feature Event Group Software Timer
Main purpose Task synchronization using event bits. Time-based application actions.
Primary mechanism Bit flags. Timer period and expiration.
Typical use Wait for sensor and communication readiness. Generate periodic or one-shot notifications.
Callback No timer-style callback. Uses a registered timer callback.

3. Combined System Architecture

A software timer can set an event bit when it expires. An application task can wait for that event bit and perform the required operation. 

             FreeRTOS Scheduler
                     |
          +----------+----------+
          |                     |
          v                     v
    Timer Service Task     Application Task
          |                     |
          v                     |
    Timer Expiration             |
          |                     |
          v                     |
    Timer Callback               |
          |                     |
          v                     |
    Set Event Bit ---------------+
                                |
                                v
                       Wait for Event Bit
                                |
                                v
                       Perform Application Work
The timer callback should perform only short operations. Lengthy application processing belongs in a separate task.

4. Required FreeRTOS APIs

API Purpose
xEventGroupCreate() Creates an event group.
xEventGroupSetBits() Sets selected event bits.
xEventGroupWaitBits() Waits for selected event bits.
xEventGroupClearBits() Clears selected event bits.
xTimerCreate() Creates a software timer.
xTimerStart() Submits a timer-start command.
xTimerStop() Submits a timer-stop command.
xTimerReset() Submits a timer-reset command.
vTaskDelay() Delays an application task.

5. Example 1 – Timer Sets an Event Bit

In this example, a periodic software timer sets an event bit whenever it expires. A monitoring task waits for the event and performs a status-check operation.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"
#include "timers.h"

#define STATUS_EVENT_BIT  (1U << 0)

EventGroupHandle_t xEventGroup;
TimerHandle_t xStatusTimer;

void StatusTimerCallback(TimerHandle_t xTimer)
{
    /* Signal that the timer period has expired. */
    xEventGroupSetBits(
        xEventGroup,
        STATUS_EVENT_BIT
    );
}

void MonitoringTask(void *pvParameters)
{
    EventBits_t receivedBits;

    for (;;)
    {
        receivedBits = xEventGroupWaitBits(
            xEventGroup,
            STATUS_EVENT_BIT,
            pdTRUE,
            pdFALSE,
            portMAX_DELAY
        );

        if ((receivedBits & STATUS_EVENT_BIT) != 0)
        {
            /* Perform status monitoring. */
        }
    }
}

int main(void)
{
    xEventGroup = xEventGroupCreate();

    if (xEventGroup == NULL)
    {
        for (;;);
    }

    xStatusTimer = xTimerCreate(
        "StatusTimer",
        pdMS_TO_TICKS(1000),
        pdTRUE,
        NULL,
        StatusTimerCallback
    );

    if (xStatusTimer == NULL)
    {
        for (;;);
    }

    if (xTaskCreate(
            MonitoringTask,
            "Monitor",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    if (xTimerStart(xStatusTimer, 0) != pdPASS)
    {
        for (;;);
    }

    vTaskStartScheduler();

    for (;;);
}

Program Explanation

  1. An event group is created.
  2. A one-second auto-reload timer is created.
  3. The monitoring task waits for the status event bit.
  4. When the timer expires, its callback sets the event bit.
  5. The monitoring task becomes eligible to execute.
  6. The task processes the event and waits again.
This example assumes successful kernel initialization and a compatible FreeRTOS port. Production code should also define stack, timer queue, task priority and error-handling policies appropriate to the target.

6. Example 2 – Sensor Timeout Using a One-Shot Timer

A one-shot timer can be used to detect whether a sensor response has arrived within a specified interval.

System Logic

Start Sensor Request
        |
        v
Start One-Shot Timer
        |
        +----------------------+
        |                      |
        v                      v
Sensor Response         Timer Expires
        |                      |
        v                      v
Stop Timer              Set Timeout Bit
        |                      |
        v                      v
Process Sensor Data     Handle Timeout

Program

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"
#include "timers.h"

#define SENSOR_TIMEOUT_BIT  (1U << 0)

EventGroupHandle_t xSensorEvents;
TimerHandle_t xSensorTimeoutTimer;

void SensorTimeoutCallback(TimerHandle_t xTimer)
{
    xEventGroupSetBits(
        xSensorEvents,
        SENSOR_TIMEOUT_BIT
    );
}

void SensorTask(void *pvParameters)
{
    EventBits_t events;

    for (;;)
    {
        /* Start a sensor request here. */

        xEventGroupClearBits(
            xSensorEvents,
            SENSOR_TIMEOUT_BIT
        );

        xTimerStart(xSensorTimeoutTimer, 0);

        /*
         * Wait for the sensor response or timeout.
         * SENSOR_RESPONSE_BIT is assumed to be defined
         * and set by the sensor communication task.
         */

        events = xEventGroupWaitBits(
            xSensorEvents,
            SENSOR_TIMEOUT_BIT,
            pdTRUE,
            pdFALSE,
            pdMS_TO_TICKS(500)
        );

        if ((events & SENSOR_TIMEOUT_BIT) != 0)
        {
            /* Sensor timeout occurred. */
        }
        else
        {
            /* The 500 ms wait ended without timeout bit. */
        }

        xTimerStop(xSensorTimeoutTimer, 0);

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void CreateSensorTimeoutTimer(void)
{
    xSensorTimeoutTimer = xTimerCreate(
        "SensorTimeout",
        pdMS_TO_TICKS(500),
        pdFALSE,
        NULL,
        SensorTimeoutCallback
    );
}
This is a focused timeout illustration, not a complete response-arbitration implementation. A production design must also define a sensor-response event bit and wait for both response and timeout conditions. It must handle races between a response arriving and the timeout callback running.

7. Example 3 – Wait for Multiple System Conditions

An embedded application may need several subsystems to become ready before normal operation begins.

Required Conditions

  • Sensor initialization complete.
  • UART communication initialized.
  • Configuration loaded successfully.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"

#define SENSOR_READY_BIT  (1U << 0)
#define UART_READY_BIT    (1U << 1)
#define CONFIG_READY_BIT  (1U << 2)

#define ALL_READY_BITS \
    (SENSOR_READY_BIT | UART_READY_BIT | CONFIG_READY_BIT)

EventGroupHandle_t xSystemEvents;

void InitializationTask(void *pvParameters)
{
    EventBits_t events;

    /* Initialize sensor. */
    xEventGroupSetBits(
        xSystemEvents,
        SENSOR_READY_BIT
    );

    /* Initialize UART. */
    xEventGroupSetBits(
        xSystemEvents,
        UART_READY_BIT
    );

    /* Load configuration. */
    xEventGroupSetBits(
        xSystemEvents,
        CONFIG_READY_BIT
    );

    for (;;)
    {
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void MainApplicationTask(void *pvParameters)
{
    EventBits_t events;

    events = xEventGroupWaitBits(
        xSystemEvents,
        ALL_READY_BITS,
        pdFALSE,
        pdTRUE,
        portMAX_DELAY
    );

    if ((events & ALL_READY_BITS) == ALL_READY_BITS)
    {
        /* All required subsystems are ready. */

        for (;;)
        {
            /* Main application processing. */
        }
    }

    vTaskDelete(NULL);
}

The application task waits until all three readiness bits are set. The pdTRUE wait-for-all parameter requires every requested bit to be present.

8. Example 4 – Periodic Task Notification Using a Timer

Event groups are useful when multiple conditions must be coordinated. If only one task needs a periodic notification, a direct task notification can be simpler and more efficient. 

#include "FreeRTOS.h"
#include "task.h"
#include "timers.h"

TaskHandle_t xControlTaskHandle;

void ControlTimerCallback(TimerHandle_t xTimer)
{
    xTaskNotifyGive(xControlTaskHandle);
}

void ControlTask(void *pvParameters)
{
    for (;;)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* Perform periodic control processing. */
    }
}

int main(void)
{
    TimerHandle_t xControlTimer;

    xTaskCreate(
        ControlTask,
        "Control",
        256,
        NULL,
        3,
        &xControlTaskHandle
    );

    xControlTimer = xTimerCreate(
        "ControlTimer",
        pdMS_TO_TICKS(100),
        pdTRUE,
        NULL,
        ControlTimerCallback
    );

    if (xControlTimer != NULL)
    {
        xTimerStart(xControlTimer, 0);
    }

    vTaskStartScheduler();

    for (;;);
}
A task notification is often preferable for a single recipient. Event groups are more appropriate when several event conditions or multiple waiting tasks must be coordinated.

9. Integrated Project – Embedded Monitoring System

Consider an embedded monitoring system with sensor acquisition, communication and periodic health monitoring.

System Requirements

Component Responsibility
Sensor Task Acquire and validate sensor readings.
Communication Task Handle UART data exchange.
Monitoring Task Check system status and fault conditions.
Software Timer Generate periodic monitoring requests.
Event Group Represent sensor-ready, communication-ready and fault conditions.
Queue Transfer sensor data and structured messages.

System Event Bits

#define SENSOR_READY_BIT  (1U << 0)
#define UART_READY_BIT    (1U << 1)
#define FAULT_EVENT_BIT   (1U << 2)
#define MONITOR_EVENT_BIT (1U << 3)

Conceptual Data Flow

          Sensor Task
              |
              v
        Sensor Data Queue
              |
              v
        Monitoring Task
              ^
              |
       Event Group Bits
              ^
              |
       Timer Callback
              ^
              |
        Software Timer

       Communication Task
              |
              v
       UART Data Exchange

Design Explanation

  1. The sensor task acquires sensor readings.
  2. Sensor data is sent through a queue.
  3. Initialization tasks set their readiness event bits.
  4. A software timer periodically requests monitoring.
  5. The timer callback sets the monitoring event bit.
  6. The monitoring task processes pending events and sensor data.
  7. Fault conditions are represented by an appropriate event or message.
Event bits represent conditions, not a count of occurrences. If several monitoring events happen before a task processes the bit, repeated sets can coalesce into one set bit. Use a queue or counting mechanism if every occurrence must be preserved.

10. Timing and Reliability Considerations

Timer Period Conversion

xTimerCreate(
    "PeriodicTimer",
    pdMS_TO_TICKS(1000),
    pdTRUE,
    NULL,
    TimerCallback
);

pdMS_TO_TICKS() converts milliseconds into RTOS ticks. The actual timing resolution depends on the configured tick rate.

Important Design Considerations

  • Use finite timeouts where indefinite waiting is not acceptable.
  • Check timer creation and command return values.
  • Keep callbacks short.
  • Size the timer command queue for expected command bursts.
  • Set task priorities based on response requirements.
  • Use queues for payloads and repeated events.
  • Protect shared data from concurrent access.
  • Do not treat a software timer as a precision hardware timer.

11. Important Programming Rules

Rule Reason
Keep callbacks short. All timer callbacks share the timer service task.
Use zero block time for callback queue operations. A callback must not block the timer service task.
Check API return values. Timer commands and event operations can fail.
Use queues for data transfer. Event bits do not carry arbitrary data payloads.
Use task notifications for simple one-to-one signaling. They can reduce the need for separate synchronization objects.
Handle event-bit clearing carefully. One task clearing shared bits can affect other waiters.
Analyze timing and scheduling. Timer expiration does not guarantee immediate callback execution.

14. Lesson Summary

  • Event groups coordinate tasks through event bits.
  • Software timers provide time-based notifications.
  • Timer callbacks execute in the timer service task.
  • Callbacks can set event bits or notify application tasks.
  • Queues are suitable for transferring structured data.
  • Event groups are suitable for coordinating multiple conditions.
  • Task notifications are useful for simple task signaling.
  • Timeout handling, race conditions and queue capacity must be considered.
  • Good design separates short notification work from lengthy processing.
