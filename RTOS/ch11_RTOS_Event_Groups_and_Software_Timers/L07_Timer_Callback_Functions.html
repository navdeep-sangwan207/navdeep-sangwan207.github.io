Timer Callback Functions

1. Learning Objectives

A timer callback function is application code executed when a FreeRTOS software timer expires. Understanding its execution context and restrictions is essential for designing reliable multitasking applications.

  • Understand the purpose of timer callback functions.
  • Learn the callback function prototype.
  • Understand callback execution context.
  • Learn how to identify timers using timer handles and IDs.
  • Understand which operations are safe inside callbacks.
  • Communicate from callbacks to application tasks.
  • Apply callback programming best practices.

2. What Is a Timer Callback Function?

A timer callback function is a function registered when a software timer is created. FreeRTOS executes this function when the timer expires.

For example, an application may use a timer callback to notify a monitoring task that a periodic status check is required.

Basic Callback Prototype

void TimerCallbackFunction(TimerHandle_t xTimer)
{
    /* Timer expiration processing */
}

Callback Parameters

Parameter Description
void The callback does not return a value.
TimerHandle_t Handle identifying the timer whose callback is executing.
xTimer Parameter containing the timer handle passed by FreeRTOS.

3. Callback Execution Context

FreeRTOS software timer callbacks execute in the context of the timer service task, also called the timer daemon task. They do not execute directly in a hardware interrupt service routine.

Execution Flow

          RTOS Tick
              |
              v
      Kernel Timer Management
              |
              v
       Timer Expiration
              |
              v
      Timer Service Task
              |
              v
       Callback Function
              |
              v
       Application Action

Important Characteristics

  • All software timer callbacks share the timer service task context.
  • A callback executes as task-context code.
  • Callbacks are not separate tasks.
  • A callback can be delayed by scheduling and timer service workload.
  • A long callback can delay other timer callbacks.
  • A callback must not block the timer service task.
A timer callback is not an ISR. Do not use ISR-specific APIs such as xQueueSendFromISR() merely because the callback is triggered by timer expiration. Use the normal task-context APIs, with zero block time where appropriate.

4. Timer Callback Registration

The callback function is registered using the final parameter of xTimerCreate().

Example

#include "FreeRTOS.h"
#include "task.h"
#include "timers.h"

void StatusCallback(TimerHandle_t xTimer)
{
    /* Short status-processing operation. */
}

TimerHandle_t xStatusTimer;

void CreateStatusTimer(void)
{
    xStatusTimer = xTimerCreate(
        "StatusTimer",
        pdMS_TO_TICKS(1000),
        pdTRUE,
        NULL,
        StatusCallback
    );

    if (xStatusTimer != NULL)
    {
        xTimerStart(xStatusTimer, 0);
    }
}

The callback is associated with the timer at creation time. When the timer expires, the timer service task invokes the registered callback.

5. Identifying the Timer Inside a Callback

The callback receives a timer handle. This handle can be used to identify the timer and retrieve its associated application-defined timer ID.

Timer Handle

void TimerCallback(TimerHandle_t xTimer)
{
    if (xTimer == xSensorTimer)
    {
        /* Sensor timer processing. */
    }
}

Timer ID

FreeRTOS allows an application-defined timer ID to be associated with a timer using the fourth parameter of xTimerCreate(). 

void *pvTimerGetTimerID(TimerHandle_t xTimer);

The returned pointer is the timer ID previously associated with that timer.

6. Using One Callback for Multiple Timers

A single callback function can be registered with multiple timers. The callback can determine which timer expired using its handle or timer ID.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "timers.h"

#define SENSOR_TIMER_ID  1
#define UART_TIMER_ID    2

TimerHandle_t xSensorTimer;
TimerHandle_t xUARTTimer;

void CommonTimerCallback(TimerHandle_t xTimer)
{
    uintptr_t timerID;

    timerID = (uintptr_t)pvTimerGetTimerID(xTimer);

    if (timerID == SENSOR_TIMER_ID)
    {
        /* Handle sensor timer expiration. */
    }
    else if (timerID == UART_TIMER_ID)
    {
        /* Handle UART timer expiration. */
    }
}

void CreateTimers(void)
{
    xSensorTimer = xTimerCreate(
        "SensorTimer",
        pdMS_TO_TICKS(1000),
        pdTRUE,
        (void *)(uintptr_t)SENSOR_TIMER_ID,
        CommonTimerCallback
    );

    xUARTTimer = xTimerCreate(
        "UARTTimer",
        pdMS_TO_TICKS(3000),
        pdFALSE,
        (void *)(uintptr_t)UART_TIMER_ID,
        CommonTimerCallback
    );

    if (xSensorTimer != NULL)
    {
        xTimerStart(xSensorTimer, 0);
    }

    if (xUARTTimer != NULL)
    {
        xTimerStart(xUARTTimer, 0);
    }
}
This example uses uintptr_t to encode small integer identifiers in the timer ID pointer. Include <stdint.h> for this type. For more complex applications, a pointer to a valid application object can be used instead.

7. Operations Allowed in a Timer Callback

Since the callback executes in task context, it can use suitable task-context FreeRTOS APIs. However, it should avoid operations that block or suspend the timer service task.

Operation Recommended Usage
Update a simple variable Suitable when access is properly synchronized.
Set a flag Suitable with appropriate concurrency protection.
xQueueSend() Suitable with zero block time.
xTaskNotify() Suitable for notifying an application task.
xEventGroupSetBits() Suitable in task context, subject to execution-time considerations.
vTaskDelay() Not suitable; it blocks the shared timer service task.
Blocking queue receive Not suitable; it can prevent other timer operations from running.
Long-running processing Move it to an application task.

8. Why Must Timer Callbacks Be Short?

All software timer callbacks execute through the same timer service task. If one callback takes too long, other expired timers and pending timer commands may have to wait.

Problem Scenario

Timer A expires
      |
      v
Callback A starts
      |
      v
Long processing operation
      |
      | Other timer work waits
      v
Callback A finishes
      |
      v
Timer B callback can execute

Recommended Design

Timer Callback
      |
      | Send event / notify task
      v
Application Task
      |
      | Perform lengthy operation
      v
Processing Complete

The callback performs a short notification operation. The application task performs the actual processing.

9. Communicating with a Task Using a Queue

A queue can transfer an event or data from a timer callback to an application task. Since the callback executes in task context, the normal queue API is used.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "timers.h"

typedef struct
{
    uint32_t eventCode;
} TimerEvent_t;

#define TIMER_EVENT_STATUS  1U

QueueHandle_t xTimerEventQueue;

void StatusTimerCallback(TimerHandle_t xTimer)
{
    TimerEvent_t event;

    event.eventCode = TIMER_EVENT_STATUS;

    /* Do not block the timer service task. */
    if (xQueueSend(xTimerEventQueue, &event, 0) != pdPASS)
    {
        /* Queue full: event was not delivered. */
        /* Apply an application-specific overflow policy. */
    }
}

void MonitoringTask(void *pvParameters)
{
    TimerEvent_t receivedEvent;

    for (;;)
    {
        if (xQueueReceive(
                xTimerEventQueue,
                &receivedEvent,
                portMAX_DELAY
            ) == pdPASS)
        {
            if (receivedEvent.eventCode == TIMER_EVENT_STATUS)
            {
                /* Perform status monitoring here. */
            }
        }
    }
}

Working

  1. The timer expires.
  2. The callback constructs an event message.
  3. The callback sends the message without blocking.
  4. The monitoring task receives the message.
  5. The task performs the application processing.
A zero-timeout queue send can fail if the queue is full. The application must define what happens when an event cannot be delivered. Do not silently assume every callback message is received.

10. Communicating with a Task Using Task Notifications

A timer callback can notify a task using xTaskNotifyGive(). This is useful when the callback only needs to signal that work is available.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "timers.h"

TaskHandle_t xMonitoringTaskHandle;

void MonitoringTimerCallback(TimerHandle_t xTimer)
{
    xTaskNotifyGive(xMonitoringTaskHandle);
}

void MonitoringTask(void *pvParameters)
{
    for (;;)
    {
        /* Wait for timer notification. */
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* Perform monitoring work. */
    }
}

xTaskNotifyGive() is a task-context notification API. The callback does not need an ISR-specific notification function.

Task notifications can accumulate notification counts when used with the counting pattern shown here. However, the receiving task's configuration and chosen notification semantics must match the application's requirements.

11. Callback and ISR Differences

Feature Timer Callback Hardware ISR
Execution context Timer service task Interrupt context
Can block? Must not block the timer service task. No.
Queue API xQueueSend() with zero block time. xQueueSendFromISR().
Notification API xTaskNotifyGive(). Appropriate FromISR variant.
Scheduling Normal task scheduling rules. Interrupt and port-specific ISR yield rules.
Typical purpose Application-level timed actions. Respond to hardware interrupt events.

12. Callback Concurrency and Shared Data

A timer callback may access data that is also accessed by application tasks. This creates possible race conditions.

Example Problem

volatile uint32_t statusCounter;

void TimerCallback(TimerHandle_t xTimer)
{
    statusCounter++;
}

void ApplicationTask(void *pvParameters)
{
    uint32_t localValue;

    for (;;)
    {
        localValue = statusCounter;

        /* Process localValue. */
    }
}

Declaring a variable volatile does not make increment operations atomic and does not provide general synchronization between tasks.

Safer Approaches

  • Use a queue to transfer data to the owning task.
  • Use task notifications when only signaling is required.
  • Use suitable atomic operations where supported.
  • Use appropriate synchronization for shared data.
  • Keep shared-state ownership clear.

13. Common Callback Programming Mistakes

Mistake Why It Is a Problem Better Practice
Calling vTaskDelay() Blocks the shared timer service task. Move delayed processing to a dedicated task.
Using blocking queue operations Can delay other timer work. Use zero block time.
Performing lengthy calculations Increases callback latency for other timers. Notify an application task.
Using ISR APIs in callbacks Callback is task context, not ISR context. Use normal task-context APIs.
Ignoring queue-send failure Application events may be lost. Define an overflow policy.
Assuming exact expiration time Scheduling and callback workload introduce delay. Account for timing latency.
Unsynchronized shared data Can cause race conditions. Use queues, notifications or synchronization.

14. Practical Activity

Activity – Timer-Based Sensor Monitoring

Objective: Design a system in which a periodic timer requests sensor monitoring without performing the monitoring work inside the callback.

  1. Create an auto-reload timer with a one-second period.
  2. Create a monitoring task.
  3. In the callback, notify the monitoring task.
  4. In the monitoring task, perform the sensor-processing operation.
  5. Handle notification accumulation according to the application requirements.
  6. Stop the timer when monitoring is disabled.
  7. Measure or analyze the effect of callback workload on other timer operations.

Expected Result: The timer callback remains short and the monitoring task performs the actual application processing.

This is a generic FreeRTOS programming exercise. Actual execution requires a compatible FreeRTOS port and target environment. Do not assume that the LPC2129 Keil uVision simulator has a supported FreeRTOS port.

16. Lesson Summary

  • Timer callbacks execute when software timers expire.
  • Callbacks execute in the timer service task context.
  • They are not hardware interrupt service routines.
  • A callback receives the timer handle as its parameter.
  • Timer IDs allow application-defined identification.
  • Callbacks should remain short and non-blocking.
  • Queues and task notifications can transfer work to application tasks.
  • Normal task-context APIs are used inside callbacks.
  • Shared data requires appropriate synchronization.
