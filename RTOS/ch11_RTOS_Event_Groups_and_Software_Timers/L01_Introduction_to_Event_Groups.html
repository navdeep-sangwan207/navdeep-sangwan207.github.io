1. Learning Objectives

Event groups are synchronization objects used in FreeRTOS to communicate the occurrence of multiple events between tasks. A task can wait for one or more event conditions before continuing its execution.

  • Understand the purpose of event groups in an RTOS.
  • Learn the concept of event bits and bit masks.
  • Understand how multiple events are represented in one event group.
  • Differentiate event groups from queues and semaphores.
  • Identify practical embedded-system applications.
  • Understand the basic FreeRTOS event-group programming model.

2. What Are Event Groups?

An event group is a synchronization object that contains a collection of event bits. Each bit represents the occurrence or status of a particular event.

Tasks can set, clear and wait for these bits. A task may continue when a specified event bit becomes set or when a required combination of bits is satisfied.

Example

Consider an embedded monitoring system with three events:

  • Sensor data received.
  • UART communication completed.
  • System initialization completed.

Each event can be represented by a separate bit in one event group.

Conceptual event group
Event bit Meaning Value when set
Bit 0 Sensor data received 1
Bit 1 UART transmission completed 1
Bit 2 System initialization completed 1
Event groups communicate event conditions. They are not intended to carry large data values or preserve every occurrence of a repeated event.

3. Why Are Event Groups Needed?

In a multitasking embedded system, several independent activities may need to complete before a task can proceed.

Example: Sensor Monitoring System

A monitoring task may need to wait until the sensor has been initialized, communication is ready and configuration data has been loaded.

Without a common event mechanism, the application may require several separate synchronization objects and additional state management.

Benefits

  • Multiple event conditions can be represented in one object.
  • Tasks can wait for one event or a combination of events.
  • Several tasks can observe event conditions.
  • Event bits can represent system readiness and operating states.
  • Task synchronization logic can become easier to organize.

4. Event Bits and Bit Masks

Event groups use individual bits to represent event conditions. A bit can be either set (1) or cleared (0).

Example Bit Assignment

#define EVENT_SENSOR_READY    (1U << 0)
#define EVENT_UART_READY      (1U << 1)
#define EVENT_CONFIG_READY    (1U << 2)
#define EVENT_SYSTEM_READY    (1U << 3)

The corresponding bit positions are:

Bit Position Mask Event
0 0001 Sensor ready
1 0010 UART ready
2 0100 Configuration ready
3 1000 System ready

Combining Event Bits

Bitwise OR combines multiple event masks. 

#define REQUIRED_EVENTS \
    (EVENT_SENSOR_READY | EVENT_UART_READY | EVENT_CONFIG_READY)

The combined mask identifies the three conditions that a task may need to wait for.

FreeRTOS reserves some event-group bits for internal control depending on the port and configuration. Do not assume every bit in the underlying EventBits_t type is available to the application. Use the supported application-bit range for the selected FreeRTOS version and port.

5. How Event Groups Work

Event groups maintain a bit pattern representing the current event conditions. Tasks and other permitted contexts interact with the group through FreeRTOS APIs.

Basic Operations

Operation Description
Set event bit Changes a selected bit from 0 to 1.
Clear event bit Changes a selected bit from 1 to 0.
Wait for event bits Blocks a task until the requested condition is satisfied or a timeout occurs.
Read event bits Returns the current event-bit state through the appropriate API.

Conceptual Example

Initial event group:

0000

Sensor becomes ready:

0001

UART becomes ready:

0011

Configuration becomes ready:

0111

At this stage, a task waiting for all three conditions can proceed because bits 0, 1 and 2 are set.

6. Event Groups in a Multitasking System

Consider three tasks that perform separate operations:

  • SensorTask sets the sensor-ready event.
  • UARTTask sets the UART-ready event.
  • ConfigTask sets the configuration-ready event.

A SystemTask waits for the required combination before starting the main application operation. 

SensorTask -----------> SENSOR_READY
                              |
UARTTask -------------> UART_READY
                              |
ConfigTask -----------> CONFIG_READY
                              |
                              v
                       EVENT GROUP
                              |
                              v
                         SystemTask
                              |
                              v
                      Start Application

Advantages

  • Each task reports its own event.
  • The receiving task does not need to poll every task continuously.
  • The receiving task can wait for a defined combination of conditions.

7. Event Groups vs Other RTOS Synchronization Objects

Feature Event Group Semaphore Queue
Main purpose Represent and synchronize event conditions Synchronization or resource signaling Data transfer between tasks
Multiple conditions Yes, through event bits Generally one synchronization condition per object Can transfer structured data items
Data storage Bit states only Token count or availability state Stores queue items
Wait for combinations Yes Not directly through one semaphore Not its primary purpose
Preserve repeated events No; repeated setting of an already-set bit coalesces Counting semaphore can count tokens up to its maximum Can preserve individual queued items until capacity is reached
Event bits represent states or pending conditions, not an event history. If an event occurs repeatedly while its bit is already set, the repeated occurrences are not counted. Use a queue or counting semaphore when every occurrence must be preserved.

8. Practical Applications of Event Groups

A. System Initialization

A task waits until clock configuration, sensor initialization, communication setup and other startup operations are complete.

B. Sensor Monitoring

Different sensor tasks set event bits when their data is ready. A monitoring task can wait for one or more sensor conditions.

C. Communication Management

Event bits can indicate that UART, SPI or network communication subsystems are ready.

D. Multi-Condition Control

A control task can wait until several operating conditions are satisfied before enabling a particular application function.

9. Important Limitations and Design Considerations

  • Event groups do not transfer arbitrary data.
  • Repeated setting of the same bit does not count repeated events.
  • Clearing a bit changes the shared state and may affect other tasks waiting on it.
  • Event-group operations may involve deferred processing when called from an ISR.
  • Use queues or task notifications when event counts or payloads must be preserved.
  • Define clear ownership and reset rules for event bits.
  • Consider timeout and error handling for tasks waiting on events.
FreeRTOS event groups are not simply hardware interrupt flags. They are kernel synchronization objects with defined task and ISR interaction rules.

12. Lesson Summary

  • Event groups are FreeRTOS synchronization objects.
  • Individual event bits represent event conditions.
  • Multiple bits can represent several independent conditions.
  • Tasks can wait for one or more specified bits.
  • Event groups are useful for initialization, monitoring and multi-condition synchronization.
  • Repeated occurrences of an already-set bit are coalesced.
  • Queues and counting semaphores are more suitable when individual occurrences or data must be preserved.
