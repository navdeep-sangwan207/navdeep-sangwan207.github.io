1. Learning Objectives

FreeRTOS software timers are managed by a shared timer service task. This task processes timer commands, checks timer expiration and executes timer callback functions.

  • Understand the purpose of the timer service task.
  • Learn the timer daemon architecture.
  • Understand the timer command queue.
  • Study timer command processing.
  • Understand timer task priority and stack depth.
  • Learn how callback execution affects timer processing.
  • Identify common timer service configuration problems.

2. What Is the Timer Service Task?

The timer service task is a kernel-managed FreeRTOS task responsible for software timer management. It is also known as the timer daemon task.

Instead of creating an independent task for every software timer, FreeRTOS uses one shared service task to process timer commands and execute callbacks.

Main Responsibilities

  • Process timer start commands.
  • Process timer stop commands.
  • Process timer reset commands.
  • Process timer period-change commands.
  • Determine when timers expire.
  • Execute registered callback functions.
  • Process other supported timer-management commands.
The timer service task is shared by all software timers. A long-running callback can delay other timer callbacks and the processing of pending timer commands.

4. Timer Command Queue

The timer command queue is an internal queue used to communicate timer-management commands to the timer service task.

Common Timer Commands

Command Purpose
Start Start a timer.
Stop Stop an active timer.
Reset Restart a timer's expiration interval.
Change Period Change the timer period and start it with the new period.
Delete Request deletion of a timer.

Command Processing Example

  1. Task A calls xTimerStart().
  2. The API attempts to place a start command in the timer command queue.
  3. The timer service task receives the command.
  4. The timer service task processes the start operation.
  5. The timer becomes active according to the command processing time.
A successful timer API return generally indicates that the command was successfully submitted to the command queue. It does not mean the requested operation has already been completed by the timer service task.

5. Timer Command Queue Length

The timer command queue has a finite capacity. If commands arrive faster than the timer service task can process them, the queue can become full.

Configuration Macro

#define configTIMER_QUEUE_LENGTH 10

This illustrative configuration defines a queue capacity of ten timer commands.

Queue Full Scenario

Application Tasks
       |
       | Many timer commands
       v
Timer Command Queue
       |
       | Queue becomes full
       v
Timer API may wait or fail
       |
       v
Timer Service Task processes commands
       |
       v
Queue space becomes available

Design Considerations

  • Estimate the maximum number of timer commands that may be pending.
  • Consider commands generated by several application tasks.
  • Consider timer commands generated from interrupt context.
  • Keep callbacks short to prevent service-task delays.
  • Check the return values of timer API functions.
  • Choose queue length based on actual application behavior.

6. Timer Service Task Priority

The timer service task has a configurable task priority. This determines how it competes with application tasks for CPU execution.

Configuration Macro

#define configTIMER_TASK_PRIORITY 2

The value shown is only an example. The appropriate priority depends on the application task priorities and the required timer-response behavior.

Priority Considerations

  • A low timer service priority may delay timer command processing.
  • A higher-priority application task may delay timer callbacks.
  • An unnecessarily high timer service priority may interfere with other tasks.
  • Callback execution time affects the service task's workload.
Timer priority affects scheduling latency, but it does not make software timer callbacks execute at an exact hardware deadline.

7. Timer Service Task Stack Depth

The timer service task requires stack memory for its execution, including callback function calls and local variables used during processing.

Configuration Macro

#define configTIMER_TASK_STACK_DEPTH 256

The value is expressed in stack units used by the selected FreeRTOS port, generally stack words rather than bytes.

Stack Memory Calculation

Stack memory =
    Stack depth x sizeof(StackType_t)

If the stack depth is 256 and sizeof(StackType_t) is 4 bytes: 

Stack memory = 256 x 4
             = 1024 bytes

This is an illustrative calculation. The actual stack element size depends on the port.

Stack Design Recommendations

  • Keep timer callbacks simple.
  • Avoid large local arrays in callbacks.
  • Avoid deep function-call chains.
  • Use stack monitoring facilities where supported.
  • Investigate stack overflow warnings during testing.

8. Timer Expiration Processing

FreeRTOS uses the RTOS tick count to determine when a software timer expires. The timer service task processes expired timers and invokes their callbacks.

Conceptual Sequence

Timer Started
     |
     v
Expiration Time Established
     |
     v
RTOS Tick Count Advances
     |
     v
Timer Becomes Due
     |
     v
Timer Service Task Processes Expiration
     |
     v
Callback Executes

Timer expiration is based on the kernel's tick-time model. The actual callback execution can occur later due to scheduling, task priority and timer service workload.

9. Effect of a Long Callback

Since all software timer callbacks execute in the timer service task, one callback that takes a long time can delay other timer operations.

Example Scenario

Timer Callback Operation Potential Effect
Timer A Long sensor calculation Delays timer service processing.
Timer B Communication timeout notification Callback may execute later than expected.
Timer C Periodic status event Callback may wait behind Timer A.

Recommended Solution

Timer Service Task
       |
       v
Short Timer Callback
       |
       | Send queue message
       v
Application Task
       |
       v
Long Processing Operation

The callback should only notify an application task. The application task should perform lengthy calculations, sensor processing or communication operations.

10. Timer Commands from Interrupt Context

Some FreeRTOS timer APIs have interrupt-safe variants. These variants are designed for use from an ISR and communicate with the timer service task through the timer command queue.

Example API

BaseType_t xTimerStartFromISR(
    TimerHandle_t xTimer,
    BaseType_t *pxHigherPriorityTaskWoken
);

The ISR-safe timer command functions do not execute the timer callback directly inside the interrupt. They submit a command for processing by the timer service task.

Important Points

  • Use only APIs explicitly documented as ISR-safe.
  • Follow the selected FreeRTOS port's ISR priority rules.
  • Check the API return value.
  • Use the appropriate ISR yield mechanism for the port.
  • Timer command queue capacity still matters.

11. Timer Service Configuration

The following configuration settings are commonly used to configure software timer functionality. 

/* Illustrative FreeRTOSConfig.h settings */

#define configUSE_TIMERS                 1
#define configTIMER_TASK_PRIORITY        2
#define configTIMER_QUEUE_LENGTH         10
#define configTIMER_TASK_STACK_DEPTH     256
Macro Purpose
configUSE_TIMERS Enables software timer support.
configTIMER_TASK_PRIORITY Sets timer service task priority.
configTIMER_QUEUE_LENGTH Sets timer command queue capacity.
configTIMER_TASK_STACK_DEPTH Sets timer service task stack depth.
These settings must be compatible with the FreeRTOS version and port. A software timer implementation also requires suitable kernel memory allocation and scheduler configuration.

12. Common Timer Service Problems

Problem Possible Cause Recommended Investigation
Timer callback never executes Timer not started, scheduler not running, or timer service configuration issue. Check creation, start result and timer configuration.
Callback executes late Scheduling delay or long callback workload. Inspect task priorities and callback execution time.
Timer API command fails Command queue full or invalid timer handle. Check return value and queue configuration.
System stack overflow Insufficient timer service task stack. Review callback stack usage and stack configuration.
Other callbacks are delayed One callback takes too long. Move lengthy processing into application tasks.
Timer timing is inconsistent Tick resolution, scheduling interference or command delays. Analyze the tick rate and system workload.

13. Practical Activity

Activity – Multiple Timer Management

Objective: Understand how one timer service task manages several software timers.

  1. Create three software timers with different periods.
  2. Register a separate callback or use a common callback.
  3. Use timer IDs to identify each timer.
  4. Send callback events to an application queue.
  5. Process the events in a separate monitoring task.
  6. Observe what happens when callback processing is intentionally made longer.
  7. Restore short callbacks and compare the design.
  8. Check timer command API return values.

Expected Result: Multiple timers are managed by one timer service task. Callback notifications are processed by the monitoring task, while callback execution time affects the responsiveness of the shared timer service.

This is a generic FreeRTOS exercise. Actual execution requires a compatible FreeRTOS port and target environment. Do not assume the LPC2129 Keil uVision simulator has a supported FreeRTOS port.

15. Lesson Summary

  • The timer service task manages FreeRTOS software timers.
  • It processes timer commands received through the timer command queue.
  • It checks timer expiration and executes callback functions.
  • All software timer callbacks share the timer service task context.
  • Queue length, task priority and stack depth affect timer service behavior.
  • Long callbacks can delay other timer operations.
  • Application tasks should perform lengthy processing.
  • ISR-safe timer command APIs are available for appropriate interrupt use.
