1. Learning Objectives

An RTOS application often needs to wait for one event from a group of possible events or for several conditions to become true simultaneously. FreeRTOS event groups support both synchronization patterns.

  • Understand wait-for-any and wait-for-all conditions.
  • Learn the role of the xWaitForAllBits parameter.
  • Analyze event-bit combinations using binary masks.
  • Understand the returned event-bit value.
  • Configure automatic clearing and timeouts.
  • Implement both waiting modes in FreeRTOS programs.

2. Event Group Fundamentals

A FreeRTOS event group contains a collection of event bits. Each bit represents a condition or event reported by a task or another permitted execution context.

Example Event Definitions

#define EVENT_SENSOR_READY  (1U << 0)
#define EVENT_UART_READY    (1U << 1)
#define EVENT_CONFIG_READY  (1U << 2)

#define EVENT_FAULT         (1U << 3)
Bit Event Meaning
Bit 0 Sensor ready Sensor initialization has completed.
Bit 1 UART ready UART initialization has completed.
Bit 2 Configuration ready Configuration loading has completed.
Bit 3 Fault A fault condition has been reported.

3. Wait-for-Any Condition

Wait-for-any means that a task becomes unblocked when at least one of the requested event bits is set.

It is useful when a task must respond to whichever event occurs first from a group of possible events.

Example

A monitoring task waits for any of these conditions:

  • UART data available.
  • Sensor threshold exceeded.
  • Communication fault detected.
#define ANY_EVENT_BITS \
    (EVENT_UART_READY | EVENT_SENSOR_READY | EVENT_FAULT)

FreeRTOS API

EventBits_t result;

result = xEventGroupWaitBits(
    xEventGroup,
    ANY_EVENT_BITS,
    pdFALSE,
    pdFALSE,
    portMAX_DELAY
);

The fourth parameter is pdFALSE, which selects wait-for-any behavior. The task proceeds when at least one requested bit is set.

Binary Example

Requested bits:  0111
Current bits:    0010
                 ----
AND result:      0010

The AND result is non-zero, so at least one requested event is present.

4. Wait-for-All Condition

Wait-for-all means that a task remains blocked until every requested event bit has been set.

It is useful when an operation must not begin until all prerequisite conditions are satisfied.

Example

A main application task must wait until sensor, UART and configuration initialization are complete. 

#define ALL_READY_BITS \
    (EVENT_SENSOR_READY | EVENT_UART_READY | EVENT_CONFIG_READY)

FreeRTOS API

EventBits_t result;

result = xEventGroupWaitBits(
    xEventGroup,
    ALL_READY_BITS,
    pdFALSE,
    pdTRUE,
    portMAX_DELAY
);

The fourth parameter is pdTRUE, which selects wait-for-all behavior.

Binary Example

Requested bits:  0111
Current bits:    0111
                 ----
AND result:      0111

All requested bits are set, so the waiting task can proceed.

5. Comparison of Wait-Any and Wait-All

Feature Wait for Any Wait for All
FreeRTOS parameter pdFALSE pdTRUE
Required condition At least one requested bit is set. Every requested bit is set.
Typical use React to one of several events. Wait for all initialization tasks.
Partial bit match Sufficient to unblock. Not sufficient to unblock.
Example UART event OR sensor event OR fault event. Sensor AND UART AND configuration ready.

7. Understanding the Returned Event-Bit Value

xEventGroupWaitBits() returns the event-bit value observed when the task leaves the wait. The returned value is useful for identifying which requested events were present.

Example

EventBits_t result;

result = xEventGroupWaitBits(
    xEventGroup,
    ANY_EVENT_BITS,
    pdFALSE,
    pdFALSE,
    portMAX_DELAY
);

if ((result & EVENT_UART_READY) != 0U)
{
    /* UART event was present. */
}

if ((result & EVENT_SENSOR_READY) != 0U)
{
    /* Sensor event was present. */
}

if ((result & EVENT_FAULT) != 0U)
{
    /* Fault event was present. */
}
A non-zero return value does not automatically mean every requested bit is set. For wait-for-all, compare the returned requested bits against the complete requested mask.

8. Clear-on-Exit with Wait-Any and Wait-All

The third parameter of xEventGroupWaitBits() determines whether requested bits are cleared after a successful wait condition.

Wait Mode Clear-on-Exit Behavior on Successful Wait
Wait-any pdFALSE Matching bits remain set.
Wait-any pdTRUE Requested bits that were set are cleared.
Wait-all pdFALSE Requested bits remain set.
Wait-all pdTRUE All requested bits are cleared.

Automatic clearing occurs when the specified wait condition is satisfied. A timeout does not automatically clear the requested bits.

Example – Wait for Any and Clear Matching Bits

result = xEventGroupWaitBits(
    xEventGroup,
    ANY_EVENT_BITS,
    pdTRUE,
    pdFALSE,
    portMAX_DELAY
);

Example – Wait for All and Keep Bits Set

result = xEventGroupWaitBits(
    xEventGroup,
    ALL_READY_BITS,
    pdFALSE,
    pdTRUE,
    portMAX_DELAY
);

9. Example 1 – Wait for Any Event

Objective: A monitoring task responds to any one of three event conditions.

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"

#define UART_EVENT_BIT    (1U << 0)
#define SENSOR_EVENT_BIT  (1U << 1)
#define FAULT_EVENT_BIT   (1U << 2)

#define ANY_EVENT_BITS \
    (UART_EVENT_BIT | SENSOR_EVENT_BIT | FAULT_EVENT_BIT)

EventGroupHandle_t xEvents;

void MonitoringTask(void *pvParameters)
{
    EventBits_t result;

    for (;;)
    {
        result = xEventGroupWaitBits(
            xEvents,
            ANY_EVENT_BITS,
            pdTRUE,
            pdFALSE,
            portMAX_DELAY
        );

        if ((result & UART_EVENT_BIT) != 0U)
        {
            /* Process UART event. */
        }

        if ((result & SENSOR_EVENT_BIT) != 0U)
        {
            /* Process sensor event. */
        }

        if ((result & FAULT_EVENT_BIT) != 0U)
        {
            /* Process fault event. */
        }
    }
}

int main(void)
{
    xEvents = xEventGroupCreate();

    if (xEvents != NULL)
    {
        xTaskCreate(
            MonitoringTask,
            "Monitor",
            256,
            NULL,
            2,
            NULL
        );

        vTaskStartScheduler();
    }

    for (;;);
}

Working

  1. The monitoring task blocks while none of the requested bits is set.
  2. Another task sets one or more event bits.
  3. The monitoring task becomes ready when at least one requested bit is set.
  4. The returned value identifies which requested bits were set.
  5. With clear-on-exit enabled, the requested bits that were set are cleared.

10. Example 2 – Wait for All Initialization Events

Objective: Start normal operation only after all three initialization tasks report success.

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"

#define SENSOR_READY_BIT  (1U << 0)
#define UART_READY_BIT    (1U << 1)
#define CONFIG_READY_BIT  (1U << 2)

#define ALL_READY_BITS \
    (SENSOR_READY_BIT | UART_READY_BIT | CONFIG_READY_BIT)

EventGroupHandle_t xEvents;

void SensorInitTask(void *pvParameters)
{
    /* Perform sensor initialization. */

    xEventGroupSetBits(xEvents, SENSOR_READY_BIT);

    vTaskDelete(NULL);
}

void UARTInitTask(void *pvParameters)
{
    /* Perform UART initialization. */

    xEventGroupSetBits(xEvents, UART_READY_BIT);

    vTaskDelete(NULL);
}

void ConfigInitTask(void *pvParameters)
{
    /* Load and validate configuration. */

    xEventGroupSetBits(xEvents, CONFIG_READY_BIT);

    vTaskDelete(NULL);
}

void ApplicationTask(void *pvParameters)
{
    EventBits_t result;

    result = xEventGroupWaitBits(
        xEvents,
        ALL_READY_BITS,
        pdTRUE,
        pdTRUE,
        pdMS_TO_TICKS(5000)
    );

    if ((result & ALL_READY_BITS) == ALL_READY_BITS)
    {
        for (;;)
        {
            /* Normal application operation. */

            vTaskDelay(pdMS_TO_TICKS(1000));
        }
    }
    else
    {
        for (;;)
        {
            /* Handle incomplete initialization. */

            vTaskDelay(pdMS_TO_TICKS(1000));
        }
    }
}

int main(void)
{
    xEvents = xEventGroupCreate();

    if (xEvents != NULL)
    {
        xTaskCreate(SensorInitTask, "SensorInit", 256, NULL, 2, NULL);
        xTaskCreate(UARTInitTask, "UARTInit", 256, NULL, 2, NULL);
        xTaskCreate(ConfigInitTask, "ConfigInit", 256, NULL, 2, NULL);
        xTaskCreate(ApplicationTask, "Application", 256, NULL, 3, NULL);

        vTaskStartScheduler();
    }

    for (;;);
}

Expected Behavior

  • All three initialization tasks perform their operations.
  • Each task sets its corresponding event bit.
  • ApplicationTask remains blocked until all three bits are set.
  • If all conditions are met before the timeout, normal operation starts.
  • Otherwise, the application follows its incomplete-initialization handling path.
This example assumes the initialization tasks set their bits only after successful completion. A production system should also report initialization failures explicitly, rather than treating every missing ready bit as an undifferentiated timeout.

11. Timeout Handling

A finite wait time prevents a task from blocking indefinitely when an expected event does not occur.

Example

EventBits_t result;

result = xEventGroupWaitBits(
    xEvents,
    ALL_READY_BITS,
    pdTRUE,
    pdTRUE,
    pdMS_TO_TICKS(3000)
);

if ((result & ALL_READY_BITS) == ALL_READY_BITS)
{
    /* All requested events were received. */
}
else
{
    /* At least one requested event was missing at timeout. */
}

The returned event bits can be inspected to identify which readiness conditions were present when the task left the wait.

A timeout is not proof that a particular subsystem failed. It indicates only that the requested condition was not satisfied within the specified wait interval. Application-specific diagnostics should identify the underlying cause.

12. Important Design Considerations

  • Use wait-any when any one event is sufficient to continue.
  • Use wait-all when every specified prerequisite must be satisfied.
  • Use named masks to make event combinations readable.
  • Check the returned bits instead of assuming the requested condition succeeded.
  • Use finite timeouts when indefinite waiting is unacceptable.
  • Understand clear-on-exit behavior before sharing an event group among multiple waiters.
  • Event bits do not count repeated occurrences.
  • Use queues when events carry data or every occurrence must be preserved.
  • Use task notifications for efficient task-directed signaling where appropriate.

15. Lesson Summary

  • Wait-any unblocks when at least one requested event bit is set.
  • Wait-all unblocks only when every requested event bit is set.
  • The fourth parameter of xEventGroupWaitBits selects the waiting mode.
  • The returned EventBits_t value identifies the event bits observed when the wait ends.
  • Clear-on-exit controls automatic clearing after a successful wait.
  • Finite timeouts help prevent indefinite blocking.
  • Event groups coordinate conditions but do not count repeated events or transfer payload data.
