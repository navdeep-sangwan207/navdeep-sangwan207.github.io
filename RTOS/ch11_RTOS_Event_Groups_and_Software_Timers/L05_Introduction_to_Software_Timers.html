1. Learning Objectives

Software timers allow an application to schedule a function to execute after a specified number of RTOS ticks. They are useful for periodic monitoring, delayed actions, timeout processing and other time-based operations.

  • Understand the purpose of software timers.
  • Differentiate hardware timers and software timers.
  • Understand timer periods and expiration.
  • Learn one-shot and auto-reload timer concepts.
  • Understand timer callbacks and the timer service task.
  • Identify timer configuration requirements.
  • Use software timers in embedded application designs.

2. What Is a Software Timer?

A software timer is an RTOS-managed timing mechanism that schedules a callback function to execute when a specified time period expires.

Unlike a hardware timer, which is implemented by a microcontroller peripheral, a FreeRTOS software timer is managed by the kernel using its timer service task and RTOS tick count.

Basic Working

  1. The application creates a software timer.
  2. The timer is assigned a period in RTOS ticks.
  3. The application starts the timer.
  4. The kernel tracks the timer expiration time.
  5. When the timer expires, its callback is processed by the timer service task.
  6. The callback performs the required short operation.
A software timer does not create a separate task for every timer. FreeRTOS uses a shared timer service task to process software timer commands and callbacks.

3. Why Are Software Timers Required?

Embedded applications frequently need to perform operations after a delay or at regular intervals. Creating a separate task for every small timing requirement can increase memory and scheduling overhead.

Common Applications

Application Timer Requirement
Sensor monitoring Schedule periodic sensor checks.
Communication timeout Detect missing responses after a defined interval.
Status indication Generate periodic status events.
Application supervision Schedule periodic health checks.
Delayed operation Trigger an action after a specified delay.
Protocol handling Implement protocol-level timeout monitoring.

4. Hardware Timer vs Software Timer

Feature Hardware Timer FreeRTOS Software Timer
Implementation Microcontroller timer peripheral. RTOS kernel service.
Time base Peripheral clock and prescaler. RTOS tick count.
Expiration handling Hardware interrupt or peripheral event. Timer service task processes expiration.
Number available Limited by hardware peripherals. Multiple timers can be created subject to memory and configuration.
Typical use PWM, input capture, precise hardware timing. Periodic application events and delayed callbacks.
Execution context Often interrupt context when interrupt-driven. Timer callback executes in timer service task context.
A FreeRTOS software timer is not a replacement for every hardware timer. Applications requiring precise waveform generation, input capture, high-resolution measurement or tightly controlled peripheral timing should use suitable hardware peripherals.

5. Software Timer Architecture

FreeRTOS uses a timer service task, also called the timer daemon task, to manage software timer operations.

Important Components

  • Timer handle: Identifies a software timer.
  • Timer period: Defines the expiration interval in ticks.
  • Timer command queue: Carries timer commands to the timer service task.
  • Timer service task: Processes timer commands and expired timers.
  • Callback function: Runs when the timer expires.
  • Timer ID: Optional application-defined value associated with a timer.

Conceptual Architecture

        Application Task
               |
               | Create / Start / Stop
               v
        FreeRTOS Timer API
               |
               v
        Timer Command Queue
               |
               v
        Timer Service Task
               |
               | Checks expiration
               v
        Timer Callback Function
               |
               v
        Application Action

Timer API commands generally communicate with the timer service task through a command queue. The timer service task processes those commands and executes callbacks when timers expire.

6. Timer Period and RTOS Tick

FreeRTOS software timer periods are specified in TickType_t units, not directly in milliseconds. The conversion depends on the configured RTOS tick rate.

Tick Rate Example

Tick Rate Nominal Tick Interval 100-Tick Period
100 Hz 10 ms 1000 ms
250 Hz 4 ms 400 ms
500 Hz 2 ms 200 ms
1000 Hz 1 ms 100 ms

Milliseconds to Ticks

TickType_t period;

period = pdMS_TO_TICKS(1000);

If the RTOS tick rate is 1000 Hz, this represents a nominal period of 1000 ticks.

Use pdMS_TO_TICKS() rather than assuming that one tick always equals one millisecond. For short intervals, conversion may produce zero ticks; ensure the requested period is valid and non-zero.

7. Timer Creation API

The xTimerCreate() function creates a software timer and returns its handle.

Function Prototype

TimerHandle_t xTimerCreate(
    const char * const pcTimerName,
    TickType_t xTimerPeriodInTicks,
    BaseType_t xAutoReload,
    void * pvTimerID,
    TimerCallbackFunction_t pxCallbackFunction
);

Parameters

Parameter Description
pcTimerName Human-readable timer name, mainly useful for debugging.
xTimerPeriodInTicks Timer period expressed in RTOS ticks. It must be non-zero.
xAutoReload pdTRUE for auto-reload; pdFALSE for one-shot operation.
pvTimerID Optional application-defined timer identifier.
pxCallbackFunction Function called when the timer expires.

Return Value

  • A valid TimerHandle_t if creation succeeds.
  • NULL if the timer could not be created.
TimerHandle_t xTimer;

xTimer = xTimerCreate(
    "StatusTimer",
    pdMS_TO_TICKS(1000),
    pdTRUE,
    NULL,
    TimerCallback
);

if (xTimer == NULL)
{
    /* Handle timer creation failure. */
}

8. Timer Callback Function

A timer callback is a function executed by the timer service task when the associated software timer expires.

Function Format

void TimerCallback(TimerHandle_t xTimer)
{
    /* Timer expiration handling */
}

Important Characteristics

  • The callback receives the handle of the timer that expired.
  • It executes in the timer service task context.
  • It is not a hardware interrupt service routine.
  • It must not call APIs that block or suspend the timer service task.
  • It should execute quickly.
  • Long processing should be transferred to an application task using a queue or task notification.
Avoid long delays, blocking queue operations, waiting for semaphores and lengthy calculations inside timer callbacks. One callback that blocks can delay other timer operations and callbacks.

9. Starting a Software Timer

The xTimerStart() API sends a start command to the timer service task.

Function Prototype

BaseType_t xTimerStart(
    TimerHandle_t xTimer,
    TickType_t xTicksToWait
);

Parameters

  • xTimer: Handle of the timer to start.
  • xTicksToWait: Maximum time the calling task waits for space in the timer command queue.

Example

if (xTimerStart(xTimer, pdMS_TO_TICKS(100)) != pdPASS)
{
    /* Timer start command was not accepted. */
}

A successful return means the command was successfully sent to the timer command queue. It does not mean that the callback has already executed.

10. One-Shot and Auto-Reload Timer Overview

FreeRTOS supports two main timer operation modes: one-shot and auto-reload. The selected mode is configured when the timer is created.

One-Shot Timer

  • Expires once after the configured period.
  • Its callback executes once for that expiration.
  • It becomes inactive after expiration.
  • It can be started again using a timer API command.

Auto-Reload Timer

  • Expires repeatedly at the configured interval.
  • The callback executes after each expiration.
  • It continues until stopped or deleted.
  • Useful for recurring monitoring and periodic status events.
Feature One-Shot Auto-Reload
Creation parameter pdFALSE pdTRUE
Expiration Once Repeatedly
Automatic restart No Yes
Typical application Communication timeout Periodic monitoring

11. Timer Configuration

Software timers require appropriate FreeRTOS configuration. Important configuration macros are generally defined in FreeRTOSConfig.h.

Configuration Purpose
configUSE_TIMERS Enables or disables software timer functionality.
configTIMER_TASK_PRIORITY Sets the timer service task priority.
configTIMER_QUEUE_LENGTH Sets the timer command queue length.
configTIMER_TASK_STACK_DEPTH Sets the timer service task stack depth. 
/* Illustrative configuration values */

#define configUSE_TIMERS                 1
#define configTIMER_TASK_PRIORITY        2
#define configTIMER_QUEUE_LENGTH         10
#define configTIMER_TASK_STACK_DEPTH     256
These are illustrative values, not universal recommendations. Select stack depth, priority and queue length based on the target application, timer callback workload and system timing requirements.

12. Timer Service Task and Command Queue

Timer operations such as start, stop, reset and change-period are communicated to the timer service task through a command queue.

Important Consequences

  • Timer commands are processed asynchronously by the timer service task.
  • Command queue capacity is finite.
  • A timer API may fail to enqueue a command if the queue remains full within the allowed wait time.
  • Callback execution depends on the timer service task being scheduled.
  • A long-running callback can delay other timer callbacks and commands.
  • Timer service task priority affects how promptly timer work is processed.
Timer periods do not guarantee exact callback execution times. Tick resolution, scheduling latency, command processing and callback execution all influence when application code runs.

13. Software Timer Limitations

  • Timer resolution is limited by the RTOS tick rate and implementation.
  • Callback execution can be delayed by higher-priority tasks.
  • Long callbacks can delay other timers.
  • Timer commands can be delayed by command queue congestion.
  • Software timers are not suitable for precise PWM generation.
  • Software timers should not replace hardware capture/compare peripherals when precise edge timing is required.
  • Tick count wraparound must be handled by the kernel's timer implementation; applications should avoid custom unsafe tick comparisons.

14. Practical Activity

Activity – Periodic System Status Monitoring

Objective: Design a FreeRTOS application that generates a periodic status event using a software timer.

  1. Create an auto-reload timer with a 1000 ms period.
  2. Write a timer callback that sends a status message to an application queue using a non-blocking operation.
  3. Create a monitoring task that receives the status message.
  4. Display or record the received status from the monitoring task.
  5. Check the return values of timer creation, timer start and queue operations.
  6. Observe how timer service task priority and callback execution time affect the application.

Expected Result: The timer periodically triggers a short callback. The monitoring task processes the resulting status event independently.

This is a design exercise. Actual execution requires a compatible FreeRTOS target or simulator. Do not assume that the LPC2129 Keil uVision simulator has a supported FreeRTOS port.

16. Lesson Summary

  • FreeRTOS software timers schedule callback functions after configured tick intervals.
  • The timer service task manages timer commands and callback execution.
  • Timer periods are specified in RTOS ticks.
  • pdMS_TO_TICKS() converts milliseconds into ticks.
  • xTimerCreate() creates a software timer.
  • xTimerStart() sends a start command to the timer service task.
  • One-shot timers expire once; auto-reload timers expire repeatedly.
  • Callbacks execute in task context and should remain short and non-blocking.
  • Software timers are suitable for application-level timing, not every precision hardware-timing requirement.
