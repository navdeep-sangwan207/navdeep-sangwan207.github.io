Chapter 16: FreeRTOS Semaphores and Mutexes

Lesson 07 – Semaphore Communication from ISR

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

An Interrupt Service Routine (ISR) is executed when a hardware or software interrupt occurs. In an RTOS-based embedded system, an ISR may need to notify a task that an event has occurred.

FreeRTOS provides special semaphore APIs for interrupt context. These APIs allow an ISR to signal a task without using task-context functions that may block.

Learning Objectives

  • Understand communication between an ISR and an RTOS task.
  • Learn why normal semaphore APIs must not be used in an ISR.
  • Understand xSemaphoreGiveFromISR().
  • Understand xSemaphoreTakeFromISR() and its limitations.
  • Learn the purpose of pxHigherPriorityTaskWoken.
  • Understand ISR-triggered context switching.
  • Design a short ISR with deferred task processing.
  • Identify common interrupt and semaphore programming errors.

1. Why ISR-to-Task Communication Is Required

Consider an embedded system that receives data through a UART peripheral. When a byte or a group of bytes is received, the hardware generates an interrupt.

The ISR should acknowledge the interrupt, capture the required information, and notify a task. The task can then perform longer processing outside interrupt context. 

        Hardware Event
              |
              v
        Interrupt Occurs
              |
              v
       Interrupt Service Routine

The ISR handles time-critical interrupt work. The task handles deferred processing that does not need to execute inside the ISR.

2. Why Normal Semaphore APIs Cannot Be Used in an ISR

The normal APIs xSemaphoreTake() and xSemaphoreGive() are intended for task context. A task may block while waiting for a semaphore. An ISR must never block because it would prevent normal interrupt completion.

Task ContextISR Context
xSemaphoreTake()xSemaphoreTakeFromISR()
xSemaphoreGive()xSemaphoreGiveFromISR()
May block for a specified timeMust not block
Runs as a scheduled taskRuns in interrupt context
Can use task-context kernel APIsMust use ISR-safe APIs where provided
Never call vTaskDelay(), a blocking queue operation, or a blocking semaphore operation from an ISR. Mutexes must not be used from an ISR.

3. xSemaphoreGiveFromISR()

This function gives a semaphore from an ISR. It is commonly used when an interrupt signals that an event has occurred.

Function Syntax

BaseType_t xSemaphoreGiveFromISR(
    SemaphoreHandle_t xSemaphore,
    BaseType_t *pxHigherPriorityTaskWoken
);

Parameters

ParameterDescription
xSemaphoreHandle of the semaphore being given.
pxHigherPriorityTaskWokenPointer to a variable used to report whether a higher-priority task was unblocked by the operation.

Return Value

Return valueMeaning
pdTRUEThe semaphore was successfully given.
pdFALSEThe give operation failed, for example because a binary semaphore was already full.

Example

void Device_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the device interrupt. */

    if (xSemaphoreGiveFromISR(
            xBinarySemaphore,
            &xHigherPriorityTaskWoken) == pdTRUE)
    {
        /* Semaphore successfully given. */
    }

    /* Use the selected port's ISR-yield mechanism
       when a higher-priority task was unblocked. */
}

The variable xHigherPriorityTaskWoken is initialized to pdFALSE. The API may set it to pdTRUE if a higher-priority task was unblocked.

4. Understanding pxHigherPriorityTaskWoken

An ISR can unblock a task that has a higher priority than the currently running task. In that situation, the scheduler may need to switch to the newly unblocked task after the ISR completes.

Example Scenario

When the ISR gives the semaphore, Task B may become Ready. Because Task B has a higher task priority than Task A, a context switch may be requested when the ISR exits.

The ISR does not directly execute Task B. It makes Task B Ready. The scheduler performs the context switch at the appropriate interrupt-exit or scheduling point.

5. ISR Yield Mechanism

Many FreeRTOS ports provide a macro for requesting a context switch at the end of an ISR when a higher-priority task has been unblocked. The exact macro depends on the port and FreeRTOS version.

A commonly encountered form in some ports is: 

portYIELD_FROM_ISR(xHigherPriorityTaskWoken);

Other ports may use a different macro or a different calling convention. Always check the selected port's header files and documentation.

Generic ISR Structure

void Device_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* 1. Acknowledge the interrupt source. */

    /* 2. Capture minimal required information. */

    /* 3. Notify a task. */
    xSemaphoreGiveFromISR(
        xBinarySemaphore,
        &xHigherPriorityTaskWoken
    );

    /* 4. Request a switch using the correct
          ISR-yield mechanism for this port. */
}
Do not assume that portYIELD_FROM_ISR() is the correct macro for every FreeRTOS port. ARM7, Cortex-M, and other architectures can have different interrupt and yield mechanisms.

6. xSemaphoreTakeFromISR()

The xSemaphoreTakeFromISR() API attempts to obtain a semaphore token from an ISR without blocking.

Function Syntax

BaseType_t xSemaphoreTakeFromISR(
    SemaphoreHandle_t xSemaphore,
    BaseType_t *pxHigherPriorityTaskWoken
);

Parameters

  • xSemaphore: Handle of the applicable semaphore.
  • pxHigherPriorityTaskWoken: Pointer to a variable used to report whether a higher-priority task was unblocked as a result of the operation, where relevant to the API and port.

Behavior

  • The operation does not wait for a token.
  • If a token is available, the take operation succeeds.
  • If no token is available, it returns failure immediately.
  • It is not a way for an ISR to wait for another task to give a semaphore.
Use xSemaphoreTakeFromISR() only for semaphore types and use cases supported by the selected FreeRTOS release. It is not a substitute for task-context mutex acquisition. Mutexes must not be taken or given from an ISR.

7. Binary Semaphore for Interrupt Notification

A binary semaphore is a common mechanism for notifying a task that an interrupt event has occurred.

Example: Interrupt Notification

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xInterruptSemaphore;

void InterruptHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge interrupt source. */

    xSemaphoreGiveFromISR(
        xInterruptSemaphore,
        &xHigherPriorityTaskWoken
    );

    /* Invoke the appropriate port-specific
       ISR-yield mechanism if required. */
}

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xInterruptSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Process the interrupt event. */
        }
    }
}

int main(void)
{
    xInterruptSemaphore = xSemaphoreCreateBinary();

    if (xInterruptSemaphore == NULL)
    {
        for (;;);
    }

    xTaskCreate(
        ProcessingTask,
        "Process",
        256,
        NULL,
        3,
        NULL
    );

    /* Configure peripheral and interrupt source
       using the selected MCU and port. */

    vTaskStartScheduler();

    for (;;);
}

Expected Operation

  1. The processing task starts and waits for the semaphore.
  2. A peripheral interrupt occurs.
  3. The ISR acknowledges the interrupt source.
  4. The ISR gives the binary semaphore.
  5. The processing task becomes Ready.
  6. The task processes the event when scheduled.
  7. The task waits for the next notification.
This example shows the RTOS communication pattern. Actual peripheral interrupt setup and ISR registration are MCU- and port-specific and must be added for a real target.

8. Binary Semaphore vs Counting Semaphore for ISR Events

FeatureBinary SemaphoreCounting Semaphore
Maximum count1Configured maximum
PurposeNotification or synchronizationCounting multiple pending events or tokens
Repeated giveAdditional gives can fail while fullCount increases until maximum
Event retentionDoes not count repeated eventsCounts events up to maximum
Payload transferNoNo

If every interrupt event must be counted, a counting semaphore may be suitable. If each interrupt carries data, a queue or another buffer-based mechanism is usually more appropriate.

9. Queue Communication from ISR

A semaphore communicates that an event occurred, but it does not transfer the event's data. If an ISR receives a data item, a queue can transfer that item to a task.

Queue Send from ISR

BaseType_t xQueueSendFromISR(
    QueueHandle_t xQueue,
    const void *pvItemToQueue,
    BaseType_t *pxHigherPriorityTaskWoken
);

Example

typedef struct
{
    uint16_t sensorValue;
    uint8_t channel;
} SensorMessage;

QueueHandle_t xSensorQueue;

void ADC_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    SensorMessage message;

    /* Read or capture the completed ADC result. */
    message.sensorValue = ADC_RESULT_VALUE;
    message.channel = 0;

    /* Acknowledge ADC interrupt source. */

    xQueueSendFromISR(
        xSensorQueue,
        &message,
        &xHigherPriorityTaskWoken
    );

    /* Use the selected port's ISR-yield mechanism. */
}

void SensorTask(void *pvParameters)
{
    SensorMessage received;

    for (;;)
    {
        if (xQueueReceive(
                xSensorQueue,
                &received,
                portMAX_DELAY) == pdTRUE)
        {
            /* Process received sensor data. */
        }
    }
}
ADC_RESULT_VALUE is a placeholder for the actual peripheral result-reading code. The queue copies the message bytes into its storage; the task receives a copy.

10. Best Practices for ISR-to-Task Communication

  1. Keep the ISR as short as possible.
  2. Acknowledge or clear the interrupt source correctly.
  3. Use only ISR-safe RTOS APIs from interrupt context.
  4. Never block or delay inside an ISR.
  5. Use a semaphore for simple event notification.
  6. Use a queue when data must be transferred.
  7. Use a counting semaphore if multiple pending events must be counted and a bounded count is appropriate.
  8. Check the return value of ISR API calls where appropriate.
  9. Use the port-specific ISR-yield mechanism.
  10. Protect shared buffers using a clear ownership and synchronization design.
  11. Ensure the interrupt priority is permitted to call FreeRTOS APIs by the selected port.
  12. Define what happens if a queue or semaphore is full.

11. Interrupt Priority and FreeRTOS API Restrictions

Not every hardware interrupt priority is necessarily permitted to call FreeRTOS APIs. The restrictions depend on the processor, interrupt controller, port implementation, and configuration.

For Cortex-M ports, FreeRTOS commonly uses NVIC priority configuration to restrict which interrupts may call kernel APIs. These Cortex-M rules must not be applied directly to ARM7.

LPC2129 Considerations

  • LPC2129 uses the ARM7TDMI-S processor.
  • It uses a Vectored Interrupt Controller (VIC), not a Cortex-M NVIC.
  • IRQ and FIQ are distinct ARM7 interrupt types.
  • Interrupt routing and masking must be handled according to the LPC2129 architecture.
  • A compatible FreeRTOS ARM7 port is required before using kernel APIs in its interrupts.
  • Verify the port's ISR entry, exit, nesting, and yield requirements.
The availability of a generic FreeRTOS ISR API does not establish that a particular LPC2129 + Keil uVision simulator project has a working FreeRTOS port. Verify the exact port and compiler support.

12. Practical Experiment

Objective

Study how a hardware interrupt can notify a task through a binary semaphore.

Procedure

  1. Create a binary semaphore before starting the scheduler.
  2. Create a task that waits for the semaphore.
  3. Configure a supported interrupt source for the target platform.
  4. In the ISR, acknowledge the interrupt.
  5. Call xSemaphoreGiveFromISR().
  6. Use the correct port-specific ISR-yield mechanism.
  7. Observe the task becoming Ready and processing the event.

Expected Result

  • The task waits while no interrupt notification is pending.
  • The interrupt triggers the ISR.
  • The ISR gives the semaphore without blocking.
  • The waiting task becomes Ready.
  • The task processes the event after it is scheduled.
For Keil uVision simulator-only work, first verify that the selected FreeRTOS ARM7 port and interrupt behavior are supported. If they are not, study the sequence using a conceptual trace or a small bare-metal ARM7 interrupt demonstration instead of claiming that the FreeRTOS experiment ran successfully.

14. Lesson Summary

  • ISRs often notify tasks about hardware events.
  • FreeRTOS provides ISR-specific APIs for semaphore communication.
  • xSemaphoreGiveFromISR() gives a semaphore without blocking.
  • xSemaphoreTakeFromISR() performs a non-blocking take where supported.
  • pxHigherPriorityTaskWoken reports whether a higher-priority task was unblocked.
  • The port-specific ISR-yield mechanism can request a context switch after interrupt processing.
  • Binary semaphores are useful for event notification.
  • Counting semaphores can count pending events up to a configured maximum.
  • Queues transfer data from an ISR to a task.
  • Interrupt priority restrictions depend on the selected architecture and FreeRTOS port.
