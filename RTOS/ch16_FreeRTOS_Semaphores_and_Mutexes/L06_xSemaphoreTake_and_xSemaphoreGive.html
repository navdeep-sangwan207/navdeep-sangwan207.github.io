Chapter 16: FreeRTOS Semaphores and Mutexes

Lesson 06 – xSemaphoreTake() and xSemaphoreGive()

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

Semaphores are synchronization objects used to coordinate tasks, signal events, and control access to shared resources. FreeRTOS provides xSemaphoreTake() and xSemaphoreGive() as fundamental operations for semaphore handling.

The take operation obtains a token or mutex ownership, while the give operation releases a token or relinquishes mutex ownership. Their exact behavior depends on the type of synchronization object.

Learning Objectives

  • Understand the purpose of take and give operations.
  • Learn the API syntax and parameters.
  • Understand blocking time and timeout behavior.
  • Interpret return values.
  • Use binary and counting semaphores correctly.
  • Understand mutex ownership rules.
  • Differentiate task-context and ISR-context APIs.
  • Develop task synchronization programs.

1. Introduction to Take and Give Operations

A semaphore maintains a synchronization state. A task uses the take operation to obtain a token. Another task or an event source can use the give operation to make a token available. 

Task A                         Task B
  |                              |
  |---- Take Semaphore           |
  |                              |
  |                         Give Semaphore
  |                              |
  |<------- Task A unblocked -----|
  |                              |
  |---- Continue execution       |

For a mutex, the take operation establishes ownership and the give operation releases ownership. A mutex is therefore not interchangeable with an ordinary event-signaling semaphore.

2. xSemaphoreTake() Function

The xSemaphoreTake() function attempts to obtain a semaphore token or acquire a mutex.

Function Syntax

BaseType_t xSemaphoreTake(
    SemaphoreHandle_t xSemaphore,
    TickType_t xTicksToWait
);

Parameters

ParameterDescription
xSemaphoreHandle of the semaphore or mutex to take.
xTicksToWaitMaximum number of RTOS ticks to wait if the object is unavailable.

Return Value

Return valueMeaning
pdTRUEThe semaphore was successfully taken.
pdFALSEThe semaphore could not be taken within the permitted wait time.

Operation

  1. The task calls xSemaphoreTake().
  2. If a token is available, it is obtained immediately.
  3. If no token is available and the wait time is zero, the call returns immediately.
  4. If waiting is permitted, the task enters the Blocked state.
  5. When a token becomes available, the task can become Ready.
  6. If the timeout expires first, the call returns pdFALSE.
A task becoming Ready does not mean it executes immediately. The scheduler selects it according to priority and scheduling rules.

3. Understanding xTicksToWait

The second parameter controls how long a task can wait for the semaphore.

ValueBehavior
0Do not wait. Return immediately if unavailable.
Finite tick valueWait for at most the specified number of ticks.
portMAX_DELAYRequest an indefinite wait where supported by the configuration.

Example: No Waiting

if (xSemaphoreTake(xSemaphore, 0) == pdTRUE)
{
    /* Token obtained immediately */
}
else
{
    /* No token was available */
}

Example: Finite Timeout

if (xSemaphoreTake(
        xSemaphore,
        pdMS_TO_TICKS(100)) == pdTRUE)
{
    /* Semaphore obtained */
}
else
{
    /* Timeout or unavailable */
}

Example: Indefinite Wait

if (xSemaphoreTake(
        xSemaphore,
        portMAX_DELAY) == pdTRUE)
{
    /* Continue after successful take */
}
The meaning of portMAX_DELAY as an indefinite wait depends on the selected FreeRTOS configuration, including INCLUDE_vTaskSuspend in configurations that use it.

4. xSemaphoreGive() Function

The xSemaphoreGive() function gives a semaphore token or releases a mutex owned by the calling task.

Function Syntax

BaseType_t xSemaphoreGive(
    SemaphoreHandle_t xSemaphore
);

Parameter

xSemaphore is the handle of the semaphore or mutex to be given.

Return Value

Return valueMeaning
pdTRUEThe give operation succeeded.
pdFALSEThe operation could not be completed.

Operation

  • For a binary semaphore, a token is made available if it is empty.
  • For a counting semaphore, the count increases if it is below its maximum.
  • For a mutex, the owning task releases the mutex.
  • If the operation makes a waiting task eligible to run, scheduling may switch to that task according to the kernel rules.
if (xSemaphoreGive(xSemaphore) == pdTRUE)
{
    /* Give operation successful */
}
else
{
    /* Give operation unsuccessful */
}

5. Take and Give with a Binary Semaphore

A binary semaphore can hold either zero or one token.

OperationCountState
Initial state0Empty
Give1Available
Take0Empty
Give again1Available

Example

SemaphoreHandle_t xBinarySemaphore;

void ConsumerTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xBinarySemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Process one signaled event */
        }
    }
}

void ProducerTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform or detect an event */

        xSemaphoreGive(xBinarySemaphore);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}
A binary semaphore stores at most one pending token. Repeated give operations while it is already full do not accumulate additional events. Use a counting semaphore or queue when every event must be retained.

6. Take and Give with a Counting Semaphore

A counting semaphore can store multiple tokens, up to its configured maximum count.

Example

SemaphoreHandle_t xCountingSemaphore;

void ConsumerTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xCountingSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Process one counted event */
        }
    }
}

void ProducerTask(void *pvParameters)
{
    for (;;)
    {
        /* An event occurs */

        if (xSemaphoreGive(xCountingSemaphore) != pdTRUE)
        {
            /* Maximum count may have been reached */
        }

        vTaskDelay(pdMS_TO_TICKS(200));
    }
}

Example Count Sequence

OperationCount
Initial count0
First give1
Second give2
Third give3
First take2
Second take1
Third take0

A counting semaphore tracks the number of available tokens. It does not store event payloads such as sensor readings or message contents. Use a queue when the actual data must be transferred.

7. Take and Give with a Mutex

A mutex protects a shared resource by allowing one task at a time to own it. 

SemaphoreHandle_t xMutex;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xMutex,
                portMAX_DELAY) == pdTRUE)
        {
            /* Access shared resource */

            xSemaphoreGive(xMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

Important Mutex Rules

  • The task that successfully takes the mutex becomes its owner.
  • The owner must release the mutex.
  • A different task must not give the mutex on behalf of the owner.
  • Mutexes cannot be taken or given from an ISR.
  • FreeRTOS mutexes support priority inheritance.
Do not use a mutex as a general event-signaling object. A binary semaphore is usually more appropriate when one task or ISR signals an event to another task.

8. Blocking and Task State Transitions

When a task cannot obtain a semaphore and specifies a nonzero wait time, it can enter the Blocked state. 

          Task calls xSemaphoreTake()
                       |
                       v
             Is token available?
                  /       \
                Yes        No
                |           |
                v           v
          Take succeeds   Is wait time zero?
                            /       \
                          Yes        No
                          |           |
                          v           v
                    Return false   Block task
                                      |
                                      v
                              Token becomes available?
                                  /        \
                                Yes        No
                                |           |
                                v           v
                             Ready      Timeout
                                           |
                                           v
                                      Return false

The task may be unblocked when another task gives the semaphore. If multiple tasks are waiting, the kernel's scheduling and priority rules determine which waiting task receives the token.

10. ISR-Specific Take and Give APIs

Interrupt Service Routines must not use task-context APIs that can block. FreeRTOS provides ISR-specific semaphore functions.

Give from ISR

BaseType_t xSemaphoreGiveFromISR(
    SemaphoreHandle_t xSemaphore,
    BaseType_t *pxHigherPriorityTaskWoken
);

Take from ISR

BaseType_t xSemaphoreTakeFromISR(
    SemaphoreHandle_t xSemaphore,
    BaseType_t *pxHigherPriorityTaskWoken
);

These ISR operations are non-blocking. They are intended for semaphore types and use cases supported by the selected FreeRTOS version and port.

Example: Giving a Binary Semaphore from an ISR

void Peripheral_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the peripheral interrupt first. */

    xSemaphoreGiveFromISR(
        xBinarySemaphore,
        &xHigherPriorityTaskWoken
    );

    /* Request a context switch using the port's ISR-yield
       mechanism when required. */
}
The exact ISR-yield macro is port-specific. Do not copy a Cortex-M-specific interrupt-priority or yield configuration into an ARM7 project without checking its FreeRTOS port.

11. Practical Example: Event Notification

Objective

To synchronize a producer task and a consumer task using a binary semaphore.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xEventSemaphore;

void ProducerTask(void *pvParameters)
{
    for (;;)
    {
        /* Simulate event detection */

        if (xSemaphoreGive(xEventSemaphore) != pdTRUE)
        {
            /* A token may already be pending */
        }

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void ConsumerTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xEventSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Process event */
        }
    }
}

int main(void)
{
    xEventSemaphore = xSemaphoreCreateBinary();

    if (xEventSemaphore == NULL)
    {
        for (;;);
    }

    xTaskCreate(ProducerTask,
                "Producer",
                256,
                NULL,
                2,
                NULL);

    xTaskCreate(ConsumerTask,
                "Consumer",
                256,
                NULL,
                2,
                NULL);

    vTaskStartScheduler();

    for (;;);
}

Expected Result

  • The consumer waits for the semaphore.
  • The producer periodically gives the semaphore.
  • A successful give can unblock the consumer.
  • The consumer processes the notification.
  • The consumer waits again for the next token.
This example demonstrates event notification only. If the producer must deliver a different data value for every event, use a queue or another data-transfer mechanism.

12. Common Programming Errors

  1. Ignoring return values: Always check whether the take or give operation succeeded.
  2. Using the wrong handle: Pass a valid, successfully created semaphore handle.
  3. Blocking inside an ISR: Use ISR-specific APIs.
  4. Using a mutex in an ISR: Mutexes are task-context synchronization objects.
  5. Incorrect timeout conversion: Use pdMS_TO_TICKS() when converting milliseconds.
  6. Assuming binary semaphore counts events: Repeated gives can coalesce into one pending token.
  7. Giving a mutex from the wrong task: Only its owner should release it.
  8. Forgetting to release a mutex: This can leave other tasks blocked indefinitely.
  9. Assuming Ready means Running: A higher-priority task or scheduling rule may determine when it executes.

13. Practical Experiment

Objective

Observe the behavior of semaphore take and give operations using two FreeRTOS tasks.

Procedure

  1. Create a binary semaphore.
  2. Create a producer task and a consumer task.
  3. Make the consumer call xSemaphoreTake() with portMAX_DELAY.
  4. Make the producer call xSemaphoreGive() periodically.
  5. Check the return values of both operations.
  6. Observe the task states using an available debugger or trace facility.
  7. Repeat using a finite timeout instead of portMAX_DELAY.

Expected Result

  • The consumer blocks while no token is available.
  • The producer makes a token available.
  • The consumer becomes Ready and later executes.
  • With a finite timeout, the consumer returns from the take operation if the timeout expires before a token arrives.
LPC2129 / Keil uVision note: Running this experiment requires a compatible FreeRTOS ARM7 port and appropriate compiler integration. LPC2129 uses ARM7TDMI-S, not Cortex-M. Verify the port and simulator support before assuming that the program will execute successfully.

15. Lesson Summary

  • xSemaphoreTake() obtains a semaphore token or mutex ownership.
  • xSemaphoreGive() releases a token or mutex ownership.
  • The take API includes a maximum wait time in ticks.
  • A task can block while waiting for a token.
  • pdTRUE indicates success and pdFALSE indicates failure.
  • Binary semaphores retain at most one pending token.
  • Counting semaphores retain tokens up to their maximum count.
  • Mutex ownership and priority inheritance distinguish mutexes from ordinary semaphores.
  • ISR-specific APIs are required in interrupt context.
  • Queues should be used when event payloads must be transferred.
