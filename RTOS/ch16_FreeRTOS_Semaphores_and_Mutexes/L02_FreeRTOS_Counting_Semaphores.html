Lesson 02 – FreeRTOS Counting Semaphores

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

A counting semaphore is a synchronization mechanism that maintains a count of available tokens. It allows a task to track multiple pending events or the number of available instances of a resource.

Unlike a binary semaphore, which can hold only one token, a counting semaphore can hold several tokens up to a configured maximum count.

Learning Objectives

  • Understand counting semaphore operation.
  • Differentiate binary and counting semaphores.
  • Learn the counting semaphore creation API.
  • Understand semaphore take and give operations.
  • Use counting semaphores for event counting.
  • Apply counting semaphores to resource-pool management.
  • Understand counting semaphore limitations.

1. What Is a Counting Semaphore?

A counting semaphore is a kernel synchronization object whose count represents the number of available tokens.

The count ranges from zero to a configured maximum value. 

0 <= Semaphore Count <= Maximum Count
  • If the count is greater than zero, a task can take a token.
  • Taking a token decreases the count by one.
  • Giving a token increases the count by one, provided the maximum has not been reached.
  • If the count is zero, a task attempting to take can block until a token becomes available or its timeout expires.

Example: Counting Available Tokens

Operation Semaphore Count
Initial count 3
Task takes one token 2
Another task takes one token 1
Another task takes one token 0
Task gives one token 1
Important: A counting semaphore stores a count, not event data. If every event contains a different value or message, use a queue to transfer that information.

2. Binary Semaphore vs Counting Semaphore

Feature Binary Semaphore Counting Semaphore
Maximum count 1 Configured maximum
Count range 0 to 1 0 to maximum
Purpose Event signaling or synchronization Counting events or available resources
Multiple pending tokens No Yes, up to maximum
Ownership No No
Priority inheritance No No
Example: A binary semaphore can represent whether at least one event is pending. A counting semaphore can represent how many events are pending, up to its maximum count.

3. Creating a Counting Semaphore

FreeRTOS provides xSemaphoreCreateCounting() to create a counting semaphore. 

SemaphoreHandle_t xSemaphoreCreateCounting(
    UBaseType_t uxMaxCount,
    UBaseType_t uxInitialCount
);

Function Parameters

Parameter Description
uxMaxCount Maximum number of tokens the semaphore can hold.
uxInitialCount Initial number of available tokens.

Return Value

  • Returns a valid SemaphoreHandle_t on success.
  • Returns NULL if creation fails, for example, because memory allocation fails.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xCountingSemaphore;

int main(void)
{
    xCountingSemaphore = xSemaphoreCreateCounting(5, 0);

    if (xCountingSemaphore == NULL)
    {
        /* Semaphore creation failed */
        for (;;);
    }

    /* Continue with task creation and scheduler startup */

    return 0;
}
The initial count must not exceed the maximum count. The example creates a semaphore with a maximum count of 5 and an initial count of 0, meaning that no tokens are initially available. This dynamic-creation API requires a suitable FreeRTOS heap.

4. Taking a Counting Semaphore

A task uses xSemaphoreTake() to obtain one token. 

xSemaphoreTake(
    xSemaphore,
    xTicksToWait
);

Operation

  1. If the count is greater than zero, the kernel decrements the count and the operation succeeds.
  2. If the count is zero, the task waits for the specified timeout.
  3. If a token becomes available before the timeout expires, the task can obtain it.
  4. If no token becomes available, the operation returns pdFALSE.

Example

if (xSemaphoreTake(xCountingSemaphore,
                   pdMS_TO_TICKS(1000)) == pdTRUE)
{
    /* One token was successfully obtained. */

    /* Perform the operation associated with this token. */
}
else
{
    /* Timeout: no token became available. */
}

Timeout Values

Value Meaning
0 Do not wait; check immediately.
Finite tick value Wait up to the specified number of ticks.
portMAX_DELAY Wait indefinitely when the relevant configuration supports indefinite blocking.

5. Giving a Counting Semaphore

A task uses xSemaphoreGive() to return or add one token to the semaphore. 

if (xSemaphoreGive(xCountingSemaphore) == pdTRUE)
{
    /* Token successfully added. */
}
else
{
    /* Semaphore was already at its maximum count. */
}

Operation

  • If the current count is below the maximum, the count increases by one.
  • If a task is blocked waiting for a token, it may become Ready after a successful give.
  • If the count is already at the maximum, the give operation fails and the count remains unchanged.
Remember: Giving a semaphore does not transfer a data item. It only changes the semaphore count and may unblock a waiting task.

6. Counting Semaphore from an ISR

An interrupt service routine can signal an event using xSemaphoreGiveFromISR(). 

BaseType_t xHigherPriorityTaskWoken = pdFALSE;

xSemaphoreGiveFromISR(
    xCountingSemaphore,
    &xHigherPriorityTaskWoken
);

/* Request a context switch if required.
   Use the ISR-yield mechanism provided by the selected port. */

Important ISR Rules

  • Use the FromISR API rather than the normal task-context API.
  • Do not block inside an ISR.
  • Keep interrupt service routines short.
  • Check the return value because the semaphore may already be at its maximum count.
  • Use the yield mechanism specified by the selected FreeRTOS port.
FreeRTOS interrupt-priority and ISR-yield rules are port-specific. Do not apply Cortex-M NVIC or BASEPRI rules to an ARM7 LPC2129 system.

7. Application 1: Counting Multiple Events

Suppose a system receives sensor events. A task must process one unit of work for every event received.

Working Principle

  1. Create a counting semaphore with maximum count 10 and initial count 0.
  2. Whenever an event occurs, the producer or ISR gives one token.
  3. The processing task takes one token.
  4. The task performs one unit of event-processing work.

Example Code

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xEventSemaphore;

void EventProducerTask(void *pvParameters)
{
    for (;;)
    {
        /* Example event-generation point */

        if (xSemaphoreGive(xEventSemaphore) != pdTRUE)
        {
            /* Token limit reached.
               Apply the application's overflow policy. */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void EventProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(xEventSemaphore,
                           portMAX_DELAY) == pdTRUE)
        {
            /* Process one event unit. */
        }
    }
}

int main(void)
{
    xEventSemaphore = xSemaphoreCreateCounting(10, 0);

    if (xEventSemaphore == NULL)
    {
        for (;;);
    }

    xTaskCreate(EventProducerTask,
                "Producer",
                256,
                NULL,
                2,
                NULL);

    xTaskCreate(EventProcessingTask,
                "Processor",
                256,
                NULL,
                2,
                NULL);

    vTaskStartScheduler();

    for (;;);
}
This is a generic FreeRTOS example. Stack-depth units and available APIs depend on the selected FreeRTOS release and port. The example's producer is a task, not a hardware ISR.

Expected Behaviour

  • The producer adds one token every 500 ms.
  • The processing task wakes when a token is available.
  • Each successful take consumes one token.
  • If the producer generates events faster than the consumer can process them, the count can increase.
  • If the maximum count is reached, additional give operations fail and the application must handle the overflow.

8. Application 2: Resource Pool Management

A counting semaphore can track the number of available instances in a pool of identical resources.

Example

Consider a system with four identical communication buffers. A counting semaphore is created with: 

xResourceSemaphore =
    xSemaphoreCreateCounting(4, 4);

Initially, all four buffer slots are available.

Operation Available Resource Count
Initial state 4
Task A obtains a resource 3
Task B obtains a resource 2
Task C obtains a resource 1
Task D obtains a resource 0
Task B releases its resource 1

Basic Resource Acquisition

if (xSemaphoreTake(xResourceSemaphore,
                   pdMS_TO_TICKS(1000)) == pdTRUE)
{
    /* A resource slot is available. */

    /* Obtain and use a specific buffer through
       the application's resource-management logic. */

    /* Release the resource slot when finished. */
    xSemaphoreGive(xResourceSemaphore);
}
else
{
    /* No resource became available in time. */
}
The semaphore tracks only the number of available slots. It does not identify which particular buffer is free. For distinct buffers, use a free-list, queue of buffer pointers, or another ownership-tracking mechanism alongside the semaphore.

9. Counting Semaphore vs Mutex

Feature Counting Semaphore Mutex
Primary purpose Count tokens, events, or available instances Protect shared resources
Ownership No ownership Has ownership
Priority inheritance No Supported by standard FreeRTOS mutexes
ISR use FromISR APIs where supported Not permitted
Typical application Event counting and resource availability Exclusive access to a shared resource

A counting semaphore is not a replacement for a mutex when exclusive ownership and priority inheritance are required.

10. Common Programming Errors

  1. Incorrect initial count: The initial count must not exceed the configured maximum.
  2. Ignoring give failure: A give can fail when the count has reached its maximum.
  3. Ignoring take timeout: Always handle the possibility that no token becomes available.
  4. Using a semaphore to transfer data: Use a queue when event payloads must be transferred.
  5. Using a counting semaphore as a mutex: Use a mutex for exclusive ownership and priority inheritance.
  6. Unbalanced resource accounting: Giving extra tokens can make the count inaccurate.
  7. Assuming the count identifies a resource: Maintain a separate free-list or resource ownership structure when individual resources must be selected.
  8. Ignoring overflow: Define what happens when the maximum count is reached.

11. Practical Experiment

Objective

To understand how a counting semaphore maintains multiple tokens and synchronizes a producer task with a consumer task.

Experiment Setup

  • Create a counting semaphore with maximum count 5.
  • Set its initial count to 0.
  • Create one producer task and one consumer task.
  • The producer gives a token periodically.
  • The consumer takes a token and processes one event.

Expected Result

  • The consumer waits while the semaphore count is zero.
  • Each successful give makes one token available.
  • Each successful take consumes one token.
  • The consumer processes events as tokens become available.
  • The count never exceeds the configured maximum.
Keil uVision / LPC2129 note: This experiment requires a compatible FreeRTOS ARM7 port, compiler integration, startup code, and linker configuration. The LPC2129 uses an ARM7TDMI-S core, not a Cortex-M core. Do not assume that a generic FreeRTOS project will run in the Keil simulator without verifying those components. The semaphore logic can also be studied using a supported FreeRTOS simulator or compatible development board.

13. Lesson Summary

  • A counting semaphore maintains a count of available tokens.
  • The count ranges from zero to the configured maximum.
  • xSemaphoreCreateCounting() creates the semaphore.
  • xSemaphoreTake() obtains one token.
  • xSemaphoreGive() adds one token.
  • xSemaphoreGiveFromISR() signals from an ISR where supported by the port.
  • Counting semaphores can count pending events and track available resource instances.
  • They do not provide ownership or priority inheritance.
  • Queues should be used when actual data must be transferred.
