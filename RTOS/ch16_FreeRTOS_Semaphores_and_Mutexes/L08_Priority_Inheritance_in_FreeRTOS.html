Lesson 08 – Priority Inheritance in FreeRTOS

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

Priority inheritance is a synchronization technique used to reduce the effects of priority inversion. FreeRTOS mutexes support priority inheritance so that a lower-priority task holding a mutex can temporarily execute at an elevated priority when a higher-priority task is waiting for that mutex.

This mechanism helps the mutex owner finish its critical section sooner and release the shared resource. It does not eliminate all blocking or guarantee that every task will meet its deadline.

Learning Objectives

  • Understand priority inversion.
  • Understand the purpose of priority inheritance.
  • Learn how FreeRTOS mutexes implement priority inheritance.
  • Understand task priority before, during, and after inheritance.
  • Study a numerical scheduling example.
  • Learn the limitations of priority inheritance.
  • Differentiate mutexes and binary semaphores in this context.
  • Apply safe resource-sharing practices.

1. What Is Priority Inversion?

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task. A common cause is a shared resource protected by a mutex.

Example Tasks

TaskPriorityPurpose
Task H3 – HighNeeds shared resource
Task M2 – MediumPerforms unrelated processing
Task L1 – LowCurrently owns shared resource

Priority Inversion Sequence

  1. Task L takes a mutex and starts using a shared resource.
  2. Task H becomes Ready and preempts Task L.
  3. Task H attempts to take the same mutex.
  4. The mutex is already owned by Task L, so Task H blocks.
  5. Task M becomes Ready and preempts Task L.
  6. Task M executes while Task H remains blocked.
  7. Task L cannot release the mutex until it gets CPU time again.
  8. Task H is indirectly delayed by Task M.

Priority inversion is not simply a low-priority task executing before a high-priority task. The important condition is that the high-priority task is blocked by a resource held by a lower-priority task, and medium-priority activity can extend that blocking.

2. What Is Priority Inheritance?

Priority inheritance is a protocol in which a task holding a mutex temporarily inherits a higher priority when a higher-priority task blocks while trying to obtain that mutex.

The mutex owner receives an elevated effective priority so that medium-priority tasks are less likely to preempt it. Once the owner releases the mutex, its priority can be reduced according to the kernel's inheritance rules.

Basic Operation

  1. Task L takes a mutex.
  2. Task H attempts to take the same mutex and blocks.
  3. Task L inherits Task H's priority.
  4. Task L executes at the inherited priority and finishes its critical section.
  5. Task L gives the mutex.
  6. Task H becomes Ready and can execute according to scheduling rules.
  7. Task L's priority is adjusted by the kernel.

Priority inheritance changes the effective priority of the mutex owner. It does not transfer mutex ownership to the higher-priority task.

3. Priority Inheritance in FreeRTOS

FreeRTOS mutexes implement a basic priority inheritance mechanism. When a higher-priority task blocks on a mutex held by a lower-priority task, the owner can inherit the priority of the highest-priority task waiting for that mutex.

Mutex Creation

SemaphoreHandle_t xMutex;

xMutex = xSemaphoreCreateMutex();

if (xMutex == NULL)
{
    /* Mutex creation failed */
}

Mutex Acquisition and Release

if (xSemaphoreTake(
        xMutex,
        portMAX_DELAY) == pdTRUE)
{
    /* Access shared resource */

    xSemaphoreGive(xMutex);
}

The priority inheritance behavior is associated with FreeRTOS mutexes. A binary semaphore does not provide the same mutex ownership and priority inheritance behavior.

Use xSemaphoreCreateMutex() for a resource that requires mutual exclusion between tasks. Do not substitute a binary semaphore when mutex ownership and priority inheritance are required.

4. Numerical Example of Priority Inheritance

Assume three tasks with the following priorities:

TaskBase PriorityFunction
Task H3High-priority control task
Task M2Medium-priority processing
Task L1Low-priority resource owner

Without Priority Inheritance

  • Task L takes the mutex.
  • Task H becomes Ready and preempts Task L.
  • Task H blocks while waiting for the mutex.
  • Task M preempts Task L.
  • Task L waits longer before it can release the mutex.

With Priority Inheritance

  • Task L takes the mutex.
  • Task H blocks while waiting for the mutex.
  • Task L inherits priority 3.
  • Task M at priority 2 cannot preempt Task L while it remains at inherited priority 3 and Ready.
  • Task L releases the mutex after completing the critical section.
  • Task H becomes Ready and is selected according to the scheduler.

5. Task Priority Before and After Inheritance

It is useful to distinguish a task's base priority from its temporary effective priority.

StageTask L Base PriorityTask L Effective Priority
Before taking mutex11
After taking mutex, no higher waiter11
Higher-priority task blocks on mutex1May rise to 3
After releasing relevant mutex1Adjusted by kernel rules

The effective priority may be temporarily raised to reduce priority inversion. The task's configured base priority remains a separate concept.

6. Priority Inheritance with Multiple Waiting Tasks

Suppose several tasks with different priorities are waiting for a mutex owned by one task.

TaskPriorityState
Task H14Blocked on mutex
Task H23Blocked on mutex
Task M2Ready
Task L1Owns mutex

The mutex owner can inherit the highest priority among tasks waiting for that mutex. In this example, the relevant inherited priority can be 4.

Exact priority adjustment and disinheritance behavior can depend on the FreeRTOS kernel version and the number of mutexes held. Do not assume a fully general priority-ceiling or priority inheritance protocol.

Choose the synchronization object according to the required behavior. Use a mutex to protect a resource shared by tasks. Use a binary semaphore for event notification, including notification from an ISR.

8. Limitations of Priority Inheritance

Priority inheritance reduces some forms of priority inversion, but it is not a complete real-time scheduling solution.

  • It does not eliminate the time spent waiting for a mutex.
  • It does not guarantee that all deadlines will be met.
  • It does not prevent deadlock.
  • It does not prevent starvation in every possible system design.
  • It does not remove blocking caused by long critical sections.
  • It does not automatically protect resources that are not guarded by the mutex.
  • It is not a substitute for careful task priority assignment.
  • FreeRTOS mutex inheritance is a basic mechanism, not a full implementation of every theoretical inheritance protocol.
Do not hold a mutex while performing long delays, lengthy calculations, or slow peripheral operations unless the design explicitly requires it and the blocking consequences have been analyzed.

9. FreeRTOS Programming Example

Objective

Create two tasks that share a resource protected by a mutex. The example demonstrates correct mutex acquisition and release.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xMutex;

int sharedCounter = 0;

void LowPriorityTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            /* Simulated short resource operation. */

            xSemaphoreGive(xMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void HighPriorityTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xMutex,
                portMAX_DELAY) == pdTRUE)
        {
            int localValue = sharedCounter;

            /* Use the protected value. */

            (void)localValue;

            xSemaphoreGive(xMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

int main(void)
{
    xMutex = xSemaphoreCreateMutex();

    if (xMutex == NULL)
    {
        for (;;);
    }

    xTaskCreate(
        LowPriorityTask,
        "Low",
        256,
        NULL,
        1,
        NULL
    );

    xTaskCreate(
        HighPriorityTask,
        "High",
        256,
        NULL,
        3,
        NULL
    );

    vTaskStartScheduler();

    for (;;);
}

Expected Result

  • The mutex is created successfully if sufficient memory is available.
  • Both tasks attempt to access the shared counter.
  • Only the task holding the mutex accesses the protected section.
  • If a higher-priority task blocks on the mutex, the owner can inherit priority.
  • The owner releases the mutex after completing the protected operation.
This example demonstrates mutex-protected access. It does not guarantee that priority inversion will occur on every run. To observe inheritance, create a controlled test in which a low priority task holds the mutex while a higher-priority task attempts to take it and a medium-priority task becomes Ready.

10. Practical Experiment

Objective

Study priority inversion and the effect of mutex-based priority inheritance.

Procedure

  1. Create three tasks with priorities 1, 2, and 3.
  2. Let the low-priority task take a mutex.
  3. Arrange for the high-priority task to request the same mutex.
  4. Make the medium-priority task Ready while the high-priority task is blocked.
  5. Observe task execution and the mutex owner's effective priority.
  6. Repeat the experiment using a binary semaphore for comparison, while carefully controlling ownership and synchronization.
  7. Compare the delay experienced by the high-priority task.

Expected Result

  • Without inheritance, medium-priority execution can delay the low-priority mutex owner.
  • With mutex priority inheritance, the low-priority owner can temporarily execute at the inherited priority.
  • The mutex owner releases the resource, allowing the waiting high-priority task to proceed.
For LPC2129 and Keil uVision, this experiment requires a verified ARM7 FreeRTOS port. Do not use Cortex-M interrupt-priority settings or assume simulator support without checking the selected port.

12. Lesson Summary

  • Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task.
  • Priority inheritance temporarily raises the effective priority of a mutex owner.
  • FreeRTOS mutexes provide a basic priority inheritance mechanism.
  • Binary semaphores do not provide mutex priority inheritance.
  • Priority inheritance does not transfer mutex ownership.
  • The mutex owner must release the mutex after using the resource.
  • Priority inheritance reduces certain delays but does not eliminate all blocking.
  • It does not prevent deadlock or guarantee real-time deadlines.
  • Short critical sections and appropriate task priorities remain essential.
