Lesson 03 – FreeRTOS Mutexes

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

A mutex, or mutual exclusion object, is a synchronization mechanism used to protect shared resources from simultaneous access by multiple tasks.

In FreeRTOS, a mutex provides ownership semantics and supports priority inheritance. These features help coordinate access to resources such as UART interfaces, shared data structures, communication peripherals, and other non-reentrant components.

Learning Objectives

  • Understand mutual exclusion and mutex operation.
  • Learn the ownership concept of a mutex.
  • Understand mutex creation and deletion.
  • Use mutex take and give operations.
  • Protect shared resources in FreeRTOS applications.
  • Understand priority inheritance.
  • Identify common mutex programming errors.

1. What Is a Mutex?

A mutex is a synchronization object that ensures only one task at a time owns a protected resource.

The term mutex comes from mutual exclusion. When a task successfully takes a mutex, it becomes the owner. Other tasks attempting to take the same mutex must wait until the owner releases it.

Basic Mutex Operation

  1. A task attempts to take the mutex.
  2. If the mutex is available, the task obtains ownership.
  3. The task accesses the protected resource.
  4. The task gives the mutex when it has finished.
  5. A waiting task may then obtain the mutex.
Example: Two tasks need to transmit messages through the same UART peripheral. A mutex can ensure that only one task performs the protected transmission operation at a time.

2. Why Are Mutexes Required?

In a multitasking system, several tasks may need to access the same resource. Without synchronization, their operations can overlap and produce incorrect results.

Example: Shared UART

Suppose Task A wants to transmit HELLO and Task B wants to transmit WORLD.

Without mutual exclusion, the output may become interleaved:

HWEOLRLLOD

The exact result depends on the timing of the tasks and the UART driver implementation.

With a Mutex

Task A takes mutex
Task A transmits "HELLO"
Task A gives mutex

Task B takes mutex
Task B transmits "WORLD"
Task B gives mutex

The protected transmissions are serialized:

HELLOWORLD
A mutex protects the operations placed inside its ownership interval. It does not automatically protect unrelated code, hardware activity, DMA transfers, or interrupt handlers.

3. Mutex Ownership

Ownership is a defining property of a mutex.

  • A task that successfully takes a mutex becomes its owner.
  • The owning task is responsible for releasing the mutex.
  • Another task cannot legitimately release a mutex owned by a different task.
  • A task should not delete or abandon a mutex while it still owns it.

Ownership Example

Task A:
    Take Mutex
    Access Shared Resource
    Give Mutex

Task B:
    Take Mutex
    Wait if unavailable
    Access Shared Resource
    Give Mutex
A mutex is not an event-signaling object. Do not use it as a substitute for a binary semaphore when one task or an ISR needs to signal an event to another task.

4. Creating a FreeRTOS Mutex

FreeRTOS provides xSemaphoreCreateMutex() to create a mutex. 

SemaphoreHandle_t xSemaphoreCreateMutex(void);

Return Value

  • Returns a valid semaphore handle if creation succeeds.
  • Returns NULL if creation fails, for example, because memory allocation fails.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xUARTMutex;

int main(void)
{
    xUARTMutex = xSemaphoreCreateMutex();

    if (xUARTMutex == NULL)
    {
        /* Mutex creation failed */
        for (;;);
    }

    /* Create application tasks here. */

    vTaskStartScheduler();

    for (;;);
}
xSemaphoreCreateMutex() is a dynamic-allocation API. Static mutex creation is also available in supported FreeRTOS configurations using xSemaphoreCreateMutexStatic().

5. Taking a Mutex

A task uses xSemaphoreTake() to obtain ownership of a mutex. 

xSemaphoreTake(
    xMutex,
    xTicksToWait
);

Operation

  1. If the mutex is available, the task takes it.
  2. If another task owns it, the calling task can enter the Blocked state while waiting.
  3. If the mutex becomes available before the timeout, the waiting task may obtain ownership.
  4. If the timeout expires first, the take operation fails.

Example

if (xSemaphoreTake(xUARTMutex,
                   pdMS_TO_TICKS(1000)) == pdTRUE)
{
    /* Mutex acquired. */

    /* Access the protected UART resource. */

    xSemaphoreGive(xUARTMutex);
}
else
{
    /* Mutex could not be obtained within the timeout. */
}
Always define a failure policy for mutex acquisition. Do not access the protected resource when the take operation has failed.

6. Giving a Mutex

The owning task releases a mutex using xSemaphoreGive(). 

if (xSemaphoreGive(xUARTMutex) != pdTRUE)
{
    /* Handle an unexpected release failure. */
}

Important Rules

  • The task that owns the mutex should release it.
  • Release the mutex after completing the protected operation.
  • Do not give the same mutex multiple times without successfully taking it again.
  • Do not block indefinitely or perform unnecessary long operations while holding a mutex.

7. Deleting a Mutex

FreeRTOS provides vSemaphoreDelete() to delete a semaphore or mutex object. 

vSemaphoreDelete(xUARTMutex);

xUARTMutex = NULL;

Deleting a mutex releases its dynamically allocated kernel storage when applicable. Static storage remains owned by the application.

Do not delete a mutex while tasks are using it or while a task owns it. Coordinate shutdown so that no task can access the object after deletion.

8. Complete Example: Protecting a Shared Resource

Objective

To use a FreeRTOS mutex to protect a shared resource accessed by two tasks.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xResourceMutex;

int sharedCounter = 0;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(xResourceMutex,
                           portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            /* Protected resource operation */

            xSemaphoreGive(xResourceMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(xResourceMutex,
                           portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            /* Protected resource operation */

            xSemaphoreGive(xResourceMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

int main(void)
{
    xResourceMutex = xSemaphoreCreateMutex();

    if (xResourceMutex == NULL)
    {
        for (;;);
    }

    xTaskCreate(TaskA,
                "TaskA",
                256,
                NULL,
                2,
                NULL);

    xTaskCreate(TaskB,
                "TaskB",
                256,
                NULL,
                2,
                NULL);

    vTaskStartScheduler();

    for (;;);
}

Program Explanation

  • A mutex is created before the scheduler starts.
  • Two tasks are created.
  • Both tasks need access to sharedCounter.
  • Each task takes the mutex before modifying the variable.
  • Each task releases the mutex after the modification.
  • The protected increment operations cannot overlap.

Expected Result

Both tasks can update the shared counter without concurrent execution of the protected increment operation.

The exact counter value at any observation time depends on task scheduling and execution timing.

The example uses a shared integer to demonstrate mutual exclusion. In a production system, the protected region should be kept short, and all accesses that require the same protection must follow the same synchronization policy.

9. Priority Inheritance in Mutexes

Priority inheritance is a mechanism that helps reduce priority inversion when a high-priority task is blocked waiting for a mutex owned by a lower-priority task.

Example Tasks

Task Priority Role
Task H High Needs the mutex
Task M Medium Unrelated processing
Task L Low Currently owns the mutex

Without Priority Inheritance

  1. Task L takes the mutex.
  2. Task H becomes Ready and attempts to take the mutex.
  3. Task H blocks because Task L owns the mutex.
  4. Task M becomes Ready and preempts Task L.
  5. Task L cannot finish its protected operation promptly.
  6. Task H remains blocked for longer than necessary.

With Priority Inheritance

  1. Task L takes the mutex.
  2. Task H attempts to take the mutex and blocks.
  3. The mutex owner, Task L, temporarily inherits the higher priority of Task H.
  4. Task L can execute ahead of Task M.
  5. Task L completes its protected operation and gives the mutex.
  6. Task H can then obtain the mutex.
  7. Task L's priority is adjusted according to the remaining inheritance conditions.
Standard FreeRTOS mutexes support a simplified priority inheritance mechanism. It reduces certain priority-inversion delays, but it does not eliminate all blocking or guarantee that every real-time deadline will be met.

11. Mutex Programming Best Practices

  • Keep the protected critical section as short as practical.
  • Always release a mutex after completing the protected operation.
  • Use a consistent lock-acquisition order when multiple mutexes are required.
  • Avoid long delays while holding a mutex.
  • Avoid blocking I/O while holding a mutex unless the design explicitly requires it.
  • Do not take or give a mutex from an ISR.
  • Do not use a mutex to transfer data between tasks.
  • Use queues or task notifications for event and data communication.
  • Consider a dedicated driver task when multiple tasks need complex access to one peripheral.
  • Check mutex creation and acquisition results.

12. Common Programming Errors

  1. Forgetting to release: Other tasks may remain blocked indefinitely.
  2. Incorrect ownership: A task must not release a mutex owned by another task.
  3. Using a mutex in an ISR: Mutex operations are task-context operations.
  4. Holding a mutex too long: This increases blocking time for other tasks.
  5. Deleting an active mutex: Tasks may access an invalid synchronization object.
  6. Assuming priority inheritance solves everything: Deadlocks and excessive blocking can still occur.
  7. Using a mutex for event signaling: Use a binary semaphore, counting semaphore, queue, or task notification as appropriate.
  8. Protecting only some accesses: Every task that accesses the same protected data must follow the synchronization design.

13. Practical Experiment

Objective

To understand how a mutex prevents simultaneous access to a shared resource by two FreeRTOS tasks.

Experiment Setup

  1. Create a shared variable.
  2. Create one mutex before starting the scheduler.
  3. Create two tasks that access the shared variable.
  4. Make each task take the mutex before modifying the variable.
  5. Release the mutex after completing the modification.
  6. Observe task execution and the shared variable.

Expected Result

  • Only one task owns the mutex at a time.
  • A task attempting to take an owned mutex waits.
  • The owning task releases the mutex after its operation.
  • A waiting task can then obtain ownership.
  • The protected operations execute without overlapping.

Do not assume that Cortex-M interrupt-priority configuration or a generic FreeRTOS port applies to this target.

15. Lesson Summary

  • A mutex provides mutual exclusion for shared resources.
  • A task that takes a mutex becomes its owner.
  • xSemaphoreCreateMutex() creates a mutex.
  • xSemaphoreTake() obtains mutex ownership.
  • xSemaphoreGive() releases the mutex.
  • vSemaphoreDelete() deletes a mutex object.
  • Standard FreeRTOS mutexes support priority inheritance.
  • Mutexes cannot be used from an ISR.
  • Mutexes are used for resource protection, not data transfer.
  • Correct locking and unlocking are essential for reliable multitasking applications.
