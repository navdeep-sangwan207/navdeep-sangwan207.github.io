Chapter 16: FreeRTOS Semaphores and Mutexes

Lesson 04 – Recursive Mutexes

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

A recursive mutex is a special type of mutex that allows the same task to take the same mutex multiple times without blocking itself.

The task must release the recursive mutex the same number of times it successfully acquired it. The mutex becomes available to other tasks only after the recursive acquisition count returns to zero.

Learning Objectives

  • Understand recursive mutexes.
  • Differentiate normal and recursive mutexes.
  • Learn recursive mutex creation APIs.
  • Understand recursive take and give operations.
  • Understand recursive acquisition counting.
  • Apply recursive mutexes to nested function calls.
  • Identify common programming errors.

1. What Is a Recursive Mutex?

A recursive mutex is a mutex that permits its current owner to acquire it repeatedly.

In a normal mutex, a task that already owns the mutex must not attempt to take it again. Doing so can cause the task to block waiting for itself.

A recursive mutex supports this situation by maintaining a recursion count for its owner.

Example

Task A takes recursive mutex
Task A takes the same recursive mutex again
Task A takes it a third time

Task A gives it once
Task A gives it a second time
Task A gives it a third time

Mutex becomes available
A recursive mutex does not allow different tasks to own the mutex simultaneously. Only the current owner can recursively acquire it.

2. Why Are Recursive Mutexes Required?

Recursive mutexes can be useful when a function that protects a resource calls another function that also attempts to protect the same resource.

Nested Function Example

Function A()
{
    Take Mutex

    Function B()

    Give Mutex
}

Function B()
{
    Take Mutex

    /* Access shared resource */

    Give Mutex
}

If both functions use the same normal mutex, Function B attempts to take a mutex already owned by the calling task. This can cause self-deadlock.

With a recursive mutex, the same task can acquire the mutex again. Each successful acquisition must still have a corresponding release.

3. Normal Mutex vs Recursive Mutex

Feature Normal Mutex Recursive Mutex
Multiple takes by owner Not supported Supported
Ownership Yes Yes
Acquisition count No recursive count Maintains recursion count
Release requirement Release once after taking Release once for every successful recursive take
Priority inheritance Supported by standard FreeRTOS mutexes Supported by standard FreeRTOS recursive mutexes
Typical use Ordinary shared-resource protection Nested calls using the same protected resource

4. Creating a Recursive Mutex

FreeRTOS provides xSemaphoreCreateRecursiveMutex() to create a recursive mutex. 

SemaphoreHandle_t xSemaphoreCreateRecursiveMutex(void);

Return Value

  • Returns a valid mutex handle if creation succeeds.
  • Returns NULL if creation fails, for example, because memory allocation fails.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xRecursiveMutex;

int main(void)
{
    xRecursiveMutex = xSemaphoreCreateRecursiveMutex();

    if (xRecursiveMutex == NULL)
    {
        /* Creation failed */
        for (;;);
    }

    /* Create application tasks here. */

    vTaskStartScheduler();

    for (;;);
}
This is a dynamic-allocation API. The selected FreeRTOS configuration must support dynamic allocation and have sufficient heap memory.

5. Taking a Recursive Mutex

A task uses xSemaphoreTakeRecursive() to acquire a recursive mutex. 

BaseType_t xSemaphoreTakeRecursive(
    SemaphoreHandle_t xMutex,
    TickType_t xTicksToWait
);

Operation

  • If the mutex is available, the task becomes its owner.
  • If the calling task already owns the mutex, the recursive acquisition count increases.
  • If another task owns the mutex, the calling task waits according to the specified timeout.
  • On success, the function returns pdTRUE.
  • On timeout or failure, it returns pdFALSE.

Example

if (xSemaphoreTakeRecursive(
        xRecursiveMutex,
        portMAX_DELAY) == pdTRUE)
{
    /* Recursive mutex acquired. */

    /* Perform protected operation. */
}

6. Giving a Recursive Mutex

A task releases a recursive mutex using xSemaphoreGiveRecursive(). 

BaseType_t xSemaphoreGiveRecursive(
    SemaphoreHandle_t xMutex
);

Operation

  • The owning task calls the give function.
  • The recursion count decreases by one.
  • If the count remains above zero, the task still owns the mutex.
  • When the count reaches zero, the mutex is released.
  • A waiting task can then obtain ownership.
Every successful call to xSemaphoreTakeRecursive() must have a matching call to xSemaphoreGiveRecursive(). Otherwise, the mutex may remain unavailable to other tasks.

7. Understanding the Recursion Count

Consider a recursive mutex with the following sequence.

Operation Recursion Count Ownership
Initial state 0 Available
Task A takes mutex 1 Task A
Task A takes again 2 Task A
Task A takes again 3 Task A
Task A gives once 2 Task A
Task A gives again 1 Task A
Task A gives third time 0 Available

The mutex is not released to another task until all recursive acquisitions have been matched by releases.

8. Practical Example: Nested Function Calls

Objective

To use a recursive mutex when one protected function calls another function that also accesses the same resource.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xRecursiveMutex;

void FunctionB(void)
{
    if (xSemaphoreTakeRecursive(
            xRecursiveMutex,
            portMAX_DELAY) == pdTRUE)
    {
        /* Protected operation in Function B */

        xSemaphoreGiveRecursive(xRecursiveMutex);
    }
}

void FunctionA(void)
{
    if (xSemaphoreTakeRecursive(
            xRecursiveMutex,
            portMAX_DELAY) == pdTRUE)
    {
        /* First protected operation */

        FunctionB();

        /* Continue protected operation */

        xSemaphoreGiveRecursive(xRecursiveMutex);
    }
}

void ApplicationTask(void *pvParameters)
{
    for (;;)
    {
        FunctionA();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    xRecursiveMutex = xSemaphoreCreateRecursiveMutex();

    if (xRecursiveMutex == NULL)
    {
        for (;;);
    }

    xTaskCreate(ApplicationTask,
                "Application",
                256,
                NULL,
                2,
                NULL);

    vTaskStartScheduler();

    for (;;);
}

Program Explanation

  1. The application creates a recursive mutex.
  2. ApplicationTask calls FunctionA.
  3. FunctionA takes the recursive mutex.
  4. FunctionA calls FunctionB.
  5. FunctionB takes the same mutex again.
  6. FunctionB completes its operation and gives the mutex.
  7. FunctionA continues and gives the mutex.
  8. The recursion count returns to zero.

Expected Result

FunctionA and FunctionB can use the same recursive mutex in nested calls without the task blocking itself. The mutex becomes available after both give operations have completed successfully.

9. Recursive Mutexes and Priority Inheritance

Standard FreeRTOS recursive mutexes support priority inheritance, similarly to normal FreeRTOS mutexes.

If a high-priority task blocks while waiting for a recursive mutex owned by a lower-priority task, the owner may temporarily inherit the higher priority.

Important Considerations

  • Priority inheritance helps reduce certain priority-inversion delays.
  • It does not remove the need for correct locking.
  • It does not prevent deadlocks caused by incorrect lock ordering.
  • Recursive acquisition does not allow another task to share ownership of the same mutex.

10. Recursive Mutex vs Normal Mutex

Aspect Normal Mutex Recursive Mutex
Creation API xSemaphoreCreateMutex() xSemaphoreCreateRecursiveMutex()
Take API xSemaphoreTake() xSemaphoreTakeRecursive()
Give API xSemaphoreGive() xSemaphoreGiveRecursive()
Same-task repeated acquisition Not supported Supported
Matching releases One for each successful take One for every successful recursive take
Priority inheritance Supported Supported

11. When Should Recursive Mutexes Be Used?

Suitable Situations

  • Nested functions access the same protected resource.
  • A legacy function hierarchy uses the same locking mechanism at multiple levels.
  • A shared library has nested calls that require the same task to retain resource ownership.

When to Avoid Them

  • Ordinary resource protection needs only one acquisition.
  • Nested locking can be removed through a clearer function design.
  • A dedicated owner task and message queue provide a simpler architecture.
  • Developers cannot reliably match every recursive take with a give.
Recursive mutexes are useful for specific nested-locking designs. They should not be used automatically for every shared resource.

12. Common Programming Errors

  1. Using normal take/give APIs: Use xSemaphoreTakeRecursive() and xSemaphoreGiveRecursive() for a recursive mutex.
  2. Unbalanced acquisition: Every successful recursive take needs one recursive give.
  3. Wrong owner: Only the owning task should release the recursive mutex.
  4. Using it in an ISR: Recursive mutexes are task-context objects and cannot be used from ISRs.
  5. Ignoring timeout: Check whether the recursive take actually succeeded.
  6. Excessive nesting: Deep recursive locking makes resource ownership difficult to maintain.
  7. Assuming it prevents all deadlocks: Recursive mutexes do not solve deadlocks involving multiple mutexes or incorrect resource ordering.

13. Practical Experiment

Objective

To observe repeated acquisition and release of a recursive mutex by the same task.

Experiment Setup

  1. Create one recursive mutex.
  2. Create an application task.
  3. In the task, take the mutex.
  4. Call a second function that takes the same mutex.
  5. Release the mutex in the second function.
  6. Return to the first function and release its acquisition.
  7. Verify that the mutex becomes available only after both releases.

Expected Result

  • The first take gives the task ownership.
  • The nested take increases the recursive acquisition count.
  • The nested give decreases the count.
  • The final give releases the mutex.
  • The task does not block itself during the nested acquisition.
LPC2129 / Keil uVision note: This experiment requires a compatible FreeRTOS ARM7 port and correct Keil integration. LPC2129 uses ARM7TDMI-S, not Cortex-M. Do not assume a Cortex-M port or interrupt-priority configuration is suitable for this processor.

15. Lesson Summary

  • A recursive mutex permits repeated acquisition by its owner.
  • Only one task owns the mutex at a time.
  • xSemaphoreCreateRecursiveMutex() creates it.
  • xSemaphoreTakeRecursive() acquires it.
  • xSemaphoreGiveRecursive() releases it.
  • Every successful take must have a matching give.
  • The mutex is released when the recursive count reaches zero.
  • Recursive mutexes support priority inheritance in standard FreeRTOS implementations.
  • They are useful for nested function calls that access the same protected resource.
  • They cannot be used from an ISR.
