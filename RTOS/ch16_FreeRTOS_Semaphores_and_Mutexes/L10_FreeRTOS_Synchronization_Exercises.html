Lesson Overview

This lesson provides programming exercises, API questions, scheduling scenarios, debugging problems, and interview preparation covering FreeRTOS semaphores and mutexes.

The exercises reinforce the use of binary semaphores, counting semaphores, mutexes, priority inheritance, ISR communication, and resource synchronization.

Learning Objectives

  • Select the correct synchronization object for a problem.
  • Write programs using FreeRTOS semaphore and mutex APIs.
  • Analyze task blocking and unblocking.
  • Understand priority inversion and priority inheritance.
  • Identify synchronization errors and deadlocks.
  • Analyze producer-consumer systems.
  • Apply ISR-safe synchronization APIs.
  • Prepare for RTOS programming interviews.

2. Conceptual Exercises

Exercise 1 – Select the Correct Object

A task must notify another task whenever a button interrupt occurs. Which synchronization object is appropriate?

Answer: A binary semaphore can be used for simple event notification. The ISR uses xSemaphoreGiveFromISR(), and the receiving task uses xSemaphoreTake().

Exercise 2 – Protect a Shared UART

Two tasks transmit messages through the same UART. Their output must not interleave. Which object should be used?

Answer: A mutex, because the UART is a shared resource requiring exclusive task ownership.

Exercise 3 – Manage Five Resources

An application has five identical resources. A maximum of five tasks may use them simultaneously. Which object can represent the available resource count?

Answer: A counting semaphore with maximum count 5 and initial count 5, combined with a resource allocation mechanism that identifies the actual resource assigned to each task.

Exercise 4 – Transfer Sensor Data

An ADC interrupt produces sensor readings that must be processed by a task. Which mechanism is more suitable for transferring each reading?

Answer: A queue using an ISR-safe send operation such as xQueueSendFromISR(). A semaphore alone does not transfer the reading.

Exercise 5 – Recursive Function Calls

A task calls Function A, which takes a mutex. Function A then calls Function B, which also needs to take the same mutex. What synchronization object may be suitable?

Answer: A recursive mutex, using xSemaphoreTakeRecursive() and xSemaphoreGiveRecursive() with matching take and give operations.

3. Programming Exercise 1 – Binary Semaphore

Problem Statement

Create two tasks:

  • Producer Task gives a binary semaphore every second.
  • Consumer Task waits for the semaphore and processes the notification.

Required APIs: xSemaphoreCreateBinary(), xSemaphoreGive(), xSemaphoreTake().

Expected Result: The consumer blocks while no token is available and processes a notification after a successful give.

4. Programming Exercise 2 – Counting Semaphore

Problem Statement

Create a counting semaphore with a maximum count of four and an initial count of four. Create five tasks that request a resource token.

Required APIs: xSemaphoreCreateCounting(), xSemaphoreTake(), xSemaphoreGive().

Expected Result: No more than four tasks can hold tokens simultaneously. The fifth task waits until a token becomes available.

5. Programming Exercise 3 – Mutex Protection

Problem Statement

Create two tasks that access a shared counter. Protect the counter using a mutex.

Required APIs: xSemaphoreCreateMutex(), xSemaphoreTake(), xSemaphoreGive().

Expected Result: Only one task at a time enters the protected section.

6. Programming Exercise 4 – ISR Notification

Problem Statement

Design an interrupt handler that gives a binary semaphore to a processing task.

Required APIs: xSemaphoreGiveFromISR(), xSemaphoreTake().

Expected Result: The ISR notifies the task without blocking. The task performs the longer processing operation.

7. Programming Exercise 5 – Producer-Consumer Buffer

Problem Statement

Implement a circular buffer with five slots using two counting semaphores and one mutex.

  • empty starts at 5.
  • full starts at 0.
  • mutex protects buffer data and indexes.

Expected Result: The producer waits when the buffer is full, and the consumer waits when it is empty.

8. Scheduling and Synchronization Problems

Problem 1 – Priority Inversion

Three tasks have the following priorities:

TaskPriority
Task H3
Task M2
Task L1

Task L owns a mutex. Task H requests the same mutex and becomes Blocked. Task M becomes Ready.

Question: Explain how Task M can delay Task H.

Answer: Task H is blocked because Task L owns the mutex. Task M has a higher priority than Task L and can preempt it. This delays Task L from releasing the mutex and indirectly delays Task H.

Problem 2 – Priority Inheritance

Using the previous task priorities, explain what happens when Task L inherits Task H's priority.

Answer: Task L temporarily executes at effective priority 3. Task M at priority 2 cannot preempt Task L while it is Ready at that inherited priority. Task L can complete its critical section and release the mutex, allowing Task H to proceed.

Problem 3 – Binary Semaphore Overflow

A binary semaphore is already full. An ISR gives it again.

Question: What happens?

Answer: The give operation fails because a binary semaphore can hold only one token. The additional event is not accumulated.

Problem 4 – Counting Semaphore

A counting semaphore has a maximum count of 5 and current count of 2. Three successful give operations occur.

Answer: The count changes from 2 to 3, then 4, then 5. A further give would fail while the semaphore remains full.

Problem 5 – Mutex Ownership

Task A takes a mutex. Task B tries to give the same mutex.

Answer: This is invalid mutex ownership behavior. The task that owns a mutex must release it.

9. Debugging Exercises

Debugging Exercise 1

Incorrect code:

if (xSemaphoreTake(xMutex, portMAX_DELAY))
{
    SharedData++;
}

/* Mutex is never released */

Problem: The task does not give the mutex after taking it. Other tasks may remain blocked.

Correction:

if (xSemaphoreTake(xMutex, portMAX_DELAY) == pdTRUE)
{
    SharedData++;

    xSemaphoreGive(xMutex);
}

Debugging Exercise 2

Incorrect code:

void UART_IRQHandler(void)
{
    xSemaphoreTake(xMutex, portMAX_DELAY);
}

Problem: A blocking task-context API is being called from an ISR. A mutex must not be used from an ISR.

Correction: Use an ISR-safe notification mechanism, such as xSemaphoreGiveFromISR() for an applicable semaphore, and defer processing to a task.

Debugging Exercise 3

Incorrect code:

xSemaphoreCreateBinary();

xSemaphoreTake(xSemaphore, portMAX_DELAY);

Problem: The created semaphore handle is not assigned to xSemaphore. The variable may be invalid or uninitialized.

Correction:

SemaphoreHandle_t xSemaphore;

xSemaphore = xSemaphoreCreateBinary();

if (xSemaphore == NULL)
{
    /* Handle creation failure */
}

Debugging Exercise 4

Incorrect code:

if (xSemaphoreTake(xSemaphore, 0) == pdTRUE)
{
    ProcessData();
}
else
{
    ProcessData();
}

Problem: The program processes data even when it has not obtained the semaphore token.

Correction: Process the operation that requires the token only after a successful take, or handle the unavailable case separately.

Debugging Exercise 5

Incorrect code:

if (xSemaphoreTake(xMutex, portMAX_DELAY) == pdTRUE)
{
    vTaskDelay(pdMS_TO_TICKS(500));
    xSemaphoreGive(xMutex);
}

Problem: The task holds the mutex during a long delay, increasing the blocking time of other tasks.

Correction: Move the delay outside the protected section when the application logic permits it.

  1. Binary semaphore

  2. xSemaphoreGiveFromISR()

Answer: B – 1.

Q4. Which object is most appropriate for transferring structured data between tasks?

  1. Mutex

  2. It enters the Blocked state

11. Interview Questions and Answers

Q1. What is a semaphore?

A semaphore is a synchronization object used to coordinate tasks, signal events, or count available tokens.

Q2. What is a mutex?

A mutex is a mutual-exclusion synchronization object that provides ownership-based access to a shared resource.

Q3. What is the difference between a mutex and a binary semaphore?

A mutex has ownership and supports priority inheritance in FreeRTOS. A binary semaphore does not have mutex ownership and is suitable for event signaling.

Q4. What is priority inversion?

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task holding a required resource, potentially with medium-priority tasks extending the delay.

Q5. What is priority inheritance?

It is a protocol in which a mutex owner temporarily inherits a higher priority when a higher-priority task blocks on that mutex.

Q6. Can a mutex be used inside an ISR?

No. Mutex APIs are intended for task context and must not be used from an ISR.

Q7. Why are ISR-specific APIs required?

An ISR cannot block. ISR-specific APIs perform permitted non-blocking kernel operations and follow the selected port's interrupt rules.

Q8. What is a counting semaphore?

A counting semaphore maintains a count between zero and a configured maximum. It can represent available tokens or pending event counts.

Q9. What is a recursive mutex?

A recursive mutex allows its owning task to take the same mutex multiple times, provided each successful recursive take is matched by a recursive give.

Q10. What is a race condition?

A race condition occurs when the result of concurrent operations depends on their timing or interleaving.

Q11. What is a deadlock?

A deadlock occurs when tasks are permanently unable to proceed because each is waiting for a resource or condition that cannot become available.

Q12. How can deadlock be reduced?

Use a consistent resource acquisition order, avoid unnecessary nested locks, keep protected sections short, and design explicit timeout or recovery policies where appropriate.

Q13. Why is a queue sometimes better than a semaphore?

A queue transfers actual data items. A semaphore communicates availability or an event but does not carry the associated payload.

Q14. What is the purpose of portMAX_DELAY?

It requests the longest supported wait. Whether it represents an indefinite wait depends on the FreeRTOS configuration.

Q15. Does priority inheritance guarantee deadline satisfaction?

No. It reduces certain forms of priority inversion but does not remove all blocking or replace schedulability analysis.

15. Chapter Summary

Semaphores and mutexes are essential RTOS synchronization mechanisms. Binary semaphores provide event signaling, counting semaphores manage token counts, and mutexes protect shared resources through ownership. FreeRTOS also provides ISR-specific communication APIs and basic mutex priority inheritance.

Correct synchronization requires more than selecting an API. Developers must also consider task priorities, blocking times, resource ownership, interrupt restrictions, buffer lifetime, and failure recovery.
