Semaphore Take and Give Operations

Chapter 09 – Semaphores and Synchronization | Lesson 06

1. Introduction

Semaphore take and give operations are fundamental synchronization mechanisms in an RTOS. They allow tasks to coordinate execution, signal events, and manage access to shared resources.

  • Take: Attempts to obtain a semaphore token.
  • Give: Makes a semaphore token available.
Key idea: A successful take consumes one available token. A successful give adds one token, subject to the semaphore's maximum count.

2. Semaphore Take Operation

In FreeRTOS, a task uses xSemaphoreTake() to obtain a semaphore.

Function syntax

BaseType_t xSemaphoreTake(
    SemaphoreHandle_t xSemaphore,
    TickType_t xTicksToWait
);

Parameters

ParameterDescription
xSemaphoreHandle of the semaphore to take.
xTicksToWaitMaximum time to wait, expressed in RTOS ticks.

Return values

Return valueMeaning
pdTRUEThe semaphore was successfully obtained.
pdFALSEThe semaphore was not obtained within the permitted wait time.

3. Semaphore Give Operation

The xSemaphoreGive() function makes a semaphore token available.

Function syntax

BaseType_t xSemaphoreGive(
    SemaphoreHandle_t xSemaphore
);

Return values

Return valueMeaning
pdTRUEThe semaphore give operation succeeded.
pdFALSEThe operation failed, such as when a binary semaphore is already available or a counting semaphore is at its maximum count.

4. How Take and Give Work Together

Consider a task waiting for an event and another task generating that event.

       +-------------------------+
       |       Task A            |
       |                         |
       | xSemaphoreTake()        |
       | Wait for event          |
       +-------------------------+
                    ^
                    |
                    |
       +-------------------------+
       |     Semaphore           |
       +-------------------------+
                    ^
                    |
                    |
       +-------------------------+
       |       Task B            |
       |                         |
       | xSemaphoreGive()        |
       | Signal event            |
       +-------------------------+

Execution sequence

  1. Task A calls xSemaphoreTake().
  2. If the semaphore is empty, Task A may enter the Blocked state.
  3. Task B calls xSemaphoreGive().
  4. A waiting task may become Ready.
  5. The scheduler selects a Ready task according to the scheduling policy.
  6. Task A resumes after the successful take operation.

5. Blocking Time in Semaphore Take

The second parameter of xSemaphoreTake() determines how long the task can wait for the semaphore.

ValueBehavior
0Do not wait. Return immediately if no token is available.
Finite tick valueWait up to the specified number of ticks.
portMAX_DELAYRequest an indefinite wait where supported by the configuration.

Example 1: Non-blocking take

if (xSemaphoreTake(
        xSemaphore,
        0) == pdTRUE)
{
    ProcessEvent();
}
else
{
    /* Semaphore unavailable */
}

Example 2: Finite timeout

if (xSemaphoreTake(
        xSemaphore,
        pdMS_TO_TICKS(100)) == pdTRUE)
{
    ProcessEvent();
}
else
{
    HandleTimeout();
}

Example 3: Indefinite wait

if (xSemaphoreTake(
        xSemaphore,
        portMAX_DELAY) == pdTRUE)
{
    ProcessEvent();
}
The conversion macro pdMS_TO_TICKS() converts milliseconds to ticks. The actual resolution depends on the configured tick rate. An indefinite wait using portMAX_DELAY depends on the relevant FreeRTOS configuration, including suspension support.

6. Semaphore Count Changes

For a counting semaphore, the take and give operations change the count.

Successful Take: Count = Count − 1
Successful Give: Count = Count + 1

Worked example

Assume the maximum count is four and the initial count is three.

OperationCount
Initial state3
Task A takes one token2
Task B takes one token1
Task C gives one token2
Task D takes one token1
Task A gives one token2

The count always remains between zero and the configured maximum.

8. Take and Give with a Mutex

A mutex is a special synchronization object used for mutual exclusion. A task takes the mutex before accessing a shared resource and gives it back after completing the operation.

Example

SemaphoreHandle_t xMutex;

void SharedResourceTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xMutex,
                portMAX_DELAY) == pdTRUE)
        {
            /* Access shared resource */
            UpdateSharedData();

            xSemaphoreGive(xMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

The task that takes a mutex must release it. FreeRTOS mutexes provide priority inheritance in supported configurations.

Do not use mutexes from ISRs. An ISR cannot block waiting for mutex ownership, and mutex ownership semantics require task context.

9. ISR-Specific Give Operation

When an interrupt occurs, the ISR may need to notify a task. FreeRTOS provides xSemaphoreGiveFromISR() for this purpose.

Syntax

BaseType_t xSemaphoreGiveFromISR(
    SemaphoreHandle_t xSemaphore,
    BaseType_t *pxHigherPriorityTaskWoken
);

Parameters

ParameterDescription
xSemaphoreSemaphore handle.
pxHigherPriorityTaskWokenPointer used to indicate whether a higher-priority task was unblocked.

Example

void TIMER_ISR(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge timer interrupt */

    if (xSemaphoreGiveFromISR(
            xSemaphore,
            &xHigherPriorityTaskWoken) == pdTRUE)
    {
        /* Semaphore successfully given */
    }

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

The ISR-safe API does not wait for a task to consume the semaphore. It records the notification and allows the scheduler to run an eligible task when appropriate.

The exact yield macro and ISR behavior depend on the selected FreeRTOS port. Always consult the port-specific documentation.

10. Timeout Handling

A timeout occurs when a task waits for a semaphore but does not obtain it within the specified wait period.

Example

void CommunicationTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xSemaphore,
                pdMS_TO_TICKS(500)) == pdTRUE)
        {
            ProcessReceivedData();
        }
        else
        {
            /* Timeout occurred */
            HandleCommunicationTimeout();
        }
    }
}

Timeout handling is useful in communication systems, sensor monitoring, and resource management.

11. Common Errors in Take and Give Operations

  • Using an invalid or uninitialized semaphore handle.
  • Ignoring the return value of xSemaphoreTake().
  • Giving a semaphore without a corresponding application event or resource release.
  • Taking a semaphore without eventually restoring a required resource token.
  • Using a blocking take operation inside an ISR.
  • Calling normal task-context give APIs from an ISR.
  • Using a mutex from interrupt context.
  • Waiting indefinitely when the application needs timeout recovery.
  • Assuming a binary semaphore counts every event.
  • Failing to handle a give operation when the semaphore is already full.

12. Best Practices

  1. Check the semaphore creation result.
  2. Check take and give return values.
  3. Select an appropriate timeout.
  4. Use ISR-specific APIs from interrupt context.
  5. Keep ISR code short.
  6. Use a mutex for task-level shared resource protection.
  7. Use a binary semaphore for simple event notification.
  8. Use a counting semaphore when multiple tokens must be tracked.
  9. Use queues when event data must be transferred.
  10. Ensure every acquired resource is released correctly.

13. Practical Activity – Semaphore Timeout

Create a task that waits for a semaphore for 200 milliseconds.

Activity requirements

  1. Create a binary semaphore.
  2. Create a task that calls xSemaphoreTake().
  3. Set the timeout to pdMS_TO_TICKS(200).
  4. If the take succeeds, process the event.
  5. If the take fails, execute timeout handling.
  6. Create another task that gives the semaphore after a configurable delay.
  7. Experiment with delays shorter and longer than the timeout.

Expected observations

Event timingExpected behavior
Semaphore given before timeoutWaiting task can obtain it.
Semaphore not given before timeoutTake returns failure.
Semaphore given after timeoutToken may remain available for a later take.
The exact observed scheduling time can differ from the requested timeout because RTOS delays and timeouts use tick resolution and scheduler timing.

15. Lesson Summary

  • xSemaphoreTake() obtains a semaphore token and can block a task.
  • xSemaphoreGive() makes a token available without blocking for capacity.
  • Take and give operations change the semaphore count when successful.
  • Timeouts allow tasks to recover when a semaphore is unavailable.
  • xSemaphoreGiveFromISR() is the ISR-safe give operation.
  • Mutexes provide task ownership and priority inheritance; binary and counting semaphores serve different synchronization purposes.
  • Always check return values and follow the selected processor port's ISR rules.
