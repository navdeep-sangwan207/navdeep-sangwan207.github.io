1. Introduction

A race condition is a software defect that occurs when the result of an operation depends on the unpredictable timing or ordering of concurrent operations.

Race conditions commonly occur when multiple tasks, threads, or interrupt handlers access shared data or resources without suitable synchronization.

Example: Two RTOS tasks increment the same shared counter. If both read the old value before either writes the updated value, one increment may be lost.

2. What Is Shared Data?

Shared data is information that can be accessed by more than one execution context.

Examples

  • Global variables.
  • Shared structures.
  • Common arrays and buffers.
  • Peripheral control registers.
  • Communication state variables.
  • Shared resource counters.
int sharedCounter = 0;

void TaskA(void)
{
    sharedCounter++;
}

void TaskB(void)
{
    sharedCounter++;
}

If these functions execute concurrently without protection, the increment operations can interfere with one another.

3. How Does a Race Condition Occur?

Consider the statement:

sharedCounter = sharedCounter + 1;

This statement is a read-modify-write operation. Conceptually, it consists of three steps:

  1. Read the current counter value.
  2. Add one to the value.
  3. Write the updated value back.

These steps are not necessarily one indivisible operation.

Example: Initial counter = 10

Execution StepTask ATask BCounter
1Reads 10—10
2—Reads 1010
3Calculates 11—10
4—Calculates 1110
5Writes 11—11
6—Writes 1111
Expected result: 12, because two increments should occur. Actual result: 11, because one update overwrites the other.

4. Race Condition vs Data Race

These terms are related but are not identical.

TermMeaning
Race conditionProgram correctness depends on the timing or ordering of operations.
Data raceIn C/C++, conflicting accesses to the same memory location occur concurrently, at least one access is a write, and the accesses are not properly synchronized or atomic.

A data race in a multithreaded C or C++ program results in undefined behavior under the language memory model. Race conditions can also occur at a higher logical level even when individual memory accesses are protected.

5. Types of Race Conditions

5.1 Read-Write Race

One task reads shared data while another task modifies it. The reader may obtain an inconsistent or outdated value.

5.2 Write-Write Race

Two tasks attempt to update the same shared location. One update may overwrite the other.

5.3 Check-Then-Act Race

A task checks a condition and then performs an operation, but another task changes the condition between those two steps.

5.4 Buffer Race

A producer modifies a buffer while a consumer is reading the same data.

5.5 Peripheral Access Race

Two tasks configure or use the same peripheral without coordinated access.

6. Race Condition in a Producer-Consumer System

Consider a shared buffer used by a producer task and a consumer task.

       +-------------------+
       |   Producer Task   |
       |                   |
       | Writes New Data   |
       +-------------------+
                 |
                 v
       +-------------------+
       |   Shared Buffer   |
       +-------------------+
                 ^
                 |
       +-------------------+
       |   Consumer Task   |
       |                   |
       | Reads Data        |
       +-------------------+

If the producer overwrites a buffer location while the consumer is reading it, the consumer may receive corrupted or inconsistent information.

Possible consequences

  • Incorrect sensor measurements.
  • Lost data samples.
  • Corrupted messages.
  • Incorrect calculations.
  • Unexpected application behavior.

7. Race Condition in Embedded Systems

Example 1: Sensor data

A sensor task updates a temperature variable while a monitoring task reads it. The monitoring task may read an outdated value or a combination of fields from different measurement cycles.

Example 2: UART communication

Two tasks transmit messages through the same UART peripheral. Their characters may become interleaved if transmission is not coordinated.

Example 3: Shared GPIO register

Two execution contexts perform read-modify-write operations on different bits of the same GPIO register. One update may unintentionally overwrite the other.

Example 4: Interrupt and task interaction

An ISR updates a shared event counter while a task reads and resets it. Without an appropriate atomic or synchronization design, events may be lost.

8. Preventing Race Conditions Using a Mutex

A mutex provides mutual exclusion. Only the task that owns the mutex can enter the protected section.

FreeRTOS example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xCounterMutex;
int sharedCounter = 0;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xCounterMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            xSemaphoreGive(xCounterMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xCounterMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            xSemaphoreGive(xCounterMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

int main(void)
{
    xCounterMutex = xSemaphoreCreateMutex();

    if (xCounterMutex == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(TaskA, "TaskA", 256, NULL, 2, NULL);
    xTaskCreate(TaskB, "TaskB", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Explanation:

  1. The mutex is created before the scheduler starts.
  2. Task A and Task B request the same mutex.
  3. Only the mutex owner accesses the counter.
  4. The owner releases the mutex after the update.
  5. The other task can then acquire the mutex.
A FreeRTOS mutex provides priority inheritance in supported configurations. A binary semaphore does not provide the same mutex ownership and priority-inheritance behavior.

9. Preventing Race Conditions Using a Critical Section

A critical section can protect a short operation against specified forms of concurrent execution.

Conceptual example

Enter_Critical_Section();

sharedCounter++;

Exit_Critical_Section();

In FreeRTOS, task-context critical sections are commonly expressed using the port's critical-section macros.

taskENTER_CRITICAL();

sharedCounter++;

taskEXIT_CRITICAL();

The exact interrupt-masking behavior depends on the processor port. Critical sections should be kept very short.

10. Preventing Race Conditions Using Atomic Operations

An atomic operation performs a supported operation indivisibly with respect to other accesses governed by the same atomic mechanism.

Conceptual C++ example

#include 

std::atomic sharedCounter(0);

void TaskA()
{
    sharedCounter.fetch_add(1);
}

void TaskB()
{
    sharedCounter.fetch_add(1);
}

In a C++ environment that supports the required atomic operation, both increments are atomic.

In embedded C or C++, verify that the compiler and target support the selected atomic operation. Some operations may use library routines or locks rather than a native instruction.

11. Preventing Race Conditions Using Queues

Instead of allowing multiple tasks to modify the same variable, a task can send data through a queue.

Producer Task
      |
      | xQueueSend()
      v
   FreeRTOS Queue
      |
      | xQueueReceive()
      v
Consumer Task

Queue operations manage access to the queue's internal storage. The receiving task obtains a copy of the configured queue item.

This design can reduce the need for application-level locking around the transferred data, provided the application does not separately access the same data through an unsafe shared path.

12. The Volatile Keyword and Race Conditions

The C volatile keyword tells the compiler that accesses to the qualified object are observable side effects and should not be treated like ordinary removable or freely cached accesses.

Example

volatile int sharedCounter = 0;

void TaskA(void)
{
    sharedCounter++;
}

void TaskB(void)
{
    sharedCounter++;
}

Declaring the variable volatile does not make the increment operation atomic. It does not provide mutual exclusion or a general inter-task synchronization guarantee.

Important: Volatile is useful for certain hardware registers and asynchronously changing objects, but it is not a replacement for mutexes, atomic operations, or appropriate critical sections.

13. Race Conditions Involving Hardware Registers

Embedded applications often access memory-mapped peripheral registers.

Suppose two tasks need to control separate output pins represented by different bits of the same GPIO register.

Illustrative read-modify-write operation

IO0SET = (1U << 5);

For LPC2129, the GPIO set register provides a bit-set operation. Using a dedicated hardware set/clear register can avoid some read-modify-write conflicts that would occur with a shared read/write register.

However, peripheral access rules must always be checked in the device reference manual. Not every register supports the same operation semantics.

For LPC2129 GPIO, use the appropriate IO0SET and IO0CLR registers for bit-level set and clear operations rather than assuming every GPIO operation should use a read-modify-write of IO0PIN.

15. Debugging Race Conditions

Race conditions are often difficult to reproduce because they depend on timing.

Useful debugging techniques

  • Inspect shared variables during execution.
  • Record task execution and event timestamps.
  • Use sequence numbers to identify missing or reordered messages.
  • Monitor queue occupancy and failed send operations.
  • Check all mutex acquisition and release paths.
  • Review ISR and task access to shared variables.
  • Use stress testing with different task delays and priorities.
  • Use an appropriate trace tool when supported.
  • Reduce shared mutable state where possible.

16. Worked Numerical Example

Two tasks each increment a shared counter 100 times.

Expected Final Value = 100 + 100 = 200

Suppose unsynchronized read-modify-write operations cause 15 updates to be lost.

Actual Final Value = 200 − 15 = 185

Answer: The counter ends at 185 instead of 200. This demonstrates how concurrent updates can be lost.

The number of lost updates is illustrative; actual behavior depends on the execution interleaving and implementation.

17. Practical Activity – Race Condition Demonstration

Design two versions of a shared-counter application.

Version A: Without synchronization

  1. Declare a shared counter.
  2. Create two tasks.
  3. Increment the counter repeatedly from both tasks.
  4. Observe the final counter value.

Version B: With synchronization

  1. Create a mutex.
  2. Protect each increment operation.
  3. Run both tasks again.
  4. Compare the final counter value with the expected result.

Expected result

The protected version should preserve the increments when all accesses to the counter follow the same mutex protocol and no other unprotected writer exists.

The unprotected version may appear to work in a particular test run. That does not prove it is correct. A race condition is often timing-dependent.

19. Lesson Summary

  • A race condition occurs when correctness depends on the timing or ordering of concurrent operations.
  • Shared variables, buffers, and peripheral registers can be affected.
  • Read-modify-write operations are a common source of lost updates.
  • Mutexes, critical sections, atomic operations, and queues help prevent race conditions when used correctly.
  • Volatile does not provide mutual exclusion or atomicity.
  • ISR and task interactions require appropriate synchronization.
  • Debugging should include timing analysis, stress testing, and shared-resource inspection.
