1. Introduction

The Producer-Consumer problem is a classical synchronization problem in operating systems and real-time systems. It describes how one or more producer tasks generate data and one or more consumer tasks process that data using a shared buffer.

  • Producer: Generates data and places it into a buffer.
  • Consumer: Removes data from the buffer and processes it.
  • Buffer: Temporarily stores data between production and consumption.
Key objective: Prevent buffer overflow, prevent buffer underflow, and protect shared buffer operations from race conditions.

2. Producer-Consumer System Architecture

       +----------------------+
       |    Producer Task     |
       |                      |
       | Generate Data        |
       +----------------------+
                  |
                  | Insert Data
                  v
       +----------------------+
       |     Shared Buffer    |
       |                      |
       |   [D1] [D2] [D3]     |
       +----------------------+
                  |
                  | Remove Data
                  v
       +----------------------+
       |    Consumer Task     |
       |                      |
       | Process Data         |
       +----------------------+

The producer and consumer may execute at different rates. Synchronization is required to coordinate access to the shared buffer.

3. Why Is Synchronization Required?

3.1 Buffer Overflow

Buffer overflow occurs when the producer attempts to insert data into a full buffer.

3.2 Buffer Underflow

Buffer underflow occurs when the consumer attempts to remove data from an empty buffer.

3.3 Race Condition

A race condition can occur when producer and consumer tasks update shared buffer indexes or counters without proper synchronization.

ProblemCauseSolution
Buffer overflowProducer inserts data when no free slot remains.Track available slots.
Buffer underflowConsumer removes data when no item is available.Track occupied slots.
Race conditionConcurrent access to shared buffer state.Protect critical operations.

4. Semaphores Used in Producer-Consumer Synchronization

The classical bounded-buffer solution uses three synchronization objects:

Synchronization objectInitial valuePurpose
MutexAvailableProtects shared buffer operations.
Empty semaphoreBuffer capacity NCounts available buffer slots.
Full semaphore0Counts occupied buffer slots.

Semaphore operations

  • Producer takes empty before inserting data.
  • Producer takes the mutex before accessing shared buffer state.
  • Producer gives full after inserting data.
  • Consumer takes full before removing data.
  • Consumer takes the mutex before accessing shared buffer state.
  • Consumer gives empty after removing data.
The empty and full semaphores count buffer slots. The mutex protects the actual shared buffer and its indexes.

5. Classical Producer-Consumer Algorithm

Producer algorithm

while (true)
{
    item = ProduceItem();

    wait(empty);

    wait(mutex);

    InsertItem(item);

    signal(mutex);

    signal(full);
}

Consumer algorithm

while (true)
{
    wait(full);

    wait(mutex);

    item = RemoveItem();

    signal(mutex);

    signal(empty);

    ConsumeItem(item);
}

The producer cannot insert when the buffer is full. The consumer cannot remove when the buffer is empty.

6. FreeRTOS Implementation Using Semaphores

The following example demonstrates a bounded circular buffer with one producer task and one consumer task.

Shared resources

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include 

#define BUFFER_SIZE 5

static uint32_t buffer[BUFFER_SIZE];

static uint32_t writeIndex = 0;
static uint32_t readIndex = 0;

static SemaphoreHandle_t xEmptySemaphore;
static SemaphoreHandle_t xFullSemaphore;
static SemaphoreHandle_t xBufferMutex;

Producer task

void ProducerTask(void *pvParameters)
{
    uint32_t item = 0;

    for (;;)
    {
        /* Generate an item */
        item++;

        /* Wait until a buffer slot is available */
        if (xSemaphoreTake(
                xEmptySemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Protect shared buffer */
            if (xSemaphoreTake(
                    xBufferMutex,
                    portMAX_DELAY) == pdTRUE)
            {
                buffer[writeIndex] = item;

                writeIndex =
                    (writeIndex + 1) % BUFFER_SIZE;

                xSemaphoreGive(xBufferMutex);

                /* One more item is available */
                xSemaphoreGive(xFullSemaphore);
            }
            else
            {
                /* Restore reserved empty slot */
                xSemaphoreGive(xEmptySemaphore);
            }
        }

        vTaskDelay(pdMS_TO_TICKS(200));
    }
}

Consumer task

void ConsumerTask(void *pvParameters)
{
    uint32_t receivedItem;

    for (;;)
    {
        /* Wait until an item is available */
        if (xSemaphoreTake(
                xFullSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Protect shared buffer */
            if (xSemaphoreTake(
                    xBufferMutex,
                    portMAX_DELAY) == pdTRUE)
            {
                receivedItem = buffer[readIndex];

                readIndex =
                    (readIndex + 1) % BUFFER_SIZE;

                xSemaphoreGive(xBufferMutex);

                /* One more slot is available */
                xSemaphoreGive(xEmptySemaphore);

                ProcessItem(receivedItem);
            }
            else
            {
                /* Restore reserved full-item count */
                xSemaphoreGive(xFullSemaphore);
            }
        }
    }
}

Application initialization

int main(void)
{
    xEmptySemaphore =
        xSemaphoreCreateCounting(
            BUFFER_SIZE,
            BUFFER_SIZE
        );

    xFullSemaphore =
        xSemaphoreCreateCounting(
            BUFFER_SIZE,
            0
        );

    xBufferMutex = xSemaphoreCreateMutex();

    if ((xEmptySemaphore == NULL) ||
        (xFullSemaphore == NULL) ||
        (xBufferMutex == NULL))
    {
        for (;;)
        {
        }
    }

    xTaskCreate(
        ProducerTask,
        "Producer",
        256,
        NULL,
        2,
        NULL
    );

    xTaskCreate(
        ConsumerTask,
        "Consumer",
        256,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}
This is an educational single-producer, single-consumer example. Production code should define recovery for every failure path, ensure resource counts remain consistent, and consider using a FreeRTOS queue instead. The mutex and semaphore handles must be successfully created before tasks start.

7. Circular Buffer Operation

A circular buffer uses two indexes:

  • writeIndex identifies the next insertion position.
  • readIndex identifies the next removal position.

After accessing an element, each index advances using modulo arithmetic.

writeIndex = (writeIndex + 1) % BUFFER_SIZE;
readIndex  = (readIndex + 1) % BUFFER_SIZE;

For a buffer size of five, the index sequence is:

Current indexNext index
01
12
23
34
40

The empty and full semaphore counts prevent the producer and consumer from confusing a full buffer with an empty buffer.

Empty Count + Full Count = BUFFER_SIZE

9. Producer-Consumer Using a FreeRTOS Queue

FreeRTOS queues provide a simpler solution for many producer-consumer applications. A queue manages data storage and task synchronization internally.

Queue creation

QueueHandle_t xDataQueue;

xDataQueue = xQueueCreate(
    5,
    sizeof(uint32_t)
);

Producer task

void ProducerTask(void *pvParameters)
{
    uint32_t item = 0;

    for (;;)
    {
        item++;

        if (xQueueSend(
                xDataQueue,
                &item,
                portMAX_DELAY) == pdTRUE)
        {
            /* Item successfully inserted */
        }

        vTaskDelay(pdMS_TO_TICKS(200));
    }
}

Consumer task

void ConsumerTask(void *pvParameters)
{
    uint32_t item;

    for (;;)
    {
        if (xQueueReceive(
                xDataQueue,
                &item,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessItem(item);
        }
    }
}

A queue copies each item into its own storage. The producer can reuse its local variable after a successful send because the queue stores a copy of the item.

For many ordinary producer-consumer applications, a FreeRTOS queue is preferable to manually combining a circular buffer, two counting semaphores, and a mutex.

10. Semaphores vs Queues in Producer-Consumer Systems

FeatureManual buffer with semaphoresFreeRTOS queue
Data storageApplication implements buffer.Queue manages item storage.
SynchronizationApplication manages counts and mutex.Built into queue operations.
Buffer indexesApplication manages indexes.Managed by queue implementation.
Data transferApplication copies data into/out of buffer.Queue copies configured items.
FlexibilityAllows custom buffer and ownership designs.Convenient for fixed-size queued items.
ComplexityHigher; more synchronization rules.Usually lower.

11. Common Problems and Their Solutions

11.1 Buffer Overflow

Problem: Producer attempts to insert data when the buffer is full.

Solution: Wait for an empty-slot token before inserting.

11.2 Buffer Underflow

Problem: Consumer attempts to remove data from an empty buffer.

Solution: Wait for a full-slot token before removing.

11.3 Race Condition

Problem: Producer and consumer modify shared indexes or buffer state without protection.

Solution: Use a mutex or a correctly designed lock-free single-producer/single-consumer structure.

11.4 Deadlock

Problem: Tasks acquire synchronization objects in an inconsistent order or fail to release resources.

Solution: Establish a consistent acquisition order and ensure every successful acquisition has a corresponding release.

11.5 Slow Consumer

Problem: The producer generates data faster than the consumer can process it.

Solution: Increase buffer capacity where appropriate, optimize processing, apply backpressure, or define an explicit data-drop policy.

13. Best Practices

  1. Choose the buffer capacity based on expected data bursts and consumer response time.
  2. Use empty and full counts consistently in a manual bounded-buffer design.
  3. Protect shared buffer state against concurrent modification.
  4. Keep mutex ownership and release rules clear.
  5. Do not hold a mutex while waiting for an event that may depend on another task acquiring that mutex.
  6. Define queue-full and buffer-overflow behavior.
  7. Use a queue when data transfer is the main requirement.
  8. Use a counting semaphore when the application must count pending events or available resource tokens.
  9. Use ISR-safe queue or semaphore APIs when communicating from an interrupt.
  10. Test producer and consumer operation under different execution rates.

14. Practical Activity

Implement a producer-consumer application using a bounded buffer.

Activity steps

  1. Create a circular buffer with five elements.
  2. Create an empty counting semaphore with initial count five.
  3. Create a full counting semaphore with initial count zero.
  4. Create a mutex for shared buffer access.
  5. Implement the producer task.
  6. Implement the consumer task.
  7. Test the system with a faster producer and a slower consumer.
  8. Observe how the producer blocks when the buffer becomes full.
  9. Observe how the consumer blocks when the buffer becomes empty.
  10. Repeat the activity using a FreeRTOS queue and compare complexity.

Expected result

The producer should not overwrite unread data, and the consumer should not read an empty buffer. Synchronization should maintain the correct buffer state.

16. Lesson Summary

  • The Producer-Consumer problem involves exchanging data through a shared buffer.
  • Empty and full counting semaphores track available and occupied slots.
  • A mutex protects shared buffer operations in the classical solution.
  • A circular buffer uses read and write indexes to reuse storage.
  • FreeRTOS queues provide built-in storage and synchronization for many producer-consumer applications.
  • Buffer capacity, data ownership, overflow handling, and task execution rates must be considered during design.
