1. Introduction

Synchronization is a mechanism used in operating systems and real-time systems to coordinate the execution of multiple tasks and control their access to shared resources.

In a multitasking system, several tasks may execute independently. They may need to access the same variable, buffer, peripheral, or hardware resource. Without proper synchronization, their operations can interfere with one another.

Example: In an embedded monitoring system, a sensor task updates a shared measurement while a display task reads it. Synchronization ensures that the display task receives a consistent value.

2. Why Is Synchronization Required?

  • To protect shared data from simultaneous conflicting access.
  • To prevent race conditions.
  • To coordinate task execution.
  • To control access to shared peripherals.
  • To signal the completion of an operation.
  • To manage producer-consumer relationships.
  • To maintain data consistency.
  • To prevent resource corruption.

The synchronization mechanism controls when a task may access a resource or proceed with a particular operation.

4. Task Synchronization vs Data Communication

Synchronization and communication are related but have different purposes.

AspectSynchronizationData Communication
Primary purposeCoordinate operations and access.Transfer information.
Typical mechanismMutex, semaphore, event group.Queue, buffer, shared memory.
ExampleWait until a peripheral is available.Transfer an ADC sample.
Main concernOrdering, exclusion, coordination.Data content, format and ownership.

A queue can provide both data transfer and synchronization because a receiving task can block until a message arrives.

5. Critical Section

A critical section is a portion of code that accesses shared data or a resource and must be protected against conflicting concurrent access.

Example

sharedCounter = sharedCounter + 1;

This operation involves reading the current value, calculating a new value, and writing it back. If two tasks perform this operation concurrently, one update may be lost.

Protected conceptual operation

Enter_Critical_Section();

sharedCounter = sharedCounter + 1;

Exit_Critical_Section();

The actual protection mechanism must be appropriate for the execution context and RTOS port.

6. Race Condition

A race condition occurs when the result of an operation depends on the timing or ordering of concurrent accesses to shared data.

Example

Assume the initial value of a shared counter is 10.

StepTask ATask B
1Reads 10—
2—Reads 10
3Calculates 11—
4—Calculates 11
5Writes 11—
6—Writes 11

The expected result after two increments is 12, but the actual result is 11.

This is a lost-update problem. A suitable synchronization mechanism or atomic operation is required to prevent it.

8. Mutual Exclusion

Mutual exclusion ensures that only one task at a time accesses a protected resource or critical section.

Example

Suppose two tasks need to use the same UART transmitter. Without protection, their output bytes could become interleaved.

Task A:
    Acquire UART mutex
    Transmit message A
    Release UART mutex

Task B:
    Acquire UART mutex
    Transmit message B
    Release UART mutex

The mutex serializes the protected operations, assuming every task follows the same locking protocol.

9. Synchronization Using a Binary Semaphore

A binary semaphore has two logical states: available and unavailable. It is commonly used to signal an event from one execution context to another.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xDataReady;

void AcquisitionTask(void *pvParameters)
{
    for (;;)
    {
        Acquire_Data();

        xSemaphoreGive(xDataReady);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xDataReady,
                portMAX_DELAY) == pdTRUE)
        {
            Process_Data();
        }
    }
}

The processing task blocks until the semaphore is available. The acquisition task signals that the operation has completed.

A binary semaphore can coalesce repeated signals: giving it while it is already available does not create an unlimited event count. Use a counting semaphore or queue when every event or data item must be retained.

10. Synchronization Using a Mutex

A mutex is a mutual-exclusion object with ownership semantics. The task that successfully takes the mutex is responsible for giving it back.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xMutex;
int sharedCounter = 0;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            xSemaphoreGive(xMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            xSemaphoreGive(xMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

Both tasks use the same mutex to protect the shared counter. The protected increment operation is performed by only one task at a time.

11. Synchronization Using Event Groups

Event groups allow multiple tasks to wait for combinations of event bits.

Example: System initialization

#define SENSOR_READY  (1U << 0)
#define UART_READY    (1U << 1)
#define DISPLAY_READY (1U << 2)

EventGroupHandle_t xSystemEvents;

/* A task waits for all three initialization events. */
void ControlTask(void *pvParameters)
{
    EventBits_t required =
        SENSOR_READY | UART_READY | DISPLAY_READY;

    for (;;)
    {
        EventBits_t bits = xEventGroupWaitBits(
            xSystemEvents,
            required,
            pdFALSE,
            pdTRUE,
            portMAX_DELAY
        );

        if ((bits & required) == required)
        {
            Start_Application();
        }
    }
}

The control task proceeds after all required bits have been set.

12. Blocking and Non-Blocking Synchronization

TypeBehavior
BlockingThe task waits until the synchronization condition is satisfied or a timeout occurs.
Non-blockingThe task checks the condition and continues if the resource is unavailable.
Timed blockingThe task waits for a specified maximum duration.

Example – Blocking mutex take

xSemaphoreTake(xMutex, portMAX_DELAY);

Example – Non-blocking mutex take

if (xSemaphoreTake(xMutex, 0) == pdTRUE)
{
    Use_Shared_Resource();
    xSemaphoreGive(xMutex);
}
else
{
    Handle_Resource_Busy();
}

The non-blocking version returns immediately if the mutex cannot be acquired.

13. Synchronization and Interrupts

Interrupts introduce another execution context that may interact with tasks and shared data.

For example, a UART receive interrupt may signal a task when a byte arrives.

Conceptual workflow

       UART Receive Event
                |
                v
           UART ISR
                |
                | Signal Task
                v
       Processing Task
                |
                v
       Process Received Data

In FreeRTOS, use the documented ISR-safe API for the selected synchronization object, such as xSemaphoreGiveFromISR() for a binary or counting semaphore.

Do not call a blocking mutex or semaphore-take operation from an ISR. ISRs cannot wait for a task-owned resource. The correct interrupt-safe API and context-switch request are port-dependent.

14. Synchronization Problems

14.1 Deadlock

Deadlock occurs when tasks are permanently blocked because each waits for a resource held by another.

14.2 Starvation

Starvation occurs when a task is repeatedly denied access to CPU time or a required resource.

14.3 Priority Inversion

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task holding a required resource.

14.4 Race Condition

Race conditions occur when concurrent operations on shared data are not adequately coordinated.

14.5 Livelock

Livelock occurs when tasks continue reacting to one another but fail to make useful progress.

15. Example – Embedded Motor Monitoring

Consider a motor monitoring system with the following tasks:

TaskResponsibilitySynchronization Requirement
Sensor TaskReads motor current and temperature.Transfers completed samples.
Processing TaskChecks operating limits.Waits for sensor data.
Display TaskDisplays operating status.Reads consistent status data.
Communication TaskTransmits motor information.Coordinates access to UART.

Possible mechanisms:

  • Queue for sensor measurements.
  • Binary semaphore for a completion event.
  • Mutex for shared display or communication resources.
  • Event group for system initialization conditions.
For safety-critical motor protection, use an appropriately designed hardware protection path or independently verified control mechanism where required. Do not rely solely on a normal-priority monitoring task.

16. Best Practices for Synchronization

  • Use a mutex to protect task-shared resources that require mutual exclusion.
  • Use semaphores for signaling and resource counting.
  • Use queues when the actual data must be transferred.
  • Keep critical sections short.
  • Acquire multiple locks in a consistent global order.
  • Always release a mutex after completing the protected operation.
  • Avoid holding a mutex while waiting for slow hardware or performing lengthy processing.
  • Check API return values and handle timeouts.
  • Do not use mutexes from ISRs.
  • Document shared-resource ownership and synchronization rules.

17. Practical Activity – Protect a Shared Counter

Design a conceptual FreeRTOS application with two tasks that increment a shared counter.

Requirements

  1. Declare a shared integer counter.
  2. Create a mutex before starting the scheduler.
  3. Create two tasks with suitable stack sizes and priorities.
  4. Both tasks should acquire the mutex before incrementing the counter.
  5. Both tasks should release the mutex after updating the counter.
  6. Print or inspect the counter from a suitable monitoring task.
  7. Compare the protected design with an unprotected version.
  8. Explain why the unprotected version can lose updates.

Expected learning outcome

Understand how mutual exclusion prevents conflicting access to shared data and why synchronization is essential in multitasking applications.

19. Lesson Summary

  • Synchronization coordinates task execution and shared-resource access.
  • Critical sections protect sensitive operations.
  • Race conditions can cause lost updates and inconsistent data.
  • Mutexes provide mutual exclusion with ownership semantics.
  • Semaphores support event signaling and resource counting.
  • Event groups coordinate tasks using event bits.
  • ISR-to-task synchronization requires interrupt-safe APIs.
  • Deadlock, starvation, livelock, and priority inversion are important synchronization problems.
