Task Synchronization Using Semaphores

1. Introduction

Task synchronization is the coordination of multiple tasks so that they execute in the correct order and respond to events or shared conditions safely.

In an RTOS, tasks operate independently from the application's perspective, but they may need to coordinate their activities. Semaphores provide a mechanism for this coordination.

Key idea: A task can wait for a semaphore before continuing. Another task can give the semaphore when a required event or operation has occurred.

2. Why Is Task Synchronization Required?

Consider an embedded system that performs sensor acquisition and data processing.

  • Task A reads sensor data.
  • Task B processes the acquired data.
  • Task C transmits the processed result.

These tasks must coordinate their execution. Processing should not begin before valid sensor data is available, and transmission should not begin before processing is complete.

Without synchronization

  • A task may read incomplete data.
  • Operations may execute in an incorrect order.
  • Events may be missed.
  • Shared data may become inconsistent.

3. Basic Task Synchronization Architecture

       +----------------------+
       |      Task A          |
       |  Perform Operation   |
       +----------------------+
                  |
                  | Give Semaphore
                  v
       +----------------------+
       |     Semaphore        |
       +----------------------+
                  |
                  | Take Semaphore
                  v
       +----------------------+
       |      Task B          |
       |  Continue Operation  |
       +----------------------+

Execution sequence

  1. Task B waits for the semaphore.
  2. Task A performs its operation.
  3. Task A gives the semaphore.
  4. Task B becomes Ready if it was waiting.
  5. The scheduler selects a Ready task according to priority and scheduling rules.
  6. Task B continues after its successful take operation.

4. Synchronization Using a Binary Semaphore

A binary semaphore is commonly used when one task must notify another task that an event has occurred.

Example: Sensor data ready

Task A acquires sensor data. Task B waits until the data is ready.

SemaphoreHandle_t xDataReadySemaphore;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        AcquireSensorData();

        xSemaphoreGive(xDataReadySemaphore);

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xDataReadySemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessSensorData();
        }
    }
}

Explanation:

  • The sensor task obtains data.
  • It gives the binary semaphore after acquisition.
  • The processing task waits for the semaphore.
  • After taking the semaphore, the processing task processes the data.
The semaphore indicates that data is ready, but it does not transfer or protect the sensor data itself. If the producer can overwrite the data while the consumer is processing it, use a queue, buffer ownership protocol, or suitable mutex protection.

5. Synchronization Between Two Tasks

Two tasks can coordinate their operations using a binary semaphore.

Example: Task A signals Task B

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xSyncSemaphore;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        /* Perform operation A */
        PerformOperationA();

        /* Notify Task B */
        xSemaphoreGive(xSyncSemaphore);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xSyncSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Continue after Task A signals */
            PerformOperationB();
        }
    }
}

int main(void)
{
    xSyncSemaphore = xSemaphoreCreateBinary();

    if (xSyncSemaphore == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(TaskA, "TaskA", 256, NULL, 2, NULL);
    xTaskCreate(TaskB, "TaskB", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Task B cannot pass its blocking take operation until Task A provides a semaphore token.

6. Synchronization Between Multiple Tasks

A counting semaphore can coordinate multiple tasks or represent multiple available tokens.

Example

Suppose several worker tasks must wait until a common initialization operation is complete.

SemaphoreHandle_t xStartSemaphore;

void WorkerTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xStartSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            PerformWorkerOperation();
        }
    }
}

void InitializationTask(void *pvParameters)
{
    InitializeSystem();

    /* Release three waiting workers */
    xSemaphoreGive(xStartSemaphore);
    xSemaphoreGive(xStartSemaphore);
    xSemaphoreGive(xStartSemaphore);

    vTaskDelete(NULL);
}

int main(void)
{
    xStartSemaphore = xSemaphoreCreateCounting(3, 0);

    if (xStartSemaphore == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(WorkerTask, "Worker1", 256, NULL, 2, NULL);
    xTaskCreate(WorkerTask, "Worker2", 256, NULL, 2, NULL);
    xTaskCreate(WorkerTask, "Worker3", 256, NULL, 2, NULL);
    xTaskCreate(InitializationTask, "Init", 256, NULL, 3, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Each successful take consumes one token. The three gives provide up to three tokens for the waiting workers.

This pattern releases up to three waiting tasks. It is not a permanent broadcast event: a worker that starts waiting after all tokens have been consumed will remain blocked until another token is given.

7. Synchronization Using a Mutex

A mutex is used when tasks need exclusive access to a shared resource.

Example: Shared communication peripheral

Suppose two tasks need to use the same UART transmitter. A mutex can prevent their transmissions from interfering with each other.

SemaphoreHandle_t xUARTMutex;

void UARTTaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xUARTMutex,
                portMAX_DELAY) == pdTRUE)
        {
            UART_SendString("Message from Task A");

            xSemaphoreGive(xUARTMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void UARTTaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xUARTMutex,
                portMAX_DELAY) == pdTRUE)
        {
            UART_SendString("Message from Task B");

            xSemaphoreGive(xUARTMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

Only one task can own the mutex at a time. The mutex is released after the protected UART operation.

For a real UART driver, consider protecting the entire logical transmission rather than individual character writes. A queue-based UART transmit architecture may be more suitable when multiple tasks generate messages.

8. Synchronization Using a Counting Semaphore

A counting semaphore can represent multiple pending events or available resource slots.

Example: Three available buffers

Assume three buffers are available. A task must take a token before obtaining a buffer and give it back after releasing the buffer.

SemaphoreHandle_t xBufferSemaphore;

void BufferWorker(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xBufferSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Obtain a specific free buffer */
            ProcessBuffer();

            /* Return the availability token */
            xSemaphoreGive(xBufferSemaphore);
        }
    }
}

int main(void)
{
    xBufferSemaphore = xSemaphoreCreateCounting(3, 3);

    if (xBufferSemaphore == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(BufferWorker, "Worker1", 256, NULL, 2, NULL);
    xTaskCreate(BufferWorker, "Worker2", 256, NULL, 2, NULL);
    xTaskCreate(BufferWorker, "Worker3", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

The semaphore tracks the number of available resource slots. An actual resource pool must separately identify which buffer is free and ensure correct ownership and release.

9. Task Synchronization vs Mutual Exclusion

Synchronization and mutual exclusion are related but different concepts.

FeatureTask SynchronizationMutual Exclusion
PurposeCoordinate task execution and event ordering.Prevent simultaneous access to a shared resource.
Typical mechanismBinary semaphore, counting semaphore, task notification, event group.Mutex or suitable critical section.
ExampleWait until sensor data is ready.Protect a shared UART transmission.
OwnershipDepends on the synchronization object.Mutex ownership is associated with the task holding it.

10. Synchronization Using Queues vs Semaphores

FeatureSemaphoreQueue
Primary purposeSynchronization and signaling.Data transfer and communication.
StoresTokens or counts.Data items.
Data transferDoes not transfer application payload.Transfers configured queue items.
Typical exampleNotify a task that an event occurred.Send a sensor measurement to another task.

If a task needs to receive both an event notification and associated data, a queue is often a better choice than a semaphore alone.

11. Common Synchronization Problems

11.1 Deadlock

Two or more tasks become permanently blocked while waiting for resources held by one another.

11.2 Priority Inversion

A high-priority task is delayed because a lower-priority task holds a resource it needs.

11.3 Starvation

A task waits for an extended period because other tasks repeatedly obtain the resource or scheduling opportunity.

11.4 Lost Notifications

A binary semaphore can represent only one pending token. Repeated events may collapse into a single notification.

11.5 Incorrect Resource Release

A task may release a resource incorrectly, fail to release it, or release a token more than once.

12. Best Practices for Task Synchronization

  1. Choose the synchronization mechanism according to the actual requirement.
  2. Use binary semaphores for simple event signaling.
  3. Use counting semaphores when multiple tokens must be tracked.
  4. Use mutexes for task-level shared resource protection.
  5. Use queues when application data must be transferred.
  6. Use ISR-safe APIs from interrupt context.
  7. Do not use mutexes from ISRs.
  8. Check semaphore creation and operation return values.
  9. Use appropriate timeouts where indefinite waiting is unsuitable.
  10. Keep shared-resource ownership and release rules clear.
  11. Avoid holding a mutex while performing long delays or unrelated operations.
  12. Analyze deadlock and priority-inversion risks.

13. Practical Embedded System Example

Consider an embedded temperature-monitoring system.

System tasks

TaskResponsibilitySynchronization
Sensor TaskAcquire temperature measurements.Give a notification after acquisition.
Processing TaskCalculate temperature status.Wait for sensor data availability.
Display TaskUpdate display information.Wait for processed data.
Communication TaskTransmit measurements.Receive data through a queue.

System flow

       +----------------------+
       |     Sensor Task      |
       +----------------------+
                  |
                  | Data Ready
                  v
       +----------------------+
       |   Binary Semaphore   |
       +----------------------+
                  |
                  v
       +----------------------+
       |   Processing Task    |
       +----------------------+
                  |
                  | Processed Data
                  v
       +----------------------+
       |        Queue         |
       +----------------------+
                  |
             +----+----+
             |         |
             v         v
       +---------+ +-----------+
       | Display | |   UART    |
       |  Task   | |   Task    |
       +---------+ +-----------+

This architecture separates sensor acquisition, processing, display, and communication. The semaphore coordinates readiness, while the queue transfers the processed data.

16. Lesson Summary

  • Task synchronization coordinates execution between RTOS tasks.
  • Binary semaphores are useful for event notification.
  • Counting semaphores can represent multiple tokens or resource availability.
  • Mutexes provide task-level mutual exclusion.
  • Queues transfer data between tasks.
  • Synchronization mechanisms must be selected according to the application requirement.
  • Deadlock, starvation, priority inversion, and lost notifications must be considered during design.
