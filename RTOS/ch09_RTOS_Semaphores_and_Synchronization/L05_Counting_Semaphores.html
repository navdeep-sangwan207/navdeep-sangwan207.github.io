Counting Semaphores

Chapter 09 – Semaphores and Synchronization | Lesson 05

1. Introduction

A counting semaphore is a synchronization object that maintains a count within a configured range. Unlike a binary semaphore, which can hold only zero or one token, a counting semaphore can hold multiple tokens.

It is commonly used for two purposes:

  • Counting occurrences of events.
  • Managing a fixed number of identical resources.
Key idea: A counting semaphore allows multiple tokens to be available. Each successful take consumes one token, while each successful give adds one token, up to the configured maximum.

2. Working Principle

A counting semaphore maintains a count between zero and its maximum value.

0 ≤ Current Count ≤ Maximum Count
CountMeaning
0No token is available. A task attempting to take may block.
1One token is available.
2Two tokens are available.
Maximum countAll configured tokens are available.

Basic operations

  • Take: Decreases the count by one if a token is available.
  • Give: Increases the count by one if the count is below the maximum.
  • Wait: A task can block until a token becomes available.

3. Counting Semaphore Example

Suppose an embedded system has four identical communication buffers.

Maximum Count = 4

Initially, all four buffers are available.

OperationCurrent CountAvailable Buffers
Initial state44
Task A takes one33
Task B takes one22
Task C takes one11
Task D takes one00
Task A releases one11

When the count reaches zero, another task requesting a buffer must wait until a token is returned.

4. Counting Semaphore for Event Counting

A counting semaphore can record multiple pending events when each event produces one successful give and the semaphore has sufficient capacity.

Example: Timer events

Suppose a timer interrupt occurs five times before a task processes the notifications.

EventSemaphore Count
Initial state0
Timer event 11
Timer event 22
Timer event 33
Timer event 44
Timer event 55

The task can then take the semaphore five times, consuming the five available tokens.

A counting semaphore records the number of pending tokens, not the details of individual events. If event identity, order, or associated data must be preserved, use a queue or another suitable data structure.

6. Creating a Counting Semaphore in FreeRTOS

FreeRTOS provides the xSemaphoreCreateCounting() function.

Syntax

SemaphoreHandle_t xSemaphoreCreateCounting(
    UBaseType_t uxMaxCount,
    UBaseType_t uxInitialCount
);

Parameters

ParameterDescription
uxMaxCountMaximum number of tokens the semaphore can hold.
uxInitialCountInitial number of available tokens.

Return value

  • A valid semaphore handle if creation succeeds.
  • NULL if creation fails.

Example

#include "FreeRTOS.h"
#include "semphr.h"

SemaphoreHandle_t xCountingSemaphore;

void CreateCountingSemaphore(void)
{
    xCountingSemaphore = xSemaphoreCreateCounting(5, 0);

    if (xCountingSemaphore == NULL)
    {
        /* Handle creation failure */
        for (;;)
        {
        }
    }
}

In this example, the maximum count is five and the initial count is zero. The semaphore starts empty.

7. Taking a Counting Semaphore

The xSemaphoreTake() function obtains one token from a counting semaphore.

Syntax

BaseType_t xSemaphoreTake(
    SemaphoreHandle_t xSemaphore,
    TickType_t xTicksToWait
);

Example

if (xSemaphoreTake(
        xCountingSemaphore,
        portMAX_DELAY) == pdTRUE)
{
    /* One token successfully obtained */
}

When a token is available, the operation succeeds and decreases the count by one. If no token is available, the task waits for the specified timeout or returns failure.

8. Giving a Counting Semaphore

The xSemaphoreGive() function adds one token to the semaphore.

Example

if (xSemaphoreGive(xCountingSemaphore) == pdTRUE)
{
    /* Token successfully added */
}

If the semaphore is already at its maximum count, the give operation fails because no additional token can be stored.

9. Complete FreeRTOS Counting Semaphore Program

This example demonstrates event counting using two tasks.

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xCountingSemaphore;

void EventConsumerTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xCountingSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Process one pending event */
        }
    }
}

void EventProducerTask(void *pvParameters)
{
    for (;;)
    {
        /* Simulate an event every 500 ms */
        vTaskDelay(pdMS_TO_TICKS(500));

        if (xSemaphoreGive(xCountingSemaphore) == pdTRUE)
        {
            /* One event token added */
        }
    }
}

int main(void)
{
    xCountingSemaphore = xSemaphoreCreateCounting(5, 0);

    if (xCountingSemaphore == NULL)
    {
        for (;;)
        {
        }
    }

    if (xTaskCreate(
            EventConsumerTask,
            "Consumer",
            256,
            NULL,
            2,
            NULL) != pdPASS)
    {
        for (;;)
        {
        }
    }

    if (xTaskCreate(
            EventProducerTask,
            "Producer",
            256,
            NULL,
            2,
            NULL) != pdPASS)
    {
        for (;;)
        {
        }
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program explanation

  1. Create a counting semaphore with a maximum count of five.
  2. Initialize its count to zero.
  3. Create the consumer task.
  4. Create the producer task.
  5. Start the scheduler.
  6. The producer gives one token approximately every 500 ms.
  7. The consumer takes a token and processes one event.

Expected behavior

The consumer task processes each successfully recorded token. If the producer generates tokens faster than the consumer can process them, the count can increase until it reaches five. Further give operations then fail until a token is consumed.

10. Counting Semaphore for Resource Management

Counting semaphores can control access to a limited number of identical resources.

Example: Three available buffers

Suppose an application has three memory buffers. A task must obtain a token before using one and return the token when the buffer is released.

#define BUFFER_COUNT 3

SemaphoreHandle_t xBufferSemaphore;

void BufferTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xBufferSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Obtain and use one free buffer */

            UseBuffer();

            /* Release the buffer token */
            xSemaphoreGive(xBufferSemaphore);
        }
    }
}

int main(void)
{
    xBufferSemaphore =
        xSemaphoreCreateCounting(BUFFER_COUNT,
                                 BUFFER_COUNT);

    if (xBufferSemaphore == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(
        BufferTask,
        "BufferTask",
        256,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}
A counting semaphore only tracks the number of available resources. It does not identify which particular buffer is free or enforce that a task returns the same buffer it obtained. Use a free-list, queue of buffer pointers, or another ownership mechanism when individual resource identity matters.

11. Counting Semaphore from an ISR

A counting semaphore can be used to record interrupt events. An ISR gives one token for each event it successfully records.

Illustrative ISR code

void TIMER_ISR(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge timer interrupt */

    xSemaphoreGiveFromISR(
        xCountingSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

The task can take tokens later and process the recorded events.

Check the return value of xSemaphoreGiveFromISR() in production code. If the semaphore reaches its maximum count, the give can fail and the event will not be represented by an additional token. The exact yield macro is port-specific.

13. Common Mistakes

  • Setting the initial count greater than the maximum count.
  • Ignoring the return value of semaphore creation.
  • Assuming a counting semaphore stores event details.
  • Giving more tokens than the maximum count allows.
  • Failing to return a resource token after use.
  • Returning a token twice for one resource.
  • Using a counting semaphore when FIFO data transfer is required.
  • Using normal task APIs inside an ISR.
  • Assuming the semaphore identifies individual free resources.

14. Practical Applications

  • Counting timer events.
  • Counting received data blocks.
  • Managing a pool of identical buffers.
  • Managing a fixed number of communication channels.
  • Tracking available hardware resources.
  • Coordinating multiple requests for a limited resource pool.
  • Recording repeated interrupt notifications.

15. Practical Activity – Resource Pool Management

Design an RTOS application that manages three identical buffers.

Tasks

  1. Create a counting semaphore with maximum count three and initial count three.
  2. Create multiple tasks that request a buffer token.
  3. Allow a task to proceed only after obtaining a token.
  4. Simulate buffer processing.
  5. Return the token after processing is complete.
  6. Observe how tasks wait when all three tokens are consumed.

Expected result

At most three tasks can hold resource tokens simultaneously. Additional tasks wait until a token is returned.

For a complete resource-pool implementation, associate each token with an actual buffer allocation and ensure that every acquired buffer is released exactly once.

17. Lesson Summary

  • A counting semaphore maintains a count between zero and a configured maximum.
  • xSemaphoreCreateCounting() creates a counting semaphore.
  • xSemaphoreTake() consumes one token.
  • xSemaphoreGive() adds one token when capacity is available.
  • Counting semaphores can count pending events or manage a fixed number of identical resources.
  • xSemaphoreGiveFromISR() supports giving a semaphore from interrupt context.
  • A counting semaphore does not store message data or identify individual resources.
  • Queues are more suitable when event data and message ordering must be preserved.
