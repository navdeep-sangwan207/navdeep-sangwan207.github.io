1. Introduction

In an embedded system, hardware peripherals generate interrupts when important events occur. Examples include timer expiration, UART reception, ADC conversion completion, and external pin changes.

When an interrupt occurs, the processor executes an Interrupt Service Routine (ISR). In an RTOS-based application, the ISR often needs to notify a task that an event has occurred.

FreeRTOS supports communication between an ISR and a task using semaphore-specific ISR APIs.

Key concept: The ISR performs minimal interrupt handling and signals a task. The task performs the longer processing operation outside interrupt context.

2. Why Is ISR-to-Task Communication Required?

Consider a UART receiver. Every time a byte arrives, the UART peripheral generates an interrupt.

Performing all communication processing inside the ISR can increase interrupt latency and delay other interrupts.

Recommended approach

  1. UART hardware receives a byte.
  2. UART generates an interrupt.
  3. ISR reads the received byte and handles the peripheral interrupt condition.
  4. ISR signals a task using an ISR-safe API.
  5. The task processes the received information.

This approach keeps the ISR short and moves application-level processing into task context.

4. Why Normal Semaphore APIs Must Not Be Used in an ISR

Normal semaphore APIs are designed for task context. Some operations may block or interact with scheduler mechanisms that are not valid inside an ISR.

Task contextISR context
xSemaphoreGive()xSemaphoreGiveFromISR()
xSemaphoreTake()xSemaphoreTakeFromISR(), where applicable
Can use a non-zero blocking timeout.Must not block or wait for a timeout.
Can use task-context APIs.Must use documented ISR-safe APIs.
Never call xSemaphoreGive() or a blocking xSemaphoreTake() from an ISR. Use the appropriate ISR-safe API for the operation and semaphore type.

5. xSemaphoreGiveFromISR()

FreeRTOS provides xSemaphoreGiveFromISR() to release a semaphore from interrupt context.

Function syntax

BaseType_t xSemaphoreGiveFromISR(
    SemaphoreHandle_t xSemaphore,
    BaseType_t *pxHigherPriorityTaskWoken
);

Parameters

ParameterDescription
xSemaphoreHandle of the semaphore being given.
pxHigherPriorityTaskWokenPointer to a variable that indicates whether a higher-priority task was unblocked by the operation.

Return value

  • pdTRUE: The semaphore was successfully given.
  • pdFALSE: The operation failed, for example, because a binary semaphore was already available or a counting semaphore was at its maximum count.

Higher-priority task notification

If giving the semaphore unblocks a task with a priority higher than the currently interrupted task, FreeRTOS can indicate this through pxHigherPriorityTaskWoken.

6. portYIELD_FROM_ISR()

After giving a semaphore, the ISR may request a context switch so that an unblocked higher-priority task can run as soon as the interrupt-exit scheduling rules permit.

BaseType_t xHigherPriorityTaskWoken = pdFALSE;

xSemaphoreGiveFromISR(
    xSemaphore,
    &xHigherPriorityTaskWoken
);

portYIELD_FROM_ISR(xHigherPriorityTaskWoken);

The yield macro is port-specific. Some FreeRTOS ports use a different form or provide a related macro. Follow the documentation for the selected port.

Giving a semaphore does not guarantee that the notified task executes immediately inside the ISR. The scheduler selects the next task at an appropriate scheduling point, normally after the ISR exits.

7. Example 1 – Binary Semaphore for Timer Interrupt

In this example, a timer interrupt signals a task whenever the timer event occurs.

Global semaphore handle

SemaphoreHandle_t xTimerSemaphore;

Timer ISR – illustrative FreeRTOS code

void TIMER_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the timer interrupt here */

    xSemaphoreGiveFromISR(
        xTimerSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

Task waiting for timer event

void TimerTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xTimerSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessTimerEvent();
        }
    }
}

Explanation

  1. The timer peripheral generates an interrupt.
  2. The ISR acknowledges the interrupt source.
  3. The ISR gives the binary semaphore.
  4. The waiting task becomes Ready.
  5. The task processes the timer event when scheduled.
A binary semaphore stores at most one pending token. If multiple timer events occur before the task consumes the token, repeated gives can fail or coalesce. Use a counting semaphore or queue if every event must be preserved.

8. Example 2 – UART Interrupt and Task Communication

In a UART-based embedded application, the ISR can capture a received byte and notify a task.

Illustrative structure

SemaphoreHandle_t xUARTSemaphore;
volatile uint8_t receivedByte;

void UART_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Read received byte from UART register */
    receivedByte = UART_ReadByte();

    /* Acknowledge or clear the UART interrupt as required */

    xSemaphoreGiveFromISR(
        xUARTSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void UARTTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xUARTSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessReceivedByte(receivedByte);
        }
    }
}
This is an architectural illustration, not a complete UART driver. A single shared byte variable can be overwritten if multiple bytes arrive before the task processes the previous one. For reliable continuous reception, use a ring buffer or queue with a defined producer-consumer ownership protocol. volatile alone does not solve data races or buffer synchronization.

9. Counting Semaphore for Interrupt Events

When every interrupt event must be counted, a counting semaphore may be more suitable than a binary semaphore.

Example

SemaphoreHandle_t xEventSemaphore;

/* Create with maximum count 10 and initial count 0 */
xEventSemaphore = xSemaphoreCreateCounting(10, 0);

The ISR can give one token for each event:

void EVENT_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the hardware event */

    if (xSemaphoreGiveFromISR(
            xEventSemaphore,
            &xHigherPriorityTaskWoken) == pdTRUE)
    {
        /* Event token recorded */
    }
    else
    {
        /* Semaphore full: event could not be counted */
    }

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

The task consumes the pending event tokens:

void EventTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xEventSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessOneEvent();
        }
    }
}

The maximum count is ten. If the task cannot keep up and the count reaches ten, another give fails. The application must define how this overflow condition is handled.

10. xSemaphoreTakeFromISR()

FreeRTOS also provides xSemaphoreTakeFromISR() for applicable semaphore types when an ISR needs to obtain a token without blocking.

Function syntax

BaseType_t xSemaphoreTakeFromISR(
    SemaphoreHandle_t xSemaphore,
    BaseType_t *pxHigherPriorityTaskWoken
);

This operation is non-blocking. It either obtains an available token or returns failure.

Do not use mutexes from an ISR. Mutex ownership and priority inheritance require task-context behavior. Use ISR-safe semaphore operations only for semaphore types supported by the API.

11. ISR-to-Task Communication Using a Queue

A semaphore communicates that an event occurred, but it does not carry the event's application data.

If the ISR must transfer a received byte or sensor value, a queue can be more appropriate.

Example – Queue data from ISR

QueueHandle_t xDataQueue;

void ADC_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    uint16_t adcValue;

    /* Read ADC conversion result */
    adcValue = ADC_ReadResult();

    /* Clear/acknowledge ADC interrupt as required */

    xQueueSendFromISR(
        xDataQueue,
        &adcValue,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void ADCProcessingTask(void *pvParameters)
{
    uint16_t receivedValue;

    for (;;)
    {
        if (xQueueReceive(
                xDataQueue,
                &receivedValue,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessADCValue(receivedValue);
        }
    }
}

The queue copies the configured item into its storage. The task receives the value later. The application should check the return value of xQueueSendFromISR() and handle queue-full conditions.

12. Binary Semaphore vs Counting Semaphore vs Queue

MechanismWhat it representsTypical application
Binary semaphoreOne pending notification token.Notify a task that an event occurred.
Counting semaphoreA count of pending tokens.Count events or available resource slots.
QueueOrdered data items.Transfer received bytes or ADC samples.

13. Important ISR Programming Rules

  1. Keep the ISR short and predictable.
  2. Acknowledge or clear the interrupt source correctly.
  3. Use only documented ISR-safe RTOS APIs.
  4. Never call a blocking task API from an ISR.
  5. Do not use mutexes from an ISR.
  6. Use the appropriate ISR yield mechanism for the port.
  7. Check the return value of queue and semaphore operations.
  8. Define how event overflow is handled.
  9. Protect shared buffers using an appropriate ownership and synchronization design.
  10. Perform lengthy processing in a task rather than the ISR.

14. LPC2129 and ARM7 Interrupt Considerations

The LPC2129 uses an ARM7TDMI-S processor and a Vectored Interrupt Controller (VIC). Its interrupt architecture differs from Cortex-M microcontrollers.

  • ARM7TDMI-S supports IRQ and FIQ exception types.
  • The LPC2129 VIC manages interrupt sources and vectored IRQ handling.
  • Interrupt acknowledgment and peripheral status clearing depend on the peripheral and interrupt source.
  • ARM7 interrupt masking uses CPSR control bits.
  • Cortex-M NVIC and BASEPRI-specific assumptions must not be applied to this processor.
The examples in this lesson explain generic FreeRTOS ISR-to-task communication. They do not establish that a compatible FreeRTOS port is available for LPC2129 with the current Keil uVision simulator setup. Verify the exact processor port before attempting to build or run these examples.

15. Practical Activity

Design an interrupt-to-task notification example using a binary semaphore.

Activity steps

  1. Create a binary semaphore before starting the scheduler.
  2. Create a task that waits for the semaphore.
  3. Configure a suitable timer or interrupt source on a supported target.
  4. In the ISR, acknowledge the interrupt.
  5. Give the semaphore using xSemaphoreGiveFromISR().
  6. Use the port-specific ISR yield mechanism where required.
  7. In the task, process the event after a successful take.
  8. Test repeated events and observe whether notifications are lost or coalesced.

Expected result

The task should respond to the interrupt notification outside the ISR. If events can arrive faster than the task processes them, evaluate whether a counting semaphore or queue is required.

17. Lesson Summary

  • Hardware interrupts are handled by ISRs.
  • ISRs can notify RTOS tasks using ISR-safe APIs.
  • xSemaphoreGiveFromISR() gives a semaphore from interrupt context.
  • xSemaphoreTakeFromISR() can obtain an available token without blocking, for applicable semaphore types.
  • portYIELD_FROM_ISR() is port-specific and can request a scheduling decision at interrupt exit.
  • Binary semaphores are suitable for simple notifications; counting semaphores track multiple tokens.
  • Queues should be considered when actual event data must be transferred.
  • Keep ISRs short and handle overflow, shared-buffer ownership, and interrupt acknowledgment correctly.
