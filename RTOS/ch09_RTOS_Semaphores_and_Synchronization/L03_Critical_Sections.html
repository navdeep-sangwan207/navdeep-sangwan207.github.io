1. Introduction

A critical section is a portion of program code that accesses shared data or a shared resource and therefore requires controlled access.

If multiple tasks or interrupt handlers can access the same resource, execution must be coordinated to prevent race conditions and inconsistent data.

Key idea: A critical section protects a sensitive operation so that conflicting execution contexts cannot interfere with it during the protected operation.

2. Why Are Critical Sections Required?

Consider two tasks updating the same counter:

sharedCounter = sharedCounter + 1;

This statement involves reading, modifying, and writing a value. If another task interrupts the operation, an update can be lost.

Common reasons for using critical sections

  • Preventing race conditions.
  • Protecting shared counters and flags.
  • Updating shared data structures.
  • Protecting short read-modify-write operations.
  • Coordinating access to resources that cannot safely be accessed concurrently.

3. Critical Section Structure

A typical protected operation has three parts:

        +--------------------------+
        | Enter Critical Section   |
        +--------------------------+
                    |
                    v
        +--------------------------+
        | Protected Operations     |
        |                          |
        | Read / Modify / Write    |
        +--------------------------+
                    |
                    v
        +--------------------------+
        | Exit Critical Section    |
        +--------------------------+
  1. Entry: Establish the required protection.
  2. Protected code: Access or modify the shared resource.
  3. Exit: Restore normal execution conditions.

4. Critical Section Without Protection

Consider the following example:

int sharedCounter = 0;

void TaskA(void)
{
    sharedCounter++;
}

void TaskB(void)
{
    sharedCounter++;
}

Both tasks access the same counter without synchronization. Their read-modify-write operations may overlap.

Task ATask BCounter
Reads 0—0
—Reads 00
Writes 1—1
—Writes 11

The expected result is 2, but the actual result can be 1.

5. Critical Section Using FreeRTOS

FreeRTOS provides port-specific critical-section macros for protecting short operations in task context.

Important macros

MacroPurpose
taskENTER_CRITICAL()Enter a critical section in task context.
taskEXIT_CRITICAL()Exit the critical section.
taskENTER_CRITICAL_FROM_ISR()Enter an ISR critical section where supported by the port.
taskEXIT_CRITICAL_FROM_ISR()Exit an ISR critical section where supported by the port.

Example

#include "FreeRTOS.h"
#include "task.h"

volatile unsigned int sharedCounter = 0;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        taskENTER_CRITICAL();

        sharedCounter++;

        taskEXIT_CRITICAL();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        taskENTER_CRITICAL();

        sharedCounter++;

        taskEXIT_CRITICAL();

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

Explanation:

  1. Task A enters the critical section.
  2. The shared counter is incremented.
  3. Task A exits the critical section.
  4. Task B can then execute its protected update.
The example illustrates task-context protection. The exact behavior of these macros depends on the FreeRTOS processor port. Do not assume that every port masks every interrupt or uses the same interrupt-priority mechanism.

6. Critical Sections and Interrupts

Interrupts can execute asynchronously relative to normal task execution. An ISR that accesses shared data may interfere with a task unless the access is properly coordinated.

Conceptual example

volatile unsigned int eventCount = 0;

/* Task context */
void ReadEventCount(void)
{
    unsigned int localCount;

    taskENTER_CRITICAL();

    localCount = eventCount;
    eventCount = 0;

    taskEXIT_CRITICAL();

    ProcessEvents(localCount);
}

/* Interrupt context */
void UART_ISR(void)
{
    eventCount++;
}

This example needs careful port-specific design. A task critical section only protects against an ISR if that critical section actually masks the relevant interrupt. If the interrupt remains enabled, the read-and-reset operation can still race with the ISR.

For task-to-ISR communication, prefer appropriate atomic operations, interrupt-safe synchronization mechanisms, or a documented ISR-to-task notification design. Use the exact rules provided by the target RTOS port.

7. Critical Sections vs Mutexes

Both mechanisms protect shared resources, but they work differently.

FeatureCritical SectionMutex
Primary purposeProtect a short operation from specified concurrent execution.Provide mutual exclusion for a shared resource.
BlockingDoes not block waiting for ownership.A task can block while waiting.
OwnershipUses port-specific critical-section rules.Has task ownership semantics.
Priority inheritanceNot a mutex priority-inheritance mechanism.FreeRTOS mutexes support priority inheritance.
Typical durationVery short.Can cover a longer task-level resource operation.
ISR usePort-specific ISR variants may exist.Mutexes must not be used from an ISR.

9. Nested Critical Sections

Some RTOS ports support nested critical sections. In a nesting design, entering a critical section more than once must be matched with the corresponding exits.

Conceptual example

taskENTER_CRITICAL();

/* Protected operation A */

taskENTER_CRITICAL();

/* Protected operation B */

taskEXIT_CRITICAL();

taskEXIT_CRITICAL();

In ports that implement nesting, the outermost exit normally restores the previous protection state.

Do not assume nesting behavior is identical across all ports. Follow the target port documentation and never leave a critical section without a matching exit.

10. Interrupt Masking and Critical Sections

Some critical-section implementations temporarily mask interrupts to prevent selected ISRs from executing during a protected operation.

On ARM7-based systems such as the LPC2129, interrupt control involves the CPSR interrupt mask bits:

CPSR BitMeaning
I bitWhen set, IRQ exceptions are masked.
F bitWhen set, FIQ exceptions are masked.

ARM7 interrupt control is different from Cortex-M interrupt-priority mechanisms. In particular, do not apply Cortex-M BASEPRI assumptions to the LPC2129.

Different levels of interrupt control

  • Peripheral-level interrupt enable or disable.
  • Vectored Interrupt Controller source enable or disable.
  • Processor-level IRQ or FIQ masking.

These controls are not interchangeable. Disabling a VIC source does not necessarily have the same effect as masking the processor's IRQ exception.

11. Risks of Long Critical Sections

Critical sections should be as short as possible.

Possible problems

  • Increased interrupt latency.
  • Delayed response to external events.
  • Missed real-time deadlines.
  • Reduced system responsiveness.
  • Increased timing jitter.
  • Potential loss of hardware events if the peripheral cannot retain them while interrupts are masked.
Never perform lengthy calculations, blocking delays, queue waits, or slow peripheral operations inside a critical section.

12. Best Practices

  1. Keep protected code short and deterministic.
  2. Use mutexes for task-level shared resource ownership.
  3. Use queues or notifications for communication between tasks and ISRs.
  4. Do not call blocking APIs inside a critical section.
  5. Do not use mutexes from interrupt context.
  6. Use the appropriate ISR-specific APIs where required.
  7. Match every critical-section entry with an exit.
  8. Understand the target processor port's interrupt-masking behavior.
  9. Avoid unnecessary global interrupt masking.
  10. Protect all conflicting accesses consistently.

13. Practical Activity – Protecting a Shared Counter

Study the following design and identify where protection is required.

Task A

void TaskA(void *pvParameters)
{
    for (;;)
    {
        taskENTER_CRITICAL();
        sharedCounter += 5;
        taskEXIT_CRITICAL();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

Task B

void TaskB(void *pvParameters)
{
    for (;;)
    {
        taskENTER_CRITICAL();
        sharedCounter += 10;
        taskEXIT_CRITICAL();

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

Expected result

When both tasks use the same valid protection mechanism for every access to the counter, their updates are serialized. The counter should equal the sum of all completed increments.

For a complete application, declare and initialize the shared variable, create both tasks, check task-creation results, and start the scheduler.

Simulator note: This is a FreeRTOS API learning example. It does not establish that a compatible FreeRTOS port is available for the LPC2129 in the user's Keil setup.

15. Lesson Summary

  • A critical section protects a short operation involving shared data or resources.
  • FreeRTOS provides port-specific critical-section macros.
  • Critical sections can prevent task-level interference and, depending on the port, selected interrupt interference.
  • Mutexes provide task-level mutual exclusion with ownership semantics.
  • Binary semaphores are useful for event signaling and synchronization.
  • Long critical sections increase interrupt latency and can harm real-time performance.
  • Always follow the target processor port's documentation.
