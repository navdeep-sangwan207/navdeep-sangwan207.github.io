2. Introduction to Latency

Latency is the time delay between an initiating event and the corresponding system response.

In an embedded real-time system, latency determines how quickly the processor or application responds after an external or internal event occurs.

Examples

  • Time between a sensor interrupt and execution of its ISR.
  • Time between a task becoming ready and starting execution.
  • Time between receiving a communication message and processing it.
  • Time between detecting a fault and activating the required response.
Low latency is useful, but predictable and bounded latency is especially important in real-time systems.

3. Types of Latency in RTOS

1. Interrupt Latency

The time between an interrupt request becoming active and the beginning of the corresponding interrupt service routine.

2. Scheduling Latency

The delay between a task becoming ready and the scheduler allowing it to begin execution.

3. Task Response Latency

The time from a task's triggering event or release until the task produces its required response. The precise measurement boundary must be defined for the application.

4. Communication Latency

The time required for information to travel from a sender to a receiver and become available for processing.

5. Context-Switching Latency

The time associated with saving one execution context and restoring another. Its contribution depends on the processor, RTOS port, and system conditions.

Latency Type Measurement
Interrupt Interrupt request to ISR start
Scheduling Task ready to task start
Task response Task release to required response
Communication Message transmission to availability at receiver
Context switching Time spent changing execution context

4. Interrupt Latency

Interrupt latency is an important timing parameter in embedded systems.

When a hardware peripheral generates an interrupt, the processor may need to complete or suspend current execution, recognize the interrupt, save required state, and begin executing the ISR.

Interrupt Response Sequence

+-----------------------------+
| Normal Program Execution    |
+-----------------------------+
              |
              v
+-----------------------------+
| Hardware Interrupt Request  |
+-----------------------------+
              |
              v
+-----------------------------+
| Interrupt Recognition       |
+-----------------------------+
              |
              v
+-----------------------------+
| Processor Context Handling  |
+-----------------------------+
              |
              v
+-----------------------------+
| ISR Execution Begins        |
+-----------------------------+

Factors Affecting Interrupt Latency

  • Interrupt masking or disabled interrupt periods.
  • Higher-priority interrupt activity.
  • Processor architecture.
  • Interrupt controller configuration.
  • Instruction completion and exception-entry behavior.
  • Memory access and bus delays.
A long critical section that disables interrupts can increase the worst-case interrupt latency of the system.

5. Scheduling Latency

Scheduling latency is the time between a task becoming ready and actually beginning execution.

A task can become ready because:

  • Its delay period expires.
  • A queue message arrives.
  • A semaphore becomes available.
  • An interrupt signals an event.
  • A higher-priority task is suspended or blocked.

Example

Task becomes ready: 10 ms
Task starts running: 12 ms

Scheduling Latency = 12 - 10
                   = 2 ms

Factors Affecting Scheduling Latency

  • Higher-priority ready tasks.
  • Interrupt processing.
  • Scheduler configuration.
  • Critical sections and scheduler suspension.
  • Kernel implementation and processor port.

A high-priority task may still experience delay due to interrupt activity or periods during which scheduling is prevented.

6. Execution Time vs Response Time

Execution time and response time are related but different timing measurements.

Execution Time

The time a task or code segment spends executing on the processor, according to the defined measurement boundary.

Response Time

The elapsed time between a task's release or triggering event and completion of its required response.

Illustrative Timeline

Task Release
    |
    v
    +------ Waiting ------+
                           |
                           v
                     Task Execution
                           |
                           v
                      Task Complete

Response Time =
Waiting Time + Execution Time
+ Other Included Interference

Example

Task Release Time       = 5 ms
Task Start Time         = 8 ms
Task Completion Time    = 14 ms

Waiting Time = 8 - 5
             = 3 ms

Execution Time = 14 - 8
               = 6 ms

Response Time = 14 - 5
              = 9 ms
Response-time analysis must account for all relevant delays, including blocking, higher-priority task interference, and interrupt activity. The exact terms depend on the system model.

7. What Is Determinism?

Determinism is the property of a system in which its behavior and timing can be predicted within specified operating conditions.

In real-time computing, deterministic behavior means that important operations complete within known and acceptable timing bounds.

Characteristics

  • Predictable interrupt response.
  • Bounded scheduling delay.
  • Known execution-time limits.
  • Controlled resource contention.
  • Predictable communication and synchronization behavior.
  • Ability to meet specified deadlines under defined assumptions.

Example

Suppose a control task must complete within 10 ms after receiving a sensor event.

Required Response Deadline = 10 ms

Measured Response Time:
7 ms

Deadline Margin:
10 - 7 = 3 ms

The measured result meets the deadline in that test. A real-time design must establish that the response-time bound remains within 10 ms under all relevant worst-case conditions.

8. Deterministic vs Non-Deterministic Behavior

Deterministic Behavior Less Predictable Behavior
Known timing bounds Unbounded or poorly understood delays
Controlled interrupt handling Uncontrolled interrupt interference
Bounded resource access Unpredictable resource contention
Analyzed task execution Unanalyzed execution paths
Deadline feasibility established Deadline behavior not established

Determinism does not mean that every operation always takes exactly the same amount of time. It means that its timing behavior is sufficiently predictable and bounded for the system requirements.

9. What Is Timing Jitter?

Jitter is the variation in the timing of an event or operation relative to its intended or nominal timing.

Example

A periodic task is intended to start every 10 ms.

Task Start Actual Start Time
10 ms
210.2 ms
319.8 ms
430.1 ms
540.3 ms

The task does not start at perfectly uniform intervals.

Common Causes of Jitter

  • Interrupt interference.
  • Variable execution time.
  • Higher-priority task activity.
  • Resource blocking.
  • Timer clock variation.
  • Communication delays.

10. Types of Jitter

1. Release Jitter

Variation in the time at which a task or event is released relative to its expected release time.

2. Start-Time Jitter

Variation in the actual start time of a task.

3. Completion-Time Jitter

Variation in the time at which a task finishes.

4. Communication Jitter

Variation in message transmission or arrival timing.

Peak-to-Peak Jitter

For a set of measured timing errors, peak-to-peak jitter is the difference between the maximum and minimum errors.

Maximum Timing Error = +0.4 ms
Minimum Timing Error = -0.2 ms

Peak-to-Peak Jitter =
0.4 - (-0.2)

= 0.6 ms

11. Worst-Case Execution Time (WCET)

Worst-Case Execution Time (WCET) is a safe upper bound on the execution time of a specified code segment under stated assumptions.

WCET is important because a real-time system must be analyzed using more than average execution time.

Example

Execution Measured Time
Run 12.1 ms
Run 22.4 ms
Run 32.2 ms
Run 42.8 ms
Run 52.5 ms

The largest observed execution time is 2.8 ms.

The largest observed measurement is not automatically the WCET. Unexecuted paths, cache or memory effects, interrupt interference, and other operating conditions may increase execution time. A defensible WCET bound requires appropriate analysis and assumptions.

12. Deadline and Response-Time Analysis

A real-time task is generally described using timing parameters such as:

  • Release time: Time at which the task becomes eligible for execution.
  • Execution time: Processor time required by the task.
  • Deadline: Latest required completion time.
  • Period: Interval between recurring releases.
  • Response time: Time from release to completion.

Example

Task Period   = 20 ms
Execution     = 5 ms
Response Time = 8 ms
Deadline      = 15 ms

Deadline Margin = 15 - 8
                = 7 ms

The task meets its deadline in this example. Complete schedulability analysis must also consider interference, blocking, release patterns, and other tasks.

13. Factors Affecting RTOS Latency

Processor Factors

  • Processor clock frequency.
  • Interrupt entry and return behavior.
  • Memory access time.
  • Bus contention and peripheral access.

RTOS Factors

  • Scheduler implementation.
  • Context-switch overhead.
  • Tick frequency and timer configuration.
  • Critical sections.
  • Interrupt masking.

Application Factors

  • Task priorities.
  • Execution time.
  • Blocking operations.
  • Shared resource access.
  • Queue and semaphore usage.
  • Interrupt service routine length.

14. Techniques to Reduce Latency

1. Keep ISRs Short

Perform only essential operations inside an ISR. Defer lengthy processing to an application task or background routine.

2. Use Appropriate Task Priorities

Assign priorities according to timing requirements, execution times, blocking behavior, and system-level analysis.

3. Reduce Critical Section Duration

Keep interrupt-disabled or scheduler-suspended sections as short as possible.

4. Avoid Unnecessary Blocking

Use suitable timeouts and communication mechanisms. Ensure high-priority tasks are not blocked indefinitely.

5. Optimize Application Code

Reduce unnecessary calculations and avoid long operations in time-critical execution paths.

6. Use Hardware Peripherals

Use timers, capture/compare units, DMA, and other hardware features when they provide more predictable timing than software polling.

7. Analyze Worst-Case Timing

Measure and analyze the worst-case execution and response behavior under relevant operating conditions.

15. Interrupt Latency vs Scheduling Latency

Parameter Interrupt Latency Scheduling Latency
Starting Event Interrupt request Task becomes ready
Ending Event ISR begins execution Task begins execution
Typical Influences Interrupt masking, priority, processor response Task priority, scheduler state, interrupt interference
Primary Concern Hardware event response Task execution response

16. FreeRTOS Latency and Timing Considerations

FreeRTOS provides scheduling and synchronization mechanisms, but application timing still depends on configuration and system design.

Important Considerations

  • Higher-priority ready tasks can preempt lower-priority tasks when preemption is enabled.
  • Interrupt processing can delay task execution.
  • Critical sections can delay interrupts or scheduling.
  • Queue and semaphore operations may cause task blocking or wakeups.
  • Context switching consumes processor time.
  • Tick frequency influences tick-based timing resolution.

Example: Task Execution Measurement

void ControlTask(void *pvParameters)
{
    for (;;)
    {
        uint32_t startTime;
        uint32_t endTime;

        startTime = Read_High_Resolution_Timer();

        Execute_Control_Algorithm();

        endTime = Read_High_Resolution_Timer();

        Record_Execution_Time(endTime - startTime);

        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

This is a conceptual example. The timer function must be implemented using a suitable hardware timer or measurement facility. The RTOS tick alone may not provide enough resolution for short execution-time measurements.

FreeRTOS scheduling behavior and interrupt-priority rules depend on the selected processor port. Do not apply Cortex-M-specific interrupt-priority configuration to an ARM7/LPC2129 system.

17. LPC2129 and Keil uVision Practical

The LPC2129 uses an ARM7TDMI-S processor and a Vectored Interrupt Controller (VIC).

Practical Exercises

  1. Configure Timer 0 to generate a periodic interrupt.
  2. Inspect the timer match and interrupt status registers.
  3. Observe the processor's transition into the interrupt handler.
  4. Record the execution of a short ISR.
  5. Compare a polling-based event-detection approach with an interrupt-driven approach.
  6. Inspect relevant ARM7 registers in the Keil debugger.

Timing Measurement Considerations

  • Use a hardware timer counter where available.
  • Define the exact start and end points of each measurement.
  • Repeat measurements under different conditions.
  • Distinguish simulated timing from physical hardware timing.
Keil simulator results can demonstrate register behavior and program flow, but they should not be treated as proof of physical interrupt latency or worst-case timing on a real LPC2129 board.

19. Lesson Summary

  • Latency is the delay between an event and its response.
  • Interrupt latency measures interrupt request to ISR start.
  • Scheduling latency measures task-ready to task-start time.
  • Execution time measures processor execution of a defined code segment.
  • Response time measures release to required completion.
  • Determinism means predictable and bounded system behavior.
  • Jitter is variation in event or task timing.
  • WCET is a safe upper execution-time bound under stated assumptions.
  • Interrupt interference and blocking can increase response time.
  • Short ISRs and bounded critical sections help improve responsiveness.
  • Real-time performance must be verified under worst-case conditions.
