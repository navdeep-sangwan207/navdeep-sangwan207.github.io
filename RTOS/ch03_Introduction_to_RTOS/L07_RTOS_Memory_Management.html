2. Introduction to Memory Management

Memory management is the process of allocating, using, tracking, and releasing memory resources in an embedded system.

An RTOS uses memory to maintain task information, task stacks, queues, semaphores, software timers, and other kernel objects.

Why Memory Management Is Important

  • Microcontrollers have limited RAM and Flash capacity.
  • Every task requires sufficient stack space.
  • Kernel objects require memory for their control structures and data.
  • Memory allocation failures can prevent application operations.
  • Stack overflow can corrupt program data and cause system failure.
  • Predictable memory usage is important for real-time reliability.
In an embedded real-time system, memory requirements should be estimated and verified before deployment. A system should not depend on unlimited memory availability.

3. Types of Memory in Embedded Systems

1. RAM – Random Access Memory

RAM is volatile memory used for temporary program data during execution.

  • Global and static variables.
  • Local variables and function call data.
  • Task stacks.
  • Heap memory.
  • Queues and kernel objects.

2. ROM – Read Only Memory

ROM is non-volatile memory. It retains stored information when power is removed.

3. Flash Memory

Flash is non-volatile memory commonly used to store embedded application firmware, constants, and configuration data.

4. EEPROM

EEPROM is non-volatile memory often used for small amounts of data that must be retained between power cycles.

Memory Volatile? Typical Purpose
RAM Yes Runtime data, stack, heap
ROM No Permanent stored instructions/data
Flash No Firmware and persistent data
EEPROM No Configuration and small persistent data

4. Program Memory and Data Memory

Embedded software uses different memory regions for instructions and data.

Program Memory

  • Stores executable instructions.
  • Usually implemented using Flash memory.
  • Contains program code and read-only constants.

Data Memory

  • Stores variables and runtime data.
  • Usually implemented using RAM.
  • Contains global variables, stacks, and heap regions.

Typical Embedded Memory Layout

+----------------------------+
|       Flash Memory         |
|                            |
|  Program Instructions      |
|  Constant Data             |
|  Initial Values for Data   |
+----------------------------+

+----------------------------+
|          RAM               |
|                            |
|  Initialized Variables     |
|  Zero-Initialized Data     |
|  Uninitialized Data        |
|  Heap                      |
|  Stack                     |
+----------------------------+

The exact layout depends on the processor, compiler, linker script, startup code, and memory configuration.

5. Stack Memory

Stack memory is used for function calls, local variables, saved registers, return addresses, and other temporary execution information.

Stack Operations

  • Function call pushes or saves required execution information.
  • Local variables may occupy stack space.
  • Function return restores the previous execution context.
  • Nested function calls increase stack usage.

Example

void Calculate(void)
{
    int a = 10;
    int b = 20;
    int result;

    result = a + b;
}

int main(void)
{
    Calculate();

    while (1)
    {
    }
}

The local variables may be stored in the function's stack frame, depending on compiler optimization and register allocation.

Stack Growth

On ARM7TDMI-S systems, the stack commonly grows toward lower memory addresses, depending on the selected stack convention and initialization. Different processor architectures may use different conventions.

Stack overflow occurs when stack usage exceeds the available stack region. It can overwrite other memory or cause unpredictable behavior.

6. Heap Memory

Heap memory is a memory region used for dynamic memory allocation during program execution.

In C, common dynamic allocation functions are:

  • malloc() – allocates a requested number of bytes.
  • calloc() – allocates memory and initializes it to zero.
  • realloc() – changes the size of an existing allocation.
  • free() – releases dynamically allocated memory.

Example

#include 
#include 

int main(void)
{
    int *ptr;

    ptr = (int *)malloc(5 * sizeof(int));

    if (ptr == NULL)
    {
        printf("Memory allocation failed\n");
        return 1;
    }

    for (int i = 0; i < 5; i++)
    {
        ptr[i] = (i + 1) * 10;
    }

    for (int i = 0; i < 5; i++)
    {
        printf("%d ", ptr[i]);
    }

    free(ptr);
    ptr = NULL;

    return 0;
}

Expected Output

10 20 30 40 50

This example demonstrates standard C heap allocation. It is not a FreeRTOS kernel allocation example.

7. How an RTOS Uses Memory

An RTOS requires memory for its kernel data structures and application tasks.

Major Memory Consumers

Component Memory Requirement
RTOS Kernel Kernel data structures and scheduler state
Task Control Block Task priority, state, stack information, and other task data
Task Stack Local data, saved context, function calls
Queue Queue control data and storage for messages
Semaphore Synchronization object data
Software Timer Timer control data and associated information

Conceptual Memory Layout

+--------------------------------+
|       Application Code         |
|          (Flash)               |
+--------------------------------+
|       RTOS Kernel Code         |
|          (Flash)               |
+--------------------------------+

+--------------------------------+
| Application Global Variables   |
+--------------------------------+
| RTOS Kernel Data               |
+--------------------------------+
| Task 1 Stack                   |
+--------------------------------+
| Task 2 Stack                   |
+--------------------------------+
| Queue Storage                  |
+--------------------------------+
| Semaphore / Timer Objects      |
+--------------------------------+
| Dynamic Allocation Heap        |
+--------------------------------+

This is a conceptual layout. Actual placement and allocation depend on the linker, compiler, RTOS port, and memory allocator.

8. Task Stack Management

Every independently executing RTOS task normally requires its own stack.

The task stack stores information needed when the task executes, including:

  • Local variables.
  • Function call frames.
  • Return addresses.
  • Saved processor registers.
  • Context information required by the RTOS port.

Example: Two Task Stacks

+-----------------------------+
| Task A Stack                |
|                             |
| Local Variables             |
| Function Call Frames        |
| Saved Context               |
+-----------------------------+

+-----------------------------+
| Task B Stack                |
|                             |
| Local Variables             |
| Function Call Frames        |
| Saved Context               |
+-----------------------------+

Important Stack Considerations

  • Estimate the maximum stack requirement for each task.
  • Consider nested function calls.
  • Consider interrupt and exception stack usage separately where applicable.
  • Account for compiler-generated stack usage.
  • Monitor stack high-water marks when supported.

9. Static Memory Allocation

Static allocation reserves memory before runtime or uses memory whose lifetime is predetermined.

Example

static int sensorBuffer[20];

void Application(void)
{
    sensorBuffer[0] = 100;
}

The array has a fixed size and exists for the lifetime of the program.

Advantages

  • Predictable memory usage.
  • No runtime allocation failure for the reserved object.
  • No heap fragmentation caused by that allocation.
  • Suitable for systems requiring deterministic resource planning.

Disadvantages

  • Memory size must be selected in advance.
  • Reserved memory may remain unused.
  • Changing resource requirements may require rebuilding the firmware.

10. Dynamic Memory Allocation

Dynamic allocation reserves memory during program execution according to runtime requirements.

In FreeRTOS, dynamic allocation is commonly performed through kernel memory allocation functions such as pvPortMalloc() and vPortFree(), subject to the selected heap implementation.

Conceptual Example

void *memoryBlock;

memoryBlock = pvPortMalloc(100);

if (memoryBlock != NULL)
{
    /* Use the allocated memory. */

    vPortFree(memoryBlock);
}

This example illustrates the FreeRTOS allocation interface. The application must include the appropriate FreeRTOS headers and use a configured heap implementation that supports the required operations.

Advantages

  • Memory can be allocated when required.
  • Useful when the number or size of objects varies.
  • Can avoid reserving large fixed buffers unnecessarily.

Disadvantages

  • Allocation can fail.
  • Allocation and release may take variable time.
  • Repeated allocation and release can cause fragmentation.
  • Memory leaks are possible if allocated blocks are not released.

11. Static vs Dynamic Memory Allocation

Parameter Static Allocation Dynamic Allocation
Allocation Time Before or at program initialization During runtime
Memory Size Predetermined Can vary at runtime
Predictability Generally higher Depends on allocator and usage
Fragmentation No heap fragmentation from fixed objects Possible
Allocation Failure Not during allocation of an already reserved object Possible at runtime
Flexibility Limited Higher
Typical Use Fixed tasks and buffers Variable runtime objects

12. FreeRTOS Memory Allocation

FreeRTOS provides configurable memory allocation mechanisms. The selected heap implementation determines how memory is allocated and released.

Common FreeRTOS Heap Implementations

Heap General Characteristics
heap_1 Allocates memory but does not support freeing allocated blocks.
heap_2 Supports allocation and freeing but does not coalesce adjacent free blocks.
heap_3 Wraps the C library's malloc() and free() functions.
heap_4 Supports allocation, freeing, and coalescing adjacent free blocks.
heap_5 Supports allocation across multiple non-contiguous memory regions and coalescing within regions.
FreeRTOS heap files are alternative implementations. A project normally selects one appropriate heap implementation rather than combining all five.

Common Allocation Functions

  • pvPortMalloc() – allocates memory from the configured FreeRTOS heap.
  • vPortFree() – releases memory when supported by the selected heap.
  • xPortGetFreeHeapSize() – reports free heap space where implemented.
  • xPortGetMinimumEverFreeHeapSize() – reports the minimum free heap recorded where implemented.

13. Memory Fragmentation

Memory fragmentation occurs when free memory is divided into separate blocks, making it difficult to satisfy a large allocation request.

Example

Initial Heap:
+--------------------------------------+
|             Free Memory              |
+--------------------------------------+

After Allocations:
+----------+----------+----------+-----+
| Used A   | Free     | Used B   |Free |
+----------+----------+----------+-----+

After More Allocations:
+----------+------+----------+----+----+
| Used A   |Free  | Used B   |Free|Used|
+----------+------+----------+----+----+

There may be enough total free memory, but not enough contiguous free space for a particular allocation.

Types of Fragmentation

  • External fragmentation: Free memory is split into separated blocks.
  • Internal fragmentation: Allocated blocks contain unused space due to allocation size or alignment rules.

Ways to Reduce Fragmentation

  • Prefer static allocation for fixed-size objects.
  • Avoid frequent allocation and release of different block sizes.
  • Use fixed-size memory pools where suitable.
  • Choose an appropriate allocator.
  • Monitor allocation failures and available heap.

14. Stack Overflow Detection

Stack overflow occurs when a task or execution context exceeds its assigned stack capacity.

Common Causes

  • Insufficient task stack size.
  • Deeply nested function calls.
  • Large local arrays.
  • Recursive function calls.
  • Excessive interrupt nesting or exception stack usage.

Possible Symptoms

  • Unexpected program crashes.
  • Corrupted variables.
  • Unexpected task behavior.
  • Processor exceptions or system resets.

FreeRTOS Stack Monitoring

UBaseType_t remainingWords;

remainingWords = uxTaskGetStackHighWaterMark(NULL);

This function reports the minimum remaining stack space observed for a task, in stack words, where supported by the port and configuration.

Stack high-water-mark measurements are useful for testing, but they do not mathematically prove that a task can never overflow. Test worst-case execution paths and account for compiler and interrupt behavior.

15. Memory Protection

Memory protection prevents software components from accessing memory regions that they are not authorized to use.

Purpose

  • Prevent one task from corrupting another task's memory.
  • Protect kernel data structures.
  • Restrict access to sensitive memory regions.
  • Improve fault isolation and system reliability.

Hardware Support

  • MPU: Memory Protection Unit, which provides configurable memory access permissions and regions.
  • MMU: Memory Management Unit, commonly used for virtual memory and address translation in more capable systems.

Not every microcontroller or RTOS provides memory isolation between tasks. Protection depends on processor hardware, kernel design, port support, and configuration.

16. Memory Management Considerations for LPC2129

The LPC2129 uses an ARM7TDMI-S core. When developing embedded C applications for this microcontroller, memory management requires attention to its available RAM and Flash resources.

Practical Considerations

  • Check the exact memory map and device datasheet.
  • Inspect the linker map file after compilation.
  • Estimate global and static variable usage.
  • Estimate stack requirements for functions and interrupts.
  • Avoid unnecessarily large local arrays.
  • Check the startup code and stack initialization.
  • Use Keil debugger memory and register views to inspect program state.
Keil uVision simulator exercises can help inspect memory addresses and program execution. They do not establish that a particular FreeRTOS ARM7 port is available or compatible. Verify the port and toolchain separately before building an RTOS application for LPC2129.

17. Practical Memory Calculation

Example 1: Task Stack Memory

Suppose an application has three tasks, each with a stack allocation of 256 stack words. If the stack word size is 4 bytes:

Total task stack memory:

Number of tasks = 3
Stack per task  = 256 words
Word size       = 4 bytes

Total = 3 × 256 × 4
      = 3072 bytes
      = 3 KB

This calculation excludes task control blocks, kernel objects, interrupt stacks, application globals, and other memory requirements.

Example 2: Queue Storage

Suppose a queue stores 10 messages, each 4 bytes long.

Queue length = 10
Item size    = 4 bytes

Storage required = 10 × 4
                 = 40 bytes

The queue control structure requires additional memory.

Example 3: Total RAM Budget

Task stacks             = 3072 bytes
Queue storage          =   40 bytes
Global variables       =  500 bytes
Other kernel objects   =  400 bytes
Application buffers    = 1000 bytes

Estimated total        = 5012 bytes

This is an illustrative budget. Actual RAM usage must be verified from the linker map, RTOS configuration, and runtime measurements.

18. Best Practices for RTOS Memory Management

  1. Estimate memory requirements before implementation.
  2. Use static allocation when predictable resource usage is important.
  3. Allocate adequate stack space for every task.
  4. Avoid large local arrays in frequently called functions.
  5. Check every dynamic allocation result.
  6. Release allocated memory when it is no longer required.
  7. Monitor heap usage and task stack margins.
  8. Use memory pools for repeated fixed-size allocations when appropriate.
  9. Inspect linker map files and compiler memory reports.
  10. Test memory usage under worst-case operating conditions.

19. Lesson Summary

  • Memory management controls allocation and use of memory resources.
  • RAM stores runtime data, stacks, and heap information.
  • Flash stores firmware and persistent information.
  • Each RTOS task normally requires its own stack.
  • Static allocation reserves fixed memory resources.
  • Dynamic allocation provides runtime flexibility.
  • FreeRTOS provides configurable heap implementations.
  • Fragmentation can prevent allocation despite sufficient total free memory.
  • Stack overflow can cause unpredictable system behavior.
  • Memory protection depends on processor hardware and RTOS support.
  • Memory budgeting and testing are essential for reliable embedded systems.
