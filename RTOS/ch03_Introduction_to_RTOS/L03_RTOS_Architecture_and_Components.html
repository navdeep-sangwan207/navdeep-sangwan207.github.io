2. Introduction to RTOS Architecture

RTOS architecture describes how the kernel, application tasks, hardware interfaces, and supporting services are organized to execute real-time applications.

An RTOS provides a structured environment for managing multiple tasks and coordinating access to processor and peripheral resources.

Major Architectural Layers

  1. Application Layer: Contains application tasks and business logic.
  2. RTOS API Layer: Provides functions through which application code accesses kernel services.
  3. Kernel Layer: Contains task management, scheduling, synchronization, and time management.
  4. Hardware Abstraction and Drivers: Provide interfaces to processor peripherals and external devices.
  5. Hardware Layer: Contains CPU, memory, timers, communication interfaces, and GPIO.
The exact architectural layers vary between RTOS implementations. A small RTOS may have a compact kernel with application-specific drivers rather than a separate formal hardware-abstraction layer.

4. RTOS Kernel

The RTOS kernel is the central software component responsible for managing tasks and providing essential operating-system services.

Main Responsibilities

  • Task creation and deletion.
  • Task scheduling and priority management.
  • Task state management.
  • Context switching.
  • Synchronization.
  • Inter-task communication.
  • Time and delay management.
  • Memory management where provided.

Kernel vs Application

RTOS Kernel Application
Manages task scheduling. Defines application tasks.
Provides queue and semaphore services. Uses queues and semaphores to exchange information.
Provides timing services. Uses delays and timers for application operations.
Manages task states. Implements application functionality.

5. Task Management Component

Task management is responsible for controlling the lifecycle and execution of tasks.

Important Task Operations

  • Task creation.
  • Task deletion.
  • Task suspension.
  • Task resumption.
  • Task delay.
  • Task priority assignment.
  • Task state transitions.

Task States

State Description
Running The task is currently executing on the CPU.
Ready The task can execute but is waiting for CPU allocation.
Blocked The task is waiting for an event, resource, or timeout.
Suspended The task has been explicitly suspended and is not eligible for execution.

Task state details and terminology can vary between RTOS implementations.

6. Task Scheduler

The scheduler is the kernel component that selects the next task to receive CPU time.

Scheduling Responsibilities

  • Maintain ready tasks.
  • Consider task priorities.
  • Select an eligible task.
  • Support preemption when configured.
  • Coordinate task blocking and waking.
  • Support time slicing where configured.

Example

Assume three tasks are ready:

  • Task A: Priority 3.
  • Task B: Priority 2.
  • Task C: Priority 1.

In a fixed-priority scheduler that selects the highest-priority ready task, Task A is selected first. If Task A blocks, Task B may execute next.

Scheduling policy, preemption, equal-priority time slicing, and other behavior depend on the RTOS and its configuration.

7. Dispatcher and Context Switching

The dispatcher is the part of the operating-system implementation responsible for transferring CPU execution to the task selected by the scheduler.

Context Switching

A context switch occurs when the processor stops executing one task and begins executing another by saving and restoring the necessary execution context.

Typical Context-Switch Operations

  1. Save the outgoing task's processor context.
  2. Update the outgoing task's state.
  3. Select the next eligible task.
  4. Restore the incoming task's processor context.
  5. Resume execution of the selected task.

Processor Context May Include

  • General-purpose CPU registers.
  • Stack pointer.
  • Program counter or return address.
  • Status register.
  • Other architecture-specific state.

Context switching allows multiple tasks to share a single processor, but it introduces execution overhead.

8. Task Control Block (TCB)

A Task Control Block (TCB) is a kernel data structure that stores information required to manage an individual task.

Typical TCB Information

  • Task stack pointer.
  • Task priority.
  • Task state or scheduling information.
  • Task identifier or handle information.
  • Scheduling list or queue links.
  • Other task-specific kernel metadata.

Conceptual TCB Structure

+-----------------------------+
|       Task Control Block    |
+-----------------------------+
| Task Identifier             |
| Task Priority               |
| Stack Pointer               |
| Task State                  |
| Scheduling Information      |
| Delay / Event Information   |
| Other Kernel Metadata       |
+-----------------------------+

The actual fields and structure layout depend on the RTOS implementation and processor port.

9. Task Stack Management

Each task normally has its own stack to store function-call information and execution context.

Stack Stores

  • Local variables.
  • Function return addresses.
  • Saved registers.
  • Processor context during task switching.
  • Other temporary execution data.

Why Is Stack Management Important?

  • Every task needs sufficient stack space.
  • Stack overflow can corrupt memory.
  • Large local arrays can consume significant stack space.
  • Deep function calls increase stack usage.
  • Interrupt nesting can require additional stack space depending on the architecture and implementation.
Stack sizes should be selected and verified using appropriate analysis and runtime checks. A task working in a short test does not prove that its stack is large enough for every execution path.

10. Interrupt Management Component

Interrupt management allows an RTOS-based application to respond to hardware and software events.

Common Interrupt Sources

  • Timer interrupts.
  • UART receive and transmit events.
  • External GPIO interrupts.
  • ADC conversion completion.
  • Communication peripheral events.

Role of an ISR

An Interrupt Service Routine (ISR) executes in response to an interrupt event.

In an RTOS application, an ISR may:

  • Acknowledge the interrupt source.
  • Read or store essential data.
  • Signal a task using an ISR-safe kernel API.
  • Request a context switch when appropriate and supported.
ISRs should generally be short. Do not call ordinary task-context RTOS APIs from an ISR unless the specific API is documented as ISR-safe. Long processing should normally be deferred to a task.

11. Synchronization Component

Synchronization coordinates task execution and protects shared resources.

Common Synchronization Mechanisms

11.1 Semaphore

A semaphore can be used to signal events or coordinate access to limited resources.

11.2 Mutex

A mutex provides mutual exclusion when multiple tasks need to access a shared resource.

11.3 Critical Section

A critical section is a region of code that must be protected against specified forms of concurrent access or interference.

Mechanism Typical Purpose
Binary Semaphore Event signaling or simple synchronization
Counting Semaphore Counting available resources or events
Mutex Mutual exclusion for shared resources
Critical Section Protect a sensitive region of code

12. Inter-Task Communication Component

Inter-task communication allows tasks to exchange information and coordinate their work.

Common Mechanisms

  • Queues: Transfer data between tasks.
  • Task Notifications: Signal or communicate with a task.
  • Event Groups: Coordinate multiple event conditions.
  • Mailboxes: Commonly used to describe message-passing mechanisms.
  • Shared Memory: Allows tasks to access common data with appropriate synchronization.

Example: Sensor-to-Control Communication

+------------------+
|    Sensor Task   |
+------------------+
         |
         | Sensor Data
         v
+------------------+
|       Queue      |
+------------------+
         |
         | Received Data
         v
+------------------+
|   Control Task   |
+------------------+
         |
         v
+------------------+
| Control Output   |
+------------------+

The queue separates sensor acquisition from control processing and allows the tasks to operate independently.

13. Time Management Component

RTOS time management provides services for delays, periodic execution, timeouts, and software timers.

Important Time Services

  • System tick generation.
  • Task delays.
  • Periodic task timing.
  • Blocking timeouts.
  • Software timers.
  • Time measurement.

System Tick

Many RTOS implementations use a periodic timer interrupt called the system tick to maintain kernel time and process time-related events.

For example, if the tick frequency is 1000 Hz:

Tick period = 1 / 1000 = 0.001 seconds = 1 millisecond.

Not every RTOS uses only a periodic tick. Some systems support tickless operation or other timer arrangements to reduce power consumption and improve timing flexibility.

14. Memory Management Component

Memory management controls the allocation and use of memory required by tasks and kernel objects.

Memory Requirements

  • Task stacks.
  • Task control blocks.
  • Queue storage.
  • Semaphore and mutex objects.
  • Software timer structures.
  • Kernel data structures.

Memory Allocation Approaches

  • Static allocation: Memory is reserved at compile time or provided by the application.
  • Dynamic allocation: Memory is obtained at runtime through an allocator.

Static allocation can provide predictable memory usage, while dynamic allocation offers flexibility but requires careful control of fragmentation and allocation failures.

15. Hardware Abstraction and Device Drivers

Device drivers provide software interfaces for controlling hardware peripherals.

Examples

  • UART driver.
  • GPIO driver.
  • ADC driver.
  • SPI driver.
  • I2C driver.
  • Timer driver.
  • CAN driver.

Application tasks can use driver functions instead of directly managing every hardware register.

Example: UART Driver Interface

void UART_Init(void);
int UART_SendByte(unsigned char data);
int UART_ReceiveByte(unsigned char *data);

These are illustrative driver interfaces, not predefined RTOS APIs. The driver implementation must be designed for the target microcontroller and its interrupt and concurrency requirements.

16. How RTOS Components Work Together

Consider a temperature-monitoring application.

  1. A hardware timer generates a periodic event.
  2. The interrupt handler acknowledges the event.
  3. The ISR signals the Sensor Task.
  4. The Sensor Task reads the ADC through the driver.
  5. The Sensor Task sends the measurement to a queue.
  6. The Control Task receives the measurement.
  7. The Control Task checks the temperature threshold.
  8. The Display Task updates the LCD.
  9. The Communication Task transmits the measurement through UART.

During this process, the scheduler selects ready tasks, synchronization services coordinate access, and time management handles periodic operations and timeouts.

17. FreeRTOS Architecture Overview

FreeRTOS is a small-footprint real-time kernel designed for embedded applications.

Core Kernel Facilities

  • Task creation and management.
  • Priority-based scheduling.
  • Queues.
  • Semaphores and mutexes.
  • Task notifications.
  • Software timers.
  • Memory allocation options.

Typical FreeRTOS Application Flow

int main(void)
{
    Hardware_Init();

    xTaskCreate(
        SensorTask,
        "Sensor",
        SENSOR_STACK_SIZE,
        NULL,
        SENSOR_PRIORITY,
        NULL
    );

    xTaskCreate(
        ControlTask,
        "Control",
        CONTROL_STACK_SIZE,
        NULL,
        CONTROL_PRIORITY,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
        // Normally not reached if the
        // scheduler starts successfully.
    }
}

This is an illustrative FreeRTOS application structure. It requires the FreeRTOS headers, kernel source, a supported processor port, valid task functions, and an appropriate configuration file.
