2. What Is an RTOS?

A Real-Time Operating System (RTOS) is an operating system designed to manage tasks and system resources while supporting predictable responses to time-critical events.

Unlike systems that primarily optimize overall throughput or user experience, an RTOS is designed to support applications where the timing of operations is an important part of correctness.

Definition: An RTOS is an operating system that provides task scheduling, synchronization, communication, and timing services to help an application meet its real-time requirements.

Example: Industrial Temperature Control

Consider a temperature-monitoring controller that performs these operations:

  1. Read temperature from a sensor.
  2. Compare the measured temperature with a threshold.
  3. Control a cooling fan.
  4. Update the display.
  5. Transmit measurement data through UART.

These operations may have different priorities and timing requirements. A critical temperature-control operation should not be delayed unnecessarily by a lower-priority display update.

3. Why Do We Need an RTOS?

In a simple embedded system, a program may execute all operations inside an infinite loop. This is called a superloop or bare-metal programming approach.

Bare-Metal Superloop Example

#include <stdint.h>

int main(void)
{
    System_Init();

    while (1)
    {
        Read_Temperature();
        Update_Display();
        Check_Alarm();
        Send_UART_Data();
        Control_Fan();
    }
}

In this approach, the operations execute sequentially. If one function takes too long, subsequent operations may be delayed.

Limitations of a Superloop

  • All operations share the same main execution flow.
  • Long-running functions can delay other activities.
  • Managing many independent operations becomes difficult.
  • Timing behavior can become difficult to analyze.
  • Adding new functionality may make the program more complex.

How an RTOS Helps

An RTOS divides application functionality into separate tasks and manages their execution using a scheduler.

For example:

  • Task 1: Sensor monitoring.
  • Task 2: Motor or fan control.
  • Task 3: Display updating.
  • Task 4: UART communication.
The RTOS does not make every task execute simultaneously on a single-core processor. It schedules tasks so they can make progress according to their priorities and timing requirements.

4. Basic Architecture of an RTOS

An RTOS generally contains a kernel and a set of services used by embedded applications.

Main Components

  1. RTOS Kernel: Core software responsible for task management and scheduling.
  2. Task Scheduler: Selects which ready task should execute.
  3. Task Management: Creates, deletes, suspends, and resumes tasks.
  4. Interrupt Management: Handles hardware and software events.
  5. Synchronization: Coordinates access to shared resources.
  6. Inter-Task Communication: Exchanges information between tasks.
  7. Time Management: Provides delays, timeouts, and software timers.
  8. Memory Management: Manages task stacks and kernel memory allocations.

Conceptual RTOS Architecture

+--------------------------------------+
|          Embedded Application        |
+--------------------------------------+
| Task 1 | Task 2 | Task 3 | Task 4     |
+--------------------------------------+
|       RTOS Kernel and Scheduler      |
+--------------------------------------+
| Queues | Semaphores | Mutexes | Timers|
+--------------------------------------+
| Interrupt and Hardware Abstraction   |
+--------------------------------------+
|              Hardware                |
| CPU | RAM | ROM | Timers | UART | GPIO|
+--------------------------------------+

This is a conceptual architecture. The exact organization and services depend on the RTOS implementation.

5. Task-Based Programming in RTOS

A task is an independently scheduled unit of execution managed by the RTOS kernel.

Each task typically has:

  • A task function or entry point.
  • A separate execution stack.
  • A priority.
  • A task state.
  • Saved processor context when it is not running.

Example: Embedded Monitoring System

Task Responsibility Illustrative Priority
Sensor Task Read sensor measurements High
Control Task Make control decisions Highest
Communication Task Transmit data using UART Medium
Display Task Update LCD information Low

The priority assignments are illustrative. Actual priorities must be determined from task deadlines, execution times, blocking, and system requirements.

6. Task Scheduling in RTOS

The scheduler determines which ready task receives CPU time.

Common Scheduling Approaches

  • Preemptive scheduling: A higher-priority ready task can interrupt the execution of a lower-priority task.
  • Cooperative scheduling: A running task generally continues until it yields, blocks, or otherwise gives up the CPU.
  • Priority-based scheduling: Tasks are selected according to their assigned priorities.
  • Round-robin scheduling: Tasks of equal priority may share CPU time in rotation.

Example

Assume three tasks are ready:

  • Task A: Priority 3.
  • Task B: Priority 2.
  • Task C: Priority 1.

If the scheduler uses fixed-priority preemptive scheduling and all three tasks are ready, Task A receives CPU time first. When Task A blocks or becomes suspended, the scheduler can select Task B.

A higher priority does not automatically guarantee that every deadline will be met. Execution time, blocking, interrupt interference, scheduling policy, and resource contention must also be considered.

7. Determinism and Predictability

Determinism in real-time systems refers to the ability to provide predictable timing behavior under specified operating conditions.

For example, a controller may be required to respond to a sensor event within a specified maximum time.

Important Timing Parameters

  • Response time: Time from an event or task release until the required response is completed.
  • Execution time: CPU time required by a task to execute.
  • Deadline: Latest time by which the required operation must finish.
  • Latency: Delay between an event and the start of its associated response.
  • Jitter: Variation in the timing of an event or task execution.

Example

A control task is released every 10 milliseconds and must complete within 5 milliseconds of each release.

Its timing requirement includes:

  • Period: 10 ms.
  • Relative deadline: 5 ms.
  • Execution time: Must be measured or bounded for the target system.

The task's execution time alone does not establish whether it meets its deadline. Scheduling delays and interference must also be considered.

11. RTOS vs Bare-Metal Programming vs General-Purpose OS

Feature Bare Metal RTOS General-Purpose OS
Kernel No OS kernel RTOS kernel General-purpose kernel
Task management Application-defined Kernel-managed tasks Process and thread management
Scheduling Application-controlled Real-time scheduling policies General-purpose scheduling policies
Memory requirements Often low Often low to moderate Usually higher
Typical use Simple microcontroller firmware Time-sensitive embedded applications Desktop and server computing
A general-purpose OS can also have real-time extensions or configurations. The distinction is based on the timing guarantees and system design, not simply the operating-system name.

12. RTOS in the LPC2129 Embedded System

The LPC2129 microcontroller is based on the ARM7TDMI-S processor core. Its peripherals can be used to build embedded applications that have multiple activities.

Example Application

Consider an LPC2129-based monitoring system with:

  • ADC for reading analog sensor values.
  • UART0 for serial communication.
  • Timer for periodic operations.
  • GPIO for control signals.
  • LCD interface for displaying measurements.

Possible Software Tasks

  1. Sensor acquisition.
  2. Measurement processing.
  3. Control output management.
  4. UART data transmission.
  5. LCD display updating.

These functions could be organized as separate tasks in a suitable RTOS environment or implemented in a bare-metal superloop.

Platform limitation: The LPC2129 is an ARM7-based microcontroller. Do not assume that a current FreeRTOS port or a particular Keil simulator configuration supports it without verifying the exact port, compiler, startup code, interrupt handling, and build environment. Register inspection in Keil alone does not demonstrate a working RTOS port.

13. Advantages and Limitations of RTOS

Advantages

  • Organizes complex applications into independent tasks.
  • Supports priority-based scheduling.
  • Provides synchronization and communication services.
  • Supports event-driven embedded applications.
  • Can provide predictable timing when the complete system is correctly designed and analyzed.
  • Improves software modularity and maintainability.

Limitations

  • Requires additional memory for the kernel and task stacks.
  • Introduces context-switching overhead.
  • Requires careful synchronization.
  • Priority inversion and deadlocks must be managed.
  • Debugging concurrent execution can be difficult.
  • An RTOS alone cannot guarantee that all deadlines will be met.

  • Applications can be divided into independently scheduled tasks.

  • RTOS services include queues, semaphores, mutexes, timers, and memory management.
  • Determinism and bounded response time are important real-time design goals.
