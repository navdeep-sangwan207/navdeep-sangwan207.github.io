2. Introduction to RTOS Applications

A Real-Time Operating System (RTOS) is used in systems where software must respond to events within defined timing constraints.

RTOS-based systems are commonly found in:

  • Industrial automation and control.
  • Automotive electronics.
  • Medical equipment.
  • Consumer electronics.
  • Robotics and automation.
  • Telecommunication equipment.
  • Aerospace and defense systems.
  • IoT and connected devices.
The main reason to use an RTOS is to organize concurrent activities and provide predictable timing behavior that can be analyzed against application deadlines.

3. Industrial Automation Applications

11. Common RTOS Examples

Several operating systems are used in embedded and real-time development.

RTOS Typical Characteristics
FreeRTOS Small embedded kernel, task scheduling, queues, semaphores and timers.
Zephyr Open-source RTOS with a broader embedded ecosystem, device drivers and connectivity support.
ThreadX / Azure RTOS Embedded RTOS technology; current product and support arrangements should be checked before selection.
QNX Neutrino Microkernel-based real-time operating system used in demanding embedded applications.
VxWorks Commercial real-time operating system used in specialized embedded and mission-critical systems.
RTEMS Open-source real-time operating system used in embedded and specialized computing environments.
PREEMPT_RT Linux Linux kernel real-time preemption capabilities for suitable real-time workloads.

These systems differ in licensing, hardware support, kernel architecture, certification options, ecosystem, and development tools.

12. Why RTOS Selection Is Important

Selecting an RTOS is an important part of embedded system design.

An unsuitable RTOS may cause:

  • Failure to meet task deadlines.
  • Excessive RAM or Flash consumption.
  • Unsupported processor or peripheral interfaces.
  • Development and debugging difficulties.
  • Licensing or maintenance problems.
  • Inadequate safety or security capabilities.
  • Long-term product support problems.
RTOS selection should begin with system requirements, not with the popularity of a particular operating system.

13. RTOS Selection Criteria

1. Processor and Hardware Support

  • Supported processor architecture.
  • Available processor port.
  • Supported compiler and toolchain.
  • Interrupt controller compatibility.
  • Peripheral and board support.

2. Timing Performance

  • Interrupt latency.
  • Scheduling latency.
  • Context-switch overhead.
  • Timer resolution.
  • Worst-case response-time requirements.

3. Memory Requirements

  • Kernel code size.
  • RAM requirement.
  • Task stack requirements.
  • Heap and memory-management support.
  • Static and dynamic allocation options.

4. Scheduling Features

  • Preemptive scheduling.
  • Priority-based scheduling.
  • Time slicing.
  • Task management.
  • Timer and timeout services.

5. Communication and Synchronization

  • Queues and message passing.
  • Binary and counting semaphores.
  • Mutexes and priority inheritance.
  • Event groups or event flags.
  • ISR-to-task communication.

6. Development Tools

  • Compiler and linker support.
  • Debugger compatibility.
  • Trace and profiling tools.
  • Simulator or emulator support.
  • Documentation and example projects.

7. Licensing and Cost

  • Open-source or commercial licensing.
  • Distribution and modification conditions.
  • Commercial support cost.
  • Certification and maintenance costs.
  • Product deployment restrictions.

8. Safety and Reliability

  • Fault handling mechanisms.
  • Memory protection where required.
  • Watchdog integration.
  • Safety documentation and certification evidence.
  • Long-term maintenance and security updates.

14. Hardware Requirements for RTOS

The hardware platform must provide sufficient resources for the selected RTOS and application.

Hardware Resource Purpose
CPU Executes tasks, interrupts and kernel operations.
RAM Stores task stacks, data and runtime objects.
Flash / ROM Stores firmware and RTOS code.
Hardware Timer Supports system tick and time measurement.
Interrupt Controller Manages processor interrupt requests and priorities.
Communication Interfaces UART, SPI, I2C, CAN, Ethernet and other interfaces.

Memory and processor requirements must be estimated using the actual application configuration rather than a generic minimum figure.

15. Software and Development Requirements

Before selecting an RTOS, verify the complete development environment.

  • Supported compiler version.
  • RTOS kernel source and processor port.
  • Board Support Package (BSP), where applicable.
  • Startup code and linker configuration.
  • Peripheral driver availability.
  • Debugging and trace support.
  • Build system and dependency management.
  • Documentation and technical support.

16. RTOS vs Bare-Metal Selection

Not every embedded application needs an RTOS.

Requirement Bare-Metal Approach RTOS Approach
Simple periodic operation Often suitable May be unnecessary
Small number of activities Often suitable Depends on complexity
Many independent tasks Can become complex Often useful
Task priorities Must be implemented manually Provided by scheduler
Inter-task communication Application-designed Kernel mechanisms available
Resource overhead Usually lower Additional kernel resources required
A well-designed bare-metal system can meet hard real-time requirements. An RTOS is useful when its scheduling and coordination services justify the additional complexity and resource usage.

18. FreeRTOS Selection Considerations

FreeRTOS is a widely used embedded RTOS kernel. It can be considered when the target processor and toolchain have a supported port.

Typical Reasons to Consider FreeRTOS

  • Small embedded kernel requirements.
  • Task-based application architecture.
  • Priority-based preemptive scheduling.
  • Queues, semaphores and mutexes.
  • Software timers.
  • Static and dynamic memory allocation options.
  • Availability of source code and documentation.

Important Checks

  • Confirm the processor port is available and maintained.
  • Check the compiler and linker configuration.
  • Verify interrupt and timer integration.
  • Estimate stack and heap requirements.
  • Check required peripheral drivers separately.
  • Test actual timing behavior on the target hardware.

19. LPC2129 and Keil uVision Considerations

The LPC2129 uses an ARM7TDMI-S core. It is useful for learning microcontroller architecture, peripheral programming, interrupts and timer operation.

Relevant Hardware Resources

  • ARM7TDMI-S processor core.
  • Vectored Interrupt Controller (VIC).
  • Timer 0 and Timer 1.
  • UART0 and UART1.
  • I2C, SPI and CAN peripherals.
  • GPIO and ADC peripherals.

Before Attempting FreeRTOS on LPC2129

  1. Verify that a compatible ARM7TDMI-S FreeRTOS port is available for the chosen version.
  2. Check whether the compiler and Keil toolchain are supported by that port.
  3. Verify timer tick integration and context-switch assembly code.
  4. Check interrupt nesting and ISR-safe API requirements.
  5. Confirm memory requirements and linker settings.
Do not assume that FreeRTOS supports LPC2129 simply because it supports other ARM processors. Cortex-M ports and their interrupt-priority configuration cannot be directly applied to the ARM7TDMI-S architecture.

With Keil uVision simulator-only practice, you can study ARM7 register behavior, timer configuration, interrupt flow and bare-metal programming. This does not establish actual RTOS port compatibility or physical timing performance.

21. Lesson Summary

  • RTOS is used in systems with timing-sensitive activities.
  • Applications include industrial automation, automotive, medical, robotics and IoT.
  • Different RTOS products support different processors and toolchains.
  • Hardware compatibility is a primary selection criterion.
  • Latency, scheduling and response-time requirements must be evaluated.
  • RAM, Flash and CPU resources must be sufficient.
  • Queues, semaphores, mutexes and timers support task coordination.
  • Licensing, security, safety and maintenance affect product selection.
  • Bare-metal programming may be preferable for simple applications.
  • FreeRTOS suitability must be checked for the exact processor port.
  • Final RTOS selection requires testing and validation on the target platform.
