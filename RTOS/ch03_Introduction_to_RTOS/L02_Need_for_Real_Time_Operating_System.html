After completing this lesson, you will be able to:

  • Understand the limitations of bare-metal superloop programming.
  • Identify problems caused by blocking operations.
  • Understand task concurrency and independent task execution.

  • Identify situations where an RTOS is unnecessary.
  • Select an appropriate software architecture for an embedded system.

2. Why Is an RTOS Required?

Embedded systems often perform several operations at the same time from the application's point of view.

For example, an industrial controller may need to:

  • Read sensor values periodically.
  • Monitor emergency input signals.
  • Control a motor.
  • Communicate through UART or CAN.
  • Update an LCD.
  • Record system information.

Each operation may have different execution requirements and timing constraints. Managing all these operations in one sequential program can become difficult as the application grows.

Primary reason: An RTOS provides structured task management, scheduling, synchronization, and timing services for embedded applications with multiple activities and real-time requirements.

3. Limitations of Bare-Metal Programming

Bare-metal programming executes application code directly on the microcontroller without an operating-system kernel.

A common approach is to use an infinite loop called a superloop.

Example: Bare-Metal Superloop

#include <stdint.h>

int main(void)
{
    System_Init();

    while (1)
    {
        Read_Sensor();
        Process_Data();
        Update_Display();
        Send_UART_Data();
        Control_Motor();
    }
}

How It Works

  1. The microcontroller initializes its peripherals.
  2. The infinite loop begins executing.
  3. Each function executes sequentially.
  4. After the final function, execution returns to the first function.

Major Limitations

  • One long-running function can delay subsequent operations.
  • Managing different task priorities is difficult.
  • Blocking operations can affect system responsiveness.
  • Application complexity increases as functions are added.
  • Timing requirements become harder to analyze.
  • Sharing data between independent activities requires careful design.
Bare-metal programming is not inherently unsuitable for real-time applications. A carefully designed interrupt-driven or cyclic-executive system can meet strict timing requirements without an RTOS.

4. Problem of Blocking Operations

A blocking operation causes the current execution flow to wait until an event or condition is satisfied.

Example: Waiting for UART Data

void Receive_UART_Data(void)
{
    while ((U0LSR & 0x01) == 0)
    {
        // Wait until data is received
    }

    received_data = U0RBR;
}

This function waits until UART data becomes available.

If it is called directly inside a superloop, other functions may not execute while the processor is waiting.

Possible Consequences

  • Sensor sampling may be delayed.
  • Control operations may execute late.
  • Display updates may be postponed.
  • Time-sensitive events may be missed.

How an RTOS Helps

In an RTOS-based application, a task can block while waiting for a queue, semaphore, notification, or other event. The scheduler can then execute another ready task.

void UART_Receive_Task(void *pvParameters)
{
    for (;;)
    {
        // Wait for data using an appropriate
        // interrupt-driven or RTOS communication method.

        Process_Received_Data();
    }
}

The exact implementation depends on the UART driver and RTOS APIs. A task that performs a blocking wait can allow other ready tasks to use the CPU.

5. Managing Multiple Independent Activities

An embedded system may contain several activities that need to progress independently.

Example: Motor Monitoring System

Activity Function Timing Requirement
Sensor Monitoring Read current and temperature Periodic
Motor Control Adjust motor operation Time-sensitive
UART Communication Transmit monitoring data Event-driven
LCD Display Display measured values Periodic, less critical
Fault Monitoring Detect abnormal conditions High responsiveness

An RTOS allows these activities to be organized into separate tasks with suitable priorities and communication mechanisms.

6. Need for Task Priorities

Not every operation in an embedded system has the same importance.

For example, detecting an overcurrent condition is generally more important than refreshing an LCD display.

Illustrative Priority Assignment

Task Priority Reason
Fault Detection Highest Must respond promptly to abnormal conditions
Motor Control High Time-sensitive control operation
Sensor Monitoring Medium Periodic data acquisition
UART Logging Low Non-critical data transmission
LCD Update Lowest Display refresh can usually tolerate some delay

Priority assignments must be based on actual deadlines, execution times, task dependencies, and system safety requirements.

A high-priority task can still miss its deadline because of interrupt interference, resource blocking, excessive execution time, or an unsuitable scheduling design.

7. Need for Predictable Timing

In real-time systems, an operation must often finish within a specified time limit.

Example: Overcurrent Protection

Consider a motor controller that monitors current and must disable its output when an overcurrent condition is detected.

Assume the design specifies that the detection and control response must complete within 2 milliseconds of the relevant event.

The system designer must account for:

  • Sensor or input detection delay.
  • Interrupt latency.
  • Task release delay.
  • Task execution time.
  • Resource blocking.
  • Output control delay.

An RTOS can help organize and schedule the software response, but the complete hardware and software path must be analyzed to verify the timing requirement.

8. Need for Inter-Task Communication

When an application is divided into multiple tasks, those tasks may need to exchange information.

Example

  1. Sensor Task reads a temperature value.
  2. Sensor Task sends the value to a queue.
  3. Control Task receives the value.
  4. Control Task checks the threshold.
  5. Display Task receives data for updating the LCD.

Common RTOS Communication Mechanisms

  • Queues: Transfer data between tasks.
  • Semaphores: Signal events or coordinate task execution.
  • Mutexes: Protect shared resources.
  • Task Notifications: Provide lightweight task signaling in FreeRTOS.
  • Event Groups: Allow tasks to synchronize using event bits.
Communication mechanisms help avoid uncontrolled access to shared data and make task interactions easier to structure.

9. Need for Better Software Modularity

In a large embedded application, placing every operation inside one main loop can make the software difficult to maintain.

Without RTOS

  • Many operations are placed in one main execution loop.
  • Function dependencies can become difficult to manage.
  • Adding new functionality can affect existing timing behavior.

With RTOS

  • Each task can handle a defined responsibility.
  • Communication can use defined kernel services.
  • Task-specific code can be tested separately.
  • Software structure can be easier to extend.

Example Software Organization

Embedded_Application/
|
|-- main.c
|-- system_init.c
|
|-- tasks/
|   |-- sensor_task.c
|   |-- control_task.c
|   |-- communication_task.c
|   |-- display_task.c
|
|-- drivers/
|   |-- adc_driver.c
|   |-- uart_driver.c
|   |-- gpio_driver.c
|   |-- timer_driver.c
|
|-- rtos/
    |-- FreeRTOSConfig.h
    |-- kernel_source/

This is an illustrative project structure. Actual directory names and organization depend on the development environment.

10. RTOS vs Superloop: Practical Comparison

Feature Bare-Metal Superloop RTOS-Based Application
Execution structure Sequential main loop Multiple scheduled tasks
Task priorities Usually application-defined Kernel-supported priorities
Task blocking May block the main loop Blocked task can allow other ready tasks to execute
Synchronization Application-defined Kernel synchronization services
Communication Shared variables and custom mechanisms Queues, notifications, and other services
Memory overhead Usually lower Additional kernel and task-stack memory
Complexity Simple for small applications Useful for complex concurrent applications

11. When Is an RTOS Not Required?

An RTOS is not necessary for every embedded application.

Bare-Metal Programming May Be Suitable When:

  • The application performs only a few simple operations.
  • Execution is naturally sequential.
  • Timing requirements can be met with a simple cyclic design.
  • Interrupt-driven processing is sufficient.
  • Memory and processing resources are extremely limited.
  • The added kernel complexity is not justified.

An RTOS May Be Beneficial When:

  • The application contains multiple independent activities.
  • Different activities have different priorities.
  • Tasks need to wait for events independently.
  • Inter-task communication is required.
  • Scheduling and timing analysis benefit from a task-based architecture.
  • The system is expected to grow in complexity.

12. Practical Embedded System Example

Consider a motor monitoring and protection system using a microcontroller.

System Requirements

  • Measure motor current through an ADC channel.
  • Monitor motor temperature.
  • Control the motor output.
  • Display operating parameters.
  • Transmit status information through UART.
  • Detect fault conditions.

Possible RTOS Task Structure

+--------------------------------+
|       Motor Monitoring System  |
+--------------------------------+
                |
     +----------+----------+
     |          |          |
+---------+ +---------+ +---------+
| Sensor  | | Control | |  Fault  |
|  Task   | |  Task   | | Monitor |
+---------+ +---------+ +---------+
     |          |          |
     +----------+----------+
                |
       +--------+--------+
       |                 |
  +---------+       +---------+
  |  UART   |       |   LCD   |
  |  Task   |       |  Task   |
  +---------+       +---------+

The tasks communicate through suitable queues, notifications, or shared resources protected by synchronization mechanisms.

For safety-critical motor protection, a dedicated hardware protection path may also be required. An RTOS task should not be the only protection mechanism when the required response is faster or more reliable than the software path can guarantee.

13. LPC2129 and Keil uVision Practical Considerations

The LPC2129 can be used to study embedded software organization, peripheral programming, interrupts, and timing concepts.

Suggested Exercises

  1. Write a bare-metal superloop for sensor reading, UART communication, and GPIO control.
  2. Identify which functions can block execution.
  3. Convert the application into a task-based design on paper.
  4. Assign illustrative priorities to each task.
  5. Draw a communication diagram using queues and semaphores.
  6. Estimate the memory required for task stacks in a hypothetical RTOS implementation.
Keil uVision simulator-only practice can demonstrate LPC2129 register operations, interrupt behavior supported by the simulator, and bare-metal timing concepts. It does not by itself establish that FreeRTOS is supported or running on the LPC2129. Verify the exact ARM7 port and build environment before attempting a real FreeRTOS implementation.

14. Lesson Summary

  • RTOS is useful when an embedded system contains multiple activities with timing requirements.
  • A superloop can become difficult to manage as application complexity increases.
  • Blocking operations can delay other activities.
  • RTOS organizes application functionality into separate tasks.
  • Task priorities help determine which ready task executes first.
  • Queues, semaphores, mutexes, and notifications support task communication and synchronization.
  • Predictable response time is important in real-time applications.
  • An RTOS can improve modularity and task management.
  • An RTOS introduces additional memory and scheduling overhead.
  • Simple embedded applications may be better implemented using bare-metal programming.
  • Correct timing depends on the entire hardware and software system, not only the RTOS.
