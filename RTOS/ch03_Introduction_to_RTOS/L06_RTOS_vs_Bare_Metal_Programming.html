2. What Is Bare-Metal Programming?

Bare-metal programming is a method of developing software that runs directly on a microcontroller without an operating-system kernel.

The application program directly controls processor registers, memory, interrupts, and peripheral hardware.

Characteristics

  • No RTOS kernel is required.
  • Application code controls program execution.
  • Peripheral registers can be accessed directly.
  • Interrupt Service Routines handle asynchronous events.
  • Program flow is commonly organized using a main loop.
  • Memory and CPU overhead can be very small.

Typical Applications

  • Simple LED controllers.
  • Basic sensor monitoring devices.
  • Small electronic control circuits.
  • Simple communication interfaces.
  • Low-resource microcontroller applications.

3. Bare-Metal Superloop Architecture

A superloop is a common bare-metal programming structure in which the main function repeatedly executes a sequence of application operations.

Architecture

+-------------------------+
|       main()            |
+-------------------------+
            |
            v
+-------------------------+
| Hardware Initialization|
+-------------------------+
            |
            v
+-------------------------+
|       while(1)          |
+-------------------------+
            |
            v
+-------------------------+
| Read Sensor             |
+-------------------------+
            |
            v
+-------------------------+
| Process Sensor Data     |
+-------------------------+
            |
            v
+-------------------------+
| Update Display          |
+-------------------------+
            |
            v
+-------------------------+
| Check Communication     |
+-------------------------+
            |
            +---- Repeat -->

Every operation is executed according to the order defined by the programmer.

Example: Simple Superloop

#include 

/* Illustrative hardware functions */
void GPIO_Init(void);
void UART_Init(void);
void Read_Sensor(void);
void Update_Display(void);
void Process_Communication(void);

int main(void)
{
    GPIO_Init();
    UART_Init();

    while (1)
    {
        Read_Sensor();
        Update_Display();
        Process_Communication();
    }
}

This example illustrates the program structure. Actual peripheral functions must be implemented for the selected microcontroller.

4. Limitations of a Traditional Superloop

Superloop programming is straightforward for small systems, but its limitations become more visible as the number of independent activities increases.

1. Sequential Execution

Each operation normally waits for the previous operation to finish before the next one begins.

2. Blocking Operations

A long delay or blocking peripheral operation can prevent the main loop from processing other activities.

3. Timing Complexity

As more functions are added, calculating the response time of each operation becomes difficult.

4. Difficult Task Coordination

Communication and coordination between independent activities may require additional flags, buffers, and state machines.

5. Code Maintenance

A large main loop can become difficult to understand, modify, and debug.

A well-designed superloop can still meet real-time requirements. These limitations are design challenges, not proof that bare-metal programming is inherently unsuitable for real-time systems.

5. Polling-Based Programming

Polling is a method in which the processor repeatedly checks the status of a hardware peripheral or event.

Example: Checking a Button

while (1)
{
    if (BUTTON_PRESSED())
    {
        LED_ON();
    }
    else
    {
        LED_OFF();
    }
}

Advantages

  • Simple to implement.
  • Easy to understand.
  • No interrupt configuration is required for the polled event.
  • Suitable for some simple applications.

Disadvantages

  • CPU time is consumed repeatedly checking status.
  • Event response depends on polling frequency.
  • Long processing operations can delay event detection.
  • Frequent polling may waste power.

6. Interrupt-Driven Bare-Metal Programming

Interrupt-driven programming allows hardware events to interrupt normal program execution.

Instead of continuously checking a peripheral, the processor executes an ISR when the configured interrupt occurs.

Example Architecture

+---------------------------+
|      Main Program         |
|                           |
| Process Application Flags |
| Perform Background Work   |
+---------------------------+
             |
             |
      Hardware Event
             |
             v
+---------------------------+
| Interrupt Service Routine |
|                           |
| Acknowledge Interrupt     |
| Capture Essential Data   |
| Set Event Flag            |
+---------------------------+
             |
             v
       Return to Main
             |
             v
     Process Event Flag

Illustrative C Example

#include 

volatile uint8_t eventFlag = 0;

/* Called by the configured interrupt mechanism */
void Timer_ISR(void)
{
    /* Acknowledge the timer interrupt here. */

    eventFlag = 1;
}

int main(void)
{
    Timer_Init();
    Timer_Interrupt_Enable();

    while (1)
    {
        if (eventFlag != 0)
        {
            eventFlag = 0;

            /* Perform periodic application work. */
            Process_Event();
        }

        /* Other background operations. */
    }
}

This is an illustrative pattern. The actual ISR declaration, interrupt acknowledgement, and event-flag protection must follow the target microcontroller's requirements.

A shared variable accessed by both an ISR and foreground code requires careful analysis. The volatile qualifier alone does not guarantee atomicity or protect against race conditions.

7. What Is an RTOS-Based Application?

An RTOS-based application uses a kernel to manage multiple independently scheduled tasks.

Instead of writing every activity inside one main loop, the programmer divides the application into separate tasks.

Typical Tasks

  • Sensor acquisition task.
  • Control task.
  • UART communication task.
  • Display update task.
  • Fault monitoring task.

RTOS Architecture

+----------------------------------+
|         Application Tasks        |
|                                  |
| Sensor Task | Control Task       |
| UART Task   | Display Task       |
+----------------------------------+
                 |
                 v
+----------------------------------+
|             RTOS Kernel          |
|                                  |
| Scheduler | Task Management      |
| Queues    | Semaphores | Timers  |
+----------------------------------+
                 |
                 v
+----------------------------------+
|          Hardware Drivers        |
+----------------------------------+
                 |
                 v
+----------------------------------+
|          Microcontroller         |
+----------------------------------+

8. Task-Based Programming in an RTOS

Each task contains a function that performs a particular application activity.

Example: Sensor Task

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

Example: Display Task

void DisplayTask(void *pvParameters)
{
    for (;;)
    {
        Update_Display();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

The scheduler determines when each ready task executes. A blocked task does not continuously consume CPU time while waiting for its delay or event.

An RTOS task is not necessarily executing continuously. It may be ready, running, blocked, or suspended depending on the kernel and its current conditions.

9. Superloop vs RTOS Task Architecture

Parameter Superloop RTOS
Execution Model Sequential main loop Kernel-managed tasks
Scheduling Programmer-defined order Kernel scheduling policy
Context Switching Usually no task context switching Supported by kernel
Interrupts Used for event handling Integrated with kernel services
Communication Flags, shared variables, buffers Queues, notifications, semaphores, etc.
Timing Must be designed and analyzed manually Kernel provides task timing services
Memory Usage Can be very small Requires kernel and task resources
Complexity Simple for small systems Structured for larger concurrent applications
Best Fit Simple and predictable control flow Multiple independent activities and coordination

10. Example: LED, Sensor, and UART Application

Consider an embedded application with three activities:

  1. Read a sensor periodically.
  2. Control an LED based on sensor data.
  3. Transmit sensor information over UART.

Superloop Approach

int main(void)
{
    Hardware_Init();

    while (1)
    {
        Read_Sensor();
        Control_LED();
        Send_UART_Data();
    }
}

If Send_UART_Data() waits for transmission to finish, sensor processing and LED updates may be delayed.

RTOS Approach

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();
        Send_Sensor_Data_To_Queue();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void ControlTask(void *pvParameters)
{
    for (;;)
    {
        Receive_Sensor_Data_From_Queue();
        Control_LED();
    }
}

void UARTTask(void *pvParameters)
{
    for (;;)
    {
        Receive_Sensor_Data_From_Queue();
        Send_UART_Data();

        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

This illustrates the separation of activities. A real implementation must define queue ownership, queue capacity, data structures, blocking behavior, and error handling. If both consumers need every sensor sample, use separate queues or another deliberate distribution mechanism rather than assuming one queue broadcasts each item.

11. Blocking and Non-Blocking Operations

Blocking Operation

A blocking operation suspends the calling task until an event, resource, or timeout condition is satisfied.

Non-Blocking Operation

A non-blocking operation returns immediately if the requested operation cannot be completed at once.

Blocking Non-Blocking
Can wait for an event or resource. Returns without waiting for the event or resource.
Can allow another ready task to execute. Allows the current task to continue immediately.
Useful for event-driven task design. Useful for polling or checking availability.

Blocking is not inherently bad in an RTOS. Properly designed blocking can reduce CPU usage and simplify task coordination.

12. CPU and Memory Overhead

Bare-Metal

  • No RTOS scheduler overhead.
  • No kernel-managed task stacks are required.
  • Program structure can be compact.
  • Application code may need custom timing and coordination logic.

RTOS

  • Uses memory for task stacks and kernel objects.
  • Consumes CPU time for scheduling and context switching.
  • Provides reusable task and synchronization services.
  • Can simplify complex application organization.

The actual resource difference depends on the application, selected kernel, configuration, and hardware.

13. When Should You Use Bare-Metal Programming?

Bare-metal programming is often appropriate when:

  • The application has only a few activities.
  • Program flow is simple and predictable.
  • Memory and CPU resources are very limited.
  • There is no need for a complex task scheduler.
  • Interrupt-driven design can satisfy timing requirements.
  • The application requires minimal software overhead.

Examples

  • Simple LED blinking.
  • Basic digital input monitoring.
  • Simple relay control.
  • Small periodic sensor-reading applications.

14. When Should You Use an RTOS?

An RTOS is often appropriate when:

  • Multiple independent activities must operate concurrently.
  • Tasks have different priorities and deadlines.
  • Inter-task communication is required.
  • Shared resources require synchronization.
  • Application complexity is growing.
  • Periodic and event-driven tasks must be coordinated.

Examples

  • Robotic control systems.
  • Industrial automation controllers.
  • Multichannel sensor monitoring systems.
  • Communication gateways.
  • Embedded motor-control applications.

15. Hybrid Approach

Some embedded applications combine bare-metal techniques and RTOS-based task management.

For example:

  • An RTOS manages sensor, communication, and display tasks.
  • A short ISR captures a hardware event.
  • The ISR signals an RTOS task.
  • The task performs the remaining processing.

This is a common RTOS design pattern. It combines interrupt-driven hardware response with kernel-managed application processing.

Avoid performing lengthy application processing inside an ISR. Keep interrupt work bounded and use appropriate ISR-safe APIs when communicating with RTOS tasks.

16. LPC2129 and Keil uVision Practical Context

The LPC2129 uses an ARM7TDMI-S processor. Its timer, UART, GPIO, ADC, and VIC peripherals can be studied through register-level programming.

Bare-Metal Exercises

  1. Configure GPIO and inspect pin registers.
  2. Generate a timer interrupt.
  3. Set a software flag inside an ISR.
  4. Process the flag in the main loop.
  5. Configure UART registers and study transmit status.
  6. Measure program execution using available simulator facilities.

RTOS Concepts to Study Separately

  • Task creation and scheduling.
  • Task stack management.
  • Queue-based communication.
  • Semaphore synchronization.
  • Task delays and periodic execution.
Your Keil simulator setup is useful for studying LPC2129 register-level and interrupt behavior. It does not automatically provide a supported FreeRTOS port. Verify ARM7TDMI-S port availability and toolchain compatibility before attempting a FreeRTOS project. Simulated peripheral register behavior should not be treated as proof of physical hardware operation.

17. Lesson Summary

  • Bare-metal programming executes application code without an RTOS kernel.
  • A superloop repeatedly executes application operations.
  • Polling checks peripheral status repeatedly.
  • Interrupt-driven programming responds to hardware events through ISRs.
  • An RTOS organizes application functionality into independently scheduled tasks.
  • The scheduler determines which ready task executes.
  • Queues, semaphores, and notifications coordinate tasks.
  • Bare-metal systems can meet real-time requirements with suitable design.
  • RTOS introduces overhead but provides reusable kernel services.
  • The correct choice depends on timing, complexity, memory, and maintenance requirements.
