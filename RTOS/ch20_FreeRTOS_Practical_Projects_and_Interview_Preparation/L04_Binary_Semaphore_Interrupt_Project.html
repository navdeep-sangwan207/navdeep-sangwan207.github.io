2. Project Introduction

This project demonstrates how a hardware interrupt can notify a FreeRTOS task using a binary semaphore.

For this example, an external interrupt is generated by a push button or another interrupt source. The ISR performs minimal processing and gives a binary semaphore. A task waiting on that semaphore wakes up and performs the application-level operation.

Project Behavior

ComponentResponsibility
External interrupt sourceGenerates an interrupt event.
ISRAcknowledges the source and signals the semaphore.
Binary semaphoreStores a pending notification token.
Application taskWakes up and processes the event.
GPIO or UART driverPerforms the selected output operation.

3. System Architecture

EXTERNAL INTERRUPT | v INTERRUPT SERVICE ROUTINE (ISR) | Acknowledge Source | xSemaphoreGiveFromISR() | v BINARY SEMAPHORE | Task Becomes Ready | v APPLICATION TASK | Process Event | GPIO / UART

The ISR does not perform lengthy application processing. It signals the task and returns. The task performs the remaining work in normal task context.

4. Why Use a Binary Semaphore?

A binary semaphore can hold one pending token. It is useful for signaling that an event has occurred.

Example

When a button interrupt occurs:

  1. The processor enters the ISR.
  2. The ISR acknowledges the interrupt source.
  3. The ISR gives the binary semaphore.
  4. The waiting task becomes Ready.
  5. The scheduler runs the task at an appropriate scheduling point.
  6. The task performs the requested operation.
A binary semaphore is a synchronization signal, not a data-transfer mechanism. If every interrupt event must be counted or associated data must be transferred, consider a counting semaphore, queue or task notification, depending on the requirements.

5. Binary Semaphore APIs

Semaphore Creation

SemaphoreHandle_t xSemaphoreCreateBinary(void);

Creates a binary semaphore. A newly created binary semaphore is initially empty.

Task Context: Take Semaphore

xSemaphoreTake(
    xSemaphore,
    xTicksToWait
);

The task attempts to take the semaphore. If it is empty, the task can block for the specified time.

ISR Context: Give Semaphore

xSemaphoreGiveFromISR(
    xSemaphore,
    &xHigherPriorityTaskWoken
);

This ISR-safe API gives the semaphore without blocking the interrupt handler.

Important Difference

APIExecution Context
xSemaphoreTake()Task context
xSemaphoreGive()Task context
xSemaphoreGiveFromISR()ISR context
xSemaphoreTakeFromISR()ISR context, where supported and applicable
Never call a blocking API or use a mutex from an ISR. Use the appropriate FromISR API supported by the selected FreeRTOS port.

7. Complete FreeRTOS Application Example

Objective: Notify a task from an external interrupt using a binary semaphore.

The following is a portable application-level template. Hardware-specific interrupt registration and acknowledgment are represented by clearly marked driver functions.

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "stdint.h"

/* Binary semaphore handle */
static SemaphoreHandle_t eventSemaphore = NULL;

/* Task declaration */
static void EventTask(void *pvParameters);

/*
 * Hardware-specific functions.
 * Implement these using the target MCU driver.
 */
void GPIO_Init(void);
void ExternalInterrupt_Init(void);
void ExternalInterrupt_Acknowledge(void);
void Event_Output_Toggle(void);

/* Application task */
static void EventTask(void *pvParameters)
{
    (void) pvParameters;

    for (;;)
    {
        /*
         * Wait until the ISR gives the semaphore.
         */
        if (xSemaphoreTake(
                eventSemaphore,
                portMAX_DELAY
            ) == pdPASS)
        {
            /*
             * Perform application processing
             * in task context.
             */
            Event_Output_Toggle();
        }
    }
}

/*
 * Interrupt handler.
 * The actual function name and interrupt
 * registration are MCU-specific.
 */
void ExternalInterrupt_Handler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /*
     * Acknowledge or clear the hardware
     * interrupt source as required.
     */
    ExternalInterrupt_Acknowledge();

    /*
     * Signal the application task.
     */
    xSemaphoreGiveFromISR(
        eventSemaphore,
        &xHigherPriorityTaskWoken
    );

    /*
     * Request a context switch on ISR exit
     * if the port requires this macro and
     * a higher-priority task was woken.
     */
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

int main(void)
{
    /* Initialize GPIO hardware */
    GPIO_Init();

    /*
     * Create binary semaphore.
     * Initially the semaphore is empty.
     */
    eventSemaphore = xSemaphoreCreateBinary();

    if (eventSemaphore == NULL)
    {
        for (;;)
        {
            /* Semaphore creation failed */
        }
    }

    /* Create application task */
    if (xTaskCreate(
            EventTask,
            "EventTask",
            256,
            NULL,
            3,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
            /* Task creation failed */
        }
    }

    /*
     * Configure interrupt hardware.
     * Ensure the interrupt is not enabled
     * before the semaphore and task exist.
     */
    ExternalInterrupt_Init();

    /* Start FreeRTOS scheduler */
    vTaskStartScheduler();

    /* Reached if scheduler startup fails */
    for (;;)
    {
    }
}
The interrupt handler's exact name, vector registration, source acknowledgment and yield macro depend on the processor port. Some ports use a different ISR-yield macro or calling convention. Verify the selected FreeRTOS port documentation before compiling.

8. Explanation of the Program

Step 1 – Declare Semaphore Handle

static SemaphoreHandle_t eventSemaphore = NULL;

This handle identifies the binary semaphore used to communicate between the ISR and task.

Step 2 – Create Binary Semaphore

eventSemaphore = xSemaphoreCreateBinary();

The semaphore is initially empty. The task will block until it is given.

Step 3 – Create Application Task

xTaskCreate(
    EventTask,
    "EventTask",
    256,
    NULL,
    3,
    NULL
);

The task waits for the interrupt notification and performs the application operation.

Step 4 – Wait for Semaphore

xSemaphoreTake(
    eventSemaphore,
    portMAX_DELAY
);

The task blocks while the semaphore is empty. It becomes Ready when the semaphore is successfully given.

Step 5 – Give Semaphore from ISR

xSemaphoreGiveFromISR(
    eventSemaphore,
    &xHigherPriorityTaskWoken
);

The ISR signals the waiting task using the ISR-safe API.

Step 6 – Request Context Switch

portYIELD_FROM_ISR(xHigherPriorityTaskWoken);

Where supported by the port, this requests a scheduling decision on ISR exit if the operation woke a higher-priority task.

9. Understanding xHigherPriorityTaskWoken

The variable indicates whether giving the semaphore caused a higher-priority task to become Ready.

BaseType_t xHigherPriorityTaskWoken = pdFALSE;

It is initialized to pdFALSE before the ISR-safe API call.

ValueMeaning
pdFALSENo higher-priority task was woken by the operation.
pdTRUEA higher-priority task was woken and a scheduling request may be needed on ISR exit.
The exact macro used to request an ISR-exit context switch is port-specific. Follow the selected port's documented ISR API pattern.

10. Binary Semaphore State Diagram

SEMAPHORE EMPTY | ISR GIVES TOKEN | v SEMAPHORE FULL | TASK TAKES TOKEN | v SEMAPHORE EMPTY

A binary semaphore can store at most one pending token. If another give occurs while it is already full, the semaphore cannot store an additional event count.

11. Why Keep the ISR Short?

Interrupt handlers should perform only the work necessary to service the hardware event and notify the application.

Recommended ISR Operations

  • Identify and acknowledge the interrupt source.
  • Capture minimal required status information.
  • Give a semaphore or send data using an appropriate ISR-safe API.
  • Request a context switch if required by the port.
  • Return promptly.

Operations to Avoid in an ISR

  • Long calculations.
  • Blocking delays.
  • Waiting for a semaphore or mutex.
  • Long UART printing operations.
  • Dynamic memory allocation unless explicitly supported and safe for the specific context.
  • Calling task-context-only FreeRTOS APIs.
Use the ISR to signal an event. Use a task to perform the application processing.

12. Binary Semaphore vs Counting Semaphore

FeatureBinary SemaphoreCounting Semaphore
Maximum count1Configured maximum
PurposeEvent signaling or synchronizationCounting events or tracking available resources
Repeated givesCoalesce when already fullIncrease count until maximum
Resource countingLimited to one tokenCan represent multiple tokens
ExampleNotify task of an interruptCount received events

If every interrupt occurrence must be counted, a counting semaphore or another event-recording mechanism may be more appropriate than a binary semaphore.

13. Important Limitation: Event Coalescing

Consider the following sequence:

  1. The first interrupt gives the semaphore.
  2. The semaphore becomes full.
  3. A second interrupt occurs before the task takes the semaphore.
  4. The semaphore remains full; it cannot represent two separate pending events.
  5. The task eventually takes the semaphore once.
A binary semaphore indicates that at least one event is pending. It does not preserve the number of repeated events. If event count or event data must be retained, use a suitable counting or queue-based design.

14. Interrupt Debouncing

A mechanical push button may generate several electrical transitions during a single press. This is called switch bounce.

If every transition generates an interrupt, one physical press may produce multiple notifications.

Possible Solutions

  • Use hardware debounce circuitry.
  • Use a suitable MCU input filter if available.
  • Use timer-based software debounce in task context.
  • Validate the input state after a debounce interval.
  • Define whether repeated edges should be ignored or counted.
Do not use a long blocking delay inside the ISR for switch debouncing. Signal the task and perform the timing-based validation outside interrupt context.

15. Interrupt Source Acknowledgment

The interrupt source must be serviced according to the MCU peripheral's requirements.

Some peripherals use a write-one-to-clear status bit. Others require reading a status register, draining a data register or performing a specific sequence.

Generic Example

void ExternalInterrupt_Handler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Device-specific acknowledgment */
    ExternalInterrupt_Acknowledge();

    /* Notify the task */
    xSemaphoreGiveFromISR(
        eventSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}
The acknowledgment function must match the hardware peripheral. Do not copy a generic status-register write into a real project without checking the device reference manual.

16. Error Handling

The application should define behavior for semaphore creation failure and unexpected give failures.

Semaphore Creation Check

eventSemaphore = xSemaphoreCreateBinary();

if (eventSemaphore == NULL)
{
    /* Enter defined fault handling */
    Error_Handler();
}

ISR Give Result

BaseType_t result;

result = xSemaphoreGiveFromISR(
    eventSemaphore,
    &xHigherPriorityTaskWoken
);

If the semaphore is already full, a further give may fail. This can be expected when binary semaphore events coalesce. If every event matters, select a different communication mechanism.

17. Alternative Design Using a Task Notification

For a simple one-to-one ISR-to-task notification, a direct-to-task notification may use less kernel-object memory and have lower overhead than a semaphore.

Task Side

static void EventTask(void *pvParameters)
{
    (void) pvParameters;

    for (;;)
    {
        ulTaskNotifyTake(
            pdTRUE,
            portMAX_DELAY
        );

        Event_Output_Toggle();
    }
}

ISR Side

void ExternalInterrupt_Handler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    ExternalInterrupt_Acknowledge();

    vTaskNotifyGiveFromISR(
        eventTaskHandle,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

Task notifications can operate as binary-style signals or count notifications, depending on the API and notification configuration. The task handle must be valid before the interrupt is enabled.

This is an alternative design, not code to combine with the binary semaphore implementation. Select one communication mechanism based on the application requirements.

18. Practical Exercise 1 – Interrupt-Controlled LED

Objective: Toggle an LED whenever the external interrupt task processes a notification.

  • Configure an interrupt input.
  • Create a binary semaphore.
  • Create an application task.
  • Give the semaphore from the ISR.
  • Toggle the LED in the task.
  • Observe the task state before and after an interrupt.

Expected result: The task remains Blocked while no event is pending and becomes Ready after the semaphore is given.

19. Practical Exercise 2 – Add Event Counting

Objective: Preserve the number of interrupt events instead of coalescing them.

  • Replace the binary semaphore with a counting semaphore.
  • Set an appropriate maximum count.
  • Use the ISR-safe give operation.
  • Take the semaphore in the application task.
  • Test behavior when the maximum count is reached.

Expected result: Multiple pending events can be represented up to the configured count limit.

20. Practical Exercise 3 – Add Debouncing

Objective: Prevent one mechanical button press from generating multiple application actions.

  • Keep the ISR short.
  • Notify a task when an edge is detected.
  • Use a task-level timer or delay for debounce validation.
  • Read the input again after the debounce interval.
  • Accept the event only if the input state is stable.

Expected result: The application processes a validated button event rather than blindly treating every electrical transition as a separate press.

21. Practical Exercise 4 – Inspect Task Response

Objective: Study the time between interrupt occurrence and task execution.

  • Record an interrupt timestamp using a suitable hardware timer.
  • Record a second timestamp when the task starts processing.
  • Calculate the observed interrupt-to-task response interval.
  • Repeat under different system loads.
  • Compare results with the application's response-time requirement.

Expected result: Measured response intervals that include interrupt handling, scheduler activity and task interference.

A measured maximum is not automatically a formal worst-case execution or response-time bound. Timing measurements must cover relevant operating conditions and be supported by analysis.

23. Keil µVision and LPC2129 Simulator Notes

The LPC2129 uses an ARM7TDMI-S core and a Vectored Interrupt Controller (VIC). It has IRQ and FIQ interrupt modes; it does not use the Cortex-M NVIC.

Useful LPC2129 Concepts

  • VIC interrupt source selection and enable configuration.
  • IRQ and FIQ routing.
  • Peripheral interrupt status and acknowledgment.
  • IRQ vector and handler registration.
  • Task notification after interrupt processing.

Simulation Study

  • Study the interrupt handler entry and exit flow.
  • Inspect relevant VIC and peripheral registers.
  • Set breakpoints at the ISR and task entry points.
  • Observe semaphore-related control flow in a compatible FreeRTOS build.
  • Review the task state transition from Blocked to Ready.
The LPC2129/Keil FreeRTOS port and simulator compatibility must be verified before attempting to execute this project. Do not assume a Cortex-M ISR example or NVIC configuration can be used on ARM7. A simulator also cannot prove real switch behavior, electrical debounce or physical interrupt timing.

25. Lesson Summary

  • A binary semaphore can synchronize an ISR with an application task.
  • The semaphore is initially empty after creation.
  • The task waits using xSemaphoreTake().
  • The ISR signals using xSemaphoreGiveFromISR().
  • ISR-safe APIs must be used from interrupt context.
  • The ISR should acknowledge the hardware source and remain short.
  • The ISR-yield mechanism is port-specific.
  • A binary semaphore stores at most one pending token.
  • Repeated events can coalesce.
  • Counting semaphores, queues and task notifications are alternatives for different requirements.
  • Hardware interrupt configuration must match the target MCU.
