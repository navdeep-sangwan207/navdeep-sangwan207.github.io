1. Project Overview

Project Title

Real-Time Embedded Monitoring and Control System Using FreeRTOS

This project develops a multitasking embedded application that acquires sensor measurements, processes data, monitors operating conditions, accepts commands and manages an actuator output through a structured RTOS architecture.

Project Objectives

  • Implement multiple independent FreeRTOS tasks.
  • Acquire sensor data at a periodic interval.
  • Transfer measurements using queues.
  • Implement event-driven fault monitoring.
  • Process commands through a communication interface.
  • Control an actuator through a single software owner.
  • Monitor task execution and system health.
  • Design a system that can be extended to real embedded hardware.
Project scope: The software architecture and example code are intended for learning and adaptation. A real deployment requires a verified FreeRTOS processor port, hardware drivers, timing analysis, electrical protection and physical testing.

Non-Functional Requirements

  • Shared resources should have explicit ownership.
  • Queue capacities and overflow policies must be documented.
  • Task stack allocation must be measured and validated.
  • Periodic operations should have specified timing requirements.
  • Fault handling should lead to a defined safe state.
  • Hardware-dependent functions should be isolated in drivers.

10. Sensor Acquisition Task

SensorTask reads an ADC channel periodically and sends a measurement structure to sensorQueue.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

extern QueueHandle_t sensorQueue;

void SensorTask(void *pvParameters)
{
    SensorData_t sample = {0};

    TickType_t lastWakeTime;
    const TickType_t samplePeriod =
        pdMS_TO_TICKS(100);

    lastWakeTime = xTaskGetTickCount();

    for (;;)
    {
        sample.adcValue = ADC_Read(0);

        sample.voltage =
            ((float)sample.adcValue * 3.3f)
            / 1023.0f;

        sample.temperature =
            sample.voltage / 0.010f;

        sample.sampleNumber++;

        sample.timestamp = xTaskGetTickCount();

        if (xQueueSend(
                sensorQueue,
                &sample,
                0
            ) != pdPASS)
        {
            /* Increment a properly synchronized
               dropped-sample diagnostic counter */
        }

        vTaskDelayUntil(
            &lastWakeTime,
            samplePeriod
        );
    }
}

Design notes:

  • The voltage formula assumes a 10-bit ADC and a 3.3 V reference.
  • The temperature conversion assumes an LM35-like sensor with nominal 10 mV/°C output.
  • ADC reference accuracy, sensor calibration, noise and acquisition settling time must be considered in real hardware.
  • The example uses zero queue wait to avoid delaying the sampling task. Queue-full behavior must be monitored.

11. Sensor Distributor Task

This task receives each sensor sample and forwards a copy to the processing and monitoring queues.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

extern QueueHandle_t sensorQueue;
extern QueueHandle_t processingQueue;
extern QueueHandle_t monitoringQueue;

void SensorDistributorTask(void *pvParameters)
{
    SensorData_t sample;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &sample,
                portMAX_DELAY
            ) == pdPASS)
        {
            if (xQueueSend(
                    processingQueue,
                    &sample,
                    0
                ) != pdPASS)
            {
                /* Record processing queue overflow */
            }

            if (xQueueSend(
                    monitoringQueue,
                    &sample,
                    0
                ) != pdPASS)
            {
                /* Record monitoring queue overflow */
            }
        }
    }
}
The distributor performs logical fan-out. If either destination queue is full, that destination may lose a sample. If every sample must be delivered to both consumers, define a stronger delivery policy, such as bounded blocking, sequence-number tracking and explicit recovery.

12. Processing Task

ProcessingTask evaluates the sensor data and creates a control request.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "event_groups.h"

#define FAULT_HIGH_TEMPERATURE  (1U << 0)

extern QueueHandle_t processingQueue;
extern QueueHandle_t controlQueue;
extern EventGroupHandle_t systemEventGroup;

void ProcessingTask(void *pvParameters)
{
    SensorData_t sample;
    uint32_t outputCommand = 0;

    for (;;)
    {
        if (xQueueReceive(
                processingQueue,
                &sample,
                portMAX_DELAY
            ) == pdPASS)
        {
            if (sample.temperature >= 40.0f)
            {
                xEventGroupSetBits(
                    systemEventGroup,
                    FAULT_HIGH_TEMPERATURE
                );

                outputCommand = 0;
            }
            else if (sample.temperature < 38.0f)
            {
                xEventGroupClearBits(
                    systemEventGroup,
                    FAULT_HIGH_TEMPERATURE
                );

                outputCommand = 50;
            }

            xQueueSend(
                controlQueue,
                &outputCommand,
                0
            );
        }
    }
}
This is an educational threshold example, not a complete safety policy. It does not define fault latching, sensor-disconnection detection, recovery authorization or independent hardware shutdown. A production design must also ensure that normal commands cannot override an active safety fault.

13. Control Task

ControlTask is the sole software owner of normal actuator output.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

extern QueueHandle_t controlQueue;

void ControlTask(void *pvParameters)
{
    uint32_t outputCommand = 0;

    for (;;)
    {
        if (xQueueReceive(
                controlQueue,
                &outputCommand,
                portMAX_DELAY
            ) == pdPASS)
        {
            if (outputCommand == 0)
            {
                Actuator_Stop();
            }
            else
            {
                Actuator_SetOutput(outputCommand);
            }
        }
    }
}

Design considerations:

  • Validate output commands before applying them.
  • Define what happens when no command arrives.
  • Consider whether the queue should retain the latest command or every command.
  • Ensure a fault condition cannot be bypassed by a queued normal command.
  • Use an independent hardware shutdown mechanism for hazards requiring protection independent of software scheduling.

14. Monitoring Task

MonitorTask receives measurements and prepares status information for transmission.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

extern QueueHandle_t monitoringQueue;
extern QueueHandle_t statusQueue;

void MonitorTask(void *pvParameters)
{
    SensorData_t sample;
    StatusMessage_t status = {0};

    for (;;)
    {
        if (xQueueReceive(
                monitoringQueue,
                &sample,
                portMAX_DELAY
            ) == pdPASS)
        {
            status.voltage = sample.voltage;
            status.temperature = sample.temperature;

            status.processedSamples =
                sample.sampleNumber;

            /* Add synchronized fault and drop
               counters from their owners */

            xQueueSend(
                statusQueue,
                &status,
                0
            );
        }
    }
}

Status fields shared across tasks need a clear ownership and synchronization strategy. Avoid reading or modifying multi-field structures concurrently without a defined protocol.

15. UART Transmission Task

UARTTxTask is the single software owner of the UART transmit interface.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include <stdio.h>
#include <string.h>

extern QueueHandle_t statusQueue;

void UARTTxTask(void *pvParameters)
{
    StatusMessage_t status;
    char message[128];

    for (;;)
    {
        if (xQueueReceive(
                statusQueue,
                &status,
                portMAX_DELAY
            ) == pdPASS)
        {
            int length = snprintf(
                message,
                sizeof(message),
                "Voltage: %.2f V, "
                "Temperature: %.2f C\r\n",
                (double)status.voltage,
                (double)status.temperature
            );

            if ((length > 0) &&
                ((size_t)length < sizeof(message)))
            {
                UART_Transmit(
                    (const uint8_t *)message,
                    (size_t)length
                );
            }
        }
    }
}

Design considerations:

  • Define whether UART_Transmit is blocking or asynchronous.
  • If DMA is used, retain buffer ownership until completion.
  • Handle transmit failures and timeouts.
  • Prevent a slow UART from indefinitely blocking unrelated application tasks.
  • For high-volume data, consider a separate TX ring buffer and DMA completion notification.

16. Command Task and Fault Management

CommandTask receives parsed commands and validates them before passing permitted requests to the control subsystem.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

extern QueueHandle_t commandQueue;
extern QueueHandle_t controlQueue;
extern EventGroupHandle_t systemEventGroup;

#define SYSTEM_FAULT_MASK  0x0000000FU

void CommandTask(void *pvParameters)
{
    Command_t command;
    uint32_t output;

    for (;;)
    {
        if (xQueueReceive(
                commandQueue,
                &command,
                portMAX_DELAY
            ) == pdPASS)
        {
            switch (command.type)
            {
                case CMD_STOP:
                    output = 0;
                    xQueueSend(controlQueue, &output, 0);
                    break;

                case CMD_SET_OUTPUT:
                    if ((command.value <= 100) &&
                        ((xEventGroupGetBits(
                            systemEventGroup
                        ) & SYSTEM_FAULT_MASK) == 0))
                    {
                        output = command.value;
                        xQueueSend(controlQueue, &output, 0);
                    }
                    break;

                case CMD_START:
                    /* Apply validated start policy */
                    break;

                case CMD_RESET_FAULT:
                    /* Reset only after checking
                       fault source and recovery rules */
                    break;

                default:
                    /* Reject unknown command */
                    break;
            }
        }
    }
}
A single queue with multiple producers needs a defined command arbitration policy. Also, checking a fault bit in CommandTask alone is not sufficient to guarantee safety: a fault can occur after the check, and older commands may remain queued. ControlTask must enforce the current safety state before applying output, and critical hazards need independent hardware protection.

18. Timing and Schedulability Analysis

Task Utilization

For a periodic task:

U = C / T

Where:

  • C = worst-case execution time.
  • T = task period.
  • U = processor utilization contributed by that task.

Illustrative Task Set

TaskWCET AssumptionPeriodUtilization
SensorTask1 ms100 ms1%
ControlTask2 ms20 ms10%
MonitorTask2 ms500 ms0.4%
DiagnosticTask1 ms1000 ms0.1%
Total illustrative utilization
= 1% + 10% + 0.4% + 0.1%
= 11.5%
These values are hypothetical and do not establish schedulability. A complete analysis must include higher-priority interference, blocking, interrupt execution, release jitter, deadlines, context-switch overhead and all other processor work. Queue-driven tasks need an appropriate arrival and workload model.

Response-Time Analysis

For a simplified fixed-priority task model:

R_i = C_i + B_i
      + sum(ceil(R_i / T_j) * C_j)

Here:

  • Rᵢ = response time of task i.
  • Cᵢ = execution time of task i.
  • Bᵢ = blocking time.
  • Cⱼ and Tⱼ = execution time and period of each higher-priority task j.

This recurrence requires appropriate fixed-priority scheduling assumptions and must be extended when release jitter, arbitrary deadlines, self-suspension or other complexities are present.

27. Lesson Summary

This major project combines the principal concepts of RTOS and FreeRTOS into one embedded-system design. It demonstrates how tasks, queues, event groups, periodic scheduling, driver interfaces, monitoring and fault management can be organized into a maintainable application.

The most important engineering lessons are clear task ownership, correct communication semantics, explicit fault handling, measured memory usage and timing analysis. A successful simulator demonstration is a useful development milestone, but it does not replace target-hardware verification.
