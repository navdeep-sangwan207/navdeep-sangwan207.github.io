1. Introduction

This lesson provides practical programming exercises to strengthen FreeRTOS concepts. The exercises progress from basic task creation to synchronization, communication, timing, memory management and complete embedded-system design.

Learning Objectives

  • Create and manage multiple FreeRTOS tasks.
  • Implement periodic and priority-based task execution.
  • Transfer data through queues and task notifications.
  • Use binary semaphores, counting semaphores and mutexes.
  • Synchronize tasks using event groups.
  • Implement software timers and timer callbacks.
  • Analyze stack usage, queue capacity and task timing.
  • Develop a structured FreeRTOS application.
Development environment: The programs use generic FreeRTOS APIs. Select a compatible processor port, compiler, startup code and hardware drivers before building them. They are not automatically compatible with every Keil or LPC2129 simulator configuration.

2. Exercise Level 1 – Basic Task Programming

Exercise 1: Create Two Independent Tasks

Objective: Create two tasks that perform separate operations.

Requirements:

  • Create Task1 and Task2.
  • Task1 increments a counter.
  • Task2 increments another counter.
  • Both tasks periodically block.
  • Check task creation results.

Program:

#include "FreeRTOS.h"
#include "task.h"
#include <stdint.h>

volatile uint32_t task1Count = 0;
volatile uint32_t task2Count = 0;

void Task1(void *pvParameters)
{
    for (;;)
    {
        task1Count++;
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void Task2(void *pvParameters)
{
    for (;;)
    {
        task2Count++;
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    BaseType_t result1;
    BaseType_t result2;

    result1 = xTaskCreate(
        Task1, "Task1", 256, NULL, 2, NULL
    );

    result2 = xTaskCreate(
        Task2, "Task2", 256, NULL, 2, NULL
    );

    if ((result1 == pdPASS) && (result2 == pdPASS))
    {
        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Expected Result: Task1 increments approximately every 500 ms and Task2 approximately every 1000 ms. Observe the counters through a debugger or suitable diagnostic interface.

Concepts: Task creation, task delay, scheduler startup and independent task execution.

Exercise 2: Create Tasks with Different Priorities

Objective: Understand the effect of task priority.

Requirements: Create a high-priority task and a low-priority task. Make both tasks periodically block so that each receives execution time.

Program:

#include "FreeRTOS.h"
#include "task.h"

volatile uint32_t highCount = 0;
volatile uint32_t lowCount = 0;

void HighPriorityTask(void *pvParameters)
{
    for (;;)
    {
        highCount++;
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void LowPriorityTask(void *pvParameters)
{
    for (;;)
    {
        lowCount++;
        vTaskDelay(pdMS_TO_TICKS(200));
    }
}

int main(void)
{
    xTaskCreate(
        HighPriorityTask,
        "High",
        256,
        NULL,
        3,
        NULL
    );

    xTaskCreate(
        LowPriorityTask,
        "Low",
        256,
        NULL,
        1,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Expected Result: Both tasks execute because they periodically enter the Blocked state. When both are Ready, the higher-priority task is preferred under standard fixed-priority FreeRTOS scheduling.

Observation: Priority does not mean that a task executes continuously. Its state and scheduling conditions also matter.

Exercise 3: Implement a Periodic Task

Objective: Use vTaskDelayUntil() to maintain a nominal periodic execution schedule.

#include "FreeRTOS.h"
#include "task.h"

void PeriodicTask(void *pvParameters)
{
    TickType_t lastWakeTime;
    const TickType_t period =
        pdMS_TO_TICKS(1000);

    lastWakeTime = xTaskGetTickCount();

    for (;;)
    {
        /* Perform periodic operation */

        vTaskDelayUntil(
            &lastWakeTime,
            period
        );
    }
}

Expected Result: The task follows a nominal 1000 ms period when its execution and scheduling conditions permit.

Analysis: What happens if the task takes longer than 1000 ms to complete? Determine an appropriate overrun policy rather than assuming the API guarantees a deadline.

3. Exercise Level 2 – Task Communication

Exercise 4: Transfer an Integer Through a Queue

Objective: Send an integer from a producer task to a consumer task.

Requirements: Create a queue with five elements. The producer sends incrementing values. The consumer receives and processes them.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include <stdint.h>

QueueHandle_t dataQueue;

void ProducerTask(void *pvParameters)
{
    uint32_t value = 0;

    for (;;)
    {
        value++;

        if (xQueueSend(
                dataQueue,
                &value,
                pdMS_TO_TICKS(100)
            ) != pdPASS)
        {
            /* Handle queue-full condition */
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ConsumerTask(void *pvParameters)
{
    uint32_t receivedValue;

    for (;;)
    {
        if (xQueueReceive(
                dataQueue,
                &receivedValue,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process receivedValue */
        }
    }
}

int main(void)
{
    dataQueue = xQueueCreate(
        5,
        sizeof(uint32_t)
    );

    if (dataQueue != NULL)
    {
        xTaskCreate(
            ProducerTask, "Producer",
            256, NULL, 2, NULL
        );

        xTaskCreate(
            ConsumerTask, "Consumer",
            256, NULL, 2, NULL
        );

        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Expected Result: The consumer receives the integer values produced by the producer.

Concepts: Queue creation, queue send, queue receive, blocking and queue error handling.

Exercise 5: Send a Structure Through a Queue

Objective: Transfer multiple sensor fields as one queue item.

typedef struct
{
    uint16_t adcValue;
    float voltage;
    uint32_t sampleNumber;
} SensorData_t;

QueueHandle_t sensorQueue;

void SensorTask(void *pvParameters)
{
    SensorData_t sample = {0};

    for (;;)
    {
        sample.adcValue = 512;
        sample.voltage =
            (sample.adcValue * 3.3f) / 1023.0f;
        sample.sampleNumber++;

        xQueueSend(
            sensorQueue,
            &sample,
            0
        );

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ProcessingTask(void *pvParameters)
{
    SensorData_t received;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &received,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process received sensor data */
        }
    }
}

Expected Result: The consumer receives a complete copy of the sensor structure.

The ADC value is a simulated example. Actual sensor acquisition requires a hardware-specific ADC driver. The queue copies the structure bytes; it does not copy dynamically referenced objects inside pointer members.

Exercise 6: Use a Task Notification

Objective: Notify a task when another task has an event to report.

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t receiverHandle;

void ReceiverTask(void *pvParameters)
{
    uint32_t notificationValue;

    for (;;)
    {
        notificationValue = ulTaskNotifyTake(
            pdTRUE,
            portMAX_DELAY
        );

        /* Process notification count */
    }
}

void SenderTask(void *pvParameters)
{
    for (;;)
    {
        xTaskNotifyGive(receiverHandle);

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    xTaskCreate(
        ReceiverTask,
        "Receiver",
        256,
        NULL,
        2,
        &receiverHandle
    );

    if (receiverHandle != NULL)
    {
        xTaskCreate(
            SenderTask,
            "Sender",
            256,
            NULL,
            2,
            NULL
        );

        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Expected Result: The receiver task blocks until it receives a task notification. With pdTRUE, the notification count is cleared when retrieved.

4. Exercise Level 3 – Semaphores and Mutexes

Exercise 7: Synchronize Two Tasks Using a Binary Semaphore

Objective: Use a binary semaphore to signal an event between tasks.

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t eventSemaphore;

void EventTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                eventSemaphore,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Handle event */
        }
    }
}

void SignalTask(void *pvParameters)
{
    for (;;)
    {
        vTaskDelay(pdMS_TO_TICKS(1000));

        xSemaphoreGive(eventSemaphore);
    }
}

int main(void)
{
    eventSemaphore = xSemaphoreCreateBinary();

    if (eventSemaphore != NULL)
    {
        xTaskCreate(
            EventTask, "Event",
            256, NULL, 2, NULL
        );

        xTaskCreate(
            SignalTask, "Signal",
            256, NULL, 2, NULL
        );

        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Expected Result: EventTask blocks until SignalTask gives the semaphore.

Analysis: Repeated gives while the binary semaphore is already full do not accumulate multiple pending events. Use a counting semaphore or queue if every event must be retained.

Exercise 8: Protect a Shared Resource Using a Mutex

Objective: Protect a shared variable from concurrent task access.

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t dataMutex;
uint32_t sharedCounter = 0;

void CounterTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                dataMutex,
                portMAX_DELAY
            ) == pdPASS)
        {
            sharedCounter++;

            xSemaphoreGive(dataMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    dataMutex = xSemaphoreCreateMutex();

    if (dataMutex != NULL)
    {
        xTaskCreate(
            CounterTask, "Counter1",
            256, NULL, 2, NULL
        );

        xTaskCreate(
            CounterTask, "Counter2",
            256, NULL, 2, NULL
        );

        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Expected Result: Both tasks increment the shared counter while holding the same mutex.

Analysis: The mutex protects this shared variable access. It does not automatically make unrelated data or hardware operations safe.

Exercise 9: Implement a Counting Semaphore

Objective: Represent a limited number of available resources.

SemaphoreHandle_t resourceSemaphore;

void WorkerTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                resourceSemaphore,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Use one available resource */

            vTaskDelay(pdMS_TO_TICKS(500));

            xSemaphoreGive(resourceSemaphore);
        }
    }
}

int main(void)
{
    resourceSemaphore =
        xSemaphoreCreateCounting(3, 3);

    if (resourceSemaphore != NULL)
    {
        xTaskCreate(
            WorkerTask, "Worker1",
            256, NULL, 2, NULL
        );

        xTaskCreate(
            WorkerTask, "Worker2",
            256, NULL, 2, NULL
        );

        xTaskCreate(
            WorkerTask, "Worker3",
            256, NULL, 2, NULL
        );

        xTaskCreate(
            WorkerTask, "Worker4",
            256, NULL, 2, NULL
        );

        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Expected Result: At most three resource tokens are available at a time. The fourth worker must wait until a token is returned.

A counting semaphore tracks the number of available tokens. If workers need to identify or obtain a particular resource, use a resource-management structure such as a queue or free-list as well.

5. Exercise Level 4 – Event Groups and Timers

Exercise 10: Synchronize Tasks Using Event Groups

Objective: Wait until two system conditions have occurred.

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"

#define SENSOR_READY_BIT  (1U << 0)
#define COMM_READY_BIT    (1U << 1)

EventGroupHandle_t systemEvents;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform sensor initialization */

        xEventGroupSetBits(
            systemEvents,
            SENSOR_READY_BIT
        );

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void CommunicationTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform communication initialization */

        xEventGroupSetBits(
            systemEvents,
            COMM_READY_BIT
        );

        vTaskDelay(pdMS_TO_TICKS(1500));
    }
}

void ApplicationTask(void *pvParameters)
{
    const EventBits_t requiredBits =
        SENSOR_READY_BIT | COMM_READY_BIT;

    for (;;)
    {
        xEventGroupWaitBits(
            systemEvents,
            requiredBits,
            pdFALSE,
            pdTRUE,
            portMAX_DELAY
        );

        /* Both conditions have been observed */
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

Expected Result: ApplicationTask proceeds when both event bits are set.

Analysis: The example leaves the bits set. If the application clears bits on exit, define how other tasks waiting on the same bits will be affected.

Exercise 11: Create a One-Shot Software Timer

Objective: Execute a callback after a specified time.

#include "FreeRTOS.h"
#include "task.h"
#include "timers.h"

TimerHandle_t oneShotTimer;

void TimerCallback(TimerHandle_t xTimer)
{
    /* Keep callback short and non-blocking */
}

int main(void)
{
    oneShotTimer = xTimerCreate(
        "OneShot",
        pdMS_TO_TICKS(3000),
        pdFALSE,
        NULL,
        TimerCallback
    );

    if (oneShotTimer != NULL)
    {
        if (xTimerStart(
                oneShotTimer,
                0
            ) == pdPASS)
        {
            vTaskStartScheduler();
        }
    }

    for (;;)
    {
    }
}

Expected Result: The timer service task processes the start command and invokes the callback after the one-shot period, subject to tick resolution and scheduling delay.

The timer service task must be enabled and configured. A successful timer API return means the command was queued, not necessarily already processed.

Exercise 12: Implement an Auto-Reload Timer

Objective: Generate a periodic software timer event.

TimerHandle_t periodicTimer;

void PeriodicCallback(TimerHandle_t xTimer)
{
    /* Signal an application task */
}

void CreatePeriodicTimer(void)
{
    periodicTimer = xTimerCreate(
        "Periodic",
        pdMS_TO_TICKS(1000),
        pdTRUE,
        NULL,
        PeriodicCallback
    );

    if (periodicTimer != NULL)
    {
        xTimerStart(periodicTimer, 0);
    }
}

Expected Result: The callback is invoked periodically by the timer service task. It should not perform lengthy processing or blocking operations.

6. Exercise Level 5 – Interrupt-to-Task Communication

Exercise 13: Signal a Task from an ISR

Objective: Use an ISR-safe semaphore API to wake a task.

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t interruptSemaphore;

void InterruptTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                interruptSemaphore,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Perform deferred interrupt work */
        }
    }
}

/* Called by the hardware interrupt vector */
void Peripheral_IRQHandler(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the peripheral interrupt here */

    xSemaphoreGiveFromISR(
        interruptSemaphore,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(
        higherPriorityTaskWoken
    );
}

Expected Result: The ISR signals the task, which becomes Ready and performs the deferred work when scheduled.

Port requirement: The interrupt handler declaration, interrupt acknowledgement, ISR-safe API availability and yield macro are processor-port-specific. This is a conceptual example, not a complete LPC2129 VIC interrupt driver.

Exercise 14: Transfer an Integer from ISR to Task Using a Queue

Objective: Send an event value from an interrupt handler to a receiving task.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include <stdint.h>

QueueHandle_t interruptQueue;

void ReceiverTask(void *pvParameters)
{
    uint32_t receivedValue;

    for (;;)
    {
        if (xQueueReceive(
                interruptQueue,
                &receivedValue,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process the event value */
        }
    }
}

void Peripheral_IRQHandler(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;
    uint32_t eventValue = 1;

    /* Read and acknowledge peripheral first */

    xQueueSendFromISR(
        interruptQueue,
        &eventValue,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(
        higherPriorityTaskWoken
    );
}

Expected Result: The receiving task processes values placed in the queue by the ISR.

Analysis: What happens if the queue is full? Add an overflow counter or another explicitly designed policy. Never use a blocking queue API from an ISR.

7. Exercise Level 6 – Memory Management and Debugging

Exercise 15: Compare Dynamic and Static Task Creation

Objective: Understand the storage requirements of both task-creation methods.

Dynamic creation:

TaskHandle_t dynamicTaskHandle;

xTaskCreate(
    WorkerTask,
    "Dynamic",
    256,
    NULL,
    2,
    &dynamicTaskHandle
);

Static creation:

static StaticTask_t taskControlBlock;

static StackType_t taskStack[256];

TaskHandle_t staticTaskHandle;

staticTaskHandle = xTaskCreateStatic(
    WorkerTask,
    "Static",
    256,
    NULL,
    2,
    taskStack,
    &taskControlBlock
);

Expected Result: Both methods create a task if the corresponding configuration and memory requirements are satisfied.

Analysis: Static creation uses application-provided storage. Dynamic creation obtains required memory from the configured allocator.

Exercise 16: Measure Task Stack High-Water Mark

Objective: Inspect the observed minimum unused stack space.

void MonitoringTask(void *pvParameters)
{
    TaskHandle_t monitoredTask =
        (TaskHandle_t)pvParameters;

    UBaseType_t unusedStack;

    for (;;)
    {
        unusedStack =
            uxTaskGetStackHighWaterMark(
                monitoredTask
            );

        /* Record unusedStack */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

Expected Result: The debugger or diagnostic output shows the minimum unused stack observed for the monitored task.

The returned value is in stack elements. Convert to bytes using unusedStack * sizeof(StackType_t). Testing must exercise realistic worst-case call paths; the measurement alone is not proof of stack safety.

Exercise 17: Detect Queue Overflow

Objective: Track failed queue sends.

volatile uint32_t droppedSamples = 0;

void ProducerTask(void *pvParameters)
{
    uint32_t sample = 0;

    for (;;)
    {
        sample++;

        if (xQueueSend(
                dataQueue,
                &sample,
                0
            ) != pdPASS)
        {
            droppedSamples++;
        }

        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

Expected Result: When the consumer cannot keep up and the queue becomes full, failed sends are counted.

Analysis: In a production system, protect shared diagnostic counters as needed. volatile alone does not make an increment atomic or provide synchronization.

8. Exercise Level 7 – Integrated Embedded Application

Exercise 18: Design a Sensor Monitoring System

Objective: Design a FreeRTOS application that periodically samples a sensor and reports threshold violations.

Required tasks:

  • SensorTask – acquires sensor samples periodically.
  • ProcessingTask – calculates the measurement and checks thresholds.
  • CommunicationTask – reports measurement and status.

Required kernel objects:

  • Queue for transferring sensor samples.
  • Queue or notification for reporting alarm status.
  • Optional event group for system state.

Design requirements:

  1. Define a sensor data structure.
  2. Choose the sampling period.
  3. Calculate the queue capacity based on sample rate and consumer delay.
  4. Define queue-full behavior.
  5. Specify threshold and hysteresis rules.
  6. Keep hardware access in a clearly defined driver layer.

Expected Result: The application transfers sensor data between tasks and reports alarm conditions without requiring each task to access the same hardware resource independently.

Exercise 19: Design a UART Communication System

Objective: Design task-based UART transmission and interrupt-driven reception.

Required architecture:

  • UARTTxTask – owns normal UART transmission.
  • UART RX ISR – reads incoming data and transfers it to a queue or ring buffer.
  • CommandTask – parses received messages.
  • StatusTask – prepares outgoing status messages.

Design questions:

  1. How will multiple application tasks request transmission?
  2. How will the RX ISR handle buffer overflow?
  3. How will message boundaries be identified?
  4. How will DMA buffer ownership be managed if DMA is used?
  5. How will UART errors be reported?

Expected Result: A modular communication design with controlled resource ownership and deferred command processing.

Exercise 20: Design a Motor Control System

Objective: Design a multitasking motor-control application.

Required tasks:

  • CommandTask – receives speed or direction commands.
  • ControlTask – calculates the control output.
  • FeedbackTask – reads speed or position feedback.
  • ProtectionTask – monitors fault conditions.
  • CommunicationTask – reports system status.

Design requirements:

  • Use a queue for command transfer.
  • Define one software owner for normal actuator output.
  • Use appropriate synchronization for shared measurements.
  • Define overcurrent and overtemperature fault handling.
  • Consider an independent hardware shutdown path.
  • Analyze control-loop period, execution time and response time.

Expected Result: A modular design that separates command handling, feedback, control, protection and communication.

A simulator-only exercise cannot establish real motor stability, power-stage safety or physical fault response. Those require appropriate hardware, instrumentation and safety testing.

9. Numerical and Analytical Exercises

Problem 1: Calculate Task Utilization

A task has execution time 2 ms and period 10 ms. Calculate utilization.

U = C / T
  = 2 / 10
  = 0.2

Utilization = 20%

Problem 2: Calculate Tick Period

The FreeRTOS tick rate is configured to 500 Hz.

Tick Period = 1 / 500
            = 0.002 seconds
            = 2 ms

Problem 3: Calculate Task Stack Memory

A task uses a stack depth of 256 elements. Assume sizeof(StackType_t) is 4 bytes.

Stack Memory = 256 × 4
             = 1024 bytes
             = 1 KB

Problem 4: Estimate Queue Storage

A queue contains 10 elements, each 16 bytes in size.

Payload Storage = 10 × 16
                = 160 bytes

This calculation excludes queue control structures, alignment and allocator overhead.

Problem 5: Calculate Sensor Voltage

A 10-bit ADC produces a count of 512 with a nominal 3.3 V reference.

Voltage = ADC Count × Vref / 1023

        = 512 × 3.3 / 1023

        ≈ 1.652 V

Problem 6: Estimate Queue Capacity

A producer generates 20 samples per second. The consumer may be delayed for 0.5 seconds. Estimate the number of samples generated during that delay.

Samples = Arrival Rate × Delay

        = 20 × 0.5

        = 10 samples

Ten samples cover only the stated interval under the assumed steady arrival rate. Add capacity for bursts and other delays, and verify that the consumer's long-term processing rate is sufficient.

13. Lesson Summary

These exercises cover the practical FreeRTOS skills expected in embedded firmware development: task creation, scheduling, communication, synchronization, interrupt handling, timing analysis, memory management and system-level design.

Complete the exercises in increasing difficulty. For each program, verify return values, inspect task states, measure timing and document any assumptions about the target processor and hardware.
