3. Understanding the Producer-Consumer Model

The producer-consumer model separates data generation from data processing.

Producer

  • Generates or acquires data.
  • Prepares a data item.
  • Sends the item to the queue.
  • Handles a failed send operation if the queue is full.

Consumer

  • Waits for data to become available.
  • Receives an item from the queue.
  • Processes the received item.
  • Returns to waiting for the next item.

The queue decouples the execution timing of the producer and consumer.

A queue does not guarantee that data will always be accepted. The application must define what happens when the queue becomes full or when data cannot be processed in time.

5. FreeRTOS Queue Concept

A FreeRTOS queue is a kernel object used to transfer data between tasks and, through suitable APIs, between interrupt handlers and tasks.

Queue Characteristics

  • A queue has a fixed capacity when created.
  • Each queue item has a fixed size.
  • Queue send operations copy the item into queue storage.
  • Queue receive operations copy an item out of the queue.
  • Tasks can block while waiting for queue space or data.
  • Queues support multiple senders and receivers.

Queue Creation API

QueueHandle_t xQueueCreate(
    UBaseType_t uxQueueLength,
    UBaseType_t uxItemSize
);
ParameterMeaning
uxQueueLengthMaximum number of items the queue can store.
uxItemSizeSize of each item in bytes.

The function returns a queue handle. A NULL handle indicates that creation failed.

6. Queue Send and Receive APIs

xQueueSend()

Sends an item to the back of a queue.

BaseType_t xQueueSend(
    QueueHandle_t xQueue,
    const void *pvItemToQueue,
    TickType_t xTicksToWait
);

xQueueReceive()

Receives and removes an item from the front of a queue.

BaseType_t xQueueReceive(
    QueueHandle_t xQueue,
    void *pvBuffer,
    TickType_t xTicksToWait
);

Return Values

Return ValueMeaning
pdPASSOperation succeeded.
errQUEUE_FULLSend operation could not complete.
errQUEUE_EMPTYReceive operation could not complete.

The exact failure result depends on the API and context. For ordinary task-context send and receive operations, check for pdPASS and handle failure appropriately.

xTicksToWait specifies how long the calling task may wait for the operation. It is not the queue's data-processing period.

8. Complete FreeRTOS Application Code

Objective: Create one producer task and one consumer task that communicate through a queue.

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "stdint.h"
#include "stdio.h"

/* Queue handle */
static QueueHandle_t sensorQueue = NULL;

/* Sensor data structure */
typedef struct
{
    uint32_t sensorId;
    int32_t temperature;
} SensorData_t;

/* Task declarations */
static void ProducerTask(void *pvParameters);
static void ConsumerTask(void *pvParameters);

/* Producer task */
static void ProducerTask(void *pvParameters)
{
    SensorData_t data;

    (void) pvParameters;

    data.sensorId = 1;
    data.temperature = 25;

    for (;;)
    {
        /* Generate simulated sensor data */
        data.temperature++;

        /* Send data to queue */
        if (xQueueSend(
                sensorQueue,
                &data,
                pdMS_TO_TICKS(100)
            ) == pdPASS)
        {
            /* Data successfully queued */
        }
        else
        {
            /* Queue send timeout or failure */
        }

        /* Generate next sample after 500 ms */
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

/* Consumer task */
static void ConsumerTask(void *pvParameters)
{
    SensorData_t receivedData;

    (void) pvParameters;

    for (;;)
    {
        /* Wait for data from producer */
        if (xQueueReceive(
                sensorQueue,
                &receivedData,
                portMAX_DELAY
            ) == pdPASS)
        {
            /* Process received data */
            printf(
                "Sensor ID: %lu, Temperature: %ld C\r\n",
                (unsigned long)receivedData.sensorId,
                (long)receivedData.temperature
            );
        }
    }
}

/* Main application */
int main(void)
{
    /* Initialize UART and other hardware here */

    /* Create queue: 5 items, each sizeof(SensorData_t) */
    sensorQueue = xQueueCreate(
        5,
        sizeof(SensorData_t)
    );

    if (sensorQueue == NULL)
    {
        for (;;)
        {
            /* Queue creation failed */
        }
    }

    /* Create producer task */
    if (xTaskCreate(
            ProducerTask,
            "Producer",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
            /* Producer creation failed */
        }
    }

    /* Create consumer task */
    if (xTaskCreate(
            ConsumerTask,
            "Consumer",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
            /* Consumer creation failed */
        }
    }

    /* Start scheduler */
    vTaskStartScheduler();

    /* Reached if scheduler startup fails */
    for (;;)
    {
    }
}
This is an application-level example. A complete target project must provide the correct FreeRTOS port, configuration, startup code, linker settings and UART implementation. The standard C library's printf() must be retargeted to a supported output interface if UART output is required.

);

The consumer displays the received temperature through the configured output interface.

10. Queue Operation Sequence

PRODUCER TASK | Generate Data | xQueueSend() | QUEUE STORAGE [25][26][27] | xQueueReceive() | CONSUMER TASK | Process Measurement | Display Result

The queue preserves the order of items sent to it under normal FIFO operation.

11. Understanding Queue Capacity

The queue in this project has a capacity of five items.

sensorQueue = xQueueCreate(
    5,
    sizeof(SensorData_t)
);

When five items are waiting in the queue, another send cannot complete until space becomes available or the send timeout expires.

Queue States

Queue StateBehavior
EmptyConsumer may block while waiting for an item.
Partially fullProducer can add another item.
FullProducer may block or receive a failure result.
Item receivedOne item is removed, creating space.
Queue capacity must be selected using expected data bursts, consumer delays and memory constraints. A larger queue does not correct a permanently slower consumer.

12. Blocking Time in Queue Operations

FreeRTOS queue operations can block a task for a specified number of ticks.

Non-Blocking Send

xQueueSend(sensorQueue, &data, 0);

The producer does not wait if the queue is full.

Finite Blocking Send

xQueueSend(
    sensorQueue,
    &data,
    pdMS_TO_TICKS(100)
);

The producer can wait up to 100 ms for space, subject to tick resolution and scheduling.

Indefinite Receive Wait

xQueueReceive(
    sensorQueue,
    &receivedData,
    portMAX_DELAY
);

The consumer can wait indefinitely for an item when the relevant configuration supports this behavior.

A blocked consumer becomes Ready when data becomes available, but it does not necessarily execute immediately. Higher-priority Ready tasks and interrupt activity can delay execution.

14. Producer Faster Than Consumer

Consider a system in which the producer generates data faster than the consumer processes it.

Example

TaskOperation Interval
Producer100 ms
Consumer500 ms

The queue may gradually fill because data arrives faster than it is processed.

Possible Solutions

  • Improve consumer processing throughput.
  • Reduce unnecessary producer sampling.
  • Increase queue capacity if bursts justify it.
  • Use a latest-value design if older readings can be discarded.
  • Define a safe overflow policy.
  • Record queue-full events for diagnostics.
Increasing queue capacity only absorbs a finite backlog. If the long-term arrival rate exceeds the service rate, the queue will eventually fill.

15. Queue Item Copying and Pointer Queues

FreeRTOS queues copy the configured number of bytes for each item.

Structure Queue

SensorData_t data;

xQueueSend(
    sensorQueue,
    &data,
    0
);

The structure contents are copied into the queue.

Pointer Queue

SensorData_t *dataPointer;

xQueueSend(
    pointerQueue,
    &dataPointer,
    0
);

When a queue stores pointers, it copies the pointer value, not the object that the pointer references.

The pointed-to object must remain valid until the receiver has finished using it. Define ownership and lifetime rules to prevent dangling pointers, data races and accidental reuse of buffers.

16. Queue Creation Failure Handling

Queue creation can fail if the required memory cannot be allocated.

sensorQueue = xQueueCreate(
    5,
    sizeof(SensorData_t)
);

if (sensorQueue == NULL)
{
    /* Handle allocation failure */
    Error_Handler();
}

In a production system, the failure handler should move the application into a defined safe state, record the fault if possible and avoid continuing with an invalid queue handle.

17. Static Queue Allocation

FreeRTOS can support static queue allocation when the relevant configuration options and APIs are available.

Example

static StaticQueue_t queueControlBlock;

static uint8_t queueStorage[
    5 * sizeof(SensorData_t)
];

static QueueHandle_t sensorQueue;

void CreateSensorQueue(void)
{
    sensorQueue = xQueueCreateStatic(
        5,
        sizeof(SensorData_t),
        queueStorage,
        &queueControlBlock
    );
}

Static allocation allows the application to provide the memory used by the queue rather than requesting it from the FreeRTOS heap.

The storage buffer must have suitable alignment and size for the target. Static allocation APIs require the corresponding FreeRTOS configuration and supported kernel version.

18. Queue Design Best Practices

  • Choose a suitable item size.
  • Calculate queue memory usage before implementation.
  • Check every queue creation result.
  • Check every send and receive result where failure is possible.
  • Use finite timeouts when the application needs recovery from stalled communication.
  • Keep consumer processing bounded.
  • Avoid unnecessary large structures in queues.
  • Define pointer ownership if pointers are queued.
  • Use queue reset only with a deliberate coordination policy.
  • Monitor queue saturation during stress testing.

Change the queue length from five items to ten items.

sensorQueue = xQueueCreate(

);

Expected result: The queue can hold ten items instead of five. Its RAM requirement increases accordingly.

20. Practical Exercise 2 – Add a Second Producer

Objective: Create another producer task that sends data to the same queue.

  • Create Producer2Task().
  • Assign a different sensor ID.
  • Send the generated structure to the same queue.
  • Keep the consumer task unchanged.
  • Observe the received sensor IDs.

Expected result: The consumer receives data from both producers. The queue provides FIFO ordering based on successful insertion order.

When multiple producers send concurrently, the queue serializes queue operations. Application-level data ordering should still be defined if timestamps, sequence numbers or source priority matter.

21. Practical Exercise 3 – Add Queue Timeout Handling

Objective: Handle a queue send timeout.

if (xQueueSend(
        sensorQueue,
        &data,
        pdMS_TO_TICKS(100)
    ) != pdPASS)
{
    /* Record queue-send failure */
    queueErrorCount++;
}

Expected result: A failed send is detected and recorded instead of silently ignored.

If queueErrorCount is accessed by multiple tasks or interrupts, protect it with an appropriate atomic or synchronization mechanism. volatile alone is not sufficient.

22. Practical Exercise 4 – Monitor Queue Occupancy

Objective: Monitor how many items are waiting in the queue.

UBaseType_t waitingItems;

waitingItems = uxQueueMessagesWaiting(sensorQueue);

This API provides a snapshot of the number of items currently waiting in the queue.

Expected result: A value between zero and the configured queue capacity. The snapshot can become outdated immediately if other tasks access the queue.

23. Practical Exercise 5 – Implement a Latest-Value Queue

Objective: Store only the latest measurement when old pending measurements are not required.

Create a queue with one item:

sensorQueue = xQueueCreate(
    1,
    sizeof(SensorData_t)
);

For a queue of length one, the producer can use:

xQueueOverwrite(
    sensorQueue,
    &data
);

Expected result: A new measurement replaces the existing pending item. This is useful for latest-value reporting, but it is not appropriate when every measurement must be processed.

25. Keil µVision and LPC2129 Simulator Notes

The LPC2129 is based on ARM7TDMI-S. Queue communication can be studied conceptually and through a compatible FreeRTOS build, but the correct port and compiler integration must be verified first.

Study Activities

  • Inspect the producer and consumer task functions.
  • Set breakpoints around queue send and receive calls.
  • Inspect the sensor data structure.
  • Observe task states when the consumer blocks.
  • Inspect queue-related variables where debugger visibility permits.
  • Review memory allocation and stack usage.
Do not assume that a standard FreeRTOS ARM7 port is automatically compatible with LPC2129 and Keil µVision. The simulator may not model all target behavior. Use a verified compatible port or a supported development board for executable hands-on testing.

27. Lesson Summary

  • FreeRTOS queues provide synchronized communication between tasks.
  • The producer generates data and sends it to the queue.
  • The consumer receives and processes queued data.
  • xQueueCreate() creates a queue.
  • xQueueSend() inserts an item.
  • xQueueReceive() removes and copies an item.
  • Queue items are copied, including structure contents.
  • Pointer queues copy pointer values, not the referenced objects.
  • Blocking times determine how long tasks may wait.
  • Queue capacity and overflow behavior must be designed carefully.
  • Static allocation can provide predictable queue memory use.
