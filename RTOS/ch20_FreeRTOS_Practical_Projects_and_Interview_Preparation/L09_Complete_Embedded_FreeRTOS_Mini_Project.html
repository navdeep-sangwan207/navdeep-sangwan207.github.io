1. Project Overview

This mini project integrates multiple FreeRTOS concepts into one embedded application. It demonstrates how tasks, queues, synchronization, sensor monitoring, UART communication and fault handling can work together.

Project Title

Real-Time Embedded Monitoring and Control System Using FreeRTOS

Project Objectives

  • Acquire sensor measurements periodically.
  • Process sensor data in a separate task.
  • Monitor operating conditions and detect faults.
  • Exchange data between tasks using queues.
  • Provide command and status communication through UART.
  • Control a simulated actuator output.
  • Use task scheduling and synchronization appropriately.
  • Develop a modular and testable embedded application.

2. Application Scenario

Consider a small industrial monitoring and control unit that monitors temperature and supply voltage and controls an actuator output.

Input / OutputPurpose
Temperature sensorMonitors system temperature.
Voltage measurementMonitors the supply voltage.
UART interfaceReceives commands and reports system status.
PWM outputControls a simulated actuator command.
Fault indicatorRepresents an application-level alarm state.

Example operating conditions:

  • Normal temperature: below the configured alarm threshold.
  • High temperature: activate an alarm condition.
  • Low or high supply voltage: report a voltage fault.
  • STOP command: request actuator shutdown.
  • STATUS command: request current measurement and operating state.
Thresholds and sensor conversion values in this lesson are illustrative. A real system must use the actual sensor specifications, calibration data and hardware safety limits.

7. Global Queue and State Definitions

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "event_groups.h"
#include "stdio.h"
#include "string.h"

#define FAULT_TEMPERATURE   (1U << 0)
#define FAULT_VOLTAGE       (1U << 1)

#define TEMP_LIMIT          60U
#define VOLTAGE_MIN         10U
#define VOLTAGE_MAX         15U

static QueueHandle_t sensorQueue;
static QueueHandle_t commandQueue;
static QueueHandle_t statusQueue;

static EventGroupHandle_t systemEvents;

#define SYSTEM_RUNNING_BIT  (1U << 0)
#define SYSTEM_FAULT_BIT    (1U << 1)

static volatile uint16_t simulatedTemperature = 30;
static volatile uint16_t simulatedVoltage = 12;

static volatile uint16_t actuatorOutput = 0;
The volatile variables above are used only to represent simple simulated input and output values. volatile does not provide atomicity, mutual exclusion or general inter-task synchronization. Production code should define clear ownership and use appropriate synchronization for shared state.

8. Hardware Abstraction Functions

Application tasks should call driver functions rather than directly manipulating peripheral registers throughout the application.

void Hardware_Init(void);

uint16_t ReadTemperatureSensor(void);

uint16_t ReadVoltageSensor(void);

void SetActuatorOutput(uint16_t value);

void DisableActuator(void);

These functions are hardware-dependent. For simulation, they can return controlled test values and update software variables instead of accessing physical peripherals.

9. Sensor Acquisition Task

The sensor task periodically reads the temperature and voltage measurements and sends them to the processing task.

static void SensorTask(void *pvParameters)
{
    SensorData_t data;
    TickType_t previousWakeTime;

    (void) pvParameters;

    previousWakeTime = xTaskGetTickCount();

    for (;;)
    {
        data.temperature = ReadTemperatureSensor();
        data.voltage = ReadVoltageSensor();

        if (xQueueSend(
                sensorQueue,
                &data,
                0
            ) != pdPASS)
        {
            /* Record dropped measurement */
        }

        vTaskDelayUntil(
            &previousWakeTime,
            pdMS_TO_TICKS(500)
        );
    }
}

The task has a nominal 500 ms sampling period. Its actual execution timing depends on the RTOS configuration and system workload.

10. Data Processing Task

The processing task receives sensor data and creates a status message.

static void ProcessingTask(void *pvParameters)
{
    SensorData_t data;
    StatusMessage_t message;

    (void) pvParameters;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &data,
                portMAX_DELAY
            ) == pdPASS)
        {
            snprintf(
                message.text,
                sizeof(message.text),
                "TEMP=%u C, VOLTAGE=%u V\r\n",
                (unsigned)data.temperature,
                (unsigned)data.voltage
            );

            if (xQueueSend(
                    statusQueue,
                    &message,
                    0
                ) != pdPASS)
            {
                /* Record dropped status message */
            }
        }
    }
}

The processing task converts measurements into a readable status message and sends it to the UART transmission queue.

11. Monitoring and Fault Detection Task

The monitoring task checks the latest sensor measurements and sets fault event bits when operating limits are exceeded.

static void MonitorTask(void *pvParameters)
{
    SensorData_t data;
    EventBits_t faults;

    (void) pvParameters;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &data,
                portMAX_DELAY
            ) == pdPASS)
        {
            faults = 0;

            if (data.temperature > TEMP_LIMIT)
            {
                faults |= FAULT_TEMPERATURE;
            }

            if (data.voltage < VOLTAGE_MIN ||
                data.voltage > VOLTAGE_MAX)
            {
                faults |= FAULT_VOLTAGE;
            }

            if (faults != 0)
            {
                xEventGroupSetBits(
                    systemEvents,
                    SYSTEM_FAULT_BIT
                );

                if (faults & FAULT_TEMPERATURE)
                {
                    xEventGroupSetBits(
                        systemEvents,
                        FAULT_TEMPERATURE
                    );
                }

                if (faults & FAULT_VOLTAGE)
                {
                    xEventGroupSetBits(
                        systemEvents,
                        FAULT_VOLTAGE
                    );
                }
            }
            else
            {
                xEventGroupClearBits(
                    systemEvents,
                    FAULT_TEMPERATURE |
                    FAULT_VOLTAGE
                );

                /*
                 * Clear the overall fault state only
                 * after the application's recovery
                 * policy confirms it is safe.
                 */
            }
        }
    }
}
This example demonstrates threshold detection, not a complete fault-latching or recovery design. The monitor task and processing task must not compete to consume the same queue: a FreeRTOS queue distributes each item to one receiving task, it does not broadcast each item to every receiver. A production design should use separate queues, a single consumer that distributes data, or another explicit fan-out mechanism.

12. Correct Sensor Data Distribution

Because both ProcessingTask and MonitorTask cannot independently receive every measurement from one ordinary queue, this project should use a dedicated distribution task or separate queues.

Recommended Design

SENSOR TASK | v SENSOR QUEUE | v SENSOR DISTRIBUTOR / \ v v PROCESSING MONITORING QUEUE QUEUE | | v v STATUS DATA FAULT CHECK

The distributor receives each sample once and copies it into the two destination queues.

Illustrative Distribution Task

static QueueHandle_t processingQueue;
static QueueHandle_t monitoringQueue;

static void SensorDistributorTask(void *pvParameters)
{
    SensorData_t data;

    (void) pvParameters;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &data,
                portMAX_DELAY
            ) == pdPASS)
        {
            if (xQueueSend(
                    processingQueue,
                    &data,
                    0
                ) != pdPASS)
            {
                /* Processing queue overflow */
            }

            if (xQueueSend(
                    monitoringQueue,
                    &data,
                    0
                ) != pdPASS)
            {
                /* Monitoring queue overflow */
            }
        }
    }
}

Now each destination task receives its own copy of every successfully distributed sample.

13. Command Processing Task

The command task receives validated commands from a UART parser or another input interface and forwards them to the control task.

static void CommandTask(void *pvParameters)
{
    Command_t command;

    (void) pvParameters;

    for (;;)
    {
        /*
         * Example command generation.
         * Replace with a UART parser in a real project.
         */
        command.type = CMD_SET_OUTPUT;
        command.value = 50;

        if (xQueueSend(
                commandQueue,
                &command,
                pdMS_TO_TICKS(50)
            ) != pdPASS)
        {
            /* Record command queue failure */
        }

        vTaskDelay(pdMS_TO_TICKS(2000));
    }
}

14. Control Task

The control task is the single software owner of the normal actuator output.

static void ControlTask(void *pvParameters)
{
    Command_t command;
    EventBits_t events;

    (void) pvParameters;

    for (;;)
    {
        events = xEventGroupGetBits(systemEvents);

        if (events & SYSTEM_FAULT_BIT)
        {
            DisableActuator();
            actuatorOutput = 0;
            continue;
        }

        if (xQueueReceive(
                commandQueue,
                &command,
                pdMS_TO_TICKS(100)
            ) == pdPASS)
        {
            switch (command.type)
            {
                case CMD_START:
                    xEventGroupSetBits(
                        systemEvents,
                        SYSTEM_RUNNING_BIT
                    );
                    break;

                case CMD_STOP:
                    DisableActuator();
                    actuatorOutput = 0;

                    xEventGroupClearBits(
                        systemEvents,
                        SYSTEM_RUNNING_BIT
                    );
                    break;

                case CMD_SET_OUTPUT:
                    if (command.value <= 100)
                    {
                        events = xEventGroupGetBits(
                            systemEvents
                        );

                        if ((events & SYSTEM_FAULT_BIT) == 0)
                        {
                            actuatorOutput = command.value;
                            SetActuatorOutput(
                                actuatorOutput
                            );
                        }
                    }
                    break;

                case CMD_STATUS:
                    /* Status handled by communication task */
                    break;

                default:
                    /* Reject unsupported command */
                    break;
            }
        }
    }
}
This simplified example checks the fault state before normal output updates, but task-level checks alone cannot guarantee immediate shutdown. A fault can occur between checking the event bits and changing the output. Critical protection should use a hardware shutdown path or another design with a clearly defined atomic safety mechanism.

15. UART Transmission Task

The UART TX task receives status messages and sends them through a hardware-specific UART driver.

void UART_SendBuffer(
    const char *buffer,
    uint16_t length
);

static void UARTTxTask(void *pvParameters)
{
    StatusMessage_t message;

    (void) pvParameters;

    for (;;)
    {
        if (xQueueReceive(
                statusQueue,
                &message,
                portMAX_DELAY
            ) == pdPASS)
        {
            UART_SendBuffer(
                message.text,
                (uint16_t)strlen(message.text)
            );
        }
    }
}

The UART driver must ensure that the message buffer remains valid until transmission no longer requires it. This example assumes the driver completes the transfer before returning.

16. Fault Recovery Policy

A complete application needs a defined policy for entering, remaining in and recovering from a fault state.

StateMeaningTypical Action
INITIALIZINGSystem is starting.Initialize drivers and RTOS objects.
READYSystem checks have passed.Accept valid commands.
RUNNINGNormal operation is active.Monitor sensors and control outputs.
FAULTUnsafe or abnormal condition detected.Disable output and record fault.
RECOVERYRecovery conditions are being checked.Require safe measurements and valid reset conditions.

For safety-relevant equipment, fault recovery should not automatically restart an actuator merely because one measurement returns to the normal range. The restart policy must account for the cause, persistence and risk of the fault.

17. Main Function and RTOS Object Creation

The following initialization example creates the queues, event group and application tasks.

int main(void)
{
    Hardware_Init();

    sensorQueue = xQueueCreate(
        5,
        sizeof(SensorData_t)
    );

    processingQueue = xQueueCreate(
        5,
        sizeof(SensorData_t)
    );

    monitoringQueue = xQueueCreate(
        5,
        sizeof(SensorData_t)
    );

    commandQueue = xQueueCreate(
        5,
        sizeof(Command_t)
    );

    statusQueue = xQueueCreate(
        8,
        sizeof(StatusMessage_t)
    );

    systemEvents = xEventGroupCreate();

    if (sensorQueue == NULL ||
        processingQueue == NULL ||
        monitoringQueue == NULL ||
        commandQueue == NULL ||
        statusQueue == NULL ||
        systemEvents == NULL)
    {
        for (;;)
        {
            /* Initialization failure */
        }
    }

    if (xTaskCreate(
            SensorTask,
            "Sensor",
            256,
            NULL,
            3,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    if (xTaskCreate(
            SensorDistributorTask,
            "Distributor",
            256,
            NULL,
            3,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    if (xTaskCreate(
            ProcessingTask,
            "Processing",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    if (xTaskCreate(
            MonitorTask,
            "Monitor",
            256,
            NULL,
            4,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    if (xTaskCreate(
            CommandTask,
            "Command",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    if (xTaskCreate(
            ControlTask,
            "Control",
            256,
            NULL,
            4,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    if (xTaskCreate(
            UARTTxTask,
            "UART_TX",
            256,
            NULL,
            1,
            NULL
        ) != pdPASS)
    {
        for (;;);
    }

    vTaskStartScheduler();

    for (;;)
    {
        /* Scheduler startup failure */
    }
}
This initialization listing is an architectural integration example. The task function definitions, sensor distributor, hardware driver implementations, UART receive/parser logic and robust fault-state handling must all be included before building a complete project. Stack depths are illustrative stack elements, not byte counts.

18. Application Data Flow

  1. Hardware initialization configures the peripherals and driver interfaces.
  2. FreeRTOS queues and event groups are created.
  3. Application tasks are created.
  4. The scheduler starts.
  5. The sensor task periodically acquires measurements.
  6. The distributor sends each sample to processing and monitoring queues.
  7. The processing task formats measurement data for reporting.
  8. The monitoring task checks the configured operating limits.
  9. The command task submits validated control requests.
  10. The control task manages normal actuator output.
  11. The UART TX task transmits status messages.
  12. Fault handling places the system into its defined safe state.

20. Debugging and Performance Analysis

During development, monitor the following:

  • Task states and priorities.
  • Queue occupancy and failed queue operations.
  • Task stack high-water marks.
  • FreeRTOS heap usage where supported.
  • Task execution time and response time.
  • Periodic task jitter.
  • Interrupt latency.
  • Fault detection and shutdown response.

Useful FreeRTOS APIs

APIPurpose
uxTaskGetSystemState()Obtains task status information, when enabled.
uxTaskGetStackHighWaterMark()Reports minimum observed unused task stack.
xPortGetFreeHeapSize()Reports free heap space where supported.
uxQueueMessagesWaiting()Reports the number of queued items at the time of the call.
xEventGroupGetBits()Reads current event-group bits.
These measurements are useful for debugging but do not prove worst-case execution time, schedulability or complete stack safety. Availability depends on the FreeRTOS version, configuration and port.

24. Lesson Summary

  • A complete embedded application can be divided into sensor, processing, monitoring, command, control and communication tasks.
  • Queues transfer structured data between tasks.
  • A distributor or explicit fan-out design is required when multiple tasks need the same measurement.
  • Event groups represent shared system conditions.
  • A single software owner should manage normal hardware output changes.
  • Fault handling must define safe-state and recovery behavior.
  • Hardware protection may be required for fast or safety-critical shutdown.
  • Task timing, queue capacity and stack usage must be measured and analyzed.
  • Simulator testing validates selected software behavior but does not replace hardware testing.
