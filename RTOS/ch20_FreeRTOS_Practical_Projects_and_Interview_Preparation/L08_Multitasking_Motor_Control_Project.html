After completing this lesson, you will be able to:

  • Understand speed command, feedback and protection tasks.

2. Project Introduction

Motor-control systems are used in industrial automation, robotics, electric vehicles, pumps, fans, conveyors and home appliances.

A motor-control application may need to perform several operations simultaneously:

  • Generate a motor speed command.
  • Read speed or position feedback.
  • Update the PWM duty cycle.
  • Monitor current and temperature.
  • Detect faults and stop the motor when necessary.
  • Communicate status through UART.

FreeRTOS allows these operations to be organized into separate tasks with defined priorities and communication mechanisms.

Project Objective

Design a multitasking motor-control application that receives a speed command, updates a simulated PWM output, monitors motor feedback and handles protection events.

This lesson demonstrates the software architecture. A real motor must be driven through a suitable power stage and gate driver. A microcontroller GPIO pin or PWM output must never be connected directly to a motor requiring substantial current.

5. Motor Control Fundamentals

Motor speed can be controlled by changing the voltage or power delivered to the motor. In many embedded applications, PWM is used to control the power stage.

Pulse Width Modulation

PWM switches a digital output between ON and OFF states at a configured frequency. The duty cycle is the percentage of one period during which the signal is active.

Duty Cycle (%) =
    (ON Time / PWM Period) * 100
Duty CycleIllustrative Interpretation
0%Output continuously inactive.
25%Output active for one-quarter of each period.
50%Output active for half of each period.
75%Output active for three-quarters of each period.
100%Output continuously active.
The relationship between PWM duty cycle and actual motor speed depends on the motor, power stage, supply voltage, load and control strategy. A 50% duty cycle does not universally mean 50% rated speed.

6. Open-Loop and Closed-Loop Motor Control

Open-Loop Control

The controller sets a PWM duty cycle without measuring actual motor speed.

  • Simple implementation.
  • Does not automatically compensate for load changes.
  • Actual speed may vary with supply voltage and load.

Closed-Loop Control

The controller measures actual motor speed and compares it with the requested speed.

Speed Error = Reference Speed - Measured Speed

A control algorithm, such as PI or PID, calculates the output command from the error.

REFERENCE SPEED | v COMPARATOR <------ MEASURED SPEED | v SPEED ERROR | v PI / PID CONTROLLER | v PWM OUTPUT | v MOTOR DRIVER | v MOTOR

7. FreeRTOS Communication Design

Different tasks need to exchange commands, measurements and fault information.

MechanismApplication
QueueTransfer speed commands or structured measurements.
Task notificationSignal a task that an event or new data is available.
Binary semaphoreSignal an event from an ISR to a task.
MutexProtect a shared resource used by multiple tasks.
Event groupRepresent system conditions such as ready, running and fault.
Use queues for data transfer and notifications or semaphores for event signaling. Do not use a mutex as a substitute for a fault-shutdown mechanism.

8. Define Motor Command Structure

A structured command can contain the requested speed and operating mode.

#include "stdint.h"

typedef enum
{
    MOTOR_STOP = 0,
    MOTOR_RUN  = 1
} MotorMode_t;

typedef struct
{
    MotorMode_t mode;
    uint16_t targetSpeed;
} MotorCommand_t;

The command is copied into a FreeRTOS queue. Both producer and consumer use the same structure definition.

9. Create FreeRTOS Queues

The command queue transfers motor commands to the motor-control task.

QueueHandle_t motorCommandQueue;

motorCommandQueue = xQueueCreate(

QueueHandle_t motorFeedbackQueue;

10. Motor Control Task

The motor-control task receives commands and updates the PWM output.

Conceptual PWM Interface

void PWM_Init(void);

void PWM_SetDutyCycle(uint16_t duty);

void PWM_Disable(void);

Motor Control Task

static void MotorControlTask(void *pvParameters)
{
    MotorCommand_t command;
    uint16_t dutyCycle;

    (void) pvParameters;

    PWM_Init();
    PWM_Disable();

    for (;;)
    {
        if (xQueueReceive(
                motorCommandQueue,
                &command,
                portMAX_DELAY
            ) == pdPASS)
        {
            if (command.mode == MOTOR_STOP)
            {
                PWM_Disable();
            }
            else
            {
                /*
                 * Illustrative mapping only.
                 * Real control requires calibrated limits.
                 */
                if (command.targetSpeed > 1000)
                {
                    command.targetSpeed = 1000;
                }

                dutyCycle =
                    (command.targetSpeed * 100U) / 1000U;

                PWM_SetDutyCycle(dutyCycle);
            }
        }
    }
}
This example uses a simplified speed-command-to-duty-cycle mapping. It is not a closed-loop speed controller. Real motor control requires feedback, calibrated limits, appropriate acceleration/deceleration behavior and independent protection.

11. Command Task

The command task represents a source of motor commands, such as a UART interface or user control panel.

static void CommandTask(void *pvParameters)
{
    MotorCommand_t command;

    (void) pvParameters;

    command.mode = MOTOR_RUN;
    command.targetSpeed = 500;

    for (;;)
    {
        if (xQueueSend(
                motorCommandQueue,
                &command,
                pdMS_TO_TICKS(100)
            ) != pdPASS)
        {
            /* Record command queue failure */
        }

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

This demonstration sends a fixed illustrative command once per second. A production command task should validate external input and reject invalid or unsafe requests.

12. Feedback Monitoring Task

The feedback task obtains speed and current measurements from hardware-specific sensor interfaces.

uint16_t ReadMotorSpeed(void);
uint16_t ReadMotorCurrent(void);

static void FeedbackTask(void *pvParameters)
{
    MotorFeedback_t feedback;

    (void) pvParameters;

    for (;;)
    {
        feedback.measuredSpeed = ReadMotorSpeed();
        feedback.measuredCurrent = ReadMotorCurrent();

        if (xQueueSend(
                motorFeedbackQueue,
                &feedback,
                0
            ) != pdPASS)
        {
            /* Record dropped feedback sample */
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

The task samples feedback every 100 ms in this example. The period must be chosen according to the motor dynamics and control-loop requirements.

13. Protection Monitoring

Motor protection can include:

  • Overcurrent detection.
  • Overtemperature detection.
  • Undervoltage and overvoltage detection.
  • Overspeed detection.
  • Stall detection.
  • Sensor failure detection.
  • Driver fault input monitoring.

Illustrative Fault Conditions

#define MAX_ALLOWED_CURRENT 800
#define MAX_ALLOWED_SPEED   1000

BaseType_t MotorFaultDetected(
    const MotorFeedback_t *feedback
)
{
    if (feedback->measuredCurrent >
        MAX_ALLOWED_CURRENT)
    {
        return pdTRUE;
    }

    if (feedback->measuredSpeed >
        MAX_ALLOWED_SPEED)
    {
        return pdTRUE;
    }

    return pdFALSE;
}

The thresholds above are example values only. Real limits must come from motor, driver and system specifications.

14. Fault Handling and Safe Shutdown

A fault should cause the motor to enter a defined safe state. The safety mechanism should not depend solely on a low-priority application task receiving a queue message.

Recommended Architecture

CURRENT / TEMPERATURE / DRIVER FAULT | v HARDWARE PROTECTION OR ISR EVENT | +-------+-------+ | | v v DISABLE POWER NOTIFY RTOS STAGE TASK | | v v SAFE OUTPUT FAULT LOGGING | v UART STATUS
  • Use a hardware driver-enable or shutdown input where appropriate.
  • Use independent overcurrent protection when required by the power-stage design.
  • Latch faults where the system requires manual reset or explicit recovery.
  • Record the fault cause and relevant measurements.
  • Define safe restart conditions.
An RTOS task is not a substitute for independent hardware protection where a fault requires a fast or safety-critical response. The safe state must be designed around the actual motor and power electronics.

15. Periodic Control Using vTaskDelayUntil()

Periodic feedback and control tasks can use vTaskDelayUntil() to maintain a nominal periodic schedule.

static void PeriodicControlTask(void *pvParameters)
{
    TickType_t previousWakeTime;
    const TickType_t period =
        pdMS_TO_TICKS(10);

    (void) pvParameters;

    previousWakeTime = xTaskGetTickCount();

    for (;;)
    {
        /* Read feedback */
        /* Calculate control output */
        /* Update PWM */

        vTaskDelayUntil(
            &previousWakeTime,
            period
        );
    }
}

This example uses a nominal 10 ms period. The actual achievable timing depends on the RTOS tick rate, task execution time, interrupt load and processor capacity.

A periodic delay function does not guarantee a control deadline. For demanding motor-control loops, a hardware timer, PWM peripheral, ADC trigger and appropriately designed interrupt or control architecture may be required.

16. PI Controller Concept

A proportional-integral controller can reduce the difference between reference and measured speed.

Error = Reference Speed - Measured Speed

Integral = Integral + Error * Sample Time

Output = Kp * Error + Ki * Integral
TermFunction
Proportional (Kp)Responds to the present error.
Integral (Ki)Accumulates error over time.
OutputControl command, usually limited to a valid range.

A practical controller must also consider output saturation, integral windup, sampling period, sensor filtering and stability.

static void MonitorTask(void *pvParameters)
{
    MotorFeedback_t feedback;

    (void) pvParameters;

    for (;;)
    {
        if (xQueueReceive(
                motorFeedbackQueue,
                &feedback,
                portMAX_DELAY
            ) == pdPASS)
        {
            if (feedback.measuredCurrent > 800 ||
                feedback.measuredSpeed > 1000)
            {
                /*
                 * Application-level fault request.
                 * Independent hardware protection
                 * may also be required.
                 */
                PWM_Disable();
            }
        }
    }
}

This skeleton is for studying task and queue organization, not for controlling a physical motor as written. In particular, the monitor task's direct call to PWM_Disable() bypasses the motor-control task's ownership. A production design should use a single, well-defined control owner or an independent hardware shutdown path, with fault handling that cannot be delayed by ordinary application traffic.

18. Important Design Improvement – Single Owner for Motor Output

In a robust application, multiple tasks should not independently modify the same PWM or motor-driver registers.

A better design is to send both normal commands and fault requests to a single motor-control owner. A separate hardware shutdown path can disable the power stage immediately when required.

SourceMessageMotor-control owner action
Command taskSet speed to 500Validate and update reference.
Command taskStop motorDisable normal drive output.
Monitor taskOvercurrent faultLatch fault and request shutdown.
Driver fault ISRHardware fault eventHardware protection disables output; task records fault.
Define one owner for each hardware resource. This reduces race conditions and makes the system easier to test and maintain.

19. Priority and Timing Considerations

  • Assign priorities based on response-time requirements.
  • Keep interrupt handlers short.
  • Measure worst-case task execution time.
  • Consider blocking time and shared-resource contention.
  • Prevent communication tasks from delaying critical control work.
  • Monitor task stack usage.
  • Check queue capacity under maximum command and feedback rates.
  • Define what happens when a control task misses its intended period.

FreeRTOS priority scheduling does not automatically guarantee that all motor-control deadlines will be met. The complete workload and timing behavior must be analyzed.

21. Practical Exercises

Exercise 1 – Fixed-Speed Command

  • Create a motor-control task.
  • Send a fixed speed command from another task.
  • Calculate an illustrative PWM duty cycle.
  • Inspect the calculated output.

Expected result: The motor-control task receives the command and calculates a bounded duty-cycle value.

Exercise 2 – Speed Feedback

  • Generate simulated speed measurements.
  • Send them through a feedback queue.
  • Display the difference between reference and measured speed.

Expected result: The application reports the speed error for each measurement.

Exercise 3 – Overcurrent Detection

  • Generate simulated current values.
  • Define an example current threshold.
  • Detect threshold violations.
  • Generate a fault event.

Expected result: The application detects an overcurrent condition and records a shutdown request.

Exercise 4 – Start and Stop Commands

  • Implement START and STOP commands.
  • Validate command input.
  • Transfer commands through a queue.
  • Ensure the motor-control owner handles all normal output changes.

Expected result: The simulated motor state changes according to valid commands.

Exercise 5 – Periodic Control Timing

  • Create a periodic task.
  • Use vTaskDelayUntil().
  • Record execution and wake-up timing.
  • Introduce additional workload and observe timing variation.

Expected result: You can observe nominal periodic scheduling and identify timing deviations.

23. Lesson Summary

  • Motor-control applications often perform several concurrent activities.
  • FreeRTOS separates these activities into tasks.
  • Queues transfer commands and feedback data.
  • PWM is commonly used to control power delivered through a motor driver.
  • Closed-loop control uses feedback to regulate motor behavior.
  • Protection must account for current, temperature, voltage and driver faults.
  • A single task should normally own software-controlled motor outputs.
  • Independent hardware protection is important for fast or safety-critical shutdown.
  • Task priorities and periods must be selected using timing requirements.
  • Simulation can validate software logic but not physical motor performance.
