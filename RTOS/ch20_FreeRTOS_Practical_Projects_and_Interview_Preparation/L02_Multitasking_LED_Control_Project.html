2. Project Introduction

In this project, multiple LEDs are controlled independently using separate FreeRTOS tasks.

Each task controls one LED and changes its state periodically. The FreeRTOS scheduler coordinates the execution of all tasks.

4. System Architecture

The application contains three independent tasks. Each task toggles its assigned GPIO and then blocks for its configured interval.

FREERTOS SCHEDULER | +------------+------------+ | | | LED1_TASK LED2_TASK LED3_TASK | | | GPIO 1 GPIO 2 GPIO 3 | | | LED 1 LED 2 LED 3 500 ms 1000 ms 2000 ms

Task Responsibilities

  • LED1_Task: Toggles LED 1 every 500 ms.
  • LED2_Task: Toggles LED 2 every 1000 ms.
  • LED3_Task: Toggles LED 3 every 2000 ms.

5. Working Principle

  1. Initialize the microcontroller GPIO pins.
  2. Configure the selected GPIO pins as outputs.
  3. Create the three LED tasks.
  4. Assign appropriate task priorities.
  5. Start the FreeRTOS scheduler.
  6. Each task toggles its assigned LED.
  7. Each task enters the Blocked state using vTaskDelay().
  8. After the delay expires, the task becomes Ready.
  9. The scheduler selects a Ready task for execution.
When a task calls vTaskDelay(), it blocks rather than continuously consuming CPU time. Other Ready tasks can execute while it waits.

        {

    }

            LED2_Task,

        {

9. Understanding vTaskDelay()

The API is used to block a task for a specified number of RTOS ticks.

vTaskDelay(pdMS_TO_TICKS(500));

If the tick rate is 1000 Hz, one tick nominally represents 1 ms. Therefore, a 500 ms delay corresponds to 500 ticks.

Important Characteristics

  • The calling task enters the Blocked state.
  • The scheduler can run another Ready task.
  • When the delay expires, the task becomes Ready.
  • Becoming Ready does not guarantee immediate execution.
  • Execution may be delayed by higher-priority tasks and interrupts.
vTaskDelay() is a relative delay. For more consistent periodic release timing, consider vTaskDelayUntil() or its newer equivalent where available. Neither API alone guarantees a task deadline.

10. Task Priority Configuration

FreeRTOS uses fixed-priority scheduling in its standard scheduler.

TaskExample PriorityReason
LED1_Task2Demonstration task.
LED2_Task2Demonstration task.
LED3_Task2Demonstration task.

In standard FreeRTOS configurations, a higher numerical priority represents a higher task priority.

What Happens with Different Priorities?

  • A higher-priority Ready task can preempt a lower-priority Running task when preemption is enabled.
  • Equal-priority Ready tasks can share processor time when time slicing is enabled.
  • A Blocked task does not consume processor time while waiting.
  • The Idle task executes when no application task is Ready.

11. Improved Periodic Task Design Using vTaskDelayUntil()

For periodic tasks, vTaskDelayUntil() can help maintain a regular release schedule.

Example: LED 1 Periodic Task

static void LED1_Task(void *pvParameters)
{
    TickType_t lastWakeTime;
    const TickType_t period = pdMS_TO_TICKS(500);

    (void) pvParameters;

    lastWakeTime = xTaskGetTickCount();

    for (;;)
    {
        GPIO_TogglePin(LED1_PIN);

        vTaskDelayUntil(&lastWakeTime, period);
    }
}

The task uses an absolute wake-time reference that advances by the specified period on each iteration.

If the task execution exceeds its period, the scheduled wake time may already have passed. The task may not block as expected. Define and test an overrun policy for production applications.

14. Optimization and Best Practices

  • Use blocking delays instead of busy waiting.
  • Use vTaskDelayUntil() for periodic scheduling where appropriate.
  • Assign priorities based on actual application requirements.
  • Check every task-creation result.
  • Allocate sufficient stack space.
  • Keep task functions simple and bounded.
  • Use a common driver interface for GPIO operations.
  • Avoid multiple tasks controlling the same GPIO without an ownership policy.
  • Use static task allocation if predictable memory use is required and supported.
  • Measure timing on the actual target hardware.

19. Keil µVision and LPC2129 Simulator Notes

The LPC2129 uses an ARM7TDMI-S processor. Its GPIO registers can be studied independently of FreeRTOS.

Example LPC2129 GPIO Register Operations

#include <LPC21xx.h>

#define LED1 (1U << 5)
#define LED2 (1U << 10)
#define LED3 (1U << 28)

void LED_GPIO_Init(void)
{
    IODIR0 |= LED1 | LED2 | LED3;

    IOCLR0 = LED1 | LED2 | LED3;
}

void LED1_Toggle(void)
{
    IO0PIN ^= LED1;
}

void LED2_Toggle(void)
{
    IO0PIN ^= LED2;
}

void LED3_Toggle(void)
{
    IO0PIN ^= LED3;
}
This is an illustrative register-level GPIO example, not a complete FreeRTOS application. For robust embedded code, use a controlled output-state variable and write the appropriate set/clear registers rather than relying on read-modify-write behavior of an output pin register.

Simulator Study

  • Inspect IODIR0 to verify output configuration.
  • Inspect IO0PIN and the relevant GPIO registers.
  • Step through the toggle functions.
  • Observe how output-state changes are represented in the simulator.
  • Use a compatible FreeRTOS ARM7 port only after verifying compiler and simulator support.

The simulator can help study register-level behavior, but it does not prove that physical LEDs illuminate or that target hardware meets the required timing.
