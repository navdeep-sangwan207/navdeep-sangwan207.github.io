1. Introduction

This lesson provides technical interview questions and answers covering Real-Time Operating Systems, FreeRTOS architecture, task management, scheduling, queues, synchronization, interrupts, memory management, debugging and embedded applications.

Interview Preparation Objectives

  • Explain RTOS concepts clearly.
  • Understand important FreeRTOS APIs and their usage.
  • Answer practical embedded-system design questions.
  • Recognize common RTOS programming mistakes.
  • Explain task synchronization and interrupt handling.
  • Discuss real-time timing and memory constraints.
In technical interviews, explain not only what an API does, but also when to use it, what can go wrong and what design alternatives are available.

2. RTOS Fundamentals

Q1. What is an RTOS?

Answer: A Real-Time Operating System is an operating system designed to manage tasks and system resources while providing predictable timing behavior. It supports scheduling, synchronization, communication and interrupt-related services.

Q2. What is the main purpose of an RTOS?

Answer: Its purpose is to coordinate concurrent activities and help the system respond to events within specified timing constraints. Predictability and deadline satisfaction are more important than simply maximizing average execution speed.

Q3. What is the difference between a hard and soft real-time system?

Answer:

  • Hard real-time: Missing a required deadline constitutes a system failure.
  • Firm real-time: A result delivered after its deadline has no value, although occasional misses may be tolerated at the overall system level.
  • Soft real-time: Late results may still be useful, but quality or performance degrades.
Q4. Is every RTOS faster than a general-purpose operating system?

Answer: No. An RTOS is designed for predictable response and bounded timing behavior. A general-purpose OS may provide higher throughput or more sophisticated services, depending on the workload.

Q5. What is determinism?

Answer: Determinism means that system behavior and timing can be predicted within defined bounds under stated operating assumptions. It does not mean that the system always executes as fast as possible.

Q6. Can a bare-metal application be a real-time system?

Answer: Yes. A bare-metal application can meet real-time requirements without an RTOS if its interrupt handling, execution time and scheduling logic are appropriately designed and analyzed.

Q7. What is interrupt latency?

Answer: Interrupt latency is the time between an interrupt request becoming active and the processor beginning the corresponding interrupt service routine. It depends on interrupt masking, current processor activity, architecture and interrupt-controller behavior.

Q8. What is task response time?

Answer: Task response time is the time from a task's release or triggering event until the task completes. It includes execution time and interference such as higher-priority tasks and blocking.

Q9. What is task jitter?

Answer: Jitter is variation in task timing, such as variation in release time, start time or completion time. Excessive jitter can affect control loops and communication timing.

Q10. What is WCET?

Answer: Worst-Case Execution Time is a safe upper bound on the execution time of a task or code segment under defined hardware and software assumptions. The largest measured execution time is not automatically the WCET.

3. Operating System and Kernel Concepts

Q11. What is a kernel?

Answer: The kernel is the core part of an operating system that manages processor scheduling, memory and system resources, and provides fundamental services to applications.

Q12. What is the difference between a process and a thread?

Answer: A process is an execution environment with its own address space and resources. Threads are execution paths within a process and generally share the process address space while maintaining separate stacks and execution contexts.

Q13. What is context switching?

Answer: Context switching is the process of saving the execution state of one task and restoring the state of another so that the processor can execute the selected task.

Q14. What information is saved during a context switch?

Answer: Depending on the processor and port, the saved context may include general-purpose registers, stack pointer, program counter, status register and other architecture-specific state.

Q15. What is multitasking?

Answer: Multitasking allows multiple tasks to make progress through scheduling. On a single-core processor, tasks normally take turns executing; this provides concurrency, not true parallel execution.

Q16. What is the difference between concurrency and parallelism?

Answer: Concurrency means multiple activities make progress over overlapping periods. Parallelism means multiple activities execute at the same time on different processing units.

4. FreeRTOS Fundamentals

Q17. What is FreeRTOS?

Answer: FreeRTOS is a real-time operating-system kernel for embedded systems. It provides task scheduling, queues, semaphores, mutexes, event groups, software timers and other kernel services.

Q18. Is FreeRTOS an operating system or a scheduler?

Answer: FreeRTOS is an RTOS kernel, not merely a scheduler. It includes scheduling and other kernel services such as inter-task communication, synchronization and timing services.

Q19. What are the major components of FreeRTOS?

Answer: Major components include task management, scheduler, queues, semaphores, mutexes, event groups, software timers, stream buffers and memory allocation support. Available features depend on the selected release and configuration.

Q20. What is FreeRTOSConfig.h?

Answer: It is the application-specific configuration header used to configure kernel behavior, tick rate, task priorities, memory allocation, software timers and other optional features.

Q21. What is a FreeRTOS port?

Answer: A port adapts the kernel to a particular processor architecture, compiler and hardware environment. It includes architecture-specific context switching, interrupt integration and other low-level functions.

Q22. Does FreeRTOS automatically support every microcontroller?

Answer: No. A compatible port and toolchain integration are required. Peripheral drivers, startup code and hardware configuration must also be provided for the selected microcontroller.

Q23. What is the FreeRTOS tick?

Answer: The RTOS tick is a periodic timing event used by the kernel for time measurement and scheduling-related operations. Its frequency is configured through configTICK_RATE_HZ.

Q24. If the tick rate is 1000 Hz, what is the tick period?

Answer: The nominal tick period is 1 millisecond.

Tick Period = 1 / 1000 seconds

Q25. Does every tick cause a context switch?

Answer: No. A tick can update kernel timing and unblock tasks. A context switch occurs when scheduling rules require a different task to run.

5. FreeRTOS Task Management

Q26. What is a task in FreeRTOS?

Answer: A task is an independently schedulable unit of execution. It has its own stack and task context, and is managed by the FreeRTOS scheduler.

Q27. What are the main task states?

Answer:

  • Running – currently executing.
  • Ready – eligible to execute.
  • Blocked – waiting for an event or time period.
  • Suspended – explicitly suspended and not eligible to execute.
Q28. What is a Task Control Block (TCB)?

Answer: The TCB is an internal kernel data structure containing task-management information such as task state, priority, stack information and scheduling data. Its internal layout is implementation-dependent.

Q29. What is TaskHandle_t?

Answer: It is an opaque handle used to refer to a FreeRTOS task through APIs. It is not the TCB itself.

Q30. What is the syntax of a FreeRTOS task function?

Answer:

void TaskFunction(void *pvParameters)
{
    for (;;)
    {
        /* Task operations */
    }
}
Q31. What is xTaskCreate()?

Answer: It dynamically creates a task using the configured FreeRTOS memory allocator.

xTaskCreate(
    TaskFunction,
    "Task1",
    256,
    NULL,
    2,
    NULL
);

The stack-depth argument is measured in stack elements, not necessarily bytes.

Q32. What is xTaskCreateStatic()?

Answer: It creates a task using stack memory and task-control-block storage supplied by the application. It requires static allocation support in the FreeRTOS configuration.

Q33. What is vTaskDelete()?

Answer: It deletes a task. Passing NULL deletes the calling task. Deleting a task does not automatically release every application resource or safely recover resources that the task owned.

Q34. What is vTaskDelay()?

Answer: It blocks the calling task for a specified number of RTOS ticks. It is useful for relative delays but does not maintain a fixed periodic start time.

Q35. What is vTaskDelayUntil()?

Answer: It schedules a task relative to its previous intended wake time. It is useful for periodic tasks because execution-time variation does not simply accumulate into the next period. It does not guarantee deadline completion.

Q37. What is vTaskSuspend()?

Answer: It suspends a task. A suspended task does not become Ready merely because a delay expires. It must be resumed explicitly.

Q38. What is the difference between vTaskResume() and xTaskResumeFromISR()?

Answer: vTaskResume() is a task-context API. xTaskResumeFromISR() is an ISR-context API where supported by the selected port. Neither should be used without checking the task's synchronization requirements.

Q39. What is task priority?

Answer: Task priority determines scheduling preference. In standard FreeRTOS configurations, a larger numerical priority represents a higher priority.

Q40. What is configMAX_PRIORITIES?

Answer: It specifies the number of available task-priority levels. Valid priority values range from zero to configMAX_PRIORITIES - 1.

6. FreeRTOS Scheduling

Q41. What is preemptive scheduling?

Answer: In preemptive scheduling, a higher-priority Ready task can take the processor from a lower-priority Running task at a scheduling point.

Q42. What is cooperative scheduling?

Answer: In cooperative scheduling, a running task normally continues until it blocks, yields or otherwise allows the scheduler to select another task.

Q43. What is time slicing?

Answer: Time slicing allows equal-priority Ready tasks to share processor time, commonly through tick-based rotation when the relevant configuration is enabled.

Q44. What is the difference between preemption and time slicing?

Answer: Preemption allows a higher-priority task to interrupt a lower-priority task's execution. Time slicing rotates execution among eligible tasks at the same priority.

Q45. What is the Idle task?

Answer: FreeRTOS creates an Idle task when the scheduler starts. It runs when no application task is Ready and performs kernel housekeeping, including reclaiming memory for some deleted dynamically allocated tasks.

Q46. What is an Idle Hook?

Answer: An Idle Hook is an application-provided function called by the Idle task when configured. It must not block or delay the Idle task.

Q47. What is scheduler suspension?

Answer: vTaskSuspendAll() temporarily prevents normal task-context scheduling. It does not disable interrupts. The matching xTaskResumeAll() call must be made to resume scheduling.

Q48. Does FreeRTOS use EDF scheduling by default?

Answer: No. Standard FreeRTOS scheduling is fixed-priority scheduling. It does not become EDF merely by changing task priorities.

Q49. What is Rate Monotonic Scheduling?

Answer: Rate Monotonic Scheduling is a fixed-priority scheduling method in which tasks with shorter periods receive higher priorities, under its standard assumptions.

Q50. What is Earliest Deadline First scheduling?

Answer: EDF is a dynamic-priority scheduling algorithm that selects the Ready task with the earliest absolute deadline. Its schedulability properties depend on assumptions such as processor model, task independence and deadline relationships.

7. Queues and Inter-Task Communication

Q51. What is a FreeRTOS queue?

Answer: A queue is a kernel object used to transfer fixed-size data items between tasks and, through appropriate APIs, between interrupt handlers and tasks.

Q52. What is xQueueCreate()?

Answer: It creates a queue with a specified capacity and item size.

QueueHandle_t queue;

queue = xQueueCreate(
    5,
    sizeof(uint32_t)
);
Q53. What is xQueueSend()?

Answer: It sends an item to a queue from task context. The item is copied into the queue. It can block for a specified number of ticks if the queue is full.

Q54. What is xQueueReceive()?

Answer: It receives and removes an item from a queue. It can block while waiting for data if the queue is empty.

Q55. What happens when a queue is full?

Answer: A send operation can fail immediately or wait for the specified block time. The application must define an overflow policy such as retrying, dropping data, recording an error or applying backpressure.

Q56. What happens when a queue is empty?

Answer: A receive operation can return immediately with failure or block for the specified waiting period until an item arrives.

Q57. Does a FreeRTOS queue copy data?

Answer: Yes. It copies the configured number of bytes from the source item into queue storage. For a pointer item, only the pointer value is copied, not the pointed-to object.

Q58. What is xQueuePeek()?

Answer: It copies the item at the front of the queue without removing it. It does not reserve the item or prevent another task from receiving it.

Q59. What is xQueueReset()?

Answer: It resets a queue by removing queued items. It does not delete the queue or change its capacity. If the queue contains pointers, resetting it does not free the pointed-to objects.

Q60. What is a queue set?

Answer: A queue set allows a task to wait for data or availability events from multiple supported queue or semaphore members. Its capacity and configuration must be designed correctly for all members.

Q61. What is the difference between a queue and a mailbox?

Answer: FreeRTOS does not require a separate traditional mailbox object. A queue with a length of one can be used for a mailbox-like purpose, such as transferring the latest value.

Q62. What is a stream buffer?

Answer: A stream buffer transfers a continuous stream of bytes. It does not inherently preserve application message boundaries.

Q63. What is a message buffer?

Answer: A message buffer transfers variable-length messages while preserving their message boundaries. Its overhead and capacity behavior differ from a normal queue.

8. Semaphores and Mutexes

Q64. What is a semaphore?

Answer: A semaphore is a synchronization mechanism used for signaling or managing a count of available resources.

Q65. What is a binary semaphore?

Answer: A binary semaphore has two logical states: available or unavailable. It is commonly used for task synchronization and signaling an event from an ISR.

Q66. What is a counting semaphore?

Answer: A counting semaphore maintains a count within a configured range. It is useful for tracking multiple available resources or counting events.

Q67. What is a mutex?

Answer: A mutex is an ownership-based synchronization object used to protect a shared resource. The task that takes the mutex must release it.

Q69. What is priority inversion?

Answer: Priority inversion occurs when a high-priority task is delayed by a lower-priority task holding a resource it needs, potentially while medium-priority tasks execute.

Q70. What is priority inheritance?

Answer: Priority inheritance temporarily raises the priority of a lower-priority task holding a mutex needed by a higher-priority task. This helps reduce certain forms of priority inversion.

Q71. Does priority inheritance eliminate all priority inversion?

Answer: No. It reduces certain priority-inversion effects, but does not eliminate all blocking, deadlocks or timing problems.

Q72. Can a mutex be used inside an ISR?

Answer: No. A mutex involves ownership and potentially blocking behavior. Interrupt handlers must use suitable non-blocking ISR-safe mechanisms.

Q73. What is deadlock?

Answer: Deadlock occurs when tasks wait indefinitely for resources held by one another. The classical conditions are mutual exclusion, hold and wait, no preemption and circular wait.

Q74. How can deadlock be prevented?

Answer: Consistent lock ordering, minimizing nested locks, limiting resource ownership time and designing explicit recovery policies can reduce deadlock risk. Timeouts alone do not prove deadlock prevention.

9. Event Groups and Software Timers

Q75. What is an event group?

Answer: An event group is a collection of event bits used to represent system conditions and synchronize tasks.

Q76. What is xEventGroupSetBits()?

Answer: It sets selected event bits from task context and returns the resulting event-bit value after the operation's event processing.

Q77. What is xEventGroupWaitBits()?

Answer: It allows a task to wait for one or more event bits. The caller can select whether it waits for any requested bit or all requested bits, and whether matching bits are cleared on exit.

Q78. Can xEventGroupSetBits() be called from an ISR?

Answer: No. Use the supported ISR-safe event-group API, such as xEventGroupSetBitsFromISR(), where available. The operation is deferred through the timer service mechanism and can fail if the timer command queue is full.

Q79. What is a FreeRTOS software timer?

Answer: A software timer is a kernel-managed timer that invokes a callback function after a configured number of ticks or repeatedly at a configured period.

Q80. What is the difference between one-shot and auto-reload timers?

Answer: A one-shot timer expires once and stops. An auto-reload timer restarts its countdown after each expiry.

Q81. In which context does a software timer callback execute?

Answer: It executes in the FreeRTOS timer service task context, not directly in a hardware ISR.

Q82. Should a timer callback contain lengthy processing?

Answer: No. Timer callbacks share the timer service task. A long callback delays other timer callbacks and timer command processing. Delegate lengthy work to application tasks.

Q83. Does pdPASS from xTimerStart() mean the timer has already started?

Answer: No. It means the timer command was successfully queued. The timer service task processes the command later.

10. Interrupt Management

Q84. What is an ISR?

Answer: An Interrupt Service Routine is a function executed in response to an interrupt event. It performs time-sensitive interrupt handling and may signal an application task to perform deferred processing.

Q85. Why should an ISR be short?

Answer: A long ISR increases interrupt latency for other sources, delays task execution and can affect real-time response. Non-essential processing should usually be deferred to a task.

Q86. What is deferred interrupt processing?

Answer: Deferred processing means the ISR performs essential hardware handling and signals a task to perform the remaining work outside interrupt context.

Q87. What is the difference between task APIs and ISR APIs?

Answer: Task APIs can have blocking behavior where supported. ISR APIs are designed for interrupt context and must not block. Examples include xQueueSend() and xQueueSendFromISR().

Q88. What is portYIELD_FROM_ISR()?

Answer: It is a port-specific mechanism used to request a context switch at ISR exit when an ISR operation wakes a higher-priority task. Exact syntax and availability depend on the port.

Q89. Can an ISR take a mutex?

Answer: No. An ISR cannot block waiting for a mutex and cannot own a mutex like a task.

Q90. What is interrupt nesting?

Answer: Interrupt nesting occurs when an interrupt handler is interrupted by another interrupt, subject to processor and interrupt-controller priority and masking rules.

Q91. What is the difference between IRQ and FIQ on ARM7?

Answer: ARM7TDMI-S provides IRQ and FIQ exception types. FIQ has additional banked registers and is designed for lower-latency handling in suitable applications. It is not simply a normal IRQ with a larger numerical priority.

11. Memory Management and Debugging

Q92. What is the difference between static and dynamic allocation?

Answer: Static allocation uses memory reserved at compile time or supplied by the application. Dynamic allocation obtains memory at runtime through an allocator.

Q93. What is heap_1?

Answer: It is a FreeRTOS heap implementation that supports allocation but does not free allocated blocks.

Q94. What is heap_2?

Answer: It supports allocation and freeing but does not coalesce adjacent free blocks, so fragmentation can occur.

Q95. What is heap_3?

Answer: It wraps the C library's malloc() and free() functions.

Q96. What is heap_4?

Answer: It supports allocation, freeing and coalescing adjacent free blocks within its managed heap region.

Q97. What is heap_5?

Answer: It supports multiple non-contiguous memory regions and can coalesce adjacent free blocks within individual regions.

Q98. What is stack overflow?

Answer: Stack overflow occurs when a task uses more stack memory than has been allocated, potentially corrupting adjacent memory or causing unpredictable behavior.

Q99. What is uxTaskGetStackHighWaterMark()?

Answer: It reports the minimum unused stack space observed for a task since the task started. Its unit is stack elements, not necessarily bytes. It is useful for measurement but does not prove that every execution path is safe.

Q100. What is configCHECK_FOR_STACK_OVERFLOW?

Answer: It configures optional stack-overflow detection mechanisms. The exact checks and behavior depend on the FreeRTOS port and configuration.

Q101. What is heap fragmentation?

Answer: Heap fragmentation occurs when free memory is divided into separated blocks, making it difficult to allocate a large contiguous block even when the total free memory appears sufficient.

Q102. What is configASSERT()?

Answer: It is a configurable assertion mechanism used to detect invalid conditions during development. Its implementation and behavior are application-specific.

12. Real-Time Scheduling and Analysis

Q103. What is CPU utilization?

Answer: CPU utilization is the fraction of processor time consumed by task execution over a specified observation interval or modeled task workload.

Q104. What is the utilization of a periodic task?

Answer: For a task with execution time C and period T, utilization is:

U = C / T
Q105. What is the Liu-Layland utilization bound?

Answer: For n independent periodic tasks under the classical assumptions of fixed-priority Rate Monotonic Scheduling, the sufficient utilization bound is:

U <= n * (2^(1/n) - 1)

This is sufficient, not necessary. A task set above the bound may still be schedulable.

Q106. Is CPU utilization below 100% enough to prove schedulability?

Answer: No. Task priorities, deadlines, blocking, execution times, interrupts and scheduling assumptions must also be considered.

Q107. What is response-time analysis?

Answer: Response-time analysis estimates or bounds the time from task release to completion while accounting for execution time, blocking and interference from higher-priority work.

Q108. What is blocking time?

Answer: Blocking time is the delay a task experiences while waiting for a resource or event that prevents it from executing, such as a lower-priority task holding a required mutex.

Q109. What is deadline miss?

Answer: A deadline miss occurs when a task or operation completes after its required deadline. Its consequence depends on whether the system is hard, firm or soft real-time.

Q110. Does vTaskDelayUntil() guarantee a hard real-time deadline?

Answer: No. It helps maintain a nominal periodic schedule but does not guarantee that the task will complete before its deadline. Scheduling and execution-time analysis are still required.

13. Practical Programming Questions

Q111. How do you create two tasks in FreeRTOS?

Answer: Call xTaskCreate() for each task, check the return value, and start the scheduler after creating the required tasks.

Q112. How do you transfer data between two tasks?

Answer: Use a queue when data must be transferred. Use a task notification or semaphore when signaling is sufficient and the application does not require a separate data object.

Q113. How do you protect a shared UART resource?

Answer: Use a mutex when multiple tasks directly access the same synchronous UART resource, or use a dedicated UART-owner task with a queue. For DMA transmission, ensure buffer ownership continues until transfer completion.

Q114. How do you send data from an ISR to a task?

Answer: Use an appropriate ISR-safe queue, semaphore or task-notification API. Keep the ISR short and use the port-specific yield mechanism if required.

Q115. How do you implement periodic sensor sampling?

Answer: Use a periodic task with vTaskDelayUntil(), read the sensor through a driver and transfer the measurement to a processing task.

Q116. How do you handle a full queue?

Answer: Check the return value and apply a defined policy: block for a bounded time, drop the newest item, overwrite a latest-value queue where appropriate, record the event or apply backpressure.

Q117. How do you handle a task that never blocks?

Answer: Inspect whether it is continuously consuming CPU time. Add appropriate blocking or event-driven waits where possible, and verify that lower-priority tasks and the Idle task receive required execution time.

Q118. How do you debug a task that does not execute?

Answer: Check whether it was created successfully, whether the scheduler started, whether it is Blocked or Suspended, whether its priority is appropriate, and whether the event or queue it waits for can actually occur.

14. Scenario-Based Interview Questions

Q119. A high-priority task is not executing. What would you investigate?

Answer: Investigate task state, scheduler operation, interrupt masking, long critical sections, scheduler suspension, blocking conditions and whether the task was created correctly.

Q120. Two tasks are writing to UART and messages are mixed. How would you solve it?

Answer: Introduce a dedicated UART-owner task with a TX queue, or protect the complete synchronous transmission interval with a mutex. For DMA, include transfer completion and buffer ownership in the design.

Q121. Sensor data is being lost. What could be the reason?

Answer: The ISR may not service the peripheral quickly enough, the queue may be too small, the consumer may be too slow, or the producer rate may exceed the consumer's processing capacity. Measure rates and define an overflow policy.

Q122. A task is taking too much CPU time. What would you do?

Answer: Profile its execution, inspect loops and blocking behavior, reduce unnecessary polling, optimize expensive operations and verify whether work can be delegated or scheduled less frequently.

Q123. A task occasionally misses its deadline. What would you investigate?

Answer: Measure worst-case execution time, blocking, interrupt interference, higher-priority task workload, release jitter and resource contention. Reassess priorities and the complete scheduling design.

Q124. A mutex is never released. What can happen?

Answer: Other tasks waiting for that mutex may remain blocked indefinitely or until a timeout occurs. Investigate all control-flow paths and ensure the owner releases the mutex correctly. Consider a safer resource-ownership design.

Q125. A timer callback is delaying other timers. What is the solution?

Answer: Keep the callback short and non-blocking. Transfer lengthy work to an application task using a queue or notification.

Q126. Why might a FreeRTOS application work in simulation but fail on hardware?

Answer: Simulation may not reproduce electrical behavior, peripheral timing, interrupt latency, analog inputs, clock configuration, hardware faults or actual driver behavior. Hardware validation is essential.

15. LPC2129 and ARM7-Specific Questions

Q127. Which processor core is used in the LPC2129?

Answer: The LPC2129 uses an ARM7TDMI-S processor core.

Q128. Which UART peripherals are available on the LPC2129?

Answer: UART0 and UART1 are available.

Q130. What is the VIC?

Answer: The Vectored Interrupt Controller manages interrupt sources and supports vectored interrupt handling on the LPC2129.

Q131. Does the LPC2129 use an NVIC?

Answer: No. The LPC2129 uses the ARM7-era VIC architecture. Cortex-M NVIC examples should not be directly applied to it.

Q132. What are the ARM7 processor modes?

Answer: ARM7TDMI-S supports User, System, Supervisor, IRQ, FIQ, Abort and Undefined modes.

Q133. What is the difference between IRQ and FIQ?

Answer: IRQ is the normal interrupt exception, while FIQ is designed for faster interrupt handling and has additional banked registers. Their behavior is defined by the ARM architecture.

Q134. Can Cortex-M FreeRTOS interrupt-priority rules be applied directly to LPC2129?

Answer: No. Cortex-M interrupt configuration mechanisms and macros are port-specific. ARM7 interrupt integration must follow the selected ARM7 FreeRTOS port.

17. Common Interview Mistakes

  • Confusing task priority with interrupt priority.
  • Assuming every tick causes a context switch.
  • Calling task-context blocking APIs from an ISR.
  • Using a mutex inside an ISR.
  • Assuming a queue of pointers copies the pointed-to data.
  • Assuming event groups preserve every repeated event.
  • Assuming timer callbacks execute in hardware interrupt context.
  • Assuming priority inheritance prevents every priority inversion.
  • Assuming a periodic delay API guarantees a deadline.
  • Assuming measured maximum execution time is a proven WCET.
  • Assuming every FreeRTOS port supports the same interrupt configuration.
  • Assuming simulation proves real hardware behavior.
