2. Project Introduction

In an embedded system, multiple FreeRTOS tasks may need to access the same hardware peripheral or software resource.

For example, two tasks may need to transmit messages through a single UART interface. If both tasks access the UART simultaneously without synchronization, their messages may become interleaved.

Project Objective

Use a FreeRTOS mutex to ensure that only one task at a time accesses the shared UART transmission interface.

ComponentResponsibility
Task 1Transmits sensor information.
Task 2Transmits system status information.
MutexProtects the shared UART resource.
UART DriverTransmits characters to the serial interface.

3. Shared Resource Architecture

TASK 1 Sensor Message | v MUTEX TAKE | | UART TRANSMISSION | MUTEX GIVE | | TASK 2 Status Message | v MUTEX TAKE | | UART TRANSMISSION | MUTEX GIVE

Both tasks use the same UART driver. The mutex provides exclusive access during the protected operation.

4. Understanding Shared Resources

A shared resource is a hardware or software component accessed by more than one execution context.

Examples of Shared Resources

ResourcePossible Users
UART peripheralLogging task and communication task
SPI peripheralDisplay task and flash-memory task
I2C peripheralSensor task and EEPROM task
Shared data structureMeasurement task and monitoring task
File systemLogging task and configuration task

Not every shared resource requires a mutex. The correct synchronization mechanism depends on the resource, access pattern, driver design and interrupt involvement.

5. What Is a Mutex?

A mutex (mutual exclusion object) is a synchronization mechanism used to protect a shared resource.

Important Characteristics

  • Only one task can own a mutex at a time.
  • A task takes the mutex before entering the protected section.
  • The owning task releases the mutex after completing the protected operation.
  • Other tasks attempting to take the mutex may block.
  • FreeRTOS mutexes support priority inheritance.
  • A mutex cannot be used as an ISR synchronization object.
A mutex is an ownership-based synchronization object. It is different from a binary semaphore, which does not enforce ownership.

6. FreeRTOS Mutex APIs

Mutex Creation

SemaphoreHandle_t xSemaphoreCreateMutex(void);

Creates a mutex and returns its handle. Check whether the returned handle is NULL.

Take Mutex

xSemaphoreTake(
    xMutex,
    xTicksToWait
);

The calling task attempts to acquire the mutex.

Give Mutex

xSemaphoreGive(xMutex);

The owning task releases the mutex.

API Summary

APIPurpose
xSemaphoreCreateMutex()Create a mutex.
xSemaphoreTake()Acquire the mutex.
xSemaphoreGive()Release the mutex.
xSemaphoreCreateMutexStatic()Create a mutex using application-provided storage, where supported.
Do not use xSemaphoreGiveFromISR() to release a mutex. Mutexes are not intended for ISR use because they depend on task ownership and priority inheritance.

8. Complete FreeRTOS Application Code

Objective: Protect a shared UART transmission function using a mutex.

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"
#include "stdint.h"
#include "stdio.h"

/* Shared mutex handle */
static SemaphoreHandle_t uartMutex = NULL;

/* Task declarations */
static void SensorTask(void *pvParameters);
static void StatusTask(void *pvParameters);

/*
 * Hardware-specific UART initialization
 * and transmission functions.
 */
void UART_Init(void);
void UART_SendString(const char *message);

/* Shared UART resource function */
static void UART_PrintProtected(const char *message)
{
    if (xSemaphoreTake(
            uartMutex,
            pdMS_TO_TICKS(100)
        ) == pdPASS)
    {
        /*
         * Protected UART operation.
         * The driver must provide the required
         * transmission-completion behavior.
         */
        UART_SendString(message);

        /* Release mutex */
        xSemaphoreGive(uartMutex);
    }
    else
    {
        /* Mutex acquisition timeout */
    }
}

/* Sensor task */
static void SensorTask(void *pvParameters)
{
    (void) pvParameters;

    for (;;)
    {
        UART_PrintProtected(
            "Sensor Task: Temperature = 28 C\r\n"
        );

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

/* Status task */
static void StatusTask(void *pvParameters)
{
    (void) pvParameters;

    for (;;)
    {
        UART_PrintProtected(
            "Status Task: System Running\r\n"
        );

        vTaskDelay(pdMS_TO_TICKS(1500));
    }
}

/* Main application */
int main(void)
{
    /* Initialize UART hardware */
    UART_Init();

    /* Create mutex */
    uartMutex = xSemaphoreCreateMutex();

    if (uartMutex == NULL)
    {
        for (;;)
        {
            /* Mutex creation failed */
        }
    }

    /* Create sensor task */
    if (xTaskCreate(
            SensorTask,
            "SensorTask",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
            /* Sensor task creation failed */
        }
    }

    /* Create status task */
    if (xTaskCreate(
            StatusTask,
            "StatusTask",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        for (;;)
        {
            /* Status task creation failed */
        }
    }

    /* Start scheduler */
    vTaskStartScheduler();

    /* Reached if scheduler startup fails */
    for (;;)
    {
    }
}
The UART driver function must have a clearly defined completion and buffering contract. If it only starts an asynchronous DMA transfer and returns, releasing the mutex immediately may allow another task to modify or reuse the transmission buffer before DMA finishes. Protect the full resource-use interval or use a dedicated UART-owner task and queue.

9. Program Explanation

Step 1 – Declare Mutex Handle

static SemaphoreHandle_t uartMutex = NULL;

This handle identifies the mutex protecting the shared UART resource.

Step 2 – Create Mutex

uartMutex = xSemaphoreCreateMutex();

The mutex is created before the application tasks begin using it.

Step 3 – Acquire Mutex

xSemaphoreTake(
    uartMutex,
    pdMS_TO_TICKS(100)
);

A task attempts to acquire the mutex and waits up to the configured timeout if another task owns it.

Step 4 – Access Shared Resource

UART_SendString(message);

The protected operation executes while the task owns the mutex.

Step 5 – Release Mutex

xSemaphoreGive(uartMutex);

The task releases the mutex so another task can acquire it.

10. Understanding Race Conditions

A race condition occurs when the result of an operation depends on the timing or interleaving of concurrent accesses.

Without Mutex

Suppose two tasks transmit messages simultaneously:

Task 1: SENSOR DATA
Task 2: SYSTEM STATUS

The UART output may become interleaved:

SENSSYTSEOMR  DATA
STATUS

This is an illustrative example of interleaved output, not a guaranteed UART result.

With Mutex

Only one task performs the protected transmission at a time. The messages are serialized at the application level.

A mutex protects the critical section only when every relevant access path follows the same locking protocol.

11. Critical Section and Mutex

A critical section is a region of code that must not be executed concurrently by competing tasks when accessing a protected resource.

if (xSemaphoreTake(
        uartMutex,
        portMAX_DELAY
    ) == pdPASS)
{
    /* Critical section */
    UART_SendString(message);

    /* End of critical section */
    xSemaphoreGive(uartMutex);
}

The mutex provides task-level mutual exclusion for this region.

A mutex does not automatically protect the resource from direct ISR access, DMA activity or code that bypasses the mutex. Those access paths need an appropriate driver-level design.

12. Mutex Ownership

A mutex has an owner: the task that successfully takes it.

OperationOwnership Rule
Take mutexTask becomes owner when acquisition succeeds.
Use protected resourceOwner performs the protected operation.
Give mutexOwner releases the mutex.
Another task attempts takeIt may block until the mutex becomes available.
A task must not release a mutex it does not own. Always check the result of the take operation before entering the protected section.

13. Priority Inversion

Priority inversion occurs when a high-priority task is delayed because a lower-priority task holds a resource it needs.

Example

TaskPriorityActivity
Task HHighNeeds the UART mutex.
Task MMediumPerforms unrelated processing.
Task LLowOwns the UART mutex.

Task L acquires the mutex. Task H becomes Ready and attempts to take it, but blocks because Task L owns it. If Task M preempts Task L, the low-priority owner may be delayed from releasing the mutex.

Task H: HIGH PRIORITY Waiting for mutex | v Task M: MEDIUM PRIORITY Preempts Task L | v Task L: LOW PRIORITY Owns mutex Cannot run to release it

14. Priority Inheritance

FreeRTOS mutexes support basic priority inheritance. When a higher-priority task blocks on a mutex held by a lower-priority task, the owner may temporarily inherit the higher priority.

Result

  • The mutex owner receives an elevated effective priority.
  • Unrelated medium-priority tasks are less likely to delay the owner.
  • The owner can complete its critical section and release the mutex sooner.
  • The original priority is restored according to the kernel's priority-inheritance rules.
Priority inheritance reduces certain forms of priority inversion. It does not eliminate all blocking, deadlock or deadline-miss possibilities.

15. Correct Mutex Usage with Timeout

A finite timeout allows the task to respond if the resource remains unavailable.

if (xSemaphoreTake(
        uartMutex,
        pdMS_TO_TICKS(100)
    ) == pdPASS)
{
    UART_SendString("System Message\r\n");

    xSemaphoreGive(uartMutex);
}
else
{
    /* Record resource acquisition timeout */
}

The timeout does not automatically fix the underlying contention. It provides an opportunity for the application to handle the failure.

16. Avoid Holding a Mutex for Too Long

Long mutex ownership increases blocking for other tasks.

Bad Design

xSemaphoreTake(uartMutex, portMAX_DELAY);

UART_SendString("Starting operation");

/* Long delay while holding mutex */
vTaskDelay(pdMS_TO_TICKS(1000));

UART_SendString("Operation complete");

xSemaphoreGive(uartMutex);

Better Design

xSemaphoreTake(uartMutex, portMAX_DELAY);

UART_SendString("Starting operation");

xSemaphoreGive(uartMutex);

/* Perform unrelated processing outside lock */
vTaskDelay(pdMS_TO_TICKS(1000));

xSemaphoreTake(uartMutex, portMAX_DELAY);

UART_SendString("Operation complete");

xSemaphoreGive(uartMutex);

Keep the protected region limited to the operations that actually require exclusive access.

17. Deadlock Prevention

Deadlock can occur when tasks wait indefinitely for resources held by one another.

Example

  • Task 1 owns Mutex A and waits for Mutex B.
  • Task 2 owns Mutex B and waits for Mutex A.
  • Neither task can continue.

Prevention Techniques

  • Define a global lock acquisition order.
  • Avoid nested mutexes where possible.
  • Keep ownership periods short.
  • Use timeouts and explicit recovery policies where appropriate.
  • Review every error path to ensure acquired mutexes are released.

18. Alternative Design: Dedicated UART Owner Task

For complex communication systems, a dedicated task can own the UART peripheral. Other tasks send messages to it through a queue.

SENSOR TASK | v MESSAGE | +----------+ | QUEUE | +----------+ | v UART OWNER TASK | UART DRIVER | SERIAL OUTPUT ^ | STATUS TASK

Advantages include:

  • Only one task directly accesses the UART driver.
  • Message ordering can be managed centrally.
  • DMA completion and buffer ownership can be handled by the owner task.
  • Other tasks do not need to acquire the UART mutex.
A dedicated owner task is often a better architecture for asynchronous peripherals or drivers with complex transaction lifetimes.

19. Practical Exercise 1 – Add a Third Task

Objective: Add a logging task that also uses the UART.

  • Create LoggingTask().
  • Use the same UART mutex.
  • Acquire the mutex before transmitting.
  • Release it after the protected transmission.
  • Test all three tasks together.

20. Practical Exercise 2 – Protect a Shared Counter

Objective: Protect a shared counter accessed by two tasks.

static SemaphoreHandle_t counterMutex;
static uint32_t sharedCounter = 0;

void UpdateCounter(void)
{
    if (xSemaphoreTake(
            counterMutex,
            portMAX_DELAY
        ) == pdPASS)
    {
        sharedCounter++;

        xSemaphoreGive(counterMutex);
    }
}

Expected result: Each increment executes under mutual exclusion, preventing concurrent task updates from interfering with one another.

The counter must not be accessed outside the same synchronization protocol. Also consider whether an atomic operation or a dedicated owner task would be more appropriate for the target.

21. Practical Exercise 3 – Simulate Priority Inversion

Objective: Study priority inversion and the effect of mutex priority inheritance.

  • Create low-, medium- and high-priority tasks.
  • Let the low-priority task acquire a mutex.
  • Make the high-priority task attempt to acquire the same mutex.
  • Allow the medium-priority task to perform unrelated work.
  • Observe task execution with and without mutex priority inheritance, using a suitable comparison mechanism.

Expected result: Observe how priority inheritance can allow the low-priority mutex owner to execute and release the mutex sooner.

22. Practical Exercise 4 – Add Mutex Timeout Handling

Objective: Detect a mutex acquisition timeout.

if (xSemaphoreTake(
        uartMutex,
        pdMS_TO_TICKS(200)
    ) == pdPASS)
{
    UART_SendString("Message\r\n");
    xSemaphoreGive(uartMutex);
}
else
{
    /* Log timeout or activate recovery policy */
}

Expected result: The task detects when the mutex cannot be acquired within the specified interval.

24. Keil µVision and LPC2129 Simulator Notes

The LPC2129 is based on ARM7TDMI-S. A mutex-based application can be studied with a compatible FreeRTOS port and toolchain.

Suggested Study Activities

  • Inspect the mutex handle and creation result.
  • Set breakpoints before and after mutex acquisition.
  • Observe task states while one task owns the mutex.
  • Study task priority changes during priority inheritance, where visible.
  • Inspect UART driver access and transmission completion logic.
  • Review the order in which tasks acquire and release shared resources.
Verify LPC2129 FreeRTOS port and Keil compiler compatibility before attempting execution. The simulator cannot establish physical UART timing, DMA behavior or electrical correctness unless those features are explicitly modeled.
