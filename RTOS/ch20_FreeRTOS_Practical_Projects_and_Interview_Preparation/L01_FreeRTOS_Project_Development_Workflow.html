2. Introduction to FreeRTOS Project Development

FreeRTOS project development is a structured engineering process in which an embedded application is divided into independent tasks and coordinated using RTOS kernel services.

A successful project must satisfy both functional requirements and timing requirements. It should also use processor, memory and peripheral resources safely.

Typical FreeRTOS Applications

  • Sensor monitoring and data acquisition.
  • Industrial automation and control.
  • Motor control systems.
  • UART, SPI, I2C and CAN communication.
  • Battery management systems.
  • Robotics and embedded monitoring systems.
  • IoT devices and gateways.
PROJECT REQUIREMENTS | SYSTEM DESIGN | HARDWARE / PORT SELECTION | FREERTOS INTEGRATION | TASK AND IPC DEVELOPMENT | BUILD AND DEBUG | TIMING / MEMORY TESTING | DEPLOYMENT

3. Requirement Analysis

Before writing code, identify exactly what the system must do.

Functional Requirements

Functional requirements describe the operations the application must perform.

  • Read sensor measurements.
  • Process user commands.
  • Control output devices.
  • Transmit status information.
  • Record errors and diagnostic information.

Non-Functional Requirements

Non-functional requirements define system quality and operating constraints.

  • Maximum response time.
  • Task execution deadlines.
  • Memory and processor limits.
  • Power consumption.
  • Reliability and fault recovery.
  • Communication throughput.

Example: Temperature Monitoring System

RequirementSpecification
Sensor acquisitionRead temperature every 100 ms.
Data processingConvert sensor data into temperature.
AlarmDetect temperature above configured limit.
CommunicationTransmit temperature over UART.
DisplayUpdate the display periodically.
Fault handlingDetect invalid sensor readings.
These values are example requirements. Actual periods and deadlines must be selected from the application specification and verified through timing analysis.

7. FreeRTOS Kernel Integration

Kernel integration means adding the correct FreeRTOS source files and processor-specific port implementation to the embedded project.

Common Kernel Files

FilePurpose
tasks.cTask creation, deletion and scheduling.
queue.cQueues and related synchronization services.
list.cInternal list management.
timers.cSoftware timer services.
event_groups.cEvent group services.
stream_buffer.cStream and message buffers.

Important Integration Requirements

  • Select the correct port for the processor and compiler.
  • Include the required port assembly or context-switch implementation.
  • Configure the system tick source.
  • Implement the required interrupt handlers.
  • Provide a correct linker memory layout.
  • Use the correct device startup code.
  • Include only the kernel modules needed by the application and configuration.
Never copy a port from a different processor family just because the source files have similar names. Context switching and interrupt handling are architecture-specific.

Divide the application into tasks according to function, timing requirements and resource ownership.

Task Design Considerations

  • Define each task's responsibility clearly.
  • Specify task period or event trigger.
  • Estimate execution time and stack requirement.
  • Define priority using timing analysis.
  • Identify shared resources.
  • Define failure and timeout behavior.
Priority values shown are examples only. Final priorities must be derived from response-time requirements, blocking and interrupt interference.

10. Task Creation and Initialization

Tasks are commonly created before the scheduler starts.

Example Application Structure

#include "FreeRTOS.h"
#include "task.h"

static void SensorTask(void *pvParameters)
{
    (void) pvParameters;

    for (;;)
    {
        /* Acquire sensor data. */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

static void CommunicationTask(void *pvParameters)
{
    (void) pvParameters;

    for (;;)
    {
        /* Process communication work. */

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

int main(void)
{
    /* Initialize hardware and required drivers. */

    if (xTaskCreate(
            SensorTask,
            "Sensor",
            256,
            NULL,
            3,
            NULL
        ) != pdPASS)
    {
        /* Handle task creation failure. */
    }

    if (xTaskCreate(
            CommunicationTask,
            "Comm",
            256,
            NULL,
            2,
            NULL
        ) != pdPASS)
    {
        /* Handle task creation failure. */
    }

    vTaskStartScheduler();

    for (;;)
    {
        /* Reached only if scheduler startup returns. */
    }
}

This example illustrates the application structure. It requires a compatible port, valid configuration, startup code and hardware initialization before it can build and run on a target.

Stack depth in xTaskCreate() is specified in StackType_t elements, not bytes. The actual byte count depends on the selected port.

11. Inter-Task Communication Design

Tasks often need to exchange data or signal events. Choose the communication mechanism based on the information being transferred and the required synchronization behavior.

MechanismTypical Application
QueueTransfer sensor readings and command structures.
Binary semaphoreSignal an event or synchronize a task.
Counting semaphoreTrack a count of available events or resources.
MutexProtect a shared resource in task context.
Task notificationSignal a particular task efficiently.
Event groupCoordinate multiple event conditions.
Stream bufferTransfer a byte stream between tasks.
Message bufferTransfer discrete messages.

Example Data Flow

SENSOR TASK | SENSOR READING | QUEUE | PROCESSING TASK | PROCESSED DATA | QUEUE | COMMUNICATION TASK

Queues are useful when the application must transfer structured data while separating producer and consumer execution.

12. Peripheral Driver Development

Peripheral drivers provide a controlled interface between application tasks and hardware devices.

Typical Embedded Drivers

  • GPIO driver.
  • UART driver.
  • ADC driver.
  • Timer driver.
  • PWM driver.
  • SPI driver.
  • I2C driver.
  • CAN driver.

Driver Design Principles

  • Keep hardware register access inside appropriate driver modules.
  • Separate application logic from peripheral details.
  • Use interrupts or DMA where appropriate.
  • Define clear buffer ownership.
  • Protect shared peripherals where necessary.
  • Provide timeout and error handling.
  • Avoid blocking operations in ISR context.
A mutex can coordinate task-level access to a peripheral, but it does not automatically protect an ISR or an active DMA transaction. The driver must define the complete resource-ownership protocol.

13. Timing and Priority Analysis

Before finalizing a design, analyze whether the application can complete required work within its deadlines.

Important Timing Parameters

  • Release time.
  • Execution time.
  • Task period.
  • Relative deadline.
  • Response time.
  • Blocking time.
  • Interrupt interference.
  • Release jitter.

Response-Time Analysis

For a fixed-priority task system under suitable assumptions, a common response-time recurrence is:

Ri = Ci + Bi
     + Σ ceil(Ri / Tj) × Cj

R_i = response time of task i
C_i = execution time of task i
B_i = blocking time
T_j = period of higher-priority task j
C_j = execution time of higher-priority task j

Iterate the equation until the result converges or exceeds the task deadline.

This simplified recurrence assumes a particular fixed-priority periodic-task model. Include interrupt interference, jitter, non-preemptive sections and other relevant effects when the actual system requires them.

  • Event groups and timer objects.
  • Communication buffers.

17. Testing Strategy

Testing should cover individual software components and the integrated application.

Test LevelPurpose
Unit testingTest individual functions and drivers.
Integration testingVerify communication between tasks and modules.
Functional testingCheck required application behavior.
Timing testingMeasure response time and deadline compliance.
Stress testingTest high load and resource contention.
Fault-injection testingVerify error detection and recovery.
Regression testingEnsure changes do not break existing behavior.

Testing Checklist

  • All tasks start correctly.
  • Task priorities are verified.
  • Queue overflow behavior is handled.
  • Semaphore and mutex usage is correct.
  • Stack usage is within the allocated limit.
  • Heap allocation failures are handled.
  • Interrupt-to-task communication works correctly.
  • Timeout and recovery paths are tested.
  • Timing requirements are verified under stress.

18. Deployment and Maintenance

After testing, the firmware is prepared for deployment to the target device.

Deployment Activities

  1. Freeze the approved source-code version.
  2. Build the release configuration.
  3. Review compiler and linker warnings.
  4. Generate the required firmware image.
  5. Program the target device using the supported interface.
  6. Verify startup and peripheral initialization.
  7. Run acceptance tests on the target.
  8. Record firmware version and configuration.
  9. Prepare recovery and update procedures.

Maintenance Activities

  • Track software changes.
  • Maintain source-code version control.
  • Document known limitations.
  • Monitor field failures.
  • Retest after kernel or compiler upgrades.
  • Maintain firmware backup and recovery procedures.

19. Example Mini Project – Temperature Monitoring System

Project objective: Design an RTOS-based temperature monitoring system with periodic sensor acquisition, threshold detection and UART reporting.

Functional Blocks

TEMPERATURE SENSOR | ADC DRIVER | SENSOR TASK | QUEUE | PROCESSING TASK / \ ALARM CHECK FILTER \ / QUEUE | COMMUNICATION TASK | UART

Task Allocation

TaskResponsibility
Sensor TaskRead ADC at a defined interval.
Processing TaskConvert ADC value, validate and compare against threshold.
Communication TaskSend readings and alarm status through UART.

Development Steps

  1. Initialize the ADC and UART drivers.
  2. Create a queue for sensor measurements.
  3. Create the sensor acquisition task.
  4. Create the processing task.
  5. Create the communication task.
  6. Configure task periods and priorities.
  7. Handle invalid readings and queue errors.
  8. Measure response time and stack usage.
  9. Test normal, threshold and sensor-fault conditions.

Expected Behavior

  • Sensor readings are acquired periodically.
  • Invalid measurements are detected.
  • Threshold violations generate an alarm condition.
  • UART reports processed measurements.
  • Tasks coordinate without uncontrolled busy waiting.

25. Keil µVision and LPC2129 Development Notes

The user's LPC2129 study environment uses Keil µVision simulation. It is useful for learning ARM7 register behavior, C execution, memory inspection and supported peripheral simulations.

Important Limitations

  • Verify that a compatible ARM7 FreeRTOS port and Keil compiler integration are available before building an RTOS project.
  • Confirm the correct context-switch and interrupt implementation.
  • Do not assume that all LPC2129 peripherals are fully modeled by the simulator.
  • Simulator observations do not replace physical hardware timing measurements.
  • UART, ADC, PWM, I2C and CAN behavior must be validated against actual hardware requirements.
For practical FreeRTOS project development, a supported STM32 Nucleo development board with a compatible toolchain is a useful hardware option. The LPC2129 simulator can remain a separate platform for ARM7 and register-level learning.
