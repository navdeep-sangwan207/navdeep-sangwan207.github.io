2. What Is Stack Overflow?

Stack overflow occurs when a task uses more stack memory than has been allocated to it.

Every task has a finite stack area. Function calls, local variables, saved registers and other execution information consume this memory.

If execution requires more space than the allocated stack provides, data outside the stack boundary may be overwritten.

ALLOCATED TASK STACK +----------------------------------+ | | | UNUSED STACK SPACE | | | +----------------------------------+ | | | CURRENT STACK DATA | | | +----------------------------------+ | STACK BOUNDARY | +----------------------------------+ | v Further stack growth may overwrite adjacent memory

The exact direction of stack growth and location of the boundary depend on the processor architecture and FreeRTOS port.

Stack overflow is a serious embedded-system fault. It can corrupt task context, kernel data, application variables or neighboring memory regions.

3. Causes of Stack Overflow

3.1 Insufficient Stack Allocation

A task may be created with a stack smaller than its actual execution requirements.

xTaskCreate(
    SensorTask,
    "Sensor",
    64,
    NULL,
    2,
    NULL
);

The stack depth of 64 elements may be insufficient for a task that uses large local arrays or deeply nested function calls. The correct size must be measured for the target and application.

3.2 Large Local Variables

void ProcessData(void)
{
    uint8_t buffer[2048];

    /* Process data */
}

A large local array can consume a significant portion of the task stack if the compiler places it there.

3.3 Deep Function Calls

void FunctionD(void)
{
    int data[100];
}

void FunctionC(void)
{
    FunctionD();
}

void FunctionB(void)
{
    FunctionC();
}

void FunctionA(void)
{
    FunctionB();
}

Nested calls can increase peak stack consumption because multiple function frames may remain active simultaneously.

3.4 Recursive Functions

void RecursiveFunction(int count)
{
    if (count <= 0)
    {
        return;
    }

    RecursiveFunction(count - 1);
}

Every recursive call can consume additional stack space. Unbounded recursion can eventually exhaust the task stack.

3.5 Library Function Usage

Some library functions, formatting routines and complex calculations can require more stack than expected.

3.6 Interrupt and Exception Handling

Interrupt handling may consume additional stack memory depending on the processor architecture, exception mechanism and RTOS port.

Do not assume that every interrupt uses the interrupted task's stack. Some architectures and ports use dedicated interrupt stacks or separate processor-mode stacks.

4. Consequences of Stack Overflow

ConsequenceDescription
Memory corruptionData outside the allocated stack may be overwritten.
Task failureThe task may stop functioning correctly.
Context corruptionSaved registers or return addresses may become invalid.
Unexpected resetThe processor may enter a fault state or watchdog recovery.
Incorrect outputVariables and calculated values may become corrupted.
System instabilityOther tasks or kernel objects may be affected.

Stack overflow may not cause an immediate crash. Some faults appear later, making diagnosis difficult.

5. FreeRTOS Stack Overflow Detection

FreeRTOS provides configurable stack-overflow checking through the configCHECK_FOR_STACK_OVERFLOW setting in FreeRTOSConfig.h.

5.1 Configuration Value 0

#define configCHECK_FOR_STACK_OVERFLOW 0

Stack-overflow checking is disabled.

5.2 Configuration Value 1

#define configCHECK_FOR_STACK_OVERFLOW 1

Enables basic stack-boundary or stack-pointer checks implemented by the selected port.

5.3 Configuration Value 2

#define configCHECK_FOR_STACK_OVERFLOW 2

Enables additional checking, commonly including examination of a known fill pattern near the stack boundary.

SettingDetection approach
0No FreeRTOS stack-overflow checking.
1Basic port-specific stack-boundary checks.
2Additional pattern checking, where implemented by the port.
The precise checks performed by values 1 and 2 are port-dependent. These settings do not guarantee detection of every possible stack corruption event.

6. Stack Overflow Hook Function

When FreeRTOS detects a stack overflow using its configured checking mechanism, it calls the application-provided hook function.

6.1 Function Prototype

void vApplicationStackOverflowHook(
    TaskHandle_t xTask,
    char *pcTaskName
);

Parameters:

  • xTask: Handle identifying the task reported by the kernel.
  • pcTaskName: Name of the task reported by the kernel.

6.2 Implementation Example

#include "FreeRTOS.h"
#include "task.h"

void vApplicationStackOverflowHook(
    TaskHandle_t xTask,
    char *pcTaskName
)
{
    (void)xTask;
    (void)pcTaskName;

    /* Record diagnostic information if safe */

    taskDISABLE_INTERRUPTS();

    for (;;)
    {
        /* Enter a safe failure state */
    }
}

The hook should avoid operations that depend on potentially corrupted task state.

The hook is application-provided. Its required declaration, configuration and behavior must match the selected FreeRTOS release and port.

7. How Stack Overflow Detection Works

A common implementation of stack checking uses stack boundary information and a known fill pattern.

7.1 Stack Fill Pattern

When a task is created, the port may initialize unused stack memory with a known byte pattern.

TASK STACK AT CREATION +--------------------------------+ | 0xA5 0xA5 0xA5 0xA5 ... | | 0xA5 0xA5 0xA5 0xA5 ... | | 0xA5 0xA5 0xA5 0xA5 ... | | | | INITIAL STACK | +--------------------------------+

The exact pattern and initialization method depend on the FreeRTOS port and implementation.

7.2 After Task Execution

As the task uses stack space, previously unused regions are overwritten by execution data.

STACK AFTER EXECUTION +--------------------------------+ | 0xA5 0xA5 0xA5 0xA5 ... | | 0xA5 0xA5 0xA5 0xA5 ... | | SAVED DATA AND LOCAL VALUES | | FUNCTION CALL FRAMES | | CURRENT STACK DATA | +--------------------------------+

The kernel can examine selected stack regions or boundary information during supported checking operations.

Pattern checking is a diagnostic technique, not a memory-protection mechanism. Corruption may occur before the scheduler detects it.

8. Stack High-Water Mark Monitoring

The high-water-mark function helps estimate how much stack has been used.

8.1 API

UBaseType_t uxTaskGetStackHighWaterMark(
    TaskHandle_t xTask
);

It reports the minimum amount of unused stack observed since the task started, expressed in stack elements.

8.2 Example

#include "FreeRTOS.h"
#include "task.h"

void MonitorTask(void *pvParameters)
{
    UBaseType_t remaining;

    for (;;)
    {
        remaining =
            uxTaskGetStackHighWaterMark(NULL);

        /* Log remaining stack elements */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

For the calling task, pass NULL.

8.3 Convert to Bytes

UBaseType_t remainingWords;
size_t remainingBytes;

remainingWords =
    uxTaskGetStackHighWaterMark(NULL);

remainingBytes =
    (size_t)remainingWords * sizeof(StackType_t);

8.4 Example Calculation

Suppose the high-water-mark result is 32 elements and each element occupies 4 bytes.

Unused stack = 32 × 4

             = 128 bytes

This means that the task has had at least 128 bytes of unused stack remaining at the observed high-water mark, subject to the port's measurement method.

9. Stack Overflow Detection vs High-Water Mark

ParameterOverflow CheckingHigh-Water Mark
PurposeDetect certain stack-boundary violationsEstimate minimum unused stack
MechanismPort-specific boundary and/or pattern checksMeasures previously unused stack
ResultCan trigger overflow hookReturns an unused-stack measurement
UsageFault detectionStack sizing and monitoring
LimitationMay not detect every corruptionOnly reflects execution paths observed so far

Both techniques complement each other. Neither replaces proper stack sizing and worst-case testing.

10. Stack Overflow Debugging Procedure

  1. Identify the task reported by the overflow hook, if available.
  2. Check the task's configured stack depth.
  3. Inspect the task function and its nested function calls.
  4. Look for large local arrays and recursive calls.
  5. Check library routines and compiler-generated stack usage.
  6. Measure the task high-water mark under realistic workloads.
  7. Inspect stack memory and saved context in the debugger.
  8. Increase stack allocation when justified by measurement.
  9. Repeat tests with worst-case inputs and error paths.
Do not simply increase every task stack arbitrarily. Identify the task with excessive usage and determine the actual source of consumption.

Compiler and debugger facilities can help identify stack consumption.

11.1 Keil uVision Simulator Considerations

In Keil uVision, a simulator-only project can be used to inspect processor registers, memory locations and execution flow when the selected processor and project configuration are supported.

For a FreeRTOS application, actual stack-overflow behavior can only be tested after a compatible FreeRTOS port and compiler integration have been built and run successfully.

A normal LPC2129 bare-metal simulation does not automatically provide FreeRTOS task scheduling or its stack-overflow checks. The ARM7 port and simulator behavior must be verified separately.

Assume a task uses the following approximate stack components:

ComponentEstimated Stack Usage

Library function usage100 bytes

Assume a design margin of 50% for this example:

Required planning size =
    500 + (500 × 0.50)

Stack depth = 750 / 4

This is an illustrative estimate, not a universal sizing formula. The final stack allocation must be validated against compiler reports, port requirements and measured worst-case execution.

13. Best Practices for Preventing Stack Overflow

  • Determine stack size using analysis and measurement.
  • Avoid large automatic local arrays in frequently called functions.
  • Prefer bounded loops over uncontrolled recursion.
  • Review library functions that use substantial stack memory.
  • Enable stack-overflow checking during development.
  • Monitor high-water marks for every important task.
  • Test error-handling and maximum-load execution paths.
  • Keep interrupt service routines short.
  • Understand whether interrupts use task, system or dedicated interrupt stacks.
  • Recheck stack usage after software or compiler changes.
  • Maintain a documented stack budget for the complete application.

16. Lesson Summary

  • Stack overflow occurs when task execution exceeds allocated stack capacity.
  • Common causes include insufficient stack size, large local arrays, recursion and deep function calls.
  • Overflow can corrupt memory, saved context and kernel data.
  • FreeRTOS provides configurable stack-overflow checking.
  • vApplicationStackOverflowHook() provides an application-level response to detected overflow.
  • uxTaskGetStackHighWaterMark() helps estimate minimum unused stack.
  • Compiler reports, debugger inspection and worst-case testing improve stack analysis.
  • Proper sizing and continuous validation are essential for reliable RTOS applications.
