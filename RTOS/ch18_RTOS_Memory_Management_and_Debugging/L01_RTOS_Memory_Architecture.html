Lesson 01 – RTOS Memory Architecture

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

Memory management is an important part of Real-Time Operating System design. An RTOS manages memory used by tasks, stacks, queues, semaphores, software timers, event groups, and application data structures.

A well-designed memory architecture helps maintain predictable execution, prevents memory corruption, and reduces the risk of system failures.

Learning Objectives

  • Understand memory architecture in embedded systems.
  • Identify major memory regions.
  • Understand RAM, ROM, Flash, and stack memory.
  • Learn how an RTOS uses memory.
  • Understand task stack allocation.
  • Differentiate static and dynamic memory.
  • Identify common memory-related problems.

1. What Is Memory Architecture?

Memory architecture describes how memory is organized and used by a processor and its software.

An embedded system typically uses several memory types for program storage, temporary data, task execution, peripheral access, and persistent information.

Basic Embedded System Memory Architecture

        Embedded Processor
                |
       +--------+--------+
       |        |        |
       v        v        v
     Flash     SRAM    Peripherals
       |        |
       |        +------------------+
       |                           |
       v                           v
  Program Code                Runtime Data
                                  |
                     +------------+------------+
                     |            |            |
                     v            v            v
                   Stack         Heap       Global Data

The exact memory organization depends on the microcontroller, processor architecture, linker configuration, and application.

2. Types of Memory in Embedded Systems

2.1 ROM – Read Only Memory

ROM is non-volatile memory. Its contents are retained when power is removed. Traditional ROM is programmed during manufacturing, while modern systems commonly use Flash or other programmable non-volatile memory.

2.2 Flash Memory

Flash memory stores program code, constant data, and sometimes persistent application information.

  • Non-volatile storage.
  • Retains information without power.
  • Used for firmware and bootloader storage.
  • Can be erased and reprogrammed within device limitations.

2.3 RAM – Random Access Memory

RAM stores data used while the application is running. Typical embedded RAM is volatile, so its contents are generally lost when power is removed.

  • Stores global and static variables.
  • Stores local variables and function call data.
  • Stores task stacks and RTOS objects.
  • May contain dynamically allocated heap memory.

2.4 SRAM

Static RAM is commonly used as the main working memory in microcontrollers. It provides fast read and write access and does not require periodic refresh like DRAM.

Memory TypeTypical UsePower Loss
FlashFirmware and persistent dataRetains contents
SRAMRuntime variables, stacks, heapContents lost
ROMFixed program or boot informationRetains contents
EEPROMSmall persistent configuration dataRetains contents

4. Stack Memory

A stack is a memory region used to manage function calls and temporary execution data.

When a function is called, the processor and compiler use stack space for items such as local variables, saved registers, and return information. The exact contents depend on the ABI and compiler.

Example

#include <stdio.h>

void Calculate(void)
{
    int a = 10;
    int b = 20;
    int result;

    result = a + b;

    printf("%d\n", result);
}

int main(void)
{
    Calculate();

    return 0;
}

The local variables in Calculate() may be placed in its stack frame. Compiler optimization can change the actual storage used.

Stack Characteristics

  • Used for function call management.
  • Stores many local variables and temporary values.
  • Each FreeRTOS task has its own task stack.
  • Stack size must be sufficient for the task's execution paths.
  • Excessive stack use can cause stack overflow.

5. Heap Memory

Heap memory is used for dynamic memory allocation during program execution.

In C, functions such as malloc(), calloc(), and free() are commonly associated with heap management.

Example

#include <stdlib.h>

int main(void)
{
    int *ptr;

    ptr = (int *)malloc(5 * sizeof(int));

    if (ptr == NULL)
    {
        return 1;
    }

    /* Use allocated memory */

    free(ptr);
    ptr = NULL;

    return 0;
}

Heap Characteristics

  • Supports dynamic memory allocation.
  • Allocation size can be determined at runtime.
  • Allocation and deallocation require management.
  • Repeated allocation and freeing may fragment memory.
  • Allocation can fail when sufficient memory is unavailable.
In real-time embedded software, dynamic allocation must be designed carefully. Unbounded allocation time, fragmentation, and allocation failure can make system behavior unpredictable.

6. How an RTOS Uses Memory

An RTOS requires memory for its kernel data structures and application objects.

RTOS ComponentMemory Requirement
Task Control Block (TCB)Task state, priority, stack reference, and scheduling information.
Task stackFunction calls, local variables, and task execution context.
QueueQueue control structure and item storage.
SemaphoreKernel object control information.
MutexControl information and ownership-related state.
Event groupEvent-bit state and control information.
Software timerTimer object and associated kernel data.

The amount and allocation method depend on whether the application uses static allocation, dynamic allocation, or a combination of both.

7. Task Stack Architecture in FreeRTOS

Every FreeRTOS task has an independent stack. The stack stores the task's execution context and data required while the task runs. 

              FreeRTOS Scheduler
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       Task A       Task B       Task C
          |           |           |
          v           v           v
      Stack A      Stack B      Stack C
      +------+     +------+     +------+
      | Data |     | Data |     | Data |
      | Calls|     | Calls|     | Calls|
      |Saved |     |Saved |     |Saved |
      |Regs  |     |Regs  |     |Regs  |
      +------+     +------+     +------+

When a task is switched out, the port-specific context-switch code saves the required processor context on that task's stack or in associated kernel structures. When the task runs again, the context is restored.

FreeRTOS task stack depth is specified in StackType_t elements in the standard task-creation API, not bytes. Actual byte usage is: 

Stack bytes = Stack depth * sizeof(StackType_t)

8. Static and Dynamic Memory Allocation in RTOS

Static Allocation

Memory is reserved before runtime. The application supplies storage for the RTOS object where static allocation is supported.

Dynamic Allocation

Memory is obtained from an allocator when the RTOS object is created during execution.

FeatureStatic AllocationDynamic Allocation
Allocation timeBefore runtime or at compile/link timeDuring execution
Memory sizePredeterminedRequested at runtime
Allocation failureUsually detected during build or initialization designCan occur at runtime
FragmentationNo allocator fragmentation for fixed objectsDepends on allocator and usage pattern
FlexibilityLess flexibleMore flexible

FreeRTOS Configuration

#define configSUPPORT_STATIC_ALLOCATION  1
#define configSUPPORT_DYNAMIC_ALLOCATION 1

These settings indicate whether the application can use the corresponding allocation methods. Exact requirements depend on the selected FreeRTOS version, port, and configuration.

9. Memory Allocation Example in FreeRTOS

A task can be created dynamically using xTaskCreate(). The kernel allocates the required task control structure and stack using the configured FreeRTOS heap implementation. 

#include "FreeRTOS.h"
#include "task.h"

void TaskFunction(void *pvParameters)
{
    for (;;)
    {
        /* Task operations */
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    BaseType_t status;

    status = xTaskCreate(
        TaskFunction,
        "Task1",
        256,
        NULL,
        2,
        NULL
    );

    if (status != pdPASS)
    {
        /* Handle allocation or task-creation failure */
        for (;;)
        {
        }
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

In this example, the task stack depth is 256 stack elements. The task's total memory requirement also includes its TCB and allocator overhead.

The example is generic FreeRTOS code. It requires a compatible port, startup code, linker configuration, heap implementation, and hardware support. It is not a claim that the LPC2129 Keil simulator setup automatically supports this FreeRTOS program.

10. Memory-Related Problems in RTOS

10.1 Stack Overflow

A task uses more stack memory than its allocated stack can provide. This may corrupt nearby memory or cause a system fault.

10.2 Heap Exhaustion

The allocator cannot satisfy a new memory request because insufficient free memory is available.

10.3 Memory Fragmentation

Free memory becomes divided into smaller blocks. The total free memory may be sufficient, but a large contiguous allocation may not be possible.

10.4 Memory Leak

Allocated memory is no longer needed but is not released. Repeated leaks can eventually exhaust available memory.

10.5 Buffer Overflow

An operation writes beyond the boundaries of an allocated buffer, potentially corrupting other data or control structures.

10.6 Use-After-Free

An application accesses memory after it has been released to the allocator. This can cause unpredictable behavior.

11. Memory Design Best Practices

  1. Estimate memory requirements before implementation.
  2. Choose task stack sizes based on actual execution paths.
  3. Use static allocation where predictable memory usage is important.
  4. Check every dynamic allocation or object-creation result.
  5. Release dynamically allocated memory when no longer required.
  6. Avoid unnecessary repeated allocation and deallocation.
  7. Validate array and buffer boundaries.
  8. Use suitable stack monitoring and debugging facilities.
  9. Keep ownership rules clear for shared buffers.
  10. Reserve memory for idle, timer service, and other required kernel tasks.

12. Practical Memory Calculation

Assume an embedded application has three tasks. Each task uses a stack depth of 256 elements, and sizeof(StackType_t) is 4 bytes on the selected port.

Stack Memory Per Task

Stack memory = Stack depth * StackType_t size

             = 256 * 4

             = 1024 bytes

Total Stack Memory

Total = Number of tasks * Stack per task

      = 3 * 1024

      = 3072 bytes

The three task stacks require 3072 bytes in total. This calculation excludes TCBs, queues, semaphores, timers, event groups, other application data, heap metadata, and additional kernel tasks.

Important: This is a stack-memory calculation, not the complete RAM requirement of the RTOS application.

15. Lesson Summary

  • Memory architecture defines how memory is organized and used.
  • Flash stores firmware and persistent information.
  • SRAM stores runtime data.
  • Program memory contains code and read-only data.
  • RAM contains data, stack, and possibly heap regions.
  • Each FreeRTOS task has its own stack.
  • RTOS objects require memory for control structures and data storage.
  • Static and dynamic allocation provide different memory-management approaches.
  • Stack overflow, heap exhaustion, fragmentation, and memory leaks are common problems.
  • Memory planning and monitoring improve system reliability.
