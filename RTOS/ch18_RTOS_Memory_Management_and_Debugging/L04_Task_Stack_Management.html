2. What Is a Task Stack?

A task stack is a dedicated memory area used by a task during execution. It stores temporary information required by function calls and execution flow.

Typical stack contents include:

  • Return addresses from function calls.
  • Local variables and temporary data.
  • Function parameters when required by the calling convention.
  • Saved processor registers.
  • Interrupt or exception context when the processor and port use the task stack for that context.
  • Compiler-generated temporary values and alignment padding.

Each FreeRTOS task normally has its own stack. This allows tasks to maintain independent execution contexts while the scheduler switches between them.

TASK 1 | +--------------+ | Task Stack 1 | +--------------+ TASK 2 | +--------------+ | Task Stack 2 | +--------------+ TASK 3 | +--------------+ | Task Stack 3 | +--------------+
The exact contents of a task stack depend on the processor architecture, compiler calling convention, FreeRTOS port and interrupt-handling implementation.

3. Stack and Heap in an RTOS

Stack and heap are different memory-management areas.

ParameterTask StackHeap
PurposeStores task execution dataProvides memory for dynamic allocation
Typical contentsLocal variables, call frames and saved contextDynamic tasks, queues, buffers and other objects
AllocationAssigned to a taskManaged by the selected allocator
LifetimeUsually exists while the task existsDepends on allocation and release operations
Common failureStack overflowAllocation failure or fragmentation
APPLICATION RAM +------------------------------------------+ | Global and static variables | +------------------------------------------+ | FreeRTOS heap | | Dynamic task objects, queues and buffers | +------------------------------------------+ | Task 1 stack | +------------------------------------------+ | Task 2 stack | +------------------------------------------+ | Task 3 stack | +------------------------------------------+

This is a conceptual memory layout. Actual placement depends on the linker script, compiler, memory map and allocation strategy.

4. How a Task Uses Its Stack

Consider a task that calls multiple functions:

void Calculate(void)
{
    int result = 0;

    result = 10 + 20;
}

void ProcessData(void)
{
    int value = 100;

    Calculate();
}

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        ProcessData();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

During execution:

  1. SensorTask() begins executing.
  2. It calls ProcessData().
  3. The function call creates the required execution frame according to the compiler and processor convention.
  4. ProcessData() calls Calculate().
  5. Additional stack space may be used for the nested call.
  6. When functions return, their stack frames are released according to the calling convention.
Compilers may keep variables in registers, optimize away unused variables or inline functions. Therefore, source-code variable sizes alone cannot accurately determine actual stack consumption.

5. Stack Pointer

The Stack Pointer (SP) is a processor register that identifies the current position of the active stack.

During function calls, returns, interrupt handling and context switching, the processor or RTOS port updates or restores stack-related state.

5.1 Stack Growth Direction

Stack growth direction depends on the processor architecture and port.

EXAMPLE: DOWNWARD-GROWING STACK Higher memory address | +--------------+ | Existing data| +--------------+ | Local data | +--------------+ | Saved context| +--------------+ | v Stack grows downward toward lower addresses

Some architectures or implementations use different conventions. Never assume that every RTOS task stack grows in the same direction.

5.2 Stack Pointer During Context Switching

When the scheduler switches from one task to another, the port saves the outgoing task's required processor context and restores the incoming task's context.

TASK A RUNNING | v Save required context | v Store Task A stack state | v Scheduler selects B | v Restore Task B context | v TASK B RUNNING

The exact register set and save/restore sequence are port-specific.

6. Task Stack Allocation in FreeRTOS

FreeRTOS provides both dynamic and static task creation methods.

6.1 Dynamic Allocation Using xTaskCreate()

With xTaskCreate(), the kernel obtains memory for the task control block and stack through the configured FreeRTOS allocator.

BaseType_t result;

result = xTaskCreate(
    SensorTask,
    "SensorTask",
    256,
    NULL,
    2,
    NULL
);

if (result != pdPASS)
{
    /* Handle task creation failure */
}

The stack-depth argument specifies the number of stack elements, not bytes.

6.2 Static Allocation Using xTaskCreateStatic()

With xTaskCreateStatic(), the application supplies the stack array and task control-block storage.

#define TASK_STACK_SIZE 256

static StackType_t taskStack[TASK_STACK_SIZE];
static StaticTask_t taskControlBlock;

TaskHandle_t taskHandle;

taskHandle = xTaskCreateStatic(
    SensorTask,
    "SensorTask",
    TASK_STACK_SIZE,
    NULL,
    2,
    taskStack,
    &taskControlBlock
);

if (taskHandle == NULL)
{
    /* Handle task creation failure */
}

The storage must remain valid for the lifetime of the task.

The availability of static creation APIs depends on the FreeRTOS configuration and version. See Lesson 02 for the complete static-versus-dynamic allocation comparison.

7. Stack Depth and Stack Size

One of the most important FreeRTOS stack-management concepts is the difference between stack depth and stack size in bytes.

In FreeRTOS task-creation APIs, stack depth is expressed in elements of type StackType_t.

Formula:

Stack size in bytes =
    Stack depth × sizeof(StackType_t)

7.1 Example: 256 Stack Elements

Assume the target defines:

sizeof(StackType_t) = 4 bytes

For a stack depth of 256:

Stack size = 256 × 4

           = 1024 bytes

           = 1 KB

7.2 Example: 512 Stack Elements

Stack size = 512 × 4

           = 2048 bytes

           = 2 KB
Do not assume that a stack depth of 256 always means 256 bytes. The byte size depends on sizeof(StackType_t) for the selected target.

8. Factors Affecting Stack Size

The required stack size depends on several application and compiler characteristics.

FactorEffect on Stack Usage
Local variablesMay consume stack space if stored in stack frames.
Nested function callsIncrease simultaneous call-frame requirements.
Recursive functionsCan cause repeated stack-frame allocation.
Interrupt handlingMay require additional stack space depending on the architecture and port.
Library functionsMay use significant internal stack space.
Floating-point operationsMay require additional register or software support, depending on the target.
Compiler optimizationCan change register usage, inlining and stack-frame size.
Function call depthDeeper call chains generally increase peak stack usage.

Consider an application with four tasks.

Total task stack memory:

1024 + 2048 + 1024 + 512

= 4608 bytes

= 4.5 KB

This is only the sum of the four task stacks. Additional RAM is required for task control blocks, queues, other kernel objects, application data and any heap overhead.

10. Stack Usage Monitoring in FreeRTOS

FreeRTOS provides a task stack high-water-mark function in supported configurations.

10.1 uxTaskGetStackHighWaterMark()

UBaseType_t uxTaskGetStackHighWaterMark(
    TaskHandle_t xTask
);

This function reports the minimum amount of stack space that has remained unused since the task started, expressed in stack elements (words), not bytes.

10.2 Example

#include "FreeRTOS.h"
#include "task.h"

void StackMonitorTask(void *pvParameters)
{
    UBaseType_t remaining;

    for (;;)
    {
        remaining =
            uxTaskGetStackHighWaterMark(NULL);

        /* Record or display remaining stack
           in stack elements */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

Passing NULL checks the calling task's stack.

10.3 Convert the Result into Bytes

UBaseType_t remainingWords;
size_t remainingBytes;

remainingWords =
    uxTaskGetStackHighWaterMark(NULL);

remainingBytes =
    (size_t)remainingWords * sizeof(StackType_t);

The calculation converts the reported unused stack elements into bytes.

A high-water mark is based on the stack usage observed so far. It does not prove that every possible execution path is safe. Exercise error handling, worst-case inputs, nested calls and exceptional paths during testing.

11. Stack Overflow Detection

Stack overflow occurs when a task uses more stack space than has been allocated to it.

Possible consequences include:

  • Corruption of adjacent memory.
  • Incorrect local variable values.
  • Corruption of saved context.
  • Unexpected task behavior.
  • System crashes or unpredictable execution.

FreeRTOS provides configurable stack-overflow checking.

11.1 Configuration

#define configCHECK_FOR_STACK_OVERFLOW    2

Common settings:

ValueMeaning
0Stack overflow checking disabled.
1Basic stack pointer or boundary checking, as implemented by the port.
2Additional stack-pattern checking, where supported by the port.

11.2 Hook Function

void vApplicationStackOverflowHook(
    TaskHandle_t xTask,
    char *pcTaskName
)
{
    /* Record task name and diagnostic data */

    taskDISABLE_INTERRUPTS();

    for (;;)
    {
        /* Enter safe failure state */
    }
}

The hook must be provided by the application when stack-overflow checking is enabled and required by the selected FreeRTOS port.

Stack-overflow detection is a diagnostic safeguard, not a guarantee that all stack corruption will be detected before damage occurs.

12. Stack Management Best Practices

  1. Estimate stack requirements before task creation.
  2. Use compiler-generated stack-usage reports when available.
  3. Measure high-water marks during realistic testing.
  4. Test worst-case execution paths and error conditions.
  5. Avoid uncontrolled recursion.
  6. Avoid unnecessarily large local arrays.
  7. Use static buffers or dedicated shared buffers where appropriate.
  8. Enable stack-overflow checking during development.
  9. Keep interrupt handlers short and understand which stack they use.
  10. Reserve an appropriate safety margin.
  11. Reassess stack sizes after compiler, library or application changes.

16. Lesson Summary

  • A task stack stores execution data, function-call information and saved context.
  • Each FreeRTOS task normally has its own stack.
  • Stack depth is measured in StackType_t elements.
  • Stack memory in bytes equals stack depth multiplied by sizeof(StackType_t).
  • Stack requirements depend on call depth, local variables, compiler behavior and interrupt handling.
  • uxTaskGetStackHighWaterMark() reports minimum unused stack observed in stack elements.
  • Stack-overflow checking can help identify stack-related faults.
  • Worst-case testing and an appropriate safety margin are essential for reliable embedded systems.
