2. What Is RTOS Debugging?

RTOS debugging is the process of identifying, analyzing and correcting software defects in a real-time operating system application.

Unlike a simple sequential program, an RTOS application contains multiple tasks, interrupts and shared resources. Therefore, debugging must consider both program logic and execution timing.

Common problems include:

  • Task not executing.
  • Unexpected task blocking.
  • Incorrect task priority.
  • Stack overflow.
  • Heap allocation failure.
  • Queue communication failure.
  • Semaphore misuse.
  • Priority inversion and deadlock.
  • Race conditions and data corruption.
  • Timing and deadline violations.

4. Breakpoint-Based Debugging

A breakpoint pauses program execution when the processor reaches a specified instruction or when a configured condition is satisfied.

4.1 Types of Breakpoints

  • Software breakpoint: Uses debugger-supported instruction replacement or another software mechanism.
  • Hardware breakpoint: Uses processor debug hardware.
  • Conditional breakpoint: Stops only when a specified condition is true, if supported.
  • Data watchpoint: Stops when a monitored memory location is accessed in a configured way, if supported.

4.2 Example

void ControlTask(void *pvParameters)
{
    int sensorValue;

    for (;;)
    {
        sensorValue = ReadSensor();

        /* Set breakpoint here */

        ProcessSensorValue(sensorValue);

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

At the breakpoint, inspect:

  • sensorValue.
  • Current processor registers.
  • Program counter.
  • Call stack.
  • Relevant global variables.
A breakpoint stops or slows the processor. This changes normal task scheduling and timing. Do not use breakpoint-based timing measurements as proof of real-time performance.

5. Watch Window and Variable Inspection

A watch window displays selected variables while the debugger is active.

Useful variables include:

  • Task handles.
  • Queue handles.
  • Semaphore handles.
  • Task counters.
  • Sensor values.
  • State-machine variables.
  • Error codes and function return values.

5.1 Example

volatile uint32_t sampleCount = 0;
volatile uint32_t errorCount = 0;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        if (ReadSensor() >= 0)
        {
            sampleCount++;
        }
        else
        {
            errorCount++;
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

Monitor sampleCount and errorCount to investigate sensor-reading behavior.

volatile may be appropriate for certain variables observed or modified outside ordinary program flow, but it does not provide atomicity, mutual exclusion or general inter-task synchronization.

6. Debugging Task Creation Problems

A task may fail to start because its creation failed, the scheduler has not started, or the task is not eligible to execute.

6.1 Common Causes

  • Insufficient heap for dynamic task creation.
  • Invalid task function or parameter.
  • Incorrect task priority.
  • Incorrect scheduler initialization.
  • Task created but blocked or suspended.
  • Stack allocation or configuration problem.

6.2 Debugging xTaskCreate()

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t sensorTaskHandle = NULL;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Sensor processing */
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void CreateSensorTask(void)
{
    BaseType_t result;

    result = xTaskCreate(
        SensorTask,
        "Sensor",
        256,
        NULL,
        2,
        &sensorTaskHandle
    );

    if (result != pdPASS)
    {
        /* Task creation failed */
        sensorTaskHandle = NULL;
    }
}

Check the return value and verify that the task handle is valid after successful creation.

The stack-depth argument is expressed in stack elements, not bytes. Its memory requirement depends on sizeof(StackType_t) for the selected port.

7. Debugging Task Scheduling Problems

A task may not run when expected because of priority, blocking, suspension or scheduler behavior.

7.1 Common Causes

  • A higher-priority task remains Ready.
  • The task is Blocked on a queue or semaphore.
  • The task is suspended.
  • The task has been deleted.
  • The scheduler is not running.
  • Long interrupt handlers delay task execution.
  • Scheduler suspension delays normal context switches.

7.2 Task State Inspection

Task status information can be collected using supported FreeRTOS APIs.

eTaskState state;

state = eTaskGetState(sensorTaskHandle);

Possible states include Running, Ready, Blocked and Suspended. A task-state result is a snapshot and can change immediately after it is read.

7.3 Useful Debugging Questions

  1. Is the scheduler running?
  2. Was the task created successfully?
  3. What is its priority?
  4. Is it Ready, Blocked or Suspended?
  5. Is it waiting indefinitely for an event?
  6. Is another task continuously occupying the processor?

8. Debugging Stack Overflow

Stack overflow occurs when a task uses more stack memory than allocated.

8.1 Common Causes

  • Large local arrays.
  • Deep function-call chains.
  • Recursive functions.
  • Large local structures.
  • Excessive nested function calls.
  • Unexpected interrupt-stack usage, depending on processor architecture.

8.2 Stack Monitoring

UBaseType_t remainingStack;

remainingStack =
    uxTaskGetStackHighWaterMark(sensorTaskHandle);

The returned value represents the minimum unused stack observed, measured in stack elements.

8.3 Overflow Detection Configuration

#define configCHECK_FOR_STACK_OVERFLOW  2

When the selected port supports the configured checking method, FreeRTOS can invoke the application stack-overflow hook.

void vApplicationStackOverflowHook(
    TaskHandle_t xTask,
    char *pcTaskName
)
{
    /* Record minimal diagnostic information.
       Avoid complex operations here. */

    for (;;)
    {
        /* Halt for investigation */
    }
}
Stack-overflow checking details depend on the FreeRTOS port. The hook may execute after memory corruption has occurred, so it should not perform unsafe logging or dynamic allocation.

9. Debugging Heap Allocation Problems

Dynamic allocation may fail when the selected heap allocator cannot satisfy a request.

9.1 Check Allocation Result

uint8_t *buffer;

buffer = pvPortMalloc(256);

if (buffer == NULL)
{
    /* Allocation failed */
}
else
{
    /* Use the allocated memory */

    vPortFree(buffer);
    buffer = NULL;
}

9.2 Monitor Free Heap

size_t freeHeap;
size_t minimumFreeHeap;

freeHeap = xPortGetFreeHeapSize();

minimumFreeHeap =
    xPortGetMinimumEverFreeHeapSize();

These monitoring functions are available only with supported heap implementations.

9.3 Common Causes

  • Insufficient available heap.
  • Memory leaks.
  • Fragmentation.
  • Incorrect allocation sizes.
  • Unreleased dynamically allocated objects.
  • Invalid memory ownership.

10. Debugging Queue Communication

Queues are commonly used to exchange data between FreeRTOS tasks.

10.1 Common Queue Problems

  • Queue creation failure.
  • Queue full condition.
  • Queue empty condition.
  • Incorrect item size.
  • Incorrect queue handle.
  • Unexpected timeout.
  • Incorrect pointer ownership.

10.2 Debugging Queue Send

BaseType_t result;
uint32_t sensorData = 123;

result = xQueueSend(
    sensorQueue,
    &sensorData,
    pdMS_TO_TICKS(100)
);

if (result != pdPASS)
{
    /* Send failed or timed out */
}

10.3 Debugging Queue Receive

uint32_t receivedData;
BaseType_t result;

result = xQueueReceive(
    sensorQueue,
    &receivedData,
    pdMS_TO_TICKS(100)
);

if (result == pdPASS)
{
    /* Process receivedData */
}
else
{
    /* No item received within the wait period */
}

Inspect the queue handle, item size, return value and blocking time.

11. Debugging Semaphore and Mutex Problems

Incorrect synchronization can cause tasks to block indefinitely or access shared resources unsafely.

11.1 Common Problems

  • Semaphore never given.
  • Semaphore given more times than expected.
  • Task waiting indefinitely.
  • Mutex not released.
  • Incorrect mutex ownership.
  • Deadlock caused by inconsistent lock ordering.
  • Using a mutex from an ISR.

11.2 Debugging a Mutex

if (xSemaphoreTake(
        uartMutex,
        pdMS_TO_TICKS(100)
    ) == pdPASS)
{
    /* Access shared UART resource */

    xSemaphoreGive(uartMutex);
}
else
{
    /* Record timeout or resource contention */
}
A task that successfully takes a mutex must release it according to the ownership design. Never use a mutex from an ISR; use an appropriate ISR-safe signaling mechanism instead.

12. Debugging Priority Inversion and Deadlock

12.1 Priority Inversion

Priority inversion occurs when a high-priority task is delayed because a lower-priority task holds a required resource.

Investigate:

  • Which task owns the mutex?
  • Which task is waiting?
  • What priorities are assigned?
  • Is priority inheritance supported and active?
  • How long does the owner hold the resource?

12.2 Deadlock

Deadlock occurs when tasks wait indefinitely for resources held by one another.

Debugging methods include:

  • Inspect all mutex ownership relationships.
  • Check task blocking states.
  • Review lock acquisition order.
  • Look for circular dependencies.
  • Use timeouts where appropriate as a detection or recovery measure.
Define a consistent global lock-acquisition order to reduce the risk of circular wait.

13. Assertion-Based Debugging

Assertions detect unexpected conditions during development.

FreeRTOS provides configASSERT() as a configurable assertion mechanism.

13.1 Example Configuration

#define configASSERT(x) \
    if ((x) == 0) { \
        taskDISABLE_INTERRUPTS(); \
        for (;;) { } \
    }

When the assertion condition is false, execution enters the failure path.

13.2 Application Example

void ProcessData(uint32_t *data)
{
    configASSERT(data != NULL);

    /* Process valid data */
}

Assertions help detect invalid handles, unexpected states and violated assumptions during development.

The assertion implementation must be appropriate for the target port and execution context. Avoid assuming that task-level interrupt-control macros are safe in every context.

14. Debugging Interrupt-Related Problems

Interrupt problems can affect RTOS task behavior and response time.

14.1 Common Causes

  • Interrupt source not enabled.
  • Incorrect interrupt vector or handler.
  • Peripheral interrupt flag not cleared.
  • Excessively long ISR.
  • Incorrect interrupt priority configuration.
  • Calling a blocking task API from an ISR.
  • Incorrect use of ISR-safe FreeRTOS APIs.

14.2 ISR Debugging Checklist

  1. Verify the peripheral interrupt source.
  2. Verify the interrupt controller configuration.
  3. Check the handler entry and exit.
  4. Confirm the interrupt flag is acknowledged correctly.
  5. Measure or inspect ISR execution duration.
  6. Check that the ISR uses only appropriate non-blocking APIs.
  7. Verify deferred task processing.
ISR priority rules and yield mechanisms are port-specific. Do not apply Cortex-M NVIC or BASEPRI rules to an ARM7 processor.

15. Debugging with Keil uVision Simulator

Keil uVision provides debugging facilities that can be useful for studying program execution in a supported simulator configuration.

15.1 Useful Debugging Features

  • Set breakpoints in C source code.
  • Execute code step by step.
  • Inspect local and global variables.
  • View CPU registers.
  • Inspect memory locations.
  • View disassembled instructions.
  • Inspect the call stack where debug information permits.
  • Observe program-counter changes.

15.2 Suggested Workflow

  1. Open the embedded project in Keil uVision.
  2. Build the project and check compiler errors.
  3. Enable debug information in the project settings.
  4. Select an appropriate simulator/debug target.
  5. Start the debug session.
  6. Set breakpoints in task functions and relevant kernel paths.
  7. Inspect variables and processor state.
  8. Step through the code and investigate unexpected behavior.
Keil simulator support for the selected FreeRTOS ARM7 port, timer configuration, interrupts and peripheral behavior must be verified separately. Simulator execution does not establish real hardware timing or electrical behavior.

16. Systematic Debugging Workflow

IDENTIFY THE FAILURE | v REPRODUCE THE PROBLEM | v COLLECT DEBUG INFORMATION | v CHECK TASK STATES | v CHECK STACK AND HEAP | v CHECK QUEUES / SEMAPHORES | v CHECK INTERRUPTS / TIMING | v IDENTIFY ROOT CAUSE | v APPLY CORRECTION | v RETEST AND VERIFY

Use a repeatable debugging process rather than changing several unrelated parameters at once.

20. Lesson Summary

  • RTOS debugging investigates task, memory, synchronization and timing problems.
  • Breakpoints and watch windows help inspect program execution.
  • Task creation and scheduling failures require checking handles, states and priorities.
  • Stack and heap monitoring help identify memory-related faults.
  • Queue, semaphore and mutex return values should be checked.
  • Assertions detect unexpected conditions during development.
  • Interrupt debugging requires attention to port-specific API and priority rules.
  • Trace analysis provides execution history and scheduling information.
  • Keil uVision simulation is useful for supported program-level inspection, but does not replace hardware validation.
