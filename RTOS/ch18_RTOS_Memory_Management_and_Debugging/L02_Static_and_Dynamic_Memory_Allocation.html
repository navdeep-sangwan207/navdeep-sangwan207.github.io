2. Introduction to Memory Allocation

Memory allocation is the process of reserving RAM for program variables, data structures and RTOS objects such as tasks, queues, semaphores and timers.

RTOS applications commonly use two allocation strategies:

  • Static allocation: Memory is reserved before runtime, generally through global or static objects and application-provided storage.
  • Dynamic allocation: Memory is requested at runtime from a memory allocator or heap.
MEMORY ALLOCATION | +---------+---------+ | | STATIC DYNAMIC | | Pre-reserved RAM Runtime request | | Known storage Allocator/heap | | Predictable size Allocation may fail

3. Static Memory Allocation

In static allocation, the application provides storage for an object before that object is created or used. The storage commonly resides in global or static variables.

3.1 Example in C

#include <stdint.h>

static uint8_t sensor_buffer[128];

int main(void)
{
    sensor_buffer[0] = 25;

    while (1)
    {
        /* Application processing */
    }
}

The array has a fixed size of 128 bytes. Its storage exists for the lifetime of the program.

3.2 Characteristics

  • Memory size is determined in advance.
  • No runtime heap allocation is required for the object.
  • Memory usage is easier to estimate during design.
  • There is no heap fragmentation for the statically reserved object.
  • Changing the required size may require changing the program and rebuilding it.
  • Unused reserved memory can reduce RAM available to other components.
Important: Static allocation does not mean that every object is automatically safe. The application must still provide enough memory, initialize it correctly and ensure that concurrent tasks access shared data safely.

4. Dynamic Memory Allocation

Dynamic allocation reserves memory while the program is running. The application requests a block from an allocator and receives a pointer to the allocated memory.

4.1 Standard C Example

#include <stdio.h>
#include <stdlib.h>

int main(void)
{
    int *data;

    data = malloc(10 * sizeof(int));

    if (data == NULL)
    {
        printf("Memory allocation failed\n");
        return 1;
    }

    data[0] = 100;

    printf("First value = %d\n", data[0]);

    free(data);
    data = NULL;

    return 0;
}

Expected output:

First value = 100

4.2 Characteristics

  • Memory is requested when required.
  • Object sizes can be selected at runtime.
  • Memory can be released and reused when supported by the allocator.
  • Allocation may fail when sufficient memory is unavailable.
  • Repeated allocation and release can cause fragmentation with some allocators.
  • Allocation and deallocation time may vary depending on the heap implementation.
Embedded-system caution: Never assume that a dynamic allocation request will succeed. Check the returned pointer or RTOS API status before using the object.

6. Memory Allocation in FreeRTOS

FreeRTOS supports static and dynamic creation of kernel objects, depending on the kernel version, configuration and APIs used.

6.1 FreeRTOSConfig.h Options

#define configSUPPORT_STATIC_ALLOCATION       1
#define configSUPPORT_DYNAMIC_ALLOCATION      1

These configuration options control whether the application can use the corresponding allocation methods.

ConfigurationMeaning
configSUPPORT_STATIC_ALLOCATIONEnables static object creation APIs.
configSUPPORT_DYNAMIC_ALLOCATIONEnables dynamic object creation APIs.

Both methods can be enabled in the same application. This allows a hybrid memory-allocation strategy.

The exact configuration requirements and available APIs depend on the FreeRTOS release and port. Use the matching release documentation and configuration template.

7. Dynamic Task Creation: xTaskCreate()

xTaskCreate() creates a task using dynamically allocated memory for its task control block and stack.

7.1 Function Syntax

BaseType_t xTaskCreate(
    TaskFunction_t pvTaskCode,
    const char * const pcName,
    configSTACK_DEPTH_TYPE usStackDepth,
    void *pvParameters,
    UBaseType_t uxPriority,
    TaskHandle_t *pxCreatedTask
);

7.2 Example

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read and process sensor data */
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    BaseType_t result;

    result = xTaskCreate(
        SensorTask,
        "Sensor",
        256,
        NULL,
        2,
        NULL
    );

    if (result != pdPASS)
    {
        /* Handle task creation failure */
        for (;;);
    }

    vTaskStartScheduler();

    for (;;);
}

Explanation:

  • SensorTask is the task function.
  • "Sensor" is the task name.
  • 256 is the stack depth in stack elements, not bytes.
  • NULL means no task parameter is supplied.
  • 2 is the task priority.
  • The final NULL means the application does not request the created task handle.
  • pdPASS indicates successful task creation.
The example is generic FreeRTOS code. It requires a compatible processor port, compiler integration, startup code and hardware or simulator support before it can run on a target.

8. Static Task Creation: xTaskCreateStatic()

xTaskCreateStatic() creates a task using memory supplied by the application. The application provides storage for both the task control block and task stack.

8.1 Function Syntax

TaskHandle_t xTaskCreateStatic(
    TaskFunction_t pvTaskCode,
    const char * const pcName,
    configSTACK_DEPTH_TYPE uxStackDepth,
    void *pvParameters,
    UBaseType_t uxPriority,
    StackType_t *puxStackBuffer,
    StaticTask_t *pxTaskBuffer
);

8.2 Example

#include "FreeRTOS.h"
#include "task.h"

#define SENSOR_STACK_SIZE 256

static StackType_t sensorStack[SENSOR_STACK_SIZE];
static StaticTask_t sensorTaskControlBlock;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read and process sensor data */
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    TaskHandle_t sensorHandle;

    sensorHandle = xTaskCreateStatic(
        SensorTask,
        "Sensor",
        SENSOR_STACK_SIZE,
        NULL,
        2,
        sensorStack,
        &sensorTaskControlBlock
    );

    if (sensorHandle == NULL)
    {
        /* Handle task creation failure */
        for (;;);
    }

    vTaskStartScheduler();

    for (;;);
}

8.3 Explanation

  • sensorStack supplies the task's stack storage.
  • sensorTaskControlBlock supplies storage for the task control block.
  • SENSOR_STACK_SIZE specifies the number of stack elements.
  • The returned task handle identifies the created task.
  • The supplied storage must remain valid for the lifetime of the task.
Design rule: Do not provide task stack or control-block storage using local automatic variables in a function that returns. The storage must remain valid while the RTOS object exists.

9. Static and Dynamic Queue Creation

FreeRTOS also supports both allocation methods for queues.

9.1 Dynamic Queue Creation

#include "FreeRTOS.h"
#include "queue.h"

QueueHandle_t sensorQueue;

void CreateSensorQueue(void)
{
    sensorQueue = xQueueCreate(
        5,
        sizeof(int)
    );

    if (sensorQueue == NULL)
    {
        /* Handle allocation failure */
    }
}

The queue storage and queue control structure are obtained dynamically.

9.2 Static Queue Creation

#include "FreeRTOS.h"
#include "queue.h"

#define QUEUE_LENGTH 5

static StaticQueue_t queueControlBlock;

static uint8_t queueStorage[
    QUEUE_LENGTH * sizeof(int)
];

QueueHandle_t sensorQueue;

void CreateSensorQueue(void)
{
    sensorQueue = xQueueCreateStatic(
        QUEUE_LENGTH,
        sizeof(int),
        queueStorage,
        &queueControlBlock
    );

    if (sensorQueue == NULL)
    {
        /* Handle creation failure */
    }
}

In this example, the application supplies both the queue's item storage and its control-block storage.

The supplied queue storage must be correctly sized and suitably aligned for the target and API requirements. Static queue APIs and storage types should be checked against the selected FreeRTOS release.

10. Static Creation APIs for Other FreeRTOS Objects

Static allocation is also available for several other kernel objects in FreeRTOS releases that support the corresponding APIs.

ObjectDynamic APIStatic API
TaskxTaskCreate()xTaskCreateStatic()
QueuexQueueCreate()xQueueCreateStatic()

MutexxSemaphoreCreateMutex()xSemaphoreCreateMutexStatic()

Software timerxTimerCreate()xTimerCreateStatic()

Static creation APIs use application-provided storage types such as:

  • StaticTask_t
  • StackType_t
  • StaticQueue_t
  • StaticSemaphore_t
  • StaticEventGroup_t
  • StaticTimer_t

Not every type or API is required for every object. For example, a static task requires both a stack buffer and a task control-block buffer. Check the relevant API declaration for the exact storage requirements.

11. FreeRTOS Dynamic Memory APIs

FreeRTOS provides allocator functions for applications and kernel components:

FunctionPurpose
pvPortMalloc()Requests a memory block from the configured FreeRTOS heap.
vPortFree()Releases a previously allocated block where supported.

11.1 Example

#include "FreeRTOS.h"

void AllocateBuffer(void)
{
    uint8_t *buffer;

    buffer = pvPortMalloc(128);

    if (buffer == NULL)
    {
        /* Handle allocation failure */
        return;
    }

    buffer[0] = 0x55;

    /* Use the buffer */

    vPortFree(buffer);
    buffer = NULL;
}

pvPortMalloc() and vPortFree() use the configured FreeRTOS heap implementation. They are not simply interchangeable with the standard C library's malloc() and free().

Do not release memory while another task, ISR or peripheral operation still uses it. Coordinate buffer ownership before freeing dynamically allocated storage.

12. Hybrid Memory Allocation

A hybrid approach combines static and dynamic allocation in one RTOS application.

For example:

  • Use static allocation for essential control tasks.
  • Use static buffers for critical communication paths.
  • Use dynamic allocation for optional objects created according to operating conditions.
  • Reserve and monitor heap capacity for runtime allocations.
HYBRID RTOS APPLICATION | +--------+--------+ | | STATIC OBJECTS DYNAMIC OBJECTS | | Control tasks Optional tasks Critical buffers Variable buffers Fixed queues Runtime objects

The choice should be based on timing requirements, RAM capacity, failure handling and application lifecycle.

13. Memory Calculation Example

Assume a FreeRTOS task uses a stack depth of 256 elements and the target's StackType_t is 4 bytes.

Stack memory required:

Stack memory = Stack depth × Size of StackType_t

             = 256 × 4

             = 1024 bytes

             = 1 KB

If three tasks each use a stack depth of 256 elements:

Total task stack memory
= 3 × 1024
= 3072 bytes
= 3 KB

This calculation covers only the task stacks. It does not include task control blocks, queues, other kernel objects, application variables or allocator overhead.

Always calculate stack memory using the actual target's sizeof(StackType_t). Stack depth is expressed in stack elements, not universally in bytes.

14. Common Memory Allocation Problems

15. Choosing an Allocation Strategy

Application requirementSuggested approach
Fixed number of critical tasksStatic task creation
Known queue size and lifetimeStatic queue creation
Optional objects created at runtimeDynamic allocation with failure handling
Strict memory predictabilityPrefer static allocation where practical
Variable workload and object sizesEvaluate dynamic allocation and allocator behavior
High-reliability embedded systemUse a documented memory budget, controlled allocation policy and runtime monitoring

Static allocation is often preferred for essential real-time objects because memory requirements can be determined in advance. Dynamic allocation remains useful when runtime flexibility is genuinely required.

18. Lesson Summary

  • Static allocation reserves application-provided storage in advance.
  • Dynamic allocation requests memory at runtime from an allocator.
  • FreeRTOS supports both strategies through separate object-creation APIs.
  • xTaskCreateStatic() requires application-provided task stack and control-block storage.
  • xQueueCreateStatic() requires application-provided queue storage and control-block storage.
  • Static allocation improves memory predictability but requires careful RAM budgeting.
  • Dynamic allocation offers flexibility but requires failure handling and memory-lifetime management.
  • A hybrid strategy can combine predictable critical objects with runtime flexibility.
