1. Learning Objectives

After completing this lesson, you will be able to:

  • Explain the purpose of the FreeRTOS heap.
  • Understand heap_1, heap_2, heap_3, heap_4 and heap_5.
  • Compare allocation and deallocation behavior.
  • Understand memory fragmentation and coalescing.
  • Use FreeRTOS heap monitoring functions where supported.
  • Select an appropriate heap implementation for an embedded application.

2. What Is the FreeRTOS Heap?

The FreeRTOS heap is a memory region used by the kernel's dynamic memory allocator. It provides memory for dynamically created RTOS objects and application allocations made through FreeRTOS memory functions.

Examples of objects that may require dynamic memory include:

  • Tasks and their stacks.
  • Queues.
  • Semaphores and mutexes.
  • Event groups.
  • Software timers.
  • Application buffers requested through pvPortMalloc().
FREE RTOS APPLICATION | KERNEL OBJECTS | DYNAMIC ALLOCATION | FREERTOS HEAP | +------------+------------+ | | | TASKS QUEUES TIMERS | | | +------------+------------+

FreeRTOS provides five commonly distributed heap implementations:

  1. heap_1
  2. heap_2
  3. heap_3
  4. heap_4
  5. heap_5
These are alternative allocator implementations. A project normally includes one selected heap implementation, not all five simultaneously. Exact availability and behavior should be checked against the FreeRTOS release being used.

3. Heap_1 – Allocation Without Freeing

heap_1.c implements a simple allocation strategy. It allocates memory from its configured heap region but does not support releasing allocated blocks using vPortFree().

3.1 Characteristics

  • Supports allocation through pvPortMalloc().
  • Does not support deallocation.
  • Previously allocated memory is not returned to the available heap.
  • Simple allocation behavior.
  • Useful when all required objects are created during initialization and remain for the system lifetime.

3.2 Memory Operation

INITIAL HEAP +--------------------------------------+ | FREE MEMORY | +--------------------------------------+ AFTER ALLOCATION 1 +------------+-------------------------+ | ALLOC 1 | FREE MEMORY | +------------+-------------------------+ AFTER ALLOCATION 2 +------------+------------+------------+ | ALLOC 1 | ALLOC 2 | FREE | +------------+------------+------------+ No block is returned to the free region.

3.3 Example

#include "FreeRTOS.h"

void InitializeApplication(void)
{
    uint8_t *buffer1;
    uint8_t *buffer2;

    buffer1 = pvPortMalloc(100);
    buffer2 = pvPortMalloc(200);

    if ((buffer1 == NULL) || (buffer2 == NULL))
    {
        /* Handle allocation failure */
        for (;;);
    }

    /* Use the buffers for long-lived objects */
}
Do not design an application around repeatedly creating and deleting dynamic objects when using heap_1. Released object memory cannot be reused through vPortFree() because this implementation does not provide deallocation.

4. Heap_2 – Allocation and Freeing Without Coalescing

heap_2.c supports allocation and deallocation. It maintains free blocks and selects a suitable block for an allocation request.

4.1 Characteristics

  • Supports pvPortMalloc().
  • Supports vPortFree().
  • Free blocks can be reused.
  • Does not coalesce adjacent free blocks.
  • Can suffer from external fragmentation.

4.2 Understanding Fragmentation

Consider a heap containing three allocated blocks:

+----------+----------+----------+----------+ | BLOCK A | BLOCK B | BLOCK C | FREE | +----------+----------+----------+----------+ After freeing A and C: +----------+----------+----------+----------+ | FREE | BLOCK B | FREE | FREE | +----------+----------+----------+----------+

Suppose a request needs a block larger than either of the two separated free regions. The request may fail even if the total free memory is sufficient.

The reason is that the free regions are not merged into one larger contiguous block.

Historical note: heap_2 is retained for compatibility and educational comparison. For many new applications requiring reusable variable-sized blocks, heap_4 or another deliberately selected allocator is generally a better starting point.

5. Heap_3 – Wrapper Around C Library Allocation

heap_3.c delegates allocation and deallocation to the C library's malloc() and free() functions.

5.1 Characteristics

  • Uses the compiler or C library memory allocator.
  • pvPortMalloc() wraps malloc().
  • vPortFree() wraps free().
  • Allocator behavior depends on the C library and target integration.
  • Thread-safety and interrupt-safety depend on the library and port integration.

5.2 Conceptual Implementation

void *pvPortMalloc(size_t xSize)
{
    void *pvReturn;

    /* Heap_3 conceptually protects the C allocator
       with the required FreeRTOS critical-section
       mechanism for the selected port. */

    pvReturn = malloc(xSize);

    return pvReturn;
}

void vPortFree(void *pv)
{
    if (pv != NULL)
    {
        free(pv);
    }
}

This is an explanatory illustration, not a replacement for the actual FreeRTOS heap_3.c source.

5.3 Important Considerations

  • The available heap capacity is controlled by the C runtime and linker configuration, not necessarily by configTOTAL_HEAP_SIZE.
  • Memory availability depends on the target's C library and runtime setup.
  • Allocation timing depends on the C library allocator.
  • Reentrancy and synchronization must be verified for the selected toolchain.
Do not assume that wrapping malloc makes every C library allocator safe in all contexts. Never call ordinary allocation functions from an ISR unless the complete implementation explicitly supports that usage.

6. Heap_4 – Allocation with Coalescing

heap_4.c supports allocation and deallocation and can combine adjacent free blocks into larger blocks. This process is called coalescing.

6.1 Characteristics

  • Supports pvPortMalloc().
  • Supports vPortFree().
  • Uses a free-list-based allocation approach.
  • Coalesces adjacent free blocks.
  • Uses a configured heap region.
  • Can still experience fragmentation when free blocks are separated by allocated blocks.

6.2 Coalescing Example

Before freeing adjacent blocks:

+----------+----------+----------+----------+ | BLOCK A | BLOCK B | BLOCK C | FREE | +----------+----------+----------+----------+

After freeing blocks A and B, the allocator can merge the adjacent free regions:

+---------------------+----------+----------+ | FREE REGION | BLOCK C | FREE | +---------------------+----------+----------+

The merged region can satisfy a larger allocation request than either original block could satisfy alone.

6.3 Configuration

#define configTOTAL_HEAP_SIZE    (20 * 1024)

For heap_4, configTOTAL_HEAP_SIZE determines the configured heap-array size in bytes in the standard implementation.

6.4 Example

#include "FreeRTOS.h"

void MemoryExample(void)
{
    uint8_t *buffer;

    buffer = pvPortMalloc(256);

    if (buffer == NULL)
    {
        /* Allocation failed */
        return;
    }

    buffer[0] = 0xAA;

    /* Finish using the buffer */

    vPortFree(buffer);
    buffer = NULL;
}
heap_4 is a common choice when an application needs dynamic allocation and reusable memory blocks. Nevertheless, it does not guarantee fixed allocation time or eliminate all fragmentation.

7. Heap_5 – Multiple Non-Contiguous Memory Regions

heap_5.c provides allocation and deallocation similar to heap_4, but it can manage multiple separate memory regions.

This is useful when a microcontroller or processor has multiple RAM banks that are not physically contiguous.

7.1 Characteristics

  • Supports dynamic allocation and deallocation.
  • Supports multiple non-contiguous heap regions.
  • Coalesces adjacent free blocks within a region.
  • Does not merge blocks across physically separate regions.
  • Requires the application to define the memory regions correctly.

7.2 Memory Layout

MICROCONTROLLER MEMORY +-------------------------------+ | RAM REGION 1 | | 0x40000000 - 0x40001FFF | +-------------------------------+ GAP / OTHER MEMORY +-------------------------------+ | RAM REGION 2 | | 0x40010000 - 0x40011FFF | +-------------------------------+ SEPARATE REGIONS | v FREERTOS HEAP_5 manages both regions

7.3 Conceptual Configuration

#include "FreeRTOS.h"
#include "portable.h"

static uint8_t ramRegion1[4096];
static uint8_t ramRegion2[8192];

static const HeapRegion_t heapRegions[] =
{
    {
        ramRegion1,
        sizeof(ramRegion1)
    },
    {
        ramRegion2,
        sizeof(ramRegion2)
    },
    {
        NULL,
        0
    }
};

void InitializeHeap(void)
{
    vPortDefineHeapRegions(heapRegions);
}

vPortDefineHeapRegions() initializes the heap_5 regions. It must be called before any FreeRTOS object or application allocation uses the heap.

This example illustrates the API structure. Real heap regions must use valid memory addresses, correct alignment and memory that is reserved for the allocator. Do not use ordinary local arrays as a substitute for correctly mapped target RAM regions in a production design.

9. FreeRTOS Heap Configuration

The FreeRTOS configuration file and heap implementation must be consistent with the selected memory strategy.

9.1 Important Configuration Options

#define configSUPPORT_DYNAMIC_ALLOCATION    1
#define configSUPPORT_STATIC_ALLOCATION     1

#define configTOTAL_HEAP_SIZE               (20 * 1024)

These settings have different purposes:

  • configSUPPORT_DYNAMIC_ALLOCATION enables dynamic creation APIs.
  • configSUPPORT_STATIC_ALLOCATION enables static creation APIs.
  • configTOTAL_HEAP_SIZE is used by heap implementations that define a heap array using this setting, such as the standard heap_1, heap_2 and heap_4 implementations.
Do not assume that configTOTAL_HEAP_SIZE controls heap_3 or the memory regions supplied to heap_5. Each implementation has its own memory-source configuration.

10. Monitoring Heap Usage

FreeRTOS provides heap-monitoring functions in supported heap implementations.

FunctionPurpose
xPortGetFreeHeapSize()Returns the current free heap size in bytes.
xPortGetMinimumEverFreeHeapSize()Returns the minimum free heap size recorded since initialization.
vPortGetHeapStats()Provides detailed heap statistics where implemented and available.

10.1 Example

#include "FreeRTOS.h"
#include "task.h"

void HeapMonitorTask(void *pvParameters)
{
    size_t currentFree;
    size_t minimumFree;

    for (;;)
    {
        currentFree = xPortGetFreeHeapSize();

        minimumFree =
            xPortGetMinimumEverFreeHeapSize();

        /* Send values to a debug console or log */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

The example assumes the selected heap implementation provides these functions.

A free-heap measurement does not prove that a future allocation of a particular size will succeed. Fragmentation, alignment and allocator metadata affect whether a suitable block is available.

11. Allocation Failure Handling

Every dynamic allocation must have a defined failure path.

11.1 Application-Level Checking

void *buffer;

buffer = pvPortMalloc(512);

if (buffer == NULL)
{
    /* Log the failure */
    /* Enter safe state or use fallback storage */
}
else
{
    /* Use allocated memory */
}

11.2 Malloc Failed Hook

FreeRTOS can optionally call an application-defined allocation-failure hook when a kernel allocation fails.

#define configUSE_MALLOC_FAILED_HOOK    1
void vApplicationMallocFailedHook(void)
{
    /* Record diagnostic information */

    taskDISABLE_INTERRUPTS();

    for (;;)
    {
        /* Enter application-defined failure state */
    }
}

The hook must be implemented according to the selected port and project configuration. It should not attempt unsafe operations such as further heap allocation during a memory-exhaustion condition.

12. Heap Fragmentation

Heap fragmentation occurs when free memory is divided into separate blocks. The total free memory may be sufficient, but no individual free block may be large enough for a request.

12.1 External Fragmentation

+------+----------+------+----------+------+ | FREE | ALLOCATED| FREE | ALLOCATED| FREE | +------+----------+------+----------+------+ Total free memory = Sum of separated free blocks Largest available block may be much smaller than total free memory.

12.2 Internal Fragmentation

Internal fragmentation occurs when an allocated block contains unused space because of alignment, allocator metadata or block-size rounding.

12.3 Prevention and Control

  • Prefer static allocation for long-lived critical objects when practical.
  • Avoid unnecessary repeated allocation and release.
  • Use fixed-size memory pools for predictable repeated-size buffers when suitable.
  • Monitor free heap and minimum-ever free heap.
  • Test allocation patterns under worst-case operating conditions.
  • Define ownership and release rules for dynamically allocated buffers.

16. Lesson Summary

  • FreeRTOS provides five commonly distributed heap implementations.
  • heap_1 supports allocation without freeing.
  • heap_2 supports allocation and freeing but does not coalesce adjacent free blocks.
  • heap_3 wraps the C library allocator.
  • heap_4 supports freeing and coalescing within its configured region.
  • heap_5 supports multiple non-contiguous memory regions and coalesces within each region.
  • Heap-monitoring functions help assess memory availability and usage history.
  • Dynamic allocation requires failure handling, memory ownership and lifetime management.
  • The allocator must be selected according to the target's memory map and real-time requirements.
