2. Memory Analysis Fundamentals

An RTOS application uses several types of memory during execution.

Memory RegionPurpose
Flash / ROMStores program instructions and constant data.
Static RAMStores global variables, static objects and other runtime data.
HeapProvides dynamically allocated memory.
Task StackStores function-call data, local variables and execution context.
Interrupt StackStores interrupt-related execution data where the architecture uses a separate stack.

The exact memory layout depends on the processor architecture, compiler, linker script and RTOS port.

3. Exercise 1 – Task Stack Size Calculation

Problem: A FreeRTOS task is created with a stack depth of 256 elements. Assume the selected port uses a 4-byte StackType_t.

Solution

Stack Depth = 256 elements

Size of StackType_t = 4 bytes

Stack Memory = 256 × 4
             = 1024 bytes
             = 1 KB

Answer: The task stack allocation is 1024 bytes.

The stack-depth parameter in FreeRTOS task-creation APIs is expressed in stack elements, not universally in bytes. Always check the selected port's StackType_t size.

4. Exercise 2 – Total Task Stack Memory

Problem: An application creates four tasks with the following stack depths. Assume each stack element is 4 bytes.

TaskStack Depth
SensorTask256
ControlTask512
CommTask384
MonitorTask128

Solution

SensorTask  = 256 × 4 = 1024 bytes
ControlTask = 512 × 4 = 2048 bytes
CommTask    = 384 × 4 = 1536 bytes
MonitorTask = 128 × 4 =  512 bytes

Total = 1024 + 2048 + 1536 + 512
      = 5120 bytes
      = 5 KB

Answer: The four task stacks require 5 KB in total.

This calculation excludes TCBs, queue storage, other kernel objects and application memory.

5. Exercise 3 – Stack High-Water-Mark Analysis

Problem: A task has a stack depth of 300 elements. Its measured high-water mark is 75 elements. Assume each stack element is 4 bytes.

Solution

Allocated Stack = 300 elements

Minimum Unused Stack = 75 elements

Maximum Observed Stack Usage =
    300 - 75
  = 225 elements

Observed Usage in Bytes =
    225 × 4
  = 900 bytes

Minimum Unused Stack in Bytes =
    75 × 4
  = 300 bytes

Answer:

  • Maximum observed stack usage: 900 bytes.
  • Minimum observed unused stack: 300 bytes.
A high-water mark reflects execution paths actually observed. It does not prove that untested paths, exceptional conditions or future workloads cannot use more stack.

6. Exercise 4 – Heap Utilization Calculation

Problem: Assume a heap implementation has a known configured capacity of 32 KB. The reported free heap is 12 KB.

Solution

Total Heap = 32 KB
Free Heap  = 12 KB

Used Heap = 32 - 12
          = 20 KB

Utilization = (20 / 32) × 100
            = 62.5%

Answer:

  • Used heap: 20 KB.
  • Free heap: 12 KB.
  • Heap utilization: 62.5%.
This calculation assumes the allocator's free-space measurement is comparable to the stated heap capacity. Do not treat it as a universal calculation for every heap implementation.

7. Exercise 5 – Minimum-Ever Free Heap

Problem: During execution, the following free-heap measurements are recorded:

MeasurementFree Heap
Initial18 KB
After Task Creation14 KB
After Queue Creation11 KB
After Temporary Allocation7 KB
After Memory Release12 KB

Solution

Minimum Free Heap =
    minimum(18, 14, 11, 7, 12)

Minimum Free Heap = 7 KB

Answer: The minimum-ever free heap observed is 7 KB.

The current free heap is 12 KB, but the system previously reached a lower value of 7 KB.

8. Exercise 6 – External Fragmentation

Problem: A heap contains three separate free blocks:

  • Block A = 128 bytes.
  • Block B = 256 bytes.
  • Block C = 512 bytes.

Solution

Total Free Memory = 128 + 256 + 512
                  = 896 bytes

Largest Free Block = 512 bytes

Suppose the application requests a contiguous block of 600 bytes.

Requested Size = 600 bytes
Largest Block  = 512 bytes

600 > 512

Allocation cannot be satisfied
by any individual free block.

Answer: The allocation may fail even though total free memory is 896 bytes.

9. Exercise 7 – Internal Fragmentation

Problem: An allocator rounds a 21-byte request up to a 24-byte allocation unit.

Solution

Requested Memory = 21 bytes
Allocated Memory = 24 bytes

Internal Fragmentation =
    24 - 21
  = 3 bytes

Answer: Internal fragmentation is 3 bytes.

This is an illustrative allocation-unit example. Actual allocator alignment and block overhead depend on the implementation.

10. Exercise 8 – Identify a Memory Leak

Problem: Study the following code.

void ProcessData(void)
{
    uint8_t *buffer;

    buffer = pvPortMalloc(128);

    if (buffer != NULL)
    {
        buffer[0] = 0x55;
    }
}

Question: What is the problem?

Solution

The allocated memory is never released. When the function returns, the local pointer disappears, but the allocated heap block remains allocated.

Corrected Code

void ProcessData(void)
{
    uint8_t *buffer;

    buffer = pvPortMalloc(128);

    if (buffer != NULL)
    {
        buffer[0] = 0x55;

        /* Complete all buffer operations */

        vPortFree(buffer);
        buffer = NULL;
    }
}

Answer: The original code contains a memory leak because it does not release the allocated block.

11. Exercise 9 – Detecting an Invalid Free

Problem: Analyze the following code.

uint8_t *buffer;

buffer = pvPortMalloc(100);

if (buffer != NULL)
{
    vPortFree(buffer);

    vPortFree(buffer);
}

Question: Why is this code unsafe?

Solution

The same allocation is released twice. This is a double-free error and can corrupt allocator data structures or cause unpredictable behavior.

Corrected Code

uint8_t *buffer;

buffer = pvPortMalloc(100);

if (buffer != NULL)
{
    vPortFree(buffer);
    buffer = NULL;
}
Setting this pointer to NULL helps prevent reuse through this particular pointer, but it does not update other aliases that may still point to the released block.

Dynamic Allocation

BaseType_t result;

    "Sensor",

    "Sensor",
    256,
    NULL,
    2,

14. Exercise 12 – Run-Time Statistics

Problem: An RTOS application reports the following accumulated run-time values.

TaskRun Time
SensorTask2500
ControlTask5000
CommTask1500
Idle1000

Solution

Total = 2500 + 5000 + 1500 + 1000
      = 10000

SensorTask = (2500 / 10000) × 100
           = 25%

ControlTask = (5000 / 10000) × 100
            = 50%

CommTask = (1500 / 10000) × 100
         = 15%

Idle = (1000 / 10000) × 100
     = 10%

Answer: ControlTask has the highest measured execution-time share at 50%.

15. Exercise 13 – Diagnose a Stack Overflow

Problem: A task repeatedly crashes when processing large data packets.

Investigation reveals:

  • The task has a small stack allocation.
  • The task uses large local arrays.
  • The task calls several nested functions.
  • The stack high-water mark is very low.

Possible Root Causes

  1. Large local arrays consume significant stack memory.
  2. Nested function calls increase stack usage.
  3. The allocated stack may be insufficient for worst-case execution paths.

Corrective Actions

  • Increase stack allocation based on measured and analyzed requirements.
  • Move large buffers to suitable static or managed memory.
  • Reduce unnecessary local variables.
  • Review function-call depth.
  • Enable supported stack-overflow checks.
  • Test error-handling and maximum-size packet paths.

16. Exercise 14 – Memory Monitoring Program

Objective: Monitor current and minimum-ever free heap in a FreeRTOS application.

Program

#include "FreeRTOS.h"
#include "task.h"

void MemoryMonitorTask(void *pvParameters)
{
    size_t freeHeap;
    size_t minimumFreeHeap;

    for (;;)
    {
        freeHeap = xPortGetFreeHeapSize();

        minimumFreeHeap =
            xPortGetMinimumEverFreeHeapSize();

        /*
          Inspect these variables in the debugger
          or report them using a suitable diagnostic
          interface.
        */

        vTaskDelay(pdMS_TO_TICKS(2000));
    }
}

Expected Result

  • freeHeap contains the current free heap measurement.
  • minimumFreeHeap contains the minimum free heap observed since heap initialization.
  • The monitoring task repeats the measurement every two seconds.
The two monitoring functions are not supported by every allocator. Confirm the selected heap implementation provides them before compiling.

18. Exercise 16 – Memory Ownership Analysis

Problem: A producer task allocates a buffer and sends its pointer through a queue.

uint8_t *buffer;

buffer = pvPortMalloc(128);

if (buffer != NULL)
{
    xQueueSend(bufferQueue,
               &buffer,
               portMAX_DELAY);
}

Question: What must the application define?

Solution

A queue containing pointers copies the pointer value, not the data stored at that address. The application therefore needs an explicit ownership and lifetime protocol.

A safe design should define:

  • Which task owns the buffer before queue submission.
  • Which task owns the buffer after successful submission.
  • What happens if queue submission fails.
  • Which task releases the buffer.
  • How the application prevents access after release.

Illustrative Corrected Pattern

uint8_t *buffer;

buffer = pvPortMalloc(128);

if (buffer != NULL)
{
    if (xQueueSend(bufferQueue,
                   &buffer,
                   pdMS_TO_TICKS(100)) != pdPASS)
    {
        /* Transfer did not occur.
           Producer still owns the buffer. */

        vPortFree(buffer);
    }
    else
    {
        /* Ownership transferred according
           to the application's queue protocol. */
        buffer = NULL;
    }
}
The consumer must release the buffer when processing is complete, or return it to a defined pool. A queue operation alone does not manage the pointed-to object's lifetime.
