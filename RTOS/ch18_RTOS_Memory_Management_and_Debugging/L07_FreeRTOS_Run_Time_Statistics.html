2. What Are Run-Time Statistics?

Run-time statistics provide information about how much processor time individual tasks have consumed while the FreeRTOS scheduler is running.

They help developers understand:

  • Which task consumes the most CPU time.
  • How processor time is distributed among tasks.
  • Whether a task is consuming unexpectedly high CPU time.
  • How application workload changes over time.
  • Whether CPU capacity is being used efficiently.
PROCESSOR TIME | +-----------+-----------+ | | | Task A Task B Task C | | | 40% 35% 25% Illustrative CPU distribution
Run-time statistics measure observed execution time. They do not, by themselves, prove that all real-time deadlines will be met.

3. Task Execution-Time Measurement

FreeRTOS can accumulate the amount of time each task spends in the Running state.

The measurement mechanism uses a dedicated run-time counter that should have a higher resolution than the normal RTOS tick counter.

3.1 RTOS Tick Counter vs Run-Time Counter

RTOS Tick CounterRun-Time Counter
Used for task delays and scheduling time.Used to measure task execution time.
Usually driven by a periodic tick interrupt.Can be driven by a faster hardware timer or another suitable counter.
Resolution depends on tick frequency.Resolution depends on the configured run-time counter.
Used by APIs such as vTaskDelay().Used for performance measurement and CPU-time statistics.

3.2 Example

Assume a run-time counter increments once every microsecond.

Start Counter = 1000
End Counter   = 7500

Execution Time = 7500 - 1000
               = 6500 microseconds
               = 6.5 milliseconds

4. Configuring Run-Time Statistics

Run-time statistics require configuration in FreeRTOSConfig.h and application-specific counter functions.

4.1 Enable Run-Time Statistics

#define configGENERATE_RUN_TIME_STATS  1

4.2 Provide a Run-Time Counter

The application must provide a counter that FreeRTOS can read. A hardware timer, free-running counter or another suitable source may be used.

/* Example configuration in FreeRTOSConfig.h */

#define configGENERATE_RUN_TIME_STATS  1

#define portCONFIGURE_TIMER_FOR_RUN_TIME_STATS() \
        ConfigureRunTimeCounter()

#define portGET_RUN_TIME_COUNTER_VALUE() \
        ReadRunTimeCounter()

The application must implement the functions used by these macros:

void ConfigureRunTimeCounter(void)
{
    /* Configure a suitable free-running
       hardware timer or counter. */
}

uint32_t ReadRunTimeCounter(void)
{
    /* Return the current counter value. */

    return 0;
}
The functions above are placeholders, not a working hardware driver. Replace them with code for the selected processor, timer peripheral and compiler. The counter must have suitable resolution and a defined overflow-handling strategy.

4.3 Required Considerations

  • The counter should advance independently of task execution.
  • Its resolution should be sufficiently fine for the application.
  • Reading the counter should be safe and efficient.
  • Counter wraparound must be considered.
  • Timer configuration must not conflict with the RTOS tick source or other peripherals.

5. How FreeRTOS Collects Run-Time Statistics

When the scheduler changes the Running task, FreeRTOS can read the run-time counter and account for the elapsed time against the task that was running.

TASK A IS RUNNING | Read run-time counter | Scheduler switches task | Calculate elapsed time | Add time to Task A | TASK B STARTS RUNNING | Repeat measurement

The accumulated value is associated with each task's run-time statistics information.

For example:

TaskAccumulated Run Time
Task A4000 units
Task B3000 units
Task C3000 units
Total10000 units

6. CPU Utilization Calculation

CPU utilization represents the proportion of measured processor time consumed by a task or group of tasks during a measurement interval.

6.1 Formula

Task CPU Utilization (%) =
    (Task Run Time / Total Measured Run Time) × 100

6.2 Numerical Example

Assume the measured run-time statistics are:

TaskRun Time
Task A4000 units
Task B3000 units
Task C2000 units
Idle Task1000 units
Total10000 units
Task A = (4000 / 10000) × 100 = 40%

Task B = (3000 / 10000) × 100 = 30%

Task C = (2000 / 10000) × 100 = 20%

Idle   = (1000 / 10000) × 100 = 10%

Total measured time is distributed as follows:

  • Task A: 40%
  • Task B: 30%
  • Task C: 20%
  • Idle task: 10%

7. Idle Task and CPU Usage

The FreeRTOS Idle task runs when no application task is Ready to execute at the currently available priority levels.

Its run-time percentage can provide an estimate of how much measured processor time was spent idle.

Estimated Busy CPU (%) =
    100 - Idle Task Percentage

Example:

Idle Task = 15%

Estimated Busy CPU = 100 - 15
                   = 85%
This interpretation assumes the measured task times account for the relevant processor execution intervals. Interrupt execution and measurement overhead may not be attributed to application tasks in the same way, depending on the port and counter implementation.

8. uxTaskGetSystemState()

uxTaskGetSystemState() obtains task status information, including accumulated run-time counters when run-time statistics are enabled.

8.1 Function Prototype

UBaseType_t uxTaskGetSystemState(
    TaskStatus_t * const pxTaskStatusArray,
    UBaseType_t uxArraySize,
    configRUN_TIME_COUNTER_TYPE * const pulTotalRunTime
);

8.2 Parameters

ParameterDescription
pxTaskStatusArrayArray where task status information is stored.
uxArraySizeNumber of entries available in the array.
pulTotalRunTimePointer to receive the total run-time counter value.

8.3 Return Value

The function returns the number of task-status entries written to the supplied array.

8.4 Example

#include "FreeRTOS.h"
#include "task.h"

#define MAX_TASKS 10

static TaskStatus_t taskStatus[MAX_TASKS];

void CollectTaskStatistics(void)
{
    UBaseType_t taskCount;
    configRUN_TIME_COUNTER_TYPE totalRunTime = 0;

    taskCount = uxTaskGetSystemState(
        taskStatus,
        MAX_TASKS,
        &totalRunTime
    );

    /* Inspect taskStatus entries and
       totalRunTime in the debugger. */
}
This API requires the relevant task-status and run-time-statistics configuration. The array must be large enough for the task population. Check the return count and do not assume that every task was captured if the array is too small.

9. TaskStatus_t Structure

Each task entry contains information about a task at the time the status information is collected.

Common fields include:

FieldDescription
xHandleTask handle.
pcTaskNameTask name.
xTaskNumberTask identification number.
eCurrentStateCurrent task state.
uxCurrentPriorityCurrent task priority.
usStackHighWaterMarkMinimum unused stack observed, in stack elements.
ulRunTimeCounterAccumulated run-time counter value.

Structure members and their exact types can vary with FreeRTOS version and configuration.

10. vTaskGetRunTimeStats()

vTaskGetRunTimeStats() formats task run-time statistics into a text buffer.

10.1 Function Prototype

void vTaskGetRunTimeStats(
    char *pcWriteBuffer
);

10.2 Example

#include "FreeRTOS.h"
#include "task.h"

#define STATS_BUFFER_SIZE 512

static char statsBuffer[STATS_BUFFER_SIZE];

void GenerateRunTimeReport(void)
{
    vTaskGetRunTimeStats(statsBuffer);

    /* Send statsBuffer to a suitable
       diagnostic output interface. */
}

A typical formatted report may look like this:

Task          Abs Time       %
--------------------------------
SensorTask    4000           40%
CommTask      3000           30%
ControlTask   2000           20%
IDLE          1000           10%
The output format is intended for diagnostics, not as a guaranteed machine-readable interface. Ensure the buffer is large enough. Formatting support and configuration requirements depend on the FreeRTOS release and port.

Configuration names and dependencies can vary between FreeRTOS versions. Check the configuration template and documentation for the exact kernel release being used.

12. Run-Time Statistics and Task Scheduling

Run-time statistics can help analyze scheduling behavior.

Example Scenario

Consider three application tasks:

TaskFunctionPriority
SensorTaskReads sensor values2
ControlTaskProcesses control logic4
CommTaskTransmits data1

Suppose the report shows:

  • SensorTask: 20%
  • ControlTask: 65%
  • CommTask: 10%
  • Idle: 5%

The ControlTask consumes the largest share of measured task execution time. The developer should investigate whether its workload is expected and whether its execution time affects lower-priority tasks.

High CPU usage is not automatically a software defect. A control task may legitimately require substantial processor time. Compare measured behavior with the system's timing requirements.

13. Limitations of Run-Time Statistics

  • Run-time measurement adds some instrumentation overhead.
  • A low-resolution counter may produce inaccurate short-task measurements.
  • Counter overflow must be handled correctly.
  • Interrupt execution may not be attributed to application tasks.
  • Formatted output consumes RAM and processing time.
  • Statistics represent observed execution, not necessarily worst-case execution time.
  • CPU percentages do not directly prove schedulability.
  • Measurement intervals and system workload affect interpretation.

14. Practical Example: Task CPU-Time Analysis

Assume a diagnostic report provides the following values:

TaskRun Time (units)
SensorTask2500
ControlTask5000
CommTask1500
Idle1000

Exercise Calculation

Total = 2500 + 5000 + 1500 + 1000
      = 10000 units

SensorTask = (2500 / 10000) × 100
           = 25%

ControlTask = (5000 / 10000) × 100
            = 50%

CommTask = (1500 / 10000) × 100
         = 15%

Idle = (1000 / 10000) × 100
     = 10%

Interpretation:

  • ControlTask consumes 50% of measured task time.
  • SensorTask consumes 25%.
  • CommTask consumes 15%.
  • Idle task consumes 10%.

15. Best Practices

  1. Use a suitable high-resolution run-time counter.
  2. Keep the counter-reading function efficient.
  3. Check counter overflow and wraparound behavior.
  4. Collect statistics over meaningful intervals.
  5. Use sufficient storage for task-status arrays and formatted output.
  6. Compare results with actual task timing requirements.
  7. Do not use run-time percentages as a replacement for WCET analysis.
  8. Consider interrupt and instrumentation overhead.
  9. Use a trace tool when more detailed execution timelines are required.
  10. Disable unnecessary diagnostic instrumentation in production builds if its overhead is unacceptable.

18. Lesson Summary

  • Run-time statistics measure accumulated task execution time.
  • A dedicated counter provides timing information at task switches.
  • configGENERATE_RUN_TIME_STATS enables the relevant feature.
  • uxTaskGetSystemState() collects task-status information.
  • vTaskGetRunTimeStats() formats a diagnostic report.
  • CPU utilization is calculated using task run time divided by total measured run time.

  • Run-time statistics are useful for profiling but do not replace real-time schedulability analysis.
