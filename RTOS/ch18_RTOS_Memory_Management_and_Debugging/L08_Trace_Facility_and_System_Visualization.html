2. What Is RTOS Tracing?

RTOS tracing is the process of recording selected operating-system and application events during program execution.

These events can be analyzed later to understand how the system behaved over time.

Typical trace events include:

  • Task creation and deletion.
  • Task switching.
  • Task entering the Blocked or Ready state.
  • Interrupt entry and exit.
  • Queue send and receive operations.
  • Semaphore take and give operations.
  • Software timer activity.
  • Application-defined events.
RTOS APPLICATION | v EVENT GENERATION | v TRACE RECORDER | v TRACE DATA STORAGE | v TRACE ANALYSIS TOOL | v SYSTEM VISUALIZATION

3. Why Is System Visualization Required?

In a multitasking system, several tasks and interrupts interact. Source-code inspection alone may not reveal the exact order and timing of events.

System visualization helps developers observe:

  • Which task was running at a particular time.
  • When a task became Ready or Blocked.
  • How long a task remained in the Running state.
  • Whether a high-priority task was delayed.
  • When interrupts occurred.
  • Whether queues or semaphores caused unexpected blocking.
  • How much time elapsed between an event and its response.
A trace is evidence of observed execution under the tested conditions. It does not automatically establish worst-case timing or prove that every possible execution path is correct.

4. Trace Events

A trace event is a recorded occurrence that provides information about system execution.

4.1 Common Event Categories

Event CategoryExample
Task eventsTask created, deleted, switched in or switched out.
Scheduler eventsContext switch, scheduler start or suspension.
Queue eventsQueue send, receive, full or empty.
Semaphore eventsSemaphore take, give or timeout.
Timer eventsTimer start, stop, expiry or callback execution.
Interrupt eventsInterrupt entry and exit, if instrumentation supports them.
User eventsSensor sample completed or communication transaction started.

4.2 Example Event Sequence

Time       Event
----------------------------------
0.000 ms   SensorTask becomes Ready
0.100 ms   SensorTask starts Running
0.500 ms   SensorTask sends queue item
0.510 ms   ControlTask becomes Ready
0.520 ms   ControlTask starts Running
1.200 ms   ControlTask blocks
1.210 ms   CommTask starts Running

This event sequence helps reconstruct the interaction between tasks.

5. Task-State Visualization

A trace viewer can display the state of each task over time.

Common FreeRTOS task states include:

StateMeaning
RunningThe task is currently executing on the processor.
ReadyThe task can execute but is not currently selected.
BlockedThe task is waiting for an event or timeout.
SuspendedThe task has been explicitly suspended.
DeletedThe task has been removed from active scheduling.

5.1 Illustrative Task Timeline

Time (ms) 0 1 2 3 4 5 Task A R----RUN----B----RUN----- Task B R--RUN--B------RUN------- Task C R---------RUN--B---------- R = Ready RUN = Running B = Blocked Illustrative timeline only

A real trace viewer presents task-state transitions along a time axis and may allow the developer to zoom into individual events.

6. Execution Timeline Analysis

An execution timeline shows which task or interrupt was active during each time interval.

6.1 Context-Switch Analysis

Consider the following sequence:

Time       Running Task       Event
------------------------------------------
0 ms       Task A             Starts
2 ms       Task A             Blocks on queue
2 ms       Task B             Starts
5 ms       Task B             Delays
5 ms       Task A             Resumes
7 ms       Task A             Completes work

From this timeline, a developer can determine:

  • Task A executed for two milliseconds before blocking.
  • Task B executed for three milliseconds.
  • Task A resumed when it became eligible and was selected.
  • The actual completion time was seven milliseconds after the initial timeline reference.
This example is simplified. Actual scheduling depends on task priorities, interrupt activity, tick timing, and other Ready tasks.

7. FreeRTOS Trace Configuration

FreeRTOS provides trace-related facilities that can be used by trace recorders and diagnostic applications.

7.1 Trace Facility Configuration

/* FreeRTOSConfig.h */

#define configUSE_TRACE_FACILITY  1

This enables additional task-status and trace-related facilities in supported FreeRTOS versions.

7.2 Trace Hook Macros

FreeRTOS provides trace hook macros for selected kernel events. These can be used to connect kernel activity to a trace recorder or custom instrumentation.

Examples of hook names include:

traceTASK_SWITCHED_IN()
traceTASK_SWITCHED_OUT()
traceTASK_CREATE()
traceTASK_DELETE()
traceQUEUE_SEND()
traceQUEUE_RECEIVE()
traceBLOCKING_ON_QUEUE_RECEIVE()
The exact set of hooks, their arguments and invocation locations depend on the FreeRTOS version. Use the matching kernel configuration template and trace-recorder integration documentation.

7.3 Custom Hook Concept

/* Illustrative configuration concept */

#define traceTASK_SWITCHED_IN() \
    RecordTaskSwitchIn()

void RecordTaskSwitchIn(void)
{
    /* Record an event using a suitable
       trace recorder or diagnostic method. */
}

A real implementation must use an appropriate recorder and must avoid blocking, excessive execution time or unsafe operations inside kernel trace hooks.

8. Trace Recording Methods

Trace information can be collected in several ways.

MethodDescriptionConsideration
RAM bufferStores trace events in memory.Consumes RAM; buffer can fill or wrap.
Streaming traceSends events to an external host.Requires a communication interface and adequate bandwidth.
Hardware traceUses processor-specific trace facilities.Depends on processor and debug hardware support.
Custom loggingApplication records selected events.May add timing overhead and miss kernel-level details.

8.1 RAM-Based Trace Buffer

+----------------------------------+ | TRACE BUFFER | +----------------------------------+ | Event 1 | | Event 2 | | Event 3 | | Event 4 | | ... | +----------------------------------+ | v HOST ANALYSIS

When a circular buffer is used, newer events may overwrite older events after the buffer becomes full. The recorder's behavior must be understood before interpreting captured data.

9. Trace Analysis Tools

Several tools can help analyze RTOS execution. Tool selection depends on the processor, compiler, debugger, trace recorder and project configuration.

9.1 Percepio Tracealyzer

Tracealyzer is a trace visualization and analysis tool that supports FreeRTOS and other embedded operating systems through suitable integrations.

  • Task execution timelines.
  • Task-state analysis.
  • Scheduling and communication-event views.
  • Performance and response-time investigation.
  • Event and dependency analysis.

9.2 SEGGER SystemView

SEGGER SystemView is a real-time recording and visualization tool for embedded applications with supported instrumentation and target integrations.

  • Task and interrupt activity.
  • Execution timelines.
  • Context-switch analysis.
  • Application event recording.

9.3 Debugger-Based Inspection

IDE debuggers can inspect task handles, memory, CPU registers and application variables. However, ordinary breakpoint-based debugging is not equivalent to continuous RTOS tracing.

Do not assume every trace tool supports every FreeRTOS port or processor. Confirm target, compiler, recorder integration and transport support before selecting a tool.

10. Run-Time Statistics vs Trace Analysis

Run-Time StatisticsTrace Analysis
Provides accumulated task execution-time values.Records a sequence of events over time.
Useful for CPU-time distribution.Useful for detailed execution history.
Usually provides summarized measurements.Can provide timelines and event relationships.
Can identify high CPU-consuming tasks.Can help explain why a task was delayed.
Does not normally show every state transition.Can show individual state transitions if recorded.

Both techniques complement each other. Run-time statistics identify workload distribution, while trace analysis helps investigate the sequence of events that produced that distribution.

11. Finding Priority Inversion Using a Trace

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task holding a shared resource.

11.1 Example

  • LowPriorityTask takes a mutex.
  • HighPriorityTask becomes Ready and requests the same mutex.
  • HighPriorityTask blocks because the mutex is owned.
  • MediumPriorityTask becomes Ready and preempts LowPriorityTask.
  • HighPriorityTask remains blocked until the mutex is released.
LOW PRIORITY TASK | Takes mutex | HIGH PRIORITY TASK requests mutex | Blocks | MEDIUM PRIORITY TASK runs | LOW PRIORITY TASK delayed | Mutex eventually released | HIGH PRIORITY TASK resumes

A trace timeline can help identify the blocking interval and the task that executed while the high-priority task was waiting.

With priority inheritance, the mutex owner may temporarily inherit the higher priority, reducing this form of inversion. Trace analysis can help verify the observed scheduling behavior.

12. Finding Queue and Semaphore Problems

Trace events can help investigate communication problems.

Observed Trace BehaviorPossible Explanation
Repeated queue-send failuresQueue may be full or consumer may be too slow.
Task repeatedly blocks on queue receiveNo message is available at the time of the request.
Semaphore take repeatedly times outExpected signaling may not be occurring.
Long delay between give and task executionTask priority, interrupt activity or scheduling may affect response.
Queue backlog continuously growsProducer rate may exceed consumer processing capacity.

Trace evidence should be combined with queue return values, task priorities and application-level measurements before deciding the cause.

13. Application-Defined Trace Events

Developers can record application-specific events to correlate kernel behavior with system operations.

Examples:

  • ADC conversion started.
  • Sensor sample completed.
  • Control calculation completed.
  • UART transmission started.
  • Communication packet received.
  • Motor-control command issued.

13.1 Conceptual Example

void ProcessSensorData(void)
{
    /* Record application event:
       SENSOR_PROCESS_START */

    ReadSensorData();

    /* Record application event:
       SENSOR_READ_COMPLETE */

    CalculateControlOutput();

    /* Record application event:
       CONTROL_CALCULATION_COMPLETE */
}

The event-recording calls are conceptual placeholders. Replace them with functions provided by the selected trace recorder.

Application-defined events are especially useful when a developer needs to relate RTOS task scheduling to physical or logical application operations.

14. Trace Buffer and Timing Overhead

Trace recording consumes system resources.

14.1 Memory Overhead

Each recorded event may require storage for information such as:

  • Event identifier.
  • Timestamp.
  • Task or object identifier.
  • Event-specific data.

For example, if an event occupies an average of 12 bytes and 1000 events are stored:

Buffer Size = 12 × 1000
            = 12000 bytes

This is an illustrative estimate. Actual event sizes depend on the recorder format and configuration.

14.2 Timing Overhead

Recording events requires execution time. Excessive instrumentation can affect:

  • Task execution time.
  • Interrupt response time.
  • Scheduling behavior.
  • Communication bandwidth.
  • Memory availability.
A trace can perturb the system being measured. Use appropriate recorder settings and compare instrumented behavior with production-like behavior.

15. Practical Trace-Analysis Workflow

  1. Define the performance or correctness problem.
  2. Identify the tasks, queues, semaphores and interrupts involved.
  3. Select a trace recorder compatible with the target platform.
  4. Configure event recording and timestamp generation.
  5. Build and run the instrumented application.
  6. Reproduce the problem under controlled conditions.
  7. Capture trace data.
  8. Inspect task states and execution timelines.
  9. Identify long blocking intervals and unexpected task switches.
  10. Correlate events with application requirements.
  11. Correct the design and repeat the measurement.

16. Practical Example: Sensor Monitoring System

Consider an embedded system with three tasks:

TaskResponsibility
SensorTaskReads sensor values and sends them to a queue.
ControlTaskProcesses sensor data and calculates an output.
CommTaskTransmits processed information.

A trace investigation may follow this sequence:

1. SensorTask starts.
2. SensorTask reads a sensor.
3. SensorTask sends a queue item.
4. ControlTask becomes Ready.
5. ControlTask receives the item.
6. ControlTask calculates the output.
7. CommTask receives the result.
8. CommTask transmits the data.

The developer can measure:

  • Time from sensor read start to completion.
  • Delay between queue send and receive.
  • ControlTask execution duration.
  • Delay before communication begins.
  • Total event-to-response time.

This helps identify whether delays originate in sensor acquisition, task scheduling, queue communication or data transmission.
