2. What Is Heap Usage?

Heap usage represents the amount of dynamically managed memory currently occupied by allocated objects.

In a FreeRTOS application, dynamic heap allocation may be used for:

  • Task control blocks and task stacks.
  • Queues and their storage.
  • Semaphores and mutexes.
  • Event groups.
  • Software timers.
  • Application buffers allocated using pvPortMalloc().
CONFIGURED HEAP +----------------------------------------+ | | | ALLOCATED MEMORY | | Tasks, queues, buffers | | | +----------------------------------------+ | | | FREE MEMORY | | | +----------------------------------------+

The available heap decreases when allocations are made and may increase when memory is released, depending on the selected heap implementation.

3. Heap Utilization

Heap utilization is the percentage of configured heap memory currently occupied by allocations.

Formula:

Heap Utilization (%) =
    (Used Heap / Total Heap) × 100

Free heap is:

Free Heap = Total Heap - Used Heap

3.1 Calculation Example

Assume the configured heap size is 20 KB and the currently free heap is 8 KB.

Total Heap = 20 KB
Free Heap  = 8 KB

Used Heap = 20 - 8
          = 12 KB

Heap Utilization = (12 / 20) × 100
                 = 60%

Therefore:

  • Used heap = 12 KB.
  • Free heap = 8 KB.
  • Heap utilization = 60%.
This simple calculation assumes the total heap capacity is known and the reported free-memory value represents the allocator's available memory. Allocator metadata and implementation-specific details must be considered when interpreting measurements.

4. FreeRTOS Heap Monitoring Functions

FreeRTOS provides several heap-monitoring functions, depending on the selected heap implementation.

FunctionPurpose
xPortGetFreeHeapSize()Returns the current free heap size in bytes.
xPortGetMinimumEverFreeHeapSize()Returns the minimum free heap size recorded since heap initialization.
vPortGetHeapStats()Provides detailed heap statistics where supported.

4.1 Current Free Heap

size_t freeHeap;

freeHeap = xPortGetFreeHeapSize();

4.2 Minimum-Ever Free Heap

size_t minimumFreeHeap;

minimumFreeHeap =
    xPortGetMinimumEverFreeHeapSize();

The minimum-ever free heap helps identify the lowest free-memory level observed during execution.

4.3 Example Monitoring Task

#include "FreeRTOS.h"
#include "task.h"

void HeapMonitorTask(void *pvParameters)
{
    size_t currentFree;
    size_t minimumFree;

    for (;;)
    {
        currentFree = xPortGetFreeHeapSize();

        minimumFree =
            xPortGetMinimumEverFreeHeapSize();

        /* Record values using a suitable
           diagnostic or logging interface. */

        vTaskDelay(pdMS_TO_TICKS(2000));
    }
}
These functions are not implemented by every heap allocator. Verify their availability in the selected heap source and FreeRTOS release.

5. Detailed Heap Statistics

Where supported, vPortGetHeapStats() returns a structure containing information about heap usage.

5.1 HeapStats_t

HeapStats_t heapStats;

vPortGetHeapStats(&heapStats);

Common fields include:

FieldDescription
xAvailableHeapSpaceInBytesTotal available free heap space.
xSizeOfLargestFreeBlockInBytesSize of the largest available free block.
xSizeOfSmallestFreeBlockInBytesSize of the smallest available free block.
xNumberOfFreeBlocksNumber of free blocks.
xMinimumEverFreeBytesRemainingMinimum free heap recorded.
xNumberOfSuccessfulAllocationsNumber of successful allocations.
xNumberOfSuccessfulFreesNumber of successful frees.

The exact structure and availability depend on the heap implementation and FreeRTOS release.

5.2 Example

#include "FreeRTOS.h"
#include "task.h"

void ReadHeapStatistics(void)
{
    HeapStats_t stats;

    vPortGetHeapStats(&stats);

    /* Inspect or record:
       stats.xAvailableHeapSpaceInBytes
       stats.xSizeOfLargestFreeBlockInBytes
       stats.xNumberOfFreeBlocks
       stats.xMinimumEverFreeBytesRemaining
    */
}

These statistics can help distinguish low overall free memory from fragmentation-related allocation problems.

6. What Is Memory Fragmentation?

Memory fragmentation occurs when available memory is divided into blocks that cannot be used efficiently for future allocation requests.

Two important types are:

  • Internal fragmentation.
  • External fragmentation.
MEMORY FRAGMENTATION | +-------+-------+ | | INTERNAL EXTERNAL FRAGMENTATION FRAGMENTATION | | Waste inside Free memory split allocated block into separate blocks

7. Internal Fragmentation

Internal fragmentation occurs when an allocated memory block contains unused space that cannot be independently allocated to another object.

7.1 Example

Assume an allocator rounds a 13-byte request up to a 16-byte allocation unit.

ALLOCATED BLOCK: 16 BYTES +-----------------------+ | 13 BYTES USED | +-----------------------+ | 3 BYTES UNUSED | +-----------------------+ Internal waste = 3 bytes

The unused space is part of the allocated block and is not available for another allocation.

7.2 Causes

  • Memory alignment requirements.
  • Allocator block-size rounding.
  • Fixed-size memory pools.
  • Metadata or allocation-unit overhead.

7.3 Reduction Techniques

  • Choose suitable allocation sizes.
  • Use appropriately sized memory pools.
  • Group related small objects where practical.
  • Understand alignment requirements.

8. External Fragmentation

External fragmentation occurs when free memory is divided into separate non-contiguous regions.

8.1 Example

INITIAL MEMORY +----------+----------+----------+----------+ | BLOCK A | BLOCK B | BLOCK C | FREE | +----------+----------+----------+----------+ AFTER FREEING A AND C +----------+----------+----------+----------+ | FREE | BLOCK B | FREE | FREE | +----------+----------+----------+----------+

Assume the free regions are 100, 150 and 200 bytes.

Total Free Memory = 100 + 150 + 200
                  = 450 bytes

Largest Free Block = 200 bytes

A request for 300 contiguous bytes cannot be satisfied by these regions, even though total free memory is 450 bytes.

8.2 Causes

  • Repeated allocation and deallocation.
  • Variable-sized allocation requests.
  • Long-lived objects separating short-lived objects.
  • Allocation patterns that leave small unusable gaps.

8.3 Reduction Techniques

  • Use static allocation for long-lived critical objects.
  • Use fixed-size memory pools for repeated buffer sizes.
  • Reduce unnecessary allocation and deallocation cycles.
  • Choose an allocator that supports coalescing where appropriate.
  • Monitor the largest free block.

9. Heap Fragmentation and FreeRTOS Heap Implementations

Different FreeRTOS heap implementations have different memory-management behavior.

HeapAllocationFreeingCoalescing
heap_1YesNoNot applicable
heap_2YesYesNo
heap_3Through C libraryThrough C libraryDepends on C library
heap_4YesYesYes
heap_5YesYesWithin individual regions

heap_4 and heap_5 can merge adjacent free blocks. However, they cannot eliminate all external fragmentation when allocated blocks separate free regions.

For details of each allocator's implementation, see Lesson 03: FreeRTOS Heap Implementations.

10. Memory Leak

A memory leak occurs when dynamically allocated memory is no longer needed but is not released, and the application loses the ability to reuse it.

10.1 Example of a Memory Leak

#include "FreeRTOS.h"

void AllocateRepeatedly(void)
{
    uint8_t *buffer;

    buffer = pvPortMalloc(100);

    if (buffer == NULL)
    {
        return;
    }

    buffer[0] = 0x55;

    /* Missing vPortFree(buffer) */

}

If this function is called repeatedly and each allocated block becomes unreachable without being freed, available heap memory will progressively decrease.

10.2 Corrected Example

#include "FreeRTOS.h"

void AllocateAndRelease(void)
{
    uint8_t *buffer;

    buffer = pvPortMalloc(100);

    if (buffer == NULL)
    {
        return;
    }

    buffer[0] = 0x55;

    /* Complete all operations using buffer */

    vPortFree(buffer);
    buffer = NULL;
}
Only free a block after all tasks, callbacks and peripherals have stopped using it. Setting one pointer to NULL does not invalidate other pointers to the same memory.

11. Heap Monitoring Example with Utilization

The following example calculates a basic heap-utilization percentage for a heap implementation with a known configured capacity.

#include "FreeRTOS.h"
#include "task.h"
#include <stdint.h>

#define HEAP_CAPACITY_BYTES  (20U * 1024U)

void CalculateHeapUsage(void)
{
    size_t freeHeap;
    size_t usedHeap;
    uint32_t utilization;

    freeHeap = xPortGetFreeHeapSize();

    if (freeHeap > HEAP_CAPACITY_BYTES)
    {
        /* Invalid assumption or configuration */
        return;
    }

    usedHeap = HEAP_CAPACITY_BYTES - freeHeap;

    utilization =
        (uint32_t)((usedHeap * 100U) /
                   HEAP_CAPACITY_BYTES);

    /* Record:
       freeHeap
       usedHeap
       utilization
    */
}

This calculation is appropriate only when the selected allocator's reported free space and configured capacity are comparable.

The example assumes a 20 KB heap. Do not use this constant for heap_3 or heap_5 unless the actual memory capacity and allocator accounting are established separately.

12. Allocation Pattern Analysis

Consider an application that allocates memory for communication buffers.

Pattern A: Repeated Variable-Sized Allocation

buffer1 = pvPortMalloc(100);
buffer2 = pvPortMalloc(300);
buffer3 = pvPortMalloc(150);

vPortFree(buffer2);

buffer4 = pvPortMalloc(250);

The allocation of 250 bytes may fail if no suitable contiguous block exists, even when the total free memory is greater than 250 bytes.

Pattern B: Fixed-Size Buffer Reuse

#define BUFFER_SIZE 256

/* Allocate a fixed-size pool or set of
   buffers during system initialization. */

/* Reuse available buffers instead of
   repeatedly requesting variable-sized
   heap blocks. */

Fixed-size buffer management can make memory use more predictable and avoid many variable-size fragmentation patterns.

13. Heap Usage in Real-Time Systems

Dynamic memory operations can affect real-time behavior.

ConcernPossible EffectDesign Approach
Variable allocation timeUncertain execution latencyMeasure allocator timing and limit runtime allocation.
Allocation failureTask or service cannot create required objectCheck return values and define recovery behavior.
FragmentationLarge allocation may fail despite sufficient total free memoryUse pools, static storage or suitable allocators.
Memory leakAvailable memory decreases over timeDefine ownership and release paths.
Heap contentionConcurrent allocations may require synchronizationReview allocator and port behavior.

For highly predictable real-time systems, a common design is to perform required dynamic allocation during initialization and avoid unpredictable allocation operations during critical runtime phases.

14. Heap Optimization Best Practices

  1. Prepare a complete RAM budget before development.
  2. Use static allocation for essential long-lived objects when practical.
  3. Choose a suitable heap implementation.
  4. Check every dynamic allocation result.
  5. Release memory only after its final use.
  6. Use fixed-size memory pools for repeated buffer sizes where appropriate.
  7. Monitor current and minimum-ever free heap.
  8. Inspect the largest free block when detailed statistics are available.
  9. Avoid unnecessary variable-sized allocations.
  10. Test worst-case allocation patterns.
  11. Define behavior for memory exhaustion.
  12. Review memory usage after major software changes.

17. Lesson Summary

  • Heap usage describes dynamically allocated memory consumption.
  • Heap utilization can be calculated from used and total heap capacity.
  • FreeRTOS provides heap-monitoring functions in supported implementations.
  • Internal fragmentation wastes space inside allocated blocks.
  • External fragmentation divides free memory into separate regions.
  • Memory leaks progressively reduce reusable heap memory.
  • Largest-free-block statistics help identify fragmentation-related limitations.
  • Fixed-size pools and controlled allocation patterns improve predictability.
  • Heap monitoring, ownership rules and failure handling are essential for reliable RTOS applications.
