FreeRTOS Features and Architecture

Kernel Components, Architecture Layers and System Execution Flow

1. Learning Objectives

This lesson examines the internal organization of FreeRTOS and the major features provided by its kernel. Understanding its architecture helps developers select appropriate kernel services and organize embedded applications efficiently.

  • Identify the major architectural layers of FreeRTOS.
  • Understand the responsibilities of the kernel.
  • Explain the role of the scheduler and task management.
  • Identify communication and synchronization services.
  • Understand tick interrupts and processor ports.
  • Distinguish kernel services from application and hardware drivers.
  • Understand how tasks interact with the kernel.

2. Major Features of FreeRTOS

2.1 Multitasking

FreeRTOS allows an application to be divided into multiple tasks. Each task has its own execution context and stack. The scheduler decides which ready task should execute.

2.2 Priority-Based Scheduling

Tasks are assigned priorities. A ready task with a higher priority is selected before a ready task with a lower priority under the standard FreeRTOS scheduling model.

2.3 Preemptive and Cooperative Scheduling

FreeRTOS can be configured for preemptive scheduling. With preemption enabled, a newly ready higher-priority task can preempt the running lower-priority task at a scheduling point. Cooperative scheduling is also possible when preemption is disabled.

2.4 Inter-Task Communication

Tasks can exchange data using queues, stream buffers, message buffers and task notifications. Event groups can coordinate multiple conditions.

2.5 Synchronization and Resource Management

Binary semaphores, counting semaphores and mutexes coordinate execution and manage shared resources.

2.6 Software Timers

Software timers provide one-shot and auto-reload time-based callback operations through the timer service task.

2.7 Configurable Memory Management

FreeRTOS supports multiple heap implementations and static allocation options. The application can select memory-management strategies according to its requirements.

2.8 Portability

Architecture-specific processor ports provide the low-level context-switching and interrupt mechanisms needed to run the kernel on different microcontrollers.

3. FreeRTOS Architecture Overview

A FreeRTOS-based embedded application can be viewed as a set of architectural layers. The application uses kernel APIs, the kernel manages tasks and communication, and the processor port connects the kernel to the CPU.

4. Application Layer

The application layer contains the product-specific functionality. Developers create tasks and use kernel services to implement the required behavior.

Example Application Tasks

Task Application Responsibility
Sensor Task Acquire sensor values and validate readings.
Communication Task Handle UART or other communication protocols.
Control Task Calculate control outputs and update actuators.
Fault Task Detect and handle abnormal system conditions.
Display Task Update status information.

Application tasks should not directly modify internal kernel data structures. They should use documented FreeRTOS APIs.

5. FreeRTOS Kernel

The kernel is the central software component that manages task execution and provides services to the application.

Major Kernel Responsibilities

  • Maintain task states and task priorities.
  • Select the next ready task for execution.
  • Manage task blocking and timeouts.
  • Provide task creation and deletion services.
  • Coordinate inter-task communication.
  • Provide synchronization mechanisms.
  • Manage software timer services when enabled.
  • Support configured memory allocation mechanisms.

Kernel Components

Component Purpose
Scheduler Selects which ready task executes.
Task Manager Creates, deletes and manages tasks.
Queue Manager Provides message and data transfer services.
Semaphore and Mutex Services Support synchronization and resource protection.
Event Group Services Coordinate multiple event conditions.
Timer Services Manage software timers and callbacks.
Tick Management Maintains the kernel's tick count and timeouts.

6. Scheduler Architecture

The scheduler determines which ready task should run. In the standard FreeRTOS scheduler, task priorities are used to select the highest-priority ready task.

Example

Task Priority State
Task A 3 Ready
Task B 2 Ready
Task C 1 Blocked

Task A is selected because it is the highest-priority ready task. Task C cannot execute until it becomes ready.

When multiple ready tasks have the same priority, time slicing may be used if enabled. The scheduler's exact behavior also depends on configuration and port implementation.

7. Task Management Services

FreeRTOS provides APIs for creating, deleting, delaying, suspending and resuming tasks.

API Purpose
xTaskCreate() Create a task using dynamically allocated memory.
vTaskDelete() Delete a task.
vTaskDelay() Block the calling task for a relative tick interval.
vTaskDelayUntil() Support periodic task execution using an absolute tick reference.
vTaskSuspend() Suspend a task.
vTaskResume() Resume a suspended task from task context.
uxTaskPriorityGet() Read a task's priority.
vTaskPrioritySet() Change a task's priority.

These APIs are explored in detail in Chapter 13, FreeRTOS Task Programming.

8. Inter-Task Communication Architecture

FreeRTOS provides several mechanisms for communication between tasks. The appropriate mechanism depends on whether the application needs to transfer data, signal an event or synchronize multiple tasks.

Mechanism Primary Purpose
Queue Transfer fixed-size data items between tasks.
Task Notification Signal or exchange lightweight notification values with a task.
Binary Semaphore Signal an event or synchronize tasks.
Counting Semaphore Track a count of available events or resources.
Mutex Protect shared resources with ownership semantics.
Event Group Coordinate multiple event conditions using bits.
Stream Buffer Transfer a stream of bytes.
Message Buffer Transfer variable-length messages.

9. Tick Interrupt and Time Management

FreeRTOS uses a periodic tick interrupt to maintain kernel time. The tick interrupt updates the tick count and supports task delays and timeout processing.

Example

If the configured tick rate is 1000 Hz, the nominal tick interval is: 

Tick Interval = 1 / Tick Frequency

              = 1 / 1000

              = 0.001 seconds

              = 1 millisecond

A task can request a delay using: 

vTaskDelay(pdMS_TO_TICKS(1000));

This blocks the task for a nominal 1000 millisecond tick interval, subject to tick conversion and scheduling behavior.

The tick interrupt is not a precision hardware waveform generator. Software timer expiration and task wake-up can be affected by tick granularity, interrupt latency, scheduling and higher-priority work.

10. Processor Port Architecture

FreeRTOS is portable because it separates much of the kernel logic from processor-specific implementation. A port provides the low-level functions needed for the target CPU and compiler.

Responsibilities of a Port

  • Initialize the processor-specific task context.
  • Implement context switching.
  • Integrate the system tick interrupt.
  • Define critical-section behavior.
  • Provide processor-specific interrupt handling.
  • Support compiler and architecture requirements.

Context Switching Concept

       Task A is Running
               |
               v
       Scheduling Event
               |
               v
       Save Task A Context
               |
               v
       Select Ready Task B
               |
               v
       Restore Task B Context
               |
               v
       Task B is Running

The context normally includes the processor state required to resume a task correctly. Its exact layout is architecture- and port-dependent.

11. Hardware Drivers and FreeRTOS

FreeRTOS does not automatically provide drivers for every microcontroller peripheral. Hardware access is normally handled by device-specific drivers or application code.

Example: UART Data Flow

      UART Hardware
            |
            v
       UART Interrupt
            |
            v
       UART Driver
            |
            v
       Queue / Notification
            |
            v
       Communication Task
            |
            v
       Application Processing

This architecture allows the interrupt handler to perform minimal work and defer longer processing to task context.

Hardware driver design, interrupt priority rules and ISR-safe FreeRTOS APIs depend on the selected processor port and target platform.

12. FreeRTOS Configuration

FreeRTOSConfig.h contains application-specific kernel configuration settings. These settings determine features such as task priorities, tick frequency, heap behavior and optional kernel services.

Examples of Configuration Macros

Macro Purpose
configUSE_PREEMPTION Enables or disables preemptive scheduling.
configUSE_TIME_SLICING Controls time slicing among equal-priority ready tasks where supported.
configTICK_RATE_HZ Configures the kernel tick frequency.
configMAX_PRIORITIES Defines the number of available task priority levels.
configTOTAL_HEAP_SIZE Defines the heap size for heap implementations that use this setting.
configUSE_TIMERS Enables software timer functionality.
configUSE_MUTEXES Enables mutex functionality.
configCHECK_FOR_STACK_OVERFLOW Configures optional task stack overflow checking.

The available configuration options and their requirements depend on the FreeRTOS version and selected processor port.

Design Considerations

  • Choose task priorities based on response requirements.
  • Use queues for sensor data transfer.
  • Use mutexes where shared-resource protection is required.
  • Keep interrupt service routines short.
  • Measure task stack requirements.
  • Analyze worst-case response times.
  • Define safe behavior for sensor and communication failures.

14. Advantages of the FreeRTOS Architecture

  • Separates application responsibilities into manageable tasks.
  • Provides standardized APIs for common RTOS services.
  • Supports different microcontroller architectures through ports.
  • Allows configurable kernel features.
  • Supports structured inter-task communication.
  • Helps organize complex embedded applications.

Architecture Limitations

  • Requires RAM for task stacks and kernel objects.
  • Incorrect task priorities can cause starvation.
  • Incorrect synchronization can cause deadlocks or race conditions.
  • Port-specific interrupt rules must be followed.
  • Kernel use alone does not guarantee deadline satisfaction.
