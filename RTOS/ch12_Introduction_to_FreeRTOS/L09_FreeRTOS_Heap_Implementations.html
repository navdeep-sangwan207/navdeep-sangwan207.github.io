1. Learning Objectives

FreeRTOS provides different heap implementations to support dynamic memory allocation. Each implementation has different characteristics related to freeing memory, fragmentation, configuration and memory-region management.

  • Understand the purpose of FreeRTOS heap files.
  • Learn how dynamic memory allocation works.
  • Compare heap_1, heap_2, heap_3, heap_4 and heap_5.
  • Understand allocation and deallocation APIs.
  • Learn about memory fragmentation and coalescing.
  • Choose a suitable heap implementation for an application.
  • Understand heap monitoring and allocation failure handling.

2. Introduction to FreeRTOS Heap

A heap is a memory area used for dynamic allocation. In FreeRTOS, the selected heap implementation provides the memory-management mechanism used by kernel allocation APIs.

Why Does FreeRTOS Need a Heap?

  • Creating tasks dynamically.
  • Creating queues dynamically.
  • Creating semaphores and mutexes dynamically.
  • Creating event groups dynamically.
  • Creating software timers dynamically.
  • Allocating application memory through FreeRTOS allocation APIs.

Important Heap APIs

void *pvPortMalloc(size_t xSize);

void vPortFree(void *pv);

size_t xPortGetFreeHeapSize(void);

size_t xPortGetMinimumEverFreeHeapSize(void);

pvPortMalloc() requests memory from the configured FreeRTOS allocator. vPortFree() releases memory where the selected implementation supports freeing.

These functions belong to the FreeRTOS memory management layer. They are distinct from the standard C functions malloc() and free(), although heap_3 uses those C library functions internally.

3. Overview of the Five Heap Implementations

Heap Allocation Freeing Main Characteristic
heap_1 Yes No Simple allocation-only approach.
heap_2 Yes Yes Does not coalesce adjacent free blocks.
heap_3 Yes Yes Wraps standard C malloc() and free().
heap_4 Yes Yes Coalesces adjacent free blocks.
heap_5 Yes Yes Supports multiple non-contiguous memory regions.

The five implementations are alternative allocator designs. A project normally selects one appropriate heap implementation rather than compiling all five together.

4. heap_1 – Allocation Only

heap_1.c is the simplest FreeRTOS heap implementation. It allocates memory but does not support freeing previously allocated blocks.

Characteristics

  • Supports dynamic memory allocation.
  • Does not support memory deallocation.
  • Simple allocation strategy.
  • No fragmentation caused by repeated freeing and reallocation.
  • Suitable when dynamically created objects remain allocated for the application's lifetime.

Conceptual Example

void *buffer1;
void *buffer2;

buffer1 = pvPortMalloc(100);
buffer2 = pvPortMalloc(200);

if (buffer1 == NULL || buffer2 == NULL)
{
    /* Handle allocation failure */
}

/* heap_1 does not provide normal freeing
   of these allocated blocks. */

Memory Behavior

Initial Heap:

+----------------------------------+
|             Free                 |
+----------------------------------+

After two allocations:

+----------+-------------+---------+
| Buffer 1 |  Buffer 2   |  Free   |
+----------+-------------+---------+

Allocated memory remains reserved.
heap_1 is useful for systems where objects are created during initialization and remain allocated until the system stops or resets.

5. heap_2 – Allocation and Freeing Without Coalescing

heap_2.c supports both memory allocation and freeing. However, it does not combine adjacent free blocks into larger blocks.

Characteristics

  • Supports pvPortMalloc().
  • Supports vPortFree().
  • Can reuse freed blocks that are suitable for a request.
  • Does not coalesce adjacent free blocks.
  • Can suffer from external fragmentation.

Conceptual Example

void *a;
void *b;
void *c;

a = pvPortMalloc(100);
b = pvPortMalloc(200);
c = pvPortMalloc(100);

if (a != NULL && b != NULL && c != NULL)
{
    vPortFree(b);
}

/* The freed block can be reused if a
   suitable later request is made. */

Fragmentation Example

Before Freeing:

+--------+--------+--------+--------+
|   A    |   B    |   C    |  Free  |
+--------+--------+--------+--------+

After Freeing B:

+--------+--------+--------+--------+
|   A    |  Free  |   C    |  Free  |
+--------+--------+--------+--------+

Two free blocks remain separate.

Even though the total free memory may be large enough, a request for one large contiguous block can fail if no individual free block is large enough.

6. heap_3 – Wrapper Around C Library Allocation

heap_3.c provides FreeRTOS allocation functions by wrapping the standard C library's malloc() and free().

Conceptual Relationship

FreeRTOS Application
        |
        v
pvPortMalloc() / vPortFree()
        |
        v
FreeRTOS heap_3 wrapper
        |
        v
C Library malloc() / free()
        |
        v
C Runtime Memory Manager

Characteristics

  • Uses the C library memory allocator.
  • Supports allocation and freeing.
  • Heap size is managed by the C runtime environment.
  • Behavior depends on the C library implementation.
  • Thread safety and timing behavior must be checked for the target toolchain.
Do not assume that configTOTAL_HEAP_SIZE controls the memory available to heap_3. Its memory comes from the C library allocator, whose configuration is toolchain- and platform-dependent.

7. heap_4 – Allocation with Coalescing

heap_4.c supports allocation and freeing and combines adjacent free blocks. This process is called coalescing.

Characteristics

  • Supports allocation and deallocation.
  • Coalesces adjacent free blocks.
  • Helps reduce external fragmentation.
  • Uses a FreeRTOS-managed heap area.
  • Commonly suitable for applications requiring repeated allocation and freeing.

Coalescing Example

Before Freeing:

+--------+--------+--------+--------+
|   A    |   B    |   C    |  Free  |
+--------+--------+--------+--------+

After Freeing B and C:

+--------+-----------------+--------+
|   A    |       Free      |  Free  |
+--------+-----------------+--------+

Adjacent free blocks can be combined
into a larger free block.

Coalescing makes larger allocations more likely to succeed than with an allocator that leaves adjacent free blocks separate. It does not eliminate every possible fragmentation pattern.

Example

void *buffer1;
void *buffer2;

buffer1 = pvPortMalloc(128);
buffer2 = pvPortMalloc(256);

if (buffer1 != NULL && buffer2 != NULL)
{
    vPortFree(buffer1);
    vPortFree(buffer2);
}

/* heap_4 can coalesce adjacent free blocks. */
heap_4 is a common choice when an application needs dynamic allocation and freeing from a single FreeRTOS-managed heap region.

8. heap_5 – Multiple Memory Regions

heap_5.c extends the heap_4-style allocation approach to support multiple non-contiguous memory regions.

Why Multiple Regions?

Some embedded systems have more than one usable RAM region. These regions may be separated in the processor's address space. 

Microcontroller Memory Map

+-----------------------+
|       RAM Region 1    |
+-----------------------+

       Address Gap

+-----------------------+
|       RAM Region 2    |
+-----------------------+

       Address Gap

+-----------------------+
|       RAM Region 3    |
+-----------------------+

Characteristics

  • Supports multiple memory regions.
  • Supports allocation and freeing.
  • Can coalesce adjacent free blocks within a region.
  • Requires explicit region configuration before allocation.
  • Useful when a target has several suitable RAM areas.

Region Configuration Concept

HeapRegion_t regions[] =
{
    { region1Start, region1Size },
    { region2Start, region2Size },
    { NULL, 0 }
};

vPortDefineHeapRegions(regions);

The region addresses and sizes must be valid for the target's memory map. The regions must be supplied in the order and format required by the selected FreeRTOS version.

Configure heap_5 regions before any API that performs dynamic allocation. Do not include memory that is reserved, inaccessible or used by another subsystem.

10. FreeRTOS Heap Configuration

The selected heap implementation must be included in the project build. The application's FreeRTOSConfig.h must also contain suitable allocation settings.

Example Configuration

#define configSUPPORT_DYNAMIC_ALLOCATION    1
#define configSUPPORT_STATIC_ALLOCATION     1

#define configTOTAL_HEAP_SIZE               (10 * 1024)

#define configUSE_MALLOC_FAILED_HOOK        1

This is an illustrative configuration fragment, not a complete FreeRTOSConfig.h file.

Configuration Considerations

  • configSUPPORT_DYNAMIC_ALLOCATION controls availability of dynamic allocation APIs.
  • configSUPPORT_STATIC_ALLOCATION controls availability of static creation APIs.
  • configTOTAL_HEAP_SIZE is used by heap implementations that define their heap using this setting.
  • configUSE_MALLOC_FAILED_HOOK enables the allocation-failure hook when supported by the selected configuration.
A project using heap_5 needs explicit memory-region setup. A project using heap_3 relies on the C runtime allocator. Do not copy heap settings blindly between projects.

11. Heap Monitoring

Heap monitoring helps identify memory pressure and unexpected allocation behavior.

Free Heap Size

size_t freeHeap;

freeHeap = xPortGetFreeHeapSize();

This reports the currently free heap memory where the selected heap implementation provides the API.

Minimum Ever Free Heap

size_t minimumFreeHeap;

minimumFreeHeap =
    xPortGetMinimumEverFreeHeapSize();

This reports the lowest free-heap value recorded since the heap began operating, where supported. It helps identify the worst observed heap usage during testing.

Allocation Failure Check

void *buffer;

buffer = pvPortMalloc(256);

if (buffer == NULL)
{
    /* Handle allocation failure */
}
else
{
    /* Use the allocated memory */

    vPortFree(buffer);
}
Do not assume that a successful allocation guarantees enough memory for all future requests. Test under representative worst-case workloads.

12. Selecting the Appropriate Heap

Application Requirement Possible Choice Reason
Objects allocated once and retained heap_1 Simple allocation-only behavior.
Legacy application using the C allocator heap_3 Wraps C malloc() and free().
Repeated allocation and freeing in one region heap_4 Coalesces adjacent free blocks.
Memory spread across multiple RAM regions heap_5 Supports multiple configured regions.

heap_2 is mainly relevant for understanding earlier FreeRTOS allocator designs and systems that have a specific reason to use it. For new designs, evaluate the coalescing behavior of heap_4 or heap_5 when repeated freeing is needed.

13. Practical Activity – Compare Heap Behavior

Objective: Understand how different heap implementations manage allocated and freed memory.

Procedure

  1. Review the source code for each heap implementation.
  2. Identify how the allocator obtains its memory region.
  3. Locate the implementation of pvPortMalloc().
  4. Locate the implementation of vPortFree(), where available.
  5. Compare how heap_2 and heap_4 handle adjacent freed blocks.
  6. Identify how heap_5 receives its memory regions.
  7. Review the allocation-failure handling mechanism.
  8. Record the advantages and limitations of each implementation.

Expected Result

A comparison table explaining allocation, deallocation, coalescing, fragmentation behavior and suitable application scenarios for each FreeRTOS heap implementation.

14. Important Design Considerations

  • Use a heap implementation that matches the target memory architecture.
  • Check the return value of every dynamic allocation operation.
  • Do not free memory while another task or peripheral still uses it.
  • Do not access an object after its storage has been released.
  • Consider static allocation for critical long-lived objects.
  • Measure allocation timing if it affects real-time behavior.
  • Keep heap monitoring and failure diagnostics in the test plan.
  • Validate memory regions against the linker map and hardware memory map.

16. Lesson Summary

  • FreeRTOS provides five commonly discussed heap implementations.
  • heap_1 supports allocation without freeing.
  • heap_2 supports freeing but does not coalesce adjacent free blocks.
