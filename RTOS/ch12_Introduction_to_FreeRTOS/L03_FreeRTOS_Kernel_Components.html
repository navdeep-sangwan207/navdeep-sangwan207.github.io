FreeRTOS Kernel Components

Scheduler, Task Management, Communication, Synchronization and Memory Services

1. Learning Objectives

The FreeRTOS kernel consists of several cooperating components that manage task execution, scheduling, communication, synchronization and time. This lesson explains the responsibilities of these components and how they interact in an embedded application.

  • Identify the major FreeRTOS kernel components.
  • Understand scheduler and task-management responsibilities.
  • Explain queue and synchronization services.
  • Understand event groups and software timer services.
  • Describe tick management and timeout processing.
  • Understand kernel memory-management options.
  • Relate kernel components to an embedded application.

3. Scheduler Component

The scheduler is responsible for selecting which ready task should execute. It uses task priority and the configured scheduling behavior.

Main Responsibilities

  • Select the highest-priority ready task.
  • Manage transitions between running, ready and blocked states.
  • Support preemptive scheduling when enabled.
  • Support time slicing among equal-priority ready tasks when configured.
  • Coordinate context switching through the processor port.

Example

Task Priority State
Sensor Task 3 Ready
UART Task 2 Ready
Display Task 1 Blocked

The Sensor Task is selected because it has the highest priority among the ready tasks.

A task's priority does not guarantee its deadline. Execution time, blocking, interrupts and higher-priority workload must also be considered.

4. Task Management Component

The task-management services allow applications to create and control independent execution units. Each task has its own stack and task context.

Important Task APIs

API Function
xTaskCreate() Creates a task using dynamically allocated memory.
xTaskCreateStatic() Creates a task using application-supplied memory.
vTaskDelete() Deletes a task.
vTaskDelay() Blocks the calling task for a relative interval.
vTaskDelayUntil() Supports periodic task execution using a previous wake-time reference.
vTaskSuspend() Suspends a task.
vTaskResume() Resumes a suspended task from task context.

Task Creation Example

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read and process sensor data. */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    BaseType_t result;

    result = xTaskCreate(
        SensorTask,
        "Sensor",
        256,
        NULL,
        2,
        NULL
    );

    if (result != pdPASS)
    {
        /* Handle task creation failure. */
        for (;;);
    }

    vTaskStartScheduler();

    for (;;);
}

The task-management component maintains the task's scheduling information and coordinates its execution with the scheduler.

5. Task Control Block (TCB)

Each FreeRTOS task is represented internally by a Task Control Block. The TCB stores information needed by the kernel to manage the task.

Typical Information Associated with a Task

  • Task stack information.
  • Current task stack pointer.
  • Task priority.
  • Task state and scheduling information.
  • Task name, where configured.
  • Task list and kernel bookkeeping information.
          Task Control Block
                   |
       +-----------+-----------+
       |           |           |
       v           v           v
    Stack       Priority    Task State
       |
       v
  Saved CPU Context
The internal TCB structure is version- and configuration- dependent. It is an internal kernel implementation detail. Application code should use public task APIs rather than directly accessing or modifying TCB fields.

6. Queue Management Component

The queue-management component provides communication between tasks and, through suitable APIs, between interrupt service routines and tasks.

Queue Responsibilities

  • Transfer data items between tasks.
  • Allow a receiver to block when the queue is empty.
  • Allow a sender to block when the queue is full, when configured to wait.
  • Support communication between multiple tasks.
  • Provide ISR-safe queue operations where supported.

Queue Data Flow

       Producer Task
             |
             | xQueueSend()
             v
       +-------------+
       |    Queue    |
       |             |
       |  Data Item  |
       |  Data Item  |
       |  Data Item  |
       +-------------+
             |
             | xQueueReceive()
             v
       Consumer Task

Important Queue APIs

API Purpose
xQueueCreate() Create a queue using dynamic allocation.
xQueueCreateStatic() Create a queue using application-supplied memory.
xQueueSend() Send an item to a queue.
xQueueReceive() Receive an item from a queue.
xQueuePeek() Read an item without removing it.
uxQueueMessagesWaiting() Get the number of items currently waiting.
FreeRTOS queues copy fixed-size items. If a queue carries a pointer, only the pointer value is copied. The application must manage the lifetime and ownership of the pointed-to data.

7. Synchronization Component

Synchronization services coordinate task execution and control access to shared resources.

Major Synchronization Objects

Object Purpose
Binary Semaphore Signal an event or synchronize two execution contexts.
Counting Semaphore Maintain a count of available tokens or events.
Mutex Protect shared resources with task ownership and priority inheritance support.
Recursive Mutex Allow the owning task to take the same mutex recursively.
Task Notification Signal or exchange notification information with a particular task.

Example: Protecting a Shared Resource

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

static SemaphoreHandle_t xMutex;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xMutex,
                portMAX_DELAY
            ) == pdTRUE)
        {
            /* Access shared resource. */

            xSemaphoreGive(xMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void CreateResourceMutex(void)
{
    xMutex = xSemaphoreCreateMutex();

    if (xMutex == NULL)
    {
        /* Handle allocation failure. */
    }
}
A mutex must be used from task context, not an ISR. The task that takes a mutex must release it. A mutex protects a shared resource only when all relevant access paths follow the same protection protocol.

8. Event Group Component

Event groups allow multiple tasks to synchronize using a collection of event bits. Each bit represents a condition or event state.

Example Event Definitions

#define SENSOR_READY_BIT  (1U << 0)
#define UART_READY_BIT    (1U << 1)
#define SYSTEM_READY_BIT  (1U << 2)

Event Group APIs

API Purpose
xEventGroupCreate() Create an event group.
xEventGroupSetBits() Set event bits from task context.
xEventGroupClearBits() Clear selected event bits.
xEventGroupWaitBits() Wait for one or more event conditions.
xEventGroupSetBitsFromISR() Request event-bit setting from ISR context through deferred processing.

Event groups are useful when a task must wait for several initialization or operating conditions. They do not store data payloads or count repeated occurrences of an already-set bit.

9. Software Timer Service Component

The software timer service manages timer expiration and executes timer callback functions in the context of the timer service task.

Timer Types

  • One-shot timer: expires once after its configured period.
  • Auto-reload timer: repeats after each expiration.

Timer Service Architecture

       Application Task
              |
              | Timer API command
              v
       Timer Command Queue
              |
              v
       Timer Service Task
              |
              v
       Timer Expiration
              |
              v
       Callback Function
              |
              v
       Notify Application

Important Timer APIs

API Purpose
xTimerCreate() Create a software timer dynamically.
xTimerCreateStatic() Create a timer using application-supplied memory.
xTimerStart() Submit a timer-start command.
xTimerStop() Submit a timer-stop command.
xTimerReset() Submit a timer-reset command.
xTimerDelete() Submit a timer-deletion command.
Timer API commands are generally sent through the timer command queue. A successful return indicates that the command was accepted for processing; it does not mean the timer service task has already processed it. Timer callbacks must not block.

10. Tick Management Component

Tick management maintains the kernel tick count and supports task delays, timeout handling and software timer timing.

Tick Frequency Example

#define configTICK_RATE_HZ 1000

At a configured tick rate of 1000 Hz, the nominal interval between ticks is one millisecond.

Delay Example

vTaskDelay(pdMS_TO_TICKS(500));

This requests a task delay corresponding to 500 milliseconds after conversion to kernel ticks.

Tick Management Responsibilities

  • Maintain the kernel tick count.
  • Track delayed tasks.
  • Process task timeout conditions.
  • Support software timer expiration.
  • Trigger scheduling when required by kernel operation.
Tick-based delays have finite resolution. A very short delay may convert to zero ticks depending on the tick rate and conversion macro. The tick count is not a calendar clock or a substitute for an RTC.

11. Memory Management Component

FreeRTOS memory management provides allocation mechanisms for kernel objects and dynamically created tasks. Applications can also use static allocation to supply memory explicitly.

Dynamic Allocation

Dynamic allocation obtains memory from a configured heap during runtime. APIs such as xTaskCreate() and xQueueCreate() may use dynamic allocation.

Static Allocation

Static allocation uses memory supplied by the application. For example, xTaskCreateStatic() creates a task using a supplied task control block buffer and stack buffer.

FreeRTOS Heap Implementations

Heap Characteristics
heap_1 Allocates memory but does not free it.
heap_2 Supports allocation and freeing but does not coalesce adjacent free blocks.
heap_3 Wraps the standard C library malloc() and free() functions.
heap_4 Supports allocation, freeing and coalescing adjacent free blocks.
heap_5 Supports multiple non-contiguous memory regions and coalescing within regions.
The heap implementation must be selected and integrated correctly. Static allocation can improve predictability, but it does not remove the need to size task stacks and kernel objects correctly.

12. Processor Port Component

The processor port connects the generic FreeRTOS kernel to the target CPU architecture. It supplies low-level functions that cannot be implemented identically on every processor.

Port Responsibilities

  • Initialize task execution contexts.
  • Save and restore processor registers during context switching.
  • Implement the port-specific scheduler start operation.
  • Integrate tick interrupt handling.
  • Define critical-section and interrupt-masking behavior.
  • Provide architecture-specific compiler support.

For example, an ARM7 port and a Cortex-M port have different processor exception and context-switching mechanisms. Their interrupt-priority rules and port-specific APIs must not be assumed to be identical.

Notify one specific task Task Notification
Signal a single event Binary Semaphore or Task Notification
Track multiple available tokens Counting Semaphore
Protect a shared peripheral Mutex

Generate periodic software events Software Timer
Transfer a byte stream Stream Buffer
Transfer variable-length messages Message Buffer

15. Common Design Mistakes

  1. Using the wrong communication object: Event groups do not replace queues when data must be transferred.
  2. Using mutexes in ISRs: Mutex operations require task context.
  3. Blocking inside timer callbacks: This delays other timer-service operations.
  4. Ignoring task stack size: Insufficient stack can cause memory corruption or faults.
  5. Using incorrect task priorities: Poor priority assignment can cause starvation or unacceptable response time.
  6. Ignoring memory allocation failures: Task and kernel-object creation can fail.
  7. Directly modifying internal kernel structures: Use public APIs instead.
  8. Assuming all ports behave identically: Context switching and interrupt rules are architecture-specific.
