2. Introduction to Kernel Objects

A kernel object is a data structure managed by the RTOS kernel to provide a specific service to an application. FreeRTOS uses kernel objects to manage tasks, communication, synchronization and timing.

Examples include:

  • Task objects for independent execution.
  • Queue objects for data communication.
  • Semaphore objects for signaling and resource counting.
  • Mutex objects for exclusive resource ownership.
  • Event group objects for condition-bit synchronization.
  • Software timer objects for time-based callbacks.

3. Task Objects

A task is an independent execution unit managed by the FreeRTOS scheduler. Each task has its own execution context and stack.

Task-Related Components

  • Task function: Contains the code executed by the task.
  • Task stack: Stores local variables, return information and saved execution context.
  • Task Control Block (TCB): Stores kernel-managed task information.
  • Task handle: Provides an application reference to a task.
  • Priority: Determines the task's scheduling precedence.

Task Handle Declaration

TaskHandle_t sensorTaskHandle = NULL;

Task Creation Example

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read sensor data */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    xTaskCreate(
        SensorTask,
        "Sensor",
        256,
        NULL,
        2,
        &sensorTaskHandle
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}
TaskHandle_t is a reference to a task, not the Task Control Block itself. The TCB is an internal kernel structure and should not be modified by application code.

4. Queue Objects

A queue is a kernel-managed communication object used to transfer data between tasks and, through suitable APIs, between interrupt service routines and tasks.

Queue Characteristics

  • Stores a fixed number of items.
  • Each item has a fixed size.
  • Data is copied into and out of the queue.
  • Tasks can block while waiting to send or receive.
  • Queues support producer-consumer communication.

Queue Handle

QueueHandle_t sensorQueue;

Queue Creation

sensorQueue = xQueueCreate(5, sizeof(int));

This creates a queue with capacity for five integer items, assuming allocation succeeds.

Sending and Receiving

int sensorValue = 250;
int receivedValue;

xQueueSend(sensorQueue, &sensorValue, portMAX_DELAY);

xQueueReceive(
    sensorQueue,
    &receivedValue,
    portMAX_DELAY
);
A queue containing pointers copies the pointer value, not the data pointed to. The application must define safe buffer ownership and lifetime rules when sending pointers.

5. Semaphore Objects

A semaphore is a synchronization object used for signaling or counting available resources. FreeRTOS supports binary and counting semaphores.

Binary Semaphore

A binary semaphore has two logical states: available or unavailable. It is commonly used for event signaling between an ISR and a task or between tasks. 

SemaphoreHandle_t eventSemaphore;

eventSemaphore = xSemaphoreCreateBinary();

Counting Semaphore

A counting semaphore maintains a count between zero and a configured maximum. It can represent a number of available resources or pending occurrences. 

SemaphoreHandle_t resourceSemaphore;

resourceSemaphore =
    xSemaphoreCreateCounting(5, 5);

In this example, the initial count is five and the maximum count is five.

Repeated binary semaphore gives do not accumulate an unlimited number of events. If every event must be preserved, consider a queue or counting semaphore.

6. Mutex Objects

A mutex is a mutual-exclusion object used to protect shared resources. It provides ownership semantics and supports priority inheritance in FreeRTOS.

Mutex Creation

SemaphoreHandle_t uartMutex;

uartMutex = xSemaphoreCreateMutex();

Mutex Usage

if (xSemaphoreTake(uartMutex, portMAX_DELAY) == pdTRUE)
{
    /* Access shared UART resource */

    xSemaphoreGive(uartMutex);
}

A task that successfully takes a mutex becomes its owner and must release it after using the protected resource.

A mutex must not be used from an ISR. Interrupt service routines must not block or take ownership of a mutex.

7. Event Group Objects

An event group is a collection of event bits. Each bit represents a condition or event state. Tasks can wait for one or more specified bits.

Event Group Handle

EventGroupHandle_t systemEvents;

Event Group Creation

systemEvents = xEventGroupCreate();

Setting Event Bits

#define SENSOR_READY_BIT   (1U << 0)
#define UART_READY_BIT     (1U << 1)

xEventGroupSetBits(
    systemEvents,
    SENSOR_READY_BIT
);

Waiting for Event Bits

EventBits_t result;

result = xEventGroupWaitBits(
    systemEvents,
    SENSOR_READY_BIT | UART_READY_BIT,
    pdTRUE,
    pdTRUE,
    portMAX_DELAY
);

In this example, the task waits until both specified bits are set. The requested bits are cleared on exit when the wait condition is satisfied.

Event groups represent condition bits, not a data queue or event counter. Repeated setting of the same bit coalesces into one set state.

8. Software Timer Objects

A software timer is a kernel object that triggers a callback function after a specified number of ticks. It can operate as a one-shot or auto-reload timer.

Timer Handle

TimerHandle_t statusTimer;

Timer Creation

statusTimer = xTimerCreate(
    "StatusTimer",
    pdMS_TO_TICKS(1000),
    pdTRUE,
    NULL,
    TimerCallback
);

Callback Function

void TimerCallback(TimerHandle_t xTimer)
{
    /* Perform short, non-blocking timer work */
}

The example creates an auto-reload timer with a nominal period of one second. Its callback executes in the timer service task.

Timer callbacks are not hardware interrupt handlers. Avoid long operations and blocking calls because they delay other timer service activity.

9. Kernel Object Handles

FreeRTOS applications use handle types to refer to kernel-managed objects. A handle is generally an opaque reference; application code should use documented APIs rather than inspect internal object structures.

Object Common Handle Type
Task TaskHandle_t
Queue QueueHandle_t
Semaphore / Mutex SemaphoreHandle_t
Event Group EventGroupHandle_t
Software Timer TimerHandle_t

Example Handle Declarations

TaskHandle_t controlTaskHandle = NULL;

QueueHandle_t commandQueue = NULL;

SemaphoreHandle_t uartMutex = NULL;

EventGroupHandle_t systemEvents = NULL;

TimerHandle_t periodicTimer = NULL;

10. Kernel Object Lifecycle

A kernel object typically passes through a lifecycle involving creation, use and deletion. The exact lifecycle depends on the object type.

          Required
              |

Common API Examples

Object Create Delete
Task xTaskCreate() vTaskDelete()
Queue xQueueCreate() vQueueDelete()
Binary Semaphore xSemaphoreCreateBinary() vSemaphoreDelete()
Mutex xSemaphoreCreateMutex() vSemaphoreDelete()
Event Group xEventGroupCreate() vEventGroupDelete()
Software Timer xTimerCreate() xTimerDelete()
These are common dynamic-creation APIs. Static creation alternatives are available for supported object types when static allocation is enabled. Deleting an object must be coordinated so that no task or ISR continues using an invalid handle.

11. Static and Dynamic Kernel Objects

Dynamic Object Creation

Dynamic creation obtains the required memory through the configured allocation mechanism. For example: 

QueueHandle_t dataQueue;

dataQueue = xQueueCreate(10, sizeof(uint32_t));

if (dataQueue == NULL)
{
    /* Handle allocation failure */
}

Static Object Creation

Static creation uses memory supplied by the application. For example: 

static StaticQueue_t queueControlBlock;

static uint8_t queueStorage[10 * sizeof(uint32_t)];

QueueHandle_t dataQueue;

dataQueue = xQueueCreateStatic(
    10,
    sizeof(uint32_t),
    queueStorage,
    &queueControlBlock
);
Dynamic Allocation Static Allocation
Memory is obtained through the configured allocator. Application supplies the memory storage.
Allocation can fail at runtime. Storage is reserved in advance.
Heap management is required for the selected allocator. Heap allocation is not required for that statically created object.
Useful when runtime object creation is needed. Useful when memory usage must be planned in advance.

12. Choosing the Correct Kernel Object

Requirement Suitable Object
Run independent application functions concurrently Tasks
Transfer structured data between tasks Queue
Signal an event occurrence Binary semaphore or task notification
Count available resources or occurrences Counting semaphore
Protect a shared resource with ownership Mutex
Wait for several independent conditions Event group
Execute an operation periodically Software timer or periodic task
Select an object according to the required communication or synchronization behavior. A mutex, semaphore and queue are not interchangeable.

13. Practical Application – Sensor Monitoring System

Consider an embedded monitoring system with a sensor task, a processing task and a communication task.

Kernel Object Design

  • Sensor task: Reads sensor data.
  • Queue: Transfers sensor readings to the processing task.
  • Processing task: Checks readings against limits.
  • Mutex: Protects a shared communication resource if multiple tasks use it.
  • Event group: Represents system readiness or fault conditions.
  • Software timer: Triggers periodic monitoring activity.
        Sensor Task
             |
             | Sensor Reading
             v
           Queue
             |
             v
       Processing Task
             |
       +-----+------+
       |            |
       v            v
   Event Group    UART Mutex
       |            |
       v            v
   Status Task  Communication Task
                    ^
                    |
             Software Timer

This design separates data transfer, condition signaling, resource protection and time-based operations into appropriate kernel services.

14. Common Kernel Object Errors

Error Possible Cause
Null handle Object creation failed, often due to insufficient memory.
Queue send failure Queue is full or timeout expired.
Queue receive timeout No item became available within the specified wait period.
Mutex not released Incorrect ownership handling or missing give operation.
Lost event occurrences Binary semaphore or event bit used where every occurrence must be counted.
Invalid handle use Object was deleted or never created successfully.
Timer callback delays Callback performs lengthy or blocking work.
