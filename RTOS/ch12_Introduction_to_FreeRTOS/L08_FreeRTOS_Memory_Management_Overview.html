FreeRTOS Memory Management Overview

RAM Organization, Static and Dynamic Allocation, Heap Management

1. Learning Objectives

Memory management is an important part of embedded real-time system design. FreeRTOS requires memory for task stacks, task control blocks, queues, synchronization objects and other kernel services.

  • Understand memory requirements in FreeRTOS.
  • Identify the main RAM regions used by an embedded application.
  • Understand task stack and kernel object memory.
  • Differentiate static and dynamic allocation.
  • Understand the role of the FreeRTOS heap.
  • Identify memory-allocation failure conditions.
  • Learn basic memory-planning techniques.

2. Introduction to Memory Management

Memory management is the process of allocating, using and releasing memory required by software. In a FreeRTOS application, memory is needed by both the kernel and the application.

Memory Required by FreeRTOS

  • Task Control Blocks (TCBs).
  • Task stacks.
  • Queue control structures and queue storage.
  • Semaphore and mutex control structures.
  • Event group structures.
  • Software timer structures.
  • Timer service task stack and queue storage.

Memory Required by the Application

  • Global and static variables.
  • Local variables and function call stacks.
  • Sensor and communication buffers.
  • Peripheral driver data.
  • Application-specific data structures.

3. Memory Organization in an Embedded System

A typical embedded application uses different memory regions for program instructions, initialized data, uninitialized data, stacks and dynamically allocated memory. 

              Microcontroller Memory
                       |
          +------------+------------+
          |                         |
        Flash                       RAM
          |                         |
     Program Code             +-----+------+
     Constant Data            |            |
                         Static Data    Runtime Data
                         (.data/.bss)       |
                                           +------+
                                           |      |
                                      Task Stacks Heap
                                           |
                                      Local Data
                                      Kernel Objects
Memory Region Purpose
Flash / ROM Stores executable program code and constant data.
.text Contains executable instructions.
.data Stores initialized global and static variables in RAM.
.bss Stores zero-initialized or uninitialized global and static variables.
Stack Stores function call information and automatic local variables.
Heap Provides memory for dynamic allocation.
Exact memory layout depends on the processor, compiler, linker script and startup code. The FreeRTOS heap is not necessarily the same as the C library heap.

4. Task Stack Memory

Every FreeRTOS task requires its own stack. The stack stores information required during task execution, including local variables, function call information and saved context.

Example

void SensorTask(void *pvParameters)
{
    int sensorValue = 100;
    float temperature = 25.5f;

    for (;;)
    {
        /* Task operations */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

The task's local variables and function execution information use its stack, subject to compiler optimization and variable storage rules.

Stack Depth Calculation

Stack Memory = Stack Depth × sizeof(StackType_t)

Example:

Stack Depth = 256 words
sizeof(StackType_t) = 4 bytes

Stack Memory = 256 × 4
             = 1024 bytes
The stack depth argument used by common FreeRTOS task-creation APIs is expressed in StackType_t elements, not bytes. The exact type size depends on the processor port.

5. Task Control Block Memory

FreeRTOS maintains a Task Control Block for each task. The TCB stores internal information required by the kernel to manage task execution.

Typical TCB Information

  • Task stack pointer.
  • Task priority.
  • Task state and scheduling information.
  • Task name and related metadata.
  • Links to internal kernel lists.
  • Other port- and configuration-dependent fields.

The kernel allocates and manages the TCB. Application code should use documented task APIs and handles instead of modifying internal TCB fields.

6. Static Memory Allocation

Static allocation means that memory for an object is supplied by the application instead of being requested from the FreeRTOS heap at runtime.

Example: Static Task Creation

static StaticTask_t taskControlBlock;

static StackType_t taskStack[256];

TaskHandle_t sensorTaskHandle;

sensorTaskHandle = xTaskCreateStatic(
    SensorTask,
    "Sensor",
    256,
    NULL,
    2,
    taskStack,
    &taskControlBlock
);

The application provides both the task stack storage and the TCB storage through the appropriate API parameters.

Advantages

  • Memory requirements can be planned in advance.
  • No heap allocation is required for that object.
  • Runtime heap fragmentation is avoided for statically allocated objects.
  • Useful for systems with strict memory constraints.

Limitations

  • Memory must be reserved before object creation.
  • Application code must manage storage lifetime.
  • Changing the number of objects at runtime is less flexible.

7. Dynamic Memory Allocation

Dynamic allocation obtains memory at runtime through an allocator. FreeRTOS provides heap implementations for supported allocation APIs.

Example: Dynamic Task Creation

TaskHandle_t sensorTaskHandle = NULL;

BaseType_t result;

result = xTaskCreate(
    SensorTask,
    "Sensor",
    256,
    NULL,
    2,
    &sensorTaskHandle
);

if (result != pdPASS)
{
    /* Handle task creation failure */
}

When successful, the kernel obtains the required memory for the task's internal control structure and stack through the configured allocation mechanism.

Advantages

  • Objects can be created when required.
  • Useful when object count varies during execution.
  • Reduces the need to reserve every object in advance.

Limitations

  • Allocation can fail at runtime.
  • Some heap strategies can suffer fragmentation.
  • Allocation and freeing can introduce timing variability.
  • Memory ownership and object lifetime must be controlled.

8. Static vs Dynamic Allocation

Feature Static Allocation Dynamic Allocation
Memory source Application-provided storage Configured allocator
Allocation time Storage reserved in advance Requested at runtime
Runtime allocation failure Not caused by a heap allocation for that object Possible
Flexibility Less flexible for changing object counts More flexible
Heap fragmentation Avoided for statically allocated objects Depends on allocator strategy
Memory planning Storage can be reserved explicitly Requires runtime allocation planning

Some embedded applications use a combination of static and dynamic allocation. The choice depends on system requirements, memory constraints and timing behavior.

9. FreeRTOS Heap Management

The FreeRTOS heap is an area of memory used by selected dynamic allocation APIs. FreeRTOS provides several heap implementation files with different allocation and freeing behavior.

Common Heap Implementations

Heap Characteristics
heap_1.c Allocates memory but does not free it. Simple and predictable after initialization.
heap_2.c Supports allocation and freeing but does not coalesce adjacent free blocks.
heap_3.c Wraps the standard C library malloc() and free() functions.
heap_4.c Supports allocation, freeing and coalescing adjacent free blocks.
heap_5.c Supports multiple non-contiguous heap regions and coalescing within regions.
Select one compatible heap implementation when using the corresponding FreeRTOS dynamic allocation functions. Do not compile multiple competing heap implementations together.

10. Memory Fragmentation

Memory fragmentation occurs when free memory is divided into separate blocks. The total free memory may be sufficient for a request, but no single suitable block may be available.

External Fragmentation Example

Initial Heap:

+--------------------------------------+
|              Free Memory             |
+--------------------------------------+

After Allocations:

+----------+--------+----------+--------+
| Block A  | Block B| Block C  | Block D|
+----------+--------+----------+--------+

After Freeing B and D:

+----------+--------+----------+--------+
| Block A  |  Free  | Block C  |  Free  |
+----------+--------+----------+--------+

Free memory exists in separate blocks.

A request for a large contiguous block can fail even when the sum of all free blocks is large enough.

Fragmentation Reduction Techniques

  • Prefer static allocation for long-lived objects where appropriate.
  • Reduce frequent allocation and freeing of different-sized blocks.
  • Use a suitable heap implementation.
  • Plan memory requirements before deployment.
  • Monitor free heap and allocation failures.
  • Use fixed-size memory pools when suitable.

11. Heap Size Configuration

Some FreeRTOS heap implementations use configTOTAL_HEAP_SIZE to define the available heap memory. 

#define configTOTAL_HEAP_SIZE (10 * 1024)

This example configures a 10 KB heap for heap implementations that use this macro.

Important Considerations

  • Heap memory is only part of total RAM usage.
  • Task stacks and static application variables also consume RAM.
  • Some heap implementations use different configuration mechanisms.
  • Alignment and port-specific requirements affect usable memory.

12. Memory Allocation Failure

A dynamic allocation request may fail if sufficient suitable memory is unavailable. FreeRTOS provides a hook that can be used to handle allocation failures when configured.

Malloc Failed Hook

#define configUSE_MALLOC_FAILED_HOOK 1

void vApplicationMallocFailedHook(void)
{
    /* Record failure or enter a safe error state */
    for (;;)
    {
    }
}

The hook is useful for diagnostics. The application's response should be designed according to its safety and recovery requirements.

Do not assume that every memory-allocation failure automatically invokes this hook. The configuration and allocation path must support it.

13. FreeRTOS Memory Monitoring APIs

FreeRTOS provides APIs that help an application inspect heap usage and task stack information.

API Purpose
xPortGetFreeHeapSize() Reports the amount of currently free heap memory where supported.
xPortGetMinimumEverFreeHeapSize() Reports the minimum free heap observed since startup where supported.
uxTaskGetStackHighWaterMark() Reports the minimum remaining stack space observed for a task, in stack words.
vTaskGetInfo() Provides task information when the required configuration is enabled.
These APIs are configuration- and port-dependent. Stack high-water marks are useful estimates of observed stack usage, not proof that every execution path is safe.

14. Memory Planning Example

Consider a controller with three application tasks. Assume StackType_t is four bytes and the selected implementation uses dynamically allocated task stacks and TCBs.

Task Stack Depth Stack Memory
Sensor Task 256 words 1024 bytes
Communication Task 384 words 1536 bytes
Control Task 256 words 1024 bytes
Total 896 words 3584 bytes

This calculation includes only the task stack storage. It does not include TCBs, queues, application buffers, timer service resources, interrupt stacks where applicable, or other system memory.

Do not use the sum of task stack sizes as the complete RAM requirement. Include all kernel, application and platform memory requirements.

15. Memory Management Best Practices

  • Estimate task stack requirements using realistic execution paths.
  • Measure stack high-water marks during representative testing.
  • Choose static or dynamic allocation deliberately.
  • Check every dynamic object-creation result.
  • Avoid unnecessary runtime allocation and freeing.
  • Use one appropriate heap implementation.
  • Monitor free heap and minimum-ever-free heap where supported.
  • Keep buffer ownership and object lifetime clear.
  • Reserve memory for interrupt and platform requirements.
  • Test memory behavior under maximum expected workload.

16. Practical Activity – Prepare a Memory Budget

Objective: Estimate RAM requirements for a small FreeRTOS application.

Procedure

  1. List the tasks required by the application.
  2. Estimate a stack depth for each task.
  3. Convert stack depths into bytes using sizeof(StackType_t).
  4. List the required queues and their storage sizes.
  5. List semaphore, mutex and event group objects.
  6. Include timer service resources if software timers are enabled.
  7. Include application buffers and global variables.
  8. Choose static or dynamic allocation for each object.
  9. Compare the estimated total with available RAM.

Expected Result

A memory budget showing estimated task stacks, kernel objects, application buffers and remaining memory margin. The estimate should be validated through build-map analysis and runtime testing on a supported target.
