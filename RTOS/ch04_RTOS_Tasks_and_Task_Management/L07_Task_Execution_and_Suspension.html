2. Introduction to Task Execution

Task execution refers to the process through which an RTOS schedules and runs application tasks.

In a multitasking system, several tasks may exist simultaneously. However, on a single-core processor, only one task can execute instructions at a time.

The scheduler decides which Ready task should receive processor time.

Example

Consider an embedded monitoring application containing:

  • Sensor Task – reads sensor values.
  • UART Task – processes serial communication.
  • Display Task – updates the display.

The RTOS manages these tasks according to their priority, state, and scheduling configuration.

Multitasking on a single-core microcontroller is achieved by switching CPU execution between tasks. It does not mean that all tasks execute simultaneously.

3. Role of the RTOS Scheduler

The scheduler is a kernel component responsible for selecting the task that should execute next.

Main Responsibilities

  • Maintain information about task states.
  • Identify Ready tasks.
  • Select an eligible task according to the scheduling policy.
  • Initiate a context switch when required.
  • Manage task execution after delays, events, and interrupts.

Basic Scheduling Flow

4. Task Execution States

A task moves through different states during its lifetime.

State Description
Ready Task is eligible for execution but is waiting for CPU time.
Running Task is currently executing on the processor.
Blocked Task is waiting for an event, delay, or timeout.
Suspended Task has been explicitly removed from scheduling until resumed.
Deleted Task has been removed from the active task set.

Task-state transitions are managed by the RTOS kernel and its scheduling mechanisms.

5. Task Execution Flow

A typical FreeRTOS task follows this execution pattern:

  1. The application creates the task.
  2. The task becomes Ready.
  3. The scheduler selects it for execution.
  4. The task executes its function.
  5. The task may block, yield, or be preempted.
  6. It becomes Ready again when its wait condition is satisfied.
  7. The scheduler selects it when appropriate.

6. Task Preemption

Preemption occurs when the scheduler stops the currently Running task and selects another Ready task.

In a preemptive priority-based scheduler, a newly Ready task with a higher priority can preempt the currently Running lower-priority task.

Example

Task Priority Initial State
Task A 2 Running
Task B 4 Blocked

When Task B's event occurs:

Before Event:
Task A: RUNNING
Task B: BLOCKED

After Event:
Task A: READY
Task B: RUNNING

This example assumes preemption is enabled and the scheduler is permitted to run. Actual switching may occur at the appropriate scheduling point.

7. Cooperative Task Execution

In cooperative scheduling, a task generally continues executing until it voluntarily yields, blocks, or otherwise allows another task to run.

Characteristics

  • Tasks explicitly give up processor time.
  • Task execution can be easier to reason about in simple systems.
  • A task that fails to yield or block may delay other tasks.
  • Responsiveness depends on task behavior.

Cooperative scheduling differs from preemptive scheduling because a higher-priority task becoming Ready does not necessarily interrupt the current task immediately.

8. Blocking a Task

A task becomes Blocked when it waits for a condition, event, resource, or time interval.

Common Reasons for Blocking

  • Waiting for a specified delay.
  • Waiting for data in a queue.
  • Waiting for a semaphore.
  • Waiting for a task notification.
  • Waiting for an event group condition.

FreeRTOS Delay Example

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

After reading the sensor, the task enters the Blocked state for the requested delay. Other eligible Ready tasks can execute during that period.

Blocking is usually preferable to continuously polling or busy-waiting when a task is waiting for an event or time interval.

9. Task Suspension

Task suspension is an explicit operation that prevents a task from being selected for execution.

A suspended task remains in the system but is removed from normal scheduling until it is resumed.

FreeRTOS Suspension API

vTaskSuspend(TaskHandle_t xTaskToSuspend);

To suspend the currently executing task:

vTaskSuspend(NULL);

To suspend another task, pass its valid task handle.

Important Characteristics

  • A suspended task does not execute.
  • It does not automatically resume when a delay expires.
  • It requires an explicit resume operation.
  • Its task resources remain allocated.
  • It can retain application resources, so ownership must be considered carefully.

10. Task Resumption

Task resumption makes an explicitly suspended task eligible for scheduling again.

FreeRTOS Resume API

vTaskResume(TaskHandle_t xTaskToResume);

Example

TaskHandle_t displayHandle;

/* Resume the Display task. */
vTaskResume(displayHandle);

After resumption, the task becomes Ready. It does not necessarily execute immediately; the scheduler selects it according to priority and scheduling rules.

vTaskResume() is not an ISR API. If a task must be resumed from an interrupt, use xTaskResumeFromISR() where supported, or consider a task notification or semaphore for event communication.

11. Difference Between Blocking and Suspension

Blocking Suspension
Task waits for an event, delay, or condition. Task is explicitly suspended.
May become Ready automatically when its wait condition is satisfied. Requires an explicit resume operation.
Can have a timeout. Does not have an automatic timeout.
Examples: queue receive and task delay. Examples: vTaskSuspend().

These states are not interchangeable. A blocked task waits for a defined condition; a suspended task is waiting for an explicit control operation.

12. FreeRTOS Task Suspension APIs

API Purpose
vTaskSuspend() Suspends a task.
vTaskResume() Resumes an explicitly suspended task.
xTaskResumeFromISR() Resumes a task from an ISR where supported.
vTaskDelay() Blocks the calling task for a relative delay.
vTaskDelayUntil() Blocks the calling task until an absolute tick-based wake time.

API availability and behavior can depend on the FreeRTOS version, port, and configuration.

13. Suspending and Resuming a Task – Complete Example

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t displayHandle;

void DisplayTask(void *pvParameters)
{
    for (;;)
    {
        Update_Display();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ControlTask(void *pvParameters)
{
    for (;;)
    {
        if (Should_Stop_Display())
        {
            vTaskSuspend(displayHandle);
        }

        if (Should_Start_Display())
        {
            vTaskResume(displayHandle);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    Hardware_Init();

    xTaskCreate(
        DisplayTask,
        "Display",
        128,
        NULL,
        1,
        &displayHandle
    );

    xTaskCreate(
        ControlTask,
        "Control",
        128,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Explanation:

  1. DisplayTask periodically updates the display.
  2. ControlTask checks the application conditions.
  3. When the stop condition is true, it suspends DisplayTask.
  4. When the start condition is true, it resumes DisplayTask.
  5. The scheduler selects eligible Ready tasks according to their priorities.
The example uses illustrative application functions. A production implementation should avoid repeatedly suspending or resuming a task unnecessarily and should define how shared resources are handled.

14. Suspending the Scheduler

FreeRTOS also provides APIs to suspend and resume scheduler activity:

vTaskSuspendAll();

/* Short, bounded operation that must not yield. */

xTaskResumeAll();

These functions are different from suspending an individual task.

Task Suspension Scheduler Suspension
Stops a selected task from being scheduled. Temporarily prevents normal task switching.
Uses vTaskSuspend(). Uses vTaskSuspendAll().
Resumed using vTaskResume(). Scheduler operation is resumed using xTaskResumeAll().
Scheduler suspension is not equivalent to disabling interrupts or entering a critical section. It does not make arbitrary code safe from interrupt access, and it should be kept short.

15. Task Yielding

Yielding means voluntarily giving other eligible tasks an opportunity to execute.

FreeRTOS API

taskYIELD();

Yielding does not mean that the calling task is permanently suspended or blocked.

If another eligible task has a higher priority, it may execute. If no suitable task is available, the calling task may continue running.

17. Common Programming Mistakes

  • Confusing a Blocked task with a Suspended task.
  • Assuming a resumed task executes immediately.
  • Calling vTaskResume() from an ISR.
  • Suspending a task while it owns a mutex or shared resource.
  • Using scheduler suspension as a replacement for critical sections.
  • Creating a high-priority task that never blocks or yields.
  • Failing to check task creation results and task handles.
  • Assuming that task suspension disables hardware interrupts.

19. Lesson Summary

  • The scheduler selects which Ready task should execute.
  • Only one task executes at a time on a single-core processor.
  • Preemption allows a suitable higher-priority task to take CPU time.
  • Blocking occurs when a task waits for an event, delay, or condition.
  • Suspension explicitly removes a task from normal scheduling.
  • vTaskSuspend() suspends a task.
  • vTaskResume() resumes an explicitly suspended task.
  • vTaskDelay() blocks a task for a relative time.
  • taskYIELD() voluntarily gives other eligible tasks an opportunity to execute.
  • vTaskSuspendAll() suspends scheduler activity, not an individual task.
