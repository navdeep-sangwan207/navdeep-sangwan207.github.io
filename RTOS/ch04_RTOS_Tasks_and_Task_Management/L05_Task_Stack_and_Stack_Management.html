2. Introduction to Stack Memory

A stack is a region of memory used for temporary data storage during program execution.

It follows the Last In, First Out (LIFO) principle. The most recently stored item is normally the first item removed.

Common Uses of a Stack

  • Function call information.
  • Local variables.
  • Function parameters, depending on the calling convention.
  • Return addresses.
  • Saved processor registers.
  • Interrupt and exception context information.
Every task needs an execution context. In a typical RTOS, each task has its own stack so that it can be paused and later resumed correctly.

3. Stack Organization

A stack is managed using a stack pointer (SP), which identifies the current stack position.

          STACK MEMORY
      +----------------------+
      | Previous stack data  |
      +----------------------+
      | Local variables      |
      +----------------------+
      | Saved registers      |
      +----------------------+
      | Return address       |
      +----------------------+
      | Function parameters  |
      +----------------------+
      |                      |
      | Current stack area   |
      +----------------------+
              ^
              |
        Stack Pointer (SP)

This is a conceptual representation. Actual stack layout depends on the processor architecture, ABI, compiler, and calling convention.

Stack Pointer

The stack pointer is a processor register that tracks the current stack position.

On ARM7TDMI-S, register R13 is used as the stack pointer (SP). Different processor modes can have banked stack-pointer registers.

4. Stack Growth Direction

Depending on the processor architecture, a stack can grow toward higher or lower memory addresses.

Descending Stack

A descending stack grows toward lower memory addresses as data is pushed.

Higher Address
+------------------+
| Older Stack Data |
+------------------+
| New Stack Data   |
+------------------+
        |
        v
Lower Address

Stack grows downward.

Ascending Stack

An ascending stack grows toward higher memory addresses as data is pushed.

Higher Address
        ^
        |
| New Stack Data   |
+------------------+
| Older Stack Data |
+------------------+
Lower Address

Stack grows upward.

ARM processors support multiple stack modes through their architecture and software configuration. The actual stack behavior must be determined from the selected processor mode and RTOS port.

5. Function Calls and Stack Frames

A stack frame is the portion of a stack used by a particular function invocation.

When a function is called, the processor and compiler may use the stack to preserve information needed to return to the calling function.

Example in C

void FunctionB(void)
{
    int value = 20;
}

void FunctionA(void)
{
    int number = 10;

    FunctionB();
}

int main(void)
{
    FunctionA();

    return 0;
}

Conceptual Execution

  1. main() calls FunctionA().
  2. A stack frame for FunctionA() may be established.
  3. FunctionA() calls FunctionB().
  4. A stack frame for FunctionB() is established.
  5. FunctionB() returns and its frame is released.
  6. FunctionA() returns to main().
Stack-frame details are compiler- and ABI-dependent. Some local variables may be held in registers or optimized away instead of being stored on the stack.

6. Process Stack vs Task Stack

In a general-purpose operating system, a process may contain multiple threads. Each thread normally has its own execution stack.

In an RTOS, each independently scheduled task normally has its own stack.

Process / Thread Model RTOS Task Model
A process contains one or more threads. An RTOS application contains multiple tasks.
Each thread normally has its own stack. Each task normally has its own stack.
Threads in a process share its address space. Tasks may share the application's memory address space unless protection is provided.
OS manages thread execution context. RTOS kernel manages task execution context.

7. Why Does Each RTOS Task Need Its Own Stack?

Consider two tasks:

  • Task A reads sensor values.
  • Task B sends information through UART.

Task A may be interrupted or preempted while executing a function. Task B may then execute before Task A resumes.

Each task must preserve its own execution information so that the scheduler can restore the correct context.

             RTOS APPLICATION
                    |
          +---------+---------+
          |                   |
       Task A              Task B
          |                   |
      Stack A              Stack B
          |                   |
      Local data           Local data
      Return state         Return state
      Saved context        Saved context
Separate task stacks prevent one task's normal function-call activity from overwriting another task's stack.

8. What Is Stored in a Task Stack?

Depending on the processor and compiler, a task stack may contain:

Stack Content Purpose
Local Variables Stores temporary function data when allocated on the stack.
Return Addresses Supports returning from function calls.
Saved Registers Preserves processor register values.
Function Call Data Supports function parameters and calling conventions.
Exception Context May preserve processor state during interrupt handling.
Temporary Data Stores intermediate values and compiler-generated data.

Not every item is necessarily stored on the stack. Register allocation, optimization, and processor-specific context handling determine the actual layout.

9. FreeRTOS Task Stack Allocation

FreeRTOS allocates a stack for every task. The stack is used for function calls, local variables, saved context, and other execution data.

With dynamic task creation, the kernel's configured memory allocator supplies the required task-control and stack memory.

With static task creation, the application supplies the stack buffer and TCB buffer.

Dynamic Allocation Example

xTaskCreate(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    NULL
);

Static Allocation Example

static StackType_t sensorStack[128];
static StaticTask_t sensorTCB;

TaskHandle_t sensorHandle;

sensorHandle = xTaskCreateStatic(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    sensorStack,
    &sensorTCB
);
In common FreeRTOS APIs, task stack depth is expressed in StackType_t elements (stack words), not bytes. The size of StackType_t is target-dependent. Always check the selected port's definitions.

10. Stack Size Calculation

To estimate task stack memory, multiply the requested stack depth by the size of one StackType_t element.

Formula:

Stack Memory (bytes) =
Stack Depth × sizeof(StackType_t)

Example

Assume a target where sizeof(StackType_t) = 4 bytes.

For a task stack depth of 128 elements:

Stack Memory = 128 × 4
             = 512 bytes

For three tasks:

Task Stack Depth Stack Memory
Sensor 128 elements 512 bytes
UART 256 elements 1024 bytes
Display 384 elements 1536 bytes
Total 768 elements 3072 bytes

This calculation covers only the task stacks. TCB memory, idle task stack, timer service task stack, kernel objects, and other application memory must be accounted for separately.

11. Stack Size Selection

Stack size must be selected according to the task's maximum execution-path requirements.

Factors Affecting Stack Usage

  • Number and depth of function calls.
  • Local arrays and local structures.
  • Nested function calls.
  • Recursive functions.
  • Compiler-generated temporary storage.
  • Interrupt and exception handling requirements.
  • Library functions such as formatted input/output.
  • Context-switch and port-specific stack requirements.
Avoid choosing a stack size only by trial and error. Use compiler stack-usage information where available, inspect worst-case call paths, and validate with runtime monitoring.

12. Stack Overflow

Stack overflow occurs when a task uses more stack memory than has been allocated to it.

When a stack exceeds its allocated boundary, it may overwrite adjacent memory or corrupt application and kernel data.

Common Causes

  • Insufficient task stack allocation.
  • Large local arrays.
  • Deep function-call chains.
  • Uncontrolled recursion.
  • Large local structures.
  • Unexpected library-function stack usage.
  • Incorrect stack-depth calculations.

Possible Symptoms

  • Unexpected processor exceptions.
  • Corrupted variables.
  • Incorrect task behavior.
  • System crashes or resets.
  • Unpredictable execution.

13. Stack Overflow Detection in FreeRTOS

FreeRTOS provides configurable stack-overflow checking.

The configuration option is:

#define configCHECK_FOR_STACK_OVERFLOW 2

Common settings include:

Setting Meaning
0 Stack overflow checking disabled.
1 Basic stack pointer boundary checking at relevant task-switch points.
2 Additional stack-fill pattern checking at relevant task-switch points.

When checking is enabled, the application can provide a hook function:

void vApplicationStackOverflowHook(
    TaskHandle_t xTask,
    char *pcTaskName
)
{
    /* Record diagnostic information. */

    taskDISABLE_INTERRUPTS();

    for (;;)
    {
        /* Halt for debugging. */
    }
}
Stack-overflow checking is diagnostic protection, not a complete memory-safety guarantee. It may detect corruption only after it has occurred, and exact checks depend on the FreeRTOS port and version.

14. Stack High-Water Mark Monitoring

FreeRTOS provides an API for measuring the minimum amount of unused stack observed since a task started.

The API is:

UBaseType_t uxTaskGetStackHighWaterMark(
    TaskHandle_t xTask
);

Example

UBaseType_t remainingStack;

remainingStack =
    uxTaskGetStackHighWaterMark(sensorHandle);

In common FreeRTOS implementations, the returned value is expressed in StackType_t units (words), not bytes.

Example Calculation

Assume:

  • Allocated stack depth = 256 elements.
  • Minimum observed unused stack = 64 elements.
  • StackType_t size = 4 bytes.
Minimum unused stack = 64 × 4
                     = 256 bytes

Maximum observed stack usage =
(256 - 64) × 4

= 192 × 4
= 768 bytes
The high-water mark reports the minimum unused stack observed during execution. It does not prove that every possible execution path has been tested or that future stack usage cannot exceed the observed maximum.

15. Stack vs Heap

Stack and heap are different memory regions with different purposes.

Stack Heap
Used for function execution context and temporary data. Used for dynamic memory allocation.
Typically managed automatically by function calls and task execution. Managed through allocation and deallocation routines.
Each RTOS task normally has its own stack. May be shared by multiple allocation requests.
Overflow can corrupt adjacent memory. Exhaustion or fragmentation can cause allocation failure.
Stack size is planned for each task. Heap size is planned for dynamic memory needs.

16. Stack Management Best Practices

  • Estimate stack requirements for every task.
  • Avoid large local arrays when static or shared buffers are more appropriate.
  • Avoid uncontrolled recursion in embedded applications.
  • Use stack-overflow checking during development.
  • Monitor task stack high-water marks.
  • Inspect compiler-generated stack-usage reports where available.
  • Consider interrupt and exception stack requirements separately where applicable.
  • Retest after changes to compiler options, libraries, or application code.
  • Do not assume a stack size suitable for one processor port is suitable for another.

17. LPC2129 and ARM7 Stack Registers

The LPC2129 is based on the ARM7TDMI-S processor core.

Important ARM7 registers include:

Register Purpose
R13 (SP) Stack Pointer.
R14 (LR) Link Register, commonly stores a return address.
R15 (PC) Program Counter.
CPSR Current Program Status Register.
SPSR Saved Program Status Register in exception modes.

ARM7 exception modes have banked registers, including mode-specific stack pointers. An RTOS port must correctly initialize and preserve the processor context required by its scheduler.

Keil uVision Practical

  1. Create a simple C program with nested function calls.
  2. Build the program with debug information.
  3. Start a debug session.
  4. Inspect R13 (SP), R14 (LR), and R15 (PC) where supported.
  5. Step through function calls and returns.
  6. Observe changes in the stack pointer and memory window.
A Keil stack-inspection exercise demonstrates ARM7 function-call behavior. It does not establish that a compatible FreeRTOS ARM7 port is available or running.

18. Lesson Summary

  • A stack is a LIFO memory structure used during program execution.
  • Each RTOS task normally has its own stack.
  • The stack pointer tracks the current stack position.
  • Function calls may use stack frames for local data and saved execution state.
  • FreeRTOS stack depth is commonly specified in StackType_t units.
  • Stack memory depends on stack depth and the size of StackType_t.
  • Stack overflow occurs when allocated stack capacity is exceeded.
  • FreeRTOS provides stack-overflow checking options.
  • uxTaskGetStackHighWaterMark() helps monitor unused stack.
  • Stack and heap are separate memory-management concepts.
  • Careful stack sizing and runtime testing improve system reliability.
