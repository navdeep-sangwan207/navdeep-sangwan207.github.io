After completing this lesson, you will be able to:

  • Understand the task-state model in an RTOS.
  • Explain Ready, Running, Blocked, and Suspended states.
  • Understand how a task moves between states.

  • Understand preemption and task blocking.
  • Explain the relationship between task states and scheduling.
  • Understand FreeRTOS task states and APIs.

2. Introduction to Task States

A task in an RTOS does not execute continuously. Depending on processor availability, scheduling decisions, delays, and events, it moves through different execution states.

The task-state model describes the current scheduling condition of a task.

For example, consider a temperature-monitoring application:

  • The sensor task becomes ready when created.
  • The scheduler selects it for execution.
  • It runs and reads the sensor.
  • It may block while waiting for a timer or event.
  • After the wait completes, it becomes ready again.
Task states help the RTOS determine which tasks can execute and which tasks must wait.

3. Main Task States

A commonly used RTOS task-state model contains four main states.

State Description
Ready The task is eligible to execute but is waiting for processor time.
Running The task is currently executing on the CPU.
Blocked The task is waiting for an event, resource, or timeout.
Suspended The task has been explicitly suspended and is not eligible for scheduling.

4. Ready State

A task is in the Ready state when it can execute but the processor is currently executing another task or handling another activity.

Example

Suppose Task A is executing and Task B is created. Task B becomes ready and waits until the scheduler selects it.

Task A: RUNNING
Task B: READY

CPU is executing Task A.

Task B is eligible to execute
but is waiting for CPU time.

When Does a Task Become Ready?

  • After successful task creation.
  • After a delay period expires.
  • After the awaited event occurs.
  • After a suspended task is resumed.
  • After a resource becomes available.

5. Running State

A task is in the Running state when it is currently executing on the processor.

Example

Task A: RUNNING
Task B: READY
Task C: BLOCKED

CPU executes Task A.

Task B waits for processor time.
Task C waits for an event.

Important Characteristics

  • The task executes its instructions.
  • It can call functions and perform calculations.
  • It may become blocked by waiting for an event.
  • It may be preempted by a higher-priority ready task.
  • It may voluntarily yield the processor.
On a single-core processor, only one task can be in the Running state at a time, although interrupts may temporarily execute outside normal task execution.

6. Blocked State

A task enters the Blocked state when it cannot continue until a particular event occurs or a specified waiting period expires.

Common Reasons for Blocking

  • Waiting for a queue message.
  • Waiting for a semaphore.
  • Waiting for a mutex.
  • Waiting for a task notification.
  • Waiting for a delay or timeout to expire.

Example

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();

        /* Task blocks for 100 ms */
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

During the delay, the task is not eligible to execute. Other ready tasks can use the processor.

Blocking is different from busy waiting. A properly blocked task does not continuously consume CPU time checking whether an event has occurred.

7. Suspended State

A task enters the Suspended state when it is explicitly suspended by the RTOS or an authorized application operation.

Example

vTaskSuspend(sensorHandle);

/* Sensor task is suspended. */

/* Resume the task when required. */
vTaskResume(sensorHandle);

Characteristics

  • A suspended task is not eligible for execution.
  • It does not become ready merely because a delay expires.
  • It must be resumed explicitly.
  • It retains its task context while suspended.
In FreeRTOS, the suspended state is distinct from the blocked state. Suspending a task is an explicit control operation, whereas blocking normally occurs while waiting for a condition or timeout.

9. Ready to Running Transition

A task moves from Ready to Running when the scheduler selects it for execution.

Example

Task Priority Initial State
Task A 3 Ready
Task B 2 Ready
Task C 1 Ready

Assuming a preemptive priority-based scheduler and that larger numbers represent higher priorities, Task A is selected first.

Task A: READY  ---> RUNNING
Task B: READY
Task C: READY

10. Running to Ready Transition

A running task can return to the Ready state when it is preempted or voluntarily yields the processor.

Common Causes

  • A higher-priority task becomes ready.
  • The running task voluntarily yields.
  • Time slicing selects another equal-priority task, if configured.

Example

Before Preemption:

Task A: RUNNING
Task B: BLOCKED

An event makes Task B ready.
Task B has higher priority.

After Preemption:

Task A: READY
Task B: RUNNING

The scheduler selects Task B, and Task A can resume when it becomes the selected ready task again.

11. Running to Blocked Transition

A running task enters the Blocked state when it waits for a condition or event that is not currently satisfied.

Examples

  • Calling vTaskDelay().
  • Waiting for data from a queue.
  • Waiting for a semaphore.
  • Waiting to acquire a mutex.
Task A: RUNNING

Task A calls:
xQueueReceive(queue, &data, portMAX_DELAY);

No message is available.

Task A: BLOCKED

When the required queue message arrives, Task A becomes ready. It does not necessarily run immediately; the scheduler still decides which ready task executes.

12. Blocked to Ready Transition

A blocked task becomes ready when its waiting condition is satisfied or its timeout expires.

Example: Queue Communication

Receiver Task:
Waits for a queue message.

Sender Task:
Places a message in the queue.

Result:
Receiver Task becomes READY.

Scheduler:
Selects the receiver when appropriate.

The transition from Blocked to Ready does not guarantee immediate execution.

13. Ready to Suspended and Suspended to Ready

A task can be explicitly suspended even when it is ready to execute.

READY
  |
  | vTaskSuspend()
  v
SUSPENDED
  |
  | vTaskResume()
  v
READY

In FreeRTOS, vTaskSuspend() removes the task from normal scheduling eligibility. vTaskResume() makes a suspended task ready again.

A task that is suspended while blocked may also need to be explicitly resumed; do not assume that the awaited event alone makes it eligible to execute.

14. Task State vs Task Priority

Task state and task priority are different properties.

Task State Task Priority
Describes the task's scheduling condition. Describes its relative scheduling importance.
Can be Ready, Running, Blocked, or Suspended. Can be configured to different levels.
Changes because of execution, waiting, or control operations. Changes through priority configuration or management APIs.
Determines whether the task is eligible to run. Helps decide which eligible task runs first.
A high-priority task in the Blocked state cannot execute until it becomes ready. A lower-priority ready task may execute in the meantime.

15. FreeRTOS Task States

FreeRTOS documents several task states:

FreeRTOS State Description
Running The task currently executing on the processor.
Ready The task can execute but is waiting for processor time.
Blocked The task waits for an event or timeout.
Suspended The task is explicitly suspended.
Deleted The task has been deleted and is no longer an active scheduled task.

Deleted is generally treated as a task lifecycle condition rather than one of the four main active scheduling states.

16. FreeRTOS APIs Related to Task States

API Purpose
xTaskCreate() Creates a task.
vTaskDelay() Places the calling task into a delayed blocked state.
vTaskDelayUntil() Provides periodic delay behavior using an absolute tick reference.
vTaskSuspend() Suspends a task.
vTaskResume() Resumes a suspended task.
xTaskResumeFromISR() Requests resumption of a suspended task from an ISR, where supported.
vTaskDelete() Deletes a task.
eTaskGetState() Returns the state of a task when the relevant configuration is enabled.
Some task-state inspection and ISR-related APIs depend on FreeRTOS configuration and processor port. Always consult the documentation for the selected FreeRTOS version.

17. Example: Task-State Changes Using FreeRTOS

The following example demonstrates a task entering a delayed state periodically.

#include "FreeRTOS.h"
#include "task.h"

void MonitorTask(void *pvParameters)
{
    for (;;)
    {
        /* Task is executing */
        Read_System_Status();

        /* Task enters Blocked state */
        vTaskDelay(pdMS_TO_TICKS(500));

        /* Task becomes Ready after the delay */
        /* Scheduler selects it when appropriate */
    }
}

int main(void)
{
    Hardware_Init();

    xTaskCreate(
        MonitorTask,
        "Monitor",
        128,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Expected Conceptual Behavior

  1. The task is created and becomes Ready.
  2. The scheduler selects it and it enters Running.
  3. It executes Read_System_Status().
  4. It calls vTaskDelay() and becomes Blocked.
  5. After the delay expires, it becomes Ready.
  6. The scheduler selects it again when appropriate.

Hardware_Init() and Read_System_Status() are application-specific functions and must be implemented separately.

18. Numerical Example: Task-State Timeline

Assume Task A executes for 2 ms and then blocks for 5 ms. Ignore context-switch overhead for this illustration.

Time Task A State Explanation
0 ms Ready Task has become eligible.
0–2 ms Running Task executes.
2–7 ms Blocked Task waits for 5 ms.
7 ms Ready Delay expires.
After 7 ms Running or Ready Depends on scheduler and competing tasks.

The task does not necessarily execute immediately at 7 ms. Its actual execution depends on scheduling conditions.

19. Common Mistakes in Understanding Task States

  • Assuming every ready task executes immediately.
  • Confusing Blocked and Suspended states.
  • Assuming a high-priority blocked task executes before ready tasks.
  • Assuming task delay consumes CPU continuously.
  • Assuming an event waking a task guarantees immediate execution.
  • Confusing task priority with task state.
  • Assuming a timer interrupt always causes a context switch.

20. LPC2129 and Keil uVision Practical

The LPC2129 uses an ARM7TDMI-S core. Task-state concepts can be studied independently of a specific RTOS port.

Suggested Exercises

  1. Create a simple C program with separate functions representing sensor, communication, and display activities.
  2. Use a software state variable to model Ready, Running, Blocked, and Suspended states.
  3. Use a timer counter or simulated time variable to model a delay.
  4. Step through the program in Keil uVision.
  5. Observe how state variables change as events are simulated.
  6. Draw the corresponding state-transition diagram.
A software state-machine exercise demonstrates task-state logic, not an actual RTOS scheduler. Do not interpret it as proof of FreeRTOS execution or real-time timing on LPC2129.

21. Lesson Summary

  • Task states describe the current scheduling condition of a task.
  • Ready tasks are eligible to execute.
  • Running tasks are currently executing on the CPU.
  • Blocked tasks wait for an event or timeout.
  • Suspended tasks require an explicit resume operation.
  • Task-state transitions occur because of scheduling, blocking, events, and control operations.
  • A task becoming Ready does not guarantee immediate execution.
  • Priority and state are different task properties.
  • FreeRTOS provides APIs to delay, suspend, resume, and delete tasks.
  • Task-state knowledge is essential for designing reliable RTOS applications.
