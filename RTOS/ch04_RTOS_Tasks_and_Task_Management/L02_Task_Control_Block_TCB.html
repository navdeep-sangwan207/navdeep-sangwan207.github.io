2. Introduction to Task Control Block

A Task Control Block (TCB) is a data structure maintained by an RTOS kernel to store information required to manage a task.

When an RTOS creates a task, it needs to maintain information about that task, including:

  • Task priority.
  • Task execution state.
  • Stack information.
  • Processor context.
  • Scheduling information.
  • Task-specific parameters and attributes.
The TCB acts as the kernel's record of a task. It allows the RTOS to track, schedule, suspend, resume, and manage task execution.

3. Why Is a TCB Required?

Consider an embedded system containing three tasks:

Task A: Sensor Monitoring
Task B: UART Communication
Task C: Display Updating

The RTOS must maintain separate information for each task.

For example:

  • Which task is ready to execute?
  • What is the priority of each task?
  • Where should a task resume after a context switch?
  • Which stack belongs to each task?
  • Is a task running, ready, or blocked?

The TCB provides the data needed by the kernel to answer these questions.

4. Basic TCB Architecture

Each task generally has an associated TCB and stack.

              RTOS Kernel
                   |
        +----------+----------+
        |          |          |
        v          v          v
      TCB A      TCB B      TCB C
        |          |          |
        v          v          v
      Stack A   Stack B    Stack C
        |          |          |
        v          v          v
      Task A    Task B     Task C

The kernel uses the TCB to manage the corresponding task and its execution context.

5. Typical Information Stored in a TCB

TCB Information Purpose
Stack Pointer Identifies the current or saved stack position.
Task Priority Helps the scheduler select tasks.
Task State Tracks whether the task is ready, running, blocked, or suspended.
Task Identifier Identifies a task within the RTOS.
Scheduling Information Supports ready lists, delay lists, and scheduling operations.
Task Parameters Maintains relevant task-specific information.
Processor Context Stores or references the state required to resume execution.
Resource and Runtime Information May track additional task attributes and resource information.

The exact TCB fields differ between RTOS implementations and processor ports. Not every listed item must be a separate field in every TCB.

6. Stack Pointer in the TCB

The stack pointer identifies the current position of a task's stack.

Each task normally has its own stack so that it can maintain its local variables, function-call information, and saved execution context independently.

Example

Task A Stack:
+-------------------+
| Local Variables   |
| Function Data     |
| Saved Registers   |
| Return Addresses  |
+-------------------+
        ^
        |
   Stack Pointer
        |
     TCB A

When the task is interrupted or switched out, the processor and RTOS port preserve the required context. The saved stack pointer allows the task to resume later.

The stack pointer is especially important during context switching because it identifies where the task's saved execution context can be restored.

7. Task Priority in the TCB

The TCB typically contains or provides access to information about task priority.

Example

Task Priority Function
Task A 3 Safety monitoring
Task B 2 Sensor acquisition
Task C 1 Display update

In this illustrative configuration, a larger priority number represents a higher priority.

The scheduler uses priority information when determining which ready task should execute.

8. Task State Information

The RTOS maintains information about the current state of each task.

Common task states include:

  • Running: Currently executing on the processor.
  • Ready: Eligible to execute but waiting for processor time.
  • Blocked: Waiting for an event, resource, or timeout.
  • Suspended: Explicitly removed from scheduling until resumed.

The TCB is associated with the information used to manage these state transitions. In many RTOS designs, list membership and other kernel structures also contribute to tracking task state.

9. TCB and Context Switching

Context switching occurs when the processor stops executing one task and begins executing another.

Context-Switching Sequence

Task A is Running
       |
       v
Context Switch Triggered
       |
       v
Save Task A Context
       |
       v
Update Task A TCB
       |
       v
Scheduler Selects Task B
       |
       v
Load Task B Context
       |
       v
Update Running Task
       |
       v
Task B Resumes Execution

Role of the TCB

  1. Provides the saved stack pointer and task information.
  2. Helps the kernel track the task being switched out.
  3. Provides access to the next task's saved context.
  4. Supports restoration of the selected task.

The exact register-saving sequence is processor- and port-specific.

10. TCB Memory Organization

A task generally requires memory for its TCB and its stack.

RTOS Task Memory
       |
       +-------------------+
       |                   |
       v                   v
  Task Control Block    Task Stack
       |                   |
       v                   v
  Priority             Local Variables
  State                Function Calls
  Stack Pointer        Saved Context
  Scheduling Data      Return Information

Memory Considerations

  • Each task requires an appropriately sized stack.
  • TCB memory is additional to task stack memory.
  • Dynamic allocation may allocate both structures from an RTOS heap.
  • Static allocation allows the application to provide memory explicitly where supported.
  • Memory usage should be estimated before creating many tasks.

11. TCB Creation in FreeRTOS

In FreeRTOS, task creation causes the kernel to initialize the task's control information and stack.

Example: Task Creation

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    xTaskCreate(
        SensorTask,
        "Sensor",
        128,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

What Happens During Task Creation?

  1. The application calls xTaskCreate().
  2. FreeRTOS allocates or obtains the required task memory.
  3. The task stack is initialized.
  4. The task's control information is initialized.
  5. The task is added to the appropriate kernel scheduling structure.
  6. The task becomes eligible for scheduling.

The exact internal operations depend on the FreeRTOS version, memory-allocation method, and processor port.

12. FreeRTOS TCB Structure

FreeRTOS maintains an internal task control structure commonly referred to as TCB_t in its kernel source.

The internal definition is implementation-specific and may change between releases.

Conceptual Structure

typedef struct
{
    StackType_t *pxTopOfStack;

    /* Task state and priority information */

    /* Scheduling list items */

    /* Task name and configuration data */

    /* Additional port-specific information */

} TCB_t;

This is a simplified illustration, not a complete or compilable definition of the actual FreeRTOS TCB.

Important Internal Concepts

  • pxTopOfStack represents the saved top-of-stack pointer.
  • Priority information supports task scheduling.
  • List items support membership in ready, delayed, or other kernel lists.
  • Additional fields may store task names, runtime statistics, and port-specific data.
Application code should normally use documented FreeRTOS APIs rather than directly accessing or modifying internal TCB fields.

13. Static and Dynamic TCB Allocation

Dynamic Allocation

In dynamic task creation, FreeRTOS obtains memory for the TCB and stack using the configured memory-allocation implementation.

xTaskCreate(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    NULL
);

Static Allocation

In static task creation, the application provides the memory used for the task stack and its control structure.

static StaticTask_t sensorTCB;

static StackType_t sensorStack[128];

TaskHandle_t sensorHandle;

sensorHandle = xTaskCreateStatic(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    sensorStack,
    &sensorTCB
);

Static allocation requires the appropriate FreeRTOS configuration, including support for static allocation.

Dynamic Allocation Static Allocation
Memory obtained at runtime. Memory supplied by the application.
Uses configured heap implementation. Uses declared memory regions or objects.
Allocation can fail if memory is insufficient. Memory availability is determined during design and build.
Flexible task creation. More explicit memory planning.

14. Task Handle and TCB

A FreeRTOS task handle is an application-facing reference to a task. It allows the application to identify a task when calling relevant kernel APIs.

Example

TaskHandle_t sensorHandle = NULL;

xTaskCreate(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    &sensorHandle
);

The task handle is not the TCB itself. It provides a reference used by the kernel to locate and manage the corresponding task.

Common APIs Using Task Handles

  • vTaskDelete()
  • vTaskSuspend()
  • vTaskResume()
  • vTaskPrioritySet()
  • uxTaskPriorityGet()

15. TCB vs PCB

Operating systems use control structures to maintain information about execution entities.

Feature TCB PCB
Full Form Task Control Block Process Control Block
Used By RTOS or task-based kernel Process-based operating system
Information Task context and scheduling data Process state and resource information
Memory Management Depends on RTOS and hardware architecture Typically includes process address-space information
Purpose Manage task execution Manage process execution and resources

TCB and PCB are related concepts, but their structures and responsibilities depend on the operating system architecture.

16. Advantages of TCB

  • Maintains organized task information.
  • Supports task scheduling.
  • Enables context switching.
  • Helps track task states.
  • Supports priority management.
  • Provides a structured mechanism for task management.
  • Allows the kernel to manage multiple tasks independently.

17. Practical Memory Calculation

Suppose an embedded application creates four tasks.

Task Stack Allocation
Sensor Task256 bytes
UART Task384 bytes
Display Task512 bytes
Control Task256 bytes
Total Stack Memory =
256 + 384 + 512 + 256

= 1408 bytes

If each TCB requires an illustrative 100 bytes:

Total TCB Memory =
4 x 100

= 400 bytes

Combined Memory =
1408 + 400

= 1808 bytes
The 100-byte TCB size is only an assumed value for this calculation. Actual TCB size depends on the RTOS version, processor port, compiler, configuration, and enabled features. Real applications also require memory for queues, timers, drivers, application data, and other objects.

19. Lesson Summary

  • TCB stands for Task Control Block.
  • It is a kernel data structure associated with a task.
  • It maintains task-related information such as priority and stack pointer.
  • It supports task scheduling and context switching.
  • Each task generally has its own stack.
  • FreeRTOS uses an internal structure commonly called TCB_t.
  • A task handle is a reference to a task, not the TCB itself.
  • TCB and stack memory can be allocated statically or dynamically.
  • Internal TCB fields are implementation-specific.
  • Applications should use documented RTOS APIs instead of modifying internal TCB fields.
