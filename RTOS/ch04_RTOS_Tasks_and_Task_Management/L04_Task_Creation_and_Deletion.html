2. Introduction to Task Creation

Task creation is the process of defining and initializing an independent unit of execution managed by an RTOS.

Consider an embedded monitoring system that performs several operations:

  • Reads temperature from a sensor.
  • Receives commands through UART.
  • Updates an LCD display.
  • Monitors system conditions.

These activities can be implemented as separate tasks. The RTOS manages their execution according to scheduling rules.

Creating a task does not necessarily mean that it starts executing immediately. It normally becomes Ready and executes when selected by the scheduler.

4. Task Function Structure

A task is implemented as a function that the RTOS invokes when the task begins execution.

General C Structure

void TaskFunction(void *pvParameters)
{
    for (;;)
    {
        /* Task operations */

        /* Optional blocking or delay */
    }
}

Explanation

  • void indicates that the function does not return a value.
  • TaskFunction is the task entry function.
  • void *pvParameters allows an application-defined parameter to be passed to the task.
  • The infinite loop allows the task to perform repeated operations.
  • Blocking calls allow other ready tasks to execute.
A FreeRTOS task function must not simply return. If the task has finished its work, it should delete itself using the appropriate API or follow another documented task-lifecycle design.

5. Task Creation Requirements

Before creating a task, the application generally needs to define:

Parameter Description
Task Function Function containing the task's operations.
Task Name Human-readable identifier used for debugging and tracing.
Stack Depth Stack allocation expressed in the units required by the API.
Task Parameter Optional pointer passed to the task function.
Priority Priority used by the scheduler.
Task Handle Optional reference used to manage the task later.

6. FreeRTOS Task Creation API: xTaskCreate()

xTaskCreate() creates a task using dynamically allocated memory.

Function Prototype

BaseType_t xTaskCreate(
    TaskFunction_t pxTaskCode,
    const char * const pcName,
    configSTACK_DEPTH_TYPE usStackDepth,
    void *pvParameters,
    UBaseType_t uxPriority,
    TaskHandle_t *pxCreatedTask
);

Parameters

Parameter Meaning
pxTaskCode Pointer to the task function.
pcName Task name used for identification and debugging.
usStackDepth Requested stack depth in StackType_t units, not necessarily bytes.
pvParameters Pointer passed to the task function.
uxPriority Task priority.
pxCreatedTask Optional pointer receiving the created task handle.

Return Value

  • pdPASS: Task creation succeeded.
  • errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY: Required memory could not be allocated.

The exact declaration can vary slightly with FreeRTOS version and configuration.

7. Example: Creating a Sensor Task

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read sensor data */
        Read_Sensor();

        /* Wait for 100 ms */
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    BaseType_t status;

    Hardware_Init();

    status = xTaskCreate(
        SensorTask,
        "Sensor",
        128,
        NULL,
        2,
        NULL
    );

    if (status == pdPASS)
    {
        /* Task created successfully */
    }
    else
    {
        /* Task creation failed */
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program Explanation

  1. Include the FreeRTOS kernel headers.
  2. Define the task function.
  3. Initialize the hardware.
  4. Call xTaskCreate().
  5. Check the returned status.
  6. Start the scheduler.
  7. The scheduler executes the task when it is eligible.

Read_Sensor() and Hardware_Init() are application-specific functions and must be implemented separately.

8. Creating Multiple Tasks

An embedded application can create multiple tasks, each responsible for a particular function.

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void UARTTask(void *pvParameters)
{
    for (;;)
    {
        Process_UART();
        vTaskDelay(pdMS_TO_TICKS(20));
    }
}

void DisplayTask(void *pvParameters)
{
    for (;;)
    {
        Update_Display();
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    Hardware_Init();

    xTaskCreate(SensorTask, "Sensor", 128, NULL, 3, NULL);
    xTaskCreate(UARTTask, "UART", 128, NULL, 2, NULL);
    xTaskCreate(DisplayTask, "Display", 128, NULL, 1, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

In this example, the sensor task has the highest priority and the display task has the lowest priority. The actual priority assignment must be based on system timing requirements.

This is an illustrative FreeRTOS application. Stack depths, task priorities, hardware functions, and memory configuration must be validated for the selected target and FreeRTOS port.

9. Static Task Creation: xTaskCreateStatic()

xTaskCreateStatic() creates a task using memory supplied by the application.

Function Prototype

TaskHandle_t xTaskCreateStatic(
    TaskFunction_t pxTaskCode,
    const char * const pcName,
    configSTACK_DEPTH_TYPE ulStackDepth,
    void *pvParameters,
    UBaseType_t uxPriority,
    StackType_t *puxStackBuffer,
    StaticTask_t *pxTaskBuffer
);

Example

#include "FreeRTOS.h"
#include "task.h"

static StaticTask_t sensorTCB;

static StackType_t sensorStack[128];

TaskHandle_t sensorHandle;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

int main(void)
{
    Hardware_Init();

    sensorHandle = xTaskCreateStatic(
        SensorTask,
        "Sensor",
        128,
        NULL,
        2,
        sensorStack,
        &sensorTCB
    );

    if (sensorHandle == NULL)
    {
        /* Handle task creation failure */
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Requirements

  • Static allocation support must be enabled in the FreeRTOS configuration.
  • The application must provide a stack buffer.
  • The application must provide a TCB buffer.
  • The buffers must remain valid for the task's lifetime.

10. Static vs Dynamic Task Creation

Feature Dynamic Static
API xTaskCreate() xTaskCreateStatic()
Memory Source Configured RTOS heap Application-provided buffers
Runtime Allocation Yes No heap allocation for the task's TCB and stack
Memory Planning Heap capacity must be considered. Buffers must be sized and provided in advance.
Failure Conditions Allocation may fail. Creation can fail if parameters or resources are invalid.
Typical Use Flexible runtime task creation. Explicit and predictable memory planning.

Static allocation is often useful in systems where runtime heap allocation is restricted. It does not automatically guarantee that the complete application is deterministic or free from memory errors.

11. Task Creation Failure

Task creation can fail for several reasons.

  • Insufficient heap memory for dynamic allocation.
  • Incorrect stack-depth configuration.
  • Invalid task function or parameters.
  • Incorrect memory-buffer configuration for static creation.
  • Application or kernel configuration problems.

Checking Dynamic Creation

BaseType_t result;

result = xTaskCreate(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    NULL
);

if (result == pdPASS)
{
    /* Successful creation */
}
else
{
    /* Allocation or creation failure */
}

Memory Monitoring

Depending on the selected heap implementation, FreeRTOS provides APIs such as:

  • xPortGetFreeHeapSize()
  • xPortGetMinimumEverFreeHeapSize()

These can help monitor available heap memory when supported by the configured port and heap implementation.

12. Task Handles

A task handle is a reference used to identify and manage a task after creation.

Example

TaskHandle_t sensorHandle = NULL;

xTaskCreate(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    &sensorHandle
);

/* sensorHandle can be used with task-management APIs. */

Task handles are useful when an application needs to:

  • Suspend a particular task.
  • Resume a particular task.
  • Change task priority.
  • Delete a task.
  • Send task notifications.
A task handle is not a copy of the task's internal TCB. It is an opaque reference managed by FreeRTOS.

13. Task Deletion

Task deletion removes a task from the RTOS scheduling system.

In FreeRTOS, the function used is:

void vTaskDelete(TaskHandle_t xTaskToDelete);

Deleting a Specific Task

vTaskDelete(sensorHandle);

Deleting the Calling Task

vTaskDelete(NULL);

Passing NULL means that the currently executing task deletes itself.

14. Task Deletion Example

Consider a temporary diagnostic task that performs a finite operation and then deletes itself.

#include "FreeRTOS.h"
#include "task.h"

void DiagnosticTask(void *pvParameters)
{
    Run_Diagnostics();

    /* Delete the current task */
    vTaskDelete(NULL);
}

int main(void)
{
    Hardware_Init();

    xTaskCreate(
        DiagnosticTask,
        "Diagnostic",
        128,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Execution Sequence

  1. The application creates the diagnostic task.
  2. The task becomes eligible for execution.
  3. The scheduler selects it.
  4. The task executes the diagnostic function.
  5. The task calls vTaskDelete(NULL).
  6. The task is removed from normal scheduling.

15. What Happens to Memory After Task Deletion?

Memory handling depends on how the task was created.

Creation Method Memory Behavior After Deletion
Dynamic task creation FreeRTOS reclaims dynamically allocated task memory according to the configured kernel and heap implementation. A self-deleting task may have cleanup deferred to the idle task.
Static task creation The application-provided buffers remain application-owned and are not automatically freed by the kernel.
Do not reuse statically allocated TCB or stack buffers until the task has been fully removed and the application has established that no kernel operation still depends on them.

16. Deleting Another Task vs Self-Deletion

Self-Deletion Deleting Another Task
The current task calls vTaskDelete(NULL). A task passes the target task handle to vTaskDelete().
The current task stops executing. The target task is removed from scheduling.
Dynamic memory cleanup may be deferred to the idle task. Kernel cleanup follows the configured implementation.
Useful for finite tasks. Useful for controlled task lifecycle management.

Deleting another task does not automatically perform application-level cleanup of resources that task owns. Resource ownership must be designed carefully.

17. Task Creation and Deletion Best Practices

  • Use meaningful task names.
  • Choose stack sizes based on analysis and testing.
  • Check the return value of dynamic task creation.
  • Prefer static allocation when explicit memory control is required.
  • Store task handles when later management is necessary.
  • Avoid unnecessary task creation and deletion in time-critical paths.
  • Ensure that shared resources are handled safely before deleting a task.
  • Do not allow task functions to return unexpectedly.
  • Monitor stack usage and heap usage.
  • Verify the FreeRTOS configuration and processor port.

18. Practical Example: Three-Task Embedded Application

The following is a conceptual application showing separate sensor, communication, and display tasks.

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void CommunicationTask(void *pvParameters)
{
    for (;;)
    {
        Process_UART();
        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

void DisplayTask(void *pvParameters)
{
    for (;;)
    {
        Update_Display();
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    Hardware_Init();

    if (xTaskCreate(SensorTask, "Sensor", 128,
                    NULL, 3, NULL) != pdPASS)
    {
        Error_Handler();
    }

    if (xTaskCreate(CommunicationTask, "UART", 128,
                    NULL, 2, NULL) != pdPASS)
    {
        Error_Handler();
    }

    if (xTaskCreate(DisplayTask, "Display", 128,
                    NULL, 1, NULL) != pdPASS)
    {
        Error_Handler();
    }

    vTaskStartScheduler();

    /* Reaching here usually indicates scheduler failure. */
    for (;;)
    {
    }
}

This example illustrates task creation and scheduling setup. A production application must also implement its hardware functions, error handling, inter-task communication, and appropriate stack and priority configuration.

19. LPC2129 and Keil uVision Practical

The LPC2129 uses an ARM7TDMI-S core. Task creation and deletion concepts can be studied using a software model even when a verified FreeRTOS port is not available for the selected environment.

Suggested Exercises

  1. Create a C structure representing a conceptual task record.
  2. Store task name, priority, state, and a simulated stack-size value.
  3. Create functions that initialize and update the task records.
  4. Simulate task creation by changing a task state to Ready.
  5. Simulate task deletion by marking the task as deleted.
  6. Use Keil debugger to inspect the data structures.
This exercise models task management in C. It does not execute the FreeRTOS kernel or establish real-time task scheduling on LPC2129.

20. Lesson Summary

  • Task creation initializes a new execution entity managed by an RTOS.
  • A task function contains the operations performed by the task.
  • xTaskCreate() uses dynamic allocation.
  • xTaskCreateStatic() uses application-provided memory.
  • Stack depth is expressed in stack units, not necessarily bytes.
  • Task handles allow applications to refer to tasks.
  • vTaskDelete() removes a task from scheduling.
  • vTaskDelete(NULL) deletes the calling task.
  • Dynamic and static task memory have different cleanup behavior.
  • Creation, stack sizing, and deletion should be designed carefully.
