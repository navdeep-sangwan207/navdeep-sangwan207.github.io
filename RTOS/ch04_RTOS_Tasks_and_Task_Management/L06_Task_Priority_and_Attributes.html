2. Introduction to Task Priority

Task priority is a scheduling attribute that indicates the relative importance of a task in an RTOS.

When multiple tasks are Ready, a priority-based scheduler uses their priorities to determine which task should execute.

Example

Consider an embedded temperature-monitoring system:

  • Task A: Emergency temperature monitoring.
  • Task B: UART communication.
  • Task C: LCD display update.

If the system assigns Task A the highest priority, it can receive processor time ahead of lower-priority ready tasks under a suitable preemptive priority-based scheduler.

Priority determines scheduling preference. It does not automatically guarantee that a task will meet its deadline.

3. Priority Levels

An RTOS usually supports multiple task-priority levels.

A conceptual priority arrangement is shown below:

       HIGHER PRIORITY

This diagram assumes that a larger numerical value represents a higher priority. Priority numbering differs between RTOS implementations.

4. High-Priority and Low-Priority Tasks

High-Priority Task Low-Priority Task
Handles time-sensitive operations. Handles less time-sensitive operations.
May preempt lower-priority tasks. May wait while higher-priority tasks are ready.
Requires careful execution-time analysis. Can often tolerate longer scheduling delays.
Examples: control loops and protection monitoring. Examples: display refresh and background logging.
Assigning unnecessarily high priorities can cause lower-priority tasks to starve. Priority selection must consider timing requirements, execution time, blocking, and system-wide workload.

5. Priority-Based Scheduling

Priority-based scheduling selects a Ready task according to its priority.

Example

Task Priority State
SensorTask 4 Ready
UARTTask 3 Ready
DisplayTask 1 Ready

Assuming a preemptive scheduler and larger numbers indicating higher priorities:

SensorTask  (Priority 4) ---> RUNNING

UARTTask    (Priority 3) ---> READY

DisplayTask (Priority 1) ---> READY

The highest-priority Ready task is selected. If SensorTask blocks, the scheduler can select UARTTask or another eligible task.

6. Preemptive Scheduling and Task Priority

In a preemptive priority-based RTOS, a higher-priority Ready task can preempt a lower-priority Running task.

Example

  1. Task A is running with priority 2.
  2. Task B becomes Ready with priority 4.
  3. The scheduler selects Task B.
  4. Task A returns to the Ready state.
  5. Task B executes until it blocks, suspends, or is preempted by an even higher-priority task.
Before:

Task A: RUNNING (Priority 2)
Task B: BLOCKED (Priority 4)

Event occurs:

Task B: READY (Priority 4)

After scheduling:

Task A: READY
Task B: RUNNING

Preemption behavior depends on scheduler configuration and the current execution context.

7. Equal-Priority Tasks

When two or more Ready tasks have the same priority, the RTOS may use time slicing or another scheduling policy.

Time-Slicing Example

Task A: Priority 2
Task B: Priority 2

Both tasks are Ready.

With time slicing enabled:
Task A executes for a time slice.
Task B may execute during a later time slice.

Time slicing among equal-priority tasks is a scheduler configuration choice. It is not necessarily enabled in every RTOS or every FreeRTOS configuration.

8. Task Attributes

Task attributes are properties that define how a task is created, identified, and managed.

Attribute Description
Task Name Identifies the task during debugging and tracing.
Task Function Defines the code executed by the task.
Priority Defines the task's scheduling priority.
Stack Depth Defines the allocated stack capacity.
Task Parameter Provides application data to the task function.
Task Handle Provides a reference to the task.
Task State Indicates whether the task is Ready, Running, Blocked, or Suspended.

These attributes are not necessarily all stored as separate fields in the internal TCB. Their implementation depends on the RTOS.

9. Assigning Priority During Task Creation

In FreeRTOS, priority is assigned through the uxPriority parameter of xTaskCreate().

Example

xTaskCreate(
    SensorTask,
    "Sensor",
    128,
    NULL,
    4,
    NULL
);

Here, the task is created with priority 4.

Creating Tasks with Different Priorities

xTaskCreate(SensorTask,
            "Sensor",
            128,
            NULL,
            4,
            NULL);

xTaskCreate(UARTTask,
            "UART",
            128,
            NULL,
            3,
            NULL);

xTaskCreate(DisplayTask,
            "Display",
            128,
            NULL,
            1,
            NULL);

These priorities are illustrative. The valid priority range is determined by configMAX_PRIORITIES.

10. FreeRTOS Priority Configuration

FreeRTOS uses the configuration macro:

#define configMAX_PRIORITIES 5

This example configures five priority levels, numbered 0 through 4.

Priority Meaning in this example
0 Lowest priority
1 Low priority
2 Medium priority
3 High priority
4 Highest application priority in this configuration

FreeRTOS reserves priority 0 for the idle task. The application can create tasks at other valid priority levels.

Increasing configMAX_PRIORITIES can increase kernel scheduling data structures and memory requirements. Select a suitable value rather than making it unnecessarily large.

11. Changing Task Priority at Runtime

FreeRTOS provides vTaskPrioritySet() to change the priority of an existing task.

Function Prototype

void vTaskPrioritySet(
    TaskHandle_t xTask,
    UBaseType_t uxNewPriority
);

Example

TaskHandle_t sensorHandle;

/* Assume sensorHandle identifies a valid task. */

vTaskPrioritySet(sensorHandle, 4);

The specified task's priority is changed to 4, subject to the configured valid priority range.

Changing the Current Task's Priority

vTaskPrioritySet(NULL, 3);

Passing NULL identifies the calling task.

12. Reading Task Priority

FreeRTOS provides uxTaskPriorityGet() to obtain a task's current priority.

Function Prototype

UBaseType_t uxTaskPriorityGet(
    TaskHandle_t xTask
);

Example

UBaseType_t currentPriority;

currentPriority =
    uxTaskPriorityGet(sensorHandle);

To obtain the priority of the calling task:

currentPriority = uxTaskPriorityGet(NULL);

Availability of priority inspection APIs may depend on FreeRTOS configuration options.

13. Priority Inversion

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task holding a resource that the high-priority task needs.

Example

  • Low-priority Task L acquires a shared mutex.
  • High-priority Task H becomes Ready and requests the same mutex.
  • Task H blocks because Task L owns the mutex.
  • Medium-priority Task M becomes Ready and preempts Task L.
  • Task L cannot run to release the mutex, so Task H remains blocked.
Task H: HIGH PRIORITY
        Waiting for mutex

Task M: MEDIUM PRIORITY
        Executing

Task L: LOW PRIORITY
        Owns mutex but cannot execute

This situation can delay a high-priority task because of medium-priority activity and a resource held by a lower-priority task.

14. Priority Inheritance

Priority inheritance is a technique used by some RTOS mutex implementations to reduce priority inversion.

When a high-priority task blocks on a mutex held by a lower-priority task, the mutex owner temporarily inherits the higher priority.

Conceptual Sequence

  1. Task L owns a mutex.
  2. Task H requests the mutex and blocks.
  3. Task L temporarily inherits Task H's priority.
  4. Task L can execute ahead of unrelated medium-priority tasks.
  5. Task L releases the mutex.
  6. Task H becomes eligible to execute.
  7. Task L returns to its appropriate priority when inheritance is no longer required.
FreeRTOS mutexes provide priority inheritance. Binary semaphores do not provide mutex-style priority inheritance.

15. Task Starvation

Starvation occurs when a task waits for a long time or indefinitely because other tasks continually receive processor time or resources.

Example

A high-priority task remains continuously Ready and does not block or yield. A lower-priority task may never receive CPU time under a strict priority-based preemptive scheduler.

Prevention Techniques

  • Assign priorities carefully.
  • Ensure high-priority tasks block when waiting for events.
  • Keep task execution bounded.
  • Use suitable scheduling policies.
  • Analyze CPU utilization and task timing.

16. Example: Priority Assignment in an Embedded System

Consider an industrial monitoring application.

Task Priority Responsibility
ProtectionTask 4 Monitors critical fault conditions.
SensorTask 3 Reads sensor information.
UARTTask 2 Processes communication data.
DisplayTask 1 Updates the user interface.

The table is an example of relative priorities, not a complete real-time scheduling design. Actual assignments require deadline, execution-time, blocking, and interrupt analysis.

For safety-critical protection, do not rely solely on task priority. Independent hardware protection and fault-handling mechanisms may be necessary.

17. Complete FreeRTOS Priority Example

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t sensorHandle;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void DisplayTask(void *pvParameters)
{
    for (;;)
    {
        Update_Display();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    Hardware_Init();

    xTaskCreate(
        SensorTask,
        "Sensor",
        128,
        NULL,
        3,
        &sensorHandle
    );

    xTaskCreate(
        DisplayTask,
        "Display",
        128,
        NULL,
        1,
        NULL
    );

    /* Change sensor task priority before scheduling. */
    if (sensorHandle != NULL)
    {
        vTaskPrioritySet(sensorHandle, 4);
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

This example demonstrates priority assignment and modification. Production code should check the return status of each task-creation call and handle failures.

18. LPC2129 and Keil uVision Practical

The LPC2129 is a single-core ARM7TDMI-S microcontroller. It can execute one task at a time, with scheduling used to share CPU time between activities.

Suggested Exercises

  1. Create three conceptual tasks: sensor, UART, and display.
  2. Assign each task a priority value in a C structure.
  3. Write a simple scheduler model that selects the highest-priority Ready task.
  4. Change a task's priority and observe the selected task.
  5. Simulate a high-priority task becoming Ready while a low-priority task is Running.
  6. Use the Keil debugger to inspect task data structures and state variables.
A software scheduler model is not a FreeRTOS kernel. Verify the availability and compatibility of a real FreeRTOS port before attempting actual task scheduling on LPC2129.

19. Lesson Summary

  • Task priority represents relative scheduling importance.
  • Priority-based scheduling selects among Ready tasks.
  • A higher-priority Ready task can preempt a lower-priority Running task in a preemptive scheduler.
  • Equal-priority tasks may share CPU time through time slicing.
  • Task attributes include name, function, stack depth, priority, parameter, and handle.
  • configMAX_PRIORITIES configures the FreeRTOS priority range.
  • vTaskPrioritySet() changes task priority.
  • uxTaskPriorityGet() reads task priority.
  • Priority inversion can delay high-priority tasks.
  • Priority inheritance helps reduce priority inversion when using mutexes.
  • Careful priority assignment helps prevent starvation and missed deadlines.
