2. Introduction to Tasks

A task is an independent unit of execution managed by an RTOS. It performs a specific operation within an embedded application.

An embedded system may need to perform several activities, such as:

  • Reading sensor values.
  • Controlling a motor.
  • Receiving UART data.
  • Updating an LCD.
  • Monitoring system faults.

Instead of writing all activities as one large program loop, an RTOS-based application can divide the work into separate tasks.

A task provides a structured way to organize application functionality. The RTOS scheduler decides which ready task executes according to the scheduling policy.

3. Task-Based Programming

In task-based programming, an application is divided into multiple logical execution units.

Example: Embedded Temperature Monitoring System

Consider a system that reads temperature, displays the value, and sends data to a computer.

Task Responsibilities

Task Responsibility
Sensor Task Reads temperature sensor data.

Each task can have its own execution logic, priority, stack, and state.

4. Why Are Tasks Required?

1. Modularity

Tasks divide a large application into smaller, manageable components.

2. Independent Execution

Different activities can be organized separately and scheduled by the RTOS.

3. Priority Management

Important activities can receive higher priority than less time-sensitive activities.

4. Better Resource Coordination

Tasks can use queues, semaphores, mutexes, and other kernel objects to coordinate access to resources.

5. Simplified Application Design

Each task can focus on one responsibility, making the application easier to maintain and test.

5. Task vs Function

A function is a reusable block of code. A task is an independently scheduled execution unit managed by the RTOS.

Function Task
Called by another function or execution flow. Scheduled by the RTOS.
Uses the caller's execution context. Has its own task execution context.
Normally returns to its caller. May run repeatedly or remain blocked.
Does not inherently have an RTOS priority. Can have a configured priority.
Does not require a separate task stack. Requires stack space for its execution.

A task function may call many ordinary functions while executing.

6. Task vs Process vs Thread

The terms task, process, and thread are related but are not identical across all operating systems.

Feature Process Thread RTOS Task
Execution Program in execution Execution stream within a process Schedulable execution unit
Address Space Usually has its own Shares process address space Depends on RTOS and hardware protection
Stack Contains one or more thread stacks Has its own stack Has its own task stack
Scheduling Through its threads Scheduled by OS Scheduled by RTOS
Priority OS-dependent OS-dependent Usually configured by application
In many embedded RTOS designs, a task is conceptually similar to a schedulable thread. It should not automatically be treated as a separate protected process.

The task may execute, wait for an event, become delayed, or be preempted by another task depending on its state and the scheduling policy.

8. Multiple Tasks in an Embedded System

A single embedded application may contain several tasks with different responsibilities.

Example: Smart Home Controller

Task Name Function Possible Priority
Safety Monitoring Monitors critical fault inputs High
Sensor Monitoring Reads environmental sensors Medium
Communication Handles network messages Medium
Display Update Refreshes the user interface Low
Data Logging Stores measurement records Low

These priorities are illustrative. Actual priorities must be assigned after analyzing deadlines, execution times, blocking, and safety requirements.

9. Task Execution on a Single-Core Processor

On a single-core microcontroller, only one task executes at a time on the processor.

The RTOS scheduler switches between tasks to provide multitasking.

Illustrative Execution Timeline

Time  ------------------------------------>

CPU:  | Task A | Task B | Task A | Task C |
      |--------|--------|--------|--------|

Task A: Sensor Processing
Task B: Communication
Task C: Display Update

Tasks may appear to run simultaneously because the processor switches between them. This is concurrency, not true parallel execution.

The LPC2129 is a single-core ARM7TDMI-S microcontroller. Its CPU can schedule multiple RTOS tasks, but it cannot execute multiple tasks in parallel on separate CPU cores.

10. Task Context

Task context is the processor and execution information required to pause a task and later resume it correctly.

Typical Context Information

  • Processor registers.
  • Program counter or return address.
  • Stack pointer.
  • Processor status information.
  • Task-specific execution state.

The RTOS saves and restores the necessary context during a context switch. The exact implementation depends on the processor architecture and RTOS port.

11. Task Priority

Task priority determines the relative scheduling importance of a task.

In a typical priority-based preemptive RTOS:

  • A higher-priority ready task can preempt a lower-priority running task.
  • A blocked task does not execute until its waiting condition is satisfied.
  • Equal-priority tasks may share processor time if time slicing is configured.

Example

Task A Priority = 3
Task B Priority = 2
Task C Priority = 1

If all three tasks are ready:

Task A is selected first
under a conventional
higher-number-means-higher-priority
configuration.

Priority numbering conventions differ between RTOS products. Always check the selected RTOS documentation.

12. Task Management by the RTOS Kernel

The RTOS kernel provides services for managing task execution.

Operation Purpose
Task Creation Creates a new task.
Task Deletion Removes a task from the scheduler.
Task Suspension Temporarily prevents a task from being scheduled.
Task Resumption Makes a suspended task eligible to execute again.
Task Delay Blocks a task for a specified time.
Priority Management Changes or retrieves task priority.
Task Scheduling Selects the next task for execution.

13. Introduction to FreeRTOS Tasks

FreeRTOS uses tasks as its basic application execution units.

A typical FreeRTOS task function has the following structure:

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read sensor data */

        /* Process sensor data */

        /* Wait for the next cycle */
        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

Explanation

  • SensorTask is the task function.
  • void *pvParameters receives the task parameter.
  • for (;;) creates a continuous task loop.
  • vTaskDelay() blocks the task for the specified tick duration.
  • The scheduler can execute other ready tasks while this task is delayed.
A FreeRTOS task function should not simply return. A task that has finished its work should delete itself or follow another documented task-termination design. The example above is a conceptual task body and requires task creation and scheduler initialization in a complete application.

14. Example: Two Independent Tasks

The following example illustrates two tasks with separate responsibilities. It assumes a compatible FreeRTOS port and board-specific LED functions.

#include "FreeRTOS.h"
#include "task.h"

void LED_Task(void *pvParameters)
{
    for (;;)
    {
        LED1_Toggle();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void Monitor_Task(void *pvParameters)
{
    for (;;)
    {
        Read_System_Status();

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    Hardware_Init();

    xTaskCreate(
        LED_Task,
        "LED",
        128,
        NULL,
        2,
        NULL
    );

    xTaskCreate(
        Monitor_Task,
        "Monitor",
        128,
        NULL,
        1,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
        /* Scheduler should normally run here. */
    }
}

Program Explanation

  • LED_Task performs LED-related operations.
  • Monitor_Task reads system status.
  • Both tasks execute independently under the scheduler.
  • The LED task has a higher configured priority in this example.
  • Each task periodically blocks using vTaskDelay().

LED_Toggle(), Read_System_Status(), and Hardware_Init() are board-specific functions and must be implemented separately.

15. Advantages of Task-Based Programming

  • Improves application modularity.
  • Simplifies organization of independent activities.
  • Supports priority-based execution.
  • Provides structured task synchronization.
  • Improves maintainability and testing.
  • Allows blocking tasks to wait without continuously polling.
  • Supports scalable embedded application design.

16. Limitations and Design Challenges

  • Each task requires stack memory.
  • Context switching introduces overhead.
  • Incorrect priorities can cause deadline failures.
  • Shared resources require synchronization.
  • Deadlocks and starvation are possible.
  • Stack overflow can cause system instability.
  • Debugging concurrent execution can be difficult.
Creating more tasks does not automatically improve performance. Task count, stack allocation, priority assignment, and communication design must be justified by application requirements.

17. Lesson Summary

  • A task is an independently schedulable execution unit managed by an RTOS.
  • Task-based programming divides an application into logical activities.
  • Each task has its own execution context and stack.
  • The scheduler selects a ready task for execution.
  • Tasks may run, block, delay, or become suspended.
  • Task priority influences scheduling decisions.
  • Single-core processors execute one task at a time.
  • FreeRTOS provides APIs for creating and managing tasks.
  • Task-based design improves modularity but requires careful resource management.
