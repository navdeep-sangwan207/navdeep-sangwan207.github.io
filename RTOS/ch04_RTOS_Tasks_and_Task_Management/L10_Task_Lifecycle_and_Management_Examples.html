2. Introduction to Task Lifecycle

A task lifecycle describes the sequence of states and operations that a task experiences from creation until deletion.

An RTOS manages each task through kernel data structures, including its task control information and execution context.

Typical Task Lifecycle

        TASK CREATION
              |
              v
          READY STATE
              |
              v
         RUNNING STATE
              |
      +-------+--------+
      |       |        |
      v       v        v
   BLOCKED  SUSPENDED  PREEMPTED
      |       |        |
      v       v        |
   READY    RESUMED    |
      |       |        |
      +-------+--------+
              |
              v
          RUNNING
              |
              v
          DELETED

The diagram is conceptual. Actual state transitions depend on the RTOS implementation and the operation performed.

3. Task Creation

Task creation allocates the resources and kernel information needed for a task.

In FreeRTOS, a task can be created dynamically or statically.

Dynamic Task Creation

BaseType_t result;

result = xTaskCreate(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    NULL
);

if (result != pdPASS)
{
    /* Handle task creation failure. */
}

Static Task Creation

static StaticTask_t sensorTCB;
static StackType_t sensorStack[128];

TaskHandle_t sensorHandle;

sensorHandle = xTaskCreateStatic(
    SensorTask,
    "Sensor",
    128,
    NULL,
    2,
    sensorStack,
    &sensorTCB
);

Static task creation requires the appropriate FreeRTOS configuration and application-provided memory.

The stack depth passed to common FreeRTOS task-creation APIs is measured in StackType_t elements, not bytes.

4. Ready State

After successful creation, a task becomes eligible for execution and enters the Ready state, subject to the kernel's startup and scheduling behavior.

A Ready task:

  • Has been created successfully.
  • Has the required task resources.
  • Is not waiting for a delay or event.
  • Can be selected by the scheduler.

A Ready task may wait while another task with a higher priority is executing.

5. Running State

A task enters the Running state when the scheduler selects it for execution.

On a single-core microcontroller, only one task executes at a time.

Example

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();
        Process_Sensor_Data();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

The task executes its operations and then blocks for the requested delay.

6. Blocking State

A task enters the Blocked state when it waits for a time interval, event, or resource.

Common Blocking Operations

Operation Reason for Blocking
vTaskDelay() Waits for a specified delay.
xQueueReceive() Waits for queue data when the queue is empty.
xSemaphoreTake() Waits for a semaphore or mutex.
ulTaskNotifyTake() Waits for a task notification.

When the wait condition is satisfied or the timeout expires, the task can become Ready again.

7. Suspended State

A task enters the Suspended state when it is explicitly suspended using an RTOS operation.

FreeRTOS API

vTaskSuspend(taskHandle);

A suspended task does not become Ready automatically when a delay expires. It requires an explicit resume operation.

Resuming a Task

vTaskResume(taskHandle);

After resumption, the task becomes eligible for scheduling.

8. Task Preemption and Yielding

A Running task can return to the Ready state when it is preempted by another task or voluntarily yields.

Task Yielding

taskYIELD();

Preemption Example

Task A: Priority 2 - RUNNING
Task B: Priority 4 - BLOCKED

An event makes Task B Ready.

Task A: READY
Task B: RUNNING

This example assumes a preemptive priority-based scheduler and that scheduling is permitted.

9. Task Deletion

Task deletion removes a task from the active task set.

FreeRTOS API

vTaskDelete(taskHandle);

To delete the currently executing task:

vTaskDelete(NULL);

Important Considerations

  • Deleting a task removes it from scheduling.
  • Dynamic task memory is reclaimed according to the FreeRTOS memory-management mechanism.
  • Memory cleanup for a self-deleting task can be deferred to the idle task.
  • Application-provided static memory remains application-owned.
  • Do not delete a task while it owns a mutex or shared resource without a proper cleanup strategy.

10. Complete Task-State Transition Table

Current State Operation / Event Possible Next State
Created Successful task creation Ready
Ready Selected by scheduler Running
Running Higher-priority task becomes Ready Ready
Running Task waits for delay or event Blocked
Running / Ready Explicit suspension Suspended
Blocked Wait condition satisfied Ready
Suspended Explicit resume Ready
Ready / Running / Blocked / Suspended Task deletion Deleted

Some RTOS implementations represent internal task states differently. This table describes the conceptual lifecycle used in this course.

11. Important FreeRTOS Task-Management APIs

API Function
xTaskCreate() Creates a task using dynamic allocation.
xTaskCreateStatic() Creates a task using application-provided memory.
vTaskDelete() Deletes a task.
vTaskSuspend() Suspends a task.
vTaskResume() Resumes an explicitly suspended task.
vTaskDelay() Blocks a task for a relative delay.
vTaskDelayUntil() Maintains a periodic wake-time reference.
uxTaskPriorityGet() Reads a task's priority.
vTaskPrioritySet() Changes a task's priority.
taskYIELD() Requests a scheduling opportunity.
xTaskGetTickCount() Returns the current RTOS tick count.
eTaskGetState() Returns a task's state when enabled.

Some APIs require corresponding INCLUDE_... configuration options in FreeRTOSConfig.h.

12. Task Management Example: Sensor Monitoring System

Consider an embedded system containing three tasks:

Task Priority Responsibility
SensorTask 3 Reads sensor information periodically.
UARTTask 2 Processes communication data.
DisplayTask 1 Updates the display periodically.

The scheduler selects the highest-priority Ready task. Each task blocks when waiting for its next operation or event.

Conceptual Execution Flow

       Priority 3

13. Integrated FreeRTOS Task-Management Program

The following example demonstrates task creation, task handles, periodic delays, priorities, and task scheduling.

#include "FreeRTOS.h"
#include "task.h"

/* Task handles */
TaskHandle_t sensorHandle;
TaskHandle_t uartHandle;
TaskHandle_t displayHandle;

/* Sensor task */
void SensorTask(void *pvParameters)
{
    for (;;)
    {
        Read_Sensor();

        Process_Sensor_Data();

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

/* UART task */
void UARTTask(void *pvParameters)
{
    for (;;)
    {
        Process_UART_Data();

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

/* Display task */
void DisplayTask(void *pvParameters)
{
    for (;;)
    {
        Update_Display();

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    Hardware_Init();

    /* Create sensor task */
    if (xTaskCreate(
            SensorTask,
            "Sensor",
            128,
            NULL,
            3,
            &sensorHandle
        ) != pdPASS)
    {
        Error_Handler();
    }

    /* Create UART task */
    if (xTaskCreate(
            UARTTask,
            "UART",
            128,
            NULL,
            2,
            &uartHandle
        ) != pdPASS)
    {
        Error_Handler();
    }

    /* Create display task */
    if (xTaskCreate(
            DisplayTask,
            "Display",
            128,
            NULL,
            1,
            &displayHandle
        ) != pdPASS)
    {
        Error_Handler();
    }

    /* Start scheduler */
    vTaskStartScheduler();

    /* Reached only if scheduler cannot start
       or subsequently exits. */
    for (;;)
    {
    }
}

Program Explanation

  1. Three task handles are declared.
  2. Hardware initialization is performed.
  3. SensorTask is created with priority 3.
  4. UARTTask is created with priority 2.
  5. DisplayTask is created with priority 1.
  6. Each task executes its operation and blocks for a delay.
  7. The scheduler manages their execution.
Read_Sensor(), Process_Sensor_Data(), Process_UART_Data(), Update_Display(), and Error_Handler() are application-specific functions and must be implemented. The example demonstrates API usage; it is not a complete board-specific project.

14. Task Management Best Practices

  • Assign priorities based on timing requirements.
  • Choose stack sizes based on measured and analyzed requirements.
  • Check every task-creation result.
  • Use task handles carefully.
  • Use blocking APIs instead of unnecessary busy waiting.
  • Keep high-priority tasks short and predictable.
  • Use mutexes to protect shared resources where appropriate.
  • Do not suspend tasks while they own shared resources.
  • Use static allocation where deterministic memory allocation is required and supported.
  • Monitor stack usage and task execution behavior.
  • Delete tasks only when their resources and ownership responsibilities are handled safely.
  • Test timing and scheduling under realistic worst-case workloads.

15. Common Task-Management Problems

Problem Possible Cause Preventive Measure
Task creation failure Insufficient heap or static resources. Check return values and memory requirements.
Stack overflow Insufficient task stack. Analyze stack usage and enable appropriate checks.
Task starvation Higher-priority task continuously executes. Review priorities and blocking behavior.
Priority inversion Shared resource ownership. Use suitable mutexes and analyze blocking.
Deadlock Tasks wait indefinitely for resources. Design resource-acquisition order and timeouts.
Unexpected task delay Blocking, interrupt load, or scheduling interference. Measure response time and analyze interference.

16. LPC2129 and Keil uVision Practical

The LPC2129 uses an ARM7TDMI-S processor with a single CPU core. Its task-management concepts can be studied through state models and debugger-based exercises.

Suggested Practical Exercises

  1. Define task structures for sensor, UART, and display operations.
  2. Implement a conceptual task-state transition model.
  3. Simulate task creation and Ready-state transitions.
  4. Model a task entering Blocked after a delay.
  5. Model task suspension and resumption.
  6. Model preemption when a higher-priority task becomes Ready.
  7. Inspect the state variables using the Keil debugger.
  8. Calculate task stack memory using stack depth and sizeof(StackType_t) for a selected target configuration.
Keil uVision simulation of ARM7 registers and application variables does not establish FreeRTOS port compatibility. Actual kernel execution requires a suitable port, correct configuration, and compatible toolchain support.

17. Lesson Summary

  • A task lifecycle covers creation through deletion.
  • Created tasks become eligible for scheduling.
  • Ready tasks wait for CPU time.
  • Running tasks execute on the processor.
  • Blocked tasks wait for events, delays, or resources.
  • Suspended tasks require explicit resumption.
  • Preemption and yielding can return a task to Ready.
  • xTaskCreate() and xTaskCreateStatic() create tasks.
  • vTaskDelete() deletes tasks.
  • vTaskSuspend() and vTaskResume() control task suspension.
  • Priority and timing influence scheduling decisions.
  • Proper resource and memory management are essential for reliable RTOS applications.
