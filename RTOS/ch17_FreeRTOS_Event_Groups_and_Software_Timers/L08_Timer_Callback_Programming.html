Lesson 08 – FreeRTOS Timer Callback Functions

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

A timer callback function is an application-defined function executed when a FreeRTOS software timer expires. It allows the application to respond to a timer event without creating a separate task for every timer.

All software timer callbacks are processed by the timer service task. Therefore, callback execution context and execution time must be considered carefully.

Learning Objectives

  • Understand timer callback functions.
  • Learn the callback function prototype.
  • Understand callback execution context.
  • Identify the timer that triggered a callback.
  • Understand timer ID usage.
  • Learn safe callback programming practices.
  • Communicate callback events to application tasks.

1. What Is a Timer Callback Function?

A timer callback function is called by the FreeRTOS timer service task when a software timer reaches its expiry time. The callback contains the application-specific action to be performed when the timer expires.

Basic Callback Prototype

void TimerCallback(TimerHandle_t xTimer);

The callback receives the handle of the timer that expired. This handle can be used to identify the timer or retrieve its application-defined timer ID.

2. Callback Execution Context

A FreeRTOS software timer callback does not execute in the hardware interrupt service routine. It executes in the context of the timer service task.

Execution ContextTimer Callback
Hardware ISRNo
Timer service taskYes
Application taskNot directly; application work can be delegated to one.

The timer service task is a normal FreeRTOS task created when software timer support is enabled and the scheduler starts. It processes timer commands and executes callbacks.

A callback can use suitable task-context FreeRTOS APIs, but it must not use APIs that block waiting for time or resources. The timer service task must remain available to process other timer events and commands.

3. Callback Function Parameters

The callback receives one parameter: 

void TimerCallback(TimerHandle_t xTimer);
ParameterDescription
xTimerHandle of the software timer whose callback is being executed.

Example

void SensorTimerCallback(TimerHandle_t xTimer)
{
    /* Timer-specific application action */
}

The timer handle can be passed to timer APIs and used to retrieve the timer ID.

4. Identifying Timers Using Timer IDs

A single callback function can be shared by multiple software timers. The application can identify the timer by retrieving its timer ID using pvTimerGetTimerID().

Function Prototype

void *pvTimerGetTimerID(
    TimerHandle_t xTimer
);

Example

static int sensorID;
static int communicationID;

void CommonTimerCallback(TimerHandle_t xTimer)
{
    void *timerID;

    timerID = pvTimerGetTimerID(xTimer);

    if (timerID == &sensorID)
    {
        /* Sensor timer expired */
    }
    else if (timerID == &communicationID)
    {
        /* Communication timer expired */
    }
}

The application supplies the timer ID when creating the timer and retrieves it inside the callback.

Timer IDs are application-defined pointer values. The application must ensure that any referenced object remains valid while the timer may use it.

5. Callback Execution Time

Timer callbacks share the execution time of one timer service task. If a callback takes too long, other expired timers and pending timer commands may be delayed.

Example of an Unsafe Callback

void UnsafeCallback(TimerHandle_t xTimer)
{
    /* Do not perform long blocking operations here */

    vTaskDelay(pdMS_TO_TICKS(1000));
}

The callback must not block the timer service task using vTaskDelay().

Better Approach

void SafeCallback(TimerHandle_t xTimer)
{
    /* Send a short notification to an application task */
    xTaskNotifyGive(xApplicationTaskHandle);
}

The application task receives the notification and performs the lengthy operation independently.

A long-running callback can delay every other timer callback handled by the same timer service task. Keep callback execution short and avoid blocking operations.

6. Communicating with Application Tasks

Timer callbacks often need to request work from another task. FreeRTOS provides several communication mechanisms suitable for this purpose.

MechanismTypical Use
Task notificationNotify one task that a timer event occurred.
QueueSend structured data or timer-event information.
Event groupSet a condition bit for one or more waiting tasks.

Example – Task Notification

static TaskHandle_t xWorkerTaskHandle;

void TimerCallback(TimerHandle_t xTimer)
{
    xTaskNotifyGive(xWorkerTaskHandle);
}

void WorkerTask(void *pvParameters)
{
    for (;;)
    {
        ulTaskNotifyTake(
            pdTRUE,
            portMAX_DELAY
        );

        /* Perform the requested application work */
    }
}

The callback gives a notification. The worker task waits for that notification and performs the longer operation.

This example uses a task notification as a lightweight signal. If every timer event must be preserved as a separate event, consider whether notification counting or a queue is more appropriate. A notification used as a bit flag can coalesce repeated events.

7. Using a Queue from a Timer Callback

Because a timer callback executes in task context, it can use task-context queue APIs. The callback should use a zero block time so that it does not block the timer service task.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "timers.h"

static QueueHandle_t xTimerEventQueue;

typedef struct
{
    unsigned int eventCode;
} TimerEvent_t;

void TimerCallback(TimerHandle_t xTimer)
{
    TimerEvent_t event;

    event.eventCode = 1;

    /* Never wait for queue space in a timer callback */
    xQueueSend(
        xTimerEventQueue,
        &event,
        0
    );
}

The queue send operation returns immediately if the queue is full because the block time is zero. The callback should check the return value in production code and define how queue-full conditions are handled.

The callback function can be the same for both timer types. The timer's configuration determines whether it expires once or repeatedly.

9. Complete Program – Timer Callback and Worker Task

Objective

Create an auto-reload timer that notifies a worker task every two seconds. The worker task performs the application operation.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "timers.h"

static TimerHandle_t xPeriodicTimer;
static TaskHandle_t xWorkerTaskHandle;

void PeriodicTimerCallback(TimerHandle_t xTimer)
{
    /* Notify the worker task */
    xTaskNotifyGive(xWorkerTaskHandle);
}

void WorkerTask(void *pvParameters)
{
    for (;;)
    {
        ulTaskNotifyTake(
            pdTRUE,
            portMAX_DELAY
        );

        /* Perform application processing here */
    }
}

int main(void)
{
    if (xTaskCreate(
        WorkerTask,
        "Worker",
        configMINIMAL_STACK_SIZE,
        NULL,
        2,
        &xWorkerTaskHandle
    ) != pdPASS)
    {
        for (;;)
        {
        }
    }

    xPeriodicTimer = xTimerCreate(
        "PeriodicTimer",
        pdMS_TO_TICKS(2000),
        pdTRUE,
        NULL,
        PeriodicTimerCallback
    );

    if (xPeriodicTimer == NULL)
    {
        for (;;)
        {
        }
    }

    if (xTimerStart(xPeriodicTimer, 0) != pdPASS)
    {
        for (;;)
        {
        }
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program Explanation

  1. Create the worker task and obtain its task handle.
  2. Create a two-second auto-reload timer.
  3. Define the timer callback.
  4. Start the timer.
  5. When the timer expires, the callback notifies the worker task.
  6. The worker task wakes and performs the application processing.
  7. The timer continues generating periodic notifications.

Expected Behavior

Approximate TimeOperation
0 secondsScheduler starts and timer is activated.
2 secondsFirst timer callback notifies the worker task.
4 secondsNext timer callback notifies the worker task.
6 secondsNext timer callback notifies the worker task.
The example assumes the timer service task is configured and the notification APIs are available in the selected FreeRTOS version. Check the return values of task creation, timer creation, timer start, and queue operations in a production application.

10. Important Callback Programming Rules

  1. Keep callback execution short.
  2. Do not call vTaskDelay() inside a callback.
  3. Do not wait indefinitely for queue space or a semaphore.
  4. Do not perform lengthy file, network, or hardware operations.
  5. Use a task notification or queue to delegate longer work.
  6. Use timer IDs to identify timers when sharing callbacks.
  7. Check queue-send results and define overflow handling.
  8. Do not treat a timer callback as an interrupt service routine.
  9. Consider the timer service task priority and stack requirements.
  10. Remember that one long callback delays other timer processing.

11. Common Programming Errors

ErrorCorrection
Using ISR APIs in a timer callback without reasonUse suitable task-context APIs.
Blocking inside the callbackUse non-blocking operations and delegate work.
Performing lengthy processingMove processing to an application task.
Ignoring timer identificationUse timer handles or timer IDs.
Ignoring queue-full conditionsCheck the return value and define an overflow policy.
Assuming callbacks execute in ISR contextRemember they execute in timer service task context.

14. Lesson Summary

  • Timer callbacks execute when software timers expire.
  • Callbacks execute in timer service task context.
  • The callback receives the expired timer's handle.
  • Timer IDs can identify different timers using a shared callback.
  • Callbacks should be short and non-blocking.
  • Long operations should be delegated to application tasks.
  • Task notifications and queues are useful communication mechanisms.
  • A blocking callback can delay other timer operations.
