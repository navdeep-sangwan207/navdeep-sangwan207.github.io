Chapter 17: FreeRTOS Event Groups and Software Timers

Lesson 01 – FreeRTOS Event Groups: Introduction

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

FreeRTOS event groups provide a mechanism for synchronizing tasks using a collection of event bits. Each bit represents a condition or event in an application. Tasks can set, clear, and wait for specific combinations of these bits.

Event groups are useful when a task must wait until one or more conditions are satisfied, such as sensor initialization, network connection, data availability, or completion of multiple operations.

Learning Objectives

  • Understand the concept of event groups.
  • Understand event bits and event flags.
  • Identify the purpose of event groups in an RTOS.
  • Understand how tasks use event groups for synchronization.
  • Compare event groups with semaphores and queues.
  • Identify practical applications of event groups.
  • Understand important FreeRTOS event-group limitations.

1. What Is an Event Group?

An event group is a FreeRTOS kernel object containing a collection of event bits. Each bit represents a Boolean condition:

  • 1: The corresponding event or condition is set.
  • 0: The corresponding event or condition is not set.

A task can wait for one event bit or a combination of event bits. Another task or an appropriate ISR-related API can set bits to indicate that events have occurred.

Example: A device must initialize three subsystems before starting normal operation:
  • Bit 0: Sensor initialized.
  • Bit 1: Communication initialized.
  • Bit 2: Storage initialized.
The application can wait until all three bits are set before allowing the main application task to proceed.

2. Event Bits and Bit Representation

An event group stores multiple event conditions in a bit pattern. Consider the following simplified eight-bit illustration: 

Bit position:  7  6  5  4  3  2  1  0

Event bits:    0  0  0  0  0  1  1  0

Binary value:  00000110

In this example:

  • Bit 0 = 0: Event 0 is not set.
  • Bit 1 = 1: Event 1 is set.
  • Bit 2 = 1: Event 2 is set.
  • All other displayed bits are zero.

Example Event-Bit Definitions

#define EVENT_SENSOR_READY    (1U << 0)
#define EVENT_UART_READY      (1U << 1)
#define EVENT_STORAGE_READY   (1U << 2)
#define EVENT_NETWORK_READY   (1U << 3)

These definitions assign a unique bit position to each application condition. Bitwise operations allow the application to combine multiple event masks.

The eight-bit diagram is only an illustration. The actual number of usable event bits depends on the FreeRTOS configuration and port. Some event-group bits are reserved internally by the kernel.

3. Why Are Event Groups Required?

A binary semaphore can represent one pending token, while an event group can represent several independent conditions in a single synchronization object.

Example: Embedded Device Startup

Suppose an embedded device contains:

  1. Temperature sensor.
  2. UART communication interface.
  3. Data storage subsystem.
  4. Network interface.

The main application task should begin its operation only after the required subsystems are initialized. 

Sensor initialized     -> Bit 0 = 1
UART initialized       -> Bit 1 = 1
Storage initialized    -> Bit 2 = 1
Network initialized    -> Bit 3 = 1

The application can wait for all four conditions or only a selected combination, depending on its startup requirements.

4. Basic Event Group Operations

FreeRTOS provides APIs to create an event group, set or clear bits, read the current bit pattern, and wait for specified conditions.

FunctionPurpose
xEventGroupCreate()Create an event group dynamically.
xEventGroupSetBits()Set one or more event bits.
xEventGroupClearBits()Clear selected event bits.
xEventGroupGetBits()Read the current event-bit pattern.
xEventGroupWaitBits()Wait for selected event conditions.
vEventGroupDelete()Delete an event group.
Event-group APIs are declared in event_groups.h. Include both FreeRTOS.h and event_groups.h in a project that uses these functions.

5. Event Groups vs Semaphores

FeatureEvent GroupSemaphore
RepresentationCollection of event bitsOne token or a count of tokens
Multiple conditionsCan represent multiple independent conditionsUsually represents one synchronization or counting condition
Wait behaviorCan wait for any or all selected bitsWaits for a token
Data transferDoes not transfer payload dataDoes not transfer payload data
Typical applicationWait for several subsystem conditionsSignal an event or manage resource tokens

Event groups do not replace every semaphore. Choose the object according to the synchronization requirement.

6. Event Groups vs Queues

FeatureEvent GroupQueue
PurposeSignal Boolean conditionsTransfer data items
PayloadEvent bits onlyFixed-size copied items
Multiple conditionsYesApplication must interpret queued items
Preserves every occurrenceNo; repeated setting of an already-set bit coalescesCan preserve queued items until capacity is reached
Typical useSubsystem readinessSensor readings and commands
Event bits represent conditions, not event counters. If the same bit is set repeatedly before it is cleared, the event group still shows that bit as set only once. Use a queue or counting semaphore when every occurrence must be recorded.

7. Practical Applications of Event Groups

Application 1 – Sensor Initialization

A monitoring task waits until all required sensors report that initialization has completed.

Application 2 – Network Connectivity

A communication task waits for network-connected and configuration-ready conditions before transmitting application data.

Application 3 – Multi-Task Operation Completion

A controller waits for multiple processing tasks to complete their assigned operations before starting the next stage.

Application 4 – Embedded System Startup

A central application task waits for communication, storage, and peripheral initialization flags.

Application 5 – System State Management

An application uses event bits to represent operating conditions such as calibration complete, fault detected, or data ready.

8. Conceptual Example – Waiting for Multiple Conditions

Consider a controller that requires both sensor initialization and UART initialization before sending measurement data. 

#define SENSOR_READY   (1U << 0)
#define UART_READY     (1U << 1)

Required conditions:

SENSOR_READY = 1
UART_READY   = 1

Combined mask:

SENSOR_READY | UART_READY

Binary representation:

00000011

The application waits for the combined mask with an all-bits condition. The next lessons explain the actual FreeRTOS API and the wait-any and wait-all options.

9. Important Design Considerations

  • Assign unique bit positions to independent conditions.
  • Define clearly which task or ISR is allowed to set each bit.
  • Understand whether bits are persistent state indicators or temporary notifications.
  • Choose whether the application needs any-bit or all-bit waiting.
  • Consider whether clearing bits on exit is appropriate.
  • Do not use event groups to transfer sensor values or structured data.
  • Remember that multiple tasks may observe the same event bits.
  • Coordinate clear-on-exit behavior when several tasks wait on shared bits.
  • Check return values from creation and other APIs.
  • Consider event-group bit limitations for the selected FreeRTOS port.

11. Lesson Summary

  • An event group is a collection of event bits.
  • Each bit represents a Boolean condition or event state.
  • Tasks can wait for one or multiple event conditions.
  • Event groups are useful for coordinating subsystem initialization and multi-task operation.
  • They do not transfer application payload data.
  • Repeated setting of an already-set bit does not count multiple event occurrences.
  • FreeRTOS event groups support synchronization using any-bit and all-bit conditions.
  • Correct bit allocation and clearing rules are important in multi-task applications.
