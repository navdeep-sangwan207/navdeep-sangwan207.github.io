Lesson 05 – Introduction to FreeRTOS Software Timers

RTOS & FreeRTOS Chapter Index Learning Portal

Lesson Overview

A software timer is a FreeRTOS kernel object that allows an application to schedule a function to execute after a specified number of RTOS ticks. A timer can be configured to expire once or repeatedly.

Software timers are useful for periodic monitoring, delayed actions, timeout handling, status updates, and other time-based application operations without dedicating a separate task to each timer.

Learning Objectives

  • Understand the concept of a software timer.
  • Understand the role of the RTOS tick count.
  • Differentiate software timers from hardware timers.
  • Understand one-shot and auto-reload timers.
  • Learn the timer callback concept.
  • Understand the timer service task.
  • Identify software timer applications and limitations.

1. What Is a Software Timer?

A software timer is managed by the FreeRTOS kernel. When the configured period expires, the kernel schedules the timer's callback function to execute in the context of the timer service task.

The timer uses the RTOS tick count to track the passage of time. It does not require a separate hardware timer peripheral for each software timer.

Example: A controller must check its communication status every five seconds. A software timer can invoke a callback every five seconds to notify an application task to perform the check.

2. Why Are Software Timers Required?

Without software timers, developers may create additional tasks or use repeated delay operations for time-based actions. A software timer provides a centralized kernel mechanism for managing multiple timer expirations.

Typical Requirements

  • Generate periodic status notifications.
  • Check communication timeouts.
  • Schedule delayed application actions.
  • Monitor periodic system conditions.
  • Trigger a task to perform maintenance operations.
  • Implement retry intervals.
  • Generate periodic application events.
A software timer callback should generally notify a task or submit a short operation. Long-running processing should be performed in an application task.

4. Software Timer vs Hardware Timer

FeatureSoftware TimerHardware Timer
ImplementationManaged by RTOS kernel.Implemented by a hardware peripheral.
Time baseRTOS tick count.Hardware counter or clock.
Callback contextTimer service task context.Often hardware interrupt context, depending on design.
PrecisionLimited by tick resolution and scheduling latency.Can provide finer hardware timing resolution.
CPU usageUses CPU time when the timer service task executes.Counter may operate independently of CPU execution.
Typical useApplication delays and periodic notifications.PWM, input capture, precise waveform timing, and hardware events.
A FreeRTOS software timer is not a replacement for every hardware timer. Precise waveform generation, motor-control PWM, and time-critical capture operations normally require appropriate hardware peripherals.

5. Types of FreeRTOS Software Timers

FreeRTOS provides two commonly used timer modes:

A. One-Shot Timer

A one-shot timer expires once after its configured period. After expiry, it becomes inactive until it is started again.

     v
Period expires
     |
     v
Callback executes
     |
     v

Applications:

  • Communication timeout.
  • Delayed shutdown request.
  • Temporary notification.
  • One-time retry delay.

B. Auto-Reload Timer

An auto-reload timer automatically reloads its period after expiry and continues generating periodic expirations while active.

Applications:

  • Periodic system monitoring.
  • Regular status reporting.
  • Periodic task notification.
  • Recurring maintenance operations.

6. Timer Period and RTOS Tick

The timer period is configured in RTOS ticks. The duration represented by one tick depends on configTICK_RATE_HZ. 

#define configTICK_RATE_HZ 1000

With a tick rate of 1000 Hz, one tick represents a nominal 1 millisecond interval.

Milliseconds to Ticks

TickType_t timerPeriod;

timerPeriod = pdMS_TO_TICKS(5000);

This requests a timer period corresponding to approximately five seconds at the configured tick rate.

Tick RateNominal Tick IntervalApproximate Ticks for 1 Second
100 Hz10 ms100
250 Hz4 ms250
500 Hz2 ms500
1000 Hz1 ms1000
Timer expiry is tick-based. Actual callback execution can occur later because the timer service task must be scheduled and process the expiry. A software timer is not a hard real-time precision guarantee.

7. Timer Callback Function

A timer callback is an application-defined function that executes when a software timer expires.

General Callback Prototype

void TimerCallback(TimerHandle_t xTimer);

The callback receives the handle of the timer that expired. The application can use this handle to identify the timer or retrieve its associated timer ID.

Example Callback

void StatusTimerCallback(TimerHandle_t xTimer)
{
    /* Perform a short operation */
    /* Or notify an application task */
}

Callback Execution Rules

  • Callbacks execute in timer service task context, not hardware ISR context.
  • Keep callbacks short and non-blocking.
  • Do not call APIs that block waiting for a resource.
  • Do not use vTaskDelay() inside a timer callback.
  • Use a queue or task notification to transfer work to another task.
  • Remember that a long callback delays processing of other timer commands and callbacks.

8. Timer Service Task Configuration

The timer service task is responsible for processing timer commands and executing timer callbacks.

The following configuration options are important when software timers are enabled: 

#define configUSE_TIMERS                 1

#define configTIMER_TASK_PRIORITY        3

#define configTIMER_QUEUE_LENGTH         10

#define configTIMER_TASK_STACK_DEPTH     256
ConfigurationPurpose
configUSE_TIMERSEnables or disables software timer functionality.
configTIMER_TASK_PRIORITYSets the timer service task priority.
configTIMER_QUEUE_LENGTHSets the capacity of the timer command queue.
configTIMER_TASK_STACK_DEPTHSets the timer service task stack depth.
The numerical values shown are illustrative configuration examples, not universal recommended settings. Choose them based on the application, selected port, kernel version, command traffic, and callback stack requirements.

9. Basic Software Timer Example

Objective

Create a one-shot timer with a five-second period and execute a callback when the timer expires.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "timers.h"

static TimerHandle_t xOneShotTimer;

void TimerCallback(TimerHandle_t xTimer)
{
    /* Timer expiry notification */
    /* Keep callback short */
}

int main(void)
{
    xOneShotTimer = xTimerCreate(
        "OneShot",
        pdMS_TO_TICKS(5000),
        pdFALSE,
        NULL,
        TimerCallback
    );

    if (xOneShotTimer == NULL)
    {
        for (;;)
        {
            /* Timer creation failed */
        }
    }

    if (xTimerStart(xOneShotTimer, 0) != pdPASS)
    {
        for (;;)
        {
            /* Timer start command was not queued */
        }
    }

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Explanation

  1. Include the timer header.
  2. Declare a timer handle.
  3. Define a callback function.
  4. Create a one-shot timer with a five-second period.
  5. Check whether timer creation succeeded.
  6. Submit the start command to the timer command queue.
  7. Start the scheduler.
  8. When the timer expires, the callback executes in timer service task context.
This example illustrates the timer API sequence. In a production application, start timers from a suitable task after the scheduler has started when command processing and error recovery need to be managed at runtime.

10. Important Timer Design Considerations

  • Choose one-shot or auto-reload mode according to the application requirement.
  • Convert time intervals using pdMS_TO_TICKS().
  • Ensure the timer service task has adequate stack space and priority.
  • Choose sufficient timer command queue capacity.
  • Check timer creation and command-submission return values.
  • Keep callback execution short.
  • Use queues or task notifications for lengthy processing.
  • Do not assume a successful timer command submission means the command has already been processed.
  • Consider tick resolution and timer-service-task scheduling latency.
  • Do not use software timers for precision waveform generation.

13. Lesson Summary

  • Software timers provide time-based operations managed by the FreeRTOS kernel.
  • Timer periods are expressed in RTOS ticks.
  • One-shot timers expire once.
  • Auto-reload timers expire repeatedly.
  • Timer callbacks execute in timer service task context.
  • The timer service task processes timer commands and expirations.
  • Timer command queues have finite capacity.
  • Callbacks should be short and non-blocking.
  • Software timers are useful for application timing, but not a substitute for precision hardware timers.
