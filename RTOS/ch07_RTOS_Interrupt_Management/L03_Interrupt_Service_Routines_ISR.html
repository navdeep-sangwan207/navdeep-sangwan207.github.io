1. Introduction to ISR

An Interrupt Service Routine (ISR), also called an interrupt handler, is a special routine executed by the processor when an interrupt or exception is accepted.

The purpose of an ISR is to service the interrupt source, acknowledge the event when necessary, and perform the minimum processing required before normal execution resumes or another task is scheduled.

Definition: An ISR is a routine associated with an interrupt source or exception vector that executes in response to an accepted interrupt or exception.

Examples include:

  • Timer interrupt handler.
  • UART receive interrupt handler.
  • ADC conversion-complete handler.
  • External interrupt handler.
  • CAN communication interrupt handler.

2. Why Are ISRs Required?

Embedded devices generate events independently of the main program. An ISR provides a mechanism to respond to these events without continuously polling each device.

Example: UART reception

When a UART peripheral receives a character, it can generate an interrupt. The processor executes the UART ISR to read the received data.

Example: Timer event

When a timer reaches its configured match value, it can generate an interrupt. The timer ISR handles the event and may update a counter or signal another part of the application.

Example: ADC conversion

When an ADC conversion completes, an interrupt can notify the processor that the conversion result is ready.

3. ISR Execution Sequence

The general sequence of interrupt handling is:

  1. A peripheral or external device generates an interrupt request.
  2. The processor or interrupt controller receives the request.
  3. The processor checks interrupt enable, priority, and masking conditions.
  4. The processor accepts the interrupt.
  5. The required execution context is saved according to the architecture and exception mechanism.
  6. Control transfers to the interrupt handler.
  7. The ISR services the interrupt source.
  8. The ISR acknowledges or clears the interrupt condition when required.
  9. The handler completes its exception-return sequence.
  10. The processor resumes execution or performs a scheduling decision.
The processor does not necessarily save every general-purpose register automatically. The exact context-saving mechanism depends on the architecture, compiler, interrupt wrapper, and operating-system port.

4. Basic ISR Structure

A generic ISR can be represented as follows:

void TIMER_ISR(void)
{
    // 1. Identify the interrupt source

    // 2. Read or capture required information

    // 3. Acknowledge or clear the interrupt

    // 4. Perform minimum required processing

    // 5. Signal a task if necessary
}

This is conceptual pseudocode. Actual ISR declarations and interrupt acknowledgement procedures depend on the microcontroller, compiler, and interrupt controller.

5. Types of ISR

5.1 Timer ISR

Handles timer-related events such as match conditions, overflow, or periodic timing events.

void TIMER_ISR(void)
{
    Clear_Timer_Interrupt_Flag();
    timer_event_count++;
}

5.2 UART ISR

Handles serial communication events such as received data, transmit-buffer availability, or error conditions.

void UART_ISR(void)
{
    if(UART_Receive_Data_Available())
    {
        received_byte = UART_Read_Data();
    }

    Clear_Or_Service_UART_Interrupt();
}

5.3 External interrupt ISR

Handles configured external input events, such as a button press or fault signal.

void EXTERNAL_ISR(void)
{
    Read_External_Event_Status();
    Acknowledge_External_Interrupt();
    external_event_flag = 1;
}

5.4 ADC ISR

Handles ADC conversion-complete events.

void ADC_ISR(void)
{
    adc_result = Read_ADC_Result();
    Clear_ADC_Interrupt_Status();
}
These examples are illustrative. A real ISR must use the exact peripheral status and acknowledgement procedure documented for the selected MCU.

7. ISR Execution Time

ISR execution time is the processor time consumed by the interrupt handler.

ISR Execution Time = ISR Completion Time − ISR Start Time

For example, suppose an ISR starts at 100 microseconds and completes at 108 microseconds.

Execution Time = 108 − 100 = 8 µs

The ISR consumes 8 microseconds of processor execution time in this example.

Long-running ISRs can delay:

  • Other interrupt handlers.
  • Higher-level application processing.
  • RTOS task execution.
  • Time-critical control operations.
ISR execution time is not the same as interrupt latency. Latency measures the delay before ISR execution begins; execution time measures the duration of the handler itself.

8. ISR Design Best Practices

8.1 Keep the ISR short

Perform only the essential operations needed to service the interrupt.

8.2 Avoid blocking operations

Do not use task delays, blocking queue receives, or blocking semaphore waits inside an ISR.

8.3 Avoid long loops

Large processing loops increase interrupt execution time and can delay other work.

8.4 Avoid unnecessary function calls

Use small, predictable operations. Function calls are not inherently prohibited, but their execution time and behavior must be considered.

8.5 Protect shared data

Variables shared between an ISR and tasks must be accessed safely. The required protection depends on data width, processor atomicity, compiler behavior, and concurrency design.

8.6 Acknowledge the interrupt source

Follow the peripheral documentation to clear or service the interrupt condition correctly.

8.7 Defer lengthy processing

Move complex calculations, formatting, protocol processing, and lengthy application operations to an RTOS task.

9. What Should Not Be Done Inside an ISR?

Do not assume that marking a variable volatile makes all shared-data operations safe. Volatile does not provide mutual exclusion or guarantee atomic read-modify-write operations.

10. ISR and RTOS Task Communication

An ISR should generally perform the urgent hardware-level work and notify an RTOS task to perform longer processing.

Example: UART receive

  1. UART receives a byte.
  2. UART interrupt is generated.
  3. UART ISR reads the byte.
  4. ISR sends the byte to an RTOS queue using an ISR-safe API.
  5. A task waiting on the queue becomes ready.
  6. The scheduler may select the task if scheduling conditions permit.
  7. The task processes the received data.
void UART_ISR(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;
    uint8_t data;

    data = UART_Read_Data();

    xQueueSendFromISR(
        uartQueue,
        &data,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(higherPriorityTaskWoken);
}

This example illustrates the common FreeRTOS queue-from-ISR pattern. The queue must already be created and shared correctly, and the exact yield macro and interrupt-priority rules depend on the selected FreeRTOS port.

This code is not directly validated for LPC2129/Keil. Do not assume a supported FreeRTOS port or a working build for that target without verifying the actual port implementation.

11. ISR-Safe RTOS APIs

An ISR-safe API is specifically designed to be called from interrupt context.

Examples from FreeRTOS include:

Task-context APIISR-context counterpart
xQueueSend()xQueueSendFromISR()
xQueueReceive()No general blocking receive-from-ISR equivalent.
xSemaphoreGive()xSemaphoreGiveFromISR()
Task notification APIsTask notification FromISR variants.
Event group set bitsxEventGroupSetBitsFromISR(), where supported by the configuration.

ISR-safe APIs do not permit the ISR to block. They are designed to perform permitted kernel operations without waiting for another task or event.

Always check the FreeRTOS API documentation for the exact function, port restrictions, and configuration requirements.

12. Nested Interrupts and ISR Execution

Some processors and interrupt controllers support nested interrupts. A higher-priority interrupt may be allowed to interrupt a lower-priority handler.

Nested interrupt handling requires careful consideration of:

  • Interrupt priority configuration.
  • Interrupt masking.
  • Stack usage.
  • Register preservation.
  • Re-entrant code requirements.
  • Shared data protection.

Nested interrupts are not automatically enabled in every system. Their behavior depends on the processor, controller, startup code, and interrupt-handler implementation.

13. ISR in LPC2129 – ARM7TDMI-S

The LPC2129 uses an ARM7TDMI-S core and a Vectored Interrupt Controller (VIC).

Important points:

  • IRQ and FIQ are separate processor exception types.
  • IRQ handlers execute in IRQ mode.
  • FIQ handlers execute in FIQ mode.
  • IRQ and FIQ use banked processor registers.
  • The VIC supports vectored IRQ handling.
  • Peripheral interrupt status must be serviced according to the peripheral specification.
  • The IRQ exception-return sequence must correctly restore processor state.

Important VIC registers

RegisterFunction
VICIntEnableEnables selected interrupt sources.
VICIntEnClrDisables selected interrupt sources.
VICIntSelectSelects IRQ or FIQ for interrupt sources.
VICVectAddrProvides the vectored IRQ handler address and participates in the VIC service protocol.
VICVectCntl0–15Configures vectored interrupt slots.

VICFIQStatusReports enabled pending FIQ sources.
LPC2129 is an ARM7 device. Do not use Cortex-M NVIC registers, Cortex-M exception-entry assumptions, or Cortex-M-specific FreeRTOS interrupt-priority configuration in its ISR implementation.

14. Conceptual LPC2129 Timer ISR

The following example shows the logical structure of a timer interrupt handler. It is not a complete register-level implementation.

#include <LPC21xx.h>

volatile unsigned int timer_count = 0;

void Timer0_ISR(void)
{
    // Service Timer 0 interrupt
    T0IR = 1U << 0;

    // Record timer event
    timer_count++;

    // Complete VIC IRQ service
    VICVectAddr = 0;
}

In this conceptual example:

  • T0IR bit 0 represents the Timer 0 MR0 interrupt flag.
  • Writing a one to the corresponding T0IR bit clears that flag.
  • timer_count records the number of serviced events.
  • Writing to VICVectAddr completes the vectored IRQ service protocol.
This fragment omits timer configuration, VIC slot configuration, startup/vector integration, compiler-specific ISR declaration, and exception-return details. A working Keil project needs all of these elements configured correctly.

15. ISR Debugging and Testing

ISR behavior should be tested systematically.

Suggested checks

  1. Verify that the peripheral interrupt source is enabled.
  2. Verify the interrupt controller configuration.
  3. Check the interrupt vector or handler address.
  4. Set a breakpoint at the ISR entry.
  5. Trigger the event using a supported simulator mechanism.
  6. Inspect peripheral status registers.
  7. Check whether the interrupt flag is cleared correctly.
  8. Verify that the processor returns to the expected execution flow.
  9. Inspect shared variables and task notifications.

Common ISR problems

Incorrect shared dataRace condition or non-atomic data access.

Keil simulator note: Register inspection and exception-flow debugging can help verify software logic. Actual interrupt timing and external hardware behavior require suitable simulator support or physical hardware testing.

17. Lesson Summary

  • An ISR services an accepted interrupt or exception.
  • ISR execution follows architecture- and compiler-specific rules.
  • Interrupt acknowledgement prevents unwanted repeated servicing.
  • ISRs should be short and predictable.
  • Blocking task operations should not be used inside an ISR.
  • RTOS applications can use ISR-safe queues, semaphores, or notifications.
  • Long processing should normally be deferred to a task.
  • LPC2129 uses ARM7 exception handling and a VIC.
  • Correct exception return and shared-data handling are essential.
