Interrupt Latency and Response Time

1. Introduction

Interrupt latency and interrupt response time are important performance parameters in real-time embedded systems.

When a hardware event occurs, the processor may not begin executing its ISR immediately. It may first need to complete an instruction, wait for an interrupt mask to be cleared, resolve interrupt priority, and perform exception-entry operations.

These delays influence how quickly the system can react to external events.

Interrupt latency is the elapsed time from the defined interrupt request event to the start of execution of the corresponding ISR.
Interrupt response time is the elapsed time from the defined interrupt request event to a specified response point. The response point must be clearly defined, such as ISR entry, completion of a critical ISR action, or completion of the entire handler.

2. Interrupt Latency

Interrupt latency measures how long the processor takes to begin executing the interrupt handler after an interrupt request becomes eligible for service.

Interrupt Latency = ISR Start Time − Interrupt Request Time

Example

A timer interrupt request becomes active at 100 µs. The first instruction of its ISR executes at 106 µs.

Latency = 106 − 100 = 6 µs

Answer: Interrupt latency is 6 microseconds.

3. Components of Interrupt Latency

Interrupt latency may contain several sources of delay.

ComponentDescription
Current instruction completionThe processor may need to complete or reach an architecturally valid point before accepting the interrupt.
Interrupt maskingThe interrupt may remain pending while the relevant interrupt class is masked.
Higher-priority interrupt interferenceAnother interrupt may be serviced first.
Interrupt arbitrationThe controller may need to select among pending requests.
Exception-entry overheadProcessor state handling and exception entry consume time.
Vector dispatchControl must reach the appropriate handler.
Memory and bus delaysInstruction fetches and data accesses may introduce additional delay.

A simplified conceptual model is:

L = I + M + A + E + V

Where:

  • L = interrupt latency.
  • I = instruction-completion delay.
  • M = masking delay.
  • A = arbitration or priority-related delay.
  • E = exception-entry overhead.
  • V = vector dispatch delay.
This is a conceptual decomposition. The terms must be defined so that no delay is counted twice. Actual processor timing may combine or overlap some operations.

4. Interrupt Masking and Its Effect

Interrupt masking temporarily prevents selected interrupts from being accepted by the processor.

For example, a program may briefly mask interrupts while updating shared data.

Disable_Interrupts();

Update_Shared_Data();

Enable_Interrupts();

If an interrupt request occurs while it is masked, the request may remain pending until the processor permits its acceptance, provided the interrupt source and controller retain the request.

Example

A maskable interrupt occurs at 100 µs. The relevant interrupt remains masked until 112 µs. After unmasking, the processor requires another 2 µs to enter the ISR.

Latency = (112 − 100) + 2
Latency = 14 µs

Answer: Interrupt latency is 14 µs.

Keep critical sections short. Excessive interrupt masking can increase latency and cause missed timing requirements.

5. Interrupt Priority and Latency

When multiple interrupt requests are pending, the processor or interrupt controller uses priority and masking rules to determine which interrupt is serviced.

A lower-priority interrupt may be delayed by a higher-priority interrupt.

Example

Consider two interrupt sources:

InterruptPriorityExecution Time
IRQ-AHigher5 µs
IRQ-BLower4 µs

Suppose IRQ-A is already being serviced when IRQ-B becomes pending. If IRQ-B cannot preempt IRQ-A, it must wait until the processor can service it.

Ignoring other overheads, the delay caused by IRQ-A is approximately 5 µs.

IRQ-B's total latency also includes its own exception-entry and dispatch delays.

6. ISR Execution Time vs Interrupt Latency

These two parameters describe different parts of interrupt handling.

ParameterMeaningExample
Interrupt latencyRequest to ISR start.6 µs
ISR execution timeISR start to ISR completion.10 µs
Request-to-handler completionRequest to completion of the ISR.16 µs
Request-to-Completion = Latency + ISR Execution Time

For the example:

6 + 10 = 16 µs

The processor begins the ISR after 6 µs and completes it 10 µs later.

7. Interrupt Response Time

Interrupt response time must be defined according to the required system action.

For example, an emergency shutdown interrupt may require the output to be placed in a safe state. In that application, ISR entry alone may not be the required response point.

Response Time = Required Response Completion − Interrupt Request Time

Example

A fault signal occurs at 50 µs. The processor starts the ISR at 55 µs. The ISR sets the safe-state output at 59 µs.

Response Time = 59 − 50 = 9 µs

Answer: The defined fault-response time is 9 µs.

8. Worked Numerical Problem 1 – Basic Latency

An interrupt request occurs at 200 µs. The ISR begins at 207 µs and completes at 215 µs.

Step 1: Calculate latency

L = 207 − 200 = 7 µs

Step 2: Calculate ISR execution time

C = 215 − 207 = 8 µs

Step 3: Calculate request-to-completion time

R = 215 − 200 = 15 µs

Answer: Latency = 7 µs, ISR execution time = 8 µs, and request-to-completion time = 15 µs.

9. Worked Numerical Problem 2 – Masking Delay

An interrupt occurs at 100 µs. The processor keeps the interrupt masked until 108 µs. ISR entry takes another 3 µs.

Solution

Masking Delay = 108 − 100 = 8 µs
Interrupt Latency = 8 + 3 = 11 µs

Answer: Interrupt latency is 11 µs.

10. Worked Numerical Problem 3 – Higher-Priority Interference

A lower-priority interrupt becomes pending while a higher-priority ISR is executing.

ParameterValue
Higher-priority ISR remaining execution time6 µs
Lower-priority interrupt entry overhead after waiting2 µs
Additional masking delay1 µs

Solution

Latency = 6 + 2 + 1
Latency = 9 µs

Answer: Under the stated simplified assumptions, the lower-priority interrupt latency is 9 µs.

11. Worked Numerical Problem 4 – Response Deadline

A fault interrupt must cause a safe-state action within 20 µs.

ParameterTime
Interrupt latency5 µs
ISR execution until safe-state action8 µs

Solution

Response Time = 5 + 8 = 13 µs

Deadline check:

13 µs ≤ 20 µs

Answer: The required response deadline is met with a margin of 7 µs under the stated timing assumptions.

12. Factors Affecting Interrupt Response

  • Processor clock frequency.
  • Instruction execution characteristics.
  • Interrupt masking duration.
  • Priority assignment.
  • Higher-priority interrupt load.
  • ISR execution time.
  • Memory wait states and bus contention.
  • Interrupt-controller configuration.
  • Critical-section implementation.
  • Compiler and exception-handler implementation.

13. Reducing Interrupt Latency

  1. Keep interrupt-disabled critical sections short.
  2. Assign interrupt priorities according to timing requirements.
  3. Keep high-priority ISRs short.
  4. Avoid unnecessary interrupt nesting and masking.
  5. Use efficient interrupt-vector configuration.
  6. Reduce avoidable memory and peripheral access delays.
  7. Use appropriate hardware peripherals for time-critical operations.
  8. Measure latency under representative worst-case interrupt load.
  9. Analyze higher-priority interference.
Do not reduce latency by blindly assigning the highest priority to every interrupt. Poor priority design can create starvation and excessive interference.

14. Interrupt Latency in RTOS

An RTOS application must distinguish between interrupt response and task response.

Consider a sensor interrupt that wakes a processing task.

  1. The sensor generates an interrupt.
  2. The processor accepts the interrupt.
  3. The ISR reads or acknowledges the sensor event.
  4. The ISR notifies a task using an ISR-safe mechanism.
  5. The task becomes ready.
  6. The scheduler selects the task when scheduling conditions permit.
  7. The task begins executing and processes the sensor data.

In this case, the task response includes additional scheduling delay after interrupt handling.

Event-to-Task Start = Interrupt Latency + ISR Work + Scheduling Delay

The equation is a simplified model. Any additional queueing, blocking, or processing stages must also be included when calculating the full event-to-action response.

15. FreeRTOS Example – Interrupt-to-Task Notification

The following conceptual example illustrates a task notified by an interrupt.

TaskHandle_t sensorTaskHandle;

void Sensor_ISR(void)
{
    BaseType_t higherPriorityTaskWoken = pdFALSE;

    Clear_Sensor_Interrupt();

    vTaskNotifyGiveFromISR(
        sensorTaskHandle,
        &higherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(higherPriorityTaskWoken);
}

void Sensor_Task(void *pvParameters)
{
    while(1)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        Process_Sensor_Data();
    }
}

Explanation:

  • The ISR acknowledges the sensor interrupt.
  • The ISR notifies the sensor task.
  • The task waits until notification is received.
  • The task performs the longer processing operation.
  • The ISR requests a yield if the port indicates that a higher-priority task was made ready.
This example follows the common FreeRTOS task-notification pattern. The task handle must be initialized correctly, and the ISR priority and yield mechanism must follow the actual port's requirements. It is not evidence of a working FreeRTOS port for LPC2129.

16. Measuring Interrupt Latency

Interrupt latency can be measured using hardware timing facilities or carefully designed instrumentation.

Method 1: Hardware timer

  1. Record a timestamp when the interrupt request is generated or externally observed.
  2. Capture another timestamp at ISR entry.
  3. Calculate the difference.

Method 2: GPIO instrumentation

  1. Generate an external interrupt signal.
  2. Set a GPIO pin as the first appropriate ISR action.
  3. Measure the time difference between the external event and GPIO transition using a logic analyzer or oscilloscope.

Method 3: Trace and debugger

Use supported trace facilities or debugger timestamps to examine event and ISR execution timing.

For reliable measurement, instrumentation overhead and timestamp resolution must be considered. The measured maximum is not automatically a proven worst-case latency bound.

17. LPC2129 Timing Considerations

The LPC2129 uses an ARM7TDMI-S processor.

Example clock configuration:

ClockFrequency
FOSC12 MHz
CCLK60 MHz
PCLK15 MHz

For a peripheral timer configured with:

PR = 14999

The timer counter increments every:

T = (PR + 1) / PCLK
T = 15000 / 15,000,000 = 1 ms

This timer configuration provides a 1 ms counter increment. It is useful for coarse timing but cannot directly resolve microsecond-scale interrupt latency.

ARM7TDMI-S does not provide the Cortex-M DWT cycle-counter facility. Keil simulator timestamps and timer models may not reproduce physical interrupt latency. Do not claim hardware-level timing accuracy from an unsupported simulation measurement.

18. Practical Activity – Interrupt Timing Analysis

Use the following hypothetical measurements to practice timing analysis:

ParameterMeasured Time
Interrupt request100 µs
ISR entry106 µs
Critical ISR action109 µs
ISR completion114 µs
Task start after notification120 µs

Calculate the following

  1. Interrupt latency.
  2. Time from ISR entry to critical action.
  3. Total ISR execution time.
  4. Request-to-critical-action response time.
  5. Request-to-task-start time.

Answers

  • Interrupt latency = 106 − 100 = 6 µs.
  • ISR entry to critical action = 109 − 106 = 3 µs.
  • ISR execution time = 114 − 106 = 8 µs.
  • Request-to-critical-action response = 109 − 100 = 9 µs.
  • Request-to-task-start time = 120 − 100 = 20 µs.

20. Lesson Summary

  • Interrupt latency measures interrupt request to ISR start.
  • Interrupt response time depends on the defined response point.
  • Interrupt masking, priority, exception entry, and bus delays influence latency.
  • ISR execution time is different from interrupt latency.
  • Interrupt response and task response are different timing measurements.
  • Short critical sections and efficient ISRs help reduce latency.
  • RTOS applications can notify tasks from ISRs using supported ISR-safe APIs.
  • Worst-case timing requires analysis beyond a single observed measurement.
  • LPC2129 timing must be evaluated with ARM7-compatible methods and realistic hardware validation.
