1. Introduction

An Interrupt Service Routine (ISR) is a special function executed in response to an interrupt request. ISRs are essential in embedded systems because they allow the processor to respond to hardware events without continuously polling peripheral status registers.

However, poorly designed interrupt handlers can increase interrupt latency, cause data loss, introduce race conditions, and affect real-time scheduling.

Therefore, ISR programming requires careful attention to execution time, interrupt priority, synchronization, hardware acknowledgement, and communication with RTOS tasks.

Primary design objective: An ISR should perform only the essential work required to service an interrupt safely and promptly. Longer processing should normally be deferred to an appropriate task or worker context.

2. Keep ISRs Short and Efficient

An ISR should execute quickly and have a predictable execution time.

Recommended operations

  • Identify the interrupt source.
  • Read the required peripheral status.
  • Capture essential data.
  • Acknowledge or clear the interrupt condition.
  • Update a small amount of shared state safely.
  • Notify a task or schedule deferred processing.

Operations to avoid

  • Long calculations.
  • Blocking delays.
  • Waiting for a mutex or semaphore.
  • Long polling loops.
  • Complex packet parsing.
  • File-system operations.
  • Blocking UART transmission.
  • Formatted output such as lengthy printf() calls.
A short ISR is not automatically a correct ISR. It must also acknowledge the peripheral correctly, preserve required data, and avoid losing interrupt events.

3. Use Deferred Interrupt Processing

Move non-urgent processing from the ISR to task context whenever practical.

Example: UART receive interrupt

The ISR should read the received byte and place it into a suitable buffer or queue. A communication task can assemble and validate the complete packet.

4. Use the Correct ISR-Safe RTOS APIs

RTOS APIs designed for task context may block or manipulate scheduler state in ways that are unsuitable for interrupt context.

FreeRTOS provides dedicated ISR-safe functions for supported communication mechanisms.

Task-context APIISR-safe API
xSemaphoreGive()xSemaphoreGiveFromISR()
xQueueSend()xQueueSendFromISR()
xTaskNotifyGive()vTaskNotifyGiveFromISR()
xTaskNotify()xTaskNotifyFromISR()
xEventGroupSetBits()xEventGroupSetBitsFromISR()

Important rules

  • Use only APIs documented as ISR-safe.
  • Do not call blocking task APIs from an ISR.
  • Do not use mutexes inside an ISR.
  • Check API return values where event loss is possible.
  • Use the appropriate ISR yield mechanism for the selected port.

5. Use the Higher-Priority-Task-Woken Mechanism Correctly

Some FreeRTOS ISR-safe APIs accept a pointer to xHigherPriorityTaskWoken.

This variable indicates whether an ISR operation has made a higher-priority task Ready.

Typical pattern

BaseType_t xHigherPriorityTaskWoken = pdFALSE;

/* Call an ISR-safe API here. */

portYIELD_FROM_ISR(xHigherPriorityTaskWoken);

The yield mechanism requests an appropriate context switch at the permitted point, normally as the ISR exits.

The exact yield macro and calling convention depend on the FreeRTOS port. Do not assume that the same macro signature applies to every processor architecture.

6. Acknowledge Interrupts Correctly

A peripheral interrupt source must be serviced according to the device's hardware documentation.

Depending on the peripheral, acknowledgement may require:

  • Reading a data register.
  • Writing a one to a status bit.
  • Clearing a pending flag.
  • Reading or writing a specific register sequence.
  • Disabling or re-enabling an interrupt source.

Incorrect acknowledgement can cause repeated interrupts, missed events, or an interrupt storm.

Do not assume that every interrupt flag is cleared by writing zero. Some hardware uses write-one-to-clear (W1C) status bits. Always follow the peripheral reference manual.

7. Avoid Unnecessary Interrupt Masking

Interrupt masking prevents selected interrupt requests from being serviced for a period of time.

Masking may be necessary when protecting shared data or performing a critical operation, but excessive masking increases interrupt latency.

Best practices

  • Keep critical sections as short as possible.
  • Mask only the required interrupt sources when supported.
  • Preserve and restore the previous interrupt state correctly.
  • Avoid long calculations while interrupts are masked.
  • Do not confuse scheduler suspension with interrupt masking.

On ARM7TDMI-S, the CPSR I bit masks IRQ exceptions and the F bit masks FIQ exceptions. These are processor-level controls, not substitutes for peripheral-specific interrupt control.

8. Handle Shared Data Safely

An ISR and a task may access the same variable or buffer. This can cause race conditions if access is not properly synchronized.

Example of shared data

volatile unsigned int eventCount = 0;

void Timer_IRQHandler(void)
{
    /* Acknowledge timer interrupt. */
    eventCount++;
}

void ApplicationTask(void *pvParameters)
{
    unsigned int localCount;

    for (;;)
    {
        localCount = eventCount;

        Process_Event_Count(localCount);

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

The volatile qualifier prevents certain compiler optimizations that would otherwise assume the variable cannot change unexpectedly. It does not make an operation atomic or provide complete synchronization.

Safer design considerations

  • Use naturally atomic access widths where guaranteed by the architecture.
  • Use suitable atomic operations or short critical sections.
  • Protect multi-field structures against inconsistent reads.
  • Use queues when transferring data simplifies synchronization.
  • Consider compiler and processor memory-ordering requirements.
A read-modify-write expression such as eventCount++ is not guaranteed to be atomic merely because the variable is declared volatile.

9. Use Appropriate Interrupt Priorities

Interrupt priorities determine which interrupt sources can preempt or delay other interrupt sources, subject to the processor and interrupt-controller design.

Priority design guidelines

  • Identify the most time-critical hardware events.
  • Keep high-priority handlers especially short.
  • Avoid unnecessary nesting.
  • Consider stack usage during nested interrupts.
  • Ensure interrupt masking does not violate deadlines.
  • Analyze the worst-case interference from other interrupt sources.

Interrupt priority and RTOS task priority are separate concepts. A high-priority interrupt does not automatically imply that its associated task has the highest task priority.

10. Handle Nested Interrupts Carefully

Nested interrupts occur when one interrupt handler is interrupted by another interrupt handler.

Although nesting can improve response for urgent sources, it also increases complexity.

Risks

  • Increased stack consumption.
  • Shared-data corruption.
  • Re-entrant function problems.
  • Longer worst-case execution paths.
  • More difficult debugging.

On ARM7TDMI-S, IRQ and FIQ have different exception behavior and banked registers. Nested handling must be designed according to the ARM architecture and the LPC2129 VIC configuration.

11. Prevent Interrupt Storms

An interrupt storm occurs when an interrupt source repeatedly generates requests without being properly serviced or controlled.

Possible causes

  • Interrupt status flag not cleared.
  • Incorrect peripheral configuration.
  • Electrical noise on an external interrupt pin.
  • Interrupt source continuously asserted.
  • Incorrect trigger selection.
  • Incorrect interrupt acknowledgement sequence.

Prevention

  • Inspect peripheral status registers.
  • Verify edge-triggered or level-triggered configuration.
  • Follow the hardware acknowledgement sequence.
  • Use suitable input filtering where available.
  • Record unexpected interrupt counts.
  • Provide a controlled fault-handling strategy.

12. Avoid Blocking and Long Polling in ISRs

An ISR must not wait for an operation that depends on another task or on an event that may not occur until the ISR finishes.

Incorrect conceptual example

void UART_IRQHandler(void)
{
    while (UART_TransmitBusy())
    {
        /* Waiting inside an ISR is undesirable. */
    }

    UART_SendByte('A');
}

Better approach

void UART_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Capture the received data. */
    /* Notify the communication task. */

    vTaskNotifyGiveFromISR(
        xCommunicationTaskHandle,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

The communication task can perform the longer transmission or processing operation using appropriate task-context APIs.

13. Manage ISR Stack Usage

Interrupt execution consumes stack space. Nested interrupts can increase the required stack depth.

Stack management guidelines

  • Avoid large local arrays in ISRs.
  • Avoid deep function-call chains.
  • Limit nested interrupt depth.
  • Consider exception-mode stack requirements.
  • Check the processor's stack allocation and initialization.
  • Use available debugging and stack-analysis facilities.

On ARM7TDMI-S, exception modes have banked stack pointers. IRQ and FIQ stack initialization must be considered during startup configuration.

14. Handle Queue and Buffer Overflow

Interrupts may generate data faster than a task can process it.

If the queue or buffer becomes full, the application must define how to handle the new event.

Possible strategies

  • Increase buffer capacity based on measured and analyzed traffic.
  • Use a suitable DMA or circular-buffer architecture.
  • Reduce unnecessary processing in the receiving task.
  • Record overflow counters.
  • Discard data according to a documented policy when loss is unavoidable.
  • Apply flow control when the communication protocol supports it.

Never silently assume that a queue-send operation always succeeds.

15. Debugging and Testing ISRs

Interrupt-related defects can be difficult to reproduce because their occurrence depends on timing and event ordering.

Recommended debugging techniques

  • Inspect interrupt enable and pending registers.
  • Verify peripheral status before and after acknowledgement.
  • Use counters to record interrupt occurrences.
  • Measure ISR duration using an available hardware timer or trace facility.
  • Inspect task states and priorities.
  • Monitor queue overflow and dropped-event counters.
  • Test burst traffic and simultaneous interrupt sources.
  • Test shared-data synchronization under repeated events.
The maximum ISR execution time observed during testing is not automatically a proven worst-case execution time. A complete timing argument must consider all relevant operating conditions and interference.

16. LPC2129 and Keil uVision Considerations

The LPC2129 uses an ARM7TDMI-S processor core and a Vectored Interrupt Controller (VIC).

Important architecture details

  • ARM7TDMI-S supports IRQ and FIQ exceptions.
  • The CPSR I bit masks IRQ exceptions.
  • The CPSR F bit masks FIQ exceptions.
  • The processor uses banked registers in exception modes.
  • The LPC2129 VIC supports interrupt-source selection and vectored IRQ handling.
  • VICVectAddr is involved in vectored IRQ handler dispatch and end-of-interrupt handling.

Simulator activity

  1. Open an LPC2129 project in Keil uVision.
  2. Inspect the processor registers and CPSR state.
  3. Review the interrupt vector and handler structure.
  4. Inspect relevant VIC registers where supported by the simulator.
  5. Set breakpoints at ISR entry and exit.
  6. Inspect variables modified by the ISR.
  7. Step through the handler and verify the intended control flow.
Keil uVision simulation can help inspect software execution and registers, but it does not guarantee complete peripheral behavior or physical interrupt timing. Do not assume a working FreeRTOS LPC2129 port without verifying a compatible port and build configuration.

17. Worked Numerical Problem 1 – ISR Execution Time

An ISR performs the following operations:

OperationTime
Read status register2 µs
Capture data4 µs
Acknowledge interrupt2 µs
Notify task3 µs

Solution

ISR Time = 2 + 4 + 2 + 3 = 11 µs

Answer: The ISR execution time is 11 µs under the stated assumptions.

18. Worked Numerical Problem 2 – Interrupt Utilization

An interrupt occurs 500 times per second. Each ISR requires 20 µs of CPU time.

Solution

CPU Time per Second = 500 × 20 µs = 10,000 µs
Interrupt CPU Utilization = 10,000 / 1,000,000 × 100
= 1%

Answer: The ISR consumes 1% of one CPU's time, assuming the stated interrupt rate and execution time remain constant.

19. Worked Numerical Problem 3 – Interrupt Stack Usage

An application has an estimated interrupt stack requirement of 96 bytes for the first ISR. A nested ISR requires another 64 bytes. Assume both stack requirements are additive and exclude any additional margin.

Solution

Combined Stack Requirement = 96 + 64 = 160 bytes

Answer: The estimated combined requirement is 160 bytes. Actual stack allocation should include additional space for exception entry, saved context, compiler-generated code, function calls, and worst-case nesting.

20. ISR Programming Checklist

  • Identify the exact interrupt source.
  • Confirm the correct interrupt vector and handler.
  • Use the correct peripheral acknowledgement sequence.
  • Keep ISR execution short and bounded.
  • Avoid blocking and sleeping operations.
  • Use documented ISR-safe RTOS APIs.
  • Handle queue and buffer overflow.
  • Protect shared data correctly.
  • Verify interrupt priorities and masking.
  • Account for nested interrupt stack usage.
  • Measure and analyze response time.
  • Test repeated events and fault conditions.

23. Lesson Summary

  • ISRs should be short, efficient, and predictable.
  • Longer operations should normally be deferred to task context.
  • Only documented ISR-safe RTOS APIs should be used in interrupt context.
  • Peripheral interrupt conditions must be acknowledged correctly.
  • Shared data requires suitable synchronization.
  • Interrupt masking, priority, and nesting affect response time.
  • Stack usage and queue overflow must be considered.
  • Testing must include repeated events, interference, and fault conditions.
