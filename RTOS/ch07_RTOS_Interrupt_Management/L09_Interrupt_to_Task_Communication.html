Interrupt-to-Task Communication

1. Introduction

In a real-time operating system, hardware interrupts and application tasks often need to exchange information.

A hardware peripheral may generate an interrupt when data is received, a timer expires, a sensor conversion completes, or an external signal changes.

The ISR handles the immediate event, while an RTOS task performs the remaining processing. A communication mechanism is needed to transfer event information or data from the ISR to the task.

Interrupt-to-task communication is the transfer of event notifications or data from interrupt context to task context using synchronization and communication mechanisms supported by the RTOS.

2. Why Is Interrupt-to-Task Communication Required?

Consider a UART peripheral receiving bytes from an external device.

The UART interrupt handler must read the received data before the hardware receive register or FIFO overruns. However, parsing a complete communication packet may require considerably more processing.

A communication task can perform the longer operation without extending the ISR unnecessarily.

Typical applications

  • UART receive interrupt to communication task.
  • ADC conversion-complete interrupt to sensor-processing task.
  • Timer interrupt to periodic control task.
  • GPIO external interrupt to event-handling task.
  • DMA completion interrupt to data-processing task.
  • CAN receive interrupt to message-processing task.

5. Interrupt-to-Task Communication Using Binary Semaphores

A binary semaphore is useful when the ISR only needs to signal that an event has occurred.

Working principle

  1. The task waits for the semaphore.
  2. The hardware generates an interrupt.
  3. The ISR performs essential hardware servicing.
  4. The ISR gives the semaphore using an ISR-safe API.
  5. The task becomes Ready.
  6. The scheduler runs the task when scheduling rules permit.

FreeRTOS example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xInterruptSemaphore;

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xInterruptSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            Process_Interrupt_Event();
        }
    }
}

void Hardware_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the peripheral interrupt here. */

    xSemaphoreGiveFromISR(
        xInterruptSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

int main(void)
{
    xInterruptSemaphore = xSemaphoreCreateBinary();

    if (xInterruptSemaphore != NULL)
    {
        xTaskCreate(
            ProcessingTask,
            "Processing",
            256,
            NULL,
            2,
            NULL
        );

        /* Configure and enable the hardware interrupt here. */
        vTaskStartScheduler();
    }

    for (;;);
}
Create the semaphore and task before enabling the interrupt. The ISR must not run while the semaphore handle is invalid. Check the return value of the ISR-safe API if event loss matters.

6. Interrupt-to-Task Communication Using Counting Semaphores

A counting semaphore can represent the number of pending events, up to its configured maximum count.

For example, a pulse counter interrupt may occur repeatedly. Each ISR gives the semaphore, and the task takes it to account for events.

Conceptual example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xPulseSemaphore;

void Pulse_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Clear or acknowledge the pulse interrupt. */

    xSemaphoreGiveFromISR(
        xPulseSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void PulseProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xPulseSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            Update_Pulse_Count();
        }
    }
}

The semaphore count must be large enough for expected bursts. If the count reaches its maximum, additional give operations cannot increase it.

7. Interrupt-to-Task Communication Using Queues

A queue transfers data from an ISR to a task. Unlike a binary semaphore, a queue can preserve individual data items in FIFO order, provided capacity is available and the application handles overflow.

UART receive example

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include <stdint.h>

QueueHandle_t xUARTQueue;

void UART_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    uint8_t receivedByte;

    /* Read from the actual UART data register. */
    receivedByte = UART_ReadByte();

    if (xQueueSendFromISR(
            xUARTQueue,
            &receivedByte,
            &xHigherPriorityTaskWoken) != pdPASS)
    {
        /* Record or handle queue overflow. */
    }

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void UARTProcessingTask(void *pvParameters)
{
    uint8_t receivedByte;

    for (;;)
    {
        if (xQueueReceive(
                xUARTQueue,
                &receivedByte,
                portMAX_DELAY) == pdTRUE)
        {
            Process_Received_Byte(receivedByte);
        }
    }
}

Advantages

  • Transfers actual data.
  • Maintains FIFO ordering for queued items.
  • Supports task blocking while waiting for data.
  • Separates hardware servicing from application processing.

8. Interrupt-to-Task Communication Using Task Notifications

FreeRTOS direct-to-task notifications provide an efficient way to signal a specific task.

They are especially useful when one ISR needs to notify one designated task without creating a separate queue or semaphore object.

Example

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t xSensorTaskHandle;

void ADC_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Read or acknowledge ADC completion status here. */

    vTaskNotifyGiveFromISR(
        xSensorTaskHandle,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        Process_ADC_Result();
    }
}

With this notification pattern, the task waits until an event is signaled. The notification count can accumulate events, subject to its finite counter capacity and the selected notification operation.

9. Interrupt-to-Task Communication Using Event Groups

Event groups allow a task to wait for one or more event bits.

They are useful when an application needs to coordinate several conditions, such as sensor-ready, communication-ready, and conversion-complete events.

FreeRTOS provides xEventGroupSetBitsFromISR() for setting event bits from interrupt context on supported configurations.

Conceptual example

#include "FreeRTOS.h"
#include "task.h"
#include "event_groups.h"

#define ADC_READY_BIT  (1U << 0)

EventGroupHandle_t xSystemEvents;

void ADC_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge ADC interrupt. */

    xEventGroupSetBitsFromISR(
        xSystemEvents,
        ADC_READY_BIT,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        xEventGroupWaitBits(
            xSystemEvents,
            ADC_READY_BIT,
            pdTRUE,
            pdTRUE,
            portMAX_DELAY
        );

        Process_ADC_Result();
    }
}
FreeRTOS event-group operations requested from an ISR may be deferred through the timer service task. The timer service task and queue must be configured appropriately. Check the return value of the ISR API and the selected FreeRTOS version and port documentation.

11. ISR-Safe APIs in FreeRTOS

FreeRTOS provides dedicated API functions for operations that must be performed from interrupt context.

Task-context APIISR-safe counterpart
xSemaphoreGive()xSemaphoreGiveFromISR()
xQueueSend()xQueueSendFromISR()
xQueueReceive()Do not use the ordinary blocking receive API in an ISR.
xTaskNotifyGive()vTaskNotifyGiveFromISR()
xTaskNotify()xTaskNotifyFromISR()
xEventGroupSetBits()xEventGroupSetBitsFromISR()

The exact set of supported APIs depends on the FreeRTOS version, configuration, and port.

Important rules

  • Use only APIs documented as ISR-safe.
  • Never use a blocking wait inside an ISR.
  • Do not use mutexes in an ISR.
  • Use the appropriate higher-priority-task-woken parameter when provided.
  • Use the port's documented ISR yield mechanism.
  • Do not assume every RTOS API has an ISR-safe counterpart.

12. The Higher-Priority-Task-Woken Variable

Many FreeRTOS ISR-safe APIs accept a pointer to a variable named xHigherPriorityTaskWoken.

The variable communicates whether the ISR operation made a higher-priority task Ready that should run as soon as interrupt handling permits.

Typical pattern

BaseType_t xHigherPriorityTaskWoken = pdFALSE;

/* Call an ISR-safe API here. */

portYIELD_FROM_ISR(xHigherPriorityTaskWoken);

The exact macro signature and behavior are port-dependent. Some ports use different yield macros or conventions.

A yield request does not mean that the task executes in the middle of the ISR. The context switch occurs according to the processor port's interrupt-exit and scheduling rules.

13. Shared Data Between ISR and Task

Sometimes the ISR and task access the same variable or buffer.

For example, a timer ISR may increment a counter while a task reads the counter.

Potential problems

  • Race conditions.
  • Partially updated data.
  • Lost updates.
  • Incorrect assumptions about atomic access.
  • Buffer ownership conflicts.

Design guidelines

  • Use appropriate atomic or critical-section techniques.
  • Keep critical sections short.
  • Consider the processor's natural atomic access width.
  • Use queues or notifications where they simplify synchronization.
  • Define ownership when transferring buffer pointers.
  • Use memory barriers where required by the architecture and compiler.

14. Priority and Communication Latency

When an ISR notifies a task, the task does not necessarily execute immediately.

Its response depends on:

  • Task priority.
  • Whether a higher-priority task is executing.
  • Interrupt and critical-section interference.
  • Scheduler state.
  • Blocking and resource contention.
  • Communication mechanism overhead.
Event-to-Task Response = ISR Processing + Scheduling Delay + Task Execution

This is a simplified timing model. Any additional blocking or interference must also be included in a complete response-time analysis.

15. Worked Numerical Problem 1 – Queue Processing Capacity

A UART receives data at 500 bytes per second. The communication task may be delayed for 100 ms.

Solution

Required Capacity = Arrival Rate × Delay
= 500 × 0.1 = 50 bytes

Answer: At least 50 bytes of buffering are needed under the stated constant-rate assumption. A practical queue should allow additional space for bursts and scheduling variation.

16. Worked Numerical Problem 2 – ISR and Task Timing

An external interrupt occurs at 200 µs. The ISR takes 5 µs. The notified task starts 7 µs after the ISR completes and requires 18 µs of execution.

Solution

ISR Duration = 5 µs
Scheduling Delay = 7 µs
Task Execution = 18 µs
Total Event-to-Completion = 5 + 7 + 18 = 30 µs

Answer: The task completes 30 µs after the interrupt occurs, under the stated assumptions.

17. Worked Numerical Problem 3 – Counting Semaphore Capacity

A pulse input generates 40 interrupts per second. The processing task may be delayed for 250 ms. Assume a constant pulse rate.

Solution

Expected Pending Events = 40 × 0.25 = 10

Answer: A counting semaphore needs capacity for at least 10 pending events under the stated assumptions. Additional capacity should be considered for burst traffic and longer delays.

18. Common Design Mistakes

  • Using task-context APIs inside an ISR.
  • Calling blocking functions from interrupt context.
  • Using a binary semaphore when every individual data item must be preserved.
  • Ignoring queue-full conditions.
  • Using a mutex inside an ISR.
  • Enabling an interrupt before creating its communication objects.
  • Failing to define shared-buffer ownership.
  • Assuming a task notification guarantees immediate execution.
  • Ignoring the task's priority and response-time requirement.

19. Practical Activity – ADC Interrupt-to-Task Communication

Design an ADC monitoring application using an ADC conversion-complete interrupt and a sensor-processing task.

Implementation steps

  1. Configure the ADC peripheral.
  2. Create a task notification or queue.
  3. Configure the ADC interrupt.
  4. In the ISR, capture the conversion result and acknowledge the interrupt.
  5. Transfer the result or signal completion to the task.
  6. In the task, convert the raw ADC count into a voltage.
  7. Apply threshold checks and update application state.
  8. Test repeated conversions and communication-buffer handling.

Example ADC conversion

For a 10-bit ADC with a 3.3 V reference:

Voltage = (ADC Count / 1023) × 3.3 V

For an ADC count of 512:

Voltage = (512 / 1023) × 3.3 ≈ 1.652 V
For LPC2129, use the actual ADC channel, pin configuration, conversion registers, and interrupt behavior. The ADC example describes the communication architecture, not a complete hardware-specific FreeRTOS port. Keil simulator results must not be treated as proof of physical ADC behavior.

21. Lesson Summary

  • Interrupt-to-task communication connects hardware event handling with application processing.
  • Binary semaphores signal events; counting semaphores count pending events.
  • Queues transfer individual data items or messages.
  • Task notifications provide efficient direct signaling to a particular task.
  • Event groups represent multiple event conditions.
  • FreeRTOS ISR-safe APIs must be used from interrupt context.
  • Shared data requires appropriate synchronization and ownership rules.
  • Task priority and scheduling delay affect the overall response time.
