1. Introduction

Interrupt handling is an important part of real-time operating systems. When a hardware device generates an interrupt, the processor executes an Interrupt Service Routine (ISR).

Some interrupt operations must be performed immediately, while other operations may require more processing time. Executing every operation inside the ISR can increase interrupt latency and affect the response of other interrupt sources.

To solve this problem, operating systems divide interrupt-related work into two conceptual stages:

  • Top half: Immediate interrupt handling.
  • Bottom half: Deferred interrupt-related processing.
The top-half and bottom-half terminology is commonly associated with Linux kernel interrupt handling. It is also useful as a general conceptual model when designing ISR-to-task communication in an RTOS.

2. What Is the Top Half?

The top half is the immediate interrupt handler executed when an interrupt is accepted by the processor.

Its primary responsibility is to perform essential operations that cannot safely be postponed.

Typical top-half responsibilities

  • Identify the interrupt source.
  • Read peripheral status registers.
  • Capture essential data.
  • Acknowledge or clear the interrupt condition as required.
  • Protect or transfer captured information.
  • Schedule or signal deferred processing.

The top half should be short, efficient, and predictable.

An interrupt handler should not perform lengthy calculations, wait for a resource, or execute operations that may sleep.

3. What Is the Bottom Half?

The bottom half performs interrupt-related processing that does not need to execute immediately inside the hardware ISR.

It runs later in an appropriate deferred execution context.

Typical bottom-half responsibilities

  • Process received communication data.
  • Parse packets and commands.
  • Calculate application-level results.
  • Update application data structures.
  • Perform logging and diagnostic operations.
  • Notify other application components.

The exact execution context depends on the operating system and deferred-work mechanism.

6. Why Separate Top Half and Bottom Half?

6.1 Reduced interrupt latency

Shorter ISRs reduce the time during which other interrupt sources may be delayed by the current handler.

6.2 Better system responsiveness

Time-sensitive interrupt sources can receive service without waiting for lengthy application processing inside another ISR.

6.3 Improved code organization

Hardware-specific interrupt handling remains separate from application-level processing.

6.4 Easier maintenance

Communication parsing, calculations, and application logic can be modified without unnecessarily increasing ISR complexity.

6.5 Better synchronization design

Deferred processing can use task-level synchronization mechanisms such as mutexes, queues, and task notifications where appropriate.

7. Top Half and Bottom Half in Linux

Linux kernel drivers commonly divide interrupt handling into an immediate primary handler and one or more deferred mechanisms.

MechanismExecution ContextCan Sleep?Purpose
Hard IRQ handlerHard interrupt context.NoImmediate interrupt servicing.
SoftirqSoftirq context.NoDeferred kernel processing.
TaskletSoftirq-based context.NoHistorically used for simpler deferred processing; deprecated in modern Linux.
WorkqueueKernel worker-thread context.Yes, where permittedDeferred work requiring process context.
Threaded IRQKernel thread context.Yes, where permittedMoves substantial interrupt processing into a schedulable thread.
Softirqs and workqueues are not interchangeable. Softirqs execute in non-sleepable context, while workqueues execute in process context and can perform operations that may sleep.

8. Softirq in Linux

A softirq is a Linux kernel mechanism used to execute deferred work outside the immediate hard interrupt handler.

Softirqs are commonly used for high-volume or performance-sensitive kernel processing.

Examples of softirq usage

  • Network packet processing.
  • Timer-related processing.
  • Block I/O-related deferred work.

Softirq execution is not equivalent to a normal application thread. It cannot sleep and must follow softirq-context restrictions.

9. Workqueues in Linux

A workqueue schedules deferred work for execution by kernel worker threads.

Workqueues are suitable when deferred operations require process context, including operations that may sleep.

Typical workqueue operations

  • Prepare a work item.
  • Initialize the work item.
  • Queue the work for execution.
  • Kernel worker thread executes the callback.
  • Complete or reschedule the work as required.

Workqueue processing is asynchronous. Queueing work does not guarantee immediate execution.

10. Threaded Interrupts in Linux

A threaded IRQ divides interrupt processing between a primary handler and a threaded handler.

  • The primary handler executes in hard interrupt context.
  • It identifies and acknowledges the event as appropriate.
  • It returns a result indicating that threaded handling is required.
  • The kernel schedules the threaded handler.
  • The threaded handler performs the remaining work in thread context.

Threaded interrupts are useful when substantial processing must be associated closely with a particular interrupt source.

11. Top Half and Bottom Half in FreeRTOS

FreeRTOS does not use Linux's softirq, tasklet, or workqueue APIs. A common FreeRTOS design uses an ISR to notify a task.

The ISR performs immediate hardware servicing and signals the task using an ISR-safe API.

Typical mechanisms

MechanismPurpose
Binary semaphoreSignal an event to a task.
Counting semaphoreCount repeated events.
QueueTransfer data or messages.
Task notificationEfficiently signal a particular task.
In a FreeRTOS application, the deferred task acts as the bottom-half processing context in this conceptual architecture.

12. FreeRTOS Example – Top Half and Bottom Half

The following example illustrates an ISR notifying a task through a direct task notification.

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t xProcessingTaskHandle;

void Hardware_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Top half:
       1. Read peripheral status.
       2. Capture essential data.
       3. Acknowledge the interrupt.
    */

    vTaskNotifyGiveFromISR(
        xProcessingTaskHandle,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* Bottom half:
           Perform longer application processing.
        */
        Process_Application_Event();
    }
}

Explanation

  1. The hardware generates an interrupt.
  2. The ISR executes the top-half operations.
  3. The ISR notifies the processing task.
  4. The ISR returns.
  5. The scheduler may run the notified task if scheduling rules permit.
  6. The task performs deferred processing.
This is a conceptual FreeRTOS example. The actual ISR vector, hardware acknowledgement, interrupt-priority rules, and yield mechanism depend on the selected processor port. It is not a verified LPC2129 FreeRTOS implementation.

13. Example – UART Top Half and Bottom Half

Consider a UART communication system that receives a command from a PC.

Top-half operations

  1. Detect UART receive interrupt.
  2. Read the received byte.
  3. Store the byte in a queue or receive buffer.
  4. Acknowledge the interrupt condition as required.
  5. Notify the communication task.

Bottom-half operations

  1. Read the received byte from the queue.
  2. Assemble the complete command.
  3. Validate the command format.
  4. Check the checksum if applicable.
  5. Execute the requested application operation.
  6. Prepare a response.

14. Choosing the Correct Deferred Mechanism

RequirementSuitable Mechanism
Signal one task that an event occurredTask notification or binary semaphore.
Count repeated event occurrencesCounting semaphore or counting notification.
Transfer received bytesQueue or appropriately synchronized ring buffer.
Process large packetsBuffer or descriptor queue with defined ownership.
Perform an operation that may sleep in LinuxWorkqueue or threaded IRQ.
Perform high-priority non-sleepable Linux deferred workSoftirq where appropriate.

The mechanism should be selected based on data volume, event frequency, latency requirements, execution context, and synchronization requirements.

15. Timing Considerations

Separating the top half and bottom half reduces the amount of work performed in interrupt context. However, the deferred task introduces its own scheduling delay.

Deferred Task Response = Task Waiting Time + Task Execution Time

The complete event-to-processing time must also account for the initial interrupt servicing and communication overhead.

For a simplified event-to-completion measurement:

Total Time = ISR Processing + Deferred Scheduling Delay + Task Processing

This expression is useful for conceptual analysis when the intervals are defined without overlap.

A short ISR does not automatically guarantee that the application meets its deadline. The deferred task must also receive sufficient priority, CPU time, and resources.

16. Worked Numerical Problem 1 – ISR Time Reduction

A hardware interrupt originally performs the following operations:

OperationExecution Time
Read status register2 µs
Capture data3 µs
Validate packet15 µs
Update application state10 µs

Original ISR execution time

2 + 3 + 15 + 10 = 30 µs

New top-half execution time

Only the status read and data capture remain in the ISR.

2 + 3 = 5 µs

Reduction

30 − 5 = 25 µs
Reduction = (25 / 30) × 100 = 83.33%

Answer: The ISR duration is reduced by 25 µs, or approximately 83.33%. The remaining 25 µs of processing still has to execute in the deferred context.

17. Worked Numerical Problem 2 – Event Processing Delay

An interrupt occurs at 100 µs. The top half completes at 106 µs. The deferred task begins at 114 µs and finishes at 134 µs.

Solution

Top-Half Duration = 106 − 100 = 6 µs
Scheduling Delay = 114 − 106 = 8 µs
Task Execution = 134 − 114 = 20 µs
Total Event-to-Completion = 134 − 100 = 34 µs

Answer: The event is fully processed 34 µs after the interrupt occurs.

18. Worked Numerical Problem 3 – Queue Buffer Capacity

A communication peripheral receives 200 bytes per second. The deferred task may be unable to execute for 150 ms. Assume a constant arrival rate.

Solution

Required Buffer Capacity = Arrival Rate × Delay
= 200 × 0.15 = 30 bytes

Answer: At least 30 bytes are needed under the stated assumptions. Additional capacity is advisable for bursts, scheduling variation, and processing delays.

19. Common Mistakes

  • Performing all processing inside the top half.
  • Calling a blocking function from interrupt context.
  • Confusing Linux softirqs with FreeRTOS tasks.
  • Assuming all bottom-half mechanisms can sleep.
  • Ignoring data-buffer ownership.
  • Failing to handle queue overflow.
  • Assuming a notified task executes immediately.
  • Ignoring deferred-task priority and deadline requirements.

20. Practical Activity – Design a Two-Stage Interrupt Handler

Design a UART-based command receiver using a top-half ISR and a bottom-half processing task.

Implementation plan

  1. Identify the UART interrupt source.
  2. Design a short ISR that captures received data.
  3. Choose a queue or ring buffer for the received bytes.
  4. Notify the processing task.
  5. Implement packet assembly in the task.
  6. Validate the packet and process the command.
  7. Define behavior for buffer overflow and invalid packets.
  8. Measure event-to-completion time in a suitable test environment.

22. Lesson Summary

  • The top half performs immediate interrupt handling.
  • The bottom half performs deferred processing.
  • Short top halves help reduce interrupt interference.
  • Linux provides softirqs, workqueues, and threaded IRQs.
  • Softirqs cannot sleep, while workqueue callbacks execute in worker-thread context.
  • FreeRTOS commonly uses ISR-safe communication APIs to notify tasks.
  • Queues are suitable for transferring data; notifications and semaphores are useful for signaling.
  • Deferred execution adds scheduling delay that must be included in timing analysis.
