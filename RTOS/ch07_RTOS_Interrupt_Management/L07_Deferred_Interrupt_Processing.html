1. Introduction

An Interrupt Service Routine (ISR) executes in response to an interrupt request. Its primary responsibility is to acknowledge the interrupt, capture essential information, and perform the minimum processing required to safely handle the event.

However, some interrupt-related operations may require significant processing time. Executing all such work inside an ISR can increase interrupt latency for other sources.

Deferred interrupt processing moves non-urgent processing from the ISR to a context that can execute later, such as an RTOS task.

Deferred processing: A technique in which an ISR performs immediate, time-critical work and schedules the remaining processing for execution outside interrupt context.

2. Why Is Deferred Processing Required?

Consider a UART receiver that receives a data packet.

The ISR may need to:

  • Read the received byte from the UART data register.
  • Store the byte in a buffer.
  • Clear or acknowledge the interrupt condition as required.
  • Notify a processing task that new data is available.

The remaining operations may include:

  • Parsing the complete packet.
  • Checking a checksum or CRC.
  • Interpreting commands.
  • Updating application data.
  • Writing results to a log or display.

These longer operations are better suited to task context rather than an ISR.

3. Top Half and Bottom Half

Operating systems often describe interrupt processing using two conceptual stages.

Top half

The top half is the immediate interrupt handler. It performs essential work that must happen promptly.

Bottom half

The bottom half performs deferred work after the immediate interrupt handling is complete or after the system schedules the relevant processing context.

FeatureTop HalfBottom Half
Execution contextInterrupt context.Deferred context, often task or kernel worker context.
Execution timeShort and bounded.Can perform more extensive processing.
BlockingCannot block.Task-based processing may block where permitted.
Typical workRead status, acknowledge event, capture data.Parse data, process buffers, update application state.
Top half and bottom half are general operating-system concepts. Linux has specific deferred-work mechanisms such as softirqs, tasklets, and workqueues. FreeRTOS generally uses tasks and ISR-safe communication APIs instead of Linux bottom-half mechanisms.

4. Immediate vs Deferred Interrupt Processing

ParameterImmediate ProcessingDeferred Processing

The ISR performs only the work necessary to safely handle the interrupt. The task performs the remaining application processing.

6. Steps in Deferred Interrupt Processing

  1. A hardware peripheral generates an interrupt request.
  2. The processor accepts the interrupt according to its masking and priority rules.
  3. The ISR reads the required peripheral status or data.
  4. The ISR acknowledges or clears the interrupt condition as specified by the peripheral.
  5. The ISR stores essential information in a buffer or communicates it through an ISR-safe RTOS mechanism.
  6. The ISR notifies the appropriate task.
  7. The ISR returns.
  8. The scheduler runs the task when scheduling conditions permit.
  9. The task performs the deferred processing.

7. Deferred Processing Using a Semaphore

A binary semaphore can be used to notify a task that an interrupt-related event has occurred.

The ISR gives the semaphore. A task waits for it and performs the deferred work.

Conceptual FreeRTOS example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xEventSemaphore;

void Hardware_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Read or acknowledge the hardware event here. */

    xSemaphoreGiveFromISR(
        xEventSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xEventSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Deferred processing */
            Process_Hardware_Event();
        }
    }
}

The semaphore must be created before the interrupt is enabled. The ISR must use the correct ISR-safe API and the yield mechanism required by the selected FreeRTOS port.

The example is a FreeRTOS programming pattern, not a verified LPC2129/Keil project. The actual interrupt handler, vector setup, peripheral acknowledgement, and port-specific ISR yield macro must be supplied for the target platform.

8. Deferred Processing Using a Queue

A queue is useful when an ISR must transfer actual data or event information to a task.

For example, a UART ISR can place received bytes into a queue. A communication task can retrieve the bytes and assemble complete messages.

Conceptual FreeRTOS example

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t xUARTQueue;

void UART_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;
    uint8_t receivedByte;

    /* Replace with the actual UART data-register read. */
    receivedByte = UART_ReadByte();

    xQueueSendFromISR(
        xUARTQueue,
        &receivedByte,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void UARTProcessingTask(void *pvParameters)
{
    uint8_t receivedByte;

    for (;;)
    {
        if (xQueueReceive(
                xUARTQueue,
                &receivedByte,
                portMAX_DELAY) == pdTRUE)
        {
            Process_Received_Byte(receivedByte);
        }
    }
}

In a real implementation, handle queue-full conditions and ensure the UART hardware is serviced quickly enough to avoid receive overruns.

9. Deferred Processing Using Task Notifications

FreeRTOS task notifications provide a lightweight way for an ISR to notify a specific task.

They are particularly useful when the ISR only needs to signal an event rather than transfer a large amount of data.

Conceptual example

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t xProcessingTaskHandle;

void Timer_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the timer interrupt here. */

    vTaskNotifyGiveFromISR(
        xProcessingTaskHandle,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

void ProcessingTask(void *pvParameters)
{
    for (;;)
    {
        ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

        /* Perform deferred timer-related processing. */
        Process_Timer_Event();
    }
}

Task notifications are efficient for signaling a particular task. They are not automatically a replacement for a queue when multiple data items must be transferred.

11. Deferred Interrupt Processing in Linux

Linux provides several mechanisms for handling work that should not be performed in the immediate hard interrupt handler.

MechanismPurpose
SoftirqRuns deferred work in softirq context.
TaskletHistorically provided a simpler deferred execution mechanism based on softirqs; deprecated in modern Linux in favor of alternatives.
WorkqueueSchedules work in process context using kernel worker threads.
Threaded IRQUses a primary interrupt handler and a schedulable threaded handler for deferred work.

Workqueues execute in process context, allowing operations that may sleep when the workqueue type and context permit it. Softirq handlers cannot sleep.

Linux kernel drivers and FreeRTOS applications use different APIs and execution models. Do not copy Linux softirq or workqueue APIs into FreeRTOS programs.

12. ISR Restrictions

Interrupt handlers operate under stricter rules than normal task functions.

Common restrictions

  • Do not call blocking functions from an ISR.
  • Do not use task APIs that may wait indefinitely.
  • Keep the handler short and bounded.
  • Use documented ISR-safe RTOS APIs.
  • Acknowledge the interrupt correctly.
  • Avoid lengthy calculations and formatted output.
  • Protect shared data against concurrent access.
  • Check communication-buffer overflow conditions.

13. ISR-to-Task Data Handling

When an ISR transfers data to a task, the design must define how the data is stored and who owns it.

For a small data item, a queue may copy the data into queue storage. For a large packet, a buffer or pointer-based design may be more efficient.

Important design considerations

  • Define buffer size and capacity.
  • Specify whether the ISR or task owns each buffer.
  • Prevent the task from reading partially updated data.
  • Define what happens when the buffer becomes full.
  • Ensure the ISR does not overwrite data still being processed.
  • Consider memory barriers and atomicity where required by the processor and compiler.

14. Worked Numerical Problem 1 – ISR Execution Time Reduction

An interrupt handler originally performs the following operations:

OperationExecution Time
Read peripheral status2 µs
Capture data3 µs
Parse packet20 µs
Update application state10 µs

Original ISR duration

2 + 3 + 20 + 10 = 35 µs

After deferring packet parsing and application updates, the ISR performs only the first two operations.

New ISR duration

2 + 3 = 5 µs

Reduction

35 − 5 = 30 µs
Reduction = (30 / 35) × 100 = 85.71%

Answer: The ISR execution time is reduced by 30 µs, or approximately 85.71%, under the stated assumptions. The deferred task still has to perform the remaining 30 µs of processing.

15. Worked Numerical Problem 2 – Queue Capacity

A UART ISR receives 100 bytes per second. The processing task may be delayed for 200 ms. Assume the arrival rate remains constant and ignore additional burst traffic.

Solution

Required Capacity = Arrival Rate × Delay
= 100 × 0.2 = 20 bytes

Answer: At least 20 bytes of buffering are required for the stated steady arrival rate and delay. A practical design should provide additional capacity for bursts and scheduling variation.

16. Worked Numerical Problem 3 – Deferred Task Response

An ISR takes 4 µs to capture data and notify a task. The task waits 6 µs before execution and requires 20 µs of CPU execution.

Task Response = Waiting Time + Task Execution Time
= 6 + 20 = 26 µs

Answer: The deferred task completes 26 µs after it becomes ready, assuming no additional blocking or interference. The initial ISR processing time is separate from this task response interval.

17. Common Design Mistakes

  • Performing complete packet processing inside the ISR.
  • Calling blocking APIs from interrupt context.
  • Ignoring queue-full or buffer-overflow conditions.
  • Using task-context APIs from an ISR.
  • Assuming a notification preserves every event automatically.
  • Failing to acknowledge the peripheral interrupt.
  • Allowing a deferred task to process shared data before it is ready.
  • Assuming the task will execute immediately after notification.

18. Practical Activity – UART Deferred Processing Design

Design a UART communication architecture with one interrupt handler and one processing task.

Suggested design

  1. Configure UART receive interrupt.
  2. Create a queue for received bytes.
  3. Create a UART processing task.
  4. Enable the UART interrupt only after the queue and task are ready.
  5. In the ISR, read the received byte and send it using an ISR-safe queue API.
  6. Check the return value to detect queue-full conditions.
  7. In the task, receive bytes and assemble a complete message.
  8. Validate the message and execute the requested application operation.

20. Lesson Summary

  • Deferred interrupt processing moves non-urgent work out of the ISR.
  • The ISR performs immediate hardware-related operations.
  • A deferred task performs longer application processing.
  • Top half and bottom half describe the two conceptual stages.
  • FreeRTOS supports deferred processing through ISR-safe semaphores, queues, and task notifications.
  • Linux provides softirqs, workqueues, and threaded IRQs.
  • Correct data ownership and buffer management are essential.
  • Deferred processing reduces lengthy ISR execution but does not eliminate task scheduling delay.
