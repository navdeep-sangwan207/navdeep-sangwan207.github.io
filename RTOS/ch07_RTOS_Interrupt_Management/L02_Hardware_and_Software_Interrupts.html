1. Introduction

Interrupts allow a processor to respond to events that require attention outside the normal sequential execution of a program.

Based on how they are generated, interrupts and related processor events can be broadly studied as:

  • Hardware-generated interrupts.
  • Software-generated interrupts.
  • Processor exceptions caused by synchronous conditions.
Important distinction: A hardware interrupt is generally generated by an external device or on-chip peripheral. A software interrupt is generated through a software-controlled instruction or mechanism. A processor exception is a broader category that also includes synchronous faults and traps.

2. Hardware Interrupts

A hardware interrupt is a request generated by hardware when an event requires processor attention.

The source may be an external device, an on-chip peripheral, or an interrupt controller.

Examples of hardware interrupts

SourceEventApplication
TimerTimer match or overflowPeriodic task timing
UARTData received or transmitter readySerial communication
GPIO/external inputConfigured input transitionPush-button detection

2.1 Hardware interrupt operation

  1. A hardware device detects an event.
  2. The device asserts an interrupt request.
  3. The interrupt controller receives the request, where applicable.
  4. The processor accepts the request if its interrupt and masking conditions permit.
  5. The processor enters the appropriate exception handler.
  6. The ISR services or acknowledges the event.
  7. The processor returns to the interrupted program or performs a scheduling decision.

3. Hardware Interrupt Example – Timer

Consider a timer configured to generate an interrupt every 1 millisecond.

Initialize_Timer();
Configure_Timer_Interval(1);
Enable_Timer_Interrupt();

while(1)
{
    Perform_Main_Application_Work();
}

void TIMER_ISR(void)
{
    Clear_Timer_Interrupt_Flag();

    system_tick_count++;
}

The timer generates an interrupt request whenever the configured event occurs. The processor executes the timer handler, updates the counter, and returns according to the processor's exception-handling mechanism.

This is conceptual pseudocode. A real LPC2129 timer implementation must configure the appropriate timer registers, match control, VIC, and interrupt acknowledgement sequence.

4. Types of Hardware Interrupt Requests

4.1 Maskable interrupts

A maskable interrupt is one whose acceptance can be controlled through processor or interrupt-controller masking mechanisms.

Masking can temporarily prevent selected interrupts from being serviced.

4.2 Non-maskable interrupts

A non-maskable interrupt (NMI) is designed for events that should not be blocked by ordinary interrupt masking.

Its exact behavior and availability depend on the processor architecture.

ARM7TDMI-S provides IRQ and FIQ exception inputs. FIQ is designed for fast interrupt handling and has additional banked registers. Do not automatically equate FIQ with a universally non-maskable interrupt: ARM7 has control mechanisms for masking both IRQ and FIQ.

5. Software Interrupts

A software interrupt is generated through a software-controlled instruction or mechanism that causes the processor to enter a defined exception or handler.

It allows software to request a controlled transition to privileged or system-level processing, depending on the architecture and operating-system design.

Examples

  • ARM software interrupt instruction.
  • System-call entry mechanisms on some processor architectures.
  • Software-generated interrupt requests through an interrupt controller, where supported.

5.1 ARM7 software interrupt instruction

ARM7TDMI-S supports the SWI instruction, commonly called Software Interrupt. It generates a Supervisor Call exception and transfers control to the SWI exception handler.

SWI #0x01

The immediate value can be used by software as a service identifier, depending on the exception-handler design.

Conceptual ARM assembly example

        AREA    SWI_DEMO, CODE, READONLY
        ENTRY

START
        SWI     0x01

STOP
        B       STOP

        END

This example generates an SWI exception. A complete program must provide an appropriate vector and handler for the intended service.

6. How a Software Interrupt Works in ARM7

When an ARM7TDMI-S processor executes an SWI instruction, the processor performs an exception-entry sequence.

  1. The SWI instruction is executed.
  2. The processor saves the return address in the banked Supervisor-mode link register.
  3. The previous CPSR is saved in the Supervisor-mode SPSR.
  4. The processor enters Supervisor mode.
  5. The IRQ mask bit is set as part of SWI exception entry.
  6. Control transfers to the SWI exception vector at address 0x00000008, or the corresponding high-vector location if configured.
  7. The SWI handler determines the requested operation.
  8. The handler performs the service and returns using an appropriate exception-return sequence.
ARM7 uses banked registers for exception handling. The SWI handler can inspect the instruction that caused the exception when it needs to decode the SWI immediate field.

8. Software Interrupt vs System Call

A system call is a controlled interface through which an application requests a service from an operating-system kernel.

Some processor architectures implement system-call entry using a software interrupt or trap instruction. Other architectures provide dedicated system-call instructions.

Software InterruptSystem Call
A processor event or exception mechanism.An operating-system service interface.
Can be used for different software-defined operations.Requests a defined kernel service.
May be used to implement system-call entry.May use SWI, trap, syscall, or another architecture-specific mechanism.
A system call is not simply another name for every software interrupt. The two concepts describe different layers: processor exception mechanism and operating-system service interface.

9. Synchronous and Asynchronous Events

Another useful classification is based on the relationship between an event and the currently executing instruction stream.

9.1 Synchronous exceptions

A synchronous exception is directly associated with the execution of a particular instruction.

Examples include:

  • Undefined instruction exception.
  • Software interrupt instruction.
  • Some processor-generated fault conditions.
  • Some system-call or trap instructions.

9.2 Asynchronous interrupts

An asynchronous interrupt is generated independently of the currently executing instruction.

Examples include:

  • Timer interrupt.
  • UART receive interrupt.
  • External hardware interrupt.
  • Peripheral event interrupt.

10. Interrupts and Exceptions in ARM7

ARM7TDMI-S provides several processor modes used during normal execution and exception handling.

Processor ModePurpose
UserNormal unprivileged application execution.
SystemPrivileged execution using the User-mode register set.
SupervisorSWI exception handling and operating-system services.
IRQNormal interrupt request handling.
FIQFast interrupt request handling.
AbortMemory access abort handling.
UndefinedUndefined instruction handling.

Important registers include:

  • R13: Stack Pointer (SP).
  • R14: Link Register (LR).
  • R15: Program Counter (PC).
  • CPSR: Current Program Status Register.
  • SPSR: Saved Program Status Register in exception modes.

IRQ, FIQ, Supervisor, Abort, and Undefined modes have banked registers used to support exception handling.

11. Software-Generated Interrupts in RTOS Applications

RTOS applications may use software-controlled mechanisms to request scheduling or communicate events.

Examples include:

  • Yielding the processor to another ready task.
  • Requesting a context switch through a port-specific mechanism.
  • Requesting an operating-system service.
  • Signaling a software-controlled interrupt or exception where supported.

However, RTOS task APIs should not be confused with processor SWI instructions. An RTOS API may execute normal function calls, manipulate kernel data structures, or invoke a port-specific trap mechanism depending on the implementation.

FreeRTOS is not Linux. FreeRTOS task APIs are kernel function interfaces, not Linux system calls. The exact mechanism used for yielding and context switching depends on the FreeRTOS port.

13. Practical Activity – Study ARM7 Exception Entry

Use the Keil uVision simulator to examine the behavior of an ARM7 SWI exception.

Suggested procedure

  1. Create a simple ARM assembly project.
  2. Add an SWI instruction in the program.
  3. Configure the exception vector and a valid SWI handler.
  4. Build the project.
  5. Start the debugger.
  6. Set a breakpoint at the SWI instruction.
  7. Execute the instruction and examine the processor mode.
  8. Inspect CPSR, SPSR, and the banked Supervisor-mode registers.
  9. Step through the exception handler and examine the return sequence.
A standalone SWI instruction without a valid exception vector and handler may not produce a useful demonstration. The exact debugger behavior also depends on the startup code and project configuration.

Questions for observation

  1. What processor mode is selected after SWI entry?
  2. Which register stores the return address?
  3. Where is the previous CPSR saved?
  4. What is the SWI vector address?
  5. How does the handler return from the exception?

15. Lesson Summary

  • Hardware interrupts are generated by hardware devices and peripherals.
  • Software interrupts are initiated through software-controlled mechanisms.
  • ARM7 supports the SWI instruction for Supervisor Call exception entry.
  • SWI entry changes the processor to Supervisor mode.
  • Synchronous exceptions are associated with instruction execution.
  • Asynchronous interrupts originate independently of the current instruction.
  • System calls are operating-system service interfaces and may use different processor entry mechanisms.
  • ARM7 provides User, System, Supervisor, IRQ, FIQ, Abort, and Undefined modes.
