Nested Interrupts and Priority

Chapter 07 – Interrupt Management in RTOS | Lesson 05

Home RTOS & FreeRTOS Course Chapter 07

1. Introduction

In an embedded system, multiple hardware devices may generate interrupt requests at the same time or while another interrupt handler is executing.

Interrupt priority determines which interrupt should receive service first. Nested interrupt handling allows an eligible higher-priority interrupt to interrupt the execution of a lower-priority ISR.

Nested interrupt: An interrupt that is accepted while another interrupt handler is already executing, causing the processor to temporarily suspend the current handler and execute the newly accepted handler.

Nested interrupts are useful in real-time systems where urgent events must be serviced without waiting for a lower-priority ISR to finish.

2. Why Are Nested Interrupts Required?

Consider an embedded controller with the following interrupt sources:

Interrupt SourcePriorityPurpose
Emergency faultVery highDetect an urgent fault condition.
TimerHighMaintain time-sensitive control operations.
UARTMediumReceive serial communication data.
Background status eventLowRecord non-urgent status information.

If the UART ISR is executing when an emergency fault occurs, the system may need to interrupt the UART handler and execute the emergency handler immediately.

Without suitable preemption, the emergency interrupt may have to wait until the current ISR completes or interrupts are unmasked.

3. Interrupt Priority

Interrupt priority represents the relative urgency assigned to an interrupt source.

The interrupt controller or processor uses priority and masking rules to decide which pending interrupt can be serviced.

Example priority assignment

Priority LevelInterruptTypical Purpose
1 – HighestEmergency faultImmediate fault response.
2TimerTime-critical event.
3UARTCommunication event.
4 – LowestBackground eventNon-urgent operation.
Priority numbering is architecture- and controller-dependent. In this table, 1 means highest priority only for illustration. Some controllers use larger numerical values for higher priority, while others use smaller values.

4. What Is Interrupt Nesting?

Interrupt nesting occurs when a new eligible interrupt is accepted during execution of an existing ISR.

Example

  1. UART interrupt occurs.
  2. Processor begins executing UART ISR.
  3. An emergency interrupt occurs.
  4. The processor accepts the higher-priority interrupt if nesting is enabled and masking rules permit it.
  5. The current UART handler is suspended.
  6. The emergency ISR executes.
  7. The processor returns to the suspended UART handler.
  8. The UART ISR completes.
Nesting is not automatic on every processor or in every interrupt-controller configuration. The current handler must permit the higher-priority interrupt to be accepted.

5. Nested Interrupt Execution Timeline

Consider the following simplified timeline:

TimeProcessor Activity
0 µsUART interrupt occurs.
2 µsUART ISR begins.
5 µsEmergency interrupt occurs.
6 µsEmergency ISR begins.
10 µsEmergency ISR completes.
11 µsUART ISR resumes.
16 µsUART ISR completes.

In this example, the emergency interrupt preempts the UART ISR.

The UART handler is delayed, but the higher-priority event receives service earlier.

7. Conditions Required for Nested Interrupts

For a higher-priority interrupt to preempt an active ISR, the system generally requires:

  1. The new interrupt source must be enabled.
  2. The interrupt request must be pending or asserted.
  3. The interrupt controller must recognize the request as eligible.
  4. The processor must not have the relevant interrupt class masked.
  5. The active handler must permit nesting.
  6. The new interrupt must have sufficient priority to preempt the active interrupt.
  7. The exception-entry and return mechanisms must preserve the required execution state.

The exact conditions depend on the processor architecture and interrupt-controller implementation.

8. Interrupt Priority and Preemption

Preemption means temporarily stopping the execution of a lower-priority handler so that a higher-priority handler can execute.

Example

InterruptPriorityExecution Time
INT-AHigh4 µs
INT-BMedium8 µs
INT-CLow10 µs

Suppose INT-C starts first. INT-B arrives while INT-C is executing, and INT-A arrives while INT-B is executing.

With suitable nesting enabled, the execution order can be:

  1. INT-C starts.
  2. INT-B preempts INT-C.
  3. INT-A preempts INT-B.
  4. INT-A completes.
  5. INT-B resumes and completes.
  6. INT-C resumes and completes.
This execution order assumes that each higher-priority request is accepted and that the processor, controller, and handler configuration permit the described nesting.

9. Maximum Nesting Depth

Maximum nesting depth is the largest number of simultaneously active interrupt handlers, including the original handler, that the system permits.

For example, if a system permits three interrupt handlers to be active simultaneously, its maximum nesting depth is three.

Nested interrupts consume stack space because each active handler may need to preserve additional execution context.

Total Stack Requirement ≈ Base Context + Σ Nested Handler Contexts

This is a conceptual estimate. A real stack calculation must include compiler-generated register saves, local variables, called functions, exception frames, alignment, and possible re-entrant execution.

Potential problems

  • Stack overflow.
  • Excessive interrupt latency for lower-priority sources.
  • Data corruption due to shared variables.
  • Unexpected recursive interrupt behavior.
  • Difficulty analyzing worst-case execution time.

10. Interrupt Masking During ISR Execution

An ISR may execute with some interrupt classes masked. Whether nesting is possible depends on the masking state.

For example, if all IRQ requests remain masked throughout an IRQ handler, another IRQ request cannot normally preempt that handler.

If the handler deliberately permits higher-priority interrupts, nested handling may be possible.

Enabling nesting requires more than simply enabling interrupts globally. The design must define which interrupt classes can preempt which handlers and how processor state is preserved.

11. IRQ and FIQ in ARM7TDMI-S

The LPC2129 uses the ARM7TDMI-S processor. It supports two important interrupt exception types:

FeatureIRQFIQ
MeaningInterrupt RequestFast Interrupt Request
PurposeGeneral interrupt handling.Fast, high-priority interrupt handling.
Banked registersBanked SP and LR.Banked SP, LR, and additional registers R8–R12.
Exception modeIRQ mode.FIQ mode.
MaskingControlled by IRQ mask bit in CPSR.Controlled by FIQ mask bit in CPSR.
Typical useUART, timer, and general peripheral events.Selected time-critical interrupt sources.

FIQ is designed to support fast handling through additional banked registers and its exception vector. It is not simply an ordinary IRQ with a higher numerical priority.

> ARM7TDMI-S does not have the Cortex-M NVIC priority model. Do not use Cortex-M priority grouping, preemption priority, subpriority, or BASEPRI terminology as if it applied directly to LPC2129.

12. ARM7 Interrupt Mask Bits

The ARM7 CPSR contains interrupt mask bits:

BitNameFunction
IIRQ mask bitWhen set, IRQ exceptions are masked.
FFIQ mask bitWhen set, FIQ exceptions are masked.

During exception entry, the processor updates the relevant mode and mask state according to the ARM architecture.

For an IRQ exception, the processor enters IRQ mode and sets the IRQ mask bit. For an FIQ exception, it enters FIQ mode and sets the FIQ mask bit and IRQ mask bit.

The FIQ exception-entry behavior helps prevent ordinary IRQ handling from disrupting the initial FIQ service. Detailed nesting behavior depends on software changes to CPSR and the system's exception-handler design.

13. Vectored Interrupt Controller (VIC) in LPC2129

The LPC2129 includes a Vectored Interrupt Controller that supports IRQ and FIQ routing and vectored IRQ handling.

Important registers

RegisterPurpose
VICIntSelectSelects whether enabled interrupt sources are routed as IRQ or FIQ.
VICIntEnableEnables selected interrupt sources.
VICIntEnClrDisables selected interrupt sources.
VICVectAddrProvides the active vectored IRQ handler address and supports IRQ service completion.
VICVectCntl0–15Configures the vectored IRQ slots and associated source selection.
VICIRQStatusShows enabled pending IRQ sources.
VICFIQStatusShows enabled pending FIQ sources.

The VIC's vectored IRQ slots provide a way to dispatch selected IRQ sources to their handlers. FIQ sources are handled through the FIQ exception mechanism rather than the normal vectored IRQ slot mechanism.

The VIC's vectored IRQ slot assignment should not be confused with a general-purpose programmable nested-priority controller. IRQ/FIQ routing and software exception handling determine the actual behavior.

14. Nested Interrupts in RTOS

In an RTOS-based embedded system, interrupt nesting and task scheduling are separate mechanisms.

  • Interrupt priority determines which eligible ISR executes first.
  • Task priority determines which ready task the scheduler selects.
  • A nested ISR may notify a task.
  • The task may become ready while another ISR is still executing.
  • Task execution normally resumes only after interrupt handling reaches a permitted scheduling point.

A high-priority interrupt does not automatically mean that the task it notifies has the highest task priority.

Interrupt priority and RTOS task priority belong to different scheduling domains. They must be designed together, but they are not interchangeable.

15. FreeRTOS Interrupt Priority Considerations

FreeRTOS requires interrupt handlers to follow the rules of the selected processor port.

Important considerations include:

  • Use only APIs documented as safe from ISR context.
  • Follow port-specific interrupt-priority restrictions.
  • Use the appropriate ISR yield mechanism.
  • Keep ISR execution time bounded.
  • Do not call blocking task APIs from an ISR.
  • Consider nested interrupt stack requirements.
The Cortex-M FreeRTOS settings such as configMAX_SYSCALL_INTERRUPT_PRIORITY are specific to Cortex-M ports. Do not apply them to the ARM7TDMI-S LPC2129 as if they were universal FreeRTOS settings.

16. Worked Numerical Problem 1 – Nested ISR Execution

Three interrupt handlers have the following execution times:

ISRPriorityExecution Time
ISR-AHigh3 µs
ISR-BMedium5 µs
ISR-CLow8 µs

ISR-C begins at 0 µs. ISR-B arrives at 2 µs. ISR-A arrives at 4 µs. Assume each higher-priority ISR can preempt the lower-priority handler.

Solution

Time IntervalExecution
0–2 µsISR-C executes for 2 µs.
2–4 µsISR-B executes for 2 µs.
4–7 µsISR-A executes for 3 µs.
7–10 µsISR-B resumes for its remaining 3 µs.
10–16 µsISR-C resumes for its remaining 6 µs.

Answer: All three handlers complete by 16 µs, excluding entry, exit, and context-saving overhead.

17. Worked Numerical Problem 2 – Stack Requirement

A system has three possible simultaneously active interrupt handlers. Their estimated stack usage is:

HandlerStack Usage
Base interrupted context40 bytes
ISR-A32 bytes
ISR-B48 bytes
ISR-C24 bytes

Solution

Total = 40 + 32 + 48 + 24
Total = 144 bytes

Answer: The simplified estimate is 144 bytes.

Actual stack allocation must include additional safety margin, exception context, compiler-generated saves, alignment, and any functions called by the handlers.

18. Advantages and Disadvantages of Nested Interrupts

Advantages

  • Faster service for urgent interrupt sources.
  • Improved response to high-priority events.
  • Better support for systems with different interrupt deadlines.
  • Reduced waiting time for eligible high-priority interrupts.

Disadvantages

  • More complicated interrupt-handler design.
  • Increased stack consumption.
  • Potential shared-data race conditions.
  • More difficult worst-case timing analysis.
  • Possibility of starvation for lower-priority interrupt sources.
  • More complicated debugging and testing.

19. Practical Activity – Study Interrupt Priority

Use the Keil uVision simulator to study interrupt-related processor state on an ARM7 project.

Suggested procedure

  1. Open an ARM7TDMI-S assembly or C project.
  2. Inspect the CPSR register.
  3. Identify the IRQ and FIQ mask bits.
  4. Study the IRQ and FIQ exception vectors.
  5. Inspect the banked IRQ and FIQ registers where supported by the debugger.
  6. Review the LPC2129 VIC configuration in a register-level project.
  7. Trace the interrupt handler and exception-return sequence.

Record the differences between IRQ mode and FIQ mode, including the banked registers.

The simulator may not reproduce real peripheral interrupt timing or every nested interrupt scenario. Treat register inspection and software-flow verification separately from physical timing validation.

21. Lesson Summary

  • Nested interrupts allow eligible higher-priority interrupts to preempt active lower-priority handlers.
  • Interrupt priority determines the relative urgency of interrupt sources.
  • Nesting requires suitable processor, controller, and software configuration.
  • Nested handlers increase stack and timing-analysis requirements.
  • ARM7TDMI-S provides separate IRQ and FIQ exception mechanisms.
  • FIQ uses additional banked registers to support fast handling.
  • The LPC2129 VIC supports IRQ/FIQ routing and vectored IRQ handling.
  • Interrupt priority and RTOS task priority are separate concepts.
  • FreeRTOS interrupt rules depend on the actual processor port.
