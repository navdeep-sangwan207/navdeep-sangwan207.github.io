1. Introduction

An interrupt is an event that causes the processor to temporarily suspend its normal execution flow and transfer control to a special routine called an Interrupt Service Routine (ISR).

Interrupts allow a processor to respond to important events without continuously checking every peripheral or input condition.

For example, an embedded controller may be executing a motor-control task when a timer interrupt occurs. The processor can temporarily execute the timer ISR and then return to the interrupted execution flow or perform a scheduling decision.

Definition: Interrupt management is the process of configuring, prioritizing, servicing, and coordinating interrupts so that an embedded system responds correctly and predictably to asynchronous events.

2. Why Are Interrupts Required?

Embedded systems interact with hardware devices and external events. These events may occur independently of the currently executing program.

Without interrupts, a processor may need to repeatedly poll hardware registers to detect events.

Polling approach

while(1)
{
    if(UART_DATA_AVAILABLE)
    {
        Read_UART_Data();
    }

    if(TIMER_FLAG)
    {
        Handle_Timer_Event();
    }

    if(BUTTON_PRESSED)
    {
        Handle_Button();
    }
}

The processor repeatedly checks the status of different devices.

Interrupt-driven approach

int main(void)
{
    Initialize_UART();
    Initialize_Timer();
    Initialize_Interrupts();

    while(1)
    {
        Perform_Main_Application_Work();
    }
}

void UART_ISR(void)
{
    // Handle UART event
}

void TIMER_ISR(void)
{
    // Handle timer event
}

In an interrupt-driven system, hardware or software events request processor attention. The processor executes the corresponding handler when the interrupt is accepted.

PollingInterrupt-driven processing
CPU repeatedly checks device status.Device requests service through an interrupt.
May waste processor time checking inactive devices.Can reduce unnecessary polling.
Response depends on polling frequency and loop execution.Response depends on interrupt recognition, masking, priority, and handler execution.
Simple to implement in small systems.Useful for asynchronous and time-sensitive events.

3. Basic Interrupt Processing Sequence

When an interrupt occurs, the processor follows an architecture-specific exception-entry sequence.

  1. An interrupt source generates an interrupt request.
  2. The interrupt controller or processor receives the request.
  3. The processor checks whether the interrupt is enabled and permitted by priority and masking rules.
  4. The processor saves the required execution state.
  5. Control transfers to the appropriate interrupt handler.
  6. The ISR performs the required short operation.
  7. The handler acknowledges or clears the interrupt source when required.
  8. The processor returns from the exception or performs a scheduling decision.
The exact sequence depends on the processor architecture and interrupt controller. Saving registers, selecting an exception mode, vector dispatch, and interrupt acknowledgement are architecture- and device-dependent operations.

4. Interrupt Sources

Interrupts can originate from internal processor events, on-chip peripherals, or external hardware signals.

Interrupt SourceDescriptionExample
Timer interruptGenerated by a hardware timer event.Periodic timer match.
UART interruptGenerated by serial communication activity.Receive data available.
GPIO interruptGenerated by an external pin transition or configured condition.Push-button input.
ADC interruptGenerated when a conversion completes or a configured event occurs.ADC conversion complete.
Communication interruptGenerated by communication peripherals.I2C or CAN event.
Software-generated interruptGenerated by an instruction or software-controlled mechanism.Operating-system service or software event.
Processor exceptionGenerated by an exceptional processor condition.Undefined instruction or data abort.
An interrupt and an exception are related but not identical concepts. An interrupt commonly refers to an asynchronous event, while an exception is a broader processor-control event that can also include synchronous faults and traps.

5. Interrupts in Embedded Systems

Interrupts are widely used in microcontroller-based applications.

5.1 Timer-based operations

A timer interrupt can trigger periodic activities such as sampling, timekeeping, or scheduling-related processing.

5.2 UART communication

A UART receive interrupt can notify the processor that incoming serial data is available.

5.3 Sensor acquisition

A peripheral event can notify the application that an ADC conversion has completed.

5.4 Motor control

Timer and capture/compare events can support periodic control calculations and measurement of motor signals.

5.5 Fault detection

External fault signals may generate interrupts so that the controller can initiate an appropriate response.

6. Interrupts in an RTOS

An RTOS uses interrupts to coordinate hardware events with scheduled tasks.

For example, consider a UART receive operation:

  1. A UART peripheral receives a byte.
  2. The UART generates an interrupt request.
  3. The UART ISR reads the received data.
  4. The ISR places the data into an appropriate communication object, if supported by the RTOS port.
  5. A task waiting for the data becomes ready.
  6. The scheduler may select that task according to the scheduling policy and priority rules.
An interrupt does not automatically mean that a task switch occurs. A task switch occurs only when the RTOS scheduling conditions require it and the port permits the switch.

Interrupt-to-task communication

7. Interrupt Management Components

7.1 Interrupt enable and disable

Interrupt enable controls whether a particular interrupt source is permitted to request service. Global masking or processor-specific masking can prevent certain interrupts from being accepted.

7.2 Interrupt priority

Priority determines the relative urgency of interrupt requests. The supported priority levels and their interpretation depend on the processor and interrupt controller.

7.3 Interrupt vector

An interrupt vector provides the processor-specific entry or address information used to transfer control to an exception or interrupt handler.

7.4 Interrupt Service Routine

An ISR is the routine executed to service an interrupt. It should generally perform only the work necessary at interrupt level.

7.5 Interrupt acknowledgement

Some interrupt sources require a status flag to be cleared or a peripheral condition to be serviced. Otherwise, the interrupt may remain pending or be generated again.

8. Interrupt Latency

Interrupt latency is the time between an interrupt request becoming active and the processor beginning execution of the corresponding ISR.

Interrupt Latency = ISR Start Time − Interrupt Request Time

Interrupt latency can be affected by:

  • Interrupt masking.
  • Higher-priority interrupt execution.
  • Processor exception-entry overhead.
  • Current instruction completion requirements.
  • Memory and bus access delays.
  • Interrupt controller arbitration.

Low and bounded interrupt latency is important in many real-time systems.

Detailed interrupt latency and response-time analysis will be covered in the following lessons.

9. Interrupt Management in LPC2129

The LPC2129 microcontroller is based on the ARM7TDMI-S processor core and uses a Vectored Interrupt Controller (VIC).

The VIC manages interrupt sources and supports vectored interrupt handling.

Important LPC2129 interrupt features

  • Vectored Interrupt Controller (VIC).
  • Multiple peripheral interrupt sources.
  • IRQ and FIQ exception handling.
  • Interrupt enable and select registers.
  • VIC vector address and control registers.
  • Peripheral-specific interrupt status and acknowledgement mechanisms.

LPC2129 uses ARM7TDMI-S, not Cortex-M. Do not use Cortex-M NVIC register names, NVIC priority terminology, or Cortex-M-specific FreeRTOS interrupt-priority configuration for this microcontroller.

10. Conceptual Interrupt Flow Example

Consider a timer that generates an interrupt periodically.

Initialize_Timer();
Enable_Timer_Interrupt();
Enable_Processor_Interrupts();

while(1)
{
    // Main application processing
}

void TIMER_ISR(void)
{
    // Read or acknowledge timer event
    // Update a counter or set an event flag
    // Keep ISR execution short
}

This is conceptual pseudocode, not a complete LPC2129 register-level implementation. A real ISR must follow the timer peripheral's interrupt-clear procedure and the processor/VIC exception-return requirements.

11. Interrupt Handling Best Practices

  • Keep ISRs short and predictable.
  • Acknowledge the interrupt source correctly.
  • Avoid long delays inside an ISR.
  • Avoid blocking operations inside an ISR.
  • Use only RTOS APIs documented as ISR-safe.
  • Use the correct interrupt priority and masking configuration.
  • Protect shared data between tasks and ISRs.
  • Consider data consistency and race conditions.
  • Measure interrupt latency and execution time where practical.
  • Move lengthy processing to an RTOS task whenever possible.

14. Lesson Summary

  • Interrupts allow processors to respond to asynchronous events.
  • Interrupt-driven processing can reduce unnecessary polling.
  • An ISR handles an interrupt at interrupt level.
  • Interrupt sources include timers, UART, ADC, GPIO, and communication peripherals.
  • RTOS applications can use queues and semaphores to transfer interrupt events to tasks.
  • Interrupt latency affects real-time response.
  • LPC2129 uses an ARM7-compatible Vectored Interrupt Controller.
  • Correct interrupt acknowledgement and short ISR execution are essential.
