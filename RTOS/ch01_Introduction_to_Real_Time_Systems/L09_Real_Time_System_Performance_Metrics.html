Real-Time System Performance Metrics

Chapter 01 | Lesson 09

Measuring execution time, response time, latency, jitter and system performance

Home Chapter Index RTOS Course

1. Introduction

Real-time system performance metrics are measurable parameters used to evaluate how efficiently and predictably a real-time system performs its operations.

Unlike ordinary computing systems, real-time systems must consider not only processing speed but also whether tasks complete within their required deadlines.

Performance measurement helps designers identify timing problems, optimize task execution, evaluate processor utilization and verify real-time requirements.

Fundamental Concept: Real-time performance is evaluated using timing, scheduling, resource-utilization and deadline-related measurements.

2. Execution Time

Execution Time is the amount of processor time required by a task to execute its instructions.

It depends on the processor architecture, instruction sequence, memory behavior, compiler optimization and execution conditions.

Types of Execution Time

  • Best-Case Execution Time (BCET): Minimum execution time under defined conditions.
  • Average Execution Time (AET): Average execution time measured across a set of executions.
  • Worst-Case Execution Time (WCET): A safe upper bound on execution time under specified assumptions.

Example

A sensor-processing task is executed multiple times. Its measured execution times are:

Execution Time
12 ms
23 ms
34 ms
43 ms
53 ms

Average measured execution time:

\[ AET = \frac{2+3+4+3+3}{5} \] \[ AET = 3\text{ ms} \]

The average is 3 ms, while the largest observed measurement is 4 ms. The largest measurement is not automatically a proven WCET bound; additional analysis may be required.

3. Response Time

Response Time is the time between the release of a task and the completion of that task.

It includes the task's execution time and may also include waiting caused by scheduling, higher-priority tasks, interrupts and resource blocking.

Formula: \[ R = F - r \]

Where:

  • R = Response Time
  • F = Task Completion Time
  • r = Task Release Time

Example

A task is released at 10 ms and completes at 17 ms.

\[ R = 17-10=7\text{ ms} \]

The response time is 7 ms.

4. Latency

Latency is the delay between an event, request or input and the corresponding response or processing stage.

The exact start and end points must be defined when measuring latency.

Types of Latency

  • Interrupt Latency: Delay between an interrupt request and the start of its ISR.
  • Communication Latency: Delay associated with transferring data between devices.
  • Input-to-Output Latency: Delay between an input event and the corresponding output response.
  • Scheduling Latency: Delay before a ready task begins execution.

Example: Interrupt Latency

A hardware interrupt occurs at 100 microseconds. The processor starts executing the corresponding ISR at 108 microseconds.

\[ L = 108-100=8\ \mu s \]

The interrupt latency is 8 microseconds.

5. Jitter

Jitter is the variation in the timing of repeated events or operations.

In periodic real-time tasks, jitter may cause task activations or output updates to occur at irregular intervals.

Example

A periodic task is expected to execute every 10 ms. Its actual start intervals are:

Cycle Actual Interval
110 ms
211 ms
39 ms
410 ms

The observed intervals vary between 9 ms and 11 ms. The peak-to-peak variation is:

\[ J_{pp}=11-9=2\text{ ms} \]

This is the peak-to-peak variation in the observed intervals. Other jitter definitions may measure deviation from the ideal schedule or variation in individual release times.

6. Deadline-Miss Ratio

The deadline-miss ratio indicates the proportion of task jobs that do not complete within their specified deadlines.

Formula: \[ \text{Miss Ratio} = \frac{\text{Number of Missed Deadlines}} {\text{Total Number of Jobs}} \] \[ \text{Miss Percentage} = \text{Miss Ratio}\times100 \]

Example

A system executes 1,000 task jobs, out of which 10 miss their deadlines.

\[ \text{Miss Ratio}=\frac{10}{1000}=0.01 \]

\[ \text{Miss Percentage}=1\% \]

7. CPU Utilization

CPU utilization represents the fraction of processor capacity consumed by task execution over a specified observation period.

For independent periodic tasks on a single processor, with execution time \(C_i\) and period \(T_i\):

\[ U=\sum_{i=1}^{n}\frac{C_i}{T_i} \]

Example

Task Execution Time Period
Task 1 2 ms 10 ms
Task 2 3 ms 15 ms
Task 3 1 ms 20 ms

\[ U=\frac{2}{10}+\frac{3}{15}+\frac{1}{20} \]

\[ U=0.2+0.2+0.05=0.45 \]

CPU utilization = 45%.

Important: CPU utilization alone does not prove that every task will meet its deadline. Scheduling policy, deadlines, blocking, interrupts and overhead must also be considered.

8. Throughput

Throughput is the amount of useful work completed by a system per unit of time.

It may be measured in:

  • Tasks completed per second.
  • Messages processed per second.
  • Data bytes transferred per second.
  • Sensor samples processed per second.

Example

A data-processing system processes 600 messages in 10 seconds.

\[ \text{Throughput}=\frac{600}{10} \] \[ =60\text{ messages/second} \]

9. Scheduling Latency

Scheduling latency is the delay between a task becoming ready to execute and the task actually beginning execution.

This delay may be caused by:

  • Execution of higher-priority tasks.
  • Interrupt processing.
  • Scheduler overhead.
  • Preemption restrictions.
  • Critical sections and scheduling suspension.
Example:
  • Task becomes ready at 20 ms.
  • Task begins execution at 22 ms.

Scheduling latency = 22 - 20 = 2 ms.

10. Blocking Time

Blocking time is the time a task is prevented from executing or proceeding because it must wait for a resource or condition.

Examples include:

  • Waiting for a mutex.
  • Waiting for a semaphore.
  • Waiting for data from a queue.
  • Waiting for a shared peripheral.

Blocking time must be considered in response-time analysis because a high-priority task can be delayed while waiting for a resource held by another task.

11. Memory Utilization

Memory utilization indicates how much available memory is being used by the application and operating system.

Important Memory Measurements

  • RAM utilization.
  • Stack usage per task.
  • Heap usage.
  • Static memory usage.
  • Memory fragmentation.
  • Remaining free memory.
Memory Utilization Formula: \[ M_U=\frac{\text{Used Memory}}{\text{Total Available Memory}} \times100 \]

Example

If an embedded controller has 32 KB of available RAM and the application uses 24 KB:

\[ M_U=\frac{24}{32}\times100=75\% \]

Memory utilization is 75%.

12. Power Consumption

Power consumption is an important performance metric for battery-powered and energy-sensitive embedded systems.

It is influenced by processor activity, clock frequency, peripheral operation, memory access and communication.

Important Measurements

  • Average power consumption.
  • Peak power consumption.
  • Energy consumed per operation.
  • Sleep-mode current.
  • Active-mode current.
Power Formula: \[ P=V\times I \] Energy Formula: \[ E=P\times t \]

13. Response-Time Analysis

Response-time analysis estimates the time required for a task to complete after it becomes ready.

For a simple execution without interference:

\[ R=C \]

Where C is the task's execution time.

In an actual real-time system, response time may also include higher-priority task interference, blocking and scheduling effects.

A simplified fixed-priority response-time recurrence for task \(i\), under the usual single-processor preemptive assumptions, is:

\[ R_i^{(k+1)} = C_i+B_i+ \sum_{j\in hp(i)} \left\lceil\frac{R_i^{(k)}}{T_j}\right\rceil C_j \]

Where:

  • \(C_i\) = WCET of task i.
  • \(B_i\) = Blocking time of task i.
  • \(hp(i)\) = Set of tasks with higher priority than task i.
  • \(T_j\) = Period of higher-priority task j.
  • \(C_j\) = WCET of higher-priority task j.

The calculation is repeated until the response-time estimate converges or exceeds the task's deadline.

15. Measuring Performance in Embedded Systems

Engineers use hardware and software tools to measure real-time system behavior.

Common Measurement Techniques

  • Hardware Timers: Measure elapsed time between events.
  • GPIO Timing: Toggle a pin around a code section and measure pulse duration using an oscilloscope or logic analyzer.
  • Cycle Counters: Measure processor cycles where supported.
  • UART Logging: Record timestamps and execution events.
  • RTOS Trace Tools: Analyze task switches and execution intervals.
  • Debugger: Inspect variables, registers and execution flow.
  • Power Analyzer: Measure current and power consumption.

Keil uVision Simulator Practice

In a simulator-based LPC2129 learning environment, you can practice timing and software behavior using:

  • Timer registers and simulated timer interrupts.
  • Debugger breakpoints and execution tracing.
  • CPU and peripheral register inspection.
  • UART output where supported by the simulator setup.
  • Software counters and timestamp variables.
Simulation Limitation: Simulator measurements do not establish physical hardware WCET, electrical interrupt latency or actual power consumption. Those measurements require the target hardware and suitable measurement equipment.

16. Lesson Summary

  • Execution time measures processor time used by a task.
  • Response time measures task release to completion.
  • Latency measures delay between defined events.
  • Jitter measures variation in timing.
  • Deadline-miss ratio measures missed task deadlines.
  • CPU utilization measures processor workload.
  • Throughput measures completed work per unit time.
  • Blocking and scheduling latency affect response time.
  • Memory and power utilization are important embedded-system metrics.
  • Performance measurement helps verify real-time requirements.
