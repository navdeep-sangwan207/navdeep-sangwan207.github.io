Real-Time vs Non-Real-Time Systems

Chapter 01 | Lesson 03

Comparing timing-critical computing with conventional computing systems

Home Chapter Index RTOS Course

1. Introduction

Computer systems are designed for different purposes. Some systems focus on producing accurate results with high throughput, while others must produce correct results within specified time limits.

Based on their timing requirements, computing systems can be broadly discussed as real-time systems and non-real-time systems.

A real-time system considers timing constraints an essential part of correctness. A non-real-time system generally focuses on functional correctness, throughput, user experience or overall performance without strict application deadlines.

Fundamental Difference: In a real-time system, a logically correct result delivered after its required deadline may be considered incorrect. In a non-real-time system, a delayed result may still be useful.

2. What is a Real-Time System?

A real-time system is a computing system whose operation must satisfy specified timing constraints. Its tasks are designed to respond to events and complete within defined deadlines.

Characteristics

  • Time constraints are part of system correctness.
  • Task deadlines must be considered during design.
  • Response time should be bounded where required.
  • Predictable execution is important.
  • Interrupts and task scheduling require careful management.
  • System behavior must be analyzed under expected workloads.

Examples

  • Automotive airbag controllers.
  • Industrial motor protection systems.
  • Medical monitoring equipment.
  • Aircraft flight-control systems.
  • Robotics and motion-control systems.

3. What is a Non-Real-Time System?

A non-real-time system is a computing system that does not generally require every operation to finish within a strict, predefined deadline.

Its primary objectives may include computational accuracy, throughput, convenience, resource utilization and user experience. A delayed result may reduce performance or convenience without necessarily causing system failure.

Characteristics

  • No strict deadline for every operation.
  • Focus on overall system performance and throughput.
  • Execution time may vary considerably.
  • Occasional delays may be acceptable.
  • Resource allocation may prioritize fairness or throughput.

Examples

  • Desktop document editing.
  • Offline file compression.
  • Batch data processing.
  • General-purpose file management.
  • Many background administrative applications.
Important: These categories depend on application requirements, not simply the device or operating system. A general-purpose operating system can run real-time applications, and an embedded device can also run non-real-time software.

4. Major Differences Between Real-Time and Non-Real-Time Systems

Parameter Real-Time System Non-Real-Time System
Primary Requirement Correct result within required time. Correct result and overall performance.
Deadlines Explicit timing deadlines may be mandatory. Strict deadlines are generally not required.
Response Time Must satisfy defined timing constraints. May vary depending on system load.
Determinism Predictable timing is important. Predictable timing is not usually a strict requirement.
Scheduling May use deadline-aware or priority-based scheduling. May prioritize fairness, throughput or responsiveness.
Late Result May be useless or constitute a failure. May still be useful.
System Design Timing analysis and deadline verification. Performance and resource optimization.
Applications Control, monitoring and protection. Office software and general computing.

5. Comparison of Scheduling Requirements

Scheduling determines which task or process receives processor time. The scheduling strategy depends on the system's objectives.

Real-Time Scheduling

  • Task priorities may be based on timing criticality.
  • Higher-priority tasks may preempt lower-priority tasks.
  • Deadlines and response times are considered.
  • Worst-case execution and blocking times may need analysis.

Non-Real-Time Scheduling

  • Scheduling may focus on fairness and throughput.
  • Interactive tasks may receive responsiveness-oriented treatment.
  • Execution delays may be tolerated.
  • Strict application deadline guarantees are not generally required.

6. Real-Time System Example: Motor Protection

Application: Overcurrent Protection Controller

A motor protection controller monitors current and issues a shutdown command when an unsafe current condition is detected.

  1. A current sensor provides a measurement.
  2. The controller checks the current value.
  3. The protection logic detects an overcurrent condition.
  4. A shutdown command is issued.
  5. The system records the fault condition.

The detection and shutdown operations must satisfy the protection system's specified timing requirements.

7. Non-Real-Time System Example: File Compression

Application: Compressing a Large File

A computer compresses a large collection of files into an archive.

  1. The user selects files.
  2. The compression application reads the data.
  3. The algorithm compresses the files.
  4. The application creates the archive.
  5. The user receives the completed output.

If compression takes longer than expected, the operation may be inconvenient, but the result can still be useful.

8. Real-Time vs Non-Real-Time Operating Systems

Operating systems provide services for managing processes, threads, memory, devices and system resources. Their design objectives can differ depending on the required timing behavior.

Feature Typical RTOS Typical General-Purpose OS
Design Focus Predictable timing and deadline requirements. General functionality, throughput and responsiveness.
Scheduling Often fixed-priority or deadline-oriented. May use fairness and dynamic scheduling policies.
Interrupt Handling Designed to support bounded response where required. Optimized for general system operation.
Kernel Services Task scheduling, synchronization and time management. Processes, threads, memory, files and devices.
Deadline Analysis Often central to system design. Not normally a general application guarantee.

Examples of RTOS kernels include FreeRTOS and other real-time operating systems. Windows and standard desktop Linux configurations are general-purpose operating systems. Specialized real-time configurations, such as PREEMPT_RT Linux, can provide stronger real-time behavior.

9. Hybrid Systems

A system can contain both real-time and non-real-time activities. Such systems are often described as mixed-criticality or mixed-workload systems, depending on their design.

Example: Automotive Electronic System

Activity Requirement
Engine control Time-sensitive control response.
Braking control Strict timing and safety requirements.
Dashboard display Timely display updates.
Media playback Generally tolerates some delay.
Diagnostic logging Often handled as a lower-priority activity.

The system must isolate and schedule activities so that less-critical workloads do not interfere with critical timing requirements.

10. When Should a Real-Time System Be Used?

A real-time approach is appropriate when an application has important timing requirements that must be satisfied.

  • Industrial process control.
  • Motor control and protection.
  • Automotive safety functions.
  • Robotics and automation.
  • Medical monitoring and control.
  • Time-sensitive communication systems.

11. When Is a Non-Real-Time System Suitable?

A conventional computing approach is generally sufficient when occasional execution delays do not violate essential application requirements.

  • Document processing.
  • Web browsing and general office applications.
  • File management.
  • Offline data analysis.
  • Batch processing and report generation.

12. Advantages and Limitations

Real-Time Systems

Advantages
  • Predictable response for appropriately designed systems.
  • Suitable for timing-critical applications.
  • Supports controlled task prioritization.
  • Useful for embedded monitoring and control.
Challenges
  • Requires careful timing analysis.
  • Resource constraints can complicate scheduling.
  • Priority inversion and blocking must be managed.
  • Verification and testing can be demanding.

Non-Real-Time Systems

Advantages
  • Suitable for general-purpose computing.
  • Can prioritize throughput and user experience.
  • Supports a wide range of applications.
  • Often provides flexible resource management.
Limitations
  • Response times may vary.
  • Strict deadline guarantees are generally unavailable.
  • Not suitable by default for safety-critical control.

13. Lesson Summary

  • Real-time systems consider timing constraints part of correctness.
  • Non-real-time systems generally prioritize functional results and overall performance.
  • Real-time tasks must satisfy their specified deadlines.
  • General-purpose operating systems do not normally guarantee arbitrary application deadlines.
  • RTOS scheduling is designed to support time-sensitive operations.
  • A single embedded system can contain both real-time and non-real-time activities.
  • System selection depends on application requirements, not simply hardware type.

Classify each application according to its primary timing requirement:

  1. Automotive airbag deployment controller.
  2. Desktop word processor.
  3. Industrial emergency shutdown controller.
  4. Offline video file conversion.
  5. Robot motion-control system.

Interview Tip: Do not define a real-time system simply as a fast system. The important distinction is whether the system can satisfy its required timing constraints.
