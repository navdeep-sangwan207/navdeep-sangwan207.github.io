2. Introduction to Interrupts

An interrupt is an event that causes the processor to temporarily suspend its current instruction flow and execute an interrupt-handling routine or other architecture-defined handler.

After handling the event, the processor may resume the interrupted program or continue according to the exception-handling mechanism.

Example

Consider a microcontroller receiving serial data through UART. When the UART receives a character and generates an interrupt, the processor can execute the corresponding interrupt service routine to process the event.

Key concept: Interrupts allow a processor to respond to events without requiring the main program to continuously check every peripheral.

3. Why Are Interrupts Required?

Without interrupts, a processor may repeatedly check peripheral status registers to determine whether an event has occurred. This technique is called polling.

Interrupt-driven operation allows a peripheral to request processor attention when a relevant event occurs.

Benefits

  • Reduces the need for continuous polling.
  • Allows timely response to external events.
  • Supports efficient peripheral communication.
  • Enables timer-based scheduling.
  • Supports asynchronous event handling.
  • Can improve CPU utilization when events are infrequent.

4. Types of Interrupts

4.1 Hardware Interrupts

A hardware interrupt is generated by a hardware device or peripheral.

Examples include:

  • Timer overflow or match events.
  • UART receive or transmit events.
  • External pin events.
  • ADC conversion completion.
  • Network interface events.

4.2 Software Interrupts

A software interrupt is initiated by executing a specific instruction or software mechanism that requests an exception or controlled transfer of execution.

Historically, software interrupt instructions have been used to request operating-system services or enter privileged execution modes.

Examples include:

  • x86 software interrupt instruction such as INT.
  • ARM7 SWI instruction.
  • Software-generated exceptions in some processor architectures.
Terminology: Modern processors use several mechanisms for system calls. A system call is an OS service interface, not simply another name for every software interrupt.

5. Polling vs Interrupt-Driven I/O

Polling

In polling, the processor repeatedly checks a device status register to determine whether an event has occurred.

while (1)
{
    if (UART_Receive_Ready())
    {
        data = UART_Read();
        Process_Data(data);
    }
}

Interrupt-Driven I/O

In interrupt-driven I/O, the processor can perform other work until the peripheral requests attention.

void UART_IRQHandler(void)
{
    if (UART_Receive_Ready())
    {
        data = UART_Read();
        Store_Received_Data(data);
    }
}

int main(void)
{
    UART_Init();
    UART_Interrupt_Enable();

    while (1)
    {
        Perform_Other_Tasks();
    }
}

The function names above are illustrative. Actual register operations and interrupt-handler names depend on the microcontroller and toolchain.

Polling Interrupt-Driven I/O
CPU repeatedly checks device status. Device requests CPU attention through an interrupt.
Can waste CPU time when events are infrequent. Can reduce unnecessary status checking.
Timing depends on polling frequency. Response depends on interrupt and processor latency.
Often simpler to implement. Requires careful interrupt handling and synchronization.

6. Interrupt Service Routine (ISR)

An Interrupt Service Routine (ISR) is a function or handler executed in response to an interrupt or exception.

Responsibilities of an ISR

  • Identify the interrupt source where required.
  • Read or acknowledge the relevant peripheral status.
  • Transfer received data into an appropriate buffer.
  • Clear or acknowledge the interrupt condition as required.
  • Notify a task or defer lengthy processing when appropriate.

Example: Timer Interrupt

volatile unsigned int timer_count = 0;

void Timer_IRQHandler(void)
{
    timer_count++;

    Clear_Timer_Interrupt_Flag();
}

int main(void)
{
    Timer_Init();
    Timer_Interrupt_Enable();

    while (1)
    {
        // Main application processing
    }
}

This is illustrative embedded C. The actual interrupt vector, timer register, and flag-clearing sequence depend on the target device.

7. Interrupt Priority

When multiple interrupt sources are active, the processor or interrupt controller may use priority levels to determine which interrupt is serviced first.

Example

Interrupt source Illustrative priority Purpose
Emergency input Highest Respond to a critical external event.
Timer interrupt High Maintain timing operations.
UART interrupt Medium Handle serial communication.
Background monitoring Low Perform non-urgent monitoring.

Priority numbering and arbitration rules vary by processor and interrupt controller. The table illustrates relative importance, not LPC2129 register settings.

8. Nested Interrupts

Nested interrupts occur when an interrupt handler is interrupted by another interrupt before the first handler finishes.

Many processors and interrupt controllers support nesting according to priority and masking rules.

Example sequence

Main Program
     |
     v
Low-Priority Interrupt
     |
     v
High-Priority Interrupt
     |
     v
High-Priority ISR completes
     |
     v
Low-Priority ISR resumes
     |
     v
Main Program resumes

Nested interrupt handling requires careful management of stack usage, register preservation, and interrupt priorities.

9. Interrupt Latency

Interrupt latency is the time between an interrupt event becoming active and the start of the corresponding interrupt service routine.

Factors affecting latency

  • Current processor instruction and architecture.
  • Interrupt masking or disabling.
  • Higher-priority interrupt activity.
  • Processor operating frequency.
  • Interrupt-controller behavior.
  • Memory and bus wait states.

Low and predictable interrupt latency is important in many real-time applications.

10. Exceptions and Traps

An exception is an event detected by the processor that changes normal program execution. Exceptions can arise from instruction execution, processor faults, or other architecture-defined conditions.

Examples

  • Division by zero, where supported as an exception condition.
  • Invalid or undefined instruction.
  • Memory access fault.
  • Breakpoint or debug event.
  • System-call trap.

Trap

A trap is commonly described as a synchronous exception associated with the execution of a particular instruction. It may be used for debugging or requesting an operating-system service.

Architecture terminology varies, so the precise classification of interrupts, traps, and exceptions depends on the processor.

11. Introduction to System Calls

A system call is a controlled interface through which a user-space program requests a service from the operating-system kernel.

Applications cannot directly perform every privileged operation. They request kernel services through defined system-call interfaces.

Why are system calls required?

  • To access files and devices through kernel-controlled interfaces.
  • To create and manage processes.
  • To allocate or manage memory through OS services.
  • To communicate between processes.
  • To use networking services.
  • To enforce access permissions and protection.
Key concept: A system call provides a controlled entry point from an application into kernel services.

12. Common Categories of System Calls

Category Purpose Linux examples
Process Management Create, execute, and terminate processes. fork(), execve(), wait(), exit()
File Management Open, read, write, and close files. open(), read(), write(), close()
Memory Management Manage virtual memory mappings. mmap(), munmap(), brk()
Device Management Access device-specific interfaces. ioctl()
Communication Exchange information between processes. pipe(), socket(), send(), recv()
Information Management Obtain process and system information. getpid(), uname()

These are Linux system-call interfaces or commonly used system-call functions. Some library functions wrap one or more system calls rather than directly corresponding to a single kernel entry.

13. How a System Call Works

A system call follows a controlled sequence of operations.

Step 1: Application Requests a Service

A user-space application calls a library function or system-call wrapper.

Step 2: System-Call Arguments Are Prepared

The system-call number and arguments are placed according to the operating-system ABI.

Step 3: Controlled Kernel Entry

A processor-specific instruction transfers control to the kernel through a defined entry mechanism.

Step 4: Kernel Validates the Request

The kernel checks the system-call number, arguments, permissions, and relevant resources.

Step 5: Kernel Performs the Service

The requested operation is performed if the request is valid and permitted.

Step 6: Return to User Space

The kernel returns a result or error indication to the application and execution continues in user mode.

User Application
       |
       v
Library / System Call Wrapper
       |
       v
System-Call Instruction
       |
       v
Kernel Entry
       |
       v
Validate Arguments and Permissions
       |
       v
Perform Requested Service
       |
       v
Return Result to User Space

14. System Calls in Linux

Linux provides system calls for file access, process creation, communication, memory management, and many other services.

Example: Reading a File

#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main(void)
{
    int fd;
    char buffer[100];
    ssize_t bytes;

    fd = open("sample.txt", O_RDONLY);

    if (fd == -1)
    {
        perror("open");
        return 1;
    }

    bytes = read(fd, buffer, sizeof(buffer) - 1);

    if (bytes == -1)
    {
        perror("read");
        close(fd);
        return 1;
    }

    buffer[bytes] = '\0';

    printf("File content: %s\n", buffer);

    close(fd);

    return 0;
}

Compilation

gcc system_call_demo.c -o system_call_demo

Execution

./system_call_demo

Create a file named sample.txt in the same directory and add some text before running the program.

Observe System Calls

strace ./system_call_demo

The strace utility displays system calls and signals observed during program execution on Linux.

15. Interrupts vs System Calls

Feature Interrupt System Call
Purpose Responds to an event requiring processor attention. Requests an operating-system service.
Origin Often hardware, but may also be software-generated. Initiated by an application through a defined interface.
Timing Hardware interrupts are generally asynchronous to the current instruction stream. Normally initiated synchronously by application execution.
Handler Interrupt or exception handler. Kernel system-call handler.
Example UART receive interrupt. Linux read() system call.
Important: A system call may use a processor trap or dedicated system-call instruction to enter the kernel. It is not necessarily implemented as a conventional hardware interrupt.

16. Interrupts and System Calls in Embedded Systems

Embedded systems use interrupts to respond to peripheral events and may use RTOS services to coordinate application tasks.

Typical examples

  • Timer interrupt for periodic scheduling.
  • UART interrupt for serial data reception.
  • ADC interrupt for conversion completion.
  • External interrupt for switch or sensor events.
  • RTOS API calls for task communication and synchronization.

On a microcontroller without a general-purpose operating-system kernel, RTOS APIs provide task-management and synchronization services. They should not automatically be described as Linux-style system calls.

17. Interrupts and System Calls in FreeRTOS

FreeRTOS applications use kernel APIs to create tasks, delay execution, communicate through queues, and synchronize tasks.

Examples of task-level APIs

xTaskCreate(...);

vTaskDelay(pdMS_TO_TICKS(100));

xQueueSend(queueHandle, &data, portMAX_DELAY);

xQueueReceive(queueHandle, &data, portMAX_DELAY);

These are FreeRTOS kernel API functions, not Linux system calls.

Interrupt-to-task communication

An ISR can notify a task using an appropriate ISR-safe FreeRTOS API, such as a queue-send or semaphore-give variant designed for interrupt context.

The ISR must follow the selected port's interrupt-priority and API restrictions. A context switch may be requested so that a newly unblocked higher-priority task can execute after the interrupt handler completes.

18. ARM7 and LPC2129 Interrupt Concepts

The LPC2129 uses an ARM7TDMI-S core and an on-chip Vectored Interrupt Controller (VIC).

Important ARM7 exception modes

  • User mode.
  • System mode.
  • Supervisor mode.
  • IRQ mode.
  • FIQ mode.
  • Abort mode.
  • Undefined mode.

IRQ and FIQ

ARM7 provides IRQ and FIQ exception types. FIQ has a dedicated banked-register arrangement intended to support fast interrupt handling.

LPC2129 VIC

The VIC manages interrupt sources and provides mechanisms for assigning interrupt channels and selecting interrupt handlers.

For example, UART0, UART1, timers, and other peripherals can generate interrupt requests through their respective peripheral and VIC configurations.

Architecture distinction: ARM7 uses its own exception and interrupt model. Do not apply Cortex-M NVIC register names or Cortex-M-specific FreeRTOS interrupt-priority configuration rules to LPC2129.

19. Best Practices for Interrupt and System-Call Handling

Interrupt-handling practices

  • Keep interrupt service routines short.
  • Acknowledge or clear interrupt sources correctly.
  • Avoid unnecessary blocking operations inside ISRs.
  • Protect shared data where required.
  • Use buffers for transferring data between interrupt and task contexts.
  • Respect interrupt priority and nesting rules.

System-call practices

  • Check return values for errors.
  • Validate input and resource permissions.
  • Handle partial reads and writes where applicable.
  • Release resources such as file descriptors.
  • Avoid assuming that every library function maps to one system call.

20. Lesson Summary

  • Interrupts allow the processor to respond to important events.
  • Hardware interrupts are generated by hardware sources.
  • Software-generated exceptions are initiated through instructions or software mechanisms.
  • An ISR handles an interrupt or exception event.
  • Interrupt priority determines service ordering according to processor rules.
  • Interrupt latency measures the time before the handler starts.
  • Exceptions are processor-detected events that alter normal execution.
  • System calls provide controlled access to kernel services.
  • Linux system calls include file, process, memory, and communication operations.
  • FreeRTOS kernel APIs are not the same as Linux system calls.
  • Interrupts do not always cause a task context switch.
