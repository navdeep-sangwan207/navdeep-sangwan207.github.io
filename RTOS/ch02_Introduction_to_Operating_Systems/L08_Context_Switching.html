2. Introduction to Context Switching

Context switching is the mechanism by which an operating system or RTOS stops the execution of one task and transfers CPU execution to another task.

Before switching, the system saves the execution state of the currently running task. It then restores the saved state of the selected task so that execution can continue from the correct point.

Example

Consider a computer running two processes:

  • Process A – Text editor.
  • Process B – Music player.

When the operating system switches from Process A to Process B, it preserves the execution state of A and restores the previously saved state of B.

Key concept: Context switching allows multiple tasks to share a processor without losing their execution progress.

3. What Is a Process Context?

A process context is the execution information and operating-system state required to manage and resume a process.

Depending on the operating system and architecture, it may include:

  • CPU register values.
  • Program counter or instruction pointer.
  • Stack pointer.
  • Processor status register.
  • Memory-management information.
  • Scheduling and process-management information.
  • Other architecture-specific execution state.

Example

If a process is interrupted while executing an instruction sequence, its saved context enables the operating system to resume it later from the appropriate execution point.

4. CPU Registers Involved in Context Switching

The processor contains registers that hold information needed during program execution.

Register Purpose
Program Counter (PC) Contains the address associated with the next instruction to execute.
Stack Pointer (SP) Points to the current stack location.
General-Purpose Registers Hold temporary data, addresses, and intermediate results.
Status Register Contains condition flags and processor-state information.
Control Registers May contain memory-management or processor-control information.

The exact registers saved depend on the processor architecture, calling convention, interrupt mechanism, and operating-system implementation.

5. How Context Switching Works

A simplified context switch between two tasks involves the following stages.

Step 1: An Event Occurs

The running task may be interrupted by a timer, request I/O, block on a resource, yield the CPU, or be preempted by a higher-priority task.

Step 2: Processor Control Transfers

The processor enters the appropriate operating-system or interrupt-handling code. Some processor state may be saved automatically by hardware, while additional state is saved by software.

Step 3: Save the Current Task Context

The operating system saves the required registers, stack pointer, and other execution information for the current task.

Step 4: Update Task State

The scheduler updates the task's state. For example, it may become ready, blocked, or remain eligible for execution depending on the event.

Step 5: Select the Next Task

The scheduler chooses a task according to the scheduling policy, priorities, and current task states.

Step 6: Restore the Selected Task Context

The system restores the saved execution state of the selected task.

Step 7: Resume Execution

The processor resumes execution using the restored state.

Important: This is a conceptual sequence. Actual context-switching details vary between operating systems and processor architectures.

6. Context-Switching Flow Example

Suppose Task A is running and the scheduler decides to execute Task B.

Task A is running
        |
        v
Timer interrupt / blocking / yield
        |
        v
Save Task A context
        |
        v
Update Task A state
        |
        v
Scheduler selects Task B
        |
        v
Restore Task B context
        |
        v
Task B starts or resumes execution

Task A's saved context is retained so it can resume later when the scheduler selects it again.

7. Role of the Scheduler and Dispatcher

Scheduler

The scheduler determines which ready task should execute next.

Its decision may depend on:

  • Task priority.
  • Scheduling algorithm.
  • Task readiness and blocking state.
  • Time-slice expiration.
  • Deadline or timing requirements in applicable systems.

Dispatcher

The dispatcher performs the operations needed to transfer CPU execution to the task selected by the scheduler.

Typical dispatcher responsibilities include restoring execution state and transferring control to the selected task.

Scheduler Dispatcher
Selects the next task. Transfers CPU execution to that task.
Applies scheduling policy. Performs the required dispatch operations.
Decides who runs next. Helps make that task run.

8. Process Context Switching

A process context switch occurs when the operating system switches CPU execution from one process to another.

In addition to saving CPU execution state, the operating system may need to change address-space-related state.

Possible operations

  • Save the current process's execution state.
  • Update process scheduling information.
  • Change memory-management context where required.
  • Restore the next process's execution state.
  • Resume execution in the selected process.

For systems using virtual memory, changing address spaces may involve page-table or memory-management-unit operations. The exact cost depends on the processor and operating system.

9. Thread Context Switching

A thread context switch occurs when CPU execution moves from one thread to another.

Threads within the same process commonly share an address space and other process resources. However, each thread has its own execution state.

Thread-specific context includes:

  • Program counter.
  • Stack pointer.
  • CPU registers.
  • Thread scheduling information.
  • Thread-specific processor state where applicable.

When switching between threads of the same process, the operating system may not need to change the address space. This can make some same-process thread switches less expensive than process switches, although the actual cost is implementation-dependent.

10. Process Switching vs Thread Switching

Feature Process Switch Thread Switch
Execution unit Between processes Between threads
Address space May need to change Often remains the same within one process
Register state Must be preserved and restored Must be preserved and restored
Memory context Process-specific context may change Shared process memory is commonly retained
Typical overhead Can be higher Can be lower for threads in the same process

11. Context Switching in Preemptive Multitasking

In preemptive multitasking, the scheduler can interrupt a running task and select another eligible task.

Example

Suppose two tasks are ready:

  • Task A – Priority 2.
  • Task B – Priority 5.

Assume a larger number represents a higher priority. If Task A is running and Task B becomes ready, a priority-based preemptive scheduler may switch to Task B.

The exact behavior depends on the scheduling policy and configuration.

12. Context Switching in Cooperative Multitasking

In cooperative multitasking, a task generally gives up CPU control voluntarily.

When a task yields or blocks, the scheduler can select another ready task.

while (1)
{
    Task_A_Work();

    // Give another task an opportunity to execute.
    Yield_CPU();

    Task_A_Continue();
}

Yield_CPU() is illustrative pseudocode, not a standard C or operating-system function.

If a cooperative task performs a long operation without yielding, other tasks may experience significant delays.

13. Context-Switching Overhead

Context-switching overhead is the processing time and resource cost associated with stopping one task and transferring execution to another.

Sources of overhead

  • Saving processor registers.
  • Restoring another task's registers.
  • Executing scheduler and dispatcher code.
  • Changing address-space state where required.
  • Cache and translation-lookaside-buffer effects.
  • Interrupt and kernel-management operations.

Illustrative calculation

Suppose a system performs 100 context switches per second and each switch consumes an average of 5 microseconds.

Total context-switching time per second:

100 × 5 microseconds
= 500 microseconds

Percentage of one second:

(500 / 1,000,000) × 100
= 0.05%

This is a simplified calculation. Real switching costs can vary with hardware, operating-system activity, cache behavior, and workload.

14. Factors Affecting Context-Switching Time

  • Processor architecture: Register count and hardware support affect save/restore operations.
  • Operating-system design: Kernel implementation affects scheduling and dispatch overhead.
  • Memory management: Address-space changes can add work.
  • Cache behavior: Switching workloads may reduce cache efficiency.
  • Task state size: Additional processor state may need saving.
  • Interrupt activity: Interrupt handling can influence the time before a task resumes.

15. Context Switching in RTOS

In a Real-Time Operating System, context switching is essential for moving CPU execution between tasks according to the scheduling policy.

Common RTOS switching events

  • A higher-priority task becomes ready.
  • A running task blocks while waiting for an event.
  • A task voluntarily yields.
  • A scheduling tick causes a scheduling decision.
  • A task completes or is suspended.

RTOS implementations aim to make scheduling and switching behavior sufficiently predictable for their intended application.

Real-time consideration: Low context-switching overhead is useful, but it does not alone guarantee real-time performance. Interrupt latency, task execution time, blocking, scheduling policy, and deadline analysis also matter.

16. Context Switching in FreeRTOS

FreeRTOS uses task context management to switch execution between tasks.

Typical sequence

  1. A scheduling event occurs, such as a tick interrupt or task blocking operation.
  2. The port-specific context-switch mechanism preserves the running task's required state.
  3. The scheduler selects the next eligible task.
  4. The selected task's saved state is restored.
  5. Execution resumes in the selected task.

Important FreeRTOS concepts

  • Each task has its own stack.
  • Task control information is maintained by the kernel.
  • The scheduler selects a ready task according to priority and configuration.
  • Port-specific code implements processor context save and restore.
  • Interrupts can trigger a scheduling decision when permitted by the port and API rules.

FreeRTOS context-switching implementation differs between processor architectures. The exact registers and interrupt mechanisms depend on the selected port.

17. Context Switching on ARM7 and LPC2129

The LPC2129 uses an ARM7TDMI-S processor. Its processor architecture provides several operating modes and banked registers that are relevant to exception handling and task-context management.

Important ARM7 registers

  • R0–R12 – General-purpose registers.
  • R13 – Stack Pointer (SP).
  • R14 – Link Register (LR).
  • R15 – Program Counter (PC).
  • CPSR – Current Program Status Register.
  • SPSR – Saved Program Status Register in exception modes.

Banked registers

ARM7 provides banked registers in certain processor modes. These help the processor handle exceptions and interrupts efficiently.

For example, IRQ mode has banked stack-pointer and link-register registers and an SPSR_irq register.

RTOS context management

An ARM7 RTOS port must preserve the state required to resume a task correctly. The exact save and restore sequence depends on the port's exception and context-switch implementation.

Simulator limitation: Keil uVision can help inspect ARM registers, processor modes, stack memory, and instruction flow. This does not establish that a particular FreeRTOS ARM7 port is supported or that physical interrupt timing has been validated on LPC2129 hardware.

18. Context Switching vs Interrupt Handling

Interrupt handling and context switching are related, but they are not the same operation.

Interrupt Handling Context Switching
Responds to an interrupt or exception event. Transfers execution from one task to another.
May execute an interrupt service routine. Saves and restores task execution state.
Does not always require a task switch. Changes the currently executing task.
Can trigger a scheduling decision. May occur as a result of that scheduling decision.

A timer interrupt may cause the scheduler to switch tasks. However, an interrupt can also be serviced and return to the same task without a task-level context switch.

19. Methods to Reduce Context-Switching Overhead

  • Avoid unnecessary task creation and excessive task switching.
  • Use suitable task priorities.
  • Choose an appropriate RTOS tick rate.
  • Keep interrupt service routines short.
  • Use blocking operations instead of continuously polling when appropriate.
  • Avoid unnecessarily frequent task yields.
  • Use efficient data-sharing and synchronization designs.
  • Measure actual performance on the target platform.

20. Lesson Summary

  • Context switching transfers CPU execution between tasks.
  • The current task's execution state must be preserved.
  • The selected task's saved state is restored before execution resumes.
  • The scheduler selects the next task.
  • The dispatcher performs the transfer of execution.
  • Process switches may require address-space changes.
  • Thread switches within one process may avoid address-space changes.
  • Context switching introduces processing overhead.
  • RTOS context switching is closely related to task scheduling.
  • Interrupt handling does not always result in a task switch.
