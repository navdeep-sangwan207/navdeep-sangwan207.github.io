Lesson Overview

Modern operating systems use processor privilege levels to protect the operating system and hardware from unauthorized application access. Two important execution modes are user mode and kernel mode. This lesson explains their responsibilities, system calls, privilege transitions and their importance in embedded systems.

Learning Objectives:

  • Understand CPU privilege levels and execution modes.
  • Differentiate user mode and kernel mode.
  • Understand privileged instructions and protected memory.
  • Explain system calls and mode transitions.
  • Differentiate system calls, interrupts and exceptions.
  • Relate processor modes to ARM7 and LPC2129.

1. Introduction to CPU Privilege Levels

A processor executes instructions for applications, operating systems and device-control software. However, allowing every application to directly access all processor resources can cause serious problems.

For example, an ordinary application should not be allowed to overwrite operating-system memory, directly reconfigure critical hardware registers or disable essential system protection.

To prevent unauthorized operations, processors provide privilege levels or execution modes. These levels determine which instructions and resources software can access.

Why are privilege levels required?

  • Protect operating-system code and data.
  • Prevent applications from accessing restricted memory.
  • Control access to hardware devices.
  • Improve system stability and security.
  • Isolate application failures from critical system components.
Important: User mode and kernel mode are logical execution privileges enforced by processor architecture and operating-system mechanisms. They are not necessarily separate physical processors.

2. What is User Mode?

User mode is a restricted processor execution mode in which normal application programs execute. Applications have access to permitted resources but cannot directly perform every privileged operation.

Characteristics of user mode

  • Used by ordinary application programs.
  • Restricts access to protected kernel memory.
  • Prevents direct execution of privileged instructions.
  • Uses system calls to request operating-system services.
  • Supports process isolation in operating systems that provide it.

Examples of user-mode programs

  • Text editors and web browsers.
  • Command-line utilities.
  • Media players and office applications.
  • Programs written in C, C++ and Python.

For example, when a C application wants to read a file, it normally requests the operating system to perform the operation rather than directly controlling the storage hardware.

3. What is Kernel Mode?

Kernel mode is a privileged processor execution mode used by the operating-system kernel. It allows the kernel to execute privileged instructions and manage protected system resources.

Characteristics of kernel mode

  • Provides privileged access to processor resources.
  • Manages memory and process execution.
  • Controls hardware through device drivers.
  • Handles system calls, interrupts and exceptions.
  • Performs scheduling and other kernel services.

Examples of kernel responsibilities

  • Managing CPU scheduling.
  • Allocating and releasing memory.
  • Managing file-system operations.
  • Controlling device drivers.
  • Handling hardware interrupts.
Kernel mode does not mean that every instruction is automatically safe. A programming error inside kernel code can affect the entire operating system.

4. User Mode vs Kernel Mode

Parameter User Mode Kernel Mode
Privilege level Restricted Privileged
Typical execution Applications Operating-system kernel
Kernel memory access Normally restricted Permitted according to architecture and configuration
Privileged instructions Not permitted Permitted
Hardware access Through approved OS interfaces Through kernel mechanisms and drivers
Failure impact Often limited to the application Can affect the whole system
Examples Browser, editor, user application Scheduler, memory manager, device driver

The separation improves protection, but the exact implementation depends on the processor architecture and operating system.

5. Processor Privilege Rings

Some processor architectures provide multiple privilege levels. The x86 architecture, for example, defines four privilege rings: Ring 0, Ring 1, Ring 2 and Ring 3.

Ring 3 – User Applications
↓ Restricted Privileges
Ring 2 – Intermediate Privilege
↓
Ring 1 – Intermediate Privilege
↓
Ring 0 – Kernel / Highest Privilege
Ring Privilege Typical Usage
Ring 0 Highest Operating-system kernel
Ring 1 Intermediate Can be used by some OS designs, but uncommon in mainstream desktop systems
Ring 2 Intermediate Can be used by some OS designs, but uncommon in mainstream desktop systems
Ring 3 Lowest Ordinary user applications

Mainstream operating systems on x86 commonly use Ring 0 for kernel execution and Ring 3 for ordinary applications. Rings 1 and 2 are generally not used for typical application and kernel separation.

Privilege rings are an x86 terminology. ARM processors use their own architecture-specific execution and privilege models. Do not assume that every processor has the same four-ring structure.

6. Privileged and Non-Privileged Instructions

Processor instructions differ in the level of access they require. Instructions that can affect critical processor or system resources may be restricted to privileged execution.

Privileged instructions

Privileged instructions are instructions that require an appropriate processor privilege level. Examples on suitable architectures include:

  • Changing certain processor control registers.
  • Changing memory-management configuration.
  • Controlling interrupt masks or processor state.
  • Configuring protected system resources.

Non-privileged instructions

Ordinary arithmetic, logical, data movement and application instructions can generally execute in user mode, subject to architecture-specific restrictions.

Instruction Category Example Typical Access
Arithmetic ADD, SUB User and kernel
Logical AND, OR User and kernel
Memory access Load and store Allowed only for accessible memory regions
Processor control Architecture-specific control operations Privileged where defined
An instruction is not necessarily privileged merely because it accesses memory. Memory permissions and processor privilege rules determine whether a particular access is allowed.

7. System Calls

A system call is a controlled mechanism through which an application requests a service from the operating-system kernel.

An application running in user mode cannot directly perform every kernel operation. It uses a system-call interface to request operations such as file access, process creation and communication.

Common Linux system-call examples

System Call Purpose
open() Open a file or other supported object.
read() Read data from a file descriptor.
write() Write data to a file descriptor.
close() Close a file descriptor.
fork() Create a new process.
execve() Replace the current process image with a new program.

System-call execution sequence

Application executes in User Mode
↓
Application requests a system service
↓
System-call instruction / controlled entry
↓
Processor enters Kernel Mode
↓
Kernel validates and performs the operation
↓
Result is returned to the application
↓
Execution resumes in User Mode

Important points

  • The kernel validates the request and relevant arguments.
  • The kernel performs the permitted operation.
  • The result or error information is returned to the application.
  • The application normally continues in user mode.

8. User-to-Kernel Mode Transition

A user application may need a protected operating-system service. The processor provides a controlled transition mechanism, commonly using a system-call instruction or trap mechanism.

Step-by-step transition

  1. An application executes in user mode.
  2. The application invokes a system-call interface.
  3. The processor transfers control to a designated kernel entry point.
  4. The processor executes the kernel handler with appropriate privileges.
  5. The kernel checks the request and performs the operation.
  6. The kernel prepares a return value or error code.
  7. The processor returns to user mode and application execution resumes.
System call vs context switch: A transition from user mode to kernel mode does not automatically mean that the CPU has switched to another process or task. A system call can execute and return within the same process and thread. A context switch occurs only when the scheduler changes the executing task or thread.

9. System Calls, Interrupts and Exceptions

System calls, interrupts and exceptions can all cause execution to enter a privileged handler. However, they have different causes.

Mechanism Cause Example
System Call Software intentionally requests a kernel service. Application requests file access.
Hardware Interrupt External or peripheral event requires processor attention. Timer interrupt or UART receive interrupt.
Exception Processor detects a condition during instruction execution. Invalid instruction or memory access fault, depending on architecture.

Hardware interrupt example

Suppose a UART peripheral receives data. It can generate an interrupt request. The processor temporarily transfers execution to the corresponding interrupt handler, which services the event.

Exception example

If a program performs an invalid memory access on a protected operating system, the processor may generate a fault or exception. The operating system can handle the fault, terminate the process or take another appropriate action.

Not every interrupt or exception is a system call. They are different mechanisms, even though each may involve a transition to privileged execution.

10. Memory Protection and Process Isolation

Memory protection prevents one application from accessing memory regions that belong to the operating system or another protected process.

Major protection mechanisms

  • Privilege checking: Controls which operations software can perform.
  • Memory protection: Restricts access to protected memory regions.
  • Process isolation: Separates the address spaces of processes.
  • Access control: Determines which users and processes can access resources.
  • Device access control: Restricts direct access to hardware resources.

Example: Process isolation

Consider two independent applications running on a protected operating system. One application should not normally be able to overwrite the memory of the other application. The operating system and processor memory-protection mechanisms enforce this separation.

↔
Process B – Separate Address Space

11. Practical Example: Using System Calls in C

The following Linux program uses the POSIX file interface to open a file, write data and close it. These operations ultimately request services from the operating-system kernel.

C program

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

int main(void)
{
    int fd;
    const char message[] = "Hello from user mode!\n";

    fd = open("sample.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);

    if (fd == -1)
    {
        perror("open");
        return 1;
    }

    ssize_t bytes_written = write(fd, message, strlen(message));

    if (bytes_written == -1)
    {
        perror("write");
        close(fd);
        return 1;
    }

    printf("Bytes written: %zd\n", bytes_written);

    close(fd);

    return 0;
}

Compilation and execution

gcc system_call_demo.c -o system_call_demo
./system_call_demo
cat sample.txt

Expected result

Bytes written: 22

File content:
Hello from user mode!

The C library provides interfaces such as open() and write(). These interfaces invoke the corresponding operating-system services, generally through system calls.

The application runs in user mode, while the kernel carries out the protected file-system and device operations. The exact internal path may involve library wrappers and additional kernel layers.

12. Practical: Observing System Calls in Linux

Linux provides the strace utility to observe system calls made by a process. It is useful for understanding how applications communicate with the kernel.

Commands

whoami
id
ls -l
strace ./system_call_demo

Command explanation

Command Purpose
whoami Displays the current effective username.
id Displays user and group identity information.
ls -l Displays file permissions and ownership information.
strace Traces system calls and signals associated with a process.

If strace is not installed on Ubuntu, install it using: 

sudo apt update
sudo apt install strace
Use sudo only when elevated permissions are required. It does not mean that every command or application should run as an administrator.

13. User Mode and Kernel Mode in Embedded Systems

Embedded processors also have execution modes and privilege mechanisms, but their implementation differs across processor families.

Embedded system without an operating system

In a simple bare-metal microcontroller application, the program generally executes directly on the processor without a separate user-space and kernel-space operating-system architecture. Privilege separation may be limited or absent.

Embedded system with an RTOS

Many microcontroller RTOS applications execute tasks in a privileged environment. Some processors and RTOS ports support memory protection through an MPU, allowing selected tasks to execute with restricted access.

ARM7 and LPC2129

The LPC2129 uses an ARM7TDMI-S processor core. ARM7 supports multiple processor modes, including:

ARM7 Mode Purpose
User Unprivileged application execution.
System Privileged execution using the user-mode register set.
Supervisor (SVC) Privileged mode commonly used for operating-system services.
IRQ Handles normal interrupt requests.
FIQ Handles fast interrupt requests.
Abort Handles memory access abort conditions.
Undefined Handles undefined instruction exceptions.

ARM7 processor modes are not the same as x86 privilege rings. Several ARM7 modes are privileged exception modes, while User mode is unprivileged.

For LPC2129 practice: In Keil uVision, use the debugger and processor-register view to inspect the CPSR mode bits, where supported by the simulator and project configuration. This helps demonstrate ARM7 processor modes without requiring physical hardware.

FreeRTOS and privilege protection

FreeRTOS commonly runs tasks in privileged mode on microcontrollers without an enabled memory-protection configuration. MPU-enabled ports can provide additional task-level memory protection, but support depends on the processor, port and configuration.

A task running under FreeRTOS should not automatically be assumed to execute in user mode. The actual privilege model must be checked for the selected MCU and RTOS port.

14. Advantages and Limitations of Mode Separation

Advantages

  • Improves operating-system security.
  • Protects kernel memory from ordinary applications.
  • Restricts unauthorized hardware access.
  • Supports process isolation and system stability.
  • Provides controlled access to operating-system services.

Limitations and overhead

  • System calls introduce execution overhead.
  • Privilege transitions require processor state handling.
  • Kernel bugs can still affect the entire system.
  • Memory protection requires suitable hardware and configuration.
  • Small microcontrollers may not provide full application isolation.

15. Lesson Summary

  • Processors use privilege mechanisms to control access to resources.
  • User mode is intended for restricted application execution.
  • Kernel mode provides privileged access to operating-system resources.
  • Privileged instructions require suitable processor permissions.
  • System calls provide a controlled interface to kernel services.
  • A mode transition does not necessarily cause a context switch.
  • Interrupts and exceptions are distinct from system calls.
  • Memory protection and process isolation improve system security.
  • ARM7 processor modes differ from x86 privilege rings.
  • RTOS privilege protection depends on processor and port capabilities.
