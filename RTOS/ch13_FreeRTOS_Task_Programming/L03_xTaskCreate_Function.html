xTaskCreate() Function

Task Creation, Parameters, Return Values and Dynamic Memory Allocation

Home RTOS Course Chapter 13

1. Learning Objectives

The xTaskCreate() function is one of the fundamental FreeRTOS APIs. It creates a new task dynamically, allocates the required task memory through the configured allocation mechanism and makes the task available to the scheduler.

  • Understand the purpose of xTaskCreate().
  • Learn its function prototype and parameters.
  • Understand task stack depth and priority.
  • Interpret the function return value.
  • Store and use a created task handle.
  • Understand dynamic memory allocation during task creation.
  • Identify common task creation failures.

2. Introduction to xTaskCreate()

FreeRTOS applications commonly use xTaskCreate() to create tasks at runtime. The application supplies a task function, name, stack depth, parameter pointer and priority. The kernel creates the task and can return its handle. 

BaseType_t xTaskCreate(
    TaskFunction_t pvTaskCode,
    const char * const pcName,
    configSTACK_DEPTH_TYPE usStackDepth,
    void *pvParameters,
    UBaseType_t uxPriority,
    TaskHandle_t *pxCreatedTask
);
The exact declaration can vary across FreeRTOS versions. Older versions commonly use configSTACK_DEPTH_TYPE-compatible parameters expressed as uint16_t. Always check the headers of the kernel release used by the project.

3. Parameters of xTaskCreate()

ParameterDescription
pvTaskCodePointer to the task function that will execute.
pcNameHuman-readable task name, mainly useful for debugging and task identification.
usStackDepthRequested stack depth, expressed in StackType_t elements (commonly called stack words), not bytes.
pvParametersPointer to data passed to the task function. Use NULL if no parameter is needed.
uxPriorityTask priority. Valid application priorities range from 0 through configMAX_PRIORITIES - 1.
pxCreatedTaskPointer to a TaskHandle_t variable where the created task handle is stored. NULL can be supplied if the handle is not required.

Understanding the Stack Depth

The stack is private execution memory used by a task for function calls, local variables, saved registers and other execution state. The requested depth is measured in stack elements rather than bytes. 

Stack memory in bytes =
    Stack depth * sizeof(StackType_t)

For example, if StackType_t is 4 bytes and a task requests 256 stack elements: 

256 * 4 = 1024 bytes
The actual size of StackType_t depends on the selected FreeRTOS port and processor architecture. Do not assume every target uses 4-byte stack elements.

4. Understanding Task Priority

FreeRTOS normally uses a fixed-priority scheduler. A task with a higher priority than a Ready task can preempt it when preemption is enabled and the scheduler is running.

PriorityTypical Interpretation
0Lowest application priority; idle task also uses the lowest priority.
1Low-priority application task.
2Medium-priority application task.
3Higher-priority application task.
configMAX_PRIORITIES - 1Highest configured task priority.

The application must choose priorities according to timing requirements, task dependencies and resource blocking. A higher priority does not automatically make a task more important in every system design.

5. Return Value of xTaskCreate()

xTaskCreate() returns a value of type BaseType_t. The application should always check this result.

Return ValueMeaning
pdPASSTask creation succeeded.
errCOULD_NOT_ALLOCATE_REQUIRED_MEMORYRequired memory could not be allocated in versions/configurations that define this error value.

In common FreeRTOS releases, the failure result is pdFAIL. Check the exact API documentation and definitions in the selected kernel version. 

BaseType_t result;

result = xTaskCreate(
    SensorTask,
    "Sensor",
    256,
    NULL,
    2,
    NULL
);

if (result == pdPASS)
{
    /* Task creation succeeded */
}
else
{
    /* Task creation failed */
}

6. Creating a Simple Task

Example: Create a task that periodically performs a monitoring operation.

#include "FreeRTOS.h"
#include "task.h"

void MonitorTask(void *pvParameters)
{
    for (;;)
    {
        /* Monitoring operation */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    BaseType_t result;

    result = xTaskCreate(
        MonitorTask,
        "Monitor",
        256,
        NULL,
        2,
        NULL
    );

    if (result == pdPASS)
    {
        vTaskStartScheduler();
    }

    for (;;)
    {
        /* Reached if scheduler could not start
           or task creation failed */
    }
}

Program Explanation

  1. Include the FreeRTOS kernel and task headers.
  2. Define the task function MonitorTask().
  3. The task executes its monitoring operation inside an infinite loop.
  4. vTaskDelay() blocks the task for approximately one second in tick-based time.
  5. xTaskCreate() requests creation of the Monitor task.
  6. vTaskStartScheduler() starts normal task scheduling after successful creation.
This is a generic FreeRTOS application example. It requires a correctly selected processor port, startup code, heap implementation, configuration and hardware/compiler integration.

7. Creating Multiple Tasks

An RTOS application usually contains multiple tasks. Each task can perform a separate function, such as sensor monitoring, communication or control. 

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read or process sensor data */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void CommunicationTask(void *pvParameters)
{
    for (;;)
    {
        /* Communication processing */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    BaseType_t result1;
    BaseType_t result2;

    result1 = xTaskCreate(
        SensorTask, "Sensor", 256,
        NULL, 3, NULL
    );

    result2 = xTaskCreate(
        CommunicationTask, "Comm", 256,
        NULL, 2, NULL
    );

    if ((result1 == pdPASS) &&
        (result2 == pdPASS))
    {
        vTaskStartScheduler();
    }

    for (;;)
    {
        /* Error handling */
    }
}

Expected Scheduling Behavior

  • SensorTask has priority 3.
  • CommunicationTask has priority 2.
  • When both are Ready, SensorTask has higher priority.
  • When SensorTask blocks, CommunicationTask can execute.
  • The scheduler selects tasks according to their states and priorities.

8. Dynamic Memory Allocation During Task Creation

The standard xTaskCreate() API uses the FreeRTOS memory allocation mechanism to obtain memory for the task's internal control structure and stack. The selected heap implementation determines how memory is managed.

The task's stack and control structure are allocated separately by the kernel's task-creation machinery. The exact allocation strategy depends on the FreeRTOS implementation and configuration.

Relevant Configuration Options

ConfigurationPurpose
configSUPPORT_DYNAMIC_ALLOCATIONEnables dynamic allocation support.
configSUPPORT_STATIC_ALLOCATIONEnables static allocation support.
configTOTAL_HEAP_SIZEConfigures heap size for heap implementations that use this setting.
configAPPLICATION_ALLOCATED_HEAPAllows an application-provided heap array in supported configurations.
configTOTAL_HEAP_SIZE is not a universal setting for every FreeRTOS heap implementation. For example, heap_3 wraps the C library allocation functions.

9. Task Creation Failure

Task creation can fail if the configured memory allocator cannot provide the required memory. Other project integration errors can prevent the application from building or starting correctly.

Common Causes

  • Insufficient FreeRTOS heap memory.
  • Excessive stack depth requested for tasks.
  • Too many dynamically allocated kernel objects.
  • Incorrect heap or allocation configuration.
  • Incorrect task function declaration.
  • Missing or incompatible FreeRTOS port files.

Basic Failure Handling

BaseType_t result;

result = xTaskCreate(
    MonitorTask,
    "Monitor",
    256,
    NULL,
    2,
    NULL
);

if (result != pdPASS)
{
    /* Record the failure */
    /* Enter a safe error-handling state */
}

In a production system, failure handling should be designed deliberately. It may include diagnostic logging, a safe-state transition or a controlled restart, depending on system requirements.

10. xTaskCreate() Versus xTaskCreateStatic()

FreeRTOS supports both dynamic and static task creation when the corresponding configuration options are enabled.

FeaturexTaskCreate()xTaskCreateStatic()
AllocationKernel allocator obtains task memory.Application supplies task memory.
Stack memoryAllocated dynamically.Supplied through a StackType_t array.
TCB memoryAllocated dynamically.Supplied through a StaticTask_t object.
Return valueBaseType_t success/failure.TaskHandle_t handle, or NULL on failure in the documented API.
ConfigurationRequires dynamic allocation support.Requires static allocation support.

Static Task Creation Example

static StaticTask_t sensorTCB;

static StackType_t sensorStack[256];

TaskHandle_t sensorHandle;

sensorHandle = xTaskCreateStatic(
    SensorTask,
    "Sensor",
    256,
    NULL,
    2,
    sensorStack,
    &sensorTCB
);

if (sensorHandle == NULL)
{
    /* Handle creation failure */
}

The stack array and StaticTask_t object must remain valid for the entire lifetime of the task. This example assumes static allocation is enabled and the API declaration matches the selected kernel.

11. Stack Sizing and Monitoring

Choosing a task stack size requires consideration of function call depth, local variables, interrupt context requirements of the port, compiler behavior and library usage.

Stack Monitoring API

UBaseType_t uxTaskGetStackHighWaterMark(
    TaskHandle_t xTask
);

This API reports the minimum remaining stack space observed since the task started, measured in StackType_t elements. It can help identify tasks that may have been allocated too much or too little stack.

A high-water mark is an observed measurement, not proof that every possible execution path is safe. Exercise worst-case code paths and use appropriate stack-overflow detection where supported.

12. Important Design Considerations

  • Choose stack depth based on measured and analyzed requirements.
  • Use meaningful task names for debugging.
  • Assign priorities based on timing and dependency analysis.
  • Check every xTaskCreate() return value.
  • Use task handles when later task control is required.
  • Keep task parameter data valid for as long as the task needs it.
  • Plan memory allocation and failure handling before deployment.
  • Do not assume a successful task creation guarantees the scheduler will start successfully.
  • Ensure the selected FreeRTOS port and compiler are compatible with the target processor.

13. Practical Activity – Create Two Tasks

Objective: Create two tasks with different priorities and verify their scheduling behavior.

Procedure

  1. Write two task functions: SensorTask and CommunicationTask.
  2. Create SensorTask with priority 3.
  3. Create CommunicationTask with priority 2.
  4. Check the return value of both task creation calls.
  5. Start the scheduler only if both tasks are created successfully.
  6. Use suitable blocking delays in both task loops.
  7. Observe task execution using a supported debugger or trace tool.

Expected Result

Both tasks should be created successfully when sufficient memory and a valid FreeRTOS port are available. The scheduler should select Ready tasks according to the configured priorities and scheduling policy.

15. Lesson Summary

  • xTaskCreate() dynamically creates a FreeRTOS task.
  • The task function defines the task's execution behavior.
  • Stack depth is specified in stack elements, not bytes.
  • Task priority determines scheduling precedence among Ready tasks.
  • pxCreatedTask can receive the new task's handle.
  • pdPASS indicates successful task creation.
  • Dynamic task creation depends on the configured memory allocator.
  • xTaskCreateStatic() uses application-supplied memory.
  • Stack sizing and allocation failure handling are important design responsibilities.
