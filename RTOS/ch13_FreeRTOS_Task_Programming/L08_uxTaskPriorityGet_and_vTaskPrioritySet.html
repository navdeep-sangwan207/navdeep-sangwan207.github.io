1. Learning Objectives

2. Introduction to Task Priority

Task priority is a numerical value assigned to a task when it is created. The scheduler uses this value to select a task from the Ready state.

In the standard FreeRTOS priority convention, a larger numerical value represents a higher priority.

TaskPriorityRelative Priority
Task A1Lower
Task B2Higher than A
Task C3Higher than B
Task D4Highest among these tasks
A task with a higher priority does not necessarily run continuously. It must be in the Ready state. A higher-priority task that is Blocked or Suspended does not prevent a lower-priority Ready task from executing.

3. FreeRTOS Task Priority Range

The number of available task priorities is configured using configMAX_PRIORITIES in FreeRTOSConfig.h. 

#define configMAX_PRIORITIES  5

With this configuration, the valid priority values are:

Priority ValueDescription
0Lowest task priority; the Idle task normally uses this priority.
1Low application priority.
2Medium application priority.
3High application priority.
4Highest configured application priority.
For configMAX_PRIORITIES = 5, valid task priorities are 0 through 4. The value 5 is not a valid task priority in this configuration. The actual configuration must be checked in the application's FreeRTOSConfig.h.

4. uxTaskPriorityGet() Function

uxTaskPriorityGet() returns the current priority of a specified task.

Syntax

UBaseType_t uxTaskPriorityGet(
    TaskHandle_t xTask
);

Parameter

ParameterDescription
xTaskHandle of the task whose priority is required. NULL refers to the calling task.

Return Value

The function returns the task's current priority as a UBaseType_t value.

Example

UBaseType_t currentPriority;

currentPriority = uxTaskPriorityGet(NULL);

This example reads the priority of the task currently executing.

5. vTaskPrioritySet() Function

vTaskPrioritySet() changes the priority of an existing task.

Syntax

void vTaskPrioritySet(
    TaskHandle_t xTask,
    UBaseType_t uxNewPriority
);

Parameters

ParameterDescription
xTaskHandle of the task whose priority must be changed. NULL refers to the calling task.
uxNewPriorityNew priority value, within the configured valid priority range.

Example

vTaskPrioritySet(workerHandle, 3);

The priority of the task identified by workerHandle is changed to priority 3, assuming that this value is valid in the application's configuration.

6. Complete Example – Reading and Changing Task Priority

The following program creates two tasks. A manager task reads and changes the priority of a worker task. 

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t workerHandle = NULL;

void WorkerTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform worker operation */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ManagerTask(void *pvParameters)
{
    UBaseType_t currentPriority;

    for (;;)
    {
        /* Read worker priority */
        currentPriority =
            uxTaskPriorityGet(workerHandle);

        /* Change worker priority */
        if (currentPriority == 1)
        {
            vTaskPrioritySet(workerHandle, 2);
        }
        else
        {
            vTaskPrioritySet(workerHandle, 1);
        }

        vTaskDelay(pdMS_TO_TICKS(2000));
    }
}

int main(void)
{
    if (xTaskCreate(
            WorkerTask,
            "Worker",
            256,
            NULL,
            1,
            &workerHandle) == pdPASS)
    {
        if (xTaskCreate(
                ManagerTask,
                "Manager",
                256,
                NULL,
                3,
                NULL) == pdPASS)
        {
            vTaskStartScheduler();
        }
    }

    for (;;)
    {
    }
}

Program Explanation

  1. WorkerTask is created with priority 1.
  2. Its handle is stored in workerHandle.
  3. ManagerTask reads the worker's priority.
  4. If the priority is 1, it changes it to 2.
  5. Otherwise, it changes it back to 1.
  6. The manager repeats this operation every two seconds.
The example demonstrates priority API usage. Actual execution order depends on task states, scheduler configuration and any higher-priority tasks in the application.

7. How Priority Changes Affect Scheduling

When a task's priority is increased, it may become the highest-priority Ready task. Under a preemptive scheduler, the currently running lower-priority task may then be preempted.

Example

TaskInitial PriorityNew Priority
Task A11
Task B23
Task C32

Initially, Task C has the highest priority. After the priority changes, Task B has the highest priority among these tasks.

If Task B is Ready and preemption is enabled, it can preempt a lower-priority running task. If Task B is Blocked, the scheduler chooses from the remaining Ready tasks.

8. Priority Assignment Strategy

Priority assignment should reflect the timing requirements and response-time needs of each task. It should not be based only on how important a task appears to the application.

Task TypeExample Priority Strategy
Time-critical controlHigher priority when response requirements justify it.
Communication processingPriority based on data-rate and latency requirements.
Sensor monitoringPriority based on sampling period and deadline.
Display updatesOften lower priority if timing is less critical.
Background loggingUsually low priority if it can tolerate delays.
There is no universal priority assignment for these task types. Use timing analysis, execution time, blocking and deadline requirements to derive an appropriate priority scheme.

9. Priority Inversion

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task that holds a resource required by the high-priority task.

Example Scenario

  1. Low-priority Task L obtains a mutex.
  2. High-priority Task H becomes Ready and needs that mutex.
  3. Task H blocks while waiting for the mutex.
  4. Medium-priority Task M becomes Ready and preempts Task L.
  5. Task L cannot run to release the mutex, so Task H remains blocked.

FreeRTOS mutexes provide priority inheritance to help reduce this form of priority inversion. However, priority inheritance does not eliminate all blocking or guarantee deadlines.

10. Priority Starvation

Starvation can occur when a low-priority task does not receive sufficient processor time because higher-priority tasks remain Ready continuously.

Example

HighPriorityTask:
    for (;;)
    {
        /* Never blocks or yields */
    }

LowPriorityTask:
    for (;;)
    {
        /* May receive no CPU time */
    }

In a preemptive fixed-priority scheduler, a continuously Ready high-priority task can prevent lower-priority tasks from running.

Prevention Techniques

  • Ensure high-priority tasks block or wait when idle.
  • Use suitable task periods and execution budgets.
  • Review priorities through schedulability analysis.
  • Keep processing bounded.
  • Use time slicing where appropriate for equal-priority tasks.

11. Important API and Configuration Considerations

  • Include the FreeRTOS task header, task.h.
  • Use TaskHandle_t to identify tasks.
  • Use UBaseType_t for priority values.
  • Check configMAX_PRIORITIES before assigning a priority.
  • Use NULL to refer to the calling task where the API permits it.
  • Priority changes do not change the task's code or stack.
  • Priority changes do not automatically implement EDF scheduling.
  • Priority changes do not remove the need for mutexes or synchronization.
Standard FreeRTOS scheduling is fixed-priority. Changing a task's priority with vTaskPrioritySet() does not turn the scheduler into an Earliest Deadline First scheduler.

12. Practical Activity – Dynamic Priority Modification

Objective: Create two tasks and dynamically change the priority of one task using vTaskPrioritySet().

Procedure

  1. Create WorkerTask with priority 1.
  2. Store its handle during task creation.
  3. Create ManagerTask with a higher priority.
  4. Read the worker priority using uxTaskPriorityGet().
  5. Change the worker priority between 1 and 2.
  6. Observe the task states and scheduling behavior using debugger or trace facilities.
  7. Repeat the experiment with preemption enabled and disabled, where supported.

Expected Result

The worker task's priority changes according to the manager task's instructions. Its scheduling position changes accordingly when it is Ready.
