1. Learning Objectives

Tasks are the basic units of execution in a FreeRTOS application. A task represents an independent activity managed by the RTOS scheduler. Understanding task functions, priorities, stacks and execution behavior is essential for designing multitasking embedded applications.

  • Learn the structure of a task function.
  • Understand multitasking and task independence.
  • Identify task priority and stack requirements.
  • Understand task execution and scheduler control.
  • Distinguish a task from a normal C function.
  • Develop a basic multitasking application structure.

2. What Is a FreeRTOS Task?

A task is an independently scheduled unit of execution. Each task has its own execution context and stack. The FreeRTOS scheduler determines which ready task should execute according to the scheduling policy and task priorities.

Examples of Tasks in an Embedded System

  • Sensor monitoring task.
  • UART communication task.
  • Motor control task.
  • Display update task.
  • Data logging task.
  • System monitoring task.

Example Application Structure

Embedded Application

        +----------------------+
        |                      |
    Sensor Task           Communication Task
        |                      |
    Read Sensor            Send UART Data

3. Task vs Normal C Function

A normal C function executes when it is called by another function. A FreeRTOS task is managed by the scheduler and has its own task context.

Feature Normal C Function FreeRTOS Task
Execution Runs when called. Runs when selected by the scheduler.
Scheduling No independent RTOS scheduling. Managed by the RTOS scheduler.
Stack Uses the calling execution context's stack. Has its own task stack.
Priority No independent RTOS task priority. Assigned a task priority.
Blocking Can block the caller if it waits. Can enter a blocked state using RTOS APIs.
Lifetime Normally returns to its caller. Usually runs in a loop until deleted or otherwise terminated.

4. Structure of a FreeRTOS Task Function

A FreeRTOS task function uses a specific function signature. It receives one parameter of type void * and returns no value.

General Syntax

void TaskFunction(void *pvParameters)
{
    for (;;)
    {
        /* Task operation */
    }
}

Explanation

Element Description
void The task function does not return a value.
TaskFunction Name of the task function.
void *pvParameters Optional parameter passed to the task when it is created.
for (;;) Common infinite-loop structure used for a continuously running task.
A task function should not simply return as though it were an ordinary function. If a task must finish, it should use the documented task-deletion mechanism or another designed termination approach.

5. Task Execution and Multitasking

FreeRTOS supports multitasking by switching execution between tasks. On a single-core microcontroller, only one task executes at a time, but tasks can appear to run concurrently because the scheduler switches between them.

Example

void TaskA(void *pvParameters)
{
    for (;;)
    {
        /* Perform Task A operation */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        /* Perform Task B operation */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

When Task A delays, it enters the Blocked state for the specified interval. The scheduler can execute another ready task during that time.

Concurrency does not necessarily mean parallel execution. On a single-core processor such as the LPC2129, tasks share the CPU through scheduling and context switching.

6. Task Priority

Every FreeRTOS task has a priority. In the standard fixed-priority scheduler, a higher priority ready task is selected ahead of a lower priority ready task.

Example Priority Assignment

Task Priority Function
Motor Control Task 4 Time-sensitive motor control processing.
Sensor Task 3 Periodic sensor data acquisition.
Communication Task 2 Data communication.
Display Task 1 Display updates.

Priority values are configuration-dependent. The highest usable priority is determined by configMAX_PRIORITIES; the idle task has the lowest priority.

Assigning a task a high priority does not automatically guarantee that its deadlines will be met. Execution time, blocking, interrupt interference and scheduling behavior must also be analyzed.

7. Task Stack

Each FreeRTOS task requires its own stack. The stack supports function calls, local variables, saved registers and other execution information.

Example Task Creation Stack Depth

xTaskCreate(
    SensorTask,
    "Sensor",
    256,
    NULL,
    2,
    NULL
);

In common FreeRTOS APIs, the stack-depth argument is specified in stack words, not bytes.

Stack Memory Calculation

Stack Memory =
    Stack Depth × sizeof(StackType_t)

If stack depth = 256 words
and StackType_t = 4 bytes:

Stack Memory = 256 × 4
             = 1024 bytes

The actual size of StackType_t depends on the processor port.

8. Task Parameters

The pvParameters argument allows application data to be passed to a task at creation time.

Example

void SensorTask(void *pvParameters)
{
    int sensorChannel;

    sensorChannel = *(int *)pvParameters;

    for (;;)
    {
        /* Use sensorChannel */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int channel = 0;

xTaskCreate(
    SensorTask,
    "Sensor",
    256,
    &channel,
    2,
    NULL
);

Important Considerations

  • The task receives a pointer, not an automatic copy of the pointed-to object.
  • The pointed-to data must remain valid for as long as the task uses it.
  • Shared parameters should be protected if multiple tasks can modify them.
  • For multiple task instances, use separate parameter structures when necessary.

9. Task States – Introduction

A FreeRTOS task moves between states according to its execution and interaction with the kernel.

State Description
Running The task is currently executing on the CPU.
Ready The task can execute but is not currently selected.
Blocked The task is waiting for an event or timeout.
Suspended The task has been explicitly suspended and is not eligible to run.
Deleted The task has been removed from the scheduler's active task set.

Detailed state transitions and scheduling behavior are covered in Chapter 04.

10. Basic FreeRTOS Multitasking Example

The following example demonstrates two task functions. One task performs a sensor-processing activity and another performs a communication activity. 

#include "FreeRTOS.h"
#include "task.h"

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Sensor processing */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void CommunicationTask(void *pvParameters)
{
    for (;;)
    {
        /* Communication processing */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    xTaskCreate(
        SensorTask,
        "Sensor",
        256,
        NULL,
        2,
        NULL
    );

    xTaskCreate(
        CommunicationTask,
        "Communication",
        256,
        NULL,
        1,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program Explanation

  1. FreeRTOS headers provide task and scheduler APIs.
  2. SensorTask performs its operation and delays for 500 ms.
  3. CommunicationTask performs its operation and delays for 1000 ms.
  4. Both tasks are created with different priorities.
  5. The scheduler starts task execution.
This is an illustrative kernel example. A real project must check each task-creation return value, provide a compatible processor port, configure the tick source and use appropriate stack sizes. It is not directly executable on the LPC2129 Keil simulator without verified ARM7 FreeRTOS integration.

11. Task Design Best Practices

  • Give each task a clearly defined responsibility.
  • Avoid putting unrelated operations into one task.
  • Choose task priorities according to timing requirements.
  • Estimate stack requirements carefully.
  • Use queues or notifications for task communication where appropriate.
  • Use mutexes to protect shared resources when ownership is required.
  • Avoid long busy-wait loops that prevent other work from executing.
  • Check all task-creation results.
  • Keep task parameters valid throughout their use.
  • Measure timing and stack usage under realistic conditions.

12. Practical Activity – Design a Three-Task Application

Objective: Design a basic multitasking embedded application using three independent tasks.

Application Requirements

Task Responsibility Example Priority
Sensor Task Acquire and process sensor readings. 3
Communication Task Transmit processed sensor data. 2
Display Task Update the application status display. 1

Procedure

  1. Define three task functions.
  2. Assign a clear responsibility to each task.
  3. Choose suitable task priorities.
  4. Estimate a stack size for each task.
  5. Create the tasks before starting the scheduler.
  6. Plan how sensor data will be transferred to the communication task.
  7. Plan how the display task will receive status information.
  8. Review the design for blocking and shared-data issues.

Expected Result

A task architecture showing three independently scheduled activities, their priorities, stack requirements and communication relationships.

14. Lesson Summary

  • A FreeRTOS task is an independently scheduled unit of execution.
  • Each task has its own execution context and stack.
  • Task functions normally use an infinite loop.
  • Task priority influences scheduling decisions.
  • Task parameters pass application data through a pointer.
  • Tasks can block, become ready and execute according to scheduler decisions.
  • Single-core multitasking provides concurrency, not simultaneous execution.
  • Good task design requires suitable priorities, stack sizes and communication methods.
