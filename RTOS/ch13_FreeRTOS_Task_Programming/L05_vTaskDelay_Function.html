vTaskDelay() Function

Relative Task Delays, Tick Conversion and Blocking Behavior

The vTaskDelay() function allows a FreeRTOS task to enter the Blocked state for a specified number of RTOS ticks. It is commonly used to introduce delays between task operations and to reduce unnecessary CPU usage.

2. Introduction to vTaskDelay()

A task does not always need to execute continuously. For example, a monitoring task may need to process data every 500 milliseconds. Instead of continuously checking for the next operation, it can block for a specified duration.

FreeRTOS provides vTaskDelay() for this purpose. 

void vTaskDelay(TickType_t xTicksToDelay);
ParameterDescription
xTicksToDelayNumber of RTOS tick periods for which the calling task should remain in the Blocked state.

The function blocks the calling task. It does not stop the entire scheduler or delay every other task.

3. Understanding the RTOS Tick

The RTOS tick is a periodic timing event used by the FreeRTOS kernel to maintain time-related operations, including task delays and timeouts. The tick frequency is configured using configTICK_RATE_HZ.

Tick Rate Examples

Tick RateNominal Tick Period
100 Hz10 ms
250 Hz4 ms
500 Hz2 ms
1000 Hz1 ms

The nominal tick period is calculated as: 

Tick period = 1 / Tick frequency

For a tick rate of 1000 Hz: 

Tick period = 1 / 1000 seconds
            = 0.001 seconds
            = 1 millisecond
The tick rate is configured for the FreeRTOS application and port. The actual tick interrupt must be correctly configured by the selected hardware port.

4. Converting Milliseconds into RTOS Ticks

vTaskDelay() accepts a delay expressed in RTOS ticks, not directly in milliseconds. FreeRTOS provides pdMS_TO_TICKS() to convert a millisecond value into ticks.

Syntax

vTaskDelay(pdMS_TO_TICKS(500));

This requests a delay corresponding to 500 milliseconds, subject to tick resolution and the conversion behavior of the selected configuration.

Example at 1000 Hz

configTICK_RATE_HZ = 1000

Delay requested = 500 ms

Ticks = 500 * 1000 / 1000

Ticks = 500

Example at 100 Hz

configTICK_RATE_HZ = 100

Delay requested = 500 ms

Ticks = 500 * 100 / 1000

Ticks = 50
If the requested time is shorter than the tick resolution, pdMS_TO_TICKS() may produce zero. A zero-tick delay does not provide a positive time delay. Check the conversion result when very short timing intervals are required.

5. Task State During vTaskDelay()

When a task calls vTaskDelay() with a positive tick count, it enters the Blocked state for the requested interval. During this period, it is not eligible to execute.

Task State Sequence

  1. The task is in the Running state.
  2. The task calls vTaskDelay().
  3. The task enters the Blocked state.
  4. Another Ready task may execute.
  5. When the delay interval expires, the task becomes Ready.
  6. The scheduler selects it when scheduling rules permit.

The task does not necessarily execute immediately when its delay expires. A higher-priority Ready task may continue executing first.

6. Simple vTaskDelay() Example

The following task performs an operation and then blocks for 1000 milliseconds before repeating. 

#include "FreeRTOS.h"
#include "task.h"

void MonitorTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform monitoring operation */

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    xTaskCreate(
        MonitorTask,
        "Monitor",
        256,
        NULL,
        2,
        NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Program Explanation

  • MonitorTask performs its application operation.
  • vTaskDelay() blocks the task for the requested interval.
  • Other Ready tasks can execute during this interval.
  • After the delay expires, MonitorTask becomes Ready again.
  • The loop repeats the operation.

7. Relative Delay Behavior

vTaskDelay() specifies a delay relative to the time at which the API is called. The task's next execution time therefore depends on both the operation's execution time and the requested delay.

Timing Example

Assume a task performs an operation that takes 20 milliseconds and then calls vTaskDelay() for 100 milliseconds.

ActivityApproximate Time
Task starts operation0 ms
Operation completes20 ms
Task blocks for requested delay20–120 ms
Task becomes ReadyApproximately 120 ms

The interval between the beginnings of consecutive operations is approximately 120 milliseconds, not 100 milliseconds.

The actual timing also depends on tick phase, scheduler behavior, higher-priority tasks and interrupt activity.

8. Periodic Task Using vTaskDelay()

A task can use vTaskDelay() to repeat an operation after a relative delay. This is simple and useful for many non-critical periodic activities. 

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read sensor */

        /* Process sensor value */

        /* Relative delay of 500 ms */
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

If sensor processing takes 15 milliseconds, the interval between the start of consecutive readings will be approximately 515 milliseconds, subject to scheduling and tick timing.

9. vTaskDelay() Versus Busy-Wait Delay

A busy-wait delay repeatedly executes instructions while waiting. This consumes CPU time. In contrast, vTaskDelay() blocks the calling task and allows the scheduler to run other eligible tasks.

FeaturevTaskDelay()Busy-Wait Delay

Other tasks can executeYes, according to scheduling rules.Depends on implementation and interrupt behavior.
Kernel schedulingIntegrated with RTOS scheduling.Does not inherently block the task through the kernel.
Timing basisRTOS tick resolution.Instruction or hardware timer based.
Typical useTask-level waiting.Specialized low-level timing where justified.

10. Zero-Tick Delay

When vTaskDelay() receives zero ticks, it does not block the calling task for a positive time interval. Depending on the scheduler configuration and implementation, a zero-tick delay can yield the processor to another task of equal priority. 

vTaskDelay(0);

For an explicit scheduling yield, taskYIELD() is the clearer API.

Do not use vTaskDelay(0) as a substitute for a positive time delay. Use taskYIELD() when the intention is to request a yield.

11. Limitations of vTaskDelay()

  • It provides a relative delay rather than a fixed periodic release schedule.
  • Execution time is added to the interval between repeated operations.
  • Tick resolution limits timing granularity.
  • Task scheduling and higher-priority activity affect actual execution time.
  • It does not guarantee that a task executes immediately after its delay expires.
  • It is not a substitute for a hardware timer when precise peripheral timing is required.

12. vTaskDelay() and vTaskDelayUntil()

Both APIs are used for task timing, but their timing behavior differs.

FeaturevTaskDelay()vTaskDelayUntil()

Typical useSimple relative waiting.Periodic task scheduling.
Execution-time effectAdded to the interval between repeated operation starts.Does not intentionally add execution time to the configured period.
Period controlLess suitable for a fixed period.Designed to help maintain a fixed task period.
Deadline guaranteeNo.No; it is not a deadline guarantee.

13. Practical Activity – Periodic Monitoring Task

Objective: Create a task that performs a monitoring operation every 500 milliseconds using vTaskDelay().

Procedure

  1. Create a task function named MonitoringTask.
  2. Place the monitoring operation inside an infinite loop.
  3. Call vTaskDelay(pdMS_TO_TICKS(500)) after each operation.
  4. Configure the FreeRTOS tick rate.
  5. Run the application on a supported target or simulator.
  6. Observe the task's state transitions using debugger or trace facilities.
  7. Compare the interval between operation starts with the requested delay.

Expected Result

The task performs its monitoring operation and then enters the Blocked state for approximately 500 milliseconds. It becomes Ready after the delay expires and executes when selected by the scheduler.
