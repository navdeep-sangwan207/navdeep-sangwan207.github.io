Task Suspension, Resumption and Task-State Management

FreeRTOS provides task suspension and resumption APIs to control whether a task is eligible for execution. These functions are useful when an application needs to temporarily stop a task and later allow it to execute again.

  • Identify common design risks and safer alternatives.

2. Introduction to Task Suspension

A task may need to stop executing temporarily without being deleted. For example, a communication task may be suspended while a system enters a maintenance mode and resumed when normal operation is restored.

FreeRTOS provides two commonly used task-control functions: 

void vTaskSuspend(TaskHandle_t xTaskToSuspend);

void vTaskResume(TaskHandle_t xTaskToResume);
FunctionPurpose
vTaskSuspend()Places the specified task into the Suspended state.
vTaskResume()Removes the specified task from the Suspended state and makes it Ready.

3. Understanding the Suspended State

A suspended task is not eligible to execute. Unlike a task in the Blocked state, it does not automatically become Ready when a delay or timeout expires.

A suspended task must be explicitly resumed using an appropriate task-control API.

Conceptual State Transition

          vTaskSuspend()
Ready / Running ----------------> Suspended
                                      |
                                      |
                                vTaskResume()
                                      |
                                      v
                                    Ready

When a suspended task becomes Ready, the scheduler selects it according to the normal scheduling rules. It does not necessarily execute immediately.

4. vTaskSuspend() Function

The vTaskSuspend() function suspends a task identified by its handle.

Syntax

void vTaskSuspend(TaskHandle_t xTaskToSuspend);

Parameter

ParameterDescription
xTaskToSuspendHandle of the task to suspend. NULL specifies the calling task itself.

Example

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t sensorHandle = NULL;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform sensor monitoring */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ControlTask(void *pvParameters)
{
    for (;;)
    {
        /* Application control operation */

        vTaskDelay(pdMS_TO_TICKS(2000));

        if (sensorHandle != NULL)
        {
            vTaskSuspend(sensorHandle);
        }
    }
}

int main(void)
{
    if (xTaskCreate(
            SensorTask,
            "Sensor",
            256,
            NULL,
            2,
            &sensorHandle) == pdPASS)
    {
        xTaskCreate(
            ControlTask,
            "Control",
            256,
            NULL,
            3,
            NULL
        );

        vTaskStartScheduler();
    }

    for (;;)
    {
    }
}

Explanation

  1. SensorTask is created and its handle is stored.
  2. ControlTask performs its application operation.
  3. ControlTask calls vTaskSuspend() using sensorHandle.
  4. SensorTask enters the Suspended state.
  5. SensorTask cannot execute again until it is resumed.

5. vTaskResume() Function

The vTaskResume() function removes a task from the Suspended state and makes it Ready.

Syntax

void vTaskResume(TaskHandle_t xTaskToResume);

Parameter

ParameterDescription
xTaskToResumeHandle of the task to resume. It must identify a valid task.

Example

void ResumeSensorTask(void)
{
    if (sensorHandle != NULL)
    {
        vTaskResume(sensorHandle);
    }
}

After resumption, the task becomes Ready. If it has a higher priority than the currently running task, preemption may occur according to the scheduler configuration.

vTaskResume() does not guarantee that the task runs immediately. It makes the task eligible for scheduling.

6. Complete Suspend and Resume Example

The following conceptual application uses a manager task to suspend and resume a monitoring task. 

#include "FreeRTOS.h"
#include "task.h"

TaskHandle_t monitorHandle = NULL;

void MonitorTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform monitoring operation */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void ManagerTask(void *pvParameters)
{
    for (;;)
    {
        /* Allow monitoring for some time */
        vTaskDelay(pdMS_TO_TICKS(5000));

        /* Suspend monitoring */
        vTaskSuspend(monitorHandle);

        /* Perform maintenance interval */
        vTaskDelay(pdMS_TO_TICKS(2000));

        /* Resume monitoring */
        vTaskResume(monitorHandle);
    }
}

int main(void)
{
    if (xTaskCreate(
            MonitorTask,
            "Monitor",
            256,
            NULL,
            2,
            &monitorHandle) == pdPASS)
    {
        if (xTaskCreate(
                ManagerTask,
                "Manager",
                256,
                NULL,
                3,
                NULL) == pdPASS)
        {
            vTaskStartScheduler();
        }
    }

    for (;;)
    {
    }
}

Execution Sequence

  1. Both tasks are created.
  2. MonitorTask periodically performs monitoring.
  3. ManagerTask waits for five seconds.
  4. ManagerTask suspends MonitorTask.
  5. ManagerTask waits for two seconds.
  6. ManagerTask resumes MonitorTask.
  7. The sequence repeats.
This example assumes ManagerTask is the only task that controls monitorHandle. In a production design, coordinate access to task handles and define what should happen if the monitored task is already suspended or deleted.

7. Self-Suspension of a Task

A task can suspend itself by passing NULL to vTaskSuspend(). 

void WorkerTask(void *pvParameters)
{
    for (;;)
    {
        /* Perform an operation */

        /* Suspend the calling task */
        vTaskSuspend(NULL);

        /* Execution continues here after resumption */
    }
}

The task remains suspended until another task resumes it using its valid task handle. After resumption, execution continues after the vTaskSuspend(NULL) call.

8. Resuming a Task from an ISR

An interrupt service routine must use APIs designed for interrupt context. The ordinary vTaskResume() function must not be called from an ISR.

FreeRTOS provides xTaskResumeFromISR() for this purpose in supported ports. 

BaseType_t xTaskResumeFromISR(
    TaskHandle_t xTaskToResume
);

The return value indicates whether resuming the task caused a context switch to be required at the end of the ISR.

Conceptual ISR Example

void Peripheral_IRQHandler(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the peripheral interrupt */

    xTaskResumeFromISR(monitorHandle);

    /*
       Use the port's documented ISR-yield
       mechanism where required.
    */
}
The exact ISR-yield macro and interrupt-priority rules depend on the FreeRTOS port. The example shows the API concept, not a complete hardware interrupt implementation.

9. Important Limitation: Resume Is Not an Event Queue

vTaskResume() does not store a pending resume request for a task that is not currently suspended. If a resume call occurs before the task has actually suspended, the call does not act as a future wake-up signal.

This creates a possible race condition:

  1. A manager intends to suspend a worker.
  2. The worker has not yet reached its suspension point.
  3. The manager calls vTaskResume().
  4. The worker later suspends itself.
  5. No pending resume request is retained by the ordinary resume API.
When the application needs a persistent event or wake-up signal, consider a task notification, semaphore or queue instead of relying on vTaskSuspend() and vTaskResume().

11. vTaskResume() Versus Task Notifications

Task notifications provide a more event-oriented way to wake a task. They can also carry a value or bit information depending on the notification API used.

FeaturevTaskResume()Task Notification
Primary purposeResume a suspended task.Signal or communicate with a task.
Pending signalDoes not retain a resume request when the task is not suspended.Notification state/value can remain pending until received.
Data transferNo notification value is transferred.Can convey a value or event bits using suitable APIs.
ISR supportxTaskResumeFromISR() where supported.ISR-safe notification APIs are available.
Typical useExplicit administrative control.Event signaling and task wake-up.

For event-driven systems, task notifications are often preferable because they avoid the lost wake-up problem associated with ordinary resume calls.

12. Suspending a Task and Resource Management

Suspending a task does not release the resources it owns. A suspended task may still own a mutex, control a peripheral or hold an application buffer.

Potential Problems

  • A suspended task may retain a mutex indefinitely.
  • Other tasks waiting for that mutex may remain blocked.
  • A peripheral may remain in an intermediate state.
  • Shared buffers may remain reserved.
  • Time-sensitive operations may miss their deadlines.
Avoid suspending a task while it owns a mutex or is performing a critical hardware operation. Prefer a cooperative pause protocol in which the task reaches a safe point and releases resources before waiting.

13. Best Practices

  • Use valid task handles and manage their lifetime carefully.
  • Use vTaskSuspend() and vTaskResume() only when explicit task-state control is required.
  • Do not call vTaskResume() from an ISR.
  • Use xTaskResumeFromISR() where supported for ISR-context resumption.
  • Use task notifications or semaphores for event signaling.
  • Do not assume vTaskResume() stores a pending event.
  • Avoid suspending tasks while they own mutexes or shared resources.
  • Define clear rules for which task is allowed to suspend or resume another task.
  • Do not use suspension as a substitute for safe peripheral shutdown.

14. Practical Activity – Suspend and Resume a Task

Objective: Create two tasks. One task performs periodic monitoring, while another task suspends and resumes it.

Procedure

  1. Create MonitorTask and store its handle.
  2. Create ManagerTask.
  3. Allow MonitorTask to execute for a defined interval.
  4. Call vTaskSuspend() from ManagerTask.
  5. Observe that MonitorTask no longer executes.
  6. Call vTaskResume() after the maintenance interval.
  7. Observe that MonitorTask becomes Ready and resumes execution when scheduled.
  8. Repeat the test and inspect task states using available debugging or trace facilities.

Expected Result

MonitorTask executes while active, enters the Suspended state when requested and becomes Ready after vTaskResume() is called. Its execution then continues according to the scheduler's priority and preemption rules.

17. Lesson Summary

  • vTaskSuspend() places a task in the Suspended state.
  • vTaskResume() makes a suspended task Ready.
  • A task can suspend itself using vTaskSuspend(NULL).
  • Another task can resume it using its task handle.

  • xTaskResumeFromISR() is the ISR-context counterpart where supported.
