2. Introduction to Multitasking

Multitasking is the execution management of multiple tasks by an operating system or RTOS. Each task performs a particular operation and the scheduler determines which Ready task receives processor time.

For example, an embedded monitoring system may contain the following tasks:

  • Sensor Task – reads sensor data.
  • Communication Task – sends data through UART.
  • Display Task – updates an LCD or display.
  • Control Task – processes inputs and controls outputs.
  • Logging Task – records system information.
On a single-core processor, multiple tasks normally execute by sharing processor time. This provides concurrency, not simultaneous parallel execution on separate CPU cores.

3. Multitasking Architecture

Each FreeRTOS task has its own execution context, including its stack and saved processor context. Tasks can communicate through kernel objects such as queues, semaphores, mutexes and task notifications.

4. Creating Multiple Tasks

FreeRTOS provides xTaskCreate() to create tasks dynamically. Each task is defined using a task function.

General Syntax

BaseType_t xTaskCreate(
    TaskFunction_t pxTaskCode,
    const char * const pcName,
    configSTACK_DEPTH_TYPE usStackDepth,
    void *pvParameters,
    UBaseType_t uxPriority,
    TaskHandle_t *pxCreatedTask
);

The exact declaration may vary with FreeRTOS kernel version and configuration. The following example illustrates the common task-creation pattern.

Example

#include "FreeRTOS.h"
#include "task.h"

void TaskA(void *pvParameters)
{
    for (;;)
    {
        /* Task A operation */
        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        /* Task B operation */
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    xTaskCreate(
        TaskA, "TaskA", 256,
        NULL, 2, NULL
    );

    xTaskCreate(
        TaskB, "TaskB", 256,
        NULL, 1, NULL
    );

    vTaskStartScheduler();

    for (;;)
    {
    }
}

TaskA has priority 2 and TaskB has priority 1. Both tasks periodically block, allowing the scheduler to execute other Ready tasks.

6. Task Priority and Scheduling

FreeRTOS normally uses fixed-priority scheduling. A Ready task with a higher numerical priority takes precedence over lower-priority Ready tasks.

TaskPriorityFunction
Control Task4Time-sensitive control operation
Sensor Task3Sensor data acquisition
Communication Task2Data transmission
Logging Task1Background logging

The priorities shown are illustrative. Real priorities should be selected after analyzing task periods, execution times, deadlines and blocking behavior.

A high-priority task that remains continuously Ready can starve lower-priority tasks. Tasks should block or wait appropriately when they have no work to perform.

7. Context Switching

Context switching occurs when the processor stops executing one task and begins executing another. The RTOS saves the outgoing task's execution context and restores the incoming task's context.

Typical Reasons for a Context Switch

  • A task blocks while waiting for an event.
  • A task enters a delay period.
  • A higher-priority task becomes Ready.
  • A task yields execution.
  • An interrupt causes a scheduling decision when appropriate.

The exact context-switch mechanism is processor- and port-specific. It normally involves saving and restoring the required registers and stack pointers.

8. Periodic Task Execution

Many embedded tasks execute periodically. For example, a sensor may be sampled every 100 milliseconds.

Using vTaskDelay()

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        /* Read sensor */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

This creates a relative delay after the operation. The operation's execution time is added to the delay when calculating the interval between operation starts.

Using vTaskDelayUntil()

void SensorTask(void *pvParameters)
{
    TickType_t xLastWakeTime =
        xTaskGetTickCount();

    const TickType_t xPeriod =
        pdMS_TO_TICKS(100);

    for (;;)
    {
        /* Read sensor */

        vTaskDelayUntil(
            &xLastWakeTime,
            xPeriod
        );
    }
}

This approach is intended to maintain a more consistent periodic schedule using an absolute wake-time reference.

10. Multitasking Example Using a Queue

This example demonstrates two tasks communicating through a FreeRTOS queue. The Sensor Task sends integer values, and the Display Task receives them. 

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"

QueueHandle_t sensorQueue = NULL;

void SensorTask(void *pvParameters)
{
    int sensorValue = 0;

    for (;;)
    {
        sensorValue++;

        xQueueSend(
            sensorQueue,
            &sensorValue,
            portMAX_DELAY
        );

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void DisplayTask(void *pvParameters)
{
    int receivedValue;

    for (;;)
    {
        if (xQueueReceive(
                sensorQueue,
                &receivedValue,
                portMAX_DELAY) == pdPASS)
        {
            /* Process received sensor value */
        }
    }
}

int main(void)
{
    sensorQueue = xQueueCreate(
        5,
        sizeof(int)
    );

    if (sensorQueue != NULL)
    {
        if (xTaskCreate(
                SensorTask,
                "Sensor",
                256,
                NULL,
                2,
                NULL) == pdPASS)
        {
            if (xTaskCreate(
                    DisplayTask,
                    "Display",
                    256,
                    NULL,
                    2,
                    NULL) == pdPASS)
            {
                vTaskStartScheduler();
            }
        }
    }

    for (;;)
    {
    }
}

Program Explanation

  1. A queue is created with five integer slots.
  2. SensorTask generates an integer value.
  3. xQueueSend() copies the integer into the queue.
  4. SensorTask delays for 500 milliseconds.
  5. DisplayTask waits for an item using xQueueReceive().
  6. When an item arrives, DisplayTask processes it.
  7. If the queue is empty, DisplayTask remains Blocked until data becomes available.
portMAX_DELAY requests an indefinite wait in configurations that support it. Queue operations should be checked for their return values in production applications.

11. Resource Sharing in Multitasking

Multiple tasks may access the same hardware peripheral or shared data. Without synchronization, simultaneous access can cause race conditions.

Examples of Shared Resources

  • UART peripheral used by multiple tasks.
  • Shared sensor-data buffer.
  • SPI or I2C peripheral driver.
  • Shared configuration data.
  • Flash or file-system interface.

A mutex can protect a shared resource when multiple tasks need exclusive access. 

SemaphoreHandle_t uartMutex;

void UartTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                uartMutex,
                portMAX_DELAY) == pdTRUE)
        {
            /* Use shared UART resource */

            xSemaphoreGive(uartMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

The mutex must be created before the task uses it. The task that successfully takes the mutex must release it. Mutexes must not be used from an ISR.

13. Multitasking Design Challenges

ChallengeDescriptionPossible Solution
Race conditionMultiple tasks access shared data without suitable synchronization.Mutexes, queues or carefully designed ownership.
Priority inversionHigh-priority task waits for a resource held by a lower-priority task.Priority inheritance and bounded resource holding.
DeadlockTasks wait indefinitely for resources held by one another.Consistent lock ordering and controlled resource ownership.
StarvationLow-priority task receives insufficient CPU time.Review priorities and ensure higher-priority tasks block appropriately.
Stack overflowTask uses more stack than allocated.Measure stack usage and configure sufficient stack depth.
Queue overflowProducer sends faster than consumer processes.Size queues and define overflow handling.
Timing jitterTask release or execution timing varies.Analyze interference and use appropriate timing mechanisms.

14. Multitasking Best Practices

  • Give each task a clear and limited responsibility.
  • Assign priorities according to timing requirements.
  • Keep task execution bounded and predictable.
  • Use queues for structured data transfer.
  • Use mutexes for shared-resource protection.
  • Use task notifications for suitable one-to-one event signaling.
  • Avoid long-running operations in high-priority tasks.
  • Check return values from task and queue creation APIs.
  • Monitor task stack usage and heap capacity.
  • Define behavior for queue-full and timeout conditions.
  • Keep interrupt service routines short and defer lengthy processing to tasks.
  • Test worst-case timing and resource contention.

15. Practical Activity – Three-Task Monitoring System

Objective: Design a multitasking application containing sensor acquisition, data processing and logging tasks.

Procedure

  1. Create a queue for raw sensor values.
  2. Create a second queue for processed values.
  3. Create SensorTask to generate or acquire sensor readings.
  4. Create ProcessingTask to receive and process the readings.
  5. Create LoggingTask to receive processed values.
  6. Assign priorities based on the system's timing requirements.
  7. Use appropriate blocking times in queue operations.
  8. Start the scheduler.
  9. Inspect task states and queue behavior using debugger or trace facilities.

Expected Result

The three tasks operate independently and exchange data through queues. When a queue is empty, its consumer can block until data arrives. The scheduler selects Ready tasks according to configured priorities and scheduling behavior.

16. Important Notes for Keil uVision Simulator

The examples in this lesson use generic FreeRTOS APIs. They require a compatible processor port, compiler integration and startup configuration.

  • The LPC2129 uses an ARM7TDMI-S processor.
  • Do not use a Cortex-M FreeRTOS port for LPC2129.
  • Verify availability of a compatible ARM7 port and Keil compiler integration.
  • Verify that the simulator supports the required port and interrupt behavior.
  • Queue and scheduler logic should be tested in a verified environment before assuming hardware behavior.
  • Peripheral output, such as actual UART transmission or sensor acquisition, requires appropriate hardware or a suitable peripheral simulation.
If the LPC2129 simulator setup cannot run a compatible FreeRTOS port, study the task logic and API design using code inspection or a supported host/target environment. Do not treat an ordinary Keil C program as proof of RTOS multitasking execution.
