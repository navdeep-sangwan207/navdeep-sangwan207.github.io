1. Learning Objectives

Tasks in an RTOS frequently share resources. Incorrect resource allocation and synchronization can cause deadlock or starvation, preventing tasks from making the progress required by the application.

After completing this lesson, you will be able to:

  • Define deadlock and starvation.
  • Explain the four necessary conditions for deadlock.
  • Understand resource allocation and circular wait.
  • Differentiate deadlock prevention, avoidance, and detection.
  • Explain how starvation occurs in priority-based scheduling.
  • Apply resource locking strategies in FreeRTOS.
  • Identify techniques to prevent deadlock and starvation in embedded systems.

2. What Is Deadlock?

Deadlock is a condition in which two or more tasks become permanently blocked because each task is waiting for a resource or event that can only be provided by another blocked task.

A deadlocked task cannot make progress through normal execution. The system may continue running other tasks, but the tasks involved in the deadlock remain blocked.

Example:
  • Task A owns Mutex 1 and requests Mutex 2.
  • Task B owns Mutex 2 and requests Mutex 1.
  • Task A waits for Task B to release Mutex 2.
  • Task B waits for Task A to release Mutex 1.
Neither task can continue. This is deadlock.

Deadlock in Embedded Systems

Deadlock can occur when tasks share resources such as:

  • UART and SPI communication interfaces.
  • I2C peripheral drivers.
  • Shared memory buffers.
  • File-system or storage access.
  • Application data structures protected by mutexes.

3. Four Necessary Conditions for Deadlock

The classical Coffman conditions identify four conditions that must hold simultaneously for a deadlock to occur in the modeled resource allocation system.

1. Mutual Exclusion

At least one resource is non-shareable and can be held by only one task at a time.

Example: A mutex allows only one task to own it at a time.

2. Hold and Wait

A task holds one resource while waiting to acquire another resource.

Example: Task A owns Mutex 1 and waits for Mutex 2.

3. No Preemption

A resource cannot be forcibly taken away from its owner; it must be released voluntarily according to the resource's ownership rules.

Example: Another task cannot simply take a mutex away from its owner.

4. Circular Wait

A circular chain of tasks exists in which each task waits for a resource held by the next task in the chain.

Example: Task A waits for B, while Task B waits for A.

Condition Meaning Example
Mutual exclusion Exclusive resource ownership Mutex
Hold and wait Holding one resource while requesting another A owns M1 and requests M2
No preemption Resource cannot be forcibly taken Mutex owner must release it
Circular wait Tasks form a circular waiting chain A waits for B; B waits for A
All four conditions are necessary for deadlock in this classical model. Preventing at least one condition can prevent that form of deadlock.

4. Deadlock Example Using Two Mutexes

Consider two tasks and two mutexes:

Task First Mutex Second Mutex
Task A Mutex 1 Mutex 2
Task B Mutex 2 Mutex 1

Execution Sequence

  1. Task A successfully takes Mutex 1.
  2. Task B successfully takes Mutex 2.
  3. Task A requests Mutex 2 and blocks.
  4. Task B requests Mutex 1 and blocks.
  5. Neither task can release its currently owned mutex.

Resource Allocation View

Task A ---- owns ----> Mutex 1
Task A <--- waits ---- Mutex 2

Task B ---- owns ----> Mutex 2
Task B <--- waits ---- Mutex 1

Circular dependency:

Task A -> Mutex 2 -> Task B
Task B -> Mutex 1 -> Task A

Result: DEADLOCK
Priority inheritance does not solve this deadlock. Raising the priority of a blocked mutex owner cannot make the owner release a mutex while it is itself blocked waiting for another mutex.

5. Deadlock Prevention

Deadlock prevention designs the application so that at least one of the four necessary deadlock conditions cannot occur.

Method 1: Eliminate Hold and Wait

A task can acquire all required resources before beginning an operation, rather than holding one resource while waiting for another.

This method may reduce resource utilization and can be difficult when resources are needed at different stages.

Method 2: Use a Global Resource Order

Assign a fixed order to mutexes and require every task to acquire them in that order.

Example resource order:
  1. Mutex 1
  2. Mutex 2
  3. Mutex 3
Every task must acquire Mutex 1 before Mutex 2 and Mutex 2 before Mutex 3 whenever it needs multiple mutexes.

Method 3: Avoid Circular Wait

A consistent locking order prevents circular resource dependencies when all tasks follow the same rule.

Method 4: Use a Dedicated Resource Owner

A dedicated task can exclusively manage a peripheral such as UART or SPI. Other tasks send requests through a queue instead of locking multiple resources directly.

Method 5: Limit Resource Ownership Duration

Keep resource ownership short and release a mutex immediately after the protected operation is complete.

6. Deadlock Avoidance

Deadlock avoidance evaluates resource requests before granting them. A request is granted only if the resulting allocation leaves the system in a safe state according to the chosen resource model.

Safe State

A system is in a safe state if there is at least one sequence in which all tasks can obtain their remaining required resources, finish execution, and release their resources.

Unsafe State

An unsafe state means that no guaranteed safe completion sequence can be established from the current allocation and declared maximum resource requirements. It does not necessarily mean that deadlock has already occurred.

Banker's Algorithm

Banker's Algorithm is a classical deadlock-avoidance algorithm. It uses information about available resources, current allocations, and each process's maximum resource requirements to determine whether a request can be granted safely.

Term Meaning
Available Resources currently free.
Allocation Resources currently assigned to each process.
Maximum Maximum resources each process may require.
Need Maximum minus current allocation. 
Need = Maximum - Allocation
Banker's Algorithm is mainly a theoretical resource-allocation technique. Ordinary FreeRTOS mutex operations do not automatically perform Banker's Algorithm checks.

7. Deadlock Detection and Recovery

In a system that does not prevent or avoid all deadlocks, detection methods can identify circular waiting or resource-allocation inconsistencies.

Detection Techniques

  • Resource allocation graph analysis.
  • Monitoring task states and mutex ownership.
  • Tracking resource acquisition and release.
  • Using diagnostic timeouts to identify unusually long waits.
  • Recording task execution traces.

Recovery Techniques

  • Abort or restart an affected task when safe.
  • Reset a subsystem into a known state.
  • Use a watchdog to recover from system-level failure.
  • Release resources through a controlled recovery mechanism.
A timeout is a detection or fault-handling mechanism, not automatic deadlock prevention. Do not forcibly delete a task that owns a mutex without a carefully designed resource-recovery strategy.

8. What Is Starvation?

Starvation occurs when a task waits indefinitely or for an unacceptably long time because other tasks repeatedly receive the CPU or required resources before it.

Unlike deadlock, a system affected by starvation may continue to make progress. Some tasks execute normally while another task receives insufficient service.

Example of Priority-Based Starvation

Consider three tasks:

Task Priority Behavior
Task H 3 – High Frequently becomes ready.
Task M 2 – Medium Occasionally becomes ready.
Task L 1 – Low Needs CPU time to perform background work.

If Task H is continuously ready, a fixed-priority preemptive scheduler may never allow Task L to execute. Task L experiences CPU starvation.

A continuously ready higher-priority task can starve lower-priority tasks under fixed-priority scheduling. This is not necessarily a scheduler malfunction; it may be a task-design or resource-budgeting problem.

9. Causes of Starvation

1. Unfair CPU Scheduling

A task may repeatedly lose CPU access to other tasks with higher priorities.

2. Resource Contention

A task may repeatedly fail to obtain a shared resource because other tasks acquire it first.

3. Incorrect Priority Assignment

A low-priority task may not receive sufficient CPU time to complete essential background operations.

4. Unfair Resource Access

An application-level resource manager may repeatedly serve certain tasks while delaying others.

5. Excessive High-Priority Activity

High-priority tasks that execute too frequently or for too long can prevent lower-priority tasks from making progress.

10. Techniques to Prevent Starvation

1. Priority Assignment

Assign priorities according to real-time importance and timing requirements. Avoid giving unnecessarily high priorities to background tasks.

2. Periodic Blocking or Delays

Periodic tasks should block or wait when they have no work to do, rather than continuously consuming CPU time.

3. Time Slicing

Equal-priority ready tasks can share processor time when the RTOS supports time slicing. This does not automatically guarantee fairness between tasks of different priorities.

4. Resource Access Policy

Use suitable queues, mutexes, and resource-management policies. Do not allow one task to monopolize a shared resource.

5. Bounded Execution

Limit the execution time of high-priority tasks and ensure that periodic workloads are schedulable.

6. Aging

In some scheduling systems, aging gradually increases the effective priority of a task that has waited for a long time. This technique is not a standard automatic feature of the FreeRTOS fixed-priority scheduler; it requires application or scheduler-level implementation.

11. Deadlock vs Starvation

Feature Deadlock Starvation
Definition Tasks wait indefinitely due to circular or dependent resource waiting. A task is repeatedly denied CPU time or a required resource.
System progress Deadlocked tasks cannot make progress. Other tasks may continue making progress.
Typical cause Circular wait and resource ownership. Unfair scheduling or resource allocation.
Priority inheritance Does not generally solve deadlock. May help some resource-related priority inversion cases, but is not a general starvation solution.
Prevention Lock ordering, resource protocols, and deadlock prevention. Suitable scheduling and fair resource allocation.
Example Task A waits for B while B waits for A. Low-priority task never receives CPU time.

12. FreeRTOS Deadlock Example

The following example illustrates how two tasks can deadlock when they acquire two mutexes in opposite orders.

This is intentionally incorrect demonstration code. Do not use this locking pattern in an application. 
#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xMutex1;
SemaphoreHandle_t xMutex2;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        xSemaphoreTake(xMutex1, portMAX_DELAY);

        /* Simulate work while holding Mutex 1. */
        vTaskDelay(pdMS_TO_TICKS(20));

        /* May block forever if Task B owns Mutex 2. */
        xSemaphoreTake(xMutex2, portMAX_DELAY);

        /* Protected operations. */

        xSemaphoreGive(xMutex2);
        xSemaphoreGive(xMutex1);

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        xSemaphoreTake(xMutex2, portMAX_DELAY);

        /* Simulate work while holding Mutex 2. */
        vTaskDelay(pdMS_TO_TICKS(20));

        /* May block forever if Task A owns Mutex 1. */
        xSemaphoreTake(xMutex1, portMAX_DELAY);

        /* Protected operations. */

        xSemaphoreGive(xMutex1);
        xSemaphoreGive(xMutex2);

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

int main(void)
{
    xMutex1 = xSemaphoreCreateMutex();
    xMutex2 = xSemaphoreCreateMutex();

    if ((xMutex1 != NULL) && (xMutex2 != NULL))
    {
        xTaskCreate(TaskA, "TaskA", 256, NULL, 2, NULL);
        xTaskCreate(TaskB, "TaskB", 256, NULL, 2, NULL);

        vTaskStartScheduler();
    }

    for (;;);
}

Why Can This Program Deadlock?

  1. Task A can acquire Mutex 1.
  2. Task B can acquire Mutex 2.
  3. Task A then waits for Mutex 2.
  4. Task B then waits for Mutex 1.
  5. Both tasks remain blocked.
The delays make the race possible but do not guarantee that deadlock will occur on every execution. A controlled test harness is needed to force and observe the exact interleaving.

13. Corrected Program Using Consistent Lock Ordering

Both tasks should acquire Mutex 1 before Mutex 2. This removes the circular lock-order dependency in this example. 

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xMutex1;
SemaphoreHandle_t xMutex2;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(xMutex1,
                           pdMS_TO_TICKS(100)) == pdTRUE)
        {
            if (xSemaphoreTake(xMutex2,
                               pdMS_TO_TICKS(100)) == pdTRUE)
            {
                /* Access resources in the defined order. */

                xSemaphoreGive(xMutex2);
            }

            xSemaphoreGive(xMutex1);
        }

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(xMutex1,
                           pdMS_TO_TICKS(100)) == pdTRUE)
        {
            if (xSemaphoreTake(xMutex2,
                               pdMS_TO_TICKS(100)) == pdTRUE)
            {
                /* Access resources in the same defined order. */

                xSemaphoreGive(xMutex2);
            }

            xSemaphoreGive(xMutex1);
        }

        vTaskDelay(pdMS_TO_TICKS(50));
    }
}

int main(void)
{
    xMutex1 = xSemaphoreCreateMutex();
    xMutex2 = xSemaphoreCreateMutex();

    if ((xMutex1 != NULL) && (xMutex2 != NULL))
    {
        xTaskCreate(TaskA, "TaskA", 256, NULL, 2, NULL);
        xTaskCreate(TaskB, "TaskB", 256, NULL, 2, NULL);

        vTaskStartScheduler();
    }

    for (;;);
}

Because both tasks acquire resources in the same global order, the circular-wait pattern in the previous example is eliminated. The finite timeouts also allow the tasks to recover from failed acquisition attempts rather than waiting indefinitely.

A timeout alone does not prove deadlock cannot occur. The consistent lock order is the key prevention measure in this example. Production code must also handle every failed acquisition, release only mutexes actually acquired, and account for the time spent waiting.

14. FreeRTOS Starvation Example

In a fixed-priority preemptive scheduler, a continuously ready high-priority task can prevent a lower-priority task from executing. 

#include "FreeRTOS.h"
#include "task.h"

volatile unsigned long ulHighCount = 0;
volatile unsigned long ulLowCount = 0;

void HighPriorityTask(void *pvParameters)
{
    for (;;)
    {
        ulHighCount++;

        /*
         * This task never blocks.
         * It may starve lower-priority tasks.
         */
    }
}

void LowPriorityTask(void *pvParameters)
{
    for (;;)
    {
        ulLowCount++;

        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

int main(void)
{
    xTaskCreate(HighPriorityTask,
                "High",
                256,
                NULL,
                3,
                NULL);

    xTaskCreate(LowPriorityTask,
                "Low",
                256,
                NULL,
                1,
                NULL);

    vTaskStartScheduler();

    for (;;);
}

Expected Behavior

  • The high-priority task remains continuously ready.
  • The low-priority task may not receive CPU time after the high-priority task starts running.
  • The low-priority counter may remain unchanged.

Improved Design

If the high-priority task does not have continuous work, it should block while waiting for an event or use an appropriate periodic delay. A queue, task notification, or semaphore can be used to wake it when work arrives.

Do not add an arbitrary delay to a task that must meet a hard real-time response requirement. Choose blocking and periodic behavior according to the application's timing analysis.

15. Embedded System Design Guidelines

  • Define a global order for acquiring multiple mutexes.
  • Avoid holding one mutex while waiting indefinitely for another.
  • Keep resource ownership intervals short and bounded.
  • Use mutexes for task-level resource protection, not from ISRs.
  • Use queues or a dedicated owner task for complex peripheral access.
  • Use finite waits where recovery is meaningful and implement timeout handling.
  • Review task priorities to identify potential starvation.
  • Ensure high-priority tasks block when they have no work to perform.
  • Monitor task states, stack usage, and resource ownership during debugging.
  • Use watchdog recovery only as part of a defined fault-management strategy.

  2. Identify which task owns each mutex.

Activity B: Starvation Analysis

Objective: Observe the effect of a continuously ready high-priority task.

  1. Create one high-priority and one low-priority task.
  2. Run the high-priority task without a blocking operation.
  3. Observe the low-priority task's execution counter.
  4. Modify the high-priority task to block while waiting for work.
  5. Compare the low-priority task's progress.

Expected Result:

  • The first activity demonstrates circular waiting and its elimination through lock ordering.
  • The second activity demonstrates how continuous high-priority execution can starve lower-priority tasks.

18. Lesson Summary

  • Deadlock occurs when tasks wait indefinitely for resources held by one another.
  • The four necessary conditions are mutual exclusion, hold and wait, no preemption, and circular wait.
  • Consistent resource ordering is a practical way to prevent circular wait.
  • Deadlock avoidance checks whether resource allocation preserves a safe state.
  • Banker's Algorithm is a classical deadlock-avoidance method.
  • Starvation occurs when a task is repeatedly denied CPU time or resource access.
  • Fixed-priority scheduling can starve low-priority tasks if higher-priority tasks remain continuously ready.
  • Priority inheritance does not eliminate deadlock.
  • Proper mutex design, bounded execution, and task-priority analysis improve RTOS reliability.
