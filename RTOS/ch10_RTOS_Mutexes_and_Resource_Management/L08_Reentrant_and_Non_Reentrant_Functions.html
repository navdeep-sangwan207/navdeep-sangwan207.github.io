Reentrant and Non-Reentrant Functions

1. Learning Objectives

In a multitasking embedded system, multiple tasks may call the same function. If a function modifies shared data without proper synchronization, its execution can interfere with another call. Reentrancy is therefore an important property in RTOS programming.

After completing this lesson, you will be able to:

  • Define reentrant and non-reentrant functions.
  • Understand local, global, and static variables.
  • Identify shared-state problems in multitasking applications.
  • Explain the relationship between reentrancy and thread safety.
  • Protect shared data using mutexes and other synchronization methods.
  • Understand reentrancy requirements for interrupt service routines.
  • Design safer functions for FreeRTOS applications.

2. What Is a Reentrant Function?

A reentrant function is a function that can be entered again before an earlier invocation has completed without causing incorrect behavior due to shared mutable internal state.

Multiple tasks or execution contexts can call a properly designed reentrant function, and each invocation can operate independently.

Characteristics

  • Uses local automatic variables for temporary data.
  • Does not rely on unprotected shared mutable state.
  • Does not modify shared global or static variables without synchronization.
  • Uses safe interfaces and operations for concurrent execution.
  • Does not depend on hidden shared state that can be corrupted by another invocation.
Example: 
int Add(int a, int b)
{
    int result;

    result = a + b;

    return result;
}
Each call has its own parameters and automatic local variable result. This function has no shared mutable state and is reentrant under ordinary execution assumptions.

3. What Is a Non-Reentrant Function?

A non-reentrant function is a function whose concurrent or nested execution can interfere with another invocation, typically because it accesses shared mutable state without adequate protection.

Characteristics

  • Uses shared global variables without synchronization.
  • Modifies static local variables that are shared across calls.
  • Uses shared buffers without ownership or locking.
  • Calls other functions that are themselves unsafe for concurrent use.
  • Depends on shared library or peripheral state without coordination.
Example: 
int Calculate(int value)
{
    static int result = 0;

    result = result + value;

    return result;
}
The static variable result persists between calls. Multiple tasks calling this function can interfere with one another unless access is synchronized.
A static variable does not automatically make a function unsafe in every possible application. The problem is concurrent access to shared mutable state without a suitable synchronization or ownership strategy.

4. Local, Global, and Static Variables

Variable Type Storage / Scope Concurrency Consideration
Automatic local variable Created for an invocation; normally stored in that invocation's stack frame or registers. Independent between task calls when not exposed through shared pointers or references.
Global variable Static storage duration; accessible according to its linkage and scope. Shared access requires synchronization or another safe ownership design.
Static local variable Static storage duration; visible only within its function. All calls to the function use the same object.
Read-only constant data Depends on declaration and implementation. Concurrent reading is normally safe if the object is not modified.

Example: Automatic Local Variable

int Square(int number)
{
    int result = number * number;

    return result;
}

Example: Global Variable

int sharedCounter = 0;

void IncrementCounter(void)
{
    sharedCounter++;
}

Example: Static Local Variable

int GetNextValue(void)
{
    static int count = 0;

    count++;

    return count;
}

In the second and third examples, multiple tasks can access the same object. The read-modify-write operations must be coordinated when concurrent access is possible.

5. Race Condition in a Non-Reentrant Function

A race condition occurs when the result of an operation depends on the timing or interleaving of concurrent accesses to shared state.

Example: Shared Counter

volatile int counter = 0;

void Increment(void)
{
    counter++;
}

The increment operation is generally a read-modify-write sequence, not necessarily one indivisible operation.

Possible Execution Sequence

Step Task A Task B Counter
1 Reads counter = 0 — 0
2 — Reads counter = 0 0
3 Calculates 1 — 0
4 — Calculates 1 0
5 Writes 1 — 1
6 — Writes 1 1

Two increments were requested, but the final counter value is 1 instead of 2. This is a lost-update race condition.

Declaring a variable volatile does not make an operation atomic and does not provide mutual exclusion or general inter-task synchronization.

6. Reentrant Function vs Thread-Safe Function

Reentrancy and thread safety are related but different concepts.

Feature Reentrant Function Thread-Safe Function
Meaning Can be entered again during an earlier invocation without unsafe interference. Can be used concurrently without causing incorrect behavior.
Shared mutable state Must be avoided or handled safely within the reentrant design. May be used if access is properly synchronized.
Mutex usage A function relying on a blocking mutex is generally not reentrant in the strict sense. A mutex can make a shared-state operation thread-safe.
Concurrency Supports safe overlapping or nested invocations. Supports safe concurrent use, possibly by serializing access.
A function protected by a mutex may be thread-safe while not being reentrant. The mutex serializes access, whereas reentrancy requires safe behavior when another invocation enters before the first one has completed.

7. Reentrant Function Using Function Parameters

One way to design reentrant functions is to pass the required data through function parameters and use local automatic variables. 

int CalculateSum(const int *data, int length)
{
    int sum = 0;

    for (int i = 0; i < length; i++)
    {
        sum += data[i];
    }

    return sum;
}

Explanation

  • The input array is supplied by the caller.
  • The accumulator sum is local to each invocation.
  • The function does not modify shared global state.
  • Multiple tasks can call it safely if the input memory remains valid and is not concurrently modified in an unsafe way.
Reentrancy of the function does not automatically make the memory passed to it safe. The caller must ensure that shared input buffers have a valid lifetime and suitable access protection.

8. Making a Shared-State Function Thread-Safe with a Mutex

If multiple tasks must update a shared variable, a mutex can protect the critical section. 

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xCounterMutex;

int sharedCounter = 0;

void IncrementCounter(void)
{
    if (xSemaphoreTake(xCounterMutex,
                       portMAX_DELAY) == pdTRUE)
    {
        sharedCounter++;

        xSemaphoreGive(xCounterMutex);
    }
}

Explanation

  1. A mutex is created before tasks use the function.
  2. A task takes the mutex before accessing the shared counter.
  3. The increment operation executes while the task owns the mutex.
  4. The task releases the mutex after the update.
  5. Another task can then access the counter.
This makes the shared update mutually exclusive when every access follows the same locking rule. The function itself is not strictly reentrant because it relies on a shared mutex and shared state. It must also be called from task context, not an ISR.

9. Reentrancy and Interrupt Service Routines

An interrupt service routine can interrupt a task at almost any instruction boundary allowed by the processor and interrupt configuration. If the ISR calls a function that the interrupted task was already using, unsafe shared state can be corrupted.

Example of an Unsafe Shared Function

int sharedValue = 0;

void UpdateValue(int value)
{
    sharedValue = value;
}

/* Task calls UpdateValue(). */
/* An ISR also calls UpdateValue(). */

If the ISR and task both access related shared data, the application must define safe ownership and synchronization rules. A simple assignment may be indivisible on a particular processor, but that does not make a larger shared-data operation safe.

ISR Design Guidelines

  • Keep interrupt service routines short.
  • Avoid functions that use shared mutable state without protection.
  • Do not call blocking functions from an ISR.
  • Do not take or give a mutex from an ISR.
  • Use suitable FreeRTOS FromISR APIs where supported by the port.
  • Defer complex processing to a task.
  • Use appropriate atomic or critical-section techniques for shared state.
A mutex is not an ISR synchronization mechanism. A task can own a mutex while an ISR occurs, and an ISR must not attempt to block waiting for that mutex.

10. Reentrancy and Standard Library Functions

Not every library function is suitable for concurrent or interrupt use. Some functions maintain internal state, use shared buffers, or rely on non-reentrant library implementations.

Function / Facility Consideration
strtok() Uses internal parsing state in common C library implementations; concurrent use can interfere.
strtok_r() Uses caller-provided state and is designed for reentrant parsing where available.
sprintf() Uses a caller-provided output buffer, but library implementation and shared input/output objects still matter.
printf() May use shared stream state and locks; generally unsuitable for ISR use.
malloc() / free() Allocator implementations may use shared internal state and synchronization; not automatically ISR-safe.
Thread safety and ISR safety depend on the C library, compiler, operating environment, and port. Never assume that a library function is safe in every execution context merely because it is available in the build environment.

11. Reentrant and Non-Reentrant Function Comparison

Feature Reentrant Function Non-Reentrant Function
Shared mutable state Avoided or safely handled. May be accessed without sufficient protection.
Local variables Usually uses independent automatic local data. May rely on shared static or global data.
Concurrent calls Can safely overlap under its documented assumptions. May interfere with each other.
Nested calls Safe if the function and its dependencies support reentrancy. May corrupt shared state.
Typical use Reusable algorithms and independent data processing. Functions requiring shared state or serialized access.

12. Practical FreeRTOS Example

The following program demonstrates a reentrant calculation function called by two independent tasks. Each task has its own input data and the calculation uses only local state. 

#include "FreeRTOS.h"
#include "task.h"

int CalculateSum(const int *data, int length)
{
    int sum = 0;

    for (int i = 0; i < length; i++)
    {
        sum += data[i];
    }

    return sum;
}

void TaskA(void *pvParameters)
{
    int valuesA[] = {10, 20, 30, 40};
    int resultA;

    for (;;)
    {
        resultA = CalculateSum(valuesA, 4);

        /* Inspect resultA using debugger or application output. */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    int valuesB[] = {1, 2, 3, 4, 5};
    int resultB;

    for (;;)
    {
        resultB = CalculateSum(valuesB, 5);

        /* Inspect resultB using debugger or application output. */

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

int main(void)
{
    xTaskCreate(TaskA, "TaskA", 256, NULL, 2, NULL);
    xTaskCreate(TaskB, "TaskB", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    for (;;);
}

Expected Results

Task Input Values Expected Sum
Task A 10, 20, 30, 40 100
Task B 1, 2, 3, 4, 5 15

Each task has its own input array and result variable. The function does not use a shared mutable accumulator, so the calculation can safely be invoked by both tasks, provided the input arrays remain unchanged during each call.

13. Best Practices for Reentrant Programming

  • Prefer automatic local variables for temporary calculations.
  • Pass input and output data through function parameters.
  • Avoid unnecessary global and static mutable variables.
  • Use mutexes for shared task-level resources when appropriate.
  • Define buffer ownership and lifetime rules.
  • Use queues or task notifications to transfer data between tasks.
  • Check whether library functions are thread-safe and ISR-safe.
  • Avoid blocking synchronization inside interrupt service routines.
  • Document any shared state and its protection mechanism.
  • Test functions under concurrent task execution.

16. Lesson Summary

  • A reentrant function can safely be entered again before an earlier invocation completes.
  • Reentrant functions avoid unsafe shared mutable internal state.
  • Global and static variables are shared across function invocations.
  • Race conditions can occur when concurrent operations access shared data without synchronization.
  • Thread-safe functions may use mutexes to serialize shared-state access.
  • Reentrancy and thread safety are related but not identical.
  • ISRs must avoid blocking operations and unsafe shared-state access.
  • Function parameters, local variables, queues, and clear ownership rules support safer RTOS designs.
