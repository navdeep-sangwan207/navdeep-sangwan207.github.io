1. Introduction

In an RTOS-based embedded system, multiple tasks may need to access the same hardware peripheral, memory location, communication interface, or software data structure.

A resource accessed by more than one task is called a shared resource.

Shared resource management ensures that concurrent tasks use these resources safely and in a controlled manner.

Key concept: A shared resource must have a clearly defined access policy. A mutex is commonly used when tasks require exclusive access to a resource.

3. Problems Caused by Uncontrolled Access

3.1 Race condition

A race condition occurs when the result of an operation depends on the timing or interleaving of concurrent execution.

Example: Shared counter

sharedCounter = sharedCounter + 1;

This statement may involve multiple machine operations:

  1. Read the current counter value.
  2. Increment the value.
  3. Write the updated value.

If two tasks perform these operations concurrently, one update may overwrite the other.

3.2 Data corruption

Concurrent modifications can leave a shared data structure in an inconsistent state.

3.3 Peripheral conflicts

Two tasks may attempt to reconfigure the same peripheral or start transactions that cannot safely overlap.

3.4 Inconsistent communication

Multiple tasks transmitting through a shared UART driver may interleave their messages if the driver does not provide suitable serialization.

4. Resource Protection Using a Mutex

A mutex provides exclusive ownership of a resource between tasks.

                v

                v

General access sequence

  1. Create the mutex before starting the tasks that use it.
  2. A task requests the mutex.
  3. If available, the task acquires ownership.
  4. The task accesses the protected resource.
  5. The task releases the mutex.
  6. Another waiting task may acquire it.

5. Shared UART Resource Management

Consider two tasks that need to send messages using the same UART peripheral.

Without resource protection

Task A:
    UART_Send("HELLO");

Task B:
    UART_Send("WORLD");

If both tasks transmit concurrently, the driver may interleave their operations.

With a mutex

Task A:
    Take UART Mutex
    UART_Send("HELLO")
    Give UART Mutex

Task B:
    Take UART Mutex
    UART_Send("WORLD")
    Give UART Mutex

The mutex serializes the protected operations, provided all tasks use the same mutex and the UART driver follows the required transaction rules.

6. Shared I2C and SPI Bus Management

6.1 I2C bus

Multiple tasks may communicate with different I2C devices using the same controller.

A mutex can protect the complete transaction, including:

  • Bus configuration where required.
  • Device address selection.
  • Register address transmission.
  • Data transmission or reception.
  • Transaction completion and cleanup.

6.2 SPI bus

Multiple SPI devices may share clock, MOSI and MISO signals while using different chip-select signals.

Resource management may need to protect:

  • SPI controller configuration.
  • Clock polarity and phase changes.
  • Chip-select activation.
  • Complete transfer sequence.
  • Chip-select deactivation.
A mutex coordinates participating tasks. It does not automatically prevent an ISR, DMA controller, or independent hardware agent from accessing the peripheral. Those access paths require their own coordination and driver design.

7. Protecting Shared Memory

Global variables and shared structures may be accessed by multiple tasks.

Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xDataMutex;

int temperature = 25;

void UpdateTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xDataMutex,
                portMAX_DELAY) == pdTRUE)
        {
            temperature = temperature + 1;

            xSemaphoreGive(xDataMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

void ReadTask(void *pvParameters)
{
    int localTemperature;

    for (;;)
    {
        if (xSemaphoreTake(
                xDataMutex,
                portMAX_DELAY) == pdTRUE)
        {
            localTemperature = temperature;

            xSemaphoreGive(xDataMutex);
        }

        /* Process the local copy outside the lock */
        ProcessTemperature(localTemperature);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    xDataMutex = xSemaphoreCreateMutex();

    if (xDataMutex == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(UpdateTask, "Update", 256, NULL, 2, NULL);
    xTaskCreate(ReadTask, "Read", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Explanation

  • Both tasks share the global variable temperature.
  • The update task locks the resource before modifying it.
  • The read task locks the resource before copying its value.
  • The read task processes a local copy after releasing the mutex.
  • The protected access prevents these two task operations from overlapping.

8. Resource Ownership and Access Policy

For every shared resource, the system designer should define who can access it and how access is coordinated.

PolicyDescription
Exclusive ownershipOnly one task accesses the resource at a time.
Dedicated owner taskOne task owns the peripheral and other tasks send requests to it.
Read-only sharingMultiple tasks may read immutable data without modifying it.
Protected shared dataTasks use a mutex around shared modifications and related reads.
Producer-consumer transferTasks exchange data through queues or buffers with defined ownership.

A dedicated owner task can simplify access to a peripheral because only that task directly controls it. Other tasks communicate through queues or notifications.

9. Resource Management and DMA

DMA (Direct Memory Access) transfers data between memory and peripherals with limited CPU intervention.

A mutex alone is not sufficient to manage a resource while DMA is active. The application must define the ownership and lifetime of the DMA buffer and coordinate transfer completion.

Typical DMA sequence

  1. A task prepares a DMA buffer.
  2. The driver configures and starts the DMA transfer.
  3. The buffer remains valid and is not modified while DMA uses it.
  4. A hardware interrupt reports transfer completion.
  5. The ISR acknowledges the interrupt and signals a task using an appropriate ISR-safe mechanism.
  6. The task processes the completed transfer and releases or reuses the buffer according to the ownership protocol.
Use queues, task notifications, semaphores and explicit buffer ownership to coordinate asynchronous DMA operations. The exact design depends on the DMA controller and peripheral driver.

11. Common Resource Management Problems

11.1 Deadlock

Two or more tasks wait indefinitely for resources held by one another.

11.2 Priority inversion

A high-priority task waits for a resource held by a lower-priority task, and intermediate-priority execution delays the owner.

11.3 Starvation

A task waits for a resource for an excessively long time because other tasks repeatedly obtain access.

11.4 Excessive blocking

A task holds a mutex while performing lengthy work or waiting for an unrelated event.

11.5 Incorrect buffer ownership

A task modifies or reuses a buffer while another task or DMA controller is still using it.

12. Resource Management Best Practices

  1. Identify every resource shared between tasks.
  2. Define an access policy for each resource.
  3. Use mutexes for task-level exclusive ownership.
  4. Use queues to transfer data and peripheral requests.
  5. Consider a dedicated owner task for complex peripherals.
  6. Keep mutex hold times short.
  7. Never wait indefinitely for an unrelated event while holding a mutex.
  8. Define buffer ownership for asynchronous operations.
  9. Coordinate ISR and DMA access separately from task-level mutex ownership.
  10. Check all RTOS API return values.
  11. Use a consistent lock ordering strategy.
  12. Test contention, timeout and error conditions.

13. Practical Activity – Shared Peripheral Management

Design a simple system with two tasks that need to use one shared UART driver.

Activity steps

  1. Create two FreeRTOS tasks.
  2. Create one mutex for the UART resource.
  3. Make both tasks request the mutex before calling the UART driver.
  4. Keep the protected transmission operation within the mutex-controlled section.
  5. Release the mutex after the operation.
  6. Observe task execution and blocking behavior where supported by the environment.
  7. Compare the design with a dedicated UART owner task receiving messages through a queue.

Expected result

The mutex-based design should serialize the protected task-level UART operations. In the dedicated-owner design, only the owner task directly accesses the UART driver, while other tasks submit messages through the queue.

15. Lesson Summary

  • Shared resources can be hardware peripherals, memory or software objects.
  • Uncontrolled concurrent access can cause race conditions and data corruption.
  • Mutexes provide exclusive ownership between tasks.
  • Queues are useful for transferring data and peripheral requests.
  • Dedicated owner tasks can simplify shared peripheral management.
  • DMA requires explicit buffer ownership and completion coordination.
  • ISRs and hardware agents need appropriate coordination beyond a task mutex.
  • Good resource management improves system reliability and predictability.
