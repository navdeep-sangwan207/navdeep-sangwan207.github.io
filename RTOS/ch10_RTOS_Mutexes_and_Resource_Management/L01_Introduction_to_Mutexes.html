1. Introduction

A mutex (Mutual Exclusion) is a synchronization mechanism used to protect shared resources from simultaneous access by multiple tasks.

In an RTOS, several tasks may need to access the same resource, such as:

  • UART communication peripheral.
  • Shared data structures and variables.
  • SPI or I2C communication bus.
  • File system or storage device.
  • Shared memory buffers.
  • Common hardware control interfaces.

If multiple tasks modify or use a shared resource without coordination, race conditions and data corruption may occur.

Key concept: A mutex allows only one task at a time to own a protected resource. Other tasks requesting the same mutex must wait until its owner releases it.

2. Meaning of Mutual Exclusion

Mutual exclusion means preventing multiple tasks from entering the same protected section simultaneously.

Example

Suppose Task A and Task B both need to transmit messages through the same UART peripheral.

Without mutual exclusion, their transmission operations may overlap, causing mixed or corrupted messages.

Without a mutex

Task A: UART_Send("HELLO");
Task B: UART_Send("WORLD");

If the transmissions interleave, the receiver may get an unexpected sequence of characters.

With a mutex

Task A:
    Take Mutex
    Transmit "HELLO"
    Give Mutex

Task B:
    Take Mutex
    Transmit "WORLD"
    Give Mutex

Only one task owns the mutex at a time, so the protected transmission operations do not overlap.

3. Basic Mutex Architecture

          +------------------+
          |      Task A      |
          +------------------+
                   |
                   | Request Mutex
                   v
          +------------------+
          |      MUTEX       |
          |                  |
          |   Resource Lock  |
          +------------------+
                   ^
                   | Request Mutex
                   |
          +------------------+
          |      Task B      |
          +------------------+

       Only one task can own the mutex
       at any particular time.

Operation sequence

  1. Task A requests the mutex.
  2. If the mutex is available, Task A becomes its owner.
  3. Task B requests the same mutex.
  4. If Task A still owns it, Task B waits.
  5. Task A finishes accessing the shared resource.
  6. Task A releases the mutex.
  7. Task B becomes eligible to obtain the mutex.

4. How a Mutex Works

A mutex generally has two important states:

StateMeaning
AvailableNo task currently owns the mutex.
OwnedA task currently holds the mutex.

Mutex acquisition

A task requests ownership using a mutex take operation. If the mutex is available, the task obtains ownership. If another task owns it, the requesting task may enter the Blocked state while waiting.

Mutex release

The owning task releases the mutex after completing the protected operation. A waiting task may then become Ready.

The scheduler selects which Ready task executes. Releasing a mutex does not mean that a particular waiting task must execute immediately.

5. Mutex Ownership

Ownership is one of the most important differences between a mutex and a binary semaphore.

  • A mutex is owned by the task that successfully takes it.
  • The owning task is responsible for releasing it.
  • A different task must not release a mutex owned by another task.
  • A mutex must not be used from an ISR.

Example

if (xSemaphoreTake(
        xMutex,
        portMAX_DELAY) == pdTRUE)
{
    AccessSharedResource();

    /* The owning task releases the mutex */
    xSemaphoreGive(xMutex);
}
Do not treat a mutex as a general event-notification semaphore. Mutex ownership is designed for task-level mutual exclusion.

6. Mutex in FreeRTOS

FreeRTOS implements mutexes using semaphore-related APIs. The mutex handle uses the SemaphoreHandle_t type.

Creating a mutex

SemaphoreHandle_t xMutex;

xMutex = xSemaphoreCreateMutex();

Taking a mutex

if (xSemaphoreTake(
        xMutex,
        portMAX_DELAY) == pdTRUE)
{
    /* Mutex successfully acquired */
}

Giving a mutex

xSemaphoreGive(xMutex);

Checking creation

xMutex = xSemaphoreCreateMutex();

if (xMutex == NULL)
{
    /* Mutex creation failed */
    HandleInitializationError();
}

The mutex must be created before tasks attempt to use it.

7. Example – Protecting a Shared Variable

Suppose two tasks need to update a shared counter. A mutex can protect the read-modify-write operation.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xCounterMutex;

int sharedCounter = 0;

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xCounterMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            xSemaphoreGive(xCounterMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xCounterMutex,
                portMAX_DELAY) == pdTRUE)
        {
            sharedCounter++;

            xSemaphoreGive(xCounterMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(150));
    }
}

int main(void)
{
    xCounterMutex = xSemaphoreCreateMutex();

    if (xCounterMutex == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(TaskA, "TaskA", 256, NULL, 2, NULL);
    xTaskCreate(TaskB, "TaskB", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Explanation

  1. Both tasks share the variable sharedCounter.
  2. Each task takes the mutex before incrementing the counter.
  3. The increment operation is protected.
  4. The task releases the mutex after updating the variable.
  5. The other task can then acquire the mutex.

This prevents the two tasks from performing the protected increment concurrently.

8. Mutex and Critical Section

Both mechanisms can protect shared data, but they have different behavior and intended use.

FeatureMutexCritical Section
PurposeTask-level resource ownership.Protect a short section of code from specified concurrent execution.
BlockingA task may block while waiting.Does not block waiting for ownership in the same manner.
OwnershipHas task ownership semantics.Does not provide mutex-style resource ownership.
Priority inheritanceSupported by FreeRTOS mutexes.Not provided as mutex priority inheritance.
ISR usageNot permitted.ISR-specific critical-section mechanisms are port-dependent.
Typical durationMay cover a longer resource operation.Should be kept very short.
FreeRTOS critical-section macros have port-specific interrupt-masking behavior. Do not assume they mask every interrupt or apply Cortex-M BASEPRI behavior to ARM7 processors.

9. Priority Inheritance in Mutexes

FreeRTOS mutexes support priority inheritance to reduce certain forms of priority inversion.

Priority inversion occurs when a high-priority task waits for a resource held by a lower-priority task, while a medium-priority task prevents the lower-priority task from running.

Basic example

  • Low-priority Task L owns a mutex.
  • High-priority Task H requests the same mutex and blocks.
  • Medium-priority Task M becomes Ready.
  • Task M can preempt Task L and delay the release of the mutex.

With priority inheritance, the mutex owner may temporarily inherit the higher priority of the blocked task. This helps the owner run and release the mutex sooner.

Priority inheritance reduces the effects of priority inversion. It does not eliminate every possible scheduling delay or guarantee that all deadlines will be met.

11. Common Mutex Programming Errors

  • Using an uninitialized mutex handle.
  • Ignoring mutex creation failure.
  • Forgetting to release a mutex after taking it.
  • Attempting to release a mutex from a task that does not own it.
  • Calling mutex APIs from an ISR.
  • Holding a mutex while waiting for an unrelated event.
  • Taking multiple mutexes in inconsistent orders.
  • Keeping a mutex locked for unnecessarily long periods.
  • Using a mutex when a simple event notification is required.
  • Assuming priority inheritance prevents all scheduling problems.

12. Best Practices

  1. Use mutexes only for task-level mutual exclusion.
  2. Keep the protected section as short as practical.
  3. Always release a mutex after successful acquisition.
  4. Use a consistent locking order when multiple mutexes are required.
  5. Avoid blocking or long delays while holding a mutex.
  6. Do not use mutexes inside ISRs.
  7. Check mutex creation and take operation results.
  8. Use queues for data transfer rather than protecting every data exchange with a mutex.
  9. Consider priority inversion when assigning task priorities.
  10. Document which task or driver owns each shared resource.

13. Practical Activity – Mutex-Based Resource Protection

Create two tasks that access a shared counter or simulated UART resource.

Activity steps

  1. Create a mutex using xSemaphoreCreateMutex().
  2. Check whether creation was successful.
  3. Create two tasks with suitable priorities.
  4. Make both tasks take the mutex before accessing the shared resource.
  5. Perform the protected operation.
  6. Give the mutex after completing the operation.
  7. Inspect task states and execution order where supported.
  8. Compare the behavior with an unprotected shared-variable example.

Expected result

Only one task should own the mutex at a time. The shared resource should not be modified concurrently by the two protected task operations.

For LPC2129 Keil simulator-only learning, this is a FreeRTOS programming exercise. A compatible FreeRTOS port must be verified before claiming that the program executes on the current target setup.

15. Lesson Summary

  • A mutex provides mutual exclusion for shared resources.
  • Only one task can own a mutex at a time.
  • FreeRTOS uses xSemaphoreCreateMutex() to create a mutex.
  • Tasks use xSemaphoreTake() and xSemaphoreGive() to acquire and release it.
  • The owning task must release the mutex.
  • FreeRTOS mutexes support priority inheritance.
  • Mutexes must not be used in ISRs.
  • Correct mutex design helps prevent race conditions and resource corruption.
