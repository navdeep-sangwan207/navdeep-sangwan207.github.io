Priority Inversion

Chapter 10 – Mutexes and Resource Management | Lesson 04

1. Introduction

Priority inversion is a scheduling problem that occurs when a high-priority task is indirectly delayed by a lower-priority task.

It commonly occurs when tasks share resources protected by mutexes. A low-priority task may hold a mutex that a high-priority task needs. While the high-priority task is blocked, a medium-priority task may execute and prevent the low-priority task from releasing the mutex.

Key concept: A high-priority task can be forced to wait because a lower-priority task owns a required resource. This reverses the expected priority-based execution order.

2. Tasks Involved in Priority Inversion

A typical priority inversion example involves three tasks:

TaskPriorityResponsibility
Task HHighNeeds a shared resource protected by a mutex.
Task MMediumPerforms an independent operation.
Task LLowInitially owns the shared-resource mutex.

Assume the priority ordering is:

Task H  = Highest priority
Task M  = Medium priority
Task L  = Lowest priority

3. How Priority Inversion Occurs

Step-by-step execution

  1. Task L starts running and takes a mutex.
  2. Task H becomes Ready and attempts to take the same mutex.
  3. Task H cannot acquire it because Task L owns it, so Task H becomes Blocked.
  4. Task M becomes Ready and preempts Task L.
  5. Task M executes while Task H remains Blocked.
  6. Task L cannot run to release the mutex until Task M stops or blocks.
  7. Task H remains delayed even though it has the highest priority.
The medium-priority task does not own the mutex. Its execution indirectly delays the high-priority task by preventing the low-priority mutex owner from running.

4. Priority Inversion Timeline

Time ------------------------------------------------------>

Task H:   ----------- BLOCKED -------------------- RUN
                       Waiting for mutex

Task M:   ------------- RUNNING --------
                       Preempts Task L

Task L:   RUN -- MUTEX HELD -- WAIT -- RUN -- RELEASE
                                      |
                                      +-- Mutex released

Events:
1. Task L takes mutex.
2. Task H requests mutex and blocks.
3. Task M preempts Task L.
4. Task L resumes and releases mutex.
5. Task H becomes Ready and can run.

The important observation is that Task H is blocked by Task L, but its waiting time is extended by Task M.

6. Effects of Priority Inversion

  • Increased response time for high-priority tasks.
  • Possible deadline misses.
  • Unpredictable task execution delays.
  • Reduced real-time system performance.
  • Potential failure of time-critical control operations.
  • Difficulty in calculating worst-case response time.

Priority inversion is particularly important in systems where high-priority tasks must respond within bounded time intervals.

7. Priority Inversion in Embedded Systems

Example: Shared communication interface

Consider an embedded controller in which:

  • A low-priority task is transmitting a diagnostic message through UART.
  • A high-priority task needs the same UART driver to report an important fault.
  • A medium-priority task performs periodic data processing.

If the low-priority task owns the UART mutex, the high-priority fault-reporting task must wait. If the medium-priority task preempts the low-priority task, the delay can become longer.

Other possible applications

  • Shared SPI or I2C controllers.
  • Shared display drivers.
  • Common memory structures.
  • Storage and file-system interfaces.
  • Shared peripheral driver state.

9. Priority Inheritance

Priority inheritance is a mechanism used to reduce priority inversion.

When a high-priority task blocks on a mutex owned by a lower-priority task, the mutex owner can temporarily inherit the higher priority.

How it works

  1. Task L owns a mutex.
  2. Task H attempts to acquire the same mutex and blocks.
  3. The RTOS temporarily raises Task L's effective priority to that of Task H, subject to the RTOS's inheritance rules.
  4. Task L can now preempt Task M.
  5. Task L completes its protected operation and releases the mutex.
  6. Task H becomes Ready and can acquire the mutex.
  7. Task L's priority is restored according to the mutex and inheritance rules.
Priority inheritance helps the mutex owner run sooner. It does not make the mutex available immediately, nor does it remove the execution time needed to finish the protected operation.

10. Priority Inversion Without and With Priority Inheritance

Without priority inheritance

Task H:  BLOCKED ---------------------- RUN
Task M:          RUNNING
Task L:  RUN -- WAIT -- RUN -- RELEASE

Task M delays the mutex owner.

With priority inheritance

Task H:  BLOCKED ----------- RUN
Task M:  READY
Task L:  RUN -- INHERITS H PRIORITY
                  |
                  +-- RELEASE MUTEX

Task L temporarily executes at H's inherited priority.

Task M no longer preempts Task L merely because Task L originally had a lower priority than Task M.

11. FreeRTOS and Priority Inheritance

FreeRTOS mutexes provide a basic priority inheritance mechanism.

Creating a mutex

SemaphoreHandle_t xMutex;

xMutex = xSemaphoreCreateMutex();

Taking a mutex

if (xSemaphoreTake(
        xMutex,
        portMAX_DELAY) == pdTRUE)
{
    AccessSharedResource();

    xSemaphoreGive(xMutex);
}

When a higher-priority task blocks on a mutex held by a lower-priority task, FreeRTOS can raise the owner's priority to reduce inversion.

Important FreeRTOS behavior

  • Priority inheritance is associated with mutexes, not ordinary binary semaphores.
  • Mutexes must be used in task context.
  • The owning task must release the mutex.
  • FreeRTOS uses a basic priority inheritance implementation rather than every feature of a full priority-ceiling or priority-inheritance protocol.
  • Holding multiple mutexes can complicate priority restoration and blocking analysis.
Do not assume that priority inheritance guarantees zero blocking or eliminates every priority inversion scenario. The design must still bound critical-section execution and resource waiting times.

12. Reducing Priority Inversion

12.1 Use mutexes appropriately

Use a mutex for shared task-level resource protection instead of using a binary semaphore as a substitute for ownership-based locking.

12.2 Keep critical sections short

Reduce the time spent holding a mutex. Perform unrelated processing after releasing it.

12.3 Avoid unnecessary resource sharing

Consider assigning a dedicated owner task to a peripheral and using queues to receive requests.

12.4 Establish a locking order

When tasks need multiple mutexes, define a consistent acquisition order to reduce deadlock risk.

12.5 Analyze blocking time

Include mutex waiting and resource blocking in worst-case response-time analysis.

12.6 Use suitable task priorities

Assign priorities according to real-time requirements, deadlines and task criticality.

14. Practical Activity – Simulating Priority Inversion

Design a three-task scheduling experiment using a compatible RTOS environment.

Task configuration

TaskPriorityAction
Task L1Take a mutex and perform protected work.
Task M2Perform independent CPU work.
Task H3Request the mutex held by Task L.

Activity steps

  1. Create one mutex.
  2. Create three tasks with the specified priorities.
  3. Arrange for Task L to acquire the mutex first.
  4. Make Task H request the mutex while Task L owns it.
  5. Make Task M ready while Task H is blocked.
  6. Observe execution order and task states.
  7. Repeat using a mutex that supports priority inheritance.
  8. Compare how quickly Task L resumes and releases the mutex.

Expected result

Without priority inheritance, Task M can delay Task L. With priority inheritance, Task L can temporarily execute at the inherited priority, helping it release the mutex sooner.

This is a generic RTOS exercise. A compatible FreeRTOS port and suitable trace or scheduling observation facilities are required. Do not assume the LPC2129 Keil simulator currently has a verified FreeRTOS port.

16. Lesson Summary

  • Priority inversion occurs when a high-priority task is delayed by a lower-priority mutex owner.
  • A medium-priority task can extend this delay by preempting the low-priority owner.
  • Priority inversion can increase response time and cause deadline misses.
  • Priority inheritance temporarily raises the mutex owner's effective priority.
  • FreeRTOS mutexes support basic priority inheritance.
  • Priority inheritance does not eliminate all blocking or guarantee deadlines.
  • Short mutex hold times and careful resource design reduce inversion risks.
