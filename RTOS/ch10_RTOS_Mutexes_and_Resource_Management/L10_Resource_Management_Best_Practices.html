1. Learning Objectives

Resource management is a fundamental part of reliable real-time embedded software. Multiple tasks may need access to shared peripherals, memory buffers, communication interfaces and other system resources. Poor resource management can cause race conditions, deadlocks, priority inversion and unpredictable response times.

  • Understand shared-resource ownership.
  • Apply appropriate synchronization mechanisms.
  • Prevent deadlocks and reduce priority inversion.
  • Manage UART, SPI, I2C and shared memory resources.
  • Understand mutex lifecycle and cleanup.
  • Design reliable resource-management architectures.

2. Understanding Resource Management

A resource is any hardware or software object that a task needs to access or modify during execution.

Examples of Shared Resources

Resource Example Possible Problem
UART Serial communication interface Interleaved messages or conflicting driver operations
SPI Shared SPI bus Conflicting bus transactions or chip-select handling
I2C Shared I2C controller Overlapping transactions
Memory Global data structure Race conditions and inconsistent data
Display LCD or graphical display Conflicting updates
File system Shared storage interface Concurrent modification or inconsistent file state
A resource is not necessarily a physical peripheral. Shared data structures, software buffers and memory-management services also require suitable coordination.

3. Resource Ownership

Resource ownership defines which task or software component is responsible for accessing and managing a particular resource. A clear ownership policy reduces unexpected interactions.

Ownership Models

A. Mutex-Based Shared Ownership

Multiple tasks can access a resource, but only the task that successfully acquires the mutex may execute the protected operation at a given time. 

if (xSemaphoreTake(xMutex,
                   portMAX_DELAY) == pdTRUE)
{
    /* Access shared resource */

    xSemaphoreGive(xMutex);
}

B. Dedicated Resource Owner Task

A single task owns a peripheral. Other tasks send requests through a queue. The owner task performs the operations in a controlled sequence. 

Task A ----\
            \
Task B ------> Request Queue
            /
Task C ----/

                 |
                 v

          Peripheral Owner Task
                 |
                 v
             UART / SPI

C. Exclusive Ownership

One task or software module is the only component allowed to access a resource. Other components communicate with its owner through defined interfaces.

Ownership Model Suitable Application
Mutex-based sharing Short operations on shared data or peripherals
Dedicated owner task Complex peripherals with asynchronous operations
Exclusive ownership Resources that should have one controlling software component

4. Best Practices for Mutex Usage

  1. Keep critical operations short: Acquire a mutex immediately before accessing the protected resource and release it as soon as the operation is complete.
  2. Check acquisition results: Never access the protected resource if mutex acquisition fails.
  3. Release only when owned: The task that acquires the mutex must release it.
  4. Avoid unnecessary nested mutexes: Multiple locks increase the complexity of resource management.
  5. Use consistent lock ordering: If multiple mutexes are required, acquire them in the same predefined order.
  6. Do not use mutexes in ISRs: ISRs must not wait for mutex ownership.
  7. Define timeout behavior: Specify what the application should do when a resource cannot be acquired in time.
  8. Protect every access: All tasks accessing the same shared data must follow the same synchronization protocol.

5. Deadlock Prevention Through Lock Ordering

Deadlock can occur when tasks acquire multiple resources in inconsistent orders.

Example of Unsafe Lock Ordering

Task A Task B
Acquires Mutex A Acquires Mutex B
Waits for Mutex B Waits for Mutex A
Cannot continue Cannot continue

Both tasks remain blocked because each owns a mutex needed by the other task.

Correct Lock Ordering

Establish a global ordering rule: every task must acquire Mutex A before Mutex B and release them in reverse order. 

/* Consistent lock ordering */

if (xSemaphoreTake(xMutexA,
                   portMAX_DELAY) == pdTRUE)
{
    if (xSemaphoreTake(xMutexB,
                       portMAX_DELAY) == pdTRUE)
    {
        /* Access resources A and B */

        xSemaphoreGive(xMutexB);
    }

    xSemaphoreGive(xMutexA);
}
The example assumes the mutex handles were successfully created and the task follows the same locking order everywhere. In production code, also define bounded wait and recovery behavior. A timeout can help detect a failed acquisition, but it does not automatically prevent every deadlock.

6. Managing Priority Inversion

Priority inversion occurs when a high-priority task is delayed because a lower-priority task owns a resource that the high-priority task requires.

Recommended Practices

  • Use FreeRTOS mutexes where task-level mutual exclusion and priority inheritance are appropriate.
  • Keep mutex ownership periods short.
  • Avoid blocking operations while holding a mutex.
  • Review task priorities and resource dependencies together.
  • Use a dedicated owner task when peripheral operations are complex.
  • Measure worst-case blocking time during system analysis.
Priority inheritance reduces certain priority inversion delays. It does not eliminate all blocking, solve deadlocks or guarantee that a task will meet its deadline.

7. Peripheral Resource Management

A. UART Management

  • Use a mutex for short, synchronous shared UART operations.
  • For asynchronous transmission, coordinate buffer ownership and completion events.
  • Consider a dedicated UART task receiving messages through a queue.
  • Do not assume that protecting the UART register write protects the entire DMA transfer.

B. SPI Management

  • Coordinate access to the shared SPI controller.
  • Configure the correct clock polarity and phase for each device.
  • Control chip-select signals as part of the complete transaction.
  • Prevent another task from changing bus configuration during an active transfer.

C. I2C Management

  • Serialize transactions through the shared I2C controller.
  • Protect the complete start-address-data-stop transaction where appropriate.
  • Handle NACK, timeout and bus-error conditions.
  • Define a bus-recovery strategy for supported hardware.

D. Shared Memory Management

  • Protect shared structures during updates.
  • Use queues when tasks need to exchange data.
  • Define buffer ownership and lifetime rules.
  • Avoid returning pointers to temporary or expired storage.

8. Dedicated Peripheral Owner Task – Example

A dedicated owner task can simplify access to a complex peripheral. In this example, several tasks submit text messages to a UART owner task through a FreeRTOS queue.

Program

#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include 

#define MESSAGE_LENGTH 40
#define QUEUE_LENGTH   8

typedef struct
{
    char text[MESSAGE_LENGTH];
} UARTMessage_t;

QueueHandle_t xUARTQueue;

/* Replace with the target-specific UART driver. */
void UART_SendString(const char *text)
{
    /*
     * Implement synchronous transmission here,
     * or use a driver completion mechanism.
     */
}

void UARTOwnerTask(void *pvParameters)
{
    UARTMessage_t receivedMessage;

    for (;;)
    {
        if (xQueueReceive(xUARTQueue,
                          &receivedMessage,
                          portMAX_DELAY) == pdPASS)
        {
            UART_SendString(receivedMessage.text);
        }
    }
}

void SensorTask(void *pvParameters)
{
    UARTMessage_t message = {0};

    for (;;)
    {
        strncpy(message.text,
                "Sensor task message\r\n",
                MESSAGE_LENGTH - 1);

        message.text[MESSAGE_LENGTH - 1] = '\0';

        xQueueSend(xUARTQueue,
                   &message,
                   portMAX_DELAY);

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void MonitorTask(void *pvParameters)
{
    UARTMessage_t message = {0};

    for (;;)
    {
        strncpy(message.text,
                "System monitor message\r\n",
                MESSAGE_LENGTH - 1);

        message.text[MESSAGE_LENGTH - 1] = '\0';

        xQueueSend(xUARTQueue,
                   &message,
                   portMAX_DELAY);

        vTaskDelay(pdMS_TO_TICKS(700));
    }
}

int main(void)
{
    /* Initialize the UART hardware and driver first. */

    xUARTQueue = xQueueCreate(
        QUEUE_LENGTH,
        sizeof(UARTMessage_t)
    );

    if (xUARTQueue != NULL)
    {
        xTaskCreate(UARTOwnerTask,
                    "UARTOwner",
                    256,
                    NULL,
                    3,
                    NULL);

        xTaskCreate(SensorTask,
                    "Sensor",
                    256,
                    NULL,
                    2,
                    NULL);

        xTaskCreate(MonitorTask,
                    "Monitor",
                    256,
                    NULL,
                    2,
                    NULL);

        vTaskStartScheduler();
    }

    for (;;);
}

Working Principle

  1. The UART owner task is the only task that directly accesses the UART driver.
  2. SensorTask creates a message and submits it to the queue.
  3. MonitorTask also submits its message to the same queue.
  4. The UART owner task receives one complete message at a time.
  5. The owner task transmits messages in queue-receive order.
FreeRTOS queues copy queue items. This example sends a fixed-size message structure, so the queue receives its own copy rather than a pointer to a task's local buffer. Check queue-send failures in production systems and define a policy for queue-full conditions.

9. Mutex Creation and Deletion Best Practices

Dynamic Creation

SemaphoreHandle_t xMutex;

xMutex = xSemaphoreCreateMutex();

if (xMutex == NULL)
{
    /* Handle allocation failure. */
}

Dynamic creation obtains the required memory through the configured FreeRTOS heap implementation.

Static Creation

StaticSemaphore_t xMutexBuffer;
SemaphoreHandle_t xMutex;

xMutex = xSemaphoreCreateMutexStatic(&xMutexBuffer);

if (xMutex == NULL)
{
    /* Handle creation failure. */
}

Static creation uses application-provided storage. It requires static allocation support and the appropriate FreeRTOS configuration and API declarations.

Deletion

/*
 * Delete only after all tasks have stopped using
 * the mutex and no task owns it.
 */
vSemaphoreDelete(xMutex);
xMutex = NULL;
Do not delete a mutex while tasks may still be waiting for it or while a task owns it. Stop or coordinate all users first. Static storage must remain valid for the lifetime of the mutex.

10. Resource Management Design Checklist

  • Identify every shared resource.
  • Define which task or module owns each resource.
  • Select a suitable synchronization mechanism.
  • Document mutex ownership and lock ordering.
  • Keep protected operations short.
  • Define timeout and error-recovery behavior.
  • Coordinate DMA and interrupt-driven transfers separately.
  • Check queue capacity and message-buffer ownership.
  • Measure worst-case blocking and task response time.
  • Test failure cases, not only normal operation.

11. Common Interview Questions

1. What is resource management in an RTOS?

Resource management is the controlled allocation, access, synchronization and release of shared hardware and software resources among concurrent tasks.

2. Why is resource ownership important?

It establishes which task or module is responsible for a resource, reducing conflicting access and simplifying debugging.

3. How can deadlock be prevented?

Use consistent lock ordering, avoid unnecessary nested locks, minimize resource dependencies and design bounded recovery behavior.

4. What is a dedicated peripheral owner task?

It is a task that exclusively manages a peripheral while other tasks submit requests through queues or another communication mechanism.

5. Does priority inheritance eliminate priority inversion?

It reduces certain priority inversion delays by temporarily increasing the priority of a mutex-owning task. It does not eliminate all blocking or guarantee deadlines.

6. Why should a mutex not be held during long delays?

Other tasks needing the same resource remain blocked, increasing their response times and potentially causing missed deadlines.

7. What is the difference between a mutex and a queue?

A mutex provides mutual exclusion and ownership. A queue transfers data between tasks and can provide synchronization as part of the communication operation.

8. How should asynchronous peripheral transfers be managed?

The design must define buffer ownership, transfer completion, error reporting and synchronization between the initiating task and the interrupt or DMA completion handler.

13. Chapter 10 – Final Summary

Mutexes and resource management are essential for reliable multitasking embedded systems. Correct synchronization prevents race conditions, protects shared resources and helps control task blocking.

  • Mutexes provide task-level mutual exclusion and ownership.
  • Priority inheritance helps reduce priority inversion.
  • Consistent lock ordering helps prevent circular-wait deadlocks.
  • Queues are useful for data exchange and peripheral-owner architectures.
  • UART, SPI and I2C operations require complete transaction coordination.
  • Asynchronous DMA and interrupt-driven transfers require explicit completion and buffer-ownership management.
  • Resource-management design must consider timing, reliability and failure recovery.
