Mutex vs Binary Semaphore

1. Introduction

A mutex and a binary semaphore are synchronization mechanisms used in Real-Time Operating Systems. Both can have two logical states, but they serve different purposes.

  • Mutex: Primarily provides mutual exclusion to protect a shared resource.
  • Binary semaphore: Primarily provides task synchronization or event signaling.

Although both are implemented using semaphore-related mechanisms in FreeRTOS, their ownership and scheduling behavior are different.

Remember: Use a mutex when a task needs exclusive ownership of a resource. Use a binary semaphore when one execution context needs to signal an event to another.

2. What Is a Mutex?

A mutex (Mutual Exclusion object) allows one task at a time to access a protected shared resource.

Example: Shared UART

Suppose Task A and Task B both need to transmit messages through UART0.

Task A:
    Take UART mutex
    Transmit message A
    Give UART mutex

Task B:
    Take UART mutex
    Transmit message B
    Give UART mutex

If Task A owns the mutex, Task B must wait until Task A releases it.

Important properties

  • A mutex has an owner.
  • Only one task can own it at a time.
  • The owning task is responsible for releasing it.
  • FreeRTOS mutexes support priority inheritance.
  • A mutex cannot be used from an ISR.

3. What Is a Binary Semaphore?

A binary semaphore is a synchronization object that can represent one pending token or event.

It is commonly used when an ISR or task signals that an event has occurred and another task needs to respond.

Example: Sensor event notification

Sensor Interrupt:
    Give binary semaphore

Sensor Processing Task:
    Wait for binary semaphore
    Process sensor event

When the event is signaled, the waiting task can become Ready.

Important properties

  • A binary semaphore has no mutex-style owner.
  • It can be given by an ISR using an ISR-safe API.
  • It can be used to signal events between execution contexts.
  • It does not provide priority inheritance.
  • Repeated gives while it is already full do not accumulate additional tokens.

6. FreeRTOS API for Mutex

Creating a mutex

SemaphoreHandle_t xMutex;

xMutex = xSemaphoreCreateMutex();

Taking a mutex

if (xSemaphoreTake(
        xMutex,
        portMAX_DELAY) == pdTRUE)
{
    AccessSharedResource();

    xSemaphoreGive(xMutex);
}

xSemaphoreTake() requests ownership. If another task owns the mutex, the calling task can wait for it.

Important points

  • Check that mutex creation succeeds.
  • Call the give operation after successful acquisition.
  • Do not release a mutex from a different task.
  • Do not call mutex take or give from an ISR.

7. FreeRTOS API for Binary Semaphore

Creating a binary semaphore

SemaphoreHandle_t xBinarySemaphore;

xBinarySemaphore = xSemaphoreCreateBinary();

A newly created FreeRTOS binary semaphore is initially empty.

Task waiting for an event

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xBinarySemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            ProcessSensorEvent();
        }
    }
}

Signaling from another task

xSemaphoreGive(xBinarySemaphore);

Signaling from an ISR

void SensorISR(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge the hardware interrupt here */

    xSemaphoreGiveFromISR(
        xBinarySemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}
The ISR example is a generic FreeRTOS pattern. The exact interrupt acknowledgment, ISR-safe API rules and yield macro depend on the selected FreeRTOS port and hardware. Do not assume this code is directly compatible with the LPC2129 Keil simulator.

8. Practical Example – Mutex for Shared UART

Two tasks need to use the same UART transmitter. A mutex prevents their protected transmission operations from overlapping.

Program structure

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xUARTMutex;

void UART_SendMessage(const char *message)
{
    /* Replace with the actual UART driver */
}

void TaskA(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xUARTMutex,
                portMAX_DELAY) == pdTRUE)
        {
            UART_SendMessage("Message from Task A");

            xSemaphoreGive(xUARTMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

void TaskB(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xUARTMutex,
                portMAX_DELAY) == pdTRUE)
        {
            UART_SendMessage("Message from Task B");

            xSemaphoreGive(xUARTMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(700));
    }
}

int main(void)
{
    xUARTMutex = xSemaphoreCreateMutex();

    if (xUARTMutex == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(TaskA, "TaskA", 256, NULL, 2, NULL);
    xTaskCreate(TaskB, "TaskB", 256, NULL, 2, NULL);

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Expected behavior

  • Task A requests the UART mutex before transmitting.
  • Task B waits if Task A currently owns the mutex.
  • After Task A releases the mutex, Task B can acquire it.
  • The two protected transmission operations do not overlap.

9. Practical Example – Binary Semaphore for an Interrupt Event

Suppose a hardware sensor generates an interrupt when new data becomes available. An ISR can signal a processing task using a binary semaphore.

Program structure

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xSensorSemaphore;

void SensorTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(
                xSensorSemaphore,
                portMAX_DELAY) == pdTRUE)
        {
            /* Read or process sensor data */
            ProcessSensorEvent();
        }
    }
}

void SensorISR(void)
{
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Acknowledge sensor interrupt */

    xSemaphoreGiveFromISR(
        xSensorSemaphore,
        &xHigherPriorityTaskWoken
    );

    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

int main(void)
{
    xSensorSemaphore = xSemaphoreCreateBinary();

    if (xSensorSemaphore == NULL)
    {
        for (;;)
        {
        }
    }

    xTaskCreate(
        SensorTask,
        "SensorTask",
        256,
        NULL,
        3,
        NULL
    );

    /* Configure hardware interrupt here */

    vTaskStartScheduler();

    for (;;)
    {
    }
}

Expected behavior

  1. The sensor generates an interrupt.
  2. The ISR acknowledges the interrupt source.
  3. The ISR gives the binary semaphore.
  4. The waiting sensor task becomes Ready.
  5. The task processes the event when scheduled.
A binary semaphore stores at most one pending token. If multiple events occur before the task consumes the token, repeated gives can coalesce. Use a counting semaphore, queue or another suitable mechanism when every event must be recorded.

10. Why Mutexes Have Priority Inheritance

Consider three tasks:

TaskPriorityRole
Task HHighNeeds a shared resource
Task MMediumIndependent processing
Task LLowCurrently owns the mutex

Task H may become blocked because Task L owns the mutex. Task M can then delay Task L from running and releasing it.

FreeRTOS mutexes support priority inheritance: Task L can temporarily inherit Task H's priority while holding the mutex that blocks Task H.

A binary semaphore does not provide this mutex priority-inheritance behavior.

Priority inheritance is a mitigation mechanism, not a complete solution to all blocking and deadline problems.

11. Can a Binary Semaphore Protect a Shared Resource?

A binary semaphore can be used to coordinate access in some designs, but it does not provide mutex ownership or priority inheritance.

For example, a task could take a binary semaphore before accessing a shared buffer and give it afterward. However, the design must carefully enforce correct take/give behavior and prevent unrelated contexts from giving it incorrectly.

For ordinary task-level resource protection in FreeRTOS, a mutex is generally the better choice.

A binary semaphore given by an ISR is useful for signaling that an event occurred. It does not automatically guarantee that the associated data buffer is protected from being overwritten or modified by another execution context.

12. Decision Guide – Which One Should You Use?

RequirementRecommended mechanism
Protect shared UART access between tasksMutex
Protect shared I2C driver state between tasksMutex
Signal a task when an interrupt occursBinary semaphore or task notification
Signal that a one-time operation is completeBinary semaphore or task notification
Count multiple pending eventsCounting semaphore or queue
Transfer structured data between tasksQueue
Protect a shared resource with priority inheritanceMutex

13. Common Mistakes

  • Using a binary semaphore as though it has mutex ownership.
  • Using a mutex to signal an ISR event.
  • Assuming repeated binary semaphore gives count every event.
  • Assuming a binary semaphore provides priority inheritance.
  • Assuming a mutex automatically protects data accessed by DMA or hardware.
  • Using a semaphore to signal data availability without defining buffer ownership.
  • Ignoring the possibility of a missed or coalesced event.
  • Holding a mutex while waiting for an event that requires another task to run.

16. Lesson Summary

  • A mutex is primarily used for mutual exclusion and shared-resource protection.
  • A binary semaphore is primarily used for task synchronization and event signaling.
  • A mutex has ownership; a binary semaphore does not.
  • FreeRTOS mutexes support priority inheritance.
  • A binary semaphore can be given from an ISR using an ISR-safe API.
  • A mutex must not be used from an ISR.
  • Repeated binary semaphore signals can coalesce.
  • Queues are often more suitable when actual data must be transferred.
