1. Learning Objectives

Priority ceiling protocols are resource synchronization techniques used in real-time systems to control priority inversion, bound resource blocking, and, under defined assumptions, prevent deadlocks.

After completing this lesson, you will be able to:

  • Define priority ceiling and resource ceiling.
  • Explain how resource ceiling priorities are assigned.
  • Understand the operation of priority ceiling protocols.
  • Differentiate the original Priority Ceiling Protocol (PCP) and Immediate Ceiling Priority Protocol (ICPP).
  • Analyze resource blocking with numerical examples.
  • Compare priority ceiling with priority inheritance.
  • Understand the limitations of applying formal protocols to FreeRTOS applications.

2. Introduction to Priority Ceiling

A real-time application may contain multiple tasks that share resources such as memory buffers, communication interfaces, peripheral drivers, and data structures.

When a task locks a shared resource, another task may need to wait. Priority ceiling protocols control the scheduling priority associated with resource access so that resource blocking is predictable and priority inversion is limited.

What Is a Resource Ceiling?

The resource ceiling priority is the highest priority among all tasks that may use a particular shared resource.

Suppose a shared SPI resource is used by:
  • Task A – priority 2
  • Task B – priority 4
  • Task C – priority 5
The ceiling priority of the SPI resource is 5, because Task C has the highest priority among the tasks that can access it.
In this lesson, larger numerical values represent higher task priorities. Some RTOS configurations use different conventions; always check the scheduler's priority ordering.

3. Resource Ceiling Assignment

The ceiling of each resource is determined during system design by identifying all tasks that may lock that resource.

Example Task and Resource Table

Task Priority Shared Resources
Task A 2 UART, SPI
Task B 4 SPI, I2C
Task C 5 UART, I2C
Task D 3 UART

Calculated Resource Ceilings

Resource Tasks Using Resource Ceiling Priority
UART A (2), C (5), D (3) 5
SPI A (2), B (4) 4
I2C B (4), C (5) 5

A resource's ceiling is based on the highest-priority task that may access it, not merely the priority of the task currently holding it.

4. Original Priority Ceiling Protocol (PCP)

The original Priority Ceiling Protocol combines resource locking, priority inheritance, and a system ceiling rule.

The system ceiling is the highest ceiling priority among resources currently locked by tasks other than the requesting task, according to the formal protocol's rules.

Basic Operation

  1. A task requests access to a shared resource.
  2. The protocol checks the current system ceiling.
  3. The request is permitted only when the protocol's ceiling admission condition is satisfied.
  4. If access is denied, the requesting task is blocked.
  5. The task responsible for the blocking resource may inherit the blocked task's priority.
  6. When the resource is released, the protocol updates the system ceiling and task priorities as required.
The original PCP admission rule is more specific than simply asking whether a task has a higher priority than the current resource owner. It considers the system ceiling and the resources held by other tasks.

Purpose of PCP

  • Control priority inversion.
  • Bound the duration of resource-related blocking under the protocol assumptions.
  • Prevent deadlock under the formal protocol's assumptions.
  • Support schedulability analysis of fixed-priority real-time tasks.

5. Immediate Ceiling Priority Protocol (ICPP)

The Immediate Ceiling Priority Protocol is also known as the Priority Protect Protocol in some real-time scheduling literature. It raises a task's active priority immediately when the task locks a resource.

How ICPP Works

  1. Each resource is assigned a ceiling priority.
  2. A task locks a resource.
  3. The task's active priority is immediately raised to the resource's ceiling priority if that is higher than its current priority.
  4. The task executes its protected operation at the raised priority.
  5. When the resource is unlocked, its active priority is recalculated according to the protocol and any other held resources.
Example:

Task L has priority 2 and locks a UART resource whose ceiling priority is 5. Under ICPP, Task L immediately executes at priority 5 while holding that resource, even if no higher-priority task has requested it yet.

Important Difference

In original PCP, priority inheritance is associated with blocking caused by resource contention and the system-ceiling admission rule. In ICPP, priority is raised immediately when a resource is locked.

6. Numerical Example of Resource Ceiling

Consider three tasks and one shared resource:

Task Priority Resource Usage
Task L 1 Uses Resource R
Task M 2 Does not use Resource R
Task H 3 Uses Resource R

The resource ceiling of R is 3 because Task H is the highest-priority task that can access it.

Illustrative ICPP Execution

Time Event Task Priority / State
0 ms Task L locks R. L's active priority rises from 1 to 3.
1 ms Task M becomes ready. M has priority 2; L remains at 3.
2 ms Task L continues its protected operation. L executes ahead of M.
4 ms Task L releases R. L's active priority is recalculated.
After 4 ms Ready tasks are scheduled. Scheduler selects the highest-priority ready task.

The example illustrates immediate priority elevation. Actual task execution and release times depend on the application and scheduler.

7. Priority Ceiling and Deadlock Prevention

Deadlock occurs when tasks wait indefinitely for resources held by one another. A common cause is inconsistent resource acquisition order.

Example of Circular Wait

  • Task A locks Resource R1.
  • Task B locks Resource R2.
  • Task A requests R2 and waits for Task B.
  • Task B requests R1 and waits for Task A.

Neither task can continue. This is a deadlock.

How Ceiling Protocols Help

Formal priority ceiling protocols restrict resource admission and priority behavior so that circular wait is prevented under their defined assumptions.

Simply assigning a high priority to a mutex owner does not automatically prevent deadlock. A system using ordinary FreeRTOS mutexes does not become a formal PCP or ICPP implementation merely because priority inheritance is enabled.

8. Priority Inheritance vs Priority Ceiling

Feature Priority Inheritance Priority Ceiling
Priority adjustment Owner inherits the priority of a blocked higher-priority task. Priority is controlled using the resource's assigned ceiling.
When priority changes When relevant priority-based blocking occurs. Depends on protocol; ICPP raises priority on resource lock.
Resource ceiling assignment Not required by basic priority inheritance. Required.
System ceiling Not part of basic priority inheritance. Used by original PCP.
Deadlock prevention Does not inherently prevent deadlock. Formal ceiling protocols can prevent deadlock under their assumptions.
Implementation Available in FreeRTOS mutexes. Requires an implementation of the selected ceiling protocol.

9. FreeRTOS and Priority Ceiling

FreeRTOS provides basic priority inheritance through mutexes, but ordinary FreeRTOS mutex APIs do not implement the full original Priority Ceiling Protocol or Immediate Ceiling Priority Protocol.

FreeRTOS Mutex Example

#include "FreeRTOS.h"
#include "task.h"
#include "semphr.h"

SemaphoreHandle_t xResourceMutex;

void ResourceTask(void *pvParameters)
{
    for (;;)
    {
        if (xSemaphoreTake(xResourceMutex,
                           portMAX_DELAY) == pdTRUE)
        {
            /* Access the shared resource. */

            xSemaphoreGive(xResourceMutex);
        }

        vTaskDelay(pdMS_TO_TICKS(20));
    }
}

int main(void)
{
    xResourceMutex = xSemaphoreCreateMutex();

    if (xResourceMutex != NULL)
    {
        xTaskCreate(ResourceTask,
                    "ResourceTask",
                    256,
                    NULL,
                    2,
                    NULL);

        vTaskStartScheduler();
    }

    for (;;);
}

This code demonstrates ordinary FreeRTOS mutex use. It does not implement a priority ceiling protocol. The application would need additional protocol logic or a kernel that explicitly supports the selected ceiling protocol.

Do not confuse a FreeRTOS task's configured priority with a resource ceiling. Calling vTaskPrioritySet() manually is not, by itself, an implementation of PCP or ICPP.

10. Embedded System Applications

Resource ceiling analysis is useful when multiple tasks share:

  • UART communication interfaces.
  • SPI-connected displays and memory devices.
  • I2C sensors and peripheral controllers.
  • Shared memory buffers.
  • Actuator-control data structures.
  • Communication protocol state machines.

Example: Shared SPI Bus

Suppose a low-priority logging task and a high-priority control task both use the same SPI bus. The resource ceiling is determined from the highest-priority task that may use the bus.

The system designer must account for the time during which the SPI bus is locked, the execution time of each protected operation, and the impact on higher-priority tasks.

11. Design Guidelines

  • Identify all tasks that access each shared resource.
  • Assign resource ceilings using the highest-priority eligible task.
  • Document resource ownership and lock ordering.
  • Keep protected operations short and bounded.
  • Include resource blocking in response-time analysis.
  • Avoid unnecessary nested resource locking.
  • Use a consistent lock order when multiple resources are required.
  • Verify that the RTOS actually implements the protocol being assumed.
  • Test worst-case contention rather than relying only on average execution times.

14. Lesson Summary

  • A resource ceiling is the highest priority of any task that can access that resource.
  • The original PCP uses a system ceiling and priority inheritance rules.
  • ICPP raises a task's active priority immediately when it locks a resource.
  • Formal ceiling protocols can bound blocking and prevent deadlocks under defined assumptions.
  • Priority inheritance and priority ceiling are different synchronization mechanisms.
  • Ordinary FreeRTOS mutexes provide basic priority inheritance, not full PCP or ICPP.
  • Resource locking time must be included in real-time analysis.
