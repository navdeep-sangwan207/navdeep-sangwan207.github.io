1. Introduction

Priority-based scheduling is a scheduling technique in which every task is assigned a priority. The scheduler selects a Ready task according to the scheduling policy and the priorities assigned to the tasks.

In many embedded RTOS implementations, priority-based scheduling allows important tasks to receive processor time before less important tasks.

Basic principle: When multiple tasks are Ready, a priority-based scheduler normally selects the eligible task with the highest priority.

Priority-based scheduling is widely used in embedded applications such as motor control, industrial automation, communication systems, medical equipment and automotive electronics.

2. What Is Task Priority?

Task priority is a numerical value or level assigned to a task to represent its scheduling importance.

A higher-priority task is generally selected before a lower-priority task when both are Ready and eligible to execute.

Illustrative Priority Levels

Task Priority Importance Example Function
Task A 5 High Motor protection monitoring
Task B 3 Medium Sensor data processing
Task C 1 Low Status display update
Important: Priority numbering is RTOS-dependent. In FreeRTOS, a larger numerical priority value represents a higher task priority. Other RTOS implementations may use different conventions.

3. How Priority-Based Scheduling Works

The scheduler examines the tasks that are currently Ready and selects the highest-priority eligible task.

Basic Scheduling Procedure

  1. Tasks are created and assigned priorities.
  2. Tasks become Ready when they are eligible to execute.
  3. The scheduler examines the Ready tasks.
  4. The highest-priority eligible task is selected.
  5. The selected task receives processor time.
  6. If that task blocks, completes its work and yields, or is preempted where supported, another task may execute.

A high-priority task cannot be selected while it is Blocked or Suspended. The scheduler chooses among eligible Ready tasks, subject to the RTOS scheduling rules.

4. Fixed-Priority Scheduling

Fixed-priority scheduling assigns a priority to each task that normally remains unchanged during execution.

The scheduler uses these assigned priorities to determine which Ready task should execute.

Characteristics

  • Each task receives a predefined priority.
  • Priority assignments normally remain constant.
  • Higher-priority Ready tasks are preferred.
  • Scheduling behavior is relatively straightforward to analyze.
  • Priority assignment must consider timing requirements and resource dependencies.

Example

Consider an embedded temperature monitoring system with three tasks:

Task Priority Responsibility
Temperature Alarm 4 Check critical temperature conditions
Temperature Processing 2 Process sensor readings
Display Update 1 Refresh the display

If all three tasks are Ready, the temperature alarm task is selected first. When it blocks or otherwise stops being eligible, the scheduler can select the next highest-priority Ready task.

5. Priority Assignment Strategies

Assigning priorities is an important part of real-time system design. Incorrect priority assignment can cause deadline misses, starvation and excessive response times.

5.1 Based on Task Criticality

Tasks associated with important protection or control functions may receive higher priorities than tasks performing non-critical display or logging operations.

5.2 Based on Timing Requirements

Tasks with demanding timing requirements may need higher priority. However, timing requirements alone do not determine a universally correct priority assignment. Execution time, blocking, interference and task dependencies must also be considered.

5.3 Rate Monotonic Priority Assignment

Rate Monotonic Scheduling (RMS) is a fixed-priority scheduling method for periodic tasks. Under its classical assumptions, the task with the shorter period receives the higher priority.

Task Period RMS Priority
Task A 10 ms Highest
Task B 20 ms Medium
Task C 50 ms Lowest
RMS is one specific priority-assignment strategy. Not every fixed-priority RTOS application uses Rate Monotonic Scheduling.

5.4 Based on System-Level Analysis

Practical priority assignment should consider:

  • Task period and relative deadline.
  • Worst-case execution time (WCET).
  • Blocking caused by shared resources.
  • Interrupt interference.
  • Task dependencies and communication.
  • Acceptable response time and deadline-miss behavior.

6. Ready Task Selection and Preemption

In a preemptive priority-based scheduler, a higher-priority task becoming Ready can cause the currently running lower-priority task to be preempted at an appropriate scheduling point.

Example

Assume the following tasks:

Task Priority Initial State
Task A 4 Blocked
Task B 2 Running
Task C 1 Ready

Initially, Task B executes because Task A is Blocked and Task C has lower priority.

When the event awaited by Task A occurs, Task A becomes Ready. Under preemptive priority scheduling, Task A can preempt Task B when the scheduler is allowed to make the scheduling decision.

Illustrative Execution Timeline

Before Task A becomes Ready

Task B: Running
Task C: Ready

After Task A becomes Ready

Task A: Running
Task B: Ready
Task C: Ready

This is an illustrative scheduling model. Actual execution depends on the RTOS configuration, interrupt handling, critical sections and scheduler state.

7. Priority-Based Scheduling in FreeRTOS

FreeRTOS uses priority-based task scheduling. In the common FreeRTOS kernel configuration, each task is assigned a priority from zero up to one less than configMAX_PRIORITIES.

FreeRTOS priority rule: A larger numerical value means a higher task priority. Priority 0 is the lowest task priority and is used by the Idle Task.

7.1 Priority Configuration

The maximum number of priority levels is configured in FreeRTOSConfig.h. 

#define configMAX_PRIORITIES    5

With this illustrative configuration, valid task priorities are 0, 1, 2, 3 and 4.

7.2 Creating Tasks with Different Priorities

#include "FreeRTOS.h"
#include "task.h"

void Task_High(void *pvParameters)
{
    while (1)
    {
        /* High-priority task operations */

        vTaskDelay(pdMS_TO_TICKS(100));
    }
}

void Task_Medium(void *pvParameters)
{
    while (1)
    {
        /* Medium-priority task operations */

        vTaskDelay(pdMS_TO_TICKS(200));
    }
}

void Task_Low(void *pvParameters)
{
    while (1)
    {
        /* Low-priority task operations */

        vTaskDelay(pdMS_TO_TICKS(500));
    }
}

int main(void)
{
    xTaskCreate(
        Task_High,
        "HighTask",
        256,
        NULL,
        4,
        NULL
    );

    xTaskCreate(
        Task_Medium,
        "MediumTask",
        256,
        NULL,
        2,
        NULL
    );

    xTaskCreate(
        Task_Low,
        "LowTask",
        256,
        NULL,
        1,
        NULL
    );

    vTaskStartScheduler();

    while (1)
    {
    }
}

The example creates three tasks with different priorities. Each task periodically blocks using vTaskDelay(), allowing other Ready tasks to execute.

The stack-depth argument in common FreeRTOS task creation APIs is expressed in StackType_t elements (words), not bytes. The example values are illustrative and must be sized for the actual target, compiler and application.

7.3 Changing Task Priority

FreeRTOS provides vTaskPrioritySet() to change a task's priority at runtime and uxTaskPriorityGet() to read its priority. 

TaskHandle_t xTaskHandle = NULL;

/* Change the priority of a task */
vTaskPrioritySet(xTaskHandle, 3);

/* Read the task priority */
UBaseType_t priority;

priority = uxTaskPriorityGet(xTaskHandle);

The handle must refer to a valid task. Availability of these APIs may depend on the relevant INCLUDE_... settings in FreeRTOSConfig.h.

7.4 Preemption Configuration

#define configUSE_PREEMPTION       1
#define configUSE_TIME_SLICING     1
  • configUSE_PREEMPTION controls whether the kernel uses preemptive scheduling in common FreeRTOS configurations.
  • configUSE_TIME_SLICING controls time slicing between equal-priority Ready tasks where supported by the kernel configuration.

These settings do not guarantee that every newly Ready task executes immediately. Interrupts, critical sections, scheduler suspension and port-specific behavior can affect when a scheduling decision takes place.

8. Priority Inversion

Priority inversion occurs when a high-priority task is indirectly delayed by a lower-priority task holding a shared resource that the high-priority task needs.

Example

  1. Low-priority Task L acquires a shared resource.
  2. High-priority Task H becomes Ready and needs the same resource.
  3. Task H blocks because Task L still owns the resource.
  4. Medium-priority Task M becomes Ready.
  5. Task M preempts Task L, delaying the release of the resource.
  6. Task H remains blocked even though it has the highest priority.

Priority Inversion Relationship

Task H: High

Waits for resource held by Task L

Task M: Medium

Preempts Task L

Task L: Low

Owns the shared resource

Solutions

  • Use mutexes with priority inheritance where supported.
  • Keep critical sections short.
  • Avoid unnecessary shared-resource access.
  • Use suitable resource-access protocols.
  • Analyze worst-case blocking time.
FreeRTOS mutexes implement priority inheritance in the kernel. Binary semaphores do not provide the same priority-inheritance behavior.

9. Priority Starvation

Starvation occurs when a task waits for processor time for an excessively long period because other tasks repeatedly receive scheduling preference.

Example

Suppose a high-priority task remains continuously Ready. A lower-priority task may receive little or no processor time under strict priority-based preemptive scheduling.

Methods to Reduce Starvation

  • Assign priorities carefully.
  • Ensure high-priority tasks block or wait when appropriate.
  • Use time slicing where suitable for equal-priority tasks.
  • Consider priority adjustment or aging if supported by the RTOS.
  • Measure CPU utilization and task response times.
Time slicing between equal-priority tasks does not automatically prevent starvation of lower-priority tasks. A continuously Ready higher-priority task can still dominate the processor.

10. Advantages and Limitations

Advantages

  • Important tasks can receive processor time before less important Ready tasks.
  • Supports responsive embedded control applications.
  • Priority assignments can reflect system requirements.
  • Fixed-priority scheduling can be analyzed using established real-time scheduling techniques.
  • Supported directly by many RTOS kernels, including FreeRTOS.

Limitations

  • Incorrect priority assignment can cause deadline misses.
  • Low-priority tasks may experience starvation.
  • Shared resources can cause priority inversion.
  • Preemption and context switching introduce overhead.
  • Priority-based scheduling alone does not prove schedulability.

11. Priority-Based Scheduling vs Other Scheduling Methods

Scheduling Method Selection Principle Typical Characteristic
Priority-Based Task priority Important Ready tasks receive preference
Round Robin Time quantum among eligible tasks Shares processor time among tasks
FCFS Arrival order Earlier arriving tasks execute first
Rate Monotonic Task period Shorter-period periodic tasks get higher fixed priorities
Earliest Deadline First Nearest absolute deadline Dynamic priority scheduling

Priority-based scheduling describes how tasks are selected using priority. Round Robin, RMS and EDF describe particular scheduling policies or algorithms. Some approaches can be combined, such as time slicing among tasks with equal priority.

12. Practical Embedded System Example

Consider an industrial motor monitoring system with three software tasks:

Task Priority Operation
Protection Task 4 Check overcurrent and fault conditions
Monitoring Task 2 Process voltage and current measurements
Display Task 1 Update motor status information

If all tasks are Ready, the protection task is selected first. Once it blocks or completes its current work, the scheduler can select the next highest-priority Ready task.

In a real motor protection system, critical shutdown behavior should also be evaluated for independent hardware protection, interrupt response, fault handling and worst-case timing. A high-priority software task alone does not establish a safety guarantee.

13. LPC2129 and Keil uVision Practical

The LPC2129 uses an ARM7TDMI-S processor and has a single CPU core. A priority-based RTOS scheduler can conceptually select one Ready task at a time on this processor.

Suggested Simulator Exercise

  1. Review the difference between Ready, Running and Blocked states.
  2. Prepare three conceptual tasks: protection, monitoring and display.
  3. Assign illustrative priorities 4, 2 and 1.
  4. Draw the Ready-task list for different task-state combinations.
  5. Identify which task should be selected in each situation.
  6. Study the ARM7 registers and observe the program counter and stack pointer during ordinary program execution.
This exercise demonstrates scheduling concepts; it does not establish that a compatible FreeRTOS port is available for the LPC2129 in Keil uVision. Verify the exact kernel port and compiler support before attempting to build and run FreeRTOS on this target. Do not apply Cortex-M NVIC priority settings to the ARM7 LPC2129.

For actual FreeRTOS multitasking experiments, use a supported development board and toolchain, or a suitable host-based FreeRTOS demonstration environment.

14. Common Mistakes

  • Assuming that a higher numerical priority always means higher importance in every RTOS.
  • Confusing task priority with hardware interrupt priority.
  • Assuming that a high-priority task can execute while Blocked.
  • Ignoring priority inversion when using shared resources.
  • Assuming time slicing prevents all forms of starvation.
  • Assuming priority-based scheduling automatically guarantees deadlines.
  • Assigning every task the highest priority.
  • Ignoring interrupt interference and task blocking during response-time analysis.

15. Lesson Summary

  • Priority-based scheduling selects tasks according to assigned scheduling priorities.
  • The scheduler normally selects the highest-priority eligible Ready task.
  • Fixed-priority scheduling normally keeps task priorities unchanged.
  • Rate Monotonic Scheduling assigns higher priority to shorter period tasks under its classical assumptions.
  • FreeRTOS uses larger numerical values for higher task priorities.
  • configMAX_PRIORITIES determines the configured priority range.
  • vTaskPrioritySet() changes a task's priority.
  • Priority inversion can occur when a high-priority task waits for a resource held by a lower-priority task.
  • Priority inheritance can help reduce priority inversion.
  • Starvation can affect lower-priority tasks.
  • Priority assignment must be supported by timing and schedulability analysis.
