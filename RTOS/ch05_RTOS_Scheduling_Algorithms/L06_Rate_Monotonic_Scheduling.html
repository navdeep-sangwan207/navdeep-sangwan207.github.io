1. Introduction

Rate Monotonic Scheduling (RMS) is a fixed-priority scheduling algorithm used in real-time systems. It assigns task priorities according to their periods.

A task with a shorter period receives a higher priority, while a task with a longer period receives a lower priority.

Basic principle: Shorter period = Higher priority. Longer period = Lower priority.

RMS is commonly used to analyze periodic real-time tasks in embedded systems where tasks must complete their work within specified deadlines.

2. What Is a Periodic Task?

A periodic task is a task that is released repeatedly at regular time intervals.

For example, a temperature monitoring task may execute every 100 milliseconds, while a display update task may execute every 500 milliseconds.

Example

Task Function Period
Task A Motor current monitoring 10 ms
Task B Temperature measurement 20 ms
Task C Display update 100 ms

Task A executes most frequently, so RMS assigns it the highest priority.

3. Important Timing Parameters

RMS analysis uses several timing parameters to determine whether periodic tasks can meet their deadlines.

Parameter Symbol Description
Execution Time C CPU execution time required by a task for one job.
Period T Time interval between successive releases.
Deadline D Latest permitted completion time for a job.
Release Time r Time at which a task job becomes eligible for execution.
Response Time R Time from release until completion of a job.

Example

Suppose a periodic task has:

  • Execution time = 2 ms
  • Period = 10 ms
  • Relative deadline = 10 ms

The task requires 2 ms of CPU time during every 10 ms period and must finish within its 10 ms relative deadline.

Classical RMS analysis commonly assumes that each task's relative deadline equals its period. This assumption is important when applying the utilization-bound test introduced later.

4. Working Principle of RMS

RMS assigns fixed priorities based on task periods. Once assigned, the priorities normally remain unchanged during operation.

Priority Assignment Rules

  1. Identify all periodic tasks.
  2. Determine the period of each task.
  3. Compare the task periods.
  4. Assign the highest priority to the shortest-period task.
  5. Assign lower priorities to longer-period tasks.
  6. Analyze whether all tasks can meet their deadlines.

Shorter period → Higher priority

5. RMS Numerical Example: Priority Assignment

Consider three periodic tasks with the following parameters:

Task Execution Time (C) Period (T)
Task A 1 ms 10 ms
Task B 2 ms 20 ms
Task C 5 ms 50 ms

Step 1: Compare Periods

Task A has the shortest period of 10 ms. Task B has a period of 20 ms, and Task C has the longest period of 50 ms.

Step 2: Assign Priorities

Task Period RMS Priority
Task A 10 ms Highest
Task B 20 ms Medium
Task C 50 ms Lowest

Step 3: Calculate Individual Utilization

The utilization of an individual periodic task is: 

U = C / T

Task A:

U1 = 1 / 10 = 0.10 = 10%

Task B:

U2 = 2 / 20 = 0.10 = 10%

Task C:

U3 = 5 / 50 = 0.10 = 10%

Step 4: Calculate Total CPU Utilization

Utotal = U1 + U2 + U3

       = 0.10 + 0.10 + 0.10

       = 0.30

       = 30%
Total CPU utilization is 30%. The task set satisfies the classical RMS utilization-bound sufficient test for three tasks.

6. CPU Utilization in RMS

CPU utilization represents the fraction of processor time required by periodic tasks.

Formula:

U = Σ (Ci / Ti)

Where:

  • Ci = Execution time of task i.
  • Ti = Period of task i.
  • U = Total CPU utilization.

Interpretation

Utilization Interpretation
0.30 or 30% Tasks require 30% of processor capacity under the model.
0.70 or 70% Tasks require 70% of processor capacity.
1.00 or 100% All modeled processor capacity is required.
Greater than 1.00 Required execution exceeds one processor's available capacity.
Utilization below 100% does not automatically prove that a fixed-priority task set is schedulable. Task periods, deadlines, execution times, blocking and interference must be considered.

7. RMS Schedulability Test

A classical sufficient schedulability bound for n independent periodic tasks under Rate Monotonic Scheduling is: 

U ≤ n (2^(1/n) - 1)

Where:

  • U = Total CPU utilization.
  • n = Number of periodic tasks.

If total utilization is at or below this bound, the task set is guaranteed schedulable under the classical RMS assumptions.

Utilization Bound for Different Task Counts

Number of Tasks (n) RMS Sufficient Utilization Bound
1 100%
2 Approximately 82.84%
3 Approximately 77.98%
4 Approximately 75.68%
5 Approximately 74.34%
10 Approximately 71.76%
As n approaches infinity Approximately 69.31%
The utilization bound is a sufficient test, not an exact maximum utilization for every task set. A task set exceeding the bound may still be schedulable.

8. Numerical Example: RMS Schedulability

Consider three periodic tasks:

Task Execution Time Period
T1 2 ms 10 ms
T2 3 ms 20 ms
T3 5 ms 50 ms

Step 1: Calculate Utilization

U1 = 2 / 10 = 0.20

U2 = 3 / 20 = 0.15

U3 = 5 / 50 = 0.10

Utotal = 0.20 + 0.15 + 0.10

       = 0.45

       = 45%

Step 2: Calculate RMS Bound

Ubound = n (2^(1/n) - 1)

       = 3 (2^(1/3) - 1)

       ≈ 0.7798

       ≈ 77.98%

Step 3: Compare

Actual utilization = 45%

RMS sufficient bound = 77.98%

45% ≤ 77.98%
Result: The task set passes the classical RMS sufficient utilization test, assuming the required model assumptions are satisfied.

9. Numerical Example: Utilization Bound Not Met

Suppose a three-task system has total utilization of 85%. 

Actual utilization = 85%

RMS sufficient bound for 3 tasks = 77.98%

85% > 77.98%

The task set fails the sufficient utilization-bound test. However, this does not prove that the task set is unschedulable. A more exact analysis, such as response-time analysis, is required.

Do not conclude that every task set above the RMS utilization bound misses a deadline. The bound is conservative.

10. Assumptions of Classical RMS

The classical RMS utilization-bound result is derived under specific assumptions.

  • Tasks are periodic.
  • Tasks are independent.
  • Task execution times are known and bounded.
  • Tasks execute on a single processor.
  • Scheduling is preemptive and fixed-priority.
  • Relative deadlines equal task periods.
  • Context-switch and scheduling overhead are ignored in the basic mathematical model.
  • There are no unmodeled blocking delays or resource-sharing interference.
Real embedded systems may contain shared resources, interrupts, release jitter, non-periodic activities and scheduling overhead. These effects must be included in a practical timing analysis.

11. RMS Scheduling Timeline

Consider two periodic tasks:

Task Execution Time Period Priority
T1 1 ms 4 ms Higher
T2 2 ms 8 ms Lower

Both tasks are released at time zero. T1 receives higher priority because its period is shorter.

Illustrative RMS Execution Timeline

T1 T2 T1 T2 T1

0–1   1–3   4–5   5–7   8–9 ms

T1 is released every 4 ms and receives CPU preference over T2 when both are Ready.

This timeline is an illustrative schedule for the stated execution and release assumptions. In a detailed schedule, idle intervals and every job's deadline should also be shown.

12. RMS and FreeRTOS

FreeRTOS supports fixed-priority task scheduling. An application can assign priorities according to the RMS principle by giving shorter-period tasks higher priorities.

Illustrative Priority Mapping

Task Period FreeRTOS Priority
Fast Monitoring Task 10 ms 3
Sensor Processing Task 20 ms 2
Display Update Task 100 ms 1
In FreeRTOS, a larger numerical value represents a higher task priority. The example priority values are illustrative and must be within the configured range.

Example: Periodic Task Structure

#include "FreeRTOS.h"
#include "task.h"

void Fast_Task(void *pvParameters)
{
    TickType_t lastWakeTime;

    lastWakeTime = xTaskGetTickCount();

    while (1)
    {
        /* Fast periodic processing */

        vTaskDelayUntil(
            &lastWakeTime,
            pdMS_TO_TICKS(10)
        );
    }
}

void Medium_Task(void *pvParameters)
{
    TickType_t lastWakeTime;

    lastWakeTime = xTaskGetTickCount();

    while (1)
    {
        /* Medium-rate processing */

        vTaskDelayUntil(
            &lastWakeTime,
            pdMS_TO_TICKS(20)
        );
    }
}

void Low_Task(void *pvParameters)
{
    TickType_t lastWakeTime;

    lastWakeTime = xTaskGetTickCount();

    while (1)
    {
        /* Slow periodic processing */

        vTaskDelayUntil(
            &lastWakeTime,
            pdMS_TO_TICKS(100)
        );
    }
}

vTaskDelayUntil() is useful for maintaining periodic task release timing relative to a previous wake time.

The task priorities must be assigned separately when creating these tasks. Their periods do not automatically determine FreeRTOS priorities.

Periodic delays alone do not prove RMS schedulability. The application must account for execution times, deadlines, blocking, interrupt interference, tick resolution and kernel overhead.

13. Advantages of RMS

  • Uses a simple fixed-priority assignment rule.
  • Short-period tasks receive higher scheduling priority.
  • Priorities do not need to change dynamically.
  • Provides a mathematical utilization-bound test.
  • Useful for periodic embedded control systems.
  • Can be implemented using priority-based RTOS schedulers.

14. Limitations of RMS

  • The classical utilization bound is conservative.
  • It is designed around periodic task models.
  • Independent task assumptions may not hold in real systems.
  • Shared resources can introduce blocking and priority inversion.
  • Non-periodic and sporadic tasks need additional analysis.
  • Different deadlines and periods require more careful analysis.
  • Interrupt and context-switch overhead can reduce available CPU time.

15. RMS vs Earliest Deadline First

Feature RMS EDF
Priority type Fixed priority Dynamic priority
Priority assignment Based on task period Based on nearest absolute deadline
Priority changes Normally fixed Can change as deadlines change
Analysis Classical utilization bound is sufficient but conservative Under ideal assumptions, utilization up to 100% is schedulable
Implementation Relatively simple fixed-priority assignment Requires dynamic deadline-based selection

RMS and EDF are important real-time scheduling algorithms. Their schedulability results depend on the task model and assumptions.

16. LPC2129 and Keil uVision Practical

The LPC2129 uses an ARM7TDMI-S single-core processor. RMS can be studied by modeling periodic tasks and assigning priorities according to their periods.

Suggested Simulator Exercise

  1. Define three periodic tasks with periods of 10 ms, 20 ms and 50 ms.
  2. Assign execution times of 1 ms, 2 ms and 5 ms.
  3. Assign the highest priority to the 10 ms task.
  4. Assign the lowest priority to the 50 ms task.
  5. Calculate total CPU utilization.
  6. Calculate the RMS utilization bound for three tasks.
  7. Compare actual utilization with the sufficient bound.
  8. Draw a scheduling timeline for the first 50 ms.
This is a scheduling-analysis exercise, not a claim that a compatible FreeRTOS port is running on LPC2129 in Keil uVision. Verify the exact ARM7 port and compiler support before attempting an actual FreeRTOS build.

17. Common Mistakes

  • Assigning higher priority to the task with the longer period.
  • Confusing execution time with task period.
  • Using total CPU utilization without considering task deadlines.
  • Treating the RMS utilization bound as an exact schedulability limit.
  • Assuming utilization below 100% always guarantees deadlines.
  • Ignoring blocking and interrupt interference.
  • Assuming FreeRTOS automatically assigns RMS priorities.
  • Assuming vTaskDelayUntil() guarantees exact physical execution timing.

18. Lesson Summary

  • RMS is a fixed-priority real-time scheduling algorithm.
  • Shorter-period tasks receive higher priority.
  • Periodic tasks execute at regular intervals.
  • Execution time, period and deadline are important timing parameters.
  • Total CPU utilization is the sum of each task's execution-time to period ratio.
  • The classical RMS sufficient utilization bound is n(2^(1/n) − 1).
  • The bound is sufficient, not necessary.
  • RMS analysis depends on specific assumptions.
  • FreeRTOS can implement RMS-style priority assignments through its fixed-priority scheduler.
  • Real systems require analysis of blocking, interrupts, overhead and worst-case execution times.
