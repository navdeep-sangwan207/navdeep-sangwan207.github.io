Lesson 09: Scheduling Latency and Overhead

1. Introduction

Scheduling latency and scheduling overhead are important performance parameters in a real-time operating system. They describe the delays and processor time associated with selecting and switching between tasks.

A real-time system must not only execute tasks correctly but also respond within specified timing requirements.

Important concept: A task can have a short execution time and still miss its deadline if it experiences excessive waiting, interrupt interference, blocking or scheduling overhead.

2. What Is Scheduling Latency?

Scheduling latency describes the delay between a scheduling event and the point at which the scheduler dispatches the appropriate Ready task.

Terminology varies between operating systems and textbooks. Therefore, a timing analysis should explicitly identify the start and end events being measured.

Example

Suppose a high-priority task becomes Ready at 10 ms, but it begins executing at 10.4 ms. 

Task Ready Time = 10 ms

Task Start Time = 10.4 ms

Scheduling Delay = 10.4 - 10

                 = 0.4 ms

The task experiences a scheduling delay of 0.4 ms under this measurement definition.

3. Types of Latency in RTOS

Latency Type Description
Interrupt Latency Time from an interrupt request becoming active to execution of the first instruction of its ISR.
Scheduling Latency Delay between a task becoming eligible for scheduling and the scheduler dispatching it, according to a clearly defined measurement boundary.
Dispatch Latency Delay associated with transferring CPU control to the selected task.
Context-Switch Latency Time spent saving the outgoing task context and restoring the incoming task context.
Task Response Time Time from a job's release or triggering event until that job completes.
These terms can overlap in different RTOS references. Do not add interrupt latency, dispatch latency and context-switch latency together unless their measurement intervals are defined to be separate.

4. What Is Interrupt Latency?

Interrupt latency is the time between an interrupt request being asserted and the processor beginning execution of the corresponding interrupt service routine.

Factors Affecting Interrupt Latency

  • Interrupt masking and disabled interrupt periods.
  • Higher-priority interrupt activity.
  • Processor exception-entry overhead.
  • Current processor instruction and architecture behavior.
  • Interrupt-controller or vector-dispatch behavior.
  • Memory and bus wait states.

Example

Interrupt Request = 5.000 ms

ISR Starts         = 5.020 ms

Interrupt Latency  = 0.020 ms

                   = 20 microseconds
Interrupt latency is not the same as task response time. The ISR may execute, wake a task and request a context switch before that task starts.

5. What Is Context Switching?

Context switching is the process of saving the execution state of one task and restoring the execution state of another task.

Context Information

  • CPU general-purpose registers.
  • Stack pointer.
  • Program counter or return address.
  • Processor status information.
  • Other architecture- or port-specific state.

Context-Switch Sequence

  1. The currently running task is interrupted or reaches a scheduling point.
  2. The processor or RTOS port saves the outgoing task context.
  3. The scheduler selects another eligible task.
  4. The incoming task context is restored.
  5. Execution resumes from the incoming task's saved state.

Context-Switch Flow

Task A Running

↓ Save Task A Context

Scheduler Selects Task B

↓ Restore Task B Context

Task B Running

6. What Is Context-Switch Overhead?

Context-switch overhead is the processor time consumed by the operations required to switch between tasks rather than performing their application work.

It may include context save and restore operations, scheduler execution, dispatch operations and other port-specific processing.

Example

Context Save Time    = 3 microseconds

Scheduler Time       = 2 microseconds

Context Restore Time = 3 microseconds

Total Overhead       = 3 + 2 + 3

                     = 8 microseconds
The illustrative context-switch overhead is 8 microseconds.

Actual overhead depends on processor architecture, compiler, RTOS implementation, memory system and the particular task-switch path.

7. Factors Affecting Scheduling Latency

Factor Effect
Interrupt Masking Can delay interrupt handling and task wake-up.
Higher-Priority Interrupts Can delay lower-priority interrupt and task processing.
Critical Sections Can delay preemption or interrupt servicing, depending on the implementation.
Scheduler Suspension Can postpone task scheduling decisions until resumed.
Context Switching Consumes CPU time during task transitions.
Task Blocking Can delay a task while it waits for a resource or event.
Resource Contention Can make a task wait for a mutex or shared resource.
Memory and Bus Wait States Can increase instruction and data access time.

8. Scheduling Overhead

Scheduling overhead is the processor time used by the scheduling mechanism and associated kernel operations.

Examples of Scheduling Overhead

  • Task selection and priority-list management.
  • Task context saving and restoring.
  • Scheduler execution.
  • Tick interrupt processing.
  • Task creation and deletion operations.
  • Inter-task communication and synchronization processing.

Scheduling Overhead Percentage

Overhead Percentage = (Overhead Time / Total Time) × 100

Suppose the scheduler and context-switch operations consume 2 ms during a 100 ms observation interval. 

Overhead Percentage = (2 / 100) × 100

                    = 2%

Therefore, the measured scheduling overhead is 2% for that observation interval.

9. Numerical Example: Task Scheduling Delay

Consider a task that becomes Ready at 20 ms.

Timing Component Duration
Interrupt recognition and entry 10 microseconds
ISR processing before task wake-up 15 microseconds
Scheduler and dispatch processing 5 microseconds
Context restoration 8 microseconds

Step 1: Add the Separate Timing Components

Total Delay = 10 + 15 + 5 + 8

            = 38 microseconds

Step 2: Determine Task Start Time

Task Ready Time = 20 ms

Total Delay = 38 microseconds

Task Start Time = 20.038 ms
This calculation assumes the listed intervals are sequential, non-overlapping and measured from the interrupt request through the first instruction of the awakened task.

10. Relationship Between Latency and Response Time

Task response time measures the total time between a job's release and completion. 

Response Time = Completion Time - Release Time

It can include several components:

  • Initial release and scheduling delay.
  • Execution time of the task.
  • Waiting for higher-priority tasks.
  • Resource blocking.
  • Interrupt interference.
  • Preemption and resumption overhead.

Example

Task Release Time = 10 ms

Task Start Time   = 10.2 ms

Task Completion   = 14.2 ms

Response Time     = 14.2 - 10

                  = 4.2 ms

The task's execution interval is 4 ms, but its response time is 4.2 ms because it also experiences 0.2 ms of initial delay.

11. Scheduling Latency and Jitter

Jitter is the variation in timing between repeated events or executions.

In periodic task systems, release jitter describes variation in the actual release time relative to the intended release time. Response-time jitter can describe variation in task completion or response times.

Example

Task Instance Actual Start Time Intended Start Time Start-Time Error
1 10.1 ms 10 ms 0.1 ms
2 20.3 ms 20 ms 0.3 ms
3 30.2 ms 30 ms 0.2 ms

The measured start-time error varies across the three task instances.

Jitter and latency are related but different. Latency describes a delay; jitter describes variation in timing.

12. Tick Interrupt and Scheduling Overhead

Many RTOS implementations use a periodic system tick interrupt to maintain kernel time and support time-based operations.

Each tick may cause the kernel to update delay counters, timeout states and scheduling information.

A higher tick frequency can improve time resolution, but it may also increase the frequency of tick-related processor overhead.

Tick Period Formula

Tick Period = 1 / Tick Frequency

Example

Tick Frequency = 1000 Hz

Tick Period = 1 / 1000

            = 0.001 seconds

            = 1 ms
Tick Frequency Nominal Tick Period
100 Hz 10 ms
250 Hz 4 ms
500 Hz 2 ms
1000 Hz 1 ms
A tick interrupt does not necessarily cause a context switch. The scheduler switches tasks only when its scheduling rules and execution state require it.

13. Effect of Interrupt Service Routines

Interrupt service routines execute in response to hardware or software interrupt events. Their execution consumes processor time that is not available to normal task execution.

Long ISR Problems

  • Increases the time before other tasks can execute.
  • Can delay lower-priority interrupt processing.
  • Can increase task response time.
  • Can increase timing jitter.
  • May cause deadline misses in heavily loaded systems.

Recommended ISR Design

  1. Keep interrupt service routines short.
  2. Read or acknowledge the relevant hardware condition.
  3. Capture essential data.
  4. Notify a task or place data into a suitable buffer.
  5. Perform lengthy processing in task context.
In FreeRTOS, use only documented ISR-safe APIs from interrupt context. The exact API and yield mechanism depend on the selected port.

14. Methods to Reduce Scheduling Latency

Technique Purpose
Short ISRs Reduce interrupt interference.
Short Critical Sections Reduce periods during which preemption or interrupts may be restricted.
Appropriate Task Priorities Ensure time-critical tasks receive suitable priority.
Efficient Context Switching Reduce time spent saving and restoring task state.
Efficient Scheduler Configuration Avoid unnecessary scheduling and tick overhead.
Suitable Synchronization Reduce unnecessary blocking and resource contention.
WCET Analysis Estimate execution-time bounds under defined assumptions.
Profiling and Measurement Identify actual timing bottlenecks.

15. Timing Measurement Techniques

Scheduling performance should be measured using a suitable hardware or software timing source.

Common Techniques

  • Hardware timer counters.
  • Processor cycle counters, where available.
  • GPIO timing measurements with an oscilloscope or logic analyzer.
  • RTOS trace tools.
  • Timestamp logging.
  • Execution-time profiling.

Measurement Considerations

  • Define the exact start and end events.
  • Measure multiple executions under different system loads.
  • Account for timer resolution and measurement overhead.
  • Distinguish average, maximum observed and proven worst-case time.
  • Repeat measurements with relevant interrupt and task interference.
The largest measured execution or latency value is not automatically a proven worst-case execution time or worst-case latency bound.

16. LPC2129 and Keil uVision Practical

The LPC2129 uses an ARM7TDMI-S processor. Its timer and interrupt facilities can be studied to understand timing behavior.

Timer Configuration Example

Consider the following clock configuration:

  • Peripheral clock (PCLK) = 15 MHz.
  • Timer prescaler register PR = 14999.

The timer counter increments once for every PR + 1 peripheral clock cycles. 

Timer Counter Frequency = PCLK / (PR + 1)

                        = 15,000,000 / 15,000

                        = 1000 Hz

Timer Counter Period    = 1 / 1000

                        = 1 ms

If the timer is configured to generate a match event at the appropriate count and reset on match, it can provide a nominal 1 ms timing interval.

Suggested Exercise

  1. Configure Timer0 with a 1 ms counter increment.
  2. Configure a suitable match event.
  3. Inspect the timer counter and interrupt flags in Keil.
  4. Record the timing of the interrupt event.
  5. Compare the intended interval with the simulator-observed interval.
  6. Discuss the effect of interrupt processing and software overhead.
Keil uVision simulator measurements demonstrate the modeled execution behavior. They do not automatically establish physical hardware timing, electrical behavior or a worst-case timing guarantee.

17. Common Mistakes

  • Confusing interrupt latency with task response time.
  • Assuming every tick interrupt causes a task switch.
  • Ignoring context-switch overhead.
  • Writing long interrupt service routines.
  • Keeping interrupts disabled for excessive periods.
  • Ignoring resource blocking and higher-priority interference.
  • Using average timing as a guaranteed worst-case bound.
  • Measuring latency without defining its start and end events.

18. Lesson Summary

  • Scheduling latency is a delay associated with task dispatch.
  • Interrupt latency is the time from interrupt request assertion to ISR execution.
  • Context switching saves and restores task execution state.
  • Scheduling overhead consumes processor time for kernel and scheduling operations.
  • Task response time includes waiting, interference, execution and relevant overhead.
  • Jitter describes variation in timing.
  • Tick frequency influences time resolution and tick-related overhead.
  • Short ISRs and critical sections help reduce timing delays.
  • Timing measurements must be interpreted within their measurement conditions and assumptions.
