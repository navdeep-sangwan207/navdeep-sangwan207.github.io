Lesson 5: Accessible Forms

Chapter 14: HTML Accessibility

Learn how to design accessible HTML forms using labels, fieldsets, legends, instructions, validation messages and appropriate form controls.

1. Introduction to Accessible Forms

HTML forms allow users to enter and submit information through a website. Examples include login forms, registration forms, contact forms, search forms and feedback forms.

An accessible form ensures that users, including people with disabilities, can understand each control, enter information and correct errors.

Why Are Accessible Forms Important?

  • Help screen reader users identify form controls.
  • Support keyboard-only navigation.
  • Make forms easier to understand and complete.
  • Provide clear instructions and error messages.
  • Reduce mistakes during data entry.
  • Improve usability across different devices.
An accessible form requires more than correctly displaying input fields. Each control needs a meaningful accessible name, understandable instructions and usable error handling.

2. Using the Label Element

The HTML <label> element provides a visible description for a form control. It helps users understand what information they should enter.

Example

<label for="username"> Username: </label> <input type="text" id="username" name="username">

The for attribute of the label must match the id of the associated form control.

How It Works

  • The label contains the visible text.
  • The input has a unique id.
  • The label's for attribute references that id.
  • The browser associates the label with the input.

Alternative: Wrapping the Input

<label> Email Address: <input type="email" name="email"> </label>

A label can also be associated with a control by containing that control.

Prefer explicit for/id association in complex forms because it makes the relationship easy to identify and maintain.

3. Accessible Text Input Fields

Text inputs should have meaningful labels that describe the information expected from the user.

Example: Registration Form

<form> <label for="full-name"> Full Name: </label> <input type="text" id="full-name" name="full-name"> <br><br> <label for="email"> Email Address: </label> <input type="email" id="email" name="email"> </form>

Important Practices

  • Provide a visible label for each input.
  • Use unique id values.
  • Associate labels correctly.
  • Use suitable input types.
  • Do not depend only on placeholder text.

4. Placeholder Text vs Label

The placeholder attribute displays temporary hint text inside an input field. It is not a replacement for a proper label.

Incorrect Practice

<input type="email" placeholder="Enter your email">

Correct Practice

<label for="email"> Email Address: </label> <input type="email" id="email" name="email" placeholder="example@email.com">
Label Placeholder
Identifies the purpose of the control. Provides a temporary hint.
Normally remains visible. Usually disappears or changes when the user enters text.
Should be provided for form controls. Optional.
Placeholder text may have limited contrast and can disappear during data entry. Always provide a proper label.

5. Grouping Form Controls with Fieldset and Legend

The <fieldset> element groups related form controls. The <legend> element provides a caption for that group.

Example: Personal Information

<form> <fieldset> <legend>Personal Information</legend> <label for="name">Name:</label> <input type="text" id="name" name="name"> <br><br> <label for="email">Email:</label> <input type="email" id="email" name="email"> </fieldset> </form>

Example: Radio Button Group

<fieldset> <legend>Select Your Preferred Course</legend> <input type="radio" id="html" name="course" value="html"> <label for="html">HTML5</label> <br> <input type="radio" id="cpp" name="course" value="cpp"> <label for="cpp">C++ Programming</label> </fieldset>

The legend provides context for the group, while each radio button has its own label.

Use fieldset and legend when controls form a meaningful group, especially radio buttons and related checkboxes.

6. Accessible Radio Buttons and Checkboxes

Radio buttons allow users to select one option from a group. Checkboxes allow users to select one or more independent options.

Accessible Radio Buttons

<fieldset> <legend>Select Your Learning Mode</legend> <input type="radio" id="online" name="mode" value="online"> <label for="online">Online</label> <br> <input type="radio" id="offline" name="mode" value="offline"> <label for="offline">Offline</label> </fieldset>

Accessible Checkboxes

<fieldset> <legend>Select Your Interests</legend> <input type="checkbox" id="embedded" name="interests" value="embedded"> <label for="embedded"> Embedded Systems </label> <br> <input type="checkbox" id="linux" name="interests" value="linux"> <label for="linux"> Linux Programming </label> </fieldset>
Radio Button Checkbox
Usually selects one option from a group. Allows multiple independent selections.
Options in a group share the same name. Related controls may share a name.
Arrow keys commonly navigate options. Space toggles the focused checkbox.

7. Accessible Select Menus

A select element allows users to choose an option from a list. It should have an associated label.

Example

<label for="technology"> Select a Technology: </label> <select id="technology" name="technology"> <option value="">Choose an option</option> <option value="html">HTML5</option> <option value="css">CSS3</option> <option value="javascript">JavaScript</option> </select>

Using Optgroup

<label for="course"> Select a Course: </label> <select id="course" name="course"> <optgroup label="Programming"> <option value="cpp">C++</option> <option value="c">C Programming</option> </optgroup> <optgroup label="Web Development"> <option value="html">HTML5</option> <option value="javascript">JavaScript</option> </optgroup> </select>

The optgroup element organizes related options under meaningful group labels.

8. Accessible Textareas

A textarea allows users to enter multi-line text. It should have an associated label.

Example

<label for="feedback"> Enter Your Feedback: </label> <textarea id="feedback" name="feedback" rows="5" cols="40"></textarea>

The label identifies the purpose of the text area, while rows and cols define its initial visible dimensions.

9. Providing Instructions for Form Fields

Some form fields require additional instructions. For example, a password may need a minimum length, or a phone number may require a specific format.

Example

<label for="password"> Password: </label> <p id="password-help"> Use at least 8 characters. </p> <input type="password" id="password" name="password" aria-describedby="password-help">

The aria-describedby attribute connects the input to additional descriptive text.

Another Example: Phone Number

<label for="phone"> Mobile Number: </label> <p id="phone-help"> Enter a 10-digit mobile number. </p> <input type="tel" id="phone" name="phone" aria-describedby="phone-help">
Use visible instructions wherever possible. aria-describedby is useful for connecting additional instructions to a control.

10. Required Fields and Indicating Mandatory Information

Some form fields must be completed before a form can be submitted. HTML provides the required attribute for this purpose.

Example

<label for="email"> Email Address (required): </label> <input type="email" id="email" name="email" required>

The required attribute enables the browser's built-in constraint validation for supported form controls.

Indicating Required Fields

<p>Fields marked as required must be completed.</p> <label for="name"> Name <span aria-hidden="true">*</span> <span class="visually-hidden">(required)</span> </label> <input type="text" id="name" name="name" required>
If an asterisk indicates a required field, explain its meaning to users. Do not rely on color or an unexplained symbol alone.

11. Accessible Form Validation

Form validation checks whether the entered information meets specified requirements. HTML provides built-in validation features such as required, type, minlength, maxlength, min, max and pattern.

Example

<form> <label for="email">Email Address:</label> <input type="email" id="email" name="email" required> <label for="age">Age:</label> <input type="number" id="age" name="age" min="18" max="100" required> <button type="submit">Submit</button> </form>

The browser can prevent submission when the entered values do not satisfy the specified constraints.

Accessible Error Messages

Error messages should explain what went wrong and how the user can correct it.

<label for="username"> Username: </label> <input type="text" id="username" name="username" aria-invalid="true" aria-describedby="username-error"> <p id="username-error"> Username is required. Enter a username. </p>

Important Validation Practices

  • Identify the field containing an error.
  • Explain the problem in clear language.
  • Provide instructions for correction.
  • Do not communicate errors through color alone.
  • Associate error messages with the relevant controls.
  • Make important validation feedback available to assistive technologies.
aria-invalid should reflect the actual validation state. Do not mark a field invalid before it has been checked unless the form's interaction design requires it.

12. Accessible Error Notifications

Dynamic error messages may appear after users submit a form or change a field. Assistive technologies should be able to identify important updates.

Using role="alert"

<div role="alert"> Error: Please enter a valid email address. </div>

The alert role communicates an important, time-sensitive message and is generally announced by assistive technologies when inserted or updated.

Using aria-live

<p id="form-status" aria-live="polite"></p> <script> document.getElementById("form-status").textContent = "Your form has been submitted."; </script>

The aria-live attribute identifies a region whose content may change dynamically.

Attribute / Role Purpose
role="alert" Communicates an important message that generally requires immediate attention.
aria-live="polite" Announces updates when the user is not being interrupted.
aria-live="assertive" Requests an immediate announcement and should be used sparingly.
aria-describedby Connects descriptive information to a control.
aria-invalid Indicates that the current value does not satisfy validation requirements.

13. Accessible Form Design with CSS

CSS can improve the visual presentation of forms. However, visual styling must not remove important accessibility features.

Example

form { max-width: 500px; margin: 20px auto; } label { display: block; margin-bottom: 6px; font-weight: bold; } input, select, textarea { width: 100%; padding: 10px; margin-bottom: 18px; border: 1px solid #777; border-radius: 5px; font-size: 16px; } input:focus-visible, select:focus-visible, textarea:focus-visible, button:focus-visible { outline: 3px solid #e76f00; outline-offset: 3px; } button { background: #174ea6; color: white; padding: 12px 20px; border: none; border-radius: 5px; cursor: pointer; } button:hover { background: #2878d0; }

CSS Accessibility Practices

  • Use readable font sizes.
  • Maintain sufficient text and control contrast.
  • Provide visible focus indicators.
  • Do not remove browser focus outlines without replacement.
  • Provide sufficient spacing between controls.
  • Ensure forms work at different screen sizes.

14. Complete Example: Accessible Registration Form

This example combines labels, fieldsets, legends, instructions, required fields, validation and accessible error feedback.

Complete HTML Code

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <meta name="viewport" content="width=device-width, initial-scale=1.0"> <title>Accessible Registration Form</title> <style> body { font-family: Arial, sans-serif; background: #f4f7fb; padding: 20px; } form { max-width: 550px; margin: auto; background: white; padding: 25px; border-radius: 10px; } label { display: block; margin-top: 15px; font-weight: bold; } input, select { width: 100%; padding: 10px; margin-top: 6px; box-sizing: border-box; } fieldset { margin-top: 20px; padding: 15px; } fieldset label { display: inline; font-weight: normal; } button { margin-top: 20px; padding: 12px 20px; background: #174ea6; color: white; border: 0; cursor: pointer; } :focus-visible { outline: 3px solid #e76f00; outline-offset: 3px; } #status { margin-top: 15px; } </style> </head> <body> <form id="registrationForm"> <h1>Course Registration</h1> <p> Fields marked as required must be completed. </p> <label for="name"> Full Name (required): </label> <input type="text" id="name" name="name" autocomplete="name" required> <label for="email"> Email Address (required): </label> <input type="email" id="email" name="email" autocomplete="email" required> <label for="phone"> Mobile Number: </label> <input type="tel" id="phone" name="phone" autocomplete="tel"> <fieldset> <legend>Select Learning Mode</legend> <input type="radio" id="online" name="mode" value="online" required> <label for="online">Online</label> <br> <input type="radio" id="offline" name="mode" value="offline"> <label for="offline">Offline</label> </fieldset> <label for="course"> Select Course: </label> <select id="course" name="course" required> <option value="">Choose a course</option> <option value="html5">HTML5</option> <option value="cpp">C++ Programming</option> <option value="linux">Linux</option> </select> <fieldset> <legend>Interests</legend> <input type="checkbox" id="embedded" name="interest" value="embedded"> <label for="embedded"> Embedded Systems </label> <br> <input type="checkbox" id="web" name="interest" value="web"> <label for="web"> Web Development </label> </fieldset> <button type="submit"> Register </button> <p id="status" aria-live="polite"></p> </form> <script> const form = document.getElementById("registrationForm"); const status = document.getElementById("status"); form.addEventListener("submit", function(event) { event.preventDefault(); if (!form.checkValidity()) { form.reportValidity(); return; } status.textContent = "Registration form completed successfully."; }); </script> </body> </html>

Expected Result

  • A registration form with a clear heading.
  • Visible labels for name, email, phone and course.
  • Radio buttons grouped under a legend.
  • Checkboxes grouped under a legend.
  • Required fields with browser validation.
  • A keyboard-visible focus indicator.
  • A status message announced through a live region.
This is a front-end demonstration. It does not store or transmit registration data. A real registration system needs a secure server-side endpoint and server-side validation.

15. Common Accessibility Mistakes in Forms

Mistake Correct Practice
Missing labels. Provide visible labels for controls.
Using placeholders as labels. Use a label element and optional placeholder hints.
Using the same id for multiple controls. Give every id a unique value.
Unclear instructions. Provide concise, understandable instructions.
Unexplained required-field symbols. Explain what the symbol means.
Radio buttons without group context. Use fieldset and legend where appropriate.
Error messages communicated only by color. Provide clear text-based error messages.
Removing focus indicators. Maintain visible keyboard focus.
Using only client-side validation for security. Validate data on the server as well.

17. Interview Questions and Answers

Q1. What is an accessible form?
A form that can be understood and operated by users with different abilities, including users of assistive technologies.
Q2. What is the purpose of the label element?
It provides a visible description for a form control and can associate with the control using for and id.
Q3. Why should placeholder not replace label?
Placeholder text may disappear during entry and does not provide the same persistent visible identification as a label.
Q4. What is the purpose of fieldset?
It groups related form controls.
Q5. What is the purpose of legend?
It provides a caption or name for a fieldset group.
Q6. What is the difference between radio buttons and checkboxes?
Radio buttons generally allow one selection from a group, while checkboxes allow independent multiple selections.
Q7. What does the required attribute do?
It indicates that a control must contain a value before the form can pass the browser's constraint validation.
Q8. What is aria-describedby?
It associates an element with one or more elements that provide additional descriptive information.
Q9. What is aria-invalid?
It indicates that the current value of a form control does not satisfy validation requirements.
Q10. What is role="alert"?
It identifies an important message that should generally be announced promptly by assistive technologies.
Q11. What is aria-live?
It identifies a region where dynamic content updates can be announced by assistive technologies.
Q12. What is HTML constraint validation?
It is the browser's built-in mechanism for checking form controls against constraints such as required, type, min, max and pattern.
Q13. Why are visible error messages important?
They explain what went wrong and help users understand how to correct their input.
Q14. Is client-side validation sufficient for security?
No. Client-side validation can be bypassed. Server-side validation is also necessary.
Q15. Which WCAG principle is related to accessible forms?
All four POUR principles can apply. Understandable is particularly relevant to clear labels, instructions and error identification; Operable is relevant to keyboard access.

  4. section

  2. href

  4. alt

  3. nav

  2. legend
  3. summary
  4. figcaption
Answer: B — legend
5. Which attribute makes a form control mandatory?
