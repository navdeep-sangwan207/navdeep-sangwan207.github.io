Lesson 6: ARIA Attributes Introduction

Chapter 14: HTML Accessibility

Learn how Accessible Rich Internet Applications (ARIA) attributes improve the accessibility of web content and interactive components.

1. Introduction to ARIA

ARIA stands for Accessible Rich Internet Applications. It is a set of attributes that provides additional accessibility information to assistive technologies, such as screen readers.

ARIA helps communicate the role, name, state and properties of interface elements when native HTML alone does not provide sufficient information.

Why Is ARIA Required?

  • To provide accessible names for interface elements.
  • To communicate the state of interactive controls.
  • To identify the purpose of custom interface components.
  • To describe relationships between interface elements.
  • To communicate dynamic content updates.
  • To improve accessibility of complex web applications.
ARIA does not automatically make an element keyboard accessible or provide its interaction behavior. Developers must implement appropriate keyboard support and functionality.

2. What Is WAI-ARIA?

WAI-ARIA is a technical specification developed by the W3C Web Accessibility Initiative. It defines roles, states and properties that help assistive technologies interpret web interfaces.

WAI-ARIA Components

  1. Roles: Identify what an element represents.
  2. States: Describe the current condition of an element.
  3. Properties: Provide additional information and relationships.

Example

<button type="button" aria-expanded="false" aria-controls="menu"> Open Menu </button> <nav id="menu" hidden> <a href="index.html">Home</a> <a href="about.html">About</a> </nav>

In this example, aria-expanded communicates whether the controlled menu is expanded, while aria-controls identifies the controlled element.

3. ARIA Roles

An ARIA role identifies the purpose or type of an element. It helps assistive technologies understand what an interface component represents.

Common ARIA Roles

Role Purpose
button Identifies an element as a button.
navigation Identifies a navigation landmark.
main Identifies the main content landmark.
banner Identifies a page-level banner landmark.
complementary Identifies supporting content.
search Identifies a search landmark.
alert Identifies an important message.
dialog Identifies a dialog component.
tab Identifies an item in a tab interface.
tabpanel Identifies the content panel associated with a tab.

Example: Navigation Role

<div role="navigation" aria-label="Main navigation"> <a href="index.html">Home</a> <a href="courses.html">Courses</a> <a href="about.html">About</a> </div>

The role identifies the element as navigation. The aria-label provides a name for this navigation region.

Prefer native semantic HTML elements when available. For example, use <nav> instead of <div role="navigation">, and use <button> instead of a generic element with role="button".

4. ARIA Accessible Names

An accessible name identifies an interface element to assistive technologies. It communicates what the element is called or what action it performs.

Using aria-label

The aria-label attribute provides an accessible name directly as a text value.

<button type="button" aria-label="Close dialog"> &times; </button>

The button has a visible multiplication sign, while its accessible name is "Close dialog".

Using aria-labelledby

The aria-labelledby attribute references another element that provides the accessible name.

<h2 id="search-heading"> Search Courses </h2> <form aria-labelledby="search-heading"> <label for="search">Course Name:</label> <input type="search" id="search" name="q"> <button type="submit">Search</button> </form>

aria-label vs aria-labelledby

aria-label aria-labelledby
Provides the name directly as text. References another element or elements by id.
Does not require a separate visible text element. Can reuse visible text already present on the page.
Useful for icon-only controls. Useful when a visible heading or label already exists.
Do not add aria-label unnecessarily when a native visible label already provides the correct accessible name. The accessible name should be concise and meaningful.

5. ARIA States and Properties

ARIA states and properties communicate additional information about interface elements. Some describe changing conditions, while others describe relationships or characteristics.

Common ARIA Attributes

Attribute Purpose
aria-expanded Indicates whether a controlled component is expanded or collapsed.
aria-hidden Controls whether an element is exposed in the accessibility tree.
aria-disabled Communicates that an element is disabled.
aria-checked Communicates the checked state of supported controls.
aria-selected Communicates the selected state of supported items.
aria-pressed Communicates the pressed state of a toggle button.
aria-required Communicates that a control is required.
aria-invalid Indicates that a value does not satisfy validation.
aria-describedby References additional descriptive information.
aria-controls Identifies an element controlled by the current element.

Example: aria-expanded

<button aria-expanded="false" aria-controls="details"> Show Details </button> <div id="details" hidden> Additional information is displayed here. </div>

When the panel is opened, the value of aria-expanded should be updated to true, and the hidden attribute should be removed.

Example: aria-pressed

<button type="button" aria-pressed="false"> Bold Mode </button>

This attribute is useful for toggle buttons that can remain in either a pressed or unpressed state.

Example: aria-disabled

<div role="button" aria-disabled="true" tabindex="0"> Unavailable Action </div>
aria-disabled communicates a disabled state but does not automatically disable interaction. Developers must implement the appropriate behavior. For native buttons, prefer the disabled attribute when the control should actually be disabled.

6. aria-hidden Attribute

The aria-hidden attribute controls whether an element is exposed to assistive technologies.

Example

<p> Welcome to NS Learning Hub. <span aria-hidden="true">★</span> </p>

The decorative star is hidden from the accessibility tree, while the text remains available to assistive technologies.

Possible Values

  • true – hides the element from the accessibility tree.
  • false – exposes the element, subject to other accessibility rules.
Never apply aria-hidden="true" to a focusable element or an ancestor of a currently focusable element. This can create a confusing experience for keyboard users. Also, aria-hidden does not visually hide content from sighted users.

7. aria-describedby Attribute

aria-describedby connects an element to additional descriptive text. It is especially useful for form instructions, help text and error messages.

Example

<label for="password"> Password: </label> <input type="password" id="password" aria-describedby="password-help"> <p id="password-help"> Password must contain at least 8 characters. </p>

The description provides additional information about the password field.

8. aria-controls Attribute

aria-controls identifies another element whose content or behavior is controlled by the current element.

Example

<button type="button" aria-controls="course-menu" aria-expanded="false"> Courses </button> <div id="course-menu" hidden> <a href="html5/index.html">HTML5</a> <a href="cpp/index.html">C++</a> </div>

The button controls the course menu. aria-controls communicates this relationship.

9. Live Regions: aria-live

Live regions allow assistive technologies to receive information about content that changes dynamically without requiring the user to move focus to that content.

aria-live Values

Value Behavior
off Does not request live announcements by default.
polite Requests announcement when the user is not being interrupted.
assertive Requests an immediate announcement and may interrupt current speech.

Example

<p id="message" aria-live="polite"></p> <button type="button" onclick="showMessage()"> Show Message </button> <script> function showMessage() { document.getElementById("message").textContent = "Your changes have been saved."; } </script>

When the button is clicked, JavaScript updates the live region. Assistive technologies can announce the new message.

Use aria-live="polite" for ordinary status updates. Reserve assertive announcements for genuinely urgent information.

10. ARIA Landmarks

Landmark roles help screen reader users navigate important sections of a web page.

Common Landmark Roles

Landmark Role Native HTML Equivalent
banner Page-level header
navigation <nav>
main <main>
contentinfo Page-level footer
complementary <aside>
search <search>
region A named section with an appropriate accessible name

Example

<header> <h1>NS Learning Hub</h1> </header> <nav aria-label="Main navigation"> <a href="index.html">Home</a> <a href="courses.html">Courses</a> </nav> <main> <h2>Available Courses</h2> <p>Explore our learning resources.</p> </main> <footer> <p>Learning and Practice Portal</p> </footer>

Native semantic elements already provide the corresponding landmark semantics. Additional ARIA landmark roles are usually unnecessary in this example.

11. ARIA in Custom Interactive Components

Modern web applications often contain custom components such as dropdown menus, tabs, accordions, dialogs and toggle buttons. ARIA can communicate their roles and states.

Example: Accessible Accordion

<h2> <button type="button" aria-expanded="false" aria-controls="panel1" id="heading1"> What is HTML5? </button> </h2> <div id="panel1" aria-labelledby="heading1" hidden> HTML5 is the modern evolution of HTML used to structure web content. </div>

The button communicates its expanded state and identifies the controlled panel. JavaScript must update the state and visibility when the user activates the button.

Example: Toggle Button

<button type="button" aria-pressed="false"> Enable Notifications </button>

The aria-pressed value should change when the toggle button changes state.

12. The First Rule of ARIA

The first rule of ARIA is:

If you can use a native HTML element or attribute that already provides the required semantics and behavior, prefer using it instead of adding ARIA.

Incorrect Example

<div role="button" tabindex="0"> Submit </div>

This creates a button-like role but does not automatically provide native button keyboard behavior or activation.

Correct Example

<button type="submit"> Submit </button>

The native button provides built-in semantics, keyboard operation and activation behavior.

13. Common ARIA Mistakes

Mistake Correct Practice
Using ARIA when native HTML is sufficient. Prefer semantic HTML elements.
Adding role="button" without keyboard support. Use a native button whenever possible.
Using aria-label unnecessarily. Prefer an existing visible label.
Not updating aria-expanded. Keep the state synchronized with the actual interface.
Hiding focusable elements with aria-hidden. Do not hide interactive content from assistive technologies.
Using aria-disabled without disabling behavior. Implement the required interaction restrictions.
Using too many assertive live announcements. Use polite announcements for routine updates.
Assuming ARIA provides keyboard interaction. Implement and test keyboard behavior separately.

14. Complete Example: Accessible Dropdown Menu

This example demonstrates a button that opens and closes a navigation menu. JavaScript updates the hidden state and aria-expanded attribute together.

Complete HTML Code

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <meta name="viewport" content="width=device-width, initial-scale=1.0"> <title>Accessible Dropdown Menu</title> <style> body { font-family: Arial, sans-serif; padding: 30px; } button { background: #174ea6; color: white; padding: 12px 18px; border: none; cursor: pointer; } nav { margin-top: 10px; padding: 15px; background: #f0f7ff; max-width: 250px; } nav a { display: block; padding: 8px; } :focus-visible { outline: 3px solid #e76f00; outline-offset: 3px; } [hidden] { display: none !important; } </style> </head> <body> <h1>NS Learning Hub</h1> <button type="button" id="menuButton" aria-expanded="false" aria-controls="courseMenu"> Courses </button> <nav id="courseMenu" aria-label="Course menu" hidden> <a href="../html5/index.html">HTML5</a> <a href="../cpp/index.html">C++ Programming</a> <a href="../linux/index.html">Linux</a> </nav> <script> const menuButton = document.getElementById("menuButton"); const courseMenu = document.getElementById("courseMenu"); menuButton.addEventListener("click", function() { const isExpanded = menuButton.getAttribute("aria-expanded") === "true"; menuButton.setAttribute( "aria-expanded", String(!isExpanded) ); courseMenu.hidden = isExpanded; }); </script> </body> </html>

Expected Result

  • A Courses button appears on the page.
  • Initially, the navigation menu is hidden.
  • Clicking the button opens the menu.
  • aria-expanded changes from false to true.
  • Clicking again closes the menu.
  • aria-expanded changes back to false.
  • The button can be operated using the keyboard.
This is a simple disclosure navigation example, not a full ARIA application menu. Ordinary website navigation generally works best with standard links inside a nav element. A complete menu design may also need additional focus management and dismissal behavior.

15. Testing ARIA Accessibility

ARIA should be tested with actual assistive technologies and keyboard interaction. Correct attributes in source code do not guarantee a usable interface.

Testing Methods

  1. Inspect the HTML source and accessibility tree.
  2. Navigate using the Tab and Shift+Tab keys.
  3. Operate buttons and controls using the keyboard.
  4. Test with screen readers.
  5. Check accessible names and control states.
  6. Verify that dynamic announcements are understandable.
  7. Test at different screen sizes and zoom levels.

Common Accessibility Testing Tools

  • NVDA – Windows screen reader.
  • JAWS – Windows screen reader.
  • VoiceOver – Apple screen reader.
  • TalkBack – Android screen reader.
  • Accessibility Inspector – Browser developer tools.
  • axe DevTools – Automated accessibility testing.
Automated tools can identify many issues, but they cannot replace manual keyboard and screen reader testing.

17. Interview Questions and Answers

Q1. What is ARIA?
ARIA is a set of accessibility attributes that communicates roles, states and properties of web interface components to assistive technologies.
Q2. What is the full form of WAI-ARIA?
Web Accessibility Initiative – Accessible Rich Internet Applications.
Q3. What are ARIA roles?
Roles identify the type or purpose of an interface element, such as button, navigation, dialog or alert.
Q4. What is aria-label?
It provides an accessible name directly as a text value.
Q5. What is aria-labelledby?
It references one or more elements whose text provides the accessible name.
Q6. What is aria-expanded?
It communicates whether a controlled component is expanded or collapsed.
Q7. What is aria-hidden?
It controls whether an element is exposed in the accessibility tree.
Q8. What is aria-describedby?
It associates an element with additional descriptive information.
Q9. What is aria-live?
It identifies a region where dynamic content changes can be announced by assistive technologies.
Q10. What is aria-controls?
It identifies the element or elements controlled by the current element.
Q11. What is the first rule of ARIA?
Prefer native HTML elements and attributes whenever they already provide the required semantics and behavior.
Q12. Does ARIA automatically provide keyboard support?
No. Developers must implement the necessary keyboard interaction.
Q13. What is aria-pressed?
It communicates the pressed state of a toggle button.
Q14. What is aria-invalid?
It indicates that the current value of a control does not satisfy validation.
Q15. Why should ARIA be tested manually?
Because correct attribute syntax does not guarantee correct interaction, keyboard support or screen reader behavior.
