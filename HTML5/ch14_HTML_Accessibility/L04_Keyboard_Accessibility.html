Lesson 4: Keyboard Accessibility

Chapter 14: HTML Accessibility

Learn how to make web pages and interactive elements usable through a keyboard without requiring a mouse or touch input.

1. Introduction to Keyboard Accessibility

Keyboard accessibility means that users can navigate and operate a website using a keyboard or keyboard-like input device.

Some users cannot operate a mouse because of motor disabilities, temporary injuries or personal preferences. Others use assistive technologies that depend on keyboard interaction.

Why Is Keyboard Accessibility Important?

  • Supports users who cannot use a mouse.
  • Helps users with motor disabilities.
  • Supports keyboard-only navigation.
  • Improves usability for many desktop users.
  • Helps ensure interactive content is accessible.
A website should not require a mouse for any essential operation. Users should be able to access and operate all relevant interactive functionality using a keyboard.

2. Common Keyboard Keys

Several keyboard keys are commonly used to navigate and operate web pages.

Key Common Function
Tab Moves focus to the next focusable element.
Shift + Tab Moves focus to the previous focusable element.
Enter Activates links and buttons when focused.
Space Activates buttons and toggles checkboxes when focused.
Arrow Keys Navigate within many controls, menus and widgets.
Escape Often closes dialogs, menus and pop-up interfaces.
Home / End Moves to the beginning or end in supported controls.
Exact keyboard behavior depends on the element, browser and operating system. For example, arrow keys do not universally move focus between every page element.

3. Understanding Keyboard Focus

Keyboard focus identifies the element that currently receives keyboard input. When a user presses Tab, the browser normally moves focus to the next focusable element in the sequential focus order.

Example

<a href="index.html">Home</a> <button type="button">Start Course</button> <input type="text" placeholder="Enter your name"> <button type="submit">Submit</button>

Press Tab repeatedly to move through the focusable controls in the page.

Focusable HTML Elements

  • Links with an href attribute.
  • Buttons.
  • Form input elements.
  • Select elements.
  • Textareas.
  • Elements with an appropriate tabindex value.
Not every HTML element is automatically included in the normal keyboard tab order. Use native interactive elements whenever possible.

4. The Tab Order

Tab order is the sequence in which elements receive keyboard focus when users press Tab.

A logical tab order helps users understand the structure and operation of a web page.

Example

<h1>Course Registration</h1> <form> <label for="name">Name:</label> <input type="text" id="name"> <label for="email">Email:</label> <input type="email" id="email"> <button type="submit">Register</button> </form>

The browser generally follows the order in which these focusable controls appear in the document.

Best Practices

  • Keep focus order logical and predictable.
  • Match the focus sequence to the visual and reading order.
  • Avoid unnecessary positive tabindex values.
  • Do not remove essential controls from keyboard navigation.

5. The tabindex Attribute

The tabindex attribute controls whether an element can receive focus and how it participates in sequential keyboard navigation.

Common tabindex Values

Value Meaning
tabindex="0" Makes an element focusable in the normal sequential tab order.
tabindex="-1" Makes an element programmatically focusable but excludes it from normal sequential Tab navigation.
Positive tabindex Places an element in a priority tab sequence; generally avoid it.

Example 1: tabindex="0"

<div tabindex="0"> This element can receive keyboard focus. </div>

Example 2: tabindex="-1"

<h2 id="course-title" tabindex="-1"> HTML5 Course Details </h2>

JavaScript can move focus to this heading when required, even though it is not normally reached through Tab navigation.

Example 3: Avoid Positive tabindex

<button tabindex="3">Third</button> <button tabindex="1">First</button> <button tabindex="2">Second</button>
Positive tabindex values can create a focus order that differs from the document order. Prefer tabindex="0" or tabindex="-1" when there is a genuine need to make a custom element focusable.

6. Keyboard Accessibility of Links

Native anchor elements with an href attribute are keyboard accessible by default. Users can normally focus them with Tab and activate them with Enter.

Correct Example

<a href="html5/index.html"> Explore the HTML5 Course </a>

Incorrect Example

<span onclick="openCourse()"> Explore the HTML5 Course </span>

A span with only an onclick handler does not automatically behave like a keyboard-accessible link.

Better Alternative for an Action

<button type="button" onclick="openCourse()"> Open Course </button> <script> function openCourse() { window.location.href = "html5/index.html"; } </script>
Use an anchor for navigation to another resource. Use a button for an action. Native HTML elements provide built-in keyboard behavior.

7. Keyboard Accessibility of Buttons

Native button elements support keyboard interaction without requiring custom keyboard event handlers.

Example

<button type="button" onclick="showMessage()"> Show Message </button> <p id="message"></p> <script> function showMessage() { document.getElementById("message").textContent = "Welcome to NS Learning Hub!"; } </script>

When focused, a native button can generally be activated using Enter or Space.

Avoid replacing native buttons with div or span elements simply to achieve a particular visual design.

8. Visible Focus Indicators

A focus indicator visually identifies the element currently receiving keyboard focus.

Without a visible focus indicator, keyboard users may not know where they are on the page.

CSS Example

a:focus-visible, button:focus-visible, input:focus-visible, select:focus-visible, textarea:focus-visible { outline: 3px solid #e76f00; outline-offset: 4px; }

What Is :focus-visible?

The :focus-visible pseudo-class allows browsers to display focus styling when they determine that a visible focus indicator is needed, commonly during keyboard navigation.

Difference Between :focus and :focus-visible

:focus :focus-visible
Matches an element when it has focus. Matches when the browser determines that a visible focus indicator should be shown.
May apply after mouse interaction. Often useful for keyboard-oriented focus styling.
Never remove the browser's focus outline without providing an equally clear alternative.

9. Keyboard Accessibility of Forms

Form controls should be reachable and operable using the keyboard. Labels and logical focus order are also important for accessible forms.

Example

<form> <label for="username"> Username: </label> <input type="text" id="username" name="username"> <br><br> <label for="password"> Password: </label> <input type="password" id="password" name="password"> <br><br> <button type="submit"> Login </button> </form>

Keyboard Behavior

  • Tab moves between focusable form controls.
  • Shift + Tab moves backwards.
  • Space toggles a focused checkbox.
  • Arrow keys commonly operate radio groups and select controls.
  • Enter may submit a form under appropriate conditions.

10. Keyboard Accessibility of Custom Controls

Custom interactive components such as dropdown menus, tabs, dialogs and custom sliders need carefully designed keyboard behavior.

Native HTML controls should be preferred whenever they meet the application's needs.

Example: Native Select Element

<label for="course"> Select a Course: </label> <select id="course" name="course"> <option value="html5">HTML5</option> <option value="cpp">C++ Programming</option> <option value="linux">Linux</option> </select>

The browser provides the standard keyboard interaction for this select control.

Common Custom Component Patterns

Component Typical Keyboard Interaction
Tabs Arrow keys commonly move between tabs; Tab enters or leaves the tab sequence.
Dialog Focus moves into the dialog; Escape may close it when appropriate.
Menu Arrow keys may move between menu items.
Checkbox Space toggles its checked state.
Radio group Arrow keys commonly move between radio options.
These are common interaction patterns, not automatic behavior for every custom widget. Custom controls must implement the expected keyboard behavior and expose their states correctly to assistive technologies.

11. Avoiding Keyboard Traps

A keyboard trap occurs when a keyboard user cannot move focus away from a particular component using the keyboard.

Example Scenario

A user opens a dialog and can navigate through its controls but cannot close it or move focus out of it.

This can prevent the user from continuing to use the page.

How to Prevent Keyboard Traps

  • Ensure users can exit interactive components.
  • Provide an accessible close mechanism for dialogs.
  • Support Escape when appropriate.
  • Manage focus when opening and closing dialogs.
  • Test keyboard navigation in every interactive component.
A modal dialog may intentionally keep focus inside itself while open. This is not a keyboard trap if users can operate and close the dialog using the keyboard.

12. Example: Accessible Dialog with Keyboard Support

The native dialog element provides built-in dialog behavior. The following example demonstrates opening and closing a dialog using keyboard-accessible buttons.

Complete HTML Code

<!DOCTYPE html> <html lang="en"> <head> <meta charset="UTF-8"> <meta name="viewport" content="width=device-width, initial-scale=1.0"> <title>Keyboard Accessible Dialog</title> <style> dialog { max-width: 400px; border: 2px solid #174ea6; border-radius: 10px; padding: 25px; } dialog::backdrop { background: rgba(0, 0, 0, 0.55); } button:focus-visible { outline: 3px solid #e76f00; outline-offset: 4px; } </style> </head> <body> <h1>Keyboard Accessible Dialog</h1> <button id="openDialog" type="button"> Open Dialog </button> <dialog id="courseDialog" aria-labelledby="dialogTitle"> <h2 id="dialogTitle"> Course Information </h2> <p> Welcome to the HTML5 course. </p> <button id="closeDialog" type="button"> Close Dialog </button> </dialog> <script> const dialog = document.getElementById("courseDialog"); const openButton = document.getElementById("openDialog"); const closeButton = document.getElementById("closeDialog"); openButton.addEventListener("click", function () { dialog.showModal(); }); closeButton.addEventListener("click", function () { dialog.close(); }); </script> </body> </html>

How to Test

  1. Open the page in a browser.
  2. Press Tab until Open Dialog receives focus.
  3. Press Enter or Space to open the dialog.
  4. Use Tab to navigate inside the dialog.
  5. Press Escape to close the modal dialog.
  6. Verify that focus returns to the opening button.
The native modal dialog opened with showModal() provides built-in focus handling and Escape behavior in supporting browsers. Test the complete interaction with your target browsers and assistive technologies.

13. Testing Keyboard Accessibility

Keyboard testing helps identify problems that may not be visible during ordinary mouse-based browsing.

Manual Testing Procedure

  1. Open the website in a browser.
  2. Do not use the mouse.
  3. Press Tab to move through interactive elements.
  4. Press Shift + Tab to move backwards.
  5. Check whether focus is always visible.
  6. Use Enter and Space to activate controls.
  7. Test menus, forms, dialogs and other widgets.
  8. Check that no component traps keyboard focus.
  9. Verify that focus order is logical.

Keyboard Accessibility Checklist

  • All essential functions are keyboard accessible.
  • Focus order is logical.
  • Focus indicators are visible.
  • Links and buttons work using the keyboard.
  • Forms can be completed without a mouse.
  • Custom widgets have appropriate keyboard behavior.
  • Users can exit dialogs and other components.
  • Focused content is not hidden behind other content.

14. Common Keyboard Accessibility Mistakes

Mistake Correct Practice
Using clickable div elements without keyboard support. Use native buttons or links.
Removing focus outlines. Provide a clearly visible focus indicator.
Using positive tabindex values unnecessarily. Keep a natural document order.
Creating keyboard traps. Provide a keyboard-operable exit.
Using mouse-only event handlers. Use native controls or implement complete keyboard interaction.
Creating confusing focus sequences. Keep focus order predictable.
Hiding focused elements behind overlays. Ensure the focused element remains visible.

16. Interview Questions and Answers

Q1. What is keyboard accessibility?
It is the ability to navigate and operate web content using a keyboard without depending on a mouse.
Q2. What is keyboard focus?
Keyboard focus identifies the element that currently receives keyboard input.
Q3. What is tab order?
It is the sequence in which elements receive focus during sequential keyboard navigation.
Q4. What does tabindex="0" do?
It makes an element focusable and includes it in the normal sequential tab order.
Q5. What does tabindex="-1" do?
It allows an element to receive programmatic focus but removes it from normal sequential Tab navigation.
Q6. Why should positive tabindex values be avoided?
They can create an unexpected focus order that differs from the natural document sequence.
Q7. What is a focus indicator?
It is a visual indication showing which element currently has keyboard focus.
Q8. What is the purpose of :focus-visible?
It allows focus styling when the browser determines that a visible focus indicator is appropriate.
Q9. What is a keyboard trap?
It occurs when a keyboard user cannot move focus away from a component using the keyboard.
Q10. How can a keyboard trap be prevented?
Provide keyboard-operable controls and ensure users can exit the component.
Q11. Can a div be keyboard accessible?
Yes, but it requires appropriate focus handling and keyboard interaction. Native interactive elements are generally preferable.
Q12. How is a native button activated by keyboard?
A focused native button can generally be activated using Enter or Space.
Q13. What is the difference between Tab and Enter?
Tab moves focus between focusable elements. Enter activates links and buttons when focused.
Q14. Why should keyboard accessibility be tested manually?
Manual testing helps identify focus, navigation and interaction problems that automated checks may not detect.
Q15. Which WCAG principle is closely related to keyboard accessibility?
The Operable principle. It requires functionality to be operable through appropriate input methods, including keyboard interaction.

17. Multiple Choice Questions (MCQs)

1. Which key moves focus to the next focusable element?
  1. Enter
  2. Tab
  3. Escape
  4. Space
Answer: B — Tab
2. Which key combination moves focus backwards?
  1. Ctrl + Tab
  2. Shift + Tab
  3. Alt + Tab
  4. Enter + Tab
Answer: B — Shift + Tab
3. What does tabindex="0" do?
  1. Hides an element
  2. Makes an element focusable in normal tab order
  3. Disables keyboard navigation
  4. Removes an element
Answer: B — Makes an element focusable in normal tab order
4. What does tabindex="-1" generally do?
  1. Disables all interaction
  2. Allows programmatic focus but excludes normal Tab navigation
  3. Moves an element to the first position
  4. Hides an element from screen readers
Answer: B
5. Which HTML element is best for a button action?
  1. div
  2. span
  3. button
  4. p
Answer: C — button
6. Which CSS pseudo-class is useful for keyboard focus styling?
  1. :hover
  2. :focus-visible
  3. :visited
  4. :empty
Answer: B — :focus-visible
7. What is a keyboard trap?
  1. A visible focus outline
  2. An element that cannot receive focus
  3. A situation where focus cannot be moved away using the keyboard
  4. A keyboard shortcut
Answer: C
8. Which key commonly activates a focused native button?
  1. Space
  2. Escape only
  3. Shift only
  4. Caps Lock
Answer: A — Space (Enter also works)
9. Which tabindex values are generally preferred when needed?
  1. 1 and 2
  2. 0 and -1
  3. 5 and 10
  4. Only positive values
Answer: B — 0 and -1
10. Which WCAG principle is associated with keyboard operation?
  1. Perceivable
  2. Operable
  3. Understandable
  4. Robust
Answer: B — Operable
