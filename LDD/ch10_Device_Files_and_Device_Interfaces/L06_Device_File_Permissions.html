Chapter: Device Files and Device Interfaces

Lesson: 6 – Device File Permissions

Prerequisites: Device Nodes, Major and Minor Number Mapping, Basic Linux File Permissions.

Objective: Understand how Linux controls access to device nodes using ownership, groups, permission bits, and device-management rules.

1. Introduction

Linux represents many hardware and software device interfaces through special files under the /dev directory.

Although these are device nodes rather than ordinary data files, Linux applies standard filesystem permission mechanisms to control which users can access them.

For example, inspect a device node:

ls -l /dev/null
ls -l /dev/tty
ls -l /dev/zero

Example output format:

crw-rw-rw- 1 root root 1, 3 Nov 12 10:30 /dev/null

The permission string, owner, group, major number, and minor number provide information about the device node.

2. Understanding Device File Permission Notation

Consider this example:

crw-rw---- 1 root dialout 188, 0 /dev/example0
Field Meaning
c Character device file.
rw- Owner has read and write permissions.
rw- Group has read and write permissions.
--- Other users have no permissions.
root Owner of the device node.
dialout Group assigned to the device node.
188, 0 Major and minor device numbers.

The three permission groups are:

  • User (u): The owner of the device node.
  • Group (g): Users belonging to the assigned group.
  • Others (o): All other users.

3. Read, Write and Execute Permissions

Linux uses three basic permission bits.

Permission Symbol Numeric Value General Meaning for a Device Node
Read r 4 Allows opening the device with read access, subject to driver and system checks.
Write w 2 Allows opening the device with write access, subject to driver and system checks.
Execute x 1 Execute permission is generally not meaningful for ordinary device I/O.

Read and write permissions are particularly important for character-device interfaces.

For example:

crw-rw----

This means the owner and group have read/write permission, while other users have no permission.

Filesystem permission bits are only one part of device access control. The driver may impose additional restrictions, and security mechanisms such as Linux capabilities, device cgroups, and security modules can also affect access.

4. Numeric Permission Representation

Linux permissions can be represented using octal numbers.

Permission Value
Read (r)4
Write (w)2
Execute (x)1
No permission0

Each digit represents permissions for one category: owner, group, or others.

Example: Permission 660

sudo chmod 660 /dev/example0
Digit Category Permission
6 Owner Read + Write (4 + 2)
6 Group Read + Write (4 + 2)
0 Others No permission

Common Permission Examples

Mode Meaning
600 Owner read/write only.
640 Owner read/write; group read.
660 Owner and group read/write.
666 Everyone read/write.
000 No permission for owner, group, or others.
Do not use permissive settings such as 666 as a general solution to device-access problems. Grant only the permissions required by the intended users and applications.

5. Changing Device Node Permissions Using chmod

The chmod command changes permission bits on a device node, provided the user has sufficient privileges.

Syntax

sudo chmod MODE DEVICE_NODE

Example

sudo chmod 660 /dev/example0

This requests read/write access for the owner and group and removes permissions for others.

Verify the Permissions

ls -l /dev/example0

Possible permission display:

crw-rw---- 1 root root 240, 0 /dev/example0

The displayed ownership and device numbers are illustrative. Actual values depend on the system and driver.

A manually changed permission on a device node may not persist after the node is removed and recreated. Device-management rules should be used for persistent configuration.

6. Changing Device Node Ownership Using chown

Linux uses ownership to determine which user and group receive the owner and group permission bits.

The chown command changes ownership.

Syntax

sudo chown USER:GROUP DEVICE_NODE

Example

sudo chown root:dialout /dev/example0

This sets:

  • Owner: root
  • Group: dialout

Verify the result:

ls -l /dev/example0

Example:

crw-rw---- 1 root dialout 240, 0 /dev/example0

7. Device Groups in Linux

Linux systems commonly use groups to grant access to particular device interfaces without granting every user unrestricted access.

Some commonly encountered groups include:

Group Typical Context
dialout Serial ports and related communication devices on many distributions.
plugdev Some removable or plug-in device access arrangements, depending on distribution configuration.
video Some video and graphics device interfaces.
audio Some audio device interfaces.

Group assignments are distribution- and device-specific. A device does not automatically belong to a particular group simply because of its function.

Check Your Groups

groups
id

Inspect a Group

getent group dialout

Add a User to a Group

sudo usermod -aG dialout $USER

After changing supplementary group membership, start a new login session for the change to take effect in newly started processes. Logging out and logging back in is the usual approach.

Add a user to a device group only when that user genuinely needs access. Membership can grant access to multiple devices assigned to that group.

8. Access Control During Device File Operations

When a user-space application opens a device node, Linux performs permission and security checks before allowing access.

User-Space Application
↓
open("/dev/example0", flags)
↓
Filesystem Permission Checks
↓
Additional Security Checks
↓
Device Driver Open Operation

If access is denied during the permission checks, the application may receive an error such as EACCES or EPERM, depending on the reason.

If access is allowed, the kernel proceeds through the device interface and the driver's relevant file operation, such as its open() callback.

Successful permission checks do not guarantee that the driver will accept the operation. The driver can still reject it for device-specific reasons.

9. Device File Permissions and udev

Modern Linux systems commonly use udev rules to manage device-node ownership, group assignments, permissions, and symbolic links.

When a device is detected and its device-model information is available, udev processes matching rules and can configure the corresponding device node.

This is useful because device nodes may be removed and recreated as devices are connected, disconnected, or managed by the system.

Example udev Rule

The following is an illustrative rule for a device identified by its kernel device name. The actual match conditions must be selected for the real device.

# Example only: match a device with kernel name example0
SUBSYSTEM=="example", KERNEL=="example0", \
    GROUP="dialout", MODE="0660"

This rule requests:

  • Group ownership: dialout
  • Permission mode: 0660

A rule must match the actual device properties. An arbitrary example rule will not automatically affect a device on every Linux system.

Inspect udev Information

udevadm info --query=all --name=/dev/null

For a real device node, this command displays available udev properties and device information.

Inspect udev Rules

ls /etc/udev/rules.d/
ls /usr/lib/udev/rules.d/

Rule locations can vary by distribution. Local administrator rules are commonly placed under /etc/udev/rules.d/.

10. Device Node Permissions and devtmpfs

devtmpfs is a kernel-managed filesystem used on many Linux systems to provide device nodes under /dev.

When a driver creates a device-model object using an appropriate interface, such as device_create(), devtmpfs and the user-space device-management system can participate in making the device node available.

Initial ownership and permissions may be influenced by device registration details, devtmpfs behavior, udev rules, and distribution configuration.

Do not assume that calling device_create() alone permanently sets every desired permission. Use appropriate device-management rules when persistent ownership and permission configuration is required.

11. Understanding Permission Errors

Consider a user-space program attempting to open a device node:

int fd = open("/dev/example0", O_RDWR);

If the user lacks the required permissions, the operation may fail.

Example shell diagnostic:

ls -l /dev/example0
id
getent group dialout

Common causes include:

  • The user is not the owner of the node.
  • The user's groups do not include the node's assigned group.
  • The node does not grant the required read or write permission.
  • A security policy or device access-control mechanism denies access.
  • The device node does not exist or refers to an unavailable interface.
  • The driver rejects the open operation even after permission checks succeed.

When diagnosing a failure, inspect ownership, permissions, group membership, device registration, and kernel logs rather than immediately changing permissions to 777.

12. Safe Practical Exercise in Ubuntu

This exercise uses the existing /dev/null device node to inspect permissions. It does not require a physical device or a custom kernel driver.

Step 1: Inspect the Device Node

ls -l /dev/null

Step 2: Inspect Detailed Metadata

stat /dev/null

Step 3: Check Your User and Groups

id
groups

Step 4: Test Normal Device Access

echo "Linux device permission test" > /dev/null
cat /dev/null

The write operation is accepted and discarded by /dev/null. Reading from it returns end-of-file immediately.

Step 5: Restore or Verify the Standard Device Configuration

ls -l /dev/null

On a typical Ubuntu installation, /dev/null is a character device with permissions commonly displayed as crw-rw-rw- and ownership root:root.

Do not change permissions or ownership of important system device nodes as part of this exercise. Use inspection commands only.

13. Best Practices for Device Access Control

  • Grant the minimum permissions required by the application.
  • Prefer suitable group-based access over unrestricted access.
  • Use udev rules for persistent device-node configuration where appropriate.
  • Do not use chmod 777 as a routine troubleshooting method.
  • Keep device ownership and group assignments consistent with system policy.
  • Check the actual device node rather than assuming its permissions.
  • Remember that filesystem permissions do not replace driver-level validation.
  • Do not assume that a process running as root bypasses every security restriction.

14. Lesson Summary

  • Device nodes use Linux filesystem ownership and permission mechanisms.
  • Permissions are divided into owner, group, and others.
  • Read and write permissions control ordinary device-file access requests.
  • chmod changes permission bits.
  • chown changes ownership.
  • Groups provide controlled access to device interfaces.
  • udev rules can configure device-node ownership and permissions.
  • devtmpfs and udev commonly participate in device-node management.
  • Driver callbacks and other security mechanisms can impose additional restrictions.
