Chapter: Device Files and Device Interfaces

Lesson: 10 – Device Interface Testing from User Space

Prerequisites: Character Device Drivers, file_operations, read(), write(), device nodes, device_create(), and device permissions.

Objective: Learn how user-space applications interact with character-device interfaces and how to test device drivers using Linux commands and C programs.

1. Introduction

A Linux device driver provides an interface through which user-space applications can communicate with devices.

For a character driver, this communication commonly takes place through a device node under the /dev directory.

User-space programs can use standard system calls such as:

  • open() – Open a device file.
  • read() – Request data from a device.
  • write() – Send data to a device.
  • ioctl() – Send device-specific control commands.
  • close() – Close the file descriptor.

Testing verifies that the driver is registered correctly, its device node is accessible, and its implemented operations behave as expected.

2. User Space and Kernel Space Communication

User applications normally execute in user space, while device drivers execute in kernel space.

User Application
↓
open() / read() / write() / ioctl()
↓
System Call Interface
↓
Virtual File System (VFS)
↓
Character Device Driver
↓
Device or Driver-Managed Data

The VFS provides a common interface for file operations. It routes operations on a device node to the appropriate registered driver operations.

The actual device interaction depends on the driver implementation. A driver may communicate with physical hardware or manage a virtual device entirely in software.

3. Verify Device Driver Registration

Before testing a device interface, confirm that the driver module is loaded.

List Loaded Modules

lsmod

To search for a particular module:

lsmod | grep my_driver

lsmod displays loadable kernel modules currently loaded. Built-in kernel components do not appear as independently loaded modules.

Inspect Kernel Messages

dmesg | tail -n 20

This displays recent messages from the kernel ring buffer.

Inspect Registered Character Device Numbers

cat /proc/devices

This helps identify the major number associated with a registered character-device driver.

4. Verify the Device Node

A device node provides the filesystem interface used by user-space programs.

For example:

ls -l /dev/mydevice

A typical device-node listing may look like:

crw------- 1 root root 240, 0 Nov 12 10:30 /dev/mydevice

Explanation:

Field Meaning
c Character device.
rw------- Permissions for owner, group and others.
root Owner of the device node.
240 Example major number.
0 Example minor number.
/dev/mydevice Device-node path.

The major and minor values above are illustrative. Actual values depend on the device number allocated by the driver.

Inspect Device Information

stat /dev/mydevice

The stat command displays filesystem metadata, including device type and device-number information.

5. Test Device Permissions

Linux checks device-node permissions when a process attempts to open a device.

For example:

ls -l /dev/mydevice

If the current user does not have permission, an attempt to open the device may fail with Permission denied.

For a controlled test, use:

sudo ls -l /dev/mydevice

To test access with elevated privileges, run the test application using:

sudo ./test_device
Use elevated privileges only when required. Do not change device permissions broadly with commands such as chmod 777. Production device permissions should be managed through appropriate udev rules and system policy.

6. Testing with Basic Linux Commands

Some device interfaces can be inspected using standard Linux commands, depending on the operations implemented by the driver.

Check Device Node

ls -l /dev/mydevice

Check Device Class in Sysfs

ls -l /sys/class/my_class/

Inspect Device Information

ls -l /sys/class/my_class/mydevice/

Check Kernel Messages

dmesg | tail -n 20
Commands such as cat, echo, and dd are useful only when the driver implements compatible read/write behavior. Do not assume every device node supports ordinary text input or output.

7. Testing open() and close() Using a C Program

The following user-space program opens a device node and closes it.

Save the program as test_device.c.

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    int fd;

    fd = open("/dev/mydevice", O_RDONLY);

    if (fd < 0) {
        perror("open failed");
        return EXIT_FAILURE;
    }

    printf("Device opened successfully\n");

    if (close(fd) < 0) {
        perror("close failed");
        return EXIT_FAILURE;
    }

    printf("Device closed successfully\n");

    return EXIT_SUCCESS;
}

Compile the Program

gcc test_device.c -o test_device

Run the Program

sudo ./test_device

Expected Output

Device opened successfully
Device closed successfully

This test checks whether the device can be opened and closed. The driver's .open and .release callbacks are involved when implemented.

8. Testing read() and write() Operations

To test data transfer, the driver must implement suitable read and write callbacks in its file_operations structure.

Driver-Side Operations

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

The user-space program can then use the standard system calls.

Example User-Space Program

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

int main(void)
{
    int fd;
    char write_buffer[] = "Hello Linux Driver";
    char read_buffer[128];
    ssize_t bytes;

    fd = open("/dev/mydevice", O_RDWR);

    if (fd < 0) {
        perror("open");
        return EXIT_FAILURE;
    }

    bytes = write(fd, write_buffer, strlen(write_buffer));

    if (bytes < 0) {
        perror("write");
        close(fd);
        return EXIT_FAILURE;
    }

    printf("Bytes written: %zd\n", bytes);

    if (lseek(fd, 0, SEEK_SET) < 0) {
        perror("lseek");
        close(fd);
        return EXIT_FAILURE;
    }

    bytes = read(fd, read_buffer, sizeof(read_buffer) - 1);

    if (bytes < 0) {
        perror("read");
        close(fd);
        return EXIT_FAILURE;
    }

    read_buffer[bytes] = '\0';

    printf("Bytes read: %zd\n", bytes);
    printf("Received: %s\n", read_buffer);

    close(fd);

    return EXIT_SUCCESS;
}
This example assumes the driver implements compatible read/write callbacks and supports seeking through its .llseek operation or another appropriate file-position mechanism. A driver that does not support seeking must be tested according to its own file-position behavior. A successful write does not guarantee that a later read returns the same data unless the driver is designed to store and return it.

Important Data Transfer Rules

  • read() may return fewer bytes than requested.
  • write() may accept fewer bytes than requested.
  • A return value of zero from read() indicates end-of-file.
  • A negative return value indicates an error; inspect errno.
  • Kernel drivers must use copy_to_user() and copy_from_user() for appropriate user-kernel buffer transfers.

9. Testing with ioctl()

The ioctl() system call allows user applications to send device-specific control commands to a driver.

Examples include:

  • Changing a device operating mode.
  • Configuring a hardware parameter.
  • Reading device status.
  • Starting or stopping a device operation.

A user-space application typically includes:

#include <sys/ioctl.h>

int ret = ioctl(fd, command, argument);

The driver must implement the corresponding ioctl handling, commonly through unlocked_ioctl in its file operations.

Detailed ioctl command design and implementation will be covered in Chapter 11.

10. Testing Device Interfaces with strace

strace traces system calls made by a user-space program. It is useful for understanding how an application interacts with a device node.

Example:

strace ./test_device

To focus on common device operations:

strace -e trace=openat,read,write,close ./test_device

Possible observations include:

  • openat() opens the device path.
  • read() requests data.
  • write() sends data.
  • close() releases the file descriptor.

On modern Linux systems, the C library's open() call commonly appears as openat() in a system-call trace.

Install strace if it is not available: 
sudo apt update
sudo apt install strace

This workflow can be used as a basic validation procedure for a character-device driver.

12. Common Testing Errors

Error Possible Cause Suggested Check
No such file or directory Device node does not exist. Check /dev, device registration and devtmpfs/udev.
Permission denied Insufficient device-node permissions. Inspect ownership and permissions; use an authorized account.
No such device Device node exists but no suitable registered driver handles the device number. Check major/minor values and cdev registration.
Invalid argument Unsupported operation or invalid parameter. Check driver callbacks and arguments.
Bad file descriptor Invalid or already closed file descriptor. Check the result of open() and file-descriptor handling.
Read returns zero End-of-file or driver-defined behavior. Inspect the read callback and file position.

13. Testing in Ubuntu VirtualBox

A virtual Ubuntu environment is suitable for learning and testing software-based character drivers.

You can practise:

  • Loading and unloading kernel modules.
  • Creating device nodes.
  • Registering character devices.
  • Testing open, read, write and release operations.
  • Inspecting sysfs and procfs information.
  • Debugging system-call interactions.
Physical GPIO, I2C, SPI and other hardware tests require access to suitable hardware or an appropriate emulation environment. A standard VirtualBox Ubuntu guest does not automatically expose the host computer's physical peripheral controllers as Linux devices.
