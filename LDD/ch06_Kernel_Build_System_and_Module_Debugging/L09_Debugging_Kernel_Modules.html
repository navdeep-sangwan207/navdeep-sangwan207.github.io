Lesson 9: Debugging Kernel Modules
Level: Intermediate
Prerequisites: Kernel modules, printk(), dmesg, module loading and unloading, and kernel build system.
Objective: Learn practical techniques and tools for identifying, analyzing and correcting problems in Linux kernel modules.

1. Introduction

Debugging is the process of identifying, analyzing and correcting errors in a software program. Kernel module debugging applies this process to code that executes inside the Linux kernel.

Kernel modules are different from ordinary user-space applications because they execute with kernel privileges. A programming mistake can affect the entire operating system.

A faulty module may cause memory corruption, invalid pointer access, kernel warnings, kernel oops messages or even a complete system crash.

Therefore, kernel developers use systematic debugging techniques to investigate problems safely.

2. Why Is Kernel Module Debugging Important?

Device drivers interact with kernel subsystems, memory management, hardware resources and other kernel components.

Debugging helps identify problems such as:

  • Incorrect module initialization.
  • Failure during module cleanup.
  • Invalid pointer dereferencing.
  • Memory allocation failures.
  • Memory leaks.
  • Race conditions.
  • Interrupt handling problems.
  • Resource conflicts.
  • Incorrect device register access.
  • Kernel API misuse.

3. User-Space Debugging vs Kernel-Space Debugging

User-Space Debugging Kernel-Space Debugging
Debugs normal application processes. Debugs kernel code and loadable modules.
Tools include GDB and application logging. Tools include printk, dmesg, ftrace, KASAN and KGDB.
A program crash usually affects that process. A kernel fault can affect the entire system.
Processes have separate virtual address spaces. Kernel code operates with kernel privileges and kernel memory access.
Ordinary debugging can often pause a process. Stopping kernel execution can affect system-wide activity and timing.

4. Common Kernel Module Debugging Techniques

Technique Purpose
printk() and pr_*() Generate diagnostic messages.
dmesg Inspect kernel ring-buffer messages.
Dynamic Debug Enable selected debug messages at runtime.
ftrace Trace kernel functions and execution events.
KGDB Perform source-level kernel debugging with GDB.
KASAN Detect many kernel memory access errors.
Lockdep Detect potential locking errors and deadlocks.
Debugfs Expose debugging information through a kernel interface.

5. Debugging with printk() and pr_*()

Logging is one of the simplest ways to debug a kernel module.

Developers place messages at important points in the module to understand its execution flow.

Example

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init debug_init(void)
{
    pr_info("debug: initialization started\n");

    pr_info("debug: checking configuration\n");

    pr_info("debug: initialization completed\n");

    return 0;
}

static void __exit debug_exit(void)
{
    pr_info("debug: cleanup started\n");
}

module_init(debug_init);
module_exit(debug_exit);

MODULE_LICENSE("GPL");

View Messages

sudo dmesg | grep -i debug

Common Logging Macros

Macro Purpose
pr_info() Informational messages.
pr_warn() Warning messages.
pr_err() Error messages.
pr_debug() Debug messages that can be controlled by configuration or Dynamic Debug.
Do not add excessive logging to frequently executed functions. Large amounts of logging can affect performance and make important messages difficult to identify.

6. Debugging Module Initialization

The initialization function is executed when the kernel loads a module.

If initialization fails, the module is not successfully loaded.

Example

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/errno.h>

static int __init test_init(void)
{
    pr_info("test: step 1 - initialization started\n");

    pr_info("test: step 2 - checking resources\n");

    pr_err("test: step 3 - simulated failure\n");

    return -EINVAL;
}

static void __exit test_exit(void)
{
    pr_info("test: cleanup executed\n");
}

module_init(test_init);
module_exit(test_exit);

MODULE_LICENSE("GPL");

This example intentionally returns a negative error code.

Load the Module

sudo insmod test.ko

Inspect the Kernel Log

sudo dmesg | tail -20

The initialization messages help identify how far the function executed before returning the error.

The registered exit function is not called as a normal unload operation when initialization fails. Resources acquired before failure must be released by the initialization error path.

7. Debugging Memory Allocation Problems

Kernel modules often allocate memory dynamically using functions such as:

  • kmalloc()
  • kzalloc()
  • kcalloc()
  • vmalloc()

Allocation can fail, so the returned pointer must be checked before use.

Example

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/slab.h>
#include <linux/init.h>

static int *buffer;

static int __init memory_init(void)
{
    buffer = kmalloc(10 * sizeof(*buffer), GFP_KERNEL);

    if (!buffer) {
        pr_err("memory: allocation failed\n");
        return -ENOMEM;
    }

    pr_info("memory: allocation successful\n");

    return 0;
}

static void __exit memory_exit(void)
{
    kfree(buffer);
    pr_info("memory: buffer released\n");
}

module_init(memory_init);
module_exit(memory_exit);

MODULE_LICENSE("GPL");

Debugging Checklist

  • Check whether allocation succeeded.
  • Verify the allocated size.
  • Use the correct allocation flags.
  • Do not access a NULL pointer.
  • Release allocated memory when it is no longer needed.
  • Check all initialization error paths for cleanup.

8. Debugging NULL Pointer Dereferencing

A NULL pointer dereference occurs when code tries to access memory through a NULL pointer.

Incorrect example:

int *ptr = NULL;

*ptr = 100;

This operation attempts to write through an invalid pointer and can cause a kernel fault if performed in kernel code.

Correct Approach

int *ptr = NULL;

if (!ptr) {
    pr_err("Invalid pointer\n");
    return -EINVAL;
}

*ptr = 100;

Validate pointers before accessing the memory they reference.

Never intentionally load a kernel module that performs an uncontrolled invalid memory access on your normal operating system.

9. Dynamic Debugging

Dynamic Debug is a Linux kernel facility that allows selected debug messages to be enabled or disabled at runtime.

It is commonly used with kernel logging macros such as pr_debug() and dev_dbg().

Check Dynamic Debug Control

sudo mount -t debugfs none /sys/kernel/debug

If debugfs is already mounted, this command may report that the mount point is busy.

Check the Control File

ls /sys/kernel/debug/dynamic_debug/

On kernels with Dynamic Debug enabled, the control file is commonly: 

/sys/kernel/debug/dynamic_debug/control

Enable Debug Messages for a Source File

echo 'file hello.c +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

Disable Debug Messages for a Source File

echo 'file hello.c -p' | sudo tee /sys/kernel/debug/dynamic_debug/control

The exact query can select messages by file, function, module, line or format string.

Dynamic Debug works only when the kernel and relevant code support it. A call to pr_debug() is not guaranteed to produce output unless its debug mechanism is enabled.

10. Debugging with ftrace

Ftrace is a Linux kernel tracing framework. It helps developers examine function execution, scheduling activity and other kernel events.

Check Available Tracers

sudo cat /sys/kernel/tracing/available_tracers

Check Current Tracer

sudo cat /sys/kernel/tracing/current_tracer

Enable Function Tracing

echo function | sudo tee /sys/kernel/tracing/current_tracer
echo 1 | sudo tee /sys/kernel/tracing/tracing_on

Read Trace Output

sudo cat /sys/kernel/tracing/trace

Disable Tracing

echo 0 | sudo tee /sys/kernel/tracing/tracing_on
echo nop | sudo tee /sys/kernel/tracing/current_tracer

Function tracing records function entry activity for traceable kernel functions. It is useful for understanding execution flow.

The tracing filesystem is commonly mounted at /sys/kernel/tracing. On some systems, tracefs may instead be available through /sys/kernel/debug/tracing. Available tracers depend on kernel configuration.

11. Debugging with KGDB and GDB

KGDB is a kernel debugging facility that allows developers to inspect kernel execution using GDB.

It supports source-level debugging techniques such as:

  • Setting breakpoints.
  • Inspecting variables.
  • Examining stack information.
  • Stepping through kernel code.
  • Investigating execution paths.
Developer Machine Running GDB
↕ Debugging Connection
Target Linux Kernel with KGDB
↓
Kernel Source-Level Debugging

Requirements

  • Kernel configured with KGDB support.
  • Suitable debugging symbols.
  • Compatible kernel source and build information.
  • A supported debugging connection or target setup.

KGDB is an advanced debugging method. It is not normally required for basic module development.

12. Debugging with KASAN

KASAN stands for Kernel Address Sanitizer. It is a dynamic memory error detector used by Linux kernel developers.

It can detect several classes of memory errors, including:

  • Out-of-bounds memory accesses.
  • Use-after-free errors.
  • Some invalid memory access patterns.

Example of a Memory Error

int *buffer;

buffer = kmalloc(4 * sizeof(int), GFP_KERNEL);

/* Incorrect: access beyond allocated array */
buffer[10] = 50;

A suitable KASAN-enabled kernel can detect this kind of out-of-bounds access during execution.

Important Requirements

  • The kernel must be built with suitable KASAN support.
  • Runtime overhead may be significant.
  • Not all kernel configurations support every KASAN mode.

13. Debugging Locking Problems with Lockdep

Kernel modules may use mutexes, spinlocks and other synchronization mechanisms.

Incorrect locking can cause deadlocks, lock-order inversions and other concurrency problems.

Lockdep is a kernel locking correctness validator that can detect many potential locking mistakes.

Common Problems

  • Acquiring locks in inconsistent orders.
  • Recursive locking errors.
  • Incorrect locking context.
  • Potential deadlock situations.

Lockdep requires appropriate kernel configuration and is particularly useful during development and testing.

14. Kernel Oops and Kernel Panic

A kernel oops is a report generated when the kernel encounters a serious fault, such as an invalid memory access.

A kernel panic occurs when the kernel determines that it cannot safely continue execution.

Kernel Oops Kernel Panic
Reports a serious kernel fault. Indicates that the kernel cannot safely continue.
The system may continue operating in some cases. The system normally stops or enters a configured panic action.
Can include register and stack information. Can include panic information and diagnostic output.

An oops can lead to a panic depending on the severity of the fault and system configuration.

Do not intentionally trigger kernel panics on your main system. Use a disposable virtual machine or dedicated test environment.

15. Useful Kernel Debugging Commands

Command Purpose
sudo dmesg Displays kernel ring-buffer messages.
sudo dmesg -w Monitors new kernel messages.
lsmod Lists loaded loadable modules.
modinfo hello.ko Displays module metadata.
sudo journalctl -k -b Displays kernel messages from the current boot.
sudo cat /sys/kernel/tracing/available_tracers Lists available ftrace tracers.
sudo cat /proc/modules Displays information about loaded modules.
sudo cat /proc/kallsyms Displays kernel symbol information, subject to access restrictions.

16. Practical Project: Debug a Kernel Module

In this exercise, create a simple module and use kernel logging to inspect its execution flow.

Step 1: Create Project Directory

mkdir kernel_debug_practice
cd kernel_debug_practice

Step 2: Create debug.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init debug_init(void)
{
    pr_info("debug: step 1 - initialization started\n");

    pr_info("debug: step 2 - checking module configuration\n");

    pr_info("debug: step 3 - configuration verified\n");

    pr_info("debug: step 4 - initialization successful\n");

    return 0;
}

static void __exit debug_exit(void)
{
    pr_info("debug: cleanup started\n");
    pr_info("debug: cleanup completed\n");
}

module_init(debug_init);
module_exit(debug_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Kernel module debugging practice");

Step 3: Create Makefile

obj-m += debug.o

all:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Step 4: Compile the Module

make

Step 5: Start Kernel Log Monitoring

sudo dmesg -w

Step 6: Load the Module in Another Terminal

sudo insmod debug.ko

Step 7: Observe Execution Messages

You should see the initialization messages generated by the module.

Step 8: Remove the Module

sudo rmmod debug

Step 9: Observe Cleanup Messages

Verify that the cleanup messages appear in the kernel log.

Step 10: Stop Log Monitoring

Press Ctrl+C in the terminal running dmesg -w.

Expected result: you should be able to trace the initialization and cleanup sequence using kernel messages.

17. Best Practices for Kernel Module Debugging

  • Start with simple logging before using advanced debugging tools.
  • Check kernel logs immediately after reproducing a problem.
  • Validate pointers before dereferencing them.
  • Check memory allocation return values.
  • Release resources on every initialization failure path.
  • Use synchronization correctly in concurrent code.
  • Use Dynamic Debug for selectively enabling debug messages.
  • Use ftrace when execution-flow analysis is required.
  • Use KASAN and Lockdep when supported by the test kernel.
  • Test experimental modules in a disposable environment.
  • Keep a record of the error, investigation and solution.

18. Summary

  • Kernel module debugging identifies and corrects kernel-space problems.
  • printk() and pr_*() macros provide diagnostic messages.
  • dmesg and journalctl help inspect kernel logs.
  • Dynamic Debug enables selected debug messages at runtime.
  • ftrace helps trace kernel function execution.
  • KGDB supports source-level kernel debugging with GDB.
  • KASAN detects many memory access errors.
  • Lockdep detects potential locking mistakes.
  • Kernel oops and panic messages indicate serious kernel faults.
  • Systematic debugging improves driver reliability.
