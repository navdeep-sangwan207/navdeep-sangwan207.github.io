Home Course Chapter 6
Lesson 4: obj-m and obj-y
Level: Beginner to Intermediate
Prerequisites: Linux kernel modules, GNU Make, Makefiles and Kbuild.
Objective: Understand the purpose of obj-m and obj-y, their differences and how Kbuild uses them to build kernel components.

1. Introduction

The Linux kernel build system uses special variables to decide which source-code objects should be compiled and how they should be included in the kernel.

Two important Kbuild variables are:

  • obj-m – Used to specify objects that should be built as loadable kernel modules.
  • obj-y – Used to specify objects that should be built into the kernel as built-in components.

Understanding these variables is important when developing external modules and studying the Linux kernel source tree.

2. What Is obj-m?

obj-m is a Kbuild variable used to identify object files that should be compiled as loadable kernel modules.

Example:

obj-m += hello.o

This declaration tells Kbuild to build a loadable module corresponding to hello.o.

If the source file is named hello.c, Kbuild compiles it and produces the required module output, normally: 

hello.ko

Characteristics of obj-m

  • Builds a loadable kernel module.
  • The module is generated as a separate .ko file.
  • It can generally be loaded using insmod or modprobe, subject to kernel requirements.
  • It can generally be removed using rmmod or modprobe -r, subject to module dependencies and usage.
  • It is commonly used in external module Makefiles.

3. What Is obj-y?

obj-y is a Kbuild variable used to identify object files that should be built into the kernel rather than generated as separate loadable modules.

Example:

obj-y += core.o

This declaration tells Kbuild to include the object core.o as part of the built-in kernel components when processing the relevant in-tree build rules.

Characteristics of obj-y

  • Builds objects as built-in kernel components.
  • Does not generate an independently loadable .ko file for that object.
  • The resulting code is linked into the kernel image or an appropriate built-in archive during the kernel build.
  • It is used in the Linux kernel source tree.
  • Built-in components cannot be independently unloaded using rmmod.
Important: A built-in component is incorporated into the kernel build. It is not a separate loadable module. Its availability depends on the kernel configuration and build.

4. Difference Between obj-m and obj-y

Feature obj-m obj-y
Purpose Builds a loadable module. Builds a built-in kernel component.
Output Normally generates a .ko file. Contributes to the built-in kernel image or built-in archive.
Loading Can be loaded separately if permitted. Already included in the built kernel.
Removal Can generally be unloaded if module rules allow it. Cannot be independently unloaded.

5. How obj-m Works

Consider an external kernel module project with the following structure: 

hello_driver/
|
|-- Makefile
|-- hello.c

The Makefile contains:

obj-m += hello.o

all:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

When you execute make, Kbuild reads the obj-m declaration and builds the object as a loadable module.

Build command:

make

Typical final output:

hello.ko

The module can then be inspected or loaded separately.

6. How obj-y Works

The obj-y variable is primarily used when building components within the Linux kernel source tree.

For example, an in-tree Makefile may contain:

obj-y += core.o
obj-y += device.o

These declarations specify that the corresponding objects should be built into the kernel as part of the relevant directory's build.

Kbuild processes these declarations according to the kernel configuration and directory hierarchy.

Important: Writing obj-y in an external module Makefile does not turn that external module into a built-in kernel component. The built-in build path belongs to the configured kernel source-tree build.

7. Relationship with Kernel Configuration

Linux kernel configuration determines whether many kernel components are included as built-in code, built as modules or excluded from the build.

Configuration options commonly use these values:

Configuration Value Meaning
y Build the feature into the kernel.
m Build the feature as a loadable module, if supported.
n Do not build the feature.

For example, a configurable driver may be selected as built-in or modular depending on its Kconfig definition and the selected kernel configuration.

Kbuild uses this configuration information when processing kernel source-tree Makefiles.

8. Multiple Objects Using obj-m

Multiple independent loadable modules can be declared in the same external module Makefile. 

obj-m += hello.o
obj-m += led_driver.o
obj-m += button_driver.o

Kbuild builds each declared module separately, provided the corresponding source files and dependencies are available.

Example project structure:

my_drivers/
|
|-- Makefile
|-- hello.c
|-- led_driver.c
|-- button_driver.c

Typical module outputs: 

hello.ko
led_driver.ko
button_driver.ko

9. Composite Modules

Sometimes a single kernel module consists of multiple C source files. Kbuild supports this using a composite object declaration.

Example:

obj-m += my_driver.o

my_driver-y := main.o helper.o

Here, main.o and helper.o are combined to create one loadable module named my_driver.ko.

Example project structure:

my_driver/
|
|-- Makefile
|-- main.c
|-- helper.c
|-- helper.h

This is different from declaring multiple independent modules using separate obj-m entries.

10. Understanding obj-m and obj-y Through an Analogy

Consider two ways of including software functionality in a system:

  • Loadable module: A separate component that can be loaded when required.
  • Built-in component: A component incorporated into the kernel during the build.

This is a useful conceptual distinction, although actual kernel build and loading behavior is controlled by Kbuild, kernel configuration and module-management rules.

↓
Separate .ko Module
↓

11. Why Does the Difference Matter?

Advantages of Loadable Modules

  • Drivers can often be loaded only when required.
  • Modules can be updated independently of the complete kernel image, subject to compatibility and deployment requirements.
  • They help keep optional functionality outside the permanently built-in kernel.
  • They are useful for many device drivers and optional kernel features.

Advantages of Built-in Components

  • Components are available as part of the kernel from the start of execution.
  • They can support early boot requirements.
  • They do not depend on a separate module-loading step.
  • They are useful for functionality required before a module-loading mechanism is available.

The choice depends on the component's role, boot requirements, kernel configuration and deployment design.

12. Common Mistakes

Mistake Correct Understanding
Assuming obj-m builds a built-in component. obj-m specifies a loadable module.
Assuming obj-y generates a separate .ko file. obj-y specifies built-in objects in an in-tree build.
Using obj-y as a replacement for obj-m in an external module project. External modules are normally declared with obj-m.
Assuming every kernel driver is a loadable module. A driver can be built-in or modular, depending on configuration and implementation.
Assuming built-in components can be removed using rmmod. Built-in components cannot be independently unloaded.

13. Practical Exercise

Create a simple external module and use obj-m to build it.

Step 1: Create the Directory

mkdir obj_m_practice
cd obj_m_practice

Step 2: Create hello.c

#include <linux/module.h>
#include <linux/kernel.h>

static int __init hello_init(void)
{
    pr_info("obj-m module loaded\n");
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("obj-m module unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("obj-m practice module");

Step 3: Create Makefile

obj-m += hello.o

all:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Step 4: Compile

make

Step 5: Check the Output

ls -l hello.ko
modinfo hello.ko

Step 6: Clean

make clean

This exercise demonstrates how obj-m is used in an external module build.

The obj-y variable is normally studied by examining Makefiles inside a configured Linux kernel source tree. Do not try to build an external module as a built-in component merely by changing obj-m to obj-y.

14. Summary

  • obj-m is used for loadable kernel modules.
  • obj-y is used for built-in kernel objects.
  • Loadable modules are normally generated as separate .ko files.
  • Built-in objects are incorporated into the kernel build.
  • Kernel configuration determines whether supported components are built-in, modular or excluded.
  • External module Makefiles commonly use obj-m.
  • Multiple independent modules can be declared using multiple obj-m entries.
  • Composite modules combine multiple object files into one module.
  • Built-in components cannot be independently unloaded.
