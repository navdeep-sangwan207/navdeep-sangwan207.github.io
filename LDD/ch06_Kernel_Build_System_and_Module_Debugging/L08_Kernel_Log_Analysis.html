1. Introduction

The Linux kernel performs many operations internally, including process scheduling, memory management, interrupt handling, device communication and module management.

When a problem occurs, the kernel can generate diagnostic messages that help developers understand what happened.

These messages are called kernel log messages. They are particularly important in Linux device driver development because many driver operations take place inside kernel space.

Kernel log analysis is the process of examining these messages to identify errors, warnings, initialization failures and unexpected system behavior.

2. What Are Kernel Logs?

Kernel logs are diagnostic messages generated by the Linux kernel and kernel components.

They may contain information about:

  • Kernel initialization.
  • Hardware detection.
  • Device driver initialization.
  • Kernel module loading and unloading.
  • Memory allocation failures.
  • Interrupt-related problems.
  • Kernel warnings and errors.
  • Kernel crashes and hardware faults.

3. Kernel Ring Buffer

The kernel ring buffer is a memory-based buffer that stores kernel messages.

Messages generated by functions such as printk() are recorded in the kernel logging system and can be read using tools such as dmesg.

Important Characteristics

  • Stores kernel diagnostic messages.
  • Uses a circular or ring-buffer organization.
  • Older messages may be overwritten as new messages arrive.
  • Provides information about kernel and driver activity.
  • Can be inspected from user space.

New messages enter as the buffer continues to operate.

The kernel ring buffer is not the same as a permanent log file. Messages may be lost when the buffer wraps or when the system restarts.

4. printk() and Kernel Logging

printk() is a kernel logging function used to generate messages from kernel code.

Example:

#include <linux/kernel.h>

printk("Device driver initialized\n");

The message can be inspected using: 

sudo dmesg

Linux also provides convenient logging macros such as pr_info(), pr_err(), pr_warn() and pr_debug(). 

pr_info("Driver initialized\n");
pr_warn("Device configuration warning\n");
pr_err("Device initialization failed\n");

These macros make kernel logging more readable and allow messages to carry appropriate severity levels.

5. Kernel Log Levels

Kernel messages have different severity levels. These levels help developers distinguish normal information from serious failures.

Level Name Meaning
0 KERN_EMERG System is unusable.
1 KERN_ALERT Action must be taken immediately.
2 KERN_CRIT Critical condition.
3 KERN_ERR Error condition.
4 KERN_WARNING Warning condition.
5 KERN_NOTICE Normal but significant condition.
6 KERN_INFO Informational message.
7 KERN_DEBUG Debug-level message.

Example:

printk(KERN_INFO "Device initialized\n");
printk(KERN_ERR "Device initialization failed\n");
printk(KERN_WARNING "Configuration warning\n");

The severity level helps control which messages are displayed on the console. It does not mean that every message is permanently stored.

6. Understanding dmesg

The dmesg command displays messages from the kernel ring buffer.

Display All Available Messages

sudo dmesg

Display Recent Messages

sudo dmesg | tail -20

Display the Last 50 Messages

sudo dmesg | tail -50

Display Messages with Human-Readable Timestamps

sudo dmesg -T

Clear the Ring Buffer

sudo dmesg -C
Clearing the ring buffer removes its currently retained messages. It does not clear persistent system journal records. Use this command carefully because it can remove useful diagnostic evidence.

7. Filtering Kernel Log Messages

A large kernel log can contain thousands of messages. Filtering makes it easier to find relevant information.

Search for Errors

sudo dmesg | grep -i error

Search for Warnings

sudo dmesg | grep -i warning

Search for a Specific Module

sudo dmesg | grep -i hello

Search for USB Messages

sudo dmesg | grep -i usb

Search for I2C Messages

sudo dmesg | grep -i i2c

Search for Multiple Terms

sudo dmesg | grep -Ei 'error|failed|warning'

The -i option ignores letter case, while -E enables extended regular expression matching.

8. Following Kernel Logs in Real Time

During driver development, it is useful to monitor kernel messages while performing an operation.

Using dmesg -w

sudo dmesg -w

This command waits for new kernel messages and displays them as they arrive.

Example Workflow

  1. Open Terminal 1.
  2. Run sudo dmesg -w.
  3. Open Terminal 2.
  4. Load a test kernel module.
  5. Observe initialization messages in Terminal 1.
  6. Remove the module and observe cleanup messages.
sudo insmod hello.ko
sudo rmmod hello

Press Ctrl+C in Terminal 1 to stop monitoring.

9. Kernel Logs and systemd Journal

Modern Linux distributions often use systemd's journal service to collect system and kernel logs.

The journalctl command can be used to inspect kernel messages and other system logs.

Display Kernel Messages

sudo journalctl -k

Display Kernel Messages from the Current Boot

sudo journalctl -k -b

Display Recent Kernel Messages

sudo journalctl -k -n 50

Follow Kernel Messages

sudo journalctl -k -f

Display Kernel Messages Since a Time

sudo journalctl -k --since "1 hour ago"
dmesg journalctl -k
Reads kernel messages from the ring buffer. Reads kernel messages collected by the systemd journal.
Useful for immediate kernel diagnostics. Useful for examining current and retained boot history.
Ring buffer contents can be overwritten. Journal retention depends on system configuration.

10. Understanding Kernel Log Timestamps

Kernel log messages commonly contain timestamps. These indicate the time associated with a message, often measured relative to the start of the current boot.

Example:

[  12.450000] hello: module initialized
[  18.320000] hello: device operation started
[  25.100000] hello: module removed

Interpretation:

  • 12.450000 represents the message timestamp.
  • The first message indicates module initialization.
  • The second message indicates a later operation.
  • The third message indicates module removal.

Use dmesg -T when a human-readable date and time representation is useful.

Human-readable timestamps are converted using the system clock and may be affected by clock adjustments. For precise timing analysis, understand the timestamp source used by the logging tool.

11. Analyzing Device Driver Messages

Device drivers often generate messages during initialization, device detection, configuration and error handling.

Example driver log messages:

[  10.120000] my_driver: initialization started
[  10.150000] my_driver: device detected
[  10.180000] my_driver: configuration completed
[  10.200000] my_driver: initialization successful

What to Look For

  • Did the driver initialization function execute?
  • Was the device detected?
  • Did resource allocation succeed?
  • Was the device configuration completed?
  • Did any error occur before initialization finished?

If initialization stops after a particular message, investigate the next operation performed by the driver.

12. Common Kernel Log Messages

Log Message Possible Meaning
Unknown symbol A required symbol could not be resolved.
Invalid module format The module is incompatible with the running kernel or its expected format.
Out of memory A memory allocation or memory-related operation failed.
Device or resource busy A resource is already occupied or cannot be accessed.
Permission denied An operation was rejected due to permissions or security policy.
Kernel BUG The kernel encountered an internal bug condition.
Oops The kernel encountered an unexpected fault or invalid operation.

A message must be interpreted in its surrounding context. The same phrase can have different implications depending on the subsystem and operation.

13. Kernel Log Levels and Filtering

Kernel messages have severity levels that can be used to identify important conditions.

Display Messages at Error Severity

sudo dmesg --level=err

Display Errors and Warnings

sudo dmesg --level=err,warn

Display Information and Higher-Severity Messages

sudo dmesg --level=info

Supported filtering options can vary with the util-linux version. Use dmesg --help to inspect the available options.

Message filtering is different from changing the kernel console log level. Filtering selects messages for display; console log-level settings control which messages are printed to the console.

14. Kernel Log Analysis Workflow

A systematic approach helps prevent incorrect conclusions when diagnosing driver problems.

Reproduce the Driver Problem
↓
Capture Kernel Messages
↓
Filter Relevant Messages
↓
Identify Errors and Warnings
↓
Analyze Timestamps and Message Order
↓
Locate the Failing Driver Operation
↓
Correct and Retest

Recommended Procedure

  1. Record the kernel version using uname -r.
  2. Capture the current kernel log.
  3. Reproduce the problem.
  4. Capture new messages using dmesg.
  5. Filter messages related to the driver.
  6. Identify the first relevant warning or error.
  7. Correlate timestamps with driver operations.
  8. Correct the underlying problem.
  9. Repeat the test and compare results.

15. Practical Project: Analyze Kernel Module Logs

In this exercise, create a module that generates messages at different severity levels.

Step 1: Create Project Directory

mkdir kernel_log_practice
cd kernel_log_practice

Step 2: Create hello.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init hello_init(void)
{
    pr_info("hello: module initialization started\n");
    pr_warn("hello: example warning message\n");
    pr_err("hello: example error-level test message\n");

    pr_info("hello: module initialization successful\n");

    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("hello: module cleanup executed\n");
}

module_init(hello_init);
module_exit(hello_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Kernel logging practice module");

The error-level message in this exercise is deliberately generated for logging practice. It does not indicate that initialization failed.

Step 3: Create Makefile

obj-m += hello.o

all:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	$(MAKE) -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Step 4: Compile the Module

make

Step 5: Load the Module

sudo insmod hello.ko

Step 6: View Kernel Messages

sudo dmesg | tail -30

Step 7: Filter Messages

sudo dmesg | grep -i hello

Step 8: Remove the Module

sudo rmmod hello

Step 9: Verify Cleanup Message

sudo dmesg | grep -i hello

Step 10: Inspect Journal Logs

sudo journalctl -k -n 50
Expected result: you should be able to identify initialization, warning, error-level test and cleanup messages in the kernel log.

16. Important Precautions During Log Analysis

  • Do not assume every error-level message means a kernel failure.
  • Read surrounding messages before interpreting an error.
  • Consider the order and timestamps of messages.
  • Remember that old ring-buffer messages can be overwritten.
  • Use persistent journal records when available.
  • Avoid clearing logs before collecting useful diagnostic information.
  • Do not expose sensitive information from system logs when sharing them.
  • Use appropriate logging levels in production drivers.
  • Avoid excessive logging in frequently executed or performance-critical paths.

17. Summary

  • Kernel logs provide diagnostic information about kernel activity.
  • The kernel ring buffer stores recent kernel messages.
  • printk() and pr_*() macros generate kernel messages.
  • Kernel messages have different severity levels.
  • dmesg displays ring-buffer messages.
  • journalctl -k displays kernel messages from the system journal.
  • grep helps filter relevant messages.
  • Real-time monitoring helps diagnose module behavior.
  • Timestamps help correlate messages with driver operations.
  • Systematic log analysis makes driver debugging more effective.
