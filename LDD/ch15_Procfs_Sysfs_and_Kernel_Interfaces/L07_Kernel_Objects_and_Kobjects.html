2. Introduction to Kernel Objects

The Linux kernel manages many different types of objects, including devices, drivers, buses and kernel subsystems.

These objects have relationships with one another. For example:

  • A device may belong to a particular bus.
  • A driver may be registered with a bus.
  • A device may have a parent controller.
  • A device may belong to a functional class.

The Linux device model provides a common framework for representing and managing these relationships. The kobject infrastructure is one of its fundamental building blocks.

3. What Is a Kobject?

A kobject is a fundamental kernel object-management structure used by the Linux kernel.

It provides common functionality for objects that participate in the kernel object model.

The main structure is: 

struct kobject;

The complete definition is available in the kernel header: 

#include <linux/kobject.h>

Main responsibilities of a kobject

  • Object naming.
  • Reference counting.
  • Parent-child relationships.
  • Association with a kset.
  • Sysfs representation.
  • Object lifecycle management.
A kobject is usually embedded inside a larger kernel structure. It provides common object-management facilities rather than representing a complete hardware device by itself.

4. Why Are Kobjects Needed?

Without a common object-management mechanism, different kernel subsystems would need to implement their own independent methods for naming, tracking and managing objects.

Kobjects provide shared infrastructure for these tasks.

Important reasons

  1. Provide a common object representation.
  2. Maintain object lifetime using reference counting.
  3. Represent parent-child relationships.
  4. Support integration with Sysfs.
  5. Help organize kernel objects into groups.
  6. Support object-related notifications and lifecycle handling.

5. The struct kobject Structure

The kobject structure is defined in the Linux kernel headers. Its internal fields are implementation details and may change between kernel versions.

Conceptually, a kobject maintains information such as:

Concept Purpose
Name Identifies the object in the object hierarchy.
Reference count Tracks references to the object.
Parent Represents the object's parent relationship.
Kset association Associates the object with a group of related objects.
Ktype Provides object-type-specific behavior and release handling.

A kobject is not normally allocated and managed as an isolated replacement for a device structure. It is commonly embedded in a subsystem-specific object.

6. Kobject and the Linux Device Model

The Linux device model uses kobjects as part of its object-management infrastructure.

For example, the device structure contains a kobject as one of its components. 

struct device {
    /* Other device fields */

    struct kobject kobj;

    /* Additional device fields */
};

This is a simplified conceptual illustration, not the complete current definition of struct device.

Because the kobject is embedded inside a larger object, the device model can use common kobject functionality while maintaining device-specific information separately.

7. Kobject Hierarchy

Kobjects can be organized into parent-child relationships. This creates a hierarchy that can be reflected in Sysfs.

Conceptual example

Root Object
│
├── Device A
│   ├── Attribute 1
│   └── Attribute 2
│
├── Device B
│   └── Attribute 1
│
└── Device C

The parent-child relationship helps represent how objects are organized.

When an object is registered with a parent, its position in the object hierarchy can be reflected in the Sysfs directory structure.

The actual Linux device hierarchy is more complex. It reflects the relationships maintained by the device model and other kernel subsystems.

8. Kobject and Sysfs

Sysfs provides a filesystem representation of kernel objects. Kobjects are closely integrated with this representation.

A registered kobject can have a corresponding directory in Sysfs.

Conceptual example

/sys/
└── example_object/
    ├── attribute1
    └── attribute2

The directory represents an object, while its attribute files expose selected information about that object.

Relationship

  • Kobject represents an object in the kernel object model.
  • Sysfs provides a user-space-visible representation.
  • Attributes expose selected object properties.
  • Callbacks handle attribute access.

9. Reference Counting in Kobjects

Reference counting is an important part of kernel object lifetime management.

A reference count tracks how many active references exist to an object.

Basic concept

  • When a reference is acquired, the count is increased.
  • When a reference is released, the count is decreased.
  • When the final reference is released, the object's release handling is invoked.
Reference Acquired
↓
Reference Count Increases
↓
Object Remains Referenced
↓ Final Reference Released
Release Callback

Important functions

Function Purpose
kobject_get() Obtains an additional reference to a kobject.
kobject_put() Releases a reference to a kobject.

The reference count is managed through these APIs. Driver code should not directly modify internal reference-count fields.

A reference-count error can cause use-after-free problems or memory leaks. Every acquired reference must be released according to the object's ownership rules.

10. Kobject Release Function

A kobject's release function handles the final cleanup of the containing object when its reference count reaches zero.

The release behavior is associated with a struct kobj_type.

A conceptual callback looks like this: 

static void example_release(struct kobject *kobj)
{
    struct example_object *obj;

    obj = container_of(kobj,
                       struct example_object,
                       kobj);

    kfree(obj);
}

This example assumes that the containing object was dynamically allocated and that its release callback owns the responsibility for freeing it.

Understanding container_of()

The container_of() macro obtains a pointer to the larger structure containing a specified member.

In this example, it converts the kobject pointer back into a pointer to struct example_object.

The release callback must free the object using the correct ownership and allocation rules. It must not free memory that belongs to a different owner.

11. Ktypes

A ktype describes behavior associated with a particular kind of kobject.

The corresponding kernel structure is: 

struct kobj_type;

A ktype can provide:

  • Release callback.
  • Default attribute groups.
  • Sysfs operations for the object type.

A simplified conceptual example is: 

static struct kobj_type example_ktype = {
    .release = example_release,
};

This illustrates the association of a release callback. Actual ktype definitions may also provide attribute groups and other operations.

12. Ksets

A kset is a collection of related kobjects. It provides a way to organize objects that belong to a common group.

The corresponding kernel structure is: 

struct kset;

Purpose of a kset

  • Group related kernel objects.
  • Support object organization.
  • Provide a common association for objects.
  • Support object-related notification mechanisms.

Conceptual example

Device Kset
│
├── Device Object A
├── Device Object B
└── Device Object C

The objects in a kset are related members of a collection. A kset is not simply another name for a parent-child hierarchy.

Concept Purpose
Kobject Represents and manages an individual kernel object.
Kset Groups related kobjects.
Ktype Defines behavior associated with a type of kobject.

13. Important Kobject Functions

Function Purpose
kobject_init() Initializes a kobject using a supplied ktype.
kobject_add() Adds an initialized kobject to the hierarchy.
kobject_init_and_add() Initializes and adds a kobject in one operation.
kobject_get() Acquires a reference to a kobject.
kobject_put() Releases a reference to a kobject.
kobject_del() Removes a kobject from the Sysfs hierarchy.
kobject_create_and_add() Creates and registers a dynamically allocated kobject.
kobject_put() Also participates in final object release when the last reference is dropped.
These functions have different ownership and lifecycle requirements. In particular, removing a kobject from Sysfs and releasing its final reference are distinct operations. Consult the kernel documentation for the target kernel version before implementing object lifecycle management.

14. Kobject Lifecycle

A typical kobject lifecycle includes allocation, initialization, registration, use and release.

Allocate Containing Object
↓
Initialize Kobject
↓
Add to Object Hierarchy
↓
Use Object and Attributes
↓
Remove from Sysfs
↓
Release References
↓
Release Callback

Lifecycle stages

  1. Allocation: Allocate the containing object using an appropriate memory-management method.
  2. Initialization: Initialize its kobject using the correct ktype.
  3. Registration: Add the object to its intended hierarchy.
  4. Use: Expose and use its supported attributes.
  5. Removal: Remove the object from the Sysfs hierarchy when appropriate.
  6. Reference release: Release owned references.
  7. Final cleanup: The release callback handles final object cleanup.
Never free a kobject-containing object merely because its Sysfs directory has been removed. Other references may still exist. Follow the reference-counting and ownership rules of the relevant subsystem.

15. Conceptual Kobject Example

The following example illustrates how a dynamically allocated object can contain a kobject and define a release callback.

It is an educational illustration of the kobject lifecycle, not a complete production driver. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/kobject.h>
#include <linux/slab.h>

struct example_object {
    struct kobject kobj;
};

static struct example_object *example;

static void example_release(struct kobject *kobj)
{
    struct example_object *obj;

    obj = container_of(kobj,
                       struct example_object,
                       kobj);

    pr_info("example object released\n");
    kfree(obj);
}

static struct kobj_type example_ktype = {
    .release = example_release,
};

static int __init example_init(void)
{
    int ret;

    example = kzalloc(sizeof(*example), GFP_KERNEL);
    if (!example)
        return -ENOMEM;

    ret = kobject_init_and_add(&example->kobj,
                               &example_ktype,
                               NULL,
                               "%s",
                               "example_object");

    if (ret) {
        kobject_put(&example->kobj);
        example = NULL;
        return ret;
    }

    pr_info("example kobject registered\n");

    return 0;
}

static void __exit example_exit(void)
{
    if (example) {
        kobject_del(&example->kobj);
        kobject_put(&example->kobj);
        example = NULL;
    }

    pr_info("example module unloaded\n");
}

module_init(example_init);
module_exit(example_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Educational Kobject Example");

Explanation

  • struct example_object contains a kobject.
  • kzalloc() allocates and zero-initializes the containing structure.
  • kobject_init_and_add() initializes the kobject and registers it in Sysfs.
  • The object appears under the Sysfs root as /sys/example_object, assuming registration succeeds.
  • example_release() is called when the final kobject reference is released.
  • kobject_del() removes the Sysfs representation.
  • kobject_put() releases the module's reference and allows final cleanup.
This example demonstrates the lifecycle of a simple standalone kobject. It does not yet create attributes. In production code, registration failure paths, additional references, concurrent access and object ownership must all be handled carefully.

16. Kobject vs Device Structure

Feature Kobject Device Structure
Representation General kernel object-management component. Represents a device in the Linux device model.
Header linux/kobject.h linux/device.h
Purpose Naming, reference counting and object hierarchy. Device-specific management and relationships.
Sysfs Provides the underlying object representation. Device-model objects are exposed through Sysfs.

A device structure uses kobject infrastructure, but a kobject by itself is not a complete device structure.

18. Practical Sysfs Inspection

You can inspect real kernel objects in Ubuntu without writing a kernel module.

Step 1: Inspect the root directory

ls /sys

Step 2: Inspect the device hierarchy

ls /sys/devices

Step 3: Inspect network class objects

ls -l /sys/class/net

Step 4: Resolve a network interface link

readlink -f /sys/class/net/lo

Step 5: Inspect bus objects

ls /sys/bus

Step 6: Inspect module objects

ls /sys/module | head

Step 7: Inspect kernel objects and interfaces

ls /sys/kernel

These commands provide a practical view of the object hierarchy managed by the running kernel.

19. Common Mistakes in Kobject Programming

Mistake Why It Is a Problem
Freeing the object too early Other references may still use the object.
Forgetting kobject_put() Can cause a reference leak.
Using the wrong ktype Can result in incorrect release handling.
Ignoring registration errors Can leave incomplete object initialization.
Confusing kset and parent hierarchy They represent different organizational concepts.
Accessing freed object memory Can cause use-after-free errors and kernel instability.

20. Lesson Summary

  • Kobjects are fundamental components of the Linux kernel object model.
  • They provide common object-management functionality.
  • Kobjects support naming, reference counting and hierarchy.
  • Sysfs provides a filesystem representation of registered kernel objects.
  • Kernel device structures commonly contain embedded kobjects.
  • Reference counting manages object lifetime.
  • Ktypes define object-specific behavior, including release handling.
  • Ksets organize related kobjects.
  • kobject_get() acquires a reference.
  • kobject_put() releases a reference.
  • Object removal and final memory release are separate lifecycle events.
