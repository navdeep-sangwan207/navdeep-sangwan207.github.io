  • Implement basic Sysfs interfaces for device and driver objects.

2. Introduction

Linux device drivers often need to expose information to user-space applications. Sysfs provides a structured interface for exposing selected device and driver properties.

Two important categories are:

  1. Device attributes: Associated with an individual device object.
  2. Driver attributes: Associated with a driver object and generally describe driver-wide information.

The choice depends on what the information represents. For example:

Information Appropriate Attribute
Temperature of one sensor Device attribute
Operating mode of one device Device attribute
Driver-wide diagnostic setting Driver attribute, if supported by the subsystem
Driver-wide version information Driver attribute or another established interface
Always use the interface provided by the relevant kernel subsystem when one exists. A custom Sysfs attribute should not duplicate an established subsystem interface.

3. What Is a Device Attribute?

A device attribute is a Sysfs attribute associated with a particular device object.

It is commonly used to expose information or controls that belong to one device instance.

Examples

  • Sensor temperature.
  • Device operating state.
  • Device configuration.
  • Device-specific measurement.
  • Device-specific status information.

Typical Sysfs locations

/sys/devices/...
/sys/class/...
/sys/bus/.../devices/...

These paths represent different views of the device model. Some entries are symbolic links to the same underlying device object.

Example

/sys/class/net/lo/mtu

This attribute exposes the MTU associated with the loopback network device.

4. What Is a Driver Attribute?

A driver attribute is a Sysfs attribute associated with a driver object.

It is generally used for information or configuration that applies to the driver as a whole rather than to one particular device instance.

Examples of possible driver-wide information

  • Driver-wide diagnostic settings.
  • Driver-wide configuration parameters.
  • Driver implementation information.
  • Driver-wide operational controls, where appropriate.

Typical Sysfs locations

/sys/bus/<bus-name>/drivers/<driver-name>/

For example, drivers registered with the platform bus are represented under the platform bus driver hierarchy. 

/sys/bus/platform/drivers/

The actual driver directory depends on the bus and driver registration.

Driver attributes are not a universal mechanism for every type of driver. Their availability and registration method depend on the relevant driver model and subsystem.

6. Device Attribute Structure

Device attributes use the following structure: 

struct device_attribute;

The relevant header is: 

#include <linux/device.h>

The structure associates a generic attribute definition with device-specific read and write callbacks.

Device attribute callback signatures

Read callback:

ssize_t show(struct device *dev,
             struct device_attribute *attr,
             char *buf);

Write callback:

ssize_t store(struct device *dev,
              struct device_attribute *attr,
              const char *buf,
              size_t count);

Common macros

DEVICE_ATTR_RO(name);
DEVICE_ATTR_WO(name);
DEVICE_ATTR_RW(name);

These macros simplify the declaration of read-only, write-only and read-write device attributes.

7. Creating a Device Attribute

Consider a device driver that wants to expose a read-only status attribute.

Example callback

static ssize_t status_show(struct device *dev,
                           struct device_attribute *attr,
                           char *buf)
{
    return sysfs_emit(buf, "Device is ready\n");
}

static DEVICE_ATTR_RO(status);

The macro creates the device attribute descriptor associated with status_show().

Registering the attribute

ret = device_create_file(dev, &dev_attr_status);

if (ret)
    return ret;

Here, dev is a valid device pointer owned and managed by the driver or subsystem.

Removing the attribute

device_remove_file(dev, &dev_attr_status);

The attribute should be removed before the associated device object is destroyed.

8. Driver Attribute Structure

Driver attributes are associated with a struct device_driver object.

The relevant header is: 

#include <linux/device.h>

The driver attribute structure is: 

struct driver_attribute;

Driver attribute callback signatures

Read callback:

ssize_t show(struct device_driver *drv,
             char *buf);

Write callback:

ssize_t store(struct device_driver *drv,
              const char *buf,
              size_t count);

The driver callback receives a driver object rather than an individual device object.

Driver attribute macros

DRIVER_ATTR_RO(name);
DRIVER_ATTR_WO(name);
DRIVER_ATTR_RW(name);

These macros declare driver attributes using the corresponding callback naming convention.

9. Creating a Driver Attribute

The following example illustrates a read-only driver attribute that reports a driver-wide identification string. 

#include <linux/module.h>
#include <linux/device.h>
#include <linux/kernel.h>

static ssize_t version_show(struct device_driver *drv,
                            char *buf)
{
    return sysfs_emit(buf, "Example Driver 1.0\n");
}

static DRIVER_ATTR_RO(version);

This declares a driver attribute descriptor named driver_attr_version.

A driver object can expose this attribute using the driver attribute registration API.

Registering the attribute

ret = driver_create_file(drv, &driver_attr_version);

if (ret)
    return ret;

Removing the attribute

driver_remove_file(drv, &driver_attr_version);

Here, drv is a valid registered driver object. Registration and removal must be coordinated with the lifetime of that object.

10. Device Attribute Registration vs Driver Attribute Registration

Operation Device Attribute Driver Attribute
Creation device_create_file() driver_create_file()
Removal device_remove_file() driver_remove_file()
Descriptor dev_attr_name driver_attr_name
Object struct device struct device_driver

The registration API must match the attribute type. A device attribute must not be passed to a driver attribute registration function, or vice versa.

11. Attribute Groups for Device Attributes

Multiple device attributes can be organized into an attribute group.

Example

static ssize_t status_show(struct device *dev,
                           struct device_attribute *attr,
                           char *buf)
{
    return sysfs_emit(buf, "ready\n");
}

static ssize_t value_show(struct device *dev,
                          struct device_attribute *attr,
                          char *buf)
{
    return sysfs_emit(buf, "100\n");
}

static DEVICE_ATTR_RO(status);
static DEVICE_ATTR_RO(value);

static struct attribute *device_attrs[] = {
    &dev_attr_status.attr,
    &dev_attr_value.attr,
    NULL,
};

static const struct attribute_group device_group = {
    .attrs = device_attrs,
};

The group can be created for a device's kobject using the Sysfs group API. 

ret = sysfs_create_group(&dev->kobj, &device_group);

To remove it: 

sysfs_remove_group(&dev->kobj, &device_group);

This approach is useful when a driver needs to expose several related attributes together.

12. Attribute Groups for Driver Attributes

Driver attributes can also be organized into groups using the appropriate Sysfs and driver-model facilities.

The generic attribute-group mechanism operates on a kobject. For driver-specific groups, the driver model provides the groups member in struct device_driver.

Conceptual declaration

static const struct attribute_group example_driver_group = {
    .attrs = example_driver_attrs,
};

static const struct attribute_group *example_groups[] = {
    &example_driver_group,
    NULL,
};

The group array can be assigned to the driver's groups member before registering the driver. The driver core manages these groups as part of the driver's registration lifecycle.

Prefer driver-model-managed attribute groups when attributes naturally belong to the driver's lifetime. This reduces the risk of creating attributes too early or removing them too late.

13. Device Attributes and Driver Attributes in Sysfs

Conceptual hierarchy

/sys/
└── bus/
    └── platform/
        ├── devices/
        │   └── example-device/
        │       ├── status
        │       └── value
        │
        └── drivers/
            └── example-driver/
                ├── bind
                ├── unbind
                └── version

This illustrates the distinction between device-level and driver-level interfaces.

The actual hierarchy depends on the bus, registered objects, kernel configuration and driver implementation. Existing attributes such as bind and unbind are provided by relevant driver-model infrastructure; they are not automatically created by every driver.

Inspecting platform drivers

ls /sys/bus/platform/drivers

Inspecting platform devices

ls /sys/bus/platform/devices

Inspecting a driver directory

ls -l /sys/bus/platform/drivers

You may see different results depending on the Ubuntu kernel and virtual machine configuration.

14. Choosing Between Device and Driver Attributes

The most important design question is:

Does the information belong to one device instance or to the driver as a whole?

Requirement Recommended Interface
Read the temperature of sensor A Device attribute for sensor A
Read the temperature of sensor B Device attribute for sensor B
Change one device's operating mode Device attribute, if appropriate
Expose a driver-wide diagnostic setting Driver attribute, if appropriate
Expose a standard bus or subsystem property Prefer the existing subsystem interface
Do not place per-device information in a driver-wide attribute if the driver manages multiple devices. Doing so can make it unclear which device the value describes or controls.

15. Synchronization and Data Management

Sysfs callbacks may access data shared with other driver operations. Such data must be protected appropriately.

Example using a mutex

static int device_mode;
static DEFINE_MUTEX(mode_lock);

static ssize_t mode_show(struct device *dev,
                         struct device_attribute *attr,
                         char *buf)
{
    int mode;

    mutex_lock(&mode_lock);
    mode = device_mode;
    mutex_unlock(&mode_lock);

    return sysfs_emit(buf, "%d\n", mode);
}

The mutex protects access to the shared variable. The same lock should be used by other code that modifies this variable under the same synchronization design.

Important considerations

  • Protect shared data against concurrent access.
  • Validate user-supplied values.
  • Do not hold a mutex across unrelated lengthy operations.
  • Do not access a device object after its lifetime ends.
  • Respect subsystem-specific locking requirements.

16. Practical Inspection in Ubuntu

You can inspect existing device and driver attributes in your Ubuntu virtual machine.

Step 1: Inspect network device attributes

ls /sys/class/net/lo

Step 2: Read the MTU

cat /sys/class/net/lo/mtu

Step 3: Read the operational state

cat /sys/class/net/lo/operstate

Step 4: Inspect the device hierarchy

readlink -f /sys/class/net/lo

Step 5: Inspect available bus drivers

ls /sys/bus/platform/drivers

Step 6: Inspect available bus devices

ls /sys/bus/platform/devices

Step 7: Inspect one driver directory

Choose a driver directory that actually exists on your system, then inspect it: 

ls -l /sys/bus/platform/drivers/<driver-name>
These commands inspect existing kernel interfaces. They do not require you to create or modify any system attributes.

17. Common Programming Mistakes

Mistake Problem Correct Practice
Using device attribute APIs for driver attributes Incorrect object and callback type. Use matching driver attribute APIs.
Exposing per-device data as driver-wide data Ambiguous results with multiple devices. Use device attributes.
Ignoring registration errors Incomplete interface initialization. Check return values and unwind resources.
Forgetting attribute removal Incorrect object lifecycle. Remove attributes before object destruction.
Skipping input validation Invalid or unsafe configuration. Validate all user input.
Ignoring concurrent access Race conditions and inconsistent state. Use suitable synchronization.

18. Lesson Summary

  • Device attributes belong to individual device objects.
  • Driver attributes belong to driver objects.
  • Device attributes use struct device_attribute.
  • Driver attributes use struct driver_attribute.
  • Device callbacks receive a struct device pointer.
  • Driver callbacks receive a struct device_driver pointer.
  • DEVICE_ATTR macros declare device attributes.
  • DRIVER_ATTR macros declare driver attributes.
  • device_create_file() and device_remove_file() manage individual device attributes.
  • driver_create_file() and driver_remove_file() manage individual driver attributes.
  • Attribute groups help organize related attributes.
  • Correct object lifetime, synchronization and validation are essential.
