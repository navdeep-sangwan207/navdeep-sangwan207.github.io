2. Introduction to Sysfs Attributes

Sysfs attributes are file-like interfaces used to expose selected information about kernel objects to user space.

A device driver can use attributes to provide information such as:

  • Device status.
  • Operating mode.
  • Configuration values.
  • Sensor measurements.
  • Driver-specific parameters.

Example

/sys/class/net/lo/mtu

This file exposes the MTU value associated with the loopback network interface.

A user-space program can read the value using: 

cat /sys/class/net/lo/mtu

A driver can similarly expose its own attributes using the Sysfs APIs.

Sysfs is designed mainly for simple text-based attributes. It is not intended to be a general-purpose mechanism for transferring large amounts of data.

3. What Is a Sysfs Attribute?

A Sysfs attribute is an interface associated with a kernel object.

It is commonly represented as a file inside a Sysfs directory.

Conceptual structure

/sys/
└── example_device/
    ├── status
    ├── mode
    └── value
Attribute Possible Purpose
status Reports the current device state.
mode Reports or configures an operating mode.
value Reports a measurement or configuration value.

The actual attributes exposed by a driver depend on its design and the relevant kernel subsystem.

4. How Sysfs Attributes Work

Sysfs attributes connect user-space file operations to kernel callback functions.

User-Space Application
↓ read() / write()
Sysfs Attribute File
↓
show() / store() Callback
↓
Driver Data or Device State

Read operation

  1. User space opens an attribute file.
  2. The application requests data.
  3. Sysfs invokes the associated show callback.
  4. The callback formats the value as text.
  5. The result is returned to user space.

Write operation

  1. User space opens a writable attribute.
  2. The application submits text data.
  3. Sysfs invokes the associated store callback.
  4. The callback validates and processes the input.
  5. The driver updates the permitted state.

5. Device Attribute Structure

For attributes associated with a device object, Linux provides struct device_attribute.

The relevant header is: 

#include <linux/device.h>

Conceptually, a device attribute associates a basic attribute definition with device-specific callbacks.

The callbacks use the following signatures:

show() callback

ssize_t show(struct device *dev,
             struct device_attribute *attr,
             char *buf);

store() callback

ssize_t store(struct device *dev,
              struct device_attribute *attr,
              const char *buf,
              size_t count);
Parameter Meaning
dev Device associated with the attribute.
attr Attribute being accessed.
buf Output buffer for show(), or input data for store().
count Number of input bytes supplied to store().
The show() and store() callback signatures differ for generic kobject attributes and device attributes. This lesson focuses on device attributes.

6. The show() Function

The show() callback is used when user space reads a Sysfs attribute.

It formats the attribute value into the supplied buffer.

Example

static int device_value = 100;

static ssize_t value_show(struct device *dev,
                          struct device_attribute *attr,
                          char *buf)
{
    return sysfs_emit(buf, "%d\n", device_value);
}

Explanation

  • device_value stores the example value.
  • value_show() is invoked for a read.
  • sysfs_emit() formats the value safely into the Sysfs output buffer.
  • The callback returns the number of bytes produced.

For example, user space executes:

cat /sys/.../value

The callback returns the text representation of the value.

In modern kernel code, sysfs_emit() is preferred for formatting ordinary Sysfs text output.

7. The store() Function

The store() callback is used when user space writes to a writable Sysfs attribute.

Example

static int device_value = 100;

static ssize_t value_store(struct device *dev,
                           struct device_attribute *attr,
                           const char *buf,
                           size_t count)
{
    int value;
    int ret;

    ret = kstrtoint(buf, 10, &value);
    if (ret)
        return ret;

    if (value < 0 || value > 1000)
        return -EINVAL;

    device_value = value;

    return count;
}

Explanation

  1. The user supplies a text value.
  2. kstrtoint() converts it into an integer.
  3. The callback checks the permitted range.
  4. The value is updated only if validation succeeds.
  5. The callback returns the number of bytes consumed.

Example user-space command

echo 250 > /sys/.../value
This is an illustrative callback. A real driver must synchronize shared state where necessary and apply changes through the correct hardware or subsystem interface. Do not expose arbitrary hardware controls without proper validation.

8. DEVICE_ATTR Macros

Linux provides macros that simplify the declaration of device attributes.

The common macros include:

Macro Purpose
DEVICE_ATTR_RO(name) Declares a read-only device attribute.
DEVICE_ATTR_WO(name) Declares a write-only device attribute.
DEVICE_ATTR_RW(name) Declares a read-write device attribute.
DEVICE_ATTR(name, mode, show, store) Declares an attribute with an explicit permission mode and callbacks.

Read-only attribute

static ssize_t status_show(struct device *dev,
                           struct device_attribute *attr,
                           char *buf)
{
    return sysfs_emit(buf, "ready\n");
}

static DEVICE_ATTR_RO(status);

The macro associates the attribute with the status_show() callback.

Read-write attribute

static ssize_t value_show(struct device *dev,
                          struct device_attribute *attr,
                          char *buf)
{
    return sysfs_emit(buf, "%d\n", device_value);
}

static ssize_t value_store(struct device *dev,
                           struct device_attribute *attr,
                           const char *buf,
                           size_t count)
{
    int value;
    int ret;

    ret = kstrtoint(buf, 10, &value);
    if (ret)
        return ret;

    if (value < 0 || value > 1000)
        return -EINVAL;

    device_value = value;
    return count;
}

static DEVICE_ATTR_RW(value);
DEVICE_ATTR_RO, DEVICE_ATTR_WO and DEVICE_ATTR_RW are convenience macros. The corresponding callback names must follow the required naming convention.

9. Creating a Sysfs Attribute File

For a device object, an attribute can be registered using device_create_file().

Function

int device_create_file(struct device *dev,
                       const struct device_attribute *attr);

The function creates the attribute file associated with the specified device.

Removing an attribute

void device_remove_file(struct device *dev,
                        const struct device_attribute *attr);

This removes an attribute previously created for that device.

Function Purpose
device_create_file() Creates a device attribute.
device_remove_file() Removes a device attribute.
The device object must be valid and remain alive while the attribute is registered. Remove attributes before destroying the associated device object.

10. Attribute Groups

When a driver exposes multiple attributes, registering them individually may become difficult to maintain.

Sysfs provides attribute groups for organizing related attributes.

Conceptual example

static DEVICE_ATTR_RO(status);
static DEVICE_ATTR_RW(value);

static struct attribute *example_attrs[] = {
    &dev_attr_status.attr,
    &dev_attr_value.attr,
    NULL,
};

static const struct attribute_group example_group = {
    .attrs = example_attrs,
};

The group can be associated with a kobject using Sysfs attribute-group APIs, or supplied through the appropriate device-model mechanism.

Important functions

sysfs_create_group()
sysfs_remove_group()

These APIs create or remove a group of attributes associated with a kobject.

Attribute groups can also be associated with device objects through device-model attribute-group facilities.

11. Difference Between Individual Attributes and Attribute Groups

Feature Individual Attribute Attribute Group
Registration One attribute at a time. Multiple related attributes together.
Management Separate create and remove operations. Group-based management.
Organization Suitable for a small number of attributes. Useful for related attribute collections.
Typical APIs device_create_file(), device_remove_file() sysfs_create_group(), sysfs_remove_group()

12. Complete Practical Example: Sysfs Kernel Module

The following educational module creates a standalone kobject with two attributes:

  • status - read-only attribute.
  • value - read-write attribute.

The example uses a standalone kobject so that it can be tested without physical hardware or a registered device.

File: sysfs_example.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/kobject.h>
#include <linux/sysfs.h>
#include <linux/slab.h>
#include <linux/mutex.h>

static struct kobject *example_kobj;

static int device_value = 100;
static DEFINE_MUTEX(value_lock);

/* Read-only status attribute */

static ssize_t status_show(struct kobject *kobj,
                           struct kobj_attribute *attr,
                           char *buf)
{
    return sysfs_emit(buf, "Driver is active\n");
}

/* Read-write value attribute */

static ssize_t value_show(struct kobject *kobj,
                          struct kobj_attribute *attr,
                          char *buf)
{
    int value;

    mutex_lock(&value_lock);
    value = device_value;
    mutex_unlock(&value_lock);

    return sysfs_emit(buf, "%d\n", value);
}

static ssize_t value_store(struct kobject *kobj,
                           struct kobj_attribute *attr,
                           const char *buf,
                           size_t count)
{
    int value;
    int ret;

    ret = kstrtoint(buf, 10, &value);
    if (ret)
        return ret;

    if (value < 0 || value > 1000)
        return -EINVAL;

    mutex_lock(&value_lock);
    device_value = value;
    mutex_unlock(&value_lock);

    return count;
}

/* Declare attributes */

static struct kobj_attribute status_attr =
    __ATTR_RO(status);

static struct kobj_attribute value_attr =
    __ATTR_RW(value);

/* Attribute group */

static struct attribute *example_attrs[] = {
    &status_attr.attr,
    &value_attr.attr,
    NULL,
};

static const struct attribute_group example_group = {
    .attrs = example_attrs,
};

/* Module initialization */

static int __init sysfs_example_init(void)
{
    int ret;

    example_kobj = kobject_create_and_add(
        "sysfs_example", kernel_kobj);

    if (!example_kobj)
        return -ENOMEM;

    ret = sysfs_create_group(example_kobj,
                             &example_group);

    if (ret) {
        kobject_put(example_kobj);
        example_kobj = NULL;
        return ret;
    }

    pr_info("Sysfs example module loaded\n");

    return 0;
}

/* Module cleanup */

static void __exit sysfs_example_exit(void)
{
    if (example_kobj) {
        sysfs_remove_group(example_kobj,
                           &example_group);

        kobject_put(example_kobj);
        example_kobj = NULL;
    }

    pr_info("Sysfs example module unloaded\n");
}

module_init(sysfs_example_init);
module_exit(sysfs_example_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Sysfs Attribute Example");

Understanding the example

  1. kernel_kobj provides the parent kobject under the kernel Sysfs hierarchy.
  2. kobject_create_and_add() creates the directory /sys/kernel/sysfs_example.
  3. __ATTR_RO(status) declares a read-only attribute.
  4. __ATTR_RW(value) declares a read-write attribute.
  5. sysfs_create_group() registers both attributes.
  6. sysfs_remove_group() removes the attributes during cleanup.
  7. kobject_put() releases the kobject reference.

Expected Sysfs directory

/sys/kernel/sysfs_example/
├── status
└── value
The example demonstrates generic kobject attributes, not device attributes. Its show() and store() callbacks therefore use struct kobject and struct kobj_attribute. Device attributes use struct device and struct device_attribute, as introduced earlier.

13. Makefile for the Sysfs Module

Create a file named Makefile:

obj-m += sysfs_example.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

The Makefile uses the kernel build system to compile the external module.

The command lines beneath all: and clean: must begin with a real tab character, not spaces.

14. Compile and Test the Module

Step 1: Install build dependencies

sudo apt update
sudo apt install build-essential linux-headers-$(uname -r)

Step 2: Create a project directory

mkdir sysfs_project
cd sysfs_project

Step 3: Create source and Makefile

Save the C example as sysfs_example.c and the Makefile in the same directory.

Step 4: Compile

make

Step 5: Load the module

sudo insmod sysfs_example.ko

Step 6: Check the Sysfs directory

ls /sys/kernel/sysfs_example

Step 7: Read the status attribute

cat /sys/kernel/sysfs_example/status

Expected output:

Driver is active

Step 8: Read the initial value

cat /sys/kernel/sysfs_example/value

Expected output:

100

Step 9: Write a new value

echo 250 | sudo tee /sys/kernel/sysfs_example/value

Step 10: Read the updated value

cat /sys/kernel/sysfs_example/value

Expected output:

250

Step 11: Test invalid input

echo 1500 | sudo tee /sys/kernel/sysfs_example/value

The callback should reject this value because the permitted range is 0 to 1000.

Step 12: Remove the module

sudo rmmod sysfs_example

Step 13: Verify cleanup

ls /sys/kernel/sysfs_example

The directory should no longer exist after successful module removal.

Step 14: Inspect kernel messages

sudo dmesg | tail -n 20

15. Important Rules for Sysfs Attribute Development

  • Keep attributes simple and text-based.
  • Use one logical value per ordinary attribute.
  • Validate all data received through store().
  • Return the correct byte count from callbacks.
  • Use sysfs_emit() for modern Sysfs text output.
  • Use suitable synchronization for shared driver data.
  • Remove attributes before destroying their associated objects.
  • Use established subsystem interfaces when available.
  • Document interfaces intended for userspace applications.
  • Do not use Sysfs for large binary data transfers.

16. Common Errors and Troubleshooting

Problem Possible Cause Action
Module compilation fails Missing kernel headers or incompatible source. Install matching headers and inspect compiler output.
Module loading fails Kernel version mismatch or initialization error. Inspect dmesg and module information.
Sysfs directory missing Module initialization failed or registration was not completed. Check module status and kernel logs.
Permission denied Attribute permissions or system security policy. Check permissions and use authorized access.
Invalid argument store() rejected the supplied value. Use an accepted value and format.
Directory remains after failure Incorrect cleanup or incomplete error handling. Review registration and removal paths.

17. Lesson Summary

  • Sysfs attributes expose selected kernel object properties.
  • Device attributes use struct device_attribute.
  • show() handles attribute reads.
  • store() handles attribute writes.
  • DEVICE_ATTR_RO declares read-only attributes.
  • DEVICE_ATTR_RW declares read-write attributes.
  • device_create_file() creates an individual device attribute.
  • device_remove_file() removes an individual device attribute.
  • Attribute groups organize related attributes.
  • sysfs_create_group() and sysfs_remove_group() manage groups.
  • Generic kobject attributes use different callback structures from device attributes.
  • Input validation, synchronization and correct cleanup are essential.
