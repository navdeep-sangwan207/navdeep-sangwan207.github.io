After completing this lesson, you will be able to:

  • Explain how sysfs is mounted.
  • Identify important sysfs directories.
  • Understand device, bus and class hierarchies.

  • Inspect sysfs attributes using Linux commands.
  • Understand how filesystem operations reach kernel callbacks.
  • Explain the relationship between sysfs and the Linux device model.

2. What Is the sysfs Filesystem?

Sysfs is a virtual filesystem that exposes the Linux kernel object model through directories, symbolic links and attribute files.

It is normally mounted at: 

/sys

Unlike a conventional filesystem, sysfs does not store ordinary files and directories on a physical storage device. Its entries represent kernel objects and their relationships.

Example

/sys/class/net/lo/mtu

This path represents the MTU attribute of the loopback network interface.

Reading the file retrieves a value exposed by the kernel's network device infrastructure.

3. Mounting the sysfs Filesystem

Linux normally mounts sysfs automatically during system startup.

The usual mount point is /sys.

Check whether sysfs is mounted

findmnt /sys

Another command is:

mount | grep sysfs

A typical mount entry resembles:

sysfs on /sys type sysfs (rw,nosuid,nodev,noexec,relatime)

The exact mount options and output may differ between Linux distributions and system configurations.

Mount sysfs manually

On a system where sysfs is not already mounted, an administrator can mount it using: 

sudo mount -t sysfs sysfs /sys
Do not attempt to mount another sysfs instance over an already populated /sys directory during normal system operation. Linux systems generally manage this mount automatically.

4. Overall Directory Structure

The sysfs filesystem contains several top-level directories. Each directory represents a category of kernel objects or interfaces. 

/sys
├── block
├── bus
├── class
├── dev
│   ├── block
│   └── char
├── devices
├── firmware
├── fs
├── kernel
└── module
Directory Function
block Block device representation.
bus Bus types, devices and drivers.
class Devices grouped by functional class.
dev Links organized by device numbers.
devices Underlying device hierarchy.
firmware Firmware-related interfaces.
fs Filesystem-related kernel interfaces.
kernel Kernel-related objects and interfaces.
module Information about kernel modules.

5. The /sys/devices Directory

The /sys/devices directory is central to the device hierarchy represented by sysfs.

It organizes devices according to their relationships in the hardware and device model.

Examples of device categories include:

  • System devices.
  • PCI devices.
  • USB devices.
  • Platform devices.
  • Storage-related devices.
  • Other registered devices.

Explore the directory

ls /sys/devices

Display a sample of its hierarchy:

find /sys/devices -maxdepth 2 -type d | head -n 30

A device's location in this hierarchy can help explain its relationship to a bus, controller or parent device.

6. The /sys/bus Directory

The /sys/bus directory represents bus types supported by the running kernel.

Examples include:

  • PCI bus.
  • USB bus.
  • I2C bus.
  • SPI bus.
  • Platform bus.

Explore available buses

ls /sys/bus

A typical bus directory may contain: 

/sys/bus/pci/
├── devices
├── drivers
└── drivers_autoprobe

The exact entries vary by bus type and kernel version.

Devices and drivers

The devices directory provides links to devices associated with the bus.

The drivers directory provides information about drivers registered with that bus. 

ls /sys/bus/pci/devices
ls /sys/bus/pci/drivers
The bus directory helps connect the device model's view of devices and drivers. The bus subsystem manages matching and binding according to its rules.

7. The /sys/class Directory

The /sys/class directory groups devices according to their functional purpose.

For example, network interfaces are grouped under: 

/sys/class/net

Other possible classes include:

/sys/class/input
/sys/class/leds
/sys/class/thermal
/sys/class/graphics
/sys/class/power_supply

These directories may not all exist on every system. Their presence depends on available hardware and kernel subsystems.

Explore network class

ls /sys/class/net

The loopback interface is commonly represented by the entry lo. 

ls /sys/class/net/lo

8. The /sys/block Directory

The /sys/block directory provides a class-oriented view of block devices.

Examples may include:

  • Hard disk devices.
  • SSD devices.
  • Virtual block devices.
  • Other registered block devices.

List block devices

ls /sys/block

Inspect a device

If a device named sda exists, inspect it: 

ls /sys/block/sda

Some attributes expose information such as device size, queue configuration and removable status.

Do not assume that the virtual machine uses a device named sda. The actual name depends on the storage controller and Linux device discovery.

9. The /sys/module Directory

The /sys/module directory provides information about kernel modules and module-related objects.

List module entries

ls /sys/module | head

An individual module directory may expose parameters, sections and other module information, depending on the module and kernel configuration.

Inspect a module

ls /sys/module
ls /sys/module/loop

The second command works only if the loop module's directory exists on the running system.

10. Symbolic Links in sysfs

Symbolic links are important in sysfs because the same kernel object may be viewed from different organizational perspectives.

For example, a network interface may be grouped under /sys/class/net, while its underlying device belongs to a location in /sys/devices.

Inspect network class links

ls -l /sys/class/net

The output commonly shows that an interface entry is a symbolic link to an underlying device path.

Resolve the link

readlink -f /sys/class/net/lo

This displays the resolved path, when the link exists.

/sys/class/net/lo
↓ Symbolic link
Underlying device path
↓
/sys/devices hierarchy

The class path offers a convenient functional view, while the device path represents the object's place in the device hierarchy.

11. Sysfs Attribute Files

An attribute file exposes a value associated with a kernel object.

Sysfs attributes are generally designed as small text interfaces, often representing one logical value per file.

Example: Network interface attributes

ls /sys/class/net/lo

Read the interface state:

cat /sys/class/net/lo/operstate

Read the interface hardware address:

cat /sys/class/net/lo/address

Read the MTU:

cat /sys/class/net/lo/mtu

These values are supplied by the kernel's networking and device infrastructure.

Read-only and writable attributes

Attribute type Meaning
Read-only User space can retrieve the value but cannot change it through that attribute.
Writable User space can submit a value if permissions and callback validation allow it.
Read-write The interface supports both reading and writing.
File permissions alone do not describe every safety requirement. A writable attribute must also validate input and enforce the rules of the relevant subsystem.

12. How Attribute Access Works

A Sysfs attribute is connected to kernel callback functions. User space accesses the attribute using normal file operations, but the value is handled by kernel code.

User Process
↓ open() / read() / write()
Virtual Filesystem Layer
↓
Sysfs
↓
show() / store() Callback
↓
Kernel Object or Device State

Read operation

  1. User space opens an attribute file.
  2. The application requests a read.
  3. Sysfs invokes the associated show callback.
  4. The callback formats the value.
  5. The value is returned to user space.

Write operation

  1. User space opens a writable attribute.
  2. The application writes a value.
  3. Sysfs invokes the associated store callback.
  4. The callback validates the supplied data.
  5. The driver or subsystem applies the permitted change.
The exact callback interface depends on whether the attribute belongs to a kobject, device or another subsystem object. Device attributes are covered in later lessons.

13. Sysfs and the /dev Directory

Sysfs and the /dev directory have different purposes. They should not be confused.

Feature Sysfs /dev
Purpose Expose kernel object information and attributes. Provide device nodes used to access device interfaces.
Representation Directories, symbolic links and attributes. Special files such as character and block device nodes.
Typical example /sys/class/net/lo/mtu /dev/null
Main role Device information and selected control. Device I/O through registered interfaces.

For example, /dev/null is a character device node, while /sys/class/net exposes information about network interfaces.

A device-model object may be associated with a device number and a corresponding device node, but sysfs attributes and device nodes are not interchangeable.

14. Sysfs Mount Options and Access

Sysfs is usually mounted automatically with system selected mount options.

Inspect the current mount options using: 

findmnt -no SOURCE,FSTYPE,OPTIONS /sys

Some common mount options have the following meanings:

Option Meaning
rw Filesystem is mounted read-write.
ro Filesystem is mounted read-only.
nosuid Do not honor set-user-ID or set-group-ID bits.
nodev Do not interpret device special files on the filesystem.
noexec Do not permit execution of programs from the filesystem.

Actual access to individual attributes is also controlled by the permissions and behavior of those attributes.

15. Sysfs ABI and Interface Stability

Sysfs attributes can become interfaces used by user-space programs, scripts and system management tools.

For this reason, kernel developers must take care when creating or changing attributes.

Important design principles

  • Use established subsystem interfaces whenever possible.
  • Expose simple and clearly defined values.
  • Document interfaces intended for user-space use.
  • Validate all input received through writable attributes.
  • Avoid changing the meaning of an existing attribute.
  • Follow the kernel's documented ABI conventions.

The kernel source tree contains documentation for userspace interfaces, including the Sysfs ABI documentation. 

Documentation/ABI/
Debugging-only interfaces should generally use Debugfs rather than being introduced as permanent Sysfs ABI interfaces.

16. Sysfs and Device Driver Development

A device driver may expose attributes through the device model. These attributes allow user-space applications to inspect or configure selected driver or device properties.

Common kernel interfaces include:

Interface Purpose
struct kobject Represents a kernel object.
struct attribute Describes a basic Sysfs attribute.
struct device_attribute Describes an attribute associated with a device.
DEVICE_ATTR_RO Declares a read-only device attribute.
DEVICE_ATTR_RW Declares a read-write device attribute.
DEVICE_ATTR_WO Declares a write-only device attribute.
sysfs_create_file() Creates an attribute file for a kobject.
sysfs_remove_file() Removes an attribute file from a kobject.

These interfaces are introduced here. Their practical use, callback definitions and lifecycle management are covered in subsequent lessons.

18. Important Points to Remember

  • Sysfs is normally mounted at /sys.
  • Sysfs represents kernel objects, not ordinary disk files.
  • /sys/devices represents the device hierarchy.
  • /sys/bus represents bus-related objects.
  • /sys/class groups devices by functional purpose.
  • Symbolic links provide different views of the same kernel objects.
  • Sysfs attributes are commonly small text interfaces.
  • Reading and writing attributes invokes kernel-side handling.
  • Sysfs and /dev provide different types of interfaces.
  • Sysfs interfaces intended for user space must be designed carefully.
