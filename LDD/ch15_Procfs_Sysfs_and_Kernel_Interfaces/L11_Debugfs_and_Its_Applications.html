2. Introduction to Debugfs

Debugfs is a virtual filesystem provided by the Linux kernel for exposing debugging information from kernel subsystems and device drivers.

It allows kernel developers to inspect internal driver state, counters, configuration values and diagnostic information from user space.

Debugfs is commonly mounted at: 

/sys/kernel/debug

Unlike ordinary filesystems, Debugfs does not normally store its contents on a physical storage device. Its entries are provided by kernel code.

Why is Debugfs needed?

During driver development, developers often need to inspect internal information that should not become part of a permanent user-space interface.

Examples include:

  • Internal driver counters.
  • Interrupt statistics.
  • Debugging flags.
  • Hardware initialization status.
  • Temporary diagnostic values.
  • Internal state of a kernel subsystem.

3. Purpose of Debugfs

Debugfs provides a convenient way to access selected kernel information without requiring a custom system call or a separate user-space debugging tool.

Example scenario

Suppose a device driver processes interrupts. During development, the developer wants to know how many interrupts have occurred.

The driver can maintain an internal counter and expose it through a Debugfs file. 

/sys/kernel/debug/example_driver/interrupt_count

A user-space developer can inspect the counter using: 

cat /sys/kernel/debug/example_driver/interrupt_count
Debugfs is primarily a development and diagnostic facility. Its interfaces are not guaranteed to remain stable across kernel versions.

4. Debugfs Architecture

A kernel driver creates Debugfs entries using Debugfs APIs. User-space applications access those entries through ordinary file operations.

User-Space Tools
↓
cat / echo / Custom Application
↓
Virtual Filesystem (VFS)
↓
Debugfs
↓
Driver Debug Callbacks
↓
Kernel Driver State

Working sequence

  1. The driver creates a Debugfs directory.
  2. The driver creates one or more debugging files.
  3. The kernel associates those entries with the relevant operations.
  4. A user-space application opens a Debugfs file.
  5. The corresponding callback provides or modifies diagnostic information.

5. Debugfs Mount Point

The conventional Debugfs mount point is: 

/sys/kernel/debug

Check whether Debugfs is mounted: 

mount | grep debugfs

Alternatively: 

findmnt /sys/kernel/debug

Mount Debugfs manually

If Debugfs is supported by the kernel but not mounted, an administrator can mount it: 

sudo mount -t debugfs none /sys/kernel/debug

Check the directory: 

ls -l /sys/kernel/debug
Mounting Debugfs requires appropriate privileges. Some systems mount it automatically during boot. If the kernel does not support Debugfs, mounting it will fail.

6. Important Debugfs APIs

The primary header used for Debugfs programming is: 

#include <linux/debugfs.h>
API Purpose
debugfs_create_dir() Creates a Debugfs directory.
debugfs_create_file() Creates a Debugfs file.
debugfs_create_u32() Creates a file exposing a 32-bit unsigned integer.
debugfs_create_u64() Creates a file exposing a 64-bit unsigned integer.
debugfs_create_bool() Creates a file exposing a Boolean value.
debugfs_create_symlink() Creates a symbolic link in Debugfs.
debugfs_remove() Removes a Debugfs entry and its descendants.
debugfs_remove_recursive() Removes a Debugfs directory hierarchy recursively.
Debugfs APIs and available helper functions can vary across kernel versions. Always check the headers for the target kernel.

7. Creating a Debugfs Directory

The debugfs_create_dir() function creates a directory inside Debugfs.

Function

struct dentry *debugfs_create_dir(
    const char *name,
    struct dentry *parent
);

Parameters

Parameter Description
name Name of the directory to create.
parent Parent directory entry. NULL means the Debugfs root.

Example

static struct dentry *debug_dir;

debug_dir = debugfs_create_dir("example_driver", NULL);

if (IS_ERR_OR_NULL(debug_dir)) {
    pr_err("Unable to create Debugfs directory\n");
    debug_dir = NULL;
}

If successful, the directory appears at: 

/sys/kernel/debug/example_driver

8. Creating a Debugfs File

The debugfs_create_file() function creates a file and associates it with file operations.

Function

struct dentry *debugfs_create_file(
    const char *name,
    umode_t mode,
    struct dentry *parent,
    void *data,
    const struct file_operations *fops
);

Parameters

Parameter Description
name Name of the Debugfs file.
mode Permission bits for the file.
parent Parent Debugfs directory.
data Private data passed to file operations through the file's private_data field.
fops File operations associated with the entry.

Example

debugfs_create_file(
    "status",
    0444,
    debug_dir,
    NULL,
    &status_fops
);

This creates a read-only Debugfs file named status under the example driver directory.

9. Creating Simple Debugfs Integer Files

Debugfs provides helper functions for exposing simple integer values without writing custom file operations.

Example: 32-bit unsigned integer

static u32 interrupt_count = 0;

debugfs_create_u32(
    "interrupt_count",
    0444,
    debug_dir,
    &interrupt_count
);

The file can be inspected using: 

cat /sys/kernel/debug/example_driver/interrupt_count

Example: Boolean value

static bool debug_enabled = true;

debugfs_create_bool(
    "debug_enabled",
    0644,
    debug_dir,
    &debug_enabled
);

This exposes a Boolean debugging setting. Writing to such a file can change the value, subject to permissions.

Simple Debugfs helpers do not automatically solve all synchronization or object-lifetime problems. Protect shared state appropriately, especially when interrupt handlers or other concurrent code access it.

10. Reading and Writing Debugfs Files

Debugfs files can support read and write operations through their associated file operations.

Read operation

A user-space application reads a Debugfs file using a command such as: 

cat /sys/kernel/debug/example_driver/status

The driver provides the output through its read-related file operation.

Write operation

A writable Debugfs file may accept diagnostic controls: 

echo 1 | sudo tee /sys/kernel/debug/example_driver/debug_enabled

The exact accepted values depend on the implementation.

File operation callbacks

static const struct file_operations debug_fops = {
    .owner = THIS_MODULE,
    .open = simple_open,
    .read = debug_read,
    .write = debug_write,
    .llseek = default_llseek,
};

The example illustrates the relationship between a Debugfs file and a driver's file operations. The actual callback implementation must handle user-kernel data transfer, validation and synchronization.

11. Complete Example: Debugfs Kernel Module

The following example creates a Debugfs directory and exposes an interrupt counter as a read-only 32-bit integer.

Source file: debugfs_example.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/debugfs.h>
#include <linux/types.h>

static struct dentry *debug_dir;
static u32 interrupt_count = 25;

static int __init debugfs_example_init(void)
{
    debug_dir = debugfs_create_dir("example_driver", NULL);

    if (IS_ERR_OR_NULL(debug_dir)) {
        pr_err("Debugfs directory creation failed\n");
        debug_dir = NULL;
        return -ENOMEM;
    }

    if (!debugfs_create_u32("interrupt_count",
                            0444,
                            debug_dir,
                            &interrupt_count)) {
        pr_err("Debugfs file creation failed\n");
        debugfs_remove_recursive(debug_dir);
        debug_dir = NULL;
        return -ENOMEM;
    }

    pr_info("Debugfs example loaded\n");

    return 0;
}

static void __exit debugfs_example_exit(void)
{
    debugfs_remove_recursive(debug_dir);
    debug_dir = NULL;

    pr_info("Debugfs example unloaded\n");
}

module_init(debugfs_example_init);
module_exit(debugfs_example_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic Debugfs Example Module");

Explanation

  1. The module includes the Debugfs header.
  2. A directory named example_driver is created.
  3. A 32-bit unsigned integer variable is declared.
  4. The interrupt_count file exposes that variable.
  5. The file is created with read-only permissions.
  6. During module removal, the Debugfs hierarchy is removed.
This is a simple learning example. A production driver must also account for concurrent access, object lifetime and any users that may already have opened a Debugfs file when teardown begins.

12. Makefile

Create a Makefile in the same directory: 

obj-m += debugfs_example.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	make -C $(KDIR) M=$(PWD) modules

clean:
	make -C $(KDIR) M=$(PWD) clean

The Makefile uses the kernel build system to compile the external kernel module.

The recipe lines beginning with make must start with a tab character in the actual Makefile.

14. Debugfs vs Procfs vs Sysfs

Feature Procfs Sysfs Debugfs
Mount point /proc /sys /sys/kernel/debug
Main purpose Process and kernel information Kernel objects and device model Debugging information
Device attributes Not its primary purpose Preferred interface Temporary diagnostic use
Stable ABI Depends on interface Expected for documented interfaces Not guaranteed
Typical use System information Device configuration Internal driver diagnostics
Kernel API examples proc_create() DEVICE_ATTR_RO() debugfs_create_file()

Selection rule

  • Use Procfs for its established process and kernel information interfaces.
  • Use Sysfs for structured device-model attributes.
  • Use Debugfs for development-time diagnostic interfaces.

15. Debugfs Security Considerations

Debugfs can expose internal kernel information. Therefore, developers must consider security when creating debugging entries.

  • Do not expose passwords, keys or sensitive information.
  • Use appropriate file permissions.
  • Validate all values received from user space.
  • Do not expose unrestricted hardware controls.
  • Protect shared data with appropriate synchronization.
  • Remove entries during driver teardown.
  • Do not assume Debugfs files are available on every system.
Debugfs is not intended to provide a stable, documented userspace ABI. Do not build production applications that depend on its internal file names or formats.

16. Common Debugfs Programming Mistakes

Mistake Problem Correct Practice
Not checking creation results Module may continue with incomplete entries. Check error pointers and NULL results as appropriate.
Not removing Debugfs entries Incorrect resource lifecycle. Remove entries during cleanup.
Using Debugfs for permanent ABI Applications may break across kernel versions. Use a documented subsystem interface.
Ignoring synchronization Concurrent access can corrupt or misreport data. Use suitable locking and atomic operations.
Unsafe write operations Invalid values may affect driver behavior. Validate and restrict accepted input.
Ignoring open-file lifetime Callbacks may access freed driver data. Manage references and teardown carefully.

17. Practical Applications of Debugfs

Application 1: Interrupt debugging

Expose the number of interrupts handled by a device driver.

Application 2: Driver state inspection

Expose whether a driver is initialized, active or in an error state.

Application 3: Performance monitoring

Expose diagnostic counters such as completed requests, timeouts or retry counts.

Application 4: Hardware debugging

During development, expose selected register values or hardware status information, with suitable access restrictions and hardware safety checks.

Application 5: Driver testing

Provide temporary controls for testing internal driver behavior in a controlled development environment.

18. Important Interview Questions

Q1. What is Debugfs?

Debugfs is a virtual filesystem used to expose kernel and driver debugging information to user space.

Q2. Where is Debugfs mounted?

It is conventionally mounted at /sys/kernel/debug.

Q3. Which header is used for Debugfs programming?

The header is linux/debugfs.h.

Q4. What is debugfs_create_dir()?

It creates a directory inside the Debugfs hierarchy.

Q5. What is debugfs_create_file()?

It creates a Debugfs file associated with file operations.

Q6. What is debugfs_create_u32()?

It creates an interface for exposing a 32-bit unsigned integer value.

Q7. What is debugfs_remove_recursive()?

It removes a Debugfs directory hierarchy and its descendant entries.

Q8. Is Debugfs suitable for production userspace ABI?

No. Debugfs does not guarantee a stable userspace ABI.

Q9. What is the difference between Sysfs and Debugfs?

Sysfs provides structured kernel-object and device attributes, whereas Debugfs exposes development-time diagnostic information.

Q10. Why must Debugfs entries be removed?

They must be removed to prevent stale interfaces and to maintain correct resource and object lifetimes.
