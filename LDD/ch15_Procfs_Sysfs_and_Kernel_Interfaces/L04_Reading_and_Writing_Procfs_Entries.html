2. Introduction to Procfs Read and Write Operations

A Procfs entry can provide information to user-space applications. Depending on its purpose and permissions, it may also accept information from user space.

For example, a driver may expose: 

/proc/my_driver/status

A user application could read the current driver status. A separate writable interface could allow an authorized application to change a supported configuration value.

Two basic operations

Operation Direction Purpose
Read Kernel to User Space Retrieve information from the kernel.
Write User Space to Kernel Send information to the kernel.

3. Architecture of Procfs Read Operation

User Application
↓
read()
↓
VFS
↓
Procfs Read Callback
↓
Kernel Data
↓

When an application reads a Procfs entry, the kernel invokes the associated read handling path. The callback provides the requested information to the user-space buffer.

4. Procfs Read Callback

A read callback is responsible for returning data when a user-space process reads a Procfs entry.

Modern callback prototype

ssize_t proc_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
);
Parameter Meaning
file Open file description associated with the entry.
buffer User-space destination buffer.
count Maximum number of bytes requested.
position Current file position.

The callback returns the number of bytes successfully provided. It returns zero when no more data is available at the current position (end of file).

A read operation may return fewer bytes than requested. User-space applications should be prepared to handle partial reads.

5. Understanding File Position

The file position tracks how much data has already been read from a file-like interface.

For Procfs entries, the callback must provide sensible position and end-of-file behavior.

Example

Suppose a Procfs entry exposes the following text: 

Driver Status: Active

If the application requests only a few bytes, the first read may return part of the text. A later read can retrieve the remaining data.

First read: bytes 0-7
↓
File position advances
↓
Second read: remaining bytes
↓
End of File: return 0

The VFS and the file-position pointer work together to support successive reads. The driver or helper used must implement the expected position semantics.

6. Using seq_file for Reading Procfs Entries

The seq_file interface simplifies the implementation of Procfs entries that produce sequential text output.

Instead of manually managing a read buffer and file position, a driver can use helpers such as:

Function Purpose
single_open() Connects the open operation to one show callback.
seq_read() Handles reading sequential output.
seq_lseek() Handles file-position changes.
single_release() Releases resources allocated by single_open().
seq_printf() Formats data into the sequential output buffer.
seq_puts() Adds a string to the sequential output buffer.

Example show callback

static int proc_show(struct seq_file *m, void *v)
{
    seq_puts(m, "Driver Status: Active\n");
    seq_printf(m, "Interrupt Count: %d\n", 25);

    return 0;
}

The seq_file interface manages buffering and successive reads for this generated output.

For ordinary text reporting, seq_file is generally preferable to writing a custom read callback from scratch.

A write callback receives data from a user-space application. The driver must validate the data before using it.

8. Procfs Write Callback

A write callback handles data sent by a user-space application to a Procfs entry.

Modern callback prototype

ssize_t proc_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
);
Parameter Meaning
file Open file description.
buffer User-space source buffer.
count Number of bytes supplied by the caller.
position Current file position.

The callback normally returns the number of bytes accepted or a negative error code if the operation fails.

9. copy_to_user() and copy_from_user()

Kernel code must not directly dereference arbitrary user-space pointers.

Linux provides special functions for transferring data between kernel space and user space.

copy_to_user()

Transfers data from a kernel buffer to a user-space buffer. 

copy_to_user(user_buffer, kernel_buffer, size);

copy_from_user()

Transfers data from a user-space buffer to a kernel buffer. 

copy_from_user(kernel_buffer, user_buffer, size);
Function Direction
copy_to_user() Kernel → User
copy_from_user() User → Kernel
Both functions return the number of bytes that were not copied, not a negative error code. A return value of zero indicates that the complete requested transfer succeeded.

Important context restriction

These functions may sleep while accessing user memory. They must not be called from interrupt context or another context where sleeping is prohibited.

10. Input Validation

Data received from user space must always be treated as untrusted input.

A write callback should validate:

  • Input length.
  • Allowed characters.
  • Numeric ranges, where applicable.
  • Expected command format.
  • Permissions and authorization.
  • Buffer boundaries.

Example validation concept

if (count == 0)
    return 0;

if (count >= sizeof(kernel_buffer))
    return -EINVAL;

This checks that the input is non-empty and fits within the destination buffer, leaving room for a terminating null character if required.

A length check alone does not validate the meaning of the input. The driver must also validate the actual command or value before applying it.

11. Complete Practical Example: Read/Write Procfs Module

The following example creates a Procfs entry named my_driver_data.

It supports:

  • Reading the stored message.
  • Writing a new message.
  • Basic input length validation.
  • Synchronization using a mutex.
  • Cleanup during module removal.

Source file: proc_rw_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/proc_fs.h>
#include <linux/seq_file.h>
#include <linux/uaccess.h>
#include <linux/mutex.h>
#include <linux/string.h>
#include <linux/errno.h>

#define PROC_NAME "my_driver_data"
#define DATA_SIZE 128

static struct proc_dir_entry *proc_entry;

static char driver_data[DATA_SIZE] = "Initial driver data";
static DEFINE_MUTEX(data_mutex);

/* Display stored information */
static int proc_show(struct seq_file *m, void *v)
{
    mutex_lock(&data_mutex);

    seq_printf(m, "%s\n", driver_data);

    mutex_unlock(&data_mutex);

    return 0;
}

/* Open callback */
static int proc_open(struct inode *inode,
                     struct file *file)
{
    return single_open(file, proc_show, NULL);
}

/* Write callback */
static ssize_t proc_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position)
{
    char temp[DATA_SIZE];
    size_t length;

    if (count == 0)
        return 0;

    if (count >= sizeof(temp))
        return -EINVAL;

    if (copy_from_user(temp, buffer, count))
        return -EFAULT;

    length = count;

    if (length > 0 && temp[length - 1] == '\n')
        length--;

    temp[length] = '\0';

    mutex_lock(&data_mutex);

    memcpy(driver_data, temp, length + 1);

    mutex_unlock(&data_mutex);

    return count;
}

/* Procfs operations */
static const struct proc_ops my_proc_ops = {
    .proc_open    = proc_open,
    .proc_read    = seq_read,
    .proc_write   = proc_write,
    .proc_lseek   = seq_lseek,
    .proc_release = single_release,
};

/* Module initialization */
static int __init proc_rw_init(void)
{
    proc_entry = proc_create(
        PROC_NAME,
        0644,
        NULL,
        &my_proc_ops
    );

    if (!proc_entry) {
        pr_err("Unable to create Procfs entry\n");
        return -ENOMEM;
    }

    pr_info("Read/write Procfs module loaded\n");

    return 0;
}

/* Module cleanup */
static void __exit proc_rw_exit(void)
{
    proc_remove(proc_entry);

    pr_info("Read/write Procfs module unloaded\n");
}

module_init(proc_rw_init);
module_exit(proc_rw_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Read and Write Procfs Example");

Program explanation

  1. driver_data stores the current message.
  2. DEFINE_MUTEX() creates a mutex protecting shared data.
  3. proc_show() displays the stored message.
  4. proc_open() initializes the seq_file interface.
  5. proc_write() receives and validates user input.
  6. copy_from_user() copies data into kernel memory.
  7. mutex_lock() and mutex_unlock() protect access to the shared message.
  8. proc_remove() removes the interface during cleanup.
This is an educational example. It is designed for simple message updates, not as a production control interface. It does not implement general multi-chunk writes or per-open read snapshots. The read output is generated when the seq_file show callback runs.

12. Makefile

Create a Makefile in the same directory as proc_rw_demo.c. 

obj-m += proc_rw_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	make -C $(KDIR) M=$(PWD) modules

clean:
	make -C $(KDIR) M=$(PWD) clean
The recipe lines beginning with make must start with a TAB character.

13. Compiling and Testing

Step 1: Install dependencies

sudo apt update
sudo apt install build-essential linux-headers-$(uname -r)

Step 2: Compile

make

Step 3: Load the module

sudo insmod proc_rw_demo.ko

Step 4: Read initial data

cat /proc/my_driver_data

Expected output:

Initial driver data

Step 5: Write new data

echo "Linux Device Driver Learning" | sudo tee /proc/my_driver_data

Step 6: Read updated data

cat /proc/my_driver_data

Expected output:

Linux Device Driver Learning

Step 7: Inspect permissions

ls -l /proc/my_driver_data

The example requests mode 0644: read and write for the owner, and read-only for group and others. Actual access is also subject to Procfs and system security checks.

Step 8: Unload the module

sudo rmmod proc_rw_demo

Step 9: Verify removal

ls /proc/my_driver_data

The entry should no longer exist after successful removal.

14. Common Errors and Their Solutions

Error Possible reason Solution
Permission denied Insufficient write permissions. Use an authorized account and correct permissions.
Invalid argument Input length or format is invalid. Validate input before writing.
Bad address User-memory transfer failed. Check copy_from_user() or copy_to_user().
Procfs entry missing Module not loaded or entry creation failed. Inspect module status and kernel logs.
Compilation error Kernel API mismatch or missing headers. Check target kernel headers and callback definitions.

Useful diagnostic commands

lsmod
sudo dmesg | tail -n 30
uname -r
ls -l /proc/my_driver_data

15. Important Programming Rules

  • Never directly dereference arbitrary user-space pointers.
  • Use copy_from_user() and copy_to_user() for user-memory transfers.
  • Remember that user-copy functions return the number of bytes not copied.
  • Validate input length before copying into fixed-size buffers.
  • Use appropriate synchronization for shared kernel data.
  • Do not hold a spinlock while performing operations that may sleep.
  • Do not call user-copy functions from interrupt context.
  • Handle partial reads and writes correctly.
  • Use seq_file for suitable sequential text output.
  • Do not assume one write system call always corresponds to one complete logical command.

16. When Should Procfs Be Used?

Procfs is useful for selected process and kernel information and for maintaining established interfaces.

For new driver development, select the interface according to the purpose of the data.

Requirement Preferred interface
Simple device attributes Sysfs
Debugging-only information Debugfs
Process information Procfs
Established subsystem functionality Subsystem-specific interface
