1. Introduction

Linux kernel code can execute in different contexts. Two fundamental contexts that every device driver developer must understand are process context and interrupt context.

Process context is associated with a schedulable task. Interrupt context is used when the kernel responds to an interrupt event.

The distinction is important because it determines whether kernel code can sleep, which synchronization mechanisms are suitable, and how device operations should be implemented.

2. What Is Process Context?

Process context is the environment in which kernel code executes on behalf of a particular task.

A task can be a normal user process or a kernel thread. When a user application requests a kernel service through a system call, the kernel executes the corresponding system-call handling code in the calling task's context.

Examples

  • A program opens a device file using open().
  • A program reads data from a device using read().
  • A program writes data using write().
  • A kernel thread performs background processing.
  • A workqueue worker executes a scheduled callback.
User Application
↓
System Call: read() / write()
↓
Linux Kernel
↓
Device Driver Callback

Characteristics

  • Execution is associated with a current task.
  • Task-specific information is available.
  • Kernel code may sleep when permitted.
  • Blocking operations can wait for resources or events.
  • Mutexes can be used for suitable sleepable synchronization.

3. What Is Interrupt Context?

Interrupt context is the execution environment used by the kernel to handle interrupt events.

A hardware device generates an interrupt to notify the processor that an event needs attention.

Examples

  • UART receives a character.
  • Network interface receives a packet.
  • Timer hardware generates an interrupt.
  • Storage controller completes a transfer.
  • GPIO hardware detects a configured event.
Hardware Device
↓
Interrupt Signal
↓
CPU Interrupt Handling
↓
Linux Interrupt Handler
↓
Immediate Processing / Deferred Work

Characteristics

  • Execution is triggered by an interrupt.
  • It is not ordinary execution on behalf of a user task.
  • Hard interrupt handlers must not sleep.
  • Processing should be short and efficient.
  • Additional work can be deferred to suitable mechanisms.

4. Process Context vs Interrupt Context

Feature Process Context Interrupt Context
Execution trigger Task execution or system call Interrupt event

Blocking operations Allowed when appropriate Not allowed in hard IRQ context

5. How Does a System Call Enter Process Context?

A system call provides an interface through which a user-space application requests a kernel service.

Execution Sequence

  1. A user application calls a library function such as read().
  2. The library or runtime invokes the appropriate system call.
  3. The processor enters the kernel through the architecture-specific system-call mechanism.
  4. The kernel validates and processes the request.
  5. The relevant subsystem or driver callback may execute.
  6. The kernel returns a result to the application.
User Program: read(fd, buffer, size)
↓
System Call Entry
↓
VFS (Virtual File System)
↓
Driver read Callback
↓
Result Returned to User Space

This is a simplified path. The exact call sequence depends on the file type, kernel version and driver implementation.

6. How Does an Interrupt Handler Execute?

An interrupt handler is registered with the kernel so that it can be invoked when a particular interrupt occurs.

Execution Sequence

  1. A hardware device generates an interrupt request.
  2. The interrupt controller and CPU process the interrupt.
  3. The kernel identifies the registered interrupt handler.
  4. The handler checks the device status.
  5. The handler performs the necessary immediate work.
  6. It may schedule deferred processing.
  7. The handler returns and normal execution continues.

Important Points

  • The handler should acknowledge or service the device as required.
  • It should avoid unnecessary processing.
  • It must not wait for a mutex or perform blocking I/O.
  • Shared data must be protected appropriately.

7. Why Cannot an Interrupt Handler Sleep?

Sleeping means suspending the current task so that it can be scheduled again later.

A hard interrupt handler is not executing as a normal schedulable task. It must complete its immediate work and return from the interrupt.

If it tries to sleep, the kernel cannot safely perform normal task scheduling from that interrupt-handling context.

Operations to Avoid in Hard IRQ Context

  • Acquiring a mutex.
  • Calling a function that waits for an event.
  • Using a sleepable memory allocation mode such as GFP_KERNEL.
  • Performing blocking I/O.
  • Calling msleep() or schedule().
Always check the kernel documentation for whether a function may sleep. A function's name alone does not establish whether it is safe in interrupt context.

8. Interrupt Context and Atomic Context

Atomic context is an execution situation in which sleeping is prohibited.

Hard interrupt handlers execute in atomic context. Softirq handlers and code holding a spinlock also have important atomic-context restrictions.

Execution Situation Can Sleep?
Normal process context Generally yes, if permitted by the operation and locks held
Hard interrupt handler No
Softirq handler No
While holding a spinlock No
Workqueue callback Generally yes
Threaded interrupt handler Generally yes, subject to its constraints

9. Synchronization in Process and Interrupt Context

Device drivers often share data between a process-context function and an interrupt handler.

For example, a driver may maintain a buffer that is updated by an interrupt handler and read by a user application's read callback.

Synchronization Mechanisms

Mechanism Purpose Context Consideration
Mutex Protect sleepable critical sections Process context
Spinlock Protect short critical sections Suitable for atomic contexts
Spinlock with IRQ control Protect data shared with local interrupt handlers Depends on the locking design
Atomic operations Perform atomic updates to supported values Useful for simple shared state
Wait queues Allow tasks to wait for conditions Waiters sleep in process context; wakeups may be triggered elsewhere
Choosing a lock requires considering every execution path that accesses the shared data, including other CPUs and interrupt handlers. Incorrect locking can cause race conditions and deadlocks.

10. Shared Data Between Process and Interrupt Context

Consider a simplified driver that maintains a counter updated by an interrupt handler. 

#include <linux/module.h>
#include <linux/interrupt.h>
#include <linux/spinlock.h>

static DEFINE_SPINLOCK(counter_lock);
static unsigned long event_count;

static irqreturn_t demo_irq_handler(int irq, void *dev_id)
{
    unsigned long flags;

    spin_lock_irqsave(&counter_lock, flags);
    event_count++;
    spin_unlock_irqrestore(&counter_lock, flags);

    return IRQ_HANDLED;
}

The example demonstrates protecting shared state with a spinlock. It is only an illustrative handler fragment: a real driver must register the IRQ, identify and service its device, and provide proper resource cleanup.

Why Use spin_lock_irqsave()?

  • It saves the previous local interrupt state.
  • It disables local interrupts while acquiring and holding the lock.
  • It protects the critical section against relevant local interrupt re-entry.
  • It restores the saved interrupt state when unlocking.

On a multiprocessor system, the spinlock also coordinates access between CPUs.

11. Deferred Interrupt Processing

A hard interrupt handler should perform only the work that must be done immediately. Longer operations can be deferred.

Common Deferred Processing Mechanisms

Mechanism Execution Context Can Sleep?
Softirq Softirq context No
Tasklet Softirq-related context No
Workqueue Worker thread Generally yes
Threaded IRQ Kernel thread Generally yes

↓

12. Threaded Interrupt Handlers

Linux supports threaded interrupt handling. This separates a short primary interrupt handler from a threaded handler that runs in a kernel thread.

The primary handler runs in interrupt context and determines whether the interrupt belongs to the device. It can request that the threaded handler perform additional processing.

Registration Example

ret = request_threaded_irq(
    irq_number,
    primary_handler,
    thread_handler,
    IRQF_ONESHOT,
    "demo_device",
    device_data
);

In this example:

  • irq_number identifies the interrupt.
  • primary_handler is the hard IRQ handler.
  • thread_handler performs deferred threaded processing.
  • IRQF_ONESHOT keeps the interrupt line masked while the threaded handler runs, as supported by the IRQ configuration.
  • device_data is passed to the handlers.

A threaded handler generally runs in process context and may sleep, subject to the driver and interrupt configuration constraints.

13. Practical Example: UART Interrupt Handling

A UART driver provides a useful example of how process and interrupt contexts cooperate.

Scenario

A UART device receives serial data and notifies the processor through an interrupt.

  1. The UART hardware receives a character.
  2. The UART generates an interrupt.
  3. The hard IRQ handler checks the device status.
  4. The handler retrieves or acknowledges the immediate event as required.
  5. Data is placed into an appropriate buffer or processing path.
  6. Waiting tasks may be notified.
  7. A user application reads the data through a device interface.
UART Receives Data
↓
Interrupt Handler
↓
Buffer / Deferred Processing
↓
Wake Up Waiting Process
↓
Application Reads Data

The exact implementation depends on the UART hardware and Linux serial subsystem. A production driver must also handle buffer overflow, error conditions and synchronization.

15. Common Mistakes in Driver Development

Mistake Possible Consequence
Calling a sleeping function in hard IRQ context Kernel warnings, deadlocks or invalid execution.
Using a mutex in an interrupt handler Invalid sleeping operation.
Using GFP_KERNEL in atomic context Allocation may attempt to sleep.
Holding a spinlock for a long time Increased latency and reduced responsiveness.
Accessing shared data without synchronization Race conditions and corrupted data.
Doing lengthy work inside the hard IRQ handler Delayed interrupt handling and poor system performance.

16. Practical Exercise

Objective

Study how Linux handles process-context and interrupt-context operations.

Procedure

  1. Open an Ubuntu terminal.
  2. Run uname -r to identify the kernel version.
  3. Run cat /proc/interrupts.
  4. Observe interrupt counters before and after generating system activity.
  5. Run ps -e to inspect running tasks.
  6. Run dmesg | tail -n 30 to inspect kernel messages.
  7. Explain which operations belong to process context and which belong to interrupt context.

Expected Result

You should understand how process execution, hardware interrupts and deferred processing work together in Linux device drivers.

A VirtualBox Ubuntu environment can be used for these basic observations. Testing real hardware interrupt drivers requires suitable hardware or an appropriate emulator.

17. Summary

  • Process context is associated with a schedulable task.
  • System-call handling normally executes in process context.
  • Interrupt context handles hardware interrupt events.
  • Hard IRQ handlers must not sleep.
  • Atomic context prohibits sleeping.
  • Mutexes are suitable for sleepable process-context synchronization.
  • Spinlocks protect short critical sections in atomic contexts.
  • Softirqs and tasklets provide deferred atomic processing.
  • Workqueues execute callbacks in worker-thread context.
  • Threaded IRQ handlers support sleepable interrupt processing.
  • Correct context selection is essential for reliable device drivers.
