1. Introduction

The Linux kernel executes code in different situations. For example, a driver function may execute because a user application called read(), because a hardware interrupt occurred, or because a kernel worker was scheduled.

The circumstances under which kernel code executes are called its execution context.

Execution context determines which kernel operations are permitted, whether the code may sleep, and how it can access resources.

This concept is particularly important in device driver development because an operation that is valid in one context may be unsafe in another.

2. What Is Kernel Execution Context?

Kernel execution context describes the environment in which a piece of kernel code is currently running.

It includes information such as:

  • Whether execution is associated with a process or task.
  • Whether the CPU is handling an interrupt.
  • Whether the current code may sleep.
  • Which resources and locks are currently held.
  • Whether preemption or interrupts are disabled.
  • Which CPU is executing the code.
Linux Kernel Execution
↓
Process Context
Interrupt Context
Softirq / Bottom-Half Context
Workqueue Context

These categories describe common execution situations. They are not all mutually exclusive architectural modes. For example, a workqueue callback executes in process context.

3. Process Context

Process context is an execution environment associated with a particular task, such as a user process or kernel thread.

When a user application makes a system call, the kernel performs the requested operation in the context of the calling task.

Examples

  • A user application calls open().
  • A user application calls read().
  • A user application calls write().
  • A kernel thread performs background processing.
  • A workqueue callback executes.

Characteristics

  • A current task is associated with execution.
  • Kernel code can often sleep when the operation permits it.
  • Blocking operations can wait for resources or events.
  • Task-specific information is available.
Process context does not mean that the CPU is executing ordinary user-space instructions. It means kernel code is executing on behalf of a task.

4. Interrupt Context

Interrupt context occurs when the kernel executes code in response to an interrupt event.

Hardware devices generate interrupts to notify the CPU about events such as data arrival, transmission completion, or a timer event.

Examples

  • UART receives data.
  • Network controller receives a packet.
  • Timer interrupt occurs.
  • Storage controller completes an operation.
  • GPIO controller detects a configured interrupt event.

Characteristics

  • Execution is triggered by an interrupt event.
  • The handler must complete its immediate work quickly.
  • Interrupt handlers must not perform operations that sleep.
  • They should avoid lengthy processing.
  • Deferred work can be scheduled for later processing.
An interrupt handler does not execute as an ordinary user process. It handles an event in interrupt context.

5. Process Context vs Interrupt Context

Feature Process Context Interrupt Context
Execution trigger Task execution or system call Interrupt event
Current task Associated with a current task Interrupt handling is not an ordinary task execution
Sleeping May sleep when permitted Must not sleep
Blocking operations Can be used when appropriate Not allowed
Typical work File operations and device requests Immediate interrupt handling
Driver example Character driver's read callback Device interrupt handler

6. Why Sleeping Is Important in Kernel Programming

In Linux kernel programming, sleeping means temporarily suspending the current task so that it can resume later when a required event or resource becomes available.

Sleeping is useful when a task must wait for an event, data, a lock, or another resource.

Examples of Operations That May Sleep

  • Waiting for data using a wait queue.
  • Acquiring a mutex when it is unavailable.
  • Allocating memory with a sleepable allocation mode.
  • Waiting for a completion.
  • Performing blocking I/O.

Why Interrupt Context Cannot Sleep

An interrupt handler is not executing as a normal schedulable task that can simply be suspended and resumed like a process-context operation.

Sleeping inside an interrupt handler can cause scheduling problems, deadlocks or kernel warnings.

Rule: Never call a function that may sleep from hard interrupt context or another atomic context where sleeping is forbidden.

7. Atomic Context

Atomic context refers to an execution situation in which the current code must not sleep or be suspended in a way that violates the required atomic operation.

Examples include:

  • Hard interrupt handlers.
  • Softirq handlers.
  • Code executing while holding a spinlock.
  • Other kernel sections where sleeping is prohibited.

Important Characteristics

  • Operations must complete without sleeping.
  • Suitable synchronization mechanisms must be used.
  • Execution time should be kept short.
  • Functions that may block must be avoided.

Atomic context is a restriction on execution behavior, not simply another name for interrupt context.

8. Kernel Context and Memory Allocation

Memory allocation methods must be selected according to the execution context.

Allocation Flag Meaning Typical Usage
GFP_KERNEL Allows the allocator to perform operations that may sleep. Normal process context.
GFP_ATOMIC Allocation mode suitable for atomic contexts; does not sleep. Some interrupt-related or atomic operations.
GFP_NOWAIT Requests allocation without sleeping or direct reclaim. Situations where waiting is not allowed.

Example: Process Context Allocation

#include <linux/module.h>
#include <linux/slab.h>

static int __init demo_init(void)
{
    char *buffer;

    buffer = kmalloc(128, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    kfree(buffer);

    return 0;
}

static void __exit demo_exit(void)
{
    pr_info("Module removed\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");

The initialization function is executed in a context where sleepable allocation is generally permitted.

GFP_ATOMIC should not be used as a universal replacement for GFP_KERNEL. Atomic allocations may fail more readily because they cannot rely on sleepable reclaim behavior.

9. Kernel Context and Locking

Synchronization mechanisms protect shared data when multiple execution paths access it.

Common Locking Mechanisms

Mechanism Can Sleep? Typical Usage
Mutex Yes, while waiting for the lock Process context
Spinlock No Short critical sections and atomic contexts
Semaphore Yes, while waiting Sleepable synchronization
Atomic Operations No sleeping is involved in the atomic operation Simple shared-value updates
Never hold a normal mutex across a hard interrupt handler. Use synchronization methods appropriate to every execution path that accesses the shared data.

10. Softirq Context

Softirqs are a mechanism for performing deferred interrupt processing in a context that is separate from the immediate hard interrupt handler.

A hard interrupt handler can schedule a softirq to perform additional work later.

Characteristics

  • Used for deferred processing.
  • Does not execute as an ordinary user task.
  • Must not sleep.
  • Designed for short, efficient processing.
  • May execute on different CPUs depending on the subsystem and configuration.

Networking is a major user of softirq processing in Linux.

11. Workqueue Context

Workqueues allow kernel code to defer work to worker threads. The callback runs in process context.

Characteristics

  • Runs through kernel worker threads.
  • Can generally sleep when the workqueue type and surrounding constraints permit it.
  • Suitable for longer deferred operations.
  • Useful when processing requires blocking operations.

Workqueue Example

#include <linux/module.h>
#include <linux/workqueue.h>

static struct work_struct my_work;

static void work_handler(struct work_struct *work)
{
    pr_info("Workqueue function executing\n");
}

static int __init demo_init(void)
{
    INIT_WORK(&my_work, work_handler);

    schedule_work(&my_work);

    return 0;
}

static void __exit demo_exit(void)
{
    cancel_work_sync(&my_work);
    pr_info("Module removed\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");

The example schedules a work item and waits for it to finish or be cancelled during module cleanup.

This is an illustrative kernel module example. Compile it against the headers for the target kernel and test it in a suitable development environment.

12. Tasklets and Deferred Work

Tasklets are a legacy mechanism for deferred interrupt processing. They execute in a softirq-related atomic context and must not sleep.

Modern driver development generally favors threaded interrupts, workqueues or other subsystem-specific mechanisms where appropriate.

Mechanism Execution Context Can Sleep?
Hard IRQ Handler Interrupt context No
Softirq Softirq context No
Tasklet Softirq-related context No
Workqueue Worker thread / process context Generally yes
Threaded IRQ Handler Kernel thread / process context Generally yes

13. Context Selection in Device Drivers

A device driver must choose the correct mechanism for each operation.

Example: UART Driver

UART Hardware Receives Data
↓
Hard Interrupt Handler
↓
Read Status / Capture Immediate Data
↓
Schedule Deferred Processing
↓
Workqueue or Other Suitable Mechanism
↓
Process Data and Notify Waiting Tasks

The actual design depends on the UART controller, subsystem APIs, data rate and latency requirements. Many serial drivers use the kernel's serial framework rather than implementing this complete path themselves.

14. Common Programming Mistakes

Mistake Why It Is Dangerous
Calling a sleepable function from an interrupt handler Can cause scheduling problems or kernel warnings.
Using a mutex in hard IRQ context Mutex acquisition may sleep.
Holding a spinlock for too long Can increase latency and reduce system responsiveness.
Using GFP_KERNEL in atomic context The allocation may sleep.
Performing lengthy work in a hard IRQ handler Delays other interrupt and system processing.
Incorrectly cancelling deferred work during cleanup Can cause callbacks to access released driver resources.

17. Summary

  • Execution context describes the environment in which kernel code runs.
  • Process context is associated with a task.
  • Interrupt context handles interrupt events.
  • Hard interrupt handlers must not sleep.
  • Atomic context prohibits sleeping.
  • Memory allocation flags must match the execution context.
  • Mutexes are sleepable synchronization mechanisms.
  • Spinlocks are used for short atomic critical sections.
  • Softirqs and tasklets perform deferred atomic processing.
  • Workqueues execute callbacks in worker-thread context.
  • Correct context selection is essential for reliable device drivers.
