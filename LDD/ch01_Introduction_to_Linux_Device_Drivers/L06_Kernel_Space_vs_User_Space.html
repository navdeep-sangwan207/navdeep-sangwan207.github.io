1. Introduction

User space and kernel space are two important execution domains in Linux. They provide different privilege levels and access permissions to programs running on a computer.

Although both use the system's virtual memory architecture, they have different responsibilities. User space is intended for applications, while kernel space is responsible for managing the operating system and hardware resources.

Understanding the differences is essential for Linux device driver development because most traditional Linux device drivers execute inside kernel space.

2. Fundamental Difference

Feature User Space Kernel Space
Execution Normal applications and user processes. Linux kernel and kernel components.
Privilege Restricted privilege. Privileged execution.
Hardware access Normally through kernel interfaces. Through kernel-managed hardware interfaces and APIs.
Memory access Restricted to the process's permitted address space. Access to kernel-managed memory, subject to architecture and protection rules.
Failure impact Usually affects the process. Can affect the entire operating system.
Examples Browser, shell, editor. Scheduler, memory manager, device drivers.
Communication Uses system calls and supported interfaces. Provides kernel services and interfaces.

3. Privilege Levels and CPU Protection

Modern processors provide privilege mechanisms that help separate operating-system code from ordinary application code.

On x86 processors, the privilege levels are commonly called rings. Linux normally runs kernel code at Ring 0 and user applications at Ring 3.

Ring 3 – User Mode
Applications
↓ System Call / Exception
Ring 0 – Kernel Mode
Linux Kernel and Device Drivers
↓
Hardware Resources

This is an x86-specific explanation. Other processor architectures use different terminology and mechanisms. For example, ARM processors use exception levels in modern AArch64 systems.

Important: Kernel mode and user mode describe CPU privilege levels. They should not be confused with Linux user accounts such as root and ordinary users.

4. Memory Protection

Linux uses virtual memory and hardware memory-protection mechanisms to control which memory regions a process can access.

User-Space Memory

  • Contains application code, data, stack and mapped memory.
  • Each process has its own virtual address space.
  • One process normally cannot directly access another process's private memory.
  • Applications cannot normally access protected kernel memory.

Kernel-Space Memory

  • Contains kernel code and kernel-managed data.
  • Used by kernel subsystems and kernel modules.
  • Access is controlled by kernel rules and processor protection.
  • Incorrect memory access in kernel code can cause serious system errors.
Virtual Address Space
↓
User Process Memory
Protected Kernel Memory
↓
Hardware Memory Protection

The exact address-space arrangement is architecture-dependent. Kernel and user virtual addresses are not fixed universal addresses across all Linux systems.

5. Hardware Access Comparison

A user application generally does not directly manipulate hardware registers. It requests an operation through a supported operating-system interface.

Kernel drivers can use kernel APIs and hardware-resource interfaces to control supported devices.

Operation User Application Kernel Driver
Read a sensor Uses an exposed device or subsystem interface. Communicates with the sensor through the appropriate kernel framework.
Configure UART Uses a serial interface. Configures the UART controller using kernel-supported mechanisms.
Handle hardware interrupt Receives events through supported interfaces. Registers and executes the appropriate interrupt handler.
Access device registers Normally cannot directly access protected registers. Uses permitted kernel resource and I/O access mechanisms.

6. Communication Between User Space and Kernel Space

Linux provides several mechanisms for communication between user-space programs and kernel components.

6.1 System Calls

System calls provide controlled entry points into the kernel. Examples include open(), read(), write() and ioctl().

6.2 Device Files

Device files under /dev provide interfaces for many character and block devices. Applications can use normal file operations where supported.

6.3 Sysfs

Sysfs exposes information about kernel objects and devices through files under /sys. Some attributes also allow controlled configuration.

6.4 Procfs

Procfs provides process and kernel information through the /proc filesystem.

6.5 Netlink

Netlink provides a communication mechanism between user-space processes and kernel components, particularly for networking and system configuration.

7. System Call Transition: User Mode to Kernel Mode

Consider a user application that wants to read data from a device. It calls the read() interface.

1. User Application
↓
2. Calls read()
↓
3. CPU Enters Kernel Mode
↓
4. Kernel Processes the Request
↓
5. Driver Performs Device Operation
↓
6. Result Returns to User Space

The transition is performed through a processor-supported system-call mechanism. The kernel validates the request, executes the relevant service and returns a result.

A system call does not necessarily invoke a device driver. For example, reading a regular file may be handled by the filesystem and storage layers, while reading a device file may invoke a device-specific driver.

8. User-Kernel Data Transfer

A user-space pointer cannot be treated as an ordinary trusted kernel pointer. The kernel must use appropriate mechanisms to access data supplied by a user process.

copy_from_user()

Copies data from a user-space address into a kernel-space buffer. It is commonly used when a user application sends data to a driver.

copy_to_user()

Copies data from a kernel-space buffer to a user-space address. It is commonly used when a driver returns data to an application. 

/* Conceptual examples inside a kernel driver */

if (copy_from_user(kernel_buffer, user_buffer, length)) {
    return -EFAULT;
}

if (copy_to_user(user_buffer, kernel_buffer, length)) {
    return -EFAULT;
}
These are illustrative kernel-code fragments, not a complete driver. The functions return the number of bytes that could not be copied; a nonzero result indicates an incomplete copy.

9. Error Handling in User Space and Kernel Space

Situation User-Space Result Kernel-Space Result
Invalid memory access May generate a segmentation fault. May generate a kernel oops or panic, depending on the fault.
Invalid operation System call may return an error. Kernel function may return a negative error code.
Program failure Usually terminates or affects that process. Can affect kernel stability or the whole system.
Resource handling Uses process-level resources. Must correctly manage kernel resources and synchronization.

10. Example: User-Space Application and Character Driver

Consider a character driver that provides a device file named /dev/mydevice.

The application performs the following operations:

fd = open("/dev/mydevice", O_RDWR);

write(fd, data, length);

read(fd, buffer, sizeof(buffer));

close(fd);

The corresponding kernel driver may implement:

  • open callback to prepare the device for access.
  • write callback to receive data from user space.
  • read callback to provide data to user space.
  • release callback to clean up when the device is closed.

11. Why Kernel Programming Requires Extra Care

Kernel code runs with high privileges and shares responsibility for system-wide operation. Therefore, kernel programming requires careful attention to:

  • Memory allocation and deallocation.
  • Pointer validation and user-kernel data transfer.
  • Concurrency and synchronization.
  • Interrupt and process execution contexts.
  • Resource management and cleanup.
  • Error handling and recovery.
  • Kernel coding standards and API usage.

13. Summary

  • User space executes normal applications with restricted privileges.
  • Kernel space executes the Linux kernel and most traditional drivers.
  • CPU privilege mechanisms help protect kernel operations.
  • Virtual memory and hardware protection isolate address spaces.
  • System calls provide controlled access to kernel services.
  • Device files, sysfs, procfs and netlink provide additional interfaces.
  • copy_to_user() and copy_from_user() support controlled data transfer.
  • Kernel programming requires careful memory and resource management.
