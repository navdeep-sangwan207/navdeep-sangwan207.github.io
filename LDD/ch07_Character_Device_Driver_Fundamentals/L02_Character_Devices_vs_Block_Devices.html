Lesson 2: Character Devices vs Block Devices
Level: Intermediate
Prerequisites: Introduction to character devices, Linux kernel architecture, device files and basic file operations.
Objective: Understand the architectural and operational differences between character devices and block devices in Linux.

1. Introduction

Linux supports different types of devices. Two important categories are character devices and block devices.

Both provide interfaces between user applications and device functionality, but they differ in their data-access models and kernel subsystems.

Character devices generally provide stream-oriented access, while block devices provide storage-oriented access using addressable blocks of data.

Understanding this distinction is important when selecting the appropriate driver architecture for a hardware device.

2. What Is a Character Device?

A character device is a device registered with the Linux character-device subsystem.

It commonly transfers data as a sequence of bytes. Applications typically access it through operations such as open, read, write and device-specific control.

Examples

  • Serial ports.
  • USB-to-serial interfaces.
  • Terminal devices.
  • Input event interfaces.
  • Random and null devices.

Example Device Files

/dev/ttyS0
/dev/ttyUSB0
/dev/null
/dev/input/event0

These examples are commonly represented as character device nodes on Linux systems.

3. What Is a Block Device?

A block device is a device registered with the Linux block-device subsystem.

Block devices provide storage-oriented access to data in addressable blocks. The kernel block layer manages requests for reading and writing storage data.

Block devices commonly support random access, meaning that data can be accessed at different logical positions rather than only as one continuous stream.

Examples

  • Hard disk drives (HDDs).
  • Solid-state drives (SSDs).
  • USB mass-storage devices.
  • Memory cards exposed as block storage.
  • Virtual block devices.

Example Device Names

/dev/sda
/dev/sda1
/dev/nvme0n1
/dev/mmcblk0

These names are examples. Actual device names depend on the hardware and kernel configuration.

5. Major Differences Between Character and Block Devices

Feature Character Device Block Device
Data model Generally stream-oriented. Block-oriented storage access.
Data organization Data is commonly transferred as bytes. Data is accessed through logical block addresses and block requests.
Access pattern Often sequential, though device-specific behavior varies. Supports random access to storage locations.
Typical purpose Communication and device interaction. Mass storage.
Kernel subsystem Character-device subsystem. Block-device subsystem.
Common interface Character-device file operations. Block I/O and storage interfaces.
Typical examples Serial ports, terminals and input event devices. HDDs, SSDs and USB mass-storage devices.
Filesystem usage Usually accessed directly through device-specific interfaces. Often contains partitions and filesystems.
Request handling Driver-specific operations handle data transfer. Block layer manages storage I/O requests.

Character devices commonly expose a stream of bytes to applications.

Consider a serial communication interface. Incoming bytes can be read by an application, while outgoing bytes can be written to the device.

Example User-Space Operations

int fd;

fd = open("/dev/ttyUSB0", O_RDWR);

if (fd < 0) {
    perror("open");
    return 1;

/* Read and write operations are performed here. */

This is an illustrative example. Real serial communication applications normally configure terminal settings and handle partial transfers and errors.

7. Data Transfer in Block Devices

Block devices are designed for storage operations. Data is addressed through logical block positions and transferred using block I/O requests.

For example, an SSD stores data in physical flash memory, but Linux normally accesses it through a logical block interface.

8. Device Nodes and Identification

Both character and block devices can be represented using special device nodes.

Their long-format listings identify the device type and display major and minor numbers.

Character Device Example

crw-rw-rw- 1 root root 1, 3 ... /dev/null

Block Device Example

brw-rw---- 1 root disk 8, 0 ... /dev/sda
First Character Meaning
c Character device node.
b Block device node.
The example major and minor numbers are illustrative. They are not universal values for every device.

9. Device Driver Structures

Character Device Driver

Character device drivers commonly use:

  • dev_t for device numbers.
  • struct cdev for character-device registration.
  • struct file_operations for operation callbacks.
  • cdev_init() to initialize a cdev object.
  • cdev_add() to add it to the kernel.

Block Device Driver

Block drivers interact with the Linux block subsystem. Their implementation uses block device and request-processing interfaces.

Depending on the kernel version and driver type, relevant interfaces include:

  • struct block_device
  • struct gendisk
  • Block request queues and operations.
  • Modern block I/O interfaces such as blk-mq.
The Linux block layer has evolved over time. Older tutorials may show interfaces that are deprecated or removed in newer kernels. Block driver development must follow the target kernel's current APIs.

10. Why Do Block Devices Use a Block Layer?

Storage devices handle large amounts of data. The Linux block layer provides common mechanisms for managing storage I/O.

Important Responsibilities

  • Manage block I/O requests.
  • Support request scheduling and merging where applicable.
  • Coordinate data transfer between filesystems and storage drivers.
  • Support caching and other storage optimizations.
  • Provide a common storage interface.

These mechanisms help the kernel manage storage devices efficiently.

11. Can a Character Device Support Random Access?

Character devices are generally stream-oriented, but their behavior is not restricted to strictly sequential data transfer.

A character driver may implement an llseek() callback or support device-specific positioning if its design permits it.

For example, a driver for a memory-backed character device may allow access to different offsets in its internal buffer.

Random access alone does not make a device a block device. The classification depends on the kernel subsystem and device interface.

12. Practical: Identify Character and Block Devices

Use the following commands in Ubuntu to inspect available device nodes.

Step 1: List Block Devices

lsblk

Step 2: List Character Device Nodes

find /dev -type c | head -20

Step 3: List Block Device Nodes

find /dev -type b | head -20

Step 4: Inspect a Character Device

ls -l /dev/null

Step 5: Inspect a Block Device

ls -l /dev/sda

If /dev/sda does not exist, inspect the device names reported by lsblk and choose an available block device node.

Step 6: Display Device Types

stat /dev/null

Use stat on an available block device node as well.

These commands only inspect device information. Do not write directly to a disk device during this introductory exercise. Direct writes can destroy partition tables or stored data.

13. When Should You Use Each Device Type?

Requirement Typical Device Model
Serial communication Character device.
Terminal input and output Character device.
Sensor data interface Often character device or a subsystem-specific interface.
Hard disk storage Block device.
SSD storage Block device.
USB mass storage Block device.
Memory-backed storage disk Block device.

Not every hardware interface should be implemented as a custom character driver. Linux provides specialized subsystems for devices such as input devices, networking, I2C, SPI and USB.

14. Summary

  • Character devices generally provide stream-oriented access.
  • Block devices provide block-oriented storage access.
  • Character drivers use the character-device subsystem.
  • Block drivers use the Linux block I/O subsystem.
  • Character device examples include serial ports and terminals.
  • Block device examples include HDDs and SSDs.
  • Both types can be represented using device nodes.
  • The first character in a long device listing identifies c or b device type.
  • Major and minor numbers identify device registrations and instances.
  • Device classification depends on the kernel interface, not only the data-access pattern.
