Lesson 4: Character Device Driver Architecture
Level: Intermediate
Prerequisites: Character devices, device nodes, Linux kernel architecture and basic kernel modules.
Objective: Understand the complete architecture of a Linux character device driver, including device registration, VFS interaction, file operations and data transfer.

1. Introduction

A Linux character device driver provides an interface between a user-space application and a character-oriented device or kernel-managed data source.

It allows applications to interact with a device using familiar file operations such as open(), read(), write() and close().

Internally, the Linux kernel uses the Virtual File System (VFS), character-device registration mechanisms and driver callback functions to process these operations.

2. Overall Character Device Driver Architecture

The following diagram shows the typical interaction between an application, the kernel and a device.

User-Space Application
↓ System Calls
Virtual File System (VFS)
↓
Character Device Infrastructure
↓
Character Device Registration: dev_t + cdev
↓
Driver Callbacks: file_operations
↓
Device-Specific Driver Logic
↓
Hardware or Kernel-Managed Device

This is a conceptual view. The kernel's internal dispatch and registration mechanisms are more detailed, but the diagram represents the main path followed by common character-device operations.

3. Main Components of Character Driver Architecture

3.1 User Application

The application accesses the device through a device node or another supported interface. It uses system calls such as open, read and write.

3.2 Device Node

A device node under /dev provides a filesystem entry associated with a device number.

3.3 Virtual File System

VFS provides a common interface for filesystem objects and routes file operations to the appropriate implementation.

3.4 Character Device Subsystem

This kernel infrastructure manages character device registrations and helps associate device numbers with driver operations.

3.5 cdev Object

The struct cdev object represents a registered character device and connects its device number range to file operations.

3.6 file_operations

This structure contains callback functions that implement operations such as open, read, write and release.

4. Role of the Device Node

A device node is a special filesystem entry that represents a device interface.

Character device nodes are commonly located under the /dev directory.

Examples

/dev/null
/dev/tty
/dev/ttyS0
/dev/ttyUSB0
/dev/input/event0

A device node contains a device type and device number information. The major and minor numbers help the kernel identify the associated device registration.

Inspect a Device Node

ls -l /dev/null

Example output:

crw-rw-rw- 1 root root 1, 3 ... /dev/null

The initial c indicates a character device node. The numbers 1, 3 represent its major and minor device numbers in this example.

5. Role of the Virtual File System (VFS)

The Virtual File System is a kernel layer that provides a common interface for filesystem and file-related operations.

Applications do not need to understand the internal implementation of every device. They use standard system calls, and VFS routes operations to the appropriate kernel implementation.

Example

fd = open("/dev/mydevice", O_RDWR);

The application requests that the device file be opened. If the device is registered and the operation is permitted, the kernel associates the open file instance with the appropriate driver operations.

The user-space open() system call and the driver's open callback are different functions. The kernel routes the system-call request through its file handling infrastructure.

6. Role of dev_t

Linux uses the dev_t data type to represent a device number.

A device number contains two logical parts:

  • Major number: Identifies the driver registration or device-number range.
  • Minor number: Identifies a particular device or instance handled by that registration.

The kernel provides helper macros to extract these values. 

MAJOR(dev)
MINOR(dev)
MKDEV(major, minor)

For example, a driver may manage multiple device instances using one major number and different minor numbers.

7. Role of struct cdev

The struct cdev structure is central to the registration of a character device.

It associates a range of device numbers with the file operations implemented by the driver.

Important Functions

Function Purpose
cdev_init() Initializes a cdev object and associates it with file operations.
cdev_add() Adds the character device to the kernel for a specified device-number range.
cdev_del() Removes the cdev from the kernel's character-device mapping.

These functions are used with device-number allocation or registration functions such as alloc_chrdev_region() and register_chrdev_region().

Removing a cdev registration does not by itself release every resource owned by the driver. The driver must also manage its memory, device objects and other resources correctly.

8. Role of struct file_operations

The struct file_operations structure contains function pointers that define how the driver responds to file operations.

Important Callbacks

Callback Purpose
open Handles opening the device file.
read Transfers data from the driver to user space.
write Transfers data from user space to the driver.
release Handles closing an open file instance.
unlocked_ioctl Handles device-specific control requests.
llseek Handles file-position changes when supported.
poll Reports readiness for nonblocking I/O and polling mechanisms.

Illustrative Structure

static const struct file_operations my_fops = {
    .owner          = THIS_MODULE,
    .open           = my_open,
    .read           = my_read,
    .write          = my_write,
    .release        = my_release,
    .unlocked_ioctl = my_ioctl,
};

The callback functions must be defined with the correct prototypes for the target kernel. Unsupported operations may be left unimplemented.

9. Data Flow: Read Operation

Consider an application reading data from a character device.

Application calls read()
↓
Kernel processes the system call
↓
VFS dispatches the file operation
↓
Driver's read callback executes
↓
Driver obtains device data
↓
copy_to_user() transfers data
↓
Application receives data

The driver commonly uses copy_to_user() when transferring data from a kernel buffer to a user-space buffer.

The driver's read callback returns the number of bytes read, zero for end-of-file where appropriate, or a negative error code.

10. Data Flow: Write Operation

When an application writes data to a character device, the kernel routes the operation to the driver's write callback.

Application calls write()
↓
Kernel processes the system call
↓
VFS dispatches the file operation
↓
Driver's write callback executes
↓
copy_from_user() transfers data
↓
Driver processes or sends data
↓
Application receives write result

The driver commonly uses copy_from_user() to copy data from a user-space buffer into a kernel buffer.

11. Device Registration and Driver Initialization

A typical character-device driver follows a sequence of registration steps.

Load Kernel Module
↓
Allocate or Register Device Numbers
↓
Initialize struct cdev
↓
Add cdev to Kernel
↓
Create Device Interface if Required
↓
Application Uses Device

During cleanup, the driver reverses its registration and releases resources.

This is a conceptual registration sequence. A real driver must check every return value and unwind already-acquired resources if a later initialization step fails.

12. Device Node Creation

A character device registration and a device node are related, but they are not the same thing.

  • cdev_add() registers the character device with the kernel.
  • mknod can create a device node manually.
  • class_create() and device_create() can be used to expose a device through the device model.
  • udev commonly manages device nodes in user space in response to device events.

Manual Device Node Example

sudo mknod /dev/mydevice c 240 0
sudo chmod 660 /dev/mydevice
ls -l /dev/mydevice

In this example, 240 is an illustrative major number and 0 is the minor number. A real driver must use the device number actually allocated or registered by the kernel.

Creating a device node alone does not register a driver. The corresponding kernel driver registration must already exist.

13. Character Driver Architecture: Important Kernel Objects

Kernel Object Responsibility
dev_t Stores the device number.
struct cdev Connects a device-number range to file operations.
struct file_operations Defines driver operation callbacks.
struct file Represents an open file instance.
struct inode Represents a filesystem object, including device-node metadata.
struct device Represents a device in the Linux device model.

These objects have different responsibilities. Understanding their relationships is essential for developing reliable character drivers.

14. Practical: Inspect Character Device Architecture in Ubuntu

Step 1: List Character Devices

find /dev -type c | head -20

Step 2: Inspect a Device Node

ls -l /dev/null
stat /dev/null

Step 3: Display Device Number Information

stat -c 'Type: %F, Major: %t, Minor: %T' /dev/null

Step 4: Inspect Kernel Device Information

ls -l /sys/dev/char/

Step 5: Inspect a Specific Device Number

ls -l /sys/dev/char/1:3

The example above refers to the commonly available /dev/null device number. Its availability can vary by system.

Step 6: Inspect Kernel Messages

journalctl -k -n 30
These exercises inspect existing Linux devices. They do not require loading an experimental driver or modifying hardware.

15. Important Design Considerations

15.1 Error Handling

Every registration, allocation and device operation should be checked for failure.

15.2 User-Kernel Data Transfer

Drivers must use appropriate helpers such as copy_to_user() and copy_from_user() instead of directly dereferencing arbitrary user pointers.

15.3 Concurrency

Multiple processes may access a device at the same time. Shared data may require synchronization using suitable kernel mechanisms.

15.4 Resource Management

Memory, device numbers, cdev objects and device-model objects must be released correctly during cleanup.

15.5 Permissions

Device-node permissions and ownership should be configured to prevent unauthorized access.

16. Summary

  • Character drivers provide interfaces to character devices.
  • User applications commonly access devices through device nodes.
  • VFS routes file operations to the appropriate driver implementation.
  • dev_t represents a device number.
  • struct cdev represents a registered character device.
  • struct file_operations defines driver callbacks.
  • copy_to_user() and copy_from_user() support safe data transfer.
  • cdev_add() registers the character device with the kernel.
  • Device nodes and kernel driver registration are separate concepts.
  • Correct error handling, synchronization and cleanup are essential.
