2. Introduction to SPI

SPI stands for Serial Peripheral Interface. It is a synchronous serial communication protocol used to exchange data between a controller and one or more peripheral devices.

SPI is commonly used in embedded systems and electronic devices.

Examples of SPI peripherals

  • Flash memory devices
  • SD card interfaces
  • ADC and DAC converters
  • Display controllers
  • Accelerometers and gyroscopes
  • Digital sensors
  • Wireless communication modules

SPI uses a clock signal generated by the controller to synchronize data transfer between connected devices.

SPI is a synchronous serial protocol. Unlike asynchronous serial communication, SPI uses a shared clock signal to coordinate data transmission and reception.

3. Basic SPI Architecture

A basic SPI system consists of one controller and one peripheral.

SPI Controller
↓ MOSI - Data from Controller to Peripheral
SPI Peripheral
↑ MISO - Data from Peripheral to Controller
SCLK - Clock generated by Controller
CS - Peripheral Selection

The controller generates the clock and controls the communication transaction. The peripheral responds to the controller's clock and chip-select signal.

Controller and peripheral terminology

Traditional Term Modern Term Role
Master Controller Generates clock and initiates communication.
Slave Peripheral or target Responds when selected by the controller.

Linux kernel documentation commonly uses the controller and peripheral terminology. Some datasheets and older technical documents still use master and slave.

4. Four Main SPI Signal Lines

A standard SPI connection uses four primary signals.

4.1 MOSI - Master Out, Slave In

MOSI carries data from the controller to the peripheral.

  • Controller transmits data.
  • Peripheral receives data.

4.2 MISO - Master In, Slave Out

MISO carries data from the peripheral to the controller.

  • Peripheral transmits data.
  • Controller receives data.

4.3 SCLK - Serial Clock

SCLK is generated by the SPI controller.

It determines when data is shifted and sampled.

4.4 CS - Chip Select

Chip Select is used to select a particular SPI peripheral.

It is commonly active-low, meaning the selected peripheral is enabled when CS becomes LOW.

Signal Direction from Controller Function
MOSI Output Controller-to-peripheral data.
MISO Input Peripheral-to-controller data.
SCLK Output Serial clock.
CS Output Peripheral selection.
Signal names and pin labels can vary across manufacturers. MOSI may also be labelled COPI (Controller Out, Peripheral In), and MISO may be labelled CIPO (Controller In, Peripheral Out).

5. SPI Connection Diagram

The following diagram shows a typical four-wire SPI connection.

SPI Controller
MOSI ─────────────────→ Peripheral MOSI
MISO ←───────────────── Peripheral MISO
SCLK ─────────────────→ Peripheral SCLK
CS ───────────────────→ Peripheral CS

Both devices share a common ground reference. Their voltage levels must also be electrically compatible.

Multiple SPI peripherals

A single SPI controller can communicate with multiple peripherals.

In a typical arrangement:

  • MOSI is shared by the peripherals.
  • MISO is shared when the peripherals support appropriate tri-state behavior.
  • SCLK is shared.
  • Each peripheral normally has a separate chip-select signal.
SPI Controller
Shared MOSI, MISO and SCLK
CS0 → Peripheral 0
CS1 → Peripheral 1
CS2 → Peripheral 2
Multiple peripherals must not drive a shared MISO line simultaneously. Proper chip-select handling and peripheral electrical behavior are essential to prevent bus contention.

6. SPI Communication Process

SPI communication is initiated by the controller.

Typical communication sequence

  1. The controller selects a peripheral using its CS signal.
  2. The controller configures the clock according to the peripheral's requirements.
  3. The controller generates clock pulses.
  4. Data bits are shifted between the controller and peripheral.
  5. The controller completes the required transfer.
  6. The controller deasserts CS to end the transaction, according to the device protocol.
CS becomes active
↓
Controller generates SCLK
↓
Data exchanged through MOSI and MISO
↓
Required transfer completed
↓
CS becomes inactive

The exact transaction format depends on the peripheral. Some devices require command bytes, address bytes, dummy bytes or multiple transfer phases.

7. Full-Duplex Communication

SPI normally supports full-duplex communication. This means the controller can transmit and receive data simultaneously during clocked data transfer.

For every clock cycle, a bit can be shifted out on MOSI while another bit is shifted in on MISO.

Example: One-byte exchange

Suppose the controller transmits:

Controller TX = 0xA5

At the same time, the peripheral returns:

Peripheral TX = 0x3C

After eight clock cycles, the controller has transmitted one byte and received one byte.

Direction Byte
Controller to Peripheral 0xA5
Peripheral to Controller 0x3C
A device may ignore received data or transmit dummy data during certain operations. Full-duplex electrical capability does not mean every peripheral command uses meaningful data in both directions.

8. SPI Clock Polarity (CPOL)

Clock Polarity determines the idle level of the SPI clock when no clock transitions are taking place in a transaction.

CPOL = 0

  • Clock is LOW when idle.
  • The clock's first transition is rising.

CPOL = 1

  • Clock is HIGH when idle.
  • The clock's first transition is falling.
CPOL Idle Clock Level First Transition
0 LOW Rising edge
1 HIGH Falling edge

9. SPI Clock Phase (CPHA)

Clock Phase determines which clock edge is used to sample data.

CPHA = 0

Data is sampled on the first clock edge and shifted on the second edge.

CPHA = 1

Data is shifted on the first clock edge and sampled on the second edge.

Both communicating devices must agree on the clock polarity and phase.

CPOL defines the clock's idle level. CPHA defines the sampling edge relative to the clock transitions.

10. Four SPI Modes

Combining CPOL and CPHA produces four standard SPI modes.

SPI Mode CPOL CPHA Idle Clock Sampling Edge
Mode 0 0 0 LOW Rising
Mode 1 0 1 LOW Falling
Mode 2 1 0 HIGH Falling
Mode 3 1 1 HIGH Rising

The sampling-edge description assumes the conventional SPI definitions: CPHA = 0 samples on the first edge, while CPHA = 1 samples on the second edge.

Linux SPI mode definitions

SPI_MODE_0
SPI_MODE_1
SPI_MODE_2
SPI_MODE_3

These mode values are used when configuring an SPI device in Linux.

Always check the peripheral datasheet for the required SPI mode. Selecting the wrong mode can result in incorrect data reception or communication failure.

11. SPI Clock Frequency

The SPI controller generates the clock signal. The frequency determines the rate at which bits are transferred.

For example, if the clock frequency is 1 MHz, one clock period is:

T = 1 / f

T = 1 / 1,000,000

T = 1 microsecond

For an eight-bit transfer, eight clock cycles are required. Ignoring setup time, command overhead and pauses, the ideal transfer time is approximately:

Transfer time = 8 / 1,000,000

              = 8 microseconds

Actual transfer time depends on controller capabilities, device timing requirements, software overhead and the structure of the transaction.

Factors affecting SPI clock frequency

  • Peripheral maximum clock frequency.
  • Controller clock and divider configuration.
  • Board wiring and signal integrity.
  • Electrical loading and cable length.
  • Peripheral setup and hold timing requirements.

12. SPI Versus I2C

SPI and I2C are widely used serial communication protocols in embedded systems.

Feature SPI I2C
Clock SCLK SCL
Data signals MOSI and MISO SDA
Typical wiring Four signals for one peripheral Two bus signals
Device selection Usually chip select Addressing
Duplex Normally full-duplex Half-duplex data direction
Clock generation Controller Controller
Acknowledgement No standard ACK bit ACK/NACK mechanism
Bus arbitration No universal standard arbitration mechanism Multi-controller arbitration is defined

When to use SPI

  • When higher data throughput is required.
  • When full-duplex transfer is useful.
  • When a peripheral provides an SPI interface.

When to use I2C

  • When reducing the number of signal wires is important.
  • When multiple addressable peripherals share a bus.
  • When the peripheral supports I2C communication.

Neither protocol is universally better. Selection depends on the peripheral, speed requirements, wiring constraints and system architecture.

13. Linux SPI Subsystem Architecture

Linux provides an SPI subsystem that separates hardware-controller management from peripheral-specific driver logic.

SPI Peripheral Hardware
↕ MOSI, MISO, SCLK, CS
SPI Controller Hardware
↕
SPI Controller Driver
↕
Linux SPI Core
↕
SPI Device Driver
↕
Peripheral-Specific Operations

Main components

Component Purpose
SPI Controller Hardware that generates the clock and performs SPI transfers.
SPI Controller Driver Controls the particular SPI controller hardware.
SPI Core Provides common SPI framework and device/driver management.
SPI Device Represents an individual peripheral connected to the controller.
SPI Device Driver Implements peripheral-specific functionality.

14. Important Linux SPI Structures

Linux uses several structures to represent SPI controllers, devices and drivers.

14.1 struct spi_controller

Represents an SPI controller in the Linux kernel.

It contains controller capabilities and operations used by the SPI Core to communicate with hardware.

14.2 struct spi_device

Represents an SPI peripheral connected to a controller.

Important information includes:

  • Associated SPI controller.
  • Chip-select information.
  • Maximum supported communication frequency.
  • SPI mode.
  • Device-specific configuration.

14.3 struct spi_driver

Represents the driver for an SPI peripheral.

It provides matching information and callbacks such as probe and remove.

Structure Purpose
spi_controller Represents the SPI controller.
spi_device Represents an individual SPI peripheral.
spi_driver Defines the peripheral-specific driver.

15. Device Tree Representation of SPI Devices

Device Tree can describe SPI controllers and the peripherals connected to them.

The following is a simplified illustrative example:

&spi0 {
    status = "okay";

    flash@0 {
        compatible = "demo,spi-flash";
        reg = <0>;
        spi-max-frequency = <10000000>;
    };
};

Explanation:

  • spi0 refers to the SPI controller node.
  • flash@0 describes a peripheral using chip-select index 0.
  • compatible identifies the device binding.
  • reg identifies the chip-select index in this SPI device context.
  • spi-max-frequency specifies the maximum supported SPI clock frequency for the device.
Unlike an I2C device, an SPI peripheral is not normally identified by a bus address. Its Device Tree reg property generally identifies its chip-select index. The exact binding and controller configuration must be followed.

16. SPI Device Communication in Linux

Linux provides APIs for SPI device communication.

Some important APIs and structures include:

API or Structure Purpose
spi_sync() Performs a synchronous SPI message transfer.
spi_async() Submits an asynchronous SPI message transfer.
spi_write() Performs a simple SPI write operation.
spi_read() Performs a simple SPI read operation.
spi_write_then_read() Writes data and then reads data in a common combined operation.
spi_transfer Describes an individual transfer.
spi_message Groups one or more transfers into a message.

These APIs are normally used by the SPI peripheral driver. Detailed practical implementation will be covered in the following SPI driver lessons.

17. SPI Advantages and Limitations

Advantages

  • Simple synchronous communication model.
  • Supports full-duplex data transfer.
  • Can provide high data throughput.
  • No standard device-address field is required.
  • Flexible transaction lengths and formats.

Limitations

  • More signal wires than I2C for a typical connection.
  • Additional chip-select signals may be needed for multiple peripherals.
  • No universal acknowledgement mechanism.
  • No universal device-discovery mechanism.
  • Clock polarity, phase and frequency must be configured correctly.

Exercise 3: Explore Linux SPI Interfaces

On an Ubuntu system that exposes an SPI controller, inspect available SPI device nodes:

ls /dev/spidev*

Inspect SPI-related kernel messages:

dmesg | grep -i spi

Inspect SPI devices in sysfs:

ls /sys/bus/spi/devices/
These commands may return no device nodes or no devices if the system does not expose an SPI controller or if no SPI peripheral has been instantiated. A typical VirtualBox installation does not automatically provide access to the host's physical SPI hardware.
