2. Introduction to SPI Peripheral Drivers

An SPI peripheral driver is a Linux kernel driver that manages a particular device connected to an SPI controller.

Examples include:

  • SPI flash memory drivers.
  • SPI temperature sensor drivers.
  • SPI ADC drivers.
  • SPI display controller drivers.
  • SPI accelerometer drivers.

The peripheral driver understands the commands, register layout, data format and operating requirements of its hardware device.

SPI Peripheral Hardware
↕ SPI Signals

The SPI Core provides common infrastructure. The peripheral driver uses the SPI APIs instead of directly programming controller registers.

Header Purpose
linux/module.h Kernel module registration and metadata.

linux/of.h Device Tree matching.
linux/slab.h Kernel memory allocation.
linux/err.h Error pointer handling utilities.

4. Understanding struct spi_driver

The struct spi_driver structure defines a peripheral-specific SPI driver.

It provides the information required by the SPI Core to match and bind a driver to an SPI device.

Simplified example

static struct spi_driver demo_spi_driver = {
    .driver = {
        .name = "demo_spi",
        .of_match_table = demo_of_match,
    },

    .probe = demo_probe,
    .remove = demo_remove,
};

Important members

Member Purpose
.driver.name Provides the driver's name.
.of_match_table Matches the driver against Device Tree compatible strings.
.probe Called when a matching SPI device is bound to the driver.
.remove Called when the SPI device is detached from the driver.

The SPI driver model also supports other matching mechanisms, including ACPI and SPI device identifiers where applicable.

5. Device Tree Matching

Device Tree describes the SPI peripheral connected to the controller.

Example Device Tree node

&spi0 {
    status = "okay";

    sensor@0 {
        compatible = "demo,spi-sensor";
        reg = <0>;
        spi-max-frequency = <5000000>;
    };
};

Explanation:

  • spi0 represents the SPI controller.
  • sensor@0 describes a peripheral using chip-select index 0.
  • compatible identifies the peripheral binding.
  • reg specifies the chip-select index.
  • spi-max-frequency specifies the maximum requested SPI clock frequency.

Driver match table

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,spi-sensor" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

The compatible string must match the hardware description and the appropriate Device Tree binding.

6. Probe Function

The probe() callback is executed when a matching SPI device is bound to the driver.

It generally performs the following operations:

  • Obtain the SPI device information.
  • Allocate private driver data.
  • Configure communication parameters where required.
  • Check required SPI controller capabilities.
  • Initialize the peripheral according to its datasheet.
  • Register any additional device interfaces.

Modern probe callback

static int demo_probe(struct spi_device *spi)
{
    dev_info(&spi->dev,
             "SPI device detected\n");

    return 0;
}

The probe callback receives a pointer to struct spi_device.

The example uses the modern one-argument SPI probe signature. Always check the target kernel headers because callback declarations can differ across kernel versions.

7. Remove Function

The remove callback is called when the SPI device is detached from the driver.

It is used to stop device-specific operations and release resources that are not managed automatically.

Modern remove callback

static void demo_remove(struct spi_device *spi)
{
    dev_info(&spi->dev,
             "SPI device removed\n");
}

Modern kernels generally use a void return type for the SPI remove callback.

Older kernel versions may use different callback signatures. Match the function declaration to the target kernel's struct spi_driver definition.

8. Private Driver Data

A practical SPI driver often requires private data for each peripheral instance.

Define a private structure

struct demo_spi_data {
    struct spi_device *spi;
    int device_state;
};

Allocate memory in the probe function:

struct demo_spi_data *data;

data = devm_kzalloc(&spi->dev,
                    sizeof(*data),
                    GFP_KERNEL);

if (!data)
    return -ENOMEM;

Associate the private data with the SPI device:

spi_set_drvdata(spi, data);

Retrieve it later:

struct demo_spi_data *data;

data = spi_get_drvdata(spi);
Function Purpose
spi_set_drvdata() Stores private driver data for an SPI device.
spi_get_drvdata() Retrieves previously stored private data.
Memory allocated using devm_kzalloc() is automatically released when the device is detached. Explicitly free it only if you used a non-managed allocation method.

9. SPI Device Configuration

SPI devices have communication parameters that must match the peripheral datasheet.

Common parameters include:

  • SPI clock frequency.
  • Clock polarity.
  • Clock phase.
  • Bits per word.
  • Bit order.

Example configuration

spi->mode = SPI_MODE_0;
spi->bits_per_word = 8;
spi->max_speed_hz = 5000000;

ret = spi_setup(spi);

if (ret) {
    dev_err(&spi->dev,
            "SPI setup failed: %d\n", ret);
    return ret;
}

The example requests SPI mode 0, eight-bit words and a maximum frequency of 5 MHz.

These values are illustrative, not universal. The actual SPI mode, frequency and word size must be selected according to the peripheral datasheet and controller capabilities. Do not change configuration fields without understanding the device requirements.

SPI mode constants

Constant CPOL CPHA
SPI_MODE_0 0 0
SPI_MODE_1 0 1
SPI_MODE_2 1 0
SPI_MODE_3 1 1

10. Basic SPI Communication APIs

The Linux SPI subsystem provides APIs for transferring data between the controller and peripheral.

API Purpose
spi_write() Transmits a buffer to the SPI device.
spi_read() Receives data from the SPI device.
spi_sync() Performs a synchronous SPI message transfer.
spi_async() Submits an asynchronous SPI message.
spi_write_then_read() Performs a write followed by a read operation.

These functions communicate through the SPI Core and the registered controller driver.

Detailed SPI communication examples and transfer structures will be covered in Lesson 10.

11. Complete Basic SPI Driver Skeleton

The following example demonstrates a basic SPI peripheral driver.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/spi/spi.h>
#include <linux/of.h>
#include <linux/slab.h>

struct demo_spi_data {
    struct spi_device *spi;
    int device_state;
};

static int demo_probe(struct spi_device *spi)
{
    struct demo_spi_data *data;
    int ret;

    dev_info(&spi->dev,
             "Demo SPI probe started\n");

    data = devm_kzalloc(&spi->dev,
                        sizeof(*data),
                        GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->spi = spi;
    data->device_state = 0;

    spi_set_drvdata(spi, data);

    /*
     * Illustrative configuration only.
     * Select values from the actual device datasheet.
     */
    spi->mode = SPI_MODE_0;
    spi->bits_per_word = 8;
    spi->max_speed_hz = 5000000;

    ret = spi_setup(spi);

    if (ret) {
        return dev_err_probe(&spi->dev,
                             ret,
                             "SPI setup failed\n");
    }

    dev_info(&spi->dev,
             "Demo SPI device initialized\n");

    return 0;
}

static void demo_remove(struct spi_device *spi)
{
    struct demo_spi_data *data;

    data = spi_get_drvdata(spi);

    dev_info(&spi->dev,
             "Demo SPI device removed\n");

    (void)data;
}

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,spi-sensor" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static struct spi_driver demo_spi_driver = {
    .driver = {
        .name = "demo_spi",
        .of_match_table = demo_of_match,
    },

    .probe = demo_probe,
    .remove = demo_remove,
};

module_spi_driver(demo_spi_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Driver Learning");
MODULE_DESCRIPTION("Basic SPI Peripheral Driver Skeleton");

Program explanation

  1. Required Linux kernel headers are included.
  2. demo_spi_data stores private information.
  3. demo_probe() runs when a matching SPI device is bound.
  4. devm_kzalloc() allocates private memory.
  5. spi_set_drvdata() stores the private data.
  6. SPI mode, word size and maximum speed are configured.
  7. spi_setup() applies the configuration through the SPI subsystem.
  8. demo_remove() handles detachment.
  9. module_spi_driver() registers and unregisters the SPI driver.
This is a driver registration and configuration skeleton. It does not identify a real sensor, read registers or verify peripheral communication. A production driver must implement the actual command protocol and error handling from the peripheral datasheet.

12. SPI Driver Registration

The macro module_spi_driver() simplifies registration of an SPI peripheral driver.

module_spi_driver(demo_spi_driver);

It provides the module initialization and exit logic needed to register and unregister the SPI driver.

Kernel Module Loaded
↓
module_spi_driver()
↓
SPI Driver Registered
↓
Matching SPI Device Found?
↓
Yes → Probe Callback
No → Driver Waits for a Matching Device
Loading an SPI driver does not automatically create an SPI peripheral. A matching SPI device must first be instantiated through Device Tree, ACPI or another supported enumeration mechanism.

13. Error Handling

Kernel drivers must check the return values of operations that can fail.

Memory allocation error

data = devm_kzalloc(&spi->dev,
                    sizeof(*data),
                    GFP_KERNEL);

if (!data)
    return -ENOMEM;

SPI configuration error

ret = spi_setup(spi);

if (ret)
    return dev_err_probe(&spi->dev,
                         ret,
                         "SPI configuration failed\n");

Communication error

SPI transfer APIs return error information. The driver should check the result and avoid using invalid or incomplete data.

For example:

ret = spi_write(spi, tx_buffer, length);

if (ret < 0) {
    dev_err(&spi->dev,
            "SPI write failed: %d\n", ret);
    return ret;
}

The buffer and length must be valid and appropriate for the actual peripheral protocol.

14. Compiling the SPI Driver

Create a source file named demo_spi.c.

Makefile

obj-m += demo_spi.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Compile

make

If compilation succeeds, the module file demo_spi.ko is generated.

Load the module

sudo insmod demo_spi.ko

Inspect module information

lsmod | grep demo_spi

modinfo demo_spi.ko

Inspect kernel messages

dmesg | tail -30

Remove the module

sudo rmmod demo_spi

15. Debugging SPI Driver Binding

Linux provides several interfaces for inspecting SPI devices and their drivers.

List SPI devices

ls /sys/bus/spi/devices/

List SPI drivers

ls /sys/bus/spi/drivers/

Inspect SPI kernel messages

dmesg | grep -i spi

Check userspace SPI devices

ls /dev/spidev*

A device directory in sysfs can exist even if no userspace spidev node exists.

Inspect the device directory and its driver symbolic link to determine whether a driver is bound.

16. Common SPI Driver Development Errors

Error Possible Cause
Probe not called No matching SPI device or incorrect compatible string.
SPI setup failure Unsupported configuration or controller limitation.
Incorrect received data Wrong SPI mode, clock frequency or command format.
Transfer timeout Controller, hardware or communication problem.
Module compilation failure Incorrect API usage or kernel-version mismatch.
No /dev/spidev node No device bound to the userspace SPI interface.

17. Ubuntu VirtualBox and LPC2129 Environment

Ubuntu VirtualBox

Your Ubuntu virtual machine can be used to:

  • Study SPI driver source code.
  • Compile external kernel modules.
  • Understand SPI driver registration.
  • Inspect kernel headers and API declarations.
  • Explore sysfs and kernel debugging messages.

A typical VirtualBox guest does not automatically have access to the host's physical SPI controller. Therefore, successful compilation and module loading do not guarantee that the probe callback will execute.

LPC2129 Keil uVision

Your LPC2129 simulator is useful for understanding hardware-level peripheral programming, but it does not run Linux kernel SPI drivers.
