2. Introduction to Peripheral Drivers

A peripheral driver is a software component that allows the Linux kernel to communicate with a hardware device.

Peripheral devices may be connected through:

  • GPIO interfaces.
  • I2C bus.
  • SPI bus.
  • Other hardware interfaces such as UART, USB and PCI.

Examples of peripheral hardware include:

  • LEDs and push buttons.
  • Temperature sensors.
  • Pressure sensors.
  • ADC and DAC devices.
  • Display controllers.
  • External flash memory.

3. Peripheral Driver Development Workflow

Developing a peripheral driver involves understanding the hardware, selecting the correct Linux subsystem and implementing the device-specific operations.

Development steps

  1. Study the peripheral datasheet.
  2. Identify the communication interface.
  3. Understand the hardware connection.
  4. Identify registers, commands and timing requirements.
  5. Choose the appropriate Linux subsystem.
  6. Create the driver source file.
  7. Implement matching and probe callbacks.
  8. Acquire and configure resources.
  9. Implement communication operations.
  10. Handle errors and resource cleanup.
  11. Compile and load the module.
  12. Test and debug the driver.

4. Selecting the Correct Linux Subsystem

The Linux kernel provides established subsystems for common hardware interfaces.

Hardware Typical Linux Interface Driver Model
LED GPIO and LED subsystem Often GPIO descriptor API and LED class framework
Push button GPIO and input subsystem GPIO descriptor API and input framework
I2C sensor I2C subsystem struct i2c_driver
SPI sensor SPI subsystem struct spi_driver
Platform-connected device Platform bus struct platform_driver
Prefer an existing kernel subsystem such as the LED, input, IIO or hwmon framework when the hardware belongs to that class. This provides standard interfaces and avoids unnecessary custom interfaces.

5. Understanding the Peripheral Datasheet

The datasheet is the primary technical reference for developing a hardware driver.

Important information includes:

  • Device identification and supported operating modes.
  • Supply voltage and electrical characteristics.
  • Pin configuration.
  • Register addresses.
  • Command formats.
  • Communication timing.
  • Initialization sequence.
  • Data format and conversion formulas.
  • Error and status conditions.

Example: Sensor register map

Register Address Purpose
Device ID 0x00 Identifies the peripheral.
Control 0x01 Configures operating mode.
Status 0x02 Reports device status.
Data 0x03 Contains measurement data.
These addresses are illustrative only. Never use example register addresses as real hardware definitions without checking the device datasheet.

6. GPIO-Based Peripheral Driver

GPIO is commonly used to control simple digital signals.

Examples include:

  • Switching an LED ON and OFF.
  • Reading a push button.
  • Controlling a reset pin.
  • Driving an enable signal.

Modern Linux GPIO drivers should normally use the GPIO descriptor API.

Required header files

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/gpio/consumer.h>
#include <linux/of.h>

GPIO descriptor functions

Function Purpose
devm_gpiod_get() Obtains a GPIO descriptor associated with a device.
gpiod_set_value_cansleep() Sets a GPIO output value when the GPIO controller may sleep.
gpiod_get_value_cansleep() Reads a GPIO value from a controller that may sleep.
devm_gpiod_put() Explicitly releases a managed descriptor when needed.

7. GPIO Device Tree Configuration

Device Tree describes which GPIO is connected to the peripheral.

Example Device Tree node

gpio_demo {
    compatible = "demo,gpio-device";

    led-gpios = <&gpio1 5 GPIO_ACTIVE_HIGH>;

    status = "okay";
};

In this example:

  • compatible identifies the device.
  • led-gpios identifies the GPIO connection.
  • GPIO_ACTIVE_HIGH describes the active electrical level.

The actual GPIO controller, line number and property must match the target hardware and its binding.

8. Basic GPIO Platform Driver Example

The following example demonstrates a simple platform driver that controls a GPIO output.

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/gpio/consumer.h>
#include <linux/of.h>
#include <linux/err.h>

struct gpio_demo_data {
    struct gpio_desc *led;
};

static int gpio_demo_probe(
    struct platform_device *pdev)
{
    struct gpio_demo_data *data;

    data = devm_kzalloc(
        &pdev->dev,
        sizeof(*data),
        GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->led = devm_gpiod_get(
        &pdev->dev,
        "led",
        GPIOD_OUT_LOW);

    if (IS_ERR(data->led))
        return dev_err_probe(
            &pdev->dev,
            PTR_ERR(data->led),
            "Failed to get LED GPIO\n");

    platform_set_drvdata(pdev, data);

    dev_info(&pdev->dev,
             "GPIO device initialized\n");

    return 0;
}

static void gpio_demo_remove(
    struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "GPIO device removed\n");
}

static const struct of_device_id gpio_demo_match[] = {
    { .compatible = "demo,gpio-device" },
    { }
};

MODULE_DEVICE_TABLE(of, gpio_demo_match);

static struct platform_driver gpio_demo_driver = {
    .probe = gpio_demo_probe,
    .remove = gpio_demo_remove,

    .driver = {
        .name = "gpio_demo",
        .of_match_table = gpio_demo_match,
    },
};

module_platform_driver(gpio_demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Driver Learning");
MODULE_DESCRIPTION("Basic GPIO Platform Driver");

This example obtains a GPIO and configures it as an output initially set to logical low. It does not create a userspace interface or periodically toggle the LED.

9. I2C-Based Peripheral Driver

An I2C peripheral driver is used for devices connected through the I2C bus.

Examples include:

  • Temperature sensors.
  • Real-time clock devices.
  • EEPROM devices.
  • GPIO expanders.

Important I2C driver components

Component Purpose
struct i2c_client Represents an instantiated I2C peripheral.
struct i2c_driver Defines the I2C peripheral driver.
probe() Initializes a matched peripheral.
remove() Handles peripheral detachment.
i2c_transfer() Transfers one or more I2C messages.

Example I2C communication helper

#include <linux/i2c.h>

static int demo_i2c_read(
    struct i2c_client *client,
    u8 reg)
{
    int ret;

    ret = i2c_smbus_read_byte_data(
        client, reg);

    if (ret < 0) {
        dev_err(&client->dev,
                "I2C read failed: %d\n",
                ret);
        return ret;
    }

    return ret;
}

This function reads one byte using the SMBus byte-data protocol. The peripheral must support that transaction format.

10. I2C Device Tree Configuration

Example I2C peripheral node:

&i2c1 {
    status = "okay";

    sensor@48 {
        compatible = "demo,i2c-sensor";
        reg = <0x48>;
        status = "okay";
    };
};

Explanation:

  • i2c1 identifies the I2C controller.
  • sensor@48 represents a peripheral at address 0x48.
  • compatible is used for driver matching.
  • reg contains the I2C address.

The address must be valid for the peripheral and must use the format expected by the Device Tree binding.

11. SPI-Based Peripheral Driver

SPI drivers manage devices connected through an SPI controller.

Examples include:

  • SPI flash memory.
  • SPI ADC devices.
  • Display controllers.
  • SPI temperature sensors.

Important SPI components

Component Purpose
struct spi_device Represents an SPI peripheral.
struct spi_driver Defines the SPI peripheral driver.
spi_write() Transmits data.
spi_read() Receives data.
spi_sync() Performs synchronous message transfer.

Example SPI communication helper

#include <linux/spi/spi.h>

static int demo_spi_read(
    struct spi_device *spi,
    u8 command,
    u8 *value)
{
    int ret;

    ret = spi_write_then_read(
        spi,
        &command,
        1,
        value,
        1);

    if (ret < 0) {
        dev_err(&spi->dev,
                "SPI read failed: %d\n",
                ret);
        return ret;
    }

    return 0;
}

The command format and number of returned bytes must match the peripheral protocol.

12. SPI Device Tree Configuration

Example SPI peripheral node:

&spi0 {
    status = "okay";

    peripheral@0 {
        compatible = "demo,spi-device";
        reg = <0>;
        spi-max-frequency = <5000000>;
        status = "okay";
    };
};

Explanation:

  • spi0 identifies the controller.
  • peripheral@0 describes the device on chip select 0.
  • compatible identifies the peripheral.
  • reg specifies the chip-select index.
  • spi-max-frequency specifies the maximum requested SPI frequency.

13. Device Tree Matching and Driver Binding

Device Tree matching connects a hardware description to a kernel driver.

Device Tree Node
↓
compatible Property
↓
Kernel Device Instantiation
↓
Driver Match Table
↓
Probe Callback

Each bus has its own driver matching and enumeration mechanisms.

Bus Device Description Driver Registration
Platform Platform Device Tree node module_platform_driver()
I2C I2C child node module_i2c_driver()
SPI SPI child node module_spi_driver()
Registering a driver does not automatically create the hardware device. A matching device must be instantiated by the relevant bus or firmware enumeration mechanism before the driver's probe callback can run.

14. Resource Management

A peripheral driver may require memory, GPIOs, interrupts, clocks, regulators and bus resources.

Linux provides managed resource APIs to simplify cleanup.

API Purpose
devm_kzalloc() Allocates zero-initialized managed memory.
devm_gpiod_get() Obtains a managed GPIO descriptor.
devm_request_threaded_irq() Requests a managed threaded interrupt.
devm_regulator_get() Obtains a managed regulator handle.
devm_clk_get() Obtains a managed clock handle.

Managed resources are automatically released when the associated device is detached.

Managed allocation does not eliminate the need to disable active hardware operations, stop work items, unregister non-managed interfaces and handle device-specific shutdown correctly.

15. Probe Function Design

The probe function is one of the most important parts of a peripheral driver.

It generally performs these operations:

  1. Receive the device structure.
  2. Allocate private driver data.
  3. Acquire GPIO and other resources.
  4. Configure communication parameters.
  5. Verify required bus functionality.
  6. Initialize the hardware according to its datasheet.
  7. Register the appropriate subsystem interface.
  8. Return success or a suitable error.

Generic probe structure

static int demo_probe(struct device *dev)
{
    struct demo_data *data;

    data = devm_kzalloc(
        dev,
        sizeof(*data),
        GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    /*
     * Acquire hardware resources.
     * Configure and initialize the device.
     * Register the required interface.
     */

    dev_info(dev, "Device initialized\n");

    return 0;
}

This is a conceptual example. The actual probe signature depends on the bus driver model.

16. Remove Function and Cleanup

The remove callback handles device detachment.

Typical cleanup operations include:

  • Stop ongoing hardware operations.
  • Disable interrupts where required.
  • Cancel work queues and timers.
  • Unregister subsystem interfaces.
  • Place the peripheral in a safe state.
  • Release resources that are not managed automatically.

Managed resources are released by the device management framework after detachment, but active asynchronous operations must still be stopped safely.

17. Error Handling and Debugging

Driver code must handle failures at every stage.

Failure Possible Response
Memory allocation failure Return -ENOMEM.
Missing required GPIO Return the descriptor error.
Unsupported bus operation Return -EOPNOTSUPP.
Peripheral communication failure Propagate the transfer error.
Hardware initialization failure Stop initialization and return the error.

Useful logging functions

dev_info(dev, "Device initialized\n");

dev_err(dev, "Device initialization failed\n");

dev_warn(dev, "Unexpected device status\n");

dev_dbg(dev, "Debug information\n");

Use device-scoped logging functions to associate messages with the relevant device.

18. Compiling a Peripheral Driver

For an external kernel module, create a Makefile.

Example Makefile

obj-m += demo_driver.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Compile

make

Load the module

sudo insmod demo_driver.ko

Inspect module information

lsmod | grep demo_driver

modinfo demo_driver.ko

Inspect kernel messages

dmesg | tail -40

Remove the module

sudo rmmod demo_driver
The example Makefile assumes that the source file is named demo_driver.c and that matching kernel build headers are installed.

19. Testing Peripheral Drivers

Testing should cover both driver registration and actual hardware communication.

Testing checklist

  • Verify that the module compiles.
  • Verify that the module loads.
  • Confirm that the device is instantiated.
  • Check whether the driver binds to the device.
  • Confirm that probe executes.
  • Check communication return values.
  • Verify received data against expected values.
  • Test invalid device responses and error conditions.
  • Check cleanup during module removal or device detachment.

Useful commands

# Kernel messages
dmesg | tail -50

# Platform devices
ls /sys/bus/platform/devices/

# I2C devices
ls /sys/bus/i2c/devices/

# SPI devices
ls /sys/bus/spi/devices/

# Registered platform drivers
ls /sys/bus/platform/drivers/

# Registered I2C drivers
ls /sys/bus/i2c/drivers/

# Registered SPI drivers
ls /sys/bus/spi/drivers/

20. Common Peripheral Driver Development Mistakes

Mistake Correction
Using incorrect register addresses Verify the peripheral datasheet.
Incorrect Device Tree compatible string Match the driver's table and binding.
Ignoring communication errors Check and propagate return values.
Using legacy GPIO interfaces unnecessarily Prefer GPIO descriptor APIs.
Ignoring resource cleanup Use managed APIs and safe shutdown procedures.
Assuming module load means probe succeeded Check device instantiation and binding.
Accessing hardware from the wrong context Respect sleepability and interrupt-context restrictions.
Creating a custom interface unnecessarily Use an appropriate kernel subsystem.

Objective: Develop a platform driver that acquires a GPIO and controls an LED.

Tasks

  1. Create a Device Tree node for the LED GPIO.

24. Ubuntu VirtualBox and LPC2129 Practice

Ubuntu VirtualBox

Your Ubuntu environment can be used for:

  • Writing GPIO, I2C and SPI driver source code.
  • Compiling external kernel modules.
  • Studying Device Tree matching.
  • Inspecting sysfs device and driver directories.
  • Debugging module loading and initialization.

However, a standard VirtualBox guest does not automatically provide physical GPIO, I2C or SPI controllers. Actual hardware communication requires suitable hardware access or an appropriate emulated environment.

LPC2129 Keil uVision

Your LPC2129 simulator is useful for studying:

  • GPIO direction and output control.
  • I2C master and slave operations.
  • SPI data transmission and reception.
  • Peripheral register configuration.
  • Interrupt-driven peripheral handling.
LPC2129 firmware development is bare-metal programming. Linux peripheral drivers use kernel APIs and run inside a Linux kernel. The two environments are related through hardware concepts, but their source code and execution models are different.
