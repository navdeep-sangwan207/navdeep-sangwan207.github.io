2. Introduction to Device Communication

A peripheral driver communicates with hardware through the corresponding Linux bus subsystem.

The driver sends commands, writes configuration values and receives data from the peripheral.

For example, a temperature sensor may require the driver to:

  1. Write a configuration value to a control register.
  2. Read the sensor's status register.
  3. Read temperature measurement registers.
  4. Convert the received bytes into a temperature value.
Linux Peripheral Driver
↓
I2C Core or SPI Core
↓
Bus Controller Driver
↓
I2C or SPI Hardware Signals
↓
Peripheral Device

The peripheral driver normally uses bus-subsystem APIs instead of directly controlling bus registers.

3. I2C Communication Basics

I2C uses two communication lines:

  • SDA: Serial Data.
  • SCL: Serial Clock.

Each I2C peripheral has an address. The controller uses this address to select the target device.

Basic I2C write operation

START
↓
Slave Address + Write Bit
↓
Register Address
↓
Data Byte
↓
STOP

Basic I2C read operation

START
↓
Slave Address + Write Bit
↓
Register Address
↓
Repeated START
↓
Slave Address + Read Bit
↓
Receive Data
↓
STOP

The exact transaction depends on the peripheral's register protocol.

4. I2C Communication APIs

Linux provides I2C communication functions through the header:

#include <linux/i2c.h>
#include <linux/i2c-dev.h>

Kernel peripheral drivers generally use linux/i2c.h and the relevant SMBus interfaces. The i2c-dev.h interface is associated with userspace I2C access.

Important I2C functions

Function Purpose
i2c_smbus_read_byte_data() Reads one byte from a register using SMBus byte-data protocol.
i2c_smbus_write_byte_data() Writes one byte to a register using SMBus byte-data protocol.
i2c_smbus_read_word_data() Reads a 16-bit word using SMBus word-data protocol.
i2c_smbus_write_word_data() Writes a 16-bit word using SMBus word-data protocol.
i2c_transfer() Performs one or more I2C messages.
i2c_master_send() Sends data to an I2C client.
i2c_master_recv() Receives data from an I2C client.
SMBus is a protocol closely related to I2C. SMBus helper functions must only be used when the peripheral supports the corresponding SMBus transaction format.

5. I2C Register Write Operation

Many I2C peripherals contain internal registers. A register write operation sends a register address followed by the data value.

Example

#include <linux/i2c.h>
#include <linux/errno.h>

static int sensor_write_register(
    struct i2c_client *client,
    u8 reg,
    u8 value)
{
    int ret;

    ret = i2c_smbus_write_byte_data(
        client, reg, value);

    if (ret < 0)
        return ret;

    return 0;
}

Parameters:

  • client: I2C peripheral information.
  • reg: Register address.
  • value: Data to write.

The function returns zero on success or a negative error code on failure.

This function assumes the device supports SMBus byte-data transactions. Some I2C devices use different register widths, command formats or multi-byte protocols.

6. I2C Register Read Operation

Reading a register is a common operation in sensor and peripheral drivers.

Example

static int sensor_read_register(
    struct i2c_client *client,
    u8 reg)
{
    int ret;

    ret = i2c_smbus_read_byte_data(
        client, reg);

    if (ret < 0)
        return ret;

    return ret;
}

The returned value is:

  • Between 0 and 255 when a byte is read successfully.
  • A negative error code when the operation fails.

Using the function

int value;

value = sensor_read_register(client, 0x10);

if (value < 0) {
    dev_err(&client->dev,
            "Register read failed\n");
    return value;
}

dev_info(&client->dev,
         "Register value: 0x%02x\n",
         value);

7. I2C Message Structure

For more flexible I2C communication, Linux provides the struct i2c_msg structure.

struct i2c_msg {
    __u16 addr;
    __u16 flags;
    __u16 len;
    __u8 *buf;
};
Member Purpose
addr I2C peripheral address.
flags Transfer flags, including read direction.
len Number of bytes in the message.
buf Pointer to the data buffer.

Important flags

I2C_M_RD

I2C_M_RD indicates a read message. Without it, the message is a write operation.

8. I2C Transfer Function

The i2c_transfer() function sends one or more I2C messages through an adapter.

Example: Register Read Using Two Messages

static int sensor_read_raw(
    struct i2c_client *client,
    u8 reg,
    u8 *value)
{
    struct i2c_msg msgs[2];
    u8 reg_buffer = reg;
    int ret;

    msgs[0].addr = client->addr;
    msgs[0].flags = 0;
    msgs[0].len = 1;
    msgs[0].buf = &reg_buffer;

    msgs[1].addr = client->addr;
    msgs[1].flags = I2C_M_RD;
    msgs[1].len = 1;
    msgs[1].buf = value;

    ret = i2c_transfer(client->adapter,
                       msgs, 2);

    if (ret < 0)
        return ret;

    if (ret != 2)
        return -EIO;

    return 0;
}

Explanation:

  1. The first message writes the register address.
  2. The second message reads one byte.
  3. Both messages are submitted in a single transfer.
  4. The I2C adapter performs the transaction.
  5. A successful transfer returns the number of messages executed.
A two-message transfer normally allows a repeated START between the register-address write and the read. The exact bus transaction and flags must follow the peripheral protocol.

9. Checking I2C Adapter Functionality

Before using an SMBus operation, a driver should verify that the adapter supports the required functionality.

Example

if (!i2c_check_functionality(
        client->adapter,
        I2C_FUNC_SMBUS_BYTE_DATA)) {

    dev_err(&client->dev,
            "SMBus byte-data not supported\n");

    return -EOPNOTSUPP;
}

This check helps prevent the driver from requesting unsupported transaction types.

10. SPI Communication Basics

SPI is a synchronous serial communication protocol that commonly uses four signals:

  • MOSI: Master Out, Slave In.
  • MISO: Master In, Slave Out.
  • SCLK: Serial Clock.
  • CS: Chip Select.

Unlike I2C, SPI does not use a standard peripheral address field. The controller selects a peripheral using its chip-select signal.

SPI can transmit and receive data simultaneously. Each transmitted bit is accompanied by a received bit, although a peripheral may ignore one direction during a particular operation.

11. SPI Transfer APIs

The SPI subsystem provides several communication functions.

API Purpose
spi_write() Transmits data to the peripheral.
spi_read() Receives data from the peripheral.
spi_sync() Performs a synchronous message transfer.
spi_async() Submits an asynchronous message transfer.
spi_write_then_read() Writes command data and then reads response data.

Simple SPI write

u8 tx_buffer[] = {
    0x20,
    0x55
};

ret = spi_write(spi,
                tx_buffer,
                sizeof(tx_buffer));

if (ret < 0) {
    dev_err(&spi->dev,
            "SPI write failed: %d\n",
            ret);
    return ret;
}

The bytes in the buffer are transmitted according to the peripheral's command protocol.

12. SPI Transfer Structure

The struct spi_transfer structure describes an individual SPI transfer.

struct spi_transfer {
    const void *tx_buf;
    void *rx_buf;
    unsigned int len;
    unsigned int speed_hz;
    unsigned int bits_per_word;
};

This is a simplified view of commonly used members; the actual kernel structure contains additional fields.

Member Purpose
tx_buf Transmit buffer.
rx_buf Receive buffer.
len Number of bytes to transfer.
speed_hz Optional transfer clock speed override.
bits_per_word Optional transfer word-size override.

When both transmit and receive buffers are supplied, the transfer can operate in full-duplex mode.

13. SPI Message Structure

A SPI message groups one or more transfers into a single transaction.

The Linux SPI message structure is:

struct spi_message;

Transfers are added to a message using:

spi_message_init(&message);

spi_message_add_tail(&transfer,
                     &message);

The message is submitted using spi_sync() or spi_async().

SPI Message
├── Transfer 1
├── Transfer 2
└── Transfer 3

Multiple transfers in a message allow a driver to express a sequence of operations while controlling chip-select behavior through the SPI framework.

14. SPI Synchronous Transfer

The spi_sync() function submits a SPI message and waits for its completion.

Example: Full-Duplex Transfer

#include <linux/spi/spi.h>

static int demo_spi_transfer(
    struct spi_device *spi)
{
    u8 tx_buffer[] = { 0x9F, 0x00, 0x00, 0x00 };
    u8 rx_buffer[sizeof(tx_buffer)] = { 0 };

    struct spi_transfer transfer = {
        .tx_buf = tx_buffer,
        .rx_buf = rx_buffer,
        .len = sizeof(tx_buffer),
    };

    struct spi_message message;
    int ret;

    spi_message_init(&message);

    spi_message_add_tail(&transfer,
                        &message);

    ret = spi_sync(spi, &message);

    if (ret < 0) {
        dev_err(&spi->dev,
                "SPI transfer failed: %d\n",
                ret);
        return ret;
    }

    dev_info(&spi->dev,
             "SPI transfer completed\n");

    return 0;
}

Explanation:

  1. Transmit and receive buffers are created.
  2. A transfer structure describes the buffers and length.
  3. A message is initialized.
  4. The transfer is added to the message.
  5. spi_sync() submits the message.
  6. The function waits for completion and returns the transfer status.
The command bytes above are illustrative. The correct command, dummy bytes, response length and chip-select timing depend on the actual peripheral datasheet.

15. SPI Write-Then-Read Operation

The spi_write_then_read() helper is useful when a peripheral requires a command or register address to be sent before returning data.

Example

static int demo_read_register(
    struct spi_device *spi,
    u8 reg,
    u8 *value)
{
    int ret;

    ret = spi_write_then_read(
        spi,
        &reg,
        1,
        value,
        1
    );

    if (ret < 0) {
        dev_err(&spi->dev,
                "SPI register read failed\n");
        return ret;
    }

    return 0;
}

The helper performs a write phase followed by a read phase within one SPI operation.

For a real device, the command may need a read bit, address shift, dummy byte or other protocol-specific formatting.

16. Asynchronous SPI Communication

With synchronous communication, the calling function waits for the transfer to finish.

With asynchronous communication, the driver submits a message and receives completion notification through a callback.

Basic asynchronous model

Driver Creates SPI Message
↓
spi_async()
↓
Driver Continues Other Work
↓
SPI Transfer Completes
↓
Completion Callback Executes

Completion callback example

static void demo_spi_complete(
    void *context)
{
    struct spi_message *message = context;

    pr_info("SPI asynchronous transfer completed: %d\n",
            message->status);
}

Before submission, the message's completion callback and context must be configured appropriately:

message.complete = demo_spi_complete;
message.context = &message;

ret = spi_async(spi, &message);

if (ret < 0) {
    dev_err(&spi->dev,
            "Could not submit SPI message: %d\n",
            ret);
    return ret;
}
An asynchronous transfer may complete after the submitting function returns. The message, transfer structures and buffers must remain valid until the completion callback runs. Do not place them in temporary stack storage that becomes invalid before completion.

17. Synchronous vs Asynchronous Communication

Feature Synchronous Asynchronous
API spi_sync() spi_async()
Waiting Caller waits for completion. Caller does not wait for transfer completion.
Completion Return from function. Completion callback.
Complexity Usually simpler. Requires careful lifetime and concurrency management.
Typical use Simple register access. Operations where non-blocking submission is useful.

Choose the communication method based on the driver's execution context, latency requirements and hardware capabilities.

18. I2C vs SPI Communication

Feature I2C SPI
Signals SDA and SCL MOSI, MISO, SCLK and CS
Device selection Address-based Chip-select-based
Data transfer Half-duplex at the protocol level Full-duplex capable
Linux API i2c_transfer() spi_sync()
Message structure struct i2c_msg struct spi_message
Transfer structure struct i2c_msg struct spi_transfer

19. Communication Error Handling

Communication failures can occur due to several reasons:

  • Peripheral not responding.
  • Incorrect device address.
  • Unsupported transfer format.
  • Incorrect SPI mode or clock frequency.
  • Electrical connection problems.
  • Controller or bus errors.

I2C error handling

ret = i2c_smbus_read_byte_data(
    client, register_address);

if (ret < 0) {
    dev_err(&client->dev,
            "I2C read failed: %d\n", ret);
    return ret;
}

SPI error handling

ret = spi_write(spi,
                tx_buffer,
                tx_length);

if (ret < 0) {
    dev_err(&spi->dev,
            "SPI write failed: %d\n", ret);
    return ret;
}

Drivers should propagate meaningful error codes and avoid treating failed transfers as valid data.

Example driver helper functions

    struct i2c_client *client,

    return i2c_smbus_read_byte_data(

}

Project tasks:

  1. Check adapter functionality during probe.
  2. Write a configuration register.
  3. Read a status register.
  4. Check for negative error returns.
  5. Log the returned register value.
These are helper functions, not a complete sensor driver. A real project must provide the device-specific match table, probe/remove callbacks and actual register definitions.

21. Practical Project: SPI Register Access

Objective: Implement a helper function that reads one register from an SPI peripheral.

Example

#include <linux/module.h>
#include <linux/spi/spi.h>

static int sensor_spi_read_reg(
    struct spi_device *spi,
    u8 reg,
    u8 *value)
{
    u8 command = reg | 0x80;
    int ret;

    ret = spi_write_then_read(
        spi,
        &command,
        1,
        value,
        1
    );

    if (ret < 0) {
        dev_err(&spi->dev,
                "SPI register read failed: %d\n",
                ret);
        return ret;
    }

    return 0;
}

Important: The bit operation reg | 0x80 is only an example of a possible read-command format. The actual read bit and address format must come from the peripheral datasheet.

22. Testing and Debugging

Useful commands for inspecting I2C and SPI devices include:

List I2C adapters

i2cdetect -l

List SPI devices

ls /sys/bus/spi/devices/

Inspect I2C devices

ls /sys/bus/i2c/devices/

Inspect kernel messages

dmesg | grep -Ei "i2c|spi"

Check SPI userspace interfaces

ls /dev/spidev*
Tools such as i2cdetect and userspace interfaces such as /dev/spidev* require the corresponding adapters, drivers and permissions. Scanning or accessing a bus can interfere with devices and should be done only when the hardware and its protocol are understood.

23. Ubuntu VirtualBox and LPC2129 Practice

Ubuntu VirtualBox

You can use Ubuntu to:

  • Study I2C and SPI API declarations.
  • Write peripheral driver source code.
  • Compile kernel modules.
  • Practice error handling and message structures.
  • Inspect available bus devices and kernel logs.

However, a typical VirtualBox guest does not expose physical I2C or SPI controllers automatically. Without a suitable controller and instantiated peripheral, communication functions cannot be tested against real hardware.

LPC2129 Keil uVision

The LPC2129 can be used to study low-level I2C and SPI peripheral communication in a bare-metal environment, subject to the simulator's peripheral support.

Linux Driver LPC2129 Firmware
i2c_transfer() Direct I2C peripheral programming.
spi_sync() Direct SPI peripheral programming.
Linux I2C/SPI Core Firmware controls peripheral registers.
Kernel module Bare-metal application.

Linux bus APIs and LPC2129 register-level programming are different development environments, even though they use the same underlying serial protocols.
