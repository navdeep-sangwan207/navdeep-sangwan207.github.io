2. Introduction to I2C Client Drivers

An I2C client driver is a Linux kernel driver responsible for controlling a particular I2C peripheral.

Examples of I2C peripherals include:

  • Temperature sensors
  • EEPROM memory devices
  • RTC modules
  • GPIO expanders
  • Display controllers
  • Power management ICs

The I2C adapter driver controls the physical I2C bus, while the I2C client driver understands the functionality and register interface of a particular peripheral.

Peripheral Hardware
↕ SDA and SCL
I2C Adapter / Controller Driver
↕
Linux I2C Core
↕
I2C Client Driver
↕
Peripheral-Specific Driver Logic
Important: The I2C client driver does not normally configure the physical controller's registers directly. The adapter driver handles controller-specific operations, while the I2C Core provides the common communication framework.

3. Main Components of an I2C Driver

The Linux I2C subsystem uses several important structures.

3.1 struct i2c_adapter

Represents an I2C bus controller or adapter.

It provides the functionality required to perform I2C transfers through a particular hardware controller.

3.2 struct i2c_client

Represents an individual I2C device connected to an adapter.

It contains information such as:

  • Device address
  • Associated I2C adapter
  • Device model information
  • Device Tree or ACPI information where applicable

3.3 struct i2c_driver

Represents the driver responsible for supporting a particular type of I2C device.

It defines callbacks and matching information used by the Linux I2C Core.

Structure Purpose
i2c_adapter Represents the I2C controller and bus adapter.
i2c_client Represents one peripheral device on an I2C bus.
i2c_driver Defines the client driver and its callbacks.

4. Header Files Required for an I2C Driver

The following kernel header files are commonly used when developing I2C client drivers.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/i2c.h>
#include <linux/of.h>
#include <linux/err.h>
#include <linux/slab.h>
Header Purpose
linux/module.h Kernel module initialization, exit and metadata.
linux/kernel.h General kernel definitions and utilities.
linux/i2c.h I2C structures, registration and communication APIs.
linux/of.h Device Tree matching support.
linux/err.h Error pointer handling utilities.
linux/slab.h Kernel memory allocation functions.

Some drivers also use linux/regmap.h when they need the Linux register-map framework for peripheral register access.

5. Understanding struct i2c_driver

The struct i2c_driver structure is the central registration structure for an I2C client driver.

A simplified conceptual example is shown below:

static struct i2c_driver demo_driver = {
    .driver = {
        .name = "demo_i2c",
        .of_match_table = demo_of_match,
    },

    .probe = demo_probe,
    .remove = demo_remove,
    .id_table = demo_id,
};

The exact fields and callback signatures should be checked against the target kernel's include/linux/i2c.h.

Important members

Member Purpose
.driver.name Provides the driver's name.
.of_match_table Matches the driver against compatible strings in Device Tree.
.probe Called when a matching I2C client is bound to the driver.
.remove Called when the driver is detached from the I2C client.
.id_table Provides I2C device identifiers for matching.

6. I2C Device Matching Mechanisms

The Linux I2C Core must identify which driver can control a particular I2C client.

Several matching mechanisms are supported.

6.1 Device Tree Matching

Device Tree describes hardware using nodes and properties.

An example I2C peripheral node is:

&i2c1 {
    status = "okay";

    sensor@48 {
        compatible = "demo,temperature-sensor";
        reg = <0x48>;
    };
};

Here:

  • sensor@48 identifies the device node and its unit address.
  • compatible identifies the hardware model or driver binding.
  • reg = <0x48> specifies the I2C target address.

The address must match the actual hardware and the binding requirements. It is not a value to choose arbitrarily.

6.2 Device Tree Match Table

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,temperature-sensor" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

The compatible string in the driver must match the compatible string in the Device Tree node.

6.3 I2C ID Table

static const struct i2c_device_id demo_id[] = {
    { "demo_i2c", 0 },
    { }
};

MODULE_DEVICE_TABLE(i2c, demo_id);

The I2C ID table supports matching using the I2C client name. It is useful for systems that instantiate I2C clients through mechanisms such as legacy board information or other non-Device-Tree enumeration methods.

6.4 ACPI Matching

On ACPI-based systems, an I2C device can also be identified through ACPI identifiers and corresponding driver matching information.

A driver can support more than one matching mechanism. Device Tree, I2C ID and ACPI matching are separate ways of identifying devices.

7. Probe Function

The probe() callback is executed when the Linux I2C Core finds a matching I2C client and binds it to the driver.

It is generally responsible for:

  • Checking whether the adapter supports required communication operations.
  • Allocating private driver data.
  • Initializing driver-specific resources.
  • Configuring the peripheral according to its datasheet.
  • Registering additional interfaces if required.

Modern probe callback

static int demo_probe(struct i2c_client *client)
{
    dev_info(&client->dev,
             "Demo I2C device detected\n");

    return 0;
}

In newer kernels, the I2C probe callback generally takes one argument: a pointer to struct i2c_client.

Older kernel versions used a two-argument I2C probe callback, typically probe(struct i2c_client *client, const struct i2c_device_id *id). Always check the callback declaration in the target kernel headers before compiling.

8. Remove Function

The remove() callback is called when the I2C client is detached from the driver.

It is used to release resources and stop driver-specific operations.

Modern remove callback

static void demo_remove(struct i2c_client *client)
{
    dev_info(&client->dev,
             "Demo I2C device removed\n");
}

Modern kernels generally use a void return type for this callback.

Older kernel versions used an int-returning remove callback. The callback signature must match the kernel version being targeted.

9. Private Driver Data

Most practical drivers need to store information specific to each peripheral instance.

This information is commonly stored in a private data structure.

Example private data structure

struct demo_data {
    struct i2c_client *client;
    int device_state;
};

Memory can be allocated using devm_kzalloc().

struct demo_data *data;

data = devm_kzalloc(&client->dev,
                    sizeof(*data),
                    GFP_KERNEL);

if (!data)
    return -ENOMEM;

Storing private data

i2c_set_clientdata(client, data);

Retrieving private data

struct demo_data *data;

data = i2c_get_clientdata(client);
Function Purpose
i2c_set_clientdata() Associates private data with an I2C client.
i2c_get_clientdata() Retrieves the previously associated private data.
devm_kzalloc() allocates zero-initialized memory managed by the device. The memory is automatically released when the device is detached, so a separate kfree() is not normally required for this allocation.

10. Complete Basic I2C Driver Skeleton

The following example demonstrates the basic structure of an I2C client driver.

It registers a driver, matches a compatible device, allocates private data and reports when the device is bound or removed.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/i2c.h>
#include <linux/of.h>
#include <linux/slab.h>

struct demo_data {
    struct i2c_client *client;
    int device_state;
};

static int demo_probe(struct i2c_client *client)
{
    struct demo_data *data;

    dev_info(&client->dev,
             "Demo I2C probe started\n");

    data = devm_kzalloc(&client->dev,
                        sizeof(*data),
                        GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->client = client;
    data->device_state = 0;

    i2c_set_clientdata(client, data);

    dev_info(&client->dev,
             "Demo I2C device initialized\n");

    return 0;
}

static void demo_remove(struct i2c_client *client)
{
    struct demo_data *data;

    data = i2c_get_clientdata(client);

    dev_info(&client->dev,
             "Demo I2C device removed\n");

    (void)data;
}

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,temperature-sensor" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static const struct i2c_device_id demo_id[] = {
    { "demo_i2c", 0 },
    { }
};

MODULE_DEVICE_TABLE(i2c, demo_id);

static struct i2c_driver demo_driver = {
    .driver = {
        .name = "demo_i2c",
        .of_match_table = demo_of_match,
    },

    .probe = demo_probe,
    .remove = demo_remove,
    .id_table = demo_id,
};

module_i2c_driver(demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Driver Learning");
MODULE_DESCRIPTION("Basic I2C Client Driver Skeleton");

Program explanation

  1. Required kernel headers are included.
  2. demo_data stores private information for the peripheral.
  3. demo_probe() runs when a matching client is bound.
  4. devm_kzalloc() allocates private data.
  5. i2c_set_clientdata() associates the data with the client.
  6. demo_remove() handles driver detachment.
  7. The Device Tree and I2C ID tables provide matching information.
  8. module_i2c_driver() handles driver registration and unregistration.
This is a registration and lifecycle skeleton, not a complete sensor driver. It does not read or write peripheral registers. A real driver must use the actual device datasheet to determine identification, initialization and communication requirements.

11. Error Handling in Probe

Kernel drivers must handle errors carefully. A probe function should stop initialization if a required operation fails.

Example: Checking adapter functionality

if (!i2c_check_functionality(client->adapter,
                             I2C_FUNC_I2C)) {
    dev_err(&client->dev,
            "Adapter does not support required I2C transfers\n");
    return -EOPNOTSUPP;
}

The function i2c_check_functionality() checks whether the adapter supports the requested I2C functionality.

For example:

  • I2C_FUNC_I2C checks for basic I2C transfer support.
  • I2C_FUNC_SMBUS_BYTE_DATA checks for SMBus byte-data operations.

Example: Reporting a probe error

if (some_initialization_failed)
    return dev_err_probe(&client->dev,
                         -EINVAL,
                         "Device initialization failed\n");

dev_err_probe() is useful for reporting probe failures, including handling deferred-probe error reporting appropriately.

The variable some_initialization_failed above is illustrative. Real code must check the return value of an actual initialization operation.

12. I2C Communication APIs

Once the client driver has been bound, it can communicate with its peripheral using I2C APIs.

API Purpose
i2c_smbus_read_byte_data() Reads one byte from an SMBus byte-data register operation.
i2c_smbus_write_byte_data() Writes one byte using an SMBus byte-data operation.
i2c_master_send() Sends a byte buffer to the I2C target.
i2c_master_recv() Receives a byte buffer from the I2C target.
i2c_transfer() Performs one or more I2C messages, including combined transfers.

These APIs are used according to the communication protocol defined by the peripheral datasheet.

Detailed I2C read/write transactions and practical communication examples will be covered in Lesson 10.

13. How an I2C Driver Gets Registered

The macro module_i2c_driver() simplifies I2C driver registration.

module_i2c_driver(demo_driver);

Conceptually, it provides module initialization and exit logic that registers and unregisters the I2C driver.

Kernel Module Loaded
↓
module_i2c_driver()
↓
I2C Driver Registered with I2C Core
↓
Matching I2C Client Found?
↓
Yes → Probe Callback Executed
No → Driver Remains Registered, Waiting for a Matching Client
Loading the driver module does not automatically create an I2C client. The client must be instantiated by a supported hardware-enumeration mechanism, such as Device Tree, ACPI or board information. Without a matching client, the probe callback will not run.

14. Device Tree and Driver Relationship

Consider the following simplified Device Tree node:

&i2c1 {
    status = "okay";

    sensor@48 {
        compatible = "demo,temperature-sensor";
        reg = <0x48>;
        status = "okay";
    };
};

The matching driver contains:

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,temperature-sensor" },
    { }
};

The Linux I2C subsystem uses the compatible information to associate the I2C client with the appropriate driver.

The client address is obtained from the Device Tree node and supplied to the driver through struct i2c_client.

Do not hard-code an adapter number such as i2c-1 in a normal Device-Tree-based client driver. The adapter is discovered and associated through the device-enumeration framework.

15. Compiling an I2C Kernel Module

The basic external module build process is similar to other Linux kernel modules.

Makefile

obj-m += demo_i2c.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Save the C source as demo_i2c.c and the build instructions as Makefile.

Build commands

make

If compilation succeeds, a module file named demo_i2c.ko is generated.

Load the module

sudo insmod demo_i2c.ko

Check kernel messages

dmesg | tail -30

List loaded modules

lsmod | grep demo_i2c

Remove the module

sudo rmmod demo_i2c
A successful module load confirms that the driver registered successfully. It does not prove that a peripheral was detected or that the probe callback ran.

16. Debugging I2C Driver Binding

Linux provides useful interfaces for examining I2C adapters, clients and driver binding.

List I2C adapters

i2cdetect -l

Inspect I2C devices

ls /sys/bus/i2c/devices/

Inspect registered I2C drivers

ls /sys/bus/i2c/drivers/

Check kernel messages

dmesg | grep -i i2c

Check device binding

ls -l /sys/bus/i2c/devices/

For a particular client, inspect its directory and look for a driver symbolic link. The link indicates which driver is bound to that client.

Do not run arbitrary I2C scans or register writes on unknown hardware. Some devices may react unpredictably to probing commands. Use I2C diagnostic tools only when you understand the bus and the connected peripherals.

17. Ubuntu VirtualBox and LPC2129 Environment

Ubuntu in VirtualBox

Your Ubuntu virtual machine can be used to:

  • Study Linux I2C driver source code.
  • Compile external kernel modules.
  • Understand I2C driver registration and matching.
  • Inspect kernel headers and module build errors.
  • Practice module loading and unloading.

However, a typical VirtualBox Ubuntu installation does not automatically expose the host computer's physical I2C controller or connected peripherals to the guest.

Therefore, the probe callback requires an actual I2C client to be instantiated in the guest environment. Compilation and module loading can be practised independently of physical hardware.

LPC2129 with Keil uVision

Your LPC2129 Keil simulator environment is useful for bare-metal I2C programming, but it is not a Linux kernel environment.

LPC2129 Bare-Metal I2C Linux I2C Driver
Direct peripheral register programming. Uses Linux I2C subsystem APIs.
Uses LPC21xx header definitions. Uses Linux kernel headers.
Application controls I2C hardware. I2C adapter driver controls hardware.
Runs in a bare-metal application. Runs inside the Linux kernel.

Both environments teach the same underlying I2C bus protocol, but their software architectures are different.
