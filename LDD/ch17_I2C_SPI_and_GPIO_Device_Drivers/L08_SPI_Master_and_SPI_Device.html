2. Introduction to the Linux SPI Model

Linux separates SPI hardware-controller management from peripheral-specific device functionality.

The SPI controller driver handles the physical controller hardware, while an SPI peripheral driver handles the communication protocol and features of a particular peripheral.

SPI Peripheral Hardware
↕ MOSI, MISO, SCLK and CS
SPI Controller Hardware
↕
SPI Controller Driver
↕
Linux SPI Core
↕
SPI Peripheral Driver

Two important sides

Controller Side Peripheral Side
Controls SPI hardware. Controls a specific SPI peripheral.
Generates clock signals. Responds to clock signals.
Manages chip-select signals. Uses the selected communication channel.
Implements controller operations. Implements peripheral-specific operations.

3. SPI Controller

An SPI controller is the hardware block responsible for initiating SPI communication.

It is usually integrated into a microcontroller or processor.

Responsibilities

  • Generate the SPI clock.
  • Transmit data through MOSI.
  • Receive data through MISO.
  • Control chip-select signals.
  • Configure clock polarity and phase.
  • Perform data transfers.
  • Manage controller-specific transfer limitations.

Examples of SPI controllers

  • SPI controller integrated into an ARM SoC.
  • SPI controller integrated into an x86 platform chipset.
  • SPI controller inside an embedded processor.
In modern Linux terminology, the controller is represented by struct spi_controller. Older kernel documentation and source code may use the name struct spi_master.

4. struct spi_controller

The Linux kernel uses struct spi_controller to represent an SPI controller.

The controller driver allocates and configures this structure before registering the controller with the SPI Core.

Important conceptual information

Member or Concept Purpose
bus_num Controller bus number where applicable.
num_chipselect Number of chip-select lines supported by the controller.
mode_bits SPI modes and related configuration capabilities supported.
bits_per_word_mask Supported bits-per-word configurations.
max_speed_hz Controller transfer speed capability, where applicable.
transfer_one Controller callback for processing an individual transfer.

This table is conceptual rather than a complete declaration. Exact members and their use depend on the target kernel version and controller implementation.

Controller allocation

Controller drivers commonly use the managed allocation API:

struct spi_controller *controller;

controller = devm_spi_alloc_host(dev,
                                 sizeof(struct controller_data));

if (!controller)
    return -ENOMEM;

The allocated private area can hold controller-specific state.

devm_spi_alloc_host() is a managed controller-allocation API. Older kernel code may use other allocation helpers, such as spi_alloc_master(). Check the target kernel headers.

5. SPI Controller Driver Responsibilities

The controller driver translates SPI Core requests into operations supported by the hardware.

Typical development tasks

  1. Obtain the controller's hardware resources.
  2. Map controller registers when required.
  3. Configure clock and pin control.
  4. Configure supported SPI modes and transfer sizes.
  5. Implement transfer operations.
  6. Register the controller with the SPI Core.
  7. Handle controller removal and resource cleanup.

A real controller driver may also implement interrupts, DMA, runtime power management and hardware-specific error recovery.

A peripheral client driver does not normally implement the controller's register-level clock generation or low-level hardware transfer mechanism. Those responsibilities belong to the controller driver.

6. SPI Controller Registration

After initializing its hardware and controller structure, the controller driver registers it with the SPI Core.

One commonly used registration API is:

int spi_register_controller(
    struct spi_controller *controller
);

Conceptually, registration makes the controller available to the SPI subsystem.

Registration lifecycle

Controller Driver Probe
↓
Allocate SPI Controller
↓
Configure Controller Capabilities
↓
Initialize Hardware
↓
Register with SPI Core
↓
SPI Controller Becomes Available

The controller driver must also handle registration failures and cleanup appropriately.

7. SPI Device

An SPI device represents an individual peripheral connected to an SPI controller.

Examples include:

  • SPI flash memory.
  • SPI temperature sensors.
  • SPI ADC converters.
  • SPI display controllers.
  • SPI accelerometers.

Each SPI device has configuration information required for communication.

Typical device configuration

  • SPI controller association.
  • Chip-select index.
  • Maximum clock frequency.
  • Clock polarity.
  • Clock phase.
  • Bits per word.

8. struct spi_device

The Linux kernel represents a peripheral using struct spi_device.

Important fields include:

Field Purpose
controller Associated SPI controller.
max_speed_hz Maximum clock frequency permitted for the device.
chip_select Chip-select index used to select the peripheral.
mode SPI mode and applicable configuration flags.
bits_per_word Number of bits in each data word.
irq Associated interrupt information where applicable.

These fields describe the device configuration used by the SPI subsystem and peripheral driver.

The SPI device is normally created by the kernel's device-enumeration mechanism, such as Device Tree or ACPI. A peripheral driver generally receives the already-created spi_device in its probe callback.

9. Chip-Select Configuration

Chip Select identifies which SPI peripheral should respond to a transaction.

For a controller with multiple peripherals, each peripheral normally has a separate chip-select line.

SPI Controller
Shared MOSI, MISO and SCLK
CS0 → SPI Peripheral 0
CS1 → SPI Peripheral 1
CS2 → SPI Peripheral 2

Chip-select index

In a Device Tree SPI peripheral node, the reg property commonly specifies the chip-select index.

flash@0 {
    compatible = "demo,spi-flash";
    reg = <0>;
};

Here, reg = <0> identifies chip-select index 0 for the controller's device binding.

Chip-select handling

The SPI subsystem normally controls chip select as part of a message transaction.

Some controllers use native hardware chip-select outputs, while others use GPIO-based chip-select lines.

Chip-select polarity and wiring must match the peripheral and board design. Incorrect chip-select configuration can prevent communication or select the wrong peripheral.

10. SPI Mode Configuration

The SPI device must be configured with the correct clock polarity and phase.

Mode CPOL CPHA
SPI_MODE_0 0 0
SPI_MODE_1 0 1
SPI_MODE_2 1 0
SPI_MODE_3 1 1

Linux represents these modes using constants such as:

SPI_MODE_0
SPI_MODE_1
SPI_MODE_2
SPI_MODE_3

Other configuration flags may be supported by the kernel and controller, such as bit order and chip-select behavior.

11. Device Tree Representation

Device Tree describes the SPI controller and the peripherals connected to it.

Example SPI controller node

spi0: spi@40013000 {
    compatible = "vendor,soc-spi";
    reg = <0x40013000 0x1000>;
    #address-cells = <1>;
    #size-cells = <0>;
    status = "okay";

    flash@0 {
        compatible = "demo,spi-flash";
        reg = <0>;
        spi-max-frequency = <10000000>;
    };
};

This is an illustrative example. The controller's compatible string, register range, clocks, interrupts, pin control and other properties must match the actual SoC binding.

Important properties

Property Meaning
compatible Identifies the controller or peripheral hardware binding.
reg Controller register range in the controller node; chip-select index in a child SPI device node.
#address-cells Defines the number of cells used for child addresses.
#size-cells Defines the number of cells used for child size fields.
spi-max-frequency Maximum SPI clock frequency requested for the peripheral.
status Indicates whether the device is enabled.
The Device Tree binding is hardware-specific. Do not copy a controller node into a real board configuration without checking the SoC documentation and binding requirements.

12. SPI Device Enumeration

Enumeration means discovering and creating device representations for hardware peripherals.

SPI devices may be instantiated through:

  • Device Tree.
  • ACPI.
  • Board information on applicable legacy systems.
  • Explicit kernel code in specialized configurations.

Device Tree enumeration sequence

Device Tree Describes SPI Controller
↓
Controller Driver Registers Controller
↓
SPI Core Processes Available Child Devices
↓
SPI Device Objects Are Created
↓
SPI Device Driver Matching Begins
↓
Matching Driver Probe Is Called

The SPI Core coordinates device creation and driver matching.

13. SPI Controller Driver vs SPI Peripheral Driver

Feature Controller Driver Peripheral Driver
Hardware controlled SPI controller Connected peripheral
Main structure spi_controller spi_device and spi_driver
Clock generation Responsible through controller hardware Requests suitable transfer configuration
Chip select Implements physical chip-select handling Uses its assigned chip-select
Data format Implements controller transfer capabilities Understands peripheral commands and responses
Registration Registers SPI controller Registers SPI driver

14. SPI Device Sysfs Interface

Linux exposes SPI devices through sysfs.

To inspect registered SPI devices:

ls /sys/bus/spi/devices/

To inspect SPI drivers:

ls /sys/bus/spi/drivers/

To inspect SPI-related kernel messages:

dmesg | grep -i spi

To inspect available SPI device nodes:

ls /dev/spidev*

Device nodes such as /dev/spidev0.0 are created only when an appropriate SPI device is bound to the userspace SPI interface driver and the relevant configuration is enabled.

An SPI device in sysfs and a userspace SPI device node are not the same thing. Kernel peripheral drivers can bind to SPI devices without creating a /dev/spidev* node.

16. Ubuntu VirtualBox and LPC2129 Environment

Ubuntu VirtualBox

Your Ubuntu virtual machine can be used to:

  • Study SPI controller and peripheral driver source code.
  • Inspect Linux SPI kernel structures.
  • Compile external SPI driver modules.
  • Understand Device Tree SPI descriptions.
  • Explore sysfs and kernel messages.

However, a typical VirtualBox installation does not automatically expose the host's physical SPI controller to the guest operating system. A real controller or suitable emulated environment is required for actual hardware transfers.

LPC2129 Keil uVision

The LPC2129 has its own hardware-specific serial peripheral interfaces and register definitions. Its bare-metal programming model is different from Linux SPI controller-driver development.

LPC2129 Bare-Metal Linux SPI Subsystem
Direct peripheral register access. SPI Core and controller APIs.
Uses LPC21xx headers. Uses Linux kernel headers.
Firmware configures controller registers. Controller driver configures hardware.
Runs in Keil simulator or hardware. Runs inside a Linux kernel.
