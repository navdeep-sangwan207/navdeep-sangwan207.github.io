2. Introduction to I2C

I2C stands for Inter-Integrated Circuit. It is a synchronous serial communication protocol used to connect integrated circuits and peripheral devices.

I2C is commonly used to connect:

  • Temperature sensors.
  • EEPROM memory devices.
  • Real-time clocks (RTC).
  • Display controllers.
  • GPIO expanders.
  • Battery monitoring devices.
  • Power management ICs.

I2C allows multiple devices to share the same two communication wires.

I2C Controller
↕ SDA and SCL
Temperature Sensor
EEPROM
RTC Device
GPIO Expander

Multiple I2C devices share one bus.

4. I2C Bus Signals

I2C uses two main signal lines.

4.1 SDA – Serial Data Line

SDA carries address and data bits between the controller and target devices.

4.2 SCL – Serial Clock Line

SCL carries the clock signal used to synchronize communication.

Signal Full Form Function
SDA Serial Data Transfers address and data bits.
SCL Serial Clock Synchronizes data transfer.
Both SDA and SCL are normally open-drain or open-collector signals. Pull-up resistors are required to establish the HIGH state.

5. I2C Electrical Architecture

I2C devices generally use open-drain outputs. A device actively pulls a line LOW or releases it. The pull-up resistor brings the released line HIGH.

VCC
↓ Pull-up resistors
SDA ───────── Shared Data Line
SCL ───────── Shared Clock Line
Controller and Target Devices

Why Pull-up Resistors Are Needed

  • Open-drain outputs cannot actively drive the bus HIGH.
  • Pull-up resistors establish the idle HIGH state.
  • Multiple devices can safely pull a shared line LOW.
  • The arrangement supports wired-AND bus behavior.

Important Electrical Considerations

  • Pull-up resistance must suit bus capacitance and speed.
  • All devices must use compatible logic voltage levels.
  • Excessively strong pull-ups increase sink current.
  • Weak pull-ups can cause slow rising edges.
  • Bus wiring and capacitance affect reliable communication.
Never assume that a 5 V I2C bus can be connected directly to a 3.3 V controller. Check device electrical specifications and use level shifting when required.

6. I2C Controller and Target Devices

I2C communication uses controller and target roles. Older documentation often uses the terms master and slave.

I2C Controller

  • Initiates communication.
  • Generates the clock during a transfer.
  • Sends the target address.
  • Controls read and write transactions.
  • Generates START and STOP conditions.

I2C Target Device

  • Responds to its address.
  • Receives data during write transactions.
  • Transmits data during read transactions.
  • Provides ACK or NACK responses.
I2C Controller
START + Address + Data
I2C Target Device
ACK / Data Response
Controller Completes Transaction with STOP

A bus may support multiple controllers. Arbitration and clock synchronization are used when multiple controllers attempt to control the bus.

7. I2C Device Addressing

Each target device has an address used by the controller to select it.

7-Bit Addressing

Most common I2C devices use 7-bit addresses.

A 7-bit address can represent 128 possible address values, although some address ranges are reserved by the I2C specification.

10-Bit Addressing

I2C also supports 10-bit addressing for a larger address space.

Address Type Address Width Number of Encoded Values
7-bit 7 bits 128
10-bit 10 bits 1024
A device's 7-bit address is not the same as the complete address byte transmitted on the bus. The address byte also includes the read/write bit.

8. I2C START and STOP Conditions

START Condition

A START condition occurs when SDA transitions from HIGH to LOW while SCL is HIGH.

STOP Condition

A STOP condition occurs when SDA transitions from LOW to HIGH while SCL is HIGH.

START: SDA HIGH → LOW while SCL HIGH
↓
Address and Data Transfer
↓
STOP: SDA LOW → HIGH while SCL HIGH

A repeated START condition allows a controller to begin another transaction without first releasing the bus with a STOP condition.

9. ACK and NACK Conditions

After each transferred byte, an acknowledgment bit is used.

ACK – Acknowledge

The receiver pulls SDA LOW during the acknowledgment clock pulse to indicate that it accepted the byte.

NACK – Not Acknowledge

The receiver leaves SDA HIGH during the acknowledgment clock pulse.

Signal SDA During ACK Clock Meaning
ACK LOW Byte acknowledged.
NACK HIGH Byte not acknowledged.

During a read transaction, the controller commonly sends ACK after receiving bytes it wants to continue reading. It sends NACK for the final byte before ending the transfer.

11. I2C Read Transaction

In a read transaction, the controller receives data from a target device.

Many devices require the controller to first select an internal register using a write phase, followed by a repeated START and a read phase.

↓
ACK
↓

↓
Repeated START
↓
Target Address + Read Bit
↓
Target Sends Data
↓

↓

The exact transaction sequence depends on the peripheral's datasheet. Not every I2C device uses internal register addressing.

12. I2C Clock Speeds

I2C supports several standardized speed modes.

Mode Typical Maximum Clock Frequency
Standard Mode 100 kHz
Fast Mode 400 kHz
Fast Mode Plus 1 MHz
High-Speed Mode 3.4 MHz
Ultra Fast-mode 5 MHz (unidirectional)

The controller, target devices, bus wiring and electrical characteristics must support the selected speed.

13. I2C Bus Arbitration and Clock Stretching

Bus Arbitration

When multiple controllers attempt to transmit simultaneously, arbitration determines which controller retains control of the bus.

Because the bus is wired-AND, a controller that releases SDA but observes LOW can detect that another controller is asserting LOW. It then loses arbitration and stops transmitting.

Clock Stretching

A target device may hold SCL LOW to delay the controller when it needs more time to process data.

The controller must support clock stretching if it communicates with devices that use this feature.

14. Linux I2C Subsystem Architecture

Linux provides an I2C subsystem that separates controller hardware from peripheral device drivers.

I2C Peripheral Driver
↕ I2C Core APIs
I2C Core
↕ Adapter Interface
I2C Adapter / Controller Driver
↕ Hardware Bus
I2C Sensor / EEPROM / RTC

Main Components

  • I2C Core: Provides common infrastructure and APIs.
  • I2C Adapter: Represents an I2C controller and its bus interface.
  • I2C Client: Represents a peripheral device connected to an adapter.
  • I2C Driver: Implements device-specific behavior.
  • Adapter Driver: Controls the physical I2C controller hardware.

15. I2C Adapter and I2C Client

I2C Adapter

An adapter represents an I2C bus controller in the Linux device model.

Examples include an SoC's built-in I2C controller or an external USB-to-I2C adapter.

I2C Client

An I2C client represents a peripheral device connected to an I2C adapter at a particular bus address.

For example, an RTC connected at address 0x68 on adapter 1 may be represented as an I2C client.

The I2C adapter is not the peripheral device. The adapter provides the bus controller; the client represents a device attached to that bus.

16. Linux I2C Device Naming

Linux commonly exposes I2C adapters through device nodes such as:

/dev/i2c-0
/dev/i2c-1
/dev/i2c-2

The number identifies an I2C adapter instance. It is not the target device address.

For example:

/dev/i2c-1

represents adapter 1. A target device connected to that adapter may have address 0x48.

When the relevant kernel support is enabled, registered I2C devices can also appear in sysfs under:

/sys/bus/i2c/devices/

17. Inspecting I2C Devices in Ubuntu

List I2C Device Nodes

ls -l /dev/i2c-*

List I2C Sysfs Devices

ls /sys/bus/i2c/devices/

Inspect I2C-Related Kernel Modules

lsmod | grep i2c

Inspect Kernel Messages

dmesg | grep -i i2c

Install I2C Tools

sudo apt update
sudo apt install i2c-tools

List Available Adapters

i2cdetect -l

Scan an Adapter

sudo i2cdetect -y 1
Only scan a bus when you understand the connected hardware and its behavior. Some devices may react unexpectedly to probing. A virtual machine may not expose a usable I2C adapter.

18. I2C Device Tree Example

Embedded Linux systems commonly describe I2C controllers and their connected peripheral devices through Device Tree.

&i2c1 {
    status = "okay";

    temperature_sensor@48 {
        compatible = "demo,temp-sensor";
        reg = <0x48>;
    };

    rtc@68 {
        compatible = "demo,rtc";
        reg = <0x68>;
    };
};

Explanation:

  • &i2c1 refers to an I2C controller node.
  • status = "okay" enables the controller node.
  • temperature_sensor@48 describes a peripheral at address 0x48.
  • rtc@68 describes a peripheral at address 0x68.
  • compatible identifies the device type for driver matching.
  • reg contains the I2C target address.
These compatible strings are illustrative. A real Device Tree must use the compatible string and binding documented for the actual peripheral and controller.

22. Important Points to Remember

  • I2C is a synchronous serial communication protocol.
  • SDA carries data and SCL carries the clock.
  • Both lines normally use pull-up resistors.
  • Multiple target devices can share one I2C bus.
  • 7-bit addressing is commonly used.
  • START and STOP conditions define transaction boundaries.
  • ACK and NACK indicate acknowledgment status.
  • Linux I2C Core provides common subsystem functionality.
  • An adapter represents the bus controller.
  • A client represents a peripheral attached to an adapter.
  • Device Tree can describe I2C peripheral devices.
  • Electrical compatibility and pull-up selection are essential.
