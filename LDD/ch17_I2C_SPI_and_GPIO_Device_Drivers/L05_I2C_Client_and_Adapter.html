2. Introduction to I2C Client and Adapter

The Linux I2C subsystem separates the controller hardware from the peripheral devices connected to it.

Two important objects are used:

  • I2C Adapter: Represents an I2C bus controller.
  • I2C Client: Represents a peripheral device connected to an I2C adapter.

For example, an embedded Linux board may contain one I2C controller connected to a temperature sensor, EEPROM and RTC.

Linux I2C Subsystem
↓
I2C Adapter – Controller 1
↓ SDA and SCL
I2C Client – Temperature Sensor (0x48)
I2C Client – EEPROM (0x50)
I2C Client – RTC (0x68)

3. What Is an I2C Adapter?

An I2C adapter is a software representation of an I2C controller in the Linux kernel.

The controller hardware generates the SCL clock and controls SDA communication according to the I2C protocol.

Examples of I2C Adapters

  • On-chip I2C controller inside an ARM-based SoC.
  • I2C controller inside an embedded processor.
  • External I2C controller connected through another bus.
  • USB-to-I2C bridge supported by a Linux adapter driver.

Responsibilities of an Adapter

  • Control the physical I2C bus.
  • Generate the clock signal.
  • Transmit and receive data.
  • Handle I2C transfer messages.
  • Support controller-specific hardware operations.
  • Expose the bus through the Linux I2C subsystem.

4. struct i2c_adapter

Linux represents an I2C adapter using the structure:

struct i2c_adapter;

It is defined in the Linux I2C header:

#include <linux/i2c.h>

The adapter structure contains information about the controller and the operations supported by its driver.

Important Conceptual Members

Member Purpose
owner Module ownership information.
algo Points to the I2C algorithm operations.
dev Associated device-model information.
nr Adapter bus number when assigned.
name Adapter name.
timeout Transfer timeout configuration.
retries Retry configuration for supported operations.
The exact fields and implementation details can vary across kernel versions. Drivers should use documented I2C subsystem APIs rather than depending on internal structure details unnecessarily.

5. I2C Adapter Driver and I2C Client Driver

Linux uses separate drivers for the controller and the peripheral.

I2C Adapter Driver

The adapter driver controls the I2C controller hardware.

Its responsibilities include:

  • Initializing the I2C controller.
  • Configuring controller clock and timing.
  • Implementing I2C transfer operations.
  • Registering the adapter with the I2C Core.

I2C Client Driver

The client driver controls a specific peripheral device connected to an adapter.

Its responsibilities include:

  • Matching the peripheral device.
  • Initializing peripheral registers.
  • Reading and writing device data.
  • Providing device-specific functionality.

↕ I2C Core
I2C Adapter Driver

Physical Peripheral Device

6. What Is an I2C Client?

An I2C client represents a peripheral device connected to an I2C adapter at a particular bus address.

Linux represents a client using:

struct i2c_client;

The structure is declared in:

#include <linux/i2c.h>

Examples

Peripheral Example Address
Temperature Sensor 0x48
EEPROM 0x50
RTC 0x68

These addresses are illustrative. Actual addresses depend on the peripheral and its hardware address configuration.

7. struct i2c_client

The struct i2c_client object stores information about a peripheral connected to an I2C bus.

Important Conceptual Members

Member Purpose
adapter Points to the adapter to which the client is connected.
addr Stores the I2C target address.
flags Contains client-specific flags.
name Contains the client name.
dev Associated Linux device-model object.
irq Associated interrupt number, when applicable.

Example Concept

struct i2c_client *client;

dev_info(&client->dev,
         "I2C address: 0x%02x\n",
         client->addr);

The I2C client is normally created by the kernel through supported device enumeration mechanisms. A peripheral driver receives the client pointer in its probe callback.

8. Relationship Between Adapter and Client

An adapter may have multiple clients attached to it.

I2C Adapter 1
├──
Client A – Address 0x48
├──
Client B – Address 0x50
└──
Client C – Address 0x68

Two clients on the same bus generally need distinct addresses. Address conflicts must be avoided unless a device-specific arrangement or separate bus segment is used.

9. I2C Device Instantiation

The kernel must know that an I2C peripheral exists before its client driver can bind to it.

Common device-instantiation mechanisms include:

  • Device Tree enumeration.
  • ACPI enumeration.
  • Explicit board information on supported legacy platforms.
  • Manual creation through supported sysfs mechanisms in controlled situations.

Device Tree Enumeration

Embedded Linux platforms commonly describe I2C peripherals in Device Tree.

&i2c1 {
    status = "okay";

    sensor@48 {
        compatible = "demo,temp-sensor";
        reg = <0x48>;
    };
};

When the I2C controller and its adapter are registered, the I2C subsystem can create a client for the described peripheral.

10. I2C Client Driver Matching

After an I2C client is created, Linux attempts to match it with a registered I2C client driver.

Matching may use:

  • Device Tree compatible strings.
  • ACPI identifiers.
  • I2C device ID tables.

Device Tree Match Table Example

static const struct of_device_id sensor_of_match[] = {
    { .compatible = "demo,temp-sensor" },
    { }
};

MODULE_DEVICE_TABLE(of, sensor_of_match);

The compatible string must match the actual device binding description.

11. I2C Driver Probe Function

When a client matches an I2C driver, the kernel calls the driver's probe function.

A modern I2C driver commonly uses:

static int sensor_probe(struct i2c_client *client)
{
    dev_info(&client->dev,
             "Sensor device detected\n");

    return 0;
}

The probe callback can:

  • Verify device identity.
  • Initialize hardware registers.
  • Allocate private driver data.
  • Configure interrupts or regulators.
  • Register a user-facing interface if required.
Probe callback signatures have changed across kernel generations. This example uses the modern one-argument I2C probe form. Always check the headers and driver API for the target kernel version.

12. I2C Driver Remove Function

The remove callback is invoked when the client device is detached or the driver is unbound.

static void sensor_remove(struct i2c_client *client)
{
    dev_info(&client->dev,
             "Sensor device removed\n");
}

The remove callback should:

  • Stop ongoing device operations.
  • Disable device interrupts where necessary.
  • Unregister interfaces created by the driver.
  • Release resources that were not device-managed.

Device-managed resources are released automatically during device teardown.

13. I2C Driver Structure

A peripheral driver is represented using struct i2c_driver.

static struct i2c_driver sensor_driver = {
    .driver = {
        .name = "demo_sensor",
        .of_match_table = sensor_of_match,
    },
    .probe = sensor_probe,
    .remove = sensor_remove,
};

The driver structure associates the probe and remove callbacks with the I2C subsystem.

The complete registration and communication workflow is covered in the next lessons.

14. I2C Adapter Numbering

Linux assigns adapter numbers to I2C buses.

Examples:

/dev/i2c-0
/dev/i2c-1
/dev/i2c-2

The number identifies the adapter instance. It does not identify a peripheral address.

Linux Name Meaning
i2c-0 Adapter number 0.
i2c-1 Adapter number 1.
i2c-2 Adapter number 2.

Adapter numbering can depend on registration order or explicit configuration. Do not assume that a particular physical controller always receives the same number across different systems.

15. I2C Client Representation in Sysfs

Linux exposes I2C devices through the sysfs device model.

List I2C Devices

ls /sys/bus/i2c/devices/

Example entries may look like:

i2c-0
i2c-1
1-0048
1-0050
1-0068

An entry such as 1-0048 commonly represents a client at address 0x48 on adapter 1.

Inspect a Client

ls -l /sys/bus/i2c/devices/1-0048/

Inspect the Bound Driver

readlink /sys/bus/i2c/devices/1-0048/driver
These example paths appear only when the corresponding adapter and client are registered. Your system may use different adapter numbers and device addresses.

16. I2C Tools for Inspection

Install I2C Tools

sudo apt update
sudo apt install i2c-tools

List Adapters

i2cdetect -l

Scan Adapter 1

sudo i2cdetect -y 1

Inspect Kernel Messages

dmesg | grep -i i2c

Inspect I2C Modules

lsmod | grep i2c

These commands help identify available adapters and registered devices.

Do not use I2C scanning or raw access commands on an unknown production bus. Probing can interfere with devices or trigger unwanted behavior. Follow the hardware documentation.

17. I2C Adapter and Client Error Handling

Error or Symptom Possible Cause Suggested Check
Adapter not available Controller driver not loaded or hardware disabled Check Device Tree and kernel logs.
Client not created Incorrect device description Check Device Tree or ACPI enumeration.
Driver not bound Device match table does not match Check compatible strings and driver registration.
Probe fails Device initialization or communication failure Inspect probe logs and hardware state.
Address conflict Two devices use the same address on one bus Check address pins and bus topology.
Transfer error Electrical fault or incorrect transaction Check wiring, timing and device datasheet.

19. Important Points to Remember

  • An I2C adapter represents a bus controller.
  • An I2C client represents a peripheral device.
  • struct i2c_adapter represents the adapter.
  • struct i2c_client represents the peripheral.
  • One adapter can have multiple clients.
  • Client addresses identify devices on the bus.
  • Device Tree is a common device-instantiation mechanism.
  • The I2C Core handles device and driver matching.
  • The client driver's probe callback initializes the peripheral.
  • Sysfs provides visibility into registered I2C devices.
