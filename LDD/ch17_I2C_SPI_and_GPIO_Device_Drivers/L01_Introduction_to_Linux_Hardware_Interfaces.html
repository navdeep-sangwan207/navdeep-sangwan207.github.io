2. Introduction to Linux Hardware Interfaces

Embedded Linux systems interact with external and internal hardware through different electrical and communication interfaces.

Examples of connected hardware include:

  • Temperature sensors.
  • Pressure sensors.
  • LCD displays.
  • LEDs and push buttons.
  • EEPROM memory.
  • Real-time clock modules.
  • ADC and DAC devices.
  • Motor controllers.

Linux provides hardware subsystems and driver APIs so that developers do not need to implement every electrical communication detail from scratch.

3. What Is GPIO?

GPIO stands for General Purpose Input/Output.

GPIO pins are configurable digital pins that can be used to read an input signal or control an output signal.

GPIO as Input

A GPIO input can read digital signals from external components.

Examples:

  • Push buttons.
  • Digital switches.
  • Logic-level sensor outputs.
  • Digital status signals.

GPIO as Output

A GPIO output can control external digital circuits.

Examples:

  • LED control.
  • Relay driver input.
  • Chip-select control.
  • Enable and reset signals.
GPIO Input: Button → Processor
GPIO Output: Processor → LED Driver

GPIO Logic Levels

Logic State Typical Meaning
LOW Logic 0, close to ground potential.
HIGH Logic 1, near the GPIO voltage level.
GPIO voltage levels are hardware-dependent. A GPIO may operate at 1.8 V, 3.3 V or another specified level. Never assume a 5 V tolerant input unless the hardware documentation explicitly confirms it.

4. What Is I2C?

I2C stands for Inter-Integrated Circuit.

It is a synchronous serial communication protocol commonly used to connect low-speed peripheral devices to a processor or microcontroller.

Two Main I2C Signals

Signal Full Form Function
SCL Serial Clock Provides the clock signal.
SDA Serial Data Carries communication data.

I2C Bus Diagram

I2C Controller
SCL + SDA
Temperature Sensor
EEPROM
RTC Module

Important I2C Characteristics

  • Uses two main bus signals.
  • Supports multiple addressed devices on a bus.
  • Uses a controller to initiate transfers.
  • Uses device addresses to select targets.
  • Uses ACK and NACK responses.
  • Uses open-drain or open-collector signaling with pull-up resistors.
  • Supports standard and higher-speed operating modes, depending on hardware.

Common I2C Applications

  • Temperature sensors.
  • EEPROM devices.
  • RTC modules.
  • Power-management ICs.
  • Sensor modules.

5. What Is SPI?

SPI stands for Serial Peripheral Interface.

It is a synchronous serial communication protocol commonly used for communication between a controller and one or more peripheral devices.

Common SPI Signals

Signal Meaning Function
SCLK Serial Clock Provides the clock signal.
MOSI Controller Out, Peripheral In Transfers data from controller to peripheral.
MISO Controller In, Peripheral Out Transfers data from peripheral to controller.
CS / SS Chip Select / Slave Select Selects the target peripheral.

SPI Bus Diagram

SPI Controller
SCLK, MOSI, MISO, CS
SPI Flash Memory
SPI Display
SPI Sensor

Important SPI Characteristics

  • Uses a clock signal.
  • Uses separate transmit and receive data lines in the common four-wire arrangement.
  • Typically uses chip-select signals to choose a peripheral.
  • Supports full-duplex data transfer in common implementations.
  • Does not define a universal device-addressing mechanism like I2C.
  • Clock polarity and phase are configured using SPI modes.
  • Can support high data rates, depending on controller and peripheral capabilities.

Common SPI Applications

  • Flash memory.
  • Display controllers.
  • High-speed sensors.
  • ADC and DAC devices.
  • Wireless communication modules.

6. Difference Between GPIO, I2C and SPI

Feature GPIO I2C SPI
Purpose Digital input/output Serial communication Serial communication
Signals One or more configurable pins SCL and SDA SCLK, MOSI, MISO and CS
Clock Not required for ordinary GPIO operations Yes Yes
Device Selection Depends on circuit design Address-based Usually chip-select based
Communication Digital signals Serial bus Serial bus
Typical Use LEDs, buttons, reset Sensors, RTC, EEPROM Flash, displays, fast sensors

7. Linux Hardware Interface Architecture

Linux provides dedicated kernel subsystems for hardware interfaces.

GPIO Subsystem

The GPIO subsystem provides standard kernel APIs for requesting and controlling GPIO lines.

I2C Subsystem

The I2C subsystem manages I2C controllers, adapters, clients and I2C device drivers.

SPI Subsystem

The SPI subsystem manages SPI controllers, SPI devices and SPI peripheral drivers.

8. Controller Driver and Peripheral Driver

It is important to distinguish between a hardware controller driver and a peripheral device driver.

Controller Driver

A controller driver manages the hardware block that implements a communication interface.

Examples:

  • SoC I2C controller driver.
  • SPI controller driver.
  • GPIO controller driver.

Peripheral Driver

A peripheral driver manages a device connected to a controller.

Examples:

  • I2C temperature sensor driver.
  • SPI flash memory driver.
  • GPIO-controlled LED driver.

The controller driver provides access to the bus controller. A peripheral driver uses the relevant subsystem API to communicate with its device. These are separate driver roles.

9. Device Tree and Hardware Interfaces

Device Tree can describe the hardware connections and resources needed by Linux.

Depending on the hardware and binding, a Device Tree description may specify:

  • Compatible string.
  • Register address and size.
  • Interrupt information.
  • Clock references.
  • Reset controls.
  • GPIO connections.
  • Pin control configuration.
  • Bus-specific peripheral addresses and properties.

Illustrative I2C Device Tree Example

&i2c1 {
    status = "okay";

    sensor@48 {
        compatible = "demo,temperature-sensor";
        reg = <0x48>;
    };
};

Here:

  • &i2c1 refers to an I2C controller node defined elsewhere.
  • sensor@48 represents an I2C peripheral at address 0x48.
  • compatible identifies the device type for driver matching.
  • reg contains the I2C address according to the bus binding.
This is an illustrative example. The controller label, compatible string, address and required properties must match the actual board and the peripheral's Device Tree binding. Do not assume every sensor uses address 0x48.

10. Linux User Space and Hardware Interfaces

Applications can interact with hardware through appropriate kernel interfaces.

Interface Common User-Space Access Purpose
GPIO GPIO character-device API and libgpiod tools Request and control GPIO lines.
I2C /dev/i2c-N using suitable interfaces Access supported I2C adapter operations.
SPI /dev/spidevB.C where enabled Perform SPI transfers from user space.

Linux also supports in-kernel peripheral drivers. A kernel driver is generally preferable when the device needs integration with a kernel subsystem, interrupt handling, power management or other kernel services.

Not every device is exposed through a generic userspace interface. Device Tree configuration, kernel configuration and driver binding determine which interfaces are available.

11. Checking Hardware Interfaces in Linux

The following commands can help inspect available interfaces on a Linux system.

List I2C Devices

ls /sys/bus/i2c/devices/

List SPI Devices

ls /sys/bus/spi/devices/

List GPIO Chips

ls /dev/gpiochip*

List I2C Device Nodes

ls /dev/i2c-*

List SPI Device Nodes

ls /dev/spidev*

Inspect Kernel Messages

sudo dmesg | tail -n 30
These commands may return no matching devices on a VirtualBox Ubuntu installation. The required hardware controller, kernel support and device configuration must be present before corresponding device nodes appear.

12. Advantages of Linux Hardware Subsystems

  • Provide standardized interfaces for hardware drivers.
  • Reduce duplicated communication code.
  • Separate controller-specific logic from peripheral logic.
  • Support hardware discovery and device matching.
  • Provide common resource-management mechanisms.
  • Support power management and interrupt integration.
  • Improve driver portability across supported hardware platforms.

14. Connection with Embedded Systems and LPC2129

The GPIO, I2C and SPI concepts are also important in bare-metal embedded development.

In your LPC2129 learning track:

  • GPIO concepts apply to controlling LEDs and reading switches.
  • I2C concepts apply to communication with external I2C peripherals.
  • SPI concepts apply to serial communication with supported SPI peripherals.
  • Peripheral registers are configured through the LPC2129 hardware documentation.

However, the Linux implementation uses kernel subsystems and driver APIs rather than direct bare-metal register programming.

Your Keil LPC2129 simulator is suitable for studying ARM7 peripheral concepts and bare-metal firmware. It does not provide a Linux kernel environment for testing Linux GPIO, I2C or SPI subsystem drivers.
