Chapter: Kernel Memory Management

Lesson: 10 – Memory Management in Device Drivers

Prerequisites: kmalloc(), kfree(), vmalloc(), GFP flags, physical and virtual memory, and DMA allocation.

Objective: Learn how to select, allocate, manage, synchronize and release memory safely in Linux device drivers.

1. Introduction

Memory management is an important responsibility in Linux device driver development.

A driver may need memory for:

  • Device-private data structures.
  • Character-device buffers.
  • Network packet buffers.
  • Hardware descriptors.
  • DMA transfer buffers.
  • Temporary data and request queues.
  • Device configuration and status information.

Unlike ordinary user-space programs, kernel code must carefully consider allocation context, synchronization, memory ownership and cleanup.

2. Why Do Device Drivers Need Dynamic Memory?

Some memory requirements are known at compile time. Other requirements depend on the device, configuration or runtime activity.

Examples

  • A character driver allocates a buffer for incoming data.
  • A platform driver allocates a private structure for each device instance.
  • A network driver manages packet buffers.
  • A hardware driver allocates DMA descriptors.
  • A driver allocates a larger buffer when the device configuration changes.

Dynamic allocation allows a driver to obtain memory when needed rather than reserving every possible buffer permanently.

Dynamic allocation must be controlled carefully. Excessive allocation, leaks and fragmentation can reduce system stability.

3. Selecting the Correct Memory Allocation API

Linux provides several memory allocation mechanisms. The correct choice depends on size, physical-contiguity requirements, execution context and device requirements.

API Memory Property Release Function Typical Use
kmalloc() Virtually and physically contiguous allocation kfree() Small kernel buffers and structures
kzalloc() Zero-initialized kmalloc-style allocation kfree() Driver-private structures
kcalloc() Zero-initialized array allocation kfree() Arrays of kernel objects
vmalloc() Virtually contiguous, not necessarily physically contiguous vfree() Larger virtual buffers
dma_alloc_coherent() DMA API-managed coherent memory dma_free_coherent() DMA descriptors and shared control buffers
dma_map_single() Maps a suitable existing buffer for streaming DMA dma_unmap_single() DMA transfer buffers

4. Memory Allocation Decision

Before allocating memory, a driver developer should answer these questions:

  1. How much memory is required?
  2. Does the memory need physical contiguity?
  3. Will a hardware device access the memory using DMA?
  4. Can the current execution context sleep?
  5. Must the memory be initialized to zero?
  6. How and when will the memory be released?

5. Memory Allocation Context

Kernel memory allocation depends on the context in which the allocation occurs.

Some kernel contexts allow sleeping, while others require the code to continue without blocking.

Execution Context Can Sleep? Typical Allocation Consideration
Process context Usually yes, if no other constraint prevents it GFP_KERNEL is commonly suitable.
Module initialization Yes, generally GFP_KERNEL is commonly suitable.
Hard interrupt handler No Avoid sleeping allocations; prefer preallocated memory.
Softirq / tasklet No Use non-sleeping approaches where allocation is unavoidable.
While holding a spinlock No Do not use an allocation mode that may sleep.
Workqueue callback Usually yes GFP_KERNEL is often suitable, subject to locking and reclaim constraints.
The safest approach in an interrupt handler is generally to use memory allocated earlier in a sleepable context. GFP_ATOMIC is not a universal solution and can still fail.

6. GFP Flags in Device Drivers

GFP flags describe allocation constraints and reclaim behavior.

Flag General Meaning
GFP_KERNEL Normal allocation that may sleep and perform reclaim.
GFP_ATOMIC Non-sleeping allocation suitable for certain atomic contexts; may use emergency reserves.
GFP_NOWAIT Non-sleeping allocation with more restricted access to reserves; may fail more readily.
GFP_NOIO Restricts reclaim from initiating I/O.
GFP_NOFS Restricts reclaim from entering filesystem paths.
__GFP_ZERO Requests zero-initialized memory.

Examples

buffer = kmalloc(256, GFP_KERNEL);

buffer = kmalloc(128, GFP_ATOMIC);

buffer = kmalloc(
    512,
    GFP_KERNEL | __GFP_ZERO
);

For routine zero-initialized allocation, kzalloc(512, GFP_KERNEL) is usually clearer.

7. Memory Allocation and Buffer Management

A driver often maintains buffers that are used repeatedly.

For example, a character driver may allocate a buffer during initialization and use it for subsequent read and write operations.

↓

Allocating a buffer once and reusing it can be more efficient than repeatedly allocating and freeing memory for every operation.

8. Example: Device-Private Data Structure

Many drivers allocate a private structure for each device instance.

#include <linux/slab.h>

struct my_device_data {
    int device_id;
    int status;
    char name[32];
};

struct my_device_data *data;

data = kzalloc(sizeof(*data), GFP_KERNEL);

if (!data)
    return -ENOMEM;

data->device_id = 1;
data->status = 0;

Using kzalloc() ensures that the structure is initially zeroed.

The driver can store the structure using the relevant device-model or driver-private-data mechanism, depending on its subsystem.

9. Memory Allocation for Character Drivers

A character driver may maintain a shared data buffer for read and write operations.

A simplified private structure could be:

#define BUFFER_SIZE 1024

struct my_char_device {
    char buffer[BUFFER_SIZE];
    size_t data_length;
    struct mutex lock;
};

This example uses an embedded fixed-size array. It does not require a separate dynamic allocation for the buffer.

If the buffer size must be determined at runtime, a driver could allocate it separately:

device_buffer = kzalloc(
    BUFFER_SIZE,
    GFP_KERNEL
);

if (!device_buffer)
    return -ENOMEM;

When multiple operations can access the buffer concurrently, suitable synchronization such as a mutex may be required.

10. Memory Management in Interrupt-Driven Drivers

Interrupt handlers execute in atomic context and must not perform operations that can sleep.

Therefore, memory required by an interrupt handler should normally be allocated before the interrupt occurs.

Driver Initialization
↓
Allocate Required Buffers
↓
Register Interrupt Handler
↓
Interrupt Occurs
↓
Handler Uses Existing Buffer

Important Rules

  • Do not call sleeping allocation paths in hard IRQ context.
  • Do not use GFP_KERNEL in a hard interrupt handler.
  • Do not call mutex_lock() in a hard interrupt handler.
  • Keep interrupt handlers short.
  • Use workqueues or threaded interrupts for work that may sleep.
  • Protect shared data using synchronization appropriate to the context.

11. Memory Management in DMA-Based Drivers

When hardware transfers data using DMA, the driver must use the DMA API rather than assuming that a normal kernel allocation is automatically suitable.

Coherent DMA Allocation

void *cpu_addr;
dma_addr_t dma_handle;

cpu_addr = dma_alloc_coherent(
    dev,
    4096,
    &dma_handle,
    GFP_KERNEL
);

if (!cpu_addr)
    return -ENOMEM;

Release

dma_free_coherent(
    dev,
    4096,
    cpu_addr,
    dma_handle
);

The CPU uses cpu_addr, while the device uses dma_handle when programmed according to its hardware specification.

12. Managed Memory Allocation

Linux provides device-managed resource APIs, commonly called devres or managed allocation APIs.

These APIs associate resource cleanup with the lifetime of a device.

Example: devm_kzalloc()

struct my_device_data *data;

data = devm_kzalloc(
    &pdev->dev,
    sizeof(*data),
    GFP_KERNEL
);

if (!data)
    return -ENOMEM;

The allocated memory is automatically released when the associated device is detached and its managed resources are cleaned up.

Other Examples

  • devm_kmalloc()
  • devm_kzalloc()
  • devm_kcalloc()
  • dmam_alloc_coherent()
Managed resources simplify cleanup, but they do not remove the need to understand resource ownership. Do not manually free a resource that is already managed by devres. Also ensure that no asynchronous activity or open-file reference can access device data after its lifetime ends.

13. Memory Leaks in Device Drivers

A memory leak occurs when allocated memory is no longer needed but is not released.

Incorrect Example

static int __init leak_init(void)
{
    char *buffer;

    buffer = kmalloc(1024, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    /* Buffer is never released. */

    return 0;
}

Correct Lifecycle

static char *buffer;

static int __init demo_init(void)
{
    buffer = kmalloc(1024, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    return 0;
}

static void __exit demo_exit(void)
{
    kfree(buffer);
    buffer = NULL;
}

The memory is allocated during initialization and released during module cleanup.

14. Error Handling and Partial Initialization

A driver initialization function may allocate multiple resources. If a later allocation fails, earlier allocations must be released.

Example

static char *buffer_a;
static char *buffer_b;

static int __init demo_init(void)
{
    buffer_a = kmalloc(512, GFP_KERNEL);

    if (!buffer_a)
        return -ENOMEM;

    buffer_b = kzalloc(1024, GFP_KERNEL);

    if (!buffer_b) {
        kfree(buffer_a);
        buffer_a = NULL;
        return -ENOMEM;
    }

    return 0;
}

static void __exit demo_exit(void)
{
    kfree(buffer_b);
    kfree(buffer_a);

    buffer_b = NULL;
    buffer_a = NULL;
}

This example demonstrates cleanup after a partial initialization failure.

Good Practice

  • Check every allocation result.
  • Release previously allocated resources on failure.
  • Keep cleanup paths easy to follow.
  • Use matching allocation and release functions.
  • Do not release memory while another execution path can still access it.

15. Memory Lifetime and Concurrency

Correct allocation and release functions are not enough. A driver must also ensure that memory remains valid for as long as it is being used.

Consider a character device with an open file descriptor. If the device is removed while that file descriptor is still active, freeing its private data immediately may cause a use-after-free bug.

Important Concepts

  • Ownership: Which part of the driver is responsible for the memory?
  • Lifetime: How long must the memory remain valid?
  • Synchronization: Can multiple execution paths access it concurrently?
  • Reference counting: Are references keeping the object alive?
  • Teardown: Have interrupts, workqueues, timers and active users been stopped or synchronized before release?
Never free a buffer simply because the device has been removed if existing file operations, work items or other asynchronous paths may still reference it.

16. Memory Alignment

Some hardware and kernel data structures require specific memory alignment.

Alignment means that an object begins at an address satisfying a specified boundary.

Example

#include <linux/slab.h>

struct my_descriptor {
    u32 address;
    u32 length;
};

struct my_descriptor *desc;

desc = kmalloc(
    sizeof(*desc),
    GFP_KERNEL
);

if (!desc)
    return -ENOMEM;

For ordinary kernel structures, the allocator provides suitable alignment for the type. Hardware descriptor alignment requirements must be checked against the device specification and the allocation API's guarantees.

Do not assume that a normal kmalloc allocation satisfies every special hardware alignment or DMA boundary constraint. Use appropriate DMA APIs and allocation facilities.

17. Memory Fragmentation

Memory fragmentation occurs when free memory is divided into smaller separated regions.

External Fragmentation

Free memory exists, but there may not be a sufficiently large physically contiguous block for a requested allocation.

Internal Fragmentation

An allocated memory block may contain unused space because the allocator provides a block larger than the exact requested size.

Reducing Allocation Pressure

  • Avoid unnecessarily large physically contiguous allocations.
  • Reuse buffers when appropriate.
  • Use vmalloc() when physical contiguity is not required and its trade-offs are acceptable.
  • Use the DMA API for device DMA requirements.
  • Consider buffer pools for repeated allocations in performance-sensitive drivers.

18. Memory Pools

Linux provides memory-pool facilities such as mempool for situations where allocations must remain possible under memory pressure.

A memory pool maintains a reserve of preallocated elements that can be used when ordinary allocation is not available.

Memory pools are useful in certain critical paths, including some storage and block I/O implementations.

They are not a general replacement for kmalloc(). Pool creation, element size, minimum reserve and allocation behavior must be designed for the particular driver.

19. Memory Debugging Tools

Linux provides tools and kernel configuration options that help detect memory-management errors.

Tool / Feature Purpose
SLUB debugging Helps detect certain slab allocator errors, such as corruption and some invalid frees.
KASAN Detects many out-of-bounds and use-after-free memory errors.
kmemleak Helps identify possible memory leaks.
Lockdep Detects certain locking problems, including potential deadlocks.
ftrace Provides tracing facilities useful for investigating kernel behavior.

Availability depends on kernel configuration, architecture and build options.

20. Complete Practical Example: Memory Allocation Module

This example demonstrates a small kernel module that allocates a private structure, allocates a buffer, checks errors and releases resources correctly.

Create driver_memory_demo.c:

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/slab.h>
#include <linux/string.h>

#define BUFFER_SIZE 256

struct driver_data {
    int device_id;
    char *buffer;
};

static struct driver_data *data;

static int __init driver_memory_init(void)
{
    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data) {
        pr_err("Unable to allocate driver data\n");
        return -ENOMEM;
    }

    data->device_id = 1;

    data->buffer = kmalloc(
        BUFFER_SIZE,
        GFP_KERNEL
    );

    if (!data->buffer) {
        pr_err("Unable to allocate buffer\n");
        kfree(data);
        data = NULL;
        return -ENOMEM;
    }

    snprintf(
        data->buffer,
        BUFFER_SIZE,
        "Linux driver memory management example"
    );

    pr_info("Device ID: %d\n", data->device_id);
    pr_info("Buffer: %s\n", data->buffer);

    return 0;
}

static void __exit driver_memory_exit(void)
{
    if (data) {
        kfree(data->buffer);
        data->buffer = NULL;

        kfree(data);
        data = NULL;
    }

    pr_info("Driver memory released\n");
}

module_init(driver_memory_init);
module_exit(driver_memory_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Driver memory management demonstration");
MODULE_AUTHOR("NS Learning Hub");

Makefile

obj-m += driver_memory_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test in Ubuntu

sudo apt update
sudo apt install build-essential linux-headers-$(uname -r)

make

sudo insmod driver_memory_demo.ko

sudo dmesg | tail -n 20

sudo rmmod driver_memory_demo

make clean

Illustrative Output

Device ID: 1
Buffer: Linux driver memory management example
Driver memory released

The output is illustrative. Actual kernel log formatting and timestamps depend on the system.

21. Best Practices for Driver Memory Management

  1. Choose the allocation API based on actual memory requirements.
  2. Use GFP_KERNEL only in contexts where sleeping is permitted.
  3. Prefer preallocated buffers in interrupt-sensitive paths.
  4. Use kzalloc() when zero initialization is required.
  5. Use the DMA API for DMA-capable devices.
  6. Check every allocation and DMA mapping result.
  7. Pair allocation and release APIs correctly.
  8. Release partially allocated resources on initialization failure.
  9. Protect shared data using suitable synchronization.
  10. Do not free objects while active users may still reference them.
  11. Use managed resources where their lifetime model is appropriate.
  12. Use memory debugging facilities during development.

22. Lesson Summary

  • Device drivers allocate memory for private data, buffers and hardware operations.
  • kmalloc(), kzalloc(), kcalloc() and vmalloc() serve different allocation needs.
  • GFP flags must match the execution context.
  • Interrupt handlers should normally use preallocated memory.
  • DMA operations must use the Linux DMA API.
  • Managed allocation APIs can simplify resource cleanup.
  • Memory leaks and use-after-free errors can destabilize the kernel.
  • Correct synchronization and object lifetime management are essential.
  • Debugging tools help detect memory corruption and leaks.
