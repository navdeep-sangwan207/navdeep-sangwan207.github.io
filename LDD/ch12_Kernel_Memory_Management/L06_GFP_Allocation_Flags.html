Chapter: Kernel Memory Management

Lesson: 6 – GFP Allocation Flags

Prerequisites: kmalloc(), kfree(), kzalloc(), kcalloc(), process context and interrupt context.

Objective: Understand GFP allocation flags, select suitable allocation behavior and avoid sleeping in atomic contexts.

1. Introduction to GFP Flags

Linux kernel memory allocation functions often accept a parameter called GFP flags.

GFP stands for Get Free Pages. These flags describe the allocation constraints and permitted behavior when the kernel attempts to obtain memory.

For example:

buffer = kmalloc(256, GFP_KERNEL);

Here:

  • kmalloc() requests memory.
  • 256 specifies the requested size in bytes.
  • GFP_KERNEL specifies the allocation behavior.

The allocator uses these flags to determine which memory-reclaim and allocation operations are permitted.

2. Why Are GFP Flags Required?

The Linux kernel executes in different contexts. Some contexts permit sleeping, while others require immediate, non-blocking execution.

For example:

  • A normal process-context function may be allowed to sleep.
  • A hard interrupt handler must not sleep.
  • A function holding a spinlock must not sleep.

The allocation request must respect these execution constraints.

3. GFP_KERNEL

GFP_KERNEL is the most commonly used allocation flag for normal kernel operations where sleeping is permitted.

Example

char *buffer;

buffer = kmalloc(512, GFP_KERNEL);

if (!buffer) {
    pr_err("Allocation failed\n");
    return -ENOMEM;
}

Characteristics

  • Suitable for sleepable process context.
  • Allows allocation paths that may block.
  • Can allow memory reclaim operations.
  • Commonly used in module initialization and ordinary driver operations when the context permits sleeping.
GFP_KERNEL must not be used in hard interrupt context or while holding a spinlock because the allocation may sleep.

4. GFP_ATOMIC

GFP_ATOMIC is used when an allocation must not sleep.

It is relevant to certain atomic contexts where the kernel cannot block the current execution path.

Example

char *buffer;

buffer = kmalloc(128, GFP_ATOMIC);

if (!buffer) {
    pr_err("Atomic allocation failed\n");
    return -ENOMEM;
}

Characteristics

  • Does not permit sleeping.
  • Can be used in suitable atomic contexts.
  • Has more restrictive allocation behavior than GFP_KERNEL.
  • Allocation failure is possible, particularly under memory pressure.
GFP_ATOMIC is not a guarantee that allocation will succeed. Avoid unnecessary allocations in interrupt handlers; preallocate buffers whenever practical.

5. GFP_KERNEL vs GFP_ATOMIC

Feature GFP_KERNEL GFP_ATOMIC
May sleep Yes No
Normal process context Suitable when sleeping is permitted Can be used, but usually unnecessary
Hard interrupt context Not suitable Suitable for certain non-sleeping allocations
While holding spinlock Not suitable May be suitable if allocation is truly required
Allocation behavior Can use reclaim paths that block Uses more restrictive non-blocking behavior

6. Process Context and Interrupt Context

Process Context

Process context refers to kernel code executing on behalf of a process or kernel thread. Such code can generally sleep when the surrounding operation permits it.

static int device_open(struct inode *inode,
                       struct file *file)
{
    char *buffer;

    buffer = kmalloc(256, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    kfree(buffer);

    return 0;
}

Interrupt Context

Interrupt handlers execute in a non-sleeping context. They must not perform operations that may block.

static irqreturn_t device_irq_handler(
    int irq, void *dev_id)
{
    /* Do not use GFP_KERNEL here. */

    return IRQ_HANDLED;
}

If interrupt processing needs a memory buffer, a common design is to allocate it in advance during initialization or another sleepable context.

7. Other Important GFP Flags

Linux provides additional allocation flags for specialized situations. The exact behavior and availability can depend on the kernel version and configuration.

Flag Purpose
GFP_NOIO Restricts memory reclaim from initiating I/O. Useful in contexts where reclaim-triggered I/O could cause recursion or deadlock.
GFP_NOFS Restricts filesystem-related reclaim activity. Useful in certain filesystem paths to avoid recursive filesystem operations.
GFP_NOWAIT Requests allocation without waiting or performing reclaim that may block. It can fail readily.
__GFP_ZERO Requests zero initialization of allocated memory.
__GFP_HIGH Allows access to certain high-priority allocation reserves, subject to kernel rules.
__GFP_NOWARN Suppresses the usual allocation-failure warning for that request.
These flags are not interchangeable. Specialized flags should be selected only after understanding the allocation path and the reason for restricting reclaim behavior.

8. Combining GFP Flags

Some GFP flags can be combined using the bitwise OR operator.

Example

buffer = kmalloc(
    256,
    GFP_KERNEL | __GFP_ZERO
);

This requests a sleepable allocation and zero initialization.

However, when zero-initialized memory is required, the clearer interface is usually:

buffer = kzalloc(256, GFP_KERNEL);

Another example of a specialized combination is:

buffer = kmalloc(
    128,
    GFP_NOIO
);

This restricts reclaim-related I/O. It does not mean that the allocation can never block.

9. GFP Flags and Memory Reclaim

When the kernel receives a memory allocation request, it may not have a suitable free block immediately available.

Depending on the GFP flags, the allocator may attempt memory reclaim to obtain memory.

Memory reclaim can involve operations such as:

  • Reclaiming eligible page-cache pages.
  • Writing dirty pages back to storage where appropriate.
  • Reclaiming eligible slab objects.
  • Other kernel memory-management activities.
Allocation Request
↓

↓

↓

Not every allocation performs reclaim. If suitable memory is already available, the request may be satisfied immediately.

10. Choosing the Correct GFP Flag

Situation Typical Choice Reason
Normal driver initialization GFP_KERNEL Sleeping is generally permitted.
Normal process-context operation GFP_KERNEL Reclaim may be permitted.
Hard interrupt handler GFP_ATOMIC if allocation is unavoidable Must not sleep; preallocation is preferable.
Allocation while holding a spinlock Preallocate or use an appropriate atomic allocation strategy Sleeping is forbidden while holding the spinlock.
Filesystem-sensitive reclaim path GFP_NOFS where required Avoids certain recursive filesystem reclaim paths.
I/O-sensitive reclaim path GFP_NOIO where required Restricts reclaim-triggered I/O.

11. Practical Example: GFP_KERNEL Allocation

Create a file named gfp_kernel_demo.c.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/slab.h>

#define BUFFER_SIZE 256

static char *buffer;

static int __init gfp_demo_init(void)
{
    buffer = kmalloc(BUFFER_SIZE, GFP_KERNEL);

    if (!buffer) {
        pr_err("GFP_KERNEL allocation failed\n");
        return -ENOMEM;
    }

    snprintf(buffer, BUFFER_SIZE,
             "Memory allocated using GFP_KERNEL");

    pr_info("%s\n", buffer);

    return 0;
}

static void __exit gfp_demo_exit(void)
{
    kfree(buffer);
    buffer = NULL;

    pr_info("GFP_KERNEL memory released\n");
}

module_init(gfp_demo_init);
module_exit(gfp_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("GFP_KERNEL allocation demonstration");

Explanation

  1. The module requests 256 bytes.
  2. GFP_KERNEL allows a sleepable allocation.
  3. The allocation result is checked.
  4. A message is stored in the buffer.
  5. The module cleanup function releases the memory.

12. Practical Example: GFP_ATOMIC Allocation

The following example demonstrates a non-sleeping allocation flag in module initialization. It is not an interrupt-handler demonstration; module initialization itself is normally sleepable.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/slab.h>

#define BUFFER_SIZE 128

static char *buffer;

static int __init gfp_atomic_demo_init(void)
{
    buffer = kmalloc(BUFFER_SIZE, GFP_ATOMIC);

    if (!buffer) {
        pr_err("GFP_ATOMIC allocation failed\n");
        return -ENOMEM;
    }

    snprintf(buffer, BUFFER_SIZE,
             "GFP_ATOMIC allocation successful");

    pr_info("%s\n", buffer);

    return 0;
}

static void __exit gfp_atomic_demo_exit(void)
{
    kfree(buffer);
    buffer = NULL;

    pr_info("GFP_ATOMIC memory released\n");
}

module_init(gfp_atomic_demo_init);
module_exit(gfp_atomic_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("GFP_ATOMIC allocation demonstration");
This example demonstrates the flag, not a recommendation to use GFP_ATOMIC in ordinary initialization code. Prefer GFP_KERNEL when sleeping is permitted.

13. Makefile

For the GFP_KERNEL example:

obj-m += gfp_kernel_demo.o

KDIR := /lib/modules/$(shell uname -r)/build

	$(MAKE) -C $(KDIR) M=$(PWD) modules

For the GFP_ATOMIC example, change the first line to:

Build each example separately or configure the Makefile for the intended module.

15. Common Mistakes

Mistake Why It Is Wrong Correct Approach
Using GFP_KERNEL in an interrupt handler The allocation may sleep. Preallocate or use an appropriate non-sleeping strategy.
Using GFP_ATOMIC everywhere It unnecessarily uses restrictive allocation behavior. Prefer GFP_KERNEL in sleepable contexts.
Assuming GFP_ATOMIC never fails Non-blocking allocation can fail. Always check the return value.
Allocating while holding a spinlock with GFP_KERNEL May sleep while holding a spinlock. Allocate before taking the lock or use a suitable atomic strategy.
Ignoring reclaim recursion Can cause deadlocks in sensitive filesystem or I/O paths. Use specialized flags only when the calling path requires them.

16. Lesson Summary

  • GFP flags control kernel memory allocation behavior.
  • GFP_KERNEL is commonly used in sleepable process context.
  • GFP_ATOMIC is used for certain non-sleeping allocation requirements.
  • GFP_NOFS and GFP_NOIO restrict specific reclaim operations.
  • GFP_NOWAIT requests allocation without waiting or blocking reclaim.
  • Allocation flags must match the execution context.
  • Allocation failure must always be handled.
  • Preallocation is often preferable in interrupt-time paths.
