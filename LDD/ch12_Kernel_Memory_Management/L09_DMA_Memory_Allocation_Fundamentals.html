Chapter: Kernel Memory Management

Lesson: 9 – DMA Memory Allocation Fundamentals

Prerequisites: Physical and virtual memory, kmalloc(), vmalloc(), GFP flags and device driver architecture.

Objective: Understand Direct Memory Access, DMA-capable memory, DMA addresses, coherent and streaming mappings, and Linux DMA APIs.

1. Introduction to DMA

DMA stands for Direct Memory Access.

It is a hardware mechanism that allows a device to transfer data to or from system memory without requiring the CPU to copy every byte individually.

DMA is commonly used by:

  • Network interface controllers.
  • Storage controllers.
  • Audio devices.
  • Graphics hardware.
  • High-speed communication peripherals.
  • Embedded-system peripherals.

DMA can reduce CPU overhead and improve data-transfer efficiency.

CPU
DMA-Capable Device
↓
System Memory

The device transfers data through the system's DMA and memory-access mechanisms.

2. Why Is DMA Required?

Consider a network device receiving a large amount of data.

Without DMA, the CPU may need to perform substantial data-copying work between device-related buffers and system memory.

With DMA, the device can transfer data directly into or out of an appropriately prepared memory buffer.

Advantages

  • Reduces CPU involvement in bulk data movement.
  • Can improve transfer efficiency.
  • Supports high-throughput hardware.
  • Allows devices to access prepared system-memory buffers.
DMA does not eliminate CPU involvement completely. The CPU still configures transfers, manages descriptors, handles completion events and performs synchronization.

4. DMA Address

A DMA address is the address that a device uses to access a memory buffer through its DMA interface.

It is represented in Linux using the dma_addr_t type.

dma_addr_t dma_handle;

Three address types must be distinguished:

Address Type Used By Meaning
CPU Virtual Address CPU and kernel code Address used by the CPU to access mapped memory.
Physical Address Memory system Address in the system's physical address space.
DMA Address DMA-capable device Address used by the device for DMA operations.
A DMA address is not necessarily equal to a physical address. An IOMMU or architecture-specific DMA translation mechanism may translate device-visible addresses.

5. DMA Address Translation

Modern systems may use an IOMMU (Input-Output Memory Management Unit).

The IOMMU can translate device-visible DMA addresses into physical addresses and enforce access restrictions.

CPU Virtual Address
↓ CPU MMU
Physical Memory
Device DMA Address / IOVA
↓ IOMMU (if present)
Physical Memory

Without an IOMMU, DMA mapping may use architecture-specific direct mappings, bounce buffers or other mechanisms.

The Linux DMA API hides many of these implementation details from device drivers.

6. Types of DMA Memory

Linux DMA programming commonly distinguishes between two broad mapping styles.

1. Coherent DMA Memory

Coherent DMA memory is allocated through the DMA API so that CPU and device accesses observe a coherent view of the memory according to the platform's DMA-coherency model.

It is often used for:

  • DMA descriptor rings.
  • Control structures shared between CPU and device.
  • Frequently updated device metadata.

2. Streaming DMA Mapping

Streaming DMA mapping is used when an existing memory buffer is temporarily mapped for a device transfer.

It is commonly used for:

  • Network packet buffers.
  • Storage data buffers.
  • Large one-direction or bidirectional data transfers.
Feature Coherent DMA Streaming DMA
Typical use Descriptors and shared control data Transfer buffers
Allocation / mapping dma_alloc_coherent() dma_map_single() and related APIs
Release / unmapping dma_free_coherent() dma_unmap_single() and related APIs
Synchronization Coherent visibility is provided, but ordering rules still matter Ownership and cache synchronization must follow DMA API rules
Coherent does not mean that CPU and device operations can be performed without synchronization. Memory barriers and correct ownership ordering may still be required.

7. Linux DMA API

Linux provides a DMA API that allows device drivers to allocate, map, synchronize and release DMA memory.

Important functions include:

API Purpose
dma_alloc_coherent() Allocates coherent DMA memory.
dma_free_coherent() Releases coherent DMA memory.
dma_map_single() Maps a suitable single CPU-addressable buffer for DMA.
dma_unmap_single() Unmaps a streaming DMA mapping.
dma_sync_single_for_cpu() Synchronizes a streaming mapping for CPU access when required.
dma_sync_single_for_device() Synchronizes a streaming mapping for device access when required.
dma_set_mask_and_coherent() Sets the device's supported DMA addressing capabilities for streaming and coherent allocations.

These functions are declared through the Linux DMA mapping interfaces, commonly included using:

#include <linux/dma-mapping.h>

8. dma_alloc_coherent()

dma_alloc_coherent() allocates a coherent DMA buffer.

Function Concept

void *dma_alloc_coherent(
    struct device *dev,
    size_t size,
    dma_addr_t *dma_handle,
    gfp_t gfp
);

Parameters

Parameter Meaning
dev Device structure for which DMA memory is allocated.
size Number of bytes to allocate.
dma_handle Output location for the DMA address.
gfp Allocation flags, subject to DMA API constraints.

Return Values

  • Returns a CPU-accessible virtual address on success.
  • Returns NULL if allocation fails.
  • Writes the corresponding device-visible DMA address to dma_handle.

Example

void *cpu_addr;
dma_addr_t dma_handle;

cpu_addr = dma_alloc_coherent(
    dev,
    4096,
    &dma_handle,
    GFP_KERNEL
);

if (!cpu_addr) {
    dev_err(dev, "DMA allocation failed\n");
    return -ENOMEM;
}

The CPU uses cpu_addr to access the allocated memory. The device is programmed with dma_handle, subject to the device's DMA programming requirements.

9. dma_free_coherent()

Memory allocated using dma_alloc_coherent() must be released using dma_free_coherent().

Function Concept

void dma_free_coherent(
    struct device *dev,
    size_t size,
    void *cpu_addr,
    dma_addr_t dma_handle
);

Example

dma_free_coherent(
    dev,
    4096,
    cpu_addr,
    dma_handle
);

The same device, size, CPU address and DMA handle used for the allocation must be supplied when releasing the allocation.

Do not release coherent DMA memory using kfree() or vfree(). Use the matching DMA API release function.

10. Streaming DMA Mapping

Streaming DMA mapping is useful when a driver already has a suitable CPU-accessible buffer and wants to make it available for a DMA transfer.

For a single buffer, Linux provides dma_map_single().

Function Concept

dma_addr_t dma_map_single(
    struct device *dev,
    void *cpu_addr,
    size_t size,
    enum dma_data_direction direction
);

DMA Directions

Direction Meaning
DMA_TO_DEVICE Data moves from system memory to the device.
DMA_FROM_DEVICE Data moves from the device to system memory.
DMA_BIDIRECTIONAL Data may move in both directions.

Example: Mapping a Transmit Buffer

dma_addr_t dma_handle;

dma_handle = dma_map_single(
    dev,
    buffer,
    buffer_size,
    DMA_TO_DEVICE
);

if (dma_mapping_error(dev, dma_handle)) {
    dev_err(dev, "DMA mapping failed\n");
    return -EIO;
}

/* Program the device using dma_handle. */

/* After the device has finished with the mapping: */
dma_unmap_single(
    dev,
    dma_handle,
    buffer_size,
    DMA_TO_DEVICE
);

This is a conceptual example. A real driver must ensure that the buffer remains valid, is not accessed in an incompatible way while device-owned, and is unmapped only after the device has finished the transfer.

11. DMA Mapping Error Checking

A successful call to dma_map_single() returns a DMA address. A failed mapping must be detected using dma_mapping_error().

dma_addr_t dma_handle;

dma_handle = dma_map_single(
    dev,
    buffer,
    size,
    DMA_TO_DEVICE
);

if (dma_mapping_error(dev, dma_handle)) {
    dev_err(dev, "Unable to map DMA buffer\n");
    return -EIO;
}

Do not assume that a DMA mapping always succeeds.

12. DMA Synchronization

Streaming DMA mappings may require explicit synchronization when ownership changes between the CPU and device.

Linux provides synchronization functions for this purpose.

Synchronize for Device

dma_sync_single_for_device(
    dev,
    dma_handle,
    size,
    DMA_TO_DEVICE
);

This prepares the mapping for device access where the DMA API requires synchronization.

Synchronize for CPU

dma_sync_single_for_cpu(
    dev,
    dma_handle,
    size,
    DMA_FROM_DEVICE
);

This prepares the mapping for CPU access after device activity where required.

Synchronization functions do not replace correct device-completion handling. The driver must know when the device has finished accessing the buffer.

13. DMA Ownership Model

A streaming DMA buffer should have a clear ownership model.

CPU Owns Buffer
↓
Prepare and Map for DMA
↓
Device Owns Buffer
↓
Transfer Completes
↓
Synchronize / Unmap
↓
CPU Owns Buffer Again

The exact sequence depends on whether the mapping is one-shot or reused and whether the transfer is to or from the device.

For a one-shot mapping, the driver normally unmaps after the device finishes. For a reused streaming mapping, the driver may use the synchronization APIs to switch ownership between CPU and device.

14. DMA Addressing Limitations

Not every device can address the entire system physical address space.

For example, a device may support only 32-bit DMA addresses even when the CPU and system RAM support wider addresses.

The driver should declare the device's DMA addressing capability.

Example

if (dma_set_mask_and_coherent(
        dev,
        DMA_BIT_MASK(32))) {
    dev_err(dev, "32-bit DMA not supported\n");
    return -EIO;
}

This requests support for 32-bit DMA addressing for streaming and coherent DMA operations.

If the device supports a wider address range, the driver should use the appropriate mask for that hardware.

15. DMA and Cache Coherency

Some systems have hardware cache coherency between the CPU and DMA devices. Other systems require explicit cache maintenance through the DMA API.

If the CPU modifies a buffer and the device reads it, the device must see the updated data.

If the device writes into a buffer and the CPU reads it, the CPU must see the device's updated data.

Potential Problems

  • CPU reads stale cached data.
  • Device reads data that has not been made visible to it.
  • CPU and device access the same buffer without correct ownership coordination.
  • Missing ordering or synchronization operations cause inconsistent results.

The Linux DMA API handles architecture-specific cache maintenance and mapping requirements when used correctly.

16. DMA and kmalloc()

A common misconception is that memory returned by kmalloc() can automatically be used by any DMA device.

Although kmalloc memory is physically contiguous for the requested allocation, it still needs appropriate DMA mapping and address handling.

Example of the mapping pattern:

buffer = kmalloc(size, GFP_KERNEL);

if (!buffer)
    return -ENOMEM;

dma_handle = dma_map_single(
    dev,
    buffer,
    size,
    DMA_TO_DEVICE
);

if (dma_mapping_error(dev, dma_handle)) {
    kfree(buffer);
    return -EIO;
}

/* Perform device transfer. */

/* After DMA has completed: */
dma_unmap_single(
    dev,
    dma_handle,
    size,
    DMA_TO_DEVICE
);

kfree(buffer);
Physical contiguity does not replace DMA mapping. Use the DMA API even when the CPU buffer came from kmalloc().

17. Practical DMA Allocation Example

The following is a basic coherent-DMA allocation pattern for a real device driver. It demonstrates the API lifecycle but does not operate a physical device by itself.

Create dma_demo.c:

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/platform_device.h>
#include <linux/dma-mapping.h>

#define DMA_BUFFER_SIZE 4096

struct dma_demo_data {
    void *cpu_addr;
    dma_addr_t dma_handle;
};

static int dma_demo_probe(struct platform_device *pdev)
{
    struct dma_demo_data *data;

    data = devm_kzalloc(
        &pdev->dev,
        sizeof(*data),
        GFP_KERNEL
    );

    if (!data)
        return -ENOMEM;

    if (dma_set_mask_and_coherent(
            &pdev->dev,
            DMA_BIT_MASK(32))) {
        dev_err(&pdev->dev,
                "DMA mask configuration failed\n");
        return -EIO;
    }

    data->cpu_addr = dma_alloc_coherent(
        &pdev->dev,
        DMA_BUFFER_SIZE,
        &data->dma_handle,
        GFP_KERNEL
    );

    if (!data->cpu_addr)
        return -ENOMEM;

    memset(data->cpu_addr, 0, DMA_BUFFER_SIZE);

    platform_set_drvdata(pdev, data);

    dev_info(&pdev->dev,
             "Coherent DMA buffer allocated\n");

    return 0;
}

static void dma_demo_remove(struct platform_device *pdev)
{
    struct dma_demo_data *data =
        platform_get_drvdata(pdev);

    if (data && data->cpu_addr) {
        dma_free_coherent(
            &pdev->dev,
            DMA_BUFFER_SIZE,
            data->cpu_addr,
            data->dma_handle
        );

        data->cpu_addr = NULL;
    }

    dev_info(&pdev->dev,
             "Coherent DMA buffer released\n");
}

static struct platform_driver dma_demo_driver = {
    .probe = dma_demo_probe,
    .remove = dma_demo_remove,
    .driver = {
        .name = "dma_demo",
    },
};

module_platform_driver(dma_demo_driver);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Coherent DMA allocation example");
This is a platform-driver code pattern, not a standalone load-and-test module. It requires a matching platform device to bind and execute probe(). The device must also have a valid DMA configuration. Kernel platform-driver callback signatures can vary across kernel versions; check the headers for the target kernel.

Code Explanation

  1. devm_kzalloc() allocates and zero-initializes the driver's private data.
  2. dma_set_mask_and_coherent() declares a 32-bit DMA addressing capability.
  3. dma_alloc_coherent() allocates the DMA buffer.
  4. cpu_addr is used by the CPU.
  5. dma_handle is the device-visible DMA address.
  6. dma_free_coherent() releases the buffer when the device is removed.

The example does not program DMA registers or initiate a transfer. Those steps require device-specific hardware documentation and driver logic.

18. DMA Development in Ubuntu VirtualBox

You can study DMA APIs and compile suitable driver code in your Ubuntu VirtualBox environment, but a successful compile does not prove that a real DMA transfer works.

Practical DMA testing requires an appropriate DMA-capable device and a correctly configured hardware or emulated environment.

  • Use kernel headers matching the running Ubuntu kernel.
  • Understand the device's DMA address width.
  • Use the DMA API rather than hardcoded physical addresses.
  • Check the device's DMA capabilities and IOMMU configuration.
  • Test hardware-dependent operations only with suitable hardware or supported emulation.

For learning, focus first on the allocation, mapping, synchronization and release lifecycle.

19. Common DMA Programming Mistakes

Mistake Why It Is Incorrect Correct Practice
Passing a CPU virtual address to the device The device needs a DMA address. Use the DMA API and program the returned DMA address.
Assuming physical address equals DMA address An IOMMU or DMA translation mechanism may be involved. Use the returned DMA handle.
Using kfree() for coherent DMA memory It is the wrong allocator release function. Use dma_free_coherent().
Forgetting dma_unmap_single() Streaming mappings remain active. Unmap after the device has finished using the mapping.
Ignoring mapping errors DMA mapping may fail. Check dma_mapping_error().
Using the wrong DMA direction The mapping direction does not describe the transfer correctly. Select DMA_TO_DEVICE, DMA_FROM_DEVICE or DMA_BIDIRECTIONAL appropriately.
CPU and device access without synchronization Can produce stale or inconsistent data. Follow DMA ownership and synchronization rules.
Assuming kmalloc() guarantees DMA suitability Physical contiguity alone is insufficient. Map the buffer using the DMA API.

20. Lesson Summary

  • DMA allows devices to transfer data directly to or from system memory.
  • DMA reduces CPU involvement in bulk data movement.
  • CPU virtual, physical and DMA addresses are distinct concepts.
  • The Linux DMA API manages device-specific mapping requirements.
  • Coherent DMA memory is commonly used for shared control structures.
  • Streaming DMA mappings are commonly used for transfer buffers.
  • dma_alloc_coherent() and dma_free_coherent() form a matching pair.
  • dma_map_single() and dma_unmap_single() form a matching pair.
  • DMA mapping errors and synchronization requirements must be handled.
  • DMA address masks must match device capabilities.
