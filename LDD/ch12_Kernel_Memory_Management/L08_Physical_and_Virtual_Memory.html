Chapter: Kernel Memory Management

Lesson: 8 – Physical and Virtual Memory

Prerequisites: Kernel memory allocation, kmalloc(), vmalloc(), GFP flags and kernel address spaces.

Objective: Understand physical addresses, virtual addresses, address translation, page tables and their importance in Linux device drivers.

1. Introduction

Computer systems use physical memory and virtual memory to manage data and provide memory protection.

Linux uses a virtual memory system that allows software to work with virtual addresses while the Memory Management Unit (MMU) translates those addresses into physical addresses when memory is accessed.

Device driver developers must understand this distinction because a CPU virtual address is not automatically a physical address or a DMA address.

2. What Is Physical Memory?

Physical memory refers to the actual RAM installed in a computer system.

It stores instructions and data that the processor and other hardware components access during operation.

Characteristics

  • It consists of physical memory locations.
  • It is implemented using RAM hardware.
  • Physical addresses identify locations in the system's physical address space.
  • The MMU and memory subsystem translate and route memory accesses as required.

Example: A system may contain 8 GB of RAM. This RAM provides physical storage for operating-system data, applications, kernel objects and buffers.

3. What Is Virtual Memory?

Virtual memory is an abstraction that gives each process its own virtual address space.

A program normally uses virtual addresses rather than directly specifying physical RAM locations.

Characteristics

  • Processes have separate virtual address spaces.
  • Virtual addresses are translated through page tables.
  • Memory protection prevents unauthorized access between processes.
  • Virtual memory can map pages to physical RAM or other backing mechanisms.
  • Kernel code also uses virtual addressing, with architecture-specific arrangements.
A virtual address is not necessarily equal to a physical address. The mapping must be established and interpreted using the appropriate kernel and architecture interfaces.

4. Virtual Address Space

Each user process operates within its own virtual address space.

A simplified process address-space layout contains regions such as:

  • Text segment – program instructions.
  • Data segment – initialized global and static variables.
  • BSS – uninitialized or zero-initialized global and static variables.
  • Heap – dynamically allocated application memory.
  • Stack – function-call and local-variable storage.
  • Memory-mapped regions – shared libraries, mapped files and other mappings.

This is a conceptual layout. Actual address-space arrangements vary by architecture, process configuration, ASLR and kernel implementation.

5. Virtual Address Space in the Linux Kernel

The Linux kernel has its own virtual address mappings and manages access to physical memory.

Kernel virtual addresses are used by kernel code to access kernel objects, allocated buffers and mapped hardware resources.

On many architectures, kernel virtual addresses occupy a region separate from user-process virtual addresses. The exact layout is architecture-dependent.

Important Distinction

  • User virtual address: Address used by a user-space process.
  • Kernel virtual address: Address used by kernel code.
  • Physical address: Address in the system's physical address space.

A driver must use suitable APIs to transfer data between user space and kernel space. It must not directly dereference an arbitrary user-space pointer as if it were a kernel pointer.

6. Memory Management Unit (MMU)

The Memory Management Unit is hardware that performs address translation and enforces memory-access permissions.

When the CPU accesses a virtual address, the MMU uses translation information maintained by the operating system.

Main Responsibilities

  • Translate virtual addresses to physical addresses.
  • Enforce read, write and execute permissions.
  • Support memory isolation between processes.
  • Generate page faults when mappings or permissions do not permit an access.

7. Page Tables

Page tables contain mappings and permission information used by the MMU to translate virtual addresses.

Linux manages page tables using architecture-specific mechanisms and common kernel memory-management abstractions.

Basic Translation Concept

A virtual address can be divided conceptually into:

  • Virtual page number.
  • Offset within the page.

The page table identifies the corresponding physical page. The offset identifies the byte within that page.

Virtual Address
↓
Virtual Page Number + Page Offset
↓
Page Table Translation
↓
Physical Page Number + Same Offset

Modern systems commonly use multiple levels of page tables. The number of levels and exact format depend on the architecture and configuration.

8. What Is a Memory Page?

A page is a fixed-size unit used by the virtual memory system.

Many Linux systems use a base page size of 4 KB, but page size is architecture- and configuration-dependent.

For a system using 4 KB pages:

Page Size = 4096 bytes

Page Offset Range:
0 to 4095

For example, a virtual address belongs to a virtual page and has an offset within that page. The page-table mapping determines which physical page corresponds to it.

Why Pages Are Important

  • Memory allocation and mapping.
  • Virtual-to-physical address translation.
  • Memory protection.
  • Page reclaim and swapping where supported.
  • DMA mapping and memory-management operations.

9. Physical Contiguity vs Virtual Contiguity

This distinction is particularly important when selecting kernel memory allocation functions.

Physically Contiguous Memory

A range of memory is physically contiguous when its physical addresses are consecutive.

Virtually Contiguous Memory

A range is virtually contiguous when consecutive virtual addresses map to consecutive positions in the virtual address range. The corresponding physical pages do not necessarily need to be adjacent.

Page 12

Consecutive physical pages

Virtually Contiguous

These pages may map to non-adjacent physical pages.

10. kmalloc() and Physical Contiguity

kmalloc() returns a kernel virtual address for a memory allocation whose backing physical memory is contiguous.

Example

#include <linux/slab.h>

char *buffer;

buffer = kmalloc(1024, GFP_KERNEL);

if (!buffer) {
    return -ENOMEM;
}

/* Use the buffer */

kfree(buffer);

The returned pointer is a kernel virtual address. The memory backing the allocation is physically contiguous for the requested range.

This property is useful for some kernel operations, but it does not automatically make the memory suitable for every DMA device.

11. vmalloc() and Virtual Contiguity

vmalloc() allocates memory that is virtually contiguous but does not require the backing physical pages to be contiguous.

Example

#include <linux/vmalloc.h>

char *buffer;

buffer = vmalloc(1024 * 1024);

if (!buffer) {
    return -ENOMEM;
}

/* Use the buffer */

vfree(buffer);

Comparison

Feature kmalloc() vmalloc()
Virtual contiguity Yes Yes
Physical contiguity Yes, for the allocation Not required
Typical use Small and medium kernel allocations Larger virtually contiguous buffers
Release function kfree() vfree()

Both functions return kernel virtual addresses, not raw physical addresses.

12. Physical Address and Virtual Address in Drivers

Device drivers sometimes need to work with hardware resources described using physical addresses.

For example, a peripheral may expose registers at a physical address. A driver generally maps those registers into kernel virtual address space before accessing them.

Conceptual Register Mapping

Physical Hardware Register Address
             |
             v
      ioremap() / Managed Mapping API
             |
             v
      Kernel Virtual Address
             |
             v
       readl() / writel()

Example of the mapping pattern:

#include <linux/io.h>

void __iomem *regs;

regs = ioremap(physical_address, resource_size);

if (!regs)
    return -ENOMEM;

/* Access mapped registers with suitable I/O accessors. */

iounmap(regs);
This is a conceptual pattern. Real drivers should normally obtain resources from the platform, PCI or other device subsystem and use managed resource APIs where appropriate. Do not invent or hardcode hardware addresses for testing.

13. Why Virtual Address Is Not a DMA Address

DMA stands for Direct Memory Access. A DMA-capable device can transfer data between the device and system memory without requiring the CPU to copy every byte.

A device may use a DMA address or I/O virtual address that is different from both the CPU virtual address and the physical address.

CPU Virtual Address
↓
CPU MMU Translation
↓
Physical Address
DMA Address / IOVA
↓
Device DMA Translation Path
↓
System Memory

The DMA address may be translated by an IOMMU or handled by architecture-specific DMA mechanisms.

Never assume that a CPU virtual address can be passed directly to a DMA device. Use the Linux DMA API, such as dma_map_single() or dma_alloc_coherent(), according to the device's requirements.

14. Kernel Functions Related to Address Translation

Linux provides interfaces for working with memory addresses. Their availability and correct use depend on the architecture and the type of memory.

Function / Interface Purpose
virt_to_phys() Converts certain kernel virtual addresses to physical addresses. It is not valid for arbitrary pointers.
phys_to_virt() Converts certain physical addresses into kernel virtual addresses on architectures that support the relevant direct mapping.
ioremap() Maps an I/O physical resource into kernel virtual address space.
iounmap() Releases an I/O mapping created with ioremap().
page_to_pfn() Obtains the page-frame number associated with a struct page.
pfn_to_page() Obtains a struct page for a valid page-frame number on supported configurations.
Do not use virt_to_phys() as a generic way to obtain DMA addresses. The DMA API handles device-specific addressing, mapping and cache-coherency requirements.

15. Page Faults

A page fault occurs when the CPU attempts to access a virtual address that requires page-table handling or violates the permitted memory-access rules.

Page faults are not always errors. Some are normal parts of virtual memory operation.

Examples

  • A process accesses a valid page that has not yet been mapped into physical memory.
  • A copy-on-write page is written and requires a private writable page.
  • A process attempts to access an unmapped or protected address.

Page Fault Handling

CPU Memory Access
↓
Page Fault
↓
Kernel Fault Handler
↓
Resolve Mapping or Report Error

If the fault can be resolved, execution may continue. If the access is invalid or cannot be resolved, the kernel may report an error or terminate the affected process. A fault caused by invalid kernel access can result in a kernel oops or panic.

16. Practical Demonstration: Allocation Types

The following module demonstrates that kernel allocations return virtual pointers. It does not attempt to translate arbitrary pointers into physical or DMA addresses.

Create memory_types_demo.c:

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/slab.h>
#include <linux/vmalloc.h>

static char *small_buffer;
static char *large_buffer;

static int __init memory_demo_init(void)
{
    small_buffer = kmalloc(256, GFP_KERNEL);

    if (!small_buffer)
        return -ENOMEM;

    large_buffer = vmalloc(1024 * 1024);

    if (!large_buffer) {
        kfree(small_buffer);
        small_buffer = NULL;
        return -ENOMEM;
    }

    snprintf(small_buffer, 256,
             "kmalloc virtual buffer");

    snprintf(large_buffer, 128,
             "vmalloc virtual buffer");

    pr_info("%s\n", small_buffer);
    pr_info("%s\n", large_buffer);

    return 0;
}

static void __exit memory_demo_exit(void)
{
    vfree(large_buffer);
    kfree(small_buffer);

    large_buffer = NULL;
    small_buffer = NULL;

    pr_info("Memory allocations released\n");
}

module_init(memory_demo_init);
module_exit(memory_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Physical and virtual memory allocation demo");

What This Demonstrates

  1. kmalloc() allocates physically contiguous backing memory.
  2. vmalloc() provides a virtually contiguous allocation.
  3. Both returned pointers are kernel virtual addresses.
  4. kfree() releases the kmalloc allocation.
  5. vfree() releases the vmalloc allocation.

obj-m += memory_types_demo.o

19. Common Mistakes

Mistake Why It Is Incorrect Correct Practice
Assuming virtual and physical addresses are identical They represent different address spaces. Use appropriate kernel address-management APIs.
Passing a kernel virtual pointer directly to a DMA device The device requires a DMA address. Use the Linux DMA API.
Using virt_to_phys() on arbitrary memory Not every virtual address has the required direct mapping. Use it only for supported address types and situations.
Using kmalloc() and releasing with vfree() Allocation and release functions do not match. Use kfree() for kmalloc() allocations.
Using vmalloc() and releasing with kfree() Incorrect allocator pairing. Use vfree() for vmalloc() allocations.
Accessing hardware registers as ordinary RAM Device I/O mappings require appropriate accessors and mapping rules. Use ioremap() or managed mappings and I/O accessors.

20. Lesson Summary

  • Physical memory represents the system's physical RAM address space.
  • Virtual memory provides address-space abstraction and memory protection.
  • The MMU performs address translation using page tables.
  • Memory is commonly managed in page-sized units.
  • kmalloc() provides a virtually and physically contiguous allocation for the requested range.
  • vmalloc() provides virtual contiguity without requiring physical contiguity.
  • Kernel virtual addresses, physical addresses and DMA addresses are different concepts.
  • Device drivers should use the DMA API for DMA operations.
  • Hardware registers should be mapped and accessed using appropriate I/O interfaces.
