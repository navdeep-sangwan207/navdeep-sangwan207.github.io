Chapter: Kernel Memory Management

Lesson: 7 – Kernel Stack and Heap

Prerequisites: kmalloc(), kfree(), vmalloc(), GFP flags, process context and kernel modules.

Objective: Understand kernel stacks, dynamically allocated kernel memory, their differences and safe memory usage in device drivers.

1. Introduction

Linux kernel code requires memory for function execution, local variables, function arguments, data structures and dynamically allocated objects.

Two important memory concepts are:

  • Kernel Stack: Memory used for function-call frames and temporary execution data.
  • Kernel Heap: A general term for dynamically allocated kernel memory managed through kernel allocators.

Understanding these areas is important because device drivers frequently use both local variables and dynamically allocated buffers.

2. What Is a Kernel Stack?

A kernel stack is a region of memory used while kernel code executes.

When a kernel function is called, the CPU and compiler-generated code use stack space for items such as:

  • Function-call information.
  • Local variables that are placed on the stack.
  • Saved register values, as required by the calling convention.
  • Temporary execution data.

Example

static void calculate_value(void)
{
    int a = 10;
    int b = 20;
    int result;

    result = a + b;

    pr_info("Result = %d\n", result);
}

In this example, the local variables may be stored on the stack, depending on compiler optimization and register allocation.

A C local variable is not guaranteed to occupy stack memory. The compiler may keep it in a register or optimize it away.

3. Kernel Stack Organization

Linux maintains kernel execution stacks for tasks. A task may enter kernel mode while executing a system call, handling an exception or performing other kernel operations.

The kernel stack is limited in size. Its size depends on architecture and kernel configuration.

Each nested function call may require additional stack space. Excessive recursion or large local arrays can therefore cause stack exhaustion.

Important Characteristics

  • Stack space is limited.
  • Function calls can increase stack usage.
  • Stack memory is automatically managed as functions enter and return.
  • Kernel code must avoid excessive stack consumption.

4. What Is the Kernel Heap?

The term kernel heap is commonly used to describe dynamically allocated memory available to kernel code.

Unlike ordinary function-local stack variables, dynamically allocated objects can remain allocated after the function that requested them returns.

Kernel memory allocation interfaces include:

Function Purpose Release Function
kmalloc() Allocates physically contiguous memory. kfree()
kzalloc() Allocates zero-initialized memory. kfree()
kcalloc() Allocates a zero-initialized array. kfree()
vmalloc() Allocates virtually contiguous memory. vfree()

These functions are kernel allocation interfaces. They use different allocator mechanisms and are not simply interchangeable versions of a single heap operation.

6. Stack Allocation Example

Consider a small local array inside a function:

static void process_data(void)
{
    int values[10] = {0};

    values[0] = 100;

    pr_info("Value = %d\n", values[0]);
}

The array is a local automatic variable. It may occupy stack space, although compiler optimization can affect its actual storage.

When the function returns, its local variable lifetime ends.

Avoid large local arrays and large local structures in kernel functions. Kernel stack space is much more constrained than typical application-process stack space.

7. Dynamic Allocation Example

When a driver needs a buffer that should remain available beyond a single function call, dynamic allocation may be appropriate.

#include <linux/slab.h>
#include <linux/errno.h>

static int allocate_buffer(void)
{
    char *buffer;

    buffer = kmalloc(1024, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    /* Use the allocated memory here. */

    kfree(buffer);

    return 0;
}

The allocation is explicitly released using kfree().

If the pointer must remain available after the function returns, it must be stored in an appropriately managed longer-lived object, such as driver state.

8. Why Large Local Variables Are Dangerous

Consider this example:

static void unsafe_function(void)
{
    char buffer[8192];

    /* Process data */
}

An 8 KB local array can consume a substantial portion of a task's kernel stack.

Depending on the architecture and configuration, this may cause stack exhaustion or leave too little stack space for nested function calls and interrupt-related execution.

Better Approach

static int safer_function(void)
{
    char *buffer;

    buffer = kmalloc(8192, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    /* Process data */

    kfree(buffer);

    return 0;
}

This example assumes the function executes in a sleepable context. The allocation must be checked and released on every relevant exit path.

9. Kernel Stack and Interrupt Handling

Interrupt handling requires special attention to stack usage.

Hard interrupt handlers execute in atomic context and must not sleep. Their stack usage must also remain controlled.

On many architectures, interrupt handling uses architecture-specific stack arrangements. Some systems use separate interrupt stacks; others have different implementation details.

  • Do not allocate large local arrays in interrupt handlers.
  • Do not call sleeping allocation paths from hard interrupt context.
  • Keep interrupt handlers short.
  • Defer lengthy processing to an appropriate workqueue or threaded interrupt handler.
  • Use preallocated buffers when interrupt-time data storage is required.

10. Stack Overflow in the Linux Kernel

Stack overflow occurs when kernel execution consumes more stack space than is available.

Common Causes

  • Deep or uncontrolled recursion.
  • Large local arrays.
  • Large local structures.
  • Excessive nested function calls.
  • Complex call chains in interrupt or exception handling.

Possible Consequences

  • Corruption of nearby memory.
  • Kernel warnings or stack-corruption reports.
  • Kernel oops or panic in severe cases.
  • Unpredictable system behavior.
Never deliberately create a kernel stack overflow on your normal Ubuntu installation. Study stack limits and diagnostics using safe code review and controlled virtual-machine experiments.

11. Memory Lifetime and Ownership

Dynamic kernel memory must have a clear owner responsible for releasing it.

A common driver design is:

struct my_device {
    char *buffer;
};

static int my_device_init(struct my_device *dev)
{
    dev->buffer = kzalloc(1024, GFP_KERNEL);

    if (!dev->buffer)
        return -ENOMEM;

    return 0;
}

static void my_device_cleanup(struct my_device *dev)
{
    kfree(dev->buffer);
    dev->buffer = NULL;
}

The driver state structure stores the pointer, allowing the buffer to remain available after the initialization function returns.

In a real driver, cleanup must be performed on every failure path after successful allocation, as well as during normal device removal.

12. Kernel Stack vs User-Space Stack

Linux applications and Linux kernel code use different execution environments.

Feature User-Space Stack Kernel Stack
Used by Application threads Kernel execution for tasks
Management Runtime and operating system Kernel and architecture-specific mechanisms
Size Usually configurable and comparatively large Relatively small and architecture-dependent
Typical allocation Local variables and function-call data Kernel function-call data and local variables
Failure impact Usually affects the application process Can affect kernel stability

13. Practical Kernel Module Example

Create a file named stack_heap_demo.c.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/slab.h>

#define BUFFER_SIZE 512

static char *heap_buffer;

static int __init stack_heap_demo_init(void)
{
    int local_value = 100;

    heap_buffer = kmalloc(BUFFER_SIZE, GFP_KERNEL);

    if (!heap_buffer) {
        pr_err("Heap allocation failed\n");
        return -ENOMEM;
    }

    snprintf(heap_buffer, BUFFER_SIZE,
             "Dynamic kernel memory example");

    pr_info("Local value = %d\n", local_value);
    pr_info("Allocated buffer = %s\n", heap_buffer);

    return 0;
}

static void __exit stack_heap_demo_exit(void)
{
    kfree(heap_buffer);
    heap_buffer = NULL;

    pr_info("Dynamic memory released\n");
}

module_init(stack_heap_demo_init);
module_exit(stack_heap_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Kernel stack and heap demonstration");

Explanation

  1. local_value is an automatic local variable and may be stored on the kernel stack.
  2. heap_buffer is a pointer to dynamically allocated kernel memory.
  3. kmalloc() allocates the buffer.
  4. snprintf() writes a bounded string into the allocated buffer.
  5. kfree() releases the allocated memory during module cleanup.

14. Makefile

obj-m += stack_heap_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Save the Makefile in the same directory as stack_heap_demo.c.

16. Common Mistakes and Best Practices

Mistake Problem Best Practice
Declaring very large local arrays Excessive stack consumption Use appropriate dynamic allocation.
Forgetting kfree() Memory leak Define clear ownership and cleanup paths.
Using a pointer after kfree() Use-after-free bug Stop accessing released memory; clear owned pointers where appropriate.
Returning a pointer to a local variable The local object's lifetime ends when the function returns. Use a valid longer-lived object or dynamic allocation.
Uncontrolled recursion Can exhaust the kernel stack. Use bounded call depth and iterative approaches where appropriate.
Sleeping allocation in interrupt context Invalid execution-context behavior Preallocate memory or defer work.

17. Lesson Summary

  • The kernel stack supports function execution and temporary local data.
  • Kernel stack space is limited and architecture-dependent.
  • Large local variables and deep recursion can cause stack exhaustion.
  • Dynamic kernel memory is obtained through allocation APIs such as kmalloc() and vmalloc().
  • Dynamic allocations require explicit lifetime and cleanup management.
  • Interrupt handlers must avoid sleeping and excessive stack usage.
  • Driver developers must understand memory ownership and prevent leaks and use-after-free errors.
