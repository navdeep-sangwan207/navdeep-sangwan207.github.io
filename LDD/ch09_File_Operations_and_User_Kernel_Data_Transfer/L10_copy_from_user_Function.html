2. Introduction to copy_from_user()

Linux device drivers frequently receive data from user-space applications. For example, an application may send a configuration value, command, or message to a character device.

The driver must transfer that data into kernel memory before processing it.

copy_from_user() is a Linux kernel function that copies data from a user-space memory region into a kernel-space memory region.

Header File

#include <linux/uaccess.h>

Function Prototype

unsigned long copy_from_user(
    void *to,
    const void __user *from,
    unsigned long n
);

Parameters

ParameterDescription
toDestination address in kernel memory.
fromSource address in user memory.
nNumber of bytes requested to be copied.

3. Direction of Data Transfer

The function name describes the source: data is copied from user space.

User-to-Kernel Data Transfer

User Buffer
copy_from_user()
Kernel Buffer

Direction: User Space → Kernel Space

Example

char kernel_buffer[100];
char __user *user_buffer;

/* Copy 100 bytes from user space */
copy_from_user(
    kernel_buffer,
    user_buffer,
    100
);

The user buffer is the source, and the kernel buffer is the destination.

4. Return Value of copy_from_user()

The return value is the number of bytes that were not copied.

Return ValueMeaning
0All requested bytes were copied successfully.
NonzeroSome bytes were not copied.

Example

unsigned long not_copied;

not_copied = copy_from_user(
    kernel_buffer,
    user_buffer,
    100
);

if (not_copied == 0) {
    pr_info("Data copied successfully\n");
} else {
    pr_err("Some data could not be copied\n");
}
copy_from_user() does not return a negative error code. It returns the number of bytes not copied. A driver commonly returns -EFAULT when the requested transfer cannot be completed and no bytes can be reported as accepted.

5. Why Is copy_from_user() Required?

User-space memory is not ordinary kernel memory. A driver must not directly dereference an arbitrary user-space pointer.

Incorrect Approach

memcpy(kernel_buffer,
       user_buffer,
       count);

This is not the correct way to access an arbitrary user-space pointer.

Correct Approach

if (copy_from_user(
        kernel_buffer,
        user_buffer,
        count)) {
    return -EFAULT;
}

The kernel user-access API handles the special requirements of transferring data across the user/kernel boundary.

6. Using copy_from_user() in a write() Callback

A character driver's write() callback receives a pointer to user-space data. The driver commonly uses copy_from_user() to move that data into a kernel buffer.

Write Callback Prototype

ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
);

Basic Example

#include <linux/uaccess.h>
#include <linux/fs.h>
#include <linux/errno.h>

#define BUFFER_SIZE 1024

static char kernel_buffer[BUFFER_SIZE];
static size_t data_size;

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position)
{
    size_t bytes_to_copy;
    unsigned long not_copied;

    if (*position < 0)
        return -EINVAL;

    if (*position >= BUFFER_SIZE)
        return -ENOSPC;

    bytes_to_copy = min(
        count,
        BUFFER_SIZE - (size_t)*position
    );

    not_copied = copy_from_user(
        kernel_buffer + *position,
        buffer,
        bytes_to_copy
    );

    if (not_copied == bytes_to_copy)
        return -EFAULT;

    bytes_to_copy -= not_copied;

    *position += bytes_to_copy;

    if ((size_t)*position > data_size)
        data_size = (size_t)*position;

    return bytes_to_copy;
}

Explanation

  1. Validate the current file position.
  2. Check that the position is within the kernel buffer.
  3. Calculate the maximum number of bytes that can be stored.
  4. Use copy_from_user() to copy the data into kernel memory.
  5. Calculate the number of bytes successfully copied.
  6. Update the file position.
  7. Update the amount of valid data stored in the buffer.
  8. Return the number of bytes accepted.
This is a simple educational example. It uses a global buffer without synchronization. A driver that permits concurrent access must protect shared state, for example with a mutex, and carefully define its write and overwrite semantics.

7. Handling Partial Copy

A copy operation may not be able to access every requested byte. The driver must account for the bytes that were successfully transferred.

Example

Requested bytes = 100

Bytes successfully copied = 80

Bytes not copied = 20

Calculate the successful transfer:

copied = requested - not_copied;

Robust Return-Value Pattern

unsigned long not_copied;
size_t copied;

not_copied = copy_from_user(
    kernel_buffer,
    user_buffer,
    bytes_to_copy
);

copied = bytes_to_copy - not_copied;

if (copied == 0)
    return -EFAULT;

return copied;

This pattern reports partial progress when some bytes were copied. The driver must also update its file position and buffer length using the actual copied count.

For a write callback, returning a positive byte count means the driver accepted that amount of data. User-space applications should handle partial writes and retry the remaining data when appropriate.

8. Using copy_from_user() in IOCTL

IOCTL operations may receive configuration structures or command parameters from an application.

For example, an application may send a new device configuration to the driver.

Shared Header: my_ioctl.h

#ifndef MY_IOCTL_H
#define MY_IOCTL_H

#include <linux/ioctl.h>

#define MY_MAGIC 'N'

struct device_config {
    int mode;
    int speed;
};

#define MY_IOCTL_SET_CONFIG \
    _IOW(MY_MAGIC, 1, struct device_config)

#endif

Kernel-Space Callback Example

#include <linux/uaccess.h>
#include <linux/fs.h>
#include "my_ioctl.h"

static struct device_config current_config;

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg)
{
    struct device_config config;

    switch (cmd) {

    case MY_IOCTL_SET_CONFIG:

        if (copy_from_user(
                &config,
                (struct device_config __user *)arg,
                sizeof(config))) {
            return -EFAULT;
        }

        /* Validate application-supplied values */
        if (config.mode < 0 || config.mode > 3)
            return -EINVAL;

        if (config.speed < 1 || config.speed > 1000)
            return -EINVAL;

        current_config = config;

        break;

    default:
        return -ENOTTY;
    }

    return 0;
}

The driver copies the user-supplied structure into a kernel-space variable before validating and using its fields.

Never assume that data received from an application is valid merely because copy_from_user() succeeded. Validate ranges, lengths, enumerations and other application-specific rules before using the data.

9. User-Space Application Example

The following example sends a message to a character device.

File: test_write.c

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

int main(void)
{
    int fd;
    const char message[] = "Hello Linux Driver";

    fd = open("/dev/mychardev", O_WRONLY);

    if (fd < 0) {
        perror("open");
        return 1;
    }

    ssize_t written = write(
        fd,
        message,
        strlen(message)
    );

    if (written < 0) {
        perror("write");
        close(fd);
        return 1;
    }

    printf("Bytes written: %zd\n", written);

    close(fd);

    return 0;
}

Compile

gcc test_write.c -o test_write

Execute

sudo ./test_write

The application sends data to the device. The driver's write callback receives the data and uses copy_from_user() to place it into kernel memory.

10. Complete Simple Character Driver Example

This example demonstrates a memory-backed character device with both read and write operations. It uses copy_from_user() for writes and copy_to_user() for reads.

File: user_transfer_driver.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/init.h>
#include <linux/uaccess.h>
#include <linux/mutex.h>
#include <linux/errno.h>

#define DEVICE_NAME "mychardev"
#define BUFFER_SIZE 1024

static dev_t dev_num;
static struct cdev my_cdev;

static char device_buffer[BUFFER_SIZE];
static size_t data_size;

static DEFINE_MUTEX(buffer_mutex);

static int my_open(
    struct inode *inode,
    struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

static ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position)
{
    size_t bytes_to_copy;
    unsigned long not_copied;
    ssize_t result;

    if (*position < 0)
        return -EINVAL;

    if (mutex_lock_interruptible(&buffer_mutex))
        return -ERESTARTSYS;

    if (*position >= data_size) {
        result = 0;
        goto out;
    }

    bytes_to_copy = min(
        count,
        data_size - (size_t)*position
    );

    not_copied = copy_to_user(
        buffer,
        device_buffer + *position,
        bytes_to_copy
    );

    bytes_to_copy -= not_copied;

    if (bytes_to_copy == 0) {
        result = -EFAULT;
        goto out;
    }

    *position += bytes_to_copy;
    result = bytes_to_copy;

out:
    mutex_unlock(&buffer_mutex);
    return result;
}

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position)
{
    size_t bytes_to_copy;
    unsigned long not_copied;
    ssize_t result;

    if (*position < 0)
        return -EINVAL;

    if (mutex_lock_interruptible(&buffer_mutex))
        return -ERESTARTSYS;

    if (*position >= BUFFER_SIZE) {
        result = -ENOSPC;
        goto out;
    }

    bytes_to_copy = min(
        count,
        BUFFER_SIZE - (size_t)*position
    );

    not_copied = copy_from_user(
        device_buffer + *position,
        buffer,
        bytes_to_copy
    );

    bytes_to_copy -= not_copied;

    if (bytes_to_copy == 0) {
        result = -EFAULT;
        goto out;
    }

    *position += bytes_to_copy;

    if ((size_t)*position > data_size)
        data_size = (size_t)*position;

    result = bytes_to_copy;

out:
    mutex_unlock(&buffer_mutex);
    return result;
}

static int my_release(
    struct inode *inode,
    struct file *file)
{
    pr_info("Device closed\n");
    return 0;
}

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

static int __init my_driver_init(void)
{
    int ret;

    ret = alloc_chrdev_region(
        &dev_num, 0, 1, DEVICE_NAME
    );

    if (ret < 0) {
        pr_err("Device number allocation failed\n");
        return ret;
    }

    cdev_init(&my_cdev, &my_fops);
    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev_num, 1);

    if (ret < 0) {
        unregister_chrdev_region(dev_num, 1);
        return ret;
    }

    pr_info("Device registered: major=%d minor=%d\n",
            MAJOR(dev_num), MINOR(dev_num));

    return 0;
}

static void __exit my_driver_exit(void)
{
    cdev_del(&my_cdev);
    unregister_chrdev_region(dev_num, 1);

    pr_info("Device driver removed\n");
}

module_init(my_driver_init);
module_exit(my_driver_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Character Driver User-Kernel Data Transfer");

Important Design Notes

  • The mutex protects the shared kernel buffer and its data-size metadata.
  • The example uses one shared buffer for all open instances.
  • The mutex is held during user-memory copying. This is permitted because mutexes can be held in sleepable process context, but it can increase contention.
  • The example demonstrates partial-copy accounting for both read and write.
  • Production drivers may need per-open buffers, more detailed error handling and a carefully defined concurrency policy.

13. Common Errors and Solutions

ProblemSolution
Using memcpy() with a user pointerUse copy_from_user().
Wrong argument orderFirst argument is kernel destination; second is user source.
Ignoring the return valueCheck the number of bytes not copied.
Returning requested count after partial copyReturn the number of bytes actually accepted.
Writing beyond kernel bufferLimit the copy length to available buffer capacity.
Using unvalidated application dataValidate all values and lengths after copying.
Calling from interrupt contextDo not call copy_from_user() in contexts where sleeping is forbidden.
Incorrect file position updateUpdate position using the successfully copied byte count.

14. Important Technical Considerations

  • copy_from_user() may fault and sleep while accessing user memory.
  • Do not call it from hard interrupt context or other atomic contexts where sleeping is forbidden.
  • Use a valid kernel destination buffer with sufficient capacity.
  • Always check the return value.
  • Validate application-supplied data before using it.
  • Protect shared kernel buffers against concurrent access.
  • Do not hold a spinlock while calling copy_from_user().
  • Use appropriate synchronization such as a mutex when the callback runs in sleepable process context.
  • Do not assume the application supplied a valid pointer or trustworthy data.
A successful copy only means that the requested bytes were transferred. It does not mean that the copied data is logically valid, safe for a device, or suitable for the driver's operation.

15. copy_from_user() vs copy_to_user()

Featurecopy_from_user()copy_to_user()
DirectionUser to KernelKernel to User
DestinationKernel memoryUser memory
SourceUser memoryKernel memory
Typical callbackwrite()read()
IOCTL useReceive configurationReturn device status
Return valueBytes not copiedBytes not copied

Both functions return the number of bytes that were not copied. Neither function returns a negative errno directly.

16. Lesson Summary

  • copy_from_user() transfers data from user space into kernel space.
  • It is declared in linux/uaccess.h.
  • The first parameter is the kernel destination.
  • The second parameter is the user-space source.
  • The third parameter specifies the requested byte count.
  • Its return value represents the number of bytes not copied.
  • It is commonly used in write() callbacks and IOCTL operations.
  • Partial-copy handling is important.
  • Validate all data received from applications.
  • Never call it in interrupt context or another context where sleeping is forbidden.
