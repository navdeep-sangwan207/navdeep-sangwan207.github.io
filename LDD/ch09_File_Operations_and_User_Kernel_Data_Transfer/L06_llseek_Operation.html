2. Introduction to File Position

When a process reads or writes a file, Linux maintains a position that indicates where the next read or write operation should occur.

This position is commonly called the file offset or file position.

For example, consider a device containing the following data:

LINUX DEVICE DRIVER

If a process reads the first five bytes, the file position normally advances by five bytes.

Initial file position = 0

Read 5 bytes:
LINUX

New file position = 5

The next sequential read begins at the updated position.

File Position Movement

Position 0
→
Read 5 bytes
→
Position 5

The file offset identifies the location of the next sequential I/O operation.

3. What Is lseek()?

lseek() is a user-space system call used to change the current file offset of an open file descriptor.

It allows an application to move the file position without necessarily reading or writing data.

Header File

#include <unistd.h>

Function Prototype

off_t lseek(int fd, off_t offset, int whence);

Parameters

Parameter Description
fd File descriptor returned by open().
offset Number of bytes by which the position is moved relative to the selected reference point.
whence Reference point used to calculate the new position.

Return Value

  • On success, returns the new file offset.
  • On failure, returns (off_t)-1 and sets errno.

4. Types of File Seeking

The third argument of lseek() determines how the new file position is calculated.

4.1 SEEK_SET

Moves the file position relative to the beginning of the file or device.

lseek(fd, 10, SEEK_SET);

The new file position becomes byte offset 10.

Beginning
──────────────→
Offset 10

Reference point: beginning of file.

4.2 SEEK_CUR

Moves the file position relative to the current position.

lseek(fd, 5, SEEK_CUR);

If the current position is 10, the new position becomes 15.

Current position = 10
Offset           = +5
New position     = 15

A negative offset can move the position backwards, provided the resulting position is valid.

4.3 SEEK_END

Moves the file position relative to the end of the file or the logical end defined by the device driver.

lseek(fd, 0, SEEK_END);

This moves the position to the end.

lseek(fd, -5, SEEK_END);

This requests a position five bytes before the end.

Beginning
──────────────→
End

SEEK_END uses the logical end position as its reference.

Comparison

Constant Reference Point Example
SEEK_SET Beginning lseek(fd, 10, SEEK_SET)
SEEK_CUR Current position lseek(fd, 5, SEEK_CUR)
SEEK_END End of file/device data lseek(fd, 0, SEEK_END)

5. What Is the llseek() Operation in a Device Driver?

Linux device drivers can provide a callback for handling file-position changes.

This callback is called .llseek and is a member of the struct file_operations structure.

When an application calls lseek() on a file descriptor, the VFS performs the seek operation using the file's seek semantics and the registered operation, when applicable.

Callback Prototype

loff_t (*llseek)(
    struct file *file,
    loff_t offset,
    int whence
);

Parameters

Parameter Description
file Pointer to the open file structure.
offset Requested offset relative to the selected reference point.
whence Seeking mode: SEEK_SET, SEEK_CUR or SEEK_END.

Return Value

  • Returns the new file position on success.
  • Returns a negative error code on failure.
Important: The kernel uses loff_t for file offsets. Do not confuse it with the user-space off_t type used by lseek().

6. Relationship Between lseek() and .llseek

The application calls lseek() from user space. The Linux Virtual File System (VFS) handles the request and applies the seek behavior associated with the opened file.

User Application
↓
lseek(fd, offset, whence)
↓
System Call / VFS
↓
File Seeking Operation
↓
Driver .llseek Callback
↓
Updated file->f_pos

The callback is responsible for implementing the device's seeking semantics when a custom operation is needed.

A driver can also use an appropriate kernel helper or provide nonseekable semantics instead of implementing a custom callback.

7. File Position in struct file

The kernel maintains the current file position in the f_pos member of struct file.

struct file {
    ...
    loff_t f_pos;
    ...
};

This is a simplified illustration of the relevant member, not the complete kernel structure.

Relationship with Read and Write

Read and write callbacks commonly receive a pointer to the current position:

ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
);

The position pointer normally refers to the file's current offset. Updating it changes the position used by subsequent sequential I/O.

Remember: The .llseek operation changes the file position, while read() and write() use that position to determine where sequential data transfer occurs.

8. Shared File Offset and Duplicated File Descriptors

The file offset belongs to the open-file description, represented in the kernel by a struct file object.

When a process duplicates a file descriptor using dup(), the new descriptor refers to the same open-file description.

int fd1 = open("/dev/mychardev", O_RDWR);
int fd2 = dup(fd1);

Both descriptors share the same file offset.

Example

lseek(fd1, 10, SEEK_SET);

/* fd2 observes the same open-file offset. */

read(fd2, buffer, 5);

/* Shared offset advances to 15. */

Similarly, descriptors inherited through fork() normally refer to the same open-file description.

By contrast, a separate open() normally creates a new open-file description with an independent file offset.

Do not assume that two descriptors always have independent offsets. The result depends on whether they refer to the same open-file description.

9. Implementing a Custom llseek() Callback

Consider a memory-backed character device with a fixed buffer size of 1024 bytes.

The driver will permit file positions from 0 through 1024. Seeking beyond this range or before position zero will be rejected.

Step 1: Define the Buffer Size

#define BUFFER_SIZE 1024

Step 2: Include Required Headers

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/overflow.h>
#include <linux/errno.h>

Step 3: Implement the Callback

static loff_t my_llseek(
    struct file *file,
    loff_t offset,
    int whence)
{
    loff_t base;
    loff_t new_pos;

    switch (whence) {

    case SEEK_SET:
        base = 0;
        break;

    case SEEK_CUR:
        base = file->f_pos;
        break;

    case SEEK_END:
        base = BUFFER_SIZE;
        break;

    default:
        return -EINVAL;
    }

    /* Check for signed arithmetic overflow. */
    if (check_add_overflow(base, offset, &new_pos))
        return -EINVAL;

    /* Validate the requested position. */
    if (new_pos < 0 || new_pos > BUFFER_SIZE)
        return -EINVAL;

    /* Update and return the file position. */
    return file->f_pos = new_pos;
}

Explanation

Code Purpose
SEEK_SET Uses zero as the reference point.
SEEK_CUR Uses the current file position.
SEEK_END Uses BUFFER_SIZE as the reference point.
check_add_overflow() Detects signed addition overflow.
new_pos < 0 Prevents a negative file position.
new_pos > BUFFER_SIZE Prevents seeking beyond the device's defined capacity.
file->f_pos = new_pos Updates the current file position.
Kernel API note: This example uses check_add_overflow() from <linux/overflow.h>. Confirm helper availability for the target kernel headers. For more complex drivers, consider the appropriate VFS position helper, such as vfs_setpos(), where available.

The example treats the device's capacity as its logical end. A device that stores variable-length data may instead use its current data length for SEEK_END.

10. Registering the llseek Callback

The custom callback must be registered in the driver's file_operations structure.

static const struct file_operations my_fops = {
    .owner  = THIS_MODULE,
    .open   = my_open,
    .read   = my_read,
    .write  = my_write,
    .llseek = my_llseek,
    .release = my_release,
};

When the device file is opened and an application requests a seek operation, the VFS can use the registered seeking behavior.

Important: The .llseek member is optional. A driver should provide seeking only when it makes sense for that device's data model.

11. Seekable and Nonseekable Devices

Not every Linux device supports random access.

Device/File Type Typical Seeking Behavior Reason
Regular disk file Seekable Data can be accessed at different file offsets.
Memory-backed character device Can be seekable Driver can manage positions in a memory buffer.
Terminal Generally nonseekable Represents a character stream.
Pipe Nonseekable Data is consumed as a stream.
Socket Nonseekable Communication is stream or message oriented.
Hardware sensor stream Depends on driver design May provide sequential readings rather than random access.

Handling Nonseekable Devices

Linux provides helpers for appropriate nonseekable file semantics. Depending on the kernel version and driver design, examples include:

nonseekable_open(inode, file);

This helper is commonly used in an open callback to mark a file as nonseekable.

Other interfaces, such as stream_open(), are available for suitable stream-oriented drivers on supported kernel versions.

A driver may also use an appropriate nonseekable llseek helper where supported by its target kernel API.

Do not register a custom seeking callback for a hardware stream unless the device actually supports meaningful random-access semantics.

12. Kernel Helpers Related to File Seeking

Helper / Operation Purpose
default_llseek() Provides generic seeking behavior for suitable seekable files.
vfs_setpos() Validates and updates a file position with an upper bound, where available.
nonseekable_open() Marks an opened file as nonseekable in suitable driver designs.
stream_open() Sets up stream-oriented file semantics on supported kernels.
fixed_size_llseek() Provides bounded seeking for suitable fixed-size files on kernels that provide it.
generic_file_llseek() Generic seeking helper associated with regular-file/page-cache contexts; not automatically suitable for a simple character driver.

Kernel APIs and helper availability can vary between kernel releases. Always inspect the headers and documentation for the kernel version targeted by the driver.

13. User-Space Program to Test lseek()

The following program opens a character device and performs different seeking operations.

Source Code: test_seek.c

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <errno.h>

int main(void)
{
    int fd;
    off_t position;
    char buffer[6] = {0};

    fd = open("/dev/mychardev", O_RDWR);

    if (fd < 0) {
        perror("open");
        return 1;
    }

    position = lseek(fd, 0, SEEK_SET);

    if (position == (off_t)-1) {
        perror("lseek SEEK_SET");
        close(fd);
        return 1;
    }

    printf("SEEK_SET position: %lld\n",
           (long long)position);

    position = lseek(fd, 5, SEEK_CUR);

    if (position == (off_t)-1) {
        perror("lseek SEEK_CUR");
        close(fd);
        return 1;
    }

    printf("SEEK_CUR position: %lld\n",
           (long long)position);

    position = lseek(fd, 0, SEEK_END);

    if (position == (off_t)-1) {
        perror("lseek SEEK_END");
        close(fd);
        return 1;
    }

    printf("SEEK_END position: %lld\n",
           (long long)position);

    position = lseek(fd, 0, SEEK_SET);

    if (position == (off_t)-1) {
        perror("lseek reset");
        close(fd);
        return 1;
    }

    ssize_t bytes = read(fd, buffer, 5);

    if (bytes < 0) {
        perror("read");
        close(fd);
        return 1;
    }

    printf("Bytes read: %zd\n", bytes);
    printf("Data: %.*s\n", (int)bytes, buffer);

    close(fd);

    return 0;
}

Compile the Program

gcc test_seek.c -o test_seek

Run the Program

sudo ./test_seek

Make sure that:

  • The character driver is loaded.
  • The device node /dev/mychardev exists.
  • The device driver's file_operations structure registers a suitable .llseek callback.
  • The driver implements compatible read and write operations.
The exact output depends on the logical data length and implementation of the character driver. The test program demonstrates file-position changes; it does not assume that every device supports seeking.

14. lseek() vs pread() and pwrite()

Linux also provides positional I/O system calls.

pread(fd, buffer, count, offset);
pwrite(fd, buffer, count, offset);

These operations transfer data at an explicitly supplied offset without changing the shared file offset in the same way as sequential read() and write().

Operation Purpose Changes Shared File Offset?
lseek() Changes current file position. Yes
read() Reads from current file position. Normally yes
write() Writes at current file position, subject to file semantics. Normally yes
pread() Reads from a specified offset. No
pwrite() Writes at a specified offset. No

Positional I/O is useful when multiple operations need independent offsets without repeatedly changing a shared file position.

15. Common Errors in llseek()

Error Possible Cause
EINVAL Invalid whence value or position outside the permitted range.
ESPIPE Seeking on a nonseekable file or stream.
Arithmetic overflow Invalid offset calculation without overflow checking.
Incorrect SEEK_END behavior Using buffer capacity when the device's logical data length should define the end, or vice versa.
Unexpected shared offset Multiple descriptors refer to the same open-file description.

16. Important Practical Considerations

  • Use loff_t for kernel file offsets.
  • Validate every requested position.
  • Protect calculations against integer overflow.
  • Define whether SEEK_END uses device capacity or current data length.
  • Do not assume every character device supports seeking.
  • Keep read(), write() and llseek() semantics consistent.
  • Remember that duplicated file descriptors share an open-file description and its offset.
  • For concurrent operations, consider the file-position and data-synchronization semantics of the driver.
  • Check the target kernel version before using optional seeking helpers.

17. Lesson Summary

  • File offset identifies the position for sequential file I/O.
  • lseek() is a user-space system call used to change the file position.
  • SEEK_SET references the beginning.
  • SEEK_CUR references the current position.
  • SEEK_END references the logical end.
  • The kernel stores the current position in file->f_pos.
  • The .llseek callback provides driver-specific seeking behavior.
  • The callback returns the new offset or a negative error code.
  • Nonseekable devices should use appropriate nonseekable semantics.
  • pread() and pwrite() perform positional I/O without changing the shared file offset.
