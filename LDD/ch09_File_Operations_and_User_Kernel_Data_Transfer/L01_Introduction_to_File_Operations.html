Chapter 9: File Operations and User-Kernel Data Transfer

Lesson 1: Introduction to File Operations
Level: Intermediate
Prerequisites: Character devices, cdev, file_operations structure and basic character-driver implementation.
Objective: Understand how Linux file operations connect user-space system calls to device-driver callbacks.

1. Introduction

Linux provides a common interface for accessing files, directories, device files and other file-like resources.

Applications use standard system calls such as:

  • open()
  • read()
  • write()
  • close()
  • lseek()
  • ioctl()
  • poll()

When an application accesses a character-device file, the Linux kernel uses the Virtual File System (VFS) to connect these operations to the appropriate device driver.

The driver provides callback functions through the struct file_operations structure.

2. What Are File Operations?

File operations are the operations that a process can perform on an opened file or device.

In Linux device-driver development, file operations are represented by the structure: 

struct file_operations

It is defined in the kernel header: 

#include <linux/fs.h>

The structure contains function pointers that associate file-related requests with driver callback functions.

Example

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

Here, the driver provides its own implementations of open, read, write and release operations.

3. Role of the Virtual File System (VFS)

The Virtual File System is a kernel subsystem that provides a common interface for different file systems and file-like objects.

Applications do not need to know the internal implementation of every device driver. They use standard system calls, while VFS dispatches operations through the appropriate kernel interfaces.

4. System Calls and Driver Callbacks

A system call is an interface through which a user-space application requests a service from the kernel.

A driver callback is a kernel function invoked by the kernel as part of handling an operation on a device file.

User-Space System Call Typical Driver Callback Purpose
open() .open Open a device file and prepare its use.
read() .read Transfer data from the device to user space.
write() .write Transfer data from user space to the device.
close() .release Release the open-file description when its final reference is closed.
lseek() .llseek Change the file position when supported.
ioctl() .unlocked_ioctl Perform device-specific control operations.
poll() .poll Report readiness for nonblocking I/O.
The mapping is conceptual rather than a promise that every system call invokes exactly one callback. Kernel handling may involve VFS, file-operation helpers and other subsystems. Some callbacks are optional.

5. Understanding the file Structure

When a process opens a file, the kernel creates or references an open-file description represented internally by a struct file.

The structure is defined in <linux/fs.h>.

It contains information associated with the opened file, including its current file position and associated file operations.

Important Concepts

Concept Meaning
struct file Represents an open-file description inside the kernel.
struct inode Represents file-system object metadata.
struct file_operations Contains callbacks for operations on the opened file.
file position Tracks the current offset for operations that use a file position.
file->private_data Provides a driver-defined pointer for per-open state.

Example: Using private_data

static int my_open(struct inode *inode,
                   struct file *file)
{
    file->private_data = NULL;

    pr_info("Device opened\n");

    return 0;
}

A driver can store a pointer to per-open information in file->private_data. It can retrieve that pointer in later callbacks.

6. The inode Structure

The inode represents a file-system object and contains metadata associated with that object.

For character devices, the inode includes the device number used to identify the registered character device.

Major and Minor Numbers

unsigned int major_number;
unsigned int minor_number;

major_number = imajor(inode);
minor_number = iminor(inode);
  • Major number identifies the device-driver registration range.
  • Minor number identifies a particular device instance or subdevice within that range.

A driver may use these values to determine which device instance is being accessed.

7. Important File Operations

A. open()

The open operation is used to access a device file. The driver's .open callback can initialize per-open state, validate access or check device availability. 

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

B. read()

The read operation transfers data from a device or kernel buffer into a user-space buffer. 

static ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
);

C. write()

The write operation transfers data from a user-space buffer into the device or kernel-side driver buffer. 

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
);

D. release()

The release operation handles final release of an open-file description. It can free per-open resources allocated by the open callback. 

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

E. llseek()

The llseek operation changes the current file position. It is useful for seekable devices and memory-backed files.

F. unlocked_ioctl()

The ioctl operation provides a mechanism for device-specific control commands that do not fit ordinary read and write operations.

G. poll()

The poll operation allows applications to check whether a device is ready for reading or writing.

8. Complete Example of file_operations

The following example shows how a driver connects callback functions through struct file_operations. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("mydriver: open called\n");
    return 0;
}

static ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
)
{
    pr_info("mydriver: read called\n");

    /* No data is provided by this demonstration. */
    return 0;
}

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
)
{
    pr_info("mydriver: write called\n");

    /* Demonstration only: no data is stored. */
    return -EOPNOTSUPP;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("mydriver: release called\n");
    return 0;
}

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("File Operations Demonstration");
This is a callback-definition demonstration, not a complete loadable character driver. It does not allocate a device number or register a cdev. The read callback returns EOF, and the write callback reports that the operation is unsupported.

Consider an application that opens a character device, writes some data, reads it and then closes the device.

10. File Descriptor vs Open-File Description

A file descriptor is a small integer used by a process to refer to an opened file.

The open-file description is the kernel object represented by struct file. It stores state such as the file position and status flags.

File Descriptor Open-File Description
Integer in a process descriptor table. Kernel object represented by struct file.
Used by application system calls. Stores open-file state and operations.
Can be duplicated using dup(). Duplicated descriptors can refer to the same open-file description.
Closing one descriptor removes that descriptor reference. Final release occurs when the open-file description is no longer referenced.
The distinction is important: closing one duplicated descriptor does not necessarily cause the driver's .release callback to run immediately. The open-file description may still be referenced by another descriptor or process.

11. User Space and Kernel Space

User-space applications and kernel-space drivers operate in different memory-access environments.

A driver must not directly dereference arbitrary user-space pointers.

Linux provides special functions for transferring data safely across this boundary.

Function Direction
copy_to_user() Kernel space → User space
copy_from_user() User space → Kernel space

These functions are commonly used in character-driver read and write callbacks. They can fail when a user-space address is invalid or inaccessible.

12. Return Values of File Operations

File-operation callbacks return values that indicate success or failure.

Return Value Meaning
Positive value from read() Number of bytes transferred.
Zero from read() End of file (EOF) or no more data for the current read position.
Positive value from write() Number of bytes accepted or written.
Zero from write() No bytes were written; normally avoid returning zero for a nonzero request without a specific reason.
Zero from open()/release() Successful completion.
Negative error code Indicates failure, such as -EFAULT or -EINVAL.

The kernel converts negative error returns into the appropriate user-space error reporting convention.

13. Common Error Codes

Error Code Description
-EINVAL Invalid argument.
-ENOMEM Insufficient memory.
-EFAULT Invalid or inaccessible user-space address.
-ENODEV Device is not available.
-EBUSY Device or resource is busy.
-EIO Input/output error.
-EOPNOTSUPP Requested operation is not supported.

14. Practical Observation Using Ubuntu

Use the basic character driver from Chapter 8 to observe how file operations are invoked.

Step 1: Load the Driver

sudo insmod basic_char_driver.ko

Step 2: Create Its Device Node

Obtain the actual major number from the driver's kernel log: 

sudo dmesg | tail -20

For example, if the driver reports major number 240: 

sudo mknod /dev/mychardev c 240 0
sudo chmod 666 /dev/mychardev

Step 3: Write Data

echo "Linux driver testing" | sudo tee /dev/mychardev

Step 4: Read Data

sudo cat /dev/mychardev

Step 5: Observe the Callbacks

sudo dmesg | tail -30

Observe messages printed by the driver's open, read, write and release callbacks.

Use the module and device-node values from your own Chapter 8 build. Do not assume the example major number will be assigned on every system.

15. Important Differences

Term Meaning
System call User-space interface for requesting a kernel service.
Driver callback Kernel function implementing a device operation.
VFS Kernel abstraction that provides a common file interface.
struct file Represents an open-file description.
struct inode Represents file-system object metadata.
file_operations Collection of callback function pointers.
File descriptor Process-level integer reference to an open file.

16. Summary

  • File operations define how a device responds to file-related requests.
  • Linux VFS provides a common interface for accessing files and device files.
  • struct file_operations connects kernel file handling to driver callbacks.
  • open(), read(), write() and close() are common user-space system calls.
  • Drivers implement callbacks such as .open, .read, .write and .release.
  • struct file represents an open-file description.
  • struct inode contains metadata and the character-device number.
  • copy_to_user() and copy_from_user() support user-kernel data transfer.
  • Callbacks communicate success, transferred byte counts or errors through return values.
