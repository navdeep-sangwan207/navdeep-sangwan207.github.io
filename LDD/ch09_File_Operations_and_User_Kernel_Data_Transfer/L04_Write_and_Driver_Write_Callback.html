Level: Intermediate

Objective: Understand the write() system call and implement a driver's .write callback to transfer data safely from user space into kernel space.

1. Introduction

The write() system call allows a user-space application to send data to an opened file or device.

In a Linux character driver, the kernel invokes the driver's .write callback when an application writes data to the device file.

The driver may store the received data in a kernel buffer, transmit it to hardware, send it through a communication interface or process it according to the device's functionality.

Common Applications

  • Sending commands to hardware.
  • Writing data to a serial device.
  • Controlling an LED through a device interface.
  • Sending configuration information to a driver.
  • Transmitting buffered data to a peripheral.

2. What Is the write() System Call?

The write() system call requests that data be transferred from a user-space buffer to an opened file descriptor.

Header File

#include <unistd.h>

Function Prototype

ssize_t write(int fd,
              const void *buffer,
              size_t count);

Parameters

Parameter Description
fd File descriptor returned by open().
buffer User-space source buffer containing data to write.
count Maximum number of bytes requested for writing.

Return Value

Return Value Meaning
Positive value Number of bytes successfully written.
Zero No bytes were written. This can occur when zero bytes are requested.
-1 System-call failure; errno describes the error.

3. Basic write() Example in User Space

#include <stdio.h>
#include <unistd.h>
#include <fcntl.h>
#include <string.h>

int main(void)
{
    int fd;
    const char message[] = "Hello Driver\n";
    ssize_t bytes;

    fd = open("/dev/mychardev", O_WRONLY);

    if (fd < 0) {
        perror("open failed");
        return 1;
    }

    bytes = write(fd, message, strlen(message));

    if (bytes < 0) {
        perror("write failed");
        close(fd);
        return 1;
    }

    printf("Bytes written: %zd\n", bytes);

    close(fd);

    return 0;
}

Compile

gcc write_test.c -o write_test

Execute

sudo ./write_test

The application opens the device in write-only mode, sends a message and closes the device.

A successful write() return means the driver accepted the reported number of bytes. It does not necessarily mean that physical hardware has completed the requested action.

4. Driver Write Callback

A character driver implements its write operation using the .write member of struct file_operations.

Function Prototype

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
);

Parameters

Parameter Description
file Represents the open-file description.
buffer User-space source buffer containing the data to be written.
count Maximum number of bytes requested.
position Pointer to the current file offset.

Return Value

  • Positive value: number of bytes accepted.
  • Zero: no bytes accepted.
  • Negative value: error code.

5. Understanding copy_from_user()

The copy_from_user() function transfers data from a user-space source buffer into a kernel-space destination buffer.

Header File

#include <linux/uaccess.h>

Function Prototype

unsigned long copy_from_user(
    void *to,
    const void __user *from,
    unsigned long n
);

Parameters

Parameter Description
to Destination address in kernel space.
from Source address in user space.
n Number of bytes requested for copying.

Return Value

Return Value Meaning
0 All requested bytes were copied.
Nonzero Number of bytes that could not be copied.
copy_from_user() does not return a negative errno value. A driver commonly returns -EFAULT if the requested copy is incomplete.

7. Basic Write Callback Example

Consider a driver that stores received data in a kernel buffer with a maximum capacity of 1024 bytes. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/uaccess.h>
#include <linux/string.h>

#define BUFFER_SIZE 1024

static char device_buffer[BUFFER_SIZE];
static size_t data_size;

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
)
{
    size_t offset;
    size_t bytes_to_copy;

    if (*position < 0)
        return -EINVAL;

    offset = (size_t)*position;

    if (offset > BUFFER_SIZE)
        return -EINVAL;

    bytes_to_copy = min(
        count,
        BUFFER_SIZE - offset
    );

    if (bytes_to_copy == 0)
        return 0;

    if (copy_from_user(
            device_buffer + offset,
            buffer,
            bytes_to_copy)) {
        return -EFAULT;
    }

    *position += bytes_to_copy;

    if (offset + bytes_to_copy > data_size)
        data_size = offset + bytes_to_copy;

    return bytes_to_copy;
}

Explanation

  1. The driver checks whether the file position is valid.
  2. It calculates the available buffer capacity.
  3. It determines the maximum number of bytes to accept.
  4. copy_from_user() transfers data into kernel memory.
  5. The file position is updated after a successful copy.
  6. The stored data size is extended when necessary.
  7. The callback returns the actual number of bytes accepted.
This example writes at the current offset. Writing at offset zero does not automatically erase older bytes beyond the newly written data. A driver that needs replacement semantics should define and implement those semantics explicitly.

8. Understanding the File Position in write()

The position parameter identifies the offset at which the driver should store incoming data.

Consider a kernel buffer initially containing: 

HELLO_____

If the next write begins at offset 5, the data is stored after the existing five characters. 

HELLOLINUX
Operation Offset Data Written Result
1 0 HELLO HELLO
2 5 LINUX HELLOLINUX

The driver must ensure that the write operation never exceeds the kernel buffer's capacity.

9. Understanding Buffer Size and count

The count parameter indicates how many bytes the application wants to write. It does not guarantee that the driver has enough space to accept all those bytes.

Example

bytes_to_copy = min(
    count,
    BUFFER_SIZE - offset
);

Suppose:

  • Buffer size = 1024 bytes.
  • Current offset = 900.
  • Requested count = 200 bytes.
  • Available space = 124 bytes.

The driver can accept at most 124 bytes in this operation.

Always validate the buffer boundary before copying user data into kernel memory.

10. Complete Read/Write Buffer Logic

A practical character driver often implements both read and write callbacks using the same kernel buffer.

The following example shows the shared buffer and synchronization logic. 

#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/uaccess.h>
#include <linux/mutex.h>

#define BUFFER_SIZE 1024

static char device_buffer[BUFFER_SIZE];
static size_t data_size;

static DEFINE_MUTEX(device_mutex);

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
)
{
    size_t offset;
    size_t bytes_to_copy;
    ssize_t ret;

    if (mutex_lock_interruptible(&device_mutex))
        return -ERESTARTSYS;

    if (*position < 0) {
        ret = -EINVAL;
        goto out;
    }

    offset = (size_t)*position;

    if (offset > BUFFER_SIZE) {
        ret = -EINVAL;
        goto out;
    }

    bytes_to_copy = min(
        count,
        BUFFER_SIZE - offset
    );

    if (bytes_to_copy == 0) {
        ret = 0;
        goto out;
    }

    if (copy_from_user(
            device_buffer + offset,
            buffer,
            bytes_to_copy)) {
        ret = -EFAULT;
        goto out;
    }

    *position += bytes_to_copy;

    if (offset + bytes_to_copy > data_size)
        data_size = offset + bytes_to_copy;

    ret = bytes_to_copy;

out:
    mutex_unlock(&device_mutex);
    return ret;
}

static ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
)
{
    size_t offset;
    size_t bytes_to_copy;
    ssize_t ret;

    if (mutex_lock_interruptible(&device_mutex))
        return -ERESTARTSYS;

    if (*position < 0) {
        ret = -EINVAL;
        goto out;
    }

    offset = (size_t)*position;

    if (offset >= data_size) {
        ret = 0;
        goto out;
    }

    bytes_to_copy = min(
        count,
        data_size - offset
    );

    if (bytes_to_copy == 0) {
        ret = 0;
        goto out;
    }

    if (copy_to_user(
            buffer,
            device_buffer + offset,
            bytes_to_copy)) {
        ret = -EFAULT;
        goto out;
    }

    *position += bytes_to_copy;
    ret = bytes_to_copy;

out:
    mutex_unlock(&device_mutex);
    return ret;
}

Why Use a Mutex?

Multiple processes or threads may access the same device simultaneously.

A mutex protects shared data from concurrent access while a read or write operation is in progress.

copy_from_user() and copy_to_user() may sleep. They must not be called while holding a spinlock or from interrupt context. A mutex is suitable for this process-context example.

11. Registering the Write Callback

The write callback is registered through the .write member of struct file_operations. 

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

When an application writes to the character device, the VFS uses the registered file operations to dispatch the request to the driver.

13. Handling Errors in the Write Callback

Error Code Possible Reason
-EFAULT User-space source could not be accessed or data could not be copied completely.
-EINVAL Invalid file position or unsupported argument.
-ENOSPC No space available for the requested data.
-EIO Device-related input/output failure.
-ERESTARTSYS An interruptible operation was interrupted and may be restarted.
-EAGAIN Operation cannot proceed immediately in a nonblocking implementation.

Example

if (copy_from_user(kernel_buffer,
                   user_buffer,
                   bytes_to_copy)) {
    return -EFAULT;
}

14. Partial Writes

A write operation may accept fewer bytes than requested. This is called a partial write.

For example, an application requests 200 bytes, but the driver has space for only 100 bytes.

Parameter Value
Requested bytes 200
Available capacity 100
Driver return value 100

The application can then write the remaining bytes using another write operation.

User-space programs should check the return value of write(). A positive value smaller than count indicates that only part of the data was accepted.

15. Blocking and Nonblocking Write Operations

Some devices may not be ready to accept data immediately.

Blocking Mode

In blocking mode, a write operation may wait until the device or buffer has enough capacity.

Nonblocking Mode

When a device is opened with O_NONBLOCK, the driver may return -EAGAIN or -EWOULDBLOCK when it cannot accept data immediately. 

int fd = open("/dev/mychardev",
              O_WRONLY | O_NONBLOCK);
O_NONBLOCK does not automatically implement nonblocking behavior. The driver must explicitly define how its read and write callbacks behave. Wait queues and readiness notification are covered in later lessons.

17. Important Differences Between read() and write()

Feature read() write()
Purpose Receive data Send data
Data direction Kernel to user User to kernel
Callback .read .write
Transfer function copy_to_user() copy_from_user()
Typical EOF behavior Returns 0 when no more data is available at the current position. No general EOF indication; returns bytes accepted or an error.
File position Usually advances by bytes read. Usually advances by bytes written.

18. Common Mistakes in Write Callbacks

Mistake Correct Approach
Directly dereferencing a user-space pointer. Use copy_from_user().
Copying more bytes than the kernel buffer can hold. Validate the offset and remaining capacity.
Ignoring copy_from_user() failures. Return an appropriate error, commonly -EFAULT.
Returning count without storing or processing data. Return the number of bytes actually accepted.
Not updating the file position. Update *position after successful transfer.
Accessing a shared buffer without synchronization. Use an appropriate synchronization mechanism.
Calling copy_from_user() in interrupt context. Perform user-memory transfers in a suitable process context.

19. Summary

  • write() is a user-space system call used to send data.
  • The driver's .write callback handles write requests.
  • copy_from_user() transfers data from user space to kernel space.
  • The callback receives file, buffer, count and file position.
  • The driver must validate offsets and buffer capacity.
  • Partial writes are valid and must be handled by applications.
  • The callback should return the number of bytes actually accepted.
  • Shared buffers require suitable synchronization.
  • Blocking and nonblocking behavior must be implemented by the driver.
