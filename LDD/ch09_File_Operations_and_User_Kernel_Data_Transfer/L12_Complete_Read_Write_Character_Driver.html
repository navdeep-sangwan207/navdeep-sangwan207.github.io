2. Introduction

A Linux character driver provides an interface through which user applications can communicate with a device or a software-backed data source.

In this lesson, we will develop a memory-backed character driver. It stores application data in a kernel buffer and allows an application to read that data later.

5. Global Variables and Kernel Buffer

The driver requires a device number, a cdev object, a data buffer and a mutex.

#define DEVICE_NAME "mychardev"
#define BUFFER_SIZE 1024

static dev_t dev_num;
static struct cdev my_cdev;

static char device_buffer[BUFFER_SIZE];
static size_t data_size;

static DEFINE_MUTEX(buffer_mutex);

Explanation

  • dev_num stores the allocated device number.
  • my_cdev represents the character device.
  • device_buffer stores the application data.
  • data_size records the number of valid bytes.
  • buffer_mutex protects shared buffer state.
The buffer and data_size are global in this educational example. Therefore, all open instances share the same data. A production driver may require per-device or per-open buffers and a more detailed concurrency design.

6. Implementing open() Callback

The open callback is invoked when a process successfully opens the registered device through its device node.

static int my_open(
    struct inode *inode,
    struct file *file)
{
    pr_info("mychardev: device opened\n");

    return 0;
}

Explanation

  • The callback receives inode and file structures.
  • The driver can inspect the device number using inode information.
  • The file structure represents the open-file description.
  • Returning zero indicates success.
  • A negative error code indicates failure.

7. Implementing read() Callback

The read callback transfers data from the kernel buffer to the user application.

Code

static ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position)
{
    size_t bytes_to_copy;
    unsigned long not_copied;
    ssize_t result;

    if (*position < 0)
        return -EINVAL;

    if (mutex_lock_interruptible(&buffer_mutex))
        return -ERESTARTSYS;

    if ((size_t)*position >= data_size) {
        result = 0;
        goto out;
    }

    bytes_to_copy = min(
        count,
        data_size - (size_t)*position
    );

    not_copied = copy_to_user(
        buffer,
        device_buffer + *position,
        bytes_to_copy
    );

    bytes_to_copy -= not_copied;

    if (bytes_to_copy == 0) {
        result = -EFAULT;
        goto out;
    }

    *position += bytes_to_copy;
    result = bytes_to_copy;

out:
    mutex_unlock(&buffer_mutex);
    return result;
}

Working

  1. Check that the file position is not negative.
  2. Acquire the mutex.
  3. Check whether the end of stored data has been reached.
  4. Calculate the number of bytes available.
  5. Use copy_to_user() to transfer the data.
  6. Calculate the actual number of bytes copied.
  7. Update the file position.
  8. Release the mutex and return the result.
Returning zero indicates end-of-file. A positive return value indicates the number of bytes successfully transferred.

8. Implementing write() Callback

The write callback receives application data and stores it in the kernel buffer.

Code

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position)
{
    size_t bytes_to_copy;
    unsigned long not_copied;
    ssize_t result;

    if (*position < 0)
        return -EINVAL;

    if (mutex_lock_interruptible(&buffer_mutex))
        return -ERESTARTSYS;

    if ((size_t)*position >= BUFFER_SIZE) {
        result = -ENOSPC;
        goto out;
    }

    bytes_to_copy = min(
        count,
        BUFFER_SIZE - (size_t)*position
    );

    not_copied = copy_from_user(
        device_buffer + *position,
        buffer,
        bytes_to_copy
    );

    bytes_to_copy -= not_copied;

    if (bytes_to_copy == 0) {
        result = -EFAULT;
        goto out;
    }

    *position += bytes_to_copy;

    if ((size_t)*position > data_size)
        data_size = (size_t)*position;

    result = bytes_to_copy;

out:
    mutex_unlock(&buffer_mutex);
    return result;
}

Working

  1. Validate the file position.
  2. Acquire the mutex.
  3. Check whether the position is within the buffer.
  4. Calculate the available buffer capacity.
  5. Copy data from user space using copy_from_user().
  6. Calculate the number of successfully copied bytes.
  7. Update the file position and data size.
  8. Release the mutex and return the transferred byte count.
This implementation writes at the current file position. It does not automatically truncate old data when a new write starts at offset zero. A shorter overwrite may therefore leave older bytes after the new data. The separate data_size value tracks the highest valid end position.

9. Implementing release() Callback

The release callback handles the final release of the open-file description.

static int my_release(
    struct inode *inode,
    struct file *file)
{
    pr_info("mychardev: device released\n");

    return 0;
}

The callback returns zero when release handling completes successfully.

The .release callback is not necessarily invoked once for every close() call. It is associated with the final release of the open-file description. The .flush callback has different close-related semantics.

10. file_operations Structure

The file_operations structure connects system-call operations to driver callbacks.

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};
MemberCallback
.ownerAssociates file operations with the module.
.openmy_open()
.readmy_read()
.writemy_write()
.releasemy_release()

The .owner = THIS_MODULE assignment helps prevent ordinary module unloading while active file operations hold references to the module.

11. Character Device Initialization

The initialization function allocates a device number, initializes the cdev object and registers the character device.

static int __init my_driver_init(void)
{
    int ret;

    ret = alloc_chrdev_region(
        &dev_num,
        0,
        1,
        DEVICE_NAME
    );

    if (ret < 0) {
        pr_err("Device number allocation failed\n");
        return ret;
    }

    cdev_init(&my_cdev, &my_fops);
    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev_num, 1);

    if (ret < 0) {
        unregister_chrdev_region(dev_num, 1);
        pr_err("Character device registration failed\n");
        return ret;
    }

    pr_info("Device registered: major=%d minor=%d\n",
            MAJOR(dev_num),
            MINOR(dev_num));

    return 0;
}

Initialization Sequence

  1. Allocate one device number dynamically.
  2. Initialize the cdev structure with file operations.
  3. Set the module owner.
  4. Register the cdev using cdev_add().
  5. Print the allocated major and minor numbers.
cdev_add() makes the device registration available immediately. All callback code and driver state must be initialized before calling it. The example does not create a /dev node automatically.

12. Module Cleanup Function

The cleanup function removes the character-device registration and releases the allocated device number.

static void __exit my_driver_exit(void)
{
    cdev_del(&my_cdev);

    unregister_chrdev_region(
        dev_num,
        1
    );

    pr_info("mychardev: driver removed\n");
}

Module lifecycle registration:

module_init(my_driver_init);
module_exit(my_driver_exit);
cdev_del() prevents new opens through this registration, but it does not terminate existing open file descriptions. Resource lifetime and active users must be managed carefully in production drivers.

15. User-Space Test Application

Create a C program that writes data to the device, returns to the beginning of the file and reads the stored data.

File: test_driver.c

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <string.h>

#define DEVICE_PATH "/dev/mychardev"
#define BUFFER_SIZE 1024

int main(void)
{
    int fd;
    const char message[] =
        "Hello from User Space!";

    char buffer[BUFFER_SIZE + 1];
    ssize_t written;
    ssize_t received;

    fd = open(DEVICE_PATH, O_RDWR);

    if (fd < 0) {
        perror("open");
        return 1;
    }

    written = write(
        fd,
        message,
        strlen(message)
    );

    if (written < 0) {
        perror("write");
        close(fd);
        return 1;
    }

    printf("Bytes written: %zd\n", written);

    if (lseek(fd, 0, SEEK_SET) < 0) {
        perror("lseek");
        close(fd);
        return 1;
    }

    received = read(
        fd,
        buffer,
        BUFFER_SIZE
    );

    if (received < 0) {
        perror("read");
        close(fd);
        return 1;
    }

    buffer[received] = '\0';

    printf("Received data: %s\n", buffer);

    close(fd);

    return 0;
}

Explanation

  1. open() opens the device in read/write mode.
  2. write() sends the message to the driver.
  3. The driver uses copy_from_user() to receive it.
  4. lseek() moves the file position to the beginning.
  5. read() requests the stored data.
  6. The driver uses copy_to_user() to return the message.
  7. close() releases the file descriptor.
This test program is intentionally simple and checks for negative errors. General-purpose applications should also loop when handling partial reads and writes, because a successful read() or write() is not guaranteed to transfer the entire requested amount.

19. Important Technical Limitations

  • This is a memory-backed software character device, not a physical hardware driver.
  • The buffer is shared by all processes opening this device.
  • The example does not implement blocking reads or wait queues.
  • The example does not implement poll(), IOCTL or nonblocking I/O.
  • The driver does not automatically create a device node.
  • The buffer has a fixed capacity of 1024 bytes.
  • The mutex protects shared buffer contents and metadata during the callbacks.
  • Holding the mutex across user-memory copying is permissible in sleepable process context, but can increase contention.
  • For production use, carefully define per-open state, overwrite behavior, buffer lifetime, device removal and concurrent access semantics.
Do not unload a driver while active users or device resources still depend on it. The module owner reference helps prevent ordinary unloading while file operations are active, but it does not replace proper resource-lifetime management.
