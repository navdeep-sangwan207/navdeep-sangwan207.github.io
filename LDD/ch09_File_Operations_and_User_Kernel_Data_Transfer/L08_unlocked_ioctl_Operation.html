2. Introduction to IOCTL

IOCTL stands for Input/Output Control.

In Linux, IOCTL is a mechanism through which a user-space application sends device-specific control commands to a kernel driver.

Normal read() and write() operations are primarily designed for transferring data. However, a device often requires additional control operations.

Examples of Device Control Operations

  • Changing the operating mode of a device.
  • Setting communication parameters.
  • Starting or stopping a device operation.
  • Reading device status or configuration.
  • Setting a timeout value.
  • Controlling a hardware feature.

These operations can be implemented through IOCTL commands when they are appropriate for the device interface.

Basic IOCTL Communication

3. Why Do We Need IOCTL?

Consider a serial communication device.

The application may need to perform the following operations:

  • Read received data.
  • Write transmit data.
  • Set baud rate.
  • Configure parity.
  • Enable or disable a communication feature.
  • Retrieve current device configuration.

Read() and write() handle data transfer, but configuration and control operations need a separate interface.

OperationTypical Interface
Receive dataread()
Transmit datawrite()
Change device configurationioctl()
Retrieve device statusioctl() or another suitable interface
Monitor readinesspoll(), select() or epoll()
IOCTL is not mandatory for every device control interface. Depending on the device and subsystem, sysfs, configfs, netlink, standard device-specific APIs or other interfaces may be more suitable.

4. User-Space ioctl() System Call

The application invokes the ioctl() system call to send a command to the device driver.

Header File

#include <sys/ioctl.h>

Common Function Prototype

int ioctl(int fd, unsigned long request, ...);

Parameters

ParameterDescription
fdFile descriptor of the opened device.
requestIOCTL command identifier.
...Optional command argument, often a pointer to user-space data.

Return Value

  • Usually returns 0 or another nonnegative value on success, according to the command's definition.
  • Returns -1 on failure and sets errno in user space.
int ret;

ret = ioctl(fd, MY_IOCTL_COMMAND, &value);

if (ret == -1) {
    perror("ioctl");
}

5. What Is unlocked_ioctl()?

The unlocked_ioctl() callback is a member of the Linux kernel's struct file_operations structure.

It handles IOCTL requests from user-space applications for a character device.

Callback Prototype

long (*unlocked_ioctl)(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
);

Parameters

ParameterDescription
filePointer to the open file structure.
cmdIOCTL command number.
argArgument supplied by the user-space application, often a user-space pointer encoded as an unsigned long.

Return Value

  • Return 0 or another nonnegative result on success, depending on the command.
  • Return a negative kernel error code on failure.
The term unlocked distinguishes this callback from the older .ioctl interface, which used the Big Kernel Lock in historical kernels. Modern drivers generally use .unlocked_ioctl and provide their own appropriate synchronization.

6. Registering unlocked_ioctl()

The callback is registered in the driver's file_operations structure.

static const struct file_operations my_fops = {
    .owner          = THIS_MODULE,
    .open            = my_open,
    .read            = my_read,
    .write           = my_write,
    .release         = my_release,
    .unlocked_ioctl  = my_ioctl
};

When an application invokes ioctl() on the corresponding device file, the VFS dispatches the request to the registered callback.

7. IOCTL Command Design

Linux provides macros to construct structured IOCTL command numbers.

The commonly used macros are defined in:

#include <linux/ioctl.h>

Four Important Macros

MacroMeaning
_IOCommand without a data-transfer argument.
_IORCommand for reading data from the driver into user space.
_IOWCommand for writing data from user space to the driver.
_IOWRCommand for bidirectional data transfer.

General Syntax

_IO(type, number)

_IOR(type, number, data_type)

_IOW(type, number, data_type)

_IOWR(type, number, data_type)

Here:

  • type: Device or driver-specific command group identifier, commonly a character constant.
  • number: Command number within that group.
  • data_type: Type describing the data argument.
The direction names describe data movement from the application's perspective: _IOR copies data from kernel to user, while _IOW copies data from user to kernel. These macros encode command metadata; they do not perform the actual copying.

8. Understanding _IO Macro

The _IO macro is used for commands that do not transfer a data structure through the third argument.

Example

#define MY_MAGIC 'N'

#define MY_IOCTL_RESET \
    _IO(MY_MAGIC, 1)

This command can request a reset or another control operation that does not require a data argument.

User-Space Usage

ioctl(fd, MY_IOCTL_RESET);

The driver receives the command number and performs the requested operation.

9. Understanding _IOR Macro

The _IOR macro defines a command that transfers data from the kernel driver to the user application.

Example

struct device_status {
    int status;
};

#define MY_IOCTL_GET_STATUS \
    _IOR(MY_MAGIC, 2, struct device_status)

The application provides a pointer to a user-space structure. The driver fills the structure and copies it to user space.

Kernel Driver
Data →
User Application

Direction: Kernel to User

10. Understanding _IOW Macro

The _IOW macro defines a command that transfers data from the user application to the kernel driver.

Example

#define MY_IOCTL_SET_VALUE \
    _IOW(MY_MAGIC, 3, int)

The user application supplies an integer value. The driver copies that value from user space into kernel space.

User Application
Data →
Kernel Driver

Direction: User to Kernel

11. Understanding _IOWR Macro

The _IOWR macro is used when data moves in both directions.

Example

struct device_config {
    int mode;
    int value;
};

#define MY_IOCTL_CONFIG \
    _IOWR(MY_MAGIC, 4, struct device_config)

The application can supply configuration information and receive updated information from the driver through the same structure.

User Application
↔
Kernel Driver

Bidirectional data transfer

12. Complete IOCTL Command Header

It is good practice to define IOCTL commands in a common header file shared by the kernel module and the user-space application.

File: my_ioctl.h

#ifndef MY_IOCTL_H
#define MY_IOCTL_H

#include <linux/ioctl.h>

#define MY_MAGIC 'N'

#define MY_IOCTL_RESET \
    _IO(MY_MAGIC, 1)

#define MY_IOCTL_GET_STATUS \
    _IOR(MY_MAGIC, 2, int)

#define MY_IOCTL_SET_VALUE \
    _IOW(MY_MAGIC, 3, int)

#define MY_IOCTL_CONFIG \
    _IOWR(MY_MAGIC, 4, int)

#endif

Using one shared header reduces the possibility of command-number mismatches between the driver and application.

For portable interfaces, define fixed-width data types and carefully designed structures. Avoid architecture-dependent pointers and ambiguous structure layouts in an ABI shared between user space and kernel space.

13. Implementing unlocked_ioctl() in a Driver

The following example demonstrates handling four IOCTL commands.

Kernel-Space Callback

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/uaccess.h>
#include "my_ioctl.h"

static int device_value;
static int device_status;

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg)
{
    int value;

    switch (cmd) {

    case MY_IOCTL_RESET:
        device_value = 0;
        device_status = 0;
        pr_info("Device reset\n");
        break;

    case MY_IOCTL_GET_STATUS:

        value = device_status;

        if (copy_to_user((int __user *)arg,
                         &value,
                         sizeof(value)))
            return -EFAULT;

        break;

    case MY_IOCTL_SET_VALUE:

        if (copy_from_user(&value,
                           (int __user *)arg,
                           sizeof(value)))
            return -EFAULT;

        device_value = value;
        pr_info("New value: %d\n", device_value);
        break;

    case MY_IOCTL_CONFIG:

        if (copy_from_user(&value,
                           (int __user *)arg,
                           sizeof(value)))
            return -EFAULT;

        device_value = value;
        device_status = 1;

        value = device_value + 10;

        if (copy_to_user((int __user *)arg,
                         &value,
                         sizeof(value)))
            return -EFAULT;

        break;

    default:
        return -ENOTTY;
    }

    return 0;
}

Explanation

CommandDriver Action
MY_IOCTL_RESETResets the stored device state.
MY_IOCTL_GET_STATUSCopies status information to user space.
MY_IOCTL_SET_VALUECopies a value from user space into the driver.
MY_IOCTL_CONFIGReceives a value and returns a modified value.
This is a teaching example. It uses simple global state and does not provide per-device or concurrent-access protection. A production driver must synchronize shared state and validate device-specific parameters.

14. User-Space Program to Test IOCTL

The following application sends IOCTL commands to the character device.

File: test_ioctl.c

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/ioctl.h>
#include <errno.h>
#include "my_ioctl.h"

int main(void)
{
    int fd;
    int value;
    int ret;

    fd = open("/dev/mychardev", O_RDWR);

    if (fd < 0) {
        perror("open");
        return 1;
    }

    ret = ioctl(fd, MY_IOCTL_RESET);

    if (ret == -1)
        perror("MY_IOCTL_RESET");
    else
        printf("Device reset successful\n");

    value = 100;

    ret = ioctl(fd, MY_IOCTL_SET_VALUE, &value);

    if (ret == -1)
        perror("MY_IOCTL_SET_VALUE");
    else
        printf("Value sent: %d\n", value);

    value = 0;

    ret = ioctl(fd, MY_IOCTL_GET_STATUS, &value);

    if (ret == -1)
        perror("MY_IOCTL_GET_STATUS");
    else
        printf("Device status: %d\n", value);

    value = 25;

    ret = ioctl(fd, MY_IOCTL_CONFIG, &value);

    if (ret == -1)
        perror("MY_IOCTL_CONFIG");
    else
        printf("Returned configuration value: %d\n",
               value);

    close(fd);

    return 0;
}

Compile

gcc test_ioctl.c -o test_ioctl

Run

sudo ./test_ioctl

Make sure the kernel module implements the same command definitions and that /dev/mychardev refers to the correct device.

15. Registering the Callback in a Complete Driver

The IOCTL callback is one member of the file_operations structure.

static const struct file_operations my_fops = {
    .owner          = THIS_MODULE,
    .open            = my_open,
    .read            = my_read,
    .write           = my_write,
    .release         = my_release,
    .llseek           = my_llseek,
    .poll             = my_poll,
    .unlocked_ioctl  = my_ioctl,
};

The driver must also register its character device using the appropriate character-device APIs, such as alloc_chrdev_region(), cdev_init() and cdev_add().

16. Error Handling in IOCTL

Error CodeMeaning / Typical Use
-ENOTTYUnsupported or unrecognized IOCTL command.
-EFAULTInvalid user-space memory address or failed user-memory transfer.
-EINVALInvalid command parameter or configuration value.
-ENOMEMMemory allocation failure.
-EPERMOperation not permitted.
-EBUSYDevice or resource is busy.

Unknown Command

default:
    return -ENOTTY;

The user-space application receives -1 and errno is set according to the returned kernel error.

17. Synchronization and Security Considerations

IOCTL callbacks can be invoked concurrently by different processes or threads.

A robust driver should consider:

  • Protecting shared device state using mutexes or other suitable synchronization primitives.
  • Validating every command and parameter.
  • Using copy_from_user() and copy_to_user() for user-memory transfers.
  • Avoiding direct dereferencing of user-space pointers.
  • Checking structure sizes and fields when accepting user-defined structures.
  • Restricting privileged operations where required.
  • Considering compatibility between 32-bit applications and 64-bit kernels.
The optional .compat_ioctl callback may be needed for certain 32-bit user-space applications running on a 64-bit kernel. Compatibility handling depends on the IOCTL data structures and ABI design.

18. Common Mistakes in IOCTL Implementation

MistakeProblem
Using different command definitions in application and driverCommand matching fails.
Directly dereferencing user pointersUnsafe kernel access and possible faults.
Ignoring copy_to_user() resultData transfer errors are not handled.
Ignoring copy_from_user() resultDriver may use incomplete or invalid data.
Not checking unknown commandsUnsupported requests may be handled incorrectly.
Not protecting shared stateConcurrent commands may cause race conditions.

19. Practical Applications of IOCTL

  • Changing serial-port configuration.
  • Controlling hardware operating modes.
  • Setting device-specific parameters.
  • Retrieving device status and statistics.
  • Controlling certain features of multimedia devices.
  • Managing device-specific operations that are not ordinary data transfers.

IOCTL is a general mechanism. Actual commands and their meanings depend on the device driver or subsystem.

20. Lesson Summary

  • IOCTL stands for Input/Output Control.
  • It provides a mechanism for device-specific control operations.
  • User applications invoke ioctl() from sys/ioctl.h.
  • Drivers commonly implement the .unlocked_ioctl callback.
  • _IO, _IOR, _IOW and _IOWR define structured command identifiers.
  • copy_to_user() transfers data from kernel to user space.
  • copy_from_user() transfers data from user to kernel space.
  • Unknown commands should return an appropriate error such as -ENOTTY.
  • Shared driver state must be protected against concurrent access.
  • IOCTL command definitions form part of the user-kernel ABI.
