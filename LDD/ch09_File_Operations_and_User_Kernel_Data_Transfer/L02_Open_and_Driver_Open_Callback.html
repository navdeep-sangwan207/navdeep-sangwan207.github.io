Lesson 2: open() and Driver Open Callback
Level: Intermediate
Prerequisites: VFS, struct file, struct inode and file_operations.
Objective: Understand how the open() system call works and how a character driver implements its .open callback.

1. Introduction

The open() system call is used by a user-space application to open a file or device file.

In Linux device-driver development, opening a character-device file normally causes the kernel to invoke the driver's .open callback.

The open callback is commonly used to:

  • Initialize per-open resources.
  • Check whether the device is available.
  • Validate access conditions.
  • Allocate a private data structure.
  • Initialize file->private_data.
  • Prevent unsupported simultaneous access when required.

2. What Is the open() System Call?

The open() system call opens a file and returns a file descriptor on success.

Header File

#include <fcntl.h>
#include <sys/types.h>
#include <sys/stat.h>
#include <unistd.h>

Function Prototype

int open(const char *pathname, int flags);

int open(const char *pathname,
         int flags,
         mode_t mode);

The third argument is used when creating a file with flags such as O_CREAT.

Example

int fd;

fd = open("/dev/mychardev", O_RDWR);

if (fd < 0) {
    perror("open failed");
}

If the operation succeeds, fd contains a non-negative file descriptor. If it fails, open() returns -1 and sets errno.

3. Common open() Flags

Flag Purpose
O_RDONLY Open for reading only.
O_WRONLY Open for writing only.
O_RDWR Open for reading and writing.
O_NONBLOCK Request nonblocking I/O behavior where supported.
O_CLOEXEC Set close-on-exec for the returned file descriptor.
O_APPEND Request append behavior for writes.
O_CREAT Create the file if it does not exist.
O_TRUNC Request truncation when applicable to a regular file opened for writing.
Not every flag has the same meaning for every device driver. For example, O_APPEND and O_TRUNC do not automatically implement append or truncation behavior in a character driver's private buffer. The driver must define any device-specific behavior it supports.

4. What Happens When a Device File Is Opened?

Consider an application opening: 

open("/dev/mychardev", O_RDWR);

A simplified sequence is:

  1. The application invokes the open() system call.
  2. The kernel validates the pathname and access permissions.
  3. The VFS resolves the device file.
  4. The character-device infrastructure identifies the registered cdev.
  5. The kernel obtains the appropriate file operations.
  6. The driver's .open callback is invoked if provided.
  7. On success, the application receives a file descriptor.

5. Driver Open Callback

The driver open callback is registered through the .open member of struct file_operations.

Function Prototype

static int my_open(struct inode *inode,
                   struct file *file);

Parameters

Parameter Description
inode Represents the device-file inode and provides access to its device number.
file Represents the open-file description and stores per-open state.

Return Value

Return Value Meaning
0 Open operation succeeded.
Negative error code Open operation failed.

6. Basic Open Callback Example

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("mychardev: device opened\n");

    return 0;
}

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
};

When a process successfully opens the registered device file, the kernel invokes my_open().

Returning zero indicates success. A negative error code indicates that the driver rejected the open request.

7. Accessing Major and Minor Numbers

The open callback receives an inode pointer. A driver can use the inode helper functions to obtain the device major and minor numbers.

Example

static int my_open(struct inode *inode,
                   struct file *file)
{
    unsigned int major_number;
    unsigned int minor_number;

    major_number = imajor(inode);
    minor_number = iminor(inode);

    pr_info("Device opened\n");
    pr_info("Major number: %u\n", major_number);
    pr_info("Minor number: %u\n", minor_number);

    return 0;
}

This is useful when one driver manages multiple device instances using different minor numbers.

8. Using file->private_data

The private_data member of struct file allows a driver to associate its own data with an open-file description.

This is commonly used for per-open state.

Example Data Structure

struct device_context {
    int device_id;
    int access_count;
};

Example Open Callback

#include <linux/slab.h>

static int my_open(struct inode *inode,
                   struct file *file)
{
    struct device_context *context;

    context = kzalloc(sizeof(*context), GFP_KERNEL);

    if (!context)
        return -ENOMEM;

    context->device_id = iminor(inode);
    context->access_count = 1;

    file->private_data = context;

    pr_info("mychardev: opened minor %d\n",
            context->device_id);

    return 0;
}

Explanation

  1. Allocate memory for a device context.
  2. Check whether allocation succeeded.
  3. Store the device minor number.
  4. Initialize the access count.
  5. Store the pointer in file->private_data.
When a driver allocates per-open memory in .open, it must release that memory in the corresponding .release callback. Otherwise, repeated open and close operations can cause memory leaks.

9. Accessing private_data in Other Callbacks

The driver can retrieve the per-open structure from the file pointer in later callbacks.

Example Read Callback

static ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
)
{
    struct device_context *context;

    context = file->private_data;

    if (!context)
        return -EINVAL;

    pr_info("Reading from device %d\n",
            context->device_id);

    return 0;
}

The callback accesses the same per-open context that was stored during the open operation.

10. Releasing Per-Open Resources

If the open callback allocates memory, the release callback should free it when the open-file description is finally released.

Example Release Callback

#include <linux/slab.h>

static int my_release(struct inode *inode,
                      struct file *file)
{
    struct device_context *context;

    context = file->private_data;

    if (context) {
        pr_info("Closing device %d\n",
                context->device_id);

        kfree(context);
        file->private_data = NULL;
    }

    return 0;
}

This prevents the per-open allocation from remaining in memory after its open-file description is released.

11. Preventing Multiple Simultaneous Opens

Some devices may allow only one process to open them at a time.

A driver can implement an exclusive-open policy using an atomic variable.

Example

#include <linux/atomic.h>

static atomic_t device_available = ATOMIC_INIT(1);

static int my_open(struct inode *inode,
                   struct file *file)
{
    if (atomic_cmpxchg(&device_available, 1, 0) != 1)
        return -EBUSY;

    pr_info("mychardev: exclusive open successful\n");

    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    atomic_set(&device_available, 1);

    pr_info("mychardev: device released\n");

    return 0;
}

The atomic compare-and-exchange operation ensures that only one opener can change the availability state from 1 to 0.

This is an exclusive-open demonstration. A production driver must also consider device removal, failure paths and the lifetime of its shared state.

12. Error Handling in the Open Callback

The open callback should return a negative error code when it cannot safely provide access to the device.

Error Code Possible Reason
-ENOMEM Memory allocation failed.
-EBUSY Device is already exclusively opened.
-ENODEV Device is unavailable or has been removed.
-EINVAL Invalid device or unsupported configuration.
-EACCES Driver-level access policy denies the operation.

Example: Allocation Failure

context = kzalloc(sizeof(*context), GFP_KERNEL);

if (!context)
    return -ENOMEM;

Example: Device Busy

if (atomic_cmpxchg(&device_available, 1, 0) != 1)
    return -EBUSY;

13. Complete Open and Release Example

This example demonstrates per-open memory allocation and cleanup. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/slab.h>

struct device_context {
    unsigned int minor_number;
};

static int my_open(struct inode *inode,
                   struct file *file)
{
    struct device_context *context;

    context = kzalloc(sizeof(*context), GFP_KERNEL);

    if (!context)
        return -ENOMEM;

    context->minor_number = iminor(inode);

    file->private_data = context;

    pr_info("mychardev: opened minor %u\n",
            context->minor_number);

    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    struct device_context *context;

    context = file->private_data;

    if (context) {
        pr_info("mychardev: released minor %u\n",
                context->minor_number);

        kfree(context);
        file->private_data = NULL;
    }

    return 0;
}

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
    .release = my_release,
};

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Open and Release Callback Example");

This source demonstrates the callback implementation only. It must be connected to a registered character device before user applications can invoke it.

14. Difference Between open() and .open

open() .open
User-space system call. Kernel-space driver callback.
Called by an application. Invoked by the kernel during device-file opening when registered.
Returns a file descriptor on success. Returns zero or a negative error code.
Declared in user-space headers such as fcntl.h. Registered through struct file_operations.
Example: open("/dev/mychardev", O_RDWR). Example: .open = my_open.

15. Important Note: close() and .release

The user-space close() system call closes one file descriptor.

The driver's .release callback is normally invoked when the associated open-file description is finally released.

If a file descriptor has been duplicated using dup() or inherited through process creation, closing one descriptor may not be enough to trigger .release.

Do not confuse .release with .flush. The .flush callback can be invoked for individual close operations, while .release handles final release of the open-file description.

17. Common Mistakes

Mistake Correct Approach
Returning success after memory allocation fails. Return -ENOMEM.
Allocating per-open data without freeing it. Free it in .release.
Forgetting to initialize private_data. Assign a valid pointer or NULL.
Assuming .release runs for every close(). Understand open-file description reference counting.
Using a shared availability flag without synchronization. Use appropriate atomic or locking mechanisms.
Accessing an invalid device instance. Validate device state before accepting access.

18. Summary

  • open() is a user-space system call.
  • The .open callback is implemented by a device driver.
  • The kernel invokes the callback when a registered device file is opened.
  • The callback receives inode and file pointers.
  • imajor() and iminor() retrieve device numbers from the inode.
  • file->private_data stores driver-defined per-open information.
  • Per-open allocations should be released in .release.
  • Atomic operations can implement exclusive-open policies.
  • Negative error codes indicate open failures.
