2. Introduction to I/O Readiness

A device driver may receive data from hardware, store data in a kernel buffer, or wait for an event before allowing a process to continue.

Consider a character device that receives data from a sensor or communication interface.

  • An application wants to read data from the device.
  • Data may not be available immediately.
  • The application should avoid repeatedly calling read() without useful data.
  • The driver needs a way to notify the application when reading or writing can proceed.

Linux provides I/O readiness notification mechanisms through poll(), select() and epoll().

3. Blocking I/O

In blocking I/O, a process may sleep when the requested operation cannot proceed immediately.

Example: Reading from a Device

read(fd, buffer, sizeof(buffer));

If the device has no data available, a blocking read callback may place the process into a waiting state until data arrives.

Typical Sequence

  1. The application calls read().
  2. The driver checks whether data is available.
  3. If data is unavailable, the driver waits using an appropriate wait queue.
  4. A hardware event or another process makes data available.
  5. The driver wakes the waiting process.
  6. The read operation continues.
Important: A blocking read does not automatically wait just because a device has no data. The driver must implement the required waiting and wake-up behavior.

4. Nonblocking I/O

Nonblocking I/O allows an application to request an operation without waiting indefinitely for data or buffer space.

A file can be opened using the O_NONBLOCK flag.

int fd = open("/dev/mychardev",
              O_RDONLY | O_NONBLOCK);

If no data is currently available, a correctly implemented driver can return -EAGAIN or -EWOULDBLOCK rather than putting the process to sleep.

Blocking vs Nonblocking I/O

Blocking I/ONonblocking I/O
May wait until the operation can proceed.Returns promptly if the operation cannot proceed.
Can sleep while waiting for data.Does not wait indefinitely for the requested I/O.
Useful for simple sequential processing.Useful for event-driven applications.
Waiting is managed by driver and VFS semantics.Application may retry or use readiness notification.
Important: Setting O_NONBLOCK does not automatically make a driver nonblocking. The driver's read() and write() implementations must explicitly handle nonblocking conditions.

5. What Is poll()?

poll() is a user-space system call that allows an application to monitor multiple file descriptors and determine whether I/O operations can proceed without blocking.

Header File

#include <poll.h>

Function Prototype

int poll(struct pollfd fds[],
         nfds_t nfds,
         int timeout);

Parameters

ParameterDescription
fdsArray of pollfd structures representing file descriptors to monitor.
nfdsNumber of entries in the array.
timeoutMaximum time to wait in milliseconds.

Return Value

  • Positive value: Number of file descriptors with reported events.
  • Zero: Timeout expired without a reported event.
  • Negative value: Error; returns -1 and sets errno.

pollfd Structure

struct pollfd {
    int   fd;
    short events;
    short revents;
};
  • fd: File descriptor being monitored.
  • events: Events requested by the application.
  • revents: Events reported by the kernel.

6. Important poll() Event Flags

EventMeaning
POLLINData is available for reading.
POLLRDNORMNormal data can be read.
POLLOUTWriting can proceed without blocking.
POLLWRNORMNormal data can be written.
POLLPRIPriority or exceptional data is available.
POLLERRAn error condition exists.
POLLHUPA hangup condition exists.
POLLNVALThe file descriptor is invalid.
POLLERR, POLLHUP and POLLNVAL are condition indicators. They are generally reported in revents rather than requested in events.

Readiness Meaning

  • POLLIN indicates that a read operation can proceed without blocking, although it may return fewer bytes than requested.
  • POLLOUT indicates that some writing can proceed without blocking; it does not guarantee that the entire requested write will fit.
  • POLLHUP can indicate that the other end of a communication channel has closed.

7. What Is the .poll Callback?

Linux character drivers can implement a .poll callback in the struct file_operations structure.

The callback reports whether the device is ready for reading or writing and registers the application's wait queue interest.

Callback Prototype

__poll_t (*poll)(
    struct file *file,
    struct poll_table_struct *wait
);

The exact callback type is defined by the target kernel headers. Modern kernels use __poll_t for the return type.

Parameters

ParameterDescription
filePointer to the open file structure.
waitPoll table used to register wait queue interest.

Return Value

The callback returns a bitmask of readiness events, such as:

EPOLLIN
EPOLLOUT
EPOLLERR
EPOLLHUP

The returned readiness flags use the poll/epoll event definitions. For example, EPOLLIN corresponds to readable data and EPOLLOUT corresponds to writable space.

8. What Is poll_wait()?

poll_wait() is a kernel helper used inside a driver's .poll callback to register a wait queue with the polling mechanism.

Function Usage

poll_wait(file, &my_wait_queue, wait);

It associates the poll request with the specified wait queue when a wait table is supplied.

The driver should register the relevant wait queues before checking the current readiness state. This ordering helps avoid missing an event that occurs while the readiness condition is being checked.

Wait Queue Declaration

static DECLARE_WAIT_QUEUE_HEAD(my_wait_queue);

Waking Waiting Processes

wake_up_interruptible(&my_wait_queue);

When data becomes available, or buffer space becomes available, the driver wakes the relevant wait queue.

Wait Queue Operation

9. Implementing .poll in a Character Driver

Consider a memory-backed character device with a shared data buffer.

Assume the driver maintains:

  • data_available: Number of bytes currently available to read.
  • BUFFER_SIZE: Maximum buffer capacity.
  • my_wait_queue: Wait queue used for readiness notification.
  • A mutex to protect shared buffer state.

Step 1: Include Required Headers

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/poll.h>
#include <linux/wait.h>
#include <linux/mutex.h>

Step 2: Declare Shared Resources

#define BUFFER_SIZE 1024

static char device_buffer[BUFFER_SIZE];
static size_t data_available;

static DEFINE_MUTEX(buffer_lock);

static DECLARE_WAIT_QUEUE_HEAD(my_wait_queue);

Step 3: Implement the .poll Callback

static __poll_t my_poll(
    struct file *file,
    struct poll_table_struct *wait)
{
    __poll_t mask = 0;

    /* Register interest in device events. */
    poll_wait(file, &my_wait_queue, wait);

    mutex_lock(&buffer_lock);

    /* Data available for reading. */
    if (data_available > 0)
        mask |= EPOLLIN | EPOLLRDNORM;

    /* Space available for writing. */
    if (data_available < BUFFER_SIZE)
        mask |= EPOLLOUT | EPOLLWRNORM;

    mutex_unlock(&buffer_lock);

    return mask;
}

Explanation

  1. The callback starts with an empty readiness mask.
  2. poll_wait() registers the wait queue.
  3. The mutex protects the shared buffer state while checking readiness.
  4. If data exists, the callback reports readable events.
  5. If free space exists, the callback reports writable events.
  6. The callback returns the readiness mask.
This is an illustrative readiness callback. A production driver must coordinate its read(), write(), poll() and wake-up paths around the same state and synchronization rules. The buffer accounting must also match the actual data-consumption and data-production logic.

10. Registering the .poll Callback

Register the callback in the file_operations structure.

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
    .poll    = my_poll,
};

Now applications can monitor the device using poll(), select() or epoll(), provided the driver implements the necessary readiness behavior.

11. Waking Up the Polling Application

Registering a wait queue is not enough. The driver must wake waiting processes when the readiness condition changes.

Example: Data Becomes Available

/* Data has been added to the device buffer. */

wake_up_interruptible(&my_wait_queue);

Example: Buffer Space Becomes Available

/* Data has been removed from the device buffer. */

wake_up_interruptible(&my_wait_queue);

After waking, the polling mechanism checks readiness again by invoking the driver's poll operation as appropriate.

The wake-up should occur after the state change has been made visible using the driver's synchronization rules. Waking a process does not itself guarantee that the device is readable or writable; the readiness condition must be checked again.

12. User-Space Program Using poll()

The following program monitors a character device for readable and writable events.

Source Code: test_poll.c

#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <fcntl.h>
#include <poll.h>
#include <errno.h>

int main(void)
{
    int fd;
    int ret;

    struct pollfd pfd;

    fd = open("/dev/mychardev",
              O_RDWR | O_NONBLOCK);

    if (fd < 0) {
        perror("open");
        return 1;
    }

    pfd.fd = fd;
    pfd.events = POLLIN | POLLOUT;
    pfd.revents = 0;

    printf("Waiting for device readiness...\n");

    ret = poll(&pfd, 1, 5000);

    if (ret < 0) {
        perror("poll");
        close(fd);
        return 1;
    }

    if (ret == 0) {
        printf("Poll timeout expired.\n");
    } else {
        printf("Events reported: 0x%x\n",
               pfd.revents);

        if (pfd.revents & POLLIN)
            printf("Device is readable.\n");

        if (pfd.revents & POLLOUT)
            printf("Device is writable.\n");

        if (pfd.revents & POLLERR)
            printf("Device error reported.\n");

        if (pfd.revents & POLLHUP)
            printf("Device hangup reported.\n");

        if (pfd.revents & POLLNVAL)
            printf("Invalid file descriptor.\n");
    }

    close(fd);

    return 0;
}

Compile

gcc test_poll.c -o test_poll

Run

sudo ./test_poll

The program waits for up to five seconds for readiness events.

The actual result depends on the device driver's implementation and current buffer state.

13. poll() vs select() vs epoll()

Linux provides three commonly used readiness notification interfaces.

Feature poll() select() epoll()
Purpose Monitor multiple file descriptors. Monitor multiple file descriptors. Monitor large sets of file descriptors efficiently.
Descriptor input Array of pollfd structures. fd_set bitmaps. Kernel-managed interest list.
Timeout Milliseconds. timeval structure. Milliseconds in epoll_wait().
Typical use Moderate descriptor sets. Small descriptor sets or existing applications. Applications managing many connections.
Descriptor limit No fixed FD_SETSIZE bitmap limit. Limited by FD_SETSIZE in common implementations. Not limited by FD_SETSIZE.

Important Functions

poll()
select()

epoll_create1()
epoll_ctl()
epoll_wait()

The .poll callback in a device driver supplies readiness information that can be used by these interfaces. It is not a replacement for the user-space poll() system call.

14. Relationship Between poll() and O_NONBLOCK

Readiness notification and nonblocking I/O are related but separate concepts.

  • poll() reports whether an operation can proceed without blocking at the time readiness is checked.
  • O_NONBLOCK changes how subsequent I/O operations behave when they cannot proceed immediately.
  • The driver must implement correct nonblocking behavior in its read() and write() callbacks.
  • Readiness can change between poll() returning and the application performing I/O.
  • Applications must handle partial I/O and retry conditions such as EAGAIN.
Race consideration: Readiness is a snapshot, not a guarantee that the next operation will complete fully. Another process may consume data or buffer space before the application performs I/O.

15. Common Mistakes in poll() Implementation

MistakeProblem

16. Practical Applications

  • Serial communication drivers waiting for incoming data.
  • Sensor drivers reporting when new samples are available.
  • Communication devices managing receive and transmit buffers.
  • Character drivers supporting event-driven user applications.
  • Drivers that need to notify applications about device readiness or hangup conditions.

For hardware-specific exercises, a suitable physical device or supported emulator is required. A standard Ubuntu VirtualBox environment can be used to learn the polling API with software-only character drivers, but it does not automatically provide access to physical GPIO, I2C or SPI peripherals.

17. Lesson Summary

  • poll() is a user-space system call for monitoring file descriptor readiness.
  • The .poll callback is implemented by a device driver.
  • poll_wait() registers the relevant wait queue.
  • Wait queues allow applications to sleep until readiness changes.
  • wake_up_interruptible() can wake waiting processes.
  • POLLIN indicates readable data and POLLOUT indicates writable capacity.
  • O_NONBLOCK must be supported by the driver's I/O callbacks.
  • select(), poll() and epoll() are user-space readiness notification interfaces.
  • Readiness can change before the application performs the actual I/O.
