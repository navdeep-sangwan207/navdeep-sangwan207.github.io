Chapter 9: File Operations and User-Kernel Data Transfer

Home Course Chapter 9
Lesson 5: release() and Driver Release Callback
Level: Intermediate
Prerequisites: open(), read(), write(), struct file and file_operations.
Objective: Understand how a driver handles the final release of an open-file description and how per-open resources are cleaned up.

1. Introduction

When an application finishes using a file or device, it normally calls the close() system call.

For a character device, the driver's .release callback provides an opportunity to free resources associated with the open-file description.

A driver may allocate memory, create per-open state or acquire resources during its .open callback. The release callback can clean up those resources.

Common Applications

  • Freeing per-open kernel memory.
  • Releasing exclusive-access state.
  • Cleaning up private data.
  • Releasing per-open buffers.
  • Recording when an open instance is finished.

2. What Is close()?

The close() system call closes a file descriptor in a user-space process.

Header File

#include <unistd.h>

Function Prototype

int close(int fd);

Example

int fd;

fd = open("/dev/mychardev", O_RDONLY);

if (fd < 0) {
    perror("open");
    return 1;
}

close(fd);

When the descriptor is closed, the kernel releases that descriptor's reference to the associated open-file description.

3. What Is the .release Callback?

The .release callback is a member of struct file_operations.

It is called when the open-file description is finally released, allowing the driver to clean up resources associated with it.

Function Prototype

static int my_release(
    struct inode *inode,
    struct file *file
);

Parameters

Parameter Description
inode Represents the device inode associated with the opened file.
file Represents the open-file description being released.

Return Value

The callback returns an integer. Normally, it returns zero after successful cleanup. 

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

4. Registering the Release Callback

The release callback is registered using the .release member of the file operations structure. 

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

When the open-file description is finally released, the kernel invokes the registered callback.

5. Difference Between close() and .release

These two operations are related, but they are not identical.

close() .release
User-space system call. Kernel driver callback.
Closes a file descriptor. Cleans up the final open-file description.
Can be called by an application. Invoked by the kernel when the open-file description is finally released.
Returns 0 or -1 to user space. Returns an integer to the kernel.
Important: .release is not necessarily called for every close() operation. If multiple file descriptors refer to the same open-file description, the final release happens only after the last reference is closed.

6. Understanding the Open-File Description

A file descriptor is a process-level reference to an open-file description. The open-file description stores information such as file status flags and the current file offset.

User Process
↓
File Descriptor 3
↓
Open-File Description
struct file
↓
Driver File Operations

When a file descriptor is duplicated using dup() or inherited through fork(), multiple descriptors may refer to the same open-file description.

Example

int fd1, fd2;

fd1 = open("/dev/mychardev", O_RDONLY);

fd2 = dup(fd1);

close(fd1);

/* fd2 still refers to the same
   open-file description. */

close(fd2);

/* The open-file description can
   now be finally released. */

In this example, closing fd1 does not immediately cause the final release because fd2 still references the same open-file description.

7. Difference Between .flush and .release

The .flush callback is another member of struct file_operations.

It is associated with closing a file descriptor. Unlike .release, it can be invoked for individual close operations even when other descriptors still refer to the same open-file description.

Feature .flush .release
Purpose Handle close-related processing. Final cleanup of the open-file description.
Invocation Can run on individual close operations. Runs when the open-file description is finally released.
Return type int int
Typical use Close-related checks or reporting errors. Freeing per-open resources. 
static int my_flush(struct file *file,
                    fl_owner_t id)
{
    pr_info("flush callback invoked\n");
    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("release callback invoked\n");
    return 0;
}
.flush and .release serve different purposes. Do not free per-open resources in .flush if other descriptors may still use the same open-file description.

8. Using file->private_data

The private_data member of struct file allows a driver to store a pointer to per-open state.

A driver can allocate memory in its open callback and release it in its release callback.

Open Callback

#include <linux/slab.h>

struct device_private {
    int read_count;
    int write_count;
};

static int my_open(struct inode *inode,
                   struct file *file)
{
    struct device_private *private;

    private = kzalloc(sizeof(*private),
                      GFP_KERNEL);

    if (!private)
        return -ENOMEM;

    file->private_data = private;

    pr_info("Device opened\n");

    return 0;
}

Release Callback

static int my_release(struct inode *inode,
                      struct file *file)
{
    struct device_private *private;

    private = file->private_data;

    kfree(private);
    file->private_data = NULL;

    pr_info("Device released\n");

    return 0;
}

Explanation

  1. open() allocates memory using kzalloc().
  2. The memory is initialized to zero.
  3. The pointer is stored in file->private_data.
  4. Read and write callbacks can access this private state.
  5. When the open-file description is finally released, .release frees the memory.
  6. The pointer is set to NULL after cleanup.

9. Understanding Per-Open Resources

A character device can be opened by multiple processes. Each independent open operation normally creates a separate open-file description.

If the driver allocates private data for each open, every open-file description has its own private state.

Character Device
↓
Process A: open()
struct file A
private_data A
Process B: open()
struct file B
private_data B
↓
Each open-file description has independent private state

This is useful for maintaining per-client information such as counters, configuration values and temporary buffers.

10. Exclusive Device Access

Some devices should allow only one independent open operation at a time.

An atomic variable can be used to control exclusive access. 

#include <linux/atomic.h>

static atomic_t device_opened = ATOMIC_INIT(0);

static int my_open(struct inode *inode,
                   struct file *file)
{
    if (atomic_cmpxchg(&device_opened, 0, 1))
        return -EBUSY;

    pr_info("Exclusive device opened\n");

    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    atomic_set(&device_opened, 0);

    pr_info("Exclusive device released\n");

    return 0;
}

Explanation

  • Initial state is zero, meaning no exclusive open is active.
  • atomic_cmpxchg() changes zero to one if the previous value was zero.
  • If another independent open attempts access while the value is one, the callback returns -EBUSY.
  • The final release resets the variable to zero.
This simple pattern assumes the module and device have a suitable lifetime and cleanup model. Production drivers must also consider device removal, active users and resource ownership.

11. Complete Character Driver Example

The following example registers a character device and implements open and release callbacks. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/slab.h>

#define DEVICE_NAME "releasechardev"

struct device_private {
    int session_id;
};

static dev_t dev;
static struct cdev my_cdev;
static int session_counter;

static int my_open(struct inode *inode,
                   struct file *file)
{
    struct device_private *private;

    private = kzalloc(sizeof(*private),
                      GFP_KERNEL);

    if (!private)
        return -ENOMEM;

    private->session_id = ++session_counter;
    file->private_data = private;

    pr_info("releasechardev: opened session %d\n",
            private->session_id);

    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    struct device_private *private;

    private = file->private_data;

    if (private) {
        pr_info("releasechardev: released session %d\n",
                private->session_id);

        kfree(private);
        file->private_data = NULL;
    }

    return 0;
}

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
    .release = my_release,
};

static int __init my_driver_init(void)
{
    int ret;

    ret = alloc_chrdev_region(&dev, 0, 1,
                              DEVICE_NAME);

    if (ret < 0)
        return ret;

    cdev_init(&my_cdev, &my_fops);
    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev, 1);

    if (ret < 0) {
        unregister_chrdev_region(dev, 1);
        return ret;
    }

    pr_info("releasechardev: registered\n");
    pr_info("releasechardev: major=%u minor=%u\n",
            MAJOR(dev), MINOR(dev));

    return 0;
}

static void __exit my_driver_exit(void)
{
    cdev_del(&my_cdev);
    unregister_chrdev_region(dev, 1);

    pr_info("releasechardev: unregistered\n");
}

module_init(my_driver_init);
module_exit(my_driver_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Character Driver Release Callback Example");
This example registers a cdev but does not create a /dev node. Create a temporary node using the major and minor numbers printed in the kernel log. The .owner field helps prevent ordinary module unloading while active file operations hold module references.

14. Create the Device Node and Test

Suppose the module reports major number 240 and minor number 0.

Create Device Node

sudo mknod /dev/releasechardev c 240 0

Replace 240 with the actual major number reported by the driver.

Set Permissions

sudo chmod 666 /dev/releasechardev

Open and Close the Device

cat /dev/releasechardev

The example has no read callback, so it is intended to demonstrate open and release behavior rather than return data.

A small open/close test program can be used instead: 

#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>

int main(void)
{
    int fd;

    fd = open("/dev/releasechardev", O_RDONLY);

    if (fd < 0) {
        perror("open");
        return 1;
    }

    printf("Device opened successfully\n");

    close(fd);

    printf("Device closed successfully\n");

    return 0;
}

Compile and Run

sudo ./open_close_test

Inspect Kernel Messages

sudo dmesg | tail -20

Expected messages include:

make clean

15. Module Unloading and Resource Management

A driver must manage its resources carefully when the device is being removed or the module is unloaded.

The cdev_del() function prevents new opens through that cdev registration. It does not automatically terminate existing open file descriptors.

The driver must ensure that resources used by active operations remain valid until they are no longer needed.

  • Free per-open allocations in .release.
  • Prevent new operations during device removal.
  • Coordinate active operations with removal.
  • Release device-number allocations during cleanup.
  • Do not free shared resources while active callbacks still use them.
The .owner = THIS_MODULE field in file_operations supports module reference management. It helps prevent normal module unloading while active file operations hold references.

16. Common Mistakes

Mistake Correct Approach
Assuming .release runs for every close(). Understand open-file description reference counting.
Freeing memory in .flush without considering shared descriptors. Use .release for final per-open cleanup.
Forgetting to free private_data. Release allocated memory in .release.
Freeing shared device resources too early. Coordinate cleanup with active users and callbacks.
Registering .release incorrectly. Use the .release member in file_operations.
Assuming module unloading calls .release for every open file. Manage open references and module lifetime correctly.

17. Summary

  • close() is a user-space system call.
  • .release is a kernel driver callback.
  • .release is called when the open-file description is finally released.
  • Multiple descriptors can refer to the same open-file description.
  • .flush and .release have different invocation behavior.
  • file->private_data stores per-open driver state.
  • kzalloc() can allocate per-open memory.
  • kfree() can release allocated memory.
  • Drivers must carefully manage resource lifetime during device removal.
