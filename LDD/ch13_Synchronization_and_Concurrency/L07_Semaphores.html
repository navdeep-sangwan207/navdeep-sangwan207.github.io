2. Introduction to Semaphores

A semaphore is a synchronization mechanism that uses a counter to control access to a shared resource or to coordinate execution between tasks.

The semaphore counter represents the number of available permits.

A task obtains a permit before proceeding. If no permit is available, the task waits until another task releases one.

Why Are Semaphores Required?

Consider a system with three identical hardware resources that can be used by different tasks.

  • Task A requests a resource.
  • Task B requests another resource.
  • Task C requests the third resource.
  • Task D must wait because all three resources are occupied.

A counting semaphore initialized to 3 can represent the availability of these resources.

Counting Semaphore = 3
↓
Task A obtains permit → 2
↓
Task B obtains permit → 1
↓
Task C obtains permit → 0
↓
Task D waits for a permit
↓
A task releases a permit → Task D may proceed

3. Semaphore Fundamentals

A semaphore maintains an integer-like count representing available permits.

Two fundamental operations are:

  • Wait operation: Obtains a permit. If none is available, the calling task waits.
  • Signal operation: Releases a permit, potentially waking a waiting task.

In the Linux kernel semaphore API, these operations are commonly represented by down() and up().

Basic Concept

down(&my_sem);

/* Use the protected resource */

up(&my_sem);

The down() operation decrements the semaphore count when a permit is available. If no permit is available, the calling task waits.

The up() operation releases a permit and can wake a waiting task.

4. Types of Semaphores

4.1 Binary Semaphore

A binary semaphore is a semaphore conceptually used with a count of either 0 or 1.

  • Count 1: One permit is available.
  • Count 0: No permit is available.

It can be used to coordinate access to a single resource or synchronize task execution.

Binary Semaphore = 1
↓
Task A obtains permit
↓
Semaphore = 0
↓
Task B waits
↓
Task A releases permit
↓
Task B may proceed

4.2 Counting Semaphore

A counting semaphore can represent multiple available instances of a resource.

For example, a semaphore initialized to 4 allows up to four successful acquisitions before additional tasks must wait.

Semaphore count = 4
↓
Task A obtains permit → 3
↓
Task B obtains permit → 2
↓
Task C obtains permit → 1
↓
Task D obtains permit → 0
↓
Task E must wait

Comparison

Feature Binary Semaphore Counting Semaphore
Conceptual count 0 or 1 Non-negative permit count
Purpose Single-resource coordination Multiple-resource management
Initial count Usually 0 or 1 Number of available resources
Concurrent permit holders At most one Up to the available permit count
Binary and counting semaphores are conceptual categories. Linux's struct semaphore is a counting semaphore; initialize it with a count of 1 if a single permit is required. For ordinary exclusive ownership in modern driver code, prefer a mutex when its ownership semantics are appropriate.

5. Linux Kernel Semaphore Data Type

Linux provides struct semaphore to represent a semaphore.

Include the following header:

#include <linux/semaphore.h>

Static Declaration and Initialization

static DEFINE_SEMAPHORE(my_sem);

In current Linux kernels, DEFINE_SEMAPHORE() initializes a semaphore with an initial count of 1.

Dynamic Initialization

static struct semaphore my_sem;

static int __init my_init(void)
{
    sema_init(&my_sem, 3);

    return 0;
}

sema_init() initializes the semaphore with the specified initial count.

In this example, three permits are available initially.

Semaphore initialization interfaces can vary across kernel versions. Check the semaphore header and documentation for the target kernel. The example uses the current two-argument DEFINE_SEMAPHORE() form.

6. Semaphore Operations

6.1 down()

Obtains a semaphore permit. If the count is zero, the task waits until a permit becomes available.

down(&my_sem);

/* Critical section or resource use */

up(&my_sem);

6.2 up()

Releases a permit. If tasks are waiting, the kernel may wake one of them.

up(&my_sem);

6.3 down_interruptible()

Attempts to obtain a permit, but allows the waiting operation to be interrupted by a signal.

int ret;

ret = down_interruptible(&my_sem);

if (ret) {
    return ret;
}

/* Use the resource */

up(&my_sem);

On success, it returns 0. If interrupted, it returns a negative error value, commonly -EINTR.

6.4 down_trylock()

Attempts to obtain a permit without waiting.

if (down_trylock(&my_sem)) {

    pr_info("No permit available\n");

} else {

    pr_info("Permit acquired\n");

    up(&my_sem);
}

Unlike many kernel trylock APIs, down_trylock() returns 0 on success and non-zero when acquisition fails.

6.5 down_killable()

Allows a waiting task to be interrupted by fatal signals.

int ret;

ret = down_killable(&my_sem);

if (ret)
    return ret;

/* Use resource */

up(&my_sem);

Operation Summary

Function Purpose
down() Obtains a permit and waits if necessary.
up() Releases a permit.
down_interruptible() Waits with signal-interruptible behavior.
down_trylock() Attempts immediate acquisition.
down_killable() Waits with fatal-signal interruption behavior.

7. How Semaphore Waiting Works

Suppose a counting semaphore is initialized with a count of 2.

Initial semaphore count = 2
↓
Task A calls down() → count = 1
↓
Task B calls down() → count = 0
↓
Task C calls down() → waits
↓
Task A calls up()
↓
Waiting Task C may be awakened

The semaphore manages the availability of permits. Tasks that cannot obtain a permit wait rather than repeatedly consuming CPU time.

The kernel manages the semaphore's internal state and waiting queue.

8. Semaphore vs Mutex

Although both can provide mutual exclusion in some designs, semaphores and mutexes have different semantics.

Feature Semaphore Mutex
Purpose Permit counting and task coordination Exclusive ownership of a resource
Count Can represent multiple permits Locked or unlocked
Ownership No mutex-style owner requirement Owned by the acquiring task
Release A permit can be released by a different context where the design allows it Must be released by its owner
Waiting Task may sleep Task may sleep
Interrupt context down() cannot be used in interrupt context; up() is non-sleeping and can be used in suitable contexts Not suitable for interrupt context
Typical use Resource pools and task synchronization Protecting shared driver data

Which One Should Be Used?

  • Use a mutex for ordinary exclusive protection of shared data in process context.
  • Use a counting semaphore when multiple resource permits must be managed.
  • Use a semaphore for certain task-coordination patterns when its semantics are appropriate.
  • Use spinlocks for short critical sections that cannot sleep.

9. Semaphore vs Spinlock

Feature Semaphore Spinlock
Waiting mechanism Task may sleep Busy waiting
Can block? Yes No
Can be used in hard interrupt context? down() cannot; up() can be used in suitable contexts Yes, with appropriate locking design
Typical purpose Resource availability and coordination Short critical-section protection
Resource counting Yes No

10. Practical Kernel Module: Binary Semaphore

Let us create a simple module using a semaphore initialized with one permit.

Source Code: semaphore_basic.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/semaphore.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Basic Semaphore Demonstration");
MODULE_VERSION("1.0");

static struct semaphore my_sem;

static int __init semaphore_basic_init(void)
{
    int ret;

    sema_init(&my_sem, 1);

    pr_info("Semaphore module loaded\n");

    ret = down_interruptible(&my_sem);

    if (ret) {
        pr_err("Semaphore acquisition interrupted\n");
        return ret;
    }

    pr_info("Semaphore acquired successfully\n");

    up(&my_sem);

    pr_info("Semaphore released successfully\n");

    return 0;
}

static void __exit semaphore_basic_exit(void)
{
    pr_info("Semaphore module unloaded\n");
}

module_init(semaphore_basic_init);
module_exit(semaphore_basic_exit);

Explanation

  1. linux/semaphore.h provides semaphore interfaces.
  2. sema_init() initializes the semaphore with one permit.
  3. down_interruptible() attempts to acquire the permit.
  4. If acquisition succeeds, the module prints a success message.
  5. up() releases the permit.

Makefile

obj-m += semaphore_basic.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Ensure that the recipe commands begin with actual tab characters.

Compile and Test in Ubuntu

make

sudo insmod semaphore_basic.ko

lsmod | grep semaphore_basic

sudo dmesg | tail -20

sudo rmmod semaphore_basic

sudo dmesg | tail -20

make clean

Expected Output

Semaphore module loaded
Semaphore acquired successfully
Semaphore released successfully
Semaphore module unloaded
This example demonstrates initialization and permit acquisition/release. It does not demonstrate contention between multiple tasks because the operations execute sequentially during module initialization.

11. Practical Kernel Module: Counting Semaphore

Now consider a resource pool with three available permits.

Source Code: counting_semaphore.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/semaphore.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Counting Semaphore Demonstration");
MODULE_VERSION("1.0");

static struct semaphore resource_sem;

static int __init counting_sem_init(void)
{
    int i;
    int ret;

    sema_init(&resource_sem, 3);

    pr_info("Counting semaphore module loaded\n");

    for (i = 0; i < 3; i++) {

        ret = down_interruptible(&resource_sem);

        if (ret) {
            pr_err("Semaphore acquisition failed\n");

            while (i > 0) {
                up(&resource_sem);
                i--;
            }

            return ret;
        }

        pr_info("Resource permit %d acquired\n", i + 1);
    }

    pr_info("Three permits acquired\n");

    for (i = 0; i < 3; i++) {
        up(&resource_sem);
    }

    pr_info("All permits released\n");

    return 0;
}

static void __exit counting_sem_exit(void)
{
    pr_info("Counting semaphore module unloaded\n");
}

module_init(counting_sem_init);
module_exit(counting_sem_exit);

Expected Output

Counting semaphore module loaded
Resource permit 1 acquired
Resource permit 2 acquired
Resource permit 3 acquired
Three permits acquired
All permits released
Counting semaphore module unloaded

The semaphore starts with three permits. The module obtains all three and then releases them.

The example demonstrates permit counting sequentially. In a real resource-pool implementation, each successful acquisition must correspond to actual resource ownership, and the permit must be returned when that resource is released.

12. Semaphores in Device Drivers

Semaphores can be useful in device drivers for resource management and task coordination.

Example Applications

  • Limiting concurrent access to a fixed number of software resources.
  • Managing a pool of reusable buffers.
  • Controlling access to a limited number of device channels.
  • Coordinating producer and consumer tasks.
  • Signaling completion or availability between execution contexts.

Conceptual Resource-Pool Example

#include <linux/semaphore.h>

#define AVAILABLE_CHANNELS 4

static struct semaphore channel_sem;

static int initialize_channels(void)
{
    sema_init(&channel_sem, AVAILABLE_CHANNELS);

    return 0;
}

static int acquire_channel(void)
{
    return down_interruptible(&channel_sem);
}

static void release_channel(void)
{
    up(&channel_sem);
}

Here, up to four permits can be acquired. A fifth task must wait until a permit is returned.

The semaphore controls the number of permits, but it does not identify which physical channel or buffer belongs to a task. A real driver must separately allocate, track and release the corresponding resource correctly.

13. Semaphore in Producer-Consumer Synchronization

The producer-consumer problem is a classical synchronization problem.

  • The producer creates data.
  • The consumer processes data.
  • The producer and consumer share a buffer.
  • The system must coordinate available and occupied buffer slots.

For a buffer with N slots, two counting semaphores can represent:

  • empty: Number of available buffer slots.
  • full: Number of occupied buffer slots.
Producer creates data
↓
Wait for empty slot
↓
Insert data into buffer
↓
Signal full slot
Consumer waits for full slot
↓
Remove data from buffer
↓
Signal empty slot

Conceptual Pseudocode

empty = N;
full  = 0;

/* Producer */
down(&empty);

/* Insert item into buffer */

up(&full);

/* Consumer */
down(&full);

/* Remove item from buffer */

up(&empty);

This pseudocode explains the permit relationship. A real producer-consumer implementation also needs appropriate protection for the shared buffer indexes and data structure, such as a spinlock or mutex selected according to the execution context.

14. Important Rules for Semaphore Usage

  1. Initialize a semaphore before using it.
  2. Use down() or a suitable variant to acquire a permit.
  3. Use up() to release a permit.
  4. Do not call blocking down() operations in interrupt context.
  5. Do not sleep while holding a spinlock, even if a semaphore is also used in the function.
  6. Ensure permits are released on all appropriate error and exit paths.
  7. Do not release more permits than the resource-management design permits.
  8. Do not assume a semaphore has mutex-style ownership.
  9. Use a mutex instead when exclusive task ownership is the actual requirement.
An incorrect number of up() operations can allow more tasks to proceed than the available resource capacity. Carefully match permit acquisition and release to resource allocation and cleanup.

15. Common Semaphore Mistakes

Mistake Why It Is Wrong
Using down() in interrupt context. It can block, but interrupt handlers must not sleep.
Forgetting to call up(). A permit remains unavailable and other tasks may wait indefinitely.
Calling up() too many times. The semaphore count may no longer represent actual resource availability.
Using a semaphore as if it had mutex ownership. Semaphores do not enforce mutex-style owner-only unlocking.
Using a binary semaphore for ordinary exclusive task ownership without considering mutex semantics. A mutex provides more appropriate ownership and debugging semantics.
Protecting a shared buffer only with a resource-count semaphore. Permit counting does not automatically protect buffer indexes or related data.
Ignoring interrupted acquisition. The code may proceed without successfully acquiring a permit.

16. Debugging Semaphore Problems

Kernel logs can help investigate semaphore-related problems.

sudo dmesg | tail -50

sudo journalctl -k -n 50

Lock debugging facilities such as lockdep may help identify certain synchronization and locking problems, depending on kernel configuration.

When investigating a semaphore issue, check:

  • Whether the semaphore was initialized correctly.
  • Whether each successful acquisition has a corresponding release.
  • Whether an interrupted wait is handled correctly.
  • Whether a blocking operation is being called from an invalid context.
  • Whether the semaphore count accurately represents available resources.

  • down() obtains a permit.
  • up() releases a permit.
  • down_interruptible() supports signal-interruptible waiting.
  • down_trylock() attempts immediate acquisition.
