Prerequisites: Kernel synchronization, concurrency, shared resources and critical sections.

Objective: Understand how race conditions occur, identify common driver scenarios and learn techniques to prevent unsafe concurrent access.

1. Introduction

A Linux device driver may be accessed by several execution paths at the same time.

For example:

  • Two user processes may access the same character device.
  • A process may update device data while an interrupt handler reads it.
  • A workqueue callback may access data also used by a file operation.
  • Two CPUs may execute driver code simultaneously.

If these execution paths access shared data without proper synchronization, a race condition may occur.

A race condition is a concurrency bug in which the result depends on the timing or ordering of operations.

2. What Is a Race Condition?

A race condition occurs when multiple execution paths access shared data and at least one access modifies that data without adequate synchronization.

Simple Example

static int counter = 0;

static void increment_counter(void)
{
    counter++;
}

The statement counter++ is a read-modify-write operation. It is not guaranteed to be atomic merely because it appears as one C statement.

Conceptually, the operation involves:

  1. Read the current counter value.
  2. Calculate the new value.
  3. Write the new value back.

Another execution path can interfere between these steps.

3. How Does a Race Condition Occur?

Assume the shared counter initially contains 5. Two processes attempt to increment it.

Step Process A Process B Counter
1 Reads counter = 5 – 5
2 – Reads counter = 5 5
3 Calculates 6 – 5
4 – Calculates 6 5
5 Writes 6 – 6
6 – Writes 6 6

The expected final value is 7, but the actual value is 6.

This is known as a lost update.

The example illustrates one possible interleaving. Actual instruction ordering depends on compiler output, processor behavior and scheduling.

4. Types of Race Conditions

4.1 Read-Write Race

One execution path reads a variable while another modifies it. The reader may observe an outdated or inconsistent value.

4.2 Write-Write Race

Two execution paths modify the same variable without coordination. One update may overwrite another.

4.3 Check-Then-Act Race

A driver checks a condition and then performs an operation, but another execution path changes the condition between the check and the action.

4.4 Use-After-Free Race

One execution path releases memory while another still accesses the object.

4.5 Initialization Race

A device or data structure becomes visible to other execution paths before initialization is complete.

5. Race Conditions in Character Drivers

Character drivers often maintain shared buffers and device state.

Consider this structure:

struct my_device {
    char buffer[1024];
    size_t data_length;
    int device_status;
};

Possible concurrent operations include:

  • Process A writes data into the buffer.
  • Process B reads the buffer.
  • An interrupt handler updates device status.
  • A workqueue callback processes received data.

If these operations are not coordinated, the driver may expose incomplete data, corrupt its buffer or read an inconsistent status value.

6. Race Conditions Between Process and Interrupt Context

A driver may share data between a normal process-context function and an interrupt handler.

Example Scenario

  • A process-context function updates a device status variable.
  • An interrupt handler reads or changes the same variable.
  • An interrupt occurs while the process is modifying the data.

The driver must select a synchronization mechanism that is valid in both contexts.

A mutex cannot be acquired in a hard interrupt handler because mutex acquisition may sleep. For short shared-data protection between process and hard-IRQ contexts, a suitable spinlock and IRQ-safe locking pattern may be required.

7. Race Conditions on Multicore Systems

On a multicore processor, different execution paths can run simultaneously on different CPU cores.

CPU 0
CPU 1
↓
Shared Memory
↓
Concurrent Access

For example, CPU 0 may increment a driver counter while CPU 1 reads or modifies it.

Disabling interrupts on CPU 0 does not stop CPU 1 from accessing the same memory.

Therefore, the driver needs an appropriate cross-CPU synchronization mechanism.

8. Race Condition Example: Check-Then-Act

Suppose a driver maintains a flag indicating whether a device is available.

Unsafe Concept

if (device_available) {
    device_available = 0;

    /* Start using the device */
}

Two processes may both observe device_available as 1 before either changes it to 0. Both may then attempt to use the device.

The check and update must be protected as one coordinated operation.

Protected Concept Using a Mutex

static DEFINE_MUTEX(device_lock);
static int device_available = 1;

static int acquire_device(void)
{
    int result = 0;

    mutex_lock(&device_lock);

    if (device_available)
        device_available = 0;
    else
        result = -EBUSY;

    mutex_unlock(&device_lock);

    return result;
}

This example is suitable only for process-context callers that may sleep. It demonstrates how the check and update are protected together.

9. Preventing Race Conditions

Linux provides several synchronization mechanisms to prevent unsafe concurrent access.

Mechanism Typical Application
Atomic operations Simple atomic counter and bit operations.
Spinlocks Short critical sections in atomic contexts.
Mutexes Longer process-context critical sections where sleeping is allowed.
Semaphores Coordination of access to a limited resource.
Read-write locks Data with multiple readers and exclusive writers.
RCU Read-mostly data structures with specialized update and reclamation rules.

The mechanism must match the execution contexts and the data access pattern.

10. Atomic Operations for Shared Counters

For a simple counter, Linux provides atomic types and operations.

Example

#include <linux/atomic.h>

static atomic_t device_counter = ATOMIC_INIT(0);

static void increment_counter(void)
{
    atomic_inc(&device_counter);
}

static int get_counter(void)
{
    return atomic_read(&device_counter);
}

atomic_inc() performs an atomic increment, and atomic_read() reads the value.

Atomic operations protect the specific operation they provide. They do not automatically protect a larger sequence of related operations or provide every required ordering guarantee.

11. Mutex-Based Protection

A mutex provides mutual exclusion for code that executes in a context where sleeping is allowed.

Example

#include <linux/mutex.h>

static DEFINE_MUTEX(data_lock);
static int shared_value;

static void update_shared_value(void)
{
    mutex_lock(&data_lock);

    shared_value++;

    mutex_unlock(&data_lock);
}

Only one task at a time can hold this mutex. Other tasks that attempt to acquire it may sleep until it becomes available.

Do not use a mutex in hard interrupt or other atomic context.

12. Spinlock-Based Protection

A spinlock protects a critical section without sleeping while waiting for the lock.

Example

#include <linux/spinlock.h>

static DEFINE_SPINLOCK(data_lock);
static int shared_value;

static void update_shared_value(void)
{
    unsigned long flags;

    spin_lock_irqsave(&data_lock, flags);

    shared_value++;

    spin_unlock_irqrestore(&data_lock, flags);
}

This pattern is commonly used when shared data may also be accessed by a local hard interrupt handler.

The interrupt-safe locking pattern prevents the local interrupt handler from interrupting the protected process-context critical section and attempting to acquire the same lock.

Keep spinlock-protected sections very short. Do not sleep, perform blocking operations or call functions that may sleep while holding a spinlock.

13. Race Conditions During Memory Release

One of the most dangerous driver bugs occurs when memory is freed while another execution path still uses it.

Unsafe Scenario

  1. A driver allocates a device-private structure.
  2. A workqueue callback receives a pointer to that structure.
  3. The device is removed and the structure is freed.
  4. The workqueue callback later accesses the freed structure.

This can cause a use-after-free error.

Safer Teardown Sequence

Stop New Operations
↓
Stop Hardware / Disable Interrupts
↓
Synchronize and Cancel Deferred Work
↓
Release References
↓
Free Memory

The exact teardown order depends on the driver architecture. The essential requirement is that no execution path can access an object after it has been freed.

14. Double-Free and Race Conditions

A double-free occurs when the same memory allocation is released more than once.

Concurrent cleanup paths can accidentally cause this problem if ownership is not clearly defined.

Example of Incorrect Ownership

/* Path A */
kfree(buffer);

/* Path B */
kfree(buffer);

If both paths release the same allocation, the driver may corrupt allocator state or trigger a kernel fault.

Prevention

  • Define one clear owner for each allocation.
  • Coordinate cleanup paths.
  • Ensure asynchronous operations are stopped before freeing shared objects.
  • Use reference counting when multiple independent users share an object's lifetime.
  • Do not assume setting a pointer to NULL alone makes concurrent cleanup safe.

15. How to Identify Race Conditions

Race conditions can be difficult to reproduce because they depend on timing and scheduling.

Common Symptoms

  • Unexpected counter values.
  • Corrupted device buffers.
  • Intermittent driver failures.
  • Unexpected kernel warnings or crashes.
  • Incorrect device state.
  • Use-after-free reports.
  • Problems that occur only under heavy load.

Useful Kernel Tools

Tool Purpose
Lockdep Detects certain locking errors and potential deadlocks.
KCSAN Kernel concurrency sanitizer that detects many data races.
KASAN Detects many memory-safety errors, including use-after-free.
ftrace Traces kernel events and execution behavior.
printk() / pr_info() Provides diagnostic messages, although logging alone cannot prove race freedom.

16. Practical Example: Kernel Module with Atomic Counter

This module demonstrates an atomic counter. It does not create a real hardware device. It is suitable for basic testing in Ubuntu VirtualBox.

Source File: race_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/atomic.h>

static atomic_t device_counter = ATOMIC_INIT(0);

static int __init race_demo_init(void)
{
    atomic_inc(&device_counter);
    atomic_inc(&device_counter);

    pr_info("Atomic counter = %d\n",
            atomic_read(&device_counter));

    return 0;
}

static void __exit race_demo_exit(void)
{
    pr_info("Race demonstration module removed\n");
}

module_init(race_demo_init);
module_exit(race_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Atomic counter demonstration");
MODULE_AUTHOR("NS Learning Hub");

Makefile

obj-m += race_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test

make

sudo insmod race_demo.ko

sudo dmesg | tail -n 20

sudo rmmod race_demo

make clean

Illustrative Output

Atomic counter = 2
Race demonstration module removed

This simple module demonstrates atomic operations, not an actual race between competing threads. A later practical exercise can introduce concurrent kernel threads to test shared-state protection.

17. Best Practices to Avoid Race Conditions

  1. Identify every shared variable and shared data structure.
  2. Document which execution paths can access each resource.
  3. Use atomic operations for suitable simple atomic updates.
  4. Use mutexes for process-context operations that may sleep.
  5. Use spinlocks for short critical sections in atomic contexts.
  6. Protect check-and-update sequences as one operation.
  7. Keep interrupt handlers short.
  8. Synchronize workqueues, timers and interrupts during cleanup.
  9. Define clear ownership and lifetime rules for allocated memory.
  10. Use lockdep and KCSAN where available during development.

18. Lesson Summary

  • A race condition occurs when concurrent execution paths access shared data without adequate synchronization.
  • A lost update is a common result of an unsafe read-modify-write operation.
  • Character drivers, interrupt handlers and workqueues can share data.
  • Multicore processors increase the possibility of simultaneous access.
  • Atomic operations protect specific atomic updates.
  • Mutexes protect process-context critical sections where sleeping is allowed.
  • Spinlocks protect short critical sections in atomic contexts.
  • Memory lifetime and cleanup must also be synchronized.
  • KCSAN and lockdep help detect concurrency problems.
