Chapter: Synchronization and Concurrency

Lesson: 3 – Critical Sections

Prerequisites: Kernel synchronization, concurrency, race conditions and shared resources.

Objective: Understand critical sections, mutual exclusion, protected code regions and their implementation in Linux device drivers.

1. Introduction

A Linux device driver often contains code that accesses shared data structures, buffers, counters and device state.

When multiple execution paths access the same data concurrently, the data may become inconsistent unless access is properly controlled.

A critical section is a section of code that accesses shared resources and requires protection against unsafe concurrent access.

Synchronization mechanisms such as mutexes, spinlocks and atomic operations are used to protect critical sections.

Process A
Process B
↓
Shared Resource
↓
Protected Critical Section

2. What Is a Critical Section?

A critical section is a portion of a program where shared data or resources are accessed or modified.

Examples include:

  • Incrementing a shared device counter.
  • Updating a device status variable.
  • Reading or modifying a shared character-device buffer.
  • Adding or removing entries from a shared queue.
  • Updating driver-private data structures.
  • Managing shared hardware state.

Example

static int device_counter;

static void update_counter(void)
{
    device_counter++;
}

The increment operation accesses shared data. If several execution paths call it concurrently, it may cause a lost update.

The shared operation therefore needs suitable synchronization.

3. Need for Critical Section Protection

Consider two processes accessing the same device buffer.

  • Process A writes new data.
  • Process B reads the same buffer.
  • Both operations overlap.

Process B might read partially updated data if the driver does not coordinate access.

Problems Without Protection

  1. Race conditions.
  2. Data corruption.
  3. Lost updates.
  4. Inconsistent device status.
  5. Unexpected driver behavior.
  6. Memory-management and object-lifetime errors.
A critical section should be protected whenever concurrent access could violate the correctness of the shared data or operation.

4. Critical Section Structure

A typical protected critical section follows three stages.

  1. Acquire the synchronization mechanism.
  2. Execute the protected code.
  3. Release the synchronization mechanism.
Acquire Lock
↓
Enter Critical Section
↓
Access Shared Resource
↓
Release Lock

The lock ensures that competing execution paths follow the required access discipline.

5. Critical Section Without Synchronization

Consider a shared counter:

static int counter = 0;

static void increment_counter(void)
{
    counter++;
}

If two CPUs execute this function simultaneously, both may read the same old value and overwrite one another's updates.

Possible Result

Operation Process A Process B Counter
1 Read 10 – 10
2 – Read 10 10
3 Write 11 – 11
4 – Write 11 11

Two increments were requested, but only one was reflected in the final value.

6. Mutual Exclusion

Mutual exclusion ensures that only one execution path at a time can enter a protected region when using an exclusive lock.

Linux provides mechanisms such as mutexes and spinlocks to implement mutual exclusion.

Conceptual Operation

Process A requests lock
↓
Lock acquired by A
↓
Process A enters critical section
↓
A releases lock
↓
Process B can acquire lock

If Process B requests the same lock while A holds it, B must wait or spin depending on the synchronization mechanism.

7. Critical Sections Using Mutexes

A mutex is a sleeping mutual-exclusion mechanism.

It is suitable for protecting critical sections in process context when the calling code is allowed to sleep.

Example

#include <linux/mutex.h>

static DEFINE_MUTEX(counter_mutex);
static int counter = 0;

static void increment_counter(void)
{
    mutex_lock(&counter_mutex);

    counter++;

    mutex_unlock(&counter_mutex);
}

Explanation

  • DEFINE_MUTEX() defines and initializes a static mutex.
  • mutex_lock() acquires the mutex.
  • counter++ executes inside the critical section.
  • mutex_unlock() releases the mutex.
Mutex acquisition may sleep. Do not use mutex_lock() in hard interrupt, softirq or other atomic contexts.

8. Critical Sections Using Spinlocks

A spinlock protects a critical section without sleeping while waiting for the lock.

It is useful for short critical sections that may be accessed from atomic contexts.

Example

#include <linux/spinlock.h>

static DEFINE_SPINLOCK(counter_lock);
static int counter = 0;

static void increment_counter(void)
{
    unsigned long flags;

    spin_lock_irqsave(&counter_lock, flags);

    counter++;

    spin_unlock_irqrestore(&counter_lock, flags);
}

Explanation

  • DEFINE_SPINLOCK() defines a static spinlock.
  • spin_lock_irqsave() acquires the lock and saves the local interrupt state.
  • The shared counter is updated inside the critical section.
  • spin_unlock_irqrestore() releases the lock and restores the saved interrupt state.
Never sleep, perform blocking I/O or call potentially sleeping functions while holding a spinlock.

9. Choosing Between Mutex and Spinlock

Feature Mutex Spinlock
Waiting behavior Task may sleep. CPU spins while waiting.
Sleeping while held Possible, where design permits. Not allowed.
Hard IRQ context Not suitable. Can be used with correct IRQ-safe design.
Typical critical section May be relatively longer. Very short.
Typical application Process-context driver operations. Atomic-context shared-data protection.

The choice must be based on the execution context and the operations performed inside the critical section, not simply on which lock appears faster.

10. Critical Sections and Interrupt Handling

Suppose a process and a hard interrupt handler access the same variable.

A process may acquire a spinlock and then be interrupted locally. If the interrupt handler attempts to acquire the same lock, it can spin forever because the interrupted process cannot resume to release it.

For this type of shared-data design, the process-context code may need to use an IRQ-safe locking operation such as:

unsigned long flags;

spin_lock_irqsave(&my_lock, flags);

/* Short critical section */

spin_unlock_irqrestore(&my_lock, flags);

The interrupt handler uses the matching locking discipline appropriate to its context.

IRQ disabling is local to the CPU. The spinlock provides cross-CPU exclusion. Disabling local interrupts alone is not a replacement for a spinlock when other CPUs can access the shared data.

11. Critical Sections in Character Device Drivers

Consider a character driver that stores data in a shared buffer.

Device Structure

#include <linux/mutex.h>

struct my_device {
    char buffer[1024];
    size_t data_length;
    struct mutex lock;
};

Conceptual Write Operation

mutex_lock(&dev->lock);

/* Update shared buffer and length. */

mutex_unlock(&dev->lock);

Conceptual Read Operation

mutex_lock(&dev->lock);

/* Read consistent buffer data. */

mutex_unlock(&dev->lock);

This demonstrates the protection strategy, not a complete read/write callback. A real driver must also handle user-copy operations, file positions, partial transfers and error conditions.

If an interrupt handler also accesses this buffer, the mutex-only design is insufficient. The driver must redesign the shared-data access and use synchronization suitable for both contexts.

12. Rules for Designing Critical Sections

  1. Identify exactly which data must be protected.
  2. Protect all relevant accesses, not just writes.
  3. Use one consistent locking discipline for each shared resource.
  4. Keep critical sections as short as possible.
  5. Do not call sleeping functions while holding a spinlock.
  6. Avoid unnecessary nested locks.
  7. Maintain a consistent lock acquisition order.
  8. Release locks on every applicable error path.
  9. Do not assume a lock alone solves memory-lifetime problems.
  10. Use lockdep during development where available.

13. Common Mistakes

Mistake Why It Is Incorrect
Using a mutex in a hard IRQ handler Mutex acquisition may sleep.
Sleeping while holding a spinlock Spinlocks must protect non-sleeping critical sections.
Protecting only some accesses Unprotected paths can still race.
Holding a spinlock for too long Other CPUs may waste time spinning.
Forgetting to unlock on an error path Other execution paths may remain blocked.
Assuming local IRQ disabling protects other CPUs Other CPUs can still access shared memory.
Freeing an object while it is still in use Can cause use-after-free even if individual data accesses are locked.

14. Practical Exercise: Mutex-Protected Counter Module

Create a simple kernel module to demonstrate a protected critical section in process context.

Source File: critical_section_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/mutex.h>

static DEFINE_MUTEX(counter_lock);
static int counter;

static void increment_counter(void)
{
    mutex_lock(&counter_lock);

    counter++;

    mutex_unlock(&counter_lock);
}

static int __init critical_demo_init(void)
{
    increment_counter();
    increment_counter();
    increment_counter();

    pr_info("Protected counter = %d\n", counter);

    return 0;
}

static void __exit critical_demo_exit(void)
{
    pr_info("Critical section demo removed\n");
}

module_init(critical_demo_init);
module_exit(critical_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Mutex protected critical section demo");
MODULE_AUTHOR("NS Learning Hub");

Makefile

obj-m += critical_section_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test in Ubuntu

sudo apt update
sudo apt install build-essential linux-headers-$(uname -r)

make

sudo insmod critical_section_demo.ko

sudo dmesg | tail -n 20

sudo rmmod critical_section_demo

make clean

Illustrative Output

Protected counter = 3
Critical section demo removed

This module demonstrates mutex usage, but its initialization function calls the increment function sequentially. It does not simulate competing threads. The mutex becomes important when multiple process-context execution paths access the shared counter concurrently.

15. Lesson Summary

  • A critical section is code that accesses shared resources and requires controlled access.
  • Race conditions can occur when critical sections are not protected.
  • Mutual exclusion prevents competing execution paths from entering an exclusive protected section simultaneously.
  • Mutexes are appropriate for sleepable process-context operations.
  • Spinlocks protect short critical sections in atomic contexts.
  • IRQ-safe spinlock variants help coordinate process and interrupt access.
  • All relevant accesses must follow a consistent synchronization strategy.
  • Locking does not automatically solve object-lifetime or memory-release problems.
