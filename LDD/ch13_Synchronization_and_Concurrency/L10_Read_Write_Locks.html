2. Introduction to Read-Write Locks

A read-write lock is a synchronization mechanism that allows multiple readers to access shared data simultaneously while ensuring that a writer has exclusive access.

It is useful when shared data is read frequently but modified less frequently.

Why Are Read-Write Locks Required?

Consider a device driver maintaining a shared configuration table.

  • Several tasks may need to read the configuration.
  • Only one task should modify the configuration at a time.
  • Reading does not normally modify the shared data.
  • Writing must exclude both other writers and readers.

A read-write lock allows concurrent readers but protects modifications from concurrent access.

Shared Driver Configuration
↓
Reader A ── Reader B ── Reader C
↓
Multiple readers can hold read locks together
Writer requests write lock
↓
Waits until conflicting readers/writers release locks
↓
Writer obtains exclusive access

3. Reader and Writer Concepts

3.1 Reader

A reader accesses shared data without modifying it.

Multiple readers can hold a read lock simultaneously.

read_lock(&my_rwlock);

/* Read shared data */

read_unlock(&my_rwlock);

3.2 Writer

A writer modifies shared data. It must obtain exclusive access.

write_lock(&my_rwlock);

/* Modify shared data */

write_unlock(&my_rwlock);

While a writer holds the write lock, other readers and writers cannot acquire the conflicting lock.

Operation Concurrent Access
Read lock Multiple readers may hold the lock simultaneously.
Write lock Only one writer holds the lock, with no concurrent readers.

4. Linux Kernel Read-Write Spinlock

Linux provides the read-write spinlock type:

rwlock_t

Include the following header:

#include <linux/spinlock.h>

Read-write spinlocks are spin-based locks. A task that cannot obtain the requested lock waits by spinning rather than sleeping.

Static Initialization

static DEFINE_RWLOCK(my_rwlock);

Dynamic Initialization

static rwlock_t my_rwlock;

static int __init my_init(void)
{
    rwlock_init(&my_rwlock);

    return 0;
}

rwlock_init() initializes a read-write spinlock.

Read-write spinlocks are not sleepable locks. Do not perform sleeping operations while holding either a read lock or a write lock.

5. Read Lock Operations

5.1 read_lock()

Acquires the read side of a read-write spinlock.

read_lock(&my_rwlock);

/* Read shared data */

read_unlock(&my_rwlock);

Multiple readers can hold the read lock at the same time.

5.2 read_unlock()

Releases the read lock.

read_unlock(&my_rwlock);

Read Operation Flow

Reader requests read lock
↓
Check lock availability
↓
Acquire read lock
↓
Read shared data
↓
Release read lock

6. Write Lock Operations

6.1 write_lock()

Acquires the exclusive write side of a read-write spinlock.

write_lock(&my_rwlock);

/* Modify shared data */

write_unlock(&my_rwlock);

The writer must wait until conflicting readers and writers have released the lock.

6.2 write_unlock()

Releases the write lock.

write_unlock(&my_rwlock);

Write Operation Flow

Writer requests write lock
↓
Wait for conflicting readers and writers
↓
Acquire exclusive write lock
↓
Modify shared data
↓
Release write lock

7. Try-Lock Operations

Linux also provides non-blocking acquisition attempts for read-write spinlocks.

7.1 read_trylock()

if (read_trylock(&my_rwlock)) {

    pr_info("Read lock acquired\n");

    /* Read shared data */

    read_unlock(&my_rwlock);

} else {

    pr_info("Read lock unavailable\n");
}

Returns non-zero if the read lock is acquired, and zero if acquisition fails.

7.2 write_trylock()

if (write_trylock(&my_rwlock)) {

    pr_info("Write lock acquired\n");

    /* Modify shared data */

    write_unlock(&my_rwlock);

} else {

    pr_info("Write lock unavailable\n");
}

Returns non-zero if the write lock is acquired, and zero if acquisition fails.

8. IRQ-Safe Read-Write Locking

Some driver data may be accessed from both process context and hard interrupt context.

If process context holds a read-write spinlock and a local interrupt handler tries to acquire the same lock, the process could deadlock unless local interrupts are appropriately controlled.

8.1 read_lock_irqsave()

unsigned long flags;

read_lock_irqsave(&my_rwlock, flags);

/* Read shared data */

read_unlock_irqrestore(&my_rwlock, flags);

8.2 write_lock_irqsave()

unsigned long flags;

write_lock_irqsave(&my_rwlock, flags);

/* Modify shared data */

write_unlock_irqrestore(&my_rwlock, flags);

These operations save the previous local interrupt state, disable local interrupts while the lock is held, and restore the saved state when unlocking.

8.3 read_lock_irq()

read_lock_irq(&my_rwlock);

/* Read shared data */

read_unlock_irq(&my_rwlock);

8.4 write_lock_irq()

write_lock_irq(&my_rwlock);

/* Modify shared data */

write_unlock_irq(&my_rwlock);
Operation Purpose
read_lock() Acquire read lock.
read_unlock() Release read lock.
write_lock() Acquire write lock.
write_unlock() Release write lock.
read_lock_irqsave() Acquire read lock while saving and disabling local interrupts.
write_lock_irqsave() Acquire write lock while saving and disabling local interrupts.
Use IRQ-safe variants only when the locking design requires them. If a hard IRQ handler accesses the same lock, the process-context side must prevent local interrupt re-entry while holding that lock. The IRQ handler itself can use the corresponding non-sleeping lock operation. On PREEMPT_RT kernels, ordinary spinlock semantics differ, so use the locking guidance for the target kernel and execution context.

9. Read-Write Lock Working Example

Suppose a driver maintains a shared integer configuration value.

Several tasks can read the value, but updates must be exclusive.

static DEFINE_RWLOCK(config_lock);

static int config_value = 100;

/* Reader */
static int get_config(void)
{
    int value;

    read_lock(&config_lock);

    value = config_value;

    read_unlock(&config_lock);

    return value;
}

/* Writer */
static void set_config(int new_value)
{
    write_lock(&config_lock);

    config_value = new_value;

    write_unlock(&config_lock);
}

Explanation

  1. The read-write lock is declared using DEFINE_RWLOCK().
  2. The reader acquires a read lock.
  3. The reader copies the shared value.
  4. The reader releases the read lock.
  5. The writer acquires the exclusive write lock.
  6. The writer updates the shared value.
  7. The writer releases the lock.

Multiple readers can execute concurrently, but a writer requires exclusive access.

10. Practical Kernel Module: Read-Write Lock

The following module demonstrates read and write lock operations in a sequential example.

Source Code: rwlock_basic.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/spinlock.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Read Write Lock Demonstration");
MODULE_VERSION("1.0");

static DEFINE_RWLOCK(my_rwlock);

static int shared_value = 100;

static int __init rwlock_init_module(void)
{
    int value;

    pr_info("Read-write lock module loaded\n");

    /* Reader section */
    read_lock(&my_rwlock);

    value = shared_value;

    read_unlock(&my_rwlock);

    pr_info("Read value: %d\n", value);

    /* Writer section */
    write_lock(&my_rwlock);

    shared_value = 200;

    write_unlock(&my_rwlock);

    pr_info("Updated value: %d\n", shared_value);

    /* Read updated value */
    read_lock(&my_rwlock);

    value = shared_value;

    read_unlock(&my_rwlock);

    pr_info("Final value: %d\n", value);

    return 0;
}

static void __exit rwlock_exit_module(void)
{
    pr_info("Read-write lock module unloaded\n");
}

module_init(rwlock_init_module);
module_exit(rwlock_exit_module);

Explanation

  1. The read-write spinlock is statically initialized.
  2. The first read operation obtains the shared value.
  3. The write operation updates the value from 100 to 200.
  4. The final read operation obtains the updated value.
This module demonstrates the APIs sequentially. It does not prove concurrent reader behavior. A real concurrency test requires multiple kernel threads accessing the same shared data.

Makefile

obj-m += rwlock_basic.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test in Ubuntu

make

sudo insmod rwlock_basic.ko

sudo dmesg | tail -20

sudo rmmod rwlock_basic

make clean

Expected Output

Read-write lock module loaded
Read value: 100
Updated value: 200
Final value: 200
Read-write lock module unloaded

11. Practical Kernel Module: Concurrent Readers

This example creates two kernel threads that read the same shared value. Both use the read side of a read-write lock.

Source Code: rwlock_readers.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/spinlock.h>
#include <linux/kthread.h>
#include <linux/delay.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Concurrent Read Lock Demonstration");
MODULE_VERSION("1.0");

static DEFINE_RWLOCK(data_lock);

static int shared_data = 500;

static struct task_struct *reader1;
static struct task_struct *reader2;

static int reader_function(void *data)
{
    int id = *(int *)data;
    int value;

    while (!kthread_should_stop()) {

        read_lock(&data_lock);

        value = shared_data;

        pr_info("Reader %d: Value = %d\n", id, value);

        read_unlock(&data_lock);

        msleep(1000);
    }

    return 0;
}

static int reader1_id = 1;
static int reader2_id = 2;

static int __init rwlock_readers_init(void)
{
    reader1 = kthread_run(
        reader_function,
        &reader1_id,
        "rw_reader_1"
    );

    if (IS_ERR(reader1)) {
        int ret = PTR_ERR(reader1);
        reader1 = NULL;
        return ret;
    }

    reader2 = kthread_run(
        reader_function,
        &reader2_id,
        "rw_reader_2"
    );

    if (IS_ERR(reader2)) {
        int ret = PTR_ERR(reader2);
        reader2 = NULL;

        kthread_stop(reader1);
        reader1 = NULL;

        return ret;
    }

    pr_info("Two reader threads started\n");

    return 0;
}

static void __exit rwlock_readers_exit(void)
{
    if (reader1) {
        kthread_stop(reader1);
        reader1 = NULL;
    }

    if (reader2) {
        kthread_stop(reader2);
        reader2 = NULL;
    }

    pr_info("Reader threads stopped\n");
}

module_init(rwlock_readers_init);
module_exit(rwlock_readers_exit);

Makefile

obj-m += rwlock_readers.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test

make

sudo insmod rwlock_readers.ko

sudo dmesg | tail -30

sudo rmmod rwlock_readers

make clean

Expected Output

Two reader threads started
Reader 1: Value = 500
Reader 2: Value = 500
Reader 1: Value = 500
Reader 2: Value = 500
Reader threads stopped

The exact log ordering and number of messages depend on scheduling.

The example demonstrates multiple readers using the read side of the lock. The shared value is never modified, so no writer thread is needed.

12. Read-Write Lock vs Ordinary Spinlock

Feature Read-Write Spinlock Ordinary Spinlock
Concurrent readers Supported Not supported
Writer access Exclusive Exclusive
Waiting Busy waiting Busy waiting
Sleeping Not allowed while held Not allowed while held
Best suited for Read-heavy shared data Short critical sections with mixed reads and writes

13. Read-Write Spinlock vs Read-Write Semaphore

Linux also provides a sleepable reader-writer lock called struct rw_semaphore.

It is different from the read-write spinlock.

Read-Write Semaphore

#include <linux/rwsem.h>

static DECLARE_RWSEM(my_rwsem);

Typical operations include:

down_read(&my_rwsem);

/* Read shared data */

up_read(&my_rwsem);
down_write(&my_rwsem);

/* Modify shared data */

up_write(&my_rwsem);

Read-write semaphores allow multiple readers or one exclusive writer. Unlike rwlock_t, they are sleepable and therefore suitable only for contexts where sleeping is permitted.

Feature rwlock_t rw_semaphore
Header linux/spinlock.h linux/rwsem.h
Waiting Busy waiting Can sleep
Read operations read_lock() down_read()
Write operations write_lock() down_write()
Read release read_unlock() up_read()
Write release write_unlock() up_write()
Typical use Short, non-sleeping read-heavy sections Longer read-heavy sections in sleepable contexts
Choose between rwlock_t and rw_semaphore based on execution context and critical-section requirements. Neither should be selected solely because one appears faster in a simple example.

14. Limitations of Read-Write Locks

  • Writers may experience delays when readers frequently acquire the lock.
  • Read-write locks have more complex behavior than ordinary spinlocks.
  • They are not appropriate for critical sections that need to sleep.
  • They may introduce overhead when the protected section is very short.
  • They do not automatically protect unrelated data.
  • They require consistent locking discipline across all access paths.

Writer Starvation

Writer starvation is a possible concern in reader-writer synchronization if readers repeatedly acquire the lock and prevent a writer from making progress. Fairness characteristics depend on the particular locking implementation and kernel configuration.

15. Best Practices

  1. Use read-write locks only when concurrent readers provide a real benefit.
  2. Keep read and write critical sections short.
  3. Never sleep while holding a read-write spinlock.
  4. Use the matching unlock operation for every successful acquisition.
  5. Use IRQ-safe variants when required by the interrupt-sharing design.
  6. Do not mix different locking mechanisms without a defined locking order.
  7. Consider a mutex or read-write semaphore for sleepable critical sections.
  8. Consider an ordinary spinlock if read-write locking adds unnecessary complexity.
  9. Measure performance rather than assuming a read-write lock is always faster.

16. Common Programming Mistakes

Mistake Why It Is Wrong
Using read_lock() to modify shared data. Multiple readers may access the protected data simultaneously.
Using write_unlock() after a read lock. The unlock operation does not match the acquired lock.
Sleeping while holding rwlock_t. Read-write spinlocks cannot be held across sleeping operations.
Forgetting to release a lock. Other tasks may remain blocked indefinitely.
Using non-IRQ-safe locking with a shared hard IRQ lock. Local interrupt re-entry can cause deadlock.
Using read-write locks for every shared variable. The extra complexity and overhead may not provide a benefit.
Assuming every kernel configuration has identical spinlock behavior. PREEMPT_RT changes the semantics of several locking primitives.

17. Debugging Read-Write Lock Problems

Useful commands for inspecting kernel messages:

sudo dmesg | tail -50

sudo journalctl -k -n 50

lsmod | grep rwlock

When debugging a read-write lock problem, check:

  • Whether the lock is initialized.
  • Whether every read acquisition has a matching read release.
  • Whether every write acquisition has a matching write release.
  • Whether any sleeping operation occurs while the lock is held.
  • Whether interrupt-context access is handled safely.
  • Whether the lock protects every concurrent access to the shared data.
  • Whether writer delays or contention affect performance.

18. Lesson Summary

  • Read-write locks provide reader-writer synchronization.
  • Multiple readers can hold a read lock simultaneously.
  • A writer requires exclusive access.
  • Linux provides rwlock_t for read-write spinlocks.
  • DEFINE_RWLOCK() performs static initialization.
  • rwlock_init() performs runtime initialization.
  • read_lock() and read_unlock() manage read access.
  • write_lock() and write_unlock() manage exclusive write access.
  • IRQ-safe variants are available for appropriate interrupt-sharing designs.
  • rw_semaphore provides sleepable reader-writer synchronization.
  • Read-write spinlocks must not be held across sleeping operations.
  • Read-write locking is most useful when concurrent reads are frequent and writes are less frequent.
