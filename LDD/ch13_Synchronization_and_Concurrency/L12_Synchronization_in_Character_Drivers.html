2. Introduction to Synchronization in Character Drivers

A Linux character driver provides an interface between user-space applications and a device or software-managed data source.

Applications can access a character device using system calls such as:

open()
read()
write()
ioctl()
poll()
close()

Multiple processes or threads may access the same character device at the same time.

For example:

  • Process A writes data to a device.
  • Process B reads data from the same device.
  • Process C changes device configuration using IOCTL.
  • An interrupt handler updates device status.

These operations may access shared driver data concurrently.

Why Synchronization Is Required

Without synchronization, concurrent operations can modify shared data unexpectedly, produce inconsistent results or corrupt driver state.

User Application A
↓ read()
User Application B
↓ write()
Interrupt Handler
↓ updates status
↓
Character Driver
↓
Shared Driver Data
↓
Synchronization Required

3. Shared Data in a Character Driver

A character driver may maintain several shared data structures.

Shared Data Purpose Possible Concurrent Access
Device buffer Stores data transferred through read and write operations. Read and write callbacks.
Device status Stores ready, busy or error state. Process and interrupt contexts.
Device configuration Stores operating parameters. Read and IOCTL operations.
Open counter Tracks active opens or application usage. Open and release callbacks.
Event state Indicates whether new data or an event is available. Interrupt and read paths.

4. Race Conditions in Character Drivers

A race condition occurs when the result of concurrent operations depends on their execution order or timing.

Example: Shared Counter

Suppose two processes execute the following operation:

counter = counter + 1;

This operation involves reading, incrementing and writing the counter. It is not necessarily atomic.

Possible Execution Sequence

Step Process A Process B
1 Reads counter = 10
2 Reads counter = 10
3 Calculates 11
4 Calculates 11
5 Writes 11
6 Writes 11

The expected result is 12, but the actual result is 11.

This is called a lost update.

5. Choosing the Correct Synchronization Mechanism

The correct synchronization mechanism depends on the execution context and the operation being protected.

Mechanism Purpose Typical Use
Mutex Sleepable exclusive locking. Protecting buffers in read and write callbacks.
Spinlock Short non-sleeping critical sections. Shared status accessed by process and interrupt contexts.
Atomic operations Atomic operations on simple integer values. Event counters and simple flags.
Wait queues Waiting for a condition to become true. Blocking read until data becomes available.
Completions Waiting for a specific event or operation to finish. Waiting for an asynchronous device operation.
Read-write locks Multiple readers or one exclusive writer. Read-heavy configuration data.
Semaphores Managing access to a limited number of resources. Counting available resources.
A mutex is generally a suitable choice for protecting a shared character-driver buffer when the callbacks execute in process context. A spinlock is appropriate only when the protected operation must be non-sleeping.

6. Using Mutexes in Character Drivers

A mutex is commonly used to protect shared data accessed by read, write and IOCTL callbacks.

Declaration

#include <linux/mutex.h>

static DEFINE_MUTEX(device_mutex);

Protecting Shared Data

mutex_lock(&device_mutex);

/* Access shared driver data */

mutex_unlock(&device_mutex);

Example: Protected Read Operation

static ssize_t device_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position)
{
    mutex_lock(&device_mutex);

    /* Access protected kernel buffer */

    mutex_unlock(&device_mutex);

    return 0;
}

This is only a synchronization illustration. A functional read callback must also implement data-length checks, file-position handling and user-space copying.

Example: Protected Write Operation

static ssize_t device_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position)
{
    mutex_lock(&device_mutex);

    /* Update protected kernel buffer */

    mutex_unlock(&device_mutex);

    return count;
}

In a complete implementation, the driver must handle buffer bounds, copy failures and partial writes correctly.

7. Using Spinlocks in Character Drivers

Spinlocks are useful when shared data is accessed from contexts that cannot sleep, such as hard interrupt handlers.

Declaration

#include <linux/spinlock.h>

static DEFINE_SPINLOCK(status_lock);

static int device_status;

Updating Shared Status

spin_lock(&status_lock);

device_status = 1;

spin_unlock(&status_lock);

Reading Shared Status

int status;

spin_lock(&status_lock);

status = device_status;

spin_unlock(&status_lock);

When an Interrupt Handler Shares the Lock

If process context and a local hard interrupt handler use the same lock, process context should use the appropriate IRQ-safe variant.

unsigned long flags;

spin_lock_irqsave(&status_lock, flags);

/* Access data shared with hard IRQ */

spin_unlock_irqrestore(&status_lock, flags);

The hard interrupt handler can use the corresponding non-sleeping locking operation under the applicable kernel locking model.

Do not call copy_to_user(), copy_from_user(), mutex_lock(), msleep() or blocking wait operations while holding a spinlock. User-copy operations may sleep.

8. Using Atomic Operations

Atomic operations are useful for simple integer counters and state updates.

Declaration

#include <linux/atomic.h>

static atomic_t open_count = ATOMIC_INIT(0);

Increment Counter

atomic_inc(&open_count);

Decrement Counter

atomic_dec(&open_count);

Read Counter

int count;

count = atomic_read(&open_count);

Example in an Open Callback

static int device_open(
    struct inode *inode,
    struct file *file)
{
    atomic_inc(&open_count);

    pr_info("Device opened. Count = %d\n",
            atomic_read(&open_count));

    return 0;
}

Example in a Release Callback

static int device_release(
    struct inode *inode,
    struct file *file)
{
    atomic_dec(&open_count);

    pr_info("Device released. Count = %d\n",
            atomic_read(&open_count));

    return 0;
}

For object lifetime and reference counting, prefer refcount_t rather than using a plain atomic_t as an unrestricted reference counter.

9. Using Wait Queues in Character Drivers

Wait queues allow a process to sleep until a particular condition becomes true.

For example, a user application may call read() when no data is available.

The driver can put the calling process to sleep until new data arrives.

Declaration

#include <linux/wait.h>

static DECLARE_WAIT_QUEUE_HEAD(data_wait_queue);

static bool data_available;

Waiting for Data

wait_event_interruptible(
    data_wait_queue,
    READ_ONCE(data_available)
);

The actual driver must check the return value and re-evaluate its data condition under the appropriate synchronization.

Waking Up Waiting Processes

WRITE_ONCE(data_available, true);

wake_up_interruptible(&data_wait_queue);

In a real driver, the producer must publish the data and update the condition using a synchronization design that guarantees correct ordering and prevents data races. READ_ONCE() and WRITE_ONCE() alone are not general-purpose locking mechanisms.

Typical Read Flow

User calls read()
↓
Check whether data is available
↓
No data available
↓
Process sleeps on wait queue
↓
New data arrives
↓
Driver wakes waiting process
↓
Process reads available data

10. Using Completions in Character Drivers

Completions are useful when one execution context must wait for a particular operation or event to finish.

For example, a character driver may initiate an asynchronous device operation and wait until the operation completes.

Declaration

#include <linux/completion.h>

static DECLARE_COMPLETION(device_completion);

Waiting for Completion

wait_for_completion(&device_completion);

Signaling Completion

complete(&device_completion);

Typical Workflow

Driver Starts Device Operation
↓
Process Waits for Completion
↓
Device Operation Finishes
↓
Completion Event Is Signaled
↓
Waiting Process Continues

Completions represent event signaling. They do not replace mutexes or spinlocks used to protect shared data.

11. Complete Practical Example: Synchronized Character Driver

This example implements a simple character driver with:

  • A shared kernel buffer.
  • A mutex protecting buffer operations.
  • A wait queue for blocking reads.
  • A condition indicating whether data is available.
  • Read and write file operations.

Source Code: sync_char_driver.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/fs.h>
#include <linux/uaccess.h>
#include <linux/mutex.h>
#include <linux/wait.h>
#include <linux/device.h>
#include <linux/version.h>

#define DEVICE_NAME "sync_char"
#define BUFFER_SIZE 256

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Synchronized Character Driver");
MODULE_VERSION("1.0");

static int major_number;

static char device_buffer[BUFFER_SIZE];

static size_t data_length;

static DEFINE_MUTEX(device_mutex);

static DECLARE_WAIT_QUEUE_HEAD(data_wait_queue);

static bool data_available;

static struct class *sync_class;
static struct device *sync_device;

/* Read operation */
static ssize_t sync_read(
    struct file *file,
    char __user *user_buffer,
    size_t count,
    loff_t *position)
{
    size_t available;
    size_t bytes_to_copy;
    int ret;

    if (count == 0)
        return 0;

    if (file->f_flags & O_NONBLOCK) {

        if (!READ_ONCE(data_available))
            return -EAGAIN;

    } else {

        ret = wait_event_interruptible(
            data_wait_queue,
            READ_ONCE(data_available)
        );

        if (ret)
            return ret;
    }

    if (*position < 0)
        return -EINVAL;

    ret = mutex_lock_interruptible(&device_mutex);

    if (ret)
        return ret;

    /*
     * Recheck the condition after acquiring
     * the mutex because another reader may
     * have consumed the data.
     */
    if (!data_available || *position >= data_length) {

        mutex_unlock(&device_mutex);

        if (file->f_flags & O_NONBLOCK)
            return -EAGAIN;

        return -EAGAIN;
    }

    available = data_length - *position;

    bytes_to_copy = min(count, available);

    if (copy_to_user(
            user_buffer,
            device_buffer + *position,
            bytes_to_copy)) {

        mutex_unlock(&device_mutex);
        return -EFAULT;
    }

    *position += bytes_to_copy;

    if (*position >= data_length) {
        data_available = false;
        data_length = 0;
        *position = 0;
    }

    mutex_unlock(&device_mutex);

    return bytes_to_copy;
}

/* Write operation */
static ssize_t sync_write(
    struct file *file,
    const char __user *user_buffer,
    size_t count,
    loff_t *position)
{
    size_t bytes_to_copy;
    int ret;

    if (count == 0)
        return 0;

    ret = mutex_lock_interruptible(&device_mutex);

    if (ret)
        return ret;

    if (data_available) {
        mutex_unlock(&device_mutex);
        return -EBUSY;
    }

    bytes_to_copy = min(count, (size_t)BUFFER_SIZE);

    if (copy_from_user(
            device_buffer,
            user_buffer,
            bytes_to_copy)) {

        mutex_unlock(&device_mutex);
        return -EFAULT;
    }

    data_length = bytes_to_copy;
    data_available = true;

    mutex_unlock(&device_mutex);

    wake_up_interruptible(&data_wait_queue);

    return bytes_to_copy;
}

/* Open operation */
static int sync_open(
    struct inode *inode,
    struct file *file)
{
    pr_info("sync_char: device opened\n");

    return 0;
}

/* Release operation */
static int sync_release(
    struct inode *inode,
    struct file *file)
{
    pr_info("sync_char: device closed\n");

    return 0;
}

/* File operations */
static const struct file_operations sync_fops = {
    .owner   = THIS_MODULE,
    .open    = sync_open,
    .read    = sync_read,
    .write   = sync_write,
    .release = sync_release,
};

static int __init sync_driver_init(void)
{
    int ret;

    major_number = register_chrdev(
        0,
        DEVICE_NAME,
        &sync_fops
    );

    if (major_number < 0) {
        pr_err("sync_char: registration failed\n");
        return major_number;
    }

#if LINUX_VERSION_CODE >= KERNEL_VERSION(6, 4, 0)
    sync_class = class_create(DEVICE_NAME);
#else
    sync_class = class_create(THIS_MODULE, DEVICE_NAME);
#endif

    if (IS_ERR(sync_class)) {

        ret = PTR_ERR(sync_class);
        unregister_chrdev(major_number, DEVICE_NAME);

        return ret;
    }

    sync_device = device_create(
        sync_class,
        NULL,
        MKDEV(major_number, 0),
        NULL,
        DEVICE_NAME
    );

    if (IS_ERR(sync_device)) {

        ret = PTR_ERR(sync_device);

        class_destroy(sync_class);
        unregister_chrdev(major_number, DEVICE_NAME);

        return ret;
    }

    pr_info("sync_char: driver loaded\n");
    pr_info("sync_char: major number = %d\n",
            major_number);

    return 0;
}

static void __exit sync_driver_exit(void)
{
    device_destroy(
        sync_class,
        MKDEV(major_number, 0)
    );

    class_destroy(sync_class);

    unregister_chrdev(
        major_number,
        DEVICE_NAME
    );

    pr_info("sync_char: driver unloaded\n");
}

module_init(sync_driver_init);
module_exit(sync_driver_exit);

Explanation of the Example

1. Shared Buffer

static char device_buffer[BUFFER_SIZE];
static size_t data_length;

The buffer stores data written by a user application.

2. Mutex

static DEFINE_MUTEX(device_mutex);

The mutex protects the shared buffer, its length and the data-availability condition.

3. Wait Queue

static DECLARE_WAIT_QUEUE_HEAD(data_wait_queue);

A blocking reader waits until data becomes available.

4. Write Operation

The write callback:

  1. Acquires the mutex.
  2. Checks whether previous data is still available.
  3. Copies data from user space.
  4. Updates the data length and availability state.
  5. Releases the mutex.
  6. Wakes waiting readers.

5. Read Operation

The read callback:

  1. Waits for data when operating in blocking mode.
  2. Acquires the mutex.
  3. Rechecks the data condition.
  4. Copies available data to user space.
  5. Updates the file position.
  6. Clears the data state when the buffer is consumed.
  7. Releases the mutex.
This is an instructional single-buffer example, not a production-ready streaming driver. It supports one outstanding message at a time, returns -EBUSY if another write arrives before consumption, and does not implement poll(), IOCTL, removal-time lifetime management or a multi-reader message-queue policy. A production driver needs an explicit buffer ownership and reader-consumption design.

	$(MAKE) -C $(KDIR) M=$(PWD) modules

	$(MAKE) -C $(KDIR) M=$(PWD) clean

12. Synchronization Design: Process Context and Interrupt Context

A character driver may share data between its file operations and an interrupt handler.

For example:

  • The interrupt handler updates a device event status.
  • The read callback checks whether an event is available.
  • The read callback waits if no event has arrived.

Possible Design

Hardware Interrupt
↓
Interrupt Handler
↓
Update Event State Under Spinlock
↓
Wake Up Wait Queue
↓
Read Callback Resumes
↓
Process Event in Sleepable Context

In this design:

  • A spinlock protects short state updates shared with hard IRQ context.
  • A wait queue allows the process to sleep until an event occurs.
  • The read callback performs user-space copying in process context.
  • The interrupt handler does not call sleeping functions.

Important Design Rule

Never hold a spinlock while calling a function that may sleep. Release the spinlock before performing operations such as user-space data copying or waiting.

13. Synchronization and poll() in Character Drivers

The poll() file operation allows applications to monitor whether a device can be read or written without blocking indefinitely.

A typical driver uses a wait queue inside its poll callback:

static __poll_t sync_poll(
    struct file *file,
    struct poll_table_struct *wait)
{
    __poll_t mask = 0;

    poll_wait(file, &data_wait_queue, wait);

    if (READ_ONCE(data_available))
        mask |= EPOLLIN | EPOLLRDNORM;

    return mask;
}

The application can then use poll() or select() to wait for readiness.

The actual readiness condition must be synchronized with the data-management logic. A production implementation should also handle concurrent consumption and buffer-state changes correctly.

poll_wait() registers the application's polling wait queue with the driver's wait queue. It does not itself wait for data to arrive.

14. Common Synchronization Mistakes

Mistake Problem
Accessing a shared buffer without locking. Concurrent read and write operations may corrupt data.
Holding a mutex in interrupt context. Mutex acquisition may sleep and is not permitted in hard IRQ context.
Sleeping while holding a spinlock. Can cause deadlocks and invalid execution-context behavior.
Calling copy_to_user() while holding a spinlock. User-copy operations may sleep.
Using atomic operations for complex data structures. Atomic integer operations do not protect arbitrary multi-field state.
Waking a wait queue without updating its condition correctly. Waiters may wake without the required data being available.
Forgetting to release a mutex on an error path. Other tasks may remain blocked.
Using a completion as a data lock. Completions signal events; they do not provide mutual exclusion.

15. Best Practices for Character Driver Synchronization

  1. Identify all shared driver data before selecting synchronization primitives.
  2. Use mutexes for shared buffers accessed in sleepable process context.
  3. Use spinlocks for short, non-sleeping operations where required.
  4. Use IRQ-safe locking when a lock is shared with a hard interrupt handler.
  5. Use atomic operations for simple counters and flags where their semantics are sufficient.
  6. Use wait queues for condition-based blocking.
  7. Use completions for one-shot or explicitly reinitialized event signaling.
  8. Define consistent lock acquisition ordering.
  9. Keep critical sections short.
  10. Handle all error paths without leaving locks held.
  11. Test concurrent access from multiple user-space processes.
  12. Use lockdep and other kernel debugging tools during development.

17. Lesson Summary

  • Character drivers may be accessed concurrently by multiple processes and interrupt handlers.
  • Shared buffers, configuration values and device status require appropriate synchronization.
  • Mutexes are useful for sleepable exclusive access.
  • Spinlocks protect short non-sleeping critical sections.
  • Atomic operations support simple integer updates.
  • Wait queues allow processes to sleep until a condition becomes true.
  • Completions provide event-based synchronization.
  • Read-write locks allow concurrent readers and exclusive writers.
  • Lock ordering and deadlock prevention are essential for complex drivers.
  • Correct synchronization must consider execution context and data lifetime.
