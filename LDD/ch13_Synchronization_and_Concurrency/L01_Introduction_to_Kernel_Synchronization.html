Chapter: Synchronization and Concurrency

Lesson: 1 – Introduction to Kernel Synchronization

Prerequisites: Linux kernel modules, character drivers, file operations, interrupts and kernel execution contexts.

Objective: Understand concurrency, shared resources, critical sections and the need for synchronization in Linux device drivers.

1. Introduction

Linux is a multitasking operating system. Multiple processes, kernel threads, interrupt handlers and other kernel execution paths can operate during overlapping periods.

A Linux device driver may be accessed by several execution paths simultaneously. If these paths access or modify the same data without proper coordination, the driver can produce incorrect results or become unstable.

Kernel synchronization is the set of techniques used to coordinate concurrent execution and protect shared resources.

Synchronization helps ensure that shared data is accessed in a controlled and consistent manner.

Process B
Interrupt Handler
↓
Shared Driver Data
↓
Synchronization Mechanism

2. What Is Concurrency?

Concurrency means that multiple execution paths make progress during overlapping periods.

On a single-core processor, execution paths may be interleaved through scheduling and interrupts. On a multicore processor, multiple execution paths may actually execute simultaneously.

Example

Suppose a character driver maintains a global variable:

static int device_counter;

Two processes access the same driver. Both attempt to increment the counter.

Without synchronization, their operations can overlap and produce an incorrect result.

Concurrency does not always mean that instructions execute at exactly the same time. Interleaving alone can create synchronization problems.

3. What Is a Shared Resource?

A shared resource is a data object or system resource that can be accessed by multiple execution paths.

Examples in Device Drivers

  • Global variables.
  • Device-private data structures.
  • Character-device buffers.
  • Hardware status information.
  • Queue data structures.
  • DMA descriptors and buffer metadata.
  • Device state and configuration information.

When several execution paths access a shared resource, the driver must define how those accesses are coordinated.

4. Why Is Synchronization Required?

Synchronization is required to prevent multiple execution paths from modifying shared data in an unsafe manner.

Main Reasons

  1. Data consistency: Prevent inconsistent shared data.
  2. Race prevention: Coordinate operations that depend on each other.
  3. Resource protection: Prevent unsafe simultaneous access.
  4. Correctness: Ensure operations produce predictable results.
  5. Reliability: Reduce corruption and unexpected driver behavior.
A device driver must be designed for concurrent access unless its interface and execution model explicitly guarantee otherwise.

5. What Is a Race Condition?

A race condition occurs when the result of an operation depends on the timing or ordering of concurrent execution paths.

Consider a shared counter initially set to 10.

Two execution paths both increment the counter.

Expected Result

Initial counter = 10

Process A increments counter
Process B increments counter

Expected final counter = 12

Possible Unsafe Execution

Step Process A Process B Counter
1 Reads 10 – 10
2 – Reads 10 10
3 Calculates 11 – 10
4 – Calculates 11 10
5 Writes 11 – 11
6 – Writes 11 11

The final value is 11 instead of 12. One increment has been lost.

This is called a lost-update problem.

6. What Is a Critical Section?

A critical section is a part of code that accesses or modifies a shared resource and therefore requires controlled access.

Example

device_counter++;

device_status = 1;

buffer[index] = value;

If these operations involve shared data, they may need protection against concurrent access.

Execution Path A
↓
Acquire Protection
↓
Critical Section
↓
Release Protection

The specific protection mechanism depends on whether the code can sleep, whether interrupts can access the same data, and whether execution can occur on multiple CPUs.

7. Process Context and Interrupt Context

Linux kernel code can execute in different contexts. Synchronization mechanisms must be selected according to those contexts.

Context Description Can Sleep?
Process context Code executing on behalf of a process or kernel thread. Usually yes, where permitted.
Hard interrupt context Code executing in response to a hardware interrupt. No.
Softirq context Deferred interrupt processing context. No.
Tasklet context Legacy deferred processing mechanism based on softirqs. No.
Workqueue context Deferred work executed by kernel worker threads. Usually yes.
A mutex may sleep while waiting for a lock. Therefore, it must not be used in hard interrupt, softirq or other atomic contexts.

8. Types of Synchronization Problems

8.1 Race Condition

Concurrent access causes an outcome that depends on execution timing.

8.2 Data Corruption

Multiple execution paths modify shared data without suitable coordination.

8.3 Lost Update

One update overwrites another update because operations overlap.

8.4 Deadlock

Two or more execution paths wait indefinitely for resources held by each other.

8.5 Starvation

An execution path is repeatedly denied access to a required resource.

8.6 Priority Inversion

A high-priority task is indirectly delayed because a lower-priority task holds a resource it needs.

9. Overview of Linux Synchronization Mechanisms

Linux provides several synchronization mechanisms. Each one is designed for particular requirements and execution contexts.

Mechanism Purpose Typical Use
Atomic operations Perform specific operations atomically. Counters and flags.
Spinlocks Protect short critical sections without sleeping. Atomic contexts and shared data.
Mutexes Provide sleeping mutual exclusion. Process-context operations.
Semaphores Control access to a resource or count of available resources. Specific resource coordination.
Wait queues Allow tasks to wait for a condition. Waiting for device data or events.
Completions Coordinate completion of an operation. Waiting for asynchronous work.
Read-write locks Allow multiple readers or an exclusive writer. Read-heavy shared data.
RCU Support efficient read-mostly access with specialized update and reclamation rules. Read-heavy kernel data structures.

These mechanisms will be studied individually in the upcoming lessons.

10. Mutual Exclusion

Mutual exclusion means that only one execution path at a time is allowed to enter a protected critical section, when the chosen locking mechanism provides exclusive ownership.

For example, a mutex can protect a shared device buffer from simultaneous modification by multiple process-context operations.

Process A
Process B
↓
Mutex Lock
↓
Protected Shared Buffer

Mutual exclusion prevents conflicting operations from entering the protected section simultaneously. It does not automatically solve every ordering, lifetime or interrupt-context problem.

11. Synchronization Example: Conceptual Device Counter

Consider a character driver maintaining a counter that can be updated by process-context operations.

Unprotected Concept

static int device_counter;

static void update_counter(void)
{
    device_counter++;
}

If multiple execution paths call this function concurrently, the increment may not be safe.

Protected Concept Using a Mutex

#include <linux/mutex.h>

static int device_counter;
static DEFINE_MUTEX(counter_lock);

static void update_counter(void)
{
    mutex_lock(&counter_lock);

    device_counter++;

    mutex_unlock(&counter_lock);
}

This example is appropriate only when callers execute in contexts where sleeping is allowed. It is not suitable for a hard interrupt handler.

A mutex protects the counter only if every code path that accesses the counter follows the same locking discipline.

12. Synchronization and Multicore Processors

Modern systems commonly contain multiple CPU cores. Different execution paths may run on different cores at the same time.

Without synchronization, two CPUs can modify shared memory concurrently.

CPU Core 0
CPU Core 1
↓
Shared Kernel Memory
↓
Synchronization Required

Disabling local interrupts on one CPU does not by itself prevent another CPU from accessing the same shared data. Cross-CPU synchronization requires an appropriate mechanism such as a spinlock or another suitable primitive.

13. Synchronization in Character Device Drivers

A character driver may have multiple open file descriptions and concurrent read, write or ioctl operations.

For example, consider a shared buffer:

struct my_device {
    char buffer[1024];
    size_t data_length;
    struct mutex lock;
};

When process-context read and write operations access the shared buffer, a mutex can protect the relevant critical sections.

However, if an interrupt handler also accesses the same data, the design must account for interrupt context. A mutex cannot be acquired in a hard interrupt handler.

The driver may need a spinlock for short atomic-context protection, or it may arrange for the interrupt handler to communicate with process context through a suitable deferred-work design.

14. General Rules for Kernel Synchronization

  1. Identify all shared resources.
  2. Identify every execution path that accesses each resource.
  3. Determine the execution context of each access.
  4. Select a synchronization mechanism appropriate to those contexts.
  5. Keep critical sections as short as practical.
  6. Use a consistent lock ordering.
  7. Do not sleep while holding a spinlock.
  8. Do not acquire a mutex from hard interrupt context.
  9. Ensure that every access follows the same protection rules.
  10. Consider object lifetime and cleanup in addition to data locking.

16. Lesson Summary

  • Concurrency occurs when execution paths make progress during overlapping periods.
  • Shared resources can be accessed by processes, threads and interrupt handlers.
  • Race conditions can cause lost updates and inconsistent data.
  • Critical sections require suitable protection.
  • Mutual exclusion controls access to protected resources.
  • Process, interrupt and deferred-work contexts have different sleeping rules.
  • Linux provides atomic operations, spinlocks, mutexes, semaphores, wait queues, completions and other mechanisms.
  • The correct synchronization mechanism depends on context and access patterns.
