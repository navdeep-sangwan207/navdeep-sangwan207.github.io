2. Introduction to Spinlocks

A spinlock is a synchronization mechanism used to protect shared data from concurrent access.

When a CPU attempts to acquire a spinlock that is already held by another execution context, it repeatedly checks the lock until it becomes available.

This repeated checking is called busy waiting or spinning.

Unlike a mutex, a spinlock does not put the waiting task to sleep while waiting for the lock.

Why Is a Spinlock Required?

Consider a driver with a shared variable accessed by two CPUs.

  • CPU 0 is updating the shared data.
  • CPU 1 also wants to update the same data.
  • Without synchronization, both CPUs may modify the data concurrently.
  • A spinlock ensures that only one CPU enters the protected critical section at a time.
CPU 0 requests spinlock
↓
Lock acquired
↓
CPU 0 executes critical section
↓
CPU 0 releases spinlock
↓
CPU 1 can acquire the lock

3. Understanding Busy Waiting

Busy waiting means that a CPU continuously checks whether a synchronization resource is available.

Suppose CPU 0 holds a spinlock and CPU 1 attempts to acquire the same lock.

CPU 0
Holds the lock
↓
Executes protected code
CPU 1
Attempts to acquire the lock
↓
Lock unavailable
↓
Continues spinning and checking
↓
Acquires lock after CPU 0 releases it

Characteristics of Busy Waiting

  • The waiting CPU does not sleep.
  • The waiting CPU repeatedly checks the lock.
  • CPU time is consumed while waiting.
  • It is suitable only when the expected waiting period is short.
Spinlocks are particularly useful for short critical sections in kernel code where sleeping is not allowed, such as certain interrupt-related paths.

4. Spinlock Data Type

Linux provides the spinlock_t type to represent a spinlock.

Include the appropriate header:

#include <linux/spinlock.h>

Static Initialization

static DEFINE_SPINLOCK(my_lock);

DEFINE_SPINLOCK() declares and statically initializes a spinlock.

Dynamic Initialization

static spinlock_t my_lock;

static int __init my_init(void)
{
    spin_lock_init(&my_lock);

    return 0;
}

spin_lock_init() initializes a spinlock object before it is used.

A spinlock must be initialized correctly before use. Do not repeatedly initialize a lock while another execution context may be using it.

5. Basic Spinlock Operations

5.1 spin_lock()

Acquires a spinlock. If another context holds it, the caller spins until the lock becomes available.

spin_lock(&my_lock);

/* Critical section */

spin_unlock(&my_lock);

5.2 spin_unlock()

Releases a previously acquired spinlock so another context can acquire it.

5.3 spin_trylock()

Attempts to acquire a spinlock without waiting indefinitely.

if (spin_trylock(&my_lock)) {

    /* Lock acquired */

    spin_unlock(&my_lock);

} else {

    /* Lock was not available */
}

It returns a non-zero value when the lock is successfully acquired and zero when it cannot be acquired immediately.

5.4 spin_is_locked()

Checks whether a spinlock appears to be locked.

if (spin_is_locked(&my_lock)) {
    pr_info("Lock appears to be held\n");
}

This is primarily a diagnostic check. It is not a safe substitute for acquiring the lock because the lock state can change immediately after the check.

6. Structure of a Spinlock-Protected Critical Section

A typical spinlock-protected operation follows this sequence:

Shared data
↓
Acquire spinlock
↓
Enter critical section
↓
Access or update shared data
↓
Release spinlock
↓
Continue normal execution

Example

static spinlock_t my_lock;
static int shared_count;

static void update_count(void)
{
    spin_lock(&my_lock);

    shared_count++;

    spin_unlock(&my_lock);
}

The increment is protected by the lock. Other execution contexts that use the same lock cannot enter their protected sections simultaneously.

All accesses that need mutual exclusion must follow the same locking protocol. Protecting only some accesses does not eliminate the race condition.

7. Spinlocks and Multiprocessor Systems (SMP)

SMP stands for Symmetric Multiprocessing. In an SMP system, multiple CPUs can execute kernel code concurrently and access shared memory.

For example:

  • CPU 0 executes a device driver's interrupt handler.
  • CPU 1 executes a system call associated with the same device.
  • Both access a shared device data structure.

A spinlock provides mutual exclusion between the contexts that acquire that same lock.

CPU 0
Process context
↘
Shared Spinlock
↗
CPU 1
Interrupt context
↓
Protected shared data

On an SMP system, the lock coordinates access across CPUs, not merely between different tasks on one CPU.

8. Spinlocks in Interrupt Context

Interrupt handlers cannot sleep. This makes spinlocks useful for protecting shared data that is accessed from interrupt context and process context.

However, using only spin_lock() in process context can cause a deadlock if the same lock is also acquired by an interrupt handler on the same CPU.

Example of the Deadlock Situation

  1. Process context acquires a spinlock.
  2. A hardware interrupt occurs on the same CPU.
  3. The interrupt handler attempts to acquire the same spinlock.
  4. The interrupt handler spins because the process context holds the lock.
  5. The process context cannot resume and release the lock until the interrupt handler finishes.
Process context acquires lock
↓
Interrupt occurs on same CPU
↓
Interrupt handler requests same lock
↓
Interrupt handler spins
↓
Process cannot resume to release lock
↓
Deadlock

Solution: Disable Local Interrupts While Holding the Lock

When process context shares a lock with a local hardware interrupt handler, use the appropriate IRQ-safe locking variant.

unsigned long flags;

spin_lock_irqsave(&my_lock, flags);

/* Critical section */

spin_unlock_irqrestore(&my_lock, flags);

spin_lock_irqsave() saves the current local interrupt state and disables local interrupts before acquiring the lock.

spin_unlock_irqrestore() releases the lock and restores the saved local interrupt state.

This pattern prevents the relevant local interrupt handler from interrupting the process context while it holds the lock. It does not disable interrupts on every CPU.

9. Important Spinlock Variants

Function Purpose
spin_lock() Acquires a spinlock.
spin_unlock() Releases a spinlock.
spin_trylock() Attempts to acquire a spinlock without waiting.
spin_lock_irq() Disables local hardware interrupts and acquires the lock.
spin_unlock_irq() Releases the lock and enables local interrupts.
spin_lock_irqsave() Saves local interrupt state, disables local interrupts and acquires the lock.
spin_unlock_irqrestore() Releases the lock and restores the saved interrupt state.
spin_lock_bh() Disables local bottom-half processing and acquires the lock.
spin_unlock_bh() Releases the lock and re-enables local bottom-half processing as appropriate.

The exact locking variant depends on which execution contexts share the protected data.

10. Spinlocks and Bottom Halves

Linux drivers may use deferred execution mechanisms such as tasklets and softirq processing. These mechanisms can access shared data alongside process context.

If process context and bottom-half context share a spinlock, the process-context side commonly uses:

spin_lock_bh(&my_lock);

/* Shared data access */

spin_unlock_bh(&my_lock);

This prevents the relevant bottom-half processing on the local CPU from running while the process context holds the lock.

For hard interrupt handlers, use the appropriate IRQ-safe design instead. Do not assume that disabling bottom halves also disables hardware interrupts.

11. Spinlock vs Mutex vs Atomic Operations

Feature Spinlock Mutex Atomic Operation
Purpose Protects short critical sections Protects critical sections that may sleep Performs supported atomic updates
Waiting mechanism Busy waiting Task may sleep Depends on the operation; no general lock ownership
Can sleep while held? No Yes, while holding the mutex in an appropriate sleepable context Not applicable to a lock held across a code section
Interrupt context Possible with correct IRQ-safe design Not allowed Many atomic operations are suitable
Complex data protection Yes Yes Not by itself
Typical application Short shared-state updates Shared buffers and longer operations Event counters and simple state updates

Selection Guidelines

  • Use atomic operations for simple independent counters and flags.
  • Use spinlocks for short critical sections that must not sleep.
  • Use mutexes for longer critical sections in sleepable process context.

12. Rules for Using Spinlocks

  1. Keep the critical section as short as possible.
  2. Never call a function that may sleep while holding a spinlock.
  3. Never use copy_to_user() or copy_from_user() while holding a spinlock because these operations may sleep.
  4. Do not perform blocking I/O while holding a spinlock.
  5. Do not acquire the same non-recursive spinlock again from the same execution path.
  6. Use the same lock consistently for shared data that requires mutual exclusion.
  7. Use IRQ-safe variants when process context shares the lock with a local hard interrupt handler.
  8. Maintain a consistent lock acquisition order when multiple locks are used.
  9. Release every successfully acquired lock on every applicable control-flow path.
A spinlock must not be held across a sleeping operation. Doing so can cause kernel warnings, deadlocks or other serious problems.

13. Practical Kernel Module: Spinlock-Protected Counter

Let us implement a simple module that protects a shared counter using a spinlock.

Source Code: spinlock_counter.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/spinlock.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Spinlock Counter Demonstration");
MODULE_VERSION("1.0");

static DEFINE_SPINLOCK(counter_lock);
static int shared_counter = 0;

static void update_counter(void)
{
    spin_lock(&counter_lock);

    shared_counter++;

    spin_unlock(&counter_lock);
}

static int __init spinlock_counter_init(void)
{
    unsigned long flags;
    int i;

    pr_info("Spinlock counter module loaded\n");

    for (i = 0; i < 5; i++) {
        update_counter();
    }

    spin_lock_irqsave(&counter_lock, flags);

    pr_info("Counter value = %d\n", shared_counter);

    spin_unlock_irqrestore(&counter_lock, flags);

    return 0;
}

static void __exit spinlock_counter_exit(void)
{
    pr_info("Spinlock counter module unloaded\n");
}

module_init(spinlock_counter_init);
module_exit(spinlock_counter_exit);

Explanation

  1. linux/spinlock.h provides spinlock definitions.
  2. DEFINE_SPINLOCK() initializes the lock.
  3. shared_counter stores the shared counter value.
  4. update_counter() acquires the lock before incrementing the counter.
  5. The lock is released immediately after the update.
  6. The final read is also protected by the same lock.

The module initialization function executes five updates. The counter is therefore expected to reach 5.

Makefile

obj-m += spinlock_counter.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Ensure that the recipe commands begin with actual tab characters.

Compile and Test in Ubuntu

make

sudo insmod spinlock_counter.ko

lsmod | grep spinlock_counter

sudo dmesg | tail -20

sudo rmmod spinlock_counter

sudo dmesg | tail -20

make clean

Expected Output

Spinlock counter module loaded
Counter value = 5
Spinlock counter module unloaded
This module demonstrates correct lock initialization, acquisition and release. Its initialization loop is sequential, so it does not demonstrate real CPU contention. A separate concurrent test would be needed to evaluate contention behavior.

14. Practical Example: Process and Interrupt Shared Data

Consider a device driver where a process-context operation and a hardware interrupt handler both update the same event counter.

A simplified locking pattern is:

#include <linux/spinlock.h>

static DEFINE_SPINLOCK(event_lock);
static unsigned int event_count;

/* Process context */
static void process_event(void)
{
    unsigned long flags;

    spin_lock_irqsave(&event_lock, flags);

    event_count++;

    spin_unlock_irqrestore(&event_lock, flags);
}

/* Hard interrupt handler */
static irqreturn_t my_interrupt_handler(
    int irq,
    void *dev_id)
{
    spin_lock(&event_lock);

    event_count++;

    spin_unlock(&event_lock);

    return IRQ_HANDLED;
}

In this pattern:

  • Process context uses spin_lock_irqsave() because the lock is also used by a local hard interrupt handler.
  • The interrupt handler uses spin_lock() because it already runs in hard interrupt context.
  • Both contexts protect the same shared counter with the same lock.
This is a synchronization pattern, not a complete loadable driver. A real interrupt handler must match the registered IRQ and device state, and all shared accesses must follow the same locking rules.

15. Common Spinlock Mistakes

Mistake Why It Is Wrong
Calling msleep() while holding a spinlock. Sleeping is not allowed while holding a spinlock.
Using copy_to_user() inside a spinlocked section. User-memory access may sleep.
Keeping a spinlock held for a long time. Other CPUs may waste time spinning.
Using spin_lock() in process context without considering a shared hard IRQ handler. A same-CPU interrupt can cause deadlock.
Using different locks for the same shared data without a valid protocol. Mutual exclusion is not guaranteed.
Forgetting spin_unlock(). The lock remains held and other contexts may spin indefinitely.
Assuming a spinlock protects code that does not acquire it. All relevant concurrent accesses must follow the locking protocol.

16. Spinlock Debugging and Testing

Linux provides debugging facilities that can help identify synchronization problems.

Check Kernel Messages

sudo dmesg | tail -50

sudo journalctl -k -n 50

Inspect Kernel Configuration

grep -E 'CONFIG_PROVE_LOCKING|CONFIG_DEBUG_SPINLOCK|CONFIG_LOCKDEP' \
/boot/config-$(uname -r)

Depending on the kernel configuration, facilities such as lockdep and spinlock debugging can help identify lock-order problems, incorrect locking usage and related errors.

These debugging facilities are not enabled in every Ubuntu kernel configuration.

Use your Ubuntu VirtualBox environment for basic module compilation and testing. A VM can demonstrate kernel synchronization code, but it may not reproduce all hardware interrupt timing and physical-device behavior.

  • spin_unlock() releases the lock.
