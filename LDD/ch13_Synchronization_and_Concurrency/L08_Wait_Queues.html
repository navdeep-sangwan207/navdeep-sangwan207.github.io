2. Introduction to Wait Queues

A wait queue is a Linux kernel mechanism that allows tasks to sleep until a specified condition becomes true or an event occurs.

Instead of continuously checking whether data is available, a task can sleep and allow the CPU to execute other tasks.

Why Are Wait Queues Required?

Consider a character device that receives data from hardware.

  • A user application calls read().
  • No data is currently available.
  • The driver must wait for new data.
  • Hardware or another kernel execution path supplies data.
  • The driver wakes the waiting task.
  • The application can continue reading.

Wait queues provide an efficient mechanism for this type of event-driven synchronization.

User Application calls read()
↓
Driver checks data availability
↓
No data available
↓
Task sleeps in wait queue
↓
New data arrives
↓
Driver wakes waiting task
↓
Task resumes and reads data

3. What Is a Wait Queue?

A wait queue maintains a collection of tasks waiting for a particular condition.

For example, multiple applications may attempt to read from a device. If no data is available, their tasks can wait until the driver signals that data has arrived.

Main Components

Component Purpose
Wait queue head Represents the queue on which tasks wait.
Waiting task A task sleeping until a condition becomes true.
Condition Determines whether the task can proceed.
Wake-up operation Notifies waiting tasks that they should recheck the condition.

Important Data Type

The Linux kernel uses:

wait_queue_head_t

It represents the wait queue head used by wait-queue operations.

4. Declaring and Initializing Wait Queues

Include the wait-queue header:

#include <linux/wait.h>

4.1 Static Initialization

static DECLARE_WAIT_QUEUE_HEAD(my_wait_queue);

This declares and initializes a wait queue head.

4.2 Dynamic Initialization

static wait_queue_head_t my_wait_queue;

static int __init my_init(void)
{
    init_waitqueue_head(&my_wait_queue);

    return 0;
}

init_waitqueue_head() initializes a wait queue head before it is used.

Use static initialization for a statically declared wait queue. Use init_waitqueue_head() when initializing a wait queue at runtime, and ensure initialization completes before concurrent access.

5. Wait Queue Operations

Linux provides several macros and functions for waiting and waking tasks.

5.1 wait_event()

wait_event() puts the calling task into a wait state until the specified condition becomes true.

wait_event(my_wait_queue, data_available);

The task sleeps while data_available is false. It resumes when the condition becomes true and is appropriately woken.

5.2 wait_event_interruptible()

This operation allows a waiting task to be interrupted by a signal.

int ret;

ret = wait_event_interruptible(
    my_wait_queue,
    data_available
);

if (ret)
    return ret;

It returns 0 when the condition becomes true. If interrupted by a signal before the condition is satisfied, it returns a negative error value, commonly -ERESTARTSYS.

5.3 wait_event_timeout()

This macro waits until the condition becomes true or the timeout expires.

long ret;

ret = wait_event_timeout(
    my_wait_queue,
    data_available,
    5 * HZ
);

The timeout is expressed in jiffies. A return value greater than zero indicates the condition became true before the timeout expired. A return value of zero indicates timeout. If the condition is already true, the macro can return a positive value immediately.

5.4 wait_event_interruptible_timeout()

This combines signal-interruptible waiting with a timeout.

long ret;

ret = wait_event_interruptible_timeout(
    my_wait_queue,
    data_available,
    5 * HZ
);

if (ret < 0) {
    pr_info("Wait interrupted\n");
} else if (ret == 0) {
    pr_info("Wait timed out\n");
} else {
    pr_info("Condition satisfied\n");
}

Wait Operation Summary

Operation Behavior
wait_event() Waits until a condition becomes true.
wait_event_interruptible() Waits until a condition becomes true or a signal interrupts the wait.
wait_event_timeout() Waits until a condition is true or the timeout expires.
wait_event_interruptible_timeout() Interruptible waiting with a timeout.

6. Wake-Up Operations

After the condition becomes true, the driver must wake the tasks waiting on the relevant wait queue.

6.1 wake_up()

Wakes tasks waiting on a wait queue according to the wake-up rules.

wake_up(&my_wait_queue);

6.2 wake_up_interruptible()

Wakes tasks waiting in an interruptible state.

wake_up_interruptible(&my_wait_queue);

6.3 wake_up_all()

Wakes all eligible tasks waiting on the queue.

wake_up_all(&my_wait_queue);

6.4 wake_up_interruptible_all()

Wakes all tasks waiting in an interruptible state.

wake_up_interruptible_all(&my_wait_queue);
Function Purpose
wake_up() Wakes eligible waiting tasks.
wake_up_interruptible() Wakes interruptible waiters.
wake_up_all() Wakes all eligible waiters.
wake_up_interruptible_all() Wakes all interruptible waiters.
A wake-up does not guarantee that the condition is still true when a task resumes. A task must recheck the condition. Wait-event macros handle the waiting and condition rechecking pattern.

7. How Wait Queues Work

Consider a driver with a Boolean condition called data_available.

Initially, the condition is false. A reader waits until data becomes available.

Initial state: data_available = false
↓
Reader calls wait_event_interruptible()
↓
Reader task sleeps
↓
Producer receives or prepares data
↓
Producer sets data_available = true
↓
Producer calls wake_up_interruptible()
↓
Reader wakes and rechecks condition
↓
Reader continues processing

This avoids continuous polling by the reader.

8. Process State During Waiting

When a task waits on a wait queue, the kernel changes its scheduling state according to the waiting operation.

Common Task States

State Meaning
TASK_RUNNING The task is runnable or currently executing.
TASK_INTERRUPTIBLE The task can be awakened by a suitable event or signal.
TASK_UNINTERRUPTIBLE The task waits without ordinary signal interruption.

Wait-event macros manage the necessary task-state transitions internally.

Prefer the standard wait-event macros over manually changing task states. They handle important scheduling and race-prevention details.

9. Wait Queues in Character Device Drivers

Wait queues are especially useful in character drivers that receive data asynchronously.

Example Scenario

Imagine a serial device receiving characters from an external source.

  • The application calls read().
  • The driver checks whether its data buffer contains data.
  • If the buffer is empty, the reader waits.
  • The interrupt handler or another appropriate producer path stores received data.
  • The producer wakes the reader.
  • The reader copies available data to user space.
UART Hardware Receives Data
↓
Interrupt Handler / Producer Path
↓
Store Data in Driver Buffer
↓
Update data_available Condition
↓
Wake Up Waiting Reader
↓
Character Driver read() Returns Data

The interrupt handler must not perform operations that can sleep. It can update suitable shared state and use an appropriate wake-up operation, while more complex processing can be deferred to a workqueue or another sleepable context.

10. Practical Kernel Module: Basic Wait Queue

The following example demonstrates a wait queue with a condition that becomes true during module initialization.

Source Code: wait_queue_basic.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/wait.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Basic Wait Queue Demonstration");
MODULE_VERSION("1.0");

static DECLARE_WAIT_QUEUE_HEAD(my_wait_queue);

static int data_available = 0;

static int __init wait_queue_init(void)
{
    pr_info("Wait queue module loaded\n");

    /*
     * Set the condition to true before waiting.
     */
    WRITE_ONCE(data_available, 1);

    /*
     * Wake any eligible tasks waiting on the queue.
     */
    wake_up_interruptible(&my_wait_queue);

    /*
     * The condition is already true,
     * so this returns without sleeping.
     */
    wait_event_interruptible(
        my_wait_queue,
        READ_ONCE(data_available)
    );

    pr_info("Wait condition satisfied\n");

    return 0;
}

static void __exit wait_queue_exit(void)
{
    pr_info("Wait queue module unloaded\n");
}

module_init(wait_queue_init);
module_exit(wait_queue_exit);

Explanation

  1. The wait queue is declared using DECLARE_WAIT_QUEUE_HEAD().
  2. The condition initially equals zero.
  3. The module sets the condition to one.
  4. wake_up_interruptible() notifies eligible waiting tasks.
  5. wait_event_interruptible() checks the condition.
  6. Because the condition is already true, the task does not sleep.
This is an initialization demonstration, not a true concurrent producer-consumer test. The next practical example shows a reader waiting for a producer thread.

Makefile

obj-m += wait_queue_basic.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test

make

sudo insmod wait_queue_basic.ko

sudo dmesg | tail -20

sudo rmmod wait_queue_basic

make clean

Expected Output

Wait queue module loaded
Wait condition satisfied
Wait queue module unloaded

11. Practical Kernel Module: Producer and Consumer

This example creates a kernel thread that acts as a producer. The module initialization function acts as a consumer and waits for the producer to make data available.

Source Code: wait_queue_producer_consumer.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/wait.h>
#include <linux/kthread.h>
#include <linux/delay.h>
#include <linux/sched.h>
#include <linux/atomic.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Wait Queue Producer Consumer Example");
MODULE_VERSION("1.0");

static DECLARE_WAIT_QUEUE_HEAD(data_wait_queue);

static atomic_t data_ready = ATOMIC_INIT(0);

static struct task_struct *producer_task;

static int producer_function(void *data)
{
    pr_info("Producer thread started\n");

    /*
     * Simulate a delay before data becomes available.
     */
    msleep(2000);

    if (kthread_should_stop())
        return 0;

    /*
     * Publish the condition before waking readers.
     */
    atomic_set(&data_ready, 1);

    pr_info("Producer: Data is available\n");

    wake_up_interruptible(&data_wait_queue);

    return 0;
}

static int __init producer_consumer_init(void)
{
    int ret;

    pr_info("Producer-consumer module loaded\n");

    producer_task = kthread_run(
        producer_function,
        NULL,
        "waitqueue_producer"
    );

    if (IS_ERR(producer_task)) {
        ret = PTR_ERR(producer_task);
        producer_task = NULL;
        return ret;
    }

    pr_info("Consumer: Waiting for data\n");

    ret = wait_event_interruptible(
        data_wait_queue,
        atomic_read(&data_ready) != 0
    );

    if (ret) {
        pr_info("Consumer wait interrupted\n");

        kthread_stop(producer_task);
        producer_task = NULL;

        return ret;
    }

    pr_info("Consumer: Data received successfully\n");

    return 0;
}

static void __exit producer_consumer_exit(void)
{
    if (producer_task) {
        kthread_stop(producer_task);
        producer_task = NULL;
    }

    pr_info("Producer-consumer module unloaded\n");
}

module_init(producer_consumer_init);
module_exit(producer_consumer_exit);

Explanation

  1. The module declares a wait queue.
  2. An atomic variable represents whether data is ready.
  3. A kernel thread is started using kthread_run().
  4. The producer waits for approximately two seconds.
  5. The producer sets the data-ready condition.
  6. The producer calls wake_up_interruptible().
  7. The consumer resumes after its wait condition becomes true.
  8. The module stops the producer thread during cleanup if it is still present.

Makefile

obj-m += wait_queue_producer_consumer.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test

make

sudo insmod wait_queue_producer_consumer.ko

sudo dmesg | tail -30

sudo rmmod wait_queue_producer_consumer

make clean

Expected Output

Producer-consumer module loaded
Producer thread started
Consumer: Waiting for data
Producer: Data is available
Consumer: Data received successfully
Producer-consumer module unloaded
The exact log ordering can vary because the producer and consumer execute concurrently. The producer's delay is illustrative, not a precise real-time timing guarantee.

12. Wait Queues and Race Conditions

Wait queues must be used with correctly synchronized conditions.

Consider the following unsafe conceptual sequence:

  1. A reader checks that data is unavailable.
  2. A producer makes data available and sends a wake-up.
  3. The reader starts waiting after the wake-up has already happened.

If the reader simply waits for a future wake-up without checking the current condition correctly, it may sleep even though data is available.

Correct Approach

Use the standard wait-event macros with a condition that is safely published and checked.

wait_event_interruptible(
    my_wait_queue,
    data_available
);

Update the condition before issuing the wake-up:

data_available = true;

wake_up_interruptible(&my_wait_queue);

For real shared data, use appropriate synchronization and memory-ordering mechanisms. A plain variable accessed concurrently without proper synchronization can cause data races.

Possible mechanisms include:

  • Atomic variables for simple shared state.
  • Spinlocks for short shared-state updates.
  • Mutexes for protected operations in process context.
  • Appropriate memory-ordering primitives when lockless communication is required.
A wake-up operation is not a substitute for protecting shared data. The condition and the data associated with it must be synchronized correctly.

13. Wait Queues vs Semaphores

Feature Wait Queue Semaphore
Primary purpose Wait for a condition or event Manage permits and resource availability
Waiting mechanism Task sleeps until condition is satisfied and it is woken Task sleeps when no permit is available
Condition Explicit condition supplied by the driver Internal semaphore permit count
Wake-up Explicit wake-up operation up() releases a permit and may wake a waiter
Typical application Waiting for incoming device data Limiting access to a resource pool

Wait Queues vs Mutexes

A mutex protects a critical section through ownership. A wait queue lets tasks sleep until a condition is satisfied. A driver may use both: a wait queue for data availability and a mutex for protecting a shared buffer.

14. Important Rules for Wait Queues

  1. Initialize a wait queue before using it.
  2. Always define a meaningful waiting condition.
  3. Use standard wait-event macros where possible.
  4. Make the condition visible safely to all relevant execution contexts.
  5. Update the condition before issuing the wake-up.
  6. Do not assume a wake-up means the condition remains true.
  7. Recheck the condition after waking.
  8. Use interruptible waits when signal cancellation is appropriate.
  9. Use timeouts when the operation must not wait indefinitely.
  10. Do not call sleepable wait operations from interrupt context.

15. Common Wait Queue Mistakes

Mistake Why It Is Wrong
Forgetting to initialize the wait queue. The queue is not ready for use.
Waiting without a valid condition. The task may remain asleep indefinitely.
Updating the condition without proper synchronization. Concurrent accesses can produce incorrect behavior.
Calling a blocking wait in interrupt context. Interrupt context cannot sleep.
Assuming every wake-up means the condition is true. Wake-ups can be spurious or another task may consume the resource first.
Ignoring the return value of interruptible waits. The wait may have been interrupted by a signal.
Using a wake-up instead of proper data locking. Wake-up operations do not automatically protect shared data.

16. Debugging Wait Queue Problems

Useful commands for examining kernel messages:

sudo dmesg | tail -50

sudo journalctl -k -n 50

lsmod | grep wait_queue

When debugging a driver that uses wait queues, investigate:

  • Whether the wait queue was initialized.
  • Whether the condition can actually become true.
  • Whether the producer sends the wake-up after publishing the condition.
  • Whether the consumer handles signals and timeouts.
  • Whether shared state is protected correctly.
  • Whether module cleanup stops producer threads and prevents further access to released resources.
