2. Introduction to Mutexes

A mutex is a synchronization mechanism used to ensure that only one task at a time can access a protected resource.

The term mutex comes from mutual exclusion.

When one task acquires a mutex, another task attempting to acquire the same mutex must wait until the owner releases it.

Unlike a spinlock, a task waiting for a mutex can be put to sleep rather than continuously consuming CPU time.

Example: Shared Device Buffer

Suppose two processes access the same character driver's data buffer.

  • Process A begins writing data.
  • Process B attempts to access the same buffer.
  • Without synchronization, their operations may interfere.
  • A mutex allows Process A to complete its protected operation before Process B enters the critical section.
Process A requests mutex
↓
Process A acquires mutex
↓
Process A accesses shared buffer
↓
Process A releases mutex
↓
Process B acquires mutex and continues

3. Why Are Mutexes Required?

Device drivers frequently maintain shared resources such as:

  • Device data buffers.
  • Configuration structures.
  • Device state variables.
  • Shared file-operation data.
  • Software queues and resource-management structures.

When multiple processes or kernel threads access these resources concurrently, a race condition may occur.

Without a Mutex

static int device_value = 0;

static void update_device_value(void)
{
    device_value++;
}

Concurrent execution of this function may cause lost updates.

With a Mutex

static DEFINE_MUTEX(device_mutex);
static int device_value = 0;

static void update_device_value(void)
{
    mutex_lock(&device_mutex);

    device_value++;

    mutex_unlock(&device_mutex);
}

The mutex ensures that tasks following the same locking protocol do not execute this protected update simultaneously.

4. Mutex Data Structure

Linux provides the struct mutex type for mutex synchronization.

Include the appropriate header:

#include <linux/mutex.h>

Static Initialization

static DEFINE_MUTEX(device_mutex);

DEFINE_MUTEX() declares and statically initializes a mutex.

Dynamic Initialization

static struct mutex device_mutex;

static int __init my_init(void)
{
    mutex_init(&device_mutex);

    return 0;
}

mutex_init() initializes a dynamically declared mutex before it is used.

A mutex must be initialized before use. Do not reinitialize a mutex while another task may be using or waiting for it.

5. Basic Mutex Operations

5.1 mutex_lock()

Acquires a mutex. If another task owns it, the calling task waits until the mutex becomes available.

mutex_lock(&device_mutex);

/* Critical section */

mutex_unlock(&device_mutex);

5.2 mutex_unlock()

Releases a mutex previously acquired by the current task.

mutex_unlock(&device_mutex);

Only the task that owns the mutex should release it.

5.3 mutex_trylock()

Attempts to acquire a mutex without waiting.

if (mutex_trylock(&device_mutex)) {

    /* Mutex successfully acquired */

    mutex_unlock(&device_mutex);

} else {

    pr_info("Mutex is currently unavailable\n");
}

mutex_trylock() returns a non-zero value if the mutex is acquired and zero otherwise.

5.4 mutex_is_locked()

Checks whether a mutex appears to be locked.

if (mutex_is_locked(&device_mutex)) {
    pr_info("Mutex appears to be locked\n");
}

This is a diagnostic check only. It does not acquire the mutex and cannot guarantee that the mutex will remain in the same state after the check.

6. How Does a Mutex Work?

A mutex manages ownership of a protected resource.

Task A requests mutex
↓
Mutex available?
↓
Yes: Task A becomes owner
↓
Task A executes critical section
↓
Task A unlocks mutex
↓
Waiting task can acquire mutex

If the mutex is already owned, a competing task may be placed into a waiting state by the kernel scheduler.

Important Characteristics

  • A mutex has an owner.
  • Only the owner should unlock it.
  • A task waiting for a mutex can sleep.
  • A mutex cannot be used in interrupt context.
  • A mutex is suitable for process-context synchronization.

7. Sleeping Behavior of Mutexes

One major difference between mutexes and spinlocks is the way they wait for access.

Spinlock Waiting

A task repeatedly checks the lock while waiting. This is busy waiting.

Mutex Waiting

A task that cannot acquire a mutex may sleep. The scheduler can run another task instead of making the waiting task continuously consume CPU time.

Task B requests an unavailable mutex
↓
Task B waits and may sleep
↓
Task A continues executing
↓
Task A releases mutex
↓
Task B becomes eligible to continue
The task waiting for a mutex is not guaranteed to run immediately after unlock. The scheduler determines when it runs.

8. Mutexes and Process Context

Mutexes are intended for contexts where sleeping is permitted, especially process context and kernel-thread context.

They are commonly used in:

  • Character driver's open() operation.
  • Character driver's read() and write() operations.
  • Device configuration operations.
  • IOCTL command processing.
  • Shared buffer management.

Example: Protecting a Shared Buffer

#include <linux/mutex.h>

static DEFINE_MUTEX(buffer_mutex);
static char device_buffer[128];

static void update_buffer(void)
{
    mutex_lock(&buffer_mutex);

    /* Modify shared buffer safely */

    mutex_unlock(&buffer_mutex);
}

Every operation that accesses the shared buffer in a way requiring mutual exclusion must follow the same locking protocol.

Never call mutex_lock() from hard interrupt context, softirq context or another atomic context where sleeping is not allowed.

9. Mutex vs Spinlock

Feature Mutex Spinlock
Meaning Mutual exclusion lock Busy-wait synchronization lock
Waiting behavior Waiting task may sleep Waiting CPU spins
Can sleep while held? Yes, in an appropriate sleepable context No
Interrupt context Not permitted Possible with correct IRQ-safe design
Typical critical section Longer or sleepable operations Short, non-sleeping operations
Ownership Has task ownership Does not have mutex-style task ownership
Typical use Shared buffers and device configuration Short shared-state updates

When Should You Use a Mutex?

  • When a protected operation may sleep.
  • When accessing a shared buffer in process context.
  • When performing longer critical sections.
  • When protecting device configuration and state.

When Should You Use a Spinlock?

  • When protecting a very short critical section.
  • When the protected code cannot sleep.
  • When synchronizing process context with an appropriately protected interrupt-related path.

10. Mutex Locking and Error Handling

Some mutex APIs provide different waiting and error-handling behavior.

10.1 mutex_lock()

mutex_lock(&device_mutex);

/* Protected operation */

mutex_unlock(&device_mutex);

Waits until the mutex can be acquired.

10.2 mutex_lock_interruptible()

Attempts to acquire the mutex, allowing the wait to be interrupted by a signal.

int ret;

ret = mutex_lock_interruptible(&device_mutex);

if (ret) {
    return ret;
}

/* Protected operation */

mutex_unlock(&device_mutex);

If the wait is interrupted, the function returns a non-zero error value, commonly -EINTR, and the mutex has not been acquired by that call.

10.3 mutex_trylock()

Attempts immediate acquisition without sleeping.

if (!mutex_trylock(&device_mutex)) {
    return -EBUSY;
}

/* Protected operation */

mutex_unlock(&device_mutex);
Function Behavior
mutex_lock() Waits until acquired.
mutex_lock_interruptible() Wait can be interrupted by a signal.
mutex_trylock() Attempts immediate acquisition.
mutex_unlock() Releases the mutex.

11. Mutexes in Character Device Drivers

A character driver may have a shared data buffer that is accessed by multiple processes.

For example, two applications may open the same device file and attempt to write data at the same time.

A mutex can protect the shared buffer from concurrent modifications.

Conceptual Driver Structure

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/mutex.h>
#include <linux/fs.h>

#define BUFFER_SIZE 128

static DEFINE_MUTEX(device_mutex);
static char device_buffer[BUFFER_SIZE];

static int device_open(struct inode *inode,
                       struct file *file)
{
    return 0;
}

static int device_release(struct inode *inode,
                          struct file *file)
{
    return 0;
}

The mutex can then be used by the driver's read, write or IOCTL operations to protect shared state.

12. Practical Kernel Module: Mutex Counter

Let us implement a simple kernel module that protects a shared counter using a mutex.

Source Code: mutex_counter.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/mutex.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Mutex Counter Demonstration");
MODULE_VERSION("1.0");

static DEFINE_MUTEX(counter_mutex);
static int shared_counter = 0;

static void update_counter(void)
{
    mutex_lock(&counter_mutex);

    shared_counter++;

    mutex_unlock(&counter_mutex);
}

static int __init mutex_counter_init(void)
{
    int i;

    pr_info("Mutex counter module loaded\n");

    for (i = 0; i < 5; i++) {
        update_counter();
    }

    mutex_lock(&counter_mutex);

    pr_info("Counter value = %d\n", shared_counter);

    mutex_unlock(&counter_mutex);

    return 0;
}

static void __exit mutex_counter_exit(void)
{
    pr_info("Mutex counter module unloaded\n");
}

module_init(mutex_counter_init);
module_exit(mutex_counter_exit);

Explanation

  1. linux/mutex.h provides mutex interfaces.
  2. DEFINE_MUTEX() initializes the mutex.
  3. shared_counter stores the shared counter.
  4. mutex_lock() acquires the mutex.
  5. The counter is incremented inside the critical section.
  6. mutex_unlock() releases the mutex.

The module performs five increments during initialization, so the expected counter value is 5.

Makefile

obj-m += mutex_counter.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Ensure that the recipe lines begin with actual tab characters.

Compile and Test in Ubuntu

make

sudo insmod mutex_counter.ko

lsmod | grep mutex_counter

sudo dmesg | tail -20

sudo rmmod mutex_counter

sudo dmesg | tail -20

make clean

Expected Output

Mutex counter module loaded
Counter value = 5
Mutex counter module unloaded
This module demonstrates mutex initialization, locking and unlocking. Its initialization loop is sequential and does not create real concurrent contention.

13. Practical Example: Protecting a Shared Character Driver Buffer

The following example demonstrates a mutex-protected write operation in a character driver.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/mutex.h>
#include <linux/uaccess.h>
#include <linux/errno.h>
#include <linux/string.h>

#define BUFFER_SIZE 128

static DEFINE_MUTEX(buffer_mutex);
static char device_buffer[BUFFER_SIZE];

static ssize_t device_write(struct file *file,
                            const char __user *user_buffer,
                            size_t count,
                            loff_t *position)
{
    size_t len;

    if (count == 0)
        return 0;

    if (mutex_lock_interruptible(&buffer_mutex))
        return -ERESTARTSYS;

    len = min(count, (size_t)(BUFFER_SIZE - 1));

    if (copy_from_user(device_buffer,
                       user_buffer,
                       len)) {
        mutex_unlock(&buffer_mutex);
        return -EFAULT;
    }

    device_buffer[len] = '\0';

    mutex_unlock(&buffer_mutex);

    return len;
}

Explanation

  1. The mutex protects the shared buffer.
  2. mutex_lock_interruptible() acquires the mutex or returns if the wait is interrupted.
  3. The write length is limited to the buffer capacity.
  4. copy_from_user() transfers data from user space.
  5. If the copy fails, the mutex is released before returning -EFAULT.
  6. The mutex is released after the buffer update.
This is a write-callback fragment, not a complete character driver. A complete implementation must also handle registration, open/release, read behavior, file-position semantics and device lifetime. copy_from_user() returns the number of bytes not copied, not a negative error code.

Because copy_from_user() may sleep, using a mutex in this process-context callback is appropriate. A spinlock must not be held across this operation.

14. Mutex Ownership and Deadlocks

A mutex is owned by the task that successfully acquires it.

Important Ownership Rules

  • The owning task should release the mutex.
  • A different task must not attempt to unlock a mutex owned by another task.
  • A task must not recursively acquire the same ordinary mutex.
  • Every successful acquisition must have a corresponding release.

Example of Incorrect Recursive Locking

static DEFINE_MUTEX(my_mutex);

static void operation(void)
{
    mutex_lock(&my_mutex);

    /* Incorrect: attempts to acquire the same mutex again */
    mutex_lock(&my_mutex);

    mutex_unlock(&my_mutex);
    mutex_unlock(&my_mutex);
}

This can deadlock because the task already owns the mutex and waits for itself to release it.

Deadlock Prevention

  • Maintain a consistent lock acquisition order.
  • Avoid recursive acquisition.
  • Keep lock ownership and release paths clear.
  • Use lockdep-enabled kernels to help identify locking errors.

15. Mutex and Atomic Operations

Atomic operations and mutexes solve different synchronization problems.

Feature Atomic Operation Mutex
Primary purpose Simple atomic data updates Mutual exclusion over a critical section
Lock ownership No mutex-style ownership Owned by the acquiring task
Waiting Individual operation executes atomically Competing task may sleep
Multiple related fields Not automatically protected together Can protect a coordinated update
Interrupt context Many atomic operations are suitable Not suitable

For a single independent event counter, an atomic operation may be simpler. For a shared buffer that requires several coordinated operations, a mutex is usually more appropriate in process context.

16. Common Mutex Mistakes

Mistake Correct Practice
Using a mutex in interrupt context. Use an appropriate non-sleeping synchronization mechanism.
Forgetting to unlock the mutex. Ensure every successful lock acquisition has a matching unlock.
Unlocking a mutex from a different task. Only the owning task should unlock it.
Acquiring the same mutex recursively. Redesign the locking structure to avoid recursive acquisition.
Using different mutexes for the same shared data without a valid protocol. Use a consistent synchronization design.
Assuming a mutex protects unguarded accesses. Ensure all relevant accesses follow the same locking protocol.
Holding multiple mutexes in inconsistent orders. Establish a consistent lock ordering.

17. Debugging Mutex Problems

Kernel logs and lock debugging facilities can help identify mutex-related problems.

Inspect Kernel Messages

sudo dmesg | tail -50

sudo journalctl -k -n 50

Inspect Lock Debugging Configuration

grep -E 'CONFIG_PROVE_LOCKING|CONFIG_DEBUG_MUTEXES|CONFIG_LOCKDEP' \
/boot/config-$(uname -r)

Depending on kernel configuration, lockdep and mutex debugging facilities can help identify:

  • Potential deadlocks.
  • Incorrect lock ordering.
  • Recursive locking problems.
  • Invalid locking or unlocking behavior.
