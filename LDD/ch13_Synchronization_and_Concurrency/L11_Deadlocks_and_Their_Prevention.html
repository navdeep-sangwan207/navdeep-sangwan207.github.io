2. Introduction to Deadlocks

A deadlock is a situation in which two or more tasks are permanently blocked because each task is waiting for a resource or lock held by another task in the same dependency cycle.

In Linux kernel programming, deadlocks can occur when synchronization mechanisms such as mutexes, spinlocks and semaphores are used incorrectly.

Simple Example

Consider two kernel threads:

  • Thread A holds Lock 1 and waits for Lock 2.
  • Thread B holds Lock 2 and waits for Lock 1.

Neither thread can continue because each is waiting for the other to release its lock.

Thread A
↓
Holds Lock 1
↓
Waits for Lock 2
Thread B
↓
Holds Lock 2
↓
Waits for Lock 1
↓
Deadlock: Neither thread can proceed

3. How Deadlocks Occur in Linux Device Drivers

Device drivers often protect shared resources using locks.

For example, a driver may have:

  • A mutex protecting device configuration.
  • A spinlock protecting interrupt-shared status.
  • A mutex protecting a data buffer.
  • A semaphore controlling access to a limited resource.

If different execution paths acquire these locks in inconsistent orders, a deadlock may occur.

Example Scenario

Thread A Thread B
Acquires Lock A Acquires Lock B
Requests Lock B Requests Lock A
Waits for Thread B Waits for Thread A

Both threads remain blocked because neither releases the lock it already holds.

4. Four Necessary Conditions for Deadlock

In the classical operating-system model, a deadlock can occur only when all four of the following conditions exist simultaneously.

4.1 Mutual Exclusion

A resource can be held by only one task at a time.

Example: A mutex provides exclusive ownership.

mutex_lock(&device_mutex);

/* Exclusive access to protected data */

mutex_unlock(&device_mutex);

4.2 Hold and Wait

A task holds one resource while waiting to acquire another resource.

Example:

mutex_lock(&lock_a);

mutex_lock(&lock_b);

/* Use protected resources */

mutex_unlock(&lock_b);
mutex_unlock(&lock_a);

If another task holds Lock B and waits for Lock A, a deadlock may occur.

4.3 No Preemption

A resource cannot simply be taken away from a task holding it. The task must release the resource according to the locking mechanism's rules.

For example, a mutex is not normally forcibly taken from its owner to satisfy another task's request.

4.4 Circular Wait

A circular dependency exists when each task waits for a resource held by another task in the cycle.

Thread A → waits for Lock B
↓
Thread B → waits for Lock C
↓
Thread C → waits for Lock A
↓
Thread A is waiting again
↓
Deadlock Cycle

Summary of Four Conditions

Condition Meaning
Mutual Exclusion Only one task can use a resource at a time.
Hold and Wait A task holds one resource while requesting another.
No Preemption A held resource cannot be forcibly taken away.
Circular Wait Tasks form a circular dependency while waiting for resources.
These are the four classical necessary conditions. Preventing at least one of them prevents deadlock under this model.

5. Deadlock Example Using Mutexes

Consider two mutexes protecting two shared resources.

Problematic Locking Pattern

static DEFINE_MUTEX(lock_a);
static DEFINE_MUTEX(lock_b);

/* Thread A */
static void thread_a_function(void)
{
    mutex_lock(&lock_a);

    mutex_lock(&lock_b);

    /* Access shared resources */

    mutex_unlock(&lock_b);
    mutex_unlock(&lock_a);
}

/* Thread B */
static void thread_b_function(void)
{
    mutex_lock(&lock_b);

    mutex_lock(&lock_a);

    /* Access shared resources */

    mutex_unlock(&lock_a);
    mutex_unlock(&lock_b);
}

Why Is This Dangerous?

  1. Thread A acquires Lock A.
  2. Thread B acquires Lock B.
  3. Thread A requests Lock B and waits.
  4. Thread B requests Lock A and waits.
  5. Neither thread can proceed.
This code illustrates an unsafe lock-ordering pattern. It is not a test to run in a production kernel or on a normal development system.

6. Deadlock Prevention Technique 1: Consistent Lock Ordering

One of the most effective ways to prevent lock-order deadlocks is to acquire multiple locks in a consistent global order.

For example, always acquire Lock A before Lock B.

Corrected Pattern

static DEFINE_MUTEX(lock_a);
static DEFINE_MUTEX(lock_b);

/* Thread A */
static void thread_a_function(void)
{
    mutex_lock(&lock_a);

    mutex_lock(&lock_b);

    /* Access shared resources */

    mutex_unlock(&lock_b);
    mutex_unlock(&lock_a);
}

/* Thread B */
static void thread_b_function(void)
{
    mutex_lock(&lock_a);

    mutex_lock(&lock_b);

    /* Access shared resources */

    mutex_unlock(&lock_b);
    mutex_unlock(&lock_a);
}

Both threads acquire Lock A first and Lock B second.

Acquire Lock A
↓
Acquire Lock B
↓
Perform Protected Operations
↓
Release Lock B
↓
Release Lock A

This removes the circular lock-order dependency between these two locks.

7. Deadlock Prevention Technique 2: Avoid Unnecessary Nested Locks

Nested locking means acquiring one lock while already holding another lock.

Nested locking is sometimes necessary, but unnecessary nesting increases the risk of deadlocks.

Recommended Approach

  • Determine whether both locks are actually required.
  • Keep the number of simultaneously held locks small.
  • Define a consistent acquisition order.
  • Document the locking order for complex drivers.
  • Release locks as soon as the protected operation is complete.
Releasing one lock before acquiring another may reduce deadlock risk, but it can also introduce race conditions if the shared state changes between the two operations. Recheck conditions after reacquiring locks where necessary.

8. Deadlock Prevention Technique 3: Keep Critical Sections Short

A critical section is the part of code that accesses shared data while holding a lock.

Long critical sections increase contention and make locking problems harder to diagnose.

Bad Practice

spin_lock(&my_lock);

msleep(1000);       /* Invalid: sleeping while holding spinlock */

spin_unlock(&my_lock);

The example is invalid because msleep() may sleep while a spinlock is held.

Better Practice

spin_lock(&my_lock);

/* Perform short, non-sleeping operation */

spin_unlock(&my_lock);

/* Sleep only after releasing the spinlock */
msleep(1000);

For longer operations that must sleep, consider an appropriate sleepable synchronization primitive, such as a mutex, when the execution context permits it.

9. Deadlock Prevention Technique 4: Use Try-Lock Carefully

Some synchronization primitives provide try-lock operations. They attempt to acquire a lock without waiting indefinitely.

Mutex Try-Lock

if (mutex_trylock(&device_mutex)) {

    /* Lock acquired */

    /* Perform protected operation */

    mutex_unlock(&device_mutex);

} else {

    pr_info("Device is busy\n");
}

mutex_trylock() returns non-zero when the lock is acquired and zero when it is unavailable.

Spinlock Try-Lock

if (spin_trylock(&my_lock)) {

    /* Lock acquired */

    /* Short critical section */

    spin_unlock(&my_lock);

} else {

    pr_info("Lock unavailable\n");
}

Try-lock operations can help avoid blocking in selected designs, but they do not automatically solve deadlocks. The driver must handle failure and maintain data consistency correctly.

10. Deadlocks Involving Interrupt Context

Deadlocks can also occur when process context and interrupt context use the same spinlock incorrectly.

Example Scenario

  1. A process acquires a spinlock.
  2. A local hardware interrupt occurs.
  3. The interrupt handler tries to acquire the same spinlock.
  4. The interrupt handler spins waiting for the process.
  5. The process cannot resume because the interrupt handler has not returned.
Process Context
↓
Acquires spinlock
↓
Local interrupt occurs
↓
Interrupt Handler requests same lock
↓
Interrupt Handler spins
↓
Process cannot resume: Deadlock

Correct Process-Context Locking

unsigned long flags;

spin_lock_irqsave(&my_lock, flags);

/* Access data shared with hard IRQ */

spin_unlock_irqrestore(&my_lock, flags);

The interrupt handler uses the corresponding non-sleeping lock operation:

spin_lock(&my_lock);

/* Access shared data */

spin_unlock(&my_lock);
This pattern applies to traditional non-RT spinlock semantics. PREEMPT_RT changes the behavior of many spinlock APIs; follow the target kernel's interrupt and locking rules.

11. Lock Ordering in Device Drivers

Complex device drivers may use multiple locks to protect different resources.

Example:

Lock Protected Resource
config_lock Device configuration
buffer_lock Shared data buffer
status_lock Device status information

A driver should define a consistent acquisition order, for example:

config_lock
↓
buffer_lock
↓
status_lock

Any code path that needs multiple locks must follow the same order. A code path must not acquire status_lock and then request config_lock if another path uses the opposite order.

12. Linux Kernel Lockdep

Lockdep is the Linux kernel lock dependency validator.

It helps detect potential locking problems, including:

  • Inconsistent lock ordering.
  • Potential circular lock dependencies.
  • Some recursive locking errors.
  • Incorrect locking usage detected by lock validation.

How Lockdep Works

Lockdep observes lock acquisition and release patterns while the kernel is running. It builds a dependency model and checks whether newly observed dependencies could form a cycle.

Kernel Lock Acquisition
↓
Lockdep Records Dependencies
↓
Checks Lock Ordering
↓
Reports Potential Locking Problems

Checking Kernel Configuration

Lockdep-related debugging options commonly include:

CONFIG_LOCKDEP
CONFIG_PROVE_LOCKING
CONFIG_DEBUG_LOCK_ALLOC
CONFIG_DEBUG_MUTEXES

Availability depends on the kernel version and configuration. Check the running kernel configuration where available:

grep -E 'CONFIG_(LOCKDEP|PROVE_LOCKING|DEBUG_LOCK_ALLOC|DEBUG_MUTEXES)' \
/boot/config-$(uname -r)

Alternatively, inspect:

zcat /proc/config.gz | grep LOCKDEP

The second command works only if the kernel exposes its configuration through /proc/config.gz.

Viewing Lockdep Warnings

sudo dmesg | grep -i -E 'lockdep|possible circular|deadlock'

sudo journalctl -k | grep -i lockdep
Lockdep detects many potential locking errors, but it cannot prove that every possible execution path is deadlock-free. A lack of warnings does not guarantee correct synchronization.

13. Lockdep Locking Assertions

Kernel code can use lockdep-related assertions to verify that a required lock is held when a function is called.

Example: lockdep_assert_held()

#include <linux/mutex.h>
#include <linux/lockdep.h>

static DEFINE_MUTEX(data_mutex);

static int shared_value = 100;

static void update_shared_value(int new_value)
{
    lockdep_assert_held(&data_mutex);

    shared_value = new_value;
}

static void update_device_data(int new_value)
{
    mutex_lock(&data_mutex);

    update_shared_value(new_value);

    mutex_unlock(&data_mutex);
}

lockdep_assert_held() documents and checks the expectation that the mutex is held when the protected function executes, when the relevant lock validation support is enabled.

It is a debugging assertion, not a replacement for acquiring the lock.

14. Deadlock Detection vs Deadlock Prevention

Deadlock Prevention Deadlock Detection
Designs the program to avoid deadlock conditions. Identifies potential or existing locking problems.
Uses consistent lock ordering. Uses debugging and validation mechanisms.
Keeps critical sections controlled. Examines lock dependencies.
Reduces circular wait. Lockdep reports dependency cycles and other problems.

15. Other Locking Problems

15.1 Self-Deadlock

A task attempts to acquire a non-recursive mutex that it already holds.

mutex_lock(&my_mutex);

mutex_lock(&my_mutex);  /* Incorrect recursive acquisition */

mutex_unlock(&my_mutex);

Linux mutexes are not recursive. Acquiring the same mutex again from its owner can result in a deadlock.

15.2 Lock Inversion

Lock inversion occurs when different execution paths acquire locks in conflicting orders.

15.3 Sleeping While Holding a Spinlock

A spinlock must not be held across a sleeping operation. This can cause serious scheduling and locking failures.

15.4 Interrupt-Related Deadlock

Incorrect locking between process context and interrupt context can cause an interrupt handler to spin on a lock held by the interrupted process.

16. Best Practices for Deadlock Prevention

  1. Define a global lock acquisition order.
  2. Avoid unnecessary nested locking.
  3. Keep critical sections short.
  4. Never sleep while holding a spinlock.
  5. Use IRQ-safe locking when required by the interrupt-sharing design.
  6. Use mutexes only in sleepable contexts.
  7. Release locks on every applicable error path.
  8. Document complex locking rules.
  9. Use lockdep-enabled kernels during development and testing.
  10. Review all execution paths that access shared driver data.

17. Practical Exercise: Safe Lock Ordering

Consider two shared resources protected by two mutexes.

Task

Write a kernel module with two mutexes:

static DEFINE_MUTEX(lock_a);
static DEFINE_MUTEX(lock_b);

Implement two functions that:

  1. Acquire lock_a first.
  2. Acquire lock_b second.
  3. Access protected data.
  4. Release lock_b first.
  5. Release lock_a last.

Verify that both functions follow the same lock acquisition order.

Expected Learning Outcome

You should understand how a consistent lock hierarchy removes circular dependencies between the two mutexes.

18. Lesson Summary

  • A deadlock occurs when tasks wait indefinitely for resources held by one another.
  • Four necessary conditions are mutual exclusion, hold and wait, no preemption and circular wait.
  • Inconsistent lock ordering is a common cause of deadlock.
  • Consistent lock ordering is a major prevention technique.
  • Nested locking should be controlled and documented.
  • Critical sections should be kept short.
  • Try-lock operations can help in selected designs but do not automatically prevent deadlocks.
  • Interrupt-related locking requires careful design.
  • Lockdep validates lock dependencies and reports potential problems.
  • Deadlock prevention must be part of the driver design, not merely a debugging activity.
