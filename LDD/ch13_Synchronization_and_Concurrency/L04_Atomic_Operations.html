2. Introduction to Atomic Operations

In a Linux kernel, multiple execution contexts may access the same shared variable. These contexts can include:

  • Multiple processes or kernel threads.
  • Different CPUs executing concurrently.
  • Process context and interrupt context.
  • Different parts of a device driver.

If two execution contexts modify a shared variable simultaneously, a race condition may occur.

Atomic operation: An operation that is performed as an indivisible operation with respect to the other accesses covered by its atomicity guarantee. Other CPUs cannot observe a partially completed atomic read-modify-write operation.

Example: Shared Event Counter

Suppose a device driver maintains an event counter. Every time an event occurs, the counter must increase by one.

counter++;

This statement looks like a single operation in C, but it generally involves multiple steps:

  1. Read the current counter value.
  2. Add one to the value.
  3. Write the updated value back.

Two CPUs may interleave these steps and overwrite each other's updates.

Initial counter = 5
↓
CPU 0 reads 5    CPU 1 reads 5
↓
CPU 0 calculates 6    CPU 1 calculates 6
↓
CPU 0 writes 6    CPU 1 writes 6
↓
Final counter = 6 (incorrect)

The expected result was 7, but the final result is 6. One increment has been lost. This is called a lost update.

3. Why Atomic Operations Are Required

Atomic operations are useful when a driver needs to update a simple shared integer or individual bits without protecting the operation with a general-purpose lock.

Common applications include:

  • Counting hardware events.
  • Maintaining packet or interrupt counters.
  • Tracking error occurrences.
  • Maintaining simple shared state flags.
  • Performing compare-and-exchange algorithms.
  • Updating individual status bits.

Atomic Increment

atomic_inc(&event_count);

The kernel provides an atomic increment operation. Concurrent atomic increments on the same atomic object are serialized with respect to that object's update, so increments are not lost.

CPU 0 requests atomic increment
↓
Kernel performs atomic update
↓
CPU 1 requests atomic increment
↓
Second atomic update is performed
↓
Both increments are preserved

4. Linux Kernel Atomic Data Types

The Linux kernel provides special data types for atomic integer operations.

4.1 atomic_t

atomic_t is the standard atomic integer type used by the Linux kernel.

#include <linux/atomic.h>

atomic_t event_count = ATOMIC_INIT(0);

Here:

  • atomic_t declares an atomic integer object.
  • event_count is the variable name.
  • ATOMIC_INIT(0) initializes the value to zero.

4.2 atomic64_t

atomic64_t provides atomic operations on a 64-bit integer where supported by the target kernel architecture.

atomic64_t total_events = ATOMIC64_INIT(0);

It is useful when a counter needs a larger numeric range than the standard atomic integer type provides.

Type Purpose Initialization
atomic_t Atomic integer operations ATOMIC_INIT(0)
atomic64_t Atomic 64-bit integer operations ATOMIC64_INIT(0)
Important: Do not access the internal representation of an atomic object directly. Use the documented atomic APIs instead of accessing fields such as counter.

5. Basic Atomic Operations

The Linux kernel provides several functions for manipulating atomic variables.

5.1 atomic_read()

Reads the current value of an atomic variable.

int value;

value = atomic_read(&event_count);

5.2 atomic_set()

Sets an atomic variable to a specified value.

atomic_set(&event_count, 10);

5.3 atomic_add()

Adds a specified value to an atomic variable.

atomic_add(5, &event_count);

5.4 atomic_sub()

Subtracts a specified value.

atomic_sub(2, &event_count);

5.5 atomic_inc()

Increments an atomic variable by one.

atomic_inc(&event_count);

5.6 atomic_dec()

Decrements an atomic variable by one.

atomic_dec(&event_count);
Function Operation
atomic_read()Reads the value.
atomic_set()Sets the value.
atomic_add()Adds a number.
atomic_sub()Subtracts a number.
atomic_inc()Increments by one.
atomic_dec()Decrements by one.

6. Atomic Operations That Return Values

Some atomic functions perform an update and also return a value. Understanding whether the returned value is the old or new value is important.

6.1 atomic_inc_return()

Increments the variable and returns the updated value.

int value;

value = atomic_inc_return(&event_count);

If the previous value was 5, the new value is 6 and the function returns 6.

6.2 atomic_dec_return()

Decrements the variable and returns the updated value.

int value;

value = atomic_dec_return(&event_count);

6.3 atomic_add_return()

Adds a specified value and returns the new value.

int value;

value = atomic_add_return(5, &event_count);

6.4 atomic_xchg()

Atomically replaces the current value with a new value and returns the old value.

int old_value;

old_value = atomic_xchg(&event_count, 100);

6.5 atomic_cmpxchg()

Performs an atomic compare-and-exchange operation.

int old_value;

old_value = atomic_cmpxchg(&event_count, 10, 20);

The operation compares the current value with 10:

  • If the current value is 10, it changes the value to 20.
  • If the current value is not 10, it leaves the value unchanged.
  • It returns the old value observed by the operation.
Function Return value
atomic_inc_return() New value after increment
atomic_dec_return() New value after decrement
atomic_add_return() New value after addition
atomic_xchg() Old value before replacement
atomic_cmpxchg() Old value observed during comparison

7. Compare-and-Exchange: Practical Explanation

Compare-and-exchange is useful when a value should be changed only if it still contains an expected value.

Consider a simple state variable:

atomic_t device_state = ATOMIC_INIT(0);

Suppose:

  • 0 means device is idle.
  • 1 means device is busy.

A driver can attempt to change the state from idle to busy:

if (atomic_cmpxchg(&device_state, 0, 1) == 0) {
    pr_info("Device successfully marked busy\n");
} else {
    pr_info("Device was already busy\n");
}

The comparison and conditional update happen atomically. Two CPUs attempting this operation cannot both successfully change the same state from 0 to 1.

Current state = 0 (IDLE)
↓
Compare current state with expected value 0
↓
Match found: replace 0 with 1
↓
New state = 1 (BUSY)
This example demonstrates an atomic state transition. More complex device state management may require additional locking and careful ordering.

8. Conditional Atomic Operations

The kernel also provides useful conditional atomic operations. Their availability and exact interfaces should be checked against the target kernel version.

8.1 atomic_add_unless()

Adds a value unless the current value equals a specified condition.

int result;

result = atomic_add_unless(&event_count, 1, 100);

The operation adds 1 unless the current value is 100. The function returns a non-zero value when the addition occurs and zero when the specified condition prevents it.

8.2 atomic_inc_not_zero()

Increments an atomic variable only if its current value is not zero.

int result;

result = atomic_inc_not_zero(&event_count);

This can be useful in certain reference-counting or state-management patterns. For object lifetime management, use the dedicated refcount_t API rather than implementing reference counting with ordinary atomic_t.

9. Atomic Bit Operations

Device drivers frequently maintain status information using individual bits. Linux provides bit-operation APIs for this purpose.

These operations generally work on memory locations containing unsigned long bitmaps.

Common Bit Operations

set_bit(0, &flags);
clear_bit(0, &flags);
change_bit(0, &flags);

test_bit(0, &flags);

test_and_set_bit(1, &flags);
test_and_clear_bit(1, &flags);
Function Purpose
set_bit() Sets the selected bit to 1.
clear_bit() Clears the selected bit to 0.
change_bit() Toggles the selected bit.
test_bit() Reads and tests the selected bit without modifying it.
test_and_set_bit() Sets the bit and returns its previous value.
test_and_clear_bit() Clears the bit and returns its previous value.

Example: Device Status Flags

#include <linux/bitops.h>

unsigned long device_flags = 0;

/* Set bit 0 */
set_bit(0, &device_flags);

/* Check bit 0 */
if (test_bit(0, &device_flags)) {
    pr_info("Device is ready\n");
}

/* Clear bit 0 */
clear_bit(0, &device_flags);

Bit numbering starts at bit zero. For example, bit 0 represents the least significant bit of the first machine word in the bitmap.

Important: Bit-operation guarantees differ by function. For example, test_bit() is a read-only test; it does not modify the bit. Some bit operations have non-atomic variants, so consult the API documentation for the exact operation and required ordering.

10. Atomic Operations vs Mutexes vs Spinlocks

Atomic operations are not a replacement for every synchronization mechanism.

Feature Atomic Operations Mutex Spinlock
Primary purpose Simple atomic updates Protecting larger critical sections Protecting short critical sections
Can sleep while held? Atomic operations themselves do not sleep May sleep while waiting Must not sleep while held
Suitable for interrupt context? Many atomic operations are suitable No With correct IRQ-safe locking design
Protect multiple related fields? Not by themselves Yes Yes
Typical use Event counter Shared device buffer Short shared-state update

When Should You Use Atomic Operations?

  • When updating a simple shared counter.
  • When performing a simple atomic state transition.
  • When setting or clearing individual shared bits.
  • When a complete lock-protected critical section is unnecessary.

When Should You Use a Lock?

  • When multiple related variables must remain consistent.
  • When a data structure requires several coordinated updates.
  • When a complete sequence of operations must be protected.
  • When an operation involves a shared buffer or complex state.
Example: Suppose a driver updates both event_count and last_event_time. Making the counter atomic does not automatically make the pair of updates consistent. A suitable lock or another carefully designed synchronization protocol may be necessary.

11. Atomicity and Memory Ordering

Atomicity and memory ordering are related but different concepts.

  • Atomicity: Prevents an atomic read-modify-write operation from being observed as a partially completed update.
  • Memory ordering: Defines the ordering and visibility of memory accesses between CPUs and execution contexts.

An atomic operation does not automatically provide every memory-ordering guarantee that a driver may need.

Example: Publishing Shared Data

Consider a producer that prepares data and then sets a ready flag. Another CPU checks the flag before reading the data.

/* Conceptual example: ordering matters */

/* Producer */
shared_data = 123;
atomic_set(&ready, 1);

/* Consumer */
if (atomic_read(&ready)) {
    value = shared_data;
}

This simplified example must not be treated as a complete publication protocol. The ordering and visibility of shared_data relative to the flag must be guaranteed by the appropriate kernel memory-ordering primitives.

Depending on the design, use documented acquire/release operations, such as appropriate atomic acquire/release variants, or explicit memory barriers. The exact API must be checked in the target kernel headers.

Do not assume that every atomic operation provides full memory barriers. Consult the Linux kernel memory model and the documentation for the exact operation being used.

Why volatile Is Not Enough

volatile int counter;

The volatile qualifier does not make an increment atomic, does not prevent lost updates, and does not provide a complete synchronization protocol between CPUs.

Use kernel atomic APIs or appropriate locking primitives instead.

12. Atomic Counter in a Linux Kernel Module

Let us implement a simple kernel module that maintains an atomic event counter.

Source Code: atomic_counter.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/atomic.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Atomic Counter Demonstration");
MODULE_VERSION("1.0");

static atomic_t event_count = ATOMIC_INIT(0);

static int __init atomic_counter_init(void)
{
    int value;

    pr_info("Atomic counter module loaded\n");

    atomic_inc(&event_count);
    atomic_inc(&event_count);
    atomic_inc(&event_count);

    value = atomic_read(&event_count);

    pr_info("Event count = %d\n", value);

    return 0;
}

static void __exit atomic_counter_exit(void)
{
    pr_info("Atomic counter module unloaded\n");
    pr_info("Final event count = %d\n",
            atomic_read(&event_count));
}

module_init(atomic_counter_init);
module_exit(atomic_counter_exit);

Explanation

  1. linux/atomic.h provides atomic operation interfaces.
  2. ATOMIC_INIT(0) initializes the counter.
  3. Each call to atomic_inc() increases the counter by one.
  4. atomic_read() reads the current value.
  5. The exit function prints the final value before the module is unloaded.

Makefile

obj-m += atomic_counter.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Important: The Makefile recipe lines must begin with actual tab characters.

Compile and Test in Ubuntu

make

sudo insmod atomic_counter.ko

lsmod | grep atomic_counter

sudo dmesg | tail -20

sudo rmmod atomic_counter

sudo dmesg | tail -20

make clean

Expected Kernel Log Output

Atomic counter module loaded
Event count = 3
Atomic counter module unloaded
Final event count = 3

The example performs three increments during module initialization. Therefore, the displayed counter value is 3.

This demonstration validates the atomic API usage, but its initialization function does not create concurrent execution. The counter is suitable for concurrent updates when the same atomic object is accessed through its documented atomic APIs.

13. Compare-and-Exchange Example

The following example demonstrates how atomic_cmpxchg() can be used to change a device state only when the expected old state is present.

Source Code: atomic_state.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/atomic.h>

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Atomic Compare and Exchange Example");

#define DEVICE_IDLE 0
#define DEVICE_BUSY 1

static atomic_t device_state = ATOMIC_INIT(DEVICE_IDLE);

static int __init atomic_state_init(void)
{
    int old_state;

    old_state = atomic_cmpxchg(
        &device_state,
        DEVICE_IDLE,
        DEVICE_BUSY
    );

    if (old_state == DEVICE_IDLE) {
        pr_info("Device changed from IDLE to BUSY\n");
    } else {
        pr_info("Device was already BUSY\n");
    }

    return 0;
}

static void __exit atomic_state_exit(void)
{
    pr_info("Final device state = %d\n",
            atomic_read(&device_state));
}

module_init(atomic_state_init);
module_exit(atomic_state_exit);

Expected Output

Device changed from IDLE to BUSY
Final device state = 1

Since the initial value is 0, the compare-and-exchange operation changes it to 1 and returns the previous value, which is 0.

14. Atomic Counters and Reference Counting

Atomic counters are useful for tracking events, but object lifetime management requires additional care.

Event Counter

A driver may use an atomic counter to track:

  • Number of received packets.
  • Number of hardware events.
  • Number of detected errors.
  • Number of completed operations.

Reference Counting

Reference counting tracks how many active users hold references to an object. The object should be released only when its reference count reaches zero and no other lifetime constraints remain.

Although atomic operations can implement basic counting, Linux provides refcount_t specifically for reference counting.

refcount_t includes additional protections against problems such as reference-count overflow and underflow.

Do not use a plain atomic_t as a casual replacement for refcount_t when managing object lifetimes. Use the dedicated reference-counting API and follow its documented ownership rules.

15. Common Mistakes in Atomic Operations

Mistake Correct Practice
Using counter++ on an atomic variable. Use atomic_inc().
Directly accessing internal atomic fields. Use documented atomic APIs.
Assuming atomic operations protect multiple variables. Use a suitable lock or synchronization protocol.
Assuming every atomic operation provides full memory ordering. Check the documented ordering guarantees.
Using volatile instead of synchronization. Use atomic APIs, locks and memory barriers as appropriate.
Using atomic_t for all reference-counting tasks. Prefer refcount_t for object lifetime management.
Assuming all atomic APIs are identical across kernel versions. Check the target kernel headers and documentation.

16. Practical Applications in Device Drivers

Application 1: Interrupt Event Counter

A driver can maintain an event counter that is incremented whenever a hardware interrupt is handled, provided the selected atomic operation is appropriate for that context.

static atomic_t irq_count = ATOMIC_INIT(0);

/* In an appropriate interrupt handler */
atomic_inc(&irq_count);

Application 2: Packet Counter

A network-related driver may count packets processed by different execution contexts.

static atomic_t packet_count = ATOMIC_INIT(0);

atomic_inc(&packet_count);

Application 3: Error Counter

A driver may maintain a shared error counter.

static atomic_t error_count = ATOMIC_INIT(0);

atomic_inc(&error_count);

pr_err("Total errors: %d\n",
       atomic_read(&error_count));

For high-frequency statistics, consider whether per-CPU counters or other specialized mechanisms are more appropriate. A single shared atomic counter may become a contention point on a heavily loaded multi-CPU system.

17. Important Linux Kernel Headers

Header Purpose
<linux/atomic.h> Atomic integer operation interfaces.
<linux/bitops.h> Bit manipulation operations.
<linux/refcount.h> Reference-counting interfaces.
<linux/memory.h> Some memory-management and barrier-related interfaces; use the specific documented header for the API being used.

For accurate development, inspect the headers and documentation corresponding to the kernel version against which the module is compiled.

18. Lesson Summary

  • Atomic operations perform supported updates indivisibly with respect to concurrent accesses to the same atomic object.
  • Ordinary read-modify-write expressions such as counter++ can cause lost updates.
  • atomic_t is used for atomic integer operations.
  • atomic64_t supports atomic 64-bit integer operations where available.
  • atomic_inc(), atomic_dec(), atomic_add() and atomic_sub() modify atomic variables.
  • atomic_inc_return() returns the updated value.
  • atomic_cmpxchg() compares and conditionally updates an atomic variable, returning the old value.
  • Bit-operation APIs help manage shared flags.
  • Atomicity does not automatically provide every required memory-ordering guarantee.
  • Mutexes and spinlocks remain necessary for complex critical sections.
  • refcount_t is preferred for object reference counting.
