2. Introduction to Completions

A completion is a Linux kernel synchronization mechanism that allows one execution context to wait until another execution context signals that an operation has finished.

It is especially useful when a task starts an asynchronous operation and must wait for its completion.

Example Scenario

Consider a driver that starts a hardware operation.

  1. The driver starts a device operation.
  2. The operation continues asynchronously.
  3. The calling task waits for the operation to finish.
  4. The hardware generates an interrupt when the operation completes.
  5. The interrupt handler signals the completion.
  6. The waiting task resumes.
Process Context
↓
Start Hardware Operation
↓
wait_for_completion()
↓
Task Sleeps
Hardware Finishes Operation
↓
Interrupt Handler
↓
complete()
↓
Waiting Task Resumes

3. Why Are Completions Required?

Many device operations do not finish immediately.

Examples include:

  • Waiting for a hardware command to finish.
  • Waiting for a DMA transfer to complete.
  • Waiting for a firmware-loading operation to finish.
  • Waiting for a kernel thread to complete a task.
  • Waiting for an asynchronous device response.

A completion provides a direct way to communicate that a particular event has occurred.

Without Completion

A task might repeatedly check whether an operation has finished. This wastes CPU resources if the operation takes a long time.

With Completion

The task sleeps until another execution context signals that the event has occurred.

4. Completion Data Structure

Linux defines the completion mechanism using:

struct completion

Include the following header:

#include <linux/completion.h>

A completion object maintains internal state and a wait queue. Drivers should use the public completion API instead of accessing its internal fields directly.

Basic Declaration

static struct completion my_completion;

This declares a completion object. It must be initialized before use.

5. Initializing Completion Objects

5.1 Static Initialization

static DECLARE_COMPLETION(my_completion);

DECLARE_COMPLETION() declares and initializes a completion object.

5.2 Dynamic Initialization

static struct completion my_completion;

static int __init my_init(void)
{
    init_completion(&my_completion);

    return 0;
}

init_completion() initializes a completion object at runtime.

Initialize the completion before any task can wait on it or signal it. Do not reinitialize a completion while other tasks may still be waiting on it or using it.

6. Completion Signaling Operations

6.1 complete()

complete() signals that an event has occurred.

complete(&my_completion);

If a task is waiting, one waiter can be awakened. If no task is waiting, the completion records a signal so that a later waiter can consume it.

6.2 complete_all()

complete_all() signals the completion for all current and future waiters until the completion is reinitialized.

complete_all(&my_completion);

It is useful when multiple tasks must be informed that a common event has occurred.

Operation Purpose
complete() Signals one completion event; normally wakes one waiting task.
complete_all() Signals completion for all waiters.

7. Completion Waiting Operations

7.1 wait_for_completion()

Waits until the completion is signaled.

wait_for_completion(&my_completion);

The calling task sleeps until another context calls complete() or complete_all().

7.2 wait_for_completion_interruptible()

Allows the wait to be interrupted by a signal.

int ret;

ret = wait_for_completion_interruptible(&my_completion);

if (ret) {
    pr_info("Completion wait interrupted\n");
    return ret;
}

pr_info("Operation completed\n");

Returns 0 on success or a negative error value if interrupted.

7.3 wait_for_completion_timeout()

Waits until the completion is signaled or a timeout expires.

unsigned long ret;

ret = wait_for_completion_timeout(
    &my_completion,
    5 * HZ
);

if (ret == 0) {
    pr_info("Operation timed out\n");
} else {
    pr_info("Operation completed\n");
}

The timeout is specified in jiffies. A positive return value indicates completion was signaled, while zero indicates timeout.

7.4 wait_for_completion_interruptible_timeout()

Combines signal-interruptible waiting with a timeout.

long ret;

ret = wait_for_completion_interruptible_timeout(
    &my_completion,
    5 * HZ
);

if (ret < 0) {
    pr_info("Wait interrupted\n");
} else if (ret == 0) {
    pr_info("Wait timed out\n");
} else {
    pr_info("Completion received\n");
}

Completion API Summary

Function Purpose
wait_for_completion() Waits until signaled.
wait_for_completion_interruptible() Waits with signal interruption support.
wait_for_completion_timeout() Waits with a timeout.
wait_for_completion_interruptible_timeout() Waits with signal interruption and a timeout.

8. How Completions Work

Consider a process that starts a device operation and waits for it to finish.

Initialize Completion
↓
Start Asynchronous Operation
↓
Task Calls wait_for_completion()
↓
Task Sleeps
↓
Operation Finishes
↓
Another Context Calls complete()
↓
Waiting Task Resumes

The completion mechanism avoids continuous polling. The waiting task can sleep while the operation proceeds independently.

9. Completion vs Wait Queue

Completions and wait queues both allow tasks to sleep and resume later, but their programming models differ.

Feature Completion Wait Queue
Purpose Signal that a specific event has occurred. Wait until a specified condition becomes true.
Initialization init_completion() init_waitqueue_head()
Signal/wake complete() wake_up() and related functions
Waiting wait_for_completion() wait_event() and related macros
Condition handling Completion state is maintained internally. Driver supplies and manages the condition.
Typical use Waiting for a specific operation to finish. Waiting for data or a condition to become available.

When Should You Use a Completion?

  • When a task needs to wait for a specific operation to finish.
  • When an interrupt handler must notify a waiting process that work is complete.
  • When one kernel thread must notify another that initialization or processing has finished.

10. Completion vs Semaphore vs Mutex

Feature Completion Semaphore Mutex
Primary purpose Event signaling Permit counting Exclusive ownership
Wait operation wait_for_completion() down() mutex_lock()
Signal/release complete() up() mutex_unlock()
Typical use Operation finished Resource available Protect shared data

These mechanisms are not interchangeable in every situation. Choose the mechanism whose semantics match the synchronization requirement.

11. Practical Kernel Module: Basic Completion

This example demonstrates signaling a completion and waiting for it.

Source Code: completion_basic.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/completion.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Basic Completion Demonstration");
MODULE_VERSION("1.0");

static struct completion my_completion;

static int __init completion_init(void)
{
    pr_info("Completion module loaded\n");

    init_completion(&my_completion);

    pr_info("Signaling completion\n");

    complete(&my_completion);

    pr_info("Waiting for completion\n");

    wait_for_completion(&my_completion);

    pr_info("Completion received successfully\n");

    return 0;
}

static void __exit completion_exit(void)
{
    pr_info("Completion module unloaded\n");
}

module_init(completion_init);
module_exit(completion_exit);

Explanation

  1. Declare a completion object.
  2. Initialize it using init_completion().
  3. Call complete() to signal the event.
  4. Call wait_for_completion().
  5. Because the completion was already signaled, the wait returns immediately.
This is a basic API demonstration. It does not demonstrate concurrent waiting because the completion is signaled before the wait begins.

Makefile

obj-m += completion_basic.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test in Ubuntu

make

sudo insmod completion_basic.ko

sudo dmesg | tail -20

sudo rmmod completion_basic

make clean

Expected Output

Signaling completion
Waiting for completion
Completion received successfully
Completion module unloaded

12. Practical Kernel Module: Producer and Consumer

This example uses a kernel thread as a producer and the module initialization function as a consumer.

The producer simulates an operation that takes two seconds. The consumer waits until the producer signals completion.

Source Code: completion_producer_consumer.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/completion.h>
#include <linux/kthread.h>
#include <linux/delay.h>
#include <linux/sched.h>

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Drivers Course");
MODULE_DESCRIPTION("Completion Producer Consumer Example");
MODULE_VERSION("1.0");

static DECLARE_COMPLETION(operation_done);

static struct task_struct *worker_task;

static int worker_function(void *data)
{
    pr_info("Worker: Operation started\n");

    msleep(2000);

    if (kthread_should_stop())
        return 0;

    pr_info("Worker: Operation finished\n");

    complete(&operation_done);

    return 0;
}

static int __init completion_pc_init(void)
{
    int ret;

    pr_info("Completion producer-consumer module loaded\n");

    worker_task = kthread_run(
        worker_function,
        NULL,
        "completion_worker"
    );

    if (IS_ERR(worker_task)) {
        ret = PTR_ERR(worker_task);
        worker_task = NULL;
        return ret;
    }

    pr_info("Consumer: Waiting for operation\n");

    wait_for_completion(&operation_done);

    pr_info("Consumer: Operation completed successfully\n");

    return 0;
}

static void __exit completion_pc_exit(void)
{
    if (worker_task) {
        kthread_stop(worker_task);
        worker_task = NULL;
    }

    pr_info("Completion producer-consumer module unloaded\n");
}

module_init(completion_pc_init);
module_exit(completion_pc_exit);

Explanation

  1. A completion object is declared using DECLARE_COMPLETION().
  2. A worker kernel thread is created using kthread_run().
  3. The worker simulates a time-consuming operation.
  4. The consumer calls wait_for_completion().
  5. The worker calls complete() when its operation finishes.
  6. The waiting consumer resumes.

Makefile

obj-m += completion_producer_consumer.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile and Test

make

sudo insmod completion_producer_consumer.ko

sudo dmesg | tail -30

sudo rmmod completion_producer_consumer

make clean

Expected Output

Completion producer-consumer module loaded
Consumer: Waiting for operation
Worker: Operation started
Worker: Operation finished
Consumer: Operation completed successfully
Completion producer-consumer module unloaded
Log ordering can vary due to concurrent execution. The example uses an uninterruptible completion wait for simplicity. In production code, consider cancellation, timeout, error handling and worker lifetime carefully.

13. Completions in Hardware Device Drivers

Completions are particularly useful when a hardware operation is started in process context and finished asynchronously.

Example: DMA Transfer

Consider a device driver that starts a DMA transfer.

  1. The driver prepares the DMA operation.
  2. The driver starts the transfer.
  3. The process waits for completion.
  4. The hardware finishes transferring data.
  5. The device generates an interrupt.
  6. The interrupt handler acknowledges the interrupt and signals completion.
  7. The waiting process resumes and processes the result.
Process Context
↓
Prepare and Start DMA
↓
wait_for_completion()
DMA Hardware Transfers Data
↓
Hardware Interrupt
↓
Interrupt Handler
↓
complete()
Process Resumes
↓
Process Transfer Result

Important Design Considerations

  • Initialize the completion before starting the asynchronous operation.
  • Use an appropriate reinitialization strategy before reusing the completion for another operation.
  • Ensure that the interrupt handler signals only the correct operation's completion.
  • Handle timeout and device-error conditions.
  • Do not release buffers or driver state while asynchronous hardware activity may still access them.
A completion only signals an event. It does not perform DMA mapping, synchronize DMA buffers, stop hardware, or guarantee that a device has safely released a buffer. Use the Linux DMA API and device-specific completion protocol correctly.

14. Reinitializing Completion Objects

A completion may be reused for multiple operations, but its state must be managed carefully.

Linux provides:

reinit_completion(&my_completion);

This resets the completion state so it can be used for a new event.

Conceptual Sequence

init_completion(&my_completion);

/* First operation */
start_operation();
wait_for_completion(&my_completion);

/* Prepare for another operation */
reinit_completion(&my_completion);

/* Second operation */
start_operation();
wait_for_completion(&my_completion);
Do not call reinit_completion() while tasks may still be waiting on the completion or while a previous operation can still signal it. Otherwise, a valid signal can be lost or the wrong operation can be associated with the signal.

15. Important Rules for Completions

  1. Initialize a completion before using it.
  2. Call complete() when the intended event occurs.
  3. Use complete_all() when all relevant waiters must be awakened.
  4. Use timeout-based waits when indefinite waiting is unacceptable.
  5. Check return values from interruptible and timeout-based waits.
  6. Do not reinitialize a completion while previous waiters or operations may still use it.
  7. Ensure the completion object remains valid until all users finish.
  8. Do not confuse event signaling with protection of shared data.
  9. Ensure module cleanup does not free resources while asynchronous work is still active.

16. Common Completion Programming Mistakes

Mistake Why It Is Wrong
Using an uninitialized completion. The completion object is not ready for use.
Waiting without a signaling path. The waiting task may remain blocked indefinitely.
Calling complete() for the wrong operation. A task may resume before its actual operation finishes.
Reinitializing while another task is waiting. A signal or waiter may be lost.
Ignoring timeout results. The driver may incorrectly assume the operation succeeded.
Freeing the completion object too early. Other execution contexts may still reference it.
Using a completion as a mutex. A completion signals an event; it does not provide mutex ownership.

17. Debugging Completion Problems

Useful commands for inspecting kernel logs:

sudo dmesg | tail -50

sudo journalctl -k -n 50

lsmod | grep completion

When investigating a completion-related issue, check:

  • Whether the completion was initialized.
  • Whether the signaling code path executes.
  • Whether the correct completion object is signaled.
  • Whether the waiting task handles timeout or interruption correctly.
  • Whether the completion is reinitialized safely.
  • Whether asynchronous operations are stopped or completed before cleanup.

18. Lesson Summary

  • A completion is a Linux kernel event-signaling mechanism.
  • It allows a task to wait until an operation finishes.
  • struct completion represents a completion object.
  • DECLARE_COMPLETION() provides static initialization.
  • init_completion() performs runtime initialization.
  • complete() signals a completion event.
  • complete_all() signals completion for all waiters.
  • wait_for_completion() waits for the event.
  • Interruptible and timeout-based waiting variants are also available.
  • reinit_completion() resets a completion for reuse when safe.
  • Completions are useful for DMA, asynchronous hardware operations and kernel-thread coordination.
  • Completions do not replace mutexes, spinlocks or DMA synchronization.
