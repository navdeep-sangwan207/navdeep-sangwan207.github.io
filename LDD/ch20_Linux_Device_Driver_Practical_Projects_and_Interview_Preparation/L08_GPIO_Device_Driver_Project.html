1. Introduction to GPIO

GPIO stands for General Purpose Input/Output. GPIO pins are configurable digital pins available on microcontrollers, processors and embedded Linux boards.

A GPIO pin can generally operate in two modes:

  • Input: Reads a digital signal from an external device.
  • Output: Drives a digital signal to an external circuit.

Common applications include LEDs, push buttons, relays, switches, sensors and control signals.

2. Project Objectives

  • Configure a GPIO as input or output.

5. Linux GPIO Descriptor API

Modern Linux GPIO consumer drivers should normally use the GPIO descriptor-based API.

FunctionPurpose
gpiod_get()Obtains a GPIO descriptor.
gpiod_put()Releases a GPIO descriptor.
gpiod_direction_input()Configures a GPIO as input.
gpiod_direction_output()Configures a GPIO as output.
gpiod_set_value_cansleep()Sets an output GPIO that may sleep.
gpiod_get_value_cansleep()Reads an input GPIO that may sleep.
devm_gpiod_get()Obtains a managed GPIO descriptor.
Important: The descriptor API uses logical active/inactive values. Device Tree polarity information is handled by the GPIO framework. Do not assume logical 1 always means an electrical high level.

6. Project Hardware Requirements

  • Embedded Linux development board with GPIO support.
  • One LED and a suitable current-limiting resistor.
  • One push button or switch.
  • Connecting wires and a breadboard.
  • Linux kernel source and matching build environment.
Hardware safety: Check the board's GPIO voltage limits and pinout before connecting anything. Use a suitable LED resistor. Never connect a GPIO directly to a voltage above its permitted input level.

7. Device Tree GPIO Mapping

A device driver can obtain GPIO connections through Device Tree. The following is an illustrative node for a board-specific device.

my_gpio_device {
    compatible = "ns,my-gpio-device";

    led-gpios = <&gpio1 5 GPIO_ACTIVE_HIGH>;
    button-gpios = <&gpio1 6 GPIO_ACTIVE_LOW>;
};

Explanation:

  • compatible identifies the device.
  • led-gpios describes the LED GPIO connection.
  • button-gpios describes the button GPIO connection.
  • GPIO_ACTIVE_HIGH and GPIO_ACTIVE_LOW specify logical polarity.
The controller label, pin numbers, Device Tree placement and compatible string must match the actual board. This example is not a universal Device Tree overlay and cannot be loaded unchanged on every board.

9. Complete GPIO Driver Source Code

This example uses a platform driver and obtains the LED and button GPIOs through Device Tree.

Create the source file:

nano gpio_driver.c

File: gpio_driver.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/platform_device.h>
#include <linux/gpio/consumer.h>
#include <linux/of.h>
#include <linux/err.h>
#include <linux/delay.h>

struct my_gpio_data {
    struct gpio_desc *led_gpio;
    struct gpio_desc *button_gpio;
};

/* Probe callback */
static int my_gpio_probe(struct platform_device *pdev)
{
    struct my_gpio_data *data;
    int button_value;
    int ret;

    data = devm_kzalloc(&pdev->dev,
                        sizeof(*data),
                        GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    /* Obtain LED GPIO as output, initially OFF */
    data->led_gpio = devm_gpiod_get(
        &pdev->dev,
        "led",
        GPIOD_OUT_LOW
    );

    if (IS_ERR(data->led_gpio))
        return dev_err_probe(
            &pdev->dev,
            PTR_ERR(data->led_gpio),
            "Failed to obtain LED GPIO\n"
        );

    /* Obtain button GPIO as input */
    data->button_gpio = devm_gpiod_get(
        &pdev->dev,
        "button",
        GPIOD_IN
    );

    if (IS_ERR(data->button_gpio))
        return dev_err_probe(
            &pdev->dev,
            PTR_ERR(data->button_gpio),
            "Failed to obtain button GPIO\n"
        );

    platform_set_drvdata(pdev, data);

    dev_info(&pdev->dev,
             "GPIO driver initialized\n");

    /* Demonstration: read button and control LED */
    button_value = gpiod_get_value_cansleep(
        data->button_gpio
    );

    if (button_value < 0)
        return button_value;

    gpiod_set_value_cansleep(
        data->led_gpio,
        button_value
    );

    dev_info(&pdev->dev,
             "Initial button state: %d\n",
             button_value);

    return 0;
}

/* Remove callback */
static void my_gpio_remove(struct platform_device *pdev)
{
    struct my_gpio_data *data =
        platform_get_drvdata(pdev);

    gpiod_set_value_cansleep(data->led_gpio, 0);

    dev_info(&pdev->dev,
             "GPIO driver removed\n");
}

static const struct of_device_id my_gpio_of_match[] = {
    { .compatible = "ns,my-gpio-device" },
    { }
};
MODULE_DEVICE_TABLE(of, my_gpio_of_match);

static struct platform_driver my_gpio_driver = {
    .probe = my_gpio_probe,
    .remove = my_gpio_remove,
    .driver = {
        .name = "ns_gpio_driver",
        .of_match_table = my_gpio_of_match,
    },
};

module_platform_driver(my_gpio_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Device Tree Based GPIO Consumer Driver");
MODULE_VERSION("1.0");

10. Understanding the Driver Code

10.1 Platform Driver

The platform driver binds to a platform device using its Device Tree compatible string.

10.2 Obtaining the LED GPIO

data->led_gpio = devm_gpiod_get(
    &pdev->dev,
    "led",
    GPIOD_OUT_LOW
);

The driver requests the GPIO named led and configures it as an output initially set to logical inactive.

10.3 Obtaining the Button GPIO

data->button_gpio = devm_gpiod_get(
    &pdev->dev,
    "button",
    GPIOD_IN
);

The driver requests the GPIO named button and configures it as an input.

10.4 Reading the Button

button_value = gpiod_get_value_cansleep(
    data->button_gpio
);

This reads the logical button state. A negative return value indicates an error.

10.5 Controlling the LED

gpiod_set_value_cansleep(
    data->led_gpio,
    button_value
);

The LED output is set according to the logical button state, taking the configured GPIO polarity into account.

10.6 Managed Resource Allocation

The devm_ functions automatically release resources when the device is detached or probe fails. This reduces manual cleanup code.

14. Important: This Example Is Not a Continuous Button Monitor

The sample driver reads the button once during probe and sets the LED once. It does not continuously monitor button changes.

To implement continuous monitoring, a driver would normally use one of these approaches:

  • GPIO interrupts for edge-triggered button events.
  • A threaded IRQ handler when operations may sleep.
  • A delayed work item for periodic polling when appropriate.

These approaches require additional synchronization, debouncing and resource-management logic.

15. GPIO Interrupts and Debouncing

Mechanical buttons can produce multiple rapid transitions when pressed or released. This behavior is called switch bouncing.

Common techniques include:

  • Hardware RC debounce circuits.
  • GPIO controller debounce support.
  • Software delayed work.
  • Interrupt masking and delayed state verification.

For interrupt-based GPIO handling, the driver can obtain an IRQ using gpiod_to_irq() and register an interrupt handler using the Linux IRQ API.

17. VirtualBox and GPIO Hardware Limitations

Ubuntu running inside VirtualBox does not automatically receive direct access to the host computer's physical GPIO pins.

Therefore, this project has two different testing possibilities:

Software Study

  • Study the GPIO API and driver source code.
  • Compile the module against the Ubuntu kernel headers.
  • Understand Device Tree mappings and probe behavior.
  • Use kernel documentation and simulated examples.

Physical Hardware Testing

  • Use a GPIO-capable embedded Linux board.
  • Configure the board-specific Device Tree.
  • Connect the LED and button safely.
  • Build and load the driver on the target board.
  • Verify actual GPIO input and output behavior.
Important for your learning setup: A successful compilation inside VirtualBox does not prove that the host laptop has usable GPIO hardware or that the driver can control a physical pin. Physical testing requires a compatible GPIO controller and correctly configured target hardware.
