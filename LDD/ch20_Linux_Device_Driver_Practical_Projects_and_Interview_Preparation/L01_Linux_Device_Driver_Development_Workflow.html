1. Introduction

Linux device driver development is a systematic process of designing, implementing, compiling, loading, testing and debugging kernel-level software that controls or communicates with hardware devices.

A device driver acts as an interface between the Linux kernel and a hardware device. It provides the kernel with the operations required to initialize, configure, access and control that device.

Professional driver development requires knowledge of Linux kernel architecture, kernel APIs, memory management, synchronization, interrupts, device models and hardware communication interfaces.

3. Understand Hardware Specifications

Before writing a driver, the developer must understand the target device and its hardware interface.

Important hardware information

  • Device type and functionality.
  • Register addresses and register definitions.
  • Interrupt number and interrupt behavior.
  • Memory-mapped I/O regions.
  • Communication protocol: GPIO, I2C, SPI, UART, USB or PCI.
  • Power, reset and initialization requirements.
  • Data format, timing and error conditions.

Hardware specifications are generally obtained from the device datasheet, technical reference manual and board documentation.

Important: A driver must use the appropriate Linux subsystem API instead of directly assuming that every hardware register can be accessed through an ordinary memory pointer.

4. Select the Appropriate Driver Framework

Linux provides different driver frameworks for different device categories.

Driver TypePurpose
Character DriverByte-oriented device communication.
Block DriverStorage devices and block-based data access.
Network DriverNetwork interface devices.
Platform DriverSoC-integrated peripherals.
I2C DriverDevices connected through the I2C bus.
SPI DriverDevices connected through the SPI bus.
USB DriverUSB-connected devices.
GPIO DriverGPIO controller and GPIO consumer interfaces.

Selecting an appropriate framework improves compatibility with the Linux device model and existing kernel subsystems.

5. Prepare the Development Environment

For this course, Ubuntu Linux running inside VirtualBox is used for kernel module development.

Step 1: Update Ubuntu

sudo apt update
sudo apt upgrade

Step 2: Install development tools

sudo apt install build-essential linux-headers-$(uname -r) \
    kmod git make gcc

Step 3: Verify the running kernel

uname -r

Step 4: Verify kernel headers

ls -l /lib/modules/$(uname -r)/build

Step 5: Verify GCC and Make

gcc --version
make --version

The installed kernel headers must match the running kernel when building an external kernel module using this workflow.

7. Write the Driver Source Code

A basic kernel module contains initialization and cleanup functions.

File: hello_driver.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init hello_driver_init(void)
{
    pr_info("Hello Driver: Module loaded successfully\n");
    return 0;
}

static void __exit hello_driver_exit(void)
{
    pr_info("Hello Driver: Module removed successfully\n");
}

module_init(hello_driver_init);
module_exit(hello_driver_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic Linux Device Driver Workflow Project");

Explanation

  • module_init() identifies the initialization function.
  • module_exit() identifies the cleanup function.
  • pr_info() writes informational messages to the kernel log.
  • MODULE_LICENSE() declares the module license.
  • __init and __exit identify initialization and cleanup code sections.

8. Create the Kernel Module Makefile

The kernel build system, known as Kbuild, is used to compile external kernel modules.

File: Makefile

obj-m += hello_driver.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean
Makefile indentation: The command lines under all and clean must begin with a real tab character, not spaces.

Explanation

  • obj-m specifies an external module to build.
  • KDIR identifies the kernel build directory.
  • M=$(PWD) identifies the external module source directory.
  • modules requests module compilation.
  • clean removes generated build files.

9. Compile the Kernel Module

Run the following command inside the project directory:

make

Successful compilation generates a kernel module file:

hello_driver.ko

Verify the generated files:

ls -l
file hello_driver.ko

The .ko extension represents a Linux kernel object module.

10. Load and Verify the Driver

Load the module into the running kernel:

sudo insmod hello_driver.ko

Check whether it is loaded:

lsmod | grep hello_driver

Inspect its kernel log messages:

sudo dmesg | tail -20

Expected initialization message:

Hello Driver: Module loaded successfully

Remove the module:

sudo rmmod hello_driver

Inspect the cleanup message:

sudo dmesg | tail -20

Expected cleanup message:

Hello Driver: Module removed successfully

11. Driver Testing and Debugging

After loading a driver, verify its behavior and inspect kernel messages.

CommandPurpose
lsmodList loaded kernel modules.
modinfo hello_driver.koDisplay module metadata.

journalctl -kView kernel journal messages.

For advanced drivers, testing should also include invalid input, resource allocation failures, concurrent access, interrupt handling and cleanup paths.

When module loading fails, inspect the kernel log immediately:

sudo dmesg | tail -40

13. Driver Deployment and Maintenance

After development and testing, a driver may be deployed as an external module or integrated into the kernel source tree.

External module installation

sudo install -D -m 644 hello_driver.ko \
    /lib/modules/$(uname -r)/extra/hello_driver.ko

sudo depmod -a

sudo modprobe hello_driver

Remove the installed module with:

sudo modprobe -r hello_driver
Note: This installation example assumes a module built for the running kernel and a suitable module-signing configuration. Secure Boot may prevent loading an unsigned module. For production systems, use appropriate signing, dependency management and kernel-version compatibility checks.
