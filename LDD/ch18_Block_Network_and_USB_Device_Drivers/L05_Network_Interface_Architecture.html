1. Introduction

A network interface is the logical interface through which Linux communicates with a network. It may represent a physical Ethernet controller, a wireless adapter or a software-created virtual interface.

The Linux network interface architecture defines how applications, networking protocols, kernel networking components and hardware interact.

A network driver is responsible for connecting a particular network controller to the common Linux networking framework.

  • Applications use socket APIs.
  • The networking stack processes protocols.
  • The network device layer manages interfaces.
  • The driver controls the network hardware.
  • The controller transmits and receives frames.

2. Overall Linux Network Architecture

+--------------------------------------+ | User Applications | | Browser, SSH, Ping, etc. | +--------------------------------------+ | v +--------------------------------------+ | Socket Layer | | socket(), send(), recv() | +--------------------------------------+ | v +--------------------------------------+ | Transport Layer | | TCP / UDP | +--------------------------------------+ | v +--------------------------------------+ | IP Layer | | IPv4 / IPv6 | +--------------------------------------+ | v +--------------------------------------+ | Routing and Traffic Control | | qdisc / TX processing | +--------------------------------------+ | v +--------------------------------------+ | Network Device Layer | | net_device | +--------------------------------------+ | v +--------------------------------------+ | Network Driver | +--------------------------------------+ | v +--------------------------------------+ | Ethernet / Wi-Fi Controller | +--------------------------------------+ | v +--------------------------------------+ | Network | +--------------------------------------+

This architecture separates protocol processing from hardware-specific operations. Different network controllers can use the same networking stack while requiring different drivers.

3. Main Components of Network Interface Architecture

3.1 Socket Layer

The socket layer provides an interface for applications to communicate through networks.

Common socket-related operations include:

socket()
bind()
listen()
accept()
connect()
send()
recv()
sendto()
recvfrom()
close()

Applications normally do not communicate directly with network hardware. They use sockets and rely on the kernel networking stack.

3.2 Transport Layer

The transport layer provides communication between application endpoints.

  • TCP: Connection-oriented and reliable byte-stream communication.
  • UDP: Connectionless datagram communication.

3.3 Network Layer

The IP layer handles logical addressing and packet forwarding. It determines how IP packets move between networks.

3.4 Network Device Layer

The network device layer provides a common interface between the Linux networking stack and individual network drivers.

3.5 Hardware Driver

The driver performs hardware-specific operations such as register configuration, DMA management, packet transmission and packet reception.

4. The net_device Structure

The Linux kernel represents a network interface using struct net_device.

It is a central data structure in network device driver development.

It represents information such as:

  • Network interface name.
  • Hardware address.
  • MTU value.
  • Interface state.
  • Transmit queue configuration.
  • Network operation callbacks.
  • Device features and capabilities.
  • Driver-private information references.

A network driver allocates and configures this structure before registering the interface.

The structure contains many kernel-managed fields. Drivers should not arbitrarily modify internal fields. Use the documented kernel APIs for the target kernel version.

5. Network Device Operations

Network device operations are callbacks supplied by a network driver to the Linux networking subsystem.

They are commonly defined using struct net_device_ops.

Callback Purpose
ndo_open Initializes and starts the network interface.
ndo_stop Stops the network interface and releases active resources.
ndo_start_xmit Handles packet transmission.
ndo_set_mac_address Changes the MAC address when supported.
ndo_get_stats64 Provides interface statistics.
ndo_set_rx_mode Configures receive filtering mode when required.
ndo_change_mtu Handles MTU changes when supported.

Not every driver needs to implement every callback. The required operations depend on the hardware and supported features.

6. Network Packet Representation: sk_buff

The Linux networking subsystem uses struct sk_buff to represent packet data and its associated metadata.

It is commonly abbreviated as skb.

Important skb Information

  • Packet length.
  • Data buffer references.
  • Network protocol information.
  • MAC, network and transport header positions.
  • Checksum metadata.
  • Packet-processing information.
+-----------------------------------+ | sk_buff | +-----------------------------------+ | Packet Metadata | +-----------------------------------+ | Protocol Information | +-----------------------------------+ | Header References | +-----------------------------------+ | Packet Length | +-----------------------------------+ | Data Buffer References | +-----------------------------------+

An skb can contain references to packet data stored in different memory regions. It should not be assumed that every packet is represented by one simple contiguous buffer.

7. Packet Transmission Architecture

Packet transmission is the process of sending data from the system to a network.

Transmission Flow

  1. An application generates data.
  2. The socket layer accepts the data.
  3. The transport layer processes TCP or UDP.
  4. The IP layer adds network-layer information.
  5. Routing selects the outgoing network interface.
  6. Traffic control and queueing process the packet.
  7. The networking subsystem invokes the driver.
  8. The driver prepares the packet for hardware transmission.
  9. The network controller transmits the frame.
  10. The driver processes transmission completion.
Application | v Socket Layer | v TCP / UDP | v IP Layer | v Routing | v Traffic Control / qdisc | v Network Device TX | v Driver: ndo_start_xmit() | v TX Descriptor Ring | v DMA / Network Controller | v Network

8. Packet Reception Architecture

Packet reception is the process of accepting incoming network frames and passing them to the Linux networking stack.

Reception Flow

  1. The network controller receives a frame.
  2. The controller places data into a receive buffer, commonly through DMA.
  3. The hardware updates the receive descriptor.
  4. An interrupt or another supported notification mechanism informs the driver.
  5. The driver schedules receive processing, commonly using NAPI.
  6. The driver processes completed receive descriptors.
  7. The driver prepares or builds an skb.
  8. The packet is submitted to the networking subsystem.
  9. IP and transport protocols process the packet.
  10. The data becomes available to the appropriate socket.
Network | v Network Controller | v RX Descriptor Ring | v DMA to Receive Buffer | v Interrupt / NAPI Poll | v Network Driver | v sk_buff | v Linux Network Stack | v Socket Layer | v Application

9. Transmit and Receive Descriptor Rings

Many network controllers use descriptor rings to manage packet transfers between system memory and hardware.

A descriptor contains information about a buffer or packet transfer. The exact descriptor format is controller-specific.

Transmit Descriptor Ring

The driver places information about outgoing packet buffers into transmit descriptors. The controller processes these descriptors and transmits the packets.

Receive Descriptor Ring

The driver provides receive buffers through receive descriptors. The controller uses these buffers to store incoming packets.

TRANSMIT RING +------------+ +------------+ | Descriptor | -> | Descriptor | +------------+ +------------+ | | v v TX Buffer TX Buffer RECEIVE RING +------------+ +------------+ | Descriptor | -> | Descriptor | +------------+ +------------+ | | v v RX Buffer RX Buffer

Descriptor rings are often implemented as circular queues. Producer and consumer positions are managed according to the hardware's documented rules.

10. DMA in Network Interface Architecture

Direct Memory Access allows a network controller to transfer packet data between device and system memory without requiring the CPU to copy every byte individually.

Transmit DMA

  1. The driver prepares packet data.
  2. The driver maps the appropriate memory for DMA.
  3. The driver provides descriptors to the controller.
  4. The controller reads the packet data.
  5. The controller transmits the frame.

Receive DMA

  1. The driver prepares receive buffers.
  2. The driver maps buffers for device access.
  3. The controller receives a frame.
  4. The controller writes packet data into memory.
  5. The driver processes the completed descriptor.
DMA addresses are not necessarily the same as CPU virtual or physical addresses. Drivers must use the Linux DMA API and follow the device's DMA addressing requirements.

11. Interrupt Architecture

Network controllers generate interrupts for events such as packet reception, transmission completion and link changes.

An interrupt informs the CPU that the device needs attention.

Typical Interrupt Events

  • RX packet notification.
  • TX completion notification.
  • Link status change.
  • Hardware error.
  • Receive queue condition.

The interrupt handler generally performs limited work and schedules additional processing where necessary.

12. NAPI Architecture

NAPI combines interrupt notification with polling to process received packets efficiently.

Instead of relying on one interrupt for every packet, the driver can process multiple packets during a polling cycle.

NAPI Processing Steps

  1. A receive event triggers an interrupt.
  2. The driver schedules NAPI processing.
  3. Receive interrupts may be masked or suppressed for the relevant queue.
  4. The kernel invokes the driver's NAPI poll callback.
  5. The callback processes packets within its budget.
  6. If more packets remain, polling continues.
  7. When the queue is drained, NAPI is completed.
  8. Interrupts are re-enabled as appropriate.
Packet Received | v Interrupt Handler | v Schedule NAPI | v NAPI Poll Callback | v Process RX Packets | v Budget Exhausted or Packets Remain? / \ Yes No | | v v Continue Polling Complete NAPI | v Re-enable RX Interrupts

NAPI helps reduce interrupt overhead under heavy network traffic.

13. Network Queues

Network interfaces use queues to manage packet transmission and reception.

13.1 TX Queue

A transmit queue stores packets waiting to be transmitted. The networking subsystem and driver coordinate queue stopping and waking when hardware resources are unavailable or become available again.

13.2 RX Queue

A receive queue manages incoming packet buffers and descriptors. The driver processes completed receive entries and prepares buffers for future packets.

13.3 Multiple Queues

High-performance network controllers may provide multiple transmit and receive queues.

Multiple queues can improve performance by allowing parallel processing across CPU cores.

Network Interface | +--------+--------+ | | TX Queues RX Queues | | +---+---+ +---+---+ | | | | TX0 TX1 RX0 RX1 | | | | CPU0 CPU1 CPU0 CPU1

Queue selection and CPU distribution may use mechanisms such as RSS, XPS and RPS, depending on the system and driver.

14. Traffic Control and qdisc

Linux traffic control manages how outgoing packets are queued and scheduled.

A queueing discipline, commonly called qdisc, can control packet scheduling, shaping and traffic prioritization.

Examples include:

  • FIFO queueing.
  • Fair queueing.
  • Traffic shaping.
  • Priority-based scheduling.

The qdisc layer operates above the hardware-specific network driver. It is part of the broader Linux traffic control architecture.

15. MTU and Ethernet Frame Size

MTU means Maximum Transmission Unit. For a conventional Ethernet interface, the common MTU is 1500 bytes.

The MTU normally describes the maximum IP packet size that can be carried in the link-layer payload without fragmentation at that link.

For a standard Ethernet frame carrying an IP packet:

  • Ethernet header: commonly 14 bytes.
  • IP packet: up to 1500 bytes with a 1500-byte MTU.
  • Ethernet frame check sequence: 4 bytes.

The conventional Ethernet frame size is therefore commonly 1518 bytes from destination MAC through FCS, excluding preamble and inter-frame gap.

IPv4 fragmentation is an IP-layer operation. Ethernet frames have their own link-layer size limits. IPv6 routers do not fragment packets in transit; fragmentation, when needed, is performed by the source using IPv6 extension headers.

Inspect MTU

ip link show

Change MTU Temporarily

sudo ip link set dev enp3s0 mtu 1400

Replace the interface name with the correct name on your system. This is a temporary configuration change and may be overwritten by network management software.

16. MAC Address and Link State

MAC Address

A MAC address is a link-layer hardware address associated with a network interface. Ethernet commonly uses 48-bit MAC addresses.

Example:

02:1A:2B:3C:4D:5E

Link State

Link state indicates whether the network interface has a usable physical or logical connection.

Common states include:

  • UP
  • DOWN
  • UNKNOWN

An interface may be administratively UP while its physical carrier is unavailable. These are different conditions.

Inspect Interface State

ip link show
cat /sys/class/net/enp3s0/operstate
cat /sys/class/net/enp3s0/carrier

The carrier file may not be available or meaningful for every type of virtual or wireless interface.

17. Network Statistics

Network statistics help monitor the operation and performance of an interface.

Common statistics include:

  • Packets transmitted.
  • Packets received.
  • Bytes transmitted.
  • Bytes received.
  • Transmission errors.
  • Receive errors.
  • Dropped packets.

Display Statistics

ip -s link show

The kernel exposes network statistics through networking interfaces. Drivers commonly implement statistics reporting through supported kernel APIs, including ndo_get_stats64 where appropriate.

18. Ethernet Driver and Network Protocol

A network device driver and a network protocol perform different functions.

Network Driver Network Protocol
Controls hardware. Defines communication rules.
Manages packet buffers and descriptors. Defines packet structure and processing.
Handles hardware interrupts and DMA. Handles addressing, delivery and reliability.
Example: Ethernet controller driver. Examples: TCP, UDP and IP.

The driver does not implement the entire TCP/IP protocol stack. It provides the hardware interface required by the networking subsystem.

19. Network Interface Registration Lifecycle

A typical network driver registration lifecycle consists of the following stages.

  1. Detect the network controller.
  2. Allocate the network interface structure.
  3. Initialize device-specific private data.
  4. Set network device operations.
  5. Configure hardware resources.
  6. Register the network interface.
  7. Open and operate the interface when requested.
  8. Stop the interface when requested.
  9. Unregister the network interface during removal.
  10. Release allocated resources.

Common networking helpers include:

alloc_etherdev()
register_netdev()
unregister_netdev()
free_netdev()
The exact allocation and registration pattern depends on the driver type and target kernel API. A PCI, USB or platform network driver also has its own bus-specific probe and remove lifecycle.

20. Network Interface Inspection in Ubuntu

The following commands help inspect the network interface architecture from user space.

List Interfaces

ip link show

Display Addresses

ip addr show

Display Routes

ip route show

Display Driver Information

sudo ethtool -i enp3s0

Display Link Information

sudo ethtool enp3s0

Display Statistics

ip -s link show enp3s0

Inspect Kernel Messages

dmesg | grep -i -E "network|ethernet|firmware"

Inspect Interface Through sysfs

ls /sys/class/net/

cat /sys/class/net/enp3s0/address

cat /sys/class/net/enp3s0/mtu

cat /sys/class/net/enp3s0/operstate

Replace enp3s0 with the interface name available on your Ubuntu installation.

21. Performance Optimization Concepts

Modern network interfaces use several techniques to improve packet processing performance.

Technique Purpose
DMA Reduces CPU involvement in data transfers.
NAPI Reduces interrupt overhead during packet reception.
Multi-queue Allows parallel packet processing.
RSS Distributes received flows across receive queues.
Checksum offload Allows hardware to calculate or verify supported checksums.
TSO Allows supported hardware to segment large TCP data.
GRO Combines certain received packets to reduce processing overhead.

The availability of these features depends on the network controller, driver and kernel configuration.

23. Important Points to Remember

  • struct net_device represents a Linux network interface.
  • struct sk_buff represents packet data and metadata.
  • struct net_device_ops defines driver callbacks.
  • ndo_start_xmit is associated with packet transmission.
  • TX and RX descriptor rings coordinate packet transfers.
  • DMA is commonly used by network controllers.
  • Interrupts notify the driver about hardware events.
  • NAPI provides polling-based packet processing.
  • qdisc manages outgoing packet queueing and scheduling.
  • Multi-queue devices can support parallel packet processing.
  • MTU defines the maximum network-layer packet size carried by a link.

25. Lesson Summary

Linux network interface architecture provides a structured connection between applications, the socket layer, transport and IP protocols, traffic control, network devices and hardware drivers.

The net_device structure represents the interface, while sk_buff represents packet data and metadata. Network drivers use descriptor rings, DMA, interrupts and NAPI to transfer packets efficiently.

Understanding this architecture is essential before studying the detailed Linux network device structures and implementing network drivers.
