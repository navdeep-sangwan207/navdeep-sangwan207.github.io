1. Introduction

The Linux block device architecture is the kernel framework responsible for managing storage devices and transferring data between the operating system and storage hardware.

It provides a common interface for different types of storage devices, including hard disks, SSDs, NVMe devices, USB storage and virtual disks.

Without this common architecture, every filesystem would need to understand the specific communication protocol of every storage controller.

Example: An ext4 filesystem does not need to know whether its data is stored on a SATA HDD, NVMe SSD or virtual disk. It communicates with the block layer, which handles the storage request through the appropriate driver.

2. Main Components of Block Device Architecture

The main components are:

  • Application and system-call interface
  • Virtual File System (VFS)
  • Filesystem layer
  • Page cache
  • Block I/O subsystem
  • BIO structures
  • Request structures
  • blk-mq multi-queue framework
  • Block device driver
  • Storage controller and hardware

3. Application and System Call Interface

Applications access files and storage through system calls. Common operations include:

System Call Purpose
open() Opens a file or device.
read() Reads data.
write() Writes data.
lseek() Changes the file offset where supported.
fsync() Requests synchronization of modified file data.
close() Closes an open file descriptor.

When an application accesses a regular file, these operations normally pass through the VFS and the relevant filesystem. The filesystem determines which storage blocks are needed.

Direct access to a block-device node follows a different path from ordinary file access, but it still uses the block-device framework.

4. Virtual File System (VFS)

The Virtual File System provides a common interface between user applications and different filesystem implementations.

Linux supports several filesystems, including:

  • ext4
  • XFS
  • Btrfs
  • FAT
  • NTFS implementations

VFS allows applications to use common operations such as open(), read(), write() and close() without knowing the internal implementation of each filesystem.

Application | v VFS | +----------+----------+ | | | v v v ext4 XFS Btrfs | | | +----------+----------+ | v Block Layer

5. Filesystem Layer

The filesystem layer organizes storage into files, directories, metadata and allocation structures.

Its responsibilities include:

  • Managing files and directories.
  • Maintaining file metadata.
  • Mapping file offsets to storage blocks.
  • Managing free and allocated storage space.
  • Requesting storage reads and writes.

For example, when an application reads a file using ext4, the filesystem determines which storage blocks contain the requested file data.

6. Page Cache

The page cache stores file data in system memory to reduce unnecessary storage-device access.

Read Operation

  1. The application requests file data.
  2. The kernel checks whether the data is cached.
  3. If cached, data can be returned from memory.
  4. If not cached, the filesystem requests the required data from the block layer.

Write Operation

Modified file data may initially be stored in memory. The kernel can write this data to storage later through writeback.

The page cache is primarily associated with buffered file I/O. Direct I/O and other I/O paths can behave differently.

7. Block I/O Subsystem

The block I/O subsystem is the central component responsible for managing storage requests.

Its responsibilities include:

  • Managing block-device I/O operations.
  • Representing and organizing I/O requests.
  • Handling request merging and dispatch.
  • Managing queues and scheduling.
  • Coordinating I/O completion.
  • Providing common infrastructure to storage drivers.

The block layer separates filesystem-specific logic from hardware-specific driver implementation.

8. BIO Structure

The struct bio structure represents a block I/O operation in the Linux kernel.

A BIO describes an operation such as reading or writing data and the memory segments involved in that operation.

Important BIO Concepts

  • Operation type, such as read or write.
  • Target block device.
  • Starting sector or logical block location.
  • Data segments represented through BIO vectors.
  • Completion handling.

A BIO can describe data distributed across multiple memory segments. The block layer can organize compatible BIO operations into requests for submission to the device.

+----------------------------------+ | BIO | +----------------------------------+ | Operation: READ / WRITE | | Target: Block Device | | Starting Sector | | Data Size | | Data Segments | | Completion Information | +----------------------------------+
A BIO represents an I/O operation, not necessarily a complete hardware command. Request construction and dispatch depend on the block layer and driver.

9. Request Structure

The struct request structure represents a block I/O request organized for processing by a device driver.

A request can contain one or more BIOs. Compatible operations may be merged to reduce overhead and improve efficiency.

Example

Suppose the block layer receives two adjacent write operations: 

BIO 1:
Starting sector = 100
Length = 8 sectors

BIO 2:
Starting sector = 108
Length = 8 sectors

If the operations are compatible and merging is permitted, the block layer may combine them into a larger request. 

Combined Request:
Starting sector = 100
Length = 16 sectors

This can reduce the number of individual requests that the driver needs to process.

10. Request Queue

A request queue manages storage requests before they are dispatched to the hardware driver.

Queue management is important because storage devices may receive many requests from multiple applications at the same time.

Queue-related responsibilities include:

  • Organizing pending requests.
  • Supporting request dispatch.
  • Applying queue limits.
  • Supporting request merging where appropriate.
  • Coordinating with the storage driver.

Modern Linux block I/O uses the multi-queue framework rather than relying on the old single-queue model.

11. blk-mq Architecture

blk-mq is the Linux block multi-queue framework. It was designed to improve scalability and performance, particularly with multi-core systems and fast storage devices.

Why Multi-Queue Is Needed

High-performance storage devices can process many commands concurrently. A single shared request queue can become a performance bottleneck when many CPU cores submit I/O.

blk-mq supports multiple software submission queues and hardware dispatch queues.

CPU Core 0 CPU Core 1 | | v v +-------------+ +-------------+ | Software Q0 | | Software Q1 | +-------------+ +-------------+ | | +--------+-------+ | v +------------------+ | Hardware Queues | +------------------+ | v +------------------+ | Storage Driver | +------------------+ | v +------------------+ | Storage Device | +------------------+

Advantages

  • Better scalability on multi-core processors.
  • Reduced contention on shared queue data.
  • Improved parallel I/O processing.
  • Suitable for high-performance NVMe storage.

12. I/O Scheduler

An I/O scheduler organizes requests before they are dispatched to a storage device.

Different workloads may require different scheduling behavior. For example, a system may prioritize latency for interactive applications or throughput for bulk data transfers.

Common scheduler concepts include:

  • Request ordering.
  • Request merging.
  • Fairness between competing I/O sources.
  • Latency management.
  • Throughput optimization.

The available schedulers depend on the kernel, device and configuration. Not every scheduler is suitable for every device.

Inspect the Active Scheduler

cat /sys/block/sda/queue/scheduler

Replace sda with the block-device name available on your system.

13. Block Device Driver

The block device driver communicates with the storage controller and performs the hardware-specific work required to process block I/O requests.

Typical responsibilities include:

  • Initializing the controller.
  • Configuring hardware queues.
  • Submitting storage commands.
  • Managing DMA operations where supported.
  • Handling interrupts and completion notifications.
  • Reporting errors and timeouts.
  • Managing device removal and resource cleanup.

Different storage devices require different drivers. For example, NVMe and USB mass-storage devices use different communication protocols and controller interfaces.

14. struct gendisk

The struct gendisk structure represents a disk within the Linux block subsystem.

It is associated with information such as:

  • Disk name.
  • Capacity.
  • Device and partition information.
  • Queue association.
  • Disk registration and lifecycle state.

The exact fields and registration APIs vary with kernel versions. A driver should use the interfaces documented for its target kernel.

15. struct block_device

The struct block_device structure represents a block-device object or a particular block-device region managed by the kernel.

It is important in the kernel's handling of block devices, partitions and associated I/O operations.

A whole disk and an individual partition can be represented as distinct block-device objects while belonging to the same underlying storage device.

16. Device Registration and Discovery

A block device must be registered with the kernel so that the block subsystem can manage it.

The driver is responsible for setting up the appropriate device structures, queues and hardware resources before making the device available.

After registration, device-management mechanisms can expose the device through the Linux device model and user-space device nodes.

Typical Discovery Flow

Storage Hardware Detected | v Controller Driver Initializes | v Storage Device Identified | v Block Device Registered | v Device Information Published | v /dev Device Node Available | v Filesystem Can Access Storage
The exact sequence differs between storage technologies. Device discovery, block registration and device-node creation are related stages, but they are not a single operation.

17. I/O Completion

After a storage operation has been submitted, the driver and device must eventually report its completion or failure.

Completion may be reported using interrupts, polling or other mechanisms supported by the hardware and driver.

Typical Completion Flow

  1. The block layer submits a request.
  2. The driver sends the required command to the controller.
  3. The controller performs the storage operation.
  4. The controller reports completion.
  5. The driver processes completion status.
  6. The block layer completes the associated I/O operations.
  7. Waiting processes can continue when their data is available.

Correct completion handling is essential for data integrity, resource management and application reliability.

18. Error Handling in Block Devices

Storage operations can fail for several reasons. The driver and block layer must handle these failures safely.

Error Possible Cause
I/O Error Device cannot complete a read or write operation.
Timeout Device does not respond within the expected time.
Media Error Storage media contains an unreadable or unwritable region.
Device Disconnect Storage device is removed or becomes unavailable.
Controller Error Controller reports a hardware or command failure.

A driver must report failures accurately, release resources and follow the recovery mechanisms appropriate to the device.

19. Inspecting Block Architecture in Ubuntu

The following commands help examine the block-device architecture of an Ubuntu system.

List Devices

lsblk

Display Kernel Partition Information

cat /proc/partitions

Inspect Queue Attributes

ls /sys/block/

Inspect a Device Queue

ls /sys/block/sda/queue/

Read Logical Block Size

cat /sys/block/sda/queue/logical_block_size

Read Physical Block Size

cat /sys/block/sda/queue/physical_block_size

Inspect Device Capacity

cat /sys/block/sda/size

Replace sda with the actual device name. The value in the size attribute is expressed in 512-byte sectors, even when the device has a different logical sector size.

Sysfs exposes kernel device and queue attributes. These are useful for inspection, but they are not a substitute for understanding the internal block-layer data structures.

20. Kernel API and Version Considerations

Linux block-device APIs have evolved significantly. Older examples may use interfaces that are no longer appropriate for current kernels.

When studying or developing a block driver:

  • Identify the exact kernel version.
  • Use the matching kernel headers and documentation.
  • Study current blk-mq-based driver examples.
  • Check the definitions of structures and registration APIs.
  • Do not copy legacy request_fn examples into a modern kernel without verifying compatibility.

For practical driver development, the kernel source tree and the official Linux kernel documentation are important references.

24. Lesson Summary

The Linux block device architecture provides a common framework for accessing storage hardware. It connects applications and filesystems to storage drivers through the VFS, page cache, block I/O subsystem and request-management infrastructure.

Important concepts include BIO structures, request structures, request queues, blk-mq, disk registration and I/O completion. Understanding these components is essential before studying how block drivers process actual read and write requests.
