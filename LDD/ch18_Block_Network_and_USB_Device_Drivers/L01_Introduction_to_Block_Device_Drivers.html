1. Introduction

A Linux block device is a device that stores and retrieves data in addressable blocks. It provides access to persistent storage and normally supports reading and writing data at logical block addresses.

Block devices are commonly used to store operating systems, files, applications, databases and other information.

Linux uses a dedicated block I/O subsystem to manage requests between filesystems, applications and storage hardware. A block device driver connects this subsystem to the underlying storage device or controller.

Example: When Ubuntu reads a file stored on a virtual hard disk, the filesystem eventually requests data from the block device layer. The appropriate storage driver communicates with the virtual storage controller to retrieve that data.

2. What Is a Block Device?

A block device is a storage device that exposes data as a sequence of addressable blocks. Each block has a logical address, allowing the operating system to request data from a particular location.

Important characteristics include:

  • Block-based access: Data is transferred in units of blocks or sectors.
  • Random access: The operating system can request data from different logical locations without reading all preceding data.
  • Persistent storage: Data normally remains stored after the device is powered off.
  • Capacity: A block device exposes a finite storage capacity.
  • Read and write operations: The operating system can retrieve and modify stored data.

Examples of Block Devices

  • Hard Disk Drives (HDDs)
  • Solid State Drives (SSDs)
  • USB mass storage devices
  • SD cards and eMMC storage
  • NVMe storage devices
  • Virtual disks used by virtual machines
  • Linux loop devices

3. Block Devices vs Character Devices vs Network Devices

Linux supports different device interfaces because different hardware devices have different communication and data-access requirements.

Feature Block Device Character Device Network Device
Data model Addressable blocks Byte stream or device-specific operations Network packets
Access Usually random access Usually sequential or device-specific Packet-based
Examples HDD, SSD, SD card UART, serial port, terminal Ethernet, Wi-Fi
Typical interface /dev/sda /dev/ttyS0 eth0, wlan0
Subsystem Block I/O subsystem Character device framework Networking subsystem
Important: A network interface is not normally represented as a block device under /dev. Linux network drivers integrate with the networking subsystem and transmit or receive network packets.

4. How Block Storage Works

A block device divides its addressable storage space into units. The operating system uses logical block addresses (LBAs) to identify where data is stored.

Example of Logical Block Addressing

Consider a storage device with 512-byte logical sectors. Each sector has a logical address.

Logical Sector Byte Offset Size
0 0 512 bytes
1 512 512 bytes
2 1024 512 bytes
3 1536 512 bytes

For a device using 512-byte logical sectors, the byte offset of logical sector N is: 

Byte Offset = N × 512

For example, logical sector 100 begins at: 

100 × 512 = 51200 bytes

Logical and Physical Sector Sizes

  • Logical sector size: The unit of addressing exposed by the device to the operating system.
  • Physical sector size: The actual physical recording or storage unit used by the device.

Some devices use 512-byte logical sectors with 4096-byte physical sectors. This is commonly called 512e storage.

A sector is not necessarily the same size as a filesystem block. For example, a filesystem may use 4096-byte blocks while the device exposes 512-byte logical sectors.

5. Linux Block Device Architecture

Linux uses several layers to process storage requests. Each layer has a specific responsibility, from the application requesting data to the hardware performing the operation.

+----------------------------------+ | User Application | +----------------------------------+ | v +----------------------------------+ | Virtual File System | | (VFS) | +----------------------------------+ | v +----------------------------------+ | Filesystem / Page Cache | +----------------------------------+ | v +----------------------------------+ | Block I/O Subsystem | +----------------------------------+ | v +----------------------------------+ | BIO / Request Structures | +----------------------------------+ | v +----------------------------------+ | blk-mq (Multi-Queue) | +----------------------------------+ | v +----------------------------------+ | Block Device Driver | +----------------------------------+ | v +----------------------------------+ | Storage Controller | +----------------------------------+ | v +----------------------------------+ | HDD / SSD / NVMe | +----------------------------------+

Architecture Components

  1. User application: Requests file or storage operations through system calls.
  2. VFS: Provides a common interface to different filesystem implementations.
  3. Filesystem: Converts file operations into storage operations when required.
  4. Page cache: Caches file data in memory to reduce unnecessary physical I/O.
  5. Block I/O subsystem: Manages block requests and coordinates their processing.
  6. BIO and request structures: Represent block I/O operations and requests.
  7. blk-mq: Provides a multi-queue framework for handling block I/O efficiently.
  8. Device driver: Communicates with the storage controller or device.
  9. Storage hardware: Performs the actual read or write operation.

6. Important Linux Block Subsystem Structures

The Linux kernel provides data structures and APIs for managing block devices. These structures are used by the block layer and storage drivers.

6.1 struct block_device

Represents a block device or a block-device region used by the kernel. It is associated with the device's block I/O and storage operations.

6.2 struct gendisk

Represents a disk as managed by the Linux block subsystem. It contains disk-related information such as its name, capacity, device information and partition-related state.

6.3 struct bio

Represents a block I/O operation. A BIO describes data segments and the operation to be performed, such as reading or writing.

6.4 struct request

Represents a block I/O request after operations have been organized for submission to a device driver.

6.5 struct request_queue

Represents queue-related state and configuration for block I/O. Modern Linux block drivers commonly work with the multi-queue (blk-mq) infrastructure.

Kernel-version note: Block-device APIs have changed over time. Modern Linux development uses the blk-mq framework. Older tutorials may show legacy request_fn-based drivers. Do not assume those older examples are suitable for a current kernel.

7. The blk-mq Framework

blk-mq means Block Multi-Queue. It is the modern Linux block layer framework designed to handle concurrent I/O efficiently.

Its important characteristics include:

  • Supports multiple hardware and software queues.
  • Improves parallel processing of storage requests.
  • Reduces contention in high-performance storage systems.
  • Works well with multi-core processors.
  • Supports high-performance devices such as NVMe SSDs.
CPU Core 0 CPU Core 1 | | v v Software Queue 0 Software Queue 1 | | +--------+-------+ | v Hardware Queues | v Storage Driver | v NVMe SSD

The block layer can organize and dispatch requests through queues. The driver and hardware controller then process these requests according to the device's capabilities.

8. Linux Block Device Naming

Linux assigns device names according to the device type, driver and discovery order or naming scheme.

Device Name Description
/dev/sda First disk using the traditional SCSI disk naming scheme.
/dev/sda1 First partition of that disk.
/dev/nvme0n1 First namespace on the first NVMe controller.
/dev/nvme0n1p1 First partition of that NVMe namespace.
/dev/mmcblk0 First MMC or SD block device.
/dev/mmcblk0p1 First partition of that device.
/dev/loop0 First loop device, which provides a file-backed block device.

Whole Disk and Partition

A whole-disk device represents the complete addressable storage device. A partition represents a defined region of that disk.

Example: 
/dev/sda       - Entire disk
/dev/sda1      - First partition
/dev/sda2      - Second partition

Partitions allow one physical or virtual disk to be divided into separate logical storage regions.

9. Major and Minor Device Numbers

Linux uses device numbers to identify devices. These numbers are represented by the kernel type dev_t.

  • Major number: Identifies the device driver or device-number range associated with a device.
  • Minor number: Identifies a particular device or device instance managed within that range.

The major and minor numbers are encoded in a device number and can be displayed using commands such as: 

ls -l /dev/sda
ls -l /dev/nvme0n1

Device nodes in /dev allow user-space programs to refer to devices. The kernel uses the device number to identify the associated device.

The udev device-management system helps create and manage device nodes dynamically when devices are detected.

10. How Linux Reads Data from a Block Device

Consider an application reading a file stored on an SSD. The operation may involve the following stages:

  1. The application calls read().
  2. The VFS routes the operation to the appropriate filesystem.
  3. The filesystem checks whether the requested data is already available in the page cache.
  4. If the data is not available, the filesystem requests the required storage blocks.
  5. The block layer represents the I/O using BIO structures and organizes requests.
  6. The block multi-queue framework dispatches requests.
  7. The storage driver communicates with the controller.
  8. The device retrieves the requested data.
  9. The completion information is passed back through the relevant kernel layers.
  10. The application receives the requested data.

Read Operation Flow

Application | v read() System Call | v VFS and Filesystem | v Page Cache Check | +---- Data Found ----> Return Data | v Block I/O Request | v Storage Driver | v Storage Device | v I/O Completion | v Application Receives Data

11. How Linux Writes Data to a Block Device

When an application writes data to a file, Linux may first update the page cache. The actual storage operation can happen later, depending on the filesystem, caching policy and synchronization requirements.

Typical stages include:

  1. The application calls write().
  2. The filesystem updates the relevant cached data.
  3. The kernel schedules writeback when required.
  4. The block layer creates and organizes write requests.
  5. The storage driver submits the requests to the controller.
  6. The device writes the data to its storage media.
  7. The operation completes and status is reported.

Applications can request stronger synchronization using operations such as fsync(), but the exact durability guarantees depend on the filesystem, device and hardware write-cache behavior.

A successful ordinary write() does not always mean that the data has already reached non-volatile storage.

12. Buffering, Caching and I/O Scheduling

Buffering and Caching

Linux uses memory to improve storage performance. The page cache stores file data in RAM so repeated reads may not require physical disk access.

Writeback allows modified cached data to be written to storage at a later time, subject to synchronization and filesystem rules.

I/O Scheduling

An I/O scheduler organizes requests before they are dispatched to a storage device. Depending on the device and workload, this can improve performance, latency or fairness.

Request Merging

The block layer may combine compatible adjacent I/O operations to reduce the number of requests sent to the device.

Queueing

Storage requests can be queued while waiting for device processing. Modern storage devices can process multiple requests concurrently.

13. Block Device vs Filesystem

A block device and a filesystem are related, but they are not the same thing.

Block Device Filesystem
Provides addressable storage blocks. Organizes data into files and directories.
Represents storage capacity. Manages filenames, metadata and directory structures.
Examples: /dev/sda, /dev/nvme0n1. Examples: ext4, XFS, Btrfs.
Can contain partitions and raw data. Can be created on a block device or another supported storage abstraction.

A filesystem is commonly created on a partition or block device. The filesystem manages how files and directories are stored within the available storage space.

14. Responsibilities of a Block Device Driver

A block device driver connects the Linux block subsystem to a storage controller or device.

Important responsibilities include:

  • Initializing and configuring the storage device.
  • Registering the device with the appropriate kernel subsystem.
  • Reporting device capacity and supported characteristics.
  • Processing read and write requests.
  • Managing request queues and I/O completion.
  • Handling device errors and timeouts.
  • Managing DMA transfers where supported and appropriate.
  • Handling hardware interrupts where required.
  • Releasing allocated resources during device removal.
A real hardware block driver must understand the controller's registers, command protocol, DMA requirements and error-handling behavior. The generic block layer does not automatically make different storage controllers interchangeable.

15. USB Mass Storage and NVMe Devices

USB Mass Storage

A USB flash drive commonly exposes storage through the USB Mass Storage protocol. Linux USB storage drivers communicate with the device and integrate it with the block subsystem.

The storage may then appear as a device such as /dev/sdb, depending on the system.

NVMe Storage

NVMe is a storage protocol designed for non-volatile memory devices, commonly connected through PCI Express.

The Linux NVMe driver communicates with the NVMe controller and exposes namespaces through the block subsystem.

An NVMe namespace may appear as: 

/dev/nvme0n1

Both USB mass storage and NVMe storage ultimately provide block-device access, although their controller interfaces and driver implementations are different.

16. Loop Devices

A loop device is a software-backed block device that allows a regular file to be accessed as a block device.

For example, a disk image file can be associated with a loop device. The kernel then provides block-device access to the contents of that file.

Useful Commands

# List loop devices
losetup -a

# List block devices
lsblk

# Display loop device information
losetup --list

Loop devices are useful for testing disk images, filesystem images and installation media without requiring a separate physical storage device.

17. Inspecting Block Devices in Ubuntu

The following commands help inspect block devices in Ubuntu. They are useful when learning block-device architecture.

1. List Block Devices

lsblk

Displays disks, partitions, sizes and mount points.

2. Display Filesystem Information

blkid

Displays filesystem types, UUIDs and labels for detected devices.

3. Display Partition Information

sudo fdisk -l

Lists partition tables and storage-device details.

4. View Kernel Partition Information

cat /proc/partitions

Displays block-device and partition information maintained by the kernel.

5. View Storage-Related Kernel Messages

dmesg | grep -i -E "block|scsi|ata|nvme|usb"

Displays relevant kernel messages about storage discovery and device initialization.

These commands are primarily for inspection. Avoid changing partition tables, formatting disks or writing raw data to devices unless you understand the consequences. Use a disposable virtual disk for experiments.

19. Block Driver Development Considerations

Developing a block driver is more complex than writing a basic character driver because it involves storage-specific operations, request processing and device management.

A block driver developer must understand:

  • Block-device registration and disk representation.
  • Device capacity and logical block size.
  • Request processing and completion.
  • blk-mq interfaces.
  • DMA and hardware controller communication.
  • Interrupt handling and error recovery.
  • Kernel-version-specific API changes.
This lesson introduces the architecture rather than presenting a complete loadable block driver. A production driver requires a defined hardware or virtual-controller interface and APIs appropriate to the target kernel version.

For learning, a RAM-backed or file-backed block device can be used to understand block operations without directly controlling physical storage hardware.

20. Important Points to Remember

  • Block devices provide addressable storage blocks.
  • They commonly support random-access read and write operations.
  • Linux uses a dedicated block I/O subsystem.
  • BIO structures represent block I/O operations.
  • Request structures organize operations for device processing.
  • Modern Linux uses the blk-mq multi-queue framework.
  • Major and minor numbers identify device instances.
  • Partitions represent regions of a block device.
  • Filesystems organize data stored on block devices.
  • USB mass storage and NVMe devices can expose block devices.
  • Loop devices provide file-backed block-device access.

23. Lesson Summary

Block devices provide Linux with a standard way to access persistent storage through addressable blocks. The Linux block I/O subsystem organizes requests, manages queues and connects filesystems to storage drivers.

Understanding block-device architecture is essential before studying request processing, network drivers and USB drivers. These topics form the foundation of the remaining lessons in this chapter.
