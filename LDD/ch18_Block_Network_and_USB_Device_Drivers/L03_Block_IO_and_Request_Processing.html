1. Introduction

Block I/O is the process of transferring data between system memory and a block storage device. Linux uses a structured request-processing mechanism to manage these operations.

When an application reads or writes data, the kernel may need to convert the operation into one or more block I/O operations. The block layer organizes these operations and submits them to the appropriate storage driver.

The driver communicates with the storage controller, and the controller performs the requested operation on the storage device.

Example: When Ubuntu reads a file from an SSD, the filesystem identifies the required storage blocks. The block layer organizes the I/O, the NVMe driver submits commands to the controller, and the SSD returns the requested data.

2. What Is Block I/O?

Block I/O refers to read and write operations performed on addressable storage regions.

Two fundamental operations are:

  • READ: Transfers data from a storage device into system memory.
  • WRITE: Transfers data from system memory to a storage device.

Block I/O operations are associated with a target block device, a storage location, a data length and the memory containing the data to be transferred.

Example

Operation: READ
Device: /dev/sda
Starting sector: 1000
Number of sectors: 8
Logical sector size: 512 bytes

The requested data size is: 

8 × 512 = 4096 bytes

3. Block I/O Processing Overview

A typical block I/O operation passes through several stages. The exact path depends on the type of I/O, filesystem, device and kernel configuration.

+--------------------------------+ | User Application | +--------------------------------+ | v +--------------------------------+ | System Call / VFS | +--------------------------------+ | v +--------------------------------+ | Filesystem / Page Cache | +--------------------------------+ | v +--------------------------------+ | BIO Creation | +--------------------------------+ | v +--------------------------------+ | Request Formation / Merge | +--------------------------------+ | v +--------------------------------+ | blk-mq Queues | +--------------------------------+ | v +--------------------------------+ | Block Device Driver | +--------------------------------+ | v +--------------------------------+ | Storage Controller | +--------------------------------+ | v +--------------------------------+ | Storage Hardware | +--------------------------------+ | v +--------------------------------+ | I/O Completion | +--------------------------------+

4. BIO Structure

The Linux kernel uses struct bio to represent a block I/O operation.

A BIO contains information describing the operation, the target block device, the starting location and the memory segments involved in the transfer.

Important BIO Information

  • Target block device.
  • Read or write operation.
  • Starting sector.
  • Data size.
  • Memory segments.
  • Completion information.
+--------------------------------------+ | struct bio | +--------------------------------------+ | Target Block Device | | Operation Type | | Starting Sector | | Data Length | | BIO Vector Information | | Completion Information | +--------------------------------------+

BIO Vector

A BIO can describe data stored in one or more memory segments. The BIO vector information identifies the memory pages and regions involved in the I/O operation.

This allows block I/O to work with data that is not necessarily stored in one physically contiguous memory region.

A BIO represents an I/O operation and its data segments. It should not be confused with a complete hardware command. The driver and block layer determine how operations are organized and submitted.

5. READ and WRITE BIO Operations

READ Operation

A read BIO requests data from a block device and transfers the data into memory.

Storage Device | | READ v Block Driver | v BIO Processing | v System Memory

WRITE Operation

A write BIO requests that data in memory be written to the specified storage location.

System Memory | | WRITE v BIO Processing | v Block Driver | v Storage Device

The operation type is represented through kernel block-layer operation definitions. The exact API names and flags should be checked against the target kernel version.

6. BIO Splitting

A single I/O operation may exceed the limits supported by a particular device or queue.

In such situations, the block layer can split an operation into smaller BIOs or requests.

Example

Suppose an operation requests 64 KiB of data, but the relevant queue limit allows a maximum transfer size of 16 KiB. 

Original I/O:
64 KiB

Possible split:
BIO 1 = 16 KiB
BIO 2 = 16 KiB
BIO 3 = 16 KiB
BIO 4 = 16 KiB

Each part can be processed according to the device's limits. The block layer tracks the completion of the split operations.

7. Request Structure

The struct request structure represents a block I/O request organized for processing by a device driver.

A request may contain one or more BIOs. The block layer can merge compatible operations to improve efficiency.

Example

Assume two adjacent write operations:

BIO 1:
Starting sector = 200
Length = 8 sectors

BIO 2:
Starting sector = 208
Length = 8 sectors

If their properties and queue limits allow merging, they may be represented as one larger request. 

Combined Request:
Starting sector = 200
Length = 16 sectors
Request merging is subject to device limits, operation flags, queue configuration and other block-layer constraints. It is not guaranteed for every adjacent operation.

8. Difference Between BIO and Request

Feature BIO Request
Purpose Represents a block I/O operation. Represents an organized request for driver processing.
Data description Describes memory segments and operation details. Can contain one or more BIOs.
Merging Can be combined with compatible operations. Can represent merged BIO operations.
Role I/O description. Request dispatch and processing.

A useful way to remember the distinction is that a BIO describes an I/O operation, while a request organizes operations for submission to a storage driver.

9. Request Queue

A request queue is responsible for managing requests that are waiting to be dispatched to the storage device.

Important queue responsibilities include:

  • Managing pending I/O requests.
  • Applying device queue limits.
  • Supporting request merging.
  • Coordinating request dispatch.
  • Supporting concurrent I/O operations.

Modern Linux block drivers generally use the blk-mq framework for request queue management.

10. blk-mq Request Processing

blk-mq is the modern Linux block multi-queue framework. It provides an architecture for handling multiple requests efficiently across multiple CPU cores and hardware queues.

Important Components

  • Software staging queues: Organize requests before dispatch to hardware queues.
  • Hardware dispatch queues: Represent queues used to submit requests to the device.
  • Driver queue operations: Allow the driver to prepare and submit requests.
  • Completion handling: Reports finished operations to the block layer.
CPU Core 0 CPU Core 1 | | v v +---------------+ +---------------+ | Software Q0 | | Software Q1 | +---------------+ +---------------+ | | +--------+--------+ | v +------------------+ | Hardware Queues | +------------------+ | v +------------------+ | Storage Driver | +------------------+ | v +------------------+ | Storage Device | +------------------+

The mapping and number of queues depend on the driver, hardware and system configuration.

11. Request Dispatch

Request dispatch is the process of submitting prepared storage requests to the device driver for execution.

In a blk-mq driver, the driver implements queue operations appropriate to the device.

A simplified conceptual sequence is:

  1. The block layer prepares a request.
  2. The request is assigned to an appropriate hardware queue.
  3. The driver obtains the request for processing.
  4. The driver prepares the required device command.
  5. The command is submitted to the controller.
  6. The device processes the command.
Modern blk-mq drivers use interfaces such as struct blk_mq_ops. The exact callbacks and registration process depend on the kernel version and driver type.

12. Request Merging

Request merging combines compatible adjacent I/O operations. It can reduce request-processing overhead and improve throughput.

Example

Request A:
Sector 500
Length 4 sectors

Request B:
Sector 504
Length 4 sectors

If the operations are compatible and the queue permits merging, the block layer may produce: 

Merged Request:
Sector 500
Length 8 sectors

Benefits

  • Reduces the number of individual requests.
  • Can reduce command-submission overhead.
  • May improve sequential I/O performance.

13. I/O Scheduling

I/O scheduling determines how requests are organized and dispatched to a storage device.

The goal may be to improve throughput, reduce latency or provide fairness among competing processes.

Common scheduling considerations include:

  • Request ordering.
  • Read and write priority.
  • Fairness.
  • Latency targets.
  • Throughput.

The scheduler options available depend on the kernel and storage device. Some high-performance devices may use different scheduling strategies from traditional rotational disks.

Inspect Scheduler

cat /sys/block/sda/queue/scheduler

The scheduler shown in square brackets is generally the currently selected scheduler.

14. DMA in Block I/O

Direct Memory Access (DMA) allows a storage controller to transfer data between the device and system memory without requiring the CPU to copy every data unit individually.

Why DMA Is Used

  • Reduces CPU involvement in data transfers.
  • Improves data-transfer efficiency.
  • Supports high-throughput storage devices.
  • Allows controllers to transfer data using memory buffers.
+--------------------+ | CPU | +--------------------+ | | Configure Transfer v +--------------------+ | Storage Controller | +--------------------+ | | DMA Transfer v +--------------------+ | System RAM | +--------------------+

Linux drivers normally use the kernel DMA mapping API to prepare memory for device access. The exact DMA operations depend on the hardware and the device's DMA capabilities.

DMA does not mean that the CPU is completely uninvolved. The CPU still prepares commands, configures transfers and handles completion or error notifications.

15. Interrupts and Polling

A storage controller needs a way to notify the driver that an operation has completed or requires attention.

Interrupt-Based Completion

The controller generates an interrupt. The driver processes the completion information and informs the block layer.

Polling-Based Completion

The driver or kernel checks completion status directly instead of waiting for a hardware interrupt.

Interrupt Polling
Device notifies the CPU. CPU or driver checks device status.
Useful for asynchronous completion. Can reduce interrupt overhead in selected workloads.
Requires interrupt handling. Requires periodic or active status checking.

The appropriate method depends on the device, workload and driver implementation.

16. I/O Completion

After a request has been processed by the storage device, the driver must report its completion to the block layer.

Completion Sequence

  1. The driver submits a command to the controller.
  2. The controller performs the requested operation.
  3. The controller reports completion or an error.
  4. The driver identifies the completed request.
  5. The driver reports the result through the block-layer completion mechanism.
  6. The block layer completes the associated I/O operations.
  7. Waiting processes can continue when appropriate.
Request Submitted | v Device Processes I/O | v Completion Detected | v Driver Handles Result | v Block I/O Completed | v Waiting Operation Continues

17. I/O Error Handling

A storage request can fail because of device errors, timeouts, media problems or controller failures.

Error Type Description
I/O Error Requested data could not be read or written.
Timeout The controller did not complete the command in time.
Media Error The storage device reports a problem with its media.
Controller Error The storage controller reports a command or hardware failure.
Device Removal The device becomes unavailable during operation.

The driver must report the result correctly and follow the device-specific recovery and cleanup procedures.

18. Block I/O Request Processing Example

Consider an application reading 4096 bytes from a file stored on a block device with 512-byte logical sectors.

Step 1: Calculate the Number of Sectors

Requested Data = 4096 bytes
Logical Sector = 512 bytes

Number of Sectors = 4096 / 512
                  = 8 sectors

Step 2: Identify the Storage Location

Starting Sector = 1000
Number of Sectors = 8

Step 3: Create the I/O Operation

The relevant kernel I/O path creates the required block I/O representation and associates the memory buffers.

Step 4: Organize the Request

The block layer organizes the operation into requests and applies applicable queue limits.

Step 5: Dispatch

The storage driver submits the required command to the controller.

Step 6: Complete

The controller transfers the data, and the driver reports completion to the block layer.

Result: The requested 4096 bytes become available to the appropriate kernel I/O path and eventually to the application.

19. Observing Block I/O in Ubuntu

Linux provides tools that help inspect block devices and observe storage activity.

1. List Block Devices

lsblk

2. Display Device Statistics

cat /proc/diskstats

This file provides kernel-maintained statistics for block devices.

3. Monitor I/O Statistics

iostat -xz 1

If the command is unavailable, install the required package: 

sudo apt update
sudo apt install sysstat

4. Monitor Processes Performing I/O

sudo iotop

If required: 

sudo apt install iotop

5. Inspect Queue Settings

ls /sys/block/sda/queue/
The exact devices and statistics depend on the virtual storage controller and workload. A VirtualBox guest normally sees virtual disks rather than the host's physical storage controller.

20. Important Kernel Programming Concepts

Block drivers are developed using kernel interfaces. Some important concepts include:

  • struct bio - describes block I/O operations.
  • struct request - represents an organized request.
  • struct request_queue - manages request queue state.
  • struct blk_mq_ops - defines blk-mq driver operations.
  • blk_mq_tag_set - configures request-tag and queue-related resources.
  • DMA mapping APIs - prepare memory for device transfers.
  • Completion mechanisms - report the result of I/O.
These are conceptual introductions, not a complete driver API recipe. Function signatures, helper functions and registration steps must be verified against the exact Linux kernel version.

24. Lesson Summary

Block I/O is the mechanism through which Linux transfers data between memory and storage devices. The kernel represents I/O operations using BIO structures, organizes them into requests and dispatches them through the blk-mq framework.

The storage driver communicates with the controller, manages DMA and completion mechanisms where applicable, and reports success or failure to the block layer.

Understanding request processing is essential for developing and debugging Linux storage drivers.
