1. Introduction

Linux supports different types of hardware through specialized device driver subsystems.

Each subsystem provides a standard programming model for a particular category of hardware.

For example:

  • Character drivers provide stream-oriented access.
  • Block drivers provide block-oriented storage access.
  • Network drivers connect hardware to the networking stack.
  • Platform drivers manage devices integrated into a system.
  • I2C and SPI drivers communicate with peripherals over serial buses.
  • USB drivers manage USB interfaces and transfers.

Understanding these differences helps a developer select the correct kernel subsystem when implementing a driver.

Examples:

  • Simple sensor interfaces.
  • Custom control devices.
  • Some input and communication devices.

14. Device Tree and Driver Matching

Many embedded Linux systems describe hardware using Device Tree.

Device Tree is commonly used for platform devices and for peripherals connected to buses such as I2C and SPI.

Platform Driver Matching

static const struct of_device_id my_of_match[] = {
    { .compatible = "vendor,my-device" },
    { }
};

MODULE_DEVICE_TABLE(of, my_of_match);

I2C Driver Matching

I2C devices can be described using Device Tree compatible strings, allowing the I2C core to match an I2C client with a suitable driver.

SPI Driver Matching

SPI peripherals can also be described in Device Tree and matched with SPI drivers.

USB Driver Matching

USB devices are normally discovered through USB enumeration and matched using USB device or interface identification information.

Device Tree describes hardware that the system needs to know about. It is not a replacement for USB enumeration or the USB descriptor mechanism.

15. Character Driver vs Bus Driver

A character driver and a bus driver solve different problems.

A character driver provides a user-space device-file interface. A bus driver manages a peripheral according to the rules of a hardware bus.

A USB serial adapter may use a USB driver to communicate with the USB interface and a serial subsystem to expose a serial port to user space.

Similarly, an I2C sensor may use an I2C client driver and expose measurements through an appropriate kernel interface such as IIO or hwmon.

16. Choosing the Correct Driver Subsystem

Hardware or Requirement Likely Subsystem
Custom byte-oriented device interface Character
Storage device Block
Ethernet controller Network
On-chip UART controller Platform plus serial subsystem
I2C temperature sensor I2C plus suitable sensor subsystem
SPI ADC SPI plus IIO subsystem
USB serial converter USB plus serial subsystem
USB Ethernet adapter USB plus network subsystem

The correct choice depends on the hardware interface, the function being provided and the Linux subsystem that best represents the device.

18. Important Difference: LPC2129 and Linux Drivers

Bare-metal peripheral programming on an ARM7 microcontroller is different from writing a Linux kernel driver.

Aspect LPC2129 Bare-Metal Linux Kernel Driver
Execution Application code runs directly on the microcontroller. Driver runs inside the Linux kernel.
Hardware Access Direct register access. Kernel-managed resource and subsystem APIs.
UART Configure UART registers directly. Use the serial subsystem and controller driver model.
GPIO Configure GPIO direction and pin registers. Use GPIO descriptor and controller APIs.
I2C Implement or use the microcontroller I2C controller. Use I2C adapter and client driver framework.
Interrupts Configure the microcontroller interrupt controller. Use Linux IRQ APIs and interrupt framework.
Debugging Keil debugger and simulator. Kernel logs, tracing, debugger and hardware tools.
LPC2129 is an ARM7 microcontroller and does not run a standard Linux kernel. Its Keil simulator exercises are useful for embedded C and peripheral fundamentals, but Linux driver APIs must be practiced on a Linux system or suitable emulator.

19. Practical Subsystem Identification Exercise

Objective

Identify Linux driver subsystems used by different hardware devices.

Tasks

  1. Connect a USB flash drive.
  2. Run lsusb.
  3. Run lsblk to inspect storage devices.
  4. Run ip link to inspect network interfaces.
  5. Run ls /sys/bus/i2c/devices/.
  6. Run ls /sys/bus/spi/devices/.
  7. Run ls /sys/bus/platform/devices/.
  8. Inspect driver bindings under the relevant sysfs directories.

Expected Result

You should be able to distinguish storage, network, USB, I2C, SPI and platform devices by their kernel subsystem representation.

The I2C, SPI and platform directories may not contain physical peripheral entries in a VirtualBox Ubuntu guest. Their presence and contents depend on the virtual hardware and guest kernel configuration.

20. Important Points to Remember

  • Each Linux device subsystem has a specialized programming model.
  • Character drivers provide byte-stream interfaces.
  • Block drivers handle storage I/O.
  • Network drivers handle packet transmission and reception.
  • Platform drivers manage integrated devices.
  • I2C and SPI drivers communicate with bus peripherals.
  • USB drivers manage USB interfaces and transfers.
  • Subsystem registration and matching mechanisms differ.
  • One physical device may involve multiple kernel subsystems.
  • Device Tree is commonly used for embedded platform, I2C and SPI devices.
  • USB devices are discovered through enumeration.
  • Kernel API details must be checked against the target kernel version.

22. Chapter 18 - Complete Chapter Summary

This chapter covered three major areas of Linux device driver development: block devices, network devices and USB devices.

Block Device Drivers

Block drivers manage storage devices and work with the block layer, BIOs, requests, queues and completion mechanisms.

Network Device Drivers

Network drivers connect NIC hardware to the Linux networking stack through structures such as net_device and sk_buff, along with transmit and receive processing.

USB Device Drivers

USB drivers manage interfaces, match device IDs, register with the USB core, initialize devices through probe and release resources through disconnect.

Subsystem Selection

The correct subsystem depends on the hardware function and the Linux abstraction that best represents it.
