1. Introduction

USB device architecture defines how a USB device is organized and how communication takes place between the host and the peripheral.

A USB device is not simply a single communication channel. It may contain multiple configurations, interfaces and endpoints.

The Linux USB subsystem uses these architectural elements to identify devices, bind drivers and manage data transfers.

Important USB architectural components include:

  • USB device.
  • USB configuration.
  • USB interface.
  • USB alternate setting.
  • USB endpoint.
  • USB descriptor.
  • USB pipe.
  • USB transfer.
  • USB Request Block (URB).

2. USB Device Hierarchy

A USB device follows a hierarchical structure. The device contains configurations, configurations contain interfaces, and interfaces contain endpoints.

+--------------------------------------+ | USB Device | +--------------------------------------+ | v +--------------------------------------+ | Configuration | +--------------------------------------+ | +-------+-------+ | | v v +----------------+ +----------------+ | Interface 0 | | Interface 1 | +----------------+ +----------------+ | | v v +----------------+ +----------------+ | Endpoints | | Endpoints | +----------------+ +----------------+

Hierarchy Explanation

Component Purpose
Device Represents the complete USB peripheral.
Configuration Defines a selectable operating configuration.
Interface Represents a functional part of the device.
Alternate Setting Provides an alternative arrangement for an interface.
Endpoint Provides a communication endpoint for data transfer.

3. USB Device

A USB device is a peripheral connected to a USB host. It is identified through information contained in its device descriptor.

Examples include:

  • USB flash drive.
  • USB keyboard.
  • USB mouse.
  • USB webcam.
  • USB serial converter.
  • USB audio device.

A USB device has an address assigned by the host during enumeration.

The device also exposes one or more configurations and associated interfaces.

4. USB Configuration

A configuration describes an operating arrangement of a USB device.

A device may provide multiple configurations, although many commonly used USB devices expose only one.

The host selects a configuration during enumeration.

Configuration Descriptor Information

  • Configuration value.
  • Number of interfaces.
  • Configuration attributes.
  • Maximum power requirement information.
  • Total descriptor length.

Configuration Descriptor Structure

struct usb_config_descriptor
{
    __u8 bLength;
    __u8 bDescriptorType;
    __le16 wTotalLength;
    __u8 bNumInterfaces;
    __u8 bConfigurationValue;
    __u8 iConfiguration;
    __u8 bmAttributes;
    __u8 bMaxPower;
};

This is a simplified view of the descriptor fields. The Linux kernel definition includes the complete structure and associated type information.

The bConfigurationValue field identifies the configuration value used when selecting a configuration. It is not necessarily the configuration's position in a list.

5. USB Interface

A USB interface represents one functional part of a USB device.

A single USB device can contain multiple interfaces. Each interface may have its own driver.

Example: Composite USB Device

A composite USB device may provide multiple functions through separate interfaces.

+--------------------------------------+ | Composite USB Device | +--------------------------------------+ | +----------+----------+ | | | v v v +------------+ +----------+ +----------+ | Interface 0| |Interface 1| |Interface 2| | | | | | | | Keyboard | | Mouse | | Audio | +------------+ +----------+ +----------+

The Linux USB core can bind appropriate drivers to individual interfaces.

Interface Descriptor

struct usb_interface_descriptor
{
    __u8 bLength;
    __u8 bDescriptorType;
    __u8 bInterfaceNumber;
    __u8 bAlternateSetting;
    __u8 bNumEndpoints;
    __u8 bInterfaceClass;
    __u8 bInterfaceSubClass;
    __u8 bInterfaceProtocol;
    __u8 iInterface;
};

6. USB Alternate Settings

An interface may provide multiple alternate settings. These allow the host to select different interface operating characteristics.

Different alternate settings can provide different endpoint arrangements or transfer requirements.

Example: A USB audio interface may provide an alternate setting with no active streaming endpoints and another setting with endpoints configured for audio streaming.

Linux provides an interface for selecting an alternate setting, including: 

usb_set_interface()

The driver must select an alternate setting supported by the device.

7. USB Endpoints

An endpoint is a source or destination for communication between the USB host and device.

Each endpoint is identified by an endpoint address. Endpoint zero is reserved for control communication and is present as the default control endpoint.

Endpoint Direction

Direction Meaning
IN Data travels from the USB device to the host.
OUT Data travels from the USB host to the device.

Endpoint Address

An endpoint address contains an endpoint number and a direction bit.

Example:

0x81

This represents endpoint number 1 in the IN direction. 

0x02

This represents endpoint number 2 in the OUT direction.

Endpoint zero is used for control transfers. Other endpoints are described by endpoint descriptors and belong to particular interfaces and alternate settings.

8. USB Endpoint Types

USB endpoints support different transfer types. The endpoint descriptor identifies the transfer type.

Transfer Type Characteristics Typical Application
Control Configuration and command communication. Device setup.
Bulk Reliable transfer without reserved latency. Storage devices.
Interrupt Periodic service with bounded latency. Human interface devices.
Isochronous Time-sensitive data with reserved bandwidth. Audio streaming.

Control endpoints are bidirectional at the protocol level. Bulk, interrupt and isochronous endpoints have a defined direction.

9. USB Descriptors

Descriptors are data structures that describe USB device capabilities and organization.

Main Descriptor Types

Descriptor Information
Device VID, PID, USB version and device-level information.
Configuration Configuration properties and interface count.
Interface Interface number, class and endpoint count.
Endpoint Endpoint address, transfer type and packet size.
String Human-readable manufacturer, product and serial information.
Interface Association Groups related interfaces for composite functions.

Device Descriptor Structure

struct usb_device_descriptor
{
    __u8 bLength;
    __u8 bDescriptorType;
    __le16 bcdUSB;
    __u8 bDeviceClass;
    __u8 bDeviceSubClass;
    __u8 bDeviceProtocol;
    __u8 bMaxPacketSize0;
    __le16 idVendor;
    __le16 idProduct;
    __le16 bcdDevice;
    __u8 iManufacturer;
    __u8 iProduct;
    __u8 iSerialNumber;
    __u8 bNumConfigurations;
};

The Linux USB core reads and interprets descriptors during device enumeration.

10. USB Pipe

A USB pipe is a logical communication channel between the USB host and a particular endpoint on a device.

In Linux, pipe values are used by USB transfer APIs to identify the target device, endpoint and transfer type.

Important pipe-related helper functions include:

usb_sndctrlpipe()
usb_rcvctrlpipe()

usb_sndbulkpipe()
usb_rcvbulkpipe()

usb_sndintpipe()
usb_rcvintpipe()

usb_sndisocpipe()
usb_rcvisocpipe()

The helper used depends on the transfer type and communication direction.

A pipe is a software representation of a communication path. It is not a separate physical wire.

11. USB Transfer Architecture

USB communication involves the host submitting transfer requests and the USB subsystem arranging their execution.

+--------------------------------------+ | USB Device Driver | +--------------------------------------+ | v +--------------------------------------+ | Transfer Request (URB) | +--------------------------------------+ | v +--------------------------------------+ | USB Core | +--------------------------------------+ | v +--------------------------------------+ | Host Controller Driver | +--------------------------------------+ | v +--------------------------------------+ | USB Host Controller | +--------------------------------------+ | v +--------------------------------------+ | USB Device | +--------------------------------------+

After the transfer completes, the USB subsystem reports the result through the completion mechanism.

12. USB Request Block (URB)

A USB Request Block represents a USB transfer request in the Linux kernel.

The USB driver allocates and initializes an URB, submits it and handles its completion.

Important URB Fields

  • Target USB device.
  • Endpoint pipe.
  • Transfer buffer.
  • Transfer buffer length.
  • Transfer flags.
  • Completion callback.
  • Transfer status.
  • Actual transferred length.

URB Lifecycle

Allocate URB | v Initialize URB | v Prepare Transfer Buffer | v Submit URB | v USB Core Processes Request | v Host Controller Performs Transfer | v Completion Callback | v Process Result | v Reuse or Free URB

13. USB Control Transfer Architecture

A control transfer is used for device configuration and control communication.

It normally contains three stages:

  1. Setup stage: Sends the request information.
  2. Data stage: Transfers optional data.
  3. Status stage: Completes the control request.
+----------------------------+ | Setup Stage | | Request and Parameters | +----------------------------+ | v +----------------------------+ | Data Stage | | Optional Data Transfer | +----------------------------+ | v +----------------------------+ | Status Stage | | Transfer Completion | +----------------------------+

A control transfer may have no data stage, depending on the request.

Linux provides helper functions such as: 

usb_control_msg()

This helper performs a synchronous control request. Its exact parameters and behavior should be checked against the target kernel headers.

14. Bulk Transfer Architecture

Bulk transfers are designed for reliable data transfer where a guaranteed delivery time is not required.

They are commonly used for:

  • USB mass storage.
  • USB serial communication.
  • Large data transfers.
  • Device firmware communication.

Bulk transfers use error detection and retry mechanisms provided by the USB protocol.

Linux Helper Functions

usb_bulk_msg()

usb_sndbulkpipe()
usb_rcvbulkpipe()

The synchronous bulk helper can be convenient for simple operations. Asynchronous drivers commonly use URBs.

15. Interrupt Transfer Architecture

Interrupt transfers are suitable for devices that need periodic or bounded-latency communication.

Examples include keyboards, mice and other input devices.

The USB host schedules service according to the endpoint's polling interval and the bus scheduling rules.

Linux Helper Functions

usb_fill_int_urb()

usb_sndintpipe()
usb_rcvintpipe()

A driver commonly submits an interrupt URB and processes incoming data in its completion callback.

16. Isochronous Transfer Architecture

Isochronous transfers support time-sensitive data streams where consistent timing is important.

Typical applications include:

  • USB audio streaming.
  • Video streaming.
  • Real-time data acquisition.

Isochronous transfers reserve bus bandwidth, but do not use the same retry mechanism as bulk transfers.

An isochronous URB contains information about individual isochronous packets, including packet lengths and statuses.

A failed isochronous packet is generally not retransmitted through the normal USB bulk-style retry mechanism. The application or driver must handle missing or corrupted stream data appropriately.

17. Linux USB Kernel Data Structures

Linux provides several important structures to represent USB devices and their components.

Structure Purpose
struct usb_device Represents a USB device.
struct usb_interface Represents a USB interface.
struct usb_driver Represents a registered USB driver.
struct usb_device_id Defines USB device matching information.
struct usb_host_interface Represents an interface alternate setting.
struct usb_host_endpoint Represents an endpoint in the host-side model.
struct urb Represents a USB transfer request.
struct usb_device_descriptor Represents device descriptor information.
struct usb_interface_descriptor Represents interface descriptor information.
The structures listed here are kernel implementation structures. Their exact fields and relationships should be studied using the headers for the kernel version being targeted.

18. USB Device Matching

The Linux USB core uses device identification information to determine whether a registered driver supports a particular USB interface.

A driver can match using fields such as:

  • Vendor ID.
  • Product ID.
  • Device class.
  • Interface class.
  • Interface subclass.
  • Interface protocol.

The matching information is commonly stored in a struct usb_device_id table.

The USB core uses the driver's matching table during driver binding.

19. USB Device Removal

When a USB device is disconnected, the USB subsystem notifies its bound driver.

The driver must:

  • Stop new operations.
  • Terminate or cancel outstanding URBs.
  • Prevent completion handlers from accessing released data.
  • Release transfer buffers.
  • Release device-specific resources.
  • Clear interface driver data.

Functions such as usb_kill_urb() are used to stop an active URB synchronously.

Disconnect handling must be carefully synchronized. An asynchronous completion callback must never access memory after the driver has released it.

20. Practical USB Architecture Inspection

Objective

Inspect the USB device hierarchy and identify descriptors, interfaces and endpoints in Ubuntu.

Commands

# List connected USB devices
lsusb

# Display detailed descriptors
sudo lsusb -v

# Display USB topology
lsusb -t

# Inspect USB device directory
ls /sys/bus/usb/devices/

# Display USB kernel messages
dmesg | grep -i usb

Procedure

  1. Connect a USB device to the computer.
  2. Run lsusb.
  3. Identify the device's VID and PID.
  4. Run lsusb -t.
  5. Inspect the detailed descriptors.
  6. Identify its configurations and interfaces.
  7. Find endpoint addresses and transfer types.
  8. Observe kernel messages after connecting and disconnecting.

Expected Result

You should understand how a USB device is represented in Linux and how its interfaces and endpoints are organized.

21. Important Points to Remember

  • A USB device can contain multiple configurations.
  • A configuration contains interfaces.
  • An interface can contain alternate settings.
  • Alternate settings define alternative endpoint arrangements.
  • Endpoints provide communication channels.
  • Endpoint zero is the default control endpoint.
  • USB defines four main transfer types.
  • Descriptors describe device capabilities and organization.
  • A pipe is a logical communication channel.
  • URBs represent USB transfer requests in Linux.
  • USB drivers commonly bind to interfaces.
  • Disconnect handling must release resources safely.

23. Lesson Summary

USB device architecture organizes a peripheral into configurations, interfaces, alternate settings and endpoints.

Descriptors describe these components, while pipes and transfer requests provide the logical communication mechanisms used by the USB subsystem.

Linux represents USB devices and their components using kernel data structures such as usb_device, usb_interface, usb_driver and urb.

Understanding this architecture is essential before implementing USB driver registration, probe and disconnect functions.
