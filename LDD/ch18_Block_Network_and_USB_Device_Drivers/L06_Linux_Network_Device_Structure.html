1. Introduction

Linux network device drivers use a collection of kernel data structures to represent network interfaces, manage packets and communicate with network hardware.

These structures provide a standard interface between the Linux networking subsystem and hardware-specific network drivers.

The important structures include:

  • struct net_device
  • struct net_device_ops
  • struct sk_buff
  • struct napi_struct
  • struct net_device_stats
  • struct ethtool_ops
  • Network transmit and receive queue structures.
  • Driver-private data structures.

3. struct net_device

The struct net_device structure represents a network interface in the Linux kernel.

For example, an Ethernet interface named enp3s0 is represented by a net_device instance.

Important information associated with this structure includes:

  • Network interface name.
  • MAC address.
  • Maximum transmission unit.
  • Interface flags and state.
  • Network device operation callbacks.
  • Transmit queue information.
  • Network device features.
  • Driver-private data association.

Conceptual Example

struct net_device
{
    /* Interface information */
    /* Network device operations */
    /* Transmit queue information */
    /* Device state and features */
    /* Driver-private data association */
};
This is a conceptual representation, not the actual kernel structure definition. The real structure contains many fields and changes between kernel versions.

4. Allocating a Network Device

A network driver needs a network device structure before it can register an interface with the networking subsystem.

For Ethernet-style devices, a commonly used allocation helper is: 

alloc_etherdev()

It allocates and initializes an Ethernet network device and provides space for driver-private data.

Conceptual Syntax

struct net_device *ndev;

ndev = alloc_etherdev(sizeof(struct my_private_data));

The size argument specifies the amount of driver-private storage associated with the allocated network device.

The returned pointer refers to the network device. The driver can access its private data using supported kernel helper functions.

5. Network Device Private Data

A network driver requires additional information that is specific to its hardware.

Examples include:

  • Hardware register information.
  • DMA descriptor ring addresses.
  • Transmit and receive buffer information.
  • Interrupt number and state.
  • NAPI structure.
  • Hardware configuration information.
  • Queue management data.

This information is commonly stored in a driver-private structure.

Example

struct my_private_data
{
    int irq_number;

    /* Hardware-specific state */
    /* DMA descriptor information */
    /* TX/RX queue information */

    struct napi_struct napi;
};

The exact members depend on the network controller.

Accessing Private Data

struct my_private_data *priv;

priv = netdev_priv(ndev);

The netdev_priv() helper retrieves the driver-private data associated with the network device.

6. struct net_device_ops

The struct net_device_ops structure contains function pointers for network interface operations.

The driver assigns supported callback functions to this structure.

Important Callbacks

Callback Purpose
ndo_open Starts the network interface.
ndo_stop Stops the network interface.
ndo_start_xmit Handles outgoing packets.
ndo_get_stats64 Reports network statistics.
ndo_set_mac_address Changes the MAC address when supported.
ndo_change_mtu Handles MTU changes when supported.
ndo_set_rx_mode Configures receive filtering mode.

Conceptual Definition

static const struct net_device_ops my_netdev_ops = {
    .ndo_open       = my_open,
    .ndo_stop       = my_stop,
    .ndo_start_xmit = my_start_xmit,
};

The callback functions must use the correct signatures and behavior for the target kernel version.

7. ndo_open Callback

The ndo_open callback is invoked when the network interface is brought up.

Typical responsibilities include:

  • Initializing the network controller.
  • Allocating or preparing receive buffers.
  • Setting up transmit and receive queues.
  • Configuring interrupts.
  • Enabling NAPI where required.
  • Starting the hardware.

Conceptual Example

static int my_open(struct net_device *ndev)
{
    /*
     * Initialize hardware.
     * Prepare DMA buffers.
     * Configure interrupts.
     * Enable receive processing.
     */

    netif_start_queue(ndev);

    return 0;
}

This is an illustrative skeleton. A real driver must initialize the hardware and handle failures correctly.

8. ndo_stop Callback

The ndo_stop callback is invoked when the network interface is stopped.

Typical responsibilities include:

  • Stopping packet transmission.
  • Disabling hardware reception.
  • Stopping or synchronizing interrupt handling.
  • Disabling NAPI.
  • Stopping hardware queues.
  • Releasing resources that are no longer required.

Conceptual Example

static int my_stop(struct net_device *ndev)
{
    netif_stop_queue(ndev);

    /*
     * Stop hardware.
     * Disable interrupts safely.
     * Stop NAPI.
     * Release active resources.
     */

    return 0;
}

9. ndo_start_xmit Callback

The ndo_start_xmit callback handles packet transmission from the networking subsystem to the driver.

It receives an skb containing the packet to transmit.

Conceptual Function

static netdev_tx_t my_start_xmit(
    struct sk_buff *skb,
    struct net_device *ndev)
{
    /*
     * Obtain driver-private data.
     * Check TX queue availability.
     * Map packet data for DMA.
     * Prepare hardware descriptors.
     * Notify the network controller.
     */

    return NETDEV_TX_OK;
}

The return value is important:

Return Value Meaning
NETDEV_TX_OK The driver accepted the packet.
NETDEV_TX_BUSY The driver could not accept the packet at that time.
The driver must follow the skb ownership rules. Returning NETDEV_TX_BUSY means the packet was not accepted and the networking subsystem may retry it. A driver must not incorrectly free or consume that skb.

10. struct sk_buff

The struct sk_buff structure represents network packet data and metadata.

It is one of the most important structures in Linux networking.

Important Information

  • Packet length.
  • Packet data references.
  • Network protocol information.
  • MAC header position.
  • Network header position.
  • Transport header position.
  • Checksum information.
  • Packet-processing metadata.
+--------------------------------------+ | sk_buff | +--------------------------------------+ | Packet Metadata | +--------------------------------------+ | MAC Header Reference | +--------------------------------------+ | Network Header Reference | +--------------------------------------+ | Transport Header Reference | +--------------------------------------+ | Packet Length | +--------------------------------------+ | Data Buffer References | +--------------------------------------+

An skb may reference linear and non-linear packet data. Drivers must use supported skb and DMA APIs rather than assuming every packet is stored in one contiguous buffer.

11. struct napi_struct

The struct napi_struct structure represents a NAPI polling context.

NAPI is used to process received packets efficiently, especially under heavy network traffic.

A driver commonly embeds a NAPI structure in its driver-private data.

Conceptual Example

struct my_private_data
{
    struct napi_struct napi;

    /* Other driver-specific members */
};

Important NAPI Functions

netif_napi_add()
napi_schedule()
napi_complete_done()
napi_disable()

The exact function signatures and helper variants depend on the target kernel version.

The driver supplies a polling callback that processes received packets within the specified budget.

12. Network Statistics

Network statistics provide information about the operation of a network interface.

Common statistics include:

  • Packets received.
  • Packets transmitted.
  • Bytes received.
  • Bytes transmitted.
  • Receive errors.
  • Transmit errors.
  • Dropped packets.

Linux provides network statistics interfaces, including struct rtnl_link_stats64 for 64-bit link statistics.

A driver may report statistics using ndo_get_stats64 where required by its design.

Conceptual Callback

static void my_get_stats64(
    struct net_device *ndev,
    struct rtnl_link_stats64 *stats)
{
    /*
     * Copy driver-maintained counters into stats.
     */
}

Actual statistics must be maintained consistently by the driver, including appropriate synchronization for concurrent access.

13. struct ethtool_ops

The ethtool interface provides tools for inspecting and configuring supported Ethernet device features.

Drivers can implement supported operations using struct ethtool_ops.

Possible capabilities include:

  • Driver information.
  • Link settings.
  • Link status.
  • Network statistics.
  • Ring parameters.
  • Coalescing settings.
  • Supported offload features.

Inspect Driver Information

sudo ethtool -i enp3s0

Inspect Link Settings

sudo ethtool enp3s0

The available commands and information depend on the driver and hardware capabilities.

14. Network Transmit Queue Structures

Linux network interfaces can have one or more transmit queues.

A transmit queue manages outgoing packet scheduling and transmission.

The networking subsystem provides queue-management functions such as: 

netif_start_queue()
netif_stop_queue()
netif_wake_queue()

netif_tx_start_all_queues()
netif_tx_stop_all_queues()
netif_tx_wake_all_queues()

These helpers allow the driver to control whether the networking subsystem should submit more packets for transmission.

Example: If a hardware transmit ring becomes full, the driver can stop the relevant queue. When transmission completes and descriptor space becomes available, the driver can wake the queue.

15. Network Device Features

Network devices may support hardware and software features that improve packet processing.

Linux represents network device feature capabilities using the networking feature mechanisms, including netdev_features_t.

Examples include:

  • Checksum offloading.
  • Scatter-gather transmission.
  • TCP segmentation offload.
  • Generic segmentation offload.
  • Receive checksum processing.

Drivers must advertise only features that are correctly supported by the hardware and implementation.

16. Network Device Registration

A network driver must register its network device before the interface can be managed by the networking subsystem.

Important Functions

Function Purpose
alloc_etherdev() Allocates an Ethernet network device and private data area.
netdev_priv() Returns the driver-private data area.
register_netdev() Registers the network interface.
unregister_netdev() Unregisters the network interface.
free_netdev() Releases the network device allocation.

Conceptual Registration Sequence

ndev = alloc_etherdev(sizeof(struct my_private_data));

if (!ndev)
    return -ENOMEM;

/* Configure the network device. */
/* Set the device operations. */
/* Initialize private data. */

ret = register_netdev(ndev);

if (ret) {
    free_netdev(ndev);
    return ret;
}

This example demonstrates the basic allocation and registration sequence only. A complete driver must also handle hardware initialization, resource acquisition, error paths and bus-specific cleanup.

17. Network Device Unregistration

When a network driver is removed, its interface must be unregistered before its memory and hardware resources are released.

Conceptual Cleanup Sequence

unregister_netdev(ndev);

/* Release hardware resources. */
/* Release DMA resources. */
/* Free driver-specific resources. */

free_netdev(ndev);

The driver must ensure that the interface is no longer active and that asynchronous operations cannot access freed resources.

18. Driver Structure Relationship

The important structures work together during network communication.

net_device | +---------+----------+ | | | v v v net_device_ops TX/RX Private Queues Data | +---------+---------+ | | | v v v NAPI DMA Hardware Structure Rings State sk_buff | v Packet Processing

The network device represents the interface. The operations structure connects the networking subsystem to driver callbacks. Private data stores hardware-specific state. The skb represents packets, while NAPI and queue structures support efficient packet processing.

19. Practical Network Inspection in Ubuntu

Use these commands to inspect network interfaces and their associated information.

List Interfaces

ip link show

Display MAC Address

cat /sys/class/net/enp3s0/address

Display MTU

cat /sys/class/net/enp3s0/mtu

Display Interface State

cat /sys/class/net/enp3s0/operstate

Display Driver Information

sudo ethtool -i enp3s0

Display Network Statistics

ip -s link show enp3s0

Display Network Device Entries

ls /sys/class/net/

Replace enp3s0 with your actual interface name.

20. Practical Exercise

Objective

Inspect network interface properties and understand the relationship between the interface and its driver.

Procedure

  1. Open the Ubuntu terminal.
  2. Run ip link show.
  3. Identify the Ethernet or virtual network interface.
  4. Inspect its MAC address.
  5. Inspect its MTU.
  6. Inspect its operational state.
  7. Run ethtool -i if supported.
  8. Record the driver name and version if available.

Expected Result

You should be able to identify the network interface, its MAC address, MTU, operational state and available driver information.

VirtualBox exposes a virtual network adapter to Ubuntu. The guest's network driver therefore operates on the virtual device model rather than directly controlling the host's physical Wi-Fi hardware.

21. Important Points to Remember

  • struct net_device represents a network interface.
  • netdev_priv() accesses driver-private data.
  • struct net_device_ops defines network callbacks.
  • ndo_open starts the network interface.
  • ndo_stop stops the network interface.
  • ndo_start_xmit handles outgoing packets.
  • struct sk_buff represents packet data and metadata.
  • struct napi_struct supports NAPI polling.
  • struct ethtool_ops provides optional ethtool operations.
  • TX queues manage outgoing packet transmission.
  • Network statistics help monitor interface operation.
  • Network registration makes the interface available to the kernel.

23. Lesson Summary

Linux network device drivers use standard kernel structures to represent interfaces, manage packet data and communicate with hardware.

The most important structures are struct net_device, struct net_device_ops, struct sk_buff and struct napi_struct.

Understanding these structures provides the foundation for implementing and debugging Linux network drivers.
