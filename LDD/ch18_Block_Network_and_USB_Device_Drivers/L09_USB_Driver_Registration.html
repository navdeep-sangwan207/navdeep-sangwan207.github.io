1. Introduction

Linux provides a USB driver framework that allows device drivers to communicate with USB peripherals.

A USB driver registers itself with the Linux USB core. The USB core compares connected USB interfaces against the driver's supported device identification table.

When a match is found, the USB core can bind the driver to the interface and invoke its probe function.

Important concepts include:

  • USB driver model.
  • struct usb_driver.
  • struct usb_device_id.
  • Vendor ID and Product ID.
  • USB interface matching.
  • usb_register().
  • usb_deregister().
  • Module initialization and cleanup.

2. USB Driver Architecture in Linux

The Linux USB subsystem contains the USB core, host controller drivers and USB device drivers.

+--------------------------------------+ | USB Device Driver | +--------------------------------------+ | v +--------------------------------------+ | USB Core | | | | Device Matching and Driver Binding | +--------------------------------------+ | v +--------------------------------------+ | Host Controller Driver | +--------------------------------------+ | v +--------------------------------------+ | USB Host Controller | +--------------------------------------+ | v +--------------------------------------+ | USB Device | +--------------------------------------+

USB Core Responsibilities

  • USB device enumeration.
  • Descriptor handling.
  • Device and interface management.
  • USB driver matching.
  • Driver binding and unbinding.
  • Transfer request management.

USB Device Driver Responsibilities

  • Declare supported USB devices or interfaces.
  • Register with the USB core.
  • Initialize a matched interface in probe.
  • Perform communication with the peripheral.
  • Release resources during disconnect.

3. USB Driver Data Structure

The Linux kernel represents a USB device driver using struct usb_driver.

It contains callback functions, a matching table and other driver information.

Important Members

Member Purpose
name Driver name.
probe Called when a supported interface is bound.
disconnect Called when the interface is disconnected or unbound.
id_table Table describing supported USB devices or interfaces.
suspend Optional power-management callback.
resume Optional power-management callback.
reset_resume Optional callback used after certain reset-resume events.

Structure Example

static struct usb_driver my_usb_driver = {
    .name       = "my_usb_driver",
    .probe      = my_usb_probe,
    .disconnect = my_usb_disconnect,
    .id_table   = my_usb_id_table,
};

The example assumes that the callback functions and device ID table have been declared.

4. USB Vendor ID and Product ID

USB devices commonly identify their manufacturer and product using two 16-bit values.

  • VID: Vendor ID.
  • PID: Product ID.

The VID identifies the vendor, while the PID identifies a product or product family assigned by that vendor.

Example

idVendor  = 0x1234
idProduct = 0x5678

These values are illustrative. A real driver must use the actual IDs assigned to the target device.

Find VID and PID in Ubuntu

lsusb

Example output:

Bus 001 Device 004: ID 1234:5678 Example USB Device

The first hexadecimal value is the VID and the second is the PID.

5. USB Device ID Table

The USB ID table specifies which devices or interfaces a driver supports.

Linux defines struct usb_device_id for this purpose.

Matching by Vendor and Product

static const struct usb_device_id my_usb_id_table[] = {
    { USB_DEVICE(0x1234, 0x5678) },
    { }
};

MODULE_DEVICE_TABLE(usb, my_usb_id_table);

The USB_DEVICE() macro creates an entry that matches the specified vendor and product IDs.

The final empty entry marks the end of the table.

Matching by Interface Class

static const struct usb_device_id my_usb_id_table[] = {
    {
        .match_flags = USB_DEVICE_ID_MATCH_INT_CLASS,
        .bInterfaceClass = 0x03,
    },
    { }
};

MODULE_DEVICE_TABLE(usb, my_usb_id_table);

This example matches interfaces belonging to USB class 0x03, commonly associated with Human Interface Devices.

A class-based match can apply to multiple products. A production driver should match sufficiently specific device or interface characteristics to avoid binding to unsupported hardware.

6. USB Matching Macros

The kernel provides macros that simplify USB ID table creation.

Macro Matching Purpose
USB_DEVICE(vendor, product) Matches a vendor and product ID.
USB_DEVICE_VER(vendor, product, lo, hi) Matches a device and a specified device-version range.
USB_DEVICE_INTERFACE_CLASS(v, p, cls) Matches device IDs and an interface class.
USB_INTERFACE_INFO(cls, sub, proto) Matches interface class, subclass and protocol.

The precise matching rules and available macros should be checked in the target kernel's USB headers.

7. Registering a USB Driver

After defining the USB driver structure, the driver must register it with the USB core.

Linux provides the registration function: 

usb_register()

A commonly used convenience macro is: 

module_usb_driver(my_usb_driver);

This macro arranges the module initialization and cleanup operations for registering and deregistering the USB driver.

Manual Registration

static int __init my_usb_init(void)
{
    return usb_register(&my_usb_driver);
}

static void __exit my_usb_exit(void)
{
    usb_deregister(&my_usb_driver);
}

module_init(my_usb_init);
module_exit(my_usb_exit);

Use either the convenience macro or explicit module initialization and cleanup functions for the same driver, not both.

8. Deregistering a USB Driver

When the driver module is unloaded, it must unregister from the USB core.

Linux provides: 

usb_deregister()

Deregistration removes the driver from the USB driver model and causes its bound interfaces to be detached. The USB core invokes the appropriate disconnect callback for interfaces being unbound.

The driver must ensure that its disconnect callback releases all interface-specific resources safely.

9. USB Driver Registration Flow

Load USB Driver Module | v Module Initialization | v usb_register() | v USB Core Registers Driver | v Compare Supported Device IDs | v Device Match? / \ No Yes | | v v Wait for Bind Driver Future | Device v probe() | v Driver Active | v Device Disconnected | v disconnect() | v Release Resources

The matching process can occur when a device is already connected or when a matching device is connected later.

10. Complete USB Driver Registration Example

The following example demonstrates a minimal USB driver registration skeleton. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/usb.h>

#define MY_VENDOR_ID   0x1234
#define MY_PRODUCT_ID  0x5678

static int my_usb_probe(struct usb_interface *interface,
                        const struct usb_device_id *id)
{
    struct usb_device *udev;

    udev = interface_to_usbdev(interface);

    dev_info(&interface->dev,
             "USB device connected: VID=%04X PID=%04X\n",
             udev->descriptor.idVendor,
             udev->descriptor.idProduct);

    return 0;
}

static void my_usb_disconnect(struct usb_interface *interface)
{
    dev_info(&interface->dev,
             "USB device disconnected\n");
}

static const struct usb_device_id my_usb_id_table[] = {
    { USB_DEVICE(MY_VENDOR_ID, MY_PRODUCT_ID) },
    { }
};

MODULE_DEVICE_TABLE(usb, my_usb_id_table);

static struct usb_driver my_usb_driver = {
    .name       = "my_usb_driver",
    .probe      = my_usb_probe,
    .disconnect = my_usb_disconnect,
    .id_table   = my_usb_id_table,
};

module_usb_driver(my_usb_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic USB Driver Registration Example");

Program Explanation

  1. linux/usb.h provides USB subsystem definitions.
  2. The VID and PID identify the target device.
  3. my_usb_probe() runs when a matching interface is bound.
  4. interface_to_usbdev() obtains the associated USB device.
  5. my_usb_disconnect() handles interface removal.
  6. The ID table defines the supported device.
  7. MODULE_DEVICE_TABLE() exposes matching information for module alias generation.
  8. module_usb_driver() handles registration and deregistration.
This is a registration demonstration, not a complete data-transfer driver. It does not submit URBs or perform device-specific communication. Replace the example IDs with real IDs before testing with hardware.

11. USB Probe Function

The USB core invokes the probe callback when a driver matches a USB interface.

The probe callback receives: 

struct usb_interface *interface

const struct usb_device_id *id

The interface represents the function being bound. The ID pointer identifies the matching entry in the driver's ID table.

Typical probe operations include:

  • Identify the associated USB device.
  • Inspect the current alternate setting.
  • Find suitable endpoints.
  • Allocate driver-private data.
  • Initialize transfer buffers and URBs.
  • Store private data using interface driver data.

Detailed probe and disconnect implementation is covered in the next lesson.

12. USB Driver and Interface Binding

USB drivers normally bind to USB interfaces rather than owning the entire physical USB device.

This supports composite devices, where different interfaces may be controlled by different drivers.

USB Device | +----------+----------+ | | v v Interface 0 Interface 1 | | v v Driver A Driver B

The USB core manages the binding relationship between interfaces and drivers.

13. USB Driver Module Compilation

A USB driver is normally compiled as a Linux kernel module during development.

Example Makefile

obj-m += my_usb_driver.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Build Commands

# Compile the module
make

# Check generated module
ls -l my_usb_driver.ko

# Inspect module metadata
modinfo my_usb_driver.ko

# Load the module
sudo insmod my_usb_driver.ko

# Check kernel messages
sudo dmesg | tail -30

# Remove the module
sudo rmmod my_usb_driver

# Clean generated files
make clean
The build requires kernel headers or a matching kernel build tree for the running kernel. Kernel API details can vary across versions.

16. USB Driver Power Management

USB drivers may provide optional suspend and resume callbacks for power-management events.

These callbacks help the driver handle device power state transitions.

  • suspend: Prepare the interface for a low-power state.
  • resume: Restore normal operation.
  • reset_resume: Handle certain resume events that involve device reset.

A driver must account for outstanding transfers and device-specific state when implementing power management.

17. USB Passthrough in VirtualBox

When testing a USB driver inside Ubuntu running in VirtualBox, the physical USB device must be made available to the guest operating system.

General Procedure

  1. Shut down the Ubuntu virtual machine if required.
  2. Open the VirtualBox virtual machine settings.
  3. Configure the USB controller supported by the installation.
  4. Start Ubuntu.
  5. Attach the physical USB device to the guest through the VirtualBox device menu.
  6. Run lsusb inside Ubuntu.
  7. Verify that the device appears in the guest.
USB passthrough depends on VirtualBox configuration, host permissions and available USB support. Without passthrough, Ubuntu may see only virtual USB devices rather than the physical peripheral.

18. Practical Exercise

Objective

Create and compile a basic USB driver registration module and observe how the Linux USB core handles matching.

Tasks

  1. Create my_usb_driver.c.
  2. Define a USB device ID table.
  3. Define probe and disconnect callbacks.
  4. Define a struct usb_driver.
  5. Register it using module_usb_driver().
  6. Create the Makefile.
  7. Compile the module.
  8. Inspect the module using modinfo.
  9. Load the module.
  10. Connect a matching USB device, if available.
  11. Observe the probe message.
  12. Disconnect the device and observe the disconnect message.
  13. Remove the module.

Expected Result

The module should load successfully. When a supported USB interface is detected and bound, the probe callback should execute. On disconnection or driver unbinding, the disconnect callback should execute.

If no matching physical USB device is available, module registration can still be tested, but probe execution cannot be demonstrated without a matching interface.

19. Important Points to Remember

  • USB drivers register with the Linux USB core.
  • struct usb_driver describes a USB driver.
  • struct usb_device_id describes supported devices or interfaces.
  • VID and PID are common device matching fields.
  • USB drivers normally bind to interfaces.
  • USB_DEVICE() is used for VID/PID matching.
  • MODULE_DEVICE_TABLE() exports module matching information.
  • usb_register() registers a USB driver.
  • usb_deregister() unregisters a USB driver.
  • module_usb_driver() simplifies module registration.
  • The USB core invokes probe and disconnect callbacks.
  • Device-specific transfers are implemented separately using USB transfer APIs.

21. Lesson Summary

USB driver registration connects a Linux USB driver to the USB core. The driver declares its supported devices through a USB ID table and provides callbacks for interface binding and removal.

The USB core performs matching and invokes the driver's probe and disconnect callbacks. Registration can be handled through usb_register() and usb_deregister(), or through the convenient module_usb_driver() macro.

This registration process is the foundation for implementing a complete USB device driver.
