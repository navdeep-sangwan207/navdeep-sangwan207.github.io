1. Introduction

A USB device driver communicates with a USB peripheral through the Linux USB subsystem.

Two important callbacks control the interface lifecycle:

  • probe(): Initializes the driver when a matching USB interface is bound.
  • disconnect(): Releases resources when the interface is disconnected or unbound.

The USB core invokes these callbacks. The driver does not normally call them directly.

USB Device Connected | v USB Enumeration | v Driver Matching | v probe() | v Initialize Interface | v Device Operation | v Device Disconnected | v disconnect() | v Release Resources

2. USB Probe Function

The probe function is called when the USB core finds a matching interface for a registered USB driver.

Function Prototype

static int my_usb_probe(
    struct usb_interface *interface,
    const struct usb_device_id *id
);

Parameters

Parameter Description
interface Represents the USB interface being bound to the driver.
id Points to the matching entry in the driver's USB ID table.

Return Value

  • Return 0 when initialization succeeds.
  • Return a negative error code when initialization fails.

A successful probe indicates that the driver accepted the interface and completed its initialization.

3. Responsibilities of the Probe Function

The probe callback performs the initial setup required for the USB interface.

Common operations include:

  1. Obtain the associated USB device.
  2. Inspect the interface descriptors.
  3. Identify the required endpoints.
  4. Allocate driver-private memory.
  5. Allocate transfer buffers.
  6. Allocate and initialize URBs if required.
  7. Store private data in the interface.
  8. Initialize any device-specific communication state.
Not every USB driver needs to allocate URBs during probe. The resources depend on the communication method and the requirements of the peripheral.

4. Obtaining the USB Device

The probe function receives a USB interface pointer. The associated USB device can be obtained using: 

struct usb_device *udev;

udev = interface_to_usbdev(interface);

The USB device structure contains information about the connected peripheral.

Examples of device information include:

  • Vendor ID.
  • Product ID.
  • Device descriptor.
  • Configuration information.
  • USB speed and device state.

Reading VID and PID

udev->descriptor.idVendor
udev->descriptor.idProduct

These descriptor fields use little-endian kernel types. For general numeric handling, use the appropriate endianness conversion helpers when necessary.

5. Inspecting Interface Information

The probe callback can inspect the current interface and its alternate setting. 

struct usb_host_interface *alt;

alt = interface->cur_altsetting;

The current alternate setting contains the interface descriptor and endpoint descriptions.

Important Interface Fields

alt->desc.bInterfaceNumber
alt->desc.bInterfaceClass
alt->desc.bInterfaceSubClass
alt->desc.bInterfaceProtocol
alt->desc.bNumEndpoints

These fields help the driver determine whether the interface provides the functionality it expects.

6. Endpoint Discovery

A USB driver must identify the endpoints needed for communication.

The current alternate setting provides the endpoint descriptors.

Endpoint Information

  • Endpoint address.
  • Endpoint direction.
  • Transfer type.
  • Maximum packet size.
  • Polling interval, where applicable.

Endpoint Helper Macros

usb_endpoint_is_bulk_in(epd)
usb_endpoint_is_bulk_out(epd)

usb_endpoint_is_int_in(epd)
usb_endpoint_is_int_out(epd)

usb_endpoint_is_isoc_in(epd)
usb_endpoint_is_isoc_out(epd)

These helpers test endpoint descriptors for the corresponding transfer type and direction.

7. Finding a Bulk IN Endpoint

A driver can search the current alternate setting for a bulk IN endpoint. 

struct usb_host_interface *alt;
struct usb_endpoint_descriptor *epd;
int i;

alt = interface->cur_altsetting;

for (i = 0; i < alt->desc.bNumEndpoints; i++) {
    epd = &alt->endpoint[i].desc;

    if (usb_endpoint_is_bulk_in(epd)) {
        dev_info(&interface->dev,
                 "Bulk IN endpoint found: 0x%02X\n",
                 epd->bEndpointAddress);
    }
}

The loop examines each endpoint descriptor belonging to the current alternate setting.

Endpoint discovery should verify that the required endpoints exist before the driver starts communication. A driver must not assume that every USB interface provides bulk IN and bulk OUT endpoints.

8. Driver-Private Data

A USB driver often requires private data to maintain its own device-specific state.

For example, private data may contain:

  • USB device pointer.
  • USB interface pointer.
  • Endpoint addresses.
  • URB pointers.
  • Transfer buffers.
  • Buffer lengths.
  • Synchronization objects.
  • Device connection state.

Example Private Structure

struct my_usb_data {
    struct usb_device *udev;
    struct usb_interface *interface;

    unsigned char bulk_in_endpoint;
    unsigned char bulk_out_endpoint;

    unsigned char *bulk_in_buffer;
    size_t bulk_in_size;

    struct urb *bulk_in_urb;
};

The exact members depend on the device and transfer requirements.

9. Storing and Retrieving Interface Data

Linux provides functions to associate private data with a USB interface.

Store Private Data

usb_set_intfdata(interface, data);

Retrieve Private Data

data = usb_get_intfdata(interface);

The disconnect callback can retrieve the same private data that was stored during probe.

Example: If probe allocates a private structure and stores it using usb_set_intfdata(), disconnect can retrieve it using usb_get_intfdata() and release its resources.

10. Allocating a USB URB

A USB Request Block represents a transfer request. Asynchronous USB drivers commonly allocate URBs during probe or when they are needed.

Allocation Function

usb_alloc_urb()

Example

data->bulk_in_urb = usb_alloc_urb(0, GFP_KERNEL);

if (!data->bulk_in_urb) {
    return -ENOMEM;
}

For a bulk URB, the isochronous packet count is zero. For isochronous transfers, the appropriate packet count must be supplied.

Freeing the URB

usb_free_urb(data->bulk_in_urb);

URB references must be managed correctly. A submitted URB must be stopped or completed before the driver releases resources that its completion handler uses.

11. Allocating a USB Transfer Buffer

The driver needs a memory buffer for USB data transfers.

Linux provides USB-aware buffer allocation helpers.

Allocation

usb_alloc_coherent()

Example

data->bulk_in_buffer =
    usb_alloc_coherent(
        data->udev,
        data->bulk_in_size,
        GFP_KERNEL,
        &data->dma_handle
    );

if (!data->bulk_in_buffer) {
    return -ENOMEM;
}

Freeing the Buffer

usb_free_coherent(
    data->udev,
    data->bulk_in_size,
    data->bulk_in_buffer,
    data->dma_handle
);

The matching allocation and release functions must be used with the same device, size, buffer and DMA handle.

For simple drivers, ordinary kernel memory may also be used for transfer buffers when the USB API and DMA requirements permit it. Coherent allocation is not mandatory for every URB.

12. USB Disconnect Function

The disconnect callback is called when the USB interface is disconnected or the driver is unbound.

Function Prototype

static void my_usb_disconnect(
    struct usb_interface *interface
);

Unlike probe, disconnect returns no value.

Its primary responsibility is to stop operations and release resources associated with the interface.

13. Responsibilities of the Disconnect Function

A safe disconnect callback normally performs the following operations:

  1. Prevent new operations from starting.
  2. Retrieve the driver's private data.
  3. Clear or invalidate the interface's private-data pointer.
  4. Stop outstanding URBs.
  5. Ensure completion callbacks cannot access freed memory.
  6. Free URBs.
  7. Free transfer buffers.
  8. Release private memory and other resources.
Disconnect handling is critical because a USB device may disappear while a transfer is active. Resource cleanup must be synchronized with asynchronous callbacks.

14. Cancelling Outstanding URBs

A submitted URB may still be active when a device disconnects.

Linux provides functions to stop USB transfers.

Function Purpose
usb_kill_urb() Stops an active URB synchronously and waits for completion handling to finish.
usb_unlink_urb() Requests asynchronous cancellation of an active URB.

For disconnect cleanup, usb_kill_urb() is often useful because it provides synchronization before dependent memory is released.

An URB that has not been submitted does not need to be killed.

15. Probe and Disconnect Lifecycle

USB Interface Matched | v probe() | v Allocate Private Data | v Inspect Endpoints | v Allocate Buffers/URBs | v Store Interface Data | v Driver Operational | v Device Removed / Unbound | v disconnect() | v Prevent New Operations | v Stop Outstanding URBs | v Release Transfer Buffers | v Free Private Data

16. Complete USB Probe and Disconnect Example

The following example demonstrates endpoint discovery, private-data allocation and resource cleanup. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/usb.h>
#include <linux/slab.h>

#define MY_VENDOR_ID   0x1234
#define MY_PRODUCT_ID  0x5678

struct my_usb_data {
    struct usb_device *udev;

    unsigned char bulk_in_endpoint;
    unsigned char bulk_out_endpoint;

    size_t bulk_in_size;
    unsigned char *bulk_in_buffer;
    struct urb *bulk_in_urb;
};

static int my_usb_probe(
    struct usb_interface *interface,
    const struct usb_device_id *id)
{
    struct usb_device *udev;
    struct usb_host_interface *alt;
    struct usb_endpoint_descriptor *epd;
    struct my_usb_data *data;
    int i;

    udev = interface_to_usbdev(interface);
    alt = interface->cur_altsetting;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->udev = usb_get_dev(udev);

    for (i = 0; i < alt->desc.bNumEndpoints; i++) {

        epd = &alt->endpoint[i].desc;

        if (usb_endpoint_is_bulk_in(epd)) {
            data->bulk_in_endpoint =
                epd->bEndpointAddress;

            data->bulk_in_size =
                usb_endpoint_maxp(epd);
        }

        if (usb_endpoint_is_bulk_out(epd)) {
            data->bulk_out_endpoint =
                epd->bEndpointAddress;
        }
    }

    if (!data->bulk_in_endpoint ||
        !data->bulk_out_endpoint) {
        dev_err(&interface->dev,
                "Required bulk endpoints not found\n");

        usb_put_dev(data->udev);
        kfree(data);
        return -ENODEV;
    }

    data->bulk_in_buffer =
        kmalloc(data->bulk_in_size, GFP_KERNEL);

    if (!data->bulk_in_buffer) {
        usb_put_dev(data->udev);
        kfree(data);
        return -ENOMEM;
    }

    data->bulk_in_urb = usb_alloc_urb(0, GFP_KERNEL);

    if (!data->bulk_in_urb) {
        kfree(data->bulk_in_buffer);
        usb_put_dev(data->udev);
        kfree(data);
        return -ENOMEM;
    }

    usb_set_intfdata(interface, data);

    dev_info(&interface->dev,
             "USB interface initialized successfully\n");

    return 0;
}

static void my_usb_disconnect(
    struct usb_interface *interface)
{
    struct my_usb_data *data;

    data = usb_get_intfdata(interface);

    usb_set_intfdata(interface, NULL);

    if (!data)
        return;

    if (data->bulk_in_urb) {
        usb_kill_urb(data->bulk_in_urb);
        usb_free_urb(data->bulk_in_urb);
    }

    kfree(data->bulk_in_buffer);

    usb_put_dev(data->udev);

    kfree(data);

    dev_info(&interface->dev,
             "USB interface disconnected\n");
}

static const struct usb_device_id my_usb_id_table[] = {
    { USB_DEVICE(MY_VENDOR_ID, MY_PRODUCT_ID) },
    { }
};

MODULE_DEVICE_TABLE(usb, my_usb_id_table);

static struct usb_driver my_usb_driver = {
    .name       = "my_usb_lifecycle_driver",
    .probe      = my_usb_probe,
    .disconnect = my_usb_disconnect,
    .id_table   = my_usb_id_table,
};

module_usb_driver(my_usb_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("USB Probe and Disconnect Example");

Important Explanation

  • kzalloc() allocates and zero-initializes private data.
  • usb_get_dev() obtains a reference to the USB device.
  • The endpoint loop searches the current alternate setting.
  • kmalloc() allocates a basic transfer buffer.
  • usb_alloc_urb() allocates a bulk URB.
  • usb_set_intfdata() associates private data with the interface.
  • usb_kill_urb() synchronously stops an active URB.
  • usb_free_urb() releases the URB reference.
  • usb_put_dev() releases the USB device reference.
  • kfree() releases allocated kernel memory.
This example allocates an URB but does not submit it. It demonstrates lifecycle and resource management, not actual USB data communication. A production driver must also implement transfer submission, completion handling, synchronization and suitable error recovery.

17. Error Handling in Probe

Probe must release all resources allocated before an initialization failure.

For example, if private data is allocated successfully but URB allocation fails, the driver must release the private data and any other previously allocated resources.

Common Error Codes

Error Code Meaning
-ENOMEM Insufficient memory.
-ENODEV Required device or endpoint is unavailable.
-EINVAL Invalid argument or configuration.
-EIO Input/output error.

Recommended Practice

  • Check every allocation result.
  • Validate required endpoints.
  • Release references on failure.
  • Do not store invalid private data.
  • Use structured cleanup paths for complex drivers.

18. Synchronization and Disconnect Safety

USB transfers are often asynchronous. A completion callback may run while the driver is handling device removal.

The driver must prevent race conditions between:

  • Disconnect and transfer completion.
  • Disconnect and new transfer submission.
  • Disconnect and user-space operations.
  • Resource cleanup and asynchronous callbacks.

Common techniques include:

  • State flags indicating device disconnection.
  • Mutexes for process-context operations.
  • Spinlocks for suitable shared state.
  • Reference counting.
  • Synchronous URB cancellation.
Do not hold a spinlock while calling a function that may sleep. Follow the locking requirements of each USB API.

19. Testing USB Probe and Disconnect

Objective

Verify that the probe and disconnect callbacks execute when a supported USB device is connected and removed.

Commands

# Compile module
make

# Load driver
sudo insmod my_usb_driver.ko

# Check connected devices
lsusb

# Monitor kernel messages
sudo dmesg -w

# Remove driver
sudo rmmod my_usb_lifecycle_driver

Testing Procedure

  1. Build the driver using matching kernel headers.
  2. Load the module.
  3. Connect a device with the matching VID/PID.
  4. Observe the probe message.
  5. Disconnect the USB device.
  6. Observe the disconnect message.
  7. Reload the module if necessary and repeat.

Expected Result

The driver should initialize the matching interface and release its resources when the device is removed or the driver is unbound.

The example module name in the Makefile determines the generated module filename. Use the correct module name when running insmod and rmmod.

20. Important Points to Remember

  • Probe is called when a matching interface is bound.
  • Disconnect is called when the interface is removed or unbound.
  • Probe returns an integer status.
  • Disconnect returns void.
  • interface_to_usbdev() obtains the associated USB device.
  • cur_altsetting provides the current alternate setting.
  • Endpoint descriptors identify available communication endpoints.
  • usb_set_intfdata() stores private interface data.
  • usb_get_intfdata() retrieves private interface data.
  • URBs represent USB transfer requests.
  • Outstanding transfers must be stopped safely before freeing dependent memory.
  • Every successful allocation must have a corresponding cleanup path.

22. Lesson Summary

The USB probe function initializes a matching interface, examines its endpoints and allocates the resources required by the driver.

The disconnect function stops active operations and releases the resources allocated during initialization.

Correct handling of URBs, transfer buffers, device references and private data is essential for reliable USB driver development.

These lifecycle callbacks form the foundation of a complete USB device driver.
