2. Introduction to Top Half and Bottom Half

When a hardware device generates an interrupt, the Linux kernel must respond quickly. However, some interrupt-related tasks may require considerable processing time.

Performing all operations inside a hard interrupt handler can increase interrupt latency and delay the handling of other interrupts.

To address this problem, interrupt processing is commonly divided into two conceptual parts:

  • Top half: Immediate interrupt handling.
  • Bottom half: Deferred processing performed later.
Hardware Interrupt
↓
Top Half: Immediate Processing
↓
Schedule Deferred Work
↓
Bottom Half: Deferred Processing

The top half performs the time-critical work, while the bottom half performs the remaining processing outside the immediate hard interrupt handler.

3. What Is the Top Half?

The top half is the immediate interrupt-handling portion of the driver. In a conventional Linux hard IRQ design, it is implemented by the registered interrupt handler.

The top half executes in hard interrupt context and must complete quickly.

Responsibilities of the top half

  • Identify whether the interrupt belongs to the device.
  • Read essential interrupt status information.
  • Acknowledge or clear the interrupt as required by the hardware.
  • Capture time-critical information.
  • Schedule deferred processing when necessary.
  • Return an appropriate IRQ result.

Example top-half handler

static irqreturn_t my_interrupt_handler(int irq,
                                        void *dev_id)
{
    struct my_device_data *data = dev_id;

    /* Check whether the device generated the interrupt. */
    if (!device_has_interrupt(data))
        return IRQ_NONE;

    /* Acknowledge the device interrupt. */
    acknowledge_device_interrupt(data);

    /* Schedule deferred processing. */
    schedule_work(&data->work);

    return IRQ_HANDLED;
}

This is a conceptual example. The device-specific functions and work structure must be defined and initialized by the actual driver.

The top half must not perform sleeping operations. It should avoid lengthy calculations, blocking operations and unnecessary processing.

4. What Is the Bottom Half?

The bottom half is the deferred part of interrupt processing. It performs work that does not need to be completed immediately inside the hard IRQ handler.

The bottom half is scheduled by the top half or another suitable kernel path.

Responsibilities of the bottom half

  • Process data collected by the top half.
  • Perform longer calculations.
  • Update software data structures.
  • Process received data.
  • Notify other parts of the driver.
  • Perform operations that are inappropriate in hard IRQ context.

The execution context of the bottom half depends on the mechanism used. A workqueue runs in process context, whereas softirqs and tasklets run in atomic context.

Bottom half is a conceptual term, not a single Linux API. Linux provides several mechanisms for deferred processing, and they have different execution-context rules.

5. Why Is Interrupt Processing Divided?

A hardware interrupt may arrive while the CPU is executing another task. The kernel must respond without keeping the system occupied in interrupt context for an unnecessarily long time.

Problems with lengthy interrupt handlers

  • Increased interrupt latency.
  • Delayed processing of other interrupts.
  • Reduced system responsiveness.
  • Long periods spent in atomic context.
  • Difficulty managing complex driver operations.

Benefits of deferred processing

  • Shorter hard IRQ execution time.
  • Better interrupt responsiveness.
  • Separation of time-critical and non-time-critical tasks.
  • Ability to use sleepable operations through workqueues.
  • Improved organization of driver code.

6. Top Half vs Bottom Half

Typical context Hard IRQ context Depends on mechanism
Sleeping Not allowed Only permitted in sleepable mechanisms such as workqueues
Workload Small and time-critical Potentially longer processing

7. Linux Bottom-Half Mechanisms

Linux provides multiple mechanisms for deferred interrupt processing. The main mechanisms include:

  1. Softirqs
  2. Tasklets (legacy mechanism)
  3. Workqueues
  4. Threaded interrupt handlers

Overview

Mechanism Execution Context Can Sleep?
Softirq Softirq context No
Tasklet Softirq-based atomic context No
Workqueue Worker-thread process context Yes, when otherwise permitted
Threaded IRQ Kernel thread context Yes, when otherwise permitted
Tasklets are a legacy mechanism. New driver designs should generally prefer workqueues or threaded IRQs where their execution semantics are appropriate.

8. Softirqs

A softirq is a statically defined deferred-processing mechanism used by the Linux kernel for high-priority, non-sleeping work.

Softirqs execute in softirq context and cannot sleep. They are used by important kernel subsystems, including networking and timers.

Characteristics

  • Designed for deferred processing.
  • Runs in atomic context.
  • Cannot use blocking operations.
  • Different softirq instances can execute concurrently on different CPUs.
  • Requires appropriate synchronization for shared data.

Examples of kernel softirq activities

  • Network receive processing.
  • Network transmit completion processing.
  • Timer-related processing.
  • Some block I/O completion processing.
Softirqs are generally a kernel-subsystem mechanism. Ordinary device drivers should not casually create their own softirq types. Prefer established driver-facing mechanisms such as workqueues or threaded IRQs.

9. Tasklets

Tasklets are a deferred execution mechanism built on top of softirqs. They were historically used by drivers to perform work after the immediate interrupt handler completed.

Characteristics

  • Execute in softirq-based atomic context.
  • Cannot sleep.
  • Provide a convenient deferred-processing abstraction.
  • Different tasklets can execute concurrently, but a particular tasklet instance is serialized against itself.

Tasklets are now considered a legacy mechanism for new driver development. Modern code should generally consider workqueues or threaded IRQs instead.

Older tutorials may demonstrate tasklet_setup(), tasklet_schedule() and tasklet_kill(). Understand these APIs when maintaining older drivers, but do not assume they are the preferred choice for new code.

10. Workqueues

A workqueue allows a driver to defer work to a kernel worker thread. Workqueue callbacks execute in process context.

Because they run in process context, workqueue functions can sleep when the surrounding locking and API rules allow it.

Important characteristics

  • Execute through kernel worker threads.
  • Run in process context.
  • Can perform sleepable operations.
  • Suitable for longer deferred tasks.
  • Can be scheduled from an interrupt handler.

Workqueue example

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/workqueue.h>

static struct work_struct my_work;

static void my_work_handler(struct work_struct *work)
{
    pr_info("Deferred work executing\n");

    /* Sleepable operations may be used
       when otherwise permitted. */
}

static irqreturn_t my_interrupt_handler(int irq,
                                        void *dev_id)
{
    pr_info("Top half executed\n");

    schedule_work(&my_work);

    return IRQ_HANDLED;
}

static int __init my_init(void)
{
    INIT_WORK(&my_work, my_work_handler);

    pr_info("Work initialized\n");

    return 0;
}

static void __exit my_exit(void)
{
    cancel_work_sync(&my_work);

    pr_info("Work cancelled or completed\n");
}

module_init(my_init);
module_exit(my_exit);

MODULE_LICENSE("GPL");
This is a conceptual workqueue demonstration, not a complete interrupt driver. A real driver must register its IRQ, initialize device state, protect shared data and ensure that no handler can schedule new work during teardown. The IRQ should be unregistered and synchronized before the work structure and its containing data are destroyed.

Important functions

Function Purpose
INIT_WORK() Initializes a work structure.
schedule_work() Schedules work on the system workqueue.
queue_work() Queues work on a specified workqueue.
flush_work() Waits for a particular work item to finish its pending execution.
cancel_work_sync() Cancels pending work and waits for executing work to finish.

11. Threaded Interrupt Handlers

Linux supports threaded interrupt handling through request_threaded_irq().

A threaded interrupt design separates a short primary handler from a threaded handler.

  • The primary handler runs in hard IRQ context.
  • The threaded handler runs in a kernel thread.
  • The threaded handler can perform sleepable operations.
  • The primary handler commonly verifies and acknowledges the interrupt and returns IRQ_WAKE_THREAD.

Conceptual example

static irqreturn_t my_primary_handler(int irq,
                                      void *dev_id)
{
    /*
     * Perform minimal hard IRQ work.
     * Verify the interrupt source.
     */

    return IRQ_WAKE_THREAD;
}

static irqreturn_t my_thread_handler(int irq,
                                     void *dev_id)
{
    /*
     * Perform deferred processing
     * in threaded context.
     */

    pr_info("Threaded handler executing\n");

    return IRQ_HANDLED;
}

The handler pair can be registered using request_threaded_irq(), with the primary and threaded handler functions supplied separately.

Threaded IRQs are especially useful when interrupt-related processing needs to sleep, for example when accessing a peripheral through a sleepable bus operation.

13. Choosing the Correct Bottom-Half Mechanism

Requirement Possible Mechanism
Short deferred processing that cannot sleep Softirq-based mechanism where appropriate
Maintaining an older tasklet-based driver Tasklet
Deferred processing that may sleep Workqueue
Interrupt handling that needs a dedicated thread Threaded IRQ
High-volume network packet processing NAPI and networking subsystem mechanisms

The correct mechanism depends on latency requirements, execution-context requirements, concurrency, ordering and the type of work being performed.

14. Common Mistakes

  1. Performing lengthy work in the top half: this increases interrupt latency.
  2. Sleeping inside a hard IRQ handler: hard IRQ context does not permit blocking operations.
  3. Assuming every bottom half can sleep: softirqs and tasklets execute in atomic context.
  4. Failing to synchronize shared data: top-half and deferred code may access the same data concurrently.
  5. Freeing work data too early: pending or executing work may still access its containing structure.
  6. Ignoring teardown ordering: stop new interrupt activity, unregister and synchronize the IRQ, and then cancel or flush deferred work as appropriate before freeing associated data.
  7. Using legacy tasklets in new designs without reason: consider workqueues or threaded IRQs where suitable.

15. Lesson Summary

  • Top half performs immediate interrupt handling.
  • Bottom half performs deferred interrupt processing.
  • The top half normally executes in hard IRQ context.
  • Bottom-half execution context depends on the mechanism.
  • Softirqs and tasklets execute in atomic context.
  • Workqueues execute in process context.
  • Threaded IRQ handlers execute in kernel-thread context.
  • Deferred processing reduces the workload of hard IRQ handlers.
  • Correct synchronization and teardown are essential.
