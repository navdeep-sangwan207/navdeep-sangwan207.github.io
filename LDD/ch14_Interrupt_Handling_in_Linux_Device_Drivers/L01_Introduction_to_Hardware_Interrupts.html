2. What Is an Interrupt?

An interrupt is an event that causes the processor to temporarily suspend its current execution flow and transfer control to a predefined interrupt-handling mechanism.

The processor responds to the event by saving the necessary execution state and transferring control to an appropriate handler or exception entry point.

After the interrupt has been handled, execution can resume according to the processor architecture and operating-system rules.

Simple Example

Suppose a keyboard is connected to a computer. When a user presses a key, the keyboard controller generates an interrupt request.

The processor receives the interrupt and Linux arranges for the keyboard driver's interrupt-handling code to process the event.

User Presses a Keyboard Key
↓
Keyboard Controller Generates an Interrupt Request
↓
Interrupt Controller Routes the Request
↓
Processor Accepts the Interrupt
↓
Linux Executes the Registered Handler
↓
Processor Resumes Appropriate Execution

3. Why Are Interrupts Required?

Hardware devices operate independently of the CPU. A device may generate data or complete an operation at a time that is not known in advance to the processor.

Examples include:

  • A keyboard receiving a key press.
  • A network interface receiving a packet.
  • A timer reaching its configured count.
  • A UART receiving a character.
  • A storage controller completing a data transfer.
  • A GPIO controller detecting an external signal transition.

Without interrupts, the processor may need to repeatedly check device status to discover whether an event has occurred.

Interrupts provide an event-driven mechanism through which hardware can request processor attention.

Advantages of Interrupts

  1. Reduce the need for continuous status checking.
  2. Allow the CPU to perform other work while a device is idle.
  3. Provide a mechanism for responding to asynchronous hardware events.
  4. Support efficient handling of device events.
  5. Help coordinate CPU and peripheral operations.
Interrupts do not eliminate all CPU overhead. Interrupt entry, handler execution, synchronization and deferred processing also consume processor time.

4. Interrupts vs Polling

Polling and interrupts are two different techniques used to detect hardware events.

Polling

In polling, the CPU repeatedly checks a device status register to determine whether an event has occurred.

while (1)
{
    if (device_status_is_ready())
    {
        process_device_event();
    }
}

This is a conceptual example. Actual device drivers use hardware-specific register access and appropriate synchronization.

Interrupt-Based Approach

In an interrupt-based design, the device signals the processor when an event requires attention.

Device generates interrupt
        |
        v
Processor receives interrupt
        |
        v
Registered handler executes
        |
        v
Device event is processed

Comparison

Feature Polling Interrupts
Event detection CPU repeatedly checks device status. Device or interrupt controller signals an event.
CPU involvement CPU performs repeated checks. CPU responds when an interrupt is accepted.
Idle behavior Polling may consume CPU time. CPU can perform other work or enter an idle state.
Implementation Requires a checking loop or periodic check. Requires interrupt configuration and a handler.
Typical use Simple devices, short checks or specific high-performance designs. Asynchronous events and many peripheral drivers.
Polling is not always inefficient. It can be appropriate when event frequency is very high, latency requirements are strict, or hardware and system design favor polling.

6. Common Sources of Hardware Interrupts

Hardware interrupts can originate from many different peripheral devices and system components.

Hardware Source Example Event
Keyboard A key is pressed or released.
Mouse Movement or button activity is reported.
UART Data is received or transmission completes.
Timer A timer reaches a programmed event.
Network interface A packet is received or transmission status changes.
Storage controller A read or write operation completes.
GPIO controller An input pin detects a configured edge or level.
USB controller A USB transfer or device event occurs.
Power-management hardware A power-related event is detected.

7. Interrupt Request (IRQ)

An Interrupt Request (IRQ) is a request for processor attention generated by a hardware source or represented through an interrupt-controller mechanism.

Linux uses IRQ numbers and interrupt descriptors to manage interrupt handling.

IRQ Number

An IRQ number identifies an interrupt line or logical interrupt in the Linux interrupt subsystem.

For example, a driver may request an IRQ using:

request_irq(
    irq_number,
    interrupt_handler,
    IRQF_SHARED,
    "my_device",
    device_data
);

This function will be studied in detail in Lesson 4.

Linux IRQ numbers are not necessarily identical to physical interrupt-controller input numbers. Firmware descriptions, interrupt domains and controller mappings may translate hardware interrupt identifiers into Linux IRQ numbers.

8. Types of Hardware Interrupts

Interrupts can be classified according to how the interrupt signal is generated and handled.

8.1 Maskable Interrupt

A maskable interrupt is an interrupt that can be disabled or masked by the processor or interrupt controller, according to the architecture and controller design.

Most ordinary peripheral interrupts are maskable.

8.2 Non-Maskable Interrupt (NMI)

A Non-Maskable Interrupt is a high-priority interrupt mechanism that is not controlled by ordinary interrupt masking in the same way as normal maskable interrupts.

It is commonly used for critical system events such as certain hardware errors or platform-specific diagnostic events.

8.3 Edge-Triggered Interrupt

An edge-triggered interrupt is generated when a signal changes state.

Common edge definitions include:

  • Rising edge: LOW to HIGH transition.
  • Falling edge: HIGH to LOW transition.
LOW → HIGH = Rising Edge
↓
HIGH → LOW = Falling Edge

8.4 Level-Triggered Interrupt

A level-triggered interrupt remains asserted while the configured active signal level is present.

For example, an interrupt may remain active while a device's interrupt-status condition is asserted.

Edge vs Level Triggering

Feature Edge-Triggered Level-Triggered
Activation Signal transition. Active signal level.
Example Rising edge of GPIO signal. Active-low interrupt signal.
Handling consideration Events must be captured without missing transitions. Source generally needs to be serviced or deasserted.

The trigger type is determined by the hardware and interrupt-controller configuration. It is not freely interchangeable for every device.

9. Hardware Interrupts, Software Interrupts and Exceptions

These terms describe different event mechanisms, although exact terminology varies between processor architectures.

Type Origin Example
Hardware interrupt External hardware or peripheral event. UART receives data.
Software interrupt Software instruction or architecture-defined mechanism. Software-triggered interrupt or legacy system-call mechanism.
Exception Condition detected during instruction execution. Invalid instruction or page fault.

Important Distinction

A hardware interrupt is generally asynchronous to the instruction currently being executed.

An exception is generally associated with the execution of an instruction or an instruction-related condition.

System-call mechanisms are architecture-dependent. For example, modern x86-64 Linux commonly uses dedicated system-call instructions rather than the older software interrupt instruction.

10. Synchronous and Asynchronous Events

Synchronous Event

A synchronous event is directly related to the instruction stream being executed by the CPU.

Examples include:

  • Invalid instruction exception.
  • Arithmetic exception where supported.
  • Page fault.

Asynchronous Event

An asynchronous event occurs independently of the current instruction being executed.

Examples include:

  • Keyboard interrupt.
  • Timer interrupt.
  • Network interface interrupt.
  • UART receive interrupt.
Hardware interrupts are commonly asynchronous. Exceptions are generally synchronous, although some architectures use broader terminology for different processor events.

11. What Happens When an Interrupt Occurs?

The following sequence describes a simplified hardware-interrupt flow.

  1. A hardware device generates an interrupt request.
  2. The interrupt controller receives and evaluates the request.
  3. The request is routed to an appropriate CPU according to the system configuration.
  4. The CPU accepts the interrupt when permitted by its interrupt state and priority rules.
  5. The processor transfers execution to an architecture-specific interrupt entry point.
  6. The operating system identifies the interrupt and dispatches the appropriate handling mechanism.
  7. The registered device handler services the event.
  8. The interrupt-handling mechanism completes and execution resumes appropriately.

Detailed Flow

Device Event Occurs
↓
Interrupt Request Generated
↓
Interrupt Controller Processes Request
↓
CPU Accepts Interrupt
↓
Architecture-Specific Interrupt Entry
↓
Linux Interrupt Dispatch
↓
Device Driver Handler
↓
Interrupt Completion and Appropriate Return

This is a conceptual flow. Actual Linux interrupt handling may involve interrupt domains, generic IRQ flow handlers, threaded IRQs, deferred work and architecture-specific code.

12. Interrupt Handling in Linux Device Drivers

Linux provides an interrupt-management framework that allows device drivers to register handlers for their devices.

A driver generally performs the following operations:

  1. Obtain the appropriate IRQ number from the platform or device configuration.
  2. Prepare the device and its interrupt-related state.
  3. Register an interrupt handler.
  4. Handle the device event when the interrupt is delivered.
  5. Release the IRQ when the driver no longer needs it.

Important Linux Interrupt APIs

API Purpose
request_irq() Registers an interrupt handler.
free_irq() Releases a previously registered interrupt handler.
disable_irq() Disables a specified IRQ and waits for active handling to complete where required by the API.
enable_irq() Enables a previously disabled IRQ.
disable_irq_nosync() Disables an IRQ without waiting for an active handler to finish.
synchronize_irq() Waits for active handling of the specified IRQ to complete.

These APIs will be studied in subsequent lessons.

13. Example: UART Receive Interrupt

Consider a UART peripheral connected to a microcontroller or embedded processor.

When a character arrives through the serial communication line, the UART hardware may generate a receive interrupt.

Sequence

External Device Sends Serial Data
↓
UART Receives Character
↓
UART Sets Receive Status
↓
UART Generates Interrupt Request
↓
CPU Runs Interrupt Handling Path
↓
UART Driver Processes Received Data

Conceptual Pseudocode

interrupt_handler()
{
    if (uart_receive_event())
    {
        data = read_uart_data_register();

        store_received_data(data);
    }

    return;
}

This is architecture-independent pseudocode, not a compilable Linux driver. A real Linux UART driver uses the appropriate UART subsystem and hardware-specific register-access methods.

14. Interrupts in Embedded Systems and Linux

Interrupts are important in both bare-metal embedded programming and Linux device-driver development.

Feature Bare-Metal Embedded System Linux Device Driver
Interrupt setup Often configured using MCU registers and vendor libraries. Managed through Linux IRQ and device-driver frameworks.
Handler Typically an interrupt service routine defined by the MCU toolchain. Registered Linux interrupt handler or threaded handler.
Interrupt vector Defined by the microcontroller architecture. Managed through architecture and kernel interrupt infrastructure.
Concurrency Depends on MCU interrupt and execution model. Must account for kernel execution contexts, SMP and synchronization.
Deferred work Often implemented using flags or a main loop. Can use threaded IRQs, workqueues and other kernel mechanisms.

Connection to LPC2129

In an ARM7 LPC2129 embedded project, a peripheral such as UART0, Timer0 or an external interrupt pin can generate an interrupt.

The microcontroller's VIC (Vectored Interrupt Controller) manages interrupt requests and vector selection.

In Linux, interrupt management is handled through the kernel IRQ subsystem and the interrupt controller available on the target platform.

Your LPC2129 Keil simulator exercises and Linux device-driver exercises use different programming environments. LPC2129 VIC register programming is not the same as Linux request_irq() programming.

15. Advantages and Limitations of Interrupts

Advantages

  • Event-driven operation.
  • Reduced continuous polling overhead in suitable workloads.
  • Efficient peripheral event notification.
  • Support for asynchronous hardware communication.
  • Useful for timers, communication devices and external signals.

Limitations and Challenges

  • Interrupt entry and handling introduce overhead.
  • High interrupt rates can consume substantial CPU time.
  • Interrupt handlers have execution-context restrictions.
  • Shared device data requires synchronization.
  • Interrupt storms can degrade system performance.
  • Incorrect acknowledgement or clearing of a device interrupt condition may cause repeated interrupts.

16. Important Linux Interrupt Concepts

Concept Meaning
IRQ Interrupt request represented in the Linux interrupt subsystem.
ISR Interrupt Service Routine; commonly used to describe the interrupt handler.
IRQ descriptor Kernel data structure that represents and manages an IRQ.
Interrupt controller Hardware that manages and routes interrupt requests.
Interrupt context Execution context associated with interrupt handling.
Hard IRQ Immediate interrupt-handling path.
Threaded IRQ Interrupt handling performed in a kernel thread, allowing sleepable processing in the thread function.
Deferred processing Moving suitable work out of the immediate interrupt-handling path.

Hard IRQ handling, threaded IRQs and deferred processing are covered in later lessons of this chapter.

17. Lesson Summary

  • An interrupt is an event that causes the processor to transfer execution to an interrupt-handling path.
  • Hardware devices generate interrupt requests when events occur.
  • Interrupts reduce the need for continuous polling in suitable designs.
  • An interrupt controller manages interrupt requests and routing.
  • Linux provides an interrupt subsystem for registering and managing device handlers.
  • IRQ numbers identify logical interrupts within Linux.
  • Interrupts may be edge-triggered or level-triggered.
  • Maskable interrupts and NMIs have different masking characteristics.
  • Hardware interrupts are generally asynchronous to the current instruction stream.
  • Linux drivers use APIs such as request_irq() and free_irq().
  • Interrupt handlers must follow strict execution-context rules.

Useful Linux Commands

cat /proc/interrupts

# Display soft interrupt statistics
cat /proc/softirqs

# Display kernel version
uname -r

# Display recent kernel messages
sudo dmesg | tail -30

/proc/interrupts displays interrupt statistics maintained by the kernel, commonly including per-CPU counts and interrupt-controller information.

/proc/softirqs displays statistics for software-interrupt processing categories. Softirqs are a Linux deferred-processing mechanism, not hardware IRQ lines.
