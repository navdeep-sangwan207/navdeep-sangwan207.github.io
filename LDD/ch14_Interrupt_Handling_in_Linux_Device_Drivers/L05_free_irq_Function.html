2. Introduction to free_irq()

The Linux kernel provides the request_irq() function to register an interrupt handler. Once the driver has finished using the interrupt, it must unregister that handler.

The free_irq() function is used to remove an interrupt handler previously registered with request_irq() or a related IRQ registration API.

Typical situations where a driver releases an interrupt include:

  • When a kernel module is unloaded.
  • When a device is removed from the system.
  • During driver cleanup after an initialization failure.
  • When the driver no longer needs a particular interrupt.
Important: free_irq() unregisters the Linux interrupt handler. It does not automatically disable the interrupt source inside the physical device, release memory, or unmap hardware registers.

3. Header File

The declaration of free_irq() is available through:

#include <linux/interrupt.h>

This header provides interrupt-related APIs, flags, handler definitions and other interrupt management declarations.

4. Syntax of free_irq()

void free_irq(unsigned int irq, void *dev_id);

Parameters

Parameter Description
irq Linux IRQ number whose registered handler is to be removed.
dev_id Device-specific identifier used to identify the registered interrupt action.

The function returns void. It does not provide an error code to indicate success or failure.

Example

free_irq(irq_number, dev_id);

5. Understanding the dev_id Parameter

The dev_id parameter is particularly important when multiple devices share the same IRQ line.

When registering an interrupt handler, the driver supplies a device-specific identifier to request_irq(). The same identifier must be supplied to free_irq() when unregistering that handler.

Example: Registration

static int irq_number;
static struct my_device_data *device_data;

ret = request_irq(irq_number,
                  my_interrupt_handler,
                  IRQF_SHARED,
                  "my_device",
                  device_data);

Corresponding removal

free_irq(irq_number, device_data);

The pointer value must match the one used during registration. Passing a different pointer may fail to identify the intended interrupt action.

Can dev_id be NULL?

  • For a non-shared IRQ, NULL can be used if NULL was supplied during registration.
  • For a shared IRQ, the dev_id must be non-NULL and unique among the handlers sharing that IRQ.
  • The same dev_id value must be passed when calling free_irq().
Important: Do not assume that NULL is a valid identifier for every interrupt registration. For shared interrupts, a unique non-NULL identifier is required.

6. How free_irq() Works Internally

Linux maintains interrupt descriptors and registered interrupt actions. When a driver calls free_irq(), the kernel identifies the matching interrupt action and removes it from the IRQ's registered handler list.

For a shared IRQ, other registered handlers remain installed. Only the action matching the supplied device identifier is removed.

Driver calls free_irq()
↓
Linux identifies IRQ action
↓
Matching handler is unregistered
↓
Active handler execution is synchronized
↓
free_irq() returns

The synchronization step is important because a handler might already be executing when the driver requests its removal.

7. Synchronization with Active Interrupt Handlers

An interrupt handler can execute concurrently with normal driver code. For example, a driver may begin its cleanup function while the CPU is already executing the interrupt handler.

The kernel ensures that free_irq() waits for executing handlers associated with the IRQ to finish before returning. This prevents the handler from continuing to access driver data after the caller proceeds with freeing that data.

Example scenario

CPU: Interrupt handler running
↓
Driver: Calls free_irq()
↓
Kernel waits for active handler
↓
Handler finishes execution
↓
free_irq() returns

Why is this necessary?

Consider a handler that accesses a device data structure:

irqreturn_t my_interrupt_handler(int irq, void *dev_id)
{
    struct my_device_data *data = dev_id;

    /* Access device-specific data */
    data->interrupt_count++;

    return IRQ_HANDLED;
}

If the driver frees data while this handler is executing, the handler may access invalid memory. This is a use-after-free problem.

Calling free_irq() and allowing it to complete before freeing the associated data helps prevent this particular race.

Do not call free_irq() from interrupt context or from the interrupt handler itself. It is a synchronous operation that may wait for an active handler to finish.

8. Correct Cleanup Sequence

Before removing an interrupt handler, the driver should stop the device from generating new interrupts whenever possible. This normally involves masking or disabling the interrupt source inside the device.

A typical cleanup sequence is:

  1. Stop new interrupt generation at the device.
  2. Clear or acknowledge any pending device interrupt as required.
  3. Call free_irq() using the original IRQ and dev_id.
  4. Release hardware mappings and other resources.
  5. Free device-specific memory after it is no longer accessible.
Mask device interrupt source
↓
Handle pending device status
↓
free_irq(irq, dev_id)
↓
Release mappings and resources
↓
Free private data
This is a typical sequence, not a universal hardware recipe. The exact order of masking, acknowledging and releasing resources depends on the device and its interrupt controller.

9. Example: Using request_irq() and free_irq()

The following is a conceptual kernel module demonstrating interrupt registration and removal. IRQ number 42 is only a placeholder for explaining the API. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/interrupt.h>

#define MY_IRQ 42

static irqreturn_t my_interrupt_handler(int irq, void *dev_id)
{
    pr_info("Interrupt received: IRQ %d\n", irq);

    return IRQ_HANDLED;
}

static int __init my_driver_init(void)
{
    int ret;

    pr_info("Driver initialization started\n");

    ret = request_irq(MY_IRQ,
                      my_interrupt_handler,
                      0,
                      "my_interrupt_demo",
                      NULL);

    if (ret) {
        pr_err("Unable to register IRQ %d\n", MY_IRQ);
        return ret;
    }

    pr_info("Interrupt handler registered\n");

    return 0;
}

static void __exit my_driver_exit(void)
{
    pr_info("Driver cleanup started\n");

    free_irq(MY_IRQ, NULL);

    pr_info("Interrupt handler unregistered\n");
}

module_init(my_driver_init);
module_exit(my_driver_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Demonstration of free_irq() API");

Code Explanation

Code Purpose
request_irq() Registers the interrupt handler.
my_interrupt_handler() Handles the interrupt notification.
module_init() Specifies the module initialization function.
module_exit() Specifies the module cleanup function.
free_irq() Unregisters the handler during cleanup.
Hardware warning: Do not load this example expecting IRQ 42 to belong to your device. A real driver must obtain its IRQ from the appropriate device resource or subsystem and must manage the device's interrupt source. An arbitrary IRQ number is not a safe hardware configuration.

10. free_irq() with Shared Interrupts

A shared interrupt allows multiple devices to use the same IRQ line. Each device registers its own handler and supplies a unique non-NULL dev_id.

Example registration

request_irq(irq,
            device_a_handler,
            IRQF_SHARED,
            "device_a",
            &device_a);

request_irq(irq,
            device_b_handler,
            IRQF_SHARED,
            "device_b",
            &device_b);

Remove only Device A's handler

free_irq(irq, &device_a);

The handler belonging to Device B remains registered. The kernel uses the supplied device identifier to find the appropriate interrupt action.

Shared IRQ
↓
Device A Handler
Device B Handler
↓
free_irq(irq, &device_a)
↓
Device A removed; Device B remains

Before removing a shared interrupt handler, the driver must disable or mask its own device's interrupt source. It must not disable the shared IRQ line in a way that disrupts other devices.

11. Difference Between free_irq() and Related Functions

Function Purpose Waits for active handlers?
free_irq() Unregisters a matching interrupt handler. Yes, before returning.
disable_irq() Disables the specified IRQ. Yes.
disable_irq_nosync() Disables the specified IRQ without waiting for active handlers. No.
synchronize_irq() Waits for active handlers to complete without unregistering the handler or disabling the IRQ. Yes.

Important distinction

  • free_irq() removes a registered handler.
  • disable_irq() disables IRQ delivery for that IRQ.
  • disable_irq_nosync() does not wait for an active handler.
  • synchronize_irq() waits for ongoing handlers but leaves the registration in place.
Synchronous operations such as free_irq(), disable_irq() and synchronize_irq() can wait for interrupt handling to finish. Do not call them while holding a lock that the interrupt handler needs to acquire. Otherwise, a deadlock can occur.

12. Race Conditions and Common Mistakes

Mistake 1: Freeing memory before unregistering the handler

kfree(device_data);
free_irq(irq, device_data);

This is unsafe because an executing handler may still access the freed memory.

Correct approach: stop the device's interrupt source, unregister the handler and allow synchronization to complete, then release the data when no other users can access it.

Mistake 2: Passing a different dev_id

request_irq(irq, handler, IRQF_SHARED,
            "device", &device_a);

/* Incorrect identifier */
free_irq(irq, &device_b);

The identifier used for removal must match the identifier provided during registration.

Mistake 3: Forgetting to mask the device interrupt source

A device may continue asserting its interrupt output even after the Linux handler is unregistered. This can cause unwanted interrupt activity or affect other devices sharing the line.

Correct approach: use the device-specific interrupt mask and status registers as required before removing the handler.

Mistake 4: Calling free_irq() while holding a handler lock

If the active interrupt handler needs a lock currently held by the cleanup function, free_irq() may wait for the handler while the handler waits for the lock. This produces a deadlock.

Correct approach: design the cleanup locking sequence so that the handler can finish before synchronous IRQ removal waits for it.

Mistake 5: Calling free_irq() from interrupt context

free_irq() may sleep while waiting for active interrupt handlers. It must be called from an appropriate process-context cleanup path, not from a hard interrupt handler.

13. What free_irq() Does Not Do

Operation Automatically performed by free_irq()?
Unregister matching IRQ action Yes
Wait for active handlers to finish Yes
Free driver private memory No
Unmap device registers No
Release device I/O or memory resources No
Disable the interrupt source inside the device No
Remove other handlers sharing the IRQ No

The driver remains responsible for managing the complete lifecycle of its device resources.

14. Managed IRQ Registration: devm_request_irq()

Linux also provides the managed API devm_request_irq() for drivers using the device resource-management framework. 

ret = devm_request_irq(dev,
                       irq,
                       my_interrupt_handler,
                       0,
                       "my_device",
                       dev_id);

The managed resource is released automatically when the associated device is detached or its managed resources are released.

Do not manually call free_irq() for the same registration that is managed by devm_request_irq(). Choose the appropriate resource-management approach and follow its lifecycle rules.

15. Testing and Observing Interrupts in Ubuntu

The following commands help inspect interrupt activity and kernel messages on an Ubuntu system.

Command 1: View interrupt statistics

cat /proc/interrupts

Displays IRQ numbers, per-CPU interrupt counts and registered interrupt handler information.

Command 2: Monitor interrupt statistics

watch -n 1 cat /proc/interrupts

Refreshes the interrupt statistics every second.

Command 3: Inspect kernel messages

dmesg | tail -n 30

Displays the latest available messages from the kernel ring buffer, including driver messages.

Command 4: Inspect kernel messages through systemd

sudo journalctl -k -n 50

Displays recent kernel messages retained in the systemd journal.

Ubuntu running inside VirtualBox may not expose the physical interrupts of external GPIO, I2C or SPI devices. These commands are useful for observing the virtual machine's available interrupt activity, but they do not replace testing on the actual target hardware.

16. Practical Applications

  • Character drivers: release an interrupt handler when a device driver is removed.
  • UART drivers: unregister interrupt handling during serial-device cleanup.
  • Network drivers: release IRQ resources during device shutdown.
  • GPIO drivers: unregister GPIO-associated interrupt handling when the device is removed.
  • Embedded Linux: release interrupts associated with peripheral devices.

17. Lesson Summary

  • free_irq() unregisters a previously registered interrupt handler.
  • Its header file is <linux/interrupt.h>.
  • Its syntax is free_irq(unsigned int irq, void *dev_id).
  • The IRQ and dev_id must identify the registered interrupt action.
  • For shared IRQs, dev_id must be unique and non-NULL.
  • Only the matching handler is removed from a shared IRQ.
  • free_irq() waits for active handlers to finish before returning.
  • The device interrupt source should normally be masked before unregistering.
  • Private memory and hardware resources must be released separately.
  • free_irq() must not be called from hard interrupt context.
