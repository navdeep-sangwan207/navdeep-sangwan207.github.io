2. Introduction to Deferred Interrupt Processing

When a hardware device generates an interrupt, the Linux kernel invokes the registered interrupt handler.

The interrupt handler should perform only essential operations because it executes in hard interrupt context. Lengthy processing can increase interrupt latency and delay other system activities.

Linux therefore provides mechanisms to defer additional work. Two historically important mechanisms are:

  • Tasklets: Deferred execution based on softirqs.
  • Workqueues: Deferred execution using kernel worker threads.
Hardware Interrupt
↓
Hard IRQ Handler
↓
Schedule Deferred Processing
↓
Tasklet or Workqueue
↓
Deferred Work Execution

The choice between tasklets and workqueues depends primarily on whether the deferred function needs to sleep, along with the driver's latency, ordering and concurrency requirements.

3. What Is a Tasklet?

A tasklet is a Linux kernel mechanism used to defer processing from a hard interrupt handler.

Tasklets are implemented using the softirq mechanism and execute in softirq context.

Characteristics of tasklets

  • Used for deferred interrupt processing.
  • Execute in atomic context.
  • Cannot sleep.
  • Cannot use mutexes or blocking operations.
  • A particular tasklet instance is not executed concurrently with itself.
  • Different tasklet instances can execute concurrently on different CPUs.
Tasklets are a legacy mechanism. They are important for understanding older Linux drivers, but new driver development should generally consider workqueues or threaded IRQs where appropriate.

4. Tasklet Data Structure and APIs

Historically, tasklets were represented using the struct tasklet_struct data structure.

Important tasklet APIs

API Purpose
tasklet_setup() Initializes a tasklet with its callback.
tasklet_schedule() Schedules a tasklet for execution.
tasklet_hi_schedule() Schedules a tasklet on the high-priority tasklet path.
tasklet_disable() Disables execution of a tasklet and waits for an active execution to finish.
tasklet_enable() Re-enables a disabled tasklet.
tasklet_kill() Waits for the tasklet to finish and prevents it from remaining scheduled.

Exact availability and lifecycle details should be checked against the target kernel version. Tasklet APIs are being phased out of new driver designs.

5. Tasklet Callback Function

A tasklet callback is invoked when the scheduled tasklet executes.

Modern tasklet_setup() callback form

#include <linux/module.h>
#include <linux/interrupt.h>

static struct tasklet_struct my_tasklet;

static void my_tasklet_function(struct tasklet_struct *task)
{
    pr_info("Tasklet callback executed\n");

    /* Non-sleeping deferred processing */
}

static int __init my_init(void)
{
    tasklet_setup(&my_tasklet, my_tasklet_function);

    pr_info("Tasklet initialized\n");

    return 0;
}

static void __exit my_exit(void)
{
    tasklet_kill(&my_tasklet);

    pr_info("Tasklet cleanup completed\n");
}

module_init(my_init);
module_exit(my_exit);

MODULE_LICENSE("GPL");

This example demonstrates initialization and cleanup. It does not schedule the tasklet because no real hardware interrupt is registered.

Scheduling a tasklet

static irqreturn_t my_interrupt_handler(int irq,
                                        void *dev_id)
{
    /* Acknowledge and identify device interrupt here. */

    tasklet_schedule(&my_tasklet);

    return IRQ_HANDLED;
}

The tasklet callback executes later through the softirq mechanism, not directly inside the hard IRQ handler.

Do not call tasklet_schedule() after the tasklet has been destroyed. During driver removal, first prevent further interrupt scheduling, unregister and synchronize the IRQ, and then call tasklet_kill() before freeing the tasklet's containing data.

6. Tasklet Execution Flow

Hardware Interrupt
↓
Hard IRQ Handler
↓
tasklet_schedule()
↓
Tasklet Marked Pending
↓
Softirq Processing
↓
Tasklet Callback Executes

The tasklet callback executes in atomic context. It must not block or sleep.

7. What Is a Workqueue?

A workqueue is a Linux kernel mechanism that allows a driver to defer work to kernel worker threads.

Unlike tasklets, workqueue callbacks execute in process context. Therefore, they can perform sleepable operations when the surrounding execution path and locking rules permit.

Characteristics of workqueues

  • Deferred execution using kernel worker threads.
  • Callbacks execute in process context.
  • Can perform operations that may sleep.
  • Suitable for longer processing tasks.
  • Can be scheduled from a hard IRQ handler.
  • Support system-provided and driver-created workqueues.

Workqueues are widely used in modern Linux driver development.

8. Workqueue Data Structures

The main workqueue data structure used for ordinary work items is struct work_struct.

A work item represents a function that should execute later in a worker thread.

Important workqueue APIs

API Purpose
INIT_WORK() Initializes a work structure.
DECLARE_WORK() Declares and statically initializes a work item.
schedule_work() Schedules work on the system workqueue.
queue_work() Queues work on a specified workqueue.
alloc_workqueue() Creates a dedicated workqueue.
destroy_workqueue() Destroys a workqueue after its work is handled.
flush_work() Waits for a particular work item to finish its pending execution.
cancel_work_sync() Cancels pending work and waits for any executing instance to finish.

9. Workqueue Initialization

A work item must be initialized before it is scheduled. The INIT_WORK() macro associates a callback function with the work structure.

Basic initialization

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/workqueue.h>

static struct work_struct my_work;

static void my_work_function(struct work_struct *work)
{
    pr_info("Workqueue callback executed\n");
}

static int __init my_init(void)
{
    INIT_WORK(&my_work, my_work_function);

    pr_info("Work item initialized\n");

    return 0;
}

static void __exit my_exit(void)
{
    cancel_work_sync(&my_work);

    pr_info("Work item cleanup completed\n");
}

module_init(my_init);
module_exit(my_exit);

MODULE_LICENSE("GPL");

This example initializes a work item but does not queue it. A real driver would schedule it after an interrupt or another event.

10. Scheduling Work

After initialization, the driver can schedule the work item using schedule_work(). 

static void my_work_function(struct work_struct *work)
{
    pr_info("Deferred work is running\n");
}

static irqreturn_t my_interrupt_handler(int irq,
                                        void *dev_id)
{
    pr_info("Interrupt received\n");

    schedule_work(&my_work);

    return IRQ_HANDLED;
}

The interrupt handler schedules the work item and returns. The worker thread executes the callback later.

Return value of schedule_work()

  • Returns true when the work was successfully queued.
  • Returns false when the work was already pending and was not queued again.
Repeated scheduling of the same work item does not create an unlimited queue of separate executions. A work item represents pending work, not an individual event counter. If every event must be preserved, the driver needs a suitable event queue or counter protected by synchronization.

11. Creating a Dedicated Workqueue

Linux also allows drivers to create their own workqueues instead of using the system workqueue.

A dedicated workqueue can be useful when a driver needs specific execution properties or isolation from unrelated work items.

Important functions

my_wq = alloc_workqueue("my_driver_wq",
                        WQ_UNBOUND,
                        1);

if (!my_wq)
    return -ENOMEM;

queue_work(my_wq, &my_work);

/* During cleanup */
destroy_workqueue(my_wq);

The example shows the allocation and queueing pattern. The work item must be initialized before it is queued.

Important workqueue flags

Flag Meaning
WQ_UNBOUND Uses unbound worker-pool execution rather than binding work to a specific CPU.
WQ_MEM_RECLAIM Provides a rescue execution context for workqueues needed during memory reclaim.
WQ_FREEZABLE Allows the workqueue to participate in system freezing.
Workqueue flags and attributes affect scheduling behavior. They should be selected according to the driver's actual requirements, not added without understanding their effect.

12. Tasklets vs Workqueues

Feature Tasklet Workqueue
Execution mechanism Softirq-based Kernel worker threads
Execution context Atomic context Process context
Can sleep? No Yes, when permitted
Mutex support No Yes, when appropriate
Typical workload Short deferred operations Longer or sleepable operations
Scheduling tasklet_schedule() schedule_work()
Modern development Legacy mechanism Commonly preferred

13. Workqueue Cleanup and Synchronization

A driver must ensure that pending or executing work does not access memory after that memory has been released.

System workqueue cleanup

cancel_work_sync(&my_work);

This cancels pending work and waits for an executing callback to finish. It is useful during driver teardown.

Dedicated workqueue cleanup

destroy_workqueue(my_wq);

Destroying a workqueue waits for its queued work to be handled before the workqueue is destroyed.

Typical driver cleanup order

  1. Prevent the device from generating new interrupts.
  2. Mask or disable the device interrupt source as required.
  3. Call free_irq() to unregister and synchronize the IRQ handler.
  4. Cancel or flush deferred work as appropriate.
  5. Destroy a dedicated workqueue if one was created.
  6. Release device resources and free private data.
Cleanup order must prevent new work from being scheduled after cancellation or destruction. A handler must not be able to queue work using a work structure that has already been freed.

14. Choosing Tasklets or Workqueues

Use workqueues when:

  • The deferred function may sleep.
  • The driver needs mutex protection.
  • The processing is relatively long.
  • The driver needs to wait for a resource or event.
  • The driver requires a worker-thread execution model.

Understand tasklets when:

  • Studying older Linux drivers.
  • Maintaining existing tasklet-based code.
  • Understanding legacy softirq-based deferred processing.

Other alternatives

  • Threaded IRQ: Useful when the interrupt handling itself needs sleepable thread execution.
  • NAPI: Used by Linux networking drivers for efficient packet processing.
  • Softirq: Primarily used by kernel subsystems for atomic deferred processing.

15. Practical Linux Commands

The following commands can help inspect kernel messages and workqueue-related activity in an Ubuntu environment.

View kernel messages

sudo dmesg | tail -n 30

View workqueue-related kernel information

grep -i workqueue /proc/kallsyms

The availability and visibility of symbols depend on kernel configuration and permissions. This command is not a complete workqueue monitoring tool.

Check kernel version

uname -r

Knowing the running kernel version is important because kernel APIs and legacy tasklet interfaces can change.

Ubuntu running inside VirtualBox is suitable for learning workqueue concepts and testing simple kernel modules. Actual peripheral interrupt testing requires suitable hardware access or an appropriate emulator.

16. Common Mistakes

  1. Sleeping inside a tasklet: tasklets execute in atomic context.
  2. Using a mutex inside a tasklet: mutex acquisition may block.
  3. Scheduling an uninitialized work item: initialize it before queueing.
  4. Freeing work data too early: pending callbacks may still access it.
  5. Assuming every interrupt event creates a separate work execution: repeated queueing of the same pending work item may be coalesced.
  6. Destroying a workqueue while the IRQ can still queue work: prevent new scheduling before teardown.
  7. Using tasklets for every new driver: consider modern alternatives.

17. Lesson Summary

  • Tasklets and workqueues are deferred-processing mechanisms.
  • Tasklets use the softirq mechanism.
  • Tasklets execute in atomic context and cannot sleep.
  • Workqueues execute callbacks in worker-thread process context.
  • Workqueue callbacks can sleep when otherwise permitted.
  • tasklet_schedule() schedules a tasklet.
  • schedule_work() schedules work on the system workqueue.
  • alloc_workqueue() creates a dedicated workqueue.
  • cancel_work_sync() synchronizes cancellation of a work item.
  • Workqueue and interrupt cleanup must be carefully ordered.
