2. Introduction to Interrupt-Driven Character Drivers

A character device driver provides a file-based interface between a user-space application and a device or software interface in the kernel.

Some character devices generate events asynchronously. Examples include:

  • UART communication devices.
  • Buttons and switches.
  • GPIO event interfaces.
  • Sensor devices.
  • Hardware controllers that generate completion interrupts.

Instead of continuously polling the hardware, an interrupt-driven driver can respond when an event occurs.

Definition

An interrupt-driven character driver is a character-device driver that uses hardware interrupts to detect device events and makes the resulting information available to user-space applications through a device interface.

3. Polling vs Interrupt-Driven Operation

Polling approach

In polling, software repeatedly checks the device status to determine whether an event has occurred. 

while (1)
{
    if (device_has_data())
    {
        read_device_data();
    }
}

This is conceptual pseudocode. Actual hardware access must use the appropriate kernel subsystem and device APIs.

Interrupt-driven approach

The hardware notifies the processor when an event occurs. The driver responds by executing its interrupt handler.

Polling Interrupt-driven
Software repeatedly checks device status. Hardware signals an event.
Can waste CPU time when events are infrequent. Can reduce unnecessary status checking.
Simple for some devices and operations. Requires interrupt configuration and synchronization.
Detection latency depends on polling frequency. Response begins through the interrupt mechanism.

4. Interrupt-Driven Character Driver Architecture

An interrupt-driven character driver combines the character device interface with the Linux interrupt subsystem.

Hardware Device
↓
Hardware Interrupt
↓
Linux Interrupt Handler
↓
Driver Event Buffer
↓
Character Device Interface
↓
User-Space Application

The interrupt handler records or acknowledges the event. A deferred-processing mechanism can perform additional work. The character-device interface then provides a way for applications to retrieve the resulting data.

Main components

  1. Hardware device and interrupt source.
  2. Interrupt registration and handler.
  3. Driver-private data structure.
  4. Event buffer or data queue.
  5. Wait queue or another notification mechanism.
  6. Character-device file operations.
  7. User-space application.

5. Role of the Interrupt Handler

The interrupt handler executes when the registered interrupt is delivered to the driver.

Typical responsibilities

  • Identify the interrupt source.
  • Check device status when required.
  • Acknowledge or clear the interrupt at the device.
  • Retrieve urgent data when required by the hardware.
  • Store event information safely.
  • Notify a waiting process or schedule deferred work.
static irqreturn_t my_irq_handler(int irq,
                                  void *dev_id)
{
    struct my_device *dev = dev_id;

    /* Check and acknowledge the device event. */

    /* Record event information safely. */

    wake_up_interruptible(&dev->read_queue);

    return IRQ_HANDLED;
}

This is a structural example. A real handler must first establish that the interrupt belongs to the device and must follow its hardware-specific acknowledgement procedure.

Do not call copy_to_user(), copy_from_user(), or blocking functions from a hard IRQ handler. They are not appropriate for hard interrupt context.

6. Driver-Private Data Structure

A character driver commonly stores its state in a private data structure. 

#include <linux/module.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/interrupt.h>
#include <linux/wait.h>
#include <linux/spinlock.h>
#include <linux/mutex.h>

struct my_device
{
    struct cdev cdev;

    int irq;

    wait_queue_head_t read_queue;

    spinlock_t lock;
    struct mutex read_mutex;

    char event_buffer[128];
    size_t data_length;

    bool data_available;
    bool stopping;
};

Purpose of important members

Member Purpose
cdev Character-device registration object.
irq Interrupt number or identifier.
read_queue Wait queue used by readers.
lock Protects shared state accessed from interrupt and process contexts.
read_mutex Serializes sleepable read-side operations.
event_buffer Stores event data.
data_length Tracks the number of valid bytes.
data_available Indicates whether data is available.
stopping Indicates that the device is being removed.

This structure is illustrative. A production driver may need a ring buffer, multiple queues, reference counting, resource-management fields and additional state.

7. Wait Queues in Interrupt-Driven Drivers

A user-space process may call read() before the device has generated any data.

The driver can use a wait queue to put the process to sleep until data becomes available.

Wait queue initialization

init_waitqueue_head(&dev->read_queue);

Wake up waiting processes

wake_up_interruptible(&dev->read_queue);

The interrupt handler or deferred-processing callback can wake readers after recording new data.

Conceptual execution flow

User Application Calls read()
↓
Driver Checks Data Availability
↓
No Data: Process Waits
↓
Hardware Generates Interrupt
↓
Driver Stores Data
↓
Wake Waiting Process
↓
read() Returns Data

8. Synchronization Between IRQ and Read Operations

The interrupt handler and the read callback may access the same event buffer.

Without synchronization, a race condition can occur. For example, a reader might access the buffer while the interrupt handler is updating it.

Protecting shared data

unsigned long flags;

spin_lock_irqsave(&dev->lock, flags);

dev->data_available = true;

spin_unlock_irqrestore(&dev->lock, flags);

The IRQ-save spinlock variant protects the critical section against relevant local interrupt interleavings and provides mutual exclusion across CPUs.

Important rules

  • Use a spinlock for short shared-state operations involving hard IRQ context.
  • Do not hold a spinlock while copying data to user space.
  • Do not sleep while holding a spinlock.
  • Use a mutex for longer process-context operations where appropriate.
  • Use a consistent locking design across all callbacks.

9. Character Driver Read Operation

The read callback transfers data from the kernel buffer to the user-space application.

The following example illustrates a single-buffer design. It assumes the driver has serialized readers and uses the same spinlock to protect the buffer and its availability flag. 

#include <linux/uaccess.h>
#include <linux/errno.h>

static ssize_t my_read(struct file *file,
                       char __user *buf,
                       size_t count,
                       loff_t *ppos)
{
    struct my_device *dev = file->private_data;
    unsigned long flags;
    size_t len;
    char local_buffer[128];
    int ret;

    if (!count)
        return 0;

    if (mutex_lock_interruptible(&dev->read_mutex))
        return -ERESTARTSYS;

    ret = wait_event_interruptible(
        dev->read_queue,
        READ_ONCE(dev->data_available) ||
        READ_ONCE(dev->stopping)
    );

    if (ret) {
        mutex_unlock(&dev->read_mutex);
        return ret;
    }

    if (READ_ONCE(dev->stopping)) {
        mutex_unlock(&dev->read_mutex);
        return -ENODEV;
    }

    spin_lock_irqsave(&dev->lock, flags);

    len = min(count, dev->data_length);
    len = min(len, sizeof(local_buffer));

    memcpy(local_buffer, dev->event_buffer, len);

    dev->data_length = 0;
    dev->data_available = false;

    spin_unlock_irqrestore(&dev->lock, flags);

    if (copy_to_user(buf, local_buffer, len)) {
        /*
         * A production driver should preserve or restore
         * data if user copying fails.
         */
        mutex_unlock(&dev->read_mutex);
        return -EFAULT;
    }

    mutex_unlock(&dev->read_mutex);

    return len;
}
This is an instructional fragment, not a complete production-ready read implementation. A robust driver should define how data is retained after copy faults, how multiple events are buffered, and how partial reads and nonblocking access are handled.

10. Nonblocking Read Operations

A user application can open a device with O_NONBLOCK.

In nonblocking mode, the read callback should not wait indefinitely for data. If no data is available, it normally returns -EAGAIN.

Conceptual behavior

if (!data_available) {
    if (file->f_flags & O_NONBLOCK)
        return -EAGAIN;

    /* Otherwise wait for data using a wait queue. */
}

The driver must explicitly implement nonblocking behavior. The presence of O_NONBLOCK in the file flags does not automatically make a driver nonblocking.

11. File Operations Structure

The character driver exposes its operations through struct file_operations. 

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .release = my_release,
};

Responsibilities

Callback Purpose
open() Prepares the per-open file state.
read() Transfers event data to user space.
release() Releases per-open resources when the open-file description is finally released.

The open callback can store a pointer to the driver's private data in file->private_data. 

static int my_open(struct inode *inode,
                   struct file *file)
{
    struct my_device *dev;

    dev = container_of(inode->i_cdev,
                       struct my_device,
                       cdev);

    file->private_data = dev;

    return 0;
}

The example assumes that the containing device object remains alive for the entire lifetime of every open file using it. A production driver must manage that lifetime explicitly.

12. Registering the Character Device and IRQ

A driver needs to initialize all resources before making the interrupt handler active.

Typical initialization sequence

  1. Allocate and initialize private device data.
  2. Initialize locks and wait queues.
  3. Initialize work items if required.
  4. Allocate a device number.
  5. Initialize the cdev structure.
  6. Register the character device.
  7. Configure the hardware and interrupt source.
  8. Register the interrupt handler.
  9. Expose the device interface when it is ready.
alloc_chrdev_region(&dev_num, 0, 1, "my_device");

cdev_init(&dev->cdev, &my_fops);
dev->cdev.owner = THIS_MODULE;

ret = cdev_add(&dev->cdev, dev_num, 1);

if (ret) {
    unregister_chrdev_region(dev_num, 1);
    return ret;
}

/* Register IRQ only after all handler state is ready. */

ret = request_irq(dev->irq,
                  my_irq_handler,
                  0,
                  "my_device",
                  dev);

if (ret) {
    cdev_del(&dev->cdev);
    unregister_chrdev_region(dev_num, 1);
    return ret;
}
This is a registration fragment, not a complete initialization routine. A real driver must also handle allocation failures, hardware setup, device-node creation and every partially initialized resource.

13. Driver Cleanup and Resource Management

When the module is removed, the driver must prevent new interrupt events and ensure that no callback accesses released resources.

Typical cleanup sequence

  1. Mark the device as stopping.
  2. Prevent new hardware interrupt events.
  3. Wake any processes waiting for data or device shutdown.
  4. Unregister the IRQ using free_irq().
  5. Cancel or flush deferred work if the driver uses it.
  6. Remove the character-device registration.
  7. Release the device number and hardware resources.
  8. Free private memory only after all users are finished.
static void my_device_cleanup(struct my_device *dev)
{
    unsigned long flags;

    spin_lock_irqsave(&dev->lock, flags);
    dev->stopping = true;
    spin_unlock_irqrestore(&dev->lock, flags);

    wake_up_interruptible(&dev->read_queue);

    /* Prevent new hardware events before unregistering IRQ. */
    disable_device_interrupts();

    free_irq(dev->irq, dev);

    /* If work items exist, cancel them here. */
    /* cancel_work_sync(&dev->work); */

    cdev_del(&dev->cdev);

    /* Release device numbers and other resources. */
}
This cleanup fragment assumes that the device interrupt control operation is valid for the hardware. The function disable_device_interrupts() is illustrative, not a Linux kernel API. Existing open files also require explicit lifetime management; cdev_del() alone does not terminate their file operations.

↓

This architecture separates hardware event detection from user-space data access.

The interrupt handler handles urgent operations, while buffering and synchronization allow user-space processes to consume event data safely.

15. Practical Testing in Ubuntu VirtualBox

A simple software-only character driver can be developed and tested inside Ubuntu VirtualBox. However, actual hardware interrupt testing requires a suitable device, hardware passthrough or an appropriate emulator.

Check kernel version

uname -r

Install matching build dependencies

sudo apt update
sudo apt install build-essential linux-headers-$(uname -r)

Build a kernel module

make

Load a module

sudo insmod my_driver.ko

View kernel messages

sudo dmesg | tail -n 40

Remove a module

sudo rmmod my_driver
Do not register an arbitrary interrupt number as if it represented a real hardware device. Use an IRQ obtained from the correct device resource or subsystem.

16. Common Problems and Their Causes

Problem Possible Cause
Interrupt handler never executes Incorrect IRQ resource, interrupt not enabled or device not generating events.
System becomes unresponsive Long-running or blocking operations in hard IRQ context.
Incorrect event data Race conditions or incorrect buffer management.
read() blocks unexpectedly Wait-queue condition or nonblocking behavior is incorrect.
Kernel crash during removal IRQ or deferred callback accesses released memory.
Events are lost Insufficient buffering or repeated events being coalesced.
Interrupt storm Device interrupt source not acknowledged or cleared correctly.

17. Best Practices

  • Keep hard IRQ handlers short.
  • Use a suitable deferred-processing mechanism.
  • Use kernel subsystems for standard hardware interfaces whenever possible.
  • Protect shared data between IRQ and process contexts.
  • Use wait queues for blocking event-driven reads where appropriate.
  • Implement nonblocking behavior explicitly.
  • Design buffer overflow and event-loss policies.
  • Initialize all handler data before registering the IRQ.
  • Prevent new events before freeing IRQ-related resources.
  • Manage existing open file descriptions and private-data lifetime.

18. Lesson Summary

  • Character drivers expose device functionality through file operations.
  • Interrupt-driven drivers respond to hardware events instead of continuously polling.
  • The hard IRQ handler performs urgent, non-sleeping operations.
  • Deferred work handles additional processing.
  • Wait queues allow processes to sleep until data becomes available.
  • Spinlocks protect shared state between interrupt and process contexts.
  • The read callback transfers event data using copy_to_user().
  • O_NONBLOCK requires explicit driver implementation.
  • free_irq() synchronizes interrupt-handler teardown.
  • Existing open files require careful resource-lifetime management.
