Chapter Overview

Hardware devices use interrupts to notify the processor that an event requires attention. Linux device drivers must handle these events efficiently while following kernel execution-context restrictions.

This chapter explains the Linux interrupt-handling architecture, interrupt service routines, IRQ registration and removal, shared interrupts, interrupt context, top-half and bottom-half processing, tasklets and workqueues. It also demonstrates how interrupt handling is integrated into device drivers.

Important Kernel APIs and Concepts

  • IRQ: Interrupt request generated by a hardware device or interrupt controller.
  • ISR: Interrupt service routine that handles an interrupt event.
  • request_irq(): Registers an interrupt handler with the kernel.
  • free_irq(): Releases an interrupt handler registration.
  • IRQF_SHARED: Flag used when an interrupt line can be shared by multiple handlers.
  • IRQ_NONE: Indicates that the interrupt was not handled by the handler.
  • IRQ_HANDLED: Indicates that the interrupt was handled.
  • Top half: Immediate interrupt-handling portion that performs time-critical work.
  • Bottom half: Deferred processing mechanism for work that does not need to run immediately.
  • Tasklets: A legacy deferred-work mechanism; new drivers should generally prefer modern alternatives such as workqueues or threaded IRQs where appropriate.
  • Workqueues: Execute deferred work in process context, where sleeping is permitted.
  • Threaded IRQ: Allows an interrupt handler's deferred portion to execute in a kernel thread.

Typical Interrupt Handling Sequence

  • Identify the interrupt source and obtain the appropriate IRQ number.
  • Register the interrupt handler using request_irq() or an appropriate managed or threaded IRQ API.
  • A device generates an interrupt event.
  • The interrupt controller and kernel IRQ subsystem dispatch the event.
  • The registered handler identifies and services the interrupt.
  • Time-consuming work is deferred when necessary.
  • The driver releases its interrupt registration during cleanup.

Interrupt Handling Guidelines

  • Keep hard interrupt handlers short and efficient.
  • Do not perform sleeping operations in hard interrupt context.
  • Do not acquire a mutex in a hard interrupt handler.
  • Use appropriate synchronization for shared data.
  • Check whether an interrupt belongs to the device when sharing an IRQ.
  • Use threaded IRQs or suitable deferred-work mechanisms for longer operations.
  • Release registered interrupts correctly during driver cleanup.
  • Ensure deferred work is cancelled or flushed safely before releasing resources it uses.
