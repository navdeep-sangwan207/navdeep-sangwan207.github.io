2. Introduction to Kernel Execution Context

The Linux kernel executes code in different situations. The execution environment in which a particular kernel function runs is called its execution context.

Execution context determines what operations are permitted while kernel code is running. In particular, it determines whether the code is allowed to sleep or wait for a resource.

Two important contexts in device-driver programming are:

  • Process context: Kernel code executing on behalf of a process or kernel thread.
  • Interrupt context: Kernel code executing as a result of an interrupt.

↓

Interrupt Context

A device driver must know its current execution context before calling kernel APIs that may block or sleep.

3. What Is Process Context?

Process context is the execution environment in which kernel code runs on behalf of a process or kernel thread.

For example, when a user application opens a device file, the Linux kernel invokes the driver's open callback in the context of the calling process.

Examples of driver operations in process context

  • open() callback
  • read() callback
  • write() callback
  • release() callback
  • unlocked_ioctl() callback
  • Kernel thread execution
  • Workqueue functions

Example: Driver read operation

static ssize_t my_read(struct file *file,
                       char __user *buffer,
                       size_t count,
                       loff_t *position)
{
    /*
     * This callback normally executes
     * in process context.
     */

    pr_info("Read operation called\n");

    return 0;
}

The read callback is normally invoked because a user process requested data from a device file.

Characteristics of process context

  • Associated with a process or kernel thread.
  • Has an identifiable current task.
  • May sleep when the calling path and locking rules permit it.
  • Can wait for events or resources.
  • Can use sleepable synchronization mechanisms such as mutexes.
Process context does not mean that every operation is automatically allowed to sleep. A process-context function must still obey locking rules and must not sleep while holding a spinlock or while executing in another atomic context.

4. What Is Interrupt Context?

Interrupt context is the execution environment in which kernel code runs because a hardware interrupt has occurred.

When a peripheral generates an interrupt, the CPU enters the interrupt-handling path. The Linux kernel then invokes the registered interrupt handler.

Example: Interrupt handler

static irqreturn_t my_interrupt_handler(int irq,
                                        void *dev_id)
{
    pr_info("Interrupt received\n");

    return IRQ_HANDLED;
}

This function executes in hard interrupt context when invoked as a hard IRQ handler.

Characteristics of hard interrupt context

  • Triggered by an interrupt event.
  • Not executed as an ordinary process-system-call operation.
  • Must complete quickly.
  • Must not perform operations that sleep.
  • Must use appropriate atomic-context synchronization.
  • Often schedules work for later processing.
A hard IRQ handler must not call functions that may sleep. Sleeping in hard interrupt context can cause serious kernel problems.

6. Why Cannot an Interrupt Handler Sleep?

A hard interrupt handler is not executing as a normal sleepable task. It is responding to an interrupt that needs timely service.

If a hard interrupt handler tries to sleep, the kernel cannot safely schedule it like an ordinary process waiting for an event. This violates the rules of atomic execution context.

Example of an incorrect operation

static irqreturn_t my_interrupt_handler(int irq,
                                        void *dev_id)
{
    msleep(100);

    return IRQ_HANDLED;
}

The call to msleep() is invalid in hard IRQ context because it attempts to put the current task to sleep.

Other operations to avoid in hard IRQ context

  • msleep() and ssleep()
  • mutex_lock() when it may block
  • wait_event() when it may wait
  • down() on a semaphore when it may block
  • Blocking memory allocations such as GFP_KERNEL
  • User-copy operations such as copy_to_user() and copy_from_user()
Some APIs have context-dependent behavior. The important rule is to consult the API's kernel documentation and ensure that the operation is safe in atomic context.

7. Sleeping and Non-Sleeping Operations

A sleeping operation is one that may block the current task until a condition is satisfied or a resource becomes available.

A non-sleeping operation completes without putting the current execution path to sleep.

Operation May sleep? Hard IRQ suitability
msleep() Yes Not allowed
mutex_lock() Yes, if contended Not allowed
kmalloc(GFP_KERNEL) May sleep Not allowed
kmalloc(GFP_ATOMIC) No sleeping allocation Can be used when appropriate
spin_lock() Does not sleep Can be used
atomic_inc() No Can be used
copy_to_user() May sleep Not allowed
GFP_ATOMIC is not a general replacement for GFP_KERNEL. It uses non-sleeping allocation behavior and may fail when suitable memory is unavailable. Keep hard IRQ allocations minimal and preferably prepare resources in advance.

8. What Is Atomic Context?

Atomic context refers to an execution environment in which the current code must not sleep or block.

Hard interrupt handlers execute in atomic context. Other kernel paths may also be atomic, such as code executing while holding a spinlock.

Important properties

  • Cannot voluntarily sleep.
  • Must not call blocking operations.
  • Requires appropriate synchronization.
  • Must execute efficiently.

The term atomic context is broader than interrupt context. Not every atomic-context operation is an interrupt handler.

9. Context-Appropriate Synchronization

Device drivers often share data between process context and interrupt context. Correct synchronization is essential to avoid race conditions.

Mutex

A mutex is a sleepable locking mechanism. It is suitable for protecting data accessed by process-context code when sleeping is allowed. 

static DEFINE_MUTEX(my_mutex);

static void process_function(void)
{
    mutex_lock(&my_mutex);

    /* Protected process-context operation */

    mutex_unlock(&my_mutex);
}

A hard IRQ handler must not acquire a mutex because it may need to wait for the lock.

Spinlock

A spinlock is a non-sleeping synchronization mechanism. It is useful for short critical sections that may be accessed from interrupt context. 

static DEFINE_SPINLOCK(my_lock);

static void process_function(void)
{
    unsigned long flags;

    spin_lock_irqsave(&my_lock, flags);

    /* Short protected operation */

    spin_unlock_irqrestore(&my_lock, flags);
}

The IRQ-save variant is useful when process-context code shares the same lock with a local hard IRQ handler. It saves the local interrupt state and disables local interrupts while the lock is held.

Synchronization comparison

Mechanism Can sleep? Typical use
Mutex Yes Process-context locking
Spinlock No Short atomic critical sections
spin_lock_irqsave() No Process context sharing a lock with local hard IRQ context
Atomic operations No Simple atomic variable updates
Never hold a spinlock while calling a function that may sleep. Keep spinlock-protected sections short.

10. How Process Context and Interrupt Context Interact

A device driver may have a user application communicating with a hardware device through a device file. The driver may also receive hardware interrupts from that device.

Example: UART driver

  1. A user application calls read() on a UART device file.
  2. The driver's read callback executes in process context.
  3. The UART receives data and generates an interrupt.
  4. The UART interrupt handler executes in hard IRQ context.
  5. The handler records the received data or updates a buffer.
  6. The handler may wake a process waiting for data.
  7. The read operation continues in process context and copies data to the user.
User Application
↓
Driver read() Callback
↓
Wait for UART Data
↓
UART Hardware Interrupt
↓
Hard IRQ Handler
↓
Wake Waiting Process
↓
read() Continues

This design allows the interrupt handler to perform only time-critical work while the process-context read operation performs operations that may sleep.

11. current and Process Context

Linux provides the current macro to refer to the task structure of the currently executing task. 

#include <linux/sched.h>

pr_info("Current process ID: %d\n", current->pid);

In process context, current identifies the task whose execution path is running the kernel code.

In interrupt context, current still refers to the task that was interrupted on that CPU; it does not mean the interrupt handler is running as an ordinary process operation.

Do not use current as proof that code is in a sleepable process context. The task identity alone does not determine whether sleeping is permitted.

12. Checking Whether Code Is in Interrupt Context

Linux provides context-checking functions through kernel headers. 

#include <linux/preempt.h>
#include <linux/interrupt.h>

if (in_interrupt()) {
    pr_info("Executing in interrupt context\n");
}

if (in_irq()) {
    pr_info("Executing in hard IRQ context\n");
}

The exact availability and semantics of context-checking helpers can vary across kernel versions. Modern code should consult the target kernel headers and documentation.

The broader in_interrupt() check can include interrupt-related contexts such as softirq context, while in_irq() specifically checks hard IRQ context on kernels that provide it.

Context-checking functions are useful for debugging and assertions. They should not be used to design APIs that unpredictably sleep in one context and not another. Prefer clear function contracts and separate context-specific implementations.

13. Why Is Work Deferred from Interrupt Context?

Interrupt handlers should perform only the work that must be completed immediately. Longer operations are often deferred to another execution context.

Examples of deferred processing mechanisms include:

  • Softirqs
  • Tasklets (legacy mechanism)
  • Workqueues
  • Threaded interrupt handlers

Workqueues execute work in worker-thread process context, where sleepable operations are permitted when otherwise appropriate. Softirqs and tasklets execute in atomic context and cannot sleep.

14. Common Mistakes

  1. Calling msleep() in a hard IRQ handler: sleeping is not allowed in hard interrupt context.
  2. Using mutex_lock() in a hard IRQ handler: a mutex may block and is not suitable for hard IRQ context.
  3. Using GFP_KERNEL in a hard IRQ handler: this allocation mode may sleep.
  4. Calling copy_to_user() in an ISR: user-copy functions may sleep and must not be used in hard interrupt context.
  5. Holding a spinlock for too long: long critical sections increase interrupt latency and reduce system responsiveness.
  6. Assuming every process-context function can sleep: other atomic constraints may still apply.
  7. Doing too much work in an ISR: lengthy processing can delay other interrupt handling.

15. Lesson Summary

  • Execution context describes the environment in which kernel code runs.
  • Process context runs on behalf of a process or kernel thread.
  • Hard interrupt context executes in response to hardware interrupts.
  • Process-context code may sleep when permitted.
  • Hard IRQ handlers must not sleep.
  • Atomic context is broader than interrupt context.
  • Mutexes are suitable for sleepable process-context locking.
  • Spinlocks are suitable for short non-sleeping critical sections.
  • Workqueues provide process-context deferred execution.
  • Softirqs and tasklets execute in atomic context.
