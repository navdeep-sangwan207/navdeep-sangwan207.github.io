2. Introduction to request_irq()

request_irq() is a Linux kernel API used by device drivers to register an interrupt handler with the Linux IRQ subsystem.

Once registration succeeds, the kernel can invoke the registered handler when the corresponding interrupt is delivered.

Why Is request_irq() Required?

A hardware device may generate an interrupt, but the Linux kernel needs to know which driver function should service that interrupt.

request_irq() establishes this association.

Device Generates Interrupt
↓
Interrupt Controller and Linux IRQ Subsystem
↓
Registered Handler
↓
Device-Specific Interrupt Service

3. Header File

The interrupt API declarations are available through:

#include <linux/interrupt.h>

A device driver commonly includes additional headers depending on its implementation.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/interrupt.h>
#include <linux/errno.h>

4. Function Declaration

The conventional declaration is:

int request_irq(
    unsigned int irq,
    irq_handler_t handler,
    unsigned long flags,
    const char *name,
    void *dev
);

The function returns an integer status:

  • 0 indicates successful registration.
  • A negative error code indicates failure.

Parameter Overview

Parameter Data Type Purpose
irq unsigned int Linux IRQ number.
handler irq_handler_t Function that services the interrupt.
flags unsigned long Interrupt configuration flags.
name const char * Name associated with the interrupt action.
dev void * Device-specific pointer passed to the handler.

5. First Parameter: IRQ Number

The irq parameter specifies the Linux IRQ number for which the driver wants to register a handler.

The IRQ number is an identifier managed by the Linux IRQ subsystem.

Important Points

  • It is a Linux IRQ number, not necessarily the hardware interrupt-controller number.
  • It may be obtained through a platform-specific or subsystem-specific device resource.
  • Device Tree-based drivers commonly obtain interrupt resources through kernel resource APIs.
  • Drivers should not assume fixed IRQ numbers across different machines.

Illustrative Declaration

unsigned int irq_number;

/* Example only: obtain the IRQ through
 * the appropriate device-specific API.
 */
Do not copy an arbitrary IRQ number from /proc/interrupts and assume it belongs to your device. A driver must obtain the correct interrupt resource for its hardware.

6. Second Parameter: Interrupt Handler

The handler parameter specifies the function that Linux invokes when the corresponding interrupt is dispatched.

The handler must follow the Linux IRQ handler signature.

static irqreturn_t my_interrupt_handler(
    int irq,
    void *dev_id
)
{
    return IRQ_HANDLED;
}

Function Parameters

Parameter Description
irq Linux IRQ number associated with the interrupt.
dev_id Device-specific pointer supplied during registration.

Return Values

  • IRQ_HANDLED – the interrupt was handled by this device.
  • IRQ_NONE – the interrupt was not generated by this device or was not handled.
  • IRQ_WAKE_THREAD – requests execution of a registered threaded handler.

A handler should inspect the device's interrupt status and perform the required device-specific service before returning.

7. Third Parameter: Interrupt Flags

The flags parameter specifies how the interrupt should be configured and registered.

Several commonly encountered flags are:

Flag Purpose
IRQF_SHARED Allows the IRQ to be shared with other registered handlers, subject to sharing requirements.
IRQF_TRIGGER_RISING Requests rising-edge triggering.
IRQF_TRIGGER_FALLING Requests falling-edge triggering.
IRQF_TRIGGER_HIGH Requests high-level triggering.
IRQF_TRIGGER_LOW Requests low-level triggering.
IRQF_ONESHOT Used with threaded IRQ handling to keep the IRQ masked while the thread runs, as supported by the IRQ flow.

Example

IRQF_TRIGGER_RISING

This requests an interrupt on a rising signal edge, provided that the interrupt controller and device configuration support it.

The trigger type must agree with the hardware and platform configuration. Drivers should not arbitrarily change a trigger type that is already described by firmware or established by the relevant subsystem.

8. Fourth Parameter: Interrupt Name

The name parameter provides a descriptive name for the interrupt action.

Example

request_irq(
    irq_number,
    my_interrupt_handler,
    0,
    "my_device_irq",
    dev
);

The name is useful when examining interrupt information in:

cat /proc/interrupts

It helps identify the registered interrupt handler or associated device.

9. Fifth Parameter: Device-Specific Pointer

The dev parameter supplies a pointer that is passed to the interrupt handler as dev_id.

It is commonly used to pass the driver's private data structure.

Example Structure

struct my_device {
    int event_count;
    void __iomem *regs;
};

Passing the Pointer

struct my_device *dev;

/* dev must point to a valid initialized object */

request_irq(
    irq_number,
    my_interrupt_handler,
    0,
    "my_device_irq",
    dev
);

Receiving the Pointer in the Handler

static irqreturn_t my_interrupt_handler(
    int irq,
    void *dev_id
)
{
    struct my_device *dev = dev_id;

    dev->event_count++;

    return IRQ_HANDLED;
}
The device data must remain valid for the entire period in which the interrupt handler is registered. Do not free the object while the handler can still access it.

10. Basic request_irq() Example

The following example demonstrates the registration pattern. It uses a placeholder IRQ number and a minimal handler for learning the API.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/interrupt.h>
#include <linux/errno.h>

#define MY_IRQ  42

static irqreturn_t my_isr(int irq, void *dev_id)
{
    pr_info("Interrupt received: IRQ %d\n", irq);

    return IRQ_HANDLED;
}

static int __init my_driver_init(void)
{
    int ret;

    ret = request_irq(
        MY_IRQ,
        my_isr,
        0,
        "my_test_device",
        &my_driver_init
    );

    if (ret) {
        pr_err("request_irq failed: %d\n", ret);
        return ret;
    }

    pr_info("Interrupt handler registered\n");

    return 0;
}

static void __exit my_driver_exit(void)
{
    free_irq(MY_IRQ, &my_driver_init);

    pr_info("Interrupt handler unregistered\n");
}

module_init(my_driver_init);
module_exit(my_driver_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic request_irq API demonstration");
This is an API demonstration, not a working hardware driver. IRQ 42 is arbitrary, and the handler has no device-specific status check or acknowledgement. Do not load it expecting a real interrupt. A real driver must obtain its IRQ from the device resource and correctly service the hardware.

11. request_irq() Registration Flow

When a driver calls request_irq(), the kernel attempts to register the specified interrupt action.

Driver Initialization
↓
Obtain and Prepare Device IRQ Resource
↓
Prepare Device Data and Handler
↓
Call request_irq()
↓
Kernel Validates Registration
↓
Success: Handler Registered
Failure: Negative Error Code

After successful registration, the IRQ subsystem can dispatch the handler when the interrupt occurs.

Registration may fail if the IRQ cannot be used as requested, the registration conflicts with an existing action, or another error occurs.

12. Error Handling in request_irq()

The driver must check the return value of request_irq().

Successful Registration

ret = request_irq(
    irq_number,
    my_isr,
    0,
    "my_device",
    dev
);

if (ret == 0) {
    pr_info("IRQ registration successful\n");
}

Failed Registration

if (ret) {
    pr_err("Unable to register IRQ: %d\n", ret);
    return ret;
}

A negative return value represents an error code.

Possible causes include:

  • Invalid or unavailable IRQ configuration.
  • Conflict with an existing non-shared handler.
  • Incompatible interrupt-sharing configuration.
  • Invalid trigger configuration.
  • Other resource or subsystem errors.

The driver should propagate the error and release any resources it allocated before the registration attempt.

13. Shared Interrupt Registration

Some interrupt lines can be shared by multiple devices.

To request a shared IRQ, the driver uses IRQF_SHARED.

Example

ret = request_irq(
    irq_number,
    my_isr,
    IRQF_SHARED,
    "my_shared_device",
    dev
);

Shared interrupt registration has important requirements:

  • The interrupt line must support sharing.
  • All registered actions on the shared IRQ must have compatible sharing configuration.
  • Each registration must provide a unique, non-NULL device identifier.
  • The handler must identify whether its own device generated the interrupt.
  • The handler must return IRQ_NONE for an interrupt it did not handle.

Shared interrupts are covered in detail in Lesson 6.

14. request_irq() vs request_threaded_irq()

Linux also provides request_threaded_irq(), which supports a primary handler and a threaded handler.

Feature request_irq() request_threaded_irq()
Primary handler Required Can be supplied or omitted in supported configurations.
Thread function Not directly specified Can be supplied.
Hard IRQ processing Handler executes in hard IRQ context. Primary handler executes in hard IRQ context when provided.
Sleepable processing Must be deferred separately. Thread function can sleep when permitted.
Typical use Short interrupt service. Devices requiring threaded interrupt processing.

Conceptual Declaration

int request_threaded_irq(
    unsigned int irq,
    irq_handler_t handler,
    irq_handler_t thread_fn,
    unsigned long flags,
    const char *name,
    void *dev
);

The primary handler can return IRQ_WAKE_THREAD to wake the registered thread function.

15. Important Rules Before Calling request_irq()

A real driver must prepare its hardware and software state carefully before registering the handler.

  1. Obtain the correct IRQ resource from the device or subsystem.
  2. Initialize the driver's private data.
  3. Map the required hardware registers.
  4. Initialize locks, buffers and other shared state.
  5. Configure the device's interrupt source appropriately.
  6. Register the handler.
  7. Enable the device's interrupt generation at the appropriate stage.
A device may generate an interrupt immediately after its interrupt source is enabled. Initialize all state needed by the handler before enabling interrupt generation. The precise ordering of request registration, controller masking and device interrupt enabling depends on the hardware.

16. Practical Linux Commands

After working with a suitable interrupt-capable driver, use these commands to inspect interrupt activity.

View Interrupt Information

cat /proc/interrupts

Monitor Interrupt Counters

watch -n 1 cat /proc/interrupts

View Kernel Messages

sudo dmesg | tail -30

Check Kernel Version

uname -r

Do not use the arbitrary IRQ number from the demonstration as a substitute for a real device resource.

17. Common Programming Mistakes

Mistake Correct Practice
Using an arbitrary IRQ number Obtain the IRQ through the correct device-resource API.
Ignoring the return value Check for registration failure and propagate the error.
Passing an invalid dev_id pointer Pass valid device-specific data that remains alive while registered.
Using an incorrect trigger flag Follow the hardware and firmware configuration.
Using IRQF_SHARED without correct handler logic Check device status and return IRQ_NONE when appropriate.
Enabling the device interrupt too early Initialize all handler-visible state first.
Forgetting to release the registration Use the corresponding free_irq() operation during cleanup.
Performing lengthy work in the handler Use an appropriate deferred-processing mechanism.

18. Lesson Summary

  • request_irq() registers a device-driver interrupt handler.
  • The function is declared through linux/interrupt.h.
  • It accepts five parameters: IRQ, handler, flags, name and dev.
  • The IRQ parameter is a Linux IRQ number.
  • The handler follows the irqreturn_t function signature.
  • Interrupt flags specify trigger and sharing configuration.
  • The device pointer is passed to the handler as dev_id.
  • A return value of zero indicates successful registration.
  • Negative return values indicate registration errors.
  • IRQF_SHARED supports shared IRQ registration when requirements are met.
  • request_threaded_irq() supports threaded interrupt processing.
  • Registered interrupt handlers must eventually be released using the appropriate cleanup API.
