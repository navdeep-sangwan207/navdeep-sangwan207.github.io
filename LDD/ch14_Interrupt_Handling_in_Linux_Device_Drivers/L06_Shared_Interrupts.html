2. Introduction to Shared Interrupts

An interrupt request (IRQ) is a signal used by a hardware device to notify the processor that it needs attention.

In some computer architectures, multiple hardware devices can be connected to the same interrupt line. This arrangement is called shared interrupt handling.

When an interrupt occurs on a shared IRQ line, the operating system may need to invoke multiple registered interrupt handlers. Each handler checks whether its own device generated the interrupt.

Example

Consider two devices connected to the same IRQ line:

  • Device A: Network controller
  • Device B: Storage controller

Both devices use IRQ 10 in this conceptual example. When IRQ 10 is signalled, Linux invokes the registered handlers so that each device can check its own interrupt status.

Network Controller
Storage Controller
↓
Shared IRQ Line: IRQ 10
↓
Linux Generic IRQ Subsystem
↓
Handler A + Handler B
IRQ 10 is only an illustrative example. Actual IRQ assignments depend on the hardware platform, firmware, interrupt controller and kernel configuration.

3. Why Are Interrupts Shared?

Hardware platforms have a finite number of interrupt lines. As the number of devices increases, sharing can help use the available interrupt resources efficiently.

Reasons for sharing

  • Limited number of physical interrupt lines.
  • Multiple peripheral devices connected through a common interrupt route.
  • Hardware architecture that supports interrupt-line sharing.
  • Efficient use of interrupt-controller resources.

Example of a system with multiple devices

Device Example IRQ Interrupt purpose
Network controller IRQ 10 Packet transmission or reception events
Storage controller IRQ 10 Storage operation completion
USB controller IRQ 11 USB-related events

The table is conceptual. Modern systems may use MSI or MSI-X interrupts, where devices can receive multiple message-signalled interrupt vectors rather than sharing a traditional physical IRQ line.

4. How Shared Interrupt Handling Works

When multiple drivers register handlers for the same shared IRQ, Linux maintains multiple interrupt actions associated with that IRQ.

When the interrupt is delivered, the kernel invokes the registered handlers according to the IRQ subsystem's handling mechanism. Each handler must determine whether its own device generated the interrupt.

Shared IRQ Occurs
↓
Linux IRQ Subsystem
↓
Invoke Handler A
↓
Invoke Handler B
↓
Each Handler Checks Device Status
↓
Return IRQ_HANDLED or IRQ_NONE

Important concept

A handler must not automatically assume that an interrupt on the shared line belongs to its device. It must inspect the device-specific status register or another reliable indication.

5. IRQF_SHARED Flag

The IRQF_SHARED flag tells the Linux IRQ subsystem that the interrupt action is allowed to share the IRQ line with other compatible interrupt actions.

Syntax

request_irq(irq,
            handler,
            IRQF_SHARED,
            "device_name",
            dev_id);

The flag is defined in the Linux interrupt header: 

#include <linux/interrupt.h>

Registration requirements

  • All handlers sharing the IRQ must register with compatible sharing settings.
  • The device identifier must be non-NULL.
  • Each registered action on that IRQ must have a unique dev_id.
  • The driver must check whether its own device caused the interrupt.
A driver cannot simply add IRQF_SHARED to an arbitrary request_irq() call and assume that sharing will work. The IRQ must be shareable on the underlying platform and existing registrations must be compatible.

6. Understanding dev_id in Shared Interrupts

The dev_id parameter identifies a particular registered interrupt action. It is commonly the address of the driver's private device structure.

Example device structures

struct my_device_data {
    int device_number;
    unsigned int interrupt_count;
};

static struct my_device_data device_a = {
    .device_number = 1,
    .interrupt_count = 0,
};

static struct my_device_data device_b = {
    .device_number = 2,
    .interrupt_count = 0,
};

The two structures have different addresses, so they can serve as distinct identifiers for their respective interrupt registrations.

Registering both devices

ret = request_irq(irq,
                  device_a_handler,
                  IRQF_SHARED,
                  "device_a",
                  &device_a);

ret = request_irq(irq,
                  device_b_handler,
                  IRQF_SHARED,
                  "device_b",
                  &device_b);

The same IRQ is used for both registrations, but the dev_id values are different.

Removing one handler

free_irq(irq, &device_a);

This removes the interrupt action associated with Device A. The registration belonging to Device B remains.

The device data passed through dev_id must remain valid for as long as the registered handler may access it. Do not free the structure before the handler has been safely unregistered and other users have stopped accessing it.

7. Identifying the Source of an Interrupt

Because multiple devices share the same IRQ, every handler must determine whether its own device generated the interrupt.

A common approach is to read a device-specific interrupt status register.

Conceptual example

static irqreturn_t device_a_handler(int irq, void *dev_id)
{
    struct my_device_data *data = dev_id;
    unsigned int status;

    status = read_device_a_status();

    if (!(status & DEVICE_A_INTERRUPT_BIT))
        return IRQ_NONE;

    /* Acknowledge or clear the device interrupt. */
    clear_device_a_interrupt();

    data->interrupt_count++;

    return IRQ_HANDLED;
}

Explanation

  1. The kernel invokes the handler for the shared IRQ.
  2. The handler obtains its device-specific data through dev_id.
  3. It reads the device's interrupt status.
  4. If the device did not generate the interrupt, it returns IRQ_NONE.
  5. If the device generated the interrupt, it handles and acknowledges the event.
  6. It returns IRQ_HANDLED.
read_device_a_status(), clear_device_a_interrupt() and DEVICE_A_INTERRUPT_BIT are illustrative placeholders. A real driver must use the actual device register definitions and correct acknowledgement sequence.

8. IRQ_HANDLED and IRQ_NONE in Shared IRQs

The return value of an interrupt handler communicates whether the handler recognized and handled the interrupt.

Return value Meaning
IRQ_HANDLED The device associated with this handler generated an interrupt and the handler handled it.
IRQ_NONE The handler did not recognize the interrupt as belonging to its device.
IRQ_WAKE_THREAD The handler requests execution of its associated threaded interrupt handler.

For shared IRQs, returning IRQ_NONE when the device did not generate the interrupt is particularly important. It allows the IRQ subsystem to determine which handlers actually recognized the interrupt.

Do not return IRQ_HANDLED unconditionally from every shared interrupt handler. A handler should verify its device's interrupt status first.

9. Complete Conceptual Example: Two Shared Handlers

The following example demonstrates the structure of two handlers registered on the same IRQ. It is a teaching example, not a loadable hardware driver. 

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/interrupt.h>

#define MY_IRQ 42

struct my_device_data {
    int device_number;
    unsigned int interrupt_count;
};

static struct my_device_data device_a = {
    .device_number = 1,
};

static struct my_device_data device_b = {
    .device_number = 2,
};

/* Placeholder status-checking functions. */
static bool device_a_has_interrupt(void)
{
    return false;
}

static bool device_b_has_interrupt(void)
{
    return false;
}

static irqreturn_t device_a_handler(int irq, void *dev_id)
{
    struct my_device_data *data = dev_id;

    if (!device_a_has_interrupt())
        return IRQ_NONE;

    data->interrupt_count++;

    pr_info("Device A handled interrupt\n");

    return IRQ_HANDLED;
}

static irqreturn_t device_b_handler(int irq, void *dev_id)
{
    struct my_device_data *data = dev_id;

    if (!device_b_has_interrupt())
        return IRQ_NONE;

    data->interrupt_count++;

    pr_info("Device B handled interrupt\n");

    return IRQ_HANDLED;
}

static int __init shared_irq_init(void)
{
    int ret;

    ret = request_irq(MY_IRQ,
                      device_a_handler,
                      IRQF_SHARED,
                      "device_a",
                      &device_a);

    if (ret) {
        pr_err("Unable to register Device A IRQ\n");
        return ret;
    }

    ret = request_irq(MY_IRQ,
                      device_b_handler,
                      IRQF_SHARED,
                      "device_b",
                      &device_b);

    if (ret) {
        pr_err("Unable to register Device B IRQ\n");

        free_irq(MY_IRQ, &device_a);

        return ret;
    }

    pr_info("Shared interrupt handlers registered\n");

    return 0;
}

static void __exit shared_irq_exit(void)
{
    free_irq(MY_IRQ, &device_b);
    free_irq(MY_IRQ, &device_a);

    pr_info("Shared interrupt handlers removed\n");
}

module_init(shared_irq_init);
module_exit(shared_irq_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Conceptual shared IRQ demonstration");

Code Explanation

Component Purpose
IRQF_SHARED Requests shared interrupt registration.
device_a Private data for Device A.
device_b Private data for Device B.
device_a_handler() Checks whether Device A generated the interrupt.
device_b_handler() Checks whether Device B generated the interrupt.
free_irq() Removes each registered interrupt action.
Important limitations: MY_IRQ 42 is a placeholder. The status-checking functions always return false, so this example does not handle real device interrupts. A real driver must use actual device resources, register access, interrupt acknowledgement and device-specific cleanup. The IRQ must also support sharing.

10. Error Handling During Shared IRQ Registration

A driver must handle failures carefully when registering multiple interrupt handlers or managing multiple devices.

For example, if the first registration succeeds but the second fails, the driver must remove the first registration before returning the error. 

ret = request_irq(irq,
                  handler_a,
                  IRQF_SHARED,
                  "device_a",
                  &device_a);

if (ret)
    return ret;

ret = request_irq(irq,
                  handler_b,
                  IRQF_SHARED,
                  "device_b",
                  &device_b);

if (ret) {
    free_irq(irq, &device_a);
    return ret;
}

This is an example of error-unwind logic. In a real driver, the cleanup path must also stop or mask the relevant device interrupt sources and release any resources already acquired.

11. Advantages and Disadvantages

Advantages Disadvantages
Efficient use of limited IRQ lines. Multiple handlers may be invoked for one interrupt.
Supports hardware architectures designed for IRQ sharing. Each handler must identify its own device's interrupt.
Allows several compatible devices to use one IRQ. Incorrect status checking can cause interrupt-handling problems.
Linux manages the registered interrupt actions. Handlers must be designed to execute efficiently.

12. Shared Interrupts and Interrupt Controllers

The interrupt controller is responsible for delivering interrupt requests to the CPU. The way sharing works depends on the hardware architecture and interrupt-controller capabilities.

In a traditional level-triggered shared IRQ arrangement, multiple devices may assert the same interrupt line. The handler list allows each driver to inspect its own device status and determine whether it needs to service the event.

Modern systems also use message-signalled interrupts (MSI and MSI-X). These interrupts are delivered as messages rather than through traditional shared physical interrupt wires. They commonly provide separate interrupt vectors to devices or device queues.

Shared IRQ handling is a property of the hardware and interrupt configuration as well as the Linux driver API. Not every IRQ can be shared.

13. Monitoring Interrupts in Ubuntu

Command 1: View interrupt information

cat /proc/interrupts

Displays interrupt counts, CPU information and registered handler names where available.

Command 2: Monitor changes

watch -n 1 cat /proc/interrupts

Refreshes the interrupt statistics every second.

Command 3: View kernel messages

dmesg | tail -n 30

Displays recent kernel ring-buffer messages.

Command 4: View kernel journal messages

sudo journalctl -k -n 50

Displays recent kernel messages retained in the systemd journal.

VirtualBox generally does not expose arbitrary physical hardware interrupt lines from the host to the guest. These commands can be used to inspect the virtual machine's available interrupts, but testing a physical shared IRQ requires suitable hardware and platform support.

14. Common Mistakes in Shared Interrupt Handling

  1. Not using IRQF_SHARED: compatible sharing registrations must explicitly request shared IRQ handling.
  2. Using NULL dev_id: shared IRQ registrations require a non-NULL identifier.
  3. Reusing dev_id: identifiers must be unique among actions sharing the IRQ.
  4. Not checking device status: each handler must identify whether its device generated the interrupt.
  5. Incorrect interrupt acknowledgement: the driver must follow the hardware-specific procedure to clear or acknowledge its interrupt.
  6. Incorrect cleanup: free_irq() must receive the original IRQ and dev_id.
  7. Freeing device data too early: the handler and any other active users must no longer access the data before it is freed.

15. Lesson Summary

  • A shared interrupt allows multiple devices to use the same IRQ.
  • Linux can invoke multiple registered handlers for that IRQ.
  • IRQF_SHARED enables a driver to request shared registration.
  • Each shared handler requires a unique, non-NULL dev_id.
  • Handlers must inspect device-specific status information.
  • IRQ_HANDLED indicates that the handler recognized and handled its device's interrupt.
  • IRQ_NONE indicates that the interrupt did not belong to that device.
  • free_irq() removes only the matching registered action.
  • Device-specific interrupt sources must be managed during cleanup.
