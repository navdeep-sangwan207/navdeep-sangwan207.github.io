2. Introduction to Deferred Interrupt Processing

When a hardware device generates an interrupt, the processor temporarily changes its execution flow so that the Linux kernel can handle the event.

The interrupt handler must respond quickly. However, a device driver may need to perform additional operations such as:

  • Reading a large amount of received data.
  • Processing a completed hardware operation.
  • Updating device buffers.
  • Communicating with other kernel subsystems.
  • Waiting for resources or performing sleepable operations.

Some of these operations cannot safely execute in hard interrupt context. Linux therefore supports deferred interrupt processing.

Definition

Deferred interrupt processing is the technique of postponing non-urgent interrupt-related work until a more suitable execution context becomes available.

3. Why Is Deferred Processing Required?

Hard interrupt handlers execute under strict timing and execution-context constraints.

Problems with lengthy interrupt handlers

  1. They increase interrupt latency.
  2. They delay the handling of other interrupts.
  3. They can reduce overall system responsiveness.
  4. They cannot perform operations that may sleep.
  5. They make interrupt handling more complex.
Device Generates Interrupt
↓
Short Hard IRQ Handler
↓
Schedule Deferred Work
↓
Return from Interrupt
↓
Perform Additional Processing
Deferred processing does not mean that the device interrupt is ignored. The driver still needs to acknowledge or manage the interrupt source correctly before deferring additional processing.

4. Immediate Processing vs Deferred Processing

Feature Immediate Processing Deferred Processing
Execution Inside hard IRQ handler After the immediate handler schedules work
Purpose Urgent interrupt operations Additional interrupt-related work
Execution time Should be short Depends on the selected mechanism
Can sleep? No Depends on mechanism; workqueues and threaded IRQs can sleep
Typical operations Acknowledge device, identify event Data processing, sleepable operations

5. Architecture of Deferred Interrupt Processing

The interrupt handler performs essential operations and schedules the remaining work.

Hardware Device
↓
Interrupt Controller
↓
Hard IRQ Handler
↓
Acknowledge / Identify Interrupt
↓
Schedule Deferred Processing
↓
Deferred Execution Mechanism

The deferred execution mechanism can be a softirq, tasklet, workqueue or threaded IRQ, depending on the requirements.

6. Types of Deferred Processing Mechanisms

Important Linux mechanisms include:

Mechanism Execution Context Can Sleep?
Softirq Softirq context No
Tasklet Softirq context No
Workqueue Worker-thread process context Yes, when permitted
Threaded IRQ IRQ kernel thread Yes, when permitted
The term bottom half describes deferred work conceptually. It does not identify one specific API. Different bottom-half mechanisms have different execution contexts and constraints.

7. Softirq-Based Deferred Processing

A softirq is a kernel mechanism for executing deferred work in a software interrupt context.

Softirqs are designed for high-performance kernel activities that need atomic execution.

Characteristics

  • Execute outside the original hard IRQ handler.
  • Run in softirq context.
  • Cannot sleep.
  • Can execute concurrently on multiple CPUs.
  • Require suitable synchronization for shared data.

The networking subsystem uses softirqs for important network packet processing activities.

Drivers normally use established kernel interfaces rather than registering their own softirq actions. Direct softirq registration is primarily intended for core kernel code.

8. Tasklet-Based Deferred Processing

Tasklets provide a higher-level interface built on softirqs. They were historically used by drivers for short deferred operations.

Execution flow

Hardware Interrupt
        |
        v
Hard IRQ Handler
        |
        v
tasklet_schedule()
        |
        v
Softirq Processing
        |
        v
Tasklet Callback

A tasklet executes in atomic context and cannot perform blocking operations.

Tasklets are a legacy mechanism and are deprecated for new driver development. Workqueues or threaded IRQs are generally better choices for new implementations.

9. Workqueue-Based Deferred Processing

A workqueue schedules a callback for execution by a kernel worker thread.

Execution flow

Hardware Interrupt
        |
        v
Hard IRQ Handler
        |
        v
schedule_work()
        |
        v
Work Item Queued
        |
        v
Kernel Worker Thread
        |
        v
Workqueue Callback

Workqueue callbacks execute in process context. They can sleep when the surrounding conditions allow it.

Example callback

#include <linux/workqueue.h>

static struct work_struct device_work;

static void device_work_handler(struct work_struct *work)
{
    pr_info("Deferred device processing started\n");

    /*
     * Perform additional processing here.
     * Sleepable operations may be used when permitted.
     */

    pr_info("Deferred processing completed\n");
}

static void initialize_device_work(void)
{
    INIT_WORK(&device_work, device_work_handler);
}

Scheduling from an interrupt handler

static irqreturn_t device_irq_handler(int irq,
                                      void *dev_id)
{
    /*
     * Identify and acknowledge the interrupt
     * using the device-specific procedure.
     */

    schedule_work(&device_work);

    return IRQ_HANDLED;
}

The callback is not executed directly by schedule_work(). The function queues the work for later execution.

10. Threaded Interrupt Handling

Linux supports threaded interrupt handlers. This mechanism allows a driver to separate a short primary interrupt handler from a sleepable threaded handler.

The primary handler executes in hard IRQ context. The threaded handler executes in an IRQ kernel thread.

request_threaded_irq()

The general function signature is: 

int request_threaded_irq(
    unsigned int irq,
    irq_handler_t handler,
    irq_handler_t thread_fn,
    unsigned long flags,
    const char *name,
    void *dev
);
Parameter Purpose
irq Interrupt number.
handler Primary hard IRQ handler.
thread_fn Threaded interrupt handler.
flags Interrupt configuration flags.
name Interrupt name.
dev Device-specific identifier.

Primary handler return values

  • IRQ_HANDLED: The interrupt was handled.
  • IRQ_WAKE_THREAD: Wake the threaded handler.
  • IRQ_NONE: The interrupt was not handled by this device.

11. Example: Threaded IRQ Handler

The following is an illustrative driver pattern. It assumes that the device-specific interrupt source has been identified and acknowledged correctly. 

#include <linux/module.h>
#include <linux/interrupt.h>

static int irq_number = 1;

static irqreturn_t my_primary_handler(int irq,
                                      void *dev_id)
{
    /*
     * Check whether this device generated
     * the interrupt.
     *
     * Perform essential non-sleeping operations.
     */

    return IRQ_WAKE_THREAD;
}

static irqreturn_t my_thread_handler(int irq,
                                     void *dev_id)
{
    pr_info("Threaded IRQ handler executing\n");

    /*
     * Additional sleepable processing can be
     * performed here when permitted.
     */

    return IRQ_HANDLED;
}

Registering the threaded interrupt

ret = request_threaded_irq(
    irq_number,
    my_primary_handler,
    my_thread_handler,
    IRQF_ONESHOT,
    "my_device",
    my_device
);

if (ret)
    return ret;

The example shows the registration pattern, not a complete hardware driver. A real driver must use its actual interrupt resource and device state.

Meaning of IRQF_ONESHOT

For a threaded interrupt, IRQF_ONESHOT keeps the interrupt line masked while the threaded handler is running, where supported by the interrupt controller and IRQ configuration.

This is useful when the device or its interrupt handling requires the threaded handler to complete before another interrupt is processed.

A primary handler may be NULL in certain configurations, including ones using IRQF_ONESHOT, where the kernel can use a default primary handler. The exact registration requirements depend on the selected flags and IRQ type.

13. Synchronization in Deferred Processing

A hard IRQ handler and a deferred callback may access the same driver data. This can create race conditions.

Example shared data

struct my_device {
    spinlock_t lock;
    unsigned int event_count;
};

If the hard IRQ handler and a worker thread both modify event_count, the driver must protect the shared data using a suitable synchronization mechanism.

Example: spinlock protection

unsigned long flags;

spin_lock_irqsave(&dev->lock, flags);
dev->event_count++;
spin_unlock_irqrestore(&dev->lock, flags);

The IRQ-save variant is appropriate when the same lock is shared between process context and a hard IRQ handler on the same CPU.

Important rules

  • Do not hold a spinlock while performing sleepable operations.
  • Use a mutex only in contexts where sleeping is allowed.
  • Protect shared data accessed by multiple CPUs.
  • Keep critical sections short.
  • Choose synchronization based on all execution contexts that access the data.

14. Interrupt and Deferred Work Cleanup

A driver must prevent deferred callbacks from accessing released memory.

Typical workqueue teardown sequence

static void my_driver_cleanup(void)
{
    /* Stop or mask device interrupt generation. */

    free_irq(irq_number, my_device);

    /* No IRQ handler should now queue new work. */
    cancel_work_sync(&device_work);

    /* Release device resources and private memory. */
}

For a driver-created workqueue, destroy it after ensuring that no further work can be queued: 

cancel_work_sync(&device_work);
destroy_workqueue(my_wq);

Threaded IRQ cleanup

free_irq(irq_number, my_device);

Unregistering the IRQ synchronizes with the associated interrupt handling, including its threaded handler, before the device data used by those handlers is freed.

The complete teardown sequence must also prevent new hardware events and new software scheduling. Never free driver data while an IRQ handler, worker thread or other callback can still access it.

15. Practical Application: UART Receive Interrupt

Consider a UART device receiving serial data.

When a character arrives, the UART generates an interrupt. The driver may need to read the received data quickly and then perform additional processing.

Conceptual sequence

UART Receives Data
↓
UART Interrupt Generated
↓
Hard IRQ Handler
↓
Read / Acknowledge Hardware
↓
Schedule Appropriate Processing
↓
Process Buffered Data

The exact implementation depends on the UART driver and subsystem. Linux serial drivers commonly use established serial-core and interrupt-handling interfaces rather than implementing an independent generic UART pipeline.

Why defer processing?

  • To minimize time spent in hard IRQ context.
  • To process buffered data efficiently.
  • To perform sleepable operations when necessary.
  • To maintain system responsiveness.

16. Important Design Considerations

  1. Identify which operations must happen immediately.
  2. Keep the primary interrupt handler short.
  3. Choose a deferred mechanism based on execution-context requirements.
  4. Protect data shared between interrupt and deferred contexts.
  5. Handle repeated interrupts and event buffering correctly.
  6. Prevent work from being scheduled after teardown begins.
  7. Verify API availability against the target kernel version.
General selection rule: use a workqueue or threaded IRQ when processing needs to sleep. Use atomic deferred mechanisms only when the processing can safely execute without sleeping and the mechanism is appropriate for the subsystem.

17. Practical Linux Commands

Check the running kernel version

uname -r

Inspect kernel interrupt counters

cat /proc/interrupts

This file displays interrupt statistics by CPU and interrupt source. It is useful for observing interrupt activity when the relevant device and driver are available.

View kernel messages

sudo dmesg | tail -n 40

Inspect interrupt-related kernel configuration

grep CONFIG_GENERIC_IRQ /boot/config-$(uname -r)

The availability of configuration entries depends on the kernel build.

18. Common Mistakes

  1. Performing lengthy operations inside hard IRQ context.
  2. Calling sleepable functions from tasklets or softirqs.
  3. Using mutexes inside hard interrupt handlers.
  4. Assuming all deferred mechanisms execute in process context.
  5. Ignoring race conditions between interrupt handlers and worker threads.
  6. Freeing driver memory before deferred work has finished.
  7. Failing to acknowledge or mask the device interrupt source correctly.
  8. Assuming IRQF_ONESHOT replaces device-specific interrupt management.

19. Lesson Summary

  • Deferred interrupt processing moves non-urgent work out of hard IRQ context.
  • Hard IRQ handlers should perform essential operations quickly.
  • Softirqs and tasklets execute in atomic context.
  • Tasklets are a legacy mechanism for new driver development.
  • Workqueues execute callbacks in worker-thread process context.
  • Threaded IRQs allow sleepable interrupt processing.
  • request_threaded_irq() registers primary and threaded handlers.
  • IRQ_WAKE_THREAD requests execution of the threaded handler.
  • IRQF_ONESHOT keeps the interrupt masked while the threaded handler runs, subject to IRQ configuration.
  • Synchronization and cleanup are essential for driver reliability.
