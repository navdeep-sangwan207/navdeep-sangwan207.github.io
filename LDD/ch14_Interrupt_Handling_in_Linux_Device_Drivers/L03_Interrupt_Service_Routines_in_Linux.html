2. Introduction to Interrupt Service Routines

An Interrupt Service Routine (ISR), also called an interrupt handler, is a function executed by the operating system when a particular interrupt is delivered.

In Linux, a device driver registers its interrupt handler with the kernel. When the associated interrupt occurs, the Linux IRQ subsystem dispatches the registered handler.

The ISR typically performs urgent operations such as:

  • Identifying the source of an interrupt.
  • Reading device status registers.
  • Acknowledging or clearing the device interrupt condition.
  • Recording the event.
  • Scheduling deferred processing when necessary.
Hardware Device Generates Interrupt
↓
Interrupt Controller
↓
Linux IRQ Subsystem
↓
Registered Interrupt Handler (ISR)
↓
Service Event / Schedule Deferred Work

3. Need for an ISR

When a device generates an interrupt, the processor must execute suitable software to respond to that event.

The ISR provides the device-specific response.

Example: UART Receive Interrupt

Consider a UART peripheral receiving a character from a serial connection.

  1. The UART receives a character.
  2. The UART updates its receive status.
  3. The UART generates an interrupt request.
  4. The Linux kernel dispatches the registered handler.
  5. The handler checks the UART interrupt status.
  6. The driver reads available data or schedules further processing.
  7. The device-specific interrupt condition is serviced as required.

Without an appropriate interrupt handler, the device event may not be serviced correctly.

4. Linux Interrupt Handler Function Signature

Linux provides a standard function type for a conventional hard interrupt handler.

irqreturn_t handler(
    int irq,
    void *dev_id
);

The function returns an irqreturn_t value.

Header File

#include <linux/interrupt.h>

Function Parameters

Parameter Description
int irq The Linux IRQ number associated with the interrupt.
void *dev_id The device-specific pointer supplied when registering the handler.

Why Is dev_id Important?

The dev_id parameter allows the handler to access the driver's private device data.

It may point to a structure containing:

  • Device register information.
  • Memory-mapped I/O addresses.
  • Device status information.
  • Synchronization objects.
  • Buffers and counters.

For a shared interrupt, the device-specific pointer is particularly important because each handler must determine whether its own device generated the interrupt.

5. Return Values of an ISR

A Linux interrupt handler returns one of the standard IRQ result values.

Return Value Meaning
IRQ_HANDLED The interrupt was recognized and handled by this handler.
IRQ_NONE The interrupt was not generated by this device or was not handled by this handler.
IRQ_WAKE_THREAD Requests execution of the threaded handler when a threaded IRQ has been registered.

Example

static irqreturn_t my_isr(int irq, void *dev_id)
{
    return IRQ_HANDLED;
}

This is a minimal illustration of the return type. A real driver must perform appropriate device-specific interrupt handling before reporting the interrupt as handled.

For a shared interrupt, returning IRQ_NONE when the device did not generate the interrupt allows the IRQ subsystem to distinguish which registered handler recognized the event.

The exact controller acknowledgement, masking and completion sequence is architecture- and controller-dependent. The device driver is responsible for the device-specific operations required by its hardware.

7. Identifying the Interrupt Source

An interrupt handler must determine whether the interrupt belongs to its device.

This is particularly important when interrupts are shared or when a controller can report multiple interrupt causes.

Example: Checking a Device Status Register

/*
 * Conceptual pseudocode only.
 * Not a compilable hardware driver.
 */

static irqreturn_t my_isr(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    unsigned int status;

    status = read_device_status(dev);

    if (!(status & DEVICE_INTERRUPT_PENDING))
        return IRQ_NONE;

    service_device_interrupt(dev, status);

    clear_device_interrupt(dev, status);

    return IRQ_HANDLED;
}

Explanation:

  1. The handler receives the device pointer.
  2. It reads the device status register.
  3. It checks whether its interrupt condition is pending.
  4. If not, it returns IRQ_NONE.
  5. If pending, it services and acknowledges the device condition.
  6. It returns IRQ_HANDLED.
The register-access functions in this example are conceptual placeholders. A real driver must use the correct register definitions, I/O accessors and acknowledgement sequence specified by the hardware documentation.

8. Accessing Hardware Registers from an ISR

Device drivers frequently access memory-mapped hardware registers to identify and service interrupts.

Linux provides I/O access functions such as:

readl()
writel()
readb()
writeb()
ioread32()
iowrite32()

These functions are used according to the device's register width, access requirements and platform conventions.

Example: Register Access

/*
 * Conceptual example.
 * Assumes dev->regs is a valid mapped I/O address.
 */

u32 status;

status = readl(dev->regs + STATUS_REG);

/* Process the device status. */

writel(status, dev->regs + STATUS_CLEAR_REG);

In this example:

  • dev->regs represents a previously mapped device I/O region.
  • STATUS_REG identifies a device status register.
  • STATUS_CLEAR_REG represents a conceptual interrupt-clear register.
  • The actual register behavior depends on the hardware specification.
Not every device clears an interrupt by writing the status value back. Some use write-one-to-clear bits, separate acknowledgement registers, read-to-clear behavior or another device-specific mechanism.

9. Hard IRQ Context

A conventional interrupt handler registered using request_irq() executes in hard interrupt context.

Hard IRQ context is a special execution context used for handling hardware interrupts.

Characteristics

  • It is entered as a result of interrupt delivery.
  • It is not an ordinary process execution context.
  • It must complete quickly.
  • It must not perform operations that may sleep.
  • It can interrupt normal kernel or user-process execution.

Hard IRQ Context vs Process Context

Feature Hard IRQ Context Process Context
Execution trigger Hardware interrupt delivery Process or kernel-thread execution
Can sleep? No Usually yes, when the operation permits it
Mutex usage Not permitted Permitted when appropriate
Blocking operations Not permitted Can be used when appropriate
Execution duration Keep very short Can perform longer operations

10. Operations That Must Not Be Performed in Hard IRQ Context

An ISR must avoid operations that can block or sleep.

Examples of Prohibited Operations

Operation Reason
mutex_lock() May block while waiting for a mutex.
down() on a blocking semaphore May put the caller to sleep.
wait_event() Waits for a condition and may sleep.
msleep() Explicitly sleeps for a period.
copy_to_user() User-memory access may fault or sleep.
copy_from_user() User-memory access may fault or sleep.
Blocking I/O operations May wait for hardware or another process.
Calling a sleeping function from hard IRQ context can cause serious kernel problems, including warnings, deadlocks and kernel failures.

11. Operations Suitable for a Short ISR

A hard interrupt handler should perform only the urgent work necessary to service the interrupt.

Typical activities include:

  • Read a device status register.
  • Identify the interrupt source.
  • Acknowledge or clear the device interrupt condition when required.
  • Capture a small amount of data.
  • Update an appropriate counter or atomic state.
  • Protect shared state using suitable non-sleeping synchronization.
  • Schedule deferred work.

Long-running work should normally be moved to an appropriate deferred-processing mechanism.

Important Synchronization Rule

If a data structure is shared between process context and a hard interrupt handler, a suitable spinlock may be required.

When process context and hard IRQ context share a lock, the process-context side may need an IRQ-safe locking variant such as:

spin_lock_irqsave(&lock, flags);

/* Critical section */

spin_unlock_irqrestore(&lock, flags);

The correct locking strategy depends on every context that accesses the shared data. A spinlock must never be held across a sleeping operation.

12. ISR and Deferred Interrupt Processing

Sometimes the interrupt handler cannot complete all required work immediately.

For example, a network interface may receive a large amount of data. Processing every packet directly inside the hard interrupt handler would increase interrupt latency.

Linux provides deferred-processing mechanisms, including:

  • Softirqs.
  • Tasklets (legacy mechanism).
  • Workqueues.
  • Threaded interrupts.
  • Subsystem-specific mechanisms such as NAPI.
Hardware Interrupt
↓
Primary Interrupt Handler
↓
Identify and Acknowledge Event
↓
Schedule Deferred Processing
↓
Deferred Handler / Worker / IRQ Thread
↓
Complete Longer Processing

Deferred processing is discussed in detail in later lessons.

13. Primary Handler and Threaded Interrupt Handler

Linux supports threaded interrupt handling through APIs such as request_threaded_irq().

A threaded IRQ can use two handler functions:

Primary Handler

  • Runs in hard interrupt context.
  • Performs urgent interrupt identification and hardware operations.
  • Can return IRQ_WAKE_THREAD to request execution of the threaded handler.

Thread Function

  • Runs in the context of a kernel thread.
  • Can sleep when otherwise permitted.
  • Can perform longer processing operations.

The IRQF_ONESHOT flag can be used with threaded interrupts to keep the IRQ line masked while the thread function is executing, according to the IRQ subsystem's handling rules.

Conceptual Example

static irqreturn_t my_primary_handler(
    int irq,
    void *dev_id)
{
    struct my_device *dev = dev_id;

    if (!device_interrupt_pending(dev))
        return IRQ_NONE;

    acknowledge_or_mask_device_irq(dev);

    return IRQ_WAKE_THREAD;
}

static irqreturn_t my_thread_fn(
    int irq,
    void *dev_id)
{
    struct my_device *dev = dev_id;

    process_device_data(dev);

    return IRQ_HANDLED;
}

This is conceptual pseudocode: the device-specific functions must be implemented using the real hardware interface. Registration and flag configuration are covered in Lesson 4.

14. Complete Conceptual ISR Flow

The following pseudocode illustrates the structure of a simple interrupt handler.

/*
 * Conceptual pseudocode only.
 * Not a complete compilable Linux driver.
 */

static irqreturn_t device_isr(int irq, void *dev_id)
{
    struct my_device *dev = dev_id;
    unsigned int status;

    /* Read device interrupt status */
    status = read_device_status(dev);

    /* Check whether this device generated the interrupt */
    if (!(status & DEVICE_IRQ_PENDING))
        return IRQ_NONE;

    /* Service urgent device event */
    capture_device_event(dev, status);

    /* Clear or acknowledge the device interrupt */
    clear_device_interrupt(dev, status);

    /* Schedule longer work if required */
    schedule_deferred_processing(dev);

    return IRQ_HANDLED;
}

Explanation

  1. The handler receives the Linux IRQ number and device pointer.
  2. It reads the device interrupt status.
  3. It checks whether its device generated the interrupt.
  4. It captures the necessary event information.
  5. It services the device interrupt condition.
  6. It schedules deferred processing when necessary.
  7. It reports that the interrupt was handled.

15. Common ISR Programming Mistakes

Mistake Correct Approach
Performing lengthy processing in the ISR Move longer operations to deferred processing.
Using a mutex in hard IRQ context Use appropriate non-sleeping synchronization.
Ignoring the device interrupt status Check the device-specific status before claiming the interrupt.
Failing to clear the device interrupt condition Follow the hardware documentation's acknowledgement procedure.
Returning IRQ_HANDLED for an unrelated shared interrupt Return IRQ_NONE when the device did not generate the interrupt.
Using invalid device data Ensure the dev_id pointer remains valid while the handler is registered.
Using user-memory access in the ISR Transfer data through a suitable process-context path.
Holding a spinlock while sleeping Keep spinlock-protected sections short and non-blocking.

16. Monitoring Interrupt Activity

Linux provides useful commands to observe interrupt activity.

Display Interrupt Statistics

cat /proc/interrupts

Monitor Interrupt Counts Continuously

watch -n 1 cat /proc/interrupts

Display Software Interrupt Statistics

cat /proc/softirqs

Display Recent Kernel Messages

sudo dmesg | tail -30

Observe whether the interrupt counters change when a suitable device generates activity.

In Ubuntu running inside VirtualBox, the guest operating system generally sees virtual devices and virtualized interrupt delivery. Physical peripheral interrupt testing requires suitable hardware access or an appropriate emulation environment.

17. Linux ISR vs LPC2129 ISR

In your embedded ARM7 learning track, interrupt service routines are implemented using the LPC2129 interrupt architecture and its VIC (Vectored Interrupt Controller).

Linux device drivers use the Linux IRQ subsystem, which provides a higher-level interrupt-management framework.

Feature LPC2129 Bare-Metal Linux Device Driver
Interrupt controller VIC Platform-specific controller and Linux IRQ subsystem
Handler registration Vector and interrupt configuration Linux IRQ registration APIs
Handler declaration Compiler- and architecture-specific ISR declaration irqreturn_t handler function
Interrupt number VIC interrupt source number Linux IRQ number, mapped from hardware as needed
Deferred processing Application-designed approach Softirqs, workqueues, threaded IRQs and other kernel mechanisms

The underlying interrupt concepts are related, but Linux drivers should use the kernel's interrupt APIs rather than directly programming the LPC2129 VIC registers.

18. Lesson Summary

  • An ISR is a function executed to service an interrupt.
  • Linux device drivers register interrupt handlers with the kernel.
  • The conventional hard IRQ handler uses the irqreturn_t return type.
  • The handler receives an IRQ number and a device-specific pointer.
  • IRQ_HANDLED indicates that the handler recognized the interrupt.
  • IRQ_NONE indicates that the interrupt was not handled by that device.
  • IRQ_WAKE_THREAD requests execution of a registered threaded handler.
  • Hard IRQ handlers must not sleep.
  • Mutexes and blocking operations must not be used in hard IRQ context.
  • Device-specific interrupt conditions must be serviced correctly.
  • Longer processing should be deferred when appropriate.
  • Threaded IRQs provide a kernel-thread execution path for suitable interrupt work.
