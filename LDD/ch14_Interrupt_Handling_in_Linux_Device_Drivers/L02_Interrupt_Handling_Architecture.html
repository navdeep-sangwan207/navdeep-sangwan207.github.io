2. Introduction to Interrupt Handling Architecture

Interrupt handling architecture describes how a hardware interrupt is generated, routed, identified and processed by the operating system.

In Linux, interrupt handling involves several layers:

  • Peripheral hardware.
  • Interrupt controller.
  • CPU interrupt entry mechanism.
  • Architecture-specific interrupt code.
  • Linux Generic IRQ subsystem.
  • Registered interrupt handler.

These layers separate hardware-specific interrupt management from device-driver logic.

Peripheral Device
↓
Interrupt Controller
↓
CPU Interrupt Entry
↓
Architecture-Specific IRQ Handling
↓
Linux Generic IRQ Subsystem
↓
Registered Device Driver Handler

3. Peripheral Hardware

A peripheral is a hardware component that performs a specific operation and may generate an interrupt when an event occurs.

Examples include:

  • UART controller.
  • GPIO controller.
  • Timer peripheral.
  • Network interface controller.
  • USB controller.
  • Storage controller.

Example: UART Receive Event

When a UART receives a character, its hardware may set a status bit and assert an interrupt signal.

The interrupt controller receives the signal and routes the interrupt according to its configuration.

UART receives data
       |
       v
UART status register updated
       |
       v
UART interrupt output asserted
       |
       v
Interrupt controller receives request

The exact register operations depend on the UART hardware and its driver.

4. Interrupt Controller

An interrupt controller is hardware that manages interrupt requests from multiple devices and communicates them to one or more CPUs.

Main Responsibilities

  • Receive interrupt requests.
  • Manage interrupt enable and mask state.
  • Apply priority and routing rules.
  • Deliver interrupts to an appropriate CPU.
  • Support interrupt acknowledgement and completion according to its architecture.

Examples of Interrupt Controllers

Controller Common Platform Description
8259 PIC Legacy x86 systems Older programmable interrupt controller.
Local APIC x86 systems Manages local CPU interrupt delivery and related interrupt functions.
I/O APIC Many x86 systems Routes external hardware interrupts toward processors.
ARM GIC Many ARM systems Generic interrupt-controller architecture for managing interrupts.
VIC Some ARM microcontrollers Vectored Interrupt Controller used in certain embedded processors.
A Linux system may contain multiple interrupt controllers arranged in a hierarchy. The controller architecture depends on the processor and platform.

5. CPU Interrupt Entry Mechanism

When the CPU accepts an interrupt, it transfers control to an architecture-defined interrupt entry point.

The CPU and architecture-specific kernel code preserve the execution state required to handle the interrupt and return appropriately.

General Sequence

  1. The CPU accepts an eligible interrupt.
  2. The processor transfers control to an interrupt entry point.
  3. Required processor state is preserved according to the architecture.
  4. Architecture-specific Linux code identifies the interrupt.
  5. Linux invokes the appropriate IRQ handling path.
  6. The interrupt handler executes.
  7. The interrupt return path restores the appropriate execution state.

The exact register-saving process and entry mechanism differ between CPU architectures.

Interrupt Vector

An interrupt vector is an architecture-specific mechanism used to identify an interrupt or exception entry point.

For example, x86 processors use an Interrupt Descriptor Table (IDT) containing descriptors for interrupt and exception handling.

ARM systems use architecture-specific exception vectors and exception-entry mechanisms.

An interrupt vector and a Linux IRQ number are not necessarily the same thing. They belong to different layers of interrupt management.

6. Linux Generic IRQ Subsystem

Linux provides a common interrupt-management framework called the Generic IRQ subsystem.

It provides a common interface for interrupt management while allowing architecture-specific and interrupt-controller-specific implementations.

Main Responsibilities

  • Manage IRQ descriptors.
  • Register and remove interrupt handlers.
  • Manage interrupt actions.
  • Support shared interrupts.
  • Manage interrupt enable and disable operations.
  • Coordinate interrupt-controller operations.
  • Support threaded interrupt handling.
  • Manage interrupt affinity where supported.

Why Is a Generic Framework Needed?

Linux runs on many hardware platforms. Each platform may use a different interrupt controller.

Without a common framework, device drivers would need to implement platform-specific interrupt management repeatedly.

The Generic IRQ subsystem provides a consistent programming interface for drivers.

Device Driver B
Device Driver C

Linux Generic IRQ Subsystem

7. IRQ Descriptor

The Linux kernel maintains an IRQ descriptor for each managed Linux IRQ.

The descriptor is represented internally by:

struct irq_desc

It stores information required to manage an interrupt.

Conceptual Responsibilities

  • Maintain IRQ state.
  • Associate interrupt actions with an IRQ.
  • Manage interrupt flow handling.
  • Maintain interrupt statistics.
  • Coordinate interrupt-controller operations.

Related Internal Structures

Structure Purpose
struct irq_desc Represents and manages an IRQ descriptor.
struct irq_data Contains IRQ data used by the IRQ subsystem and interrupt-controller operations.
struct irqaction Represents a registered interrupt action, including its handler and related information.
struct irq_chip Provides interrupt-controller operations for managing IRQs.
These are internal kernel structures. Ordinary device drivers normally use public IRQ APIs instead of directly manipulating IRQ descriptors or controller internals.

8. Interrupt Handler Registration

A device driver registers an interrupt handler with the Linux kernel using an appropriate IRQ API.

The most commonly introduced API is:

request_irq()

Its declaration is available through:

#include <linux/interrupt.h>

Conceptual Syntax

int request_irq(
    unsigned int irq,
    irq_handler_t handler,
    unsigned long flags,
    const char *name,
    void *dev
);
Parameter Description
irq Linux IRQ number.
handler Interrupt handler function.
flags Interrupt configuration flags.
name Name associated with the interrupt action.
dev Device-specific data pointer.

Lesson 4 explains request_irq() in detail.

9. IRQ Number and Hardware IRQ Number

It is important to distinguish between a Linux IRQ number and a hardware interrupt identifier.

Hardware IRQ

The hardware interrupt controller identifies interrupt sources according to its own numbering and topology.

Linux IRQ

The Linux IRQ subsystem uses a Linux IRQ number to identify an interrupt managed by the kernel.

Linux can map hardware interrupt identifiers into Linux IRQ numbers through interrupt-domain mechanisms.

Hardware Interrupt Source
↓
Hardware IRQ / Controller Identifier
↓
Interrupt Domain Mapping
↓
Linux IRQ Number
↓
Linux IRQ Descriptor and Handler
Never assume that a hardware interrupt-controller number is always identical to the Linux IRQ number. The mapping depends on the platform and interrupt-controller configuration.

10. Interrupt Domains

An interrupt domain is a Linux kernel abstraction that maps hardware interrupt identifiers to Linux IRQ numbers.

Interrupt domains are particularly important on systems with complex interrupt-controller hierarchies.

Why Are Interrupt Domains Needed?

  • Different interrupt controllers have independent hardware numbering.
  • A platform may contain multiple interrupt controllers.
  • Hardware interrupt identifiers must be mapped into Linux IRQ numbers.
  • Hierarchical interrupt controllers may require multiple translation stages.

Conceptual Example

Suppose a peripheral generates hardware interrupt identifier 25 through a controller. Linux maps that interrupt into a Linux IRQ number used by the device driver.

The resulting Linux IRQ number is determined by the kernel's mapping process. It should not be assumed to equal 25.

11. Interrupt Flow Handling

Linux uses interrupt flow handlers to manage the handling sequence associated with different interrupt-controller and trigger configurations.

Common internal flow-handler concepts include:

Flow Handler General Purpose
Level flow Handles level-triggered interrupt flow.
Edge flow Handles edge-triggered interrupt flow.
Fast EOI flow Uses an end-of-interrupt operation as defined by the interrupt controller.
Per-CPU flow Handles interrupts associated with per-CPU interrupt arrangements.
Simple flow Provides a simpler interrupt flow for suitable interrupt-controller configurations.

The Generic IRQ subsystem coordinates the selected flow handler with the interrupt-controller operations.

Device drivers generally do not select or call these internal flow handlers directly. They are managed by the kernel's IRQ infrastructure.

12. Interrupt Acknowledgement and End of Interrupt

Interrupt controllers often require acknowledgement or completion operations as part of interrupt handling.

Interrupt Acknowledgement

Acknowledgement is an operation used to indicate that an interrupt has been recognized or accepted according to the controller's protocol.

End of Interrupt (EOI)

An EOI operation informs the interrupt controller that the handling stage has completed sufficiently for the controller to update its state or permit further interrupt delivery.

The exact acknowledgement and EOI sequence depends on the interrupt-controller architecture and Linux IRQ flow handling.

A driver may also need to clear a device-specific interrupt status condition. This is different from the interrupt controller's acknowledgement or EOI operation. The device-specific requirement must be followed to prevent repeated interrupts.

13. Interrupt Affinity

Interrupt affinity controls which CPU or CPUs may receive a particular interrupt.

On a multi-core system, interrupt affinity can help distribute interrupt processing across CPUs.

Example

Suppose a system contains four CPUs:

CPU 0
CPU 1
CPU 2
CPU 3

An interrupt may be configured to target a selected CPU or CPU mask, depending on platform capabilities.

Why Is Affinity Useful?

  • Distribute interrupt-processing load.
  • Improve CPU cache locality in suitable workloads.
  • Support performance tuning.
  • Control interrupt placement in multi-core systems.

Linux Interface

Linux exposes interrupt information and affinity controls through procfs on systems that support them.

# View interrupt counts and CPU distribution
cat /proc/interrupts

# View an IRQ's affinity mask
cat /proc/irq/IRQ_NUMBER/smp_affinity_list

Replace IRQ_NUMBER with an actual Linux IRQ number shown by the system.

Affinity interfaces and permitted values depend on architecture, interrupt-controller support and kernel configuration.

14. Shared Interrupt Architecture

Some hardware platforms allow multiple devices to share an interrupt line.

When a shared interrupt is delivered, Linux may invoke the handlers registered for that IRQ. Each handler must determine whether its own device generated the interrupt.

Device A
Device B
Device C
↓
Shared Interrupt Line
↓
Linux IRQ Subsystem
↓
Handler A → Checks Device A
Handler B → Checks Device B
Handler C → Checks Device C

A handler that does not recognize its device's interrupt should indicate that it did not handle the interrupt.

Shared interrupt registration has specific requirements, including appropriate flags and a unique, non-NULL device identifier for each registration.

Shared IRQs are studied in Lesson 6.

15. Viewing Interrupt Information in Linux

Linux provides useful interfaces for inspecting interrupt activity.

15.1 /proc/interrupts

cat /proc/interrupts

This displays interrupt statistics, including counts for individual CPUs and interrupt names or controller information.

15.2 /proc/softirqs

cat /proc/softirqs

This displays per-CPU statistics for Linux softirq categories.

15.3 /proc/irq

ls /proc/irq

This directory contains per-IRQ information and controls where supported.

15.4 Kernel Messages

sudo dmesg | tail -30

This displays recent messages from the kernel ring buffer.

The availability of individual procfs entries depends on kernel configuration and platform support. A virtual machine may expose virtualized interrupt controllers and devices rather than the physical host's complete interrupt topology.

16. Simplified End-to-End Example

Consider a Linux system receiving a network packet.

  1. The network interface receives a packet.
  2. The device updates its status and generates an interrupt request.
  3. The interrupt controller routes the interrupt to a CPU.
  4. The CPU enters the architecture-specific interrupt path.
  5. Linux identifies the associated IRQ descriptor.
  6. The Generic IRQ subsystem dispatches the registered network-device handler.
  7. The driver acknowledges or services the device interrupt according to hardware requirements.
  8. Additional packet processing may be scheduled through mechanisms such as NAPI.

For many Linux network drivers, the interrupt handler does not process every packet completely. It may schedule NAPI polling to process packets efficiently.

NAPI is a networking-specific mechanism combining interrupt notification with polling-based packet processing. It is not a replacement for the entire Linux interrupt subsystem.

  • Peripheral devices generate interrupt requests.
  • Interrupt controllers manage interrupt routing and delivery.
  • The CPU uses an architecture-specific interrupt entry mechanism.
  • Linux uses the Generic IRQ subsystem for common interrupt management.
  • struct irq_desc represents an IRQ descriptor.
  • Interrupt domains map hardware interrupt identifiers to Linux IRQ numbers.
  • IRQ flow handlers manage different interrupt-triggering arrangements.

  • /proc/interrupts provides useful interrupt statistics.
