Chapter: IOCTL and Device Control

Lesson: 1 – Introduction to IOCTL

Prerequisites: Character Device Drivers, file_operations, open(), read(), write(), and user-kernel data transfer.

Objective: Understand IOCTL, why device drivers need control commands, and how user-space applications communicate with drivers through the ioctl() system call.

1. Introduction

Linux device drivers provide interfaces that allow user-space applications to communicate with hardware devices or software-based devices.

Common file operations include:

  • open() – Opens a device file.
  • read() – Requests data from a device.
  • write() – Sends data to a device.
  • release() – Handles the release of an open file description.

However, some device operations are not naturally represented by reading or writing a stream of bytes.

For example:

  • Changing a device operating mode.
  • Setting a communication speed.
  • Starting or stopping a device operation.
  • Resetting a device.
  • Retrieving device-specific status information.

Linux provides the IOCTL mechanism for these device-specific control operations.

2. What Is IOCTL?

IOCTL stands for Input/Output Control.

It is a system-call interface that allows a user-space application to send control commands to a device driver.

The general user-space function is:

int ioctl(int fd, unsigned long request, ...);

Where:

Parameter Description
fd File descriptor obtained by opening a device file.
request Device-control command understood by the driver.
... Optional third argument, commonly an integer value or pointer to user-space data, depending on the request.

The driver receives the command through its ioctl handler, commonly implemented using unlocked_ioctl in a character driver's file_operations structure.

IOCTL is not a replacement for read() and write(). It complements them by providing a mechanism for device-specific control operations.

3. Why Is IOCTL Required?

Consider a character driver that controls a software-based device or a hardware peripheral.

The application may need to perform operations that do not represent ordinary data transfer.

Requirement Example Control Operation
Device configuration Set operating mode.
Communication configuration Configure baud rate or communication parameters.
Device management Reset or initialize a device.
Operation control Start or stop an operation.
Status information Retrieve device status or configuration.

These operations can be implemented using IOCTL commands instead of inventing an unrelated read/write data format for every control request.

The following diagram illustrates the basic communication path.

The driver examines the command and performs the corresponding operation.

If the command requires data exchange, the driver may copy data between user space and kernel space using appropriate kernel APIs.

5. IOCTL vs read() and write()

Both IOCTL and ordinary file operations allow user applications to interact with a device, but their purposes differ.

Feature read() write() ioctl()
Main purpose Receive data. Send data. Control or configure a device.
Typical operation Read sensor data. Send output data. Change device mode.
Common arguments Buffer and byte count. Buffer and byte count. Command and optional argument.
Driver callback .read .write .unlocked_ioctl

Example

Imagine a temperature sensor driver:

  • read() – Retrieve temperature data.
  • write() – Send supported configuration data, if designed that way.
  • ioctl() – Change measurement mode or request a sensor reset.

The exact interface depends on the driver's design and the relevant subsystem API.

6. User-Space ioctl() Function

To use IOCTL from a C application, include the appropriate header:

#include <sys/ioctl.h>

The application must first open the device file.

int fd;

fd = open("/dev/mydevice", O_RDWR);

if (fd < 0) {
    perror("open");
    return 1;
}

Then it can issue a device-control command:

int ret;

ret = ioctl(fd, command, argument);

if (ret < 0) {
    perror("ioctl");
}

Finally, close the device:

close(fd);
The request code and argument format must match the interface implemented by the driver. An arbitrary command cannot be assumed to work with every device.

7. Driver-Side IOCTL Handler

For a character driver, IOCTL handling is commonly provided through the unlocked_ioctl member of struct file_operations.

Basic structure:

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
)
{
    switch (cmd) {
        case COMMAND_ONE:
            /* Handle command one */
            break;

        case COMMAND_TWO:
            /* Handle command two */
            break;

        default:
            return -ENOTTY;
    }

    return 0;
}

Register the handler in the file operations structure:

static const struct file_operations my_fops = {
    .owner          = THIS_MODULE,
    .unlocked_ioctl = my_ioctl,
};

The handler receives the command number and optional argument. It should validate the command and argument before performing any operation.

The third argument to the user-space ioctl() function is variadic. The driver handler receives it as an unsigned long value. If it represents a pointer, the driver must treat it as a user-space address and use appropriate access and copy mechanisms.

8. IOCTL Command Identification

A driver may support multiple control operations. It therefore needs a way to distinguish one command from another.

For example:

COMMAND_ONE
COMMAND_TWO
COMMAND_THREE

Linux provides command-construction macros such as:

  • _IO
  • _IOR
  • _IOW
  • _IOWR

These macros encode command information such as command type, command number, data direction, and data size.

They are used to define structured IOCTL request codes. Their detailed design is covered in Lesson 4.

9. IOCTL Return Values and Error Handling

The user-space ioctl() function generally returns:

Return Value Meaning
Nonnegative value Successful operation; the exact meaning depends on the request.
-1 in user space System call failed. The C library sets errno.

Inside a Linux kernel handler, errors are normally represented by negative error codes.

For example:

return -ENOTTY;

ENOTTY commonly indicates that the requested ioctl operation is not appropriate for the device or is unsupported.

Other possible errors include:

  • -EINVAL – Invalid argument.
  • -EFAULT – Invalid user-space memory access or copy failure.
  • -ENOTTY – Unsupported or inappropriate IOCTL request.
  • -ENOMEM – Memory allocation failure, where applicable.

10. Advantages of IOCTL

  • Provides a standard system-call mechanism for device-specific control.
  • Separates control operations from ordinary data transfer.
  • Supports multiple commands through one interface.
  • Can exchange structured configuration and status data.
  • Allows user applications to control device behavior without directly accessing hardware registers.

Limitations and Design Considerations

  • Driver and application must agree on command definitions and data structures.
  • Incorrect pointer handling can cause kernel faults or security problems.
  • Command interfaces must remain compatible across software versions where required.
  • Drivers must validate user-provided values and check access permissions where necessary.

11. Practical Applications

Device Possible IOCTL Operation
Sensor driver Configure measurement mode.
Communication driver Configure communication parameters.
Display driver Configure display-specific settings.
Industrial control driver Start, stop or reset a supported operation.
Software character driver Change a simulated device operating mode.

These are illustrative examples. Modern Linux subsystems often provide dedicated interfaces for common hardware classes, and drivers should use those interfaces where appropriate rather than inventing private IOCTL commands unnecessarily.

12. Lesson Summary

  • IOCTL means Input/Output Control.
  • It provides a system-call interface for device-specific control operations.
  • User applications invoke it using ioctl().
  • Character drivers commonly implement it through unlocked_ioctl.
  • IOCTL complements read() and write().
  • Command definitions must match between the application and driver.
  • Kernel handlers must validate commands, arguments and user-space pointers.
  • Unsupported commands should return an appropriate error.
