Chapter: IOCTL and Device Control

Lesson: 7 – IOCTL Data Transfer

Prerequisites: IOCTL macros, unlocked_ioctl(), structures, copy_to_user() and copy_from_user().

Objective: Understand how data is transferred between user space and kernel space during IOCTL operations, including scalar values, structures, buffers and bidirectional exchanges.

1. Introduction

IOCTL provides a mechanism for an application to request device-specific control operations from a kernel driver. Many IOCTL commands also require information to move between user space and kernel space.

Examples include:

  • Sending a new operating mode to a device.
  • Reading the current device status.
  • Sending configuration parameters.
  • Receiving sensor or device information.
  • Exchanging a request and response structure.

Because user-space and kernel-space memory are separated, a driver must use safe user-memory access mechanisms when transferring data.

A user-space address must not be treated as an ordinary kernel pointer. Use the appropriate kernel user-access functions to transfer data.

2. User Space and Kernel Space

Linux separates application memory from kernel memory to provide protection and isolation.

User Space
IOCTL System Call
Kernel Space

Applications request kernel services through system-call interfaces.

A user-space application can pass an address to the kernel through an IOCTL argument. That address refers to application memory, not ordinary kernel memory.

The driver uses functions such as:

  • copy_from_user() – copies data from an application into kernel memory.
  • copy_to_user() – copies data from kernel memory into an application.

3. Data Transfer Direction

4. Understanding the IOCTL Argument

The standard callback has this form:

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
);

The arg parameter carries the third argument supplied to the IOCTL request. For pointer-based commands, it commonly represents a user-space address.

For example, the application calls:

int value = 50;

ioctl(fd, SET_DEVICE_VALUE, &value);

The driver receives the argument in arg and converts it to the appropriate user-pointer type for a user-access operation.

int value;

if (copy_from_user(
        &value,
        (int __user *)arg,
        sizeof(value))) {
    return -EFAULT;
}
The __user annotation identifies a pointer that refers to user-space memory. It helps kernel tooling and developers distinguish user pointers from kernel pointers.

5. Transferring a Single Integer to the Driver

Use an _IOW request when the application sends an integer value to the driver.

Command Definition

#define SET_DEVICE_VALUE \
    _IOW('N', 1, int)

User-Space Code

int value = 150;

if (ioctl(fd, SET_DEVICE_VALUE, &value) == -1) {
    perror("SET_DEVICE_VALUE");
}

Kernel-Space Code

int value;

if (copy_from_user(
        &value,
        (int __user *)arg,
        sizeof(value))) {
    return -EFAULT;
}

/* Validate and use the received value */

if (value < 0 || value > 1000)
    return -EINVAL;

The driver receives the integer in its own kernel-space variable and validates it before using it.

6. Transferring a Single Integer to User Space

Use an _IOR request when the application retrieves an integer from the driver.

Command Definition

#define GET_DEVICE_VALUE \
    _IOR('N', 2, int)

Kernel-Space Code

int value = 250;

if (copy_to_user(
        (int __user *)arg,
        &value,
        sizeof(value))) {
    return -EFAULT;
}

User-Space Code

int value;

if (ioctl(fd, GET_DEVICE_VALUE, &value) == -1) {
    perror("GET_DEVICE_VALUE");
} else {
    printf("Device value: %d\n", value);
}

7. Transferring Structures

When multiple related values must be transferred, a structure is often more suitable than several independent scalar arguments.

Structure Definition

struct device_status {
    int mode;
    int speed;
    int error_code;
};

IOCTL Definition

#define GET_DEVICE_STATUS \
    _IOR('N', 3, struct device_status)

Kernel-Space Code

struct device_status status;

status.mode = 1;
status.speed = 100;
status.error_code = 0;

if (copy_to_user(
        (struct device_status __user *)arg,
        &status,
        sizeof(status))) {
    return -EFAULT;
}

User-Space Code

struct device_status status;

if (ioctl(fd, GET_DEVICE_STATUS, &status) == -1) {
    perror("GET_DEVICE_STATUS");
} else {
    printf("Mode: %d\n", status.mode);
    printf("Speed: %d\n", status.speed);
    printf("Error: %d\n", status.error_code);
}

8. Transferring a Buffer

Some IOCTL operations need to transfer an array or a block of data rather than a single integer or fixed structure.

For example, an application may send a short configuration string or a block of binary parameters.

Example Command

#define SEND_DEVICE_DATA \
    _IOW('N', 4, char[64])

The application provides a buffer containing up to 64 bytes.

User-Space Code

char data[64] = "Device configuration";

if (ioctl(fd, SEND_DEVICE_DATA, data) == -1) {
    perror("SEND_DEVICE_DATA");
}

Kernel-Space Code

char kernel_buffer[64];

if (copy_from_user(
        kernel_buffer,
        (char __user *)arg,
        sizeof(kernel_buffer))) {
    return -EFAULT;
}

/* Process the received buffer */

This example uses a fixed-size buffer. Both sides must agree on its size and format.

For variable-length transfers, define a clear length field and enforce a maximum size. Validate the length before allocating memory or copying data. Never trust a length supplied by an application.

9. Bidirectional Data Transfer

The _IOWR macro is suitable when the application sends input data and the driver returns output data through the same argument.

Command Definition

struct device_request {
    int command;
    int input_value;
    int output_value;
};

#define DEVICE_EXCHANGE \
    _IOWR('N', 5, struct device_request)

Kernel-Space Handler Concept

struct device_request request;

/* Copy input structure */

if (copy_from_user(
        &request,
        (struct device_request __user *)arg,
        sizeof(request))) {
    return -EFAULT;
}

/* Process the request */

if (request.command == 1) {
    request.output_value = request.input_value * 2;
} else {
    return -EINVAL;
}

/* Return updated structure */

if (copy_to_user(
        (struct device_request __user *)arg,
        &request,
        sizeof(request))) {
    return -EFAULT;
}

return 0;

The driver first copies the input structure into kernel memory, processes the request and then copies the response back to the application.

10. Understanding Copy Function Return Values

Both copy_to_user() and copy_from_user() return the number of bytes that could not be copied.

Return Value Meaning
0 All requested bytes were copied successfully.
Nonzero Some or all bytes could not be copied.

Correct error handling:

if (copy_from_user(&value,
                   (int __user *)arg,
                   sizeof(value))) {
    return -EFAULT;
}

-EFAULT indicates an invalid or inaccessible memory address or an unsuccessful user-memory transfer.

Do not interpret the return value of copy_to_user() or copy_from_user() as a negative errno. They return an uncopied-byte count.

11. Data Transfer and Memory Safety

Correct IOCTL data transfer requires more than calling a copy function.

  • Check user pointers through the copy functions.
  • Validate all input values.
  • Validate lengths before variable-size transfers.
  • Initialize output structures before copying them to user space, so uninitialized kernel data is not exposed.
  • Use compatible structure definitions.
  • Protect shared device state using appropriate synchronization.
  • Do not call user-copy functions from interrupt context because they may sleep.

Example: Initialize an Output Structure

struct device_status status = { 0 };

/* Fill fields with valid device information */

status.mode = 1;
status.speed = 100;
status.error_code = 0;

if (copy_to_user(
        (struct device_status __user *)arg,
        &status,
        sizeof(status))) {
    return -EFAULT;
}

12. Variable-Length Data Transfer Design

When the amount of data changes from request to request, the application and driver need a clearly defined length protocol.

A typical structure can contain a length field and a fixed-size data array:

#define MAX_DATA_SIZE 256

struct device_buffer {
    __u32 length;
    __u8 data[MAX_DATA_SIZE];
};

The driver should:

  1. Copy the request structure from user space.
  2. Check whether the requested length is within the permitted limit.
  3. Process only the valid number of bytes.
  4. Set the response length correctly.
  5. Copy the response structure back if required.

For a flexible array or separate user pointer design, additional allocation, pointer validation and compatibility considerations are necessary.

13. Common Mistakes

Mistake Correct Practice
Directly dereferencing a user pointer. Use user-memory copy functions.
Ignoring the copy function's return value. Check for a nonzero uncopied-byte count.
Trusting a user-supplied length. Validate it against a maximum allowed size.
Returning uninitialized kernel data. Initialize output data before copying.
Using different structure layouts. Maintain a compatible user-kernel ABI.
Calling user-copy functions in interrupt context. Perform these operations in an appropriate sleepable context.

14. Lesson Summary

  • IOCTL can transfer scalar values, structures and buffers.
  • copy_from_user() transfers application data into kernel memory.
  • copy_to_user() transfers kernel data into application memory.
  • _IOW, _IOR and _IOWR describe the intended data direction in the request code.
  • Copy functions do not replace input validation.
  • Variable-length transfers require strict size validation.
  • Output data should be initialized before being returned.
  • User-copy operations must not be performed from interrupt context.
