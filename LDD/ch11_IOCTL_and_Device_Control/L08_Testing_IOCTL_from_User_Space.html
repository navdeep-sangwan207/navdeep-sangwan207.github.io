Chapter: IOCTL and Device Control

Lesson: 8 – Testing IOCTL from User Space

Prerequisites: IOCTL command macros, character drivers, unlocked_ioctl(), user-kernel data transfer and C programming.

Objective: Learn to compile and execute a user-space test application, invoke IOCTL commands, verify driver responses and troubleshoot common errors.

1. Introduction

After implementing an IOCTL handler in a Linux character driver, the next step is to test it from a user-space application.

The application uses the ioctl() system call to send request codes and arguments to the driver.

Testing helps verify:

  • Whether the device file can be opened.
  • Whether the IOCTL request reaches the correct callback.
  • Whether the driver recognizes the command.
  • Whether input data is copied correctly.
  • Whether output data is returned correctly.
  • Whether invalid requests are handled safely.

The test application acts as a client of the character driver. It sends commands and checks the returned results.

3. Requirements for Testing

Before testing, ensure that the following components are available:

Component Purpose
Linux kernel headers Required to build the kernel module against the selected kernel.
GCC compiler Compiles the user-space test program.
Kernel module Contains the character driver and IOCTL handler.
Device number registration Associates the driver with a major/minor device number.
Device node Provides the application with a path such as /dev/mydevice.
IOCTL header Provides matching request codes and structure definitions.

This lesson uses a memory-backed software device for demonstration. It does not require a physical peripheral.

4. Define IOCTL Commands

Create a shared header named my_device_ioctl.h.

#ifndef MY_DEVICE_IOCTL_H
#define MY_DEVICE_IOCTL_H

#ifdef __KERNEL__
#include <linux/ioctl.h>
#else
#include <sys/ioctl.h>
#endif

#define MY_DEVICE_MAGIC 'N'

#define DEVICE_RESET \
    _IO(MY_DEVICE_MAGIC, 1)

#define SET_DEVICE_VALUE \
    _IOW(MY_DEVICE_MAGIC, 2, int)

#define GET_DEVICE_VALUE \
    _IOR(MY_DEVICE_MAGIC, 3, int)

#endif

The header defines three commands:

  • DEVICE_RESET – resets the stored value.
  • SET_DEVICE_VALUE – sends an integer to the driver.
  • GET_DEVICE_VALUE – retrieves an integer from the driver.
In a production interface, use compatible shared types and structure definitions. The user-space and kernel-space command definitions must produce matching request codes.

5. User-Space Test Application

Create a file named test_ioctl.c.

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>

#include "my_device_ioctl.h"

int main(void)
{
    int fd;
    int value;

    fd = open("/dev/mydevice", O_RDWR);

    if (fd == -1) {
        perror("open");
        return EXIT_FAILURE;
    }

    printf("Device opened successfully\n");

    /* Reset device */

    if (ioctl(fd, DEVICE_RESET) == -1) {
        perror("DEVICE_RESET");
        close(fd);
        return EXIT_FAILURE;
    }

    printf("Device reset successful\n");

    /* Send value to driver */

    value = 250;

    if (ioctl(fd, SET_DEVICE_VALUE, &value) == -1) {
        perror("SET_DEVICE_VALUE");
        close(fd);
        return EXIT_FAILURE;
    }

    printf("Value sent: %d\n", value);

    /* Retrieve value from driver */

    value = 0;

    if (ioctl(fd, GET_DEVICE_VALUE, &value) == -1) {
        perror("GET_DEVICE_VALUE");
        close(fd);
        return EXIT_FAILURE;
    }

    printf("Value received: %d\n", value);

    close(fd);

    return EXIT_SUCCESS;
}

The application performs three IOCTL operations and checks each return value.

6. Understanding the Test Program

Step 1: Open the Device

fd = open("/dev/mydevice", O_RDWR);

The open() function returns a file descriptor if the device is opened successfully. Otherwise, it returns -1 and sets errno.

Step 2: Reset the Device

ioctl(fd, DEVICE_RESET);

This sends a command without a pointer-based data argument.

Step 3: Send Data

value = 250;
ioctl(fd, SET_DEVICE_VALUE, &value);

The driver receives the integer through copy_from_user().

Step 4: Receive Data

value = 0;
ioctl(fd, GET_DEVICE_VALUE, &value);

The driver returns the integer through copy_to_user().

Step 5: Close the Device

close(fd);

This releases the application's file descriptor.

7. Compile the Application

Open an Ubuntu terminal and move to the directory containing the source file and shared header.

gcc -Wall -Wextra test_ioctl.c -o test_ioctl

The compiler creates an executable named test_ioctl.

Check that the executable exists:

ls -l test_ioctl

If compilation fails, check:

  • Whether the shared header is in the correct directory.
  • Whether all command definitions are present.
  • Whether the application includes <sys/ioctl.h>.
  • Whether the C source contains syntax errors.

8. Verify the Character Device

Before running the application, verify that the driver is loaded.

lsmod | grep my_device

Check the kernel log:

sudo dmesg | tail -n 20

Check whether the device node exists:

ls -l /dev/mydevice

Inspect the device number:

stat /dev/mydevice

The device node's major and minor numbers must correspond to the character device registered by the driver.

A device node does not by itself create or register a driver. It must refer to a registered device number handled by the appropriate driver.

9. Run the Test Application

Execute the application:

sudo ./test_ioctl

Using sudo is only for a controlled learning environment where device permissions require elevated access. In normal deployments, configure appropriate device ownership and permissions instead.

Expected Output

Device opened successfully
Device reset successful
Value sent: 250
Value received: 250

The returned value should match the value stored by the driver.

Actual output depends on the implementation of the character driver and its initial state.

10. Verify Driver Kernel Logs

The driver can use kernel logging functions such as pr_info() to report important events.

View recent kernel messages:

sudo dmesg | tail -n 20

For example, a driver may log:

Device reset successful
Device value updated: 250
IOCTL GET_DEVICE_VALUE received

These messages help confirm whether the driver processed the expected commands.

Kernel logs are diagnostic information, not a replacement for checking the application's return values. Also, dmesg reads the kernel ring buffer; persistent journal records can be inspected separately with journalctl -k.

11. Test Invalid IOCTL Commands

A good test program should also verify that unsupported commands are rejected.

For example, define an unknown request:

#define INVALID_COMMAND _IO('N', 99)

Test it from user space:

if (ioctl(fd, INVALID_COMMAND) == -1) {
    perror("INVALID_COMMAND");
}

If the driver returns -ENOTTY, the user-space application normally observes an ioctl() failure with errno set to ENOTTY.

This test checks whether the driver's default command-handling case works correctly.

12. Test Invalid Input Values

Suppose the driver accepts values only between 0 and 1000.

Send an invalid value:

value = 5000;

if (ioctl(fd, SET_DEVICE_VALUE, &value) == -1) {
    perror("SET_DEVICE_VALUE");
}

The driver should validate the value and return -EINVAL for an invalid range.

The application should observe the failure and handle it appropriately.

Input validation must happen in the kernel driver. User-space validation is useful for application quality, but it cannot be trusted as the only security boundary.

13. Common Errors and Troubleshooting

Error Possible Cause What to Check
ENOENT Device path does not exist. Check /dev/mydevice.
EACCES or EPERM Insufficient permissions. Check device-node permissions and access policy.
ENOTTY Unsupported IOCTL command. Compare command definitions and driver switch cases.
EFAULT User-memory copy failed. Check the pointer and data size.
EINVAL Invalid argument or value. Check the driver's validation rules.
Unexpected output Incorrect state or data handling. Check copy operations and driver logic.

14. Testing Checklist

  • Confirm that the kernel module builds successfully.
  • Confirm that the module loads successfully.
  • Confirm that the character device is registered.
  • Confirm that the device node uses the correct major/minor numbers.
  • Compile the user-space application.
  • Test every supported IOCTL command.
  • Verify data returned by the driver.
  • Test invalid command numbers.
  • Test invalid input values.
  • Check kernel logs for unexpected errors.
  • Close the device and unload the module safely.

15. Lesson Summary

  • User-space programs invoke IOCTL commands through ioctl().
  • The application must open the correct device node first.
  • Request codes must match the definitions used by the driver.
  • Input and output arguments must follow the driver's expected data format.
  • The application should check every ioctl() return value.
  • Kernel logs help diagnose driver-side problems.
  • Invalid commands and invalid data should be tested.
  • Testing should cover normal operation and error conditions.
