Chapter: IOCTL and Device Control

Lesson: 6 – Passing Structures Through IOCTL

Prerequisites: C structures, IOCTL macros, unlocked_ioctl(), copy_to_user() and copy_from_user().

Objective: Learn how to transfer multiple related values between a user-space application and a kernel driver using structures.

1. Introduction

An IOCTL command often needs to transfer more than one value. For example, a device configuration operation may require a mode, operating speed, channel number and status.

Instead of creating a separate IOCTL command for every individual value, a driver can use a C structure to group related fields into one data object.

Passing a structure through IOCTL is useful for:

  • Device configuration.
  • Reading multiple device status values.
  • Setting operating parameters.
  • Transferring sensor configuration.
  • Exchanging command and response information.
A structure is normally passed through IOCTL using a pointer to user-space memory. The driver must copy the structure into kernel memory before accessing its fields.

2. Why Use Structures in IOCTL?

Suppose a device requires three configuration values:

int mode;
int speed;
int channel;

These values can be grouped into one structure.

struct device_config {
    int mode;
    int speed;
    int channel;
};

The application can now pass one pointer to the structure rather than managing several independent arguments.

Without Structure With Structure
Multiple separate values and commands may be required. Related fields can be transferred in one request.
Interface can become difficult to maintain. Configuration is grouped into one defined data object.
Adding parameters may require additional interface changes. A carefully versioned structure can support interface evolution.

For an input structure, the driver copies the structure from user space into a local kernel variable.

For an output structure, the driver fills a kernel-space structure and copies it back to the application.

4. Defining the Structure

Consider a device configuration structure.

struct device_config {
    int mode;
    int speed;
    int channel;
};
Field Purpose Example
mode Selects device operating mode. 1
speed Sets an operating speed parameter. 100
channel Selects a device channel. 2

The same structure definition must be available to both the kernel driver and the user-space application.

5. Defining IOCTL Commands for Structures

Use _IOW when the application supplies a structure to the driver, _IOR when the driver returns a structure, and _IOWR when both directions are required.

#define MY_DEVICE_MAGIC 'N'

#define SET_DEVICE_CONFIG \
    _IOW(MY_DEVICE_MAGIC, 1, struct device_config)

#define GET_DEVICE_CONFIG \
    _IOR(MY_DEVICE_MAGIC, 2, struct device_config)

#define UPDATE_DEVICE_CONFIG \
    _IOWR(MY_DEVICE_MAGIC, 3, struct device_config)

The data type passed to these macros is the structure type, not a pointer type.

The macros encode request metadata, including the size of the associated type. They do not copy the structure or validate its pointer.

6. Passing a Structure from User Space to Kernel Space

Consider the SET_DEVICE_CONFIG command. The application supplies configuration values, and the driver receives them.

User-Space Application

struct device_config config;

config.mode = 1;
config.speed = 100;
config.channel = 2;

if (ioctl(fd, SET_DEVICE_CONFIG, &config) == -1) {
    perror("SET_DEVICE_CONFIG");
}

Driver-Side Handler

static long set_device_config(
    unsigned long arg
)
{
    struct device_config config;

    if (copy_from_user(
            &config,
            (struct device_config __user *)arg,
            sizeof(config))) {
        return -EFAULT;
    }

    /* Validate the received configuration */

    if (config.mode < 0 || config.mode > 3)
        return -EINVAL;

    if (config.speed < 1 || config.speed > 1000)
        return -EINVAL;

    if (config.channel < 0 || config.channel > 7)
        return -EINVAL;

    /* Apply configuration to driver state */

    return 0;
}

The driver first copies the complete structure into kernel memory. It then validates each field before using the values.

7. Passing a Structure from Kernel Space to User Space

For GET_DEVICE_CONFIG, the driver fills a kernel-space structure and returns it to the application.

Driver-Side Handler

static long get_device_config(
    unsigned long arg
)
{
    struct device_config config;

    /* Read current driver configuration */

    config.mode = 1;
    config.speed = 100;
    config.channel = 2;

    if (copy_to_user(
            (struct device_config __user *)arg,
            &config,
            sizeof(config))) {
        return -EFAULT;
    }

    return 0;
}

User-Space Application

struct device_config config;

if (ioctl(fd, GET_DEVICE_CONFIG, &config) == -1) {
    perror("GET_DEVICE_CONFIG");
} else {
    printf("Mode: %d\n", config.mode);
    printf("Speed: %d\n", config.speed);
    printf("Channel: %d\n", config.channel);
}

The application receives the values after the driver successfully copies the structure into user space.

8. Bidirectional Structure Transfer Using _IOWR

Sometimes the application sends initial values and the driver modifies the same structure before returning it.

For example, an application may request a device configuration update. The driver validates the requested settings and returns the actual settings that were accepted.

Command Definition

#define UPDATE_DEVICE_CONFIG \
    _IOWR(MY_DEVICE_MAGIC, 3, struct device_config)

Driver Handler

static long update_device_config(
    unsigned long arg
)
{
    struct device_config config;

    /* Receive application data */

    if (copy_from_user(
            &config,
            (struct device_config __user *)arg,
            sizeof(config))) {
        return -EFAULT;
    }

    /* Validate input */

    if (config.mode < 0 || config.mode > 3)
        return -EINVAL;

    if (config.speed < 1 || config.speed > 1000)
        return -EINVAL;

    if (config.channel < 0 || config.channel > 7)
        return -EINVAL;

    /* Apply settings and prepare response */

    config.speed = 100;

    /* Return updated structure */

    if (copy_to_user(
            (struct device_config __user *)arg,
            &config,
            sizeof(config))) {
        return -EFAULT;
    }

    return 0;
}

User-Space Application

struct device_config config;

config.mode = 1;
config.speed = 150;
config.channel = 2;

if (ioctl(fd, UPDATE_DEVICE_CONFIG, &config) == -1) {
    perror("UPDATE_DEVICE_CONFIG");
} else {
    printf("Accepted mode: %d\n", config.mode);
    printf("Actual speed: %d\n", config.speed);
    printf("Accepted channel: %d\n", config.channel);
}

This example demonstrates the transfer pattern. The driver should only return values that accurately represent the configuration it has accepted or applied.

9. Complete IOCTL Handler Using a Structure

The following example combines the three operations in one callback.

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
)
{
    struct device_config config;

    switch (cmd) {

        case SET_DEVICE_CONFIG:

            if (copy_from_user(
                    &config,
                    (struct device_config __user *)arg,
                    sizeof(config))) {
                return -EFAULT;
            }

            if (config.mode < 0 || config.mode > 3)
                return -EINVAL;

            if (config.speed < 1 || config.speed > 1000)
                return -EINVAL;

            if (config.channel < 0 || config.channel > 7)
                return -EINVAL;

            /* Apply settings */

            return 0;

        case GET_DEVICE_CONFIG:

            config.mode = 1;
            config.speed = 100;
            config.channel = 2;

            if (copy_to_user(
                    (struct device_config __user *)arg,
                    &config,
                    sizeof(config))) {
                return -EFAULT;
            }

            return 0;

        default:
            return -ENOTTY;
    }
}

Register this callback in the character driver's file operations:

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .unlocked_ioctl = my_ioctl,
};

This is a focused IOCTL implementation example. It assumes the structure, command definitions and required driver state have already been declared.

10. Structure Compatibility Between User Space and Kernel Space

Passing structures across the user-kernel boundary requires careful attention to the binary layout of the structure.

Both sides must agree on:

  • Field types.
  • Field order.
  • Field sizes.
  • Alignment and padding.
  • Structure size.

Prefer Fixed-Width Integer Types

For stable interfaces, use types such as:

#include <linux/types.h>

/* Example kernel-side ABI structure */

struct device_config {
    __u32 mode;
    __u32 speed;
    __u32 channel;
};

For user-space code, the corresponding structure can use compatible fixed-width types such as uint32_t from <stdint.h>, with matching field order and layout.

Why Avoid Uncontrolled Pointer Fields?

A structure containing pointers is more complicated because user-space and kernel-space pointer sizes or address representations may differ. Such interfaces require explicit pointer handling and may require a compatibility implementation.

For long-lived driver interfaces, define a stable ABI. Consider including a version or size field when the structure may evolve, and avoid changing the meaning or layout of an already published structure.

11. 32-Bit and 64-Bit Compatibility

A 64-bit Linux kernel may support 32-bit user-space applications. In that situation, pointer sizes and some structure layouts can differ.

Potential problems include:

  • Different pointer widths.
  • Different alignment and padding.
  • Different structure sizes.
  • Different representations of pointer-containing fields.

Drivers that need to support 32-bit applications on a 64-bit kernel may implement the compat_ioctl callback and use appropriate compatibility types and conversion logic.

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .unlocked_ioctl = my_ioctl,
    /* .compat_ioctl = my_compat_ioctl, */
};

The commented entry is only a placeholder. A real compatibility callback must be implemented correctly before it is registered.

12. Common Mistakes

Mistake Correct Approach
Directly accessing a user-space structure pointer. Copy the structure into kernel memory using copy_from_user().
Copying the wrong structure size. Use the correct shared structure definition and sizeof().
Using different field definitions in the application and driver. Maintain compatible shared ABI definitions.
Not validating received fields. Validate all fields before applying configuration.
Using pointer fields without compatibility planning. Prefer fixed-width data fields or design explicit compatibility handling.
Assuming _IOWR automatically copies data both ways. Explicitly implement copy-in and copy-out operations.

13. Lesson Summary

  • Structures group related parameters into one IOCTL argument.
  • _IOW is commonly used for input structures.
  • _IOR is commonly used for output structures.
  • _IOWR supports bidirectional structure exchange.
  • The driver uses copy_from_user() and copy_to_user().
  • All received fields must be validated.
  • User and kernel structure layouts must be compatible.
  • Pointer-containing structures require special attention to 32-bit and 64-bit compatibility.
