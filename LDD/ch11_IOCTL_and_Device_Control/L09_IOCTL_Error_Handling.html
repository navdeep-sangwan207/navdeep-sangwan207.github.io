Chapter: IOCTL and Device Control

Lesson: 9 – IOCTL Error Handling

Prerequisites: IOCTL macros, unlocked_ioctl(), copy_to_user(), copy_from_user() and user-space testing.

Objective: Understand common IOCTL errors, kernel error codes, argument validation, user-memory access failures and reliable error handling in character drivers.

1. Introduction

Error handling is an essential part of Linux device-driver development. An IOCTL request may fail because of an unsupported command, invalid input, inaccessible user memory, unavailable hardware or an internal driver problem.

A reliable driver must detect these conditions and return an appropriate error code instead of continuing with invalid data.

Good IOCTL error handling helps to:

  • Prevent invalid operations.
  • Protect kernel memory.
  • Provide meaningful feedback to applications.
  • Improve driver reliability.
  • Make debugging easier.

2. IOCTL Error-Handling Architecture

User Application
ioctl() ↓
Kernel IOCTL Handler
↓
Command Validation
↓
Argument Validation
↓
Data Transfer and Operation
↓
Success or Error Return

The driver should validate the request before performing an operation that could change device state.

3. Kernel Error Codes

Linux kernel functions commonly return zero or a negative error code to indicate failure.

Error Code Meaning Typical IOCTL Situation
-EINVAL Invalid argument Unsupported parameter value or invalid length.
-EFAULT Bad address User-memory copy fails.
-ENOTTY Inappropriate IOCTL for the device Unknown or unsupported command.
-ENOMEM Out of memory Required kernel allocation fails.
-EBUSY Device or resource busy Operation cannot proceed while a resource is in use.
-ENODEV No such device Device is unavailable or has been removed.
-EIO Input/output error Hardware or device operation fails.
-EPERM Operation not permitted Operation is prohibited by the driver's policy.

These are examples, not an exhaustive list. Choose the error code that accurately represents the failure.

4. Handling Unsupported IOCTL Commands

The driver should explicitly identify the supported commands. A switch statement is commonly used.

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg)
{
    switch (cmd) {

    case DEVICE_RESET:
        /* Perform reset operation */
        return 0;

    case SET_DEVICE_VALUE:
        /* Handle input value */
        return 0;

    case GET_DEVICE_VALUE:
        /* Return device value */
        return 0;

    default:
        return -ENOTTY;
    }
}

The default case rejects commands that the driver does not support.

-ENOTTY is the conventional response for an unsupported IOCTL request. Do not silently report success for an unknown command.

5. Handling Invalid Input Values

Applications can send unexpected or invalid values. The driver must validate input independently.

Example: Validate an Integer

int value;

if (copy_from_user(
        &value,
        (int __user *)arg,
        sizeof(value))) {
    return -EFAULT;
}

if (value < 0 || value > 1000) {
    return -EINVAL;
}

/* Continue with the valid value */

return 0;

This example performs two checks:

  1. Checks whether the input can be copied from user memory.
  2. Checks whether the integer is within the accepted range.

6. Handling copy_from_user() Failure

copy_from_user() transfers data from user space into kernel memory.

It returns the number of bytes that could not be copied. A nonzero return indicates an incomplete transfer.

struct device_config config;

if (copy_from_user(
        &config,
        (struct device_config __user *)arg,
        sizeof(config))) {
    return -EFAULT;
}

/* Process config only after successful copy */

Never process a partially copied structure as though it were complete.

The destination structure should not be trusted after a failed copy. Return an error and do not use its contents as a valid request.

7. Handling copy_to_user() Failure

copy_to_user() transfers data from kernel memory into user space.

struct device_status status = { 0 };

status.mode = 1;
status.speed = 100;
status.error_code = 0;

if (copy_to_user(
        (struct device_status __user *)arg,
        &status,
        sizeof(status))) {
    return -EFAULT;
}

return 0;

If the destination user-memory region cannot be accessed completely, the driver returns -EFAULT.

Initialize output structures before copying them to user space to avoid exposing uninitialized kernel memory.

8. Handling Invalid Buffer Lengths

When an IOCTL operation uses a variable-length buffer, validate the length before allocation or data transfer.

#define MAX_DATA_SIZE 256

if (length == 0 || length > MAX_DATA_SIZE) {
    return -EINVAL;
}

/* Allocate or process only after validation */

Important validation checks include:

  • Reject zero length if an empty transfer is not permitted.
  • Reject lengths larger than the supported maximum.
  • Check arithmetic for integer overflow when calculating sizes.
  • Ensure allocation sizes match the validated length.
  • Do not trust an application-supplied pointer or length.
The size encoded in an IOCTL request macro is not a substitute for validating the actual data supplied by the application.

9. Handling Memory Allocation Errors

A driver may allocate kernel memory to process a large or variable-length IOCTL request.

char *buffer;

buffer = kmalloc(length, GFP_KERNEL);

if (!buffer) {
    return -ENOMEM;
}

/* Use buffer after successful allocation */

kfree(buffer);

Always release allocated memory on every exit path after allocation. If several operations can fail, use a clear cleanup strategy.

GFP_KERNEL allocation may sleep, so it must only be used in an appropriate sleepable execution context.

10. Handling Hardware Operation Failures

Some IOCTL commands control actual hardware. The operation can fail because a device is disconnected, a bus transaction fails or hardware reports an error.

Illustrative example:

static long set_device_mode(int mode)
{
    int ret;

    ret = hardware_set_mode(mode);

    if (ret < 0) {
        return ret;
    }

    return 0;
}

The exact error returned should reflect the underlying operation and the driver's documented interface.

Do not assume every hardware failure should be converted to -EIO. Preserve a meaningful error code when appropriate.

11. Returning Errors to User Space

When a kernel IOCTL handler returns a negative error code, the user-space ioctl() system call normally returns -1 and sets errno to the corresponding positive error number.

Kernel-Space Return

return -EINVAL;

User-Space Handling

if (ioctl(fd, SET_DEVICE_VALUE, &value) == -1) {
    perror("SET_DEVICE_VALUE");
}

For example, an invalid argument may produce a message similar to:

SET_DEVICE_VALUE: Invalid argument

The application can also inspect errno directly:

#include <errno.h>
#include <stdio.h>

if (ioctl(fd, SET_DEVICE_VALUE, &value) == -1) {

    if (errno == EINVAL) {
        printf("Invalid input value\n");
    }
    else if (errno == EFAULT) {
        printf("Memory transfer failed\n");
    }
    else {
        perror("IOCTL failed");
    }
}

12. Safe IOCTL Handler Design

A well-designed handler follows a predictable sequence:

Receive IOCTL Request
↓
Check Command
↓
Validate and Copy Input
↓
Validate Parameters
↓
Perform Device Operation
↓
Copy Output if Required
↓
Return Result

For state-changing operations, validate all relevant inputs before modifying device state. Consider what should happen if a later operation fails.

13. Example: Complete IOCTL Error-Handling Pattern

The following is an illustrative handler fragment. It assumes the command definitions and device state are declared elsewhere in the driver.

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg)
{
    int value;

    switch (cmd) {

    case DEVICE_RESET:
        /* Reset device state */
        device_value = 0;
        return 0;

    case SET_DEVICE_VALUE:

        if (copy_from_user(
                &value,
                (int __user *)arg,
                sizeof(value))) {
            return -EFAULT;
        }

        if (value < 0 || value > 1000) {
            return -EINVAL;
        }

        /* Update device state */
        device_value = value;

        return 0;

    case GET_DEVICE_VALUE:

        value = device_value;

        if (copy_to_user(
                (int __user *)arg,
                &value,
                sizeof(value))) {
            return -EFAULT;
        }

        return 0;

    default:
        return -ENOTTY;
    }
}
This fragment illustrates command dispatch and error returns. A real driver must also define and protect device_value appropriately, for example with a mutex when concurrent operations can access shared state. Hardware-specific operations need their own validation and failure handling.

14. Common IOCTL Error-Handling Mistakes

Mistake Correct Approach
Returning zero for every command. Return an error for unsupported commands or failed operations.
Ignoring copy function results. Check for a nonzero uncopied-byte count.
Using an invalid user pointer directly. Use copy_to_user() and copy_from_user().
Accepting any input value. Validate parameters and permitted ranges.
Trusting user-supplied lengths. Enforce maximum sizes and check arithmetic.
Returning uninitialized data. Initialize output structures and fields.
Leaking allocated memory on an error path. Release resources before returning.
Ignoring concurrency. Protect shared device state using suitable synchronization.

15. Lesson Summary

  • IOCTL handlers must validate commands and arguments.
  • -ENOTTY is commonly used for unsupported IOCTL commands.
  • -EINVAL indicates invalid arguments.
  • -EFAULT indicates an unsuccessful user-memory transfer.
  • -ENOMEM indicates an allocation failure.
  • Copy functions return an uncopied-byte count, not a negative errno.
  • Variable-length requests require strict bounds checking.
  • Allocated memory and other resources must be released on failure paths.
  • Applications should check ioctl() results and handle errno.
