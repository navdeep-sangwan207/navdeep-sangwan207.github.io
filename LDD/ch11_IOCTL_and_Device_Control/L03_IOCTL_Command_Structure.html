Chapter: IOCTL and Device Control

Lesson: 3 – IOCTL Command Structure

Prerequisites: Introduction to IOCTL, need for IOCTL operations, character drivers and file_operations.

Objective: Understand how Linux IOCTL request codes are organized, how command fields are encoded, and how drivers identify and process commands.

1. Introduction

A device driver may support many control operations. For example, a driver may support commands to reset a device, configure its mode, retrieve its status and enable a feature.

The driver must identify which operation the application is requesting. Linux uses an IOCTL request code for this purpose.

A request code is passed as the second argument to the user-space ioctl() system call.

ioctl(fd, request_code, argument);

The request code is a numeric value interpreted by the driver. Linux provides macros to construct structured request codes.

2. What Is an IOCTL Command Code?

An IOCTL command code is an identifier that tells a driver which control operation the application wants to perform.

For example, a conceptual device interface may define:

DEVICE_RESET
DEVICE_START
DEVICE_STOP
DEVICE_GET_STATUS

These names represent different operations. In an actual Linux driver, they should normally be defined using the standard IOCTL macros rather than arbitrary numbers.

Why Structured Command Codes?

  • Help distinguish different operations.
  • Can encode the type of device or command group.
  • Can encode the direction of data transfer.
  • Can encode the size of the associated data type.

3. Components of an IOCTL Request Code

Linux provides the _IOC family of macros to construct request codes.

A structured IOCTL request commonly contains four fields:

Direction
Type / Magic
Command Number
Argument Size
Field Purpose
Direction Describes the intended data-transfer direction between user space and kernel space.
Type / Magic Identifies the command group or device interface.
Command Number Identifies a particular operation within the command group.
Argument Size Encodes the size of the associated data type.
The exact bit widths and layout are architecture- and kernel-ABI-dependent. Use the standard macros rather than manually constructing request-code bit patterns.

4. Direction Field

The direction field describes the intended direction of data transfer associated with a command.

Macro Meaning
_IO No data argument is encoded as being transferred through the IOCTL command.
_IOR User application reads data from the driver.
_IOW User application writes data to the driver.
_IOWR Data is transferred in both directions.

The direction describes the user-space perspective:

  • _IOR: the driver provides data to the application.
  • _IOW: the application provides data to the driver.
  • _IOWR: data moves both ways.
The direction encoded in a request code does not automatically perform copying. The driver must explicitly validate and transfer user-space data using appropriate kernel APIs.

5. Type or Magic Field

The type field identifies a command group. It is commonly represented by a character or another suitable identifier.

For example:

#define MY_DEVICE_MAGIC 'N'

The character 'N' is an example identifier for a fictional device interface.

Choosing a unique command group identifier helps reduce accidental conflicts with other IOCTL interfaces.

The magic value is not a security mechanism. It does not authenticate the application or guarantee that the caller is authorized to execute a command.

6. Command Number Field

The command number identifies an individual operation within a command group.

For example:

#define CMD_RESET       0
#define CMD_START       1
#define CMD_STOP        2
#define CMD_GET_STATUS  3

These numbers are illustrative command identifiers. They are combined with a type and direction using IOCTL macros in the next lesson.

Command numbers should be assigned consistently and should not be changed casually after an interface has been released.

7. Argument Size Field

The size field encodes the size of the data type associated with a request.

For example, a command may exchange an integer:

sizeof(int)

Or it may exchange a structure:

struct device_status {
    int mode;
    int state;
    unsigned int error_count;
};

sizeof(struct device_status)

The standard macros such as _IOR, _IOW and _IOWR derive the encoded size from the type supplied to the macro.

The encoded size is metadata in the request code. It does not validate the actual memory area supplied by the application. The driver must still validate and safely access user-space memory.

8. How the Driver Uses the Command Code

The user-space application sends a request code through ioctl(). The kernel dispatches the request to the driver's IOCTL callback.

Application
↓
ioctl(fd, request, argument)
↓
Kernel IOCTL Dispatch
↓
unlocked_ioctl()
↓
Command Validation
↓
Execute Requested Operation

A simplified driver handler may use a switch statement:

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
)
{
    switch (cmd) {
        case DEVICE_RESET:
            /* Reset operation */
            break;

        case DEVICE_START:
            /* Start operation */
            break;

        default:
            return -ENOTTY;
    }

    return 0;
}

This example illustrates command dispatch only. Real request identifiers should be defined using the standard IOCTL macros.

9. Important Header File

Linux kernel drivers commonly include:

#include <linux/ioctl.h>

This header provides the IOCTL command-construction macros.

User-space applications commonly include:

#include <sys/ioctl.h>

Both sides must use compatible definitions for the request codes and associated data structures.

10. ABI Compatibility and Command Design

IOCTL commands form part of the interface between user-space applications and kernel drivers. This interface is commonly referred to as an Application Binary Interface (ABI).

Careless changes to command numbers or data structures can break existing applications.

Important Design Rules

  • Use standard IOCTL macros to define commands.
  • Choose a suitable command-group identifier.
  • Assign stable command numbers.
  • Use fixed-width integer types in shared structures where appropriate.
  • Consider structure padding and 32-bit versus 64-bit compatibility.
  • Validate command codes and user-provided data.
  • Document the interface for application developers.
Avoid exposing kernel pointers or architecture-dependent data layouts in a user-space IOCTL ABI. Design shared structures carefully for compatibility.

11. Common Mistakes

Mistake Correct Approach
Using arbitrary command numbers without a defined interface. Use standard IOCTL macros and documented command definitions.
Assuming direction bits perform data copying. Implement explicit user-kernel data transfer.
Assuming the encoded size validates the pointer. Validate and safely copy user-space memory.
Changing command identifiers after release. Maintain a stable interface or introduce a versioned design.
Using duplicate command identifiers carelessly. Maintain a documented command-number allocation.

12. Lesson Summary

  • An IOCTL request code identifies a device-control operation.
  • Structured request codes can encode direction, type, command number and data size.
  • The direction is defined from the user-space perspective.
  • The type field identifies a command group.
  • The command number identifies a particular operation.
  • The size field encodes the associated data type size.
  • Standard macros should be used to construct request codes.
  • The driver must still validate commands and safely handle user-space memory.
