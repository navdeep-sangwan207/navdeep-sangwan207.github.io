Chapter: IOCTL and Device Control

Lesson: 4 – _IO, _IOR, _IOW and _IOWR

Prerequisites: IOCTL command structure, user-kernel data transfer and character device drivers.

Objective: Understand the four standard Linux IOCTL command-construction macros and learn to define commands for different data-transfer requirements.

1. Introduction

Linux provides standard macros to construct IOCTL request codes. These macros help encode the command type, command number, data direction and associated data type size.

The four commonly used macros are:

  • _IO
  • _IOR
  • _IOW
  • _IOWR

They are generally defined in the kernel header <linux/ioctl.h>. User-space programs commonly include <sys/ioctl.h>.

These macros construct request codes. They do not automatically transfer data. The driver must implement the required operation and safely copy data when necessary.

2. General Syntax

The general forms are:

_IO(type, number)

_IOR(type, number, data_type)

_IOW(type, number, data_type)

_IOWR(type, number, data_type)
Parameter Meaning
type Command-group identifier, commonly called the magic number.
number Command number identifying an operation.
data_type Type of data associated with the command. Used by the typed macros to encode its size.

The data type is written as a type name, not as a variable or pointer expression.

_IOR('N', 1, int)

This defines a request that returns an integer-sized value from the driver's perspective.

3. _IO Macro

_IO is used for a command that does not encode a data-transfer argument.

Syntax

_IO(type, number)

Example

#define MY_DEVICE_MAGIC 'N'

#define DEVICE_RESET \
    _IO(MY_DEVICE_MAGIC, 1)

Here:

  • 'N' identifies the command group.
  • 1 identifies the reset operation.
  • No data type is specified.

Possible Applications

  • Request a device reset.
  • Request a simple start operation.
  • Request a simple stop operation.

User-space invocation:

ioctl(fd, DEVICE_RESET);

The driver can identify the request in its IOCTL handler.

4. _IOR Macro

_IOR is used when the application reads data from the driver.

Syntax

_IOR(type, number, data_type)

Example

#define GET_DEVICE_VALUE \
    _IOR(MY_DEVICE_MAGIC, 2, int)

This request is intended to return an integer value from the driver to the application.

Kernel Driver
Data →
User Application

_IOR: User application receives data

User-Space Example

int value;

if (ioctl(fd, GET_DEVICE_VALUE, &value) == -1) {
    perror("GET_DEVICE_VALUE");
}

Driver-Side Concept

int value = 100;

/* Conceptual copy to user space */
if (copy_to_user((int __user *)arg,
                 &value,
                 sizeof(value))) {
    return -EFAULT;
}

The driver copies the result from kernel memory to the application's memory.

5. _IOW Macro

_IOW is used when the application writes data to the driver.

Syntax

_IOW(type, number, data_type)

Example

#define SET_DEVICE_VALUE \
    _IOW(MY_DEVICE_MAGIC, 3, int)

The application provides an integer value to the driver.

User Application
Data →
Kernel Driver

_IOW: User application sends data

User-Space Example

int value = 250;

if (ioctl(fd, SET_DEVICE_VALUE, &value) == -1) {
    perror("SET_DEVICE_VALUE");
}

Driver-Side Concept

int value;

if (copy_from_user(&value,
                   (int __user *)arg,
                   sizeof(value))) {
    return -EFAULT;
}

/* Validate and use value */
if (value < 0 || value > 1000)
    return -EINVAL;

The driver copies the value from user space into kernel memory and validates it before using it.

6. _IOWR Macro

_IOWR is used when data is exchanged in both directions.

Syntax

_IOWR(type, number, data_type)

Example Structure

struct device_config {
    int mode;
    int speed;
};

Command Definition

#define CONFIGURE_DEVICE \
    _IOWR(MY_DEVICE_MAGIC, 4, struct device_config)

The application supplies configuration information, and the driver may update the same structure with results or actual device settings.

User Application
↔
Kernel Driver

_IOWR: Data moves in both directions

User-Space Example

struct device_config config;

config.mode = 1;
config.speed = 100;

if (ioctl(fd, CONFIGURE_DEVICE, &config) == -1) {
    perror("CONFIGURE_DEVICE");
}

/* Driver may have updated config */
printf("Mode: %d\n", config.mode);
printf("Speed: %d\n", config.speed);

The driver should copy the structure into kernel memory, validate it, perform the operation, and copy updated results back to user space if required.

7. Comparison of the Four Macros

Macro Direction from User-Space Perspective Typical Use
_IO No encoded data-transfer argument Reset, start or stop command
_IOR Kernel to user space Retrieve device status
_IOW User space to kernel Set device configuration
_IOWR Both directions Exchange configuration and result data
The R and W letters are interpreted from the user application's perspective. _IOR means the application reads data; _IOW means the application writes data.

8. Complete Command Definition Example

The following example defines four commands for a fictional character device.

#ifndef MY_DEVICE_IOCTL_H
#define MY_DEVICE_IOCTL_H

#include <linux/ioctl.h>

#define MY_DEVICE_MAGIC 'N'

#define DEVICE_RESET \
    _IO(MY_DEVICE_MAGIC, 1)

#define GET_DEVICE_VALUE \
    _IOR(MY_DEVICE_MAGIC, 2, int)

#define SET_DEVICE_VALUE \
    _IOW(MY_DEVICE_MAGIC, 3, int)

struct device_config {
    int mode;
    int speed;
};

#define CONFIGURE_DEVICE \
    _IOWR(MY_DEVICE_MAGIC, 4, struct device_config)

#endif

This header can be shared conceptually between the kernel driver and its user-space application, provided the shared definitions are compatible with both build environments.

For a real shared header, avoid including kernel-only headers unnecessarily in user-space code. Use compatible fixed-width types and conditional includes where needed. The example above is a kernel-oriented teaching header.

9. How the Driver Handles These Commands

The driver's unlocked_ioctl callback receives the request code and argument.

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
)
{
    switch (cmd) {

        case DEVICE_RESET:
            /* Perform reset */
            return 0;

        case GET_DEVICE_VALUE:
            /* Copy value to user space */
            return 0;

        case SET_DEVICE_VALUE:
            /* Copy value from user space */
            return 0;

        case CONFIGURE_DEVICE:
            /* Exchange configuration */
            return 0;

        default:
            return -ENOTTY;
    }
}

This is a dispatch outline, not a complete functional driver. Each command must implement its required data handling, validation, synchronization and device operation.

10. Important Safety Rules

  • Never directly dereference a user-space pointer in kernel code.
  • Use copy_from_user() for input data.
  • Use copy_to_user() for output data.
  • Check the return value of each copy operation.
  • Validate all values received from user space.
  • Return -ENOTTY for unsupported requests where appropriate.
  • Do not assume the IOCTL direction bits perform copying automatically.
  • Keep command definitions and data structures compatible between driver and application.
copy_from_user() and copy_to_user() return the number of bytes not copied, not a negative error code. A nonzero return should normally be handled as an error, commonly by returning -EFAULT.

11. Common Mistakes

Mistake Correct Approach
Using _IOR when the application sends data. Use _IOW for application-to-driver data.
Using _IOW when the application receives data. Use _IOR for driver-to-application data.
Passing a variable instead of a type to the macro. Specify a data type such as int or a structure type.
Assuming the macro performs data copying. Implement copy operations in the driver.
Ignoring invalid user input. Validate all arguments and structure fields.

12. Lesson Summary

  • _IO defines a command without an encoded data-transfer argument.
  • _IOR defines a command for data returned to user space.
  • _IOW defines a command for data supplied by user space.
  • _IOWR defines a command for bidirectional data exchange.
  • The type and command number identify the request.
  • Typed macros encode the size of the associated data type.
  • The driver must implement actual data copying and validation.
  • Command definitions must remain compatible between user space and kernel space.
