Chapter: IOCTL and Device Control

Lesson: 5 – Implementing IOCTL in Character Drivers

Prerequisites: Character driver fundamentals, file_operations, ioctl command macros, copy_to_user() and copy_from_user().

Objective: Implement an IOCTL handler, connect it to file_operations and invoke commands from a user-space application.

1. Introduction

A character device driver commonly provides open(), read(), write() and release() operations. However, some device operations require more than ordinary data reading and writing.

For example, an application may need to:

  • Reset a device.
  • Change an operating mode.
  • Configure a sampling rate.
  • Retrieve device status.
  • Enable or disable a device feature.

These control operations can be implemented through the IOCTL interface.

In a character driver, IOCTL is normally implemented through the unlocked_ioctl member of the struct file_operations structure.

2. IOCTL Implementation Architecture

User Application
↓ ioctl()
VFS / IOCTL System Call Interface
↓
Driver unlocked_ioctl()
↓
Command Handler
↓
Device or Driver State

The sequence is:

  1. The application opens the device file.
  2. The application calls ioctl() with a request code and optional argument.
  3. The kernel dispatches the request to the driver's IOCTL callback.
  4. The driver checks the command.
  5. The driver performs the requested operation.
  6. The driver returns a success value or an error code.

3. IOCTL Command Header

Driver and application must agree on command definitions and data structures. A shared header is a convenient way to keep them consistent.

Example header: my_device_ioctl.h

#ifndef MY_DEVICE_IOCTL_H
#define MY_DEVICE_IOCTL_H

#include <linux/ioctl.h>

#define MY_DEVICE_MAGIC 'N'

#define DEVICE_RESET \
    _IO(MY_DEVICE_MAGIC, 1)

#define GET_DEVICE_VALUE \
    _IOR(MY_DEVICE_MAGIC, 2, int)

#define SET_DEVICE_VALUE \
    _IOW(MY_DEVICE_MAGIC, 3, int)

#endif

The three commands have different purposes:

Command Purpose
DEVICE_RESET Reset operation without an encoded data-transfer argument.
GET_DEVICE_VALUE Return an integer value to the application.
SET_DEVICE_VALUE Receive an integer value from the application.
This header is written for the kernel-side example. A production shared header should use types and conditional includes compatible with both kernel and user-space compilation environments.

4. unlocked_ioctl() Callback

The unlocked_ioctl() callback receives three parameters.

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
);
Parameter Description
file Pointer to the open file description associated with the device.
cmd IOCTL request code sent by the application.
arg Argument supplied by the application. For pointer-based commands, it contains a user-space address.

The driver generally uses a switch statement to select the required operation.

switch (cmd) {
    case DEVICE_RESET:
        /* Reset device */
        break;

    case GET_DEVICE_VALUE:
        /* Return device value */
        break;

    case SET_DEVICE_VALUE:
        /* Set device value */
        break;

    default:
        return -ENOTTY;
}

-ENOTTY is commonly returned when the driver does not recognize or support the requested IOCTL command.

5. Implementing the Driver State

For this teaching example, the driver maintains an integer value in kernel memory.

static int device_value = 0;

The variable represents a simple software-controlled device setting. It is not connected to physical hardware.

The driver will support three operations:

  • Reset the stored value to zero.
  • Return the current value to user space.
  • Accept a new value from user space.

6. Implementing the IOCTL Handler

The following handler implements all three commands.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/uaccess.h>
#include "my_device_ioctl.h"

static int device_value = 0;

static long my_ioctl(
    struct file *file,
    unsigned int cmd,
    unsigned long arg
)
{
    int value;

    switch (cmd) {

        case DEVICE_RESET:
            device_value = 0;
            pr_info("Device value reset\n");
            return 0;

        case GET_DEVICE_VALUE:

            value = device_value;

            if (copy_to_user(
                    (int __user *)arg,
                    &value,
                    sizeof(value))) {
                return -EFAULT;
            }

            return 0;

        case SET_DEVICE_VALUE:

            if (copy_from_user(
                    &value,
                    (int __user *)arg,
                    sizeof(value))) {
                return -EFAULT;
            }

            if (value < 0 || value > 1000) {
                return -EINVAL;
            }

            device_value = value;

            pr_info("Device value updated: %d\n",
                    device_value);

            return 0;

        default:
            return -ENOTTY;
    }
}

Explanation

DEVICE_RESET: Sets the stored value to zero.

GET_DEVICE_VALUE: Copies the current kernel value into the application's memory using copy_to_user().

SET_DEVICE_VALUE: Copies an integer from user space using copy_from_user(), validates its range and updates the kernel variable.

Default case: Returns -ENOTTY for unsupported requests.

The copy functions return the number of bytes not copied. A nonzero result indicates that the transfer was incomplete; this example handles it by returning -EFAULT.

7. Connecting IOCTL to file_operations

Defining the callback is not sufficient. The driver must register it in the file_operations structure.

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .unlocked_ioctl = my_ioctl,
};

When the application issues an IOCTL request on a file descriptor associated with this driver, the kernel can dispatch it to my_ioctl().

The unlocked_ioctl callback does not automatically provide a driver-specific lock. If multiple applications or threads can access shared state, the driver must implement appropriate synchronization, such as a mutex.

8. User-Space Application

The application opens the device file and sends IOCTL requests.

Example: test_ioctl.c

#include <stdio.h>
#include <stdlib.h>
#include <fcntl.h>
#include <unistd.h>
#include <sys/ioctl.h>
#include "my_device_ioctl.h"

int main(void)
{
    int fd;
    int value;

    fd = open("/dev/mydevice", O_RDWR);

    if (fd < 0) {
        perror("open");
        return EXIT_FAILURE;
    }

    /* Set a value */
    value = 250;

    if (ioctl(fd, SET_DEVICE_VALUE, &value) == -1) {
        perror("SET_DEVICE_VALUE");
        close(fd);
        return EXIT_FAILURE;
    }

    printf("Value sent to driver: %d\n", value);

    /* Read the value */
    value = 0;

    if (ioctl(fd, GET_DEVICE_VALUE, &value) == -1) {
        perror("GET_DEVICE_VALUE");
        close(fd);
        return EXIT_FAILURE;
    }

    printf("Value received from driver: %d\n", value);

    /* Reset the device */
    if (ioctl(fd, DEVICE_RESET) == -1) {
        perror("DEVICE_RESET");
        close(fd);
        return EXIT_FAILURE;
    }

    close(fd);

    return EXIT_SUCCESS;
}

The application performs the following operations:

  1. Opens /dev/mydevice.
  2. Sends 250 to the driver.
  3. Requests the stored value.
  4. Receives the value from the driver.
  5. Resets the stored value.
  6. Closes the device file.

9. Important Note About the Shared Header

The driver and application need matching IOCTL request definitions. However, the kernel-oriented header shown earlier includes <linux/ioctl.h>, whereas a user-space application normally uses <sys/ioctl.h>.

For a portable shared header, conditional compilation can select the appropriate include:

#ifndef MY_DEVICE_IOCTL_H
#define MY_DEVICE_IOCTL_H

#ifdef __KERNEL__
#include <linux/ioctl.h>
#else
#include <sys/ioctl.h>
#endif

#define MY_DEVICE_MAGIC 'N'

#define DEVICE_RESET \
    _IO(MY_DEVICE_MAGIC, 1)

#define GET_DEVICE_VALUE \
    _IOR(MY_DEVICE_MAGIC, 2, int)

#define SET_DEVICE_VALUE \
    _IOW(MY_DEVICE_MAGIC, 3, int)

#endif

Both sides must use compatible definitions. For more complex structures, use suitable fixed-width types and ensure that structure layout, alignment and padding are compatible. Drivers supporting 32-bit applications on a 64-bit kernel may also need a compat_ioctl implementation.

10. Building and Testing in Ubuntu

Before testing, the character driver must be compiled, loaded and registered, and a device node must exist. This lesson focuses on the IOCTL handler and application; it does not provide a complete registration module.

Compile the User-Space Application

gcc test_ioctl.c -o test_ioctl

Run the Application

sudo ./test_ioctl

The device node /dev/mydevice must point to the character device registered by the driver. Its major and minor numbers must match the driver's registration.

Expected Result

Value sent to driver: 250
Value received from driver: 250

The reset operation should also complete successfully. The driver may log the reset and value update operations in the kernel log.

sudo dmesg | tail
This is a software-only example. It demonstrates IOCTL dispatch and data transfer, not control of a physical peripheral. In a VirtualBox Ubuntu environment, physical hardware access requires suitable USB/device passthrough or other hardware access configuration.

11. Common Errors and Troubleshooting

Problem Possible Cause / Solution
open() fails Check whether the device node exists, its major/minor numbers and permissions.
ioctl() returns ENOTTY Check the command definition and whether the driver handles that request.
ioctl() returns EFAULT Check the user pointer and the copy operation.
ioctl() returns EINVAL The driver may have rejected an invalid value or argument.
Incorrect value returned Check the kernel state, command direction and data type.
Driver does not receive the command Check that unlocked_ioctl is registered in the correct file_operations structure.

12. Best Practices

  • Use a unique command group identifier and organize command numbers consistently.
  • Use the standard IOCTL macros rather than manually constructing request numbers.
  • Validate every value received from user space.
  • Use copy_to_user() and copy_from_user() for pointer-based data transfers.
  • Return meaningful negative kernel error codes.
  • Protect shared driver state with suitable synchronization.
  • Keep user-space and kernel-space structure definitions compatible.
  • Consider 32-bit compatibility when supporting applications with a different pointer size.
  • Do not call user-copy functions from interrupt context because they may sleep.

13. Lesson Summary

  • IOCTL provides a control interface for character device drivers.
  • unlocked_ioctl implements the driver's IOCTL callback.
  • The cmd parameter identifies the requested operation.
  • The arg parameter commonly carries a user-space pointer for data-transfer commands.
  • copy_from_user() receives application data.
  • copy_to_user() returns driver data to the application.
  • The callback is connected through file_operations.
  • The application invokes commands using the ioctl() system call.
