1. Introduction

Linux supports dynamically loading kernel modules without rebuilding or rebooting the entire operating system. This makes it possible to add certain kernel functionality while the system is running.

The insmod command is used to insert a compiled kernel module file into the currently running kernel.

A kernel module is commonly compiled into a file with the .ko extension, which stands for kernel object.

2. What Is insmod?

insmod is a Linux command-line utility that requests insertion of a specified kernel module file.

It passes the module file to the kernel through the module loading interface. The kernel then checks whether the module can be loaded and executes its initialization function if loading proceeds successfully.

Basic Syntax

sudo insmod module_name.ko

Example:

sudo insmod hello.ko

Administrative privileges are normally required because loading kernel code changes the running kernel.

3. Understanding the .ko File

The .ko file is the compiled loadable kernel module. It contains kernel code, data and module metadata.

A typical source-to-module workflow looks like this:

hello.c
↓
Kernel Build System (Kbuild)
↓
hello.ko
↓
insmod hello.ko
↓
Running Kernel

The source file is not loaded directly. It must first be compiled against the appropriate kernel build environment.

4. How insmod Works

When a user executes insmod, the following general sequence takes place:

  1. The user supplies the path to a compiled module file.
  2. The utility requests module insertion from the kernel.
  3. The kernel validates and prepares the module.
  4. Required symbol references and relocations are resolved.
  5. The module initialization function is invoked.
  6. If initialization succeeds, the module becomes loaded.
User executes insmod
↓
Module file is submitted
↓
Kernel validates module
↓
Symbols and relocations processed
↓
Initialization function executes
↓
Module becomes active

If validation or initialization fails, the insertion request fails. The kernel performs appropriate cleanup for the failed load.

5. Creating a Kernel Module for Testing

Before using insmod, create and compile a simple kernel module.

Source Code: insmod_demo.c

#include <linux/module.h>
#include <linux/init.h>

static int __init insmod_demo_init(void)
{
    pr_info("insmod_demo: Module loaded\n");

    return 0;
}

static void __exit insmod_demo_exit(void)
{
    pr_info("insmod_demo: Module removed\n");
}

module_init(insmod_demo_init);
module_exit(insmod_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Demonstration of insmod command");
MODULE_VERSION("1.0");

Makefile

obj-m += insmod_demo.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

The commands under all and clean must begin with a tab character.

Compile the Module

make

After successful compilation, the file insmod_demo.ko should be available in the current directory.

6. Loading a Module Using insmod

Use the following command to load the compiled module: 

sudo insmod insmod_demo.ko

If the command completes successfully, the module's initialization function has returned success and the module has been inserted.

Verify Module Loading

lsmod | grep insmod_demo

You can also inspect the kernel log: 

sudo dmesg | tail

Expected Kernel Log Message

insmod_demo: Module loaded

7. Loading a Module Using an Absolute Path

The module file does not need to be in a system module directory. You can supply its full path. 

sudo insmod /home/user/driver/insmod_demo.ko

Replace the example path with the actual location of your compiled module.

To load a module from the current directory, use: 

sudo insmod ./insmod_demo.ko

8. Passing Parameters to a Module

Some kernel modules accept parameters that configure their behavior during loading.

Kernel module parameters can be declared using macros such as module_param().

Example: Parameterized Module

#include <linux/module.h>
#include <linux/init.h>

static int count = 10;

module_param(count, int, 0444);

static int __init parameter_init(void)
{
    pr_info("Parameter module loaded\n");
    pr_info("count = %d\n", count);

    return 0;
}

static void __exit parameter_exit(void)
{
    pr_info("Parameter module unloaded\n");
}

module_init(parameter_init);
module_exit(parameter_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Kernel module parameter example");

Load with a Parameter

sudo insmod parameter_demo.ko count=25

The value 25 is assigned to the module parameter before its initialization function runs.

The third argument of module_param() specifies permission bits for the corresponding sysfs parameter attribute when one is exposed. A value of 0444 makes it read-only.

9. Difference Between insmod and modprobe

Both commands can load kernel modules, but their dependency-handling behavior differs.

Feature insmod modprobe
Input Normally takes a module file path. Normally takes a module name or alias.
Dependency handling Does not automatically resolve and load dependencies. Uses the module dependency database to handle dependencies.
Typical use Testing a locally compiled module. Managing installed system modules.
Module lookup User specifies the file. Searches configured module directories.

Examples

# Insert a specific module file
sudo insmod ./my_driver.ko

# Load an installed module by name
sudo modprobe my_driver
Important: modprobe uses dependency information maintained for installed modules. It does not automatically resolve dependencies for an arbitrary local module file in the same way that a direct insmod request would need them supplied.

10. Common Errors While Using insmod

Error or Symptom Possible Cause Suggested Check
File exists The module may already be loaded, or a conflicting module name may exist. Check with lsmod.
Invalid module format Module may have been built for a different or incompatible kernel. Check uname -r and modinfo.
Unknown symbol A required exported symbol may be unavailable. Inspect dependencies and kernel logs.
Operation not permitted Insufficient privileges or security policy restrictions. Check privileges and Secure Boot/module-signing policy.
No such file or directory The module file path is incorrect. Check the filename and directory.
Initialization returns an error The module's initialization function failed. Inspect the kernel log.

To inspect recent kernel messages after a failed insertion, use: 

sudo dmesg | tail -n 30

On systems where kernel logs are restricted, use the system journal: 

sudo journalctl -k -n 30

11. Kernel Compatibility and vermagic

A kernel module must be compatible with the running kernel. The compiled module includes version information commonly referred to as vermagic.

You can inspect the running kernel version using: 

uname -r

Inspect the module's version information using: 

modinfo insmod_demo.ko

Build external modules against the appropriate kernel headers and build configuration for the target kernel.

Note: Matching version strings alone do not guarantee module compatibility. Configuration, symbol availability, architecture and kernel ABI details also matter.

12. Removing the Module

After testing, remove the module using rmmod. 

sudo rmmod insmod_demo

The module's registered exit function executes during successful removal.

Verify removal:

lsmod | grep insmod_demo

If the module is no longer loaded, the command should produce no matching module entry.

13. Complete Practical Workflow

Use the following sequence to practice compiling, loading, inspecting and removing a module. 

# 1. Create a working directory
mkdir insmod_practice

# 2. Enter the directory
cd insmod_practice

# 3. Create source code and Makefile
# Use your text editor to create both files.

# 4. Compile the module
make

# 5. Inspect module metadata
modinfo insmod_demo.ko

# 6. Load the module
sudo insmod ./insmod_demo.ko

# 7. Verify loading
lsmod | grep insmod_demo

# 8. Check kernel messages
sudo dmesg | tail

# 9. Remove the module
sudo rmmod insmod_demo

# 10. Verify removal
lsmod | grep insmod_demo

# 11. Clean build files
make clean

14. Safety Considerations

  • Only load modules from trusted sources.
  • Build modules for the intended kernel and architecture.
  • Test unfamiliar modules in a virtual machine.
  • Check kernel logs after loading failures.
  • Do not force-load an incompatible module without understanding the risks.
  • Remember that kernel code runs with high privileges and can crash the system.
Ubuntu in VirtualBox is suitable for learning module compilation and basic loading. Physical GPIO, I2C and SPI experiments require suitable hardware access or an appropriate emulation environment.
