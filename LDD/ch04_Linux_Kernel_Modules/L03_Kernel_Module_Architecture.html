1. Introduction

A Linux kernel module is a separately compiled component that can be loaded into the running kernel. It extends kernel functionality without requiring the entire kernel to be rebuilt for every module change.

To understand kernel module development, it is important to understand its internal architecture, source-code organization, initialization process, operational logic and cleanup process.

A typical module contains:

  • Header files.
  • Module initialization function.
  • Module functionality.
  • Module cleanup function.
  • Module registration macros.
  • Module metadata.

4. Header Files Used in Kernel Modules

Kernel modules use Linux kernel header files instead of ordinary user-space application headers for kernel-specific functionality.

Common header files

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
HeaderPurpose
linux/module.hModule declarations, metadata macros and module-related interfaces.
linux/kernel.hKernel facilities, including logging interfaces.
linux/init.hInitialization and cleanup annotations such as __init and __exit.
linux/fs.hFile-system and character-device related definitions.
linux/slab.hKernel memory allocation interfaces such as kmalloc().
linux/interrupt.hInterrupt handling interfaces.

Only include the headers required by the functionality being implemented.

5. Module Initialization Function

The initialization function is executed when the module is successfully inserted into the running kernel.

It is commonly used to:

  • Initialize internal data structures.
  • Allocate required resources.
  • Register a device driver.
  • Register a character device.
  • Initialize hardware-related interfaces.
  • Prepare the module for operation.

Example

static int __init hello_init(void)
{
    pr_info("Hello: Module initialized\n");

    return 0;
}

The function returns an integer status. Returning 0 indicates successful initialization. A negative error code indicates failure.

The meaning of __init is discussed in the initialization and cleanup function lessons.

6. Module Operational Functions

After successful initialization, the module may provide its intended functionality through kernel interfaces.

For example, a character device driver may implement callbacks for:

  • Opening a device file.
  • Reading device data.
  • Writing device data.
  • Controlling device operations.
  • Releasing device resources.

These functions are not automatically executed merely because a module is loaded. They are invoked when the relevant kernel subsystem or user-space interaction calls them.

Conceptual example

static int device_open(struct inode *inode,
                       struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

This callback is an example of a function that could be associated with a character device's file operations. A complete character driver requires additional registration and implementation steps.

7. Module Cleanup Function

The cleanup function is executed when the module is successfully removed from the kernel.

It is responsible for releasing resources acquired by the module.

Typical cleanup operations

  • Unregistering a device driver.
  • Removing a character device.
  • Freeing allocated memory.
  • Releasing hardware resources.
  • Removing interfaces created by the module.
  • Stopping module-managed activities.

Example

static void __exit hello_exit(void)
{
    pr_info("Hello: Module cleanup completed\n");
}

A cleanup function returns void. It should release resources in a safe order and prevent further use of objects being destroyed.

8. Module Registration Macros

Linux provides macros to register the initialization and cleanup functions.

module_init()

module_init(hello_init);

Associates hello_init() with module initialization.

module_exit()

module_exit(hello_exit);

Associates hello_exit() with module removal for a loadable module.

Combined example

module_init(hello_init);
module_exit(hello_exit);

These macros provide the module lifecycle entry points. They do not themselves implement the module's device operations.

9. Module Metadata

Kernel modules can include metadata that describes their purpose and ownership.

Example

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic Linux Kernel Module");
MODULE_VERSION("1.0");
MacroPurpose
MODULE_LICENSE()Declares the module's license.
MODULE_AUTHOR()Identifies the author.
MODULE_DESCRIPTION()Describes the module.
MODULE_VERSION()Provides a module version string.

Module metadata can be inspected using the modinfo command.

10. Complete Example of Kernel Module Architecture

The following example combines the major components of a simple module.

Source file: hello_module.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

/* Initialization function */
static int __init hello_init(void)
{
    pr_info("Hello: Module initialization started\n");

    return 0;
}

/* Cleanup function */
static void __exit hello_exit(void)
{
    pr_info("Hello: Module cleanup started\n");
}

/* Register lifecycle functions */
module_init(hello_init);
module_exit(hello_exit);

/* Module metadata */
MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Example Kernel Module");
MODULE_VERSION("1.0");

Explanation of execution

  1. The kernel module loader receives the compiled module.
  2. The module is checked and prepared for loading.
  3. The initialization function is called.
  4. If initialization succeeds, the module becomes active.
  5. When removal is requested and permitted, the cleanup function is called.
  6. The module is removed from the running kernel.

11. Kernel Module Source-Code Organization

A small module may contain only one C source file. A larger driver may be divided into multiple source files and header files.

Example project structure

hello_module/
│
├── hello_module.c
├── helper.c
├── helper.h
└── Makefile

Each file has a specific responsibility:

FilePurpose
hello_module.cMain module initialization and cleanup logic.
helper.cAdditional implementation functions.
helper.hDeclarations shared between source files.
MakefileBuild instructions for the kernel module.

In larger projects, source files are organized according to functionality, such as device registration, hardware communication and interrupt handling.

12. Kernel Module Build Architecture

The Linux kernel build system, known as Kbuild, compiles module source files and generates a .ko file.

Example Makefile

obj-m += hello_module.o

all:
    make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
    make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

The Makefile must use a tab character before each recipe command.

Build command

make

Generated output

hello_module.ko

The build process may also generate intermediate files such as object files and module metadata. These are managed by the kernel build system.

14. Error Handling in Module Architecture

Initialization functions should check whether each required operation succeeds.

Example

static int __init hello_init(void)
{
    int result;

    result = some_initialization_function();

    if (result) {
        pr_err("Initialization failed\n");
        return result;
    }

    pr_info("Module initialized successfully\n");
    return 0;
}

Note: some_initialization_function() is a placeholder, not a real kernel API. A production driver should use the actual return conventions of the APIs it calls.

When initialization involves several resources, the module must release any resources already acquired if a later operation fails. This prevents resource leaks and inconsistent kernel state.

16. Important Points to Remember

  • A kernel module is a separately compiled kernel component.
  • A typical module contains initialization and cleanup functions.
  • module_init() registers the initialization function.
  • module_exit() registers the cleanup function.
  • Operational functions provide the module's actual functionality.
  • Module metadata describes the module.
  • Kbuild is used to compile kernel modules.
  • A compiled loadable module normally has a .ko extension.
  • Initialization should validate every required operation.
  • Cleanup must release resources safely.
