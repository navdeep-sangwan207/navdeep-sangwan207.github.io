1. Introduction

Linux supports two major ways of including kernel functionality in an operating system:

  1. Built-in kernel functionality: Code is compiled directly into the kernel image.
  2. Loadable kernel modules: Code is compiled separately and can be loaded into the running kernel when required.

These approaches allow Linux developers to choose how individual drivers and kernel features are incorporated into the operating system.

In kernel configuration, these choices are commonly represented by:

  • y – Build the feature into the kernel.
  • m – Build the feature as a loadable module, if modular support is available.
  • n – Do not build the feature.

2. What Is a Built-in Kernel Component?

A built-in kernel component is compiled directly into the Linux kernel image during kernel compilation.

It becomes available as part of the kernel when the system boots.

Characteristics

  • Compiled into the kernel image.
  • Available as part of the kernel after boot.
  • Does not require a separate module-loading operation.
  • Cannot be independently unloaded like a loadable module.
  • Its code is included in the kernel image even if the feature is not actively used.

Example

A system may build essential storage or filesystem support directly into the kernel so that it is available early during boot.

3. What Is a Loadable Kernel Module?

A loadable kernel module is compiled separately from the main kernel image and can be inserted into the running kernel.

It is commonly stored in a file with the .ko extension.

Characteristics

  • Compiled as a separate module.
  • Can be loaded after the system boots.
  • Can often be removed when it is no longer required.
  • Requires compatibility with the running kernel.
  • May have dependencies on other modules or kernel symbols.

Example

A USB device driver may be available as a loadable module and loaded when the corresponding device is needed.

4. Difference Between Built-in and Loadable Components

Feature Built-in Kernel Component Loadable Kernel Module
Compilation Compiled into kernel image. Compiled separately.
File representation Part of the kernel image. Usually a .ko file.
Availability Available when the kernel starts. Available after successful loading.
Loading operation No separate module insertion. Loaded using module management tools.
Removal Cannot be independently unloaded. Can often be unloaded if not in use.
Memory use Code is part of the kernel image. Module memory is allocated when loaded.
Dependency handling Resolved during kernel build and link. Module dependencies must be satisfied.
Development Often requires rebuilding the kernel. Many changes can be tested by rebuilding the module.
Typical use Essential early-boot functionality. Optional drivers and features.

5. Kernel Configuration: y, m and n

Linux kernel configuration determines whether a feature is built into the kernel, built as a module or excluded.

ConfigurationMeaningResult
yBuilt-inFeature becomes part of the kernel image.
mModuleFeature is compiled as a loadable module.
nDisabledFeature is not built.

Example

Suppose a kernel configuration option controls a particular device driver:

CONFIG_EXAMPLE_DRIVER=y

The driver is built into the kernel.

CONFIG_EXAMPLE_DRIVER=m

The driver is built as a loadable module, provided the driver supports modular compilation.

# CONFIG_EXAMPLE_DRIVER is not set

The driver is disabled in that kernel build.

These are illustrative configuration examples. Actual option names depend on the driver and kernel version.

6. Understanding Kernel Configuration Tools

Linux provides configuration tools for selecting built-in and modular kernel features.

menuconfig

make menuconfig

Provides a text-based menu interface for configuring the kernel.

nconfig

make nconfig

Provides an alternative text-based configuration interface.

oldconfig

make oldconfig

Updates an existing configuration against the kernel's current configuration options, prompting for new options as appropriate.

Check the running kernel configuration

grep CONFIG_MODULES /boot/config-$(uname -r)

On systems where the kernel configuration is available at this path, the output indicates whether loadable module support was enabled.

Important: Some distributions expose the configuration through /proc/config.gz or another location. Availability depends on the kernel build.

7. Role of CONFIG_MODULES

The kernel configuration option CONFIG_MODULES controls support for loadable kernel modules.

Enabled

CONFIG_MODULES=y

The kernel supports loadable modules.

Disabled

If module support is disabled, the kernel cannot load external modules using the normal Linux module-loading mechanism.

When building a custom kernel, this option is important if you intend to develop and test loadable device drivers.

8. Advantages of Built-in Kernel Components

  • Available immediately when the kernel starts.
  • Useful for essential boot-time functionality.
  • No separate module insertion is required.
  • Can simplify dependency availability during early boot.
  • Useful for systems with fixed hardware and tightly controlled configurations.

Limitations

  • Code is included in the kernel image.
  • It cannot be independently unloaded.
  • Changing the component generally requires rebuilding and deploying the kernel.
  • Optional functionality may increase the kernel image size.

9. Advantages of Loadable Kernel Modules

  • Can be loaded when required.
  • Can often be unloaded when no longer needed.
  • Useful for optional device support.
  • Allow separate development and testing of drivers.
  • Can reduce the amount of optional code permanently resident in the kernel.
  • Support modular distribution and maintenance of kernel features.

Limitations

  • Module loading can fail because of compatibility problems.
  • Dependencies must be resolved.
  • Modules require correct installation and management.
  • Incorrect module code can crash the kernel.
  • Some modules may be restricted by Secure Boot or kernel security policy.

10. When Should a Feature Be Built In?

Built-in functionality is appropriate when a component must be available before the system can load external modules or when it is essential to the boot process.

Typical examples

  • Essential storage-controller support required to access the root filesystem.
  • Filesystem support needed to mount the root filesystem.
  • Core kernel functionality required during early boot.
  • Features required in a fixed, minimal embedded Linux configuration.

Not every storage or filesystem driver must be built in. The correct choice depends on the boot design, initramfs contents and system configuration.

11. When Should a Feature Be a Loadable Module?

Loadable modules are appropriate when functionality is optional or when it is useful to load the feature only when required.

Typical examples

  • Optional USB device drivers.
  • Some network interface drivers.
  • Optional filesystem support.
  • Hardware-specific peripheral drivers.
  • External drivers developed and tested separately.

For embedded Linux systems, the choice depends on boot requirements, memory constraints, hardware configuration and system maintenance strategy.

12. Inspect Built-in and Loadable Features

Linux provides several ways to inspect the current kernel and its installed modules.

Check kernel version

uname -r

Check module support in kernel configuration

grep CONFIG_MODULES /boot/config-$(uname -r)

List loaded modules

lsmod

Inspect installed module directories

ls /lib/modules/$(uname -r)/

Find a module file

find /lib/modules/$(uname -r) -name '*.ko*' | head

Remember that lsmod lists loadable modules currently loaded into the kernel. Built-in components do not appear as separate loaded modules in that list.

13. Static and Dynamic Module Selection in Embedded Linux

Embedded Linux systems often use a carefully selected kernel configuration because they may have limited memory, storage and processing resources.

For example, a dedicated industrial controller may use built-in support for the hardware required to boot and operate the system, while optional peripheral drivers may be built as modules.

System requirementPossible choice
Required before root filesystem is mountedBuilt-in, or available through the initramfs boot process.
Optional peripheralLoadable module.
Fixed hardware configurationBuilt-in or module, depending on boot and maintenance needs.
Driver under active developmentLoadable module for convenient testing, where supported.
Very small system imageCarefully selected built-in and modular features.

The decision is based on system architecture rather than a universal rule that modules are always better or worse.

14. Practical Exercise: Inspect Kernel Module Support

Objective: Identify the running kernel version, check module support and inspect loaded and installed modules in Ubuntu.

Step 1: Display the kernel version

uname -r

Step 2: Check module support

grep CONFIG_MODULES /boot/config-$(uname -r)

Step 3: List currently loaded modules

lsmod

Step 4: Count loaded modules

lsmod | wc -l

The result includes the header line printed by lsmod.

Step 5: List installed module directories

ls /lib/modules/$(uname -r)/

Step 6: Locate module files

find /lib/modules/$(uname -r) -name '*.ko*' | head -n 10

Step 7: Inspect a module

modinfo loop

Expected Result

You should be able to identify the current kernel version, determine whether loadable module support is enabled, view loaded modules and inspect installed module files.

15. Important Points to Remember

  • Built-in kernel code is compiled into the kernel image.
  • Loadable modules are compiled separately.
  • The kernel configuration symbol y represents built-in functionality.
  • The symbol m represents a loadable module.
  • The symbol n disables a feature.
  • CONFIG_MODULES controls loadable module support.
  • Built-in components cannot be independently unloaded.
  • Loadable modules can often be inserted and removed at runtime.
  • Essential early-boot functionality may need to be built in or included in the initramfs.
  • The correct selection depends on the target system's requirements.
