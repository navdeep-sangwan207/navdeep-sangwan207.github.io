1. Introduction

Error handling is an essential part of Linux kernel and device driver development. A device driver interacts with hardware, manages kernel resources and provides services to userspace applications.

During these operations, different problems can occur:

  • Memory allocation may fail.
  • A device may not be available.
  • A hardware operation may time out.
  • A requested resource may already be in use.
  • A userspace request may contain invalid data.
  • A driver may fail to initialize.

Proper error handling allows a driver to detect failures, report meaningful errors, release resources and prevent system instability.

2. What Is Kernel Error Handling?

Kernel error handling is the process of detecting, reporting and recovering from failures that occur during kernel operations.

Kernel Operation
↓
Check Operation Result
↓
Success or Failure?
↓
Continue or Handle Error
↓
Return Status / Log / Cleanup

A driver should not assume that every operation succeeds. It must examine return values and handle failure conditions explicitly.

3. Common Causes of Kernel Errors

Error Source Example
Memory allocation kmalloc() returns NULL.
Invalid parameters A userspace application sends an unsupported value.
Hardware failure A peripheral does not respond as expected.
Resource conflict A device resource is already reserved.
Permission problem An operation is not permitted.
Timeout A device does not complete an operation within the expected time.
Initialization failure A required subsystem or resource cannot be initialized.

4. Kernel Error Codes

Linux kernel functions commonly report failures using negative error codes. These codes indicate the type of failure.

The kernel defines standard error constants in <linux/errno.h> and related headers.

Error Code Meaning Typical Situation
-EINVAL Invalid argument Invalid function parameter.
-ENOMEM Out of memory Memory allocation failure.
-ENODEV No such device Requested device is unavailable.
-EBUSY Device or resource busy Resource is already in use.
-EIO Input/output error Hardware or I/O operation failed.
-ETIMEDOUT Operation timed out Device did not respond in time.
-EACCES Permission denied Access is not permitted.
-EFAULT Bad address Invalid userspace memory address.
-EEXIST File or resource already exists Duplicate resource or entry.
-ENOENT No such entry Requested object or entry is missing.
Kernel functions normally return negative error values. Do not confuse these with the positive errno values commonly observed by userspace applications.

5. Returning Errors from Kernel Functions

A kernel function can return an integer status value. Zero commonly indicates success, while a negative value indicates failure.

Example

#include <linux/errno.h>

static int validate_value(int value)
{
    if (value < 0)
        return -EINVAL;

    return 0;
}

The caller should inspect the returned status before continuing. 

int ret;

ret = validate_value(10);

if (ret < 0) {
    pr_err("Invalid value\n");
    return ret;
}

pr_info("Value accepted\n");

6. Error Handling in Module Initialization

The module initialization function returns an integer. Returning zero indicates successful initialization. Returning a negative error code indicates failure.

Example

#include <linux/module.h>
#include <linux/init.h>
#include <linux/errno.h>
#include <linux/printk.h>

static int __init error_demo_init(void)
{
    int device_available = 0;

    if (!device_available) {
        pr_err("Required device is unavailable\n");
        return -ENODEV;
    }

    pr_info("Module initialized successfully\n");

    return 0;
}

static void __exit error_demo_exit(void)
{
    pr_info("Module removed\n");
}

module_init(error_demo_init);
module_exit(error_demo_exit);

MODULE_LICENSE("GPL");

In this example, initialization fails because the required device is unavailable. The kernel receives the negative error code.

The device_available variable is only a simplified demonstration. Real drivers detect device availability through their relevant bus, device and subsystem interfaces.

7. Error Handling During Memory Allocation

Memory allocation is a common source of errors in kernel programming. A driver must check the returned pointer before using it. 

#include <linux/module.h>
#include <linux/slab.h>
#include <linux/errno.h>
#include <linux/printk.h>

static char *buffer;

static int __init allocation_demo_init(void)
{
    buffer = kmalloc(1024, GFP_KERNEL);

    if (!buffer) {
        pr_err("Memory allocation failed\n");
        return -ENOMEM;
    }

    pr_info("Memory allocated successfully\n");

    return 0;
}

static void __exit allocation_demo_exit(void)
{
    kfree(buffer);
    buffer = NULL;

    pr_info("Memory released\n");
}

module_init(allocation_demo_init);
module_exit(allocation_demo_exit);

MODULE_LICENSE("GPL");

If memory allocation fails, the initialization function returns -ENOMEM.

8. Resource Cleanup After Initialization Failure

A driver may acquire several resources during initialization. If a later operation fails, previously acquired resources must be released.

Example Scenario

  1. Allocate memory.
  2. Acquire another required resource.
  3. The second operation fails.
  4. Release the memory allocated in step 1.
  5. Return the appropriate error code.
Start Initialization
↓
Allocate Memory
↓
Acquire Resource
↓
Did It Succeed?
↓
No → Release Memory → Return Error
↓
Yes → Continue Initialization

Example Code

#include <linux/module.h>
#include <linux/init.h>
#include <linux/slab.h>
#include <linux/errno.h>
#include <linux/printk.h>

static char *buffer;

static int acquire_resource(void)
{
    /* Demonstration: simulate a failure. */
    return -EBUSY;
}

static int __init cleanup_demo_init(void)
{
    int ret;

    buffer = kmalloc(1024, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    ret = acquire_resource();

    if (ret) {
        pr_err("Resource acquisition failed\n");

        kfree(buffer);
        buffer = NULL;

        return ret;
    }

    pr_info("Initialization successful\n");

    return 0;
}

static void __exit cleanup_demo_exit(void)
{
    kfree(buffer);
    buffer = NULL;

    pr_info("Cleanup completed\n");
}

module_init(cleanup_demo_init);
module_exit(cleanup_demo_exit);

MODULE_LICENSE("GPL");

Here, the simulated resource acquisition fails. Therefore, the memory is released before the initialization function returns.

If module initialization returns an error, the module does not become successfully loaded and its normal module exit function is not called. Initialization code must therefore release resources it acquired before returning an error.

9. Error Handling Using goto

In kernel code, goto is commonly used for structured cleanup when a function acquires multiple resources.

Each error label releases the resources that were successfully acquired before that point.

Example

static int __init goto_demo_init(void)
{
    char *buffer1;
    char *buffer2;

    buffer1 = kmalloc(100, GFP_KERNEL);

    if (!buffer1)
        return -ENOMEM;

    buffer2 = kmalloc(200, GFP_KERNEL);

    if (!buffer2)
        goto err_free_buffer1;

    pr_info("Both buffers allocated\n");

    kfree(buffer2);
    kfree(buffer1);

    return 0;

err_free_buffer1:
    kfree(buffer1);
    return -ENOMEM;
}

This simplified function demonstrates reverse-order cleanup. In a real module, successfully acquired resources would normally remain available until the module's cleanup path releases them.

10. Logging Errors Using printk() and pr_err()

Kernel messages help developers identify failures during module initialization and runtime operation.

Logging Function Purpose
pr_info() Reports informational messages.
pr_warn() Reports warning conditions.
pr_err() Reports error conditions.
pr_debug() Reports debugging messages when enabled by the applicable configuration.

Example

if (!buffer) {
    pr_err("Unable to allocate buffer\n");
    return -ENOMEM;
}

pr_info("Buffer allocated successfully\n");

Use messages that describe the operation and failure clearly. Avoid excessive logging in frequently executed paths.

11. Handling Invalid Function Arguments

Kernel functions should validate their inputs before performing operations.

Example

#include <linux/errno.h>

static int set_device_value(int value)
{
    if (value < 0 || value > 100)
        return -EINVAL;

    /* Process the valid value. */

    return 0;
}

The function accepts values from 0 to 100. Values outside that range produce -EINVAL.

12. Handling Errors in Userspace Data Transfer

Character device drivers often exchange data with userspace applications using functions such as copy_to_user() and copy_from_user().

These functions return the number of bytes that could not be copied. A return value of zero means the complete transfer succeeded.

Example

#include <linux/uaccess.h>
#include <linux/errno.h>

static int copy_example(char __user *user_buffer,
                        const char *kernel_buffer,
                        unsigned long length)
{
    if (copy_to_user(user_buffer, kernel_buffer, length))
        return -EFAULT;

    return 0;
}
The example demonstrates the error check only. Complete read and write callbacks must also handle file offsets, partial transfers and the appropriate return-value conventions. These topics are covered in Chapter 9 – File Operations and User-Kernel Data Transfer.

13. Best Practices for Kernel Error Handling

  • Check return values from functions that can fail.
  • Return meaningful negative error codes.
  • Use -EINVAL for invalid arguments.
  • Use -ENOMEM for allocation failures.
  • Use -ENODEV when the required device is unavailable.
  • Release acquired resources on every failure path.
  • Use clear error messages with pr_err().
  • Avoid hiding errors by returning success after a failure.
  • Prevent resource leaks and invalid memory access.
  • Keep cleanup paths understandable and consistent.

14. Lesson Summary

  • Kernel error handling detects and manages failures.
  • Kernel functions commonly return negative error codes.
  • Zero commonly indicates successful completion.
  • -EINVAL indicates an invalid argument.
  • -ENOMEM indicates memory allocation failure.
  • Initialization functions must clean up resources before returning an error.
  • goto can simplify multi-resource cleanup paths.
  • pr_err() helps report errors in kernel logs.
  • Userspace data transfer functions require explicit error checking.
