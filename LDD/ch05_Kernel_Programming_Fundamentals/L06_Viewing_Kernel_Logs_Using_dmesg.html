1. Introduction

During Linux kernel and device driver development, developers need to inspect messages generated by the kernel and loaded modules.

These messages help identify module loading problems, hardware detection failures, memory allocation errors, driver initialization issues and other kernel events.

Linux provides the dmesg command to display messages from the kernel ring buffer.

2. What Is dmesg?

dmesg stands for display message. It is a Linux command-line utility used to read and display messages from the kernel ring buffer.

The kernel records messages from its subsystems, device drivers and other kernel components. These messages can be examined using dmesg.

Kernel / Device Driver
↓

3. What Is the Kernel Ring Buffer?

The kernel ring buffer is a memory area used to store kernel log messages. It is called a ring buffer because new entries can overwrite older entries when the available buffer space is exhausted.

The buffer is managed by the kernel. It stores messages generated during system startup and normal operation.

Important Characteristics

  • Stores kernel log messages in memory.
  • Receives messages from kernel subsystems and drivers.
  • Has a limited capacity.
  • Older messages may be overwritten by newer messages.
  • Can be inspected using dmesg.

4. Basic dmesg Command

The simplest way to display kernel messages is: 

dmesg

This displays the available messages from the kernel ring buffer.

Example Output

[    0.000000] Linux version ...
[    0.125000] Initializing cgroup subsys cpuset
[    1.250000] CPU: detected processor
[    2.100000] Kernel command line: ...
[    5.320000] systemd[1]: Starting system services

The output above is illustrative. Actual messages depend on the kernel version, hardware and installed system services.

5. Understanding Kernel Log Timestamps

Kernel messages commonly contain timestamps enclosed in square brackets. 

[  125.450000] Device driver initialized

In this example, the timestamp indicates approximately 125.45 seconds after the kernel's time reference established during boot.

Part Meaning
[ Beginning of the timestamp.
125.450000 Time value in seconds.
] End of the timestamp.
Message text Kernel event or diagnostic information.

6. Display Recent Kernel Messages

Kernel logs can be lengthy. The tail command can display only the most recent lines.

Display Last 10 Lines

dmesg | tail

Display Last 20 Lines

dmesg | tail -n 20

Display Last 50 Lines

dmesg | tail -n 50

This is particularly useful after loading or removing a kernel module.

7. Display Kernel Logs with Human-Readable Timestamps

The -T option asks dmesg to display timestamps in a human-readable date and time format. 

dmesg -T

Example Output

[Wed Nov 11 18:30:10 2026] Driver initialized

Human-readable timestamps are useful when correlating kernel events with other system logs.

The converted timestamps may be approximate, especially when system time changes occur. The monotonic-style timestamps are generally useful for examining event order and elapsed time.

8. Follow Kernel Messages in Real Time

The -w option makes dmesg wait for and display new messages as they are added to the kernel ring buffer. 

sudo dmesg -w

Use Case

  1. Open a terminal.
  2. Run sudo dmesg -w.
  3. Keep the terminal running.
  4. Load or remove a kernel module in another terminal.
  5. Observe the new kernel messages.

Press Ctrl + C to stop following the log.

9. Filter Kernel Messages by Priority

The --level option filters messages according to their kernel log priorities.

Display Error Messages

sudo dmesg --level=err

Display Warning and Error Messages

sudo dmesg --level=warn,err

Display Informational Messages

sudo dmesg --level=info

Display Messages from Multiple Levels

sudo dmesg --level=err,warn,notice

The level filter uses message priority, not the console log-level setting.

10. Search Kernel Messages Using grep

The grep command can search kernel log output for a particular word or message.

Search for Error Messages

dmesg | grep -i error

Search for Warning Messages

dmesg | grep -i warning

Search for a Device Name

dmesg | grep -i usb

Search for a Driver Name

dmesg | grep -i logging_demo

The -i option performs a case-insensitive search.

11. Clear the Kernel Ring Buffer

The -C option clears the kernel ring buffer when permitted by the system. 

sudo dmesg -C

After clearing, new kernel messages can be observed without older entries in the buffer.

Clearing the ring buffer is generally unnecessary for routine driver debugging. Do not clear logs on a production system when those messages may be needed for troubleshooting or incident investigation.

12. Display Kernel Messages with Log-Level Information

The -x option displays additional information about message facilities and priorities where available. 

dmesg -x

This can help identify the classification of messages while examining kernel logs.

13. Save Kernel Logs to a File

Kernel messages can be redirected to a file for later analysis.

Save Complete Available Output

dmesg > kernel_logs.txt

Append New Output to an Existing File

dmesg >> kernel_logs.txt

Save Only Error Messages

sudo dmesg --level=err > kernel_errors.txt

Read the Saved File

cat kernel_logs.txt

Saving logs is useful for comparing behavior before and after driver changes.

14. dmesg and systemd Journal

Modern Linux distributions commonly use systemd's journal service to collect system and kernel messages.

Display Kernel Messages from the Journal

journalctl -k

Display Kernel Messages from the Current Boot

journalctl -k -b

Follow New Kernel Messages

sudo journalctl -k -f

Display Kernel Messages from the Previous Boot

journalctl -k -b -1

Access to previous-boot journal entries depends on whether persistent journal storage is enabled.

Command Purpose
dmesg Reads the kernel ring buffer.
journalctl -k Displays kernel messages collected by the systemd journal.
journalctl -k -f Follows new kernel messages in the journal.

15. Debugging Kernel Modules Using dmesg

During module development, dmesg helps verify whether initialization and cleanup functions execute successfully.

Example Kernel Module

#include <linux/module.h>
#include <linux/init.h>
#include <linux/printk.h>

static int __init dmesg_demo_init(void)
{
    pr_info("dmesg_demo: Module initialized\n");
    return 0;
}

static void __exit dmesg_demo_exit(void)
{
    pr_info("dmesg_demo: Module removed\n");
}

module_init(dmesg_demo_init);
module_exit(dmesg_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("dmesg demonstration module");

Compile the Module

make

Load the Module

sudo insmod dmesg_demo.ko

Search for Its Message

sudo dmesg | grep dmesg_demo

Remove the Module

sudo rmmod dmesg_demo

Check Again

sudo dmesg | grep dmesg_demo

You should find the initialization and removal messages if they remain in the ring buffer and are accessible to your account.

16. Common dmesg Commands Reference

Command Description
dmesg Display kernel messages.
dmesg -T Display human-readable timestamps.
dmesg -w Follow new kernel messages.
dmesg | tail Display recent messages.
dmesg | grep error Search for error text.
dmesg --level=err Filter error-priority messages.
dmesg -x Display facility and priority information where available.
dmesg -C Clear the kernel ring buffer.
journalctl -k Display kernel messages from the systemd journal.

17. Common Problems and Solutions

Problem Possible Cause Solution
Operation not permitted Kernel log access is restricted. Try sudo dmesg if authorized.
Module message not found Module did not load, message was overwritten, or search text differs. Check module status and search the exact message.
Too much output Large number of kernel messages. Use tail, grep or --level.
Old messages missing Ring buffer capacity was exceeded or cleared. Use journal logs if the messages were collected and retained.
Previous boot logs unavailable Persistent journal storage may not be enabled. Check systemd journal configuration.

18. Best Practices for Kernel Log Analysis

  • Inspect logs immediately after loading or removing a module.
  • Use grep to isolate messages from a particular driver.
  • Use timestamps to understand event order.
  • Filter by priority when investigating errors.
  • Compare logs before and after code modifications.
  • Use journalctl -k when historical journal data is needed.
  • Avoid clearing the ring buffer unnecessarily.
  • Record relevant diagnostic output when reporting a driver bug.
