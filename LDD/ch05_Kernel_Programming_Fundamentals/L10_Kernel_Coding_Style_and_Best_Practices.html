1. Introduction

Linux kernel development requires more than writing code that compiles successfully. Kernel code must also be readable, maintainable, efficient and safe.

A Linux device driver interacts directly with kernel services, hardware interfaces and shared system resources. Poor programming practices can cause:

  • Kernel crashes and system instability.
  • Memory leaks and invalid memory access.
  • Race conditions and synchronization problems.
  • Resource conflicts.
  • Unnecessary performance overhead.
  • Difficult debugging and maintenance.

Linux kernel coding style provides conventions that help developers maintain consistent source code.

2. What Is Linux Kernel Coding Style?

Linux kernel coding style is a set of conventions and recommendations for writing kernel source code.

These conventions cover:

  • Indentation and formatting.
  • Variable and function naming.
  • Comments and documentation.
  • Function structure.
  • Error handling.
  • Memory management.
  • Header file organization.

3. Linux Kernel Coding Style Documentation

The Linux kernel source tree contains an official coding-style document: 

Documentation/process/coding-style.rst

This document describes conventions followed by Linux kernel developers. It is useful when writing modules and preparing code for kernel development.

The document is maintained in the official Linux kernel source repository.

4. Indentation and Formatting

Consistent indentation makes kernel source code easier to read and review.

Linux kernel style generally uses tabs for indentation, with a standard display width of eight columns.

Incorrect Formatting

static int example(void)
{
int value=10;
if(value>0){
pr_info("Positive\n");
}
return 0;
}

Improved Formatting

static int example(void)
{
	int value = 10;

	if (value > 0) {
		pr_info("Positive\n");
	}

	return 0;
}

Notice the consistent indentation, spacing and placement of braces.

5. Naming Conventions

Meaningful names help developers understand the purpose of variables, functions and structures.

Element Recommended Style Example
Variables Descriptive lowercase names device_count
Functions Descriptive lowercase names device_init()
Structures Descriptive names struct device_data
Constants Often uppercase where appropriate MAX_BUFFER_SIZE

Example

/* Less descriptive */
int x;
int y;

/* More descriptive */
int device_count;
int buffer_size;

Names should explain the role of the object without becoming unnecessarily long.

6. Braces and Conditional Statements

Kernel code generally places the opening brace of a function on the next line. Control statements follow the kernel's established formatting style.

Example

static int check_device(int status)
{
	if (status == 0) {
		pr_info("Device ready\n");
		return 0;
	}

	pr_err("Device not ready\n");
	return -ENODEV;
}

Braces make the scope of conditional blocks clear and help prevent accidental logic errors.

7. Function Design

Functions should have a clear purpose. Avoid putting unrelated operations into one large function.

Good Function Design

static int allocate_device_buffer(void)
{
	/* Allocation logic */
	return 0;
}

static void release_device_buffer(void)
{
	/* Cleanup logic */
}

static int initialize_device(void)
{
	/* Device initialization logic */
	return 0;
}

Separating operations into smaller functions improves readability, testing and maintenance.

8. Variable Declaration and Initialization

Variables should be declared clearly and initialized before use.

Example

static int __init variable_demo_init(void)
{
	int status = 0;
	int device_count = 0;

	status = device_count + 1;

	pr_info("Device count: %d\n", status);

	return 0;
}

Avoid using uninitialized variables because their contents are unpredictable.

9. Header File Organization

Kernel source files should include the headers required for the APIs and definitions they use.

Example

#include <linux/module.h>
#include <linux/init.h>
#include <linux/kernel.h>
#include <linux/slab.h>
#include <linux/errno.h>
#include <linux/printk.h>
Header File Purpose
linux/module.h Kernel module definitions and metadata.
linux/init.h Module initialization and exit annotations.
linux/kernel.h General kernel definitions and utilities.
linux/slab.h Kernel allocation interfaces such as kmalloc().
linux/errno.h Kernel error-code definitions.
linux/printk.h Kernel logging interfaces.

Include only the headers required by the source file. Do not rely on unrelated headers to indirectly include definitions.

10. Comments and Documentation

Comments should explain why a particular operation is required, especially when the logic is not immediately obvious.

Example

/*
 * Allocate a buffer for storing device data.
 * The buffer is released during module cleanup.
 */
buffer = kmalloc(1024, GFP_KERNEL);

if (!buffer)
	return -ENOMEM;

Avoid comments that simply repeat what the code already makes obvious.

11. Error Handling Best Practices

Every operation that can fail should be checked according to its documented return-value convention.

Example

static int __init error_check_demo_init(void)
{
	char *buffer;

	buffer = kmalloc(128, GFP_KERNEL);

	if (!buffer) {
		pr_err("Memory allocation failed\n");
		return -ENOMEM;
	}

	pr_info("Memory allocated successfully\n");

	kfree(buffer);

	return 0;
}

This example checks the allocation result and releases the memory after use.

12. Memory Management Best Practices

  • Use the appropriate kernel allocation API.
  • Check allocation results before accessing memory.
  • Release memory when it is no longer required.
  • Avoid double-free and use-after-free errors.
  • Do not use userspace malloc() and free() in kernel code.
  • Avoid large local arrays on the limited kernel stack.
  • Use the correct allocation flags for the execution context.
  • Maintain clear ownership of allocated memory.

13. Concurrency and Synchronization Practices

Multiple execution contexts may access shared driver data. For example, a process context and an interrupt handler may interact with the same device state.

Without appropriate synchronization, race conditions can occur.

Recommended Practices

  • Identify shared data before implementing callbacks.
  • Protect critical sections using suitable synchronization primitives.
  • Use mutexes in sleepable contexts where appropriate.
  • Use spinlocks for short critical sections that cannot sleep.
  • Never hold a spinlock while performing a sleepable operation.
  • Consider lock ordering to prevent deadlocks.
Synchronization is covered in detail in Chapter 13 – Synchronization and Concurrency.

14. Avoiding Common Kernel Programming Mistakes

Mistake Potential Result Better Practice
Ignoring return values Undetected failures. Check operation results.
Uninitialized pointers Invalid memory access. Initialize pointers before use.
Memory leaks Kernel memory consumption increases. Implement complete cleanup paths.
Wrong allocation flags Sleeping in a non-sleepable context. Choose flags based on execution context.
Excessive logging Kernel log flooding and performance overhead. Use appropriate log levels and frequencies.
Unprotected shared data Race conditions. Use appropriate synchronization.
Incorrect resource cleanup Resource leaks or invalid operations. Track ownership and release resources correctly.

15. Using checkpatch.pl

The Linux kernel source tree includes a script named checkpatch.pl. It helps identify coding-style issues and some common patch problems.

It is commonly used when reviewing patches or checking kernel source changes.

Example Command

./scripts/checkpatch.pl --file driver.c

To inspect a patch file, use: 

./scripts/checkpatch.pl patch-file.patch

The script can report formatting and style issues. It does not prove that the driver is correct, secure or free of runtime bugs.

16. Kernel Code Compilation and Warning Checks

Compiler warnings can reveal potential programming errors. Developers should understand and resolve relevant warnings rather than ignoring them.

Build a Kernel Module

make

Build with Additional Warning Checks

make W=1

The exact warnings depend on the kernel version, compiler and build configuration. Additional warnings should be reviewed rather than treated automatically as proof of a bug.

17. Complete Practical Kernel Module

The following example combines several coding practices:

  • Meaningful variable names.
  • Appropriate header files.
  • Memory allocation checking.
  • Kernel logging.
  • Correct memory cleanup.

Source Code: coding_style_demo.c

#include <linux/module.h>
#include <linux/init.h>
#include <linux/slab.h>
#include <linux/errno.h>
#include <linux/printk.h>

#define DEVICE_BUFFER_SIZE 128

static char *device_buffer;

static int __init coding_style_demo_init(void)
{
	device_buffer = kzalloc(DEVICE_BUFFER_SIZE,
				GFP_KERNEL);

	if (!device_buffer) {
		pr_err("Unable to allocate device buffer\n");
		return -ENOMEM;
	}

	pr_info("Device buffer allocated successfully\n");

	return 0;
}

static void __exit coding_style_demo_exit(void)
{
	kfree(device_buffer);
	device_buffer = NULL;

	pr_info("Device buffer released\n");
}

module_init(coding_style_demo_init);
module_exit(coding_style_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Kernel coding style demonstration");

Makefile

obj-m += coding_style_demo.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Use a tab character before each recipe command in the Makefile.

Compile the Module

make

Load the Module

sudo insmod coding_style_demo.ko

Check Kernel Messages

sudo dmesg | tail -n 15

Remove the Module

sudo rmmod coding_style_demo

Expected Messages

Device buffer allocated successfully
Device buffer released

19. Lesson Summary

  • Linux kernel coding style improves consistency and readability.
  • Use meaningful names for variables, functions and structures.
  • Follow consistent indentation and formatting.
  • Include the appropriate kernel header files.
  • Check return values and handle failures.
  • Manage memory and other resources carefully.
  • Protect shared data using suitable synchronization.
  • Use checkpatch.pl to identify style issues.
  • Review compiler warnings and test modules systematically.
