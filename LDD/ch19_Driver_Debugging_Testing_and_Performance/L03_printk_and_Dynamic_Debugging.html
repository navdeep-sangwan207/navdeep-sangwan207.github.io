Lesson: L03 – printk() and Dynamic Debugging
Level: Intermediate
Focus: Kernel logging, log levels, printk(), pr_*() macros and dynamic debug

1. Introduction

Kernel logging is one of the most widely used techniques for debugging Linux device drivers. Developers insert diagnostic messages into kernel code to understand execution flow, inspect variable values and identify errors.

The Linux kernel provides the printk() function and convenient logging macros such as pr_info(), pr_err() and pr_debug().

Dynamic debugging allows selected debug messages to be enabled or disabled at runtime without recompiling the kernel or module.

2. Understanding printk()

printk() is a kernel logging function used to print messages into the kernel log buffer.

Unlike the user-space printf() function, printk() executes in kernel space and supports kernel-specific log levels.

Basic Syntax

printk(KERN_INFO "Driver initialized\n");

Example

#include <linux/module.h>
#include <linux/init.h>
#include <linux/kernel.h>

static int __init demo_init(void)
{
    printk(KERN_INFO "Demo driver initialized\n");
    return 0;
}

static void __exit demo_exit(void)
{
    printk(KERN_INFO "Demo driver removed\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");

3. Kernel Log Levels

Linux defines several log levels to indicate the importance of a kernel message.

MacroPriorityMeaning
KERN_EMERG0System is unusable.
KERN_ALERT1Immediate action required.
KERN_CRIT2Critical conditions.
KERN_ERR3Error conditions.
KERN_WARNING4Warning conditions.
KERN_NOTICE5Normal but significant condition.
KERN_INFO6Informational message.
KERN_DEBUG7Debug-level message.

Example

printk(KERN_ERR "Device registration failed\n");
printk(KERN_WARNING "Device configuration warning\n");
printk(KERN_INFO "Device initialized\n");
printk(KERN_DEBUG "Debug information\n");
The priority indicates message severity. Whether a message appears on the active console depends on the console log level and system configuration. Messages may still be available in the kernel log buffer.

4. pr_*() Logging Macros

The kernel provides convenient logging macros that avoid repeatedly writing the KERN_* prefix.

MacroPurpose
pr_emerg()Emergency message
pr_alert()Alert message
pr_crit()Critical message
pr_err()Error message
pr_warn()Warning message
pr_notice()Notice message
pr_info()Informational message
pr_debug()Debug message

Example

pr_info("Device initialized\n");
pr_err("Device registration failed\n");
pr_warn("Configuration value is unusual\n");
pr_debug("Register value = %d\n", value);

Advantages

  • Improves source-code readability.
  • Uses standard kernel log levels.
  • Provides consistent logging style.
  • Supports dynamic debug for appropriate debug call sites.

5. dev_*() Logging Macros

When a driver has access to a struct device pointer, device-specific logging macros can add device context to messages.

MacroPurpose
dev_err()Device-related error
dev_warn()Device-related warning
dev_notice()Device-related notice
dev_info()Device-related information
dev_dbg()Device-related debug message

Example

static int my_probe(struct platform_device *pdev)
{
    struct device *dev = &pdev->dev;

    dev_info(dev, "Device probe started\n");

    return 0;
}

Device-specific logging is particularly useful when the same driver manages multiple hardware devices.

6. Kernel Ring Buffer

Kernel log messages are stored in a kernel-managed ring buffer. The buffer has a limited capacity, so older messages may be overwritten as new messages arrive.

6.1 Display Kernel Messages

dmesg

6.2 Display Recent Messages

dmesg | tail -n 30

6.3 Follow New Messages

dmesg -w

6.4 Display Human-Readable Timestamps

dmesg -T

6.5 Clear the Ring Buffer

sudo dmesg -C
Clearing the ring buffer removes existing messages from that buffer. It does not repair a driver problem and may remove useful diagnostic evidence. Save relevant logs before clearing them.

7. Console Log Level

The console log level determines which messages are printed to the kernel console. It is separate from the existence of messages in the kernel log buffer.

7.1 Inspect Console Settings

cat /proc/sys/kernel/printk

The output contains four integer values representing current console and default message-level settings.

7.2 Change Console Log Level

sudo dmesg -n 7

This changes the console log level to show messages up to debug priority, subject to system configuration.

7.3 Restore a Typical Default Level

sudo dmesg -n 4

8. Dynamic Debugging

Dynamic debug provides runtime control over selected debug messages compiled using pr_debug(), dev_dbg() and related supported debug call sites.

It is especially useful when a driver contains many debug messages but only a small subset is required for a particular investigation.

8.1 Check Kernel Support

grep CONFIG_DYNAMIC_DEBUG /boot/config-$(uname -r)

8.2 Check debugfs

mount | grep debugfs

If debugfs is supported but not mounted, it can be mounted using:

sudo mount -t debugfs none /sys/kernel/debug

8.3 Locate Dynamic Debug Control

ls /sys/kernel/debug/dynamic_debug/

The control interface is commonly:

/sys/kernel/debug/dynamic_debug/control

8.4 Display Available Debug Call Sites

sudo cat /sys/kernel/debug/dynamic_debug/control

8.5 Enable Debug Messages for a Module

echo 'module my_driver +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

8.6 Disable Debug Messages for a Module

echo 'module my_driver -p' | sudo tee /sys/kernel/debug/dynamic_debug/control

8.7 Enable Messages for a Source File

echo 'file my_driver.c +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

8.8 Enable Messages for a Function

echo 'func my_probe +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

8.9 Enable Messages for a Line Range

echo 'file my_driver.c:100-150 +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

8.10 Disable All Selected Messages

echo 'module my_driver -p' | sudo tee /sys/kernel/debug/dynamic_debug/control
Dynamic debug cannot enable arbitrary messages that were not compiled into the kernel or module. Its control syntax and available call sites depend on kernel configuration and version.

9. Practical Project: printk() Logging

Objective: Create a kernel module that uses different logging levels and inspect the resulting messages.

9.1 Source Code: printk_demo.c

#include <linux/module.h>
#include <linux/init.h>
#include <linux/kernel.h>

static int __init printk_demo_init(void)
{
    pr_emerg("printk_demo: emergency example\n");
    pr_alert("printk_demo: alert example\n");
    pr_crit("printk_demo: critical example\n");
    pr_err("printk_demo: error example\n");
    pr_warn("printk_demo: warning example\n");
    pr_notice("printk_demo: notice example\n");
    pr_info("printk_demo: informational example\n");
    pr_debug("printk_demo: debug example\n");

    return 0;
}

static void __exit printk_demo_exit(void)
{
    pr_info("printk_demo: module removed\n");
}

module_init(printk_demo_init);
module_exit(printk_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("printk logging demonstration");

9.2 Makefile

obj-m += printk_demo.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

9.3 Compile and Load

make
sudo insmod printk_demo.ko

9.4 Inspect Messages

dmesg | tail -n 30

9.5 Unload the Module

sudo rmmod printk_demo

Expected result: The kernel log contains the demonstration messages with their corresponding priorities. The pr_debug() message may require dynamic debug to be enabled.

10. Practical Project: Dynamic Debugging

Objective: Enable and disable debug messages without rebuilding the module.

10.1 Source Code: dynamic_demo.c

#include <linux/module.h>
#include <linux/init.h>
#include <linux/printk.h>

static int __init dynamic_demo_init(void)
{
    pr_info("dynamic_demo: module initialized\n");
    pr_debug("dynamic_demo: initialization debug message\n");

    return 0;
}

static void __exit dynamic_demo_exit(void)
{
    pr_info("dynamic_demo: module cleanup\n");
    pr_debug("dynamic_demo: cleanup debug message\n");
}

module_init(dynamic_demo_init);
module_exit(dynamic_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Dynamic debugging demonstration");

10.2 Makefile

obj-m += dynamic_demo.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

10.3 Build the Module

make

10.4 Enable Debug Messages

Ensure the dynamic debug control file is available. Enable messages for the module before loading it:

echo 'module dynamic_demo +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

10.5 Load the Module

sudo insmod dynamic_demo.ko
dmesg | tail -n 20

10.6 Disable Debug Messages

echo 'module dynamic_demo -p' | sudo tee /sys/kernel/debug/dynamic_debug/control

10.7 Remove the Module

sudo rmmod dynamic_demo

Expected result: Informational messages appear normally. Debug messages appear when their call sites are enabled through dynamic debug.

12. Best Practices for Kernel Logging

  • Use the appropriate severity level.
  • Prefer pr_*() macros for ordinary driver logging.
  • Use dev_*() macros when device context is available.
  • Include useful device identifiers and relevant values.
  • Avoid excessive messages in high-frequency paths.
  • Do not print sensitive data.
  • Use dynamic debug for detailed diagnostic messages.
  • Do not rely on console output as the only source of diagnostic information.
  • Remove temporary noisy logging before production deployment.

13. Troubleshooting

Problem 1: pr_debug() Messages Are Not Visible

Check dynamic debug support and enable the relevant call sites.

Problem 2: Dynamic Debug Control File Is Missing

Check CONFIG_DYNAMIC_DEBUG and ensure debugfs is mounted.

Problem 3: Messages Do Not Appear on the Console

Check the console log level. The messages may still be present in the kernel ring buffer.

Problem 4: Important Messages Are Missing

The ring buffer may have overwritten older messages. Capture logs while reproducing the issue.

Problem 5: Too Many Messages Are Generated

Reduce logging frequency, use appropriate log levels and enable only the required dynamic debug call sites.

15. Interview Questions and Answers

Q1. What is printk()?

printk() is a kernel logging function used to write messages into the kernel log buffer.

Q2. What is the difference between printf() and printk()?

printf() is a user-space C library function, whereas printk() is a kernel logging function.

Q3. What is KERN_INFO?

It is a kernel log-level prefix for informational messages.

Q4. What is pr_debug()?

It is a kernel macro used to generate debug-level messages. Eligible call sites can be controlled using dynamic debug.

Q5. What is dynamic debugging?

It enables or disables selected debug messages at runtime without rebuilding the module.

Q6. What is the kernel ring buffer?

It is a kernel-managed buffer that stores kernel log messages.

Q7. What is the purpose of dmesg?

It displays kernel messages from the ring buffer.

Q8. What is the difference between pr_info() and dev_info()?

pr_info() logs a general informational message. dev_info() logs an informational message associated with a particular struct device.

16. Lesson Summary

  • printk() is the basic kernel logging function.
  • Kernel log levels indicate message severity.
  • pr_*() macros provide convenient logging interfaces.
  • dev_*() macros include device context.
  • dmesg displays kernel ring-buffer messages.
  • Dynamic debug controls selected debug call sites at runtime.
  • Proper logging helps diagnose driver faults and improve maintainability.
