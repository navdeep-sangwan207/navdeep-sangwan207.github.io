2. Introduction to Kernel Testing Frameworks

Linux kernel testing frameworks provide structured methods to test kernel code and functionality.

Testing frameworks reduce dependence on manual testing and help developers detect defects during development.

Why testing frameworks are required

  • Verify individual kernel functions.
  • Test kernel subsystem behavior.
  • Detect regressions after code changes.
  • Automate repetitive test cases.
  • Improve code reliability.
  • Validate kernel interfaces.

Important Linux testing frameworks

FrameworkMain Purpose
KUnitIn-kernel unit testing.
kselftestTesting kernel functionality through kernel interfaces.
Kernel test infrastructureBuilds and executes different kernel test suites.
KernelCIKernel build and testing automation across configurations and platforms.

3. Introduction to KUnit

KUnit is a unit testing framework built into the Linux kernel.

It allows developers to test kernel code in a controlled environment without requiring a complete hardware device for every test.

KUnit characteristics

  • Runs tests within the kernel.
  • Supports test cases and test suites.
  • Provides assertion and expectation macros.
  • Reports test results using structured output.
  • Can be integrated into kernel build and test workflows.

Where KUnit is useful

  • Testing helper functions.
  • Testing data structures.
  • Testing input validation.
  • Testing internal kernel logic.
  • Testing error-handling paths.

5. KUnit Test Case

A KUnit test case is generally implemented as a function that receives a pointer to a struct kunit.

Example

static void addition_test(struct kunit *test)
{
    int result;

    result = 10 + 20;

    KUNIT_EXPECT_EQ(test, result, 30);
}

Here:

  • addition_test() is the test function.
  • test provides the KUnit test context.
  • KUNIT_EXPECT_EQ() compares the actual and expected values.

6. KUnit Assertions and Expectations

KUnit provides macros to verify conditions during testing.

MacroPurpose
KUNIT_EXPECT_EQ()Checks equality.
KUNIT_EXPECT_NE()Checks inequality.
KUNIT_EXPECT_TRUE()Checks whether a condition is true.
KUNIT_EXPECT_FALSE()Checks whether a condition is false.
KUNIT_EXPECT_NULL()Checks for a NULL pointer.
KUNIT_EXPECT_NOT_NULL()Checks for a non-NULL pointer.
KUNIT_ASSERT_EQ()Checks equality and aborts the current test on failure.
KUNIT_ASSERT_NOT_NULL()Requires a non-NULL pointer and aborts the current test on failure.

Example

static void validation_test(struct kunit *test)
{
    int value = 50;

    KUNIT_EXPECT_TRUE(test, value > 0);
    KUNIT_EXPECT_EQ(test, value, 50);
    KUNIT_EXPECT_NE(test, value, 100);
}
EXPECT macros record a failed expectation and continue the test where possible. ASSERT macros stop the current test when the assertion fails.

7. Creating a KUnit Test Suite

A test suite groups related test cases.

Example

#include <kunit/test.h>
#include <linux/module.h>

static int add_values(int a, int b)
{
    return a + b;
}

static void add_test(struct kunit *test)
{
    KUNIT_EXPECT_EQ(test, add_values(2, 3), 5);
}

static void add_zero_test(struct kunit *test)
{
    KUNIT_EXPECT_EQ(test, add_values(10, 0), 10);
}

static struct kunit_case add_test_cases[] = {
    KUNIT_CASE(add_test),
    KUNIT_CASE(add_zero_test),
    {}
};

static struct kunit_suite add_test_suite = {
    .name = "addition-test-suite",
    .test_cases = add_test_cases,
};

kunit_test_suite(add_test_suite);

MODULE_LICENSE("GPL");

Explanation

  1. The header file provides KUnit definitions.
  2. add_values() is the function being tested.
  3. Each test function checks a specific condition.
  4. KUNIT_CASE() registers a test case in the suite.
  5. kunit_test_suite() registers the suite with KUnit.

8. KUnit Configuration

KUnit support must be enabled in the kernel configuration.

Important configuration options

ConfigurationPurpose
CONFIG_KUNITEnables the KUnit framework.
CONFIG_KUNIT_TESTEnables selected KUnit framework tests.
CONFIG_KUNIT_ALL_TESTSEnables all available KUnit tests that are configured for this option.

Check kernel configuration

grep CONFIG_KUNIT /boot/config-$(uname -r)

If the configuration file is available, this command displays the KUnit-related settings.

Check current kernel version

uname -r
Some Ubuntu distribution kernels may not enable all KUnit features. You may need a suitable kernel build or a kernel configuration with KUnit support.

9. Running KUnit Tests

KUnit tests can be run using supported kernel build and execution methods.

Method 1: UML

User-Mode Linux (UML) allows a Linux kernel to run as a user-space process. It is useful for running kernel tests without booting a separate physical machine.

Example command from a configured kernel source tree

./tools/testing/kunit/kunit.py run

The KUnit tool can configure, build and execute tests according to the supplied options and kernel source configuration.

Method 2: Run selected tests

./tools/testing/kunit/kunit.py run --help

Use the help output for the options supported by your kernel source version.

10. KUnit Test Output

KUnit reports whether individual test cases pass or fail.

Illustrative output

TAP version 14
1..1
    # Subtest: addition-test-suite
    1..2
    ok 1 - add_test
    ok 2 - add_zero_test
ok 1 - addition-test-suite

This is an illustrative KTAP-style result. Exact output can differ between kernel versions and test execution environments.

Interpretation

  • ok indicates a passing test.
  • not ok indicates a failed test.
  • Subtests identify individual test cases.
  • The suite result summarizes the grouped tests.

11. Introduction to kselftest

kselftest is the Linux kernel's self-testing framework.

It provides test programs that verify kernel functionality through available kernel interfaces.

Characteristics

  • Many tests execute from user space.
  • Tests interact with kernel interfaces.
  • Supports automated test execution.
  • Contains tests for many kernel subsystems.
  • Useful for regression and integration testing.

Typical testing areas

  • System calls.
  • Memory management.
  • Networking.
  • Filesystems.
  • Timers.
  • Seccomp and other security interfaces.
  • Driver-related interfaces where tests are provided.

12. kselftest Directory Structure

In the Linux kernel source tree, kselftest is located under:

tools/
  testing/
    selftests/
      timers/
      networking/
      filesystems/
      vm/
      seccomp/
      ...

Each directory may contain its own tests, build rules and test instructions.

13. Building kselftest

kselftest can be built from a configured Linux kernel source tree.

Step 1: Enter the kernel source directory

cd linux

Step 2: Build a selected test suite

make -C tools/testing/selftests TARGETS=timers

Step 3: Run the selected test suite

sudo make -C tools/testing/selftests TARGETS=timers run_tests

The timers suite is an example. Select a target that exists in your source tree.

14. Running Individual kselftest Programs

Individual selftest programs can often be executed directly after building their suite.

Find test executables

find tools/testing/selftests -type f -executable

List available test directories

ls tools/testing/selftests

Follow the README and test instructions for the selected suite. Some tests require root privileges, particular kernel configuration options or specific hardware.

16. Applying KUnit to Device Drivers

KUnit is useful for testing the internal logic of a device driver.

Example: Validate a sensor reading

#include <kunit/test.h>
#include <linux/module.h>

static int validate_sensor_value(int value)
{
    if (value < 0 || value > 1023)
        return -EINVAL;

    return 0;
}

static void sensor_valid_test(struct kunit *test)
{
    KUNIT_EXPECT_EQ(test, validate_sensor_value(512), 0);
}

static void sensor_invalid_test(struct kunit *test)
{
    KUNIT_EXPECT_EQ(test, validate_sensor_value(1200), -EINVAL);
}

static struct kunit_case sensor_cases[] = {
    KUNIT_CASE(sensor_valid_test),
    KUNIT_CASE(sensor_invalid_test),
    {}
};

static struct kunit_suite sensor_suite = {
    .name = "sensor-validation",
    .test_cases = sensor_cases,
};

kunit_test_suite(sensor_suite);

MODULE_LICENSE("GPL");

This example tests the input-validation logic independently of a physical sensor.

The example is a KUnit test suite, not a standalone module for ordinary insmod testing. Build and execute it through a kernel configuration and KUnit workflow that supports the test.

17. Applying kselftest to Device Drivers

kselftest is useful when driver functionality is exposed through interfaces that can be exercised from user space.

Examples

  • Open a device file.
  • Read and write device data.
  • Send supported IOCTL commands.
  • Validate error responses.
  • Test sysfs attributes.
  • Verify behavior after device configuration changes.

Example test flow

Test Program
     |
     v
Open Device File
     |
     v
Write Test Data
     |
     v
Read Device Data
     |
     v
Verify Expected Result
     |
     v
Close Device File

These are typical user-space test operations. A project can implement them as selftests even when it does not use an existing upstream kselftest suite.

20. Best Practices

  • Write tests for important driver helper functions.
  • Cover normal, boundary and invalid input conditions.
  • Use KUnit for internal kernel logic.
  • Use kselftest for relevant kernel interfaces.
  • Keep tests repeatable and independent where possible.
  • Check test output rather than assuming success.
  • Run regression tests after modifying driver code.
  • Document required kernel configuration and hardware.
  • Use a virtual machine for suitable isolated experiments.
  • Do not assume that every driver can be tested without its hardware.

22. Lesson Summary

  • KUnit and kselftest are important Linux kernel testing frameworks.
  • KUnit provides in-kernel unit testing.
  • KUnit organizes tests into suites and individual test cases.
  • Assertions and expectations verify test results.
  • KTAP provides structured test output.
  • kselftest validates kernel functionality through kernel interfaces.
  • Both frameworks support systematic testing and regression detection.
  • KUnit is useful for internal driver logic, while kselftest is useful for interface-level testing.
