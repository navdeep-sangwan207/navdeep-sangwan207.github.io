2. Introduction to Fault Injection

Fault injection is a testing technique in which faults are deliberately introduced into a system to observe how software responds.

In Linux device-driver development, fault injection helps verify that drivers handle unexpected failures safely.

Why fault injection is required

  • Test error-handling code.
  • Detect resource leaks.
  • Verify memory allocation failure handling.
  • Test device initialization failures.
  • Check recovery from hardware communication errors.
  • Prevent kernel crashes and system instability.

Example

Suppose a driver allocates memory during initialization. If the allocation fails, the driver must return an error and release any resources that were already acquired.

5. Linux Kernel Fault Injection Framework

The Linux kernel provides fault injection infrastructure to help test how kernel code behaves when selected operations fail.

Depending on the kernel configuration, supported mechanisms may include:

  • Failslab – injects slab allocation failures.
  • Fail page allocation – injects page allocation failures.
  • Fail user-copy – tests selected user-copy failure paths.
  • Fail function – injects failures into eligible functions.
  • Failing I/O – tests selected block I/O error paths.
  • Failsunmap – tests selected unmapping-related failure paths.
The available fault injection mechanisms depend on the kernel version, configuration and the subsystem being tested. Not every driver operation can be fault-injected automatically.

6. Kernel Configuration for Fault Injection

Fault injection support must be enabled in the kernel configuration.

Important configuration options

ConfigurationPurpose
CONFIG_FAULT_INJECTIONEnables kernel fault injection infrastructure.
CONFIG_FAULT_INJECTION_DEBUG_FSProvides fault injection controls through debugfs.
CONFIG_FAILSLABEnables slab allocation fault injection.
CONFIG_FAIL_PAGE_ALLOCEnables page allocation fault injection.
CONFIG_FAIL_FUNCTIONEnables eligible function failure injection.
CONFIG_FAIL_MAKE_REQUESTSupports selected block I/O failure injection.

Inspect the current kernel configuration

grep -E 'CONFIG_FAULT_INJECTION|CONFIG_FAIL' \
/boot/config-$(uname -r)

Options not enabled may appear as # CONFIG_OPTION is not set or may be absent from the configuration file.

7. Understanding debugfs

debugfs is a virtual filesystem used to expose debugging information and controls from kernel components.

Some fault injection interfaces are exposed through debugfs.

Check whether debugfs is mounted

mount | grep debugfs

Mount debugfs if required

sudo mount -t debugfs none /sys/kernel/debug

Inspect fault injection controls

ls /sys/kernel/debug/fail*

If the kernel supports the relevant options, fault injection control directories may appear under:

/sys/kernel/debug/fail_page_alloc
/sys/kernel/debug/failslab
Do not assume these paths exist. Their availability depends on kernel configuration and implementation. Do not enable fault injection on a production machine.

8. Memory Allocation Failure Testing

Memory allocation failure is one of the important error conditions in kernel programming.

Example allocation

struct my_device *dev;

dev = kzalloc(sizeof(*dev), GFP_KERNEL);

if (!dev)
    return -ENOMEM;

If memory allocation fails, kzalloc() returns NULL.

Correct error handling

  • Check the returned pointer.
  • Return an appropriate error code.
  • Release resources acquired earlier.
  • Do not access the NULL pointer.
  • Do not continue initialization with incomplete state.

Testing scenarios

  • First allocation fails.
  • Second allocation fails after the first succeeds.
  • Allocation fails during device probe.
  • Allocation fails during a repeated operation.

9. Error Handling During Driver Initialization

A driver may acquire multiple resources during initialization. If a later step fails, earlier resources must be released.

Example initialization sequence

static int my_driver_init(void)
{
    int ret;

    ret = allocate_device_memory();
    if (ret)
        return ret;

    ret = register_device_number();
    if (ret)
        goto err_memory;

    ret = create_device_interface();
    if (ret)
        goto err_device_number;

    return 0;

err_device_number:
    unregister_device_number();

err_memory:
    free_device_memory();

    return ret;
}

This demonstrates reverse-order cleanup using error labels.

In a real driver, use the actual resource-acquisition and release APIs. Managed resource APIs such as devm_* may simplify cleanup in suitable probe paths.

10. I/O Failure Testing

Device drivers communicate with hardware through interfaces such as I2C, SPI, USB, PCI and memory-mapped registers.

Communication can fail because of:

  • Disconnected hardware.
  • Device not responding.
  • Bus communication errors.
  • Invalid device state.
  • Timeout conditions.
  • Controller errors.

Example I2C error handling

ret = i2c_master_send(client, buffer, length);

if (ret < 0) {
    dev_err(&client->dev, "I2C transfer failed: %d\n", ret);
    return ret;
}

if (ret != length)
    return -EIO;

The driver checks both negative errors and short transfers. A short transfer is not necessarily reported as a negative error, so the returned byte count must also be checked.

11. Timeout and Recovery Testing

Hardware may fail to respond within the expected time. A driver should avoid waiting indefinitely.

Example polling with timeout

unsigned long timeout;

timeout = jiffies + msecs_to_jiffies(1000);

while (!device_ready()) {
    if (time_after(jiffies, timeout))
        return -ETIMEDOUT;

    usleep_range(1000, 2000);
}

This is an illustrative polling pattern for a context where sleeping is permitted.

What should be tested?

  • Device responds before timeout.
  • Device never responds.
  • Device responds just before timeout.
  • Device becomes unavailable during an operation.
  • Driver performs safe cleanup after timeout.

12. Fail Function Mechanism

The fail-function mechanism can inject errors into selected eligible kernel functions.

It is useful for testing how kernel code handles failures returned by functions that support error injection.

Example inspection

cat /sys/kernel/debug/fail_function/injectable

The exact interface and available injectable functions depend on the kernel configuration and version.

Typical testing process

  1. Identify an eligible function.
  2. Configure a controlled injection test.
  3. Execute the relevant driver operation.
  4. Observe the returned error.
  5. Check whether cleanup was successful.
  6. Disable injection and repeat the normal test.

13. Fail Page Allocation

Fail page allocation is used to simulate failures in page allocation paths.

Kernel components use page allocation for memory that is managed in page-sized units.

Typical applications

  • Testing page allocation error handling.
  • Testing memory-intensive operations.
  • Validating recovery from memory pressure.
  • Checking resource cleanup.

Possible control directory

/sys/kernel/debug/fail_page_alloc/

Inspect the files available in this directory before using the interface.

14. Failslab – Slab Allocation Failure Injection

Failslab injects failures into selected slab allocator operations.

Kernel objects are frequently allocated through interfaces such as:

  • kmalloc()
  • kzalloc()
  • kmem_cache_alloc()

Failslab helps test whether code handles these allocation failures correctly.

Possible control directory

/sys/kernel/debug/failslab/

Testing objectives

  • Detect missing NULL checks.
  • Verify cleanup labels.
  • Check partially initialized objects.
  • Prevent use-after-free and memory leaks.

15. Fault Injection in Character Drivers

Character drivers provide file operations such as open, read, write and ioctl. Each operation should handle failures safely.

OperationFailure ScenarioExpected Handling
OpenDevice unavailableReturn an error.
ReadInvalid user bufferReturn an appropriate error.
WriteInvalid input or allocation failureReject input or return an error.
IOCTLUnsupported commandReturn -ENOTTY.
ReleaseRepeated cleanupAvoid double-free and invalid resource access.

Example user-copy error handling

if (copy_from_user(kernel_buffer, user_buffer, count))
    return -EFAULT;

copy_from_user() returns the number of bytes that could not be copied. A nonzero return value indicates that the complete copy did not succeed.

16. Testing Driver Recovery

Recovery testing verifies whether a driver returns to a safe state after a failure.

Example recovery sequence

Normal Operation
      |
      v
Fault Occurs
      |
      v
Detect Error
      |
      v
Stop Invalid Operation
      |
      v
Release Temporary Resources
      |
      v
Reset or Recover Device
      |
      v
Resume or Report Failure

Important checks

  • No resource remains unintentionally allocated.
  • No invalid pointer is accessed.
  • Locks are released correctly.
  • Device state remains consistent.
  • Subsequent operations behave correctly.

18. Practical Exercise – Test an Allocation Failure Path

Objective: Write a kernel helper that handles memory allocation failure safely.

Example source file

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/slab.h>
#include <linux/init.h>

static int __init fault_test_init(void)
{
    char *buffer;

    buffer = kzalloc(128, GFP_KERNEL);

    if (!buffer) {
        pr_err("Memory allocation failed\n");
        return -ENOMEM;
    }

    snprintf(buffer, 128, "Kernel allocation test");

    pr_info("%s\n", buffer);

    kfree(buffer);

    return 0;
}

static void __exit fault_test_exit(void)
{
    pr_info("Fault test module unloaded\n");
}

module_init(fault_test_init);
module_exit(fault_test_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Kernel allocation error handling example");

Test procedure

  1. Build the module using the kernel build system.
  2. Load the module.
  3. Inspect the kernel log.
  4. Unload the module.
  5. Review the allocation failure path in the source code.

Expected Result: When allocation succeeds, the module prints the test message and releases the allocated memory. If allocation fails, it reports the error and returns -ENOMEM.

This exercise demonstrates explicit error handling. It does not force the allocation to fail. To test an injected failure, use a suitably configured kernel fault injection facility in an isolated test environment.

20. Safety Precautions

  • Use a virtual machine or dedicated test system.
  • Take a VM snapshot before fault injection.
  • Never experiment on a production kernel.
  • Do not inject failures into critical storage or networking paths on an important system.
  • Understand the active fault injection controls before enabling them.
  • Record the kernel version and configuration.
  • Check logs and system behavior after each test.
  • Disable fault injection after the experiment.
  • Reboot the test environment if the system becomes unstable.
