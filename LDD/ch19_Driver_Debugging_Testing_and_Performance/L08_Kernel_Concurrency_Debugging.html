2. Introduction to Kernel Concurrency

Concurrency occurs when multiple execution contexts access shared resources during overlapping periods.

Linux kernel code may execute concurrently through:

  • Multiple processes or kernel threads.
  • Multiple CPU cores.
  • Interrupt handlers.
  • Softirqs and tasklets.
  • Workqueues.
  • Timer callbacks.

When multiple execution contexts access shared data without suitable synchronization, the system may produce incorrect results or unstable behavior.

3. What Is a Race Condition?

A race condition occurs when the result of an operation depends on the timing or ordering of concurrent execution.

Example

Assume two kernel threads increment the same shared counter.

int counter = 0;

/* Thread A */
counter = counter + 1;

/* Thread B */
counter = counter + 1;

Both threads may read the same initial value before either writes its updated value.

Possible execution sequence

StepThread AThread BCounter
1Read 0-0
2-Read 00
3Calculate 1-0
4-Calculate 10
5Write 1-1
6-Write 11

The expected result is 2, but the final result is 1. This is a lost-update race.

4. What Is a Deadlock?

A deadlock occurs when two or more execution contexts wait indefinitely for resources held by one another.

Example

  • Thread A holds Lock 1 and waits for Lock 2.
  • Thread B holds Lock 2 and waits for Lock 1.
  • Neither thread can continue.
Thread A                 Thread B
--------                 --------
Acquire Lock 1           Acquire Lock 2
       |                        |
       v                        v
Wait for Lock 2          Wait for Lock 1
       |                        |
       +------ DEADLOCK --------+

Four necessary deadlock conditions

  1. Mutual exclusion: A resource cannot be used simultaneously by conflicting operations.
  2. Hold and wait: A thread holds one resource while waiting for another.
  3. No preemption: A resource cannot simply be taken away.
  4. Circular wait: Threads form a circular chain of resource dependencies.

5. Introduction to Lockdep

Lockdep is the Linux kernel lock dependency validator.

It tracks lock usage and dependencies to detect potential deadlocks and incorrect locking patterns.

Lockdep helps detect

  • Potential circular lock dependencies.
  • Inconsistent lock acquisition order.
  • Some recursive locking errors.
  • Incorrect use of locking classes.
  • Potential interrupt-context locking problems.

Lockdep is particularly useful during kernel and device-driver development because it can report suspicious locking relationships before they cause an actual deadlock.

6. How Lockdep Works

Lockdep observes locking operations and builds a dependency graph.

Example dependency graph

Thread A:
Lock A -> Lock B

Thread B:
Lock B -> Lock A

Dependency Graph:
Lock A -> Lock B
   ^         |
   |         v
   +---------+

Circular Dependency Detected

When lock acquisition creates a circular dependency, lockdep can report a potential deadlock.

Important concepts

  • Lock class: A category of locks sharing a dependency identity.
  • Lock dependency: A relationship created when one lock is acquired while another is held.
  • Lock ordering: The sequence in which locks are acquired.
  • Lock validator: The mechanism that checks dependencies for potential problems.

7. Lockdep Kernel Configuration

Lockdep is generally enabled through kernel debugging configuration options.

Common configuration options

CONFIG_LOCKDEP=y
CONFIG_PROVE_LOCKING=y
CONFIG_DEBUG_LOCK_ALLOC=y
CONFIG_DEBUG_MUTEXES=y
CONFIG_DEBUG_SPINLOCK=y
CONFIG_LOCK_STAT=y

These options are related but serve different purposes. Exact dependencies and availability vary by kernel version and configuration.

Check the running kernel configuration

grep -E 'CONFIG_(LOCKDEP|PROVE_LOCKING|DEBUG_LOCK_ALLOC|LOCK_STAT)=' \
/boot/config-$(uname -r)

If the configuration file is unavailable, the kernel may expose its configuration through /proc/config.gz, if enabled.

zcat /proc/config.gz | grep CONFIG_LOCKDEP

8. Understanding Lock Ordering

Consistent lock ordering is one of the most important techniques for avoiding deadlocks.

Incorrect lock ordering

/* Thread A */
mutex_lock(&lock_a);
mutex_lock(&lock_b);

/* Thread B */
mutex_lock(&lock_b);
mutex_lock(&lock_a);

Each thread acquires the locks in a different order, creating a potential circular dependency.

Consistent lock ordering

/* Thread A */
mutex_lock(&lock_a);
mutex_lock(&lock_b);

/* Thread B */
mutex_lock(&lock_a);
mutex_lock(&lock_b);

Both threads follow the same lock order. This removes the particular circular-wait pattern shown above, although other synchronization errors may still exist.

9. Lockdep Reports

When lockdep identifies a suspicious locking pattern, it may print a warning in the kernel log.

Example illustrative report

WARNING: possible circular locking dependency detected

CPU: 1 PID: 1234 Comm: test_driver

Possible unsafe locking scenario:
Thread A:
  lock_acquire
  mutex_lock

Thread B:
  lock_acquire
  mutex_lock

Call Trace:
  dump_stack
  lock_acquire
  mutex_lock

This is an illustrative example, not a complete real kernel report.

Investigation procedure

  1. Read the warning and identify the involved locks.
  2. Inspect the lock acquisition sequence.
  3. Identify the relevant driver functions.
  4. Check whether the locks are acquired in different orders.
  5. Correct the locking design.
  6. Repeat testing and inspect the kernel log.

10. Mutex Debugging

A mutex protects shared data by allowing only one task at a time to hold it.

Example

static DEFINE_MUTEX(my_mutex);

static void update_device_state(void)
{
    mutex_lock(&my_mutex);

    /* Protected operation */

    mutex_unlock(&my_mutex);
}

Common mutex mistakes

  • Forgetting to unlock a mutex.
  • Unlocking a mutex that is not held by the current task.
  • Attempting recursive locking of a non-recursive mutex.
  • Using a mutex in interrupt context.
  • Holding a mutex for an unnecessarily long period.
Mutexes are sleeping locks. They are suitable for task context, not for ordinary hard interrupt handlers.

11. Spinlock Debugging

A spinlock protects shared data by making a competing CPU wait until the lock becomes available.

Example

static DEFINE_SPINLOCK(my_lock);

static int shared_value;

static void update_value(void)
{
    unsigned long flags;

    spin_lock_irqsave(&my_lock, flags);

    shared_value++;

    spin_unlock_irqrestore(&my_lock, flags);
}

Common spinlock mistakes

  • Forgetting to release the spinlock.
  • Holding a spinlock while performing a sleeping operation.
  • Using inconsistent lock ordering.
  • Incorrect interrupt-state handling.
  • Holding the lock for too long.
Never call a potentially sleeping function while holding a spinlock. Doing so can cause serious kernel problems.

12. Interrupt Context and Locking

Device drivers must consider whether shared data is accessed from process context, interrupt context or both.

If an interrupt handler and a process-context function use the same lock, interrupt-safe locking may be necessary to avoid deadlock.

Example process-context protection

unsigned long flags;

spin_lock_irqsave(&my_lock, flags);

/* Access shared data */

spin_unlock_irqrestore(&my_lock, flags);

spin_lock_irqsave() saves the local interrupt state and disables local interrupts while acquiring the lock. The corresponding unlock restores the saved state.

This is useful when the same lock is also acquired by an interrupt handler on that CPU.

13. Understanding Lock Classes

Lockdep groups locks into lock classes so that it can reason about dependencies between different lock instances.

For example, a driver may create multiple device objects, each containing a mutex. Depending on the locking design, these mutexes may be treated as instances of the same lock class.

Why lock classes matter

  • They help lockdep identify dependency relationships.
  • They allow lock ordering to be checked across code paths.
  • They help distinguish independent locking patterns.

Advanced kernel code can use lockdep class-management APIs when multiple lock instances require distinct dependency treatment. Such annotations must reflect the real locking design rather than suppress warnings arbitrarily.

15. KCSAN – Kernel Concurrency Sanitizer

KCSAN is a dynamic data-race detector for the Linux kernel.

It uses sampling-based instrumentation to detect conflicting accesses to shared memory that are not properly synchronized.

Example configuration

CONFIG_KCSAN=y

Example race

int shared_counter;

/* CPU 0 */
shared_counter++;

/* CPU 1 */
shared_counter++;

If the accesses are concurrent and lack appropriate synchronization, KCSAN may report a data race.

Lockdep vs KCSAN

FeatureLockdepKCSAN
Main purposeLocking correctnessData-race detection
FocusLock dependencies and usageConflicting memory accesses
MethodTracks locking relationshipsSampling-based access monitoring
Typical findingPotential circular lock dependencyUnsynchronized shared-data access

16. Practical Exercise – Inspecting Lockdep Messages

Objective: Learn how to inspect lock-related kernel warnings.

Step 1: Check kernel configuration

grep -E 'CONFIG_(LOCKDEP|PROVE_LOCKING)=' \
/boot/config-$(uname -r)

Step 2: Inspect kernel logs

dmesg | grep -i lockdep
dmesg | grep -i "circular locking"
dmesg | grep -i "possible deadlock"

Step 3: Follow kernel messages

sudo dmesg -w

Step 4: Review a warning

If a lockdep warning is present, identify the lock names, dependency chain and function call traces.

Expected Result: You should be able to determine whether the running kernel exposes lockdep support and inspect available locking warnings. A system without lockdep support or without a detected problem may produce no matching output.

17. Practical Exercise – Designing Safe Lock Ordering

Objective: Understand how consistent locking order prevents a circular dependency.

Unsafe design

Thread A:
    mutex_lock(&lock_a);
    mutex_lock(&lock_b);

Thread B:
    mutex_lock(&lock_b);
    mutex_lock(&lock_a);

Safer design

Thread A:
    mutex_lock(&lock_a);
    mutex_lock(&lock_b);

    /* Critical section */

    mutex_unlock(&lock_b);
    mutex_unlock(&lock_a);


Thread B:
    mutex_lock(&lock_a);
    mutex_lock(&lock_b);

    /* Critical section */

    mutex_unlock(&lock_b);
    mutex_unlock(&lock_a);

Analysis

  1. Both threads acquire Lock A first.
  2. Both threads acquire Lock B second.
  3. Both release locks in reverse order.
  4. The circular dependency in the original example is removed.

Expected Result: Understand how a consistent global lock-ordering rule reduces deadlock risk. This is a design exercise; it does not itself execute or test kernel locking.

18. Best Practices for Concurrency Debugging

  • Identify every execution context that accesses shared data.
  • Choose a suitable synchronization mechanism.
  • Document lock ordering.
  • Keep critical sections short.
  • Never sleep while holding a spinlock.
  • Use lockdep during kernel development where supported.
  • Use KCSAN to investigate possible data races.
  • Inspect kernel logs after stress testing.
  • Test driver removal and error paths for synchronization defects.
  • Do not ignore locking warnings without understanding their cause.
