2. Introduction to Kernel Crash Analysis

Kernel crash analysis is the process of investigating a Linux kernel failure to determine its root cause.

A kernel crash may result from a faulty device driver, memory corruption, invalid pointer access, synchronization problems, hardware faults or defects in kernel subsystems.

Crash analysis involves collecting diagnostic information, examining the processor state, analyzing the stack trace and identifying the source-code location responsible for the failure.

Why Is Crash Analysis Important?

  • Identify the root cause of kernel failures.
  • Debug faulty Linux device drivers.
  • Investigate memory corruption.
  • Understand unexpected system reboots.
  • Improve driver reliability.
  • Prevent repeated kernel crashes.
Important: Kernel crash analysis is different from ordinary application debugging. The investigation may require kernel symbols, a matching kernel image, a crash dump and architecture-specific knowledge.

3. Common Causes of Kernel Crashes

CauseDescription
NULL pointer dereferenceAccessing memory through a NULL pointer.
Use-after-freeAccessing an object after its memory has been released.
Buffer overflowWriting beyond the allocated buffer size.
Race conditionIncorrect behavior caused by unsynchronized concurrent access.
DeadlockExecution contexts wait indefinitely for resources held by each other.
Stack overflowExcessive stack consumption or recursion.
Invalid DMA accessIncorrect DMA address handling or memory ownership.
Hardware failureFaults involving memory, processor or other hardware components.

Device drivers can cause crashes because they execute in kernel space and interact directly with kernel data structures and hardware resources.

4. Kernel Crash Analysis Workflow

A systematic workflow helps developers avoid guessing and identify the actual cause of a crash.

  1. Detect the failure: Identify the Oops, panic or unexpected reboot.
  2. Collect logs: Retrieve kernel messages and system journal entries.
  3. Preserve crash data: Obtain vmcore or other available crash records.
  4. Identify the environment: Record kernel version, architecture and loaded modules.
  5. Inspect the crash: Analyze registers, stack trace and task information.
  6. Resolve symbols: Map addresses to functions and source-code locations.
  7. Find the root cause: Inspect memory access, locking and object lifetime.
  8. Apply a correction: Fix the driver or kernel defect.
  9. Retest: Reproduce the original workload and verify the correction.

5. Sources of Kernel Crash Information

Crash analysis can use information from several sources.

SourceInformation Available

pstoreCrash-related records preserved by supported platform storage backends.
Serial consoleKernel output captured through a serial connection.

Inspect Recent Kernel Messages

dmesg | tail -n 100

Inspect Kernel Journal

sudo journalctl -k

Inspect Previous Boot Logs

sudo journalctl -k -b -1

Inspect pstore

ls -l /sys/fs/pstore
Logs may be incomplete if the system crashes before they are written to persistent storage. A crash-dump mechanism provides more detailed information when correctly configured.

6. Understanding Kernel Crash Dumps

A kernel crash dump is a captured record of kernel memory and state at the time of a crash.

It allows developers to investigate a failure after the system has rebooted.

What Can a Crash Dump Contain?

  • Kernel memory information.
  • Processor register state.
  • Task and process information.
  • Kernel stack traces.
  • Loaded module information.
  • Kernel data structures.
  • Memory contents relevant to the failure.

What Is vmcore?

vmcore is a crash dump file containing captured kernel memory information. It is commonly analyzed using the Linux crash utility.

ls -lh /var/crash

Crash dump storage locations depend on the distribution and kdump configuration.

7. Introduction to kdump

kdump is a Linux kernel crash-dumping mechanism.

It uses a reserved area of memory to load a secondary kernel called the capture kernel. When the main kernel crashes, the system attempts to start the capture kernel and preserve crash information.

How kdump Works

  1. The system boots with memory reserved for a crash kernel.
  2. The normal production kernel runs.
  3. A serious kernel failure occurs.
  4. The crash kernel is started through the kexec mechanism.
  5. The capture kernel accesses the crashed kernel's memory image.
  6. Crash information is saved, commonly as a vmcore file.
  7. The dump can be analyzed later.

8. Checking kdump Configuration

On Ubuntu systems, kdump-related packages and services may be available depending on the release and installation.

Check Whether kdump Tools Are Installed

dpkg -l | grep kdump

Check the Service

systemctl status kdump-tools

Inspect the Configuration

cat /etc/default/kdump-tools

Check Kernel Command Line

cat /proc/cmdline

Look for a crashkernel= parameter. Its value and required memory depend on the kernel, platform and distribution.

Inspect Reserved Memory

dmesg | grep -i crash
Do not copy an arbitrary crashkernel memory reservation into a production boot configuration. Verify the correct value for the machine and ensure that the system can still boot normally.

9. Introduction to the crash Utility

The crash utility is a tool for analyzing kernel crash dumps and, in supported configurations, live kernel state.

It allows developers to inspect kernel tasks, stacks, symbols, memory and other kernel data structures.

Install on Ubuntu

sudo apt update
sudo apt install crash

Check Version

crash --version

Open a Crash Dump

crash /path/to/vmlinux /path/to/vmcore

Here:

  • vmlinux is the matching uncompressed kernel image with debugging symbols.
  • vmcore is the captured crash dump.
The kernel image and dump must match the crashed kernel build and architecture. A compressed boot image such as vmlinuz is generally not a substitute for the matching debug-symbol-rich vmlinux file.

11. Analyzing a Kernel Backtrace

A backtrace helps developers understand the sequence of functions active when the crash occurred.

Illustrative Backtrace

crash> bt

PID: 1234
COMMAND: test_driver

 #0  driver_read
 #1  vfs_read
 #2  ksys_read
 #3  __x64_sys_read
 #4  do_syscall_64

This example shows an illustrative read path from a system call into a driver callback.

Analysis Procedure

  1. Identify the crashing task.
  2. Locate the first relevant driver function.
  3. Check the function's source code and call path.
  4. Inspect its pointer arguments and shared objects.
  5. Review locking and allocation operations.
  6. Compare the stack trace with the driver source and matching symbols.
A backtrace is evidence, not proof of the root cause. Memory corruption can damage the stack or cause a failure far away from the original defect.

12. Analyzing Kernel Tasks and Processes

Kernel crash analysis often requires identifying which task was executing when the failure occurred.

Display Tasks

crash> ps

Display a Task Backtrace

crash> bt

Why Task Analysis Is Important

  • Identify the process associated with the failure.
  • Determine whether the crash happened in process context.
  • Investigate kernel worker threads.
  • Inspect task states and blocked operations.
  • Identify possible deadlocks and lock contention.

Interrupt and other non-process contexts require additional interpretation because they may not correspond to an ordinary user process.

13. Analyzing Kernel Modules

A faulty external or in-tree module can be responsible for a crash.

Display Loaded Modules

crash> mod

Inspect Module Information

modinfo driver_module.ko

Check Running Kernel Version

uname -r

Inspect Module Dependencies

modinfo -F depends driver_module.ko

Always use the exact module build associated with the crashed kernel when resolving addresses and examining module symbols.

14. Kernel Symbols and Debug Information

Kernel symbols associate addresses with function and variable names. Debug information can additionally map code locations to source files and line numbers.

Important Files

  • vmlinux – Uncompressed kernel image, often available with symbols.
  • System.map – Kernel symbol address map for a particular build.
  • *.ko – Kernel module object files.
  • *.debug – Separate debug information files when provided.

Find a Kernel Symbol

grep " printk$" /boot/System.map-$(uname -r)

Resolve an Address

addr2line -e vmlinux -f -i 0xffffffff81000000

The address above is illustrative. Use the correct address and matching uncompressed image for the actual crash.

Kernel address randomization, module relocation and architecture-specific address handling can affect symbol resolution. Follow the crash tool's symbol information and use the correct build artifacts.

15. Investigating Memory Corruption

Memory corruption occurs when kernel code changes memory that it does not own or accesses memory incorrectly.

Common Sources

  • Writing beyond an array boundary.
  • Use-after-free.
  • Double free.
  • Incorrect pointer arithmetic.
  • DMA buffer ownership errors.
  • Incorrect reference counting.
  • Race conditions involving object lifetime.

Useful Debugging Tools

ToolPurpose
KASANDetects many out-of-bounds and use-after-free memory errors.
kmemleakDetects possible memory leaks.
SLUB debuggingHelps detect slab allocator misuse and corruption.
UBSANDetects certain undefined behavior conditions.
lockdepDetects certain locking errors and potential deadlocks.

These facilities require appropriate kernel configuration and may have performance or memory overhead.

16. Analyzing Deadlocks and Locking Problems

A deadlock occurs when two or more execution contexts wait indefinitely for resources held by one another.

Example Scenario

Thread A:
    lock(mutex_A)
    lock(mutex_B)

Thread B:
    lock(mutex_B)
    lock(mutex_A)

If both threads acquire their first lock simultaneously, each can wait for the other lock indefinitely.

Investigation Techniques

  • Inspect task states and backtraces.
  • Review lock acquisition order.
  • Use lockdep where available.
  • Check whether locks are held across blocking operations.
  • Examine workqueues and kernel threads waiting for locks.

17. Crash Analysis for Device Drivers

Driver crash analysis focuses on interactions between hardware, kernel frameworks and driver-owned resources.

Important Areas to Inspect

Driver AreaPotential Defect
Probe functionIncomplete initialization or missing error cleanup.
Remove functionResources released in an unsafe order.
Interrupt handlerInvalid pointer or unsafe operation in interrupt context.
DMA handlingIncorrect mapping, synchronization or ownership.
Read/write callbacksInvalid user-copy handling or buffer access.
WorkqueuesWork accessing resources after teardown.
Power managementIncorrect suspend/resume resource handling.

Example Driver Investigation Checklist

1. Check probe and initialization paths.
2. Check every allocation and release operation.
3. Validate pointer and buffer access.
4. Inspect IRQ and workqueue interactions.
5. Review locking and reference counting.
6. Check remove and shutdown paths.
7. Compare the crash with driver source symbols.

18. Crash Analysis Using GDB

GDB can inspect symbols and source-level information when suitable debugging information is available.

Open a Kernel Image

gdb /path/to/vmlinux

Inspect a Function

(gdb) info functions driver_read

Inspect Source Code

(gdb) list driver_read

Inspect a Symbol

(gdb) info address driver_read

For full post-mortem kernel dump analysis, the crash utility is commonly used. GDB is useful for examining symbols and source-level information and can be used in specialized kernel debugging workflows.

21. Best Practices for Kernel Crash Analysis

  • Record the exact kernel version and architecture.
  • Preserve the original vmcore before analysis.
  • Use matching kernel and module debug symbols.
  • Collect logs from before and after the failure when available.
  • Identify the crashing task and CPU.
  • Inspect the complete stack trace rather than only one function.
  • Check memory allocation and release paths.
  • Investigate locking, interrupts and workqueues.
  • Reproduce the issue using a controlled development environment.
  • Document the root cause and corrective action.
  • Retest under the original workload.
  • Protect crash dumps because they may contain sensitive memory contents.

23. Interview Questions and Answers

Q1. What is kernel crash analysis?

Answer: It is the process of investigating a kernel failure to identify its root cause using logs, stack traces, registers and crash dumps.

Q2. What is vmcore?

Answer: vmcore is a crash dump file containing captured kernel memory information.

Q3. What is kdump?

Answer: kdump is a Linux crash-dumping mechanism that uses a reserved capture kernel to save crash information.

Q4. What is a capture kernel?

Answer: It is a secondary kernel started after a crash to collect and save information about the failed kernel.

Q5. What is the crash utility?

Answer: It is a tool used to analyze kernel crash dumps and inspect kernel data structures.

Q6. Why is vmlinux required for crash analysis?

Answer: The matching vmlinux image provides kernel symbols and, when available, debugging information required to interpret the dump.

Q7. What is a kernel backtrace?

Answer: A backtrace displays the function call sequence associated with a task or failure context.

Q8. What does the crash command bt do?

Answer: It displays the backtrace for the selected or current task.

Q9. What does the crash command ps do?

Answer: It displays task information from the crash dump.

Q10. What does the crash command mod do?

Answer: It displays information about kernel modules.

Q11. What is System.map?

Answer: It is a symbol map containing kernel symbol addresses for a particular build.

Q12. Why must debug symbols match the crashed kernel?

Answer: Kernel builds can differ in addresses, functions and structure layouts. Mismatched symbols can produce incorrect analysis.

Q13. What is KASAN?

Answer: KASAN is a kernel memory error detector that can identify many out-of-bounds and use-after-free accesses.

Q14. What is kmemleak?

Answer: It is a kernel facility that helps detect possible memory leaks.

Q15. What is lockdep?

Answer: Lockdep is a kernel locking validator that detects certain locking errors and potential deadlocks.

Q16. What is a post-mortem analysis?

Answer: It is an investigation performed after a failure using preserved logs, dumps and other diagnostic information.

Q17. Can a driver cause a kernel crash?

Answer: Yes. Invalid memory access, incorrect DMA handling, race conditions and resource lifetime defects can cause kernel crashes.

Q18. What is the role of GDB?

Answer: GDB can inspect kernel symbols and source-level information when suitable debugging information is available.

Q19. Why should crash dumps be protected?

Answer: They may contain sensitive information from kernel memory, including data belonging to processes and devices.

Q20. What is the most important step in crash analysis?

Answer: Identifying the actual root cause using reliable evidence rather than assuming that the first visible failing function introduced the defect.

24. Lesson Summary

  • Kernel crash analysis identifies the root cause of kernel failures.
  • Crash information can come from logs, pstore, serial consoles and vmcore files.
  • kdump uses a capture kernel to preserve crash information.
  • The crash utility analyzes kernel dumps.
  • Backtraces and task information help identify the execution path.
  • Matching symbols are essential for reliable source-level analysis.
  • Memory corruption and locking defects are common crash causes.
  • Driver probe, remove, interrupt and DMA paths deserve careful inspection.
  • Controlled testing helps verify the corrective action.
