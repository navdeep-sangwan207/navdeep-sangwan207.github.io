2. Introduction to Driver Testing

Driver testing is the process of verifying that a Linux device driver works correctly, handles errors safely and interacts properly with the kernel and hardware.

A driver may compile successfully but still contain functional, memory-management, synchronization or hardware-interaction problems.

Why Driver Testing Is Important

  • Verify correct hardware communication.
  • Detect kernel crashes and memory corruption.
  • Identify incorrect device behavior.
  • Validate error handling.
  • Check concurrent access.
  • Verify resource cleanup.
  • Improve system stability and reliability.
A successful compilation is not proof that a driver is correct. Runtime testing and validation are essential.

A suitable development environment is required before testing a kernel driver.

Required Components

  • Kernel headers matching the running kernel.
  • GCC compiler and build tools.
  • Kernel source code when required.
  • Kernel debugging tools.
  • Driver source code and Makefile.
  • Test application.

5. Basic Kernel Module Testing

The first testing stage for a simple driver module is to verify compilation, loading, execution and unloading.

Step 1: Compile the Module

make

Step 2: Inspect Generated Files

ls -l

Typical build outputs include:

  • driver.ko – Kernel module.
  • driver.o – Object file.
  • Module.symvers – Symbol version information, when generated.
  • modules.order – Module build ordering information.

Step 3: Load the Module

sudo insmod driver.ko

Step 4: Check Loaded Modules

lsmod | grep driver

Step 5: Inspect Kernel Logs

dmesg | tail -n 30

Step 6: Unload the Module

sudo rmmod driver

Step 7: Verify Removal

lsmod | grep driver
Expected Result: The module should load without errors, perform its initialization, and unload cleanly.

6. Functional Testing of Character Drivers

Character drivers commonly expose a device interface through which user-space applications communicate with kernel code.

Important Operations to Test

  • open()
  • read()
  • write()
  • release()
  • ioctl()
  • poll(), when supported.

Testing Checklist

TestExpected Behavior
Open deviceDevice opens successfully when available and permitted.
Read deviceReturns valid data or the documented result.
Write deviceAccepts valid input and handles invalid input safely.
Close deviceReleases per-open resources correctly.
Multiple opensFollows the driver's documented concurrency policy.
Invalid device pathReturns an appropriate error.
Invalid IOCTLReturns an appropriate error such as -ENOTTY.

8. Unit Testing with KUnit

KUnit is the Linux kernel unit testing framework.

It allows developers to test kernel functions and components using test cases that run in kernel space.

Features

  • Tests individual kernel functions.
  • Supports test suites and test cases.
  • Provides assertion and expectation facilities.
  • Can be integrated with kernel build and test workflows.
  • Helps identify defects early in development.

Basic KUnit Test Example

#include <kunit/test.h>

static void addition_test(struct kunit *test)
{
    int result = 10 + 20;

    KUNIT_EXPECT_EQ(test, result, 30);
}

static struct kunit_case example_cases[] = {
    KUNIT_CASE(addition_test),
    {}
};

static struct kunit_suite example_suite = {
    .name = "driver_example_test",
    .test_cases = example_cases,
};

kunit_test_suite(example_suite);

MODULE_LICENSE("GPL");

This example demonstrates the KUnit test structure. A complete build requires the appropriate KUnit configuration and integration with the kernel build system.

Check KUnit Configuration

grep CONFIG_KUNIT /boot/config-$(uname -r)

Important KUnit Features

FeaturePurpose
KUNIT_CASE()Registers a test case.
KUNIT_EXPECT_EQ()Checks equality without immediately aborting the test.
KUNIT_ASSERT_EQ()Checks equality and aborts the current test on failure.
KUNIT_EXPECT_TRUE()Checks whether an expression is true.
KUNIT_EXPECT_FALSE()Checks whether an expression is false.

9. Integration Testing

Integration testing checks whether different components work together correctly.

Driver Integration Points

  • Kernel device model.
  • Character device subsystem.
  • Platform driver framework.
  • Device Tree.
  • I2C or SPI subsystem.
  • GPIO subsystem.
  • Interrupt handling.
  • User-space applications.

Example: I2C Sensor Driver

  1. Verify the I2C adapter is registered.
  2. Check whether the sensor is physically connected.
  3. Confirm the Device Tree description is correct.
  4. Verify driver probe and device initialization.
  5. Read sensor data through the supported interface.
  6. Compare the reading with a known reference.
  7. Test disconnection and reconnection behavior where supported.

Useful Commands

i2cdetect -l

i2cdetect -y 1

ls /sys/bus/i2c/devices/
Use I2C probing commands only when appropriate for the connected hardware. Some devices do not tolerate arbitrary address probing. These commands will not provide physical I2C access through an ordinary VirtualBox guest unless the hardware is correctly passed through.

10. Stress Testing

Stress testing checks driver behavior under repeated operations or heavy workloads.

Common Stress Tests

  • Repeated module load and unload.
  • Repeated device open and close.
  • Continuous read and write operations.
  • Multiple concurrent processes.
  • High-frequency interrupt activity.
  • Repeated device connection and removal.

Example: Repeated Device Access

for i in $(seq 1 100)
do
    cat /dev/mydevice > /dev/null
done

Example: Repeated Module Load and Unload

for i in $(seq 1 20)
do
    sudo insmod mydriver.ko || break
    sudo rmmod mydriver || break
done

Run the second test only with a module designed for repeated initialization and removal, and ensure no dependent device or process is using it.

Monitor Kernel Logs

dmesg -w

Monitor Memory

free -h

cat /proc/meminfo

11. Negative Testing and Error Handling

Negative testing checks whether a driver handles invalid input and failure conditions safely.

Examples

  • Invalid IOCTL command.
  • Incorrect buffer size.
  • Invalid device number.
  • Failed memory allocation.
  • Missing hardware.
  • Invalid configuration values.
  • Permission-denied access.
  • Device removal while users are active.

Example: Invalid Device Path

cat /dev/nonexistent_device

Expected behavior: user space reports that the device does not exist.

Example: Invalid IOCTL

A test application can issue an unsupported command and verify that the driver returns an appropriate error, commonly -ENOTTY.

Why Negative Testing Matters

  • Prevents unsafe memory access.
  • Improves error recovery.
  • Validates input checking.
  • Reduces system crash risks.

12. Regression Testing

Regression testing verifies that previously working functionality continues to work after code changes.

Example

Suppose a driver developer fixes a read() function. The updated driver should also be tested for:

  • Device initialization.
  • Device opening.
  • Write operations.
  • IOCTL operations.
  • Concurrent access.
  • Resource cleanup.
  • Module removal.

Regression Testing Workflow

  1. Maintain a set of existing test cases.
  2. Record expected results.
  3. Apply code changes.
  4. Rebuild the driver.
  5. Run all relevant tests.
  6. Compare actual and expected results.
  7. Investigate failures.

13. Hardware Validation

Hardware validation checks the driver against the actual electronic device or peripheral.

Important Validation Areas

  • Electrical connections.
  • Power supply and voltage levels.
  • Clock configuration.
  • Bus configuration.
  • Interrupt signals.
  • Data transfer accuracy.
  • Device initialization timing.
  • Reset and recovery behavior.

Example: SPI Device Validation

  1. Verify MOSI, MISO, SCLK and chip-select connections.
  2. Confirm the SPI mode.
  3. Check clock frequency limits.
  4. Verify chip-select behavior.
  5. Send a known command.
  6. Read a known response.
  7. Compare received data with expected data.
VirtualBox Ubuntu can be used for many software-level driver exercises, but physical GPIO, I2C, SPI and interrupt validation requires suitable hardware access. A VM does not automatically expose the host computer's physical peripherals.

15. Testing Driver Resource Cleanup

A driver must release resources correctly when initialization fails, the device is removed or the module is unloaded.

Resources to Validate

  • Dynamically allocated memory.
  • Character device numbers.
  • cdev registrations.
  • Device nodes and class objects.
  • Interrupt registrations.
  • Timers.
  • Workqueues.
  • GPIO descriptors.
  • I2C and SPI resources.
  • Open file references.

Testing Procedure

  1. Load the module.
  2. Verify resource registration.
  3. Use the device interface.
  4. Stop asynchronous operations.
  5. Unload or unbind the driver.
  6. Verify resource cleanup.
  7. Repeat the process.

Useful Inspection Commands

lsmod

cat /proc/devices

ls /sys/class

ls /sys/bus/platform/drivers

dmesg | tail -n 50

16. Practical Lab: Test a Memory-Based Character Driver

Objective

Build and test a simple character driver that supports read and write operations using an in-memory buffer.

Source Code: test_char.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/uaccess.h>
#include <linux/slab.h>
#include <linux/mutex.h>

#define DEVICE_NAME "testchar"
#define BUFFER_SIZE 256

static dev_t dev_num;
static struct cdev test_cdev;
static char *device_buffer;
static size_t data_size;
static DEFINE_MUTEX(buffer_lock);

static int test_open(struct inode *inode, struct file *file)
{
    pr_info("testchar: device opened\n");
    return 0;
}

static int test_release(struct inode *inode, struct file *file)
{
    pr_info("testchar: device closed\n");
    return 0;
}

static ssize_t test_read(struct file *file,
                         char __user *user_buffer,
                         size_t count,
                         loff_t *offset)
{
    ssize_t ret;

    if (*offset < 0)
        return -EINVAL;

    if (mutex_lock_interruptible(&buffer_lock))
        return -ERESTARTSYS;

    ret = simple_read_from_buffer(
        user_buffer,
        count,
        offset,
        device_buffer,
        data_size
    );

    mutex_unlock(&buffer_lock);

    return ret;
}

static ssize_t test_write(struct file *file,
                          const char __user *user_buffer,
                          size_t count,
                          loff_t *offset)
{
    size_t len;

    if (mutex_lock_interruptible(&buffer_lock))
        return -ERESTARTSYS;

    len = min(count, (size_t)(BUFFER_SIZE - 1));

    if (copy_from_user(device_buffer, user_buffer, len)) {
        mutex_unlock(&buffer_lock);
        return -EFAULT;
    }

    device_buffer[len] = '\0';
    data_size = len;

    mutex_unlock(&buffer_lock);

    return len;
}

static const struct file_operations test_fops = {
    .owner = THIS_MODULE,
    .open = test_open,
    .release = test_release,
    .read = test_read,
    .write = test_write,
    .llseek = default_llseek,
};

static int __init testchar_init(void)
{
    int ret;

    device_buffer = kzalloc(BUFFER_SIZE, GFP_KERNEL);

    if (!device_buffer)
        return -ENOMEM;

    ret = alloc_chrdev_region(&dev_num, 0, 1, DEVICE_NAME);

    if (ret)
        goto err_buffer;

    cdev_init(&test_cdev, &test_fops);
    test_cdev.owner = THIS_MODULE;

    ret = cdev_add(&test_cdev, dev_num, 1);

    if (ret)
        goto err_region;

    pr_info("testchar registered: major=%d minor=%d\n",
            MAJOR(dev_num), MINOR(dev_num));

    return 0;

err_region:
    unregister_chrdev_region(dev_num, 1);

err_buffer:
    kfree(device_buffer);
    return ret;
}

static void __exit testchar_exit(void)
{
    cdev_del(&test_cdev);
    unregister_chrdev_region(dev_num, 1);
    kfree(device_buffer);

    pr_info("testchar removed\n");
}

module_init(testchar_init);
module_exit(testchar_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Character Driver Testing Example");

Makefile

obj-m += test_char.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Step 1: Build

make

Step 2: Load Module

sudo insmod test_char.ko

Step 3: Find Major Number

cat /proc/devices | grep testchar

Suppose the displayed major number is 240. Use the actual number shown on your system.

Step 4: Create Device Node

sudo mknod /dev/testchar c 240 0

sudo chmod 666 /dev/testchar

Step 5: Write Data

echo "Linux driver testing" > /dev/testchar

Step 6: Read Data

cat /dev/testchar

Expected output:

Linux driver testing

Step 7: Inspect Logs

dmesg | tail -n 20

Step 8: Remove Driver

sudo rm -f /dev/testchar

sudo rmmod test_char
This is a teaching example. It does not implement a complete production-grade device lifecycle. In particular, it assumes the device is not in active use during module removal. A production driver needs proper device-node management, open-file lifetime handling and synchronization with active operations before freeing its buffer.

17. Driver Validation Checklist

Build Validation

  • Compilation completes without errors.
  • Warnings are reviewed.
  • Module matches the target kernel.

Functional Validation

  • Module loads successfully.
  • Device initializes correctly.
  • Read and write operations work as designed.
  • IOCTL commands behave correctly.
  • Invalid requests are rejected safely.

Memory and Concurrency Validation

  • No known memory leaks remain.
  • No known out-of-bounds accesses remain.
  • Shared data is properly synchronized.
  • Resource cleanup is verified.

Hardware Validation

  • Correct electrical connections.
  • Correct device configuration.
  • Expected data transfer.
  • Correct interrupt behavior.
  • Safe recovery after device errors.

Reliability Validation

  • Repeated load and unload tested.
  • Repeated open and close tested.
  • Stress tests completed.
  • Regression tests completed.
  • Failure recovery verified.

18. Common Driver Testing Problems and Troubleshooting

ProblemPossible CauseSolution
Module compilation failsMissing or mismatched kernel headersInstall headers matching the target kernel.
Module loading failsSymbol mismatch, invalid module or dependency issueInspect dmesg and module information.
Device node missingRegistration or udev configuration issueInspect device registration and logs.
Read returns no dataEmpty buffer or incorrect file offset handlingInspect read and write logic.
Write failsPermission, validation or copy errorCheck permissions and copy_from_user() handling.
System becomes unstableMemory corruption or synchronization errorUse KASAN, KCSAN and kernel logs where available.
Repeated unload failsActive references or incomplete cleanupReview module and device lifetime management.
Hardware test failsElectrical or configuration problemCheck power, wiring, timing and bus configuration.

19. Best Practices for Driver Testing

  • Build and test in a controlled environment.
  • Use a disposable virtual machine for risky kernel experiments.
  • Test both normal and invalid inputs.
  • Use automated tests wherever practical.
  • Check kernel logs after important operations.
  • Use KUnit for suitable unit-level tests.
  • Use kselftest for relevant kernel subsystem tests.
  • Use sanitizers and Lockdep when available.
  • Test repeated device initialization and removal.
  • Verify resource ownership and cleanup.
  • Perform hardware tests on supported target hardware.
  • Keep test results and kernel configuration records.

21. Interview Questions and Answers

Q1. What is driver testing?

Answer: It is the process of verifying driver functionality, reliability, safety and correct interaction with hardware and kernel subsystems.

Q2. What is unit testing?

Answer: Unit testing verifies individual functions or small software components independently.

Q3. What is integration testing?

Answer: Integration testing checks whether different components work correctly together.

Q4. What is functional testing?

Answer: It verifies that the driver performs the operations specified by its requirements.

Q5. What is stress testing?

Answer: Stress testing evaluates driver behavior under heavy or repeated workloads.

Q6. What is negative testing?

Answer: Negative testing checks how the driver handles invalid inputs and failure conditions.

Q7. What is regression testing?

Answer: Regression testing ensures that code changes do not break previously working functionality.

Q8. What is KUnit?

Answer: KUnit is the Linux kernel unit testing framework.

Q9. What is kselftest?

Answer: kselftest is a collection of tests used to validate Linux kernel subsystems and features.

Q10. What is syzkaller?

Answer: syzkaller is a coverage-guided kernel fuzzer that generates system-call sequences to discover kernel bugs.

Q11. Why should a driver be tested after module loading?

Answer: Successful loading confirms initialization completed, but further tests are needed to validate device operations and cleanup.

Q12. Why is repeated load and unload testing important?

Answer: It helps identify resource leaks, incomplete cleanup and initialization problems.

Q13. What is hardware validation?

Answer: It verifies driver operation with actual hardware, including electrical connections, timing, communication and data accuracy.

Q14. Why are kernel logs important during testing?

Answer: They provide diagnostic messages about initialization, driver operations, warnings and kernel errors.

Q15. What is the purpose of a test plan?

Answer: A test plan defines the test objectives, procedures, expected results, environment and acceptance criteria.

Q16. Why should invalid input be tested?

Answer: It verifies that the driver rejects unsafe or unsupported requests without corrupting memory or destabilizing the kernel.

Q17. Can a virtual machine perform all hardware validation?

Answer: No. A VM can support software-level testing and selected virtual devices, but physical peripheral validation requires suitable hardware access.

Q18. What is the difference between KUnit and kselftest?

Answer: KUnit focuses on kernel unit tests, while kselftest provides tests for kernel features and subsystems, often exercising them through user-space interfaces.

Q19. What is a regression test suite?

Answer: It is a collection of previously defined tests rerun after code changes to check for regressions.

Q20. What makes a driver ready for release?

Answer: It should meet its functional requirements, pass relevant safety and reliability tests, handle errors correctly and have validated resource management on supported targets.
