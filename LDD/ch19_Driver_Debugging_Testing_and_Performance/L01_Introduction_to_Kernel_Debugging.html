1. Introduction to Kernel Debugging

Kernel debugging is the process of identifying, analyzing and correcting problems that occur inside the Linux kernel or its components.

A device driver executes in kernel space and interacts with hardware, memory, interrupts and other kernel subsystems. An error in a driver can affect the entire operating system.

Kernel debugging helps developers identify problems such as:

  • Kernel crashes.
  • Kernel oops messages.
  • Invalid memory access.
  • Memory leaks.
  • Race conditions.
  • Deadlocks.
  • Interrupt-handling failures.
  • Incorrect hardware communication.
  • Resource allocation and cleanup errors.
Example: A character driver may work correctly during normal read and write operations but crash when the device is unloaded. Kernel debugging helps identify whether the problem is caused by an invalid pointer, an active callback or incorrect resource cleanup.

2. Why Kernel Debugging Is Important

Unlike an ordinary user-space application, a kernel driver has privileged access to system resources.

A programming error can affect other kernel components and may cause the complete system to become unstable.

Major Reasons

  1. System stability: Prevent kernel crashes and unexpected reboots.
  2. Memory safety: Detect invalid pointers, use-after-free and memory corruption.
  3. Concurrency: Identify race conditions and synchronization problems.
  4. Hardware reliability: Diagnose incorrect register access, interrupts and DMA operations.
  5. Performance: Identify unnecessary processing, excessive interrupts and inefficient data transfers.
  6. Resource management: Verify correct allocation and release of memory, IRQs and device resources.

3. User-Space Debugging vs Kernel Debugging

User-space programs and kernel modules execute in different protection environments.

Aspect User-Space Debugging Kernel Debugging
Execution User space Kernel space
Privilege Restricted privileges Privileged execution
Common debugger GDB KGDB, GDB and kernel-specific tools
Logging printf(), application logs printk(), pr_info(), pr_err()
Failure impact Usually affects one process Can affect the entire system
Memory access Process virtual memory Kernel-managed memory and mappings
Debugging difficulty Generally easier More complex and potentially disruptive
A normal GDB session debugging a user-space application does not automatically provide debugging access to kernel code. Kernel-aware debugging support is required.

4. Common Device Driver Problems

4.1 Null Pointer Dereference

A driver accesses memory through a pointer whose value is NULL or otherwise invalid. 

struct my_device *dev = NULL;

/* Incorrect: dev is NULL */
dev->status = 1;

This can result in a kernel fault.

4.2 Use-After-Free

A driver accesses memory after it has been released. 

struct my_device *dev;

dev = kmalloc(sizeof(*dev), GFP_KERNEL);

if (!dev)
    return -ENOMEM;

kfree(dev);

/* Incorrect: accessing freed memory */
dev->status = 1;

4.3 Memory Leak

Memory is allocated but not released when it is no longer required. 

void *buffer;

buffer = kmalloc(1024, GFP_KERNEL);

if (!buffer)
    return -ENOMEM;

/* Missing kfree(buffer) */

4.4 Race Condition

Two execution contexts access shared data concurrently without sufficient synchronization.

4.5 Deadlock

Two or more execution contexts wait indefinitely for resources or locks held by each other.

4.6 Incorrect Interrupt Handling

An interrupt handler may access invalid data, perform operations that can sleep or fail to acknowledge or process a hardware event correctly.

5. Kernel Debugging Architecture

Kernel debugging uses multiple techniques. The developer selects the appropriate method depending on whether the problem involves execution flow, memory, timing, hardware or system stability.

6. printk() for Kernel Logging

The printk() function writes messages to the kernel log buffer.

It is commonly used to observe driver initialization, device detection, errors and important execution events.

Syntax

printk(KERN_INFO "Driver initialized\n");

Common Log Levels

Macro Purpose
KERN_EMERG Emergency messages.
KERN_ALERT Immediate action required.
KERN_CRIT Critical conditions.
KERN_ERR Error messages.
KERN_WARNING Warning messages.
KERN_NOTICE Important normal conditions.
KERN_INFO Informational messages.
KERN_DEBUG Debugging messages.

Preferred Convenience Macros

pr_info("Device initialized\n");
pr_err("Device initialization failed\n");
pr_warn("Unexpected device state\n");
pr_debug("Debug information\n");

These macros improve readability and are widely used in modern Linux kernel code.

7. Viewing Kernel Logs

Kernel messages can be inspected using several Linux commands.

Command 1: dmesg

dmesg

Displays messages from the kernel ring buffer.

Command 2: Follow New Messages

sudo dmesg -w

Displays new kernel messages as they arrive.

Command 3: Kernel Journal

sudo journalctl -k

Displays kernel messages collected by the systemd journal, where available.

Command 4: Follow Kernel Journal

sudo journalctl -kf

Follows new kernel messages in real time.

Command 5: Filter Error Messages

dmesg | grep -i error
dmesg | grep -i warning
dmesg | grep -i usb

8. Dynamic Debugging

Dynamic debug allows selected kernel debugging messages to be enabled at runtime when the relevant code has been compiled with dynamic debug support.

It can help developers obtain detailed diagnostic information without enabling every debug message permanently.

Check Dynamic Debug Support

mount | grep debugfs

ls /sys/kernel/debug/dynamic_debug/

Enable Debug Messages

sudo sh -c 'echo "module my_driver +p" > \
/sys/kernel/debug/dynamic_debug/control'

Disable Debug Messages

sudo sh -c 'echo "module my_driver -p" > \
/sys/kernel/debug/dynamic_debug/control'

The module name and debug query must match the actual kernel code and its compiled dynamic-debug metadata.

10. Kernel Oops and Kernel Panic

Kernel Oops

A kernel oops is a diagnostic report generated when the kernel encounters a serious error, such as an invalid memory access.

Depending on the circumstances, the kernel may be able to continue running after an oops, but the system may already be in an unreliable state.

Kernel Panic

A kernel panic occurs when the kernel cannot safely continue operation.

It may stop normal execution and can require a system reboot.

Kernel Oops Kernel Panic
Reports a serious kernel fault. Indicates the kernel cannot safely continue.
System may continue in some cases. Normal kernel operation stops.
May result in a panic. Often requires recovery or reboot.

11. Debugging Memory Problems

Memory problems are common in kernel drivers because drivers manage resources directly.

Common Memory Errors

  • Null pointer dereference.
  • Use-after-free.
  • Double free.
  • Out-of-bounds access.
  • Memory leaks.
  • Invalid DMA buffer handling.

Memory Allocation Example

struct my_device *dev;

dev = kzalloc(sizeof(*dev), GFP_KERNEL);

if (!dev)
    return -ENOMEM;

/* Use dev */

kfree(dev);

The allocation and cleanup paths must be correct, including when initialization fails partway through.

12. Debugging Concurrency Problems

Kernel drivers may execute in several contexts:

  • Process context.
  • Interrupt context.
  • Softirq context.
  • Workqueue context.
  • Timer callback context.
  • USB completion callback context.

If these contexts access shared data without suitable synchronization, race conditions may occur.

Common Synchronization Tools

  • Mutexes.
  • Spinlocks.
  • Atomic operations.
  • Wait queues.
  • Completions.
  • Read-write locks.
The correct synchronization primitive depends on the execution context. For example, a mutex cannot be used in interrupt context because acquiring it may sleep.

13. Debugging Hardware Interaction

Device drivers communicate with physical hardware through registers, interrupts, DMA and bus protocols.

Problems can occur when:

  • Incorrect register offsets are used.
  • Hardware is accessed before it is powered or initialized.
  • Interrupts are not configured correctly.
  • DMA addresses or mapping directions are incorrect.
  • Device communication times out.
  • Hardware resources are not released correctly.

Useful Inspection Commands

lspci -k
lsusb
lsblk
ip link
cat /proc/interrupts
cat /proc/iomem
cat /proc/ioports

These commands help inspect hardware and kernel resource information, depending on the device and system permissions.

14. Debugging in Ubuntu VirtualBox

Ubuntu running inside VirtualBox can be used to learn many kernel debugging techniques.

Suitable Activities

  • Compile and load kernel modules.
  • Inspect kernel messages.
  • Test character drivers.
  • Inspect USB devices passed through to the guest.
  • Use ftrace when supported.
  • Practice memory allocation and error handling.
  • Inspect kernel configuration.

Check Kernel Version

uname -r

Check Kernel Configuration

grep CONFIG_DEBUG_FS /boot/config-$(uname -r)
grep CONFIG_DYNAMIC_DEBUG /boot/config-$(uname -r)
grep CONFIG_KASAN /boot/config-$(uname -r)

A configuration option may be absent, disabled or unavailable in the running kernel. Some debugging features require a specially configured kernel.

A VirtualBox guest does not automatically expose all physical hardware to Ubuntu. USB devices require appropriate USB controller configuration and guest attachment. Hardware-specific debugging may require a physical target.

15. Practical Exercise: Debug a Kernel Module

Objective

Create a simple kernel module that generates log messages during initialization and removal.

Source Code: debug_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init debug_demo_init(void)
{
    pr_info("debug_demo: module initialized\n");

    pr_info("debug_demo: checking driver state\n");

    pr_debug("debug_demo: debug message\n");

    return 0;
}

static void __exit debug_demo_exit(void)
{
    pr_info("debug_demo: module removed\n");
}

module_init(debug_demo_init);
module_exit(debug_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Kernel Debugging Demonstration Module");

Makefile

obj-m += debug_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compilation

make

Load the Module

sudo insmod debug_demo.ko

Check Kernel Messages

dmesg | tail -20

Remove the Module

sudo rmmod debug_demo

Check the Removal Message

dmesg | tail -20

Expected Result

debug_demo: module initialized
debug_demo: checking driver state
debug_demo: module removed
The pr_debug() message may not appear unless the relevant debugging configuration or dynamic-debug controls enable it.

16. Kernel Debugging Workflow

Identify the Problem | v Reproduce the Error | v Collect Kernel Logs | v Inspect Driver Code | v Identify the Root Cause | v Apply a Code Fix | v Recompile the Module | v Test the Correction | v Verify System Stability | v Document the Result

A structured workflow reduces guesswork and makes driver debugging repeatable.

17. Kernel Debugging Best Practices

  1. Understand the driver architecture before debugging.
  2. Use meaningful log messages.
  3. Check all memory allocation results.
  4. Validate pointers before dereferencing them.
  5. Review every error-handling path.
  6. Use correct synchronization for shared data.
  7. Do not perform sleeping operations in atomic context.
  8. Check resource cleanup during driver removal.
  9. Use debugging tools appropriate to the failure.
  10. Test on a recoverable development system.
  11. Keep kernel symbols and source information consistent when using source-level debugging.
  12. Record the kernel version and configuration used during testing.

18. Important Points to Remember

  • Kernel debugging identifies problems inside the Linux kernel.
  • Device drivers execute in privileged kernel space.
  • A driver bug can affect the complete operating system.
  • printk() and pr_*() macros are important logging mechanisms.
  • dmesg and journalctl help inspect kernel messages.
  • KGDB supports source-level kernel debugging in suitable configurations.
  • ftrace and perf help analyze execution and performance.
  • Memory errors include leaks, invalid access and use-after-free.
  • Race conditions and deadlocks are concurrency problems.
  • Kernel oops and kernel panic indicate serious kernel failures.
  • Debugging requires systematic reproduction, diagnosis and verification.

20. Lesson Summary

Kernel debugging is an essential part of Linux device driver development. It helps developers identify programming errors, memory problems, synchronization failures and hardware communication issues.

Logging, kernel tracing, debugging tools and systematic testing provide different ways to investigate failures.

A reliable driver must not only work correctly during normal operation but must also handle errors, device removal, concurrent execution and resource cleanup safely.

This lesson establishes the foundation for the debugging techniques covered in the remaining lessons of Chapter 19.
