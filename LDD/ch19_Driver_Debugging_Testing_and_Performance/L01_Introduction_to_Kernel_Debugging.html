1. Introduction

Kernel debugging is the process of identifying, analyzing and correcting errors in the Linux kernel and its components, including device drivers and kernel modules.

Unlike ordinary application debugging, kernel debugging is more complex because kernel code executes in privileged mode and interacts directly with system resources such as memory, processors, interrupts and hardware devices.

A defect in a device driver can cause incorrect device operation, memory corruption, system instability, kernel warnings, kernel oops messages or even a complete system crash.

Kernel debugging techniques help developers identify the root cause of these problems and improve driver reliability.

2. Why Kernel Debugging Is Required

Kernel debugging is necessary because device drivers operate close to the operating system and hardware.

  • System stability: Prevent kernel crashes and unexpected system failures.
  • Memory correctness: Detect memory leaks, invalid pointers and buffer overflows.
  • Concurrency: Identify race conditions and synchronization problems.
  • Hardware communication: Diagnose incorrect register access and device communication.
  • Performance: Identify unnecessary delays and resource bottlenecks.
  • Error recovery: Verify that drivers handle failures safely.

3. User-Space Debugging vs Kernel-Space Debugging

Linux separates application execution from privileged kernel execution.

4. Common Device Driver Problems

4.1 NULL Pointer Dereference

Occurs when a driver accesses a pointer that contains NULL instead of a valid memory address.

struct device_data *data = NULL;

/* Incorrect: dereferencing a NULL pointer */
data->status = 1;

4.2 Memory Leak

A memory leak occurs when dynamically allocated memory is not released after it is no longer required.

void *buffer;

buffer = kmalloc(1024, GFP_KERNEL);

if (!buffer)
    return -ENOMEM;

/* Missing kfree(buffer) on an exit path */

4.3 Race Condition

A race condition occurs when multiple execution contexts access shared data without proper synchronization, potentially producing unpredictable results.

4.4 Deadlock

A deadlock occurs when execution contexts wait indefinitely for locks held by one another.

4.5 Invalid Hardware Access

Incorrect register addresses, invalid I/O operations or improper device resource handling can cause driver failures.

7. Viewing Kernel Messages with dmesg

The dmesg command displays messages stored in the kernel ring buffer.

# Display kernel messages
dmesg

# Display the latest 30 messages
dmesg | tail -30

# Follow new kernel messages
sudo dmesg -w

# Display messages with timestamps
dmesg -T

# Search for errors
dmesg | grep -i error

# Search for warnings
dmesg | grep -i warning

These commands are useful when investigating module loading errors, device initialization problems and kernel warnings.

8. Introduction to printk()

printk() is a kernel logging function used to print messages from kernel code.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init debug_demo_init(void)
{
    printk(KERN_INFO "Debug Demo: Module loaded\n");
    return 0;
}

static void __exit debug_demo_exit(void)
{
    printk(KERN_INFO "Debug Demo: Module unloaded\n");
}

module_init(debug_demo_init);
module_exit(debug_demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Basic Kernel Debugging Example");

Kernel log messages can be inspected using:

sudo dmesg | tail -20
Important: printk() is a kernel logging function. Do not use the standard C library function printf() inside a Linux kernel module.

10. Kernel Oops and Kernel Panic

Kernel Oops

A kernel oops is a report generated when the kernel encounters an invalid operation or serious internal error. Depending on the failure and system state, the kernel may continue running or may become unstable.

Kernel Panic

A kernel panic occurs when the kernel encounters a critical condition from which it cannot safely continue execution. The system may stop or reboot.

Kernel oops and panic reports often contain register information, process details and call traces that help developers identify the source of a failure.

11. Basic Kernel Module Debugging Workflow

  1. Write the kernel module.
  2. Compile it using the kernel build system.
  3. Load the module using insmod or modprobe.
  4. Inspect kernel messages using dmesg.
  5. Reproduce the problem.
  6. Analyze errors, warnings and call traces.
  7. Correct the source code.
  8. Recompile and test again.
  9. Unload the module and verify cleanup.
# Build the module
make

# Load the module
sudo insmod debug_demo.ko

# Check loaded modules
lsmod | grep debug_demo

# Inspect kernel messages
sudo dmesg | tail -30

# Remove the module
sudo rmmod debug_demo

# Inspect unload messages
sudo dmesg | tail -20

12. Practical Exercise: Basic Kernel Logging

Objective: Create a kernel module that prints initialization and cleanup messages and inspect them using dmesg.

Source File: debug_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init debug_demo_init(void)
{
    pr_info("Debug Demo: Initialization successful\n");
    return 0;
}

static void __exit debug_demo_exit(void)
{
    pr_info("Debug Demo: Cleanup successful\n");
}

module_init(debug_demo_init);
module_exit(debug_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("Linux Device Driver Learner");
MODULE_DESCRIPTION("Kernel Logging Practical");

Makefile

obj-m += debug_demo.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Execution

make
sudo insmod debug_demo.ko
sudo dmesg | tail -10

sudo rmmod debug_demo
sudo dmesg | tail -10

make clean

Expected Result

Debug Demo: Initialization successful
Debug Demo: Cleanup successful

The messages confirm that the module initialization and cleanup functions executed.

Environment note: Run this practical in Ubuntu with kernel headers matching the running kernel. In VirtualBox, use a snapshot or test VM because kernel modules execute with kernel privileges. Do not deliberately trigger a kernel crash on your primary system.

14. Lesson Summary

  • Kernel debugging identifies and corrects errors in kernel code and device drivers.
  • Kernel-space failures can affect the entire operating system.
  • Common problems include memory leaks, invalid pointers, race conditions and deadlocks.
  • printk() and dmesg are fundamental kernel logging tools.
  • Advanced tools include ftrace, GDB, KGDB, debugfs, KASAN and lockdep.
  • A systematic debugging workflow improves driver stability and reliability.
