2. Introduction to Kernel Sanitizers

A kernel sanitizer is a debugging facility that detects certain classes of programming errors while the Linux kernel is running or being tested.

Kernel device drivers interact with memory, hardware, interrupts, processes and shared resources. Incorrect handling can result in:

  • Memory corruption.
  • Buffer overflows.
  • Use-after-free errors.
  • Data races.
  • Undefined behavior.
  • Memory leaks.
  • Invalid memory accesses.

Sanitizers instrument or monitor kernel operations to help identify these problems.

Why Sanitizers Are Important

  1. Detect bugs during development.
  2. Provide diagnostic information.
  3. Identify the source of memory errors.
  4. Improve driver reliability.
  5. Reduce difficult-to-reproduce failures.
Sanitizers are debugging aids. They do not guarantee that a driver is completely free from defects.

4. KASAN – Kernel Address Sanitizer

KASAN is a kernel memory error detector.

It helps detect invalid memory accesses during kernel execution.

Errors Detected by KASAN

  • Out-of-bounds access.
  • Use-after-free.
  • Some stack and global memory access errors, depending on configuration and mode.

Working Principle

  1. Compiler instrumentation checks memory accesses.
  2. Shadow memory records whether memory regions are accessible.
  3. Invalid accesses are detected by the runtime.
  4. The kernel generates a diagnostic report.
  5. Developers inspect the access and allocation stack traces.

Check KASAN Configuration

grep CONFIG_KASAN /boot/config-$(uname -r)

Check Kernel Logs

dmesg | grep -i KASAN

Illustrative Report

BUG: KASAN: slab-out-of-bounds
Read of size 4 at address ...
Call Trace:
 driver_read_function
 ...

This is an illustrative report. Actual output depends on the kernel version and detected error.

Advantages

  • Provides detailed memory error reports.
  • Can identify allocation and access locations.
  • Useful during driver development and testing.
KASAN can add substantial memory and execution overhead. It is generally intended for debugging kernels rather than ordinary production deployments.

5. KCSAN – Kernel Concurrency Sanitizer

KCSAN is a dynamic data-race detector for Linux kernel code.

Purpose

It identifies conflicting memory accesses that occur concurrently without suitable synchronization.

Working Principle

  1. Kernel memory accesses are instrumented.
  2. KCSAN samples selected accesses.
  3. It monitors whether conflicting accesses occur.
  4. Potential data races are reported.
  5. Developers review the synchronization design.

Check Configuration

grep CONFIG_KCSAN /boot/config-$(uname -r)

Inspect Reports

dmesg | grep -i KCSAN

Typical Problems

  • Unsynchronized shared counters.
  • Concurrent access to driver state.
  • Interrupt and process context data races.
  • Workqueue and system-call concurrency bugs.
KCSAN is dynamic and sampling-based. A clean test run does not prove that all data races have been eliminated.

6. UBSAN – Undefined Behavior Sanitizer

UBSAN detects selected forms of undefined behavior in C code.

Examples of Problems

  • Invalid shift operations.
  • Some forms of signed integer overflow.
  • Misaligned memory accesses.
  • Invalid assumptions about certain data types.

Check Configuration

grep CONFIG_UBSAN /boot/config-$(uname -r)

Inspect Kernel Logs

dmesg | grep -i UBSAN

Illustrative Report

UBSAN: Undefined behaviour in driver_example.c
shift exponent is too large for type

This is an illustrative message, not guaranteed literal output.

Why UBSAN Is Useful

It can detect suspicious operations that may cause unpredictable results or hardware-dependent failures.

7. KFENCE – Kernel Electric-Fence

KFENCE is a low-overhead sampling-based memory error detector.

It uses guarded memory allocations to detect selected memory safety errors.

Problems It Can Detect

  • Out-of-bounds accesses involving guarded objects.
  • Use-after-free involving monitored allocations.

Working Principle

  1. Selected allocations are monitored.
  2. Guard pages are placed around monitored memory.
  3. Invalid accesses may hit protected regions.
  4. The kernel reports the detected error.

Check Configuration

grep CONFIG_KFENCE /boot/config-$(uname -r)

Inspect Kernel Logs

dmesg | grep -i KFENCE
KFENCE samples allocations. It is not expected to detect every invalid access.

8. kmemleak – Memory Leak Detection

kmemleak helps identify possible unreachable kernel memory allocations.

Check Availability

ls /sys/kernel/debug/kmemleak

Mount Debugfs

sudo mount -t debugfs none /sys/kernel/debug

Request a Scan

echo scan | sudo tee /sys/kernel/debug/kmemleak

Read Reports

sudo cat /sys/kernel/debug/kmemleak

Use Cases

  • Investigating unreleased driver allocations.
  • Testing module initialization and removal.
  • Checking repeated device bind and unbind operations.
  • Reviewing error-path cleanup.

Refer to Lesson 7 for the complete kmemleak workflow.

9. Lockdep – Lock Dependency Validator

Lockdep validates kernel locking behavior and detects potential locking problems.

Problems It Helps Identify

  • Potential circular lock dependencies.
  • Inconsistent lock ordering.
  • Some recursive locking errors.
  • Some incorrect interrupt-context locking combinations.

Check Configuration

grep -E "CONFIG_LOCKDEP|CONFIG_PROVE_LOCKING" \
/boot/config-$(uname -r)

Inspect Kernel Logs

dmesg | grep -i -E "lockdep|possible deadlock|locking"

Importance in Drivers

Drivers often combine mutexes, spinlocks, interrupts and workqueues. Lockdep helps developers validate their locking design.

10. SLUB Debugging

SLUB is a slab allocator implementation used by the Linux kernel on many configurations.

SLUB debugging features help identify memory corruption and allocator misuse.

Important Debugging Features

  • Red zoning: Helps detect accesses beyond object boundaries.
  • Poisoning: Fills selected memory regions with known patterns to help identify invalid usage.
  • Allocation tracking: Records allocation information where enabled.
  • Consistency checks: Detect certain allocator metadata problems.

Inspect Slab Information

cat /proc/slabinfo

Use slabtop

sudo slabtop

Check SLUB Debug Configuration

grep CONFIG_SLUB_DEBUG /boot/config-$(uname -r)
SLUB debugging options and boot parameters vary across kernel versions. Some debugging modes require a kernel configured with the relevant support.

11. Ftrace – Function Tracing

Ftrace is the Linux kernel tracing framework.

It helps developers understand kernel execution paths and timing.

Common Uses

  • Function tracing.
  • Function graph tracing.
  • Interrupt and scheduling event analysis.
  • Investigating unexpected execution sequences.
  • Driver performance analysis.

Check Tracefs

mount | grep tracefs

Mount Tracefs if Required

sudo mount -t tracefs nodev /sys/kernel/tracing

Inspect Available Tracers

cat /sys/kernel/tracing/available_tracers

Inspect Available Events

cat /sys/kernel/tracing/available_events

Enable Function Tracing

cd /sys/kernel/tracing

echo function | sudo tee current_tracer

echo 1 | sudo tee tracing_on

sudo cat trace

Stop Tracing

echo 0 | sudo tee tracing_on

echo nop | sudo tee current_tracer
Use a suitable test environment. Function tracing may generate substantial output and add overhead.

12. Perf – Linux Performance Analysis Tool

perf is a performance analysis tool for Linux.

Common Applications

  • CPU profiling.
  • Hardware performance counter analysis.
  • Software event analysis.
  • Scheduler behavior investigation.
  • Function-level performance analysis.

Check Installation

perf --version

List Available Events

perf list

Record Performance Data

sudo perf record -a -g -- sleep 10

View Report

sudo perf report

Trace Selected System Calls

sudo perf trace -- sleep 2

Exact event availability depends on CPU hardware, kernel configuration and permissions.

13. GDB and KGDB

GDB

GDB is a debugger used to inspect program execution, variables, stack frames and symbols.

KGDB

KGDB provides kernel debugging support through a debugger connection, commonly using a serial connection or another supported transport.

Common GDB Commands

gdb vmlinux

(gdb) list
(gdb) info functions
(gdb) info variables
(gdb) bt
(gdb) quit

Useful Kernel Debugging Information

  • Kernel symbols.
  • Debug information.
  • Matching vmlinux image.
  • Kernel configuration.
  • Matching source code.
A normal GDB session can inspect kernel symbols and offline data. Live kernel debugging requires an appropriate setup such as KGDB or another supported debugging interface.

16. Practical Lab: Inspect Kernel Debugging Support

Objective

Inspect the debugging and sanitizer options available in the running Ubuntu kernel.

Step 1: Check Kernel Version

uname -r

Step 2: Check Kernel Configuration File

ls /boot/config-$(uname -r)

Step 3: Inspect Sanitizer Options

grep -E "CONFIG_(KASAN|KCSAN|UBSAN|KFENCE|DEBUG_KMEMLEAK)=" \
/boot/config-$(uname -r)

Step 4: Inspect Lockdep Options

grep -E "CONFIG_(LOCKDEP|PROVE_LOCKING|DEBUG_LOCK_ALLOC)=" \
/boot/config-$(uname -r)

Step 5: Check Debugging Interfaces

ls /sys/kernel/debug

ls /sys/kernel/tracing

Step 6: Check Tools

gdb --version

perf --version

crash --version

Some tools may not be installed. Some kernel interfaces may be unavailable because the kernel was not built with the relevant configuration.

Expected Result: You should be able to identify which debugging facilities and tools are available in your Ubuntu environment.

17. Practical Lab: Analyze Kernel Messages

Objective

Use kernel logs to identify diagnostic messages associated with memory and concurrency debugging.

Step 1: Display Recent Messages

dmesg | tail -n 50

Step 2: Search for Sanitizer Messages

dmesg | grep -i -E "KASAN|KCSAN|UBSAN|KFENCE"

Step 3: Search for Locking Warnings

dmesg | grep -i -E "lockdep|possible deadlock|locking"

Step 4: Follow Kernel Logs

sudo dmesg -w

Step 5: Stop Following Logs

Ctrl + C

Expected Result

The commands display available kernel messages. A system without sanitizer support or detected problems may produce no matching messages.

Objective

Enable function tracing and inspect the resulting trace output.

Step 1: Mount Tracefs

sudo mount -t tracefs nodev /sys/kernel/tracing

Step 2: Enter Trace Directory

cd /sys/kernel/tracing

Step 3: Check Available Tracers

cat available_tracers

Step 4: Enable Function Tracing

echo function | sudo tee current_tracer

echo 1 | sudo tee tracing_on

Step 5: Generate Some Activity

sleep 1

Function tracing may not be available in every kernel. It can also produce a large trace. Use short test intervals and inspect available tracing options first.

20. Best Practices for Kernel Debugging

  • Select the debugging tool according to the suspected defect.
  • Use a dedicated test kernel for sanitizer-based debugging.
  • Preserve kernel logs and crash reports.
  • Use matching source code and debug symbols.
  • Test drivers under realistic workloads.
  • Use stress testing for concurrency problems.
  • Check every allocation and cleanup path.
  • Review lock ordering and interrupt context.
  • Use ftrace and perf to investigate execution and performance.
  • Record the exact kernel version and configuration.
  • Reproduce and retest after every fix.
  • Do not treat a clean sanitizer run as proof of defect-free code.

22. Interview Questions and Answers

Q1. What is a kernel sanitizer?

Answer: It is a kernel debugging facility that detects selected programming errors during testing or execution.

Q2. What is KASAN?

Answer: KASAN is the Kernel Address Sanitizer. It detects many memory safety errors such as out-of-bounds and use-after-free accesses.

Q3. What is KCSAN?

Answer: KCSAN is the Kernel Concurrency Sanitizer, used to detect data races.

Q4. What is UBSAN?

Answer: UBSAN detects selected forms of undefined behavior in kernel code.

Q5. What is KFENCE?

Answer: KFENCE is a low-overhead sampling-based memory error detector that uses guarded allocations.

Q6. What is kmemleak?

Answer: kmemleak helps identify possible unreachable kernel memory allocations.

Q7. What is Lockdep?

Answer: Lockdep validates locking dependencies and helps identify potential deadlocks.

Q8. What is SLUB debugging?

Answer: It provides slab allocator debugging features that help detect memory corruption and allocator misuse.

Q9. What is ftrace?

Answer: Ftrace is a Linux kernel tracing framework used to inspect function execution and kernel events.

Q10. What is perf?

Answer: Perf is a Linux performance analysis tool used for profiling and performance counter analysis.

Q11. What is KGDB?

Answer: KGDB is a kernel debugging facility that supports source-level debugging through a debugger connection.

Q12. Can KASAN detect memory leaks?

Answer: KASAN primarily detects memory safety errors. kmemleak is the dedicated kernel facility for identifying possible memory leaks.

Q13. Can KCSAN detect every data race?

Answer: No. It is a dynamic sampling-based detector and may not observe every race.

Q14. Why are debugging kernels useful?

Answer: They can include instrumentation and diagnostic facilities that help identify errors that are difficult to detect in normal builds.

Q15. Why should sanitizer overhead be considered?

Answer: Instrumentation can increase memory usage and execution time, so performance results from debugging kernels may differ from production kernels.

Q16. What is the purpose of /proc/slabinfo?

Answer: It provides statistics about kernel slab caches.

Q17. What is the purpose of tracefs?

Answer: It provides the interface used to configure and read Linux kernel tracing information.

Q18. What is the difference between ftrace and perf?

Answer: Ftrace focuses on kernel function and event tracing, while perf provides broader performance profiling and event analysis.

Q19. Why are matching debug symbols important?

Answer: They allow debugging tools to map machine addresses to functions, source files and line numbers.

Q20. Which tool should be used to detect a kernel data race?

Answer: KCSAN is specifically designed to detect kernel data races.
