2. Introduction to Memory Leaks

A memory leak occurs when dynamically allocated memory is no longer needed but is not properly released.

In Linux kernel programming, drivers frequently allocate memory for device structures, buffers, request objects and other resources.

If the driver fails to release allocated memory, the system gradually loses available memory.

Example Scenario

A driver allocates memory whenever a device is opened but forgets to release it when the device is closed. Repeated open and close operations can cause memory usage to increase.

Effects of Memory Leaks

  • Gradual loss of available kernel memory.
  • Increased memory pressure.
  • Allocation failures.
  • Reduced system performance.
  • Instability in long-running systems.
  • Possible failure of important kernel operations.
Important: A memory leak is different from a use-after-free error. A leak means allocated memory is not released; use-after-free means memory is accessed after it has been released.

3. Kernel Memory Allocation Functions

Linux provides several functions for allocating and releasing kernel memory.

FunctionPurpose
kmalloc()Allocates physically contiguous kernel memory.
kzalloc()Allocates memory and initializes it to zero.
kcalloc()Allocates an array and initializes it to zero.
kfree()Releases memory allocated by compatible kmalloc-family functions.
vmalloc()Allocates virtually contiguous memory that need not be physically contiguous.
vfree()Releases memory allocated by vmalloc().
devm_kzalloc()Allocates zeroed memory managed by the device resource-management system.
kmem_cache_alloc()Allocates an object from a slab cache.
kmem_cache_free()Returns an object to its slab cache.

Example: kmalloc() and kfree()

#include <linux/slab.h>

int *ptr;

ptr = kmalloc(sizeof(*ptr), GFP_KERNEL);

if (!ptr)
    return -ENOMEM;

*ptr = 100;

kfree(ptr);
ptr = NULL;

Memory allocated using kmalloc() must be released using the appropriate deallocation routine.

4. How Memory Leaks Occur in Drivers

Example 1: Missing kfree()

static int __init leak_init(void)
{
    char *buffer;

    buffer = kmalloc(1024, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    pr_info("Memory allocated\n");

    /* Memory is not released */

    return 0;
}

static void __exit leak_exit(void)
{
    pr_info("Module unloaded\n");
}

The allocated buffer is not stored in a persistent reference and is never released. Unloading the module does not automatically free ordinary kmalloc allocations.

Example 2: Incorrect Error Handling

static int initialize_device(void)
{
    struct device_data *data;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    if (hardware_setup())
        return -EIO; /* Leak: data was not freed */

    return 0;
}

If hardware_setup() fails, the allocated structure is lost without being freed.

Corrected Example

static int initialize_device(void)
{
    struct device_data *data;
    int ret;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    ret = hardware_setup();

    if (ret) {
        kfree(data);
        return ret;
    }

    return 0;
}
A complete driver must also retain and eventually release data on the successful path. This example demonstrates cleanup on an initialization failure.

5. Memory Leak vs Other Memory Errors

ProblemDescription
Memory leakAllocated memory is not released when no longer needed.
Use-after-freeMemory is accessed after being released.
Double freeThe same allocation is released more than once.
Buffer overflowData is written beyond the valid buffer boundary.
Uninitialized memoryCode reads memory before it has been initialized.
Invalid freeCode attempts to release memory using an incorrect pointer or allocator.

These errors are related to memory management, but they require different detection and debugging techniques.

6. Introduction to kmemleak

kmemleak is a Linux kernel memory leak detector.

It provides a mechanism for identifying possible memory allocations that are no longer reachable through recognized pointers.

How kmemleak Works

  1. It tracks selected kernel memory allocations.
  2. It scans memory areas for pointers that may reference allocated objects.
  3. It identifies allocations that appear unreachable.
  4. It reports possible memory leaks.
  5. Developers investigate the reports and correct the resource-management problem.

Important Characteristics

  • It is a debugging facility, not a complete proof of memory correctness.
  • It can report false positives.
  • Some legitimate allocations may appear unreachable to its scanning algorithm.
  • It requires appropriate kernel configuration.
  • It can introduce runtime and memory overhead.
kmemleak performs conservative analysis. A report indicates a possible leak and must be investigated; it does not automatically prove that the allocation is definitely leaked.

7. Checking kmemleak Support

First, check whether the running kernel exposes the kmemleak interface.

Check the Interface

ls /sys/kernel/debug/kmemleak

If the file exists, the facility may be available. The debugfs filesystem must be mounted.

Mount Debugfs if Necessary

sudo mount -t debugfs none /sys/kernel/debug

Check Kernel Configuration

grep CONFIG_DEBUG_KMEMLEAK /boot/config-$(uname -r)

Expected configuration when enabled:

CONFIG_DEBUG_KMEMLEAK=y

The exact configuration depends on the kernel build.

8. Using kmemleak

When kmemleak is available, developers can request a scan and read the resulting reports.

Step 1: Check the Current Report

sudo cat /sys/kernel/debug/kmemleak

Step 2: Request a Scan

echo scan | sudo tee /sys/kernel/debug/kmemleak

Step 3: Read the Report

sudo cat /sys/kernel/debug/kmemleak

Step 4: Clear Existing Reports

echo clear | sudo tee /sys/kernel/debug/kmemleak

Step 5: Request Another Scan

echo scan | sudo tee /sys/kernel/debug/kmemleak

sudo cat /sys/kernel/debug/kmemleak
Use the clear command carefully. It clears the existing kmemleak report state; it does not repair or free leaked memory. Follow the documentation for the running kernel before using additional kmemleak controls.

9. Understanding kmemleak Reports

A kmemleak report may include information about an allocation that appears unreachable.

Illustrative Report

unreferenced object 0xffff888012345000 (size 1024):
  comm "test_process", pid 1234, jiffies 100000
  backtrace:
    kmalloc_trace
    driver_allocate_buffer
    driver_probe

This is an illustrative report. Actual fields and formatting depend on the kernel version and allocation path.

Important Fields

FieldMeaning
Unreferenced objectAddress of a suspected unreachable allocation.
SizeSize of the reported allocation.
CommTask name associated with the allocation.
PIDProcess identifier associated with the allocation context.
BacktraceAllocation call path where available.

How to Investigate

  1. Identify the allocation function.
  2. Find the corresponding driver source code.
  3. Trace every success and error path.
  4. Check whether the allocation is intentionally retained.
  5. Check whether a pointer is stored in a location kmemleak can recognize.
  6. Verify whether the object is eventually released.

10. Slab Allocator Debugging

The Linux kernel uses slab allocation mechanisms to efficiently manage frequently allocated objects.

Slab debugging options help detect certain allocation and memory corruption problems.

Important Features

  • Red zones can help detect memory writes beyond object boundaries.
  • Poisoning can help identify certain invalid memory accesses.
  • Allocation tracking can help identify where objects were allocated.
  • Consistency checks can detect allocator metadata corruption.

Inspect Slab Information

cat /proc/slabinfo

Use slabtop

sudo slabtop

slabtop displays statistics about kernel slab caches.

Slab allocator statistics are not a direct measurement of memory leaks. A large cache may be legitimate because the kernel retains objects for reuse.

11. KASAN for Memory Error Detection

KASAN (Kernel Address Sanitizer) is a kernel debugging facility that detects many memory safety errors.

Errors KASAN Can Detect

  • Out-of-bounds memory access.
  • Use-after-free.
  • Some invalid memory accesses involving stack and global objects, depending on KASAN mode and configuration.

How KASAN Works

  1. Compiler instrumentation and kernel runtime support track memory accessibility.
  2. Memory accesses are checked against the relevant metadata.
  3. Invalid accesses generate diagnostic reports.
  4. The report helps identify the faulting instruction and allocation or free history where available.

Check Kernel Configuration

grep CONFIG_KASAN /boot/config-$(uname -r)
KASAN is primarily a memory safety detector, not a dedicated memory leak detector. kmemleak is specifically intended to help identify possible memory leaks.

12. Reference Counting and Memory Management

Kernel objects may be shared by multiple components. Reference counting helps track how many users still hold references to an object.

Why Reference Counting Is Important

  • Prevents objects from being freed while still in use.
  • Helps manage shared resource lifetimes.
  • Supports safe cleanup when the last reference is released.

Example Using refcount_t

#include <linux/refcount.h>
#include <linux/slab.h>

struct my_object {
    refcount_t refs;
    int value;
};

static struct my_object *my_object_create(void)
{
    struct my_object *obj;

    obj = kzalloc(sizeof(*obj), GFP_KERNEL);

    if (!obj)
        return NULL;

    refcount_set(&obj->refs, 1);
    obj->value = 100;

    return obj;
}

static void my_object_get(struct my_object *obj)
{
    refcount_inc(&obj->refs);
}

static void my_object_put(struct my_object *obj)
{
    if (refcount_dec_and_test(&obj->refs))
        kfree(obj);
}
This is an educational example. A real implementation must ensure that references are acquired safely while the object is alive and that object access is synchronized appropriately.

13. devm_* Resource Management

Linux provides device-managed resource allocation APIs, commonly called devm APIs.

These APIs associate resources with a device. The device resource-management framework releases managed resources automatically during device teardown.

Example: devm_kzalloc()

struct device_data *data;

data = devm_kzalloc(
    &pdev->dev,
    sizeof(*data),
    GFP_KERNEL
);

if (!data)
    return -ENOMEM;

The memory is released automatically when the associated device's managed resources are released.

Advantages

  • Reduces manual cleanup code.
  • Helps simplify error handling in probe functions.
  • Reduces some resource leak risks.
Do not manually kfree() memory returned by devm_kzalloc(). Also, devm APIs do not eliminate all lifetime problems: resources must not be accessed after device teardown.

14. Memory Leak Prevention in Driver Initialization

Driver initialization often contains multiple operations that can fail. Every successfully allocated resource must be cleaned up if a later operation fails.

Example: Manual Cleanup

static int driver_initialize(void)
{
    struct device_data *data;
    int ret;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    ret = allocate_buffer(data);

    if (ret)
        goto err_data;

    ret = register_device();

    if (ret)
        goto err_buffer;

    return 0;

err_buffer:
    free_buffer(data);

err_data:
    kfree(data);
    return ret;
}

This example demonstrates the reverse-order cleanup pattern.

Cleanup Order

  1. Release the most recently acquired resource first.
  2. Continue in reverse order through initialization.
  3. Release the main structure last.

15. Detecting Memory Leaks in a Driver Development Workflow

A practical debugging workflow can combine static inspection, runtime instrumentation and repeated testing.

Recommended Process

  1. Review every allocation call.
  2. Identify all corresponding release paths.
  3. Check probe failure and remove paths.
  4. Run repeated open, close, bind and unbind tests.
  5. Inspect memory usage and slab statistics.
  6. Use kmemleak when supported.
  7. Use KASAN for memory safety errors.
  8. Inspect allocation backtraces.
  9. Fix resource lifetime problems.
  10. Repeat the test and compare results.

Useful Commands

cat /proc/meminfo

cat /proc/slabinfo

sudo slabtop

sudo cat /sys/kernel/debug/kmemleak

dmesg | grep -i -E "kasan|kmemleak|slab"

16. Practical Lab: Memory Allocation and Cleanup

Objective

Create a kernel module that allocates memory during initialization and releases it during module removal.

Source Code: memory_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/slab.h>

static char *buffer;

static int __init memory_demo_init(void)
{
    buffer = kzalloc(1024, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    snprintf(buffer, 1024, "Linux Kernel Memory Demo");

    pr_info("Memory allocated successfully\n");
    pr_info("Buffer content: %s\n", buffer);

    return 0;
}

static void __exit memory_demo_exit(void)
{
    kfree(buffer);
    buffer = NULL;

    pr_info("Memory released successfully\n");
}

module_init(memory_demo_init);
module_exit(memory_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Kernel Memory Allocation and Cleanup Demo");

Makefile

obj-m += memory_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Build the Module

make

Load the Module

sudo insmod memory_demo.ko

Inspect Kernel Messages

dmesg | tail -n 10

Expected messages include:

Memory allocated successfully
Buffer content: Linux Kernel Memory Demo

Unload the Module

sudo rmmod memory_demo

Expected message:

Memory released successfully
Expected Result: The module allocates a 1024-byte buffer during initialization, uses it, and releases it during module removal.

19. Best Practices for Kernel Memory Management

  • Check every allocation result.
  • Release memory on all error paths.
  • Use the correct deallocation function for each allocator.
  • Initialize structures when appropriate using kzalloc() or kcalloc().
  • Use devm APIs where device-managed resource lifetimes are appropriate.
  • Use reference counting for shared object lifetimes.
  • Avoid double free and use-after-free errors.
  • Validate array sizes and buffer lengths.
  • Test repeated driver initialization and removal.
  • Use kmemleak for possible leak detection when supported.
  • Use KASAN for memory safety debugging.
  • Document resource ownership clearly.

21. Interview Questions and Answers

Q1. What is a memory leak?

Answer: A memory leak occurs when dynamically allocated memory is no longer needed but is not released.

Q2. What causes memory leaks in kernel drivers?

Answer: Missing cleanup operations, incomplete error handling and incorrect resource lifetime management can cause memory leaks.

Q3. What is kmemleak?

Answer: kmemleak is a Linux kernel debugging facility that helps identify possible unreachable memory allocations.

Q4. What is the purpose of kmalloc()?

Answer: kmalloc() allocates physically contiguous kernel memory.

Q5. What is the purpose of kzalloc()?

Answer: kzalloc() allocates kernel memory and initializes it to zero.

Q6. What is the purpose of kfree()?

Answer: It releases memory allocated by compatible kmalloc-family allocation functions.

Q7. What is the difference between kmalloc() and vmalloc()?

Answer: kmalloc() returns physically contiguous memory, whereas vmalloc() provides virtually contiguous memory that may not be physically contiguous.

Q8. What is KASAN?

Answer: KASAN is a kernel memory error detector that identifies many out-of-bounds and use-after-free accesses.

Q9. Is KASAN a memory leak detector?

Answer: No. KASAN primarily detects memory safety errors. kmemleak is designed to help identify possible memory leaks.

Q10. What is slab allocator debugging?

Answer: It uses allocator debugging features to detect certain memory corruption and allocation misuse problems.

Q11. What is reference counting?

Answer: Reference counting tracks how many active references exist to an object and helps determine when it can be released.

Q12. What is devm_kzalloc()?

Answer: It allocates zeroed memory associated with a device's managed resources, which are released during device teardown.

Q13. Why is error-path cleanup important?

Answer: A driver may successfully allocate some resources before a later initialization step fails. Those earlier resources must be released.

Q14. What is a double-free error?

Answer: It occurs when the same memory allocation is released more than once.

Q15. How can memory leaks be prevented?

Answer: By tracking resource ownership, checking allocation failures, cleaning up every error path and testing repeated initialization and removal.

Q16. Does an empty kmemleak report prove that no leak exists?

Answer: No. kmemleak is a conservative detector and may not identify every possible leak.

Q17. What is the purpose of /proc/slabinfo?

Answer: It provides information about kernel slab caches and their allocation statistics.

Q18. Why should devm-managed memory not be manually freed with kfree()?

Answer: Its lifetime is managed by the device resource framework. Manually freeing it can cause invalid release operations or double free.

Q19. What is the reverse-order cleanup pattern?

Answer: Resources are released in the opposite order from which they were acquired.

Q20. Why is memory leak testing important for embedded Linux?

Answer: Embedded systems may run continuously with limited memory, so unreleased allocations can eventually cause allocation failures and instability.

22. Lesson Summary

  • A memory leak occurs when allocated memory is not released.
  • Kernel drivers must manage memory and resource lifetimes carefully.
  • kmalloc(), kzalloc() and vmalloc() provide different allocation behaviors.
  • kmemleak helps identify possible unreachable allocations.
  • Slab debugging helps investigate allocator-related problems.
  • KASAN detects many memory safety errors.
  • Reference counting helps manage shared object lifetimes.
  • devm APIs simplify device resource cleanup.
  • Error paths must release previously acquired resources.
  • Repeated testing helps identify resource leaks.
