2. Introduction to Kernel Module Testing

Kernel module testing is the process of verifying that a loadable kernel module works correctly, safely and reliably.

Unlike ordinary user-space programs, kernel modules execute in kernel space. A defect can affect the entire operating system.

Why testing is important

  • Detect programming errors before deployment.
  • Verify correct module initialization and cleanup.
  • Check memory allocation and resource management.
  • Validate user-space and kernel-space communication.
  • Detect race conditions and synchronization problems.
  • Prevent system crashes and data corruption.

3. Types of Kernel Testing

Testing TypePurpose
Unit TestingTests individual functions or small components.
Integration TestingTests interaction between driver components.
System TestingTests the complete driver in the operating environment.
Functional TestingChecks whether specified operations work correctly.
Regression TestingChecks whether new changes break existing functionality.
Stress TestingTests behavior under heavy or repeated workloads.
Performance TestingMeasures latency, throughput and resource usage.
Negative TestingChecks behavior with invalid inputs and failure conditions.

4. Unit Testing

Unit testing verifies individual functions or small logical components independently.

For a character device driver, functions that may be tested include:

  • Device initialization.
  • Memory allocation helpers.
  • Input validation.
  • Data-processing functions.
  • IOCTL command validation.
  • Error-handling paths.

Example: Data validation function

static int validate_value(int value)
{
    if (value < 0 || value > 100)
        return -EINVAL;

    return 0;
}

Test cases should cover:

-1-EINVAL
00

1000
101-EINVAL

This kind of helper is suitable for isolated unit testing using a kernel testing framework such as KUnit.

Integration test cases

  • Device registration succeeds.
  • Device node is available.
  • Open callback is invoked correctly.
  • Write operation transfers valid data.
  • Read operation returns expected data.
  • Release callback performs cleanup.
  • Resources are released after errors.

7. Testing Kernel Module Loading and Unloading

Every loadable kernel module should be tested for initialization and cleanup behavior.

List loaded modules

lsmod

Load a module

sudo insmod my_driver.ko

Check module information

lsmod | grep my_driver
modinfo my_driver.ko

Inspect kernel messages

sudo dmesg | tail -n 30

Remove the module

sudo rmmod my_driver

Verify removal

lsmod | grep my_driver

If the module is no longer listed, it has been removed from the loaded-module list.

Use the actual module name without the .ko extension with insmod and rmmod. Do not unload a driver that is currently in use by a critical device.

8. Testing Character Device Drivers

A character driver can be tested from user space through its device node.

Check device node

ls -l /dev/mydevice

Test writing data

echo "Hello Driver" | sudo tee /dev/mydevice

Test reading data

sudo cat /dev/mydevice

The actual result depends on how the driver's read and write callbacks are implemented. A driver that does not retain or return written data will not behave like a normal storage device.

Additional checks

  • Try opening the device multiple times.
  • Test empty and large input buffers.
  • Test invalid IOCTL commands.
  • Test access with different user permissions.
  • Check error return values.

9. Negative Testing

Negative testing verifies that a driver handles invalid or unexpected conditions safely.

Examples

  • Invalid IOCTL command.
  • Zero-length read or write.
  • Invalid user-space pointer.
  • Memory allocation failure.
  • Repeated open and close operations.
  • Device access after removal.
  • Unsupported device configuration.

Example: Invalid IOCTL handling

static long my_ioctl(struct file *file,
                     unsigned int cmd,
                     unsigned long arg)
{
    switch (cmd) {
    case MY_IOCTL_RESET:
        return 0;

    default:
        return -ENOTTY;
    }
}

An unsupported IOCTL command should return an appropriate error instead of silently performing an unintended operation.

10. Regression Testing

Regression testing checks whether modifications to a driver introduce defects in previously working functionality.

Example

Suppose a developer modifies the read callback to improve performance. Regression testing should verify that:

  • Read operations still return correct data.
  • Write operations remain unaffected.
  • IOCTL operations still work.
  • Memory is released correctly.
  • Module initialization and cleanup still work.

Automated test cases can be executed again after each important code change.

11. Introduction to KUnit

KUnit is the Linux kernel's in-kernel unit testing framework.

It allows developers to write and execute tests for kernel code, including individual functions and internal components.

KUnit features

  • Kernel-level unit testing.
  • Test cases organized into test suites.
  • Assertions and expectation checks.
  • Integration with kernel build and test infrastructure.
  • Structured test result reporting.

Example KUnit test

#include <kunit/test.h>

static int add_values(int a, int b)
{
    return a + b;
}

static void add_values_test(struct kunit *test)
{
    KUNIT_EXPECT_EQ(test, add_values(2, 3), 5);
    KUNIT_EXPECT_EQ(test, add_values(0, 0), 0);
}

static struct kunit_case add_test_cases[] = {
    KUNIT_CASE(add_values_test),
    {}
};

static struct kunit_suite add_test_suite = {
    .name = "add-values-test",
    .test_cases = add_test_cases,
};

kunit_test_suite(add_test_suite);

MODULE_LICENSE("GPL");

This example demonstrates a simple test of a pure helper function. A complete KUnit test must be built and executed using a kernel configuration with the required KUnit support.

12. Introduction to kselftest

kselftest is the Linux kernel's self-testing framework. It contains tests for kernel interfaces and subsystems, commonly including user-space test programs.

Purpose

  • Test kernel functionality through supported interfaces.
  • Validate system calls and subsystem behavior.
  • Run repeatable tests across kernel versions.
  • Help detect regressions.

Kernel source location

tools/testing/selftests/

Build and run an individual selftest suite

cd linux
make -C tools/testing/selftests TARGETS=timers
sudo make -C tools/testing/selftests TARGETS=timers run_tests

The selected target is only an example. Available targets depend on the kernel source version and configuration.

13. Automated Testing

Automated testing executes predefined test cases without requiring a developer to perform every step manually.

Advantages

  • Repeatable testing.
  • Reduced manual effort.
  • Faster regression detection.
  • Consistent test execution.
  • Useful test logs and reports.

Example shell test script

#!/bin/bash

MODULE="my_driver"

echo "Checking whether module is loaded..."

if lsmod | grep -q "^${MODULE} "; then
    echo "Module is already loaded."
else
    echo "Loading module..."
    sudo insmod "${MODULE}.ko" || exit 1
fi

echo "Checking module..."
lsmod | grep "^${MODULE} "

echo "Recent kernel messages:"
sudo dmesg | tail -n 15

echo "Removing module..."
sudo rmmod "${MODULE}" || exit 1

echo "Module test completed."

Save the script as test_module.sh.

Make it executable

chmod +x test_module.sh

Execute the test

./test_module.sh
Run this only with a test module that is safe to load and unload. The script assumes the module file is in the current directory and that its name matches the module name.

14. Stress Testing

Stress testing evaluates driver behavior under heavy or repeated workloads.

Examples

  • Repeatedly opening and closing a device.
  • Performing many read and write operations.
  • Testing multiple concurrent processes.
  • Running the driver for an extended period.
  • Testing repeated module initialization and cleanup.

Example user-space stress loop

for i in $(seq 1 1000)
do
    echo "Test $i" > /dev/mydevice
done

This example repeatedly writes data to a device node. It should only be used with a test driver designed to accept such writes.

15. Testing Memory and Resource Management

Drivers must release all resources correctly when operations fail or the module is unloaded.

Resources to test

  • Allocated kernel memory.
  • Device numbers.
  • Character-device registrations.
  • Interrupt handlers.
  • Timers and workqueues.
  • Device and class objects.
  • Locks and synchronization objects.

Useful debugging facilities

ToolPurpose
KASANDetects many kernel memory access errors.
kmemleakHelps detect possible memory leaks.
lockdepDetects certain locking errors.
KCSANDetects data races.
SLUB debuggingHelps investigate slab allocator issues.

16. Testing in a Virtual Machine

Ubuntu running inside VirtualBox provides a useful isolated environment for learning and testing many Linux kernel modules.

Recommended workflow

  1. Take a VirtualBox snapshot before risky kernel experiments.
  2. Record the running kernel version.
  3. Install matching kernel headers and build tools.
  4. Build a test module.
  5. Load and test it in the guest operating system.
  6. Monitor kernel messages.
  7. Remove the module and check cleanup.

Check kernel version

uname -r

Check installed headers

ls /lib/modules/$(uname -r)/build
VirtualBox is suitable for many software-driver tests, but it does not automatically provide access to physical GPIO, I2C or SPI controllers on the host. USB passthrough can expose supported USB devices when configured.

18. Practical Exercise – Test a Basic Kernel Module

Objective: Build, load, inspect and unload a simple kernel module.

Step 1: Create the source file

Create test_module.c.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init test_module_init(void)
{
    pr_info("Test module loaded successfully\n");
    return 0;
}

static void __exit test_module_exit(void)
{
    pr_info("Test module unloaded successfully\n");
}

module_init(test_module_init);
module_exit(test_module_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic kernel module testing example");

Step 2: Create the Makefile

obj-m += test_module.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Step 3: Compile the module

make

Step 4: Load the module

sudo insmod test_module.ko

Step 5: Check kernel messages

sudo dmesg | tail -n 10

Step 6: Check loaded modules

lsmod | grep test_module

Step 7: Unload the module

sudo rmmod test_module

Step 8: Verify cleanup

sudo dmesg | tail -n 10

Expected Result: The module should compile, load and unload successfully. Kernel messages should show the initialization and cleanup messages.

19. Best Practices for Kernel Module Testing

  • Test in an isolated development environment.
  • Keep a backup or VM snapshot before risky tests.
  • Test initialization and cleanup paths.
  • Check every important error-handling path.
  • Test invalid input and boundary conditions.
  • Use KUnit for suitable unit tests.
  • Use kselftest for relevant kernel interface tests.
  • Automate repeatable test procedures.
  • Monitor kernel logs during testing.
  • Repeat regression tests after code changes.
  • Never treat a successful module load as proof that the driver is correct.
