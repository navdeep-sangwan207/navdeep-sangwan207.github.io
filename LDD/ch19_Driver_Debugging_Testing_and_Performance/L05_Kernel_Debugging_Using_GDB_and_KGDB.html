1. Learning Objectives

After completing this lesson, you will be able to:

  • Understand the role of GDB in Linux kernel debugging.
  • Differentiate between GDB and KGDB.
  • Understand kernel debugging symbols.
  • Use GDB to inspect kernel symbols and source code.
  • Understand breakpoints, watchpoints and backtraces.
  • Understand remote debugging using KGDB.
  • Identify the limitations of kernel debugging in a virtual machine.

2. Introduction to GDB

GDB (GNU Debugger) is a debugging tool used to examine program execution, inspect variables, set breakpoints and identify software errors.

GDB is commonly used for user-space application debugging. It can also inspect kernel-related symbols and analyze kernel debugging information when suitable debug symbols and kernel images are available.

Important GDB capabilities

  • Set breakpoints at functions or source-code lines.
  • Execute programs step by step.
  • Inspect variables and memory.
  • Display function call stacks.
  • Examine registers and processor state.
  • Inspect compiled code and debugging symbols.

3. Why Is GDB Used in Kernel Development?

Kernel code executes in privileged mode. A defect in a kernel module can affect the entire operating system.

GDB-based debugging helps developers investigate:

  • Incorrect pointer references.
  • Unexpected function execution.
  • Incorrect variable values.
  • Kernel call-stack problems.
  • Unexpected control flow.
  • Module and kernel symbol information.
Important: GDB alone does not automatically attach to a running Linux kernel. Live kernel debugging requires an appropriate debugging interface, such as KGDB, or another supported kernel-debugging mechanism.

4. Kernel Debugging Symbols

Debugging symbols associate compiled machine instructions with information such as function names, source-code locations and variable details.

Without debug information, debugging output may contain mostly memory addresses and limited symbol information.

Why symbols matter

  • Identify kernel functions.
  • Map instructions to source-code lines.
  • Inspect local variables when available.
  • Understand stack traces.

Useful kernel configuration options

CONFIG_DEBUG_INFO=y
CONFIG_GDB_SCRIPTS=y
CONFIG_FRAME_POINTER=y

These options depend on kernel version, architecture and debugging requirements. Some may not be available or necessary in every kernel configuration.

5. Inspecting Kernel Symbols with GDB

GDB can inspect an uncompressed kernel image containing suitable debugging information.

For example, on many x86 systems, the kernel image is available as vmlinux in the kernel build directory.

Start GDB

gdb vmlinux

Useful GDB commands

CommandPurpose
info functionsList known functions.
info variablesDisplay known variables.
listDisplay source code.
disassembleDisplay machine instructions.
break function_nameSet a breakpoint.
btDisplay a backtrace.
quitExit GDB.
(gdb) info functions
(gdb) list
(gdb) disassemble
(gdb) quit
Note: A kernel image containing symbols is not the same as a live debugging connection. Inspecting symbols does not stop or control the running kernel.

6. Understanding Breakpoints

A breakpoint tells a debugger to pause execution when a specified location is reached.

Example GDB commands

(gdb) break start_kernel
(gdb) info breakpoints
(gdb) delete 1

In live kernel debugging, a breakpoint can pause kernel execution. This can affect the entire system, including other CPUs and time-sensitive operations.

Types of breakpoints

  • Function breakpoint: Stops at a function.
  • Source-line breakpoint: Stops at a source-code line.
  • Conditional breakpoint: Stops when a condition is satisfied.
  • Hardware breakpoint: Uses processor debugging support where available.

7. Understanding Watchpoints

A watchpoint monitors a variable or memory location and reports when its value changes or is accessed, depending on the watchpoint type.

Common GDB watchpoint commands

(gdb) watch variable
(gdb) rwatch variable
(gdb) awatch variable
(gdb) info watchpoints
CommandMeaning
watchStop when an expression changes.
rwatchStop when an expression is read.
awatchStop when an expression is accessed.

Watchpoint support and the number of hardware watchpoints depend on the target processor and debugging environment.

8. Understanding Backtraces

A backtrace displays the sequence of function calls that led to the current execution point.

It is especially useful when investigating crashes, unexpected function calls and kernel faults.

GDB command

(gdb) bt
(gdb) backtrace

A typical backtrace contains:

  • Function names.
  • Source-code locations, when symbols are available.
  • Function arguments, when available.
  • Call-stack relationships.
Kernel crash reports may also provide stack traces through kernel logs. These traces can be analyzed alongside symbol information.

9. Introduction to KGDB

KGDB (Kernel GNU Debugger) is a kernel debugging facility that allows a debugger such as GDB to communicate with a running Linux kernel.

KGDB typically uses a serial connection or another supported transport to connect a development machine to the target machine.

KGDB architecture

Development Computer
        |
        | GDB
        |
   Debugging Link
        |
        | Serial / Supported Transport
        |
Target Linux System
        |
        | KGDB
        |
   Linux Kernel
        |
   Kernel Module

The development computer runs GDB, while the target system runs the kernel being debugged.

10. GDB vs KGDB

FeatureGDBKGDB
Full nameGNU DebuggerKernel GNU Debugger
Main purposeGeneral debuggingLive Linux kernel debugging
Kernel awarenessCan inspect kernel symbols and imagesProvides a kernel debugging interface
BreakpointsFor supported debugging targetsCan set breakpoints in a live kernel
Remote debuggingSupportedUses GDB remote debugging protocol
Typical useApplication and offline analysisKernel and driver debugging

KGDB is not a replacement for GDB. It provides the kernel-side support that allows GDB to debug the running kernel.

11. KGDB Configuration

KGDB support must be enabled in the target kernel configuration. Exact configuration options and transport support depend on the kernel version and platform.

Common configuration options

CONFIG_KGDB=y
CONFIG_KGDB_SERIAL_CONSOLE=y
CONFIG_DEBUG_INFO=y

Some systems also require architecture-specific debugging support and a suitable serial driver.

Kernel boot parameters

A typical serial KGDB setup may use parameters similar to:

kgdboc=ttyS0,115200
kgdbwait
  • kgdboc configures the KGDB I/O transport.
  • ttyS0 identifies a serial port in this example.
  • 115200 specifies the baud rate.
  • kgdbwait requests that the kernel wait for a debugger during boot.
These are configuration examples, not universal commands. The serial device name, kernel configuration, bootloader setup and transport support must match the target system. Incorrect boot parameters can prevent normal booting.

12. Connecting GDB to a KGDB Target

Once KGDB is configured and the target kernel is ready, GDB can connect through the configured debugging transport.

Example workflow

# On the development computer
gdb vmlinux

# Inside GDB
(gdb) target remote /dev/ttyUSB0

The example assumes a supported serial connection exposed as /dev/ttyUSB0. Actual device names and connection arrangements vary.

After connection

(gdb) break some_kernel_function
(gdb) continue
(gdb) bt
(gdb) info registers
(gdb) continue

GDB commands allow the developer to inspect execution, examine registers and resume the target kernel.

13. Debugging a Linux Device Driver

KGDB can help investigate problems in a device driver by allowing the developer to inspect the kernel while driver code is executing.

Example driver function

static int mydriver_open(struct inode *inode,
                         struct file *file)
{
    pr_info("mydriver: device opened\n");

    return 0;
}

A developer can use kernel symbols and source information to investigate the function when it is reached during a suitable KGDB debugging session.

Possible debugging objectives

  • Check whether the open callback executes.
  • Inspect the inode and file structures.
  • Trace unexpected control flow.
  • Investigate a kernel fault.
  • Inspect the call stack and processor registers.

15. Limitations and Safety Considerations

  • Kernel debugging requires compatible kernel images and debugging symbols.
  • KGDB support must be built into or enabled in the target kernel.
  • Serial debugging requires a correctly configured transport.
  • Breakpoints can pause kernel execution and affect system responsiveness.
  • Timing-sensitive bugs may disappear or change when debugging.
  • Debugging a production system can cause service interruption.
  • Kernel and GDB versions, architecture and symbol files must be compatible.
Do not experiment with KGDB boot parameters on your primary operating system without a recovery method. Use a disposable virtual machine or dedicated test system.

16. Practical Exercise – Inspecting Kernel Symbols

Objective: Learn how GDB opens a kernel image and displays debugging information.

Environment: Ubuntu Linux in VirtualBox.

Step 1: Install GDB

sudo apt update
sudo apt install gdb

Step 2: Locate the kernel image

ls -l /boot/vmlinuz-$(uname -r)

The compressed boot image is not normally the preferred input for source-level GDB inspection. A suitable uncompressed vmlinux image with debug symbols is required.

Step 3: Install matching debug information

On Ubuntu, availability and package names depend on the kernel build and repository configuration. One possible package family is:

linux-image-$(uname -r)-dbgsym

If matching debug symbols are unavailable, use a separately built test kernel with debug information enabled.

Step 4: Open the suitable kernel image

gdb /path/to/vmlinux

Step 5: Inspect symbols

(gdb) info functions
(gdb) info variables
(gdb) quit

Expected Result: GDB loads the kernel image and displays available symbol information. This exercise does not attach to or modify the running kernel.

17. VirtualBox and KGDB Practical Notes

Since this course uses Ubuntu in VirtualBox, distinguish between inspecting kernel symbols and performing live remote kernel debugging.

  • GDB can be used inside Ubuntu to inspect a suitable kernel image.
  • Live KGDB debugging requires a compatible target kernel and configured debugging transport.
  • A virtual serial port can be configured in VirtualBox for a controlled two-machine debugging arrangement.
  • Two virtual machines may be used: one as the development machine and one as the target.
  • Both machines need compatible kernel source, build configuration and symbols.
Recommended learning approach: First practise GDB commands and symbol inspection. Then study KGDB architecture and remote debugging before attempting a live kernel-debugging setup.
