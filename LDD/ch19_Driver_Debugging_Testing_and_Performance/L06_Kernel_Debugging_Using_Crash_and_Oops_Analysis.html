2. Introduction to Kernel Crashes

The Linux kernel manages system resources, memory, processes, hardware and device drivers. A serious error in kernel code can affect the stability of the entire operating system.

A kernel crash occurs when the kernel encounters an error that prevents it from continuing normal execution safely.

Common causes

  • Invalid memory access.
  • Dereferencing a NULL pointer.
  • Use-after-free errors.
  • Buffer overflow or memory corruption.
  • Incorrect interrupt handling.
  • Race conditions and synchronization errors.
  • Invalid hardware or DMA operations.
  • Defects in kernel modules.

3. What Is a Kernel Oops?

A kernel Oops is a diagnostic report generated when the Linux kernel detects a serious error during execution.

It usually contains information that helps developers identify the location and circumstances of the failure.

An Oops report may contain

  • Kernel version and system information.
  • Error description.
  • Faulting instruction pointer.
  • CPU register values.
  • Process name and process identifier.
  • Call trace.
  • Loaded kernel modules.
BUG: unable to handle kernel NULL pointer dereference
Oops: 0002 [#1] SMP
CPU: 0 PID: 1234 Comm: test_app
RIP: 0010:my_driver_function+0x20/0x80
Call Trace:
  my_driver_function
  device_operation
  ...

This is an illustrative example. Actual Oops messages differ according to the processor architecture and kernel version.

4. What Is a Kernel Panic?

A kernel panic occurs when the kernel determines that it cannot safely continue operating.

Depending on the configuration and failure, the system may stop execution, reboot automatically or enter a crash-dump capture process.

Typical causes

  • Critical kernel data corruption.
  • Severe memory-management failure.
  • Fatal errors in kernel code.
  • Unrecoverable hardware or architecture exceptions.
  • An Oops escalated to panic by kernel policy.
Kernel panic - not syncing:
Fatal exception in interrupt
An Oops does not always immediately stop the system. However, continuing after an Oops can leave kernel state corrupted and cause additional failures.

6. Understanding Kernel Call Traces

A call trace displays the sequence of function calls associated with an error.

It helps developers understand how execution reached the faulty function.

Example

Call Trace:
 dump_stack
 my_driver_read
 vfs_read
 ksys_read
 __x64_sys_read
 do_syscall_64
 entry_SYSCALL_64_after_hwframe

How to interpret it

  1. Identify the function associated with the fault.
  2. Locate the function in the driver source code.
  3. Inspect the functions called before the failure.
  4. Check pointers, memory access and synchronization.
  5. Correlate the trace with the surrounding kernel log messages.
A call trace is not always a complete chronological history. It represents the stack at the time of the report, and its interpretation depends on symbols, architecture and stack reliability.

7. Understanding Register Information

Kernel Oops reports commonly include processor register values at the time of the fault.

Registers are small, high-speed storage locations inside the CPU. They hold addresses, data and execution-state information.

Examples of x86-64 registers

RegisterTypical purpose
RIPInstruction pointer
RSPStack pointer
RBPFrame pointer when used
RAXGeneral-purpose register
RBXGeneral-purpose register
CR2Faulting linear address for certain page faults

For example, if the report identifies a page fault and shows an invalid address in the relevant fault information, the developer investigates the pointer or memory access that produced it.

Register names and meanings vary by CPU architecture. The table describes common x86-64 examples, not ARM or ARM64 register conventions.

8. Common Driver Errors Behind Oops Reports

8.1 NULL Pointer Dereference

struct my_device *dev = NULL;

/* Invalid access */
dev->status = 1;

The code attempts to access a structure member through a NULL pointer.

8.2 Use-After-Free

kfree(dev);

/* Invalid: memory has already been freed */
dev->status = 1;

The driver accesses memory after releasing it.

8.3 Invalid Array Access

int values[5];

values[10] = 100;

The code writes outside the valid array bounds. In kernel code, such memory corruption can cause unpredictable failures.

8.4 Incorrect Resource Handling

Examples include releasing an interrupt handler incorrectly, accessing an unmapped I/O region or using a device resource after its lifetime has ended.

9. Collecting Kernel Error Messages

The kernel log buffer stores messages generated by the kernel. These messages can help identify the sequence of events leading to an error.

Useful commands

dmesg
dmesg -T
dmesg -w
dmesg | tail -n 50
sudo journalctl -k
CommandPurpose
dmesgDisplay kernel messages.
dmesg -TDisplay human-readable timestamps where supported.
dmesg -wFollow new kernel messages.
dmesg | tail -n 50Display the latest 50 lines.
journalctl -kDisplay kernel messages stored by systemd journal.

After a reboot, earlier messages may not remain in the normal ring buffer. Persistent journal storage or crash-dump facilities may be needed to preserve failure information.

10. What Is a Kernel Crash Dump?

A kernel crash dump is a snapshot of relevant system memory captured after a kernel failure.

It allows developers to investigate the system state after the original failure, without needing to reproduce the problem immediately.

Important crash-dump information

  • Kernel memory state.
  • CPU register information.
  • Process and task structures.
  • Kernel stack information.
  • Loaded module information.
  • Memory-management state.

A common crash-dump file is named vmcore.

/var/crash/
    timestamp/
        vmcore
        dmesg

The exact directory structure depends on the crash-dump configuration and distribution.

11. Introduction to Kdump

Kdump is a Linux kernel crash-dumping mechanism. It uses a reserved memory region to start a secondary capture kernel after the production kernel crashes.

Kdump architecture

Primary Linux Kernel
        |
        | Fatal Kernel Failure
        |
     Kexec
        |
        v
Capture Kernel
        |
        | Collects Memory Information
        |
        v
     vmcore
        |
        v
Offline Crash Analysis

Main components

  • Primary kernel: The normal operating kernel.
  • Reserved memory: Memory reserved for crash capture.
  • Capture kernel: A secondary kernel used to collect crash information.
  • vmcore: The captured memory dump.
Kdump must be configured before a crash occurs. It cannot normally recover a complete memory dump from a system that has already crashed without a configured capture mechanism.

12. Introduction to the crash Utility

The crash utility is an interactive tool for analyzing Linux kernel crash dumps and live systems where supported.

It can examine kernel structures, processes, memory, stacks and kernel symbols.

Install crash on Ubuntu

sudo apt update
sudo apt install crash

Basic syntax

crash <VMLINUX_FILE> <VMCORE_FILE>

The kernel image and dump must be compatible. Use the matching uncompressed kernel image and appropriate debugging symbols for meaningful analysis.

14. Analyzing a Driver Crash

Consider a hypothetical character driver that crashes while handling a read request.

Example faulty code

static ssize_t my_read(struct file *file,
                       char __user *buffer,
                       size_t count,
                       loff_t *offset)
{
    struct my_device *dev = file->private_data;

    dev->status = 1;

    return 0;
}

If file->private_data is NULL or contains an invalid pointer, accessing dev->status may cause a kernel fault.

Debugging procedure

  1. Collect the Oops or panic report.
  2. Identify the faulting function and instruction.
  3. Inspect the call trace.
  4. Check how private_data is initialized.
  5. Verify the device structure's lifetime.
  6. Inspect the relevant source code and symbols.
  7. Correct the driver and repeat testing.

Safer validation example

static ssize_t my_read(struct file *file,
                       char __user *buffer,
                       size_t count,
                       loff_t *offset)
{
    struct my_device *dev = file->private_data;

    if (!dev)
        return -EINVAL;

    dev->status = 1;

    return 0;
}

This NULL check addresses one possible failure. It does not replace correct initialization, synchronization or lifetime management.

15. Kernel Symbols and Address Resolution

Crash reports often contain memory addresses and symbol offsets. Kernel symbol information helps translate these values into meaningful function names and locations.

Useful tools

uname -r
cat /proc/kallsyms
nm vmlinux
addr2line -e vmlinux ADDRESS

/proc/kallsyms exposes available kernel symbols, subject to system permissions and security settings. nm lists symbols in an object or executable file. addr2line maps suitable addresses to source locations when debugging information is available.

Address resolution requires the correct kernel image, matching build and appropriate symbol information. Kernel address randomization and relocation must also be considered when analyzing runtime addresses.

16. Practical Exercise – Inspecting Kernel Logs

Objective: Learn to identify kernel warnings and errors using Ubuntu.

Step 1: Display kernel messages

dmesg | tail -n 50

Step 2: Search for error messages

dmesg | grep -i error

Step 3: Search for warnings

dmesg | grep -i warning

Step 4: Search for Oops or panic messages

dmesg | grep -Ei 'oops|panic|BUG:'

Step 5: Inspect kernel journal messages

sudo journalctl -k -b

Expected Result: You should be able to inspect kernel logs and identify whether warnings, errors, Oops messages or panic messages are present. A normal system may not contain any Oops or panic records.

17. Practical Exercise – Inspecting a Crash Dump

Objective: Understand the offline crash-analysis workflow.

This exercise requires an existing crash dump and the matching kernel image. Do not intentionally crash your normal Ubuntu installation to create one.

Step 1: Install the crash utility

sudo apt update
sudo apt install crash

Step 2: Identify the required files

ls -lh /path/to/vmlinux
ls -lh /path/to/vmcore

Step 3: Open the dump

crash /path/to/vmlinux /path/to/vmcore

Step 4: Inspect the crash

crash> sys
crash> log
crash> bt
crash> ps
crash> mod

Expected Result: The crash utility loads the dump and displays available system, log, process, stack and module information. The quality of the analysis depends on the completeness of the dump and the matching symbols.

18. Common Challenges in Crash Analysis

  • Missing or incomplete crash dumps.
  • Using a kernel image from a different build.
  • Missing debugging symbols.
  • Corrupted stack information.
  • Memory corruption occurring before the reported fault.
  • Difficulty identifying the original cause from secondary errors.
  • Architecture-specific differences in register and stack interpretation.

Crash analysis is an investigative process. The reported fault location may be where corrupted state was detected, rather than where the original defect occurred.
