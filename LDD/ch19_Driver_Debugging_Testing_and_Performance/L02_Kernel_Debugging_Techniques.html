Level: Intermediate
Focus: Debugging kernel modules and Linux device drivers

1. Introduction

Kernel debugging is the process of identifying, analyzing and correcting errors in Linux kernel code and device drivers.

Unlike ordinary user-space applications, kernel code executes with privileged access to system resources. A programming error can cause memory corruption, system instability, a kernel oops or a kernel panic.

Linux provides several debugging techniques and tools:

  • Kernel log inspection.
  • Source-level debugging.
  • Kernel tracing.
  • Dynamic instrumentation.
  • Crash dump analysis.
  • Memory and concurrency checking.
  • Driver-specific diagnostic interfaces.

2. Common Kernel Debugging Problems

3. Kernel Log-Based Debugging

Kernel messages are an important first source of diagnostic information.

3.1 dmesg

The dmesg command displays messages from the kernel ring buffer.

dmesg
dmesg -T
dmesg -w
dmesg | tail -n 50

3.2 Filter Driver Messages

dmesg | grep -i driver
dmesg | grep -i error
dmesg | grep -i warning

3.3 journalctl

On systems using systemd, journalctl can be used to inspect kernel logs.

sudo journalctl -k
sudo journalctl -k -b
sudo journalctl -k -p warning
Note: Access to kernel logs may require elevated privileges or suitable system permissions.

4. Source-Level Debugging

Source-level debugging allows a developer to inspect kernel execution using source code, breakpoints, registers and variable information.

4.1 GDB

GDB is the GNU Debugger. It can be used with suitable kernel debugging configurations and debugging targets.

4.2 KGDB

KGDB provides facilities for debugging the Linux kernel using a remote GDB session.

It can allow developers to:

  • Set breakpoints in kernel code.
  • Inspect registers.
  • Examine memory.
  • Step through kernel execution.
  • Investigate driver behavior.

4.3 KDB

KDB is a kernel debugger that provides a command-line debugging environment for supported kernel configurations.

4.4 Typical Debugging Workflow

  1. Build a kernel or module with suitable debugging information.
  2. Configure a supported debugging environment.
  3. Connect to the target kernel.
  4. Set breakpoints or inspect execution.
  5. Reproduce the issue.
  6. Examine the call stack and relevant variables.
  7. Correct the code and retest.

5. Dynamic Debugging

Dynamic debugging allows selected debug messages to be enabled at runtime without enabling every debug message in the kernel.

It is useful when debugging a specific driver or source file.

5.1 Check Dynamic Debug Support

mount | grep debugfs
ls /sys/kernel/debug/dynamic_debug/

5.2 Enable Messages for a Module

echo 'module my_driver +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

5.3 Enable Messages for a File

echo 'file my_driver.c +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

5.4 Disable Messages

echo 'module my_driver -p' | sudo tee /sys/kernel/debug/dynamic_debug/control
Dynamic debug requires the relevant kernel support and debugfs interface. The exact control entries depend on the running kernel and compiled debug call sites.

6. Function Tracing

Function tracing helps developers understand which kernel functions execute and how execution flows through the system.

6.1 ftrace

ftrace is a Linux kernel tracing framework used to investigate function calls, scheduling activity, latency and other kernel events.

6.2 Check Available Tracers

cd /sys/kernel/tracing
cat available_tracers

On systems using the older mount location, tracing files may be available under /sys/kernel/debug/tracing.

6.3 Select a Function Tracer

cd /sys/kernel/tracing

echo nop | sudo tee current_tracer
echo function | sudo tee current_tracer

cat trace

6.4 Stop Tracing

echo nop | sudo tee current_tracer

6.5 Function Graph Tracer

echo function_graph | sudo tee current_tracer
cat trace

The function graph tracer can show nested function calls and help identify where execution time is being spent.

7. Tracepoints and perf

7.1 Tracepoints

Tracepoints are predefined instrumentation points in the kernel. They expose events that tracing tools can observe.

7.2 List Available Events

sudo perf list

7.3 perf

perf is a performance analysis tool that can collect and analyze information about CPU usage, events, scheduling and other system behavior.

sudo perf stat ls
sudo perf top

For kernel tracing, perf can also record supported events and produce reports.

sudo perf record -a
sudo perf report
The available events and tracing features depend on kernel configuration, CPU support, permissions and installed perf tools.

8. Debugging Kernel Modules

External kernel modules can be debugged using a combination of logging, dynamic debug, tracing and source-level debugging.

8.1 Inspect Module Information

lsmod
modinfo my_driver.ko

8.2 Inspect Kernel Messages

sudo dmesg -w

8.3 Check Module Loading

sudo insmod my_driver.ko
lsmod | grep my_driver

8.4 Remove Module

sudo rmmod my_driver

8.5 Common Module Debugging Checklist

  • Verify the module was compiled for the running kernel.
  • Check module dependencies.
  • Inspect initialization and cleanup functions.
  • Check return values from kernel APIs.
  • Verify memory allocation and release paths.
  • Check synchronization around shared data.
  • Inspect device registration and resource acquisition.
  • Verify that all resources are released during cleanup.

9. Practical Example: Debugging a Kernel Module

Objective: Create a module that generates diagnostic log messages and practise inspecting its execution.

9.1 Source Code: debug_demo.c

#include <linux/module.h>
#include <linux/init.h>
#include <linux/printk.h>

static int __init debug_demo_init(void)
{
    pr_info("debug_demo: initialization started\n");

    pr_info("debug_demo: checking driver resources\n");

    pr_warn("debug_demo: demonstration warning message\n");

    pr_info("debug_demo: initialization completed\n");

    return 0;
}

static void __exit debug_demo_exit(void)
{
    pr_info("debug_demo: cleanup started\n");
    pr_info("debug_demo: module removed\n");
}

module_init(debug_demo_init);
module_exit(debug_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Kernel debugging demonstration module");

9.2 Makefile

obj-m += debug_demo.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

9.3 Compile

make

9.4 Load the Module

sudo insmod debug_demo.ko

9.5 Inspect Messages

dmesg | tail -n 20

9.6 Remove the Module

sudo rmmod debug_demo

Expected Result

debug_demo: initialization started
debug_demo: checking driver resources
debug_demo: demonstration warning message
debug_demo: initialization completed
debug_demo: cleanup started
debug_demo: module removed

Actual output may include timestamps, log-level formatting and messages from other kernel components.

10. Debugging a Kernel Module Loading Failure

Suppose a module fails to load with an error such as:

insmod: ERROR: could not insert module driver.ko: Invalid module format

Follow these steps:

  1. Check the running kernel version using uname -r.
  2. Check the module metadata using modinfo.
  3. Verify that the module was built against matching kernel headers and configuration.
  4. Inspect dmesg for the detailed kernel error.
  5. Check module dependencies and symbol availability.
  6. Check module signing requirements if signature enforcement is enabled.
uname -r
modinfo driver.ko
dmesg | tail -n 40

12. Troubleshooting

Problem 1: dmesg Permission Denied

sudo dmesg

Some Linux configurations restrict access to kernel logs for unprivileged users.

Problem 2: Dynamic Debug Control Is Missing

Check whether dynamic debug and debugfs are supported and enabled in the running kernel.

grep CONFIG_DYNAMIC_DEBUG /boot/config-$(uname -r)
mount | grep debugfs

Problem 3: Tracing Directory Is Missing

Check whether tracefs is mounted.

sudo mount -t tracefs nodev /sys/kernel/tracing

Only perform the mount if it is not already mounted and the kernel supports tracefs.

Problem 4: perf Command Not Found

sudo apt update
sudo apt install linux-tools-common linux-tools-$(uname -r)

Package names and availability can vary by Ubuntu release and kernel build.

14. Interview Questions and Answers

Q1. What is kernel debugging?

It is the process of diagnosing and correcting problems in kernel code and device drivers.

Q2. What is KGDB?

KGDB is a kernel debugging facility that supports remote source-level debugging using GDB.

Q3. What is ftrace?

ftrace is a kernel tracing framework used to observe function execution, events and latency.

Q4. What is dynamic debugging?

It allows selected debug messages to be enabled at runtime.

Q5. What is the purpose of dmesg?

It displays messages stored in the kernel ring buffer.

Q6. What is the difference between debugging and tracing?

Debugging investigates faults and program state. Tracing records execution events and behavior over time.

Q7. What is perf?

perf is a Linux performance analysis tool that can collect and report hardware and software performance events.

Q8. Why should kernel logs be checked after loading a module?

They can reveal initialization errors, warnings, resource failures and other diagnostic information.

15. Lesson Summary

  • Kernel debugging identifies faults in kernel code and device drivers.
  • dmesg and journalctl help inspect kernel logs.
  • KGDB and KDB support source-level or interactive debugging.
  • Dynamic debug enables selected diagnostic messages.
  • ftrace and tracepoints help inspect kernel execution.
  • perf supports performance and event analysis.
  • Systematic debugging reduces driver development time and improves reliability.
