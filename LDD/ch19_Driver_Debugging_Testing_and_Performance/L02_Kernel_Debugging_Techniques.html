1. Introduction to Kernel Debugging Techniques

Kernel debugging techniques are methods used to investigate problems in Linux kernel code and device drivers.

Different techniques are useful for different types of failures. For example, logging helps identify execution flow, tracing helps understand function calls, and source-level debugging allows developers to inspect variables and execution state.

Common kernel debugging techniques include:

  • Kernel logging using printk() and pr_*() macros.
  • Dynamic debug.
  • Debugging using GDB and KGDB.
  • Kernel tracing using ftrace.
  • Function tracing and event tracing.
  • Debugging through debugfs.
  • Memory and concurrency debugging.
  • Crash dump analysis.

2. Logging-Based Debugging

Logging is one of the simplest techniques for understanding the execution flow of a driver.

Developers insert messages at important locations, such as module initialization, device registration, probe(), read(), write(), interrupt handling and device removal.

Example

static int my_driver_open(struct inode *inode,
                          struct file *file)
{
    pr_info("my_driver: open called\n");

    return 0;
}

When a user-space application opens the device file, the message can be inspected using:

sudo dmesg | tail -20

Advantages

  • Simple to implement.
  • Useful for identifying execution order.
  • Does not require a separate source-level debugger.
  • Useful during module development.

Limitations

  • Excessive logging can affect performance.
  • It does not automatically show every variable or execution state.
  • Timing-sensitive bugs may change when logging is added.

3. Dynamic Debugging

Dynamic debug allows developers to enable selected pr_debug() messages at runtime without recompiling the module, provided the kernel and code were built with the required dynamic-debug support.

Check the Dynamic Debug Interface

sudo mount -t debugfs none /sys/kernel/debug

cat /sys/kernel/debug/dynamic_debug/control

Enable Messages for a Module

echo 'module my_driver +p' | \
sudo tee /sys/kernel/debug/dynamic_debug/control

Disable Messages

echo 'module my_driver -p' | \
sudo tee /sys/kernel/debug/dynamic_debug/control

Enable Messages for a Specific File

echo 'file my_driver.c +p' | \
sudo tee /sys/kernel/debug/dynamic_debug/control

The module name or source filename must match the actual compiled code.

4. Source-Level Debugging

Source-level debugging allows developers to inspect kernel source code while it is executing.

A debugger can help inspect:

  • Variable values.
  • Function call sequences.
  • Stack traces.
  • Execution locations.
  • Memory addresses.
  • Conditional branches.

GDB

GDB is the GNU Debugger. It supports debugging programs and can also be used for kernel debugging when connected to a suitable kernel debugging target.

KGDB

KGDB provides kernel debugging support through a remote debugger connection. GDB running on a development machine can communicate with a target kernel configured for KGDB.

Ordinary GDB cannot simply attach to a running Linux kernel like it attaches to a normal user-space process. Kernel symbols, compatible debug information and a suitable debugging connection are required.

5. Kernel Debugging Using KGDB

KGDB is a kernel source-level debugging facility that allows a developer to control kernel execution using GDB.

Basic Architecture

+--------------------------+ | Development Computer | | | | GDB | +------------+-------------+ | Serial / Network Debug Connection | +------------v-------------+ | Target Linux System | | | | KGDB | | | | Linux Kernel | | | | Device Driver | +--------------------------+

Typical Requirements

  • Kernel configured with KGDB support.
  • Suitable kernel debug information.
  • GDB with compatible architecture support.
  • Supported serial or network debugging connection.
  • Access to the matching kernel source and symbols.

KGDB is particularly useful when investigating difficult driver problems that cannot be understood through logging alone.

6. Kernel Tracing

Kernel tracing records selected kernel activities so developers can understand what happens during execution.

Tracing is useful for investigating:

  • Function execution order.
  • Interrupt activity.
  • Scheduling behaviour.
  • System-call activity.
  • Function execution time.
  • Kernel event sequences.

ftrace

ftrace is the Linux kernel tracing framework. It provides function tracing, event tracing and other tracing facilities depending on kernel configuration.

Check Tracefs

mount | grep tracefs

ls /sys/kernel/tracing

If tracefs is not mounted, it may be mounted with:

sudo mount -t tracefs tracefs /sys/kernel/tracing

7. Function Tracing Using ftrace

Function tracing records function calls made by the kernel.

Check Available Tracers

cd /sys/kernel/tracing

cat available_tracers

Enable Function Tracing

echo function | sudo tee current_tracer

Enable Tracing

echo 1 | sudo tee tracing_on

Read the Trace

sudo cat trace

Stop Tracing

echo 0 | sudo tee tracing_on

Reset the Trace

echo nop | sudo tee current_tracer
echo | sudo tee trace
Tracing output may contain a large amount of data. Keep tracing focused on the required functions or events. Availability and permissions depend on the running kernel configuration.

8. Function Graph Tracing

Function graph tracing records function entry and return relationships. It helps visualize nested function execution and approximate function durations.

Select the Function Graph Tracer

cd /sys/kernel/tracing

echo function_graph | sudo tee current_tracer
echo 1 | sudo tee tracing_on

View Results

sudo cat trace

Stop Tracing

echo 0 | sudo tee tracing_on

Function graph tracing can help identify which functions are called during a driver operation and where execution spends time.

9. Event Tracing

Event tracing records specific kernel events, such as scheduling, interrupts, system calls and block I/O events.

List Available Events

cd /sys/kernel/tracing

cat available_events

Enable a Scheduler Event

echo 1 | sudo tee events/sched/sched_switch/enable

Inspect the Trace

sudo cat trace

Disable the Event

echo 0 | sudo tee events/sched/sched_switch/enable

Event names depend on the kernel version and configuration. Check available_events before enabling a particular event.

10. Debugging Through debugfs

debugfs is a virtual filesystem designed primarily for kernel developers to expose debugging information.

It is commonly mounted at:

/sys/kernel/debug

Mount debugfs

sudo mount -t debugfs none /sys/kernel/debug

List Debugging Entries

ls /sys/kernel/debug

Kernel subsystems and drivers may create debugging files and directories under debugfs.

debugfs is not intended to provide a stable user-space ABI. Its entries can change between kernel versions and should not be treated as permanent application interfaces.

11. Memory Debugging Techniques

Kernel memory debugging techniques help identify invalid memory operations and allocation problems.

TechniquePurpose
KASANDetects memory safety problems such as out-of-bounds access and use-after-free.
kmemleakReports possible unreachable kernel memory allocations.
SLUB debuggingHelps detect certain slab allocator problems.
Page poisoningHelps expose some memory corruption and use-after-free problems.
DEBUG_PAGEALLOCProvides additional checks for page allocation and freeing.

Check Memory Debugging Configuration

grep -E 'CONFIG_(KASAN|DEBUG_KMEMLEAK|SLUB_DEBUG)' \
/boot/config-$(uname -r)

These facilities may require a specially configured kernel and may add execution or memory overhead.

12. Concurrency Debugging

Concurrency debugging helps identify errors caused by multiple execution contexts accessing shared resources.

Common Problems

  • Race conditions.
  • Deadlocks.
  • Incorrect lock ordering.
  • Missing synchronization.
  • Unsafe access to shared variables.

Important Kernel Facilities

FacilityPurpose
LockdepDetects locking dependency problems and potential deadlocks.
KCSANDetects certain data races.
Atomic operationsProvide atomic updates to supported data types.
Spinlock debuggingHelps investigate incorrect spinlock usage.

These facilities are especially useful for drivers that use interrupts, workqueues, timers and multiple threads.

13. Crash Dump Analysis

A crash dump contains information about system memory and execution state at the time of a kernel crash.

Crash dump analysis can help investigate failures that cannot easily be reproduced.

Important Components

  • Kernel crash dump.
  • Matching kernel image and debug symbols.
  • Kernel configuration information.
  • Crash analysis utilities such as crash.

Check Whether kdump Is Available

systemctl status kdump

On Ubuntu, the service and package configuration may differ. A crash dump facility must be installed and configured before a crash occurs.

Crash Utility

crash /path/to/vmlinux /path/to/vmcore

The vmlinux file should correspond to the crashed kernel and contain suitable debugging information.

15. Practical Exercise: Trace Kernel Functions

Objective

Use ftrace in Ubuntu to observe kernel function execution.

Step 1: Check Tracefs

mount | grep tracefs

Step 2: Open the Tracing Directory

cd /sys/kernel/tracing

Step 3: Check Available Tracers

cat available_tracers

Step 4: Select Function Tracing

echo function | sudo tee current_tracer

Step 5: Start Tracing

echo 1 | sudo tee tracing_on

Step 6: Read Trace Data

sudo cat trace | head -50

Step 7: Stop Tracing

echo 0 | sudo tee tracing_on

Step 8: Reset the Tracer

echo nop | sudo tee current_tracer

Expected Result

The trace file should contain function execution records if function tracing is supported and enabled. The exact functions and output depend on kernel activity.

Run tracing commands with appropriate privileges. Do not leave broad tracing enabled unnecessarily because it can generate large logs and affect performance.

16. Debugging Workflow for Device Drivers

Reproduce Driver Failure | v Collect Kernel Logs | v Select Debugging Method | +---------+---------+ | | | v v v Logs Tracing KGDB | | | +---------+---------+ | v Analyze Root Cause | v Fix Driver | v Recompile and Test | v Verify Correct Behaviour

17. Best Practices

  1. Choose a debugging method appropriate to the problem.
  2. Start with kernel logs before using more complex tools.
  3. Use targeted tracing rather than tracing everything.
  4. Keep kernel source, configuration and debug symbols consistent.
  5. Disable tracing when testing is complete.
  6. Use memory and concurrency debugging facilities when needed.
  7. Test driver error paths as well as normal operation.
  8. Use a recoverable development environment for risky experiments.
  9. Record the kernel version and debugging configuration.
  10. Verify that the fix does not introduce new failures.

18. Important Points to Remember

  • Logging is the simplest kernel debugging technique.
  • Dynamic debug enables selected debug messages at runtime.
  • KGDB supports source-level kernel debugging.
  • ftrace provides function and event tracing.
  • Function graph tracing shows nested function execution.
  • debugfs exposes kernel debugging information.
  • KASAN and kmemleak help investigate memory problems.
  • Lockdep and KCSAN help identify concurrency issues.
  • Crash dumps help investigate kernel failures.
  • Different problems require different debugging tools.

20. Lesson Summary

Linux provides several debugging techniques for investigating device-driver failures. Logging and dynamic debug help inspect messages, KGDB supports source-level debugging, and ftrace records kernel execution and events.

Memory debugging, concurrency analysis and crash dump examination provide additional methods for diagnosing complex kernel problems.

Choosing the correct technique and following a systematic debugging workflow are essential for developing stable and reliable Linux device drivers.
