2. Introduction to Debugfs

debugfs is a virtual filesystem provided by the Linux kernel for exposing internal debugging information to user space.

Kernel developers and driver developers use debugfs to inspect internal driver state, counters, configuration values and diagnostic information during development and troubleshooting.

It is commonly mounted at:

/sys/kernel/debug

Unlike a normal disk filesystem, debugfs does not store ordinary files on a storage device. Its entries are interfaces created by kernel components.

Why Do We Need Debugfs?

  • Inspect internal driver variables.
  • Read hardware or software status information.
  • Monitor event and error counters.
  • Expose diagnostic information without creating a complete device interface.
  • Support development-time debugging and testing.
Important: debugfs is intended for debugging and development. It is not a stable userspace ABI and should not be used as the primary interface for production applications.

3. Debugfs vs Procfs vs Sysfs

Linux provides multiple virtual filesystems. Their purposes are different.

Filesystem Mount Point Primary Purpose
debugfs /sys/kernel/debug Kernel and driver debugging information.
procfs /proc Process information and selected kernel interfaces.
sysfs /sys Device, driver, bus and kernel object representation.

Example Uses

  • debugfs: Display a driver's internal interrupt counter.
  • procfs: Inspect process information through /proc.
  • sysfs: Inspect a device's attributes under /sys/devices.
Do not expose stable application configuration or essential production controls through debugfs. Use an appropriate subsystem interface, sysfs attribute, device node, netlink interface or another documented ABI instead.

4. Mounting Debugfs

Before accessing debugfs entries, check whether the filesystem is mounted.

Step 1: Check the Mount

mount | grep debugfs

Step 2: Mount Debugfs if Required

sudo mount -t debugfs none /sys/kernel/debug

Step 3: Verify the Mount

mount | grep debugfs
ls /sys/kernel/debug

Step 4: Inspect Existing Entries

ls -l /sys/kernel/debug
Mounting debugfs may require root privileges. Some distributions or security configurations may restrict access to it.

5. Important Debugfs APIs

The Linux kernel provides helper functions for creating and removing debugfs entries.

API Purpose
debugfs_create_dir() Creates a debugfs directory.
debugfs_create_file() Creates a debugfs file with file operations.
debugfs_create_u32() Creates a simple interface for a 32-bit unsigned value.
debugfs_create_bool() Creates a simple interface for a Boolean value.
debugfs_create_x32() Creates an interface for displaying a 32-bit value in hexadecimal.
debugfs_remove() Removes a debugfs entry and its descendants.
debugfs_remove_recursive() Recursively removes a debugfs directory tree; available in kernels that provide this API.
debugfs_initialized() Checks whether debugfs support is initialized.

Header File

#include <linux/debugfs.h>

Basic Directory Creation

struct dentry *debug_dir;

debug_dir = debugfs_create_dir("my_driver", NULL);

This creates a directory named my_driver under the debugfs root when debugfs is available.

Creating a Debugfs File

struct dentry *file;

file = debugfs_create_file(
    "status",
    0444,
    debug_dir,
    NULL,
    &my_fops
);

The file operations structure defines how user space reads or writes the debugfs file.

6. Creating a Debugfs Directory and File

Suppose a character driver maintains an internal event counter. We want to expose that counter through debugfs.

The directory structure will look like this:

/sys/kernel/debug/
    my_debug_driver/
        event_count

The event_count file will display the current counter value.

Example Kernel Module

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/debugfs.h>
#include <linux/atomic.h>
#include <linux/uaccess.h>
#include <linux/err.h>

static struct dentry *debug_dir;
static atomic_t event_count = ATOMIC_INIT(0);

static ssize_t event_count_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position)
{
    char text[32];
    int value;
    int length;

    value = atomic_read(&event_count);

    length = scnprintf(
        text,
        sizeof(text),
        "%d\n",
        value
    );

    return simple_read_from_buffer(
        buffer,
        count,
        position,
        text,
        length
    );
}

static const struct file_operations event_count_fops = {
    .owner = THIS_MODULE,
    .read = event_count_read,
    .llseek = default_llseek,
};

static int __init debugfs_demo_init(void)
{
    struct dentry *file;

    pr_info("Debugfs demo: module loaded\n");

    debug_dir = debugfs_create_dir(
        "my_debug_driver",
        NULL
    );

    if (IS_ERR_OR_NULL(debug_dir)) {
        pr_err("Failed to create debugfs directory\n");
        return -ENOMEM;
    }

    file = debugfs_create_file(
        "event_count",
        0444,
        debug_dir,
        NULL,
        &event_count_fops
    );

    if (IS_ERR_OR_NULL(file)) {
        debugfs_remove(debug_dir);
        debug_dir = NULL;
        pr_err("Failed to create event_count file\n");
        return -ENOMEM;
    }

    atomic_set(&event_count, 10);

    pr_info("Debugfs demo: entries created\n");

    return 0;
}

static void __exit debugfs_demo_exit(void)
{
    debugfs_remove(debug_dir);
    debug_dir = NULL;

    pr_info("Debugfs demo: module unloaded\n");
}

module_init(debugfs_demo_init);
module_exit(debugfs_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Debugfs demonstration kernel module");

How the Program Works

  1. The module includes the debugfs header.
  2. An atomic counter is initialized to zero.
  3. debugfs_create_dir() creates the driver directory.
  4. debugfs_create_file() creates the event_count file.
  5. The read callback obtains the counter value.
  6. simple_read_from_buffer() safely transfers the formatted text to user space.
  7. debugfs_remove() removes the directory and its child entries when the module is unloaded.
This is an educational standalone module. A real driver would normally connect its debugfs entries to actual driver state and manage the lifetime of that state carefully. The example initializes the counter to 10 but does not increment it automatically.

9. Using debugfs_create_u32()

For simple debugging variables, the kernel provides helper functions that avoid writing a custom read callback.

Example

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/debugfs.h>

static struct dentry *debug_dir;
static u32 driver_status = 1;

static int __init simple_debug_init(void)
{
    debug_dir = debugfs_create_dir(
        "simple_driver",
        NULL
    );

    if (IS_ERR_OR_NULL(debug_dir))
        return -ENOMEM;

    if (IS_ERR_OR_NULL(debugfs_create_u32(
            "driver_status",
            0444,
            debug_dir,
            &driver_status))) {
        debugfs_remove(debug_dir);
        debug_dir = NULL;
        return -ENOMEM;
    }

    pr_info("Simple debugfs module loaded\n");
    return 0;
}

static void __exit simple_debug_exit(void)
{
    debugfs_remove(debug_dir);
    debug_dir = NULL;

    pr_info("Simple debugfs module unloaded\n");
}

module_init(simple_debug_init);
module_exit(simple_debug_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Simple debugfs u32 example");

After loading the module, read the value using:

sudo cat /sys/kernel/debug/simple_driver/driver_status

Expected output:

1
debugfs_create_u32() exposes a reference to the supplied variable. The variable must remain valid while the debugfs entry can be accessed. Synchronization is also necessary if the value can be changed concurrently.

10. Reading and Writing Debugfs Files

Debugfs files can be read-only or read-write depending on their permissions and file operations.

Read-Only File

debugfs_create_file(
    "status",
    0444,
    debug_dir,
    NULL,
    &status_fops
);

Read-Write File

debugfs_create_file(
    "control",
    0644,
    debug_dir,
    NULL,
    &control_fops
);

A read-write debugfs file requires appropriate read and write callbacks in its file operations structure.

A write callback typically receives a user-space buffer. It must validate the input and use suitable kernel user-copy functions such as copy_from_user().

File permissions alone are not a complete security boundary. Debugfs is not intended as a secure production control interface. Avoid exposing dangerous operations or sensitive data.

11. Debugging Driver State Using Debugfs

A driver may expose several diagnostic values through a dedicated debugfs directory.

Example Directory Structure

/sys/kernel/debug/my_device/
    status
    interrupt_count
    error_count
    transfer_count
    last_error
Debugfs Entry Information
status Current software or device state.
interrupt_count Number of interrupts processed.
error_count Number of detected errors.
transfer_count Number of completed data transfers.
last_error Last recorded error information.

These entries can help developers determine whether a driver is receiving interrupts, completing transfers or encountering errors.

Example Inspection Commands

sudo cat /sys/kernel/debug/my_device/status

sudo cat /sys/kernel/debug/my_device/interrupt_count

sudo cat /sys/kernel/debug/my_device/error_count

sudo cat /sys/kernel/debug/my_device/transfer_count

12. Debugfs and Driver Synchronization

Debugfs callbacks execute in response to user-space operations. They may run concurrently with normal driver operations.

For example, an interrupt handler may update a counter while a user-space process reads that counter through debugfs.

Common Synchronization Mechanisms

Mechanism Typical Use
atomic_t Simple atomic counters.
mutex Protect shared data in process context.
spinlock Protect shared data in contexts where sleeping is not allowed.
READ_ONCE() Perform a single compiler-visible read of a shared value.
WRITE_ONCE() Perform a single compiler-visible write of a shared value.
Never use a mutex in a hard interrupt handler. Choose the synchronization mechanism according to the execution context and the data being protected. READ_ONCE() and WRITE_ONCE() do not replace full locking when multiple fields must be kept consistent.

13. Debugfs Cleanup and Error Handling

Every debugfs entry created by a module must be managed carefully.

Important Rules

  • Check for errors when creating directories and files.
  • Remove created entries if initialization fails partway through.
  • Remove debugfs entries when the module is unloaded.
  • Ensure callbacks cannot access driver data after it has been freed.
  • Prevent module unload while active operations can still reference module-owned resources.

Cleanup Example

static struct dentry *debug_dir;

static void cleanup_debugfs(void)
{
    debugfs_remove(debug_dir);
    debug_dir = NULL;
}

Removing a parent directory with debugfs_remove() also removes its descendants. The driver must still handle the lifetime of objects referenced by open file operations correctly.

14. Common Debugfs Problems and Troubleshooting

Problem Possible Cause Solution
Directory not found Module not loaded or entry creation failed. Check dmesg and module status.
debugfs path missing Filesystem not mounted. Mount debugfs if permitted.
Permission denied Insufficient user privileges. Use appropriate administrative permissions.
File cannot be created Invalid parent or unsupported debugfs configuration. Check return values and kernel configuration.
Module unload problem Active references or incorrect cleanup. Review file-operation lifetime and resource cleanup.
Incorrect counter value Race condition or incorrect update logic. Use appropriate synchronization.

15. Debugfs Security and Best Practices

  • Use debugfs primarily for development and diagnostic purposes.
  • Do not expose passwords, keys or other sensitive information.
  • Do not provide unrestricted access to dangerous hardware operations.
  • Validate all user-provided input in write callbacks.
  • Use suitable locking for shared driver state.
  • Keep debugfs callbacks simple and safe.
  • Remove all entries during cleanup.
  • Use stable kernel interfaces for production applications.
  • Check the target kernel's API and configuration before building a module.

18. Interview Questions and Answers

Q1. What is debugfs?

Answer: debugfs is a virtual filesystem used to expose internal kernel and driver debugging information to user space.

Q2. Where is debugfs normally mounted?

Answer: It is commonly mounted at /sys/kernel/debug.

Q3. Which header file is required for debugfs APIs?

Answer: linux/debugfs.h.

Q4. Which function creates a debugfs directory?

Answer: debugfs_create_dir().

Q5. Which function creates a debugfs file?

Answer: debugfs_create_file().

Q6. What is the purpose of debugfs_remove()?

Answer: It removes a debugfs entry and its descendants.

Q7. What is the difference between debugfs and procfs?

Answer: debugfs is primarily intended for debugging internal kernel and driver state, while procfs exposes process information and selected kernel interfaces.

Q8. Is debugfs intended as a stable userspace ABI?

Answer: No. Its interfaces are intended for debugging and may change between kernel versions.

Q9. Can debugfs files be read and written?

Answer: Yes. Their access behavior depends on the permissions and file operations supplied when they are created.

Q10. Why is synchronization important in debugfs callbacks?

Answer: Debugfs callbacks may access data concurrently with other driver operations, so shared state must be protected appropriately.

Q11. What is debugfs_create_u32() used for?

Answer: It creates a simple debugfs interface for a 32-bit unsigned integer.

Q12. Should production applications depend on debugfs?

Answer: No. Production interfaces should use documented, stable kernel interfaces appropriate to the device or subsystem.

Q13. What happens if debugfs is not mounted?

Answer: The filesystem entries cannot be accessed through the usual mounted path. Mounting may be required if the kernel supports it and system policy permits it.

Q14. Why must debugfs entries be removed during module cleanup?

Answer: To prevent stale entries and ensure that debugfs callbacks do not reference invalid module resources.

Q15. What is the role of file_operations in debugfs?

Answer: It defines the operations, such as read and write, that are performed when user space accesses a debugfs file.

19. Lesson Summary

  • debugfs is a virtual filesystem for kernel and driver debugging.
  • Its common mount point is /sys/kernel/debug.
  • debugfs_create_dir() creates directories.
  • debugfs_create_file() creates files with custom operations.
  • debugfs_create_u32() and related helpers expose simple values.
  • Driver state and diagnostic counters can be inspected from user space.
  • Synchronization is important when shared data is accessed concurrently.
  • Entries and referenced resources must be cleaned up safely.
  • debugfs is not a stable production userspace ABI.
