2. Introduction to Kernel Memory Debugging

Linux device drivers frequently allocate, access and release kernel memory. Incorrect memory handling can cause kernel crashes, data corruption and security vulnerabilities.

Memory-debugging tools help developers detect programming errors during kernel development and testing.

Common kernel memory errors

  • Out-of-bounds access: Reading or writing outside an allocated memory region.
  • Use-after-free: Accessing memory after it has been released.
  • Double free: Releasing the same allocation more than once.
  • Memory leak: Allocated memory is never released when no longer needed.
  • Uninitialized memory: Reading memory before assigning a valid value.
  • Invalid pointer access: Using an incorrect or corrupted pointer.

4. KASAN – Kernel Address Sanitizer

KASAN (Kernel Address Sanitizer) is a dynamic memory-error detector integrated into the Linux kernel.

It instruments memory accesses and uses shadow memory to track whether memory regions are valid for access.

KASAN detects

  • Out-of-bounds reads.
  • Out-of-bounds writes.
  • Use-after-free errors.
  • Some invalid memory-access patterns.

Example faulty code

static void memory_test(void)
{
    char *buffer;

    buffer = kmalloc(8, GFP_KERNEL);

    if (!buffer)
        return;

    buffer[8] = 'A';  /* Out-of-bounds write */

    kfree(buffer);
}

The allocation contains eight bytes, with valid indices from 0 through 7. Writing to index 8 accesses memory beyond the allocation.

Example configuration

CONFIG_KASAN=y
CONFIG_DEBUG_INFO=y

The exact KASAN mode and additional configuration depend on the kernel version and architecture.

KASAN uses compiler instrumentation and shadow-memory metadata to track memory accessibility.

When an instrumented access violates the memory-access rules, KASAN reports diagnostic information.

Typical report information

  • Error category.
  • Faulting address.
  • Access size and type.
  • Relevant allocation information.
  • Freeing information, when available.
  • Call stacks associated with the access.
KASAN adds runtime and memory overhead. It is generally most useful in dedicated debugging or test kernels rather than performance-sensitive production configurations.

6. KMSAN – Kernel Memory Sanitizer

KMSAN (Kernel Memory Sanitizer) detects the use of uninitialized values in kernel code.

Uninitialized memory contains data that has not been explicitly assigned a valid value for the intended operation.

Example faulty code

static void test_uninitialized(void)
{
    int value;

    if (value == 10)
        pr_info("Value is ten\n");
}

The variable value is read before initialization. Its value is indeterminate.

Corrected example

static void test_initialized(void)
{
    int value = 0;

    if (value == 10)
        pr_info("Value is ten\n");
}

KMSAN detects

  • Uninitialized variable use.
  • Uninitialized values passed to functions.
  • Uninitialized data used in conditions or calculations.
  • Some cases where uninitialized data is copied to user space.
KMSAN requires suitable compiler and architecture support. It has significant overhead and is generally used with specially built test kernels.

8. KFENCE – Kernel Electric-Fence

KFENCE is a low-overhead sampling-based memory-safety error detector for the Linux kernel.

It uses specially guarded memory objects to detect selected invalid memory accesses.

KFENCE can detect

  • Out-of-bounds accesses involving sampled objects.
  • Use-after-free involving sampled objects.
  • Some invalid memory-access patterns.

Example configuration

CONFIG_KFENCE=y

Additional configuration controls sampling frequency and pool behavior.

KFENCE does not inspect every allocation. It samples allocations to provide useful memory-error detection with relatively low runtime overhead.

9. SLUB Allocator Debugging

The Linux kernel uses slab allocators to efficiently manage frequently allocated kernel objects. SLUB is a widely used slab allocator implementation.

SLUB debugging provides checks that help identify corruption and misuse of allocated objects.

Common SLUB debugging checks

  • Red zones around objects.
  • Poisoning freed or unused memory.
  • Allocation and free tracking.
  • Consistency checks.
  • Detection of selected memory corruption patterns.

Example boot parameter

slub_debug=FZPU
FlagPurpose
FEnable sanity checks.
ZAdd red zones.
PPoison objects.
UTrack allocation and free information.

Exact options and behavior depend on the kernel version. SLUB debugging can increase memory use and execution overhead.

10. kmemleak – Kernel Memory Leak Detector

kmemleak is a kernel memory-leak detector that uses a tracing garbage-collector-like approach to identify allocated objects that appear to be unreachable.

It reports possible memory leaks rather than proving that every reported allocation is definitely leaked.

Example leak

static int __init leak_init(void)
{
    void *buffer;

    buffer = kmalloc(1024, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    /* Missing kfree() */
    return 0;
}

If the allocation becomes unreachable without being released, kmemleak may report it.

Useful controls

mount -t debugfs none /sys/kernel/debug

echo clear | sudo tee \
/sys/kernel/debug/kmemleak

echo scan | sudo tee \
/sys/kernel/debug/kmemleak

sudo cat /sys/kernel/debug/kmemleak

These commands require kmemleak support in the running kernel and appropriate permissions. Do not clear existing reports unless you intend to reset the current detection baseline.

11. DEBUG_PAGEALLOC

DEBUG_PAGEALLOC is a kernel debugging facility that can help detect invalid accesses to freed pages.

It changes page-allocation behavior so that accesses to certain freed pages can trigger faults rather than silently accessing stale memory.

Example configuration

CONFIG_DEBUG_PAGEALLOC=y

Typical uses

  • Investigating page-level use-after-free errors.
  • Detecting invalid access to released pages.
  • Debugging certain memory-corruption problems.

Its behavior and performance cost vary by architecture and kernel configuration.

12. UBSAN – Undefined Behavior Sanitizer

UBSAN detects selected forms of undefined behavior in C code using compiler instrumentation.

Examples of undefined behavior

  • Signed integer overflow.
  • Invalid shift operations.
  • Some invalid alignment accesses.
  • Other compiler-supported undefined operations.

Example

int value = 2147483647;
value = value + 1;

Signed integer overflow in C is undefined behavior. A suitable UBSAN configuration can help report this kind of defect.

Example kernel configuration

CONFIG_UBSAN=y

14. Memory Debugging in Device Drivers

Device drivers frequently allocate memory for device state, buffers, requests and data structures.

Example driver allocation

struct my_device {
    int status;
    char *buffer;
};

static int my_device_init(struct my_device *dev)
{
    dev->buffer = kmalloc(128, GFP_KERNEL);

    if (!dev->buffer)
        return -ENOMEM;

    dev->status = 0;

    return 0;
}

Correct cleanup

static void my_device_cleanup(struct my_device *dev)
{
    kfree(dev->buffer);
    dev->buffer = NULL;
}

The driver must ensure that all users of the buffer have finished before it is freed. Cleanup must also be safe when initialization fails partway through.

Common driver memory mistakes

  • Not checking allocation return values.
  • Freeing memory while another execution context still uses it.
  • Failing to release memory on error paths.
  • Accessing memory after device removal.
  • Copying data beyond the allocated buffer size.

15. Practical Exercise – Identifying an Out-of-Bounds Error

Objective: Understand how KASAN reports an invalid memory access.

Study the following kernel code:

static void test_memory_access(void)
{
    char *buffer;

    buffer = kmalloc(8, GFP_KERNEL);

    if (!buffer)
        return;

    buffer[0] = 'A';
    buffer[7] = 'B';

    /* Invalid access */
    buffer[8] = 'C';

    kfree(buffer);
}

Analysis

  1. Eight bytes are allocated.
  2. Indices 0 through 7 are valid.
  3. Index 8 is outside the allocation.
  4. KASAN can detect the invalid write when the relevant instrumentation is enabled.
  5. The developer should correct the array bounds.

Corrected access

buffer[7] = 'C';

Expected Result: You should understand why the original write is invalid and how a memory-safety detector can identify it. Actual KASAN testing requires a compatible kernel built with KASAN support.

16. Practical Exercise – Understanding Memory Leaks

Objective: Identify an allocation that is not released.

Incorrect cleanup

static int __init my_init(void)
{
    void *buffer;

    buffer = kmalloc(256, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    return 0;
}

The allocated memory is not released by this example. If no other owner retains or releases it, this is a leak.

Improved lifecycle

static int __init my_init(void)
{
    void *buffer;

    buffer = kmalloc(256, GFP_KERNEL);

    if (!buffer)
        return -ENOMEM;

    /* Use the buffer */

    kfree(buffer);

    return 0;
}

In a real driver, memory may need to remain allocated until device removal. In that case, retain a valid reference and release it in the correct cleanup path rather than freeing it immediately.

Expected Result: Understand the relationship between allocation, ownership, use and cleanup.
