1. Introduction

Kernel logging is one of the most important debugging methods used in Linux device-driver development.

When a kernel module is loaded, a device is detected, an interrupt occurs or a driver operation fails, developers need a way to record what happened.

Linux provides two important facilities:

  • printk(): Writes messages into the kernel log buffer.
  • dmesg: Displays messages stored in the kernel ring buffer.
Example: If a USB driver fails to detect a device, the developer can insert logging statements into the probe() function and inspect the resulting messages using dmesg.

2. What Is printk()?

printk() is a kernel logging function used to print messages from kernel code.

It is similar in purpose to printf() in user-space C programming, but it operates within the kernel environment.

Syntax

printk("Message\n");

Example

printk("Linux driver initialized\n");

The message is stored in the kernel log buffer and can be viewed using kernel logging tools.

printk() is a kernel function. It must not be used in ordinary user-space applications. Use printf() or another user-space logging facility there.

3. printk() Log-Level Format

Kernel messages can include a severity level. The level helps control how messages are classified and displayed.

Syntax

printk(KERN_INFO "Driver initialized\n");

The KERN_INFO prefix identifies the message as informational.

Common Log Levels

MacroSeverityPurpose
KERN_EMERG0System is unusable.
KERN_ALERT1Immediate action required.
KERN_CRIT2Critical condition.
KERN_ERR3Error condition.
KERN_WARNING4Warning condition.
KERN_NOTICE5Normal but significant condition.
KERN_INFO6Informational message.
KERN_DEBUG7Debugging message.

4. printk() Examples Using Different Log Levels

printk(KERN_EMERG "Emergency message\n");

printk(KERN_ALERT "Alert message\n");

printk(KERN_CRIT "Critical message\n");

printk(KERN_ERR "Driver error\n");

printk(KERN_WARNING "Driver warning\n");

printk(KERN_NOTICE "Driver notice\n");

printk(KERN_INFO "Driver initialized\n");

printk(KERN_DEBUG "Debug information\n");

Each message has a severity level. The kernel console log level determines which messages are printed to the console; it does not mean that all lower-priority messages are discarded from the log buffer.

5. Modern Kernel Logging Macros

Modern Linux kernel code commonly uses convenience macros instead of writing the full printk() prefix each time.

MacroEquivalent LevelPurpose
pr_emerg()EmergencyEmergency messages.
pr_alert()AlertImmediate attention.
pr_crit()CriticalCritical failures.
pr_err()ErrorError reporting.
pr_warn()WarningWarning messages.
pr_notice()NoticeSignificant events.
pr_info()InformationNormal information.
pr_debug()DebugDebugging information.

Example

pr_info("my_driver: initialized\n");

pr_err("my_driver: device registration failed\n");

pr_warn("my_driver: unexpected device state\n");

pr_debug("my_driver: entering probe function\n");

These macros make driver code more readable and consistent.

6. What Is dmesg?

dmesg is a Linux command used to display messages from the kernel ring buffer.

It helps developers inspect messages generated during:

  • Kernel boot.
  • Kernel module loading and removal.
  • Device detection.
  • Driver initialization.
  • Hardware communication.
  • Interrupt handling.
  • Kernel warnings and errors.

Basic Command

dmesg

This displays the available kernel log messages in the terminal.

7. Common dmesg Commands

7.1 Display All Available Messages

dmesg

7.2 Display the Last 20 Messages

dmesg | tail -20

7.3 Display the First 20 Messages

dmesg | head -20

7.4 Follow New Messages

sudo dmesg -w

This displays new kernel messages as they arrive.

7.5 Display Human-Readable Timestamps

dmesg -T

This attempts to convert kernel timestamps into human-readable time values. The converted time may not be perfectly accurate for every event, especially across changes in system time.

7.6 Display Messages with Severity Information

dmesg -x

7.7 Display Only Error Messages

dmesg --level=err

7.8 Display Warning and Error Messages

dmesg --level=warn,err

7.9 Search for USB Messages

dmesg | grep -i usb

7.10 Search for Driver Messages

dmesg | grep -i my_driver

8. Kernel Ring Buffer

The kernel ring buffer is an in-memory buffer that stores kernel log messages.

It is called a ring buffer because new messages are written into a circular storage area. When the buffer becomes full, older entries may be overwritten by newer entries.

Kernel Components | v printk() | v Kernel Ring Buffer | +------+------+ | | v v dmesg journalctl | | +------+------+ | v Developer Reads Logs

Important Characteristics

  • Stores kernel-generated messages.
  • Supports kernel diagnostics.
  • Has a limited buffer capacity.
  • Older messages may disappear as new messages arrive.
  • Can be inspected using dmesg.

User-Space Example

{
    printf("Hello from user space\n");

    return 0;
}

Kernel-Space Example

#include <linux/module.h>
#include <linux/kernel.h>

static int __init demo_init(void)
{
    pr_info("Hello from kernel space\n");
    return 0;
}

static void __exit demo_exit(void)
{
    pr_info("Kernel module removed\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");

10. Controlling Kernel Console Log Level

Linux maintains a console log level that controls which kernel messages are printed to the console.

View Current Console Log Level

cat /proc/sys/kernel/printk

The output contains four numeric values. They represent the current console log level, the default message level, the minimum console level and the default console level.

Temporarily Change Console Log Level

sudo dmesg -n 7

This changes the console log level to allow more messages to be printed to the console.

Restore a More Restrictive Level

sudo dmesg -n 4
Changing the console log level affects console output. It does not necessarily remove messages from the kernel ring buffer.

11. printk() in Device Driver Functions

Logging can be added to different callbacks to understand driver execution.

Module Initialization

static int __init my_init(void)
{
    pr_info("Driver initialization started\n");

    pr_info("Driver initialization completed\n");

    return 0;
}

Module Exit

static void __exit my_exit(void)
{
    pr_info("Driver cleanup started\n");

    pr_info("Driver removed\n");
}

Open Callback

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("Device file opened\n");

    return 0;
}

Read Callback

static ssize_t my_read(struct file *file,
                       char __user *buffer,
                       size_t count,
                       loff_t *offset)
{
    pr_info("Read operation called\n");

    return 0;
}

Write Callback

static ssize_t my_write(struct file *file,
                        const char __user *buffer,
                        size_t count,
                        loff_t *offset)
{
    pr_info("Write operation called\n");

    return count;
}

These examples demonstrate logging placement. A complete read/write implementation must also handle data transfer, offsets, return values and user-space memory safely.

12. Device-Specific Logging with pr_fmt()

The pr_fmt() macro can add a common prefix to messages in a source file.

Example

#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt

#include <linux/module.h>
#include <linux/kernel.h>

static int __init demo_init(void)
{
    pr_info("Driver initialized\n");

    pr_err("Example error message\n");

    return 0;
}

static void __exit demo_exit(void)
{
    pr_info("Driver removed\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");

The output messages include the module name as a prefix, making it easier to identify which driver generated them.

13. Logging Best Practices

  1. Use pr_info() for important informational messages.
  2. Use pr_err() for actual error conditions.
  3. Use pr_warn() for unexpected but recoverable conditions.
  4. Use pr_debug() for detailed debugging information.
  5. Include the device or driver name in messages when useful.
  6. Avoid logging repeatedly inside high-frequency interrupt or data-transfer paths.
  7. Do not print sensitive information.
  8. Remove unnecessary temporary logs before production release.
  9. Use meaningful error messages.
  10. Check kernel logs after loading and unloading modules.

14. Practical Exercise: Kernel Logging Module

Objective

Create a kernel module that uses different log levels and inspect its messages through dmesg.

Source Code: logging_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>

static int __init logging_demo_init(void)
{
    pr_info("logging_demo: initialization started\n");

    pr_warn("logging_demo: warning example\n");

    pr_err("logging_demo: error message example\n");

    pr_info("logging_demo: initialization completed\n");

    return 0;
}

static void __exit logging_demo_exit(void)
{
    pr_info("logging_demo: module removed\n");
}

module_init(logging_demo_init);
module_exit(logging_demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Kernel Logging Demonstration");

Makefile

obj-m += logging_demo.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile the Module

make

Load the Module

sudo insmod logging_demo.ko

View Kernel Messages

sudo dmesg | tail -20

Filter Module Messages

sudo dmesg | grep logging_demo

Remove the Module

sudo rmmod logging_demo

Verify Removal

sudo dmesg | tail -20

Expected Result

logging_demo: initialization started
logging_demo: warning example
logging_demo: error message example
logging_demo: initialization completed
logging_demo: module removed

The exact timestamps, prefixes and ordering in the complete log output may vary.

16. Important Points to Remember

  • printk() is a kernel logging function.
  • printf() is generally used in user-space applications.
  • KERN_INFO and KERN_ERR are kernel log-level prefixes.
  • pr_info(), pr_err() and pr_debug() are convenient logging macros.
  • dmesg displays kernel ring-buffer messages.
  • The ring buffer has limited capacity.
  • dmesg -w follows new kernel messages.
  • pr_fmt() can add a common source-file message prefix.
  • Console log level controls console visibility.
  • Excessive logging can affect performance.

18. Lesson Summary

printk() and its convenience macros provide a simple and effective way to record messages from Linux kernel code. These messages help developers understand driver initialization, device operations, hardware communication and error conditions.

The dmesg command displays kernel ring-buffer messages and provides useful filtering and monitoring options.

Correct log levels, meaningful messages and controlled logging make kernel debugging more effective and help developers diagnose device-driver problems.
