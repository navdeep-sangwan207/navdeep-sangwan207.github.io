2. Introduction to Platform Devices

Linux supports many different types of hardware. A processor-based system may contain UART controllers, I2C controllers, SPI controllers, timers, watchdogs, GPIO controllers and other peripheral devices.

These peripherals need software drivers so that the Linux kernel can initialize them, configure their registers, handle interrupts and provide services to other kernel subsystems or user-space applications.

Many peripherals integrated into a System-on-Chip (SoC) do not have a self-describing discovery mechanism comparable to PCI configuration space or USB enumeration. The kernel therefore needs another way to represent these devices and associate them with suitable drivers.

The Linux platform device model provides this mechanism.

What is a Platform Device?

A platform device is a device represented through the Linux platform bus and device model. It commonly describes hardware that is part of a processor-based system and whose resources are known through firmware or platform-specific information.

Its description may include:

  • Memory-mapped register ranges.
  • Hardware interrupt numbers.
  • DMA-related resources.
  • Other platform-specific hardware information.
Important: A platform device is a Linux device-model concept. It is not simply another name for every embedded device. It commonly represents non-discoverable on-chip peripherals, but the platform bus can also represent other devices that fit this model.

3. Why Are Platform Devices Required?

Consider an ARM-based SoC containing a UART controller. The UART hardware may be connected internally to the processor and controlled through a fixed memory-mapped register range.

The kernel needs to know:

  • Where the UART registers are located.
  • Which interrupt is associated with the UART.
  • Which driver is compatible with the hardware.
  • How the device should be initialized and managed.

Unlike a typical PCI device, this UART may not be independently discoverable by scanning a standard configuration space. Its hardware description must come from another source.

The platform device model allows the kernel to represent the hardware and match it with a suitable platform driver.

Main Reasons

  1. Hardware representation: It provides a standard kernel representation for platform-oriented hardware.
  2. Resource management: It describes resources such as memory regions and interrupts.
  3. Driver matching: It allows the kernel to associate a device with a compatible driver.
  4. Device lifecycle: It provides standard registration, binding, probing and removal mechanisms.
  5. Subsystem integration: It allows peripheral drivers to integrate with Linux kernel frameworks.

4. Examples of Platform Devices

Many SoC-integrated peripherals are commonly implemented as platform devices.

The Linux kernel receives the hardware description and creates appropriate device-model objects. For devices represented through the platform bus, platform drivers can then bind to those objects.

Remember: The SoC hardware architecture describes the physical hardware. The Linux platform bus is a software device-model mechanism used to represent and manage suitable devices.

6. Platform Devices vs PCI and USB Devices

Linux supports multiple bus types. The main difference between these device models is how devices are discovered, described and matched with drivers.

Feature Platform Device PCI Device USB Device
Typical use SoC-integrated or platform-described hardware PCI/PCIe devices USB peripherals
Discovery Often firmware description or platform code PCI enumeration USB enumeration
Identification Device Tree compatible strings, ACPI IDs or platform IDs Vendor and device IDs Vendor and product IDs
Driver model Platform driver PCI driver USB driver
Common examples SoC UART, timer and controller Network or storage card USB keyboard, mouse and storage

PCI Device Discovery

PCI devices can be discovered by the PCI subsystem through configuration space. The subsystem reads device identification information and matches it with registered PCI drivers.

USB Device Discovery

USB devices are discovered through the USB host controller. During enumeration, the USB subsystem obtains descriptors that identify the connected device and its capabilities.

Platform Device Discovery

Platform devices often do not provide an equivalent standard self-enumeration mechanism. Their descriptions commonly come from:

  • Device Tree on many embedded ARM and other systems.
  • ACPI firmware tables on systems that use ACPI.
  • Platform or board-specific kernel code that registers devices.

7. Introduction to the Linux Platform Bus

The Linux device model organizes hardware and software drivers through buses. A bus provides a common mechanism for registering devices, registering drivers, matching them and managing their lifecycle.

The platform bus is a Linux bus type used by platform devices and platform drivers.

It provides the infrastructure for:

  • Registering platform devices.
  • Registering platform drivers.
  • Matching devices with drivers.
  • Calling the driver's probe function when a match occurs.
  • Managing device removal and driver unbinding.

The platform bus does not itself operate the peripheral hardware. The matched driver contains the device-specific logic, while the bus provides the device-model infrastructure.

8. Platform Device and Platform Driver

Two important kernel structures are used in platform driver development:

8.1 struct platform_device

This structure represents a platform device in the Linux device model. It contains information associated with the device, including its name, resources and embedded generic device-model information.

Resources can describe:

  • Memory-mapped register ranges.
  • Interrupt numbers.
  • DMA-related resources.
  • Other platform-specific resources.

8.2 struct platform_driver

This structure represents a driver that can bind to platform devices. It includes callbacks and matching information.

Important elements include:

  • probe() – called when a suitable device is bound to the driver.
  • remove() – called when the device is detached from the driver.
  • driver – contains generic driver-model information, including matching information.

Registration Functions

Function Purpose
platform_driver_register() Registers a platform driver with the platform bus.
platform_driver_unregister() Unregisters a previously registered platform driver.

These functions are commonly used by platform driver modules to register and unregister their drivers.

9. How Platform Device and Driver Matching Works

The platform bus needs to determine whether a registered platform driver supports a particular platform device.

Matching can use different mechanisms, including:

  • Device Tree matching: Uses compatible strings supplied in Device Tree.
  • ACPI matching: Uses ACPI identifiers.
  • Platform ID matching: Uses platform device identifiers.
  • Name-based matching: Can use matching names in applicable cases.

For many modern embedded systems, Device Tree matching is particularly important.

Example Device Tree Node

The following is an illustrative UART device description:

uart0: serial@40000000 {
    compatible = "vendor,soc-uart";
    reg = <0x40000000 0x1000>;
    interrupts = <5>;
    status = "okay";
};

Explanation:

  • serial@40000000 is the node name and unit address.
  • compatible identifies the hardware programming model.
  • reg describes the register address and size.
  • interrupts describes the interrupt using the relevant interrupt-controller binding.
  • status indicates that the device is enabled.
Device Tree note: The address and interrupt in this example are illustrative only. A real Device Tree source file must follow the SoC's binding and may require root #address-cells, #size-cells, an interrupt-parent, clock properties, reset properties and other required fields.

A platform device may also be created through ACPI firmware enumeration or registered directly by platform-specific kernel code. Device Tree is not the only way to create platform devices.

10. Basic Platform Driver Binding Sequence

The following sequence describes the general lifecycle when a platform device and a compatible driver are registered.

↓

↓
5. Driver Obtains Resources and Initializes Hardware
↓
6. Driver Operates the Device
↓
7. Remove Callback Runs When Unbound or Removed

The exact timing depends on registration order. If a matching driver is already registered when a device appears, binding can happen immediately. If the device exists first, registering a matching driver can trigger the probe process.

Role of the Probe Function

The probe function is responsible for initializing a device after a successful match.

A typical probe function may:

  • Obtain the device's memory and interrupt resources.
  • Map hardware registers into kernel virtual address space.
  • Request an interrupt handler if needed.
  • Initialize locks, buffers and driver state.
  • Register the device with an appropriate Linux subsystem.

Role of the Remove Function

The remove function releases resources and reverses the initialization performed for the device. It must ensure that interrupts, hardware activity and references to driver-managed data are handled safely.

11. Platform Device Resources

Platform devices often need hardware resources before a driver can operate them. These resources are represented using Linux resource descriptions.

Resource Type Meaning Example
IORESOURCE_MEM Memory address range UART register block
IORESOURCE_IRQ Hardware interrupt resource UART interrupt
IORESOURCE_DMA DMA-related resource DMA channel information in applicable platform descriptions
IORESOURCE_IO I/O port address range Port-mapped I/O on architectures that use it

Memory-Mapped I/O

Memory-mapped I/O (MMIO) allows the CPU to access hardware registers through an address range in the physical address space.

For example, a UART controller might have registers for:

  • Transmitting data.
  • Receiving data.
  • Configuring baud rate.
  • Enabling interrupts.
  • Checking device status.
Important: A physical register address must not be directly dereferenced as an ordinary C pointer in a Linux kernel driver. The driver must obtain and map the resource using the appropriate kernel I/O APIs.

In later lessons, you will study resource acquisition and mapping APIs such as devm_platform_ioremap_resource().

12. Physical Address vs Kernel Virtual Address

Hardware documentation commonly specifies physical register addresses. Linux kernel drivers normally access mapped I/O registers through kernel virtual addresses.

13. Device Tree and ACPI

The Linux kernel needs hardware descriptions to understand devices that cannot be discovered through a standard bus enumeration mechanism.

Device Tree

Device Tree is widely used in embedded Linux systems, particularly on ARM-based platforms. It describes hardware components and their relationships in a structured format.

A Device Tree description can provide:

  • Compatible hardware identifiers.
  • Register address ranges.
  • Interrupt information.
  • Clock connections.
  • Reset controls.
  • GPIO connections.
  • DMA configuration.

ACPI

Advanced Configuration and Power Interface (ACPI) is another firmware-based mechanism used to describe devices, resources and power-management information.

ACPI is common on many PC systems and is also supported by some ARM and embedded platforms.

Feature Device Tree ACPI
Common environment Embedded Linux systems PC and supported embedded systems
Description format DTS source compiled into DTB Firmware tables and ACPI objects
Device identification Compatible strings ACPI identifiers
Linux integration Device Tree subsystem ACPI subsystem

14. Inspecting Platform Devices in Ubuntu

Linux exposes information about platform devices through the sysfs device model.

Command 1: Check Kernel Version

uname -r

Purpose: Displays the running Linux kernel release.

Command 2: List Platform Devices

ls /sys/bus/platform/devices

Purpose: Lists platform device objects currently exposed through sysfs.

Command 3: List Platform Drivers

ls /sys/bus/platform/drivers

Purpose: Lists platform drivers registered with the platform bus and exposed through sysfs.

Command 4: Inspect Device Attributes

find /sys/bus/platform/devices -maxdepth 2 -type f

Purpose: Finds files exposed under platform device directories. These may include attributes describing device state or relationships.

Command 5: Check Device Tree Availability

ls /sys/firmware/devicetree/base

Alternative location on some systems:

ls /proc/device-tree

These paths are not guaranteed to exist on every system. Their availability depends on how the kernel was booted and configured.

Command 6: Search Kernel Messages

dmesg | grep -i platform

Purpose: Searches the current kernel message ring buffer for messages containing the word platform.

Command 7: Inspect Device Directories

find /sys/devices -maxdepth 3 -type d | head

Purpose: Displays a small sample of directories in the Linux device hierarchy.

Expected observation: Your Ubuntu VirtualBox installation may show platform devices associated with virtual hardware, system components or kernel infrastructure. The list may be sparse and does not necessarily contain the SoC UART, I2C, SPI or GPIO controllers found on an embedded development board.

16. Practical Environment: Ubuntu VirtualBox and Embedded Boards

Your Ubuntu installation inside VirtualBox is suitable for learning many Linux kernel development concepts, including:

  • Kernel source code and headers.
  • Platform bus and driver model concepts.
  • Sysfs inspection.
  • Kernel module compilation.
  • Basic platform driver source-code analysis.

However, a virtual machine does not automatically expose the physical UART, I2C, SPI or GPIO controllers of an embedded SoC. Hardware-level platform driver testing requires a suitable development board, a supported emulator such as QEMU, or another environment that provides the required device model.

Difference from LPC2129 Keil programming: Your LPC2129 Keil uVision simulator exercises bare-metal ARM7 programming. Linux platform drivers use Linux kernel APIs, the Linux device model and a running Linux kernel. These are related embedded-systems topics, but they are different development environments.

18. Lesson Summary

  • Platform devices are represented through the Linux platform bus.
  • They commonly describe SoC-integrated peripherals and other platform-oriented hardware.
  • UART, I2C, SPI, GPIO, timers and watchdogs are common examples.
  • Platform devices often rely on firmware descriptions or platform code rather than PCI-style enumeration.
  • Device Tree and ACPI are important sources of hardware information.
  • struct platform_device represents a platform device.
  • struct platform_driver represents a platform driver.
  • The platform bus matches devices with compatible drivers.
  • The probe callback initializes a matched device.
  • The remove callback handles device detachment and cleanup.
  • Resources can include memory ranges, interrupts and DMA-related information.
  • Hardware registers must be accessed through appropriate kernel I/O mapping and access APIs.
