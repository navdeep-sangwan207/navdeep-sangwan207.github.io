2. Introduction to Device Tree

A Device Tree is a data structure used by Linux to describe the hardware components of a system.

It provides information about hardware such as:

  • Processors and CPU cores.
  • Memory regions.
  • UART controllers.
  • I2C and SPI controllers.
  • GPIO controllers.
  • Interrupt controllers.
  • Timers and clocks.
  • Hardware buses and connected peripherals.

Instead of hardcoding every hardware detail into the Linux kernel, a board can provide a hardware description separately.

The kernel reads this description during boot and uses it to identify and configure hardware devices.

Physical Hardware
↓
Device Tree Description
↓
Linux Kernel Parses Hardware Information
↓
Devices Registered with Kernel Subsystems
↓
Suitable Device Drivers Bind to Devices

3. Why Is Device Tree Needed?

Embedded Linux systems may use the same processor architecture but different board designs.

For example, two ARM-based development boards may use:

  • Different UART register addresses.
  • Different interrupt numbers.
  • Different GPIO connections.
  • Different memory layouts.
  • Different I2C and SPI peripherals.
  • Different clock configurations.

If all these details were hardcoded into kernel driver source code, supporting multiple boards would become difficult.

Device Tree separates hardware description from driver implementation.

Without Device Tree

  • Hardware details may be hardcoded in board-specific kernel code.
  • Supporting a new board may require additional kernel source changes.
  • Hardware configuration and driver code become more tightly coupled.

With Device Tree

  • Hardware configuration is described separately.
  • A driver can support multiple compatible boards.
  • Board-specific resources can be supplied through firmware descriptions.
  • Kernel code can be reused across different hardware designs.

4. Device Tree and Platform Drivers

Device Tree is particularly important in embedded Linux systems that use platform devices.

A hardware node in Device Tree may describe a UART controller, timer or other SoC peripheral.

The kernel can use this information to create a corresponding device object and register it with the appropriate subsystem or bus.

For a platform device, the platform bus can match the device's compatible string against a platform driver's OF match table.

Device Tree Node
↓
Device Tree Compatible Property
↓
Platform Device Created by Kernel Infrastructure
↓
Platform Driver OF Match Table
↓
Probe Callback
A Device Tree node does not automatically become a platform device in every situation. The kernel's bus and subsystem-specific code determines how each node is populated and represented.

5. Device Tree Source (DTS)

Device Tree Source is a human-readable language used to describe hardware.

Files commonly use the .dts extension.

Device Tree Source uses a hierarchical structure containing nodes and properties.

Basic Syntax

/dts-v1/;

/ {
    model = "Demo Embedded Board";
    compatible = "demo,embedded-board";

    memory {
        device_type = "memory";
        reg = <0x80000000 0x10000000>;
    };
};

Explanation

Element Meaning
/dts-v1/; Declares the Device Tree source format version.
/ Root node of the Device Tree.
model Human-readable board model description.
compatible Identifies compatible hardware or board implementations.
memory Example child node describing system memory.
reg Describes a register or address range using parent-defined cell formats.
This is a syntax illustration. Real Device Tree memory descriptions must follow the binding and address-cell conventions of the target platform. The root node commonly uses properties such as #address-cells and #size-cells to define how address and size values are encoded.

6. Device Tree Nodes

A node represents a hardware component or a logical grouping of hardware information.

Nodes can contain:

  • Properties.
  • Child nodes.
  • Hardware resource descriptions.
  • References to other nodes.

Example

/ {
    soc {
        uart0: serial@40000000 {
            compatible = "demo,soc-uart";
            reg = <0x40000000 0x1000>;
            status = "okay";
        };
    };
};

In this example:

  • soc represents a system-on-chip bus or container.
  • serial@40000000 is a UART-related node.
  • uart0 is a label that can be referenced elsewhere.
  • compatible identifies the hardware type.
  • reg describes the register address and size according to the parent bus format.
  • status indicates whether the device is enabled.
The example uses illustrative addresses and a generic compatible string. Actual node names, bindings and register addresses must follow the SoC documentation and Linux Device Tree bindings.

7. Device Tree Properties

Properties provide configuration and hardware information inside a node.

Property Purpose
compatible Identifies compatible hardware or a board implementation.
reg Describes address and size information for resources.
interrupts Describes interrupt information according to the interrupt parent.
status Indicates whether a node is enabled, disabled or otherwise configured.
clocks References clock providers and may include clock specifier values.
resets References reset controllers and reset specifiers.
gpios References GPIO controllers and GPIO specifiers.
pinctrl-0 References a pin-control configuration state.
pinctrl-names Provides names for pin-control states.
interrupt-parent Identifies the interrupt controller used to interpret interrupt information.

The exact properties supported by a node depend on its hardware binding.

8. The Compatible Property

The compatible property is one of the most important properties for driver matching.

It identifies the hardware programming model supported by a device.

Example Device Tree Node

uart0: serial@40000000 {
    compatible = "demo,soc-uart";
    reg = <0x40000000 0x1000>;
    status = "okay";
};

Matching Driver Table

static const struct of_device_id demo_of_match[] = {
    {
        .compatible = "demo,soc-uart"
    },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

The compatible string in the Device Tree node can match the compatible string in the driver's OF match table.

This allows the kernel to identify a driver that supports the described hardware.

The compatible string must match the documented hardware binding. Inventing a compatible string without a corresponding driver or binding does not create hardware support.

9. The reg Property

The reg property describes address and size information for a device's resources.

For a memory-mapped peripheral, it commonly describes the register address and the size of the register region.

Example

uart0: serial@40000000 {
    compatible = "demo,soc-uart";
    reg = <0x40000000 0x1000>;
};

In this illustrative example:

  • 0x40000000 is the starting address.
  • 0x1000 is the region size.

The encoding of reg depends on the parent node's #address-cells and #size-cells properties.

The kernel can translate the Device Tree resource information into resource structures that a platform driver can access through platform resource APIs.

10. The Interrupts Property

Many hardware devices generate interrupts when events occur.

The interrupts property describes the interrupt information for a device.

Example

uart0: serial@40000000 {
    compatible = "demo,soc-uart";
    reg = <0x40000000 0x1000>;

    interrupt-parent = <&intc>;
    interrupts = <5>;
};

In this illustration:

  • interrupt-parent references an interrupt controller.
  • interrupts provides the interrupt specifier.

The meaning and number of interrupt cells depend on the interrupt controller binding.

A driver can retrieve a Linux IRQ number using:

int irq;

irq = platform_get_irq(pdev, 0);

if (irq < 0)
    return irq;

11. The Status Property

The status property indicates the operational availability of a Device Tree node.

Common Values

Value Meaning
"okay" The device is enabled.
"disabled" The device is disabled.
"reserved" The device or region is reserved according to the platform description.
"fail" or "fail-sss" Indicates a failure state, optionally with a platform-specific reason.

Example

uart0: serial@40000000 {
    compatible = "demo,soc-uart";
    reg = <0x40000000 0x1000>;
    status = "okay";
};

A disabled node is generally not populated as an active device through the normal Device Tree population process.

12. Device Tree Labels and References

Labels allow one node to be referenced from another node.

Example

/ {
    intc: interrupt-controller {
        interrupt-controller;
        #interrupt-cells = <1>;
    };

    uart0: serial@40000000 {
        compatible = "demo,soc-uart";
        interrupt-parent = <&intc>;
        interrupts = <5>;
    };
};

Here:

  • intc: defines a label for the interrupt controller.
  • uart0: defines a label for the UART node.
  • &intc references the interrupt controller node.

Labels and references help describe relationships between hardware components.

13. Device Tree Include Files

Large Device Tree descriptions are often divided into multiple files.

Common file types include:

Extension Purpose
.dts Board-specific Device Tree source.
.dtsi Device Tree source include file, often used for SoC-level descriptions.
.dtb Compiled Device Tree Blob.

A board-specific DTS file may include a SoC-level DTSI file.

Example

/dts-v1/;

#include "demo-soc.dtsi"

/ {
    model = "Demo Development Board";
    compatible = "demo,development-board";
};

The included file can contain common processor and peripheral descriptions, while the board file adds or modifies board-specific configuration.

14. Device Tree and Driver Probe

Device Tree information can be used by the platform driver during probe.

For example, the driver can:

  • Match the device through the compatible property.
  • Retrieve memory resources.
  • Retrieve interrupt information.
  • Obtain clocks and reset controls.
  • Read device-specific configuration properties.

Example Probe Function

static int demo_probe(struct platform_device *pdev)
{
    struct resource *res;
    int irq;

    res = platform_get_resource(
        pdev,
        IORESOURCE_MEM,
        0
    );

    if (!res)
        return -ENODEV;

    irq = platform_get_irq(pdev, 0);

    if (irq < 0)
        return irq;

    dev_info(&pdev->dev,
             "Memory resource and IRQ retrieved\n");

    return 0;
}

The driver does not need to hardcode the memory address or interrupt number. It obtains resource information associated with the registered device.

15. Device Tree During Linux Boot

On many embedded systems, the bootloader loads a Device Tree Blob and passes its address to the Linux kernel.

Power-On and Hardware Initialization
↓
Bootloader Starts
↓
Bootloader Loads Kernel and DTB
↓
Kernel Receives Device Tree
↓
Kernel Parses Hardware Description
↓
Devices and Subsystems Initialized

The exact boot process depends on the architecture, firmware and bootloader configuration.

The kernel can use Device Tree information during early initialization and later device population.

16. Viewing Device Tree Information in Linux

Linux systems that use Device Tree commonly expose the live hardware description through:

/sys/firmware/devicetree/base

Some systems also provide:

/proc/device-tree

Useful Commands

ls /sys/firmware/devicetree/base

ls /proc/device-tree

find /sys/firmware/devicetree/base -maxdepth 2 -type d

cat /sys/firmware/devicetree/base/model

cat /sys/firmware/devicetree/base/compatible

Many Device Tree properties are stored as binary data rather than ordinary text. The cat command may not display them in a human-readable format.

To inspect a property as hexadecimal bytes, use:

hexdump -C /sys/firmware/devicetree/base/soc/serial@40000000/reg
The example path depends on the actual system Device Tree. A node with that exact name may not exist on your computer.

17. Device Tree Compiler

The Device Tree Compiler, commonly called dtc, converts Device Tree Source into Device Tree Blob format and can also decompile a DTB into source form.

Compile DTS to DTB

dtc -I dts -O dtb -o demo-board.dtb demo-board.dts

Decompile DTB to DTS

dtc -I dtb -O dts -o demo-board.dts demo-board.dtb

Install Device Tree Compiler on Ubuntu

sudo apt update

sudo apt install device-tree-compiler

The compiler checks Device Tree syntax and produces a compiled representation. Syntax validation alone does not prove that the hardware description follows every required binding or matches the actual board.

18. Device Tree Bindings

A Device Tree binding defines how a particular hardware component must be represented in Device Tree.

Bindings specify:

  • Required properties.
  • Optional properties.
  • Property data formats.
  • Valid property values.
  • Relationships with other hardware nodes.

Linux kernel Device Tree bindings are commonly documented using YAML schemas.

They are maintained in the kernel source tree under:

Documentation/devicetree/bindings/

For example, a UART controller binding defines the expected compatible strings and hardware resource properties for that UART implementation.

Always consult the relevant binding and SoC documentation before writing or modifying a real Device Tree node.

19. Common Device Tree Mistakes

  • Using an incorrect compatible string.
  • Providing an incorrect register address or size.
  • Using the wrong address-cell or size-cell format.
  • Specifying an incorrect interrupt controller or interrupt specifier.
  • Leaving a required device node disabled.
  • Referencing an undefined label.
  • Ignoring the hardware binding requirements.
  • Assuming every Device Tree node becomes a platform device.
  • Assuming a syntactically valid DTB guarantees successful driver probing.

20. Practical Exercise: Create a Simple Device Tree

Install the Device Tree Compiler:

sudo apt update
sudo apt install device-tree-compiler

Create a file named demo-board.dts:

/dts-v1/;

/ {
    compatible = "demo,board";
    model = "Demo Device Tree Board";

    #address-cells = <1>;
    #size-cells = <1>;

    memory@80000000 {
        device_type = "memory";
        reg = <0x80000000 0x10000000>;
    };
};

Compile the source:

dtc -I dts -O dtb -o demo-board.dtb demo-board.dts

Check the generated file:

file demo-board.dtb

Decompile the generated file:

dtc -I dtb -O dts -o output.dts demo-board.dtb

Compare the original source and decompiled output.

This is a compiler exercise only. Do not replace the Device Tree of your running Ubuntu system with this example. The example describes illustrative memory information and is not a valid hardware configuration for an arbitrary computer.

21. Device Tree and ACPI Comparison

Linux supports different methods of describing platform hardware. Device Tree and ACPI are two important approaches.

Device Tree ACPI
Commonly used in embedded systems. Commonly used in PCs, servers and many modern platforms.
Usually supplied as a DTB by firmware or a bootloader. Firmware provides ACPI tables.
Hardware is described using nodes and properties. Hardware is described through ACPI tables and objects.
Uses compatible strings for many driver-matching cases. Uses ACPI identifiers and matching mechanisms.
Source files commonly use DTS and DTSI formats. Source descriptions commonly use ASL and compiled AML.

22. Lesson Summary

  • Device Tree describes hardware components and their relationships.
  • It separates board-specific hardware information from driver code.
  • Device Tree Source uses the DTS format.
  • Compiled Device Tree information is commonly stored in DTB format.
  • Nodes represent hardware components or logical groupings.
  • Properties describe hardware resources and configuration.
  • compatible is important for driver matching.
  • reg describes address and size information.
  • interrupts describes interrupt information.
  • Device Tree can provide information used during platform-device creation and driver probing.
  • dtc compiles and decompiles Device Tree files.
  • Bindings define the required Device Tree representation for hardware.
