2. Introduction to Platform Driver Development

A platform driver is a Linux kernel driver used for hardware devices that are generally integrated into a system-on-chip (SoC) or otherwise described by platform firmware.

Examples include:

  • UART controllers.
  • Memory-mapped timers.
  • SoC GPIO controllers.
  • Interrupt controllers.
  • Memory controllers.
  • Other integrated hardware peripherals.

Platform driver development involves writing a kernel module that matches a registered platform device and initializes its resources.

3. Platform Driver Development Workflow

A typical development workflow consists of the following stages:

  1. Identify the target hardware.
  2. Study its register map and hardware documentation.
  3. Identify memory, interrupt, clock, reset and GPIO resources.
  4. Describe the hardware using Device Tree or another supported firmware mechanism.
  5. Create a platform driver structure.
  6. Define the compatible match table.
  7. Implement the probe callback.
  8. Retrieve and initialize hardware resources.
  9. Implement required device operations.
  10. Implement cleanup and remove handling.
  11. Compile and load the driver.
  12. Test and debug on the target system.

4. Development Environment

Platform driver development requires a suitable Linux kernel development environment.

Common Requirements

  • Linux kernel headers or a configured kernel source tree.
  • GCC or a suitable cross-compiler.
  • GNU Make and Kbuild.
  • Device Tree Compiler when working with DTS files.
  • Target hardware or a suitable emulator.
  • Root or equivalent permissions for module loading and device testing.

Install Basic Build Tools on Ubuntu

sudo apt update
sudo apt install build-essential linux-headers-$(uname -r)
sudo apt install device-tree-compiler

Check the Kernel Version

uname -r

Check GCC

gcc --version

Check DTC

dtc --version
Kernel headers must match the kernel against which the external module is being built. Embedded targets often require a configured kernel build tree and a cross-compilation toolchain instead of the headers from the development PC.

5. Platform Driver Structure

A platform driver is represented by struct platform_driver.

Basic Structure

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,

    .driver = {
        .name = "demo-platform-driver",
        .of_match_table = demo_of_match,
    },
};
Member Purpose
probe Initializes a matched platform device.
remove Handles device unbinding and cleanup.
driver.name Provides the driver's name.
driver.of_match_table Provides Device Tree compatible matching information.
id_table Provides platform device ID matching information when used.

6. Device Tree Description for the Hardware

A platform driver commonly uses Device Tree to obtain hardware information.

Illustrative Device Tree Node

/dts-v1/;

/ {
    compatible = "demo,embedded-board";

    soc {
        #address-cells = <1>;
        #size-cells = <1>;

        demo_device: demo-device@40000000 {
            compatible = "demo,platform-device";
            reg = <0x40000000 0x1000>;
            status = "okay";
        };
    };
};

The compatible string connects the hardware description with the driver's OF match table.

The address and size values are illustrative only. Real DTS nodes must use the target SoC's bus address format, interrupt controller definitions and applicable binding schemas. An actual peripheral may also require clocks, resets, pinctrl and other resources.

7. Creating the Device Tree Match Table

The driver declares which compatible hardware it supports.

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,platform-device" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

The of_match_table is assigned to the driver's embedded struct device_driver.

The kernel uses this table when matching the platform device with the driver.

8. Implementing the Probe Function

The probe callback is called when a suitable device is matched with the driver.

It is commonly responsible for:

  • Allocating private driver data.
  • Retrieving hardware resources.
  • Mapping memory-mapped registers.
  • Obtaining clocks and resets.
  • Obtaining GPIO descriptors.
  • Requesting interrupts.
  • Initializing the hardware.

Basic Probe Function

static int demo_probe(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Platform device detected\n");

    return 0;
}

Returning zero indicates successful initialization.

If a required resource is temporarily unavailable, the driver may return -EPROBE_DEFER so that probe can be retried later.

9. Retrieving Memory Resources

Platform drivers often need access to memory-mapped hardware registers.

The platform API provides:

struct resource *platform_get_resource(
    struct platform_device *pdev,
    unsigned int type,
    unsigned int num
);

For example:

struct resource *res;

res = platform_get_resource(
    pdev,
    IORESOURCE_MEM,
    0
);

if (!res)
    return -ENODEV;

The first memory resource is requested using resource index zero.

Mapping the Resource

void __iomem *base;

base = devm_platform_ioremap_resource(pdev, 0);

if (IS_ERR(base))
    return PTR_ERR(base);

This managed helper retrieves and maps the selected memory resource.

The returned pointer is an I/O memory pointer. Register access should use appropriate kernel I/O accessors such as readl() and writel(), not ordinary pointer dereferencing.

10. Allocating Private Driver Data

Drivers often need a private data structure to store information about a device.

Example Structure

struct demo_data {
    void __iomem *base;
    int irq;
};

Allocate Memory

struct demo_data *data;

data = devm_kzalloc(
    &pdev->dev,
    sizeof(*data),
    GFP_KERNEL
);

if (!data)
    return -ENOMEM;

Store Private Data

platform_set_drvdata(pdev, data);

Retrieve Private Data

struct demo_data *data;

data = platform_get_drvdata(pdev);

Using device-managed allocation simplifies cleanup when the device is detached or probe fails.

11. Retrieving Interrupt Resources

A platform device may have one or more interrupt resources.

Get the First IRQ

int irq;

irq = platform_get_irq(pdev, 0);

if (irq < 0)
    return irq;

The returned IRQ number can be used with an appropriate IRQ registration API.

Requesting an Interrupt

static irqreturn_t demo_irq_handler(
    int irq,
    void *dev_id
)
{
    return IRQ_HANDLED;
}

A managed interrupt request can be performed using:

ret = devm_request_irq(
    &pdev->dev,
    irq,
    demo_irq_handler,
    0,
    "demo-platform-irq",
    data
);

if (ret)
    return ret;
This handler is only a structural example. A real handler must identify and acknowledge the interrupt source according to the hardware specification. It must also use correct shared-interrupt and interrupt-trigger configuration.

12. GPIO Integration

Platform drivers can use the Linux GPIO descriptor API to access GPIO lines described by firmware.

Example Device Tree Property

demo-device@40000000 {
    compatible = "demo,platform-device";
    led-gpios = <&gpio0 12 0>;
    status = "okay";
};

This is illustrative. The actual GPIO controller label, line number and flags depend on the board.

Example Driver Access

#include <linux/gpio/consumer.h>

struct gpio_desc *led;

led = devm_gpiod_get(
    &pdev->dev,
    "led",
    GPIOD_OUT_LOW
);

if (IS_ERR(led))
    return PTR_ERR(led);

The consumer name "led" corresponds to the Device Tree property led-gpios.

The GPIO descriptor API provides a hardware-independent interface to GPIO lines.

13. Complete Platform Driver Example

The following example combines Device Tree matching, private data allocation and memory resource mapping.

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/io.h>
#include <linux/slab.h>

struct demo_data {
    void __iomem *base;
};

static const struct of_device_id demo_of_match[] = {
    {
        .compatible = "demo,platform-device"
    },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static int demo_probe(struct platform_device *pdev)
{
    struct demo_data *data;

    data = devm_kzalloc(
        &pdev->dev,
        sizeof(*data),
        GFP_KERNEL
    );

    if (!data)
        return -ENOMEM;

    data->base = devm_platform_ioremap_resource(
        pdev,
        0
    );

    if (IS_ERR(data->base))
        return PTR_ERR(data->base);

    platform_set_drvdata(pdev, data);

    dev_info(&pdev->dev,
             "Platform driver probe successful\n");

    return 0;
}

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Platform driver removed\n");
}

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,
    .driver = {
        .name = "demo-platform-driver",
        .of_match_table = demo_of_match,
    },
};

module_platform_driver(demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic Platform Driver Development Example");

Code Explanation

  1. Kernel headers provide platform, OF and memory-mapping APIs.
  2. demo_data stores device-specific information.
  3. demo_of_match defines the compatible string.
  4. MODULE_DEVICE_TABLE() exports module matching information.
  5. demo_probe() is called after a matching device is bound.
  6. devm_kzalloc() allocates zero-initialized private memory.
  7. devm_platform_ioremap_resource() obtains and maps the memory resource.
  8. platform_set_drvdata() associates private data with the device.
  9. demo_remove() handles unbinding.
  10. module_platform_driver() registers and unregisters the driver.
This is a framework example, not a complete functional peripheral driver. The Device Tree must describe a real, valid memory resource. The example does not read or write registers and should not be deployed against arbitrary physical addresses.

14. Creating the Makefile

External kernel modules are normally compiled using Kbuild.

Makefile

obj-m += demo_platform.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD  := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Save the driver source as demo_platform.c and the build instructions as Makefile.

Compile

make

A successful build normally produces demo_platform.ko.

15. Loading and Testing the Driver

Insert the Module

sudo insmod demo_platform.ko

Check Module Information

lsmod | grep demo_platform

Inspect Kernel Logs

sudo dmesg | tail -n 30

Remove the Module

sudo rmmod demo_platform
The module can load successfully even if no device matches it. In that case, the probe callback is not executed. A matching platform device must be registered by the system.

16. Testing Platform Driver Binding

Linux exposes platform devices and drivers through sysfs.

List Platform Devices

ls /sys/bus/platform/devices/

List Platform Drivers

ls /sys/bus/platform/drivers/

Inspect a Device

ls -l /sys/bus/platform/devices/

When a device is bound to a driver, its sysfs directory commonly contains a driver symbolic link.

17. Error Handling and Best Practices

Situation Recommended Handling
Private memory allocation fails Return -ENOMEM.
Memory resource is missing Return an appropriate error such as -ENODEV.
Resource mapping fails Check with IS_ERR() and return PTR_ERR().
IRQ retrieval fails Check the returned error before requesting the IRQ.
Dependency is not ready Use -EPROBE_DEFER when appropriate.
Device is removed Stop hardware activity and release non-managed resources.

Development Best Practices

  • Use managed resource APIs where appropriate.
  • Validate every resource before using it.
  • Use dev_info(), dev_warn() and dev_err() for device-specific logging.
  • Use Device Tree bindings that accurately describe the hardware.
  • Never assume a physical register address is valid on another board.
  • Use the correct subsystem API for GPIO, clocks, resets and interrupts.
  • Do not access hardware registers without mapping and appropriate I/O accessors.
  • Test probe failure and device removal paths.
  • Check kernel-version API changes when porting a driver.

18. Common Platform Driver Development Problems

Problem Possible Cause Investigation
Probe is not called No matching device or incompatible string Inspect Device Tree, sysfs and match table.
Module compilation fails Kernel API or header mismatch Check kernel headers and build logs.
Memory mapping fails Invalid or unavailable resource Check the Device Tree resource and error code.
IRQ request fails Invalid IRQ or incorrect flags Inspect interrupt configuration and logs.
Probe is deferred Required supplier is unavailable Inspect clocks, regulators, GPIOs and reset providers.
Driver loads but does not bind Device not registered or no match Inspect platform device and driver directories.

Step 9: Remove the Module

sudo rmmod demo_platform

Expected Result

The module should compile and load if the build environment is configured correctly. If the system has no registered device with the matching compatible string, the probe callback will not run. This is an expected result on a typical x86 VirtualBox installation.

Do not invent a memory resource or manually bind the example driver to arbitrary hardware. Testing successful probe and register access requires a valid device description and suitable hardware or an appropriately configured emulator.

Ubuntu in VirtualBox

Your Ubuntu virtual machine is suitable for learning:

LPC2129 Bare-Metal Development Linux Platform Driver Development
