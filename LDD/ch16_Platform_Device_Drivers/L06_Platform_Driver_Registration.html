2. Introduction to Driver Registration

Writing a platform driver is not sufficient to make it active. The driver must be registered with the Linux platform bus.

Driver registration makes the driver known to the kernel device model. The platform bus can then compare it with platform devices that are already registered or are registered later.

When a suitable device is found, the kernel attempts to bind the driver to that device and invokes its probe callback when the required conditions are met.

3. Platform Driver Registration API

The Linux kernel provides the following function:

int platform_driver_register(
    struct platform_driver *driver
);

This function registers a platform driver with the platform bus.

Parameters

Parameter Description
driver Pointer to the platform-driver structure being registered.

Return Value

  • Returns 0 when registration succeeds.
  • Returns a negative error code when registration fails.

Example

static int __init demo_init(void)
{
    int ret;

    ret = platform_driver_register(&demo_driver);

    if (ret)
        pr_err("Driver registration failed: %d\n", ret);

    return ret;
}

The driver is registered during module initialization.

4. Platform Driver Unregistration API

When a platform driver is no longer needed, it must be unregistered.

void platform_driver_unregister(
    struct platform_driver *driver
);

This function removes the driver from the platform bus.

Unregistration causes devices bound to the driver to be detached through the device-model lifecycle. The driver's remove callback is invoked for applicable bound devices.

Example

static void __exit demo_exit(void)
{
    platform_driver_unregister(&demo_driver);

    pr_info("Platform driver unregistered\n");
}
The registration and unregistration operations must be paired correctly. Do not unregister a driver that was never successfully registered.

5. Manual Driver Registration

A platform driver can be registered manually using module initialization and exit functions.

Complete Registration Pattern

static int __init demo_init(void)
{
    return platform_driver_register(&demo_driver);
}

static void __exit demo_exit(void)
{
    platform_driver_unregister(&demo_driver);
}

module_init(demo_init);
module_exit(demo_exit);

Execution Sequence

  1. The kernel loads the driver module.
  2. The module initialization function executes.
  3. platform_driver_register() registers the driver.
  4. The platform bus checks for matching devices.
  5. The probe callback may be invoked for a matching device.
  6. When the module is unloaded, the exit function executes.
  7. platform_driver_unregister() unregisters the driver.

6. Using module_platform_driver()

Linux provides a helper macro called module_platform_driver().

It simplifies the standard module initialization and exit code for a platform driver.

module_platform_driver(demo_driver);

Conceptually, the macro provides registration and unregistration wrappers around the platform driver.

For a simple driver, it avoids writing separate module_init() and module_exit() functions just for registration.

Comparison

Manual Registration module_platform_driver()
Uses explicit initialization and exit functions. Uses a helper macro.
Calls platform_driver_register() directly. Generates the standard registration wrapper.
Calls platform_driver_unregister() directly. Generates the standard cleanup wrapper.
Useful when custom module initialization or cleanup is required. Useful for straightforward platform-driver modules.
Do not use module_platform_driver() together with separate module_init() and module_exit() definitions for the same module registration path. The macro already provides those module entry points.

7. What Happens During Driver Registration?

When platform_driver_register() is called, the platform driver is registered with the generic driver model through the platform bus infrastructure.

The driver core can then examine devices that are already present on the bus.

Registration Process

  1. The platform driver structure is prepared.
  2. The driver registration function is called.
  3. The driver becomes available to the platform bus.
  4. The driver core checks registered platform devices for possible matches.
  5. Matching is performed using supported mechanisms such as Device Tree, ACPI, platform ID tables or applicable name-based matching.
  6. If a device matches, the kernel attempts to bind the driver.
  7. The probe callback is called when binding proceeds successfully.

If no matching device exists, registration can still succeed. The driver remains registered and may match a device that appears later.

Driver registration and successful device probing are different events. A successful return from platform_driver_register() does not prove that a hardware device has been found or initialized.

8. Device Registration Before or After Driver Registration

The Linux device model supports different registration orders.

Case 1: Device Registered First

↓

The device model handles matching as devices and drivers become available. Developers do not normally need to enforce a fixed registration order.

9. Matching Mechanisms Used During Registration

The platform bus can use several mechanisms to determine whether a driver supports a device.

Matching Mechanism Description
Device Tree Matches a device's compatible property against the driver's OF match table.
ACPI Matches supported ACPI identifiers when applicable.
Platform ID Table Matches platform device identifiers against the driver's ID table.
Name-Based Matching Uses applicable device and driver names as a matching mechanism.

For embedded Linux systems, Device Tree matching is particularly common.

10. Complete Platform Driver Registration Example

The following module demonstrates platform-driver registration using module_platform_driver().

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/kernel.h>

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,registration-device" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static int demo_probe(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Probe called: device matched\n");

    return 0;
}

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Remove called: device detached\n");
}

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,

    .driver = {
        .name = "demo-registration-driver",
        .of_match_table = demo_of_match,
    },
};

module_platform_driver(demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Platform Driver Registration Example");

Explanation

  1. The required kernel headers are included.
  2. The OF match table defines the supported compatible string.
  3. MODULE_DEVICE_TABLE() exports the matching information for module tooling.
  4. The probe callback logs a message when a matching device is bound.
  5. The remove callback logs a message when the device is detached.
  6. The platform driver structure connects the callbacks and match table.
  7. module_platform_driver() registers and unregisters the driver with the module lifecycle.
This example does not create a platform device. A device with the compatible string demo,registration-device must already be registered through a valid mechanism. The remove callback signature shown is for kernels using a void-returning platform remove callback; check the target kernel headers.

11. Building the Kernel Module

Save the source file as:

demo_platform_registration.c

Create a Makefile in the same directory:

obj-m += demo_platform_registration.o

KDIR := /lib/modules/$(shell uname -r)/build
PWD := $(shell pwd)

all:
	$(MAKE) -C $(KDIR) M=$(PWD) modules

clean:
	$(MAKE) -C $(KDIR) M=$(PWD) clean

Compile the module:

make

Load the module:

sudo insmod demo_platform_registration.ko

Check kernel messages:

dmesg | tail -n 30

Remove the module:

sudo rmmod demo_platform_registration
Loading the module can successfully register the driver even if no matching device exists. In that case, the probe message will not appear. Test only on a suitable development system and use matching hardware descriptions.

12. Common Registration Errors

Error or Symptom Possible Cause
Module fails to load Module compilation, symbol, dependency or kernel-version problem.
Driver registration returns an error Invalid driver configuration or registration conflict.
Probe is not called No matching device, incompatible match information or device not registered.
Probe returns an error Missing resources, unavailable dependencies or hardware initialization failure.
Module cannot be removed The module may be in use or cleanup may not have completed.
Compilation reports callback type mismatch Driver callback signature differs from the target kernel version.

14. Best Practices

  • Keep driver registration and device registration conceptually separate.
  • Use module_platform_driver() when standard registration wrappers are sufficient.
  • Check the return value of manual registration functions.
  • Provide appropriate Device Tree or ACPI match information.
  • Handle errors carefully in the probe callback.
  • Release manually managed resources during removal or probe-failure cleanup.
  • Use managed resource APIs where appropriate.
  • Verify callback signatures against the target kernel headers.
  • Do not assume that successful registration means successful hardware initialization.

15. Lesson Summary

  • Platform drivers must be registered with the platform bus.
  • platform_driver_register() registers a platform driver.
  • platform_driver_unregister() unregisters it.
  • module_platform_driver() simplifies standard module registration.
  • Driver registration makes the driver available for device matching.
  • The driver can match devices registered before or after it.
  • Matching can use Device Tree, ACPI, platform ID tables or applicable name-based mechanisms.
  • The probe callback is invoked when a suitable device is bound to the driver.
  • Successful driver registration does not guarantee that a matching device exists.
