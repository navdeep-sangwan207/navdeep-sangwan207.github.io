2. Introduction to Probe and Remove Functions

The probe and remove callbacks are central to the lifecycle of a Linux platform driver.

The probe() function initializes a device after the kernel has matched it with a suitable driver.

The remove() function handles device detachment and cleanup when the device is removed from the driver.

3. Probe Function

The probe callback is declared as a member of struct platform_driver.

A commonly used modern signature is:

static int demo_probe(struct platform_device *pdev)
{
    return 0;
}

Parameter

pdev is a pointer to the platform device that has matched the driver.

Through this pointer, the driver can access:

  • Device resources.
  • Embedded generic device object.
  • Platform device information.
  • Device-specific data and configuration.

Return Value

Return Value Meaning
0 Probe completed successfully.
Negative error code Probe failed.
-EPROBE_DEFER A required dependency is not ready; the driver core may retry later.

4. When Is Probe Called?

The kernel calls the probe callback when the driver core successfully matches a device with a driver and proceeds with binding.

Probe may be triggered when:

  • A matching platform device is registered after the driver.
  • A matching platform driver is registered after the device.
  • A deferred probe is retried after a dependency becomes available.
  • A device is reattached to a driver through an appropriate device-model operation.
Driver registration alone does not guarantee that probe will execute. A suitable device must exist, match the driver and satisfy the required dependencies.

5. Responsibilities of the Probe Function

The probe function prepares the hardware and the driver's software state.

Typical Probe Operations

  1. Identify the device.
  2. Retrieve hardware resources.
  3. Map memory-mapped registers.
  4. Acquire clocks, regulators or GPIO descriptors where required.
  5. Allocate driver-private data.
  6. Configure hardware registers.
  7. Request interrupts if required.
  8. Register interfaces with relevant kernel subsystems.
  9. Return success after initialization.

Not every driver needs all these operations. The exact steps depend on the hardware and the subsystem being implemented.

6. Accessing the Device Object

The platform device contains an embedded generic device object.

Inside probe, it can be accessed using:

&pdev->dev

For example:

static int demo_probe(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Probe function called\n");

    return 0;
}

Device-associated logging macros include:

  • dev_info() – informational message.
  • dev_err() – error message.
  • dev_warn() – warning message.
  • dev_dbg() – debugging message.

7. Retrieving Memory Resources

Platform devices may contain memory resources that describe hardware register ranges.

A driver can retrieve a memory resource using:

struct resource *res;

res = platform_get_resource(
    pdev,
    IORESOURCE_MEM,
    0
);

if (!res)
    return -ENODEV;

Function Parameters

Parameter Meaning
pdev Platform device pointer.
IORESOURCE_MEM Requests a memory resource.
0 Requests the first resource of that type.

The function returns a pointer to the resource or NULL if the requested resource is unavailable.

8. Mapping Memory Resources

Hardware registers are often accessed through memory-mapped I/O (MMIO).

A driver should not directly dereference a physical hardware address. It must obtain an appropriate I/O mapping.

A common managed API is:

void __iomem *base;

base = devm_platform_ioremap_resource(pdev, 0);

if (IS_ERR(base))
    return PTR_ERR(base);

Explanation

  1. devm_platform_ioremap_resource() obtains the selected memory resource.
  2. It requests the resource and creates an I/O mapping.
  3. The returned pointer is an I/O-memory pointer.
  4. IS_ERR() checks whether the returned pointer represents an error.
  5. PTR_ERR() extracts the negative error code.
Managed I/O mappings are released automatically when the device is detached and its managed resources are released. Do not manually call iounmap() for a mapping obtained through this managed API.

9. Retrieving an Interrupt Resource

A platform driver may need an interrupt to respond to hardware events.

The platform API provides:

int irq;

irq = platform_get_irq(pdev, 0);

if (irq < 0)
    return irq;

The second argument identifies the zero-based interrupt resource index.

The returned value is the Linux IRQ number or a negative error code.

A negative return can include -EPROBE_DEFER. Propagate the error instead of converting every failure into a generic error.

The driver can subsequently request the interrupt using an appropriate interrupt API such as devm_request_irq(), with a correctly implemented interrupt handler.

10. Driver-Private Data

Many drivers need private memory to store device-specific information.

A private structure may contain:

  • Mapped register base address.
  • IRQ number.
  • Device configuration.
  • Synchronization objects.
  • Buffers and state information.

Example

struct demo_data {
    void __iomem *base;
    int irq;
};

Allocate managed private data in probe:

struct demo_data *data;

data = devm_kzalloc(
    &pdev->dev,
    sizeof(*data),
    GFP_KERNEL
);

if (!data)
    return -ENOMEM;

platform_set_drvdata(pdev, data);

The function platform_set_drvdata() associates the private data with the platform device.

It can be retrieved later using:

struct demo_data *data;

data = platform_get_drvdata(pdev);

Because devm_kzalloc() is used, the allocated memory is released automatically when the device's managed resources are released.

11. Probe Error Handling

Probe can fail at different stages. The driver must handle errors correctly.

Consider a device that needs a memory resource and an interrupt.

static int demo_probe(struct platform_device *pdev)
{
    struct resource *res;
    int irq;

    res = platform_get_resource(
        pdev,
        IORESOURCE_MEM,
        0
    );

    if (!res)
        return -ENODEV;

    irq = platform_get_irq(pdev, 0);

    if (irq < 0)
        return irq;

    dev_info(&pdev->dev,
             "Resources retrieved successfully\n");

    return 0;
}

This example retrieves resources but does not map memory or register an interrupt handler.

Common Probe Errors

Error Possible Reason
-ENODEV Required device or resource is unavailable.
-ENOMEM Memory allocation failed.
-EINVAL Invalid configuration or argument.
-EBUSY Resource is already in use.
-EPROBE_DEFER A required dependency is not ready.

12. Remove Function

The remove callback is responsible for handling device detachment.

A common modern signature is:

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Device removed\n");
}

It is invoked when a bound device is detached from the driver, such as during device removal or driver unregistration.

Typical Remove Operations

  • Stop ongoing hardware activity.
  • Prevent new operations from starting.
  • Disable hardware interrupts where necessary.
  • Unregister interfaces created by the driver.
  • Release manually managed resources.
  • Ensure asynchronous work is cancelled or completed.
  • Place hardware into a safe state where required.
Some kernel versions use an integer-returning platform remove callback, while newer kernels commonly use a void-returning callback. Always follow the target kernel's declared function-pointer type.

13. Managed and Unmanaged Resources

Linux provides device-managed resource APIs, commonly called devres or managed resources.

Managed resources are associated with the device and automatically released when the device is detached and its managed resources are cleaned up.

Managed API Purpose
devm_kzalloc() Allocates zero-initialized memory managed by the device.
devm_platform_ioremap_resource() Obtains and maps a platform memory resource with managed cleanup.
devm_request_irq() Requests an interrupt with managed release.
devm_gpiod_get() Obtains a GPIO descriptor with managed cleanup.

Managed vs Unmanaged Resources

Managed Unmanaged
Released automatically through device resource management. Usually requires explicit cleanup.
Reduces cleanup code. Requires careful tracking of acquisition and release.
Useful for many ordinary probe operations. Useful when custom lifetime control is required.
Managed resources do not eliminate the need for a remove callback. The driver must still stop hardware activity, unregister interfaces and cancel asynchronous operations where necessary. Resource release alone does not guarantee safe hardware shutdown.

14. Probe Failure and Cleanup

If probe fails after acquiring resources, the driver must ensure that partially initialized state is cleaned up.

Managed resources simplify this process because resources acquired through devres are released when failed probing is unwound.

However, the driver must still reverse operations that are not managed automatically.

Example Concept

static int demo_probe(struct platform_device *pdev)
{
    struct demo_data *data;

    data = devm_kzalloc(
        &pdev->dev,
        sizeof(*data),
        GFP_KERNEL
    );

    if (!data)
        return -ENOMEM;

    platform_set_drvdata(pdev, data);

    /*
     * Additional initialization goes here.
     * Return an error if initialization fails.
     */

    return 0;
}

If this probe function returns an error, the device-managed allocation is released as part of probe-failure cleanup.

15. Complete Platform Driver Example

This example demonstrates managed memory mapping, interrupt retrieval, private data and probe/remove callbacks.

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/interrupt.h>
#include <linux/io.h>
#include <linux/slab.h>

struct demo_data {
    void __iomem *base;
    int irq;
};

static irqreturn_t demo_irq_handler(
    int irq,
    void *dev_id
)
{
    struct demo_data *data = dev_id;

    /*
     * Replace with hardware-specific
     * interrupt status handling.
     */

    (void)data;

    return IRQ_HANDLED;
}

static int demo_probe(struct platform_device *pdev)
{
    struct demo_data *data;
    int ret;

    data = devm_kzalloc(
        &pdev->dev,
        sizeof(*data),
        GFP_KERNEL
    );

    if (!data)
        return -ENOMEM;

    data->base = devm_platform_ioremap_resource(
        pdev,
        0
    );

    if (IS_ERR(data->base))
        return PTR_ERR(data->base);

    data->irq = platform_get_irq(pdev, 0);

    if (data->irq < 0)
        return data->irq;

    platform_set_drvdata(pdev, data);

    ret = devm_request_irq(
        &pdev->dev,
        data->irq,
        demo_irq_handler,
        0,
        dev_name(&pdev->dev),
        data
    );

    if (ret)
        return ret;

    dev_info(&pdev->dev,
             "Device initialized successfully\n");

    return 0;
}

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Device detached\n");
}

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,probe-remove-device" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,

    .driver = {
        .name = "demo-probe-remove",
        .of_match_table = demo_of_match,
    },
};

module_platform_driver(demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Platform Driver Probe and Remove Example");

Code Explanation

  1. struct demo_data stores the device's private information.
  2. devm_kzalloc() allocates zero-initialized private memory.
  3. devm_platform_ioremap_resource() obtains and maps the first memory resource.
  4. platform_get_irq() obtains the first interrupt.
  5. platform_set_drvdata() associates private data with the device.
  6. devm_request_irq() requests the interrupt with managed cleanup.
  7. demo_irq_handler() is called when the requested interrupt is delivered.
  8. demo_remove() handles device detachment.
  9. module_platform_driver() registers the driver.
This is a structural teaching example, not a complete functional hardware driver. A real interrupt handler must inspect and acknowledge the device's interrupt status using the hardware specification. The example assumes that the device provides a valid memory resource and IRQ. The IRQ handler currently does not acknowledge hardware, so it should not be deployed against a real interrupt-generating device unchanged.

16. Important Difference: Probe and Module Initialization

The module initialization function and platform driver's probe callback are different functions.

Module Initialization Probe Callback
Runs when the module is loaded. Runs when a matching device is bound to the driver.
Registers the driver. Initializes a particular device.
Does not require a matching hardware device to exist. Requires a matching device and successful binding conditions.
Uses module initialization mechanisms. Is called by the device-driver core.

Similarly, module exit and device remove are different lifecycle operations. Module exit unregisters the driver; that unregistration causes bound devices to be detached and their remove callbacks to run.

17. Common Mistakes

  • Assuming probe runs immediately when a module is loaded.
  • Ignoring errors returned by resource APIs.
  • Accessing physical register addresses without mapping them.
  • Requesting an interrupt without a valid handler.
  • Failing to stop hardware activity during removal.
  • Manually freeing resources that are already managed by devres.
  • Forgetting to clean up unmanaged resources after probe failure.
  • Using the wrong remove callback signature for the kernel version.
  • Returning success from probe when essential initialization failed.

19. Lesson Summary

  • probe() initializes a device after successful matching and binding.
  • The probe callback receives a struct platform_device pointer.
  • platform_get_resource() retrieves a resource description.
  • devm_platform_ioremap_resource() maps a memory resource.
  • platform_get_irq() retrieves an interrupt number.
  • devm_kzalloc() allocates device-managed memory.
  • platform_set_drvdata() stores private driver data.
  • remove() handles device detachment and cleanup.
  • Managed resources simplify cleanup but do not replace hardware shutdown logic.
  • Probe and remove callback signatures must match the target kernel version.
