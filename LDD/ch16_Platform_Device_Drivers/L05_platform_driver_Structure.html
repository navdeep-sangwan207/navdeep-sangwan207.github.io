2. Introduction to struct platform_driver

The Linux kernel uses struct platform_driver to represent a driver that manages devices on the platform bus.

A platform driver contains information about how the kernel should initialize, operate and remove a supported platform device.

For example, an embedded SoC may contain a UART controller. A UART platform driver provides the software implementation needed to initialize and manage that controller.

Other examples include:

  • GPIO controller drivers.
  • SoC timer drivers.
  • Watchdog drivers.
  • Memory controller drivers.
  • Platform-specific peripheral drivers.

3. Header File

The platform driver interface is provided through:

#include <linux/platform_device.h>

This header provides the platform-device and platform-driver definitions and associated APIs.

4. Conceptual Structure of platform_driver

The actual kernel definition may vary across kernel versions. The following is a simplified conceptual representation of commonly used members:

struct platform_driver {
    int (*probe)(struct platform_device *pdev);

    void (*remove)(struct platform_device *pdev);

    struct device_driver driver;

    const struct platform_device_id *id_table;

    /* Additional kernel-version-specific members */
};

This is an educational representation, not a complete copy of the kernel's actual structure definition.

Important Members

Member Purpose
probe Called when the driver successfully matches a device and the device is ready for driver initialization.
remove Called when the device is detached from the driver, allowing cleanup.
driver Embedded generic device-driver object containing common driver-model information.
id_table Provides a table of platform-device identifiers for applicable name-based matching.
Some kernel versions contain additional callbacks or fields. For example, newer kernels may provide a void-returning remove callback, while older versions used an integer return type. Always check the target kernel headers.

5. Understanding the Probe Function

The probe() callback is one of the most important parts of a platform driver.

It is called when the kernel finds a suitable match between a registered platform device and a platform driver.

The callback receives:

struct platform_device *pdev

This pointer provides access to the device's resources and generic device-model object.

Typical Probe Responsibilities

  1. Identify the device and its hardware configuration.
  2. Retrieve memory and interrupt resources.
  3. Map memory-mapped registers.
  4. Allocate driver-private data.
  5. Initialize hardware.
  6. Register any required subsystem interfaces.
  7. Return success or an appropriate error code.

Basic Probe Example

static int demo_probe(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Platform device matched\n");

    return 0;
}

Returning zero indicates successful initialization. Returning a negative error code indicates that probing failed.

A probe function can return -EPROBE_DEFER when a required dependency, such as a clock, regulator or GPIO provider, is not ready. The driver core can retry probing later.

6. Understanding the Remove Function

The remove() callback is used when a device is detached from its driver.

It allows the driver to release resources and stop hardware activity.

Typical Remove Responsibilities

  • Stop hardware operations.
  • Disable interrupts where necessary.
  • Unregister interfaces created by the driver.
  • Release manually allocated memory.
  • Release resources not managed automatically by the device resource-management system.

Example

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Platform device removed\n");
}

The exact callback signature depends on the target kernel version. Check the definition of struct platform_driver in the headers used to compile the module.

7. Understanding the Embedded driver Member

The driver member is an embedded object of type struct device_driver.

It connects the platform driver with the generic Linux driver model.

Common information supplied through this member includes:

  • Driver name.
  • Owner module.
  • Device Tree match table.
  • Power-management operations.
  • Other generic driver-model configuration.

Example

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,

    .driver = {
        .name = "demo-platform-driver",
    },
};

The .driver.name field provides the generic driver name. It is distinct from the name of a Device Tree compatible string.

8. Device Tree Match Table

Modern embedded Linux systems commonly describe hardware using Device Tree.

A platform driver can provide an Open Firmware match table using struct of_device_id.

Example Match Table

#include <linux/of.h>

static const struct of_device_id demo_of_match[] = {
    {
        .compatible = "demo,platform-device"
    },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

The compatible string identifies the hardware programming model supported by the driver.

The driver connects the table to its generic driver object:

.driver = {
    .name = "demo-platform-driver",
    .of_match_table = demo_of_match,
},

The kernel can use this table to match a Device Tree-described device with the platform driver.

Important: The Device Tree node must use a compatible string supported by the driver. A matching table in the module does not create the hardware device by itself.

9. Platform Device ID Table

A platform driver may also provide an ID table for matching platform devices through their platform device names.

Example

static const struct platform_device_id demo_ids[] = {
    { "demo-uart", 0 },
    { }
};

The table can be assigned to the driver:

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,

    .id_table = demo_ids,

    .driver = {
        .name = "demo-platform-driver",
    },
};

This is an alternative matching mechanism for applicable platform devices. Device Tree and ACPI matching are also common in modern systems.

10. Registering a Platform Driver

A platform driver must be registered with the platform bus before it can manage matching devices.

Linux provides the following APIs:

API Purpose
platform_driver_register() Registers a platform driver.
platform_driver_unregister() Unregisters a platform driver.
module_platform_driver() Provides standard module initialization and cleanup for a platform driver.

Manual Registration Concept

static int __init demo_init(void)
{
    return platform_driver_register(&demo_driver);
}

static void __exit demo_exit(void)
{
    platform_driver_unregister(&demo_driver);
}

module_init(demo_init);
module_exit(demo_exit);

This explicitly registers the driver during module initialization and unregisters it during module exit.

Using module_platform_driver()

The kernel provides a convenient macro:

module_platform_driver(demo_driver);

For a simple module, this macro replaces the need to write the standard registration and unregistration wrapper functions manually.

11. Complete Basic Platform Driver Example

The following example demonstrates a basic platform driver that matches a Device Tree compatible string and logs messages when its callbacks are invoked.

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/kernel.h>

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,platform-device" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static int demo_probe(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Platform device matched successfully\n");

    return 0;
}

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Platform device removed\n");
}

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,

    .driver = {
        .name = "demo-platform-driver",
        .of_match_table = demo_of_match,
    },
};

module_platform_driver(demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic Platform Driver Demonstration");

Code Explanation

  1. linux/module.h provides kernel module definitions.
  2. linux/platform_device.h provides platform driver definitions.
  3. linux/of.h provides Device Tree matching definitions.
  4. demo_of_match[] contains supported compatible strings.
  5. MODULE_DEVICE_TABLE() exposes device matching information for module tooling.
  6. demo_probe() runs when a matching device is bound to the driver.
  7. demo_remove() handles device detachment.
  8. demo_driver describes the platform driver.
  9. module_platform_driver() handles driver registration and unregistration.
Important: Loading this module does not create a platform device. A matching device must already exist, for example through Device Tree enumeration or another valid device-registration mechanism. The remove callback signature shown here is appropriate for kernels that use a void-returning platform remove callback; check your target kernel headers.

12. Device and Driver Relationship

The platform device and platform driver are separate kernel objects.

Platform Device Platform Driver
Represents a hardware device. Represents software that manages the hardware.
Contains device identity and resource information. Contains callbacks and driver matching information.
Uses struct platform_device. Uses struct platform_driver.
Can be created from firmware or registered by platform code. Can be registered as a kernel module or built into the kernel.
Is passed to the driver's probe callback. Uses probe and remove callbacks to manage the device.

13. Inspecting Platform Drivers in Ubuntu

Use the following commands to inspect platform drivers exposed through sysfs.

List Platform Drivers

ls -l /sys/bus/platform/drivers

Inspect a Specific Driver

ls -l /sys/bus/platform/drivers/DRIVER_NAME

List Platform Devices

ls -l /sys/bus/platform/devices

Check Kernel Messages

dmesg | grep -i platform

Replace DRIVER_NAME with an existing driver directory.

Not every Ubuntu virtual machine exposes physical SoC platform peripherals. The available devices depend on the virtual hardware and kernel configuration.

14. Common Mistakes

  • Confusing struct platform_driver with struct platform_device.
  • Assuming that registering a driver automatically creates a hardware device.
  • Forgetting to provide a valid matching mechanism.
  • Using a Device Tree compatible string that does not match the hardware node.
  • Performing hardware initialization without checking resource availability.
  • Ignoring error returns from probe operations.
  • Using a callback signature that does not match the target kernel version.
  • Forgetting to release resources that were allocated manually.

15. Lesson Summary

  • struct platform_driver represents a driver for platform-bus devices.
  • probe() initializes a matched device.
  • remove() handles device detachment and cleanup.
  • driver embeds the generic struct device_driver.
  • id_table supports platform-device ID matching.
  • of_match_table supports Device Tree matching.
  • platform_driver_register() registers a driver.
  • platform_driver_unregister() unregisters a driver.
  • module_platform_driver() simplifies module registration.
  • A matching platform device must exist before the probe callback can run.
