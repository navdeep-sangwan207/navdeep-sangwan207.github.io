2. Introduction

Linux uses the platform device model to represent and manage many hardware components that are not discovered through standard bus enumeration mechanisms.

Two important objects participate in this model:

  • Platform device: Represents the hardware device.
  • Platform driver: Contains the software implementation that operates supported hardware.

For example, an embedded SoC may contain a UART controller. The platform device describes the UART hardware and its resources. The platform driver contains the code that configures the UART, transmits data, receives data and handles interrupts.

3. What Is a Platform Device?

A platform device is a Linux device-model object registered with the platform bus.

It represents a hardware component and provides information needed by the kernel to identify and manage that component.

For example, a UART platform device may be associated with:

  • A UART register address range.
  • An interrupt number.
  • Device identification information.
  • Firmware node information.
  • Other device-specific configuration.

Example: UART Platform Device

Imagine a UART controller with the following illustrative hardware description:

Property Example Value
Device name soc-uart
Register base 0x40000000
Register size 0x1000 bytes
Interrupt 5 (illustrative)
Compatible string vendor,soc-uart

This information describes the hardware. It does not contain the UART driver implementation.

4. What Is a Platform Driver?

A platform driver is a kernel driver registered with the platform bus. It contains the software logic for operating one or more supported platform devices.

A platform driver generally provides:

  • Device matching information.
  • A probe callback.
  • A remove callback.
  • Driver-specific initialization and cleanup code.

Example: UART Platform Driver Responsibilities

  1. Identify a supported UART device.
  2. Obtain its memory and interrupt resources.
  3. Map the UART registers.
  4. Configure baud rate and communication parameters.
  5. Enable required hardware interrupts.
  6. Connect the device to the appropriate Linux serial subsystem.
  7. Release resources when the device is removed.
A platform driver contains the operating logic. A platform device provides the device-model representation and hardware description. These are separate objects with different responsibilities.

6. The struct platform_device Structure

The kernel defines struct platform_device in its platform-device interfaces. It represents a platform device and connects it with the generic Linux device model.

Its exact definition can vary across kernel versions. The following is a simplified conceptual representation, not a complete copy of a particular kernel header:

struct platform_device {
    const char *name;
    int id;

    struct device dev;

    u32 num_resources;
    struct resource *resource;

    /* Additional kernel fields */
};

Important Members

Member Purpose
name Platform device name.
id Device instance identifier; special values can represent an unnamed instance.
dev Embedded generic device-model object.
num_resources Number of resource entries in the resource array.
resource Pointer to the platform device's resource array.

The embedded struct device connects the platform device to common device-model services such as parent-child relationships, driver binding, sysfs and device lifetime management.

Modern platform devices may be created from Device Tree or ACPI. In those cases, device information is populated through firmware enumeration, and developers should normally use the supplied device rather than manually constructing another one.

7. The struct platform_driver Structure

The kernel defines struct platform_driver for drivers that operate platform devices.

The following is a simplified conceptual representation:

struct platform_driver {
    int (*probe)(struct platform_device *pdev);

    void (*remove)(struct platform_device *pdev);

    struct device_driver driver;

    const struct platform_device_id *id_table;

    /* Additional kernel fields */
};

This representation illustrates important members. The actual structure and callback signatures must be checked against the target kernel headers.

Important Members

Member Purpose
probe Initializes a matched platform device.
remove Handles cleanup when the device is detached.
driver Generic driver-model information, including driver name and matching tables.
id_table Platform device ID matching table for applicable devices.

Device Tree and ACPI matching tables are commonly associated with the embedded driver member through its generic driver-model fields.

8. Relationship Between Device and Driver Structures

The platform device and platform driver are associated through the platform bus and Linux driver core.

When the driver core finds a match, the platform driver's probe callback receives a pointer to the platform device being initialized.

This pointer gives the driver access to the device-model object and its associated resources and firmware information.

9. How Matching Takes Place

A platform driver can support multiple devices. The platform bus uses matching information to determine whether the driver supports a particular device.

Device Tree Matching

A Device Tree node may contain:

serial@40000000 {
    compatible = "vendor,soc-uart";
    reg = <0x40000000 0x1000>;
    interrupts = <5>;
    status = "okay";
};

A driver can declare a matching table using the compatible string:

static const struct of_device_id uart_of_match[] = {
    { .compatible = "vendor,soc-uart" },
    { }
};

The table is typically connected to the driver's generic driver structure:

.driver = {
    .name = "soc-uart-driver",
    .of_match_table = uart_of_match,
},

The example illustrates Device Tree matching. A production driver must also follow the relevant binding, resource requirements and kernel API conventions.

Other Matching Methods

  • ACPI matching through ACPI identifiers.
  • Platform ID matching through an ID table.
  • Applicable name-based matching.

10. Probe Function

The probe callback is invoked when a platform device is successfully matched with a driver and the driver core attempts to bind them.

The callback commonly receives:

static int my_probe(struct platform_device *pdev)
{
    /* Device initialization */
    return 0;
}

Common Probe Operations

  1. Obtain memory resources.
  2. Map registers into kernel virtual address space.
  3. Obtain interrupt information.
  4. Initialize driver data and synchronization objects.
  5. Configure the hardware.
  6. Register the device with an appropriate kernel subsystem.

A successful probe normally returns 0. If initialization fails, it returns an appropriate negative error code.

The probe callback must handle partial initialization carefully. If an operation fails after resources have been acquired, those resources must be released before returning an error. Managed resource APIs can simplify this process.

11. Remove Function

The remove callback handles cleanup when a device is unbound from its driver or removed from the system.

A simplified example is:

static void my_remove(struct platform_device *pdev)
{
    /* Stop device activity and release driver-specific resources */
}

In newer kernel versions, the remove callback commonly returns void. Older kernels may use a different callback signature, so always consult the target kernel headers.

Typical Cleanup Operations

  • Stop hardware activity.
  • Disable interrupts and release manually acquired handlers.
  • Unregister subsystem interfaces.
  • Release manually allocated memory.
  • Prevent active operations from accessing freed data.

Resources obtained through managed device APIs are generally released automatically when the device is detached, subject to the relevant API's lifetime rules.

12. Complete Conceptual Platform Driver Example

The following example demonstrates the basic organization of a platform driver module. It registers a driver and prints messages when a matching device is probed or removed.

This example does not access hardware registers. It is intended to demonstrate driver registration and matching.

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/kernel.h>

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,platform-device" },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static int demo_probe(struct platform_device *pdev)
{
    dev_info(&pdev->dev, "Platform device matched\n");

    return 0;
}

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev, "Platform device removed\n");
}

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,

    .driver = {
        .name = "demo-platform-driver",
        .of_match_table = demo_of_match,
    },
};

module_platform_driver(demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Basic Platform Driver Demonstration");

Code Explanation

Code Element Explanation
platform_device.h Provides platform device and driver interfaces.
of_device_id Defines Device Tree compatible identifiers.
MODULE_DEVICE_TABLE() Exports device matching information for module alias generation.
demo_probe() Runs when a matching device is bound.
demo_remove() Runs when the device is detached.
module_platform_driver() Creates module initialization and exit registration logic for the platform driver.
Important: Loading this module alone does not create a matching platform device. A device with the compatible string demo,platform-device must already be registered, for example through a suitable Device Tree description. Without a matching device, the module can load successfully without the probe callback being called.

13. Understanding module_platform_driver()

The macro module_platform_driver() is a convenient way to register and unregister a platform driver from a loadable kernel module.

Conceptually, it performs the work of an initialization function and an exit function:

static int __init demo_init(void)
{
    return platform_driver_register(&demo_driver);
}

static void __exit demo_exit(void)
{
    platform_driver_unregister(&demo_driver);
}

module_init(demo_init);
module_exit(demo_exit);

The macro avoids writing this repetitive registration boilerplate manually.

When the module is loaded, its registration logic runs. When the module is unloaded, the driver is unregistered, and bound devices are detached through the driver lifecycle.

14. Device Resources and Driver Access

The platform device provides hardware resource information to the driver. The driver obtains the resources using platform and generic device APIs.

Common resource categories include:

  • IORESOURCE_MEM – memory-mapped register ranges.
  • IORESOURCE_IRQ – interrupt resources.
  • IORESOURCE_DMA – DMA-related resources.
  • IORESOURCE_IO – port-mapped I/O ranges where applicable.

For example, a driver may obtain and map a memory resource using:

struct resource *res;
void __iomem *base;

res = platform_get_resource(pdev, IORESOURCE_MEM, 0);

base = devm_platform_ioremap_resource(pdev, 0);

if (IS_ERR(base))
    return PTR_ERR(base);

This is an illustrative resource-mapping fragment. The separate res variable is not needed in this fragment unless the driver uses the resource for another purpose.

devm_platform_ioremap_resource() obtains and maps the selected memory resource and manages the mapping lifetime with the device.

Do not directly dereference the physical address from a hardware manual. Use the kernel resource and I/O mapping APIs, then access registers with appropriate I/O accessors such as readl() and writel().

15. Inspecting Platform Devices and Drivers in Ubuntu

You can inspect the platform device model through sysfs.

List Platform Devices

ls -l /sys/bus/platform/devices

List Platform Drivers

ls -l /sys/bus/platform/drivers

Inspect a Specific Device

ls -l /sys/bus/platform/devices/DEVICE_NAME

Replace DEVICE_NAME with an actual entry shown by the first command.

Check for a Driver Link

readlink /sys/bus/platform/devices/DEVICE_NAME/driver

If the device is bound to a driver and the link exists, the command displays the target. If no driver is bound, the path may not exist.

Inspect Kernel Messages

dmesg | grep -i platform

These commands inspect the running environment. The devices and drivers available depend on the kernel configuration, firmware description and virtual or physical hardware.

16. Common Mistakes

  • Confusing the platform device with the platform driver.
  • Assuming driver registration creates a hardware device.
  • Assuming every platform driver immediately receives a probe callback.
  • Ignoring Device Tree or ACPI matching information.
  • Accessing hardware registers through an un-mapped physical address.
  • Failing to clean up resources when probe fails.
  • Assuming every platform device has a matching driver.
  • Copying callback signatures from a different kernel version without checking the target headers.

17. Lesson Summary

  • A platform device represents hardware in the Linux device model.
  • A platform driver contains software for operating supported hardware.
  • struct platform_device represents the platform device.
  • struct platform_driver represents the platform driver.
  • Platform devices provide resource and identification information.
  • Platform drivers provide matching information and callbacks.
  • The platform bus and driver core manage matching and binding.
  • The probe callback initializes a matched device.
  • The remove callback handles cleanup.
  • platform_driver_register() registers a platform driver.
  • platform_driver_unregister() unregisters a platform driver.
  • module_platform_driver() simplifies module registration boilerplate.
