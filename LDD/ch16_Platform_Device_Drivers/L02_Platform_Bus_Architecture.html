2. Introduction to Platform Bus Architecture

The Linux kernel supports different types of hardware devices. These devices may be connected through PCI, USB, I2C, SPI or other buses. Some hardware, especially peripherals integrated into a System-on-Chip (SoC), is represented through the platform bus.

The platform bus is part of the Linux device model. It provides a common framework for registering platform devices and platform drivers, matching them and managing their lifecycle.

The platform bus is not a physical electrical bus that must exist as a separate external connector. It is a software abstraction implemented by the Linux kernel.

Why Is a Bus Model Needed?

Without a common device model, each hardware driver would need to implement its own mechanisms for device discovery, registration, driver association and lifecycle management.

The Linux device model provides reusable infrastructure so that different bus types can follow a consistent approach.

3. Position of the Platform Bus in Linux Architecture

The platform bus operates within the Linux driver core and device model. It connects registered platform devices with registered platform drivers.

The driver core provides common infrastructure for device and driver registration. The platform bus supplies platform-specific matching and lifecycle integration.

The actual driver communicates with the hardware using appropriate kernel APIs.

4. Main Components of Platform Bus Architecture

The platform bus architecture involves several important components.

4.1 Platform Device

A platform device represents a hardware device registered with the platform bus.

It may contain or reference:

  • Device name and identification information.
  • Memory-mapped register ranges.
  • Interrupt resources.
  • DMA-related information.
  • Generic Linux device-model information.

4.2 Platform Driver

A platform driver represents software that supports one or more platform devices.

It generally provides:

  • Device matching information.
  • A probe callback.
  • A remove callback.
  • Driver-specific initialization and cleanup logic.

4.3 Platform Bus

The platform bus connects platform devices and platform drivers. It handles the matching process and participates in the device binding lifecycle.

4.4 Driver Core

The Linux driver core provides generic services such as device registration, driver registration, binding, unbinding, reference management and sysfs representation.

4.5 Firmware Description

Firmware information can describe hardware resources and device identifiers. Device Tree and ACPI are common sources of this information.

5. Platform Bus Data Flow

Consider an SoC containing a UART controller. The firmware describes its hardware resources, and Linux creates a corresponding device-model object.

The firmware description does not itself implement the driver. It supplies information about the hardware. The driver contains the code needed to operate that hardware.

6. Device Registration

A device must be registered with the Linux device model before it can participate in normal bus matching.

For platform devices, registration is performed through platform-device APIs or by firmware enumeration paths that create platform devices.

Examples of platform-device registration APIs include:

  • platform_device_register()
  • platform_device_add()
  • platform_device_register_full()

These APIs are used in different device creation workflows. They are not interchangeable in every situation.

Conceptual Registration Sequence

  1. Hardware information becomes available.
  2. A platform device object is prepared.
  3. Its resources and identification information are configured.
  4. The device is registered with the platform bus.
  5. The driver core makes it available for matching.
Important: Modern embedded systems often obtain platform devices through firmware enumeration. A driver developer normally does not manually create a second platform device for hardware that is already described and instantiated by Device Tree or ACPI.

7. Driver Registration

A platform driver must register with the platform bus before it can bind to matching devices.

The commonly used registration function is:

platform_driver_register(&my_platform_driver);

To unregister the driver:

platform_driver_unregister(&my_platform_driver);

These functions are commonly used in a kernel module's initialization and exit paths.

Conceptual Driver Registration Sequence

  1. The driver structure is initialized.
  2. Matching information is supplied.
  3. The probe and remove callbacks are defined.
  4. The driver is registered with the platform bus.
  5. The driver core checks for matching devices.

Registration does not mean that every device will automatically bind. A compatible device must be present and matching must succeed.

8. Device and Driver Matching

One of the main responsibilities of the platform bus is to determine whether a platform driver supports a platform device.

The Linux platform bus can use several matching mechanisms.

8.1 Device Tree Matching

Device Tree matching uses compatible strings declared in the hardware description and listed by the driver.

For example, a Device Tree node might contain:

compatible = "vendor,soc-uart";

A driver can provide a matching table containing the same compatible identifier.

8.2 ACPI Matching

On systems using ACPI, devices can be matched using ACPI identifiers and the driver's ACPI match table.

8.3 Platform ID Matching

Platform drivers can also provide a platform device ID table for devices that use platform IDs.

8.4 Name-Based Matching

Platform matching also supports applicable name-based matching mechanisms. This is particularly relevant to platform devices registered directly by platform code.

Matching Method Information Used Typical Context
Device Tree Compatible string Embedded Linux
ACPI ACPI hardware identifier ACPI-based systems
Platform ID Platform device ID Platform-code-created devices
Name Matching Device and driver names Applicable legacy or direct registration cases

9. Driver Binding and the Probe Callback

When the platform bus finds a compatible driver for a device, the driver core can bind the driver to that device.

The driver's probe callback is then invoked as part of the binding process.

Typical Probe Responsibilities

  • Verify device-specific configuration.
  • Obtain memory and interrupt resources.
  • Map hardware registers.
  • Initialize device state.
  • Configure hardware.
  • Register with an appropriate kernel subsystem.
Device and Driver Registered
↓
Matching Completed
↓
Driver Bound to Device
↓
Probe Callback Executed
↓
Device Initialized

If probe fails, the driver core handles the unsuccessful binding attempt. The probe implementation must release resources it acquired before returning an error.

Important: A successful driver registration and a successful device probe are different events. Registration adds the driver to the bus; probe initializes a particular matched device.

10. Device Unbinding and Remove Callback

A platform driver may be detached from a device when the device is removed, the driver is unregistered, or the binding is explicitly changed.

The remove callback handles cleanup for the device.

Typical Remove Responsibilities

  • Stop ongoing hardware operations.
  • Disable and release interrupts where appropriate.
  • Unregister subsystem interfaces created by the driver.
  • Release device-specific resources.
  • Ensure no active operation can access freed driver data.
Driver Bound to Device
↓
Device Unbinding or Removal
↓
Remove Callback
↓
Cleanup and Resource Release
↓
Driver No Longer Bound

Exact callback signatures and details can vary with Linux kernel versions. Later lessons will examine the platform driver structure and callback implementation.

11. Role of the Linux Driver Core

The platform bus does not independently implement every aspect of device management. It uses the common Linux driver core.

The driver core provides functionality such as:

  • Device and driver registration infrastructure.
  • Device-driver binding and unbinding.
  • Reference counting and object lifetime management.
  • Sysfs representation of devices and drivers.
  • Power-management integration.
  • Common device hierarchy management.

The platform bus supplies the platform-specific bus implementation and matching logic while using these shared facilities.

12. Sysfs Representation of the Platform Bus

Linux exposes much of its device model through the sysfs virtual filesystem.

The platform bus is normally visible at:

/sys/bus/platform/

Important directories include:

Path Purpose
/sys/bus/platform/devices Platform devices associated with the platform bus.
/sys/bus/platform/drivers Registered platform drivers.
/sys/bus/platform/drivers_autoprobe Bus-level control related to automatic probing, when exposed.

Device and driver directories may contain symbolic links and attributes that show relationships and state.

Inspect Platform Bus

ls -l /sys/bus/platform

List Platform Devices

ls -l /sys/bus/platform/devices

List Platform Drivers

ls -l /sys/bus/platform/drivers

Inspect a Device Directory

find /sys/bus/platform/devices -maxdepth 2 -type f

Inspect a Driver Directory

find /sys/bus/platform/drivers -maxdepth 2 -type f
Observation: Some entries under sysfs are symbolic links rather than regular files. Use ls -l to identify these relationships. The exact list depends on the running kernel and hardware environment.

13. Understanding Device and Driver Links in Sysfs

When a driver successfully binds to a device, sysfs can expose the relationship between them.

A bound device may contain a symbolic link named:

driver

This link points to the driver directory associated with the device.

A driver's sysfs directory may contain a devices directory or equivalent links representing devices bound to that driver.

Inspect Driver Binding

ls -l /sys/bus/platform/devices

Choose an actual device name from the output and inspect it:

ls -l /sys/bus/platform/devices/DEVICE_NAME

Replace DEVICE_NAME with an existing entry. If a driver link is present, it indicates that the device is bound to a driver.

Not every platform device will have a bound driver. A device can exist in the device model without a matching driver being registered or successfully probing.

14. Platform Bus vs Other Linux Buses

The platform bus is one of several bus models supported by Linux.

Bus Typical Device Driver Model
Platform SoC UART, timer, GPIO controller Platform driver
PCI PCIe network or storage controller PCI driver
USB USB keyboard or storage device USB driver
I2C I2C sensor or EEPROM I2C client driver
SPI SPI flash or sensor SPI driver

Some controllers themselves may be platform devices, while the peripherals attached to those controllers are represented through their respective I2C or SPI bus models.

For example, an SoC's I2C controller may be a platform device. An external temperature sensor connected to that controller is generally represented as an I2C client device.

15. Example: SoC I2C Controller and I2C Sensor

Consider an embedded board containing an I2C controller integrated into the SoC and an external temperature sensor connected to it.

SoC Processor
↓
I2C Controller Hardware
↓
Platform Device and Platform Driver
↓
Linux I2C Adapter
↓
I2C Temperature Sensor
↓
I2C Client Driver

The I2C controller driver manages the controller hardware and registers an I2C adapter with the I2C subsystem.

The I2C subsystem then represents attached peripherals as I2C client devices. A separate I2C client driver handles the temperature sensor.

Key distinction: The I2C controller and the I2C peripheral are different devices. The controller may be managed by a platform driver, while the peripheral is managed by an I2C client driver.

16. Common Mistakes

  • Confusing platform bus with a physical bus: The platform bus is a kernel software abstraction.
  • Assuming every embedded peripheral is a platform device: Devices may belong to I2C, SPI, USB or other bus models.
  • Confusing registration with probing: Registering a driver does not guarantee that a device will successfully probe.
  • Assuming Device Tree contains driver code: Device Tree describes hardware; the driver implements device operation.
  • Assuming every device has a bound driver: A device can be registered without a matching driver.
  • Ignoring cleanup: Remove and error-handling paths must release resources safely.
  • Assuming VirtualBox exposes physical SoC peripherals: Hardware access depends on the virtual machine and emulated devices available.

17. Lesson Summary

  • The platform bus is part of the Linux device model.
  • It connects platform devices with platform drivers.
  • The Linux driver core provides common device-management infrastructure.
  • Platform devices can be created through firmware enumeration or platform code.
  • Platform drivers register through platform driver APIs.
  • Matching can use Device Tree, ACPI, platform IDs or applicable name-based mechanisms.
  • Successful matching can lead to driver binding and probe execution.
  • The remove callback handles cleanup during unbinding or device removal.
  • Sysfs exposes platform devices, drivers and their relationships.
  • An SoC I2C or SPI controller can be a platform device even though its attached peripherals use separate bus models.
