2. Introduction to Device Tree Matching

Linux device drivers must identify which hardware devices they support.

In embedded Linux, hardware information is commonly provided through Device Tree. A Device Tree node describes a peripheral, while a driver declares which compatible hardware it supports.

Device Tree matching is the process of comparing the node's compatible information with the driver's declared match table.

Device Tree Node
↓
compatible = "demo,soc-uart"
↓
Driver OF Match Table
↓
Compatible Entry Found
↓
Driver Probe Callback

3. The Compatible Property

The compatible property identifies the programming model or hardware implementation represented by a Device Tree node.

Example Device Tree Node

uart0: serial@40000000 {
    compatible = "demo,soc-uart";
    reg = <0x40000000 0x1000>;
    status = "okay";
};

Here, the compatible string is:

demo,soc-uart

The driver can declare support for this string in its OF match table.

Compatible strings commonly follow a vendor-specific naming convention. Real drivers should use the documented compatible string for the actual hardware, not an arbitrary name.

4. The of_device_id Structure

The Linux kernel provides the struct of_device_id structure for matching drivers against Device Tree nodes.

It is defined in the kernel's OF (Open Firmware) Device Tree infrastructure.

Common Fields

Field Purpose
name Matches a node name in supported matching contexts.
type Matches a Device Tree node type in supported contexts.
compatible Matches a compatible string.
data Stores driver-specific match data associated with an entry.

Most modern platform drivers primarily use the compatible field.

5. Creating an OF Match Table

An OF match table is an array of struct of_device_id entries.

Example

static const struct of_device_id demo_of_match[] = {
    { .compatible = "demo,soc-uart" },
    { }
};

The first entry declares a compatible hardware string.

The final empty entry terminates the table.

Assigning the Table to a Platform Driver

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,
    .driver = {
        .name = "demo-uart-driver",
        .of_match_table = demo_of_match,
    },
};

The of_match_table member connects the match table to the driver's embedded device-driver structure.

6. Understanding MODULE_DEVICE_TABLE()

The macro MODULE_DEVICE_TABLE() exports device matching information in a form that module tools can use.

Syntax

MODULE_DEVICE_TABLE(of, demo_of_match);

Here:

  • of identifies the Open Firmware / Device Tree matching category.
  • demo_of_match is the OF match table.

This information can be used to generate module alias information for automatic module loading by userspace mechanisms.

MODULE_DEVICE_TABLE() does not itself register the driver or cause the probe callback to run. Runtime matching is performed through the driver core using the driver's match table.

7. How Device Tree Matching Works

The general matching sequence for a platform driver is:

  1. The bootloader or firmware supplies the Device Tree to the kernel.
  2. The kernel parses the hardware description.
  3. Appropriate device-population code registers devices with their relevant subsystems.
  4. A platform device is registered when the node is represented as a platform device.
  5. The platform driver is registered.
  6. The platform bus checks whether the driver supports the device.
  7. The OF matching mechanism compares compatible information.
  8. If a match is found, the driver's probe callback is called.
Bootloader Supplies DTB
↓
Kernel Parses Device Tree
↓
Platform Device Registered
↓
Platform Driver Registered
↓
OF Compatible Matching
↓
Probe Callback Executed

The driver and device can be registered in either order. If a matching counterpart becomes available later, the driver core can perform matching then.

8. Multiple Compatible Strings

A Device Tree node can contain more than one compatible string.

This is useful when a device is compatible with a newer implementation and also follows an older, more general programming model.

Example

uart0: serial@40000000 {
    compatible = "vendor,soc-uart-v2",
                 "vendor,soc-uart";
    reg = <0x40000000 0x1000>;
    status = "okay";
};

The compatible strings are listed from the most specific implementation toward more general compatible implementations.

A driver may contain entries for both supported implementations:

static const struct of_device_id demo_of_match[] = {
    { .compatible = "vendor,soc-uart-v2" },
    { .compatible = "vendor,soc-uart" },
    { }
};

The kernel's OF matching mechanism can match a supported compatible entry in the node's compatible list.

9. Using Match Data

The data field in an OF match entry can point to driver-specific information.

This allows one driver to support multiple hardware variants with different capabilities or register layouts.

Example

struct demo_variant {
    unsigned int version;
    unsigned int fifo_size;
};

static const struct demo_variant variant_a = {
    .version = 1,
    .fifo_size = 16,
};

static const struct demo_variant variant_b = {
    .version = 2,
    .fifo_size = 64,
};

static const struct of_device_id demo_of_match[] = {
    {
        .compatible = "demo,uart-v1",
        .data = &variant_a,
    },
    {
        .compatible = "demo,uart-v2",
        .data = &variant_b,
    },
    { }
};

Inside probe, the driver can retrieve the match data:

const struct of_device_id *match;
const struct demo_variant *variant;

match = of_match_device(
    demo_of_match,
    &pdev->dev
);

if (!match)
    return -ENODEV;

variant = match->data;

if (!variant)
    return -EINVAL;

dev_info(&pdev->dev,
         "Hardware version: %u\n",
         variant->version);

This illustrates how a driver can select hardware-specific configuration based on the matched Device Tree entry.

10. Complete Platform Driver Example

The following example demonstrates Device Tree matching in a simple platform driver.

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/of.h>
#include <linux/kernel.h>

static const struct of_device_id demo_of_match[] = {
    {
        .compatible = "demo,platform-device"
    },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

static int demo_probe(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Device Tree matched successfully\n");

    return 0;
}

static void demo_remove(struct platform_device *pdev)
{
    dev_info(&pdev->dev,
             "Platform device removed\n");
}

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,
    .driver = {
        .name = "demo-platform-driver",
        .of_match_table = demo_of_match,
    },
};

module_platform_driver(demo_driver);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Device Tree Matching Demonstration");

Explanation

  • linux/platform_device.h provides platform-driver definitions.
  • linux/of.h provides Device Tree matching definitions.
  • demo_of_match contains supported compatible strings.
  • MODULE_DEVICE_TABLE() exports matching information for module alias generation.
  • demo_probe() runs after a matching device is bound to the driver.
  • demo_remove() handles device unbinding.
  • module_platform_driver() registers and unregisters the driver.
This is a matching demonstration, not a complete hardware driver. Loading this module alone does not create a device. A matching device must already be registered through the relevant platform or firmware-population mechanism.

11. Device Tree Matching vs Platform ID Matching

Linux platform drivers can support more than one matching mechanism.

Device Tree Matching Platform ID Matching
Uses OF compatible strings. Uses platform device IDs.
Common in firmware-described embedded hardware. Common with devices registered by platform code.
Uses of_device_id. Uses platform_device_id.
Table assigned through of_match_table. Table assigned through id_table.

Platform ID Table Example

static const struct platform_device_id demo_ids[] = {
    { "demo-device", 0 },
    { }
};

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,
    .id_table = demo_ids,
    .driver = {
        .name = "demo-driver",
    },
};

A driver can support both OF matching and platform ID matching when required.

12. Device Tree Matching vs Driver Name Matching

The platform bus also supports matching using device and driver names in applicable cases.

For example:

static struct platform_driver demo_driver = {
    .probe = demo_probe,
    .remove = demo_remove,
    .driver = {
        .name = "demo-platform-device",
    },
};

The driver name is useful for platform-device name matching, but it is not a replacement for a proper OF compatible table when the hardware is described using Device Tree.

13. Checking Device Tree Matching in Linux

On a Device Tree-based system, you can inspect the live Device Tree and platform driver information.

Check the Live Device Tree

ls /sys/firmware/devicetree/base

Check Platform Devices

ls /sys/bus/platform/devices/

Check Platform Drivers

ls /sys/bus/platform/drivers/

Check Driver Binding

ls -l /sys/bus/platform/devices/

A device directory may contain a driver symlink when it is bound to a driver.

Inspect Module Information

modinfo demo_driver.ko

Module alias information may include OF-compatible aliases when the driver exports its match table.

14. Debugging Device Tree Matching Problems

If a platform driver's probe function does not execute, inspect the matching process systematically.

Problem What to Check
Compatible string mismatch Compare the Device Tree compatible value with the driver's OF table.
Node disabled Check whether the node has status = "okay".
Device not registered Check whether the relevant bus or subsystem populated the node.
Driver not loaded Check module loading and kernel configuration.
Missing OF match table Check the driver's of_match_table assignment.
Probe returns an error Inspect kernel logs and the resources requested by probe.
Missing dependency Check clocks, regulators, GPIOs, resets and other suppliers.

Useful Commands

dmesg | grep -i platform
dmesg | grep -i device
dmesg | grep -i probe
ls /sys/bus/platform/devices/
ls /sys/bus/platform/drivers/

15. Deferred Probe

A driver may match a device but still be unable to complete initialization because a required resource provider is not ready.

For example, a peripheral driver may depend on:

  • A clock provider.
  • A regulator.
  • A GPIO controller.
  • A reset controller.
  • A pin-control provider.

In such cases, probe may return:

return -EPROBE_DEFER;

The driver core can retry probe later when the required dependency becomes available.

A successful compatible match and a successful probe are different events. Matching identifies a suitable driver; probe performs device initialization.

16. Device Tree Matching and Driver Module Aliases

Linux module tools can use device aliases to identify which modules may support a particular device.

When a driver includes:

MODULE_DEVICE_TABLE(of, demo_of_match);

the build system can generate OF-related module alias information.

Inspect it using:

modinfo demo_driver.ko

Alias information helps userspace module-loading mechanisms select a suitable module when a device is discovered.

Actual driver binding still depends on the device being registered, the driver being available and the runtime matching process succeeding.

17. Best Practices for Device Tree Matching

  • Use documented compatible strings.
  • Follow the relevant Device Tree binding schema.
  • Use the most specific compatible string first.
  • Include fallback compatible strings only when hardware compatibility is genuine.
  • Use match data for hardware variants when appropriate.
  • Check node status and resource descriptions.
  • Use kernel device logging functions during probe and remove.
  • Handle deferred probe correctly when dependencies are not ready.
  • Do not assume a module loading successfully means a device has matched.
  • Test on the intended hardware or a suitable emulator.

18. Practical Exercise: Create a Device Tree Match Table

Objective: Understand how a platform driver matches a Device Tree compatible string.

Step 1: Create a Sample Device Tree Node

demo_device: demo-device@40000000 {
    compatible = "nslearninghub,demo-device";
    reg = <0x40000000 0x1000>;
    status = "okay";
};

Step 2: Create the OF Match Table

static const struct of_device_id demo_of_match[] = {
    {
        .compatible = "nslearninghub,demo-device"
    },
    { }
};

MODULE_DEVICE_TABLE(of, demo_of_match);

Step 3: Assign It to the Platform Driver

.driver = {
    .name = "demo-device-driver",
    .of_match_table = demo_of_match,
},

Step 4: Understand the Expected Flow

  1. The kernel receives a Device Tree containing the node.
  2. The appropriate subsystem registers the device.
  3. The platform driver is registered.
  4. The platform bus checks the OF match table.
  5. The compatible string matches.
  6. The probe callback is invoked.
This is a matching exercise. The illustrative node must be placed within a valid target board Device Tree, with correct address-cell, size-cell, bus and resource definitions, before it can represent real hardware.
