2. Introduction to struct platform_device

The Linux kernel uses struct platform_device to represent a device that belongs to the platform bus.

It is an important part of the Linux platform device model. The structure contains device identification information, resource information and an embedded generic device-model object.

For example, an SoC may contain:

  • UART controller.
  • I2C controller.
  • SPI controller.
  • GPIO controller.
  • Timer.
  • Watchdog controller.

When these devices are represented through the platform bus, the Linux kernel uses platform-device objects to manage them.

SoC Hardware Peripheral
↓
Hardware Description and Resources
↓
struct platform_device
↓
Linux Platform Bus
↓
Matching Platform Driver

3. Definition of struct platform_device

The actual definition is provided by the Linux kernel platform-device headers, commonly through:

#include <linux/platform_device.h>

The exact structure definition can change between kernel versions. The following is a simplified conceptual representation of important members:

struct platform_device {
    const char *name;
    int id;

    struct device dev;

    u32 num_resources;
    struct resource *resource;

    /* Additional kernel fields */
};

This example is for understanding the structure's organization. It is not a complete replacement for the target kernel's actual header definition.

Main Members

Member Description
name Name associated with the platform device.
id Instance identifier used in platform device naming and identification.
dev Embedded generic Linux device-model object.
num_resources Number of resource entries in the resource array.
resource Pointer to the resource array associated with the platform device.

4. Understanding the name Member

The name member identifies the platform device in platform-device registration workflows.

For example, a platform device might be registered with a name such as:

uart-controller

The device name is useful in device identification and applicable name-based matching.

However, modern firmware-described devices may be matched using Device Tree compatible strings or ACPI identifiers instead of relying only on the platform device name.

The platform device name and the Device Tree compatible string serve different purposes. The name identifies the platform device object, while the compatible string describes the hardware programming model for matching.

5. Understanding the id Member

The id member distinguishes instances of devices that share the same platform device name.

For example, a system may have two devices with the same base name:

  • uart-controller.0
  • uart-controller.1

The instance identifier helps distinguish these devices in platform-device naming workflows.

Platform device APIs commonly use a negative identifier such as PLATFORM_DEVID_NONE to indicate that a device should not receive a numbered instance suffix. Other special identifiers are used by specific registration helpers.

Example Concept

Device name: uart-controller
Device ID:   0

Device name: uart-controller
Device ID:   1

The exact sysfs device name depends on the registration method and kernel implementation.

6. Understanding the dev Member

The dev member is an embedded object of type struct device.

This is one of the most important members of struct platform_device because it connects the platform device with the generic Linux device model.

Through this object, a platform device participates in common kernel infrastructure such as:

  • Device registration.
  • Driver binding and unbinding.
  • Parent-child device relationships.
  • Device reference counting.
  • Sysfs representation.
  • Power management.
  • Firmware-node association.
  • Device-specific logging.

Accessing the Embedded Device Object

Inside a platform driver's callback, the generic device object can be accessed through:

&pdev->dev

For example:

dev_info(&pdev->dev, "Device initialized\n");

The dev_info() macro prints a device-associated informational message.

Remember: pdev is a pointer to struct platform_device. The expression pdev->dev accesses its embedded generic device object.

7. Understanding the resource Member

The resource member points to an array of resource descriptions associated with the platform device.

A resource describes a hardware resource such as:

  • Memory-mapped register range.
  • Interrupt resource.
  • DMA-related resource.
  • I/O port range where applicable.

Each resource is represented using struct resource.

Conceptual Resource Structure

struct resource {
    resource_size_t start;
    resource_size_t end;
    unsigned long flags;

    /* Additional kernel fields */
};

This is a simplified illustration. The actual kernel structure includes additional fields.

Member Meaning
start Starting address or resource identifier.
end Ending address or resource identifier.
flags Describes the resource type and associated attributes.

8. Types of Platform Device Resources

Linux defines resource flags to identify different types of hardware resources.

Resource Flag Meaning Example
IORESOURCE_MEM Memory address range. UART register block.
IORESOURCE_IRQ Interrupt resource. UART interrupt.
IORESOURCE_DMA DMA-related resource. DMA channel information where applicable.
IORESOURCE_IO Port-mapped I/O range. I/O ports on architectures that support them.

Example Resource Description

Consider a UART controller with the following illustrative resources:

Memory resource:
Start = 0x40000000
End   = 0x40000FFF
Type  = IORESOURCE_MEM

Interrupt resource:
Start = 5
End   = 5
Type  = IORESOURCE_IRQ

The memory resource describes a 4 KB register range. The interrupt resource identifies an interrupt number in the relevant interrupt domain.

Resource addresses and interrupt numbers are hardware-specific. An interrupt value must be interpreted according to the platform's interrupt-controller description; it is not universally a CPU interrupt vector number.

9. Understanding num_resources

The num_resources member indicates how many entries are present in the platform device's resource array in the applicable registration model.

For example, if a manually registered device has one memory resource and one interrupt resource, its resource array contains two entries.

num_resources = 2;

The driver can request resources by type and index through platform resource helper functions.

For firmware-created devices, resources are populated through the relevant enumeration and resource-management paths. Developers should use the platform resource APIs rather than assuming a manually supplied resource array exists in every case.

10. Example: Manually Defined Platform Device Resources

The following example illustrates how platform resources can be described for a platform device registered directly by platform code.

#include <linux/module.h>
#include <linux/platform_device.h>
#include <linux/ioport.h>

static struct resource uart_resources[] = {
    {
        .start = 0x40000000,
        .end   = 0x40000FFF,
        .flags = IORESOURCE_MEM,
    },
    {
        .start = 5,
        .end   = 5,
        .flags = IORESOURCE_IRQ,
    },
};

static struct platform_device uart_device = {
    .name = "demo-uart",
    .id = -1,
    .resource = uart_resources,
    .num_resources = ARRAY_SIZE(uart_resources),
};

static int __init demo_init(void)
{
    return platform_device_register(&uart_device);
}

static void __exit demo_exit(void)
{
    platform_device_unregister(&uart_device);
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Example Platform Device Registration");

Code Explanation

  1. struct resource describes the memory and interrupt resources.
  2. IORESOURCE_MEM identifies the memory range.
  3. IORESOURCE_IRQ identifies the interrupt resource.
  4. uart_resources contains two resource entries.
  5. platform_device describes the device.
  6. platform_device_register() registers the device with the platform bus.
  7. platform_device_unregister() unregisters it during module cleanup.
Safety and integration note: This is a structural example, not a ready-to-load driver for arbitrary hardware. The address and interrupt are illustrative. Do not register a device over resources already owned by real hardware or another driver. On modern Device Tree or ACPI systems, hardware devices are normally instantiated through firmware rather than duplicated manually.

11. Platform Device Registration APIs

Linux provides multiple APIs for registering platform devices.

API Purpose
platform_device_register() Registers a prepared platform device.
platform_device_unregister() Unregisters a previously registered platform device.
platform_device_alloc() Allocates and initializes a platform device object.
platform_device_add() Adds an allocated platform device to the device model.
platform_device_put() Releases a reference to a platform device object.
platform_device_register_full() Registers a platform device using a structured set of registration information.

The appropriate API depends on how the platform device is constructed and managed.

12. Accessing Resources from a Platform Driver

When a platform driver is matched with a platform device, its probe callback receives a pointer to that device.

static int demo_probe(struct platform_device *pdev)
{
    struct resource *res;

    res = platform_get_resource(pdev, IORESOURCE_MEM, 0);

    if (!res)
        return -ENODEV;

    dev_info(&pdev->dev,
             "Memory resource available\n");

    return 0;
}

The function:

platform_get_resource(pdev, IORESOURCE_MEM, 0);

requests the first memory resource associated with the platform device.

The final argument is the resource index. If the requested resource is not available, the function returns NULL.

Mapping the Memory Resource

A driver commonly maps a memory resource using:

void __iomem *base;

base = devm_platform_ioremap_resource(pdev, 0);

if (IS_ERR(base))
    return PTR_ERR(base);

This API obtains and maps the selected memory resource. The mapping is managed by the device resource-management system and is released automatically when the device is detached, subject to normal managed-resource lifetime rules.

13. Platform Device and Device Tree

In modern embedded Linux systems, platform devices are frequently created from Device Tree descriptions.

For example:

uart0: serial@40000000 {
    compatible = "vendor,soc-uart";
    reg = <0x40000000 0x1000>;
    interrupts = <5>;
    status = "okay";
};

The Device Tree subsystem processes the hardware description and creates the corresponding device-model objects when appropriate.

The platform driver can then match the device using the compatible string and receive the resulting platform-device pointer in its probe callback.

The exact resources exposed to the driver depend on the SoC binding, interrupt-controller configuration, address translation and kernel firmware-enumeration code.

14. Platform Device Lifecycle

A platform device follows a lifecycle managed by the Linux device model.

Hardware Description Available
↓
Platform Device Object Prepared
↓
Device Registered
↓
Platform Bus Matching
↓
Driver Probe
↓
Device Operational
↓
Device Unregistered or Detached

The device may be created before or after its driver is registered. The driver core attempts matching as devices and drivers become available.

15. Inspecting Platform Devices in Ubuntu

Use the following commands to inspect the platform device model.

List Platform Devices

ls -l /sys/bus/platform/devices

Inspect a Device Directory

ls -l /sys/bus/platform/devices/DEVICE_NAME

Replace DEVICE_NAME with an existing entry.

Inspect Device Attributes

find /sys/bus/platform/devices -maxdepth 2 -type f

Check Driver Binding

readlink /sys/bus/platform/devices/DEVICE_NAME/driver

Search Kernel Messages

dmesg | grep -i platform

Some platform devices in a virtual machine may represent virtual or system-level components rather than physical SoC peripherals.

16. Common Mistakes

  • Assuming struct platform_device contains the hardware driver implementation.
  • Confusing the embedded struct device with the entire platform device structure.
  • Assuming every platform device is manually registered by a driver developer.
  • Using physical addresses directly without proper resource mapping.
  • Assuming resource index zero always represents a memory resource.
  • Ignoring the difference between resource information and the mapped I/O address.
  • Registering duplicate devices for hardware already described by firmware.
  • Using illustrative resource addresses on real hardware without checking its documentation.
