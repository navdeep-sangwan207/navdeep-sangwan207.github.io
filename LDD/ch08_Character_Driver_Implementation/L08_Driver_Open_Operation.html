Chapter 8: Character Driver Implementation

Home Course Chapter 8
Lesson 8: Driver Open Operation
Level: Intermediate
Prerequisites: struct cdev, cdev_init(), cdev_add() and struct file_operations.
Objective: Understand how the Linux kernel invokes a driver's open callback when a user-space application opens a character-device file.

1. Introduction

In Linux, applications access many devices through files located in the /dev directory.

For example, an application may open a character device using: 

int fd = open("/dev/mydevice", O_RDWR);

When the application opens the device, the kernel performs the necessary file-system and device-driver operations.

If the device is associated with a character driver, the driver's .open callback can be invoked.

This callback allows the driver to prepare the device for use by the application.

2. What Is the Driver Open Operation?

The driver open operation is a callback function registered through the .open member of struct file_operations.

It is generally responsible for preparing an open file instance. Depending on the driver, it may:

  • Check whether the device is available.
  • Validate access conditions.
  • Initialize per-open data.
  • Allocate resources required for the open instance.
  • Store private data in the file structure.
  • Return an error if the device cannot be opened.

Basic Syntax

static int my_open(struct inode *inode,
                   struct file *file)
{
    /* Device initialization or validation */

    return 0;
}

A successful open callback normally returns 0. A failure is represented by a negative kernel error code.

3. Open Callback Function Parameters

The open callback receives two important parameters.

Parameter Description
struct inode *inode Represents the inode associated with the device file. It provides information about the file-system object.
struct file *file Represents the open file instance. It stores file-operation state, flags, position and private data.

Function Prototype

int (*open)(struct inode *inode,
            struct file *file);
The callback signature must match the target kernel's struct file_operations definition. Do not replace it with a user-space function signature.

4. How the Open Operation Works

The following diagram shows the simplified path from a user-space open() request to the driver callback.

5. Registering the Open Callback

The driver's open callback is associated with the file_operations structure. 

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("Device opened successfully\n");
    return 0;
}

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
};

The operations structure is then associated with the character device: 

cdev_init(&my_cdev, &my_fops);

my_cdev.owner = THIS_MODULE;

ret = cdev_add(&my_cdev, dev, 1);

Once the cdev is registered and a usable device node is available, applications can attempt to open the device.

6. Accessing Device Information Through inode

The inode parameter can provide access to the device's major and minor numbers.

A common example is: 

unsigned int major_number;
unsigned int minor_number;

major_number = imajor(inode);
minor_number = iminor(inode);

pr_info("Major: %u Minor: %u\n",
        major_number,
        minor_number);

The imajor() and iminor() helper functions extract the device numbers from the inode.

The driver can use this information when it manages multiple minor numbers under a common major number.

7. Understanding struct file

The struct file structure represents an open file instance in the kernel.

Some important concepts include:

Member Purpose
f_op Points to the file-operation methods associated with the open file.
f_flags Contains file status and access flags.
f_pos Represents the current file position.
private_data Driver-usable pointer for storing per-open private state.
This is a conceptual list of useful members, not a recommendation to manipulate internal file-structure fields directly. Use the appropriate kernel APIs and respect the target kernel version.

8. Using file->private_data

The private_data member is commonly used by drivers to associate private information with an individual open file instance.

For example, a driver may allocate a structure for each open operation.

Example Data Structure

struct device_private {
    int open_count;
    int device_id;
};

Allocate Private Data in Open

#include <linux/slab.h>

static int my_open(struct inode *inode,
                   struct file *file)
{
    struct device_private *data;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->open_count = 1;
    data->device_id = iminor(inode);

    file->private_data = data;

    pr_info("Device opened: minor=%d\n",
            data->device_id);

    return 0;
}

Here:

  • kzalloc() allocates zero-initialized kernel memory.
  • GFP_KERNEL specifies a normal kernel allocation context.
  • file->private_data stores the allocated structure pointer.
  • iminor(inode) obtains the minor number.
If private data is allocated during open(), the driver must release it when the corresponding open-file instance is finally released.

9. Handling Open Errors

The open callback should check conditions that could prevent successful device access.

Error Code Meaning
-ENOMEM Insufficient memory for required allocation.
-EBUSY Device or resource is already busy.
-ENODEV Device is unavailable or no longer present.
-EINVAL Invalid argument or unsupported condition.
-EACCES Access is not permitted.

Example: Rejecting a Second Open

A simple exclusive-open policy can use an atomic variable. 

#include <linux/atomic.h>
#include <linux/errno.h>

static atomic_t device_opened = ATOMIC_INIT(0);

static int my_open(struct inode *inode,
                   struct file *file)
{
    if (atomic_cmpxchg(&device_opened, 0, 1))
        return -EBUSY;

    pr_info("Exclusive device open successful\n");

    return 0;
}

The atomic compare-and-exchange operation ensures that only one caller can change the state from zero to one successfully.

The driver must reset the state when the open instance is released. Otherwise, future opens will continue to fail.

This is a simplified single-device example. For multiple devices, per-device state should be used. Drivers must also ensure that open and release state is correctly synchronized with device removal.

10. Open Flags and Access Modes

User-space applications can specify access modes when opening a device.

Flag Meaning
O_RDONLY Open for reading only.
O_WRONLY Open for writing only.
O_RDWR Open for reading and writing.
O_NONBLOCK Request nonblocking behavior where supported.
O_APPEND Request append behavior for supported file operations.

A driver can inspect file->f_flags to determine relevant open flags. 

if (file->f_flags & O_NONBLOCK) {
    pr_info("Nonblocking mode requested\n");
}

The access mode can be checked using the kernel's file->f_mode flags, such as FMODE_READ and FMODE_WRITE, where appropriate.

11. Complete Practical Example

This example registers a character device and implements an open callback that allocates private data for each open-file instance. The release callback frees it.

File: driver_open_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/init.h>
#include <linux/slab.h>

#define DEVICE_NAME "driver_open_demo"

struct device_private {
    unsigned int minor_number;
};

static dev_t dev;
static struct cdev my_cdev;

static int demo_open(struct inode *inode,
                     struct file *file)
{
    struct device_private *data;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->minor_number = iminor(inode);

    file->private_data = data;

    pr_info("Device opened: minor=%u\n",
            data->minor_number);

    return 0;
}

static int demo_release(struct inode *inode,
                        struct file *file)
{
    struct device_private *data;

    data = file->private_data;

    kfree(data);
    file->private_data = NULL;

    pr_info("Device released\n");

    return 0;
}

static const struct file_operations demo_fops = {
    .owner = THIS_MODULE,
    .open = demo_open,
    .release = demo_release,
};

static int __init demo_init(void)
{
    int ret;

    ret = alloc_chrdev_region(
        &dev,
        0,
        1,
        DEVICE_NAME
    );

    if (ret < 0) {
        pr_err("Device number allocation failed\n");
        return ret;
    }

    cdev_init(&my_cdev, &demo_fops);
    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev, 1);

    if (ret < 0) {
        pr_err("cdev_add failed: %d\n", ret);
        unregister_chrdev_region(dev, 1);
        return ret;
    }

    pr_info("Driver registered\n");
    pr_info("Major: %u Minor: %u\n",
            MAJOR(dev), MINOR(dev));

    return 0;
}

static void __exit demo_exit(void)
{
    cdev_del(&my_cdev);
    unregister_chrdev_region(dev, 1);

    pr_info("Driver unregistered\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Character Driver Open Operation Demo");

Program Explanation

  1. The module allocates one device number.
  2. The file_operations structure registers the open and release callbacks.
  3. The open callback allocates private data using kzalloc().
  4. The minor number is stored in the private structure.
  5. The structure pointer is assigned to file->private_data.
  6. The release callback retrieves and frees the private data.
  7. The module exit function unregisters the character device.
This example demonstrates kernel-side registration and callback implementation. It does not create a /dev node. Also, do not unload the module while device instances are still in use. A production driver needs suitable device-node management and careful synchronization of device removal with open instances.

14. Common Mistakes

Mistake Correct Approach
Using the wrong callback parameters Use the inode and file parameters required by the kernel API.
Returning a positive value for ordinary success Normally return zero on successful open.
Forgetting to check kzalloc() Check for NULL and return -ENOMEM.
Allocating private data but never freeing it Release per-open allocations in the release callback.
Assuming open creates a device node Device-node creation is a separate device-management step.
Using an unsynchronized open counter Use appropriate atomic or locking mechanisms for shared state.
Ignoring device removal and active opens Manage device and resource lifetimes carefully.

15. Summary

  • The open callback is registered through the .open member of file_operations.
  • It is invoked when a device file is opened through the VFS.
  • The callback receives struct inode and struct file pointers.
  • It normally returns zero on success or a negative error code on failure.
  • The inode can provide major and minor device numbers.
  • file->private_data can store per-open driver information.
  • Resources allocated during open must be released appropriately.
  • Open-state management may require atomic operations or locks.
