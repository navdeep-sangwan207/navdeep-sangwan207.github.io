Chapter 8: Character Driver Implementation

Home Course Chapter 8
Lesson 3: cdev_init() Function
Level: Intermediate
Prerequisites: struct cdev, file_operations, device numbers and character-device registration.
Objective: Understand how cdev_init() initializes a character-device object and associates it with file-operation callbacks.

1. Introduction

The Linux kernel provides the cdev_init() function to initialize a character-device object.

A character driver uses struct cdev to represent its registered character-device interface inside the kernel.

Before a cdev can be registered using cdev_add(), it must first be initialized and associated with the appropriate file_operations structure.

This association is performed by cdev_init().

2. What Is cdev_init()?

cdev_init() is a Linux kernel helper function used to initialize a character-device structure.

It prepares the cdev object for registration and associates it with the driver's file operations.

Header file:

#include <linux/cdev.h>

Function prototype:

void cdev_init(
    struct cdev *cdev,
    const struct file_operations *fops
);

Important Characteristics

  • It initializes a character-device object.
  • It associates the cdev with file operations.
  • It does not allocate a device number.
  • It does not register the cdev with the kernel.
  • It does not create a device node.
  • It does not return an error code because its return type is void.

3. Function Parameters

Parameter Meaning
cdev Pointer to the character-device structure that must be initialized.
fops Pointer to the file_operations structure containing driver callbacks.

Example

static struct cdev my_cdev;

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
};

cdev_init(&my_cdev, &my_fops);

Here:

  • my_cdev is the character-device object.
  • my_fops contains the supported file operations.
  • cdev_init() associates the two.

4. Understanding struct cdev

The struct cdev type is defined by the Linux kernel's character-device infrastructure.

It represents a character device and provides the association between device numbers and file operations.

Conceptually, its internal structure contains members such as: 

struct cdev {
    struct kobject kobj;
    struct module *owner;
    const struct file_operations *ops;
    struct list_head list;
    dev_t dev;
    unsigned int count;
};
This is a simplified conceptual representation. Internal members and implementation details can vary across kernel versions. Driver developers should use the kernel's cdev helper functions rather than directly manipulating internal fields.

Declaring a cdev Object

static struct cdev my_cdev;

This declares a cdev object with static storage duration.

5. Understanding file_operations

The file_operations structure contains function pointers that define the operations supported by a driver.

Header file:

#include <linux/fs.h>

Example

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
    .release = my_release,
};

Important Members

Member Purpose
.owner Associates the operations with the owning module.
.open Called when the device file is opened.
.release Called when the opened file is released.
.read Handles read operations when implemented.
.write Handles write operations when implemented.
.unlocked_ioctl Handles supported device-control requests.

The driver only needs to implement callbacks that it actually supports.

6. How cdev_init() Works

The following diagram illustrates the relationship between the cdev object and file operations.

struct file_operations
↓
my_fops
↓
cdev_init(&my_cdev, &my_fops)
↓
Initialized struct cdev
↓
cdev_add()
↓
Registered Character Device

The important point is that cdev_init() performs initialization, while cdev_add() performs registration.

7. Step-by-Step Use of cdev_init()

Step 1: Include Header Files

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>

Step 2: Declare the cdev Object

static struct cdev my_cdev;

Step 3: Define File Operations

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
};

Step 4: Initialize the cdev

cdev_init(&my_cdev, &my_fops);

Step 5: Set the Module Owner

my_cdev.owner = THIS_MODULE;

Step 6: Register the cdev

ret = cdev_add(&my_cdev, dev, 1);
The cdev must be fully initialized before cdev_add() is called. Once registration succeeds, the driver should be ready to receive operations.

8. Difference Between cdev_init() and cdev_add()

Feature cdev_init() cdev_add()
Purpose Initializes the cdev object. Registers the cdev with the kernel.
Associates file operations Yes Uses the operations already associated with the cdev.
Uses device number No Yes
Return type void int
Can report registration failure No return value Yes, through a negative error code.

Example sequence: 

cdev_init(&my_cdev, &my_fops);

my_cdev.owner = THIS_MODULE;

ret = cdev_add(&my_cdev, dev, 1);

9. Complete Practical Example

This kernel module demonstrates device-number allocation, cdev initialization and registration.

File: cdev_init_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/init.h>

#define DEVICE_NAME "cdev_init_demo"

static dev_t dev;
static struct cdev my_cdev;

static int demo_open(struct inode *inode,
                     struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

static int demo_release(struct inode *inode,
                        struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

static const struct file_operations demo_fops = {
    .owner = THIS_MODULE,
    .open = demo_open,
    .release = demo_release,
};

static int __init demo_init(void)
{
    int ret;

    ret = alloc_chrdev_region(
        &dev,
        0,
        1,
        DEVICE_NAME
    );

    if (ret < 0) {
        pr_err("Device number allocation failed\n");
        return ret;
    }

    pr_info("Major: %u Minor: %u\n",
            MAJOR(dev), MINOR(dev));

    cdev_init(&my_cdev, &demo_fops);

    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev, 1);

    if (ret < 0) {
        pr_err("cdev_add failed\n");
        unregister_chrdev_region(dev, 1);
        return ret;
    }

    pr_info("cdev_init completed\n");
    pr_info("Character device registered\n");

    return 0;
}

static void __exit demo_exit(void)
{
    cdev_del(&my_cdev);

    unregister_chrdev_region(dev, 1);

    pr_info("Character device removed\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("cdev_init Function Demonstration");

Program Explanation

  1. Declare a device number and cdev object.
  2. Define the driver's open and release callbacks.
  3. Create the file_operations structure.
  4. Allocate one device number dynamically.
  5. Initialize the cdev using cdev_init().
  6. Set the module owner.
  7. Register the cdev using cdev_add().
  8. Remove the cdev and release the number during cleanup.
This example registers a cdev but does not create a /dev node. The open and release callbacks can be exercised only after an appropriate device node or device-model interface is created.

12. Common Mistakes

Mistake Correct Approach
Using an undeclared cdev object Declare a valid struct cdev object first.
Passing an invalid fops pointer Provide a valid file_operations structure.
Calling cdev_add() before initialization Call cdev_init() first.
Assuming cdev_init() registers the device Call cdev_add() separately.
Assuming cdev_init() allocates device numbers Use alloc_chrdev_region() or register_chrdev_region().
Forgetting cdev_del() Remove the registered cdev during cleanup.
Releasing device numbers too early Remove the cdev before releasing its number range.

13. Summary

  • cdev_init() initializes a character-device object.
  • It associates a cdev with a file_operations structure.
  • Its return type is void.
  • It does not allocate device numbers.
  • It does not register the cdev.
  • cdev_add() registers the initialized cdev.
  • cdev_del() removes the registered cdev.
  • Device-node creation is a separate operation.
