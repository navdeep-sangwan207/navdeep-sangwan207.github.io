Lesson 5: cdev_del() Function
Level: Intermediate
Prerequisites: struct cdev, cdev_init(), cdev_add() and device-number allocation.
Objective: Understand how to remove a registered character-device object safely.

1. Introduction

In Linux character-device driver development, a driver must manage both registration and removal of its character-device interface.

The cdev_add() function registers a character-device object with the kernel.

When the driver is unloaded or the device is being removed, cdev_del() is used to remove that registration.

It is an important part of character driver cleanup.

2. What Is cdev_del()?

cdev_del() is a Linux kernel helper function that removes a previously registered character device from the kernel's character- device infrastructure.

Header file:

#include <linux/cdev.h>

Function prototype:

void cdev_del(struct cdev *p);

Important Characteristics

  • Removes the cdev registration.
  • Prevents new opens through that registration.
  • Does not release the allocated device-number range.
  • Does not automatically delete a device-model object created with device_create().
  • Does not automatically terminate existing open file descriptors.
  • Has a void return type.
cdev_del() is not a complete device-driver cleanup function. Other resources, such as device numbers, device-model objects, buffers and allocated memory, must be released separately.

3. Function Parameter

Parameter Description
p Pointer to the character-device object that was previously registered.

Example

cdev_del(&my_cdev);

Here, my_cdev is the character-device object that was previously registered using cdev_add().

4. Character Device Lifecycle

A character-device object normally passes through the following stages.

Declare struct cdev
↓
Allocate Device Number
alloc_chrdev_region()
↓
Initialize cdev
cdev_init()
↓
Register cdev
cdev_add()
↓
Character Device Available
↓
Remove Registration
cdev_del()
↓
Release Device Number
unregister_chrdev_region()

This lifecycle shows that initialization, registration, removal and device-number release are separate operations.

5. Why Is cdev_del() Required?

When a kernel module is unloaded, its registered character-device interface must no longer accept new opens through that registration.

If the cdev registration is left behind while its associated driver resources are released, the kernel could encounter invalid references or unsafe access.

Main Reasons

  • Remove the character-device registration.
  • Prevent new opens through the removed registration.
  • Support orderly driver shutdown.
  • Allow the device-number range to be released afterward.
  • Help prevent stale device registrations.

6. cdev_del() Does Not Close Existing File Descriptors

One of the most important concepts in character-device programming is the difference between preventing new opens and handling existing open files.

Calling cdev_del() prevents new opens through that cdev registration. It does not automatically close file descriptors that were already opened.

Example Scenario

User Process A opens /dev/mydevice
↓
Driver open callback executes
↓
Driver calls cdev_del()
↓
New opens through this registration are prevented
↓
Existing file descriptor still requires safe lifetime management
A driver must not free memory or other resources still being used by existing file operations. Safe teardown may require reference counting, synchronization, active-user tracking and suitable object-lifetime management.

7. Difference Between cdev_del() and unregister_chrdev_region()

These two functions are often used together, but they perform different tasks.

Feature cdev_del() unregister_chrdev_region()
Purpose Removes the cdev registration. Releases a reserved device-number range.
Parameter Pointer to struct cdev. Starting dev_t and count.
Return type void void
Removes cdev registration Yes No
Releases device numbers No Yes

Example

cdev_del(&my_cdev);

unregister_chrdev_region(dev, 1);

8. Complete Practical Example

This example demonstrates how a character-device registration is removed during module cleanup.

File: cdev_del_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/init.h>

#define DEVICE_NAME "cdev_del_demo"

static dev_t dev;
static struct cdev my_cdev;

static int demo_open(struct inode *inode,
                     struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

static int demo_release(struct inode *inode,
                        struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

static const struct file_operations demo_fops = {
    .owner = THIS_MODULE,
    .open = demo_open,
    .release = demo_release,
};

static int __init demo_init(void)
{
    int ret;

    ret = alloc_chrdev_region(
        &dev,
        0,
        1,
        DEVICE_NAME
    );

    if (ret < 0) {
        pr_err("Device number allocation failed\n");
        return ret;
    }

    cdev_init(&my_cdev, &demo_fops);

    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev, 1);

    if (ret < 0) {
        pr_err("cdev_add failed: %d\n", ret);
        unregister_chrdev_region(dev, 1);
        return ret;
    }

    pr_info("Character device registered\n");
    pr_info("Major: %u Minor: %u\n",
            MAJOR(dev), MINOR(dev));

    return 0;
}

static void __exit demo_exit(void)
{
    cdev_del(&my_cdev);

    pr_info("cdev registration removed\n");

    unregister_chrdev_region(dev, 1);

    pr_info("Device number range released\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("cdev_del Function Demonstration");

Program Explanation

  1. Allocate a device-number range.
  2. Initialize the cdev object.
  3. Associate file operations with the cdev.
  4. Register the cdev using cdev_add().
  5. When the module is unloaded, call cdev_del().
  6. Release the device-number range using unregister_chrdev_region().
The example uses a static cdev object and module reference management through file_operations.owner. In a production driver, additional lifetime handling may be needed for device state, asynchronous operations and resources used by open files.

11. Common Mistakes

Mistake Correct Approach
Calling cdev_del() before cdev_add() Remove only a cdev that was successfully registered.
Assuming cdev_del() releases device numbers Call unregister_chrdev_region() separately.
Freeing active driver resources immediately Ensure existing users and operations no longer reference those resources.
Assuming existing file descriptors are automatically closed Manage existing open files and object lifetimes explicitly.
Releasing device numbers before removing cdev Remove the cdev registration first.
Assuming cdev_del() deletes /dev nodes Remove device-model objects separately when they were created.

12. Summary

  • cdev_del() removes a registered character-device object.
  • It accepts a pointer to struct cdev.
  • Its return type is void.
  • It prevents new opens through that registration.
  • It does not automatically close existing file descriptors.
  • It does not release device-number ranges.
  • unregister_chrdev_region() releases device numbers.
  • Safe driver cleanup requires proper resource-lifetime management.
