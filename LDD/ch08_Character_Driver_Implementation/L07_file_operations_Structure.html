Home Course Chapter 8
Lesson 7: file_operations Structure
Level: Intermediate
Prerequisites: Character devices, struct cdev, cdev_init() and cdev_add().
Objective: Understand how Linux connects system calls from user space to driver callback functions through struct file_operations.

1. Introduction

A character-device driver provides an interface through which user-space applications can communicate with a device.

Applications use standard system calls and file operations such as open(), read(), write() and close().

The Linux kernel needs a mechanism to connect these operations to the corresponding functions implemented by a device driver.

Linux provides the struct file_operations structure for this purpose.

2. What Is struct file_operations?

struct file_operations is a kernel structure containing function pointers for operations that can be performed on an open file or device.

A character driver implements selected callback functions and assigns their addresses to the appropriate members of this structure.

Header file:

#include <linux/fs.h>

Basic Declaration

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
    .read = my_read,
    .write = my_write,
    .release = my_release,
};

Here, each designated initializer associates a file-operation member with a driver callback function.

A driver does not need to implement every available file operation. It implements only the operations required by its interface.

3. Why Is file_operations Required?

Consider a user-space program that opens a device file and writes data to it. 

int fd = open("/dev/mydevice", O_RDWR);

write(fd, "Hello", 5);

close(fd);

The application uses standard system calls. It does not directly call the driver's internal functions.

The kernel uses the registered operation callbacks to dispatch these requests to the driver.

Main Responsibilities

  • Connect file operations to driver callbacks.
  • Provide an interface between user space and kernel space.
  • Define supported operations for a device.
  • Allow different drivers to implement different behavior.
  • Support standard file-related operations on device files.

4. Relationship Between cdev and file_operations

The cdev object represents a registered character device. Its associated file_operations structure describes the callbacks used to handle file operations.

User-Space Application
open(), read(), write(), close()
↓
Linux Kernel VFS
Virtual File System
↓
Character Device Infrastructure
struct cdev
↓
struct file_operations
Function Pointers
↓
Driver Callback Functions
my_open(), my_read(), my_write()
↓
Device or Driver Data

During cdev initialization, the driver associates its operations structure with the cdev: 

cdev_init(&my_cdev, &my_fops);

The cdev is then registered using: 

cdev_add(&my_cdev, dev, 1);

5. Important Members of file_operations

The Linux kernel provides many possible file-operation callbacks. The following are commonly used in character-device drivers.

Member Purpose
.owner Associates operations with the owning kernel module for reference management.
.open Handles opening a device file.
.read Handles reading data from a device.
.write Handles writing data to a device.
.release Handles release of an open file after its final reference is closed.
.llseek Handles changes to the file position.
.unlocked_ioctl Handles device-specific control commands.
.poll Supports readiness notification and polling.
.mmap Supports mapping device or driver memory into a user process.
.flush Handles a file flush request when supported by the driver.
The complete structure contains additional members. Available members and callback signatures can vary between kernel versions. Always consult the headers for the target kernel.

6. Understanding the .owner Member

A common initialization is: 

.owner = THIS_MODULE,

THIS_MODULE represents the current loadable kernel module.

Setting the owner helps the kernel manage the module reference associated with open file operations. This helps prevent normal module unloading while the module is in use.

For ordinary loadable character-device modules, setting .owner = THIS_MODULE is a standard and important practice.

7. Understanding the .open Member

The .open member points to a callback that the kernel invokes when a device file is opened. 

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

A successful open callback normally returns zero. If opening fails, it returns a negative error code.

The callback can also initialize per-open state and store a pointer in file->private_data.

8. Understanding the .read Member

The .read member points to the callback used when an application reads from a device file. 

static ssize_t my_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
)
{
    pr_info("Read operation requested\n");
    return 0;
}

Important parameters:

Parameter Description
file Represents the open file instance.
buffer User-space destination buffer.
count Maximum number of bytes requested.
position Pointer to the file position.

A real read implementation generally transfers data to user space using copy_to_user().

Returning zero from a read callback normally indicates end-of-file. It is not a demonstration of a successful transfer of data.

9. Understanding the .write Member

The .write member points to the callback used when an application writes data to a device. 

static ssize_t my_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
)
{
    pr_info("Write operation requested\n");
    return count;
}

Important parameters:

Parameter Description
file Represents the open file instance.
buffer User-space source buffer.
count Number of bytes requested for writing.
position Pointer to the file position.

A real write implementation generally transfers data from user space using copy_from_user().

The example above is only a callback demonstration. It reports the requested byte count without actually copying or storing the user data. A production implementation must return the number of bytes actually processed or a suitable error.

10. Understanding the .release Member

The .release member points to the callback invoked when an open file's final reference is released. 

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

This callback can release resources allocated specifically for an open file instance.

It is important to understand that release is not necessarily invoked once for every individual close() call if the file description has been duplicated or shared.

11. Declaring a file_operations Structure

A driver typically defines its operations structure using designated initializers. 

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

This structure is commonly declared as static const because the driver does not need to modify its callback table after initialization.

Why Use Designated Initializers?

  • They make callback assignments clear.
  • They avoid depending on structure-member order.
  • They allow unused members to remain zero-initialized.
  • They make code easier to maintain.

12. Complete Practical Example

The following module demonstrates a character-device driver with open, read, write and release callbacks.

File: file_operations_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/init.h>

#define DEVICE_NAME "file_operations_demo"

static dev_t dev;
static struct cdev my_cdev;

static int demo_open(struct inode *inode,
                     struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

static ssize_t demo_read(
    struct file *file,
    char __user *buffer,
    size_t count,
    loff_t *position
)
{
    pr_info("Read callback invoked\n");

    /* No data is provided in this basic example. */
    return 0;
}

static ssize_t demo_write(
    struct file *file,
    const char __user *buffer,
    size_t count,
    loff_t *position
)
{
    pr_info("Write callback invoked\n");

    /*
     * This is a callback demonstration only.
     * No user data is copied or stored.
     */
    return -EOPNOTSUPP;
}

static int demo_release(struct inode *inode,
                        struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

static const struct file_operations demo_fops = {
    .owner = THIS_MODULE,
    .open = demo_open,
    .read = demo_read,
    .write = demo_write,
    .release = demo_release,
};

static int __init demo_init(void)
{
    int ret;

    ret = alloc_chrdev_region(
        &dev,
        0,
        1,
        DEVICE_NAME
    );

    if (ret < 0) {
        pr_err("Device number allocation failed\n");
        return ret;
    }

    cdev_init(&my_cdev, &demo_fops);
    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev, 1);

    if (ret < 0) {
        pr_err("cdev_add failed: %d\n", ret);
        unregister_chrdev_region(dev, 1);
        return ret;
    }

    pr_info("Device registered\n");
    pr_info("Major: %u Minor: %u\n",
            MAJOR(dev), MINOR(dev));

    return 0;
}

static void __exit demo_exit(void)
{
    cdev_del(&my_cdev);
    unregister_chrdev_region(dev, 1);

    pr_info("Device unregistered\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("file_operations Structure Demonstration");

Program Explanation

  1. alloc_chrdev_region() allocates a device-number range.
  2. demo_fops defines the driver's supported file operations.
  3. cdev_init() associates the operations structure with the cdev.
  4. cdev_add() registers the character device.
  5. The callbacks handle requests dispatched to the driver.
  6. Module cleanup removes the cdev and releases the device numbers.
This example does not create a /dev node. It demonstrates the callback structure and kernel-side registration. A device-model interface or a manually created device node is needed for ordinary user-space access.

15. Common Mistakes

Mistake Correct Approach
Using an incorrect callback signature Match the callback prototype in the target kernel headers.
Forgetting .owner Use .owner = THIS_MODULE for ordinary loadable modules.
Confusing read and write buffers read transfers data to user space; write receives data from user space.
Directly dereferencing a user pointer Use appropriate user-access functions such as copy_to_user() and copy_from_user().
Assuming all callbacks are mandatory Implement only the operations required by the driver.
Returning an incorrect byte count Return the number of bytes actually transferred or a suitable error.

16. Summary

  • struct file_operations contains callback function pointers.
  • It is declared in linux/fs.h.
  • The driver associates it with a cdev using cdev_init().
  • .open handles opening a device file.
  • .read handles read requests.
  • .write handles write requests.
  • .release handles final release of an open file.
  • .owner = THIS_MODULE supports module reference management.
  • Callbacks execute in kernel space and must handle user-space pointers safely.
