Lesson 9: Driver Release Operation
Level: Intermediate
Prerequisites: struct file_operations, driver open operation and file->private_data.
Objective: Understand how the release callback handles cleanup when an open device-file instance is finally released.

1. Introduction

In the previous lesson, we studied the driver open operation. The open callback prepares a device for use by a user-space application.

After the application finishes using the device, it generally closes its file descriptor using: 

close(fd);

When the final reference to the corresponding open file description is released, the Linux kernel can invoke the driver's .release callback.

The release callback allows the driver to free resources associated with that open-file instance.

2. What Is the Release Operation?

The release operation is a callback registered through the .release member of struct file_operations.

Its responsibilities may include:

  • Freeing memory allocated during open().
  • Releasing per-open private data.
  • Updating device usage information.
  • Releasing resources reserved by the open instance.
  • Performing final per-file cleanup.

Basic Syntax

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("Device released\n");

    return 0;
}

The release callback normally returns zero. Its return value is generally not used by close() as a reliable way to report cleanup failure to the application.

3. Release Callback Function Parameters

Parameter Description
struct inode *inode Represents the inode associated with the device file.
struct file *file Represents the open file instance being released.

Function Prototype

int (*release)(struct inode *inode,
               struct file *file);

The driver uses the file parameter to access per-open information, including its private data pointer.

4. How the Release Operation Works

User-Space Application
close(fd)
↓
Linux Kernel VFS
File Reference Management
↓
Final Open-File Reference Released
↓
Driver .release Callback
my_release()
↓
Release Per-Open Resources
Free Memory / Update State
↓
Open-File Instance Cleanup

This is a simplified conceptual sequence. The kernel manages file references and may delay final release until all references to the open file description are gone.

5. Registering the Release Callback

The release callback is registered in the file_operations structure. 

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("Device opened\n");
    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("Device released\n");
    return 0;
}

static const struct file_operations my_fops = {
    .owner = THIS_MODULE,
    .open = my_open,
    .release = my_release,
};

The driver associates this structure with its character device through cdev_init(). 

cdev_init(&my_cdev, &my_fops);

6. Releasing file->private_data

A common use of the release callback is freeing memory allocated during the open operation.

Consider this private structure: 

struct device_private {
    unsigned int minor_number;
    int status;
};

Allocate Memory in Open

static int my_open(struct inode *inode,
                   struct file *file)
{
    struct device_private *data;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->minor_number = iminor(inode);
    data->status = 1;

    file->private_data = data;

    return 0;
}

Free Memory in Release

static int my_release(struct inode *inode,
                      struct file *file)
{
    struct device_private *data;

    data = file->private_data;

    kfree(data);
    file->private_data = NULL;

    pr_info("Private data released\n");

    return 0;
}

The release callback retrieves the allocated pointer, frees the memory and clears the private-data pointer.

A useful rule is: resources allocated specifically for an open-file instance should normally be released when that instance is finally released.

7. Difference Between close() and release()

These two terms are related but they are not the same operation.

close() .release Callback
User-space system call. Kernel-space driver callback.
Called by an application to close a file descriptor. Invoked when the open-file description is finally released.
Managed by the user-space application. Implemented by the device driver.
Returns a user-space result such as 0 or -1. Returns an integer kernel result.
Do not assume that every close() call immediately invokes the driver's release callback. Duplicated file descriptors and shared file descriptions can keep the same open instance alive.

8. Difference Between release() and flush()

Linux file_operations also provides a .flush callback. It is different from .release.

.flush .release
Can be called on close of a file descriptor. Called when the open-file description is finally released.
May be called multiple times for a shared open-file description as descriptors are closed. Normally called once for the final release of that open-file description.
Can be used for close-related checks or flushing. Commonly used for final per-open cleanup.
Optional callback. Optional callback.

A driver should not use flush() and release() interchangeably. Their invocation and responsibilities are different.

9. Managing Device Open Counts

Some character devices allow only one open instance at a time. The driver can maintain an open state to enforce this policy.

For a single device, an atomic variable can be used to prevent simultaneous successful opens.

Example

#include <linux/atomic.h>
#include <linux/errno.h>

static atomic_t device_opened = ATOMIC_INIT(0);

static int my_open(struct inode *inode,
                   struct file *file)
{
    if (atomic_cmpxchg(&device_opened, 0, 1))
        return -EBUSY;

    pr_info("Device opened\n");

    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    atomic_set(&device_opened, 0);

    pr_info("Device released\n");

    return 0;
}

The open callback changes the state from zero to one. If the device is already marked as open, the callback returns -EBUSY.

The release callback resets the state so that another application can open the device.

This simplified example is suitable for understanding the concept. A real driver must maintain per-device state and coordinate open operations, device removal and active users safely.

10. Handling Resources During Release

A driver may allocate different types of resources during open(). The release callback must handle the resources owned by that open instance.

Resource Typical Cleanup
Kernel memory allocated with kzalloc() kfree()
Memory allocated with kmalloc() kfree()
Per-open buffers Free the corresponding allocation.
Per-open state structures Release after the final user of the structure is finished.
Exclusive-open state Update the device's state using proper synchronization.

Some resources are shared across all open instances. Such resources must not be freed simply because one file descriptor is closed.

11. Complete Practical Example

This example registers a character device and implements both open and release callbacks. The open callback allocates per-open memory, and release frees it.

File: driver_release_demo.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/init.h>
#include <linux/slab.h>

#define DEVICE_NAME "driver_release_demo"

struct device_private {
    unsigned int minor_number;
    int status;
};

static dev_t dev;
static struct cdev my_cdev;

static int demo_open(struct inode *inode,
                     struct file *file)
{
    struct device_private *data;

    data = kzalloc(sizeof(*data), GFP_KERNEL);

    if (!data)
        return -ENOMEM;

    data->minor_number = iminor(inode);
    data->status = 1;

    file->private_data = data;

    pr_info("Device opened: minor=%u\n",
            data->minor_number);

    return 0;
}

static int demo_release(struct inode *inode,
                        struct file *file)
{
    struct device_private *data;

    data = file->private_data;

    if (data) {
        pr_info("Releasing private data\n");
        kfree(data);
        file->private_data = NULL;
    }

    pr_info("Device released\n");

    return 0;
}

static const struct file_operations demo_fops = {
    .owner = THIS_MODULE,
    .open = demo_open,
    .release = demo_release,
};

static int __init demo_init(void)
{
    int ret;

    ret = alloc_chrdev_region(
        &dev,
        0,
        1,
        DEVICE_NAME
    );

    if (ret < 0) {
        pr_err("Device number allocation failed\n");
        return ret;
    }

    cdev_init(&my_cdev, &demo_fops);
    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev, 1);

    if (ret < 0) {
        pr_err("cdev_add failed: %d\n", ret);
        unregister_chrdev_region(dev, 1);
        return ret;
    }

    pr_info("Driver registered\n");
    pr_info("Major: %u Minor: %u\n",
            MAJOR(dev), MINOR(dev));

    return 0;
}

static void __exit demo_exit(void)
{
    cdev_del(&my_cdev);
    unregister_chrdev_region(dev, 1);

    pr_info("Driver unregistered\n");
}

module_init(demo_init);
module_exit(demo_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Character Driver Release Operation Demo");

Program Explanation

  1. The module allocates a character-device number.
  2. The cdev is initialized with the file_operations structure.
  3. The open callback allocates a private data structure.
  4. The private data pointer is stored in file->private_data.
  5. When the open-file description is finally released, the release callback is invoked.
  6. The release callback frees the private data.
  7. The module cleanup removes the cdev registration and releases the device number.
This module does not create a /dev node. To exercise the callbacks, a device node associated with the allocated major and minor numbers must also be made available. Keep the module loaded while an open instance is active; do not remove the cdev or free device resources while callbacks or existing users can still access them.

14. Common Mistakes

Mistake Correct Approach
Freeing memory that was never allocated Check the private-data pointer before freeing it.
Forgetting to free per-open data Release owned memory in the release callback.
Confusing close() and release() Understand file-descriptor references and final open-file release.
Freeing shared device resources in release() Release only resources owned by that open instance.
Not resetting exclusive-open state Update state safely when the open instance is released.
Assuming release runs on every close() Account for duplicated and shared file descriptions.
Unloading while resources are still in use Coordinate device removal with active file instances and callbacks.

15. Summary

  • The release callback is registered through the .release member of file_operations.
  • It is called when the open-file description is finally released.
  • It receives inode and file pointers.
  • It is commonly used to free per-open resources.
  • file->private_data provides access to per-open driver state.
  • close() and .release are different operations.
  • .flush and .release also have different purposes.
  • Shared resources require proper lifetime management.
