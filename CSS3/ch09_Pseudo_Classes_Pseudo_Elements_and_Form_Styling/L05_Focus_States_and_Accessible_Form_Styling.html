Build keyboard-friendly interfaces with visible focus indicators and accessible form controls.

1. Learning Objectives

  • Understand keyboard focus and accessibility.
  • Differentiate :focus and :focus-visible.
  • Use :focus-within for parent containers.
  • Design visible focus indicators.

2. What Is Focus?

Focus identifies the element that currently receives keyboard input or other user interaction.

For example, when a user presses the Tab key, the browser typically moves focus to the next focusable element in the sequential focus order.

Common Focusable Elements

  • Text inputs.
  • Buttons.
  • Links with href attributes.
  • Select controls.
  • Textareas.
  • Elements made focusable using tabindex.

Why Focus Matters

  • Supports keyboard-only users.
  • Helps users identify their current position.
  • Improves form usability.
  • Supports users with motor impairments.
  • Improves overall interface accessibility.
Focus is not the same as hover. Hover generally represents pointer interaction, while focus identifies the element currently receiving keyboard or programmatic focus.

3. The :focus Pseudo-Class

The :focus pseudo-class selects an element when it has focus.

Syntax

selector:focus {
    property: value;
}

Example

input:focus {
    border-color: blue;
    outline: 2px solid lightblue;
}

HTML

<label for="username">Username</label>

<input
    type="text"
    id="username"
    placeholder="Enter username"
>

Live Demonstration

When the input receives focus, its focus styles are applied.

4. The :focus-visible Pseudo-Class

:focus-visible selects an element when the browser determines that a visible focus indicator should be presented.

It is particularly useful for keyboard navigation because it helps display focus indicators without necessarily showing the same indicator after every pointer interaction.

Syntax

button:focus-visible {
    outline: 3px solid blue;
    outline-offset: 3px;
}

Example

a:focus-visible,
button:focus-visible,
input:focus-visible {
    outline: 3px solid #174ea6;
    outline-offset: 3px;
}

Live Demonstration

Use the Tab key to navigate these controls.

Example Link

Important Difference

:focus :focus-visible
Selects an element whenever it has focus. Selects a focused element when the browser determines a visible indicator is appropriate.
May apply after pointer or keyboard interaction. Commonly displays an indicator for keyboard navigation.
Useful for general focus styling. Useful for keyboard-oriented focus indicators.
The browser decides when :focus-visible matches. Do not assume it is exclusively a keyboard selector.

5. The :focus-within Pseudo-Class

:focus-within selects an element when that element or one of its descendants has focus.

Syntax

parent:focus-within {
    property: value;
}

Example

.form-group:focus-within {
    background: #eef5ff;
    border: 1px solid blue;
}

HTML

<div class="form-group">
    <label for="email">Email</label>
    <input type="email" id="email">
</div>

Live Demonstration

When the input receives focus, the parent card changes its border and background.

Practical Applications

  • Highlighting an entire form group.
  • Highlighting search boxes.
  • Indicating active navigation components.
  • Improving the visibility of grouped controls.

6. Focus Indicators and Outline

A focus indicator visually communicates which element currently has keyboard focus.

Outline Property

button:focus-visible {
    outline: 3px solid blue;
    outline-offset: 3px;
}

Important Outline Properties

Property Purpose
outline-style Defines the outline style.
outline-width Defines outline thickness.
outline-color Defines outline color.
outline-offset Controls spacing between the border edge and outline.
outline Shorthand for outline width, style and color.

Outline vs Border

Border Outline
Part of the CSS box model. Does not occupy box-model layout space.
Can affect element dimensions under content-box sizing. Does not change layout dimensions.
Can be applied to create normal visual boundaries. Commonly used for focus indicators.
Never remove the browser's focus outline without providing a clearly visible replacement. Keyboard users need to know which control is active.

7. Keyboard Navigation

Keyboard navigation allows users to interact with an interface without using a mouse.

Key Common Function
Tab Moves focus forward through sequentially focusable elements.
Shift + Tab Moves focus backward.
Enter Activates links and commonly submits forms when appropriate.
Space Activates buttons and toggles checkboxes when focused.
Arrow Keys Navigate within controls such as radio groups and select menus, depending on control behavior.
Escape May close dialogs, menus or other dismissible interfaces when implemented.

Basic Keyboard Test

  1. Load the page.
  2. Press Tab.
  3. Observe the focused element.
  4. Continue pressing Tab.
  5. Use Shift + Tab to move backward.
  6. Activate links and buttons using the keyboard.
Native HTML controls provide built-in keyboard behavior. Custom widgets must implement appropriate keyboard interaction and focus management.

8. Understanding tabindex

The tabindex attribute controls whether an element can receive keyboard focus and how it participates in sequential keyboard navigation.

Value Behavior
tabindex="0" Makes an element sequentially focusable in the natural document order.
tabindex="-1" Allows programmatic focus but excludes the element from normal sequential Tab navigation.
Positive tabindex Places an element into a priority focus order before elements with tabindex="0". Generally avoid it.

Example

<div tabindex="0">
    Keyboard focusable element
</div>

<div tabindex="-1" id="message">
    Programmatically focusable element
</div>

JavaScript Example

const message = document.getElementById("message");

message.focus();
Avoid positive tabindex values because they can create confusing focus sequences that differ from the visual and document order. Prefer semantic interactive elements.

9. Accessible Form Labels

Every form control should have a clear, programmatically associated label.

Recommended HTML

<label for="email">
    Email Address
</label>

<input
    type="email"
    id="email"
    name="email"
    required
>

Why Labels Matter

  • Identify the purpose of a form field.
  • Provide an accessible name for the control.
  • Allow users to click the label to focus or activate its associated control.
  • Improve usability on touch devices.

Alternative: Wrapping Label

<label>
    Email Address
    <input type="email" name="email">
</label>
Use visible labels rather than relying only on placeholder text. A placeholder disappears when the user starts entering information.

10. Accessible Error Messages and Instructions

Users should receive clear instructions and error messages when a form field needs correction.

HTML Example

<label for="password">Password</label>

<input
    type="password"
    id="password"
    name="password"
    aria-describedby="password-help"
    required
>

<small id="password-help">
    Use at least 8 characters.
</small>

Important Attributes

Attribute Purpose
aria-describedby Associates descriptive instructions or messages with a control.
aria-invalid Indicates that a control's value is invalid.
aria-required Communicates required status to assistive technology when needed, especially in custom widgets.
required Native HTML constraint that marks a supported control as mandatory.

CSS Error Styling

input[aria-invalid="true"] {
    border: 2px solid #c62828;
}

.error-message {
    color: #c62828;
    font-size: 14px;
}
Do not add aria-invalid="true" automatically to every empty required field before validation. Set it when the application has determined that the field is invalid, and provide a clear explanation.

11. Accessible Form Styling

An accessible form should have visible labels, readable text, sufficient contrast, clear instructions and visible focus indicators.

Recommended CSS

form {
    max-width: 500px;
}

label {
    display: block;
    margin-bottom: 6px;
    font-weight: bold;
}

input,
select,
textarea {
    width: 100%;
    padding: 11px;
    border: 1px solid #777;
    border-radius: 5px;
    font: inherit;
}

input:focus-visible,
select:focus-visible,
textarea:focus-visible,
button:focus-visible {
    outline: 3px solid #174ea6;
    outline-offset: 3px;
}

button {
    padding: 11px 18px;
    cursor: pointer;
}

Accessibility Checklist

  • Provide visible labels.
  • Use appropriate input types.
  • Identify required fields.
  • Provide clear instructions.
  • Make keyboard focus visible.
  • Use sufficient color contrast.
  • Provide understandable error messages.
  • Ensure controls have usable sizes and spacing.
  • Do not communicate errors using color alone.

Build a registration form with associated labels, keyboard focus indicators, instructions and accessible error styling.

                    <option value="css">CSS3</option>
                    <option value="html">HTML5</option>

Expected Result

  • A centered registration form.
  • Clearly associated labels.
  • Parent form groups highlighted when their controls receive focus.
  • Visible keyboard focus indicators.
  • Native required-field and email validation.
  • Password minimum length validation.
  • Readable instructions associated with the relevant fields.
This project demonstrates frontend form design, not account creation. A production registration system requires secure backend processing, server-side validation, password hashing and appropriate error handling.

13. Common Accessibility Mistakes

Mistake Better Practice
Removing outline without replacement. Provide a visible focus indicator.
Using placeholder as the only label. Provide a visible label associated with the input.
Using positive tabindex values. Use natural document order and tabindex="0" or "-1" only when appropriate.
Using color alone to communicate errors. Provide text messages and appropriate programmatic state.
Creating clickable div elements without keyboard support. Use native buttons and links whenever possible.
Creating an unpredictable focus order. Keep DOM order aligned with the intended interaction order.
Making focus indicators too subtle. Use sufficiently visible indicators with adequate contrast.
Removing focus from controls without a clear reason. Preserve logical focus behavior and manage focus deliberately.

14. Testing Accessibility with Developer Tools

Manual Keyboard Testing

  1. Open the page in a browser.
  2. Do not use the mouse.
  3. Press Tab repeatedly.
  4. Check whether focus is always visible.
  5. Press Shift + Tab to move backward.
  6. Use Enter and Space to activate controls.
  7. Check whether the focus order follows the logical page order.

Browser Developer Tools

  • Inspect computed styles for focus indicators.
  • Check matched :focus and :focus-visible rules.
  • Inspect label associations and form attributes.
  • Check for elements with positive tabindex.
  • Test at different zoom levels and viewport sizes.
Automated accessibility tools are useful, but they cannot replace manual keyboard testing and assistive-technology testing.

15. Placement Interview Questions

Q1. What is focus in CSS?

Answer: Focus represents the state of an element that currently receives keyboard or programmatic focus.

Q2. What is :focus?

Answer: It selects an element whenever that element has focus.

Q3. What is :focus-visible?

Answer: It selects a focused element when the browser determines that a visible focus indicator is appropriate.

Q4. What is :focus-within?

Answer: It selects an element when the element itself or one of its descendants has focus.

Q5. What is the difference between :focus and :focus-visible?

Answer: :focus matches every focused element, while :focus-visible uses browser heuristics to determine when a visible focus indicator should be shown.

Q6. Why are focus indicators important?

Answer: They help keyboard users identify the currently focused control.

Q7. What is outline-offset?

Answer: It controls the distance between an element's outline and its border edge.

Q8. Does outline occupy layout space?

Answer: No. Outline does not occupy space in the CSS box model.

Q9. What is tabindex="0"?

Answer: It makes an element focusable through normal sequential keyboard navigation in document order.

Q10. What is tabindex="-1"?

Answer: It allows programmatic focus but removes the element from normal sequential Tab navigation.

Q11. Why should positive tabindex values generally be avoided?

Answer: They can create confusing keyboard navigation sequences that do not follow the natural document order.

Q12. Why should every form input have a label?

Answer: A label identifies the purpose of the input and provides an accessible name for assistive technology.

Q13. What is aria-describedby?

Answer: It associates an element with additional descriptive text, such as instructions or error messages.

Q14. What is aria-invalid?

Answer: It communicates that a form control's value is invalid.

Q15. Should a developer remove the default browser outline?

Answer: Not without providing an equally visible or better focus indicator.

Q16. What is keyboard accessibility?

Answer: It means users can operate the interface using a keyboard without depending on pointer input.

17. Lecture Summary

  • :focus selects focused elements.
  • :focus-visible provides browser-determined visible focus styling.
  • :focus-within selects parents containing a focused element.
  • Outline is useful for visible focus indicators.
  • Outline does not occupy box-model layout space.
  • tabindex controls focusability and sequential navigation.
  • Visible labels are essential for form usability.
  • aria-describedby associates instructions and descriptions.
  • aria-invalid communicates invalid state.
  • Manual keyboard testing is essential.
