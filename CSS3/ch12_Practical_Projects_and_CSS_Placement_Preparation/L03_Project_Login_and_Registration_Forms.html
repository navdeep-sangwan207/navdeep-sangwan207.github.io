Lecture 3: Project – Login and Registration Forms

Build responsive authentication form interfaces using semantic HTML, CSS Grid, Flexbox, form controls, validation states and accessible styling.

1. Project Objectives

Login and registration forms are common components in web applications. They are frequently included in frontend development assignments because they test HTML form knowledge, CSS layout skills, responsive design and accessibility.

  • Create a semantic login form.
  • Create a registration form.
  • Use appropriate HTML input types.
  • Associate labels with form controls.
  • Apply built-in HTML constraint validation.
  • Style focus, valid and invalid states.
  • Use Grid and Flexbox for responsive layouts.
  • Understand the difference between frontend validation and server-side validation.

4. Step 1 – Understand HTML Form Elements

<form action="/login" method="post">

    <label for="email">Email Address</label>

    <input
        type="email"
        id="email"
        name="email"
        required
    >

    <label for="password">Password</label>

    <input
        type="password"
        id="password"
        name="password"
        required
    >

    <button type="submit">Sign In</button>

</form>

Important form elements

Element Purpose
form Groups controls for data submission.
label Provides an accessible name for a form control.
input Accepts user input.
button Provides an action such as submitting a form.
select Provides a selection control.
textarea Accepts multi-line text.

5. Step 2 – Choose Appropriate Input Types

Input Type Typical Use
text Name or general text.
email Email address with browser syntax validation.
password Password input with masked characters.
tel Telephone number.
checkbox Remember me or terms acceptance.
submit Form submission control.

The name attribute identifies submitted form data. A control without a name is generally not included in the form's submitted data.

6. Step 3 – Use HTML Constraint Validation

<input
    type="email"
    name="email"
    required
>

<input
    type="password"
    name="password"
    required
    minlength="8"
>

<input
    type="text"
    name="username"
    required
    minlength="3"
    maxlength="30"
>

Common validation attributes

Attribute Purpose
required Makes a control mandatory.
minlength Sets the minimum text length.
maxlength Sets the maximum text length.
min and max Set numeric or date range limits where supported.
pattern Specifies a regular expression constraint.
type="email" Checks whether the entered value has valid email syntax.
Browser validation does not verify that an email address exists or belongs to the user. It also does not provide security against malicious requests. Always validate data on the server.

8. Step 5 – Style Labels and Inputs

.form-group {
    margin-bottom: 18px;

    display: block;
    margin-bottom: 7px;

}

.form-group input {
    width: 100%;
    padding: 12px;

}

.form-group input:focus {
    outline: none;

}
When removing the default outline, provide a clear replacement focus indicator. The example uses a border change and a visible focus shadow.

9. Step 6 – Style Validation States

.form-group input:focus-visible {
    outline: 3px solid #8bbcff;
    outline-offset: 2px;
}

.form-group input:required:valid {
    border-color: #198754;
}

.form-group input:required:invalid:not(:placeholder-shown) {
    border-color: #dc3545;
}

The :valid and :invalid pseudo-classes represent the control's constraint validation state. The placeholder selector in this example helps avoid showing an invalid border before the user enters anything.

12. Expected Result

  • The login form appears initially.
  • The registration link switches to the registration form.
  • The Sign In link returns to the login form.
  • Required fields are checked by browser validation.
  • Email fields use email syntax validation.
  • Password fields require at least eight characters in registration.
  • The registration form checks whether both passwords match.
  • The interface remains usable on narrow screens.
  • Keyboard focus is visible and moves to the new form after switching.
Successful frontend validation does not create an account or authenticate a user. The example prevents normal form submission for demonstration purposes. A real application needs secure server endpoints, password hashing, session management and appropriate protections against abuse.

13. Important Accessibility Practices

  • Every input should have a visible, associated label.
  • Use meaningful input types and autocomplete values.
  • Provide visible keyboard focus indicators.
  • Use descriptive error messages.
  • Associate help and error text with controls using aria-describedby when needed.
  • Do not rely only on color to communicate errors.
  • Use appropriate button types.
  • Make the form usable at browser zoom and narrow viewport widths.

Example: Associating an error message

<label for="email">Email Address</label>

<input
    type="email"
    id="email"
    name="email"
    aria-describedby="email-help"
    required
>

<small id="email-help">
    Enter a valid email address.
</small>

14. Common Problems and Debugging

Problem Possible Cause Correction
Input extends outside the card. Padding and width calculations. Use box-sizing: border-box.
Label does not focus its input. Incorrect for and id values. Match the label's for attribute to the input id.
Required field submits empty. Missing required attribute or disabled validation. Check required and form validation settings.
Email accepts malformed text. Input uses text instead of email. Use type="email".
Passwords do not match but form continues. No confirmation comparison. Compare both values before accepting the form.
Focus outline is not visible. Outline removed without replacement. Provide a visible focus style.
Form is too wide on mobile. Fixed width without a responsive maximum. Use width: 100% and max-width.

15. Placement Interview Questions

Q1. What is the purpose of the form element?

It groups controls for collecting and submitting user-provided information.

Q2. Why should labels be associated with inputs?

Labels provide accessible names and enlarge the clickable area when explicitly associated with controls.

Q3. What is the difference between GET and POST?

GET requests are intended to retrieve resources and commonly encode parameters in the URL. POST requests submit data in the request body. Neither method alone provides encryption; HTTPS is required for transport security.

Q4. What does the required attribute do?

It makes a form control mandatory for successful constraint validation.

Q5. What is the difference between type="text" and type="email"?

Email inputs provide email-oriented browser validation and input behavior. Text inputs accept general text.

Q6. What is autocomplete?

It gives the browser hints about the type of information a control expects, helping autofill work correctly.

Q7. What is the difference between disabled and readonly?

Disabled controls are generally not focusable and are not submitted with the form. Readonly controls can generally receive focus and their values are submitted when they have a name.

Q8. Does HTML validation replace backend validation?

No. Client-side validation can be bypassed. The server must validate submitted data independently.

Q9. How do you make a form responsive?

Use flexible widths, max-width, responsive spacing, Grid or Flexbox, and appropriate media queries.

Q10. How can you check whether two passwords match?

Compare their values in JavaScript before allowing the registration workflow to continue. The server must also enforce relevant rules.

18. Key Takeaways

  • Semantic HTML forms provide a structured input interface.
  • Labels should be explicitly associated with controls.
  • Input types improve browser behavior and validation.
  • CSS Grid and Flexbox simplify responsive form layouts.
  • Focus and validation states improve usability.
  • JavaScript can provide additional client-side feedback.
  • Server-side validation is mandatory for real authentication.
