Character Device Drivers

Learn how to create a basic Linux character device driver using kernel modules, device numbers, cdev and file operations.

1. Introduction to Character Device Drivers

A character device driver provides a byte-oriented interface between a userspace application and a device.

Applications commonly interact with character devices using file operations such as open(), read(), write() and close().

Examples

  • UART serial devices.
  • Terminal devices.
  • Some input devices.
  • Custom character devices.
  • Some embedded hardware interfaces.
Definition: A character device driver is a Linux kernel driver that exposes a byte-oriented device interface to userspace.

2. Character Device Driver Architecture

A userspace application accesses a device node. The kernel routes the file operations to the registered character-device driver. 

       User Application
              |
              v
         open()/read()
         write()/close()
              |
              v
        Device Node (/dev)
              |
              v
       Virtual File System
              |
              v
       Character Device Core
              |
              v
          Driver Callbacks
              |
              v
         Hardware Device

In this lesson, we build a simple character driver that stores data in a kernel buffer. It demonstrates the driver interface without accessing physical hardware.

3. Important Components

A. Device Number

Linux identifies a character device using a device number containing:

  • Major number — identifies a device-number registration or range.
  • Minor number — identifies an individual device instance.

B. struct cdev

The cdev structure represents a character device within the kernel.

C. struct file_operations

This structure defines the callbacks used when a process accesses the device.

D. Device Class and Device Node

A device class helps organize devices in the Linux device model. The device model can create a device node through userspace device management such as udev.

4. Important Kernel Functions

Function Purpose
alloc_chrdev_region() Allocates character-device numbers dynamically.
unregister_chrdev_region() Releases allocated device numbers.
cdev_init() Initializes a cdev structure.
cdev_add() Adds a character device to the kernel.
cdev_del() Removes a character device.
class_create() Creates a device class.
device_create() Creates a device-model entry.
device_destroy() Removes the device-model entry.
class_destroy() Destroys the device class.

5. struct file_operations

struct file_operations connects userspace file operations with driver callback functions.

Common Members

Member Purpose
.owner Associates operations with the owning module.
.open Called when the device is opened.
.read Called when data is read.
.write Called when data is written.
.release Called when the file is closed.
.unlocked_ioctl Handles device-specific control operations.

Example

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

The callbacks must use the kernel-defined function signatures.

6. User Space and Kernel Space Data Transfer

A kernel driver cannot safely treat userspace pointers as ordinary kernel memory pointers.

Linux provides special functions for copying data between userspace and kernel space.

copy_to_user()

Copies data from a kernel buffer to a userspace buffer. 

copy_to_user(user_buffer, kernel_buffer, length);

copy_from_user()

Copies data from a userspace buffer into a kernel buffer. 

copy_from_user(kernel_buffer, user_buffer, length);
These functions return the number of bytes that could not be copied, not a normal negative errno value. A driver should handle partial-copy failures correctly.

8. Practical Example: Simple Character Driver

We will create a simple character device named mychardev.

The driver will:

  • Register a character-device number.
  • Initialize and add a cdev structure.
  • Create a device class and device node.
  • Implement open(), read(), write() and release().
  • Store received data in a kernel buffer.
  • Send stored data back to userspace.
This is a learning example, not a production driver. It supports a single shared buffer and is not designed for concurrent access or complex device lifecycle management.

Step 1: Create a Project Directory

mkdir ~/char_driver
cd ~/char_driver

Step 2: Create Driver Source File

Filename: mychardev.c

#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/fs.h>
#include <linux/cdev.h>
#include <linux/device.h>
#include <linux/uaccess.h>
#include <linux/string.h>

#define DEVICE_NAME "mychardev"
#define CLASS_NAME  "mycharclass"
#define BUFFER_SIZE 256

static dev_t dev_number;
static struct cdev my_cdev;
static struct class *my_class;
static struct device *my_device;

static char device_buffer[BUFFER_SIZE];
static size_t data_size;

static int my_open(struct inode *inode,
                   struct file *file)
{
    pr_info("mychardev: device opened\n");
    return 0;
}

static int my_release(struct inode *inode,
                      struct file *file)
{
    pr_info("mychardev: device closed\n");
    return 0;
}

static ssize_t my_read(struct file *file,
                       char __user *user_buffer,
                       size_t count,
                       loff_t *offset)
{
    size_t available;
    size_t bytes_to_copy;

    if (*offset >= data_size)
        return 0;

    available = data_size - *offset;

    bytes_to_copy = count;
    if (bytes_to_copy > available)
        bytes_to_copy = available;

    if (copy_to_user(user_buffer,
                     device_buffer + *offset,
                     bytes_to_copy))
    {
        return -EFAULT;
    }

    *offset += bytes_to_copy;

    pr_info("mychardev: read %zu bytes\n",
            bytes_to_copy);

    return bytes_to_copy;
}

static ssize_t my_write(struct file *file,
                        const char __user *user_buffer,
                        size_t count,
                        loff_t *offset)
{
    size_t bytes_to_copy;

    bytes_to_copy = count;

    if (bytes_to_copy > BUFFER_SIZE)
        bytes_to_copy = BUFFER_SIZE;

    if (copy_from_user(device_buffer,
                       user_buffer,
                       bytes_to_copy))
    {
        return -EFAULT;
    }

    data_size = bytes_to_copy;
    *offset = 0;

    pr_info("mychardev: wrote %zu bytes\n",
            bytes_to_copy);

    return bytes_to_copy;
}

static const struct file_operations my_fops = {
    .owner   = THIS_MODULE,
    .open    = my_open,
    .read    = my_read,
    .write   = my_write,
    .release = my_release,
};

static int __init my_driver_init(void)
{
    int ret;

    pr_info("mychardev: initializing\n");

    ret = alloc_chrdev_region(
        &dev_number, 0, 1, DEVICE_NAME);

    if (ret < 0)
    {
        pr_err("Failed to allocate device number\n");
        return ret;
    }

    cdev_init(&my_cdev, &my_fops);
    my_cdev.owner = THIS_MODULE;

    ret = cdev_add(&my_cdev, dev_number, 1);

    if (ret < 0)
    {
        pr_err("Failed to add cdev\n");
        goto error_unregister;
    }

    my_class = class_create(CLASS_NAME);

    if (IS_ERR(my_class))
    {
        ret = PTR_ERR(my_class);
        goto error_cdev;
    }

    my_device = device_create(
        my_class,
        NULL,
        dev_number,
        NULL,
        DEVICE_NAME
    );

    if (IS_ERR(my_device))
    {
        ret = PTR_ERR(my_device);
        goto error_class;
    }

    pr_info("mychardev: registered successfully\n");

    return 0;

error_class:
    class_destroy(my_class);

error_cdev:
    cdev_del(&my_cdev);

error_unregister:
    unregister_chrdev_region(dev_number, 1);

    return ret;
}

static void __exit my_driver_exit(void)
{
    device_destroy(my_class, dev_number);
    class_destroy(my_class);
    cdev_del(&my_cdev);
    unregister_chrdev_region(dev_number, 1);

    pr_info("mychardev: removed\n");
}

module_init(my_driver_init);
module_exit(my_driver_exit);

MODULE_LICENSE("GPL");
MODULE_AUTHOR("NS Learning Hub");
MODULE_DESCRIPTION("Simple Character Device Driver");
MODULE_VERSION("1.0");
Kernel API compatibility: This example uses the one-argument class_create() interface found in Linux 6.4 and newer. Older kernels use a different signature. Check your kernel headers before compiling.

Step 3: Create the Makefile

Filename: Makefile

obj-m += mychardev.o

all:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) modules

clean:
	make -C /lib/modules/$(shell uname -r)/build M=$(PWD) clean

Step 4: Compile the Driver

make

If compilation succeeds, a kernel module named mychardev.ko should be generated.

Step 5: Load the Driver

sudo insmod mychardev.ko

Step 6: Check Kernel Messages

sudo dmesg | tail -n 20

Step 7: Check Device Node

ls -l /dev/mychardev

The device node should normally be created through the device model and userspace device management.

Step 8: Write Data to the Device

echo -n "Hello from userspace" | sudo tee /dev/mychardev

Step 9: Read Data from the Device

sudo cat /dev/mychardev

Expected data:

Hello from userspace

Step 10: Unload the Driver

sudo rmmod mychardev

Step 11: Clean Build Files

make clean

9. Understanding the Driver Source Code

alloc_chrdev_region()

Allocates a dynamic major/minor number range for the driver.

cdev_init()

Associates the cdev object with the file_operations structure.

cdev_add()

Makes the character device available to the kernel's character-device system.

class_create()

Creates a device class in the Linux device model.

device_create()

Creates a device-model entry. With suitable devtmpfs and userspace device management, a device node appears in /dev.

copy_from_user()

Copies userspace data into the driver's kernel buffer.

copy_to_user()

Copies kernel-buffer data to userspace.

module_init() and module_exit()

Define the initialization and cleanup functions for the loadable kernel module.

10. Important Limitations of the Example

  • The driver uses a single global buffer.
  • It does not implement locking for concurrent access.
  • It does not implement non-blocking I/O.
  • It does not implement poll or asynchronous notification.
  • It does not communicate with physical hardware.
  • It does not provide a device-specific ioctl interface.
Kernel code executes with high privilege. A driver bug can crash the entire system. Test experimental modules in a disposable virtual machine and keep important data backed up.

11. Troubleshooting

Problem 1: Kernel Headers Not Found

Check:

uname -r

ls -l /lib/modules/$(uname -r)/build

Install the matching kernel headers if they are available for your kernel.

Problem 2: Module Insertion Failed

Inspect:

sudo dmesg | tail -n 30

Check for kernel-version mismatch, invalid module format, unresolved symbols or module-signing restrictions.

Problem 3: Device Node Not Found

Check:

ls -l /dev/mychardev

ls -l /sys/class/mycharclass/

Check the kernel messages and whether devtmpfs and userspace device management are functioning.

Problem 4: Module Is Busy

Close applications that have the device open before attempting to unload the module.

13. Interview Questions and Answers

Q1. What is a character device driver?

It is a kernel driver that provides a byte-oriented interface to userspace.

Q2. What is struct cdev?

It represents a character device in the Linux kernel.

Q3. What is struct file_operations?

It defines callbacks for operations such as open, read, write and release.

Q4. What is alloc_chrdev_region()?

It dynamically allocates a range of character-device numbers.

Q5. What is cdev_add()?

It adds a character device to the kernel's character-device system.

Q6. What is device_create()?

It creates a device-model entry associated with a device number.

Q7. Why is copy_to_user() required?

It safely copies data from kernel memory to userspace.

Q8. Why is copy_from_user() required?

It safely copies data from userspace into kernel memory.

Q9. What is the purpose of cdev_del()?

It removes the character device from the kernel's character-device system.

Q10. What is the purpose of class_create()?

It creates a class in the Linux device model.

Q11. What does module_init() do?

It identifies the module initialization function.

Q12. What does module_exit() do?

It identifies the module cleanup function.

Q13. What is the difference between a major and minor number?

The major number identifies a device-number registration or range. The minor number identifies a device instance within that range.

Q14. Why should kernel drivers be tested carefully?

Kernel drivers execute in privileged context, so errors can affect the stability of the entire system.
