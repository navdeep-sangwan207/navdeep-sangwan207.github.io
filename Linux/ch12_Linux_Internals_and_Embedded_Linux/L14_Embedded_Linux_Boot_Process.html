Embedded Linux Boot Process

Understand how an embedded processor starts, initializes hardware, loads the Linux kernel and launches user applications.

1. Introduction to the Embedded Linux Boot Process

The Embedded Linux boot process is the sequence of operations performed when an embedded device is powered on or reset.

During this process, the processor initializes essential hardware, executes boot firmware, loads the Linux kernel, mounts the root filesystem and starts user-space applications.

Definition: The boot process is the sequence of initialization and loading operations that makes an embedded Linux system ready to execute applications.

2. Complete Embedded Linux Boot Sequence

A typical embedded Linux boot sequence is:

          Power ON / Reset
                  |
                  v
          Processor Reset State
                  |
                  v
        Boot ROM / Initial Firmware
                  |
                  v
          First-Stage Bootloader
                  |
                  v
         Second-Stage Bootloader
              (e.g. U-Boot)
                  |
                  v
          Load Linux Kernel
                  |
                  v
       Load Device Tree Blob (DTB)
                  |
                  v
          Linux Kernel Startup
                  |
                  v
       Hardware and Driver Init
                  |
                  v
          Mount Root Filesystem
                  |
                  v
          Start Init Process
             (PID 1)
                  |
                  v
       Start Services and Daemons
                  |
                  v
        Embedded Applications

This is a general model. The exact stages depend on the processor, firmware, bootloader and board design.

3. Stage 1: Power-On and Processor Reset

When power is applied, the processor enters its reset state.

Typical initial operations include:

  • Processor reset sequence.
  • Selection of the reset entry point.
  • Execution of initial firmware or Boot ROM.
  • Basic processor and platform initialization.

The processor begins execution from an architecture- and platform-defined reset address or boot location.

Important Concept: Boot ROM

Boot ROM is firmware stored in non-volatile memory inside the processor or SoC. It is generally provided by the chip manufacturer.

It may perform operations such as:

  • Checking boot configuration.
  • Selecting a boot device.
  • Loading initial boot firmware.
  • Performing secure boot verification.
Boot ROM is different from the Linux kernel. It executes before the operating system is loaded.

4. Stage 2: First-Stage Bootloader

Some embedded platforms use a first-stage bootloader (FSBL) to perform early hardware initialization.

Its responsibilities may include:

  • Initializing clocks.
  • Configuring pin multiplexing.
  • Initializing DRAM.
  • Setting up essential hardware.
  • Loading or transferring control to the next stage.

In many systems, external RAM must be initialized before larger software components can be loaded into it.

Not every embedded processor uses a separate first-stage bootloader. Some systems combine early initialization and later bootloader functionality.

5. Stage 3: Second-Stage Bootloader (U-Boot)

U-Boot (Universal Boot Loader) is a widely used open-source bootloader in embedded Linux systems.

It provides an environment for initializing hardware, selecting boot sources, loading the kernel and passing boot parameters.

Important U-Boot Responsibilities

  • Initialize additional hardware.
  • Access storage devices.
  • Load the Linux kernel into memory.
  • Load the Device Tree Blob.
  • Set kernel command-line parameters.
  • Transfer execution to the kernel.

Common U-Boot Commands

Command Purpose
help Displays available commands.
printenv Displays environment variables.
setenv Sets an environment variable.
saveenv Saves environment variables when supported.
bdinfo Displays board information.
bootcmd Environment variable containing the default boot command.
bootz Boots a supported compressed ARM Linux zImage.
booti Boots a supported ARM64 Linux Image.

Example U-Boot Commands

printenv
bdinfo
help

The commands available depend on the U-Boot build and target platform.

6. Stage 4: Loading the Linux Kernel

The bootloader loads the Linux kernel image from a boot source such as:

  • eMMC storage.
  • SD card.
  • NAND or NOR flash.
  • USB storage.
  • Network boot server.

The kernel image is placed at an appropriate memory address according to the platform's boot requirements.

Common Kernel Image Types

Image Description
Image Common ARM64 Linux kernel image.
zImage Self-decompressing compressed kernel image commonly used on 32-bit ARM.
uImage Legacy U-Boot image format with a header.
FIT Flattened Image Tree container for one or more boot components.
The correct image format and boot command depend on the processor architecture, bootloader configuration and kernel build.

7. Stage 5: Device Tree Blob (DTB)

A Device Tree describes hardware information that the Linux kernel needs to understand the target board.

The Device Tree Source file normally uses the .dts extension. It is compiled into a Device Tree Blob with the .dtb extension.

Why Is Device Tree Required?

  • Describes CPU and memory information.
  • Describes peripheral devices.
  • Provides hardware addresses and interrupts.
  • Describes buses and connected components.
  • Provides information used by device drivers.

Example Device Tree Source

/dts-v1/;

/ {
    compatible = "example,my-board";
    model = "Example Embedded Board";

    memory@80000000 {
        device_type = "memory";
        reg = <0x80000000 0x10000000>;
    };
};

This is only an illustrative fragment. A real board Device Tree requires architecture-specific and hardware-specific information.

Compile a Device Tree

dtc -I dts -O dtb -o board.dtb board.dts

The Device Tree Compiler (dtc) converts Device Tree Source into a binary blob.

8. Stage 6: Linux Kernel Initialization

After the bootloader transfers control, the Linux kernel begins its startup process.

Major kernel initialization activities include:

  • Early processor and architecture setup.
  • Memory management initialization.
  • Interrupt handling initialization.
  • Scheduler initialization.
  • Kernel subsystem initialization.
  • Device driver initialization.
  • Root filesystem preparation.

Kernel Initialization Flow

       Kernel Entry Point
               |
               v
       Early Architecture Setup
               |
               v
       Memory Initialization
               |
               v
       Interrupt Initialization
               |
               v
       Kernel Subsystem Setup
               |
               v
       Driver Initialization
               |
               v
       Mount Root Filesystem
               |
               v
       Start Initial User Space

Kernel initialization is more complex than a simple strictly linear sequence: many initialization operations depend on architecture, configuration and subsystem ordering.

9. Stage 7: Root Filesystem Mounting

The root filesystem contains the userspace environment required by Linux to run programs and services.

Typical Root Filesystem Directories

/
|
+-- bin/
+-- dev/
+-- etc/
+-- home/
+-- lib/
+-- proc/
+-- root/
+-- run/
+-- sbin/
+-- sys/
+-- tmp/
+-- usr/
+-- var/

Common Root Filesystem Storage Types

  • EXT4 filesystem on eMMC or SD card.
  • SquashFS for compressed, commonly read-only root filesystems.
  • UBIFS on suitable NAND flash configurations.
  • Initramfs stored or supplied in memory.
  • Network root filesystem in supported configurations.

What Is Initramfs?

Initramfs is an early userspace filesystem archive that the kernel can unpack and use during boot.

It can contain utilities and scripts needed to discover storage, load modules, unlock encrypted devices or mount the final root filesystem.

An initramfs is not the same as the permanent root filesystem. It may be used temporarily before the real root filesystem is mounted.

10. Stage 8: Init Process and PID 1

Once the root filesystem is available, the kernel starts the initial userspace process, normally with Process ID 1.

The initial process is commonly called init.

Common Init Systems

Init System Description
systemd Service and system manager used by many Linux distributions.
BusyBox init Lightweight init implementation often used in small embedded systems.
SysVinit Traditional Unix-style initialization system.

Responsibilities of Init

  • Starts system services.
  • Runs initialization scripts.
  • Sets up the system environment.
  • Starts required background processes.
  • Manages the transition to the operational state.

Check PID 1 in Linux

ps -p 1 -o pid,comm,args

This command displays information about the initial process.

11. Stage 9: Services and Application Startup

After the init process starts, the system launches the required services and application programs.

Examples include:

  • Network initialization.
  • Logging services.
  • Device management.
  • Communication services.
  • Industrial control applications.
  • Monitoring and diagnostic applications.

Example Linux Commands

ps aux
uptime
systemctl list-units --type=service

The systemctl command applies to systems using systemd. Other embedded systems may use different service management mechanisms.

12. Kernel Command-Line Parameters

The bootloader can pass parameters to the kernel through the kernel command line.

Common parameters include:

Parameter Purpose
console= Selects a kernel console device.
root= Identifies the root filesystem device or location.
rootwait Waits for the root device to become available.
ro Requests mounting the root filesystem read-only initially.
rw Requests mounting the root filesystem read-write.
init= Specifies an alternative initial userspace program.
quiet Reduces some kernel console messages.
loglevel= Controls the kernel console log level.

Example Kernel Command Line

console=ttyS0,115200 root=/dev/mmcblk0p2 \
rootwait rw

This is an illustrative example. The console device and root partition must match the actual target board.

Inspect Kernel Command Line

cat /proc/cmdline

13. Embedded Linux Boot Troubleshooting

Boot failures can occur at different stages. Identifying the last successful stage helps narrow down the problem.

Problem Possible Cause
No boot output Power, reset, clock, boot mode or serial console issue.
Bootloader not starting Invalid boot media, firmware or boot configuration.
Kernel not loading Incorrect image, memory address or boot command.
Kernel panic Kernel configuration, driver or hardware issue.
Unable to mount root filesystem Wrong root device, missing driver or invalid filesystem.
Init process failure Missing or invalid init executable or userspace files.
Application not starting Missing libraries, configuration or service startup failure.

Useful Diagnostic Commands

dmesg
dmesg | less
cat /proc/cmdline
lsblk
mount
df -h
ps aux
Always capture the complete serial console log during embedded boot debugging. It often identifies the last successful initialization stage.

14. Embedded Linux Boot Time Optimization

Many embedded products require predictable and reasonably fast startup. Boot time can be improved by examining each boot stage.

Common Optimization Techniques

  • Remove unnecessary kernel features and drivers.
  • Reduce unnecessary bootloader delays.
  • Initialize only required hardware.
  • Reduce unnecessary startup services.
  • Use suitable storage and filesystem configurations.
  • Start independent services in parallel where supported.
  • Measure boot time before and after changes.

systemd Boot Analysis

systemd-analyze
systemd-analyze blame
systemd-analyze critical-chain

These commands are available on systemd-based systems and help identify slow startup services and dependencies.

16. Interview Questions and Answers

Q1. What is the Embedded Linux boot process?

It is the sequence of operations that initializes hardware, loads the kernel, mounts the root filesystem and starts user-space applications.

Q2. What is Boot ROM?

Boot ROM is early firmware stored in non-volatile memory in a processor or SoC.

Q3. What is a bootloader?

A bootloader initializes required hardware and loads the operating-system kernel.

Q4. What is U-Boot?

U-Boot is an open-source bootloader widely used in embedded systems.

Q5. What is a Device Tree?

It is a data structure that describes hardware information to the Linux kernel.

Q6. What is a DTB file?

A DTB is a compiled binary Device Tree Blob generated from Device Tree Source.

Q7. What is the root filesystem?

It contains the userspace files, libraries, utilities and applications needed by Linux.

Q8. What is init?

Init is the initial userspace process, normally PID 1, responsible for starting system services and processes.

Q9. What is initramfs?

It is an early userspace filesystem archive used during kernel startup.

Q10. What is the purpose of rootwait?

It tells the kernel to wait for the specified root device to become available.

Q11. What is a kernel panic?

A kernel panic is a serious kernel failure from which the system cannot safely continue normal operation.

Q12. How can Embedded Linux boot time be reduced?

By removing unnecessary startup work, optimizing hardware initialization, reducing service dependencies and measuring boot performance.
