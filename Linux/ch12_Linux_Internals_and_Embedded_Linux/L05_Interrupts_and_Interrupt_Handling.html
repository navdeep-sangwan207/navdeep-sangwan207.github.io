Interrupts and Interrupt Handling

Understand how Linux responds to hardware events, processes interrupt requests and manages interrupt handling efficiently.

1. Introduction to Interrupts

An interrupt is a signal or event that causes the processor to temporarily suspend its current execution flow and transfer control to an interrupt-handling mechanism.

Interrupts allow the processor to respond to important events without continuously checking every hardware device.

Definition: An interrupt is an event that requests processor attention and causes execution to be redirected to an appropriate interrupt handler.

Examples of Interrupt Events

  • Keyboard key press.
  • Mouse movement or button click.
  • Network packet arrival.
  • Timer expiration.
  • Storage device completion notification.
  • Hardware error notification.

2. Why Are Interrupts Required?

Consider a keyboard connected to a computer. The CPU needs to know when a key is pressed.

Without an interrupt mechanism, the processor could repeatedly check the keyboard status. This approach is called polling.

With interrupts, the keyboard controller can notify the processor when an event occurs.

Advantages of Interrupts

  • Reduce unnecessary continuous polling.
  • Improve processor utilization.
  • Support asynchronous hardware events.
  • Enable efficient device communication.
  • Improve responsiveness to external events.

3. Interrupt vs Polling

Interrupt Polling
Device notifies the processor about an event. Processor repeatedly checks device status.
Can reduce unnecessary CPU work. May waste CPU time checking inactive devices.
Event-driven mechanism. Repeated checking mechanism.
Requires interrupt handling support. Requires periodic or continuous status checks.

Polling Example

while (1)
{
    if (device_status == READY)
    {
        process_device_data();
    }
}

Interrupt-Based Concept

void interrupt_handler(void)
{
    process_device_event();
}

The second example is conceptual C code. Actual interrupt handlers depend on the processor architecture and operating system.

4. Types of Interrupts

4.1 Hardware Interrupts

Hardware interrupts are generated by external hardware devices or interrupt controllers.

Examples:

  • Keyboard interrupt.
  • Timer interrupt.
  • Network interface interrupt.
  • USB device interrupt.

4.2 Software Interrupts

Software-generated events cause execution to enter a defined exception or interrupt mechanism.

Software interrupts have historically been used for system services and controlled transitions into privileged execution.

On modern Linux systems, system calls commonly use architecture-specific instructions such as syscall on x86-64 or SVC on ARM. Do not assume that every system call is implemented as a traditional hardware IRQ.

4.3 Processor Exceptions

Exceptions are synchronous events generated while an instruction is executing.

Examples include:

  • Division by zero.
  • Invalid instruction.
  • Page fault.
  • Memory access violation.

5. Interrupt Request (IRQ)

IRQ stands for Interrupt Request. It represents an interrupt request associated with a hardware device or interrupt source.

When a device generates an interrupt, the interrupt controller routes or prioritizes the request according to the system architecture.

Common IRQ-Related Concepts

  • Interrupt source: device or hardware event.
  • IRQ number: identifier used by the interrupt subsystem.
  • Interrupt controller: manages interrupt routing and priority.
  • Interrupt handler: code that handles an interrupt.
IRQ numbers are architecture- and platform-dependent. Modern systems may use interrupt controllers such as APIC or GIC, and devices may use MSI/MSI-X rather than traditional fixed interrupt lines.

6. Interrupt Service Routine (ISR)

An Interrupt Service Routine (ISR) is a function or handler that executes in response to an interrupt.

In Linux device-driver development, the interrupt handler is commonly registered using request_irq() or related APIs.

Basic Interrupt Handling Flow

  1. A hardware device generates an interrupt.
  2. The interrupt controller identifies the source.
  3. The processor enters the appropriate interrupt context.
  4. The Linux interrupt subsystem dispatches the handler.
  5. The handler performs essential immediate work.
  6. Deferred work may be scheduled if additional processing is required.
  7. Interrupt handling completes and normal execution resumes.

7. Interrupt Handler in Linux

Linux device drivers register interrupt handlers through kernel interrupt-management APIs.

Important Function: request_irq()

The request_irq() function registers an interrupt handler for a specified IRQ.

General Syntax

int request_irq(
    unsigned int irq,
    irq_handler_t handler,
    unsigned long flags,
    const char *name,
    void *dev
);

Parameters

Parameter Description
irq Interrupt number.
handler Function called when the interrupt is handled.
flags Interrupt configuration flags.
name Name used to identify the interrupt.
dev Device-specific identifier or pointer.

Important Related Function

free_irq(irq, dev);

free_irq() releases an interrupt registration. The dev argument must match the value used when registering the handler.

8. Conceptual Linux Interrupt Handler Example

The following example illustrates the structure of a Linux interrupt handler. It is not a standalone driver and must not be compiled or loaded without a real device and correctly configured interrupt source. 

#include <linux/module.h>
#include <linux/interrupt.h>

static irqreturn_t my_interrupt_handler(
    int irq,
    void *dev_id)
{
    pr_info("Interrupt received: IRQ %d\n", irq);

    return IRQ_HANDLED;
}

Explanation

  • irqreturn_t is the interrupt handler return type.
  • irq identifies the interrupt being handled.
  • dev_id identifies the device associated with the handler.
  • pr_info() writes a message to the kernel log.
  • IRQ_HANDLED indicates that the interrupt was handled.
Never request an arbitrary IRQ number on your Ubuntu VM just to test this example. A real driver must obtain the correct IRQ from its device and platform configuration.

9. Top Half and Bottom Half

Interrupt processing is divided conceptually into immediate work and deferred work.

9.1 Top Half

The top half is the immediate interrupt handler. It executes in interrupt context.

Typical responsibilities:

  • Identify the interrupt source.
  • Acknowledge or clear the device interrupt.
  • Capture essential device status.
  • Schedule deferred processing when required.

9.2 Bottom Half

The bottom half performs work deferred from the immediate interrupt handler.

Linux provides several deferred-processing mechanisms:

  • Softirqs
  • Tasklets (legacy mechanism; newer code generally prefers other mechanisms)
  • Workqueues
  • Threaded IRQ handlers
Top Half Deferred Processing
Runs in interrupt context. Runs later through a suitable deferred mechanism.
Must complete quickly. Can handle more processing.
Cannot sleep. Workqueues and threaded handlers can sleep.
Handles urgent interrupt work. Handles non-immediate work.

10. Softirqs

Softirqs are a Linux mechanism for executing deferred work outside the immediate hardware interrupt handler.

They are used for performance-sensitive processing in parts of the kernel.

Examples of Softirq Usage

  • Network packet processing.
  • Timer-related processing.
  • Block I/O completion processing.

Softirq handlers execute in atomic context. They must not sleep.

11. Tasklets

Tasklets are a mechanism built on top of softirqs for scheduling deferred work.

They have historically been used in device drivers to defer processing from interrupt handlers.

Tasklets are a legacy interface and are deprecated in newer Linux kernel development. For new driver designs, consider threaded IRQs, workqueues or other appropriate mechanisms.

12. Workqueues

Workqueues allow kernel work to execute in process context through worker threads.

Advantages

  • Can perform operations that may sleep.
  • Useful for lengthy deferred processing.
  • Can interact with mutex-protected resources.
  • Support asynchronous kernel tasks.

Common Workqueue APIs

INIT_WORK()
schedule_work()
flush_work()
cancel_work_sync()

The exact API and lifecycle depend on the kernel version and driver design.

13. Threaded Interrupt Handlers

Linux supports threaded interrupt handlers. They separate a short primary interrupt handler from a handler that executes in a kernel thread.

This approach is useful when interrupt processing needs operations that may sleep.

Common Registration API

request_threaded_irq()

The primary handler runs in interrupt context. The threaded handler runs in thread context.

14. Interrupt Context Restrictions

Interrupt context has stricter execution rules than normal process context.

Important Restrictions

  • Do not call functions that may sleep in a hard IRQ handler.
  • Avoid lengthy processing.
  • Do not perform blocking I/O.
  • Use suitable synchronization primitives.
  • Defer lengthy work to an appropriate mechanism.
Calling a sleeping function from an inappropriate interrupt context can cause kernel warnings, deadlocks or system instability.

15. Viewing Interrupt Information in Linux

Linux exposes useful interrupt information through the proc filesystem.

View Interrupt Statistics

cat /proc/interrupts

This file shows interrupt counts and associated device or interrupt-controller information.

Monitor Interrupt Statistics

watch -n 1 cat /proc/interrupts

This refreshes the output every second. Press Ctrl+C to stop.

View Softirq Statistics

cat /proc/softirqs

View Kernel Messages

sudo dmesg | tail -n 30
Interrupt names and counts depend on the hardware, kernel configuration and virtual machine environment. Your Ubuntu VM output will not necessarily match another computer.

16. Interrupt Handling in Embedded Systems

Interrupts are essential in embedded systems because microcontrollers frequently respond to external events in real time.

Examples

  • Timer interrupt for periodic scheduling.
  • UART interrupt for received data.
  • GPIO interrupt for a button press.
  • ADC interrupt when conversion completes.
  • External interrupt from a sensor.

Example: UART Receive Interrupt

When a UART peripheral receives a character, it can generate an interrupt. The ISR reads the received data and stores it in a buffer for further processing. 

void UART_IRQHandler(void)
{
    /* Read UART status and received data. */
    /* Store data in a receive buffer. */
    /* Clear or acknowledge the interrupt as required. */
}

This is conceptual code. Actual register operations depend on the microcontroller.

Embedded Linux Relevance

In Embedded Linux, device drivers use the kernel interrupt subsystem to handle hardware events from UART, SPI, I2C, GPIO, network controllers and other peripherals.

18. Interview Questions and Answers

Q1. What is an interrupt?

An interrupt is an event that requests processor attention and redirects execution to an appropriate handler.

Q2. Why are interrupts used?

They allow the processor to respond to events without continuously polling every device.

Q3. What is an IRQ?

IRQ stands for Interrupt Request. It identifies an interrupt source within the interrupt system.

Q4. What is an ISR?

An Interrupt Service Routine is the handler responsible for responding to an interrupt.

Q5. What is the difference between polling and interrupts?

Polling repeatedly checks device status, while interrupts notify the processor when an event occurs.

Q6. What is request_irq()?

It registers an interrupt handler for a specified interrupt source.

Q7. What is free_irq()?

It releases a previously registered interrupt handler.

Q8. What is a top half?

It is the immediate interrupt-handling portion that executes in interrupt context.

Q9. What is a bottom half?

It is deferred processing performed after the immediate interrupt handler.

Q10. What is a softirq?

A softirq is a Linux mechanism for executing deferred kernel processing in a non-sleeping context.

Q11. What is a workqueue?

A workqueue schedules kernel work to execute in process context using worker threads.

Q12. Can an interrupt handler sleep?

A hard IRQ handler must not sleep. Deferred mechanisms such as workqueues or threaded handlers can perform sleepable operations.

Q13. Which file displays interrupt statistics?

/proc/interrupts

Q14. Which file displays softirq statistics?

/proc/softirqs

  • The top half performs immediate interrupt processing.
  • Deferred processing handles work that should not be performed immediately.
